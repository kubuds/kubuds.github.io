I. Kernel and Version Dynamics

1.1 Nested user-pointer hardening for getaddrinfo merged: a single snapshot replaces layered validation (11-03)

Date: 2026-11-03 09:04 (merge time)　Source: PR #11977

The maintainer rework reported in the previous issue was merged at the start of this window: 57 lines added, 17 removed, touching only syscall_netdb.c under the network syscall directory.

The flaw in the original implementation was layered validation: only the top-level res buffer passed in by the user was checked, after which the resolved socket address was written through res->ai_addr, a user-controlled nested pointer—under Smart/MMU builds this turned a single getaddrinfo() into an arbitrary kernel write. The hints fields were still read directly from user memory after the top-level check passed, leaving a TOCTOU window in between. The return-value check on the servname copy was also wrong—comparing a size_t against 0, which is always false.

The fix uses lwp_get_from_user() to copy res and hints into a temporary kernel structure in one shot, after which all nested pointers come from this validated snapshot; nested sockaddrs and the outer addrinfo are written back uniformly with lwp_put_to_user(), with the target address range validated by the existing helper, so the kernel no longer dereferences unchecked user pointers. Along the way, the kernel addrinfo is allocated by sizeof(*k_hints), and k_res is freed on the newly added error paths.

The value of this change is not in the line count but in the pattern it demonstrates: for nested user pointers, layered validation has an inherent TOCTOU gap, and a one-shot snapshot is the provably safe path. The author notes in the PR that verification consisted only of compiling syscall_netdb.o under the K230 RT-Smart configuration, with the full build left to CI, and no user-mode privilege-escalation reproduction.

1.2 DM365 SPI prescaler divide-by-zero triggered when max_hz is 0 (11-03)

Date: 2026-11-03 13:11 (merge time)　Source: PR #11957, Issue #11950

6 lines added, touching only bsp/dm365/drivers/spi-davinci.c—the smallest change in this window.

davinci_spi_setup_transfer() passes cfg->max_hz straight to davinci_spi_get_prescale(), which computes DIV_ROUND_UP(clk_get_rate(dspi->clk), max_speed_hz). If max_hz is 0 in the configuration and the data width is valid, this division lands on zero and faults immediately. The fix checks max_hz == 0 before computing the prescaler and returns -RT_EINVAL; the non-zero-rate path is untouched.

The verification conditions are stated honestly: no DM365 hardware was available, so only two things were done—compiling bsp/dm365/drivers/spi-davinci.c with arm-none-eabi-gcc produced no new warnings; and replicating the width check and prescaler logic on the host side, data_width = 9, max_hz = 0 produced SIGFPE before the change and returns -RT_EINVAL after, while the prescaler result at 1 MHz matches the pre-change behavior. DM365 is an old TI ARM9 platform, and BSPs like this have almost no test coverage; adding the divide-by-zero guard is already a net gain.

1.3 mailbox test case always fails on second run: four completion flags never cleared (11-03)

Date: 2026-11-03 10:53 (merge time)　Source: PR #11963, Issue #6565

11 lines added, touching only src/utest/mailbox_tc.c.

The symptom is that running core.ipc_mailbox a second time within the same boot always fails: the first run passes, and the second triggers an assertion failure rt_object_get_type(...) == RT_Object_Class_MailBox in the receiving thread, at _rt_mb_recv() line 2884. The root cause is that the four *_thread_finish flags are only ever set to 1 by the worker threads and never cleared; on the second run the test body’s wait loop while (static_mb_recv_thread_finish != 1 || ...) falls straight through, so rt_mb_detach() is called while the worker thread started in this round is still blocked in rt_mb_recv() and has not yet exited; the thread then resumes with an error and continues using a mailbox that has already been detached. The dynamic-mailbox half has the same shape, just never triggered separately.

The fix clears the flags in utest_tc_init(), a hook the utest framework calls before each test case run. Issue #6565 is an old ticket opened in 2021; this change fixes the remaining half of it.

1.4 Macro comments at end of line or above: coding style gains a section of criteria (11-03)

Date: 2026-11-03 09:48 (merge time)　Source: PR #11973, Issue #10097

72 lines added, all in documentation: 32 lines in coding_style_cn.md and 40 in coding_style_en.md, each adding a “Macro Comments” subsection to Section 8, with no code changes.

The original style guide only said “statement comments may only be placed above or to the right of the code,” without saying which form macros should use or why, so both styles coexist in the same repository. The author surveyed the status quo before setting the rule: under include/, 135 macro comments use trailing /**<, of which 87 (64.4%) exceed 80 columns, with line 24 of kerrno.h at 95 columns—groups of constant macros deliberately keep column alignment and accept the overrun. So the criterion is not line length but “how much explanation is needed”: if one comment suffices, put it at end of line; if a paragraph is needed (parameterized macros, where inputs, expansion results, and usage constraints must be described), put it above with @def.

The documentation also adds a practical difference: with MACRO_EXPANSION enabled, a trailing /**< attaches to the macro’s expansion point, so when the same macro expands in multiple places the comment position may be unexpected; a block comment above always binds to the definition site. Therefore macros that expand frequently should prefer a block comment above. All examples are taken from real code in the repository (the error-code group in kerrno.h, RT_ALIGN in rtdef.h), not invented.

II. Security Follow-up and Merge Queue

2.1 timerfd accepts arbitrary fd: two system calls yield kernel PC control (11-04)

Date: 2026-11-04 01:08 (report time)　Source: Defect #11984

Reported by XueDugu, baseline master 5d1fb66d13 (v5.4.0-dev). The impact statement notes: affected since v5.0.2, introduced by 7c2f807a on 2023-09-23 (the timerfd system call merge, i.e. #8067).

The issue itself is short: timerfd_do_settime() and timerfd_do_gettime() fetch an arbitrary descriptor from the process fd table, then cast df->vnode->data directly to struct rt_timerfd * without verifying that the file is actually a timerfd. Linux has a file->f_op != &timerfd_fops check at the same spot that returns -EINVAL; RT-Thread has no equivalent. So the vnode->data of any user-reachable fd object gets treated as a timerfd: the kernel takes and releases a forged mutex inside a foreign object, writes the attacker-supplied itimerspec into it, then dereferences tfd->timer (a linked-list unlink plus rt_free on an arbitrary qword).

What is truly fatal is a negative it_value.tv_sec: it causes timerfd_timeout(tfd) to run synchronously, and its first statement rt_wqueue_wakeup(&tfd->timerfd_queue, POLLIN) walks the wait-queue head read from the confused object and calls entry->wakeup(entry, key) — an indirect function-pointer call where both the pointer and r0 come from attacker-chosen memory.

The report gives the full chain: on 32-bit RT-Thread, signalfd is the perfect confusion object — the first 128 bytes of its context are sigset_t sigmask, copied verbatim from a user pointer by signalfd() (NUL bytes allowed), enough to cover a forged timerfd header, including setting the rt_mutex type byte to the mutex type, leaving owner at 0 so the take succeeds immediately, and setting timerfd_queue.waiting_list.next. Because the RT-Smart kernel shares page tables with user space and dereferences user mappings directly, the forged wait-queue node can live in the attacker’s own user memory.

The reproduction environment is qemu-vexpress-a9 with a default RT_USING_SMART build (timerfd and signalfd are on by default under Smart), running a libc-free user-mode ELF as /sbin/init. The control group calling into a real timerfd returns 0 and the kernel survives; the attack group does signalfd(-1, mask, 0) plus timerfd_settime(sfd, 0, {it_value.tv_sec = -1}), producing a kernel prefetch abort with fully controlled PC, byte-for-byte identical across three runs, with r00:0x10000 visible in the registers. The conclusion: two unprivileged system calls, both official POSIX-style interfaces, are enough to achieve kernel control-flow hijacking.

2.2 POSIX timer id is unvalidated; console device can be overwritten on RT-Smart (11-03)

Date: 2026-11-03 12:35 (report time)　Source: Defect #11980

Same reporter, earlier the same day. timer_gettime() and timer_settime() use the user-supplied timer_t directly as an index: timer = _g_timerid[(rt_ubase_t)timerid], with no timerid < TIMER_ID_MAX check. The sibling function timer_delete() has that check, so this is not a design trade-off but an omission.

On an ordinary MCU build this is an out-of-bounds read; on RT-Smart it goes further — an attacker can pick a pointer that happens to sit next to _g_timerid and reinterpret the target kernel object as a struct timer_obj. The specific alias found in the QEMU image is index 0x35a5 (13733) pointing at _console_device: timer_settime() then overwrites fields of this live UART device with the attacker-controlled itimerspec, including rx_indicate and ops, so a single received UART byte jumps control flow to an attacker-specified address, running at EL1.

Hardware-side verification was also done: on a Pico 2 W (RP2350) built with the original ctime.c and resource_id.c, disassembly confirms the timer_settime() entry is ldr.w r6, [r5, r0, lsl #2]; running timer_oob with 0x20000000 computes the address as 0xa000202c, which is unmapped, and after the fault the USB CDC connection disappears or the shell stalls. The software baseline is likewise v5.4.0-dev, the introducing commit is 077e9841, and the first affected version is v5.0.2.

2.3 Arbitrary kernel write in block-device partition ioctl gets a proposal (11-03)

Date: 2026-11-03 15:51 (proposal time)　Source: Proposal #11981, Defect #11952

19 lines added, 5 removed, one file changed, author liangzhan5, proposal self-marked as draft.

The problem is in RT_DEVICE_CTRL_BLK_PARTITION: the command treats a raw pointer passed from user space as the destination of rt_memcpy, letting an unprivileged process achieve arbitrary kernel writes. There is a secondary flaw — err is not updated after rt_memcpy completes, so even when the ioctl ultimately returns -1, the target address has already been modified, and the error code does not match reality. The author also notes that commands such as RT_DEVICE_CTRL_BLK_GETGEOME may have the same class of problem.

The fix takes two paths: under RT_USING_LWP, use lwp_self() to determine whether the current context is user mode; if so, first copy the partition data to a temporary kernel-stack variable, then safely copy it back with lwp_put_to_user(), returning -EFAULT and performing no write when the pointer is invalid; for non-user (in-kernel) calls, keep the original rt_memcpy path and add err = RT_EOK. Verification only extends to compiling on qemu-vexpress-a9 and manual review.

The corresponding defect #11952 was opened on October 29 by the same reporter — 5 days from report to proposal.

4.3 Dual-MCU Disinfection Device: M7 Handles Motion, M3 Handles Spraying, Both Run RT-Thread (11-03)

Date: 2026-11-03 14:02 (push time)　Source: Repository: GD32

A competition project called “Jingxun Weishi” (Clean Patrol Guardian), an intelligent disinfection mobile device for small and medium public areas such as classrooms, corridors, and public seating. The architecture is dual-MCU: GD32H759IMT6 (Cortex-M7) as the motion main controller, STM32F103C8T6 (Cortex-M3) for spray control, both running RT-Thread 4.1.1.

The point of such projects isn’t technical difficulty but the engineering trade-off of “one M7 isn’t enough, add an M3 to share the load”: motion control demands real-time performance, while spraying and remaining-volume monitoring are slow variables. Splitting them leaves headroom on both chips, and the communication cost is covered by a single serial protocol.

V. Industry Applications

5.1 RV32IM Dual-Issue FPGA CPU Brings RT-Thread Nano into the CoreMark Verification Chain (11-03)

Date: 2026-11-03 20:58 (push time)　Source: Repository: RISC-V-CPU

An RV32IM pipelined CPU project targeting Xilinx Kintex-7, with the latest push updating the experiment entry point. On the CPU side: RV32IM instruction set, machine-mode CSRs and timer interrupts, a main execution channel plus an integer side channel supporting eligible dual-instruction pairing; the front end has BTB, RAS, and indirect jump prediction, while the memory side has dual-channel forwarding, load/store pairing, and cache-hit bypass.

The software side is where RT-Thread comes in: it runs RT-Thread Nano v3.1.5, with a UART command line and CoreMark 1.0, plus an optional cmcrc16 custom instruction. Target device is xc7k325tffg900-2, Vivado 2023.2.

The verification data is more detailed than typical hobby projects: with timingopt15 plus a 256-line DCache and an ideal 180 MHz clock, a 100-iteration CoreMark behavioral simulation yields 31,445,017 CPU cycles, 30,605,777 retired instructions, CPI 1.027421, a final CRC of 0x988c, and 7 directed regressions passing. Shortcomings are also stated: after routing at 180 MHz, WNS is -1.371 ns and WHS is +0.013 ns—timing has not converged and no bitstream has been generated; the 100-iteration simulation is only for functional and CPI comparison, and on-board frequency is subject to the implementation report.

For RT-Thread, the significance here is that Nano has once again been used as the minimal runnable software stack for CPU verification—exposing problems in interrupt, context-switch, and timer paths better than bare-metal tests.

VI. Trends and Summary for This Issue

6.1 Trends: On the security side, moving from reports to proposals; on the testing side, moving from checklists to code

In the 24 hours of this issue, 4 pull requests were merged into the main repository (#11977, #11973, #11963, #11957), 4 new proposals were opened (#11979, #11981, #11982, #11983), and 2 new defects were filed (#11980, #11984). The volume is on par with the previous issue, but the structure has changed: the previous issue was about clearing the backlog, while this issue is about opening new accounts and shoring up infrastructure.

The first thread is the two new security reports, which are highly consistent in shape—both are “descriptors or identifiers not type-checked.” timerfd does not check whether the fd is a timerfd, and the POSIX timer does not check whether the id is out of bounds; both entry points treat the user-supplied value directly as an entry pointing to a kernel object. Together with the previous issue’s graphics negative offset (user-supplied offset not sign-checked) and pipe (user pointer not validated), the four can be grouped into the same class: RT-Smart’s syscall layer lacks unified validation at the “value → object” step. The fixes for this class of defect are not complicated; the hard part is finding all the entry points.

The second thread is that response speed is increasing. #11952 was a block device partition arbitrary write reported on October 29, and by November 3 there was proposal #11981; yesterday’s getaddrinfo rework (#11977) was merged today; the pipe patch continues to be updated in the queue. The four stages—report, proposal, maintainer rework, and merge—can now be completed within a few days, a clear change from the previous issue’s assessment of “many reports, few patches.” The cost is that review pressure has shifted to the maintainers’ side—five items remain under review in the queue, and each requires someone to read and understand the reproduction steps.

The third thread is that the Z-version test checklist has begun producing code. #11972, reported in the previous issue, broke down “can the Z version ship” into per-framework QEMU and utest checklists, and this issue saw three proposals directly referencing it: an in-firmware virtual loopback bus for SPI (#11979), a simulated bus utest for the I2C framework (#11982), and #11983, which adds looping and memory sampling to automated runs (this one is a follow-up to #11963, solving the problem that “running only once cannot detect memory leaks”). Combined with today’s merged mailbox test case that can be run repeatedly, the testing foundation on the CI side is moving toward “repeatable and observable.”

On the ecosystem side, two moves in opposite directions are both worth watching: on one hand, a chip vendor is scripting batch releases of BSP repositories (HPMicro’s 12 repositories at the same version yesterday); on the other hand, individual developers are adding Studio BSPs for third-party boards such as the Wildfire HPM6750 BTB and community BSPs for older platforms such as the Nuvoton N9H30. Vendors ensure consistency across boards, while the community fills in long-tail coverage—together these two ends form the full picture of RT-Thread’s board-level ecosystem.

On the events side, Wuzhen “Xinguang” is the most significant item in this issue: a national-level platform included the “heterogeneous converged edge intelligent AIOS foundation” among 35 promoted products, shifting the narrative from “real-time control foundation” to “edge intelligent operating system,” with the focus on robot “brain” and “cerebellum” coordination. The WTCC alliance article that appeared the same day is exactly this narrative in a specific scenario—three types of Agent solutions, the division of labor with Arm China, and an emphasis on embodied intelligence. Promotion and engineering are on the same line, which is rare in past event articles.

6.2 Limitations and Deduplication Notes

The forum club.rt-thread.org still returned 468 with a WAF challenge page in front of it during this issue, so the post list and body text could not be read; the information gap on the community discussion side was filled by GitHub and media columns.
