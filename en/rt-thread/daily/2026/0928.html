I. Kernel and Version Dynamics

1.1 Mainline merges two maintenance fixes: GD32VW553H-EVAL build cleanup and ipc file tidy-up (09-26 ~ 09-27)

Date: 2026-09-26 19:58 / 09-27 12:18 (Beijing time, merge time)　Source: PR #11837, PR #11832, merge commit b40aeb146, merge commit 05badce95

The mainline merged two small fixes within the window. The first (#11837) fixes a failure in the CI cleanup stage of the GD32VW553H-EVAL BSP: the riscv-none job exited during the scons -c cleanup step after a successful build and packaging — the root cause being that the package pre-check registered in SConstruct (bsp_pkg_check) also ran unconditionally in cleanup mode, while during cleanup the package may already have been removed or not yet fetched; the fix short-circuits this check directly in clean mode (1 file, +3/-0), leaving the check logic for normal builds unchanged. The proposal was submitted by the GitHub Copilot coding agent (copilot-swe-agent), with the agent session triggered by a maintainer and the change completed about 3 minutes after the issue was opened; it was merged by Rbb666 on 09-26 19:58. The second (#11832) removes a redundant __RT_IPC_SOURCE__ macro definition from components/drivers/ipc/SConscript (1 file, +1/-1), part of clearing the 09-24 review queue, merged on 09-27 12:18.

1.2 Review queue gains two robustness fixes: STM32 linker script stack alignment and devtmpfs path out-of-bounds (09-27)

Date: 2026-09-27 20:57 ~ 21:11 (Beijing time, creation time)　Source: PR #11841, PR #11842

The review queue gained two robustness fixes within the window. The first (#11841) corrects stack alignment in all STM32-family linker scripts: changing the .stack section’s ALIGN(4) to ALIGN(8) to comply with the ARM AAPCS requirement that the stack pointer be 8-byte aligned at public function boundaries, corresponding to the old defect #7527 reported in 2023-05 (4-byte stack alignment causing incorrect double argument passing in variadic functions); the change covers 12 templates and 98 boards, 110 linker scripts in total (+220/-220), without touching any board’s memory layout. The second (#11842) fixes a stack buffer overflow in devfs: _path_separate() and _get_subdir() in devtmpfs.c do not accept a buffer length parameter, so a single path component exceeding 255 bytes causes an out-of-bounds write (up to about 3.8KB out of bounds, with the written content and length controlled by the caller, potentially overwriting the return address); the fix aligns devfs with the existing validation in tmpfs (out-of-bounds returns -ENAMETOOLONG, 1 file +48/-8), with the commit signed with the [HUST CSE] prefix. Both are currently under review.

1.3 FinSH path completion heap overflow defect report: submitter has claimed it and plans to fix (09-26)

Date: 2026-09-26 03:55 (Beijing time, creation time)　Source: Issue #11839

The community filed a high-severity defect report for the FinSH component within the window: when triggering path auto-completion (Tab key) in msh, the msh_auto_complete_path logic does not perform strict bounds checking when concatenating the current working directory with user input, so an overly long or deeply nested path can cause a heap buffer out-of-bounds write (CWE-122), affecting v5.3.0 and the current mainline, as well as boards such as STM32F407-ATK. The issue includes a defect description and labels (bug, in progress, etc.); the submitter Acen28 claimed the issue the same day and plans to submit a fix themselves. This is another memory-safety lead advanced by community auditing, following the devtmpfs out-of-bounds issue (see 1.2).

2.2 Forum tutorial “MCU Linker Script ‘Upgrade’”: orphan sections and alignment handling (09-28)

Date: 2026-09-28 08:17 (publish time, updated 11:03)　Source: forum article 54cb40d33610387a, companion video on Bilibili

An update to community author “大目熊”’s MCU low-level series (the previous installment, “MCU GNU Linker Script”, was covered on 09-22): this installment takes on orphan sections and alignment issues in more depth. Key points: use -Wl,--warn-orphan to have the linker list sections not explicitly placed; classify sections by the SHF_ALLOC flag into those needed at runtime (.text/.rodata/.data/.bss, which require allocated memory regions) and those not needed (.debug_*, .comment, .ARM.attributes, symbol tables, etc., listed explicitly but not allocated), and place each one accordingly; .ARM.exidx/.ARM.extab belong to the ALLOC category and must be placed with start/end symbols exported; finally, wrap up with 4-byte alignment, verifying that all linker warnings are eliminated and the map file matches the script description. Includes a companion video on Bilibili; this is community tutorial content.

III. Ecosystem and Vendor Adaptation

3.1 Qinheng CH32V003F4P6-EVT Board Support Proposal Enters Review (09-25)

Date: 2026-09-25 21:11 (Beijing time, creation time; updated on 09-27)　Source: PR #11838

Contributor cms19859230182-lang (previously the author of the CH32V203 BSP and ESP32-C6 proposals) submitted a BSP proposal for the Qinheng CH32V003F4P6-EVT development board. The CH32V003F4P6 features a RISC-V core, 48MHz clock, 16KB Flash, 2KB SRAM, and TSSOP20 package; the default image enables only UART1 (TX PD5 / RX PD6, 115200 into msh), with debugging via single-wire SWDIO (PD1) connected to an external WCH-LinkE. The submitter has tested it: built with WCH RISC-V GCC 8.2.0 (-march=rv32ec -mabi=ilp32e), the image is 15680 bytes (fitting into 16KB Flash), and after flashing, the serial output shows the RT-Thread banner and msh prompt. The proposal contains 5 commits and 47 files (+9258/-0), and is currently under review.

Date: 2026-09-28 08:45 ~ 09:09 (push time)　Source: canopennode-rtt, lely-canopen-rtt

Community contributor wdfk-prog (the submitter of the canopennode package merged into v1.2.0 on 09-24 in the RT-Thread package index) published documentation sites for two CANopen integration repositories within the window: canopennode-rtt (CANopenNode integration, supporting logical device mode for multi-device nodes) and lely-canopen-rtt (Lely CANopen integration, single-owner EV/IO2 runtime with static object dictionary, optional master services) both pushed MkDocs manuals and Doxygen API documentation; the lely repo additionally added PR documentation validation CI. Both packages previously had introductory posts on the RT-Thread forum (the lely master usage long-form article was covered on 09-11). Investment in industrial communication package development continues.

3.3 AWTK Open Source License Switches to Apache 2.0 (09-26)

Date: 2026-09-26 08:50 (commit time)　Source: zlgopen/awtk license change commit

The general-purpose embedded GUI toolchain AWTK (zlgopen/awtk, 3.3k stars) switched its license entirely from LGPL-2.1 to Apache License 2.0 within the window (LICENSE file +201/-504), committed by project lead author lixianjing. AWTK and its RT-Thread packages (awtk, etc.) have long served GUI application development on RT-Thread, and the license relaxation facilitates commercial integration. This is an ecosystem reference item (not RT-Thread-specific).

IV. Industry Applications

4.1 Luckfox RV1103 Single-Chip Drone Prototype: RISC-V Core Runs RT-Thread Flight Controller (09-27)

Date: 2026-09-27 17:25 ~ 20:04 (creation and push time)　Source: luckfox-rv1103-drone

Developer nguyencanhanh has published a single-chip quadcopter drone prototype: centered on the Rockchip RV1103 (Luckfox Pico Mini B), with the Cortex-A7 running Linux handling the camera, NPU recognition, Wi-Fi, GPS, and remote control reception, while the on-chip RISC-V MCU core (HPMCU) runs RT-Thread executing a 1kHz flight control loop; the project’s goal is to answer with empirical data whether “a single-chip architecture can fly directly,” with an external independent flight controller as the fallback option. As of 09-27: no actual flight yet, but Linux and the MCU are already running in parallel, the 1kHz loop has been tested, and the flight control software can run fully in a simulator with 3D control views; the custom LFX_FC_R1 flight controller board (46×46mm) has completed routing. The project is open-sourced under MIT + CERN-OHL-P licenses, and is a community individual prototype.
