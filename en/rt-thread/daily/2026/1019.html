I. Kernel and Version Dynamics

1.1 Kernel version number switched to v5.4.0: version macros and Kconfig first, release artifacts not yet available (10-17)

Date: 2026-10-17 09:43 (merge time)　Source: PR #11875, include/rtdef.h

Maintainer Rbb666 merged the version switch proposal (2 files +4/-3): the version macros in include/rtdef.h changed from 5.3.1 to 5.4.0, with a changelog entry dated 2026-10-17 added; the default value of RT_VER_NUM in src/Kconfig changed from 0x50301 to 0x50400. The author ran scons –pyconfig-silent with the qemu-vexpress-a9 default configuration and confirmed that RT_VER_NUM in the generated rtconfig.h is 0x50400. As of 10-19, the repository’s latest tag and release are still v5.3.0 (released 09-10), and the ChangeLog.md title is still v5.3.0, indicating that this is only the start of a version cycle; the 5.4.0 release notes and artifacts have not yet appeared. Community defect tickets within the window already label master as v5.4.0-dev.

1.2 Next RISC-V major refactor merged: 165 files unify RV32/RV64, Sv32~Sv57 and AIA land together (10-17)

Date: 2026-10-17 09:44 (merge time)　Source: PR #10320, Issue #10722

The RISC-V architecture refactor (#10320), nearly five months in the making, was merged: 4 commits, 165 files +15134/-2617. Contents include ISA management interfaces, 32E/32I/64I consolidation, cache handling by CBOM ISA, Sv32/Sv39/Sv48/Sv57/Sv64 MMU and SVPBMT, merged M-mode and S-mode CSR operations, SMP, APLIC/IMSIC (AIA), CLIC, ACLINT/CLINT, INTC and PLIC, optional DM (via OFW only), merged T-HEAD vendor code, plus DM ported on qemu-virt64-riscv64 and support for booting from a non-zero core. In the plan table, S-mode RT-Thread, S-mode RT-Smart (including APP, DM, no MMU, no DM) and M-mode (DM, no DM) are all checked off; BSP adaptation is still pending. On the same day, six RISC-V task tickets — #10722, #9571, #9567, #9566, #9521, #11226 — were closed in a batch.

1.3 Thirteen RT-Thread Smart proposals filed in bulk: syscall split, signal and MMU fixes, K230D adaptation (10-18 ~ 10-19)

Date: 2026-10-18 19:35 ~ 10-19 02:49 (created / updated)　Source: PR #11896, PR #11897, PR #11892

Maintainer BernardXiong opened 13 proposals in a row (#11885 ~ #11897) within two minutes, from 19:35 to 19:36 on 10-18; all are under review as of this issue’s cutoff. The main thread is getting Smart running on QEMU and real boards: qemu-virt64-riscv64/aarch64 enable RT_USING_SMART, riscv64 disables SMP, ext4/elm are mounted on virtio-blk with ptyfs and procfs mounted; libcpu/riscv fixes early page-table physical offset conversion, per-core page-table inheritance of user mappings, and user-mode exception handling, and adds XuanTie architecture selection and SVPBMT; lwp splits syscall implementations, fixes signal delivery order and ELF segment protection, and completes TIOCLINUX and TIOCGWINSZ; K230D adds a 128MB DDR configuration and ext4 root filesystem. Also included: SAL RAW socket protocol validation, lwip loopback NIC, 8250 earlycon register width, SDIO block size, poll routed through DFS file operations, and a UTIME_OMIT fix.

1.4 ESP32-C6 SPI proposal merged after revision: segmented transfer, BSP-owned gdma, bit-width validation moved earlier (10-16)

Date: 2026-10-16 11:31 (merge time)　Source: PR #11846, PR #11870

The ESP32-C6 SPI proposal under review in the previous issue was merged after review revisions (7 files +1253/-26): with DMA disabled, transfers are segmented per the IDF single-transfer 64-byte limit; gdma.c is changed to a BSP-owned copy to prevent C3/C6 shared builds from overwriting each other; bit-width validation is moved ahead of bus initialization. Behaviorally, the IDF SPI master is linked only when BSP_USING_SPI is selected, and the default image still has SPI disabled; the shared ESP driver no longer passes through SPI mode and returns the actual number of bytes transferred; chip select comes from SPI2_IOMUX_PIN_NUM_CS, and an empty configuration returns -RT_EINVAL. Meanwhile, the proposal to adapt C3/C6 to ESP-IDF v6.1 and upgrade the RISC-V toolchain to GCC 15.2 (#11870) is still under review.

1.5 HPMicro BSP upgraded to hpm_sdk v1.13.0, adds HPM5100EVK board support (10-17)

Date: 2026-10-17 16:28 (merge time)　Source: PR #11871, packages index commit

bsp/hpmicro upgraded from hpm_sdk v1.10.0 to v1.13.0 (434 files +23873/-16669): adds board, startup, applications, Kconfig, documentation and images for hpm5100evk (HPM5151), and registers it in ALL_BSP_COMPILE.json and the BSP list; 11 existing boards are resynced to the new SDK while preserving RT-Thread-side changes (clock_time-based drv_timer, scons integration with CXX, artifacts output to build/, named Kconfig choices, board_delay_* routed through rt_hw_us_delay, board-level codec files, etc.), and the driver layer is synced to v1.13.0. The package index had already added hpm_sdk v1.13.0 on 10-14.

1.6 Four security audit reports: libdl arbitrary write, lwp signal out-of-bounds, OFW stack overflow, lwip-dhcpd remote denial of service (10-17 ~ 10-19)

Date: 2026-10-17 14:25 ~ 10-19 00:37 (created / updated)　Source: Issue #11898, Issue #11882, Issue #11879, Issue #11878

Contributor XueDugu filed four defect tickets in a row within the window, each with the introducing commit, affected version range and QEMU reproduction environment. #11898: libdl/dlmodule performs no bounds checking on ELF relocation metadata, so a malformed .mo can write kernel-mode memory with controlled values at load time; this traces back to a 2018 commit in v3.1.0, and the ARM/RISC-V/x86 relocation implementations are structurally identical. #11882: lwp’s sys_sigaction does not validate the signal number, allowing out-of-bounds reads and writes of the kernel heap (Smart, since v5.0.0). #11879: OFW device tree expansion has no nesting depth limit, overflowing the 64-entry np_stack (since v5.0.2). #11878: after the lwip-dhcpd lease pool is exhausted, dhcp_client_alloc loops forever, allowing an unauthenticated remote peer to saturate the entire lwIP stack (since v4.0.0). All four tickets remain open.

1.7 DFS code-collision proposal closed, then rewritten and reopened: device control commands now encoded by device class (10-17)

Date: 2026-10-17 16:55 ~ 17:06 (closed / reopened time)　Source: PR #11869, PR #11881

The DFS-layer proposal (#11869) noted in the previous issue, concerning the collision between F_GETFL/F_SETFL and RT_DEVICE_CTRL_*, was closed on 10-17 16:55 without being merged; 11 minutes later, author CXSforHPU opened #11881 (3 files +37/-20), solving it at the encoding level instead: introducing RT_DEVICE_CTRL_BASE(Type) = (device class + 1) × 0x100, where the high byte denotes the device class and the low byte the index within the class, and migrating pin configuration commands and serial hardware control commands to after their respective class base addresses, so that generic control commands no longer collide with POSIX’s 3 and 4. The new proposal is under review.

II. Official and Community Activities

2.1 Ruiching platform V1.8.4 release preview: industrial gateway virtual NIC, QY1503 encoder and MIPI RGB666, live stream walkthrough on 10-21 (10-16)

Date: 2026-10-16 (publish time)　Source: EE Times China report

RT-Thread (Ruiside) released a preview of the Ruiching platform V1.8.4 to media, with updates covering industrial gateways, peripheral drivers, display interfaces and debugging tools: the EG1200 industrial gateway adds a virtual NIC and NFS network filesystem mounting, allowing direct network access to the dev board filesystem for easier data sharing and remote debugging; a new QY1503 rotary encoder driver targets motor closed-loop control, position feedback and speed measurement; the RC-Pi-3506’s MIPI is adapted to RGB666, enabling more display models; also added are MIPI power-on timing control, GPIO pin pull-up/pull-down configuration, and the amp_device debug command (to view AMP inter-core communication status and device allocation). The official live stream is scheduled for 10-21 20:00, demonstrating each item on the RC-Pi-3506 in real hardware.

2.2 Community tutorial: extracting the Cortex-M crash scene from HardFault (10-17)

Date: 2026-10-17 17:04 (publish time)　Source: Community article

Community author “大目熊” published the first part of a Cortex-M crash localization series, explaining the HardFault handling approach: the exception entry has already pushed 8 key registers onto the stack, and the fault cause is written to the SCB status register, so developers only need to read and print them in HardFault to locate the faulting site; the article walks through the trigger paths per the HFSR description and notes that this first part only covers “printing the scene”, leaving call-chain unwinding for the next part. It has direct reference value for MCU firmware debugging where no core dump mechanism exists, and fills a gap in the community’s content on system-level troubleshooting methods.

III. Ecosystem and Vendor Adaptation

3.1 RT-Thread Env v2.0.3 Released: Plugin System and Toolchain Management at the Core (10-17)

Date: 2026-10-17 01:37 ~ 09:13 (commit / merge time)　Source: env version commit, EET-China report

The Env repository completed its version switch on the same day (env.json and info.py point to v2.0.3) and merged built-in documentation navigation for the WebUI (+291/-36), allowing standalone HTML documents to be tracked; PR #302 was merged on 10-17 at 09:13. An official introductory article was published at the same time. The focus of v2.0.3 is plugins: features are packaged as .epack files that can be installed, upgraded, enabled, disabled, and uninstalled. Plugins can add command-line commands and extend WebUI pages, and an official epack development tool is provided (initialization, validation, build, testing). Before installation, source, permissions, and integrity must be verified; plugins run with the current user’s privileges and are not a security sandbox. The toolchain has two entry points: SDK download and installation, and registration of local toolchains (MDK, IAR). On Windows, the Env terminal can be opened directly by right-clicking in the BSP directory. This version targets RT-Thread 5.1.0 and later as well as the main development branch.

3.2 RT-Thread UART Evaluation of NOVOSENSE NS800RT7P65D and BSP Configuration Improvements (10-16)

Date: 2026-10-16 (publish time)　Source: EET-China evaluation

A media outlet published a UART evaluation of the NS800RT7P65 based on RT-Thread. The chip is a dual Cortex-M7 real-time MCU in NOVOSENSE’s NSSine series, based on ARMv7E-M with a double-precision FPU, DSP extensions, and an MPU. The article covers UART resources and register configuration at the chip level through to functional testing at the code level, verifying that after menuconfig configuration rtconfig.h generates the corresponding macros, all UART devices are registered, and the console is mapped to different serial ports one by one for testing. The author also notes hardcoded baud rate, stop bits, and other settings in the board-level driver, and suggests mapping them into menuconfig to improve BSP robustness; an improvement proposal has been submitted. The same chip also appears in this window’s community project “RenHua” (see 4.1).

3.3 Allwinner F101 YuzukiNeko New BSP Proposal: M/S Dual Configuration and a Full Set of DM Drivers (10-17)

Date: 2026-10-17 12:55 (creation time)　Source: PR #11877

The community submitted board support for the Allwinner F101 (Sun252i) YuzukiNeko (134 files, +26189/-3): both M-mode and S-mode configurations are provided, along with DM drivers for clock, reset, pinctrl, DMA, SDIO, SPI, USB, audio, thermal management, RTC, PWM, ADC, NVMEM, watchdog, DVFS, G2D, and JPEG. On the display side, a Sunxi DE0/TCON0 output backend is added, covering RGB, LVDS, and MIPI-DSI, with an ST77916 QSPI screen configuration; on the CherryUSB side, Sunxi MUSB glue is added. It also fixes power domains, DVFS, graphics, UART reset and register shifts, QSPI, the thermal management workqueue, input capture, and DM USB integration. The proposal is under review.

IV. Industry Applications

4.1 Facility Agriculture: K230 + NS800RT7P65D “RenHua” Intelligent Pollination Robot (10-17)

Date: 2026-10-17 14:59 (publish time)　Source: Community article

The community published an intelligent pollination robot for greenhouse tomatoes. The robot body uses a Hiwonder K230 vision module for perception and a NOVOSENSE NS800RT7P65D as the main controller, equipped with a four-channel encoded-motor chassis, a robotic arm composed of stepper motors and three HTS-35H bus servos, and actuators including a vibration motor and a blowing DC motor. The environmental node uses an ESP8266 with a DHT11 and an SGP30 to collect temperature, humidity, and CO2, uploading via WiFi and MQTT; the host side includes a server backend, Web, and a Qt desktop client. The system supports switching between three pollination modes: vibration, touch, and blowing. When K230 recognizes a flower, it triggers the robotic arm to position and pollinate; when disease is detected, images are uploaded for backend analysis.

4.2 Public Health: GD32F303 + STM32F103 Dual-Board “Scavenger” Intelligent Disinfection Device (10-17 ~ 10-18)

Date: 2026-10-17 16:35 ~ 10-18 21:19 (commit / publish time)　Source: Community article, Allin-JO/GD32

The community published a mobile disinfection device for classrooms, corridors, and public seating, using a “GD32 lower-level controller + ESP8266 (WiFi/MQTT) + cloud server + PC/Web multi-client” architecture. It integrates atomized spraying, movement control, disinfectant level monitoring, video backhaul, and QR-code appointment booking, forming a closed loop of collection, transmission, processing, and control. The author states that a proof-of-concept prototype and three-client software integration have been completed, positioning it as a foundation for innovation and entrepreneurship and student training projects. The accompanying repository Allin-JO/GD32 received two commits on 10-17, completing the migration of the main controller from STM32F103 to GD32F303 and tidying up the repository.
