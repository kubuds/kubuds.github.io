II. Kernel and Security

2.1 virtio trust boundary issue claimed then released after thirteen hours (11-21)

Date: 2026-11-20 22:51 to 11-21 11:41 (claim and release). Source: #11327.

The issue was filed by XueDugu on April 13, affecting master and six release tags from v5.0.0 to v5.2.2.

The problem surface is in five virtio drivers: input, console, gpu, blk, net. They directly use the id from the backend-provided used ring as a local array index without first validating the range.

The net one has an extra layer. When used len is less than the header length, the length calculation underflows, and the copy then proceeds with that length.

Maintainer GuEe-GUI’s reply on April 14: mainline VirtIO is about to be deprecated, use cases are somewhat experimental, further fixes are not recommended, see #11232 for the new version.

On November 20 at 22:51, niuxiaoch claimed it with /claim. On November 21 at 11:41, the same account released it with /unclaim. Less than thirteen hours apart.

Assessment: The disagreement over how to handle this issue has not been resolved. Basis: both signals—”fix not recommended” and “someone claimed it”—are present simultaneously, and the claim lasted only thirteen hours.

2.2 Power management registration interface gains race and lock protection (11-20)

Date: 2026-11-20 22:20 (proposal). Source: #12075.

The proposal fixes #10075. That issue describes rt_pm_device_register hanging after power management is enabled.

The first change is ordering. Originally the list node was linked into _pm.device_list first, then device_pm’s fields were initialized. The proposal swaps the two steps.

The second is protection. List operations are wrapped with interrupts disabled, while memory allocation and free are left outside the critical section.

The latter is precisely the precondition for #10075 not hanging. The proposal body states that if allocation were placed inside the interrupt-disabled region, it would deadlock under SMP.

Scale: one file, 39 lines added, 3 lines removed, two commits, verification board qemu-vexpress-a9.

Assessment: The trade-off in the fix is more noteworthy than the fix itself. Basis: the proposal handles “interrupts disabled” and “allocation that may sleep” separately, rather than using one big lock for convenience.

III. Drivers and Frameworks

3.1 CAN framework refactor spans BSPs from ten vendors (11-21)

Date: 2026-11-21 10:03 (updated). Source: #12054.

The proposal was raised by wdfk-prog on November 14 and updated to its sixth commit within the window.

The scale is 42 files, 9,187 lines added, 5,292 lines removed. Labels cover BSPs from ten vendors: NXP, STM32, Loongson, HC32, Renesas, GD32, Phytium, AT32, WCH, and Novosns.

The core of the approach is to stop maintaining a transmit software queue in the generic CAN layer. The controller’s built-in hardware mailboxes become the sole queuing resource.

The description states the responsibility boundary in one line: the generic layer handles hardware resources, synchronization, ownership, termination, and lifecycle; transmit buffering, retry, scheduling, and protocol QoS go to the upper layer.

Three related discussions are linked. #11767 is the refactor plan, #11759 is TX Full Flush and hardware Abort, and #11779 is driver lifecycle.

Assessment: This is a framework-level change, not a point fix. The basis is that the changes land in both the generic layer and ten BSPs, and the description rewrites the responsibility boundary.

3.2 Serial V1 reopen with a different mode: a four-byte buffer interpreted as a forty-eight-byte struct (11-20)

Date: 2026-11-20 13:27 issue, 13:42 proposal. Source: #12072, #12073.

The symptom is the same serial device first opened with interrupt transmit, then reopened with DMA transmit.

The first open allocates a four-byte transmit FIFO. The DMA transmit path interprets it as a forty-eight-byte DMA struct.

The out-of-bounds point is specific. The data_queue member starts at offset 4, which falls exactly outside the original four-byte allocation.

The root cause is in the flag bits. The open flag mask contains both the interrupt transmit and DMA transmit bits, so changing only the transmit mode still goes through rt_serial_open() again.

The fix returns -RT_EBUSY when the mode differs and preserves the existing mode bits on reopen. The scale is one file, 18 lines added, 12 lines removed.

Assessment: The entry point for this class of defect is the flag-bit design, not a mistake in a particular driver. The basis is that the fix is in the framework’s open path, not in a specific BSP.

3.3 SWM341 classic CAN receive copies by hardware DLC, overrunning the eight-byte buffer (11-21)

Date: 2026-11-21 00:28 (proposal). Source: #12076.

The symptom is that the hardware DLC of a classic CAN frame may exceed 8. The driver still copies by this length into a fixed eight-byte buffer.

Both paths overrun: CAN_Receive and swm_can_recvmsg. The proposal links issue #11425.

The fix is direct: clamp the length to 8 bytes before both copies. The scale is two files, 8 lines added.

Assessment: Both defects in the window are in length and mode validation. The basis is that #12073 fixes the framework’s mode bits and #12076 fixes the BSP’s copy length, with different authors and different locations.

IV. Toolchain and Documentation

4.1 mkromfs pads by character count, misaligning UTF-8 directory entries (11-20)

Date: 2026-11-20 20:42 (proposal). Source: #12074.

When generating the binary ROMFS image, the tool script computes padding by character count but writes to disk by UTF-8 byte count. When a name contains Chinese characters, the two numbers differ.

An example is enough to illustrate the problem. With image base 0x1000 and input path “中a/文”, the nested directory table is placed at 0x102a. Directory entries require four-byte alignment.

The fix encodes first, then computes padding. When the encoded length is a multiple of four, it also appends a NUL terminator.

For the same example, the directory table now starts at 0x102c. The author notes the change was assisted by OpenAI Codex.

Verification is a new tool test case. The case fails on 6fdfe70062 and passes with the change applied; a byte-by-byte comparison of an ASCII tree was also performed.

Assessment: The defect appears only under non-ASCII paths, which regular test cases do not cover. The basis is that the original test compared a pure ASCII directory tree.

4.2 Two commands in the macOS QEMU quick start stall readers (11-22)

Date: 2026-11-22 14:49 issue, 11-23 02:02 proposal. Source: #12082, #12083.

The first is in step 1.3. The command writes a quoted tilde into PATH, and a tilde inside quotes is not expanded, so the last segment is stored literally as-is.

The second is in step 5.3. The documentation tells readers to run ./qemu_nographic.sh after formatting sd0, but this filename does not exist in the BSP directory. The actual name is qemu-nographic.sh.

The issue author states that only the PATH behavior was verified; no macOS build was run and QEMU was not started.

The proposal was submitted by BernardXiong and modifies the same English document. The interval from issue to proposal is about eleven hours.

Assessment: How fast a documentation defect is fixed depends on who reads it. The basis is that the reporter stopped at behavior verification while the maintainer changed the document directly.

V. BSP and Hardware: Allwinner V861

5.1 Five Proposals Form a Progressive Chain from Single-Core to Dual-Core SMP (11-21)

Date: 2026-11-21 15:16 to 17:40 (submitted). Source: #12077, #12078, #12079, #12080, #12081.

All five were submitted by cms19859230182-lang and target the same board: the Avaota F2 based on the Allwinner V861. The BSP directory is bsp/allwinner/avaota-f2.

The chain has five steps: C907 single-core board support, the E907 heterogeneous side, hardware MSGBOX and OpenAMP-shaped endpoints, MMC card detection and sector reads, and C907 dual-core SMP.

Each step leaves an on-board pass marker, in order: HETERO-OK, RPMSG-OK, OPENAMP-EPT-OK, mmc0 card OK, and SMP-OK hart0=0 hart1=1.

The dependencies form a chain. #12078 depends on #12077, #12079 on #12078, #12080 on #12079, and #12081 on #12080.

As a result, the line counts of the five proposals are cumulative and cannot be summed. #12081 lists 79 files and 6,092 added lines, which include the content of the first four.

The descriptions state their boundaries. #12079 specifies OpenAMP-shaped named endpoints, not the full libmetal and virtio-rpmsg stack; #12080 states that no filesystem or block-write support is claimed.

Assessment: This is a BSP bring-up split into verifiable milestones. The basis is that each step has its own pass marker and acceptance document, and the dependencies form a chain.

5.2 Maintainer Review: Acceptance File Rejected, Toolchain Switched to env 2.x and sdk (11-21)

Date: 2026-11-21 18:44 and 18:46 (review). Source: #12077 review.

Two inline comments. The first targets bsp/allwinner/avaota-f2/ACCEPTANCE.md, stating “the submission of this file is not accepted.”

The second targets the README. It suggests switching to env 2.x and managing toolchain installation and removal via the sdk command.

The maintainer added that when a toolchain already exists locally, simple configuration suffices for automatic detection and use.

The author replied on November 22 at 16:20 with “Fine, I’ll delete this file,” and wrote in the general comment at 16:32 the same day, “All changes done, please review.”

Assessment: The entry ticket for a new BSP is not feature count but consistency with existing engineering conventions. The basis is that the review raised only documentation and toolchain points and did not question the driver implementation.

5.3 Chip Side: Dual-Core C907 plus E907, with RVV 1.0 (11-23)

Date: 2026-11-23 (spec verification). Source: Allwinner V861 product page, Allwinner Online V861 documentation.

The V861 is positioned as a network camera processor. It has dual-core XuanTie C907 at up to 1.4GHz, with the RV64GCBV and RV32GCBV instruction sets.

Each of the two big cores has a 128-bit vector unit supporting RVV 1.0; both integrate single- and double-precision floating-point units.

The little core is a single XuanTie E907 at up to 800MHz, with the RV32IMAFC instruction set. It also has a 1 TOPS INT8 neural network accelerator; on the imaging side the vendor claims AI-ISP 2.0.

On the board side, the Avaota F2 is open-source hardware, 40 × 22 mm, with 128MB DDR3 and 16MB SPI NOR, and the camera connects via MIPI CSI.

The repository status was also checked. On master, bsp/allwinner already contains the d1 and d1s directories; avaota-f2 does not yet exist.

Assessment: This is a new position for RT-Thread on RISC-V camera SoCs. The basis is that Allwinner’s previous RT-Thread BSPs were the D1 series, while the V861 belongs to the IPC product line, with vector units and an NPU.

6.2 Thread-tracking pull request closed after a year and two months (11-21)

Date: 2026-11-21 23:28 (closed). Source: #10689.

The pull request was opened on September 12, 2025, adding two fields to the thread list: startup count and last switch time.

The author validated it on a single-core M4 and posted full output. He noted himself that he had not used the SMP portion.

The maintainer’s comment on September 23, 2025 was that last time is only a very weak reference, that real-time systems do not pay much attention to this value, and that the change was of little significance. The pull request carried the -1 label. It was closed on November 21 without being merged.

Assessment: The closure was based on a design trade-off, not code quality. The basis: the dispute centered on whether these two metrics deserved a place in the thread list, and the author had already provided usable output.

6.3 Two new repositories bring RT-Thread into CarPlay and smartwatches (11-22)

Date: 2026-11-22 (pushed). Sources: rt-carplay, helios-sf32.

rt-carplay is a CarPlay receiver SDK written in C under GPL-3.0. The repository was created on November 15, with a push in the early hours of November 23.

It separates the protocol core and portable runtime into parts that do not depend on RT-Thread headers, then provides two host ports: RT-Thread and embedded Linux. The README is restrained about capability boundaries, stating explicitly that these interfaces do not claim official Ultra support.

helios-sf32 is LVGL smartwatch firmware for the SiFli SF32LB52 development board, built on the OpenSiFli SDK and RT-Thread. It was pushed on the evening of November 22 and has 12 stars.

Assessment: Neither project is in the official repository, but both treat RT-Thread as a target runtime. The basis: both the READMEs and the repository topics explicitly mention an RT-Thread port or an RTOS dependency.

VII. Summary and Trend Observations

7.1 The weekend’s incremental activity was entirely on the pull request side

Over three days the main repository saw zero commits and zero merges, with ten new pull requests and a net queue increase of nine.

Assessment: The weight of this window is in pull requests, not in landed code. The basis: the only action that would have reached the main branch did not happen, while the pull request side carried two complete technical threads.

7.2 Three pull requests carry traces of AI collaboration

#12073 includes a Claude session link, and #12074 and #12082 note assistance from OpenAI Codex. The three span the serial framework, ROMFS tooling, and documentation.

Their shape is similar: the problem is clearly located, the change surface is small, and the verification method is spelled out. All three also add test cases or verification commands.

Assessment: AI collaboration has become a standard way of writing in this batch of pull requests, no longer a rare case. The basis: three of the ten new pull requests proactively disclosed it, and all wrote specific commands in their verification sections.

7.3 The entry ticket for a new BSP is consistency with existing conventions

The five V861 pull requests cover a very broad functional surface, yet the maintainer’s comments landed on two documents: the acceptance file is not accepted, and the toolchain must go through env 2.x and sdk.

Assessment: BSP review is gated on engineering conventions, not driver capability. The basis: in the same batch, the driver implementation was not questioned; what was called out was the process documentation and how the toolchain is obtained.

7.4 A longer queue does not mean worsening backlog

Pull requests went from 142 to 151, issues from 341 to 342. Merges were zero, but 21 pull requests were updated.

Assessment: This is a gap in the merge window, not a review standstill. The basis: the maintainers were still reviewing the V861 pull requests over these two days and filed a documentation fix themselves the same day, with all the action in review and patching.

7.5 After the last commit

6fdfe700 is a CI configuration change that selects the memory heap in mem.cfg. Since then there have been no commits on the main branch.

Assessment: When the next merge lands matters more than how many land. The basis: the queue already holds large changes such as the CAN framework refactor, and once the review cycle ends, landings will come in a cluster.
