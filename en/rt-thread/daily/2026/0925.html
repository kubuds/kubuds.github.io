I. Kernel and Version Updates

1.1 WCH CH32V203C8T6 Development Board BSP Merged into Mainline (09-24)

Date: 2026-09-24 16:21 (Beijing time, merge time; proposal created on the evening of 09-22)　Source: PR #11827, merge commit 386b877b

Mainline merged one new board support within the window: the WCH CH32V203C8T6-EVT-R0 development board BSP, located at bsp/wch/risc-v/ch32v203c-evt-r0. The board uses the Qingke V4B core (CH32V20x_D6), with 64KB zero-wait-state Flash and 20KB SRAM; because the official SDK only provides a D8W startup file and directly calls Exit() for D6, a standard software package build cannot produce firmware. The proposal fills this gap with a D6 interrupt vector table (software interrupt symbol SW_handler) and 64KB/20KB linker scripts, and patches the SDK package script only under this condition, without affecting the D8W flow. The default image enables GPIO and UART1 (USART1 multiplexed on PA9/PA10), while PWM, ADC, RTC, independent watchdog, and USB device are retained in menuconfig (the 64KB capacity cannot simultaneously accommodate USB and the aforementioned four peripheral categories). The proposal also includes two shared driver fixes: drv_usbd.c adjusts the 16-bit SRAM offset for USBFS DMA and the SET_ADDRESS write timing (endpoint buffers must reside in SRAM, full-speed packet length 64 bytes), and drv_iwdt.c adds adaptation for the CH32V2 series. The proposal comprises 4 commits and 26 files (+2216/-57).

1.2 rt_vsnprintf Width Semantics Defect and Kernel Fix Proposal (09-24)

Date: 2026-09-24 20:52 ~ 21:29 (Beijing time, times of the defect report and fix proposal)　Source: Issue #11833, PR #11834

A community contributor submitted a kernel defect report and accompanying fix within the window: the current rt_vsnprintf implementation (especially the tiny version) mishandles the semantics of %[width].[precision]s, where the minimum width is mistakenly treated as a maximum width truncation—for example, %3s formatting “abcdef” outputs “abc” instead of the full string, and left-aligned %-3s and %*s variants are similarly affected. The fix proposal was submitted in parallel, with changes covering rt_vsnprintf_std.c, rt_vsnprintf_tiny.c, and the corresponding unit test TC_rt_sprintf.c (3 files total, +37/-18), adding boundary checks, implementing combined width and precision functionality, and optimizing test cases. The defect report has 3 discussion comments, and the fix proposal is under review.

1.3 Three New Proposals Added to Review Queue: Network Stack Fixes and Build Cleanup (09-24)

Date: 2026-09-24 14:15 ~ 17:52 (Beijing time, creation times)　Source: PR #11831, PR #11835, PR #11832

The review queue added five proposals in total this period, of which the kernel vsnprintf fix is covered in 1.2 and the ESP32-C6 board support in 3.1; this item covers the remaining three. The first fixes a port allocation defect in lwip-nat: the original implementation allocates translation ports by scan counter rather than idle slot index, and upon entering the allocation path the counter always equals the table size, causing every new mapping to receive the same port, concurrent UDP/TCP sessions to conflict with each other, and return traffic to potentially match the wrong table entry; the proposal also completes lwIP 2.1 adaptation (header file renames and timeout interfaces), and tightens the NAT application condition to require both source and destination networks to match the rule, with LRU eviction of the oldest entry when the ICMP table is full (1 file, +41/-11). The second adds the missing string.h header to lwip-dhcpd: dhcp_server_raw.c directly calls memcmp / memset / strlen / strncmp / strchr without including the standard header, and implicit declaration truncates the strchr() return pointer on 64-bit targets (1 file). The third removes the redundant __RT_IPC_SOURCE__ macro definition from components/drivers/ipc/SConscript (1 file).

III. Ecosystem and Vendor Adaptation

3.1 Espressif ESP32-C6 Dev Board BSP Proposal and Package Source Code Submitted in Sync (09-25)

Date: 2026-09-25 01:20 ~ 02:38 (Beijing time, creation and update times of the proposal and its companion package proposal)　Source: mainline PR #11836, esp-idf package PR #17

A community contributor submitted a mainline BSP proposal for the Espressif ESP32-C6-DevKitC-1 dev board within the window: the module is ESP32-C6-WROOM-1 (RISC-V, 8MB Flash), adding bsp/ESP/ESP32_C6, with GPIO, UART0 (GPIO16/17) and ADC enabled by default; the proposal emphasizes that the C6 must use a dedicated bootloader image (the C3 image cannot be reused), that Flash is DIO 8MB 80MHz, and that the application offset is 0x10000. Because the upstream esp-idf package has not been updated since 2023-11-26 and lacks C6 source code, the contributor simultaneously submitted PR #17 in the package repository to add the C6 scons build source; both proposals are under review (mainline side: 2 commits, 40 files, +9492/-50). This contributor is the same person who submitted the CH32V203 BSP in 1.1, spanning both the WCH and Espressif RISC-V chip lines on the same day.

3.2 Community Releases RT-Thread Nano Port Without IDF: Runs on ESP32-S31 (09-25)

Date: 2026-09-25 10:04 (Beijing time, push time)　Source: esp32s31_rtt_nano repository

A community developer published an RT-Thread Nano port targeting the Espressif ESP32-S31 (dual-core RISC-V, 320MHz, with 16MB Flash and 16MB PSRAM onboard), notable for completely bypassing the ESP-IDF build system: hand-written startup assembly and linker script, compiled directly with riscv32-esp-elf-gcc, flashed independently with esptool, with the image loaded directly by the chip bootROM from Flash 0x2000 (no IDF second-stage bootloader); the console runs over the chip’s built-in USB-Serial/JTAG, the tick uses SYSTIMER, interrupts use CLIC, and PIN / SPI (including QSPI) / I2C peripherals are integrated into the RT-Thread device framework, verifiable directly in msh. The project has undergone reproducible-build verification (89 tracked files build into a byte-identical image in a clean directory). It is a personal project, provided for community reference.
