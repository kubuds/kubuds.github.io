II. Kernel and Security

2.1 Mailbox handles are not validated, allowing read/write to arbitrary kernel memory (11-19)

Date: 2026-11-19 03:36 (fix proposal submitted). Source: #11960.

The issue was filed by XueDugu on October 31, titled around an unvalidated fake object enabling arbitrary kernel read/write. The issue cites ecf2d8215961 (2022-12-03) as the introducing commit, with v5.0.0 as the first affected version; v5.3.0 and master remain affected. It is tagged in progress, with five comments.

The mechanism has three layers. sys_mb_send() passes the user-supplied mb directly to rt_mb_send(). sys_mb_recv() validates the output pointer value but not mb. The RT_ASSERT in the mailbox implementation only reads the type field of the struct.

LWP already has an object ownership table, maintained by lwp_user_object_add/delete. These IPC system calls bypass that table.

The path is therefore direct. A process maps a page and fills it with a fake struct rt_mailbox. It sets type to RT_Object_Class_MailBox, points msg_pool at an arbitrary kernel address, and then calls the public mailbox system calls.

The PoC runs on qemu-virt64-aarch64. The configuration is GICv2, single core, 128 MiB. The switches are RT_USING_SMART=y, RT_USING_MAILBOX=y, RT_USING_DEBUG=n.

The result is that the target qword changes from 0x74003e2f2068736d to 0x1122334455667788, and sys_mb_recv can read the same qword back.

The issue also includes board-level validation on a Raspberry Pi Pico 2 W (RP2350). The board runs single-address-space RT-Thread, validating the kernel mailbox API primitive; the user/kernel boundary is demonstrated by the QEMU full-system run.

III. Device Layer and Build Tools

3.1 Device lifecycle lock made an option that is off by default (11-19)

Date: 2026-11-19 10:44 (proposal). Source: #12068.

The proposal responds to #11234. That issue was raised on March 3 and described how multiple threads opening and closing the same device concurrently causes ref_count to be miscounted. The proposal has 5 commits, 5 files, 366 lines added, and 48 lines removed.

The approach adds a new Kconfig option, RT_USING_DEVICE_LIFECYCLE_LOCK, which depends on device and mutex and is off by default. When enabled, each device uses its own priority-inheritance mutex to serialize initialization, open-mode decisions, reference-count updates, and driver callbacks.

Callbacks may sleep. Calls from different threads wait for the current transition to finish. Recursive transitions on the same device return -RT_EBUSY. Nested calls across devices require the caller to guarantee lock ordering.

The defect was reproduced on vexpress-a9 with a counting driver. In the baseline, an independent device receives two driver opens and has two active references; after the final close and reopen overlap, only one reference remains, open_flag drops to zero, and the driver does not reopen. It reproduces on both single-core and dual-core SMP.

The test case is 229 lines and runs under kernel_basic.cfg, which already enables this option.

Assessment: Being off by default means existing behavior is unchanged; only explicit enablement alters scheduling and latency. This is based on the option depending on device and mutex, and on the proposal carving out a separate exception for the single-threaded board-init case that opens the console.

3.2 dfs open failures now report positive errno (11-19)

Date: 2026-11-19 08:54 (proposal). Source: #12067.

The proposal relates to #10558. That issue was raised on July 28, 2025 and described the inconsistent sign of error codes from rt_set_errno(). The proposal has 4 commits, 6 files, 108 lines added, and 71 lines removed.

There are three symptoms. Opening a nonexistent file on a mounted filesystem returns -1, but errno is negative. When the descriptor table is full, DFS v1 reports -ENOMEM in errno, while DFS v2 returns 0, and the caller treats 0 as a valid descriptor. On RT-Smart, ARM processes receive this false success from both the raw syscall and the musl side.

The fix carries the allocation-failure reason out of the private slot helper. Reaching the descriptor limit reports EMFILE; failure to grow the table or allocate a file object reports ENOMEM; the shared allocator publishes the error after unlocking. A failed POSIX open() returns -1 with the corresponding positive errno, and a successful open may still return descriptor 0.

The test case is added to tc_posix_api.c, 60 new lines, covering both the missing-file and full-table cases. The A9 DFS CI configuration is switched to the current Kconfig symbols and selects the board-level sd device.

The validation environment is bsp/qemu-vexpress-a9, QEMU 7.2.22. Both DFS v1 and v2 are run, the filesystem is tmpfs, and DFS_FD_MAX=12.

The proposal body attributes the symptom to commit 6fdfe700. In the repo, that hash is the mem.cfg commit, which only touches memheap test cases.

Assessment: This reference appears to be a typo. This is based on 6fdfe700’s commit message being unrelated to dfs, and on none of the three commits merged on 11-18 containing dfs changes.

3.3 Local compile flags for grouped libraries applied twice (11-19)

Date: 2026-11-19 22:03 (proposal). Source: #12070.

The proposal fixes #4417. That issue was raised on March 4, 2021 and labeled enhancement. The change touches only tools/building.py, with 27 lines added and 21 lines removed.

The symptom is that a group declared with LIBRARY=True that also carries local compile flags registers two different SCons actions for the same object. One goes through the library builder, the other is generated when the application processes the local flags.

The fix compiles the library group’s objects with local flags the same way as an ordinary group, then archives them. During a normal application build, these library sources are no longer added to the separate local-object traversal.

Validation used SCons 4.11.1 and a minimal fixture with scons -Q -n. No firmware build or board-level test was run.

IV. Trade-offs of Serial V1

4.1 The timeout event has no branch in V1’s switch (11-19)

Date: 2026-11-19 22:54 (discussion update). Source: #11909.

RT_SERIAL_EVENT_RX_TIMEOUT has the value 0x05. It is defined in dev_serial.h, but the switch in rt_hw_serial_isr() only handles 0x01 through 0x04, and there is no default branch.

When a driver sends this event, the framework does nothing. The event is silently dropped.

Two drivers in the repo rely on it to split data frames. The ch579m BSP sends it from drv_uart.c when UART_II_RECV_TOUT arrives.

The SWM341 driver in the synwit libraries sends the same event from drv_uart.c when UART_IT_RX_TOUT is set.

Both BSPs use V1, so the “frame received” notification never reaches the application layer. Frame boundaries are lost, and the only fallback is reporting via RX_IND based on the FIFO watermark.

The situation differs in V2. dev_serial_v2.h only defines 0x01 through 0x04, without this macro, so a driver referencing it would fail to compile outright. The author notes that adding a case in V2’s isr would raise 'RT_SERIAL_EVENT_RX_TIMEOUT' undeclared. If V2 needs this semantics, it should go through the read-side RT_SERIAL_CTRL_SET_RX_TIMEOUT.

4.2 A five-line fix and six hundred lines of formatting (11-19)

Date: 2026-11-19 (scope of the proposed changes). Source: 34d2a002.

The proposal spans 4 files in total, adding 868 lines and deleting 504. The number looks large, but it becomes clear once broken down.

The actual fix is 34d2a002, which adds 5 lines and deletes 0 in dev_serial.c. The fix merges the timeout event into the RX_IND branch: first drain the hardware FIFO, then invoke rx_indicate with the length already buffered in the software FIFO.

Another commit, 87b851b4, is clang-format, adding 622 lines and deleting 505 in the same file. The formatting is what inflates the diff.

The remaining three files are test cases. uart_rx_timeout.c is 226 lines, Kconfig 5 lines, SConscript 11 lines. The test cases do not depend on hardware and can run without a board.

4.3 The maintainer’s stance: keep V1 for compatibility, steer new BSPs to V2 (11-20)

Date: 2026-11-20 06:54 (comment). Source: #11909 discussion thread.

The controversy surfaced as early as October 22. Rbb666’s comment was: V2 has been out for a long time, and maintaining V1 and V2 in parallel over the long term is a trap; personally, I think V1 should be frozen for historical compatibility only, with serial’s focus shifting to V2.

The same comment contains two more facts. RTT’s summer camp and introductory training still use V1. Many BSPs only use serial for MSH, with very shallow requirements, a legacy matter. He believes subsequent BSPs should proactively guide contributors to prioritize V2, and BSPs such as Renesas have already adapted to V2.

Early this morning Yunlk replied, building on this positioning. Since V1 will continue in service, the events it silently drops are worth fixing. This proposal only adds one case, touches neither V2 nor any driver interface, and includes test cases that do not depend on hardware.

Assessment: This discussion defines V1’s nature: not frozen, but low-maintenance. The basis is that the maintainer said “BSPs that only want to use it for MSH can keep V1,” not “V1 stops accepting fixes.”

Date: 2026-11-19 14:05 (proposal update). Source: packages #2059.

The package itself is an MQTT 3.1.1 client supporting QoS 1 and bounded I/O, optional TLS with CA and hostname verification, and depending on Mbed TLS 2.x. The version is pinned to v1.1.1 (commit c4956bee), with v1.1.0, v1.0.1, v1.0.0 and latest retained in the index; older versions hide the newly added channel options.

The configurable items are Host, port, Client ID, account and Topic. The proposal notes it contains no personal server credentials and is not tied to any board, sensor, or course application.

There is also an optional layer: command routing at the single-device, group, and deployment levels, kept separate by device state and acknowledgment topics, with the routing layer off by default. It comes with a standalone Python teacher-side web controller, including feature toggles, a roster, an action allowlist, an auth API, and Mosquitto 2.x ACL export.

7.2 An assertion is not an ownership check

RT_ASSERT reads the type field in the struct. In a fake object, that field is filled in by the caller.

Assessment: This kind of gap cannot be stopped by an assertion. The basis: the PoC passes the assertion simply by writing type as RT_Object_Class_MailBox, whereas a real ownership check must rely on the object table.
