I. Kernel and Version Dynamics

1.1 Kernel and Driver Fix Merge Batch: ofw Hash Table Out-of-Bounds Fix and N32 Timer Completion Landed (10-15)

Date: 2026-10-15 13:32 ~ 13:50 (merge time)　Source: PR #11845, PR #11812

Two community fixes were merged within the maintainer window. The first is a device tree ofw fix (#11845, 1 file +4/-2, merged by maintainer Rbb666): it corrects two out-of-bounds hazards in the phandle hash table — the allocation count is changed from max-min to max-min+1 (the lookup index is phandle-min, so when phandle takes the upper bound of the range it would originally access beyond the allocated region), and the expansion zeroing is changed to start from the end of the old table based on the old entry count (the original implementation did not subtract the starting value, so zeroing was incorrect when the starting phandle was not 1); the author validated at function level with 6 test cases under GCC using ASan/UBSan. The second is N32 timer completion (#11812, 39 files +3956/-105): it adds the previously missing clock source and ATIM/GTIM/BTIM instance table branches for N32H47x_48x and N32H49x (the two series share drv_tim.c but previously only the H7xx branch was implemented), changes the LPTIM tick to be derived from the real LSI, extends PWM and quadrature encoder synchronously, and adds ci-attach entries for the three boards that actually compile to the driver feature declarations, following up on #11800.

1.2 lwip Section Content Macro Control Proposal Merged: Three Network Stack Commits Concluded (10-15)

Date: 2026-10-15 13:04 ~ 13:28 (commit / merge time)　Source: PR #11815

1.3 9PFS Exposes Two Defects in Succession: ARMv7-A Unaligned Access Causes Kernel Abort, getdents Out-of-Bounds Read Confirmed Reproducible (10-15)

Date: 2026-10-15 20:33 ~ 21:18 (comment / creation time)　Source: Issue #11868, Issue #11289

Contributor XueDugu advanced two 9PFS filesystem defect cases within the window. The first is a newly opened defect ticket #11868: the 64-bit value-fetch macro on the receive path dereferences the buffer with an ordinary pointer (get_rx_value64_of); under ARMv7-A, GCC generates LDRD which requires 8-byte alignment, while the struct size of 292 and the protocol constant of 42 make rx_buffer+42 always 6 mod 8 — any Tstat response (including a completely normal response) will trigger an alignment exception and kernel data abort in dfs_9pfs_open / dfs_9pfs_stat; the report traces back to the commit that introduced 9PFS in 2025-12, gives a CVSS 3.1 rating of 7.5 (remote denial of service) with a complete reproduction chain on QEMU vexpress-a9, and includes disassembly and addr2line verification. The second is #11289, opened in March (the getdents path trusting the stat/name lengths sent by the server, causing an out-of-bounds read), which was confirmed reproduced by the community on master (bsp/simulator + ASan) on the evening of 10-15; the root cause is that the received byte count is discarded and record boundaries are not validated. Both cases remain open.

1.4 New Proposal: DFS-Layer F_GETFL/F_SETFL and Device Control Command Code Collision Disambiguation (10-16)

Date: 2026-10-16 00:51 (creation time)　Source: PR #11869

Contributor CXSforHPU opened a DFS-layer disambiguation proposal (2 files +56/-15): POSIX’s F_GETFL(=3), F_SETFL(=4) collide numerically with RT-Thread’s
RT_DEVICE_CTRL_CONFIG(=3), RT_DEVICE_CTRL_CLOSE(=4), and the two command sets share the same integer argument, so drivers may misinterpret under the fcntl path — dfs_v2’s ioctl is pure pass-through, and drivers such as serial may even treat F_GETFL as CONFIG to reconfigure hardware when LWP is closed. The proposal does not change the command encoding, but instead disambiguates by argument form: command 3 with an argument is forwarded to the driver, without an argument returns file status flags per POSIX; command 4 without an argument is forwarded to the driver, with an argument goes to the upper-layer setting, with both dfs_v1 and dfs_v2 implementations modified in sync while preserving the socket notification path.

1.5 Under-Review Proposal Evaluation: ESP32-C6 SPI Receives Three Line-Level Comments with Point-by-Point Author Response (10-15)

Date: 2026-10-15 13:38 ~ 16:30 (review / response time)　Source: PR #11846

The ESP32-C6 SPI support proposal (#11846) received three line-level review comments from maintainer Rbb666: first, with DMA disabled, the IDF single-transfer limit is 64 bytes, while the driver still submits whole packets, so a 65-byte message will trigger an abort and should be transferred in segments or at least return an error code; second, when C3/C6 share ESP-IDF-latest, building C6 permanently rewrites gdma.c to a four-argument call, and subsequently building C3 will report too many arguments, so a target macro or separate copy should be used instead; third, the bit-width check occurs after the bus is successfully initialized, so a 16-bit request that fails and is retried at 8 bits will abort because the bus is already initialized, and the check should be done before requesting resources. The author responded that each item will be rectified (segmented sending within the driver, retaining two sets of calls by target macro with bidirectional build verification, and moving the bit-width check earlier), and agreed to remove the rewrite logic in the build script.

1.6 Under-Review Discussion: Debate Deepens Over Whether to Keep the aarch64 GIC Acknowledge Path (10-15)

Date: 2026-10-15 13:57 ~ 19:39 (comment time)　Source: PR #11860

An in-depth technical discussion emerged within the window for the aarch64 GIC fix proposal (#11860): author Xenithya explained that what was removed is a redundant GICD_ICPENDR clear-pending write before EOI — when the same edge source re-asserts a new event during interrupt handling (as in their NPU scenario: first reporting an AXI error then reporting completion), this write erases the re-latched pending and causes the new interrupt to be permanently lost, and provided measured data: keeping the write results in a completion interrupt loss in about 19~33 inferences, while after removal the pure interrupt path had zero failures across 480,000 inferences. Maintainer GuEe-GUI responded twice: the semantics of this function need to be understood in terms of GIC non-EOI mode, and the problem may also lie in how traps.c calls the interrupt acknowledge interface, suggesting that the trap path modification be verified in parallel. The proposal remains open.

3.1 Community Project: SiFli SF32LB525 (Huangshan Pi) Board-Level FreeDOS Port Released (10-15 ~ 10-16)

Date: 2026-10-15 22:11 ~ 2026-10-16 03:08 (commit time)　Source: equence/sf8086

Community developer released the porting project sf8086: porting the 8086tiny emulator to the SiFli Technologies SF32LB525 (Huangshan Pi, Cortex-M33) development board based on RT-Thread, running FreeDOS directly on the board — the BIOS, boot floppy, and Turbo C 2.01 compilation toolchain all reside in firmware, with no dependence on external storage; the A: drive is a RAM disk rebuilt from flash on each boot (about 144 KB available), capable of running DOS tools such as EDIT, DEBUG, and ZIP; the RT-Thread shell and the DOS console share UART1 (including adaptation commits for serial arbitration, terminal key mapping, etc.). The project pushed 13 commits within the window, including an MS-DOS 6.22 boot disk build script and board-level running screenshots, with the repository tagged with topics such as rt-thread, sifli, sf32lb525, and freedos.

Other ecosystem channels remained silent within the window: the packages software package index (most recent merge 10-14), the Studio SDK index (most recent update 10-10), the env tool repository (most recent commit 10-09), the N32 device driver repository (most recent commit 10-14), and the GD32 vendor downstream all had no pushes within the window.
