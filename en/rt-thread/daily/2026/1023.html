I. Kernel and Version Dynamics

1.1 RISC-V ticket spinlock switched to AMO: unlock side no longer goes through LR/SC retries, K1 SMP config simultaneously raised from 4 to 8 cores (10-22)

Date: 2026-10-22 17:59 (merge time)　Source: PR #11904, cpuport.c, K1 BSP README

This change lands in libcpu/risc-v/common/cpuport.c, replacing the implementations of both the lock and unlock paths of the ticket spinlock. Previously both sides used an LR/SC loop to perform a read-modify-write on the same word: the lock side incremented the next-ticket number in the upper 16 bits, recombined it with the current-holder number in the lower 16 bits into a single word, and wrote it back; the unlock side likewise went through LR/SC to increment the holder number. The revised comments spell out two failure modes: first, the ticket-acquisition path and an unlock path retrying LR/SC can interrupt each other on the same reservation set, falling into livelock under high-core contention—this is precisely the SMP stall mentioned in the title; second, the unlock’s whole-word read-modify-write overwrites tickets newly claimed during the concurrent period.

The fix changes ticket acquisition to a single-instruction atomic add via amoadd.w.aqrl (AMO cannot fail, so there is no retry to be interrupted), with the ticket increment set to 1 << 16, keeping both 16-bit counters within the low 32 bits—the comment explicitly notes this also holds on RV64, hence the 32-bit-wide amoadd.w rather than amoadd.d. The unlock side drops the atomic read-modify-write entirely: only the holder writes the holder number, so a single 16-bit halfword store performing “increment by one” suffices, preserving concurrently claimed tickets and eliminating LR/SC; each side gains an rt_hw_barrier() to ensure critical-section memory accesses are ordered after observing the other side’s release, and that publication completes before advancing the holder number.

The same proposal changes CONFIG_RT_CPUS_NR in bsp/spacemit/k1 and RT_CPUS_NR in rtconfig.h from 4 to 8, and adds notes to the two K1 READMEs and the support matrix in bsp/README.md, following the order of “fix the lock first, then open up the core count.” Per the current K1 README, the SoC is 64-bit RISC-V with 8 integrated X60 cores and vector extension; the BSP uses device tree, is booted by U-Boot/OpenSBI running in S-mode, and the validation platform is the Banana Pi BPI-F3. The entire proposal spans 6 files with +33/-37—a modest change in size but one touching RISC-V multicore infrastructure.

1.2 Message queue FIFO preempted by higher-priority thread: two-year-old issue yields a minimal reproducer that reproduces reliably on mainline (10-22)

Date: 2026-10-22 13:54 (comment time)　Source: Issue #4940, ipc.c

The old issue from August 2021 was pushed forward again within the window. The issue originally pointed out that message queues and mailboxes cannot guarantee first-in-first-out under RT_IPC_FLAG_FIFO; the maintainer’s reply at the time acknowledged that “there is no locking here, whereas semaphore effectively does locking,” and no fix has landed since. The new comment follows this thread with a minimal reproducer and states it reproduces reliably on mainline.

The reproducer configuration creates a queue via rt_mq_create() with msg_size=4, max_msgs=1, and RT_IPC_FLAG_FIFO: a low-priority thread (20) first performs a blocking receive, and since the queue is empty it hangs at the head of the wait queue; a high-priority thread (10) does not enter the queue wait but instead blocks on a semaphore; the main thread sends a message, and the low-priority thread is removed from the wait queue and enters the ready queue; the main thread then releases the semaphore, making the high-priority thread ready; after the main thread delays to yield the CPU, the high-priority thread runs first and takes that message with a non-blocking receive. The message does not reach the waiter at the front of the queue—FIFO semantics are broken by priority preemption.

The nature of the problem differs from 1.1: it is not a race window but a semantic choice of “dequeue on wake”—once woken, the waiter leaves the wait queue and becomes an ordinary ready thread, after which any higher-priority non-blocking fetch can legitimately take the message it should have received. The comment mentions that uClinux’s approach is to wake without dequeuing, removing from the pending queue only once the lock is actually acquired, which can serve as a reference for a fix. The issue remains open, and there is no corresponding proposal in this issue.

II. Security and Stability Follow-up

2.1 NVMe leaks 4,480 bytes per inactive namespace: a compliant drive loses about 1.1 MB of kernel heap on every boot (10-23)

Date: 2026-10-23 01:15 (created)　Source: Issue #11919, nvme.c

Researcher XueDugu filed a kernel heap leak in the NVMe driver at the end of the window. nvme_scan_device() uses the device-controlled nn (Number of Namespaces) from the Identify Controller response as the loop bound, probing each ID from 1 to nn, and each iteration first does rt_calloc for a 4,480-byte rt_nvme_device before sending the Identify command for that ID. Neither failure path returns this memory: nsze == 0 (namespace allocated but not active, a normal response permitted by the spec) takes continue; an Identify command error takes goto _free_res, skipping the free.

Impact per the author’s measurements: under the default configuration of the official qemu-virt64-aarch64 BSP, idle kernel heap with no NVMe attached is 66,941,784 bytes; with a single-namespace drive reporting nn = 1 it is 66,931,592 bytes, which is normal; with QEMU’s stock nvme device it drops to 65,774,912 bytes — QEMU always reports nn = 256 while exposing only 1 namespace, and that response is legal, so 255 inactive IDs each leak 4,536 bytes (including the memheap header), i.e. 1,156,872 bytes, about 1.1 MB, per boot, or 1.8% of the 64 MB kernel heap. Hot-plug and rescan accumulate this linearly; if a device reports a larger nn (e.g. 0xFFFFFF), the loop keeps allocating until the heap is exhausted and the system can no longer boot, with the serial console stalling after hello rt-thread and never printing a prompt.

The author assigns CWE-401 and CVSS 3.1 4.9 (Medium, AV:P), noting that “the 1.1 MB per-boot leak needs no attacker”; only “heap exhaustion causing boot failure” requires a malicious or malformed controller. The defect was introduced by commit 945114fd5 (NVMe support, #9591) on 2024-11-24 and is present in every release since v5.2.0 and in current mainline. The recommended fix is to move this allocation to after the namespace is confirmed valid and add the missing frees on both failure paths, and not to trust nn directly as the bound (cap it by mnan, or use the CNS 02h Active Namespace ID list instead). The ticket is currently untagged and unassigned.

2.2 9PFS trusts the server length field directly: ASAN out-of-bounds read runs through the 8.3 MB receive buffer; fix proposal opened (10-22)

Date: 2026-10-22 19:36 (created)　Source: PR #11918, Issue #11289, dfs_9pfs.c

dfs_9pfs_read() and dfs_9pfs_getdents() contain out-of-bounds reads decoupled from the server reply length; the proposal (+58/-4) touches only dfs_9pfs.c. The root cause is that the byte count returned by p9_transaction() is discarded (passed as RT_NULL), after which the code directly uses the message’s count, each record’s stat_size, and name_len without ever comparing them against the amount of data actually received; as long as the server returns a message with a huge count but a short actual body, the parser reads past the receive buffer. Under normal conditions the skipped . records do not hit the fd->pos >= end exit condition, so the parser can keep advancing.

The author built a fake in-memory 9P server with bsp/simulator (x86-64, ASAN, -fsanitize=address): handshake and Tstat/Topen/Tclunk are answered normally, but Tread returns only an 11-byte message with count falsely reporting about 2 GB, and the area behind the receive buffer is filled with forged . records plus an ASAN poison guard band. Before the fix this triggers AddressSanitizer: use-after-poison, with the read position landing at byte 8,334,515 within the 8 MB heap region and the process ABORTing; after the fix the malicious reply is rejected (returning P9_READ_UNEXPECTED_DATA or -EIO), normal directory parsing is unaffected, and hello.txt and subdir are still listed.

The fix has four steps: both functions pass the actual received byte count into p9_transaction() and verify it is at least P9_MSG_READ_DATA; count is clamped to rx_size - P9_MSG_READ_DATA instead of trusting the message value; getdents validates per record whether the remaining bytes can hold the length field, whether stat_size exceeds the remaining data, and whether name_len exceeds the current record; the read path likewise clamps the actual bytes read (the author specifically notes that got <= set is insufficient, since set itself may exceed the receive capacity). The patch passes git apply --check on the latest master.

The change touches 55 files, +4564/-333, in three parts: C3 and C6 each adapted to the ESP-IDF v6.1 compatibility surface (portmacro.h FreeRTOS V11 declarations, sections.ld, port.c, main.c, rtconfig.py, and minor ADC/SPI driver changes); the RISC-V toolchain upgraded from gcc 11.2 (esp-2022r1) to gcc 15.2 (esp-15.2.0_20251204), with corresponding changes to the CI workflow, docker, and tools/ci; and the FreeRTOS-Wrapper changes explicitly split out into a separate proposal.

At merge time the author’s validation was build-level only: all thirteen C3 attachconfig configurations pass on gcc 15.2 plus the esp-idf #18 package, the C6 default configuration compiles and links, and the hardware on-board row reads “pending validation, C3 flash package ready.” In other words, this is a merge gated on build success. The significance for RISC-V is that C3 and C6 are RISC-V cores (unlike the Xtensa-based S2 and S3), and together with the already-merged package-side CONFIG_IDF_RTOS_RTTHREAD switch, this path is now in place from package to main repo, with the remaining risk concentrated on hardware bring-up.

4.2 GD32VW553 added to the at_device package: RISC-V Wi-Fi 6 plus BLE 5.2 chip selectable directly via menuconfig (10-22)

Date: 2026-10-22 09:21 (merge time)　Source: RT-Thread-packages PR #2047, GD32VW553 product page

The at_device package in RT-Thread-packages adds a GD32VW553 entry, +68/-0, consisting of one source line in iot/at_device/Kconfig and a new gd32vw553/Kconfig (67 lines). Configuration options cover the initialization mode (optionally initialized asynchronously by a thread), whether to enable AT socket, and example parameters: network device name defaults to wifi0, SSID and password, AT client device name defaults to uart4, serial baud rate defaults to 115200 (range 9600 to 2000000), receive line buffer length, and reset pin number and active level (-1 means no hardware reset).

The GD32VW553 is a wireless MCU in GigaDevice’s GD32V series; per the vendor product page it has a RISC-V core at up to 160 MHz, integrates 2.4 GHz Wi-Fi 6 (802.11b/g/n/ax, HT20) and Bluetooth LE 5.2, with 4 MB on-chip Flash and 320 KB SRAM, plus DSP hardware acceleration and a double-precision floating-point unit. Making it an AT device means RT-Thread does not drive the radio directly but treats the module as an external network device accessed over UART via AT commands — the same approach as the package’s existing ESP8266, ESP32, EC20, SIM800C and other entries, i.e. a low-cost connectivity path rather than a deep port.

4.4 scons –attach crashes outright on Chinese Windows: 4 emoji markers replaced with ASCII (10-22)

Date: 2026-10-22 18:00 (merge time)　Source: PR #11908, attachconfig.py

Four print lines in tools/attachconfig.py used emoji status markers, which makes the entire command unusable on Chinese Windows. The cause is that Python’s stdout encoding follows the locale code page (936/GBK on Simplified Chinese systems), which cannot encode U+2705 and U+274C, so the first print throws UnicodeEncodeError and aborts; since --attach=?, --attach=<name>, and --attach=default all go through the same function, all three paths fail together. Setting PYTHONIOENCODING=utf-8 works around it, but ordinary users would not know that.

The fix replaces the four occurrences with plain ASCII [OK] and [ERR] markers while keeping the existing ANSI color codes — tools/env_utility.py and tools/ci/bsp_buildings.py already use ANSI colored output, so this follows existing convention. The emoji under tools/ci/ were left alone because they are written into GitHub Actions summary Markdown and rendered as UTF-8, unaffected by console encoding. The change touches only 4 print lines with no logic involved; the author did a before/after comparison on Windows 11 Chinese edition with the default code page 936, using the ra6m3-hmi-board directory, currently the only BSP with an attachconfig.yml. This kind of issue does not involve the kernel, but it directly affects the first-time experience for domestic developers.

V. Summary and Trend Observations

5.1 Trends in This Issue

  • The RISC-V multicore path received two foundational pieces on the same day: the ticket lock was changed from bidirectional LR/SC retry to “acquire the ticket with AMO, release the lock with a half-word store,” eliminating the livelock surface at its root, and K1 was immediately opened up to 8 cores; meanwhile, ESP32-C3/C6 gained the ESP-IDF 6.1 base and the GCC 15.2 toolchain. The former fixes multicore correctness, the latter fixes the availability of the new base — both are “unremarkable but decisive for how stably things run” work.
  • The mainline shifted from idle to a concentrated wrap-up: after three consecutive days of zero commits, three proposals and four commits were merged within three hours on 10-22. The rhythm looks more like maintainers batching up a round of reviews and handling them all at once than a rebound in development intensity; since v5.4.0 there is only a version macro, indicating the release process has still not started.
  • “Device- or server-controlled metadata as length” has become a family of defects: the same researcher reported three issues within two days — an NFS out-of-bounds write, an NVMe heap leak, and a 9PFS out-of-bounds read — with 9PFS already carrying a convergent fix. The author himself traced this line back to older mtd-cfi and usbhost issues; patching them one by one costs far more than investigating by family.
  • Encoding problems on Chinese Windows are starting to be treated as fixable defects: scons --attach fails entirely because an emoji throws an exception under GBK, a high-frequency pain point for domestic developers. Fixes like this are low in technical sophistication but directly beneficial, and are worth viewing alongside other Windows adaptation items in the toolchain.
  • GigaDevice filled in wireless and UI foundational pieces together: within 24 hours, GD32VW553 entered at_device and the GD32EmbeddedUI example entered the LVGL package — the former a RISC-V Wi-Fi 6 module, the latter a UI example — pointing to a complete solution rather than a single-point commit.
