I. Three CVE Fixes Merged: Random Numbers, Wireless Frames, and rt-link

1.1 Random Numbers: Seed Changed from a Fixed Value to tick and a Hardware Source (11-12)

Date: 2026-11-12 15:51 (merge time)　Source: PR #12022

rt_random had always been a predictable linear congruential generator, with a fixed default seed, so the sequence it produced was identical on every boot. Code that used it as a cryptographic random number source was effectively writing the key into the boot image. The PR description ties the risk directly to CVE-2024-25389 and the older issue #8283, and the merge makes three changes: mixing rt_tick_get() into the seed on first read; XORing hardware output into the return value when a hardware cryptographic random source is enabled; and stating clearly in Kconfig and code comments that this is not a cryptographically secure random number generator.

The change is small: two files, 70 lines added, 2 lines removed, and apart from rt_random.c only 6 lines of explanatory text in Kconfig. It was merged by Rbb666, and the author is the same account that has been submitting audit checklists all week. The significance of this change is not in the amount of code but in the fact that it acknowledges one thing: writing “not a CSPRNG” into the configuration interface is more reliable than quietly swapping the algorithm.

1.2 Wireless Management: Negative Length Rejected Before Allocation (11-12)

Date: 2026-11-12 15:47 (merge time)　Source: PR #12020

The length parameter of rt_wlan_send_to_thread() is a signed integer, so an expression such as sizeof(header) + len wraps around to a huge unsigned value when len is negative; the subsequent allocation and zeroing then proceed using that value, and the heap is overwritten past its bounds. The fix puts the check first: len < 0 returns a parameter error immediately, and only after confirming the value is non-negative is it converted to an unsigned type for the length calculation.

One file, 9 lines added, 3 lines removed, corresponding to CVE-2024-25388 and issue #8285. The PR body deliberately includes the sentence “all other wireless management behavior is unchanged”; in a security fix this sentence is necessary: the closer a change is to a common path, the more its impact surface must be spelled out.

1.3 rt-link: This Time the Fix Is on the Transmit-Side Framing (11-12)

Date: 2026-11-12 10:23 (merge time)　Source: PR #12018, Bug #8289

The previous issue covered long-frame reassembly on the rt-link receive side (issue #12030 and PR #12031); what was merged today is the transmit side of the same module: the final frame length is not validated before framing, so an oversized payload writes straight through the static transmit buffer. The fix checks the data length and frame length before copying, and rejects anything out of bounds.

One file, 23 lines added, 3 lines removed, corresponding to CVE-2024-25395. Looking at the two days together, the problems on rt-link’s transmit and receive paths take the same form: the length in the frame header is treated as trusted input, yet it comes precisely from the link peer. The receive side was found through an issue, the transmit side was dug out through the CVE list, and the two threads converged in the same month.

II. The Other Three Merged in the Same Batch: libdl, Memory Pool, NFS

2.1 libdl: Three Architecture Relocators Fixed Together (11-12)

Date: 2026-11-12 14:35 (merge time)　Source: PR #12016, Issue #11898

When computing the relocation write target, the dynamic module loader used “module memory base + offset - virtual start address” without validating the resulting range. A crafted module file could make the offset underflow or overflow, writing directly into kernel memory during the relocation phase. The fix adds a target-range validation function that uses overflow-safe arithmetic to confirm the write range falls within module memory, then wires it into the ARM, RISC-V, and x86 relocators. It also adds bounds checks for ELF section header indices, symbol table indices, and relocatable object file sections, aborting on load failure and freeing already-allocated section memory.

This is the largest change in the batch: five files, 205 lines added, 37 removed. Three architectures changed at once indicates the problem lies in the shared loading path, not in any single port. Corresponds to Issue #11898 from October 18.

2.2 Memory Pool: The Sentinel Convention Behind a False Alarm (11-12)

Date: 2026-11-12 10:14 (merge time)　Source: PR #12014

This fix addresses not a vulnerability but a misjudgment that causes real downtime. When freeing “the last block, whose next points to the heap-tail sentinel,” the validation logic required the next entry’s memory pool pointer to equal the current pool. But older versions and vendor-customized small memory pools keep only the used bit in the sentinel, leaving the pointer null—so the assertion fires and the system halts.

The fix explicitly accepts the case where “next equals the heap-tail offset,” while keeping the same-pool check for everything else. In the description, the author explicitly rejects the simpler alternative of checking prev, on the grounds that prev points to the previous block and is 0 for the first block, which would loosen the validation overall. A memory test case is included that simulates a sentinel with only the used bit set and verifies full-block coalescing.

Corresponds to the older Issue #10632 from 2025. Such issues never appear on any CVE list, but they may cause more field reboots than vulnerabilities do.

2.3 NFS: Clamping the Server-Supplied Length to the Minimum of Three (11-12)

Date: 2026-11-12 09:35 (merge time)　Source: PR #12012, Issue #11917

The NFS read path used the byte count returned by the server directly as the memory copy length, accounting for neither the requested amount nor the decoded data length. The fix clamps each copy to the minimum of “server count, request count, decoded length,” advances the buffer and offset by the actual bytes copied, and breaks out of the loop on a response that makes no progress, avoiding a busy loop.

Two other spots in the same function were fixed as well: the write path advances by actual bytes on short writes; and when an RPC failure occurs after a partial read succeeds, it returns the bytes already read instead of zeroing the accumulated value and making the caller believe zero bytes were read. Three files, 67 lines added, 15 removed, with the read and write upper bounds unified under the same maximum transfer unit definition. Corresponds to Issue #11917 from October 18; review checked each item on the 11th and approved.

III. Second Batch of Ten Commits: One Each for M0 and M23 on the Same Issues

3.1 HardFault Stack Selection: Old Assembly-Layer Defect Fixed on Two Ports (11-12)

Date: 2026-11-12 13:26 and 14:19 (proposal time)　Source: Proposal #12043, Proposal #12049, Defect #3584

The hardware exception entry on Cortex-M0 and M23 unconditionally takes the stack frame from the process stack pointer. For a hardware exception triggered inside an interrupt service routine, the stack frame is actually pushed onto the main stack pointer, so the backtrace shows the wrong context. The fix selects between the main stack and the process stack based on the relevant bit in the exception return value, aligning with the existing approach in the M3 port.

Each proposal modifies three assembly files (GCC, RVDS, and IAR toolchains), adding 21 lines and deleting 3. Defect #3584 is a long-standing issue from years ago; this time the same author completes it on both ports, clearing historical debt port by port.

3.2 Do Not Restore MSP When VTOR Is Zero (11-12)

Date: 2026-11-12 13:29 and 14:30 (proposal time)　Source: Proposal #12044, Proposal #12050, Defect #4728

On the first context switch, the code reads the top of stack through the vector table offset register to restore the main stack pointer. On cores without this register, or when the read value is zero, this effectively writes zero to the main stack pointer, and the next push lands at address zero. The fix skips the restore when the read value is zero and keeps the original behavior when non-zero.

Same paired structure as the previous item: one for M0 and one for M23, each modifying three assembly paths. Together the two add 18 lines; defect #4728 is likewise an old issue.

3.3 FIFO Inversion in mb/mq: Head-of-Queue Bypassed (11-12)

Date: 2026-11-12 13:56 (proposal time)　Source: Proposal #12045, Defect #4940

Under the FIFO flag, mailboxes and message queues wake only the head waiter, but the data remains in the shared queue. A higher-priority thread can then take the message in non-blocking mode, leaving the woken waiter with nothing; it can only re-queue at the tail, reversing the first-come-first-served order. The fix performs resource reservation and handoff on the FIFO path—”dequeue only after acquisition”—returning the reservation on timeout or signal interruption; priority mode behavior is unchanged.

One file, 435 lines added, 12 deleted: the largest of this batch of ten and the only one that directly touches kernel scheduling semantics. Defect #4940 is another old debt. If merged, this will change the actual behavior of mailboxes and message queues under high-priority preemption and deserves a separate mention in the next release notes.

3.4 Four Small Fixes: fdt Depth, musl Console, UART Timing, sdio Thread Stack (11-12)

Date: 2026-11-12 13:23 to 14:14 (proposal time)　Source: Proposal #12048, Proposal #12047, Proposal #12042, Proposal #12046

The device tree expansion function descends into child nodes using a fixed-size stack but has no runtime depth limit; the existing depth pre-check only takes effect in debug builds, so release builds can still overflow the stack (#11879): add a limit check before pushing, failing and returning when exceeded.

Under the musl library configuration, when the kernel sets up the console it calls the user-space file-open interface; after trapping into the syscall table the number is mismatched and the console cannot be opened (#11716): switch to the kernel filesystem’s strong-symbol path without touching the syscall table, so the user-space binary interface is unaffected. This commit deletes more lines than it adds—a rewrite back to the correct layer.

Under the Smart configuration, the UART is registered as a terminal device before the work queue is created, which can hang at startup (#11718): when the work queue is not ready, put the UART on a pending queue and complete registration during component initialization. The sdio interrupt thread’s default stack size originally followed the idle thread, and when the idle thread stack is set to 512 this path easily overflows (#11694): change it to an independent default of 2048.

All four are marked as statically verified, not board-tested. They extend the same audit line, only shifting from “out-of-bounds writes” to “initialization timing” and “default configuration.”

IV. Features and Compatibility: STM32 Input Capture, YMODEM Delay

4.1 STM32 Input Capture: Four Channels per Timer (11-12)

Date: 2026-11-12 19:32 (proposal time)　Source: Proposal #12052

The existing STM32 input capture driver registers devices per physical timer, so only one capture channel can be selected per timer; the remaining idle channels on the same chip go unused, and there is no channel-pair-based PWM input or dual-edge capture mode. The proposal extends the driver so that one physical timer can register multiple independent edge-capture devices (timers 1 through 4 each selectable on channels 1 through 4), with exclusive PWM input or dual-edge mode selected per timer.

Five files, 1529 lines added, 290 deleted. Among a week of audit proposals, this is the only functional extension, contributed by a community contributor rather than the audit line. Structural driver changes usually require board-level verification, so the review cycle will be longer than for safety fixes.

4.2 YMODEM: Forty Milliseconds Between ACK and C (11-12)

Date: 2026-11-12 17:41 (proposal time)　Source: Proposal #12051

After receiving the second end-of-transmission character, the YMODEM receiver sends two bytes back to back: the acknowledgment and the character C. When sent back to back, if the sender’s UART driver timeout setting or interrupt handling is not robust enough, one of them gets swallowed (only the acknowledgment is read, the character C is missed), and the sender declares the transfer failed. The fix inserts a 40 ms delay between the two sends.

One file, 7 lines added. This kind of fix does not change protocol semantics; it merely leaves a gap for unreliable UART links—field experience written back into code.

V. Official Statements and Community Activities

5.1 RT-Smart Toolchain: Same Issue Proposed Twice, Closed Twice (11-13)

Date: 2026-11-10 to 2026-11-13 (issue and closure times)　Source: Issue #12025, PR #12041, PR #12028

The issue itself is a compilation problem: after enabling Smart and vDSO on a QEMU virtual machine, building the user-space library with the newlib toolchain leaves four clock constants undefined. The maintainer reproduced it on November 10 and proposed a fix, then self-corrected three hours later, concluding: “For Smart, the toolchain must use a special compiler with a modified musl library; the standard newlib toolchain is not supported, and this issue should not be handled.” The first PR was closed the same day.

Early this morning, the same author submitted a second PR adding a compatibility header that supplies fallback values for the missing constants matching the Linux interface numbers (monotonic raw 4, realtime coarse 5, monotonic coarse 6, boottime 7), and stated that the clock-to-index mapping was unchanged. This PR was closed at 06:04 Beijing time today, and the issue was closed as completed at the same time, with a single comment: this issue is being closed for now; some relationship documentation needs to be provided later.

Two PRs, two closures, and the outcome shifted from “fix the code” to “document it.” For developers using Smart, this is more useful than the fix itself: choosing the wrong toolchain will stall you at the compilation stage, and the official documentation does not currently make this relationship clear.

VI. Summary and Trend Observations

6.1 Yesterday’s Forecast for Phase Two Materialized the Same Day

The previous edition’s assessment was that “the audit is shifting from the CVE list to the project’s own issues,” and today’s facts connect the two: the batch of PRs opened on November 9 and 10 was merged in six commits during the daytime of November 12, three of them carrying CVE numbers (random number, wireless management, rt-link send side), and the other three covering dynamic module relocation, memory pool assertions, and NFS read length.

Merge times ran from 09:35 to 15:51 Beijing time, completed within six hours. The same person merged all of them, indicating that this line of work has entered a stable review channel and is no longer scattered community submissions.

6.2 Verification Standard for the Six Merges: All Marked as Not Board-Tested

The verification sections of all six are almost identical in phrasing: static review, no board run, no attack samples constructed. The only one with automated test cases is the memory pool commit, which includes over forty lines of tests; for the NFS commit, one reviewer checked the implementation item by item and gave a conclusion.

This is both the source of efficiency and the source of risk. Static review can catch arithmetic errors in lengths and indices, but not timing and concurrency. Proposals that change kernel semantics, such as “fetch first, then dequeue,” still need board-level and stress-test evidence before they can be trusted.

6.3 Three CVE Proposals Still in the Queue

The other three CVE-numbered PRs from the same batch saw no activity today: command-line file operation path construction (CVE-2024-25390), variable export table population (CVE-2024-25392), and YMODEM path copy (CVE-2024-25394). Their shape is similar to the six already merged—unbounded copies and capacity limits—and the lack of review may simply be scheduling.

Several other non-CVE PRs remain in the queue: Smart’s inter-process object ownership validation (#12015, a semantic overhaul spanning multiple files), the ESP32-C3 chip revision field (#12013), and DHCP expired lease reclamation (#12024).

6.4 Review Queue: 163 PRs, 358 Issues

Compared with the previous edition, PRs are up 5 and issues down 7. The drop in issues corresponds to several items closed today (including old issues closed alongside merged PRs and the Smart toolchain issue), while the increase in PRs comes mainly from the ten opened today.

Single-account concentration is worth noting: the six merged today and the ten newly opened (including one closed the same day) come from the same author, and the merges were done by the same maintainer. One audit line advanced by one person and gated by one person is efficient, but it also means the pace of this line depends entirely on these two people’s time.
