1.1 Next RISC-V Architecture Refactor Proposal Gains Founder’s Merge Push, Submitter Rebases and Refreshes Overnight (09-29 ~ 09-30)

Date: 2026-09-29 21:09 (founder’s comment) ~ 09-30 00:01 (latest commit)　Source: PR #10320

The long-stalled main-repo RISC-V architecture refactor proposal “Next RISC-V” (#10320, 171 files, +15018/-3490) received a clear push forward within the window: founder Bernard Xiong commented at 09-29 21:09, “This PR should be mergeable soon; meanwhile, try enabling device tree on some RISC-V SoCs as well,” and named maintainers and the submitter to follow up. Subsequently, submitter GuEe-GUI triggered three consecutive refresh cycles for the proposal from that evening into the early hours of the next day (21:22, 23:54, 00:01, with the formatting and memory-comparison pipelines rerunning accordingly), and the latest head commit “Refactor the RISC-V architecture port” was rebased at 09-30 00:01 onto the current mainline head dc8aaa73f. Key points of the proposal: ISA management interfaces, RV32E/32I/64I unification, CBOM-based cache handling, Sv32~Sv64 MMU and SVPBMT, merged M/S-mode CSR operations, SMP, AIA (APLIC/IMSIC), CLIC, ACLINT/CLINT, PLIC, device tree (DM) support, T-HEAD vendor code merge, qemu-virt64-riscv64 device tree port, and booting from a non-zero core. The plan checklist shows S-mode RT-Thread, RT-Smart, and the device tree path have been verified, while remaining combinations (including M-mode and no-MMU) are still in progress. Since its submission in 2026-05, the proposal has accumulated 74 review comments.

1.2 Kernel calloc Overflow Fix Proposal Passes Review (09-29 ~ 09-30)

Date: 2026-09-29 22:34 (submitted) ~ 09-30 08:30 (LGTM received)　Source: PR #11848

Contributor luchenxu73 submitted kernel fix #11848 (single commit, 3 files, +57/-3): rt_calloc does not check whether count×size overflows during allocation; when the limit is exceeded the result wraps around, creating an out-of-bounds risk from inconsistent allocation and zeroing. The fix precomputes the allocation size and rejects allocation when the limit is exceeded, touching include/rtdef.h, src/kservice.c, and the memory unit test src/utest/mem_tc.c (new test case), verified on qemu-vexpress-a9. The proposal received a community review “LGTM” at 08:30 on the morning of 09-30, making it the fastest-advancing new proposal within the window.

1.3 Three Driver and BSP Fix Proposals Submitted Together: ofw Hash Out-of-Bounds, ESP32-C6 SPI, ESP32-C3 Linker Script (09-29)

Date: 2026-09-29 20:11 ~ 21:53　Source: PR #11845, PR #11846, PR #11847

Within roughly an hour and a half on the evening of 09-29, the community submitted three fix proposals in quick succession, all with test evidence, still pending review. The first (#11845) fixes an out-of-bounds access in the device tree (ofw) phandle hash table: the number of allocated entries uses the difference of the range, while the lookup index is computed from the difference between the phandle and the start value, causing an out-of-bounds access when the upper bound of the range is accessed; during expansion, the zeroing position also fails to subtract the start value. The fix adds one to the entry count and, during expansion, zeroes the newly added region starting from the end of the old table. The author completed function-level verification of 6 test cases with GCC plus AddressSanitizer/UBSan (start phandle values of 1, 5, and 128, plus a test expanding the upper bound of 128 to 256). The second (#11846) enables on-demand compilation of SPI for Espressif ESP32-C6: after selecting BSP_USING_SPI, it hooks into the IDF SPI master, fixes issues where the shared ESP driver did not return the number of transferred bytes and the chip-select pin value, and returns -RT_EINVAL when the configuration is empty (6 files, +466/-19). The third (#11847) fixes wildcards in the ESP32-C3 linker script under Windows paths: wildcards written with “/” in sections.ld fail to match the riscv directory object files in Windows target paths, causing vector jump relocations to exceed the limit; switching to “?” makes it compatible with both separators. This is the same change as #11816, redone this time on the latest mainline, with scons build passing under Windows with GCC 11.2.0.

IV. Industry Applications

4.1 Universiti Sains Malaysia Final-Year Project Update: RA8P1 + RT-Thread Edge Acoustic Event Detection Firmware Verification (09-30)

Date: 2026-09-30 05:49 ~ 05:50 (commit time)　Source: KhaiFaw/ai-acoustic-event-detection

The third-party project under the topic:rt-thread ecosystem, “Acoustic event detection at the edge” (a mechatronics engineering final-year project at Universiti Sains Malaysia), submitted two consecutive updates within the window: reconciling the acoustic firmware build with the model contract, fixing an input scaling inconsistency between the embedded model and the firmware, and adding software verification records (16 host tests and one full BSP local build passed; the corrected firmware has not yet been evaluated via on-device flashing). The project is based on the Renesas RA8P1 Titan board: RT-Thread provides the OS framework, Renesas FSP provides device support, CMSIS-DSP implements the FFT, and TensorFlow Lite Micro runs the INT8 CNN; a MAX9814 microphone captures 16000 audio samples, which after MFCC feature extraction are used to classify six sound categories on-device: baby crying, glass breaking, alarm/siren, knocking, doorbell, and background.
