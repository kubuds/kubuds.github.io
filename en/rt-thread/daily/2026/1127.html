Source: #12054.
#12090.

#12054 was closed at 10:33 without merging. It was opened on November 14, with 10 commits, 46 files, 8946 lines added and 5521 lines deleted. Two minutes later, the same branch refactor/can-framework was resubmitted as #12090, with 12 commits, 46 files, 8936 lines added and 5549 lines deleted.

The author wdfk-prog’s first comment under #12090 was a complaint about rebase costs. Some BSPs’ CAN had been updated on master, and merge conflicts forced a rebase. Maintainer Bernard Xiong replied “bring in an AI Agent, let AI watch it,” and mentioned the env pilot. This reply does not change the technical conclusion.

The refactor’s responsibility boundaries are clearly defined in this version. Generic CAN is only responsible for hardware resource management, synchronization, ownership, terminal, and lifecycle. Transmit buffering, retries, scheduling, and protocol QoS are delegated to the upper protocol stack or application. The new design removes the TX software queue and uses the controller’s hardware mailboxes directly as the sole queuing resource.

#12090’s CI has 30 checks: 27 passed, 3 skipped, no failures.

Assessment: The renumbering is not a change of approach. The basis is identical file counts, with 10 fewer lines added and 28 more lines deleted—the same branch rebased.

1.3 Maintainer’s Initial Review of #12090: Two Open Questions, Explicitly Not an Approval (11-27)

Date: 2026-11-27 03:06 (review).
Source: #12090.

Bernard Xiong gave an initial review conclusion for head e2224ab and stated the coverage was incomplete. The reviewed scope includes the contract in can_internal.h and the full text of can_tx.c and can_rx.c. It also includes the open/close/control lifecycle in dev_can.c, and the sendmsg and TX interrupt critical paths in STM32 bxCAN. Not reviewed: the remaining 30 BSP adapters, all API changes in dev_can.h, Kconfig and the CI matrix, and the utest cases.

The first open question is that STM32 bxCAN has AutoBusOff disabled. Lines 173 to 175 of drv_can.c change ABOM from ENABLE to DISABLE, while also changing AutoRetransmission to ENABLE. The proposal description does not explain this behavior change. With ABOM disabled, the controller will not automatically recover after entering bus-off. Calling RT_CAN_CMD_START at this point returns -RT_ERROR because the HAL state is not READY. Users can only close and reopen, going through DeInit and configure to recover. The review considers this a visible regression for fieldbus scenarios that rely on automatic bus-off recovery.

The second open question is that the data path remains closed after a management operation fails. _can_reconfigure() jumps directly to out_unlock when a BSP operation returns an error. At this point TX admission is already closed and RX is paused, with no rollback except for SET_PRIV parameter validation. After SET_BAUD, SET_FILTER, or CONFIGURE fails for hardware reasons, the device still cannot send or receive until START is called again or close/open is performed. The review offers two paths: if fail-closed is intentional, document it in the public API; otherwise, restore was_accepting and RX admission for non-STOP commands.

The review concludes by stating: no real-board verification; 46 files and 8936 lines added constitute a large refactor; recommends a complete review in the next round before deciding whether to approve.

II. Review Progress: Two Converge, One Awaits CI

2.1 serial_v2 DMA cache-line alignment approved by maintainer (11-27)

Date: 2026-11-26 11:16 to 2026-11-27 03:03.
Source: #12084.
Issue #12063.

Issue #12063 concerns an old problem with Cortex-M7 after enabling D-Cache. The serial_v2 DMA ping buffer is allocated within the RX FIFO block, and its start address is never 32-byte aligned. When SCB_InvalidateDCache_by_Addr invalidates a cache line, it also corrupts the heap blocks before and after it. The TX side carries the same risk.

The proposal aligns the ping buffer start address to 32 bytes after the ringbuffer. dma_ping_bufsz is rounded up to an integer multiple of the cache line, and the total allocation size is adjusted accordingly. Author liangzhan5 also reverted the local fix in the hpmicro BSP. The change touches 1 file, adding 9 lines and deleting 2. The author notes having no physical board on hand and performing static analysis only.

At 11:16, Rbb666 raised two inline comments. The first targets the hpmicro revert. The HPM6750 cache line is 64 bytes, while the framework only guarantees 32-byte alignment. After removing the BSP alignment, a flush on non-blocking DMA TX may write back the FIFO head or adjacent heap blocks along with it. The second targets the allocation condition: it only checks the global RT_SERIAL_USING_DMA, so boards using pure interrupt reception would also allocate an extra 32 bytes.

The author replied that evening at 21:00. The TX-side change was dropped, on the grounds that “there is actually no real scenario that needs protection.” The HPM BSP alignment is retained, and that file is no longer touched.

At 03:03 on November 27, Bernard Xiong approved on head 156fbaf. The review confirmed the change now retains only the RX ping buffer alignment, removes the TX-side change, and keeps the HPM BSP alignment — the right direction. The implementation computes the offset as sizeof(struct rt_serial_rx_fifo) + rx_bufsz. Allocation reserves RT_ALIGN(dma_ping_bufsz, RT_CPU_CACHE_LINE_SZ) plus one extra cache line, then aligns the start address.

Assessment: This is the only proposal in this issue that completed the full review cycle. The basis: comments, rework, and approval closed within 24 hours, and the disputed point was narrowed to a single buffer.

2.2 devtmpfs out-of-bounds write: conflicts and reproduction addressed, seven pending runs approved before CI release (11-27)

Date: 2026-11-26 20:06 to 2026-11-27 03:03.
Source: #11842.

#11842 fixes a stack overflow in devtmpfs. _path_separate() and _get_subdir() do not accept a buffer length, and rt_memcpy a path component of arbitrary length into the caller’s 256-byte stack array. dentry->pathname can be up to 4092 bytes, so a single component exceeding 255 bytes overflows, with the out-of-bounds reach at about 3.8 KB — enough to overwrite the return address. The upstream tmpfs functions of the same name already validate parent_size, file_size, and name_size and return -ENAMETOOLONG; the devfs copy is a missed item.

At 20:06, author HANYAODONG reported two things. The conflict was resolved, and mergeable_state changed from dirty to unstable. The conflict was confined to one file.
Its path is .github/utest/configs/components/dfs.cfg. Master’s #12067 renamed the dfs utest options; the merge keeps master’s form and appends its own config after it.

The verification gap was also closed. The author replayed locally on bsp/qemu-vexpress-a9 in the exact order of utest_auto_run. Appending dfs.cfg to .config, generating with scons –pyconfig-silent, then compiling with scons. RT_UTEST_TC_USING_DEVTMPFS_PATH appears in rtconfig.h, compilation passes, and all three test cases PASSED under QEMU.

At 03:03 on November 27, Bernard Xiong re-reviewed the new head ebbaae39. Relative to 56382719, it adds only a merge commit with origin/master; the PR’s own 5 files have no new changes. The earlier static review conclusion on 557c58de still holds. The conflict is cleared, and unstable is only because the new head’s workflows await approval.

The maintainer then approved the 7 pending runs on that head. These include pkgs_test, ToolsCI, MemBrowse, format check, utest_auto_run, static analysis, and BSP static build. The conclusion leaves an opening: it cannot yet be confirmed whether utest_auto_run passes, and it will be updated once the devtmpfs test case actually runs in CI and PASSED.

III. Allwinner V861: Third Review Round, 15 Inline Comments

3.1 Heterogeneous Demo Fails: No Response on the C907 Side (11-26)

Date: 2026-11-26 11:13 (review).
Source: #12078.

#12078 adds E907-side board support plus a minimal heterogeneous demo. 2 commits, 77 files, 8791 lines added. Rbb666’s summary is a single sentence: flashing the PR’s two images per the README, the heterogeneous demo does not run, because there is no response from the C907 side.

Specifically, at applications/main.c line 11, C907 only prints and exits, without writing AMP_SLOT_C907 and AMP_SLOT_C907_REPLY. E907 waits until HETERO-FAIL.

Another point targets e907’s main.c line 92. The code directly reads the old MSGBOX address 0x03003010, while #12079 has marked this base address as unusable. The review asks for this read to be removed. The rationale: the DRAM round trip does not depend on this probe, and when unmapped it also triggers a memory access exception.

3.2 UART0 Ownership and Exception Return: Three Proposals Share the Same Flaws (11-26)

Date: 2026-11-26 11:08 and 11:13 (review).
Source: #12078.
#12079.

The UART0 problem appears twice. On startup, C907 resets the UART0 that E907 is using; FinSH on both sides enables interrupt-driven reception, and both contend to read the same FIFO. The review asks for a single designated UART0 initialization and receive endpoint for heterogeneous mode. #12079 is more direct: e907’s main.c line 83 initializes uart0 again, which clears the FIFO and disables the receive interrupt, and the duplicate registration itself will also fail.

The exception handling problem also appears twice. In both proposals, board/trap.c line 27 returns directly from synchronous exceptions, restoring the original mepc, so the faulting instruction triggers repeatedly. The review asks for mcause and mepc to be recorded on both sides before entering exception handling.

Stack size is the third hard conflict. #12077’s Kconfig line 24 makes the SMP interrupt entry compute each core’s stack top from configuration, while the startup assembly and linker script still hardcode 8192. Raising the configured value makes the interrupt stack overrun the reserved region; the review asks for a single source of truth for stack size. E907’s Kconfig line 21 is the opposite direction: menuconfig can still enable SMP, but E907 has no SMP port compiled in and no secondary-core startup path.

3.3 Naming and Driver Sharing: Two Proposals Asked to Rework the Same Spots (11-26)

Date: 2026-11-26 11:08 and 11:13 (review).
Source: #12078.
#12079.

The naming issue points to two places. drv_rpmsg and drv_openamp actually only wrap shared-memory ping/reply, not the full libmetal or virtio-rpmsg stack. The review asks for names that reflect actual functionality, such as drv_amp_mailbox and drv_amp_endpoint, with references on both sides and the README updated accordingly.

The driver-sharing issue also recurs. The UART, FDT, and MMC driver sources are identical on both sides and should be moved under Allwinner’s libraries/drivers/, with both BSPs referencing the same implementation. The E907-side MMC copy does not participate in the build at all.

#12079 has two more details. drv_openamp.c line 189 reads the doorbell first, which consumes the OA_EVT_LINK sent by E907, so the host side may time out first; the review asks for stale tokens to be filtered in the link loop. e907’s main.c line 146 compares by reply length, so a truncated reply passes acceptance as long as the prefix matches; the review asks for send and receive lengths to be validated as equal first.

The documentation does not match either. #12079’s main now outputs OPENAMP-EPT-OK, while the README still uses RPMSG-OK as the acceptance criterion.

As of this issue’s cutoff, all three proposals remain open, and the author has not yet replied to this batch of comments. CI status: #12078 has 26 of 30 passing with 4 skipped, #12079 likewise 26 passing and 4 skipped, #12077 has 28 passing and 2 skipped, with no failures.
