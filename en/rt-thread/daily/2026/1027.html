II. Security and Stability Follow-up

2.1 signalfd global counter out-of-bounds: from the 11th call onward, kernel pointers are written outside the heap block (10-26)

Date: 2026-10-26 16:13 (creation time)　Source: Issue #11933

This is the most significant item in this issue. The researcher points out that
components/libc/posix/io/signalfd/signalfd.c uses a file-scope global counter is_head_init to index the per-file-descriptor private array sfd->lwp[10], and signalfd_add_notify() performs no bounds check before use. signalfd_close() never rolls back this counter, so it only increases and never decreases; when a new context is created, only lwp[0 .. is_head_init-1] is cleared, so a second creation in the same process can never match its own entry and inevitably takes the write branch.

The consequences are described concretely: lwp[] is the last member of struct rt_signalfd_ctx, and the entire structure is 1536 bytes on arm32, so the array sits exactly at the end of the heap block. On the 11th call to signalfd(-1, ...), the write lands on the first word outside the allocated block, i.e., the next block header of the small memory allocator; thereafter each creation pushes it 4 bytes further out (8-byte stride on 64-bit), forming a continuous kernel heap out-of-bounds write whose pace is controlled by the caller, and the value written is a kernel pointer.

The impact scope was checked tag by tag by the author: the introducing commit is 7c3d966d (#8001) from 2023-09-11, and v5.0.2 / v5.1.0 / v5.2.0 / v5.2.1 / v5.2.2 / v5.3.0 as well as current master (5d1fb66d) are all affected. The only trigger precondition is RT_USING_SMART=y—RT_USING_POSIX_SIGNALFD defaults to y under that configuration, and both official QEMU Smart BSP configurations also enable it, so a default RT-Smart build can trigger it. Reproduction uses bsp/qemu-vexpress-a9 (Cortex-A9, 32-bit, FAT sd card root filesystem), with the PoC installed as /sbin/init.

Currently there is no corresponding fix proposal for this issue, and it has not been labeled.

2.2 musl thread list use-after-free under concurrent exit: the futex lock fails to provide mutual exclusion (10-26)

Date: 2026-10-26 11:22 (creation time)　Source: Issue #11932

The second defect report comes from another reporter, in an environment of RT-Thread 5.2.2 RT-Smart, SMP, aarch64, musl 1.2.5. The symptom is a user process crash during concurrent pthread_create and pthread_exit, with the crash point in musl_pthread_exit: the thread descriptor written during list removal has already been freed or unmapped (Data Abort), or the thread’s return address has been overwritten with 0 (Instruction Abort).

The author’s conclusion is that the problem is entirely in user space: musl uses the futex-based __tl_lock / __tl_sync to protect the thread list, but under SMP concurrent exit this set of locks does not truly provide mutual exclusion, causing the doubly linked list to be corrupted; the kernel-side futex implementation itself is semantically correct and is not responsible for this defect. The reproduction material is a 1000-round, 8-thread tl_race program, which crashes within a few hundred rounds.

This issue carries three labels: bug, Arch: ARM/AArch64, and RT-Smart, and includes a complete analysis document. Like 2.1, it falls on the RT-Smart line, but at a different layer: 2.1 is the kernel heap, while this one is user-space libc.

2.3 Two time subsystem fixes move to mature status: settimeofday cast removal, gmtime_r handling of negative timestamps (10-26)

Date: 2026-10-26 14:17 and 17:48 (last updated)　Source: PR #11928, PR #11929

The two corresponding fixes for the four time subsystem issues recorded in the previous issue advanced one step within this window, and both checked “mature version, can be merged”.

#11928 changes only one file, +185/-135: settimeofday() originally cast tv_sec with (long) before checking its sign; under a configuration where ILP32 has a 64-bit time_t and a 32-bit long, valid timestamps between 2^31 and 2^32-1 are truncated into negative numbers, and the function rejects them with EINVAL before touching the RTC device—2208988800 (2040-01-01) is rejected this way. The fix validates by the field’s own type without casting.

#11929 changes two files, +104/-9: gmtime_r() splits the timestamp using C division and modulo, but C division truncates toward zero, so under negative input the remainder is negative, and the year loop can only move toward the future; thus -1 yields 1970-01-01 00:00:-1, and -31536000 turns the year field into 1970-01--364. The fix normalizes the negative path before splitting.

Neither has been merged. The other two (the timer_gettime() truncation #11924 and the time subsystem work item investigation #11927) saw no new progress in this window.

Date: 2026-10-26 09:15 and 11:37 (merge and close times)　Source: RT-Thread-packages/esp-idf proposal #19, main repo proposal #11926

#11926, recorded in the previous issue, sought to adjust the FreeRTOS header include order for ESP32 C3/C6 in the main repo to fix the build failure on master after the ESP-IDF v6.1 adaptation. This round of discussion produced another path: a maintainer suggested in a comment “have the AI change idf to scons” and pointed to proposal #19 in the package repo; another maintainer then asked whether the package repo change should be merged first.

The result is that package repo proposal #19 (fix(scons): prioritize RT-Thread FreeRTOS headers) was merged on 10-26 09:15, and main repo #11926 was closed without merging at 11:37. In other words, the header priority issue is resolved at the SCons build script level, and the main repo no longer changes the include order. The significance for BSP maintainers is that esp-idf-related build issues should henceforth be handled in the package repo first, with the main repo only carrying kernel and framework-side changes.

The only code action in the organization that day was an extension slimming submitted and merged by the maintainer himself. 49 files, +883/-4826, version bumped to 0.4.14, with the resulting vsix at 1,296,751 bytes.

Far more was removed than added: four feature blocks—the Kconfig view, SDK manager, toolchain settings, and Symbolic Analysis—were removed wholesale, along with the ELF and DWARF parsers (elf-parser.ts, dwarf-parser.ts, handleElf.ts, roughly 887 lines combined) and 291 lines of settings documentation. From a product positioning standpoint, this is a clear retreat: the extension no longer attempts to replicate RT-Thread Studio’s configuration and debugging capabilities inside VS Code, keeping only two things—the “Env entry point + embedded browser”—to reduce size and maintenance surface.

3.2 Eclipse project generator misses kernel macros: a fix for Studio’s 24 implicit declaration warnings (10-26)

Date: 2026-10-26 23:33 (last updated)　Source: main repo proposal #11930

The community long-form article covered in the previous issue documented “Studio builds reporting 24 rt_sched_* implicit declaration warnings,” and this round brings a corresponding proposal: single file, +151/-2, fixed from the project generator side.

The root cause is stated clearly: the scheduler interfaces in include/rtsched.h are guarded by the two macros __RT_KERNEL_SOURCE__ and __RT_IPC_SOURCE__, which the gcc and armclang branches inject via LOCAL_CPPDEFINES in src/SConscript. Command-line scons builds recognize them, but tools/targets/eclipse.py, which Studio invokes before every make, does not collect this group-level definition, so dist-exported projects produce 24 -Wimplicit-function-declaration warnings: 1 in clock.c, 7 in ipc.c, 12 in thread.c, 1 in timer.c, and 3 in scheduler_comm.c.

The fix promotes __RT_KERNEL_SOURCE__ to the Kernel group’s global CPPDEFINES, consistent with the existing msvc branch. The change does not touch kernel source code, only the project generation script.

4.2 STM32 Ethernet adds ops layer and SR8201F PHY, ADC log level lowered (10-26)

Date: 2026-10-26 10:25 (last updated)　Source: main repo proposal #11819

A three-in-one driver proposal, 4 files, +34/-3, covering three independent issues on the STM32 side.

First, the ADC driver’s default log level was too high, flooding output during normal use; it is changed to DBG_WARNING with the macro switch retained. Second, the ETH driver lacked ops layer adaptation, so the upper-layer network framework could not operate the device through a unified interface; this proposal implements and registers the ops callback set. Third, the PHY driver did not support the SR8201F, so boards using that chip could not bring up Ethernet; this proposal adds the identification ID, initialization flow, and register configuration, and adds it to the PHY list. The verification board is stm32f429-atk-apollo, with RT_USING_DEVICE_OPS, BSP_USING_ETH, and PHY_USING_SR8201F enabled in the configuration.

5.2 Community long-form article “rtthread Startup Chain Analysis”: splits Reset_Handler to main into three stages (10-26)

Date: 2026-10-26 08:59 (published)　Source: Community article: rtthread Startup Chain Analysis

The community article API added only this one piece in the window, about 5,700 characters. The author states the environment is STM32F103C8T6 + RT-Thread 4.0.3 + RT-Thread Studio 2.3.1 (GCC), and declares that the code in the article comes from the actual build of this project, not copied from a manual.

The chain is split into three stages: the first is assembly, where Reset_Handler copies .data initial values from Flash to SRAM, zeroes .bss, calls SystemInit, and jumps to entry—the author specifically calls out a common misconception: SystemInit does not configure the main frequency to 72MHz; it only resets RCC to the reset state and sets SCB->VTOR to the Flash start address; the second is C initialization, where entry enters rtthread_startup(), and only inside rt_hw_board_init() are the 72MHz clock and heap configured, after which the main, timer, and idle threads are created; the third is scheduler startup, where rt_system_scheduler_start() picks the highest-priority ready thread, running the timer thread first by default, and main() only appears after rt_components_init() inside main_thread_entry().

The end of the article also provides four “easy-to-misremember points” and a section on self-verification methods, serving as a summary of common confusion points when reading kernel code.
