I. Weekly Highlights

  • SpacemiT K1’s first BSP merged into mainline, marking the first application-processor-class RISC-V platform to enter the main tree (10-19): Proposal #11132 was filed on 2026-01-11 and landed by author GuEe-GUI after roughly nine months of review — 4 commits, 173 files, +53862/-12 — as a follow-up to the Next RISC-V refactor (#10320). The BSP targets a 64-bit RISC-V platform integrating 8 X60 cores, booted by U-Boot/OpenSBI and running in S-mode, with MMU and SMP enabled by default; the validation platform is the Banana Pi BPI-F3. It already supports PCIe/NVMe, eMMC HS400, Ethernet and PTP, HDMI framebuffer, JPU and V2D acceleration, audio, CPUfreq, and thermal management. The driver layer is extracted separately into bsp/spacemit/dm (147 files, 49 C files, about 30 modules) for reuse by SoCs in the same family.

  • RISC-V ticket spinlock switched to atomic add; K1’s SMP configuration raised from 4 to 8 cores the same day (merged 10-22): Proposal #11904 changes ticket acquisition to a single amoadd instruction and release to a single 16-bit halfword store — 6 files, +33/-37. The original implementation ran a load-reserved/conditional-store loop for both acquire and release on the same word, so under high multi-core contention the reservations would cancel each other and fall into livelock; the whole-word read-modify-write on release could also overwrite concurrently issued new ticket numbers. Both root causes are eliminated together, with a memory barrier added on each side. This code is shared by all RISC-V boards, so its impact is broader than a single BSP.

  • ESP32-C3/C6 adaptation to ESP-IDF v6.1 lands end to end; RISC-V toolchain jumps to GCC 15.2 (10-21 ~ 10-22): On the package side, RT-Thread-packages’ esp-idf completed its full upgrade from 5.1 to 6.1.0 and was merged on 10-21 at 15:23 (over 20,000 changed files), adding a components/rtthread porting layer and a CONFIG_IDF_RTOS_RTTHREAD kernel-replacement switch; main-repo proposal #11870 was merged on 10-22 at 15:42, touching 55 files. The thirteen C3 configurations and the C6 default configuration compile successfully, but the on-hardware row still reads “to be verified.” C3 and C6 are RISC-V cores, and this path is now in place from package to main repo.

  • Six defect tickets opened this week, five of them memory and boundary safety; a single NVMe boot leaks about 1.1 MB of kernel heap (10-20 ~ 10-23): Six new tickets — #11902 (use-after-truncate in tmpfs), #11905 (cromfs directory name out of bounds), #11906 (Chinese Windows encoding), #11913 (raw DHCP option out-of-bounds read), #11917 (NFS out-of-bounds write), #11919 (NVMe heap leak) — of which all but the encoding issue are memory and boundary safety. #11919 leaks 1,156,872 bytes per boot on QEMU’s stock NVMe device, accumulating linearly with hotplug; the report cites CWE-401 and CVSS 3.1 4.9. The introducing commit for #11917 traces back to 2010, affecting all versions since v1.2.0.

  • RT-Thread Smart moves from batch proposals to a testable stage; fixes proposed for out-of-bounds issues in signals and device tree (10-18 ~ 10-22): The maintainer opened 13 proposals in two minutes (#11885 ~ #11897) between 19:35 and 19:36 on 10-18, covering enabling Smart on qemu-virt64, disabling SMP on riscv64, mounting ext4 and ptyfs over virtio-blk, splitting lwp syscalls, and 128MB DDR adaptation for K230D. Fixes for this week’s corresponding defects followed: lwp signal number validation (#11899), OFW device tree depth pre-check (#11901, changed to debug-gated after review), cromfs directory name bounds (#11911), and tmpfs use-after-truncate (#11910). On the libdl dynamic module defect, the maintainer stated that bounds checking can be fixed locally, but memory isolation requires moving to user mode.

  • Two independent scheduler paths converge on the same predicate; retesting a three-year-old case exposes a single-core double free (10-21): A community member posted three consecutive comments on the timeslice patch #6645, suspended since 2022, pulling it back into review; its predicate — “only insert at queue head when still running and preempted with timeslice not exhausted” — matches exactly the conclusion independently reached by this week’s new proposal #11907. However, #6645’s “deferred write of READY” implementation triggers a double free of the TCB when idle reclaims on the single-core path (the scheduler group’s utest crashes reliably), and isolation experiments show the problem is not in where YIELD is cleared. The recommendation is to proceed on the basis of #11907’s “save stat_before first, then decide.”

  • Mainline rhythm was “three days of silence, then a single wrap-up”: 7 commits and 6 proposals this week, four commits within three hours on 10-22 (10-19 ~ 10-23): Two on 10-19 (early rt_null registration #11884, K1 first version #11132), zero commits from 10-20 through the morning of 10-22, then four in a row from 15:42 to 18:00 on 10-22 (ESP32 #11870, ticket lock and K1 eight-core #11904, attachconfig #11908), and the clang-format rules proposal #11859 on 10-23 at 17:09. No movement on the release side: the latest tag and release artifacts remain v5.3.0 from 09-10; v5.4.0 has only the version macro and Kconfig defaults merged on 10-17, with no release notes or binaries.

  • Vendors advance in the same week: RT-Thread Ruibing V1.8.4 released with industrial-site fixes, GigaDevice fills in two building blocks — networking and UI — within 24 hours (10-21 ~ 10-22): Ruibing V1.8.4 was released on 10-21 (adds QY1503 encoder, MIPI RGB666, GPIO pull-up/pull-down, amp_device debug commands; fixes EtherCAT interrupt affinity, netstat hang under telnet, UART DMA baud rate), with the IDE upgraded to V1.5.62 in step; on the GigaDevice side, GD32VW553 entered the at_device package on 10-22, the GD32EmbeddedUI example entered the LVGL package index one day after its repo was created, and the Studio SDK index picked up Gino Pi (GD32H77D) 1.1.0 and PyOCD 0.3.1 the same day.

Security and Defects

Date: 2026-10-20 ~ 2026-10-23　Source: Issue #11919

  • Six new issues: #11902 tmpfs sets ENOMEM when rt_realloc(data, 0) returns a null pointer but still returns success, so a legitimate ftruncate(fd, 0) frees the buffer first and then reports success (all versions since v5.0.2, reproduced on QEMU aarch64 and RP2350, claimed by the community on 10-20); #11905 cromfs does not bound the directory name length when reading directory entries, allowing reads past the directory entry buffer and hijacking the kernel program counter (since v5.0.0, both generations of the DFS implementation share the same origin, unclaimed); #11913 the raw-API DHCP server option traversal does not first check buf + 1 < end, allowing reads past the 1500-byte pbuf by up to 4 bytes (the socket implementation in the same directory already performs this check, which confirms the missing point); #11917 nfs_read uses the count returned by the server as the memcpy length, and the built-in cat with an 81-byte stack buffer can have its return address overwritten (introduced by a 2010 commit); #11919 NVMe scanning uses the namespace count reported by the device as the loop upper bound, allocating 4480 bytes before each command is sent, and neither failure path frees it. Also, #11906 is a console encoding defect under Chinese Windows, classified under the toolchain side (see Section III).
  • Five fix proposals: #11899 restricts the signal number to 1 through 64 at the sys_sigaction entry and adds the same check inside lwp_signal_action; #11901 pre-traverses to find the maximum depth before device tree expansion and rejects depths over 63 (changed after review to be gated by a debug switch); #11911 constrains the cromfs directory name length; #11910 fixes the use-after-free after zero-length truncation in tmpfs; #11918 makes both the 9PFS read and getdents paths converge the message length to the actual number of bytes received, with the author reproducing it using bsp/simulator plus ASan and a fake 9P server (before the fix, use-after-poison was triggered, with the read position landing at byte 8,334,515 of an 8 MB heap region).
  • Still unresolved: #11878 lwip-dhcpd lease pool exhaustion infinite loop, #11905, #11913, and #11917 have no claimants, of which #11917 only had a status refresh this period.
  • Common pattern: The common form of the five security defects this week is “device- or server-controlled metadata being used directly as the length or upper bound of a memory operation.” The same researcher reported the NFS, NVMe, and 9PFS issues within two days, and stated that the clues trace back to older issues in mtd-cfi and usbhost. Fixing them one by one costs more than investigating by family.

Date: 2026-10-19 ~ 2026-10-23　Source: PR #11907

VI. Trend Observations

  • The entry of application-processor-class RISC-V platforms into the mainline is the week’s most significant structural change: K1 was merged in the form of S-mode, MMU and multicore SMP, with PCIe/NVMe, HDMI and multimedia acceleration, marking RT-Thread’s transition on high-end RISC-V platforms from “able to boot” to “peripherals complete”; drivers are separated into a bsp/spacemit/dm layer, and the BSP directory is beginning to show a “vendor layer plus board layer” division of labor, with K1 merely the first user. Such platforms will continue to expose generic code defects in reverse — the three fixes to atomic compare-and-swap, power domain naming, and DVFS duplicate checking brought out in the same batch this week are evidence.
  • Multicore correctness became the week’s technical mainline: The livelock surface of ticket locks was eliminated at the root, the expected value of atomic compare-and-swap is no longer overwritten by the status register, and same-priority ready ordering was restored to first-come-first-served — all three are issues long masked by default behavior, and all were located within the same week. On the scheduler side, there is also the case of “two implementations unaware of each other converging on the same discriminant,” with cross-proposal horizontal comparison replacing discussion of single patches.
  • Security audits now show a family pattern, and the cost of patch-by-patch fixing is exceeding the benefit: The common form of this week’s five security defects is trusting externally controllable metadata as memory operation lengths or upper bounds, involving five components: NFS, NVMe, 9PFS, cromfs, and DHCP. Reporters now supply the introducing commit, affected version range, and reproduction environment, lowering the cost of fixes; but duplicate defects caused by the same origin of the v1 and v2 DFS implementations (the cromfs case has two copies, neither constrained) suggest that family-based triage and structural convergence are needed.
  • The mainline shows a “silent—concentrated wrap-up” rhythm, and the release process has not yet started: After three consecutive days of zero commits, four commits landed within three hours, all handled by the same maintainer, looking more like batch processing after accumulated reviews. Since 10-17, v5.4.0 has only version macros and Kconfig defaults, with no tag, no binaries, and no release notes; this “version number first, release artifacts lagging” state has persisted for a week, and the next issue should verify against the release page and ChangeLog whether the gate has truly opened.

The latter often yields higher marginal benefit for domestic developers.
