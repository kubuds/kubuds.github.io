  • All six 2024 CVEs landed: filed 11-10, merged in two batches on 11-12 and 11-13 (11-10 ~ 11-13): In the early hours of November 10, over a span of just over five hours, the same reporter submitted eleven boundary checks by module, six of which map directly to CVEs disclosed in 2024 — adjacent in numbering and structurally identical in fix: FinSH path concatenation (CVE-2024-25390), WLAN transmit length (CVE-2024-25388), rt_random weak seed (CVE-2024-25389), var_export export table (CVE-2024-25392), rt-link transmit framing (CVE-2024-25395), and YMODEM path copy (CVE-2024-25394). Three were merged on 11-12 (random number, wireless management, rt-link transmit side) and the other three on 11-13. The common thread is stated in the proposal descriptions: RT_ASSERT had been treated as the last line of boundary defense, yet assertions are often disabled in production configurations.

  • RISC-V FPU context-switch defect closed in five and a half days; fs0–fs11 and fcsr added to the switch frame (11-07 ~ 11-13): While porting ArtInChip D213 (C906, M-mode), reporter boa-z found fs1 incorrect after a thread switch, reproduced it on the official qemu-virt64-riscv (QEMU 10.0.13, OpenSBI 1.6, RV64D, single hart), and confirmed two issues: voluntary switches saved only integer callee-saved registers, so two threads using floating point overwrote each other’s fs0–fs11 (expected 0x3ff0000100000000, got 0x3ff0000000000000); and timer preemption saved f0–f31 but not fcsr, silently altering the rounding mode and exception flags. A maintainer produced #12006 four hours later, adding fs0–fs11 and fcsr to the switch frame with guaranteed 16-byte alignment; it was merged at 09:37 on 11-13 — five days and ten hours from report to merge.

  • Two RISC-V interrupt controller paths aligned in the same week: both APLIC and PLIC changed to handle-first, complete-after (11-10 ~ 11-11): #11966, merged 11-10, changes the APLIC EOI path — first checking in in_clrip whether the device is still asserting the interrupt before deciding whether to write setipnum_le, fixing the issue where a counting program printed only RISC-V test: 0 and stalled after enabling AIA on QEMU 8.2.2; #12011, merged 11-11, changes the PLIC ordering — dispatching handler_irq() before writing the claim, and temporarily setting the enable register around completion for the case where “the handler masks its own interrupt source.” The two came from different authors as independent submissions; both defects stem from “the completion action being decoupled from the actual state of the interrupt source.”

  • WCH Qingke fast interrupts unified around kernel capabilities; 337 net lines removed across 27 files (11-09): #12004, merged at 11:12 on 11-09, adds the CONFIG_WCH_USING_FAST_IRQ configuration option, uses a unified interrupt-attribute macro to select fast or normal interrupts by chip series, adjusts the interrupt handlers of peripheral drivers and BSPs one by one, and updates the CH32V203 startup file to the new usage; validation boards are ch32v208w-r0 and ch32v307v-r1. Deletions (1424) outnumber additions (1087) — a convergence that folds copy-paste back into a single set of macros. At 10:27 the same day, the package repository updated the CH32V2/V3 SDK (#2052), landing in both repositories the same day.

  • utest multi-round runs catch a leak on day three: atomic test case leaks 25 KB per round (11-11 ~ 11-13): #11983, merged 11-09, lets the test framework run multiple rounds consecutively and sample free memory and the thread table between rounds. #12033 on 11-11 acted on this for core.atomic: test_atomic_add() creates a semaphore and three dynamic threads each round without reclaiming them; on qemu-vexpress-a9 with three rounds enabled, heap usage went 63608 → 88848 → 114088 bytes, up 25240 per round, with ps showing three residual t1/t2/t3 each in close state; after the fix, three rounds hold steady at 38368 with zero residue. Merged 11-13.

  • Official news feed silent for a full week; WeChat account covers the STM32 four-city tour and TC397X Safety OS (11-11, 11-13): The official news feed has added nothing since the batch of five at 15:54 on 11-06 — four consecutive daily briefings from 11-10 to 11-13 plus the release-day check, five issues with zero additions. Meanwhile the WeChat column kept updating: at 11:47 on 11-11 it posted the STM32 seminar tour (Suzhou 11-12, Beijing 11-19, Chengdu 12-03, Shenzhen 12-10, with RT-Thread exhibiting on site); at 13:30 on 11-13 it published “Infineon AURIX TC397X Six-Core Platform SafetyOS — From ‘Able to Run’ to ‘Controlled Operation’,” presenting the full picture of the four protection layers and the six-core boot path.

Kernel and RISC-V Interrupts

Date: 2026-11-09 ~ 2026-11-13　Source: main repo pull list, defect #12005, defect #12010

  • RISC-V FPU context (#12006): The switch frame adds fs0 through fs11 and fcsr, the trap frame gains fcsr access, the switch frame size is rounded up to guarantee 16-byte alignment, and frames constructed by interrupt switching initialize fcsr; offset and layout macros are added to context_ext.h and stack.h. It remained marked pending review until merged on 11-13 and is the only kernel fix in this period that directly touches floating-point state consistency.
  • Two completion-path fixes for APLIC and PLIC: APLIC (#11966) is 14 lines and PLIC (#12011) is 35 lines; the latter also requires temporarily setting the enable register before and after completion, following Linux’s SiFive PLIC driver. The 11-12 daily juxtaposed the two: one was “wrote setipnum_le when it shouldn’t have,” the other “completed before it should have been handled.”
  • Two each for M0 and M23 on the same issues (#12043/#12049, #12044/#12050): The HardFault entry selects between the main stack and the process stack based on a bit in the exception return value, aligning with the existing M3 port approach (defect #3584); on the first context switch, if VTOR reads as zero, restoring the main stack pointer is skipped to avoid writing MSP as zero (defect #4728). Both proposals modify the GCC, RVDS, and IAR assembly paths.
  • mb/mq FIFO inversion still under review (#12045): Under the FIFO flag, mailbox and message queue only wake the head waiter while data remains in the shared queue; a high-priority thread taking it non-blockingly leaves the original waiter empty-handed and able to requeue only at the tail. The fix is resource reservation and handoff — “dequeue only after acquisition” — at +435/-12, the largest of this batch of ten and the only one directly changing kernel scheduling semantics; not yet merged.
  • Non-SMART CPU time accounting (#12001, merged 11-07): Only the user-mode time accounting branch is wrapped in RT_USING_SMART, a two-line change affecting CPU utilization readings for all non-Smart projects. It is a weekend-boundary item within the Monday window.

Security and Auditing

Date: 2026-11-09 ~ 2026-11-13　Source: main repo defect list, proposal #12015, proposal #12016

  • Trust boundaries are the main thread of this phase: The two heaviest changes on 11-10 both address “trust the external input first, check the type later” — dlmodule computes the relocation write target as “module memory base + offset − virtual start address” without validating the range, so a crafted .mo can write into kernel memory during relocation (#12016, five files +205/-37, merged); LWP IPC system calls pass raw user-supplied object pointers straight into rt_sem_*, mutex, event, mailbox, mq, and timer, so a fake object yields arbitrary kernel read/write (#12015, three files +284/-44, still under review).
  • Network and filesystem side: The NFS read path treats the server-returned count directly as a memcpy length, so an abnormal or malicious server can write past the caller’s buffer; the fix converges on the minimum of “server count, request count, decoded length” and tightens the XDR limit to 1024 bytes (#12012, merged 11-12); 9PFS getdents truncates the 16-bit name_len into the 8-bit d_namlen, and values of 256 or more wrap around and bypass the check (#12035, still under review).
  • Configuration constants and lease periods: The DHCP server’s lease_end is never read after being written, so leases never expire; DHCP_DEFAULT_LIVE_TIME (0x80510100) after PP_HTONL() is roughly sixty-eight years on the wire, inconsistent with “reclaim by day,” and is changed to 86400 seconds (#12024, still under review). The memory pool fix addresses a false alarm that caused a real stall: freeing “the last block, whose next points to the heap_end sentinel” falsely triggers an assertion (#12014, merged 11-12, corresponding to old 2025 defect #10632).
  • ptyfs leak and the legacy USB back-and-forth: The pts unregister path does not free the struct ptyfs_file allocated at registration, so repeated open()/close() of /dev/pts/* can be continuously triggered by an ordinary user (#12023, reported 11-10); the maintainer produced #12029 twelve hours later (still under review). The legacy USB host stack treats the device-reported bLength as the full descriptor read length, allowing out-of-bounds writes (#12026); the maintainer’s #12027 added length validation and then closed it as “legacy code, no longer continuously fixed”; in the early hours of 11-12 another reporter refiled #12036 (five files +71/-13, covering hub descriptors and wMaxPacketSize), merged 11-13 09:47.
  • vDSO clock constants: two proposals, two closures: Four clock constants are undefined when the newlib toolchain compiles RT-Smart vDSO user code (#12025). The first macro-adding proposal #12028 was closed the same day; the second compatibility-header proposal #12041 was closed 11-13 06:04, with the issue closed as completed and the comment “closing for now; some relationship explanation will be needed later.” The resolution shifted from changing code to supplementing documentation: Smart’s toolchain must use a dedicated compiler built with a modified musl library.
  • Verification is consistent and conservative: The vast majority of security proposals merged this week are marked “static review only, not run on hardware, no PoC constructed”; the only one with automated test cases is the memory pool fix (forty-odd lines of tests), and the NFS fix had its implementation checked item by item in review. The 11-13 batch is the same; before entering a release these should not be treated as verified protections.

III. Ecosystem and Vendor Adaptation

Vendor BSPs and Drivers

Date: 2026-11-09 ~ 2026-11-13　Source: PR #12004, PR #11844, PR #12052

  • WCH: Fast interrupts are now configured uniformly according to QingKe core capabilities (#12004, merged 11-09), 27 files, +1087/-1424, validated on the ch32v208w-r0 and ch32v307v-r1 boards; PM component support for CH32V208 (#12007) depends on the previous change and is still under review. On the package side, the CH32V2/V3 SDK was updated in sync (#2052, four files, +18). WCH is one of the largest RISC-V MCU vendors in China by shipment volume, and interrupt configuration and power management directly determine usability in low-power scenarios.
  • Espressif: A missing asterisk was added to the ESP32-C3 linker script (#12009, one-line change) — the IRAM rule for esp_ringbuf was written as *esp_ringbuf?(...), which matches no object files, so the 0x1fa4 bytes of ringbuf.o fell into an orphan section; once the end of .flash.text is less than 64KB from a boundary, rodata and code end up on the same page. The issue of ESP32-C3 v1.x chips being rejected by prebuilt images was fixed by changing the full version range to min_rev=0, min_rev_full=3, max_rev_full=199 per ESP-IDF (#12013, merged 11-13 16:42). ESP32-S3 was a “half-landed” change: #11844’s title says include path fix while its body says new directory, but only one 25-line file, libcpu/xtensa/esp32s3/SConscript, was actually merged; bsp/ESP still contains only ESP32_C3, ESP32_C6, libraries, and tools, so the BSP path referenced by the script does not currently resolve.
  • Canaan: K230’s PWM readback treated the compensation value as the high-level count — writes store period_count - high_count, but readback used it directly as high_count, so setting 25% read back as 75% (#12032). The fix shares a single pwmcmp0 read and returns a 0 pulse width for negative values across channels; measured on a 01Studio CanMV K230 with GPIO52/PWM4, cross-channel readback changed from 50000 and 4294942296 ns to 50000 and 0 ns. Merged 11-13.
  • Bouffalo: The ADC driver used the caller-supplied channel number directly to compute the DMA buffer index, so negative, out-of-range, and unconfigured channels would read invalid sample slots; the fix adds range and configuration-list validation and exhaustively tests all 256 values of rt_int8_t (#12003, merged 11-09, host-side validation only).
  • STMicroelectronics (STM32): No new merges this week, but the community proposed a structural extension to the existing input capture driver (#12052, see review queue). Last week’s STM32F1/H7 input capture merge filled in “one channel per timer”; this change goes further to support four independent captures and dual-edge mode on the same timer.
  • Renesas: The RH850 G4KH port proposal is still a draft, 48 files, +3916 lines, including TRAP0 thread switching, nested interrupts, FPU context, and the qemu-rh850-u2c board; kernel_basic passes 22/22 on QEMU, and both hard-float and soft-float builds are in the CI matrix.

Conferences and Events

Date: 2026-11-11 ~ 2026-12-10　Source: Electronic Engineering Album: STM32 Seminar, ST Official Events Page

  • 2026 STM32 Seminar four-city tour: Suzhou on November 12, Beijing on November 19, Chengdu on December 3, and Shenzhen on December 10. According to the ST official events page, the scale is 2 summits plus 5 forums, 8 interactive talks, 35+ technology demos, and 25 partners, with the exhibition area covering robotics, graphics applications, smart locks, wireless audio, and edge AI. RT-Thread will exhibit on-site with its latest products; the article also includes a repost lottery, drawing 3 winners who each receive a NUCLEO-G031K8, with a deadline of December 10. The first stop, Suzhou, falls on 11-12 itself.
  • Productization framing of TC397X Safety OS (11-13 13:30): The article argues that “a general RTOS first solves how to run, while a Safety OS further solves how to run under control in the event of a fault,” and presents four layers of protection—the hardware MPU establishes a private mapping for each thread and switches the access window synchronously on context switch; user mode and system call mechanisms let untrusted applications run with restricted privileges; the OSA application container packages code, data, threads, MPU mappings, and lifecycle into an independent unit, with the fault path being “illegal access → MPU block → Protection Trap → fault backtracking → terminate the faulty application thread group,” and diagnostics can resolve down to CPU, Trap Class, TIN, call chain, application name, and thread name; software sentinel checks are used together with MPU stack protection.
  • Concrete path for six-core capability: CPU0 completes clock, Port, DMA, GPT, and global RTOS initialization, while the other cores wait and then enter their own core startup; each core separately initializes its scheduler, tick, system threads, and MPU; GPSR inter-core interrupts send remote scheduling requests, hardware atomic operations and ticket spinlock protect shared state, and each core runs a 1 kHz tick. On the platform side, Infineon TC397 SSW is used to complete six-core startup, MCAL initializes MCU, Port, DMA, GPT, STM, DIO, and UART, miniBsw/EcuM organizes the Pre-OS flow, both GCC and TASKING link layouts are supported, and integration directions are reserved for Wdg, SMU, CRC, E2E, DEM, and DET.
  • Verification and certification framing: The full codebase complies with MISRA C and has completed 100% MC/DC coverage testing; safety mechanism descriptions, test evidence, process documentation, and certification support are available, covering ISO 26262 ASIL, IEC 61508 SIL, and EN 50128 SIL. The article also provides a purchase link and limited-time pricing for the TC3 evaluation kit; this is product promotion, so this report records only its functional safety statements and does not cite promotional information.

VI. Trend Observations

  • The audit line has moved from “batch submission” to “batch fulfillment,” with throughput dependent on two people: Eleven commits in one day on 11-10, seven in the early hours of 11-12, and 28 merged across 11-12 and 11-13, including 22 in a single day on 11-13. The structure recorded in the daily reports is clear—proposals mostly come from the same account, and merges are mostly completed by the same maintainer. Efficiency is high, but this line’s throughput depends entirely on these two people’s time; once either end stalls, the queue piles up again (proposals rising from 149 to 163 between 11-11 and 11-13 is the evidence).
  • The attack surface uniformly converges on “validate external input before copying,” but verification remains static: Across the two batches of six 2024 CVEs and the project’s own issues, the fixes almost all move length or index checks ahead of the action. The cost is that all these fixes are marked “no board flashing, no PoC constructed,” with the only automated test cases being the two related to the memory pool and utest. For downstream distributions, these patches can only be considered “reviewed,” not “verified,” before entering a release.
  • RISC-V’s weight rose noticeably this week: FPU context (fs0 through fs11 and fcsr), APLIC’s EOI timing, and PLIC’s completion ordering all closed within a week; meanwhile, the M0 and M23 HardFault stack selection and VTOR-zero issues were also completed. But all three RISC-V defects were found by the same reporter in ArtInChip D213’s M mode without device model enabled—the non-DM path has no persistent CI, which is a structural gap that individual diligence cannot fill.
  • Test infrastructure is starting to “pay off”: On the third day after utest multi-round runs went live, it caught a 25 KB per-round leak in core.atomic; dlmodule regression entered QEMU CI; and the per-framework checkboxes required by the QEMU virtual device list (#11972) are becoming test cases. The value of this line is not in the current week, but in giving “whether the Z release can ship” a verifiable evidence chain.
  • Version cadence remains unchanged; release prerequisites are more worth watching than release dates: v5.3.0 has been stuck at 09-10 with no tag for two months; mainline activity concentrates on defects and testing rather than version numbers. The version management process (#11956) and QEMU test list (#11972) that appeared last week remain two programmatic documents, with no new review conclusions this week—the next observation point is whether the list can actually run on QEMU, not when 5.4.0 will ship.
  • External communication has become dual-track, with product narrative tilting toward functional safety: The official website interface has been silent for a full week, while the WeChat account published consecutive posts on the contest, the STM32 tour, and TC397X Safety OS. The latter’s wording is worth noting: from “running correctly by accident” to “running under control within explicit boundaries,” translating safety from a certification checklist into four layers of runtime protection. This says more about the product’s current focus than the 11-06 scale figures of “2.5 billion installations, 300,000 developers.”
