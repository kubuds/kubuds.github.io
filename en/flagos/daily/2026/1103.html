1.3 FlagQuantum: 21 merges in a single day on the synthesis line, UP-01 and the AO/PF acceptance lines running in parallel (11-02 ~ 11-03)

Date: 2026-11-02 ~ 2026-11-03　Sources: FlagQuantum PR #1002 · FlagQuantum PR #1004 · FlagQuantum PR #1006 · FlagQuantum PR #1010 · FlagQuantum PR #1013 · FlagQuantum PR #1018 · FlagQuantum PR #1021

  • Semantics line (UP): #1002 first routes PHASE gates with raw constant angles through the existing CoreIR; #1003 establishes UP-00’s semantic boundary while preserving Qmod’s RZ compatibility; #1004 brings UP-01’s Python program namespace to the foreground — functions decorated with @synth.qfunc can directly express allocations, gates, and outputs, with the compiler side capturing typed qfunc preparation and arithmetic composition, and the runtime side executing in-program preparation through a brand-new port. The PR body gives a reproducible example: a program with two qubit allocations, a Hadamard transform, and result |= x*x+y can be compiled and executed within the same common workflow.
  • Arithmetic line (AO): #1006 establishes AO-00’s arithmetic baseline and an independent oracle, and codifies “verification scope must not be overstated” as a checker rule; #1010 lands AO-01, performing guarded common-subexpression elimination and sound bit-fact normalization on pure expressions; #1013 lands AO-02, completing guarded square, constant, and terminal XOR implementations. The three progress in AO-00 to AO-02 order, each preserving the prior step’s resource baseline and acceptance evidence.
  • Performance line (PF): #1018 establishes PF-00’s Python compile-latency and OS RSS baselines, making timing, memory, and diagnostic queues isolated observations without changing production code or replacing existing resource baselines; #1021 uses PF-01 to reuse already-validated plan fields, reducing redundant validation and object rebuilding on the Services side. Together they turn “how long one synthesis takes and how much memory it uses” into reproducible numbers rather than one-off observations.
  • Side lines in sync: On the QEC side, #1012 verifies the compositional correctness of noisy surface memory experiments, #1015 preserves correction records for coherent matching, and #1019 validates chunked scheduling and late memory invalidation; on the runtime side, #1017 lets Module training reuse the normalized IR, #1014 reduces default diagnostic snapshot overhead, and #1020 codifies the lazy Torch compile boundary as an approved contract. Two more, #1022 and #1023, opened at 00:21 and 01:19 at the end of the window, still aimed at the synthesis line and runtime.
  • Assessment: What these 21 merges share is breaking “one big feature” into “independently acceptable units” — semantics, arithmetic, and performance each with a baseline, an oracle, and fail-red evidence. For the quantum stack this matters more than any single performance number: it means any future register-allocation or gate-synthesis change can immediately be measured for cost against the existing ledger.

1.5 FlagGems: Kunlunxin XPU3 fixes silent wrong shapes, fourteen performance and contract closures (11-02)

Date: 2026-11-02　Sources: FlagGems PR #8038 · FlagGems PR #8034 · FlagGems PR #7976 · FlagGems PR #8123 · FlagGems PR #8245 · FlagGems PR #8049

  • Correctness fix: #8038 is the most worthwhile read of the day. The out-of-place scalar overloads in the foreach series take a fast path when “same dtype, same device, same element count,” allocating output uniformly by the first tensor’s shape and then slicing views — but the fast path’s admission condition compares element counts rather than shapes, so lists with different shapes but equal element counts all inherit the first tensor’s shape, producing silently wrong results. The fix changes admission to full-shape comparison; two other PRs switch sixteen scalar outputs to single-base addressing and merge list outputs into one flat buffer.
  • Contract fixes: #7976 changes the foreach dot-notation slot index to come from program_id(0); #8034 evaluates the autotuned grid before submitting JIT, avoiding launches with an unevaluated grid; #7956 unpacks the ternary return value of scalar parsing, correcting the fast-path value.
  • Performance closures: #8056 adds fast paths for triu_, resolve_neg, le, and bitwise right shift; #8245 adds pointwise fast paths for flip, ge, and lerp and reverts the previous BF16 1D tile refactor; #8108 fuses the exact path of pool3d backward and skips the pointwise pipeline for small multiplies; #8107 unrolls Chebyshev’s t/w when per-channel degrees match; #8030 speeds up choose_qparams_optimized, kl_div, and two Bessel kernels; #8111 blocks the Jacobi sweep so nuclear_norm needs only nb launches instead of k; #8049 adds a single-formula fast path for linspace; #8248 brings another set of operator-specialization performance fixes.
  • Rollback signal: #8123 reverts “Kunlunxin BF16 pointwise performance optimization” on grounds of introducing a regression; the same day, #8245 redoes it with a different approach and explicitly “removes #8052’s BF16 1D tile refactor.” A revert and a redo in the same window show that XPU3 pointwise optimization is still experimental, with insufficient shape coverage before merge.
  • Assessment: The keyword for this Kunlunxin group is “contract” — one fix each for implicit conventions at four levels: shape, slot, grid, and return value. The common consequence of such issues is silent wrong results rather than crashes, which is more worth recording in a daily briefing than a performance regression.

  • AMD performance line one: #256 adds chunked_sgmv_expand, gate_up_lora_b, sgemm_lora_b, per_group_transpose, silu_and_mul, and fused_rmsnorm for RDNA3 (gfx1100), tuned and tested on a Radeon PRO W7900D; outputs are bit-identical to the generic implementations except for fused_rmsnorm. The competition batch brings coverage, the gfx1100 batch brings runnability on real hardware, and the two complement each other; but the review depth of competition PRs (mostly bulk merges) versus the bit-exactness requirements on the AMD side creates a clear quality gradient.

  • Event: The “Intelligent Computing System Innovation and Open Ecosystem” sub-forum of the 2026 GAI+C AI+ Conference was held in Beijing on 10-31, with a recap published online on 11-02. The forum was hosted by the Jiuyuan Intelligent Computing System Ecosystem Consortium and the Beijing Artificial Intelligence Association; on site, three joint results were released — “Jiuyuan × Phytium,” “Jiuyuan × TileLang,” and “Jiuyuan × SenseTime Multimodal Large-Model Training and Inference Suite” — and the 2026 Autumn Qiyuan AI Competition was launched.
  • Narrative: In his keynote report at the conference, Zheng Weimin, an academician of the Chinese Academy of Engineering, directly pointed to domestic compute’s problem of “cards available but hard to use, chimney-style adaptation,” and proposed a unified software stack to support cross-platform operation with “one set of code, no modifications.” This is highly isomorphic with FlagOS’s technical proposition, but the actor is a different ecosystem line (the Jiuyuan Consortium and Qiyuan Lab).
  • Relation to FlagOS: The report does not mention FlagOS; this item is recorded as a parallel ecosystem move to observe the competitive landscape of domestic unified software stacks, and is not counted as FlagOS project progress.
  • To watch: Jiuyuan’s choice to release jointly with TileLang shows that the compiler layer is becoming the alliance point for ecosystem consortia; FlagOS’s corresponding assets are FlagTree and the TLE language extension. The route differences between the two lines at the “unified compiler” layer are worth continued tracking in subsequent windows.

III. Deep Dive into Member Units and Backend Vendors

3.1 DAMO XuanTie: Dedicated Operators, MM Cost Model, and chunk_kda Advanced on Three Fronts on the Same Day (11-02)

Date: 2026-11-02　Source: FlagGems PR #8240 · FlagTree PR #1236 · FlagGems-vllm PR #1038

  • Operator layer: 13 XuanTie-specific operators were merged into FlagGems within 43 minutes, covering special functions, 3D convolution, quantized LSTM, matrix norms, and pooling backward. What these entries share is that generic Triton implementations yield low returns on XuanTie, and after specialization they can go directly into the operator library’s default dispatch.
  • Compiler layer: #1236 upgraded the XuanTie ZW810E MM/MV cost model package to 1.1.0, added it to the FlagTune model catalog, and made the auto-tuning contract accept an explicit configs list—validating each entry by parameter name and legal values, and rejecting forms that coexist with config_space. The package’s 8 BF16 mm variants plus 2 mul models constitute the first complete cost model for auto-tuning on XuanTie.
  • Inference layer: #1038 added optimizations for the chunk_kda on both the Tianshu and XuanTie backends, part of the long-sequence path in FlagGems-vllm.
  • Assessment: XuanTie’s actions that day spanned the operator, compiler, and inference layers, all pointing toward “specialization” rather than “generic compatibility.” This aligns with XuanTie’s positioning as a high-performance RISC-V core: first fill in specialized implementations for long-tail operators, then let the cost model drive auto-tuning, and finally deliver in the inference framework.

3.2 Kunlunxin: XPU3 foreach Contract Fix and Fourteen Performance Closures (11-02)

Date: 2026-11-02　Source: FlagGems PR #8038 · FlagGems PR #8034 · FlagGems PR #8123 · FlagGems PR #8245

  • Silent error: #8038 pointed out that the foreach fast path compares only element counts, not shapes; a list of tensors with different shapes but the same element count would all inherit the first tensor’s shape, producing output that neither errors nor goes out of bounds. The fix gates admission on full shape and changes sixteen scalar outputs to single-base-address addressing, merging list outputs into a flat buffer.
  • Grid and slots: #8034 evaluates the auto-tuning grid before submitting the JIT; #7976 changes the foreach slot index to be taken from program_id(0); #7956 fixes the unpacking of the ternary return value in scalar parsing.
  • Performance patches: #8056, #8245, #8108, #8107, #8030, #8105, #8111, #8049, and #8248—nine in total—covering the pointwise fast path, pool3d backward fusion, Chebyshev expansion, Jacobi blocking, and the single-formula linspace.
  • Rollback: #8123 reverted the BF16 pointwise optimization due to a regression; #8245 redid it with another approach and reverted the 1D tile refactor from #8052. One revert and one replacement show this path is still being iterated.
  • Assessment: Kunlunxin’s value that day was not in performance numbers but in fixing a shape contract that would silently compute wrong results. For a multi-backend operator library, such defects are more dangerous than being ten times slower—they won’t be caught by benchmarks, only encountered downstream as “precision anomalies” in models.

3.3 Ascend and Hygon: Two Implementations of W8A8 INT8, GEMM and BMM (11-02)

Date: 2026-11-02　Source: FlagGems PR #6060 · FlagGems PR #7741 · FlagGems PR #7774 · FlagGems PR #7760

  • Ascend GEMM: #6060 adds an Ascend backend for mm_w8a8_int8 and mm_w8a8_int8_out, dispatched through the public entry point. The operator takes pre-quantized INT8 A and B, FP32 scalar or per-row/per-column scales, and an optional bias; after integer multiply-add it applies scales on both sides and bias, outputting BF16, FP16, or FP32. Small-M narrow-N cases use a vector multiply-add kernel, with each FP32 reduction segment capped at 1024 INT8 products to keep the integer part exact. Asymmetric zero points are not supported.
  • Hygon BMM: #7741 adds per-channel bmm_w8a8 for Hygon, reusing the existing scaled-MM kernel and tile selection to fuse INT8 matrix multiplication, FP32 per-channel scaling, and output conversion into a single kernel.
  • Precision fix: #7774 on the Ascend side promotes both operands before calling CANN libdevice’s pow, avoiding underflow and precision loss under mixed precision.
  • Hopper performance: #7760 optimizes FP8 W8A8 BMM with a TMA pipeline, the corresponding optimization on the NVIDIA side.
  • Assessment: The two vendors each added one W8A8 path in the same window—Ascend chose the full semantics of GEMM (including per-row/per-column scales and three output dtypes), while Hygon chose per-channel scaling reuse for BMM. The difference lies in the trade-off between breadth of semantic coverage and implementation reuse, and also reflects the differing quantization needs of their respective downstream models.

3.4 Moore Threads: True 1D GEMM for Conv1D Pulls All 26 Benchmark Cases Above the 0.8x Line (11-02)

Date: 2026-11-02　Source: FlagGems PR #6754 · FlagGems PR #7428 · FlagGems PR #6903 · FlagBLAS PR #157 · FlagTree PR #1314

  • Conv1D results: #6754 adds conv1d backend coverage for MTT S5000, raising the official conv1d_padding benchmark from 18/26 cases meeting the target to 26/26 cases at no less than 0.80x torch; previously all FP32 K3/K5 padding cases were only 0.41 to 0.53x.
  • Three-layer changes: First, conv1d previously had no MTHREADS coverage and all went through generic conv2d; small-group shapes would materialize padding, and W=1 shapes hit only a single valid OW channel. After rerouting, redundant padding and bias allocation were removed and degenerate width dispatch fixed. Second, a dedicated Triton-MUSA Conv1D kernel was added, partitioning a 3D grid by M equal to N times Lout, so output channels no longer require division and modulo. Third, weights are pre-packed ordered by kernel width, input channels, and output channels, paired with SQMMA with precision compensation.
  • Supporting work: #7428 optimizes one_hot validation and inference on S5000; #6903 treats empty indices as a no-op for index_add; #157 adds MUSA’s L1 BLAS; #1314 skips membar between two asynchronous TME copies.
  • Assessment: This is a rare complete case in this window of “pulling all benchmarks above the line”—routing, dedicated kernel, weight layout, and instruction-level precision compensation changed simultaneously, with before-and-after comparisons provided. It is a replicable template for other backends.

3.5 MetaX, Iluvatar, Tsingmicro, Enflame, and Horizon: Operators on One Side, Contracts on the Other (11-02)

Date: 2026-11-02　Source: FlagGems PR #7590 · FlagGems PR #7015 · Torch-FL PR #704 · Torch-FL PR #702 · FlagGems-vllm PR #1038 · FlagDNN commit

  • MetaX: #7590 optimizes the default and out paths of triangular_solve; #7015 adds the forward and out paths of cudnn_batch_norm and fixes the paired backward; Torch-FL #702 corrects the skip reason for the MetaX SDPA case—originally attributed to fp32, but the actual cause was something else, a test-credibility fix.
  • Iluvatar: #1038 adds Iluvatar backend optimization for chunk_kda; FlagDNN fixes the GPU name registration for iluvatar (a single commit); FlagGems #7664 enables the apply_repetition_penalties benchmark on Iluvatar.
  • Tsingmicro: Torch-FL #704 brings tsingmicro into the conf-and-registration-set consistency check; previously this platform was excluded from the six platforms, so conf/registration-set mismatches could not be caught by CI. This is a pure test change, but it closes the contract gap on the Tsingmicro side.
  • Enflame: Only one PR under review in this window, fixing CUDA-specific device guards for four operators on the Enflame side of KernelGen (#8104), not yet merged.
  • Horizon: No new commits or PRs under review in this window; the BPU convolution and pooling paths from the previous window did not advance in this one.
  • Assessment: The five vendors’ actions fall into two categories—MetaX and Iluvatar are adding operators and benchmarks, Tsingmicro is adding test contracts, and Enflame and Horizon are in a quiet period. For member units, whether they keep appearing in the daily merge list is itself a direct indicator of investment intensity.

IV. Summary and Trend Observations

Date: 2026-11-02 ~ 2026-11-03　Sources: flagos-ai organization repositories · build-infra PR #1589 · FlagQuantum PR #1004 · FlagGems PR #8240

  • The AMD line filled in three layers within a single window: On the build side, a new FlagTree amd packaging line was added, with A/B reconciliation proving equivalence (maxdiff 1.526e-05, 9/9); on the runtime side, the rocm7.2.4 torch closure was aligned to the pinned combination of vLLM 0.32; on the operator side, ten operators covering LoRA and attention were added for gfx1100. Taken together, AMD has moved from “having a backend” to “having a traceable build, a reproducible runtime, and tunable operators.”
  • The quantum stack has entered a “delivery by acceptance unit” phase: 21 merges in a single day were distributed across three lines—UP (semantics), AO (arithmetic), and PF (performance)—each with its own baseline, oracle, and fail-is-red evidence. This decomposition lets every change to the quantum compiler have its cost measured against the existing ledger, which supports long-term evolution better than chasing single-point speedup ratios.
  • XuanTie turned specialized operators into batches: 13 specialized operators were merged within 43 minutes, averaging 3.3 minutes per merge, concentrated in long-tail items such as special functions, 3D convolution, quantized LSTM, and pooling backward. This shows that KernelGen’s XuanTie production line now has batch supply capability, and that review can also digest work in parallel by backend.
  • Review throughput is the real bottleneck right now: This window saw 162 merges and 192 newly opened PRs, with 311 total under review, of which FlagGems alone accounts for 210 (148 newly opened). Merge volume fell 11.5% versus the previous 24-hour window, while newly opened volume rose 128.6%—the structure of “production lines running at full capacity, review under strain” remains unchanged.
  • 2.3.0 is still stuck at the image-first stage: The base layer and the four layers for Cambricon, MetaX, Hygon, and AMD have all had changelog dates backfilled under the 2.3.0 name, and runtime images have been pushed by backend, but the community release/2.3 manifest still returns 404 and there are zero new GitHub Releases. There has been no substantive progress compared with the previous issue; if the manifest is still not frozen this work week, the release window will be squeezed by the next version’s planning.
  • The news side marked its second consecutive quiet window: 24 groups of Chinese and English queries produced zero component-level hits, the latest CSDN column article is still dated 10-29, and HN had zero direct hits. The two ecosystem background items (the Wuzhen open-source exhibition hall and the three joint releases of the Jiuyuan consortium) are both explicitly labeled as peripheral events and were not counted as project progress.
