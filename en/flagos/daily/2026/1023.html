1.3 FlagQuantum: 53 Commits, 20 Merges — Native Rydberg Moves from Contract to Code (10-22)

Date: 2026-10-22　Source: FlagQuantum commits · PR #700 · PR #707 · PR #714

  • Totals: 53 commits, 20 merges — 40% of the org’s commits and second in merges. Compared with the prior issue (84 commits, 34 merges) the scale has halved, but the nature has changed: the prior issue was dynamic-circuit Program IR and plotting-chain completion; this issue is neutral-atom physics moving from documentation into execution.
  • Core frontend (#700, 22 files, +2198/−16): Native Rydberg control no longer borrows circuit adaptation; Core provides the frontend directly on ProgramRecord. Records gain typed context and control fields; the existing validator accepts only one physical profile and reuses CFG/SSA checks; continuous-path safety is decided by exact arithmetic on encoded coordinates, decoupled from numerical evolution; source encoding reuses the existing scalar codec, and native-specific strict fields and canonical checks reject illegal input before any tensor decoding. No new IR layer, binder, solver, registry, or root export is introduced.
  • User API: RydbergProgram is constructed from atoms, sites, length and time units, C6, loss rate, minimum spacing, transport channel, and drive channel, and exposes three actions: move, pulse, to_ir. The example output shows atom identifiers ('a','b'), dimensions (3,3), controlled position (3.0,0.0), and survival operator shape (9,9). The PR explicitly states that “a controlled position does not imply physical presence.”
  • Simulation (#707, 19 files, +1488/−188): Native Rydberg programs can go through the existing Lindblad plan, run, and initial-density adjoint entry points; the user declares atoms, linear transport, pulses, and absorption loss, and Simulation assembles the interval matrices itself; plan 1.7 is sealed to exactly seven outer fields, and the source is not recompiled at runtime. The experimental numerical path is CPU-only, with one to two g/r/lost roles, and larger scales are rejected before exponential memory allocation; geometry is an interval-midpoint approximation of the applied linear path, with grid-convergence evidence recorded separately from solver accuracy.
  • Examples (#714, 3 files, +217): Trains two pulse amplitudes as bindings and moves an atom pair; the measured output over 40 steps and 128 intervals is: unconditional RR rises from 0.0431 to 0.1228, survival-conditioned RR 0.1500, no-flag selection RR 0.1439, and exact numerical replay holds. The local default full run passes 14,584 and skips 167 in about 518 seconds; the first round at 64 intervals failed one gradient at 2.28e-10, and after refining to 128 intervals it passed without changing the solver or assertions.
  • Assessment: Within a single day, the quantum stack connected three stages — “can declare atoms and pulses,” “can compute dynamics,” and “can train control parameters” — and each stage states its capability boundary (no claims of sampling events, feedback, heating, quantum motion, GPU, or distributed execution, nor of M3 completion). This is the most informative single-repo progression this quarter: write the contract as an implementation that can reject, then open it up block by block.

1.4 FlagQuantum: Deployment Rejection, Vendor Retirement, and a Terminal-Sampling Proposal (10-22)

Date: 2026-10-22　Source: PR #701 · PR #705 · PR #716 · PR #720

  • Deployment-side rejection (#701, 3 files, +78/−1): Native physics programs are not digital circuits; the package builder previously read circuit metadata from ProgramRecord and raised AttributeError, while the Pauli package builder raised a directionless TypeError. Now both entry points hand off to Core’s rejection logic before backend selection, compilation, and emission, uniformly raising CapabilityError with the message “native Rydberg timelines cannot be executed as circuits, use flagquantum.lindblad.” Four new regressions all failed before the fix and, after it, 39 tests pass on each of three Python versions.
  • Vendor retirement (#705, 17 files, +159/−621): The generic NeutralAtomProvider never had a corresponding external service or task protocol; it only parsed local geometry and always rejected submission. Per proposal 082, the module and the two Remote namespace exports are deleted outright — no aliases, no empty-shell adapters; Core’s geometry, RydbergProgram, and the legacy plan/source firmware remain unchanged.
  • Terminal-sampling proposal (#716, 4 files, +379): Following #707, proposal 083 defines Runtime’s sample_terminal primitive — consuming ordered full-space tensor Kraus branches, reusing SuperOperator, the existing density checks, the current MeasurementResult, Core tensor encoding, and the Torch random source. The example gives existence labels ('no_flag','flag') with probabilities 0.68/0.32, and Fock-number labels 0/1/2 with probabilities 0.6/0.3/0.1, ending with an explicit print of “Framework terminal instrument API: proposed, not implemented.” The PR body states that proposal 083 is neither approved nor implemented.
  • Other branches: #710 installs Circuit methods when registering custom operators; #711 rejects non-unitary matrices in the Circuit adjoint; #712 preserves extremely small nonzero gates exactly (no threshold folding to zero); #713 audits dynamic-circuit promotion readiness; #720 covers measurement capacity variation with rank and representation-consistency intervals; #721 makes control instructions carry their own operands; #722 calibrates engine ordering under an injected clock, eliminating intermittent failures.
  • Assessment: Half of this issue’s quantum-stack merges went into “rejection” and “deletion” — rejecting packaging physics programs as circuits, deleting a vendor with no external service, and freezing an unapproved sampling interface. Such actions add no capability, but they determine whether M3’s boundaries will be credible later.

1.7 build-infra: Kunlunxin Becomes FlagTree’s Seventh Backend, flagcx 0.14.0 Pinned Across All Backends (10-22)

Date: 2026-10-22　Source: PR #1468 · PR #1471 · PR #1459 · PR #1462

  • Totals: 13 commits, 13 merges, all by tengqm — the most concentrated platform-side repo of the period.
  • Seventh backend (#1468, 3 files, +428/−9): packaging/flagtree/kunlunxin uses the same two-stage Containerfile shape as recent backends — --target builder is a publishable build environment (bare ubuntu 22.04 plus apt toolchain, with prebuilt inputs staged into the FlagTree offline cache), and the final stage builds the wheel on top. Kunlunxin has five unique constraints: first, ten prebuilt inputs with cache matched by directory name, where two LLVM 19 packages share the tarball root xtdk-llvm19-ubuntu2004_x86_64 and land as xtdk-llvm19 and xtdk-llvm19-printf, so filestore names carry version suffixes, and only the triton toolkit, rooted at .triton/, needs --strip-components; second, the frontend is selected by environment variable, LLVM_SYSPATH must remain unset, and the common LLVM is the validated branch while XTDK is the fallback; third, pybind11 is pinned exactly to 3.0.1, since 3.0.4 changed internals construction and would SIGSEGV the dispatcher; fourth, it does not use apt’s patchelf but resolves it from PATH or the copy bundled in the common LLVM package, matching the vendor CI path; fifth, it does not add TRITON_APPEND_CMAKE_ARGS=-DCMAKE_BUILD_TYPE=Release, because the vendor wheel Kunlunxin ships is itself rel-with-asserts, and for an external compiler the optimization level is not a packaging detail.
  • Communication dependency (#1471, 3 files, +60/−4): flagcx==0.14.0 was previously pinned only in the nvidia-cuda12.8 and nvidia-cuda13.3 rows, while the other eighteen backends still resolved from triton/_C. This change adds exact pins to the remaining eighteen, with tags taken from the value actually served by the vendor index rather than derived from the backend key (hygon-dtk26.04 publishes +dtk2604); spacemit and thead-ppu2.0.0 are not pinned because neither index has a flagcx wheel. The same PR also fixed two documentation descriptions that had become stale as a result.
  • Documentation line: Design records and site pages for eight components — vllm-plugin-FL, FlagTree, FlagCX, FlagGems, FlagLibs, Megatron, SGLang, verl — merged continuously between 12:50 and 17:42 (#1462 to #1470), the first time this quarter that “build design” has been written up as searchable site content.
  • Other: #1459 removes the stale vendor-prefixed hygon wheel row; #1461 lets callers narrow the manifest download mode.
  • Assessment: The builder expands from six backends to seven, and on the same day the communication library goes from “a special case in two nvidia rows” to an explicit dependency for all backends. The latter is the more substantive change: it determines whether the communication layer still follows the same install and symbol-resolution path when switching backends.

1.8 Torch-FL: Tsingmicro Connects rocprofiler-sdk, Kunlunxin Cross-Card Copy Moves to Peer Primitives (10-22)

Date: 2026-10-22　Source: PR #630 · PR #634 · PR #632 · PR #629

  • Totals: 12 commits, 12 merges, spanning six platforms: MPS, Kunlunxin, Ascend/Hygon/MetaX/PPU, GCU, and Tsingmicro.
  • Tsingmicro device profiling (#630, 15 files, +1383/−39): On Tsingmicro, torch.profiler previously produced only CPU activity — the platform was routed to an unavailable stub, PrivateUse1 had no registered device profiler, there were no kernel events, no CPU-to-kernel arrows, and self_device_time_total was always 0. This PR adds a rocprofiler-sdk-based DeviceTracer and a standalone profiling tool libtorch_fl_profiler.so, associates each NPU kernel back to the aten op that launched it, and renders in the CUDA trace CPU/device layout; it also measures on TX8110 and pins FLAGOS_BUILD_VENDOR=ON for Tsingmicro (the vendor directory holds a random-number kernel), and completes install and profiling docs. Behavior is unchanged when profiling is not requested.
  • Kunlunxin cross-card copy (#634, 3 files, +55): CrossDeviceMemcpy was calling the same-card-semantics xpu_memcpy (type XPU_DEVICE_TO_DEVICE), which returns −801 when passed pointers on two different cards and does not write the destination, so any flagos:N → flagos:M transfer silently did nothing. It now uses the SDK’s peer primitive xpu_memcpy_peer. The problem was found via the last bert failure on P800; a synchronous call would not mask it, indicating it was not a timing issue but that the bytes were never written.
  • Preload ordering (#632): liblaunch_shared.so reported undefined symbol: cudaMemcpy; that symbol is a versioned definition in /usr/local/xcudart/lib/libcudart.so.12 and only resolvable after the Triton launcher dlopens, so Kunlunxin’s CUDA-compatible runtime is now preloaded earlier.
  • Other: #629 adds a convolution_overrideable exception for cuda/dcu/metax/ppu; #626 keeps Qwen3.5’s metadata view on MPS; #635 moves type conversion onto the device in FlagGems-led CUDA builds; #631 keeps MPS tests on the Apple runner; #618 adds a temporary diagnostic note for GCU capability AssertionError.
  • Assessment: The day’s mainline is not performance but the availability of two foundational capabilities — observability (Tsingmicro can see a device timeline for the first time) and multi-card correctness (Kunlunxin cross-card copy had been wrong all along). Such fixes never appear in any benchmark table, but they force every upper-layer multi-card experiment’s conclusions to be recomputed.

1.9 FlagTree: AMD RDNA Gains a Prefill Path, MUSA Gets Per-Copy TME Caching (10-22)

Date: 2026-10-22　Source: PR #1365 · PR #1385 · PR #1278 · PR #1415

  • AMD prefill (#1365, 66 files, +3163/−260): On top of #1364’s M=1 decode path, adds M>1 prefill execution, including prefill mode for the dense Qwen3 importer, M>1 rendering codegen (with WMMA lm_head), a fused matmul-plus-RMS-norm-stats kernel and gather-reduce normalization finish, per-prefill-token KV writes into independent cache slots, and “prefill emits logits only for the last token” — slicing only the position before lm_head rather than materializing all positions. RDNA’s prefill WMMA GEMM microkernel is 10 to 30 times faster than the GEMV loop at M>1 and is auto-selected by M; on the decode side, split-K cuts lm_head from 17.0 to 14.9 ms/token and per-layer wide projections from 14.9 to 10.5 ms/token. On W7900 (gfx1100) and R9700 (gfx1201), after a fresh compile, prefill is finite and argmax=241 matches the torch reference (max error about 0.5, a bf16 near-tie), and decode next_token=25 is unchanged.

IV. Summary and Trend Observations

  • Capacity structure: FlagGems alone accounts for 56% of merges, the quantum stack for 40% of submissions, with build and runtime at roughly 10% each. Merge volume hit a new high for the past week while submissions declined, indicating that the day’s theme was clearing backlog rather than expansion — consistent with the state following two consecutive days of large merges on 10-20 and 10-21.
  • The first cell of the 2.3 cycle: FEP-0140 and FEP-0141 merged on 10-21, and on 10-22 Hygon landed both vLLM 0.28.0 and SGLang 0.5.18. This chain went from “writing the matrix into docs” to “first validated pass” in a single day — the fastest requirement-to-evidence loop this quarter. The remaining nine vendors and two version lines are the main workload for the next six weeks.
  • Build-layer convergence: Kunlunxin becomes FlagTree’s seventh backend, flagcx 0.14.0 is pinned across twenty backends, and optest becomes an installable package. Together, the effect is “no more editing install scripts when switching backends,” which matters more for 2.3 delivery speed than any single-point performance gain.
  • Observability becomes the new weak spot: Tsingmicro gets a device timeline for the first time, and Kunlunxin’s cross-card copies had been failing silently. Both suggest that after “it runs,” the first hurdle for multi-backend is observability and reproducibility, not speed; the test porting and case-contract rework of the past two weeks (61 commits by lukatao alone) is another expression of the same judgment.
  • Risk one: All 20 FlagQuantum merges were done by a single account, and the new native Rydberg path covers only CPU and one or two roles. Physical-semantics validation depends on the same group writing both tests and implementation, leaving no independent external review; proposal 083 (terminal sampling) is not yet approved, and fast-tracking it would simultaneously change the Runtime, measurement results, and random source.
  • Risk two: “Bulk updates” like Enflame #7077 lack a verifiable breakdown — 26 files and +3520 lines cannot be mapped to specific operators or specific gains; and Kunlunxin’s three fused-MoE performance figures were measured against a substitute baseline. Both will distort subsequent cross-vendor comparisons.
  • Watch items: Whether the next vendor for vLLM 0.28 (Tsingmicro or MetaX) reuses Hygon’s empty-backend template; whether the FlagTree 0.7.1 development build (0.7.1.dev1 from 10-20) goes GA before 2.3; whether TransformerEngine-FL’s three NPU PRs merge before the weekend; and whether the silence from Horizon and Cambricon extends into next week’s report.
