1.8 Fused communication operators: RS+add+RMSNorm+AG ring kernel enters FlagGems and the SGLang plugin (11-03)

Date: 2026-11-03　Source: FlagGems PR #8317 · sglang-plugin-FL PR #166 · FlagGems-sglang PR #279 · FlagGems PR #8347

  • Kernel design: FlagGems #8317 adds two Triton kernels fusing “communication + normalization” (under review, +1403 lines, 3 files). fused_rs_add_rms_norm_ag replaces all_reduce(x) plus fused_add_rms_norm(x, residual) with a single ring kernel, doing reduce-scatter, residual add, RMSNorm, and all-gather in one pass; rank r owns only the rows in [r*chunk, min(T,(r+1)*chunk)), normalization runs only on those rows, and the residual stays in scattered form. With gather=False it stops after the owner step, doing only RS plus add plus RMSNorm. The companion fused_qkv_norm_ag handles the other end: normalizing q and kv separately on scattered qkv outputs, passing rest (k_pe) through unchanged, and running only the AG half of the ring.
  • Ring implementation: data moves concurrently over C channels, where channel c is a ring over ranks; on PPU 810E it directly reuses the pccl 28-channel graph ring so every hop goes over the ICN link. After each send, a flag is incremented on the successor, and the receiver waits for flag >= base + step; flags only increase and the buffer parity flips on each call, so a predecessor entering call n+1 won’t touch data still being read in call n.
  • Upper-layer integration: sglang-plugin-FL #166 makes this RS + norm + AG fused kernel an option for pure TP prefill on the XuanTie side (under review); FlagGems-sglang #279 merges six model-level operators (sglang fused in-place RoPE, topk_softmax, fused_moe, chunk_gated_delta_rule_fwd, fused recurrent gated delta rule and its packed decode version) along with per-platform vendor overrides, +13061/-79 lines, 85 files, where rms_norm matches the existing one_pass_rms_norm in math and ABI and is therefore merged as _mthreads, _thead, _hygon overrides rather than as new operators.
  • Supporting cleanup: XuanTie-side #8347 is under review, removing the K-alignment fallback for NT GEMM on PPU; FlagTree #1348 merged, preserving the explicit swizzled TLE layout and avoiding the copied chained dot warp layout.
  • Assessment: folding communication into operators is a common way to cut TP inference latency, but it requires the operator library to master both communication primitives and numerical contracts. This FlagGems batch is piloted first on the PPU and SGLang lines, indicating the capability is still tied to specific hardware topologies and not yet abstracted into a cross-backend general component.

III. Deep Dive into Member Units and Backend Vendors

3.1 Tsingmicro: TXDA on 0.28 Does Eager Only, Explicitly Rejects Graph Mode (11-03)

Date: 2026-11-03　Source: vllm-plugin-FL PR #642 · vllm-plugin-FL PR #641 · FlagGems PR #8279

  • Trade-off: The body of #642 is worth reading word for word. Segmented native graphs were already implemented and passed the full gate for two models under TP8 (snapshots R10 and R6d), but Dense TP1 correctness was never resolved. Rather than shipping “a graph mode that only works at some parallelism levels,” the author deleted the graph capture and partitioning implementation, rejected graph and compile configs at the configuration stage, and pointed users directly to --enforce-eager.
  • Rejection surface: MLA, sparse attention, speculative decoding, and context parallelism are each rejected item by item along their specific unsupported paths, rather than being disabled wholesale. This approach lets error messages point to the specific capability instead of letting users fail halfway through a run.
  • Validation environment: 8× TX8110 64G, with vLLM in the image at 0.28.0+empty—built from upstream tag commit 2cf0a69 with VLLM_TARGET_DEVICE=empty, without the vllm._C extension, with all kernels coming from the plugin or FlagGems. This effectively turns “is the plugin truly self-sufficient” into a hard constraint.
  • Scale: +3067 / −146 lines, 29 files, plus a docs/usage/tsingmicro.md deployment guide.
  • Assessment: This is the engineering trade-off most worth recording today. The most common failure mode in multi-backend adaptation is to ship a mode that only holds at a specific parallelism level and then expose it as numerical errors at the user site. #642 trades “one fewer mode” for “no mode that is wrong only under certain configurations”—the cost is explicit and the boundary is clear.

3.2 MetaX: C550’s 0.28 Is an “Empty Adaptation,” All Changes Kept Inside the Plugin (11-03)

Date: 2026-11-03　Source: vllm-plugin-FL PR #554 · vllm-plugin-FL PR #693 · FlagGems-vllm PR #1050 · FlagGems-vllm PR #1054

  • What “empty adaptation” means: The vendor-side MetaX-MACA/vLLM-metax has no 0.28 path yet, so #554 was done on the premise that “upstream has no corresponding branch”—all changes stay within vllm_fl/ and the MetaX CI scripts, with backend behavior gated by vendor name or runtime detection so other vendors are unaffected. +2838 / −70 lines, 36 files.

Review explicitly rejected the “write startup hooks into site-packages” approach, and that rejection itself applies to all vendors going forward.
  • Dual-track status: On the same day 0.28 was merged, the 0.32 C550 adaptation (#693) was opened at 02:23; on the FlagGems-vllm side, #1050 raises the sparse QSA dot tile lower bound to 16, and #1054 makes GLM5.3’s causal convolution and sparse MLA kernels runnable on C550 (under review), along with three operator optimizations under review: gdn_w8a16, fused_indexer_weight_scale, and layernorm.

IV. Summary and Trend Observations

Date: 2026-11-03 ~ 2026-11-04　Sources: flagos-ai organization repositories · Merged PR search

  • Faster merges, concentrated production: 177 merges, up 9.3% from the previous window; 117 newly opened PRs, down 39.1%; 271 in-review PRs updated during the window, down 12.9%. But the drop in newly opened PRs comes almost entirely from a shift in pace at a single repo, FlagGems, where 59 of them came from the same author and clustered on the Kunlunxin and Enflame product lines. Organization-wide, 1,602 PRs remain in review, a merge-to-review ratio of about 1 to 9, so review pressure has not materially eased.
  • 0.28 closes out as 0.32 opens up: Four backends — Tsingmicro, MetaX, Moore Threads, and Ascend — closed out vLLM 0.28.0 on the same day, totaling 150 files and 17,051 added lines; meanwhile, five 0.32 adaptations are moving through the review queue. Running the maintenance line and the target line in parallel has become the norm, and vendors must maintain two validation environments at once — a hidden cost of multi-chip adaptation.
  • Benchmark comparability is becoming new infrastructure: FlagGems’ 23 benchmark migrations in two minutes consolidated the H800 reference readings for four operator categories into a unified JSON; together with optest’s Feishu test summaries, FlagTree’s Feishu multi-dimensional tables, and FlagCX’s four-platform coverage, the benchmarking pipeline is shifting from “each writing its own” to “one shared ruler.” This window, 26 PRs landed on CI and benchmarking, 14.7% of merges.
  • Both paths for onboarding new chips are now proven: Biren entered TransformerEngine-FL via the SUPA backend (skeleton first, with no hardware validation record), Moore Threads landed on both the inference plugin and tensor library lines simultaneously, and Iluvatar walked the operator line with ten dedicated operators in a single day. Onboarding speed is no longer the bottleneck — validation depth is: Biren’s backend is currently only a skeleton, with no hardware gating record on par with Tsingmicro or MetaX.
  • 2.3.0 is still image-first: The base layer has expanded to six layers (including CANN 9.2.1), runtime images are pushed per backend, and changelog dates are backfilled layer by layer, but the community’s release/2.3 manifest still returns 404. Three consecutive windows have passed with no manifest freeze, and a gap is accumulating between what is actually released and what was planned.
  • Three things to watch: First, when the release/2.3 manifest appears, which determines whether 2.3.0 can ship this month; second, when the five 0.32 adaptations merge, which determines whether the target line slips again; third, whether the fused communication operator (RS+add+RMSNorm+AG) can be abstracted from the PPU and SGLang pilots into a cross-backend general component.
