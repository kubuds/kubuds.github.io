Today’s Highlights: Horizon BPU wired in as an eager operator backend; FlagCX tags v0.14.1 and completes three more rpm backends; Moore Threads open-sources Megatron-MUSA-Titan (10-28)

Date: 2026-10-28　Sources: Torch-FL PR #674 · FlagCX tag v0.14.1 · FlagCX PR #673 · IT之家 report · Megatron-MUSA-Titan repo (full list in appendix)

  • New backend surface: Torch-FL merged Horizon BPU’s per-operator execution layer (#674, 31 files, +5698/−145). Previously BPU registered no compute operators on PrivateUse1 — hbDNNInferV2 only accepts a fully compiled graph, so every aten call fell through to cpu_fallback, and backends_bpu.conf was empty. This change adds the missing intermediate layer: on the x86 side (off-board), hbdk4 compiles a per-operator .hbm artifact library, C++ kernels are generated to submit those artifacts, and a drobotics conf route is added. It covers 40 elementwise operators (32 unary, 8 binary) across 11 shape buckets; on RDK S600, all 440 artifacts matched NumPy with zero differences.
  • Version surface: FlagCX tagged v0.14.1 on 10-28 at 17:25 (commit 7ed4a82, titled “generate device bitcode per adapter, no longer hardcoding NVIDIA”, i.e. #668 merged on 10-18). The tag is a git tag only, with no GitHub Release body; the previous v0.14.0 formal Release dates back to 9-28. The same archive also shows a v0.15.0.dev0 tag (predating this window). In the same window, the 0.14.0-rc2 line received a scatter of patches (#683, under review).
  • Packaging surface: FlagCX’s rpm line expanded from three backends to six (#673, 10 files, +295/−8). The three new ones — libflagcx-tsm (Tsingmicro), libflagcx-sunrise (Sunrise), and libflagcx-du (Hygon DCU) — require no vendor base image: the SDK unpacks to /opt or /usr/local and invokes no package manager, so an openEuler image plus a file repo is a complete build environment; vendor sonames are filtered uniformly per the existing Ascend convention.
  • News surface: On 10-28, Moore Threads announced the open-sourcing of its large-model training infrastructure Megatron-MUSA-Titan, focused on trillion-parameter MoE training on 10,000-card-scale clusters, covering both pretraining and reinforcement learning; it is already in continuous use for pretraining on its 10,000-card cluster, supports blockwise FP8, combines DeepEP with ACE asynchronous communication for expert parallelism and compute overlap, and can work with the slime and miles RL frameworks. The repo MooreThreads/Megatron-MUSA-Titan exists on GitHub, but there were no pushes in this window (last push 10-16) — an “announced open-source, code unchanged” state.
  • Assessment: Each of the three threads advances one layer — plugging a new chip into the eager path (BPU), pushing the communication library’s delivery surface from source tree to tags and distribution packages (FlagCX), and extending the training-stack open-source narrative from FlagOS to member organizations’ own projects (Megatron-MUSA-Titan). The first two are directly relevant to this stack; for the third, watch whether its code flows back as reusable training components for FlagOS.

1.3 FlagGems: Kunlunxin scalar-chain fusion ~10x faster, Enflame reference-implementation batch fixes open (10-28)

Date: 2026-10-28　Sources: FlagGems PR #7617 · FlagGems PR #7600 · FlagGems PR #7850 · FlagGems PR #7803 · FlagGems PR #7036 · FlagGems PR #7061 · FlagGems PR #7223

  • Fused kernel: the Kunlunxin XPU3 side adds backend specialization for eight out-of-place scalar-chain operators (#7617, 275 lines). Isomorphic float lists go through one fused kernel: small shapes use a single launch with all pointers passed as kernel arguments, large shapes use streaming tiles; outputs come from one allocation plus unbind rather than one allocator call per tensor. Relative time for the eight operators rises from 0.083–0.126 to 0.813–0.934, roughly seven to ten times.
  • Contiguous-segment kernels: the batch-norm inference and QKV transform operators change from “one program per (n,c) slice” to “one program per contiguous BLOCK of elements, recovering the channel or packed row from the flat index” (#7600). Aggregate metrics rise from 0.228 to 1.357 and from 0.260 to 5.062 respectively; the fp32 single-precision cell is still below 0.8, which the author judges by the aggregate metric and states explicitly in the description.
  • Vectorization fix: masked_fill’s integer-view fast path kept the whole kernel scalar because arith.extsi has no vector form (fp16 0.34, fp32 0.50); rewritten as the f32 form x*(1-m)+V*m, it rises from 0.577 to 0.829 on P800, with masked_fill_ and masked_fill_scalar benefiting as well, and 594 test cases passing (#7850).
  • Imports and executor: the Kunlunxin backend fails to import directly on the latest master commit — the _result_dtype helper was removed from the shared executor in #7561 but the backend still references it (#7803, 90 lines); after fixing the import, the shared executor then reported operand #0 does not dominate this use, also fixed in this PR.
  • Operator coverage: KernelGen adds _indices_copy (#7223, 250 lines, verified on H20), but performance is only 0.21x torch — a coverage addition, not a speedup in the near term. lighting_indexer’s reference implementation now accumulates per head, cutting peak memory from about 8.6 GiB and fixing an OOM on 40 GiB cards (#5852).
  • Open side: 53 new PRs this window, mostly lukatao’s Enflame reference-implementation fixes (#7890 through #7908, consecutive), covering Kaiser/inplace ldexp, aminmax, special_round, LU, vander/slogdet, median/stacking/Lanczos, Adagrad, batch-norm ABI, and more; plus a one-line AMD fix (#7908) — AMD’s vendor descriptor sets the device name to cuda without a triton_extra_name, so pow, tanh, exp, rsqrt, erf, gelu, etc. all route to __nv_* and are rejected by the AMD backend.

1.4 FlagGems-sglang: AMD gfx1100 gains Mamba operators, Enflame core_shapes actually takes effect (10-28)

Date: 2026-10-28　Sources: FlagGems-sglang PR #231 · PR #232 · PR #229 · PR #233 · PR #237 · PR #236

  • AMD side: adds gfx1100 versions of causal_conv1d_fn, chunk_state_varlen, and bmm_chunk for the RDNA3 tier (#231, 578 lines), tuned and tested on Radeon PRO W7900D; the three change only launch parameters, with outputs bit-identical to the generic kernels. Time slicing follows the longest sequence rather than a fixed 128 tokens × 4 channels, and dstate above 128 switches to smaller tiles and a 16-token K step.
  • Enflame side: #229 added _enflame/core_shapes.yaml, but no code in the repo loads it — init_user_config() only has a hardcoded kunlunxin branch (root-cause analysis in #232). #232 generalizes shape-file lookup to “derive _<vendor>/core_shapes.yaml from vendor_name, use it if present, otherwise fall back to the shared default,” and also fixes the latent issue where the kunlunxin path was set unconditionally and raised FileNotFound when the file was absent.
  • Test infrastructure: candidate injection is unified between correctness tests and benchmarks (#233, 9 files); standalone benchmark sessions previously did not register --override, and candidate-only mode called a nonexistent registry method; get_override() exposes the actual candidate, and normal timing, preflight, and profiling share one resolver. Also adds per-case dummy-candidate call validation (#237) and a package-level import fix (#236, avoiding sys.modules conflicts).
  • Case listing: the silu benchmark supports listing cases without tensors and replaying them exactly (#234), with --list-cases pagination wrapping up the 238 merged PRs.

1.5 Compilers: FlagPrism adds Enflame, Ascend TensorView load/store reduced, FlagMega speeds up RDNA decode (10-28)

Date: 2026-10-28　Sources: FlagTree PR #1239 · FlagTree PR #1426 · FlagTree PR #1439 · FlagTree PR #1456 · FlagTree PR #1454 · flir PR #86

  • Profiling and debugging: FlagPrism’s debugger and profiler extend to the Enflame backend (#1239, 5 files, +119/−31). CMake and Python add Enflame to the supported list and enable it by default, keeping an explicit opt-out and mutual exclusion with Proton; at runtime, kernels launched with debugging go through the FlagPrism gateway, with metadata capture handled separately from the hidden control-buffer argument, while normal execution still uses the direct path.
  • IR and load/store: the Ascend backend gains the TensorView access path (#1426, 32 files, +4901 lines, merged into triton_v3.5.x). Kernels build encoded views on the base pointer with three explicit constructors, then load/store whole blocks by index; out-of-bounds lanes are filled with zero/nan/inf/-inf or dropped, and the backend chooses between “indexed-payload DMA” and “element-wise copy with zero padding” based on the index pattern between CommonIR and HIVM.
  • AMD decode: FlagMega optimizes batch-1 decode for Qwen3-1.7B bf16 (#1439, 44 files, merged into feature/flagmega). R9700 (gfx1201) reaches 154 tok/s at context 1, 150 at 1K, 139 at 4K, 125 at 8K; W7900 (gfx1100) reaches 167, 162, 149, 136 tok/s respectively, with measured bandwidth of 530–597 GB/s, 82%–87% of the card’s measured streaming ceiling.
  • Correctness: the AMD backend’s CanonicalizePointers no longer asserts, instead merging fat-pointer attributes of arith.select (#1456); the RLC side no longer re-tags producers whose layout change is illegal or unsafe (#1454).
  • CI and open PRs: FlagGems CI assets move into FlagTree (#1443, #1447); 9 new open PRs, including syncing the Tsingmicro backend to the internal Triton 3.6 dev line (#1459, 27 files, +2264 lines, with a per-launch precision API and CoreIR entry), the rpm line switching to consuming published wheels to build Ascend packages (#1461, the first line needing neither vendor SDK nor hardware), four software-pipelining bug fixes on NVIDIA Hopper (#1460, cp.async with eviction policy leaves undefined address descriptors on ptxas 12.8–13.1), Ascend structured permutation and persistent-loop performance (#1466), P800 SDNN 1-D modulo loads (#1465), and flir’s Ascend split/join and static permutation lowering (#86).

  • Enflame inference: the GCU backend adds Qwen3.5 FP8 support (#358, 20 files, +3367 lines, based on release/0.2). It introduces W8A8 block-scaled FP8 inference and reworks kernel patches around GCU300/GCU400 hardware limits so FP8 MoE models run in both eager and full-graph modes.
  • Communication wiring: the vLLM plugin now takes FlagCX from the installed package (#525, 11 files).   • Operators: FlagGems-vllm adds fused all-reduce RMSNorm (#773, 6 files, +3191 lines): all-reduce + residual add + RMSNorm, with optional static quantization (FP8, NVFP4 on SM100+), supporting FP16/BF16 at TP2/TP4/TP8, plus benchmarks against vLLM’s FlashInfer implementation and representative GLM-5.2 shapes. ihc_pre’s stage1 merge replaces tl.atomic_add with per-split-slot writes (#1017) — atomic adds made results depend on block arrival order and were not bit-reproducible on repeated launches; determinism is restored.
  • Dependencies and regressions: TransformerEngine-FL rolls the three 3rdparty/ submodules back to upstream v2.17’s validated baseline (#150): #129 had mistakenly advanced cutlass by 240 commits (4000+ files), cudnn-frontend from v1.25.0 to an unreleased snapshot, and googletest from v1.14.0 to master HEAD.

1.7 Build and release: changelog goes live on site and Harbor, two never-pushed Cambricon images withdrawn (10-28)

Date: 2026-10-28　Sources: build-infra PR #1545 · PR #1547 · PR #1548 · PR #1549 · PR #1542 · PR #1543

  • Changelog goes live: per-image changelogs now appear both at the end of site pages and as Harbor repository descriptions across all three release tiers (#1545, 455 files, +19080 lines). Previously changelogs were written only inside the repo with no consumer, so site pages, in-repo readmes, and Harbor descriptions all lacked this section, and application tiers had not even a description line. Sections are implemented as “recomputed rather than rendered inline with the body”: page bodies each have their own generator and cadence, and inline sections would be overwritten by the last line, losing reasons written in between. Empty pending entries and upstream_prs are not published; the same window first made the reasons bilingual (Chinese/English) (#1542).
  • Withdrawing nonexistent images: Harbor has no megatron_training0.18.2-cambricon-neuware4.7.2 or megatron_rl0.18.2-cambricon-neuware4.7.2 repositories, yet both 0.18.2 status matrices recorded image_tag: 2.2.0-0.3.0 (#1547, 13 files, +29/−496). That tag came from the commit that first created the matrices, not from the recording step, so the docs pipeline published launch pages, readmes, and changelogs for two nonexistent images, and every subsequent pubdoc-app run 404’d on those two repos (the other 107 accepted description PUTs).
  • Root cause of the failed image push: in the 0.18.2 wheel, platform_register has no MLU platform, and after torch_mlu’s gpu_migration aliases the CUDA surface to MLU, PlatformCUDA is selected and the pipeline-parallel group is never initialized; the MLU registration (MLF #125, including #188/#190/#191) landed only on release/0.2, and v0.3.0, 0.3.0-rc2, and main lack the file with no port in flight. The fix was to withdraw the claim rather than force it: remove image_tag from both backends, set launch_docs: false, and delete the two changelogs so that “changelog file set == published set” holds again (151 files in that set; only this block was never delivered).
  • Builder gap filled: the amd-rocm7.2.4 runtime image is based on ubuntu 24.04, and FlagCX wheels built in it link GLIBC_2.38, rejected by the wheel line’s 22.04 gate (22.04-incompatible symbols: GLIBC_2.38, GLIBCXX_3.4.32, __isoc23_). This PR gives that line a self-contained 22.04 builder, bringing the glibc floor back to 2.35: installing the jammy ROCm 7.2.4 packages (rccl/hip-dev plus the hipsolver/hipfft/miopen-hip headers torch needs, and amdgpu-core from the graphics repo), deadsnakes Python 3.12, and a pinned torch 2.11.0+rocm7.2 (#1548, 204 lines).
  • Gate moved earlier: application-tier pages previously had no consistency check — after changing an image_tag or changelog reason, pages and Harbor-facing readmes stayed stale (#1549, 6 files). Now gen_descriptions.py --app-only --check is wired into .githooks/pre-commit and CI, rebuilding images.yaml and diffing whenever the status matrix, application changelogs, application pages, or application readmes are touched.
  • Open: the repackaging line’s dependency resolution now reads the PEP 503 simple index directly (#1543) — the old implementation spawned a pip index versions subprocess per dependency, and the JSON API 404s on the Aliyun mirror, so 0.28/0.32 repackaging took about two hours and needlessly downloaded a 300MB triton wheel.

III. Deep Dive into Member Units and Backend Vendors

3.1 Horizon Robotics: BPU Becomes an Operator-by-Operator Executable PrivateUse1 Backend for the First Time (10-28)

Date: 2026-10-28　Source: Torch-FL PR #674 · PR #676 · PR #678 · PR #673

  • Integration approach: The BPU’s unit of execution is the .hbm artifact produced by hbdk4, and hbdk4 can only run on x86; the board can neither compile nor ship artifacts with the repo. The prior conclusion was “by design, eager is not possible.” This change splits it into three layers: build single-operator .hbm libraries off-board, generate C++ kernels that submit these artifacts, and add drobotics conf routing.
  • Coverage and validation: 40 elementwise operators, 11 shape buckets, all 440 artifacts on RDK S600 compared against NumPy with zero difference, and aten calls on flagos tensors indeed land on the BPU. The author also records two negative findings: libhbtl.so is merely a CPU reference implementation (ldd shows only libc/libstdc++/libm, and hbtl::ucp::Add has cpu/wall of 1.00), and dynamic shapes are not executable on HBRT 4.7.5 (the loader declares that axis as stride 0, while task validation requires no less than 64).
  • Three follow-up fixes: #676 adds two dispatcher.h switches for kDrobotics; previously the dispatch log name for BPU builds always printed unknown, and KernelSetOf reported the BPU’s own kernel library as unowned. #678 fixes three copy branches that unconditionally box to CUDA—the default FlagGems-led NVIDIA and DAMO XuanTie PPU wheels intentionally link against the CPU-only pip torch, so the CUDA copy kernel’s DispatchStub is empty and the first call fails with missing kernel for cuda. #673 fixes the mismatch between vendor name and platform id in the build record (hygon/dcu, mthreads/musa, enflame/gcu, nvidia/cuda), which is the root cause of eight unit test failures on the Hygon DCU lane.
  • Under review: #672 unifies the claim granularity of soft-lowp matrix operators (declared by conf key, decoded by family), #677 routes FlagGems calls with keyword arguments to the active backend, #680 redefines device aliases by the vendor held in the build record, and #681 reads the libtorch_cuda probe from the torch prefix rather than the interface target.
  • Assessment: This is the only integration in this window where “a new platform goes from unusable to usable.” The value lies in opening the path rather than in performance—40 elementwise operators are a starting point, while backbone operators such as convolution still rely on the torch.compile whole-graph path.

3.2 Kunlunxin: Scalar-Chain Fusion and Contiguous-Segment Kernels, Three Speedups on P800 (10-28)

Date: 2026-10-28　Source: FlagGems PR #7617 · PR #7600 · PR #7850 · PR #7803 · FlagCX PR #682

  • Scalar chains: The fused kernels for eight out-of-place scalar-chain operators raise relative time from 0.08~0.13 to 0.81~0.93 (#7617). The gain comes mainly from the host side: a single output allocation plus unbind replaces one allocator call per tensor; for small shapes, a single launch passes all pointers as arguments.
  • Contiguous segments: After batch-norm inference and QKV transformation were switched to contiguous-segment kernels, aggregate metrics went from 0.228 to 1.357 and from 0.260 to 5.062 (#7600). The original implementation organized work by (n,c) slices or 2D tiles, with non-contiguous reads and writes; the new implementation has each program cover a contiguous run of elements and derives the channel or packed row from a flat index.
  • Masked fill: masked_fill on P800 improves from 0.577 to 0.829 (#7850) by replacing sign extension of the integer mask with a 0/1 float multiply after sitofp, making the entire kernel vectorizable; in terms of precision, m is exactly 0/1, so results are bit-identical.
  • Maintainability: #7803 fixes the Kunlunxin backend failing to import on current master (the shared executor removed the _result_dtype helper) and fixes a dominance compilation error in the shared executor on uni_sram—without the fix, no Kunlunxin test can start.
  • Communication side: FlagCX’s Kunlunxin platform traits move cstddef outside the __xpu__ guard (#682); previously, when parsed from comm_traits.h, size_t was not yet visible, and host-side compilation of the public device API failed outright.

3.3 Enflame: Convolution Uses a Workload-Tier Table, conv3d Drops Channel Padding (10-28)

Date: 2026-10-28　Source: FlagGems PR #7036 · FlagGems PR #7061

  • conv_transpose2d: The generic implementation’s single default schedule (64,32,32,4) plus one 3x3/stride2 special case is replaced by seven hardware-tuned tiers indexed by data type, kernel size, stride, and output channel count (BLOCK_NHW/CI/CO, num_warps, num_stages), switching between two kernel variants depending on whether the output fits in L2—the direct-sweep variant is faster within L2, while the phase-specialized variant is more stable once the output exceeds L2 (#7036, +1886 lines).
  • conv3d: On the Enflame side, BLOCK_CI is already no less than 16, and FlagTree’s AABS also pulls shrunken tiles back to the 16x16x16 lower bound, so the generic path’s channel padding of weight_c to 16 is pure per-call allocation and copy overhead; removing it yields bit-identical output. In addition, BLOCK_NI_DO_HO_WO gains 32 and 64 small-spatial tiles so that small shapes can also fill the device (#7061).
  • Assessment: Both are long-tail tuning in the same direction—replacing “generic, correct but slow” paths with localized schedules while deleting unprofitable overhead such as padding.

3.4 Enflame: Qwen3.5 FP8 on GCU, core_shapes Wired Up, FlagPrism Integrated for the First Time (10-28)

Date: 2026-10-28　Source: vllm-plugin-FL PR #358 · FlagGems-sglang PR #232 · FlagTree PR #1239 · optest PR #14

  • Inference: The GCU backend adds W8A8 block-scaled inference for Qwen3.5 FP8, and kernel patches are reworked around GCU300/GCU400 constraints so that FP8 MoE works in both eager and whole-graph modes (#358, 20 files).
  • Shape table: Enflame’s core_shapes.yaml had been ineffective for a week—there was no load point anywhere in the repo, and the benchmark only recognized a hardcoded kunlunxin branch (#229 added the file, #232 fixed loading). The fix generalizes lookup to any vendor and also fixes the FileNotFoundError caused by the kunlunxin path being set unconditionally.
  • Toolchain: FlagPrism’s profiler and debugger are extended to Enflame and enabled by default (#1239); debug-enabled kernel launches go through the gateway, and the compiler handling needed for L2 capture stays inside the Enflame backend; optest brings S60 into CI for both FlagGems variants (#14).
  • Under review: the TXDA eager backend upgrade for vLLM 0.28 (#642), Enflame profiler and runner support in TransformerEngine (under review), and a large batch of reference implementation fixes on the FlagGems side (see 1.3).

3.5 DAMO XuanTie: MiniMax Sparse Attention on PPU, Geometric Mean 1.8x (10-28)

Date: 2026-10-28　Source: FlagAttention PR #111 · FlagAttention repo

  • Content: Adds MiniMax sparse attention (MSA) inference operators for the DAMO XuanTie PPU backend, covering index scoring, top-k block selection, and sparse attention itself, with both prefill and decode paths implemented (6 files, +4644 lines).
  • Capabilities: Supports paged KV cache, causal masking, and forced block selection; adapts matrix computation layout and kernel launch for 810E; prefill index scoring is parallelized over KV pages, alleviating insufficient parallelism on the query side; FP8 inputs are converted to BF16 for computation, without using native FP8 matrix multiplication.
  • Performance: Against the SGLang generic Triton implementation as baseline, on 810E prefill passes 21/21 with a geometric mean of 2.299x (minimum 1.965, maximum 5.434), and decode passes 18/18 with a geometric mean of 1.354x (1.289~1.485), for a total of 39/39 and a geometric mean of 1.800x.
  • Assessment: This is the first sparse attention path on PPU, contrasting with the BPU integration in Torch-FL in the same window—one fills in coverage of backbone operators, the other fills in special operators for new model structures.

IV. Summary and Trend Observations

  • A new path is now open: Horizon BPU has gone from “architecturally unable to support eager execution” to a PrivateUse1 backend capable of per-operator execution (40 elementwise operators, 440 artifacts with zero differences), accompanied by fixes to dispatch log naming and the CUDA copy kernel guard. This is the most structurally significant integration of the period, but it covers only elementwise operators; the mainline still relies on whole-graph compilation.
  • The communication layer has entered the tagging and distribution-package stage: FlagCX tagged v0.14.1 (generating device bitcode per adapter), the rpm line expanded from three backends to six, and wheel releases are now tracked in build-infra. Note that this tag has no Release body, inconsistent with the practice for v0.14.0.
  • Release engineering is catching up: changelog site deployment with Harbor, withdrawal of two Cambricon megatron images that were never pushed, app-page consistency checks added to pre-commit and CI, and a 22.04 builder for AMD 7.2.4. These produce no new capabilities, but they directly determine whether the 2.3 release checklist can be self-verifying.
  • Structural changes in open PRs: open PRs fell from 401 to 288, and newly opened from 269 to 101; the 135-commit batch in FlagGems-Experimental from the previous period was neither merged nor added to. The bulk of open PRs is now FlagGems at 181, of which 53 newly opened are mostly Enflame reference-implementation fixes — indicating that the bottleneck in multi-backend acceptance lies in reference implementations and test criteria, not operator supply.
  • Multiple branches require differentiated counting: FlagGems merges to both master and kernelgen-dev (#7905, #7934); FlagTree merges are split across triton_v3.5.x and feature/flagmega; FlagGems-Experimental’s default branch is infra-ci. Counting by default branch understates actual work, while searching by commits misses repos where operators are backfilled atomically.
  • Three points to watch: first, whether a Release note is added after v0.14.1 and whether it enters the 2.3 checklist; second, whether the BPU path expands from elementwise operators to mainline operators such as convolution; third, whether Megatron-MUSA-Titan code actually starts being pushed after the window, and whether it forms reuse with Megatron-LM-FL.
