1.2 build-infra: Ascend’s Four Wheels Migrated to a 22.04 Self-Contained Builder; Tsingmicro and Sunrise Added Same Day (10-19)

Date: 2026-10-19　Source: PR #1414 · PR #1418 · PR #1422 · PR #1417 · base directory

  • Core problem: Ascend’s four wheels were originally built in a 24.04 runtime image, producing libflagcx.so and _C*.so linked against GLIBC_2.38, which abort outright on the bundle’s 22.04 physical machines. PR #1414 gives each configuration line its own ubuntu:22.04 builder, putting it on the same channel as other vendors and lowering the glibc floor to 2.35.
  • One recipe serving four lines: ascend.mk only links -ltorch_npu -lascendcl -lhccl, independent of the specific chip; but the toolchain itself does not carry these link-time dependencies—libhccl.so and <hccl/hccl.h> come from the chip ops package—so the recipe installs both the toolkit and the ops package (excluding nnal/ATB), with the 910b vs. 910c difference passed via the ops installer’s chip token (builder.ops_product, 910b and A3).
  • Verification criteria: The SDK floor is proven with import torch_npu (which dlopens CANN toolchain libraries) rather than import torch (pure CPU on that line); ASCEND_OPP_PATH, ASCEND_AICPU_PATH, TOOLCHAIN_HOME, and LD_LIBRARY_PATH flow from set_env.sh into /etc/profile.d/vendor.sh—the same file sourced during wheel builds.
  • Two new backends added same day: Sunrise (PR #1418, a 22.04 self-contained builder for the sunrise wheel, followed by PR #1420 recording that the wheel was re-released as 22.04-clean) and Tsingmicro (PR #1422, a 22.04 self-contained builder for the tsingmicro wheel). The vendor matrix under base/ is now nvidia (cuda12.8 / cuda13.3), ascend (cann8.5.0 / cann9.0.0, including 910c), cambricon (neuware4.4.3 / 4.7.2), enflame (tops1.9.10 / 1.10.6), hygon (dtk26.04), iluvatar (corex4.4.0 / 4.5.0), metax (maca3.7.2.1 / 3.8.1.3), sunrise (tangrt1.2.0), tsingmicro (tsm260610)—9 vendors in total.
  • Three FlagTree-side changes: PR #1417 adds the Enflame builder and makes verification steps data-driven; PR #1419 fixes the “assert Enflame backend at build time” pattern; PR #1421 pre-stages the Enflame toolkit deb into the builder image, reducing per-build download dependencies. Additionally, PR #1410 reads the pybind11 ABI back from the actually emitted plugin rather than hardcoding a literal, and PR #1413 makes a failed plan fail the entire run instead of skipping the build.
  • Assessment: None of these 16 changes is feature development—all close the gap between “builds on this machine” and “runs on the target machine.” Combined with the six-backend 22.04 consolidation from 10-16 to 10-18, FlagCX’s artifact channel has transitioned from “patching backend by backend” to “one backend per line, one shared 22.04 recipe.”

1.3 FlagQuantum: 405-File Merge Expands Quantum Stack; M0 Roadmap Established (10-19)

Date: 2026-10-19　Source: PR #635 · PR #637 · PR #642 · Repository

  • Scale: 23 commits and 9 merges, tying for the highest commit count of the day. PR #635 alone touches 405 files, +114463/−3983, adding 159 public names: algorithms from 45 to 148, quantum error correction from 84 to 108, remote invocation from 20 to 32, observables from 12 to 20, compiler from 12 to 17, simulation from 8 to 11, plus a new flagquantum.operators package (4 exports). The capability registry grows from 68 to 97 entries, with development_evidence from 20 to 47.
  • Boundary discipline: All new names are subpackage entry points; Stable Core’s flagquantum.__all__ remains 41 exports, byte-identical to main. The PR description explicitly states that “promotion to Stable Core follows a separate proposal path,” and adds three contract documents (compiler pass admission, multi-level IR internal interfaces, real-time messaging).
  • Roadmap: PR #637 establishes phased scope, dependencies, and acceptance criteria for M0 through M4, requiring reuse of the existing Core IR, compiler, dynamics solvers, runtime, and PyTorch integration, covering five hardware types—superconducting, neutral atoms, ion traps, photonic, and topological; M1 starts from mixed-dimensional state spaces. The same PR also fixes precision in contracted Gaussian overlap integrals (switching to math.fsum for cancellation-sensitive sums, plus a primitive-basis regression test).
  • Dynamics and compiler: PR #639 supports mixed-dimensional state spaces, PR #640 supports explicitly truncated bosonic operators, PR #641 supports coefficient training for static operator sums, and PR #642 lets callers inject their own passes by name at two optimization points. Over 10 additional test and documentation commits change numerical assertions to “precision-based repeatability comparisons” rather than fixed literals.
  • Assessment: The quantum stack is moving from “framework prototype” to “general-purpose quantum computing framework”—PR #635 adds coverage (error correction, chemistry, real-time invocation, superoperators), while PR #637 adds boundaries and phases. Merged the same day, they signal that M0’s starting point is to document existing capabilities clearly, not to expand the API first.

  • Assessment: The significance of this article lies not in the number of figures but in the fact that it breaks down the 2.2 gains into “individually verifiable cases”—each figure carries a model name, chip model, concurrency level, and comparison baseline. The 2.2 coverage in the previous two daily briefs centered on the four aggregate metrics from the main forum; this article fills in the grouped evidence.

3.1 Hygon: FlagBLAS six-precision GEMM and L1 support land in the repo together (10-19)

Date: 2026-10-19　Source: FlagBLAS PR #151 · PR #149 · FlagGems PR #6584

  • Action: PR #151 merges six-precision kernels for gfx936 — sgemm/hgemm/bfgemm/dgemm/cgemm/zgemm — and PR #149 merges L1 support; both landed in master on the same day. On the FlagGems side, the hygon_mv timeout issue was fixed (#6584).
  • Technical approach: BF16 uses a tuning pool + TN three-way strategy + padding path, with a performance report attached; FP64 uses an MMAC dot-product kernel; half precision and complex use independent Triton kernels + shape-bucketed configurations; the reference implementation switches to calling hipBLAS via ctypes instead of cupy — indicating the test environment deliberately avoids depending on the CUDA ecosystem.
  • Gap: dgemm depends on FlagTree’s fp64 MMAC support; whether the compiler-side capability has landed in mainline requires watching subsequent FlagTree MMAC commits. Currently we can only confirm that the dependency is documented in the PR.
  • Assessment: Hygon’s prior FlagOS investment centered on build channels and device interfaces (/dev/itrctl); entering the BLAS mainline means it is now stepping up at the layer where “performance can be measured directly by benchmarks.”

IV. Summary and Trend Observations

  • Trend 1: Unification of the artifact channel precedes feature expansion. build-infra had 16 commits and 16 merges in a single day, all centered on the 22.04 self-contained builder; the four Ascend wheels, Sunrise, and Tsingmicro were pulled into the same recipe on the same day, and the base/ directory formed a matrix of 17 baseline images across 9 vendors. The lowering of the glibc floor from 2.38 to 2.35 more directly determines “whether the wheels can be installed on users’ machines” than any new operator. This thread connects with the six-backend consolidation from 10-16 to 10-18 into a complete chain, and can be seen as the first systematic catch-up after the FlagOS 2.2 release.
  • Trend 2: The quantum stack is moving from framework prototype to boundary definition for a general-purpose framework. FlagQuantum merged 405 files and 159 new public names in a single day, while using the M0-to-M4 roadmap to clarify the reuse prerequisites for five categories of hardware, and keeping the Stable Core’s 41 exports unchanged. This approach of “expanding subpackages while locking the core” is consistent with the positioning of FlagQuantum as the technical foundation document at the 10-18 Liangzhiyun release—before talking about capabilities externally, first write clearly which parts are stable interfaces.
  • Trend 3: Investment on the domestic compute side is shifting from “operators” to “benchmarks and foundational libraries”. Hygon completed six-precision GEMM and L1 support in FlagBLAS; Iluvatar added equivalent performance baselines in FlagDNN and pushed directly to master; Enflame laid out the GCU300 baseline and vLLM benchmark workflow in FlagTree; Moore Threads worked on three lines simultaneously: FlagGems, FlagTrain, and FlagSparse. The common thread is that all of them can be measured directly by benchmarks, rather than merely “supporting a certain operator.”
  • Trend 4: KernelGen has entered the final stretch of sparse and view semantics. On the merged side, _coalesce, ccol_indices_copy, and _neg_view_copy, together with more than ten sparse operators under review (_sparse_mm family, coo/csr index conversion, copy_sparse_to_sparse_), indicate that the dense mainline has largely been cleared out; meanwhile, Kunlunxin forms the largest single-backend queue with 30 under review, and the XPU3 attention family and RNN family are the main body to be merged next.
  • Trend 5: The news side has entered a post-conference digestion period, and the information focus is back on the repositories. There was 1 valid news item within the 24-hour window (China.com’s 10-19 technical breakdown, adding seven quantitative cases); direct searches by component name returned zero hits for a second consecutive period, and sub-forum minutes and workshop content have not yet been written up. Experience suggests that one to two days after such a window, secondary reporting from sub-forums usually appears, which can serve as an observation point for the next issue.
  • Watch for next issue: First, when the FlagQuantum feat/m0-common-foundation branch (created 10-19 16:47) will land a PR; second, the merge pace of the FlagGems batch of sparse kernels in the review queue; third, whether build-infra will replicate the “one backend per line” recipe to the artifact lines of FlagTree and Torch-FL; fourth, whether the conference sub-forum minutes will be made public.
