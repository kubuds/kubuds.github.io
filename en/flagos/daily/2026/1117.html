Today’s Focus: 2.3.0 runtime images begin per-vendor bookkeeping; Hygon dtk26.10 and FlagTree 0.7.1a1 complete version interlock (11-16)

Date: 2026-11-16　Source: build-infra #1831 · build-infra #1832 · build-infra #1833 · build-infra #1834

  • Bookkeeping: All 13 of build-infra’s merges today revolve around a single thread—four bot-generated documentation records (#1824 and #1835 update runtime, #1833 updates base, #1834 adds the changelog date for hygon-dtk26.10) write the 2.3.0 tag into the description pages of each vendor’s base and runtime images. On the Hygon side, two tags are directly visible: flagos-base-hygon-dtk26.10:2.3.0 and flagos-runtime-hygon-dtk26.10:2.3.0. The images pin flagtree==0.7.1a1+hcu3.6, flag_gems==5.4.0, flagcx==0.14.1+dtk2610, and torch==2.13.0+dtk2610, with Triton 3.7.0 retained as an optional switchable item.
  • Reason for pairing: The description in #1831 spells out the root cause precisely—hygon 26.10’s clang-18 switched from bare dtk_llvm.run to dtk_llvm-1.0.0+dtk2604.2609221416.g5f9d5e, and the numRecords parameter of llvm.amdgcn.make.buffer.rsrc is i32 in the old package but i64 in the new one; FlagTree emitted i32 before 0.7.0 and i64 starting from 0.7.1a1. When the two are mismatched, every kernel compilation reports Intrinsic has incorrect argument type—which is exactly the failure the 26.10 line had previously hit on the F path. This change locks aillvm and FlagTree to the same version pair, and on hygon25 verifies with a locally built cp312 wheel that the add and reduction kernels produce values consistent with torch on the FlagTree path.
  • Registration: #1832 adds the index record for the cp312 wheel of flagtree-0.7.1a1+hcu3.6 in flagos-pypi-hygon—that index previously had only the cp310 record for 0.7.0, while the 26.10 runtime now pins 0.7.1a1, so the missing piece was exactly the wheel this line needs to install.
  • Schedule: Per the community 2.3 timeline, the FEP merge deadline is 11-13, feature freeze and rc0 cut is 11-30, rc1 is 12-07, rc2 is 12-14, final freeze is 12-25, and GA is 12-30. The 2.3.0 tags written today belong to the pre-release line and do not equal an official release; the daily will henceforth record in two layers: “images land first, release follows.”
  • Implication: The real fragility of a cross-chip stack often lies not in operator semantics but in the binary conventions between the compiler and driver packages—a single change in an intrinsic’s parameter width can break compilation for an entire vendor line. Only by writing such pairings into build-infra’s contract checks (check_flagtree_contract.py --rows hcu-dtk2610 reports no drift) is the premise of “the same code running on multiple chips” truly pinned down.

1.4 FlagGems: exponential_ Random-Stream Replay and clone FakeTensor Crash Fixed the Same Day (11-16)

Date: 2026-11-16　Source: FlagGems #8141 · FlagGems #8893 · FlagGems #9266

  • Random-stream replay: #8141 notes that vLLM samples via the exponential-race form argmax(probs / q), q ~ Exp(1), so exponential_ must return i.i.d. samples and advance the generator between calls. The f32 unroll8 kernel takes one philox counter per output element, but the wrapper only advances the generator by N/8, so each call replays the previous call’s 7/8 of the random stream — in a 2^20-scale sampling, q2[:-N/8] and q1[N/8:] coincide exactly across 917504 elements. The fix reserves counters according to the programs actually launched (including tail lanes that are masked but still sampling).
  • Log fast-path distortion: safe_fast_log_f32 splits ln(u) into exponent*ln2 + p(mantissa); when u is slightly below 1, both terms are about 0.69 and cancel, leaving the polynomial’s ~1e-5 absolute error directly in the result and distorting the left tail. Fixed in the same PR.
  • Crash under compile: #8893 addresses x.clone() reporting “Cannot access data pointer of Tensor (e.g. FakeTensor…)” inside torch.compile with FlagGems enabled — aten::clone is a composite operator whose Meta implementation goes through the default backend kernel, so shape propagation lands in flag_gems/ops/clone.py and calls data_ptr() on a FakeTensor. The fix detects is_meta or fake_mode inputs and resolves the output layout directly without launching a kernel; 3 new cases covering memory formats times transposed/regular were added, and test_clone.py passes 64 items. AMD’s vllm-plugin-FL adaptation is pinned to this PR.
  • Benchmark defect: #9266 fixes the hardcoded backend dispatch in the router_gemm benchmark so it picks the kernel for the current backend.

1.5 FlagGems-vllm: First BNSD FlashAttention Forward for Ascend 950DT, Sampling and Speculative Decoding Operators Completed (11-16)

Date: 2026-11-16　Source: FlagGems-vllm #1245 · FlagGems-vllm #1194 · FlagGems-vllm #1115 · FlagGems-vllm #1163

  • 950DT forward: #1245 adds a BNSD FlashAttention forward for Ascend 950DT (dense and causal branches), registered as flash_attention_fwd under _ascend/a5/ops and dispatched via SpecOpRegistrar’s a5 architecture key, +2215 lines, 7 files. The interface is dense-form q[B,Hq,S,D], k/v[B,Hkv,S,D], fp16, D ∈ {64,128}, Hq % Hkv == 0, Sq == Skv, kept distinct from the existing varlen/paged paths.
  • Implementation approach: The kernel uses plain tl.dot plus online softmax (dense and causal share build_tile_order, _max_nan, and _COMPILE_OPTS), delegating Cube/Vector pipeline splitting to the compiler (--set-cv-pipeline-mode) rather than hand-writing cann.scope and sync_block_* scheduling; the causal branch no longer peels the diagonal block out of the pipelined KV loop, and masking becomes an in-tile row/column comparison. The mask uses a true -inf instead of qk + (-1e6) — when q·k·scale approaches 1e6 the finite bias is overwhelmed; the author notes this was reproduced against the vendor implementation.
  • T-Head PPU: #1194 adds cast_sigmoid (elementwise sigmoid with explicit output and compute dtype, for vLLM’s grouped top-k gating scores); sigmoid is written as 1/(1+exp2(-x*log2(e))) so the exponential maps to an SFU instruction and log2(e) folds into the parameter, with the FP32 result converted only once on store; autotune candidates are registered in both T-Head and NVIDIA tune_configs.
  • Sampling and speculative decoding: five consecutive merges complete the draft-to-sample chain — draft slot padding (#1171), watermark mask (#1112), draft sampling collection (#1113), sampling output (#1158) and sampled/rejected counts (#1115), under the operator names pad_trailing_draft_slots, draft_watermarking_mask, gather_draft_sampled, gather_sampler_output
    and get_num_sampled_and_rejected.
  • Sampling counter on H100: #1115 changes H100 to process at most 128 requests per Triton program (previously one program per request), adds a T-Head backend implementation, and auto-selects it on PPU devices.
  • Extension scaffolding: #1163 adds the optional flaggems_vllm.extensions namespace (+1288 lines, 44 files), dispatching arch → vendor → generic in descending order and raising NotImplementedError when an implementation is missing rather than falling back to torch computation; it is kept separate from flaggems_vllm/ops/ because the latter is pulled into _FULL_CONFIG by enable() and patched into ATen. This is scaffolding only, with no operators yet.
  • Other merges: #1229 adds exact-FP32 cooperative_topk for Ascend 910B4 and Tianshu BI-V150 (148 passed, 8 skipped); #1225 aligns CI naming and structure with FlagGems; #1253 makes benchmarks use the vLLM reference when available.

1.6 FlagTree: TLE Tracking Shares Byte Ranges Across Calls, AMD Atomic-Ordering Barrier Ported from Triton 3.9 (11-16~11-17)

Date: 2026-11-16 ~ 2026-11-17　Source: FlagTree #1537 · FlagTree #1654 · FlagTree #1626 · FlagTree #1662

  • TLE alias analysis: #1537 makes TLE’s barrier analysis track physical byte ranges and borrowed shared memory — shared buffers may alias via byte offsets or be passed as borrowed arguments, with the callee’s scratch landing in the translated call frame; the old analysis only looked at callee exit accesses and thus missed ordering between caller and callee and between atomic return broadcasts. The change propagates call entry and exit summaries (with frame offsets) and checks atomic scratch in the operator’s owning function (+1043/-11, 8 files, native compilation changes guarded by __TLE__).
  • Verification strength: All 5 new TLE MLIR regression files pass, including a cross-call atomic case that fails on the original implementation; 15 GPU cases pass on H800, and the 4-warp owned-alias case reproduces 64/128 wrong values on main; the full TLE MLIR suite passes 121, with the same 7 failures as main.
  • AMD atomic ordering: #1654 ports Triton v3.9’s Insert CTA barriers for atomic memory semantics and a structured-binding fix in emitFence. The observed failure is stark — on AMD, release atomics lower only to buffer_wbl2 + s_waitcnt covering the current wave, so with more than 4 warps per program, other warps’ writes are not visible before the barrier count advances: 4-warp and 8-warp runs read stale data 0-2 and 1-2 times per 300 launches, and 16-warp runs 300/300. FlagGems’ linalg_matrix_power grid-sync kernel hits exactly this, with test_linalg_matrix_power.py failing 30-32/506 cases per run on Instinct.
  • Non-MFMA dot: #1626 fixes AMD Backend BlockPingpong behavior on non-MFMA dot, porting the corresponding Triton v3.7 change.
  • Backend list: #1662 adds the Intellifusion backend to the readme and updates the TLE support list (-922 lines are documentation reflow).

3.1 Moore Threads: 12 Dedicated foreach Family Operators Merged in One Batch (11-16)

Date: 2026-11-16　Source: FlagGems #9186 · FlagGems #9288 · build-infra #1829 · FlagSparse #120

  • Operator surface: The foreach family gains 12 dedicated operators in one pass, covering two unary variants of abs and acos, five binary variants of add (Scalar, ScalarList, List, Scalar, ScalarList), three three-segment variants of addcdiv (Scalar, ScalarList, Tensor), and two forms of true_divide. 3.3 Hygon: LLVM and FlagTree Version Interlock for dtk26.10 (11-16)

Date: 2026-11-16　Source: build-infra #1831 · build-infra #1832 · FlagAttention #136 · build-infra runtime docs

  • Pairing details: clang-18 in the 26.10 base image is now provided by
    dtk_llvm-1.0.0+dtk2604.2609221416.g5f9d5e. That build widens the numRecords parameter of llvm.amdgcn.make.buffer.rsrc from i32 to i64, while FlagTree only emits i64 starting from 0.7.1a1; when the two are mismatched, every kernel compilation reports Intrinsic has incorrect argument type. The runtime therefore pins FlagTree to 0.7.1a1+hcu3.6 and adds that version’s cp312 wheel to the flagos-pypi-hygon index (previously only the cp310 record for 0.7.0 existed).
  • Image contents: flagos-runtime-hygon-dtk26.10:2.3.0 contains Python 3.12,
    FlagTree 0.7.1a1+hcu3.6, FlagGems 5.4.0, FlagCX 0.14.1+dtk2610, torch 2.13.0+dtk2610, and flash_attn 2.8.4+dtk2610; host driver 6.4.2-V2.1.0, chip model Hygon BW1000. Inside the container you can switch between FlagTree and Triton 3.7.0, and environment variables can re-pin FlagTree and FlagGems versions before startup.
  • Operator side: FlagAttention #136 simplifies dispatch and validation for Hygon GLA.
  • Observation: The keyword for the Hygon line is “pairing” rather than “addition” — only by locking the driver package, LLVM, FlagTree, and the wheel in the index to the same set of versions does reproducibility become possible.

3.4 Iluvatar CoreX: FlagCX Adds GDR Device Family and PXN Topology Query (11-16)

Date: 2026-11-16　Source: FlagCX #714 · FlagGems-vllm #1229

  • Capability surface: #714 adds Iluvatar’s GDR device family to FlagCX’s PAL layer and advertises GPU memory registration capability through the IB adapter, supplying the IXCUDA peer-access query needed for PXN topology discovery; it also fixes allocation cleanup when GDR pointer setup fails, preserves existing write-flush behavior, and re-enables the previously quarantined SendRecv and PXN AlltoAll cases.
  • Validation: The PR self-reports local checks as 11/11 on the Iluvatar runner script, 9/9 on adapter GPU CI checks, and 3/3 on platform configuration, with the modified GDR and IBRC code passing local syntax checks; the PR also states that hardware results for CoreX GPU and IB must be confirmed outside the merge process, with acceptance criteria being four one-sided cases with no skips, PXN AlltoAll showing relay traffic on both logical nodes, and SendRecv passing in all three modes: HYBRID P2P, forced NET, and PXN.
  • Operator side: #1229’s cooperative_topk adds an exact FP32 implementation for Iluvatar BI-V150 — a shared-memory histogram plus candidate compaction, with exact refinement on capacity overflow, preserving the six-parameter API and in-place INT32 output.
  • Build context: FlagGems-vllm #659’s AMD adaptation notes mention that HEAD already includes one Iluvatar conflict resolution, indicating that the Iluvatar and AMD adaptation lines share the same batch of conflict handling on vLLM 0.32.

3.5 Ascend: 950DT’s a5 Architecture and KMCompiler Silent Wrong-Value Fix in Parallel (11-16)

Date: 2026-11-16　Source: FlagGems-vllm #1245 · FlagGems-vllm #1229 · FlagGems #8886 · FlagAttention #138

  • New architecture: The 950DT BNSD FlashAttention forward enters _ascend/a5/ops with a5 as the architecture key, alongside the existing varlen/paged paths in _ascend/fused/attention.py; this PR uses “generate a usable forward for new hardware first” as the entry point, delivering benchmarks and accuracy tests together.
  • Precision stance: The mask uses a true -inf replacement rather than qk + (-1e6); the author’s rationale is that a finite bias can be breached when q·k·scale approaches 1e6 — this kind of implementation difference that “looks like it runs but errs at the boundary” is precisely the hardest part to catch in cross-chip alignment.
  • Silent wrong values: #8886 fixes silent wrong values from KMCompiler on Ascend for polygamma and GRU caused by blockify region mismatches (the title directly names silent wrong results). Silent wrong values are more dangerous than compilation failures, because downstream only sees degraded accuracy.
  • Other: #1229’s Ascend 910B4 cooperative_topk uses segmented CANN sort/merge plus integer-key refinement and a masked histogram; FlagAttention #138 addresses Ascend-side compatibility issues; on the build line, 0.7.1+ascend3.5 was already released on 11-12, with no new additions this period.
