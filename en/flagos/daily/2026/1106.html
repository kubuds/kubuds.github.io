III. Deep Dive into Member Units and Backend Vendors

3.1 Cambricon: CNNL Fused Attention Forward and Backward, 190 Fallbacks Cleared to Zero (11-05)

Date: 2026-11-05　Source: Torch-FL #748 · Torch-FL #749 · Torch-FL #757 · Torch-FL #754

  • Root cause: SDPA was decomposed into three leaf operators on the Cambricon backend because cambricon was excluded from composite coverage, so every attention pass had to write the B×H×S×S score matrix into HBM and read it back. #748 restored CNNL’s fused forward into coverage: 8 files, +315/−27 lines.
  • Backward after forward: #749 filled in the gradient path with CNNL’s fused backward and wrapped it together with the forward into a C++ autograd Function, so a single training call runs both passes through the fused kernel. 3 files, +342/−112 lines.
  • Census-style wrap-up: #757 did not look at individual operators but first ran a fallback census over a complete Qwen3 causal language model training step, finding only two remaining fallback points—aten::mul.out at 188 times and aten::embedding_dense_backward at 2 times, 190 in total; after both were switched to execute via CNNL on MLU, the same step reported zero operator CPU fallbacks.
  • Engineering details: The Cambricon code generator was extended with these two operators, and gen_vendor_confs.py re-derived routing so that factory configuration and registration files can no longer contradict each other; #754 keeps mul’s operands on device and shares the runtime queue, avoiding round trips of intermediate results to the host.
  • Authors and tooling: All three PR bodies carry an AI agent information section, with tools dsh (DeepSeek Harness) and another coding agent, models labeled deepseek-v4.1-flash and gpt-6.1-sol, and human review uniformly by the same maintainer.
  • Assessment: Going from “it runs” to “zero fallbacks” is the dividing line for training usability. Of the 190 fallbacks, 188 came from a single operator, showing that this kind of wrap-up relies on a census rather than guesswork.

3.2 Enflame: GCU300 Clears 25 PRs Overnight, NVIDIA External Symbols Replaced One by One with Local Implementations (11-05)

Date: 2026-11-05　Source: FlagGems #8443 · FlagGems #8442 · FlagGems #8441 · FlagGems #8429 · FlagGems #8426 · FlagGems #8417 · FlagTree #1576

  • Scale: 25 merged PRs, all prefixed with KernelGen and Enflame, all by the same author; the 41 GCU300 coverage PRs newly opened in the previous issue began landing in bulk here.
  • Approach one: split out external symbols. Several PRs center on “runs without NVIDIA’s __nv_* external symbols”—__nv_nearbyintf, __nv_y0f / __nv_y1f, __nv_j0f, normcdfinv, etc., each replaced with a local implementation, corresponding to operators such as choose_qparams_optimized, special_bessel_y0/y1, special_bessel_j0, and special_ndtri.
  • Approach two: switch algorithm paths. special_chebyshev_polynomial_t now uses a dedicated kernel; linalg_householder_product uses a single-pass reflector sweep; linalg_inv_ex uses a single-kernel Gauss-Jordan; compute_linear_combination replaces the outer product with tl.dot; mixed_dtypes_linear rewrites packing and tiling.
  • Approach three: strip out incompatible compile-time features. renorm_’s autotuning causes this backend’s compiler to abort outright, so the whole block was dropped; the fake_quantize series switches to magic-add rounding to avoid extern dependencies; launch parameters for adaptive_avg_pool3d_backward, cholesky_inverse, and linalg_tensorinv are now planned on the host side.
  • Approach four: fix launch geometry. Launch geometry for special_i1e and special_modified_bessel_k0 was corrected one by one, along with the batch-norm functional kernel geometry for linalg_householder_product.
  • Compiler side: #1576 newly opened, adding SoC-level distribution enhancements for TLE, moving operator-level rewrites one step toward compiler capabilities.
  • Assessment: The method on this line is to translate “upstream formulations” into “formulations this backend supports,” clearing the ledger item by item. The cost is a large number of PRs with small individual changes; the benefit is that coverage can go from a few dozen operators to over a thousand within two weeks.

3.4 Ascend: Flash Attention Fixes UB Overflow, Adds varlen Forward and D=256 (11-05)

Date: 2026-11-05　Source: FlagGems #7581 · FlagGems-vllm #1048 · FlagGems-vllm #1077 · FlagBLAS #159 · FlagCX #692 · FlagTree #1507

  • Flash Attention: #7581 fixes UB overflow and backward compilation issues in forward and backward, 5 files, +1865/−286 lines. The approach bounds both tiling and buffering for forward and backward, compiles dQ separately from dK/dV while retaining FP32 accumulation, tail handling, and GQA gradient reduction.
  • Two capabilities added: Ascend’s varlen forward is newly added and registered; for dense D=256, K is first loaded in contiguous [N, D] order and then transposed for QK, the forward KV tile is enlarged, and only dQ’s query tile is enlarged, while dK/dV stays within the buffer limit.
  • Boundary alignment: The causal full mask and masked region are aligned to KV tile boundaries, avoiding tile overlap when BLOCK_N is greater than BLOCK_M.
  • Regression: Forward regression against a CPU reference was added, covering FP16 and BF16, causal and non-causal, padded head dimensions, sequence tails, and GQA.
  • Inference side: #1048 implements a fused indexer weight scaling operator with TLE, two-stage pipeline, 4096-element tiling, UB allocation via TLE, retaining FP32 output; shapes taken from GLM-5.3-Flash. Three XCS tag fixes the same day aligned perf inputs with tags.
  • Other: #159 optimizes Ascend cgemm and scores it against an archived H100 baseline (under review); #692 enables PCI topology for PAL under AscendCL and DCMI fallback (under review); #1507 makes the Ascend 3.5 compiler export triton_key (under review).

IV. Summary and Trend Observations

Date: 2026-11-05 ~ 2026-11-06　Source: flagos-ai organization · PR links for each item in this issue (see appendix)

  • In one sentence: The day’s main thread was “closing out”—Enflame cleared 25 GCU300 rewrite PRs in one pass, Cambricon completed fused attention forward and backward and drove training-step fallbacks to zero, and the community sent 7 FEPs into review, preparing for 2.3’s 11-13 deadline.
  • Observation one: The pace fell back, but the direction became clearer. Commits went 238→123 and merges 167→94, but what landed in specific repos was all “finishing the last stretch”: Torch-FL adding backward, FlagGems clearing the ledger, FlagTree opening the door to vendor hand-written kernels. On a wrap-up day after the breadth phase ends, output looks smaller, but the push toward usability is more direct.
  • Observation two: The FEP batch is the real boundary of 2.3’s scope. The seven new FEPs point to the same thing—writing “multi-backend capability” as acceptance-testable items: FlagMega v0.1’s MegaKernel compilation, TLE Raw’s five backends, FlagPrism v0.2’s multi-backend debugging, and FLIR optimization on Ascend and GPGPU. All are Provisional Drafts and all note that GPU acceptance has not been run, indicating these are scope declarations rather than completion declarations; the real hard boundary is the 11-13 merge deadline.
  • Observation three: Version engineering is beginning to “retire audibly”. cuda12.8 was frozen because torch 2.13 no longer ships cu128 wheels; the approach is to add an enabled field and set it to false, keeping specs and docs while letting the sole resolver block it from all matrices. Freezing is neither deletion nor laissez-faire—this pattern is worth reusing for other backend retirements.
  • Observation four: CI capacity became FlagQuantum’s main work. None of the 27 commits involved quantum algorithms; all were about sorting out hosted runner capacity, image eligibility, coverage partitioning, and cancellation semantics. The fault-tolerant compilation branch already has an integration PR of 276 files and 31k lines; if test infrastructure can’t keep up, it’s just spinning in place.
  • Observation five: AI agents are the main committers; the bottleneck is review. Of the 94 merges, 25 came from the same agent session, with PR bodies carrying tool, model, and human-review fields. The review-side pending pool still has 255 PRs, with 87 newly opened, and FlagGems and FlagTree account for 60%—writing is no longer the bottleneck.
  • To watch: Whether the seven FEPs can be taken in before 11-13; whether FlagGems’ pending pool will drop along with Enflame’s clearing; when FlagQuantum’s fault-tolerant compilation integration PR will move from draft to formal review; and whether the cuda13.3 line will touch the torch version again before 2.3.0 rc0 (11-30).
