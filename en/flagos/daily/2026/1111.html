1.2 Torch-FL: 14 merges in a single day after rename; Cambricon Qwen3 training step lands (11-10)

Date: 2026-11-10　Source: Torch-FL repo · Torch-FL #809 (Cambricon Qwen3 training step) · Torch-FL #789 (Kunlunxin FlagGems routing)

  • Positioning: Torch-FL is the repo formerly named PyTorch-Plugin-FL; the README now reads torch-fl, exposing a single flagos device that routes each operator among four implementation classes — reusable local kernels, portable compiler kernels, vendor-native implementations, and explicit CPU fallback. The same batch of docs commits also renamed the related documentation to torch-fl.
  • Single-day scale: 14 merges, making it the fourth-largest repo by commits this period and the fastest-growing major repo, with another 102 open issues.
  • Cambricon: #809 supplies the 17 Cambricon operators needed by the Qwen3 training step directly from the code generator locally, including the in-place arithmetic family, three fused CNNL entry points, four view operators, and zeros, sqrt, and div, while also fixing a lifetime defect in fill_.
  • Build defect found along the way: torch_bindings had never been compiled with USE_CAMBRICON, so the binding that tells Triton which cnrt queue to launch into did not exist at all; Triton was effectively running on an empty queue with no ordering guarantee relative to CNNL kernels.
  • Performance status: The training step takes 1.86× the time of torch_mlu and has not yet caught up; the PR itself states it only addresses operator coverage and queue ordering, not performance parity.
  • Multi-backend in the same batch: #801 adds an experimental TileOPs vendor route, #802 adds argmin and max.dim/min.dim on MPS, #797 moves Tianshu backend type conversion back to the device side, and #790 relaxes the Tianshu fused-attention switch to the model’s own call pattern.
  • Under review: A PR routing 316 operators measured on P800 wholesale to FlagGems is still under review — the next major move on the Kunlunxin side.

1.3 FlagGems: 149 merges; of 130 KernelGen commits, 89 MetaX and 20 Hygon (11-10)

Date: 2026-11-10　Source: FlagGems repo · FlagGems #8723 (Qingwei backend upgraded to FlagTree 0.7.0) · FlagGems #8643 (Kunlunxin var and vander)

  • Scale: 149 commits and 149 merges, all in this repo, accounting for 60% of organization-wide merges; 130 carry the KernelGen label, split by backend into MetaX 89, Hygon 20, NVIDIA 9, Moore Threads 9, and Kunlunxin 3.
  • MetaX foreach family: The 89 are the full foreach-prefixed operator set, covering tensor, scalar, list, and in-place variants of the add, mul, and div families, plus maximum, minimum, log, log2, log10, log1p, abs, acos, neg, addcdiv, and more — a whole-family completion rather than scattered patches.
  • Hygon: The 20 dedicated operators are mainly special functions, pooling, deconvolution, embedding_bag backward, hash_tensor, and fused matrix multiply, plus quality-check items adding layer_norm and native_layer_norm.
  • Correctness fixes: cdist_backward now dispatches gradient formulas by p-norm; Kunlunxin gains a batch_norm backward override and fixes to the var signature and vander override; the benchmark JSON record for W8A8 INT8 matrix multiply is restored.
  • Engineering hygiene: A pre-commit hook for full-width punctuation was added, along with a fix for an unused-variable warning in Moore Threads linalg_tensorinv; trailing commas and import order in the metax and mthreads operator files were also cleaned up.

1.11 docs: FlagPrism vendor adaptation spec rewritten as an interface contract (11-10)

Date: 2026-11-10　Source: docs #580 (FlagPrism adaptation spec) · FlagPrism repo

  • Change size: About 390 lines added and 30 removed in each of Chinese and English, rewriting what was a one-page adaptation requirement into a full specification.
  • Structure: Organized into four sections — goals, Profiler adaptation interface, Debugger integration, and zero impact when disabled — and clarifies three information classes: basic instrumentation information, numerical summaries, and chip performance information, of which only the third depends on the vendor Profiler.
  • Interface-ization: Specifies 6 pure virtual interfaces for vendor adapters (backend name, device type, supported hardware metrics, collection plan generation, etc.) and fixes the runtime collection flow at six steps: generate plan, configure collector, start/stop operators, flush, stop, and import.
  • Significance: Onboarding a new chip to FlagPrism shifts from code changes to implementing a set of interfaces, consistent with the backend adaptation approach of other FlagOS components.

III. Deep Dive into Member Units and Backend Vendors

3.1 Cambricon: 17 Operators in the Qwen3 Training Step Switched to CNNL, Dual-Queue Out-of-Order Issue Fixed (11-10)

Date: 2026-11-10　Source: Torch-FL #809

  • Coverage: 17 operators now supplied directly from the code generator to Cambricon native implementations; the training step no longer routes these operators through FlagGems.
  • Categories: In-place arithmetic family, three fused CNNL entry points (add-divide, add-multiply, linear interpolation), four view operator types (slice, alias, transpose, unsafe view), plus zeros, sqrt, and div.
  • Defects: Fixed a lifecycle issue in fill_; more critically, torch_bindings was not compiled with USE_CAMBRICON, so Triton launched on an empty cnrt queue with no ordering constraint against CNNL kernels — this class of silent defect throws no error, only intermittent wrong numbers.
  • Performance: This training step still takes 1.86x as long as torch_mlu; the PR explicitly states it only addresses coverage and correctness, not performance parity.
  • Effort level: A single change covering 17 operators plus a build-system defect — the heaviest member-unit item this period.

3.2 Kunlunxin: All Four Blockers Closed on P800, FlagGems Routing Left Empty Pending Profiling (11-10)

Date: 2026-11-10　Source: Torch-FL #789 · FlagGems #8643 · FlagGems #8641

  • Problem: The Kunlunxin wheel was in fact already compiled into FlagGems, but the backend config routed zero operators to it, so every FlagGems-covered operator fell back to CPU on Kunlunxin.
  • Four blockers: The config generator could not route any operator to Kunlunxin (the escape hatch documented was a silent no-op), no registration file existed for the FlagGems slot, the runtime glue needed to run FlagGems under CPU-only torch was missing, and the native-vs-FlagGems priority config did not name the platform.
  • Result: All four blockers closed and end-to-end validation passed on P800; however, the allowlist remains empty and the config file is byte-for-byte identical to before the change — per the author, the first route must be backed by P800 profiling data.
  • Next: A PR routing all 316 P800-measured operators to FlagGems is under review — the next step for this line.
  • Operator side: FlagGems also added a batch_norm backward override for Kunlunxin the same day, and fixed the var signature and vander override.

3.3 MetaX: 89 KernelGen Commits in a Single Day, foreach Family Rolled Out Wholesale (11-10)

Date: 2026-11-10　Source: FlagGems (MetaX KernelGen batch) · FlagGems-vllm #849

  • Scale: 89 KernelGen-specific operators merged, 68% of all org-wide KernelGen merges — the largest backend queue this period.
  • Family breakdown: Concentrated in foreach-prefixed operators — add, multiply, divide, min/max, log, abs, acos, neg, add-divide, and others, with tensor, scalar, list, and in-place variants nearly all aligned one-to-one: a complete family fill-in.
  • Assessment: This pattern indicates MetaX has finished mapping the interface semantics of the foreach family and handed it en masse to the auto-generation pipeline, with humans only reviewing — a different stage of work from last period’s 63 Enflame commits “grinding out defects operator by operator.”
  • Portability: The indexer K-quantized cache collection operator now uses a single portable implementation shared by Ascend and MetaX, reducing the fork where each wrote its own.

3.4 Hygon: 20 Specialized Operators Merged, BW1100 Added to CI Test Labels (11-10)

Date: 2026-11-10　Source: FlagGems (Hygon KernelGen batch) · FlagTree #1597 (hcu3.6-bw1100 test label) · FlagTree (FP64 matmul-add support)

  • Operators: 20 specialized operators merged, covering 3D and 2D adaptive pooling backward, special Chebyshev polynomial, special i1e, index reduction, Lanczos upsampling backward, divide and dequantize, soft-threshold backward, remainder, in-place multiply, overwritable convolution, depthwise separable convolution, convolution mode, embedding_bag dense backward, masked scaling, MPS-specific attention math variants, convolution double backward, tensor hash, and matmul with bias activation.
  • Compiler: FlagTree added Hygon FP64 matmul-add support in the same batch, indicating its FP64 path no longer relies solely on emulation.
  • CI: Added Qwen test labels for the hcu3.6 + BW1100 combination — the new-generation chip has entered routine regression.
  • Numerics library side: FlagGems quality checks added layer_norm and native layer_norm — correctness backstops for a foundational normalization operator.

3.5 Iluvatar, Moore Threads, T-Head, Tsingmicro: Small Steps on Backend Versions and Wheel Installation (11-10)

Date: 2026-11-10　Source: FlagTree #1409 · FlagGems-vllm #1148 · FlagGems #8723

  • Iluvatar: FlagTree added set_layout support and bumped LLVM to 0.7.0 to fix attention; Torch-FL moved type conversion back to the device side and relaxed the enablement conditions for fused attention — both reduce host-side round trips.
  • Moore Threads: FlagTree fixed PH1 warp specialization and SQMMA synchronization; on the FlagGems side, 9 KernelGen merges, including a specialized implementation of linalg_householder_product.
  • T-Head: FlagGems-vllm added a thead install entry that directly installs the PPU vendor build of the vLLM wheel, and enabled FP8 fused-operator test coverage. This is T-Head’s PPU accelerator card line, not the XuanTie (DAMO) RISC-V processor.
  • Tsingmicro: FlagGems bumped the tsm260610 backend to the FlagTree 0.7.0 + tsingmicro3.6 corresponding version — a pinning that follows the compiler mainline.

IV. Summary and Trend Observations

  • Competition sprint pushes the operator library up an order of magnitude: 17 SGLang competition operators merged at once, plus MetaX’s 89-commit full foreach family fill-in, brought single-day merges to a recent high of 245; but the review queue also rose to 343, making review bandwidth the main bottleneck.
  • Torch-FL, post-rename, has become the second front: 14 merges in one day, with the Cambricon and Kunlunxin lines advancing simultaneously — and both are filling in the “routing” layer rather than operator implementations themselves, indicating FlagOS’s competitive dimension is shifting from operator count to framework-integration completeness.
  • A compiler and runtime version matrix is taking shape: Over the past week, runtime 2.3.0 has successively locked in five backend lines — Ascend CANN 9.2.1, NVIDIA CUDA 13.3, MetaX, T-Head PPU 2.1.0, and AMD ROCm 7.2.4 — with Ascend 9.2.1 additionally opening a daily-build line; the release cadence is now split by vendor.
  • Adaptation work is becoming contractualized: FlagPrism codifies vendor adaptation into a 6-interface spec, FlagTree turns performance tuning into four compiler switches, and FlagGems-vllm blocks unregistered exported operators at CI — all three moves turn verbal agreements into verifiable contracts.
  • Domain libraries are laying skeletons: FlagOmni is still documentation and package structure on its second day since repo creation; FlagCV and FlagTrain have first wired the evaluation loop into optest, with no public release yet; the value of these libraries can only be assessed once the first batch of operators lands.
  • To watch: Whether the PR routing 316 P800-measured operators merges and opens Kunlunxin’s FlagGems path; whether results are announced after the competition ends on November 13; whether 2.3.0 ships as a unified release once the remaining backend lines are filled in.
