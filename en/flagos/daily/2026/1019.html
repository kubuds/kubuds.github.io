1.2 New Repo FlagCV: Multi-Backend Image Operator Library Skeleton Aligned with OpenCV Interfaces Merged (10-18 ~ 10-19)

Date: 2026-10-18 ~ 2026-10-19　Source: FlagCV · PR #1 · commit history

  • Facts: FlagCV, created on 10-14, landed its first commit “Add project skeleton and bitwise_and operator” at 10-18 23:14, followed by “Restructure as an immediate-mode skeleton without operators” at 10-19 01:24, and merged PR #1 (author zhangjieBaai) at 10-19 01:38. The PR description states three design orientations: interfaces aligned with OpenCV (five headers under include/flagcv/—core / imgproc / gpumat / handle / types—corresponding to opencv2’s core and imgproc), multi-backend structure following FlagDNN, and kernels written in Triton; this PR only lands the skeleton, with no operators.
  • Structure: Of the repo’s 81 paths, backends/ already lays out six backends at once—nvidia / thead / ascend / hygon / iluvatar / mthreads (each with CMakeLists, backend.cpp, compiler.py, and kernels/registry.json); src/ is split into five blocks: core, imgproc, image, lowering, runtime; compiler/flagcv_codegen is the code generation entry point; docs/ already has three documents: architecture, numerical-tolerance, operator-development.
  • Assessment: This is the first time the FlagOS operator map extends from “large models / scientific computing” to image processing—previously gaps of the FlagCV kind were shared between FlagDNN (deep learning operators) and vendors’ own CV libraries; now it stands as a separate repo with an OpenCV-compatible interface. The six backend directories being laid out at once rather than added one by one indicates the team intends to directly reuse the existing FlagDNN multi-backend paradigm; the numerical-tolerance document appearing before the operators also matches FlagOS’s established rhythm on the KernelGen line of “establish acceptance criteria first, then land operators in batches.” The risk is that the match between image processing operators (interpolation, color space, morphology) and Triton’s expressiveness has not yet been validated, and the repo has no runnable operators yet, so no conclusions should be drawn about its coverage in the short term.

1.3 build-infra: FlagCX Six-Backend 22.04 Self-Contained Builders Finalized; FlagTree Per-Backend Builders and Daily Wheel Matrix Take Shape (10-16 ~ 10-18)

Date: 2026-10-16 ~ 2026-10-18　Source: build-infra #1369 · #1371 · #1372 · #1380 · #1389 · #1394 · #1398 · #1399 · #1403 · #1404 · #1407

  • FlagCX line: Within 24 hours, one “22.04 self-contained builder” was landed for each of six backends—nvidia (#1372), hygon (#1380), cambricon 4.7.2 (#1389, with a companion pandas dependency fix #1391), metax (#1394), enflame (#1398), iluvatar (#1403); each builder uses ubuntu:22.04 as the glibc floor, pre-installs the vendor SDK into the image, builds the wheel on top of it, and leaves a trace in wheel-info (#1375 / #1395 / #1400). #1407 adds a dispatch-level --no-bitcode switch: the v0.14.0 tag predates FlagCX #668’s bindings/ir Makefile, so re-releasing iluvatar’s 0.14.0+corex4.4.0 / corex4.5.0 pins no longer produces device bitcode, avoiding setup.py throwing directly on non-nvidia adaptors.
  • FlagTree line: Builders are merged from “two workflows doing one thing” into a single matrix, with one line in backends.yaml carrying the Containerfile, image repo, runner label, disk budget, and acceptance assertions (#1369); daily wheels likewise become one line per backend, with plan computing version and filename line by line (#1371), metax joins the daily line (#1377), iluvatar joins the target and daily lines (#1390 / #1393), sunrise consolidates builder and wheel into a single file and enables the daily line (#1399 / #1402), and the ascend backend pair becomes a two-stage builder (#1404 / #1405, where the build environment is the delivery environment, reading CANN and pinning AscendNPU-IR accordingly). #1397 explicitly removes FlagCX from iluvatar’s FlagTree wheel, drawing the boundary between the two artifacts.
  • Packaging line: Wheel upload moves from the runner’s local python to execution inside the uploader image (#1381 / #1382 / #1388); release-type workflows accept pull/<N> as a ref (#1347), allowing PR branches to run the release chain first; FlagGems-sglang enters both the noarch deb/rpm and flaglibs wheel lines (#1387); bundle deep smoke tests switch to real-device device + compiler JIT/execution (#1365), and validation runs on the bundle’s glibc floor (22.04) (#1376).
  • Assessment: This batch is not scattered patching but a compression of “N backends × M artifact types” into “one matrix + one backends.yaml”—adding a backend goes from “writing another workflow” to “adding a line.” Unifying on 22.04 is the other side of the same logic: only by pinning the glibc floor of both build and delivery environments can cross-distro wheels be “one artifact installable in many places.” This directly corresponds to the “35 chips” mentioned in the main forum—the chip count must be supported by a reproducible delivery surface, otherwise scale is just a list.

  • KernelGen (NVIDIA) batch operator landing: Around 10-16 14:06 ~ 14:50 and 16:11, thirty-plus “[KernelGen][Nvidia] Add operator with Triton kernel” PRs were merged in a burst, covering convolution and transposed-convolution kernels, FFT, small linear-algebra decompositions (Cholesky, eigenvalues, inverse, tensor-solve), RNN / LSTM / GRU cells, and sparse or aliasing copy operators (coalesce, col_indices_copy, values_copy, diagflat, gradient, dense_dim, _dim_arange, _dimV); FlagGems-Experimental landed 3 more (dstack and a per-channel quantized-tensor factory).

  • Kunlunxin optimization wave: Twenty-plus PRs concentrated on the XPU backend—amax / mv / i0 / cauchy, euclidean_dist / normed_cumsum, batch_norm_backward / layer_norm_backward, masked_scatter / nonzero / addr / logit, foreach_copy / foreach_pow_list / foreach_tan, float_power_ / gather_backward / scatter_add_ / to_copy, tril_ / arange, le_scalar_ / one_hot / mhc_pre, index_select_backward; among these, #7213 rewrites cumsum’s row scan as a prefix-sum matrix multiply, and #7144 / #7218 add int16 dtype support and precision fixes.

The density of the twenty-plus Kunlunxin PRs deserves separate note: this is the most concentrated optimization investment by a single domestic backend within the three-day window.

1.5 FlagTree: SpaceMiT RISC-V Backend Adds smt_rvisa Raw-Kernel eDSL, Retires Private TLE Dialect (10-16)

Date: 2026-10-16　Source: FlagTree #1381 · #1394

  • Facts: #1381 (author alex-spacemit) updates the SpaceMiT RISC-V (K3) backend, doing three things at once—adding smt_rvisa, a raw-kernel eDSL where the author explicitly specifies SEW / VL / tiling / instruction selection rather than leaving it to the scheduler; kernels are lowered via a C++ builder API (no MLIR text generated), with an additional LLVM direct-output path that uses MLIR Python bindings to produce llvm.func directly and skips spine-opt entirely; the backend no longer keeps a private TLE dialect copy and instead consumes the common third_party/tle; it also fixes pointer / memory space lowering defects exposed by the raw path.
  • Companion changes: #1394 updates the Ascend CI py311 / py312 and ascend3.5 workflows; open #1395 ([SPEC][XPU] reuse core analysis and route TritonTypes.td) and #1396 (Ascend3.5 py312 delivery workflow) show that specification work continues on both the XPU and Ascend lines; #1387 skips the tle.gpu.alloc alias test on enflame.
  • Assessment: The RISC-V backend in FlagTree used to be “compiles and runs”; this issue marks the first appearance of a hand-written entry point targeting the vector unit—explicit control over SEW / VL means RVV vector length and tiling strategy can be written into the kernel rather than relying on automatic scheduling inference. Retiring the private TLE copy is a governance action: multiple backends sharing one TLE dialect prevents “one semantics per backend.” For RISC-V AI chips (the SpacemiT K3 line), this is a step from “can run models” toward “can squeeze performance.”

II. News Coverage and Ecosystem

2.1 Main Forum: Six Sets of Numbers and a Four-Layer Architecture for FlagOS 2.2 (10-18)

Date: 2026-10-18　Source: DOIT, “Lin Yonghua: Zhongzhi FlagOS 2.2 Released, the Token Economy Is Moving Toward Physical AI” · Conference agenda page

  • Scale figures: Covers 21 AI chip vendors and 35 chips; 9 major operator libraries totaling 1,454 operators (up 890 from the previous version); 27.6% cross-chip operator performance improvement (across 10 chips); 264 code contributors (+55% period-over-period). Community metrics also include: 730+ active contributors, 100+ member organizations, coverage of 30+ countries, and 55,800+ developers; from 2.1 to 2.2, merged PRs rose from 1,890 to 4,890, new issues from 420 to 1,423, and commits from 5,100 to 9,730. The report states that 2.2 was released on September 30; on the GitHub side, the 24 items on the 2.2 list were actually committed between 09-28 and 09-29 (see the 09-29 / 09-30 daily briefs). There is a two-day discrepancy between the public statement and the repository commit dates; the repository is authoritative.
  • Compilation and tuning: FlagTree covers 20 vendor backends in a single repository, adding NVIDIA TileIR, AMD, DAMO XuanTie, SpacemiT, Huixi, and ARM64 CPU backends, with the main branch upgraded to Triton 3.6; FlagOSTune speeds up the search for operators such as matrix multiplication by up to 298x. End-to-end measurements: on NVIDIA, DSV4-flash throughput +12.63% and first-token latency −20.22%; on Moore Threads S5000, Qwen3.6-35B-A3B reaches 82.29%–89.83% of H100-equivalent throughput, exceeding the vendor’s native implementation by 4%–19%. Within the overall +27.6% cross-chip gain, Kunlunxin P800 speedup rose 191.2% and Ascend 910B rose 160.7%.
  • Toolchain: Newly released FlagPrism (cross-chip debugging and performance analysis, able to localize numerical deviations to the statement level; already supports Ascend, Tianshu Zhixin, Moore Threads, NVIDIA, and Enflame); a unified plugin system changes the “N×M” combination into an “N+M” decoupling, covering inference (vLLM / SGLang), training (Megatron-LM / TransformerEngine), reinforcement learning (VeRL), and base frameworks (Torch-FL); FlagOS-Compressor provides unified cross-chip quantization for the first time — after W8A8 on a 397B MoE, size is reduced by 49.1% while GPQA-Diamond remains at 84.85%, validated on H20 and domestic PPUs; Day0 capability achieves adaptation of a new model to up to 12 chips within one day, with simultaneous distribution to HuggingFace, ModelScope, Tencent Cloud, Huanxin Community, and the National Supercomputing Internet.
  • Token and model cases: DeepSeek V4.1 Flash inference performance on H100 improves 18%–20%, with total throughput of about 9,190 tok/s at 64-way concurrency; DAMO XuanTie 810E improves 77%–82% and achieves usable 16-way concurrency; FP4 index scoring speeds up 2.75x on average, and FP8 Dense GEMM 1.41x. GLM-5.3-Flash on Ascend 910B improves throughput 2.04x, reduces cold TTFT for long context by 8.1% and ITL at full load by 16.6%, reaching 99.7% of the official API’s performance with 19.4%–27.6% better cost-effectiveness.
  • Embodied AI, edge, and internationalization: On the embodied side, VLM speeds up about 2.3x (MFU 33%), Tx2V about 1.9x (MFU 36%), Action about 2.0x (MFU 35%), and training MFU 33%–36%, versus 23% for Cosmos3-Nano and 30% for Cosmos3-Super; on the edge, MiniCPM5-2B runs on an Arm CPU using only the CPU, with prefill at 1,135 tokens/s and generation at 90 tokens/s; after coordination between FlagTree-CPU and SME2 / NEON I8MM, full-model Prefill improves a further 21%–25%, and on Mac M5 Pro, Xing4.0 29B-A4B improves 252.09% over native vLLM; internationally, the UN “Open Computing Working Group” was approved on 9-28, with 300+ global institutions registering within two weeks, and the first meeting planned to be held during the November APEC summit.
  • Assessment: The value of these figures lies not in any single number but in breaking “scale” into four verifiable layers — chip count (35), operator count (1,454), performance gain (+27.6%, with a breakdown across 10 chips), and contributor count (264). Compared with the “how many chips are supported” framing of the 2.1 era, the 2.2 narrative has shifted to “whether shared optimizations on the same set of chips can accumulate”; the two new tools, FlagPrism and FlagOS-Compressor, are precisely the tooling expression of that statement.

2.2 Quantum-AI Cloud Launched: FlagOS Execution Stack Underpins FlagQuantum (10-18)

Date: 2026-10-18　Source: DOIT main forum report (Quantum-AI Cloud section) · Official agenda (Quantum-AI Cloud platform launch, 10:05–10:15) · FlagQuantum v0.3.0

  • Facts: On the morning of 10-18, the Quantum-AI Integration sub-forum included a “Quantum-AI Cloud platform launch” session (agenda 10:05–10:15). According to the main forum report, Quantum-AI Cloud was jointly launched by the Beijing Academy of Artificial Intelligence (BAAI) and the Beijing Academy of Quantum Information Sciences (BAQIS), using the FlagOS Execution Stack to support the FlagQuantum quantum framework, interfacing with the “Jiuding” AI computing system and the “QUAFU” quantum computer to enable hybrid quantum-classical job scheduling.
  • Code-side corroboration: The FlagQuantum v0.3.0 release notes (10-16) already state that “Jiuding and Quafu tasks are resumable (opt-in receipts)” and “Quafu multi-circuit results preserve order,” while v0.3.1 adds local research capability services and versioned evidence bundles — indicating that at the time of the Quantum-AI Cloud launch, the quantum-side task submission, receipt, and result-ordering pipeline already existed in the package, rather than only framework-level interfaces.
  • Assessment: This is the first cloud-service-form product of FlagOS extending from “AI training and inference” to “quantum-classical hybrid.” A boundary worth noting: the v0.3.0 / 0.3.1 notes explicitly state that it does not run on quantum hardware and does not include an MCP server or agent runtime; hardware execution is handled on the Jiuding and QUAFU side — the division of labor is “FlagOS handles scheduling and the execution stack, the quantum institute handles hardware and cloud.” Follow-up points to watch are when Quantum-AI Cloud will open externally, and whether FlagQuantum’s multi-chip backends (Hygon / Moore Threads) will be incorporated into cloud scheduling.

IV. Summary and Trend Observations

  • Narrative and engineering aligned for the first time: The main forum framed 2.2 as “large-scale shared optimization” (21 vendors, 35 chips, 1,454 operators, +27.6%, 264 contributors), while the single heaviest item on the GitHub side in the same window happened to be build-infra’s six-backend 22.04 builder and per-backend daily wheel matrix—both answer the same question: the chip roster must be backed by a reproducible delivery surface. This is the most noteworthy correspondence of this issue.
  • The operator domain is expanding, but the direction of expansion needs to be seen clearly: KernelGen landed thirty-plus NVIDIA operators over three days, mostly boundary operators such as _dim_arange, values_copy, and _has_same_storage_numel, indicating that trunk coverage is nearing completion and work has moved into cleanup of alias and view semantics; meanwhile, incremental work on domestic backends remains concentrated on Kunlunxin (twenty-plus optimizations) and DAMO XuanTie (GEMM completion), and the coverage gap between backends has not narrowed. The establishment of the FlagCV repo is expansion in another direction—from LLMs and scientific computing toward OpenCV-style image processing, with six backend directories laid out at once, but the repo has no runnable operators yet, so it should not be overestimated in the short term.
  • The quantum line has taken on product form: The dual release of FlagQuantum 0.3.0 / 0.3.1 plus the external launch of Liangzhi Cloud write engineering capabilities such as “resumable Jiuding / QUAFU tasks” into the release notes, while explicitly stating that it does not run on hardware and contains no agent runtime. The division of labor is “FlagOS does the execution stack and scheduling, the quantum institute does hardware and cloud”—this explains the boundary better than the vague slogan of “quantum-intelligence integration.”
  • On the RISC-V side, the action is deep in the compiler: SpaceMiT’s smt_rvisa lets authors explicitly control SEW / VL / instruction selection and retires the private TLE copy—such changes appear in no external messaging, yet they determine whether the RVV backend can move from “it runs” to “it can push performance.”
  • To watch: First, per-session notes from the conference’s sub-forums and workshops have not yet been published; beyond the main forum, technical and tactical content (unified IR, Token Factory, edge deployment) currently exists only as agenda framing. Second, when Liangzhi Cloud will open externally. Third, when FlagCV will land its first runnable operator. Fourth, the training side (Megatron-LM-FL / TransformerEngine-FL / FlagScale) had zero pushes over three days—whether this is normal silence around the conference or the starting point of the 2.3 cycle needs confirmation in the next issue.
