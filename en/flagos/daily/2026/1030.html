Together, the two repos mean reference implementations can run directly as candidates without external candidate files — tests are no longer a “does the operator exist” switch but a comparison of “does the implementation match the reference.”
  • Takeaway: All three tracks point to the same thing — the software stack’s bottleneck is shifting from “writing the operators” to codifying three kinds of engineering discipline: the build assumptions of a new SDK, the execution path of reference implementations, and the cross-chip comparability of models. The eight DTK 26.10 merges show that the cost of a hardware generation switch falls almost entirely on packaging and dependency resolution rather than the kernels themselves; meanwhile, the MiniCPM-OCR benchmarks provide, for the first time, two sets of comparable numbers: normalized throughput and on-device latency.

1.4 Test infrastructure: ref-as-candidate lands in two repos; 57 test PRs closed in a single day (10-29)

Date: 2026-10-29　Sources: FlagGems PR #7630 · FlagGems-sglang PR #239 · FlagGems-sglang PR #241 · FlagGems-sglang PR #249 · FlagGems-sglang PR #242

  • Mechanism: --ref-as-candidate lets correctness tests and benchmarks run an explicitly declared reference implementation as the candidate (get_candidate("negative", reference=torch.negative)), no longer relying on external candidate files. A missing reference, a non-callable reference, or a test body that never actually calls the candidate all fail explicitly; skips and xfails cannot mask contract errors, and an all-skipped run does not count as a valid execution. Validation comprised 26 host regressions plus 32 checks against master and the PR merge preview.
  • Rollout: FlagGems-sglang merged 11 PRs the same day, moving all correctness suites to get_candidate (#241), completing reference declarations (#240, #244), adding benchmark case enumeration and replay (#239), adding a definitions directory with a silu_and_mul example (#245), and adding mrotary_embedding candidate comparison with a portable reference and cross-device native validation (#247, #249).
  • Scale: 57 test fixes by a single author merged in one day (mostly reference contracts, fixtures, and benchmark entry-point corrections across backends), covering skip conditions and reference ABIs for Ascend, MetaX (MUSA), Enflame, Kunlunxin, and Nvidia.
  • Automation: Added a daily automatic master to kernelgen-dev sync PR (#242); the bot has already produced two syncs that day (#243, #246). This chain turns drift between “upstream trunk” and the “KernelGen development line” from manual rebases into a once-daily auditable merge.
  • Assessment: Once tests shifted from “passing” to “comparable,” the tests themselves began to need reference-implementation contracts; that is the real content of the day’s 57 fixes—not adding tests, but adding references.

This is not a port of old files but a re-migration based on the current main’s pipe, warp specialize, and SQMMA representations, merging the previously separate compilers (the common version for addmm/baddbmm, the SPMC version for bmm) into one superset: supporting stage and phase advancement in dynamic loops, one producer to many consumers, named and implicit reads, segmented completion with consumer epoch derivation, and single-issue, fused-consumer, and 16-warp persistent paths.

Previously load(..., Acquire) and load(..., Relaxed) emitted the same instruction, leaving observers without a fence after seeing a flag; this PR changes it to read-then-fence, selecting strength by scope, and adds the address-space symbol for launchKernel and the getLastError slot. 2.1 MiniCPM-OCR Dual Models Day0-Adapted to 12 Platforms; DAMO XuanTie Reaches 98.7% of Native Throughput (10-29)

Date: 2026-10-29　Source: FlagOS Day0 Adaptation for MiniCPM-OCR & Jev · FlagRelease Model Card Entry · vllm-plugin-FL Documentation · Torch-FL Documentation

  • Models: ModelBest, in collaboration with OpenBMB, has open-sourced the MiniCPM-OCR series. The 2B MiniCPM-OCR Jev acts as an “AI quality inspector,” scoring the reliability of parsing results and able to connect to different OCR models; it achieves an overall AUROC of 0.936 on JevOCRBench, close to Qwen3.5-397B-A17B’s 0.938.
  • Platforms and paths: Coverage spans 12 platforms: DAMO XuanTie, NVIDIA, Huawei Ascend, Hygon, Kunlunxin, MetaX, Moore Threads, Tsingmicro, Tianshu Zhixin, Enflame, Mac (ARM), and ESWIN. Version baseline: vLLM v0.24.0, vllm-plugin-FL v0.3.0, FlagGems v5.4.0.
  • Performance basis: On NVIDIA, Jev runs Torch-FL + FlagGems + FlagTree; with 12 samples, batch 1, and single-card BF16, average discrimination is 76.2 ms versus 62.7 ms native, giving actual compute throughput at 82.3% of native. On DAMO XuanTie, the average is 63.56 ms, with throughput reaching 98.7% of NVIDIA H100 native. OCR 1.0 on DAMO XuanTie runs vLLM-plugin-FL + FlagGems + FlagTree; both sides use single-card BF16 (peak compute taken as 989 TFLOPS and 123 TFLOPS), and after peak-normalization, single-document P50 throughput is 169.3% of native and 137.1% in batch scenarios.
  • On-device: The ARM side covers Mac and ESWIN. Jev uses only the M5 CPU; across 12 samples, average per-page-block discrimination is 1.2 s with a median of 895 ms, excluding prior full-page OCR parsing. The implementation retains BF16 weights and the discrimination head, uses SME2 matrix instructions to accelerate the main linear layers, and hooks into the operator execution path via Triton TLE Raw.
  • Observation: This is the first recent adaptation note to present “cross-chip throughput” and “on-device latency” under a single consistent basis—98.7% is an actual throughput ratio, while 169.3% is a ratio normalized by peak compute; the two are not interchangeable. The article also honestly states that the 169.3% figure holds on the premise that lower-peak-compute platforms achieve higher utilization, not that a single card is faster.

IV. Summary and Trend Observations

  • The cost of hardware generational switching is concentrated on the build side: none of the eight merged DTK 26.10 changes touched the kernel; all were container paths, interpreter versions, runner overrides, and soname dependencies. Python 3.12 and torch 2.13.0+dtk2610 invalidated the entire existing cp310 builder, and between 26.04 and 26.10, libmpi and libibverbs shifted from “hashed into the wheel” to “linked at runtime”—changes of this kind can only be discovered through node-by-node testing.
  • The Day0 model narrative shifts toward comparable numbers: the MiniCPM-OCR adaptation notes give the actual throughput ratio (98.7%), the throughput ratio normalized to peak (169.3%), and edge-side latency (1.2 seconds on M5, median 895 ms), each with its stated preconditions. This is the first recent material from this stack to state “catching up to native” and “higher utilization” separately, which is more informative than a single multiplier.
  • Test infrastructure becomes an independent mainline: ref-as-candidate landed in both the FlagGems and FlagGems-sglang repos, paired with 57 test fixes the same day and the daily automated sync of kernelgen-dev; testing has shifted from “is the operator there” to “do the reference and the implementation agree.” The output of this line does not show up in operator counts, but it determines the credibility of all subsequent backend alignment.
  • The quantum line is self-contained: 60 commits in one day on FlagQuantum systematically archived the circuit synthesis specifications and delivery documents for CS-01 through CS-07, while FlagQAI built the local workbench in parallel. It is unrelated to multi-chip adaptation and is the only software-stack mainline in the 2.x cycle that is decoupled from hardware.
  • Three points to watch: first, the release/2.3 manifest in the community repo has not yet been established while the build side is already accounting against 2.3.0—will the release notes be filled in; second, neither FlagCX v0.14.1 nor FlagTree’s vendor-split 3.6 tags have Release bodies, so downstream can only infer content from tag names; third, Megatron-LM-FL’s DeepSeek-V4 upstream sync has opened [1/N] and [2/N]—will this training stack, stalled for two weeks, truly resume pushing.
