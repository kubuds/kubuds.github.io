Today’s Focus: SpacemiT Open-Sources RVISA Virtual ISA Specification Working Draft, First Round Adds IME/VME/AME Mapping Sets and Blocked MMA (repo created 11-04, commits 11-05)

SpacemiT has opened a new repository on GitHub, spacemit-com/rvisa, proposing RVISA (RISC-V Virtual ISA), which defines a virtual instruction notation layer for RISC-V scalar, vector, and matrix computation. The repository was created on November 4, and three substantive commits landed in a single day on November 5: first the MkDocs documentation site and Pages publishing workflow, then example source forms of the RVISA notation and the first batch of IME/VME/AME mappings, and finally PR #2 defining programmer-expressible tile layouts and blocked matrix multiply (blocked MMA). The current specification version is 0.2.0.

RVISA’s positioning is stated fairly clearly: it deliberately sits above NVIDIA PTX and below cuTile. Upward, it is not bound to any front-end language, and source-language front-end implementations are explicitly excluded from this version’s scope; downward, it does not directly specify any chip’s instruction encoding, but instead makes “target mappings” into versioned profiles that declare, item by item, which register classes, register groups, and instruction sequences they map to, along with the corresponding upstream revision number and validation evidence for that profile. The notation form follows the RVV Intrinsics approach to express typed operations, operand roles, and register-group constraints; tiles range from one-dimensional to N-dimensional, reshape and axis permutation must preserve element positions, and layouts are derived from linear layouts.

What best illustrates the problem it aims to solve is the “expressibility requirement”: any optimization of an RVISA tile computation must be writable by the programmer at the notation level. This constraint targets precisely the most common failure mode when matrix extensions land—the compiler quietly does its own vectorization, the programmer can neither see nor change it, and switching to another chip means rewriting everything. RVISA attempts to make this layer explicit, so that the same notation runs different mapping profiles on different implementations while semantics stay consistent.

Maturity needs to be stated clearly: the specification status file itself says this is a working draft, not an approved RISC-V International specification. The core model, type and operand rules, tile layouts and optimization, and key operation signatures already give concrete contracts, but the target mapping profiles are registered only as drafts, with no implementation-consistency evidence yet established; the MLIR dialect is marked TBD; the reference payload consists only of source forms in .rvisa notation and cannot be compiled or executed; and the executable conformance tooling is likewise TBD. The repository also contains three draft RFCs, 0001 through 0003, covering the instruction and register mapping contract, the core type and operation contract, and programmer-expressible tile layouts, respectively.

Placed in today’s industry coordinates, this is two expressions of the same logic as what Quintauris is doing on the MCU side in the same batch: the fragmentation brought by open instruction sets must ultimately be converged by some stable “software target” layer. On the MCU side, convergence happens on binary compatibility and interrupt semantics; on the AI matrix side, it happens on virtual notation and mapping contracts. The difference is that EM-Altair is backed by a joint venture of six major automotive and embedded vendors, whereas RVISA is currently a working draft led by a single vendor—whether it is picked up by upstream matrix-extension discussions will depend on whether anyone subsequently fills in implementation evidence for the IME, VME, and AME lines in that mapping table.

Today’s Focus: Quintauris Releases EM-Altair, an MCU-Class RISC-V Standardized Platform with RV32IM as the Baseline for Binary Compatibility (released 11-03, reported 11-05)

On November 3, Quintauris released EM-Altair, which it describes as a standardized embedded platform for microcontroller-class RISC-V systems. It does not define new cores; instead, it defines a set of hardware, firmware, and runtime requirements that “compliant implementations must behave consistently against”: four layers covering the ISA profile, privileged architecture, boot and runtime services, and security services. Vendors can implement their own microarchitectures, but software faces the same target. Chief Product Officer Angel Berrio Moreno put it as “the same binary, the same interrupt behavior, the same security assumptions.”

In concrete terms, EM-Altair uses RV32IM as its baseline, paired with a clearly bounded set of mandatory and optional extensions, fixing interrupt, atomic operation, CSR behavior, and memory ordering rather than leaving them a moving target. The interrupt portion specifies a bounded, high-throughput architecture aimed at hard real-time workloads; isolation uses PMP covering machine mode and optional user mode to separate trusted from untrusted code; security practices align with ASIL-B equivalent requirements and reserve security hooks for firmware integrity and device protection. The target scenarios are stated plainly: body electronics, zonal and cockpit controllers, EV energy management, as well as industrial control loops, IoT sensor nodes, and wearables.

The accompanying tool is QNTAF, Quintauris’s own verification and certification framework. Per the official description, vendors can run benchmark, conformance, and security test suites on three target types—cloud, simulator, and FPGA—wire these tests into CI/CD, and generate the traceable artifacts required for certification. The specification and tools are open to SoC vendors, RTOS developers, and OEMs. Quintauris was founded in 2023 as a joint venture by Bosch, Infineon, Nordic, NXP, Qualcomm, and STMicroelectronics, and does three things: profiles, reference architectures, and software components.

This news is worth reading alongside Infineon’s November 4 release of AURIX RC1. Infineon is a founding member of Quintauris, and AURIX RC1 merges the AURIX and TRAVEO T2G product lines onto a single RISC-V base, while EM-Altair provides precisely the common execution environment on top of that base—chipmakers do the implementation, the joint venture does conformance, and RTOSes and compilers need only adapt once to a single target. For domestic teams working on automotive-grade and industrial RISC-V, this means two things are happening at once: the barrier to foundational software is falling (AUTOSAR, RTOS, and toolchains no longer need to be rebuilt by each vendor), while the barrier to entry is rising (customers will ask “does it comply with a given profile?”).

P4 Launcher Delivers a PC-Like Experience for Loadable Apps on ESP32-P4, with 21 PAPP Apps (11-05)

Developer Gil Tal has released P4 Launcher, an open-source application platform for ESP32-P4 development boards with touchscreens. It boots directly into its own interface; apps are stored as .papp files on a microSD card and loaded into PSRAM at startup, so adding or removing apps only requires copying files to the card—no need to reflash firmware or reboot the device. There are currently 21 PAPP apps, mostly emulators and games: Neo Geo and Atari 2600 emulators, Doom, Quake, Duke Nukem 3D, OpenTyrian, plus a clock and a file manager.

In implementation, the interface is based on LVGL, with a compositor responsible for scaling the UI to different resolutions; the audio engine supports up to 8 channels at 4 to 192 kHz; up to four input devices can be connected for multiplayer gaming, with support for PS3 and Nintendo controllers; firmware can be updated from the microSD card or GitHub, and a new version that fails to boot automatically rolls back. The project also provides an SDK for developers to write their own PAPP apps, along with two compatibility layers: one reimplements the odroid_* interfaces, and the other implements the old PAPP v1 service table—the latter is precisely why old code like Doom and Quake can run on the original glue layer. The code is based on ESP-IDF v5.5.2 and has been adapted for Guition’s 4.3-inch and 7-inch boards as well as the M5Stack Tab5.

The value of such a project is not “it can play games,” but that it has made the whole set of conventions for app packaging, loading, updating, and rollback work on an MCU. The ESP32-P4 is Espressif’s high-performance RISC-V model (dual-core HP plus an LP core), and PSRAM bandwidth, display, and audio subsystems are exactly the pressure points for this kind of workload; a mature application-container convention says more about platform usability than running one more emulator.

Cercis M100 Selected as a “China Chip” RISC-V Ecosystem Promotion Demonstration Case, Putting a Separate Price on the Ecosystem Ledger for Automotive-Grade MCUs (11-05)

Changsha Evening News reported on November 5 that the results of the 21st “China Chip” outstanding product solicitation for 2026 have been announced, and the Cercis M100 automotive-grade RISC-V MCU, independently developed by Hunan Cercis Semiconductor, was selected as a “RISC-V Ecosystem Promotion Demonstration Case.” The solicitation is guided by the Ministry of Industry and Information Technology and hosted by the China Center for Information Industry Development; the newly established “RISC-V Ecosystem Promotion Demonstration Case” category focuses on selecting projects with demonstration value in technology implementation, ecosystem adaptation, upstream-downstream joint promotion, and large-scale adoption.

The Cercis M100 is built on a foundation laid by a team incubated at Great Wall Motor’s Technology Center: it is China’s first automotive-grade MCU designed on an open-source RISC-V core, entered mass production and vehicle deployment on December 18, 2025, and is mainly used in body control scenarios such as combination headlights, ambient lighting, and combination switches; as of October 9 this year, cumulative shipments have exceeded 10 million units. The company says it has developed more than 15 core IPs in-house, possesses a complete MCAL, low-level driver SDK, real-time operating system, and development/debugging environment, and has passed ISO 26262 ASIL-D process certification, ASIL-B product certification, ASPICE, and AEC-Q100. Its product line has expanded to the M100/M200/M300 and companion power driver chips; the M200 is planned for tape-out in Q4 this year (40nm process), targeting combination instrument clusters, T-BOX, gateways, BCM, and more; and the E100 cerebellum control chip for embodied intelligence is in development.

The highlight here is not the chip’s specifications but the award criteria: making “ecosystem promotion” a separate award category means the review process has begun to price “upstream-downstream joint adaptation and large-scale adoption,” rather than comparing only performance and process. For a domestic automotive-grade RISC-V team that only entered vehicle deployment at the end of 2025 and only passed 10 million units this October, the sample value of this path outweighs the award itself.

India’s MeitY Sets a 24-Month Target for Homegrown GPUs and Pushes Commercialization of the SHAKTI and VEGA RISC-V CPUs (Reported 11-05)

On November 5, Tom’s Hardware cited an ETGovernment interview (published November 4) with S. Krishnan, Secretary of India’s Ministry of Electronics and Information Technology (MeitY): under the “India Semiconductor Mission 2.0” framework, India plans to produce a homegrown GPU chip in about 24 months. The mission was approved by the cabinet in July 2026, with a scale of about $15 billion and a 12-year duration. Krishnan divides the AI hardware ecosystem into five layers—energy, accelerator chips, computing infrastructure and servers, AI models, and applications—and says Indian companies VVDN, Kaynes, and Avalon are already manufacturing servers, while the Centre for Development of Advanced Computing (C-DAC)’s in-house Rudra server series has been licensed by the government to local manufacturers.

The need for restraint is also clear: the GPU goal has not disclosed manufacturing partners, chip suppliers, or architecture licensing details, and is a policy declaration and roadmap; the verifiable part is the commercialization path of SHAKTI and VEGA, and their existing products (100MHz-class 32-bit MCUs) are still far from “AI acceleration.” India’s semiconductor market is currently about $50 billion, with official expectations of approaching $100 billion by 2030.

IV. Embodied Intelligence and Robotics Special Chapter

SpacemiT manipulation component: device exclusivity, arrival detection, timeouts, and fault locking folded into the device session (11-05)

manipulation is the robotic arm control component in the SpacemiT robotics SDK, and what it does is “unified control of robotic arms and end effectors”: select hardware via device configuration, issue actions through the same set of commands or C++/Python interfaces, and provide kinematics, hand-eye calibration, and device utilities. It currently ships with three drivers: the software-simulated mock_device; agx_nero_revo2, corresponding to the AgileX Nero seven-axis with an optional Revo2 right hand (Revo2 has no position feedback); and so101, five-axis with an optional stock gripper, plus a servo calibration tool.

Its architectural trade-offs are stated very explicitly. C++ applications link the component library directly and use DeviceSession in-process; command-line and Python applications go through DeviceClient, which launches the local process manipulation-device serve and issues requests over JSONL; YAML waypoint tasks are executed by manipulation-device run. The device session uniformly handles device exclusivity, arrival detection, cancellation, timeouts, and fault locking. The driver layer is responsible only for model protocols and unit conversion; kinematics and hand-eye calibration take models from device.yaml and descriptions/, with no hardcoded models; to add a new device, implement Arm and EndEffector and register them.

Most worth noting is that passage: “the component does not auto-enable, does not auto-clear errors, does not auto-home, does not auto-retry.” In embodied intelligence projects, the easiest place to cut corners is letting middleware make decisions for people—and once these four things are done automatically, on-site personnel lose the basis for judgment when problems arise. Putting the safety boundary at the session layer rather than the driver layer is the restraint that robotics middleware ought to have.

dice_arena runs the full dice-game pipeline with K3 plus Nero seven-axis plus Revo2 dexterous hand (11-05)

dice_arena is a comprehensive demo on the same SDK: visual cup grasping, cup shaking and placing, hand-eye calibration, dice recognition, voice announcements, and a web game. The hardware list is written concretely—a SpacemiT K3 development board as the main controller, an AgileX Nero seven-axis robotic arm connected via a USB-CAN adapter (SocketCAN, 1Mbps), a Revo2 right-hand dexterous hand mounted at the end effector (six control channels, sharing the controller connection with the arm), an Intel RealSense D435i for cup grasping and calibration, a top-down USB camera for dice recognition (Logitech C920 by default, MJPEG), plus a ChArUco calibration board, a speaker, and green cups.

On the software side, dice-arena serve starts video forwarding, local voice, and the game backend; the backend runs a state machine (rule explanation, cup grasping, cup shaking, cup placing, visual judgment, result gesture, return to HOME), invoking each component by slot; cup grasping is handled by CupApplication, which recognizes the cup body from RealSense images, solves the inverse kinematics, and checks the path, with actions issued via manipulation’s DeviceClient; recognition is performed by vision_yolov8_objdetect inferring on the SpacemiT EP, with the feed pushed to MediaMTX over RTSP and played in the browser via WebRTC; voice is synthesized by tts_moss_nano calling the local MOSS-TTS and played through PipeWire on the board.

What is truly valuable is the failure handling: the task policy library libcup_task.so checks stage ordering via a C ABI; once an action is issued, a failure locks it, and states requiring manual intervention are written to task_state.json; after a program restart it still refuses to move until on-site personnel have dealt with it and run dice-arena reset. The thing most easily omitted in embodied intelligence demos is exactly this state machine—and it is precisely the part that can least be omitted in mass production.

V. Summary and Trend Observations

There are two main threads today—one about abstraction layers, one about standardization—converging on the same question.

SpacemiT’s RVISA provides a layer of virtual instruction notation on the AI matrix side, writing “the optimizations a programmer can express” as hard constraints, then mapping them to the three still-in-progress matrix extensions IME, VME, and AME via versioned mapping profiles; Quintauris’s EM-Altair provides a binary-compatible execution environment on the MCU side, fixing interrupts, atomics, CSRs, and memory ordering into a set of behaviors that a compliant implementation must follow. Both are answering who should converge the fragmentation brought by open instruction sets: rather than letting chip vendors each interpret the spec their own way, insert a stable software target between spec and implementation. The difference lies in governance structure—one is a joint venture of six major vendors, the other a working draft from a single vendor.

The focus of domestic vendors’ moves continues to shift from “chips and boards” toward “components and specs.” In a single day SpacemiT advanced the RVISA spec, three robotics SDK repositories, and the K3 robotic arm manual; Sophgo provided end-to-end stress-test numbers for 2-core and 3-core rather than peak compute; Zijing turned “ecosystem promotion” into a case that can be submitted for recognition. What these three have in common is that they are all filling in the “can others actually use it” side, rather than shipping another chip with higher specs.

Automotive-grade remains the biggest battleground, and today shows three layers advancing simultaneously: the chip layer (Infineon AURIX RC1, 11-04), the platform spec layer (Quintauris EM-Altair), and the ecosystem case layer (Zijing M100 selected as a China Chip demonstration case). These three layers are not in competition but are different positions along the same industry chain doing the same thing—turning open instruction sets into deliverable automotive-grade products.

On the benchmarking side, the pattern continues of “solidifying the measurement method first.” Five of GEM5’s six commits today are infrastructure such as checkpoints, traces, PMUs, and weekly performance tasks; riscv100.top’s comparison view yesterday and today’s leaderboard rollback are the same kind of phenomenon: the leaderboard is still in a settling period, and the comparability of the numbers deserves more attention than the numbers themselves.
