Today’s Focus: Qwenputer compiles an RV32IM CPU into Qwen3.5 weights, using GDN state as RAM (10-28)

Developer Divyansh Agrawal has released Qwenputer: an untrained Qwen3.5-4B that compiles a 32-bit RISC-V CPU directly into the model weights and uses the model’s own Gated DeltaNet layer state as memory. Within the window it was picked up by Adafruit, Startup Fortune, and several other outlets, and sparked discussion on Hacker News.

The technical path has three steps. The first step turns GDN into precisely addressable RAM: set the gate to 1, set the write strength beta to 1, and encode keys with one-hot vectors, so each write overwrites exactly one row and each query reads exactly one value; the GDN head thus becomes row-addressable storage whose state size does not grow with context. The second step compiles the CPU into layers: with no training, a compiler maps steps such as “read register / add / conditional jump” one by one onto attention heads (table lookup), feed-forward layers (arithmetic), and DeltaNet heads (RAM), with the CPU occupying the 11 layers before Qwen’s 32 layers. The third step runs execution out during decoding: each instruction corresponds to a few generated tokens (ADDR specifies the write row, VAL carries the value, STEP ends the instruction), and these tokens are themselves the execution trace.

The core is RV32IM plus the Zba extension, along with a small big-number unit. The official claim is that it passes riscv-tests, that program results match qemu, and that it free-runs (i.e., advances entirely on its own output with no reference machine correcting it mid-way) for 18 million instructions with not a single error; about 230,000 output positions were compared against reference-machine replay with zero mismatches. It can run C and MicroPython, but requires a small driver, RvChat, to load firmware and keep trace tokens out of the Qwen layers, so for now it cannot be run directly via an ordinary generate call. On performance, each instruction costs several decoding tokens, and the benchmark batched executor runs at about 3,200 CPU tokens/second on an L4.

On results, on the DeepMind arithmetic set div_big scores 97.5% (Qwen with a Python tool: 95%; base model: 72.5%), mul_big 97.5% (tool: 100%; base: 55%), mul_div_multiple_longer 100% (tool: 97.5%; base: 90%), and add_or_sub_big 97.5% (tool: 97.5%; base: 87.5%); on NUPA long-integer arithmetic it rises from 48.6% to 100%. An experimental file system was also built alongside it (1,024-slot directory, up to 512 files, roughly 53,000 tokens of text), which persists across sessions once written to GDN state. The cost is an 18.8 GB checkpoint (about twice the base model, mostly zero padding).

  • Observation: This is not industry news and should not be read as a product announcement. It is worth including because it demonstrates two things related to RISC-V: first, any deterministic ISA can be compiled into weights — the barrier to an ISA has never been instruction encoding but the software stack and ecosystem; second, the model’s internal addressable state can serve as a deterministic execution environment, which is a ready-made testbed for safety research such as “compiling monitoring capability into the weights so the model itself cannot tamper with it.” The flip side must be seen just as clearly: 18.8 GB of weights, several tokens per instruction, and the need for a dedicated driver mean it is destined to be a research apparatus rather than a chip replacement — teams actually building RISC-V chips need not adjust their roadmaps because of it.

I. Open-Source Community and Software Ecosystem

1.1 XiangShan difftest supports remote XDMA board relay, enabling cross-machine scheduling for FPGA verification

Date: 2026-10-28　Source: GitHub: OpenXiangShan/difftest commit history

Three commits landed in the difftest window, the core one being feat(fpga): support a remote XDMA board relay (#1011): the link between the DUT on FPGA and the reference model is reworked to be relayed through a remote XDMA board, so the verification machine and the board no longer need to be co-located on the same host. Two companion commits: fix(fpga): let fork REF finish after the final endpoint (#1010), which corrects the timing under which the reference model wraps up after the final endpoint in fork scenarios; and fix(mma): accept zero-sized reference operations (#1012), which lets the matrix extension path tolerate zero-length reference operations so that no-ops are not rejected as errors.

  • Observation: Taken together, these three commits show difftest evolving from a “single-machine comparator” into a “remotely schedulable verification service.” The remote relay addresses resource utilization—a single FPGA verification setup often sits idle in a queue, and once the link can cross machines, multiple users and tasks can time-share it. For teams building RISC-V cores, verification machine time is usually scarcer than design manpower, making this kind of change more practical than yet another performance optimization.

1.4 CORE-V CVW fixes CBO cache management: uncached cbo.zero stalls through final beat and PBMT alias dispatch

Date: 2026-10-28　Source: GitHub: openhwfoundation/cvw commit history

The CORE-V CVW repo merged two cache block operation (CBO) fixes: Stall an uncached cbo.zero through its final beat makes cbo.zero in uncached regions stall all the way to the final beat, preventing the pipeline from being released before the write response completes; Send cbo.clean/flush/inval to the D$ through PBMT=NC/IO aliases ensures these three operations still reach the data cache correctly when the page table entry is marked as non-cacheable or an IO alias. The two were merged via PR #2010 and #2008.

  • Observation: CBO is among the most easily overlooked instruction groups in RVA23—it does not show up on performance leaderboards like vector extensions do, but the final-beat timing in uncached regions and PBMT alias handling are exactly the spots that “never trigger in normal operation, and corrupt data when they do.” This is precisely where projects like CORE-V, which test spec boundaries one by one, earn their value.

At the ~$150 price point, it is affordable enough for both the amateur radio community and the vocational education market.

2.2 Microchip PIC64-HPSC Releases Early Radiation Results: TID 200 krad(Si), SEL 78.2 MeV·cm²/mg

Date: 2026-10-28 (announced 10-27)　Source: Microchip: PIC64-HPSC program milestone press release, Hacker News discussion: PIC64GX 64-bit RISC-V quad-core microprocessor

Microchip announced early program milestones for the PIC64-HPSC high-performance spaceflight computing series. Early radiation characterization of the radiation-hardened PIC64-HPSC1000-RH shows a total ionizing dose (TID) of 200 krad(Si), with single-event latchup (SEL) tested to 78.2 MeV·cm²/mg under specified operating conditions; in single-event effect characterization, the system controller exhibited no uncorrectable errors and required no external reset. Meanwhile, the early access program has delivered silicon and development kits to customers, and board partners are developing VPX and VNX+ compute modules based on the platform. The series originated from NASA and JPL’s assessment of future spaceflight computing needs, with the HPSC contract awarded to Microchip in 2022; NASA’s FY26 Civil Space Shortfall priority list ranks “advanced in-orbit computing for spaceflight operations” as the third-ranked technology shortfall.

  • Observation: Space is one of the few markets for RISC-V where demand is real, the metrics are hard, and substitutes are not accepted. The 200 krad(Si) tier means mission coverage can extend from LEO to beyond the Moon, and SEL and SEE data are the entry ticket for space-grade selection—without measured radiation data, no matter how open the architecture, it will not make it into a qualified parts catalog. Another notable aspect of this thread is the path: the government defines the requirements first (NASA/JPL assessment), a commercial company delivers the platform, and then board partners adapt it into VPX form factors—a supply chain far longer than consumer electronics but with much greater certainty.

Date: 2026-10-28　Source: StreetInsider/ABNewswire: GUITION launches VisionGo series press release

GUITION, under Shenzhen Jingcai Intelligent, has released the VisionGo series of embedded display modules, led by the 7-inch ESP32-P4 all-in-one display JC1060P470C_I_W_Y: dual-core RISC-V at 360 to 400MHz class, 1024×600 IPS capacitive touch, 32MB PSRAM, 16MB Flash, integrated WiFi and Bluetooth, a TF card slot, multiple GPIOs, and MIPI-CSI support on some models. The full series spans 1.28 inches to 21.5 inches, and the company says it is compatible with ESP-IDF, Arduino IDE, MicroPython, LVGL, ESPHome, and Home Assistant.

  • Observation: The ESP32-P4 is solidifying the “HMI display plus main controller” into a standard module form factor. For teams building smart home panels, energy storage inverter HMIs, or EV charger displays, such modules lower the hardware barrier to “pick a screen and write the UI,” leaving differentiation only in structure and algorithms—which also means hardware margins in mid-to-low-end HMI will be eroded even faster.

2.4 SiFive Positions RISC-V as the AI Accelerator Control Layer, with X100/X200/X300 as ACUs

Date: 2026-10-28 (SiFive blog 10-16, Jon Peddie analysis 10-26, community discussion sparked 10-28)　Source: SiFive: The Next Leap in Datacenter AI — Orchestrating Custom Accelerators with Intelligent Control Units, Jon Peddie Research: SiFive makes the case for RISC-V as the control layer for custom AI accelerators

SiFive proposes using its Intelligence series processors as “accelerator control units” (ACUs), inserting a programmable control plane between the host processor and custom accelerators to handle low-latency command dispatch, data movement, pre/post-processing, and algorithm tuning. Its argument targets three shortcomings of conventional approaches: hardwired state machines require costly hardware respins when algorithms or data formats change; frequent data movement on a shared bus introduces unacceptable latency and blocks memory pipelines; and offloading low-level scheduling to the host CPU consumes host compute while amplifying latency. The series is segmented with the X100 for control-intensive scenarios sensitive to area and latency, while the X200 and X300 offer greater vector bandwidth and compute. Jon Peddie Research’s analysis adds two deployment data points: Google data centers already use the Intelligence X200 as AI compute hosts, and another unnamed top-tier US semiconductor company has licensed the X100 for industrial edge AI.

  • Observation: This judgment is worth noting in the trends column—RISC-V’s commercial value is shifting from “ISA substitute” to “a fixed role in heterogeneous systems.” SiFive’s own phrasing is that “value is moving out of the ISA,” with the remaining differentiation in implementation and system integration. The implication for domestic vendors is equally direct: rather than directly replacing Arm main controllers, it is better to build the control and scheduling layer alongside AI accelerators—a path with far lower software ecosystem requirements and one that is easier to win orders with first.

III. In-depth Look at Domestic Teams

3.1 ESWIN Computing CTO He Ning: Automotive-Grade and Embodied Intelligence as Second and Third Growth Curves; RISC-V Consumer AI NAS to Enter Mass Production in Q4

Date: 2026-10-28　Source: [21st Century Business Herald: 21 Dialogue ESWIN Computing CTO He Ning, the High-Value Inflection Point for RISC-V Is Coming](https://m.21jingji.com/article/20261028/herald/c00176cd6a36a5ee0b9f1caf628e8f13_zaker.html)

In an interview after the summit, He Ning, Senior Vice President and Chief Technology Officer of ESWIN Computing, offered several specific judgments. First, the integration of RISC-V and AI follows three paths: RISC-V as the main control CPU with an external NPU (loose coupling, already common in products); RISC-V entering the AI unit to handle scheduling (NVIDIA GPUs embed a large number of small RISC-V cores internally); and giving RISC-V its own AI compute capability through vector and matrix extensions. He gave a timeline: matrix extensions account for more than 80% of large-model computation, and it will take another one to two years for the specification to mature and enter products, and another two to three years after that before standardized products reach scale; “the explosion of deep RISC-V-AI integration will probably take more than three years.” Second, the software ecosystem remains the biggest obstacle, but three windows of opportunity have emerged: AI is restructuring software and hardware together, large models have restructured the algorithm and operator toolchains, and the center of gravity of compute is shifting from training to inference (the inference ecosystem is significantly less complex than training).

On the implementation side, there are three concrete advances. On the automotive-grade side, the EAM2011 is China’s first automotive-grade MCU supporting lightweight AI applications, equipped with a self-developed 32-bit RISC-V core, and has entered volume application in display assemblies, in-vehicle wireless charging, and battery management systems; the self-developed RISC-V CPU IP R520A has passed TÜV Rheinland’s ASIL-D functional safety certification, becoming the world’s first multi-core, multi-architecture RISC-V core to pass ASIL-D (the earlier R500A was the world’s first RISC-V core to obtain ASIL-B certification). On the edge and intelligent computing side, the company has partnered with Zspace to launch the world’s first consumer-grade AI NAS based on the RISC-V architecture, with mass production and sales planned for the fourth quarter of 2026. On the ecosystem side, the company has mass-produced more than 150 products, serves 220 customers worldwide, and is advancing its ecosystem through the RISAA ecosystem technology platform and the RDI alliance it led the establishment of.

  • Observation: The most solid statement in the interview is that the barrier in automotive-grade lies not in the chip but in the system—from the supply chain and Tier1 to automaker adoption, the chain is extremely long, and producing the chip is only the first step. ASIL-D matters because it turns “can we get into the intelligent driving domain” from a business question into a certificate question; once the certificate is obtained, RISC-V’s flexibility is qualified to match the frequently changing parts of “intelligent vehicle function integration.” As for the AI NAS, Q4 mass production is a verifiable time point worth revisiting next quarter.

Date: 2026-10-28　Source: GitHub: spacemit-com/spine-triton commit history

4.2 unitree-go2 switches to terrain-only V2 walking policy, zero-copy IMU snapshot reads

Date: 2026-10-28　Source: GitHub: spacemit-robotics/unitree-go2

V. Summary and Trend Observations

1. The next step for verification infrastructure is resource pooling. Today’s remote XDMA board relay in XiangShan difftest removes the constraint that “the verification machine and the board must be on the same host.” Combined with the past three days’ fast-ref and fork checks, reftrace record replay, and the MMA synchronous verification toggle, difftest’s technical roadmap has shifted from increasing the speed of individual comparisons to scheduling multiple sets of verification resources. Teams working on RISC-V cores in China generally lack machine time, so this path has more practical value than adding yet another performance optimization point.

2. RISC-V’s role in AI is shifting from “replacing the main controller” to “a fixed supporting player.” Two independent statements appeared on the same day: SiFive positioned its Intelligence series as control units for AI accelerators (Google data centers already use the X200 as an AI compute host), while ESWIN’s He Ning broke down the integration of RISC-V and AI into three paths—main-controller offload, intra-unit scheduling, and instruction-set extension—and gave a three-year timeline. Both point to the same judgment: head-on replacement on advanced process nodes is not today’s main battlefield; the control plane, scheduling plane, and inference side are where orders can be won.

3. Automotive-grade certification is the dividing line this round, not consumer electronics. ESWIN’s R520A obtained TÜV Rheinland ASIL-D (the world’s first multi-core, multi-architecture RISC-V core), the EAM2011 automotive-grade MCU has already entered mass production in vehicles, and the consumer AI NAS developed with Jizhikongjian is scheduled for mass production in Q4. Of these three lines, ASIL-D is the only threshold that cannot be bypassed through price competition: it turns “can we get into the intelligent-driving domain” into a certification question. For other domestic RISC-V vendors aiming at high-value scenarios, this certificate’s timeline deserves separate tracking.

4. The robotics stack has moved from “synchronization” to “development.” spacemit-robotics, which yesterday was judged to be batch mirror synchronization, today produced ten substantive commits across four repositories: the middleware layer integrated motion adapters and operator clients, whole-body control added tabular coupling and feedback recovery, Go2 switched to a terrain-only V2 policy, and the IMU driver expanded to a third vendor’s serial protocol while reusing the kernel IIO. The method for reading this section should still be to look at the content of main-branch commits, but conclusions must follow the evidence.

5. Information volume and basis for judgment in this issue. After deduplication within the Chinese and English Google News windows, substantive new items centered on six: Qwenputer, the ESWIN CTO interview, LILYGO K230, Microchip PIC64-HPSC, GUITION VisionGo, and the SiFive control-layer discussion; the rest were follow-up summit interpretations and stock-market pieces, excluded under the deduplication rules. The open-source side was the main body of this issue: the XiangShan verification chain, openRuyi’s rust-vmm, CORE-V’s CBO fixes, and SpacemiT’s compiler/robotics stack all have verifiable commit records.
