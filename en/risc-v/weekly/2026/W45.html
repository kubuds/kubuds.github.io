RISC-V Weekly Report (2026-11-02 ~ 2026-11-06)

2026-11-06 Kubuds

Reporting period: Monday, November 2, 2026 through Friday, November 6, 2026 — 5 working days, 5 daily-brief source sets. The 11-02 issue used a 72-hour window (covering 10-30 05:00 to 11-02 05:00); the other four used 24-hour windows. The body therefore contains a few items dated 10-30 to 11-01, with the original date noted in each item’s title.

Sources: The daily RISC-V Global Briefs (five issues: 11-02, 11-03, 11-04, 11-05, 11-06); plus a 168-hour window re-check of followed GitHub organizations and key repositories (anonymous API rate limits were exhausted for most of the week, so each repo’s commits.atom was checked individually), dual-source verification of openRuyi (main-repo commits and the official news page), a day-by-day archived summary from riscv100.top, and supplementary checks of RISC-V International member company websites.

Editorial note: This week’s throughline is “the layer that turns an open instruction set into deliverable products.” In automotive, four layers advanced simultaneously within one week: Infineon moved its flagship AURIX product line to RISC-V (silicon); Quintauris released EM-Altair, a binary-compatible execution environment (platform specification); C*Core completed AUTOSAR and IAR adaptation (domestic software stack); and Zijing M100 was selected as a “China Chip” ecosystem promotion demonstration case (a large-scale adoption example). On the AI matrix side, SpacemiT open-sourced the RVISA virtual ISA working draft, attempting to insert a “programmer-expressible” mapping contract between PTX and cuTile. On the distribution side, openRuyi set the default ISA level for riscv64-openruyi-linux to RVA23U64, making RVA23 the default baseline rather than an option. All three threads answer the same question: which layer absorbs the fragmentation that comes with an open instruction set.

I. Weekly Highlights

  • Infineon launches its first RISC-V automotive-grade MCU platform, AURIX RC1, with up to 12 cores, ASIL D, and samples in H1 2027 (11-04): This is Infineon’s first MCU platform based on RISC-V and the first time the AURIX product line adopts an open instruction set. Officially positioned as a complement to, not a replacement for, the existing portfolio, current TriCore parts remain in supply. On specifications, a single chip carries up to 12 32-bit processing cores, a parallel processing unit for edge AI, and up to 40MB of embedded memory, with plans for same-family variants adding 64-bit microprocessor capability; on the safety side it reaches ASIL D, information security meets ISO/SAE 21434 and the Cyber Resilience Act, and post-quantum cryptography support is reserved; on communications it supports CAN XL, 10BASE-T1S and multi-gigabit Ethernet, with some variants integrating BRIGHTLANE switching and hardware data routing. The key to the product logic is merging the previously separate AURIX and TRAVEO T2G lines into a single generation, using one RISC-V base to cover zone control, body, chassis, battery management, powertrain, ADAS safety and cockpit, backed by the DRIVECORE software stack providing AUTOSAR, virtual prototypes and AI-assisted migration tools. Timeline: the family concept will be shown at electronica 2026 in Munich from November 10 to 13 (Hall C3, Booth 502), with samples targeted for H1 2027. Previously, automotive-grade RISC-V was mostly driven by new entrants and domestic vendors; a first-tier vendor switching its mainline products over means the AUTOSAR stack, functional safety certification, toolchains and Tier 1 adaptation resources will follow this line. Source: Infineon press release infpr202611-026

  • Quintauris releases EM-Altair, codifying binary compatibility for MCU-class RISC-V as four layers of compliance requirements (released 11-03, reported 11-05): It does not define a new core but a set of hardware, firmware and runtime requirements that “a compliant implementation must exhibit consistently”: four layers — ISA profile, privileged architecture, boot and runtime services, and security services — where vendors can each implement their own microarchitecture while software faces a single target. The baseline is RV32IM, with a clearly bounded set of mandatory and optional extensions fixing interrupt, atomic operation, CSR behavior and memory ordering; on the interrupt side it specifies a bounded high-throughput architecture for hard real-time, isolation uses PMP covering machine mode and optional user mode, and security practice aligns with ASIL-B equivalent requirements. The accompanying QNTAF verification and certification framework supports cloud, simulator and FPGA targets for benchmark, conformance and security testing, and integrates with CI/CD to generate traceable artifacts. Quintauris was formed in 2023 as a joint venture by Bosch, Infineon, Nordic, NXP, Qualcomm and STMicroelectronics. Read alongside Infineon’s RC1, chip vendors do the implementation and the joint venture does consistency, so RTOSes and compilers need to adapt to only one target once — domestic teams face “lower barriers for base software, higher barriers for compliance” happening at the same time. Sources: Quintauris release, New Electronics report

  • DAMO XuanTie C950 wins the “China Chip” Annual Major Innovation Breakthrough Product Award, and ten customer chips carrying XuanTie cores win awards on the same list (conference 11-02 / reported 11-03): On November 2, at the results ceremony of the 21st “China Chip” outstanding product selection held in Hengqin, Zhuhai, Alibaba DAMO Academy’s XuanTie C950 took the highest-threshold “Annual Major Innovation Breakthrough Product Award”; at the previous edition XuanTie received “Outstanding Supporting Service Enterprise” and “RISC-V Ecosystem Promotion Demonstration Case.” Moving from the ecosystem-promotion category to the product-innovation category says something in itself about this IP vendor’s position in the industry. Parameters are unchanged from the March launch: 8-instruction decode, 16-stage pipeline, out-of-order window of over 1000 instructions, up to 3.2GHz, and SPECint2006 single-core breaking 70 points for the first time; what is new this time is deployment data — cumulative shipments across the series exceed 6 billion units, with over 400 customers and over 1000 licenses, and C950 supports all mandatory and optional extensions of RVA23.1 with native CoVE confidential computing. More noteworthy than the main award is the customer list on the same roster: Dongfang Suanxin DF1000 (C908 plus C906) also won the Major Innovation Breakthrough Product award; Allwinner T536 (E907), Jiangyuan D1 (C908 plus E907), Wuqi WQ9301 (E907) and Hongsi HSRU3 (E906) won Outstanding Technological Innovation Product; Qingwei TX81 (C908) and Taixin TXW82X won Outstanding Market Performance Product; Jiangxinchuang D12X (C906), Jiuchen TD1601 (E906) and Maitexin MEGA188 (E902) won the Xinhuo Rising Star Product award. The ten chips span six markets — near-memory computing, industrial control, cloud inference, wireless connectivity, reconfigurable AI and display drivers — yet use four tiers of cores from the same IP family, which says more about the product line’s coverage density than a single flagship winning an award. Source: Jiwei report (reposted by Sohu)

  • RISC-V embodied intelligence open solution RV-EAI released at the Wuzhen “Light of the Internet” expo, open-sourced by six organizations (11-04): The solution was released by the openKylin Embodied Intelligence Working Group together with Milk-V, Chaorui Technology, Shanghai OpenLoong, SpacemiT and Kuya Technology — six organizations in total — under the working codename “Qiyuan,” with all details evolving continuously as open-source projects in GitHub repositories and on the official website. The proposition is to “release interfaces, manifests and reference implementations rather than a fixed complete machine,” splitting a robot by real-time requirements into a body layer (microsecond-level current loop), a cerebellum layer (millisecond-level control loop, with a real-time core running an RTOS and connecting to the joint bus via CAN-FD and EtherCAT), and a cerebrum layer (ten-millisecond-level inference handling perception, planning and VLA), all three built on the same RISC-V instruction set (RVA23, with RVV, IME, AME and VME). The verifiable definition of “open” is five pluggable points: on the body side, joint drive and MCU offerings from Zhongke Benyuan, HPMicro, GigaDevice, WCH and Espressif; on the cerebellum side, K3/SoM260, Zhihe A210 and UR-DP1000/Titan; on the cerebrum compute side, K3, Axera AX650N and Rockchip RK1828; at the operating system layer, five distributions — openKylin, Debian, Ubuntu, Fedora and openEuler — plus the RT-Thread real-time domain; at the framework and model layer, FlagOS, llama.cpp, TileLang and vendor runtimes. The acceptance criterion is stated explicitly: swap out one point and the other four need no changes, nor does the upper layer need re-adaptation, and it must pass conformance tests. The site also publishes self-tested data on a real SpacemiT K3 machine (Bianbu 4.0.7, kernel 6.18.3, collected October 21): local inference of a 1B vision-language model at 24.09 t/s, a 24B MoE model at 12.00 t/s, and IME2 at 970 GMAC/s per core (5632 GMAC/s across 8 threads), with a clear distinction between vendor-claimed peaks and usable throughput. The weight of this material lies not in the launch event but in how many real machine models the compatibility matrix ultimately fills in. Sources: Jiachen Plan WeChat account, RV-EAI website, kubuds/RV-EAI repository

  • SpacemiT open-sources the RVISA virtual ISA specification working draft, with the first round adding IME/VME/AME mappings and blocked MMA (repo created 11-04, commits 11-05): The new repository spacemit-com/rvisa proposes a RISC-V Virtual ISA, defining a layer of virtual instruction notation for scalar, vector and matrix computation; the current specification version is 0.2.0. Its positioning is stated clearly: it deliberately sits above NVIDIA PTX and below cuTile — it binds to no front-end language (source-language front-end implementations are explicitly out of scope for this version) and does not directly specify any chip’s instruction encoding, instead making “target mappings” versioned profiles that declare item by item which register classes, register groups and instruction sequences they map to, with upstream revision numbers and verification evidence attached. The notation follows RVV Intrinsics in expressing typed operations, operand roles and register-group constraints; tiles support one to N dimensions, reshape and axis permutation must preserve element positions, and layouts are derived from linear layouts. What best explains the problem it aims to solve is the “expressibility requirement”: any optimization of an RVISA tile computation must be writable by the programmer at the notation level — targeting precisely the failure mode where, as matrix extensions land, compilers silently vectorize and code must be rewritten for every new chip. Maturity needs to be stated plainly: the specification status file itself says this is a working draft, not a RISC-V International-approved specification; target mapping profiles are registered only as drafts with no implementation conformance evidence yet established; the MLIR dialect and executable conformance tools are both marked TBD; and the reference workload exists only as .rvisa notation source form and cannot be compiled or executed. The repository also contains three draft RFCs, 0001 through 0003, covering the instruction and register mapping contract, the core type and operation contract, and programmer-expressible tile layouts. It is the same logic as EM-Altair on the MCU side in two manifestations: fragmentation must ultimately converge on some stable layer of “software target,” with the difference in governance structure — one led by a joint venture of six major vendors, the other a single vendor’s working draft. Sources: spacemit-com/rvisa repository, specification status page

  • Linux 7.4 turns “fast unaligned access” into a runtime probe, letting distribution kernels gain up to 11% bandwidth (10-30): This change came in two steps. The 7.3 change submitted by Tenstorrent let a “kernel compiled for RISC-V hardware supporting fast unaligned memory copies” skip software alignment, with self-tested bandwidth gains of up to 11%, but it required enabling at compile time — and a distribution kernel must serve a range of hardware, always including chips with slow unaligned access, so the benefit could only remain in custom kernels. 7.4 moves the determination onto HAVE_EFFICIENT_UNALIGNED_ACCESS as a runtime probe: only when the hardware is probed to actually support it do user-space copies skip software alignment, so generic builds and distribution kernels can carry it by default. Other RISC-V changes merged into 7.4 in the same batch include crash hotplug, some page-table functions taking optimized paths, context-switch optimizations, the B extension reported in hwcap and hwprobe, and Zic64b reporting support. Together these are a step toward “the kernel ascertains platform capabilities and schedules on them itself,” and reporting on the hwprobe side is precisely the prerequisite for optimizations like runtime probing. One judgment from community discussion is worth recording: almost every vendor except SiFive supports fast unaligned access, and SiFive supports it only on its newer-generation performance cores — so once distributions enable this optimization, the actual benefit depends on whether chips report it truthfully in hwprobe. Sources: Phoronix, Hacker News discussion

  • openRuyi sees about 58 main-repo commits over five working days, RVA23U64 becomes the default baseline, and RuyiAI components enter the distribution (10-30 to 11-06): The daily pace was 6, 7, 15, 10 and 20 commits, plus 4 more during Friday daytime and commits to supporting repos such as clang-wrap. Three threads are most worth noting: first, llvm23 23.1.4 was added (a 1220-line spec plus two patches), adding an openruyi vendor to LLVM and setting the default ISA level for the riscv64-openruyi-linux triple directly to RVA23U64 — without passing an extra -march, the compiler generates code for RVA23, making RVA23 the default baseline rather than an optional optimization tier. Second, on 11-03 python-tilelang-ruyiai, python-triton-ruyiai and buddy-mlir were brought into the distribution as SPECs, meaning this RISC-V AI software stack is starting to be distributed as installable packages rather than via source-build scripts; kernel debuginfo support was completed the same day, making stack traces for online performance issues usable for the first time. Third, on 11-05 a single timestamp pushed in 20 document-format import libraries (libvisio, libwpd, libwps, libzmf, libabw, libcdr, libetonyek, libmspub, libodfgen, liborcus, libstaroffice and others), all from the same family of libraries that LibreOffice’s format import filters depend on — closing a dependency closure rather than adding scattered packages. The rest are engineering updates: Firefox 159, an expat 2.10.0 security fix, ollama 0.40.7, and CI switching to a scoped OBS signing key. The official news page’s latest items are still the two from October 2026 (10-19), and the November release has not shipped, so this week there is only repository-side progress and no distribution release. Sources: openRuyi main repository, openRuyi official news page, llvm23 spec

  • Andes slows its high-end RISC-V CPU Cuzco, redirecting engineering resources to an AI business that already accounts for half of revenue (11-02): In a November 2 Taipei report by EE Times, Andes CTO Charlie Su confirmed the company has slowed development of its high-end core Cuzco. Cuzco was originally a project of Condor, the company spun out for Andes’s data-center-class high-end core, publicly disclosed at Hot Chips 2025 and brought back in-house earlier this year; it is not cancelled, will still become a product and may be renamed, but the timeline has been stretched. On the numbers, AI now accounts for half of Andes’s revenue, having grown 30% last year with 50% growth expected this year; its in-house deep learning accelerator is modest in scale (about 4 TOPS at 1GHz) and comes with its own compiler, and the bulk of AI revenue comes from AI chip companies using Andes CPU cores for control, orchestration and data movement, with Meta, d-Matrix, Fractile and Axelera named among customers. Near-term priorities are controller cores for the storage market (10 customers already in volume production with small controller cores), automotive and robotics. This runs counter to the narrative that “RISC-V is charging into high-end data center” but is not contradictory — high-end core development has not stopped; the commercial cadence is now set by market momentum rather than the roadmap, and what actually pays is AI edge and control planes. Source: EE Times

II. Instruction Set and Architecture Ecosystem

XiangShan: 18 main-repo commits in one week, the heaviest being a CBO decode bug

The XiangShan main repo (kunminghu-v3) merged 18 commits this week, plus GEM5 6, NEMU 4, and difftest 11 (including nine from 10-30 to 11-01). The direction is highly consistent: finding bugs and adding observability, not adding features.

  • CBO opcode mistakenly OR-combined into cbo.zero (11-03, #6754): In cache block operation instructions, the operation type should select the complete opcode as a whole, but the code performed a bitwise OR of the “full CBO opcode” with the “base opcode.” When a CBIE request converts inval into flush, the OR operation combined cbo.inval and cbo.flush into cbo.zero—changing the semantics from “invalidate this block” to “zero this block.” Inval merely discards; zero writes data. A data-bearing zero landing on a line in use by another hart or about to be written back is silent data corruption, and it triggers only under specific operation sequences—undetectable by benchmarks or routine regression.
  • Four memory-access fixes concentrated troubleshooting (11-03): #6762 makes flush wait for CBO zero to finish enqueueing first; #6718 fixes the forwarding mask for unaligned accesses crossing 16 bytes; #6714 fixes the MdpHit determination when waitSqidx has already retired; #6678 fixes LoadUnit rollback info being overwritten by the next instruction under the same RobIdx. All four share the trait of failing only under specific interleavings: unaligned access combined with forwarding, retirement and hit determination in the same cycle, two consecutive loads with the same RobIdx triggering replay.
  • TAGE stores alt info into meta (11-03, #6800): Previously training reads and prediction reads contended for the same storage; the change stores alt information additionally into meta, and the training side issues a training read only when TAGE mispredicts or the actual branch outcome differs from the prediction—taking a high-frequency read path off the critical path, the most typical tradeoff in a branch predictor.
  • Frontend and prefetch: The frontend introduces FtqPrefetchQueue (10-30), the first step of the iprefetch refactor; in the same period, prefetch.i/r/w are decoded into LSU prefetch operations, and MBTB allocation suppression for hidden VBTB branches is fixed. On 11-05, another fix addresses MissQueue still merging stores while a prefetch miss is speculative (#6842)—merging a store with an undetermined prefetch means that if the prefetch is cancelled, the writeback data’s ownership goes wrong.
  • Observability and engineering process: Added BPU performance counters related to s2_override (#6777), and decode signals for former/latter remaining writeback counts in CROB (#6749); refreshed the README and added an AGENTS.md at the repo root aimed at AI coding agents (#6849), specifying build methods, code style, and commit conventions—an RTL project actively maintaining such a file indicates agents are already assumed participants in the daily development workflow.
  • Verification chain: NEMU fixes vscause retaining the injected interrupt number when hvictl injects an interrupt (#1279), marks zero-length vector loads as dirty (#1278), and routes matrix accesses through the shared TLB optimization path (#1275); difftest splits matrix AMU events into “writeback” and “completion” categories (#1025), and preserves asynchronous AME checker state during squash replay (#987)—long-latency instructions like MMA inherently have completion order differing from writeback order, and expressing two things with one event必然 misjudges in multi-core or replay scenarios. Among the nine difftest commits from 10-30 to 11-01, the MMA backend packing FP8 products into cache words is a step on the precision path.
  • All six GEM5 commits concern testing methodology: google trace and cbp trace wired into CI, Fetch Block Size statistics PMU added, SPEC06 RVV checkpoint profile updated, optional switch added to the weekly performance task, a hardware prefetch algorithm survey document added, and cpu-o3 filtering resolve inputs by “oldest same-cycle squash.”
  • Sources: XiangShan, #6754, NEMU, difftest #1025, GEM5

CORE-V: 29 commits in three batches, half on “installable, buildable, benchmark-runnable”

CORE-V Wally (cvw) merged 29 commits in three batches this week (three from 11-02 to 11-03, fifteen from 11-04 to 11-05, eleven from 11-05 to 11-06), plus one cvfpu commit. Structurally they fall into three groups:

  • Spec details: #1974 stops caching invalid PTEs per Svvptc (an RVA23 optional extension)—previously HPTW would write walk results landing on V=0 leaf or non-leaf PTEs into ITLB/DTLB, whereas Svvptc allows the handler to set V to 1 and retry directly without issuing SFENCE.VMA; an implementation caching invalid PTEs would fault permanently. The fix routes the walker through the existing FAULT path and writes nothing to the TLB. This is a textbook case of “the spec gives you an optional extension, and the implementation must leave a path for its legal use.”
  • Microarchitecture progress: #2050 changes the register file to a latch-based implementation (trading area and power for timing), #2046 routes HPTW AMO accesses through bus atomic transactions, #2052 fixes eBuFsmArb last-beat handling, #2048 introduces synthesis auto-ungroup, #2045 advances the RV32IMCB configuration into the regression flow.
  • Delivery engineering quality: Fixed the custom install script under Ubuntu 26.04 (#2061), rebuilt buildroot (#2039), adjusted Embench speed test and CoreMark compile options (#2031, #2024), changed code coverage to per-configuration statistics and brought rv64gc to 100%, and fixed stale values in wallyTracer’s RVVI trace fields (pte/page type/ppn/virtual and physical addresses and access type often carried values from the trap handler’s code page on TLB hits, causing ACT functional coverage to be recorded incorrectly).
  • Assessment: CVW is a teaching- and research-oriented core, but it has recently treated Ubuntu 26.04 compatibility, buildroot rebuilds, and CoreMark/Embench compile options as serious work—half its commits land on “installable, buildable, benchmark-runnable.” That cadence is closer to the engineering quality of tapeout preparation and external delivery than to RTL meant only for papers.
  • Sources: cvw commit log, CVW #1974

Secure microarchitecture: SecDMP delivers the first open-source DMP implementation on a RISC-V core

A team including KU Leuven (NDSS 2027 submission) first implemented the first open-source DMP (Data Memory-dependent Prefetcher) on a RISC-V processor, empirically demonstrating that the only existing defense aiming to preserve DMP performance cannot stop the entire class of leakage, then proposed SecDMP: it requires marking secrets in memory, ensures the DMP never encodes secrets into microarchitectural state, and formally proves its leakage does not exceed a “baseline without DMP,” all without sacrificing performance on public data; the hardware cost is no more than 0.5% area on the research core. The value to the open-source core community is that optimizations like DMP are moving from big-vendor proprietary designs to configurable cores, so security design must enter the RTL early rather than being patched after tapeout. In the same week, a joint team from Ruhr University Bochum, the Max Planck Institute for Security and Privacy, and Georgia Tech implemented all four randomized caches—CEASER-S, ScatterCache, SassCache, and MIRAGE—as the last-level cache of a single multicore out-of-order RISC-V SoC, built a complete FPGA prototype, and ran the full SPEC CPU 2017 rate and GAPBS workloads; by their account, this is the first horizontal evaluation of these four designs on the same full-system hardware platform. The paper focuses on implementation difficulties and tradeoffs; the public abstract gives no quantitative performance-overhead comparison. Both lines of research point to the same thing: RISC-V microarchitectural innovation has reached the stage where security costs must be quantified alongside it. Sources: arXiv:2610.37454 SecDMP, IndexBox coverage of the randomized-cache paper

Compilers and toolchains: RVA23U64 becomes the distro default, Nuclei goes VS Code, Espressif splits trace decoding into its own repo

  • openRuyi llvm23 23.1.4 (10-30): Adds an openruyi vendor to LLVM, sets the default ISA level of the riscv64-openruyi-linux triple to RVA23U64, and wires that triple into both the x86_64 and riscv64 Triple handling paths to keep cross-builds working. This is the clearest statement on the toolchain side this week: RVA23 is no longer an optional optimization tier.
  • Nuclei releases Nuclei Studio VS Code IDE preview (10-30, Shenzhen): The official development tool now comes in both Eclipse and VS Code forms; the current release is a Windows developer preview 0.1.0 with Chinese and English UIs, installed as a VSIX into an existing VS Code (requires 1.134.0 or later), and still relies on Nuclei Studio IDE 2025.10 underneath. The compatibility strategy is “don’t rewrite, copy as much as possible”: Eclipse-version projects can be imported directly, cproject compatibility handling is built in, the new-project wizard is identical, and SDK and BSP are still distributed as NPK packages interchangeable between the two versions; debugging supports OpenOCD, J-Link, QEMU, and NucleiModel, all through CDT gdbtarget, with Live Watch added; on the AI side there is no walled garden—Kimi, GLM, DeepSeek, and Qwen are all supported. The roadmap lists Linux and macOS support, profiling, code coverage, ETrace, and flash programming. For the domestic RISC-V developer ecosystem, the real significance of this step is the migration of the entry point—Eclipse’s slow startup and heaviness have long been complaints, while the VS Code side can conveniently connect to local or cloud models.
  • Espressif splits trace decoding into its own repo (11-05/11-06): esp-riscv-trace pushed 4 commits, adding GitLab CI, pre-commit configuration, updating GitHub workflows, and finally merging ci/pre_commit_and_pipelines into master. The repo was created on August 26; at the top level is a Python package named esp_riscv_trace, which does trace data decoding and tool-side support rather than RTL. Chip trace support is only the first step; being able to decode it into something human-readable is what makes it usable—delivering it as an independent component (dual CI plus pre-commit checks) is how that judgment is implemented. In the same period, Nuclei’s tool guide added rvtrace documentation and Hummingbird debugger troubleshooting, as RISC-V instruction tracing moves from high-end cores and dedicated probes into the standard documentation system of MCU vendors.
  • Sources: openRuyi llvm23 spec, Design & Reuse release, esp-riscv-trace, nuclei-tool-guide

III. Operating Systems and Distributions

openRuyi: ~58 commits across five periods, moving from “having packages” to “being operable”

Beyond the three main threads described in the first chapter (RVA23U64 default baseline, RuyiAI components entering the repository, office dependency closure), two engineering threads this week are worth noting separately.

Previously kernel modules were stripped, so stack traces could only show addresses with missing symbol names.
  • Friday daytime fill-in: After 11-06 05:00, the main repository had another 4 commits (clonezilla, llvm-defaults plus python-clang, tmux 3.8, qt6-qtwebengine build fix), still within the Friday workday and counted in this week. The official news page scrapes normally; the latest announcements remain the two from October 2026 (Ruyi Firmware, RISC-V ecosystem public infrastructure), and the November release has not shipped—this week is rolling maintenance rather than a release sprint.
  • Sources: openRuyi main repository commit log, openRuyi official news page

revyos/linux: Twenty config commits merged at once, K3’s platform surface widens noticeably

revyos’s 7.3.y branch merged 20 kernel config commits at once on 11-03, all stamped with the same timestamp—a single concentrated sync. On the hardware side, newly added or enabled: SpacemiT K3’s UFS and display controller, K3’s USB3 PHY and a full group of Type-C/TCPM/UCSI/FUSB301/DP alternate mode, ESWIN EIC7700’s ARCH plus DWMAC Ethernet and pinctrl, AST display, LM63 temperature sensor, and Banana Pi F3’s K1 USB2. On the platform capability side, two are more critical: a new linuxboot config (for deployment scenarios that load the kernel as firmware), and two CI pipelines—cross and native builds—added to solve the long-standing problem that kernel config changes could not be validated at commit time; also a PicoHeart errata switch and ONIE TLV NVMEM layout enabled (an asset-tag format for batch deployment of switches and network devices). Assessment: this distribution is moving from “the board boots” toward “complete system peripherals and verifiable changes.” Source: revyos/linux commit log (7.3.y)

OpenBSD 8.0 and felix86: hwcap, AIA, Sstc, and the long tail of the x86 compatibility layer

  • OpenBSD 8.0 (released 10-20, reported 11-03): This release’s riscv64 increments concentrate on architectural features rather than drivers—the kernel now probes CPU extensions and reports them to userland via AT_HWCAP/AT_HWCAP2 in elf_aux_info, so userland programs can dispatch code paths by hardware capability; the kernel adds V vector extension support, implements bounce buffers, supports the RISC-V advanced interrupt architecture with two new drivers, imsic and aplic, and adds Sstc timer extension support; the same release retires the Loongson port. For RISC-V distributions, hwcap reporting is more fundamental infrastructure than any single optimization—without it, userland can only guess branches at compile time.
  • felix86 fourteen commits (11-04/11-05): The recompiler that brings x86/x86-64 games to RISC-V Linux released version 26.11 on November 2; this window is the post-release fix wave, focused on Linux compatibility layer correctness: signal delivery for PTRACE_SYSCALL, PTRACE_SETSIGMASK restoration, 32-bit setrlimit, returning EINVAL when statfs64 length is invalid, the tid pointer for fork-cloned child threads, root directory escape checks for creat and statfs, the extended mask for 32-bit signal frames, and an infinite loop on slash-only paths; on the recompiler side, fixing the FSW C1 bit on x87 stack exceptions, moving the bad-address thunk before the code cache, and implementing TSO optimization for Volatile Metadata. Dense commits of this kind usually mean the main flow already runs, and what remains is making games and runtimes stop crashing intermittently.

Robotics Software Stack: Manipulator Framework, Full Dice Pipeline, and Humanoid Navigation — Three Layers Completed in One Week

  • Unified manipulator control framework (10-30): spacemit-robotics/manipulation landed a single commit of 85 files, +8605 lines, with directories split by capability: calibration contains ChArUco calibration, a hand-eye calibration CLI, and sampling tools; diagnostics has arm_check and an operator CLI; kinematics provides URDF-based forward kinematics; motion is the device service and CLI; bindings/python provides the client and operator support layer. The vendor treats the manipulator as a system component with “calibration, diagnostics, kinematics, and a service interface” rather than a snippet of example code.
  • Device sessions and safety boundaries (11-05): The architectural trade-offs in manipulation are stated explicitly — C++ applications link the component library directly and use DeviceSession in-process; the command line and Python go through DeviceClient, which spawns a local process and dispatches requests over JSONL; YAML waypoint tasks are executed by manipulation-device run. Device sessions uniformly handle device exclusivity, arrival determination, cancellation, timeouts, and fault locking; the driver layer only handles model protocols and unit conversion, while kinematics and hand-eye calibration load models from configuration — adding a new device just means implementing Arm and EndEffector and registering them. Most noteworthy is the passage stating that “components do not auto-enable, do not auto-clear errors, do not auto-home, do not auto-retry” — once middleware does these four things automatically, on-site personnel lose the basis for judgment when problems arise; placing safety boundaries at the session layer rather than the driver layer is the restraint that robotics middleware ought to have.
  • dice_arena full pipeline (11-05): SpacemiT K3 serves as the main controller; an AgileX Nero seven-axis manipulator connects via a USB-CAN adapter (SocketCAN, 1Mbps); the end effector is a Revo2 right-hand dexterous hand (six control channels); an Intel RealSense D435i is used for cup grasping and calibration; dice recognition uses a top-mounted USB camera; a ChArUco calibration board, speaker, and green cups round out the setup. On the software side, dice-arena serve starts video forwarding, local voice, and the game backend; the backend runs a state machine (rule explanation, cup grasping, cup shaking, cup placement, visual judgment, result gesture, return to HOME). Cup grasping is handled by CupApplication, which uses RealSense images to recognize the cup body, solves inverse kinematics, and checks the path; recognition is performed by vision_yolov8_objdetect inferring on the SpacemiT EP, with the feed pushed via RTSP to MediaMTX and then played in the browser via WebRTC; voice is synthesized by tts_moss_nano calling the local MOSS-TTS. What is truly valuable is the failure handling: the task policy library checks stage ordering via C ABI; once an action is issued and fails, it locks immediately; states requiring manual intervention are written to task_state.json, and after a program restart it still refuses to move until on-site personnel resolve the issue and execute reset.
  • Humanoid and SDK consolidation (11-04/11-05): humanoid_linglong adds LingLong’s SuperMimic standing policy configuration, gripper models, and manipulation scenarios; ros2_humanoid adds two complete configurations of RGBD SLAM and Nav2 for G1; manifest pushed three commits in a row to formally add manipulation and dice_arena to the SDK repository manifest, while docs-ros was updated with the Orbbec camera guide and K3 manipulator operation and dice game guides. The repository manifest determines which components belong to the SDK, the documentation determines whether developers can follow along, and the components determine whether hardware actions can be reused — all three advancing on the same day shows this line is moving from point demos to deliverables with versions, manifests, and manuals.

VI. Trend Watch

  • The automotive battleground has shifted from “does it have a RISC-V core” to “which profile does it conform to”: This week it appeared at all four layers simultaneously—at the chip layer, Infineon moved its AURIX mainline to RISC-V; at the platform-spec layer, Quintauris used EM-Altair to pin down interrupts and memory ordering; at the software-stack layer, Guoxin completed AUTOSAR and IAR adaptation; and at the ecosystem-case layer, Zijin M100 was selected as a demonstration case on shipments of tens of millions of units. For domestic teams this is both a dividend (AUTOSAR, RTOS, and toolchains need not be rebuilt by every vendor) and pressure (customers will ask “does it conform to a given profile”).
  • Convergence layers for fragmentation are emerging at different heights, each in a different form: RVISA offers a virtual instruction notation on the AI-matrix side, turning “optimizations a programmer can express” into hard constraints; EM-Altair provides a binary-compatible execution environment on the MCU side; openRuyi makes RVA23U64 the default triple; Linux 7.4 uses hwprobe to make runtime probing possible. What these four share is that, rather than leaving each chip vendor to interpret the spec on its own, they insert a stable software target between spec and implementation.
  • Open-source core investment is shifting toward verification and observability: Of XiangShan’s 18 commits this week, the weightiest was a decode bug that would turn inval into zero; the same period added BPU counters, CROB debug signals, and an AGENTS.md aimed at AI coding agents. CVW brought rv64gc coverage to 100% and treated Ubuntu 26.04 installation and buildroot rebuilds as serious work; all six GEM5 commits concerned checkpoints, traces, PMU, and weekly performance tasks. Scores are only worth comparing when built on reproducible measurement—this has become the consensus among open-source cores.
  • Domestic suppliers are moving from “publishing specs” to “delivering usable products”: SpacemiT advanced on specs (RVISA), SDK manifests, robot-arm manuals, and safety boundaries (no auto-enable/clear faults/return to home/retry) all in one week; Sophgo offered end-to-end stress tests on 2-core and 3-core configurations rather than peak compute; Zijin turned “ecosystem promotion” into a case that can be formally submitted; Nuclei moved its development entry point from Eclipse to VS Code. All four are shoring up the “can others actually use it” side.
  • Commercialization pace is set by market momentum, not roadmaps: Andes slowing its high-end Cuzco core and shifting resources to its AI business, which already accounts for half of revenue, and Infineon moving its mainline to RISC-V are two signals pointing in opposite directions but not contradictory—Cuzco is not cancelled, it is waiting for a signal worth accelerating on; what is actually paying today is AI edge, control plane, and automotive. For teams building high-end cores, this is a reality check on “who pays first.”
  • Benchmark sites are in a consolidation phase of “locking down methodology first”: This week’s leaderboard had only backfills, comparison views, and a version-progress page, with no new measurements; the 39 “delistings” on 11-06 were an artifact of comparison rows disappearing. This is the same kind of move as XiangShan adding checkpoints, traces, and PMU on GEM5—the comparability of numbers matters more than the numbers themselves.
