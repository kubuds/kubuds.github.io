Today’s Focus: ruyi 0.54.0-beta.20261102 released, first tag after a 39-day gap; ABI compatibility moves from package scanning to host checking, with only three packages annotated on the index side (11-02)

Date: 2026-11-02　Sources: 0.54.0-beta.20261102, PR #507 host ABI compatibility probing, PR #496 ELF ABI scanner, packages-index commits

At 18:37 on 11-02 (Beijing time), ruyi released 0.54.0-beta.20261102. The tag commit landed at 15:16, and 0.54.0b20261102 appeared in sync on PyPI; the stable channel remains 0.53.0 from 09-24. This is the first new tag in the 39 days since 0.53.0—the previous pre-release, 0.54.0-alpha.20260918, predates 0.53.0 by six days, meaning no alpha or beta shipped at all throughout October. The “late-October target missed” noted in the previous daily briefing now has a follow-up: it was not cancelled, but pushed to the first business day of November before cutting the beta.

The release notes list thirteen PRs, but the comparison baseline is 0.52.0-alpha.20260714, so nine PRs from 08-24 onward that had already landed in 0.53.0 are listed again verbatim. Comparing against 0.53.0 directly, the net new additions are only four: #503 test timeouts computed by package count, #508 vendor naming documentation, #507 host ABI compatibility probing, and #509 fetch error reporting. The “thirteen changes” readers see on the release page differ from the actual increment by two and a half months—this is the first point to clarify in this issue.

The substance of this release centers on #507: a new ruyi admin check-abi command performs host ABI probing and compatibility determination for a given package; ruyi list shows host compatibility notes, and ruyi install warns when a package is incompatible. The determination is tri-state (compatible, incompatible, undetermined) and distinguishes between lenient and strict predicate sets; on the RISC-V side it also handles edge cases such as floating-point ABI filtering of ld.so.cache, parsing of versioned single-letter extensions, stack alignment requirements, and missing weak symbol versions not counting as failure. The patch is +5760/−834 across 64 files, the largest single change in this release.

The layers need to be kept distinct: the ABI scanner #496 was merged back on 09-16 and shipped with 0.53.0—it can scan directories and tar/zip/deb archives, produce deterministic .abi.toml annotations, and provides rescan-package-abi. What 0.54.0-beta adds is the consumer side: taking the annotations and comparing them against the current host to answer “can this package run on this machine.” The toolchain half is in place this issue; the data half has only just begun: packages-index made three consecutive commits between 13:09 and 13:26, adding ABI annotations for three packages—wlink, qemu-system-riscv-upstream, and gnu-ruyisdk—eleven files in total, of which qemu has only two amd64 files and no riscv64.

Against the 327 package version description files in the index, three packages means the vast majority of packages can only return “undetermined” under check-abi. This does not affect the command’s usability, but it does mean that for now it is more a debugging tool for packagers and early adopters than a general safeguard for ordinary users installing packages. Bringing annotation coverage up will require rescanning package by package through the build pipeline, and this is a line worth watching before the 0.54.0 stable release.

2.2 Host ABI Compatibility Lands: check-abi, Three-State Verdicts, and Install Warnings (11-02)

Date: 2026-11-02　Source: PR #507, PR #496 ELF ABI scanner, PR #509 fetch error reporting

PR #507 merged at 13:27 (+5760/−834, 64 files), moving ABI capability from “describing packages” to “describing hosts and comparing them.” Specifically, four things:

First, host probing. New HostABIReport and HostABIProber read host capabilities by architecture: ISA level on x86-64, BTI/PAC on AArch64, the ISA extension set and floating-point ABI on RISC-V; the implementation goes through the installed system’s library paths and ld.so.cache rather than in-process dynamic loading.

Second, verdicts. Three states—compatible, incompatible, undetermined—with lenient and strict predicate sets used for “warn” and “block” scenarios respectively; ruyi admin check-abi is for packagers to debug, ruyi list folds the conclusion into notes, and ruyi install warns on incompatibility.

Third, RISC-V-side detail fixes: filter ld.so.cache entries by host floating-point ABI, parse versioned single-letter extensions, judge by stack alignment requirements, do not treat missing weak symbol versions as failure, and reject libraries with mismatched ELF class.

Fourth, note hygiene: cap note size, discard invalid notes before caching, invalidate old notes before rebuilding artifacts, and support stripping leading directories from archive paths.

In the same version, #509 fixes reporting of fetch failures: non-2xx responses are no longer treated as “download succeeded” and left as an error page, resumable partial downloads are preserved, and HTTP status, redirects, connection failures, and stalled transfers each get their own message. This one matters more to actual users than the ABI check—previously an error page returned by the server would be mistaken for a completed download.

Five Chinese and English queries—RuyiSDK, RuyiAI, “如意” RISC-V, openRuyi, and RuyiSDK RISC-V—all returned zero hits within the 24-hour window. General RISC-V news had several items that day (RISC-V user-copy runtime detection in Linux 7.4, Qwen weights embedding a RISC-V CPU, etc.), none directly related to this topic, so they are excluded per established scope.

VI. Trend Observations

6.1 The gap closes with a beta; 0.54.0’s flagship item is “can this machine run it”

0.54.0 went from the 09-18 alpha to the 11-02 beta, a 45-day gap; 0.53.0’s stable release to beta took 39 days. During this period the ruyi main branch was not idle—the ABI series of commits landed in two batches on 10-30 and 11-02—but the release channel did not restart until the first workday of November.

When it restarted, the chosen content was clear: host ABI compatibility. This is not a “new feature” selling point but a shift from empirical judgment to a queryable item for “will it run once installed.” For a package manager targeting multi-vendor boards and toolchains, this direction outranks adding a few more packages.

6.2 The release notes’ baseline is misaligned, re-listing two and a half months of old changes

Thirteen entries versus four is the most easily misread point this issue. The release notes’ comparison baseline stops at 0.52.0-alpha.20260714, not 0.53.0; thus the 08-24 “RuyiSDK Certified” vendor marking, the 09-16 ABI scanner, and the 09-23 cross-repo install state fix all reappear in the 0.54.0-beta changelog.

The implication for downstream: you cannot use this list to determine “what changed from 0.53.0 to 0.54.0”—you have to run the comparison interface yourself. Adding a step to the release process to “take the previous stable release as the baseline tag” would not be hard, but the cost to reader trust is not small.

6.3 Data plane lags the tooling plane; ABI checks mostly return “undetermined”

The tooling has completed the three-state determination, install warnings, and the check-abi debug command, but the data side has only three packages and eleven annotations—less than one percent of the 327 package version description files; qemu-system-riscv-upstream even has only an amd64 annotation.

This means what users can actually feel at this stage is “some packages show compatibility” rather than “all packages can be confirmed before install.” To make this chain a general capability requires the build pipeline to rescan package by package and backfill—work counted per package that will not complete automatically with a release. Next issue can check whether the annotation count in packages-index keeps growing, as the criterion for whether this line has truly started.

6.4 openRuyi’s clearing of backlog coexists with missing releases; the bottleneck is release, not development

Seven merges landed on 11-02 alone, five of them old PRs from August to early October; four direct commits landed the same day. Development activity is not lacking, but the 2026.10 monthly release is still unpublished, and the news page is held up only by two October features.

Read alongside the ruyi situation, this points to the same judgment: both distribution pipelines of the RuyiSDK ecosystem (package manager and distribution) showed a “code moving, releases not moving” state in October. 0.54.0-beta has restarted the package manager line; the distribution line must wait for 2026.10 or skip straight to 2026.11, at which point it can be judged whether this is process delay or cadence adjustment.
