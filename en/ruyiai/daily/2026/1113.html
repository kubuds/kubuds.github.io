Today’s Highlight: Seven VIR Merges Land in buddy-mlir in One Day — Masks, bf16, Reductions, and Integer Matmul Each Wired into the Vector Path (11-12)

Date: 2026-11-12　Sources: PR #1052, PR #1053, PR #1054, PR #1055, PR #1056, PR #1057, PR #1058

From 08:12 to 14:44 (Beijing time) on 11-12, the buddy-mlir mainline merged seven consecutive middle-end changes, numbered #1052 through #1058, all authored by zhanghb97. What the seven share is that operator forms previously confined to scalar loops are now wired, category by category, into VIR’s vector lowering path: i1 masks, libm-only math functions, bf16, fast-math flags, all reduction kinds, rank-0 fill, and integer matmul. Each comes with lit tests and quantitative data, and most also include measurements on SG2044 and SpacemiT K3.

The first, #1052, addresses the threshold for memory access. When a memref element type is i1, scalable vectors were previously rejected outright (with the message a memref of i1 needs fixed vectors), because a memref occupies one byte per element while an i1 vector occupies one lane per bit — only fixed-length vectors have a per-lane lowering. Triton’s load/store masks are exactly i1 memrefs: on the pure VIR pipeline with scalable vectors, 179 of 325 Triton-RISCV test files were stuck on this error. The fix reads and writes by byte — contiguous accesses use llvm.load/store on i8 vectors, while non-contiguous strip-mined regions use vp.strided.load/store with all lanes enabled; it also sizes i1 lanes as one byte, where previously a region whose first dynamic vector was i1 was sized at 1 bit, yielding under VLEN 256 a scale like vector<[512]xi1> — sixteen register groups.

#1053 handles math functions LLVM refuses to lower on scalable vectors (erf, erfc, cbrt, powf, atan2, acosh, etc.) by expanding lane by lane: for vector<[N]xT>, extract each of the N times vscale lanes, call the scalar function, then insert. The trigger was that convert-math-to-libm treats scalable vectors like fixed-length ones, computing only the first N and silently zeroing the rest — a scalable erf under VLEN 128 (vscale 2) has half its lanes wrong. The effect shows directly in test coverage: on the Triton-RISCV FlagGems suite of 4045 items on SG2044 (VLEN 128), passing tests rose from 3980 to 4006, with the 26 fixed being test_erf and test_gelu, and no new failures.

#1054 is the most heavily validated of the batch. RVV only places bf16 in vector registers with Zvfbfmin; without that extension LLVM refuses to lower even a single load (Scalarization of scalable vectors is not supported). The change adds an rvv-mattr parameter to the lowerer, defaulting to assuming Zvfbfmin is present (Buddy’s several RVV targets — K3’s X100 and A100, and SG2044 — all have it); when -zvfbfmin is given explicitly, it instead treats values as integer bits, reading and writing bf16 vectors as i16 vectors, using integer operations for extf and truncf (truncf rounding to nearest even), and handling absf and negf via the sign bit. The two paths were compared input by input on both SG2044 and K3: truncf over all 2^32 f32 values, and extf, absf, negf, and extf-mulf-truncf over all 2^16 bf16 values, with bit-identical results.

#1055 fixes fast-math flags being dropped in strip-mined lowering: an arith.mulf with contract plus arith.addf was rebuilt as plain fmul and fadd, which LLVM will not fuse. Flags are now propagated with the same-kind operators to the vector loop and epilogue, so f32 multiply-add yields vfmacc and bf16 yields vfwmaccbf16 under +zvfbfwma; the author compared fmaf expansion bit for bit over 4M lanes on K3’s X100 and A100, with matching results. This is the only one of the seven that directly changes instruction selection.

#1056 extends vir.reduce from only floating-point add and maxnum to all vector.reduction kinds: add, mul, minsi, minui, maxsi, maxui, and, or, xor, minnumf, maxnumf, minimumf, maximumf, with integer support as well, and a verifier checking that kind and element type match. Previously Triton’s integer sums, min/max, products, and all/any (along with argmin, argmax, count_nonzero, bitonic sort, and radix sort that depend on them) stayed in loops. The change adds 570 lines across 9 files; the scalar epilogue uses vector::makeArithReduction’s combiner, and vector<[1]xT> takes yesterday’s #1051 LLVM intrinsic path.

#1057 and #1058 close out two remaining categories. #1057 lowers linalg.fill on rank-0 memrefs (mostly reduction accumulators) to a single memref.store, cutting residual linalg.fill in FlagGems’ 1811 kernels from 393 to 0. #1058 enables integer matmul lowering: when A and B are the same integer type and no wider than C, sign- or zero-extend before multiply-add (without fma), so on RVV int8 matmul yields vsext.vf2 plus vwmacc.vx, and unsigned yields vzext.vf2 plus vwmaccu.vx; the same PR also fixes an assertion failure in dynamic-shape matmul — M and K were originally taken inside the vir.set_vl region and erased while still in use by a later pass. After the change, none of the 1811 kernels contain linalg.matmul (previously 2, namely the int8 one).

Today’s Highlights: triton-riscv lands the BOSCAME FPGA SPM path, plus open PRs for a 40% wheel slim-down and explicit targets moving to -O3 (11-12)

Date: 2026-11-12　Sources: PR #104 BOSCAME FPGA, PR #116 wheel slimming, PR #117 explicit target -O3

#104 merged at 17:40 (Beijing time), wiring the BOSCAME FPGA SPM path into triton-riscv: AOT contract export, lit and integration tests, kernels under examples/BOSCAMEFPGA, launch and makefile, with entry documentation in docs/BoscameAOT.md and the example README. The first line of buddy-hash.txt pins the buddy-mlir commit that lands SPM, ensuring the example and compiler versions match. Author caihanyi111 opened this PR on 11-09; self-testing covered only formatting and lint, with the full build left to CI on both x64 and riscv64.

Two more open engineering changes landed the same day, both aimed at the release artifacts themselves. #116 notes that the LLVM and buddy tools bundled into the wheel previously used –strip-unneeded, leaving debug sections intact: a single triton-shared-opt carried nine .debug sections at 407 MB; switching to –strip-all brings it down to 118 MB, and the combined payload of the seven tools drops from about 970 MB to about 576 MB, roughly 60% of the original size. The author also records a rejected approach — pointing bin/llc directly at buddy-llc (which is LLVM llc plus buddy patches) — but buddy-llc does not exit after writing its output, so it cannot replace the plain llc invoked on the non-IME path.

#117 changes the optimization level on the cross-compilation path: when a RISC-V target triple is given explicitly (cross-compiling, or enabling the cross-compile switch on a RISC-V host), the build previously skipped the LLVM middle end, llc used its default optimization level, and loops that MLIR left in scalar form stayed scalar in the object file. The change runs opt -O3 and llc -O3 first for such builds, with the triple and features matching llc; the native RISC-V path without a triple (llc -O0, with a source comment noting miscompiles at higher levels) and the IME path (via buddy-llc) are untouched. The same PR also adds +zvfbfmin to the default llc features — otherwise scalable bf16 aborts outright in llc, while buddy-mlir’s #1054 assumes the extension is present by default, so the two sides must stay in sync.

1.1 pytorch riscv branch: CI adds two criteria — Jenkins return code and zero-test-case pass (11-13)

Date: 2026-11-13　Source: PR #56

The riscv branch merged #56 at 00:25 (Beijing time), changing only one file, .github/workflows/ci-riscv64.yml (16 lines added, 7 deleted), by author yuzibo. The trigger was that in the community CI, PytorchCi’s 39th build showed “build succeeded, CI job failed, parent job still recorded as passed” — one such case being statistics where failed was 0 and pass was also 0.

The change adds two criteria: a non-zero Jenkins return code fails the step directly; and a statistics count with PASSED equal to 0 is also judged a failure — only PASSED greater than 0 and FAILED equal to 0 counts as a pass. For a branch that runs nightly packages every day, this is more worth noting than a feature change — if a green mark allows zero test cases to pass, regressions become invisible.

III. Vector Extensions and Operator Optimization

3.1 i1 masks read/written byte-wise; 179 of 325 test files previously failed on this (11-12)

Date: 2026-11-12　Source: PR #1052

Scalable vector access for i1 previously only had per-lane lowering for fixed-length vectors, so load/store on memrefs with i1 elements was rejected outright—and Triton’s masks are exactly i1 memrefs. Running the pure VIR pipeline, 179 of 325 test files failed because of this—the widest-impact change among the seven in this batch.

Lowering is now done byte-wise: contiguous access uses llvm.load/store of i8 vectors; non-contiguous access falling in strip-mined regions uses vp.strided.load/store (mask fully enabled, length fully supplied). There is also a size fix: when the first dynamic vector in a region is i1, element width was previously counted as 1 bit, yielding vector<[512]xi1> at VLEN 256—sixteen register groups when read as bytes; i1 lanes now count as one byte each.

3.2 bf16 lowered to integer bit operations without Zvfbfmin, both paths compared input-by-input (11-12)

Date: 2026-11-12　Source: PR #1054

The bf16 path previously had only one possibility—”Zvfbfmin present”; without that extension LLVM does not even lower loads for scalable bf16. The change passes rvv-mattr as a parameter to the lowerer, defaulting to assuming Zvfbfmin (K3’s X100 and A100, and SG2044 all have it); with -zvfbfmin it switches to integer bits: bf16 vectors are read/written as i16, extf and truncf use integer operations, absf and negf flip the sign bit, and NaN takes the canonical value.

Verification is exhaustive input-by-input: truncf over all 2^32 f32 values; extf, absf, negf, and extf-mulf-truncf over all 2^16 bf16 values, bit-compared against the Zvfbfmin path on both SG2044 and K3 cores. If f8 types or (without Zvfbfmin) bf16 appear in other operators or in memrefs of non-integer memory spaces, it falls back to fixed-length vector lowering.

3.3 Reduction covers all kinds; int8 matmul emits vwmacc.vx (11-12)

Date: 2026-11-12　Source: PR #1056, PR #1058

vir.reduce previously recognized only floating-point add and maxnum; integer sum, min/max, product, and all/any all stayed in loops. It now accepts integers and floats and all kinds of vector.reduction; the verifier checks that kind matches element type, and scalar tails are finished element-by-element with a combiner. Integer and min/max reductions are exact; floating-point sum and product remain ordered except under reassoc.

Integer matmul is likewise filled in: when A and B share the same integer type and are no wider than C, extend first then multiply-accumulate; on RVV, int8 yields vsext.vf2 and vwmacc.vx (unsigned: vzext.vf2 and vwmaccu.vx). The same change fixes an assertion failure in dynamic-shape matmul—M and K are taken within the vir.set_vl region and erased during use by later passes, reporting “expected that op has no uses”.

3.4 Three test-surface numbers: 3980 to 4006, 393 to 0, 2 to 0 (11-12)

Date: 2026-11-12　Source: PR #1053, PR #1057, PR #1058

Each of the three changes provides a verifiable quantitative result, all measured on Triton-RISCV’s FlagGems suite: the math-functions change raised passing tests from 3980 to 4006 out of 4045 on SG2044 (VLEN 128), with the 26 fixed being test_erf and test_gelu; the rank-0 fill change reduced residual linalg.fill across 1811 kernels from 393 to 0; the integer matmul change reduced residual linalg.matmul from 2 to 0.

Taken together, the three numbers say one thing: VIR as the sole pipeline is no longer at the “can it run” stage, but at converging on “which operators still remain in linalg or scalar form”.

VI. Trend Observations

6.1 What this day filled in was shape coverage, not performance

Of the seven patches, only #1055 (fast-math flags) directly changes instruction selection; the other six bring forms previously left in loops into the vector path: i1 masks, libm-only math functions, bf16, reduction kinds, rank-0 fill, and integer matrix multiplication. The right yardstick for this kind of change is “how much linalg or scalar path remains,” not benchmark scores—393 down to 0, 2 down to 0, and 179 failing files going to zero all use that yardstick.

Comparing this with yesterday’s #1050 strip-mined remainder narrowing shows the division of labor across the two days: first saturate the vector loops with lanes (performance), then let every operator enter the vector loop (coverage). Doing it in the reverse order would be wasted work.

6.2 Numerical validation has reached the scale of exhaustive inputs

#1054 ran all 2^32 f32 values through truncf and all 2^16 bf16 values through conversions and sign operations; #1055 compared the fmaf expansion bit by bit across 4M lanes. This level of validation cost shows that bf16 is now treated as a shipping path, not an “optimize when there’s time” item.

This echoes the 11-02 paper discussing LLVM’s silent degradation when auto-vectorizing bf16/fp16 on RISC-V—the same risk point: wrong results without an error. The validation approach in this batch of PRs is a direct response to this kind of silent error.

6.3 The release artifact itself has become an engineering metric

Three changes on the same day concern “what gets shipped”: the triton-riscv wheel shrank from about 970 MB to about 576 MB (triton-shared-opt alone from 407 MB to 118 MB), buddy-mlir nightlies are packaged per batch, and pytorch’s CI criterion blocks false greens from zero test cases passing. For RISC-V users, downloading a wheel costs far more than on x86, so the size and trustworthiness of release artifacts are becoming metrics on par with features.
