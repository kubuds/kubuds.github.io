Today’s Focus: triton-riscv Merges Triton 3.9.0 Plugin Refactor — Patch Set Cleared, Standalone Distribution Package Retired (11-05)

Date: 2026-11-05　Source: PR #98, commit list, PR #92

At 11:13 on 11-05 (Beijing time), trdthg’s PR #98 “Bump Triton to main (3.9.0)” was merged: 5 commits, 66 files, 1,806 lines added, 3,868 lines deleted. The deletions are roughly twice the additions, and that ratio defines the nature of this refactor — it is not adding another layer of patches on top of an existing branch, but deleting the practice of patching altogether.

The first change is the backend form. Triton’s TRITON_PLUGIN_DIRS mechanism installs backend/ as a triton_shared backend plugin, registers the entry point, links the C++ plugin into libtriton.so, and copies triton-shared-opt into the package as well. The standalone triton-riscv distribution package disappears accordingly, and imports in the code are uniformly redirected through this plugin name. The backend itself now locates buddy-opt, buddy-llc, mir-translate, and triton-shared-opt via paths.py; the CPU driver declares itself active only when no GPU backend is present.

The second change is clearing the patch set. The patches/ directory and the scripts that applied patches are all deleted. The patch set previously existed for two reasons: to let Triton build in environments without NVIDIA/AMD toolchains, and to absorb frequent LLVM API changes. Now that buddy-mlir’s LLVM distribution ships with NVPTX/AMDGPU targets and lld, and Triton’s GPU dependency paths are pointed at a stub directory, neither reason holds, so the patch set no longer has any value.

The third change is consolidating the packaging path. release.sh no longer assembles a second wheel: Triton’s plugin support already places the backend and triton-shared-opt inside Triton’s wheel, so the script only strips tools and runs bdist_wheel directly. Makefile becomes the unified entry point for setup, build, test, lit, and clean, with test depending on lit.

The cost is written into the same PR’s commit message. Triton 3.9’s frontend reads fields such as backend_name from the backend; without it, every tl.atomic_* call throws AttributeError, causing 383 FlagGems test cases to fail on riscv64. Adding the three fields backend_name, default_dot_input_precision, and deprecated_fp8_dot_operand_dtypes this time is what closes out the failures. There are concessions on the example side as well: upstream rejected the frontend patches for asin/acos/atan/atan2, so the examples switch to libdevice, which lowers them to the same __nv_* extern_elementwise, which triton-shared then converts into MLIR math operators.

On the same path, PR #92 “Rebase integration onto the official Triton v3.8.0 release” was closed unmerged that day. The two-route dispute recorded in the previous issue (#92 favoring stability at 3.8.0, #98 following the 3.9.0 mainline) has now converged on the latter.

I. RuyiAI Stack Progress (PyTorch / Triton / TileLang RISC-V Porting)

1.1 triton-riscv: Build Entry Point Consolidated into Makefile, Backend Installed into Triton Package as Plugin Directory (11-05)

Date: 2026-11-05　Source: Commit list, PR #98

The backend’s import path within the Triton package is triton.backends.triton_shared. The installation surface is narrower than before: there are no longer two distribution packages, and no assumption of a sibling buddy-mlir checkout. The documentation’s narrative about “two packages,” the patching steps, and the sibling-checkout assumption have all been removed. In setup.py, shutil.which("lit") now prefers the pip-installed lit console script over the one bundled with the LLVM distribution. The latter calls main() without an if __name__ == "__main__" guard, and Python 3.14’s forkserver multiprocessing re-runs it when importing the main module, causing the lit target to fail at 80-way concurrency.

The backend’s path resolution for local tools has also changed: buddy-opt, buddy-llc, mir-translate, and triton-shared-opt are now uniformly resolved by paths.py. CPU driver activation is determined by “no GPU backend present,” which differs from the previous environment-variable-based approach and behaves more predictably on machines with multiple coexisting backends.

1.2 triton-riscv: Release Cadence Changed to Daily Nightly, Weekend Release; pytest Concurrency Set to 16 (11-05)

Date: 2026-11-05　Source: PR #99, Release list

PR #99 aligns the release cadence with buddy-mlir: the nightly job publishes nightly/<date>-<sha> pre-releases, and the weekend job publishes release/<date>-<sha> marked as the latest version; runs are skipped when there are no new commits, releases remain in draft state until all wheels are uploaded, and workflow_dispatch provides an out-of-band dev/patch option. Two nightly builds were produced that day under this cadence: nightly/20261105-48bde12 (19:50) and nightly/20261105-849a180 (22:48).

On the testing side, the pytest suite was switched to 16 processes. This number is empirically grounded: on a 207-test slice, 1 process took 360 seconds, 8 processes 89 seconds, 16 processes 67 seconds, and 24 processes 67 seconds, while 32 and 64 were actually slower—each test case is a serial chain of “compile, triton-shared-opt, llc, execute, compare,” and beyond a certain point more processes contend for the shared compilation cache. Previously, when run serially, the flaggems suite took 1 hour 14 minutes. setup.sh installs pytest-xdist, and the count can be overridden with PYTEST_WORKERS.

Date: 2026-11-05　Source: Issue 080 article, GCC Zba commit

IV. Buddy Compiler Updates

4.1 Runtime adds a shared serving generation controller to support device-side token sourcing (11-05)

Date: 2026-11-05　Source: PR #1018, commit c2fd2e1

PR #1018 adds a model-agnostic serving generation controller: 18 files, 2045 new lines, letting runtime adapters share a single set of generated-token budgets, stop conditions, usage accounting, and streaming cleanup. Callers can either use host sampling via LLMSession or a token source that supplies tokens directly from the device side.

A few implementation details are worth noting: string stop conditions are matched on raw bytes first and then UTF-8 decoded, avoiding misjudgment at multi-byte boundaries; the token budget counts both the first prediction and the EOS/stop token; a fixed random seed supports a value of zero; and repetition penalty is applied once per token ID after deduplication within the request’s history window. The first token comes from prefill, so throughput statistics attribute the first selection to prefill and subsequent selections to decode, reporting zero throughput when there is zero decode work. The generation paths of the existing CLI and server entry points remain unchanged, with golden tests using fixed logits and the production DeepSeek tokenizer and sampler to protect outputs. Follow-up adapter integrations are tracked separately under DeepSeek R1 (#1021), Llama 3.1 TTNN (#1022), and Qwen3-VL, among others.

4.2 VIR scalable vector lowering patches: broadcast goes through vector<[2]xT>, kernels downgraded per llc options (11-05)

Date: 2026-11-05　Source: PR #1030, PR #1031

Both midend changes target scalable vectors. The lowering of vir.shuffle is split into several stages: broadcast first goes through vector<[2]xT> and then takes the first half (vector.scalable.extract) to obtain vector<[1]xT>, because when vector.broadcast is applied directly to vector<[1]xT>, LLVM generates a shufflevector with mask [0], which createOrFold folds away as an identity operation, leaving the remaining vscale-1 lanes all poison; llc turns the insertelement into a vfmv.s.f that writes only lane 0, and once this value is stored to a register instead of being merged into a .vf instruction, the result is wrong. After switching to [2]xT, llc uses vfmv.v.f to complete the broadcast at the LMUL of [1]xT, with no increase in instruction count and one fewer instruction in the loop. The other change downgrades kernels according to options such as llc’s -mattr, and the test vir-broadcast-scalable-one.mlir covers both the strip-mining path and the set_vl-with-result path.

VI. Trend Observations

6.1 From maintaining a fork to piggybacking on upstream: pluginization trades patch cost for version coupling

Date: 2026-11-05　Source: PR #98, PR #92

In a single day, triton-riscv went from “maintaining a patched Triton fork” to “a plugin for upstream Triton,” netting over two thousand lines deleted and eliminating the patch directory entirely. The payoff is straightforward: future upstream version bumps no longer require replaying patches, packaging collapses to a single wheel, and the install surface drops from two distribution packages to one.

The cost is equally clear, and it surfaced the same day: Triton 3.9’s frontend reads a backend_name field from the backend, and its absence caused 383 FlagGems test cases to fail. Parasitizing on upstream extension points means upstream frontend implicit contracts become interfaces that must be satisfied—and these contracts are often undocumented, discoverable only by hitting them in tests. Whether this refactor succeeds should not be judged by how many lines were deleted today, but by the cost of replaying it at the next upstream version bump, and by whether downstream suites like FlagGems still need a dedicated person watching versions.

6.2 Desktop office gap-filling on the packaging side and the silent parallel of the AI stack

Date: 2026-11-05　Source: openRuyi commit list, RuyiAI-Stack organization

openRuyi saw forty-one commits in a single day, thirty-seven of them on LibreOffice’s dependency chain: first twenty-one document import filters, then the AFDKO font toolchain, followed by in-review PRs for Firebird, PDFium, ZXing, SANE, and Box2D. This is not scattered updating but a complete desktop office suite packaging effort advanced component by component in batches.

On the same day, the RuyiAI stack was silent apart from triton-riscv: zero commits on pytorch’s RISC-V branch, zero on tilelang-riscv, zero on llvm-project’s riscv branch. The two tracks are driven by different people, different repositories, and different cadences; at the daily-report level they are worth viewing separately, and activity on the packaging side should not be mistaken for progress on the AI stack.

6.3 Issue 080’s increments land in the compiler and runtime, not the application-layer frontend

Date: 2026-11-05　Source: Issue 080 article

The four most substantive items in Issue 080 are all at the low level: three GCC Zb* optimizations into mainline, six LLVM P-ext and XTHeadBb merges, the OpenJDK JEP 544 AOT port merge, and V8’s vector tail and VLEN handling. The application-layer frontend (PyTorch, TileLang) saw no corresponding capability integration this period.

This distribution points to the same thing as 6.1: the focus at this stage is making existing operators and language runtimes run stably and correctly on RISC-V, not expanding frontend coverage. For downstream users, perceptible near-term changes will appear in compiler output and JDK behavior, not in the list of newly supported frameworks.
