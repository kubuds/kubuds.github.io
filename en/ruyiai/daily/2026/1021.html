III. Vector Extensions and Operator Optimization

3.1 IREE 3.13.0 Official Release: RISC-V V f32 vfmacc.vf MMA Enters Release (10-19)

Date: 2026-10-19　Source: IREE v3.13.0 Release, PR #24933 RISC-V V inner_tiled MMA

IREE v3.13.0 was released on 10-19 at 19:26. The CPU backend adds an inner_tiled MMA for RISC-V V f32 vfmacc.vf (PR #24933), mapping vector floating-point multiply-add directly onto RISC-V V’s fused multiply-accumulate. Meanwhile, LLVMCPU scalable vectorization now requires --iree-llvmcpu-vscale-range to be specified, taking the larger of the two lower bounds when the +zvl*b feature is present. On the model side, PT2E per-tensor, per-channel-group, and per-token quantized import into LinalgExt Q/DQ is retained.

The significance for this stack lies in the path comparison: RuyiAI’s tilelang-riscv and triton-riscv take the Tile-level DSL to RVV route, while IREE takes MLIR→LLVMCPU scalable vectorization. On the same RVV, both frontends simultaneously select f32 multiply-add as an optimization target, indicating that this instruction form has become a consensus landing point for RISC-V AI backends.

3.2 Verification and Cache Side: Three riscv-arch-test Merges, XiangShan CoupledL2 Banked SRAM (10-19 to 10-20)

Date: 2026-10-19 to 2026-10-20　Source: riscv-arch-test PR #2413 Sdtrig, PR #2791 S_F/S_V/S_VF, PR #2858 Vector Instruction SEW Coverage, XSCache PR #36, XiangShan PR #6738

Three merges landed within the RISC-V architecture test window: Sdtrig’s A-extension trigger coverage points and Sm/S/U three-mode icount coverage (10-20 05:53); adding S_F/S_V/S_VF to the S suite to cover the privilege levels actually used by operating systems (10-20 02:53); and extending vector instructions to all valid SEWs while filling in SEW=8 vrgatherei16 and fault-only-first LMUL selection (10-19 21:55). Together, the three push the verification surface toward “S-mode + full SEW,” providing a usable regression baseline for teams running RVV operators on K1/K3.

On the XiangShan side, CoupledL2 splits directory and data SRAM banks by set index, restricting MCP2 stalls to consecutive accesses within the same bank, and pauses acceptance of new prefetches when RequestBuffer occupies 2 slots (PR #36, merged 10-19 15:12; default bank split value is 2, revertible to 1); the main repository subsequently updated the XSCache pointer to incorporate this change (PR #6738). Cache parallelism and prefetch admission are adjusted together—a verifiable microarchitectural change.

VI. Trend Observations

6.1 Dependency closure work proceeds in parallel along three language-specific tracks: Rust fills in the uv backend, Go removes vendoring, Python fills in cloud storage

The 42/42/42 structure of this period’s 137 commits is no coincidence; it reflects three independent package-completion tracks advancing on the same day. On the Rust side, work centers on three families—windows-* 0.61, zerocopy/rkyv, and cap-std/io-lifetimes—together with python-uv-build, pointing to the Rust dependencies of Python build tools such as uv. On the Go side, the work is mainly minio and Prometheus/Kubernetes components, together with three de-vendoring PRs that change “bundle with source” into “bundle by dependency.” On the Python side, all major cloud backends for fsspec are filled in at once. The common goal of all three tracks is to complete the dependency closure so that Python AI and cloud-native deployments on RISC-V do not need to compile on site.

Worth noting is how this layer relates to RuyiAI: PyTorch’s DataLoader, checkpoint, and dataset tooling generally access remote storage through fsspec, so whether the backends are complete directly determines whether training scripts can run on K1/K3. This portion of dependencies that the distribution fills in for the upper layers matters more to “whether it can be used” than any single operator optimization.

6.2 The PyTorch branch enters a daily-replay rhythm: baseline updated daily, patch series unchanged

The same pattern has been observed for two consecutive days: a full-branch rewrite push at 09:14 on 10-19 and another at 08:32 on 10-20, with committer timestamps across the whole branch uniformly rewritten, local patch titles unchanged one by one, and the only change being the sync range of the upstream baseline. This approach decouples “tracking upstream” from “maintaining patches,” at the cost of an untraceable branch history—any downstream that references by SHA (CI caches, image builds, issue reproduction) will break every day. If this rhythm becomes fixed, the branch should be versioned by its “set of patch titles” rather than by SHA when read.

Meanwhile, the state of the three fork lines continues to diverge: PyTorch replays daily, LLVM has been silent for eight days since 10-12, and Triton nightly builds resumed with one version on 10-19 and then stopped. The three lines correspond to three states of investment, and also suggest that the current bottleneck of the RuyiAI stack is not the compilation backend itself but the sustained supply of review and release capacity.

6.3 What a server-class platform brings to the distribution is a compliance checklist, not a new porting task

Coverage of the SpacemiT V100 lists openRuyi among the available distributions for the server platform. If this holds, the implication is not “openRuyi needs to do a new port” but a set of specification-compliance requirements: RVA23, the server SoC/platform specification, BRS, and the security model—five items—plus the UEFI/ACPI/SMBIOS firmware chain. What the distribution needs to do is mostly align its existing user-space packages, installer, and image pipeline with the specifications, rather than rewrite components.

The current evidence remains incomplete: the openRuyi main repo had zero server-related commits that day, the firmware line (ruyifirmware, edk2-ruyi) has been silent since 10-15, and the 2026.10 release has not yet shipped. There are three things to watch: whether the openRuyi 2026.10 release notes mention the server platform; whether ruyifirmware/edk2-ruyi resume commits targeting the V100; and whether a V100 entry appears in the support matrix.
