Today’s Highlight: K3 Firmware Release 3 “Ruyi Firmware 20261015” — System Information Page and UEFI Driver Emulation (x64/ARM64) Land, AMD ARM64 GOP 1.68 Pilot

Date: 2026-10-15　Source: Ruyi Firmware 20261015 release, edk2-ruyi: System Information page commit a8ea1ac6, edk2-ruyi: SPI emulation switch commit 5581e304, edk2-ruyi: ARM64 GOP 1.68 commit c13cf98c, coreboot: A100-only interrupt fix 7b1ac324, ruyifirmware: raw SPI flashing documentation 6aece1c0

The openRuyi firmware packaging repository ruyifirmware released its third firmware release “Ruyi Firmware 20261015” on 10-15 (the first two being 10-13 and 10-14), fully covered in this window. This release has two main threads: first, visualization and information — UEFI Setup adds a read-only “System Information” page covering CPU, memory, PCIe devices and link speeds, and storage details; SMBIOS now reports DRAM type, part number, and configured speed; PCI graphics cards are initialized earlier and a graphics console re-entrancy issue when opening Setup is fixed; IMG GPU core frequency is fixed at 1228.8 MHz. Second, UEFI driver emulation — x64 and ARM64 driver emulation are both included in DEBUG and RELEASE packages (disabled by default), with CPU mode and emulation switches merged into Platform Settings, selections saved in a dedicated SPI sector (with CRC and read-back verification) and taking effect after reboot; experimental AMD ARM64 GOP 1.68 is enabled for the listed early GCN, Polaris, and Vega M graphics cards (other devices still use the onboard x64 GOP, with no fallback on replacement failure). On the fix side: A100-only mode interrupt mapping (with a matching coreboot fix: restricting the S-mode interrupt table to A100 harts and shifting the IMSIC/SSWI register windows); first-install documentation now uses raw SPI flashing.

This release was completed through coordinated work across multiple K3 firmware stack repositories on 10-15: edk2-ruyi 6 commits (System Information page, DRAM SMBIOS, graphics console reconnection, Platform Settings grouping, ARM64 GOP, SPI emulation switch), coreboot k3/port 2 commits (interrupt routing fix, DRAM configuration passed to payload), ruyifirmware build 8 commits, MultiArchUefiPkg branch 2 commits (AArch64 guest support entering the Makefile, platform policy switch).

3.2 External developments: riscv.org publishes DAMO XuanTie interview — C950 runs Qwen3.8-27B locally (over 30 tokens/s), AME matrix extension advances standardization (10-15)

Date: 2026-10-15　Source: V Questions with… DAMO Academy’s Dr. Jianyi Meng (RISC-V International)

The RISC-V International blog published an interview with Jianyi Meng, Chief Scientist of DAMO XuanTie: the XuanTie team ran the Qwen3.8-27B large model locally on a 64-core target configuration of its RISC-V processor C950, achieving throughput exceeding 30 tokens/s (roughly 20 to 22 words/s) without relying on a discrete GPU or NPU accelerator; reaching this throughput requires roughly 400 GB/s-class memory data movement, which C950 achieves with high-bandwidth memory paired with its in-house matrix extension already validated in silicon. The team subsequently joined forces with Qualcomm, IBM, VRULL, ISCAS, BOSC, and other members to launch the AME (Attached Matrix Extension) task group at RISC-V International to drive standardization. Key points from the interview: quantization, matrix instructions, on-chip storage, bandwidth, and kernel-level optimization must be co-designed as a whole; prefill is dominated by dense matrix computation, while decode shifts to a memory-bandwidth bottleneck; dedicated matrix registers (INT4 / INT8 to INT32, FP4 / FP8 / FP16 / BF16 to FP32 mixed-precision accumulation) are used to avoid competing with RVV registers; the specification still needs to cover data layout, accumulators, rounding and saturation, context save/restore, exceptions and virtualization, and compiler and ABI mapping. Jianyi Meng currently serves as Vice Chair of the RISC-V China Summit, which opens on 10-18 in Shenzhen; his outlook focuses on the data center ecosystem, a complete software chain, and architectural innovation.

V. Trend Observations

5.1 K3 Firmware Advances “Configurable + Simulatable” in Parallel: Enablement Strategy for Driver Emulation and Peripheral Compatibility Observations

K3 firmware has entered its third release day, with capabilities layering “simulatable UEFI drivers” on top of “selectable CPU modes”: x64 and ARM64 emulation are off by default, enabled via Platform Settings and persisted; AMD ARM64 GOP 1.68 pilots coverage of early GCN / Polaris / Vega M GPUs under an experimental label, and the no-fallback-on-failure setting indicates a deliberately conservative compatibility path. Points to watch: first, the stability and performance cost of the emulation layer under real mixed workloads; second, the pace at which simulatable drivers and the device list expand (whether NICs, storage, etc. are covered beyond GPUs); third, how this is delivered in coordination with openRuyi images and the kernel ruyi/7.3.y display patches (DP and GPU power domains).

5.2 Divergent Cadence Across Two Fork Maintenance Lines: PyTorch Rebuilds Continue Daily, LLVM Replay Misses a Third Window

The PyTorch riscv branch maintains a rebuild roughly every 24 hours (23 commits this round, 8 PRs refreshed in batch; the 101-commit diff versus the previous round’s head includes upstream merges), with a stable automated cadence; the LLVM riscv branch, by contrast, has seen no overnight replay for a third consecutive window since 10-12, marking a clear divergence in maintenance cadence between the two forks. Points to watch: whether LLVM replay returns, and whether the division of labor with the ruyisdk-side llvm-project maintenance line (XTHeadVector-related work) has shifted.

5.3 Expanding Kernel and Distro Maintenance Surface: ruyi/7.3.y Opens, Security Batches, and Unified XuanTie Key Naming

On the kernel tree, openRuyi linux has opened ruyi/7.3.y and landed 31 commits within the window (mainly K3 peripherals, display, and SG2044 migration replay), forming parallel maintenance alongside 7.2.y; linux-xuantie-kernel has unified vendor extension keys into the XUANTIE form—a convergence at the naming and branding level that favors consistent references on the hwprobe and toolchain sides. On the distro side, openRuyi landed 5 security packages the same day (cups / nltk / capstone / llama-cpp / multipath-tools), with CVE response trending toward batch processing. Points to watch: when 7.3.y enters the image release channel, and whether the release frequency of security batches remains stable.
