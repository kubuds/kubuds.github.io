Today’s Highlight: K3 decode attention moved onto VIR, performance on par with hand-written RVV kernels (10-28)

Date: 2026-10-28　Source: buddy-mlir PR #1014, K3 docs, triton-riscv PR #91, llvm-project rebase workflow

The most substantive step today came at 09:36: buddy-mlir’s #1014 “K3: write the decode attention in the VIR dialect” was merged (4 files, +476/−14), moving the entire decode attention of the K3 w4g32 kernel onto the VIR dialect. This is not another round of dialect capability fill-in, but the first time a real model’s kernel has been used for reconciliation—on one side the previously hand-written RVV vector kernel, on the other a VIR kernel assembled in Python, comparing numerics, instruction counts, and on-board throughput.

The approach breaks down into four layers. The construction layer no longer hand-assembles operators and hand-assembles types (previously operator names and type descriptions had to be written into strings), but instead goes through buddy_mlir.dialects.vir’s SetVLOp, load, shuffle, fma, reduce; one work item is a vir.set_vl region, with length taken as half the head dimension (64 lanes), each head being a scalable vector formed by joining the two RoPE halves, and the region returns that head’s (max, sum). The rotation layer loads, rotates, and scales q within the region, with rotate_half lowered to a single vir.shuffle, and cos/sin stored as two rows of equal-length data, so vir.from_vector is no longer needed. The memory view layer uses memref.expand_shape to split q, the KV cache, the output, and q’s normalization weights into 2×64 along the last dimension. The normalization layer (Qwen3’s q/k norm) gets its own one-dimensional vir.set_vl region, computing the sum of squares over the two halves following the _head_rmsnorm approach.

Pipeline parameters changed accordingly: kernel lowering switched from vector-width=128 to rvv-vlen=1024, use-scalable=false, with vector sizes determined by analysis based on the A100’s registers, because the region contains vir.shuffle, each head is kept as a vector group of 128 f32 (LMUL 4). The author states plainly in the PR: switching to use-scalable=true is the next commit’s job. The old _attn_decode_fn is retained, and the A210 kernel’s decode attention still uses it.

All three results are solid. On numerics, with and without q/k normalization, it is bit-identical to _attn_decode_fn; on machine code, the two parallel bodies each have 178 vector instructions, the key-value loop has the same instructions as the old version, with only two spill-reload positions changed; on-board throughput (K3, buddy-cli greedy decoding, three alternating rounds, 9 pairs of generated text fully identical) all three tiers fall in the same range—after 63 tokens, 28.26~28.49 vs. 28.10~28.58; after 458 tokens, 26.82~27.13 vs. 27.02~27.04; after 900 tokens, 25.37~25.41 vs. 25.29~25.77. The author notes: two builds of the same code can differ by up to 2%, and the ranges overlap.

Two other commits today accompany this main line. First, llvm-project’s riscv branch gained a 244-line automatic rebase workflow (see 1.1), moving the problem of “PRs on the author’s fork falling behind the baseline” from manual work into Actions. Second, triton-riscv’s dependency anchor was raised another notch by renovate to dev20261028 (see 1.3), but this nightly build was produced before this morning’s three merges, so even if this dependency update is merged, downstream still won’t get #1014—using today’s results requires waiting for the next nightly build.

I. RuyiAI Stack Progress (PyTorch / Triton / TileLang RISC-V Porting)

1.1 llvm-project: No More Re-basing; Adds “One-Click Rebase of Author Forks” Workflow (10-28)

Date: 2026-10-28　Source: riscv branch commit cf00909d, full workflow text, riscv branch commit list

Unlike the previous issue’s “fifth full-branch replay in five days,” the local patch set on the riscv branch is untouched this period: the branch head advanced one commit from ed439f3e, and compared with the previous head it is 1 ahead, 0 behind, touching only 1 file. The new commit (cf00909d, authored 23:27, committed 23:54) is a pure CI asset—.github/workflows/autorebase.yml, +244/−0.

The workflow’s design intent is stated in its comments: it is installed on the default branch of the author’s source repository, run manually from Actions with a target PR number, uses the source repository’s own GITHUB_TOKEN, and requires no custom secrets or labels. It is triggered via workflow_dispatch with two inputs—the PR number (required) and “dry run only, no push” (enabled by default). It runs on ubuntu-24.04 with a 90-minute timeout; the comments explicitly require that PR code, hooks, builds, or submodules never be executed while holding write permissions, and the git config points hooksPath, attributesFile, and fsmonitor all to /dev/null, with GIT_TERMINAL_PROMPT=0 and GIT_EDITOR=true. Conflict handling has a dedicated function: for cases -Xours cannot handle (including modify/delete conflicts), it walks ls-files --unmerged entry by entry—taking the local version if stage 2 exists, deleting otherwise; during rebase it first checks whether the baseline is already an ancestor, and can recognize “equivalent patches” and discard duplicate old baseline patches.

What this addresses is a concrete cost that has recurred over the past several issues: the branch is fully replayed once a day, so PRs on the author’s fork immediately fall behind, and manual replay is both slow and prone to scrambling the patch set. The boundary needs to be clear—it rebases other people’s PRs; the branch’s own daily full replay still requires maintainer action. It reduces the cost of “following the baseline” from manual judgment to a single scheduled run with a dry run, but it does not automate the trigger condition. Its real value can only be verified when the next external PR is submitted against the new baseline.

II. RuyiSDK Toolchain and Distributions

2.1 openRuyi PR #1350: Three commits rebased, GCC build cost quantified at 2.81x (10-28)

Date: 2026-10-28　Source: openRuyi PR #1350, review comments, PR commit list

At 16:22, all three commits in the RuyiAI trio packaging PR (buddy-mlir, python-triton-ruyiai, python-tilelang-ruyiai) were rewritten within the same minute, clearly a rebase onto the latest main branch; the current scope is 9 files, +680/−0, 14 lines more than recorded in the previous issue. The PR was refreshed again at 18:15 due to review comments, now totaling 13 comments, and remains unmerged.

The most informative item this issue comes from the author’s reply at 10:41. The previous issue’s framing was “GCC can be substituted, but build time is at least 1.5x”; this issue provides measured data: on a riscv64 machine, switching buddy-mlir’s build from LLVM to GCC changed the time from 8814 seconds to 24798 seconds (about 2 hours 27 minutes versus 6 hours 53 minutes), 2.81x, and that GCC build failed at the link stage and did not complete.

This turns the debate from a matter of position into a matter of cost. “Whether to externalize the LLVM bundled with buddy-mlir” was originally a dispute between two technical approaches; it now has a number that a distribution build farm can understand: 2.81x means scheduling, machine occupancy, and timeout policies all need to be recalculated. The author’s other rationale also holds up better as a result—the LLVM used by buddy-mlir is only used within its own packages, and those packages pin specific LLVM commits, so keeping it in-package is what makes it reproducible. He also notes that triton upstream’s setup.py has a mandatory check for whether git is executable, so either a git build dependency must be added or setup.py must be patched (the latter will break as triton is upgraded).

3.2 Vector width convention: VIR side set to 1024 bits, one LMUL 4 group per head (10-28)

Date: 2026-10-28　Source: buddy-mlir PR #1014, llvm riscv branch commit 1811501f, commit ed439f3e

#1014 sets the target vector length for kernel lowering at 1024 bits and requires that scalable vectors not be used, so each head (128 f32) occupies exactly one LMUL 4 vector group, and the vir.shuffle in that region also completes within the group—size, grouping, and instruction are all constrained by the same set of parameters. This is a technical convention worth recording this period.

This convention is one end of the same thing as the upstream backend. In the previous window, the llvm riscv branch merged #30, which lowers IME intrinsics to SpacemiT A100 dot-product instructions, and #31, which added HP/SP and pack/unpack lowering paths for A100 plus scheduling calibration. One is the backend doing instruction selection and scheduling by register; the other is the kernel expression layer sizing vectors by register. No document states whether the parameters in the two places constrain each other, and no cross-validation has been done on K3—whether this convention loosens when the switch to scalable vectors happens in the next stage (the author has said this is the next change) is the point most worth watching.

IV. Buddy Compiler Updates

4.1 K3 decode attention moved onto VIR: bit-exact numerics, K3 measured throughput in the same range (10-28)

Date: 2026-10-28　Source: buddy-mlir PR #1014, K3 documentation changes, test file

Last issue recorded the Python bindings from #1009 as “going from a buddy-opt-only feature to a programmable dialect”; this issue delivers the first real thing written with those bindings: #1014 merged (09:36), 4 files, +476/−14, of which 264 lines are new kernel implementation, 152 lines of tests, 10 lines of lowering pipeline, and 50 lines of K3 documentation.

The technical points are covered in “Today’s Highlights”; here we add only three verifiable details. First, the PR explicitly states this is a redo of the closed #998, and the redo rests on the four subsequent commits: activity-based sizing (#1000), rows (#1005), vir.shuffle (#1006), and Python bindings (#1009)—in other words, this is not an independent optimization but a one-shot stress test of the foundation laid by those four. Second, the validation is fairly rigorous: the tests do bit-level comparison of _attn_decode_fn, covering with and without threads, start offsets 0/15/16/37/70, and 0/37 when q/k normalization is enabled; the qk_norm path in test_k3_w4_moe.py also runs the VIR kernel; check-buddy 239 + 401 all pass. Third, at the machine-code level the two parallel bodies each have 178 vector instructions, the key-value loop is identical to the old version, only two spill-reload positions changed, and the q rotation went from an operation on two LMUL 2 half-groups to vfneg plus one register move.

One point to keep in check: this “performance parity” was obtained on a single K3 board, with greedy decoding, over three sequence lengths, and the author notes that two builds of the same code can differ by 2%. What it proves is that VIR no longer introduces a performance penalty—not that VIR is already better than hand-written kernels.

VI. Trend Watch

6.1 From “can express” to “runs just as fast”: VIR performs its first performance reconciliation against a real model kernel

Over the past three issues, this thread has been filling in expressiveness: on 10-26, seven commits in one night added scalable vectors; on 10-27, Python bindings were added; on 10-28, the entire K3 decode attention was ported over, with on-board throughput reconciled. The significance lies in the combination of three numbers—bit-level numerical consistency, identical instruction counts (178 each), and overlapping throughput ranges. Homegrown dialects most easily get stuck at “runs but slow,” and #1014 at least proves this hurdle has been cleared for now.

But two things are still missing to judge whether this stack can truly replace hand-written kernels. First, coverage: only decode attention was ported this time; the A210 kernel still uses the old function, and the MoE, quantization, and prefill paths remain untouched. Second, scalable vectors: this issue explicitly disables use-scalable; once enabled in the next commit, vector size will no longer be determined at compile time, the LMUL 4 grouping assumption will loosen, and whether numerical values and instruction counts can hold will need to be reconciled again. Until then, treating “VIR has caught up with hand-written kernels” as a conclusion is premature; the accurate statement is “caught up in the K3 decode attention segment, at a fixed vector length.”

6.2 The cost of rebasing shifts from patch drift to governance: the workflow takes over rebasing, but the branch itself still relies on people

On the same day, the llvm riscv branch stopped full-branch replay and switched to a 244-line automated rebase workflow. This shift deserves a separate note: the pace over the past five days was “one full-branch replay per day, rewriting twenty commits each time,” with author dates unchanged, committer dates unified, and no new functionality in the patch set itself. This approach keeps up with upstream, but the cost is that external contributors’ PRs are always one step behind—anyone who wants to submit must replay it themselves.

The new workflow turns this into a dispatch of “fill in the PR number, dry-run by default, one-click push,” always taking the riscv side on conflicts, automatically discarding duplicate patches, and never executing PR code or builds. It does not solve the branch’s daily following, but it separates part of “the cost of following the baseline” from the maintainer’s manual judgment. What to watch next is whether external PRs actually increase as a result—if no external PR is submitted against the new baseline within two weeks of the workflow going live, that would indicate the bottleneck is not the rebase tool but something else.

6.3 The distribution-layer debate now has a price: a 2.81× build-time ratio is more persuasive than “preference”

#1350 has been debated for nearly a month, with the core disagreement being whether buddy-mlir’s bundled LLVM should be externalized. The previous issue’s framing was still “GCC can be used, but at least 1.5× the time”; this issue the author provides measurements: on riscv64, 8814 seconds becomes 24798 seconds, 2.81×, and the GCC run failed to link and did not complete. The nature of the debate has thus changed—from technical preference to build-farm scheduling arithmetic.

The lesson for the RuyiAI stack is not in the conclusion but in the method: many disagreements in RISC-V distribution packaging (whether to vendor, whether to externalize the toolchain, whether to ship IR with the package) ultimately come down to three measurable numbers—build time, image size, and reproducibility. Last issue, openRuyi withdrew the “ship LLVM IR with the package” route; this issue, #1350 uses 2.81× to defend “keep LLVM in the package.” The two judgments point in opposite directions, but rest on the same kind of cost accounting. The next thing to watch is whether this PR can be merged with this number attached—if not, it would indicate the distribution’s tolerance for build duration is lower than the author expects, and that is what truly needs adjusting.
