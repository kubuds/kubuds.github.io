Today’s Highlights: buddy-mlir merges Qwen3-0.6B FP16 optimization, Prefill 86.01 token/s (11-23)

Source: PR #1001.

#1001 was merged on 11-23 at 14:51, titled “Optimize Qwen3-0.6B FP16 Prefill and Decode on K3 A100”. It changes 23 files, adding 560 lines and deleting 50.

Benchmarks were run on the same K3’s A100 cores 8 through 15, eight physical cores, with identical inputs. Prefill evaluates 128 positions; Decode is measured for 32 steps starting from position 96; load time is excluded.

Implementation Prefill (token/s) Decode (token/s)
Buddy mainline, unoptimized FP16 4.24 0.84
llama.cpp 71.64 14.38
Buddy, this PR 86.01 13.45

Prefill is 20.1% higher than llama.cpp and 20.3x the mainline baseline. Decode is 13.45 token/s, 6.5% lower than llama.cpp, still 16.0x the mainline.

The two metrics move in opposite directions. Prefill relies on tiled GEMM and native VLEN=1024, while Decode is limited by single-token GEMV bandwidth. The PR description states that the comparison uses all-position logits, aligning the two sides on this point.

The kernel side reuses results from #997, including IME FP16 GEMM and GEMV, Decode weight packing, and RVV and SiLU optimizations. Attention uses a vector width of 64, and Decode splits only one KV path.

Configuration is centralized in
models/qwen3/specs/f16_k3_a100.json, and the default pipeline is unaffected. In the file, VLEN is 1024, Prefill vector width is 64, Decode packing width is 32, and thread count is 8. Output vocabulary weights are stored separately so the layout can be selected per projection.

On correctness, 96 Decode tokens and three repeated greedy-generation test cases all match the PyTorch reference. The PR description also notes that the full check-buddy run was blocked by a disabled Python package target and could not be run in full.

4.2 #1077 proposes strip and zstd unification, targeting the single-asset limit (11-23)

Source: PR #1077.

#1077 was opened on 11-23 at 11:05, modifies only one file, and has not yet been merged. Its title is “Pack the LLVM and buddy tarballs with zstd”.

The PR description gives the motivation. The riscv64 LLVM installer package, after gzip, slightly exceeds GitHub’s 2 GiB single-asset limit. nightly/v0.1.5.dev20261120 therefore failed to publish, with the API returning 422 and “size must be less than 2147483648”.

The proposal has three parts: strip binaries and shared libraries, remove the MLIR Python bindings, and switch to zstd -19 –long=27 packaging. The author’s estimate is that LLVM drops from 2047 MB to about 840 MB, and buddy from 264 MB to about 180 MB.

The description also mentions two supporting items. triton-riscv’s setup.sh can already read .tar.zst; the first release after this change lands needs to run llvm_cache_mode=clean once, because the cache key does not include this filtering.

VI. Trend Observations

6.1 Model optimization shifts to batch reuse

#1001 explicitly states that it reuses #997’s kernels, weight packaging, and RVV/SiLU optimizations. Whisper Base, PaddleOCR-VL-0.9B, and EmbeddingGemma in the queue also reference the same path.

This shows that model acceleration on K3 A100 has shifted from one-off efforts to templating. The main work for adding a new model is writing configuration and running correctness checks, rather than rewriting kernels.

There are two pieces of evidence. First, configuration is centralized in each model’s specs directory; second, the PR descriptions repeatedly use the terms “shared kernels” and “reuse”.

6.2 Release numbering advances faster than content

ruyi moved from 0.55.0-beta to 0.56.0-alpha, with the code diff being only three lines of version number. The reissued official tag for triton-riscv also points to the old commit from 11-18.

Both repos saw “new version, no new code” on the same day. This shows that the release cadence is driven by version planning, not by the volume of changes.

The downstream impact is that version numbers no longer indicate how much content there is. To judge whether an upgrade is worthwhile, you need to look at the set of items in the release notes, not the size of the number.

6.3 Device-side code begins to leave the main repo

The website repo deleted 775 lines this round, handing the device runtime over to a separate repo and submodule. In the same period, ruyi-imager-webview and ruyi-imager-electron appeared under the ruyisdk-test organization.

The direction is to split the flashing tool into components that can be released and tested independently. The main repo thus becomes smaller, and build permissions can be isolated separately.

Worth noting is that the new repos sit under a test organization and have not yet migrated to the main ruyisdk organization. Whether this step happens can serve as a follow-up observation point.
