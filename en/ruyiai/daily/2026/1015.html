Today’s Highlight: Second K3 Firmware Release — UEFI Setup Introduces CPU Mode Selection (X100/A100) with Persistence; OpenSBI K3 v4 Series and coreboot / EDK2 Land in Coordination on the Same Day

Date: 2026-10-14　Source: Ruyi Firmware 20261014 Release, OpenSBI K3 v4 series integration commit, edk2-ruyi commit ba4ff0ad, coreboot k3/port commit list, opensbi k3/port commit list

The openRuyi firmware packaging repository ruyifirmware released its second firmware version, “Ruyi Firmware 20261014,” on the afternoon of 10-14 (14:42). Its core feature is bringing choice to K3’s CPU configuration: the UEFI setup interface now offers CPU mode selection, with the setting persisted and taking effect on the next boot. Tools such as fastfetch can identify the mode as k3 / k3-x100-a100 / k3-a100. The three modes are: X100-only (default, 8 X100 cores, RVV VLEN 256, H extension retained); X100 + A100 mixed (16 cores, both RVV and H extensions disabled); A100-only (8 A100 cores, VLEN 1024, H extension disabled).

This release was completed through coordinated work across four K3 firmware stack repositories on the same afternoon: OpenSBI’s k3/port branch first landed the K3 v4 series (13 commits; 6 with the FROMLIST prefix at 09:50, 7 with the RUYI prefix at 13:05); coreboot’s k3-pico-itx selects the CPU tier via SPI configuration (14:11) and moves device tree fixup earlier to execute before payload handoff; on the EDK2 side, edk2-ruyi adds “persistent CPU selection mode” (14:11); ruyifirmware then integrates the OpenSBI K3 v4 series (13:05) and the K3 CPU selection mode (14:24) in sequence, completing packaging and release.

Only one day separates the first firmware release (20261013) from this one. K3’s delivery focus has shifted from link bring-up (the previous day’s batch debut of 35 EDK2 platform commits) to the hardware configuration surface — CPU cluster combinations and extension toggles are now left to firmware-layer selection. Points to watch: the performance and compatibility trade-offs of each mode (especially the mixed mode with RVV / H disabled and the big-core mode) under real workloads, how setting persistence behaves across firmware upgrade paths, and how it coordinates with the openRuyi distribution image (kiwi-image) and the toolchain under development (K1/K3 adaptation).

3.2 External developments: RISE releases SpeexDSP RVV optimizations, measured speedups on K1/K230 (10-14)

Date: 2026-10-14　Source: RISE blog post, Hacker News discussion

The RISE project published progress on RVV optimizations for SpeexDSP (author: Tristan Matthews): introducing Meson builds, Checkasm tests, and hand-written RVV kernels for SpeexDSP, validated on K1 (VLEN 256) and K230 (VLEN 128) — K1 floating-point resampling achieved roughly 3.71x / 3.59x speedups over Clang 18 / GCC 13 baselines, respectively. This work extends RVV optimization into foundational multimedia libraries such as VoIP and audio resampling, directly relevant to the SpacemiT platform tracked by RuyiSDK / openRuyi (entry captured via the intelligence repo’s 10-14 issue; classified as external ecosystem development).
