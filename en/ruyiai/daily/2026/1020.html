3.2 Intelligence side: two proposals on kernel read-only mappings and syscall return values, plus C907/E907 boot path updates (10-19)

Date: 2026-10-19　Source: ruyiai-daily issue 10-19, PAGE_KERNEL_RO proposal, syscall return value proposal, SyterKit C907 commit, K3 PCIe patch v7

The RISC-V section of the tech intelligence repo’s 10-19 issue (pushed 10-19 06:16) records four items. First, a proposal on linux-riscv to define PAGE_KERNEL_RO, noting that when RISC-V lacks this definition it falls back to the writable PAGE_KERNEL, leaving mappings that should be read-only — such as HugeTLB vmemmap — with write permission; the proposal includes a reproduction on QEMU virt and a before/after page-table comparison. Second, the syscall restart path needs to check the full return value, fixing a return-value truncation issue. Third, SyterKit sets the mstatus vector state to initial in the C907 image so that the boot state matches the RVV code compiled into the image, while E907 sets up the system mapping before enabling caches. Fourth, the SpacemiT K3 PCIe patch v7 received new review comments questioning the use of the PHY bulk API to control all PHYs across multiple ports at once, pointing out that each port has its own PHY and PERST#, so the resource modeling needs to be re-justified.

5.3 Industry side: SpacemiT V100 server-class RISC-V processor unveiled at the summit (10-19)

Date: 2026-10-19　Source: Phoronix: SpacemiT V100

On 10-19, SpacemiT unveiled the server-class RISC-V processor V100 during the summit. According to Phoronix, the V100 uses a 46-core hybrid architecture—6 XiangShan Kunminghu V2R2 cores plus 40 SpacemiT X100 cores—clocked at 2.2 to 2.4GHz, built on a 12nm process with a 120W TDP, supporting eight-channel DDR5-4800 and 52 lanes of PCIe 5.0, reaching 92 cores in a dual-socket configuration; the vendor claims it is the first chip to fully comply with the RISC-V server specification, supporting UEFI, ACPI, and SMBIOS.

The significance for this topic lies in the platform form factor rather than the chip itself: the server specification makes UEFI/ACPI/SMBIOS mandatory, and the adaptation path for the system software stack differs from that of existing development boards and embedded platforms. The current ruyi 0.54.0 roadmap focuses on K1/K3 toolchain adaptation and ABI compatibility detection, with a support matrix centered on consumer and embedded boards; for a server platform to enter the support scope, new firmware, distribution, and image pipelines would be required. No public action by RuyiSDK or openRuyi regarding the V100 was observed that day.

VI. Trend Observations

6.1 Distribution packaging strategy shifts toward dependency-based packaging: bulk Rust crate imports and Go de-vendoring advance in parallel

Of openRuyi’s 221 commits in a single day, about 200 are newly added packages, the vast majority of them Rust crates; PRs submitted the same day also switch minio and picoclaw from self-contained vendor archives to distribution-packaged dependencies. Both lines point to the same thing: the distribution’s unit of packaging is shifting from “upstream source tree” to “reusable dependency package,” which reduces duplicate packaging and lets CVE fixes ship per package (the concurrent CVE batch was indeed split and submitted by package). For a RISC-V distribution, maintenance cost lies mainly not in the primary packages but in the completeness of the dependency closure; this batch of commits is an effort to fill out that closure.

6.2 Three upstream fork maintenance lines diverge: PyTorch replays daily, LLVM silent for seven days, Triton nightly builds resume

PyTorch’s riscv branch keeps a daily replay (one at 10-19 09:14 in this window, a history rewrite with no new patches), with upstream main synced daily; LLVM’s riscv branch has had no pushes for seven days since 10-12, with two FPGA backend PRs stalled since 10-13; Triton’s nightly builds resumed on 10-19 after a seven-day hiatus. The three repositories represent three states of investment: one pipeline running, one awaiting review, one just resuming builds. Points to watch are whether the LLVM branch restarts on a new upstream baseline, and whether Triton nightlies return to a daily cadence.

6.3 Server-class platforms come into view: UEFI/ACPI/SMBIOS specification requirements change the system software adaptation path

SpacemiT’s V100 brings the RISC-V server specification to a concrete product, and the specification’s UEFI, ACPI, and SMBIOS become hard requirements. This differs from the current RuyiAI/RuyiSDK adaptation path targeting embedded and consumer platforms such as K1/K3: the latter centers on board images, toolchains, and support matrices, while the former requires end-to-end alignment of firmware, boot, and distribution installation chains. The openRuyi firmware line (ruyifirmware, edk2-ruyi) has gone quiet over the past two days; if server platforms become the next-stage target, the effort and priority of this line may need reassessment.
