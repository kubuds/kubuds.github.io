Today’s Focus: Ruyi Firmware Ships Two Releases on Consecutive Days, HiFive Unmatched Enters the Support List (11-07, 11-08)

Date: 2026-11-07, 2026-11-08　Source: Ruyi Firmware 20261107, Ruyi Firmware 20261108, Firmware repo commit list

openRuyi’s UEFI firmware project shipped two releases in two nights. 20261107 was published at 22:21 (Beijing time) on 11-07, and 20261108 at 22:47 on 11-08, marked as a pre-release; each release carries four build artifacts.

20261107 is the feature release for this window, and its biggest change is expanding support from SpacemiT K3 to the SiFive HiFive Unmatched: adding SPI boot, JTAG recovery, NVMe and USB boot, and persistent UEFI variables for that board. Alongside this expansion, the release notes list four supporting adjustments: separate DEBUG and RELEASE packages for each board; PXE and HTTP ISO boot controls added to Platform Settings (off by default); UEFI driver emulation now enabled by default, changeable in Setup or settable as the image default via a configuration script; and both boards now share the Ruyi logo and boot countdown bar, with a file selector added to the Firmware Update screen. The K3 side also gets two usability fixes: improved responsiveness of the graphical console, and reading the RTC on P1 during the UEFI boot phase.

20261108 changes only the K3 line: USB Fastboot switches to EDK2’s shared implementation, usable for firmware updates, readback, and booting EFI applications from memory; it also reports the EDK2 firmware version via fastboot getvar version-bootloader. This change folds a vendor-proprietary flashing channel into the standard EDK2 path — a directly usable interface for production lines and after-sales service, and for developers it means no dedicated tool is needed to confirm the firmware version.

Both releases carry the same compatibility statement: Linux mainline support is provided on a best-effort basis; known framebuffer issues have workarounds given in the release notes. Judging by the three releases in a row from 20261013 to 20261015 in October (CPU mode selection, System Information page), this firmware line has settled into a daily iteration cadence, and the addition of Unmatched is its first step beyond a single chip vendor.

Today’s Highlight: Models compiled for an exact VLEN silently compute wrong results on other VLENs; buddy-mlir switches to load-time validation (11-08)

Date: 2026-11-08　Source: PR #1032, commit 4063c48

PR #1032 addresses a class of failure mode that is worse than an error: no error at all, just wrong results. A RISC-V model built for an exact VLEN has vector code that is only valid for that one VLEN—llc is explicitly told the VLEN (+zvlNb and -riscv-v-vector-bits-max), and the scalable vectors in decode attention are sized accordingly (#1028, #1030). On a different VLEN, the model does not crash; it simply produces incorrect results. The commit message gives a concrete example: on K3, the DeepSeek-R1 rax built with prefill_ime (BUDDY_RISCV_VLEN=1024) lands on an X100 core (VLEN 256) when /proc/set_ai_thread has not been executed, producing wrong results with no warning whatsoever.

The fix moves validation forward to load time. runtime/rvv/BuddyRvvVlen.c is linked into the model library as a constructor; as soon as the library is loaded, it reads vlenb, and if it does not match the exact VLEN used at build time, it prints a message and terminates the process with _exit(1). Using _exit rather than exit is deliberate: running destructors while the loader holds its lock would deadlock. The constructor form covers all loaders, including command-line tools, servers, and tests; generic RVV builds (without an exact VLEN) and other targets are unaffected.

A second commit followed review, changing the check from “based on build variables” to “based on the final llc options.” The original approach had two problems: first, native builds may specify a VLEN via the model’s own LLC_ATTRS, and if BUDDY_RISCV_VLEN disagrees with it, the validated value would not match the actual code; second, it was only linked into the third stage, missing both Qwen3-VL shims (vision and decode) and the split-link path. Now the build script extracts the exact VLEN from the final llc options (the same place VIR lowering reads it), and the third stage, both shims, and split linking all carry it; if the options contradict each other at configure time, the build fails immediately.

Testing is the other half of this change: test_buddy_rvv_vlen.py builds the model library for each VLEN from 128 to 65536; only the host’s VLEN can load it, and all others exit with code 1.
test_buddy_rvv_vlen_cmake.py exercises the configure script across combinations of the build VLEN variable, LLC attributes, prefill selection, and zvl parameters. On-device validation was completed on both X100 and A100 cores of K3, and the repository’s self-checks passed 239 plus 409 items.

1.2 triton-riscv: Add missing riscv64 codegen library for the AMD backend; nightlies now ship x86_64 and riscv64 wheels (11-07)

Date: 2026-11-07　Source: PR #102, nightly aa51ac2, nightly 6895885

PR #102 is titled “Add AMD support,” but its actual content is supplying a missing library rather than adding a new backend. The upstream AMD backend requires libtriton_amd_codegen.so: either a prebuilt copy is downloaded, or it is built against a separately pinned LLVM version—and neither path has a riscv64 variant. The library itself is small and can be compiled in seconds with the LLVM already present in the repo. setup.sh therefore builds it locally and places it at the agreed path when the library is detected missing, and env.sh points TRITON_AMD_CODEGEN_PATH at it—the previous GPU dependency stub redirected all GPU downloads to an empty directory, which also skipped upstream’s fetch of this library, while plugin compilation still reads that path. Without it, the AMD backend refuses to compile anything.

This change also clarifies the repo’s positioning after the plugin refactor: the same tree both produces riscv64 Triton and hosts, at build time, the components other backends need—multi-backend coexistence no longer relies on branch switching. Two nightlies were produced on the new cadence within the window (11-06 12:08 and 11-07 07:52), each with two artifacts: a cp312-abi3 x86_64 wheel (~320 MB) and a riscv64 wheel (~337 MB). Previous nightlies had five to six artifacts; the drop in artifact count is consistent with the stable-ABI single-wheel, backends-folded-into-the-Triton-package direction.

III. Vector Extensions and Operator Optimization

3.1 buddy-mlir: Model library built for exact VLEN plus load-time validation; on K3, accidental execution on X100 cores is blocked immediately (11-08)

Date: 2026-11-08　Source: PR #1032, commit 4063c48

The change spans twelve files, adding 547 lines and deleting 86, with the core being a C file of just over ten lines: runtime/rvv/BuddyRvvVlen.c. It is linked into the model library as a constructor; on load it reads vlenb and compares it against the exact VLEN used at build time, printing a message and exiting on mismatch. The accompanying build-script changes are more involved than the runtime code—buddy_rvv_vlen.cmake now derives VLEN from the final llc options (sharing the same read logic as VIR lowering), buddy_model.cmake compiles that object file once the spec and options are determined, and the third stage, the two Qwen3-VL shims, and the layered linking all carry it explicitly.

The documentation was updated in tandem for the A210 and K3 DeepSeek-R1 deployment notes, clarifying the boundary between “which builds use exact VLEN and which use generic RVV”: the A210 kernels use fixed-length vectors with no VIR, and llc can lower for any VLEN no smaller than 128, making it a generic build; K3’s prefill_ime requires 1024, making it an exact-VLEN build. This boundary previously existed only in build-script comments; it is now enforced at runtime.

3.2 buddy-mlir: Detect the RISC-V host’s VLEN during VIR lowering, fixing the bit-exact failure in riscv64 CI since #1030 (11-08)

Date: 2026-11-08　Source: PR #1037, commit 79ffafd

The second commit by the same author on the same day fixes an error in the opposite direction. When neither rvv-vlen is given nor scalable vectors are enabled, -lower-vir-to-vector sizes fixed-length vectors by host register width, but its host detection covered only x86 (AVX2, AVX-512) and SVE: RISC-V hosts with the V extension always fell back to the generic default (128 bits, 16 registers), regardless of the actual VLEN.

The consequences showed up in tests. Since #1030, the kernels pipeline lowers VIR by host when no llc options are given; the riscv64 CI host has VLEN 256 but was treated as 128-bit: the squared norms of q and k were split into vector<32xf32> segments for summation, in a different order from the bit-by-bit comparison against the vector kernels, so vir decode qk_norm ... same bits evaluated to false. This problem was present in every riscv64 run on main; x86 (AVX-512) got a width of 1024, so it always passed. The author first added a change that pinned rvv-vlen=1024 use-scalable=false in tests only, then reverted it—that would have created a second place to set VLEN outside the llc options, conflicting with the direction of #1032. The final fix detects the RISC-V host during lowering (reading host CPU features and hwprobe) and sizes by the real VLEN, with the test file replaced by a new case in host form.

6.1 The firmware line moves from single-board to multi-board: what Unmatched and PXE boot point to

Date: 2026-11-07　Source: Ruyi Firmware 20261107

Ruyi Firmware had previously iterated almost entirely around SpacemiT K3, with all three October releases filling in K3’s CPU mode selection, system information page, and flashing path. 20261107 is the first to bring SiFive’s HiFive Unmatched into support, and not as a minimal bring-up: SPI boot, JTAG recovery, NVMe and USB boot, and persistent UEFI variables are all provisioned at once — taking a development board from “it lights up” to “it works as a workstation.”

The next question is who supplies the third board.

6.2 The cost of exact VLEN specialization: silent miscalculation is harder to catch than a crash

Date: 2026-11-08　Source: PR #1032, PR #1037

K3’s dual-cluster structure lays RISC-V’s VLEN problem bare on a single machine: the A100 core has VLEN 1024 and the X100 core has VLEN 256, and the same executable run on the wrong cluster won’t crash — it will just compute wrong results. This used to be handled by deployment documentation reminders (write /proc/set_ai_thread first); now it is caught by load-time validation. For a toolchain that delivers models, failing to start is preferable to producing wrong results — that is the value of #1032.

On the same day, #1037 proves the same point from the other side: the host-defined default (128 bits, 16 registers) happens to be equivalent to a large VLEN on x86, but on riscv64 it changes the summation order, and bit-for-bit comparison fails immediately. One patch covers build time and the other run time; what they share is that neither assumes any longer that “VLEN is whatever the compiler decides.” Scalable vectors are supposed to be RVV’s standard answer, but in inference kernels that require bit-level reproducibility, exact VLEN is still the better trade; the cost is that such validation must follow the final llc options rather than build variables.
