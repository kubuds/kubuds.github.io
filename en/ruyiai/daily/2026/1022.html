Today’s Focus: IREE Mainline Lands RVV f16 Multiply-Accumulate MMA; LLVM riscv Branch Rebased and Rewritten After Eight Days of Silence

Date: 2026-10-21　Sources: IREE commit e7490c3b, IREE PR #25000, LLVM riscv branch commit list, two-head comparison

At 16:48 on 10-21, IREE merged the RISC-V V f16 inner_tiled MMA lowering into mainline (PR #25000, 946 lines changed, of which over 800 are tests). This is the second precision tier after the f32 vfmacc.vf path in v3.13.0 released on 10-19: the native f16 enum had already landed in mainline in an earlier commit, and this change adds the two lowering and widening paths—f16 times f16 yielding f16 goes through vfmacc.vf, while f16 times f16 yielding f32 goes through vfwmacc.vf; with only +zvfhmin, these degrade respectively to “widen the accumulator to f32, run vfmacc, then truncate back” and “widen both panels to f32 and run vfmacc”. Tile N is vlen/8, and at VLEN=256 the cost model counts the three paths as 14, 7, and 6 respectively.

The performance data offers something more useful than “supported”: on X60 (VLEN=256), single-threaded inner_tiled under both native f16 and vfwmacc encodings is already faster than the mmt4d ukernel; large shapes at 4 and 8 threads are still slower. In other words, instruction selection on a single core is already in place, and the remaining gap lies in tiling and threading; that tracking item is #24932.

On the same day, RuyiAI’s own LLVM branch ended eight days of silence. Yesterday’s report listed “whether the LLVM branch will restart on a new upstream baseline” as an observation point, and this window provides the answer: the riscv branch was rewritten wholesale at 23:00 on 10-21, with head moving from 0fb2da86 to dd05e5b5; SyncBots advanced the upstream integration to b3b5e33, and the comparison with the old head is diverged (1769 ahead, 26 behind, 300 files differing). The patch series within the branch is fully preserved: BOSC AME extension (#16), Buckyball vendor extension (#20), alignment with the Pebble core ISA (#23), AME path design (#24), xtame design update (#27), AME instruction update (#29), IME builtins to SpacemiT A100 dot instructions (#30), and A100 HP/SP and pack/unpack scheduling (#31, #32). The conclusion should be stated clearly: this is a rebase-and-replay, not new patches; the two FPGA PRs (#25, #28) had their timestamps refreshed in the same batch at 00:59 on 10-22 and remain open.

Placing the two side by side, today’s message is “upstream is moving forward, local work is waiting for review”: on the IREE side, one precision step from f32 to f16 was completed in two days, while on the RuyiAI side the compiler patches stay usable only by rebasing, and the rate at which the review queue is drained remains the real metronome of this chain.

III. Vector Extensions and Operator Optimization

3.1 IREE: RVV f16 vfmacc and vfwmacc plus Zvfhmin fallback land on main (10-21)

Date: 2026-10-21　Source: commit e7490c3b, PR #25000, performance tracking #24932, f32 version PR #24933

This commit adds a lowering path for RISC-V V f16 inner_tiled MMA, reusing the lowerRiscvVFmaccLike introduced in #24933 and the hoisted accumulator legalization, with Tile N set to vlen/8. Encoding selection is split into three tiers by extension availability: f16 × f16 → f16 with +zvfh uses vfmacc.vf; f16 × f16 → f32 uses the widening vfwmacc.vf; with only +zvfhmin, the two paths respectively go through “extf the accumulator to f32, f32 vfmacc, truncf back” and “extf both panels, then f32 vfmacc”. When both tiers are legal, the native path is taken by enum order. At VLEN=256 the cost model reports intrinsics_m 14 (native), 7 (vfwmacc), and 6 (both zvfhmin fallbacks).

On the performance side there is only a directional conclusion: on X60 (VLEN=256), single-threaded inner_tiled with native f16 and vfwmacc is already faster than the mmt4d ukernel, while large shapes at 4 and 8 threads remain slower. Tests land with the commit, including a 187-line encoding materialization case, a 414-line lowering case, and build changes for the e2e matmul, giving directly regressable coverage.

3.2 IREE: scalable-vector distribution tiling aligned to base × vscaleMax (10-21)

Date: 2026-10-21　Source: commit 9ea0f2f2, PR #24849

The LLVMCPU backend has another scalable-vector change the same day: aligning scalable-vector distribution tiles to base * vscaleMax. This kind of alignment is routine legalization on the VLA (vector-length-agnostic) path — tile sizes must be divisible by an integer multiple of the hardware’s actual VLEN, otherwise tail-block degradation occurs on narrow-VLEN hardware. This change and the f16 MMA in 3.1 both belong to the CPU backend, and together they constitute the current RISC-V V progress in IREE.

VI. Trend Observations

6.1 Dependency closure enters its endgame: Go shifts from “de-vendoring” to “filling in import paths”

The package-addition threads in the previous three issues were laid out separately: Python filling out the full fsspec cloud-storage family, Rust filling out the crate closure, and Go starting on de-vendoring. This issue, the center of gravity on the Go side’s 51 commits has clearly shifted later—first filling in base dependencies (etree, yaml, gnostic, tabwriter, and about ten others), then filling in the import paths for the k8s trio plus moby-sys and smarty-assertions, and only finally landing the three genuinely “build without vendored dependencies” commits for sonobuoy, umoci, and go-mtree.

The ordering itself shows that the completion condition for de-vendoring is not deleting the vendor directory, but making every depended-upon module resolvable in the distribution under its original import path; without filling in the missing import paths, deleting vendor simply causes an immediate compile failure. So “filling in import paths” is the last mile of this round. The direct implication for RISC-V users is that container image tools and conformance testing tools go from “packaged with the source” to “packaged per distribution dependencies,” improving both build reproducibility and the propagation path for security updates—future CVEs only require upgrading a single Go module, not rebuilding the whole package.

6.2 Two riscv branches fully rewritten on the same day: replay has become routine operations, review remains the bottleneck

This issue, the riscv branches of pytorch and llvm-project each underwent a full-branch rewrite on the same day: pytorch at 03:00 (the third consecutive day), llvm at 23:00 (a rebase after eight days of silence). The common features are uniformly rewritten committer timestamps, an unchanged set of patch titles, and SHA values that expire daily; the difference is cadence—pytorch is a daily-updated baseline, llvm rebases on a chosen schedule, and after rebasing the diff against the old head reaches 300 files, almost all from the new upstream.

The engineering significance of this approach is decoupling “tracking upstream” from “maintaining local patches,” at the cost of untraceable history. Any downstream that references by SHA (image builds, CI caches, issue reproduction) will break daily or after each rebase; these two branches should be versioned by their set of patch titles rather than by SHA. More noteworthy is that the patches themselves added nothing in this window: pytorch’s seven open PRs only refreshed timestamps, and llvm’s two FPGA PRs likewise only refreshed timestamps. The replay mechanism is already solid; the actual metronome has become the digestion rate of the review queue.

6.3 RVV backend fills in f16 before discussing throughput: the signal from IREE’s precision-coverage ordering

Looking at the 10-19 f32 vfmacc.vf (v3.13.0) together with the 10-21 f16 vfmacc/vfwmacc (#25000), IREE climbed one precision step in two days on the RISC-V V inner_tiled MMA path, reusing the same lowerRiscvVFmaccLike and the same accumulator legalization both times. The order is to first guarantee a correct path (f32), then pick the fastest one according to extension availability (native f16, widened f16, +zvfhmin fallback), with the cost model pricing the three paths separately.

Measurements on the X60 make the bottleneck location clear: single-threaded is already faster than the mmt4d ukernel, while 4-thread and 8-thread are still slower, indicating that once single-core instruction selection is in place, what remains is tiling and threading. For tilelang-riscv and triton-riscv, this is a roadmap that can be compared item by item—the Tile N = vlen/8 derivation and the cost model’s tiering are both worth comparing on the same basis in their own lowering, rather than just checking “whether f16 is supported.”
