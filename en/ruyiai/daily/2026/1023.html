3.3 Paper: Restructuring FlashAttention on Long-Vector Processors Yields 1.84–2.08× Measured Speedup (10-21)

Date: 2026-10-21 (slightly before this window’s start; included because the arXiv index first made it visible within this window)　Source: arXiv 2610.29489v1

“Reorienting the Vector Axis: Restructuring FlashAttention for Long-Vector Processors” (Emmanuel Irabor, Marc Casas) ports PyTorch’s CPU FlashAttention kernel to a RISC-V CPU with 2KB vector registers, and starts with a blunt baseline: only 16.2% of peak floating-point throughput.

The cause analysis is specific. The original kernel advances query row by row: the multiply with V is vectorized along the 64-element head dimension; softmax’s per-row max and sum are reductions that “collapse an entire register into a scalar”; and the polynomial coefficients of the software exponential function compete with tile data for vector registers, causing spills to the stack. Together, these three keep vector register utilization low.

Neither fix changes the algorithm or the numerics. The first transposes the score tile together with the running output so that queries fall on a linear contiguous axis—so a single parameter, “how many queries fit in a tile,” uniformly determines the vector length of every kernel section, configurable per machine, and the two reductions disappear naturally. The second moves the polynomial coefficients into scalar registers, eliminating spills and cutting softmax’s vector memory instructions by 78.7%.

Measured results: at head dimension 64, the two changes together bring the full-kernel cycle count down to a 1.84–2.08× speedup, raising floating-point utilization from 16.2% to 29.7%; an FPGA with the same design ranks the two changes consistently and benefits more, reaching 2.71×.

The significance for this stack lies in the method, not the numbers: vector-length adaptation and register pressure are the structural problems in triton-riscv’s and tilelang-riscv’s RVV lowering—not “whether intrinsics exist.” The paper’s “match queries per tile to the machine” and IREE’s choice of vlen/8 for Tile N are the same class of decision and can be compared directly on equal terms.

V. Community, Events, and Official Homepage

5.1 Summit retrospective post published: two talks, six posters, seven live demos (10-22)

Date: 2026-10-22　Source: Forum post #2893, Ruyi package manager poster

The forum published a retrospective post on the 6th RISC-V China Summit at 11:31 on 10-22. Scale figures given in the post: over 3,600 in-person professional attendees, 10 RuyiSDK team members on site, in the form of two technical talks, six technical posters, and a standalone D15 booth.

The two talks were “RISC-V Course Porting Methods and RuyiSDK Ecosystem Building” (Luo Yunxiang) and “Mastering the RISC-V Vector Extension: Practical Go Optimization on RVV” (Meng Zhuo, Zhu Junxian). The former proposed three main threads—”open the door, pave the road, teach the people”—with the approach of running simulation and visualization on the host or in the cloud while pushing drivers and inference down to the board. The latter focused on the engineering problems of connecting managed-language runtimes to RVV, including vector-length agnosticism, assembly stubs, and inlining optimization.

The six posters concentrated their information in numbers. VI. Trend Watch

6.1 Replay moves from “scheduled” to “daily”: llvm rebases two days in a row for the first time

Our read in the previous two issues was that pytorch rebases daily while llvm rebases on a schedule: pytorch had rewritten at 03:00 three times in a row, while llvm had rebased only once after eight quiet days. This window overturns the second half of that judgment—llvm rewrote the entire branch again at 23:00 on 10-22, exactly one day later.

The difference in span between the two rebases explains the mechanism: yesterday’s rebase, ahead 1769 and 300 files, was a concentrated catch-up on eight days of upstream backlog; today’s, ahead 275 and still 300 files, is routine catch-up on a single day’s increment. The branch has entered a state of “moving the baseline forward a small step each day,” converging on the same operational model as pytorch.

The cost is unchanged: committer timestamps are uniformly rewritten, SHAs expire daily, and any downstream that references these branches by SHA goes stale that same day—so these two branches should be read by their set of patch titles, not by SHA. The benefit is also unchanged: no new patches were added; all seven open PRs in pytorch and two in llvm only refreshed their timestamps, and actual progress is still determined by the review queue.

6.2 openRuyi enters a spec-completion phase: 54 cleanup commits outweigh 22 upgrades

Of the 81 commits in this window, 54 are the same kind of normalization change (adding source checksums, switching to %autochangelog), covering a run of package names from m to x; actual version upgrades number 22, a ratio of 2.5 to 1.

This differs from the previous phase of “filling in the dependency closure”: back then, Go dropped vendoring and Rust added crates, with the goal of making packages build at all; what is being cleaned up now is auditability and automated bookkeeping—source checksums make build inputs verifiable, and %autochangelog makes changelogs generated from commit history rather than written by hand. The user-perceivable benefit lands on the security-update path: only once a unified path works will CVE fixes propagate along a single route. The ISAC source-sync problem (see 2.6) is a reminder of the other side—however good the specs, users still see no updates when the release channel is blocked.

6.3 The distro begins laying down a desktop and virtualization validation stack

A group of proposals pointing the same direction has appeared in the open PR queue: qemu enabling GUI test features (#1421), adding virglrenderer (#1415), ovmf supporting fwupd (#1436), adding ydotool (#1457), and fixing a man-page conflict in xorriso (#1489).

The five items belong to virtualization, graphics virtualization, firmware update, input automation, and the optical-disc image toolchain; together they point to one thing: running a full desktop on RISC-V and validating it automatically. This is the other end of the same requirement as the “AI-driven IDE graphical testing” shown at the summit—for a test framework to drive a real interface, it first needs scriptable input and a virtualizable graphics stack. Desktop support was previously a weak spot for RISC-V distributions; this batch of proposals breaks it into tasks that can be merged one by one.

6.4 The extension landing path takes shape: compilation, simulation, and operators arrive in sequence

Taking AME as an example, a complete path from proposal to usability is visible this week: first the backend design and instruction-set definitions (LLVM #16, #24, #27, #29), then the lowering and scheduling implementation (#30, #31, #32), while the simulator provides executable semantics (QEMU ame-0.6), and finally the operator library provides testable kernels and a validation suite (AME-operator).

The P extension follows the same path but is already past the halfway point: QEMU covers all instructions, GCC support is updated to 0.6, and on the LLVM side intrinsics such as mulq, multiply-high accumulate, sati/usati, and Packed Pair are being merged upstream in batches. By comparison, the P extension lacks application-side benchmarks, and AME lacks real hardware.

This order is itself worth recording as a method: without a simulator you cannot validate the compiler, and without an operator library you cannot validate the simulator. Before all three are in place, talking about performance is meaningless; once they are, the bottleneck shifts to hardware and real measurements. This week’s progress is “complete,” not “faster.”
