Today’s Highlight: RuyiTuner v1.8 Released, Real-Compilation Comparison Stage Completed Over the Weekend, Three-Stage Pipeline Takes Shape

Date: 2026-09-25 ~ 2026-09-27　Source: v1.8 Release, CHANGELOG, real_compile split commit

RuyiTuner is the Ruyi community’s LLVM-oriented compiler tuning tool, which automatically searches for pass sequences that maximize code size reduction based on “optimization synergy analysis.” At 09:06 Beijing time on the morning of 09-25, the tool released v1.8 (tag pointing to commit a032c28c “Add ruyi-cc to use pass seq into project”). The updates consolidated in v1.8 relative to v1.7 (09-17) include: the --search_scope project mode for searching a common pass sequence across the entire project (aggregate-fitness GA), the --max-path-length parameter, and the scripts/ruyi-cc.sh compiler wrapper script—which plugs the optimal sequence into the project’s normal compilation flow (make CC=scripts/ruyi-cc.sh), with the sequence nested according to the scoring convention, code-generation options such as -fPIC / -mcmodel forwarded to llc, and full compilation, linking, and compress/decompress functional verification completed on bzip2-1.0.2. Of these, the project-level search and --max-path-length portions were tracked separately in earlier windows (09-22 / 09-24).

Development did not stop after the release: over two days, 09-25 (7 commits, 09:06 ~ 19:31) and 09-27 (6 commits, 16:11 ~ 18:22), the v1.x branch saw 13 consecutive commits (merged into main twice), advancing the 1.9 version line to the point where “real-compilation comparison” took shape—first persisting the project-level search sequence to disk (09-25 17:04), then adding the stage that “actually compiles the source with the optimal sequence and reports the size reduction rate” to the main entry point (18:27), and subsequently folding the capability in from the temporary wrapper script and deleting scripts/ruyi-cc.sh (19:31); on 09-27 the stage was split into a standalone script real_compile.py (18:10), forming a three-stage pipeline together with train.py and run.py (stage titles 1/3 through 3/3), and completing: renumbering outputs by stage (enumeration files changed to the Step1 prefix, sequences and results changed to the Step2 prefix), no longer persisting intermediate files for synergy-pair lookup (switched to in-memory passing), --dataset supporting a single .c / .i source file, the GA’s obj-size scoring switching to the pic relocation model (aligning with clang’s default convention on x86_64), the real-compilation stage reusing the C→IR cached .ll files, extracting x86 / RISC-V code size data by project, and updating the schematic diagram to V2.0.

As of the end of the window, 1.9 has not yet been released (the latest Release is still v1.8), and its changes have been fully written into the CHANGELOG “1.9 version changes” section; the tool’s version and architecture generality remain unchanged (not bound to an LLVM version or target architecture, with the target determined by the target triple of the input IR). This round of refactoring consolidated the previous form of “two-stage search + external compilation wrapper script” into a built-in three-stage pipeline.

V. Trend Observations

5.1 Weekend Exception: A High-Frequency Iteration Window for a Solo Maintainer

RuyiTuner was the only high-frequency development surface in this window — on 09-25 and 09-27, the same maintainer pushed 13 consecutive commits and merged into main twice, closing out a cross-window refactor (from a temporary compile wrapper script to a built-in real compilation stage) into a three-stage pipeline. Looking back at the release cadence: v1.6 (08-31) to v1.7 (09-17) spanned about two and a half weeks, v1.7 to v1.8 (09-25) took 8 days, and 1.9 changes are already in flight — the tooling line iterates at a “usable increment per week” pace, in contrast to the quiet of the main stack in this new window.

5.2 “Release-Maintain” Cadence: Main Repo Silent After 0.53.0

In the first full window after the ruyi 0.53.0 release (09-24), the main repo saw only one test submodule follow-up (#503); the three issues related to the 0.53 release cycle (#495, #498, #501) are all now closed, leaving only the long-term tracking item #401 (PyPI installation readiness tracking on RISC-V) still open. Combined with the preview in issue 077 of “next version at the end of October,” we are currently in a quiet maintenance stretch between versions — release quality focus shifts to community installation feedback.

5.3 The RT-Thread Line of the Support Matrix Continues to Expand

The only merge into the support matrix in this window was the RT-Thread 5.3.1 report for ESP32-C3; over the past two weeks, the matrix’s RISC-V board coverage has come mostly from the two RTOSes RT-Thread and Zephyr (CH32V307 and ESP32-C3 updated consecutively), while three entries for the Milk-V Duo S platform (RT-Thread / RT-Thread Smart / Zephyr) remain queued. The OS-level test catalog for RISC-V development boards continues to densify.

5.4 Gaps and Focus Points in This Window

Gaps: the RuyiAI-Stack main stack (pytorch / triton-riscv / llvm-project and other feature lines) has been silent for a second consecutive week, with the divergence between the framework side waiting and the tooling side running hot now in its second week; the technology intelligence repository is in its second week of interruption (four consecutive issues absent since the 09-24 issue); the forum and external news sides are entirely silent. Focus points: first, the openRuyi 2026.09 monthly release announcement (end-of-month window); second, the merge cadence of the three pending support matrix entries; third, the follow-up content of llvm-project PR #168 and the two pre-research branches; fourth, whether ruyiai-daily resumes publishing; fifth, community feedback on ruyi 0.53.0 and new issue activity.
