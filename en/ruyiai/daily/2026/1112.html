Today’s Focus: RuyiSDK Biweekly Progress Issue 080 Published on the Community Forum, Covering Three Tools and Six Compiler Upstream Merges (11-11)

Date: 2026-11-11　Source: Biweekly Progress Issue 080 (Community Forum), wechat-articles summary submission #405

Issue 080 was posted to the RuyiSDK community forum on 11-11 at 17:53 (Beijing time), six days after the in-repo draft of 11-05. This issue closes out the “three tool releases”: package manager 0.54.0, Ruyi Imager 1.1.0, and VS Code extension 0.1.7 are all named, of which 0.54.0 and Imager 1.1.0 are formal releases within this window, while extension 0.1.7 is in fact the 09-28 version, with 0.1.8-beta.1 (10-30) already following; it is carried over here per the draft’s wording, and readers should not treat it as a new version.

The package manager item is the same 0.54.0 as in the previous daily report; what Issue 080 adds is the testing angle: 0.54.0-beta.20261102 and extension v0.1.7 were judged to meet the exit criteria, see the test report for details; on the toolchain side, CI is not yet run on Python 3.15 pending pygit2 support for Python 3.15, which is the only explicit deferral in this issue. The next version is set for late November.

The compiler section is the most substantive content in this issue. Three RISC-V GCC backend optimizations entered the GCC development mainline on 10-27 (r17-5638, r17-5639, r17-5640): Zba adds combined recognition of shift-add with integer division and remainder; Zbs exploits bclr’s own shift-index semantics to eliminate redundant masks, improving code generation for RV32/RV64 bitmap operations; Zbkb fixes the cost model and match priority of packh—previously, when Zbb and Zbkb were both enabled, the better instruction could not be selected. All three come with regression tests. On the RISE-CI side, container services and GitHub Actions were connected, a multilib build scenario check was added, and integration of LLM-based evaluation of CI errors is planned; performance benchmarking is moving toward SPEC CPU 2026, starting with environment and resource assessment, which has already identified a memory shortfall for running the full SPECspeed 2026 on K3.

On the LLVM side, six PRs for the RISC-V P extension and GlobalISel have been merged upstream (#235306, #235245, #234450, #237815, #238214, #234484), focused on accumulation merging for packed multiply-accumulate, branch elimination for 64-bit funnel shifts on RV32, and widening of narrow-type leading-zero and trailing-zero counts under XTHeadBb. RuyiSDK’s own LLVM branch has two more: preliminary support for the RV32/RV64 matrix extension per the Ztt specification and intrinsics documentation v0.6 (#169, covering assembly/disassembly, Clang types and intrinsics, IR and code generation, M/A/CC register allocation and spill handling), and GitHub Actions CI for the AME branch (#170).

One item each on the runtime and language sides is worth noting: OpenJDK’s JEP 544 (AOT static compilation) RISC-V port passed functional tests, met expected performance gains, and has been merged into the mainline (#32311), with ten additional RISC-V-related PRs entering the mainline and three backported to 17u/21u/25u; the V8 review list includes “Allow vlen=1024” (CL8585179), pointing to the same hardware fact as the two K3 fixes in this issue’s buddy-mlir. On the Go side, five CLs were submitted, of which the RVV implementation of GreenGC’s filterNil has been merged.

Community and content: packages-index added GNU toolchain support for SpacemiT K1/K3 and supplemented ABI compatibility information for some packages; the development board support matrix added Chinese and English reports for Milk-V Jupiter2 with Bianbu 4.0.1 and SpacemiT K3 Pico-ITX with Bianbu 4.0.8 LXQt, and updated the Ubuntu 24.04.5 report for VisionFive 2 Lite; the examples repo added Dhrystone and SiFive Kernel Library Chinese examples for HiFive Premier P550, a llama-server deployment example for Jupiter2, and extended the K3 ROS 2 course entry to chapters 11 through 15 (scan matching, SLAM, and localization).

Today’s Focus: buddy-mlir Fixes Lane Loss in Reductions on VLEN 1024, Twenty-Five Tests Go from Wrong to Right (11-11)

Date: 2026-11-11　Source: PR #1051

PR #1051 was merged on 11-11 at 23:51 (Beijing time), fixing a bug that only surfaces on long-vector hardware: performing vir.reduce on a scalable vector of width 1 leaves only lane 0 in the result. The cause is not VIR’s own canonicalization but downstream—vector.reduction’s ElideSingleElementReduction treats vector<[1]xT> as a “single-element” vector, rewriting it to vector.extract of lane 0 combined with the accumulator, and the remaining vscale - 1 lanes vanish.

The trigger condition is VLEN 1024: a region of 16 f32 values is vector<[1]xf32> (vscale 16) in a single vector, whereas at VLEN 128 and 256 it is vector<[4]xf32> and wider, never reaching this path. The author measured on the A100 core of SpacemiT K3, where all 25 reduction tests produced wrong values—for example, amax over 512 values yielded 1.853 instead of 4.101; the same tests pass on the CI riscv64 runner (VLEN 256). This is precisely why such defects are hard to catch: CI’s vector width coverage does not reach the width of shipping hardware.

The fix bypasses canonicalization and constructs the reduction directly with the LLVM intrinsics that vector.reduction ultimately lowers to—llvm.vector.reduce.fadd for floating point with the accumulator as the starting value, and maxnum plus the accumulator for fmax—changing both lowering paths of vir.reduce. The author notes this is the same workaround as splat’s broadcastTo. Accompanying tests go into the VIR cases under tests/Conversion, and check-buddy passes on both x86 (using main’s LLVM) and SG2044 natively.

What this means for the stack: Triton-RISCV’s reduction operators on K3 (amax, max, mean, sum, cumsum, rms_norm, mse_loss, vector_norm, euclidean_dist, attention) were previously silently wrong on this board, not crashing. Only after the fix does discussing performance become meaningful.

III. Vector Extensions and Operator Optimization

3.1 Strip-Mined set_vl Lane Remainder Steps Down by Half-Width, YOLOv8 Hotspot on K3 Emerges from Scalar Dot Product (11-11)

Date: 2026-11-11　Source: PR #1050

#1050 was merged on 11-11 at 20:12. Previously a strip-mined vir.set_vl ran the main loop only at the selected width, dumping all remaining lanes into a scalar tail loop; regions with fewer lanes than one vector were entirely scalar. Running f32 YOLOv8 on K3’s A100 core (VLEN 1024), the pose head’s 51 output channels yield vectors of 64 lanes, and the result was that the hottest loop (5% of total model time) was a scalar flw plus fmadd.s dot product, with scalar floating-point instructions accounting for 39% of the 150,000 perf samples.

The fix steps the lanes after the main loop down successively to half-width and quarter-width, each level used at most once and in lane order, before finally handing off to the scalar tail loop, which retains only the portion below the minimum width (fixed 2 lanes, scalable [1]). There are no masks: scalable vectors check the remainder at runtime with scf.if, fixed-length vectors resolve it at compile time when vl is constant, so the affine tail loop’s bounds remain affine; when vl is dynamic, the scalar tail is retained.

Numerics are unchanged—each lane computes the same operation, and the lane order seen by ordered reductions is also unchanged; the author verified bit-identity using an FNV hash of the forward output on K3. This fixes performance, not correctness, but what it buys is that the hottest code on long-vector hardware finally goes to the vector unit.

4.1 Preserve Scaling Factor When Cloning Dynamic Vector Types (11-11)

Date: 2026-11-11　Source: PR #1048

#1048 was merged on 11-11 at 08:32, with the title being the change itself: carry the scaling factor along when cloning dynamic vector types. This is the wrap-up of the previous issue’s 4.3 (printing, parsing, and verification of dynamic vector types)—that batch made the scaling factor visible and verifiable at the text level, and this commit ensures it is not lost on the type cloning path. 5.2 China Science Daily front page covers the Institute of Software’s decade, with Ruyi community and the kernel homology plan mentioned (11-10)

Date: 2026-11-10　Source: China Science Daily report

The 11-10 front page of China Science Daily published a ten-year retrospective of the Institute of Software’s RISC-V basic software team. Several verifiable facts are worth noting: the Ruyi community was founded in November 2024; as of the end of 2025, code contributed by industry partners such as Alibaba and ZTE under the “RISC-V kernel homology” plan exceeded half of the total; and the RVA23 releases published by openEuler and openKylin all adopt the results of this homologous kernel work. The article also mentions that the software migration tool follows a “neuro-symbolic fusion” path (program analysis and formal verification as the foundation, large models for efficiency gains, and engineers’ experience distilled into rules and knowledge bases to delineate boundaries), already deployed in communities such as openEuler; and that a master’s student added a RISC-V backend and vector instruction optimizations to OpenCV, which were merged into the official mainline.

The “open-source AI compiler project for RISC-V” mentioned in the article is buddy-mlir, whose VIR commits mostly come from this team. This report provides the organizational background of this stack: the Ruyi community, kernel homology, and the compiler and migration tools all come from the same team; the changes scattered across different repositories in the daily briefings are, at the institutional level, one and the same line.

VI. Trend Observations

6.1 Release chain before features: what triton-riscv fixed this week was “can we ship a package at all”

Of the three merges in triton-riscv during the window, two were CI and release scripts and one was a README note on installation prerequisites — zero functional changes. The nightly build’s own release notes are also about git authentication on the runner. This is not stagnation; it is a project that just graduated from “runs on real hardware” to “GPU backend enabled by default” filling in reproducibility: anonymous git traffic on the self-hosted riscv64 runner cannot obtain authentication, which looks like a minor infrastructure issue but in practice determines whether a nightly package comes out every day.

The contrast with RuyiSDK makes this clear: the package manager can turn ABI compatibility into a pre-install warning because its release chain is already stable enough for that kind of fine-grained work. triton-riscv is on the same path, just a few steps behind.

6.2 VLEN 1024 is becoming a shared pressure point for compilers and runtimes

Within a single day, three independent pieces of evidence pointed to the same parameter: buddy-mlir’s reduction lane loss only shows up at VLEN 1024 (VLEN 128 and 256 both pass), the motivation for narrowing the strip-mined remainder comes from 64-lane vectors on the K3 A100 core, and “Allow vlen=1024” appears in V8’s reviewer list. Previously this kind of discussion stayed at the architectural parameter level; now it has landed on “which test fails at which width.”

The direct requirement for testing is to cover shipping widths: the original CI riscv64 runner is VLEN 256, which happens to pass on the #1051 issue. That lesson is worth more than the few lines of fixed code — any reasoning involving vscale must be verified at 1024.

6.3 The biweekly progress draft and publish dates are six days apart; read its items separately

Issue 080 took shape in the repo on 11-05 but was only posted to the forum on 11-11. So in the same text, 0.54.0 and Imager 1.1.0 are “released” (things that happened on 11-10), and plugin 0.1.7 is also “released” (a 09-28 event, followed by 0.1.8-beta.1 on 10-30). Reading it straight through by publish date makes it easy to mistake three tools for a triple launch on the same day.

A workable reading is two-layered: for tool versions, look at Release dates; for compiler and runtime items, look at upstream merge dates (the three GCC items are dated 10-27). The daily briefing has already been split along these lines, and readers comparing against the biweekly progress should do the same.
