Today’s Focus: Buddy Compiler 0.1.3 Goes Stable — Ten of Sixteen Commits Are RVV Scalable Vectorization, Release Notes Mention Only the Server ABI (10-31)

Date: 2026-10-31　Sources: BUDDY MLIR 0.1.3, commit diff between v0.1.2 and v0.1.3, PR #999 rvv-vlen, PR #1003 scalable vector width selection

At 07:01 on 11-01 (Beijing time), buddy-mlir shipped stable release 0.1.3. The previous stable release was 0.1.2 on 10-25, with five nightlies in between. The release notes expand on exactly one item: the new buddy-server ABI (#1015), which consolidates the per-modality model plugin handles into a unified interface, plus unified paths for loading, status queries, invocation, streaming, and cancellation.

But pulling the commit diff between v0.1.2 and v0.1.3 shows this release actually packs sixteen commits across 136 files, ten of which are a single block of RISC-V vectorization work under [midend][VIR]:

  • #999 introduces (rvv-vlen), making scalable vector length a vectorization target attribute;
  • #1000 counts live vectors in nested loops as input to vector width selection;
  • #1002 makes scalable strip-mining loops step by vscale;
  • #1003 selects scalable vector widths for RVV;
  • #1004 lowers set_vl with results into scalable vectors;
  • #1005 handles multi-dimensional dynamic vector bands with results in set_vl;
  • #1006 adds dynamic vector row-level vir.shuffle;
  • #1007 unifies the index conventions of vir.load / vir.store;
  • #1008 automatically infers the width of index vectors;
  • #996 adds vir.from_vector and reduces reassociation.

Two more commits belong to the VIR line but not under the [midend] prefix: the VIR dialect implementation of decode attention ([frontend][tools]) and Python bindings for VIR (#1009). In other words, twelve of the sixteen commits touch the vector dialect layer, yet the release notes say not a word about RISC-V or RVV.

This gap is worth noting because it changes the answer to the question “where is the RISC-V progress in this stack?” The prior assessment in earlier issues was: buddy-mlir’s RISC-V work mainly flows through nightlies, stable releases are occupied by general work like ABI refactoring, and downstream can only anchor to nightly tags to get RVV changes. 0.1.3 proves that assessment only half right — the stable release did absorb the RVV block, but the release notes were not updated to match, so anyone reading the release page would think 0.1.3 is just a server-side refactor, when in fact it is a release with significantly advanced scalable vectorization capability.

The direct implication for downstream: triton-riscv raised its dependency anchor to the dev20261030 nightly at 13:15 on 10-31 (PR #91). That nightly predates the 0.1.3 stable build, but the two share the same content (0.1.3 was cut from the main branch head on 10-29), so those ten RVV commits are already live downstream; what hasn’t caught up is the fact that “the anchor still says nightly tag” — under the current renovate cadence, switching to release/v0.1.3 will take another round.

A caveat on scope: these ten commits focus on scalable vectorization of the VIR dialect, i.e., the lowering path from set_vl to scalable vectors — not end-to-end model performance data; the release notes provide no benchmarks either. The advance in vectorization capability is verifiable; how fast it runs has no answer this issue.

III. Vector Extensions and Operator Optimization (VecIntrinBench / IntrinTrans / FBGEMM)

3.1 All three vector repos silent this period; latest commits stalled at 02-13, 06-25, and 07-13 respectively

Date: 2026-11-01 (status)　Source: VecIntrinBench, IntrinTrans, FBGEMM

None of the organization’s three vector-themed repositories received any in-window commits this period, and their latest commit times fall in three different quarters: VecIntrinBench stalled at 02-13, IntrinTrans at 06-25, and FBGEMM at 07-13. The three respectively cover vector intrinsic benchmarks, intrinsic translation, and quantized operator backends, and originally formed a triangle of “what to measure, how to translate, how to implement operators.”

That triangle is now stalled as a whole, and the stall points differ, indicating this is not a single unified project termination but rather each cooling down naturally. VecIntrinBench having been idle for nearly nine months is the most notable case—if a vector intrinsic benchmark library goes without updates for a long time, the coverage it measures drifts further and further from the set the compiler actually supports.

3.2 Operator work has shifted entirely to the triton-riscv lowering path (10-31 to 11-01)

Date: 2026-10-31 to 2026-11-01　Source: PR #93, PR #94, PR #95, PR #96, PR #97

Since all three dedicated repos have stalled, the actual operator-layer work front can only be read from the triton-riscv PR queue. The five newly opened PRs this period all revolve around “information preservation,” broken down as follows:

#93 handles masks on scalar load/store—the scalar memory access path is the most prone to dropping masks as constant-true during lowering; once dropped, conditional scalar reads and writes become unconditional in the structured IR, and out-of-bounds accesses won’t error but instead read dirty data. #94 handles lane offsets in mixed pointers, i.e., when a pointer expression has both a base address and per-lane offsets, the analysis phase keeps only the base address and treats offsets as constants; #96 handles incomplete tensor masks, i.e., broadcast semantics when the mask shape is smaller than the tensor shape; #97 handles stacked zero strides, i.e., when multiple dimensions all have zero stride, they may be collapsed into one dimension after lowering.

#95 is the only one that adds capability rather than preserving information: lowering tensor gather. Previously gather could only go through the unstructured path, with no corresponding implementation on the structured path; #95 fills that gap.

The common backdrop for all five is the same thing: correctness at this layer is exposed by “bringing real operators up and running them,” not by regression tests. The eight PRs accumulated over three weeks (three on 10-29 plus five this period) all fall into this category. The mechanism works but is costly—each batch of operators brought up requires fixing a string of edge cases, and the verification strength of the fixes varies (of the three on 10-29, one ran the full lit suite of 291 items, one ran only targeted regressions, and one ran only a single file).

3.3 Performance mainline #85 stalled at 10-18, in stark contrast to the five lowering-path PRs

Date: 2026-10-18 (status)　Source: PR #85 softmax and matmul optimization

#85 “softmax and matmul optimization” has not been updated since 10-18 23:55 and remains in place this period. It is the repo’s only open PR explicitly targeting performance, and it forms a clear contrast with the five lowering-path PRs: five PRs a week on the correctness side, no movement on the performance side for half a month.

For a stack meant to “run real models,” this contrast has concrete consequences: correctness fixes like masks, offsets, and strides determine “whether it computes correctly,” while softmax and matmul optimization determine “whether it computes fast enough.” The former is advancing rapidly while the latter sits idle, meaning that even if all 604 operators are brought up, end-to-end performance remains at the level of three weeks ago.

IV. Buddy Compiler Updates

4.1 BUDDY MLIR 0.1.3: Sixteen Commits, One Hundred and Thirty-Six Files, Release Notes Cover Only the ABI (10-31)

Date: 2026-10-31　Source: BUDDY MLIR 0.1.3, commit diff v0.1.2…v0.1.3, PR #1015 buddy-server new ABI, PR #1009 VIR Python bindings

The commit diff for 0.1.3 corroborates what was already covered in “Today’s Highlights”; here we add three observations not in that section.

First, this release’s file footprint is larger than its commit count suggests: sixteen commits touched 136 files, a substantial share of them from the interface refactor in #1015 (four new runtime headers added, four sets of per-modality plugin handles and their corresponding unit tests removed). In other words, 0.1.3 packs two things at once—ten consecutive advances in the vector dialect, and a plugin-system consolidation spanning more than seventy files—overlapping in time (the ten VIR commits from 10-25 to 10-27, #1015 on 10-29) but reviewed separately.

Second, the commit [frontend][tools] Implement the decode attention in the VIR dialect is easy to overlook, but it points in a different direction from the earlier VIR lowering: writing decode attention as an implementation in the VIR dialect amounts to building a direct path from dialect to vectorization for the specific workload of “attention decoding.” This is the first commit in VIR’s move from a “general-purpose vector dialect” toward “workload-specific optimization.”

Third, the VIR Python bindings (#1009) mean this dialect can be constructed and inspected from the Python side; the direct benefit downstream is that projects like triton-riscv can generate VIR at the Python layer for unit validation without going through the full compilation chain each time.

4.2 Nightly Builds and Downstream Anchors: Three-Hop Latency Closed Within Two Days, Anchor Still on Nightly (10-31)

Date: 2026-10-31　Source: nightly dev20261030, triton-riscv PR #91, Releases list

A previous issue noted a fixed-latency structure: buddy-mlir merge → next-day nightly build → renovate dependency update → triton-riscv merge, with the three hops typically taking one to two days. This issue the chain ran through end to end, so we can check the actual time spent at each step:

#1015 merged to main on 10-29 at 15:08; the nightly dev20261030 was published on 10-30 at 08:49 (including #1015); renovate’s #91 merged into triton-riscv on 10-31 at 13:15. From merge to downstream pickup, two days and five minutes in total, consistent with the “one to two days” estimate.

But the shape of the anchor hasn’t changed: triton-riscv still depends on the dev20261030 nightly tag, not the official release/v0.1.3 published on 10-31 at 23:01. The two tags share the same source (0.1.3 was cut from the main-branch head on 10-29, and so was dev20261030); the difference is reproducibility—nightly tags get their references overwritten by subsequent builds, official tags do not. For a stack headed into a distribution, anchoring on nightlies long-term means the sources pinned inside the package are not reproducible over the long run—the same class of concern as “patches should be generated with git format-patch” in 2.3.

4.3 Three PRs Under Review Missed 0.1.3, Whisper and Interface Alignment Still Pending (10-31 status)

Date: 2026-10-31 (status)　Source: PR #1011, PR #1013, PR #994, open PR list

The sixteen commits in 0.1.3 do not include #1011, #1013, or #994, meaning they have not yet been taken into an official release. Their nature: #1011 forces the count in scalable VIR slices to int64 (on the same vector-width line as this issue’s ten VIR commits), #1013 lets Whisper reuse preprocessing within a single transcription, and #994 aligns the buddy-server interface with llama-server.

The most awkward of the three is #994: the llama-server interface it wants to align with is exactly the layer that #1015 refactored away. 0.1.3 has already consolidated the per-modality plugin handles into a unified ABI; if #994 merges in its original direction, it amounts to stacking another compatibility layer on top of an interface that was just rewritten. The PR does not discuss this conflict, and this issue we have not seen it closed or redirected—its current state is “neither in the release nor rejected.”

#1011’s situation is similar but the opposite direction: it is the closing item on the vector-width line, while the ten VIR commits from the same period already landed in 0.1.3. A closing item left outside the release means 0.1.3’s scalable vectorization still has no settled answer at the boundary of “slice counts exceeding 32 bits.”

VI. Trend Observations

6.1 The official release notes are out of sync with the code diff, and RISC-V progress is buried in the commit history

The methodological significance of 0.1.3 outweighs the release itself: when a project’s “public description” and “what is actually shipped” diverge over time, outsiders can only infer its state by reverse-engineering the commit history. In this cycle, the release notes mention only the server-side ABI refactor, while twelve of the sixteen commits touch the VIR vector layer.

This disconnect carries a compounding cost. For downstream users, deciding “whether to upgrade” requires consulting the release notes, the commit diff, and the dependency anchors simultaneously; for upstream, the work that most deserves visibility does not appear on the pages where it should—the most systematic vectorization progress of the past three months has no corresponding description in the blog, the docs, or the release notes. For a stack whose narrative is “RVV to Matrix,” reducing vectorization progress to ten lines of commit titles is a waste.

The more practical risk lies on the review side: if the release notes cover only part of the changes, reviewers’ attention will concentrate on that part, and the remaining changes will never be revisited once they have “shipped in an official release.”

6.2 triton-riscv shifts from “fix one, merge one” to “batch submission,” but the acceptance side is still missing

The three PRs on 10-29 were “merged back-to-back within 80 minutes”; this cycle’s five PRs were “opened back-to-back within two days, not yet merged.” The former shows that maintainers have a fast track for clear bug fixes; the latter shows that the new batch has not yet reached that stage. The difference between the two tempos is not development intensity but review bandwidth.

These five, plus the three from 10-29, add up to eight similar fixes in three weeks, all pointing to information loss in the fallback path. The number itself is a signal: this path has no systematic equivalence checking, so issues can only be found by hitting them operator by operator and patched one by one. Meanwhile, the single most valuable thing for downstream—turning the export of FlagGems’ 604 operators into a standing nightly regression—still has not been done. Although PR #56 has recovered from its stall since 09-16 (one push at 10-30 20:50, now expanded to 156 new files, with exported entries growing from 468 to 604), it remains open.

As long as acceptance lives in PRs rather than in the pipeline, the question “can this batch of operators run on riscv64?” will keep being deferred.

6.3 The distribution side’s monthly commitments keep slipping, and stack-level packaging is still reworking at the spec layer

In the last three days of October, two lines directly related to “distribution” missed their windows at the same time: ruyi 0.54.0’s “end of October” target slipped, and openRuyi’s 2026.10 release was still unpublished as of 11-02. Neither line has stalled on the code side—openRuyi had six commits on 10-30, and ruyi had one documentation merge—so the bottleneck is the release process itself, not development.

Meanwhile, the three-piece stack-level PR #1350 has passed its sixth week and is still reworking at the spec level. Taken together, these three items point to the same structural problem: in this ecosystem, “building things” and “shipping things” are two separate capabilities. The former advances across multiple repositories simultaneously; the latter has not completed a single on-time release in nearly two months.

For RuyiAI, the most practical short-term recommendation is not to push for releases but to write the three non-standard points from section 2.3 (buddy-mlir bundling its own LLVM, triton depending on git, tilelang requiring toolchain discovery) into a packaging convention, so that reviews of #1350 do not have to re-litigate the same issues every week—only by lowering the round-trip cost can a monthly release cadence become feasible.
