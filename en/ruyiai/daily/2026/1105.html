Today’s Focus: AME backend pins i32 matrix accumulators to AccReg, configurable tile operations deferred until expansion (11-04)

Date: 2026-11-04　Source: commit f346011, PR #35

At 15:40 on 11-04 (Beijing time), the riscv branch of RuyiAI-Stack/llvm-project gained a new commit f346011, touching 8 files, +412/−1, authored by caihanyi111 with caohanghang as co-author. The change targets the LLVM backend implementation of the RISC-V AME matrix extension (recorded in code as BOSCAME), in two parts.

The first part is register classification. Loop-carried accumulator PHIs take their default register class from the type table, while nxv32i32 was previously registered only as TileReg; the accumulator operands and results of the accumulate instructions mlce32.m, mqma.*, and msce32.m are all confined to AccReg, so every loop edge had to generate a copy between the tile and accumulator register banks, and copyPhysReg could not expand such cross-bank copies into a single AME instruction. The fix registers nxv32i32 as AccReg as well; for targets that also enable the V extension, RVV re-registers the type, leaving default behavior unchanged. Same-bank whole-register copies are now expanded using mmve64.t.t and mmve64.a.a; cross-bank copies remain a hard error and are no longer downgraded to per-lane indexed moves.

The second part is scheduling. Each tile configuration and its consumers are kept in an ordered, side-effecting pseudo-instruction until expansion just before emit; matrix registers become allocatable, MMA accumulators are tied, zero-accumulator definitions do not read old values, and branch relaxation accounts for the fully expanded size. The commit also adds three tests: ordering of configurable load/MMA/store, standalone accumulators and zero-value definitions, and both RVV and non-RVV selections, plus the relaxed branches.

The commit message states the motivation: the upper-level TTIR-to-BOSCAME lowering requires reduction loops to keep i32 accumulators in AccReg throughout. Per the context in the commit message, this chain corresponds to the matrix operator path on the TileLang side; what the LLVM side fills in is the register allocation and scheduling layer, not new instructions.

3.3 arXiv: bf16/fp16 silently degrade under auto-vectorization on RVV (11-02, outside window)

Date: 2026-11-02 (outside window, past three days)　Source: arXiv 2611.03917

There were no new RISC-V-related papers on arXiv within the window; one study from the past three days directly relevant to RVV vectorization is worth noting. Authors Vaishnavi Kouru and Robert Chun compare LLVM’s RISC-V auto-vectorization using multiply-add loops at four precisions—fp32, int8, bf16, and fp16: under the common baseline of -march=rv64gcv, int8 and fp32 vectorize cleanly, while bf16 and fp16 degrade into extensive scalar fallbacks, with fp16 even degrading into per-element software conversion calls unless zvfbfmin/zvfbfwma and zvfhmin are additionally enabled.

Dynamic instruction counts under QEMU user mode give the magnitude: the baseline bf16 and fp16 kernels execute 17.0× and 75.9× the instruction counts of the extension-enabled versions, respectively. The paper also notes that compiler diagnostics do report this degradation, but the wording does not distinguish between “solvable by adding a compiler flag” and “inherent conversion cost,” so users get no direct signal pointing to the fix. For the RuyiAI stack, this is two ends of the same problem as the vector math function additions in issue 080: one end lacks library functions, the other lacks visibility into feature flags.

IV. Buddy Compiler Updates

4.1 VIR’s set_vl semantics tightened: exact VLEN and arbitrary VLEN split into two paths (11-04 to 11-05)

Date: 2026-11-04 to 11-05　Source: PR #1028, merge commit dd57775, PR #1029, merge commit 61ba191

Two PRs from zhanghb97 landed in sequence within the window, clarifying the semantics of set_vl in the VIR dialect.

#1028 (merged 11-04 23:54) makes rvv-vlen denote the target’s exact VLEN: vscale = rvv-vlen / 64, a vector<[N]xT> holds N times vscale lanes, and splitting is done on full vectors. Previously rvv-vlen was treated as the minimum VLEN, with masks all true yet still left in the code—llc kept vid and vmslt, memory accesses carried masks, RoPE’s rotate_half became slides plus masked selects, and masks even overflowed in decode attention. Kernels on K3 built for a 1024-bit vector width are the typical case for this path.

#1029 (merged 11-05 01:32) handles the generic build without rvv-vlen: here the code must hold for any VLEN, strip-mined regions step by N times vscale at runtime, and vectors are sized to the minimum 128 bits; a set_vl with a result is rejected outright with “requires rvv-vlen, i.e. exact VLEN,” whereas this pass previously only reported an error. Fixed vectors remain as-is without rvv-vlen, sized to the host; declaring a minimum VLEN above 128 is not allowed.

Together, the two mean: semantics no longer rely on “masks happening to be all true” as a fallback—at compile time you must state whether this code is compiled for a specific VLEN or for any VLEN.

4.2 CI: pytorch 2.15 enters the test matrix, LLVM release enables NVPTX/AMDGPU and lld (11-04)

Date: 2026-11-04　Source: PR #1026, PR #1027, PR #1025

#1026 adds pytorch 2.15 to the test matrix, covering 2.11 through 2.15. The change was prompted by a real regression: under 2.15 the latest full check failed at tests/Python/AtenOps/test_resize_enlarge.py, and the failure occurred before the importer—AOT autograd’s functionalization now rejects enlarging resize_ on an already-functionalized tensor, and torch.compile fails on the same function too, so the graph never reaches ResizeOp. The fix replaces the test with the out-of-place aten.resize, which goes through the same ResizeOp handler and produces the same MLIR, passing across the full 2.11 to 2.15 matrix.

#1027 gives CI-released LLVM the NVPTX/AMDGPU targets and enables lld; #1025 bumps LLVM to bef335e2143c. All three are infrastructure, but the regression recorded in #1026 is worth noting: upstream tightening of functionalization shows up as “the graph never reaches the backend” rather than a backend error.
