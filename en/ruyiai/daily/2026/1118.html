Today’s Focus: LLVM fork merges XAME, ZTT v0.6 matrix backend lands 47 files in one go (11-17)

Date: 2026-11-17　Source: PR #36, merge commit 542365c

At 15:05 on 11-17, RuyiAI’s llvm-project fork merged #36 “[RISCV][XAME] Add ZTT v0.6 matrix backend support”. The PR was opened the previous morning and completed review the next day: 47 files, +4084 −19, of which the instruction definition RISCVInstrInfoXAME.td alone accounts for 1732 lines, builtin definitions 517 lines, register info 120 lines, plus a 262-line state-handling pass. This is the fork’s mainline’s first change since it stalled on 11-02.

What was merged is a complete matrix backend path, not scattered instructions: xame as a local feature name (version 0.6) lowers the matrix and accumulator SSA values in the LLVM IR produced by MLIR down to RISC-V instructions; the llvm.riscv.ztt.* builtin names and the riscv.ztt.matrix/riscv.ztt.acc target types follow the ZTT v0.6 compiler interface and constitute a downstream implementation of the interim Attached Matrix Extension. The documentation specifies two fixed profiles: the default +xame is 8×8, 16 M registers, 8 ACCs, with a 64-bit element cap; +xame,+xame-gem5 is 4×4, 32 M, 4 ACC, 128-bit. Both count in 32-bit register units.

The bulk of the engineering effort is in registers and calling conventions: 138 shared instruction encodings, matrix and ACC register groups, CSR operands, and profile-specific assembly and disassembly; after register allocation a new state pass is added to ensure descriptors, data, and state are not clobbered during register copies and spills. Matrix parameters use a compiler-local calling convention, not the RISC-V psABI standard; both caller and callee must agree on the same profile and register types, and parameters exceeding the register file are rejected and can only go through memory. Scalar overloads are uniformly normalized to unsigned XLEN-bit types; frontends needing signed interpretation must sign-extend themselves.

Validation covers three areas: LLVM RISC-V CodeGen and MC 3381/3382 pass, all 11 XAME-specific tests pass, and the only failure is a pre-existing baseline encoding discrepancy in xboscame-valid.s (the test expects ACC encoding 8, whereas in the unmodified definitions ACC0 is 0; the BOSCAME file itself was untouched); all 10 AME conversion regressions in the external Buddy MLIR harness pass; a 4×4 integer matrix multiply (A from 1 to 16, B all ones) compiles, links, and runs in AME_gem5, with the 16 outputs being exactly the row sums 10, 26, 42, 58, and guest exit code 0.

Today’s Highlight: triton-riscv Fixes bf16 Converter ABI, riscv64’s Three CI Legs All Green on Real Hardware for the First Time (11-17)

Date: 2026-11-17　Source: PR #121, Issue #114

At 18:37 on 11-17, triton-riscv merged #121 “Fix the launcher ABI of the bf16 conversion helpers”, two files +190 −7, the bulk being the prototypes of two helpers in backend/driver.py, plus a new 166-line test. The problem lay in the register class: the launcher defined __truncsfbf2 and __extendbfsf2 with uint16_t integer prototypes, whereas the call sites generated by llc pass bf16 in floating-point registers—xmm0 on x86-64, fa0 on riscv64—with the caller taking the value from the low 16 bits; the integer return lands in eax/a0, so every kernel converting fp32 to bf16 stored the residue of the previous floating-point operation, either zero or garbage.

The fix changes the prototypes of both helpers to float, keeping the bf16 bits in the low 16 bits of the floating-point return value; __bf16 itself cannot be used because the launcher is compiled by g++, and g++ 13 on Ubuntu 24.04 does not have this type on riscv64. __truncdfbf2 and the rest of the bf16 libcall family are explicitly listed as unchanged, since the current lowering does not produce them.

The new test python/examples/test_bf16_convert.py aligns fp32 and bf16 conversions bit-for-bit against torch’s int16 view, covering the four boundary classes of round-to-nearest-even (below half, ties with even and odd lsb, above half, and float32 max to infinity), four of which failed before the fix; it then pins down the libcall path with relocation assertions—host-target builds are skipped on x86 with avx512bf16 (where llc lowers bf16 natively and does not go through the helper), while riscv64 builds strip +zvfbfmin to force conversions through the launcher, incidentally serving as a probe of the bare runtime path.

The verification results are worth recording: on x86 host, the reproducer kernel from #114 returns [-5.0, -0.5, 2.5, 7.0] after the fix, versus all zeros before; the host example suite passes 4028 with 14 skipped, and the 10 failures are pre-existing failures in test_affine_grid_generator and test_avg_pool3d (they fail identically with the fix stashed, and neither case uses bfloat16); all three riscv64 CI legs (three Python versions) pass the full suite—the first time this fix has been verified on real riscv64. After merging with the FlagGems branch from #120, all 41 bf16 xfail pins turned into passes, with 461 cases passing.

2.1 openRuyi Introduces openssl-3 Compatibility Package with Ten RISC-V Optimization Patches (11-17)

Date: 2026-11-17　Source: Commit 9f1c8f64, openRuyi packaging repo

At 16:13 on 11-17, the packaging repo added SPECS/openssl-3, version 3.6.5, with 11 files and +5603 lines. The commit message is blunt: openssl 4.x has ABI changes, so following the practice of other distributions, an openssl-3 compatibility package is provided first; it will conflict with the current openssl 3.x, and installation failure is expected. The main openssl.spec in the repo still says 3.6.5, meaning this is a paving-the-way move—the compatibility package is in place first, so downstream has a fallback when the main package switches to 4.x.

The ten patches brought in are all RISC-V vector and assembly optimizations: a hand-written assembly implementation of ChaCha20 (686 lines), GHASH multi-block aggregation (997 lines), GHASH Zvbc multi-block aggregation (615 lines), GHASH Zvkg multi-block aggregation (255 lines), SHA256 instruction reordering (66 lines), an AES-XTS comment fix (44 lines), an SM4-CBC implementation (883 lines), an AES-128-CBC decryption improvement (456 lines), SM2 generic riscv64 assembly (1360 lines), plus a shared jitterentropy patch. Cryptographic libraries are starting to take advantage of vector crypto extensions like Zvbc and Zvkg on RISC-V, the same thread as last week’s Go backfill of Zvk AES.

III. Vector Extensions and Operator Optimization

3.1 Two Members of the bf16 libcall Family Still Lack Regression Coverage (11-17 Status)

Date: 2026-11-17　Source: PR #121

The description of #121 draws its own boundary: __truncdfbf2 and the remaining members of the bf16 libcall family are left unchanged because the current lowering does not produce them; __extendbfsf2 had its prototype changed but no tests were run — both targets inline bf16-to-f32 as shifts, with zero relocations, so the only way to confirm the argument register class is to disassemble the launcher’s .so and inspect the movss %xmm0 prologue. This means that if some future lowering degrades into a scalar libcall, no test case will catch that path.

Comparing with #117 makes this clearer: #117 puts +zvfbfmin into the default feature string, steering cores with vector extensions toward vector conversion; #121 fixes the path that falls back to libcall when that extension is absent. The semantics of the two paths must be bit-for-bit identical, yet only the vector path currently has bit-exact tests; the libcall path relies on the four boundary cases added in this round.

3.2 IREE 3.14.0 Adds f16/bf16 inner_tiled MMA for RISC-V V (11-16)

Date: 2026-11-16　Source: IREE v3.14.0

At 18:15 on 11-16, IREE released 3.14.0. The RISC-V V path of the CPU backend gains inner_tiled MMA for f16 (vfmacc, vfwmacc, Zvfhmin) and bf16 (vfwmaccbf16); math.roundeven now stays as a native instruction on riscv64 with the D extension instead of falling back to a software sequence; and one .vmfb reproducibility issue was fixed (LLVMCPU no longer writes uninitialized source location lines).

IREE follows a different MLIR downstream route, parallel to Buddy/RuyiAI’s Linalg-to-llvm-cpu path. Its addition of bf16 MMA in the same week shows that low-precision matrix multiplication has become a shared to-do item across RISC-V compiler stacks.

VI. Trend Observations

6.1 Matrix extensions now have a compiler outlet

The XAME change puts 138 instructions, two profiles, register scheduling, and calling conventions into LLVM in one go, and validates them with Buddy’s AME conversion and actual gem5 runs. As with last week’s RVV bf16, whether an extension is usable now depends on three things being in place at the same time: the compiler can generate it, the simulator can run it, and the operator library has a corresponding entry point. Shipping only instruction definitions without the compiler now amounts to not shipping at all on RISC-V.

6.2 This week’s main thread is bf16

#117 puts +zvfbfmin into the default feature string, #121 fixes the register class for libcalls when that extension is absent, and IREE 3.14.0 adds bf16 MMA for RISC-V V—three actions point to the same thing: bf16 on RISC-V is not one path but “vector extension goes vector, otherwise goes libcall.” The two paths must be bit-for-bit identical, and a missing link in either will show up as the hardest-to-debug symptom of all: “the result is zero.”

6.3 The distribution is preparing for an ABI migration

The openssl-3 compatibility package landed first while the main package remains at 3.6.5, with the conflict explicitly documented as expected behavior; on the same day, abaci-bot hardened ABI comparison, SPDX validation, and the CVE embargo cache. openRuyi treats “ABIs that will break in the future” as an engineering item to manage in advance rather than patching on the day of the switch. This approach determines whether a distribution can track upstream over the long term far more than merging a few extra packages.

6.4 The information side keeps idling while the code side is busy

External news had zero hits, the forum had no new topics, and the three homepage pages did not move, yet within the window two compiler mid-end changes were merged, there were 19 packaging repo commits and 20 governance bot commits. The daily report’s value for judgment continues to depend on reading commit contents rather than counting news items; when release notes are empty or missing, the only option is to go back to merge commits and test records to verify.

Limitations

This issue’s window is 24 hours (11-17 04:30 to 11-18 04:30). On the GitHub side, Atom feeds and anonymous APIs were cross-checked; some repositories are counted via Atom. The pytorch fork’s default branch is riscv, with main serving only as an upstream mirror; the body describes each branch separately. XAME／ZTT v0.6 is a provisional-version extension, and its instruction encoding and profile may change later; this issue records only the state and verification results at the time of merge and does not imply acceptance by upstream LLVM. The RISC-V conclusions for IREE are taken from the v3.14.0 release notes and were not re-tested on hardware. On the external news side, Google News was scraped via a proxy, and eight sets of queries returned zero hits; it cannot be ruled out that Chinese-language media carried reports that were not indexed.
