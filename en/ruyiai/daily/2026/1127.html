Today’s Highlight: triton-riscv merges PR #135, CPU lowering and matmul unified through VIR (11-26)

Source: PR #135.

At 17:41 on 11-26, PR #135 was merged into the triton-riscv mainline. Titled “Unify standard CPU lowering and matmul through VIR”. Author WuXintong123, with 12 commits. 2 files changed, 255 lines added, 124 lines deleted.

The previous report noted this PR was still under review, with the branch already containing the merged #129, and the only remaining difference from mainline being backend/compiler.py; this batch of differences has now fully landed.

The changes concentrate in five areas. RVV vector width is now derived from the largest +zvlNb in the target features, defaulting to 128 bits. An explicit target_vector_bits is also accepted. The standard pipeline vectorizes masked stores, and rewrites for crop, transpose, and producer-fused reductions are moved ahead of bufferization. Standard matmul is unified through VIR on both fixed-width and RVV targets, with register tiling configured by target vector width and register count. A new target_tune passes -mtune through to opt and llc. Example values include spacemit-x100, spacemit-a100, and xt-c920v2. On the x86 side, vector width was also fixed along the way. opt now adds prefer-vector-width to functions beforehand, allowing targets like Emerald Rapids to use the full 512 bits.

The PR description states that -mattr continues to define the ISA, while -mcpu can enable extensions not reported by the hardware; the division of labor between the two is unchanged.

The dependency is not resolved: a Buddy release containing buddy-mlir#1068 is still required, and the version currently pinned by mainline predates the needed passes and options. CI that compiles kernels must wait for the new release and the Buddy version update.

Today’s Highlight: buddy-mlir adds XSAIAME dialect, RISC-V matrix extension enters the IR layer (11-26)

Source: PR #1071.

At 17:18 on 11-26, PR #1071 was merged, adding the xsai_ame dialect. 32 files changed, 1541 lines added, 1 line deleted, author xyyy1420.

The dialect provides typed SSA IR for XSAI’s ZAMES matrix extension and ZMASYNC synchronization extension. LLVM backend support already entered mainline with the LLVM upgrade in #1067; this change only adds the IR and Python bindings. Lowering to llvm.riscv.xsai.* intrinsics and Linalg conversion are left to follow-up PRs, and the LLVM gitlink is untouched.

There are two types. !xsai_ame.tile<kind, MxN, element> has kind taking a, b, or c, corresponding to A as MxK, B as NxK, and C as MxN. Dimensions are positive or dynamic. There are 15 element types in total: on the integer side i4, u4, i8, u8, i32; on the floating-point side fp8e4m3, fp8e5m2, fp16, bf16, and tf32. The rest are fp32, nvfp4, mxfp4, fp2pack4, and fp2pack5. !xsai_ame.sync is an SSA handle to the matrix synchronization register; physical register numbers do not enter the interface.

Operations include load, store, mma, mzero, as well as msyncregreset, mfence, mrelease, and macquire. load/store move tiles between registers and rank-2 memref views, with optional transpose; the view shape must match the tile. mma checks the a/b/c kinds and static K/M/N dimensions; element type combinations are not validated, and which combinations are supported is determined by the hardware implementation and the LLVM backend.

All four synchronization operations carry memory effects; they will not be deleted and will not be reordered across memory accesses.

The dialect is registered in buddy-opt and InitAll. On the Python side it provides dialect registration, TileType and SyncType, and ODS-generated operator constructors.

1. RuyiAI Stack Progress (PyTorch / Triton / TileLang RISC-V Porting)

1.1 Seven Sets of Measurements in PR #135: matmul Gains the Most, CPU Tuning Near Parity (11-26)

Source: PR #135.

The PR presents seven sets of historical measurements, all geometric-mean ratios relative to a baseline, where a value below 1 means faster. Samples come from their respective experiments, not a single full benchmark run.

There are three sets on RVV, VLEN 256, SpacemiT X100. Masked tile copy elimination covers 1726 cases, with CPU time 0.934 and wall clock 0.941. Masked memory and reduction rewriting covers 8643 cases, with CPU time 0.952 and wall clock 0.959. The VIR matmul change targets 553 cases, with CPU time 0.810 and wall clock 0.807.

On x86-64, AVX-512, Emerald Rapids, the vector-width preference fix covers 1712 cases, with CPU time 0.959 and wall clock 0.956.

All three CPU tuning sets are on 1726 cases. C920v2 at VLEN 128 is 0.995, and X100 at VLEN 256 is 0.989. A100 at VLEN 1024 is 1.000.

The PR also states that all 1726 cases in the copy-elimination control passed, as did all 856 cases in the matmul control. The VLEN fix restored large-scale Euclidean distance object checks under VLEN 256 and 1024.

VI. Trend Observations

6.1 With backend unification complete, the bottleneck shifts to operator inventory and Buddy version pinning

#135 closed out the structure of “standard CPU and matmul lowered along two separate paths”; the gains are concentrated in matmul at 0.810 and masked memory rewriting at 0.952.

CPU tuning scores 1.000 on the A100 with VLEN 1024, indicating this item currently yields no incremental gain on wide-vector machines. This judgment is based on the three tuning samples described in the PR itself, not a full regression.

The next bottleneck is not in the compilation path but in two places: the 279 operators under review have not advanced, and the Buddy distribution is still pinned to a version earlier than #1068.

6.2 The rollout pace of matrix extensions depends on two follow-up PRs: lowering and conversion

buddy’s matrix extensions now have two sets of IR: AME (ZTT v0.6) and XSAI AME (ZAMES/ZMASYNC).

Both lack the complete chain from “Linalg to dialect” and “dialect to intrinsic.” The PR description for #1071 also lists these two steps as follow-up work.

Assessment: matrix instructions will not enter end-to-end model performance data in the short term; what the midend merge changes first is expressiveness.

6.3 Distribution packaging focus shifts from kernel tracking to application-layer usability

openRuyi had 28 changes this window, with zero kernel changes; office suite corpora, RDF, linear programming solvers, and fonts account for most of them.

The inclusion of box64 is the only change in this batch that broadens the software surface, giving a runtime path to some software distributed only as x86 binaries.

There were no new packages on the AI stack side this window; the packaging status of triton and buddy is the same as the previous issue.
