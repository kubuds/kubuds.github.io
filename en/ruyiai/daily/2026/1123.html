Today’s Highlight: FP16 optimization for DeepSeek-R1-Distill-Qwen-1.5B on K3 A100 merged, Prefill 43.42 token/s (11-23)

Source: PR #997. Commit 3d5d674a. K3 config f16_k3.json.

#997 was merged on 11-23 at 00:25, created on 10-25, with review spanning nearly a month. It changes 20 files, including a newly added A100 legalization pass, IME dialect extensions, and model configuration.

The PR description lists four core techniques. First, four FP32 accumulators stay resident in registers across the entire K reduction; Prefill uses 8×32 tiling, and Decode computes 32 output channels per block. Second, some Decode projection weights are packed into N32/K8 panels, while the remaining projections keep the original RVV layout. Third, Prefill uses native VLEN=1024 with a BLIS width of 64, and fuses elementwise operators and vectorized SiLU. Fourth, the above choices are centralized in models/deepseek_r1/specs/f16_k3.json, leaving the default pipeline of existing configurations unchanged.

Measured data is recorded per the PR description. Prefill evaluates 128 positions; Decode measures 32 steps starting from position 64; eight threads; A100 cores 8 to 15; four samples taken.

Implementation Prefill (token/s) Decode (token/s)
Buddy mainline, packed FP16 4.53 5.88
llama.cpp (SpacemiT backend 0.1.6) 27.95 3.90
Buddy, this PR 43.42 6.06

Prefill is about 8.6× faster than the Buddy mainline and 55% higher than llama.cpp. Decode is 55% higher than llama.cpp and only 3% higher than the Buddy mainline.

The Prefill figures include session and interface call overhead, as noted in the PR description. The llama.cpp side uses FP16 GGUF weights and FP16 KV cache, with identical input IDs on both sides.

The same set of kernels has been reused for other models. #1075 targets Whisper Base, #1076 targets PaddleOCR-VL-0.9B, and #1001 targets Qwen3-0.6B. All three reference the pass and weight packing from #997.

1.2 FlagGems examples add two more batches: 72 + 61 operators, stacking up to 279 (11-21, 11-22)

Source: PR #131. PR #132.

#131 was opened on 11-21 18:53, covering 72 operators. #132 was opened on 11-22 18:48, covering 61 operators. Both only modify python/examples/flaggems/.

The four families in #131 are coordinate copy, internal copy and allocation, shape construction, and type conversion and fill. The PR description lists three upstream deviations: the padding wrapper takes aten’s (w, h, d) order and then reorders to the kernel’s (d, h, w); replication’s backward scans by scalar source position to match aten’s accumulation order; and rot90 misses the last-dimension term when rank is greater than 2.

The four families in #132 are BLAS wrappers and sparse smm, gamma special functions, quantized operators, and low-precision and sparse matrix multiplication. The PR description states that fp64 dot products can only reach fp32 accumulation, so such contractions are changed to scalar FMA loops to preserve precision; e5m2 fp8 has no fallback path, so it is upcast inside the kernel, while e4m3 and int8 use native paths.

Test counts keep climbing. #131 records 7830 passing and 739 new; #132 records 8617 passing and 787 new. Both run on x86_64, excluding three pre-existing crashing files.

The five PRs form a chain: 63 in #126, 43 in #127, 40 in #130, 72 in #131, and 61 in #132, totaling 279 operator examples. Per the PR descriptions, when predecessors are unmerged the diff counts predecessor commits: #131 is 34 commits and 548 files relative to main, and #132 is 38 commits and 670 files.

3.2 Vector Work Moves into Model Kernels: VLEN 1024, SiLU, and exp Approximation (11-22)

Sources: PR #997. PR #1076. PR #1075.

#997 makes the Prefill BLIS column width configurable and allows hardware VLEN to be validated at function entry. The A100 configuration uses VLEN=1024 with a width of 64.

In the same change, SiLU is fused and vectorized, and exp uses the upstream MLIR polynomial approximation. The PR description notes that the polynomial changes rounding and is validated separately from the default path.

#1076 fuses attention’s bmm1, scale, softmax, and bmm2 into a single tiled kernel, keeps softmax in L1, and uses vector exp. The same change adds a vectorized erf to -approximate-vector-exp, so GELU no longer calls a scalar function per lane.

#1075 takes a different path. The encoder’s P @ V is lowered to an FP32-accumulating RVV kernel with 4-row M unrolling, while matmul_transpose_b and conv_1d_ncw_fcw are lowered to IME.

What the three changes share is binding vector width to hardware VLEN. The tuning in triton-side #129 from the previous issue used the same approach, so the parameter conventions on both sides can be compared.

3.3 FlagGems Examples Extend to Special Functions and Quantized Operators (11-22)

Sources: PR #127. PR #132.

The special-functions branch covers the Bessel family, four kinds of Chebyshev plus shifted variants, two kinds of Hermite, Laguerre, and Legendre, along with log_softmax and logsumexp.

Intrinsics that the toolchain cannot lower fall back to closed forms. erfcx uses a three-segment blend, and the tail of log_ndtr is computed as −t² + log(erfcx(t)/2).

The quantization and low-precision branch covers the fake-quantization family and its learnable variants, 4-bit dynamic quantized linear, scaled mm, int8/int4 weight packing, mixed-precision linear, and CSR and semi-structured products.

Precision handling is documented in the PR description. fp64 dot products can only reach fp32 accumulation on the Triton side, so such contractions are changed to scalar FMA loops; e5m2 fp8 has no lowering path and is upconverted inside the kernel; e4m3 and int8 use native paths.

4.2 0.1.6 adds dump() support, 0.1.7 compresses LLVM assets (11-21)

Source: PR #1074. Commit a848378f.

The rationale for #1074 is stated very concretely. The nightly build is built from main, but #1062 landed on the llvm-multitarget branch, so the 0.1.5 LLVM package only has dumpPretty(), not dump().

The downstream symptom is a link failure, reporting undefined reference to mlir::Operation::dump() and mlir::Value::dump() const. The fix is to enable LLVM_ENABLE_DUMP, restoring only these two helpers without turning on assertions.

The PR description also notes: LLVM installations are cached by hash, so subsequent versions need to run llvm_cache_mode=clean once to pick up this switch.

0.1.7 addresses the asset size limit. The commit message states that the riscv64 LLVM installation package, after gzip, slightly exceeds the 2 GiB per-asset limit, which is why v0.1.6 reported “size must be less than 2147483648”.

The fix is to truncate developer tools not used downstream, removing src, share, and libexec, and stripping the rest. On x86_64, measured size drops from 1617 MB to 817 MB.

The description also records a failed attempt. Initially files were deleted outright, but LLVMExports.cmake aborted at the configure stage because imported targets pointed to missing files, so the approach was changed to truncation.

Both versions now have 8 assets each. The riscv64 LLVM package on 0.1.7 is 1,138,715,828 bytes, below the limit.

4.3 DeepSeek optimization merged, four model PRs queued (11-23)

Source: PR #997. PR #1075. PR #1076. PR #1001.

#997 was covered in today’s highlights. Here we only note its position in the PR queue: it is the parent of this round of model optimizations.

#1075 does Whisper Base, opened 11-22 17:10. The PR description gives an end-to-end time of 2.031 seconds versus 1663.03 seconds on main, a 818.8x speedup, with RTF dropping from 345.39 to 0.42. Preprocessing 0.101 seconds, encoder 1.622 seconds, decoding 0.272 seconds.

#1075 also fixes a memory issue. In the STFT loop, make_rfftp_plan(400) creates a plan on every call, leaking about 1 GB; it is changed to be hoisted outside the 3001-frame loop and the buffer is released.

#1076 does PaddleOCR-VL-0.9B, opened 11-22 22:08. End-to-end 30.82 seconds, a 21x speedup over the FP16 RVV baseline of 525.71 seconds. Prefill 25.04 seconds, Decode 5.78 seconds (18 tokens, 3.11 token/s). The 19 generated tokens match PyTorch FP16 exactly.

#1001 does Qwen3-0.6B, opened 10-26 and still under review. It directly reuses #997’s IME FP16 GEMM/GEMV kernels and Decode weight packing.

The signal from these four combined: a single set of A100 kernels is now covering three workload classes—LLM, speech, and OCR.

VI. Trend Observations

6.1 Releases Shift from Monthly Cadence to Patching Downstream Blockers

The previous issue noted that ruyi pushed 0.55.0 to late November. This issue, ruyi shipped a beta, while buddy-mlir released three versions in three days.

Neither 0.1.6 nor 0.1.7 is a feature release. One fixes a missing dump() in downstream linking, the other compresses asset size to stay under the 2 GiB limit.

The basis for this judgment is the commit messages: #1074 explicitly mentions triton’s undefined reference, and a848378f explicitly states size must be less than 2147483648.

This shows version numbers are being used as a patching channel. The cost is that 0.1.7 and 0.1.6 diverge, and downstream must wait for the next merge to get both fixes together.

6.2 A Model Optimization Pipeline Forms on K3 A100

After #997 merged, the same set of IME kernels has appeared in PRs for three models: Whisper, PaddleOCR-VL, and Qwen3.

All three performance figures were recorded on the same machine K3-002, the same core group 8 to 15, eight threads, VLEN=1024. They are directly comparable.

The magnitude of gains varies widely. DeepSeek’s Prefill is 8.6x on the backbone, while Whisper’s end-to-end is 818.8x. The latter’s baseline comes from a single F32 forward pass without encoder reuse, inflating the multiplier.

The verifiable criterion is that the token sequence matches the reference implementation. #1076 records all 19 tokens identical and includes the OCR text.

6.3 Toolchain Side Enters a Period of Pending-Merge Queue Buildup

The five FlagGems PRs in triton-riscv form a chain totaling 279 operator examples. Each must wait for the previous one to merge before recomputing its diff.

pytorch’s riscv branch stopped at 11-15, and tilelang-riscv stopped at 11-16. Neither has new commits.

The ruyi side is the opposite: six PRs merged within a day and a beta was released. The difference is that ruyi’s changes are concentrated in the CLI and configuration, with a narrow review surface.

Limitations

This issue’s window is 3 days (11-20 04:30 to 11-23 04:30), covering the weekend. The Monday window is counted as 3 days, directly continuing from the cutoff of the 11-20 issue.

None of the three releases 0.1.5 through 0.1.7 have release notes; the body text is empty. Version differences can only be inferred from the commits pointed to by tags and the compare results; the official project has not listed them item by item.

The fork status of 0.1.7 versus 0.1.6 comes from the GitHub compare API. If a merge follows later, the conclusion needs to be re-verified.

The performance figures in #997, #1075, and #1076 were all measured and reported by the PR authors themselves; this issue did not re-test on K3 hardware. Whisper’s 818.8x is based on a single F32 forward pass without encoder reuse as the baseline; the multiplier should not be compared across models.

Of the 19 changes in ruyi 0.55.0-beta, 13 have no corresponding commits within the window; the article treats them as accumulated during the 0.54.0 cycle and has not verified the landing dates item by item.

Forum spam posts were judged by title and not opened individually for verification. Of the six Google News queries, only one XiangShan report was hit, unrelated to this issue’s topic, and was excluded. The latest arXiv paper is 11-19, with no new items within the window.
