II. RuyiSDK Toolchain and Distributions

2.1 openRuyi PR #1350: The RuyiAI trio enters the distribution; author responds to review comments item by item the same day (10-27)

Date: 2026-10-27　Source: PR #1350, PR #1350 review comments, PR #1350 commits

PR #1350 is the most important item in the distribution layer this issue: a single PR adds three packages at once—buddy-mlir (an LLVM-based MLIR compilation framework), python-triton-ruyiai (RISC-V Triton), and python-tilelang-ruyiai (RISC-V TileLang backend). All 3 commits landed on 9-21 between 09:46 and 09:48 (within two minutes), totaling 9 files, +666/−0.

The timeline is worth recording: the PR was opened on 9-21; on 9-24 maintainer Z572 raised three change requests (why git is needed, whether buddy-mlir should provide a macro file for Triton to locate its LLVM, and whether buddy-mlir should first build a fixed-version clang with GCC and then build itself with the new clang); on 9-28 the author replied and fixed two of them; then it stalled for nearly a month, until three consecutive replies at 17:55, 17:57, and 18:54 on 10-27 addressed the remaining disputes one by one.

The technical content of the three replies is more informative than the progress itself. First, triton upstream’s setup.py forcibly checks whether git can be executed, so either add git as a build dependency or modify setup.py (requiring a new patch file, which easily falls out of sync when triton updates)—the author chose the former. Second, the LLVM bundled with buddy-mlir is used only inside that package, and these packages are always pinned to a specific LLVM commit, so the author prefers to keep it inside the build process rather than externalizing it as a standalone macro package. Third, switching to GCC to build a fixed-version LLVM/clang is technically feasible, but would increase build time by at least 1.5x.

These three points all point to the same trade-off: the build chains of these RuyiAI packages are highly coupled (Triton depends on buddy-mlir’s LLVM, TileLang depends on the buddy-mlir toolchain), and once they are split apart according to the distribution’s convention of “externalizing dependencies and reusing system packages,” both build cost and mismatch risk rise. The author chose to preserve the coupling and accept the size and build-time cost—a clear statement of position on the packaging route.

IV. Buddy Compiler Updates

4.1 VIR Gains Python Bindings: From a buddy-opt-Only Tool to a Programmable Dialect (10-27)

Date: 2026-10-27　Source: PR #1009, buddy-mlir commit list

Merged at 22:42, #1009 is the core Buddy Compiler action in this window: 12 files, +614/−1, adding a new buddy_mlir.dialects.vir module. The commit message states the pain point plainly — VIR previously had no Python bindings at all, so VIR decode attention could only assemble ops via ir.Operation.create("vir....") and types via ir.Type.parse("!vir.vec<...>"), and the entire VIR lowering could only run inside the single buddy-opt executable.

The implementation follows the existing dialect pattern: ODS op definitions (VIRBinding.td) plus a C API plus a nanobind extension, structurally identical to upstream dialects in the same repo that ship their own types, such as quant. Per the PR description, it comes in three parts — Ops, Types, and pass registration that hooks VIR lowering into Python.

The significance lies not in the tooling itself but in composability: once VIR can be constructed and lowered directly from Python, op descriptions, shape inference, and test cases can all live on the Python side, and frontends (Triton, TileLang) no longer need C++-side hooks to interface with VIR. For an intermediate representation that could previously only be validated inside a single executable, this marks a shift from “compiler internal” to “externally callable dialect.”

Note that #1009 was followed immediately by #1011 “Cast the scalable VIR piece count to int64_t” (open), indicating that integer-width issues on the scalable vector path have only just been touched in the past two days. The Python bindings merely open the door; stability is still being worked out.

4.2 Five PRs Under Review: piece count to int64, Whisper Preprocessing Reuse, buddy-server Source Cleanup (10-27)

Date: 2026-10-27 (status)　Source: PR #1011, PR #1013, PR #1012, PR #1010

Five open PRs were updated during the window, falling into three groups.

VIR and scalable vectors: #1011 explicitly casts VIR’s piece count from its default width to int64_t. Piece count refers to how many segments a scalable vector is split into; participating in subsequent multiply-adds as 32-bit carries overflow risk for large shapes. This fix belongs to the same cleanup category as #1008 from the previous issue (index vector width assertion).

Model examples: #1013 reuses Whisper preprocessing within each transcription; #1012 adds validation for Whisper output and enables x64 CI tests. Both are routine example quality improvements and do not involve RISC-V.

Infrastructure: #1010 reorganizes the buddy-server source and test directory structure. Separately, #993 adds the tile.upsample_nearest op and recognition pattern, and #932 fixes row padding for C move-out in Gemmini OS blocked matrix multiplication; both were also updated within the window but contain earlier content.

VI. Trend Observations

6.1 Expression layer, tooling layer, and distribution layer each fill a gap on the same day

Place this issue’s three events on a single timeline: on the night of 10-26, VIR completed scalable vector expressions; on the night of 10-27, Python bindings were added; and throughout 10-27, distribution packaging was being pushed. These three stages are inherently sequential—first it can express, then it can be called, and finally it can be distributed. In previous issues, the pattern was consistently “expression layer fast, tooling and distribution layers lagging”; this issue marks the first time all three lines advanced in parallel on the same day.

However, to judge whether this stack is truly closing the loop, two known gaps remain. First, the re-anchoring of triton-riscv is automated, and adaptation verification has not yet caught up; whether the interface changes between 0.1.1 and 0.1.3 will surface downstream will only be known next issue. Second, the pytorch riscv branch has had zero commits for six consecutive days, while the distribution side is already packaging it (#1352)—the package follows a branch that is not moving, and whether it will already be behind the upstream baseline by the time the package is merged is a risk worth watching.

6.2 Beyond pre-release cleanup, the distribution begins to subtract

This issue’s two sets of openRuyi actions are different in nature: one set is addition (45 commits, 13 new packages, 12 security updates, a coordinated upgrade of the entire Samba family), and the other is subtraction (three reverts withdrawing LLVM IR from bundled distribution). What we saw in previous issues was always “pre-release cleanup”—filling dependencies, clearing CVEs, switching versions; this issue is the first time we see an explicit functional rollback.

This indicates that openRuyi’s maintenance focus is shifting from “covering more packages” to “ensuring the quality boundaries of existing packages”: experiments such as IR distribution bring cascading costs in package size, ABI, and infrastructure, and are prioritized for removal under release pressure. For the RuyiAI stack, this is a two-sided signal—the packaging channel is becoming more standardized (#1350 and #1352 are both converging item by item according to distribution conventions), but tolerance for “experimental build methods” (such as embedded LLVM or self-vendored components) will decline in tandem. The author’s insistence in #1350 on keeping buddy-mlir’s LLVM inside the package is precisely a negotiation against this direction, and the outcome is worth observing.
