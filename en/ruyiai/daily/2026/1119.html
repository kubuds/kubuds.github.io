Today’s Highlight: FlagGems operator set adds 63 more, triton-riscv example repo expands to 239 files (11-18)

Date: 2026-11-18　Source: PR #126. PR #120.

At 22:32 on 11-18, triton-riscv opened #126 “Add FlagGems operators (63 ops)”. It moves 63 aten operators into python/examples/flaggems/ as Triton examples, each paired with a test against the aten CPU reference implementation.

This branch builds on top of the still-open #120. Per the PR description, of the 24 commits and 239 files relative to main, 111 files belong to #120 and 128 are new here. Once #120 is merged, this PR will be rebased down to its own commits.

The operators fall into six groups by purpose. The first four are scalar elementwise, comparison and bit-shift, 12 ops; elementwise mid-range, view and factory, 14 ops; numeric, logical and ldexp, 11 ops; unsafe indexing, amp and quantization helpers, 9 ops. The last two are masked softmax, pdist and linear packing, 9 ops; foreach and fused optimizers, 8 ops. The last two groups include _foreach_binary with 81 wrappers and _foreach_unary with 60 entries.

This toolchain cannot lower some libdevice builtins, and buddy-opt rejects the calls outright. The author substituted closed-form equivalents and measured error empirically against fp64 and torch. tan goes through sin/cos, with relative error no more than 1.2e-7. log2 becomes log times 1/ln2, no more than 3.2e-7. lgamma uses Lanczos g=7 plus the reflection formula, no more than 6.4e-4. sinh, cosh and tanh go through exponential forms, with error between 2.4e-5 and 6.3e-5.

erfc gets the most careful treatment. In fp32, computing 1-erf directly is identically zero for x greater than or equal to 3.5, so below 2.85 it uses 1-erf and above that switches to a 12-term asymptotic series; worst case at the seam is 6.4e-4, and above it no more than 1.3e-4. The four boundary values plus infinity and NaN match torch exactly.

Semantics follow torch, and wherever upstream FlagGems diverges, each case is pinned down with a test. _fused_adam applies weight decay in L2 form (g plus wd times p), and amsgrad takes the max of the uncorrected v. _fused_adamw_ does decoupled decay first, then the step. _fused_adagrad_ and _fused_sgd_ skip the update only when found_inf is exactly 1.

Validation records the full FlagGems suite passing 6416 cases, run locally on x86_64, excluding three pre-existing native-crash files. Tolerances leave 1.6x to 10x headroom over the measured worst-case error.

Today’s Focus: XSAI Matrix and Sync Interfaces Land in Fork, Buddy Side Swaps AME Implementation for ZTT v0.6 (11-18)

Date: 2026-11-18　Sources: llvm-project PR #33. buddy-mlir PR #1066. buddy-mlir PR #1064.

At 02:05 on 11-19 (Beijing time), a merge commit 163d6a7 appeared on the riscv branch of the llvm-project fork. It corresponds to PR #33 “Add XSAI ZAMES and ZMASYNC vendor extensions”, a 5150-line patch covering matrix and sync builtins, target extension types, register classes, instruction encoding, and assembly/disassembly.

The implementation uses RV64 SelectionDAG, including config materialization before register allocation and expansion after allocation; it tracks matrix memory operands, validates builtin immediate ranges, and emits clear diagnostics during RV32 code generation. Matrix tile types live in the riscv.xsai.zames.tile.* namespace, and sync values in riscv.xsai.zmasync.sync.

The author lists three scope gaps: matrix copy, spill and reload, and cross-function ABI. Vector exp2, MXFP, and XX8 conversion extensions are explicitly out of scope for this change. Validation consists of 28 dedicated tests passing, plus 11 smoke scenarios.

At 23:14 the same day, buddy-mlir merged #1064 “Bump LLVM to 542365c9cd38”, which only changes the llvm submodule pointer. The LLVM update being followed is exactly the XAME/ZTT v0.6 backend in the fork, i.e. the merge recorded in the previous daily briefing.

Then at 23:36, #1066 “Replace legacy AME with ZTT v0.6 operations” was opened: 30 files, +8349 −1277. It replaces the retired AME dialect, defines 138 typed instruction operations under the existing ame namespace, and unifies lowering of both interfaces to llvm.riscv.ztt.*.

#1066 ships with two sets of test cases and two freestanding gem5 validation workloads. The author states no commitment to numerical compatibility with the old ISA contract. A 4×4 signed integer workload passes exact comparison on AME_gem5: matrix A set to 1 through 16, B all ones, C initialized to zero; all 16 results match an independent scalar reference, the printed row sums are 10, 26, 42, 58, and both guest processes exit with code 0.

The three threads point in the same direction: LLVM provides backend capabilities, the compiler middle end connects the dialect and lowering paths, and the Triton side validates with operator examples.

1.3 Nightly Wheel Sheds 668 MB of Redundancy, strip Aligned with Packaging Path (11-18)

Date: 2026-11-18　Source: PR #125. Nightly 20261118.

On 11-18 18:43, #125 “Strip the copies the wheel actually packages” was merged, three files, +37 −31. Previously, the strip step in release.sh operated on artifacts in the source tree, while the wheel packaged a different copy in the build directory, so three large items were missed.

Per the numbers given in the PR: triton-shared-opt is 398 MB in the wheel, about 118 MB after stripping. libtriton.so is 441.5 MB, about 144 MB after stripping. libtriton_amd_codegen.so exists in both amd/lib and amd/codegen/build, at 84 MB each. Together that is 668 MB of avoidable members in a 502 MB wheel.

The fix has four steps: strip the copies that are actually packaged, remove the duplicate cmake build tree, fail outright rather than silently skip when strip does not take effect, and check the final size before release. The PR also has the Release Wheels workflow print the final size on every PR without publishing.

The previous issue recorded an earlier attempt where strip-all cut wheel weight by forty percent; this change fills in the missed copies. The most recent nightly before the merge is nightly/20261118-e9c34b7 (released 11-18 09:59 Beijing time), whose size has not yet been rebuilt under the new process; the next nightly build will be the first under the new accounting.

III. Vector Extensions and Operator Optimization

3.1 FlagGems Suite Fills libdevice Gaps with Closed-Form Substitutions, 6416 Items Pass (11-18)

Date: 2026-11-18　Source: PR #126.

The value of #126 goes beyond operator count. It lists, one by one, the libdevice builtins this toolchain currently cannot lower, and provides testable substitute expressions—effectively a catalog of backend capability gaps.

The rejection points mentioned in the list are concentrated in buddy-opt. pow can only go through the libdevice version; ** in the AST is unsupported. round is changed to explicit half-to-even. erfc is handled piecewise due to insufficient fp32 precision. Each substitute expression comes with relative error and boundary behavior, making later comparison easier when swapping back to native builtins.

The testing methodology is also worth noting: all tolerances leave 1.6x to 10x margin over the worst measured error, and seeds are process-independent. This approach makes regression results for new operators reproducible rather than dependent on luck.

IV. Buddy Compiler Updates

4.1 LLVM submodule bumped to 542365c; PR opened to replace the AME dialect with ZTT v0.6 (11-18)

Date: 2026-11-18　Source: PR #1064. PR #1066.

#1064 changes only one line of gitlink: it moves the llvm submodule from f346011a to 542365c9, the latest commit on the riscv branch of the RuyiAI LLVM fork. This commit includes the XAME/ZTT v0.6 backend, target extension types, builtins, and two profiles.

#1066 then replaces the entire old AME implementation on the Buddy side. It defines 138 typed instruction ops, along with custom assembly syntax, builtin bridging, and matrix/accumulator target extension types; both interfaces are lowered to llvm.riscv.ztt.* via --lower-ame, and the retired AME ops and examples are removed.

The acceptance criteria match the backend merge on 11-17: two workloads — 4×4 signed integers and a parameterized kernel — are run on gem5 and pass exact comparison. The author states this is a functional check, with no performance testing and no claim of numerical-behavior compatibility with the old ISA.

The main-branch nightly is still at nightly/v0.1.4.dev20261113; no separate release was cut for this submodule update.

4.2 Transpose tiling pass cuts the transpose bucket from 199.6G cycles to 31.5G (11-18)

Date: 2026-11-18　Source: PR #1065.

#1065 adds the linalg-transpose-tile pass: it rewrites linalg.transpose on memrefs into scf.parallel loops tiled by tile-size × tile-size, changing only loop order, with bit-identical results.

The default lowering moves elements one by one along full-row strides on the swapped axis, repeatedly flushing the cache on large matrices. Measured on x86 with a graph of 240 materialized weight transposes, the author reports the transpose bucket dropping from 199.6G cycles to 31.5G, an 84% reduction.

The PR checklist is not fully ticked: the existing-tests and documentation items are empty, and the code-style item is unchecked. These need to be completed before merge.

VI. Trend Observations

6.1 The operator validation suite is expanding fast

Within a week, triton-riscv’s FlagGems examples grew from 54 operators to 117 across two batches, and the file count rose from 111 to 239. That pace shows the backend can now cover the backbone of common aten operators; the remaining work centers on precision patches and edge-case behavior.

6.2 Matrix extensions now have a three-layer stack, top to bottom

The backend is in LLVM, the dialect and lowering are in Buddy, and validation is in Triton and gem5. All three landed separately this week, with interface names unified on ZTT v0.6, while XSAI starts a separate native namespace. The two can coexist without conflict, but downstream users will have to pick a side.

6.3 The toolchain is in pre-release cleanup

Wheel slimming, dependency pinning, dialect replacement, board documentation — none of these are new features; they are debts that must be cleared before release. Biweekly report issue 081 putting V100 on-board measurements into the draft shows the documentation side is doing the same cleanup.
