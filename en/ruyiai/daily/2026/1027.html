Date: 2026-10-26　Sources: buddy-mlir main branch commit list, #1002 step by vscale, #1008 index vector auto-sizing, Biweekly Progress Issue 079

The most concentrated progress this issue comes from Buddy Compiler. From 22:48 Beijing time on 10-26 to 03:22 on 10-27, all seven commits within four and a half hours landed on VIR (vectorized intermediate representation), all revolving around the same switch use-scalable: first making strip-mining loops step by vscale (#1002), then making vector size selection compute by vscale = VLEN/64 and LMUL on RVV (#1003), then lowering vir.set_vl with results to scalable vectors (#1004, #1005), adding row permutation vir.shuffle for dynamic vectors (#1006), unifying the index conventions of vir.load and vir.store (#1007), and finally fixing the assertion crash of index vectors without an explicit width (#1008). 1.2 llvm-project upstream: 17 RISC-V passes migrated to NewPM within one hour (10-26)

Date: 2026-10-26　Sources: InsertVSETVLI migration, PreAllocZilsdOpt migration, DeadRegisterDefinitions migration

Of the 221 upstream commits brought in by the rebase, 21 are RISC-V related, and 17 of those are NewPM ports, all authored by Aiden Grossman and concentrated between 12:59 and 13:55 Beijing time on 10-26—under one hour. The list covers the backend’s main passes: post-instruction-selection VSETVLI insertion, CSR read/write and VXRM writes, VMV0 elimination, compressed instruction generation, prologue/epilogue optimization, base address merging, LoadStore optimization, Zilsd pre-allocation, branch optimization and QCRelax marking, plus dead register definition elimination, redundant copy elimination, indirect jump tracking, landing pad setup, and constant hoisting.

The significance lies not in any single change but in pipeline ownership: these passes long lived in LegacyPM, and migrating to NewPM aligns them with the new pass manager’s analysis cache, pass ordering, and debugging interfaces. The direct impact on downstream forks is that every rebase now carries this set of changes, and -passes= names and pipeline composition move up accordingly.

1.3 llvm-project upstream, remainder: VXRM speculative writes narrowed, Zibi equality exit, GlobalISel saturating conversions (10-26)

Date: 2026-10-26　Sources: VXRM speculative writes #234972, Zibi equality exit #225619, GlobalISel saturating conversions #234885

The remaining four commits fall into three areas. On the vector fixed-point side, #234972, merged at 09:22, restricts speculative VXRM writes to loops carrying the vxrm-pipeline-flush attribute, avoiding premature rounding-mode writes in loops without flush guarantees. On the loop optimization side, #225619 at 15:01 makes LSR prefer equality comparisons as loop exits on the Zibi target, matching its zero branch delay design. On the GlobalISel side, #2316b297 at 19:31 adds legalization for G_FPTOSI_SAT and G_FPTOUI_SAT, making floating-point-to-integer saturating conversions available on the global instruction selection path.

There is also #235546 at 17:00, a pure performance cleanup: converting the analyses used by gather/scatter lowering and the VL optimizer to lazy requests. Together the four commits point in the same direction—the RISC-V backend is filling in correctness details and new-pipeline compatibility rather than adding new extensions.

2.3 openRuyi: Go Backports Zvk Vector Cryptography Optimization for SHA-2 (10-26)

Date: 2026-10-26　Source: openRuyi PR #1512, openRuyi merged PR list

PR #1512, merged at 18:33, is the only distribution change in this window directly related to the RISC-V instruction set: it backports Go mainline’s Zvk SHA-2 support into openRuyi’s Go packaging. Zvk is the RISC-V vector cryptography extension family, and SHA-2 is its most commonly used algorithm suite; the backport means the Go toolchain in the distribution can use vector instructions directly on cores that support the extension, without waiting for the next major Go release.

IV. Buddy Compiler Updates

4.1 Seven VIR Commits in One Night: Loop Stepping and Index Conventions Completed in One Pass (10-26)

Date: 2026-10-26 to 2026-10-27　Source: #1002 Step by vscale, #1003 RVV Scalable Size, #1006 Dynamic Vector Row Permutation, #1007 Unified Index Convention

Seven commits were made back-to-back by the same author from 22:48 to 03:22 the next day, numbered #1002 through #1008, all prefixed with [midend][VIR]. The content breaks down into three layers.

The first layer covers loops and sizes: #1002 fixes the step of the strip-mining loop—previously, when vir.set_vl had no result, it was lowered to a main loop stepping by a constant vector-width, yet each iteration accessed memory by N times vscale lanes, so iterations overlapped when vscale was greater than 1; #1003 makes size selection compute by vscale = VLEN/64 on RVV, so that N and SEW determine LMUL instead of falling back to fixed-length vectors; #1008 fixes an assertion triggered when an index vector without an explicit width took its size from the element bit width.

The second layer is vir.set_vl with a result: #1004 allows it to lower to scalable vectors—previously its decomposition (vl and the width vector, and the scalar of vl modulo the width) depended on a compile-time-known lane count; #1005 further supports multi-dimensional dynamic vectors, because the query in decode attention is brought in from outside the region via vir.from_vector.

The third layer is memory access and permutation: #1006 adds vir.shuffle for row permutation of dynamic vectors; #1007 unifies the index conventions of vir.load and vir.store, so that both result-bearing and result-less set_vl map rows to the dimensions before the last dimension of the memref on multi-dimensional dynamic vectors, consistent with vector.load.

4.2 Motivation Chain: The Expressiveness Gap for Decode Attention and RoPE (10-26)

Date: 2026-10-26　Source: #1005 Multi-dimensional Dynamic Vectors, #1006 Row Permutation, buddy-mlir main branch commit list

Judging from the commit messages, these seven commits are not a generalized vectorization overhaul but were forced out by specific operators. The trigger is VIR’s decode attention: RoPE’s rotate_half needs to swap the front and back halves of a 128-element head and then negate them, i.e. [-x[1], x[0]], which is essentially a row permutation; but VIR previously could not express row permutation of dynamic vectors, so the query could only be computed outside with fixed-length vectors and then brought into the region.

Thus #1006 adds permutation, #1005 adds multi-dimensional dynamic vectors, and #1007 adds the index entry point—the three together form a path that “keeps the entire decode attention inside VIR.” The significance of this path lies in portability: once the operator can be fully expressed, switching the backend between RVV fixed-length and scalable only affects lowering, not the intermediate representation.

VI. Trend Observations

6.1 Upstream Switches Pipelines, Local Switches Representation: One Step Each on the Same Day

On 10-26, two RVV-related lines moved at the same time: upstream migrated 17 RISC-V backend passes into the NewPM, while locally VIR’s scalable vector support was completed up to the index convention. The former changes how the compiler’s internal pipeline is organized; the latter changes the intermediate representation’s ability to express RVV. Both point to the same outcome—RVV scalable vectors are no longer merely “generatable,” but “fully expressible and able to pass stably through the new pipeline.”

But the middle layer has not kept up. triton-riscv’s buddy-mlir anchor remains pinned to the 10-17 nightly, and the pytorch riscv branch has had zero commits for five consecutive days. This means that progress at both the upstream and local ends has not yet reached the two levels of the RuyiAI stack: operator generation and framework adaptation. To judge whether this stack is truly advancing, the next issue should watch two things: whether triton-riscv updates its anchor and rebuilds, and whether the pytorch branch resumes replay.

6.2 Release Window Pinned to Month-End by the Biweekly Report; the Distribution Enters a Wrap-Up Rhythm of Patching Security and Accumulating Packages

Issue 079 states two dates more clearly than before: ruyi 0.54.0 has been moved to the end of October due to a release cycle adjustment, with the current official version remaining at 0.53.0; openRuyi 2026.10 is still unreleased. Correspondingly, of openRuyi’s 80 commits this issue, 31 are security fixes, 18 are Rust crate completions, and 14 are version updates, involving 48 packages—a typical pre-release cleanup: first complete the dependency chain and clear CVEs, then cut the version.

Notably, an ISCAS software source synchronization issue has left packages-index with no package updates for nearly two weeks, which will cause what ruyi users see during ruyi update to lag behind the repository’s actual state. If 0.54.0 is released on schedule while the software source has not recovered, there will be a period of mismatch between the package manifest and the distribution version—a risk point to verify in the next issue.
