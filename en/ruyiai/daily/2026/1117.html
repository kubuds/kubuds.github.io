Today’s Focus: tilelang-riscv merges #6, RISC-V backend defaults to buddy-opt (11-16)

Date: 2026-11-16　Source: PR #6, merge commit 2204c7e

On 11-16 at 14:56, tilelang-riscv merged #6 “RISC-V backend defaults to buddy-opt, with two examples added for BOSC and GEMM”. 22 files, +835 −284, two commits: the 11-04 “select buddy-opt as default and split the two toolchain roots”, and the 11-13 “add examples, update docs”. This is the repo’s first change since #5 merged on 11-03, and the repo still has only the main branch.

The structural change is in toolchain.py (+62 −4): Buddy and LLVM each have their own independent toolchain root directory, TILELANG_RISCV_OPT can explicitly override the optimizer, and the optimizer choice is written into the RISC-V compilation cache key (kernel_cache.py +4). This is more practical than the surface-level “swap the default value” — previously there was still a risk of hitting stale cached artifacts after switching optimizers; now the cache key carries the optimizer, effectively turning “which toolchain is used” into a searchable build dimension.

Two kinds of examples were added: examples/riscv/gemm is a host-side FP16 GEMM (gemm.py +47), and examples/riscv/bosc is a standalone-buildable BOSC INT8 GEMM firmware (build.py +190, launch.c +122, env.sh and README). The largest documentation change is docs/get_started/BuildOnSG2044.md (+55 −178), rewritten from step-by-step manual operations to portable paths and streamlined usage. Three test files were also added: toolchain tests +126 lines, compilation cache tests +29 lines, and adaptation pipeline tests +45 lines, all under the testing/python/riscv directory.

Today’s Focus: triton and buddy touch the toolchain on the same day—LLVM decoupled and dump() restored (11-16)

Date: 2026-11-16　Sources: triton-riscv PR #123, buddy-mlir PR #1062, triton-riscv PR #115

At 18:14 on 11-16, triton-riscv opened #123, “Decouple the backend toolchain from Triton’s LLVM.” The problem is stated in the description: the CPU backend adds no C++ to libtriton.so, and all passes go through the out-of-process triton-shared-opt, but add_triton_plugin still links the MLIR libraries and their LLVM chain into libtriton.so, so the backend toolchain can only use the one LLVM that Triton itself was compiled with. The fix is to turn off TRITON_SHARED_BUILD_CPU_BACKEND and add llvm-hash.txt to pin the LLVM package separately: libtriton.so uses the LLVM matching the Triton source, triton-shared-opt is built with Triton, and buddy-opt／buddy-translate／buddy-llc／opt／llvm-objdump come from the buddy release, exchanging only textual IR with each other. RISC-V’s +v and +xsmtime are needed only by llc, so the LLVM that Triton depends on no longer has to carry RISC-V patches. Three files, +16 −2; llvm-hash.txt is temporarily pinned to nightly/v0.1.4.dev20261103, and apart from libtriton.so having one fewer plugin, the build artifacts are unchanged.

Later in the same window (11-17 01:23), buddy-mlir opened #1062, “Build LLVM with dump() support.” The LLVM package is built with -DLLVM_ENABLE_ASSERTIONS=OFF, while MLIR／LLVM’s dump() is defined only when assertions are enabled or LLVM_ENABLE_DUMP is set, so any downstream call fails to link. The PR provides evidence: mlir::Operation::dump() is present in the nightly/v0.1.4.dev20261103 package but has disappeared from the nightly/v0.1.4.dev20261113 package. Triton is exactly such a downstream: with NDEBUG on, the header does not even declare it, and with it off, it fails to link. The patch adds just one line, LLVM_ENABLE_DUMP=ON, preserving the Release build.

Both issues point to the same place: buddy’s LLVM package is already triton-riscv’s default upstream, and a single nightly package swap can block downstream compilation. Renovate’s #115 happens to pin the dependency to nightly/v0.1.4.dev20261113 (still being updated at 21:40 on 11-16); if #1062 does not land, that pin will keep causing trouble.

II. RuyiSDK Toolchain and Distributions

2.1 openRuyi Backports Zvk AES to Go 1.27 (11-16)

Date: 2026-11-16　Source: Commit 6592b995

At 14:21 on 11-16, the packaging repo landed SPECS: go: Backport SHA-2 AES optimization, adding the patch 1005-release-branch.go1.27-crypto-internal-fips140-aes-bl.patch (468 lines), with two lines added to go.spec in tandem. The description is straightforward: backport Zvk-based AES support from Go master to the 1.27 release branch; submitted by Julian Zhu.

Zvk is RISC-V’s vector crypto extension family. The patch fills in the FIPS-140 AES block routines under crypto/internal, allowing AES on riscv64 to use vector instructions rather than a purely scalar implementation; whether it is enabled depends on runtime detection of Zvk, and cores without the extension still take the original path. Last week the packaging repo had just bumped Go to 1.27.4 and filled in thirty-odd Go packages; this commit adds performance after the version settled, the second layer of “adapt first, optimize next.”

Date: 2026-11-16　Source: python-maturin 9d1e409e, mupdf 3d32c749, rpm-config e2baa296

Three small changes also landed the same day. python-maturin (17:44, 2 insertions, 1 deletion) adds the missing unicode-xid build dependency, which previously caused failures in a clean build environment due to the missing crate. mupdf (14:54, 1 insertion, 6 deletions) removes the entire python clang workaround—import clang.cindex now works directly without presetting environment variables.

rpm-config-openruyi (11:15, 16 lines) fixes the scoping of toolchain macros: the version-suffix macro was previously unrelated to the toolchain family, so setting a version number for one toolchain would also rename another toolchain’s commands—for example, specifying major version 23 for clang would expand the GCC command set to gcc-23. The fix makes the toolchain family a macro parameter, generating suffixes only for the selected family; the commit is marked Fixes 939eeb124. Such macro errors do not blow up immediately; they only surface when a package uses both toolchains at once.

III. Vector Extensions and Operator Optimization

3.1 +zvfbfmin Becomes a Necessity in the Default Feature String (11-16)

Date: 2026-11-16　Source: PR #117

Three boundaries in #117’s description are worth recording. First, without Zvfbfmin, LLVM does not lower even load and convert for scalable bf16 vectors, and llc directly reports Scalarization of scalable vectors is not supported. Second, buddy-mlir’s lower-vir-to-vector preserves scalable bf16 vectors and assumes by default that the target has Zvfbfmin, so without this extension downstream fails wholesale at the llc stage. Third, once added, conversions go through vfwcvtbf16.f.f.v and vfncvtbf16.f.f.w, delegating the widening/narrowing conversions between bf16 and fp32 to the vector unit.

The RVV targets the project supports (SpacemiT K3, SOPHGO SG2044) all carry this extension; cores without it can override the default feature string via TRITON_RISCV_LLC_FEATURES. DEFAULT_MARCH is untouched because it only drives the GCC link step, and GNU as 2.42 does not recognize zvfbfmin—objects compiled with +zvfbfmin still link fine.

VI. Trend Observations

6.1 Toolchain Boundaries Redrawn: One LLVM No Longer Covers Everything

triton-riscv #123 and buddy-mlir #1062 are two sides of the same day. The former pulls the backend toolchain out of libtriton.so and pins LLVM separately via llvm-hash.txt; the latter restores the dump() that had been disabled by LLVM_ENABLE_ASSERTIONS=OFF. Together they show that the RuyiAI line no longer assumes “one LLVM rules all”: Triton ships its own copy, the buddy distribution has one, and the backend llc has one, each handling its own segment, with interfaces converging on textual IR.

6.2 Compiler Choice Becomes a Build Dimension

tilelang-riscv #6 makes buddy-opt the default while also writing the optimizer into the cache key. This matters more than “changing a default”: once the optimizer enters the cache key, artifacts of the same kernel under different toolchains will not contaminate each other, and switching toolchains goes from “tweaking environment variables by trial and error” to “an explicit build parameter.” Adding BOSC and GEMM examples effectively gives this path two reproducible acceptance points.

6.3 Distributions Begin to Absorb RISC-V-Specific Extensions

openRuyi’s activity this week centered on extensions: Go backfills Zvk AES, the triton wheel ships with +zvfbfmin by default, and the kernel patchset and config were refreshed twice in one day. None of these are parts that generic upstream can cover automatically; they must be filled in item by item by distribution and toolchain maintainers. After RVA23, the differentiation is shifting from “whether it runs” to “whether the vector and crypto extensions are usable.”

6.4 The Daily Information Surface Keeps Idling

The official homepage is static, ruyiai-daily is on day nine of its gap, and external news has zero hits; all material in this issue comes from commits and PRs across four GitHub organizations plus two forum posts. In this state, the report’s judgment value depends mainly on understanding the commit contents rather than the number of news items—especially for the triton release with empty release notes, where one can only go back to the commits the tag points to.
