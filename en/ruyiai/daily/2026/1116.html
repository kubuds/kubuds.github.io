Today’s Focus: BUDDY MLIR 0.1.4 Officially Released, Nineteen of Thirty Commits Land in the VIR Middle End (11-15)

Date: 2026-11-15　Source: BUDDY MLIR 0.1.4, 0.1.3 to 0.1.4 diff, PR #1059

At 08:01 on 2026-11-15 (Beijing time), buddy-mlir shipped the official 0.1.4 release, two weeks after 0.1.3 (10-31). From 0.1.3 to 0.1.4 there are thirty commits in total, nineteen of which carry the middle-end prefix, and they share a single theme: taking the scalable-vector (VIR) lowering path from “can run a handful of operators” to “covers a class of shapes.”

These nineteen commits fall into four groups. The first group is shape coverage: #1017 fixes narrowing in scalable-vector tiling counts; #1056 completes all reduction kinds for integers and floats; #1057 lowers rank-0 memref linalg.fill to a single store; #1058 supports integer matrix multiplication and fixes dynamic dimensions; #1041 routes convolution through VIR as well. The second group is VLEN handling: #1028 lowers set_vl for an exact rvv-vlen; #1029 can also generate code for any VLEN when there is no rvv-vlen; #1032 and #1037 respectively prevent “a model compiled for one exact VLEN” from being moved to a different VLEN, and lower according to the host’s V extension width; #1046 validates dynamic vector types and prints the scaling factor as m2; #1048 preserves the scaling factor when cloning dynamic vector types. The third group is tiling and composition: #1031 lowers scalable-vector shuffle in several slices; #1047 merges vector slices for associative reductions; #1045 gives vir.set_vl a single-block region; #1050 documents which operators strip-mined set_vl supports; #1051 handles full-lane reductions of vector<[1]xT>. The fourth group is the seven commits from 11-12 already covered in the previous report (the masking, libm, bf16, fast-math, reduction, rank-0, and integer matmul items among #1052 to #1058), which all enter the official release this time.

Beyond VIR there are eleven side branches: on the model side, #1042 adds YOLOv8 detection and pose on SpacemiT K3, and #1044 changes the A100 llc parameters to be taken from a100_llc_args; on the runtime side, #1018 adds a shared serving generation controller; on the compiler side, #1025 bumps LLVM to bef335e2143c, and #1027 ships LLVM with NVPTX, AMDGPU, and lld; on the testing side, #1026 adds PyTorch 2.15 to the matrix; on the backend side, #1033 adds SPM optimization for BOSCAME; on the tooling side, #1030 lets the kernel lower VIR to the target corresponding to the llc options.

Worth noting is the release timing: the last commit on main is still #1058 at 14:44 on 11-12, and there were no new commits between then and the 11-15 release. In other words, 0.1.4 and the 11-13 nightly are the same tree; the official release effectively gives that tree two extra days of observation rather than stacking another layer of changes.

Today’s Highlight: openRuyi Adopts python-torch-ruyiai, RuyiAI’s PyTorch Snapshot Enters the Distribution (11-13)

Date: 2026-11-13　Source: openRuyi commit add python-torch-ruyiai, python-torch-ruyiai.spec, PyTorch riscv branch

At 22:58 on 11-13 (Beijing time), the openRuyi packaging repo landed a new package, python-torch-ruyiai. This is the first time RuyiAI appears in openRuyi as a distribution package: version 2.15.0~a0+git20260921, source tracking the RuyiAI-Stack riscv branch (commit 6d667e1e), CPU-only, built with the clang toolchain, and it cannot coexist with the distribution’s existing python-torch.

Three packaging difficulties can be read from the spec file. The first is BLAS: OpenBLAS’s Fortran cdotu_/cdotc_ return complex values in registers, while PyTorch’s non-CBLAS path takes the result from the first argument per f2c convention, so dot and vdot on complex tensors silently return 0; patch 2001 enables the CBLAS path and makes PYTORCH_BLAS_USE_CBLAS_DOT=ON in the spec take effect under native builds as well (upstream only reads this variable during cross-compilation). The second is RVV gating: the __riscv_v_intrinsic macro is also defined under the rva20 baseline, so the old condition selected deep-convolution vector kernels that should never be used; patch 2011 switches to checking __riscv_vector. The third is the build backend: the RuyiAI snapshot requires scikit-build-core 1.0 or later, while openRuyi still ships 0.12.x and python-pyvex pins an upper bound, so patch 2012 simply bundles this backend as source, while also removing the license file glob that cannot be satisfied after trimming the third-party tree.

Dependency handling follows the “use system libraries where possible” approach: a batch of switches such as USE_SYSTEM_CPUINFO, USE_SYSTEM_ONNX, USE_SYSTEM_SLEEF, USE_SYSTEM_PYBIND11, and USE_SYSTEM_PTHREADPOOL are enabled, USE_CUDA, USE_ROCM, USE_MKLDNN, and USE_XNNPACK are disabled, and distributed and TensorPipe are retained. The third-party directory keeps only the components actually compiled (gloo, flatbuffers, cpp-httplib, kineto, tensorpipe, miniz), and tensorpipe’s bundled libuv and libnop are also unpacked. The check phase does not run the fork’s full test suite (most are blocklisted on riscv64, and the remaining failures are recorded in fork issues 33 and 34); instead it runs a functional smoke test: matrix multiplication, autograd, two hundred training steps, plus a guard that complex dot/vdot must not be zero—exactly covering the path fixed by patch 2001.

The same night, the packaging repo also landed llvm22/23/24 with PIE enabled and clang resource dir generation, clang-wrap bumped to 20261113, and cmake bumped to 4.4.5; judging by timing, these fill in the installation layout for the in-distribution clang build.

1.1 pytorch riscv branch: CI criterion revised twice in one day, return code replaced by stats file (11-13)

Date: 2026-11-13　Source: PR #56, PR #57

At 00:25 on 11-13, PR #56 was merged, adding a criterion to the riscv64 CI yaml: when a new job builds successfully but executes no test cases (0 failures, 0 passes), the parent job previously recorded a pass, so a check was added to fail on any non-zero Jenkins return code. Seventeen hours later (17:04), PR #57 was merged, removing that return-code check entirely and instead fetching pytorch-ci-stat.json via curl --fail first, then judging by the statistics values. The two commits total +35 −20 lines, both touching only .github/workflows/ci-riscv64.yml.

Revising the same criterion twice in one day shows the return-code approach is inherently unstable: Jenkins exit codes can still be 0 when the build succeeds but all test cases fail, so the return code alone cannot block false greens. After switching to reading the stats file, the criterion shifts from “did the job die” to “did the test cases run”—the same direction of tightening as the “zero test cases passed” criterion in the previous report.

III. Vector Extensions and Operator Optimization

3.1 ABI mismatch in bf16 conversion helper functions: llc reads the return value from a floating-point register, but the launcher returns it as an integer (11-14)

Date: 2026-11-14　Source: PR #121, issue #114

A new PR fixing bf16 was opened on 11-14. In the launcher, two conversion helper functions were originally declared with integer prototypes: the truncation function returned uint16_t, and the extension function’s parameter was also uint16_t; but the call sites generated by llc pass bfloat through floating-point registers — on x86-64 the return value lands in xmm0, on riscv64 in fa0, and the caller reads the low 16 bits of the register. Integer returns go through eax/a0, so every kernel that converts an fp32 result to bf16 was storing zeros or garbage left over from the previous floating-point operation.

The PR’s verification was quite thorough: on an x86 host, disassembly shows the call site as callq __truncsfbf2 followed by vmovaps %xmm0 and then vpextrw, with eax never read; cross-compiling to riscv64 (with +zvfbfmin removed from the feature string) shows fa0 passed in and fmv.x.w reading back from fa0, while the helper’s integer return is in a0. The fix is to change the prototypes to float so both sides land in the same register class, with the bf16 bits still in the low 16 bits; __bf16 cannot be used because the launcher is compiled with g++, and g++ 13 on Ubuntu 24.04 does not have that type on riscv64. The newly added test_bf16_convert.py compares bit-for-bit against torch, covering multiple round-to-nearest-even edge cases; four of them failed before the fix.

3.2 Five batches of fifty-four FlagGems operator examples: 587 passing, 41 bf16 cases strictly xfailed (11-13)

Date: 2026-11-13　Source: PR #120

Another PR opened on 11-13 adds FlagGems operator examples to triton-riscv in batches: five independent batches combined into one integration sequence, 13 commits in total, 54 operator examples, covering unary math (acosh, arcsin, log1p, sinc, etc.), binary operations (bitwise_xor, copysign, fmax, nextafter, etc.), activations (hardshrink, mish, relu6, etc.), reductions (amin, argwhere, frobenius_norm, nansum, etc.), window functions and losses (bartlett, blackman, hamming, kaiser, bce, huber_loss, kl_div, l1_loss).

The five test groups on the x86 backend passed 77, 128, 114, 126, and 142 items respectively, 587 in total; another 41 bf16 cases were written as strict xfails, precisely because of the launcher ABI defect in 3.1 — an ungated riscv64 CI run showed all 41 bf16 tests failing. 3.3 After the explicit target goes through -O3, the flash attention object gains three vector divides (11-14)

Date: 2026-11-14　Source: PR #117

A quantifiable change brought in by #117 is recorded in the test changes: the assembly assertions for the two attention kernels previously looked for scalar fdiv.s; after the middle-end runs at -O3 the division is vectorized, so the assertions were changed to accept vfdiv.vv/vfdiv.vf. Taking the flash attention kernel as an example, the object goes from 1 vfdiv.vf plus 1 fdiv.s and 3 vfmul to 4 vfdiv.vf and 36 vfmul. This is the most visible difference between the two build paths, “middle-end not run” and “run at -O3”.

3.4 wheel slimmed by 40% with strip-all: triton-shared-opt drops from 407 MB to 118 MB (11-13)

Date: 2026-11-13　Source: PR #116

#116 changes the strip applied to the bundled LLVM and buddy tools at packaging time from --strip-unneeded to --strip-all. Previously the single triton-shared-opt executable carried nine debug sections and 407 MB; after the change it is 118 MB, and applying the same treatment to the other six tools shrinks the entire wheel payload from about 970 MB to about 576 MB. The PR also records a rejected approach: pointing bin/llc at buddy-llc (the two produce identical output), but buddy-llc does not exit after writing its output, so it cannot replace the ordinary llc invoked by the non-IME path.

4.2 Open PR #1059: Replacing memref Copies with Vector Moves, Cutting the Sample from 66 ms to 2.8 ms (11-13 Status)

Date: 2026-11-13　Source: PR #1059

#1059 is still under review, but the data is worth recording now. It addresses a regression in finalize-memref-to-llvm: only memrefs with identity layouts or statically contiguous shapes can use llvm.memcpy; all other memref.copy operations degrade into memrefCopy calls that copy one element at a time—and the masked loads and stores in Triton kernels (dynamic lengths with offsets, matrix tiling) are exactly this kind of copy. When profiling on K3, such copies accounted for 44% to 99% of kernel time for add, exp, softmax, and matmul after lowering through VIR.

The fix lowers memref.copy with unit stride in the last dimension into vector loads and stores using vir.set_vl on the last dimension, with a loop over rows; in the fixed-vector path, the main and tail loops change from affine.for to scf.for, because the vl computed inside the loop is not a valid affine operand. Results on K3: add on X100 (VLEN 256) drops from 66.1 ms to 2.76 ms, and on A100 (VLEN 1024) from 138.9 to 2.26; across 1811 FlagGems kernels, memrefCopy calls drop from 3694 to 819 (affected kernels from 1499 to 317); the 4043-test suite still passes 4036 tests on SG2044 and K3, with the other 7 failing under the original pipeline as well.

VI. Trend Observations

6.1 The packaging layer has become the new battleground for RuyiAI adoption

The two heaviest items in this window are not about algorithms: one is turning a PyTorch snapshot into a distro package, the other is cutting wheel size by forty percent. Of the six patches in the torch package, three are build and ABI issues (CBLAS complex dot, system fmt and concurrentqueue, submodule checks), one is a macro definition gated on the wrong condition (__riscv_v_intrinsic vs __riscv_vector), and only one is a genuine feature adaptation. This shows the RuyiAI stack has moved from “can it compile” to “can it be installed, can it be linked, can other packages depend on it”—the pitfalls at this layer are more tedious than vectorization in the kernel, and they matter more to whether a user’s first attempt succeeds.

6.2 The stable release is the same tree as the nightly

The way 0.1.4 was released is worth noting: the last batch of VIR changes landed on 11-12, a nightly came out on 11-13, the stable tag was cut on 11-15, with zero commits in between. This effectively defines “release” as confirmation of an existing nightly rather than another round of integration. That is good for downstream—the nightly pinned by Renovate is the same tree as the stable release, so switching over brings no functional difference, just a more traceable version number.

6.3 The performance ledger has turned to the copy page

The data in #1059 shows that the biggest cost in the VIR path right now is not arithmetic but data movement: masked loads and stores degrade into element-by-element copies, accounting for 44% to 99% of kernel time, which makes the simplest operator like add forty times slower than the non-VIR path (66.1 vs 1.60 ms). After switching to vector moves a gap remains (2.76 vs 1.60), but it is back in the same order of magnitude. This thread follows directly from last issue’s “shape coverage”: once shapes are filled in, the next gains come from pushing down peripheral overhead such as copies and layout transforms.

6.4 CI criteria are still being trial-and-errored

The pytorch riscv64 CI changed its criteria twice in one day: first adding the Jenkins return code, then switching to reading a stats file. Such back-and-forth is common in small teams, but it exposes a non-trivial problem—a pipeline that “builds successfully but executes zero test cases” renders every downstream green badge meaningless.
