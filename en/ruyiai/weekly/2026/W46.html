2.2 triton-riscv’s Heterogeneous Path: RISC-V Host Driving AMD Cards

Date: 2026-11-10　Source: PR #110 enable GPU backend by default, README

After #110 merged, this repo’s positioning expanded from “running Triton only on the vector units of RISC-V CPUs” to “driving heterogeneous accelerators from a RISC-V host.” Of the three changes, the build side builds and packages the riscv64 AMD codegen library using the existing Buddy LLVM SDK; the driver side fixes the ambiguity when choosing between CPU and GPU, with the rule being to prefer an available GPU (a net deletion of four lines in that file); the documentation side adds an AMD GPU section to the README, explaining that the backend activates itself via torch.version.hip when ROCm is present, that the wheel does not bundle the ROCm runtime, and that forcing a fallback to CPU uses TRITON_DEFAULT_BACKEND=triton_shared.

Real-hardware validation is what gives this change its weight: SG2044 with an RX 7900 XTX, with torch and ROCm from openRuyi’s software repository, plus a test of automatic fallback when the GPU device is hidden. At a time when no mainstream AI accelerator card ships a RISC-V host driver, supporting AMD cards first is the most realistic step—ROCm’s RISC-V-side work is already maintained in the openRuyi repo, and the same group of people is pushing both.

The timing gap is worth noting: the nightly nightly/2026-11-10-209274f published at 10:22 that day predates this merge, so that package does not yet include the GPU backend.

2.3 Release Chain and Artifacts: Three CI Fixes, Wheels 40% Lighter, Explicit Targets Switched to -O3

Date: 2026-11-11 to 11-12　Source: PR #113 shared git auth, PR #116 wheel slimming, PR #117 -O3 and +zvfbfmin

All three merges on 11-11 were in the release chain; none changed compiler functionality. #113 extracted the “one-off global git config” that CI and release.sh each duplicated into a shared scripts/_git-auth.sh: anonymous git traffic on the self-hosted riscv64 runner cannot obtain authentication, so when upstream FetchContent pulls googletest it returns 401 and hangs at the username prompt with no tty. #111 fixes the release script itself; #112 is documentation, removing the torch install command no longer needed on the CPU path after #110, and adding to the AMD section that “torch must be installed, and it must be a build that can use the AMD GPU.” All three were by the same author, concentrated between 17:59 and 21:11.

III. RuyiSDK Toolchain and Distributions

3.1 ruyi 0.54.0: Turning “Can It Be Installed” into a Computable Fact

Date: 2026-11-10　Source: ruyi 0.54.0, PR #507 ELF ABI compatibility

The feature surface of 0.54.0 is exactly the full content of the 11-02 pre-release 0.54.0-beta.20261102; the official release adds only one version-number commit over the pre-release, totaling seventy-one commits and seventy-four files since 0.53.0. The core is ELF ABI compatibility: whether a precompiled binary can run on a target device depends on a set of facts scattered across the ELF file header—which dynamic libraries it needs, which symbol versions it requests from those libraries, and architecture-specific capability requirements. Previously nothing in the software source recorded these; ruyi now scans them out, stores them, and compares them before installation.

The RISC-V path is the most labor-intensive to collect, because its extensions are concatenated as versioned strings: this period’s commits include parsing versioned single-letter extensions, filtering ld.so.cache entries by host floating-point ABI, and factoring in stack alignment requirements. Host-side probing for x86-64 and AArch64 is also implemented; host libraries are resolved by the requested soname, and an unresolvable soname reports “undetermined” rather than a hard failure—this three-state design separates “cannot install” from “don’t know.” The data plane goes through the repository-side ABI sidecar, resolved by distfile name; rescan-package-abi and plugin artifacts gain strip-components to handle archives with leading directories; the sidecar has a size cap, and a bad sidecar is discarded as “no ABI information.”

IV. Vector Extensions and Operator Optimization

4.1 The three vector repos remain silent; all vector-side progress is in VIR

Date: 2026-11-09 to 11-13 (status)　Source: FBGEMM, VecIntrinBench, IntrinTrans

The three repos VecIntrinBench, IntrinTrans, and FBGEMM saw zero commits all week, with head commits stalled at 02-13, 06-25, and 07-13 respectively—silence that has now persisted for months. This does not mean there is no vector-side progress: this week’s vector changes all occurred at the VIR layer of buddy-mlir, and they fall into two categories—one determining “whether something can enter a vector loop” (coverage), the other determining “whether the vector loop is fully utilized” (performance). Investment is concentrated in the compiler rather than in measurement tooling, and this division of labor has remained unchanged since September.

4.2 i1 masks read/written byte-wise (#1052)

Date: 2026-11-12　Source: PR #1052

When the memref element type is i1, scalable vectors were previously rejected outright (with the message a memref of i1 needs fixed vectors), because a memref occupies one byte per element while an i1 vector occupies one lane per bit—only fixed-length vectors have a per-lane lowering. Triton’s load/store masks happen to be exactly i1 memrefs: when going through the pure VIR pipeline with scalable vectors, 179 of the 325 Triton-RISCV test files got stuck on this error, making this the most broadly impactful of the week’s seven patches.

The fix is to read/write byte-wise: contiguous accesses use llvm.load/store of i8 vectors, while non-contiguous strip-mined regions use vp.strided.load/store with all lanes enabled; incidentally, i1 lanes are now sized as one byte—previously a region whose first dynamic vector was i1 was counted as 1 bit, which under VLEN 256 would yield a size like vector<[512]xi1>, i.e. sixteen register groups.

4.3 Per-lane expansion of libm-only math functions (#1053)

Date: 2026-11-12　Source: PR #1053

Math functions that LLVM refuses to lower on scalable vectors (erf, erfc, cbrt, powf, atan2, acosh, etc.) are now expanded per lane: for vector<[N]xT>, each of the N times vscale lanes is extracted one by one, the scalar function is called, and the result is inserted back. The trigger was that convert-math-to-libm handled scalable vectors the same as fixed-length vectors, computing only the first N and silently zeroing the rest—a scalable erf under VLEN 128 (vscale 2) had half its lanes wrong. The effect shows directly in the test surface: on the FlagGems suite of 4045 items on SG2044 (VLEN 128), the number passing rose from 3980 to 4006; the 26 fixed items are test_erf and test_gelu, with no new failures.

4.4 The two bf16 paths and exhaustive verification (#1054)

Date: 2026-11-12　Source: PR #1054

RVV places bf16 in vector registers only with Zvfbfmin; without that extension, LLVM refuses to lower even a single load. The change adds an rvv-mattr parameter to the lowering, defaulting to assuming Zvfbfmin is present (Buddy’s several RVV targets—K3’s X100 and A100, and SG2044—all have it); when -zvfbfmin is given explicitly, it instead treats values as integer bits, reading/writing bf16 vectors as i16, using integer operations for extf and truncf (truncf rounding to nearest-even), and routing absf and negf through the sign bit.

The verification method is the heaviest part of the week: truncf covers all 2^32 f32 values, while extf, absf, negf, and extf-mulf-truncf cover all 2^16 bf16 values, compared bit-for-bit against the Zvfbfmin path on both the SG2044 and K3 cores, with identical results. This level of verification cost shows that bf16 is being treated as a shipping path rather than an “optimization for when there’s time.”

4.5 fast-math flags and all reduction kinds (#1055, #1056)

Date: 2026-11-12　Source: PR #1055, PR #1056

#1055 fixes fast-math flags being dropped in the strip-mined lowering: an arith.mulf plus arith.addf carrying contract was rebuilt as plain fmul and fadd, which LLVM would not fuse. Now the flags propagate with the same-kind operators into the vector loop and the tail, so f32 multiply-add can emit vfmacc, and bf16 under +zvfbfwma emits vfwmaccbf16; the author compared the fmaf expansion bit-for-bit over 4M lanes on K3’s X100 and A100, with matching results. This is the only one of the seven patches that directly changes instruction selection.

#1056 expands vir.reduce from recognizing only floating-point add and maxnum to all kinds of vector.reduction: add, mul, minsi, minui, maxsi, maxui, and, or, xor, minnumf, maxnumf, minimumf, maximumf, with integers supported as well, and a verifier checking that kind and element type match. Previously Triton’s integer sum, min/max, product, and all/any (along with the argmin, argmax, count_nonzero, bitonic sort, and radix sort that depend on them) all remained in loops. The change adds 570 lines across 9 files.

4.6 Wrapping up residual paths: rank-0 fill and integer matmul (#1057, #1058)

Date: 2026-11-12　Source: PR #1057, PR #1058

#1057 lowers linalg.fill on rank-0 memrefs (mostly reduction accumulators) to a single memref.store, reducing residual linalg.fill in the 1811 FlagGems kernels from 393 to 0. #1058 enables integer matmul to lower as well: when A and B are the same integer type and no wider than C, sign- or zero-extend first and then multiply-add (without fma); on RVV, int8 matmul yields vsext.vf2 plus vwmacc.vx, and unsigned yields vzext.vf2 plus vwmaccu.vx; the same patch also fixes an assertion failure in dynamic-shape matmul—M and K were originally taken inside the vir.set_vl region and erased while still in use by a later pass. After the change, no linalg.matmul remains among the 1811 kernels.

Together, the two patches provide a verifiable coverage metric: not a benchmark score, but “how many linalg or scalar paths remain.”

V. Buddy Compiler Updates

5.1 The First Half of VLEN Exactness: #1032 and #1037

Date: 2026-11-08　Source: PR #1032, PR #1037

The problem #1032 addresses is a class of failure that fails the wrong way: no error, just wrong results. A RISC-V model built for an exact VLEN has vector code that is valid only for that one VLEN—llc is explicitly told the VLEN (+zvlNb and -riscv-v-vector-bits-max), and the scalable vectors in decode attention are sized accordingly. On a different VLEN, the model does not crash; it simply produces wrong results.

The fix moves validation forward to load time: runtime/rvv/BuddyRvvVlen.c is linked into the model library as a constructor; as soon as the library is loaded it reads vlenb, and if it does not match the exact VLEN used at build time, it prints a message and terminates the process with _exit(1). Using _exit rather than exit is deliberate—running destructors while the loader holds its lock would deadlock. A follow-up change after review moved the check from “judging by build variables” to “judging by the final llc options”: previously a native build could specify the VLEN via the model’s own LLC_ATTRS, and if BUDDY_RISCV_VLEN disagreed with it, the checked value would not match the actual code; moreover, the check was only linked into the third stage, missing Qwen3-VL’s vision and decode shims as well as the layered-linking paths. Now the build script extracts the exact VLEN from the final llc options (reading the same place as VIR lowering), and conflicting options fail outright at configure time. Testing is the other half of this change: test_buddy_rvv_vlen.py builds the model library for each VLEN from 128 to 65536; only the host’s own can load, and all others exit with code 1. The docs were updated in step, with the two DeepSeek-R1 deployment notes for A210 and K3 spelling out the boundary between “which builds are exact-VLEN” and “which are generic RVV”—A210’s kernels are fixed-length vectors with no VIR, so it is a generic build; K3’s prefill_ime requires 1024, so it is exact-VLEN.

#1037 fixes an error in the other direction: -lower-vir-to-vector, when neither rvv-vlen is given nor scalable vectors are enabled, sizes fixed-length vectors by the host register width, but its host detection covers only x86 (AVX2, AVX-512) and SVE; a RISC-V host with the V extension always falls through to the generic default (128 bits, 16 registers). The consequence showed up in tests: since #1030, the kernels pipeline lowers VIR by host when no llc options are given, and the riscv64 CI host is VLEN 256 but was treated as 128-bit, so the squared q and k norms were split into vector<32xf32> partial sums, differing in order from the bit-for-bit comparison against the vector kernels, and vir decode qk_norm ... same bits evaluated to false. The author first added a change that pinned rvv-vlen=1024 use-scalable=false in tests only, then reverted it—that would have created a second place to set VLEN outside the llc options, conflicting with the direction of #1032. The final fix detects a RISC-V host in the lowering stage (reading host CPU features and hwprobe) and sizes by the real VLEN.

5.2 f32 YOLOv8 Runs End-to-End Through VIR (#1041)

Date: 2026-11-09 (merged 11-10 01:07)　Source: PR #1041, merge commit 18c66ec

#1041 takes the f32 YOLOv8 graph end-to-end through VIR: first Linalg-to-VIR lowering, then VIR-to-vector-dialect lowering. Previously this pass had no convolution pattern, and three other operator classes in the graph failed outright—one change adds both the convolution and those three. The scale: fourteen files, 1,646 lines added, 115 removed, thirteen commits.

Both convolution families are covered: 2D NHWC with HWCF and 2D NHWC with FHWC. Vectorization is along the output channel F; for each (kh, kw, c) the input element is broadcast into one vir.fma per output pixel, so every vector access is contiguous and there is no cross-lane reduction—reductions need horizontal instructions and a subsequent reduction tree, which is costly at narrow VLEN; the price is that the FHWC filter must first be copied in parallel into an HWCF buffer, trading one extra transfer for contiguous access in the inner loop.

The three previously failing operator classes are filled in as well: rank-0 inputs (memref<f32> fed directly into linalg.generic reports invalid reassociation at memref.expand_shape; changed to load once and broadcast), linalg.reduce preserving the last dimension (e.g. DFL softmax’s 1x16x4x2100, dimensions=[1], addf combined with maximumf), and named ops reading linalg.index (e.g. linalg.map iota in upsample). The on-device numbers are clear: on K3, f32 YOLOv8 pose’s raw output changes by at most 6e-5, and the gap to PyTorch remains within 6e-4 (bus) and 8e-4 (zidane), unchanged from before; the detect model’s detections are unchanged and speed does not drop; f32 and IME dynamic library outputs are byte-for-byte identical to before.

5.3 YOLOv8 Enters rax: Detection and Pose on the K3 Matrix Engine (#1042)

Date: 2026-11-10　Source: PR #1042

#1042 wires Ultralytics YOLOv8 into buddy-cli’s rax format: yolov8n detection (eighty COCO classes) and yolov8n-pose (seventeen keypoints), both with 320x320 input. The f32 model goes through VIR lowering; if the spec says ime: true, it runs on the SpacemiT K3 matrix engine instead.

The two fixes added during review are more informative than the model itself. First, weight validation: the manifest carries params_size, and the runner requires the weight file to match it; previously a short weight file let the model read past the buffer. The runner is also required to accept only rax packages, because when the library and weights are supplied separately the pose model would be run with the detection model’s parameters. Second, TCM copies: the TCM copy of IME weights is cached by weight address, so new weights read into a freed buffer would hit the stale copy; now the kernel-side invalidation function is called after every weight load. The spec keeps both params_size and ime_params_size, so the f32 version can still be built with ime: false—one graph, two backend paths, one comparable baseline.

7.2 Coverage before performance: the 393→0, 2→0, 179→0 framing

Of buddy-mlir’s seven patches this week, only #1055 directly changes instruction selection; the other six bring forms previously left in loops into the vector path: i1 masks, libm-only math functions, bf16, reduction kinds, rank-0 fill, and integer matmul. Contrast this with the previous day’s #1050, which narrows the strip-mined remainder. The division of labor across the two days is clear: first let the vector loop fill its lanes (performance), then let every operator enter the vector loop (coverage). Reversing the order wastes effort — a full-width loop with only the same few operators inside it.

7.3 VLEN 1024 becomes a shared pressure point for compiler and runtime

Three changes this week point directly at VLEN 1024: load-time validation (#1032), reduction lane loss (#1051), and the strip-mined remainder (#1050). What they share is the same hardware fact recurring at every layer — K3’s prefill_ime must be 1024, 16 f32 on the A100 core is one full vector, and a shape like vector<[1]xT> simply cannot be reached at VLEN 128/256.

The same signal appeared upstream in the same week: V8’s review list shows “Allow vlen=1024” (CL8585179). This shows that long vectors are no longer just a local configuration for one board, but are beginning to enter the general paths of runtimes and browsers. The risk follows — CI’s riscv64 runner is VLEN 256 while shipping hardware is 1024, so the two are inherently misaligned in test coverage; a defect like #1051, “all green in CI, all wrong on the board,” is exactly the product of that misalignment.

7.4 The verification cost of silent wrong values has reached the scale of exhaustive inputs

#1054 ran all 2^32 f32 values through truncf and all 2^16 bf16 values through conversions and sign operations; #1055 compared the fmaf expansion bit by bit across 4M lanes; #1041’s acceptance criterion was “byte-for-byte identical to before the change”; #1051’s acceptance criterion was 25 reduction tests going from wrong to right. The four use different verification methods, but all answer the same question: is the result correct, not is it fast.

The reason is clear: the defects fixed this week are almost all “no error, just wrong results” — a model built for an exact VLEN silently misbehaves on different hardware, scalable erf has half its lanes zeroed, reductions keep only lane 0, and mask-based size computation yields sixteen register groups. Crashes are easy to spot; wrong values are not. When verification cost rises to the scale of exhaustive inputs, it means this stack now treats foundational operators like bf16 and reductions to shipping standards.

Worth noting are the two new governance repos this week: the release spec repo writes requirement numbering and priority into process, and ruyi-deck is positioned as an “operations console for repos and releases.” Neither produces code, yet both point at the same gap — a monthly release must ship across the packaging repo, images, and firmware, and what is missing is not commits but the step that converges commits into a releasable version.

7.6 “Can it be installed” becomes a computable fact for the first time

ruyi 0.54.0 turns ELF ABI compatibility into a three-state determination (compatible, incompatible, undetermined) and exposes it in three places: list, install, and admin check-abi. The significance is not the feature itself but turning “can this package run on my machine” from a judgment call into data that can be queried, compared, and troubleshot.

This matters especially for RISC-V: the same prebuilt binary behaves differently on hosts with different extension combinations and different floating-point ABIs, and in the past the only option was trial and error. The three-state design also leaves room for “undetermined,” avoiding treating the unknown as incompatible — that distinction determines whether the tool is usable in real environments. The next thing to watch is sidecar coverage: which packages have ABI information added and which still have “no information.” The packages-index mentioned in issue 080 adding ABI compatibility information for some packages is a continuation of this line.
