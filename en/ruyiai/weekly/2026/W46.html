II. RuyiAI Stack Progress (PyTorch / Triton / TileLang RISC-V Adaptation)

2.1 triton-riscv: From “Eighteen Nightly Tags” to the First Official Release

Date: 2026-11-06 to 2026-11-14　Source: Official release tag, PR #105 README switched to wheel-first

This repo completed three steps this week: establishing the release tier (the first release/ tag), switching the install path from source to wheel, and taking the heterogeneous backend from “compiles” to “runs on real hardware.” The three steps depend on each other in sequence—without a reproducible wheel tag, GPU backend validation could only stop at source builds; and AMD backend validation in turn exposed several issues in the release chain that only appear on the self-hosted riscv64 runner.

2.1.1 The Tag Itself Is the Entire Content of the Release Action

Date: 2026-11-06, 11-09　Source: release/20261108-6895885, PR #101

release/20261108-6895885 points to commit 6895885, the merge commit of the 11-06 “add missing riscv64 codegen library for AMD” (#102), the same point as nightly nightly/20261106-6895885. The three commits that day (#105, #106, #107) all landed after the tag and did not make it into this package—meaning the first official release actually packages last weekend’s code state.

Two supporting changes to the release chain had already landed earlier in the window: #101 fixed two release-chain issues exposed after #100 (the release workflow now uses the same checkout action version as CI, and scripts/release.sh adds a backend registration step so that wheels produced by release carry the same plugin registration info as wheels built by CI); #102 makes setup.sh build the AMD codegen library locally and place it at the agreed path when it detects it is missing, with env.sh pointing TRITON_AMD_CODEGEN_PATH at it. The nightly additionally appends a unique version suffix .dev<date>, because previously every build shared Triton’s own version number and the package index would reject duplicate versions.

2.1.2 Install Path Switched to Wheel-First, Quick Start Now Points to Disassembly

Date: 2026-11-09　Source: PR #105, PR #107

#105 rewrote the install section of the README: first the wheel path and the package index hosting it, then the required LLVM archive and the variable pointing to it; the source path is compressed into make setup (create .venv, clone the pinned Triton, download the pinned LLVM and buddy build), and the previous instructions—”create a virtual environment, install dependencies, fifteen variables in the env script”—are condensed into a short note. #107 then made a correction: the package index does not yet have triton and buddy tools, so the address given for the binary install in the README would fail; it was changed to point to the two projects’ respective GitHub releases and install wheels from disk. The same commit also fixed a lit crash under Python 3.14—Triton uses which to find lit on PATH, and the lit in the LLVM tree calls main at module level; Python 3.14 defaults to the forkserver start method on Linux, which crashes directly on re-import; the fix is to put the build interpreter’s bin directory first on PATH.

2.2 triton-riscv’s Heterogeneous Path: RISC-V Host Driving AMD Cards

Date: 2026-11-10　Source: PR #110 enable GPU backend by default, README

With #110 merged, this repo’s positioning expands from “running Triton only on the vector units of RISC-V CPUs” to “driving heterogeneous accelerators from a RISC-V host.” Of the three changes, the build side builds and packages the riscv64 AMD codegen library using the existing Buddy LLVM SDK; the driver side fixes the ambiguity when choosing between CPU and GPU, with the rule being to prefer an available GPU (a net deletion of four lines in that file); the documentation side adds an AMD GPU section to the README, explaining that the backend activates itself via torch.version.hip when ROCm is present, that the wheel does not bundle the ROCm runtime, and that forcing a fallback to CPU uses TRITON_DEFAULT_BACKEND=triton_shared.

Real-hardware validation is what gives this change its weight: SG2044 paired with an RX 7900 XTX, with torch and ROCm from openRuyi’s software repository, plus a separate test of automatic fallback when the GPU device is hidden. At a time when no mainstream AI accelerator card ships a RISC-V host driver, supporting AMD cards first is the most realistic step—ROCm’s RISC-V-side work is already maintained in the openRuyi repo, and the same group of people is pushing both.

The timing gap is worth noting: the nightly nightly/2026-11-10-209274f published at 10:22 that day predates this merge, so that package does not yet include the GPU backend.

2.3 Release Chain and Artifacts: Three CI Fixes, Wheel Slimmed by 40%, Explicit Targets Switched to -O3

Date: 2026-11-11 to 11-12　Source: PR #113 shared git auth, PR #116 wheel slimming, PR #117 -O3 and +zvfbfmin

All three merges on 11-11 were in the release chain; none changed compiler functionality. #113 extracts the “one-off global git config” that CI and release.sh each copied separately into a shared scripts/_git-auth.sh: anonymous git traffic on the self-hosted riscv64 runner cannot obtain authentication, so when upstream FetchContent pulls googletest it returns 401 and hangs at the username prompt with no tty. #111 fixes the release script itself; #112 is documentation, removing the torch install command no longer needed by the CPU path after #110, and adding to the AMD section that “torch must be installed, and it must be a build that can use AMD GPUs.” All three were by the same author, concentrated between 17:59 and 21:11.

The two open changes on 11-12 both target the artifacts themselves. #116 points out that the LLVM and buddy tools packed into the wheel previously used --strip-unneeded, leaving debug sections intact: triton-shared-opt alone carried nine .debug sections and was 407 MB; switching to --strip-all reduced it to 118 MB, and the total payload of the seven tools dropped from about 970 MB to about 576 MB, roughly 60% of the original size. #117 changes the optimization level of the cross-compilation path: when an explicit RISC-V target triple is given, the build previously skipped the LLVM middle end and llc used the default optimization level, so MLIR loops left in scalar form remained scalar in the object file; the change runs opt -O3 and llc -O3 first for such builds, while the native path without a triple (llc -O0) and the IME path are untouched. The same commit also adds +zvfbfmin to the default llc features—otherwise scalable bf16 aborts directly in llc, and buddy-mlir’s #1054 assumes the extension is present by default, so the two must stay in sync. These two were still open in the 11-13 daily report, and #117 was merged into main at 15:19 on 11-14.

Date: 2026-11-13　Source: PR #56 riscv64 CI criteria, riscv branch commit list

III. RuyiSDK Toolchain and Distributions

3.1 ruyi 0.54.0: Turning “Can It Be Installed” into a Computable Fact

Date: 2026-11-10　Source: ruyi 0.54.0, PR #507 ELF ABI compatibility

The feature surface of 0.54.0 is exactly the full content of the 11-02 pre-release 0.54.0-beta.20261102; the official release adds only one version-number commit over the pre-release, totaling seventy-one commits and seventy-four files since 0.53.0. The core is ELF ABI compatibility: whether a precompiled binary can run on a target device depends on a set of facts scattered across the ELF file header—which dynamic libraries it needs, which symbol versions it requests from those libraries, and architecture-related capability requirements. Previously nothing in the software source recorded these; ruyi now scans this information out, stores it, and compares it before installation.

The RISC-V path is the most labor-intensive to collect, because its extensions are concatenated as version-numbered strings: this period’s commits include parsing versioned single-letter extensions, filtering ld.so.cache entries by host floating-point ABI, and factoring in stack alignment requirements. Host-side probing for x86-64 and AArch64 is also implemented; host libraries are resolved by the requested soname, and an unresolvable soname reports “undetermined” rather than a hard failure—this three-state design separates “cannot install” from “don’t know.” The data plane goes through the repository-side ABI sidecar, resolved by distfile name; rescan-package-abi and plugin artifacts gain strip-components to handle archives with a leading directory; the sidecar has a size limit, and a bad sidecar is discarded as “no ABI information.”

3.4 openRuyi Packaging: Dual Kernel Lines, glibc 2.44, and KDE Plasma 6.8.2

Kernel version bumps in openRuyi usually come with a config re-check—RISC-V platform peripheral, power management, and filesystem options are maintained inside %ifarch riscv64 conditional blocks, so the config refresh is more noteworthy than the version number itself; on 11-12 there were two more wrap-up commits changing only the patchset and config (2 lines each).

The host-side catch-up is equally evident: glibc was upgraded to 2.44 and ran the full test suite on x86_64, and rpm-config-openruyi gained x86_64 architecture macros and tune configuration. Wayland-related items advanced together in the same window: wayland 1.26.0, wayland-protocols 1.50, plasma-wayland-protocols 1.23.0, and wlroots 0.20.2. For a RISC-V distribution, a wholesale desktop stack upgrade is one of the scenarios most likely to expose architecture problems, and such batches usually don’t come out all green on the first try.

3.5 Security and Toolchain: Seven Python Commits, Eight OpenTelemetry Packages, llvm23 23.1.5

Date: 2026-11-09 to 11-12　Source: openRuyi commit list

Among the batch of commits on 11-09, seven are marked as security fixes: urllib3 upgraded to 2.8.0 (fixing three CVEs), tornado to 6.6 (three CVEs and two GHSAs), pymongo to 4.19.0 (four CVEs), dnspython to 2.9.1, websockets to 17.4, trio to 0.35.0, and aioquic to 1.7.2 (six GHSAs). What these share is the networking and async stack—HTTP clients, DNS, WebSocket, QUIC, async runtimes; they are not desktop components, yet they determine whether containers, CI, and cloud-native toolchains can run securely on riscv64.

Among the thirty-six commits on 11-11 alone, the largest cluster is OpenTelemetry: eight packages upgraded to 1.45.2 (exporter-otlp and its three sub-packages grpc/http/proto-common, proto, api, sdk), semantic-conventions upgraded to 0.66b2, plus two new packages, exporter-otlp-common and exporter-http-transport; this observability stack previously had only a few scattered packages, and this round fills it out to cover common OTLP combinations. The second cluster is four Python authentication packages, all marked with security fixes: pyjwt 2.15.1, oauthlib 4.0.1, joserfc 1.8.0, and authlib 1.9.3.

On the toolchain side, llvm23 was upgraded to 23.1.5, and the daily snapshot package clang-wrap is on its own track—the latter follows up to 20261111, the third consecutive day tracking the upstream snapshot, meaning the compiler downstream receives changes every week; these two packages are the foundation of the self-hosting compilation chain on RISC-V and also the source of the LLVM archives that triton-riscv depends on at build time. One more commit deserves separate mention: the Python bindings of the llvm22, llvm23, and llvm24 packages now use text substitution to point clang’s bindings at the versioned libclang—in a distribution where multiple LLVM versions coexist, if the bindings point at an unversioned name, installing a second version will overwrite the first.

3.6 Devices and Peripherals: Three OpenCL Packages, the fwupd Chain, qemu-rustsbi

Date: 2026-11-11 to 11-12　Source: gcab package addition, OVMF FMP capsule patch, fu740 recovery flow

On 11-11 three OpenCL packages were added: opencl-headers, opencl-icd-loader, and clinfo. IV. Vector Extensions and Operator Optimization

4.1 The three vector repos remain silent; all vector-side increments are in VIR

Date: 2026-11-09 to 11-13 (status)　Source: FBGEMM, VecIntrinBench, IntrinTrans

The three repos VecIntrinBench, IntrinTrans, and FBGEMM had zero commits all week, with head commits stalled at 02-13, 06-25, and 07-13 respectively—silence that has persisted for months. This does not mean there is no progress on the vector side: this week’s vector changes all occurred at the VIR layer of buddy-mlir, and fall into two categories—one determining “whether something can enter a vector loop” (coverage), the other determining “whether the vector loop is fully utilized” (performance). Investment is concentrated in the compiler rather than measurement tooling, and this division of labor has remained unchanged since September.

4.2 i1 masks read/written byte-wise (#1052)

Date: 2026-11-12　Source: PR #1052

When the memref element type is i1, scalable vectors were previously rejected outright (with the message a memref of i1 needs fixed vectors), because a memref occupies one byte per element while an i1 vector occupies one bit per lane—only fixed-length vectors have a per-lane lowering. Triton’s load/store masks happen to be exactly i1 memrefs: when going through the pure VIR pipeline with scalable vectors, 179 of the 325 Triton-RISCV test files were stuck on this error, making this the most broadly impactful of the week’s seven changes.

The fix is to read/write byte-wise: contiguous accesses use llvm.load/store of i8 vectors, while non-contiguous strip-mined regions use vp.strided.load/store with all lanes enabled; incidentally, i1 lanes are now sized as one byte—previously a region whose first dynamic vector was i1 was counted as 1 bit, which under VLEN 256 would yield a size like vector<[512]xi1>, i.e. sixteen register groups.

4.3 Per-lane expansion of libm-only math functions (#1053)

Date: 2026-11-12　Source: PR #1053

Math functions that LLVM refuses to lower on scalable vectors (erf, erfc, cbrt, powf, atan2, acosh, etc.) are now expanded per lane: for vector<[N]xT>, each of the N times vscale lanes is extracted one by one, the scalar function is called, and the result is inserted back. The trigger was that convert-math-to-libm handled scalable vectors the same as fixed-length vectors, computing only the first N and silently zeroing the rest—a scalable erf under VLEN 128 (vscale 2) had half its lanes wrong. The effect shows directly in the test surface: in the FlagGems suite of 4045 items on SG2044 (VLEN 128), the number passing rose from 3980 to 4006; the 26 fixed items are test_erf and test_gelu, with no new failures.

4.4 The two bf16 paths and exhaustive verification (#1054)

Date: 2026-11-12　Source: PR #1054

RVV places bf16 in vector registers only with Zvfbfmin; without that extension, LLVM refuses to lower even a single load. The change adds an rvv-mattr parameter to the lowering, defaulting to assuming Zvfbfmin is present (several of Buddy’s RVV targets have it: K3’s X100 and A100, and SG2044); when -zvfbfmin is explicitly given, it instead treats values as integer bits, reading/writing bf16 vectors as i16, using integer operations for extf and truncf (truncf rounding to nearest-even), and routing absf and negf through the sign bit.

The verification method is the heaviest part of the week: truncf covers all 2^32 f32 values, while extf, absf, negf, and extf-mulf-truncf cover all 2^16 bf16 values, compared bit-for-bit against the Zvfbfmin path on both the SG2044 and K3 cores, with identical results. This verification cost indicates that bf16 is being treated as a shipping path rather than an optimization to get to “when there’s time.”

4.5 fast-math flags and all reduction kinds (#1055, #1056)

Date: 2026-11-12　Source: PR #1055, PR #1056

#1055 fixes fast-math flags being dropped in the strip-mined lowering: an arith.mulf with contract plus arith.addf was rebuilt as plain fmul and fadd, which LLVM would not fuse. Now the flags are propagated along with the same-kind operators to the vector loop and epilogue, so f32 multiply-add can produce vfmacc, and bf16 under +zvfbfwma produces vfwmaccbf16; the author compared the fmaf expansion bit-for-bit over 4M lanes on K3’s X100 and A100, with consistent results. This is the only one of the seven changes that directly alters instruction selection.

#1056 expands vir.reduce from recognizing only floating-point add and maxnum to all kinds of vector.reduction: add, mul, minsi, minui, maxsi, maxui, and, or, xor, minnumf, maxnumf, minimumf, maximumf, with integer support included, and the verifier checks whether kind and element type match. Previously Triton’s integer sum, min/max, product, all/any (and the argmin, argmax, count_nonzero, bitonic sort, and radix sort that depend on them) all remained in loops. The change adds 570 lines across 9 files.

4.6 Wrapping up residual paths: rank-0 fill and integer matmul (#1057, #1058)

Date: 2026-11-12　Source: PR #1057, PR #1058

#1057 lowers linalg.fill on rank-0 memrefs (mostly reduction accumulators) to a single memref.store, reducing residual linalg.fill in the 1811 FlagGems kernels from 393 to 0. #1058 enables integer matmul to lower as well: when A and B are the same integer type and no wider than C, sign- or zero-extend first, then multiply-add (without fma); on RVV, int8 matmul yields vsext.vf2 plus vwmacc.vx, and unsigned yields vzext.vf2 plus vwmaccu.vx; the same change also fixes an assertion failure in dynamic-shape matmul—M and K were originally taken inside the vir.set_vl region and erased during use by a later pass. After the change, no linalg.matmul remains among the 1811 kernels.

Together, the two changes provide a verifiable coverage metric: not a benchmark score, but “how many linalg or scalar paths remain.”

V. Buddy Compiler Updates

5.1 The First Half of VLEN Exactness: #1032 and #1037

Date: 2026-11-08　Source: PR #1032, PR #1037

The problem #1032 addresses is a class of failure that fails the wrong way: no error, just wrong results. A RISC-V model built for an exact VLEN has vector code that is valid only for that one VLEN—llc is explicitly told the VLEN (+zvlNb and -riscv-v-vector-bits-max), and the scalable vectors in decode attention are sized accordingly. On a different VLEN, the model does not crash; it simply produces wrong results.

The fix moves validation forward to load time: runtime/rvv/BuddyRvvVlen.c is linked into the model library as a constructor; as soon as the library is loaded it reads vlenb, and if it does not match the exact VLEN used at build time, it prints a message and terminates the process with _exit(1). Using _exit rather than exit is deliberate—running destructors while the loader holds its lock would deadlock. A follow-up after review changed the check from “judging by build variables” to “judging by the final llc options”: previously a native build could specify the VLEN via the model’s own LLC_ATTRS, and if BUDDY_RISCV_VLEN disagreed with it, the validated value would not match the actual code; moreover, the check was only linked into the third stage, missing Qwen3-VL’s vision and decode shims and the layered-linking paths. Now the build script extracts the exact VLEN from the final llc options (the same place VIR lowering reads it), and contradictory options fail directly at configure time. Testing is the other half of this change: test_buddy_rvv_vlen.py builds the model library for each VLEN from 128 to 65536; only the host’s own can load, and all others exit with code 1. The documentation was updated in step, with the two DeepSeek-R1 deployment notes for A210 and K3 clarifying the boundary between “which builds are exact VLEN and which are generic RVV”—A210’s kernels use fixed-length vectors with no VIR and are generic builds; K3’s prefill_ime requires 1024 and is an exact-VLEN build.

#1037 fixes an error in the other direction: when -lower-vir-to-vector is given neither rvv-vlen nor scalable vectors, it sizes fixed-length vectors by the host register width, but its host detection only covers x86 (AVX2, AVX-512) and SVE; a RISC-V host with the V extension always falls back to the generic default (128 bits, 16 registers). The consequence showed up in tests: since #1030, the kernels pipeline lowers VIR by host when no llc options are given, and the riscv64 CI host is VLEN 256 but was treated as 128-bit, so the squared q and k norms were split into vector<32xf32> partial sums, in a different order from the bit-for-bit comparison against the vector kernel, and vir decode qk_norm ... same bits evaluated to false. The author first added a change that pinned rvv-vlen=1024 use-scalable=false in tests only, then reverted it—that would have created a second place to set the VLEN outside the llc options, conflicting with the direction of #1032. The final fix detects a RISC-V host in the lowering stage (reading host CPU features and hwprobe) and sizes by the real VLEN.

5.2 f32 YOLOv8 Runs End-to-End Through VIR (#1041)

Date: 2026-11-09 (merged 11-10 01:07)　Source: PR #1041, merge commit 18c66ec

#1041 takes the f32 YOLOv8 graph end-to-end through VIR: first Linalg-to-VIR lowering, then VIR-to-vector-dialect lowering. Previously this pass had no convolution pattern, and three other classes of operators in the graph failed outright—one change adds both the convolution and those three classes. The scale: fourteen files, 1,646 lines added, 115 removed, thirteen commits.

Both convolution families are covered: 2D NHWC with HWCF and 2D NHWC with FHWC. Vectorization runs along the output channel F; for each (kh, kw, c) the input element is broadcast into one vir.fma per output pixel, so every vector access is contiguous and there is no cross-lane reduction—reductions need horizontal instructions and a subsequent reduction tree, which is clearly costly at narrow VLEN; the price is that the FHWC filter must first be copied in parallel into an HWCF buffer, trading one extra copy for contiguous access in the inner loop.

The three previously failing operator classes are filled in as well: rank-0 inputs (memref<f32> fed directly into linalg.generic reports invalid reassociation at memref.expand_shape; changed to load once and broadcast), linalg.reduce preserving the last dimension (e.g. DFL softmax’s 1x16x4x2100, dimensions=[1], addf combined with maximumf), and named operators reading linalg.index (e.g. linalg.map iota in upsample). The on-device numbers are clear: on K3, f32 YOLOv8 pose’s raw output changes by at most 6e-5, and the gap to PyTorch remains within 6e-4 (bus) and 8e-4 (zidane), unchanged from before; the detect model’s detections are unchanged and speed does not drop; the f32 and IME dynamic library outputs are byte-for-byte identical to before.

5.3 YOLOv8 Enters rax: Detection and Pose on the K3 Matrix Engine (#1042)

Date: 2026-11-10　Source: PR #1042

#1042 wires Ultralytics YOLOv8 into buddy-cli’s rax format: yolov8n detection (eighty COCO classes) and yolov8n-pose (seventeen keypoints), both with 320x320 input. The f32 model goes through VIR lowering; if the spec says ime: true, it runs on the SpacemiT K3 matrix engine instead.

Two fixes added during review are more informative than the models themselves. The first is weight validation: the manifest carries params_size, and the runner requires the weight file to match it; previously a short weight file would let the model read past the buffer. The runner is also now required to accept only rax packages, because when the library and weights were supplied separately, the pose model would be run with the detection model’s parameters. The second is TCM copies: the TCM copy of IME weights was cached by weight address, so new weights read into a freed buffer would hit the stale copy; now the kernel-side invalidation function is called after every weight load. The spec keeps both params_size and ime_params_size, so an f32 version can still be built with ime: false—one graph, two backend paths, one comparable baseline.

Date: 2026-11-08 to 11-12　Source: PR #1038, PR #1035, triton-riscv PR #104

VII. Trend Watch

7.1 Release chain before features: this week’s work was “can we ship a package at all”

Among the merges into triton-riscv this week, only #110 (AMD backend) is a feature; the rest — #101, #102, #105, #107, #111, #112, #113 — are all on the release chain: registering the backend into the wheel, local builds of the AMD codegen library, wheel-first README, lit lookup order, git auth extraction, and the torch prerequisite for the AMD section. Add #116’s wheel slimming and #117’s -O3, and this repo’s output for the week can be summarized as “make the install path reproducible, downloadable, and verifiable.”

This is not an isolated phenomenon: the main content of ruyi 0.54.0 is also “check whether it can be installed before installing,” pytorch’s #56 plugs “zero passing test cases still counts as green,” and buddy-mlir’s nightly fills a six-day packaging gap. Four repos doing the same kind of work in the same week shows this stack has moved from “proving it runs” to “proving it ships.”

7.2 Coverage before performance: the 393→0, 2→0, 179→0 framing

Of buddy-mlir’s seven patches this week, only #1055 directly changes instruction selection; the other six bring forms previously left in loops into the vector path: i1 masks, libm-only math functions, bf16, reduction kinds, rank-0 fill, and integer matmul. The right yardstick for this kind of change is “how many linalg or scalar paths remain,” not benchmarks — 393 down to 0, 2 down to 0, 179 failing files to zero all use this yardstick.

Contrast this with the previous day’s #1050, which narrows strip-mined remainders. The division of labor across the two days is clear: first let vector loops fill their lanes (performance), then let every operator enter vector loops (coverage). Reversing the order wastes effort — a full-width loop that still only contains the same handful of operators.

7.3 VLEN 1024 becomes a shared pressure point for compiler and runtime

Three changes this week point directly at VLEN 1024: load-time validation (#1032), reduction lane loss (#1051), and strip-mined remainders (#1050). The common thread is the same hardware fact recurring at every layer — K3’s prefill_ime must be 1024, 16 f32 on an A100 core is one full vector, and shapes like vector<[1]xT> simply cannot be reached on VLEN 128/256.

The same signal appeared upstream in the same week: V8’s review list shows “Allow vlen=1024” (CL8585179). This shows long vectors are no longer just a local configuration for one board but are entering the general paths of runtimes and browsers. The risk follows — CI’s riscv64 runner is VLEN 256 while shipping hardware is 1024, so test coverage is inherently misaligned; defects like #1051, where “CI is all green and the board is all wrong,” are exactly the product of that misalignment.

7.4 The verification cost of silent wrong values has reached the scale of exhaustive inputs

#1054 ran all 2^32 f32 values through truncf and all 2^16 bf16 values through conversions and sign operations; #1055 compared the fmaf expansion bit by bit across 4M lanes; #1041’s acceptance criterion was “byte-for-byte identical to before the change”; #1051’s acceptance criterion was 25 reduction tests going from wrong to right. The four use different verification methods, but all answer the same question: is the result correct, not is it fast.

The reason is clear: nearly every defect fixed this week was “no error, just wrong results” — a model built for an exact VLEN silently misbehaves on different hardware, scalable erf zeroes out half its lanes, reductions keep only lane 0, and mask-based bit sizing produces sixteen register groups. Crashes are easy to spot; wrong values are not. When verification cost rises to the scale of exhaustive inputs, it means this stack now treats foundational operators like bf16 and reductions to shipping standards.

7.5 Rolling packaging decouples from monthly releases

The openRuyi packaging repo saw its highest commit density in recent memory this week (a single-day peak of thirty-six commits, with KDE, security, toolchain, and device-facing work all advancing in parallel), while the externally visible monthly release is still stuck at 2026.09. The two are not contradictory: rolling packaging and monthly releases are two separate tracks; daily updates show the engineering is moving, and the missing release shows the release process or verification cycle is stuck.

Worth noting are the two new governance repos this week: the release spec repo writes requirement numbering and priority into process, and ruyi-deck is positioned as “the operations console for repos and releases.” Neither produces code, yet both point at the same gap — a monthly release must ship across the packaging repo, images, and firmware, and what’s missing is not commits but the step that converges commits into a releasable version.

7.6 “Can it be installed” becomes a computable fact for the first time

ruyi 0.54.0 turns ELF ABI compatibility into a three-state determination (compatible, incompatible, undetermined) and exposes it in three places: list, install, and admin check-abi. The significance is not the feature itself but turning “can this package run on my machine” from a judgment call into queryable, comparable, debuggable data.

This matters especially for RISC-V: the same prebuilt binary behaves differently on hosts with different extension combinations and floating-point ABIs, and in the past the only option was trial and error. The three-state design also reserves an “undetermined” tier, avoiding treating the unknown as incompatible — that distinction determines whether the tool is usable in real environments. The next thing to watch is sidecar coverage: which packages have ABI information added and which still have “no information.” The packages-index mentioned in issue 080 adding ABI compatibility information for some packages is a continuation of this line.
