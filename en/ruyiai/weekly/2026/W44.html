Reporting period: October 26, 2026 (Monday) through October 30, 2026 (Friday), 5 working days in total.

llvm-project riscv branch: five rebases in five days, then stops; governance assets take over

Date: 2026-10-26 to 10-30　Source: riscv branch commit list, autorebase workflow, RISCV_CONTRIBUTING.md

This week’s rebase sequence was 474 commits on 10-25, 221 on 10-26, and 237 on 10-27. All three replays share the same characteristics: the head commit title remains “[RISCV] Add A100 HP/SP and pack/unpack lowering with calibrated scheduling (#31)”, the 26-commit lag exactly equals the number of local patches, and a commit-by-commit comparison shows titles and order unchanged; in the 10-27 run, 20 local commits were rewritten and force-pushed within the same minute (committer timestamps clustered between 15:00:29 and 15:00:31), while author timestamps ranged from July 1 to October 3. In other words, these three days’ work consisted of moving the existing patch set onto a new baseline; all functional increments came from upstream.

The pace changed starting 10-28. The branch advanced by only one commit, cf00909d, containing .github/workflows/autorebase.yml (+244/−0): installed on the author’s source repository default branch, triggered by workflow_dispatch, with two inputs — PR number and “dry-run only, no push” (enabled by default); running on ubuntu-24.04 with a 90-minute timeout; comments explicitly require never executing PR code, hooks, builds, or submodules while holding write permissions, and the git config points hooksPath, attributesFile, and fsmonitor all to /dev/null; conflict handling walks ls-files --unmerged for cases -Xours cannot cover, taking the local side when stage 2 exists and deleting otherwise, and can identify “equivalent patches” to discard duplicate old-baseline patches.

In the 10-29 23:00 full-branch replay, the genuinely new commit was [workflows] Push rebased PRs directly and document contribution options (author time 10-29 09:59): autorebase.yml lost 8 lines (removing the dry_run input and dry-run branch) and gained an 82-line RISCV_CONTRIBUTING.md. The guide offers two paths — open an issue first, have a maintainer cut a work/issue-NNN working branch from the current riscv, and submit PRs to the working branch; or submit a PR directly to riscv and manually trigger the rebase, with the workflow pushing back to the source branch using --force-with-lease with an explicit expected SHA. The document also notes that pushes using GITHUB_TOKEN typically do not trigger subsequent push/PR workflows, so whether CI ran on the updated SHA must be confirmed manually.

Assessment: this branch’s routine activity had already become purely “following the baseline” — five rebases in five days with zero local patch changes. This week’s new information is a change in governance: separating the cost of external contributors “always being one step behind” from maintainer manual judgment, turning it into a dispatch with explicit boundaries (no PR code execution, no rewriting of riscv itself, no auto-merge). Removing the dry-run lowers friction while shifting the risk of “pushing the wrong history” forward to contributors; the effect will only be verifiable after one or two external PRs.

llvm-project upstream: 17 RISC-V passes migrated to NewPM in one hour

Date: 2026-10-26　Source: InsertVSETVLI migration, PreAllocZilsdOpt migration, DeadRegisterDefinitions migration

Among the 221 upstream commits brought in by the 10-26 rebase, 21 are RISC-V related, of which 17 are NewPM ports, all authored by Aiden Grossman, clustered between 12:59 and 13:55 (Beijing time) — under one hour. The list covers the backend’s main passes: post-instruction-selection VSETVLI insertion, CSR read/write and VXRM writes, VMV0 elimination, compressed instruction generation, prologue/epilogue optimization, base address merging, LoadStore optimization, Zilsd pre-allocation, branch optimization and QCRelax marking, plus dead register definition elimination, redundant copy elimination, indirect jump tracking, landing pad setup, and constant hoisting.

The remaining four fall into three directions: the vxrm-pipeline-flush attribute restricts speculative VXRM writes to loops with flush guarantees; LSR prefers equality comparisons as loop exits on Zibi targets; GlobalISel adds legalization for G_FPTOSI_SAT and G_FPTOUI_SAT, making saturating float-to-int conversions available on the global instruction selection path. Another commit changes the gather/scatter lowering and VL optimizer’s use analysis to lazy requests.

The significance is not in any single change but in pipeline ownership: these passes long lived under LegacyPM, and migrating to NewPM aligns them with the new pass manager’s analysis cache, pass ordering, and debugging interfaces. The direct impact on downstream forks is that every rebase carries this set of changes, and -passes= names and pipeline composition shift accordingly — this is one of the few places where actual content changed this week even as the riscv branch “rebased without patch changes.”

openRuyi Packaging Direction: Samba Coordinated Upgrade and the LLVM IR Distribution Path Reverted

Date: 2026-10-27　Source: PR #1509 Revert llvm ir, PR #1428 Samba, PR #1511 dms-shell

In past issues, openRuyi’s keyword was “add”: add packages, add security, add Rust crates. This week saw the first clear subtraction — #1509, merged at 15:15, contains just three commits with a net deletion of 105 lines (+5/−105), reverting three experimental packaging changes: the llvmir feature for gsl, building pixman with clang and shipping IR with the package, and distributing LLVM IR with libjpeg-turbo.

The PR description gives no rationale; from the content, the direction was to compile libraries to LLVM IR and ship it with packages, leaving an interface for re-optimization or deferred code generation. For a RISC-V distribution this is a trade-off worth recording: IR distribution could in theory reuse upstream optimizations, but without a matching toolchain it merely shifts the cost onto users.

The addition on the other side was the “coordinated upgrade”: Samba and its three dependency libraries changed versions together, and every package depending on the tevent/tdb/talloc ABIs had to be rebuilt — the most typical bulk action in a distribution. In the same week there was both the addition of “rebuilding a whole swath of packages for consistency” and the subtraction of “cutting an experimental path for maintainability,” showing that maintenance focus is shifting from “covering more packages” to “holding the quality boundary of existing packages.”

RuyiAI Trio Packaging: #1350 Moves from Direction Debate to Spec Cleanup

Date: 2026-10-27 to 10-29　Source: PR #1350, PR #1350 review comments

#1350 is the week’s most important item at the distribution layer: a single PR adding three packages at once — buddy-mlir, python-triton-ruyiai, and python-tilelang-ruyiai. The timeline: PR opened 9-21 (three commits between 09:46 and 09:48), maintainer Z572 raised three change requests on 9-24, the author fixed two on 9-28, then it stalled for nearly a month; on 10-27 between 17:55 and 18:54 three replies addressed each point in turn; on 10-28 at 16:22 the three commits were rebased onto the latest main branch in the same minute; on 10-29 between 16:19 and 16:24 the first round of five code-level review comments arrived.

The focus of the debate is shifting. Before 10-27 it was “should buddy-mlir’s bundled LLVM be externalized” — the author’s rationale being that these packages always pin a specific LLVM commit and LLVM is used only inside the package, so keeping it bundled is what makes builds reproducible; also, triton’s upstream setup.py hard-checks whether git is executable, so one must either add a git build dependency or patch setup.py (the latter breaking on triton upgrades). On 10-28 the author quantified the cost of “switching to a GCC build”: on riscv64, 8814 seconds became 24798 seconds, 2.81×, and that build failed at the link stage without completing. That number turned the debate from a technical preference into build-farm scheduling arithmetic: 2.81× means machine occupancy, timeout policy, and release windows all have to be recalculated.

The 10-29 review turned to mechanical conventions: no blank lines needed between BuildOption(xxx) entries; python-triton-ruyiai is missing BuildRequires: python3dist(wheel); Provides must align with actual package names; the necessity of Conflicts: python-%{srcname} needs justification; patches must be generated with git format-patch, and there is an unreferenced patch in the same directory; an empty %check needs a comment explaining why. Such comments typically appear at the stage where “the direction is accepted and it’s time to wrap up.” As of week’s end the PR stands at 10 files, +838/−0, with 18 review comments, still open.

VIR: Seven Scalable Vector Commits in One Night, Python Bindings the Next Day

Date: 2026-10-26 to 10-27　Source: #1002 step by vscale, #1007 unify index convention, #1009 Python bindings

From 22:48 on 10-26 to 03:22 on 10-27, the same author landed seven commits in a row (#1002 through #1008), all prefixed [midend][VIR], all revolving around the same switch use-scalable, and divisible into three layers. Loop and size layer: #1002 fixed the strip-mining step — previously, when vir.set_vl had no result, it lowered to a main loop stepping by a constant vector-width, yet each iteration accessed memory at N times vscale lanes, so iterations overlapped when vscale was greater than 1; #1003 made size selection compute vscale = VLEN/64 on RVV, so that N and SEW determine LMUL instead of falling back to fixed-length vectors; #1008 fixed an assertion crash when the index vector had no explicit width. vir.set_vl with a result: #1004 allowed it to lower to scalable vectors, and #1005 further supported multi-dimensional dynamic vectors. Memory access and permutation: #1006 added vir.shuffle for row-wise permutation of dynamic vectors, and #1007 unified the index convention of vir.load and vir.store.

The motivation was not a generalized vectorization overhaul but pressure from a concrete operator: in decode attention, RoPE’s rotate_half must swap the two halves of a 128-element head and negate one (i.e. [-x[1], x[0]]), which is essentially a row-wise permutation, and VIR previously could not express row-wise permutation of dynamic vectors — the outer layer had to compute with fixed-length vectors and then carry the query into the region. So #1006 added permutation, #1005 added multi-dimensional dynamic vectors, and #1007 added the index entry point; together the three form a single path that “keeps the whole decode attention inside VIR.”

#1009, merged at 22:42 the next day (12 files, +614/−1), added Python bindings: previously VIR had neither an operator-construction entry point nor a type-construction entry point on the Python side — operator names and type descriptions had to be hand-assembled in strings, and the entire lowering could only run inside the single buddy-opt executable; the implementation uses ODS-defined operators plus a C API plus a nanobind extension, isomorphic to dialects in the repo that ship their own types such as quant, split into Ops, Types, and pass registration. The significance lies in composability — operator descriptions, shape inference, and test cases can all be written on the Python side, and frontend-to-VIR integration no longer depends on adding hooks on the C++ side.

K3 Decode Attention Ported to VIR: Bit-Exact Numerics, Identical Instruction Count, Overlapping Throughput Ranges

Date: 2026-10-28　Source: PR #1014, K3 doc changes, test file

#1014 was merged at 09:36 (4 files, +476/−14, of which 264 lines are kernel, 152 lines tests, 10 lines lowering pipeline, 50 lines docs), moving the entire decode attention of the K3 w4g32 kernel onto the VIR dialect. This is the first reconciliation against a real model’s kernel — the previously hand-written RVV vector kernel on one side, the VIR kernel assembled in Python on the other, comparing numerics, instruction counts, and on-board throughput.

The implementation has four layers: the construction layer no longer hand-assembles operators and types but goes through buddy_mlir.dialects.vir’s SetVLOp, load, shuffle, fma, reduce, where one work item is a vir.set_vl region of length half the head dimension (64 lanes) returning that head’s (max, sum); the rotation layer loads, rotates, and scales q inside the region, with rotate_half becoming a single vir.shuffle and cos/sin stored as two rows of equal-length data, no longer needing vir.from_vector; the memory-view layer uses memref.expand_shape to split q, the KV cache, the output, and q’s normalization weights into 2×64 along the last dimension; the normalization layer opens a separate one-dimensional vir.set_vl region for Qwen3’s q/k norm. VII. Trend Observations

VIR has completed “expression—invocation—reconciliation,” but the conclusion can only be “no introduced loss”

Over the past three weeks this mainline has been continuously filling in expressiveness: on 10-26, seven commits in one night brought in scalable vectors; on 10-27, Python bindings were added; on 10-28, the entire decode attention of K3 was ported over and reconciled against on-board throughput. The meaning of this week lies in the three numbers taken together—bit-level numerical consistency, identical vector instruction counts (178 each), and overlapping throughput ranges. Homegrown dialects most easily get stuck at the “runs but slow” stage; this week at least proves that this stage has been passed for now.

But reading this as “VIR has caught up with hand-written kernels” goes too far. The accurate statement is “no introduced loss in this segment of K3 decode attention, at a fixed vector length.” Two gaps are clear: coverage is limited to decode attention—the A210 kernel, MoE, quantization, and prefill paths are all untouched; and scalable vectors are explicitly disabled (use-scalable=false). Once the next commit enables them, vector size will no longer be determined at compile time, the LMUL 4 grouping assumption will loosen, and whether numerics and instruction counts can hold will need to be reconciled again. The author himself noted in the PR a 2% difference between two builds of the same code—a magnitude that precisely illustrates the boundary of the “on par” conclusion.

Branch governance diverges: llvm writes rules and drops dry-runs; pytorch relies on replay and a sync bot

Within the same month, two branches gave two different answers. The llvm riscv branch has a large patch set (26 commits) and many external contributions, with conflicts and history drift as the main cost, so it is worth writing documentation (RISCV_CONTRIBUTING.md) and configuring workflows (autorebase.yml), and removing the “dry-run” step—push on success, minimizing friction and shifting risk forward to contributors, with --force-with-lease and SHA re-checks as the safety net. The pytorch riscv branch has a small patch set (11 commits); the cost of the maintainer replaying it once is lower than the cost of maintaining a process, so it continues daily or every-other-day whole-branch replays, plus a sync bot that raises the baseline to the latest upstream.

What both share is “a long-term stable local patch set”: llvm’s 26 commits and pytorch’s 11 commits saw no new features this week. The right way to track these two branches is not to look at SHAs or commit counts—replays rewrite committer timestamps uniformly and commit counts inflate with upstream—but to look at the set of patch titles and at what upstream has brought in (this week, 17 passes migrated to NewPM and isel completion for the P extension).

To judge whether a branch governance approach is working, look at two verifiable signals: on the llvm side, whether external PRs actually increase after the workflow goes live (if no one submits against the new baseline within two weeks, the bottleneck is not the rebase tooling); on the pytorch side, whether replays stabilize back to daily (this week was a single catch-up after seven days of silence—scheduled rather than routine).

Packaging becomes the real bottleneck of the RuyiAI stack, and the debate starts to have a price

#1350 has been debated for nearly a month, with the core disagreement being whether the LLVM bundled with buddy-mlir should be externalized. Last week’s position was still “GCC can be used, but takes at least 1.5x the time”; this week the author provides measurements: on riscv64, 8814 seconds becomes 24798 seconds, 2.81x, and the GCC run failed at the link stage. The nature of the debate thus shifts from technical preference to build-farm scheduling arithmetic—2.81x means machine occupancy, timeout policies, and release windows all need recalculation.

The lesson for the whole stack is methodological rather than conclusive: many disagreements in RISC-V distribution packaging (whether to vendor, whether to externalize the toolchain, whether to ship IR with the package) ultimately come down to three measurable numbers—build time, image size, and reproducibility. In the same week, openRuyi withdrew the “ship LLVM IR with the package” approach (#1509), while #1350 used 2.81x to defend “keep LLVM in the package”—two opposite directions of judgment based on the same kind of cost accounting.

Looking further, this week’s review comments on #1350 have shifted from design approach to spec writing (missing BuildRequires, Provides alignment, patch format, empty %check comments), indicating that the question of “whether it can be swallowed by the distribution” has become “whether the package itself is conventional enough.” Three unconventional points—buddy-mlir bundling LLVM, triton depending on the git executable, and tilelang needing to discover the buddy-mlir toolchain—each require patches and explanations, and each explanation costs maintainers time to judge. If the three-piece suite is to enter the monthly release cadence, converging them into one or two clear packaging conventions (e.g., the toolchain uniformly provided by buddy-mlir, patches uniformly stacked via git format-patch) would be less work than responding to review comments one by one.

What really needs to be added next is not more lowering but a benchmark that runs nightly and reports instruction counts and LMUL—otherwise “performance on par” and “performance improvement” cannot be distinguished under 2% noise.
