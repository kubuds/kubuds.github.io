Today’s Highlights

The center of gravity shifted this window. In the previous issue, the main repo merged five commits in a single day, all landing on Ascend; in this issue, the main repo saw only one documentation commit over 72 hours (an LSP repo link), while TileOPs merged fifteen commits in three days and TileFoundry three, plus nine in the Ascend adaptation repo—nearly all code volume moved to operator libraries and schedulers. TileOPs merged eleven commits in a single day on 11-15, among them expanding the decode-side W4A16 tile from a single consumer warpgroup to two, speeding up seven decode rows by 10–20% and stretching its lead over marlin to more than 1.20x. This is not scattered patching but a coordinated three-layer change across “operator + selector + cost model”: first the selector is made to pick the dual-warpgroup tile on more shapes, then the tile gains metadata loading sliced along K, and finally a nightly 32-row regression confirms no row got slower.

The same day produced the most notable causal chain of this issue. #2896 on 11-13 replaced the 128-row W4A16 tile with a hand-written warp-specialized main loop, cutting chunked-prefill on H200 from 37.3 microseconds to 31.6 microseconds; about 46 hours later, #2901 was fixing it—the out_shared staging of sliced_pair was written inside the conditional branch i // wg_rows == bz, and TileLang sometimes places the barrier guarding this write, which covers all 256 consumer threads, inside that same branch; the other warpgroup can never reach that barrier, the two warpgroups stall on different instances of the same barrier, and the kernel hangs. Worse, the barrier placement is not stable between two compilations of the same cache key, and CI’s persistent kernel cache keeps replaying the bad build, so gpu-smoke on main simply hung. The fix itself is plain—have both warpgroups do the staging, each storing only its own half—but it shows one thing: the correctness of automatic warp specialization no longer depends only on pass order but also on which branch the barrier is inserted into, and that location is opaque to the compilation process.

The second item is on the issue side, and its scale is more striking than the code side. In 72 hours the tile-ai org opened 406 new issues, of which a single account, cn-sys, opened 172 in 1 hour 46 minutes on the evening of 11-15 (numbered #4208–#4381 consecutively, with not one interleaved from another source), and ilovexsir opened 142 in three batches over three days; together the two account for 314, or 77% of the total. cn-sys’s batch ranges from concrete numbers in examples and READMEs (flash-attention claims forward error below 0.5%, while all five checkers in the same directory use 5%; deepgemm’s benchmark uses 8192 as cache_size, but that parameter is in MB, equivalent to allocating 8 GiB to flush a 128 MiB L2) all the way into the compiler proper: auto-schedule’s IR structure visitor misses fields, and PTO codegen’s pointer element type falls back to a hardcoded bfloat16. ilovexsir’s batch is more systematic: the 142 issues correspond to five batch PRs (#4201–#4205, opened in the same minute), each fixing a group of entry points that “should have errored but didn’t”—for example, T.copy(transpose='False') silently enables transpose because the string ‘False’ is truthy, and _make_ascend_target() uses dict(target_dict or {}), dropping all falsy config keys. A pipeline is forming between audit and fix, at the cost of a review queue backlogged to 102.

The third item is that operator migration on the Ascend side has entered the stage of “landing in batches by algorithm family.” On 11-13 alone, tilelang-ascend merged nine commits: the forward pipelined version, backward, and topk reduction trio for DSA sparse attention; the chunk_delta trio for KDA; plus the bitwise four-in-one, the alloc API docs, and a catlass submodule upgrade. These are no longer single-point fixes but organized by model: DeepSeek V3.2’s sparse MLA fuses DQK into a single 512+64=576 GEMM, the Kimi-family KDA absorbs the gated decay into a host-precomputed M matrix, and the backward operator cuts 79395 microseconds to 27388 microseconds. Meanwhile catlass went from v1.0.0-6 to v2.2.0, incidentally fixing a previously fully silent defect: the old CopyL1ToL0A/L0B had no float specialization, so fp32 GEMM output NaN or negative infinity without erroring.

The RISC-V side breaks its silence for the first time in this issue. kubuds’s TVM line opened a new kubuds-riscv-hikari branch alongside mahiru and karen; its five commits include a K3 port and validation report, unlocking the rv64gc build (the USE_LLVM=ON linking problem and an eight-thread build), grid partitioning for decode 4 tiles and prefill 8 tiles, and provenance records for the public XSMTVDotII/vmadot spec; at the same time, the community index page received its first PR, adding the kubuds fork’s project description to the README. The MLIR line (RuyiAI-Stack/tilelang-riscv) and references to the Sophgo TPU repo remain untouched, and the two lines still need to be viewed separately.

1.2 TileOPs: four performance merges on 11-13, one line each for MoE, GQA, softmax, W4A16 (11-13)

On the first day of the window, TileOPs merged four in a row, covering four different workload types. The soft reduction put the 16-bit softmax row on a cluster of two 256-thread CTAs instead of four 128-thread CTAs, completing the “shift by scaled maximum” for the fp16 term with a single FFMA (#2898). The split upper bound for paged GQA is now jointly constrained by the number of key tiles in the window and the combine’s read volume (#2892), incidentally closing the long-pending calibration request #2496.

1.3 TileOPs: eleven merges in a single day on 11-15, W4A16 decode tiles another 10–20% faster (11-15)

Eleven merges in one day on 11-15, of which #2955 was the day’s closer: the W4A16 selector moved the “at most 32 rows” deferred-scaling pick from one 128-thread consumer warpgroup to two, distributing by weight row count and splitting by K slice to preserve CTA count, while stream-K still keeps a single warpgroup. The rationale is that decode tiles are instruction-issue bound while the cost model favors a single warpgroup—measured on that path, issue slot occupancy was 49.5% and DRAM only 54%. As a result, seven decode rows are 10–20% faster than main, leading marlin by at least 1.20x, with prefill-mlp-up unchanged and still 0.7% behind torch. The same day, #2952 merged the target-side kernel’s two tables into one, copying before reading to avoid “dictionary changed size during iteration” under concurrency, and #2904 fixed a call with “no device, no named target, no process default” throwing _Unresolved object is not callable.

1.4 TileOPs: ping-pong hat-trick, MoE shared expert beats FlashInfer-CUTLASS in every repetition (11-15)

Three progressive merges on the same theme. #2919 first had the grouped GEMM selector’s own 64x256 single-warpgroup compact tile run dual-warpgroup ping-pong, so each tile’s epilogue falls under the other group’s mainloop, taking the down-projection GEMM of ds-v3-grouped-t2048 from 1818 µs to 1707. #2953 extended the same technique to the selector’s own 64-row compact tiles, covering fused gate/up and short grouped tiles, and explicitly noted “short grouped tiles still keep one warpgroup because their epilogue is too short to hide anything”; the result is that FusedMoESharedExpert’s ds-v3-grouped-t2048 beats FlashInfer-CUTLASS in every repetition (median 5674 vs 5744 µs), with no program in the 32-row six-operator set getting slower. #2915 then staged the unfused ping-pong grouped GEMM output in 64-column TMA boxes, gaining a fifth ring level (an extra 40 KiB tier for 64x256 tiles).

Source: https://github.com/tile-ai/TileOPs/pull/2919, https://github.com/tile-ai/TileOPs/pull/2953, https://github.com/tile-ai/TileOPs/pull/2915

1.5 TileOPs: #2901 fixes the hang introduced by #2896, barrier landed inside a warpgroup branch (11-15)

This is the most worthwhile read of the issue. After #2896 merged, gpu-smoke on main hung: sliced_pair stages out_shared under the condition i // wg_rows == bz, and after layout lowering only the consumer warpgroup that “keeps that half tile” executes the staging loop; TileLang sometimes inserts the barrier guarding this write—covering all 256 consumer threads—inside this branch, which the other warpgroup never reaches, so the two groups stop on different instances of the same barrier and the kernel waits forever. The explicit barrier added earlier in #2899 was not enough to prevent it—the compiler can still insert barriers inside the branch on its own. The fix moves staging out of the condition: both consumer warpgroups write their own half. What’s truly striking is the second half: the barrier placement varies between two compilations of the same cache key, and the persisted CI kernel cache replays the bad build indefinitely, so one unstable instrumentation became a stable failure.

Source: https://github.com/tile-ai/TileOPs/pull/2901, https://github.com/tile-ai/TileOPs/pull/2899, https://github.com/tile-ai/TileOPs/pull/2896

1.6 TileOPs: #2918 lets compiled graphs be reused across processes, one pyupgrade touches 1926 sites (11-15)

#2918 changes the compilation-boundary key from “one uuid per process” to “operator class + parameter digest + construction-time tensor layout + the instance’s index within the class,” so later-started processes can directly reuse Inductor’s FX graph cache and AOT autograd cache; the cost is that parameters must be re-traced once assigned new values, and in-place modification is rejected outright during tracing. The same PR brings pyright --verifytypes to 100% for the tileops.backend, authoring, and manifest packages (previously 100%/50%/21%) and applies ruff’s UP rules repo-wide—1926 sites across 307 files. Such commits produce no performance numbers, but they determine nightly and CI wait times, and whether newcomers can read the code via type hints.

Source: https://github.com/tile-ai/TileOPs/pull/2918

1.7 TileOPs: manifest adds four spec-only operators, from Embedding to RoPE cos/sin (11-15)

#2920 adds “spec only, no implementation” manifest entries for the four operators missing from the five pilot models: EmbeddingFwdOp (including integer tables, for DeepSeek-V4-Flash’s hash routing), MaskedScatterFwdOp, RMSNormGatedFwdOp (with a sigmoid-gated activation parameter), and RoPECosSinFwdOp (angles per token, allowing x to be a strided view to support tail-column rotation). It also adds the tileops.indexing family, adds a torch reference implementation for each to tests/test_spec_reference.py, and prices embedding, masked scatter, and RoPE by rows read (two roofline functions plus one inline bytes, each with a hand-written oracle). The significance of this approach: nail down the interface and pricing first; the implementation can be filled in by later contributors.

Source: https://github.com/tile-ai/TileOPs/pull/2920

1.8 TileOPs: #2951 splits adaptive pooling by lane, three pooling ops on main fail to compile on narrow-long shapes (11-15)

AdaptiveAvgPool2dLanesKernel splits each bin across a power-of-two number of lanes (at most one warp), with each lane reading its own tap via an unconditional vector load with clamp, then folding with shfl_xor. The driving root cause: the original implementation ran one thread per output over the full bin, giving the unbatched ResNet head only 8 CTAs and DRAM occupancy below 3%. It also fixes a harder problem—adaptive_bin did not widen to int64 when the product overflowed int32, so all three adaptive pooling operators failed to build on main for the shape (1, 1, 150001, 16) -> (100000, 1).

Source: https://github.com/tile-ai/TileOPs/pull/2951

1.9 TileFoundry: #325 unifies all callee naming with a single FunctionRef (11-13)

The IR previously had five ways of naming callees—bound Function/PrimFunction objects, slot-bound instance calls, reserved calls, launch targets, variant tags—and each consumer resolved them its own way, with the evaluator even picking definitions from “the loaded reading” rather than module scope. #325 collapses them into a static leaf FunctionRef(path, name): the path is relative to the caller, a None segment denotes a runtime index passed as a leading operand, and core.resolve(scope, ref) becomes the sole resolver; the resolver also defines “a name declared later in @module” as an error (DeclarationOrderError). Associated cleanup includes computing StoragePlan.scratch before emission, removing relaunch, and having the host entry declare and hand off scratch.

Source: https://github.com/tile-ai/TileFoundry/pull/325

1.10 TileFoundry: dimension arithmetic folded into the scalar renderer, Mesh selection slices no longer dropped (11-13)

#324 folds DimAdd, DimSub, DimMul, DimFloorDiv, DimMod, DimMin, DimMax into render_dim_call in codegen/scalar_expr.py; previously three CUDA emitters each maintained their own + - * / % table, so writing “loop bounds from mesh coordinates” (range(cta.i * 32, cta.i * 32 + 32)) on CUDA directly reported “no codegen handler for DimMul.” #323 fixes another class of silent error: relabeling selections like Mesh(threads[0:16], layout=(16,)) lost the slice at offset 0, so lowering did not emit the contains guard and every thread in that layer ran the entire region; now relabeling selections are slices at any starting point, while whole-layer selections remain unsliced meshes.

Source: https://github.com/tile-ai/TileFoundry/pull/324, https://github.com/tile-ai/TileFoundry/pull/323

II. Multi-Backend Adaptation (Ascend / Hygon / MetaX / Moore Threads)

2.1 Ascend: DSA Sparse Attention Trio Merged the Same Day — Forward, Backward, and topk Reduction All in Place (11-13)

tilelang-ascend merged three DSA (DeepSeek Sparse Attention) operators in two slots on the first day of the window, at 03:25 and 09:49. The forward pipelined version #1870 targets V3.2’s sparse MLA prefill: each query block selects KV rows by top-K, fuses DQK into a single 512+64=576 K dimension for one GEMM (no longer three-stage wgmma), uses a persistent grid of 20 cores, and combineCV automatically switches between Cube/Vector. The backward #1928 uses a two-pass structure, with dKV written out via fp32 GM atomic scatter (under the benchmark shape, each row is contributed by roughly 448 tokens on average), dropping the cumulative time from 79,395 to 27,388 microseconds, a 65.5% reduction. #1884 adds the topk probability-mass reduction, with Expert mode, T.Scope("C") dual-streamed with two AIVs’ T.Scope("V"), and manual cross-core flags.

Sources: https://github.com/tile-ai/tilelang-ascend/pull/1870, https://github.com/tile-ai/tilelang-ascend/pull/1928, https://github.com/tile-ai/tilelang-ascend/pull/1884

2.2 Ascend: KDA Chunk Trio Merged the Same Day — State Recurrence Kept Entirely in UB (11-13)

Three KDA (Kimi Delta Attention) commits were merged the same day at 03:26 and 08:19. #1895 is the dhu path of chunk_delta_bwd: each (b, h) block’s fp32 state [DK, block_DV] stays in UB throughout the backward chunk recurrence without returning to GM, GEMMs use T.mma, and each GEMM gets its own named L0 scratch to cut false dependencies at the name granularity. #1896 is chunk_delta_h_fwd: it refactors the h_new = M@h + K^T@U M-form into a host-side precomputed M = diag(exp2(gk_last)) - K^T@W, fully absorbing the gating so the kernel has zero transcendental functions. #1799 is Chunk Delta H itself, which explicitly abandons fp32 GEMM in favor of bf16 — the rationale being that gate decay keeps the recurrence eigenvalues below 1, so a 1-ULP bf16 error does not amplify over 512 recurrence steps.

Sources: https://github.com/tile-ai/tilelang-ascend/pull/1895, https://github.com/tile-ai/tilelang-ascend/pull/1896, https://github.com/tile-ai/tilelang-ascend/pull/1799

2.3 Ascend: catlass Upgraded to v2.2.0, Silent NaN in Old fp32 GEMM Fixed (11-13)

#1989 upgrades 3rdparty/catlass from v1.0.0-6 (67fd282) to the official tag v2.2.0 (6c0a3242), and makes six TLA API adaptations to src/tl_templates/ascend/common.h (39+/48-), with all helper external signatures unchanged and zero changes to codegen or the Python layer. The primary motivation for the upgrade is a bug fix: the old CopyL1ToL0A/L0B had no float specialization, so fp32 inputs to T.gemm_v0 would output NaN or negative infinity without raising any error; after the upgrade the same kernel is bit-identical. Other benefits include absorbing 17 months of community fixes (zN fractal padding holes, cross-core flag deadlocks, interval DataCopy for small-M GM→L1), and opening four follow-up channels: HF32, GEMM+Bias fusion, quantized side-output, and FP8. The author reports full regression across four independent environments with zero regressions introduced by the upgrade.

Source: https://github.com/tile-ai/tilelang-ascend/pull/1989

2.4 Ascend: bitwise Four-in-One — uint8 PTO wrapper’s Tail-Byte Overrun Corrupts the Sentinel (11-13)

#2000 combines four PRs — bitwise_and/or/not/lshift — into one (due to conflicts sharing common.h and elementwise.py). The core issue is the PTO uint8 tand/tor wrappers: the initial fix used ceil(ColValid / 2) to handle “odd columns’ tail byte not being processed,” but review pointed out that on a 256-byte buffer, buf[0:255] would process an out-of-bounds uint16 pair, clobbering c[255] into a[255] | b[255] — a controlled test showed the sentinel 0xA5 becoming 0x03; the final approach uses floor(ColValid/2) safe pairs plus scalar handling of the trailing valid byte, with PtoSetWaitFlag providing bidirectional cross-pipe synchronization before and after. The same commit also adds a frontend binary_op size assertion on src1: previously dst=64, src0=64, src1=32 would compile and run, with src1 read as 64 elements — an out-of-bounds read of 32.

Source: https://github.com/tile-ai/tilelang-ascend/pull/2000

2.5 mlir-ascend: 22 TLIR Dialect PRs Under Review — Unary Ops and Cross-Pipe Sync Added Together (11-13 ~ 11-15)

tilelang-mlir-ascend’s main had zero commits in the window, but 22 PRs were opened, all advanced by five contributors following the same “six-touchpoint” template: TLOps.td defines the operator, TLOps.cpp writes the verifier, codegen_tlir.cc/.h does TIR→TLIR, ConvertTLToHIVM.cpp does TLIR→HIVM, two FileCheck tests, and CMakeLists.txt registration. The operators added span four categories: unary scalar functions (tl.not, abs, sqrt, rsqrt, rec, exp, ln, cos), tensor operations (tl.flip, tl.pad, tl.gather, tl.transpose, vbitcast), reductions (reduce_sum/max/min/reduce), and synchronization primitives (tl.set_flag + tl.wait_flag are both needed to form a complete producer/consumer pair). tl.flip is the first TL operator with attributes, so usePropertiesForAttributes = 0 was set at the dialect level to bypass TableGen’s Properties storage. On the memory side there are also TL_L0A/L0B/L0C/L1 address spaces and explicit mapping of local/local.var.

Sources: https://github.com/tile-ai/tilelang-mlir-ascend/pull/236, https://github.com/tile-ai/tilelang-mlir-ascend/pull/247, https://github.com/tile-ai/tilelang-mlir-ascend/pull/248, https://github.com/tile-ai/tilelang-mlir-ascend/pull/259

V. Trend Observations

First, the main repo is quiet while the operator libraries are active—the shift in focus has now persisted for two consecutive windows. In the previous issue, the main repo had five Ascend commits in a single day and TileOPs had zero commits for consecutive days; this issue reverses that: the main repo had one documentation commit in 72 hours, while TileOPs had fifteen commits over three days and TileFoundry had three. Taken together, TileLang’s development focus is moving from “the compiler proper” to “operator libraries + schedulers”: changes to the compiler proper are concentrated on fixing regressions (the cleanup phase of the PTO line), while new capabilities increasingly appear in the form of operator-library tiles, selectors, and cost models. The evidence is not just the number of merges but also the direction of dependencies—TileOPs’ performance conclusions cite TileFoundry’s roofline and scheduling, yet the TileLang main repo gave them nothing new this window.

Second, the correctness of automatic warp specialization has become a first-class risk. The chain from #2896 to #2901 shows that when a performance change delegates synchronization responsibility to compiler-inserted instrumentation, the placement of that instrumentation becomes part of correctness—and it is opaque to upper layers: compiling twice with the same cache key can place a barrier inside a branch or outside it. Combined with CI’s persistent kernel cache, an occasional bad instrumentation gets frozen into a stable failure. There is currently no structural fix, only local workarounds such as “move writes out of conditional branches”; if more tiles adopt ping-pong in the future, similar hangs will likely recur.

Third, auditing has shifted from “finding problems” to “mass-producing problems on a pipeline”. In three days, 406 issues were filed, 314 of them by two accounts: cn-sys’s 172 were written within 1 hour and 46 minutes, and ilovexsir’s 142 map directly to five batch-fix PRs. This pattern does compress the cycle from “defect discovery to fix” (issues and PRs coexist on the same day), but it shifts the pressure to the review side: 102 PRs under review, 30 merged, of which 22 isomorphic mlir-ascend PRs can only be reviewed by a very small number of people. The bottleneck in the next phase will be review bandwidth, not discovery speed.

Fourth, Ascend operator migration is entering “batch landing by model family”. The three DSA pieces correspond to DeepSeek V3.2, and the three KDA pieces correspond to the Kimi family of linear attention; nine commits in a single day all point to complete pipelines for specific models rather than scattered operators. This is good news for downstream—the cost of model migration shifts from “assembling operators one by one” to “porting by family in batches”—but it also means the quality weight of the underlying template library rises. The old catlass defect, where an fp32 GEMM output NaN without reporting any error at all, is a case in point: it hides in a third-party submodule and cannot be caught by operator-level tests.

Fifth, the four RISC-V sources show substantive progress for the first time, but only one of them is moving. kubuds’ TVM route opened a new hikari branch and provided K3 porting validation and RVV grid data; the community index page included this fork for the first time. The MLIR route (RuyiAI) and the Sophgo TPU repo references are unchanged. The division of labor between the two routes is now clear: the TVM route is doing “getting it running, with measured data,” while the MLIR route remains at “design exists, no commits.” The judgment is unchanged—this line is still a small-scale effort, worth tracking window by window, but not suitable for measuring progress week by week.

Limitations: The conclusions in this issue come from the GitHub search API and repository atomic streams, without code-level verification; the performance figures in PRs are taken from the benchmark tables the authors provided in their PR descriptions (H200, CUDA 13.2, PyTorch 2.13) and were not re-tested locally. Issue statistics rely on the search API’s total_count and five pages of paginated results (406 matches the item-by-item tally), and title classification is only a rough keyword-based split. The default branch of tilelang-ascend is ascendc_pto rather than main; the first query fetching commits from main returned 404, and it was re-queried after correction. Neither mlir-ascend’s harness nor hygon’s tilelang-tileops-fix branch had any commits during the window. There were zero news hits, so no external reports are available for cross-validation.
