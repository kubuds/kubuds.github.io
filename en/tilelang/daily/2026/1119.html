Today’s Highlights: TileFoundry Lands Metal Target and Automatic Differentiation on the Same Day

In a single day on 11-18, TileFoundry merged two platform-level changes. #354 adds an Apple Metal target, and #355 adds automatic differentiation. The former extends the compilation pipeline to Apple GPUs; the latter lets the framework generate backpropagation itself. Neither produces runnable kernels: Metal only goes as far as TIR, and automatic differentiation only generates HIR modules.

On the Metal side, metal.Target("apple.m2_pro.gpu") is added. The topology is threadgroup to thread. Hardware parameters are written in TOML with public sources cited. The capability table directly adopts 27 native MSL function names.

Under T.metal there are nine instruction operators in total. The matrix group is ldmatrix, stmatrix, matmul, and mma. The reduction and shuffle group is reduce, prefix, shuffle, shuffle_fill, and ballot. A single call covers G SIMD groups; quad groups are expressed with the same set of operators on a mesh of width 4.

One file per operator. typeinfer, access, and evaluator rules are written in the same file, with layouts using named constants. MSL does not specify the lane mapping for matrices; the author measured on an M2 Pro and wrote the specification accordingly. HIR is matched via hir_matches. MatMul on fragment operands lowers to matmul, and Reshard between memory and fragment lowers to ldmatrix and stmatrix. This change supersedes the earlier #294, which could not be rebased due to target interface restructuring.

On the automatic differentiation side, differentiate(module, wrt, recompute) is added. It returns two modules: <Name>Forward and <Name>Backward. The forward pass returns the result and a saved tuple. The backward pass receives the result gradient and saved, and returns gradients one by one according to wrt.

Backward rules are written per operator in their respective files and registered via the newly added interfaces/autodiff. Coverage includes all operator classes of the built-in Qwen model, plus ReLU and Log. It supports sibling and child-slot calls, tuple parameters, MeshRegion, and loops with statically countable iteration counts.

Loops only stack values that change per iteration. Values used only by induction variables, captures, and constants are recomputed in the backward pass, so layer loops do not copy weights. Gradient layouts follow DTensor.

Source: https://github.com/tile-ai/TileFoundry/pull/354.

Today’s Focus: TileOPs lands 23 merges in one day, FP8 quantization chain completed, two performance debts closed same day

On 11-18, the TileOPs main branch took 23 merges, running from 10:17 to 21:50 Beijing time. The main thread was FP8: per-token grouped quantization, short-row GEMM streaming, paged decode rewrite, and WGMMA primitivization — four commits entering main on the same day.

FP8QuantPerTokenGroupFwdOp introduces UE8M0 scales (#3026). Output is bit-for-bit identical to DeepSeek-V4-Flash’s act_quant(x, 128, "ue8m0"), with scales stored as float8_e8m0fnu. A new inplace pseudo-quantization means the strided kv[..., :448] in the model no longer needs to be copied first.

The UE8M0 path uses bfloat16x2 for reduction and scaling, and drops the clamp before the saturating e4m3 conversion. The reference implementation is vLLM’s per_token_group_fp8_quant; the numerics for DeepSeek and TileKernels are given in comments.

The FP8 paged GQA decode kernel was rewritten wholesale (#2997). Each CTA takes one request’s packed rows, one KV head, and a segment of keys. Each FP8 key/value tile is dequantized only once, and a TMA warp handles page copies. The ceiling comes from shared memory: on H200, an 8-row tile can serve 44,287 requests, and a 64-row tile 33,023.

Short-row FP8 now goes through 64-row block streaming (#3010). One producer warpgroup moves b through a deep TMA ring, and one consumer warpgroup accumulates the FP8 WGMMA partial sums for each 128-wide K step into float32.

The main branch previously padded 8 or 16 rows up to 64- or 128-row tiles. That left 160 tiles landing on 132 CTAs, or falling back to split-K. Measured throughput was only 31% to 52% of DRAM peak.

Two cleanups landed in the same batch. #3030 switches the four k32 WGMMA per step in the FP8 stream to TileLang primitives. dense_wgmma_helper.h is deleted accordingly, and the TrailingFence template parameter used only by that kernel is removed with it. #3029 fixes shared memory accounting: the scale buffer was previously summed in raw bytes without accounting for 1024-byte alignment. The shape m=16, n=163840, k=3584 therefore failed at launch.

Two performance debts were closed the same day. #3023 rewrites TopKSelect: calls with fewer than twice the SM count of rows go to a register kernel. It reads one row from global memory at a time, and a 4096-bucket histogram determines the threshold; long rows go through radix, loading four keys per 16 bytes. Three decode rows went from roughly 2x behind vLLM to 1.22 to 1.34x ahead, closing #3016.

#3022 makes the MLA cache copy each row as 16-byte vectors, with up to 1024 threads. The main branch left the copy to layout inference, turning the 448-wide latent into 7 scalar 2-byte accesses per thread. This was the direct cause of DeepSeek-V4-Flash decode lagging vLLM.

Source: https://github.com/tile-ai/TileOPs/pull/3026.

I. Core Project Progress

1.1 Main repo CPU backend adds serial lowering for two logical reductions: any_of and all_of

#4389 adds dedicated lowering for tl.any_of and tl.all_of to the CPU backend. Previously these two operators could not go through the regular CPU pipeline. The implementation adds a new LowerCPUAnyAll pass, inserted before LowerTileOp. The lowering is a serial scan in row-major order with short-circuiting: any_of stops on the first true value, all_of stops on the first false value.

Empty reductions take the standard identity elements: false for any_of, true for all_of. Numeric elements are converted to booleans by nonzero-ness, and NaN in floating point and bfloat16 is treated as true. Reductions in while conditions are reinitialized and rescanned on each condition evaluation, preserving the original semantics. The pass is also exposed to the CPU Python transformation interface.

Source: https://github.com/tile-ai/tilelang/pull/4389.

1.2 topk regression test sets a Z3 resource limit to eliminate timeouts on CUDA CI

#4407 addresses the timeout of test_topk_candidate_overflow on CUDA CI. The cause was costly Z3 queries issued during the simplification phase. The fix sets arith.z3_rlimit to 100 when the test loads the kernel, keeping the other existing JIT options. The change applies only to this regression test.

The author generated TIR locally for the four topk specializations and confirmed that Simplify completes with the limit set. The author also notes: there is no CUDA code generation on the local machine, and no remote GPU available. Full compile time and GPU correctness were not verified.

Source: https://github.com/tile-ai/tilelang/pull/4407.

1.3 Ascend autotuning test removes cross-NPU probe to avoid contaminating subsequent cases

#4401 deletes the other_npu branch in the set_autotune_inputs test. That branch performed a cross-NPU copy to determine whether the runtime supports inter-device input alignment. On some Torch-NPU and CANN combinations, this copy aborts the NPU context.

Catching RuntimeError and skipping the case does not restore the context. Subsequent unrelated cases in the same pytest process then fail as well, so the failure manifestation depends on execution order. After removal, three coverage cases remain: inputs captured on the current NPU stay on the current NPU, inputs captured on CPU are moved to the benchmark device, and passed tensors must match the benchmark device.

Source: https://github.com/tile-ai/tilelang/pull/4401.

1.4 CUDA Tile IR backend RFC resubmitted: only converts what Tile IR can express

#4402 and #4403 submit the RFC for the CUDA Tile IR backend, in Chinese and English respectively, under docs/compiler_internals/tileir/. The goal is to generate CUDA Tile IR from TileLang programs and hand it to tileiras for compilation and scheduling. Layout, pipelining, warp specialization, and instruction selection are all decided by tileiras, optimized per hardware generation.

The backend only converts semantics that Tile IR can express correctly. Semantics that cannot be converted produce a compile error and the program is rejected; full compatibility with the existing CUDA backend is not a goal. The benefits cited by the author: good performance from autotuning alone, without modifying kernels or hand-writing architecture-specific schedules.

This version is a redo of the earlier #3247. Reviewers noted that the old implementation had too many try-catch blocks, lowered case by case for each form seen, built a separate IR, and wrote passes in roughly 18,500 lines of Python. The new RFC redesigns around these four points. The PR is currently a draft, with discussion in #4403.

Source: https://github.com/tile-ai/tilelang/issues/4403.

II. Multi-Backend Adaptation (Ascend / Hygon / Moore Threads / MetaX / Sunrise)

2.1 MLIR Ascend mlir-dialect branch merges tl.shl, tl.shr, tl.cast in one day

The MLIR Ascend repo’s merges land on the mlir-dialect branch, not main. The branch head advanced from 06:23 to 08:47 (UTC) on 11-18, merging three TLIR operators in one day.

#211 adds tl.shl, lowered to hivm.hir.vshl, reusing the existing NpuirShl helper. #212 adds tl.shr, supporting only i16, i32, i64, with round as a boolean attribute defaulting to true. That PR honestly documents one known mismatch: rhs is modeled as a tensor operand, while HIVM’s vshr has a ScalarOnlyHWTrait<1> constraint. The root cause is that the constructors of NpuirShr and npuir_shr do not accept scalars, left for follow-up.

#214 adds tl.cast, with round_mode restricted to six values: round, rint, floor, ceil, trunc, odd. That PR also changes a dialect-level setting: TL_Dialect adds usePropertiesForAttributes = 0. The reason is that tl.cast is the first operator in this dialect with a non-operand attribute, and going through ODS’s default Properties generation would produce a broken CastOp. All three PRs include FileCheck tests, taken from real captured output.

Source: https://github.com/tile-ai/tilelang-mlir-ascend/pull/214.

2.2 MLIR Ascend under review: tl.vrelu, tl.abs, tl.or, tl.xor and RoPE kernel

Four more TLIR operators are under review. tl.vrelu is in #261, tl.abs in #238, the latter lowered to hivm.hir.vabs. tl.or is in #225, tl.xor in #228. All four follow the same pipeline of “dialect operator + TIR lowering + HIVM conversion.”

#263 takes a different path, directly adding a rotary position embedding kernel rather than filling in individual operators. Separately, #260 replaces the ascend-mfu skill in the harness with ascend-roofline. The new skill uses a Cube/Vector model to give peak, counts, roofline, MFU, BWU and hardware references. Its FMA probe calibrates to 26.3 TFLOPS on this device and build, 88% of the nominal 30 TFLOPS.

Source: https://github.com/tile-ai/tilelang-mlir-ascend/pull/263.

2.3 Hygon single PR bundles twelve fixes, covering intrinsics, precision and integer vectors

The Hygon repo has only one merge in the window (#27), but its contents cover twelve areas. On the intrinsic side, it fixes hexp call ambiguity and cos/sin dispatch. On the precision side, it fixes fp64 truncation failures and __builtin_bit_cast size mismatches. On the vector codegen side, it fixes shuffle lowering and enables full-wave shuffle reduction.

New capabilities include: rng operations backed by hipRAND, buffer load rebasing, and a cache_warmup intrinsic. There are also several cleanups: 8-bit integer vector broadcasting, pipelined epilogue unrolling for runtime iteration counts, shuffle mask guards, and an ordering fix in FP4 codegen. On the CI side, it pins the NumPy ABI. The commit is signed by two Hygon engineers.

Source: https://github.com/tile-ai/tilelang-hygon/pull/27.

The Sunrise repo merges #11, bumping the version to 0.1.15+sunrise.1.2.1. That PR syncs three upstream sources — TileLang, TileOPs and TileKernels — and updates the TANG and PTPU integrations. The tag appeared the same day, with the previous version being 0.1.15+sunrise.1.2.0.

III. Ecosystem and Adopters (TileOPs target list / TileKernels / topa / docs site)

3.1 Two mHC operators retired as a public API break, three HyperConnection operators take over, under review

#3021 removes MHCPreFwdOp and MHCPostFwdOp, along with their kernels, manifest entries, workloads, benchmarks, and tests, following the plan in #2796. DeepSeek-V4-Flash and GLM-5.3-Flash switch to HyperConnection’s pre, post, and head operators. The mhc.expansion manifest primitive is also removed, since only the deleted operators used it.

This change is registered in scripts/ci/api_compat_allow.txt as a reviewed public API break. That file records reviewed interface removals, and the removal decision must be confirmed during review.

The three replacement proposals are under review: #3032 adds pre, #3035 adds post, #3039 adds head. Separately, #3036 adds sqrt-softplus and hash routing for DeepSeek-V4-Flash to FusedTopKFwdOp. #3038 adds attention sink and index-only selection to DSADenseFwdOp. This group of changes points to the same thing: rearranging the sequence-modeling and attention interfaces around DeepSeek-V4’s actual structure.

Source: https://github.com/tile-ai/TileOPs/pull/3021.

3.2 Seven performance-target issues turn “gap to the fastest library” into an acceptance checklist

Seven new performance-target issues were opened in the window, each with hardware, shape, and target. #3018 tracks the gap to FlashAttention 3 on GQA variable-length vision rows with head dim 72. #3019 tracks the gap to vLLM on MLA cache writes. The corresponding fixes are #3023 and #3022, with #3022 closing #3019 the same day.

#3037 gives the full DSADense comparison table: H200 at 1500 MHz, bf16 dense peak around 811 TFLOPS. CSA rows reach about 58% of peak because each pair’s softmax and the next pair’s key gathering sit between two matrix multiplies. HCA’s 4k rows pay the cost of 64 key blocks, counting 160 keys as 192.

#3031 tracks the gap to TileKernels for HyperConnection pre on decode and medium sequences. #3034 tracks the decode rows of GatedPoolCompress, targeting SOTA on that shape.

Source: https://github.com/tile-ai/TileOPs/issues/3037.

3.3 TileKernels comparison-timing proposal: the benchmark image is still pinned to tilelang 0.1.12

#3028 proposes adding DeepSeek’s TileKernels to the benchmark comparison so that DeepSeek-V4 rows are timed directly against DeepSeek’s own kernels. The obstacle is the version: TileKernels requires tilelang no lower than 0.1.15, while the benchmark image is pinned to 0.1.12. No benchmark can currently import it.

The proposal gives three mappings. FP4QuantPerGroupFwdOp and FP8QuantPerTokenGroupFwdOp map to per_token_cast. SiLUAndMulFwdOp maps to quant.swiglu_forward. The acceptance condition is that these benchmarks actually time TileKernels in CI and that the nightly run records them as a comparison. This explains why, in the descriptions of the two quantization proposals filed the same day, TileKernels’ numbers can only be given in comments.

Source: https://github.com/tile-ai/TileOPs/issues/3028.

3.4 topa runs a full review round with one command; the GPU is exclusive only during timing

topa merged #41 and #43, turning review into repeatable rounds. #41 makes every PR change trigger a new attempt: a new head gets a full review, everything else only a recheck. Results are posted only when the PR is unchanged and still open. On the GPU side, a per-card-locked topa-bench is added, which holds a card exclusively only during timing and yields it to other rounds the rest of the time.

#43 compresses the three-step flow into a single topa review <PR>. Review comments are fixed at three single-sentence points: problem, reproduction, fix. The review directory for the same PR keeps the worktree and posted.json, and a second review fetches only when the local copy is behind GitHub. The no-change wait for a review round is relaxed from 60 minutes to 10 hours.

Beyond these two, topa opened 10 new issues in the window (#35 to #46). They are all actionable work items with fix(...) titles, focused on roofline pricing. They include computing makespan by CTA wave, pricing scatter by number of written rows, and counting resident CTAs into the grid. These are the next batch of tasks the pipeline has queued for itself.

Source: https://github.com/tile-ai/topa/pull/41.

V. Trend Observations

  • Platform boundaries are expanding: a Metal target and automatic differentiation landed on the same day, extending the compiler from inference kernels toward training and Apple GPUs. Both stop at the IR layer, and the order is clear: interfaces first, backends and runtimes later.
  • FP8 is entering delivery: quantization, short-row streaming, paged decode, and WGMMA primitivization all landed the same day, each benchmarked against vLLM, FlashInfer, or DeepSeek’s own implementation. Performance acceptance remains separate from the merge bar; both #3010 and #3005 self-assessments are still below the acceptance line.
  • Performance debt is now managed issue by issue: seven new target issues spell out hardware, shape, and target multiple. Two were fixed and closed the same day they were opened; the list is driving delivery, not just recording debt.
  • Ascend shows a two-track speed gap: the main repo this issue only wraps up tests and CI, while the MLIR route added three TLIR operators in one day. The former is converging; the latter is still in the early stage of paving one operator at a time.
  • Backend distributions are starting to fork: Sunrise already has 0.1.15+sunrise.1.2.1, MetaX is preparing 0.1.12+musa.5, and Hygon is following up with merge-style fixes. With three vendors releasing separately, version alignment and the compatibility matrix will become a new maintenance cost.
