Today’s Highlights

Today’s merge volume fell from yesterday’s 24 to 12, but the structure is more concentrated: five in the Ascend-specific repo, five in the main repo, and one each in TileFoundry and TileOPs. The Ascend batch is entirely algorithm-side operators, and all of them are the kind that can be used directly by upstream models. The kpool compression operator for the GLM-5.3-Flash sparse attention indexer packs per-dimension softmax pooling, BF16 boundaries, normalized Hadamard-128 rotation, and E4M3 quantization into a single pure Vector kernel; each block covers 64 pools, with two vector subkernels handling 32 each, zero host-side reordering, and strided transfers directly following the caller’s 3D layout. E4M3 encoding is implemented with pure integer bit operations (round-half-even, including subnormals, saturating to 448), relying on neither the FP8 type nor approximation. Chunk Scaled Dot KKT is the A = gate(K K^T) in the chunked gated linear attention forward pass, with static four-block unrolling, zero GM workspace, and zero host operators; match rates for all three L0 and L1 cases are 1.0.

The main repo’s theme today is the compilation and launch layer. Full-warp reduction now uses redux.sync: on the main branch, four independent 32-lane FP32 max reductions expand to 20 shuffles on CUDA 13.1, sm_103a; after the change they become four redux.sync.max.f32 instructions with no shuffles. Integer reductions use hardware reduction on SM80 and above; FP32 max/min is available only on sm_100a, sm_100f, sm_103a, and sm_103f; narrow types (including CUTLASS’s FP16 and BF16) are promoted to FP32; FP64 still uses the shuffle path. The author explicitly does not claim end-to-end speedup and provides only instruction-level comparisons. The autotuner’s concurrent compilation, meanwhile, splits the compile lock that was previously held for the entire section: each coverage config is copied into an independent JITImpl via dataclasses, only candidates sharing the first-stage key are serialized, and debug output writes to disk remain serialized. The author’s cross-backend validation is 1797 items on Ascend, 3220 on ROCm, 95 on Metal, and 5500 on CUDA.

Another detail worth noting: today’s newly opened reverse-indexing miscompilation defect (#3705) was reproduced at runtime using the tilelang branch repo under the T-HEAD name. This indicates that a full-fledged team is already tracking this upstream code as the foundation of its own hardware stack, rather than treating it merely as an external dependency.

I. Core Project Progress

1.1 Main repo: full-warp reduction switched to redux.sync; four 32-lane FP32 max reductions go from 20 shuffles to 4 hardware reductions (#3692)

Merged 10-29 15:08, 4 files +337/-35. Previously, ordinary cross-thread reductions (such as T.reduce_max) were still expanded into shuffle trees even when the whole group was an aligned full warp: on main branch 837486a, four independent 32-lane FP32 max reductions compiled to 20 shuffles and zero redux instructions with sm_103a and CUDA 13.1; after the change they are four redux.sync.max.f32 and zero shuffles. The approach reuses the existing warp_reduce helper from scalar and batched full reductions: callers only check thread geometry (whether aligned to a warp, unit stride, full warp), while architecture, data type, and operator dispatch are left to the helper. Integer reductions use hardware redux on SM80 and above, with smaller integers promoted to 32 bits; FP32 max/min are only available on sm_100a, sm_100f, sm_103a, and sm_103f; narrow floats are promoted to FP32 before entering the helper, while FP64 keeps its precision and stays on the shuffle path. Sub-warp, strided, and packed reductions, as well as unsupported operators and targets, all fall back to shuffle; cross-warp shared-memory exchange and barriers are unchanged. A compile failure is also fixed along the way: custom unsigned integer reducers previously failed to compile because inline dispatch returned an empty type; they now fall back to shuffle. PTX regression assertions check for the real instructions and the absence of shuffles, and runtime coverage includes signed/unsigned boundary values, batched non-zeroing, NVRTC execution, non-finite values, signed zero, and exact FP64 results. The author explicitly does not claim end-to-end speedup. An existing known issue is also noted in the description: batched reductions fail for FP16 and BF16 at batch=4 with two outputs per thread and batch=8 with four outputs per thread; the original template on main branch reproduces it as well, and the failure occurs in the lowering stage, unrelated to this change.

1.2 Main repo: autotuner’s independent JIT configs now compile concurrently; the lock is kept only for candidates with the same key (#3476)

Merged 10-29 16:24, 2 files +54/-46. On main branch, _make_jit_compile_func held a single lock for the entire compilation period, serializing even configs that only used default compile options, so frontend, lowering, and device compilation were all queued. The fix constructs a candidate JITImpl for each override config with dataclasses.replace, keeping backend, target, output selection, log level, compile flags, and debug options at their original values; default options still go through the original lazy call path, preserving its kernel cache and object identity; only candidates sharing the first-stage key (computed by the argument binder used by get_tir, preserving positional arguments, defaults, and factories with tensor annotations) are serialized; shared output for debug files is still serialized inside compilation, covering debug_root_path, IR dump settings, and layout visualization. Acceptance data comes from the cross-backend pipeline: the Ascend job merged 3be11be6 with main branch c58a86f0, Python 3.12.14, torch_npu 2.10.0, CANN 9.3.0, with 1797 checks passed, all 50 AscendC examples passed, and 44 PTO examples passed with 6 skipped; the ROCm 7.2 job on gfx942 passed 3220 and skipped 2765; the Metal job on macOS arm64 passed 95 and skipped 5; the CUDA job on H100 PCIe with cu130 passed 5500 checks and skipped 491, with examples at 76 passed and 14 skipped; the CuTeDSL job had 75 passed, 17 skipped, and 2 unexpected passes.

1.3 Main repo: Ascend buffer view layouts and pointer units no longer propagate across aliases (#3623)

Merged 10-29 13:17, 23 files +1139/-438. Multiple buffers created by T.view or T.reshape can share the same storage while requiring different layouts; previously layouts were resolved uniformly by the shared data variable, which could select the wrong Cube mapping or DMA address, and stale tiling geometry could drop version offsets or interpret typed pointer offsets with the wrong unit. This change attaches layout to the individual Buffer view throughout layout inference, fractal storage normalization, multi-buffer materialization, and copy and matmul lowering; view identity is preserved through layout mapping and compact L0 spacing application, and raw pointer offsets are remapped according to their own element units. Layouts no longer propagate across storage aliases; each view uses its own annotation, an operator-inferred layout, or plain addressing. On the same versioned allocation, Cube views can now use different MajorK and MajorMN layouts, provided the logical strides are dense, the base offset is zero, the operand types are compatible, and the padded storage sizes are equal. Multi-buffer aliases share one physical slot size, converted by each view’s element unit without propagating index mappings; a view merely reinterprets existing bytes, so writers must write in the representation the consumer expects, and the access-pointer interface can be used when a view must be selected for built-in instructions.

1.4 Main repo: GM-to-L1 copy and out-of-bounds padding merged into one scheduling task, removing a redundant MTE2 barrier (#3543)

Merged 10-29 11:39. The global-memory-to-L1 copy and its out-of-bounds padding jointly prepare the same L1 data; previously the padding could be split into a separate scheduling task, so synchronization inserted a redundant MTE2 pipeline barrier between the copy and the padding. This change compiles each copy and its padding into the same Ascend task, so consumers wait for the complete data including padding; FP8 MX K-tail padding is likewise merged in and retains conditional padding within the task, and existing explicit task scopes remain unchanged with no nesting introduced; the former MX deferred-padding queue is removed, and each operand’s padding immediately follows its own copy. 47 focused tests pass, covering both ordinary out-of-bounds padding and MX tail blocks.

1.6 Three new defects filed: padded shared buffer via bulk copy reports shape mismatch, negative-scale iterative graph miscompiles reverse indexing, view bit width overflows in int32 (#3704 / #3705 / #3707)

All three issues point to boundaries of static checking. First, #3704 reports that when a global tensor whose last dimension is not 16-aligned (for example K=100) is copied into a padded shared buffer (BK = cdiv(K,16) times 16 = 112), once this copy is routed to the bulk copy path, lowering directly reports a shape mismatch between the shared block and the global block (112 vs 100), at the bulk lowering of the CUDA copy; padded buffers work fine on the elementwise path, and padding is exactly the common pattern for satisfying matmul alignment, so any kernel using it together with bulk copy can hit this. Second, #3705 reports that flatten-buffer simplification miscompiles reverse indexing on a negative-scale iterative graph; the reproduction environment is v0.1.15 and a source build of the tilelang branch repo under T-HEAD, and the report also verified that the affected split function is unchanged in upstream main branch and the corresponding TVM revision, making it a shared upstream path. Third, #3707 reports that views and reshapes multiply in int32 when checking buffer bit width, wrapping above 2^31: the Qwen3.8 lm_head weight is 248320 times 2560 bytes of NVFP4, totaling 5,085,593,600 bits, and the bit-width product wraps to 790,626,304, after which converting the static view bit count to an int32 constant throws a literal-out-of-range error.

1.7 Three fixes under review: bit width switched to int64, CPU scalar GEMM clears only the target region, cache disable bypasses both in-process caches (#3708 / #3709 / #3710)

Corresponding to the three defects above and yesterday’s cache semantics topic, the fixes went under review the same day. The bit-width change multiplies static dimension products as Python integers, converts symbolic dimensions to int64, and converts literals exceeding int32 to int64 constants; the regression case directly uses the buffer from that issue (view shape 248320 times 5120), which errors on main branch and passes after the change, and same-shape views with symbolic dimensions are also covered. The CPU change fixes scalar matmul zeroing the entire underlying buffer when clearing the accumulator: for a 4-by-4 output buffer initialized to 7, calling a subregion of rows and columns 1 to 3 would zero the 12 elements outside the region; the fix initializes only with the output region’s own offset and extent, and the regression case accordingly uses an all-ones 2-by-2. The cache change fixes #3699 recorded yesterday: disabling the kernel cache only flipped the cache state, while the jit wrapper still checked two in-process caches before actually compiling, so ordinary calls within a block would get a kernel compiled earlier in the same process; the fix reads the cache switch at call time (also covering environment-variable disabling), skips both in-process caches while disabled, and restores afterward. The test went from 1 failed and 4 passed before the change to all 5 passing.

II. Multi-Backend Adaptation (Ascend / Hygon / Moore Threads / MetaX)

2.1 Ascend: kpool compression operator for GLM-5.3 sparse attention indexer merged, single-kernel pure Vector path (#1910)

Merged at 15:41 on 10-29. For each pool (pool_size = 4), the operator adds the score tensor to the positional encoding, then performs per-dimension softmax pooling; the pooled vector passes through the BF16 boundary, is multiplied by a normalized Sylvester Hadamard-128 rotation (divided by the square root of 128), and is finally E4M3-quantized with per-vector FP32 power-of-two absolute-max scaling: the E4M3 rows and scaling factors are written to a contiguous scratch area, from which the host adapter scatters them into the paged cache (the key cache carries E4M3 as unsigned bytes; the scale cache is written in place as FP32). The implementation is a single-kernel pure Vector path; developer mode enables the three switches for auto-sync, auto vector-and-matrix core merging, and memory planning. Each block covers 64 pools, with two vector subcores each handling 32 independent parallel pools; the host performs zero reordering, and the kernel reads directly with strides according to the caller’s 3D layout, with positional encoding folded into pooling. E4M3 encoding is pure integer bit manipulation: round-half-even, including subnormals, saturating to 448, with no FP8 types and no approximation.

2.2 Ascend: Chunk Scaled Dot KKT forward operator for chunked gated linear attention merged, static four-chunk unrolling, zero GM workspace (#1803)

Merged at 15:01 on 10-29. Adds a scaled dot-product forward for chunked inner products: for the forward computation of chunked gated linear attention, A equals the gate-gated K times K transpose. Implemented as a single compiler-decorated kernel, statically unrolling four chunks for on-chip fusion, with zero global memory workspace and zero host operator calls, and all four developer-mode switches enabled. Tests are tiered into L0, L1, L2, and boundary levels, selectable from the command line; L0 covers three cases (with gating, without gating, small-scale with gating), with accuracy checked against a PyTorch CPU FP32 golden reference using dual mixed-tolerance gates. The reported test shape is batch 1, sequence length 32768, 32 heads, head dimension 128, chunk 64, gating enabled, BF16 input/output, FP32 accumulation; all three cases each of L0 and L1 pass, with a match rate of 1.0000 and maximum absolute error between 0 and 0.25.

2.3 Ascend: Fix merged for W4A4 int4-by-int4 GEMM producing entirely wrong results, root cause being misreported type size and silently disabled dedicated transpose instruction (#1731)

This one, still under review yesterday, was merged today at 15:08, corresponding to #438. The root cause is three layers of compounding errors. First, fractal geometry was derived assuming type size equals 1, but the nibble-packed type occupies only 4 bits per element with two elements per byte, so the correct element count for a 32-byte C0 block is 64 rather than 32; all copy strides, repeat counts, and byte calculations were off by a factor of two, and data piled up in the wrong locations in L0A and L0B. Second, the transposed load of the B operand was silently dropped: the generic load path sets a transpose flag for the zN-to-nZ conversion, but the 4-bit dedicated instruction hardcodes transpose off and ignores that flag, so B never gets the layout the matrix multiply instruction expects; the correct path is the dedicated load with transpose, which has no documentation whatsoever in the CANN headers, so probe kernels were used to empirically reverse-engineer the parameters on device (move the full block in one repeat, repeat count = N divided by 64, source stride = K rounded up to 16 then divided by 64, destination gap = 3), and that version actually works in 2048-byte blocks, differing from the generic documentation’s 512-byte fractal unit. Third, the byte count between vector and global memory was likewise computed as 1 byte per element rather than 0.5, making each row copy twice as long and mixing in adjacent row data. The compute instruction itself was always correct, faithfully multiplying the misplaced data; the symptom was 99.6% mismatch, with outputs of -501 and 627 versus correct values of 641 and 1785. The report also documents the global memory int4 packing convention: two nibbles per byte, low nibble for even elements and high nibble for odd elements, with row r starting at byte position r times N divided by 2, consistent with CANN’s own format.

Source: https://github.com/tile-ai/tilelang-ascend/pull/1731

2.4 Ascend: depthwise_conv_2d example resubmitted, switched to manifest-based test channel to avoid the concurrent batch (#1920)

Merged at 15:43 on 10-29. This is a resubmission of #1915: after the original merged, the nightly full CI failed and it was reverted via #1919, with the root cause being that the L0 largest-shape case triggered an unknown error under the eight-way concurrent legacy script batch; this PR slims that case by a quarter and registers the operator into the continuous-integration operator test manifest via the Pytest channel, the same route as the other twenty-five migrated operators, fully withdrawing it from the concurrent batch, with the kernel body byte-for-byte identical to the original. The operator itself supports fp16, fp32, bf16 and arbitrary kernel size, stride, padding, and dilation; strides 1, 2, and 4 take the quantized-region path, others fall back to scalar inner product; the implementation is padding plus convolution as two kernels plus a 1-by-1 fast path, a pure Vector path, with the grid adaptive to geometry rather than hardcoded core counts. Several measured constraints in the report are worth noting: the padding phase costs roughly the number of statements times 35 nanoseconds, independent of byte count, so the tail band is closed with truncation; on the shared memory side, a copy destination offset not aligned to 32 bytes triggers a 0x26 exception in the vector core; synchronization uses a hand-written champion model (auto-sync disabled in the convolution section), with adjacent depth-1 transfers and a compute event protocol between channels, while a depth-2 protocol or inserting a full barrier midway deadlocks.

2.6 Ascend under review: Three NPUIR language-layer view and broadcast fixes (#1962 / #1960 / #1961)

Three PRs entered review the same day and depend on each other. First, #1962 fixes the view descriptor for local unified buffers: the bridge layer looks up buffers by shared data variable, which may return an allocation memory reference without the descriptor applied, so same-type offset aliasing reads the allocation prefix, different-type aliasing enters copy sinking with the allocation’s element type, and same-type reshaping may enter reductions with wrong dimensions; the fix introduces a unified view-acquisition helper, using checked reinterpret casts for same-type non-identity views, and single-block byte allocation plus typed view operations for multi-element-type accesses to preserve common storage identity. Second, #1960 fixes views dropping the source offset: when rebuilding a buffer from a data variable, the view lost the element offset, so offset aliasing started from allocation offset zero rather than the source’s first element address; the fix preserves the offset for same types, converts by element width when the byte-level type changes and requires divisibility, and rejects unaligned or unsupported conversions outright, without introducing storage or data copies. Third, #1961 changes unary vector broadcast inference to use the access region: previously broadcast dimensions were inferred from the original buffer shape, so writing an 8-by-8 source into rows 8 to 16 of a 24-by-8 target failed; the fix infers from the generated memory reference type, preserving the access segment’s shape and existing compatibility checks. All three include independent clean-baseline builds and bitwise verification notes.

Source: https://github.com/tile-ai/tilelang-ascend/pull/1962

2.7 Ascend under review: Fix for bitwise XOR unsigned-byte workspace view in the PTO backend (#1959)

Entered review at 16:36 on 10-29, closing #1721. In the PTO backend, the temporary workspace for bitwise XOR was passed to the instruction as a raw 1D byte region rather than the required 2D view: at generation time the destination’s 2D shape was copied into the workspace’s shape info but not marked as a slice, so a 1D block descriptor was resolved for unsigned bytes (the workspace does no type reinterpretation), and the instruction read and wrote out of bounds at runtime. The workspace itself is a 1D region allocated by source element count, and its capacity suffices for aligned 2D blocks; the failure was in the descriptor, not the capacity. The fix inherits the destination shape, then forcibly constructs a 2D view and marks it as a slice; tests add multiple coverage groups for unsigned and signed bytes (2D automatic temporary, explicit 1D temporary, 1D, aligned non-zero-offset slice with sentinel, signed bytes), and retain the 16-bit regression.

3.2 TileOPs under review: GEMM recomputes grid grouping and resident block count under a power cap; q-b DRAM reads drop from 168 MB to 94 MB (#2794)

Entered review on 10-29 at 21:44, 2 files, +35/-12, following up on the performance issue for back-to-back calls. Two changes: first, when A fits in one L2 cache partition but B does not, grid grouping lets one group span all rows, so each B block is read from memory only once instead of once per 16-row group; on the q-b shape of DeepSeek V3 prefill (4096 by 24576 by 1536, NT layout), memory reads drop from 168 MB to 94 MB. The split boundary for narrow blocks remains constrained by 16-row groups, and the selection is unchanged. Second, the resident block count on width-uniform dual-cooperative-group grids is changed to a ceiling resident count computed from the block count, total block count, and processor count, rather than using the processor count directly, because the busiest block must run the same number of blocks regardless, while each wave can read fewer distinct panels; ping-pong, narrow-block, and mixed-width grids still use the processor count. Tests run the operator suite on H200, CUDA 13.2, PyTorch 2.13, and TileLang 0.1.12: 212 passed, 24 skipped.

Source: https://github.com/tile-ai/TileOPs/pull/2794

3.3 TileFoundry: AMX runtime operators converted to 39 static TIR contracts, a breaking change (#279)

Merged on 10-29 at 15:59, a breaking change (the commit title carries an exclamation mark). The motivation is to give AMX an explicit, typed operator declaration that agents can match and evaluate from the same computation description. The approach describes 24 AMX runtime operator families as 39 statically registered contract versions, with parameter domains, operand and layout patterns, side-effect sets, and target capabilities M1 through M4; it adds a Python evaluator and a raw C simulator as the gold standard, plus 59 representative atomic cases covering all 39 static operators, with high-level and mid-level IR cases running real 2-, 4-, 8-, and 12-thread domains and verifying candidate acceptance and rejection; high-level candidates are discovered from in-operator match declarations, preserving target-specific capability inference. Naming is unified under the AMX namespace, aliases are held by the registration entry point, and registered names are given by a unified query; CPU execution uses thread topology, with private logical AMX register state, and the thread count is not the AMX engine count. Validation is 46 focused tests passing, including one comparison against 57 raw C results and two lifecycle checks.

Source: https://github.com/tile-ai/TileFoundry/pull/279

V. Trend Observations

The rhythm on the Ascend side has shifted from “porting the backend” to “filling in operators.” Yesterday’s entry was the NPUIR backend merging into main, with acceptance criteria of 504 self-tests and 71 versus 72 examples; four of the five commits merged today are operators and examples, arranged according to upstream model requirements: GLM-5.3’s indexer compression, the inner product of block-gated attention, four-bit quantized matrix multiplication, and depthwise convolution for quantized vision models. What these operators share is that quantization and fusion are written into the kernel itself (E4M3 pure-integer encoding, four-bit packing conventions, dual-kernel plus 1×1 fast path) rather than left for host-side remediation. At the same time, two commits establish engineering standards: operator performance profiling enters the process, and unstable test cases caused by concurrent batches move to a checklist-based test channel. This shows that the main contradiction on the Ascend side is shifting from “can it compile” to “can the operator’s numerics and performance be stably accepted.”

The main repo’s three commits today (hardware reduction, concurrent compilation, out-of-bounds copy grouping) correspond to instruction selection, compile latency, and emission quality — all compiler-core issues rather than language-layer features. This is consistent with yesterday’s new-defect direction: the boundaries of static checks such as out-of-bounds, aliasing, and bit width are being opened one by one. Two of today’s three new defects (batched copy with padded buffers, view bit-width overflow) were triggered on real model shapes, indicating that TileLang’s usage has reached a scale where boundary conditions are encountered: NVFP4 weights of 248320 by 5120, and attention head dimensions where K is not a multiple of 16.

The most notable ecosystem development today is “fork-ization.” An independent operator repo has appeared in the Ascend community; T-HEAD has a TileLang branch repo with a PPU branch; PTO-ISA has turned both its problem sets and benchmarks into companion repos; and another dev-tools repo releases the sinking tracker as an independent package. The common premise of these moves is treating TileLang as the foundation of one’s own hardware stack: needing to change layouts for one’s own instruction set, perform acceptance testing with one’s own test system, and accumulate experience in one’s own knowledge format. For a domain-specific language, this is a harder adoption signal than star counts, but it also means upstream must begin to face the long-term cost of “how branches synchronize with upstream”: today’s #3705 defect is exactly what branch users hit first in real builds.
