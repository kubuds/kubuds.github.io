I. Core Project Progress

1.1 Main repo: out_idx outputs now allocated on the caller’s stream; five-of-five corruption on H100 reproduction drops to zero (#3649)

Merged 10-26 22:36, 5 files +183/-31, fixes #3648. The cython, nvrtc, and cutedsl adapters all accept stream= and launch on that stream, but out_idx outputs were allocated with torch.empty on the current torch stream; the caching allocator reuses blocks ordered only by “allocation stream,” so a block of memory that still had queued work was returned as free, and that work then overwrote the kernel results. The fix adds output_allocation_stream(stream, device): it returns the caller’s stream when it differs from the current stream, otherwise null; a zero handle maps to the default stream, because older PyTorch’s ExternalStream(0) yields a pooled stream rather than the default stream. On an H100 80GB the reproduction went from 4/5, 5/5, 5/5 corrupted to 0/5 for each of the three adapters, and the new test file passes 10 items. The author explicitly rejected adding wait_stream: that would make every call order the launch stream behind all work on the current stream.

Source: https://github.com/tile-ai/tilelang/pull/3649

1.2 Main repo: NVRTC device-side compilation wired into the TVM-FFI execution path, new compile key entries (#3285)

Merged 10-27 00:02, 12 files +133/-133. Adds tl.cuda_compiler="nvrtc", working with the existing TVM-FFI host runtime: NVRTC compiles device-side CUDA source into a cubin, the shared CUDA runtime module imports those bytes, and host-side binding, scalar conversion, conditionals, loops, and launch preparation are still generated by TVM-FFI; the default remains nvcc, and the old execution_backend="nvrtc" adapter keeps its original implementation. The binary cache key now includes the compiler name and NVCC/NVRTC versions, hashed together with target details and effective compile options; architecture tokens such as 90a and 100f are preserved as-is, and incompatible targets report a diagnostic before compilation; every successfully created NVRTC program is destroyed in a finally block. The PR’s CI on H20 ran 5506 passed, 491 skipped, 76 examples passed, 3220 passed on the ROCm 7.2 channel, and 1797 passed on the Ascend channel.

1.5 Main repo: SM120 block-scaled GEMM explicitly unrolls the K atom; FullCol config gains 51% (#3286)

Merged 10-26 16:36, 4 files +308/-2. This is the follow-up to #3257’s introduction of T.gemm_blockscaled and T.mma_gemm_blockscaled: when the A operand comes from register fragments, the K-atom loop previously used T.serial, making every fragment access a runtime index, and nvcc in pipelined and warp-specialized kernels that it does not unroll itself would keep the fragment in local memory, i.e. spill the MMA path; switching to T.unroll(..., explicit=True) makes every access a compile-time constant. The second change: when both SFA and SFB are in shared memory, each MMA pair previously read shared memory three times; now each lane loads a compact selection pack once per K atom, covering both row-major and block-K-major layouts. On RTX PRO 6000 Blackwell, 143 pass and 4 skip, with output bit-identical to the float32 reference; in the register-A benchmark FullRow gains 2.7%, Square 11.1%, and FullCol 51% (348.5 to 526.7 TFLOPS), and ptxas-reported spills drop from 664 and 484 bytes to 320 and 160. The author also notes that the block_K = 128 with row-major shared scale path already fails validation on main, unrelated to this change, and is left for separate investigation.

1.7 Main repo: sm8x sparse metadata operand dtype no longer falls through without a fallback (#3335)

Merged 10-26 16:54, 1 file +12/-5. The sparse metadata layout constructor dispatches by architecture, pairing the MMA operand dtype with the metadata buffer width; the sm90 branch rejects unsupported dtypes, but the sm8x branch was written as two whitelist checks with no fallback, so any other spelling fell through to the placement logic below, which infers group and interweave from buffer width alone. The consequence: float8_e4m3fn (torch’s canonical spelling) was accepted as 16-bit metadata and given the fp16 group 32 and interweave 4 convention; any unrecognized spelling, including typos, was also accepted at any width. Unsupported dtypes now raise an error.

1.10 New defect: three misplaced-barrier cases in ThreadSync, with three fixes under review (#3680 / #3682 / #3681)

#3680, opened 10-26 19:56, reports that tl.ThreadSync places barriers incorrectly in three places: a guard on a per-thread value is treated as block-uniform, so the barrier stays inside the branch and waits for threads that skipped it; a barrier in one branch of an if clears the outer sequence’s pending dependencies, so when the block skips that branch, writes before the if conflict with reads after it; and when a loop’s trip count is per-thread (e.g. modulo thread ID), the barrier stays inside the loop body, and the partially synchronized lowering fails outright with “cannot prove thread rectangle.” #3682 (3 files, roughly +39/-7, 12 new tests) uses a forward analysis pass to collect buffers that may hold per-thread values and shrinks the synchronization summary by branch and loop reachability; the author states the change only reports races, does not eliminate them, and does not split branches. #3681 fixes another crash from the same root: since sm_100, float32 loops are vectorized to 256 bits, and broadcasting to 8 lanes generated an expression taking the address of a temporary, which NVRTC rejected with “must be an lvalue”; the fix assembles the bits directly with __float_as_uint plus shifts. A companion tvm fork PR #88 translates boolean bitwise operations into logical operations, letting the prover reach the same conclusion within a 10000-step budget.

1.12 Under review: transpose target shape validation, region-scoped kill reordering (#3677 / #3670)

#3677 moves tl.transpose target shape validation into the TransposeNode constructor, running after NormalizeToAccessRegion, so it also covers direct construction that bypasses the Python wrapper; equality is decided with arith::Analyzer::CanProveEqual rather than comparing Python dimension lists, so (3, n+1) and an independently constructed (n+1, 3) are still accepted, and constant mismatches report the axis number and both lengths. Previously a mismatched target lowered to out-of-bounds indices, producing wrong results or out-of-bounds writes. 13 tests pass on the CPU target. #3670 replaces the leftover scope_level mechanism in shared-memory liveness analysis: that value only increments inside For bodies containing SeqStmt and never increments for While, so it errs in both directions—in the While case the kill point does not cross the back edge, the packer overlaps mutually exclusive regions, and on sm90 measured results double each round; in the sibling-loop case it lets the kill cross the whole region boundary. The new rule computes from the real outer For and While chains and each loop’s contiguous interval, clamping both the out-of-bounds and early-stop directions.

II. Multi-Backend Adaptation (Ascend / Hygon / MetaX)

2.1 Ascend Main Repo: Precise Addressing Interface with Versioned On-Chip Buffers (#3607)

Merged 10-26 10:04, 14 files +982/-26. Adds T.annotate_buffer_addresses, allowing precise byte-level addressing of allocations in the UB, L1, L0A, L0B, L0C, and SS pools within the post-scheduling Ascend pipeline; buffers placed into addressing must first declare a fixed number of versions via T.annotate_buffer_versions. Validation occurs after version expansion and layout completion, covering missing or unsupported version counts, overlaps, misalignment, dynamic sizes, and capacity overflow; the allocator must also reserve space for the SIMT UB context and yield to the AIV private address space, and L0 scale factor handles follow their data allocations. Partial mappings pin only the given ranges, while remaining buffers are placed in aligned free space and may not reuse occupied addresses; pools without addressing annotations retain their original behavior. During subcore projection, only annotations on active storage copies are retained.

2.3 Ascend Under Review: Early Rejection of On-Chip Memory Overflow, E4M3 UB-to-L1 Copy, View Layouts and Pointer Units (#3655 / #3639 / #3623)

#3655 makes MergeUBAllocations reject overflow against target physical capacity during lowering: two independent loops each legitimately select two 32 KB L0A slices, and after merging 64 KB exactly fills capacity; previously this emitted pointer offsets past the end of the physical buffer without any size metadata, and now it produces a short diagnostic. #3639 enables E4M3 UB-to-L1 copy: ND inputs are automatically rearranged via the existing scatter and post-copy pipeline, or copied directly into pre-arranged NZ inputs, reusing existing geometry checks and adding FP8 element-size handling to footprint and latency analysis. #3623 makes buffers created by T.view and T.reshape each preserve their own layout, avoiding incorrect Cube mapping or DMA address selection when resolving layouts through shared data variables, and remaps bare pointer offsets in their own element units.

2.4 Ascend Under Review: Optional Batch Scheduling, Cross-Core Sync Requires Batch Mode, L0C Dual-Copy Direct Conversion (#3675 / #3614 / #3468)

#3675 adds optional batch scheduling to Ascend (schedmode 1): in normal mode the scheduler launches an operator as soon as the required core resources are partially available, so full-core synchronized operators across multiple streams may interleave; batch mode waits for all resources to be ready before launching as a whole, and must be used for full-core synchronization scenarios; #3614 describes the symptoms and fix for the same mechanism under mode 0. #3468 handles the A5 limitation that FixPipe cannot enable dual-destination mode and quant_pre simultaneously, letting T.dual_copy perform L0C fp32 to f16/bf16 conversion directly, eliminating one Vector conversion, one fp32 UB buffer, and the L0C-to-UB fp32 bandwidth.

2.6 Ascend Repo: W4A4 int4 Matrix Multiply Produces Wrong Results, Root Cause Is Nibble Packing Treated as 1 Byte (#1731)

#1731 updated 10-26, with fairly complete localization and reproduction. The entire C++ template stack derives fractal geometry from sizeof(AscendC::int4b_t) == 1, but this type is nibble-packed, so a 32-byte C0 block correctly holds 64 elements rather than 32; thus all three layers of movement exhibit a twofold deviation: LoadData parameters from L1 to L0A/L0B are computed with the wrong constant, and data stacks at the wrong on-chip positions; the transposed load of the B operand is hard-coded off by load_cbuf_to_cb_s4 and silently drops the flag, so B never gets the nZ layout expected by mad_s4; byte lengths between UB and GM are computed at 1 byte per element, copying twice as much per row and mixing in adjacent rows. The compute instructions themselves are correct, so the symptom is “normal magnitude, all values wrong” (the original report had 99.6% mismatch). The fix all lands in src/tl_templates/ascend/common.h and two transformations, adds a W4A4 example and 10 int4 regressions, and takes the 1024 cube end-to-end from 99.6% mismatch to zero mismatch; the existing gemm_v0 suite (48 items), l1_to_l0 and gm_to_ub (263 items), and elementwise (492 items) all pass.

Source: https://github.com/tile-ai/tilelang-ascend/pull/1731

2.7 Ascend Repo: GM-to-UB Copies with More Than Two Dimensions Fold Leading Dimensions into DMA Rows (#1805)

#1805 fixes #1231. The DMA model of copy_gm_to_ub and copy_ub_to_gm is a 2D rectangle, but AscendCopy::Lower takes only the last two active dimensions of the region as rows and columns; when there are more than two active dimensions, leading dimensions are silently dropped: a 3D block copy A[t:t+16, :, :] (region 16, 4, 8, 512 elements total) is lowered to 4 and 8, the DMA moves only 32 elements, and the remaining 15 tokens of the UB slice are uninitialized, so subsequent computation reads garbage. The fix folds leading dimensions into the DMA row count, changing both directions. On the same day, the Ascend repo also had a batch of documentation fact-check PR updates (sin and cos, axpy, clamp, bitwise series, clear, fill), among which the clamp one also fixes the ineffective lower bound of T.tile.clamp on PTO.

3.2 TileOPs: D128 dense forward splits keys; prefill-rope drops from 31.04 µs to 17.09 (#2777)

Merged 10-26 22:45, 2 files +527/-124. In the D128 dense call, if a 128-row tile leaves SMs idle, each tile’s keys are split into min(SM count divided by tile count, key steps of the shortest tile) parts, and only when the split can shave two key steps off the longest tile; each part writes an unnormalized fp32 output carrying that row’s scaling max and sum, and the merge kernel weights by the maximum max, so neither cancellation terms nor large logits lose precision. In the tile’s last key step, if a warpgroup’s last needed key falls within the low 64 keys, softmax masks and exponentiates only those 64, and warpgroup 0’s causal diagonal step always hits. On H200 at 1500 MHz, prefill-rope f16 and bf16 drop from 31.04 and 31.01 to 17.09 and 17.09 µs, 2.324× and 2.328× versus FA3; qwen3-8b chunked prefill drops from 31.30 to 17.79. Net +14 test nodes.

3.3 TileOPs: D128 persistent forward rewritten per-thread and writes LSE (#2774)

Merged 10-26 18:22, 2 files +656/-48. 3.4 TileOPs: Fused-add LayerNorm rows split across CTAs; precision defect filed separately (#2768 / #2773)

#2768 merged 10-26 15:45, 5 files +525/-24. The starting point was a nightly benchmark regression (llama-70b decode row from 0.0037 to 0.0044 ms); investigation showed it was not a code change but a tuning reselection: after the tuning key changed, FusedAddLayerNormKernel retuned, and the tuner, timing candidates back-to-back from L2, picked 1024 threads, 19% slower cold than 256 threads. The new FusedAddLayerNormHeldKernel keeps a row (on SM90, one cluster CTA’s share) in registers, splits a row across up to 8 CTAs when that is cheaper on the busiest SM, and picks the block size among whole warp counts that divides the share’s access count; dispatch chooses between “queued rows” and “registers over 255” by mutual rejection, and tuning only offers widths the tuned build’s share can fill, so decode rows cannot be reselected. llama-70b decode is 2.368 µs versus flash-attn’s 4.800. A precision issue exposed by the same change is filed as #2773: fp32 sum-based mean and variance lose precision when rows are far from zero (a row of constant 10000.1 normalizes to about 0.7 instead of the bias), and near 1e36 the sum of squares overflows to all-NaN; the author suggests Welford or a two-pass scaling method.

3.6 TileOPs: Alignment check for call tensors moved up to the operator layer, three follow-ups (#2772 / #2778 / #2780)

#2772 merged 10-26 15:28, 55 files +373/-224: before an implementation runs, the executor copies call tensors whose storage start is not 16-byte aligned into aligned storage, copies back the written ones on success, and returns the caller’s tensors; if a copied tensor overlaps another argument (and at least one side is written), it rejects before running, since the copy would mask the kernel’s own checks; storages without an address (fake tensors or wrappers that refuse reads) are not copied; kernel-side alignment and staging logic (including MoE grouped GEMM, causal convolution state, and fused QK-norm RoPE qkv) is removed entirely. The cost is 1–2 percentage points more host time for aligned calls on the hot path, and 4.4 points for MoEPostPermuteFwdOp with out. #2778 folds this decision into the generated observer and lets the plan cache decide copying, with the hot path only reading that decision; the executor’s separate address walk is removed. #2780 opened 10-26: currently only four kernels check out for overlap with inputs, the rest with out race silently, and each check re-reads data_ptr (12 extra times per call for MoEPostPermuteFwdOp); the direction is to declare per-operator in the manifest whether overlap is allowed and check uniformly at the operator layer.

3.8 TileOPs under review: Paged prefill for FP8 queries multiplies value in e4m3 (#2775)

Opened 10-26 17:20, still updated 10-27 07:00. GQAPagedFP8WSKernel moves the FP8 query’s value product into e4m3: the converting warp transposes each value tile into a K-major e4m3 operand (ldmatrix transpose, one byte permute per word, stmatrix), orders keys within each 16 so each thread’s scores are exactly the probabilities it supplies, then rounds probabilities to e4m3 with in-register packing. Softmax follows FA3’s FP8 form: a 2^8 offset keeps small probabilities out of e4m3 subnormals, the row max moves with each larger score, and key tiles are scanned backward from the last. On H200, llama-8b-fp8-prefill drops from 369.3 to 339.8 µs (versus FA3 from 1.000 to 1.087), qwen3-fp8-ragged-odd from 130.9 to 123.9. The author honestly notes the precision tolerance is relaxed from 2^-4 to 2^-3 because e4m3 probabilities themselves carry about half a 2^-4 of rounding, and FA3 also exceeds on such inputs.

3.10 TileFoundry: Dynamic shared memory sized by the kernel’s actual view (#271)

Opened 10-26 and under review, 12 files +340/-32. The synthesized host entry previously passed dynamic_smem=0 to every TIR kernel, so kernels accessing shared memory via integer TensorView offsets ran without dynamic shared memory and never raised cudaFuncAttributeMaxDynamicSharedMemorySize even above 48 KiB. The author chooses to size by the furthest byte the kernel actually reaches rather than by target capacity, for two reasons: CUDA counts static and dynamic shared memory against the same per-block limit, and this runtime itself holds some static shared memory (ProgramMetaData or shared allocation tensors), so requesting full capacity would fail to launch outright; and the per-block request also determines how many blocks fit on an SM—on sm_89, requesting 99 KiB allows only one block even if only 512 bytes are used. Codegen also now declares smem_base once before the first statement, because in loop_outputs it previously landed inside the first loop’s block and was invisible to the second loop, causing nvcc undefined-identifier errors. Both GPU tests pass on H200 and sm_89; without the patch the former hits illegal memory access and the latter fails to compile.

Source: https://github.com/tile-ai/TileFoundry/pull/271

3.11 TileFoundry: Whole windows emitted as the operand itself; sm_89 GEMM compiles again (#273)

Opened 10-26 and under review, 5 files +54/-24. Code written by schedule finalize for sm_89 GEMM did not compile: lowering wrapped the entire accumulator in a window starting at zero and covering its full length, T.ptr_of(acc[0:0+16, 0:0+8]), and CUDA codegen reports “expected normal source layout” for pointer slices of sharded register tiles; further down, MMA reads register shards as bare slices like lhs_frag_dst[0:0+16, 0:0+32], which likewise has no handling branch. These windows are in fact whole operands. The fix goes into lowering: ConvertHIRToTIR determines once whether a window covers its operand (static-zero start, size equal to operand shape), the three window-construction sites share that determination, and it finally emits T.ptr_of(acc), with MMA reading shards directly. Of 49 schedule fixtures with TIR twins, 29 change their finalize output accordingly; sm_89 GEMM and mesh views compile again, and two wgmma outputs get past the pointer-slice rejection and stop at the next view, which is likewise rejected on main.

Source: https://github.com/tile-ai/TileFoundry/pull/273

3.12 New TileFoundry defect: analysis double-counts shared memory peak and does not propagate it to TIR (#272)

Opened 10-26; the author found it while reviewing #271. Both gaps point to the same consequence: a program that passes analysis is rejected at launch, or the final TIR cannot state how much shared memory it needs. First, the memory analysis compares smem against facts.memory.shared.per_cta (101376 bytes on sm_89), but CUDA applies this limit to static and dynamic shared memory together, and the runtime itself holds 12 bytes of __shared__ ProgramMetaData; this occupancy is written only in runtime.cuh and not told to the analysis, so placements within exactly 12 bytes pass analysis and are rejected at launch. Second, the analysis records the per-CTA shared memory high-water mark in RegionMemoryMetadata.peaks, but ConvertHIRToTIR does not write it into the produced TIR, and PrimFunction.metadata neither prints nor parses it, so it must be recomputed after finalize (#271 does exactly this by scanning all integer-address shared memory views), and a host entry the author writes that requests too little will not be caught before running.

Source: https://github.com/tile-ai/TileFoundry/issues/272

V. Trend Observations

  1. The center of gravity of correctness defects has shifted from “performance regressions” to “not reported at compile time, failing only on specific architectures or memory domains.” All three mainline items that day were of this type: output allocated on the wrong stream (#3649, corrupting only on non-default streams when the current stream has queued work), a TMA cache hint missing a template argument (#3683, failing only on bulk loads with an eviction_policy), and sm8x sparse metadata lacking a fallback (#3335, where only torch’s canonical spelling was recognized, and the wrong fp16 layout convention was applied). What these defects have in common is that they require hardware or parameter preconditions outside normal CI coverage, so they are increasingly driven by the fuzzing series—five of the six closed that day in this chapter came from that series.

  2. Synchronization and memory planning have become the main battleground. The three ThreadSync defects in #3680 that surfaced that day, together with the two fixes in #3682 and #3681, the prover fix in tvm fork repository #88, the regionalized kill reordering in main repository #3670, and TileFoundry #272’s shared memory peak not landing in TIR, all point to the same thing: the compiler’s synchronization and memory judgments are shifting from “heuristic” to “provable.” This also explains why #3666 matters—it replaces the built-in TVM with a separately packaged TIRx, after which such prover fixes can enter the mainline on a normal release cadence rather than remaining in the fork repository.

  3. Backend adaptation has entered a “precise control” phase. Ascend’s T.annotate_buffer_addresses allows the UB, L1, L0A, L0B, L0C, and SS pools to be addressed by byte with overlap, alignment, and capacity validation; Hygon’s register pipeline, warp divergence, and dual-bank partitioning of the scale buffer all push “it runs” toward “it can be laid out according to hardware structure.” These capabilities are concentrated in the past two weeks, indicating that domestic backends have passed the usability threshold and are beginning to address performance ceilings.

  4. Release engineering remains a weak point. TileOPs’s first release, after documentation, manifest, packaging, API stability, and input validation were all ready, has been stuck for days on the TestPyPI dry run and the first tag, with the PyPI artifact still at 2025-10-09. For an operator library with 196 stars and 14 merges that day, installability determines external adoption speed more than another 1 percentage point of optimization; the only unfinished technical item in the tracking issue is MHA row 0.996, and management should not let it continue to block the tag.

  5. The external ecosystem is expanding in parallel. The RISC-V community hub repository, the CANN operator repository, and the Hexagon backend repository appeared or were updated on the same day, indicating that TileLang is turning from “a project of the tile-ai organization” into an ecosystem with separate repositories on multiple platforms. For domestic readers, the RISC-V direction is especially worth tracking: it is directly related to the earlier hardware路线 of AI glasses and on-device inference, but it is still only an empty skeleton, and substantive progress will depend on whether runnable operators and backends land later.
