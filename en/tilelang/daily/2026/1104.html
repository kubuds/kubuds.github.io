Today’s Highlights

The main thread today is a fix that “takes back the performance.” #3643, merged in the previous window, addressed a real correctness issue: separate calls to ThreadSync("shared") and ThreadSync("shared.dyn") could assign the same named barrier ID to disjoint thread groups. The fix was to have the later call preserve IDs already consumed by the earlier one—but this preservation rule also blocked something else: the same group of threads could originally reuse the same ID across two scopes. The cost landed directly on TileKernels’ mhc_pre_big_fuse kernel: this kernel has 96 threads per block, with threads 32 to 95 running a two-stage cp.async pipeline. The sync after the async wait gets ID 3 on the first pass, and the buffer-dependency sync for the same 64 threads gets ID 4 on the second pass. That extra ID raised the barrier resources declared in the compiled artifact from 4 to 5; when running hidden dimension 1280 on B300, the barrier occupancy ceiling thus dropped from 16 blocks/SM to 12 blocks/SM, while register, shared memory, and sync instruction counts were unchanged. #3761’s approach is to have ThreadSync accept an ordered list of scopes, with the CUDA pipeline changed to ThreadSync(["shared", "shared.dyn"]). Sync is still planned and inserted in the original scope order, but some barrier IDs are allocated uniformly only after both scopes have been processed. Before sharing an ID across scopes, a brand-new analyzer proves that the participation predicate holds over the entire candidate thread range; branch and Bind contexts are provided by ConstrVisitor, thread-related predicates are treated as proof obligations rather than assumed true, proven-dense groups use the bounding-box volume directly and skip enumeration of partial thread counts, unproven groups keep the scope in the key and include the participant count in the key, and explicitly numbered barriers (including IDs allocated by an earlier ThreadSync) continue to be preserved. The change is 401 lines across 4 files.

The author did a very clean attribution experiment in the description: changing only the number of barrier resources declared in the compiled artifact, without touching any executable instruction, reproduces the same slowdown. This kind of experiment is worth noting—it turns “performance regression” from an impression into an identifiable single variable, and it makes the acceptance criterion for the fix explicit: not a vague “benchmarks got faster,” but resource declarations back to 4 and occupancy back to 16 blocks/SM.

The second item is supply-side subtraction and consistency of conventions. #3736 deletes tilelang/language/ast/, tilelang/language/parser/, and tilelang/language/tir/entry.py together. These are modules left over from an early local fork of the TVMScript parser, about 3380 lines of Python, with no remaining callers in the repo: the language layer now uses the upstream tvm.tirx.script.parser interface through tilelang.language.tir.common, AST and statement override registration lives in tilelang.language.overrides, and T.prim_func and T.macro are exported by tilelang.language.eager. The actual change is 1 line added, 3384 lines deleted, 10 files, while also removing the ignore rule for *language/ast* in docs/conf.py; public language-layer exports are covered by dialect tests and frontend port tests. #3546 fixes the device convention for autotuning: the supply closure installed by set_autotune_inputs resolved the benchmark device from a parameter that no call site ever passes—what is actually passed is the kernel argument list—so the CUDA or CPU fallback branch moved every captured tensor to CPU on machines without CUDA, and every tuning round failed due to a launcher device mismatch. The closure now uses get_current_device(), the same policy as default tensor supply: CUDA behavior is unchanged, Ascend and MPS now supply on the current device, and other backends still fall back to CPU. Acceptance was on dual-card Ascend950: three Ascend autotuning regressions all failed before the fix and all passed after; in the main repo, 12 tests in testing/python/autotune/ passed and 28 were skipped, with another 3 failing because that machine has no CUDA, which the author explicitly left for CUDA CI to verify.

The third item is on the Ascend side: GM-to-L1 copies expand from “one descriptor per matrix” to whole batches. #3689 allows a [B, M, N] region to be written as a single T.copy; lowering generates batched ND2NZ descriptors, preserving the source-side batch and row strides, deriving the destination-side batch pitch from the physical layout, and routing transposed batches through DN2NZ; source batches beyond the GM boundary are skipped directly while destination storage is left untouched, and M/N tail zero-padding applies only to valid batches. Existing 2D and single-matrix behavior is unchanged; the implementation targets only the AscendC backend and requires the L1 destination to be in canonical matrix layout, with PTO out of scope. Validation was on Ascend950DT with CANN 9.2: 50 AscendC example tests and 1733 Ascend unit tests passed, of which 28 device cases cover batch and M/N tail blocks, whole-batch out-of-bounds, non-contiguous source strides, larger destination storage, and rectangular transpose; CUDA and PTO cases were excluded, and the CI image’s CANN 9.3 was not tested locally, which the author noted in the description. The change is 579 lines across 10 files.

The fourth item is the landing of a hidden thread in TileFoundry. In the previous report it was still listed as “under review”; it merged in this window: #285 makes the commits, waits, and fences planned by sync analysis actually emitted by CUDA lowering, and reverse-validates each one against the plan, throwing LoweringError on mismatch. On the corpus, the default flow yields 14 programs plus sync and rejects 31; for those 14, the TIR differs from mainline only by the newly added statements, and another 30 are identical to mainline; on a single sm_89, 7 programs that build and carry sync were run, 6 matched the reference exactly with clean synccheck and memcheck, while lowering those same 7 the mainline way produced 4 wrong results. The direct symptom the author cites in the motivation is a maximum deviation of 659 for E4M3 GEMM on sm_89. This change adds 788 lines, deletes 214, across 25 files, advancing from “the analysis can prove it” to “emission must match the proof.”

Merged 11-04 00:50, +401 / -72 lines, 4 files. 1.4 Under review: Scalar casts in conditions no longer narrow data vector width, following up on yesterday’s #3734 (#3759)

Updated 11-03 14:09, +148 / -29 lines, 2 files. This closes out yesterday’s merged #3734: #3734 correctly tightened the width limit for data casts after DecoupleTypeCast, but it also made casts inside scalar conditions start limiting data vector width — on b5cb02633, a guarded BF16 copy could be squeezed from 16 lanes to 4 because the condition contained an int64 cast, even when that condition is uniform across all 16 lanes. The fix reuses the planner’s existing condition-uniformity analysis for the cast width exemption, visiting if statements, tirx.if_then_else and Select conditions of scalar predicates separately from their clauses: casts in conditions no longer impose a data-type width limit, casts in clauses still do, and the condition-cast constraint is retained on targets with per-lane vector predicates; the memory-guard behavior of #3579 and the guarded FP32-to-BF16 limit fixed by #3734 are both unchanged. Regression coverage includes uniform guards at 8 and 16 lanes, all three condition forms, FP32 casts inside clauses, vector predicates and rounding-bit grouping; the nine int64 guard cases fail before the fix, and the final legalization and cast-rounding suites pass 74 tests in total.

1.5 Under review: Two user-visible errors become explicit diagnostics (#3765 / #3767)

Both updated around 11-04 01:10, filed by the same reporter. #3765 corresponds to #3653: for a partial barrier guarded by a single thread-index bound, when that bound is a multiple of the warp size, all threads in a warp agree on the condition; but the general arithmetic proof missed thread_binding < 448 when the enclosing branch uses bitwise &, and ThreadSync aborted outright. This PR explicitly accepts this case when the thread dimension is a whole number of warps (also covering bounds equal to or beyond that dimension), while other conditions still go through the existing proof path. #3767 corresponds to #3005: when a fragment is distributed across threads and the same fragment is read and written with two structurally different indices in one T.Parallel body (e.g. a cross-lane pattern like buf[i] and buf[(i + 1) % N]), it cannot be lowered without cross-thread exchange; previously ParallelOpNode::RecordBufferAccess hit an ICHECK in StructuralEqual and surfaced as a compiler internal assertion; it is now a ValueError that includes both index expressions and explains that the fragment cannot be accessed this way. Both are “replace an internal assertion with a diagnostic the user can understand” changes whose perceived impact outweighs their size.

1.6 Under review: Fall back when a padded shared tile cannot be copied wholesale; account 2-CTA TMA bytes to the peer leader (#3738 / #3766)

Both updated between 11-03 21:31 and 21:47. #3738 fixes #3704: a T.copy from a global region smaller than the padded shared tile (e.g. K=100 into BK=112) was classified as a full-tile TMA copy by ClassifyWarpSpecializedCopy and SelectCopyInstForLowering, then failed hard in lowering with s_extent == g_extent (112 vs. 100). The cause is that the selection logic only checked last-dimension alignment, dtype pairing and global stride, not whether the padded extent can form a single whole-tile copy; this PR adds that criterion and falls back to the normal copy path when it does not hold. #3766 fixes TMA byte counting in cluster scenarios: a cta_group::2 TMA load clears the peer bit of the barrier address, so the bytes of a CTA pair both land on the even CTA’s barrier, whereas tma_copy with a cluster barrier previously expected cluster_size × tile_bytes only on rank 0 — which happened to be right for (2,1,1) and (1,2,1), but for (4,1,1) and (2,2,1) rank 0 received only 2 shares while expecting 4, with the other bytes landing on rank 2’s barrier. Neither is a new feature; both are the “internal error the moment a boundary condition breaks” class of defect.

2.3 Ascend Under Review: copy_pipe_to_l1 Sync Annotation Split by Execution Engine, Fixing Wrong Results Reproducing 10/10 on A2/A3 (#1981)

Updated 11-03 20:36, corresponding to #1780. The root cause is clearly stated: A2/A3’s PTO cross-core V-to-C communication relays through GM, and the three transfer stages belong to three engines — AIV’s MTE3 does the UB-to-GM send, AIC’s MTE2 does the GM-to-L1 receive (TPOP’s internal TLOAD), and AIC’s MTE1 does L1-to-L0A; but copy_pipe_to_l1 is tagged PIPE_MTE3 in operation_config.h, so the auto-sync pass generates set_flag(PIPE_MTE3, PIPE_MTE1, …) plus the corresponding wait_flag between it and copy_l1_to_l0a — yet it waits on the AIC core’s own MTE3, whose queue is empty and whose event is set immediately, so MTE1’s read of L1 may be released before MTE2 finishes writing, and L0A gets stale data, producing wrong MMA results. The mis-annotation was introduced with #1238; in the same table copy_pipe_to_ub and copy_l0c_to_pipe are both annotated by execution-side engine, and only this one retained the sender’s perspective. Two pieces of reproduction evidence: after changing PIPE_MTE3 to PIPE_MTE2 in the generated source, the issue author saw 10/10 exact recovery, while locally on the latest main, 10/10 runs were wrong, with up to 16384/16384 mismatched elements in a single run. The fix follows the issue’s suggestion to split the name rather than replace it outright: copy_pipe_to_l1 is annotated PIPE_MTE2 (A2/A3’s GM-to-L1 load), and a new copy_pipe_to_l1_bind is annotated PIPE_MTE1 (waiting for L1 readiness and binding addresses on the A5 direct path), following the existing precedent of copy_pipe_to_ub and copy_pipe_to_ub_V to avoid fixing A2/A3 while breaking A5. The same root issue also covers the WAR direction: MTE2’s TLOAD may overwrite the same L1 buffer while MTE1 is still reading.

Source: https://github.com/tile-ai/tilelang-ascend/pull/1981

2.4 Ascend Under Review: First Parallel-Axis Broadcast via Scalar Read, Chunk O Forward Migration, MHA Example (#1979 / #1866 / #1879)

All three were updated in a burst on the afternoon of 11-03, forming a milestone batch for Ascend operators. #1979 corresponds to #1885: the failing family reduces to one pattern — a 1D UB operand indexed by the first T.Parallel axis (or an outer serial variable) appears on the left side of a binary expression, exactly the shape of the issue’s reproducer dk_i = sum_j v[j] * A[j, i]; all 5 FAILs in the 21-point bisection matrix belong to this family, independent of reduction direction or broadcast form. The root cause is that when AscendLowerParallelToVector lowers a 2D parallel nest into a row loop, the entry HandleSimpleCase only performs scalar-access detection on the right operand, so the left side takes the vector path and hits the UB alignment trap; this PR makes the first-axis broadcast operand take the scalar read as well. #1866 migrates Chunk O forward (chunk-based gated linear attention O forward, GDN) to the Ascend NPU, using developer mode with four pass configurations (automatic C/V merge, automatic C/V sync, auto-sync, memory planning), a single @tilelang.jit kernel with a fixed 20-core grid-stride loop, achieving on-chip fusion, zero GM workspace, and zero host ATen operators. #1879 adds an MHA forward example: BSHD layout, Expert-mode three-dispatch MMA pipeline, split into 5 Python files across wrapper, shared layer, and three-form modules, with the wrapper containing no T.* code and doing only metadata validation and JIT dispatch; is_causal uses a bottom-right-aligned mask, and fully masked rows are protected by sumexp + 1e-30 to output 0; all 20 cann-bench cases pass accuracy, with an average speedup of 0.97x versus the torch-npu baseline and a composite score of 73.13 (measured locally on 910B2). 0.97x means no net gain yet, but as an example it provides the skeleton for “how to write a complete attention operator on Ascend.”

3.3 TileOPs: Variance merge starts from the first partial, no more NaN for constant inputs (#2821)

Merged 11-03 18:04, +43 / -4 lines, 3 files. The defect was that variance merging started from an empty accumulator: merging a large finite mean into an empty accumulator overflowed the squared difference before it was multiplied by zero weight, so the variance of constant inputs became NaN; affected were var, std, and var_mean calls with a reduction on each side of the retained axis. The fix initializes the merge from the first real partial, with subsequent partials following the existing Chan recurrence; row reduction, dispatch, output layout, and the public API are unchanged. This kind of “empty accumulator + large offset” numerical trap is not rare in the reduction family; what’s worth noting is that it only surfaces on shapes that reduce on both sides of the retained axis—ordinary whole-axis reductions won’t catch it.

V. Trend Observations

First, performance regressions are beginning to be treated as first-class citizens, and the methodology of the fix is more noteworthy than the conclusion. The ID retention rule introduced by #3643 to fix correctness is itself necessary and correct; #3761 did not revert it, but instead allowed retention and reuse to coexist at different levels—before sharing an ID across scopes, first prove that the participating predicate always holds; if it cannot be proven, fall back to scoped counting. Together with the author’s isolation experiment that “only changes the declared barrier resource count,” this fix chain separates two things—”correctness” and “resource declaration”: the latter is a variable that can be reproduced and validated independently. This ability to separate concerns is precisely the mark of a compiler project moving from “it runs” to “it is maintainable.”

Second, Ascend’s engineering is advancing on two legs simultaneously. One is architecture: #1975 moves the entire TileLang-Ascend into the mainline multi-backend framework with 2,887 files and 600,000 added lines, using identifiers such as arch="dav-2201" for backend dispatch, with the goal of letting A2A3 and A5 coexist orthogonally in the same repository; the other is pipeline: mlir-ascend’s #208 writes Codex’s three workflows—initialization, onboarding, and recovery—along with task handoff into .workspace/, and the main repo and the Ascend repo each have their own Agent directory. Looking at “migrating the repo” and “using an agent to migrate the repo” on the same day reveals that the bottleneck on the Ascend side has shifted from “missing operators” to “missing a consistent engineering skeleton and a reusable migration process.”

Third, the culture of self-justification in operator libraries is deepening. Nearly all of the TileOPs PRs under review this issue write the “evidence” into the PR: the EP8 group size of Qwen3-30B-A3B measured on a real route (taking layer 44, the median-skew layer among the 48 layers), the TIR of 35 mask constructions matching the mainline byte for byte, the L2 flush change accompanied by a comparison table of the 46-line implementation and an explanation that the old flush left 120 MB of dirty lines, and the W4A16 cost model explicitly stating “which terms were removed because the data cannot pin them down.” TileFoundry takes another path—turning synchronization into a provable analysis, then having lowering verify it in reverse, and directly listing the cases the analysis rejects (TMA and wgmma completion semantics not yet declared, loops with unequal cross-thread boundaries). Together, the two paths point to the same orientation: better to admit “not proven” than to treat “it runs” as “it is correct.”

Fourth, the risk surface is concentrating on installation form. Of the 7 new issues in one day, four came from the same external reporter using the pip package, running WSL, and using a consumer-grade sm_89 card, all with reproducible scripts attached; #3775 is a production combination of “pip package + multiple CUDA contexts + nvrtc backend + CUDA graph capture.” These are not deep compiler defects, yet they determine the experience of a new user’s first attempt. Contrasting with the Ascend repo’s daily test of 3,030 items all green while the semantic deviation of sat=False still relies on manual reports, it is clear that there is still a gap between the shape of test coverage and the shape of real usage.

One final observation: the news side remains blank this issue, with 12 of the 15 candidates being repository discoveries. TileLang’s external visibility is still tied to events such as “DeepSeek and Ascend,” while day-to-day progress happens only in commits. For those tracking this project, this means the main body of the daily report can only be PRs and issues, not coverage—this has been the stable pattern for several consecutive issues.
