Today’s Focus: Main repo version bumped to 0.1.16, tags and PyPI still at 0.1.15

#3887 landed on main at 00:22 Beijing time on 11-25, changing only the VERSION file, from 0.1.15 to 0.1.16. Package metadata and documentation both read the version from this file, so a single change completes all version declarations.

The proposal lists three verification items. Release metadata resolves to 0.1.16 under NO_VERSION_LABEL=ON. The three version-provider tests pass. Both pre-commit run --all-files and bash format.sh pass.

No action has been taken on the release side yet. The latest GitHub tag is still v0.1.15. The latest Release is still v0.1.15 from 2026-09-30. The latest tilelang on PyPI is also 0.1.15.

Therefore this issue does not state “0.1.16 has been released.” The accurate statement is that the version number is in place; tagging, publishing the Release, and pushing to PyPI are still to come.

The previous 0.1.15 was 55 days before this version bump. During that period the main branch accumulated the batch of ROCm fixes, three Z3 patches, and the Ascend wheel tests.

Source: https://github.com/tile-ai/tilelang/pull/3887.

Today’s Focus: Six ROCm merges in one day; FP4 conversion fixed and reduction decision changed to wave-width-based

Of the 12 commits to the main repo that day, 6 carry the ROCm prefix. These changes all target defects in real quantization and reduction paths.

#3665 fixes two HIP template gaps. The first is an incorrect return value from T.cast(x, T.float4_e2m1fn). Code generation writes the conversion as (fp4_e2_t)x, but that type only has explicit fp4_e2_t(uint8_t raw). The float is therefore truncated to an integer and stored as raw bits: 1.0 comes back as 0.5, 2.0 as 1.0, 6.0 as 4.0, and negatives are likewise wrong.

The second is a missing E8M0 type in the HIP template. Both were exposed when running the DeepSeek-V4 QAT quantizer in VeOmni, on gfx942 and gfx950, with UE8M0 scales. In the 0.1.15 wheels these two headers match the main branch and are equally affected.

#3959 changes the criterion for whether a reduction needs a workspace. The old code returned true whenever the reduction thread count exceeded 32. In practice tl::AllReduce only uses a workspace when some step crosses a wave, so a 64-thread reduction on wave64 allocated LDS that was never accessed. The workspace is also a shared-memory access in the IR, so ThreadSync inserted a barrier for every reduction there.

The fix compares against the target wave width; behavior on wave32 targets is unchanged. Barriers are retained on paths that genuinely cross waves.

#3729 lets FP16 and BF16 T.gemm on gfx1200 accept the standard linear shared layout. Previously, calling make_linear_layout on A_shared and B_shared and then computing T.gemm raised Get different layout. The existing WMMA emitter could already fetch data under that mapping; the problem was in the compatibility check.

The approach extends the shared-layout compatibility callback to four parameters: operator, operand buffer, actual layout, and target. The ROCm side then validates reuse per input; the emitter and index mapping are unchanged.

Three more are engineering details. #3954 makes compile_flags and tl.device_compile_flags actually pass through to hipcc. Previously these two parameters only entered the cache key and did not change device code.

#3958 adds occupancy reporting to hip_resource_info. #3956 documents the limitation of T.gemm when the number of rows per wave is very small.

Source: https://github.com/tile-ai/tilelang/pull/3665.

Today’s Focus: Ten Ascend defects filed in one day, all pointing to missing API parameter validation

On 11-24, a single author filed 10 Ascend defects in tilelang, numbered #4490 through #4499. All ten reports share the same test environment. Hardware is a single-die Ascend 950PR with 128 GB of memory. Software is CANN 9.2.1, HDK 26.0.RC1, openEuler 24.03, torch 2.10.0+cpu, and torch_npu 2.10.0.post4.

Six of them are “accepted inputs the backend cannot compile.” #4490’s T.atomic_add accepts int8, uint8, and float8 buffers. #4492’s T.atomic_max and T.atomic_min accept int8 and uint8. #4491’s T.reduce_sum accepts bfloat16 and float8. #4494’s T.simd.vabs and T.simd.vneg accept bf16 and fp8 registers.

#4495’s T.gemm accepts any unit_flag_ctrl; passing -1 or 999999 still compiles silently. #4497’s T.gemm accepts GM-scope operands, and the backend cannot find a compilable path.

Four are closer to crashes or miscompilation. #4496 runs T.fill on a float8_e4m3fn shared buffer, directly causing a core dump in the bisheng compiler. #4498’s T.gemm accepts a K that no TILE_K_SUB divides evenly, then fails an assertion in auto-scheduling. #4499’s scalar T.sqrt and T.rsqrt fail at kernel compile time with a stl_pair.h redeclaration error. #4493’s five atomic interfaces have no lowering implementation on Ascend.

There is also one correctness defect from an independent source. #4484 points out that SimdVF’s reduction lowering maps all non-sum reduction types to max, so T.reduce_min returns the maximum value. This one comes from source review and was not reproduced on device.

The common thread across this batch: types and values that should be rejected at compile time are let through and only fail in the backend. Together with the 6 documentation-vs-implementation inconsistencies from 11-23, these are all interface-contract gaps.

Source: https://github.com/tile-ai/tilelang/issues/4498.

I. Core Project Progress

1.1 Z3 low-bit masks switched to integer modulo encoding; main repo follows the bump and reverts the solver limit on TopK tests

The TVM submodule tilelang_main branch merged #98 today, and the main repo’s #4482 followed the bump at 14:03. All three fixes trace back to specific defects in Z3Prover.

First, constant signed right shifts such as (n + 4095) >> 12 previously went through the bit-vector path via three steps: int2bv, bvashr, bv2int. When such a shift appears in a loop bound, subsequent pure-integer queries in the same scope carry both Int and BitVec constraints, often exhausting the default resource budget in tirx.Simplify.

Second, VisitShiftOp in CanProve added the assertions b >= 0 and b < 64 directly to the shared solver. This pollutes subsequent queries and conflicts with outer scopes. Meanwhile, DivNode and ModNode used Z3’s Euclidean / and %, so truncmod(a, 4) >= 0 could be proven even for negative dividends.

Third, masks like tx & 31 still went through bit-vectors in index-expression simplification. #98 translates x & (2^k - 1) into x mod 2^k. The proposal records a concrete cost: in one device function the simplifier asked 156 similar queries, taking 11.7 seconds, with the counterexample being tx = 4.

On the test side, stop the bleeding first, then revert. #4463 at 09:51 limited arith.z3_rlimit to 100 in two ROCm test files, because four DeepSeek and GLM TopK cases each took 494 to 605 seconds.

#4489 at 20:40 reverted that limit, citing that #4482 makes constant signed right shifts cheap. The comparison used the same build b4c67597, TVM de131ae4, Z3 4.15.4, taking the median of three cold runs.

Source: https://github.com/tile-ai/tilelang/pull/4482.

1.2 Dist pipeline adds Ascend wheel tests; that half had never run on real hardware

#4419 landed on main at 22:59. The proposal states the premise: the Linux wheel is a combined CUDA, ROCm, Ascend build, but test-wheels-gpu only runs the first two halves. The Ascend half had never executed on a real NPU before wheel release.

A new test-wheels-ascend job runs on a self-hosted Ascend runner, with environment setup shared with the Ascend job in ci.yml. The current image is cann9.3.0-weekly.20261112-ubuntu22.04-py3.13. The registry also has cann9.2.0, 9.2.1 and py3.10 to py3.12 variants, so the matrix can be extended.

The job first fetches the built Linux x86_64 wheel and installs it into a --system-site-packages virtual environment. The container’s torch and torch_npu are pre-pinned.

It then moves the source package aside to ensure import tilelang hits the wheel rather than the source tree. The wheel is an abi3 build with wheel.py-api = "cp39", so a single artifact installs on any Python version.

Source: https://github.com/tile-ai/tilelang/pull/4419.

1.3 vote and sync builtins preserve 64-bit predicates; 1 << 32 no longer judged false

#3777 landed on main at 09:53. CUDA’s vote and block-sync builtins only accept 32-bit int predicates, e.g. __any_sync, __syncthreads_count.

Passing int64 or uint64 implicitly narrows the value. Non-zero predicates whose low 32 bits are 0 were therefore judged false, with 1 << 32 the most direct example.

Seven interfaces were affected. The vote group is T.any_sync, T.all_sync, T.ballot, T.ballot_sync. The sync group is T.syncthreads_count, T.syncthreads_and, T.syncthreads_or.

The fix normalizes predicates wider than 32 bits into an explicit != 0 first, then passes a boolean to the builtin. A runtime regression for 1 << 32 was added, and the entire warp vote test file passes.

Source: https://github.com/tile-ai/tilelang/pull/3777.

II. Multi-Backend Adaptation (Ascend / Hygon / Moore Threads / MetaX)

2.1 Two Ascend sub-repo commits land in mainline: DMA row folding and install script hardening

The default branch of tilelang-ascend is ascendc_pto, not main; per-repo scripts that fetch by main will get empty results. Two commits landed on this branch within the window.

#1805 fixes multi-dimensional copies in Ascend copy. For GM and UB regions exceeding two dimensions, leading dimensions are folded into the DMA row count, originating from #1231. #1946 hardens install_ascend.sh: it aborts directly when the shmem build fails, and the path in set_env.sh is now resolved from the script’s own directory, originating from #1728.

Several items in the sub-repo’s in-review PRs and newly opened issues within the window are also worth noting. #2025 fixes Ascend UB column storage and DMA sizes. #2035 reports that with threads=2, AscendVidReduction generates incorrect broadcast and dim=0 reduction results. The daily test in #2034 records that on 11-24, 3120 items ran and 3120 passed.

Source: https://github.com/tile-ai/tilelang-ascend/pull/1805.

2.2 MLIR Ascend merges tl.wait_flag and tl.vbitcast on the dialect branch

Both merges landed on the mlir-dialect branch; no new commits on master within the window. This branch is the evolution line for the TLIR dialect.

#248 adds tl.wait_flag. Together with the previous day’s tl.set_flag, it forms a complete producer-consumer synchronization primitive. The syntax is tl.wait_flag[#tl.pipe<...>, #tl.pipe<...>, %event_id] : i64. It reuses the #tl.pipe attribute introduced by set_flag and adds no new attributes or types. The TIR-to-TLIR lowering reuses the same PipeFromString and GetEventID.

#249 adds tl.vbitcast, spanning the TIR, TLIR, and HIVM stages, with the verifier checking shape consistency and equal element bit widths. This commit also fixes a real defect. CodeGenTileLangTLIR’s VisitStmt_(LetStmtNode*) previously ignored op->value entirely, so any let-bound call result was silently dropped. The handle return of tl.npuir_bitcast depends precisely on this path.

The in-review #250 lowers tl.ln to hivm.hir.vln. The proposal also notes that the non-TLIR path’s BitcastCodegen has a similar historical gap.

Source: https://github.com/tile-ai/tilelang-mlir-ascend/pull/249.

III. Ecosystem and Adopters (TileOPs Operator Library / FlashQLA / topa)

3.1 Sixteen TileOPs merges, the main thread still bypassing 0.1.15’s bounds-check overhead

Across the sixteen titles, the same sentence recurs in different phrasings: removing the bounds checks that a certain generic path brings on 0.1.15.

#3161 makes the FP8 indexer’s warp-specialized kernel bypass 0.1.15’s bounds checks. #3151 makes Mamba’s CausalConv1dFwdOp keep a wave’s prefill grid resident on 0.1.15. #3142 makes MoE’s FP8 grouped GEMM keep only one branch per task and spread the mask shards across all SMs.

#3146 goes the other direction. It moves Tensor out-of-bounds clamping to within the input dtype instead of promoting to a wider integer before clamping.

This thread began with #3133 on 11-23, “recover the 25-line regression.” Over two days, the recovery effort shifted from “compare against 0.1.12” to “bypass checkpoint by checkpoint.”

Source: https://github.com/tile-ai/TileOPs/pull/3161.

3.2 Sampling, convolution, and reduction each get one structural change

Two on the sampling side. #3157 bins the split top-p rows using global atomics. #3158 switches the binning sum for the same row to fixed-point summation, making the mask reproducible.

One each for convolution and indexing. #3148 splits the symmetric Conv2d contraction onto idle SMs. #3156 makes the two-input concat take four vectors per thread just past one wave.

Two on reduction. #3152 completes the leading axis in a single launch, split across thread-block clusters. #3154 folds in-block any and all with a single barrier or a single OR.

Three on linear attention. #3160 adds over-one-chunk preprocessing for SM90’s KDA fp16 given-gate prefill on the chunk-parallel path. #3159 binds the GDN partition pass’s transfer flag as a value so 0.1.15 doesn’t drop it. #3144 makes KDA’s key-major state decode in memory order and carries packed sequences along with it.

Source: https://github.com/tile-ai/TileOPs/pull/3158.

3.3 Nightly tests now report per-model batch-1 prefill and decode throughput

#3153 makes the nightly pipeline report per-model batch-1 prefill and decode tokens per second on a single card. Previously the nightly run reported only pass/fail and elapsed time, not throughput.

#3155 was opened the same day, requiring CUDA graph replay of each model’s decode step. This treats the measurement method itself as a work item, complementing #3153’s metric definitions.

#3150 belongs to the Mamba thread, routing CausalConv1dUpdateFwdOp’s decode state rows through shared memory.

Source: https://github.com/tile-ai/TileOPs/pull/3153.

V. Trend Observations

  • The release cadence is on the eve of a release. 0.1.15 shipped on 9-30, and 55 days later the version number has advanced to 0.1.16. This release’s accumulation is mainly ROCm fixes, three Z3 patches, and release-chain engineering rather than new features.

  • Performance-regression governance has settled into a fixed playbook. First add a limit to stop the bleeding, then fix the root cause, and finally withdraw the limit and re-test. #4463, #4482, and #4489 all completed within a day, with a TVM submodule update in between.

  • Ascend’s weak spot has shifted from operator coverage to interface contracts. None of the ten defects in a day calls for a new operator; all are “inputs that shouldn’t be accepted being accepted.” These are cheap to fix but steadily erode user trust.

  • TileOPs’ optimization framing is still chasing framework versions. The extra overhead from 0.1.15’s generic path requires downstream to bypass it operator by operator. At least five PRs in two days carry this in their titles, indicating there is still no automated reconciliation between version upgrades and operator-library performance.

  • The RISC-V side has been unchanged for two consecutive windows. Both the TVM route and the MLIR route are stalled in place; this window saw no activity even on the index page.
