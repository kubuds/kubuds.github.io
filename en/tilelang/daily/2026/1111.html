I. Core Project Progress

1.1 Mainline: CUDA adds L2 prefetch instructions and six eviction priority levels; non-default priorities require SM80+ (#3490)

#3490 (6 files, +185/−1) fills in three previously missing prefetch builtins: L1 prefetch, uniform L1 prefetch, and L2 prefetch, while making “eviction priority” a first-class parameter EvictPriority, with six levels: default, evict normal, evict first, evict last, no change, and no allocate. The global load template is reworked accordingly: the previously hardcoded fixed-width load wrappers are replaced with a templated API that can specify non-coherent loads, L1 eviction priority, and the byte count for L2 prefetch.

The behavioral boundaries are clearly specified: default-priority L2 prefetch uses ordinary global or local instructions, while the remaining priorities map to evict_normal and evict_last and require compute capability 8.0 or above; on devices below that threshold these combinations are invalid. For kernel authors, the significance is that previously, to get behavior like prefetch.global.L2::evict_last, you had to write inline assembly yourself; now you can declare it in TileLang source and the compiler selects the path based on the target architecture.

Source: https://github.com/tile-ai/tilelang/pull/3490

1.2 Mainline: Symmetric clamp with NaN propagation lowered to a single min.NaN.xorsign.abs (#3605)

#3605 (7 files, +203/−1) adds T.clamp_symmetric(x, limit), which on CUDA SM86 and above clamps FP16, BF16, and FP32 operands uniformly to [-limit, limit], preserving signed zero and subnormals; if any operand is NaN, it returns a canonical NaN, without preserving the original NaN’s sign or payload. Non-positive numeric limits are outside the API contract, and the existing T.clamp is unaffected.

In implementation it lowers directly to min.NaN.xorsign.abs.*, one clamp instruction per scalar or per pair of FP16/BF16, with vector inputs going through the existing vectorizable operator registration and CUDA packed emission paths, introducing no runtime checks. The validation criteria are strict: both the language and codegen test suites pass 86 with 2 skipped; SASS inspection under CUDA 13.1 for SM86 and SM100 confirms that FMNMX.NAN.XORSIGN, HMNMX2.NAN.XORSIGN, and HMNMX2.BF16_V2.NAN.XORSIGN all appear as expected in both scalar and packed forms. The value of this kind of change lies in numerical stability: in quantized inference, losing NaN during clamping is a common source of silent errors; once the semantics are delegated to a single hardware instruction, NaN is no longer quietly turned into a boundary value.

Source: https://github.com/tile-ai/tilelang/pull/3605

1.3 Mainline: CI no longer restarts the full pipeline on PR label changes; ROCm watchdog raised above the workflow timeout (#3911)

#3911 (1 file, +2/−2) only changes trigger conditions, but the problem description is worth recording. The main CI previously triggered on both labeled and unlabeled events, and CodeRabbit applies multiple labels to a new PR at once, so the same PR produced multiple identical full CI runs within seconds; the shared concurrency group then canceled these runs one by one, keeping only the last.

The evidence is in #3908: four labels landed with the same timestamp, producing four CI runs, with the original run and the first three replacements all canceled, while no CI job reads PR labels, so these restarts provided no coverage. The fix removes these two event types from the triggers, keeping opened, synchronize, reopened, ready_for_review, and manual triggers, with the concurrency policy continuing to handle cancellation of stale head updates. The same change also raises the ROCm runner’s watchdog threshold above the workflow timeout, so AMD jobs are no longer forcibly killed at 40 minutes.

Source: https://github.com/tile-ai/tilelang/pull/3911

2.1 Ascend: host-mapped buffer parameters under review, 14 files with 529 new lines (#3909)

#3909 extends the explicit host-mapped buffer contract established on the CUDA side in #3802 to Ascend: previously Ascend kernels uniformly rejected CPU tensor arguments, even when their storage was visible on the NPU, and callers could only work around this by disabling tensor validation. This belongs to the same line as #3892 (torch.compile support), #3893 (direct dequantization of L0C accumulators), and #3891 (L2 flush API), all under review in the previous window: what Ascend is currently filling in is interface and semantic consistency, not an operator list.

2.5 Metal: SIMD-group destination out-of-bounds write reproduced on M4, fix premised on provable footprint (11-10)

#3907 reports a silent out-of-bounds write: when copying an explicit 8x8 metal.simdgroup matrix to an 8x1 output, the compiler emits a full simdgroup_store with a row stride of 1; the logical output is correct, but it overwrites the seven elements after the output. The reproduction environment is documented in full—Apple M4, tvm_ffi, compilation cache disabled, and extra backing storage used as a sentinel to detect the out-of-bounds write. The upstream baseline is 72d986e1.

The fix PR #3912 (2 files, +116/−1) does not add a runtime check; instead, before emitting each SIMD-group store, it requires the arithmetic analyzer to prove that the full 8x8 footprint falls both within the destination buffer and within the requested destination region; if it cannot be proven, a readable ValueError is raised during lowering, while full tiles whose last element lands exactly on the boundary are still supported. In the same window, #3906 ([Metal] Resolve the auto execution backend to tvm_ffi) is also under review, part of the same backend’s execution-path convergence. This is the third time Metal has appeared in this window this month, shifting from adding operators to fixing correctness boundaries—usually a sign that people have started running non-toy shapes on Apple chips for real.

2.8 New Observation: TileLang–Weft CPU/RVV Line Sees 40 Commits in One Day, All 553 Benchmark Cases Pass Numerical Checks (11-10)

Beyond the four sources, a more active RISC-V line has emerged, and this issue marks the first time it has enough factual substance to report. Tianchen-ai/tilelang-weft is a fork of upstream tilelang v0.1.15 that adds the Weft CPU programming model: on top of the native TileLang AST it introduces five categories of author information—Encoding fields and bit layers, logical axes and tile domains, Levels and staged snapshots, grouped partials with finite bit widths and explicit conversions, and per-loop pipeline depth—then uses a shared set of physical passes to cover both RISC-V and x86 simultaneously, so that the same source construct enters either the RVV/IME or the x86 SIMD/AMX lowering path. Within the window the repo saw 17 commits, and the benchmark repo tilelang-weft-bench added another 23, concentrated on packed-row decoding (Q1/Q2/Q4_K/Q6_K/IQ3/IQ4), IME1/IME2 record-level contraction, runtime K-dimension reduction, and dynamic rotary traversal.

The benchmark results are worth quoting verbatim: 150 operator IDs form 553 platform cases (SG2044 133, K1 137, K3 A100 136, x86 147), of which 543 have a comparable external reference implementation. Numerical checks pass 553/553, but only 41 cases are “faster than the reference implementation”; the median native speedup is 0.0580× on SG2044, 0.1143× on K1, and 0.1074× on K3 A100, with the x86 side not listed in that table. The value of this data line is not in the scores but in the fact that it quantifies, for the first time at single-operator granularity, “how far TileLang-written RISC-V CPU operators are from hand-written native libraries”—and it is fully reproducible (the benchmark repo ships its own constraint files and CSV export).

Two technical routes must be distinguished: Weft follows a CPU route that imports the native TileLang AST early into its own Canonical IR, which is not the same implementation as the TVM backend continued by the kubuds- prefixed branches or the MLIR Linalg/SCF rewrite of RuyiAI-Stack/tilelang-riscv; the three must not be conflated.

III. Ecosystem and Adopters

3.1 TileOPs: W4A8 calls at 33 to 40 tokens rerouted to the 40-token decode tile, 4.3% to 11.3% faster on out-of-band grids (#2888)

#2888 (2 files, +69/−47) fixes a misalignment in a rule-based decision. On an H200 with 132 SMs, once the number of 128-row tiles for a W4A8 call at 33 to 40 tokens exceeds the SM count, the call falls into the “133 to 225 tiles, K = 7168 / 7680 / 8192” band and keeps going down the prefill path, when such calls should actually use the 40-token decode tile.

The root cause is that after one wave, the completion order of the two paths inverts: the prefill kernel splits tiles with stream-K, while the decode kernel’s consecutive terms that run earlier finish first. The original band covered only part of the grid and also wrongly admitted a set of evenly divisible grids—on those grids prefill actually finishes first. The fix narrows the band to keep only the four cases that genuinely belong to prefill (N not a multiple of 128, K not a multiple of 512, the 512−K term divisible on the SM, 64-row weight blocks a power of two and at least 512 KiB apart). On out-of-band grids it is 4.3% to 11.3% faster than main.

The same PR also adds a previously uncovered test: the decode kernel’s cross-CTA ready flag missing a reset. The Result line is marked below bar, i.e. it does not meet that item’s performance target bar, but what is corrected is the decision rule itself—”wrong path changed to right path” rather than “tuning for score.”

Source: https://github.com/tile-ai/TileOPs/pull/2888

3.2 TileOPs: DeltaNet forward dispatches by device shared-memory budget, SM89 regains the chunk 128 path (#2891)

#2891 (2 files, +78/−27) picks up the pit left by #2645: that change sent all calls with dim_k less than twice the chunk length into state walk, and walk’s output pass at chunk 128, dim_v 64 needs at least 114688 bytes of shared memory (131072 at dim_v 128), while SM89 only provides 101376, so those calls are simply unavailable on SM89; the recurrence retained in the kernel needs only 98560 bytes.

The fix makes the kernel take walk only when walk’s lower bound actually fits, otherwise recurrence, and the refusal path reads the smaller of the two bounds. Calls already served on main keep their existing programs across the SM80, SM89, and SM90 budgets.

Performance is recorded honestly: on SM89 main rejects these calls, so the baseline can only be FLA’s chunk_delta_rule forward (whose own chunk is 64); at chunk 128, dim_k 128 this change is 9% to 41% slower than FLA (TileOPs/FLA ratios across six cases: 1.41, 1.21, 1.28, 1.09, 1.28, 1.09); on SM90 main already serves them, and against main the three cases all have a ratio of 1.00, no regression. On the test side, test_deltanet_fwd_serves_chunk_128_in_sm89_shared_memory is added, checking the dispatch decision against SM89’s device facts, so it also runs on SM90 CI.

Source: https://github.com/tile-ai/TileOPs/pull/2891

3.3 TileOPs: backward w/u program reuses buffers, 114944 bytes squeezed to 98560 bytes (#2890)

#2890 (3 files, +155/−20) is the other half paired with the previous item. Since #2625, the backward w/u program must assemble du, dk_corr, and dw on the fly from the walked-out dh, and TileLang 0.1.12 places dh and S, v_new and du in separate buffers despite their lifetimes not overlapping, so the program occupies 114944 bytes, exceeding SM89’s 101376.

The fix adds a reuse switch to compute_w_u_bwd_tl, enabled only under equal head dims: S, du, and Aw take over the buffers of dh, v_new, and Au after their respective last reads, bringing the program down to 98560 bytes; the kernel sets it only when “the bound without the switch exceeds device shared memory,” and refusal likewise reads the bound with reuse. Two other spots are fixed along the way: walk now picks value tiles only among widths that “fit in a single stage” (previously on a batch 8, 16 head, head dim 128/128 16-bit case it picked a tile needing 131072 bytes, failing at launch on SM89); and _parallel_live_bytes now accounts for the c×c attention tile each chunk’s gradient program still holds while assembling partial du.

This last item cascades into a string of conclusions: with the accounting added, refusal makes SM90 also reject three calls that main lets through but that fail to run (16-bit chunk 64, head dim 256/256 needs 237568 bytes to launch on SM90), and identifies that 16-bit chunk 128, head dim 32/256 and float32 chunk 64, 32/256 fail to launch on main, while 16-bit chunk 128, 16/256 does not even compile. Backward benchmark (bf16, batch 4, 4096 tokens, 8 heads, chunk 64, head dim 128/128): 1.530 ms vs. FLA 1.554 ms, ratio 0.98.

Source: https://github.com/tile-ai/TileOPs/pull/2890

3.4 TileOPs: tests dispatch by cluster and shared-memory facts, SM89 failures drop from 9 to 3 (#2889)

#2889 (3 files, +26/−2) is the test-side companion to these two fixes. The LayerNorm fused-add case asserting “rows still normalized per row when far from zero” has a split branch that builds FusedAddLayerNormHeldKernel, and that kernel holds these rows only when the cluster can split each 12288-wide float32 row; only SM90 has clusters. On SM89 the held kernel’s rules send such rows to the fragment kernel, so the four cases added by #2811 and #2846 still fail after the numerical check passes. The fix calls check_held_launch first and skips the split cases on devices without clusters; the five 8192-wide split cases are likewise skipped on SM89.

It also explicitly marks two cases that only fit on SM90 as sm90: the bf16 GLA backward added by #2637 (chunk 128, head dim 64/64) and the float32 DeltaNet forward added by #2645 (chunk 128, 64/128), each needing 196608 bytes of shared memory. Regression data: on a single SM89, the four test files go from 40 passed, 9 failed, 3 skipped to 35 passed, 3 failed, 14 skipped; the remaining three are chunk 32 GLA backward, which need a kernel change to pass. On a single SM90 all 46 items pass in both versions, showing the skip markers did not take away SM90 coverage.

Source: https://github.com/tile-ai/TileOPs/pull/2889

3.5 TileOPs: paged GQA split count bounded by in-window key tiles, under review (#2892)

#2892 (2 files, +28/−11) is under review and changes the upper bound of GQAPagedFwdKernel._splits_for. Previously the split count was computed to cover the SM count before the window narrowed the key range, so a three-tile window would open 16 splits at batch 1; without RoPE it would keep growing toward “resident,” doubling the cost on the combine side—combine must read each split’s partial per row tile on a single CTA.

The new rule first caps the cp.async split count at the number of in-window key tiles; without RoPE, beyond the SM-covering count the upper bound is isqrt(key_tiles * block_N / block_M), the point where combine’s partial row count is comparable to one chunk’s key row count. The PR comments include the calibration data requested by #2496, covering regret statistics over 379 configurations. #2893, newly opened in the same window, is the follow-up list for this family and remains open.

Source: https://github.com/tile-ai/TileOPs/pull/2892 , https://github.com/tile-ai/TileOPs/issues/2893

3.6 TileFoundry: six analyzer and spec-gap issues in one day, two filed cross-repo by a TileOPs author (11-10)

TileFoundry opened 6 new issues in the window, from two sources.

The first group is a direct product of the source-spec reorganization in #312; zhen8838 opened four in a single minute at 02:42, all marked “found by reading code, not reproduced with a program”: #314’s JIT cache key prints only the entry function and topology, with callees appearing only by name, so two Modules with identical entry text but different callees get the same cache key; #315 defaults to the first valid topology when the caller gives no topology_level, instead of asking the target which levels declare max_physical_units; #316 in loops with depth less than 4 advances the cursor by one loop-body duration rather than the whole loop span, so work after the loop does not wait for the loop to finish; #317’s passes.md §7.1 states that on-chip memory callee return values must be copied into the caller’s buffer, otherwise it must fail with LoweringError, but convert_hir_to_tir has no corresponding rejection.

The second group was filed by TileOPs author lcy-seso at 12:04 and 12:29, both pressing the analyzer with real operators: #318 uses an elementwise clamp on H200 for placement pricing, pointing out that once the CTA grid exceeds one wave, the split input’s footprint is multiplied by the wave count, and noting the same behavior was reported in #298, #303, #307, #311, all closed as not planned, and still reproduces on the current build; #319 schedules a 4096×7168×16384 resident SM90 NT GEMM and yields five findings at once, the hardest being that check --help says bf16 has 8 explicit mantissa bits with a rounding bound of 2^-9, whereas bf16 actually has 7 explicit mantissa bits and unit roundoff 2^-8, so the rtol derived from it is only half what it should be.

The shape of this issue group is worth noting: the analyzer’s mispricing is exposed not by unit tests but by putting real operators on it, and the filer comes from the operator-library side.

3.7 Third party: Hexagon NPU backend grows from a shell into a branch that runs on-device models, LFM2-1.2B runs end-to-end on the NPU (11-10)

In the 11-09 window, xwhzz/tilelang-hexagon was still “README unchanged from TileLang, no verifiable backend changes”; after the 22:07 push in this window the content is filled in. The fork adds a TileLang backend for Qualcomm’s Hexagon NPU, developed and validated on the v79 cDSP of a Snapdragon 8 Elite phone: tile ops such as T.copy, T.gemm, T.Parallel, T.reduce_*, T.Pipelined compile to HVX vector code, HMX matrix multiply, VTCM buffers, and DMA streams, executed on the NPU via FastRPC.

The validation target is LFM2-1.2B: batch 1 runs end-to-end, with prefill, decode, and sampling all written in TileLang and running on the NPU; projection layers are 4-bit (GPTQ, one fp16 scale per 64 columns), tied embedding and head are 8-bit, on-device WikiText-2 perplexity is 16.68 vs. a bf16 reference of 16.29. The significance for TileLang’s boundary is clear: previous “non-NVIDIA, non-Ascend” backends were mostly CPUs or domestic accelerator cards, and Hexagon is the first branch to put a complete decode loop on a phone DSP, and it gives an accuracy comparison rather than throughput alone.

Source: https://github.com/xwhzz/tilelang-hexagon

4.2 Adjacent developments: Meta publishes TLX blog post; Triton’s low-level extensions already run on three production workloads (11-10)

On the same day, the Meta engineering blog published “How We Built TLX: A Hardware-Native GPU Compiler for Production ML at Scale,” covering Triton Low-Level Extensions: adding explicit warp-group and cluster-level orchestration on top of Triton’s block-based programming model, letting developers use execution-side hardware capabilities such as warp specialization, asynchronous transfers, and tensor memory without giving up Triton’s development speed. The post lists three destinations already running in production—recommendation system training, recommendation system inference, and large-scale LLM pretraining—and provides a chart of kernel count growth inside Meta over 10 months: Triton kernel count grew about 3.8x, CUDA about 2.0x.

It belongs in the TileLang daily because it marks another solution on the same track: TileLang adds automatic scheduling and multiple backends upward from a tile-level DSL, while TLX adds explicit orchestration downward from Triton. The two give opposite answers to “who writes kernels”—TLX lets ML engineers keep using Triton and drop down locally, while TileLang has authors explicitly describe tiles and pipelines and hand them to the compiler. By comparison, what TileLang has added this year is mostly backends and operator correctness; the orchestration-layer abstraction still rests on the T.Pipelined and T.annotate_* interface set.

Sources: https://engineering.fb.com/2026/11/10/open-source/tlx-a-hardware-native-gpu-compiler-for-production-ml , https://arxiv.org/abs/2605.10905

V. Trend Observations

First, the main repo’s output focus is shifting from operators to primitives. #3490’s prefetch and eviction priorities, #3605’s NaN clamping, the under-review #3897 CPU scan operator, and #3903’s process-parallel compilation share a common trait: “give authors a new tool” rather than “make some operator a few points faster.” The acceptance criteria for such changes differ too: #3605 uses the presence or absence of three instructions in SASS as evidence, and #3490 uses a compute-capability threshold as its boundary—both can be rechecked independently of specific shapes. For downstream users, this means more usable patterns after 0.1.16, but each new primitive has its own architecture threshold, so cross-generation ports must be checked one by one.

Second, the shared-memory budget has become an explicit constraint on the linear-attention line. SM89’s 101376 bytes and the demand-side figures of 114688, 131072, and 196608 determine how large the chunk is, whether to use walk or recurrence, and on which architecture tests run. The solutions in #2890 and #2891 follow the same idea: rather than forcing down demand, let dispatch choose a path based on device facts and use the same bound in refusal—preferring to refuse early over crashing at launch. Once this pattern runs smoothly on DeltaNet, the GLA family will most likely copy it—the three chunk-32 failures left by #2889 are exactly the next block.

Third, the testing approach is shifting from “cross by architecture” to “judge by device facts.” #2889 did not delete or permanently skip the SM89 cases; instead it first checks check_held_launch and then decides to skip. The two new tests in #2891 and #2890 also branch decisions based on SM89 device facts, so they still run on SM90 CI. This approach is more robust than skipif markers based on device compute capability, because it verifies the decision logic itself rather than the hardware.

Fourth, TileFoundry’s mispricing problem keeps being pushed back by the operator side. #318 states outright that the same behavior was reported in four closed issues, all marked not planned; #319 gives five at once with a specific 962.1 vs. 1213.6 GFLOP deviation. The analyzer is the premise of TileLang’s “price first, then choose scheduling” route; a 26% pricing deviation will make automatic selection decide wrongly. Such gaps won’t slow any single operator, but they will make automation systematically choose wrong on boundary grids.

Fifth, divergence on the RISC-V side is widening rather than converging. The four sources (TVM route, MLIR route, SOPHGO TPU, community index) are uniformly stalled, while the third-party Weft line does 40 entries a day and has already quantified the gap down to individual operators (SG2044 median 0.0580x). Taken together, the two facts show that the stagnation is not for lack of people working on it, but because the official four sources have not formed a loop of “automatically discover gaps, automatically verify, automatically queue”—the Weft line only took off after building its own benchmark engine. If this 553-case benchmark can be cited by the official four sources as an acceptance standard, progress on the RISC-V side will for the first time have a comparable denominator.
