Today’s Highlights

There is only one main thread today: TileLang has ported DeepSeek’s MLA decode kernel to Ascend 950, and it has done so in a way that the compiler can schedule. #3678 adds 1,997 lines, 20 files, and 42 commits in one go, covering both the BF16 prefill and compact FP8 decode paths, and also including optional FP8 and FP4 extra KV caches, attention sink, illegal indices, and per-query independent lengths. The implementation approach is noteworthy: the attention loop, online softmax, dequantization, and scheduling are all written in TileLang, relying on T.Stage to let the compiler manage buffer versions and synchronization; QK and PV use two different layout views of the same L0B storage ring; and L1 placement is specified directly with T.annotate_buffer_addresses; prefill splits four disjoint output slices out of a single accumulator allocation, and drains each slice as soon as its normalization is computed. To make this style of writing work, the compiler side simultaneously adds three capabilities — L0C-to-UB copies preserve NZ output, each AIV stream is selected before its own pipeline, and explicitly scheduled stages keep source order when their physical issue phases are the same. The target shapes are written very narrowly: 64 heads, Dqk and Dv both 512, and topk a multiple of 64.

The second thread is fixing a real compiler regression. #3734 deals with ViT forward on SM100: Cannot convert type float32x16 to CUDA type. The path is long but every step is clear — the vectorization planner chose 16 lanes for a 256-bit BF16 store and deferred the cast constraint, expecting DecoupleTypeCast to split computation and memory access; but #3579 had just excluded “guards for reading memory” from decoupling (duplicating these guards would change semantics), so the final legalization step was still choosing widths according to the deferred strategy, and the residual FP32 expression was stretched into a 512-bit vector, which the CUDA backend cannot express. The fix is to make the deferred constraint a planner parameter rather than an IR attribute; only the final legalization step passes false, the guard’s FP32-to-BF16 conversion drops to 8 lanes, and successfully decoupled BF16 copies still keep 16 lanes; address casts are also removed from the data vector type constraint and their legality is judged by the existing access analysis.

The third thread is the debugging experience. #3703 changes #line directives from “anchoring only the first line of each TIR statement” to optional graded emission: level 0 disables it, 1 keeps the original behavior, and 2 and above re-anchor every non-empty line generated for each line, including statements expanded into multiple lines and closing braces. The implementation is placed in the C-family output stream shared by CUDA, HIP, CPU C, C host, Metal, and Ascend, without touching vendored TVM; statements and functions without source spans are explicitly switched to <tilelang-generated>, and user source text is preserved verbatim to avoid breaking macro continuations and string literals. A new environment variable TILELANG_EMIT_LINE_DIRECTIVES serves as the Python-side default and is folded into the pass configuration before cache lookup. Locally, 42 tests pass and 6 are skipped; the CUDA and HIP cases were skipped on the author’s machine, and the actual behavior of cuda-gdb has not yet been directly verified — the author states this explicitly. On the same day, the LSP repo followed up with one commit aligning CUDA debugging to the new line mapping.

The pace on the operator side has not stopped, but the direction has changed. Of the 7 merges in TileOPs in a single day, 6 are performance and 1 is test infrastructure, all from the same author; each still comes with an H200 measured table and a checklist regression gate. The most valuable is #2816: it adds a tileops_test target that exists only during testing, computes a shared workload reference for each operator on PrivateUse1, and means the smoke tests in tests/ops no longer have to stand on CUDA. The change is 1,281 lines across 59 files, and the author also clearly states the boundary — comparing against a shared reference can only prove backend-independent contracts and portability, not the numerical correctness of a real backend; that line is still tracked in #2611.

Finally, there is a hidden thread in TileFoundry. #283 turns “how shared memory accesses should be ordered” into an analysis layer: a synchronization family walks each function in lowering emission order, and for each shared memory access takes the instruction, issue mesh, operands, and byte range, and plans commit/wait and scope fences before conflicting accesses. Of 83 scheduling fixtures, it plans 52 and rejects 31 (24 use TMA copies and 6 use wgmma, whose completion semantics are not yet declared; 1 requires inserting a fence in a loop with unequal cross-thread boundaries). The companion #285 is under review, turning the plan into CUDA lowering and validating it in reverse: of the 7 programs that can be built on a single sm_89 card, 6 match the reference exactly, and synccheck and memcheck are completely clean, whereas lowering the way main does produces wrong results in 4 of the same 7; the direct symptom given in the #283 description is that the E4M3 GEMM on sm_89 is off by up to 659.

I. Core Project Progress

1.1 Mainline: Persistent FlashMLA kernel for Ascend 950, dual paths of BF16 prefill and compact FP8 decode (#3678)

Merged on 11-02 09:26, adding 1,997 lines and deleting 17 lines, across 20 files and 42 commits — the heaviest item in this window. The kernel targets Ascend 950: prefill runs BF16, decode runs compact FP8, with optional extra KV cache in FP8 and FP4, and support for attention sink, invalid indices, and per-query independent lengths. The attention loop, online softmax, dequantization, and scheduling are all expressed in TileLang, driven by T.Stage together with compiler-managed buffer versions and synchronization; QK and PV share two different layout views of a single L0B storage ring, and L1 placement is specified via T.annotate_buffer_addresses; prefill splits four disjoint output slices within the existing accumulator allocation, each with its own synchronization event, draining each slice as soon as its normalization completes; decode uses a full-row output copy. Three compiler-side supports were added: L0C-to-UB copies preserve NZ output, each AIV stream is selected before its pipeline, and explicit scheduling stages keep source order when flattened at the physical issue phase. The target is 64 heads, Dqk and Dv both 512, and topk a multiple of 64; pair gather reuses the documented zero-burst codegen workaround; the PR ships with correctness and benchmark runners, buffer-reuse and query-boundary regressions, and a README carrying the FlashMLA MIT notice.

Source: https://github.com/tile-ai/tilelang/pull/3678

1.2 Mainline: Residual 512-bit vectors after cast decoupling is skipped, ViT forward fails to compile on SM100 (#3734)

Merged on 11-02 09:05. On e8225d7f5, the SM100-targeted ViT forward reports Cannot convert type float32x16 to CUDA type at the guarded FP32-to-BF16 output store: the planner selects 16 lanes for the 256-bit BF16 store and defers the cast constraint, expecting DecoupleTypeCast to separate compute from memory access; after #3579 made decoupling skip guards that read memory, the subsequent LegalizeVectorizedLoop kept deferring under the same policy, so the residual FP32 expression became a 512-bit vector that the CUDA side cannot represent. The fix makes defer_cast_constraints a C++ parameter of the planner (not an IR attribute), chosen by the caller per phase: LayoutInference and LowerTileOp keep true, final legalization always passes false, and the computed width is forwarded as an explicit vectorize_hint so the rewriter does not re-plan with the default policy. The guarded FP32-to-BF16 drops to 8 lanes, successfully decoupled BF16 copies keep 16 lanes, and the guard safety check is retained; address casts and access-pointer parameters are excluded from data vector type constraints, contiguous addresses are lowered to a scalar base plus stride with legality decided by the existing access analysis, and aligned vector accesses with int64 indices and the four-lane atomic case are unaffected.

Source: https://github.com/tile-ai/tilelang/pull/3734

1.3 Mainline: #line directives re-anchored per line, debugger mapping gains optional dense mode (#3703)

Merged on 11-02 04:06, 682 lines added across 11 files. Previously #line emission anchored only the first line generated by a TIR statement, and subsequent lines were advanced by the compiler’s logical line numbers, so cuda-gdb attributed generated loads, arithmetic, and stores to unrelated Python lines; synthesized statements and closing braces could inherit an advanced mapping, and functions without a source span inherited the previous function’s source file. This PR extends tl.emit_line_directives into levels: 0 or False disables it and keeps the default, 1 or True keeps statement-level, and 2 or above re-anchors every non-empty generated line (including multi-line expanded statements and closing braces). The implementation lives in the C-family output streams, covering CUDA, HIP, CPU C, C host, Metal, and Ascend, without modifying vendored TVM; it also records source spans for statements and functions, explicitly switches source-less regions to <tilelang-generated>, and preserves user text verbatim to avoid breaking macro continuations and string literals. A new TILELANG_EMIT_LINE_DIRECTIVES serves as the Python-side default, folded into the pass config before cache lookup, with explicit config taking precedence (including when the default value is invalid). Verified locally with a Metal plus LLVM build: the line-directive and compile-only groups pass 42 and skip 6; with directives removed, the vectorized-add and conditional-select fixtures produce identical output at levels 0, 1, and 2. The author notes that CUDA and HIP cases were skipped on the local machine and cuda-gdb behavior was not directly tested.

Source: https://github.com/tile-ai/tilelang/pull/3703

1.4 Mainline: Attention examples derive tiles from device shared-memory limits, going from 2 pass / 7 fail to 9 pass on RTX PRO 6000 (#3702)

Merged on 11-02 06:59, 345 lines added across 13 files. The non-tuned paths of several attention examples hard-coded Hopper-sized tiles, which fail immediately on sm_86, sm_89, and sm_120 where the per-block dynamic shared memory limit is about 99 KiB: the error asks for 163840 bytes of allowed dynamic shared memory while device 0 allows at most 101376 bytes per block. Each example now derives its tile from shared_memory_per_block_optin, following the existing GQA decode example (example_gqa_decode.py); datacenter configurations are unchanged because each branch only triggers below the previous tile requirement. Landing points on ~99 KiB devices: the four attention sink examples use 64×64 two-stage with 128 threads (forward) and 64×32 one-stage with 128 threads (backward), example_gqa_bwd.py uses 64×64 forward and 64×32 backward, and example_mla_decode.py takes BLOCK_N 32 and BLOCK_H 16. The latter two gain a threads parameter: with 64-row or 16-row tiles, T.gemm needs four warps so each warp owns a full 16 rows, and 256 threads fail to lower outright (reporting a layout conflict for acc_s and acc_s_cast respectively, and no legal warp partition for M=16 N=32). Verified on RTX PRO 6000 Blackwell (sm_120): CUDA passes all 9 (previously 2 pass / 7 fail), and CuTeDSL also passes all 9; H100 has a 227 KiB opt-in limit, still uses the original tiles, and likewise passes all 9.

3.5 TileOPs: Norm statistics subtract an in-row element, eliminating overflow near 1e36 (#2811)

Merged at 11-02 05:10. The root cause is stated plainly: all mean and variance kernels sum the raw row in fp32, and the sum grows with the row’s offset (roughly N times x ); rows near 1e36 overflow outright and all outputs become NaN. Even without overflow, the mean is rounded at the scale of the offset, and x − mean carries that rounding into every element, so the variance computed for a constant row equals the square of the rounding, normalizing to plus or minus weight instead of bias. The fix adds an invariant to every fp32 quantity formed from a row: it is bounded only by the row’s spread, not by its offset—implemented by taking “some element in the row” as the baseline and subtracting it, using the warp’s first element for warp-dominant kernels and the row’s first element for tiled kernels. This is a direct fix for the same class of problem as the four Norm operator defects listed under #2812 in the previous issue’s report.

Source: https://github.com/tile-ai/TileOPs/pull/2811

3.7 TileFoundry: shared-memory ordering as a provable analysis layer, 52 of 83 fixture plans accepted and 31 rejected (#283)

Merged at 11-02 02:09. The problem is real: finalize does not emit commit, wait, or barrier between shared-memory accesses, so schedules that stage through shared memory race, and on the card sm_89 E4M3 GEMM deviates from torch by up to 659. The direction set by #267 is “an analysis that orders accesses on the HIR” plus “lowering that emits in target order,” emitting only the minimal correct form and rejecting anything it cannot prove; this change delivers the analysis part. The new synchronization family walks each function in lowering’s emission order: for each shared-memory access, it takes the instruction, emission mesh, and operands from analysis/emission.py, the scope from IterationScope, and the byte count from the placement recorded by the memory family; before a conflicting access it plans one commit plus one wait (for outstanding cp.async writes) and one fence covering “the innermost scope holding both,” numbered by the active position of the child node that runs first. Operators declare how their effects complete via the new registry visitor_registry/completion.py, and anything undeclared is treated as UNKNOWN; the family rejects accesses after UNKNOWN, UNKNOWN accesses still in flight on return, fences inserted in loops that do not wait across thread boundaries, and reserved calls whose callee holds shared memory. By default no caller requests this family, so the 75 scheduling fixtures that finalize are byte-identical to main; of the 83 fixtures, 52 are planned and 31 rejected (24 use TMA copies and 6 use wgmma, with completion semantics not yet declared; 1 requires a fence in a loop at a thread-dependent boundary), and corpus cases assert these rejections individually.

Source: https://github.com/tile-ai/TileFoundry/pull/283

4.2 SIMD loads of cross-row and transposed views lose their DMA dependency, with the root cause in logical region reconstruction (#3749)

The most technically substantive issue in this batch, reported with an environment of main branch e8225d7f5, Ascend950PR, and CANN 9.2.0. The problem is that two consecutive SIMD loads lose their dependency on an earlier GM-to-UB copy: first, a row-major load that starts in the middle of a row and crosses into the next row; second, an access to a transposed view where the physically contiguous dimension is not the last logical dimension. The root-cause path is described in detail: the generated tl.access_ptr covers the physical load range, but the logical region reconstructed by MemoryAccessDetector::LogicalPointerRegion misses part of it, so dependency analysis concludes that the input DMA is unrelated to the load, AutoSchedule moves the input copy after the load, and InsertSync also emits no MTE2-to-V set/wait. In the minimal reproduction, work.shape is (2, 128); first T.copy(A, work[1, 0:64]), then inside T.SimdVF() T.simd.vld(work[0, 64]) reads 128 contiguous half-precision elements: the generated read descriptor is tl.access_ptr(work[0, 64], 128, 1), physically covering [64, 192), of which [128, 192) is exactly the part just written by the DMA, while the reconstructed region is work[0:1, 0:128], i.e. physical [0, 128), entirely missing the written interval; the row count is computed as ceil(128/128) = 1 row, and the starting column 64 is not counted. This sits on the same foundation that this window’s main work on FlashMLA and PTO vectorization is shoring up, and when it hits, it silently produces wrong results.

Source: https://github.com/tile-ai/tilelang/issues/3749

V. Trend Observations

The most noteworthy judgment of the day is this: Ascend is no longer an “adaptation target” but a “first-launch target.” FlashMLA, a core kernel on DeepSeek’s own decoding path, is written directly into the mainline targeting Ascend 950, and it uses low-level capabilities prepared for explicit scheduling such as T.Stage and annotate_buffer_addresses, rather than opening a separate repository for porting. Together with the three compiler-side supports (preserving NZ from L0C to UB, selecting the AIV stream before the pipeline, and emitting explicit stages in source order), it is clear that the Ascend path is moving from “it runs” to “it runs according to scheduling intent.”

The second thread is that the center of gravity of correctness is shifting downward. The previous issue reverted a whole set of ThreadSync correctness improvements for the TIRX migration, and this issue immediately produced two follow-ups: mainline #3752 tunes z3 solver resource limits, and #3735 proposes using modular index disjointness to reduce the shapes that need to be proven; meanwhile #3749 digs a defect where “dependency analysis cannot see the physical load range” down to the level of MemoryAccessDetector::LogicalPointerRegion. Putting these together with the hidden thread from TileFoundry—where the analysis layer can prove shared-memory ordering for 52 of 83 fixtures, while doing lowering the main way would make 4 of 7 programs compute incorrectly—the same signal appears three times: the main risk for TileLang now is not insufficient functionality but “the generated code looks right but is actually wrong,” and the team’s chosen approach is to turn correctness into refutable proofs rather than plugging holes one patch at a time.

The third is that testing and contracts are beginning to form an independent layer. TileOPs’ tileops_test decouples smoke tests from CUDA, and compile-contract-gate separates the dispatch contract from workload data generation; both were merged within the same hour, and the author explicitly noted that “a shared reference cannot prove a real backend correct.” This habit of stating separately “what can be tested” and “what has been proven” says more about the project emerging from its prototype phase than merging a few more performance patches.

Finally, note a contrast: on the operator side, 7 performance merges landed in a single day, 6 of them with H200 measured tables, while on the news side all three channels had zero hits in 24 hours. TileLang’s external visibility remains concentrated on events such as “DeepSeek open-sources Ascend components,” and day-to-day progress happens almost entirely inside the repository. For anyone tracking this project, that means the body of the daily report can only be commits and PRs, not coverage.
