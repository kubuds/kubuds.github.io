Today’s Highlights

This window merged 32 PRs (TileOPs 20, tilelang 8, tilelang-ascend 3, TileOPs docs site 1), plus one official release: TileFoundry tagged 0.0.3 on 10-21 at 10:26. The three lines have different centers of gravity. The eight merges in the main repo are almost entirely cleanup of defects that “don’t error but produce untrustworthy results”—batched reduction handling only the first output block, cast rounding annotations being silently dropped, CUDA targets without arch silently falling back to sm_50, pipelining losing transitive dependencies; TileOPs took MLA prefill backward from the op layer to an SM90 warp-specialized kernel in one day, while advancing four small-scale paths on SM89—FP8 BMM, W4A16, paged DSA, and NSA top-k—bringing the review queue down from 16 to 9; on the Ascend side, the DeepGEMM heuristic and epilogue alignment (#3577) that was still under review yesterday merged today, and the Ascend repo fixed a memory access modeling defect that caused corrupted keepdim reduce output (#1795). I. Core Project Progress

1.1 Main repo: batched finalize_reducer previously reduced only the first output block (#3070)

Merged 10-22 01:16, 2 files +29/-5, fixes #2623. The lowering of the batched finalize_reducer called run_batch only once at the start of the buffer; the remaining consecutive output blocks were never reduced at all: when the output dimension exceeds the batch size, later segments received not the reduction result but uninitialized or stale values from the previous round. The fix emits a batched all-reduce with the correct offset block by block according to ceil(OutputDim / batch)—128 outputs with batch=4 emits 32 calls—while also switching the remapped reducer buffer to a flat view, addressing each batch with a constant linear offset, removing the previous shape and stride reconstruction, and retaining all chunk calls. Verification was done on an L40S: new sum/max/min numerical regressions cover fp16 and fp32 with batch 4/8/16, 23 finalize_reducer-related cases pass, and the external reproduction matrix shows zero mismatches across 16 cases. This is a classic “correct at small sizes, silently wrong at large sizes” class of defect.

Source: https://github.com/tile-ai/tilelang/pull/3070

1.2 Main repo: BF16→FP32 vectorized conversion switched to inline PTX packed lane conversion (#3595)

Merged 10-21 19:28, 4 files +19/-7. Adds tl::__tl_cvt_bf16x2_to_f32x2, which uses inline PTX to convert paired BF16 lanes into f32x2 in one go, replacing the per-lane scalar promotion path; all three lane widths of 2, 4, and 8 remain supported. The expected values for vectorized cast and layout inference were updated accordingly, and the BF16 cast tests were narrowed to the existing coverage without expanding the assertion surface. The change does not affect semantics, only the generated instruction sequence; the impact surface is every BF16 compute path that goes through vectorized cast.

Source: https://github.com/tile-ai/tilelang/pull/3595

1.3 Main repo: unroll pass preserves empty stepped loops, ROCm Select lowered per lane (#2887)

Merged 10-21 19:20. The loop unroll pass previously eliminated stepped loops with a trip count of 0 as empty shells, changing the program structure seen by subsequent passes; the fix preserves such empty loops during unrolling. The same commit also changes the vectorized Select on the ROCm side to lower per lane, avoiding whole-group lowering failures on unsupported targets. One change is in IR structure and the other in backend lowering; being combined in one commit indicates they were prompted by the same reproduction scenario.

Source: https://github.com/tile-ai/tilelang/pull/2887

1.4 Main repo: software pipelining preserves transitive copy dependencies, thread domains participate in region conflict determination (#2822)

Merged 10-21 18:13. Pipeline planning previously followed only direct dependencies, so indirect (transitive) copy dependencies were lost at the planning stage and the waits on dependent copies were deleted along with them; meanwhile, the physical region conflict check had two separate sets of criteria on the planning and lowering sides. The fix uses a backward worklist to follow both scalar and buffer copy dependencies, makes planning and lowering share a single physical region conflict check, keeps replay bindings within scope, and fills in coverage for transitive producers, strided aliases, and the sequential TMA fallback path. A second commit introduces thread domains into region conflict determination: accesses are first expanded to the materialized thread domain before regions are compared, so disjoint shared-memory slices can still be pipelined while cross-thread dependencies and physical overlap of strided buffers are preserved; the same domains are used for pipeline planning, dependency validation, and buffer versioning.

Source: https://github.com/tile-ai/tilelang/pull/2822

1.5 Main repo: upfront validation of cast source/target/rounding combinations (#3350)

Merged 10-21 13:49. round is only lowerable for explicitly listed combinations: PTX cvt.rs requires an f32 source, a 32-bit rbits operand, and a specific packed target. Other combinations were previously let through at branch dispatch, and the rounding annotation silently disappeared; scalar loops already rejected these combinations, but vectorized loops did not, so the same cast behaved differently in the two loop forms. A typical example is f32→E8M0: its helper rounds toward positive infinity and does not accept a rounding parameter at all, yet the vectorized branch never read round. Illegal combinations are now rejected uniformly before dispatch, so no branch can drop the annotation anymore; the accompanying tests pass the parameter only for the rs mode that genuinely accepts rbits.

Source: https://github.com/tile-ai/tilelang/pull/3350

1.6 Main repo: CUDA target without arch rejected instead of silently defaulting to sm_50 (#2860)

Merged 10-21 13:32, 1 file, fixes #1049. On machines with a CUDA toolkit but no usable GPU, a CUDA target without a specified arch degraded to a bare cuda, and TVM then silently filled in arch=sm_50, with compilation proceeding toward a wrong SM and no diagnostics throughout—exactly the trap of tilelang.compile(func) with target="auto". The fix lands in _cuda_target_from_arch, the single entry point shared by auto-detection and an explicit target="cuda", which now raises an actionable error stating the two ways to specify an explicit arch ({"kind":"cuda","arch":"sm_90"} or TILELANG_DEFAULT_TARGET). Headless compilation still works as long as a concrete arch is given, since codegen and nvcc depend only on the toolkit, with device access deferred until kernel launch. Three GPU-less unit tests were added at one point during the PR and removed in the final commit, leaving only the entry-point validation.

Source: https://github.com/tile-ai/tilelang/pull/2860

2.3 Main Repo Ascend: Integer Signedness Fix for warp_reduce_max/min on PTO (#3582)

Merged on 10-21 10:21. PTO’s pto.redux_max/min rejects typed integers: PTOAS requires an unsignedness carrier plus an explicit signedness, so int32/uint32 T.warp_reduce_max/min fails to compile outright, reporting “requires signedness=’signed’ or ‘unsigned’ for integer values.” The fix routes warp_reduce_sum/max/min uniformly through contrib.ptodsl’s tl.redux_* wrappers (now exported), with the wrappers providing the carrier and signedness, and gates on value dtype in the manner of AscendAllReduce; the issue references main repo #3541 and PTOAS #1579. Verification is two-layered: lower-only codegen tests over an op × dtype grid, and sparse dual-target (ascend/pto) execution tests — using uint32 lanes ≥2^31 to directly expose signedness mistakes.

2.4 Ascend Repo: Sub-32B Compact Row-Pitch Source Cannot Be Expressed, keepdim reduce Output Corrupted (#1795)

Merged on 10-21 17:15, 2 files +302/-3, fixes #1682, and is the most technically substantial item in this window. The root cause is at the template layer: copy_ub_to_gm unconditionally generates a multi-burst DataCopyPad, while the MTE3 engine implements the system-level convention that “UB narrow rows are stored in 32B slots” — the source address advances by ceil(blockLen/32) + srcStride 32B blocks per burst. For producers that write rows on 32B boundaries this is an exact match; but T.reduce_max’s (M,1) fp32 output is written compactly by the V-pipe with a row pitch of only 4B, which the engine cannot express. In practice the second burst reads element 8 instead of element 1 (in [127, 1151, 71, 199], 1151 is exactly the value of element 8); the write side is fine — the error is in the DMA source address sequence. The fix has two halves: when both sides are packed and total ≤ 65535, collapse into a single flat burst (M×L bytes, exploiting the “single burst length is arbitrary” contract); non-expressible row pitches that are not multiples of 32B are changed to an explicit trap() abort, guarded by compile-time if constexpr, generating no extra code for 32B multiples and sub-32B slot layouts. Why not degrade: bisheng’s cross-pipe automatic synchronization only covers straight-line intrinsics; wrapping DataCopyPad in a conditional branch, or placing a GM scalar write in a sibling branch, causes bisheng to generate bad synchronization code and deadlock the device (in practice, per-row DMA wrapped in a runtime branch triggers an aicore exception). 14 test cases cover the flat/multi paths, the keepdim reduce reproduction, UB loop reuse, the legal single-burst form of non-expressible pitches, and the explicit abort; the test environment is Ascend910 A3 (dav-c220) / CANN 9.0.0 local build. The PR itself notes two remaining boundaries: sub-32B compact row pitch with a pitched destination (e.g., writing (M,1) fp32 into one column of a wide tensor) still uses slot stepping; blockCount > 4095 (12-bit field) still silently truncates (a 4200-row test copies only the first 104 rows), to be filed as a separate issue.

Source: https://github.com/tile-ai/tilelang-ascend/pull/1795

2.5 Ascend Repo: JIT Cache Switches to Atomic Publication and Recovers When Cache Is Deleted (#1903)

Merged on 10-21 16:20, 7 files +1026/-86, related to #1836. The original implementation overwrote build artifacts in place into kernel_lib.so; if another process had already loaded that shared library, it would read a file being rewritten. The fix first copies artifacts to a separate temporary file in the same directory, then publishes atomically with os.replace(); if the cached library has been deleted before loading, after confirming via the error message and file state it returns a cache miss and recompiles; if the directory disappears during the save phase, it skips saving and retains the compilation or tuning result already obtained; permission errors, missing dependency libraries, invalid ELF, and serialization internal exceptions continue to propagate upward rather than being swallowed as a miss. Coverage includes KernelCache, AutoTunerCache, and AutotuneResult, without changing cache keys, operator computation logic, or CI parallelism. 41 host-only test cases pass (9 for atomic publication, 32 for cache-deletion recovery); the PR itself notes no NPU-side integration verification was done. The atomic publication part follows the implementation of #1853 and retains the original author’s information.

Source: https://github.com/tile-ai/tilelang-ascend/pull/1903

III. Ecosystem and Adopters (TileOPs / TileFoundry / Operator Libraries)

3.1 TileFoundry: 0.0.3 tagged and released — instruction-level scheduling + refactored analysis + H200 and Apple AMX examples

The previous issue noted that “the 0.0.3 announcement is already in the README, tag still pending”; this issue, on 10-21 at 10:26, it was officially released, with PyPI as tilefoundry==0.0.3, codename “Agent-driven scheduling”. The core change is where scheduling authority resides: the compiler lists which instructions can implement each HIR operation and what each requires, the agent selects among the candidates, and the compiler then lowers the selected schedule to TIR. The accompanying CLI has tilefoundry schedule candidates and schedule facts to display candidates and constraints, tf.schedule records the selection, and tilefoundry schedule finalize completes the lowering; instructions are declared as AtomSched operations with explicit TIR operand contracts, starting from CUDA MMA atoms, SM90 WGMMA, and async copies. The analysis portion was refactored into memory (segmented allocation, footprint and reuse windows, loop-aware buffer lifetimes), cost (work and traffic counted by execution scope, each access relation declaring what it reads), and structure (definition facts, valuation contexts, and scope snapshots unified through visit context, with projection reuse so each corpus case is analyzed only once). The new tutorial walks a single 8192×5120 by 5120×17408 GEMM all the way to the optimal AtomSched kernel on H200.

The performance side gives three sets of real numbers: Qwen3.8-27B prefill on a single H200 at 1024 / 4096 / 8192 tokens is 80.29 / 309.61 / 631.19 ms respectively, versus SGLang’s 89.06 / 317.11 / 638.25 ms; short sequences at 128 / 256 / 512 / 1024 tokens are 1.88× / 1.41× / 1.10× / 1.03× SGLang respectively; the Qwen prefill example on Apple M2 Pro implements the large projection as an FP16 AMX outer product. Both Qwen3.8-27B runs produce the same first token as transformers at every length. Two known issues: the wheel does not yet package TileFoundry’s CUDA runtime headers, so tf.compile cannot build CUDA kernels from an installed package (a source checkout is required; fixed in the next version), and the performance timeline misprices insert_slice / tf.zeros across mesh locations and does not show mesh lane underfill (#239).

Source: https://github.com/tile-ai/TileFoundry/releases/tag/v0.0.3

3.3 TileOPs: dense GQA supports FP32 attention sink (#2515)

Merged 10-21 22:42. Adds an optional per-head FP32 attention sink for dense GQA prefill and decode, covering FP16/BF16/FP8 on SM90, RoPE, softcap, and sliding window; other architectures reject sink calls outright. Semantically each sink is an unscaled, non-softcapped logit in the denominator: -inf disables that sink, +inf directly zeroes that head’s output, and split decode must preserve sink weights under large logits. Also fixes a benchmark distortion — the chunked prefill benchmark was previously being measured as single-query decode; the fused-RoPE tail cases adjust KV length to 271/1025 to cover split execution.

Source: https://github.com/tile-ai/TileOPs/pull/2515

3.4 TileOPs: concentrated fill-in of SM89 small-scale paths (#2681 / #2672 / #2669 / #2654)

All four merged PRs address L40S/4090-class gaps. #2681 changes the default tile for FP8 BMM on SM89 to 64×64 — conditioned on the result grid having at most one block per SM; large grids keep 128×128; the author gives single-GPU measurements on PyTorch 2.13.0 + CUDA 13.0 + TileLang 0.1.12: 1×16×64×128 drops from 5.161 to 3.799 us, 16×128×128×1024 from 12.943 to 7.414 us, while 4096³ goes from 512.573 to 583.680 us instead (that row’s tile is unchanged; this is noise). #2672 raises the default M upper bound for 64-column W4A16 from 16 to 64, with replay times at M=17 / 32 / 64 dropping 43.35% / 47.20% / 40.00% respectively, while retaining explicit configuration overrides and numerical tolerance. #2669 implements SM89 paged DSA with MMA, preserving the 656-byte FP8 latent cache layout, BF16 rounding, natural-log LSE, and dead position behavior: batch 4 / 128 head / 256 positions is 0.269 ms versus 0.727 ms for the PyTorch FP32 reference, and 48×64 head×2048 positions is 2.543 versus 2.535 ms; the author explicitly writes that “the large case is essentially at parity and does not constitute a general advantage”. #2654, for small token counts, computes and moves only the covered 8-token accumulator prefix, opening 40-token decode up to M33–40 on a 132-SM H200 with N divisible by 128, 133–225 output tiles, and K∈{7168, 7680, 8192}.

Source: https://github.com/tile-ai/TileOPs/pull/2681, https://github.com/tile-ai/TileOPs/pull/2672, https://github.com/tile-ai/TileOPs/pull/2669, https://github.com/tile-ai/TileOPs/pull/2654

3.5 TileOPs: NSA top-k extended to 2048 compressed chunks on SM89 and output slots completed (#2674 / #2675 / #2673)

Three PRs revolve around the same SM89 path. #2674 lets group48 reuse the existing tiled top-k program: one tile per token (48 query head rows), column-wise GEMM warp layout; #2675 raises top-k selection on SM89 from the previous cap to 1024–2048 compressed chunks, covering head dim 64 / 128 / 256; #2673 fixes output filling when candidates are insufficient — every requested top-k slot must be filled with -1, whereas previously the 32-slot sorting band would leave stale values in slots 32–63. Separately, #2684 adds an upper bound to the NSA sorting capacity for packed requests, using min(total_chunks, ceil(total_tokens / block_size)) and then aligning to the scoring tile.

Source: https://github.com/tile-ai/TileOPs/pull/2674, https://github.com/tile-ai/TileOPs/pull/2675, https://github.com/tile-ai/TileOPs/pull/2673

3.6 TileOPs: GDN single-kernel prefill and quantized normalization splitting (#2682 / #2679)

#2682 targets GDN forward for linear attention: its prefill was slower than FlashInfer on 79 rows in the nightly batch (0.57×–0.98×); the fix is to fold prefill into a single kernel when “the walk can fill the SMs”. #2679 handles FusedAddRMSNormPerTokenQuant: about 25 SASS instructions per element are spent on elementwise math; the change packs the elementwise math and splits wide rows across clusters. Both PRs replace “serial overhead within a single operator” with “wider parallelism and fewer instructions”, the same idea as the SM89 small-scale path tuning group the same day.

Source: https://github.com/tile-ai/TileOPs/pull/2682, https://github.com/tile-ai/TileOPs/pull/2679

V. Trend Observations

The nature of compiler defects is expanding from “computing the wrong number” to “choosing the wrong target.” Of the eight merges into the main repo this issue, four change “what the compiler thinks it is doing”: a CUDA target without an arch silently falls back to sm_50 (#2860), cast rounding annotations are silently dropped by branch (#3350), batched reductions process only the first output block (#3070), and pipeline planning loses transitive dependencies (#2822). What they share is that they do not raise errors and only produce untrustworthy results under certain sizes or certain loop shapes—harder to locate than crashes, and also showing that the project places silent correctness ahead of feature expansion.

The bottleneck on the Ascend line has shifted to the memory model and runtime boundaries. Sub-32B compact row spacing cannot be expressed via DMA and can only be explicitly aborted (#1795); cache concurrency is changed to atomic publication with deletion recovery added (#1903); PTO’s integer signedness has to be patched up by a wrapper layer (#3582). None of these three is “adding an operator”; they are “keeping existing operators from failing under boundary conditions.” Together with the merged DeepGEMM heuristic alignment, the Ascend side is shifting from capability coverage to engineering reliability.

Analyst firms are beginning to treat TileLang as the criterion for Ascend usability. SemiAnalysis uses “only TileLang among the six repos was usable at the time” to define the completeness of DeepSeek’s Ascend support—more than any single technical blog post, this shows TileLang’s position in the domestic-compute narrative: from an experimental DSL to the default carrier layer. The same report also gives a reverse signal—optimization is concentrated on supernodes, x86 host support is still incomplete, and generality lags behind performance.

The center of gravity of the attention stack is moving from inference forward passes to training backward passes. Within a single day, TileOPs filled in the op layer for MLA prefill backward, the SM90 warp-specialized kernel, and data-fetch order optimization, plus grouped KV head handling for GQA backward—fully aligned with the backward-operator backfill on the Ascend side since last month (indexer_bwd, SiTU-GLU backward, WY fast backward). TileLang’s coverage on the training side is being systematically filled in.

SM89 is moving from “it runs” to “it’s tuned.” Four lines—FP8 BMM tiling, the M upper bound for W4A16, paged DSA, and NSA top-k—were all worked on the same day, and all give single-card measurements along with qualifiers such as “does not constitute a general advantage.” Consumer-grade and single-card inference scenarios have become one of the performance targets, and at the same time the authors’ self-discipline on benchmark methodology has clearly tightened.

The division of labor between scheduling and correctness is becoming clear between TileFoundry and the main repo. The main repo continues to tighten semantics and correctness, while TileFoundry 0.0.3 hands “which instruction to choose” to the agent and leaves “guaranteeing semantics” to the compiler, giving reproducible numbers with two examples: H200 and Apple AMX. If this division stabilizes, the TileLang ecosystem will develop a two-layer structure: “the language layer guards correctness, the agent layer fights for performance.”
