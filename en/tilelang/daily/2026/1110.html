I. Core Project Progress

1.1 Mainline: dense views restore precise logical regions, cross-row dependencies refined to the row (#3890)

After #3805, multi-element pointer accesses through explicit-stride views all fall back to the entire buffer, even when the view is dense row-major. The consequence is concrete: reading row 0 of a (2, 128) BF16 view is treated as reading both rows, creating a spurious V-to-MTE2 dependency on a subsequent DMA write to row 1. In TileKernels’ engram_gate_bwd, this erased the distinction between two slots of a BF16 view over FP32 storage, the precise-region assume_no_conflict hint failed to match, and synchronization stalled the next slot’s DMA behind the previous head’s vector computation.

#3890 first proves that the explicit stride indeed describes a dense row-major view, then reuses #3805’s offset-aware reconstruction (including cross-row carry, with a conservative fallback when it cannot be expressed), leaving physical lifetime and reuse analysis untouched and limiting the change to logical dependency precision. Indirect accesses remain conservative: gather/scatter indices and vld2 with offsets can reach beyond the compact access_ptr range, so regardless of whether the buffer is a dense view, an implicit layout, or one-dimensional, the entire logical buffer is retained in front of such consumers, preserving the V-to-MTE2 synchronization required before DMA covers indirectly reachable rows. New regression tests distinguish “overlapping slots” from “adjacent slots”.

Source: https://github.com/tile-ai/tilelang/pull/3890

3.2 TileOPs: three boundary-input fixes—K=0 empty contraction, variable-length GQA hang, GLA backward shared memory

The common shape of the three bug fixes is “does not occur under default parameters, only blows up on boundary inputs.” #2878: the K=0 empty contraction previously raised OpNotAvailableError on SM89, because the cp.async kernel’s narrow-row rule guards the innermost-dimension load in 4-byte units, while with K=0 the main loop never runs the K steps at all; after the fix, test_gemm.py -m "smoke or sm89" goes from 63 passed 6 failed to 66 passed 4 failed, the remaining four being SM90-only cases. #2876: the fused RoPE in variable-length GQA forward hangs when the rotary half-width is padded to a value not divisible by the thread count (rotary width 10, 5 chunks padded to 6, 128 threads); the root cause is that CI’s TileLang places the barrier inside the guard, so threads on the padding chunk skip it; a new split_reads puts “read plus rotate” and “write back” in two rounds, enabled only for the variable-length GQA kernel. #2880: float32 GLA backward at chunk 64 needs 114688 bytes of shared memory, while SM89 has only 101376; the fix assembles the dv state term after the dA product, at v’s last use, letting the decayed key take v’s place, bringing it down to 98304 bytes, with gradients bit-identical to the default order.

Source: https://github.com/tile-ai/TileOPs/pull/2878 , https://github.com/tile-ai/TileOPs/pull/2876 , https://github.com/tile-ai/TileOPs/pull/2880

3.3 TileOPs: Softmax keeps the whole row in registers, one exponential per element, instruction count down 21% to 23%

#2886 makes SoftmaxClusterSplitKernel also serve 16-bit rows of up to 8 shares of 16KB: each CTA keeps the share’s whole row in registers, 128 threads per CTA, one exponential per element. The original segmented program did two exponentials per element and routed half the shares through shared memory; 16-bit rows had 52% more instructions than quack, and 65536-element rows lagged by 3%. #2871 replaces the exponentials of the two register-resident softmaxes with a bare MUFU.EX2 plus one row reciprocal, adding a shared primitive exp_shifted_scaled that first multiplies by 2 to the 24th power, ensuring terms roundable to nonzero float32 remain normal numbers, with the reciprocal’s scaling factor canceling automatically. Executed instructions drop 23% at 512 columns and 21% at 2048; bf16 at 512 columns is 16.67 microseconds versus quack’s 16.35, and at 2048 columns 62.99 versus 62.21.

Source: https://github.com/tile-ai/TileOPs/pull/2886 , https://github.com/tile-ai/TileOPs/pull/2871

3.4 TileOPs: RMSNorm narrow block asks the compiler for the residency cap, short-row warp activity stops dropping

#2884’s paired RMSNorm 64-thread block (one row of 1024 16-bit elements, two vectors per thread) now requests the SM’s 32-block residency cap from the compiler; without the cap, ptxas gives 40 registers per thread, and one H200 SM holds only 24 of the 32-block cap, dropping warp activity on short-row loads to 64%. The wider paired block keeps its register configuration unchanged to avoid affecting large-row throughput.

Source: https://github.com/tile-ai/TileOPs/pull/2884

3.5 TileFoundry: 1491 files reorganized per source spec, rules enforced in pre-commit

#312 is the window’s only large change: 1491 files, +41324 to −42379, closing #296. The approach is to write down as rules what previously had no enforced constraint: a new docs/spec/code-organization.md states the S1–S11 and C1–C11 Python source rules and the layering table, with scripts/code_organization_lint.py, ruff, and import-linter enforced in pre-commit; the rules apply to every .py file, the only configuration being src and per-file exemptions, and __init__.py only re-exports, with no __all__. Structurally, ir/ is split into expr, types, dim, utils, core, pattern, clause, hir, tir; visitor_registry and evaluator are merged into seven pieces under interfaces—valuation, typeinfer, verify, cost, access, evaluator, schedule; the root compile.py moves into compiler/, script.py and module.py into parser/, and assembly logic into bootstrap.py; Go-style qualified names (types.TensorType) are adopted, and Options are split by phase after clang’s CompilerInvocation. The implication for downstream: TileFoundry’s internal import paths change in this version, and scripts referencing private symbols need to follow.

Source: https://github.com/tile-ai/TileFoundry/pull/312

V. Trend Observations

First, capacity and pass rate in the performance queue have decoupled. Three batches of 6 each, 18 in a day — capacity is stable; but 10 marked below bar shows that the current pipeline’s goal is not “get faster this round” but “localize the gap to a fixable degree this round.” The root cause in #2887 is the most typical: the base tile splits B into 256-byte fragments read across rows, and DRAM streaming efficiency is lower than with fewer rows and longer runs, so it switches to 64-row blocks with a deeper loop. Even if such changes miss the score, they pin down the direction for the next step. To judge the maturity of a performance PR, readers should look at the Result line first, then check whether the root cause is reproducible.

Second, registers and dispatch have become the common bottleneck in this batch. #2884 is register quota capping the number of resident blocks (40 registers means the 32-block ceiling only holds 24 blocks), #2870 is 6272 128-thread blocks versus 1568 512-thread blocks — a fourfold difference in dispatch count, and #2885 is a 192-wide tile with higher fill rate but row-mask storage dividing by 192 overflows registers. All three point to the same thing: on SMs like the H200, operator performance is no longer determined by arithmetic volume but by the second-order parameter set of “how many registers per thread, how many blocks per SM, how many dispatches per block.”

Third, the bottleneck on the Ascend line has shifted from development volume to review bandwidth. The default branch has had no merges for three days, yet more than 20 PRs are stacked in review, and the topics have shifted from operator migration to toolchain interfaces (torch.compile, L2 flush, L0C dequantization). The dense-view fix in #3890 points the same way: it adds no new capability but makes the existing dependency analysis hold on more shapes. For users, improved usability of the Ascend path will first show up as “more shapes compile with correct dependencies,” not as a longer list of new operators.

Fourth, versions and structure are moving in the same window. tilelang’s 0.1.16 version-number PR, TileFoundry’s 1491-file reorganization, and the MetaX docs pushing the SDK companion package to musa.5 and raising the glibc threshold are all “pre-release preparation.” Downstream teams tracking versions need to check three places at once: the main repo tag, the backend repo’s musa.* or ascendc_pto branch, and build-time dependencies (glibc, apache-tvm-ffi). A previous window had the pitfall of “upgrading tilelang_musa without upgrading tvm-ffi”; this period’s docs write it up as an explicit rule.

Finally, the RISC-V line. The four-source patrol shows no change in 24 hours: the two kubuds- branches of kubuds/tilelang-riscv-kubuds, the MLIR route of RuyiAI-Stack/tilelang-riscv, the index page of TongmingLAIC/tilelang-riscv, and the SOPHGO branch of TongmingLAIC/tilelang-tpu all remain at their original references — this is now the third consecutive window (archived on 11-07, 11-09, 11-10) with no change. Contrasted with the GPU side’s “three batches a day” cadence, the RISC-V side is still on a manually driven weekly cadence; the gap is not in engineering effort but in whether there is a loop that automatically discovers gaps, automatically verifies, and automatically queues.
