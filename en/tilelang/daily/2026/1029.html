Today’s Highlights

Today’s window centers on the Ascend side. tilelang-mlir-ascend merges the entire NPUIR backend for Ascend 910 (A2/A3) into the mainline in a single commit touching 55 files with 21,490 added lines: on the Python side, the tilelang/ascend910 package (backend / adapter / codegen / compiler / execution_backend / jit / pipeline / runtime / target, plus the kernel, copy, gemm, and npuir dialect surfaces under language); on the C++ side, the developer and expert emitters under src/ascend910/target, the op layer, and three passes — LowerNpuirBlock, NpuLoopVectorize, and RewriteFDivToMul; the runtime gains npu_launcher.h and npu_utils; installation goes through install_npuir.sh; and the target alias accepts ascend910 / ascend-910 / a2 / a3 / npuir. The author’s acceptance criteria are the repo’s two bundled test suites: all 504 pytest testing/npuir cases pass, and 71 of 72 examples pass with 0 timeouts and 0 errors — the sole failure, deepseek_v32/fp8_lighting_indexer.py, fails identically on the old backend on the same machine and is an environment and tolerance issue. A second commit aligns behavior differences with the old backend item by item, focusing on bf16 legalization (HIVM does not accept bf16 operands, so computation is done in fp32 with explicit conversion) and copy sinking for dynamic extents.

TileOPs merged seven commits today, with both main threads on the performance side. The selector no longer fits against the manifest; instead it is recalibrated on busy time (device_busy_ms) across 160 dense shapes, 60 shapes with m in 9–32, and 264 shapes with m≤8, using coordinate descent on softmin expected log regret. End-to-end busy-time regret on the held-out manifest drops from 5.79% to 0.48%, and the m≤8 holdout set drops from 14.18% to 1.79%. On the GEMM side, coop2_swap is added: non-NT layouts are converted to a transposed persistent kernel, with two consumer warpgroups each holding 128 rows, tail writes landed back via stmatrix.trans and TMA transpose, and mixed wide/narrow tiles supported (e.g., 2112 = 13×160 + 32 split into 160-wide tiles plus a 128 narrow tile); 2112×7168×4096 TN drops from 195.3 µs to 175.3 µs, and another H200 on the same machine reads 174.3 down to 158.5 µs — both beating QuACK’s 187.9 and 167.0 µs.

The reduction side broke and was fixed the same day. In the morning, #2787 implemented NaN propagation for extrema reductions using int32 keys, and #2788 changed the row tiles of the parallel cumsum; both landed around 07:00, after which #2790 and #2792 respectively closed out the two regressions: cumsum was changed to seed-based segmentation with two launches ((8,65536) float32 from 12.75 µs to 5.18 µs, also fixing mainline launch failures above 65535 tiles), and extrema switched to PTX max.NaN / min.NaN with a separate kernel for rows that are not whole 16-byte vectors (amax (2048,4096) bf16 back from 8.352 µs to 6.976 µs, faster than FlagGems). This “introduce and fix within the same day” cadence shows that TileOPs’ nightly benchmarks are now catching regressions the same day.

I. Core Project Progress

1.1 Main repo: Index coefficients of scalar reads no longer leak into lane counts; compile crash for row widths above 32768 closed (#3453)

Merged 10-28 11:06, single file +8/-5. A kernel that reads a full row in vectorized fashion while also reading individual elements of that row by index failed to compile with InternalError: Can’t fetch the lanes of a scalable vector when the row width modulo 65536 was at least 32768. Root cause was in VectorTypeAccessChecker::OnArrayAccess: it recorded scalar reads as access_dtype.with_lanes(me->coeff), where me->coeff is the modulo coefficient of the read index — for x[row, 0] that is the row width. DataType’s lane count is only 16 bits and is read back as int16, so 32768 through 65535 was treated as a scalable vector and lanes() threw directly in get_preferred_dtype, while wider multiples silently wrapped. The fix stores the coefficient separately in an int64_t, uses it for the modulo in compatibility checks, and keeps only the element type in the dtype of scalar reads. The original trigger was TileOPs’ GroupNorm: both the 40960 and 163840 group widths in Stable Diffusion hit it. Verified with two wheel builds compared: mainline fails to compile at both 32768 and 40960 widths, while this change builds at all tested widths.

Source: https://github.com/tile-ai/tilelang/pull/3453

1.2 Main repo: Batched all-reduce resolves thread ranges via the scalar branch; fixes all 2048 outputs wrong when batch>1 (#3341)

Merged 10-28 05:46, 2 files +170/-8. The scalar all-reduce branch resolves the participating thread range before emitting the call (ResolveAllReduceThreadRange when reducing_threads exceeds 32 and the target supports named barriers), but the batched branch took block boundaries directly as offset and barrier width. When the reduction threads are a partial range not starting at 0, such as [32, 96), the batched call indexed from thread 0 and barred on whole blocks, folding uninitialized registers of non-participating threads into the reduction: batch=1 was correct, batch=2 on the same kernel produced all 2048 output elements wrong with a maximum absolute error of 1083 and no diagnostics. The fix makes the batched branch use the same resolution as the scalar branch, passing the resolved offset and range to MakeBatchAllReduce, with workspace stride still the block size. A new test runs batch=1 and batch=2 on the same kernel and compares against the torch reference.

Source: https://github.com/tile-ai/tilelang/pull/3341

Merged 10-28 08:14. SIMT atomic operations previously did not validate the shape of the passed region, so mismatched shapes only surfaced as wrong results or crashes in codegen. This change adds region shape validation on both the CUDA and ROCm paths, rejecting invalid regions at compile time.

1.5 Main repo: atomic_addx4 target dtype narrowed to float* (#3369)

Merged 10-28 16:08, 3 files +27/-9. The generic CUDA implementations of atomic_addx4 and atomic_addx4_ret previously accepted any target pointer, so int32 or int64 targets fell through to float semantics and computed wrong results. This change restricts both generic overloads to float* targets, leaving the existing fp16 and bf16 specializations untouched; the Python-side API stays type-neutral, and integer targets on the CPU backend are unaffected. A regression case for compile failure with integer targets is added on the CUDA side, and accumulation correctness cases for two integer widths are added on the CPU C backend.

2.4 Ascend repo under review: root cause and fix for incorrect W4A4 int4×int4 GEMM results (#1731)

Under review, 7 files +634/-24, fixes #438. The root cause is that the entire C++ template stack derives fractal geometry from sizeof(AscendC::int4b_t) == 1, whereas int4b_t is a nibble-packed type: the correct element count for a 32-byte C0 block is 64, not 32, so all copy strides, repeat counts, and byte counts are off by a factor of 2. Three layers compound: the LoadData parameters from L1 to L0A/L0B are derived from that constant, so data piles up in the wrong place; the zN-to-nZ transpose of the B operand is silently disabled by the s4-specific instruction load_cbuf_to_cb_s4, requiring a switch to LoadDataWithTranspose to load_cbuf_to_cb_transpose_s4, whose parameter semantics are undocumented in the CANN headers, forcing the author to reverse-engineer them on-device with probe kernels (correct parameters repeatTimes = N/64, srcStride = roundUp16(K)/64, dstGap = 3, and the s4 version works in 2048-byte blocks rather than the 512-byte fractal stated in the docs); the UB-to-GM byte length is computed at 1 byte per element, moving twice as much per row and mixing in adjacent rows. The mad_s4 instruction itself is correct; the symptom is 99.6% mismatch, with output -501/627 versus the correct answer 641/1785.

III. Ecosystem and Adopters (TileOPs / TileFoundry)

3.1 TileOPs: Selector recalibrated on busy-hour conditions, manifest regret cut from 5.79% to 0.48% (#2784)

Merged 10-28 10:51, 4 files +259/-203. The dense selector’s scoring now uses a tensor_core_tflops multiplied by a structural factor; previously structural differences only showed up in a single max(), so memory-bound shapes scored basic, simple, and coop2 equally. The launch_us term was removed (it fits to 0 under busy-hour conditions). The m≤8 NT band replaces hand-tuned thresholds with a streaming model: per-CTA rate is min(ns·rows·bk·2/latency, cta_gbps), waves are computed from SMEM-limited residency, plus a DRAM floor of n·k·2/dram_tbps and a split-K reduction term. The TN/TT persistent kernel path is now wired up (A/B SMEM tiles follow the storage layout, transpose_A/B); 176/192 widths, narrow tiles, ping-pong, and split-K remain NT-only. Calibration is done under busy-hour conditions across three grids of 160/60/264 shapes, 7 interleaved CUPTI rounds taking the median, with softmin expected log regret via coordinate descent and tau annealing 0.1→0.05→0.02. End-to-end results: held-out manifest 5.79% to 0.48%, calibration grid 9.28% to 2.65%, m 9–32 3.13% to 2.09%, m≤8 11.20% to 1.17%, m≤8 held-out set 14.18% to 1.79%.

3.2 TileOPs: Non-NT layouts moved to transposed persistent kernel, 2112×7168×4096 TN from 195.3 to 175.3 µs (#2789)

Merged 10-28 21:06, 4 files +620/-15, resolves #2785. Adds coop2_swap: for TN/TT/NN it computes Cᵀ = op(B)ᵀ·op(A)ᵀ, runs a persistent kernel over 256×block_n tiles, with two consumer warpgroups each holding 128 rows, and writes the tail back transposed via stmatrix.trans and TMA. Mixed tile widths (narrow_n and row_mix) keep M from being wasted on padding—e.g. 2112 = 13×160 + 32 splits into width 160 plus narrow 128, wide runs first and narrow finishes, with the split point taken from coop2’s narrow-tile _busiest_cta metric. The selector enumerates coop2_swap block_n 128 and 160 outside NT, structural factor 1.2, refit under busy-hour conditions. H200 busy hour: 2112×7168×4096 TN from 195.3 to 175.3 µs (QuACK 187.9), 24576×1536×4096 TN from 421.9 to 416.4 µs; on another H200, 174.3 to 158.5 (QuACK 167.0) and the 384–402 µs range respectively. 3.7 TileFoundry: Ring stage binding and compile flow unified, 70 files (#277)

Merged 10-28 16:55, 70 files +1567/-1298, supersedes #276. Two motivations: unbound ring views and stage selection could carry views without SSA names into CUDA operands; and the three compile entry points each assembled different pass lists. The fix stores ring stages as a set of bound TensorViews, binding once per consuming scope, and shares default_pipeline across finalize, compile, and scaffold; the core host entry pass is resolved via Target.resolve with CUDA providing the @bind implementation; Module.entry becomes the host starting point, and the analysis’s shared-memory peak is carried into host launch; all CPU hosts in the call chain participate in linking, with the root host first. Contract changes: link_program drops entries, the loader binds the first linked host, and build requires a CPU host root. Remaining risks are noted in the PR: #278 tracks Broadcast layout normalization, #255 tracks SymbolRef and function references.

V. Trend Observations

The Ascend side’s approach over the past two days is now clear: the main repo merges small fixes by the hour (cache keys, register phases), the dedicated repo mlir-ascend moved the 910 NPUIR path from a feature branch into the main branch with a single 20,000-line merge, and tilelang-ascend is filling in documentation and operators on its established dual-backend cadence of PTO and AscendC. The three operate at different tempos but point to the same thing: the 910 compiler path is shifting from “it runs” to “it’s acceptance-ready,” and the 504 self-tests and 71/72 examples are the acceptance criteria given this time. Notably, the a2a3 scheduler migration in the review queue spans 100 files, indicating that the next phase of change is at the scheduling layer rather than the operator layer.

On the performance side, the focus is on the measurement methodology itself. These two TileOPs changes move both the selector and GEMM conclusions to busy time (device_busy_ms), and in the same PR present the difference between single-call and back-to-back invocation: under the single-call reading, this implementation leads QuACK, while in back-to-back, power-capped training scenarios, six of the ten large rows lag behind. This is a more important signal than “how many microseconds a given row is faster by,” because training is in practice back-to-back. #2791 makes this a standalone item, showing the team now treats the methodology issue as a product issue rather than glossing it over as benchmark bias.

On engineering hygiene, three things are worth noting today: first, self-inflicted breakage and self-repair within the same batch (#2787/#2788 merged in the morning, #2790/#2792 reverted in the afternoon), which shows the nightly benchmark’s fallback is working but also that the semantic boundaries of this reduction code remain fragile; second, the semantic hole in without_kernel_cache() (#3699) was caught during the migration — the two in-process cache layers do not honor CacheState, so tests believe they are cold-compiling while actually getting an old kernel, and such defects render “all our tests pass” meaningless; third, 13 example failures on SM120 (#3701) expose examples hardcoding Hopper dimensions, and as Blackwell installations grow, this kind of “examples are not the product” debt will be repeatedly charged.
