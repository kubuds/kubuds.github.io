Today’s Highlights

The main thread of this window is cleanup. The five merges in the main repo (+1903/−617, 22 file changes) added no new operators and no new backends; four of them are wrapping up the tail of the PTO vectorization overhaul from the #3512 round: VMI descriptors were fetched incorrectly on typed-view gather/scatter and single-element loads, so #3894 fixes 6 files in one go, +925/−550; the analytic traversal bound scalar definitions too early, and IntSet threw an exception when evaluated on a wrapping cast, so #3793 adds a guard; lane-layout inference treated the vector block address of explicit SIMD as a scalar lane access, so the old form no longer compiled, and #3796 preserves the old path; codegen_pto was changed to emit si32/si64 while PTO atomics only accept signless, so #3792 performs a local reinterpretation at the call boundary. What these four share is that “after the overhaul, previously legal programs are no longer legal” — an inevitable cost of a large change, but four consecutive windows from 11-10 to 11-13 have all been paying this bill, which suggests the regression surface of the PTO line is wider than estimated.

The fifth merge, #3614, is of a different nature: it is not a bug fix but deadlock prevention. Ascend kernels have two scheduling modes: mode=0 is “launch the operator as soon as cores are available,” and mode=1 is “wait until all core resources the operator needs are in place, then launch as a whole.” If an operator that performs all-core synchronization is launched in normal mode, it may get only some of the cores and run ahead to the all-core barrier to wait for the rest, while the rest are occupied by another stream — resources form a cycle, and the device hangs outright. This change identifies “cross-core synchronization with constant 0” on the codegen side, automatically sets __schedmode__(1), and resets the flag per function to prevent leakage into subsequent entry points; at the same time, it narrows the integer-form mode in the cross-core set/wait interfaces to 0/1/2/4, leaving non-integers unvalidated to preserve symbolic quantities. The regression file is 78 lines and covers seven cases: all-AIC, all-AIV, the AIC+AIV combined protocol, three local modes, and flag reset.

The activity on the ROCm side is more noteworthy than Ascend’s. Less than an hour after the window opened, the same account filed seven PRs in a row, 22 files +624/−19, all based on 72d986e1, forming a complete set of HIP-side patches: compile flags previously went only into the cache key and not into hipcc (#3954); 8/16-lane broadcasts of 8-bit integer vectors emitted make_uint2/make_uint4, which hipcc rejects (#3955); T.gemm on small tiles reported useless messages like “Divide by zero” (#3956); T.annotate_min_blocks_per_sm was dropped on HIP, and on gfx90a a 256×128×32 fp16 GEMM was locked to one block per CU due to 143 VGPRs plus 128 AGPRs (#3957); occupancy and scratch usage showed only raw numbers without conversion (#3958); a 64-thread reduction on wave64 allocated an LDS block for nothing (#3959); in HIP, uint2/uint4 are structs, so fp16 fragments that live across loops were pushed back to the stack by SROA, consuming 80 bytes of scratch per lane (#3960). ROCm had long been recorded in this daily report as “an occasional one-off”; appearing as a series within a single day is the most obvious structural change this issue.

The third item is on the harness branch of mlir-ascend: three merges totaling +7632/−24 and 64 file changes, none of which land on main or master. The content is not compiler functionality but a “knowledge base written for people (or agents) who want to write operators”: #220 adds the Ascend950 simulation trace workflow (msprof collection, viewing in MindStudio Insight, supplementing GET/RLS events with the dump from the same run, exporting npusim SQLite for timeline analysis; all 38 existing tests pass on WSL); #221 is an installable version of the operator design guide (phase decomposition, SIMD/SIMT selection, storage budgeting, tile pipelining, plus a Cube MFU and conditional Roofline calculator, and it saves snapshots of nine upstream TileLang Skill documents for offline reading); #226 adds BMM and w4a8 Gemm quantization examples, and a conv example went in with the same batch. I. Core Project Progress

1.1 Ascend: Cross-core sync mode=0 forces batch scheduling, all-core barrier no longer deadlocks on core contention with multiple streams (#3614)

This change touches 5 files, +102/−1, of which 78 lines are a new regression test for the schedmode flag; the actual compiler change is only about twenty lines: in Ascend codegen, after identifying “cross-core sync with constant 0,” it sets __schedmode__(1), and makes this flag a per-function-reset member to avoid leaking into subsequent entry points.

To see why this is necessary, return to the scheduling semantics. Ascend kernel mode=0 is normal mode—it launches as soon as the partial core resources required by the operator are available, and operators from different streams can overlap; mode=1 is batch mode—it launches as a whole only after all core resources required by the operator are in place. Operators performing all-core sync (full AIC sync, full AIV sync, and the combined protocol of “AIV sync with local AIC → full AIC sync → sync back to local AIV,” which internally contains a mode=0 phase) may, when launched in normal mode, obtain only some cores and run ahead to wait at the all-core barrier, while the cores it waits for are occupied by another stream and will not be released—resources form a cycle, and the device deadlocks. Batch mode eliminates this window.

The interface was also narrowed along the way: in the cross-core set/wait interface, the integer form of mode_id accepts only 0, 1, 2, 4, and other integers are rejected outright; non-integers are not validated, to preserve the possibility of passing symbolic quantities. The docstring also adds a factual note—the modes listed in the same API documentation are not consistent across the three targets: 910B/910C support 0/1/2, and only 950 adds 4. The regression covers seven cases: full AIC, full AIV, and the AIC+AIV combination should each enable batch mode; mode=1/2/4 should remain default; and the flag does not persist between functions.

Source: https://github.com/tile-ai/tilelang/pull/3614

1.2 Ascend PTO: VMI descriptors and logical-overlap validation closed out together, a single +925/−550, the largest of this period (#3894)

#3894 is the largest change in this window (6 files, +925/−550), putting two independent matters in one branch. The first is fixing VMI memory descriptors, involving two forms: gather/scatter on typed views, and single-element loads—both take a base address and stride when constructing the descriptor that are inconsistent with the actual access. The second is removing the redundant logical-overlap rejection in the VMI frontend.

The premise of the second matter is worth stating clearly: removing the validation is not a relaxation, but because the shared-memory detector fix (#3805) has already landed, and blocking again in the frontend is duplicate interception that also falsely rejects forms such as cross-row, transpose, and dynamic views that should be allowed through. In other words, the same semantics were judged once at each of two layers; once the earlier one was fixed, the latter became a burden.

The −550 lines of deletions mainly come from consolidating these two places. The implication for downstream is that on the PTO target, the two styles—gather/scatter on typed views and single-element loads—go from “compiles but produces wrong results” to “either correct or caught by the detector.”

Source: https://github.com/tile-ai/tilelang/pull/3894

1.3 Ascend PTO: Scalar cast facts protected, wrapping casts no longer make IntSet evaluation throw (#3793)

The reproducer is tiny: u = uint32(i - 1), with i in [0, 63]. u has nothing to do with any VMI address, yet LegalizePTOVMIMemoryAccess fails on it. The root cause is the analyzer-aware traversal introduced in #3512—it eagerly binds scalar definitions into the analysis context, and when IntSet evaluates cast endpoints, if another sub-analyzer has already installed an underestimated bound, the wrapping cast throws.

The fix is to skip unsafe analysis during lowering (2 files, +571/−13). This kind of “analyzers contaminating each other’s assumptions” problem is the most time-consuming in a compiler after a major overhaul: the error is reported on a scalar unrelated to the fault, and the stack does not show who installed the wrong bound first.

Source: https://github.com/tile-ai/tilelang/pull/3793

1.4 Ascend PTO: Explicit SIMD parallel loops no longer rejected by lane-layout inference (#3796)

The PTO lane-layout inference introduced in #3512 rejects existing T.Parallel nests whenever explicit SIMD instructions are written inside. The reason is that inference treats the addresses of these loops as scalar lane accesses, whereas they actually iterate over vector blocks.

A typical example is given in the PR: a T.Parallel(2, 32) nest whose loop body uses S.vld(temp[h, block * 64]) and the corresponding S.vsts(...), processing one 64-element FP32 vector per iteration. This style was legal and commonly used before inference appeared, and after inference landed it uniformly failed to compile. The change touches 5 files, +194/−17, and the approach is to preserve the legacy explicit-SIMD parallel semantics and let inference apply only to the forms it should govern.

Source: https://github.com/tile-ai/tilelang/pull/3796

1.5 Ascend PTO: Integer atomics switched to signless compatibility wrappers, signed inputs now compile (#3792)

After #3512, codegen_pto emits pto.si32/pto.si64 for TileLang integer values, while PTO’s atomic interface accepts only signless i32/i64, so T.atomic_add, T.atomic_max, and T.atomic_min on integer buffers all failed to compile (previously mentioned in the same batch of items in the last issue; landed on main at 11:27 in this window).

The fix performs local adaptation only at the generated call boundary (4 files, +111/−36): pointers and operands are reinterpreted as signless at the same width, the pointer’s address space is preserved, and the return value is restored to the logical type; min/max retain their original signed or unsigned comparison semantics. This way the logical type system established by #3512 need not be overturned, and the adaptation is confined to the atomic layer.

Source: https://github.com/tile-ai/tilelang/pull/3792

2.7 ROCm: Seven PRs opened as a series within an hour, 22 files +624/−19 (11-12)

The seven were opened in succession within one minute, from 07:56 to 07:57 (Beijing time), by the same author, all based on 72d986e1, and together form a set of HIP-side patches:

  • #3954 (3 files, +65/−2) passes compile_flags and tl.device_compile_flags into hipcc. Previously these parameters only entered the kernel cache key and did not affect actual compilation; the only thing that could change device code generation was the process-level HIPCC_COMPILE_FLAGS_APPEND.
  • #3955 (2 files, +70/−9) fixes broadcasting of 8-bit integer vectors: with 4 lanes, ICHECK hits a non-constant; with 8 and 16 lanes, it emits make_uint2/make_uint4 with one argument per byte, which hipcc rejects outright.
  • #3956 (3 files, +102/−1) adds readable errors for small-tile T.gemm. 16×32 with 256 threads walks into the MFMA macro generator and reports “Divide by zero,” or hits “Layout infer conflict” when the output of one gemm is fed directly as the A operand of the next; neither case previously had usable information.
  • #3957 (6 files, +102/−5) changes the “minimum blocks per SM” annotation on HIP from “discarded” to “emit a launch bound based on waves per EU.” The motivation includes measurements: on gfx90a, a 256×128×32 fp16 GEMM compiles to 143 VGPRs plus 128 AGPRs with occupancy 1, so it can only fit one block per CU no matter how much LDS remains.
  • #3958 (2 files, +73/−0) adds occupancy reporting to hip_resource_info. hipcc already reports Occupancy and ScratchSize, but nobody converts them into blocks per CU—which is what actually determines whether a kernel can use all the LDS it requested for two blocks.
  • #3959 (2 files, +58/−2) fixes ROCm’s reduction workspace determination. AllReduceNeedsWorkspace returns true when there are more than 32 reduction threads, while tl::AllReduce only uses a workspace when crossing a wavefront, so on wave64 a 64-thread reduction allocates a block of LDS it never touches; and because the workspace counts as a shared-memory access in the IR, ThreadSync wraps every such reduction in a barrier.
  • #3960 (4 files, +154/−0) keeps fp16 fragments actually in registers. In HIP, uint2/uint4 are structs, so vector copies into or out of local arrays degrade to memcpy, and after SROA the array still lives on the stack: on clang 18 / ROCm 6.2.4, an fp16 fragment that resides across a loop and holds 2 rows of K and V per thread consumes 80 bytes of scratch per lane.

The seven total 22 files +624/−19, covering six layers: compile parameters, code generation, launch bounds, occupancy reporting, reduction workspace, and register residency. This is the first time a systematic set has appeared since this daily began tracking ROCm.

3.3 TileFoundry: Two fixes in review — Mesh selection slicing and dimension arithmetic (11-12)

TileFoundry opened two PRs at 21:56 (Beijing time), both of the “looks right when written, miscompiles when built” variety:

#323 fixes the parser dropping slices that start at zero. When relabeling a threads[0:16] range via Mesh with layout=(16,), if the selection starts at offset 0, the parser drops the slice when constructing the new mesh, and after lowering no contains guard is emitted, so every thread in that layer runs the region; whereas the direct form with threads[0:1] as writer: preserves the slice and behaves correctly — only the relabeling path is broken.

#324 fixes dimension arithmetic in codegen. When loop bounds come from mesh coordinates (e.g. range(cta.i * 32, cta.i * 32 + 32)), CUDA codegen reports no codegen handler for DimMul on cuda.Target: the shared scalar renderer is responsible for writing loop bounds, conditions, and mbarrier phases — it handles comparisons but not dimension arithmetic — while the three CUDA emitters each maintain their own + - * / % table.

4.1 Second wave of Ascend 950 audit: eight issues concentrated on predicates and low-level SIMD surface (11-12)

During the window, the organization opened 18 new issues: 15 in the main repo, 2 in tilelang-ascend, and 1 in mlir-ascend. Of the 15 in the main repo, 8 were filed by NebulaMao in clusters by theme within a dozen or so minutes after 18:39, all running on Atlas 950 / Ascend950PR (npu-smi 25.7.rc1.10), version 0.1.15.

Taking the eight one by one: after any_sync/all_sync are exported, source generation leaves unresolved tl.any_sync/tl.all_sync calls; a legal int64 cross-warp reduce_sum emits an undefined HwReduce<SumOp,long>; T.simd.update_mask/pintlv/pdintlv do not validate predicate width and can emit nonexistent b64 helpers; T.simd.pge silently degrades to pset_bXX (via asc_create_mask_bXX) instead of pge_bXX; T.copy’s l2_cache_ctrl accepts out-of-range integers and casts them with int32 wraparound; T.set_atomic(..., dtype="int32") written as documented emits a nonexistent *_int32 CANN helper name; T.simd.vld2 accepts mismatched DINTLV widths and 64-bit dtypes, silently emitting ignored or illegal deinterleaving loads; T.ascend_pipe_barrier("PIPE_V") is silently dropped by AscendC codegen.

Compared with the 30 issues in the previous installment, this wave lands lower down: the previous round was mostly about kernel parameters and high-level semantics (block count, num_stages, dtype tables, pad_value routing), whereas this round is almost entirely on the factory functions for predicates and vector instructions at the T.simd.* layer. Together, the two rounds sweep the Ascend frontend’s “silent failure surface” all the way from parameter validation down to instruction encoding.

Sources: https://github.com/tile-ai/tilelang/issues/3992 , https://github.com/tile-ai/tilelang/issues/3993 , https://github.com/tile-ai/tilelang/issues/3976

4.2 Corresponding fixes for the audit already queued: a dozen-plus validation PRs advancing in parallel (11-12)

The audit is not one-way complaining. Among the 50 main-repo PRs under review and updated the same day, a large batch targets exactly these gaps, and they are almost all “reject illegal input” rather than “add new features”: #3973 changes hf32’s nearest_zero in the CCE backend from NEAREST_AWAY back to NEAREST_ZERO; #3972 aligns the GEMM input dtype table bidirectionally with the two codegen backends (float8_e5m2 was being wrongly rejected on the Python side); #3971 accepts the .dyn spelling of shared.l0c; #3969 rejects pad_value for non-UB destinations; #3968 advances the mask count for ND-to-NZ scatter so the loop can terminate; #3967 and #3970 switch to directly rejecting bit reductions and batch reductions instead of emitting types absent from the template; #3966 rejects PK4_B32 stores on 16-bit vectors; #3965 skips signal latency when running msprof on a non-main thread; #3963 switches to runtime tail masks for partial passes of ND-to-NZ; #3863 rejects FP4 lane counts whose packed size is illegal; #3862 folds the resolved NPU architecture into the kernel cache key.

These PRs share a highly consistent shape: first demonstrate that “this path makes the compiler emit something nonexistent or silently compute wrong,” then add a rejection at the frontend or a correct path during lowering. For a compiler that must be deployed across multiple domestic accelerators, this kind of change is worth more than new operators.

Sources: https://github.com/tile-ai/tilelang/pull/3973 , https://github.com/tile-ai/tilelang/pull/3972 , https://github.com/tile-ai/tilelang/pull/3968

4.3 Three new CUDA-side issues: cp.async two-byte, exponential layout-inference time, Pipelined explicit order (11-12)

The three new CUDA-side issues are each representative. #3988: fp16 T.gemm with M=1 and odd K goes through pipelined cp.async and still emits illegal 2-byte transfers (IsValidCPAsyncTransferBytes fails to catch it); reproducible on both 0.1.15 and main (348e807), while the regression form fixed by #2365 at the time passes—indicating there are still uncovered shapes in the same family. #3987: the time taken by tl.LayoutInference and tl.LowerTileOp grows exponentially with reused subexpressions in T.Parallel; reproduction only needs lowering under sm_120a, no kernel launch required. The corresponding fix #3997 is already queued (bounding the work of condition proofs; the same regression goes from 34.89 seconds—exceeding the 10-second compile limit—to passing). #3996: when T.Pipelined has explicit order/stage and the copy goes through a fragment intermediary, it reports “Fragment buffer access with non-zero index [1]”, yet that index in the error is not in the user program—the error message points at the wrong place.

CUDA fixes under review the same day also include #3998 (fall back to scalar MMA when the shared layout does not match the ldmatrix precondition, fixing #2642) and #3975 (perform a full-CTA barrier before automatically releasing single-CTA TMEM; warp 0 previously did not wait for other warps to finish using it).

V. Trend Observations

First, the cleanup period after a major overhaul is longer than the overhaul itself, and the cost falls on “previously legal programs no longer being legal.” #3512 replaced PTO’s vectorization and type system together, and the four consecutive windows since have all been patching its regression surface: execution backend default switch (11-11), integer atomics (11-11, 11-12), explicit SIMD parallel loops and scalar cast facts (11-12), VMI descriptors (11-12). What these four categories of issues have in common is not “new features computing wrong results” but “old code no longer compiling or producing changed results.” For compiler projects, the debugging cost of such regressions far exceeds that of new-feature bugs—the error location is often on a scalar or address unrelated to the fault, and the stack trace gives no indication of who first installed the wrong assumption.

Second, the backend matrix has shifted from “one player advancing alone” to “multiple players starting simultaneously,” and the forms have differentiated into four categories. This issue’s five commits in the main repo are all on Ascend, but in the same window ROCm opened seven commits in one series, Hygon produced ten commits on one branch in a single day, Sunrise is running its release pipeline, and Hexagon is pushing TileLang to mobile DSP in the form of a personal fork. The four forms (upstream built-in backend, vendor adaptation repo, independent distribution, third-party fork) correspond to four depths of investment, and this differentiation itself is a usable indicator of each vendor’s degree of dependence: vendor repos track versions, distributions track the mainline, forks track their own hardware.

Third, “engineering for agents” is beginning to appear at scale. The harness branch of mlir-ascend gained +7,632 lines in one day, consisting of a skill library, a simulated trace workflow, and a Roofline calculator, serving “people or agents who write operators” rather than the compiler itself; in the same week, the README of the Hexagon fork explicitly states that the backend and models were rewritten by AI agents under the maintainer’s guidance, with 75 PRs in four days accounting for over 80% of the current code. The two developments point in the same direction: the abstraction layer of DSLs like TileLang happens to fall at the granularity where “agents can write it correctly,” so the ecosystem is beginning to lay out toolchains for agents rather than just documentation for humans. This item is worth tracking weekly.

Fourth, the four RISC-V sources have been silent for six consecutive windows, forming a stark contrast with overall activity. The TVM route, the MLIR route, the community index page, and the Sophgo TPU—all four upstreams remain at their original references, while in the same period the main repo merged five commits in a day, ROCm opened seven at once, and third-party forks are advancing a new hardware backend. Beyond the four sources, the CPU line (Weft) has not been updated since reaching an interim conclusion on 11-11. The judgment is unchanged: TileLang work on the RISC-V side remains at the stage of “routes exist, commits are few,” and the truly trackable touchpoint is still whether those two mutually independent implementation routes continue to advance.
