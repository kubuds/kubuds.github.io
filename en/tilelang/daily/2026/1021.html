I. Core Project Progress

1.1 Main repo: Vectorization analysis incorporates non-zero loop lower bound (#3579)

Merged on 10-21 00:27, 10 files +818/-198, following up on the guard fix in #2819 and closing issues #2669 and #2616. The original implementation compared f(i) with f(floor(i / W) * W) to determine whether an expression has the same value within each vector group, which implicitly assumed the loop starts at 0; when the loop lower bound is non-zero, unit-step vectorization would compute addresses of different lanes as the same group, invalidating the proofs for broadcast loads and whole-group shared conditions. The new determination incorporates the loop minimum into the analysis and preserves nested guards when hoisting mixed-precision conversions. This is a compiler defect that would silently change numerical results.

Source: https://github.com/tile-ai/tilelang/pull/3579

1.2 Main repo: Cross-thread WAW detection for shared memory (#2821)

Merged on 10-20 23:41, 3 files +153/-19, fixes #2698. On shared memory, S[tx] and S[tx + 10] are two addresses for a single thread, but writes from different threads can overlap; the original WAW check reused the same thread variable for both accesses, thus missing detections and failing to insert barriers. The fix uses two distinct thread instances for same-iteration WAW and renames their respective Bind definitions, reusing the existing RAW/WAR model, while loop-carried WAW retains the original handling. Tests cover both “should insert” and “should not insert” cases, including guarded writes, Bind-derived indices, disjoint partitions, and threadIdx.y/z permutations; 95 cases pass across the thread-sync and issue test suites.

Source: https://github.com/tile-ai/tilelang/pull/2821

1.3 Main repo: Unsupported MMA tiles require explicit K padding (#2818)

Merged on 10-20 16:41, 5 files +57/-14, fixes #2715. The generic MMA emitter could silently shrink the K atom before constructing operand layouts, causing FP16 K=8 to produce incorrect results; irregular sizes such as K=20 and K=28 failed directly at the shared memory layout inference stage with unclear messages. Now the tile’s K is validated against the architecture-fixed K atom at emitter initialization, throwing ValueError if not evenly divisible, with the input dtype, the required divisibility relation, and the suggested padding value (e.g., FP16 K=20 on SM80 reports atom 16 and suggests padding to K=32 with zero-filled extra elements).

Source: https://github.com/tile-ai/tilelang/pull/2818

1.4 Main repo: fragment reduce supports keep-dim targets (#2815)

Merged on 10-20 16:35, 8 files +343/-63, fixes #2530. T.reduce_sum and similar crashed at compile time when reducing (64, 64) along dim=1 to (64, 1) (Check failed: vars.size() == InputDim() (2 vs. 1)). Yet the documented contract in reduce_op.py explicitly accepts both [X, Y] and [X, 1, Y] output shapes and already constructs the corresponding expected shapes, so this was a backend gap rather than misuse. The fix teaches both lowering paths and preserves the original behavior for targets without keep-dim.

Source: https://github.com/tile-ai/tilelang/pull/2815

1.5 Main repo: TIR predicates rewritten in sync with integer bitwidth promotion (#3550)

Merged on 10-20 09:59, 4 files +950/-27. After integer indices are promoted to a wider bitwidth, bounds checks guarding buffer accesses were still computed at the old bitwidth, theoretically allowing out-of-bounds accesses to pass. A new IndexPredicateRewriter records promotion information for each access in ConfigIndexBitwidth and FlattenBuffer, then rewrites the relevant guards after the access statement is processed; matching is restricted to equivalent addition and multiplication forms, preserving unrelated conditions, data-value expressions, and fixed-width bounds. Five new test categories are added: index promotion, guard rewriting, access scoping, vector endpoints, and conflicting promotions.

Source: https://github.com/tile-ai/tilelang/pull/3550

1.6 Main repo: CuTeDSL scan adds participating-thread offset (#3576)

Merged on 10-20 12:49, 2 files +30/-6. The shared memory scan lowering introduced a participating-thread offset in #3536, but the CuTeDSL-side helper still generated calls with the old constructor arguments, so tl.CumSum1D(32, False, 0).run(...) directly raised a constructor argument error; the codegen assertion that broke in the same batch was also the source of the two CUDA CI failures in #2815. The fix adds an optional thread_offset (defaulting to 0 for compatibility) to the 1D and 2D cumsum/cummax helpers, subtracts the offset before selecting participating lanes and warps, and marks CUDA-specific tests with requires_cuda.

Source: https://github.com/tile-ai/tilelang/pull/3576

1.7 Main repo CI: Performance regression job pinned to H100 (#3569)

Merged on 10-20 16:00, 1 file +15/-1. The PR regression bot compares per-kernel latency against a baseline, and the numbers are only meaningful on the same GPU model used to collect the baseline. The organization is introducing self-hosted H20 capacity machines for regular correctness CI, whose label set overlaps with the existing [self-hosted, nvidia]; without differentiation, benchmark jobs would be silently picked up: H20’s FP16 dense throughput is about 148 TFLOPS, roughly seven times lower than H100’s ~990 TFLOPS, and its FP64 path is also heavily cut down, so every benchmark would report non-existent regressions. The pr-regression job is now required to carry the h100 label and to verify before starting that the assigned GPU is indeed an H100, failing fast on a mislabeled runner rather than publishing misleading numbers.

Source: https://github.com/tile-ai/tilelang/pull/3569

II. Multi-Backend Adaptation (Ascend / MetaX / Hygon / Moore Threads)

2.1 Ascend Main Repo: L0 Local Copy Supports Explicit Pitch (#3511)

Merged on 10-20 14:16, 24 files +1458/-187, the largest Ascend-direction change in this window. Previously a GEMM tile could only be filled by a single L1→L0A/L0B copy, non-zero destination origins were rejected, and each copy derived a compact pitch from its own region, so two halves moved separately could not be assembled into the target whole block; MajorK/MajorMN transposed loads were also restricted. Adds an Ascend-specific parameter T.copy(..., l0_pitch=...) to specify the L0 pitch per fractal block, with the caller supplying the consumer GEMM’s compact pitch (including dynamic tail blocks); omitting the parameter preserves the original behavior for compact regions. In the example, both halves of the 64-row A tile specify l0_pitch=4. Also handles lowering of aligned destination offsets, physical boundary and transpose-group validation, and allocation and buffer version spacing.

Source: https://github.com/tile-ai/tilelang/pull/3511

2.2 Ascend Main Repo CI: Split Build and Test Within a Single Check (#3564)

Merged on 10-20 12:06, 1 file +61/-9. Consolidates Ascend build and test results into a single Test for Ascend PR check, presenting failure stages step by step and listing each stage’s conclusion in the workflow summary. The CANN environment is set up once and built once; the AscendC examples, PTO examples, and Ascend unit tests run as three separate steps of the same job. When the build succeeds and the workflow is not cancelled, a failing suite does not stop the remaining suites, and the overall result is still marked as failed. CANN variables are passed via GITHUB_ENV.

Source: https://github.com/tile-ai/tilelang/pull/3564

2.3 Ascend Repo: DSA Sparse Fine-Tuning Backward Operator indexer_bwd (#1887)

Merged on 10-20 15:26, 2 files +1294. Adds indexer_bwd for the Ascend NPU, serving DSA sparse fine-tuning, supporting both the AscendC and PTO backends. The operator computes gradients of the lightning-indexer KL fine-tuning loss with respect to dIndexQ, dWeights, and dIndexK, and supports variable-length packed sequences. The implementation has three tiers: a fast kernel with persistent GEMM targeting contiguous and shared-row index layouts, with pipelining and fewer transfers; a general kernel supporting arbitrary index layouts, including gradient accumulation for -1 invalid indices; and a separate cast kernel for precision conversion.

Source: https://github.com/tile-ai/tilelang-ascend/pull/1887

2.4 Ascend Repo: SiTU-GLU Backward Operator (#1877)

Merged on 10-20 15:22, 5 files +854. Semantics align with CANN ops-nn’s aclnnSituGluGrad, used for the gated-activation backward of Kimi K3 Stable LatentMoE: t = tanh(gate / beta), s = sigmoid(gate), situ_a = beta * t * s; the upstream branch takes tanh or passes through depending on whether linear_beta is positive, outputting grad_gate and grad_up. The accuracy baseline is an independently implemented fp64 PyTorch reference, cross-validated against the official aclnn on 910B3, with a maximum relative error of about 3e-3, consistent with bf16 rounding expectations.

Source: https://github.com/tile-ai/tilelang-ascend/pull/1877

2.5 Ascend Repo: cann-bench Adds LSTM and GRU (#1892 / #1902)

Both merged the same day, +2304 and +2267 respectively. LSTM covers the i/f/g/o four gates and cell-state temporal recurrence, supporting multi-layer stacking (numLayers ≤ 8), bidirectionality, batchFirst layout, projection dimensionality reduction (projSize > 0, LSTMP), and optional bias; weights are passed as a TensorList with “one tensor per layer per direction”, outputs are (y, hn, cn), and the implementation consists of 12 @tilelang.jit kernels. The main path uses the fused seq path, with one launch per (layer, direction); within the kernel, T.serial(S) iterates over time steps to complete the dual GEMM, bias broadcast, gating, and state update, while the x-side gating contribution unrelated to recurrence is precomputed in parallel across all time steps by a separate xgemm. GRU consists of 8 kernels: the combined z/r/n three-gate GEMM runs on Cube, gating and state updates run on Vector, cross-core data is relayed through a GM workspace, and AUTO_SYNC is manually disabled—according to the commit description, automatic mode generates about 58 PipeBarriers per time step.

Source: https://github.com/tile-ai/tilelang-ascend/pull/1892, https://github.com/tile-ai/tilelang-ascend/pull/1902

III. Ecosystem and Adopters (TileOPs / TileFoundry / Operator Libraries)

3.1 TileOPs: Paged GQA forward switched to paged warp-specialized program (#2668)

Merged 10-20 22:41, 8 files +901/-103. The new GQAPrefillPagedWSKernel (SM90) takes over GQAPrefillPagedWithKVCacheFwdOp: a single append launch writes chunks into pages (keys rotated under fused RoPE, both quantized on the FP8 pool) and rotates the query, after which the warp-specialized program in GQAPagedFwdOp performs attention over the enlarged cache. The program serves head dim 256 (single query slot) and query groups wider than 16 heads on a single KV head (flattening the (T * H, D) query into rows); pools of dims 64 and 256 not covered by the FP8 program are read via the 16-bit page mirror, capped at 4 GiB per call; when a request may be split, requests are sorted by cache length, longest first, up to 128 requests.

Source: https://github.com/tile-ai/TileOPs/pull/2668

3.2 TileOPs: FP8 lightning indexer switched to dual-warpgroup consumption (#2666)

Merged 10-20 22:41, 6 files +448/-2. The original implementation had one warpgroup multiply a 64-key tile, then ran an epilogue as long as the product (per-head key scale, FMUL and FADD separate); there was also a clean sweep writing -inf outside the window at 2.5 TB/s—per the commit message, this accounted for 425 of the 472 microseconds in chunk-prefill-kscale; in the decode call a single query occupies one CTA across all 16384 keys, taking 289 microseconds. The new FP8LightningIndexerWSKernel (SM90) uses a TMA warp to stream 64-key tiles to two consumer warpgroups in alternation, one m64n256 FP8 WGMMA per tile, with the consumer epilogue consolidated into a csrc helper.

Source: https://github.com/tile-ai/TileOPs/pull/2666

3.3 TileOPs: MLA decode moves to the offset seesaw program (#2665)

Merged 10-20 22:39, 7 files +881/-590. MLADecodeSeesawKernel (SM90, 512 + 64 latent, single KV head) takes over MLADecodeWithKVCacheFwdOp, following the offset seesaw approach of MLAPagedFwdOp and reading k and k_pe per request via TMA; the program body moves to
kernels/attention/mla/seesaw.py, providing both paged and dense entry points, and the split construction of MLAPagedFwdOp produces the same storage as before. A request’s keys are cut into a number of runs given by the smaller of the SM count per block and half the tile count, merged with log-sum-exp; the dense path keeps partial results per output dtype, with 16-bit outputs staged in a warpgroup-owned key buffer and then written out via TMA.

Source: https://github.com/tile-ai/TileOPs/pull/2665

3.4 TileOPs: Tensor core ceiling changed to the operand-set envelope (#2661)

Merged 10-20 22:27, 4 files +125/-82. Nightly run 39299002056 flagged GemmW4A8FwdOp at 105% and 108% of the tensor_core.fp8 ceiling; investigation showed the ceiling itself was too low: the original calibration took cuBLAS throughput on random operands, but under a 700 W power cap the operand values directly determine clocks, so a kernel drawing less power than random cuBLAS can run above that rate. gemm_throughput.py now also times all-zero operands, records the best rate per operand set in calibration_operands, and takes the maximum as the calibrated value—consistent with the existing envelope rule for HBM calibration; h200.yaml is re-labeled accordingly.

Source: https://github.com/tile-ai/TileOPs/pull/2661

3.5 TileOPs: Backend tests and torch-compile baseline runnable on non-CUDA devices (#2658)

Merged 10-20 13:17, 10 files +241/-48, fixing three TileOPs-side failures exposed by the MTT S5000 run in #2595. First, torch_musa renames PrivateUse1, so readers registered as "privateuseone" in test_backend.py and test_kernel_dispatch.py could not read it; they now resolve the device type through the privateuseone name directly. Second, torch_musa prints on import, breaking import checks that compare the entire stdout; a new tests/fresh_interpreter.py reads only a single marked result line, and seven such checks are switched over uniformly. Third, the torch-compile path without Triton is restored on non-CUDA environments.

Source: https://github.com/tile-ai/TileOPs/pull/2658

3.6 TileOPs: SM89 single-row single-column routed to vector GEMM (#2660)

Merged 10-20 10:35, 3 files +87/-11. Extends the existing CUDA-core GEMV implementation to SM89: the single-row left operand with transposed weights and the single-column right operand without transpose reuse the same kernel body, while the two-row crossover point remains calibrated for SM90. Tuning candidates are also filtered by the selected device’s shared memory budget, with the largest accepted staged ring at 96 KiB; the generated program declares at most 192 bytes of reduction scratch; single-row/single-column inputs whose contiguous storage starts at an unaligned element offset are handled by the existing alignment helper.

Source: https://github.com/tile-ai/TileOPs/pull/2660

3.7 TileOPs: Three builder cache and tuning contract fixes (#2662 / #2663 / #2664)

All three merged 10-20 13:16. #2662 adds a 32-entry LRU cache to the SM89 FP8 grouped GEMM builder, aligned with the existing SM90 builder and repo conventions, so repeated calls with the same four shape parameters reuse the JIT factory; #2663 adds the same 32-entry LRU to the two builders for dense GLA subchunk prefill, with the cache key retaining shape, scale, activation dtype, and gate dtype, and the launch thread config left as an inner factory parameter; #2664 restores the 12-input contract of the paged GQA ordinary tuning supplier—it previously expected 8 inputs but returned 9, missing three query/key/value scales, and removes the unsupported num_split candidate key. All three declare no device-side performance claims and unchanged compute bodies.

V. Trend Observations

Compiler correctness became the main theme of this window, rather than feature expansion. Of the 9 merges into the main repo, 5 were silent-bug cleanups: vectorization assuming loops start at zero (#3579), missed shared-memory WAW detection (#2821), the MMA emitter silently shrinking the K atom (#2818), a crash in fragment reduce with retained dimensions (#2815), and predicates not following index bit-width promotion (#3550). What these defects share is that they do not raise errors—they only produce wrong results or miss barriers—making them the hardest class for users to locate in production. On the same day, TileOPs’ #2661 was also fixing the “performance ceiling definition,” indicating that the project now treats “trustworthy numbers” as an engineering goal on par with “running fast.”

The Ascend line is shifting from filling in examples to the training side. Three of the five merges are backward or recurrent operators (indexer_bwd, situ_glu_grad, LSTM/GRU), and situ_glu_grad directly aligns with the gated activation of Kimi K3 Stable LatentMoE and provides cross-validation data against aclnn on 910B3. Together with #3577’s alignment of DeepGEMM-Ascend configuration selection and the epilogue, Ascend-side coverage is expanding from inference forward passes to training backward passes, state recurrence, and large-model MoE gating.

PTO is becoming a second execution path alongside AscendC. #3512 under review is a 21k-line vectorization framework (T.Parallel → PTO VMI, targeting Ascend 950), #3516 proposes making tvm_ffi the default execution backend for the pto target, and together with a set of copy and predicate fixes in #3530, #3573, #3581, and #3582, the engineering effort on the PTO line has clearly exceeded the scale of isolated patches. At the same time, the main repo uses #3511 to add L0 local copy capability on the AscendC side—the two paths advance in parallel rather than one replacing the other.

The toolchain is spilling over into standalone repos. Within a single day, three new repos appeared (the Chinese tutorial, the CANN community operator repo, and the Hexagon backend experiment) along with a VS Code extension, and the main repo moved lower trace entirely to devkit (#3583, removing 4,390 lines). Community-side expansion is now outpacing the main repo’s module boundaries, consistent with the July “multi-backend language dialect” refactoring direction: the main repo narrows to semantics and IR, while tools and backend experiments move outside.

The explicit definition of CI criteria is worth noting. #3569 locks performance regressions to H100 and fails fast on mislabeled cards, #3564 splits the Ascend build and tests into separate steps of the same check, and #2661 relabels the tensor-core ceiling using an operand-set envelope—all three are about “making numbers comparable,” which directly affects the admission threshold for subsequent PRs.
