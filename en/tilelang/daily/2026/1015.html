I. Core Project Progress

1.1 Main Repo: Ascend Wraps Up Four Areas — Independent AIV Execution (#3485), PTO DeepGEMM Codegen (#3330), Cross-Warp Allreduce Fix (#3494), Example Target Selection (#3474) (10-14)

Date: 2026-10-14　Source: Independent AIV (#3485) / PTO codegen (#3330) / allreduce fix (#3494) / example target selection (#3474)

  • Independent AIV execution (#3485): Extends Ascend AutoSchedule so that AIV0 and AIV1 can execute different work under sid-dependent control flow — supporting alternating epilogues, dequantization/epilogue division of labor, disjoint input partitioning, and in-loop role switching. The implementation moves AssignCore ahead of latency estimation and scheduling, establishes independent identities for AIV-local UB buffers and scalar state, and models pipeline resources, special register dependencies, UB capacity, and synchronization flag banks per participating core; the unified-kernel collective path and one/two-AIV launch geometry are preserved. L0C→UB copies still execute on the AIC.
  • PTO DeepGEMM codegen (#3330): Tracks tl.ascend_set_mmad_direction across control flow and encodes the effective direction onto MAD instructions, rejecting MADs reachable under conflicting directions; supports SIMD post-increment loads (returning both data and an updated pointer), UB address-to-PTODSL pointer conversion in mixed AIC/AIV kernels, dynamic L0C→UB dimensions and strides, and int16 signed packed MX scale; improves code generation for conditional expressions and runtime loops. Reports 14 of 15 DeepGEMM PTO cases passing, with test_bf16_m_grouped_padding still blocked because the PTOAS VPTO backend cannot legalize FP32→BF16 conversion.
  • Cross-warp allreduce fix (#3494): When a cross-warp allreduce call covers multiple independent reduction groups, the ascend and pto targets incorrectly delivered the first group’s results to all groups; this fix addresses the correctness issue (follow-up to #3469).
  • Example target selection (#3474): Removes hardcoded target="ascend" from Ascend examples and tests, deferring instead to the TILELANG_DEFAULT_TARGET environment variable; the DeepGEMM JIT entry point supports execution_backend="auto"; CI runs the Ascend example suite once each with the ascend and pto targets, and documentation spells out how selection works.

1.2 Main Repo: Three Infrastructure Items — CPU OpenMP Parallel Grid Loops (#3109), C-Family Codegen Shared Emission (#3289), Windows NVCC Switches to MSVC (#3510) (10-14)

Date: 2026-10-14　Source: CPU OpenMP (#3109) / codegen sharing (#3289) / Windows MSVC (#3510)

  • CPU OpenMP parallelization (#3109): Adds optional OpenMP parallelization of grid loops for the CPU backend — introduces MaterializeCPUParallelGrid to convert annotated CPU grid loops into parallel loops, with loop collapse, thread count configuration, minimum trip count thresholds, and allocation sinking; adds OpenMP compile flags and pass configuration options for Linux / macOS / Windows; tests cover correctness, pragmas, allocation sinking, thresholds, and the single-dimension case. The CPU backend gains grid-level parallelism for the first time.
  • C-family codegen sharing (#3289): Introduces CodeGenTileLangCBase to unify CUDA, HIP, CPU C, Ascend C++, Metal, and C host code generation; fixes an issue where T.import_source, T.Kernel(prelude=...), and pragma_import_c swallowed the next generated line when the source text lacked a trailing newline or ended with a backslash; imported content is ordered as “headers → imports → generated declarations and functions” with two separating newlines guaranteed. Verification: 83 focused regression tests pass, 405 related codegen and launch suite tests pass.
  • Windows NVCC switches to MSVC (#3510): NVCC rejects the clang-cl selected by get_cplus_compiler() — instead selects cl.exe from the NVCC subprocess environment (without changing host C++ compiler selection), adds a VS 2026 18/* fallback path, and no longer passes -ccbin=None on non-Windows platforms; under CUDA 13.3 the reproduction case fails before the fix and compiles successfully after.

Date: 2026-10-14　Source: ROCm scan (#2326) / test infrastructure (#3502) / CodeRabbit labels (#3513)

Verification: the CUDA scan suite passes 17 tests on B300, and 2 CuTeDSL source generation tests pass; AMD-side runtime verification is left to ROCm CI.

III. Ecosystem and Adoption

3.1 TileOPs: Foundry performance batch closes out 11 PRs — softmax / pooling / normalization / reduction all rolled out (10-14)

Date: 2026-10-14　Source: softmax (#2570) / three pooling PRs (#2572 / #2573 / #2579) / three normalization PRs (#2576 / #2581 / #2585) / two reduction PRs (#2571 / #2578) / two GEMM and Elementwise PRs (#2582 / #2577)

  • softmax (#2570): Added 16-byte L2 evict-last load tileops::load16_evict_last; whole-vector rows (up to 64 elements per thread) now use register-resident _held_row, folding max and sum via warp shuffle; SoftmaxWarpRowsKernel covers rows up to 2KB, and both the register and shared-memory paths of SoftmaxOnChipKernel use the new load. 39 of 42 SoftmaxFwdOp rows lead the fastest baseline by 1.1% to 78.1%, with (32768, 65536) float32 matching quack; the two lm-head rows still trail (0.909x / 0.934x).
  • Three pooling PRs: #2572 MaxPool1dIndices — new load_evict_last scalar load, adjacent outputs stored as vectors, sincnet-local at 1.009x / 1.006x versus torch-compile and 1.049x faster than the older kernel (float32); #2573 AvgPool3d — windows with fixed divisor and taps ≤32 now read all taps in one pass (L1/L2 evict-last) and use select to exclude out-of-domain values, while non-power-of-two fixed divisors go through float32(float64(sum) * float64(1/divisor)) with no slow-path branch, producing bit-identical results to PyTorch; #2579 MaxPool3dIndices — float32 tile-aligned windows process two adjacent outputs per thread, with values/indices stored as vectors, cutting c3d-pool1 from 170.1 µs to 166.0 µs.
  • Three normalization PRs: #2576 RMSNorm — split into four bodies by row width (256 to 2048 elements use warp row splitting, above 4096 use whole-vector register residency, above 16384 use two passes, the rest use fragments), with both the jit builder and autotune selecting tuning spaces by body; #2581 InstanceNorm — whole-vector rows (up to 2048 elements) use one warp per row and 8 rows per block, with all 12 InstanceNormFwdOp rows matching or leading, and three wider-channel rows rising from 0.980x-0.988x to 1.042x-1.108x; #2585 follow-up — warp rows capped at 1024 columns, fewer rows per block for small batches (down to 1 row) to guarantee at least 128 blocks per grid, and three training paths switched to reciprocal division to align with torch mean.
  • Two reduction PRs: #2578 any/all — float16 / bfloat16 / float32 rows are read as 32-bit words and tested with bitwise ops (sign-bit mask, with -0.0 treated as 0 and NaN as non-zero), and warps of 16 or fewer are folded serially by lane 0; #2571 group tile counting — the GroupTiling prefix sum for varlen and grouped grids now uses intra-CTA inter-warp shuffle scan (keeping the loop for 8 groups or fewer), using 62 registers instead of 152 for 4096 groups at 32 threads, benefiting all GroupTiling callers (GQA / MLA / FP8 varlen, paged GQA, varlen key RoPE, grouped GEMM, GLA/GDN/KDA varlen).
  • GEMM and Elementwise: #2582 grouped GEMM — tile epilogue can alternate between two staging buffers (continuing to the next tile while stores are in flight), and the producer warp-group keeps only one warp issuing copies, with all four MoE workloads leading quack (fwd 1.015x, dgrad 1.012x, wgrad 1.033x; previously main was 0.936x-0.968x and 0.869x); #2577 SiluAndMul — both halves use load16_evict_last, and fixes an error when input is not 16-byte aligned (vector_aligned).

3.2 TileOPs: Four linear attention and MoE PRs — KDA prefill inversion, GLA backward memory, expert search skip, permute bounds (10-14)

Date: 2026-10-14　Source: KDA prefill (#2584) / GLA backward (#2569) / MoE search skip (#2575) / permute bounds (#2559)

  • KDA prefill inversion stabilization (#2584): KDA prefill failed under correlated keys — main failed on 6 chunk cases and 2 fused cases (including NaN); the fix solves in FP32 using 16-row diagonal blocks and reuses existing shared buffers for block products, keeps gated prefixes in FP32 registers, stores only reference rows in shared metadata, and removes mixed-dtype shared views that went out of bounds under TileLang 0.1.12; chunk and fused prefill share the inversion helper, with 4 regression cases added (two half-precision types × two paths × partial chunks). sm89 benchmarks (against the FLA 0.5.2 external baseline) pass FP64 comparison for both outputs and final state.
  • GLA backward memory reuse (#2569): On SM89, the shared memory request for FP32 chunk32/K64/V192 drops from 131072 to 98304 bytes, falling within SM89’s 101376 limit (reusing the state buffer after both dh consumers finish, adding a block barrier before loading h); an asymmetric FP32 regression was added. Note: this fixes a launch failure, but speed remains slower than FLA (0.0942 / 0.4164 ms versus FLA’s 0.0550 / 0.1494 ms at 256 / 2048 tokens), and the PR explicitly does not claim a speedup.
  • MoE expert search skip (#2575): Once the tight per-row MMA tile finds its owning expert, binary search over the remaining expert boundaries stops (the old logic still ran a lookup for every remaining expert); group sentinels are reused, tiles that miss still search all experts, and the physical prefix-sum / alignment / masked path behavior is unchanged. sm89 (RTX 6000 Ada) benchmarks cover the K512/N256 tight-row scenario.
  • permute-align bounds (#2559): Bounds and correctness fixes for the case where all 12 rows trailed vLLM’s moe_align_block_size — errors out instead of producing wrong results when threads is not a multiple of 32, empty routing calls return num_tokens_post_pad=0 for any expert count, out-of-range expert_ids are padded to values beyond the expert count, the verifier and docs align on the result set, and the expert loop gains bounds and per-block scatter range reservation.

V. Trend Observations

5.1 All-Backend v0.1.15 Alignment Nearing Completion

  • After upstream v0.1.15 (09-30) was released, MetaX caught main up to the v0.1.15 node on 10-13, and Hygon completed a full upgrade via #20 in this window and established a release branch — both backends aligned within two weeks of each other, with Hygon bringing block-scaled GEMM layout planning into the new baseline during the upgrade. Moore Threads remains stalled after 09-30, while Ascend is subsequently filling in API documentation item by item through “documentation fact-checking.” The multi-backend “same version, same semantics” foundation is converging.

5.2 The Main Repo’s “Infrastructure Day”: Compilation-Surface Refactoring and Platform Rollout

  • More than half of the 10 merges in a single window are compilation and platform infrastructure: C-family codegen sharing (unified base classes for CUDA / HIP / CPU / Ascend / Metal), CPU OpenMP grid parallelism, Windows MSVC toolchain, test infrastructure caching, ROCm scan wavefront — plus four new PTO/Ascend repos opened. During the release quiet period (15 days without a new version after v0.1.15), firepower is clearly directed at low-level extensibility and new platform support, which is mutually reinforcing with the rhythm of “MoE/performance merges → foundation growth → new version.”

5.3 Nightly Foundation +41: Tests Expand in Sync with Merges

  • The single-day +41 correctness items mark the largest increase in the past week, corresponding one-to-one with the 16 TileOPs merges (performance batches generally carry test-node additions, attention extensions carry new workload rows). The rolling accounting of “one merge, one foundation increment” continues to deposit verification of each change into nightly snapshots — static preparation before release continues to accumulate steadily.

5.4 Ascend Repo’s Rollback Discipline: Even Low-Priority Cases Are Guarded

  • The first three “documentation fact-checking” PRs were rolled back entirely due to abnormal regex mismatches in low-priority expected-failure cases, then redone in trimmed form — exposing a two-tier verification structure where “CI does not run low-priority cases at the PR stage, with the daily full suite as backstop.” This “rollback—redo” rather than “push forward with wounds” handling shows that CI governance in the Ascend adaptation repo is shifting from “all pass” to “precise assertions, unified criteria,” and also means that merge quality within the window is continuously constrained by daily full runs.
