Today’s Highlights

This window saw only 6 merges in the organization, another third down from the previous period’s 9, but the structure matters more than the number: 3 of the 6 landed in the main repo, all on Ascend, with not a single one on CUDA or CPU. The largest is #3516 (20 files, +1549/−182), which promotes tvm_ffi to the default execution backend for the pto target—previously target="pto" went through the Cython launcher; now execution_backend="auto" resolves directly to tvm_ffi, with shared host codegen generating MakePackedAPI and C host, and the Ascend runtime launching the aibin compiled from PTODSL via aclrtLaunchKernelWithHostArgs, matching the path used by AscendC kernels. Alongside is a module-level toolchain callback: the entire PTODSL module is compiled in one pass within the device build step (ptodsl → ptoas → bisheng fatobj-link → extract .aicore_binary), with results keyed by ptoas parameters, ptoas version, and CANN identity. The old path is retained as execution_backend="pto", with bit-identical output from both.

The second, #3776, is a tightening on the solver side. AutoSchedule previously started its bisection from a fixed period lower bound; this change takes the maximum of three necessary conditions: the single-task bound uses the maximum of each task’s initiation interval; the resource-group bound sorts pairwise-conflicting tasks by residual value and derives from adjacent differences and head-to-tail differences that the period is no less than the sum of initiation intervals; the self-dependency bound solves S_u - S_u >= wait - d*P backwards to obtain a period no less than ceil(wait/d), with version-dependent distances further scaled by num_stages. No additional lower-bound probing was introduced, and the scheduling model is unchanged. Empirical results on the weekly build of Ascend 950PR with CANN 9.3.0: with compilation caching disabled and one warm-up plus three measured runs alternating, all Ascend examples compile successfully with unchanged scheduling results, and cumulative Z3 solving time drops 10.04%.

The third item is not in the main repo. Hygon’s distributed trio #36 (6 files, +2022/−0) merged into the distributed branch rather than main at 16:20, comprising three compute-communication fused operators: a Block-Push version of GEMM + AllReduce, a Block-Push version of GEMM + ReduceScatter, and a Block-Pull version of AllGather + GEMM, with performance data and implementation notes in the README. The same day, #37 opened HCU’s ds_read_vector Alt2 and LDS layout inference. This line runs from the 10-29 push-wave reduce-scatter example all the way to the fused operator list—the first time the Hygon repo has done distributed work systematically.

The fourth item is a concentrated burst on the quality side: of the 35 new issues in the window, 30 landed in the main repo, 26 of them aimed squarely at Ascend. Two accounts each filed a dozen-plus between afternoon and late night, highly consistent in form—not “it ran wrong” but “it should have errored yet passed silently”: T.Kernel accepts zero or negative block counts, T.alloc_l1 accepts a 2 GiB allocation, T.Persistent accepts negative waves and stages, T.unroll accepts −1 and emits #pragma unroll -1, and negative tensor dimensions crash the compiler outright. I. Core Project Progress

1.1 Ascend: PTO target default execution backend switched to tvm_ffi; whole module compiled and cached at device build stage (#3516)

#3516 (20 files, +1549/−182) is the largest change this period. The substance of the change is migrating the pto target from a “dedicated Cython launcher” to “the same host path as AscendC”: when target="pto" is paired with execution_backend="auto", it resolves to tvm_ffi, the shared host codegen handles MakePackedAPI and C host construction, and the Ascend runtime module launches the aibin produced by PTODSL via aclrtLaunchKernelWithHostArgs.

On the device build side, a new module-level toolchain callback compiles the entire PTODSL module in one pass: ptodsl frontend output, ptoas lowering, bisheng fatobj linking, then .aicore_binary extraction, with artifacts cached by aibin. The cache key incorporates ptoas parameters, ptoas version, and CANN identity together—this point is critical, since previously such keys omitted the toolchain version, causing cross-CANN upgrades to hit stale artifacts.

Validation coverage is broad, with four new test groups: auto resolving to tvm_ffi, callee-allocated outputs, dynamic shapes and dynamic outputs, multi-device kernels, dynamic shared memory, cube/vector mixed GEMM, source accessor, exported libraries, host-side loop launches, and host-side profiling ranges; additionally, equivalence tests bit-compare tvm_ffi against the old pto on three kernels—vecadd, multi-kernel, and dynamic shared memory; two cache test groups cover binary caching and kernel caching respectively, including cache hits skipping the toolchain, corrupted entries raising errors, and hits in a fresh process. The old path is retained as planned, to be retired after coverage is confirmed.

Source: https://github.com/tile-ai/tilelang/pull/3516

1.2 Ascend: AutoSchedule tightens cycle lower bound with three necessary conditions, cutting Z3 solve time by 10.04% (#3776)

#3776 (1 file, +20/−1) changes only the initial value, not the algorithm: the original bisection started from a fixed lower bound, whereas now three necessary conditions are computed first and the maximum is taken. The single-task bound retains the hard lower bound on each task’s initiation interval; the resource-clique bound targets cliques of pairwise resource conflicts, sorts task residual values in ascending order, and derives from the sum of adjacent-difference constraints and first-last-difference constraints that the cycle is no less than the sum of initiation intervals within the clique, with the clique itself greedily enumerated using each task as a seed; the self-dependency bound is solved back from S_u - S_u >= wait - d*P, with version-dependent distance bounded above by num_stages.

The empirical environment is specified in detail: Huawei Ascend 950PR, CANN 9.3.0 weekly build 20261009.01, compile cache disabled, one warm-up and three measurements alternating per configuration. There are two results: all Ascend examples compile successfully with scheduling results identical to before the change (indicating only the lower bound was tightened, not the solution), and cumulative time in the Z3 solve phase dropped 10.04%. The bisection bounds and solve-state handling are unchanged, and no additional lower-bound probing flow was introduced.

The value of such a change to upstream lies not in single-point performance but in the fact that as solver time grows with operator scale, the waste from the bisection starting point amplifies linearly—writing necessary conditions into the initial value is equivalent to saving a meaningless interval on every solve.

Source: https://github.com/tile-ai/tilelang/pull/3776

1.3 Ascend: Integer atomics adapted to signless carriers, 12 PTO cases covering 32-bit and 64-bit (#3794)

#3794 (4 files, +52/−6) fixes the fallout from #3512. That change moved signed integer types from signless i32/i64 to si32/si64, while PTO’s atomic interface requires signless carriers, so integer add/min/max atomics in SIMT kernels failed to compile outright.

The fix performs local adaptation at the generated PTODSL call boundary: pointers and operands are reinterpreted as signless at the same width, preserving the pointer’s address space, and return values are restored to the logical type; min/max retain their original signed or unsigned comparison semantics. This way the logical type system introduced by #3512 is not overturned, and the adaptation is confined to the atomic layer.

Regression cases land in test_simtvf_atomics.py under testing/ascend/language/simtvf, covering 32-bit and 64-bit add/min/max, negative operands, returning the old value, values exceeding 32 bits, and unsigned initial values with the high bit set; the 12 new PTO cases all pass on Ascend. #3792, merged in the same batch, fixes another facet of the same family of issues: T.atomic_add/max/min failing to compile on PTO due to signed inputs.

1.5 TIRx: Two in-review changes for ceildiv and split div/mod with negative scale, same root as nested floor division bug (#93, #94)

On the tile-ai/tvm side, two changes are in review within the window: #94 ([Fix][TIRx] Make ceildiv exact for signed divisors) and #93 ([Arith] Guard negative scales in canonical split div/mod). Both fix two ends of the same class of problem—once signs enter integer division and modulo, the preconditions for canonicalization rewrites no longer hold, so “exactness” and “safety” must be handled separately: ceildiv requires results to remain exact with signed divisors, while split div/mod must reject canonicalization under negative scales.

This points to the same place as #3937 newly opened in the main repo that day ([BUG] Nested floor division produces wrong integers under negative multipliers): once negative coefficients enter the rewrite chain of arithmetic simplification, boundary conditions are easily missed. The difference is that #3937 is a user-side reproduction, while #93/#94 are proactive hardening on the compiler side.

2.8 Beyond the Four Sources: TileLang–Weft Releases weft-parity, 553/553 Within 1.03× of Triton (11-11)

The CPU line recorded in the previous issue now has a conclusive version. Tianchen-ai/tilelang-weft and its benchmark repository each pushed a commit on the same day (08:51 and 08:52), changing the release tag from v0.1.15-weft.2 to weft-parity and rewriting the results table and results handbook.

The new methodology has two layers. The first is a paired comparison against Triton: all 553 items have a matching native Triton control, and each item satisfies “TileLang native time no more than 1.03× the corresponding Triton time” — SG2044 133/133, K1 137/137, K3 A100 136/136, and x86 147/147, totaling 553/553 across the four platforms. Candidate and control are measured alternately on the same batch of inputs, and the candidate is the same native library exported after passing source-level JIT numerical checks. The second layer is the ratio against external reference libraries: 543 cases have a matching reference, of which 468 are faster than the reference, with platform median ratios of SG2044 1.3598, K1 1.3176, K3 A100 1.6569, and x86 1.2917.

These two sets of numbers must be read separately from the previous issue. The previous issue recorded the old table for the same batch of cases: 41 cases faster than the reference, with an SG2044 median of 0.0580×. The two commits on the same day replaced that table wholesale, for the reason stated in the commit title — “performance inheritance from the shared compiler across four platforms.” According to the results handbook, TileLang native TIRx now imports the same Canonical compiler used by Triton–Weft, and the full packed workload preserves input preparation, encoding, integer partials, scale/min branches, and output updates. In other words, the jump comes from the measured object changing from “author-written programs” to “shared-compiler output,” not from the same implementation getting twenty times faster in a single day. This must be stated clearly when citing; the new table must not be used to overwrite the old conclusion.

There is also one correction worth noting: two Q1 controls on K3 previously used an old Triton artifact that overflowed when negating −128 — the boundary input yielded −2048, when the correct result should be 0. After the shared compiler’s exact I8 reduction was fixed and regenerated, the artifacts from both frontends pass that input; triton_historical_us retains the old timing, and triton_control_note flags the corrected comparison. This is the only disclosure in this issue of “the control itself was wrong,” and it says more about how seriously this benchmark takes reproducibility than any score does.

The technical routes still need to be kept distinct: Weft follows a CPU route that imports the TileLang native AST early into its own Canonical IR, which is not the same implementation as the TVM backend continued by the kubuds- prefixed branches or the MLIR Linalg/SCF rewrite in RuyiAI-Stack/tilelang-riscv.

III. Ecosystem and Adopters

3.1 TileOPs: Zero commits on mainline, two stacked W4A16 PRs push chunked-prefill-tile from 37.3 to 31.6 microseconds (#2895, #2896)

TileOPs had zero commits on the main branch this period, but opened five performance PRs, two of which are stacked members of the same family. #2895 (3 files, +183/−3) converts the W4A16 tile split along K into a cluster of paired CTAs: each CTA holds the rows of one consumer warpgroup, receives the FP32 partials for those rows in the peer’s shared memory via st.async, and then writes them out, so these tiles no longer launch a split-K reduction or round-trip through the FP32 workspace. On H200 at 1500 MHz, chunked-prefill-tile drops from 37.3 microseconds to 34.7 microseconds (torch dequantized matmul is 37.5 microseconds), with output bit-identical to the reduction path.

#2896 (3 files, +525/−5) stacks another layer on top: the 128-row 128-column W4A16 tile switches to a hand-written warp-specialized main loop that decodes the next K tile while the previous WGMMA is still running, and releases the ring segment only after the WGMMA reading that segment retires; since the cost model has no term for this, a calibration rule is used instead to place these tiles on four 128-wide K segments. The same benchmark drops to 31.6 microseconds, 1.19× torch dequantized matmul, with output bit-identical to the pipelined main loop.

Both PRs belong to the performance checklist in #2130, and #2896 explicitly states it is stacked on #2895 and that its commits will show alongside until the earlier PR merges.

Source: https://github.com/tile-ai/TileOPs/pull/2895 , https://github.com/tile-ai/TileOPs/pull/2896

3.2 TileOPs: FP8 grouped GEMM for DeepSeek-V3 prefill routes A scale through TMA (#2894)

#2894 (1 file, +2/−2) changes only two config entries: stage_scales for ds-v3-ep8-prefill-up and ds-v3-ep8-prefill-down goes from 1 back to 0, so their 128-row tiles fetch A scale from the TMA box added in #2865 rather than relaying through the producer. 3.3 TileOPs: softmax two-CTA cluster meets the bar, long-K NT GEMM selector change falls short (#2898, #2897)

#2898 (SoftmaxFwdOp, marked bar met) moves two 32 KB softmax rows from a cluster of four 128-thread CTAs to a cluster of two 256-thread CTAs: on SM90 every CTA slot can hold a two-CTA cluster, whereas a four-CTA cluster leaves empty slots. Two register-side changes accompany it—row maxima are fetched as packed 16-bit pairs, and each float16 element uses a single FFMA to shift by the tile’s scaled maximum; bfloat16 and float32 still subtract the max first, because their max times log2(e) would overflow fp32 range. The root cause is stated in the description: the benchmark runs H200 at 1500 MHz, and the register scheme executes 17% more instructions than quack and is issue-rate limited.

#2897 (GEMMFwdOp, marked below bar) goes the other way and missed. It targets the selector’s decision: beyond 64 K steps, a 176- or 192-wide ping-pong tile replaces the wider coop2 tile only when it covers more “output per byte of operand,” so ds-v3-prefill-o-proj switches from a 128x176/144 ping-pong to a 128x256/240 coop2. The problem is that this row runs under H200’s 700 W power wall, where time tracks energy per call: the 176-wide tile uses 2.7% fewer cycles than DeepGEMM but moves 21% more operand bytes into the SM, so it runs at a lower clock. The PR honestly marks itself as below bar; its value is in quantifying that cycle counts are not a valid criterion under a power wall.

Source: https://github.com/tile-ai/TileOPs/pull/2898 , https://github.com/tile-ai/TileOPs/pull/2897

IV. Community, Tutorials, and Events

4.1 A Systematic Audit of the Ascend Frontend: 30 Issues in One Day, 26 Directly Targeting Ascend (11-11)

During the window, 35 new issues were opened at the organization level, of which 30 landed in the main repo, 3 in TileFoundry, and 2 in tilelang-ascend. Of the 30 in the main repo, 26 had titles directly prefixed with Ascend, concentrated across two accounts: 12 from cn-sys (submitted consecutively from 15:19 to 16:14) and 13 from JINITAIMEI121 (08:31 to 10:39); the remaining one was a PTO multi-region duplicate-physical-segment report.

What these issues share is not “wrong results” but “things that should not pass yet do.” One class is parameter validation: T.Kernel accepts zero or negative block counts, T.Persistent accepts negative wave_size and num_stages, T.Pipelined accepts negative num_stages and invalid order/stage metadata, T.unroll accepts −1 and emits #pragma unroll -1, loop constructors accept zero or negative extents, negative tensor dimensions crash the compiler outright (a native crash rather than a Python exception), and T.alloc_l1 accepts a 2 GiB allocation with no capacity check whatsoever. Another class is semantic mismatch: hf32’s nearest_zero compiles to NEAREST_AWAY, the GEMM input dtype table and codegen disagree in both directions, reduce_bitand/bitor/bitxor emit types undefined in the Ascend templates, batch reduction degrades to a scalar AllReduce entry point with no batch overload, the pad_value of a GM-to-L1 copy is routed into an L1 fill that only accepts zero, a same-type ND-to-NZ scatter loops forever because the mask count does not fall back, and partial-VL rows produce a nonexistent PAT_VL<N> pattern. A third class is toolchain: vsts_pack_quarter has no 16-bit branch, so PK4_B32 stores on b16 vectors are silently dropped; module serialization discards the device source, leaving cached kernels with no source to inspect when launch fails; and the msprof backend’s autotuning necessarily fails because it calls signal.signal() from a worker thread.

This batch is not scattered grumbling; in form it resembles an organized audit: the same account filed them in thematic runs within half an hour, with titles uniformly of the form “[BUG] Ascend: …” plus a one-line root-cause summary. The significance for upstream is that the Ascend frontend’s “soundness” gaps were laid out on the table all at once—3060 daily tests all passing does not mean illegal inputs are rejected, because the tests cover the legal paths.

Sources: https://github.com/tile-ai/tilelang/issues/3941, https://github.com/tile-ai/tilelang/issues/3928, https://github.com/tile-ai/tilelang/issues/3947

4.2 In-Review Fixes Echo the Audit: VMI Mask Validation, SIMD Fill Restoration, E4M3 ND/NZ Copy (11-11)

Among the in-review PRs updated that day, a batch lines up precisely with the gaps above. #3861 and #3917 are two halves of the same thing: the VMI unary and vector-scalar factories previously only checked whether a mask was “present,” not its dtype or lane count, so passing an ordinary vector as a predicate would still make it all the way to codegen—seven operators (vabs, vneg, vrelu, vexp, vln, vsqrt, vnot) are built on this factory, and the vector-scalar side’s vadds, vmuls, vmaxs, vmins, vshls, vshrs have weak forms too.

#3795 fixes another side effect of #3512: when T.clear is applied to an int32 UB buffer inside T.SimdVF(), the generated vector broadcast only supports floating point and PTO compilation fails—because the PTO pipeline replaces the original SIMD pass with a dedicated Parallel pass, incidentally dropping the fill lowering. The fix adds a LowerSimdVFFill after buffer-version normalization and before PTO Parallel validation, reusing vdup/vsts for contiguous and complete vector regions while the rest still takes the old path; it also preserves the numeric conversion of the floating-point tl.simd.vdup, fixing the case where “int32 7 is bit-broadcast into roughly 9.809e-45.”

#3639 adds E4M3 ND/NZ UB-to-L1 copies, #3926 makes T.Kernel reject non-positive block counts and negative Pipelined num_stages, #3854 fixes division by zero for sub-byte elements in SimdVF lowering, and #3668 adds interleaved strided UB-to-GM writes within T.PerCoreTask() on AIV cores. Separately, #3915 and #3916 handle AssertStmt error kinds and in-place assertions for condition checks.

4.4 Methodology Correction: The Old Triton Artifact in Two K3 Q1 Comparisons Overflows on Negating -128 (11-11)

This gets its own entry because what it affects is not the score but comparability. In the same batch of commits that published weft-parity, the benchmark repo disclosed that the two K3 Q1 comparisons had previously used the retained Triton Canonical program, which overflows when negating −128—the boundary input yields −2048 when the correct result should be 0. After the shared compiler’s exact I8 reduction fix was regenerated, the artifacts from both frontends pass that input; the historical timing is retained in the triton_historical_us field, and the correction note is recorded in triton_control_note.

An erroneous control implementation is a common trap for benchmark projects: once the reference side is wrong on a boundary input, the tested side “underperforming the reference” may just mean the reference is faster at being wrong. Read together with the paired methodology in 2.8, this disclosure shows that this CPU line is moving from “the author’s program versus an external library” to “paired comparison of artifacts from the same compiler”—more credible methodologically, but the two tables cannot be mixed.

Source: https://github.com/Tianchen-ai/tilelang-weft-bench/blob/main/docs/results.zh-CN.md

V. Trend Observations

First, Ascend’s weight on the mainline keeps rising, and the focus is shifting from “adding operators” to “adding execution paths and solvers.” All three main-repo merges this issue are Ascend: switching the default execution backend, tightening the solver’s lower bound, and adapting atomics to the type system. None of the three adds to the operator list; all change “how the same program gets compiled, run, and how long compilation takes.” Against the record since October, Ascend-side merges have moved from filling in AscendC operators to three layers: interface semantics, execution backend, and scheduling solver.

Second, the CUDA side has entered a long review period. Last issue still had three CUDA instruction-level primitives landing on main; this issue has zero merges and six in review (ldmatrix/stmatrix, 256-bit vectorization, im2col scheduling, pipelined operand lifetimes, async GEMM lifetimes, PASS config namespace). A falling merge rate together with a thickening review queue usually means review bandwidth has become the bottleneck, not that development has stalled.

Third, quality auditing is starting to run in parallel with feature development. The shape of 26 Ascend issues in one day shows that someone in the community is already doing systematic illegal-input auditing, and the corresponding fix PRs were in the queue the same day (mask validation, negative-parameter rejection, fill lowering restoration). For a project spreading its backend across multiple domestic chips, this is a good thing: 3060 daily tests all passing only proves the legal paths work; the ability to reject illegal paths depends on audits like these.

Fourth, the four RISC-V sources have been silent for five consecutive windows, but the CPU line outside those four has reached an interim conclusion. The TVM route, the MLIR route, the community index page, and the Sophgo TPU—all four upstreams remain at their original citations; meanwhile TileLang–Weft, using the shared Canonical compiler, brought all 553 items to within 1.03× of Triton, with median ratios of 1.29 to 1.66 across the four platforms. Note that this is a result after a methodology switch and cannot be compared directly with last issue’s 0.058×. The real things to watch: whether this “same compiler, two frontends” approach can make its way upstream in reverse, and whether the RISC-V RVV/IME path gets proven out first by projects outside the four sources.

Limitations: This issue’s GitHub anonymous API quota was exhausted early in collection; PR bodies and merge details were filled in via the search API and the commit atom streams of non-default branches. For a few PRs, file and line counts are search-API return values and the diffs were not reviewed line by line; the hygon and mlir-ascend merges landed on non-default branches and were checked per branch. The news side had only zero hits, with no external coverage for cross-validation.
