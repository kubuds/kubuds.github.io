Reporting period: Monday, November 16, 2026 through Friday, November 20, 2026 — 5 business days, 5 daily reports; plus a supplementary 168-hour check of the 30 repositories in the tile-ai organization on the publication date (November 21).

Part 1 · Brief

This section is the weekly highlight selection, 800 words or fewer by default (701 words this issue); full entries, itemized lists, and sources are archived in Part 2.

This week’s five daily reports record 141 merges and 467 newly opened issues. TileOPs alone accounts for 84 merges, while the main repo has only 12, four of which are runtime fixes.

  • Security incident: On 11-15, the upstream Ascend repo’s CI was targeted by an external PR that injected scripts, and a contributor’s token was stolen; four repositories saw PRs in the same style, all closed without merging, with disclosure in issue #2016.

This week’s judgment: For two consecutive windows the main battleground has been the operator library, and the bottleneck has shifted from development volume to review bandwidth; barrier instrumentation for automatic warp specialization has become a first-class risk, and v0.1.15 has been stalled for 51 days, with all changes stuck outside the next tag.

Runtime and Execution Paths

  • Device state restoration (#3872, merged 11-16): The tvm_ffi host stub only sets the current device and does not restore it. Calling a cuda:1 tensor on cuda:0 produces correct results but leaves the current device on cuda:1. Subsequent allocations with device="cuda" silently drift. The fix wraps the call in torch.cuda.device(...) at the adapter layer and restores on exit.
  • NVRTC single-argument kernels (#3880, merged 11-16): Argument names and types were joined with ", ". With a single argument, the result is not a tuple, and cuLaunchKernelEx throws a TypeError outright. The fix is a tuple literal with a trailing comma.
  • cython dynamic shared memory (#3882, merged 11-16): The dynamic shared memory limit was previously set only once in init(). That attribute is per-device. Kernels needing more than 48 KB would fail with cudaErrorInvalidValue on other devices. The fix generates a _set_dynamic_smem() helper per kernel and tracks devices already raised.
  • ROCm HIP runtime reuse (#3899, merged 11-16): PyTorch’s ROCm wheel loads libamdhip64 with RTLD_LOCAL, so the stub cannot find it. The fix first probes for an already-mapped runtime with RTLD_NOLOAD. This avoids a second dlopen copy whose module handle spans runtimes, causing the first kernel launch to fail.
  • Unsigned buffer reads (#3875, merged 11-17): On the CuTeDSL target, values read from uint8, uint16, and uint32 buffers were treated as signed. The root cause is that MLIR integers have no unsigned bit, while codegen starts from the iterator type on every global and shared memory access. The author probed with 256 uint8 values on an RTX PRO 6000. Five variants each got 128 values wrong on main. The fix makes tl.make_tensor accept dtype= and reattaches the type to the view.
  • Layout placeholder variables stay bound across serialization (#4410, merged 11-20): tl.Layout, tl.Fragment, and tl.PartialFragment express index and thread mappings with in-process singleton tirx::Var placeholders. Identity is determined by object identity, not name_hint. After a layout round-trips through pickle or tvm.ir.save_json, the placeholders are rebuilt. So map_forward_index([7]) returns [_i], and OutputShape() computes (32,) as (_i + 1,). Lowering an annotated PrimFunc in a spawned worker fails with “forward map must be injective”. The fix routes the bound placeholder Var references through the same ObjectGraphSerializer channel.
  • CUDA Tile IR backend RFC resubmitted (#4402, #4403, 11-19): The goal is to generate CUDA Tile IR from TileLang programs and hand it to tileiras for compilation and scheduling. Layout, pipelining, warp specialization, and instruction selection are all decided by tileiras. The backend only converts semantics that Tile IR can express correctly. Anything it cannot convert raises a compile error and rejects the program; full compatibility with the existing CUDA backend is not a goal. This version is a redo of the earlier #3247. Reviewers had noted the old implementation had too many try-catch blocks and wrote passes in roughly 18,500 lines of Python.

Correctness and Bug Fixes

  • CPU backend gains logical reduction lowering (#4389, merged 11-18): tl.any_of and tl.all_of previously could not go through the regular CPU pipeline. A new LowerCPUAnyAll pass is inserted before LowerTileOp. It lowers to a row-major serial scan with short-circuiting. Empty reductions take the standard identity element. NaN in floating point and bfloat16 is treated as true.
  • topk regression test timeout (#4407, merged 11-18): test_topk_candidate_overflow timed out on CUDA CI. The cause was an expensive Z3 query issued during simplification. The fix sets arith.z3_rlimit to 100 for that test. The author notes there is no CUDA codegen on their machine, so full compile time and GPU correctness were not verified.
  • Ascend autotuning test drops cross-NPU probe (#4401, merged 11-18): That branch performed a cross-NPU copy. On some Torch-NPU and CANN combinations, this copy aborts the NPU context. Catching RuntimeError and skipping the case does not restore the context. Subsequent unrelated cases in the same pytest process then fail. The failure therefore depends on execution order.
  • New bug report: MLA decode example missing write-after-read sync (#4412, 11-19): The report points to examples/deepseek_mla/example_mla_decode_ws.py. It claims the right warpgroup reads sum_exp_shared without waiting for the left warpgroup’s write. The report has no fix attached and no reproduction environment noted. Recorded this issue as “reported, pending”.
  • Fix under review: skip layout-incompatible TMA promotion during warp specialization (#4413, 11-19): On b1367a59, a pipelined GEMM targeting sm_90a fails to lower. The trigger is its 8-bit B tile using a padded swizzled layout. Loading A makes the loop eligible for warp specialization. The pass then also promotes B’s plain copy to TMA, and LowerBulk rejects padded layouts. The fix checks the target layout annotation of each candidate TMA load.
  • Hang fix chain (#2896 → #2899 → #2901, 11-15): After #2896 merged, gpu-smoke on main hung. sliced_pair stages out_shared under the condition i // wg_rows == bz. After layout lowering, only the consumer warpgroup that keeps that half tile executes the staging loop. TileLang sometimes inserts the barrier guarding this write into that branch. That barrier covers all 256 consumer threads. The other warpgroup never reaches it. The two groups stall on different instances of the same barrier. Worse, the barrier placement is not stable across two compilations with the same cache key. CI’s persistent kernel cache keeps replaying the bad build. The fix moves staging out of the conditional so both consumer warpgroups write their own half.

CI, Testing, and Benchmarks

  • Benchmark timing switches to nvbench cold measurement (#2985, 11-17): Previously each sample synchronized to the host before the call, and host-side launch overhead showed up as device idle time. The new approach holds the stream with a blocking kernel and enqueues all samples for one reading back to back. Each sample resets, flushes L2, and executes its call, with no host synchronization in between.
  • Nightly sweep budget doubled (#2996, 11-17): Cold measurement increased runtime. The latest round ran 20,259 seconds before being cut off by the 6-hour budget, leaving 5 of 61 benchmark files unrun. The shared 2,015 cases went from 15,180 seconds to 19,103 seconds, a 1.26x increase. The fix raises the total budget from 21,600 to 36,000 seconds and the job timeout from 380 to 620 minutes.
  • Ascend benchmarks switch to device-side L2 flush (#3891, merged 11-17): The old approach read a scratch buffer. Cache state depended on the replacement policy and could differ between rounds. The new approach calls aclrtDeviceL2CacheFlush before each NPU event or msprof sample.
  • TileOPs-nightly snapshot (11-15): Two commits landed on the snapshots branch. One corresponds to run 43654108754, testing commit abe2086e. The other corresponds to run 43738645759, testing commit e4444654, i.e. #2955. This chain is the source of several performance conclusions in this issue.

III. Multi-Backend Adaptation

Ascend (tilelang-ascend and the main-repo Ascend backend)

  • Repo-side cadence: The default branch ascendc_pto merged nine commits on 11-13. No new commits in the three periods since. The nine include the DSA trio (#1870, #1928, #1884), the KDA trio (#1895, #1896, #1799), the catlass upgrade (#1989), the bitwise four-in-one (#2000), and the alloc API docs (#1642).
  • DSA trio: The forward pipelined version targets sparse MLA prefill for DeepSeek V3.2. Each query block selects KV rows by top-K and fuses DQK into a single K dimension of 512+64=576 for one GEMM. Persistent grid of 20 cores. The backward pass uses a two-pass structure, with dKV written out via fp32 GM atomic scatter. Under the benchmark shape, each row is contributed to by an average of about 448 tokens. Cumulative time dropped from 79,395 µs to 27,388 µs, a 65.5% reduction. The topk reduction uses Expert mode, with dual-stream on two AIVs plus a manual cross-core flag.
  • KDA trio: The dhu path of chunk_delta_bwd stays entirely in UB to do the backward chunk recurrence. chunk_delta_h_fwd absorbs the gate into a host-side precomputed M matrix, with zero transcendental functions in the kernel. Chunk Delta H itself explicitly abandons fp32 GEMM in favor of bf16. The rationale is that gate decay keeps the recurrence eigenvalues always below 1.
  • catlass v2.2.0 (#1989): Upgraded from v1.0.0-6 to the official tag v2.2.0, with six TLA API adaptations to src/tl_templates/ascend/common.h. The helper’s external signatures are unchanged. The primary motivation is a bug fix. The old CopyL1ToL0A/L0B had no float specialization, so fp32 inputs to T.gemm_v0 would output NaN or negative infinity without error. The other benefits are absorbing 17 months of community fixes and opening four channels: HF32, GEMM+Bias fusion, quantized inline output, and FP8.
  • Newly reported defect #2017 (11-17): This is a report using a three-arm control, on 910B3 with CANN 9.2.0. The scenario is scattering 64 consecutive single-precision numbers in UB into GM along the sequence dimension during FLA’s WY fast backward. The target tensor’s head dimension is in the last dimension. The author compared three approaches: contiguous writes, direct strided writes, and strided writes via a GM staging buffer. Three layers of problems were identified. The first is incorrect compiler offload parameters. The second is a mismatch between hardware slot addressing and the compact layout. The third is that the 32-byte slot footprint of narrow transfers causes UB allocation to be underestimated.
  • Chip model identification defect #2023 (11-19): Ascend.__init__ determines the chip by string containment. It first checks 910B, then 310P, and the final fallback 910 is always treated as Ascend910A. The Atlas A3 device name is Ascend910_9362. It matches neither of the first two, so it falls into the fallback bucket. The consequence is three parameter mismatches. ub_cap is taken as 262144 bytes, actual 196608. l0c_cap is taken as 262144 bytes, actual 524288, exactly half of the real value. compute_max_core is taken as 32, whereas it should actually be queried via cube_core_num. carver uses these three values for feasibility screening and cost modeling. Halving L0C will directly screen out configurations with large C tiles.
  • Main-repo Ascend under review: #4385 fixes the msprof cache flush annotation. #4396 lowers any_sync and all_sync to masked warp vote instructions. #4397 makes the backend reject unsupported SIMD predicate widths. #3924 proposes a new Ascend-specific nightly wheel pipeline. The pipeline uses cibuildwheel to produce manylinux packages, triggers daily at 20:00 UTC, and disables CUDA and ROCm during the build. #4411 publishes standard Linux wheels to the Ascend community OBS. #4012 changes the max_vector_bits default to 128 and supports 16-lane fp8 SIMT vectors. #4016 is a performance tuning skill written for Ascend. #1760 enables FP32 GEMM support in the AscendC backend; opened on September 8 and still being updated this week.
  • Five dtype audit items (#4391 to #4395): The core conclusion is that T.simd unary and binary operators perform no dtype validation at all before being passed into compiler-internal calls. CANN 9.2.1’s CCE vector interfaces provide only partial overloads. For example, absolute value has only five integer and half-precision, single-precision overloads, with no bf16. XOR has only two 32-bit integer ones. The frontend lets through 70 of 225 combinations directly. The reduction family’s whitelist is similarly missing, with 27 of 63 combinations not intercepted. The other two are more specific. The part parameter of T.simd.vcvt defaults to 0, which lands on “even part,” converting only half the elements. The docs claim support for 40 dtype pairs, while the frontend actually implements 33. Item 5 points out that six T.ascend_* synchronization primitives all fail inside T.SimdVF(). The report environment is Ascend 950PR (dav-3510), CANN 9.2.1, openEuler 24.03.

Coverage includes shifts, flips, concatenation, range generation, trigonometric functions, gather, transpose, vector activation, four kinds of reduction, L0A/L0B/L0C/L1 address spaces, atomic add, bitcast, cross-pipe set/wait flag, pad, sqrt and reciprocal, sort, type conversion, and logical operations. VI. Trend Observations

First, the main battleground has shifted from the compiler proper to operator libraries and schedulers, and this shift has held for two consecutive windows. Of the 141 merges this week, TileOPs accounts for 84, while the main repo has only 12. Of those 12 in the main repo, four are runtime bugfixes and two are version and documentation. Last week’s situation was similar. Work in the main repo is concentrated on fixing regressions, while new capabilities increasingly appear in the form of operator library tiles, selectors, and cost models. The basis for this judgment is not just the merge count, but also the direction of dependencies. TileOPs’ performance conclusions must cite TileFoundry’s roofline and scheduling, yet the main repo gave them nothing new this week.

Second, auditing has become pipeline-based, and the bottleneck has moved from “discovery” to “review”. In period 11-16, 406 issues were opened within 72 hours, with two accounts contributing 314. The 172 from cn-sys were written in 1 hour 46 minutes. The 142 from ilovexsir correspond directly to five batch fix PRs. This pattern does compress the cycle from “defect discovery to fix,” with issues and PRs coexisting on the same day. But it shifts the pressure to the review side. Period 11-16 had 102 under review and 30 merged. Among them, 22 isomorphic mlir-ascend PRs can only be passed by a very small number of people. The bottleneck in the next stage will be review bandwidth, not discovery speed.

Third, the security boundary is the only unavoidable negative event this week, and what it exposes is a structural problem. The self-hosted CI was penetrated by an external PR, and a personal token was stolen and misused. Same-style PRs appeared simultaneously across four repositories. This shows that the default setting of “new contributor PRs directly triggering self-hosted server CI” is a shared risk surface at the organizational level. The author’s handling was to revoke old authorizations, preserve the malicious fork for evidence, and perform security handling on the self-hosted CI server. The recommended fix is that new contributor PRs should require maintainer approval before triggering. This also applies to the entire RISC-V and AI compiler community. The trust boundary of self-hosted runners should be tightened by default, rather than judged separately per repository.

Fourth, the correctness of automatic warp specialization has become a first-class risk. The chain from #2896 to #2901 illustrates one thing. When a performance change delegates synchronization responsibility to compiler automatic instrumentation, the instrumentation location becomes part of correctness. And it is opaque to the upper layers. Compiling twice with the same cache key, the barrier may land inside a branch or outside it. Combined with CI’s persistent kernel cache, an occasional bad instrumentation gets solidified into a stable failure. There is currently no structural solution to this problem, only local workarounds such as “move write operations out of conditional branches.” If more tiles go ping-pong in the future, similar hangs will most likely recur.

Fifth, the platform boundary is expanding outward, but all of it stops at the IR layer. On the same day, the Metal target and automatic differentiation landed, extending the compiler from inference kernels toward training and Apple GPU. Neither produces a runnable kernel. The order is clear: establish the interface first, then fill in the backend and runtime. In the same week, TileFoundry used 303 files to converge terminology and layout algorithms into a single specification. This is equivalent to changing the intermediate representation from “growing out of the implementation” to “defined first, then implemented.” Such changes increase review cost in the short term, but in the long term determine whether the IR can be correctly implemented by external backends.

Sixth, the long-delayed release is the common exit problem for all progress this week. v0.1.15 has been stuck at 09-30, and as of this Friday it has been 51 days. The main repo’s runtime fixes, Ascend’s execution backend changes, and TileOPs’ operator completions must all wait for the next tag before they can enter downstream distribution packages. In contrast, independent distributions are already moving forward. Sunrise released 0.1.15+sunrise.1.2.1, MetaX is preparing v0.1.12+musa.5, and Hygon is following up with merge-style corrections. With the three releasing separately, version alignment and the compatibility matrix will become a new maintenance cost.

Seventh, the four RISC-V sources advanced once each in two branches this week, and the pace remains discontinuous. The TVM route opened a new hikari branch, providing K3 porting validation and RVV grid data. The MLIR route merged buddy-opt defaulting and two examples. The community index page included a TVM-side fork for the first time. But all three periods since 11-18 have been silent. The division of labor between the two routes is already clear. The TVM route is working on “getting it running, with measured data.” The MLIR route is stuck at “having a design, having examples.” This line is worth following by window, but progress should not be measured weekly.
