1.1 ARM 配置搬出公共 Kconfig：libcpu 開始按架構分家（11-05）

日期：2026-11-05 22:26（合入時間）　來源：提案 #11988、議題 #9187

267 行新增、173 行刪除，三個檔案：新增 libcpu/arm/Kconfig，原 libcpu/Kconfig 裡 ARM 相關的架構標識、核心型號、ARM MMU/MPU 與 GIC 配置整體搬進架構目錄，原地用 rsource 引入；公共能力與跨架構的 KERNEL_VADDR_START 留在原檔案。作者 zijunteng238-dot 上午 11:51 建提案，晚上 22:26 合入，十個半小時走完全程。

這次的做法值得單獨記一筆：它不新增選單、不改符號、不改預設值、不改依賴與 select 關係，只搬家。驗證方式也不是「編譯過了就算」——作者用 Kconfiglib 14.1.0 對拆分前後的全部解析符號做對比，配置值、型別、可見性、可賦值範圍、預設值與選擇關係逐項一致，排除檔案路徑與行號變化後沒有新增解析警告；比對覆蓋五個 BSP：frdm-k64f（Cortex-M4）、qemu-vexpress-a9（Cortex-A9）、renesas/rzt2m_rsk（Cortex-R52）、qemu-virt64-aarch64 與 qemu-virt64-riscv，並在 RISC-V 上跑了 scons –menuconfig 比對選單輸出。另外在記憶體裡給 A9、AArch64、RISC-V 開啟 SMART 與 IOREMAP_LATE 再比一輪，未寫回配置檔案。

對長期維護的意義在結構：libcpu/Kconfig 此前把 CPU 公共能力和多架構配置混在一起，任何架構加選項都要動同一個檔案，衝突與誤改機率隨架構數量上漲。這次拆完，RISC-V、ARM 各自的 Kconfig 可以獨立演進，與上一期文件化的版本釋出流程是同一條治理線——先把結構理順，再談版本節奏。配套新增了 documentation/4.tool/scons/libcpu_kconfig_arm_split.md，把拆分範圍、依賴處理與驗證結果都寫進倉庫，後續搬其它架構可以照此執行。

1.2 RISC-V Smart 的 MMU 與使用者異常：四處根因一起修（11-05）

日期：2026-11-05 11:15（合入時間）　來源：提案 #11892

109 行新增、8 行刪除，四個檔案，維護者 BernardXiong 提的，10 月 18 日建、本期合入，中間經過 11 條行內評審。這條對 RISC-V 側的 RT-Smart 是本期最實質的一筆。

改動列了四條根因，都是同一類問題的不同側面。其一，早期頁表指標沒有按核心物理偏移做轉換，核心被載入到非零實體地址時頁表描述符指錯地方。其二，每個 hart 的核心頁表繼承了使用者對映，等於在 hart 之間留下了不該有的地址空間。其三，早期頁表在開啟 MMU 之前沒有清理。其四也是最要命的一條：未處理的使用者態異常會讓核心整體終止，而不是隻結束當前程序——使用者程序的一條野指標就能拖垮系統。

對應的修法是：新增玄鐵架構選擇與 SVPBMT 選項；早期頁表指標帶核心物理偏移轉換；允許 MPR 範圍延伸到低於連結核心基址；啟用 MMU 前先清理早期頁表；清掉每 hart 核心頁表裡的使用者地址項；使用者異常只終止當前 LWP；上報使用者上下文期間保持中斷開啟。

驗證條件寫得坦白：BSP 用 qemu-virt64-riscv 與 bsp/k230，配置 RT_USING_SMART 加 ARCH_RISCV64，作者本地沒跑構建，理由是環境裡沒有 RISC-V musleabi 工具鏈，交 CI 驗證。這與上一期串列埠那筆的驗證說明是同一種坦白，方向上沒問題，但 RISC-V Smart 這條線上的執行時行為最好還是靠實機複測兜底。

1.3 訊號投遞不再持鎖睡眠，ELF 段保護順序糾正（11-05）

日期：2026-11-05 11:16（合入時間）　來源：提案 #11895、提案 #11899

兩筆同屬 lwp 子系統，都由 BernardXiong 合入。第一筆 #11895 改五個檔案、58 行新增、27 行刪除，含 RISC-V 側的彙編入口 lwp_gcc.S、lwp_elf.c 與 lwp_signal.c，三個提交。核心是順序問題：訊號處理路徑會拿睡眠鎖，因此必須保持可排程，程式碼裡用 OPEN_INTERRUPT 與 CLOSE_INTERRUPT 在關鍵段落顯式開關中斷；同時糾正了 ELF 段保護的施加順序，避免先寫後保護。

第二筆 #11899 更小，16 行新增，兩個檔案：sys_sigaction 在索引動作陣列之前校驗訊號編號，拒絕小於等於零與超過 _LWP_NSIG 的取值，返回 EINVAL。這類「先校驗再索引」補丁最近幾期已經出現多筆，屬於同一批審計的產物。

2.1 ivshmem 把裝置配置字當可信輸入，/dev 節點成了任意實體記憶體通道（11-06）

日期：2026-11-06 00:54（報告時間）　來源：缺陷 #11992

報告者 XueDugu，延續他最近幾期在 PCI 與裝置驅動側的一條線。問題在 ivshmem 驅動的探測函式：當 BAR2 報告的尺寸為零時，程式碼走 JailHouse 回退分支，直接從 PCI 配置空間 0x40 到 0x4f 四個雙字讀取共享記憶體的地址與大小——這四段由裝置側決定，驅動沒有任何校驗，隨後把它們交給 rt_ioremap，而 rt_ioremap 本身不檢查實體地址合法性。

後果鏈條很短：惡意或格式異常的裝置把「共享記憶體」描述成核心記憶體區間，對映照樣成功，視窗再被註冊成 /dev/ivshmemN。之後的讀寫走的是官方 open/read/write 路徑裡的兩次 memcpy，一次把核心內容拷給使用者，一次把使用者資料寫回核心。於是任何非特權程序只要開啟這個裝置節點，就拿到任意核心實體記憶體的讀寫能力，位元組粒度、資料完全可控，不需要任何特殊 ioctl 或額外許可權。

報告還指出一處附帶問題：原始碼把 64 位欄位拆成兩個 32 位寫入，在 32 位構建上會寫到相鄰欄位，等於順手破壞結構體。這條與 MSI-X 那條同一個模式——裝置韌體提供的值被當作可信輸入，而驅動側缺少「先校驗後使用」的固定動作。

2.2 兩小時十一分鐘後出修復：新增選項把 JailHouse 回退關進籠子（11-06）

日期：2026-11-06 03:05（提案時間）　來源：提案 #11993

99 行新增、7 行刪除，兩個檔案，維護者 BernardXiong 提的，狀態待審，已有一條討論。

修法分四層。第一層是預設關閉危險路徑：新增 RT_IVSHMEM_JAILHOUSE 選項，預設 n，幫助文字寫明裝置必須可信；不開啟它時，BAR2 不存在就直接拒絕探測，不再讀配置字。第二層是對映前校驗：尺寸非零、地址加尺寸不溢位、整個區間能用本地指標與尺寸型別表達。第三層是型別修正：四個配置雙字先讀進 64 位區域性變數，不再透過 32 位別名寫結構體欄位，順帶修掉相鄰欄位被踩的問題。第四層是檢查配置空間讀取的返回值，讀失敗不再繼續。

驗證只到編譯與格式：兩種選項組合（JAILHOUSE 關與開）在 qemu-virt64-aarch64 上都能編譯透過，改過的檔案過 clang-format。從 00:54 報告到 03:05 提案，兩小時十一分鐘，比上一期 MSI-X 的六小時又快了一截。

3.1 Titan Board 接上 OpenMV：170 個 Python 示例，NPU 走 TFLM（11-05）

日期：2026-11-05 17:30（專欄釋出時間）　來源：電子工程專輯：Titan 也能玩 OpenMV 了、工程：Titan_Openmv

RT-Thread 官方專欄本期釋出 Titan Board 的 OpenMV 工程，把 RT-Thread 5.1、OpenMV 5.0.1 與 MicroPython 一起搬到這塊基於瑞薩 RA8P1 的板子上：1 GHz Cortex-M85 跑系統與應用，250 MHz Cortex-M33 協處理，Ethos-U55 NPU 配到 500 MHz，外掛 32 MiB HyperRAM 存影象與執行記憶體，峰值 AI 算力標稱 256 GOPS。外設側接 OV5640 MIPI 攝像頭、FAT/FAT32 SD 卡、USB HS 的 CDC 與 MSC 複合裝置，以及板載三色 LED 與按鍵。

示例規模是這次的主要賣點：共 170 個獨立 Python 指令碼，傳統視覺 124 個，覆蓋相機控制、拍照錄影、繪圖、濾波、顏色跟蹤、條碼、特徵檢測與 AprilTag；機器學習 23 個，配 20 個面向 Ethos-U55-256 的模型檔案與一個由 CPU 執行的數值迴歸模型，任務覆蓋手勢（剪刀石頭布、手掌檢測、21 點手部關鍵點）、人臉與姿態（人臉檢測、468 點關鍵點、人體姿態）、目標識別（行人、貓狗、COCO80 常見物體）與影象分類分割。

工程組織方式對上手有實際幫助：程式碼在 SDK 的 project/Titan_Openmv，同時支援 RT-Thread Studio 與 SCons；構建產出兩個必須配套使用的檔案——rtthread.hex 走 DAP-Link 或 J-Link 燒錄，openmv-vision.bin 走 USB 複合裝置傳輸，兩者必須來自同一次構建。模型與標籤放 models/sdcard/，按說明覆制到 SD 根目錄即可；指令碼里的 /rom 是 SD 根目錄的只讀別名，不需要另建目錄；想讓作品開機自啟，把應用存成 SD 根目錄的 main.py。文中還特別提醒 IDE 裡顯示的 AE3 只是協議相容標識，不能刷 Alif AE3 的韌體，板子用的是本工程的 RA8P1 韌體。

兩點技術判斷：一是這套組合把「相機採集、影象處理、神經網路推理、外設控制」串在同一條 Python 指令碼里，端側視覺的門檻從寫 C 驅動降到改引數；二是運算元按支援情況在 CPU 與 NPU 之間分流，TFLM 負責排程，意味著模型能不能跑起來取決於運算元覆蓋，示例裡的 20 個模型本身就是一份可用的覆蓋清單。

日期：2026-11-06 07:05（合入時間）　來源：提案 env #304、提案 sdk #11、索引目錄 env-plugins

4.1 ESP32-C3 預編譯映象拒絕 v1.x 晶片：最小版本欄位沒對齊（11-05）

日期：2026-11-05 23:24（報告時間）　來源：缺陷 #11991

報告者 anamarija-j，影響版本寫明 v5.3.0 與 master cbadbdf，硬體是 ESP32-C3、晶片修訂 v1.1（ROM 版本 esp32c3-eco7-20230720），BSP 為 bsp/ESP/ESP32_C3。這是本期唯一一條 RISC-V BSP 的迴歸缺陷。

現象分兩段：esptool 直接拒絕燒寫，提示預編譯的 bootloader.bin 要求晶片修訂 3 及以上，而這塊板子是修訂 1；加 –force 強燒後，二級 bootloader 能啟動，但在讀分割槽表之前停止，日誌寫明晶片是 V101、應用配置的最低修訂是 3。

根因在欄位語義：預編譯 bootloader 只填了舊的 min_chip_rev 欄位（值 3），全量欄位 min_chip_rev_full 是 0；這顆 ESP-IDF v5.0-dev 的 bootloader 恰好拿舊欄位與次版本號比較，v1.1 的次版本是 1，於是判定不滿足。BSP 的 SConstruct 同樣只設定 image.min_rev = 3，生成的 rtthread.bin 帶同樣的問題。換句話說，同一個「最低修訂」用新舊兩套欄位表達，預編譯產物與構建指令碼都只寫了舊的那套，遇到按新規則解讀的晶片就卡住。

這條的實際影響面不小：ESP32-C3 是 RT-Thread 生態裡最常見的 RISC-V 無線 MCU 之一，預編譯映象不能用等於新使用者第一次上板就失敗，只能自己從頭編譯。修法不復雜，SConstruct 與預編譯產物同時寫 min_chip_rev_full 即可，但要連帶重新出包。

4.2 BSP 與測試基建五筆：D1s 進 QEMU、efm32 進 menuconfig、三套框架測試（11-05）

日期：2026-11-05（合入時間）　來源：提案 #11903、提案 #11867、提案 #11883、提案 #11982、提案 #11976

BSP 側兩筆，都是「讓板子更好用」的方向。全志 D1s 補了 qemu-d1s.sh 啟動指令碼，可以直接在 d1s 的 QEMU 機型上跑這個 BSP，省掉找映象與拼引數的步驟（#11903）。EFM32 補了 Kconfig 與 .config，正式支援 scons –menuconfig，此前只能手改配置（#11867）。

測試基建三筆，方向一致：給框架本身加模擬裝置測試。看門狗補冒煙測試，容忍超時量化的誤差與非可停止的關閉路徑（#11883，對應缺陷 #11446）；I2C 用模擬匯流排覆蓋框架層，不依賴真實硬體（#11982）；DAC 用模擬裝置測試（#11976）。三筆都由社群貢獻者提交，加上 2.5 裡待審的 QEMU 自動執行改造，可以看出一個明確動作：把驅動框架的驗證從「等硬體」變成「進 CI」。

5.1 一天三十一筆：積壓清賬取代逐步推進

本期 24 小時主倉庫合入 31 筆提案，是近期最大的一次單日批次。時間分佈很集中：02:47 到 03:18（北京時間 10:47 至 11:18）的 31 分鐘內合入 17 筆，05:23 到 10:40 之間再合入 13 筆，最後一筆 ARM Kconfig 拆分在 22:26 單獨落地。

另一個訊號是合入者的結構。31 筆裡 usualtreee 7 筆、BernardXiong 5 筆、cms19859230182-lang 4 筆、adilalperenciftci 2 筆，其餘 13 筆來自不同貢獻者。稽核與提交的分工已經比較清楚：外部貢獻者出補丁，維護者做校驗與合批。

5.2 趨勢：裝置側輸入成為第二個主戰場

把最近四期連起來看，攻擊面在挪位置。10 月底到 11 月初報的多是系統呼叫層的「值到物件」缺校驗：getaddrinfo 的巢狀使用者指標、pipe 的 ioctl 指標、timerfd、塊裝置分割槽的裸指標。這一期的兩條新缺陷換了前提——MSI-X 要求插進來一塊惡意裝置，ivshmem 要求裝置把配置字填成核心地址。共同點是：裝置韌體提供的暫存器被核心當作可信輸入，而 rt_ioremap 不做實體地址合法性檢查，於是「裝置說什麼就對映什麼」。

處置速度是另一條線：MSI-X 從報告到提案 6 小時、到合入兩天；ivshmem 從報告到提案 2 小時 11 分。報告者給的是帶 PoC、帶日誌、帶版本追溯的完整材料，維護者拿到就能直接改，這比流程規定更能壓縮修復時間。代價是佇列繼續變厚：48 筆待審更新，塊裝置分割槽那筆掛了三天仍未合。

第三條線是結構與工具同步推進：libcpu/Kconfig 開始按架構分家，版本編號與釋出流程已經成文，Env 的外掛分發從中心化市場改成「倉庫索引加 Release」，測試則從等硬體改成進 CI。這四件事不在一條線上，但都是把「靠人記」換成「靠結構約束」。
