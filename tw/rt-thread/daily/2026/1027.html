二、安全與穩定性跟進

2.1 signalfd 的全域性計數越界：第 11 次呼叫起把核心指標寫到堆塊之外（10-26）

日期：2026-10-26 16:13（建立時間）　來源：Issue #11933

這是本期分量最重的一條。研究者指出 components/libc/posix/io/signalfd/signalfd.c 裡用一個檔案作用域的全域性計數器 is_head_init 去索引每個檔案描述符私有的陣列 sfd->lwp[10]，而 signalfd_add_notify() 在使用前沒有任何邊界檢查。signalfd_close() 從不回退這個計數，所以它只增不減；新建上下文時又只清零 lwp[0 .. is_head_init-1]，同程序再次建立時永遠匹配不到自己，必然走寫入分支。

後果寫得很具體：lwp[] 是 struct rt_signalfd_ctx 的最後一個成員，整個結構在 arm32 上是 1536 位元組，陣列正好壓在堆塊末尾。第 11 次呼叫 signalfd(-1, ...) 時，寫入落在分配塊之外第一個字，即小記憶體分配器的下一個塊頭；此後每建立一次再向外推 4 位元組（64 位下 8 位元組步長），形成持續、由呼叫方控制節奏的核心堆越界寫，寫進去的值還是核心指標。

影響面按作者逐個標籤核對：引入點是 2023-09-11 的 7c3d966d（#8001），v5.0.2 / v5.1.0 / v5.2.0 / v5.2.1 / v5.2.2 / v5.3.0 與當前 master（5d1fb66d）全部命中。觸發前提只有 RT_USING_SMART=y——RT_USING_POSIX_SIGNALFD 在該配置下預設為 y，兩個官方 QEMU Smart BSP 的配置也都開著，因此預設的 RT-Smart 構建即可觸發。復現用 bsp/qemu-vexpress-a9（Cortex-A9、32 位、FAT sd 卡根檔案系統），PoC 以 /sbin/init 安裝。

目前該單無對應修復提案，也未打標籤。

2.2 musl 執行緒連結串列在併發退出下的釋放後使用：futex 鎖沒有起到互斥作用（10-26）

日期：2026-10-26 11:22（建立時間）　來源：Issue #11932

第二份缺陷單來自另一位報告者，環境是 RT-Thread 5.2.2 的 RT-Smart、SMP、aarch64、musl 1.2.5。現象是併發 pthread_create 與 pthread_exit 時使用者程序崩潰，崩點在 musl_pthread_exit：連結串列摘除時寫入的執行緒描述符已經被釋放或解除對映（Data Abort），或者執行緒的返回地址被改寫成 0（Instruction Abort）。

作者的定位結論是問題完全在使用者態：musl 用基於 futex 的 __tl_lock / __tl_sync 保護執行緒連結串列，但在 SMP 併發退出的場景下這組鎖沒有真正提供互斥，導致雙向連結串列被寫壞；核心側 futex 實現本身語義正確，不承擔這個缺陷。復現材料是一個 1000 輪、8 執行緒的 tl_race 程式，幾百輪內即崩。

該單帶 bug、Arch: ARM/AArch64、RT-Smart 三個標籤，附完整分析文件。與 2.1 一樣，落在 RT-Smart 這條線上，但層次不同：2.1 是核心堆，這一條是使用者態 libc。

2.3 時間子系統兩處修復轉為成熟版：settimeofday 去強轉、gmtime_r 處理負時間戳（10-26）

日期：2026-10-26 14:17 與 17:48（最後更新）　來源：PR #11928、PR #11929

上一期記錄的時間子系統四單，對應的兩筆修復在本視窗內推進了一步，且都勾選了「成熟版本，可合入」。

#11928 只改一個檔案，+185/-135：settimeofday() 原來先用 (long) 把 tv_sec 強轉再判斷正負，在 ILP32 且 time_t 為 64 位、long 為 32 位的配置下，2^31 到 2^32-1 之間的合法時間戳會被截成負數，函式在碰 RTC 裝置之前就以 EINVAL 拒絕——2208988800（2040-01-01）就是這樣被拒的。修法是按欄位自身型別校驗，不做強轉。

#11929 兩個檔案 +104/-9：gmtime_r() 用 C 的除法與取模拆時間戳，而 C 的除法向零截斷，負輸入下餘數為負，年份迴圈又只能往未來走，於是 -1 得到 1970-01-01 00:00:-1、-31536000 的年份欄位變成 1970-01--364。修法是把負數路徑規範化後再拆。

兩單都沒有合入。另兩筆（timer_gettime() 截斷 #11924、時間子系統工作項調研 #11927）本視窗內無新進展。

日期：2026-10-26 09:15 與 11:37（合入與關閉時間）　來源：RT-Thread-packages/esp-idf 提案 #19、主倉提案 #11926

上一期記錄的 #11926 想在主倉裡調整 ESP32 C3／C6 的 FreeRTOS 標頭檔案包含順序，以修掉 ESP-IDF v6.1 適配後 master 上的構建失敗。這輪討論給出了另一條路徑：維護者在評論裡提出「讓 AI 把 idf 改成 scons」，並指向包倉的提案 #19；另一維護者隨後追問是否要先合包倉那筆。

3.2 Eclipse 工程生成器漏傳核心宏：Studio 的 24 個隱式宣告警告有了解法（10-26）

日期：2026-10-26 23:33（最後更新）　來源：主倉提案 #11930

上一期收錄的社群長文記錄過「Studio 構建報 24 個 rt_sched_* 隱式宣告警告」，這輪有了對應提案：單檔案 +151/-2，從工程生成器一側修。

根因寫得很清楚：include/rtsched.h 裡的排程器介面由 __RT_KERNEL_SOURCE__ 與 __RT_IPC_SOURCE__ 兩個宏保護，gcc 與 armclang 分支在 src/SConscript 裡透過 LOCAL_CPPDEFINES 注入，命令列 scons 構建能識別，但 Studio 每次 make 之前呼叫的 tools/targets/eclipse.py 不收集這個組級定義，於是 dist 匯出工程出現 24 條 -Wimplicit-function-declaration：clock.c 1 條、ipc.c 7 條、thread.c 12 條、timer.c 1 條、scheduler_comm.c 3 條。

修法是把 __RT_KERNEL_SOURCE__ 提到 Kernel 組的全域性 CPPDEFINES，與既有的 msvc 分支保持一致。改動不涉及核心原始碼，只動工程生成指令碼。

5.2 社群長文《rtthread啟動鏈路分析》：從 Reset_Handler 到 main 拆成三段（10-26）

日期：2026-10-26 08:59（釋出）　來源：社群文章：rtthread啟動鏈路分析

社群文章介面在視窗內只新增了這一篇，約 5700 字，作者自述環境是 STM32F103C8T6 + RT-Thread 4.0.3 + RT-Thread Studio 2.3.1（GCC），並宣告文中程式碼取自本工程實際構建，不是照抄手冊。

鏈路拆成三段：第一段是彙編，Reset_Handler 把 .data 初值從 Flash 搬到 SRAM、清零 .bss、調 SystemInit、跳 entry——作者特意點出一個常見誤解，SystemInit 並不把主頻配到 72MHz，它只是把 RCC 打回復位狀態並把 SCB->VTOR 設到 Flash 起始；第二段是 C 初始化，entry 進入 rtthread_startup()，rt_hw_board_init() 裡才配 72MHz 時鐘與堆，隨後建 main、timer、idle 三個執行緒；第三段是排程器啟動，rt_system_scheduler_start() 挑優先順序最高的就緒執行緒，預設先跑 timer 執行緒，main() 要等到 main_thread_entry() 裡 rt_components_init() 之後才出場。

文末還給了四個「容易記錯的點」與一節自驗方法，屬於讀核心程式碼時的常見困惑點彙總。

5.3 媒體側 24 小時無新稿，最近仍是 10-24 的 RISC-V 峰會報道（10-26）
