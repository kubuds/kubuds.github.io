一、核心與版本動態

1.1 掛起三年的時間片排程提案補做核對：判別式與 #11907 殊途同歸，但「延後寫 READY」在單核引出重複釋放（10-21）

日期：2026-10-21 14:16 ~ 14:41（評論時間）　來源：PR #6645、PR #11907

2022-11-23 提交的時間片排程補丁（#6645）長期掛在 Status: waiting for test，社群成員 Yunlk 在視窗內連發三條評論把它重新拉回評審視野。第一，補丁改的 src/scheduler.c 在當前主線上已被拆分為 scheduler_comm.c、scheduler_up.c、scheduler_mp.c，原補丁無法直接應用，評論給出了改動點與新版檔案的逐處對應。第二，該補丁的核心判別式——只有「仍在執行且時間片未用盡被搶佔」才插隊首，其餘一律隊尾——與 #11907 獨立得出的結論完全一致，兩條互不知情的路徑收斂到同一判斷，作者稱這本身可作為方向有效性的旁證。第三，真正的分歧在實現手段：本補丁刪掉插入開頭寫 READY 的覆蓋、改為插入末尾統一置位並清 YIELD，導致插入期間執行緒狀態仍為 RUNNING。

按此邏輯移植到單核路徑後，QEMU vexpress-a9 上訊號量喚醒順序由 BA 修正為 AB、啟動順序由 DC 修正為 CD，三執行緒時間片輪轉正常，但排程組 utest 穩定崩潰：rt_smem_free 斷言失敗，回溯為 rt_free ← rt_defunct_execute ← idle_thread_entry，即 idle 回收已結束執行緒時對同一 TCB 二次釋放，兩次執行在同一用例復現。隔離實驗把 rt_schedule() 裡原有那處 YIELD 清除加回去，崩潰照舊，說明問題不來自清除位置，而出自「延後寫 READY」。補測 SMP（雙核配置）後判別式同樣有效，重複釋放只在單核路徑觀察到；作者同時更正了自己此前「SMP 未測」的說法。結論建議：判別式值得保留，但以 #11907 的「先存 stat_before 再判斷」為基礎推進，#6645 若要繼續需先查清單核下的二次釋放。

1.2 動態模組未初始化全域性變數修復：BSS 段分配指標不推進等四處缺陷一併處理（10-21）

日期：2026-10-21 21:09（建立時間）　來源：PR #11915、Issue #5705

貢獻者 usualtreee 針對 2022 年 3 月報告的 #5705 開出修復，問題在當前主線 1c801efa 上仍可復現。缺陷集中在可重定位模組（ET_REL）載入路徑 dlmodule_load_relocated_object()，即 Cortex-M 等啟用 RT_USING_MODULE 的板級所走的路徑：其一，BSS 段（SHT_NOBITS）載入後分配指標不推進，多個 NOBITS 段會重疊在同一塊記憶體；其二，段符號重定位公式缺少段連結地址修正；其三，SHN_COMMON 符號（tentative 定義的未初始化全域性變數）被靜默跳過，原因是程式碼去讀 shdr[0xfff2] 取段名得到垃圾值後不匹配；其四，該路徑從不構建 module->symtab，dlsym() 對 ET_REL 模組永遠失敗。

修法對應四點：BSS 段載入後按段大小推進指標；rodata/bss/data 段重定位統一為「段載入地址 − 段連結地址 + 符號值」；為 SHN_COMMON 單獨分配公共塊，並把該分支前置到段名匹配之前以避免越界讀；從 .symtab 收集全域性函式符號構建 module->symtab。改動兩個檔案 +147/-9，在 qemu-vexpress-a9 上用三個測試模組驗證：修復前 ET_REL 模組 dlsym 失敗，修復後成功且兩個未初始化全域性變數地址（0x600d2008 與 0x600d2004）互不重疊、特徵值寫入回讀透過，兩個 ET_DYN 模組結果不變。提案已過 CLA，處於 components 組評審。

二、安全與穩定性跟進

2.1 NFS 讀路徑以服務端計數做 memcpy 長度：一次 cat 即可覆蓋返回地址（10-22）

日期：2026-10-22 02:13（建立時間）　來源：Issue #11917、dfs_nfs.c

貢獻者 XueDugu 新開 NFS 客戶端缺陷單，屬可直接利用的記憶體破壞。nfs_read() 把請求長度限制在 1024 位元組以內，但複製時用的是服務端回覆裡的 READ3resok.count，既不與呼叫方請求長度比較，也不與同一回覆裡解碼出的資料長度比較；XDR 解碼側用 xdr_bytes(..., ~0) 作上限，長度校驗永遠不觸發。兩個計數字段在協議裡相互獨立，惡意服務端完全可以對一次 80 位元組的請求回 count = 512 加 512 位元組資料。

後果落在內建的 cat 命令上：dfs_file.c 用 char buffer[81] 承接讀取，單次 cat 一個檔案即可越過緩衝尾部最多約 430 位元組，覆蓋 finsh 執行緒棧上的返回地址。缺陷由 2010-05-20 的提交 0fbfdec40d 引入，自 v1.2.0 起的每個版本都受影響，含 v5.3.0 與當前主線。作者在 QEMU vexpress-a9 與 RP2350 實板上分別復現；NFS 客戶端自己組裝 AUTH_SYS、走無認證的 UDP，掛載的服務端或路徑上的注入者均可控制溢位內容。該單目前未被認領。

2.2 raw-API DHCP 服務端選項遍歷缺邊界：最多越過 1500 位元組緩衝 4 位元組（10-21）

日期：2026-10-21 15:49（建立時間）　來源：Issue #11913、dhcp_server_raw.c

另一位研究者 K-ANOY 報告 raw-API DHCP 服務端的越界讀。選項查詢函式只保證返回指標落在緩衝區內，遍歷時 buf[1] 未先校驗 buf + 1 < end，末尾只剩一個位元組的選項頭會讀出界一位元組；呼叫方隨後按固定寬度取值（請求 IP 讀 4 位元組、訊息型別讀 1 位元組），把選項頭擺在尾部即可讓 opt[2]..opt[5] 越過 1500 位元組的 pbuf 堆塊最多 4 位元組。同一目錄下基於套接字的 dhcp_server.c 恰好做了這些檢查——長度是否越界、宣告長度是否有效、length < 4 與 length < 1——反證 raw 版本缺的正是這幾道。

觸發條件只是同網段任意主機向 UDP/67 發一個選項區被截斷的報文，無需認證；作者在 ASan 下完成邏輯級復現，並指出被讀出的值只用於比對與分支，未直接外傳。該單已打 bug 與 component: net 標籤，尚未認領。

四、生態與廠商適配

4.1 ESP-IDF v6.1 包側合入：C3/C6 出現用 RT-Thread 替換 FreeRTOS 的官方開關（10-21）

日期：2026-10-21 15:23（合入時間）　來源：RT-Thread-packages/esp-idf PR #18

RT-Thread-packages 的 esp-idf 包完成自 5.1 到 6.1.0 的整包升級併合入，變更檔案兩萬餘。相對官方 v6.1，這次合入帶了三處 RT-Thread 側的結構性改動：新增 components/rtthread/（C3/C6 的移植層、rtconfig.h、board/context、CMake 與連結指令碼），新增 components/riscv/vectors_rtthread.S，並在 FreeRTOS、esp_system、esp_timer 等處加 CONFIG_IDF_RTOS_RTTHREAD 開關路徑；menuconfig 裡對應「Component config → FreeRTOS → Extra → Replace FreeRTOS with RT-Thread」。對 RISC-V 而言這一步的意義在於：C3、C6 屬 RISC-V 核心（與 Xtensa 的 S2/S3 不同），此前只能在 IDF 5.x 上按舊整合方式跑 RT-Thread，現在拿到的是 6.1 底座加一條官方承認的核心替換通道。

4.2 BSP 側同批提案阻塞解除：C3 十三個配置全透過，上板待驗（10-21）

日期：2026-10-21 15:24（評論時間）　來源：PR #11870

與包側配套的主倉提案 #11870 在本視窗獲得維護者一句「esp-idf 已合」的回覆，此前的阻塞點消除。該提案改動 55 個檔案 +4554/-333：C3 與 C6 分別適配 ESP-IDF v6.1 的相容面（portmacro.h 的 FreeRTOS V11 宣告、sections.ld、port.c、main.c、rtconfig.py 及 ADC/SPI 驅動小改），並把 RISC-V 工具鏈從 gcc 11.2（esp-2022r1）升到 gcc 15.2（esp-15.2.0_20251204），CI workflow、docker 與 tools/ci 同步調整。作者給出的驗證是 C3 十三個 attachconfig 配置全部編譯透過、C6 預設配置編譯連結透過，硬體上板仍待補；ESP32-S3 的移植與 FreeRTOS 相容層的改動另開提案，不在這一筆裡。

4.3 OSPI 與 OctaFlash 進入元件層：SFUD 支援 1-1-1 與 8-8-8 兩種模式（10-21）

日期：2026-10-21 15:22（建立時間）　來源：PR #11912

現有驅動層只有 SPI 與 QSPI 通路，經 SFUD 訪問八線 Flash 沒有原生路徑。本提案在元件層補 OSPI：新增匯流排、裝置、配置與訊息定義及傳輸助手，同時保留既有 SPI/QSPI 路徑；把 OSPI 傳輸與器件探測接進 SFUD，覆蓋讀、寫、擦與狀態查詢，並在器件表裡加入 MX25LM51245G 用於驗證。為跑通整條鏈路，另加通用 STM32 OctoSPI 底層驅動 drv_ospi.c（504 行）與 L4 系列配置頭，並在 stm32l4r9-st-eval 板級補 OCTOSPI1 的引腳、時鐘與 MSP 配置及進入 OPI STR/DTR 模式的輔助函式，順帶修掉該板級堆與連結佈局造成的 .bss 重疊。改動 32 個檔案 +3728/-956，四個提交，CLA 已籤，評審已指派 STM32 組三位維護者；作者報告已在實板上以 GCC 構建執行，1-1-1 與 8-8-8 兩種模式均可被 SFUD 識別。

4.4 Cortex-A 的 GIC 列印函式修正格式符：%p 傳非指標屬未定義行為（10-21）

日期：2026-10-21 18:00（建立時間）　來源：PR #11914

libcpu/arm/cortex-a 下 GICv2 與 GICv3 的資訊列印函式存在四類格式說明符與實參型別不匹配：實體地址是 rt_uint32_t 卻用 %p 列印，屬未定義行為；GIC 版本號是 unsigned long、最大中斷號與中斷號是 unsigned int，卻都用 %d。以 -Wall -Wformat 編譯 Cortex-A 板級時這些全部報警。提案把 %p 改為 0x%08x、%d 改為 %u，並對由 0xfUL 取出的版本號加顯式 unsigned int 轉換，兩個檔案 +64/-40，只動格式符不動執行時邏輯。

4.5 睿擎 V1.8.4 與新 IDE：編碼器、MIPI RGB666、GPIO 上下拉、GD32H7 工程支援（10-21）

日期：2026-10-21 11:50（釋出時間）　來源：電子工程專輯：睿擎平臺 V1.8.4 釋出、睿擎文件中心

睿擎平臺釋出 V1.8.4，SDK 側 6 項新增、4 項修復，RuiChingStudio IDE 同步升到 V1.5.62。新增能力集中在 RC3506 的外設與顯示：加入 QY1503 絕對值旋轉編碼器驅動，走 SSI 介面並提供正交脈衝 PWM 輸出示例，面向電機閉環與角度測量；MIPI DSI 補 RGB666（18 位色深）適配，顯示格式與 lane 數經裝置樹配置；開放 mipi_display_start() 介面，讓應用自行決定顯示初始化時機，便於安排顯示與背光的上電順序；GPIO 新增 PIN_MODE_INPUT_PULLUP 與 PIN_MODE_INPUT_PULLDOWN 兩種輸入模式，省掉外部上下拉電阻；新增 amp_device 除錯命令，可檢視 AMP 架構下裝置歸屬（RT-Thread 側或 Linux 側）、中斷親和性與時脈頻率。IDE 側新增 GD32H7 系列的工程建立、構建與 J-Link/DAP-Link 下載除錯支援，並最佳化 GD32H7 與 RK3576 工程的連結流程；完整更新日誌與 SDK 已同步到文件中心。

五、行業應用

5.1 睿擎 V1.8.4 的工業現場修復：EtherCAT 中斷親和性、telnet 下 netstat 卡死、UART DMA 波特率（10-21）

日期：2026-10-21 11:50（釋出時間）　來源：電子工程專輯：睿擎平臺 V1.8.4 釋出、睿擎更新日誌

同一版本的四項修復全部指向工業現場：EtherCAT 的任務與中斷此前未繫結同一 CPU，中斷預設落在 CPU0，多工切換時偶發訪問衝突並宕機，修復後兩者繫結同核；telnet 遠端執行 netstat 會阻塞無響應，已修；UART DMA 示例設定波特率失敗，根因在 DMA 串列埠初始化流程，已修正；4.3 寸屏示例調高背光 PWM，改善戶外可視性。結合前一期已報道的 EG1200 工業閘道器虛擬網口與 NFS 掛載、以及基於 RC-Pi-3506 的 ROS2 輪轂電機運動控制方案，睿擎這條產品線本期呈現的是「閘道器側聯網能力」與「運動控制側實時性」兩條並行的推進，修復項也多來自實際專案反饋而非內部測試。

六、總結與趨勢觀察

6.1 本期趨勢

  • 排程器討論從「各提各的」走向「比對實現」：三年掛起的 #6645 被重新核對，其判別式與 #11907 獨立收斂，但兩種實現手段在記憶體安全上分出高下——延後寫 READY 在單核引出 idle 回收路徑的二次釋放，儲存舊狀態的寫法沒有。這類跨提案的橫向比對比單條補丁更有決策價值，也讓 #11907 事實上成為推進基線。
  • 缺陷報告持續由外部研究者驅動，且帶完整影響面：一天兩筆記憶體問題，NFS 棧溢位的引入提交可回溯到 2010 年、影響自 v1.2.0 起的全部版本，DHCP 越界讀則以同目錄另一個實現的檢查項反證缺失點。兩份報告都給了復現環境與觸發條件，修復成本因此大幅降低。
  • RISC-V 側拿到一條核心替換通道：ESP-IDF 6.1 整包升級合入後，C3/C6 可透過 CONFIG_IDF_RTOS_RTTHREAD 用 RT-Thread 替換 FreeRTOS，工具鏈同時跳到 GCC 15.2；主倉 BSP 提案的阻塞點同日消除，只差上板驗證。這是本週期內 RISC-V 相關最有分量的一步。
  • 主線靜止、版本停在九月：連續三日零提交、零合入，v5.4.0 只有版本宏。活動全部集中在在審提案、缺陷單與包倉庫，與官方渠道停更形成同一種節奏。
  • 廠商平臺按版本穩定迭代，且把現場問題納入修復：睿擎 V1.8.4 的六項新增與四項修復都對應具體場景（編碼器閉環、MIPI 屏適配、AMP 除錯、EtherCAT 親和性），IDE 同步擴到 GD32H7，說明工業平臺的競爭力正從「能不能跑」轉向「現場穩不穩」。
