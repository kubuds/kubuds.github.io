一、核心與版本動態

1.1 瑞薩 RZ/N2L 中斷重複分發修復合入：Cortex-R52 trap 層與 FSP 向量表雙重分發致 CANFD 使能後串列埠中斷錯掛（PR #11765）

日期：2026-09-10（10:09 北京時間合入）　來源：RT-Thread/rt-thread commits（PR #11765）

視窗內主倉庫唯一一筆功能性合入，也是本日最有分量的核心級修復。PR #11765 [libcpu][cortex-r52] Fix duplicate interrupt dispatch on Renesas RZ（CYFS 提交、Rbb666 合入）於 09-10 上午正式進入 master，改動集中在 libcpu/arm/cortex-r52/trap.c（+25/-27，單檔案）。

問題根因由提交者描述得很清楚：RZ/N2L 平臺使用瑞薩 FSP（Flexible Software Package）管理中斷向量，而當前 Cortex-R52 的 trap 處理在呼叫 bsp_common_interrupt_handler() 之後，又把 GIC 的 INTID 當作 FSP 向量表索引、再經 RT-Thread 的 isr_table 分發一次——形成雙重分發。使能 CANFD 後，UART RX 的 GIC INTID 321 會錯誤命中 g_vector_table[321] 的 CANFD TX ISR，表現為控制檯敲回車即進入錯誤中斷並觸發 data abort。修復方向是去掉多餘的一次分發，讓中斷沿單一鏈路進入。

該 PR 08-28 建立，評審約兩週後於 09-10 合入，屬瑞薩 BSP 方向又一處平臺級正確性修復。同步觀察：同屬瑞薩與底層方向的長期 PR #11228（klibc 位元組對齊訪問引發的硬體錯誤）與 #11313（瑞薩 clock_timer 分頻設定）在 09-10 上午均有更新，仍在評審佇列中，瑞薩/KLIBC 線的評審節奏正在加快。

1.2 Rust 元件構建指令碼去除 clean 階段的 toml 依賴（PR #11791）

日期：2026-09-09（13:31 北京時間合入）　來源：RT-Thread/rt-thread commits（PR #11791）

主倉庫視窗內另一筆合入，改動為 components/rust/examples/modules/SConscript（+3/-2），標題 [rust][build] Avoid toml dependency during clean。執行 clean 目標時不再依賴 toml 解析，使清理流程在未安裝相關 Python 依賴的環境下也能完成。PR 09-09 12:56 建立、13:31 合入，全程約 35 分鐘，是本日流轉最快的一筆；提交者 CYFS，合入者 Rbb666。

這筆改動本身很小，但與視窗內另兩筆 Rust 相關動作合看，可觀察到 RT-Thread 的 Rust 元件（rust 元件示例模組）正處在持續打磨期：構建指令碼的健壯性最佳化屬於典型的「掃地」型維護，通常出現在一門新語言支援從「能跑」走向「日常可用」的階段。

日期：2026-09-09 ~ 2026-09-10　來源：RT-Thread/rt-thread pulls

  • [bsp/renesas][drivers] Fix SCI SPI runtime configuration and transfer errors（PR #11792，CYFS3，09-09 17:25 建立，2 個提交、+254/-193）：排查 RZ/N2L EtherKit 的 SCI SPI 迴環問題時，發現共享 SCI SPI 驅動存在數處缺陷——RZ 分頻介面把 false 當作分頻結果指標傳入且未使用 FSP 配置中的實際時鐘源；執行時配置未能可靠傳遞給 FSP，重複配置也未正確關閉舊例項；配置過程把 RT-Thread 的位寬單位從 bit 誤改為 byte；收發等待超時或出錯後仍返回傳輸長度，導致呼叫方誤判成功。09-10 上午該 PR 仍有更新，為瑞薩驅動線的下一筆重點評審物件（與 1.1 同屬 RZ/N2L EtherKit 平臺）。
  • [docs] point QEMU Linux quick start at qemu-nographic.sh（PR #11793，shiptux，09-09 23:53 建立，+12/-0）：指出快速上手文件只提 ./qemu.sh，而該指令碼傳 -serial stdio 卻不帶 -nographic，QEMU 會嘗試開啟 GTK 視窗，在無顯示環境或 SSH 下卡在 gtk initialization failed；BSP 本身已提供 qemu-nographic.sh 並在 README 中推薦用於伺服器場景，故補充文件說明。延續 09-08 兩筆文件 PR（#11789/#11790）的同一貢獻者修文件節奏。
  • Harden FinSH console switching against unsafe output devices（PR #11455，Copilot，09-10 09:26 關閉，未合入）：該 PR 06-09 建立、累計 5 個提交（+290/-18），目標是給 rt_console_set_device() 加裝置校驗，只允許提供控制檯安全開啟標誌或具備中斷/DMA 非同步傳送能力的裝置被切換為控制檯，並保留舊控制檯直到新裝置校驗透過，以消除 ISR 或故障處理上下文中向阻塞裝置列印導致的崩潰路徑。開放三個月後關閉未合併，判斷為方案未獲採納（同批的另一隻 Copilot 提交 #11454 sys_getaddrinfo 指標加固仍在評審）。視窗內主倉庫另有新開 PR 3 只、合入 2 筆、新建 Issue 0 只。

三、生態與廠商適配

3.1 兆易創新生態倉庫 GD32 四筆 BSP 集中合入：103c / 107c / 205r / e503v 向新 BSP 架構升級（09-09）

日期：2026-09-09（13:52 ~ 19:56 北京時間）　來源：GD32-MCU-IOT/gd32_rt-thread commits

topic:rt-thread 生態倉庫中，GD32 系列下游倉庫（GD32-MCU-IOT/gd32_rt-thread）在視窗內集中合入四筆 BSP 分支 PR，是當日生態側體量最大的一組動作：

  • gd32103c-eval（PR #69，13:52 合入，26 檔案 +4783/-2341）：為 GD32F103VCT6（Cortex-M3）補齊 BSP 板級初始化與 IDE 工程模板，使其可在 Keil（AC6）/ GCC / IAR 三工具鏈下編譯燒錄並跑通 utest，新增 F10x 驅動配置頭與 board 級初始化。
  • gd32205r-start（PR #65，15:09 合入，18 檔案 +6294/-6283）：新增 board_msd_init.c 完成 UART GPIO 初始化，移除 UART RX DMA 相關 Kconfig 與 rtconfig.h 選項，工程檔案更新至 chip family GD32F20xxE。
  • gd32107c-eval（PR #66，19:38 合入，15 檔案 +4213/-2439）：升級到新的 GD32 BSP 架構，新增 f10x 的 dma/uart/spi/i2c 配置頭與 SOC_SERIES_GD32F10x 系列支援、board_msd_init.c。
  • gd32e503v-eval（PR #67，19:56 合入，35 檔案 +10876/-2525）：適配 e503v 系統與常用外設，覆蓋 GPIO、I2C、SPI、USART、DMA。

四筆改動的共同主線是「向新 GD32 BSP 架構遷移」：統一補 board_msd_init.c 板級初始化、統一重排 Kconfig/.config 配置項、統一重新整理 Keil/IAR 工程檔案。貢獻者為 junying2025 與 yuanshuo0，屬兆易創新生態側主導提交。該倉庫為 RT-Thread 下游倉庫而非主倉庫，內容是 GD32 器件家族（本次均為 ARM Cortex-M 核心）在 RT-Thread 上的板級適配，作為廠商生態推進的觀測視窗收錄。

3.2 軟體包索引新增 STM32N6 HAL SDK 包索引（PR #2037）

日期：2026-09-09（15:26 北京時間合入）　來源：RT-Thread/packages commits（PR #2037）

RT-Thread 軟體包索引倉庫視窗內新增一筆：[hal_sdk] add stm32n6 軟體包倉庫索引（yans6666 提交，09-09 14:10 建立、15:26 合入，Rbb666 評審）。這是 STM32N6 系列 HAL SDK 的包倉庫索引落地，使開發者可在包管理器中直接引用 STM32N6 的 HAL 支援。STM32N6 為意法半導體帶自研 NPU 的高階 MCU 系列，索引落地意味著該平臺的 RT-Thread 接入進入軟體包化階段，與近期 STM32 方向的多筆驅動適配（BDMA for SPI、乙太網驅動適配新 HAL API）形成同一條廠商線。
