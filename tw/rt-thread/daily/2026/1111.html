一、核心與驅動合入

1.1 RISC-V APLIC：電平中斷撤銷後不再補發 MSI（11-10）

日期：2026-11-10 16:58（合入時間）　來源：提案 #11966

一個檔案、14 行新增、1 行刪除，改的是 libcpu/risc-v/common/pic/pic-riscv-aplic.c，作者 zijunteng238-dot，11 月 1 日提交、本期合入。上期報告在待審佇列裡點名過這一筆，今日落地。

現象是 QEMU 8.2.2 上跑 bsp/qemu-virt64-riscv：RV64、四核 SMP、開 AIA（APLIC/IMSIC），一個每 1000 毫秒列印一次的計數程式只輸出 RISC-V test: 0 就停住。根因在電平中斷的 EOI 路徑——驅動無條件寫 setipnum_le，裝置其實已經撤銷中斷，舊版 QEMU 仍據這次寫入補發一條 MSI，形成持續的虛假中斷，把系統定時器壓住，延時執行緒再也回不來。修法是 EOI 時先讀 in_clrip 裡該輸入的整流狀態（已按中斷極性折算），只有裝置仍在拉高才寫 setipnum_le，既保留電平中斷的重觸發能力，也不給已撤銷的源補發機會。

同一提案把 qemu-virt64-riscv 的 main.c 從列印一次改成 0 到 9 的計數迴圈，每次列印後延時一秒，用來觀察修復後的執行緒恢復。驗證覆蓋三種配置：開 AIA 四核並關閉網路/NVMe/virtio-console/PCI serial、關 AIA 四核、開 AIA 四核預設裝置組合，三者均能完整輸出十行；未覆蓋真實 APLIC 硬體、低電平外設與其他 QEMU 版本。

QEMU 上游已自行修掉這一模擬缺陷，RT-Thread 這一筆屬於給舊版模擬器的相容補丁——它修的不是核心邏輯錯誤，而是「驅動按規範寫、模擬器按缺陷解」這類只在虛擬平臺上出現的錯位。

二、安全加固批次：一天十一筆邊界檢查

2.1 六項 2024 年 CVE 集中收口（11-10）

日期：2026-11-10 01:04 ~ 06:45（提案時間）　來源：提案列表

11 月 10 日一天之內，同一位報告者（cms19859230182-lang）提交十一筆邊界檢查補丁，其中六筆直接對應 2024 年披露的 CVE，編號相鄰、修法同構——都是「先判長度，再進複製」：

  • 提案 #12017：FinSH 拼目錄路徑用無界 rt_sprintf / rt_strcpy / strcat，自動補全按 DFS_PATH_MAX 重新分配並封頂各段複製，長度判斷由 > 改回 >=（補上 NUL 的差一），對應 CVE-2024-25390、議題 #8286。
  • 提案 #12020：rt_wlan_send_to_thread() 的 len 是有符號 int，負值會讓 sizeof + len 與 memcpy 按巨大 size_t 處理，改為 len < 0 直接返回 -RT_EINVAL，對應 CVE-2024-25388、議題 #8285。
  • 提案 #12022：rt_random 是可預測 LCG 且預設種子弱，首次讀取時混入 rt_tick_get() 與可選硬體隨機源，並在註釋與 Kconfig 裡標明非 CSPRNG，對應 CVE-2024-25389、議題 #8283。
  • 提案 #12019：var_export 填充 ve_exporter_tab[2048] 時無容量限制，生產構建關掉斷言後直接寫穿，改為填滿即停、執行時夾住計數、零元素不進氣泡排序，對應 CVE-2024-25392、議題 #8290。
  • 提案 #12018：rt-link 組幀前不校驗最終幀長，超長載荷寫穿靜態 sendbuffer，改為先判 data_len 與幀長再 memset/memcpy，對應 CVE-2024-25395、議題 #8289。
  • 提案 #12021：YMODEM 的 _rym_send_begin 用無界 rt_sprintf 寫協議緩衝，上傳下載用 rt_strncpy(..., DFS_PATH_MAX) 可能不補 NUL，改為 rt_snprintf 封頂、上限 sizeof-1 並顯式補零，對應 CVE-2024-25394、議題 #8291。

六筆的共同點在於「斷言當邊界用」：RT_ASSERT 在生產配置裡常被關掉，此前多處把斷言當作最後一道檢查，實際等於沒有檢查。這一批把限制改成執行時判斷，斷言只留作除錯輔助。

2.2 裝載器與核心物件：libdl 重定位、LWP IPC 屬主校驗（11-10）

日期：2026-11-10 01:40 與 01:36（提案時間）　來源：提案 #12016、提案 #12015

這是本批次技術分量最重的兩筆，改的都是信任邊界。

#12016 改五個檔案、205 行新增、37 行刪除。dlmodule 計算重定位寫目標時用 mem_space + r_offset - vstart_addr 而不校驗範圍，一個構造過的 .mo 可以讓 r_offset 下溢或上溢，在重定位階段直接寫進核心記憶體。修法是新增 dlmodule_check_rel_target()，用防溢位的算術確認目標區間落在模組記憶體內，接進 ARM、RISC-V、x86 三個重定位器；同時補上 ELF 節頭索引（sh_link、e_shstrndx）、符號表索引（ELF*_R_SYM）與 ET_REL 節邊界檢查，並讓 dlelf.c 在失敗時中止載入、釋放 section_load_addr。對應 10 月 18 日的缺陷 #11898。

#12015 改三個檔案、284 行新增、44 行刪除。RT-Smart 的 LWP IPC 系統呼叫原先把使用者傳入的裸物件指標直接送進 rt_sem_* / mutex / event / mailbox / mq / timer，偽物件即可造成任意核心讀寫。修法是新增 lwp_user_object_get() 與 lwp_user_object_put()：解引用之前先拒絕使用者空間地址，要求控制代碼存在於呼叫者的使用者物件 AVL 樹，比對 rt_object_get_type()，並在系統呼叫全程（含所有錯誤路徑）持有一份引用；lwp_ref_count 同時覆蓋屬主與在途引用，核心物件要等最後一個引用消失才銷燬。對應 10 月 31 日的缺陷 #11960。

兩筆都沒有構造攻擊樣本，驗證停留在靜態審計與編譯層面，這也決定了它們短期內不會進 release。

2.3 記憶體與網路：記憶體池斷言誤報、DHCP 租約過期回收（11-10）

日期：2026-11-10 01:04 與 06:45（提案時間）　來源：提案 #12014、提案 #12024

#12014 修的是一個假警報，但造成的是真實的系統停擺：rt_smem_free() 釋放「最後一塊、其 next 指向 heap_end 哨兵」的塊時會誤觸發 MEM_POOL 斷言。修法顯式接受 mem->next == heap_end 這種偏移，其餘情況仍保持原有校驗；作者明確拒絕改用 mem->prev 判斷，理由是 prev 指向上一塊（首塊為 0），會把校驗放鬆。附帶的 core.mem 用例模擬只剩使用位的哨兵場景，驗證整塊合併。對應 2025 年的舊缺陷 #10632。

#12024 修的是 DHCP 服務端的賬期：lease_end 寫入後從不被讀取，租約永不過期、地址永不回收；順帶發現 DHCP_DEFAULT_LIVE_TIME（0x80510100）經 PP_HTONL() 後線上上是約六十八年，與「按天回收」的語義完全不符，一併改為 86400 秒。改動把租約改成絕對過期時間，分配前惰性回收過期節點，命中、新建、ACK 三條路徑統一續租。驗證只做了 lwIP 2.0.3 / 2.1.2 / 2.2.1 三個版本的語法檢查。

這筆屬於「配置常量寫錯方向」的典型：宏名說的是存活時間，取值卻是把納秒級的數當秒用，不出問題只是因為沒人真去等它過期。

三、議題與修復閉環

3.1 ptyfs 控制代碼洩漏：報告當天出修復（11-10）

日期：2026-11-10 14:04（議題）/ 11-11 02:14（提案）　來源：缺陷 #12023、提案 #12029

ptyfs_unregister_pts() 把 pts 檔案從根連結串列摘掉、回收單元號，卻不釋放 ptyfs_register_pts() 分配的 struct ptyfs_file。單元號被複用之後，反覆 open() / close() /dev/pts/* 就能持續洩漏記憶體，普通使用者即可觸發。報告者 XueDugu 附了迴圈復現。

十二小時後維護者 BernardXiong 提交 #12029（三個檔案、11 行新增、2 行刪除），在登出路徑上把 pts 檔案一起釋放，目前待審。這是本期唯一一筆「報告與修復同窗閉環」的條目。

3.2 legacy USB host：一筆修復被維護政策關閉（11-10）

日期：2026-11-10 18:13（提案）/ 11-11 00:50（議題）　來源：缺陷 #12026、提案 #12027

缺陷描述的是老 USB 主機棧（components/legacy/usb/usbhost/）：裝置描述符的 bLength 未經校驗就被當作讀取長度，進而寫進靜態裝置陣列，惡意 USB 外設可造成越界寫與控制流劫持。報告者在 qemu-virt64-aarch64 上端到端復現，並註明主倉 master（自報 v5.4.0-dev，核查於提交 5d1fb66d）在 11 月 11 日重讀時仍未修復。

維護者隨後提交 #12027（一個檔案、8 行新增）做長度校驗，隨即自行關閉並留言：「這個是 legacy 的程式碼，將不再持續修正、維護。」修復方向沒有爭議，關閉理由是維護範圍——這條路徑上的已知攻擊面，此後要由使用者自己評估。

3.3 vDSO 時鐘常量：議題成立、修法被否（11-10）

日期：2026-11-10 20:39（議題）　來源：缺陷 #12025、提案 #12028

用 newlib 工具鏈編譯 RT-Smart 的 vDSO 使用者程式碼時，CLOCK_MONOTONIC 與 GNU 系時鐘 ID 均未定義：newlib 只在 _POSIX_MONOTONIC_CLOCK 下暴露前者、在 _GNU_SOURCE 下暴露後者，而 vDSO 的自由編譯配置兩者都沒設。提案 #12028（一個檔案、22 行新增）選擇在本地補定義，維護者判定「這個是錯誤的修正，應該關閉」，當日關閉。

同一現象下兩種處理方式的分歧很清楚：一種是在編譯單元裡補宏，讓構建透過；另一種是讓自由編譯配置與 POSIX 特性宏對齊。後者沒寫進提案，缺陷本身仍開放。

4.1 ESP32-S3 移植的半截落地：構建指令碼進倉、BSP 不在倉內（11-10）

日期：2026-11-10 11:53（合入時間）　來源：提案 #11844、bsp/ESP 目錄

一筆容易被誤讀的合入。提案 #11844 的標題是「修正 xtensa_context.h 的包含路徑」，正文寫的卻是新增 bsp/ESP/ESP32_S3 與 libcpu/xtensa/esp32s3 兩個目錄：ESP32-S3-DevKitM-1、Xtensa LX7、UART0 走 GPIO43/44、8MB DIO flash、應用在 0x10000、CI 新增 xtensa-esp32s3-elf GCC 12.2.0。

實際合入的只有一個檔案：libcpu/xtensa/esp32s3/ 目錄下的 SConscript，25 行。核查主倉 bsp/ESP 目錄，當前只有 ESP32_C3、ESP32_C6、libraries、tools 四項，沒有 ESP32_S3；libcpu/xtensa/esp32s3 下也只有這一個指令碼，沒有任何 C 原始檔。指令碼本身按 bsp/ESP/ESP32_S3 去解析 ESP-IDF 軟體包路徑，而該路徑目前不存在。

也就是說這是半個移植：CPU 埠的構建腳手架先進了主倉，BSP、節拍處理、sdkconfig 與板級驗證都不在。提案 9 月 28 日建立、11 月 10 日合入，六週里正文描述的其餘部分沒有一併落地。對使用者的現實含義是：現在拿不到可編譯的 ESP32-S3 BSP，指令碼引用的路徑暫時解析不到。

6.2 六項 CVE 與兩年半的時差

日期：2026-11-10　來源：CVE-2024-25388 等對應議題

六項 CVE 對應的原始議題編號在 #8283 至 #8291 之間，屬 2024 年的報告批次，到今天補齊約兩年半。這不必讀作懈怠：RTOS 專案的評審資源集中在晶片適配與版本釋出上，若非有人按清單回頭掃，這類「需要構造畸形輸入才能觸發」的條目會一直沉在佇列底部。

真正值得記的是修復方式的一致性——六筆都在補同一個洞：把斷言當邊界。斷言在生產構建裡會被關掉，這件事在嵌入式專案里人人知道，但把它當檢查用的程式碼仍成規模存在。

6.3 待審佇列 149 筆提案、365 個議題

日期：2026-11-11（核查）　來源：提案列表、議題列表

較上一期的 140 筆提案、362 個議題，提案增九筆、議題增三筆。構成很清楚：視窗內 2 筆合入、14 筆新增提案、2 筆提交後關閉，淨增九筆；議題側新增四筆（ptyfs、USB host、vDSO、PLIC 次序），其中一條來自上期已收錄的 PLIC 議題跟進。

上期點名的幾筆仍未合入：tty ioctl 使用者指標校驗（#11937，自 v5.1.0 起影響所有 RT-Smart 板，風險最高）、ivshmem 視窗校驗（#11993）、RISC-V FPU 上下文（#12006）、CAN 驅動重構（#11779）。今日新增的 #12015 與 #12016 正好覆蓋了 #11960 與 #11898 兩條核心級風險，但都還在審。

6.4 修復被政策關閉：legacy 程式碼的邊界

日期：2026-11-10　來源：提案 #12027

本期有兩筆提案由維護者本人提交後當日關閉，理由都不是技術不成立：一筆說修正方向錯（vDSO 補宏），一筆說這段程式碼進入不再維護狀態（legacy USB host）。後者更值得注意——缺陷描述裡明確寫了「惡意 USB 外設可造成越界寫與控制流劫持」，這是可物理接觸的攻擊面。

一個走過二十年的 RTOS 必然揹著 legacy 元件，宣佈不再維護是合理的資源決策；但對仍在用 RT_USING_USB_HOST 老棧的產品，這條宣告等於把安全責任轉移到整合方。專案文件裡如果能把這類「不再維護但仍在樹內」的元件列成清單，會比散落在單個提案評論裡更有用。
