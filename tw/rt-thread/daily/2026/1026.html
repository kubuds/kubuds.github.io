一、核心與版本動態

1.1 主線 72 小時只有兩筆提交：lwIP 迴環 netdev 合入，clang-format 規則細化帶 thread.c 示例（10-25）

日期：2026-10-23 17:09 與 2026-10-25 19:26（合入時間）　來源：PR #11859、PR #11893、主倉庫提交記錄

週末三天的視窗裡，master 只落了這兩筆提交，節奏與上一期「三日零提交後集中收尾」的判斷連得上：合入動作都發生在非工作時段（週五 17:09、週日 19:26），評審本身沒有停，只是開發側沒有新程式碼。

第一筆是 clang-format 規則的收口，2 個檔案 +83/-77，只動 .clang-format 與 src/thread.c。分支名帶著討論線索 style/clang-format-discussion-11653，兩個提交日期都是 10-09，主體是「對齊、花括號換行與空格規則」的細化，第二個提交把 src/thread.c 按新規則整體格式化作為示例。也就是說這是一筆拖了兩週的評審收尾，不是新工作。提案裡還記了一條工具事實：index++ 這類寫法在 clang-format 18.1.8 與 23.1.3 上都會保持原樣，沒有對應配置項可以強制改寫，校驗用 --dry-run --Werror。

第二筆是 lwIP 迴環裝置進 netdev 框架，3 個檔案 +54/-0。此前 lwIP 的迴環口沒有註冊成 netdev，導致兩類問題：走 127.0.0.1 的工具鏈跑不起來；沒有物理鏈路的網路名稱空間裡沒有預設可用的介面。改動新增 RT_LWIP_USING_LOOPBACK 配置項，把 lo／lo0 註冊為 netdev 並置為 link up，在未指定介面時選迴環作預設介面，同時把 RAW 接收郵箱調大以容納迴環回顯。驗證配置給的是 qemu-virt64-riscv，提案裡寫明「本地未編譯，由 CI 驗證構建」——這與上個月多筆提案的放行口徑一致：合入以構建透過為條件，上板另行跟進。

版本側依舊沒有動作：最新發布物與標籤還是 09-10 的 v5.3.0，10-17 那筆 v5.4.0 的版本宏至今沒有配發布說明、二進位制或預釋出標籤。

1.2 qemu-virt64 開啟 RT-Thread Smart：riscv64 關 SMP、ext4 與 elm 掛塊裝置、ptyfs 與 procfs 上掛（10-25）

日期：2026-10-25 19:50（最後更新）　來源：PR #11896

這份提案 14 個檔案 +1263/-1075，把 qemu-virt64-riscv 與 qemu-virt64-aarch64 兩個 BSP 的 RT_USING_SMART 開啟。此前這兩個 virt 平臺名義上支援 Smart，但 virtio 塊裝置沒有標準的根檔案系統初始化流程，pty 也沒有掛載點，很多特性在 QEMU 下根本沒法測。

改動可以拆成四塊：riscv64 側關掉 SMP，與 Smart 的單核配置對齊；新增一段初始化流程，在 virtio-blk0 上掛 ext4 或 elm；把 ptyfs 掛到 /dev/pts、procfs 掛到 /proc；重新生成 .config 與 rtconfig.h。構建驗證寫明 riscv64 用 RISC-V musl 通用工具鏈、aarch64 用 aarch64 musl 工具鏈，本地未跑、由 CI 驗證。

值得注意的是依賴關係：這份提案顯式依賴剛合入的 #11893（RT_LWIP_USING_LOOPBACK 配置符號），.config 是在 #11893 之上生成的，作者說明會在依賴合入後 rebase 並重新生成配置。這類跨提案的配置耦合在 qemu 平臺改造裡常見，也解釋了為什麼迴環口要先於 Smart 使能落地——沒有迴環，Smart 下大量依賴本機地址的測試跑不起來。

1.3 lwp_syscall.c 一萬一千行拆分：165 個系統呼叫入口按子系統分檔案，行為不變（10-25）

日期：2026-10-25 19:50（最後更新）　來源：PR #11894

components/lwp/lwp_syscall.c 單個檔案超過一萬一千行，把記憶體、檔案系統、socket、程序、IPC 與時間六類系統呼叫堆在一起，評審與檢索都很困難。提案把它拆到 components/lwp/syscall/ 目錄，按子系統分檔案，新增共享的系統呼叫分派表與內部標頭檔案，並在 LWP 的構建指令碼里註冊新目錄。

規模上這是本視窗最大的一筆：22 個檔案 +12223/-11638，幾乎全是移動與改名。提案自稱「機械重構，無功能變更」，並強調 165 個系統呼叫入口與行為完全保持不變。驗證同樣是「本地未編譯，CI 驗證」，配置是 CONFIG_RT_USING_SMART=y。

從工程角度看，這類拆分本身不產生新能力，但它決定了後續 lwp 缺陷（例如本期 2.2 的 sys_poll 迴繞）能不能在一個可讀的檔案裡定位。上一期記錄的那份 9PFS 長度收斂提案也屬於同一條線索：Smart 側的程式碼正在從「能用」轉向「可維護」。

二、安全與穩定性跟進

2.1 時間子系統一夜間四單連報：settimeofday 窄化、gmtime_r 負時間戳、timer_gettime 截斷，附一份 A 至 F 工作項調研（10-23／10-24）

日期：2026-10-23 21:04 與 2026-10-24 20:25（建立時間）　來源：Issue #11922、Issue #11923、Issue #11924、Issue #11927

10-23 晚間，同一研究者在 components/libc/compilers/common/ctime.c 上連著開了三單，加上次日的一份調研單，把時間子系統的語義問題一次性攤開。三單的基線都是 master 的 a59e72fb5c，全部為原始碼級隔離復現，未上板。

第一單是 settimeofday() 的型別窄化：校驗時先 (long)tv->tv_sec 強轉，在 time64／long32 的 32 位 ARM ABI 下（time_t 為 64 位有符號、long 為 32 位），合法的正時間戳會被轉成負數，於是在調 RTC 驅動之前就返回 -1 並置 EINVAL。作者用 GNU Arm Embedded 10.3-2021.10 做了型別尺寸與窄化行為的隔離驗證。

第二單是 gmtime_r() 對負時間戳的處理：函式返回非 NULL，但欄位非法。給出的四個對照值很直觀——-1 得到 1970-01-01 00:00:-1、-86400 得到 1970-01-00 00:00:00（yday 為 -1）、-31536000 的年份欄位變成 1970-01--364、-2208988800 應為 1900-01-01 卻得到 1970-01--25566。根因是取模取餘都用 C 的向零截斷語義，負輸入下餘數為負，而年份迴圈只能向未來走。

第三單是 timer_gettime() 的截斷：總剩餘納秒先存進 rt_uint32_t 再拆秒與納秒，10 秒即 100 億納秒，賦給 32 位變數直接丟失高位。受影響配置是 RT_USING_POSIX_TIMER 與 RT_USING_CLOCK_TIME 同時開啟。

第四單（10-24 20:25）不是缺陷而是調研：把 tick、clock_time、RTC、libc 與 VDSO 各自維護時間基線的問題整理成一份帶工作項的設計建議，列出十項不足（設時不統一、clockid 語義混亂、軟 RTC 假同步、迴繞與溢位、hrtimer 回退、PM 分叉、啟動授時狀態、NTP 版本邊界等），給出 A 至 F 六項可跟蹤工作項與 P0 至 P2 的優先順序，並明確普通 MCU 走完 A 至 D 即到階段性終點。該單自己宣告是靜態分析，未編譯未上板。

配套的修復提案已經開出兩筆：#11928 讓 settimeofday() 按欄位自身型別校驗、不再統一轉 long；#11929 處理 gmtime_r() 對紀元前時間戳的規範化。兩筆都在 10-24 提交，仍未合併。

2.2 32 位 RT-Smart 的 sys_poll 迴繞：8 位元組堆塊被當成 0x20000001 項遍歷，核心堆越界讀寫（10-24）

日期：2026-10-24 03:39（建立時間）　來源：Issue #11925

這份缺陷單在 10-24 凌晨提交，問題落在 components/lwp/lwp_syscall.c 的 sys_poll() 與 libc 側的 poll() 之間。使用者態傳入的 nfds 在計算分配大小時，nfds * sizeof(struct pollfd) 在 32 位目標上以 size_t 寬度運算，超過約 1.79 億項就會迴繞成一個小值——於是核心按 8 位元組的堆塊去做 0x20000001 項的遍歷，讀寫都落在堆外。

影響面按作者給出的口徑：僅 32 位 RT-Smart 受影響，64 位構建下乘積會提升到 64 位，超大分配直接以 -ENOMEM 失敗，不會迴繞。引入點是 2022-12-03 的 ecf2d821（sync branch rt-smart，#6641），首個受影響版本為 v5.0.0，v5.0.0 至 v5.3.0 與當前 master（5d1fb66d）均在列。復現用的是 bsp/qemu-vexpress-a9。

這條與上一期 9PFS、NVMe 那族「裝置或服務端可控的後設資料當長度用」不同：這次是使用者態可控的計數在窄位寬下回繞，屬經典整數邊界問題，但因為落點在系統呼叫入口與核心堆之間，後果直接是核心堆越界讀寫。該單目前無對應修復提案。

2.3 上一期合入的 ESP-IDF v6.1 適配在 master 上把 C3／C6 構建打紅，include 順序修復已提（10-25）

日期：2026-10-25 17:49（最後更新）　來源：PR #11926、PR #11870（上期合入）

上一期記錄的 ESP32-C3／C6 適配 ESP-IDF v6.1 於 10-22 合入，當時的上板一欄寫的是「待驗證」。兩天後 master 上的 C3／C6 構建轉紅：按提案描述，master 的兩次 CI 執行（40043597502、39929831359）復現了同一現象，並且所有 PR 的 RT-Thread BSP Static Build Check 與 MemBrowse Memory Report 都跟著變紅。

根因不在適配程式碼本身，而在構建順序。ESP-IDF 包在 components/rtthread/scons/ 下放了一個 FreeRTOS.h 的 scons shim，用 #include_next 轉發到 <freertos/FreeRTOS.h>，要求 RT-Thread 的 FreeRTOS-Wrapper include 目錄排在 shim 之後、ESP-IDF 自帶 FreeRTOS V11 核心頭之前。但兩個包的 SConscript 載入順序由目錄遍歷順序決定，並不穩定；一旦 ESP-IDF 先載入，#include_next 就解析到 V11 的頭，Wrapper 提供的 configNUMBER_OF_CORES、configMINIMAL_STACK_SIZE、configUSE_PREEMPTION 等預設值全部落空，編譯 drv_uart.c 時直接 #error。

修復提案只動 3 個檔案，把 FreeRTOS include 目錄順序固定下來。這條值得記一筆的原因不是缺陷本身，而是反饋鏈條：上期以「構建透過」為放行條件的合入，在本期被 CI 抓到了順序依賴，修復提案當天就開出來了。

2.4 既有缺陷提案的狀態盤點：NVMe 洩漏、9PFS 長度、tmpfs UAF、dlmodule 全域性量、FDT 深度均待合併（10-25）

日期：2026-10-25（核查時間）　來源：PR #11920、PR #11918、PR #11910、PR #11915、PR #11901

上期收錄的幾筆修復在視窗內都有更新，但都沒有合入，狀態停在「提案已開、等待評審」：NVMe 每遇一個非活動名稱空間漏分配（#11920，10-25 00:35 更新）、9PFS 把服務端長度欄位收斂到實際接收位元組（#11918，10-24 17:19 更新）、tmpfs 截斷到零長度時的釋放後使用（#11910，10-23 23:31 更新）、可載入模組未初始化全域性量（#11915，10-24 17:27 更新）。

視窗內補進來的兩筆是新的：一是 FDT 解平鋪的深度限制（#11901，10-25 15:49 更新），fdt_unflatten_single() 用固定 64 項的棧 np_stack 暫存遍歷路徑，壓棧前不查深度，深度超過 64 層的 DTB 會棧越界寫，作者在 qemu-virt64-aarch64 上覆現，修法是在解平鋪前用一條獨立的手工棧遍歷算出最大深度、超過 63 層直接拒絕；二是串列埠 rx_indicate 被誤清（#11931，10-26 01:34 更新），echo xxx /dev/uart0 之後控制檯不再響應，作者排除了「open_flag 被覆蓋」這條舊解釋——現在 rt_device_open() 在 OFLAG_MASK 匹配時根本不調驅動的 open——把真因定在 serial_fops_close() 無條件清 rx_indicate，而裝置仍被控制檯持有（ref_count 只從 3 降到 2）。

同一批裡還有兩筆驅動層的正確性修補：#11891 改 TIOCGWINSZ 不再借 finsh_getchar() 讀終端應答（原來會消耗輸入、且只在 tshell 執行緒可用），並在 termios 未變化時跳過 UART 重配以免復位 FIFO；#11885 修 utimensat() 對 UTIME_OMIT 的判斷取反，此前請求「不改 mtime」反而會覆蓋 mtime 並忽略呼叫方給的時間戳。

三、官方與社群活動

3.1 六屆 RISC-V 中國峰會的系統軟體視角報道刊出：RISC-V 瓶頸正從核轉向系統軟體（10-24）

日期：2026-10-24（釋出）　來源：電子工程專輯：端側 AI 成 RISC-V 新戰場、RT-Thread 專欄頁

RT-Thread 在電子工程專輯的專欄於 10-24 刊出一篇峰會側記，標題把落點放在「端側 AI 成 RISC-V 新戰場」。報道給出的峰會規模是 1 場主論壇、7 場平行分論壇加 Member Day 技術專場，議題覆蓋人工智慧、資料中心與高效能運算、軟體生態、嵌入式與物聯網、晶片設計與驗證、汽車電子與機器人。

3.2 GDR：把 RT-Thread 核心物件檢視搬進 GDB，QEMU 閉環覆蓋 3.1.x／4.0.x／4.1.x（10-25）

日期：2026-10-25（釋出）　來源：電子工程專輯：從 LoRaWAN 移植踩坑出發、GDR 倉庫

這是一篇少見地把「除錯腳手架」當正式工程來做的社群長文。起點是兩年前把 Semtech 的 LoRaWAN 協議棧 SWL2001 從 Zephyr 移植到一顆資源受限的國產微控制器上，底層是裁剪過的 RT-Thread Nano；四十多個 HAL 介面逐個對映，任何語義偏差都只在執行期暴露。真正的難點在觀測：FinSH 一跑，radio planner 的時序就被擾動，觀測行為改變了被觀測系統；GDB 原生只給指標，看一個訊號量要沿 rt_object_container 走連結串列、做 container_of 換算再 cast，十個物件就是五六十條命令。

GDR 的做法是把這類機械勞動固化成 GDB 的 Python 命令，提供三層能力：聚合命令（rtthread threads／timers／system／semaphores／objects）輸出全域性快照，執行緒表裡帶 StkUsed 與 MaxStkUsed 兩個基於棧填充模式的峰值水位；便捷函式 $gdr_thread("worker2") 與 $gdr_object(...) 返回原生 gdb.Value，後續欄位鑽取仍用 GDB 表示式；pretty-printer 把核心物件摺疊成一行摘要，例如互斥量直接顯示持有者。

與 FinSH 的本質區別是完全無侵入：所有資訊只透過 GDB 讀符號與目標記憶體，不呼叫韌體裡的任何函式，因此既適用於根本沒有 shell 的 Nano 場景，也適用於 HardFault 之後已經無法執行程式碼的死後分析。工程上幾個決定值得記：不再自動探測 RTOS（改為顯式 gdr init rtthread 4.0.5，但用符號存在性探測 SMP、堆管理器、IPC 元件這些配置差異）；所有佈局知識集中在一個檔案裡並標註 COUPLED；用 QEMU 啟動真實韌體做 pytest 斷言，CI 矩陣覆蓋 Cortex-A9（3.1.0 至 3.1.5、4.x）與 RV64（4.0.4 至 4.1.1）。作者也寫明瞭邊界：本人已不做微控制器開發，工具只在 QEMU 矩陣裡驗證過，尚未經真實板卡檢驗；後續計劃是 agent skill、VSCode 外掛與 FreeRTOS 適配。

4.1 TriCore（AURIX）進 Env SDK：tricore-gcc 13.4.1 與 qemu-tricore 兩個包合入，覆蓋 TC2xx／TC3xx／TC4xx（10-26）

日期：2026-10-26 00:10 與 07:57（合入時間）　來源：RT-Thread/sdk PR #9、RT-Thread/sdk PR #10、toolchains-ci v1.12、toolchains-ci v1.13

本期最實質的一筆不在主倉庫，而在 Env 的 SDK 倉庫：兩個 PR 先後合入，把 Infineon TriCore（AURIX）這條車規架構的編譯與模擬通路補進了 RT-Thread 的工具鏈體系。

第一筆是 tricore-gcc 工具鏈包，4 個檔案 +112，Linux 與 Windows 各一套 Kconfig 與 package.json，包名 tricore-gcc、版本 v13.4.1、開關 PKG_USING_TRICORE_GCC。工具鏈上游是 NoMore201/tricore-gcc-toolchain（EEESlab 11.3.0 的下游，帶 CI 自動構建），組成是 GCC 13.4.1、binutils 2.40、newlib、GDB 14.0，目標三元組 tricore-elf，覆蓋 TriCore 1.3／1.3.1／1.6／1.6.1／1.6.2／1.8，對應 TC2xx、TC3xx、TC4xx 三代晶片。釋出物放在 toolchains-ci 的 v1.12：Linux 包 251 MB，Windows 包 466 MB。Windows 包補了上游漏帶的 libwinpthread-1.dll（同時放在 bin/ 與 libexec/gcc/tricore-elf/13.4.1/），否則在未裝 MSYS2 的機器上編譯器起不來。

第二筆是 qemu-tricore 模擬器包，同樣是 4 個檔案 +112，開關 PKG_USING_QEMU_TRICORE，版本 v1.0.0，釋出物在 toolchains-ci 的 v1.13（Linux 5.4 MB、Windows 9.4 MB）。背景寫得清楚：tricore-gcc 包自帶的 QEMU 9.2.3 只有 KIT_AURIX_TC277_TRB（TC2xx）與 tricore_testboard 兩臺機器，模擬不了 TC3／TC4，所以單獨引入 Zephyr 側在用的一支。原始碼是 linumiz/qemu-tricore 的 release/ifx/tricore-1.0 分支（tag v1.0.0，QEMU 10.2.94），支援的三臺機器是 KIT_AURIX_TC277_TRB、KIT_AURIX_TC397B_TRB、KIT_A3G_TC4D7_LITE，CPU 模型 tc2x／tc3x／tc4x。外設只做了 ASCLIN0 串列埠、STM 系統定時器、IR 中斷路由、SCU 與時鐘、SFR 橋、片上 RAM 與 Flash 對映，CAN、乙太網、ADC、GPIO、DMA 都沒有——夠跑核心與串列埠 shell，不夠做外設驅動驗證。為支援 Windows 交叉編譯，TriCore 側還改了兩處可移植性問題（ENOTBLK／O_* 條件編譯與 hwaddr 日誌格式）。

兩點必須寫清楚。其一，這只是工具鏈與模擬先行：主線的 libcpu 目錄現有 19 個架構（aarch64、arc、arm、avr32、blackfin、c-sky、ia32、m16c、mips、nios、ppc、risc-v、rx、sim、sparc-v8、ti-dsp、unicore32、v850、xilinx），沒有 tricore，bsp 下也沒有 AURIX 板級目錄；倉庫裡能查到的 TriCore 記錄是 2020 年前後的幾次嘗試（#4311 架構適配、#4488 與 #4527 的 TASKING 工具鏈與 FinSH 支援），狀態都是 Closed，沒有併入主線。其二，兩筆提案的 Windows 包都只做了 PE 匯入表檢查，未在 Windows 實機執行，作者自己在 PR 裡建議合入前補跑一次編譯。

把這兩點合起來看，意義在於路線變化：早年的 TriCore 適配依賴 TASKING 商業工具鏈，門檻高且難以進社群；這次換成開源 GCC 13.4.1 加 QEMU 模擬，先解決「能編、能跑、能調」，至於 BSP 與驅動，是後面的事。對車規場景（域控、安全島、AURIX TC3xx／TC4xx 是這塊的主力）而言，這是必要但不充分的一步。

4.4 驅動與 CI：OSPI 八線 Flash、I2C 控制事務序列化、STM32 包測試併發鎖（10-23／10-25）

日期：2026-10-23 至 2026-10-25（更新與合入時間）　來源：PR #11912、PR #11820、pkgs-test PR #37

驅動層最大的一筆是 OSPI 與 OctaFlash 支援（#11912），32 個檔案。此前 RT-Thread 的 SPI 驅動層沒有原生的 OSPI 通路，八線 Flash 只能繞。改動在 components 層補 OSPI 的匯流排、裝置、配置與訊息定義，以及傳輸輔助函式與構建選項，同時保留既有 SPI 與 QSPI 路徑；把 OSPI 傳輸與探測接進 SFUD，支援讀、寫、擦除與狀態／控制操作，並在 SFUD 裝置表裡加了 MX25LM51245G 用於驗證；為了讓整條路徑能在硬體上跑通，還加了通用 STM32 OctoSPI 驅動與 stm32l4r9-st-eval 的板級 OSPI Flash 支援，使 SFUD 能以 1-1-1 與 8-8-8（OPI STR／DTR）兩種模式訪問。

I2C 那筆（#11820）修的是匯流排控制與傳輸的競態：rt_i2c_control() 可能在 rt_i2c_transfer() 使用匯流排期間改控制器配置，尤其在 SET_MAX_HZ 上。改法是讓控制命令取同一把匯流排互斥鎖、走統一出口釋放，並在 API 文件裡寫明控制需要執行緒上下文。驗證用的是主機側 pthread 互斥介面卡，覆蓋併發傳輸與控制、控制與控制、頻率更新、鎖與回撥錯誤、以及控制裡巢狀傳輸；未打補丁的原始碼在同一迴歸集裡失敗。

CI 側的那筆在 pkgs-test（#37），1 個檔案 +11/-7，解釋得很完整：STM32 軟體包測試並行跑多個版本，每個任務有獨立 BSP 副本，但仍共用 bsp/stm32/libraries 下的 HAL／CMSIS 驅動目錄；原來的 sem_stm32 只保護編譯、不保護依賴更新，於是會出現一個任務在另一個任務克隆依賴未完成時對同一目錄 git pull，Git 報未跟蹤檔案將被覆蓋並中止，失敗又被框架統一報成 compile failure。上一期合入的 #11870 測試即栽在這上面（失敗日誌可查）。修法是把鎖上移到 __build()，讓依賴更新與編譯處在同一個臨界區，同時刪掉 __build_scons() 裡的重複加鎖避免自死鎖，並用 try/finally 保證異常釋放。

五、總結與趨勢觀察

5.1 本期趨勢

  • 車規架構走「工具鏈先行」：TriCore／AURIX 這次進的是 Env SDK 而不是主倉庫——開源 GCC 13.4.1 與 qemu-tricore 兩個包先補齊編譯與模擬，主線 libcpu 仍無 tricore 移植、bsp 下也無 AURIX 板級目錄。對比 2020 年前後依賴 TASKING 商業工具鏈的那批嘗試（均以 Closed 收場），這次的路徑更可能落地，但距離「能上板」還差 BSP 與驅動。
  • 主線極靜、提案面極活：72 小時 master 只有 2 筆提交，而視窗內 25 筆 PR 有更新、6 筆合入（主倉庫 2、sdk 2、packages 1、pkgs-test 1）。合入動作集中在週五傍晚與週日晚間，評審沒停，開發側確實在收。
  • 缺陷研究從單點轉向子系統：時間子系統一夜間四單（三缺陷加一份帶 A 至 F 工作項的調研），兩筆修復提案次日提交，形成「報—析—修」的短閉環；lwp 的 sys_poll 迴繞則單列出 32 位 RT-Smart 在使用者態可控計數上的整數邊界問題，與上期那族「裝置或服務端後設資料當長度」的缺陷互補，說明核心仍在為歷史包袱付賬（ecf2d821 可追到 2022 年）。
  • 以構建為放行條件的合入開始被 CI 反噬：上一期 ESP-IDF v6.1 適配合入兩天後，master 上 C3／C6 構建轉紅，波及所有 PR 的靜態構建檢查；修復提案當天開出。這條鏈條本身是健康的，但也說明「本地未編譯、CI 驗證」的口徑需要配套的順序穩定性保障。
  • 端側 AI 的落點從跑模型轉向接工具：ai/Agent 包加 STT 上傳端點、預設後端換到 DeepSeek 官方 API，社群大賽作品用 agent 包把 MQTT 操作註冊成工具供核心排程，加上 10-26 晚的「雙核加肌電意圖」直播，方向一致——RTOS 正被當成 agent 的執行時，實時性與異構分工是它相對通用 Linux 的賣點。
