一、核心與版本動態

1.1 clang-format 鎖到 22.1.8，src/ 下 73 個核心原始檔一次性重排（10-30）

日期：2026-10-30 18:20（合入時間）　來源：提案 #11936

75 個檔案、新增 3852 行、刪除 3023 行，作者 CYFS3，關聯此前的 #11653 與已合入的 #11859。問題不在格式本身：格式檢查 CI 透過 pip 安裝 clang-format，手動格式化工作流透過 apt 安裝，兩處都沒有固定版本，同一份程式碼在不同時間可能跑出不同結果，格式檢查因此不可復現。

改動拆成三個獨立提交。一，新增 tools/ci/requirements-format.txt，把版本固定為 22.1.8，兩條工作流都改為從該檔案安裝，手動工作流補上 actions/setup-python 提供 Python 環境；二，.clang-format 開啟 AllowShortLoopsOnASingleLine、關閉 BraceWrapping.BeforeWhile，空迴圈保持單行、do-while 統一寫成 } while (...)；三，用同一版本遞迴格式化 src/ 下 73 個 C 與標頭檔案，含 klibc、utest、perf、smp 子目錄，69 個產生改動、4 個本已合規。中英文編碼規範同步補上安裝、版本確認與編輯器配置三節。

Kconfig、SConscript 與其他目錄不在本次範圍內，說明這是一次按目錄推進的格式收斂，而不是全倉重排。

1.2 dlmodule 收掉 2022 年報告的 #5705（10-30）

日期：2026-10-30 10:54（合入時間）　來源：提案 #11915、缺陷 #5705

2 個檔案、新增 215 行、刪除 45 行，改動落在 dlelf.c 與 dlelf.h。修的是 2022 年 3 月報告、掛了四年多的缺陷 #5705：動態模組裡訪問未初始化全域性變數時地址重疊或無法重定位。作者在最新 master 上覆現後，把根因拆成四條。

一，BSS 段（SHT_NOBITS）載入後分配指標不推進，多個 NOBITS 段會重疊在同一塊記憶體；二，原實現按段名共用 rodata、bss、data 三類的基址，沒有按符號所屬段的實際載入地址算重定位地址，多段場景會指錯位置；三，SHN_COMMON 符號（tentative 定義的未初始化全域性變數）的重定位被靜默跳過——程式碼去讀 shdr[0xfff2]，拿到垃圾段名後不匹配；四，這條路徑從不構建 module->symtab，導致 dlsym() 對 ET_REL 模組永遠失敗。

修法對應四條：BSS 段載入完成後推進分配指標；rodata、bss、data 段符號統一按「段載入地址加段內偏移」計算；為 SHN_COMMON 單獨分配公共塊，尺寸核算與重定位共用同一套對齊演算法，並把該分支的處理提前到段名匹配之前，避免越界讀；從 .symtab 收集 GLOBAL FUNC 符號構建 module->symtab，與 ET_DYN 路徑從 .dynsym 構建的做法對齊。

驗證在 qemu-vexpress-a9 上完成，開啟 RT_USING_MODULE，執行三個測試模組，覆蓋 ET_DYN 標準流程與核心符號經 GOT 匯入兩條路徑。影響面是走 ET_REL 載入路徑的 BSP，Cortex-M 系列開啟動態模組的工程首當其衝。

二、安全跟進與待合併佇列

2.1 RT-Smart mailbox 不校驗核心物件指標，偽造物件可讀寫核心記憶體（10-31）

日期：2026-10-31 14:26（報告時間）　來源：缺陷 #11960

報告者 XueDugu，核對的基線是當天 master cbc19778。問題在 mailbox 的系統呼叫入口：它把使用者傳進來的核心物件指標直接轉發給核心 mailbox API，沒有校驗這個物件是否屬於呼叫者 LWP、是不是 mailbox、是否落在核心記憶體。於是一個非特權程序可以構造「偽造物件」，讓核心按自己的規則去讀寫它，效果等價於一個任意核心讀寫的原語。

報告把時間線寫得很完整：缺陷由提交 ecf2d8215961（2022-12-03，RT-Smart 系統呼叫邊界調整）引入，首個受影響版本 v5.0.0，v5.3.0 與當前 master（5.4.0-dev）仍在。驗證做了兩層——QEMU 的 qemu-virt64-aarch64 全系統執行（virt、GICv2、單核、128 MiB、開 RT_USING_SMART 與 RT_USING_MAILBOX）證明使用者態到核心的越界路徑；Raspberry Pi Pico 2 W（RP2350）在板級驗證核心 mailbox API 原語本身，後者跑的是單地址空間的普通 RT-Thread，用來說明問題不止於 Smart 的隔離層。

截至發稿，這筆缺陷沒有認領、沒有對應修復提案，評論只有 CI 機器人的 /claim 提示。

2.2 pipe 的 FIONREAD 直接寫使用者給的指標，同型缺陷連續第三次出現（10-30）

日期：2026-10-30 19:13（報告時間）　來源：缺陷 #11958

同一報告者的第二筆。pipe 的 ioctl 在 FIONREAD 與 FIONWRITE 兩個分支裡直接 *((int *)args) = ...，把環形緩衝的資料長度或剩餘空間寫進 args 指向的地址；RT-Smart 的 sys_ioctl() 把原始使用者引數一路轉發、沒有 copyout，pipe 這一層也不判斷該地址是不是使用者地址。結果是普通程序可以指定任意核心地址，讓核心往裡寫四個位元組，寫入的值受 pipe 當前狀態約束。

影響範圍 v5.0.0 至 v5.3.0 與 master（5.4.0-dev），驗證在 QEMU vexpress-a9、Cortex-A9、32 位 RT-Smart、開 RT_USING_POSIX_PIPE、pipe 緩衝 512 位元組的環境上完成。

這是同型缺陷連續第三次出現：先是終端子系統的 ioctl 丟掉 FreeBSD 的 copyin 前提（缺陷 #11937），接著是塊裝置把 24 位元組分割槽表寫到呼叫者指定的核心指標（#11952），本期是 pipe（#11958）。三處成因一致——fops 層沿用「引數已經是核心地址」的老假設，而使用者態入口沒有補上轉換層。2.1 的 mailbox 缺陷屬於同一個引入提交留下的家族，只是越界方式從「往裡寫」變成「把使用者指標當核心物件」。

2.3 poll 與 epoll 的計數乘法迴繞（10-30）

日期：2026-10-30 11:59（提案時間）　來源：提案 #11954

1 個檔案、新增 28 行，修 #11925 的前半部分。sys_poll() 用使用者給的數量算核心緩衝區大小，32 位下乘法會迴繞，但隨後仍用未迴繞的原始數量遍歷：nfds 取 0x20000001、pollfd 結構 8 位元組時，乘積 0x1_00000008 被截成 8；訪問校驗與 kmem_get 都按 8 位元組透過，poll() 卻會遍歷 536,870,913 項，do_pollfd() 裡讀 pollfd->fd、寫 revents 全部落在分配塊之外。64 位構建不受影響，乘積提升到 64 位，超大分配直接返回 ENOMEM。

sys_epoll_pwait() 是同一形狀，且它的計數是 int，負值也要一併拒絕。修法是在拿這些數量算任何大小之前先判：nfds 大於 SIZE_MAX / sizeof(*fds) 就返回 -EINVAL；epoll 側再加計數小於 0 的判斷。寫法與 sys_sendmsg、sys_recvmsg 裡對 msg_iovlen 的校驗保持一致。

同一批在途的還有 #11899（sys_sigaction 校驗訊號號）與 #11895（訊號投遞順序與 ELF 段保護），共同點是把使用者態傳入的編號、長度、指標在進入核心邏輯前先校一遍。

2.4 RISC-V AIA：APLIC 電平中斷 EOI 無條件寫 setipnum（11-01）

日期：2026-11-01 20:40（提案時間）　來源：提案 #11966

8 個檔案、新增 1367 行、刪除 10 行。現象是 QEMU 8.2.2 上跑 bsp/qemu-virt64-riscv、RV64、四核 SMP 加 AIA（APLIC 與 IMSIC）配置時，一個帶 rt_thread_mdelay(1000) 的計數程式只列印出 RISC-V test: 0 就停住，延時執行緒再也回不來。

定位結果是 APLIC 驅動在處理電平中斷的 EOI 時無條件寫 setipnum_le。舊版 QEMU 在裝置已經撤銷中斷之後，仍可能因為這次寫入產生新的 MSI，形成持續的虛假中斷，把系統定時器的處理壓住，延時執行緒因此無法恢復。修法是先讀 in_clrip 裡對應的有效輸入狀態（rectified input，已考慮中斷極性），只在裝置仍保持中斷有效時才寫 setipnum_le——既保住電平中斷的重觸發能力，也不給已撤銷的中斷補一發。

復現程式也一併改了：BSP 的 main.c 從「列印一次 Hello RISC-V」改成 0 到 9 的計數迴圈，每次列印後延時一秒。驗證環境為 QEMU 8.2.2、OpenSBI v1.3、riscv64-unknown-elf-gcc 13.2.0；開著 AIA、四核、關掉網路與 NVMe 與 virtio-console 與 PCI 串列埠的三組配置都能完整輸出。

這條線對做端側 AI 的團隊有參考價值：它承認端側算力邊界，把互動與呈現放在板端、把推理留在上游——與大賽作品裡「NPU 跑小模型、複雜判斷上雲」是同一套取捨。

4.1 NXP RT1180 工業乙太網連結指令碼進入待審佇列（10-30）

日期：2026-10-30 19:57（提案時間）　來源：提案 #11959

一筆針對 NXP i.MX RT1180 的 BSP 提案，補的是工業乙太網場景需要的連結指令碼。RT1180 帶多路千兆乙太網與 TSN 交換，這類工程對記憶體分割槽與段佈局的要求比通用 BSP 嚴格，連結指令碼往往要先落地，驅動與其他外設才好接。提案仍在佇列，尚無合入時間。

同視窗的硬體側與底層小修還有三筆在排隊：#11961 為 C++ 執行緒初始化靜態 TLS；#11965 阻止 gcc 把 klibc 裡 kstring.c 的位元組迴圈識別成 memset 與 memcpy 呼叫——自實現的字串函式被編譯器改寫成庫函式呼叫，這類改寫在核心自舉語境下需要單獨交代；#11963 與 #11964 是兩筆 utest 補測，分別讓 mailbox 用例可以重複執行、覆蓋訊號投遞到 mdelay 阻塞執行緒的情形。

4.2 上一期報的兩筆驅動缺陷已有補丁（10-30 ~ 10-31）

日期：2026-10-30 18:16 / 10-31 21:11（提案時間）　來源：提案 #11957、提案 #11962

上一期報告裡那四筆驅動側缺陷，已有兩筆等到了補丁。#11957 對應 DM365 SPI 的除零：在 setup 階段拒絕 max_hz 為 0，避免預分頻計算把它當除數。#11962 對應 Bluetrum AB32 的 ADC：在讀取前校驗通道號，不再讓對映失敗後默默回退到 0、再拿原始通道號索引資料暫存器陣列。

兩筆都還沒合入，另外兩筆（Bouffalo ADC 越界讀 #11949、HPM ADC 通道狀態索引 #11951）本期仍無對應提案。這類缺陷的共同點沒變：rt_adc_read() 與 rt_spi_configure() 這一層不做引數校驗，把責任下推給每個驅動，而多數驅動沒有做。

五、行業應用

5.1 大賽作品賽後集中開源：四個邊緣 AI 視覺專案壓在兩款板卡上（10-30 ~ 11-01）

日期：2026-10-30 ~ 2026-11-01（倉庫建立時間）　來源：倉庫：Titan Mini PCB Inspector

視窗內 GitHub 上出現 15 個新建的 RT-Thread 相關倉庫，其中 7 個自述為 2026 RT-Thread 嵌入式大賽參賽作品，集中開源時間落在 10-30 至 11-01，與大賽「作品在論壇發帖並把程式碼開源」的要求對得上。

瑞薩 Titan Board Mini（RA8P1，Cortex-M85 加 Ethos-U55）上有兩個。一是 Titan Mini PCB Inspector：攝像頭看板、800×480 LCD 顯示、串列埠 HMI 互動，Ethos-U55 做本地推理、雲端大模型寫建議，斷網時退回表驅動專家規則，不靜默失效。二是靈犀智眸：INT8 量化的姿態模型單幀檢測最多 10 人、每人 17 個關鍵點，再按規則判舉手、趴桌、站立、坐正四類行為，加權後輸出 0 到 100 的專注度評分，事件帶時間戳寫 SD 卡 CSV，原始畫面不出教室。

富瀚 MC632X（Cortex-A7）上有兩個同名 SENTINEL。一個接 M5Stack AtomS3R 小智做語音播報，雙路 800×480 MJPEG 網頁預覽、人形檢測與絆線進出統計，夜間轉周界佈防與錄影留證；另一個強調脫離 PC 獨立執行，一根電源線一根網線，上電後自動完成配網、媒體管線與 Web 服務啟動。

四個專案的取捨一致：模型壓到端側 NPU 或 MCU，複雜判斷上雲或交給規則引擎，原始畫面不出裝置。這與 3.2 直播裡「大腦在 PC、肉體在板端」是同一套工程判斷。

5.2 從賽題板到產線：雙 Cortex-M7 的 20 kHz 無感 FOC 與編碼器閉環定位（10-31）

日期：2026-10-30 ~ 2026-11-01（倉庫建立時間）　來源：倉庫：NS800RT7P65D FOC 與 CANopen

納芯微 NS800RT7P65D 是雙 Cortex-M7 的電機控制晶片，這個專案把它拆成兩個邏輯 CPU：一個跑 20 kHz 的 ADC 取樣與 PWM，做無感 FOC、滑模觀測器與 PLL 估算，帶硬體關斷；另一個跑 UART 與 FinSH、CANopenNode v4.1 與 CiA 402 橋接、CAN 收發。跨核只走非同步命令郵箱和一份六欄位、24 位元組的一致性快照，不做共享記憶體亂讀。底層是 RT-Thread 5.3.1 的 SMP 配置。

英飛凌 PSoC Edge E84 上的 EdgeDoctor-RT 走另一條路：每 20 毫秒處理一個振動資料塊，1 秒滑動視窗提 64 維頻帶特徵，送 64-32-5 的 MLP 判正常、軸承內圈故障、軸承外圈故障、不對中、不平衡五類狀態，並給置信度與處置建議；基線是官方的 Edgi_Talk_M55_XiaoZhi v1.4.0，只疊應用層，不改啟動、連結、HAL 與 Wi-Fi 資源。

兩例運控作品更能說明賽題板的下沉程度：NXP FRDM-MCXA346 上一個做步進電機閉環定位，編碼器反饋加 Python 與 Tkinter 上位機，跑 10 度與 90 度定位、相對反轉 45 度與回軟體零點；另一個做超聲波避障加煙霧檢測的檢測小車，視覺識別放在 PC 側。

平臺分佈值得記一筆：Titan Board Mini 與 MC632X 各兩塊、PSoC Edge E84 一塊、NS800RT7P65D 一塊、FRDM-MCXA346 兩塊，覆蓋大賽板卡清單裡的五款。

六、本期趨勢與總結

6.1 趨勢：合入端靜、補丁端密，RT-Smart 的邊界在被系統性清賬

本期 72 小時裡主倉庫只有 2 筆合入（10-30 10:54 的 dlmodule 修復、18:20 的 clang-format 重排），但新建提案 11 筆、新建缺陷 3 筆，全部落在 10-30 至 11-01。週末視窗「合入少、提交多」屬常態，值得看的不是數量而是落點。

第一條線是工程基礎設施。clang-format 鎖版本解決的是同一份程式碼在不同機器上格式結論不同；版本管理 CI 與釋出流程解決的是基線漂移、Z 與 Y 的釋出邊界不清。兩件事都不改一行核心邏輯，卻決定了後面所有補丁能不能被穩定評審——上一期把 lwp 那一萬一千行的單檔案拆成 20 個檔案，走的是同一條路。

第二條線是 RT-Smart 的使用者態邊界。終端 ioctl、塊裝置 ioctl、pipe ioctl、mailbox 物件指標，四處問題形狀一致：fops 與系統呼叫層沿用「引數已是核心地址、物件已是核心物件」的老假設。報告者把引入提交追到 2022-12-03 的 ecf2d8215961，說明這不是新程式碼引入的迴歸，而是這條邊界從建立起就沒做過系統性校驗。在途補丁覆蓋 poll 與 epoll 的計數迴繞、sigaction 的訊號號、ELF 段保護與靜態 TLS，方向對，但 mailbox 與 pipe 兩筆還沒有人認領。

第三條線是生態側的表達方式。官方新聞介面停在 6 月 17 日已進入第六個月，對外發布改由媒體專欄承擔；社群活躍度則明顯轉到「作品」上——一個週末 7 個大賽作品開源到 GitHub，五個落在邊緣 AI 視覺與診斷，兩個落在電機與運動控制。對關注 RT-Thread 落地的人來說，這批倉庫比官方通稿更能說明板卡廠商與開發者在拿它做什麼。

6.2 侷限性與去重說明

論壇 club.rt-thread.org 本期前置 WAF 挑戰頁，作品帖列表與文章正文無法直接讀取，參賽作品資訊改由 GitHub 倉庫自述（README、目錄結構、建立時間）與電子工程專輯官方專欄交叉核驗，未逐帖比對論壇原文。
