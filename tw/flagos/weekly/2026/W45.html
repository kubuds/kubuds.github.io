base 與 runtime：hygon-dtk26.10 10-31 ~ 11-04 基礎映象裝 ROCm 感知的 Open MPI，執行時補 flagcx 0.14.1 的海光 DTK 26.10 構建版，python 3.12 配 DTK 26.10 的 torch 閉包；廠商 triton 升到 3.7.0+dtk2610 後只有 hcu 驅動 active，修掉 serve 退回 V1 model runner 的問題

  • 釋出態：community 的 release/2.3 目錄目前只有釋出時間表，清單檔案按計劃在 11-30 特性凍結時生成。按 2.3 時間表，FEP 合入截止 11-13、特性凍結 11-30 拉 rc0、rc1 12-07、rc2 12-14、封板 12-25、GA 12-30。映象跑在清單前面屬計劃內節奏，11-13 才是這一版範圍的硬邊界。

三、元件與程式碼共建

FlagGems：一週五批，從覆蓋率轉向可比性與後端專屬實現

  • 映象先行是計劃內節奏，11-13 才是硬邊界：23 個 base 與 23 個 runtime 全部記上 2.3.0，而清單檔案要到 11-30 特性凍結才生成；按排期，FEP 合入截止 11-13、rc0 11-30、rc1 12-07、rc2 12-14、封板 12-25、GA 12-30。映象跑在清單前面不是脫節，真正值得盯的是 11-13 之前七份新 FEP 能否收進、以及 cuda13.3 這條線是否還會再動 torch 版本。

  • 多晶片適配從「模板複製」轉入「按後端算賬」：同一個 vLLM 0.28.0，四條後端給出四種策略——清微主動放棄圖模式換正確性邊界，沐曦在上游無分支時做外掛自足，摩爾執行緒把圖收進單個檔案並帶進原生 MCCL，昇騰只做解碼圖。適配工作不再有統一模板，每家按自己的驗證能力與下游模型需求取捨，隱性成本是同時維護 0.28 與 0.32 兩套環境。

  • 評測可比性成為新的基礎設施：FlagGems 兩分鐘 23 筆把四類運算元的 H800 參考讀入收斂到統一 JSON，optest 按廠商探查實際註冊的運算元清單、補英偉達基線，FlagTree 與 FlagCX 把結果推飛書多維表、把覆蓋跑到四個平臺。這條線不產出運算元數量，卻決定跨後端分數是否可信；本週 26 筆落在 CI 與評測側，佔單日合入的 14.7%。

  • 瓶頸穩定落在評審端，而不是生產端：11-04 日報記錄全組織在審存量 1602 筆，合入與在審之比約 1 比 9；11-05 至 11-06 視窗內更新在審仍有 288 與 255 筆，FlagGems 與 FlagTree 兩倉佔六成。同期多筆 PR 正文自帶 AI agent 的工具、模型與人工評審欄位，說明寫程式碼這一端已被 agent 放大，產能瓶頸轉到評審與驗證環境。

  • 新晶片接入的兩條路徑都已跑通，差距在驗證深度：壁仞以 SUPA 後端進入 TransformerEngine-FL，屬骨架先行、無硬體驗證記錄；寒武紀以原生平臺進 Torch-FL 並在八卡 MLU590-M9 上實測，次日把訓練步回退清零；天數以一天十筆專用運算元走運算元產線。接入速度已不是門檻，能不能拿出硬體門禁記錄才是分水嶺。

  • 量子棧的工程化路徑已經清楚：910C 的 167 項硬體驗收、x*256 從 28 個分配量子位與 4 GiB 態緩衝降到 19 個與 8 MiB 的資源賬目、fail-closed 的迴歸 lane，三者構成「語義、資源、硬體」三份可核對證據。本週 27 筆提交沒有一筆是量子演算法本身，全部用於讓測試可信、runner 可復現，說明這個階段先付基礎設施的賬是共識。

  • 運營側的短板仍在對外敘事：2.2 的產業案例已經能給出 25% 到 12%、19.87%、10 倍這類硬數字，但元件級新聞連續多個視窗零命中，第三方媒體覆蓋尚未形成。對 FlagOS 而言，技術產出與外部可見度之間的落差，可能比任何一個後端的功能缺口更影響生態擴張速度。
