  • 判斷：四家的共同特徵是「模型倉先行、運算元修復隨後」，與崑崙芯、海光的路徑一致。九芯交付的真正門檻不在模型倉上架，而在各家的執行時矩陣能否被後續幾周持續維護。

四、總結與趨勢觀察

  • Day-0 交付進入批次化階段：一週內 GLM-5.3-Flash 九芯與 MiniMax-M3.1-Flash 九芯連續兩次同日齊發，且本輪統一為 W8A8 單一路徑、四家 Express 版。交付的可複製性已經建立，下一步的觀察點是「同一格式在不同模型上是否穩定」以及模型卡版本矩陣是否隨上游升級同步更新。
  • 2.3.0 處於「已授權、未釋出」的懸置期：build-infra 的門禁、changelog、重建授權、版本引數化四件事全部就位，標籤尚未打出。與 2.2 釋出前不同的是，本輪把「容器啟動時選元件版本」做成了正式能力，意味著執行時與運算元庫、編譯器的版本解耦，長期看會改變適配與驗證的顆粒度。
  • 組織活躍度高度集中於量子棧：FlagQuantum 單倉佔 82.5% 提交、54% 合入。這種集中帶來快速的結構重整（QEC 包拆分、Quafu SDK 切換），也使組織級的「非量子側」吞吐明顯回落——日均合入從 163 筆降至 91 筆，主要差額來自 FlagGems 與 FlagGems-sglang 的回落。
  • 競賽賽道成為運算元供給主渠道：FlagGems-sglang 34 筆合入中絕大多數來自外部貢獻者的 Competition-Track1，兩小時內可合入 30 筆。供給快、稽核集中，測試契約的補齊依賴事後批次，這條通道的長期質量需要觀察缺陷迴歸率。
  • 廠商側修復進入長尾期：崑崙芯、昇騰、沐曦、摩爾執行緒本期的動作以「已有運算元修到能用」為主，另有一次 CPU 運算元誤移植的回撤。這是後端接入後的必然階段，也說明 2.2 的 1,454 個運算元清單在真實晶片上仍存在覆蓋與精度缺口。
  • 資訊面相對平靜：44 條新聞候選僅 3 條有效，無新版本釋出、無新倉庫建立（新倉均為 10-13 至 10-14 建立）。本期內容主體來自 GitHub，屬典型的「程式碼活躍、釋出會靜默」視窗。
  • 侷限說明：本期提交檢索為 GitHub search 的 total_count 口徑（612 筆），按提交 URL 去重後逐條歸倉，個別倉庫可能存在跨頁重複導致的 ±1 誤差；FlagQuantum 的 505 筆含合併提交與分支同步提交，不能等同於 505 個功能改動；FlagRelease 的時間戳為 Hugging Face 的 UTC 記錄，已換算北京時間；廠商通稿中的「Day-0」「率先」等表述為公司口徑，未取得第三方驗證；InfoQ 的成本數字為按租金折算的測算，非實測對照。
