解讀：這 7 個運算元的語義覆蓋面很典型——silu_and_mul（啟用融合）、causal_conv1d_fn / chunk_local_cumsum_scalar / merge_state（SSM/類 Mamba 卷積與狀態運算元）、per_group_transpose / mrope_fused（mRoPE 組轉置與融合）、fused_moe_gemm（MoE 融合 GEMM），與 SGLang 真實推理負載（混合注意力、MoE）一一對應，驗證了賽題”取自真實推理業務”的設定。對 FlagOS 而言更重要的是社群共建管道的首次閉環：賽事 8 月中旬開賽後約三週，首批成果即按賽規以統一格式、統一程式碼規範回到官方倉庫並由維護者補全測試/文件——「開放賽題→平臺評測→榮譽激勵→官方倉庫沉澱」的運算元眾智迴圈開始產出；且每批次（後續每 7 天一評）都會帶來新的 PR 合入流，FlagGems-sglang 將取代 FlagSparse 成為觀察”外部貢獻密度”的新視窗（FlagSparse 的 AlphaSparse 外部佇列是另一條已跑通的眾智通道，見 09-05 日報）。另注意 yzw1128 提交的 silu_and_mul 與 build-infra #763 中 iluvatar 的 flag_gems silu_and_mul 黑名單同名（不同倉庫、不同問題域，純屬巧合）。

1.2 build-infra：映象 tag 記錄分支 per-backend 唯一化、啟動頁按交付記錄門禁（09-06）

來源：#756（961c0fed）、#759（8f012fd4）

  • #756（12:42）：record_app_image_tag.py 原先把所有記錄累積到單一共享分支 auto/app-image-tag，任一歷史遺留的 open 記錄 PR（任意 app/後端）都會以 rebase 衝突阻塞後續所有記錄（mthreads-musa4.3.6 的記錄即以 run 34009399235 失敗過一次）——改為按 auto/app-image-tag-<backend>-<app-key> per-record 派生獨立分支，記錄互相解耦。
  • #759（14:48）：gen_data 原先僅憑 configs 的 deps_app key 是否出現來生成 app 啟動頁，但 key 在驗證完成之前就會被加上（以觸發構建），導致未驗證後端（例：vllm0.20.2-iluvatar-corex4.4.0，deps_app 存在但 launch_docs=false、cells 未驗證）也會洩漏出啟動頁並進入每個 app 映象——改為以矩陣 launch_docs 記錄為門禁，未驗證後端不再生成啟動頁。

解讀：兩條都是”交付記錄系統自身的可信度修復”——前者消除記錄管道單點故障（共享分支互踩），後者消除驗證狀態與頁面釋出狀態脫鉤造成的假陽性（與 09-05 寒武紀”無語義門禁假陽性”問題同源不同層：那次是執行驗證門禁缺失，這次是文件生成門禁缺失）。這類元工程修復在 2.2”驗證-打 tag-記錄”週期裡持續出現，說明發布審計面正在被逐層收緊。

1.3 FlagCX：UIL p2p hang 修復與無加速器 CICD 門禁（09-06）

來源：PR #542（511cdace，taozhiwei）、PR #568（8737bab4，MC952-arch）

  • #542（20:21 合入）：[UIL] 修復通訊域大於 2 時 p2p 掛起問題——PR 附帶完整 unittest 復現（多 rank send_receive 場景），屬 UIL（統一通訊層）在跨卡拓撲擴充套件時的收斂性缺陷修復。通訊域（communication domain）大於 2 意味著該路徑面向多卡真實叢集拓撲，而非單對單除錯場景。
  • #568（21:50 合入）：[CICD] 無加速器環境跳過 API 測試——CI 在未掛載 GPU/加速器的 runner 上不再執行依賴硬體的 API 測試，避免假失敗/假透過，測試門禁按執行環境自適應。

解讀：FlagCX 在 08-27 完成 FlagOS Enflame collective 全流程（#554）並打 v0.14.0-rc0.post1 後，本視窗兩條提交分別是功能性收斂修復（p2p 多域掛起）與CI 工程化（無卡門禁自適應）——與 build-infra 同節奏：功能擴充套件暫緩、驗證與交付質量優先，符合 2.2 rc0 週期”驗證-打 tag-記錄”的收口特徵。
