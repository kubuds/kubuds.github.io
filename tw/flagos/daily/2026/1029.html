1.3 FlagGems：崑崙芯標量鏈融合提速十倍，燧原參考實現批次修復在審（10-28）

日期：2026-10-28　來源：FlagGems PR #7617 · FlagGems PR #7600 · FlagGems PR #7850 · FlagGems PR #7803 · FlagGems PR #7036 · FlagGems PR #7061 · FlagGems PR #7223

  • 融合核心：崑崙芯 XPU3 側為八個出位標量鏈運算元加後端特化（#7617，275 行）。同構 float 列表走一個融合核心：小形狀單次發射、把所有指標作為核心引數帶進去，大形狀走流式分塊；輸出從一次分配加 unbind 得到，而非每張量一次分配器呼叫。八個運算元的相對耗時從 0.083~0.126 提到 0.813~0.934，即約七到十倍。
  • 連續段核心：batch-norm 推理與 QKV 變換兩個運算元由「每 (n,c) 切片一個 program」改為「每 program 處理一段連續 BLOCK 元素、由平坦索引反推通道或打包行」（#7600）。聚合指標分別從 0.228 提到 1.357、從 0.260 提到 5.062；fp32 單精度那格仍低於 0.8，作者按聚合口徑判定，並在正文裡寫明。
  • 向量化修復：masked_fill 的整數檢視快路徑因 arith.extsi 無向量形式整核停留在標量（fp16 0.34、fp32 0.50），改寫為 x*(1-m)+V*m 的 f32 形式後 P800 上從 0.577 提到 0.829，masked_fill_、masked_fill_scalar 同步受益，594 個用例透過（#7850）。
  • 匯入與執行器：崑崙芯後端在 master 最新提交上直接匯入失敗——_result_dtype 助手已隨 #7561 從共享執行器移除，而後端仍在引用（#7803，90 行）；修掉匯入後，共享執行器又報 operand #0 does not dominate this use，本筆一併修。
  • 運算元覆蓋：KernelGen 補 _indices_copy（#7223，250 行，H20 驗證），但效能只有 torch 的 0.21 倍——屬補齊覆蓋率的產物，短期不能當加速項看。lighting_indexer 的參考實現改為逐頭累加，峰值記憶體從約 8.6 GiB 降下來，修掉 40 GiB 卡上的 OOM（#5852）。
  • 在審側：本視窗新開 53 筆，多數是 lukatao 的燧原參考實現修復（#7890 至 #7908 連號），涉及 Kaiser/inplace ldexp、aminmax、special_round、LU、vander/slogdet、median/stacking/Lanczos、Adagrad、batch-norm ABI 等；另有 AMD 側一行修復（#7908）——AMD 的廠商描述符把裝置名設成 cuda 且未給 triton_extra_name，導致 pow、tanh、exp、rsqrt、erf、gelu 等全部走 __nv_* 被 AMD 後端拒絕。

1.5 編譯器：FlagPrism 接入燧原，昇騰 TensorView 取存降低，FlagMega 提速 RDNA 解碼（10-28）

  • 剖析與除錯：FlagPrism 的偵錯程式與剖析器擴到燧原後端（#1239，5 檔案加 119 行減 31 行）。CMake 與 Python 側把燧原加入支援列表並預設開啟，保留顯式關閉項與與 Proton 的互斥；執行時把帶除錯的核心發射改走 FlagPrism 閘道器，後設資料捕獲與隱藏的控制緩衝引數分開處理，普通執行仍走直髮路徑。
