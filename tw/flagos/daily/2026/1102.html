1.3 FlagQuantum：昇騰 910C 原生支援合入，167 項硬體驗收透過（10-31）

日期：2026-10-31　來源：FlagQuantum PR #958 · FlagQuantum PR #970 · FlagQuantum 提交 c417d80

  • 驗收資料：PR 正文記錄的組合硬體執行結果為 167 passed, 293 warnings in 115.41s；其中兩個整合檔案分別覆蓋 142 個電路、噪聲、TEBD 與 QEC 用例，以及 25 個動力學用例，並含兩次冷程序計劃重放。另附 CPU 側改動路徑迴歸 1332 passed, 3 skipped in 21.04s，能力與證據欄位契約測試 23 項透過。
  • 覆蓋範圍：complex64/complex128 態向量、MPS、張量網路與密度矩陣；autograd 與顯式梯度方法；混合訓練、噪聲與 TEBD；原生 Ising/Lindblad/Rydberg 動力學與儀器；QEC 預解碼器訓練；owner-sharded 態向量、MPS 與張量網路訓練。PR 明確說明 CPU 預設值、公開簽名與 schema 版本保持不變，新增的是裝置能力提案中已獲批的加法式原生動力學能力。

  • CI 側：#970 在預置 ARM64 runner 上建 fail-closed 原生迴歸 lane，配套提交把原生迴歸所用 action 歸檔釘到已驗證提交、在隔離 runner 映象裡保留原生 wheel provenance、用已認證 provider 覆蓋繼承的 wheel 版本，並讓原生測試進度流式寫入 watchdog。
  • 意義：此前 910C 只有實驗性 split-FP32 路徑的證據，這條線把量子棧的昇騰適配推到原生 provider 層，並把「硬體驗收記錄」寫進倉庫文件與 CI，而不是留在個人環境裡。

1.4 FlagQuantum：單視窗 35 筆合入，合成線資源賬目進入契約化階段（10-31 ~ 11-02）

日期：2026-10-31 ~ 2026-11-02　來源：FlagQuantum PR #1000 · FlagQuantum PR #995 · FlagQuantum PR #993 · FlagQuantum PR #984

  • 總量與結構：FlagQuantum 72 小時內合入 35 筆，其中合成線 28 筆、昇騰原生支援 1 筆、CI 與工具 5 筆、模擬文件與修復 2 筆。合成線是絕對主體，且全部圍繞「可提交輸入、可驗證語義、可核算資源」三件事。

  • 輸入面：#969 提出公共 Qmod 輸入與共享 Program 語義，#971 准入有界 Qmod 檔案與文字輸入，#985 准入原生一位元相位語句，#993 與 #994 支援有界 within/apply 作用域及其巢狀。Qmod 從內部格式變成對外可提交的輸入形態。
  • 語義面：#972、#981、#982、#990 依次補上無符號相等/小於謂詞、從 Python 條件一致地選值、無符號關係與鏈式區間謂詞、原生無符號比較表示式；#974、#984、#995、#997 把謂詞相位與已初始化暫存器借用組合起來，並做到不依賴臨時標誌位。
  • 資源面：#988 與 #989 在暫存器呼叫中驗證 Const 借用與 fresh-output；#991 驗證計算結果清理與儲存複用，#992 驗證本地所有權與零槽複用；#999 對已證明無進位的常量加法削減工作區，#1000 對精確 2 的冪乘法削減臨時位。以 x * 256 為例，基線為 28 個分配量子位、18 個工作區位、14 個操作、深度 6、4 GiB 態緩衝；合入後為 19 個分配量子位、9 個工作區位、12 個操作、深度 4、8 MiB 態緩衝。x * 4 探針則由 14/12 分配與使用位、8 工作區位、24 操作、深度 18、256 KiB 降到 10/10、4、10、深度 4、16 KiB。
  • 邊界與口徑：PR 明示這些是「精確資源核算」，不是執行時加速、最優性或程序峰值記憶體的保證；零、一、非 2 的冪常量、兩個量子運算元、以及帶零下界的派生值仍走通用乘法；改動只落在 Compiler 的 lowering 一處生產檔案。
  • 含義：量子合成編譯器過去一個季度的主線是「能合成多少構造」，這個視窗轉成「每個構造的資源賬目能否被複算與迴歸」。這類工作的價值不在單點效能，而在於讓資源預算成為可迴歸的契約——與主線運算元庫的效能補丁是兩種不同性質的工程。

  • 對比：摩爾執行緒維持「按模型補注意力」的節奏，地平線則在補基礎運算元族的覆蓋面。兩種節奏的差別在於前者服務具體模型上線，後者服務後端可用性。

四、總結與趨勢觀察

日期：2026-10-30 ~ 2026-11-02　來源：flagos-ai 組織 · FlagQuantum PR #958 · build-infra PR #1584 · 新浪科技：AI 零幀起手寫運算元

  • 節奏：72 小時內 17 倉推送、256 筆提交、115 筆合入、275 筆在審。按日均折算，提交約 85 筆、合入約 38 筆，均低於上一期 24 小時視窗的 189 筆與 183 筆，週末效應顯著。與此同時在審總量上升 8.7%、新開 146 筆，形成「產出降、積壓升」的組合。
  • 結構：FlagQuantum 148 筆提交與 FlagQAI 42 筆合計 190 筆，佔全部提交的 74%；主線運算元與編譯（FlagGems 16、Torch-FL 13、FlagTree 2）合計 31 筆，佔 12%。週末的產出結構由量子與智慧體兩條新線支撐，主線依賴工作日廠商投入。
  • 釋出：2.3.0 的兩條映象層（海光 DTK 26.10、AMD ROCm 7.2.4）已完成 changelog、依賴釘固與描述重新整理，但 release/2.3 清單目錄仍未建立、release-info 站點未列 2.3.0。按 2.2 的路徑，2.3 還差清單凍結與站點上線兩步，下一個工作周是關鍵視窗。
  • 技術方向：量子棧這一視窗的重心從「支援哪些構造」轉到「資源賬目能否復算」——x * 256 從 28 個分配量子位、4 GiB 降到 19 個、8 MiB 是可被迴歸驗證的硬數字。配合 910C 的 167 項硬體驗收與 fail-closed 迴歸 lane，量子線正在形成「語義、資源、硬體」三份可核對的證據，這比單點效能更接近工程可用。
  • 風險：FlagGems 在審 158 筆、新開 82 筆，絕大部分來自 KernelGen 批次提交，合入 18 筆與之嚴重不匹配。若 2.3 凍結前評審吞吐不提升，要麼釋出被積壓拖住，要麼大批運算元繞開評審進主線，兩者都會削弱「合入即驗證」的口徑。
  • 外部參照（非 FlagOS 專案）：面壁智慧 10-30 開源運算元生成系統 ForgeKernel，公開直播中在 B200 上經 22.5 小時、42 輪迭代把 FlashMLA prefill 從 1834 微秒壓到 472 微秒，較 DeepSeek 的 518 微秒快 9.8%，並稱在 CANNBench 的 A3、950DT、950PR 三榜登頂。它與 FlagOS 的 KernelGen 屬同一賽道，說明「AI 寫運算元」已從論文指標進入公開打榜與真實框架接入階段；對 FlagOS 的啟示不在模型能力，而在評審與驗證流程能否承接生成速度——這正是本期 FlagGems 積壓暴露的問題。
