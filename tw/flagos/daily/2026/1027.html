1.3 達摩院玄鐵：FlagBLAS 一次性補齊 15 組 BLAS1 運算元，一萬六千行落庫（10-26）

日期：2026-10-26　來源：FlagBLAS PR #154 · FlagBLAS 提交

  • 規模：單筆 PR 改動 17 個檔案、新增 16,168 行、刪除 9 行，合入時間為 10-26 08:57，是當日非量子倉裡體量最大的一筆。
  • 覆蓋：一次補齊 BLAS 第一層十五組運算元——向量最值與求和（AMAX、AMIN、ASUM）、向量累加與複製（AXPY、COPY）、點積三類（DOT、DOTC、DOTU）、歐氏範數（NRM2）、平面旋轉四類（ROT、ROTG、ROTM、ROTMG）、向量縮放與交換（SCAL、SWAP）。
  • 層面：這是數值庫層面的補齊而非推理運算元補齊。BLAS1 是上層 BLAS2 與 BLAS3、以及 LAPACK 求解器的前置依賴，缺一層就無法自底向上自洽；對玄鐵而言，此前在 FlagOS 裡的存在感集中在推理路徑（真武 Express 版、稀疏注意力），數值庫是空檔。
  • 鏈路：該 PR 在上一期日報中仍記為在審，本視窗完成合入，從「在審」到「落庫」跨了一個視窗。
  • 判斷：一家後端在 FlagOS 裡的成熟度，通常按「能跑推理、能跑訓練、數值庫自洽」三段衡量。玄鐵本視窗跨到第三段的第一級臺階，後續看 BLAS2 與 BLAS3 是否跟進，以及 FP8 路徑（FlagTrain 側在審的 fp8 GEMM 有玄鐵分支）能否共用同一套數值庫。

1.6 FlagCV：首個定位說明合入，Triton 視覺運算元庫對外成形（10-26）

日期：2026-10-26　來源：FlagCV · FlagCV PR #2

  • 定位：FlagCV 自述為「以 Triton 實現的高效能運算機視覺庫」，在 OpenCV 形狀的介面下提供常用影象處理原語——色彩轉換、濾波、幾何變換、算術運算，並以 OpenCV 的 CUDA 基線為對標，目標是在多種 GPU 架構上達到參考級正確性與有競爭力的效能。
  • 依賴關係：構建在 FlagTree 之上（FlagOS 維護的 Triton 分支，支援多硬體後端），對外提供與廠商無關的運算元介面，後端可插拔。
  • 時間線：倉庫於 10-14 建立（當時僅有佔位），10-18 落骨架並撤掉運算元實現改為「即時模式骨架」，10-26 合入 About 與 README 說明。即程式碼骨架在前、定位說明在後，本視窗補的是「這個倉到底做什麼」。

  • 海光：Torch-FL 修 DCU 執行時的構建源（#654）——DCU 的 runtime_dir 原先指向只放 ABI 墊片的目錄，導致執行時庫由 32 個樁連結而成，構建能過但一 import 就報未定義符號，改動 71 檔案、1.1 萬行；同日在審的 #627 為開啟裝箱的 DCU 構建接上真實流。
  • 天數：Torch-FL #660 修 Iluvatar 上 bf16 GEMM 退回主機執行的問題——2048 見方的 bf16 mm 實測 0.41 TFLOPS，低於同機 CPU 的 0.54，而同運算元 fp16 為 80.2、廠商自帶 torch 為 84.6；根因是支援判斷未納入 bf16 且 mm 與 addmm 在主機側複製了轉置權重。修完後走廠商 BLAS。
  • 摩爾執行緒：FlagTree 打出 MThreads 專用標籤（0.7.1a1+mthreads3.6），FlagGems-vllm 合入 chunk_kda 的 MThreads 最佳化（#990），MUSA 後端的 TLE 快取持久化改動上週已落。
  • 判斷：四家的共同點是「修能跑但跑得慢或跑一半炸」的問題，而不是加新運算元。這類缺陷最難在外部復現，也最能說明後端矩陣的真實完成度——廠商側提交的仍以自家平臺的正確性與效能為主，跨平臺統一語義的工作仍靠 FlagOS 主幹推動。

四、總結與趨勢觀察

  • 2.3.0 已走完一遍完整管道，標籤仍未打出：執行時的門禁、changelog、重建授權、版本引數化在 10-23 至 10-25 就位，10-26 授權應用層重建並把標籤收斂成 2.3.0-0.3.0。從「執行時重新整理」到「應用跟版」這一步通常緊跟正式釋出，本週仍是關鍵觀察窗。
  • 後端矩陣在擴張而非收斂：AMD ROCm 7.2.4 基礎映象新增，說明 2.3 週期還在加平臺。與之對應，玄鐵補 BLAS1、清微接 RPM 打包、崑崙芯補裝置位碼——四件事分屬數值庫、打包、通訊三個層面，都是「接進來之後才需要做」的工作。
  • 數值庫與訓練棧成為新戰場：FlagBLAS 一次性補十五組 BLAS1 運算元、FlagTrain 一批運算元鋪到七家後端，兩條線都在 2.3 週期加速。推理運算元的邊際收益在下降（FlagGems 本期以 KernelGen 自動生成批次與後端調優為主），訓練與數值庫的缺口更明顯。
  • 視覺方向首次成形，但缺效能證據：FlagCV 把定位寫成「Triton 實現的 OpenCV 形狀視覺運算元庫，對標 OpenCV CUDA 基線」，接在 FlagTree 上。目前只有說明與骨架，沒有任何基準或非 GPU 後端資料，判斷其價值為時尚早。
  • 評審頻寬成為瓶頸：提交增 37%、在審增 23%、合入降 18%、新開降 18%。開發側在積累，評審側在消化。FlagGems 與 FlagTree 兩個倉的在審量（52 與 9）與合入量（49 與 4）的落差最明顯，而這兩倉恰好是 2.3 的編譯器與運算元版本來源。
  • 量子棧進入場景鋪開期：糾錯碼、中性原子、熱浴三類物理場景同期推進，仍按四段留證作業。它繼續佔據全組織近六成提交，但相對上一期的日均已回落三分之二。
  • 資訊面連續第三個視窗只有成員單位通稿：12 條候選 2 條有效，FlagOS 自身無版本釋出、無新倉、無對外公告。內容主體仍來自 GitHub，屬典型「程式碼在填後端、傳播在等節點」的視窗。
  • 侷限說明：提交檢索為 GitHub search 的 total_count 口徑（185 筆），與合併 PR 檢索（133 筆）因壓縮合並與索引延遲存在口徑差，FlagGems 出現合入數（49）高於提交檢索數（28）即屬此類，報告內以合入數為準；FlagQuantum 的 109 筆含合併與分支同步提交，不等同於 109 個功能改動；FlagTree 的 0.7.1a1+mthreads3.6 經 Release 列表與 Tag 介面雙向核對為純 Tag，無 Release 說明；廠商通稿中的「無需改程式碼」「對齊或超過論文」等表述為公司口徑，未取得第三方復現；清微稿件中「20 家廠商、30 餘款晶片」與大會口徑的 21 廠商、35 晶片不一致，已在正文標註歸屬。
