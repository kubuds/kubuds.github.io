本視窗形態 = RC1 測試穩定期的”工程基建 + 運算元矩陣”雙線：交付側最大動作落在 build-infra（昇騰 910C 新後端 + 60 個 app 映象 changelog 基線與門控），程式碼側延續運算元自動生成流水線的高流速（主倉 39 條 + 實驗倉 60 條），領域庫與工具鏈則出現 FlagBLAS Ascend L3 三連、FlagTree TLE 多卡通訊等實質能力擴充套件。

1.1 build-infra：昇騰 910C base/runtime 後端雙線新增，60 個 app 映象 changelog 基線落地（09-09/09-10）

來源：build-infra #803（09-09 20:27）、#801（09-09 13:42）、#802（09-09 20:22）、#807（09-10 09:38）、#799/#800（09-09 10:42/10:43）、#804、#805、#806

  • 昇騰 910C 後端新增（#803）：新增 ascend-cann8.5.0-910c / ascend-cann9.0.0-910c 雙後端，使同一 CANN 線可構建到昇騰 910C 晶片。910C 的晶片專用 ops 包使用 A3 token（Ascend-cann-A3-ops），兩個 base Containerfile 與 910B 兄弟版位元組級一致，僅 PRODUCT ARG 預設值（910b→A3）與檔案頭不同。本視窗首次把昇騰晶片矩陣從 910B 擴到 910C。
  • 範圍刻意收口：新增 configs.yaml 塊有意省略 deps_app 與 env.app.*，使 910C 後端暫不進入 app 構建矩陣（deps_app 存在與否即 app 納入的門控），待 app 製品產出並驗證後再放開——沿用”先立 base/runtime、後進 app”的穩妥接入順序。
  • 順帶修復廠商解析：三個 verify 指令碼的廠商切分由末位連字元（${VAR%-*}）改為首位連字元（${VAR%%-*}），與 generate_matrix.py / verify_base.py 對齊；舊邏輯在 ascend-cann9.0.0-910c 這類雙連字元鍵下會解析出不在 run.vendors 裡的廠商名，導致 run flags 為空。配套 #804（910B runner overrides 強制 910b label）、#806（910C base 構建走 runner proxy build-args）。
  • 60 個 app 映象 changelog 基線（#801）：在 app/<app>/changelogs/ 下為 flagos-app 已釋出的全部 60 個 app 映象建立 YAML 基線，逐映象記錄當前 registry 駐留 tag 及其構建歷史（新→舊），每條含重建原因、push_time 日期與所納入的上游 PR；registry 已不再承載的舊 tag 折入後繼條目的 history（成為其唯一痕跡）。配套 #802（用 registry push_time 回填日期）、#807（push 時強制 changelog 門控）。交付可追溯性從”映象 tag 記錄”升級為”逐映象變更史”。
  • 摩爾執行緒 Megatron 應用映象雙線登記（#799/#800）：為 mthreads-musa4.3.6 與 mthreads-musa5.2.0 兩條線記錄 app image tag 2.1.2-0.3.0_rc0.post1_3.g6e8d7ffc7。另 #805 把外部 GitHub Actions 固定到完整 commit SHA（供應鏈加固）。

解讀：昇騰 910C 的接入方式值得注意——它沒有新開一條技術路線，而是把 910C 當成”910B 線的晶片同構變體”處理：Containerfile 位元組級複用、只換 ops 包 token，且用 deps_app 缺位把新晶片攔在 app 矩陣之外。這是 RC 測試期”可進新適配、不進新特性”紀律在多晶片工程上的具體投影：新硬體隻立骨架，不擾動既有交付面。60 個 app 映象 changelog 基線 + push 門控的組合，則把 build-infra 從”記錄發生了什麼”推進到”強制解釋為什麼”，是 2.2 GA 前審計面收緊的訊號。

解讀：KernelGen 的產出流速從上視窗的 12 條/半天回升到本視窗約 25 條/半天，說明”AI 自動生成運算元”已是常態化管道而非批次事件——這與 1.3 實驗倉 60 條的合入量相互印證。本視窗的操作面分布也說明了當前的工程重心：在 2.2 凍結期裡，新增能力全部走”生成器補運算元 + 廠商後端專用化”，手寫架構級改動為零；CI 側反而加大了約束（three-dot diff、rule-check-required、併發控制），是 GA 前把交付紀律收緊的典型動作。

  • 實驗倉單視窗 60 條視窗內提交，按後端計：Iluvatar 約 36 條（special 函式族、池化反向、linalg_svdvals、histc、median、mvlgamma、matmuladd 等）、MThreads 約 16 條、Ascend 3 條（special_erfinv、unsafe_masked_index、zero）、Hygon 2 條。
  • 海光專用 flash attention 入庫（#597）：為 Hygon DCU 後端新增 _flash_attention_forward 專用實現，檔案落入 src/flag_gems/runtime/backend/_hygon/ops/，由 BAAI 側開發者提交。此前該後端在實驗倉只有 _amp_foreach_non_finite_check_and_unscale_ 等輕量運算元，專用注意力運算元是首次。
  • 另一條 Hygon 運算元為 adaptive_avg_pool2d_backward（#598）。兩條均在同日/次日進入預設分支。

解讀：海光兩條的落點比運算元數量更有資訊量——_flash_attention_forward 是注意力路徑上的核心運算元，09-08 主倉剛修過 Hygon 後端 flash attention 的 BLOCK_M 取塊缺陷，本視窗專用實現即入庫，構成”先修通用路徑、再上專用實現”的接力。Iluvatar（天數智芯）單視窗 36 條繼續是實驗倉最大產能來源，與主倉 KMCompiler 的 Iluvatar gru 形成”實驗倉批次驗證 → 主倉 KMCompiler 生成/釋出”的分工閉環。

1.4 推理外掛層：達摩院玄鐵 PPU fused persistent_topk、Arm CPU Qwen W4A8/GDN、sglang 運算元配置（09-09）

來源：FlagGems-vllm #754（09-09 19:58）、vllm-plugin-FL #433（09-09 15:35）、#474（09-09 17:40）、FlagGems-sglang #60（09-09 18:56）

  • 達摩院玄鐵 PPU fused persistent_topk（FlagGems-vllm #754）：在 runtime/backend/_thead/fused/ 下新增並註冊 persistent_topk.py（2394 行），面向 T-Head PPU-ZW810E；由 KMCompiler 生成。上一視窗（09-08）該運算元的測試/benchmark 剛改為脫離 vLLM native op 可自測（#747），本視窗即為正式實現與註冊落地。
  • Arm CPU 側 Qwen 量化推理（vllm-plugin-FL #433）：在 CPU 上整合 Qwen 的 packed W4A8 與 GDN（Gated Delta Net）路徑，是外掛層向 Arm CPU 推理場景的擴充套件。
  • KV 快取一致性修復（#474）：恢復來自 #382 的 FlagGems KV cache 更新（attention 路徑迴歸修復）。
  • sglang 外掛運算元配置（FlagGems-sglang #60）：新增 operators 配置檔案，使 sglang 外掛側運算元啟用集合可配置化。

解讀：四條指向同一件事——外掛層正在為”多框架 × 多晶片 × 多部署形態”補齊配置面與專用運算元。玄鐵 PPU 的 persistent_topk 完成了從”可自測”到”已註冊”的兩步走；Arm CPU 的 W4A8/GDN 則把外掛層的作用域從加速卡延伸到 CPU 推理棧；sglang 運算元配置化降低了按晶片裁剪運算元集合的成本。三條合起來說明推理外掛層已進入”逐 kernel 廠商化 + 配置面治理”的成熟期工程。

  1. 政策層面 FlagOS 進入北京市五年規劃文字（本期最重要變化）：北京市”十五五”數字經濟規劃明確”強化 RISC-V 智算指令集創新，深化眾智（FlagOS）開源生態建設，佈局靈璣（LinkeeOS）智慧體作業系統”，把 FlagOS 與十萬卡叢集建設能力、信創軟硬體融合寫在同一政策句內。這是 FlagOS 首次出現在北京市五年規劃級檔案中，其角色從”智源牽頭的開源專案”上升為市級自主可控算力基礎設施的系統軟體棧載體。
  2. build-infra 完成昇騰 910C 後端接入，並落地 60 個 app 映象的 changelog 基線：910C 以”910B 線晶片同構變體”方式接入（Containerfile 位元組級複用、僅換 A3 ops token），且用 deps_app 缺位刻意攔在 app 構建矩陣之外；60 映象 changelog + push 門控把交付記錄升級為”逐映象變更史 + 強制原因說明”。交付側的審計面與晶片矩陣同視窗擴張。
