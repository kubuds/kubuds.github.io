1.5 FlagGems：崑崙芯 XPU3 修復靜默錯誤形狀，十四筆效能與契約收口（11-02）

日期：2026-11-02　來源：FlagGems PR #8038 · FlagGems PR #8034 · FlagGems PR #7976 · FlagGems PR #8123 · FlagGems PR #8245 · FlagGems PR #8049

  • 正確性修復：#8038 是當日最值得讀的一筆。foreach 系列的 out-of-place 標量過載在「同 dtype、同裝置、同元素數」時走快路徑，輸出統一按第一個張量的形狀分配再切檢視，而快路徑的准入條件比較的是元素數而非形狀——於是形狀不同但元素數相同的列表會全部繼承首個張量的形狀，產生靜默錯誤結果。修復把准入改為按完整形狀判定，另兩筆把十六個標量輸出改為單基址定址、把列表輸出合併為一塊平坦緩衝。
  • 契約修復：#7976 把 foreach 點號取槽位的索引改為取自 program_id(0)；#8034 在提交 JIT 之前先求值自動調優的網格，避免以未求值的網格啟動；#7956 解包標量解析的三元返回值，修正快步路徑的取值。
  • 效能收口：#8056 為 triu_、resolve_neg、le 與位右移補快路徑；#8245 為 flip、ge、lerp 補點態快路徑並撤掉上一版 BF16 一維 tile 重構；#8108 融合 pool3d 反向的精確路徑、對小乘法跳過點態管線；#8107 在每通道度數一致時展開 Chebyshev 的 t/w；#8030 加速 choose_qparams_optimized、kl_div 與兩個 Bessel 核；#8111 把 Jacobi 掃描分塊，使 nuclear_norm 只需 nb 次啟動而非 k 次；#8049 為 linspace 做單公式快路徑；#8248 另有一組運算元特化效能修正。
  • 回滾訊號：#8123 撤回「崑崙芯 BF16 點態效能最佳化」，理由是引入迴歸；同日 #8245 以不同方案重做並明確「撤掉 #8052 的 BF16 一維 tile 重構」。一撤一補同視窗發生，說明 XPU3 側的點態最佳化仍在試驗期，合併前缺少足夠的形狀覆蓋。

3.4 摩爾執行緒：Conv1D 真一維 GEMM 把 26 個基準例全部拉過 0.8 倍線（11-02）

日期：2026-11-02　來源：FlagGems PR #6754 · FlagGems PR #7428 · FlagGems PR #6903 · FlagBLAS PR #157 · FlagTree PR #1314

  • Conv1D 結果：#6754 為 MTT S5000 增加 conv1d 後端覆蓋，把官方 conv1d_padding 基準從 18/26 例達標提到 26/26 例不低於 0.80 倍 torch；此前所有 FP32 K3/K5 padding 例只有 0.41 至 0.53 倍。
  • 三層改法：其一，conv1d 原先無 MTHREADS 覆蓋、全部走通用 conv2d，小分組形狀會實體化 padding、W=1 形狀只命中單條有效 OW 通道；改路由後去掉冗餘 padding 與 bias 分配並修退化寬度分派。其二，新增專用 Triton-MUSA Conv1D 核，按 M 等於 N 乘 Lout 做三維網格切分，輸出通道不再做除法取模。其三，權重預打包為按核寬、輸入通道、輸出通道排列，配合帶精度補償的 SQMMA。
  • 配套：#7428 最佳化 S5000 上 one_hot 的校驗與推理；#6903 把空索引視為 index_add 的空操作；#157 補 MUSA 的 L1 BLAS；#1314 在兩次非同步 TME 複製間跳過 membar。
  • 判斷：這是本視窗少見的「把基準全部拉過線」的完整案例——路由、專用核、權重佈局、指令級精度補償四層同時改，且給出前後對照。對其他後端是一個可複製的模板。

3.5 沐曦、天數、清微、燧原與地平線：一側補運算元，一側補契約（11-02）

日期：2026-11-02　來源：FlagGems PR #7590 · FlagGems PR #7015 · Torch-FL PR #704 · Torch-FL PR #702 · FlagGems-vllm PR #1038 · FlagDNN 提交

  • 沐曦：#7590 最佳化 triangular_solve 的預設與 out 路徑；#7015 新增 cudnn_batch_norm 的前向與 out，並修正成對反向；Torch-FL #702 修正 MetaX SDPA 用例的跳過理由——原先歸因於 fp32，實際原因另有其他，屬於測試可信度修復。
  • 天數：#1038 為 chunk_kda 補天數後端最佳化；FlagDNN 修 iluvatar 的 GPU 名稱登記（單筆提交）；FlagGems #7664 把 apply_repetition_penalties 的基準開進 Iluvatar。
  • 清微：Torch-FL #704 把 tsingmicro 納入 conf 與註冊集一致性檢查，此前該平臺被排除在六個平臺之外，配置與註冊集不一致無法被 CI 捕獲。這是一筆純測試改動，但補上了清微側的契約缺口。
  • 燧原：視窗內僅一筆在審 PR，為 KernelGen 的 Enflame 側修四個運算元的 CUDA 專用裝置守衛（#8104），尚無合入。
  • 地平線：本視窗無新增提交或在審 PR；上一視窗的 BPU 卷積與池化路徑未在本視窗繼續推進。
  • 判斷：五家的動作分兩類——沐曦與天數在補運算元與基準，清微在補測試契約，燧原與地平線處於靜默期。對成員單位而言，能不能持續出現在每日合入列表裡，本身就是投入強度的直接指標。

四、總結與趨勢觀察

日期：2026-11-02 ~ 2026-11-03　來源：flagos-ai 組織倉庫 · build-infra PR #1589 · FlagQuantum PR #1004 · FlagGems PR #8240

  • AMD 線在一個視窗內補齊三層：構建側新增 FlagTree 的 amd 打包線並以 A/B 對賬證明等價（maxdiff 1.526e-05，9/9）；執行時側把 rocm7.2.4 的 torch 閉包對齊到 vLLM 0.32 的釘固組合；運算元側為 gfx1100 補 LoRA 與注意力共十個運算元。三者合起來，AMD 從「有後端」變成「有可追溯的構建、可復現的執行時、可調優的運算元」。
  • 量子棧進入「按驗收單元交付」階段：單日 21 筆合入分佈在 UP（語義）、AO（算術）、PF（效能）三條線，每條都有獨立基線、oracle 與失敗即紅的證據。這種拆法讓量子編譯器的每次改動都能被既有賬目測出代價，比追求單點加速比更能支撐長期演進。
  • 玄鐵把專用運算元做成了批次：13 個專用運算元 43 分鐘內合入，平均 3.3 分鐘一筆，集中在特殊函式、三維卷積、量化 LSTM 與池化反向等長尾條目。這說明 KernelGen 的玄鐵產線已具備批次供給能力，評審也能按後端並行消化。
  • 評審吞吐是當前真正的瓶頸：本視窗合入 162 筆、新開 192 筆，在審總量 311 筆，其中 FlagGems 一倉 210 筆（新開 148）。合入量較上一 24 小時視窗下降 11.5%，新開量卻上升 128.6%——產線開足、評審吃緊的結構沒有改變。
  • 2.3.0 仍停在映象先行：base 層與寒武紀、沐曦、海光、AMD 四層都已在 2.3.0 名下回填 changelog 日期，執行時映象也按後端推送，但 community 的 release/2.3 清單仍為 404、GitHub Release 零新增。與上一期相比沒有實質推進，若本工作周仍不凍結清單，釋出視窗會被下一版規劃擠壓。
  • 新聞側連續第二個平靜視窗：24 組中英文查詢零元件級命中，CSDN 專欄最新文仍為 10-29，HN 零直命中。生態背景兩條（烏鎮開源展館、九源聯合體三項聯合釋出）均明確標註為周邊事件，未計入專案進展。
