今日重點：Torch-FL 把 FlagGems 的 Python 提交路徑編譯成原生 host，Qwen3-0.6B 熱啟動開銷降到廠商 PyTorch 的 1.17 倍（11-14~11-16）

日期：2026-11-14 ~ 2026-11-16　來源：Torch-FL #824 · Torch-FL #839 · Torch-FL #822（需求單） · Project 14

  • 結果：#824 把 FlagGems 的 Python 側 host 邏輯——後設資料、記憶體分配、啟發式與 Triton 發射準備——編譯成帶守衛的原生 host 程式，同時保留原有的裝置核心。完整 Qwen3-0.6B 推理下，prefill/decode 的熱啟動 CPU 提交耗時從 211.51/203.92 毫秒降到 28.46/27.15 毫秒；廠商 PyTorch 為 24.43/22.96 毫秒，折算延遲比為 1.17 與 1.18。
  • 驗收門檻：#822 要求國產加速器上與廠商 PyTorch 同物理卡、同工作量對比，達到吞吐比不低於 0.80 或延遲比不高於 1.25。英偉達側已進門檻，國產卡側尚無公開資料；#824 自述為實驗性英偉達推理實現，不是預設模式切換，也不構成全運算元覆蓋的宣告。
  • 連續性：11-15 至 11-16 凌晨連合六筆——#826 編譯 FlagGems 原始碼與模型 host，#835 讓原生 host 登錄檔全量入賬，#836 生成帶 schema 型別的 eager 條目，#837 生成原始碼呼叫橋接，#838 保留標量語義，#839 降低共享 host 開銷（+2388/-55，15 檔案）。這條線按「單模型跑通、登錄檔補齊、開銷下壓」的順序推進，不是零散的效能補丁。
  • 設計取向：#823 的設計稿在實現之前定下路線，結論是決定上限的是記憶體分配而不是核心發射，因此第一階段直接從分配器取記憶體；#824 與 #826 合入後計劃獲維護者批准，#829 與 #830 承接後續。
  • 含義：FlagGems 的 eager 路徑一直帶著一層「Python 稅」——每次呼叫都要在 Python 裡做後設資料、分配與發射準備。把這層編譯掉之後，跨芯推理的差距從「核心寫得好不好」擴到「host 路徑怎麼組織」，2.3 的推理效能驗收口徑需要同時寫明 host 側基線。
