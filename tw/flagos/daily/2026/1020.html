1.2 build-infra：昇騰四輪子遷入 22.04 自包含 builder，清微與曦望同日補齊（10-19）

日期：2026-10-19　來源：PR #1414 · PR #1418 · PR #1422 · PR #1417 · base 目錄

  • 核心問題：昇騰的四個輪子原本在 24.04 執行時映象裡構建，產出的 libflagcx.so 與 _C*.so 鏈到 GLIBC_2.38，在 bundle 的 22.04 物理機上直接 abort。PR #1414 為每一行配置獨立的 ubuntu:22.04 builder，與其它廠商行走同一通道，glibc 底線降到 2.35。
  • 一個配方服務四行：ascend.mk 只鏈 -ltorch_npu -lascendcl -lhccl，與具體晶片無關；但工具鏈本身不帶這些連結期依賴，libhccl.so 與 <hccl/hccl.h> 來自晶片 ops 包，因此配方同時安裝 toolkit 與 ops 包（不含 nnal/ATB），910b 與 910c 的差異透過 ops 安裝器的晶片令牌（builder.ops_product，910b 與 A3）傳入。
  • 驗證口徑：SDK 底線用 import torch_npu（會 dlopen CANN 工具鏈庫）證明，而不是 import torch（該行上是純 CPU）；ASCEND_OPP_PATH、ASCEND_AICPU_PATH、TOOLCHAIN_HOME、LD_LIBRARY_PATH 從 set_env.sh 落到 /etc/profile.d/vendor.sh，與輪子構建時 sourced 的是同一份檔案。
  • 同日補齊兩個新後端：曦望（PR #1418，sunrise wheel 的 22.04 自包含 builder，隨後 PR #1420 記錄該輪子以 22.04-clean 重發）與清微（PR #1422，tsingmicro wheel 的 22.04 自包含 builder）。至此 base/ 目錄下的廠商矩陣為 nvidia（cuda12.8 / cuda13.3）、ascend（cann8.5.0 / cann9.0.0，含 910c）、cambricon（neuware4.4.3 / 4.7.2）、enflame（tops1.9.10 / 1.10.6）、hygon（dtk26.04）、iluvatar（corex4.4.0 / 4.5.0）、metax（maca3.7.2.1 / 3.8.1.3）、sunrise（tangrt1.2.0）、tsingmicro（tsm260610），共 9 家廠商。
  • FlagTree 側三筆：PR #1417 加燧原 builder 並把驗證步驟改成資料驅動；PR #1419 修掉「構建期斷言燧原後端」的寫法；PR #1421 把燧原 toolkit 的 deb 預置進 builder 映象，減少每次構建的下載依賴。另有 PR #1410 把 pybind11 ABI 從實際發出的外掛裡讀回、而不是寫死字面量，PR #1413 讓失敗的 plan 直接讓整個 run 失敗而不是跳過構建。
  • 判斷：這 16 筆沒有一筆是功能開發，全部在消除「本機能編、目標機能跑」之間的縫隙。與 10-16 至 10-18 的六後端 22.04 收口連起來看，FlagCX 的製品通道已從「逐個後端打補丁」過渡到「一行一個後端、同一套 22.04 配方」。

1.3 FlagQuantum：405 檔案合入量子棧擴容，M0 路線圖確立（10-19）

日期：2026-10-19　來源：PR #635 · PR #637 · PR #642 · 倉庫

  • 規模：23 筆提交、9 筆合入，是當日提交量並列第一的倉庫。PR #635 單筆 405 個檔案、+114463/−3983，新增 159 個公開名：演算法包由 45 增至 148、量子糾錯由 84 增至 108、遠端呼叫由 20 增至 32、可觀測量由 12 增至 20、編譯器由 12 增至 17、模擬由 8 增至 11，並新開 flagquantum.operators 包（4 個匯出）。能力登錄檔由 68 項增至 97 項，其中 development_evidence 由 20 增至 47。
  • 邊界紀律：所有新名都是子包入口，Stable Core 的 flagquantum.__all__ 仍為 41 個匯出、與 main 位元組一致；PR 正文明確「提升到 Stable Core 走獨立提案路徑」，同時新增三份契約檔案（編譯器 pass 准入、多級 IR 內部介面、real-time 訊息）。
  • 路線圖：PR #637 確立 M0 至 M4 的分階段範圍、依賴與驗收標準，要求複用現有 Core IR、編譯器、動力學求解器、執行時與 PyTorch 整合，覆蓋超導、中性原子、離子阱、光子與拓撲五類硬體；M1 從混合維狀態空間起步。同一 PR 還修正了收縮高斯重疊積分的精度問題（改用 math.fsum 處理相消敏感求和，並補一條原始基序迴歸）。
  • 動力學與編譯器：PR #639 支援混合維狀態空間，PR #640 支援顯式截斷的玻色運算元，PR #641 支援靜態運算元和的係數訓練，PR #642 允許呼叫方按名字在兩個最佳化點注入自有 pass。另有 10 餘筆測試與文件提交把數值斷言改成「按精度重複性比較」，而非按固定字面量比較。
  • 判斷：量子棧正在從「框架雛形」走向「通用量子計算框架」——PR #635 補的是覆蓋面（糾錯、化學、實時呼叫、超運算元），PR #637 補的是邊界與階段。兩者同日合入，意味著 M0 的起點是把已有能力寫清楚，而不是先擴 API。

1.5 FlagBLAS：海光 gfx936 六精度 GEMM 合入（10-19）

日期：2026-10-19　來源：PR #151 · PR #149 · 倉庫

  • 主體：PR #151 合入海光 gfx936 的廠商專用 GEMM 核心，覆蓋 sgemm、hgemm、bfgemm、dgemm、cgemm、zgemm 六種精度（+7060/−127，23 個檔案）。hgemm/cgemm/zgemm 走獨立 Triton 核心與按形狀分檔的配置，配 ctypes 調 hipBLAS 的參考實現與不依賴 cupy 的測試；dgemm 走 fp64 MMAC 點積核心；bfgemm 帶調優池、TN 三路策略與 padding 路徑。
  • 依賴關係：dgemm 明確依賴 FlagTree 的 fp64 MMAC 支援——BLAS 的精度補齊把編譯器側的能力缺口暴露了出來，這是跨倉協同的一處實證。
  • 配套：同日 PR #149 合入 Hygon L1 支援並補齊 L1 基準形狀，另有 sgemm 單筆（#91）與註釋英文化、移除 ABS 運算元等整理提交；倉庫視窗內 9 筆提交、3 筆合入，是當日提交量第四的倉庫。
  • 判斷：FlagBLAS 此前只有 v0.3.0（09-28）一輪發布，日常提交不多；單日九筆、六精度齊上，是海光通道在 FlagOS 2.2 之後第一次成體系的投入。

1.6 FlagTree：燧原 GCU300 基線與 AMD RDNA 降級路徑、昇騰 3.5 py312 交付（10-19）

四、總結與趨勢觀察

  • 趨勢一：製品通道的統一先於功能擴張。build-infra 單日 16 筆提交、16 筆合入，全部圍繞 22.04 自包含 builder；昇騰四輪子、曦望、清微在同一天被拉進同一套配方，base/ 目錄形成 9 家廠商 17 個基線映象的矩陣。glibc 底線由 2.38 降到 2.35 這件事，比任何一個新運算元都更直接地決定「輪子能不能裝到使用者的機器上」。這一線索與 10-16 至 10-18 的六後端收口連成完整鏈條，可視為 FlagOS 2.2 釋出後的第一個系統性補課。
  • 趨勢二：量子棧從框架雛形轉入通用框架的邊界定義。FlagQuantum 單日 405 檔案、159 個新公開名合入，同時以 M0 至 M4 路線圖明確五類硬體的複用前提，並保持 Stable Core 的 41 個匯出不變。這種「擴子包、鎖核心」的做法，與 10-18 量智雲釋出時把 FlagQuantum 作為技術底稿的定位一致——對外講能力之前，先把哪些是穩定介面寫清楚。
  • 趨勢三：國產算力側的投入正在從「運算元」走向「基準與基礎庫」。海光在 FlagBLAS 補齊六精度 GEMM 與 L1 支援；天數在 FlagDNN 補等價效能基線並直推 master；燧原在 FlagTree 鋪 GCU300 基線與 vLLM 基準工作流；摩爾執行緒同時動 FlagGems、FlagTrain、FlagSparse 三條線。共同點是都可被基準直接度量，而非僅「支援某運算元」。
  • 趨勢四：KernelGen 進入稀疏與檢視語義的掃尾段。合入側的 _coalesce、ccol_indices_copy、_neg_view_copy 與在審側十餘筆稀疏運算元（_sparse_mm 族、coo/csr 索引互轉、copy_sparse_to_sparse_）說明稠密主幹已基本清倉；同時崑崙芯以 30 筆在審構成單一後端最大佇列，XPU3 的注意力族與 RNN 族是下一批要合入的主體。
  • 趨勢五：新聞面進入會後消化期，資訊重心回到倉庫。24 小時視窗內有效新聞 1 條（中華網 10-19 的技術拆解，補七個量化案例），元件名直查連續零命中，分論壇紀要與工作坊內容尚未成稿。按經驗，這類視窗後的一到兩天通常會出現分論壇的二次報道，可作為下一期的觀察點。
  • 下一期關注：一是 FlagQuantum 的 feat/m0-common-foundation 分支（10-19 16:47 建立）何時落 PR；二是 FlagGems 那批稀疏核心在審佇列的合入節奏；三是 build-infra 是否把「一行一個後端」的配方複製到 FlagTree 與 Torch-FL 的製品線；四是大會分論壇紀要是否公開。
