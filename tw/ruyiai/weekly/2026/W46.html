2.1 triton-riscv：從”十八個夜間標籤”到第一個正式釋出

日期：2026-11-06 至 2026-11-14　來源：正式釋出標籤、PR #105 README 改為 wheel 優先

這條倉本週走完了三步：把釋出層級立起來（第一個 release/ 標籤）、把安裝路徑從原始碼改成 wheel、把異構後端從”能編”做到”能在真機上跑”。三步之間有先後依賴——沒有可復現的 wheel 標籤，GPU 後端的驗證就只能停在原始碼構建；而 AMD 後端的驗證又反過來暴露了釋出鏈上幾處只在自託管 riscv64 runner 上出現的問題。

2.1.1 標籤本身是釋出動作的全部內容

日期：2026-11-06、11-09　來源：release/20261108-6895885、PR #101

release/20261108-6895885 指向提交 6895885，也就是 11-06 那筆”為 AMD 補 riscv64 缺失 codegen 庫”（#102）的合入提交，與夜間版 nightly/20261106-6895885 是同一個點。當天三筆提交（#105、#106、#107）都在標籤之後落地，沒有進這個包——這意味著第一個正式版打的其實是上週末的程式碼狀態。

釋出鏈的兩處配套改動此前已在視窗內落地：#101 修 #100 之後暴露的兩處釋出鏈問題（釋出工作流改用與 CI 相同的檢出動作版本，scripts/release.sh 增加後端註冊步驟，讓 release 產出的 wheel 與 CI 構建的 wheel 具備同樣的外掛註冊資訊），#102 讓 setup.sh 在檢測到 AMD codegen 庫缺失時本地構建並放到約定路徑、env.sh 把 TRITON_AMD_CODEGEN_PATH 指向它。夜間版另加了唯一版本字尾 .dev<日期>，因為此前每次構建共用 Triton 自己的版本號，包索引會拒絕重複版本。

2.1.2 安裝路徑換成 wheel 優先，快速開始改成看反彙編

日期：2026-11-09　來源：PR #105、PR #107

#105 重寫了 README 的安裝段：先給 wheel 路徑與承載它的包索引，再給所需的 LLVM 歸檔與指向變數；原始碼路徑壓縮成 make setup（建 .venv、克隆固定版 Triton、下載固定版 LLVM 與 buddy 構建），原先”建虛擬環境、裝依賴、環境指令碼十五個變數”的說明收成一條短注。#107 隨後做了修正：包索引目前還沒有 triton 與 buddy 工具，README 裡那條二進位制安裝給出的地址會失敗，於是改為指向兩個專案各自的 GitHub releases、從磁碟裝 wheel。同一筆還修了 Python 3.14 下 lit 崩潰——Triton 用 which 在 PATH 裡找 lit，而 LLVM 樹裡那份 lit 在模組級呼叫 main，Python 3.14 在 Linux 上預設改用 forkserver 啟動方式，重新匯入時直接崩潰；修法是把構建直譯器的 bin 目錄放到 PATH 最前。

2.2 triton-riscv 的異構路線：RISC-V 宿主驅動 AMD 卡

日期：2026-11-10　來源：PR #110 預設啟用 GPU 後端、README

#110 合入後，這條倉的定位從”只在 RISC-V CPU 的向量單元上跑 Triton”擴到”從 RISC-V 主機驅動異構加速器”。三條改動裡，構建側用現有 Buddy LLVM SDK 構建並打包 riscv64 的 AMD codegen 庫；驅動側修掉 CPU 與 GPU 二選一時的歧義，規則是優先選用可用的 GPU（該檔案淨刪四行）；文件側在 README 加 AMD GPU 一節，說明 ROCm 在位時後端透過 torch.version.hip 自行啟用、wheel 不帶 ROCm 執行時、強制回 CPU 用 TRITON_DEFAULT_BACKEND=triton_shared。

真機驗證是這條改動的分量所在：SG2044 配 RX 7900 XTX，torch 與 ROCm 來自 openRuyi 的軟體倉，另測了隱藏 GPU 裝置時的自動回落。在一個主流 AI 加速卡都不帶 RISC-V 宿主驅動的時點，先支援 AMD 卡是最現實的一步——ROCm 的 RISC-V 側工作本來就在 openRuyi 倉裡維護，兩者是同一批人在推。

時間差值得記下：當天 10:22 出的夜間版 nightly/2026-11-10-209274f 早於這筆合入，因此那個包還不含 GPU 後端。

2.3 釋出鏈與釋出物：三筆 CI 修復、wheel 減重四成、顯式目標改走 -O3

日期：2026-11-11 至 11-12　來源：PR #113 共享 git 認證、PR #116 wheel 瘦身、PR #117 -O3 與 +zvfbfmin

11-11 的三筆合入全在釋出鏈上，沒有一筆改編譯器功能。#113 把 CI 與 release.sh 各自複製的一份”一次性全域性 git 配置”抽成 scripts/_git-auth.sh 共用：自託管 riscv64 runner 上的匿名 git 流量拿不到認證，上游 FetchContent 拉 googletest 時返回 401 並在沒有 tty 的情況下卡在使用者名稱提示。#111 修釋出指令碼本身；#112 是文件，在 #110 之後刪掉 CPU 路徑已不需要的 torch 安裝命令，並給 AMD 一節補上”要裝 torch，而且必須是能用 AMD GPU 的構建”。三筆作者同一人，時間集中在 17:59 至 21:11。

4.2 i1 掩碼按位元組讀寫（#1052）

日期：2026-11-12　來源：PR #1052

memref 元素型別為 i1 時，可伸縮向量此前被直接拒絕（提示 a memref of i1 needs fixed vectors），因為 memref 每元素佔一位元組、i1 向量每位佔一車道，只有定長向量有逐車道的下降。而 Triton 的 load/store 掩碼恰好就是 i1 memref：走純 VIR 管線加可伸縮向量時，325 個 Triton-RISCV 測試檔案裡 179 個卡在這個錯誤上，是本週七筆裡影響面最廣的一筆。

改法是按位元組讀寫：連續訪問用 i8 向量的 llvm.load/store，非連續的 strip-mined 區域用 vp.strided.load/store 全車道開啟；順帶把 i1 車道按一位元組計尺寸——此前首個動態向量為 i1 的區域按 1 位算，VLEN 256 下會得出 vector<[512]xi1> 這種十六組暫存器的規模。

4.3 libm-only 數學函式逐車道展開（#1053）

日期：2026-11-12　來源：PR #1053

LLVM 不肯在可伸縮向量上下降的數學函式（erf、erfc、cbrt、powf、atan2、acosh 等）改為逐車道展開：對 vector<[N]xT> 的 N 乘 vscale 條車道逐條 extract、調標量函式、再 insert。誘因是 convert-math-to-libm 對可伸縮向量的處理與定長向量一樣、只算前 N 條，其餘靜默置 0——一個可伸縮 erf 在 VLEN 128（vscale 2）下有一半車道是錯的。效果直接體現在測試面：FlagGems 套件 4045 項在 SG2044（VLEN 128）上透過數從 3980 升到 4006，修好的 26 項是 test_erf 與 test_gelu，無新增失敗。

4.4 bf16 的兩條路徑與窮舉驗證（#1054）

日期：2026-11-12　來源：PR #1054

RVV 只有帶 Zvfbfmin 才把 bf16 放進向量暫存器，沒有該擴充套件時 LLVM 連一次載入都不肯下降。改動給下降器加了 rvv-mattr 引數，預設按有 Zvfbfmin 處理（Buddy 的幾個 RVV 目標 K3 的 X100 與 A100、SG2044 都有）；顯式給 -zvfbfmin 時改為按整數位處理，把 bf16 向量當 i16 讀寫、extf 與 truncf 用整數運算（truncf 按就近取偶）、absf 與 negf 走符號位。

驗證方法是本週最重的一處：truncf 覆蓋全部 2^32 個 f32，extf、absf、negf 及 extf-mulf-truncf 覆蓋全部 2^16 個 bf16，在 SG2044 與 K3 兩塊核上與 Zvfbfmin 路徑逐位比對，結果相同。這種驗證成本說明 bf16 已經按出貨路徑對待，而不是”有空再說”的最佳化項。

4.5 fast-math 標誌與全部歸約種類（#1055、#1056）

日期：2026-11-12　來源：PR #1055、PR #1056

#1055 修的是 fast-math 標誌在 strip-mined 下降裡被丟掉：一個帶 contract 的 arith.mulf 加 arith.addf 被重建成普通 fmul 與 fadd，LLVM 不會融合。現在標誌隨同種運算元傳遞到向量迴圈與尾部，f32 乘加能出 vfmacc，bf16 在 +zvfbfwma 下出 vfwmaccbf16；作者在 K3 的 X100 與 A100 上以 4M 車道逐位比對 fmaf 展開，結果一致。這是七筆裡唯一一筆直接改指令選擇的。

#1056 把 vir.reduce 從只認浮點的 add 與 maxnum，擴到 vector.reduction 的全部種類：add、mul、minsi、minui、maxsi、maxui、and、or、xor、minnumf、maxnumf、minimumf、maximumf，整數一併支援，並由 verifier 校驗 kind 與元素型別是否匹配。此前 Triton 的整數求和、min/max、乘積、all/any（以及依賴它們的 argmin、argmax、count_nonzero、雙調排序與基數排序）都留在迴圈裡。改動新增 570 行、涉及 9 個檔案。

4.6 殘留路徑收尾：rank-0 填充與整數矩陣乘（#1057、#1058）

日期：2026-11-12　來源：PR #1057、PR #1058

#1057 把 rank-0 memref 的 linalg.fill（多數是歸約的累加器）降成一次 memref.store，FlagGems 1811 個核心裡殘留的 linalg.fill 從 393 降到 0。#1058 讓整數矩陣乘也能下降：A、B 為同一整數型別且不寬於 C 時先做符號或零擴充套件再乘加（不帶 fma），RVV 上 int8 矩陣乘得到 vsext.vf2 加 vwmacc.vx，無符號則是 vzext.vf2 加 vwmaccu.vx；同筆還修掉動態形狀 matmul 的斷言失敗——M 與 K 原本在 vir.set_vl 區域內取，被後續 pass 在使用中擦除。改完 1811 個核心裡已無 linalg.matmul。

兩筆合起來給出的是可複核的覆蓋率口徑：不是跑分，而是”還剩多少 linalg 或標量路徑”。

五、Buddy Compiler 動態

5.1 VLEN 精確化的前半程：#1032 與 #1037

日期：2026-11-08　來源：PR #1032、PR #1037

#1032 解決的問題是一類錯誤的失敗方式：不報錯，只算錯。按精確 VLEN 構建的 RISC-V 模型，向量程式碼只對那一個 VLEN 成立——llc 被明確告知 VLEN（+zvlNb 與 -riscv-v-vector-bits-max），decode attention 裡的可伸縮向量也按它定尺。換到別的 VLEN 上，模型不崩潰，直接給出錯誤結果。

修法是把校驗前移到載入時刻：runtime/rvv/BuddyRvvVlen.c 作為建構函式被連結進模型庫，庫一被載入就讀 vlenb，發現與構建時的精確 VLEN 不符就列印資訊並以 _exit(1) 結束程序。用 _exit 而不是 exit 是有意的——載入器持鎖期間跑解構函式會死鎖。評審後又補了一筆，把校驗從”按構建變數判斷”改成”按最終 llc 選項判斷”：原先原生構建可能透過模型自帶的 LLC_ATTRS 指定 VLEN，若 BUDDY_RISCV_VLEN 與它不一致，校驗值會和實際程式碼不符；且只連結進了第三階段，Qwen3-VL 的視覺與解碼兩個 shim、以及分層連結的路徑都漏掉了。現在由構建指令碼從最終 llc 選項裡取出精確 VLEN（與 VIR 降低讀同一處），配置階段發現選項互相矛盾就直接失敗。測試是這條改動的另一半：test_buddy_rvv_vlen.py 為 VLEN 128 到 65536 分別構建模型庫，只有宿主那一個能載入，其餘全部以退出碼 1 結束。文件同步更新了 A210 與 K3 兩篇 DeepSeek-R1 部署說明，把”哪些構建是精確 VLEN、哪些是通用 RVV”的邊界寫清楚——A210 的核心是定長向量、沒有 VIR，屬於通用構建；K3 的 prefill_ime 必須 1024，屬於精確 VLEN。

#1037 修的是另一個方向的錯誤：-lower-vir-to-vector 在不給 rvv-vlen、也不開可伸縮向量時，按宿主暫存器寬度給定長向量定尺，但它的宿主識別只覆蓋 x86（AVX2、AVX-512）與 SVE，帶 V 擴充套件的 RISC-V 宿主一律落到通用預設值（128 位、16 個暫存器）。後果出現在測試裡：自 #1030 起，kernels 流水線在沒有 llc 選項時按宿主降低 VIR，riscv64 CI 宿主是 VLEN 256 卻被當成 128 位處理，q、k 範數的平方被切成 vector<32xf32> 分段求和，與向量核心逐位元比較的順序不同，vir decode qk_norm ... same bits 判定為假。作者先加了一筆只在測試裡固定 rvv-vlen=1024 use-scalable=false 的改動，隨即自行回退——那等於在 llc 選項之外再造一處 VLEN 設定，與 #1032 的方向衝突。最終修法是在降低階段識別 RISC-V 宿主（讀取宿主 CPU 特性與 hwprobe），按真實 VLEN 定尺。

5.2 f32 YOLOv8 端到端走通 VIR（#1041）

日期：2026-11-09（合入於 11-10 01:07）　來源：PR #1041、合入提交 18c66ec

#1041 把 f32 YOLOv8 圖端到端走通 VIR：先做 Linalg 到 VIR 的降低，再做 VIR 到向量方言的降低。此前這條 pass 裡沒有卷積 pattern，圖裡另有三類運算元直接失敗——一筆改動同時補上了卷積與那三類。規模是十四個檔案、新增一千六百四十六行、刪除一百一十五行、十三個提交。

卷積兩族都覆蓋：二維 NHWC 配 HWCF 與二維 NHWC 配 FHWC。向量化沿輸出通道 F 展開，對每個 (kh, kw, c) 把輸入元素廣播成每個輸出畫素一個 vir.fma，因此每次向量訪問都是連續的，也沒有跨 lane 的歸約——歸約需要橫向指令與後續的規約樹，在窄 VLEN 上代價明顯；代價是 FHWC 過濾器要先並行複製進 HWCF 緩衝，多一次搬運換內層迴圈的連續訪問。

三類此前失敗的運算元一併補齊：rank-0 輸入（memref<f32> 直接進 linalg.generic 會在 memref.expand_shape 報 invalid reassociation，改為載入一次後廣播）、保留末維的 linalg.reduce（如 DFL softmax 的 1x16x4x2100、dimensions=[1]、addf 與 maximumf 組合）、讀取 linalg.index 的命名運算元（如 upsample 裡的 linalg.map iota）。真機口徑很清楚：在 K3 上 f32 YOLOv8 pose 的原始輸出最多變化 6e-5，與 PyTorch 的差距仍在 6e-4（bus）與 8e-4（zidane）以內、與改動前一致；detect 模型的檢測結果不變、速度沒有下降；f32 與 IME 動態庫的輸出與改動前逐位元組相同。

七、趨勢觀察

7.1 釋出鏈先於功能：這一週修的是”能不能出包”

triton-riscv 一週內的合入裡，只有 #110（AMD 後端）是功能，其餘 #101、#102、#105、#107、#111、#112、#113 全在釋出鏈上：後端註冊進 wheel、AMD codegen 庫的本地構建、README 的 wheel 優先、lit 查詢順序、git 認證抽取、AMD 一節的 torch 前提。再加上 #116 的 wheel 瘦身與 #117 的 -O3，這條倉本週的產出可以概括為”讓裝機路徑可復現、可下載、可驗證”。

這不是個別現象：ruyi 0.54.0 的主要內容也是”裝之前先判能不能裝”，pytorch 的 #56 堵的是”零用例透過也算綠”，buddy-mlir 的夜間版補的是六天的出包缺口。四個倉同周做同一類事，說明這條棧已經從”證明能跑”進入”證明能交付”的階段。

7.2 覆蓋面優先於效能：393→0、2→0、179→0 的口徑

本週 buddy-mlir 七筆裡只有 #1055 直接改變指令選擇，其餘六筆做的是把此前留在迴圈裡的形態接進向量路徑：i1 掩碼、libm-only 數學函式、bf16、歸約種類、rank-0 填充、整數矩陣乘。評價這類改動的口徑應當是”還剩多少 linalg 或標量路徑”，而不是跑分——393 降到 0、2 降到 0、179 個失敗檔案歸零，都是這個口徑。

對照前一天 #1050 的 strip-mined 餘量降寬，兩天的分工很清楚：先讓向量迴圈吃滿車道（效能），再讓所有運算元都能進向量迴圈（覆蓋）。順序反過來會做無用功——空有滿寬度的迴圈，進去的運算元還是那幾個。

7.3 VLEN 1024 成為編譯器與執行時的共同壓力點

一週內有三處改動直接指向 VLEN 1024：載入期校驗（#1032）、歸約丟車道（#1051）、strip-mined 餘量（#1050）。共同點是同一個硬體事實在各層反覆出現——K3 的 prefill_ime 必須 1024，A100 核上 16 個 f32 就是一個完整向量，vector<[1]xT> 這種形狀在 VLEN 128/256 上根本走不到。

同一周的上游側也出現同一訊號：V8 的審閱名單裡出現 “Allow vlen=1024”（CL8585179）。這說明長向量不再只是某塊板的本地配置，而是開始進入執行時與瀏覽器的通用路徑。風險隨之而來——CI 的 riscv64 runner 是 VLEN 256，出貨硬體是 1024，兩者的測試覆蓋天然錯位；#1051 那種”CI 全綠、板子上全錯”的缺陷，正是這種錯位的產物。

7.4 靜默錯值的驗證成本已到窮舉輸入的量級

#1054 對 truncf 跑了全部 2^32 個 f32、對轉換與符號運算跑了全部 2^16 個 bf16；#1055 在 4M 車道上逐位比對 fmaf 展開；#1041 的驗收標準是”與改動前逐位元組相同”；#1051 的驗收標準是 25 項歸約測試從錯到對。四筆的驗證方式不同，但都在回答同一個問題：結果對不對，而不是跑得快不快。

原因也清楚：這一週修的缺陷幾乎全是”不報錯、只算錯”——按精確 VLEN 構建的模型換硬體靜默出錯、可伸縮 erf 有一半車道被置 0、歸約只剩 lane 0、掩碼按位算尺寸導致十六組暫存器。崩潰容易被發現，錯值不會。當驗證成本上升到窮舉輸入的量級時，說明這條棧已經按出貨標準對待 bf16 與歸約這些基礎運算元。

7.5 滾動打包與月度定版脫鉤

openRuyi 打包倉本週提交密度是近期最高（單日峰值三十六筆，KDE、安全、工具鏈、裝置面四條線並進），而對外可見的月度版本仍停在 2026.09。兩件事不矛盾：滾動打包與月度定版本來就是兩條線，日更說明工程在動，缺版說明發版流程或驗證週期卡住。

值得留意的是本週新增的兩個治理倉：release 規範倉把需求編號與優先順序寫成流程，ruyi-deck 定位為”倉庫與釋出的操作檯”。兩者都不產出程式碼，指向的卻是同一個缺口——一個月度版本要跨打包倉、映象、韌體多個倉發，缺的不是提交，而是把提交收斂成一個可釋出版本的那道工序。

7.6 “能不能裝”第一次變成可計算的事實

ruyi 0.54.0 把 ELF ABI 相容性做成三態判定（相容、不相容、未判定），並在 list、install、admin check-abi 三處暴露。這件事的意義不在功能本身，而在把”這個包能不能在我的機器上跑”從經驗判斷變成可查詢、可比對、可排障的資料。

對 RISC-V 尤其重要：同一份預編譯二進位制在不同擴充套件組合、不同浮點 ABI 的宿主上行為不同，過去只能靠試。三態設計還留出了”未判定”這一檔，避免把未知當成不相容——這個區分決定了工具在真實環境中是否可用。下一步可觀察的是 sidecar 的覆蓋面：哪些包補了 ABI 資訊、哪些仍是”無資訊”，080 期提到的 packages-index 為部分包補 ABI 相容資訊，是這條線的延續。
