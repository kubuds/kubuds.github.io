triton-riscv：一天之內從「打補丁的分支」變成「上游外掛」（11-05）

日期：2026-11-05　來源：PR #98、提交列表、PR #92

改造分三處。第一處是後端形態：Triton 的 TRITON_PLUGIN_DIRS 機制把 backend/ 裝成 triton_shared 後端外掛，註冊入口點、把 C++ 外掛鏈進 libtriton.so、把 triton-shared-opt 一併複製進包；獨立發行包隨之消失，程式碼裡的匯入統一改走 triton.backends.triton_shared；後端自身改為透過 paths.py 查詢 buddy-opt、buddy-llc、mir-translate 與 triton-shared-opt，CPU 驅動宣告自己僅在沒有任何 GPU 後端時才處於活動狀態。

第二處是補丁集清零。patches/ 目錄與施加補丁的指令碼全部刪除。補丁集此前存在的理由有兩個：讓 Triton 在沒有 NVIDIA/AMD 工具鏈的環境裡構建，以及兜住 LLVM API 的頻繁變動。現在 buddy-mlir 的 LLVM 發行版帶 NVPTX/AMDGPU 目標與 lld（#1027），再把 Triton 的 GPU 依賴路徑指向 stub 目錄，兩個理由都不成立。

第三處是出包路徑合併。release.sh 不再組裝第二個 wheel，只剝掉工具、直接 bdist_wheel；Makefile 成為 setup、build、test、lit、clean 的統一入口。順帶修了一處 Python 3.14 的坑：setup.py 裡 shutil.which("lit") 會優先取 pip 安裝的 lit 控制檯指令碼，而 LLVM 發行版自帶的那個呼叫 main() 時沒有 if __name__ == "__main__" 保護，forkserver 多程序在匯入主模組時會重跑它，lit 目標在 80 併發下因此失敗。

代價寫在同一個 PR 的說明裡：Triton 3.9 的前端會從後端讀取 backend_name 等欄位，缺了它每個 tl.atomic_* 呼叫都會拋 AttributeError，riscv64 上有 383 個 FlagGems 用例因此失敗；補上 backend_name、default_dot_input_precision 與 deprecated_fp8_dot_operand_dtypes 三個欄位後失敗面才收掉。示例側也有讓步：上游拒收了 asin/acos/atan/atan2 的前端補丁，例子改用 libdevice，靠它降到同樣的 __nv_* extern_elementwise，再由 triton-shared 轉成 MLIR math 運算元。

七、趨勢觀察

分發鏈路打通，但「打包完成」不等於「能力同步」

#1350 的意義不在版本號，而在分發路徑第一次被寫成發行版配置：以前要用這套棧，得自己拉 triton-riscv、tilelang-riscv 與 buddy-mlir，按文件設 BUDDY_MLIR_BINARY_DIR 一類變數；現在 openRuyi 的打包倉裡有了這三個元件，使用者的安裝門檻從「會編編譯器」降到「會裝包」。

但三份 spec 錨定的程式碼都早於本期上游：triton 停在 09-13、tilelang 停在 10-28、buddy 停在 0.1.2，而三個倉庫本週都還有新動作。最刺眼的是 tilelang——11-03 剛合入的 PR #5 是十八天靜默後的第一筆功能，卻不在當天合入的 RPM 裡。版本串 3.8.0+git20261103 會強化誤讀，把打包日期當成程式碼日期。要解決這個落差，要麼建立定期的 bump 流程，要麼在包描述裡寫清快照日期；否則每合入一筆功能，包與倉庫的差距就再拉大一點。

外掛化把補丁成本換成版本繫結，383 個失敗用例是首付

triton-riscv 的收益很直接：以後跟隨上游升版不再需要重放補丁，出包只剩一個 wheel，安裝面從兩個發行包降到一個。代價同樣明確，而且是同一天暴露的：Triton 3.9 的前端從後端讀 backend_name 欄位，缺它就有 383 個 FlagGems 用例失敗。寄生在上游擴充套件點意味著上游前端的隱式契約變成必須滿足的介面，而這些契約往往沒有文件，只能在測試裡撞出來。

判斷這次改造是否成功，不看今天刪了多少行，看下一次上游升版時重放的成本，以及 FlagGems 這類下游套件是否還需要專人盯版本。到本週末，跟隨上游的路徑已經清晰，配套的驗收流水線仍未建立：#56「Migrate additional FlagGems operators」仍是開放狀態，「這批運算元能不能在 riscv64 上跑通」這個問題仍然只能在 PR 裡回答。

後端成為本週主軸，前端與執行時靜止

本週的可核增量幾乎全部落在「編譯與降級」：LLVM 的 AME 後端補暫存器歸類與 tile 排程、buddy-mlir 的 BOSCAME 打通契約到 FPGA、VIR 把 set_vl 的 VLEN 語義收緊、tilelang 補 streaming load 的降級路徑。與此同時，pytorch 的 RISC-V 分支三次重放、零功能增量，main 側一百餘筆上游同步裡沒有一筆涉 RISC-V。

這個分佈說明這一階段的重點是讓已有運算元在 RISC-V 上降得對、跑得穩，而不是擴大前端覆蓋面。對下游使用者來說，短期內可感知的變化會出現在編譯產物與 JDK 行為上，而不是新框架支援列表裡。與之配套的短板也在同一處：效能方向唯一一條明確以最佳化為目標的 triton PR #85 仍停在 10-18，半個月沒有動靜。

發版節奏：beta 出了，正式版與月度版仍在視窗外

十月末兩條月度承諾同時落空，十一月第一週各有一半下文：ruyi 在 11-02 出了 0.54.0-beta，39 天斷檔後第一跳，並把 0.54 的正式版定到 11 月 11 日前後；openRuyi 的 2026.10 月度公告到 11-07 仍未出現，成為首個整月缺版。

兩條線的程式碼側都不算停滯——openRuyi 主倉本週 156 筆提交，ruyi 有 ABI 探測與取包修復落地——所以卡點在版本凍結、公告撰寫、映象構建與釋出這一段。這與上週的判斷一致：這個生態的「把東西做出來」與「把東西發出去」是兩套能力，前者在多個倉庫同時推進，後者在近兩個月裡沒有一次按期完成。

基準側長期空白，讓「最佳化是否有效」無法回答

VecIntrinBench 停更近九個月、IntrinTrans 四個月、FBGEMM 三個月，三個倉全周零提交。同一周裡，glibc 與 newlib 補了十八個向量數學函式、LLVM 合了六筆 P-ext 與 Ztt v0.6、buddy-mlir 鋪開 209 個檔案的矩陣後端——能力在擴張，度量沒有跟上。

後果不是抽象的：沒有更新的內建函式基準，就無法回答「編譯器實際支援集合漲了多少」；沒有常駐的效能基線，就無法回答「BOSCAME 路徑比舊路徑快多少」。本週所有與效能有關的表述都只有「未觀察到明顯迴歸」這一級別，而這類表述無法支撐選型。

桌面包與 AI 棧並行，兩條線不在同一個節奏上

openRuyi 一週 156 筆提交，其中 74 筆是 firecracker 的 Rust 依賴閉包、37 筆是 LibreOffice 依賴鏈——這是按元件分批推進的桌面辦公套件打包。同一天（11-05），RuyiAI 棧除 triton-riscv 外全部靜默：pytorch 的 RISC-V 分支零提交、tilelang-riscv 零提交、llvm-project 的 riscv 分支零提交。

兩條線由不同的人、不同的倉庫、不同的節奏推進。對讀者而言，把打包側的活躍當作 AI 棧的進展是一種誤讀；對專案而言，這種分工本身沒問題，但週報層面必須分開記——否則「提交數」這個指標會持續給出錯誤的繁榮感。
