2026-10-23 苦芽科技

素材來源：本刊每日 RuyiAI 動態報告 5 期（2026-10-19 至 2026-10-23，每期視窗為前一日 04:30 至當日 04:30，其中週一為過去 3 天、覆蓋週末）；另含 RuyiAI-Stack、ruyisdk、buddy-compiler 三個組織的 168 小時倉庫核查，openRuyi-Project 重點倉庫補充核查，RuyiSDK 開發者社群與 openRuyi 發行版新聞頁雙源複核，以及 RuyiAI 官方主頁三頁快照（核查覆蓋至 10-24 上午）。

論文：長向量處理器上重排 FlashAttention，實測加速 1.84 至 2.08 倍

arXiv 2610.29489v1《Reorienting the Vector Axis: Restructuring FlashAttention for Long-Vector Processors》（Emmanuel Irabor、Marc Casas）把 PyTorch 的 CPU FlashAttention 核心移植到帶 2KB 向量暫存器的 RISC-V CPU 上，先給出一個不客氣的基線：只達峰值浮點吞吐的 16.2%。

原因分析具體：原核心按查詢行逐行推進，與 V 的乘沿 64 元素頭維向量化，softmax 的逐行最大值與求和是「把整個暫存器塌縮成標量」的歸約，軟體指數函式的多項式係數還要與 tile 資料搶向量暫存器，導致溢位到棧，三項疊加使向量暫存器利用率上不去。兩條改法都不改演算法與數值：其一，把分數 tile 與執行輸出一起轉置，讓查詢落線上性連續軸上，於是「一個 tile 裡裝多少查詢」這一個引數就統一決定核心各段的向量長度，兩個歸約自然消失；其二，把多項式係數搬進標量暫存器，消除溢位，softmax 的向量訪存指令減少 78.7%。

實測：頭維 64 時兩項合起來把整核週期降到 1.84 至 2.08 倍加速，浮點利用率從 16.2% 升到 29.7%；同設計的 FPGA 對兩項改動的排序一致且收益更高，達 2.71 倍。對本棧的意義在方法而非數字：向量長度自適應與暫存器壓力正是 triton-riscv 與 tilelang-riscv 在 RVV 降級上的結構性問題，而非「有沒有 intrinsics」；文中「按機器匹配 tile 內查詢數」與 IREE 把 Tile N 取 vlen/8 屬同一類決策，可直接做同口徑比較。來源：arXiv 2610.29489

擴充套件落地路徑成形：編譯、模擬、運算元三層齊備才算可用，齊備之後瓶頸轉到硬體實測

以 AME 為例，本週可見一條擴充套件從提案到可用的完整路徑：先有後端設計與指令集定義（LLVM #16、#24、#27、#29），再有降低與排程實現（#30、#31、#32），同時模擬器給出可執行語義（QEMU ame-0.6），最後運算元庫提供可測的 kernel 與驗證套件（AME-operator）。Ztt 也在本週補齊一側——ruyisdk/llvm-project 的 AME 分支落下 spec v0.6 初版支援，與 GCC 側 Ztt Md 支援、QEMU 的 Ztt 指令族實現對應。

P 擴充套件走同一條路但已到後半程：QEMU 覆蓋全部指令（12 筆收尾批），GCC 更新到 0.6，LLVM 側 mulq、乘高位累加、sati/usati、Packed Pair 等 intrinsics 分批合入上游。對照來看，P 擴充套件缺應用側 benchmark，AME 缺真機。這個順序值得作為方法記錄：沒有模擬器無法驗證編譯器，沒有運算元庫無法驗證模擬器；三者齊備之前談效能沒有意義，齊備之後瓶頸才轉移到硬體與實測。本週的進展是「齊備」而不是「更快」。

RVV 後端焦點從「有沒有指令」轉向「分塊與執行緒化」

IREE 用兩天走完 f32 到 f16 的精度臺階，兩次都複用同一個 lowerRiscvVFmaccLike 與同一套累加器合法化，次序是先保證有正確路徑（f32），再按擴充套件可用性挑最快的一條（f16 原生、f16 加寬、+zvfhmin 回退），代價模型對三條路徑分別定價。X60 上的實測把瓶頸位置說清楚了：單執行緒 inner_tiled 已快於 mmt4d ukernel，4 執行緒與 8 執行緒仍慢。

arXiv 那篇長向量 FlashAttention 重構給出的結論同源：把分數 tile 與執行輸出轉置、讓查詢落線上性連續軸之後，兩個歸約自然消失、暫存器溢位消除，整核週期降到 1.84 至 2.08 倍，浮點利用率從 16.2% 升到 29.7%。兩者都在說同一件事——單核指令選擇到位之後，剩下的是分塊引數與執行緒化。對 tilelang-riscv 與 triton-riscv 來說，這是可逐條對照的路線圖：Tile N = vlen/8 的取法、代價模型的分檔方式、tile 內查詢數與向量長度的繫結關係，都值得在自家 lowering 裡做同口徑比較，而不是隻看「是否支援 f16」。

發行版開始鋪桌面與虛擬化驗證棧，平臺形態出現伺服器與嵌入式兩條路徑

openRuyi 的開放 PR 佇列裡出現一組同向提案：qemu 開啟 GUI 測試特性（#1421）、新增 virglrenderer（#1415）、ovmf 支援 fwupd（#1436）、新增 ydotool（#1457）、修 xorriso 的 man 頁衝突（#1489）。五項分屬虛擬化、圖形虛擬化、韌體更新、輸入自動化與光碟映象工具鏈，合起來指向「在 RISC-V 上跑完整桌面並對其做自動化驗證」——這與峰會展示的「AI 驅動 IDE 圖形化測試」是同一需求的兩端。

平臺形態同時出現分岔。伺服器級以進迭 V100 為代表，規範裡的 UEFI、ACPI、SMBIOS 成為硬要求，BRS 符合性測試與安裝鏈路是入場券；嵌入式與消費級以 K1/K3 為代表，路徑是板卡映象、工具鏈與支援矩陣。本週 ruyi-imager 新增 K3 的 UFS 與 UEFI 供給支援，是該分岔在工具側的第一個具體動作；而 openRuyi 主倉整週零筆伺服器平臺相關提交，V100 的相容清單能否兌現要看 2026.10 版本與後續韌體線動作。
