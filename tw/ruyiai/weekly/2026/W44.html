日期：2026-10-26　來源：InsertVSETVLI 遷移、PreAllocZilsdOpt 遷移、DeadRegisterDefinitions 遷移

餘下四筆分屬三個方向：vxrm-pipeline-flush 屬性把 VXRM 的投機寫限制在帶重新整理保證的迴圈內；LSR 在 Zibi 目標上優先選等值比較作迴圈出口；GlobalISel 補上 G_FPTOSI_SAT 與 G_FPTOUI_SAT 的合法化，使浮點到整數的飽和轉換在全域性指令選擇路徑可用。另有一筆把收集散播降級與 VL 最佳化器用到分析改為惰性請求。

意義不在單筆改動，而在管線歸屬：這批 pass 長期掛在 LegacyPM，遷入 NewPM 後與新 pass manager 的分析快取、pass 順序與除錯介面對齊。對下游 fork 的直接影響是每次換基都會帶上這套變動，-passes= 名稱與 pipeline 組成會隨之上移——這也是本週 riscv 分支「換了基但補丁不變」時，實際內容發生變化的少數幾處之一。

七、趨勢觀察

VIR 走完「表達—呼叫—對賬」，但結論只能是「不引入損失」

過去三週這條主線一直在補表達力：10-26 一夜七筆把可伸縮向量補進來，10-27 補上 Python 繫結，10-28 直接把 K3 的解碼注意力整段搬過去，並拿板上吞吐做對賬。三個數字合起來才是這周的意義——數值位級一致、向量指令數相同（各 178 條）、吞吐區間重疊。自研方言最容易卡在「能跑但慢」這一關，本週至少證明這一關暫時過了。

但把它讀成「VIR 已追平手寫核心」就過頭了。準確說法是「在 K3 解碼注意力這一段、在固定向量長度下不引入損失」。兩處缺口明確：覆蓋面只有解碼注意力，A210 核心、MoE、量化與預填充路徑都沒動；可伸縮向量被顯式關閉（use-scalable=false），下一筆開啟之後向量尺寸不再由編譯期決定，LMUL 4 的分組假設會鬆動，屆時數值與指令數能不能守住，需要重新對賬。作者自己也把同一份程式碼兩次構建的 2% 差異寫在 PR 裡，這個量級恰好說明「持平」結論的邊界。

分支治理分道：llvm 寫規則並取消預演，pytorch 靠重放與同步機器人

同一個月內兩條分支給出了兩種答案。llvm 的 riscv 分支補丁集大（26 筆）、外部貢獻多，衝突與歷史漂移是主要成本，於是值得寫文件（RISCV_CONTRIBUTING.md）與配工作流（autorebase.yml），並把「預演」這一步刪掉——成功即推送，把摩擦降到最低、把風險前移給貢獻者，靠 --force-with-lease 與 SHA 複檢兜底。pytorch 的 riscv 分支補丁集小（11 筆），維護者自己重放一次的成本低於維護流程的成本，於是繼續每日或隔日整枝重放，再加一個同步機器人把基線抬到上游最新。

兩者的共同點是「本地補丁集長期不變」：llvm 的 26 筆、pytorch 的 11 筆，本週都沒有新增功能。跟蹤這兩條分支的正確方式不是看 SHA 或提交數——重放會把提交者時間統一改寫、把提交數隨上游膨脹——而是看補丁標題集合，以及上游帶進來了什麼（本週是 17 個 pass 遷入 NewPM 與 P 擴充套件的 isel 補齊）。

判斷一條分支治理是否見效，可以看兩個可驗證的訊號：llvm 這邊，工作流上線後外部 PR 是否真的變多（若兩週內仍無人按新基線提交，說明瓶頸不在重基工具）；pytorch 這邊，重放是否重新穩定為每日（本週是七日靜默後一次補做，屬擇期而非流水）。

打包成為 RuyiAI 棧的真實瓶頸，爭論開始有價格

#1350 爭論了將近一個月，核心分歧是 buddy-mlir 自帶的 LLVM 要不要外接。上週的口徑還是「可以用 GCC，但至少 1.5 倍時間」，本週作者給出實測：riscv64 上 8814 秒變 24798 秒，2.81 倍，且用 GCC 那次在連結階段失敗。爭論的性質於是從技術偏好變成構建農場的排期算術——2.81 倍意味著機器佔用、超時策略與釋出視窗都要重算。

這條對整條棧的啟示在方法而非結論：RISC-V 發行版打包的許多分歧（是否 vendor、是否外接工具鏈、是否隨包分發 IR），最終都要落到「構建時間、映象體積、可復現性」三個可測的數字上。同一周裡 openRuyi 收回「隨包分發 LLVM IR」的路線（#1509），#1350 用 2.81 倍守住「LLVM 留在包內」，兩次判斷方向相反，依據卻是同一類成本核算。

更進一步看，#1350 本週的複核意見已經從設計路線轉到 spec 寫法（缺 BuildRequires、Provides 對齊、補丁格式、空 %check 註釋），說明「能不能被髮行版吞下」的問題已經變成「包本身夠不夠常規」。三處非常規點——buddy-mlir 自帶 LLVM、triton 依賴 git 可執行、tilelang 需要發現 buddy-mlir 工具鏈——每一處都需要補丁與解釋，每個解釋都要維護者花時間判斷。若希望三件套進入月度發行節奏，把它們收斂成一兩條明確的打包約定（例如統一由 buddy-mlir 提供工具鏈、統一用 git format-patch 的補丁堆疊），比逐條回應複核意見更省事。

月末承諾集體後移：發行版轉入「按月鋪量、按周清掃」節奏

本週兩個月末承諾同時落空：ruyi 0.54.0 仍只有 09-18 的 alpha，openRuyi 2026.10 未發。與之對應，openRuyi 主倉本週 234 筆提交裡，KDE 框架一次 64 包、Samba 全家聯動、qemu 11.1.2 與 libvirt 回移、12 個 C/C++ 安全更新——這是典型的「鋪量與清掃並行」，而不是「切版本前的凍結」。

兩條流水線的節奏差異也值得記：KDE 包有上游 spec 可參照、有既定版本節奏，重打包是機械動作，所以能在一天內完成 64 個包；而 RuyiAI 三件套是從零寫的 spec，既要解釋「為什麼把 LLVM 留在包內」，又要解釋「為什麼 %check 為空」，從 09-21 開到現在仍在返工。發行版的「按月鋪量」能力與「接納新包」的成本並不對稱，後者取決於包本身有多常規。

對讀者的實際含義：ruyi 使用者在 10 月底仍會拿到 0.53.0；若 0.54.0 在 11 月初發布，還要看 ISCAS 軟體源是否恢復，否則 ruyi update 看到的包清單會落後於倉庫實際狀態。這兩件事是下一週期的首要核實項。

缺陷發現依賴單一入口，驗收鏈比修復鏈更脆弱

本週三筆 triton-riscv 修復的共同來源不是測試套件，而是「把 FlagGems 運算元搬上 triton-riscv」這件事本身：張量填充值的掩碼載入、迴圈攜帶的 gather 偏移、雜湊運算元的重複索引比對，三者都落在降級層與驗證層的邊界上。這類缺陷在編譯器自己的 lit 套件里長不出來，得有一個真實運算元庫按批次方式往上壓。

順序問題隨之暴露：修復先落地，需要它們的遷移 PR #56 卻停在 09-16。一批「為某個用法準備的修復」暫時沒有對應的用法在跑，若 #56 恢復時 Triton 上游又換了幾輪，三筆修復是否還與新基線相容需要重新驗證；若長期不恢復，這套端到端驗收集等於停擺，下一批缺陷要等外部使用者撞上。週期末尾 #56 有一次更新（10-30 20:50），但仍未合入——這是下週期最值得盯的一處。

推論是可以落地的：對一個以「能跑真實模型」為目標的棧，把遷移做成常駐迴歸（哪怕只有幾十個運算元、每晚跑一次）比再多合幾筆修復更有價值。工具鏈層面的證據也在同一周出現——#83 的驗證是本週三筆裡最硬的一筆（lit 291 透過、18 項執行時檢查），而它恰好也是與真實運算元整合最深的一筆。

基準側長期空白，讓「最佳化是否有效」無法回答

VecIntrinBench 停在 02-13、cpuinfo 停在 05-20、IntrinTrans 停在 06-25、FBGEMM 停在 07-13——四個向量相關倉庫全周零提交，停更時長以月計。與此同時，本週的效能結論只能靠 K3 板上的吞吐區間，而作者明確寫下同一份程式碼兩次構建可差 2%；三筆修復的驗證也只給透過數，不給向量化質量的任何指標（指令條數、佔用 LMUL、暫存器溢位次數）。

這不是本週新增的問題，但三筆合入與一次效能對賬把它照得更清楚：一條以「向量能力上行」為目標的棧，缺少持續跑分的向量內建基準，就很難判斷後續最佳化是真提升還是波動。下一步真正該補的不是更多 lowering，而是一個每晚能跑、能給指令數與 LMUL 的基準——否則「效能持平」與「效能提升」在 2% 噪聲下無法區分。
