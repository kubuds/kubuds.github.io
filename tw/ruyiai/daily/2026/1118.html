今日重點：LLVM fork 合入 XAME，ZTT v0.6 矩陣後端一次進 47 個檔案（11-17）

日期：2026-11-17　來源：PR #36、合併提交 542365c

11-17 15:05，RuyiAI 的 llvm-project fork 合入 #36「[RISCV][XAME] Add ZTT v0.6 matrix backend support」。PR 在前一天上午開出，一天內走完評審：47 個檔案、+4084 −19，其中指令定義 RISCVInstrInfoXAME.td 一項就 1732 行，內建定義 517 行，暫存器資訊 120 行，另有一個 262 行的狀態處理 pass。這是該 fork 的主幹自 11-02 停滯之後的第一筆改動，也是近半個月來體量最大的一筆。

合入的是一條完整的矩陣後端路徑，不是零散指令：xame 作為本地特性名（0.6 版），把 MLIR 產出的 LLVM IR 裡的矩陣與累加器 SSA 值降到 RISC-V 指令；llvm.riscv.ztt.* 內建名與 riscv.ztt.matrix／riscv.ztt.acc 目標型別沿用 ZTT v0.6 的編譯器介面，屬於臨時版附加矩陣擴充套件（Attached Matrix Extension）的下游實現。文件寫明兩套固定 profile：預設 +xame 為 8×8、16 個 M 暫存器、8 個 ACC、元素上限 64 位；+xame,+xame-gem5 為 4×4、32 個 M、4 個 ACC、128 位。兩者都按 32 位暫存器單元計。

工程量主要在暫存器與呼叫約定：138 條共享指令編碼、矩陣與 ACC 暫存器組、CSR 運算元、按 profile 區分的彙編與反彙編；暫存器分配後新增一遍狀態 pass，保證描述符、資料與狀態在暫存器複製和溢位時不被沖掉。矩陣引數走編譯器本地呼叫約定，不是 RISC-V psABI 標準，呼叫雙方必須約定同一 profile 與暫存器型別，超出暫存器檔案的引數會被拒絕，只能走記憶體。標量過載一律按無符號 XLEN 位型歸一化，需要符號解釋的前端自行符號擴充套件。

驗收覆蓋三處：LLVM RISC-V CodeGen 與 MC 3381/3382 透過，11 個 XAME 專項測試全過，唯一失敗是 xboscame-valid.s 的既有基線編碼差異（測試期望 ACC 編碼 8，而未改動的定義裡 ACC0 是 0，BOSCAME 檔案本身未動）；外部 Buddy MLIR harness 的 10 個 AME 轉換回歸全過；4×4 整數矩陣乘（A 取 1 到 16、B 全一）在 AME_gem5 裡編譯、連結並執行，16 個輸出正好是 10、26、42、58 的行和，guest 退出碼 0。

今日重點：triton-riscv 修 bf16 轉換器 ABI，riscv64 三條 CI 腿首次實機全綠（11-17）

日期：2026-11-17　來源：PR #121、問題 #114

11-17 18:37，triton-riscv 合入 #121「Fix the launcher ABI of the bf16 conversion helpers」，兩個檔案 +190 −7，主體是 backend/driver.py 裡兩個 helper 的原型，加一份 166 行的新測試。問題出在暫存器類：launcher 把 __truncsfbf2 與 __extendbfsf2 定義成 uint16_t 整數原型，而 llc 生成的呼叫點按 bf16 走浮點暫存器——x86-64 用 xmm0、riscv64 用 fa0，呼叫方從低 16 位取值；整數返回落在 eax／a0，於是每個 fp32 轉 bf16 的核心存下去的都是上一次浮點運算的殘留，要麼零要麼垃圾。

修法是把兩個 helper 的原型改成 float，讓 bf16 位待在浮點返回值低 16 位；__bf16 本身用不了，因為 launcher 由 g++ 編譯，而 Ubuntu 24.04 的 g++ 13 在 riscv64 上沒有這個型別。__truncdfbf2 與 bf16 libcall 家族其餘成員明確列為不改動，當前 lowering 不產生它們。

新測試 python/examples/test_bf16_convert.py 把 fp32 與 bf16 的互轉按 torch 的 int16 檢視逐位對齊，覆蓋 round-to-nearest-even 的四類邊界（半值以下、偶數與奇數 lsb 的 tie、半值以上、float32 最大值到無窮），修前其中四例失敗；再用重定位斷言釘住 libcall 路徑——host 目標構建在帶 avx512bf16 的 x86 上跳過（那裡 llc 原生降 bf16，不走 helper），riscv64 構建則剝掉 +zvfbfmin，逼轉換走 launcher，順帶當作裸執行時路徑的探針。

驗證結果值得記：x86 host 上 #114 的復現核心修復後返回 [-5.0, -0.5, 2.5, 7.0]，修前全為零；host 示例套件 4028 透過、14 跳過，10 個失敗是 test_affine_grid_generator 與 test_avg_pool3d 的既有失敗（stash 掉修復後同樣失敗，且這兩個用例不用 bfloat16）；riscv64 三條 CI 腿（三個 Python 版本）整套透過——這是該修復第一次在真實 riscv64 上驗證。與 #120 的 FlagGems 分支合流後，41 個 bf16 的 xfail 釘全部轉正，461 個用例透過。

2.1 openRuyi 引入 openssl-3 相容包，帶十個 RISC-V 最佳化補丁（11-17）

日期：2026-11-17　來源：提交 9f1c8f64、openRuyi 打包倉

11-17 16:13，打包倉新增 SPECS/openssl-3，版本 3.6.5，11 個檔案、+5603。提交說明寫得很直白：openssl 4.x 有 ABI 變化，先按其他發行版的做法提供 openssl-3 相容包；它會與當前 openssl 3.x 衝突，安裝失敗屬預期。倉裡主 openssl.spec 現仍寫 3.6.5，也就是說這是一次提前鋪路的動作——相容包先就位，主包切 4.x 時下游才有退路。

帶來的十個補丁都是 RISC-V 向量與彙編最佳化：ChaCha20 的點彙編實現（686 行）、GHASH 多塊聚合（997 行）、GHASH 的 Zvbc 多塊聚合（615 行）、GHASH 的 Zvkg 多塊聚合（255 行）、SHA256 的指令重排（66 行）、AES-XTS 註釋修正（44 行）、SM4-CBC 實現（883 行）、AES-128-CBC 解密改進（456 行）、SM2 的 generic riscv64 彙編（1360 行），外加一筆 shared jitterentropy 補丁。加密庫在 RISC-V 上開始吃 Zvbc、Zvkg 這類向量加密擴充套件，與上週 Go 回填 Zvk AES 是同一條線。

三、向量擴充套件與運算元最佳化

3.1 bf16 libcall 家族還剩兩處沒有迴歸網（11-17 狀態）

日期：2026-11-17　來源：PR #121

#121 的說明自己劃了邊界：__truncdfbf2 與 bf16 libcall 家族其餘成員不改，因為當前 lowering 不產生它們；__extendbfsf2 雖然改了原型，卻沒有執行測試——兩個目標都把 bf16 到 f32 內聯成移位，重定位為零，只能反彙編 launcher 的 .so 看 movss %xmm0 序言來確認引數暫存器類。這意味著如果將來某個 lowering 退化成標量 libcall，這條路徑沒有用例接住。

對照 #117 就看得更清楚：#117 把 +zvfbfmin 放進預設特徵串，讓有向量擴充套件的核走向量轉換；#121 修的是沒有該擴充套件時退回 libcall 的那條路。兩條路的語義必須逐位一致，現在只有向量路徑有逐位測試，libcall 路徑靠這次補的四類邊界用例撐著。

3.2 IREE 3.14.0 給 RISC-V V 補 f16/bf16 inner_tiled MMA（11-16）

日期：2026-11-16　來源：IREE v3.14.0

11-16 18:15，IREE 釋出 3.14.0。CPU 後端的 RISC-V V 路徑新增 f16（vfmacc、vfwmacc、Zvfhmin）與 bf16（vfwmaccbf16）的 inner_tiled MMA；math.roundeven 在帶 D 擴充套件的 riscv64 上保持原生指令，不再走軟體序列；.vmfb 的可復現性也修了一處（LLVMCPU 不再寫未初始化的源位置行）。

IREE 走的是另一條 MLIR 下游路線，與 Buddy／RuyiAI 的 Linalg 到 llvm-cpu 路徑平行。它在同一周補 bf16 MMA，說明低精度矩陣乘已經是各家 RISC-V 編譯棧的共同待辦。

3.3 VecIntrinBench、IntrinTrans 與 FBGEMM 仍靜默（11-17 狀態）

日期：2026-11-17　來源：VecIntrinBench、IntrinTrans、FBGEMM（RuyiAI fork）

六、趨勢觀察

6.1 矩陣擴充套件開始有編譯器出口

XAME 這一筆把 138 條指令、兩套 profile、暫存器排程與呼叫約定一次做進 LLVM，並用 Buddy 的 AME 轉換與 gem5 實跑驗收。與上週的 RVV bf16 一樣，一條擴充套件是否可用，現在取決於三件事是否同時到位：編譯器能生成、模擬器能跑通、運算元庫有對應入口。只發指令定義、不補編譯器，在 RISC-V 上已經等於沒釋出。

6.2 這一週的主線是 bf16

#117 把 +zvfbfmin 放進預設特徵串，#121 修沒有該擴充套件時 libcall 的暫存器類，IREE 3.14.0 給 RISC-V V 補 bf16 MMA——三條動作指向同一件事：bf16 在 RISC-V 上不是一條路，而是「有向量擴充套件走向量、沒有就走 libcall」。兩條路必須逐位一致，任一環缺失都會表現為「結果為零」這種最難查的症狀。

6.3 發行版在做 ABI 遷移準備

openssl-3 相容包先落地、主包仍停在 3.6.5，衝突被明確寫成預期行為；同一天 abaci-bot 把 ABI 對比、SPDX 校驗與 CVE 禁運快取硬化。openRuyi 把「將來會斷的 ABI」當成工程項提前管，而不是等切換當天再補。這種做法比多合幾個包更能決定發行版能不能長期跟上游。

6.4 資訊面繼續空轉，程式碼面很忙

外部新聞零命中、論壇無新主題、官網三頁不動，但視窗內有兩個編譯器中改動合入、19 筆打包倉提交、20 筆治理機器人提交。日報的判斷價值繼續取決於讀提交內容，而不是數新聞條數；發行說明為空或缺失時，只能回到合併提交與測試記錄裡核對。
