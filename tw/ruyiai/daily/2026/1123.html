今日重點：buddy-mlir 三天連發 0.1.5、0.1.6、0.1.7，RISC-V 輪子隨版交付（11-20 至 11-22）

來源：BUDDY MLIR 0.1.5、0.1.6、0.1.7。PR #1074。

三天內 buddy-mlir 打了三個正式版。0.1.5 釋出於 11-20 23:40，0.1.6 釋出於 11-21 22:49，0.1.7 釋出於 11-22 01:12，間隔分別約 23 小時與 2 小時。

三個版本的標籤都指向具體提交。0.1.5 指向 20d3a102，即 11-19 合入的 ZTT v0.6 方言替換。0.1.6 指向 8cbc1a9b，即 #1074「Release LLVM with dump() support」。0.1.7 指向 a848378f，標題為「Shrink the LLVM tarball so it fits in one release asset」。

每個版本都帶 8 個資產。除 x86_64 的 wheel 與 tar.gz 外，還有 manylinux_2_39_riscv64 的 wheel 與 tar.gz、riscv64 的 buddy-cli 單檔案，以及 LLVM 24.0.0git 的兩套預編譯包。

體積上，0.1.7 的 riscv64 wheel 為 380,057,776 位元組，x86_64 wheel 為 365,782,329 位元組。riscv64 的 buddy-cli 為 436,952 位元組，x86_64 為 759,592 位元組。LLVM 側 x86_64 包 1.03 GB，riscv64 包 1.14 GB。

三個版本都沒有釋出說明，正文為空。可核對的資訊只有標籤、提交與資產清單。

今日重點：DeepSeek-R1-Distill-Qwen-1.5B 在 K3 A100 上的 FP16 最佳化合入，Prefill 43.42 token/s（11-23）

來源：PR #997。提交 3d5d674a。K3 配置 f16_k3.json。

#997 在 11-23 00:25 合入，建立於 10-25，評審歷時近一個月。改動 20 個檔案，含新增的 A100 合法化 pass、IME 方言擴充套件與模型配置。

PR 說明給出的核心手段有四條。第一，四個 FP32 累加器在整條 K 歸約上常駐暫存器，Prefill 走 8×32 分塊，Decode 每塊算 32 個輸出通道。第二，部分 Decode 投影權重打成 N32/K8 面板，其餘投影保留原 RVV 佈局。第三，Prefill 用原生 VLEN=1024 與 BLIS 寬度 64，並融合逐元素運算元、向量化 SiLU。第四，以上選擇集中到 models/deepseek_r1/specs/f16_k3.json，既有配置的預設流水線不變。

實測資料按 PR 說明記錄。Prefill 評估 128 個位置，Decode 從第 64 個位置起測 32 步，八執行緒，A100 核心 8 至 15，取四次樣本。表中單位為 token/s。

Prefill 相對 Buddy 主幹提升約 8.6 倍，相對 llama.cpp 高 55%。Decode 相對 llama.cpp 高 55%，相對 Buddy 主幹只高 3%。

Prefill 的數字包含會話與介面呼叫的開銷，PR 說明已註明。llama.cpp 一側用 FP16 GGUF 權重與 FP16 KV cache，雙方輸入 ID 一致。

同一套核心已被複用到其他模型。#1075 做 Whisper Base，#1076 做 PaddleOCR-VL-0.9B，#1001 做 Qwen3-0.6B。三筆都引用 #997 的 pass 與權重打包。

1.2 FlagGems 示例再開兩支：72 + 61 個運算元，堆疊到 279 個（11-21、11-22）

來源：PR #131。PR #132。

#131 在 11-21 18:53 開出，覆蓋 72 個運算元。#132 在 11-22 18:48 開出，覆蓋 61 個運算元。兩支都只改 python/examples/flaggems/。

#131 的四族是座標複製、內部複製與分配、形狀構造、型別轉換與填充。PR 說明列出三處上游偏差：padding 包裝按 aten 的 (w, h, d) 順序接收，再重排到核心的 (d, h, w)；replication 的反向按標量源位置掃，以貼合 aten 的累加順序；rank 大於 2 時 rot90 漏掉了末維項。

#132 的四族是 BLAS 包裝與稀疏 smm、gamma 特殊函式、量化運算元、低精度與稀疏矩陣乘。PR 說明寫明 fp64 點積只能到 fp32 累加，因此這類收縮改為標量 FMA 迴圈保精度；e5m2 fp8 沒有降級路徑，改為核心內上轉，e4m3 與 int8 走原生。

測試數繼續上漲。#131 記 7830 項透過、739 項新增；#132 記 8617 項透過、787 項新增。都在 x86_64 上跑，排除了三個既有崩潰檔案。

五支 PR 串成一條鏈：#126 的 63 個、#127 的 43 個、#130 的 40 個、#131 的 72 個、#132 的 61 個，合計 279 個運算元示例。按 PR 說明，前序未合時 diff 會把前序提交計入，#131 相對 main 是 34 個提交、548 個檔案，#132 是 38 個提交、670 個檔案。

三、向量擴充套件與運算元最佳化

3.1 VecIntrinBench、IntrinTrans 與 FBGEMM 繼續靜默（11-23 狀態）

來源：VecIntrinBench。IntrinTrans。FBGEMM。

三個倉視窗內零提交。最後提交時間分別是 02-13、06-25 與 07-13。

向量內在函式的基準與轉換工具已三個季度未動。當前能看到的向量效能資料，主要來自 triton-riscv 的運算元測試與 buddy 的模型實測。

這並不代表向量方向停擺。視窗內的向量工作寫在模型核心裡，見下一條。

3.2 向量工作轉入模型核心：VLEN 1024、SiLU 與 exp 近似（11-22）

來源：PR #997。PR #1076。PR #1075。

#997 把 Prefill 的 BLIS 列寬做成可配置，並可在函式入口校驗硬體 VLEN。A100 配置取 VLEN=1024，配合寬度 64。

同一筆裡 SiLU 改為融合並向量化，exp 走上游 MLIR 的多項式近似。PR 說明寫明多項式會改變舍入，與預設路徑分開驗證。

#1076 把 attention 的 bmm1、scale、softmax、bmm2 合成單個分塊核心，softmax 留在 L1，用向量 exp。同一筆給 -approximate-vector-exp 加了向量化 erf，讓 GELU 不再逐 lane 調標量函式。

#1075 走另一條路。編碼器的 P @ V 降為 4 行 M 展開的 FP32 累加 RVV 核心，matmul_transpose_b 與 conv_1d_ncw_fcw 降到 IME。

三筆的共同點是把向量寬度與硬體 VLEN 繫結。上一期 triton 側 #129 的調優用的是同一思路，兩側的引數口徑可以對照。

3.3 FlagGems 示例覆蓋到特殊函式與量化運算元（11-22）

來源：PR #127。PR #132。

特殊函式一支覆蓋貝塞爾家族、四類 Chebyshev 與移位版、兩種 Hermite、Laguerre、Legendre，另有 log_softmax 與 logsumexp。

工具鏈無法降級的 intrinsic 改走閉式。erfcx 用三段混合，log_ndtr 的尾部改算 −t² + log(erfcx(t)/2)。

量化與低精度一支覆蓋偽量化家族及其可學習變體、4 位動態量化線性、scaled mm、int8/int4 權重打包、混合精度線性、CSR 與半結構化乘積。

精度處理寫進了 PR 說明。fp64 點積在 Triton 側只能到 fp32 累加，這類收縮改為標量 FMA 迴圈；e5m2 fp8 無降級路徑，核心內上轉；e4m3 與 int8 走原生。

四、Buddy Compiler 動態

4.1 0.1.5 到 0.1.7 的標籤與提交對應關係（11-22）

來源：標籤列表。compare 0.1.6…0.1.7。

三個標籤各對應一筆提交。0.1.5 是 20d3a102，0.1.6 是 8cbc1a9b，0.1.7 是 a848378f。

compare 顯示 0.1.6 相對 0.1.5 領先 1 個提交，就是 #1074 的 dump() 修正。0.1.7 相對 0.1.6 是分叉狀態：領先 1 個、落後 1 個。

0.1.7 的父提交是 20d3a102，也就是 0.1.5 的基線。這意味著 0.1.7 不含 dump() 修正。

對下游有直接影響。triton 需要 mlir::Operation::dump() 才能連結，0.1.5 與 0.1.7 都缺這個符號，只有 0.1.6 帶。

目前 triton 側釘的仍是 nightly/v0.1.4.dev20261103（#115 未合）。若按 #115 升到 release/v0.1.7，連結問題會回來。

4.2 0.1.6 補 dump() 支援，0.1.7 壓縮 LLVM 資產（11-21）

來源：PR #1074。提交 a848378f。

#1074 的起因寫得很具體。夜間版從 main 構建，但 #1062 落在 llvm-multitarget 分支，所以 0.1.5 的 LLVM 包只有 dumpPretty()，沒有 dump()。

下游現象是連結失敗，報 undefined reference to mlir::Operation::dump() 與 mlir::Value::dump() const。修法是開 LLVM_ENABLE_DUMP，只恢復這兩個 helper，不開啟斷言。

PR 說明另提醒：LLVM 安裝按雜湊快取，之後的版本要跑一次 llvm_cache_mode=clean 才會帶上該開關。

0.1.7 處理的是資產上限。提交說明寫明 riscv64 的 LLVM 安裝包 gzip 後略超單資產 2 GiB 上限，v0.1.6 因此報過「size must be less than 2147483648」。

修法是截斷下游用不到的開發者工具，去掉 src、share 與 libexec，並 strip 其餘部分。x86_64 實測從 1617 MB 降到 817 MB。

說明裡還記了一次失敗嘗試。最初直接刪除檔案，結果 LLVMExports.cmake 在 configure 階段因匯入目標指向缺失檔案而中止，所以改成截斷。

兩個版本現各有 8 個資產。riscv64 的 LLVM 包在 0.1.7 上是 1,138,715,828 位元組，低於上限。

4.3 DeepSeek 最佳化合入，四個模型 PR 排隊（11-23）

來源：PR #997。PR #1075。PR #1076。PR #1001。

#997 已在今日重點展開。這裡只補它在 PR 佇列裡的位置：它是這輪模型最佳化的母本。

#1075 做 Whisper Base，11-22 17:10 開出。PR 說明給出端到端 2.031 秒，主幹是 1663.03 秒，提速 818.8 倍，RTF 從 345.39 降到 0.42。預處理 0.101 秒，編碼器 1.622 秒，解碼 0.272 秒。

#1075 還修了一個記憶體問題。STFT 迴圈裡 make_rfftp_plan(400) 每次呼叫都建計劃，洩漏約 1 GB，改為提到 3001 幀迴圈之外並釋放緩衝。

#1076 做 PaddleOCR-VL-0.9B，11-22 22:08 開出。端到端 30.82 秒，相對 FP16 RVV 基線 525.71 秒提速 21 倍。Prefill 25.04 秒，Decode 5.78 秒（18 個 token，3.11 token/s）。生成的 19 個 token 與 PyTorch FP16 完全一致。

#1001 做 Qwen3-0.6B，10-26 開出至今在審。它直接複用 #997 的 IME FP16 GEMM/GEMV 核心與 Decode 權重打包。

四筆合起來的訊號是：一套 A100 核心正在覆蓋 LLM、語音、OCR 三類負載。

4.4 方言與匯出側另有五筆在審（11-23 狀態）

6.2 K3 A100 上形成模型最佳化流水線

#997 合入後，同一套 IME 核心已出現在 Whisper、PaddleOCR-VL、Qwen3 三個模型的 PR 裡。

三筆的效能數字都按同一臺機器 K3-002、同一組核心 8 至 15、八執行緒、VLEN=1024 記錄。橫向可比。

收益的量級差別很大。DeepSeek 的 Prefill 是主幹 8.6 倍，Whisper 的端到端是 818.8 倍。後者的基數來自未做編碼器複用的 F32 單次前向，倍數被基線放大。

可複核的口徑是 token 序列與參考實現一致。#1076 記了 19 個 token 全等，並貼出 OCR 文字。
