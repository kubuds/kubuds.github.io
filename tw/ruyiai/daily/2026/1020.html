技術情報倉庫 10-19 期（10-19 06:16 推送）的 RISC-V 段記錄四組內容：其一是 linux-riscv 上的 PAGE_KERNEL_RO 定義提案，指出 RISC-V 缺該定義時會退回可寫的 PAGE_KERNEL，導致 HugeTLB vmemmap 等本應只讀的對映保留寫許可權，提案給出 QEMU virt 上的復現與修復前後頁表對照；其二是系統呼叫重啟路徑需檢查完整返回值，修正返回值截斷問題；其三是 SyterKit 在 C907 映象中把 mstatus 向量狀態置為 initial，使啟動狀態與編譯進映象的 RVV 程式碼一致，E907 則在開啟快取前先設定系統對映；其四是 SpacemiT K3 PCIe 補丁 v7 收到新審閱意見，質疑用 PHY bulk API 一次控制多埠全部 PHY 的做法，指出每埠有獨立 PHY 與 PERST#，資源建模需重新論證。

5.3 產業側：進迭時空 V100 伺服器級 RISC-V 處理器在峰會發布（10-19）

日期：2026-10-19　來源：Phoronix：SpacemiT V100

10-19，進迭時空（SpacemiT）在峰會期間釋出伺服器級 RISC-V 處理器 V100。按 Phoronix 報道，V100 採用 46 核混合架構——6 個香山昆明湖 V2R2 核加 40 個 SpacemiT X100 核，主頻 2.2 至 2.4GHz，12nm 工藝，120W TDP，支援八通道 DDR5-4800 與 52 通道 PCIe 5.0，雙路可達 92 核；廠方稱其為首款完整符合 RISC-V 伺服器規範的晶片，支援 UEFI、ACPI、SMBIOS。

對本主題的意義在於平臺形態而非晶片本身：伺服器規範把 UEFI/ACPI/SMBIOS 變成必需項，系統軟體棧的適配路徑與現有的開發板、嵌入式平臺並不相同。當前 ruyi 0.54.0 的規劃集中在 K1/K3 工具鏈適配與 ABI 相容檢測，支援矩陣以消費級與嵌入式板卡為主；伺服器平臺若要進入支援範圍，需要新的韌體、發行版與映象鏈路。當日未見 RuyiSDK 或 openRuyi 針對 V100 的任何公開動作。

六、趨勢觀察

6.1 發行版打包策略轉向按依賴打包：Rust crate 批次匯入與 Go 去 vendor 同步推進

openRuyi 單日 221 筆提交裡，約 200 個是新增包，其中絕大多數為 Rust crate；同日提交的 PR 又把 minio、picoclaw 從自帶 vendor 歸檔改為使用發行版打包的依賴。兩條線指向同一件事：發行版的打包單位從「上游原始碼樹」變成「可複用的依賴包」，這既能減少重複打包、也讓 CVE 修復可以按包下發（同期 CVE 批次正是按包拆分提交）。對 RISC-V 發行版而言，維護成本主要不在主包，而在依賴閉包的完整度，這批提交是補閉包的動作。

6.2 三條上游 fork 維護線分化：PyTorch 按日重放、LLVM 七日靜默、Triton 夜間構建恢復

PyTorch 的 riscv 分支保持每日重放（本視窗 10-19 09:14 一次，屬歷史重寫、無新補丁），上游 main 每日同步；LLVM 的 riscv 分支自 10-12 起七日無推送，兩筆 FPGA 後端 PR 停在 10-13；Triton 的夜間出包在停更七日後於 10-19 恢復。三個倉庫代表三種投入狀態：一條流水線在跑、一條在等評審、一條剛恢復出包。觀察點是 LLVM 分支是否隨新上游基線重啟，以及 Triton 夜間版能否回到逐日節奏。

6.3 伺服器級平臺進入視野：UEFI/ACPI/SMBIOS 規範要求改變系統軟體適配路徑

進迭 V100 把 RISC-V 伺服器規範落到具體產品，規範裡的 UEFI、ACPI、SMBIOS 成了硬要求。這與當前 RuyiAI/RuyiSDK 面向 K1/K3 等嵌入式與消費級平臺的適配路徑不同：後者以板卡映象、工具鏈與支援矩陣為主，前者需要韌體、引導與發行版安裝鏈路整體對齊。openRuyi 韌體線（ruyifirmware、edk2-ruyi）近兩日轉入靜默，若伺服器平臺成為下一階段目標，這條線的工作量與優先順序可能需要重估。
