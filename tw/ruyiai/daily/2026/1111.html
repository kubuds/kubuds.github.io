今日重點：ruyi 0.54.0 正式釋出，宿主 ABI 相容性檢查進入使用者命令（11-10）

日期：2026-11-10　來源：ruyi 0.54.0 釋出、0.53.0 至 0.54.0 變更比對、PR #507

0.54.0 在 11-10 21:15（北京時間）釋出，是正式版而非預發。上一版 0.53.0 是 09-24，間隔四十七天；中間只有 11-02 的 0.54.0-beta.20261102。正式版相對該預發只多了一筆版本號提交，功能面就是預發的全部內容；從 0.53.0 算起，這一版共七十一筆提交、七十四個檔案。

主體功能是 ELF ABI 相容性資訊的採集與匹配。一個預編譯二進位制能否在目標裝置上跑起來，取決於一批散落在 ELF 檔案頭裡的事實：需要哪些動態庫、向這些庫索取了哪些符號版本、以及架構相關的能力要求。此前軟體源裡沒有任何地方記錄它們，ruyi 現在把這些資訊掃出來、存下來、並在安裝前比對。

採集面按架構分：x86-64 記 ISA feature level，AArch64 記 BTI 與 PAC，RISC-V 記 ISA 串。RISC-V 這條最費工，因為它的擴充套件是按版本號拼串的，本期提交裡有解析帶版本的單字母擴充套件、按宿主浮點 ABI 過濾 ld.so.cache 條目、以及把棧對齊要求算進去。宿主側另外實現了 x86-64 與 AArch64 的探測，宿主庫按請求的 soname 解析，遇到無法解析的 soname 報”未確定”而不是判死。

使用者可見的變化落在三處命令：ruyi list 在備註裡顯示宿主相容性（非二進位制包隱藏該項），ruyi install 在裝不相容的包時告警，ruyi admin check-abi 供排障。資料面走倉庫側的 ABI sidecar，按 distfile 名解析；rescan-package-abi 與外掛產物新增 strip-components，用來處理歸檔裡有前導目錄的情況。sidecar 有大小上限，壞 sidecar 被當作”無 ABI 資訊”丟棄，不會讓整次安裝失敗。

另一類是取件鏈路的修復：#509 讓非 2xx 的 HTTP 響應如實報錯，並丟棄失敗的首次下載、給卡住的傳輸加上限。這類改動不顯眼，但對一個要從映象站拉幾百兆工具鏈的包管理器來說，比新增功能更影響體驗。

設計文件 docs/elf-abi-compat-design.md 隨版本入倉，釋出說明給出的安裝路徑仍是 PyPI 與服務所映象站，單檔案二進位制需重新命名為 ruyi 才能使用。

今日重點：triton-riscv 在 RISC-V 宿主上預設啟用 AMD GPU 後端（11-10）

日期：2026-11-10　來源：PR #110、README

PR #110 在 11-10 17:51（北京時間）合入，標題是”預設啟用 GPU 後端”。改動有三件事：用現有的 Buddy LLVM SDK 構建並打包 riscv64 的 AMD codegen 庫；修掉 riscv64 上 CPU 與 GPU 驅動二選一時的歧義，規則是優先選用可用的 GPU；以及改掉驅動層那處讓選擇變含糊的判斷（該檔案淨刪四行）。

驗證是在真機上做的：SG2044 配 RX 7900 XTX，torch 與 ROCm 來自 openRuyi 的軟體倉；另測了隱藏 GPU 裝置時能否自動回落到 CPU。這條口徑比”能編過”硬得多——它說明 RISC-V 主機確實把核心發到了 AMD 卡上跑，而不是在 CPU 上兜底。

README 同步加了一節 AMD GPU 用法：ROCm 在位時後端透過 torch.version.hip 自行啟用，寫法和上游教程一致；wheel 不帶 ROCm 執行時，torch 與 ROCm 要另裝；強制回 CPU 用 TRITON_DEFAULT_BACKEND=triton_shared。改動共六個檔案，集中在 README、backend/driver.py 與 scripts 下的 build、env、release、setup 四個指令碼。

有一個時間差值得記下：當天 10:22（北京時間）出的夜間版 nightly/2026-11-10-209274f 打在提交 209274f 上，早於這筆合入，因此這個包還不含 GPU 後端。要拿到它得等下一版夜間版。

對整條棧來說，這是路線層面的變化：triton-riscv 此前只回答”如何在 RISC-V CPU 的向量單元上跑 Triton”，現在還要回答”如何從 RISC-V 主機驅動異構加速器”。在一個主流 AI 加速卡都不帶 RISC-V 宿主驅動的時點，先支援 AMD 卡是最現實的一步——ROCm 的 RISC-V 側工作已經在 openRuyi 倉裡維護。

1.1 triton-riscv：外掛改名 PR 在審，環境變數的取值將隨之一變（11-10）

日期：2026-11-10　來源：PR #109、提交列表

#109 要解決的問題是名不副實：name.conf 決定安裝出的包名與入口點，於是外掛現在叫 triton.backends.triton_shared，可它報告的目標是 cpu，選項字首又已經是 triton_riscv。改法是統一叫 riscv，理由是對齊上游的命名習慣——外掛按目標家族命名（nvidia、amd），裝置名（cuda、hip）留給 target。

連帶變化是環境變數：TRITON_DEFAULT_BACKEND 的取值從 triton_shared 變成 riscv，也就是今日重點那條裡”強制回 CPU”的寫法會在合入後失效。工具名 triton-shared-opt 與 C++ 側不動。第二筆提交給改名觸及的六十個檔案補 ruff，這批檔案此前從未被 lint，帶十九個既有違規。

PR 狀態是開放，11-10 18:56（北京時間）還有更新，尚未合入。同一天更新過的開放 PR 還有 #103（補教程）與 #104（BOSCAME FPGA 的 SPM 示例與 AOT 契約前端），三條都屬於”能上手、能復現”的基礎工作。

四、Buddy Compiler 動態

4.1 buddy-mlir：YOLOv8 檢測與姿態跑上 K3 矩陣引擎，權重與 TCM 複製補兩處修正（11-10）

日期：2026-11-10　來源：PR #1042

#1042 把 Ultralytics YOLOv8 接進 buddy-cli 的 rax 格式：yolov8n 檢測（八十類 COCO）與 yolov8n-pose（十七個關鍵點），輸入都是 320x320。f32 模型走 VIR 降低，規格里寫 ime: true 則改跑 SpacemiT K3 的矩陣引擎。

評審階段補的兩處修正比模型本身更有資訊量。一是權重校驗：清單裡帶 params_size，執行器要求權重檔案與它一致，此前權重檔案偏短會讓模型讀過緩衝區；同時要求執行器只接受 rax 包，因為單獨給庫與權重時，姿態模型會被按檢測模型的引數跑起來。二是 TCM 複製：IME 權重的 TCM 副本按權重地址快取，新權重讀進已釋放的緩衝區時會命中舊副本，現在每次權重灌載後呼叫核心側的失效函式。

規格里同時保留 params_size 與 ime_params_size，這樣 ime: false 時仍能構建 f32 版本。這條設計與前一天的 VIR 端到端走通是同一條線：同一張圖，兩條後端路徑，一份可對比的基線。

4.2 buddy-mlir：vir.set_vl 區域收緊為一個塊，多塊區域不再靜默丟運算元（11-10）

日期：2026-11-10　來源：PR #1045

vir.set_vl 的區域型別原是 AnyRegion，原始碼裡留著”區域限制待定”的註釋。校驗器與 -lower-vir-to-vector 的每一處 lowering 都只取 region.front()，於是多塊區域能透過校驗，其餘塊裡的運算元被靜默丟棄。復現很清楚：一個 set_vl 裡的 load 與 store 落在第二個塊（cf.br ^bb1 之後），降低結果是兩個空的 affine.for；空區域則能過校驗，隨後在 pass 裡以”找不到錨型別”失敗。

改法是把型別改成 SizedRegion<1>，註釋刪掉，校驗器不再自己防空區域（ODS 先驗塊數），只保留”塊無引數”這一條。測試裡新增兩塊與零塊兩種非法輸入。這類改動不產出新功能，但它把一類”編得過、算得錯”的路徑變成了編譯期錯誤，價值在可診斷性上。

4.3 buddy-mlir：動態向量型別與縮放因子的列印、解析與校驗補齊（11-10）

日期：2026-11-10　來源：PR #1046

縮放因子此前列印成屬性形式 #vir.sf<m2>，而型別語法與示例給的是 m2；解析側留著”待補錯誤提示”的註釋，行為有多處不一致：#vir.sf<x2> 與 mq 會崩潰（解析返回空屬性而沒有報錯，型別解析器把它當成有效值），m3、m0、f128 被接受，!vir.vec<0x?xf32> 被接受，而 !vir.vec<?xvector<4xf32>> 被拒且位置報成 unknown。

改動分三塊：列印改用 sf.str()，#vir.sf<m2> 仍可讀入；屬性側加 genVerifyDecl，要求比例是 m 或 f、取值 2 至 64 且為二的冪（與 Python 繫結已有的檢查一致）；型別側要求動態維之前的各維靜態且為正。第二個提交把錯誤定位修到真實位置。對一門還在成型的中間方言，解析器的嚴格程度直接決定前端能否可靠地報錯。

4.4 buddy-mlir：reassoc 歸約先按 lane 合塊，修 VLEN 128 宿主上的位不一致（11-10）

日期：2026-11-10　來源：PR #1047

在 VLEN 128 的 RISC-V 宿主（SG2044 的 C920 核）上，test_k3_w4_kernels.py 的 qk_norm 出現位不一致。原因是 K3 解碼注意力的 q、k 歸一化把一個頭的六十四個 f32 平方和放進沒有 shuffle 的 set_vl 區域，降低按宿主定尺（#1037），VLEN 128 下變成兩塊 vector<32xf32>（LMUL 8）；而 vir.reduce 把每塊依次併入前一塊的結果，與向量核心裡的單次 vector<64xf32> 歸約順序不同——LLVM 會把寬向量拆半、逐 lane 相加再歸約一次。CI 的 riscv64 跑在 VLEN 256 上，那裡只有一塊，所以一直透過。

改法是讓跨多塊的 reassoc 歸約按 LLVM 的方式合併：n 塊先補寬到 2 的冪 h，第 p 塊與第 p+h/2 塊相加，直到只剩一塊再歸約一次。這已經是同一主題的第四個修正（前有載入期 VLEN 校驗、宿主定尺、FMA 尾部舍入），指向的驗收標準一致：換實現可以，換數值不行。

4.5 buddy-mlir：五十個 Python 檔案改名，A100 llc 選項收斂到統一入口（11-10）

日期：2026-11-10　來源：PR #1043、PR #1044

#1043 把五十個帶連字元的 Python 檔名改成下劃線：同目錄下已有下劃線命名的檔案，帶連字元的無法 import，函式也就無法被測試或複用。改動覆蓋 models、examples、.agents/skills 與 tests 四處，同步修了 CMake、shell 指令碼、README 與文件裡的引用。MLIR 上游二百四十一個 Python 檔案裡有二百三十七個是下劃線命名，這次是對齊上游規範。

#1044 修的是 YOLOv8 的 IME 路徑：lower_to_obj.sh 自己拼了一套 A100 的 llc 選項（含 +zvl1024b 與 -riscv-v-vector-bits-max=1024），卻只用後者檢查構建的 VLEN。自 #1032 起 VLEN 統一由 BUDDY_RISCV_VLEN 指定，其他模型都從 a100_llc_args 取，且校驗的是 llc 實際讀到的精確 1024。舊指令碼會被 +zvl256b 或無 VLEN 的構建騙過：VIR 按任意 VLEN 降低，object 卻按 1024 編。現在指令碼直接追加統一入口給出的選項，不滿足 VLEN 1024 就停下，並新增一個用樁工具跑的測試。

六、趨勢觀察

6.1 0.54 的釋出間隔翻倍，代價在跨三種架構的 ABI 採集

0.52 到 0.53 隔了二十二天，0.53 到 0.54 隔了四十七天。翻倍的這段時間裡，提交幾乎都壓在一條線上：把 ELF ABI 相容性從”沒有記錄”做到”能採、能存、能比對、能在安裝前告警”。這條路要同時處理 x86-64 的 ISA level、AArch64 的 BTI 與 PAC、RISC-V 的版本化擴充套件串，是三種架構的知識而不是三次相似的編碼。

值得注意的是它先落在一個包管理器裡，而不是某個發行版的質量流程裡。包管理器是唯一能在”使用者點安裝”那一刻做判斷的位置，把相容性判斷放在這裡，等於把發行版級的驗證成本前移到一次本地比較。

6.2 “能不能裝”第一次變成可計算的事實

RISC-V 的碎片化不在指令集本身，而在基線：同一份 riscv64 二進位制，可能在 RVA20 的板子上跑不起來，也可能在一個沒有向量單元的核上直接非法指令。此前這類問題靠文件、靠論壇回帖、靠試。0.54 把每個包的動態庫需求、符號版本與架構能力要求寫成 sidecar，宿主側探出對應事實再比對，於是”這個包裝不上”從一句經驗變成一條可復現的結論。

副作用是資料維護：sidecar 要隨包更新，strip-components 一類的歸檔差異要單獨處理，壞 sidecar 要有明確的降級策略。0.54 把這些邊角都寫進了程式碼，說明設計時已經算過維護成本。

6.3 RISC-V 宿主加 AMD 卡進入主線

triton-riscv 從”在 RISC-V 向量單元上跑 Triton”擴充套件到”從 RISC-V 主機驅動 AMD GPU”，預設路徑直接選 GPU。這條組合此前只在廠商演示裡出現，現在進了預設分支，並且有真機驗證（SG2044 配 RX 7900 XTX）。

現實意義在於：主流 AI 加速卡的宿主驅動生態幾乎都為 x86 與 Arm 準備，RISC-V 機器長期只能靠 CPU 跑推理。讓 RISC-V 主機把核心發到一張消費級 AMD 卡上，是繞開這個生態缺口最省力的一條路——ROCm 在 RISC-V 上已經有維護，缺的只是編譯器後端這一環。

6.4 VIR 的修補物件從”算錯”轉向”靜默出錯”

本視窗 buddy-mlir 的六筆裡，至少三筆針對的是”不報錯但結果不對”：多塊 set_vl 區域靜默丟運算元、縮放因子解析崩潰或放過非法值、跨塊歸約順序改了數值。前兩類以前會讓編譯器安靜地產出一個錯的結果，現在變成編譯期錯誤；第三類靠逐位元組比對才抓得住。

這類問題的共同點是修復成本低、發現成本高。它們能在這個階段被成批清掉，說明 VIR 已經有了一套能跑真機、能比基線的測試面——沒有 K3 與 SG2044 上的對照，4.4 那種 VLEN 128 與 256 的差異根本不會顯形。
