今日重點：三件套進發行版打包、triton-riscv 換錨、VIR 補上 Python 繫結（10-27）

日期：2026-10-27　來源：openRuyi PR #1350、triton-riscv PR #90、buddy-mlir PR #1009

本期三條主線在同一個視窗內各走了一步，而且第一次互相接上。

第一條是分發層。openRuyi 的 PR #1350「Add Ruyiai packages」把 buddy-mlir、python-triton-ruyiai、python-tilelang-ruyiai 三個 spec 一次提交（3 筆提交、9 個檔案、+666/−0），9-21 開出後經維護者 Z572 在 9-24 提出修改要求，討論停在 9-28；10-27 17:55 至 18:54（北京時間）作者 nekorouter 連續回覆三條複核意見，逐條解釋 git 構建依賴、buddy-mlir 自帶 LLVM 是否外接、以及改用 GCC 構建的代價。同日另一條 PR #1352 把 PyTorch 的 RISC-V 適配單獨成包。兩筆都仍未合入，但已經從「擱置」回到「逐條收斂」。

第二條是工具層。triton-riscv 的依賴錨點在 19:43 由 renovate 機器人提交併合入（#90，+2/−2），buddy-mlir 從 nightly/v0.1.1.dev20261017 直接跳到 nightly/v0.1.3.dev20261027，跨過整個 0.1.2 正式版與兩個夜間構建。上一期日報把「錨點是否更新」列為觀察項，本期給出了答案：更新了，而且一次跨兩級。這意味著 10-26 夜裡那七筆 VIR 可伸縮向量改動，自本期起進入下游構建鏈路。

第三條是表達層。buddy-mlir 的 #1009「[midend][VIR] Python bindings」在 22:42 合入（12 個檔案、+614/−1），把 VIR 這個此前只能在 buddy-opt 裡跑、且要用 ir.Operation.create("vir....") 手工拼運算元、用 ir.Type.parse("!vir.vec<...>") 手工拼型別的方言，正式做成了 buddy_mlir.dialects.vir 模組，走 ODS 加 C API 加 nanobind 擴充套件的常規路徑。

三條放在一起看：VIR 能表達可伸縮向量（前一期），現在能被 Python 驅動（本期），再往下有發行版打包通道（本期在審）。這條棧缺的從來不是單點能力，而是「表達—工具—分發」三段的接通，本期是少見的同日各有進展。

二、RuyiSDK 工具鏈與發行版

2.1 openRuyi PR #1350：RuyiAI 三件套進發行版，作者當日逐條回應複核意見（10-27）

日期：2026-10-27　來源：PR #1350、PR #1350 複核評論、PR #1350 提交

PR #1350 是本期分發層最重要的一筆：一個 PR 同時加三個包——buddy-mlir（基於 LLVM 的 MLIR 編譯框架）、python-triton-ruyiai（RISC-V 版 Triton）、python-tilelang-ruyiai（RISC-V 版 TileLang 後端）。3 筆提交全部落在 9-21 的 09:46 至 09:48（兩分鐘內），共 9 個檔案、+666/−0。

時間線值得記下來：9-21 開 PR，9-24 維護者 Z572 提三處修改要求（為什麼需要 git、buddy-mlir 是否應提供 macro 檔案供 Triton 定位其 LLVM、buddy-mlir 是否應先用 GCC 構建固定版本 clang 再用新 clang 構建自身），9-28 作者回復並修掉兩處；隨後停擺近一個月，10-27 17:55、17:57、18:54 連續三條回覆把剩下的爭議逐條說清。

三條回覆的技術內容比進度本身更有資訊量。其一，triton 上游的 setup.py 會強制檢查 git 能否執行，所以要麼加 git 構建依賴，要麼改 setup.py（需新增補丁檔案，且 triton 更新時容易失配）——作者選擇前者。其二，buddy-mlir 自帶的 LLVM 只在該包內部使用，且這些包始終鎖定到具體 LLVM 提交，因此傾向於把它留在構建流程內部，而不外接成獨立 macro 包。其三，改用 GCC 構建固定版 LLVM/clang 在技術上可行，但構建時間至少增加 1.5 倍。

這三條指向同一個取捨：RuyiAI 這幾個包的構建鏈耦合度高（Triton 依賴 buddy-mlir 的 LLVM、TileLang 依賴 buddy-mlir 工具鏈），一旦按發行版的「依賴外接、複用系統包」慣例拆開，構建成本與失配風險都會上升。作者選擇保住耦合、承擔體積與構建時間，是打包路線上的一次明確表態。

2.2 openRuyi PR #1352：PyTorch RISC-V 適配單獨成包，安裝後自帶冒煙測試（10-27 狀態）

日期：2026-10-27（狀態）　來源：PR #1352、python-torch-ruyiai spec 檔案

PR #1352 把 RuyiAI-Stack/pytorch 單獨打成 python-torch-ruyiai（8 個檔案、+783/−0），與 #1350 同日更新，狀態仍為開放，唯一一筆提交停在 9-21 11:22。

補丁集讀起來是一條完整的發行版適配清單：2001 強制 OpenBLAS 走 cblas 複數點積、2003 改用系統 fmt、2005 改用系統 cmake 依賴、2006 跳過無用的子模組預構建檢查、2011 把 RVV kernel 按目標向量能力門控、2012 內嵌 scikit-build-core。另有一個 pytorch-smoke-test.py，說明這個包在安裝後要跑一次冒煙測試才算透過——對發行版而言，這比單純「能裝上」更前進一步。

2011 那條尤其值得注意：把 RVV kernel 的啟用條件從「編譯時假定支援」改成「按目標向量能力門控」，正是社群裡反覆出現的問題——RVA20 等不含向量擴充套件的目標上，打包時若不門控，會生成無法執行的程式碼。這類修補通常要等使用者在實際板子上撞到才補，現在提前進了打包補丁。

與 #1350 一樣，這個包也宣告瞭 AI 輔助（Assisted-by: Deepseek V4.1 Flash），並按 openRuyi 的 AI 貢獻政策做了勾選與署名。

2.4 openRuyi：三筆 revert 收回「隨包分發 LLVM IR」路線（10-27）

日期：2026-10-27　來源：PR #1509 Revert llvm ir、openRuyi 提交列表

四、Buddy Compiler 動態

4.1 VIR 補上 Python 繫結：從 buddy-opt 專用變成可程式設計方言（10-27）

日期：2026-10-27　來源：PR #1009、buddy-mlir 提交列表

22:42 合入的 #1009 是本視窗 Buddy Compiler 一側的核心動作：12 個檔案、+614/−1，新增 buddy_mlir.dialects.vir 模組。提交說明把痛點寫得直白——VIR 此前沒有任何 Python 繫結，所以 VIR 的 decode attention 只能用 ir.Operation.create("vir....") 拼運算元、用 ir.Type.parse("!vir.vec<...>") 拼型別，整套 VIR 降級也只能在 buddy-opt 這一個可執行檔案裡跑。

實現方式選了「跟著現有方言走」：ODS 定義運算元（VIRBinding.td）加 C API 加 nanobind 擴充套件，與同倉庫裡 quant 等自帶型別的上游方言同構；按 PR 描述分三塊——Ops、Types、以及把 VIR 降級掛進 Python 的 pass 註冊。

這一步的意義不在工具本身，而在可組合性：一旦 VIR 能被 Python 直接構造與降級，運算元描述、形狀推導、測試用例都可以寫在 Python 側，前端（Triton、TileLang）與 VIR 的對接不必再依賴 C++ 側加鉤子。對一條此前只能在單一可執行檔案裡驗證的中間表示來說，這是從「編譯器內部件」轉向「可供外部呼叫的方言」。

需注意 #1009 合入後緊接出現 #1011「Cast the scalable VIR piece count to int64_t」（開放），說明可伸縮向量路徑上的整型寬度問題這兩天才被觸及，Python 繫結只是開啟了入口，穩定性仍在磨合。

4.2 在審五筆：piece count 轉 int64、Whisper 預處理複用、buddy-server 原始碼整理（10-27）

日期：2026-10-27（狀態）　來源：PR #1011、PR #1013、PR #1012、PR #1010

視窗內有更新的開放 PR 共五筆，方向分三組。

VIR 與可伸縮向量：#1011 把 VIR 的 piece count 從預設寬度顯式轉成 int64_t。piece count 指一個可伸縮向量被切成幾段，按 32 位參與後續乘加在大形狀下有溢位風險，這條修法與上一期的 #1008（索引向量寬度斷言）屬同一類收尾。

六、趨勢觀察

6.1 表達層、工具層、分發層在同一天各補一塊

把本期的三件事放在一條時間軸上：10-26 夜裡 VIR 補齊可伸縮向量表達，10-27 夜裡補上 Python 繫結，10-27 全天在推發行版打包。三段本來是依次遞進的——先能表達，再能被呼叫，最後能被分發——過去幾期一直是「表達層快、工具層與分發層滯後」，本期第一次出現同日三線並進。

但要判斷這條棧是否真在閉環，還有兩個已知缺口。其一，triton-riscv 換錨是自動化的，適配驗證尚未跟上，0.1.1 到 0.1.3 之間的介面變化會不會在下游暴露，下期才知道。其二，pytorch 的 riscv 分支連續六日零提交，而分發側已經在給它打包（#1352）——包跟著的是一個不動的分支，等包合入時是否已經落後上游基線，是需要盯的風險。

6.2 發版前清掃之外，發行版開始做減法

本期 openRuyi 的兩組動作性質不同：一組是加法（45 筆提交、13 個新增包、12 個安全更新、Samba 全家聯動升級），另一組是減法（三筆 revert 收回 LLVM IR 隨包分發）。過去幾期看到的都是「發版前清掃」——補依賴、清 CVE、切版本；本期第一次看到明確的功能性回收。

這說明 openRuyi 的維護重心正在從「覆蓋更多包」轉向「保證已有包的質量邊界」：IR 分發這類實驗會帶來包體積、ABI 與基礎設施的連鎖成本，在發版壓力下被優先砍掉。對 RuyiAI 棧而言這是雙面訊號——打包通道更規範了（#1350、#1352 都在按發行版慣例逐條收斂），但對「帶實驗性質的構建方式」（如內嵌 LLVM、自帶 vendor）容忍度也會同步下降。作者在 #1350 裡堅持把 buddy-mlir 的 LLVM 留在包內，恰恰是逆著這個方向的一次交涉，結果值得觀察。
