今日重點：ruyi 0.54.0-beta.20261102 出包，39 天斷檔後第一跳；ABI 相容性從掃包走到判主機，索引側只有三個包有旁註（11-02）

日期：2026-11-02　來源：0.54.0-beta.20261102、PR #507 主機 ABI 相容性探測、PR #496 ELF ABI 掃描器、packages-index 提交

11-02 18:37（北京時間），ruyi 釋出 0.54.0-beta.20261102。標籤提交落在 15:16，PyPI 同步出現 0.54.0b20261102；正式版通道仍是 09-24 的 0.53.0。這是 0.53.0 之後 39 天裡的第一個新標籤——上一個預發版 0.54.0-alpha.20260918 比 0.53.0 還早六天，換言之整個十月沒有出過任何 alpha 或 beta。上一期日報記的「十月末口徑落空」，在這裡有了下文：不是取消，而是拖到十一月第一個工作日才切 beta。

釋出說明列了十三筆 PR，但比較基準寫的是 0.52.0-alpha.20260714，於是 08-24 以來、早已進入 0.53.0 的九筆又原樣列了一遍。真按 0.53.0 對差，淨新增只有四筆：#503 測試超時按包數計算、#508 廠商命名文件、#507 主機 ABI 相容性探測、#509 取包錯誤上報。釋出頁讀者看到的「十三筆變更」與實際增量之間差了兩個半月，這是本期需要先說明的一點。

這個版本的實際內容集中在 #507：新增 ruyi admin check-abi 命令，對給定包做主機 ABI 探測與相容性判定；ruyi list 會顯示主機相容性備註，ruyi install 在不相容時給出告警。判定是三態的（相容、不相容、未判定），並區分寬鬆與嚴格兩套謂詞；RISC-V 側還處理了 ld.so.cache 的浮點 ABI 過濾、帶版本號的單字母擴充套件解析、棧對齊要求，以及弱符號版本缺失不算失敗這類邊界。補丁規模 +5760/−834、64 個檔案，是這一版裡最大的一筆。

需要分清的是層次：ABI 掃描器 #496 早在 09-16 就已合入並隨 0.53.0 釋出——它能掃目錄與 tar/zip/deb 歸檔，產出確定性的 .abi.toml 旁註，並提供 rescan-package-abi。0.54.0-beta 新增的是消費側：拿旁註去比對當前主機，回答「這個包在這臺機器上能不能跑」。工具鏈的這一半本期到位，資料的那一半才剛剛開始：packages-index 在 13:09 至 13:26 連提三筆，為 wlink、qemu-system-riscv-upstream、gnu-ruyisdk 三個包補上 ABI 旁註，共十一份檔案，其中 qemu 只有 amd64 兩份、沒有 riscv64。

對照索引裡 327 個包版本描述檔案，三個包意味著絕大多數包在 check-abi 下只能返回「未判定」。這不影響命令本身可用，但決定了它現在更像一個給打包者與早期採用者的除錯工具，而不是普通使用者裝包時的普遍保障。旁註的覆蓋面要追上來，得靠構建管線逐包重掃，這會是 0.54.0 正式版之前值得盯的一條線。

2.2 主機 ABI 相容性落地：check-abi、三態判定與安裝告警（11-02）

日期：2026-11-02　來源：PR #507、PR #496 ELF ABI 掃描器、PR #509 取包錯誤上報

PR #507 在 13:27 合入（+5760/−834、64 個檔案），把 ABI 能力從「描述包」推進到「描述主機並比對」。具體是四件事：

一是主機探測。新增 HostABIReport 與 HostABIProber，按架構讀取主機能力：x86-64 的 ISA level、AArch64 的 BTI/PAC、RISC-V 的 ISA 擴充套件集合與浮點 ABI；實現上走已安裝系統的庫路徑與 ld.so.cache，不做程序內動態載入。

二是判定。給出相容、不相容、未判定三態，寬鬆與嚴格兩套謂詞分別用於「提示」與「阻斷」場景；ruyi admin check-abi 供打包者除錯，ruyi list 把結論並進備註，ruyi install 在不相容時告警。

三是 RISC-V 側的細節修正：按主機浮點 ABI 過濾 ld.so.cache 條目、解析帶版本號的單字母擴充套件、按棧對齊要求判定、不把弱符號版本缺失當成失敗、拒絕 ELF class 不符的庫。

四是旁註治理：限制旁註大小、快取前丟棄無效旁註、重建產物前先失效舊旁註、支援從歸檔路徑剝掉前導目錄。

同一版本的 #509 修的是取包失敗的上報：非 2xx 響應不再被當成「下載成功」留下錯誤頁，保留可續傳的部分下載，並把 HTTP 狀態、重定向、連線失敗、傳輸停滯分別給出提示。這條對實際使用者比 ABI 檢查更直接——此前服務端返回錯誤頁會被誤判為已下載。

2.3 packages-index 補 ABI 旁註：三個包、十一份檔案，覆蓋面仍是個位數（11-02）

日期：2026-11-02　來源：packages-index 提交、gnu-ruyisdk riscv64 旁註、wlink 旁註、qemu 旁註

三筆提交集中在 #507 合入（13:27）前的十八分鐘內：13:09 給 toolchain/gnu-ruyisdk 加 0.20260921.0（含三份旁註），13:18 給 board-util/wlink 加兩份版本共六份旁註，13:26 給 emulator/qemu-system-riscv-upstream 加兩份 amd64 旁註。

以 gnu-ruyisdk 的 riscv64 旁註為例，可以看到掃描器記錄到什麼粒度：整個歸檔 2178 個檔案，識別出 43 個 ELF，排除 5478 個（含非 ELF 與排除規則命中）；e_machines=[243]，依賴五個 soname；版本需求上限 GLIBC 2.38、GLIBCXX 3.4.21、CXXABI 1.3.9；ISA 屬性記錄到帶版本號的粒度（rv64i2p1、m2p0、a2p1、f2p2、d2p2、c2p0，外加 zicsr、zifencei、zmmul），棧對齊 16。這足以支撐「主機能不能跑這份工具鏈」的判定。

但覆蓋面是硬約束：索引內共 327 個包版本描述檔案，有旁註的只有 3 個包、11 份檔案；wlink 與 gnu-ruyisdk 有 riscv64 旁註，qemu-system-riscv-upstream 只有 amd64 兩份。也就是說，一個 RISC-V 使用者現在去查絕大多數包，得到的都會是「未判定」。

六、趨勢觀察

6.1 斷檔以 beta 收尾，0.54.0 的旗艦項是「這臺機器能不能跑」

0.54.0 從 09-18 的 alpha 走到 11-02 的 beta，中間隔了 45 天；0.53.0 正式版到 beta 隔了 39 天。這段時間裡 ruyi 主分支並非沒有程式碼——ABI 系列提交在 10-30 與 11-02 分兩批落地——但釋出通道直到十一月的第一個工作日才重新開動。

重新開動時選的內容很明確：主機 ABI 相容性。這不是一個「新功能」式的賣點，而是把「裝了能不能跑」從經驗判斷變成可查詢項。對一個面向多廠商板卡與工具鏈的包管理器來說，這個方向的優先順序高於再加幾個包。

6.2 釋出說明的基準錯位，把兩個半月的舊賬又列了一遍

十三筆對四筆，是本期最容易誤讀的地方。釋出說明的比較基準停在 0.52.0-alpha.20260714，而不是 0.53.0；於是 08-24 的「RuyiSDK Certified」廠商標記、09-16 的 ABI 掃描器、09-23 的跨倉安裝狀態修復，全部又出現在 0.54.0-beta 的變更清單裡。

對下游的含義是：不能拿這份清單判斷「0.53.0 到 0.54.0 變了什麼」，得自己跑比較介面。專案在釋出流程裡補一步「基準標籤取上一個正式版」並不難，但對讀者的信任成本影響不小。

6.3 資料面落後於工具面，ABI 檢查多數時候只能回「未判定」

工具已經把三態判定、安裝告警、check-abi 除錯命令都做齊了，資料側卻只有三個包、十一份旁註，佔 327 個包版本描述檔案的不到百分之一；qemu-system-riscv-upstream 甚至只有 amd64 旁註。

這意味著現階段使用者真正能感受到的，是「某些包會顯示相容性」而不是「裝包前都能確認」。要把這條鏈路補成普遍能力，需要構建管線逐包重掃並回填——這是一項按包計的工作量，不會隨版本釋出自動完成。下一期可以看 packages-index 的旁註數量是否繼續增長，作為這條線是否真正啟動的判據。

6.4 openRuyi 的清賬與缺版並存，卡點在釋出不在開發

11-02 一天七筆合入，其中五筆是八月至十月初的舊 PR；同一天還有四筆直接提交。開發側並不缺動作，但 2026.10 的月度版本仍未釋出，新聞頁只能靠兩篇十月專題撐住內容。

這與 ruyi 側的情形並讀，指向同一個判斷：RuyiSDK 生態的兩條分發流水線（包管理器與發行版）在十月都出現了「程式碼在走、發版不走」的狀態。0.54.0-beta 已經把包管理器這條線重新拉起來；發行版這條線要等 2026.10 或直接跳到 2026.11，屆時才能判斷是流程延遲還是節奏調整。
