今日重點：triton-riscv 一日三筆合入，全部源自 FlagGems 運算元遷移暴露的降級缺陷（10-29）

日期：2026-10-29　來源：PR #58、PR #83、PR #82、提交列表

15:38 到 16:58 的 80 分鐘內，triton-riscv 主分支連續合入三筆，作者都是 maochuanjun，改的都是同一層——Triton 到結構化/非結構化 IR 的降級路徑。這在時間上並不尋常：該倉上一筆非依賴更新的程式碼提交是 10-09 的 #86，中間二十天只有 renovate 的夜間版錨點，而這三筆本身分別掛了 82 天、43 天、44 天才合入。

三筆各自對準一個具體缺陷。#83（16:38，4 個檔案、+160/−16）修帶非均勻張量填充值的掩碼載入，即 tl.load(ptr, mask=mask, other=cur) 這種寫法。原實現只認標量或 splat 的填充值，遇到真張量就卡在標量提取上，降級後的 IR 裡留著不支援的指標操作；改法是結構化載入與非結構化 gather 兩條路徑都支援張量填充，用 arith.select(mask, loaded, other) 恢復未命中通道，同時允許標量提取失敗而不報錯，把處理權交回撥用方。#58（16:58，2 個檔案、+125/−0）修迴圈攜帶的 gather 偏移丟失：scf.for 裡被攜帶的張量一旦退出結構化形態，輔助狀態只剩中性佔位符，用它重建迴圈結果會把 gather/scatter 塌成連續的 tts.make_tptr，迴圈裡累積的偏移全丟；改法是先校驗被分析的運算元確實是 scf.for 的結果，是則直接保留原始迴圈結果作偏移，並新增一條 loop_result_gather.mlir 迴歸。#82（15:38，1 個檔案、+23/−3）修雜湊測試的不確定性：原測試用隨機索引、允許重複目標位，非歸約雜湊下哪個源值勝出都合法，卻拿單一 PyTorch CPU 結果做精確比對；改法把 1D、2D 與原地比對改用唯一目標索引，另加六個重複索引用例（512、1023、1024 三檔長度，原地與非原地各一組），只校驗勝出值來自正確目標的源集合、未命中的目標保持原值。

三筆的動機都寫在 PR 描述裡，且都指向同一處：FlagGems 運算元遷移。#83 服務於 unique_dim 的實現，#58 服務於 broadcast_to（該核心此前為繞開這個誤編譯，把 range(MAX_DIMS) 換成了 tl.static_range），#82 是遷移過程中雜湊運算元比對失敗倒逼出來的測試修正。也就是說，這三筆不是迴歸測試發現的缺陷，而是「把一批 PyTorch 運算元搬到 triton-riscv 上跑」這件事逼出來的缺陷。

驗證強度值得記一筆。#83 明確寫在與 RuyiAI 相關的 riscv64 機器上驗證：新迴歸的三條 RUN/FileCheck 全過，全量 lit 291 透過、9 個預期失敗、0 個意外失敗，張量填充的執行時檢查 18 項透過（覆蓋結構化與 gather 兩條路徑、float32/float64/int64、空掩碼/部分掩碼/全掩碼、負零、NaN 與非法未命中 gather 偏移），與更新後的 unique_dim 整合 23 項透過。#58 只跑了針對性的 TritonToStructured 迴歸，#82 只跑該測試檔案（21 透過）——三筆的驗證深度並不齊平，前兩筆偏區域性、第三筆偏單檔案。

需要剋制的是因果順序：修復先落地，而需要這些修復的遷移 PR #56 仍停在 09-16，開放未合併。這意味著三筆合入後，broadcast_to 裡那個 tl.static_range 繞行可以撤回、unique_dim 可以按原寫法提交，但「整批運算元是否能在 riscv64 上跑通」這個問題本期沒有答案——要等 #56 恢復推進才能驗證。

1.2 llvm-project：riscv 分支整枝重放，新增貢獻指南並取消預演開關（10-29）

日期：2026-10-29　來源：riscv 分支提交列表、提交 faf4def312、RISCV_CONTRIBUTING.md、autorebase 工作流

23:00 前後，riscv 分支做了一次整枝重放：可見的 25 筆提交，committer 時間全部落在 23:00:40 到 23:00:44 這 4 秒內。重放內容裡有一筆是真的新東西——[workflows] Push rebased PRs directly and document contribution options（作者時間 10-29 09:59），改動兩個檔案：autorebase.yml 刪掉 8 行（去掉 dry_run 輸入與對應的預演分支），新增 82 行的 RISCV_CONTRIBUTING.md。

這份指南把「怎麼往 riscv 分支送東西」寫成了兩條路。路一是先開 issue、由維護者從當前 riscv 切一條 work/issue-NNN 工作分支，貢獻者往工作分支提 PR，維護者整合後併入 riscv——適合多人協作、需要穩定歷史的工作項。路二是直接向 riscv 提 PR，基線一變就手動觸發重基工作流：工作流跑在 PR 源倉庫、用源倉庫的 GITHUB_TOKEN、以 --force-with-lease 帶明確期望 SHA 推回源分支，衝突一律取 riscv 側（含改刪衝突中保留 riscv 側的刪除），等價補丁自動跳過，絕不改寫 riscv 本身、也絕不自動合併。

與上一期那份 244 行工作流相比，最大的變化是預演被取消：上一期預設「只預演不推送」，本期改成「成功即推送，沒有預覽選項」，文件裡也明寫了這一句。這是把摩擦降下來的同時把風險前移——貢獻者本地分支必須及時同步，否則舊基線歷史可能被推回去；文件裡專門有一段提醒儲存未提交工作、避免把舊基線推回遠端。另一處細節值得記下：文件明確說用 GITHUB_TOKEN 推送通常不會觸發後續的 push/PR 工作流，因此更新後的 SHA 上 CI 是否跑過需要人工確認。

2.3 openRuyi 在審：#1350 首輪程式碼級複核 18 條，ollama 安全更新待合（10-29 狀態）

日期：2026-10-29（狀態）　來源：PR #1350 Ruyiai packages、PR #1514 ollama、PR #1490 交叉工具鏈、PR #1516 qemu-rustsbi

3.2 FlagGems 遷移成了 triton-riscv 的缺陷發現機制（10-29）

六、趨勢觀察

6.1 修復先於驗收：三筆修復靠遷移過程中攢下的問題單，不靠迴歸測試

本期三筆合入暴露了一個順序問題：先有修復，後有驗收。unique_dim 的張量填充、broadcast_to 的迴圈偏移、雜湊運算元的重複索引，三處缺陷都不是編譯器自己的測試發現的，而是把 FlagGems 運算元往上搬時撞出來的；修復合入了，需要它們的遷移 PR #56 卻停在 09-16 未動。結果是一批「為某個用法準備的修復」暫時沒有對應的用法在跑。

這種狀態的風險不在當下而在下個月：如果 #56 恢復時 Triton 上游又換了幾輪，三筆修復是否還與新基線相容，需要重新驗證一遍；而如果 #56 一直不恢復，這套「端到端驗收集」就等於停擺，下一批缺陷要等外部使用者撞上。對一個以「能跑真實模型」為目標的棧來說，把遷移做成常駐迴歸（哪怕只有幾十個運算元、每晚跑一次）比再多合幾筆修復更有價值。

6.2 分支治理的兩種寫法：llvm 寫規則並取消預演，pytorch 靠整枝重放

同一天裡，兩條分支給出了兩種治理答案。llvm 的 riscv 分支整枝重放了一遍，真正新增的是一份貢獻指南：把「往 riscv 送程式碼」拆成「向維護者工作分支提 PR」與「直接向 riscv 提 PR 並手動觸發重基」兩條路，同時把工作流的預演開關刪掉——成功即推送，沒有預覽。pytorch 的 riscv 分支則只是重放到上游 3afdbd3，再讓同步機器人補一筆依賴快取修正，沒有任何流程文件。

兩者的成本結構不同。llvm 分支的補丁集大、外部貢獻多，衝突與歷史漂移是主要成本，所以規則化值得寫文件、值得配工作流；pytorch 分支的補丁集小（11 筆），維護者自己重放一次的成本低於維護流程的成本。取消預演這一點則需要觀察：把摩擦降下來的同時把「推送錯歷史」的風險前移給貢獻者，靠 --force-with-lease 與狀態複檢兜底，實際效果要看下一兩個外部 PR。

6.3 發行版按月鋪量，棧級三件套按月卡審

openRuyi 本期 76 筆提交、10 筆合入，其中 64 筆是一批 KDE 框架升級；ruyi-imager 從 1.0.0 到 1.1.0-rc.1 用了七週，節奏正常；而同屬「分發」的另一側，RuyiAI 三件套的打包 PR #1350 從 09-21 開到現在，仍在 spec 規範層面返工。兩條流水線的差別不在人手，而在成熟度：KDE 包有上游 spec 可參照、有既定的版本節奏，重打包是機械動作；三件套是從零寫的 spec，既要解釋「為什麼把 LLVM 留在包內」，又要解釋「為什麼 %check 為空」。

這對 RuyiAI 的啟示是：能被髮行版吞下的前提是包本身足夠「常規」。buddy-mlir 自帶 LLVM、triton 依賴 git 可執行、tilelang 需要發現 buddy-mlir 工具鏈——三處非常規點各自都需要補丁與解釋，每個解釋都要維護者花時間判斷。若希望三件套進入月度發行節奏，把這三處非常規點收斂成一兩條明確的打包約定（例如統一由 buddy-mlir 提供工具鏈、統一用 git format-patch 的補丁堆疊），比逐條回應複核意見更省事。
