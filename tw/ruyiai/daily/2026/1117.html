今日重點：tilelang-riscv 合入 #6，RISC-V 後端預設改走 buddy-opt（11-16）

日期：2026-11-16　來源：PR #6、合併提交 2204c7e

11-16 14:56，tilelang-riscv 合入 #6「RISC-V 後端預設改用 buddy-opt，並補上 BOSC 與 GEMM 兩個示例」。22 個檔案、+835 −284，兩筆提交：11-04 的「把 buddy-opt 選為預設並拆開兩套工具鏈根」，11-13 的「補示例、改文件」。這是該倉自 11-03 合入 #5 之後的第一筆改動，倉裡目前仍只有 main 一個分支。

改動的骨架在 toolchain.py（+62 −4）：Buddy 與 LLVM 各自有獨立的工具鏈根目錄，TILELANG_RISCV_OPT 可顯式覆蓋最佳化器；最佳化器的選擇被寫進 RISC-V 的編譯快取鍵（kernel_cache.py +4）。這一條比表面上的”換預設值”更實用——此前換最佳化器後仍有命中舊快取產物的風險，現在快取鍵帶上最佳化器，等於把”用哪套工具鏈”變成可檢索的構建維度。

示例補了兩類：examples/riscv/gemm 是宿主機上的 FP16 GEMM（gemm.py +47），examples/riscv/bosc 是一套可獨立構建的 BOSC INT8 GEMM 韌體（build.py +190、launch.c +122、env.sh 與 README）。文件側改動最大的是 docs/get_started/BuildOnSG2044.md（+55 −178），從分步手工操作改成可移植路徑與精簡用法。測試同時補齊三份：工具鏈測試 +126 行、編譯快取測試 +29 行、適配管線測試 +45 行，都在 testing/python/riscv 目錄下。

今日重點：triton 與 buddy 同一天動工具鏈，LLVM 解耦並補回 dump()（11-16）

日期：2026-11-16　來源：triton-riscv PR #123、buddy-mlir PR #1062、triton-riscv PR #115

11-16 18:14，triton-riscv 開出 #123「把後端工具鏈從 Triton 的 LLVM 裡解耦」。問題寫在說明裡：CPU 後端不往 libtriton.so 里加任何 C++，pass 全部走程序外的 triton-shared-opt，但 add_triton_plugin 仍把 MLIR 庫及其 LLVM 鏈進了 libtriton.so，於是後端工具鏈只能用 Triton 自己編譯時那一個 LLVM。改法是關掉 TRITON_SHARED_BUILD_CPU_BACKEND，新增 llvm-hash.txt 單獨釘 LLVM 包：libtriton.so 用與 Triton 原始碼匹配的 LLVM，triton-shared-opt 隨 Triton 構建，buddy-opt／buddy-translate／buddy-llc／opt／llvm-objdump 走 buddy release，彼此只交換文字 IR。RISC-V 的 +v 與 +xsmtime 只有 llc 需要，因此 Triton 依賴的 LLVM 不必再背 RISC-V 補丁。三個檔案、+16 −2；llvm-hash.txt 暫釘 nightly/v0.1.4.dev20261103，除 libtriton.so 少一個外掛外，構建產物不變。

同日之後（11-17 01:23），buddy-mlir 開出 #1062「Build LLVM with dump() support」。LLVM 包用 -DLLVM_ENABLE_ASSERTIONS=OFF 構建，而 MLIR／LLVM 的 dump() 只在開啟斷言或 LLVM_ENABLE_DUMP 時才定義，下游一旦呼叫就連結失敗。PR 裡給了實證：mlir::Operation::dump() 在 nightly/v0.1.4.dev20261103 的包裡有，在 nightly/v0.1.4.dev20261113 的包裡消失了。Triton 正是這樣的下游：開 NDEBUG 時標頭檔案裡連宣告都沒有，不開又連結不上。補丁只加一行 LLVM_ENABLE_DUMP=ON，保住 Release 構建。

兩件事指向同一處：buddy 的 LLVM 包已經是 triton-riscv 的預設上游，一個 nightly 換包就能把下游編譯卡住。Renovate 的 #115 恰好把依賴釘在 nightly/v0.1.4.dev20261113 上（11-16 21:40 仍有更新），#1062 若不進，這顆釘子就會一直扎著。

2.1 openRuyi 給 Go 1.27 回填 Zvk AES（11-16）

日期：2026-11-16　來源：提交 6592b995

11-16 14:21，打包倉落下一筆 SPECS: go: Backport SHA-2 AES optimization，新增補丁 1005-release-branch.go1.27-crypto-internal-fips140-aes-bl.patch（468 行），go.spec 同步加兩行。說明文字寫得很直接：把 Go master 上基於 Zvk 的 AES 支援回填到 1.27 釋出分支；提交者 Julian Zhu。

Zvk 是 RISC-V 的向量加密擴充套件族。補丁補的是 crypto/internal/fips140/aes 的 block 例程，讓 riscv64 上的 AES 可以走向量指令而不是純標量實現；是否啟用取決於執行期對 Zvk 的檢測，沒有該擴充套件的核仍走原路徑。上週打包倉剛把 Go 升到 1.27.4 並補齊三十餘個 Go 包，這一筆是在版本落定之後補效能，屬於”先適配、再最佳化”的第二層。

三、向量擴充套件與運算元最佳化

3.1 +zvfbfmin 成了預設特徵串裡的必需品（11-16）

日期：2026-11-16　來源：PR #117

#117 的說明裡有三條邊界值得記下來。其一，沒有 Zvfbfmin 時，LLVM 對可伸縮 bf16 向量連 load 與 convert 都不降，llc 直接報 Scalarization of scalable vectors is not supported。其二，buddy-mlir 的 lower-vir-to-vector 會保留可伸縮 bf16 向量，並預設假設目標有 Zvfbfmin，所以缺這個擴充套件時下游會在 llc 階段整批失敗。其三，加上之後轉換走 vfwcvtbf16.f.f.v 與 vfncvtbf16.f.f.w，也就是把 bf16 與 fp32 之間的寬窄轉換交給向量單元。

專案支援的 RVV 目標（SpacemiT K3、SOPHGO SG2044）都帶這個擴充套件；沒有的核可以用 TRITON_RISCV_LLC_FEATURES 覆蓋預設特徵串。DEFAULT_MARCH 沒有動，因為它只驅動 GCC 連結那一步，而 GNU as 2.42 並不認識 zvfbfmin——用 +zvfbfmin 編出來的物件仍然能鏈上。

六、趨勢觀察

6.1 工具鏈邊界被重新劃：一個 LLVM 不再包打全場

triton-riscv #123 與 buddy-mlir #1062 是同一天的兩面。前者把後端工具鏈從 libtriton.so 裡摘出去，用 llvm-hash.txt 單獨釘 LLVM；後者補回被 LLVM_ENABLE_ASSERTIONS=OFF 關掉的 dump()。兩件事合起來說明 RuyiAI 這條線已經不再假設”一個 LLVM 打天下”：Triton 自帶一份、buddy 發行版一份、後端 llc 一份，各管一段，介面收斂到文字 IR。

6.2 編譯器選擇變成構建維度

tilelang-riscv #6 把 buddy-opt 設為預設，同時把最佳化器寫進快取鍵。這比”換個預設值”重要：最佳化器一旦進入快取鍵，同一份 kernel 在不同工具鏈下的產物就不會互相汙染，切換工具鏈也從”改環境變數試錯”變成”明確的構建引數”。示例補上 BOSC 與 GEMM，等於給這條路徑配了兩個可復現的驗收點。

6.3 發行版開始吃 RISC-V 專屬擴充套件

openRuyi 這一週的動作集中在擴充套件上：Go 回填 Zvk AES，triton 輪子預設帶 +zvfbfmin，核心 patchset 與 config 一天內兩次重新整理。這些都不是通用上游能自動覆蓋的部分，必須由發行版與工具鏈維護者逐項補齊。RVA23 之後，差異化的地方正在從”能不能跑”轉向”能不能用到向量與加密擴充套件”。

6.4 日更資訊面繼續空轉

官方主頁不動、ruyiai-daily 斷檔第九天、外部新聞零命中，本期全部素材來自四個 GitHub 組織的提交與 PR，以及論壇的兩篇帖子。這種狀態下報告的判斷價值主要取決於對提交內容的理解，而不是新聞條數——發行說明為空的 triton 正式版尤其如此，只能回到 tag 指向的提交去讀。
