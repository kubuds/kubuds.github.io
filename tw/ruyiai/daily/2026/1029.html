今日重點：K3 解碼注意力搬上 VIR，效能與手寫 RVV 核心持平（10-28）

日期：2026-10-28　來源：buddy-mlir PR #1014、K3 文件、triton-riscv PR #91、llvm-project 重基工作流

本期最實質的一步發生在 09:36：buddy-mlir 的 #1014「K3: write the decode attention in the VIR dialect」合入（4 個檔案、+476/−14），把 K3 w4g32 核心的解碼注意力整段搬到 VIR 方言上。這不是又一次方言能力補齊，而是第一次拿真實模型的核心去做對賬——一邊是此前手工寫的 RVV 向量核心，一邊是用 Python 拼出來的 VIR 核心，比數值、比指令數、比板上的吞吐。

做法可以拆成四層。構造層不再手工拼運算元、手工拼型別（此前要在字串裡寫運算元名與型別描述），改走 buddy_mlir.dialects.vir 的 SetVLOp、load、shuffle、fma、reduce；一個 work item 就是一段 vir.set_vl 區域，長度取頭維的一半（64 lanes），每個頭是一個由 RoPE 兩半拼成的可伸縮向量，區域返回該頭的 (max, sum)。旋轉層把 q 在區域內載入、旋轉、縮放，rotate_half 落成一條 vir.shuffle，cos/sin 存成兩行等長資料，於是不再需要 vir.from_vector。記憶體檢視層用 memref.expand_shape 把 q、KV cache、輸出和 q 的歸一化權重按最後一維切成 2×64。歸一化層（Qwen3 的 q/k norm）單獨開一段一維 vir.set_vl 區域，按 _head_rmsnorm 的做法對兩半求平方和。

流水線引數也跟著改了：核心降級從 vector-width=128 換成 rvv-vlen=1024、use-scalable=false，向量尺寸由分析按 A100 的暫存器定，因為區域裡有 vir.shuffle，每個頭保持為一個 128 個 f32 的向量組（LMUL 4）。作者在 PR 裡寫得很直白：切到 use-scalable=true 是下一筆的事。舊的 _attn_decode_fn 保留，A210 核心的解碼注意力還在用它。

結果三項都硬。數值上，帶與不帶 q/k 歸一化，都與 _attn_decode_fn 位級一致；機器碼上，兩個並行體各 178 條向量指令，鍵值迴圈與舊版指令相同，只有兩處溢位暫存器的過載位置換了；板上吞吐（K3、buddy-cli 貪心解碼、三輪交替、9 對生成文字完全一致）三檔全部落在同一區間——63 token 後 28.26~28.49 對 28.10~28.58，458 token 後 26.82~27.13 對 27.02~27.04，900 token 後 25.37~25.41 對 25.29~25.77。作者自己註明：同一份程式碼兩次構建的差異可達 2%，區間是重疊的。

同日另有兩筆與這條主線配套。一是 llvm-project 的 riscv 分支補了一份 244 行的自動重基工作流（詳見 1.1），把「作者 fork 上的 PR 跟不上基線」這件事從手工搬進 Actions。二是 triton-riscv 的依賴錨點被 renovate 再抬一級到 dev20261028（詳見 1.3），但這版夜間構建的出包時間早於當日上午三筆合入，所以即便這筆依賴更新合入，下游也還拿不到 #1014——要用上今天的成果，得等下一版夜間構建。

1.1 llvm-project：不再換基，補上「作者 fork 一鍵重基」工作流（10-28）

日期：2026-10-28　來源：riscv 分支提交 cf00909d、工作流全文、riscv 分支提交列表

與上一期「五天內第五次整枝重放」不同，本期 riscv 分支的本地補丁集一筆未動：分支頭部從 ed439f3e 往前走了一筆，與上一期頭部的對比是領先 1 筆、落後 0 筆、只動 1 個檔案。這筆新增的提交（cf00909d，作者 23:27、提交 23:54）是純 CI 資產——.github/workflows/autorebase.yml，+244/−0。

工作流的設計意圖寫在註釋裡：安裝在作者源倉庫的預設分支上，在 Actions 裡手工填入目標 PR 號執行，使用源倉庫自己的 GITHUB_TOKEN，不需要自定義金鑰或標籤。觸發方式是 workflow_dispatch，兩個輸入——PR 號（必填）與「只預演不推送」（預設開啟）。執行環境 ubuntu-24.04、超時 90 分鐘；註釋明確要求「絕不在持有寫許可權的情況下執行 PR 程式碼、鉤子、構建或子模組」，git 配置裡把 hooksPath、attributesFile、fsmonitor 全部指到 /dev/null，GIT_TERMINAL_PROMPT=0、GIT_EDITOR=true。衝突處理有專門函式：-Xours 處理不了的場景（含改刪衝突）逐個走 ls-files --unmerged，有第 2 階段就取本地、沒有就刪除；重基時先判斷基線是否已是祖先，能識別「等價補丁」並丟棄重複的舊基線補丁。

這筆要解決的是過去幾期反覆出現的一個具體成本：分支一天整枝重放一次，作者 fork 上的 PR 立刻落後，靠人工逐個重放既慢又容易把補丁集弄亂。需要說清邊界——它重基的是別人的 PR，分支自身每日整枝重放仍需維護者操作；它把「跟隨基線」的成本從人工判斷降為一次帶預演的排程，但並沒有自動化的觸發條件。真正的價值要等下一個外部 PR 按新基線提交時才能驗證。

2.1 openRuyi PR #1350：三筆提交重基，GCC 構建代價量化為 2.81 倍（10-28）

日期：2026-10-28　來源：openRuyi PR #1350、複核評論、PR 提交列表

16:22，RuyiAI 三件套打包 PR 的三筆提交（buddy-mlir、python-triton-ruyiai、python-tilelang-ruyiai）在同一分鐘內全部重寫，明顯是重基到最新主分支；當前規模 9 個檔案、+680/−0，與上期記錄相比多了 14 行。PR 在 18:15 因複核評論再次重新整理，評論總數 13 條，仍未合入。

本期最有資訊量的一條來自作者 10:41 的回覆。上一期的口徑是「可以用 GCC 替代，但構建時間至少 1.5 倍」；本期給出了實測：在 riscv64 機器上把 buddy-mlir 的構建從 LLVM 換成 GCC，時間從 8814 秒變成 24798 秒（約 2 小時 27 分對 6 小時 53 分），2.81 倍，且那次用 GCC 的構建在連結階段失敗、沒有跑完。

這條把爭論從立場問題變成了成本問題。「是否把 buddy-mlir 自帶的 LLVM 外接」原本是兩條技術路線之爭，現在有了發行版構建農場能看懂的數字：2.81 倍意味著排期、機器佔用與超時策略都要重算。作者的另一條理由也因此更站得住——buddy-mlir 用到的 LLVM 只在自己包內使用，且這些包都鎖定了具體的 LLVM 提交，留在包內才可復現。同時他也說明 triton 上游的 setup.py 有強制檢查 git 是否可執行，所以要麼加 git 構建依賴，要麼打補丁改 setup.py（後者會隨 triton 升級而失效）。

六、趨勢觀察

6.1 從「能表達」到「跑得一樣快」：VIR 第一次拿真實模型核心做效能對賬

過去三期這條主線一直在補表達力：10-26 一夜七筆把可伸縮向量補進來，10-27 補上 Python 繫結，10-28 直接把 K3 的解碼注意力整段搬過去，並且拿板上吞吐做了對賬。三個數字合起來才是這次的意義——數值位級一致、指令數相同（各 178 條）、吞吐區間重疊。自研方言最容易卡在「能跑但慢」這一關，#1014 至少證明這一關暫時過了。

但要判斷這條棧是否真的可替代手寫核心，還缺兩件事。一是覆蓋面：這次只搬瞭解碼注意力，A210 核心仍用舊函式，MoE、量化與預填充路徑都還沒動；二是可伸縮向量：本期明確關掉了 use-scalable，下一筆開啟之後，向量尺寸不再由編譯期決定，LMUL 4 的分組假設會鬆動，屆時數值與指令數能不能守住，需要重新對賬。在此之前，把「VIR 已追平手寫核心」當成結論都過早，準確說法是「在 K3 解碼注意力這一段、在固定向量長度下追平」。

6.2 換基的成本從補丁漂移轉向治理：工作流接管重基，分支自身仍靠人

同一天裡，llvm 的 riscv 分支停止整枝重放，改為補一份 244 行的自動重基工作流。這個轉向值得單獨記一筆：過去五天的節奏是「一天一次整枝重放、每次重寫二十筆提交流」，作者時間不動、committer 時間統一，補丁集本身沒有新增功能。這種做法能跟住上游，但代價是外部貢獻者的 PR 永遠落後一格，誰要提交就得自己重放。

新工作流把這件事做成了「填 PR 號、預設預演、一鍵推送」的排程，衝突一律取 riscv 側、重複補丁自動丟棄、絕不執行 PR 程式碼與構建。它不解決分支自身的每日跟隨，但把「跟隨基線的成本」從維護者的手工判斷裡分出來一部分。下一階段要觀察的是外部 PR 是否真的因此變多——如果工作流上線後兩週內仍無外部 PR 按新基線提交，那說明瓶頸不在重基工具，而在別處。

6.3 分發層的爭論開始有價格：2.81 倍的構建時間比「偏好」更有說服力

#1350 爭論了將近一個月，核心分歧是 buddy-mlir 自帶的 LLVM 要不要外接。上一期的口徑還是「可以用 GCC，但至少 1.5 倍時間」，本期作者給出了實測：riscv64 上 8814 秒變 24798 秒，2.81 倍，且用 GCC 那次連結失敗沒跑完。爭論的性質於是變了——從技術偏好變成構建農場的排期算術。

這條對 RuyiAI 棧的啟示不在結論，而在方法：RISC-V 發行版打包的很多分歧（是否 vendor、是否外接工具鏈、是否隨包分發 IR），最終都要落到「構建時間、映象體積、可復現性」這三個可測的數字上。上一期 openRuyi 收回「隨包分發 LLVM IR」的路線，本期 #1350 用 2.81 倍守住「LLVM 留在包內」，兩次判斷方向相反，但依據是同一類成本核算。接下來的看點是這筆 PR 能否帶著這個數字合入——如果不能，說明發行版對構建時長的容忍度低於作者預期，那才是真正需要調整的地方。
