3.3 論文：長向量處理器上重排 FlashAttention，實測加速 1.84 至 2.08 倍（10-21）

日期：2026-10-21（略早於本期視窗起點，因 arXiv 索引在本視窗內首次可見而收錄）　來源：arXiv 2610.29489v1

《Reorienting the Vector Axis: Restructuring FlashAttention for Long-Vector Processors》（Emmanuel Irabor、Marc Casas）把 PyTorch 的 CPU FlashAttention 核心移植到帶 2KB 向量暫存器的 RISC-V CPU 上，先給出一個不客氣的基線：只達峰值浮點吞吐的 16.2%。

原因分析得很具體。原核心按查詢行逐行推進：與 V 的乘沿 64 元素頭維向量化，softmax 的逐行最大值與求和是「把整個暫存器塌縮成標量」的歸約，軟體指數函式的多項式係數還要與 tile 資料搶向量暫存器，導致溢位到棧。三項疊加，向量暫存器的利用率上不去。

兩條改法都不改演算法與數值。第一條把分數 tile 與執行輸出一起轉置，讓查詢落線上性連續軸上——於是「一個 tile 裡裝多少查詢」這一個引數就統一決定了核心各段的向量長度，可按機器配置，同時兩個歸約自然消失。第二條把多項式係數搬進標量暫存器，消除溢位，softmax 的向量訪存指令減少 78.7%。

實測：頭維 64 時，兩項合起來把整核週期降到 1.84 至 2.08 倍加速，浮點利用率從 16.2% 升到 29.7%；同設計的 FPGA 對兩項改動的排序一致且收益更高，達 2.71 倍。

對本棧的意義在方法而非數字：向量長度自適應與暫存器壓力正是 triton-riscv 與 tilelang-riscv 在 RVV 降級上的結構性問題，而不是「有沒有 intrinsics」；文中「按機器匹配 tile 內查詢數」與 IREE 把 Tile N 取 vlen/8 屬同一類決策，可直接做同口徑比較。

五項分屬虛擬化、圖形虛擬化、韌體更新、輸入自動化與光碟映象工具鏈，合起來指向同一件事：在 RISC-V 上跑完整桌面並對其做自動化驗證。這與峰會展示的「AI 驅動 IDE 圖形化測試」是同一需求的兩端——測試框架要驅動真實介面，就必須先有可指令碼化的輸入與可虛擬化的圖形棧。桌面支援此前是 RISC-V 發行版的弱項，這批提案把它拆成了可逐項合入的任務。

6.4 擴充套件落地路徑成形：編譯、模擬、運算元三層先後到位

以 AME 為例，本週可見一條擴充套件從提案到可用的完整路徑：先有後端設計與指令集定義（LLVM #16、#24、#27、#29），再有降低與排程的實現（#30、#31、#32），同時模擬器給出可執行語義（QEMU ame-0.6），最後運算元庫提供可測的 kernel 與驗證套件（AME-operator）。

P 擴充套件走同一條路但已到後半程：QEMU 覆蓋全部指令，GCC 支援更新到 0.6，LLVM 側 mulq、乘高位累加、sati/usati、Packed Pair 等 intrinsics 分批合入上游。對照來看，P 擴充套件缺應用側 benchmark，AME 缺真機。

這個順序本身值得作為方法記錄：沒有模擬器無法驗證編譯器，沒有運算元庫無法驗證模擬器。三者齊備之前談效能沒有意義，齊備之後瓶頸才轉移到硬體與實測。本週的進展是「齊備」而不是「更快」。
