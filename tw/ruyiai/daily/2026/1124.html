今日重點：buddy-mlir 合入 Qwen3-0.6B FP16 最佳化，Prefill 86.01 token/s（11-23）

來源：PR #1001。

#1001 在 11-23 14:51 合入，標題為「Optimize Qwen3-0.6B FP16 Prefill and Decode on K3 A100」。改動 23 個檔案，加 560 行、刪 50 行。

實測在同一臺 K3 的 A100 核心 8 至 15 上完成，八個物理核，輸入端一致。Prefill 評估 128 個位置，Decode 從第 96 個位置起測 32 步，載入時間不計。

實現 Prefill（token/s） Decode（token/s）
Buddy 主幹，未最佳化 FP16 4.24 0.84
llama.cpp 71.64 14.38
Buddy，本 PR 86.01 13.45

Prefill 比 llama.cpp 高 20.1%，是主幹基線的 20.3 倍。Decode 為 13.45 token/s，比 llama.cpp 低 6.5%，仍是主幹的 16.0 倍。

兩項指標方向相反。Prefill 走的是分塊 GEMM 與原生 VLEN=1024，Decode 受限於單 token 的 GEMV 頻寬。PR 說明寫明比較使用 all-position logits，雙方口徑在這點上對齊。

核心側複用了 #997 的成果，包括 IME FP16 GEMM 與 GEMV、Decode 權重打包、RVV 與 SiLU 最佳化。Attention 用向量寬度 64，Decode 只切一路 KV。

配置集中到
models/qwen3/specs/f16_k3_a100.json，預設流水線不受影響。檔案裡 VLEN 為 1024，Prefill 向量寬度 64，Decode 打包寬度 32，執行緒數 8。輸出詞表權重單獨存放，以便按投影選擇佈局。

正確性側，96 個 Decode token 與三組重複貪心生成用例都與 PyTorch 參考一致。PR 說明也指出，完整的 check-buddy 被禁用的 Python 包目標擋住，未能全量跑。

4.2 #1077 提 strip 與 zstd 統一，目標是單資產上限（11-23）

來源：PR #1077。

#1077 在 11-23 11:05 開出，只改一個檔案，尚未合入。標題為「Pack the LLVM and buddy tarballs with zstd」。

PR 說明給出起因。riscv64 的 LLVM 安裝包 gzip 後略超 GitHub 單資產 2 GiB 上限。nightly/v0.1.5.dev20261120 因此釋出失敗，介面返回 422 與「size must be less than 2147483648」。

方案有三點：strip 二進位制與共享庫、去掉 MLIR Python 繫結、改用 zstd -19 –long=27 打包。作者給出的預估是 LLVM 從 2047 MB 降到約 840 MB，buddy 從 264 MB 降到約 180 MB。

說明裡另提兩處配套。triton-riscv 的 setup.sh 已能讀 .tar.zst；此改動落地後的首個發行需跑一次 llvm_cache_mode=clean，因為快取鍵不含這次過濾。

6.1 模型最佳化轉入批次複用

#1001 明確寫著複用 #997 的核心、權重打包與 RVV/SiLU 最佳化。佇列裡的 Whisper Base、PaddleOCR-VL-0.9B、EmbeddingGemma 也引用同一條路徑。

這說明 K3 A100 上的模型加速已經從單點攻關轉為模板化。新增一個模型的主要工作是寫配置與跑正確性，而非重寫核心。

判斷依據有兩條。一是配置集中到每個模型的 specs 目錄，二是 PR 說明反覆出現「shared kernels」與「reuse」的表述。

6.2 釋出編號推進快於內容

ruyi 從 0.55.0-beta 推到 0.56.0-alpha，程式碼差異只有版本號三行。triton-riscv 補發的正式標籤也指向 11-18 的舊提交。

兩個倉在同一天出現了「有新版本、無新程式碼」的情況。這說明發布節奏由版本規劃驅動，而不是由變更量驅動。

對下游的影響是版本號不再指示內容多少。判斷是否值得升級，需要看發行說明的條目集合，而不是編號大小。

6.3 裝置側程式碼開始離開主倉

網站倉這一輪刪掉 775 行，把裝置執行時交給獨立倉與子模組。同期 ruyisdk-test 組織下出現 ruyi-imager-webview 與 ruyi-imager-electron。

方向是把刷寫工具拆成可獨立發版、可獨立測試的元件。主倉因此變小，構建許可權也能單獨隔離。

需要留意的是新倉落在一個測試組織下，尚未遷到 ruyisdk 主組織。這一步是否會發生，可作為後續觀察點。
