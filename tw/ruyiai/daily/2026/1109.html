今日重點：Ruyi Firmware 連續兩日發版，HiFive Unmatched 進入支援列表（11-07、11-08）

日期：2026-11-07、2026-11-08　來源：Ruyi Firmware 20261107、Ruyi Firmware 20261108、韌體倉提交列表

openRuyi 的 UEFI 韌體專案在兩晚內連出兩版。11-07 22:21（北京時間）釋出 20261107，11-08 22:47 釋出 20261108 並標記為預釋出；兩版各帶四個構建產物。

20261107 是本視窗的功能版，最大變化是把支援面從 SpacemiT K3 擴到 SiFive HiFive Unmatched：新增該板的 SPI 啟動、JTAG 恢復、NVMe 與 USB 啟動，以及持久化 UEFI 變數。圍繞這一擴充套件，釋出說明裡還有四項配套調整：每塊板分別提供 DEBUG 與 RELEASE 兩套包；Platform Settings 里加入 PXE 與 HTTP ISO 啟動控制（預設關閉）；UEFI 驅動模擬改為預設啟用，可在 Setup 中改，也可用配置指令碼設成映象預設值；兩塊板統一使用 Ruyi logo 與啟動倒計時條，Firmware Update 介面加了檔案選擇器。K3 側另有兩條體驗修正：改善圖形控制檯的響應速度，以及在 UEFI 啟動階段讀取 P1 上的 RTC。

20261108 只改 K3 一條線：USB Fastboot 切換到 EDK2 的共享實現，可用於韌體更新、回讀，以及從記憶體啟動 EFI 應用；同時透過 fastboot getvar version-bootloader 上報 EDK2 韌體版本。這條改動把廠商私有的刷機通道併入 EDK2 標準路徑，對產線與售後是可直接使用的介面，對開發者則意味著不再需要專用工具確認韌體版本。

兩版都保留同一句相容性宣告：Linux 主線支援按盡力而為的方式提供；已知的 framebuffer 問題在發行說明裡給出繞行辦法。從 10 月的 20261013 至 20261015 三連發（CPU 模式選擇、System Information 頁）看，這條韌體線已進入按日迭代的節奏，而 Unmatched 的加入是它第一次跨出單一晶片廠商。

今日重點：按精確 VLEN 編譯的模型在別的 VLEN 上會靜默算錯，buddy-mlir 改為載入期校驗（11-08）

日期：2026-11-08　來源：PR #1032、提交 4063c48

PR #1032 解決的問題是一類錯誤的失敗方式：不報錯，只算錯。按精確 VLEN 構建的 RISC-V 模型，向量程式碼只對那一個 VLEN 成立——llc 被明確告知 VLEN（+zvlNb 與 -riscv-v-vector-bits-max），decode attention 裡的可伸縮向量也按它定尺（#1028、#1030）。換到別的 VLEN 上，模型不崩潰，直接給出錯誤結果。提交說明給出的例項很具體：K3 上按 prefill_ime 構建的 DeepSeek-R1 rax（BUDDY_RISCV_VLEN=1024）在沒有執行 /proc/set_ai_thread 時會落到 X100 核心（VLEN 256）上執行，結果錯誤而無任何提示。

修法是把校驗前移到載入時刻。runtime/rvv/BuddyRvvVlen.c 作為建構函式被連結進模型庫，庫一被載入就讀 vlenb，發現與構建時的精確 VLEN 不符就列印資訊並以 _exit(1) 結束程序。用 _exit 而不是 exit 是有意的：載入器持鎖期間跑解構函式會死鎖。建構函式的形式覆蓋了所有載入方，包括命令列工具、服務端與測試；通用 RVV 構建（不指定精確 VLEN）與其它目標不受影響。

評審後又補了第二筆提交，把校驗從“按構建變數判斷”改成“按最終 llc 選項判斷”。原先的問題有兩個：一是原生構建可能透過模型自帶的 LLC_ATTRS 指定 VLEN，若 BUDDY_RISCV_VLEN 與它不一致，校驗值會和實際程式碼不符；二是隻連結進了第三階段，Qwen3-VL 的視覺與解碼兩個 shim、以及分層連結的路徑都漏掉了。現在由構建指令碼從最終 llc 選項裡取出精確 VLEN（與 VIR 降低讀同一處），第三階段、兩個 shim 與分層連結全部帶上，配置階段發現選項互相矛盾就直接失敗。

測試是這條改動的另一半：test_buddy_rvv_vlen.py 為 VLEN 128 到 65536 分別構建模型庫，只有宿主那一個能載入，其餘全部以退出碼 1 結束；test_buddy_rvv_vlen_cmake.py 用配置指令碼覆蓋 BUDDY_RISCV_VLEN、LLC_ATTRS、prefill_ime 與 zvl 引數的各種組合。真機驗證在 K3 的 X100 與 A100 兩種核心上完成，倉庫自檢 239 加 409 項透過。

1.2 triton-riscv：為 AMD 後端補 riscv64 缺失的 codegen 庫，夜間版出 x86_64 與 riscv64 兩個 wheel（11-07）

日期：2026-11-07　來源：PR #102、夜間版 aa51ac2、夜間版 6895885

PR #102 的標題是“加入 AMD 支援”，實際內容是補一個缺失的庫，而不是新增一個後端。上游的 AMD 後端需要 libtriton_amd_codegen.so：要麼下載預編譯副本，要麼針對單獨固定版本的 LLVM 自行構建，而這兩條路都沒有 riscv64 版本。這個庫本身很小，用倉庫裡現成的 LLVM 幾秒鐘就能編出來。setup.sh 因此在檢測到庫缺失時本地構建並放到約定路徑，env.sh 把 TRITON_AMD_CODEGEN_PATH 指向它——原來的 GPU 依賴 stub 會把所有 GPU 下載指向空目錄，順帶也跳過了上游對該庫的拉取，而外掛編譯時仍要讀這個路徑。沒有它，AMD 後端拒絕編譯任何東西。

這條改動也說明外掛化改造之後這個倉的定位：同一棵樹既產出 riscv64 的 Triton，也在構建期容納其它後端所需的元件，多後端共存不再靠分支切換。視窗內兩筆夜間版按新節奏產出（11-06 12:08 與 11-07 07:52），每版兩個產物，分別是 cp312-abi3 的 x86_64 wheel（約 320 MB）與 riscv64 wheel（約 337 MB）；此前的夜間版是五到六個產物，產物數下降與 stable ABI 單 wheel、後端併入 Triton 包這條線一致。

三、向量擴充套件與運算元最佳化

3.1 buddy-mlir：按精確 VLEN 構建的模型庫加載入期校驗，K3 上誤跑在 X100 核心會被立即攔下（11-08）

日期：2026-11-08　來源：PR #1032、提交 4063c48

改動共十二個檔案、新增五百四十七行、刪除八十六行，核心是一個十幾行的 C 檔案：runtime/rvv/BuddyRvvVlen.c。它作為建構函式連結進模型庫，載入時讀 vlenb 並與構建時的精確 VLEN 比對，不一致就列印資訊後退出。配套的構建指令碼改動比執行時程式碼更復雜——buddy_rvv_vlen.cmake 現在從最終 llc 選項推導 VLEN（與 VIR 降低共用同一段讀取邏輯），buddy_model.cmake 在規格與選項確定後編譯該目標檔案，第三階段、Qwen3-VL 的兩個 shim 與分層連結都顯式帶上。

文件同步更新了 A210 與 K3 兩篇 DeepSeek-R1 部署說明，把“哪些構建是精確 VLEN、哪些是通用 RVV”的邊界寫清楚：A210 的核心是定長向量、沒有 VIR，llc 對任何不小於 128 的 VLEN 都能降低，屬於通用構建；K3 的 prefill_ime 必須 1024，屬於精確 VLEN。這條邊界過去只存在於構建指令碼的註釋裡，現在有了執行期強制。

3.2 buddy-mlir：降低 VIR 時識別 RISC-V 宿主的 VLEN，修掉 riscv64 CI 自 #1030 起的位元級失敗（11-08）

日期：2026-11-08　來源：PR #1037、提交 79ffafd

同一人同日提交的第二筆，修的是另一個方向的錯誤。-lower-vir-to-vector 在不給 rvv-vlen、也不開可伸縮向量時，按宿主暫存器寬度給定長向量定尺，但它的宿主識別只覆蓋 x86（AVX2、AVX-512）與 SVE：帶 V 擴充套件的 RISC-V 宿主一律落到通用預設值（128 位、16 個暫存器），無論實際 VLEN 是多少。

後果出現在測試裡。自 #1030 起，kernels 流水線在沒有 llc 選項時按宿主降低 VIR，riscv64 CI 宿主是 VLEN 256，卻被當成 128 位處理：q、k 範數的平方被切成 vector<32xf32> 分段求和，與向量核心逐位元比較的順序不同，vir decode qk_norm ... same bits 判定為假。這個問題在 main 的每一次 riscv64 執行中都存在，x86（AVX-512）拿到的是 1024 的寬度，所以一直透過。作者先加了一筆只在測試裡固定 rvv-vlen=1024 use-scalable=false 的改動，隨即自行回退——那等於在 llc 選項之外再造一處 VLEN 設定，與 #1032 的方向衝突。最終修法是在降低階段識別 RISC-V 宿主（讀取宿主 CPU 特性與 hwprobe），按真實 VLEN 定尺，測試檔案換成宿主形態的新用例。

6.1 韌體線從單板走向多板：Unmatched 與 PXE 啟動指向的場景

6.2 精確 VLEN 特化的代價：靜默算錯比崩潰更難發現

日期：2026-11-08　來源：PR #1032、PR #1037

K3 的雙簇結構把 RISC-V 的 VLEN 問題攤開在同一臺機器上：A100 核心 VLEN 1024，X100 核心 VLEN 256，同一個可執行檔案在錯誤的簇上跑，不會崩，只會算錯。過去這個問題靠部署文件提醒（先寫 /proc/set_ai_thread），現在靠載入期校驗兜住。對一個交付模型的工具鏈來說，寧可啟動失敗也不要出錯誤結果——這是 #1032 的價值。

同日 #1037 從另一側證明同一件事：宿主定尺的預設值（128 位、16 個暫存器）在 x86 上恰好等價於大 VLEN，在 riscv64 上則改變了求和順序，逐位元比較立刻失敗。兩個補丁一個管構建期、一個管執行期，共同點是都不再假設“VLEN 由編譯器隨便定”。可伸縮向量（scalable vector）本來是 RVV 的標準答案，但在需要位元級復現的推理核心裡，精確 VLEN 仍然更划算；代價就是這類校驗必須跟著最終 llc 選項走，而不是跟著構建變數走。

6.3 週末視窗的分工：AI 棧靜默，打包與韌體推進
