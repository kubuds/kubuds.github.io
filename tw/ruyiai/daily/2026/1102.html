今日重點：Buddy Compiler 0.1.3 出正式版，十六筆提交裡十筆是 RVV 可伸縮向量化，釋出說明只寫了服務端 ABI（10-31）

日期：2026-10-31　來源：BUDDY MLIR 0.1.3、v0.1.2 與 v0.1.3 的提交差集、PR #999 rvv-vlen、PR #1003 scalable vector 寬度選擇

11-01 07:01（北京時間），buddy-mlir 釋出正式版 0.1.3，上一個正式版是 10-25 的 0.1.2，中間隔了五個夜間版。釋出說明只展開了一項內容：buddy-server 的新 ABI（#1015），即把按模態各寫一套的模型外掛控制代碼收斂成統一介面，外加統一的載入、狀態查詢、呼叫、流式與取消路徑。

但把 v0.1.2 與 v0.1.3 的提交差集拉出來看，這一版實際裝了十六筆提交、一百三十六個檔案，其中十筆是 [midend][VIR] 下一整段 RISC-V 向量化工作：

  • #999 引入 (rvv-vlen)，把可伸縮向量長度作為向量化目標屬性；
  • #1000 在巢狀迴圈裡統計活躍向量數，作為向量寬度選擇的輸入；
  • #1002 讓可伸縮 strip-mining 迴圈按 vscale 步進；
  • #1003 為 RVV 選擇可伸縮向量寬度；
  • #1004 把帶結果的 set_vl 降級成可伸縮向量；
  • #1005 處理 set_vl 中多維動態向量帶結果的情形；
  • #1006 新增動態向量行級 vir.shuffle；
  • #1007 統一 vir.load / vir.store 的索引約定；
  • #1008 自動推導索引向量的寬度；
  • #996 新增 vir.from_vector 並減少重結合。

另有二筆同屬 VIR 線但不在 [midend] 字首下：decode attention 的 VIR 方言實現（[frontend][tools]）與 VIR 的 Python 繫結（#1009）。也就是說，十六筆裡有十二筆動的是向量方言這一層，而發行說明一個字都沒提 RISC-V 或 RVV。

這個落差值得記一筆，因為它改變了「這份棧的 RISC-V 進展在哪裡」這個問題的答案。此前幾期的判斷是：buddy-mlir 的 RISC-V 工作主要走夜間版，正式版被 ABI 重構這類通用工作佔住，下游要拿到 RVV 改動只能錨夜間標籤。0.1.3 證明這條判斷只對了一半——正式版確實把 RVV 那一段收進來了，但版本說明沒有跟著更新，看釋出頁的人會以為 0.1.3 只是一次服務端重構，而實際拿到的是一個可伸縮向量化能力顯著前移的版本。

對下游的直接含義是：triton-riscv 在 10-31 13:15 把依賴錨點抬到了 nightly/v0.1.3.dev20261030（PR #91），這個夜間版的日期早於 0.1.3 正式版的出包時間，但兩者內容同源（0.1.3 從 10-29 的主分支頭部切出），所以 RVV 那十筆已經在下游生效；真正沒跟上的是「錨點仍寫夜間標籤」這件事——按現有的 renovate 節奏，切到 release/v0.1.3 還要再等一輪。

需要剋制的是覆蓋面：這十筆集中在 VIR 方言的可伸縮向量化，即從 set_vl 到 scalable vector 的降級鏈路，不是端到端模型效能資料；釋出說明裡也沒有給出任何基準。向量化能力前移是可核實的，能跑多快這一期沒有答案。

一、RuyiAI 棧進展（PyTorch / Triton / TileLang RISC-V 適配）

1.1 pytorch：riscv 分支 11-01 凌晨第二次整枝重放，基線仍停在 3afdbd3（11-01）

日期：2026-11-01　來源：pytorch riscv 分支、PR #51 riscv64 本地映象、PR #44 bytes_to_scalar 修正、開放 PR 列表

11-01 03:00，riscv 分支做了一次整枝重放：分支上二十筆提交的提交時間被統一改寫到 03:00:26 至 03:00:27 這一兩秒內，作者時間全部保持原樣。頭提交是 1867c9b8，資訊仍是 [SyncBots] Integrate PyTorch at 3afdbd3，而這筆同步提交本身的作者時間是 10-29 12:48——也就是說，這次重放沒有換基線，分支仍停在上游 3afdbd3，與 10-29 那次重放落點相同。

與 10-29 那次相比，差別只在形式：上一期是「七日靜默後重放 + 同步機器人補一筆依賴快取修正」，這一期是「三日後再重放一次、內容不動」。分支上的補丁集也沒有變化，仍是 Add riscv64 image locally (#51)、Fix bytes_to_scalar for float/complex on RISC-V (#44)、Scope linear cross entropy ULP tolerance to RISC-V (#42)、inductor opinfo blocklist (#50) 以及更早的 CI 與測試容差改動。

這種「基線不動、只改提交時間」的重放通常有兩種成因：一是重放到同一基線的不同修補順序上，用來消掉衝突標記或清理歷史；二是自動化任務按週期無條件重放。無論哪種，對本期的內容是零增量，值得記的只有節奏——兩週內兩次整枝重放，且都沒有伴隨新的上游同步。

需要留意的仍是那條錯位：分發側的 python-torch-ruyiai（openRuyi #1352）按分支產物構建，分支頭部每次重放都會換 SHA，包內鎖定的來源落點就得重新對齊；這一期沒有看到對齊動作。

1.2 llvm-project：riscv 分支 11-01 深夜重放，A100 的 IME/AME 下調在列（11-01）

日期：2026-11-01　來源：llvm-project riscv 分支、RISCV_CONTRIBUTING.md、重基工作流

11-01 23:00，riscv 分支同樣做了一次整枝重放，二十六筆分支自有提交的提交時間被統一改寫到 23:00:22 至 23:00:26。頭提交是 afdd0982，內容是 [workflows] Push rebased PRs directly and document contribution options（作者時間 10-29 01:59），即上一期記的那筆「取消預演、新增貢獻指南」的改動——它仍然是分支頭部，本期沒有更新的東西壓在上面。

分支裡與本棧最相關的仍是 A100 那兩筆：[RISCV] Lower IME intrinsics to SpacemiT A100 dot instructions (#30) 與 [RISCV] Add A100 HP/SP and pack/unpack lowering with calibrated scheduling (#31)。前者把 IME 內建函式降到 A100 的點積指令，後者補上 HP/SP 兩種精度形態的 pack/unpack 降級並帶校準後的排程模型；再往下一層是 [AME] Update BOSC AME instructions (#29) 與 [RISCV] Update xtame design (#27)，構成「AME 設計文件 → 指令定義 → 內建函式 → 降級與排程」的完整鏈路。這條鏈路服務於矩陣擴充套件，是 RuyiAI「從 RVV 到 Matrix」敘事在編譯器側的落點。

一處需要下一期複核的不一致：分支上最近一條 [SyncBots] Integrate LLVM at b3b5e33 的作者時間停在 09-29，但把當前頭提交與上一期頭提交做提交比較，返回的差集裡包含 10-30 的上游提交（如 [clang][AST] Don't give NestedNameSpecifier pointer identity in DynTypedNode (#233153)、[libc] Add truncation casts to avoid warnings in file_test.cpp (#237262)）。兩者放在一起只有一種解釋：這次重放在改寫歷史的同時把上游基線前移了，而同步機器人的記錄沒有隨之新增一條。同步記錄與實際基線脫節，會讓「這條分支基於哪個上游」這類判斷只能靠比較介面反推，建議後續在分支上補一條顯式的基線說明。

1.3 triton-riscv：兩筆合入、五筆新開，另有一筆重基到官方 Triton v3.8.0（10-30 至 11-01）

日期：2026-10-30 至 2026-11-01　來源：PR #55 asin 前端補丁、PR #91 依賴更新、PR #92 重基到 Triton v3.8.0、提交列表

真正的變化在 PR 佇列。maochuanjun 在 10-31 15:20 至 11-01 17:36 之間連開五筆，全部落在降級與分析兩層：

2.2 openRuyi 在審：Prometheus 依賴批次十三筆，box64 與 firecracker 補進佇列（10-30 至 11-01）

日期：2026-10-30 至 2026-11-01　來源：PR #1561 box64、PR #1559 firecracker、PR #1516 qemu-rustsbi、PR #1562 binutils RISC-V 測試跟蹤、PR #1547 至 #1557 Prometheus 批次

開放佇列在視窗內有二十四筆更新，規模比上一期大，結構化特徵也明顯：

最大一簇是 Prometheus v3.13 的模組依賴批次，共十三筆（#1540、#1441、#1547 至 #1557），全部由同一作者按 DAG 順序分批提交，標題統一為「Add Prometheus v3.13 modules - DAG dependency batch NN」。這種「把一張依賴圖切成十幾筆按層提交」的做法，在發行版裡通常是不得不為之——一次性提交會被審查者要求拆分，而按層拆又能保證每筆可獨立構建驗證。代價是合入視窗被拉長，任何一層卡住後面的都進不去。

第二簇是虛擬化與二進位制翻譯：#1561 新增 box64（在 RISC-V 上跑 x86-64 程式的動態重編譯器）、#1559 新增 firecracker（輕量微虛擬機器）、#1516 新增 qemu-rustsbi（RustSBI 作者 luojia65 提交，已有五條討論）。三筆疊起來看，指向的是同一類需求——在 RISC-V 桌面上跑非原生軟體與隔離負載。

第三類是與 RISC-V 直接相關的維護項：#1562 binutils: Track RISC-V pr19719 test failures，把 binutils 裡一個 RISC-V 相關的已知測試失敗登記成跟蹤項，而不是直接修。這種做法在發行版裡意味著「構建能過、測試不全綠」，對下游用 binutils 做連結的人是有用資訊。

其餘是三筆常規版本跟隨：#1563 把 Node.js 升到 26.13.0 並改用系統庫、#1544 把 firefox 升到 159、#1421 給 qemu 開啟一批 GUI 測試用的特性。

六、趨勢觀察

6.1 正式版的說明與程式碼差集脫節，RISC-V 進展被藏在提交歷史裡

0.1.3 這件事的方法論意義大於它本身：一個專案的「對外說明」與「實際裝進去的東西」如果長期不一致，外部對它的判斷就只能靠提交歷史反推。這一期的具體表現是，釋出說明只寫了服務端 ABI 重構，而十六筆提交裡十二筆動的是 VIR 向量層。

這種脫節有慣性代價。對下游而言，判斷「要不要升級」需要同時看 release notes、提交差集與依賴錨點三處；對上游而言，真正想被看見的工作沒有出現在該出現的頁面上——近三個月最成體系的向量化進展，在部落格、文件、發行說明三處都沒有對應描述。一個以「RVV 到 Matrix」為敘事的棧，把向量化進展寫成提交歷史裡的十行標題，是一種浪費。

更實際的風險在評審側：如果版本說明只覆蓋一部分改動，那麼複核者的注意力也會集中在那一部分，另一部分改動在「已經被裝進正式版」之後就不再有人回頭看了。

6.2 triton-riscv 從「修一筆合一筆」轉向「批次提審」，驗收側仍缺位

10-29 那三筆是「80 分鐘內連續合入」，本期五筆是「兩天內連續開出、尚未合入」。前者說明維護者對明確的缺陷修復有快速通道，後者說明新一批改動還沒走到那一步。兩種節奏之間的差別不在開發強度，而在評審頻寬。

這五筆加上 10-29 的三筆，三週裡累積八筆同類修復，全部指向降級路徑的資訊丟失。這個數量本身是訊號：說明這條路徑沒有建立起系統性的等價性檢查，只能靠逐個運算元撞、逐個撞完補。而對下游最有價值的一件事——把 FlagGems 那 604 個運算元的匯出做成每晚跑一次的常駐迴歸——仍然沒有做。PR #56 雖然從 09-16 的停滯裡恢復（10-30 20:50 有一次推送，規模已擴充套件到 156 個新檔案、匯出條目從 468 到 604），但它仍是開放狀態。

只要驗收還在 PR 裡而不在流水線裡，「這批運算元能不能在 riscv64 上跑通」這個問題就會反覆被推遲。

6.3 發行版側的月度承諾連續落空，棧級打包仍在 spec 層返工

十月的最後三天裡，兩條與「分發」直接相關的線同時錯過了視窗：ruyi 0.54.0 的「10 月底」口徑落空，openRuyi 的 2026.10 版本到 11-02 未發。兩條線的程式碼側都不算停——openRuyi 在 10-30 還有六筆提交，ruyi 有一筆文件合入——所以卡點在發版流程本身，而不在開發。

與此同時，棧級的三件套 #1350 已經跨過第六週，仍在 spec 規範層面返工。這三件事放在一起，指向同一個結構性問題：這個生態的「把東西做出來」與「把東西發出去」是兩套能力，前者在多個倉庫同時推進，後者在近兩個月裡沒有一次按期完成。

對 RuyiAI 而言，短期最實際的建議不是催發版，而是把 2.3 裡那三處非常規點（buddy-mlir 自帶 LLVM、triton 依賴 git、tilelang 需要工具鏈發現）寫成一份打包約定，讓 #1350 的複核不必每週重新討論同一批問題——把往返成本降下來，才談得上進入月度發行節奏。
