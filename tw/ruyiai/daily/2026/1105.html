今日重點：AME 後端把 i32 矩陣累加器固定在 AccReg，配置化 tile 操作延至展開前（11-04）

日期：2026-11-04　來源：提交 f346011、PR #35

11-04 15:40（北京時間），RuyiAI-Stack/llvm-project 的 riscv 分支新增一筆提交 f346011，改動 8 個檔案、+412/−1，作者 caihanyi111，合作者 caohanghang。改動物件是 RISC-V AME 矩陣擴充套件在 LLVM 裡的後端實現（程式碼中記作 BOSCAME），分兩塊。

第一塊是暫存器歸類。迴圈攜帶的累加器 PHI 從型別表取預設暫存器類，而 nxv32i32 原先只註冊為 TileReg；累加指令 mlce32.m、mqma.*、msce32.m 的累加器運算元與結果都限定在 AccReg，於是每條迴圈邊都要在 tile 與 accumulator 兩個暫存器堆之間生成一次複製，而 copyPhysReg 無法把這種跨堆複製展開成單條 AME 指令。修法是給 nxv32i32 同時註冊 AccReg；對同時啟用 V 擴充套件的目標，RVV 會重新註冊該型別，預設行為不變。同堆的整暫存器複製改用 mmve64.t.t 與 mmve64.a.a 展開；跨堆複製保留為硬錯誤，不再降級成按 lane 的索引搬移。

第二塊是排程。每份 tile 配置與其消費者被保持在一條有序、帶副作用的偽指令裡，直到 emit 前才展開；矩陣暫存器改為可分配，MMA 的累加器做 tie，零累加器的定義不讀舊值，分支鬆弛把完整展開後的尺寸計入。提交同時新增三份測試：配置化 load/MMA/store 的順序、獨立累加器與零值定義、RVV 與非 RVV 兩種選擇，以及放寬後的分支。

提交說明寫明瞭動機：上層 TTIR 到 BOSCAME 的降級要求歸約迴圈把 i32 累加器一直留在 AccReg。這條鏈路正是 tilelang-riscv 下來的矩陣運算元路徑，LLVM 側補的是暫存器分配與排程這一層，而不是新增指令。

3.2 雙週進展 080 草稿：glibc libmvec 與 newlib 向量數學補函式（11-04）

日期：2026-11-04　來源：080 期草稿、文章倉提交列表

RuyiSDK 微信文章倉 11-04 的更新裡，080 期草稿的「基礎元件」兩節已寫成。基礎 C 庫部分：glibc 把 sinpif、sqrt、sqrtf、tanf 移植進現有的 libmvec 框架；newlib 把 atanhf、atan2f、atanpif、atan2pif、exp2f、cosf、coshf、cospif、exp10f、expf、log2f、log2p1f、rsqrtf、expm1f 共 14 個函式移植進現有向量數學框架。

這批函式是 RVV 上做低精度推理與啟用計算的底座：向量數學庫缺函式時，運算元只能退回標量路徑，編譯器側的 RVV 降級再好也發揮不出來。草稿其餘章節（包管理器、IDE、GCC、LLVM、OpenJDK、Go、QEMU 等）尚為空。

3.3 arXiv：bf16/fp16 在 RVV 上自動向量化靜默降級（11-02，視窗外）

日期：2026-11-02（視窗外，近三日）　來源：arXiv 2611.03917

視窗內 arXiv 沒有新的 RISC-V 相關論文；近三日有一篇與 RVV 向量化直接相關的研究值得記錄。作者 Vaishnavi Kouru 與 Robert Chun 用 fp32、int8、bf16、fp16 四種精度的乘加迴圈對比 LLVM 的 RISC-V 自動向量化：在 -march=rv64gcv 這一共同基線下，int8 與 fp32 能幹淨地向量化，bf16 與 fp16 退化為大量標量回退，fp16 甚至退化成逐元素的軟體轉換呼叫，除非額外開啟 zvfbfmin/zvfbfwma 與 zvfhmin。

QEMU 使用者態下的動態指令數給出了量級：基線 bf16 與 fp16 核心執行的指令數分別是開啟擴充套件版本的 17.0 倍與 75.9 倍。論文同時指出編譯器診斷確實會報告這種退化，但措辭上不區分「加一個編譯選項就能解決」與「固有轉換成本」，使用者拿不到指向修法的直接訊號。對 RuyiAI 棧來說，這與 080 期補向量數學函式是同一問題的兩端：一端缺庫函式，一端缺特性開關的可見性。

四、Buddy Compiler 動態

4.1 VIR 的 set_vl 語義收緊：精確 VLEN 與任意 VLEN 分成兩條路徑（11-04 至 11-05）

日期：2026-11-04 至 11-05　來源：PR #1028、合併提交 dd57775、PR #1029、合併提交 61ba191

zhanghb97 的兩筆 PR 在視窗內先後合入，把 VIR 方言裡 set_vl 的語義講清楚了。

#1028（11-04 23:54 合入）讓 rvv-vlen 表示目標的精確 VLEN：vscale = rvv-vlen / 64，一個 vector<[N]xT> 持有 N 乘 vscale 條 lane，切分按完整向量做。此前 rvv-vlen 被當作最小 VLEN，掩碼全部為真卻仍留在程式碼裡——llc 保留 vid 與 vmslt，訪存帶著掩碼，RoPE 的 rotate_half 變成 slides 加掩碼選擇，解碼注意力裡掩碼還發生了溢位。K3 上的核心按 1024 位向量寬度構建，正是這一路徑的典型場景。

#1029（11-05 01:32 合入）處理不給 rvv-vlen 的通用構建：此時程式碼必須對任意 VLEN 成立，strip-mined 區域按 N 乘 vscale 在執行時步進，向量按最小的 128 位定尺寸；帶結果的 set_vl 會被直接拒絕，報「需要 rvv-vlen，即精確 VLEN」，而這個 pass 以前只是報錯。固定向量在無 rvv-vlen 時保持原樣，按主機定尺寸；不允許宣告高於 128 的最小 VLEN。

兩筆合起來的含義是：語義不再靠“掩碼碰巧全真”兜底，編譯期就要說明這份程式碼是為某個確定 VLEN 編的，還是為任意 VLEN 編的。

4.2 CI：pytorch 2.15 進測試矩陣，LLVM 發行開 NVPTX/AMDGPU 與 lld（11-04）

日期：2026-11-04　來源：PR #1026、PR #1027、PR #1025

#1026 把 pytorch 2.15 加入測試矩陣，覆蓋 2.11 到 2.15。引發改動的是一個真實迴歸：在 2.15 下最新的 full check 在 tests/Python/AtenOps/test_resize_enlarge.py 處失敗，且失敗發生在 importer 之前——AOT autograd 的 functionalization 現在拒絕在已函式化的張量上放大 resize_，torch.compile 在同一函式上也失敗，圖根本到不了 ResizeOp。改法是把測試換成 out-of-place 的 aten.resize，走同一個 ResizeOp handler，產出同樣的 MLIR，2.11 到 2.15 全矩陣透過。

#1027 讓 CI 釋出的 LLVM 帶上 NVPTX/AMDGPU 目標並啟用 lld；#1025 把 LLVM 升到 bef335e2143c。三筆都是基礎設施，但 #1026 記錄的這個迴歸值得留意：上游對 functionalization 的收緊會以“圖到不了後端”的形式出現，而不是後端報錯。

六、趨勢觀察

6.1 後端先行，前端與執行時靜止

日期：2026-11-05　來源：llvm-project riscv 分支、buddy-mlir 提交列表

這一天的增量都落在“編譯與降級”：LLVM 的 AME 後端補暫存器歸類與 tile 排程，buddy-mlir 的 VIR 把 set_vl 的 VLEN 語義收緊。與此同時，pytorch、triton-riscv、tilelang-riscv 三個前端倉全部零提交。棧的推進集中在把已有的運算元穩定地降到底層，而不是接入新的前端能力。

6.2 打包側的日常維護與發版停滯並存

日期：2026-11-05　來源：openRuyi 提交列表、ruyi Release 列表

openRuyi 一天十筆提交，內容是 firefox、expat 與四個 Python 包，加上 CI 簽名方式與工作流容器化的試驗（其中容器化當日回退）；ruyi 與 packages-index 零提交，2026.10 月度版仍缺位。發行版的日常維護在走，面向 AI 棧的發版沒有走。上一期把這種狀態概括為“卡點在釋出不在開發”，本期在發行版側仍然成立。

6.3 向量數學的補強先出現在文稿裡

日期：2026-11-05　來源：080 期草稿、VecIntrinBench

080 期草稿裡最實的內容是 glibc libmvec 與 newlib 的向量數學函式移植，而對應的基準與轉譯倉庫（VecIntrinBench、IntrinTrans）仍是靜默。這說明底層庫的向量化工作在推進，但它沒有以提交的形式出現在 RuyiAI-Stack 的重點倉裡——RuyiSDK 的基礎元件線（GCC、glibc、newlib、V8）與 RuyiAI 棧的重點倉並不是同一批人、同一批倉庫。下期值得對照兩邊的節奏。
