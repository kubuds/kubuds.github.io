今日重點：triton-riscv 合入 Triton 3.9.0 外掛化改造，補丁集清零、獨立發行包退場（11-05）

日期：2026-11-05　來源：PR #98、提交列表、PR #92

11-05 11:13（北京時間），trdthg 的 PR #98「Bump Triton to main (3.9.0)」合入：5 筆提交、66 個檔案、新增 1806 行、刪除 3868 行。刪除量約為新增量的兩倍，這決定了這次改造的性質——它不是在既有分支上再加一層補丁，而是把打補丁這種做法整體刪掉。

第一處變化是後端形態。Triton 的 TRITON_PLUGIN_DIRS 機制把 backend/ 裝成 triton_shared 後端外掛，註冊入口點、把 C++ 外掛鏈進 libtriton.so、把 triton-shared-opt 一併複製進包。獨立的 triton-riscv 發行包隨之消失，程式碼裡的匯入統一改走這個外掛名。後端自身改為透過 paths.py 查詢 buddy-opt、buddy-llc、mir-translate 與 triton-shared-opt；CPU 驅動宣告自己僅在沒有任何 GPU 後端時才處於活動狀態。

第二處變化是補丁集清零。patches/ 目錄與施加補丁的指令碼全部刪除。補丁集此前存在的理由有兩個：讓 Triton 在沒有 NVIDIA/AMD 工具鏈的環境裡構建，以及兜住 LLVM API 的頻繁變動。現在 buddy-mlir 的 LLVM 發行版帶 NVPTX/AMDGPU 目標與 lld，再把 Triton 的 GPU 依賴路徑指向一個 stub 目錄，兩個理由都不成立，補丁集也就不再有存在價值。

第三處變化是出包路徑合併。release.sh 不再組裝第二個 wheel：Triton 的外掛支援已經把後端與 triton-shared-opt 放進 Triton 的 wheel 裡，指令碼只剝掉工具、直接 bdist_wheel。Makefile 成為 setup、build、test、lit、clean 的統一入口，test 依賴 lit。

代價寫在同一個 PR 的提交說明裡。Triton 3.9 的前端會從後端讀取 backend_name 等欄位，缺了它每個 tl.atomic_* 呼叫都會拋 AttributeError，riscv64 上有 383 個 FlagGems 用例因此失敗。這次補上 backend_name、default_dot_input_precision 與 deprecated_fp8_dot_operand_dtypes 三個欄位，失敗面才收掉。示例側也有讓步：上游拒收了 asin/acos/atan/atan2 的前端補丁，例子改用 libdevice，靠它降到同樣的 __nv_* extern_elementwise，再由 triton-shared 轉成 MLIR math 運算元。

同一路徑上的 PR #92「Rebase integration onto the official Triton v3.8.0 release」當日以未合併關閉。上一期記錄的兩條路線之爭（#92 求穩到 3.8.0、#98 跟進 3.9.0 主線）至此收斂到後者。

一、RuyiAI 棧進展（PyTorch / Triton / TileLang RISC-V 適配）

1.1 triton-riscv：構建入口收斂到 Makefile，後端按外掛目錄裝進 Triton 包（11-05）

日期：2026-11-05　來源：提交列表、PR #98

外掛化之後，後端在 Triton 包內的匯入路徑是 triton.backends.triton_shared。這套東西的安裝面比之前窄：不再有兩個發行包，也不再假設旁邊有一份 buddy-mlir 檢出。文件裡關於“兩個包”的敘述、補丁步驟與同級檢出假設一併刪除，setup.py 裡 shutil.which("lit") 會優先取 pip 安裝的 lit 控制檯指令碼，而不是 LLVM 發行版自帶的那個。後者呼叫 main() 時沒有 if __name__ == "__main__" 保護，而 Python 3.14 的 forkserver 多程序在匯入主模組時會重跑它，lit 目標在 80 併發下因此失敗。

後端查詢本地工具的路徑也改了：buddy-opt、buddy-llc、mir-translate、triton-shared-opt 統一由 paths.py 解析。CPU 驅動的活動判定是“沒有 GPU 後端在場”，這與之前靠環境變數判斷的做法不同，在多後端共存的機器上行為更可預期。

1.2 triton-riscv：發版節奏改為每日 nightly、週末 release，pytest 併發定在 16（11-05）

日期：2026-11-05　來源：PR #99、Release 列表

PR #99 把發版節奏對齊 buddy-mlir：夜間任務釋出 nightly/<date>-<sha> 預釋出，週末任務釋出 release/<date>-<sha> 並標記為最新版本；沒有新提交時跳過，release 在所有 wheel 上傳完成前保持草稿狀態，workflow_dispatch 提供一次帶外的 dev/patch 選擇。當日兩筆夜間版已按此節奏產出：nightly/20261105-48bde12（19:50）與 nightly/20261105-849a180（22:48）。

測試側把 pytest 套件改成 16 程序。選這個數字有實測依據：在 207 個用例的切片上，1 程序 360 秒、8 程序 89 秒、16 程序 67 秒、24 程序 67 秒，32 與 64 反而更慢——單個用例是“編譯、triton-shared-opt、llc、執行、比對”的序列鏈，程序再多就爭用共享編譯快取。此前序列跑時，flaggems 套件要 1 小時 14 分。setup.sh 會安裝 pytest-xdist，可用 PYTEST_WORKERS 覆蓋。

1.3 triton-riscv：stable ABI wheel 覆蓋 3.12 至 3.15，修 manylinux 工具鏈探測（11-05）

日期：2026-11-05　來源：PR #100、PR #101

PR #100 按上游 Triton 的 cp312-abi3 做法構建 wheel：scripts/env.sh 與 scripts/release.sh 設定 TRITON_STABLE_ABI=ON，用受限 API（Py_LIMITED_API=0x030C0000）編譯 nanobind，setup.py 把 wheel 標記為 cp312-abi3。一個 wheel 覆蓋 3.12 之後的所有直譯器（3.12/3.13/3.14/3.15），釋出矩陣從三個 Python 減到一個。原始碼保持未打補丁——上游本身就提供這個開關。

同一分支還修了兩處構建指令碼問題。其一是 release.sh 硬編碼 /opt/rh/gcc-toolset-14/enable 且在 dnf install clang 之前檢查它，而 manylinux 映象是滾動更新的 :latest，當時已經帶 gcc-toolset-15，導致啟用指令碼從不執行，clang 找不到 crtbeginS.o、-lstdc++、-lgcc（riscv64）與 libstdc++ 的 <version> 頭（x64），兩個架構都構建失敗；現在先裝 clang，再按存在性啟用全部工具鏈、最新的放最後。其二是隻有一個 abi3 wheel 之後，矩陣裡 python: ["3.12", "3.13", "3.14"] 只會把同一個 wheel 重複構建三遍。PR #101 當日開出、仍未合併，處理釋出工作流在檢出清理階段的失敗。

3.1 LLVM：六筆 P-ext 與 XTHeadBb 上游 PR 合入，Ztt 矩陣擴充套件 v0.6 初版落地（11-05）

日期：2026-11-05　來源：080 期文稿、LLVM PR 235306、LLVM PR 237815

080 期列出的上游合入共六筆，集中在打包 SIMD 與位操作：P 擴充套件把更多 pm*add* 加後續加法的模式合成 pm*adda* 類指令（#235306），改進 RV32 上 64 位 funnel shift 的程式碼生成（#235245），新增帶擴寬水平加法的打包乘累加 intrinsics（#234450），併為 Clang 補上打包位元組水平乘累加 intrinsics 的有符號、無符號與混合符號三種形式（#234484）；GlobalISel 側在 XTHeadBb 下先擴寬窄型別的 G_CTLZ_ZERO_POISON（#237815）、把 G_CTTZ 擴寬到 XLEN 後再走 G_CTLZ 以選出 th.ff1（#238214）。

RuyiSDK 的 LLVM 分支另有兩筆：基於 Ztt 規範與 intrinsics 文件 v0.6 初步支援 RV32/RV64 矩陣擴充套件，涵蓋彙編與反彙編、Clang 型別與 intrinsics、LLVM IR 與程式碼生成，以及 M/ACC 暫存器分配、複製與溢位處理（#169）；為 AME 分支增加 GitHub Actions CI，自動構建 RISC-V 目標的 LLVM/Clang 並跑 CodeGen、彙編與語義測試（#170）。

3.2 GCC：Zba/Zbs/Zbkb 三項最佳化進入主線，啟動 SPEC CPU 2026 評測準備（11-05）

日期：2026-11-05　來源：080 期文稿、GCC Zba 提交

三項 RISC-V 後端最佳化已於 10 月 27 日進入 GCC 開發主線（r17-5638 至 r17-5640）：Zba 側完善移位加法與整數除法、取餘的組合識別；Zbs 側利用 bclr 自身的移位索引語義消掉多餘掩碼計算，改進 RV32/RV64 點陣圖操作；Zbkb 側修正 packh 的成本模型與匹配優先順序，解決 Zbb 與 Zbkb 同時啟用時選不到更優指令的問題。

配套的工具鏈 CI 也有進展：RISE-CI 打通了 Hertner 容器服務與 GitHub Actions，新增 multilib 構建場景檢查，後續計劃接入 LLM 對 CI 報錯做評估與分析。效能側啟動基於 SPEC CPU 2026 的 RISC-V 真實硬體評測準備，已識別出候選 K3 平臺跑完整 SPECspeed 2026 的記憶體瓶頸，正在評估其他硬體方案。

四、Buddy Compiler 動態

4.1 runtime 新增共享 serving 生成控制器，支撐裝置側取詞（11-05）

日期：2026-11-05　來源：PR #1018、提交 c2fd2e1

PR #1018 新增一個與模型無關的 serving 生成控制器，18 個檔案、新增 2045 行，讓執行時介面卡共享同一套生成 token 預算、停止條件、用量記賬與流式清理。呼叫方既可以走 LLMSession 的宿主取樣，也可以走裝置側直接給出 token 的 token 源。

實現上有幾處值得記：字串停止條件先按原始位元組匹配、再做 UTF-8 解碼，避免多位元組邊界誤判；token 預算把首個預測與 EOS/停止 token 都計入；固定隨機種子支援零值；重複懲罰在請求的歷史視窗內按 token ID 去重後各施加一次。首個 token 來自 prefill，因此吞吐統計把首次選擇記到 prefill、後續選擇記到 decode，零 decode 工作時報告零吞吐。原有 CLI 與服務端入口的生成路徑保持不變，用固定 logits 與生產環境的 DeepSeek 分詞器、取樣器做黃金測試保護輸出。後續介面卡接入分別跟蹤在 DeepSeek R1（#1021）、Llama 3.1 TTNN（#1022）與 Qwen3-VL 等條目上。

4.2 VIR 可伸縮向量 lowering 補片：廣播改走 vector<[2]xT>、核心按 llc 選項降級（11-05）

日期：2026-11-05　來源：PR #1030、PR #1031

兩筆 midend 改動都針對可伸縮向量。vir.shuffle 的 lowering 拆成若干段：廣播先經 vector<[2]xT> 再取前半（vector.scalable.extract）得到 vector<[1]xT>，因為直接對 vector<[1]xT> 做 vector.broadcast 時 LLVM 會生成掩碼 [0] 的 shufflevector，被 createOrFold 當成恆等操作摺疊掉，剩下的 vscale-1 個 lane 全是 poison；llc 會把 insertelement 變成只寫 lane 0 的 vfmv.s.f，一旦這個值不併入 .vf 指令而是存進暫存器，結果就錯了。改走 [2]xT 後 llc 用 vfmv.v.f 在 [1]xT 的 LMUL 上完成廣播，指令數不增，迴圈裡還少一條。另一筆讓核心按 llc 的 -mattr 等選項降級，測試 vir-broadcast-scalable-one.mlir 覆蓋剝離與 set_vl 帶結果兩條路徑。

六、趨勢觀察

6.1 從維護分支到寄居上游：外掛化把補丁成本換成版本繫結

日期：2026-11-05　來源：PR #98、PR #92

triton-riscv 用一天時間把自己從“維護一份打了補丁的 Triton 分支”改成“上游 Triton 的一個外掛”，淨刪兩千餘行，補丁目錄整個消失。這種做法的收益很直接：以後跟隨上游升版不再需要重放補丁，出包只剩一個 wheel，安裝面從兩個發行包降到一個。

代價同樣明確，而且是同一天暴露的：Triton 3.9 的前端從後端讀一個 backend_name 欄位，缺它就有 383 個 FlagGems 用例失敗。寄生在上游擴充套件點意味著上游前端的隱式契約變成了必須滿足的介面，而這些契約往往沒有文件，只能在測試裡撞出來。判斷這次改造是否成功，不看今天刪了多少行，看下一次上游升版時重放的成本，以及 FlagGems 這類下游套件是否還需要專人盯版本。

6.3 080 期的增量落在編譯器與執行時，不在應用層前端

日期：2026-11-05　來源：080 期文稿

080 期最實的四條都在底層：GCC 三項 Zb* 最佳化進主線、LLVM 六筆 P-ext 與 XTHeadBb 合入、OpenJDK 的 JEP 544 AOT 移植合入、V8 的向量尾部與 VLEN 處理。應用層前端（PyTorch、TileLang）本期沒有對應的能力接入。
