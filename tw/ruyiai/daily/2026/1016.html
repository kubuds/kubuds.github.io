日期：2026-10-15　來源：Ruyi Firmware 20261015 釋出、edk2-ruyi：系統資訊頁提交 a8ea1ac6、edk2-ruyi：SPI 模擬開關提交 5581e304、edk2-ruyi：ARM64 GOP 1.68 提交 c13cf98c、coreboot：A100-only 中斷修復 7b1ac324、ruyifirmware：raw SPI 刷寫文件 6aece1c0

openRuyi 韌體打包倉庫 ruyifirmware 於 10-15 釋出第三期韌體「Ruyi Firmware 20261015」（前兩期為 10-13、10-14），本視窗完整覆蓋。本期兩條主線：一是視覺化與資訊面——UEFI 設定新增只讀「System Information」頁，覆蓋 CPU、記憶體、PCIe 裝置與鏈路速率、儲存詳情；SMBIOS 同步報告 DRAM 型別、部件號與配置速率；PCI 顯示卡提前初始化並修復開啟 Setup 時的圖形控制檯重入問題；IMG GPU 核心頻率固定為 1228.8 MHz。二是 UEFI 驅動模擬——x64 與 ARM64 驅動模擬同時納入 DEBUG 與 RELEASE 包（預設關閉），CPU 模式與模擬開關併入 Platform Settings，選擇儲存在 SPI 專用扇區（帶 CRC 與回讀校驗）、重啟後生效；併為列名的早期 GCN、Polaris、Vega M 顯示卡接入實驗性 AMD ARM64 GOP 1.68（其餘裝置仍用板載 x64 GOP，替換失敗不回退）。修復側：A100-only 模式中斷對映（coreboot 同源修復：S 態中斷表限制到 A100 hart 並移位 IMSIC/SSWI 暫存器視窗）；首次安裝文件改用 raw SPI 刷寫。

五、趨勢觀察

5.1 K3 韌體「可配置 + 可模擬」並行推進：驅動模擬的啟用策略與外設相容觀察

K3 韌體進入第三個釋出日，能力面從「CPU 模式可選」疊加「UEFI 驅動可模擬」：x64 與 ARM64 模擬預設關閉、經 Platform Settings 啟用並持久化，AMD ARM64 GOP 1.68 以實驗名義試點覆蓋早期 GCN / Polaris / Vega M 顯示卡，替換失敗不回退的設定意味著這是一條偏保守的相容路徑。觀察點：其一，模擬層在真實混合負載下的穩定性與效能代價；其二，可模擬驅動與裝置清單的擴充套件節奏（顯示卡以外是否覆蓋網絡卡、儲存等）；其三，與 openRuyi 映象、核心 ruyi/7.3.y 顯示補丁（DP 與 GPU 電源域）的協同交付方式。

5.2 兩條 fork 維護線節奏差異：PyTorch 重建按日延續，LLVM 重放第三視窗未續

PyTorch riscv 分支保持約每 24 小時一輪重建（本輪 23 筆、8 筆 PR 同步重新整理；較上輪頭部共 101 筆差異含上游併入），自動化節奏穩定；LLVM riscv 分支則在 10-12 之後連續第三個視窗未見隔夜重放，兩條 fork 的維護節奏出現明顯分野。觀察點：LLVM 重放是否迴歸，以及其與 ruyisdk 側 llvm-project 維護線（XTHeadVector 相關工作）的分工是否生變。

5.3 核心與發行版維護面擴張：ruyi/7.3.y 開局、安全批次與玄鐵鍵名統一

核心樹上，openRuyi linux 新開 ruyi/7.3.y 並在視窗內落下 31 筆（K3 外設、顯示與 SG2044 遷移重放為主），與 7.2.y 形成並行維護；linux-xuantie-kernel 把廠商擴充套件鍵統一為 XUANTIE 形態——命名與品牌層面的收束利於 hwprobe 與工具鏈側的一致引用。發行版側，openRuyi 同日落 5 個安全包（cups / nltk / capstone / llama-cpp / multipath-tools），CVE 響應趨於批次化。觀察點：7.3.y 何時進入映象釋出通道、安全批次的釋出頻率是否穩定。
