今日重點：buddy-mlir 修 VLEN 1024 上的歸約丟車道，二十五項測試從錯到對（11-11）

日期：2026-11-11　來源：PR #1051

PR #1051 在 11-11 23:51（北京時間）合入，修的是一個只在長向量硬體上現形的錯誤：對寬度為 1 的可伸縮向量做 vir.reduce，結果只留下 lane 0。成因不在 VIR 自己的規範化，而在下游——vector.reduction 的 ElideSingleElementReduction 把 vector<[1]xT> 當成”只有一個元素”的向量，改寫成 vector.extract 取 lane 0 再與累加器合併，其餘 vscale - 1 條車道就此消失。

觸發條件是 VLEN 1024：一個 16 個 f32 的區域在一塊向量裡就是 vector<[1]xf32>（vscale 16），而 VLEN 128 與 256 上它是 vector<[4]xf32> 及更寬，走不到這條路徑。作者在 SpacemiT K3 的 A100 核上實測，25 項歸約測試全部給出錯值，例如 512 個值的 amax 得 1.853 而非 4.101；同一批測試在 CI 的 riscv64 runner（VLEN 256）上是透過的。這正是此類缺陷難被發現的原因：CI 的向量寬度覆蓋不到出貨硬體的寬度。

修法繞開規範化，直接用 vector.reduction 最終會降到的 LLVM intrinsics 構造歸約——浮點用 llvm.vector.reduce.fadd 並以累加器作起始值，fmax 則接 maxnum 與累加器，vir.reduce 的兩條 lowering 都改。作者註明這是與 splat 的 broadcastTo 相同的繞行手法。配套測試進 tests/Conversion 下的 VIR 用例，check-buddy 在 x86（用 main 的 LLVM）與 SG2044 原生兩側透過。

對這條棧的意義：Triton-RISCV 在 K3 上的歸約運算元（amax、max、mean、sum、cumsum、rms_norm、mse_loss、vector_norm、euclidean_dist、attention）此前在這塊板子上是靜默錯值，不是崩潰。修完才有資格談效能。

三、向量擴充套件與運算元最佳化

3.1 strip-mined set_vl 的車道餘量按半寬逐級降低，K3 上 YOLOv8 的熱點從標量點積裡出來（11-11）

日期：2026-11-11　來源：PR #1050

#1050 在 11-11 20:12 合入。此前一個被 strip-mine 的 vir.set_vl 只按選定寬度跑主迴圈，剩下的車道全丟進標量尾迴圈；車道數不足一個向量的區域更是整段標量。在 K3 的 A100 核（VLEN 1024）上跑 f32 YOLOv8，姿態頭的 51 個輸出通道得到 64 車道的向量，結果是最熱的那個迴圈（佔整模 5% 時間）是一段標量 flw 加 fmadd.s 的點積，perf 採 15 萬樣本里標量浮點指令佔了 39%。

改法是讓主迴圈之後的車道依次降到半寬、四分之一寬，每一檔最多用一次且按車道順序，最後才交給標量尾迴圈，尾迴圈只留不足最小寬度（定長 2 車道、可伸縮 [1]）的部分。沒有掩碼：可伸縮向量在執行期用 scf.if 判餘量，定長向量在 vl 為常量時編譯期判掉，這樣仿射尾迴圈的邊界仍是仿射的；vl 動態時保留標量尾。

數值不變——每條車道算的還是同樣的運算，有序歸約看到的車道順序也沒變，作者用 K3 上前向輸出的 FNV 雜湊驗證了同一位。這條修的是效能，不是正確性，但換來的是長向量硬體上最熱那段程式碼終於走向量單元。

3.2 向量三倉仍靜默，向量側的增量全在 VIR 層（11-12 狀態）

日期：2026-11-12（狀態）　來源：VecIntrinBench、IntrinTrans、FBGEMM

三個向量相關倉頭提交仍停在 02-13、06-25、07-13，數月沒有動靜。這不等於向量側無人做事：本視窗的兩筆 buddy-mlir 改動（歸約的車道處理與 strip-mined 餘量降寬）都直接決定生成什麼向量指令，度量工具與轉譯器兩倉的靜默，說明投入仍集中在編譯器而非基準。

日期：2026-11-11　來源：PR #1048

本視窗 buddy-mlir 的三筆裡，兩筆的實測環境都是 SpacemiT K3 的 A100 核（VLEN 1024），其中 #1051 明確寫著問題由 Triton-RISCV 在該核上暴露。同一時期，RuyiSDK 雙週進展記 V8 合入 “Allow vlen=1024”，triton-riscv 在 K3 上跑 ROCm 的驗證也是上一期的事。三條彼此獨立的線在同一個引數上匯合，說明 1024 位向量已是這條棧出貨形態的預設前提，而 CI 常見的 128 與 256 位不再是足夠的測試面。

六、趨勢觀察

6.1 釋出鏈先於功能：triton-riscv 這一週修的是”能不能出包”

視窗內 triton-riscv 三筆合入裡兩筆是 CI 與釋出指令碼，一筆是 README 的安裝前提，功能面零改動；夜間版自己的說明文字也在講 runner 上的 git 認證。這不是停滯，而是把一個剛從”能跑真機”升級到”預設啟用 GPU 後端”的專案補上可復現性：自託管 riscv64 runner 的匿名 git 流量拿不到認證，看起來是基礎設施小事，實際決定夜間包是否每天都能出來。

對照 RuyiSDK 那側就清楚：包管理器能把 ABI 相容性做成安裝前的告警，是因為它的釋出鏈已經穩到可以做這種精細活。triton-riscv 正在走同一條路，只是晚了幾步。

6.2 VLEN 1024 正在成為編譯器與執行時的共同壓力點

一天之內三處獨立證據指向同一個引數：buddy-mlir 的歸約丟車道只在 VLEN 1024 上現形（VLEN 128 與 256 都對），strip-mined 餘量降寬的動因來自 K3 A100 核上 64 車道的向量，V8 的審閱名單裡出現 “Allow vlen=1024”。此前這類討論停在架構引數層面，現在落到”哪條測試在什麼寬度上會錯”。

對測試面的直接要求是覆蓋出貨寬度：原 CI 的 riscv64 runner 是 VLEN 256，恰好在 #1051 的問題上透過。這條教訓比修好的那幾行程式碼更值錢——凡是與 vscale 相關的推理，都得在 1024 上驗一遍。

6.3 雙週進展的草稿日與上線日差六天，讀它的條目要分開看

080 期 11-05 就在倉裡成形，11-11 才發到論壇。於是同一份文字里，0.54.0 與 Imager 1.1.0 是”已釋出”（11-10 的事），外掛 0.1.7 也是”已釋出”（09-28 的事，之後還有 10-30 的 0.1.8-beta.1）。如果按上線日通讀，很容易把三款工具當成同一天的三連發。

可行的讀法是分兩層：工具版本看 Release 時間，編譯器與執行時條目看上游合入時間（GCC 那三項寫的是 10-27）。日報這邊已按這個口徑拆分，讀者對照雙週進展時也宜如此。
