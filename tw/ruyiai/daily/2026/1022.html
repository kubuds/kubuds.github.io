今日重點：IREE 主幹落下 RVV f16 乘加 MMA，LLVM riscv 分支八日靜默後換基重寫

日期：2026-10-21　來源：IREE 提交 e7490c3b、IREE PR #25000、LLVM riscv 分支提交列表、兩輪頭部對比

IREE 在 10-21 16:48 把 RISC-V V 的 f16 inner_tiled MMA 下降併入主幹（PR #25000，946 行改動，其中測試 800 餘行）。這是 10-19 釋出的 v3.13.0 裡 f32 vfmacc.vf 那條路徑之後的第二級精度：原生 f16 列舉已在前序提交落主幹，本次補上下降與加寬兩條通路——f16 乘 f16 得 f16 走 vfmacc.vf，f16 乘 f16 得 f32 走 vfwmacc.vf；只有 +zvfhmin 時分別退化為「累加器擴到 f32 做 vfmacc 再截回」與「兩面板擴到 f32 做 vfmacc」。Tile N 取 vlen/8，VLEN=256 下代價模型把三條路徑分別計為 14、7、6。

效能資料給出了比「已支援」更有用的資訊：在 X60（VLEN=256）上，單執行緒 inner_tiled 在原生 f16 與 vfwmacc 兩種編碼下已經快於 mmt4d ukernel；4 執行緒與 8 執行緒的大形狀仍然偏慢。也就是說單核上的指令選擇已經到位，剩下的差距在分塊與執行緒化，這條跟蹤項是 #24932。

同一天 RuyiAI 自己的 LLVM 分支結束了八日靜默。昨日報告把「LLVM 分支是否隨新上游基線重啟」列為觀察點，本視窗給出了答案：riscv 分支於 10-21 23:00 整枝重寫，head 由 0fb2da86 變為 dd05e5b5，SyncBots 把上游整合推進到 b3b5e33，與舊 head 對比為 diverged（領先 1769、落後 26、300 檔案差異）。分支內的補丁序列完整保留：BOSC AME 擴充套件（#16）、Buckyball 廠商擴充套件（#20）、與 Pebble 核 ISA 對齊（#23）、AME 路徑設計（#24）、xtame 設計更新（#27）、AME 指令更新（#29）、IME 內建到 SpacemiT A100 dot 指令（#30）、A100 HP/SP 與 pack/unpack 排程（#31、#32）。結論要說清楚：這是一次換基重放，不是新補丁；兩筆 FPGA PR（#25、#28）在 10-22 00:59 同批重新整理了時間戳，仍停在開放狀態。

把兩件事並排放，今日的資訊是「上游在往前走、本地在等評審」：IREE 側 f32 到 f16 的精度臺階兩天走完一級，RuyiAI 側的編譯器補丁則靠換基維持可用，評審佇列的消化速度仍是這條鏈路的實際節拍器。

三、向量擴充套件與運算元最佳化

3.1 IREE：RVV f16 vfmacc 與 vfwmacc 及 Zvfhmin 回退落主幹（10-21）

日期：2026-10-21　來源：提交 e7490c3b、PR #25000、效能跟蹤 #24932、f32 版本 PR #24933

本次提交為 RISC-V V 的 f16 inner_tiled MMA 補上下降路徑，複用 #24933 引入的 lowerRiscvVFmaccLike 與上提的累加器合法化，Tile N 取 vlen/8。編碼選擇按擴充套件可用性分三層：f16 乘 f16 得 f16 且帶 +zvfh 時用 vfmacc.vf；f16 乘 f16 得 f32 時用加寬的 vfwmacc.vf；只有 +zvfhmin 時兩條路徑分別走「累加器 extf 到 f32、f32 vfmacc、truncf 回」與「兩面板 extf 後 f32 vfmacc」。當兩層都合法時按列舉先後取原生路徑。VLEN=256 下代價模型給出 intrinsics_m 14（原生）、7（vfwmacc）、6（兩條 zvfhmin 回退）。

六、趨勢觀察

6.1 依賴閉包進入收口期：Go 從「去 vendor」轉向「補匯入路徑」

前三期的補包線索是分頭鋪開的：Python 補 fsspec 雲端儲存全家、Rust 補 crate 閉包、Go 起步去 vendor。本期 Go 側 51 筆的重心明顯後移——先補基礎依賴（etree、yaml、gnostic、tabwriter 等十筆），再補 k8s 三件套與 moby-sys、smarty-assertions 的匯入路徑，最後才落 sonobuoy、umoci、go-mtree 三筆真正的「build without vendored dependencies」。

順序本身說明去 vendor 的完成條件不是刪掉 vendor 目錄，而是讓每個被依賴模組在發行版裡能按原匯入路徑解析；缺了匯入路徑的補齊，刪 vendor 只會直接編譯失敗。因此「補匯入路徑」才是這一輪的最後一公里。對 RISC-V 使用者的直接含義是：容器映象工具與一致性測試工具從「隨原始碼打包」變成「按發行版依賴打包」，構建可復現性與安全更新的傳導路徑同時改善，後續 CVE 只需升級單個 Go 模組，不必重建整包。

6.2 兩個 riscv 分支同日整枝重寫：重放已成常態運維，評審仍是瓶頸

本期 pytorch 與 llvm-project 的 riscv 分支在同一天各做了一次整枝重寫：pytorch 在 03:00（連續第三日），llvm 在 23:00（八日靜默後換基）。共同特徵是提交者時間統一改寫、補丁標題集合不變、SHA 每日失效；差異在節奏——pytorch 是日更基線，llvm 是擇期換基，換基後與舊 head 的差異達 300 檔案，幾乎全部來自新上游。

這種做法的工程意義是把「跟上游」與「維護本地補丁」解耦，代價是歷史不可追溯。任何按 SHA 引用的下游（映象構建、CI 快取、issue 復現）都會每天或每次換基後失效，讀這兩個分支應以補丁標題集合而非 SHA 作版本判據。更值得注意的是本視窗補丁本身沒有新增：pytorch 七筆開放 PR 只重新整理時間戳，llvm 兩筆 FPGA PR 同樣只重新整理時間戳。重放機制已經穩固，實際節拍器變成了評審佇列的消化速度。

6.3 RVV 後端先補 f16 再談吞吐：IREE 的精度覆蓋次序給出的訊號

把 10-19 的 f32 vfmacc.vf（v3.13.0）與 10-21 的 f16 vfmacc/vfwmacc（#25000）連起來看，IREE 在 RISC-V V 的 inner_tiled MMA 路徑上兩天走完一級精度臺階，且兩次都複用同一個 lowerRiscvVFmaccLike 與同一套累加器合法化。次序是先保證有正確路徑（f32），再按擴充套件可用性挑最快的一條（f16 原生、f16 加寬、+zvfhmin 回退），代價模型對三條路徑分別定價。

X60 上的實測把瓶頸位置說清楚了：單執行緒已快於 mmt4d ukernel，4 執行緒與 8 執行緒仍慢，說明單核指令選擇到位之後，剩下的是分塊與執行緒化。對 tilelang-riscv 與 triton-riscv 來說，這是可逐條對照的路線圖——Tile N = vlen/8 的取法與代價模型的分檔方式，都值得在自家 lowering 裡做同口徑比較，而不是隻看「是否支援 f16」。
