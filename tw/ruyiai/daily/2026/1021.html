三、向量擴充套件與運算元最佳化

3.1 IREE 3.13.0 正式版：RISC-V V f32 vfmacc.vf MMA 進入 release（10-19）

日期：2026-10-19　來源：IREE v3.13.0 Release、PR #24933 RISC-V V inner_tiled MMA

IREE v3.13.0 於 10-19 19:26 釋出，CPU 後端新增 RISC-V V f32 vfmacc.vf 的 inner_tiled MMA（PR #24933），把向量浮點乘加直接對映到 RISC-V V 的 fused multiply-accumulate；同時 LLVMCPU 的可伸縮向量化改為必須指定 --iree-llvmcpu-vscale-range，帶 +zvl*b 特性時取兩個下界中的較大值。模型側保留 PT2E 的 per-tensor、per-channel-group、per-token 量化匯入到 LinalgExt Q/DQ。

對本棧的意義在路徑對照：RuyiAI 的 tilelang-riscv 與 triton-riscv 走的是 Tile 級 DSL 到 RVV 的路線，IREE 走 MLIR→LLVMCPU 可伸縮向量化。同一條 RVV 上，兩種前端同時把 f32 乘加選為最佳化目標，說明該指令形態已成為 RISC-V AI 後端的共識落點。

3.2 驗證與快取側：riscv-arch-test 三筆合入、香山 CoupledL2 分組儲存體（10-19 至 10-20）

日期：2026-10-19 至 2026-10-20　來源：riscv-arch-test PR #2413 Sdtrig、PR #2791 S_F/S_V/S_VF、PR #2858 向量指令 SEW 覆蓋、XSCache PR #36、XiangShan PR #6738

RISC-V 架構測試視窗內合入三筆：Sdtrig 的 A 擴充套件觸發器覆蓋點與 Sm/S/U 三模式 icount 覆蓋（10-20 05:53）、向 S 套件新增 S_F/S_V/S_VF 以覆蓋作業系統實際使用的特權層級（10-20 02:53）、向量指令擴充套件到所有有效 SEW 並補齊 SEW=8 的 vrgatherei16 與 fault-only-first 的 LMUL 選擇（10-19 21:55）。三筆共同把驗證面推向「S 模式 + 全 SEW」，對在 K1/K3 上跑 RVV 運算元的團隊是可用的迴歸基線。

六、趨勢觀察

6.1 依賴閉包建設按語言分三線並行：Rust 補 uv 後端、Go 去 vendor、Python 補雲端儲存

本期 137 筆提交的 42/42/42 結構不是巧合，而是三條獨立的補包線同日推進：Rust 側圍繞 windows-* 0.61、zerocopy/rkyv、cap-std/io-lifetimes 三族，配合 python-uv-build，指向 uv 這類 Python 構建工具的 Rust 依賴；Go 側以 minio 與 Prometheus/Kubernetes 元件為主，配合去 vendor 的三筆 PR 把「隨原始碼打包」改成「按依賴打包」；Python 側一次性補齊 fsspec 的全部主流雲後端。三條線的共同目標是把依賴閉包填滿，讓 RISC-V 上的 Python AI 與雲原生部署不必現場編譯。

值得記錄的是這一層與 RuyiAI 的關係：PyTorch 的 DataLoader、checkpoint、資料集工具普遍經 fsspec 訪問遠端儲存，後端齊備與否直接決定訓練指令碼能否在 K1/K3 上跑通。發行版替上層補的這部分依賴，比單個運算元最佳化更能決定「能不能用」。

6.2 PyTorch 分支進入每日重放節奏：基線日更，補丁序列不動

連續兩日觀察到同一模式：10-19 09:14 與 10-20 08:32 各一次整枝重寫推送，全分支提交者時間被統一改寫，本地補丁標題逐條不變，變化只在上游基線的同步範圍。這種做法把「跟上游」與「維護補丁」解耦，代價是分支歷史不可追溯——任何按 SHA 引用的下游（CI 快取、映象構建、issue 復現）都會每天失效。若這一節奏固定下來，讀取該分支時應以「補丁標題集合」而非 SHA 作為版本判據。

同期三條 fork 線的狀態繼續分化：PyTorch 每日重放、LLVM 自 10-12 起八日靜默、Triton 夜間出包恢復到 10-19 一版後停住。三條線對應三種投入狀態，也提示 RuyiAI 棧當前的瓶頸不在編譯後端本身，而在評審與出包的持續供能。

6.3 伺服器級平臺給發行版帶來的是相容清單，而非新的移植任務

進迭 V100 的報道把 openRuyi 寫進伺服器平臺的可用發行版清單。若這條成立，含義並非「openRuyi 要做一次新的移植」，而是一套規範符合性要求：RVA23、伺服器 SoC/平臺規範、BRS 與安全模型五項，加上 UEFI/ACPI/SMBIOS 的韌體鏈路。發行版要做的更多是把已有的使用者態包、安裝器與映象鏈路對齊到規範，而不是重寫元件。

當前證據仍不完整：openRuyi 主倉當日零筆伺服器相關提交，韌體線（ruyifirmware、edk2-ruyi）自 10-15 起靜默，2026.10 版本尚未釋出。觀察點有三個：openRuyi 2026.10 是否在釋出說明中提及伺服器平臺；ruyifirmware/edk2-ruyi 是否恢復針對 V100 的提交；支援矩陣是否出現 V100 條目。
