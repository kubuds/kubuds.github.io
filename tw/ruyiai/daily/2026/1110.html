今日重點：triton-riscv 出第一個正式釋出標籤，安裝路徑從原始碼改為 wheel（11-09）

日期：2026-11-09　來源：釋出標籤 release/20261108-6895885、PR #105、PR #107

11-09 06:59（北京時間）打出的 release/20261108-6895885 是這個倉的第一個正式釋出標籤：此前十八個標籤全部是 nightly/ 字首，倉裡從來沒有 release/ 這一層。釋出物兩個 wheel，分別是 x86_64（manylinux_2_27 與 2_28）與 riscv64（manylinux_2_39），統一 cp312-abi3，版本串 triton-3.9.0。

標籤指向提交 6895885，也就是 11-06 那筆”為 AMD 補 codegen 庫”（#102）的合入提交，與夜間版 nightly/20261106-6895885 是同一個點。當天三筆提交（#105、#106、#107）都在標籤之後落地，沒有進這個包。這意味著”第一個正式版”打的其實是上週末的程式碼狀態，釋出動作本身是這個標籤的全部內容。

與標籤同日的 #105 重寫了 README，把安裝段從原始碼優先改成 wheel 優先：先給 wheel 路徑與承載它的包索引，再給它們所需的 LLVM 歸檔與一個指向變數；原始碼路徑壓縮成 make setup（建 .venv、克隆固定版 Triton、下載固定版 LLVM 與 buddy 構建），原先那段”建虛擬環境、裝依賴、環境指令碼十五個變數”的說明收成一條短注。

快速開始也換了寫法：不再只列印 ok: True，而是把核心編到 riscv64-unknown-linux-gnu，保留目標檔案並 grep 反彙編，列印後端生成的 vsetivli、vle32.v、vfadd.vv、vse32.v。對一個編譯器專案來說，這比一句斷言更能說明”後端真的出了向量指令”。

夜間版另加了唯一版本字尾 .dev<日期>：此前每次構建共用 Triton 自己的版本號，包索引會拒絕重複版本。wheel 的釋出動作放在 wheel job 內部，避免重複下載產物，並以 PYPI 系列金鑰存在為條件、在包索引側尚未就緒時繼續執行而不失敗。

#107 隨後做了修正：包索引目前還沒有 triton 與 buddy 工具，README 裡那條二進位制安裝給出的地址會失敗，於是改為指向兩個專案各自的 GitHub releases、從磁碟裝 wheel，並寫明 LLVM 壓縮包的來源。同一筆提交還修了 Python 3.14 的 lit 崩潰。

今日重點：buddy-mlir 把整張 f32 YOLOv8 圖降到 VIR，K3 上輸出逐位元組一致（11-10）

日期：2026-11-09（合入於 11-10 01:07 北京時間）　來源：PR #1041、合入提交 18c66ec

PR #1041 把 #1042 的 f32 YOLOv8 圖端到端走通 VIR：先做 Linalg 到 VIR 的降低，再做 VIR 到向量方言的降低。此前這條 pass 裡沒有卷積 pattern，圖裡另有三類運算元直接失敗——一筆改動同時補上了卷積與那三類。

規模是十四個檔案、新增一千六百四十六行、刪除一百一十五行、十三個提交。作者 zhanghb97，11-09 08:57 開出，當晚合入。

卷積兩族都覆蓋：二維 NHWC 配 HWCF 與二維 NHWC 配 FHWC。向量化沿輸出通道 F 展開（輸出與 HWCF 過濾器的最後一維），對每個 (kh, kw, c) 把輸入元素廣播成每個輸出畫素一個 vir.fma，因此每次向量訪問都是連續的，也沒有跨 lane 的歸約。FHWC 過濾器先並行複製進 HWCF 緩衝；輸出行放進 scf.parallel，每行一個 F lane 的 vir.set_vl。

三類此前失敗的運算元一併補齊。一是 rank-0 輸入：memref 直接進 linalg.generic 會在 memref.expand_shape 報 invalid reassociation，改為載入一次後廣播。二是保留末維的 linalg.reduce，例如 DFL softmax 的 1x16x4x2100、dimensions=[1]、addf 與 maximumf 組合，改為沿末維向量化、被歸約維上的切片逐元素合併，不生成 vir.reduce。三是讀取 linalg.index 的命名運算元，例如上取樣裡的 linalg.map iota，補上與同類 linalg.generic 相同的標量迴圈。

真機口徑很清楚：在 K3 上，f32 YOLOv8 pose 的原始輸出最多變化 6e-5，與 PyTorch 的差距仍在 6e-4（bus）與 8e-4（zidane）以內，與改動前一致；detect 模型的檢測結果不變，速度沒有下降；f32 與 IME 動態庫的輸出與改動前逐位元組相同。

一、RuyiAI 棧進展（PyTorch / Triton / TileLang RISC-V 適配）

1.1 triton-riscv：換成 torch 2.15.0 後 flaggems 七個用例失敗，改為防禦式讀取（11-09）

日期：2026-11-09　來源：PR #106、提交 cfdf4f7

riscv64 的 CI 裝的是索引裡帶的 torch，最新的 2.15.0 一來，flaggems 套件裡七個用例失敗。修完的結果是三千八百二十六項透過、兩項跳過。

五例 median 的問題出在名字張量：median.py 實現了 torch 的命名張量支援，而 2.15.0 這個構建沒有 Tensor.names，判空函式在核心還沒執行前就拋 AttributeError。改法是防禦式讀取該屬性，把沒有這個 API 的構建當作”無名字”，這與現有檢查對”名字全為 None 的張量”給出的答案一致。作者也說明了為什麼不能直接刪掉這段程式碼：上游 flaggems 仍然無保護地呼叫 names，且命名張量在更早的 torch 版本里確實存在。

兩例 sinh 的 fp16 用例原先按相對與絕對誤差各 1e-4 比較，fp16 達不到（實測相對差 6.6e-4），fp32 保留 1e-4。同時把 torch 2.10 從 riscv64 的安裝裡去掉，重新跟隨索引。對一條跟著上游 torch 走的 CI 來說，這類維護是無法外包的成本：上游一變，套件就要重新對齊。

1.2 triton-riscv：Python 3.14 下 lit 崩潰，CI 改為優先用 pip 裝的 lit（11-09）

日期：2026-11-09　來源：PR #107、提交 209274f

紅的是 CI 裡 Python 3.14 那個任務。Triton 用 which 在 PATH 裡找 lit，而 LLVM 樹裡那份 lit 在模組級呼叫 main，Python 3.14 在 Linux 上預設改用 forkserver 啟動方式，重新匯入時直接崩潰。

修法很輕：把構建直譯器的 bin 目錄放到 PATH 最前，查詢就會先命中 pip 裝的那份 lit。這與 1.1 同屬”CI 跟著上游跑”之後的收尾，也解釋了為什麼三筆提交裡有兩筆是環境而不是編譯器。

三、向量擴充套件與運算元最佳化

3.1 buddy-mlir：卷積沿輸出通道向量化，FHWC 過濾器先轉成 HWCF（11-10）

日期：2026-11-09（合入於 11-10 01:07 北京時間）　來源：PR #1041、合入提交 18c66ec

卷積的降低策略值得單獨看，因為它決定了後面所有調優的空間。選擇是沿輸出通道 F 向量化，而不是沿輸入通道 C 做歸約：對每個 (kh, kw, c)，把一個輸入元素廣播成每個輸出畫素一個 vir.fma。

直接好處是每次向量訪存都連續，且沒有跨 lane 的歸約——歸約需要橫向指令與後續的規約樹，在窄 VLEN 上代價明顯。代價是過濾器佈局必須匹配：FHWC 排列的過濾器要先並行複製進 HWCF 緩衝，多一次搬運，換來內層迴圈的連續訪問。

輸出行用 scf.parallel，每行一個 F lane 的 vir.set_vl。此前的 VIR 到向量降低對動態向量的前導靜態維發序列 affine.for，而並行化 pass 穿不過 vector.load，這次改成 scf.parallel，條件是記憶體訪問允許。另外，每個輸出畫素佔一個迭代的做法保留在 Linalg 到 VIR 的降低裡，”多次迭代共享一次向量載入”由後端在帶結果的向量設定內自行合併，把暫存器決策留給目標。

3.2 buddy-mlir：補齊 rank-0 輸入、保留末維的 reduce 與讀 linalg.index 的運算元（11-10）

日期：2026-11-09（合入於 11-10 01:07 北京時間）　來源：PR #1041、合入提交 18c66ec

三類失敗運算元各有各的坑。rank-0 輸入（單元素 memref 直接進 linalg.generic）會在形狀展開處報無效重關聯，現在改為載入一次再廣播。

保留末維的 reduce 更容易被忽略：DFL softmax 的 1x16x4x2100、dimensions=[1]、組合子 addf 與 maximumf，原來的 pass 直接報錯。新做法是沿末維向量化、把被歸約維上的切片逐元素合併，不生成 vir.reduce；此前能降的那些形態保持不變。

第三類是讀 linalg.index 的命名運算元，例如上取樣裡的 linalg.map iota。命名運算元沒有泛型 op 的 body 可抄，過去被跳過，現在給它補上與同類 linalg.generic 相同的標量迴圈。

四、Buddy Compiler 動態

4.1 評審收斂的三處：並行行記憶體依賴、FMA 舍入、reduce 分派（11-10）

日期：2026-11-09（合入於 11-10 01:07 北京時間）　來源：PR #1041

三處評審意見都變成了程式碼改動。並行行的記憶體依賴：行之間沒有 SSA 依賴，但可能有記憶體依賴，於是只在能證明各行訪存互相獨立時才用 scf.parallel——每個寫都是 vir.store 且存的向量帶這些行；被寫元素互不重疊（單位佈局，或 stride 全為靜態並按 stride 排序後互相巢狀）；凡可能與被寫 memref 重疊的訪問都必須用同樣的基址、下標與秩。不滿足就退回序列 affine.for。新增的測試檔案覆蓋四種情形：可並行、跨行共享標量讀寫、stride 為 0 的 memref、讀取另一行正在寫的資料。

FMA 這條更細：VIR 到向量的降低在主迴圈裡把 vir.fma 降成向量 fma，尾部迴圈裡卻拆成乘法加加法，同一個 op 在向量 lane 與尾部 lane 上給出不同舍入。測試用 a 等於 1 加 2 的負 23 次方、b 等於 1 減 2 的負 23 次方、c 等於負 1 這一組，向量 lane 得負 2 的負 46 次方、尾部 lane 得 0。現在尾部改用 math.fma，兩邊一致，測試同時檢查兩側。這個改動會讓尾部 lane 有舍入級差異，K3 上 f32 YOLOv8 的輸出變化上限就是前面那個 6e-5。

reduce 的分派條件也收窄了：判定函式與舊實現實際支援的情形完全對齊（元素型別 f32、組合子 addf 或 maxnumf、各秩對應的維度等），避免把不該走快路徑的 reduce 也吞進去。

日期：2026-11-10（狀態）　來源：PR #1035、PR #1038、PR #1039、PR #1040

六、趨勢觀察

6.1 這一輪補的是交付鏈路，不是運算元

三筆 triton-riscv 提交裡，兩筆是安裝與測試鏈路（README 改為 wheel 優先、flaggems 跟上新 torch），一筆是 CI 的 Python 3.14 相容，沒有一筆動編譯器本身。加上週日那個第一個正式釋出標籤，這一天的主題是”讓人能裝上、能裝對”。

這種輪次在任何專案裡都會出現，但容易被誤讀為沒有進展。實際上從原始碼安裝到 wheel 安裝，是從”開發者能編”到”使用者能裝”的分界：原始碼路徑要求使用者自己準備 LLVM、buddy 構建與幾十個環境變數，wheel 路徑只要一條命令。對 RISC-V 這種長期靠”自己編”的生態，這一步的邊際價值高於再最佳化一個運算元。

6.2 逐位元組一致正在成為 VIR 降低的驗收標準

11-08 的兩筆改動用載入期校驗攔住 VLEN 不符、讓宿主定尺按真實 VLEN 走，今天的 #1041 又把”f32 與 IME 動態庫輸出與改動前逐位元組相同”寫進驗證口徑。三筆改動指向同一個標準：降低可以換實現，但不能改數值。

這個標準比”精度在容差內”更嚴格，也更適合編譯器：容差能掩蓋順序錯誤，逐位元組比較不能。代價是每次改動都要有一份可復現的基線，而 K3 這種雙核心（兩個簇的 VLEN 不同）的機器恰好提供了最難的基線。

6.3 桌面棧與安全更新接管了打包節奏

六十五筆提交裡，四十筆是 KDE Plasma 6.8.2、七筆是 Python 安全更新，其餘是 Wayland、wget2 與 llvm 繫結一類的零散升版。AI 棧這一天只有四筆提交，發行版側卻有六十多筆。

這個比例說明 openRuyi 當前的瓶頸在跟上游，而不是造新東西：桌面與語言執行時的上游版本一放，打包倉就要在一兩天內全部跟上；而 AI 棧的節奏圍繞模型與工具鏈，按周甚至按版本走。
