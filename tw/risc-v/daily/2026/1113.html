今日重點：達摩院玄鐵釋出 XL-300 吞吐型互聯 IP，8 核非同步連線配 32MB 可配 L3（11-12）

IT之家 11 月 12 日上午報道，阿里巴巴達摩院旗下 RISC-V 品牌玄鐵（XuanTie）釋出高吞吐快取一致性互聯 IP 設計 XL-300。報道給出的規格是：最多支援 8 個核心的非同步連線，資料位寬 256bit，L3 Cache 最大可配置到 32MB，8 核併發線性度達到 90% 以上，頻寬上限相比前代 XL-200 提升約一倍。新增的 Direct Memory Transfer 支援被單獨點出，作用是繞過傳統路徑，突破大容量 L3 與高匯流排延遲帶來的吞吐瓶頸。驅動之家、鳳凰網科技、新浪科技與搜狐在同日轉載了同一條訊息，內容一致，均為 IT之家口徑。

這條訊息的分量不在單點引數，而在「互聯 IP」這個位置。RISC-V 這幾年在單核效能、向量與矩陣擴充套件上的進展是可驗證的，但要把多顆核拼成一顆可用的 SoC，拼的是快取一致性協議、跨核頻寬與延遲、L3 的容量與分割槽策略——這部分過去是 Arm 與 x86 生態靠多年迭代堆出來的護城河，也是國內 RISC-V 伺服器晶片最容易在矽後暴露問題的地方。玄鐵把 XL-300 的三個指標擺在最前面（8 核非同步連線、32MB L3、90% 線性度），指向的正是「多核能不能真的跑出多核效能」這個最樸素的問題。8 核併發線性度 90% 意味著第 8 顆核帶來的邊際收益仍有第一顆核的九成，這個數字比峰值頻寬更能說明一致性協議與匯流排仲裁的實際水平。

需要把時間線擺清楚，避免把舊產品讀成新品。XL-300 並非首次露面：今年 3 月一篇 C930 深度解析文章裡，玄鐵技術負責人已經把它列為與旗艦伺服器核 C930 搭配的最強互聯 IP，當時給出的口徑是單 Cluster 最多 8 核、L3 最大 23MB、相比 XL-200 頻率提升 20% 且頻寬翻倍、面積僅增加 5%。再往前，2025 年 2 月的玄鐵生態大會上，XL200 還只是「將提供更大規模、更高效能的多簇一致性互聯」的研發計劃。也就是說，XL-300 的定位是 C930 這一代伺服器級 IP 的配套互聯，本期報道帶來的是更完整的對外規格披露。

兩處口徑差異值得記下來。其一，L3 容量：3 月的說法是最大 23MB，本期報道是 32MB。二者可能是不同配置檔位（單 Cluster 與多 Cluster、或不同工藝庫下的 SRAM 容量），也可能是規格隨迭代上調，官方尚未釋出可核對的規格書，本刊按兩條獨立口徑並列記錄，不取其中一條覆蓋另一條。其二，本期報道用「釋出」而非「量產」或「授權落地」，與 3 月「已與 C930 配套」的表述並不矛盾——IP 的對外發布、客戶授權與矽上驗證是三個不同階段，報道本身沒有披露授權客戶數量。

對產業觀察者，更有價值的問題是這條線接下來往哪走。玄鐵的 XT-Link 系列從 2024 年 7 月的 XL100（首款快取一致性多 Cluster 互聯，8 至 32 核擴充套件、支援大小核）走到 XL200、再到 XL300，節奏大致是一年一代，每一代的著力點從「能不能連」轉向「連得多快」再到「大 L3 下的吞吐效率」。這條路徑與 C930 的 SPECint2006 15/GHz 級別單核效能是配套關係：單核越強，對互聯的頻寬與一致性要求越高，否則多核只是把瓶頸從執行單元挪到匯流排上。國內做伺服器與高效能 SoC 的團隊若採用玄鐵核，互聯 IP 的可選範圍與授權條件，實際決定了他們能不能做出 32 核以上的機型。

一、開源社群與軟體生態

香山昆明湖 V3 三筆：ROB 拆分功能與除錯緩衝、FP 發射佇列接入 topdown 計數器、BJU 補 isRVC 後設資料（11-12）

香山昆明湖 V3 分支在視窗內落地三筆，分屬三個方向。第一筆是重排序緩衝（ROB）的結構治理：此前 ROB 為每個槽位無條件儲存一份完整的入隊 uop，放在 debug_microOp 欄位裡；名字雖為除錯，異常處理與 VLS 處理也在讀它，導致正常 RTL 依賴了一個只該用於除錯的結構。改動引入 RobSlotInfo，只保留正常 RTL 真正需要的三個欄位（commitType、fuType、fuOpType）存入 slotUopBuf，把除錯用的整份複製剝離出去。這類改動的收益不在週期數，而在面積、時序與後續擴充套件成本：一份多餘的寬位向量在 ROB 裡躺了若干代，每加一個欄位都要跟著放大。

第二筆是把浮點發射佇列與 ROB 的 topdown 計數器接通：把浮點發射活動與佇列狀態報給 topdown 採集器，包含發射取消的來源；整數與浮點發射佇列的狀態一併喂進 ROB 頭部分類，浮點已發射 uop 計入發射計數；取消來源歷史按所有編碼來源分配長度，並只在 ROB 頭被歸類為發射取消時更新取消時間。第三筆是修復：JumpUnit 在預測錯誤或後端故障時建立後端重定向，但把重定向 bundle 清零，沒有把 io.in.bits.ctrl.isRVC 賦給 redirect.isRVC，結果壓縮跳轉指令（如 c.jr）的後端重定向裡 isRVC 被清成 false，影響後續對指令長度的判斷。

三筆連起來看是一次典型的「結構治理 + 可觀測性補齊」組合。topdown 計數器的意義在於把「流水線為什麼空轉」從經驗判斷變成可歸因的資料：前端取指不足、後端發射阻塞、還是 ROB 滿導致的停頓，各自有獨立計數。對香山這類要跑 SPEC 與真實負載的開源核，能不能快速定位瓶頸決定了迭代速度；而 ROB 拆分與 isRVC 修復這類工作不產生任何效能數字，卻直接決定加新特性時的改動半徑。

openRuyi 五筆：LLVM 23 升 23.1.5，雙核心補丁與配置重新整理，gcab 與 OVMF 的 fwupd 支援入樹（11-12）

openRuyi 主倉在視窗內落地五筆，全部集中在 SPECS 目錄，時間跨度從上午 9 點 13 分到 11 點 27 分。第一筆把 llvm23 升到 23.1.5，這是本月內 LLVM 23 分支的又一次補丁級跟進。隨後兩筆由同一位提交者完成，分別重新整理 linux 與 linux-lts 的補丁集與配置——注意是「refreshing patchset」與「refresh config」兩件事一起做，意味著下游維護的那批 RISC-V 補丁要跟著新基線重排，同時核心配置項也要重新對齊；這種成對重新整理往往發生在核心穩定版小版本更新之後，是發行版保持可編譯的必要動作。

第四筆新增 gcab 軟體包。gcab 是 GNOME 陣營的 Cabinet 檔案（.cab）讀寫工具，本身很小，但它出現在依賴鏈上通常意味著某個上層元件需要處理韌體或驅動包。第五筆正好印證：ovmf 增加對 fwupd 的支援。fwupd 是 Linux 上的韌體更新守護程序，走到 OVMF（UEFI 韌體）這一層，說明 openRuyi 在把「韌體可更新」做成發行版能力，而不是讓使用者手工刷寫。對 RISC-V 平臺這是一條容易被忽略但很實際的需求：板卡廠商的韌體釋出節奏與發行版不同步，有 fwupd 通道才能在不重灌系統的前提下推 BIOS 與韌體修復。

把五筆放在一起看，openRuyi 這個視窗沒有釋出新版本，也沒有大功能，做的是「把上游基線跟住、把韌體更新鏈路補齊」。這與它 10 月兩篇公告（Ruyi Firmware 提供開放 UEFI 韌體方案、生態基礎設施定位）是一條線上的延續：韌體方案講的是「怎麼開放地啟動」，fwupd 支援講的是「啟動之後怎麼持續修」。

difftest 兩筆：映象解碼與 RAM 載入分離、gsim 構建去掉 tee 管道（11-12）

difftest 倉庫視窗內兩筆改動都在工程層。第一筆把映象的解碼與 RAM 載入兩個步驟分開：此前載入一個映象時，解析格式與寫入記憶體耦合在同一段邏輯裡，改動引入獨立的解碼階段，讓「讀得懂映象」與「裝得進記憶體」各自可測、可替換。對差分測試框架，這類解耦的價值在於新增映象格式時不必碰記憶體佈局程式碼，反之調整記憶體模型也不影響格式解析。

第二筆修復的是一個很容易被忽略的構建陷阱：gsim 的生成規則裡寫了 gsim-gen-cpp ... | tee gsim-gen-cpp.log，而 Make 預設沒有設定 -o pipefail，管道的退出碼取的是 tee 的狀態，永遠是 0。結果是 gsim-gen-cpp 因 bug 或 OOM 被殺掉時，make 仍然繼續呼叫 gsim-gen-emu，最後以一個令人費解的 SimTop.h not found 報錯收場。改動直接刪掉內部 tee，理由寫得很清楚：verilator.mk 沒有這麼做，使用者想留日誌可以自己在命令列外層加管道。這是那種「修一次省掉後來每個人半小時」的提交。

樂鑫 22 倉批次推送：模組庫、影片與語音元件、晶片 errata 同批更新（11-12）

樂鑫（espressif）在視窗內有 22 個倉庫出現推送，是整個視窗內組織級推送最密集的一家。清單可以分成幾類：主機側與雲側有 esp-hosted-linux、esp-cloud-common；晶片配套有 esp-chip-errata、esp-phy-lib、esp-coex-lib、esp-hal-3rdparty、usb-pids；無線與藍芽模組庫有 esp32s31-bt-lib、esp32h4-bt-lib；多媒體有 esp-video-components、esp-vision、esp-gmf；框架與工具有 esp-matter、esptool-js、idf-eclipse-plugin、esp-board-manager、esp-idf-security-dashboard、homebrew-eim；另有 esp-claw（2379 星）、esp-ptp、developer-portal、musl。

這類同日多倉推送在樂鑫身上是常態，屬釋出列車與上游同步，本刊不逐條拆分。值得留意的是媒體與藍芽兩條支線仍在擴：esp-video-components、esp-vision 與 esp-gmf 三個倉同時動，說明端側視覺與音訊鏈路還在補元件；esp32s31-bt-lib 與 esp32h4-bt-lib 出現在同一批，則是新晶片配套庫在跟進。對用 ESP32-C 系列（C2/C3/C5/C6/C61，RISC-V 核心）做產品的團隊，這些庫的更新節奏基本決定了新模組能不能第一時間拿到可用韌體。

二、產品與生態動態

Start9 推出 RISC-V 路由器：進迭時空 K1 八核、StartWRT 發行版、300 美元（11-12）

開源軟硬體廠商 Start9 在 11 月 12 日正式釋出其 RISC-V 路由器，與深度數智（DeepComputing）聯合打造，主控是進迭時空 K1（八核 64 位 RISC-V），執行基於 OpenWrt 的 StartWRT 發行版，定價 300 美元（約合人民幣 2006 元），隨附一臺 TP-Link 四口交換機。硬體配置為 4GB LPDDR4 記憶體、16GB eMMC 儲存，無線走一塊可更換的 miniPCIe 模組（AsiaRF AW7916-NPD，Wi-Fi 6E，2.4GHz 與 5GHz 併發，外接天線），外部介面為 1 個千兆 WAN、1 個千兆 LAN、2 個 USB 3.0 Type-A、1 個 USB-C 與 microSD 讀卡器。

Start9 官方頁面把「開放到什麼程度」寫得很細，這一點比引數更有參考價值。公開的部分包括：RISC-V 指令集本身、這塊板所衍生的 K1 參考原理圖（已隨文件釋出）、啟動棧 OpenSBI 與 U-Boot、Linux 核心與 mt76 無線驅動、以及 MIT 許可的 StartWRT；不開放的部分也點名了——無線射頻韌體（廠商不提供開源韌體，模組可拆、拆了照樣能跑），以及上電時執行一次的兩段早期二進位制（DRAM 初始化與一階段引導），後者正在替換中。這種「把不能開源的部位逐個列出來」的做法，在開源硬體產品裡比籠統宣稱「完全開源」更有可信度。

產品定位也值得說明：這臺路由器的賣點不是吞吐，而是「每個裝置走哪條隧道由你決定」——按配置檔案分流、可串聯兩家 VPN 使單一供應商無法同時掌握身份與去向、每套配置獨立指定 DoH 解析、網路層做裝置隔離。這類需求過去由 x86 小主機加 OpenWrt 承擔，功耗與體積都不理想；換成八核 RISC-V 之後，把家用閘道器、私有云入口與網路隔離做進一臺低功耗盒子成為可行選項。對進迭時空，這是 K1 在消費級網路裝置上的一個整機級落地案例，也說明 K1 的軟體棧（OpenSBI/U-Boot/核心/發行版）已經能支撐第三方做完整產品，而不只是開發板。

五、總結與趨勢觀察

一、互聯 IP 從配角變成 RISC-V 伺服器化的主線。 玄鐵 XL-300 這一期披露的規格里，最能說明問題的不是 32MB L3，而是「8 核併發線性度 90% 以上」——這是一條只有真正跑過多核負載才敢給的指標。單核效能靠微架構，多核效能靠一致性與匯流排；國內 RISC-V 在單核上已經能用 SPECint2006 15/GHz 這個量級對話，接下來兩三年的勝負手會落在多核擴充套件效率與矽後穩定性上。XL100 到 XL300 一年一代的節奏，說明這條線被當作產品在做，而不是一次性交付。

二、整機落地正在從開發板轉向消費品。 Start9 的 RISC-V 路由器 300 美元、八核 K1、把「哪些開源哪些不開源」逐項寫明，這是一個成熟硬體產品的寫法；SingNova 把 12 核 RISC-V 加資料流做成能接 128 路攝像頭的桌面盒子，同樣是整機思路。兩者共同點是軟體棧自己維護（StartWRT、自研資料流執行時），不再依賴某塊 x86 主機。RISC-V 要證明的不是「能跑 Linux」，而是「能撐起一臺要賣給普通使用者或整合商的裝置」。

三、開源硬體這條支線在往「可審計」走。 Baochip-1x 用 22nm、RV32IMAC、公開 RTL 與 RRAM 換「每顆電晶體都能交代清楚」，市場很小但需求真實。它與高效能伺服器路線不衝突，反而補上了 RISC-V 敘事裡最容易缺的一塊：在安全審查與供應鏈追溯日益嚴格的場景，能讀到 RTL 比跑分高更值錢。

四、工具鏈與工程衛生成為這一天的暗線。 difftest 去掉一個 | tee 讓構建失敗不再偽裝成 SimTop.h not found，香山把除錯用的 uop 複製從正常 RTL 裡剝離，進迭給漏發的版本補上手動通道，openRuyi 把韌體更新接進 fwupd——四件事都不產生效能數字，但都在減少「下次改動要付的代價」。一個生態成熟與否，往往看這些不寫進發布說明的提交有多密。
