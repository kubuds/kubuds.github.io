今日重點：進迭時空開源 RVISA 虛擬 ISA 規範工作草案，首輪補入 IME/VME/AME 三套對映與 blocked MMA（11-04 建倉、11-05 提交）

進迭時空（SpacemiT）在 GitHub 上開出一個新倉庫 spacemit-com/rvisa，提出 RVISA（RISC-V Virtual ISA，RISC-V 虛擬指令集架構），為 RISC-V 的標量、向量與矩陣計算定義一層虛擬指令記法。倉庫 11 月 4 日建起，11 月 5 日一天內推了三筆實質提交：先落地 MkDocs 文件站與 Pages 釋出流程，再補入 RVISA 記法的示例源形與首批 IME/VME/AME 對映，最後由 PR #2 定義「程式設計師可表達」的 tile 佈局與分塊矩陣乘（blocked MMA）。當前規範版本號為 0.2.0。

RVISA 的定位寫得比較清楚：它刻意站在 NVIDIA PTX 之上、cuTile 之下。往上看，它不繫結任何一門前端語言，源語言前端實現明確被排除在本版範圍之外；往下看，它不直接規定某顆晶片的指令編碼，而是把「目標對映」做成版本化的 profile，逐條宣告對映到哪一組暫存器類、暫存器組與指令序列，並附上該 profile 對應的上游修訂號與驗證證據。記法形式上參照 RVV Intrinsics 的做法表達型別化操作、運算元角色與暫存器組約束，tile 從一維到 N 維，reshape 與軸置換必須保持元素位置，佈局由線性佈局推導。

最能說明它想解決什麼問題的是「可表達性要求」這一條：任何對 RVISA tile 計算的最佳化，都必須能被程式設計師在記法層寫出來。這條約束針對的正是矩陣擴充套件落地時最常見的失敗方式——編譯器偷偷做了一套向量化，程式設計師既看不見也改不動，換一顆晶片就得重寫。RVISA 試圖把這一層顯式化，讓同一段記法在不同實現上走不同的對映 profile，而語義保持一致。

需要說清楚的是成熟度：規範狀態檔案自己寫明這是 working draft，不是 RISC-V International 的已批准規範。核心模型、型別與運算元規則、tile 佈局與最佳化、關鍵操作簽名已給出具體契約，但目標對映檔案只登記為草案、尚未建立實現一致性證據；MLIR dialect 標註為 TBD；參考負載只有 .rvisa 記法的源形，不能編譯執行；可執行一致性工具同樣是 TBD。倉庫另有 RFC 0001 至 0003 三份草案，分別覆蓋指令與暫存器對映契約、核心型別與操作契約、程式設計師可表達的 tile 佈局。

放到今天的產業座標裡看，這與同一批次 Quintauris 在 MCU 側做的事是同一個邏輯的兩種表現：開放指令集帶來的碎片化，最終要由某一層穩定的「軟體目標」來收斂。MCU 側收斂在二進位制相容與中斷語義上，AI 矩陣側收斂在虛擬記法與對映契約上。差別在於，EM-Altair 背後是六家車規與嵌入式大廠的合資公司，RVISA 目前是單家廠商主導的工作草案——它能否被上游矩陣擴充套件的討論接住，要看後續是否有人把 IME、VME、AME 三條線的實現證據填進那張對映表。

今日重點：Quintauris 釋出 EM-Altair，MCU 級 RISC-V 標準化平臺以 RV32IM 為基線做二進位制相容（11-03 釋出、11-05 報道）

Quintauris 11 月 3 日釋出 EM-Altair，自稱是面向微控制器級 RISC-V 系統的標準化嵌入式平臺。它不定義新核，而是定義一套「合規實現必須一致地表現」的硬體、韌體與執行時要求：ISA profile、特權架構、啟動與執行時服務、安全服務四層，廠商可以各自實現微架構，但軟體面對的是同一個目標。公司首席產品官 Angel Berrio Moreno 的表述是「同一個二進位制、同樣的中斷行為、同樣的安全假設」。

具體口徑上，EM-Altair 以 RV32IM 為基線，配一組邊界明確的必選與可選擴充套件，把中斷、原子操作、CSR 行為與記憶體序固定下來，而不是留成一顆移動的靶子。中斷部分規定了一套有界且高吞吐的架構，面向硬實時負載；隔離用 PMP 覆蓋機器模式與可選的使用者模式，用來分隔可信與不可信程式碼；安全實踐對齊 ASIL-B 等效要求，併為韌體完整性與裝置保護預留安全鉤子。目標場景寫得直白：車身電子、區域與座艙控制器、電動車能量管理，以及工業控制迴路、物聯網感測節點與可穿戴。

配套工具是 QNTAF，Quintauris 自家的驗證與認證框架。按官方描述，廠商可以在雲端、模擬器與 FPGA 三類目標上跑基準、一致性與安全測試套件，把這些測試接進 CI/CD，並生成認證所需的可追溯產物。規範與工具面向 SoC 廠商、RTOS 開發者與 OEM 開放。Quintauris 由博世、英飛凌、Nordic、恩智浦、高通與意法半導體於 2023 年合資成立，做的就是 profile、參考架構與軟體元件這三件事。

這條訊息與 11 月 4 日英飛凌釋出 AURIX RC1 值得放在一起讀。英飛凌是 Quintauris 的創始成員，AURIX RC1 把 AURIX 與 TRAVEO T2G 兩條產品線併到同一套 RISC-V 底座上，而 EM-Altair 提供的正是這套底座之上的共同執行環境——晶片廠做實現，合資公司做一致性，RTOS 與編譯器只需對一個目標適配一次。對國內做車規與工業 RISC-V 的團隊，這意味著兩件事同時發生：基礎軟體的門檻在降低（AUTOSAR、RTOS、工具鏈不必每家重做），而進入門檻在抬高（客戶會拿「是否符合某個 profile」來問）。

香山 XiangShan 修 MissQueue 推測預取下的 store 合併，GEM5 六筆集中在評測基礎設施（11-05）

香山主倉今日一筆：修 MissQueue 在預取 miss 處於推測狀態時仍然合併 store 的問題（#6842）。這是正確性修復而非效能改動——store 與一次尚未確定的預取合併，一旦預取被取消，寫回的資料歸屬就會出錯。

GEM5 側六筆，方向明顯偏向評測基礎設施：把 google trace 與 cbp trace 接進 CI（#1272）、補 Fetch Block Size 的統計 PMU（#1291）、更新 SPEC06 的 RVV checkpoint profile 並對齊標量浮點部分、給周效能任務加上可選開關（#1300）、加一篇硬體預取演算法綜述文件（#1302），以及 cpu-o3 用「最老的同週期 squash」過濾 resolve 輸入（#1282）。

把這兩條與 riscv100.top 上 10 月以來的榜面變化放在一起看，香山這條線近期的動作重心是「先把測法固定下來」：checkpoint profile 決定復現的是哪一段負載，trace 決定能追到什麼粒度，PMU 決定效能數字能不能拆開解釋，周效能任務決定這些數字多久出一次。分數只有建立在可復現的測法上才有比較價值。

P4 Launcher 在 ESP32-P4 上做出可裝載應用的類 PC 體驗，21 個 PAPP 應用（11-05）

開發者 Gil Tal 釋出 P4 Launcher，一個面向帶觸控式螢幕的 ESP32-P4 開發板的開源應用平臺。它開機直接進入自己的介面，應用以 .papp 檔案存放在 microSD 卡上，啟動時載入 PSRAM，因此增刪應用只需往卡里拷檔案，不必重刷韌體、也不必重啟裝置。目前已有 21 個 PAPP 應用，以模擬器與遊戲為主：Neo Geo 與 Atari 2600 模擬器、Doom、Quake、Duke Nukem 3D、OpenTyrian，另有時鐘與檔案管理。

實現上，介面基於 LVGL，合成器負責把 UI 縮放到不同解析度；音訊引擎支援最多 8 路、4 至 192kHz；最多接四個輸入裝置做多人遊戲，支援 PS3 與任天堂手柄；韌體可從 microSD 或 GitHub 更新，新版本起不來會自動回滾。專案另提供 SDK 讓開發者寫自己的 PAPP 應用，並帶兩層相容層：一層重實現 odroid_* 介面，一層實現舊的 PAPP v1 服務表——後者正是 Doom、Quake 這些老程式碼能用原膠水層跑起來的原因。程式碼基於 ESP-IDF v5.5.2，已適配 Guition 的 4.3 英寸與 7 英寸板以及 M5Stack Tab5。

這類專案的價值不在「能玩遊戲」，而在於它把應用打包、裝載、更新與回滾這一套約定在 MCU 上跑通了。ESP32-P4 是樂鑫的 RISC-V 高效能型號（雙核 HP 加 LP 核），PSRAM 頻寬、顯示與音訊子系統正好是這類負載的壓力點；一套成熟的應用容器約定，比多跑一個模擬器更能說明平臺可用性。

日期：2026-11-05　來源：CNX Software 報道、giltal/ESP32_P4_Launcher

二、產品與生態動態

先楫第二屆生態大會定檔 11 月 21 日深圳，14 場議程把 RISC-V MCU 與 AI 綁在一起（11-04）

進迭 manipulation 元件：把裝置獨佔、到位判定、超時與故障鎖定收進裝置會話（11-05）

manipulation 是進迭機器人 SDK 裡的機械臂控制元件，做的是「統一控制機械臂與末端執行器」：用裝置配置選擇硬體，用同一套命令或 C++／Python 介面下發動作，並提供運動學、手眼標定與裝置工具。當前帶三種驅動：軟體模擬的 mock_device；agx_nero_revo2，對應松靈 Nero 七軸、可選 Revo2 右手（Revo2 沒有位置反饋）；so101，五軸、可選原配夾爪，附舵機校準工具。

它的架構取捨寫得很明確。C++ 應用直接鏈元件庫、在程序內用 DeviceSession；命令列與 Python 應用走 DeviceClient，由它拉起本機程序 manipulation-device serve，經 JSONL 下發請求；YAML 點位任務由 manipulation-device run 執行。裝置會話統一處理裝置獨佔、到位判定、取消、超時與故障鎖定。驅動層只負責型號協議與單位換算，運動學與手眼標定從 device.yaml 與 descriptions/ 取模型，不寫死型號；接新裝置實現 Arm 與 EndEffector 並註冊即可。

最值得記的是那段「元件不自動使能、不自動清錯、不自動歸位、不自動重試」。具身智慧專案裡最容易圖省事的地方就是讓中介軟體替人做決定，而這四件事一旦被自動做掉，出問題時現場人員就失去了判斷依據。把安全邊界放在會話層而不是驅動層，是機器人中介軟體該有的剋制。

五、總結與趨勢觀察

今天有兩條主線，一條講抽象層，一條講標準化，落在同一個問題上。

進迭時空的 RVISA 在 AI 矩陣側給出一層虛擬指令記法，把「程式設計師能表達的最佳化」寫成硬約束，再用版本化的對映 profile 對上 IME、VME、AME 三種尚在推進的矩陣擴充套件；Quintauris 的 EM-Altair 在 MCU 側給出二進位制相容的執行環境，把中斷、原子、CSR 與記憶體序固定成一套合規實現必須遵守的行為。兩者都在回答開放指令集帶來的碎片化該由誰收斂：不是讓晶片廠各自解釋規範，而是在規範與實現之間插一層穩定的軟體目標。差別在治理結構——一個是六家大廠的合資公司，一個是單家廠商的工作草案。

國內廠商的動作重心繼續從「晶片與板卡」轉向「元件與規範」。進迭一天裡同時推進 RVISA 規範、機器人 SDK 三個倉庫與 K3 的機械臂手冊；算能給出 2 核與 3 核的端到端壓測數字而不是峰值算力；紫荊把「生態推廣」做成了可申報的案例。這三件事的共同點是都在補「別人能不能用起來」這一側，而不是再發一顆引數更高的晶片。

車規仍是最大戰場，且今天呈現出三個層次同時推進的局面：晶片層（英飛凌 AURIX RC1，11-04）、平臺規範層（Quintauris EM-Altair）、生態案例層（紫荊 M100 入選中國芯示範案例）。三層之間不是競爭關係，而是同一條產業鏈上不同位置在做同一件事——把開放指令集變成可交付的車規產品。

評測側則繼續「先固化測法」。GEM5 今天的六筆裡有五筆是 checkpoint、trace、PMU、周效能任務這類基礎設施，riscv100.top 昨天的對比檢視與今天的榜面回退也是同一類現象：榜面還在整理期，數字的可比性比數字本身更值得關注。
