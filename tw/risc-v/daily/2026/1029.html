今日重點：Qwenputer 把 RV32IM CPU 編譯進 Qwen3.5 權重，以 GDN 狀態充當 RAM（10-28）

開發者 Divyansh Agrawal 釋出 Qwenputer：一個未經過訓練的 Qwen3.5-4B，把一顆 32 位 RISC-V CPU 直接編譯進模型權重，並用模型自身的 Gated DeltaNet 層狀態作為記憶體。它在視窗內被 Adafruit、Startup Fortune 等多家媒體轉述，並在 Hacker News 上引發討論。

技術路徑有三步。第一步把 GDN 精確化為可定址 RAM：把門控置 1、寫強度 beta 置 1、鍵用 one-hot 編碼，每次寫入只覆蓋一行、每次查詢只讀取一個精確值，於是 GDN 頭變成逐行定址的儲存，且狀態大小不隨上下文增長。第二步把 CPU 編譯成層：無需訓練，編譯器把「讀暫存器／相加／條件跳轉」等步驟逐一對映成注意力頭（查表）、前饋層（算術）與 DeltaNet 頭（RAM），CPU 佔據 Qwen 32 層之前的 11 層。第三步把執行在解碼中跑出來：每條指令對應幾個生成 token（ADDR 指定寫入行、VAL 攜帶數值、STEP 結束指令），這些 token 本身就是執行軌跡。

這顆粒心是 RV32IM 加 Zba 擴充套件，另帶一個小型大數單元，官方稱透過 riscv-tests、程式結果與 qemu 一致，並自由執行（free-running，即完全依賴自身輸出推進、中途無參考機糾正）1800 萬條指令無一處錯誤；對約 23 萬個輸出位置與參考機回放比對，零不一致。它能跑 C 與 MicroPython，但需要一個小驅動 RvChat 載入韌體並把軌跡 token 擋在 Qwen 層之外，因此暫時不能直接以普通的 generate 呼叫執行。效能上每條指令耗費數個解碼 token，基準批處理執行器在 L4 上約 3200 CPU token／秒。

效果上，在 DeepMind 算術集上 div_big 得分 97.5%（給 Qwen 加 Python 工具為 95%、基礎模型 72.5%）、mul_big 97.5%（工具 100%、基礎 55%）、mul_div_multiple_longer 100%（工具 97.5%、基礎 90%）、add_or_sub_big 97.5%（工具 97.5%、基礎 87.5%）；在 NUPA 長整數算術上從 48.6% 提升到 100%。附帶還做了一個實驗性檔案系統（1024 槽目錄、最多 512 個檔案、約 5.3 萬 token 文字），寫入 GDN 狀態後可跨會話保留。代價是檢查點 18.8 GB（約為基礎模型兩倍，大部分為零填充）。

  • 觀察：這不是產業新聞，不宜按產品訊息讀。它值得收錄的原因在於演示了兩件與 RISC-V 相關的事：一是任何確定性 ISA 都能被編譯成權重，ISA 的門檻從來不在指令編碼，而在軟體棧與生態；二是模型內部的可定址狀態可以充當確定性執行環境，這對「把監控能力編譯進權重、模型自己無法篡改」這類安全研究是現成的試驗檯。反面同樣要看清：18.8 GB 權重、每指令數個 token、需要專用驅動，註定它是研究裝置而不是晶片替代品——真正做 RISC-V 晶片的團隊不必因此調整路線。

一、開源社群與軟體生態

1.1 香山 difftest 支援遠端 XDMA 板卡中繼，FPGA 驗證可跨機排程

日期：2026-10-28　來源：GitHub：OpenXiangShan/difftest 提交記錄

difftest 視窗內 3 筆提交，核心是 feat(fpga): support a remote XDMA board relay（#1011）：把 FPGA 上的待測核與參考模型之間的鏈路改造成可經遠端 XDMA 板卡中繼，驗證機與板卡不再要求同機同席。配套兩筆，一是 fix(fpga): let fork REF finish after the final endpoint（#1010），修正 fork 場景下參考模型在最後一個端點之後才收尾的時序；二是 fix(mma): accept zero-sized reference operations（#1012），讓矩陣擴充套件路徑容忍零長度的參考操作，避免空操作被當作錯誤拒絕。

  • 觀察：這三筆合起來說明 difftest 正在從「單機比對器」變成「可遠端排程的驗證服務」。遠端中繼解決的是資源利用率——一套 FPGA 驗證環境往往排隊等人，鏈路能跨機後就能被多人多工分時使用。對做 RISC-V 核的團隊，驗證機時通常比設計人力更稀缺，這類改動比多一個效能最佳化點更實用。

1.2 香山 GEM5 增加 TEA 剖析選項，XiangShan CI 更新 profile 與模糊測試

日期：2026-10-28　來源：GitHub：OpenXiangShan/GEM5 提交記錄、GitHub：OpenXiangShan/XiangShan 提交記錄（kunminghu-v3 分支）

GEM5 側新增 cpu-o3: Add optional TEA profiling for XiangShan（#1255），為香山模型掛上可選的 TEA 剖析通路；此前視窗內該倉庫剛合入 sv48 功能級 TLB 初始化修正、CDP 中 L2 預取源識別修正、Sstc 定時器支援等一批架構級修復。香山主倉同日 ci: update profile & improve fuzz（#6758），更新 CI 剖析配置並強化模糊測試流程。

  • 觀察：剖析能力與模糊測試同時推進，是核進入「效能歸因 + 長跑穩定性」階段的標誌。GEM5 這條線尤其值得關注——它不是簡單的效能模型，而是帶 TEA 剖析的體系結構探索平臺，香山的很多微結構決策在 RTL 之前先在這裡試。

1.3 openRuyi 單日 20 筆：rust-vmm 元件族成組入庫，krb5 服務體系重構

日期：2026-10-28　來源：GitHub：openRuyi-Project/openRuyi 提交記錄

openRuyi 主倉視窗內 20 筆提交（提交流前 20 條全部落在視窗內），分四塊。第一塊是 rust-vmm 元件族成組入庫：新增 rust-linux-loader 0.14、rust-vm-memory 0.18、rust-kvm-ioctls 0.25，rust-acpi-tables 升到 0.2.1。第二塊是 krb5 服務體系重構，三筆一併處理：KDC 路徑與 systemd 服務統一對齊、realm 配置改為中性並可沿用上游憑據約定、構建選項改用系統庫並跑上游測試。第三塊是語言與構建基礎設施：go 回移索引最佳化、go-google-api 與 go-git 相關包跟進 gcfg v2 依賴、cmake 提供 Python 分發包後設資料、python-scikit-build-core 升 1.1.1、python-httptools 放寬 setuptools 版本釘、attr 升 2.6.0。第四塊是收尾修補：ceph 跟進 main 分支新快照、procps 修 rpm 名並恢復 uptime、新增 sql-migrate、python-graphql-core 降到 3.2.13、刪除 python-backports-zstd。

  • 觀察：rust-vmm 四件套一次性入庫是本期最實質的訊號。這套元件是 Cloud Hypervisor 等 Rust 虛擬化棧的地基，成組進入發行版意味著在 RISC-V 上跑 Rust 寫的 VMM 的依賴已經打通。相比把某個應用移植過來，把虛擬化底座的語言棧換掉，影響面要深一層。

1.4 CORE-V CVW 修正 CBO 快取管理：非快取 cbo.zero 末拍停頓與 PBMT 別名下發

日期：2026-10-28　來源：GitHub：openhwfoundation/cvw 提交記錄

CORE-V 的 CVW 倉庫合入兩處快取塊操作（CBO）修正：Stall an uncached cbo.zero through its final beat 讓非快取區間的 cbo.zero 一直停頓到最後一拍，避免在寫響應完成前就釋放流水；Send cbo.clean/flush/inval to the D$ through PBMT=NC/IO aliases 讓這三類操作在頁表項被標記為非快取或 IO 別名時仍正確送達資料快取。兩筆經 PR #2010、#2008 合併。

  • 觀察：CBO 是 RVA23 裡最容易被忽視的一組指令——它不像向量擴充套件那樣出現在效能榜上，但非快取區間的末拍時序與 PBMT 別名處理都是「平時不觸發、一觸發就是資料破損」的位置。CORE-V 這類把規範邊界逐條對著測的專案，價值正在於此。

2.2 Microchip PIC64-HPSC 公佈早期輻照結果：TID 200 krad(Si)、SEL 78.2 MeV·cm²/mg

日期：2026-10-28（釋出 10-27）　來源：Microchip：PIC64-HPSC 專案里程碑新聞稿、Hacker News 討論：PIC64GX 64 位 RISC-V 四核微處理器

Microchip 公佈 PIC64-HPSC 高效能航天計算系列的早期專案里程碑。抗輻照型號 PIC64-HPSC1000-RH 的早期輻照表徵顯示總電離劑量（TID）達到 200 krad(Si)，單粒子鎖定（SEL）在指定工作條件下測試至 78.2 MeV·cm²/mg；單粒子效應表徵中系統控制器未出現不可糾正錯誤，也無需外部復位。同期早期訪問計劃已向客戶提供矽片與開發套件，板卡夥伴正在開發基於該平臺的 VPX 與 VNX+ 計算模組。該系列源自 NASA 與 JPL 對未來航天計算需求的評估，2022 年將 HPSC 合同授予 Microchip；NASA FY26 民用空間短缺優先順序清單把「航天操作先進在軌計算」列為第三位的技術短板。

  • 觀察：航天是 RISC-V 少有的「需求真實、指標硬、且不接受替代」的市場。200 krad(Si) 這一檔意味著任務範圍可從低軌覆蓋到月球以遠，而 SEL 與 SEE 資料是宇航級選型的入場券——沒有實測輻照資料，架構再開放也進不了型號目錄。這條線索的另一個看點是路徑：政府先定需求（NASA／JPL 評估），商業公司交付平臺，再由板卡夥伴做 VPX 形態適配，這是一條比消費電子長得多但確定性更高的產業鏈。

日期：2026-10-28　來源：StreetInsider／ABNewswire：GUITION 釋出 VisionGo 系列新聞稿

深圳晶彩智慧旗下 GUITION 釋出 VisionGo 系列嵌入式顯示模組，旗艦為 7 英寸 ESP32-P4 一體屏 JC1060P470C_I_W_Y：雙核 RISC-V 主頻 360 至 400MHz 級、1024×600 IPS 電容觸控、32MB PSRAM、16MB Flash，整合 WiFi 與藍芽，配 TF 卡槽、多路 GPIO，部分型號支援 MIPI-CSI。全系列覆蓋 1.28 英寸至 21.5 英寸，官方稱相容 ESP-IDF、Arduino IDE、MicroPython、LVGL、ESPHome 與 Home Assistant。

  • 觀察：ESP32-P4 正在把「HMI 屏加主控」固化成標準模組形態。對做智慧家居面板、儲能逆變器人機介面、充電樁顯示屏的團隊，這類模組把硬體門檻壓到「選屏加寫 UI」，剩下的差異化只在結構與演算法——這也意味著中低端 HMI 的硬體毛利會更快被抹平。

2.4 SiFive 把 RISC-V 定位為 AI 加速器控制層，X100／X200／X300 做 ACU

日期：2026-10-28（SiFive 部落格 10-16，Jon Peddie 分析 10-26，10-28 在社群引發討論）　來源：SiFive：The Next Leap in Datacenter AI — Orchestrating Custom Accelerators with Intelligent Control Units、Jon Peddie Research：SiFive makes the case for RISC-V as the control layer for custom AI accelerators

SiFive 提出用 Intelligence 系列處理器充當「加速器控制單元」（ACU），在主機處理器與定製加速器之間插一層可程式設計控制面，負責低延遲命令派發、資料搬運、前後處理與演算法調整。其論證針對傳統方案的三個缺陷：硬連線狀態機在演算法或資料格式變化時需要昂貴的硬體重做（respin）、共享匯流排上的頻繁資料搬移帶來不可接受的延遲並阻塞訪存流水、把底層排程壓給主機 CPU 會同時吃掉主機算力並放大時延。系列分工是 X100 面向控制密集且對面積與時延敏感的場景，X200 與 X300 提供更大向量頻寬與算力。Jon Peddie Research 的分析補充了兩條落地資訊：Google 資料中心已把 Intelligence X200 用作 AI 計算主機，另有一家未具名的美國一級半導體公司獲得 X100 授權用於工業邊緣 AI。

  • 觀察：這條判斷值得記進趨勢欄——RISC-V 的商業價值正在從「ISA 替代品」轉向「異構系統裡的固定角色」。SiFive 自己的表述是「價值正在移出 ISA」，剩下的差異化在實現與系統整合。對國內廠商的含義同樣直接：與其正面替換 Arm 主控，不如在 AI 加速器旁做控制層與排程層，這條路徑對軟體生態的要求低得多，也更容易先拿到訂單。

三、國內團隊深挖

3.1 奕斯偉計算 CTO 何寧：車規與具身智慧成第二、第三增長曲線，RISC-V 消費級 AI NAS 四季度量產

日期：2026-10-28　來源：21 世紀經濟報道：21 對話｜奕斯偉計算 CTO 何寧，RISC-V 高價值拐點將到來

奕斯偉計算高階副總裁、技術長何寧在峰會後的專訪中給出幾條具體判斷。其一，RISC-V 與 AI 的融合分三條路徑：RISC-V 作主控 CPU 外接 NPU（鬆散結合，產品已多）、RISC-V 進入 AI 單元內部承擔排程（英偉達 GPU 內部即嵌入大量小型 RISC-V 核）、以及透過向量與矩陣擴充套件讓 RISC-V 自身具備 AI 算力。他給出時間表：矩陣擴充套件佔大模型計算八成以上，規範成型並進入產品還需一到兩年，再過兩到三年才會有成規模的標準化產品；「RISC-V 與 AI 深度融合的爆發，大概還需要三年以上」。其二，軟體生態仍是最大障礙，但出現三個機會視窗：AI 正在把軟硬體一起重構、大模型重構了演算法與運算元工具鏈、算力重心從訓練轉向推理（推理生態複雜度顯著低於訓練）。

落地層面有三條硬進展。車規側，EAM2011 是國內首顆支援輕量級 AI 應用的車規級 MCU，搭載自研 32 位 RISC-V 核心，已批次應用於顯示屏總成、車載無線充電與電池管理系統；自研 RISC-V CPU IP R520A 已透過德國萊茵 TÜV 的 ASIL-D 功能安全認證，成為全球首個透過 ASIL-D 的多核多架構 RISC-V 核心（此前 R500A 為全球首個獲 ASIL-B 認證的 RISC-V 核心）。邊緣與智算側，公司與極空間合作推出全球首款基於 RISC-V 架構的消費級 AI NAS，計劃 2026 年第四季度正式量產發售。生態側，公司已量產超過 150 款產品、服務全球 220 家客戶，並依託 RISAA 生態技術平臺與牽頭成立的 RDI 聚力聯盟推進生態。

  • 觀察：訪談裡最紮實的一句是車規的壁壘不在晶片而在體系——從供應鏈、Tier1 到車廠匯入，鏈條極長，晶片做出來只是第一步。ASIL-D 之所以關鍵，是因為它把「能不能進智駕域」從商務問題變成了一張證書問題；拿到證書之後，RISC-V 的靈活性才有資格去匹配「智慧汽車功能融合」這種需求頻繁變化的部分。至於 AI NAS，四季度量產是個可驗證的時間點，值得在下季度回看。

3.2 進迭時空 spine-triton 跟進 spine-mlir 0.8.1，VMT4D 示例重調分塊

日期：2026-10-28　來源：GitHub：spacemit-com/spine-triton 提交記錄

進迭時空的 Triton 後端倉庫視窗內 5 筆提交（含 2 筆合併），實質兩件：一是把預編譯 spine-mlir 的下載連結升到 0.8.1，並同步更新版本號；二是把矩陣-向量轉置 4D（VMT4D）示例重調到「基準最優」的 128×32 分塊並做預處理轉置。前一日該倉庫還修了 smt_rvisa: fix constexpr capture shadowing kernel params——RISC-V ISA 側常量捕獲遮蔽 kernel 引數的問題，以及 CI 在設定 BUILD_COMMIT 時跳過非 wheel 任務的守衛。

  • 觀察：spine-mlir 是編譯器側的上游，spine-triton 跟進 0.8.1 說明兩倉在同步節奏上已經形成配合。更值得注意的是「示例即基準」的做法：把 VMT4D 示例的分塊引數釘在實測最優值上，下游整合方拿到的就不是一個能跑通的樣例，而是一個可復現的效能基線。

3.3 算能 LLM-TPU 新增 Qwen3.6-35B-A3B bmodel 連結

日期：2026-10-28　來源：GitHub：sophgo/LLM-TPU 提交記錄

算能 LLM-TPU 倉庫新增 feat: add qwen3.6-35b-a3b bmodel link，為 Qwen3.6-35B-A3B 提供已編譯 bmodel 的下載連結。該倉庫此前的適配節奏包括 MiniCPM5-2B 與 MiniCPMV4.7 的 Python 示例（面向 BM1684X 與 CV84X6），以及 bge-reranker-v2-m3 與 MinerU2.5-Pro 的相容性支援。

  • 觀察：35B-A3B 是 MoE 稀疏模型，啟用引數只有 3B 量級，能在 TPU 上以 bmodel 形式提供下載，說明算能的模型適配已從稠密小模型轉向稀疏大模型——這類模型對記憶體頻寬與排程更敏感，對算力峰值反而不苛刻，恰好是國產 TPU 的舒適區。只給連結不給程式碼，是國內廠商常見的分發方式，權重與編譯產物由模型方託管。

四、具身智慧與機器人專章

4.1 進迭時空 humanoid_common 接入運動介面卡與運算元客戶端，whole-body 控制支援表格化耦合

日期：2026-10-28　來源：GitHub：spacemit-robotics/humanoid_common、GitHub：spacemit-robotics/control_whole_body

spacemit-robotics 的 humanoid_common 合入 integrate motion adapters and operator clients，把運動介面卡與運算元客戶端接入統一執行時；此前一筆（10-26）已接入運算元語音客戶端與靜態引數。control_whole_body 同日合入 support tabulated couplings and feedback recovery（#8），為全身控制增加表驅動的關節耦合與反饋恢復路徑。

  • 觀察：昨天這一欄還是「批次同步、無實質提交」，今天同組織在 04:07 與 04:08（UTC）連出兩筆功能提交，判斷需要隨之修正——進迭的機器人中介軟體層在持續推進。所謂「運算元客戶端」，是把動作、語音等能力以遠端服務方式接入本體執行時的做法，這與其九月底以來的一串提交（運算元服務、固定基座軌跡控制、上肢接管、SONIC 運動選擇）是同一條線：humanoid_common 正在變成機器人本體的中介軟體層，而不是某個型號的驅動集合。

4.2 unitree-go2 切換為僅地形 V2 行走策略，IMU 快照零複製讀取

日期：2026-10-28　來源：GitHub：spacemit-robotics/unitree-go2

unitree-go2 倉庫視窗內 6 筆提交，重點是行走策略與感知讀取：改用「僅地形」的 V2 行走策略並把模型下載固定到指定版本，同時保留既有模型歸檔下載架構；效能側 read IMU snapshots without copying motor state（PR #4）讓 IMU 快照讀取不再連帶複製電機狀態；此外修復 CI 迴歸下 SBUS 依賴載入與可選 SBUS 恢復的硬體配置說明。

  • 觀察：「僅地形」意味著策略不再按臺階、斜坡等工況分支，而是用一套地形策略覆蓋——這是把 sim2real 的域隨機化範圍收窄、換取實機穩定性與可復現性的常見取捨。零複製讀取 IMU 快照則直接對應 1kHz 級控制環裡的抖動來源：把電機狀態從資料路徑上摘掉，讀延遲就從「與狀態量成正比」變成常數。

4.3 peripherals-imu 支援 HI91 串列埠反饋，BMI270 IIO 通道複用

日期：2026-10-28　來源：GitHub：spacemit-robotics/peripherals-imu

peripherals-imu 視窗內兩筆：feat(imu): support HI91 serial feedback（#21）新增 HI91 的串列埠反饋解析；perf(imu): reuse BMI270 IIO channels and pace sensor reads（#22）改為複用 BMI270 的核心 IIO 通道並對感測器讀取做節流。該倉庫此前已覆蓋 BMI270 的 SPI 事件驅動、IWT603 與 Forsense 的 UART 驅動，以及 ICM42670P 的中斷輸出。

  • 觀察：IMU 驅動這條線正在從「每型號一套協議」走向「核心 IIO 統一入口 + 少量私有協議兜底」。對整機廠這是個好訊號——感測器更換不再需要改應用層，只要核心裡有 IIO 通道；對進迭自己，支援到第三家串列埠協議（IWT603、Forsense、HI91）意味著它的機器人參考設計正在適配更多國產 IMU 供應商。

五、總結與趨勢觀察

一、驗證基礎設施的下一步是資源池化。 香山 difftest 今天這筆遠端 XDMA 板卡中繼，把「驗證機與板卡必須同機」這個約束去掉。結合近三日的 fast-ref 與 fork 檢查、reftrace 記錄回放、MMA 同步驗證開關，difftest 的技術路線已經從提高單次比對速度，轉到排程多套驗證資源。國內做 RISC-V 核的團隊普遍缺機時，這條路比再堆一個效能最佳化點更有現實價值。

二、RISC-V 在 AI 裡的角色正在從「替代主控」變成「固定配角」。 同一天出現兩處獨立表述：SiFive 把 Intelligence 系列定位成 AI 加速器的控制單元（Google 資料中心已把 X200 用作 AI 計算主機），奕斯偉何寧把 RISC-V 與 AI 的融合拆成主控外掛、單元內排程、指令集擴充套件三條路徑並給出三年的時間表。兩者指向同一個判斷——先進製程上的正面替代不是當下主戰場，控制面、排程面與推理側才是能拿到訂單的位置。

三、車規是這一輪的分水嶺，而不是消費電子。 奕斯偉 R520A 拿到 TÜV 萊茵 ASIL-D（全球首個多核多架構 RISC-V 核心）、EAM2011 車規 MCU 已批次上車、與極空間合作的消費級 AI NAS 排到四季度量產。三條線裡，ASIL-D 是唯一一條無法靠價格戰繞過的門檻：它把「能不能進智駕域」變成證書問題。國內其餘 RISC-V 廠商若要做高價值場景，這張證書的時間表值得單獨跟蹤。

四、機器人棧從「同步」轉為「開發」。 昨天判定為批次映象同步的 spacemit-robotics，今天在四個倉庫出了十筆實質提交：中介軟體層接入運動介面卡與運算元客戶端、全身控制支援表格化耦合與反饋恢復、Go2 切換到僅地形 V2 策略、IMU 驅動擴到第三家串列埠協議並複用核心 IIO。這一欄的判讀方法仍應堅持看主分支提交內容，但結論要跟著證據走。
