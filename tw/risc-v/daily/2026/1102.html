今日重點：Linux 7.4 把「快非對齊訪問」改為執行期探測，發行版核心可吃到最多 11% 頻寬收益（10-30）

Linux 7.4 的 RISC-V 架構改動已併入主線，其中一條最佳化值得單獨記：跳過軟體對齊的判定從編譯期挪到了執行期。

這條最佳化的來路分兩步。Linux 7.3 由 Tenstorrent 提交的改動，讓「為支援快速非對齊記憶體複製的 RISC-V 硬體編譯的核心」跳過軟體對齊，Tenstorrent 自測頻寬提升最高 11%。但 7.3 要求該能力在編譯時開啟，而一個發行版核心要服務一批硬體，其中總有慢速非對齊訪問的晶片，於是這條收益只能留在定製核心裡，通用構建吃不到。7.4 把判定改掛到 HAVE_EFFICIENT_UNALIGNED_ACCESS 上做執行期探測：只有探測到硬體確實支援快速非對齊訪問，使用者態複製才跳過軟體對齊。這樣一來，發行版 RISC-V 核心與其它通用構建都能預設帶上這條最佳化，而不必為老硬體保留一份特製映象。

同批併入 7.4 的 RISC-V 改動還有：crash 熱插拔支援、部分頁表函式走最佳化路徑、上下文切換的一處最佳化、「B」擴充套件進入 hwcap 與 hwprobe 上報，以及 Zic64b 擴充套件的上報支援。這幾條單看都不大，但合起來是「核心把 RISC-V 平臺能力摸清並交給自己排程」的一步——尤其是 hwprobe 側的上報，正是執行期探測這類最佳化的前提。

社群討論裡有一個值得記錄的判斷：Hacker News 上有讀者問快速非對齊訪問是否只屬伺服器 CPU，回覆指出除 SiFive 外幾乎各家都支援，SiFive 只在新一代效能核上支援。這提示發行版開啟這條最佳化後，實際受益面取決於晶片是否在 hwprobe 裡如實上報，而不是取決於產品定位。

一、開源社群與軟體生態

香山前端引入 FtqPrefetchQueue，iprefetch 重構第一步（10-30）

第 6691 號是香山前端本輪最重的一筆，16 個檔案、+471/−198。改動核心是新增 FtqPrefetchQueue，把取指預取從 ICache-top 上收到 FTQ 側統一排程。

原設計的三個問題寫得很直白。其一，FTQ 只負責 FDIP，來自 memblock 的 Zicbop 軟體預取 prefetch.i 由 ICache-top 處理，每週期只能收 1 個請求，且總是把軟體預取排在高優先順序——同一週期多條 prefetch.i 只有 1 條生效，其餘被靜默丟棄，效能收益低於預期。其二，密集 prefetch.i 會阻塞 FDIP 請求，反過來拉低效能。其三，prefetchPipe 要麼處理 1 條 prefetch.i、要麼處理 1 至 2 條 FDIP，即使兩者在 SRAM 上並不衝突也不能並行，流水線利用率偏低。

新佇列的做法是：先快取軟體預取請求，緩解丟失；再按佇列空位與當前 FDIP 距離選擇出隊來源，解決阻塞；並允許 FDIP 與預取在同一週期並行發射，解決利用率。作者還留了擴充套件口——後續可以把 PDIP 一類演算法的結果直接塞進同一佇列。這是把預取從「一條通路」變成「一級可排程資源」的改法，比單純調優先順序更接近長期方案。

日期：2026-10-30　來源：XiangShan #6691

香山修 MBTB 對隱藏 VBTB 分支的分配抑制（10-30）

第 6750 號修的是預測器後設資料互相壓制的問題。VBTB 在預測時只暴露最早命中的那一條分支，但訓練階段仍可能命中一條「隱藏分支」——這條分支在預測時沒被看到，卻因為訓練命中而抑制了 MBTB 的分配，結果是同一條分支反覆預測失敗。

改法分三處：只有在「預測時確實暴露過、且訓練時仍駐留」這兩個條件同時成立時，才因 VBTB 駐留而抑制 MBTB 寫入；把全部 NumWay+1 條後設資料條目傳給 AlignBank，以便區分「VBTB 預測命中」與「SRAM 命中」；條件分支載荷只在真正 taken 時寫入，因為 not-taken 的解決路徑攜帶的是順序下一條 PC 而非分支目標。最後一條同時施加於 MBTB 與 VBTB，並保留計數器訓練與 IFU 失效請求（attribute=None）。改動只有 2 個檔案、+33/−19，但屬於「預測器越複雜、後設資料口徑越要對齊」的典型修復。

日期：2026-10-30　來源：XiangShan #6750

香山把 prefetch.i/r/w 解碼為 LSU 預取操作（10-30）

第 6735 號改軟體預取指令的處理流程：prefetch.i、prefetch.r、prefetch.w 在譯碼階段被識別為 LSU 的預取操作，並從 CROB 中排除。這一步與第 6691 號的佇列化改動配套——只有先把預取從「普通訪存指令」裡分出來，FTQ 側的預取佇列才有獨立的請求來源，不必再與 load/store 爭同一條提交路徑。

difftest 兩天九筆：MMA 後端把 FP8 乘積打包進 cache word（10-30 至 11-01）

difftest 在三天裡提交 9 筆，全部圍繞 MMA（矩陣乘加）驗證的效能，節奏上是一次集中攻堅。

最技術的一筆是第 1023 號：把相鄰的 FP8 乘積記錄塞進同一個 cache word 的低 16 位與高 16 位，省一半暫存器；每個 word 先用偶數 lane 初始化，解碼前對兩個半字分別掩碼，保證相鄰符號欄位互不串擾，長度為奇數的尾塊也照此處理。第 1021 號把比對搬到 GPU 上（11 檔案、+420/−90）：DUT 快照上傳與參考計算解耦，活躍結果行直接在 GPU 上比對，成功只回傳狀態位元組，僅失配時才下載參考結果做診斷；回退路徑用 memcpy 替代較慢的 SSE2 streaming-store；複用連續熱槽並從 CUDA 服務直接上傳其區間；去掉每個字首的 ready／enqueue 確認，同時保住 LightSSS 會話生命週期。第 1018 號把 CUDA 傳輸、計算與結果校驗流水化，第 1017 號讓 LightSSS 支援 CUDA 後端，第 1020 號把 XDMA 中繼請求打包以降延遲，第 1019 號簡化有符號 INT8 參考歸約，第 1016 號複用運算元槽的連續活躍字首，第 1004 號隔離 Delta 與 AXI 時序。方向很清楚：驗證器不再只求「算得對」，還要「算得起」。

openRuyi 引入 llvm23 23.1.4，riscv64-openruyi-linux 預設 RVA23U64（10-30）

六筆提交裡最重要的是新增 llvm23 包（1220 行 spec 加兩個補丁）。補丁做的事情比版本號更有資訊量：給 LLVM 增加 openruyi 這一 vendor，並把 riscv64-openruyi-linux 三元組的預設 ISA 級別直接定為 RVA23U64——也就是說不額外傳 -march 時，編譯器按 RVA23 生成程式碼。這對發行版是一個明確表態：RVA23 不再是「可選最佳化檔」，而是預設基線；同時補丁也把 openruyi-linux 三元組接進 x86_64 與 riscv64 兩套 Triple 處理路徑，保證交叉構建可用。

其餘五筆是滾動維護：ollama 升到 0.40.7 並標註 security-fixes；clang-wrap 更新到 20261030；新增 tree-sitter 的 C++ 與 Go 兩個 Go 語言繫結包以及 go-pointer 依賴。官網新聞頁最新仍是 2026.09 版（9-30 釋出），10 月版尚未釋出，10-19 的兩篇（Ruyi Firmware、社群公共基礎設施）已在 10 月中旬報告中收錄，本期不重複。

日期：2026-10-30　來源：openRuyi 提交記錄、llvm23 spec

CORE-V CVW 按 Svvptc 不再快取無效 PTE（10-30）

第 1974 號修的是一個只在 RVA23 選項下才暴露的死鎖：此前 HPTW 會把「遍歷落在 V=0 的葉或非葉 PTE 上」的結果寫進 ITLB/DTLB，之後命中該快取項時一直從快取條目觸發 page fault，直到執行 SFENCE.VMA 才恢復。問題在於 Svvptc（RVA23 的可選項）允許處理程式把 V 置 1 後直接重試、不發 SFENCE.VMA——在這種合法用法下，快取了無效 PTE 的實現會永久 fault。改法是讓遍歷器自己走既有 FAULT 路徑從 LEAF 報錯，不往 TLB 寫任何東西，下一次訪問重新遍歷即可看到更新後的 PTE；相應地 tlbcontrol 不再檢查 PTE.V，ITLB 的 ENVCFG_ADUE_1 覆蓋排除也從第 18 行移到第 16 行。這是「規範給了你一個可選項，實現必須為它的合法用法留出通路」的典型案例。

日期：2026-10-30　來源：CVW #1974

Qwenputer 把 RV32IM 編譯進 Qwen3.5-4B 權重，用注意力狀態當 RAM（10-30）

開發者 Divyansh Agrawal 於 10-22 釋出的實驗模型 Qwenputer，10-30 經中文媒體轉述後進入大眾視野。做法是把 RV32IM 指令集及擴充套件「編譯」進 Qwen3.5-4B 的權重，用模型自帶的 Gated DeltaNet 狀態充當可精確定址的 RAM，從而在前向傳播裡跑真正的程式——不需要訓練，編譯器直接寫出每個權重：注意力頭做查表、前饋單元以查詢表實現算術、DeltaNet 頭持有記憶體。

可核對的收益集中在精確算術：大整數乘法從原版 55.0% 升到 97.5%，大整數除法 72.5% 到 97.5%，加減 87.5% 到 97.5%，多次乘除的更長鏈路 90.0% 到 100%，合成整數算術 75.0% 到 97.5%；長整數基準 NUPA 從 48.6% 到 100%。專案自述該 CPU 透過官方 RISC-V 測試，連續執行約 1,800 萬條指令無錯；還實驗性地做了「模型內檔案系統」，在 GDN 狀態裡存最多 512 個檔案、約 5.3 萬詞元。

代價同樣明確：模型體積漲到約 18.8GB（接近原版兩倍），每條 CPU 指令要生成多個詞元，原本毫秒級的計算可能拖到數秒，執行還需專用驅動，不能像普通模型那樣直接載入；專案已在 Hugging Face 與 GitHub 開源，可在單張 24GB 視訊記憶體顯示卡上跑。這條對 RISC-V 圈的意義不在效能，而在於「RISC-V 作為確定性執行層被另一種系統借用」——它驗證了 RV32IM 這套極簡 ISA 適合被形式化地嵌入異構載體。

五、總結與趨勢觀察

一、核心側的關鍵詞從「支援」轉向「按硬體能力排程」。 Linux 7.4 把快非對齊訪問的判定從編譯期挪到執行期，一條 7.3 時代只能留在定製核心裡的最佳化，現在發行版核心預設就能帶上，Tenstorrent 自測的頻寬收益上限是 11%。同批併入的 hwcap／hwprobe 的「B」擴充套件與 Zic64b 上報，正是這類執行期決策的資料來源。對國內幾家 RISC-V 發行版，這是零成本收益，但前提是晶片在 hwprobe 裡如實上報——硬體廠把能力報全，比多做一次微架構最佳化更能讓使用者立刻受益。

二、香山前端進入「預取佇列化」階段。 第 6691 號把 iprefetch 從 ICache-top 的「每週期 1 條」邏輯上收到 FTQ，先解決丟失與阻塞，再談 PDIP 一類演算法；配套的 MBTB／VBTB 修正說明瓶頸已從「取指頻寬」轉向「後設資料精度」。兩條線合起來看，前端最佳化正在從加緩衝轉向「把預取當成一級可排程資源」，這類改動的收益要靠長期負載才能驗出來，短期跑分未必好看。

三、差分驗證開始為加速器運算元付效能成本。 difftest 三天 9 筆全部圍繞 MMA：FP8 乘積打包、GPU 側比對、CUDA 流水化、XDMA 中繼打包、LightSSS 支援 CUDA 後端。RISC-V AI 核要走量產，驗證吞吐必須跟上運算元複雜度，否則「算得對」會變成「算不完」。這組改動的方向比單筆收益更值得記錄。

四、工具鏈兩側同時定基線。 openRuyi 引入 llvm23，並把 riscv64-openruyi-linux 三元組的預設 ISA 定到 RVA23U64；芯來把 IDE 從 Eclipse 遷到 VS Code，並把 xlmodel、工具鏈與大端除錯文件同步到 2026.10。前者定「預設生成什麼程式碼」，後者定「開發者從哪裡進來」，兩者都屬於長週期決定，短期看不到效果，但會影響此後一兩年的預設選擇。

五、國內側本週期產出集中在算能與芯來，路線從板卡上移到系統棧。 算能的實質工作是模型支援與一個解碼退化 bug 的修復（logits 拷進 4 位元組 token 緩衝，導致每步解碼破壞查表），這類缺陷只有真機逐 token 比對才能定位；芯來把工具鏈入口換到 VS Code 並順手補齊 AI 助手接入。玄鐵與奕斯偉在視窗內空檔，進迭時空則同時推進 Bianbu AgentOS 傘倉與機械臂控制框架——一家公司把「端側 agent 執行時」和「機械臂標定／診斷／運動學」並列推進，說明其 RISC-V 軟體棧的重心正從驅動與文件轉向可交付的系統層。本期新聞側偏薄：中英文查詢去重後實質新增只有 Linux 7.4、Qwenputer、Nuclei Studio 三條，其餘為股市稿、消費電子與舊文重發；開源側仍是主體。
