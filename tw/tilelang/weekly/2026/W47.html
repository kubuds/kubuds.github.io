TileLang週報（2026-11-16 ~ 2026-11-20）

2026-11-20 苦芽科技

執行時與執行路徑

  • 裝置狀態還原（#3872，11-16 合入）：tvm_ffi 宿主 stub 只設當前裝置、不還原。在 cuda:0 上呼叫 cuda:1 的張量，結果正確但當前裝置被留在 cuda:1。後續 device="cuda" 的分配會靜默漂移。修法是在介面卡層用 torch.cuda.device(...) 包住呼叫，並在結束時還原。
  • NVRTC 單引數核心（#3880，11-16 合入）：引數名與型別用 ", " 拼接。單引數時拼出的不是元組，cuLaunchKernelEx 直接拋 TypeError。改為帶尾逗號的元組字面量即可。
  • cython 動態共享記憶體（#3882，11-16 合入）：動態共享記憶體上限原先只在 init() 裡設一次。該屬性是逐裝置的。需要超過 48 KB 的核心在其餘裝置上會報 cudaErrorInvalidValue。改為每個核心生成 _set_dynamic_smem() 幫助函式，並記錄已提升的裝置。
  • ROCm HIP 執行時複用（#3899，11-16 合入）：PyTorch 的 ROCm wheel 用 RTLD_LOCAL 載入 libamdhip64，stub 找不到它。修法是先用 RTLD_NOLOAD 探測已對映的執行時。這樣可以避免 dlopen 出第二份後模組控制代碼跨執行時，導致首個 kernel 啟動失敗。
  • 無符號緩衝讀取（#3875，11-17 合入）：CuTeDSL 目標上，從 uint8、uint16、uint32 緩衝區讀出的值被當成有符號數。根因是 MLIR 整數無符號位，而程式碼生成對全域性與共享記憶體的每次訪問都從迭代器型別出發。作者在 RTX PRO 6000 上用 256 個 uint8 值做探針。五種寫法在主分支上各錯 128 個值。修法是讓 tl.make_tensor 接受 dtype=，並把型別重新掛回檢視。
  • 佈局佔位變數跨序列化保持繫結（#4410，11-20 合入）：tl.Layout、tl.Fragment、tl.PartialFragment 用程序內單例 tirx::Var 佔位符表達索引與執行緒對映。判斷依據是物件同一性，不是 name_hint。佈局經 pickle 或 tvm.ir.save_json 往返後，佔位符被重建。於是 map_forward_index([7]) 返回 [_i]，OutputShape() 把 (32,) 算成 (_i + 1,)。在 spawn 出來的 worker 裡降載帶註解的 PrimFunc，會以「forward map must be injective」失敗。修法是把繫結的佔位 Var 引用納入同一個 ObjectGraphSerializer 通道。
  • CUDA Tile IR 後端 RFC 重新提交（#4402、#4403，11-19）：目標是從 TileLang 程式生成 CUDA Tile IR，交給 tileiras 編譯與排程。佈局、流水、warp 特化與指令選擇都由 tileiras 決定。後端只轉換 Tile IR 能正確表達的語義。轉換不了的直接報編譯錯誤並拒絕該程式，不追求與現有 CUDA 後端完全相容。這版是對早先 #3247 的重做。評審曾指出舊實現 try-catch 過多，用約 1.85 萬行 Python 寫 pass。

正確性與缺陷修復

  • CPU 後端補邏輯歸約降載（#4389，11-18 合入）：tl.any_of 與 tl.all_of 此前無法走 CPU 常規管線。新增 LowerCPUAnyAll pass，插在 LowerTileOp 之前。降載為按行主序的序列掃描，並帶短路。空歸約取標準單位元。浮點與 bfloat16 的 NaN 視為真。
  • topk 迴歸測試超時（#4407，11-18 合入）：test_topk_candidate_overflow 在 CUDA CI 上超時。原因是化簡階段發起了代價高昂的 Z3 查詢。修法是給該測試設定 arith.z3_rlimit 為 100。作者註明本機沒有 CUDA 程式碼生成，完整編譯耗時與 GPU 正確性未驗證。
  • 昇騰自調優測試移除跨 NPU 探測（#4401，11-18 合入）：該分支會執行一次跨 NPU 複製。在部分 Torch-NPU 與 CANN 組合上，這次複製會中止 NPU 上下文。捕獲 RuntimeError 後跳過用例並不能恢復上下文。同一 pytest 程序裡後續無關用例會跟著失敗。故障表現因此依賴執行順序。

六、趨勢觀察

第一，主戰場已經從編譯器本體移到運算元庫與排程器，這個位移連續兩個視窗成立。本週 141 筆合入裡，TileOPs 佔 84 筆，主倉只有 12 筆。主倉那 12 筆裡，四筆是執行時 bugfix，兩筆是版本與文件。上一週的情形也類似。主倉的工作集中在修迴歸，新增能力更多以運算元庫的瓦片、選擇器、代價模型的形式出現。判斷依據不只是合入數，還有依賴方向。TileOPs 的效能結論要引用 TileFoundry 的 roofline 與排程，而主倉這一週沒有給它們任何新東西。

第二，審計已經流水線化，瓶頸從「發現」轉到「評審」。11-16 期 72 小時新開 406 條 issue，兩個賬號貢獻 314 條。cn-sys 的 172 條在 1 小時 46 分鐘內寫完。ilovexsir 的 142 條直接對應五個 batch 修復 PR。這套模式確實在壓縮「缺陷發現到修復」的週期，同一天內 issue 與 PR 並存。但它把壓力轉移到評審端。11-16 期在審 102 筆、合入 30 筆。其中 22 筆 mlir-ascend 同構 PR 只能由極少數人過。下一階段的瓶頸會是評審頻寬，而不是發現速度。

第三，安全邊界成為本週唯一不可迴避的負面事件，暴露的是結構問題。自建 CI 被外部 PR 穿透，個人 token 被盜用。四個倉庫同時出現同風格 PR。這說明「新貢獻者 PR 直接觸發自建伺服器 CI」這個預設設定在組織層面是共用的風險面。作者的處置是撤銷舊授權、保留惡意 fork 取證、給自建 CI 伺服器做安全處理。建議的改法是新貢獻者 PR 需維護者批准後才觸發。這條對整個 RISC-V 與 AI 編譯社群同樣適用。自建 runner 的信任邊界應當預設收緊，而不是按倉庫各自判斷。

第四，自動 warp specialization 的正確性已經成為一等風險。#2896 到 #2901 這條鏈說明了一件事。當一個效能改動把同步責任交給編譯器自動插樁時，插樁位置就成了正確性的一部分。而它對上層不透明。同一個 cache key 兩次編譯，屏障可能落在分支內，也可能落在分支外。再疊上 CI 的持久化核心快取，偶發的壞插樁會被固化成穩定失敗。這一問題目前沒有結構性解法，只有「把寫操作挪出條件分支」這類區域性規避。如果後續更多瓦片走 ping-pong，同類掛死大機率會再出現。

第五，平臺邊界在向外擴，但都停在 IR 層。同一天落 Metal 目標與自動微分，編譯器從推理核心伸向訓練與 Apple GPU。兩者都不產出可執行的核心。順序很清楚，先立介面，後補後端與執行時。同一周 TileFoundry 用 303 個檔案把術語與佈局演算法收斂到單一規格。這相當於把中間表示從「實現中長出來」改為「先定義再實現」。這類改動短期增加評審成本，長期決定 IR 能否被外部後端正確實現。

第六，版本長期不發，是本週所有進展的共同出口問題。v0.1.15 停在 09-30，至本週五已 51 天。主倉的執行時修復、昇騰的執行後端改動、TileOPs 的運算元補齊，最早都要等下一個 tag 才能進下游發行包。與之對照，獨立發行版已經在往前走。Sunrise 出 0.1.15+sunrise.1.2.1，沐曦在備 v0.1.12+musa.5，海光以合併式修正跟進。三家各自發版，版本對齊與相容矩陣將成為新的維護成本。

第七，RISC-V 四源本週兩支各推進一次，節奏仍不連續。TVM 路線新開 hikari 分支，給出 K3 移植驗證與 RVV 網格資料。MLIR 路線合入 buddy-opt 預設化與兩個示例。社群索引頁第一次收錄 TVM 側 fork。但 11-18 起三期全部靜默。兩條路線的分工已經明確。TVM 路線在做「能跑起來、有實測資料」。MLIR 路線停在「有設計、有示例」。這條線值得按視窗跟，但不宜按周計算進度。
