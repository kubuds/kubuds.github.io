編譯器、語言層與執行路徑

  • PTO 執行後端換代（#3516，11-11 合入，20 檔案 +1549/−182）：target="pto" 配 execution_backend="auto" 時解析為 tvm_ffi，共享 host codegen 負責 MakePackedAPI 與 C host，昇騰執行時用 aclrtLaunchKernelWithHostArgs 啟動 PTODSL 編出的 aibin，路徑與 AscendC 核心一致。裝置構建側新增模組級工具鏈回撥，把整個 PTODSL 模組一次編譯完成（ptodsl → ptoas → bisheng fatobj-link → 抽取 .aicore_binary），快取鍵把 ptoas 引數、ptoas 版本與 CANN 身份一併算進去。舊路徑保留為 execution_backend="pto"，兩套產出逐位一致；驗證面含動態形狀、多裝置核心、cube/vector 混合 GEMM、快取命中與損壞條目拋錯等四組新測試。
  • AutoSchedule 收緊週期下界（#3776，1 檔案 +20/−1）：原先從一個固定下界起二分，改為取三條必要條件的最大值——單任務界用各任務啟動間隔的最大值，資源團界對成對沖突任務按殘餘值排序後由相鄰差與首尾差推出週期不小於團內啟動間隔之和，自依賴界由 S_u - S_u >= wait - d*P 反解出 ceil(wait/d)，版本相關距離按 num_stages 折算。實證在 Ascend 950PR、CANN 9.3.0 周版本上：昇騰示例全部編譯透過且排程結果不變，Z3 求解階段累計耗時降 10.04%。沒有引入額外的下界探測，也沒有改排程模型。
  • 跨核同步強制批排程以防死鎖（#3614，5 檔案 +102/−1，其中 78 行為迴歸）：mode=0 是「有可用核就啟動」，mode=1 是「等運算元所需全部核資源到位再整體啟動」。做全核同步的運算元若在普通模式啟動，可能只拿到部分核就先跑到全核屏障上等待，而它等的核正被另一條流佔著——資源成環，裝置掛死。改法是在 codegen 側識別出「帶常量 0 的跨核同步」後自動置 __schedmode__(1)，並把該標誌按函式重置以防洩漏。順帶把跨核 set/wait 的整數 mode_id 收窄到 0/1/2/4，並寫明三個目標的模式集合並不一致（910B/910C 支援 0/1/2，950 才多出 4）。
  • VMI 描述符與邏輯覆蓋校驗一併收口（#3894，6 檔案 +925/−550）：修 typed view 的 gather/scatter 與單元素載入兩類形態在構造描述符時基址與步長取錯；同時刪掉前端冗餘的邏輯覆蓋拒絕——刪校驗不是放鬆，而是共享記憶體檢測器的修復（#3805）已落地，前端再攔一遍會誤傷跨行、轉置與動態檢視。
  • CUDA 側補兩組指令級原語（11-10 合入）：#3490（6 檔案 +185/−1）補 L1 預取、uniform L1 預取與 L2 預取，並把驅逐優先順序做成一等引數 EvictPriority（預設、普通驅逐、優先驅逐、最後驅逐、不改變、不分配六檔），非預設優先順序要求計算能力 8.0 以上；#3605（7 檔案 +203/−1）新增 T.clamp_symmetric(x, limit)，在 SM86 及以上把 FP16/BF16/FP32 統一鉗到 [-limit, limit]、保留帶符號零與次正規數，任一運算元為 NaN 時返回規範 NaN，實現直接降到單條 min.NaN.xorsign.abs，並以 SASS 裡三種標量與打包形態的出現作驗收證據。

六、趨勢觀察

第一，大改造的善後期比改造期更長，成本落在「原本合法的程式不再合法」上。#3512 把 PTO 的向量化與型別體系一起換掉之後，連續四個視窗都在補它的迴歸面：執行後端換預設（11-11）、整數原子（11-11、11-12）、顯式 SIMD 並行迴圈與標量 cast 事實（11-12）、VMI 描述符（11-12）。這四類問題的共同點不是「新功能算錯」，而是「舊寫法編譯不過或結果變了」。對編譯器專案，這類迴歸的排查成本遠高於新功能的 bug——報錯位置常常落在一個與故障無關的標量或地址上，堆疊裡看不出是誰先裝錯了假設。

第二，昇騰的瓶頸已從「能不能編譯」移到「宣告與實現是否一致」，而評審頻寬是這條線的硬上限。十月的 14 條靜態缺陷之後，本週兩波審計把缺口從引數層掃到 T.simd 指令層，形態幾乎全是「宣告支援但實現走了另一條路」或「本該拒絕卻靜默透過」；而相對應的修復 PR 有十餘筆同時在審。tilelang-ascend 預設分支四個視窗零合入、在審佇列卻持續增厚，3060 項每日測試全過——測試覆蓋的是合法路徑，非法路徑的拒絕能力得靠審計。真正的驗收應該從「透過率」換成「宣告與實現的生成式對齊」：從 HCU_MCPU_SET 生成後端必須覆蓋的架構清單，從 intrinsic 登錄檔生成 dtype/位寬支援矩陣。

第三，後端矩陣從「一家獨進」變成四點同時開工，投入深度分成四類。本期主倉八筆全在昇騰，但同視窗 ROCm 一次開出七筆成系列、海光一條分支一天十筆、Sunrise 在走釋出流水線（ci/sunrise-0.1.15-1.2.1-r6 建刪 80 秒）、Hexagon 以個人 fork 的形式把 TileLang 推到手機 DSP。四種形態（上游內建後端、廠商適配倉、獨立發行版、第三方 fork）對應四種投入深度，這個分化本身就是判斷各廠商依賴程度的可用指標：廠商倉跟版本、發行版跟主線、fork 跟自己的硬體。

第四，TileFoundry 的定價缺口在被運算元側反覆頂回，這比單個運算元變慢更危險。#318 明說同一行為在四條已關閉 issue 裡報過、都被標 not planned、當前構建仍復現；#319 一次給五條且帶 962.1 對 1213.6 GFLOP 的偏差（26%）；bf16 的尾數口徑在 check --help 與硬體事實之間差了整整一位。分析器是 TileLang「先定價再選排程」路線的前提，定價偏 26% 會讓自動選擇在邊界網格上系統性選錯。這類缺口不會讓任何單個運算元變慢，但會讓自動化安靜地做錯決定。

第五，「給 agent 用的工程化」開始成規模出現。mlir-ascend 的 harness 分支一日 +7632 行，內容是技能庫、模擬 trace 流程與 Roofline 計算器，服務物件是「寫運算元的人或 agent」而不是編譯器本身；同一周，Hexagon fork 的 README 直接寫明後端與模型由 AI agent 在維護者指導下重寫、四天 75 個 PR 佔當前程式碼八成以上。兩件事方向一致：TileLang 這類 DSL 的抽象層恰好落在「agent 能寫對」的粒度上，於是生態開始為 agent 鋪工具鏈，而不是隻為人鋪文件。這一條值得按周跟。

第六，RISC-V 四源連續六個視窗靜默，與整體活躍度形成明顯反差，但差距的量化方式本週變了。TVM 路線、MLIR 路線、社群索引頁、算能 TPU 四個上游全部停在原引用；四源之外那條 CPU 線在 11-11 換口徑後給出 553/553 落在 Triton 1.03 倍內的結論，但同一批用例在前一天還是「41 例快於參考、SG2044 中位 0.0580 倍」。兩套數字都不是造假，差別在於被測物件是「作者手寫程式」還是「共享編譯器產物」。真正的觀察點是：這套「同一編譯器、兩套前端」的做法能否反向進入上游，以及 RVV/IME 路徑是否會被四源之外的專案先跑通。停滯不是沒人做，而是官方四源還沒有形成「自動發現差距、自動驗證、自動排隊」的迴路。
