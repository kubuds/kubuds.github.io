TileLang週報（2026-10-19 ~ 2026-10-23）

2026-10-23 苦芽科技

報告週期：2026 年 10 月 19 日（週一）至 10 月 23 日（週五），共 5 個工作日 素材來源：本刊每日 TileLang 社群動態日報 5 期（10-19、10-20、10-21、10-22、10-23），五期採集視窗合計 10-16 07:00 至 10-23 07:00；另經 tile-ai 組織 29 個倉庫的 168 小時視窗補充核查與各倉庫釋出頁、標籤、VERSION 檔案複核（詳見附錄）

一、本週要聞

  • TileFoundry 0.0.3 正式釋出，把指令級排程交給 agent，H200 上 Qwen3.8-27B 預填三檔全面快於 SGLang（10-21）：10-21 10:26 打出 v0.0.3，PyPI 為 tilefoundry==0.0.3，代號「Agent-driven scheduling」。核心變化是排程權歸屬——編譯器列出每個 HIR 操作可由哪些指令實現、各自需要什麼，agent 在候選中選定，編譯器再把選定的排程下降為 TIR；配套 CLI 增加 schedule candidates 與 schedule facts，指令以 AtomSched 操作宣告並帶顯式 TIR 運算元契約，從 CUDA MMA atom、SM90 WGMMA 與非同步複製起步。效能面給出三組真實數字：Qwen3.8-27B 預填在單張 H200 上 1024 / 4096 / 8192 token 分別為 80.29 / 309.61 / 631.19 ms，SGLang 為 89.06 / 317.11 / 638.25 ms；短序列 128 / 256 / 512 / 1024 token 分別是 SGLang 的 1.88 / 1.41 / 1.10 / 1.03 倍。已知問題兩項：wheel 尚未打包 CUDA 執行時標頭檔案（從安裝包出發編不出 CUDA kernel，需原始碼 checkout，下個版本修），以及效能時間線對 insert_slice、tf.zeros 跨 mesh 位置的定價有誤（#239）。

  • SemiAnalysis 設 TileLang Ascend 專章：六個獲昇騰支援的倉庫中，文章寫作時只有 TileLang 可用（10-21 ~ 10-22）：10-21 釋出的《The Huawei-DeepSeek Symbiosis》副題直接列出華為 Ascend 950PR 微基準、DSv4.1 Flash 分析、DeepSeek 的昇騰支援、AICPU 與 TileLang Ascend。與 TileLang 直接相關的三點：其一，獲得昇騰支援的六個倉庫（TileLang、DeepGEMM、DeepEP、TileKernels、FlashMLA、DeepSelect）中，寫作時只有 TileLang 可用，因為 CANN 9.2.0 尚未釋出，而 DeepSeek 要求 CANN 9.2.0 與 C++20 編譯器，9.2.0-beta.2 不提供後者；其二，昇騰 950 後端已併入 TileLang 主倉、而非只存在於單獨適配倉，提供原生編譯、排程、同步與執行時整合，AutoSchedule 依據資料依賴與預估執行時間決定重疊與片上緩衝槽數，在 950PR 上對小尺寸單運算元最多縮短 40%；其三，與 CANN、Triton-ascend 對比時「某些尺寸可以打平或超過 CANN」，最優實現隨尺寸切換（作者註明為熱快取下的樸素基準）。文章同時點出生態缺口：多數最佳化面向超節點，x86 主機上 vLLM-Ascend 0.26.0rc1 仍有多處問題。10-22 南華早報《Jensen’s nightmare》轉述同一份報告，屬二次傳播，不構成新的技術進展，但說明該判斷正在進入主流媒體口徑。

  • 主倉一週完成三輪正確性硬化，缺陷型別從「算錯數」擴到「選錯目標」與「編譯期狀態失真」（10-19 ~ 10-23）：第一輪清 warp 特化與流水線幾何——#3503 讓純 TMA 生產者每個執行緒都到達正向屏障（修 #3470 的 parity 掛死）、#2342 讓兄弟流水線共享緩衝只展開一次（修 #2309 的四維 LayoutInference 崩潰）、#3536 給共享緩衝上的 T.cumsum 補執行緒偏移、#2822 保留傳遞性複製依賴。第二輪清靜默數值錯誤——#2818 要求不支援的 MMA tile 顯式 K 填充（原先會悄悄縮小 K 原子）、#2815 修 (64,1) 保留維歸約崩潰、#3550 讓 TIR 謂詞隨整數位寬提升同步改寫、#3070 修批式 finalize_reducer 只歸約首個輸出塊、#3350 對 cast 的源/目標/舍入三組合前置校驗、#2860 讓無 arch 的 CUDA target 報錯而非靜默填 sm_50。第三輪清編譯期狀態——#3579 把非零迴圈下界納入向量化分析（10 檔案 +818/-198，關掉 #2669 與 #2616）、#3612 在向量化重寫前克隆 analyzer、#3226 修並行迴圈切分後舊 analyzer 繫結失效。三批的共同點是不報錯、只在特定尺寸或迴圈形態下給出不可信結果。

  • 昇騰線重心移到訓練反向與底層資料通路，單週合入 11 筆適配倉 PR 並開出 sparse_mla 雙向（10-20 ~ 10-23）：訓練側運算元集中落地——#1887 的 indexer_bwd（+1294，服務 DSA 稀疏微調，同時支援 AscendC 與 PTO 雙後端，分快速、通用、cast 三檔 kernel）、#1877 的 SiTU-GLU 反向（+854，語義對齊 CANN 的 aclnnSituGluGrad，用於 Kimi K3 Stable LatentMoE 門控啟用反向，910B3 上與官方 aclnn 交叉校驗最大相對誤差約 3e-3）、#1892 的 LSTM（+2304，12 個 jit kernel，支援多層堆疊、雙向、LSTMP 投影）與 #1902 的 GRU（+2267，8 個 kernel，手動關掉 AUTO_SYNC 以避開每時間步約 58 個 PipeBarrier）。在審佇列接著補 sparse_mla 前向與反傳（#1929 / #1928）、GLM-5.3 的 kpool 壓縮（#1910）與 WY fast 系列（#1827 等）。資料通路一側，#3530 以 18 檔案 +993/-256 讓壓縮 NZ 緩衝支援部分 UB→L1 複製並顯式給出 C0 組行距；#1795 定位到亞 32B 緊湊行距源無法表達，實測第二個 burst 讀到 element 8 而非 element 1，修掉 keepdim reduce 的輸出錯亂；#1903 把 JIT 快取改為原子釋出並在快取被刪除時恢復。

  • TileOPs 一週合入 68 筆，SM89 與 SM90 並列成主線，規格與基準覆蓋同時報 205/205（10-19 ~ 10-23）：組織統計分支在 10-18 單日 20 筆、視窗 44 筆合入後重新整理為「已實現 205/205、已基準 205/205」，兩項同時滿格。SM90 方向一週新增六個 warp 特化 kernel——分頁 GQA 前向（#2668）、FP8 lightning indexer 雙 consumer warpgroup（#2666）、MLA 解碼錯位蹺蹺板（#2665）、dense prefill 持久化遍歷（#2706）、dense GQA decode（#2694）、因果滑窗 band（#2696）。SM89 方向則為消費級與單卡場景集中補位：塊縮放 FP8 分組 GEMM（#2659）與 INT8 W8A8（#2655）同日落地、FP8 BMM 預設瓦片改 64×64（#2681，1×16×64×128 從 5.161 降到 3.799 us）、W4A16 的 M 上界擴到 64（#2672，M=17 / 32 / 64 分別下降 43.35 / 47.20 / 40.00 個百分點）、分頁 DSA 用 MMA 實現（#2669，0.269 ms 對 PyTorch FP32 參考 0.727 ms）、NSA top-k 擴到 2048 個壓縮塊（#2675）。同期兩筆 NaN 修復都出現在 warp 特化路徑上：共享記憶體活躍期判斷錯誤（#2708）與 fast math 下 FMA 融合溢位（#2699）。

  • PTO 從「獨立執行路徑」走向「自動向量化 + 預設執行後端」（在審，10-18 起）：主倉 PTO 向量化框架 #3512 讓使用者在 T.SimdVF(lanes=L) 內書寫標量並行的 T.Parallel（逐元素、控制流、歸約），由編譯器向量化為 PTO VMI 指令、經 PTOAS 編譯後在 Ascend 950 上執行，規模從 10-18 的 44 檔案、18988 行增至 10-21 的 50 檔案、21022 行；#3516 擬讓 target="pto" 配 execution_backend="auto" 解析到 tvm_ffi 並設為預設。已合入的配套為一串儲存、謂詞與歸約語義修復：#3514 的 T.alloc_ss、#3437 的 SimdVF dim=1 歸約、#3582 的 PTO 整數符號性、#3581 的謂詞指數增長、#3523 的 SIMT 向量區域性變數分配。主倉同時用 #3511 補 AscendC 側的 L0 區域性複製顯式 pitch（24 檔案 +1458/-187，讓一個 GEMM tile 可由多次複製拼成）——兩條路徑是並行推進而非替換關係。

  • 下游分發形態出現第二例：Sunrise 打出 0.1.15+sunrise.1.2.0 釋出 PR（10-22）：#9 於 10-22 16:48 建 candidate/sunrise-0.1.15-1.2.0-20261019 分支並開 PR，把 Sunrise 分發版更新到 0.1.15+sunrise.1.2.0，納入 TileLang 0.1.15 及配套評審過的 TileOPs、TileKernels、TVM、tvm-ffi 變更；源匯入與合併、分發適配分開提交，最終適配 TANG 後端的 wheel 並修掉切片 GEMM 迴歸。自報驗證為本機契約測試 55 透過、TANG 流水線 codegen 測試 54 透過、兩個 lint job 與信任邊界檢查透過；但 S2 wheel 構建出包後，裝後 import 冒煙檢查在 tangGetDeviceCount 處失敗。該 PR 尚未合入。

編譯器、語言層與執行路徑

  • Windows ARM64 進發布流水線（#2962，10-19 合入，12 檔案 +356/-45）：新增 PowerShell 安裝指令碼從 NVIDIA 預釋出通道拉取 CUDA 13.4 的 windows_arm64 本地安裝包並落到固定路徑，新增 FindPipCUDAToolkit 模組與 windows_arm64_clang_compat.h 相容頭，解決 MSVC 工具鏈在 ARM64 上的標頭檔案與內建差異，同步調整 pyproject、兩份 requirements 與佈局、MSVC 輔助模組。這是繼 ROCm 與昇騰之後補上的第三個非 x86 交付面。
  • lower trace 拆分宿主與裝置原始碼（#3496，10-19 合入，6 檔案 +121/-63）：裝置側輸出 codegen_device.cpp 與 .original 基線、.latest 最新版，宿主側另出 codegen_host.cpp 與同結構基線，report.html 以軟連結指向最近一次執行。與之呼應，在審的 #3583（13 檔案 +106/-4390）把 lower trace 實現、專屬環境配置與相關測試從主倉整體抽走，只保留共享的編譯器插樁介面，讓追蹤工具獨立演進。
  • CUDA 16 位數學降級補齊（#3172，3 檔案 +463/-8）：asin、acos、asinh、acosh、atanh、log1p、atan2、hypot、copysign、ldexp、nextafter 缺 CUDA 專用下降規則，float16 與 bfloat16 呼叫在 codegen 階段無人接管。修復把它們註冊進 CUDAMath 並補 half_t、bfloat16_t 過載：十個運算元按 float32 求值再轉回，nextafter 改為按 16 位編碼做整數比較步進，以便在 fast math 下保住 bfloat16 次正規數。
  • eager 前端保留 Python 原始碼位置（#3558，4 檔案）：把生成的迴圈呼叫對映回 for 語句、上下文包裝對映回 with 語句，並補上可迭代引數解包的位置，修 traceback 與覆蓋率錯位。
  • BF16→FP32 向量化轉換改走內聯 PTX（#3595，4 檔案 +19/-7）：新增成對 lane 一次轉 f32x2 的實現，替掉逐 lane 標量提升，2、4、8 三種 lane 寬度均保持支援，語義不變、只動指令序列。
  • 展開 pass 與 ROCm Select（#2887）：迴圈展開不再消掉 trip count 為 0 的 stepped 迴圈，ROCm 側向量化 Select 改為逐 lane 下降，避免整組下降在不支援的目標上失敗。
  • softmax 跨 16-CTA 叢集分裂（#2632，10-18 合入）：針對 lm-head 這類少行長行（4×102400）新增核，舊實現每行 58 段經全域性記憶體交換 (max, sum) 並跨 grid 屏障，新實現把一行攤到 16-CTA 叢集的暫存器上，每個元素只取一次指數，跨 warp、跨 CTA、跨叢集用 shuffle 樹按 max-first 摺疊。
  • 在審方向：除 PTO 兩筆外，[Transform] Locate VerifyBufferInit reads outside tile ops（#3620）、[Codegen] Add unsigned mulhi intrinsic（#3617）、[Transform] Keep assumption checks with local dependencies in scope（#3611）、[Transform] Preserve tl.assume predicates that simplify to true（#3610）、[CPU] Support clz in C and C host code generation（#3609）在視窗內有更新；#3597 的混合符號移位修復與 tile-ai/tvm fork 的 #87

成對提交，另 #86 把上游迴圈作用域修復回移。fork 在審 25 筆、主倉在審 163 筆，TIRx 側先行、主倉跟進這條協作路徑本週第二次出現。

正確性與缺陷修復

  • 10-19：共享緩衝上的 T.cumsum 在 warp 特化下補執行緒偏移（#3536，4 檔案 +101/-38，CUDA 與 HIP 兩套 scan 模板引入 thread_offset）；call_extern 的裸 data 變數保守標記為寫入（#2618，新增 69 行用例覆蓋「call_extern 寫輸出緩衝」，方向是寧可少做最佳化也不做錯最佳化）。

六、趨勢觀察

  • 正確性硬化的層次在遞進，而不是在同層重複：上週主倉清的是「形狀與幾何校驗」，本週三段各不相同——先是 warp 特化與流水線的幾何與屏障（#3503、#2342、#3536、#2822），再是靜默數值錯誤（#2818、#2815、#3550、#3070、#3350、#2860、#3125），最後落到編譯期狀態一致性（#3579、#3612、#3226）。第三段最值得留意：這類缺陷生成的 kernel 可能仍然正確，但編譯器對使用者說的和它實際做的不一致；TileLang 正在接入 agent 自動寫 kernel，編譯期狀態能否自洽會直接決定 agent 迭代閉環能不能收斂。
  • 昇騰側的瓶頸已從運算元數量移到記憶體模型、執行時邊界與訓練反向：本週 11 筆適配倉合入裡，反向與遞迴運算元佔五筆（indexer_bwd、SiTU-GLU 反向、LSTM、GRU、CrossEntropy 文件），主倉側最大的一筆是 NZ 佈局的 UB→L1 行距表達（#3530，18 檔案），技術密度最高的是亞 32B 緊湊行距不可表達只能顯式中止（#1795）。加上 JIT 快取原子釋出（#1903）與 PTO 謂詞指數增長（#3581），這條線的主題是「讓已有運算元在邊界條件下不出錯」。配合 CANN 社群另起 ops-tilelang 運算元倉，可以讀出分工：運算元資產由社群倉承載，主倉專注後端語義與 codegen。
  • SM89 與 SM90 成為並列的兩條硬體主線，且排優先順序的標準從峰值效能轉向可獲得性：SM90 方向本週產出六個 warp 特化 kernel，SM89 方向則把塊縮放 FP8、INT8 W8A8、FP8 BMM、W4A16、分頁 DSA、NSA top-k 六條路徑同時推進，且 PR 普遍附帶單卡實測並寫明「不主張 SM90 執行結果」「大用例基本打平，不構成普遍優勢」。Ada 級顯示卡（L40S、4090 一類）是國內開發者手裡的主力硬體，這一取向與 SemiAnalysis 指出的「最佳化多面向超節點、通用性落後於效能」正好互補。
  • 生態層的組織動作多於程式碼層：主倉本週無釋出、無 breaking change，但組織外出現了中文系統教程倉、CANN 社群運算元倉、agent SKILL 工作流、Hexagon 後端實驗、VS Code 擴充套件與 SAIL 包裝倉；組織內則有 TileFoundry 0.0.3 的 agent 排程、Sunrise 的第二個分發形態、TileOPs 的規格滿格。把「人寫規則、agent 調優、倉裡沉澱基線」三者合看，昇騰側與 TileLang 整體的工程分工正在重排，而程式碼節奏本身是平靜的。
  • 分析機構開始把 TileLang 當作昇騰可用性的判據：SemiAnalysis 用「六個倉庫中只有 TileLang 當時可用」來定義 DeepSeek 昇騰支援的完成度，這比任何單篇技術部落格都更能說明 TileLang 在國產算力敘事裡的位置——從實驗性 DSL 變成預設承載層。同一篇報告也給出反向訊號：最佳化集中在超節點、x86 主機支援仍不完整，效能與通用性之間存在明顯取捨。SCMP 的轉述說明該判斷正在進入主流媒體口徑。
  • 下一期關注點：主倉 v0.1.16 是否釋出（已靜默 23 天）；TileOPs 的 0.1.12 鎖定能否解除（#2554 關閉後未見新版方案，雙基線驗證仍是閘門）；PTO 的 #3512 與 #3516 能否合入（決定 PTO 是否成為預設執行後端）；TileFoundry 0.0.3 的 wheel 缺標頭檔案與 #239 定價問題是否在下個版本修復；Sunrise 的 S2 wheel 在 tangGetDeviceCount 處的失敗如何處置；昇騰 sparse_mla 前向與反傳（#1929 / #1928）、GLM-5.3 kpool（#1910）的落地節奏；海光 gcy_merge_main 的暫存器流水開關清理何時進 main。
