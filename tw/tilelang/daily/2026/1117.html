今日重點：上游昇騰倉 CI 被濫用、貢獻者憑據被盜的公開披露

11-16 14:16（北京時間），貢獻者 liggest 在 tile-ai/tilelang-ascend 提 issue #2016，公開說明自己賬號在 11-15 被冒用，並交代了一條完整的攻擊鏈：11-15 早 7 點起，一個名為 miramar-labs 的賬號（該賬號本身疑為被盜號）提交 PR #2014，在其中加入會在 CI 執行時收集伺服器資訊的惡意指令碼；倉庫 CI 跑在自建伺服器上，中招後攻擊者從伺服器取走大量資訊與登入憑據，其中包含屬於 liggest 的 GitHub token。11-15 上午 9:39 至 11:40，攻擊者用該 token 冒充 liggest：在 #2014 下連發 18 條評論，疑似把公開 PR 當取貨視窗；在 tile-ai/TileOPs 提兩個帶挖礦指令碼的 PR（#2902、#2903，很快被維護者關閉）；另在 SemiAnalysisAI/InferenceX 提同類 PR #5086，試圖驅動對方的 benchmark 伺服器執行，16 日凌晨被其本人發現並關閉。作者稱兩個挖礦指令碼因 GitHub 自動檢查未被執行，也沒有查到執行記錄。

處置側：賬號本身有雙重認證，未直接被接管；作者撤銷了 GitHub CLI 與 VSCode 的舊授權，稱 token 已失效、15 日後賬號無異常；惡意 fork 暫時保留取證；被盜資料的 CI 伺服器待安全處理；#2014 也需處理，否則仍有重新觸發惡意指令碼的風險。作者給出的建議是：新貢獻者的 PR 改為需維護者批准後才觸發使用自建伺服器的 CI 流程。

核查側：GitHub 檢索顯示 miramar-labs 在 11-14 23:18Z 至 11-15 02:04Z 間向四個倉庫提交了同風格 PR——tile-ai/tilelang #4148、tile-ai/tilelang-ascend #2014、tile-ai/tilelang-mlir-ascend #251、tile-ai/TileOPs #2900，名義都是「快取預熱」或「CI 能力探測」；四個 PR 全部已關閉、無一合入，#2014 於 11-16 11:29 關閉。作者在 issue 關閉後另補一條評論，稱先前描述「看起來也有誇大成分，總之賬號已恢復」，因此上述損失範圍仍以作者自述為準，尚無第三方複核。對本社群的直接影響有三點：自建 CI 的信任邊界被外部 PR 穿透、個人 token 的生命週期要納入審計、同名 PR 會在多個倉庫同時出現。

一、核心專案進展

1.1 主倉四筆 bugfix 合入：JIT 裝置還原、NVRTC 單引數、cython 動態共享記憶體、ROCm HIP 執行時複用

主倉視窗內合入四筆，全部是執行時缺陷而非新特性。#3872 修 tvm_ffi 宿主 stub 只設當前裝置、不還原的問題：在 cuda:0 上呼叫 cuda:1 的張量，結果正確但當前裝置被留在 cuda:1，後續 device="cuda" 的分配會靜默漂移；修法是在介面卡層用 torch.cuda.device(...) 包住呼叫並在結束時還原。#3880 修 NVRTC 後端單引數核心無法啟動：引數名與型別用 ", " 拼接後，單引數時拼出的不是元組，cuLaunchKernelEx 直接拋 TypeError；改為帶尾逗號的元組字面量。#3882 修 cython 後端動態共享記憶體上限只在 init() 裡設一次的問題——該屬性是逐裝置的，需要超過 48 KB 的核心在其餘裝置上會報 cudaErrorInvalidValue；改為每個核心生成 _set_dynamic_smem() 幫助函式並記錄已提升的裝置。#3899 修 ROCm 下 HIP stub 找不到 PyTorch 自帶 libamdhip64 的問題：PyTorch 的 ROCm wheel 用 RTLD_LOCAL 載入，stub 先用 RTLD_NOLOAD 探測已對映的執行時，避免 dlopen 出第二份執行時後模組控制代碼跨執行時、首個 kernel 啟動失敗。

來源：https://github.com/tile-ai/tilelang/pull/3872 、https://github.com/tile-ai/tilelang/pull/3882 、https://github.com/tile-ai/tilelang/pull/3899

1.2 manifest 升級為宣告式引數型別，pilot 模型介面一次補齊

#2958 把 manifest 從「只能描述固定張量與標量」擴充套件到能宣告張量序列（torch.cat）、標量或張量二選一（flash_attn 的 seqlen_offsets、torch.clamp(min)）、必填但可為 None（mamba_ssm 的 bias）三類簽名，並把呼叫期輸入統一改成帶 type 與 default 的宣告；原先為「標量或張量」拆出的三組 Scalar/Tensor 運算元對隨之合併。#2967 在此之上補齊 pilot 模型的介面真值：七個新登記為 spec-only 的條目（含 torch 參考實現），十五個已實現條目補上 pilot 模型實際傳入的引數與輸入，核心遇到非預設值以 OpNotAvailableError 拒絕，條目狀態仍保持 implemented，基準行遇到該錯誤按「不可用」記錄而不是判失敗。

來源：https://github.com/tile-ai/TileOPs/pull/2958 、https://github.com/tile-ai/TileOPs/pull/2967

1.3 三個新運算元：門控 RMSNorm 與 MaskedScatter 落地，Embedding 合入當日回退

#2984 新增 RMSNormGatedFwdOp：按最後一軸分組做 RMSNorm，可由 silu(z) 或 sigmoid(z) 在歸一化之前或之後門控，全程 float32 計算、只舍入一次；一個 TileLang 核心覆蓋所有呼叫形態（8 條 lane、每條兩次 16 位元組訪問構成 128 寬行，16 行組成 128 執行緒的 CTA，更寬的組把 lane 翻倍到 1024 並跨 warp 用共享記憶體求和），暫存器上限定在每執行緒 64，門控的指數與倒數各用一條指令。基準對齊 vLLM 的 RMSNormGated、mamba_ssm 的 rmsnorm_fn、fla 的 rms_norm_gated、Hugging Face 的 Qwen3_5RMSNormGated 以及 torch 參考與 torch.compile，達到驗收線。#2982 新增 MaskedScatterFwdOp（out-of-place 版 masked_scatter，支援 fp16/bf16/fp32 與 input、mask 廣播）：每個 CTA 領一段完整的 mask 連續段（行數以 32 KB 為界），先數清本段之前的真值段再掃描自身，每 16 位元組向量只讀一次（真值段讀 source、假值段讀 input），段位元組超過四塊時先做一次分塊計數；對照 torch eager 與 torch.compile 達線，vLLM 的原地多模態合併因語義不同列為不可比。

同日另有反覆：#2977 合入 EmbeddingFwdOp 後，#2983 在當天把它整體回退，理由是該 PR 屬誤合，新運算元應走單獨的 TileFoundry 輪次；回退後該條目回到 spec-only，核心、運算元、基準、測試與工作負載一併移除。#2975 仍在審，是同一運算元的正式提案（按 token 索引 gather 權重行）。

來源：https://github.com/tile-ai/TileOPs/pull/2984 、https://github.com/tile-ai/TileOPs/pull/2982 、https://github.com/tile-ai/TileOPs/pull/2983

1.4 GEMM 三條量化線：INT8 W8A8 改 192 寬 ping-pong，W4A8/W4A16 stream-K 各自收尾

#2959 讓 INT8 ping-pong GEMM 在「最忙 CTA 的列數不多於 128×128 瓦片」時改用 128×192 瓦片，網格末尾按 bf16 GEMM 的窄瓦片規則收成整 32 列的儲存盒（在本期 manifest 的每條 prefill 行上都是 160 寬），每種寬度發一條對應寬度的 WGMMA；同等最忙 CTA 工作量下，192 寬瓦片每 MAC 搬運的 TMA 與 WGMMA 共享記憶體位元組更少、CTA 切換消費者的次數少三分之一，llama3-8b prefill-qkv 最後一波最忙 CTA 的列數由 1536 降到 1504。#2960 改 W4A8 prefill 的 stream-K 收尾：當其餘部分分塊都已落盤時，偏晚到達的 0 號貢獻者不再寫自己那份部分和，改由計數湊滿該瓦片的貢獻者收尾，每 CTA 只用一條 acquire-release 原子（放在命名屏障之後）替代每個執行緒的 fence，無 CTA 互相等待；只有含 stream-K 瓦片的程式走新路徑，其餘編譯結果與主分支一致。#2964 修 W4A16 stream-K 的錯位：核心原本用 cta == first_cta 保護「補齊未使用槽位並做 ceil 除法」的邏輯，TileLang 的化簡在 CTA 的第二段之後把它整段丟掉、在第一段之後把它摺疊，導致兩個 CTA 共用的瓦片留下未寫槽位、歸約讀到髒記憶體，最大誤差從 2.4 到無窮；改為在構建該程式的裝置上由宿主一次性建表，按「瓦片內第幾個 CTA」定位槽位。

量化 GEMM 的覆蓋面同步補：#2969 新增 42 條 W4A16 行、13 條 W4A8 行與 11 條 FP8 行，每行對應 Llama-3 8B/70B、Qwen3 8B/32B 或 DeepSeek-V3 的一個真實投影（TP1 或 TP8、解碼批），此前 W4A16 的基準行只覆蓋 45 個解碼排程區中的 3 個。另有一筆在審的 #2990（W4A16 解碼瓦片配對條件收緊），起因是 issue #2966 記錄的同批改動在部分 8 行與 16 行形狀上比改動前更慢。

來源：https://github.com/tile-ai/TileOPs/pull/2959 、https://github.com/tile-ai/TileOPs/pull/2964 、https://github.com/tile-ai/TileOPs/pull/2969

1.5 注意力與線性注意力：paged GQA 校準續篇、DeltaNet 啟動配置、GLA 反向共享記憶體

#2956 續 paged GQA 的校準：拆分的歸約改為按 split 為主序存權重表、每個行塊一個 CTA，並讀掃描生成的請求對映（原先按行並行寫 [block_M, num_split] 表，在 16 與 32 路拆分時序列化）；GQAPagedFwdKernel.default_config 只在打包後的行真正填滿時才用 128 行查詢瓦片（48 行頁會讓關鍵瓦片窄於一條 WGMMA，解碼打包反被撐到 128 行）；左視窗情形下 RoPE 預處理也改為按窗內範圍準備。#2978 讓 WS 核心接手「視窗覆蓋整張頁表、不會隱藏任何 key」的情形：此前 WS 核心拒絕一切不帶 RoPE 的視窗，window4096/long-b1-q2048-kv2048 因此落到 cp.async 核心，耗時是 FA3 的 2.17 倍；該 PR 自評仍低於驗收線（below bar），屬改善而非達標。

線性注意力側，#2979 修 DeltaNetChunkFwdOp 在 chunk_size=16 下的啟動配置（準備與輸出最多兩條 warp，奇數 V/8 只允許一條，遞迴列的 warp 數必須整除 8 列瓦片數），#2980 把 chunk 啟動上限改為從每個 GEMM 的 warp 瓦片推導，修掉 chunk 32/64/128 下一批「TileLang warp 劃分失敗」的形狀（此前只對 chunk 16 特判），並讓不合規的 chunk_size/dim_k/dim_v 在構建期被拒絕而不是隨機失敗。#2965 在 SM89 上把 GLA 反向的共享記憶體生命週期壓回 99 KiB 預算內（重算門控因子、過載狀態梯度），恢復四個此前超限的 dtype/形狀組合（FP32 的 32×64×192、32×32×256 與 FP16/BF16 的 32×128×128），仍有三組保持拒絕。#2976 把兩條 DeltaNet 計時用例標為 SM90，避免在 SM89 上先構建僅 SM90 可用的解碼 warp 核心。

來源：https://github.com/tile-ai/TileOPs/pull/2956 、https://github.com/tile-ai/TileOPs/pull/2978 、https://github.com/tile-ai/TileOPs/pull/2980

1.6 測試與基準：GDN 掃描裁到每個排程區一行，fp8 用例迴歸各自目標

#2981 把 GDNFwdOp 的工作負載從 151 行 283 例裁到「每個排程區留一行」：規則是每個 bf16 組（核心身份、形狀區間、H200/SM89 排程區）保留首行，fp16 只在每個排程區首次出現的那一行保留，q35-gva-decode-b1 與 q35-gva-decode-b8 各留一行。#2991 修 tileops_test 的裝置判定：_Reference._device() 原先從標量上讀 .device，而 #2958 之後核心按位置接收呼叫期標量，導致 nightly off-cuda-suite 在 a0b7aeb6 上出現 61 個失敗；同時把三條 fp8 用例標回 in_tree_kernels，因為它們檢查的是樹內核心的拒絕行為，而 tileops_test 目標一律走參考實現。

來源：https://github.com/tile-ai/TileOPs/pull/2981 、https://github.com/tile-ai/TileOPs/pull/2991

三、生態與採用方（TileFoundry / topa / 站點 / TileKernels / FlashQLA）

3.1 TileFoundry 驗證器重構為單一 ctx 遍歷器，同步補共享記憶體寫衝突分析

#336 把 TIR 驗證器原先各自一套的遍歷器（walk_stmt、Binders、iter_all_stmts、獨立的 interfaces/verify visitor 與 mesh_scope 棧）合併到 StmtExprVisitor：可攜帶可選的 ctx，先按邊界順序訪問語句內的表示式再訪問子語句，分析不再按結構雜湊索引 Call 對映。該 PR 同時交代了一個警示：FSDP 訓練示例在 #325 與 #293 之後已經無法構建，而沒有測試捕獲到這一點。#326 補上共享記憶體寫衝突分析：cuda/analysis/threads.py 把每個共享記憶體寫與自身跨執行緒配對，只要某個 layout 能把每個位元組唯一分配給發起的執行緒、或關係證明兩個執行緒不會碰到同一位元組，才放行；此前「每個執行緒都向整塊共享記憶體瓦片發起同一次動作」會被接受，而下降階段為填充與複製生成的正是這類寫。

來源：https://github.com/tile-ai/TileFoundry/pull/336 、https://github.com/tile-ai/TileFoundry/pull/326

3.2 TileFoundry 單日新開 11 條 issue，集中在代價模型與排程器補洞

#337 至 #347 共 11 條新 issue，主題高度集中在「price/evaluate」——多波網格的拆分輸入只計價一次、按行計價的索引複製與 gather、masked row gather 的排程與檢查、DimVar 切片起點、per-thread 的 copy_async、f16 暫存器 MMA 與標量縮放的拆分暫存器、零填充邊界瓦片的 flash-attention 收尾等。其中 #344 說明為什麼這些缺口必須先補：帶呼叫方 cos/sin 表的旋轉位置編碼需要按 token 直接把錶行讀進暫存器，缺少帶索引的 gmem 到暫存器複製時，14 個工作負載裡有 5 個無法排程。這類 issue 是 TileOPs 新運算元能否按期落地的上游前置條件。

來源：https://github.com/tile-ai/TileFoundry/issues/344

3.3 topa 引入 new-op 輪次與狀態機，issue 按標題型別自動路由到 TileFoundry

topa 視窗內合入四筆。#24 讓 spec-only 的 manifest 條目有正式的 new-op 輪次入口（topa round start <Op> [--issue N]），並把輪次進度改成顯式狀態機，准入時拒絕已指派他人的 issue、他人已提名該運算元或關閉該 issue 的 PR、同一運算元或 issue 上的活躍輪次；#25 按 TileOPs 標題型別路由：[Perf] 進 perf 輪次，[Feat] 提名單個 spec-only 運算元的進 new-op、只提名已實現運算元的進新增的 extend 型別，其餘進 general，並規定每輪只對「生成程式與主分支不同」的其他運算元行計時，程式相同者標 unchanged 並附 program_diff 記錄；#23 解決輪次容器讀不到已安裝包內檢查清單的問題（把 topa 包按宿主路徑只讀掛載）；#22 修獨佔模式下空閒 GPU 被永久排除的問題——只有 nvidia-smi 列出計算程序時才算不可用。另有一筆 #26 在審，允許人工把 STOPPED 的輪次恢復到一個狀態。

來源：https://github.com/tile-ai/topa/pull/24 、https://github.com/tile-ai/topa/pull/25 、https://github.com/tile-ai/topa/pull/22

3.4 站點文件跟 manifest 變更，採用方兩倉視窗內無提交

TileOPs.github.io 合入兩筆：#86 跟隨 #2958 描述呼叫期 type/default、member()、list[Tensor] 與 random_ints，並把 API 頁改為 ClampFwdOp、LerpFwdOp、MaskedFillFwdOp 三個運算元（不再用 Scalar/Tensor 對），RoPE 頁改用 vLLM 的 (positions, query, key) 簽名；#87 補 validate_inputs 現在也校驗每個 in_range 邊界、int 成員可接受 float、以及 0.x 小版本破壞性變更的複核說明。採用方兩側：deepseek-ai/TileKernels 與 QwenLM/FlashQLA 視窗內均無提交（最新提交分別為 10-14 與 10-30）。

來源：https://github.com/tile-ai/TileOPs.github.io/pull/86 、https://github.com/tile-ai/TileOPs.github.io/pull/87

五、趨勢觀察

  • 運算元庫已成主戰場：本期 30 筆合入裡，TileOPs 佔 18 筆，主倉只有 4 筆執行時 bugfix；社群的工作重心從編譯器本體轉向運算元實現與介面真值。
  • 介面先於實現：manifest 的引數型別、pilot 模型介面在同一天補齊，隨後新運算元按輪次逐個落地，Embedding 的誤合與當日回退說明流程正在收緊，而非放鬆。
  • 流程工具化：topa 的 new-op 輪次、狀態機與 issue 路由，配合 TileFoundry 的代價模型補洞，構成「運算元需求 → 排程可行性 → 實現與驗收」的閉環，這一層是過去兩週增長最快的部分。
  • 效能修復開始反噬：W4A16 配對瓦片在部分小形狀上出現回退（issue #2966），量化 GEMM 的最佳化已進入「必須按形狀分檔」的階段，單一瓦片策略很難再普遍獲益。
  • 安全邊界需補：自建 CI 被外部 PR 穿透、個人 token 被盜用的事件提示，新貢獻者 PR 的 CI 觸發許可權應當預設需要維護者批准，這一條對整個 RISC-V 與 AI 編譯社群同樣適用。
  • RISC-V 側節奏平穩：本期只有 MLIR 路線一筆合入（buddy-opt 預設化與示例補齊），TVM 路線與算能 TPU 側無動作，屬正常的交替推進。
