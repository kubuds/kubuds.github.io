今日重點

這個視窗組織內只有 6 筆合入，比上一期的 9 筆再降三分之一，但結構比數字更值得看：6 筆裡 3 筆在主倉，且全部落在昇騰，沒有一筆 CUDA 或 CPU。最大的一筆是 #3516（20 個檔案，+1549/−182），把 tvm_ffi 提為 pto 目標的預設執行後端——此前 target="pto" 走的是 Cython 啟動器，現在 execution_backend="auto" 直接解析到 tvm_ffi，共享 host codegen 生成 MakePackedAPI 與 C host，並由昇騰執行時用 aclrtLaunchKernelWithHostArgs 啟動 PTODSL 編譯出的 aibin，路徑與 AscendC 核心一致。配套的是一處模組級工具鏈回撥：整個 PTODSL 模組在 device build 步驟內一次編譯完成（ptodsl → ptoas → bisheng fatobj-link → 抽取 .aicore_binary），結果按 ptoas 引數、ptoas 版本與 CANN 身份進快取鍵。舊路徑保留為 execution_backend="pto"，兩套產出逐位一致。

第二筆 #3776 是求解器側的收緊。AutoSchedule 原本用一個固定的週期下界起二分，這次改成取三條必要條件的最大值：單任務界沿用各任務啟動間隔的最大值；資源團界對成對沖突的任務按殘餘值排序，由相鄰差與首尾差推出週期不小於各啟動間隔之和；自依賴界由 S_u - S_u >= wait - d*P 反解出週期不小於 ceil(wait/d)，版本相關距離再按 num_stages 折算。沒有引入額外的下界探測，也沒有改排程模型。實證在 Ascend 950PR、CANN 9.3.0 的周版本上：關閉編譯快取，一熱三測交替，全部昇騰示例編譯透過且排程結果不變，Z3 求解階段累計耗時降 10.04%。

第三件事不在主倉。海光的分散式三件套 #36（6 個檔案，+2022/−0）在 16:20 合入 distributed 分支而非 main，內容是 Block-Push 版本的 GEMM + AllReduce、Block-Push 版本的 GEMM + ReduceScatter、Block-Pull 版本的 AllGather + GEMM 三個計算通訊融合運算元，效能資料與實現說明寫在 README。同一天 #37 開出 HCU 的 ds_read_vector Alt2 與 LDS 佈局推斷。這條線從 10-29 的 push-wave reduce-scatter 示例一路走到融合運算元清單，是海光倉第一次成體系地做分散式。

第四件事是質量側的一次集中爆發：視窗內 35 條新 issue 有 30 條落在主倉，其中 26 條直指昇騰。兩個賬號在下午到深夜之間各報了十餘條，形態高度一致——不是「跑錯了」，而是「本該報錯卻靜默透過」：T.Kernel 接受零或負的 block 數、T.alloc_l1 接受 2 GiB 分配、T.Persistent 接受負的 wave 與 stage、T.unroll 接受 −1 並吐出 #pragma unroll -1、負張量維度直接把編譯器打崩。另一組是語義錯位：hf32 的 nearest_zero 編譯成 NEAREST_AWAY、GEMM 輸入 dtype 表與 codegen 雙向不一致、reduce_bitand 一族吐出昇騰模板未定義的型別、同型 ND 轉 NZ 散射因掩碼計數不回退而陷入死迴圈。這批 issue 大多仍開放，但當日已有 VMI mask 校驗、SIMD fill 恢復等對應修復在審。

來源：https://github.com/tile-ai/tilelang/pull/3516 、 https://github.com/tile-ai/tilelang/pull/3776 、 https://github.com/tile-ai/tilelang-hygon/pull/36 、 https://github.com/tile-ai/tilelang/issues/3920

一、核心專案進展

1.1 昇騰：PTO 目標預設執行後端切到 tvm_ffi，整模組在裝置構建階段編譯並快取（#3516）

#3516（20 個檔案，+1549/−182）是本期最大的一筆。改動的實質是把 pto 目標從「專用 Cython 啟動器」遷到「與 AscendC 同一條 host 路徑」：target="pto" 配 execution_backend="auto" 時解析為 tvm_ffi，共享 host codegen 負責 MakePackedAPI 與 C host 構建，昇騰執行時模組用 aclrtLaunchKernelWithHostArgs 啟動由 PTODSL 編出的 aibin。

裝置構建側新增一個模組級工具鏈回撥，把整個 PTODSL 模組一次編譯完成：ptodsl 前端產出、ptoas 下沉、bisheng 的 fatobj 連結、再到 .aicore_binary 抽取，產物按 aibin 快取。快取鍵把 ptoas 引數、ptoas 版本與 CANN 身份一併算進去——這一點很關鍵，此前這類鍵漏掉工具鏈版本時，跨 CANN 升級會命中舊產物。

驗證面鋪得很寬，新增四組測試：auto 解析到 tvm_ffi、被調方分配輸出、動態形狀與動態輸出、多裝置核心、動態共享記憶體、cube/vector 混合 GEMM、source accessor、匯出庫、host 側迴圈啟動與 host 側 profiling 區間；另有等價性測試逐位比對 tvm_ffi 與舊 pto 在 vecadd、多核心與動態共享記憶體三種核心上的結果；兩組快取測試分別覆蓋二進位制快取與核心快取，其中快取命中跳過工具鏈、損壞條目拋錯、以及在全新程序裡命中。舊路徑按計劃保留，待覆蓋確認後再退役。

來源：https://github.com/tile-ai/tilelang/pull/3516

1.2 昇騰：AutoSchedule 用三條必要條件收緊週期下界，Z3 求解時間降 10.04%（#3776）

#3776（1 個檔案，+20/−1）只改初值，不改演算法：原來的二分從一個固定下界起步，現在先算三條必要條件再取最大值。單任務界保留各任務啟動間隔的硬下界；資源團界針對成對資源衝突的團，把任務殘餘值升序排列後，由相鄰差的約束與首尾差的約束相加得出週期不小於團內啟動間隔之和，團本身用每個任務作種子貪心列舉；自依賴界由 S_u - S_u >= wait - d*P 反解，版本相關距離以 num_stages 為上界。

實證環境寫得很具體：華為 Ascend 950PR、CANN 9.3.0 的 20261009.01 周版本，關編譯快取，每個配置一熱三測交替。結果有兩條：昇騰示例全部編譯透過且排程結果與改前一致（說明只收緊了下界、沒有改變解），Z3 求解階段累計耗時下降 10.04%。二分上下界與求解狀態處理均未改動，也沒有引入額外的下界探測流程。

這類改動對上游的價值不在單點效能，而在於排程器的求解時間隨運算元規模增長時，二分起點的浪費會線性放大——把必要條件寫進初值，等於給每次求解省掉一段無意義的區間。

來源：https://github.com/tile-ai/tilelang/pull/3776

1.3 昇騰：整數原子操作適配 signless 載體，12 條 PTO 用例覆蓋 32 位與 64 位（#3794）

#3794（4 個檔案，+52/−6）修的是 #3512 的後遺症。那筆改動把有符號整數型別從 signless 的 i32/i64 改成 si32/si64，而 PTO 的原子介面要求 signless 載體，於是 SIMT 核心裡的整數 add/min/max 原子操作直接編譯失敗。

改法是在生成的 PTODSL 呼叫邊界做區域性適配：把指標與運算元按同寬重解釋為 signless，保留指標的地址空間，返回值再還原成邏輯型別；min/max 保持原本的有符號或無符號比較語義。這樣 #3512 引入的邏輯型別體系不被推翻，適配只壓在原子這一層。

迴歸用例落在 testing/ascend/language/simtvf 下的 test_simtvf_atomics.py，覆蓋 32 位與 64 位的 add/min/max、負數運算元、返回舊值、超過 32 位的值、以及高位為 1 的無符號初值；新增的 12 條 PTO 用例在昇騰上全過。同批合入的 #3792 修的是同一族問題的另一面：T.atomic_add/max/min 因有符號輸入在 PTO 上編譯失敗。

來源：https://github.com/tile-ai/tilelang/pull/3794

1.4 主線：視窗三筆合入全在昇騰，CUDA 與 CPU 側盡在在審佇列，版本仍停 v0.1.15

把主倉視窗內的三筆合入按方向拆開看，結論很直接：#3516、#3776、#3794 全部落在昇騰，CUDA 與 CPU 側零合入。上一期還有三筆 CUDA 指令級原語進主幹，這一期一筆都沒有——不是 CUDA 側停了，而是全部堆在評審佇列：#3809（SM90 共享轉置降到 ldmatrix/stmatrix）、#3826（int16x16/uint16x16 的 256 位向量化）、#3723（SIMT im2col 提到 warp 特化之前）、#3923（流水 GEMM 運算元活到完成等待）、#3898（非同步 GEMM 共享運算元生命週期）都在視窗內有更新但未合。

版本側仍然掛起。主倉釋出頁最新仍是 09-30 的 v0.1.15，tag 序列未變；0.1.16 的版本號 PR 未在視窗內更新。TileOPs 釋出頁最新仍是 10-27 的 v0.1.0。也就是說，本期合入的 1549 行昇騰執行後端改動，最早也要等下一個 tag 才會進下游發行包。

來源：https://github.com/tile-ai/tilelang/releases 、 https://github.com/tile-ai/tilelang/pull/3809 、 https://github.com/tile-ai/tilelang/pull/3826

1.5 TIRx：ceildiv 與負 scale 的 split div/mod 兩筆在審，與巢狀 floor division 報錯同源（#93、#94）

tile-ai/tvm 側視窗內有兩筆在審：#94（[Fix][TIRx] Make ceildiv exact for signed divisors）與 #93（[Arith] Guard negative scales in canonical split div/mod）。兩筆都在修同一類問題的兩端——符號進入整除與取模後，規範化的改寫前提不再成立，於是「精確」與「安全」需要分開處理：ceildiv 要求帶符號除數時結果仍然精確，split div/mod 則要在負 scale 下拒絕規範化。

這與主倉當日新開的 #3937（[BUG] 巢狀 floor division 在負乘數下產出錯誤整數）指向同一處：負係數一旦進入算術化簡的改寫鏈，邊界條件很容易被漏掉。區別在於 #3937 是使用者側復現，#93/#94 是編譯器側先手加固。

來源：https://github.com/tile-ai/tvm/pull/94 、 https://github.com/tile-ai/tvm/pull/93 、 https://github.com/tile-ai/tilelang/issues/3937

二、多後端適配

2.1 海光：分散式三件套合入 distributed 分支，Block-Push 與 Block-Pull 兩條通訊路徑（#36）

#36（6 個檔案，+2022/−0）在上一期還是開啟狀態，本期 16:20 合入，落點是 distributed 分支而不是 main——該倉預設分支 main 的最新提交仍是 11-06，因此這筆改動不會出現在預設分支的提交列表裡，只有按分支查才能看到。落點差異需要寫明：main 與 v0.1.15-release 同引用，distributed 已單獨走出 11-03 的 signal 原語、10-29 的 push-wave reduce-scatter 示例與本期的三件套。

內容三個運算元：Block-Push 版本的 GEMM + AllReduce、Block-Push 版本的 GEMM + ReduceScatter、Block-Pull 版本的 AllGather + GEMM。Push 由計算側主動把結果推給對端，Pull 由計算側去拉對端的 allgather 結果，選哪條路徑取決於通訊域大小與重疊視窗，README 裡給了效能對照與實現方式。驗證側在 11-06 已補 Torch 效能基線到 GEMM reduce-scatter 基準，本期未再改。

來源：https://github.com/tile-ai/tilelang-hygon/pull/36

2.2 海光：ds_read_vector Alt2 與 LDS 佈局推斷開審（#37）

同一天 11:21 開出 #37（[HCU] Support ds_read_vector Alt2 and inferred LDS layouts），方向是把兩種指令形態補齊：ds_read_vector 的第二種編碼形態，以及可由約束推匯出的 LDS 佈局。這與 11-06 合入的 #34（用 DPP 與 lane swap 最佳化 reduction 的 XOR shuffle、並在自由候選之前先傳播已知佈局約束）是同一條佈局推導線，區別在於 #34 處理 reduction 側的通道交換，#37 處理向量讀的編碼與佈局落地。

海光倉當前有 15 個分支，其中 feat/hcu-* 系列六條、distributed 一條，說明這家後端的工作面已經從單卡指令擴充套件到通訊與佈局兩翼。

來源：https://github.com/tile-ai/tilelang-hygon/pull/37

2.3 mlir-ascend：CI 收為 Ascend 950 AscendC 單一 PR 門禁（#222）

#222（五個工作流檔案，+7/−9）在 10:27 合入 master 分支。改法刻意做小：所有作業定義、條件與步驟一律不動，只改每個工作流檔案的 on: 塊——這是最不容易被併發編輯的區域，合併衝突面因此最小。

動機寫得很直白：此前每個 PR 都會在整個上游矩陣上展開（自建 NVIDIA、AMD gfx942、macOS，以及一條先編 CANN 再跑兩遍 examples/ascend 與 testing/ascend 的昇騰腿），而 master 上唯一在開發的後端就是 Ascend 950，其餘腿基本是噪音，還在佔用稀缺硬體；PTO 後端當期也沒有人在推進。改完之後 PR 門禁只剩兩項：清潔程式碼 lint，以及 Ascend 950 的 AscendC 一條線。

這條改動對下游的含義是：mlir-ascend 倉的准入基線從此只有一代硬體，舊代昇騰的迴歸將不再作為合併條件。

3.3 TileOPs：softmax 兩 CTA cluster 達標，long-K NT GEMM 選擇器改動未達標（#2898、#2897）

4.1 昇騰前端一輪系統性審計：一日 30 條 issue，26 條直指昇騰（11-11）

4.4 口徑修正：K3 兩項 Q1 對照的舊 Triton 產物在 -128 取負時溢位（11-11）

把這條單列，是因為它影響的不是分數而是可比性。基準倉在釋出 weft-parity 的同批提交裡披露：K3 的兩項 Q1 對照此前用的是保留的 Triton Canonical 程式，該程式在對 −128 取負時溢位——邊界輸入得到 −2048，而正確結果應為 0。修復精確 I8 歸約的共享編譯器重新生成之後，兩種前端的產物都透過該輸入；歷史耗時保留在 triton_historical_us 欄位，修正說明寫在 triton_control_note。

對照實現出錯是基準類專案的常見陷阱：一旦參考側在邊界輸入上錯了，被測側的「不如參考」可能只是參考錯得更快。這條披露與 2.8 的配對口徑合起來看，說明這條 CPU 線在從「作者程式對比外部庫」轉向「同編譯器產物配對比較」，方法論上更可信，但兩張表不能混用。

來源：https://github.com/Tianchen-ai/tilelang-weft-bench/blob/main/docs/results.zh-CN.md

五、趨勢觀察

一是昇騰在主線上的權重繼續上升，且從「補運算元」轉向「補執行路徑與求解器」。本期主倉三筆全是昇騰：執行後端換預設、求解器收緊下界、原子操作適配型別體系。這三筆都不增加運算元名單，但在改「同一段程式怎麼被編出來、跑起來、以及多久能編完」。對照 10 月以來的記錄，昇騰側的合入已經從補齊 AscendC 運算元，走到介面語義、執行後端、排程求解器這三層。

二是CUDA 側進入長評審期。上一期還有三筆 CUDA 指令級原語進主幹，本期零合入而六筆在審（ldmatrix/stmatrix、256 位向量化、im2col 排程、流水運算元生命週期、非同步 GEMM 生命週期、PASS 配置名稱空間）。合入速率下降與在審佇列增厚同時出現，通常意味著評審頻寬成了瓶頸，而不是開發停擺。

三是質量審計開始與功能開發並行。一日 26 條昇騰 issue 的形態說明，社群裡已經有人在做系統性的非法輸入審計，而對應的修復 PR 當日就在佇列裡（mask 校驗、負引數拒絕、fill 下沉恢復）。這對一個正在把後端鋪到多家國產晶片的專案是好事：3060 項每日測試全過只證明合法路徑可用，非法路徑的拒絕能力得靠這類審計。

四是RISC-V 四源連續五個視窗靜默，但四源之外的 CPU 線給出了階段性結論。TVM 路線、MLIR 路線、社群索引頁、算能 TPU 四個上游都停在原引用；而 TileLang–Weft 用共享 Canonical 編譯器把 553 項全部做到 Triton 的 1.03 倍以內，四平臺中位倍率 1.29 至 1.66。需要注意這是口徑切換後的結果，不能與上一期的 0.058 倍直接比較。真正的觀察點是：這套「同一編譯器、兩套前端」的做法能否反向進入上游，以及 RISC-V 的 RVV/IME 路徑是否會被四源之外的專案先跑通。
