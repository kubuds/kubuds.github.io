今日重點：FlashQLA v0.1.4 釋出，雙卡 CP 擴到消費級 Blackwell

QwenLM/FlashQLA 於 11-25 23:16 釋出 v0.1.4，倉庫現有 770 星。這是採用方一側本視窗最完整的一次版本交付。

釋出說明列了三條主線。第一條是跨分割槽修正的精度路徑，支援 FP32 與三遍 TF32x3，由執行時按 wave 感知的啟發式選擇。卡間 h0 與 dht 摺疊改為經槽位對映直接讀已匯聚的 (h, M) 緩衝，不再物化解包與重索引。

第二條是 SM120 與 SM121 上的雙卡 CP，前向與反向都覆蓋卡間加卡內組合。實現透過新增 aggregate_card_state 與 aggregate_m 完成。

第三條是 ZigZag 卡間 CP 佈局。第 r 個 rank 負責每篇文件的第 r 塊與第 2·cp−1−r 塊，與注意力層的切分位置對齊，且不要求改動 TileLang kernel。

其餘改動偏工程。KKT 求解改成 8×8 對角塊代入，合併 FP16 MMA 與 FP32 遞推，按 FlashInfer 的塊狀求逆獨立重寫。flash_qla.warmup() 可把全部靜態引數組合預編譯進 JIT 快取。CP 介面 build_cp_context 預設開啟卡間與卡內，並接受 zigzag=。

修復項裡有一條與上一期日報的 SM120 線索相接。block_DV=64 與一處 __threadfence_block 阻止 nvcc 把 g_exp_shared 提升到屏障之外。反向屏障現在先提交 dV 寫入，再讓 K 複用 dqkv_shared。

基準覆蓋三檔硬體。單卡為 H200、GB200 與 RTX 5090。雙卡 CP 為 H200×8、GB200×4 與 RTX 5090×2。釋出另附 Auto-CP 與 Dual-CP 的技術報告。

來源： https://github.com/QwenLM/FlashQLA/releases/tag/v0.1.4。

今日重點：夜間輪子改掛 0.1.16，版本串改制帶出兩處迴歸

tilelang-nightly 視窗內出了兩個輪子。11-25 13:18 的構建為 v0.1.16+d20261125.git3684ae6a，22:30 的為 v0.1.16+d20261125.gitfa93ba14。前一日還是 v0.1.15+d20261124。

這說明 11-24 合入的版本號已進入打包鏈。GitHub 標籤最新仍是 v0.1.15，Releases 最新仍為 9-30 的 v0.1.15，PyPI 上 tilelang 也是 0.1.15。所以準確說法是構建側已到 0.1.16，釋出尚未完成。

版本串格式同步改了。舊格式為 0.1.15+cuda.d20260125.githash，新格式為 0.1.16+githash，dYYYYMMDD 日期段不再出現。

改制帶出兩處迴歸，都在 11-25 17:26 前後報出，環境為原始碼構建 a3a4f9ce。

#4513 報 build_date() 對 dev 版本靜默返回 None。該函式的正則為 [+.]d(\d{8})，依賴日期段。新舊兩種格式的解析本身都正確，問題在於實際產物已不帶日期段。

#4514 報昇騰 NPU 上 do_bench 必崩，錯誤為 aclrtDeviceL2CacheFlush failed: 207000。profiler 的 NPU 路徑把 cache 緩衝改成 cache_numel=0 的空佔位後，_flush_cache 會無條件呼叫 aclrtDeviceL2CacheFlush(None)。在 dav-3510 與 CANN 9.2.1 上該呼叫失敗。兩條 issue 均已有 4 條討論。

來源： https://github.com/tile-ai/tilelang/issues/4513。

今日重點：主倉三筆全在快取子系統，快取鍵納入工具鏈版本

主倉視窗內只有三筆提交，兩筆直接改快取。這與前幾日 ROCm 批次修復、昇騰缺陷報告形成明顯分工。

#4511 把當前 CUDA 與昇騰工具鏈版本納入 kernel 快取鍵，改 20 個檔案。新增 tilelang/contrib/bisheng.py，pto_toolchain.py 相應瘦身。BackendModule 增加 toolchain_stamp 回撥，允許零引數呼叫。CUDA 編譯器選擇摺疊進 _cuda_compiler_module。

改動動機是快取失效邊界。此前換編譯器或換 CANN 版本後，舊二進位制仍可能命中快取。測試側同步補了昇騰二進位制快取、PTO 快取與 JIT 診斷三處用例。

#3756 處理共享快取的許可權。快取條目先暫存再整目錄改名釋出，因此沿用建立程序的 umask。在 SGID 加組可寫的共享快取根上，umask 077 的程序會發出 0700 與 0600 的條目，其他使用者讀不到。

修法是釋出前legalize暫存條目。快取根帶 SGID 時目錄改為 0o2755，檔案改為 0o644 並保留可執行位。不帶 SGID 的根，以及不支援該位的檔案系統，保持原樣。該筆新增 148 行許可權迴歸測試，並修了共享快取目錄初始化與多根查詢。

配套還有一筆在審。#4512 題為按工具鏈身份給可執行快取做鍵，與 #4511 屬同一主題。

來源： https://github.com/tile-ai/tilelang/pull/4511。

一、核心專案進展

1.1 快取鍵納入 CUDA 與昇騰工具鏈版本，跨工具鏈複用被切斷

#4511 由 LeiWang1999 於 23:09 合入，是本期唯一的功能性改動。提案說明分四步走：先按活躍工具鏈給 CUDA 與昇騰 JIT kernel 做鍵，再把工具鏈感知限制在 CUDA，隨後把昇騰工具鏈也納入，最後統一各後端的工具鏈印記。

結構上新增 BackendModule.toolchain_stamp 鉤子。CUDA 側由 tilelang/cuda/backend.py 提供版本串，昇騰側由 tilelang/ascend/backend.py 提供。兩者都改走 contrib 下的適配層。

測試側改了六個檔案。除三類快取用例，還調整了 host-mapped 輸出校驗測試，該測試顯式關掉 kernel 快取。

來源： https://github.com/tile-ai/tilelang/pull/4511。

1.2 共享快取按 SGID 釋出組可讀條目，umask 077 不再產出私有目錄

#3756 由 KellyFrog 於 16:18 合入，改 kernel_cache.py 與一個新測試檔案。提案把問題歸因到釋出方式：暫存後整目錄改名，許可權來自 umask，與共享根的 SGID 意圖不一致。

判定條件只看快取根是否帶 SGID。帶則目錄 0o2755，檔案 0o644，可執行位保留。不帶則不動，覆蓋 Windows 等不支援該位的檔案系統。

測試覆蓋共享根與私有根兩種情形。非 POSIX 系統與不支援 POSIX 許可權的檔案系統會跳過。

來源： https://github.com/tile-ai/tilelang/pull/3756。

1.3 CUDA 注意力樣例測試並行化，CI 單作業時間壓縮

#4485 把 block causal attention 的樣例用例改成並行跑，並給 Z3 加預算。改 3 個檔案，含 ci.yml 一行。

提案中途撤過一次 DeepSeek TopK 的 Z3 預算覆蓋，隨後恢復 z3 限額。前一日的 #4463 與 #4489 也圍繞同一組 TopK 用例的求解器耗時，本期這筆屬測試時長的收尾。

來源： https://github.com/tile-ai/tilelang/pull/4485。

1.4 夜間輪子改標 0.1.16，build_date() 對 dev 版本返回 None

兩個夜間輪子都基於 0.1.16。22:30 那個對應提交 fa93ba14，即本期 #4485 的合入點。13:18 那個對應 3684ae6a，屬視窗起點後的第一筆。

#4513 指出 tilelang.build_date() 在 0.1.16+gita3a4f9ce 上返回 None。

解析側對舊格式與新格式都正確。舊格式 0.1.7.post3+cuda.d20260127.gita17230e4 能解析出 20260127。手工構造的新格式也能。唯獨真實 dev 產物不行。

這是公開 API 的靜默迴歸，不影響構建與執行，但會讓依賴構建日期的診斷與復現指令碼失效。

來源： https://github.com/tile-ai/tilelang/issues/4513。

二、多後端適配（昇騰 / 海光 / 摩爾執行緒 / 沐曦）

2.1 昇騰子倉給 bitwise_xor 加 dtype 前置校驗，崩潰改成 ValueError

#1986 於 15:24 合入 ascendc_pto 分支，改 6 個檔案。提案關聯 #1722，目標是讓不支援的輸入在進入編譯器前被拒。

前端檢查 dst、src0、src1 三個運算元。允許 int8、uint8、int16、uint16、int32、uint32，拒絕浮點與 64 位整數。判斷按標量元素型別做，相容向量化 dtype。

lowering 階段另做一次檢查，覆蓋繞過公開 API 直接構造 intrinsic 的路徑。int32 與 uint32 僅在 PTO A5 且關閉 tl.ascend_memory_planning 時放行。

裝置端計算實現與 workspace 分配未改。測試側讓 XOR 的 tmp 契約用合法 int16 緩衝，保留原有的 workspace 槽位與佈局斷言。

來源： https://github.com/tile-ai/tilelang-ascend/pull/1986。

三、生態與採用方（TileOPs 運算元庫 / FlashQLA / TileFoundry）

3.1 TileOPs 九筆，DeepSeek-V4-Flash 兩條模型級效能

TileOPs 視窗內 9 筆合入，兩筆直接改模型側呼叫方式。

#3171 把 DeepSeek-V4-Flash 的 indexer ReLU 改成非原地。ReLUFwdOp(inplace=True) 會把結果寫進新緩衝再拷回輸入，而該模型只讀返回的分數。這次複製回寫在 4096 token 預填、ratio-4 層上涉及 537 MB 分數的多一次讀寫。

#3170 讓四類索引張量每個 Step 只算一次，由第一個讀它的層負責。四類分別是 top-k 讀取的 closed-entry 計數與零首項、全 closed 層的整份 key index、以及解碼步的 ring 槽位。視窗型別為 int32，索引層不再逐層重算。

來源： https://github.com/tile-ai/TileOPs/pull/3171。

3.2 解碼步改由 CUDA graph 重放，昨日工作項當日落地

#3168 於 15:00 合入，改 10 個檔案。CausalLM.forward 現在同時服務兩個模型：模型提供本次呼叫的索引後設資料與轉發主體。

cuda_graph 預設開啟。解碼步在 CUDA 裝置上重放 _run 的圖，token 緩衝與 Step.moved_to 原地改寫。每個相位的首步先急切執行，再在模型自己的流上捕獲。

這條正是上一期新開工作項 #3155 的實現。配套在審的 #3175 要求兩個模型的每個解碼運算元都透過 CUDA Graph 捕獲資格測試。

來源： https://github.com/tile-ai/TileOPs/pull/3168。

3.3 foundry 五筆：INT8 tile 擴到 192 寬，量化與取樣各修一處空轉

五筆以 foundry 為字首，都屬運算元級調優。

#3162 給 INT8 64 行 GEMM 的 tile 表加 80、112、192 三檔。192 寬走 T.wgmma_gemm 而非 dense WGMMA helper。48、144、176、208、224、240 仍排除，實測每次選中都更慢。

#3163 讓 FP8 原地分組量化的末塊只載入實際存在的行。單塊啟動時，例如 DeepSeek-V4-Flash 一行七組的 KV，冗餘載入會讓 kernel 多花 64 至 96 納秒。

#3164 把 16 位 concat 輸入經共享記憶體展寬到 float32，用 16 位元組讀與整行寫。#3166 把拆分的 top-p 行分箱摺疊到塊內每個執行緒。#3167 讓 16 位 isinf 一次處理兩個 lane，塊大小 1024 執行緒。

#3169 另修 RoPE 參考實現裡零 token 的頭數計算。

來源： https://github.com/tile-ai/TileOPs/pull/3162。

上一期該筆還在審，本期合入。它把 TileFoundry 的驗證面從單運算元擴到訓練步級。

來源： https://github.com/tile-ai/TileFoundry/pull/366。

五、趨勢觀察

  • 快取正從實現細節變成一等公民。一天之內三筆圍繞它：快取鍵認工具鏈、共享快取認許可權、在審那筆按工具鏈身份給可執行快取做鍵。多使用者構建與多工具鏈並存是驅動因素。

  • 0.1.16 的釋出路徑已鋪到構建側。夜間輪子先改標 0.1.16，標籤與 PyPI 仍停在 0.1.15。版本串去掉 backend 標籤後，兩處依賴舊格式的程式碼當天就報了迴歸，說明格式變更的相容面比預期寬。

  • 昇騰的缺陷構成在變。前一日是十個「不該接受的輸入被接受」，本期是 T.fmod 缺下降、SimtVF 作用域誤判、PTODSL 多 kernel 符號衝突。問題從介面契約下沉到編譯與連結層，單條修復成本上升。

  • TileOPs 的最佳化開始落到模型呼叫方式，而不只是 kernel 內部。ReLU 換非原地、索引張量每步只算一次、解碼步整體走 CUDA graph，三者都在減少排程與複製，而非提升單核算力。

  • 採用方節奏在加快。FlashQLA 一天內完成 v0.1.4 的程式碼、基準、文件與技術報告，TileFoundry 把驗證面推到訓練步級。TileLang 的下游不再只寫 kernel，也開始寫系統級示例。

  • RISC-V 側連續三個視窗零變化。TVM 路線與 MLIR 路線都停在原位，索引頁也沒有新 PR。
