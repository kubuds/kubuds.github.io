今日重點

這個視窗最重的動作是減法。主線把三週前合入的精確執行緒計數（#3291）整筆回退（#3733），理由寫得很直白：那套改動把昂貴的計數查詢搬到了滿塊柵欄檢查之前，即使所有執行緒都會到達柵欄也要跑證明，當前 TVM 的求解預算會被耗盡並返回部分計數，於是本來合法的 remap 與 sequence 輔助 kernel 直接以「Cannot prove a thread rectangle」編譯失敗。回退在兩套 ThreadSync 實現上同時進行，刪掉 #3291 引入的測試，補一個「迴圈對多數執行緒為空、256 執行緒仍全部到達柵欄」的歸約用例；商守衛、精確參與執行緒界、非矩形執行緒集這些正確性改進也一起撤回，新開的 #3732 留作遷移後重新最佳化的跟蹤單。這是明確標註為臨時措施的遷移讓路：TileLang 正在準備 TIRX 遷移以擺脫當前 TVM fork 依賴，配套的 TVM fork 最佳化提案已經關閉。

第二條線是昇騰在補地基。#1948 修的是宿主側一筆與運算元規模無關的固定損耗：Cython wrapper 每次呼叫都無條件構造 TVM Analyzer，實測在 910B3 上約 0.28 毫秒一次，而它只在形狀為符號表示式時才用到；改成惰性構造後，vec add 單塊從 442 至 467 微秒降到 105.1 微秒，32 塊從 441 至 493 微秒降到 108.0 微秒，kpool 壓縮從 447 至 450 微秒降到 111.3 微秒，作為下限的裸 ctypes 呼叫約 12 微秒沒變。同期 #1971 的 RFC 給出同步實現的替換路線：移植主線同步核心加獨立的 Z3 證明服務，用舊 TIR 適配層接進現有編譯流水，保留 TVM、排程、記憶體規劃、AscendC/PTO codegen 與執行 ABI，驗收透過後再切預設實現並刪除舊演算法——與 #1975 把整個 Ascend 倉遷到主線多後端架構是一件事的兩個落點。

第三條線在運算元庫。TileOPs 在 11-01 一天合入 13 筆，幾乎全部是效能補丁，且每筆都附 H200 實測表與 manifest 迴歸門檻。其中 #2808 把 GQA 稠密前向的程式選擇收成一條規則，相對最快候選程式的選擇遺憾從 1.818 降到 1.017（2 至 128 個 query 位置、586 次呼叫），並修掉主線一個真實錯誤：score scale 在乘上 log2(e) 後於 FP32 下消失，輸出變成 NaN 或錯值。

一、核心專案進展

1.1 主線：ThreadSync 的精確執行緒計數回退，為 TIRX 遷移讓路（#3733）

合於 11-01 14:50。被回退的 #3291 把精確執行緒計數移到滿塊柵欄檢查之前，並加入矩形認證，代價是即使全部執行緒都到柵欄也要跑一遍 CountSatisfyingValues；TVM 側求解預算耗盡後返回部分計數，remap 與 sequence 輔助 kernel 隨即以「[ThreadSync] Cannot prove a thread rectangle」失敗。迴歸在主線 cc903dcb9 加未改動的 TVM pin 4211874e9e 上覆現，新用例把它縮成「迴圈對多數執行緒為空、256 執行緒仍全部到達柵欄」。回退同時覆蓋共享與昇騰兩套實現，恢復滿塊快速路徑與舊的部分計數行為；原文明確這是 TIRX 遷移期間的臨時緩解，TVM fork 側的最佳化提案 tile-ai/tvm#89 已關閉，後續最佳化轉入 #3732。

來源：https://github.com/tile-ai/tilelang/pull/3733

1.2 主線：CUDA 跨 warp 全歸約合併為一次共享記憶體交換，256 執行緒從 6 道柵欄降到 2 道（#3715）

合於 10-30 20:26。舊實現在 CUDA 歸約標頭檔案 reduce.h 裡從 threads/2 遞迴到 scale，凡是 offset 不小於 32 的每一步都做一次完整的共享記憶體寫讀交換並配兩道柵欄：256 執行緒塊的三步（128、64、32）合計 3 次共享記憶體往返、6 道柵欄，512 執行緒塊是 4 次、8 道。改法是把所有跨 warp 步驟壓成一次交換（每元素一次 st.shared、共 2 道柵欄）：先在 warp 內做 scale 小於 32 的那一段，再讓每個 warp 內組裡不超過 cross_radix 的若干 lane 協作摺疊，暫存器壓力有上界。標量與批次兩條路徑都改了。

來源：https://github.com/tile-ai/tilelang/pull/3715

1.3 主線：PTO 後端的 T.Parallel 向量化落地第一里程碑，逐元素運算元走 VMI 指令（#3512）

合於 10-30 01:29。目標是讓使用者在 T.SimdVF(lanes=L) 裡寫標量並行的逐元素 T.Parallel，由編譯器向量化成 PTO VMI 指令，再經 PTOAS 在昇騰 950 上執行。分工寫得很清楚：TileLang 側負責邏輯 lane 佈局推導、向量化 pass 流水線、VMI 指令生成與 Fragment 邏輯對映；PTOAS 側負責物理暫存器切分、掩碼具體化、Fragment 緩衝與向量暫存器分配、mem_bar 插入。路線圖分五個里程碑，本筆是 M1 核心框架（逐元素計算，覆蓋 extent 能否被 lanes 整除兩種情況），M2 控制流、M3 reduce、M4 UB 容量規劃與暫存器分配、M5 非連續訪問與更寬的 PACK 資料型別依次跟進。

來源：https://github.com/tile-ai/tilelang/pull/3512

1.4 主線：昇騰 DeepGEMM 的 scale 緩衝改用寫計數多緩衝，資料載入可提到條件載入之前（#3629）

合於 10-30 05:48。DeepGEMM 會在多個 K 塊之間複用 scale factor，本筆新增顯式的寫計數多緩衝模式，讓 scale 緩衝的版本按真實寫入推進：每個 owner 迴圈迭代裡只在第一個實際執行的寫任務處推進一次，後續寫入共享該版本，沒有寫入的迭代沿用舊值，支援多個不相交 owner 與共享時鐘。這樣資料載入可以排到條件化的 scale 載入之前；同時把 DeepGEMM 的 K 迴圈攤平，在 L1 與 L0 上都先取資料再取 scale，並補了守衛更新、巢狀更新、保留讀、flag 與緩衝複用以及 FP4 的 K 主序與 MN 主序帶尾塊和環形迴繞的用例。該模式要求顯式版本數，並假定每個 owner 迭代最多一次更新。

來源：https://github.com/tile-ai/tilelang/pull/3629

1.5 主線：兩筆修復合入，CPU 標量 GEMM 只清目標區域、負索引合法化跳過不可達分支（#3709 / #3712）

兩筆都在 10-30 合入，屬上一期在審條目的落地。#3709 讓 CPU 標量 GEMM 只清理目標區域，此前會連帶清掉不屬於本次輸出的範圍；#3712 讓 LegalizeNegativeIndex 跳過不可達分支，避免對不會執行的程式碼做負索引改寫。這兩條與上一期報告的 #3708、#3710 屬同一批缺陷清理，其中 #3708 的位寬改 int64、#3710 的關快取時繞過兩層程序內快取仍在審。

來源：https://github.com/tile-ai/tilelang/pull/3709、https://github.com/tile-ai/tilelang/pull/3712

1.6 主線：語言層清掉 proxy 裡兩個無人使用的 Ref 佔位（#3722）

合於 10-31 17:31。tilelang/language/proxy.py 裡同時存在兩個 Ref：一個給型別檢查用的 tirx.Var 樁，一個空的執行時類，兩者在樹內都沒有消費者；對外的 T.Ref 實際來自 eager.builder，那裡的實現才是宏引用引數的本體。本筆刪掉兩個佔位、_T 型別變數以及隨之無用的 Generic、TypeVar 匯入，保留 T.Ref 與宏引用行為，只移除 tilelang.language.proxy.Ref 這條無人使用的直接匯入路徑。前端構造測試 179 項透過、6 項跳過，執行時身份檢查確認 T.Ref 仍是 eager.builder.Ref。

來源：https://github.com/tile-ai/tilelang/pull/3722

1.7 新開缺陷與在審：TMEM 靜默丟結果、ROCm 符號找不到、TF32 就近偶數舍入（#3721 / #3711 / #3714）

#3721 是本視窗最值得警惕的一條：在 sm_100a 上對 TMEM 做 T.gemm，當 threads/32 不能整除 N 時，編譯能過、PTX 裡卻一條 tcgen05.mma 都沒有，T.copy(Ct, Cl) 讀的是沒人寫過的 TMEM，乘積被靜默丟棄；復現裡 threads=256 出一條，threads=384 出零條，作者懷疑 src/cuda/op/gemm.cc 給 TCGEN05 返回 {1, num_warps} 分割槽時缺了覆蓋性檢查。#3711 報告 ROCm 7.14 與 10.0 的 PyTorch wheel 下 kernel 報「named symbol not found」。#3714 在審，為 fp32 到 tf32 的轉換補上就近偶數舍入（cvt.rn.tf32.f32 與飽和形式），非飽和要求 SM90 以上、飽和要求 SM100 以上，關閉對應的功能請求 #3713。

來源：https://github.com/tile-ai/tilelang/issues/3721、https://github.com/tile-ai/tilelang/issues/3711、https://github.com/tile-ai/tilelang/pull/3714

二、多後端適配（昇騰 / 海光 / 摩爾執行緒 / 沐曦）

2.1 昇騰：Cython wrapper 惰性構造 TVM Analyzer，910B3 單次呼叫從約 450 微秒降到約 106 微秒（#1948）

合於 10-30 07:44。CythonKernelWrapper.forward() 此前每次呼叫都無條件構造一個 TVM Analyzer()，在 910B3 上是約 0.28 毫秒的固定宿主開銷，而該物件只在 result 或 workspace 形狀為符號表示式時才用到；靜態 shape 的 kernel 完全用不上，卻同樣付這筆錢。改法是把構造延遲到 tir.PrimExpr 分支內並按需複用。實測：vec add 單塊 442 至 467 微秒降到 105.1 微秒，32 塊 441 至 493 微秒降到 108.0 微秒，kpool 壓縮 447 至 450 微秒降到 111.3 微秒，裸 ctypes 呼叫約 12.5 微秒降到約 12 微秒。新增兩例迴歸，分別驗證靜態路徑不構造、符號路徑按需構造。

來源：https://github.com/tile-ai/tilelang-ascend/pull/1948

2.2 昇騰：RFC 提出把同步實現換成主線核心加獨立 Z3 證明服務（#1971）

本 RFC 不預設提速結論，只固定比較基線：Ascend 倉在 TileLang 43b0b69 與 TVM c2921fd 上、IR 基礎是舊 tvm.tir；主線在 TileLang 1c0f402 與 TVM 4211874e9e 上、IR 基礎已是 tvm.tirx 與 tvm.s_tir，物件與註冊體系也換成新 FFI 與反射設施。因此遷移不能簡化為複製一個 InsertSync 檔案。建議路線是移植主線同步核心與獨立 Z3 證明服務，透過舊 TIR 適配層接入現有編譯流水，保留現有 TVM、排程、記憶體規劃、AscendC/PTO codegen 與執行 ABI，完成支援範圍、正確性、效能與安裝驗收後再切換預設實現並刪除舊同步演算法。配套 PR 為 #1965。

來源：https://github.com/tile-ai/tilelang-ascend/issues/1971

2.3 昇騰在審：把 TileLang-Ascend 整體遷到主線多後端架構（#1975）

10-31 提出並持續更新，目標是按提案 #1911 把 TileLang-Ascend 遷移到 TileLang 主線的多後端架構上；描述裡給出兩份差異對照，一份對 ascendc_pto 分支，一份對主線。這條與 2.2 的 RFC 是同一條收斂路徑的兩個層面：一條改同步演算法，一條改倉的骨架。

來源：https://github.com/tile-ai/tilelang-ascend/pull/1975

2.4 昇騰在審：GLM-5.3 kpool 的 fp8_mqa_logits 示例，雙 kernel 加 AIV/Cube 分工（#1966）

五、趨勢觀察

這一視窗最值得記錄的判斷來自上游自己：寧可回退正確性改進，也要把 ThreadSync 的複雜度從關鍵路徑上撤下來。回退說明裡寫清了代價——商守衛、精確參與執行緒界、非矩形執行緒集這三類改進一併撤回，只保留舊的保守路徑，#3732 留待 TIRX 遷移完成後再談最佳化。一個編譯器專案願意公開寫「我們的證明器預算不夠，先退回保守實現」，比再堆多少功能都更能說明當前階段的真實約束：TIRX 遷移是主線第一優先順序，其他最佳化都要給它讓路。

與之呼應的是昇騰側兩份「向主線收斂」的文字：#1971 的 RFC 要把同步演算法換成主線核心加獨立 Z3 證明服務，先調研、後替換、中間留舊 TIR 適配層；#1975 直接把整個 Ascend 倉遷到主線多後端架構。兩條路都要付出遷移成本，於是近期的可見工作會偏向地基類：#1948 把每次呼叫的固定宿主開銷從約 450 微秒壓到約 106 微秒，四筆文件事實核查，CI 清理內部快取引用，都是這類工作。

TileOPs 的節奏則從「發版」切到「調優」。72 小時 15 筆合入裡 13 筆壓在同一天，幾乎每筆都附 H200 實測表與「manifest 無回退」宣告，並且開始用選擇遺憾這類指標描述排程規則的好壞（#2808 從 1.818 到 1.017）。這意味著運算元庫的競爭點已經從「有沒有這個運算元」變成「每條 shape 上是否都挑對了程式」，而這恰好是 TileLang 這類 DSL 相對手寫 kernel 的長期價值所在。

生態側出現兩條新分叉。一條是硬體方言：海光把 gfx948 當 gfx946 相容、昇騰繼續補 PTO 文件與符號形狀。另一條是語言出口：RISC-V 研究鏈把受限 PrimFunc 降到單 hart RVV C，星標很低、作者也明確宣告不是官方後端，但它把 TileLang 的 IR 當作可移植資產來用，與昇騰、海光的倉級分支適配是同一類訊號。多條分叉同時存在，上游 TIRX 遷移能否給出穩定的 IR 邊界，將決定這些下游投入是沉澱還是返工。
