今日重點：Ascend 950 後端公開釋出——134 提交原生後端 PR 開出，0.1.15 版本號同步提升（09-30）

日期：2026-09-30　來源：Ascend 950 後端 PR（#3308）／ 版本提升 PR（#3309）／ 釋出分支 ascend-950-0930

09-30 凌晨，TileLang 主倉連開兩筆標誌性 PR：標註「Public Release 9/30」的昇騰 950 原生後端與版本號提升至 0.1.15。前者以 134 提交、379 檔案、+79956/-733 的體量，把昇騰線從獨立適配倉推進為主倉的一等後端：

  • 端到端路徑：新增 Ascend 語言方言，覆蓋核心啟動、記憶體分配、資料搬運與計算操作，含硬體特化 lower、自動排程與同步、裝置程式碼生成、畢昇（Bisheng）編譯與 NPU 執行時裝載；使用者以 target="ascend" 可直接開發 Ascend 950 核心。
  • 程式設計模型：單核心內組合 Cube（AIC）T.gemm 與 Vector（AIV）計算；T.SimdVF / T.SimtVF 區域混合 SIMD 與 SIMT 程式設計；UB / L1 / L0 顯式分配；T.copy / T.dual_copy 分塊搬運與跨核傳輸；含 MXFP8 / MXFP4 塊縮放 GEMM 低精度路徑。
  • 編譯器與排程：昇騰分形佈局的自動推斷與儲存歸一化；AutoSchedule 做依賴與時延感知的 Cube/Vector 排程、流水與多緩衝；排程感知的核內與跨核同步插入，附帶冗餘同步消除、標誌位自動分配與複用。
  • 構建整合：USE_ASCEND 構建開關、畢昇編譯鏈、執行時載入與核心啟動均入主倉；按既有後端介面接入多後端架構，複用共享編譯器設施。
  • 評估口徑（PR 內）：對照 Torch NPU，以 BF16 GEMM、FP8 轉換與 GQA 反向各 4 個形狀評測；GEMM 與 GQA 報 TFLOP/s、FP8 轉換報有效 GB/s。
  • 規模與署名：分支與 main 同步、領先 134 提交，視窗內仍在追加修復（最新提交恢復廣播向量化與標量歸約，09-30 凌晨）；Co-author 計 10 位，含 2 位 deepseek.com 署名開發者。
  • 聯動：同日開出的 0.1.15 版本提升 PR 僅改 VERSION 一行（0.1.14 至 0.1.15），與 950 後端相鄰落賬，是否同批發布待觀察。

判讀：若合併，昇騰 950 將首次以主倉原生後端形態落地（此前昇騰支援主要由獨立適配倉承載），「多後端」從映象倉適配升級為主幹能力；對使用方，昇騰 950 的運算元開發與 DeepGEMM 風格核心可直接用 TileLang 編寫。風險面在於體量（379 檔案、約 8 萬行新增）帶來的審查與合併後穩定性成本，且 NPU 側效能目前僅有 PR 內圖表的公開口徑。

1.1 主倉：Simplify 未用繫結消除器合入——讀後寫、副作用與後設資料引用均有迴歸兜底（09-29）

日期：2026-09-29　來源：Simplify 未用繫結（#3293）

  • 上期新開條目本視窗合入：為 tl.Simplify 增加 UnusedBindRemover，當其值可在不丟棄相關副作用與 volatile 緩衝讀取的前提下被捨棄時，反覆移除未使用的 BindNode。
  • 邊界規則：遍歷反射欄位與容器以保留被後設資料引用的繫結；緩衝區定義與載入謂詞中用到的繫結一律保留；迴歸用例覆蓋未用宏繫結、讀後寫、副作用、volatile 讀取、後設資料引用與共享表示式節點。
  • 意義：tl.Simplify 的清理能力擴充套件與上週的模餘數界修復（#3294）同向——變換層「敢刪什麼、必留什麼」逐步寫成可測試的明確清單。

1.2 主倉：Windows wheel 構建恢復 ccache 命中——clang-cl 引數改分寫（09-29）

日期：2026-09-29　來源：Windows 構建修復（#3305）

  • 問題：Windows wheel 構建恢復 ccache 後仍反覆重編 TVM——單次約 32 分鐘、554 次未命中、命中率僅 20.63%，連續三晚夜構建同型。根因是 CMake 對 clang-cl 輸出粘連式 -imsvc<path> 引數，ccache 4.9.1 將其計入預處理雜湊，PEP 517 依賴目錄一變快取鍵就變；既有包裝器可歸一化預處理文字但去不掉命令列差異。
  • 修復：將 -imsvc <path> 改為分寫形式，快取鍵恢復穩定；同日建立併合入，評審批註自動摘要複核。

1.3 主倉佇列：七筆新開與原子操作修復線，開放 PR 計 116 筆（09-29/09-30）

日期：2026-09-29、2026-09-30　來源：主倉 PR 列表／ 原子操作修復（#3307）／ DeepSelect 示例（#3304）／ 打包向量比較（#3303）

  • 視窗內新開 7 筆：#3303 為 FP16/BF16 打包向量比較（修缺陷單 #3302，掩碼內建歸一 0/1、NaN 正確的不等於，CUDA 12 以下與低算力保留標量回退）；#3304 提交 DeepSeek DeepSelect Top-K 的 TileLang 示例（無內聯 PTX，依賴在審的 #3303 與 #3296，在 RTX 5090 上對照 torch.topk 給出 129 組實測）；#3306、#3307 為原子操作修復線（int64 原子 max/min 與 AtomicStore 的 int64/bf16/fp16 崩潰，可溯源至 #1716 的型別歸一化；#3306 關閉未合入、#3307 接續在審）；#3308、#3309 見今日重點。
  • 存量更新：SM120 暫存器 A GEMM（#3286）、z3 執行緒推斷（#3291）、C 源匯入換行（#3289）、popcount 擴充套件（#3300）等視窗內均有更新。

1.4 TileOPs：INT8 量化與反量化四枚核心合入——逐位對齊 torch 參考（09-29/09-30）

日期：2026-09-29、2026-09-30　來源：逐張量反量化（#2304）／ 逐通道反量化（#2306）／ 逐張量量化（#2307）／ 逐通道量化（#2308）

  • 上期「先定契約、再落實現」進入核心兌現期：INT8 家族的量化與反量化共四枚運算元層在核心側落地，清單狀態轉 implemented，輸出逐位對齊 torch 參考實現（含 scale 下溢為零的邊界用例）。
  • 逐張量反量化（#2304）：q 按扁平序列讀取，每執行緒每步轉一個 16 位元組輸出向量、每 64 執行緒塊四步且先發全部載入；碼點經指數偏置整數加法加 FADD 轉換（繞開 I2F）；塊內輸出先入共享記憶體再做批次寫出（SM90 上走 cp.async.bulk）；新增 L1 evict-last 載入輔助（streaming_load.h）。
  • 逐通道反量化（#2306）：向量跨行時在兩行尺度間選擇，任意 K 單程式執行；逐通道量化（#2308）：一個 CTA 獨佔一行、行內常駐暫存器，尺度用倒數加兩次 FMA 正確舍入，行首行尾與鄰行共享向量並做掩碼。
  • 逐張量量化（#2307）：單次協同啟動完成——第一階段讀入並交換 amax 分片（網格級屏障），第二階段量化出片；每次呼叫構建核心，顯式宣告編譯邊界。
  • 進度：量化族 9 枚 spec-only 條目中已有 7 枚進入核心實現（INT8 六枚 + INT4 一枚），FP8 逐塊與 SmoothQuant 尚未見核心 PR。

1.5 TileOPs：INT4 逐組量化核心合入，塊量化兩筆排隊（09-30）

日期：2026-09-30　來源：INT4 逐組量化（#2317）／ 逐塊量化（#2316，在審）／ 逐塊反量化（#2318，在審）

  • INT4 逐組量化落位兩枚核心：packed_weight、weight_scale、weight_zero 與 torch 參考逐位相等，且採用 GemmW4A16FwdOp.repack 的打包格式——W4A16 權重鏈路的格式對齊是本次最實用的相容點。
  • 核心要點：每 lane 持一個 32 元素塊，128 元素 K 步內無需跨 lane 搬數；四乘四字轉置出 16 位元組連續儲存；組尺寸支援 32 至 1024 的 2 的冪；另備行核心版本。
  • 在審兩筆：INT8 逐塊量化（#2316）與逐塊反量化（#2318）——均沿用 #2304 的排程模板，補齊“張量/通道/塊”三檔的最後一塊。

1.6 TileOPs：取樣運算元層合入——上期排隊六枚正式落賬（09-29）

日期：2026-09-29　來源：取樣運算元層（#2299）

  • 上期報告記為「排隊待審」的六枚取樣運算元層（TopKMask、MinPMask、TopPMask、TopKTopPMask、SamplingFromProbs、ChainSpeculativeSampling）於 09-29 下午合入：運算元層、工作負載與測試一次備齊，參考數值對齊 FlashInfer 0.6.16（bf16/fp16/fp32 三檔），隨機數用 Philox4x32-10 整數張量算術實現、與 Random123 已知答案向量一致。運算元層仍為宣告式（kernel_types = {}），核心實現待後續 PR。

1.7 TileOPs：注意力四筆——FP8 表示式下沉、varlen 出站轉共享記憶體、SM89 頭維 512 修復（09-29/09-30）

日期：2026-09-29、2026-09-30　來源：FP8 GQA 葉子運算元（#2294）／ varlen 預填出站（#2313）／ SM89 頭維 512（#2312）／ 滑窗用例分層（#2311）

  • FP8 GQA 下沉（#2294）：輸出累加器清零改用 T.clear、KV 尾部掩碼錶達為佈局感知的 T.Parallel 迴圈，刪除兩處已無用的 CUDA 輔助；屬 #2113 增量。評估過的 softcap 的 T.tanh 替換因回退被有意排除——保留近似 tanh 路徑。
  • varlen 出站走 SMEM（#2313）：varlen GQA 預填的輸出不再從 acc_o 片段雜湊寫出，而是經已失效的查詢塊共享緩衝整行 16 位元組寫出，零額外共享記憶體開銷；部分塊保留守衛式直寫。
  • SM89 頭維 512 修復（#2312）：單 warpgroup 的 32 行塊不再把分數塊留在暫存器（此前佈局推斷衝突導致 block_m=32 候選從未編譯成功）；預設配置新增 32×16 候選（需 68 KiB，低於 SM89 上限）。
  • 測試分層（#2311）：滑窗 varlen 的 8 個用例標記 SM90 專用——此前在 SM89 上是以失敗出現而非跳過。

1.8 TileOPs：核心介面與共享記憶體治理兩筆（09-29）

日期：2026-09-29　來源：核心介面與分派（#2300）／ 共享記憶體上限表（#2303）

  • 核心介面化（#2300）：為運算元宣告核心介面，經單一查詢分派——把「核心介面、實現、呼叫規格、可用性」等七個概念寫進 ops-design 設計文件；替換實現按介面契約校驗而非僅按鍵名，後端可在內建實現旁增補自己的實現。
  • 共享記憶體治理（#2303）：共享記憶體上限收斂到統一表格；FP8 GEMM 宣告 supported_archs = [90]（SM89 呼叫被明確拒絕而非誤選 TMA/WGMMA 核心）；稀疏 MLA 對視訊記憶體放不下的呼叫做下界評估後拒絕（如 SM86/SM89 上每塊 64 頭、d=512 需不低於 100 KB 超出 99 KB 上限的場景，此前會啟動失敗）。

1.9 TileOPs：CI 與工程規範三筆——八併發冒煙、絕對匯入、清單校驗單次化（09-29/09-30）

日期：2026-09-29、2026-09-30　來源：GPU 冒煙八併發（#2314）／ 絕對匯入規範（#2310）／ 清單校驗單次化（#2319）

  • 冒煙提速（#2314）：PR 冒煙從單程序單卡改為八工作程序；簽名檢查惰性生成；並順手修復 bs1 解碼的屏障衝突。背景值得記錄：主分支推送的測試數 4281 增至 5174（+21%）、pytest 耗時 324 秒增至 605 秒（+87%），增量主要來自清單體系的 CPU 工作而非核心測試。
  • 規範（#2310）：src/tileops/ 全部匯入改為絕對匯入並用 ruff TID252 強制（ban-relative-imports = "all"，234 檔案重寫）；設計文件同步。
  • 清單校驗（#2319）：validate_manifest.py 每 PR 由三次跑改一次（GPU 冒煙中該測試佔關鍵路徑 22 至 32 秒），並讓 FMA 飽和度量跟隨被取樣 GPU。

1.10 TileOPs：元素級提速兩筆——除法回退按執行緒一次、f32 雙 16 位元組裝載（09-29/09-30）

日期：2026-09-29、2026-09-30　來源：除法回退（#2305）／ f32 裝載與 bool 儲存（#2309）

  • 除法族（#2305）：FloorDivide、Remainder 與 floor 模式 Div 在 #2291 改為逐位精確後回退 1.01 至 1.28 倍；現改為 fast_func 逐執行緒統一快判，僅在失敗執行緒回讀運算元執行精確回退，核心維持 32 暫存器上限；16 位快路徑用 a * (1/b) 上推修正。
  • f32 裝載（#2309）：同形狀二元核每執行緒改兩次 16 位元組裝載（對齊 inductor 的 XBLOCK 1024 四 warp 形態）；比較與邏輯類 bool 結果改按執行緒連續段一次儲存——此前 1.002 至 1.006 倍於 torch-compile 的行由此收斂。

2.2 昇騰：ascend 倉兩筆修復——TVM 一行補丁揭開回退真因（09-29）

日期：2026-09-29　來源：TVM 回溯越界補丁（#1846）／ CI 子模組清理（#1847）

  • 回退真因水落石出（#1846）：給固定的 TVM 子模組加一行補丁，修復 TVM 生成錯誤呼叫棧時的越界讀（std::string tmp(symname, symsize) 改為單引數構造）。背景是上期報告記錄的「#1829 合入 4 天后被整筆回退」：9 個期望拋 tvm.error.InternalError 的編譯器負例在 x86 runner 上穩定 SIGSEGV、在 ARM runner 上穩定透過；同機單變數 A/B 實驗表明崩潰來自這一 TVM 缺陷，與 #1829 的邏輯無關。補丁沿用既有 apply_tvm_patches.sh 機制（三個構建入口自動應用、已應用者跳過、未來不適用時構建直接報錯而非靜默）。
  • CI 清理（#1847）：自託管 runner 上 actions/checkout 不清子模組、git submodule update 又只在 commit 變化時切指標，導致上一 PR 打進 TVM 的補丁洩漏進後續所有構建（#1846 的構建即因殘留報補丁無法應用）；修復為構建前重置子模組。
  • 判讀：#1829 被回退並非其自身缺陷——被回退特性是否按乾淨基線重提，是接下來的觀察點。

五、趨勢觀察

5.1 從契約到核心：量化族 48 小時完成兌現

上期報告的觀察點是「本批運算元層尚無核心，後續看核心落地節奏」。不到 48 小時，量化族 9 枚中 7 枚已進入核心實現：INT8 四枚合入且逐位對齊 torch 參考，INT4 逐組一枚合入並對齊 W4A16 打包格式，INT8 逐塊兩枚在審。單批 PR 的說明正規化也已成型——逐筆註明與參考實現的逐位一致性、編譯邊界、清單狀態與拒絕語義，「先證明正確、再談效能」。按此節奏，剩餘 FP8 逐塊與 SmoothQuant 兩枚的落地是下一觀察視窗的看點。

5.2 Ascend 950：多後端敘事從「適配倉」走向「主倉原生」

昇騰 950 後端以 379 檔案、約 8 萬行新增的 PR 直投主倉，且與 0.1.15 版本提升同日開出——TileLang 的「多後端」正在從映象倉適配升級為主幹能力，對標基線也直接選擇華為自家的 Torch NPU。署名中可見 deepseek.com 郵件與多位社群核心開發者共 10 人 Co-author，說明昇騰線是多方協同的整建制投入，而非單點適配。需要冷靜看待的是：PR 尚未合入、體量巨大、效能資料目前僅有 PR 內圖表口徑；合入後的主線穩定性與跟進維護成本將是更長週期的觀察點。

5.3 工程承載力：測試量 +21% 下的 CI 重構

主分支測試數 4281 增至 5174（+21%）、pytest 耗時 +87%，增量主要來自清單體系的 CPU 側工作——這正是「200 運算元、契約先行」策略的直接成本。當日回應是三項工程化：GPU 冒煙八併發、簽名檢查惰性化、清單校驗單次化（去掉每 PR 兩輪重複校驗）。能力擴張期把 CI 從「夠用」重鑄為「扛規模」，是這一週被低估的基建敘事。

5.4 空白與風險點

其一，多後端分化繼續：沐曦（09-24 後）、摩爾執行緒（09-17 後）、MLIR 昇騰（09-24 後）靜默，熱度集中於昇騰與海光；其二，主倉「開多合少」未逆轉——本視窗合入 2 筆、新開 7 筆，開放 PR 達 116 筆，審查頻寬仍是瓶頸，昇騰 950 大 PR 的合入節奏將直接檢驗這一點；其三，#1829 被回退特性的重提、0.1.15 正式出版與 TileRT v0.1.6 釋出頁補票均懸而未決；其四，量化與取樣式核心的驗證目前以逐位對齊與單機基準為限，端到端模型精度影響尚無公開驗證。
