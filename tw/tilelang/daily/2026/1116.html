今日重點

這個視窗的重心換了位置。上一期主倉一天五筆合入、全部落在昇騰；本期主倉 72 小時只有一筆文件提交（LSP 倉庫連結），而 TileOPs 三天十五筆、TileFoundry 三筆，加上昇騰適配倉九筆——程式碼量幾乎全部轉移到了運算元庫與排程器上。TileOPs 在 11-15 一天之內合入十一筆，其中解碼側的 W4A16 瓦片從單 consumer warpgroup 擴到兩個，七條解碼行快 10–20%，對 marlin 的領先拉到 1.20 倍以上。這不是零散修補，而是按「運算元 + 選擇器 + 代價模型」三層一起改：先讓選擇器在更多形狀上選中雙 warpgroup 的瓦片，再給瓦片補上按 K 切片的後設資料載入，最後用 nightly 的 32 行迴歸確認沒有一行變慢。

同一天裡出現了本期最值得記的一條因果鏈。11-13 的 #2896 把 128 行 W4A16 瓦片換成手寫 warp-specialized 主迴圈，在 H200 上把 chunked-prefill 從 37.3 微秒壓到 31.6 微秒；36 小時後，#2901 在修它——sliced_pair 的 out_shared 暫存被寫在 i // wg_rows == bz 的條件分支裡，而 TileLang 有時會把守護這次寫操作的、覆蓋全部 256 個消費執行緒的屏障放進同一個分支，另一個 warpgroup 永遠走不到那個屏障，兩個 warpgroup 停在同一屏障的不同例項上，核心掛死。更麻煩的是屏障落點在同一 cache key 的兩次編譯之間並不穩定，而 CI 的持久化核心快取會把壞構建一直重放下去，於是 main 上的 gpu-smoke 直接掛了。修法本身很樸素——讓兩個 warpgroup 都做暫存，各自只存自己那一半——但它說明了一件事：自動 warp specialization 的正確性已經不只取決於 pass 順序，還取決於屏障被插在哪個分支裡，而這個位置對編譯過程不透明。

第二件事在 issue 側，量級比程式碼側更醒目。72 小時內 tile-ai 組織新開 406 條 issue，其中 cn-sys 一個賬號在 11-15 傍晚 1 小時 46 分鐘裡連開 172 條（編號 #4208–#4381 連續，無一條夾帶其他來源），ilovexsir 三天分三批開了 142 條，兩人合計 314 條，佔全量的七成七。cn-sys 這一批的覆蓋面從 examples 與 README 的具體數字（flash-attention 號稱前向誤差低於 0.5%、而同目錄五個檢查器全用 5%；deepgemm 的 benchmark 用 8192 當 cache_size，而該引數單位是 MB，等於分配 8 GiB 去刷 128 MiB 的 L2）一直延伸到編譯器本體：auto-schedule 的 IR 結構訪問器漏欄位、PTO codegen 的指標元素型別取了個硬編碼 bfloat16 兜底。ilovexsir 那一批更成體系：142 條 issue 對應五個 batch PR（#4201–#4205，同一分鐘開出），每個 PR 修一組「本該報錯卻沒報錯」的入口，比如 T.copy(transpose='False') 因為字串 ‘False’ 是真值而靜默開啟了轉置、_make_ascend_target() 用 dict(target_dict or {}) 把所有 falsy 配置鍵丟掉。審計與修復之間開始形成流水線，代價是在審佇列堆到 102 筆。

第三件事是昇騰側的運算元遷移進入了「按演算法家族成批落地」的階段。11-13 一天裡，tilelang-ascend 合入九筆：DSA 稀疏注意力的前向流水版、反向、topk 歸約三件套，KDA 的 chunk_delta 三件套，加上 bitwise 四合一、alloc API 文件與 catlass 子模組升級。這些不再是單點補洞，而是按模型走：DeepSeek V3.2 的 sparse MLA 把 DQK 合成 512+64=576 一次 GEMM、Kimi 系 KDA 把門控衰減吸收到 host 端預計算的 M 矩陣裡、反向運算元把 79395 微秒壓到 27388 微秒。與此同時 catlass 從 v1.0.0-6 升到 v2.2.0，順帶修掉一個此前完全靜默的缺陷：舊版 CopyL1ToL0A/L0B 沒有 float 特化，fp32 GEMM 直接輸出 NaN 或負無窮而不報錯。

RISC-V 側本期首次打破靜默。kubuds 的 TVM 路線從 mahiru、karen 之外新開 kubuds-riscv-hikari 分支，五筆提交裡有 K3 移植與驗證報告、rv64gc 構建解鎖（USE_LLVM=ON 的連結問題與八執行緒構建）、解碼 4 瓦片與預填充 8 瓦片的網格劃分、以及 XSMTVDotII/vmadot 公開規格的溯源記錄；同一時間，社群索引頁收到第一筆 PR，把 kubuds fork 的專案說明寫進 README。MLIR 路線（RuyiAI-Stack/tilelang-riscv）與算能 TPU 倉的引用則一動不動，兩條路線仍要分開看。

1.1 主倉 72 小時只有一筆文件合入，版本仍停 v0.1.15（11-13）

tile-ai/tilelang 的 main 在 72 小時視窗內只有一次提交：11-13 16:20（UTC）的 210611dc，內容是把文件裡的 TileLang LSP 倉庫連結更新到新地址（#4052）。沒有新運算元、沒有後端改動、沒有釋出——最新 tag 仍是 09-30 的 v0.1.15，版本號已在原地停了六週。

對照上一期主倉一天五筆昇騰合入、合計 +1903/−617，這個視窗的主倉幾乎靜止。但靜止只發生在 main 上：主倉有 51 筆 PR 在視窗內更新、27 筆視窗內新開，其中 #4201 到 #4205 五個 batch PR 與 #4138、#4207 的 cast 生命週期修復都是實質改動，只是還沒跨過 review 門檻——這一期主倉的產出形態是「審計 + 提 PR」，不是「合入」。

來源：https://github.com/tile-ai/tilelang/pull/4052

1.2 TileOPs：11-13 四筆效能合入，MoE、GQA、softmax、W4A16 各一條線（11-13）

視窗首日 TileOPs 連合四筆，覆蓋四類不同負載。MoE 分組 GEMM 的 FP8 前向把 A 的 scale 從生產者暫存改成走 TMA box（#2894），讓 ds-v3-ep8-prefill-up 與 -down 的 128 行瓦片把 stage_scales 從 1 降到 0，H200 上分別從 269.3 微秒降到 262.0、從 142.2 降到 137.2，對 DeepGEMM 的比值升到 1.096 與 1.157。W4A16 的 128 行瓦片改成手寫 warp-specialized 主迴圈，在上一塊 WGMMA 還在跑的時候解碼下一塊 K（#2896），chunked-prefill 從 37.3 微秒降到 31.6。軟歸約把 16 位 softmax 行放到兩個 256 執行緒 CTA 的叢集上而不是四個 128 執行緒 CTA，fp16 項用一條 FFMA 完成「按縮放後的最大值平移」（#2898）。分頁 GQA 的切分上界同時被視窗內的 key 瓦片數與 combine 的讀量卡住（#2892），順帶關閉了 #2496 那條懸了很久的標定請求。

來源：https://github.com/tile-ai/TileOPs/pull/2894、https://github.com/tile-ai/TileOPs/pull/2896、https://github.com/tile-ai/TileOPs/pull/2898、https://github.com/tile-ai/TileOPs/pull/2892

1.3 TileOPs：11-15 單日十一筆，W4A16 解碼瓦片再快 10–20%（11-15）

11-15 一天十一筆合入，其中 #2955 是當日的收口：W4A16 選擇器把「至多 32 行」的延遲縮放挑法從一個 128 執行緒 consumer warpgroup 挪到兩個，按權重行數分攤、按 K 切片拆分以保住 CTA 數，stream-K 仍留單 warpgroup。理由是解碼瓦片被指令發射卡住而代價模型偏愛單 warpgroup 的做法——實測那條路徑上 issue slot 佔用 49.5%、DRAM 只有 54%。結果七條解碼行比 main 快 10–20%，對 marlin 領先至少 1.20 倍，prefill-mlp-up 未變且仍落後 torch 0.7%。同一天還有 #2952 把目標側核心的兩張表併成一張、讀取前先複製以避免併發下「迭代中字典改變大小」，#2904 修掉一次「沒有裝置、沒有具名 target、沒有程序預設」的呼叫丟擲 _Unresolved object is not callable 的問題。

來源：https://github.com/tile-ai/TileOPs/pull/2955、https://github.com/tile-ai/TileOPs/pull/2952、https://github.com/tile-ai/TileOPs/pull/2904

1.4 TileOPs：ping-pong 三連，MoE 共享專家在每個重複裡壓過 FlashInfer-CUTLASS（11-15）

同一主題三筆遞進。#2919 先讓分組 GEMM 選擇器自己挑出的 64x256 單 warpgroup 緊緻瓦片改跑雙 warpgroup 的 ping-pong，使每個瓦片的收尾落在另一組的 mainloop 之下，ds-v3-grouped-t2048 的下投影 GEMM 從 1818 微秒降到 1707。#2953 把同一手法推到選擇器自己的 64 行緊緻瓦片上，覆蓋融合 gate/up 與短分組瓦片，並明確「短分組瓦片仍留一個 warpgroup，因為它的收尾太短、藏不住東西」；結果是 FusedMoESharedExpert 的 ds-v3-grouped-t2048 在每次重複裡都壓過 FlashInfer-CUTLASS（中位 5674 對 5744 微秒），32 行六運算元的程式變化沒有一行變慢。#2915 則把未融合的 ping-pong 分組 GEMM 輸出按 64 列 TMA box 暫存，換來第五個環級（64x256 瓦片多出 40 KiB 一檔）。

來源：https://github.com/tile-ai/TileOPs/pull/2919、https://github.com/tile-ai/TileOPs/pull/2953、https://github.com/tile-ai/TileOPs/pull/2915

1.5 TileOPs：#2901 修 #2896 帶來的掛死，屏障落進了 warpgroup 分支（11-15）

這是本期最值得讀的一筆。#2896 合入後，main 上的 gpu-smoke 掛了：sliced_pair 在 i // wg_rows == bz 這個條件下暫存 out_shared，經佈局 lowering 後只有「保留那半個瓦片」的 consumer warpgroup 會執行暫存迴圈；TileLang 有時會把守護這次寫操作的、覆蓋全部 256 個消費執行緒的屏障插進這個分支，另一個 warpgroup 永遠走不到，兩組停在同一屏障的不同例項上，核心死等。#2899 先前加的那道顯式屏障並不足以阻止它——編譯器仍可自行在分支內插屏障。修法是把暫存挪出條件：兩個 consumer warpgroup 都寫自己的那一半。真正刺眼的是後半句：屏障落點在同一 cache key 的兩次編譯之間會變化，而持久化的 CI 核心快取會把壞構建一直重放，於是一次不穩定插樁變成了穩定失敗。

來源：https://github.com/tile-ai/TileOPs/pull/2901、https://github.com/tile-ai/TileOPs/pull/2899、https://github.com/tile-ai/TileOPs/pull/2896

1.6 TileOPs：#2918 讓編譯圖跨程序複用，一次 pyupgrade 改 1926 處（11-15）

#2918 把編譯邊界的鍵從「每程序一個 uuid」換成「運算元類 + 引數摘要 + 構造期張量佈局 + 該例項在類內的序號」，於是後啟動的程序可以直接複用 Inductor 的 FX 圖快取與 AOT autograd 快取；代價是引數一旦被賦新值就要重追蹤，被就地修改則在追蹤期直接拒絕。同一筆還把 tileops.backend、authoring、manifest 三個包的 pyright --verifytypes 拉到 100%（此前為 100%/50%/21%），並把 ruff 的 UP 規則全倉應用——307 個檔案 1926 處。這類提交不產生效能數字，但它決定了 nightly 與 CI 的等待時間，也決定了新人能不能靠型別提示讀程式碼。

來源：https://github.com/tile-ai/TileOPs/pull/2918

1.7 TileOPs：manifest 補四個 spec-only 運算元，從 Embedding 到 RoPE 餘弦正弦（11-15）

#2920 給試點的五個模型缺的四個運算元補了「只有規格、沒有實現」的清單條目：EmbeddingFwdOp（含整數表，對應 DeepSeek-V4-Flash 的雜湊路由）、MaskedScatterFwdOp、RMSNormGatedFwdOp（帶 sigmoid 門控的啟用引數）、RoPECosSinFwdOp（按 token 給角度，允許 x 是帶步長的檢視以支援尾列旋轉）。同時新增 tileops.indexing 家族、給每條補 torch 參考實現到 tests/test_spec_reference.py、按讀取行數為 embedding、masked scatter 與 RoPE 定價（兩個 roofline 函式加一個內聯 bytes，各配手寫 oracle）。這套做法的意義在於：先把介面與定價釘死，實現可以是後來者補的。

來源：https://github.com/tile-ai/TileOPs/pull/2920

1.8 TileOPs：#2951 自適應池化按 lane 拆分，主分支三種池化在窄長形狀上編譯不過（11-15）

1.9 TileFoundry：#325 用一種 FunctionRef 統一全部被調者命名（11-13）

IR 裡此前有五種命名被調者的方式——繫結的 Function/PrimFunction 物件、槽繫結的例項呼叫、保留呼叫、啟動目標、變體標籤——每個消費者各按自己的方式解析，求值器甚至從「載入的讀法」而不是模組作用域裡挑定義。#325 把它們收成一個靜態葉子 FunctionRef(path, name)：路徑相對呼叫者，None 段表示執行期索引、作為前導運算元傳入，core.resolve(scope, ref) 成為唯一解析器；解析器同時把「@module 裡後宣告的名字」定義為錯誤（DeclarationOrderError）。連帶的清理包括 StoragePlan.scratch 改為發射前算好、刪掉 relaunch、host 入口宣告並轉交 scratch。

五、趨勢觀察

一是主倉靜、運算元庫動，重心位移已經連續兩個視窗。上一期是主倉一天五筆全昇騰、TileOPs 連續零提交；這一期反過來，主倉 72 小時一筆文件，TileOPs 三日十五筆、TileFoundry 三筆。把兩期並起來看，TileLang 的開發重心正從「編譯器本體」移到「運算元庫 + 排程器」：編譯器本體的改動集中在修迴歸（PTO 那條線的善後期），而新增能力更多以運算元庫的瓦片、選擇器、代價模型的形式出現。判斷依據不只是合入數，還有依賴方向——TileOPs 的效能結論要引用 TileFoundry 的 roofline 與排程，而 TileLang 主倉這一期沒有給它們任何新東西。

二是自動 warp specialization 的正確性已經成為一等風險。#2896 到 #2901 這條鏈說明：當一個效能改動把同步責任交給編譯器自動插樁時，插樁位置就成了正確性的一部分，而它對上層不透明——同一個 cache key 兩次編譯，屏障可能落在分支內也可能落在分支外。再疊上 CI 的持久化核心快取，偶發的壞插樁會被固化成穩定失敗。這一問題目前沒有結構性解法，只有「把寫操作挪出條件分支」這類區域性規避；如果後續更多瓦片走 ping-pong，同類掛死大機率會再出現。

三是審計已經從「發現問題」變成「流水線生產問題」。三天 406 條 issue、兩個賬號 314 條，其中 cn-sys 的 172 條在 1 小時 46 分鐘內寫完，ilovexsir 的 142 條直接對應五個 batch 修復 PR。這套模式確實在壓縮「缺陷發現到修復」的週期（同一天內 issue 與 PR 並存），但它把壓力轉移到了評審端：在審 102 筆、合入 30 筆，其中 22 筆 mlir-ascend 同構 PR 只能由極少數人過。下一階段的瓶頸會是評審頻寬，而不是發現速度。

四是昇騰的運算元遷移進入「按模型家族成批落地」。DSA 三件套對應 DeepSeek V3.2，KDA 三件套對應 Kimi 系線性注意力，一天之內九筆都指向具體模型的完整鏈路，而不是零散運算元。這對下游是好訊息——模型遷移的成本從「逐個運算元湊」變成「按家族批次搬」；但也意味著底層模板庫的質量權重上升，catlass 那個 fp32 GEMM 輸出 NaN 而完全不報錯的舊缺陷就是例證：它藏在第三方 submodule 裡，靠運算元層測試發現不了。

五是RISC-V 四源首次出現實質推進，但只有一支在動。kubuds 的 TVM 路線新開 hikari 分支並給出 K3 移植驗證與 RVV 網格資料，社群索引頁第一次收錄該 fork；而 MLIR 路線（RuyiAI）與算能 TPU 倉引用未動。兩條路線的分工已經明確：TVM 路線在做「能跑起來、有實測資料」，MLIR 路線停在「有設計、無提交」。判斷不變——這條線目前仍屬小規模投入，值得按視窗跟，但不宜按周計算進度。

侷限說明：本期結論來自 GitHub 檢索介面與倉庫原子流，未做程式碼級複核；PR 的效能數字取自作者在 PR 描述裡給出的基準表（H200、CUDA 13.2、PyTorch 2.13），未在本機複測。issue 統計依賴 search 介面的 total_count 與五頁翻頁結果（406 條與逐條彙總一致），標題分類只按關鍵詞粗分。tilelang-ascend 的預設分支是 ascendc_pto 而非 main，首次查詢按 main 取提交返回 404，已改正後重查。mlir-ascend 的 harness 與 hygon 的 tilelang-tileops-fix 分支視窗內均無提交。新聞側零命中，無外部報道可交叉驗證。
