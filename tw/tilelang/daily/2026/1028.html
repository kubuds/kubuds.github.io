今日重點

一、核心專案進展

1.1 主倉：ROCm 的 exp/sin/cos 不再預設降到快速內建，sin/cos 誤差從 7.8e-04 降到 6.6e-08（#3621）

合於 10-27 22:39，5 檔案 +107/-17，修 #3618。在 HIP 上，T.exp、T.exp10、T.log、T.log2、T.log10、T.sin、T.cos 七個預設函式無論 tl.enable_fast_math 如何設定都會降到 __expf 一類快速內建，而 CUDA 側按 #875 的約定走精確實現；反過來，顯式的 T.__exp 等快速運算元在 HIP 上根本不下沉，在 tilelang.rocm.language 裡直接拋 AttributeError。本筆讓 HIP 與 CUDA 採用同一策略：七個預設運算元改派 HIPMath，八個帶下劃線的快速運算元新增最低下沉規則指向 HIPFastMath，並統一挪進 FAST_MATH_INTRINSICS 列表由 ROCm 語言層匯出。精度對比取 #3618 的復現：MI300X 上 exp 與 exp10 看相對誤差、sin 與 cos 看絕對誤差（x 到 1e4），四列依次為 T.exp、T.exp10、T.sin、T.cos，主幹為 3.7e-06 / 4.1e-06 / 7.8e-04 / 7.8e-04，本筆為 8.3e-08 / 8.1e-08 / 6.6e-08 / 6.4e-08。

來源：https://github.com/tile-ai/tilelang/pull/3621

1.2 主倉：自動目標改讀當前 HIP 裝置，多卡機上不再固定取 0 號卡架構（#3594）

合於 10-27 22:37，2 檔案 +24/-1。determine_target(“auto”) 在 ROCm 上落到註冊的 HIP 探測器，而該探測器無條件讀 torch.cuda.get_device_properties(0)，於是當前 HIP 裝置不是 0 號卡時，自動探測給出的是 0 號卡的架構；CUDA 側早就在用 torch.cuda.current_device()，ROCm 沒有跟上。修法是先取當前裝置索引再查屬性，並用 normalize_rocm_arch 去掉特性字尾。新增測試把 current_device() 打樁返回 1，同時記錄所有被探測過的索引，斷言探測到 gfx942 且只碰過 1 號卡；修復前該斷言得到 probed == [0]。作者註明本機無 ROCm 裝置，測試只用打樁 torch 驗證探測助手，未跑真實 HIP 執行時；與本日另一筆 #3549 改動的是不同函式（#3549 在 tilelang/contrib/rocm.py，本筆在 tilelang/rocm/target.py）。

來源：https://github.com/tile-ai/tilelang/pull/3594

1.3 主倉：TMA gather/scatter 的常量行索引轉為 int32，字面量寫法不再編譯崩（#3365）

合於 10-27 09:15，2 檔案 +44/-2，修 #2601。tma_gather4 與 tma_scatter4 兩個前端助手在收到 Python 整數形式的行索引時直接透傳，落到 TIR 裡沒有確定的整型寬度，於是在 Blackwell 上編譯崩潰；其他行表示式保持原樣。本筆只把 Python 整數轉成 int32 的 TIR 常量，並補一個受 Blackwell 門控的編譯迴歸，用字面量行索引分別編譯 gather 與 scatter，再檢查生成的 CUDA 原始碼裡確實出現對應指令。作者說明該測試只驗證能編譯，不驗證執行時數值正確；且提交者本機的 Windows Python 3.13 環境裡 Home Assistant 的 pytest 外掛依賴 fcntl，pytest 收集階段就失敗，本筆的 TileLang 測試在本地並未真正跑起來。

來源：https://github.com/tile-ai/tilelang/pull/3365

1.4 主倉：NVRTC 與 CuTeDSL 按首個輸入張量所在裝置取當前流（#3359）

合於 10-27 08:11，2 檔案 +5/-4，接 #3301 的 F149 與 #3408。兩個介面卡此前用字串字首判斷目標型別，且預設取呼叫方當前裝置的當前流，於是呼叫方當前 GPU 與張量所在 GPU 不一致時選錯流。本筆改用目標種類判斷，並按首個輸入張量的裝置查當前流，顯式傳入的流控制代碼仍然最高優先，無張量的 NVRTC 呼叫維持原語義。這是繼昨日 out_idx 輸出分配流（#3649）之後，流語義清理的第二筆。作者劃清邊界：本筆只修流選擇，跨裝置的預設流啟動上下文仍是未解項，這類呼叫方必須自己在啟動前把張量所在裝置設為當前裝置，補丁裡沒有逐呼叫的裝置守衛；驗證時用真實 Torch 流與 GPU 啟動覆蓋了同裝置與跨裝置的非預設流，但未建立跨裝置預設流上下文的正確性。

來源：https://github.com/tile-ai/tilelang/pull/3359

1.5 主倉：自動調優快取鍵納入 compile_flags，同一核心換編譯選項不再複用舊二進位制（#3338）

合於 10-27 16:57，3 檔案 +28/-1，接 #3301 的 F131。自動調優器把編譯結果持久化快取，但快取標識裡沒有 compile_flags，於是同一個核心換一組裝置編譯器選項後仍會命中舊二進位制，測出來的效能與真實編譯結果對不上。本筆讓 CompileArgs 真正存下並按原有順序參與雜湊，並把 flag 從 JIT 實現經 AutoTuner.set_compile_args() 一路透傳到候選編譯、逐配置的 pass 合併、分組裝置編譯與快取核心載入。驗證覆蓋三條既有快取鍵測試，以及用原生執行時對 CUDA 做的定點對比：列表與字串兩種 flag 形式都能在逐配置覆蓋中存活；作者指出原先的合併邏輯會把編譯器宏丟掉，正是這次要堵的口子。

來源：https://github.com/tile-ai/tilelang/pull/3338

1.6 主倉：ThreadSync 把 address_of 記為寫，不透明呼叫後的柵欄補上（#3346）

合於 10-27 05:49，2 檔案 +62/-1，接 #3301 的 F305，延續昨日的柵欄語義主線。address_of 本身不攜帶訪問資訊，它只把指標交給下游，但訪問分類器把它的型別硬編碼成讀，於是一塊共享緩衝經不透明呼叫寫入後不會進 writes 集合，後續的全塊讀找不到衝突寫、也不再規劃柵欄，執行緒就這樣搶過寫入讀到寫前內容。實測的 CUDA 輸出很直白：T.address_of(B[0]) 形式在 extern 之後沒有柵欄，而 T.access_ptr(B, “w”) 形式有；後者顯式宣告瞭訪問型別，所以這個洞一直沒被發現。loop_unswitching.cc 早已按寫保守處理 address_of，ThreadSync 是唯一的例外。本筆把 address_of 記為寫，方向是保守的：指標用途未知就可能被寫，而柵欄規劃只需在安全側錯一次；新增兩個用例，斷言該核心下沉後 extern 之後跟著 __syncthreads()。

來源：https://github.com/tile-ai/tilelang/pull/3346

1.7 主倉：執行時行程數的流水線 epilogue 直接展開，分頁解碼恢復可編譯（#3356）

合於 10-27 07:02，1 檔案 +5/-1。T.Pipelined 迴圈的行程數是執行期值時，只要 epilogue 展開兩步以上且帶非同步複製，CUDA codegen 就報 TypeError: Downcast from tirx.Sub to ir.IntImm failed。根因在 EmitImpl：prologue 與 epilogue 的 extent 是常量時才展開，以保證每次迭代的等待計數是常量；而 epilogue 的 extent 是 end - start，即 (n + max_stage) - n，n 為常量時在構造期摺疊，n 為執行期時保持為 Sub，as_const_int 返回空，於是 epilogue 被當成 T.unroll 迴圈發射，其等待寫成 T.ptx_wait_group(1 - k) 這樣讀迴圈變數的形式，而 ptx_wait_group 只收立即數。修法是判斷前先看化簡後的 extent，常量邊界的情形化簡回自身，與原來一致。該缺陷由下游 TileOPs#1852 報出並二分到 afcebed1 之後，破壞物件是分頁解碼——其行程數來自 KV 長度。作者在 sm_89、CUDA 13.0 上雙版編譯對比，新增測試在主幹失敗、在本筆透過。

來源：https://github.com/tile-ai/tilelang/pull/3356

1.8 主倉：切片填充與負索引的靜態邊界兩修，越界寫與靜默負地址關閉（#3352 / #3347）

合於 10-27 05:37 與 05:14，合計 4 檔案 +100/-3。前者針對 Fill 構造器的靜態邊界檢查：原來逐維只校驗 min >= 0 與 extent <= shape，而 extent <= shape 只對從緩衝起點開始的區域成立；一個起點靠裡的切片兩項都透過，卻被下沉成越界寫——T.fill(As[6:12], 7) 在長度 8 的緩衝上編譯透過，發射出 As[threadIdx.x + 6] = 7，寫到 6 到 11。修法是把區域末端也對照目標形狀校驗，且新條件要求起點與長度都是靜態，錨定在零的區域與符號起點區域都不受影響；T.clear 共用同一節點，缺陷相同也一併關閉。後者針對 LegalizeNegativeIndex：原來把負索引加一次緩衝長度就了事，沒有範圍檢查，長度 8 的緩衝上 A[-9] 得到 -1、A[-10] 得到 -2，跳出分配起點且無任何診斷，而 NumPy 與 PyTorch 對同樣的索引拋 IndexError。修法是僅在分析器能證明迴繞後仍為負時拒絕，並報出索引與長度，所有在範圍內的常量與全部動態索引維持原行為。

1.9 主倉：T.ws(-1) 區域在所有執行緒上執行，落單寫法不再丟存（#3354）

3.4 TileOPs 合入四條：where 與 masked_fill 可調優、D128 因果對角按 64 鍵打分、稀疏長 GDN 預填充拆分、變更日誌按釋出日定日期（#2782 / #2783 / #2779 / #2781）

四筆在 10-27 合入，恰是釋出前的收尾。#2782 修 request_tune() 在 WhereFwdOp、MaskedFillTensorFwdOp、MaskedFillScalarFwdOp 上拋 ValueError 的問題：自動調優拒絕隨機生成的整型輸入，而這三個核心把 bool 條件或掩碼當 uint8 傳；隨機選擇器只改變每個元素取哪個運算元、不改變候選的工作量，故宣告隨機整型輸入安全；新增三個測試節點，主幹上三例全失敗。#2783 最佳化 D128 稠密程式的因果對角：當因果呼叫只有一段 key 且兩個長度都在 128 行邊界上時，第一個消費 warpgroup 的對角 key 瓦片對全部行都遮蔽了高 64 鍵，於是這一步改按 m64n64 的 QK 配 64 鍵 softmax 跑；該選擇是編譯期標誌（diag_aligned，進核心鍵），因為執行期在 64 與 128 寬 QK 之間分支會讓 ptxas 在某些特化上序列化每條 WGMMA（C7511），改用標誌後所有 manifest 裡的 D128 預填充特化都不再出 C75xx。#2779 把 SM89 上稀疏長序列的 GDN 預填充拆成狀態掃描加獨立輸出程式，適用於稠密、key 主序的 D128 輸入且至少 16384 token、狀態掃描 CTA 不超過 SM 數四分之一的情形；基準裡 (1, 16384, 4, 128) bf16 的耗時從約 0.612 毫秒降到約 0.470 毫秒，與 flash-linear-attention 的 0.441 毫秒相比為 0.939 倍。#2781 把 CHANGELOG 裡 0.1.0 的日期定為它進 PyPI 的那天（2026-10-27），並刪掉貢獻者文件裡的釋出一次配置與 Actions 點選路徑。

來源：https://github.com/tile-ai/TileOPs/pull/2782、https://github.com/tile-ai/TileOPs/pull/2783、https://github.com/tile-ai/TileOPs/pull/2779、https://github.com/tile-ai/TileOPs/pull/2781

3.5 TileFoundry 合入兩條：整視窗按運算元本身下發、動態共享記憶體按核心實際用量定尺寸（#273 / #271）

兩筆均在 10-27 合入。#273 修 sm_89 GEMM 的下沉：schedule finalize 寫出的內容編不過，因為下沉把整個累加器包進一個從零開始、跨度等於自身的視窗 T.ptr_of(acc[0:0+16, 0:0+8])，而 CUDA codegen 拒絕分片暫存器瓦片的指標切片，報「要求普通源佈局」；MMA 又把暫存器片段讀成 lhs_frag_dst[0:0+16, 0:0+32] 這樣的裸 Slice，codegen 同樣無處理器。修法在下沉側：StoragePlan.operand 本來就把「從零開始且跨滿運算元的視窗」當作運算元本身，但物化與指令下發仍構造 Slice；改為只判定一次——對 MLIR 的 TrivialSubViewOpFolder 做同樣的替換。#271 修動態共享記憶體：合成的宿主入口給每個 TIR 核心都用 dynamic_smem=0 啟動，經整型 TensorView 偏移訪問共享記憶體的核心因此沒有分到空間，超過 48 KiB 還需設定 cudaFuncAttributeMaxDynamicSharedMemorySize 而啟動器從不設定；作者沒有采納 #267 裡「按目標容量給滿」的建議，改為按核心實際用量定尺寸，理由是靜態共享記憶體與動態共享記憶體同計一個上限、且每塊申請多少決定一個 SM 能放幾塊——sm_89 上要滿 99 KiB 會讓用 512 位元組的核心也只放得下一塊。CUTLASS 與 TileLang 都按同樣方式定尺寸。

來源：https://github.com/tile-ai/TileFoundry/pull/273、https://github.com/tile-ai/TileFoundry/pull/271

五、趨勢觀察

第一，TileOPs 0.1.0 把「運算元庫」這件事的成本結構換了一種演算法。傳統做法是運算元數量隨硬體與模型需求線性增長，人力是瓶頸；這裡的做法是每個運算元先寫一份 YAML 規格，把簽名、負載與 roofline 宣告清楚，再由 agent 生成與調優核心，最後用規格派生的測試與基準做准入。206 個運算元、195 筆 foundry 標籤合入是這個流程的第一次全量交付。它能否持續，取決於兩件事：規格能否覆蓋複雜融合運算元（路線圖第一步正是這個），以及基準能否擋住「調優到基準上但實際不魯棒」的核心——FusedAddLayerNormFwdOp 在遠離零的行上丟精度這條已知問題，恰好是這類風險的一個樣本。

第二，本視窗的合入幾乎全是「靜默錯誤」。ROCm 的數學函式預設走快速內建會讓 sin/cos 差出三個數量級；address_of 被當成讀會讓不透明呼叫後的共享記憶體讀到寫前內容；T.ws(-1) 的區域在零個執行緒上執行，存全部丟棄且不報錯；切片填充按長度而非末端校驗，直接越界寫；負索引迴繞後仍為負，落到分配起點之前。這五條的共同點是編譯透過、執行不報錯、結果錯，且都在最近兩週內被集中發現。對一門要給大模型寫核心的語言，這類缺陷的代價遠高於編譯期報錯，它們指向同一個工程需求：把「不報錯但行為不對」的寫法在編譯期拒掉。本視窗的邊界校驗兩修與 ws(-1) 修正在做的就是這件事。

第三，後端覆蓋正在從「廠商主導」轉向「社群自發」。官方維護的昇騰、海光、沐曦、摩爾執行緒四條線之外，Hexagon DSP 後端在一天裡落 15 筆並把線性代數原語鋪到 Crouton 瓦片上，PPU 版出現零改動包裝器，CANN 社群自建運算元倉並用它串出 DeepSeek V4.1 Flash 的模型片段。這些動作都不在 tile-ai 組織的倉庫裡，卻都依賴 TileLang 的語言層穩定性。這也是 0.1.0 凍結公開 API、並把 API 相容性檢查做成 CI 門禁的意義所在——下游越多，向後相容的價值越高。

第四，快取身份這件事被兩個後端同時盯上。主倉把 compile_flags 納入自動調優快取鍵（#3338），昇騰把 Bisheng 構建身份納入二進位制快取鍵（#3691）。同一個核心在不同編譯選項或不同編譯器下產生的二進位制不同，快取若只按原始碼與形狀做鍵就會誤命中，測出來的效能與真實編譯結果對不上。兩條獨立路線在同一天做同一件事，說明這類問題在實際使用中已經足夠痛。
