一、核心專案進展

1.1 主倉：批式 finalize_reducer 此前只歸約首個輸出塊（#3070）

合於 10-22 01:16，2 檔案 +29/-5，修 #2623。批式 finalize_reducer 的下降只在緩衝區開頭呼叫一次 run_batch，其餘連續輸出塊根本沒有被歸約：輸出維度大於 batch 時，後面各段拿到的不是歸約結果，而是未初始化或上一輪遺留的值。修復按 ceil(OutputDim / batch) 逐塊發射帶正確偏移的批式 all-reduce——128 個輸出、batch=4 時發射 32 次呼叫，同時把重對映 reducer 緩衝改用扁平檢視、每批以常量線性偏移定址，去掉原先的形狀與步長重建，並保留全部 chunk 呼叫。驗證在 L40S 上完成：新增 sum/max/min 數值迴歸，覆蓋 fp16 與 fp32、batch 4/8/16，23 項 finalize_reducer 相關用例透過，外部復現矩陣 16 例零失配。屬典型的”小尺寸正確、大尺寸靜默錯”的一類缺陷。

來源：https://github.com/tile-ai/tilelang/pull/3070

1.2 主倉：BF16→FP32 向量化轉換改走內聯 PTX 打包 lane 轉換（#3595）

合於 10-21 19:28，4 檔案 +19/-7。
新增 tl::__tl_cvt_bf16x2_to_f32x2，用內聯 PTX 把成對的 BF16 lane 一次轉成 f32x2，替掉逐 lane 的標量提升路徑；2、4、8 三種 lane 寬度均保持支援。同步更新了向量化 cast 與佈局推斷的期望值，並把 BF16 cast 的測試收斂到既有覆蓋範圍，不擴大斷言面。改動不涉及語義，只動生成的指令序列，影響面是所有走向量化 cast 的 BF16 計算路徑。

來源：https://github.com/tile-ai/tilelang/pull/3595

1.3 主倉：展開 pass 保留空 stepped 迴圈，ROCm 的 Select 改逐 lane 下降（#2887）

合於 10-21 19:20。迴圈展開 pass 此前會把 trip count 為 0 的 stepped 迴圈當成空殼消掉，改變後續 pass 看到的程式結構；修復改為在展開過程中保留這類空迴圈。同筆還改了 ROCm 側的向量化 Select：改為逐 lane 下降，避免整組下降在不支援的目標上失敗。兩處改動一在 IR 結構、一在後端下降，合在同一筆裡，說明它們由同一個復現場景引出。

來源：https://github.com/tile-ai/tilelang/pull/2887

1.4 主倉：軟體流水保留傳遞性複製依賴，執行緒域參與區域衝突判定（#2822）

合於 10-21 18:13。流水規劃此前只跟直接依賴，間接（傳遞性）的複製依賴會在規劃階段丟失，dependent copy 的等待隨之被刪；同時物理區域衝突檢查在規劃與下降兩側各有一套口徑。修復用一個後向 worklist 同時跟隨標量與 buffer 複製依賴，讓規劃與下降共享同一份物理區域衝突檢查，保留重放繫結在作用域內，並補齊傳遞生產者、strided alias 與順序 TMA 回落路徑的覆蓋。第二筆提交把執行緒域引入區域衝突判定：訪問先展開到物化執行緒域再比較區域，使互不相交的共享記憶體切片仍可流水，同時保住跨執行緒依賴與 strided 緩衝的物理重疊；同一套域用於流水規劃、依賴校驗與 buffer 版本化。

來源：https://github.com/tile-ai/tilelang/pull/2822

1.5 主倉：cast 的源/目標/舍入三組合前置校驗（#3350）

合於 10-21 13:49。round 只在顯式列出的組合下可下降：PTX cvt.rs 要求 f32 源、32 位 rbits 運算元與特定的打包目標。其餘組合此前在分支分派時被放過，舍入註解就此靜默消失；標量迴圈本來就會拒絕這些組合，向量化迴圈不拒絕，於是同一個 cast 在兩種迴圈形態下行為不同。典型例子是 f32→E8M0：它的 helper 向正無窮舍入、根本不接受舍入引數，而向量化分支從未讀過 round。現在在分派之前統一拒絕非法組合，任何分支都無法再丟註解；配套測試只給真正接受 rbits 的 rs 模式傳該引數。

來源：https://github.com/tile-ai/tilelang/pull/3350

1.6 主倉：無 arch 的 CUDA target 拒絕而非靜默填 sm_50（#2860）

合於 10-21 13:32，1 檔案，修 #1049。在有 CUDA toolkit 但沒有可用 GPU 的機器上，未指定 arch 的 CUDA target 會退化成裸 cuda，TVM 隨後靜默填入 arch=sm_50，編譯繼續推進到一個錯誤的 SM，全程沒有任何診斷——這正是 tilelang.compile(func) 配 target="auto" 的陷阱。修復落在 _cuda_target_from_arch：自動檢測與顯式 target="cuda" 共用的唯一入口，改為丟擲可操作的錯誤，並在錯誤裡給出顯式 arch 的兩種寫法（{"kind":"cuda","arch":"sm_90"} 或 TILELANG_DEFAULT_TARGET）。headless 編譯只要給了具體 arch 依然可用，因為 codegen 與 nvcc 只依賴 toolkit，裝置訪問推遲到 kernel 啟動。PR 過程中一度加入三個無 GPU 單測，最終提交把它們撤下，改動只剩入口校驗。

來源：https://github.com/tile-ai/tilelang/pull/2860

2.3 主倉昇騰：warp_reduce_max/min 在 PTO 上的整數符號性修復（#3582）

合於 10-21 10:21。PTO 的 pto.redux_max/min 拒絕帶型別的整數：PTOAS 要求無符號性載體加一個顯式 signedness，於是 int32/uint32 的 T.warp_reduce_max/min 直接編譯失敗，報「requires signedness=’signed’ or ‘unsigned’ for integer values」。修復把 warp_reduce_sum/max/min 統一走 contrib.ptodsl 的 tl.redux_* 包裝（現已匯出），由包裝提供載體與符號性，並按 AscendAllReduce 的方式對 value dtype 設門；問題單引用了主倉 #3541 與 PTOAS #1579。驗證分兩層：op × dtype 網格的 lower-only codegen 測試，以及稀疏的雙目標（ascend/pto）執行測試——用 ≥2^31 的 uint32 lane 把符號性寫錯直接暴露出來。

來源：https://github.com/tile-ai/tilelang/pull/3582

2.4 昇騰倉：亞 32B 緊湊行距源無法表達，keepdim reduce 輸出錯亂（#1795）

合於 10-21 17:15，2 檔案 +302/-3，修 #1682，是本視窗技術含量最高的一筆。根因在模板層：copy_ub_to_gm 無條件生成一條多 burst 的 DataCopyPad，而 MTE3 引擎實現的是系統級「UB 窄行按 32B 槽存放」約定——源地址每 burst 前進 ceil(blockLen/32) + srcStride 個 32B 塊。對按 32B 邊界寫行的生產者這是精確匹配；但 T.reduce_max 的 (M,1) fp32 輸出是 V-pipe 緊湊寫入、行距只有 4B，引擎無法表達。實測第二個 burst 讀到的是 element 8 而不是 element 1（[127, 1151, 71, 199] 裡 1151 恰是 element 8 的值），寫入側沒問題，錯在 DMA 讀源的地址序列。修復分兩半：兩側皆 packed 且 total ≤ 65535 時摺疊成一條 flat 單 burst（M×L 位元組，利用「單條 burst 長度任意」的契約）；不可表達的非 32B 倍數行距改為 trap() 顯式中止，用編譯期 if constexpr 守衛，對 32B 倍數與亞 32B 槽佈局不生成額外程式碼。為什麼不降級：bisheng 的跨管道自動同步只覆蓋直線 intrinsics，用條件分支包裹 DataCopyPad、或兄弟分支裡放 GM 標量寫，都會讓 bisheng 生成壞的同步程式碼並導致裝置死鎖（實測逐行 DMA 被執行時分支包裹即觸發 aicore 異常）。14 個用例覆蓋 flat/multi 路徑、keepdim reduce 復現、UB 迴圈複用、不可表達 pitch 的合法單 burst 形式與顯式中止；測試環境為 Ascend910 A3（dav-c220）/ CANN 9.0.0 本地構建。PR 自述保留兩個邊界：亞 32B 緊湊行距且帶行距目的（如把 (M,1) fp32 寫進寬張量的某一列）仍走槽步進；blockCount > 4095（12 位欄位）仍會靜默截斷（4200 行實測只拷前 104 行），擬另立 issue。

來源：https://github.com/tile-ai/tilelang-ascend/pull/1795

五、趨勢觀察

編譯器缺陷的性質從「算錯數」擴到「選錯目標」。 本期主倉八筆合入裡，四筆改變的是「編譯器以為自己在做什麼」：無 arch 的 CUDA target 靜默退到 sm_50（#2860）、cast 的舍入註解按分支靜默丟棄（#3350）、批式歸約只處理首個輸出塊（#3070）、流水規劃丟失傳遞性依賴（#2822）。它們的共同點是不報錯，只在某些尺寸或某些迴圈形態下給出不可信結果——比崩潰更難定位，也說明專案把靜默正確性放在了功能擴張之前。

昇騰線的瓶頸已移到記憶體模型與執行時邊界。 亞 32B 緊湊行距無法用 DMA 表達、只能顯式中止（#1795）；快取併發改為原子釋出並補刪除恢復（#1903）；PTO 的整數符號性要靠包裝層補齊（#3582）。這三筆都不是「加運算元」，而是「讓已有運算元在邊界條件下不出錯」，配合 DeepGEMM 啟發式對齊合入，昇騰側正從能力覆蓋轉向工程可靠性。

分析機構開始把 TileLang 當作昇騰可用性的判據。 SemiAnalysis 用「六個倉庫中只有 TileLang 當時可用」來定義 DeepSeek 昇騰支援的完成度，這比任何單篇技術部落格都更能說明 TileLang 在國產算力敘事裡的位置：從實驗性 DSL 變成預設承載層。同一篇報告也給出反向訊號——最佳化集中在超節點、x86 主機支援仍不完整，通用性落後於效能。

注意力棧的重心從推理前向移到訓練反向。 TileOPs 一天內補齊 MLA 預填充反向的 op 層、SM90 warp 特化 kernel 與取數順序最佳化，再加上 GQA 反向的分組 KV head 處理，與昇騰側上月以來的反向運算元補位（indexer_bwd、SiTU-GLU 反向、WY fast 反向）完全同向。訓練側的 TileLang 覆蓋度正在被系統性補齊。

SM89 從「能跑」走向「調優」。 FP8 BMM 瓦片、W4A16 的 M 上界、分頁 DSA、NSA top-k 四條線同日動刀，且都給出單卡實測與「不構成普遍優勢」這類限定語。消費級與單卡推理場景成了效能目標之一，同時作者對基準口徑的自我約束明顯變嚴。

排程與正確性的分工在 TileFoundry 與主倉之間變得清晰。 主倉繼續收緊語義與正確性，TileFoundry 0.0.3 則把「選哪條指令」交給 agent、把「保證語義」留給編譯器，並用 H200 與 Apple AMX 兩個示例給出可復現數字。這條分工如果穩定下來，TileLang 生態會出現「語言層守正確、agent 層搏效能」的雙層結構。
