今日重點

今天視窗的重心在昇騰側。tilelang-mlir-ascend 把 Ascend 910（A2/A3）的 NPUIR 後端整條併入主幹，一筆 55 檔案、21490 行新增：Python 側是 tilelang/ascend910 包（backend / adapter / codegen / compiler / execution_backend / jit / pipeline / runtime / target 加 language 下的 kernel、copy、gemm、npuir 方言面），C++ 側是 src/ascend910/target 下的開發者與專家兩套發射器、op 層與 LowerNpuirBlock、NpuLoopVectorize、RewriteFDivToMul 三個 pass，執行時補了 npu_launcher.h 與 npu_utils，安裝走 install_npuir.sh，target 別名接受 ascend910 / ascend-910 / a2 / a3 / npuir。作者給出的驗收是倉庫自帶的兩套用例：pytest testing/npuir 504 項全透過、examples 72 例中 71 例透過且 0 超時 0 報錯，唯一失敗的 deepseek_v32/fp8_lighting_indexer.py 在舊後端上同機同樣失敗，屬環境與容差問題。第二筆提交是逐條對齊舊後端的行為差異，重點在 bf16 合法化（HIVM 不接受 bf16 運算元，改為 fp32 計算後顯式轉換）與動態 extent 的複製下沉。

TileOPs 今天合入七筆，兩條主線都在效能側。選擇器不再貼著 manifest 擬合，改為在忙時（device_busy_ms）上按 160 個稠密 shape、60 個 m 9–32 的 shape、264 個 m≤8 的 shape 重新標定，用 softmin 期望對數遺憾做座標下降；端到端忙時遺憾在留出的 manifest 上從 5.79% 降到 0.48%，m≤8 的留出集從 14.18% 降到 1.79%。GEMM 側新增 coop2_swap：把非 NT 佈局換成轉置的持久核心，兩個消費者 warpgroup 各持 128 行，尾寫經 stmatrix.trans 與 TMA 轉置落回，並支援寬窄 tile 混排（例如 2112 = 13×160 + 32 拆成 160 寬 tile 加 128 窄 tile），2112×7168×4096 TN 從 195.3 微秒降到 175.3 微秒，同機上另一塊 H200 讀到 174.3 降到 158.5 微秒，均壓過 QuACK 的 187.9 與 167.0 微秒。

歸約側則同日先壞後修。上午 #2787 用 int32 鍵實現 extrema 歸約的 NaN 傳播、#2788 改並行 cumsum 的行 tile，兩筆都在 07 時前後落地，隨後 #2790 與 #2792 分別把兩個迴歸收掉：cumsum 改成按種子分段、兩次發射（(8,65536) float32 從 12.75 微秒降到 5.18 微秒，同時修掉主幹的 65535 tile 以上發射失敗），extrema 改用 PTX 的 max.NaN / min.NaN 並在非整 16 位元組向量的行上走單獨核心（amax (2048,4096) bf16 從 8.352 微秒回到 6.976 微秒，快於 FlagGems）。這類”同一天內引入再修掉”的節奏說明 TileOPs 的夜間基準已經把迴歸攔在了當天。

一、核心專案進展

1.1 主倉：標量讀的索引係數不再混進 lane 數，行寬 32768 以上的編譯崩潰關閉（#3453）

合於 10-28 11:06，單檔案 +8/-5。一個用向量化方式讀整行、同時又按下標讀該行單個元素的 kernel，在行寬對 65536 取模後不小於 32768 時編譯報 InternalError: Can’t fetch the lanes of a scalable vector。根因在 VectorTypeAccessChecker::OnArrayAccess：它把標量讀記為 access_dtype.with_lanes(me->coeff)，而 me->coeff 是讀下標的模係數，對 x[row, 0] 就是行寬；DataType 的 lane 數只有 16 位並按 int16 讀回，32768 到 65535 因此被當成可伸縮向量，lanes() 在 get_preferred_dtype 裡直接拋錯，更寬的倍數則靜默迴繞。修法是把係數單獨存進 int64_t，相容性判斷改用它取模，標量讀的 dtype 只保留元素型別。這個缺陷的原始觸發場景是 TileOPs 的 GroupNorm：Stable Diffusion 的 40960 與 163840 兩個組寬都會踩到。驗證用兩次 wheel 構建對比：主幹在 32768 與 40960 兩個寬度上編譯失敗，本筆在所有測試寬度上都能構建。

來源：https://github.com/tile-ai/tilelang/pull/3453

1.2 主倉：批次 all-reduce 按標量分支解析執行緒區間，batch>1 時 2048 個輸出全錯的問題修復（#3341）

合於 10-28 05:46，2 檔案 +170/-8。標量 all-reduce 分支在發射呼叫前會先把參與執行緒的區間解析出來（reducing_threads 大於 32 且目標支援命名柵欄時走 ResolveAllReduceThreadRange），批次分支卻直接取塊邊界當偏移與柵欄寬度。當歸約執行緒是 [32, 96) 這種不從 0 開始的區域性區間時，批次呼叫從 0 號執行緒索引、按整塊等柵欄，非參與執行緒未初始化的暫存器被折進歸約：batch=1 正確，batch=2 在同一 kernel 上 2048 個輸出元素全部錯，最大絕對誤差 1083，且沒有任何診斷。修法是讓批次分支與標量分支同一套解析，把解析出的偏移與範圍傳給 MakeBatchAllReduce，工作區 stride 仍保持塊大小。新增測試在同一 kernel 上跑 batch=1 與 batch=2 並對 torch 參考比對。

來源：https://github.com/tile-ai/tilelang/pull/3341

1.3 主倉：SIMT 原子區域的形狀校驗補上，越界區域在編譯期拒絕（#3465）

合於 10-28 08:14。SIMT 原子操作此前不校驗傳入區域的形狀，形狀不匹配的寫法一路走到 codegen 才表現出錯誤結果或崩。本筆在 CUDA 與 ROCm 兩條路徑上補齊區域形狀校驗，把不合法區域提前到編譯期拒絕。

來源：https://github.com/tile-ai/tilelang/pull/3465

1.4 主倉：稀疏 MMA 的 K 尾塊不再被靜默放過（#3367）

合於 10-28 16:01。稀疏 MMA 在 K 方向上有未處理的尾塊時，此前不報錯而是沿用整塊的搬運與計算引數，數值靜默偏差。本筆顯式拒絕這類 K 尾塊，把問題挪到編譯期。

來源：https://github.com/tile-ai/tilelang/pull/3367

1.5 主倉：atomic_addx4 的目標 dtype 收窄到 float*（#3369）

合於 10-28 16:08，3 檔案 +27/-9。CUDA 的 atomic_addx4 與 atomic_addx4_ret 通用實現此前接受任意目標指標，int32 或 int64 目標會落到 float 語義上算錯。本筆把兩個通用過載限制為 float* 目標，fp16 與 bf16 的既有特化不動；Python 側 API 保持型別中立，CPU 後端的整數目標不受影響。CUDA 側新增整數目標編譯失敗的迴歸用例，CPU C 後端新增兩種整數寬度的累加正確性用例。

來源：https://github.com/tile-ai/tilelang/pull/3369

1.6 主倉：非 restrict 引數的 handle 字尾不再被裁掉（#3366）

合於 10-28 13:19。引數去重時按去掉 _handle 字尾的名字比較，導致同一個核心裡 A 與 A_handle 兩個不同引數被當成同一個，程式碼生成只發一份。修法改為按精確名加變數身份去重，並新增 CUDA 側 A 與 A_handle 並存的迴歸用例。

來源：https://github.com/tile-ai/tilelang/pull/3366

1.7 主倉：TMA 描述符只記錄已校驗的名字（#3484）

合於 10-28 17:12。TMA 描述符的登記此前在校驗之前完成，校驗失敗的描述符名留在表裡，後續同名的合法描述符會被誤判為重複。本筆把登記挪到校驗之後。

來源：https://github.com/tile-ai/tilelang/pull/3484

1.8 主倉：profiler 輸出索引統一校驗，標量與列表形式同一套邊界規則（#3486）

合於 10-28 19:24，2 檔案 +15/-9，修 #2884。profiler 與 adapter 兩側此前對 result_idx 的處理不一致：標量形式做過邊界檢查、列表形式沒有，負索引也未歸一。本筆讓 BaseKernelAdapter 與 Profiler 共用一套規則，接受 None、整數或整數列表，按 -len(params) 到 len(params)-1 判定，合法負索引歸一、越界與非整數元素拋 ValueError。新增 28 項 CPU 側迴歸覆蓋標量與列表兩種路徑。

來源：https://github.com/tile-ai/tilelang/pull/3486

1.9 主倉：T.Parallel 的 coalesced_width 統一轉 IntImm（#3374）

合於 10-28 16:27。coalesced_width 傳 Python 整數時，部分路徑直接以原生整數進入 pass，型別斷言在後續變換裡失敗。本筆在語言層統一轉成 IntImm，消除寫法差異帶來的失敗。

來源：https://github.com/tile-ai/tilelang/pull/3374

1.10 主倉：測試基建把 cache 敏感用例改走 without_kernel_cache（#3695 / #3696）

合於 10-28 01:59 與 09:19。承接昨日記錄的 issue #3694（核心快取命中破壞假定冷編譯的測試），兩筆把檢查編譯產物、原始碼與診斷資訊的用例改走 without_kernel_cache() 或顯式 .compile(…)，讓斷言看到的是本次構建的結果而不是程序內快取裡的舊 kernel。

來源：https://github.com/tile-ai/tilelang/pull/3696

來源：https://github.com/tile-ai/tilelang/pull/3695

1.11 新增缺陷三條：SM120 上 13 個示例失敗、IfStmtBinding 指數級編譯、without_kernel_cache 不強制重編（#3701 / #3700 / #3699）

三條新開 issue 指向測試與編譯時間。其一，#3701 在 RTX PRO 6000 Blackwell（sm_120，動態共享記憶體上限 99 KiB）上跑完整 examples 套件，CUDA 與 CuTeDSL 兩個後端都是 13 失敗 199 透過 27 跳過，失敗集逐字相同：7 例是示例在非 –tune 路徑上硬編碼 Hopper 尺寸的 tile（如 attention_sink 要 163840 位元組、deepseek_mla 解碼要 231424 位元組），4 例是參照實現 flash-attn 2.5.8 沒有 sm_12x 核心，另兩例分別是 ReduceOp 下沉與 ThreadSync 無法證明執行緒範圍。其二，#3700 報告在迴圈裡重複寫 x = x + x 並加上 i < N 守衛時，tl.LayoutInference 從 0.087 秒漲到 118.5 秒，關掉 replayable bind 內聯即退回 0.100 秒。其三，#3699 指出 without_kernel_cache() 只翻轉 CacheState（只被磁碟快取讀取），而 @tilelang.jit 包裝器在 JITImpl.compile() 之前還會查程序內的 _call_form_cache 與 _kernel_cache，因此該塊內的一次普通呼叫並不保證重新編譯。

來源：https://github.com/tile-ai/tilelang/issues/3701

二、多後端適配（昇騰 / 海光 / ROCm）

2.1 昇騰：910 A2/A3 的 NPUIR 後端併入 mlir-ascend 主幹，504 項自測全透過、72 個示例僅 1 例環境性失敗（#207）

2.4 昇騰倉在審：W4A4 int4×int4 GEMM 結果錯誤的根因與修法（#1731）

在審，7 檔案 +634/-24，修 #438。根因是整條 C++ 模板棧都用 sizeof(AscendC::int4b_t) == 1 推分形幾何，而 int4b_t 是半位元組打包型別：32 位元組的 C0 塊正確元素數是 64 而不是 32，於是所有複製 stride、repeat 次數與位元組計數全部 2 倍偏差。三層疊加：L1 到 L0A/L0B 的 LoadData 引數由該常數推出，資料堆到錯誤位置；B 運算元的 zN 到 nZ 轉置被 s4 專用指令 load_cbuf_to_cb_s4 靜默關掉，必須改走 LoadDataWithTranspose 到 load_cbuf_to_cb_transpose_s4，而其引數語義在 CANN 標頭檔案裡沒有文件，作者只能用探針 kernel 在裝置上逆向（正確引數 repeatTimes = N/64、srcStride = roundUp16(K)/64、dstGap = 3，且 s4 版本按 2048 位元組塊而不是文件寫的 512 位元組 fractal 工作）；UB 到 GM 的位元組長度按每元素 1 位元組算，每行多搬一倍並混入相鄰行。mad_s4 指令本身正確，症狀是 99.6% 不匹配、輸出 -501/627 而正確答案 641/1785。

五、趨勢觀察

昇騰側的推進方式這兩天已經很清楚：主倉按小時合入小修（快取鍵、暫存器相位），專用倉 mlir-ascend 用一次兩萬行的合併把 910 的 NPUIR 路徑從特性分支搬進主幹，tilelang-ascend 則在 PTO 與 AscendC 雙後端的既定節奏上做文件與運算元補齊。三處節奏不同但指向同一件事：910 的編譯器路徑正在從”能跑”轉向”可驗收”，504 項自測與 71/72 示例就是這次給出的驗收口徑。值得注意的是在審佇列裡 a2a3 的排程器遷移佔到了 100 檔案，說明下一階段的變動量在排程層而不在運算元層。

效能側的看點在測量口徑本身。TileOPs 這兩筆把選擇器和 GEMM 的結論都挪到了忙時（device_busy_ms），並在同一份 PR 裡給出單次呼叫與背靠背呼叫的差別：單次讀法下本實現領先 QuACK，背靠背、功率封頂的訓練場景裡十條大行有六條落後。這是一個比”某行快了多少微秒”更重要的訊號，因為訓練實際就是背靠背。#2791 把這件事單獨立項，說明團隊已經把口徑問題當成產品問題處理，而不是當作基準偏差粉飾過去。

工程衛生上今天有三條值得記：一是同一批內的自傷與自修（#2787/#2788 上午合入、#2790/#2792 下午收回歸），說明夜間基準的兜底在起作用，但也說明歸約這套程式碼的語義邊界仍然脆；二是 without_kernel_cache() 的語義漏洞（#3699）被從遷移過程中揪出來，程序內兩層快取不吃 CacheState，測試自以為在冷編譯其實拿的是舊 kernel，這類缺陷會讓”我們的測試全過”失去意義；三是 SM120 上 13 個示例失敗（#3701）暴露出示例硬編碼 Hopper 尺寸的問題，Blackwell 裝機量上來後這類”示例不是產品”的債務會被反覆計入。
