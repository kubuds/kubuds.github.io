今日重點

這一天的主線是一筆「把效能要回來」的修復。上一視窗合入的 #3643 解決了一個真實的正確性問題：分別呼叫的 ThreadSync("shared") 與 ThreadSync("shared.dyn") 可能把同一個命名屏障 ID 分配給互不相交的執行緒組。修法是讓後一次呼叫保留前一次已經用掉的 ID，但這條保留規則同時擋住了另一件事——同一組執行緒在兩個作用域之間本來可以複用同一個 ID。代價直接落在 TileKernels 的 mhc_pre_big_fuse 核心上：這個核心每塊 96 個執行緒，執行緒 32 到 95 跑兩段式 cp.async 流水線，非同步等待之後的同步在第一遍拿到 ID 3，同一批 64 個執行緒的緩衝依賴同步在第二遍拿到 ID 4，多出來的那個 ID 讓編譯產物宣告的屏障資源從 4 變成 5；在 B300 上跑隱藏維 1280 時，屏障佔用上限因此從 16 塊/SM 降到 12 塊/SM，暫存器、共享記憶體與同步指令數都沒有變化。#3761 的處理辦法是讓 ThreadSync 接受一個有序的作用域列表，CUDA 流水線改成 ThreadSync(["shared", "shared.dyn"])，同步仍按原來的作用域順序規劃與插入，但部分屏障的 ID 在兩個作用域都處理完之後才統一分配；跨作用域共用一個 ID 之前，用一個全新的分析器證明參與謂詞在整個候選執行緒範圍內成立，分支與 Bind 上下文由 ConstrVisitor 提供，執行緒相關的謂詞按證明義務處理而不是預設成立，已證密的密集組直接用包圍盒體積、跳過部分執行緒數的列舉，未證明的組則把作用域留在鍵裡並讓參與者計數一起入鍵，顯式編號的屏障（含更早一次 ThreadSync 分配的 ID）繼續保留。改動 401 行、涉及 4 個檔案。

作者在描述裡做了一個很乾淨的歸因實驗：單獨改編譯產物裡宣告的屏障資源數、不動任何可執行指令，就能復現同樣的變慢。這類實驗值得記一筆——它把「效能回退」從觀感變成了可指認的單一變數，也讓修復的驗收標準變得明確：不是籠統地跑分變快，而是資源宣告回到 4、佔用回到 16 塊/SM。

第二條是供給側的減法與口徑統一。#3736 把 tilelang/language/ast/、tilelang/language/parser/ 與 tilelang/language/tir/entry.py 一併刪掉，這些是早期本地 TVMScript 解析器分叉留下的模組，約 3380 行 Python，倉內已無呼叫方：語言層現在透過 tilelang.language.tir.common 使用上游的 tvm.tirx.script.parser 介面，AST 與語句覆寫註冊在 tilelang.language.overrides，T.prim_func 與 T.macro 由 tilelang.language.eager 匯出。實際改動是新增 1 行、刪除 3384 行、10 個檔案，同時移除了 docs/conf.py 裡針對 *language/ast* 的忽略規則；公開的語言層匯出由方言測試與前埠測試兜住。#3546 修的是自動調優的裝置口徑：set_autotune_inputs 安裝的供給閉包從一個呼叫點從不傳入的引數上解析基準裝置，實際傳過去的是核心引數列表，於是 CUDA 或 CPU 的兜底分支在沒有 CUDA 的機器上把每個捕獲張量搬到 CPU，每一輪調優都因啟動器裝置不匹配失敗；現在閉包改用 get_current_device()，與預設張量供給同一策略，CUDA 行為不變、昇騰與 MPS 改為在當前裝置上供給、其餘後端仍退到 CPU。驗收在雙卡 Ascend950 上：三筆昇騰自動調優迴歸修前全敗、修後全過，主倉 testing/python/autotune/ 12 項透過、28 項跳過，另有 3 項因該機沒有 CUDA 而失敗，作者明確留給 CUDA CI 驗證。

第三條在昇騰側：GM 到 L1 的複製從「一個描述符一個矩陣」擴到整批。#3689 允許把 [B, M, N] 區域寫成一個 T.copy，lowering 生成批次 ND2NZ 描述符，保留源側的批與行 stride，目的側的批間距按物理佈局推導，轉置批次走 DN2NZ；超出 GM 邊界的源批直接跳過並保持目的儲存不動，M/N 的尾部補零隻作用於合法批。既有二維與單矩陣行為不變，實現只針對 AscendC 後端、且要求 L1 目的端是規範矩陣佈局，PTO 不在本次範圍內。驗證在 Ascend950DT 與 CANN 9.2 上：50 個 AscendC 示例測試與 1733 個昇騰單測透過，其中 28 個裝置用例覆蓋批與 M/N 尾塊、整批越界、非連續源 stride、目的儲存更大與矩形轉置；CUDA 與 PTO 用例被排除，CI 映象用的 CANN 9.3 未在本地測到，這一點作者寫在了描述裡。改動 579 行、10 個檔案。

第四條是 TileFoundry 的一條暗線落地。上一期報告裡它還掛在「在審」，這一視窗合入：#285 讓 sync 分析規劃出的提交、等待與柵欄真正由 CUDA lowering 發射，並逐條反向校驗實際發射與計劃是否一致，不一致拋 LoweringError。語料上的結果是預設流程 14 個程式加上同步、拒絕 31 個，這 14 個的 TIR 與主線差別只有新增語句，另有 30 個與主線完全相同；單張 sm_89 上跑了 7 個能構建且帶同步的程式，6 個與參考完全一致、synccheck 與 memcheck 全乾淨，而同樣這 7 個按主線的方式 lower 有 4 個結果錯誤。作者在動機裡給的直接症狀是 sm_89 的 E4M3 GEMM 最大偏 659。這一筆 788 行新增、214 行刪除、25 個檔案，把「分析能證明」推進到「發射必須與證明一致」。

1.4 在審：條件中的標量 cast 不再壓縮資料向量寬度，承接昨日 #3734（#3759）

11-03 14:09 更新，新增 148 行、刪除 29 行，2 個檔案。這是對昨日合入的 #3734 的收尾：#3734 在 DecoupleTypeCast 之後正確收緊了資料 cast 的寬度限制，但也讓「標量條件裡的 cast」開始限制資料向量寬度——在 b5cb02633 上，一個受守衛的 BF16 複製可能因為條件裡有一個 int64 cast，從 16 個 lane 被壓到 4 個，哪怕該條件在 16 個 lane 上完全一致。修法是把規劃器已有的條件一致性分析複用到 cast 寬度豁免上，把 if 語句、tirx.if_then_else 與標量謂詞的 Select 條件從它們的子句裡分出來單獨訪問，條件裡的 cast 不再施加資料型別寬度限制，子句裡的 cast 仍然施加，並在帶逐 lane 向量謂詞的目標上保留條件 cast 的約束；#3579 的記憶體守衛行為與 #3734 修好的守衛 FP32 轉 BF16 限制都保持不變。迴歸覆蓋 8 lane 與 16 lane 的一致守衛、三種條件形式、子句內的 FP32 cast、向量謂詞與舍入位分組，九個 int64 守衛用例修前失敗，最終合法化與 cast 舍入兩組套件共 74 項透過。

來源：https://github.com/tile-ai/tilelang/pull/3759

五、趨勢觀察

第一，效能回退開始被當成一等公民，而且修法在方法論上比結論更值得記。#3643 為修正確性引入的 ID 保留規則，本身是必要且正確的；#3761 沒有把它回退，而是讓保留與複用在不同層級上並存——跨作用域共用一個 ID 之前先證明參與謂詞恆成立，證明不了就退回帶作用域的計數。配合作者那個「只改宣告的屏障資源數」的隔離實驗，這條修復鏈把「正確性」與「資源宣告」兩件事拆開了：後者是可以單獨復現、單獨驗收的變數。這種拆分能力，恰恰是編譯器專案從「能跑」走向「可維護」的標誌。

第二，昇騰的工程化在兩條腿上同時推進。一條是架構：#1975 用 2887 個檔案、60 萬行新增把整個 TileLang-Ascend 搬進主線多後端框架，靠 arch="dav-2201" 這樣的標識做後端分流，目標是讓 A2A3 與 A5 在同一個倉里正交共存；另一條是流水線：mlir-ascend 的 #208 把 Codex 的初始化、接入、恢復三套工作流和任務交接寫進 .workspace/，主倉與昇騰倉也各自有 Agent 目錄。把「遷移倉」與「用智慧體遷移倉」放在同一天看，能看出昇騰側的瓶頸已經從「缺運算元」轉向「缺一致的工程骨架與可複用的遷移流程」。

第三，運算元庫的自證文化在加深。TileOPs 本期在審的幾筆，幾乎都把「證據」寫在 PR 裡：真實路由測出的 Qwen3-30B-A3B EP8 組大小（取 48 層裡偏斜居中的第 44 層）、35 個掩碼構建的 TIR 與主線位元組一致、L2 flush 改動附 46 行實現的對照表並說明舊 flush 留下 120 MB 髒行、W4A16 的代價模型明確寫出「哪些項被刪掉是因為資料釘不住」。TileFoundry 走的是另一條路——把同步做成可證明的分析，再讓 lowering 反向校驗，分析拒絕的情形直接列出來（TMA 與 wgmma 的完成語義尚未宣告、跨執行緒邊界不等的迴圈）。兩條路合起來說明同一個取向：寧可承認「沒證明」，也不把「跑通了」當成「對了」。

第四，風險面在往安裝形態上集中。一天 7 條新 issue 裡，四條來自同一位使用 pip 包、跑 WSL、用消費級 sm_89 卡的外部報告人，全部附了可復現指令碼；#3775 則是生產環境裡「pip 包 + 多 CUDA 上下文 + nvrtc 後端 + CUDA graph 捕獲」的組合。這些不是編譯器的深層缺陷，卻決定了新使用者第一次嘗試時的體驗。對照昇騰倉日測 3030 項全綠而 sat=False 的語義偏差仍靠人工報告，可以看出測試覆蓋的形狀與真實使用形狀之間還有距離。

最後一點觀察：本期新聞側依舊空白，15 條候選裡 12 條是倉庫發現。TileLang 的對外聲量仍然繫結在「DeepSeek 與昇騰」這類事件上，而日常進展只發生在提交裡。對跟蹤這個專案的人來說，這意味著日報的主體只能是 PR 與 issue，而不是報道——這已經是連續多期的穩定形態。
