今日重點

這一天的主線只有一件事：TileLang 把 DeepSeek 的 MLA 解碼核心搬到了昇騰 950 上，而且是按編譯器可排程的寫法搬的。#3678 一次性加入 1997 行、20 個檔案、42 次提交，覆蓋 BF16 prefill 與緊湊 FP8 decode 兩條路徑，還帶可選的 FP8 與 FP4 額外 KV 快取、attention sink、非法索引與逐 query 獨立長度。實現方式值得注意：注意力迴圈、線上 softmax、反量化與排程全部寫在 TileLang 裡，靠 T.Stage 讓編譯器管理緩衝版本與同步，QK 與 PV 用同一塊 L0B 儲存環的兩個不同 layout 檢視，L1 的落位用 T.annotate_buffer_addresses 直接指定；prefill 在一個累加器分配裡分出四個不相交的輸出切片，歸一化算完一片就排空一片。為了讓這套寫法成立，編譯器側同時補了三處能力——L0C 到 UB 的複製保留 NZ 輸出、每個 AIV 流在自身流水線之前選定、顯式排程的階段在物理發射相位相同時保持原始碼順序。目標形狀寫得很窄：頭數 64、Dqk 與 Dv 都是 512、topk 為 64 的倍數。

第二條線是修一處真實的編譯器迴歸。#3734 處理的是 SM100 上的 ViT 前向：Cannot convert type float32x16 to CUDA type。路徑很長但每一步都清楚——向量化規劃器為一個 256 位的 BF16 儲存選了 16 個 lane，並推遲 cast 約束，指望 DecoupleTypeCast 把計算和訪存拆開；而 #3579 之前剛把「讀記憶體的守衛」從解耦裡排除（重複這些守衛會改變語義），於是最終合法化那一步仍在按推遲策略選寬度，殘留的 FP32 表示式被撐成 512 位向量，CUDA 後端表達不了。修法是把推遲約束做成規劃器的引數而非 IR 屬性，只有最後一步合法化傳 false，守衛的 FP32 轉 BF16 降到 8 個 lane，成功解耦的 BF16 複製仍保留 16 個 lane；地址 cast 也從資料向量型別約束裡摘出來，靠既有的訪問分析判合法性。

第三條線是除錯體驗。#3703 把 #line 指令從「每條 TIR 語句只錨定首行」改成可選的分級發射：級別 0 關閉、1 保持原狀、2 以上對每一行生成的非空行重新錨定，包括被展開成多行的語句和收尾大括號。實現放在 CUDA、HIP、CPU C、C host、Metal、Ascend 共用的 C 系輸出流裡，不動 vendored 的 TVM；沒有原始碼跨度的語句和函式顯式切到 <tilelang-generated>，使用者原文逐字保留以免破壞宏續行與字串字面量。新增環境變數 TILELANG_EMIT_LINE_DIRECTIVES 作為 Python 側的預設值，在快取查詢之前折進 pass 配置。本地 42 項透過、6 項跳過，CUDA 與 HIP 的用例在作者機器上被跳過，cuda-gdb 的實際行為尚未直接驗證——作者自己寫明瞭這一點。同日 LSP 倉跟進一筆，把 CUDA 除錯對齊到新的行對映。

運算元側的節奏沒有停，但方向變了。TileOPs 單日 7 筆合入裡有 6 筆效能、1 筆測試基建，全部來自同一作者；每筆仍然附 H200 實測表與清單迴歸門檻。其中最有價值的是 #2816：新增一個只在測試時存在的 tileops_test 目標，在 PrivateUse1 上為每個運算元算出共享的 workload 參考，讓 tests/ops 的冒煙測試不再必須站在 CUDA 上。改動 1281 行、59 個檔案，作者同時把邊界寫清楚了——比對共享參考只能證明後端無關的契約與可移植性，不能證明真實後端的數值正確性，那條線仍掛在 #2611。

最後是 TileFoundry 的一條暗線。#283 把「共享記憶體訪問應當如何排序」做成分析層：一個同步族按 lowering 的發射順序走每個函式，對每次共享記憶體訪問取指令、發射 mesh、運算元與位元組範圍，在衝突訪問前規劃 commit/wait 與作用域內柵欄。83 個排程夾具裡它規劃 52 個、拒絕 31 個（24 個用 TMA 複製、6 個用 wgmma，兩者的完成語義尚未宣告；1 個需要在跨執行緒邊界不等的迴圈裡插柵欄）。配套的 #285 在審，把計劃變成 CUDA lowering 並反向校驗：sm_89 單卡上能構建的 7 個程式裡 6 個與參考完全一致、synccheck 與 memcheck 全乾淨，而按 main 的方式 lower，同樣是這 7 個裡有 4 個結果錯誤；#283 的描述裡給出的直接症狀是 sm_89 的 E4M3 GEMM 最大偏 659。

一、核心專案進展

1.1 主線：昇騰 950 的持久化 FlashMLA 核心，BF16 prefill 與緊湊 FP8 decode 雙路徑（#3678）

合於 11-02 09:26，新增 1997 行、刪除 17 行，20 個檔案、42 次提交，是本視窗最重的一筆。核心面向昇騰 950，prefill 走 BF16、decode 走緊湊 FP8，可選 FP8 與 FP4 的額外 KV 快取，並支援 attention sink、非法索引與逐 query 的獨立長度。注意力迴圈、線上 softmax、反量化與排程全部用 TileLang 表達，靠 T.Stage 與編譯器管理的緩衝版本和同步驅動；QK 與 PV 共用一塊 L0B 儲存環的兩個不同 layout 檢視，L1 落位由 T.annotate_buffer_addresses 指定；prefill 在既有累加器分配內分出四個不相交輸出切片，並配獨立同步事件，歸一化完成一片即排空一片；decode 用整行輸出複製。編譯器側補三處支援：L0C 到 UB 的複製保留 NZ 輸出、每個 AIV 流在其流水線之前選定、顯式排程階段在物理發射相位打平時保持原始碼順序。目標為頭數 64、Dqk 與 Dv 均 512、topk 為 64 的倍數，pair gather 沿用已記錄的零 burst 程式碼生成繞法；隨附正確性與基準執行器、緩衝複用與 query 邊界迴歸、以及帶 FlashMLA MIT 宣告的 README。

來源：https://github.com/tile-ai/tilelang/pull/3678

1.2 主線：cast 解耦被跳過後殘留的 512 位向量，SM100 上 ViT 前向編譯失敗（#3734）

合於 11-02 09:05。在 e8225d7f5 上，面向 SM100 的 ViT 前向在受守衛的 FP32 轉 BF16 輸出儲存處報 Cannot convert type float32x16 to CUDA type：規劃器為 256 位 BF16 儲存選 16 個 lane 並推遲 cast 約束，期待 DecoupleTypeCast 把計算與訪存分離；#3579 讓解耦跳過那些會讀記憶體的守衛之後，後續 LegalizeVectorizedLoop 仍沿用同一策略繼續推遲，殘留的 FP32 表示式於是變成 512 位向量，CUDA 側無法表示。修法是把 defer_cast_constraints 做成規劃器的 C++ 引數（不是 IR 屬性），由呼叫方按階段選擇：LayoutInference 與 LowerTileOp 維持 true，最終合法化一律傳 false，並把算出的寬度作為顯式 vectorize_hint 前傳，避免重寫器用預設策略重新規劃。守衛的 FP32 轉 BF16 降到 8 個 lane，成功解耦的 BF16 複製仍保留 16 個 lane，守衛安全檢查保留；地址 cast 與訪問指標引數從資料向量型別約束中排除，連續地址降為標量基址加步長，由既有訪問分析判定合法性，int64 索引的對齊向量訪問與四 lane 原子用例不受影響。

來源：https://github.com/tile-ai/tilelang/pull/3734

1.3 主線：#line 指令改為逐行重錨定，偵錯程式對映可選密集模式（#3703）

合於 11-02 04:06，682 行新增、11 個檔案。此前的 #line 發射只錨定一條 TIR 語句生成的第一行，後續行會被編譯器邏輯行號推進，cuda-gdb 於是把生成的載入、運算與儲存歸到無關的 Python 行；合成語句與收尾大括號可能繼承已推進的對映，沒有原始碼跨度的函式還會繼承前一個函式的原始檔。本筆把 tl.emit_line_directives 擴成分級：0 或 False 關閉並保持預設，1 或 True 維持語句級，2 以上對每一行非空生成行重新錨定（含多行展開的語句與收尾大括號）。實現落在 C 系輸出流，覆蓋 CUDA、HIP、CPU C、C host、Metal 與 Ascend，未改動 vendored TVM；同時記錄語句與函式的原始碼跨度，無源區域顯式切到 <tilelang-generated>，使用者原文逐字保留以避免破壞宏續行與字串字面量。新增 TILELANG_EMIT_LINE_DIRECTIVES 作為 Python 側預設值，在快取查詢前折進 pass 配置，顯式配置優先（包括預設值非法時）。本地用 Metal 加 LLVM 構建驗證：行指令與 compile-only 兩組 42 項透過、6 項跳過；去掉指令後，向量化加法與條件選擇兩個夾具在級別 0、1、2 下產物完全一致。作者註明 CUDA 與 HIP 用例在本機被跳過，cuda-gdb 行為未直接測試。

來源：https://github.com/tile-ai/tilelang/pull/3703

1.4 主線：注意力示例按裝置共享記憶體上限推 tile，RTX PRO 6000 上由 2 過 7 敗變為 9 全過（#3702）

合於 11-02 06:59，345 行新增、13 個檔案。多個注意力示例的非調優路徑把 Hopper 尺寸的 tile 寫死，在 sm_86、sm_89、sm_120 上每塊動態共享記憶體上限約 99 KiB，啟動直接失敗：報錯原文是要求把允許的動態共享記憶體設為 163840 位元組，而裝置 0 每塊最多 101376 位元組。現在每個示例從 shared_memory_per_block_optin 推 tile，做法沿用既有的 GQA decode 示例（example_gqa_decode.py）；資料中心配置不變，因為每條分支只在低於上一檔 tile 需求時才觸發。約 99 KiB 裝置上的落點：attention sink 四個示例分別是 64×64 兩階段 128 執行緒（前向）與 64×32 一階段 128 執行緒（反向），example_gqa_bwd.py 前向 64×64、反向 64×32，example_mla_decode.py 取 BLOCK_N 32、BLOCK_H 16。後兩者新增 threads 引數：64 行或 16 行 tile 下 T.gemm 需要四個 warp 才能讓每個 warp 獨佔整塊 16 行，256 執行緒會直接 lower 失敗（分別報 acc_s 與 acc_s_cast 的 layout 衝突、以及 M=16 N=32 無合法 warp 劃分）。另外 flash-attn 2.x 沒有 sm_12x 核心，四個 varlen 示例原本在參考步驟就拋錯，現改為探測一次 flash_attn_varlen_supported，不支援則改用純 PyTorch 的 varlen_attention_ref（覆蓋 GQA、右下對齊的 causal 與 window_size）。驗證在 RTX PRO 6000 Blackwell（sm_120）上：CUDA 9 項全過（原為 2 過 7 敗），CuTeDSL 同樣 9 項全過；H100 有 227 KiB 可選上限，仍走原 tile，同樣 9 項透過。

來源：https://github.com/tile-ai/tilelang/pull/3702

1.5 主線：CUDA float32x8 位轉換改用內建 bit cast，SASS 指令從 19 條降到 18 條（#3748）

合於 11-02 09:58，20 行新增、3 行刪除，修 #3679 並取代 #3681。改動只用 CUDA：把 float32x8 的位重解釋從位運算序列換成 __builtin_bit_cast(uint64_t, make_float2(v, v))，生成的 SASS 指令數從 19 條降到 18 條。幅度不大，但屬於編譯器後端裡典型的「語義等價、產物更短」的一類收尾。

來源：https://github.com/tile-ai/tilelang/pull/3748

二、多後端適配（昇騰 / 海光 / 摩爾執行緒 / 沐曦）

2.1 昇騰：WY Fast 前向運算元新增、wy_fast_bwd_split 反向分段遷移（#1827 / #1828）

兩筆同在 11-02 02:33 合入，前後相差不到一分鐘。#1827 以「遷移並新增」的方式把 WY Fast 運算元搬到 Ascend NPU 側，#1828 遷移並補上 wy_fast_bwd_split 的分段反向。WY 表示法是線性注意力一類模型裡把遞推矩陣乘化簡成低秩形式的常用手段，前向與反向分段配合，等於把這條運算元鏈在昇騰上補齊到可訓練。兩筆的 PR 描述只有模板問候語，改動範圍以標題與提交為準，本報告不對內部實現細節作推斷。

合於 11-02 05:10。根因寫得很直接：所有均值與方差核心都對原始行做 fp32 求和，和隨行的偏移量增長（約 N 乘 x ），靠近 1e36 的行直接溢位，全部輸出變成 NaN；即使沒溢位，均值也會在偏移量量級上舍入，x − mean 把這個舍入帶進每個元素，於是常數行算出的方差等於舍入的平方，歸一到正負 weight 而不是 bias。修法是給每個由行構成的 fp32 量加一條不變式：它只被行的擴散度約束，不被偏移量約束——實現上取「行內某個元素」作基準再相減，warp 主導的核用 warp 首元素、分片核用行的首元素。這條與上一期報告裡 #2812 列出的四個 Norm 運算元缺陷是同一類問題的正面修復。

4.2 跨行與轉置檢視的 SIMD 載入丟掉 DMA 依賴，根因落在邏輯區域重建（#3749）

同批裡技術含量最高的一條，報告人環境為 main 分支 e8225d7f5、Ascend950PR、CANN 9.2.0。問題是兩處連續 SIMD 載入丟掉了對更早一次 GM 到 UB 複製的依賴：一是行主序載入從行中間開始並跨到下一行，二是訪問轉置檢視且物理連續維不是最後一個邏輯維。根因路徑寫得很細：生成的 tl.access_ptr 覆蓋物理載入範圍，而 MemoryAccessDetector::LogicalPointerRegion 重建出的邏輯區域漏掉了其中一部分，依賴分析於是認為輸入 DMA 與載入無關，AutoSchedule 把輸入複製挪到載入之後，InsertSync 也不發 MTE2 到 V 的 set/wait。最小復現裡 work.shape 為 (2, 128)，先 T.copy(A, work[1, 0:64])，再在 T.SimdVF() 裡 T.simd.vld(work[0, 64]) 讀 128 個連續半精度元素：生成的讀描述符是 tl.access_ptr(work[0, 64], 128, 1)，物理覆蓋 [64, 192)，其中 [128, 192) 正是剛被 DMA 寫過的部分，而重建出的區域是 work[0:1, 0:128] 即物理 [0, 128)，完全錯過被寫區間；行數按 ceil(128/128) 算成 1 行，起始列 64 沒被計入。這條與本視窗主力在補的 FlashMLA、PTO 向量化是同一塊地基，一旦命中就是靜默錯結果。

來源：https://github.com/tile-ai/tilelang/issues/3749

五、趨勢觀察

這一天最值得記的判斷是：昇騰不再是「適配目標」，而是「首發目標」。FlashMLA 這種 DeepSeek 自家解碼路徑上的核心核心，直接以昇騰 950 為目標寫在主線裡，用的還是 T.Stage、annotate_buffer_addresses 這類為顯式排程準備的底層能力，而不是另開一個倉做移植。配合編譯器側那三處支援（L0C 到 UB 保留 NZ、AIV 流在流水線前選定、顯式階段按原始碼順序發射），可以看出昇騰路徑正在從「能跑」轉向「能按排程意圖跑」。

第二條線索是正確性的重心在下移。上一期主線為 TIRX 遷移回退了一整套 ThreadSync 正確性改進，這一期立刻出現兩條補位：主線 #3752 調 z3 求解資源上限，#3735 提出用模組化索引的不相交性減少需要證明的形狀；同時 #3749 把一處「依賴分析看不見物理載入範圍」的缺陷挖到了 MemoryAccessDetector::LogicalPointerRegion 這一層。把這些和 TileFoundry 那條暗線放在一起看——分析層能證明 83 個夾具裡的 52 個共享記憶體排序，而 lowering 按 main 的方式做會讓 7 個程式裡的 4 個算錯——同一個訊號出現了三次：TileLang 現在的主要風險不是功能不夠，而是「生成的程式碼看起來對、實際不對」，而團隊選擇的做法是把正確性做成可拒絕的證明，而不是靠補丁逐個堵。

第三條是測試與契約開始獨立成層。TileOPs 的 tileops_test 把冒煙測試從 CUDA 上摘下來，compile-contract-gate 把 dispatch 契約與 workload 資料生成拆開，兩者都在同一小時內合入；作者同時明確寫了「共享參考不能證明真實後端正確」。這種把「能測什麼」和「證明了什麼」分開表述的習慣，比多合幾筆效能補丁更能說明這個專案正在走出原型期。

最後注意一個反差：運算元側單日 7 筆效能合入、6 筆都帶 H200 實測表格，而新聞側三通道 24 小時零命中。TileLang 的對外聲量仍然集中在「DeepSeek 開源昇騰元件」這類事件上，日常進展幾乎只發生在倉庫裡。對跟蹤這個專案的人來說，這意味著日報的主體只能是提交與 PR，而不是報道。
