這個視窗的主線是善後。主倉五筆合入（+1903/−617，22 處檔案改動）沒有一筆新增運算元、沒有一筆新後端，四筆都在收 #3512 那輪 PTO 向量化改造的尾巴：VMI 描述符在 typed view 的 gather/scatter 與單元素載入上取錯，於是 #3894 一次改掉 6 個檔案、+925/−550；分析式遍歷把標量定義提前繫結，IntSet 在迴繞 cast 上求值拋異常，於是 #3793 加了保護；車道佈局推斷把顯式 SIMD 的向量塊地址當成標量車道訪問，老寫法直接編譯不過，於是 #3796 保留舊路徑；codegen_pto 改成發 si32/si64 而 PTO 原子只認 signless，於是 #3792 在呼叫邊界做區域性重解釋。這四筆的共同點是「改造之後原有的合法程式不再合法」，屬於大改動的必然代價，但從 11-10 到 11-13 連續四個視窗都在付這筆賬，說明 PTO 這條線的迴歸面比預估的寬。

第五筆 #3614 是另一種性質：它不是修 bug，而是防死鎖。昇騰核心有兩種排程模式，mode=0 是「有可用核就啟動運算元」，mode=1 是「等運算元所需的全部核資源到位再整體啟動」。做全核同步的運算元如果在普通模式下啟動，可能只拿到一部分核就先跑到全核屏障上等其餘的核，而其餘的核正被另一條流佔著——資源成環，裝置直接掛死。這筆改動在 codegen 側識別出「帶常量 0 的跨核同步」後自動置 __schedmode__(1)，並把該標誌按函式重置以防洩漏到後續入口；同時把跨核 set/wait 介面裡整數形態的 mode 收窄到 0/1/2/4，非整數不校驗以保留符號量。迴歸檔案 78 行，覆蓋全 AIC、全 AIV、AIC+AIV 組合協議、三個區域性模式與標誌重置共七種情形。

一、核心專案進展

1.1 昇騰：跨核同步 mode=0 強制 batch 排程，全核屏障不再與多流搶核死鎖（#3614）

這筆改動 5 個檔案、+102/−1，其中 78 行是新增的迴歸檔案（test_ascend_schedmode.py，位於 testing/ascend/target/ 下），真正的編譯器改動只有二十餘行：在 Ascend codegen 裡識別出「帶常量 0 的跨核同步」後置 __schedmode__(1)，並把這個標誌做成按函式重置的成員，避免洩漏到後續入口。

要看清它的必要性得回到排程語義。昇騰核心的 mode=0 是普通模式——只要運算元所需的部分核資源可用就啟動，不同流的運算元可以重疊；mode=1 是批模式——等運算元所需的全部核資源到位再整體啟動。做全核同步的運算元（全 AIC 同步、全 AIV 同步，以及「AIV 與本地 AIC 同步 → 全部 AIC 同步 → 再同步回本地 AIV」的組合協議，其內部含一個 mode=0 階段）在普通模式下啟動時，可能只拿到部分核就先跑到全核屏障上等待，而它等的那些核正被另一條流佔著且不會釋放，資源成環，裝置死鎖。批模式消除的就是這個視窗。

順帶做了介面收窄：跨核 set/wait 介面裡整數形態的 mode_id 只接受 0、1、2、4，其餘整數直接拒；非整數不校驗，以保留符號量傳參的可能。文件串也補了一句實情——同一份 API 文件列出的模式在三個目標上並不一致：910B/910C 支援 0/1/2，950 才多出 4。迴歸覆蓋七種情形：全 AIC、全 AIV、AIC+AIV 組合各自應開批模式，mode=1/2/4 應保持預設，以及標誌在函式之間不殘留。

來源：https://github.com/tile-ai/tilelang/pull/3614

1.2 昇騰 PTO：VMI 描述符與邏輯覆蓋校驗一併收口，單筆 +925/−550 為本期最大（#3894）

#3894 是本視窗最大的一筆（6 個檔案，+925/−550），把兩件獨立的事放在一個分支裡。第一件是修 VMI 記憶體描述符，涉及兩類形態：typed view 的 gather/scatter，以及單元素載入——兩者在構造描述符時取的基址與步長與實際訪問不一致。第二件是把 VMI 前端冗餘的邏輯覆蓋拒絕刪掉。

第二件事的前提值得寫清：刪校驗不是放鬆，而是因為共享記憶體檢測器的修復（#3805）已經落地，前端再攔一遍屬於重複攔截，且會誤傷跨行、轉置與動態檢視這些本該放行的形態。換句話說，同一處語義在兩個層次上各做了一次判斷，先落地的那個修好之後，後一個就成了負擔。

−550 行的刪除量主要來自這兩處的收斂。對下游的含義是：typed view 的 gather/scatter 與單元素載入兩類寫法在 PTO 目標上從「能過但結果不對」變成「要麼正確、要麼被檢測器攔下」。

來源：https://github.com/tile-ai/tilelang/pull/3894

1.3 昇騰 PTO：標量 cast 事實加保護，迴繞 cast 不再讓 IntSet 求值拋錯（#3793）

復現形態很小：u = uint32(i - 1)，i 落在 [0, 63]。u 與任何 VMI 地址都無關，但 LegalizePTOVMIMemoryAccess 會在它上面失敗。根因在 #3512 引入的分析器感知遍歷——它會把標量定義積極繫結進分析上下文，而 IntSet 在求 cast 端點時，若其它子分析器已經裝入了一個被低估的界，迴繞 cast 就會拋異常。

修法是在下沉期跳過不安全的分析（2 個檔案，+571/−13）。這類「分析器之間互相汙染假設」的問題在大改之後的編譯器裡最費時間：報錯位置在一個與故障無關的標量上，堆疊裡也看不出是誰先裝錯了界。

來源：https://github.com/tile-ai/tilelang/pull/3793

1.4 昇騰 PTO：顯式 SIMD 並行迴圈不再被車道佈局推斷拒收（#3796）

#3512 引入的 PTO 車道佈局推斷會拒掉既有的 T.Parallel 巢狀——只要裡面寫了顯式 SIMD 指令。原因是推斷把這些迴圈的地址當成標量車道訪問，而它們實際是在向量塊上迭代。

典型例子寫在 PR 裡：一個 T.Parallel(2, 32) 巢狀，迴圈體用 S.vld(temp[h, block * 64]) 與對應的 S.vsts(...)，每次迭代處理一條 64 元素的 FP32 向量。這種寫法在推斷出現之前是合法且常用的，推斷上線後一律編譯失敗。改動 5 個檔案、+194/−17，做法是保留舊式的顯式 SIMD 並行語義，讓推斷只作用於它該管的形態。

來源：https://github.com/tile-ai/tilelang/pull/3796

1.5 昇騰 PTO：整數原子改走 signless 相容包裝，有符號輸入可編譯（#3792）

#3512 之後 codegen_pto 對 TileLang 的整數值發 pto.si32/pto.si64，而 PTO 的原子介面只接受 signless 的 i32/i64，於是整數緩衝上的 T.atomic_add、T.atomic_max、T.atomic_min 全部編譯失敗（此前已在上一期的同批條目中提到，本視窗 11:27 落主幹）。

改法只在生成的呼叫邊界做區域性適配（4 個檔案，+111/−36）：把指標與運算元按同寬重解釋為 signless，保留指標的地址空間，返回值再還原成邏輯型別；min/max 保持原本的有符號或無符號比較語義。這樣 #3512 建立的邏輯型別體系不必推翻，適配壓縮在原子這一層。

來源：https://github.com/tile-ai/tilelang/pull/3792

1.6 主線口徑：五筆合入全為昇騰，+1903/−617，版本仍停 v0.1.15（11-12）

審計不是單向的抱怨。同一天在審更新的 50 筆主倉 PR 裡，有一大批正對著這些缺口，且幾乎全是「拒絕非法輸入」而非「新增功能」：#3973 把 hf32 的 nearest_zero 在 CCE 後端從 NEAREST_AWAY 改回 NEAREST_ZERO；#3972 讓 GEMM 輸入 dtype 表與兩個 codegen 後端雙向對齊（float8_e5m2 被 Python 側誤拒）；#3971 接受 shared.l0c 的 .dyn 拼寫；#3969 拒絕非 UB 目的地的 pad_value；#3968 推進 ND 轉 NZ 散射的掩碼計數使迴圈能終止；#3967 與 #3970 改為直接拒絕位歸約與批次歸約，不再發出模板裡沒有的型別；#3966 拒絕 16 位向量上的 PK4_B32 儲存；#3965 在非主執行緒跑 msprof 時跳過訊號延遲；#3963 改用執行時尾掩碼處理 ND 轉 NZ 的部分趟；#3863 拒絕打包後尺寸非法的 FP4 車道數；#3862 把解析出的 NPU 架構折進核心快取鍵。

這批 PR 的形態高度一致：先證明「這條路徑會讓編譯器發出不存在的東西或靜默算錯」，再在前端加一道拒絕或在下沉期補一條正確路徑。對一個要鋪到多家國產加速器的編譯器，這類改動的價值高於新增運算元。

來源：https://github.com/tile-ai/tilelang/pull/3973 、 https://github.com/tile-ai/tilelang/pull/3972 、 https://github.com/tile-ai/tilelang/pull/3968

4.3 CUDA 側三筆新 issue：cp.async 兩位元組、佈局推斷指數級耗時、Pipelined 顯式 order（11-12）

CUDA 側三筆新 issue 各有代表性。#3988：fp16 的 T.gemm 在 M=1、K 為奇數時走流水的 cp.async，仍會發出非法的 2 位元組傳輸（IsValidCPAsyncTransferBytes 攔不住），0.1.15 與主幹（348e807）均可復現，而 #2365 當時修的迴歸形態是透過的——說明同一族問題還有未覆蓋的形狀。#3987：tl.LayoutInference 與 tl.LowerTileOp 的耗時隨 T.Parallel 中複用子表示式呈指數增長，復現只需 sm_120a 下降、不必起核心；對應的修復 #3997 已在佇列（限制條件證明的工作量，同一迴歸從 34.89 秒、超過 10 秒編譯上限，變為透過）。#3996：T.Pipelined 帶顯式 order/stage、且複製經片段中轉時，報「Fragment buffer access with non-zero index [1]」，而報錯裡的那個下標並不在使用者程式裡——錯誤資訊指錯了地方。

同日在審的 CUDA 修復還有 #3998（共享佈局與 ldmatrix 前提不符時回退標量 MMA，修 #2642）與 #3975（自動釋放單 CTA TMEM 前先做全 CTA 屏障，warp 0 此前不等其它 warp 用完）。

來源：https://github.com/tile-ai/tilelang/issues/3987 、 https://github.com/tile-ai/tilelang/issues/3988 、 https://github.com/tile-ai/tilelang/pull/3997

五、趨勢觀察

一是大改造的善後期比改造期更長，且成本落在「原本合法的程式不再合法」上。#3512 把 PTO 的向量化與型別體系一起換掉，之後連續四個視窗都在補它的迴歸面：執行後端換預設（11-11）、整數原子（11-11、11-12）、顯式 SIMD 並行迴圈與標量 cast 事實（11-12）、VMI 描述符（11-12）。這四類問題的共同點不是「新功能算錯」，而是「舊寫法編譯不過或結果變了」。對編譯器專案，這類迴歸的排查成本遠高於新功能的 bug——報錯位置常常在一個與故障無關的標量或地址上，堆疊裡看不出是誰先裝錯了假設。

二是後端矩陣從「一家獨進」變成「多點同時開工」，形態也分化成四類。本期主倉五筆全在昇騰，但同視窗 ROCm 一次開出七筆成系列、海光一條分支一天十筆、Sunrise 在走釋出流水線、Hexagon 以個人 fork 的形式把 TileLang 推到手機 DSP。四種形態（上游內建後端、廠商適配倉、獨立發行版、第三方 fork）對應四種投入深度，這個分化本身就是判斷各廠商依賴程度的可用指標：廠商倉跟版本、發行版跟主線、fork 跟自己的硬體。

三是「給 agent 用的工程化」開始成規模出現。mlir-ascend 的 harness 分支一日 +7632 行，內容是技能庫、模擬 trace 流程與 Roofline 計算器，服務物件是「寫運算元的人或 agent」而不是編譯器本身；同一周，Hexagon fork 的 README 直接寫明後端與模型由 AI agent 在維護者指導下重寫、四天 75 個 PR 佔當前程式碼八成以上。兩件事方向一致：TileLang 這類 DSL 的抽象層恰好落在「agent 能寫對」的粒度上，於是生態開始為 agent 鋪工具鏈，而不是隻為人鋪文件。這一條值得按周跟。

四是RISC-V 四源連續六個視窗靜默，與整體活躍度形成明顯反差。TVM 路線、MLIR 路線、社群索引頁、算能 TPU 四個上游全部停在原引用，而同期主倉一天五筆合入、ROCm 一次七筆、第三方 fork 在推進一個新硬體後端。四源之外那條 CPU 線（Weft）在 11-11 給出了階段性結論後也未再更新。判斷不變：RISC-V 側的 TileLang 工作仍處在「有路線、少提交」的階段，真正可跟的落點還是那兩條相互獨立的實現路線是否繼續推進。

侷限說明：本期 GitHub 匿名 API 額度（60 次/小時）在採集早期耗盡，隨後改用兩種不吃額度的通道補齊——PR 增刪行與檔案數走 diff 端點統計，非預設分支的提交走分支級 atom 流；因此 1.2 至 1.5 四筆合入的檔案數與行數為 diff 端點實測值，正文描述取檢索介面返回的 PR 摘要，未逐行復核 diff。Hexagon fork 的視窗內推送經七個分支的 atom 流逐一比對定位到 fix/hexagon-dma-load-only，其餘分支同期無新提交。第三方運算元倉的官方屬性無法從倉庫本身核實，已在正文標註。新聞側只有零命中，無外部報道可交叉驗證。
