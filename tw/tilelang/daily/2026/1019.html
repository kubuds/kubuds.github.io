今日重點：TileOPs 單日 20 筆把八運算元推入已實現，昇騰三筆與海光塊縮放收口——PTO 向量化框架進入在審（10-16）

週末三天的重心從主倉移到運算元庫：TileOPs 在 10-18 一天合入 20 筆，視窗內累計 44 筆，直接把 8 個此前僅有 spec 的運算元推入 implemented 狀態，覆蓋 MLA varlen 前填、DSA 分頁解碼、因果卷積、Hadamard 變換、W4A8 GEMM、分頁 KV 匯聚與注意力狀態合併。主倉 tilelang 同視窗 5 筆合入，兩筆是 CUDA warp-specialization 與流水線佈局的正確性修復，三筆屬昇騰；海光倉庫把塊縮放 GEMM 的 scale copy 從打包、原生化到流水化補齊。更值得關注的是在審佇列：昇騰 PTO 向量化框架 #3512 以 44 檔案、近兩萬行新增把 T.Parallel 編譯到 PTO VMI，目標直指 Ascend 950；主倉 51 筆在審中 27 筆標 BugFix，說明專案正處在運算元鋪開之後的正確性硬化階段。

一、核心專案進展

1.1 主倉：純 TMA 生產者納入正向屏障，修復 warp-specialization 死鎖（#3503）

在純 TMA 生產者配置下，ProducerConsumerWSRewriter 讓生產者迴圈跑遍所有生產者 warp，但此前只有被選中的執行緒到達正向（full）屏障，1 至 3 號生產者 warp 只等背壓（empty）屏障，與消費者不同步，可能落後兩個相位並在複用的 parity 上掛死整塊。改動讓每個生產者執行緒都到達正向屏障（arrive_count 取 producer_extent），與 SIMT、cp.async 生產者的既有做法一致，修 #3470。

來源：tile-ai/tilelang#3503（10-16）

1.2 主倉：兄弟流水線共享緩衝只展開一次，修 LayoutInference 崩潰（#2342）

兩個相鄰的 T.Pipelined 迴圈共用 alloc_shared 緩衝但 num_stages 不同（例如 2 與 4）時，第一條流水線把緩衝從 (64,32) 展開為 (2,64,32)，第二條的收集階段把已展開的緩衝當成原始分配再插一維，得到四維 (4,2,64,32)，LayoutInference 的 ICHECK 直接失敗。改動按原始分配識別並只展開一次，替換此前的 #2337，修 #2309，新增 349 行、刪除 6 行。

來源：tile-ai/tilelang#2342（10-16）

1.3 主倉在審：Profiler 三連修復與 eager 前端原始碼定位（#3559 / #3560 / #3561 / #3558）

Profiler 三筆針對基準誤差與跨裝置問題：#3559 修跨裝置 CUDA Graph 捕獲為空（複用上一張卡快取的捕獲流，replay 不執行，迴歸計數為 9 而非 27）；#3560 在後續呼叫覆蓋前快照輸出；#3561 把 cache-flush 時間排除出早停判據，避免先試慢候選改變最終勝者。另有 #3558 把 eager 重寫器的模板行號對映回使用者語句首行，修 traceback 與覆蓋率錯位。

來源：tile-ai/tilelang#3559、#3561、#3558（10-18）

二、多後端適配（昇騰 / 沐曦 / 海光 / 摩爾執行緒）

2.1 昇騰：SS 緩衝、RNG 狀態重置與 SimdVF 歸約三筆合入（#3514 / #3331 / #3437）

#3514 新增 T.alloc_ss：dav-3510 上一個 AIC 與其兩個 AIV 共享的標量儲存，每個 AIV 可釋出自己的 uint32 字，AIC 經打包的 uint64 檢視讀取；組內 3 KiB SS 池、32 位元組對齊基址、版本計數與同步走標準緩衝管線。#3331 在 AddFunction 中重置 RNG 狀態，避免兄弟核心殘留的 __asc_rng_state 導致 bisheng 報未宣告識別符號。#3437 讓 SimdVF 內 dim=1 歸約只存 lane 0。

來源：tile-ai/tilelang#3514、#3331、#3437（10-16）

2.2 昇騰：T.Parallel 向量化到 PTO VMI 框架在審，44 檔案、近兩萬行（#3512）

該 PR 讓使用者在 T.SimdVF(lanes=L) 內書寫標量並行 T.Parallel（逐元素、控制流、歸約），由編譯器向量化為 PTO VMI 指令，再經 PTOAS 編譯到 Ascend 950 執行。分工上，TileLang 側負責邏輯 lane 佈局、向量化 pass 管線、VMI 指令生成與 Fragment 邏輯對映，工具鏈側負責物理暫存器切分、mask 物化與向量暫存器分配。改動 44 個檔案、新增 18988 行、刪除 67 行，是 PTO 線從執行路由走向自動向量化的關鍵一步。

來源：tile-ai/tilelang#3512（10-18）

2.3 海光：塊縮放 GEMM 的 scale copy 三筆——K-major 打包、FP32 MLS、流水化（#22 / #23 / #24）

#22/#23 支援 K-major LDS 的打包 scale copy，並支援 gfx946 原生 FP32 MLS GEMM（kPack=2），同時補塊縮放、TF32、FP32 迴歸；#24 進一步支援塊縮放 GEMM 中的流水化 scale copy，新增 357 行、刪除 47 行、5 檔案。三筆在 10-16 至 10-17 間全部合入，海光線的塊縮放 GEMM 從「能算」推進到與主倉流水線對齊。

來源：tile-ai/tilelang-hygon#22、#24（10-17）

2.4 沐曦與摩爾執行緒：metax dev 線同步主線並修 xfail；musa 視窗內無推送（10-16）

tilelang-metax 預設分支為 dev，視窗內兩筆合入：#160 修 MetaXGPU 的 xfail 用例（含 test_cuda_fma_fmul.py 等），#161 將 main 合入 dev，屬跟隨主倉基線的常規同步。tilelang-musa 預設分支 main 視窗內零提交，最新一次仍是 09-30 的「Prepare public TileLang MUSA 0.1.15」。tilelang-mlir-ascend 最新提交停在 10-15，無視窗內推送。

來源：tile-ai/tilelang-metax（10-16）

三、生態與採用方（TileOPs / TileFoundry / 運算元庫）

3.1 TileOPs：注意力側兩筆轉正——MLAVarlen 轉 implemented、DSAPaged 落地（#2629 / #2633）

#2629 把 MLAVarlenFwdOp 狀態改為 implemented，此前打包 varlen 的 MLA 前填核心已合入，本筆補齊 manifest 要求，並讓 MLAVarlenCall 按 DeepSeek-V3 8×4K、DeepSeek-V3 混合 512–16K、Kimi K2 4×8K 三種配置構建呼叫，BF16 與 FP16 雙精度註冊基準，對標 FA3 的 flash_attn_varlen_func 與 FlashInfer 的 BatchPrefillWithRaggedKVCacheWrapper。#2633 新增 DSAPagedFwdOp，在 FlashMLA 的 DeepSeek-V3.2 656 位元組行格式上做分頁 FP8 潛快取的分塊解碼，返回 o 與 lse，SM90 核心以兩個 64 槽鍵塊緩衝在三個 warp 組間輪轉，128 頭時兩段 64 頭按 2-CTA 叢集協作。

來源：tile-ai/TileOPs#2629、#2633（10-18）

3.2 TileOPs：CausalConv1d 雙運算元、Hadamard 變換與 SM90 W4A8 GEMM 補齊（#2627 / #2624 / #2590）

#2627 新增 CausalConv1dFwdOp 與 CausalConv1dUpdateFwdOp，寬度 2 至 4、可選 bias 與 SiLU、FP32 累加，前填走打包序列（cu_seqlens 與可選 has_initial_state），解碼每序列推進一步，狀態形狀 [B, D, W-1] 與 vLLM 的 causal_conv1d_update 對齊。#2624 的 HadamardTransformFwdOp 支援 base_order 1/12/20/28/40、n 至 2^28、fp16/bf16 配 FP32 累加，用一次 16 位 MMA 對完成四級蝶形。#2590 的 GemmW4A8FwdOp 在 SM90 上做 FP8 e4m3 啟用乘組縮放 INT4 權重、BF16 輸出，decode 核服務 M≤32，更大 M 走 warp 特化前填核。

來源：tile-ai/TileOPs#2627、#2624、#2590（10-18）

3.3 TileOPs：線性注意力四家族逐點位效能收口（GLA / GDN / KDA / DeltaNet）（10-18）

視窗內 TileOPs 絕大多數合入標 [Perf]，集中在四條線性注意力線。GLA：前填狀態鏈去掉一次矩陣乘（#2626）、decode 狀態按 value 切片一鍵一塊（#2631）、SM89 BF16 的 gate 梯度歸約展開（#2618）與鍵歸約部分展開（#2617）。GDN：前填只在走查留下空閒 SM 時才分割槽（#2628），強 gate 衰減下保持前填有限（#2594）。KDA：chunk scan 拆成狀態走查與塊並行輸出（#2623），狀態尾條件改為布林判定（#2630）。DeltaNet：反向狀態梯度每塊只做一次矩陣乘（#2625）。

來源：tile-ai/TileOPs#2626、#2631、#2628、#2623（10-18）

3.4 TileOPs：Softmax 跨 16-CTA 叢集分裂與 GLA decode 狀態切片（#2632 / #2631）

#2632 針對 lm-head 這類少行長行（4×102400，FP16/BF16）新增 SoftmaxClusterSplitKernel：舊實現每行 58 段經全域性記憶體交換 (max, sum) 並跨 grid 屏障，新實現把一行攤到 16-CTA 叢集的暫存器上，每個元素只取一次指數，跨 warp、跨 CTA、跨叢集用 shuffle 樹按 max-first 摺疊，每 CTA 只向對端共享記憶體發一對值。#2631 則把 GLA decode 每頭一塊改為每塊一個 value 切片，只讀一次狀態，鍵軸歸約先用 16 位元組向量做區域性和再一次批次交換。

來源：tile-ai/TileOPs#2632、#2631（10-18）

3.5 TileFoundry：儲存計劃與發射計劃分離，schedule 里程碑修正（#243 / #241）（10-18）

#243 把原始分配決策留在 analysis 層，移除可執行別名釋出與 MemoryMetadata.alias，拆出只讀的 StoragePlan / IssuePlan、TirBuilder、命名與單一 LoweringContext；訪問結果做記憶化，轉發複用其值，並修復在稀疏物理佈局下仍按邏輯位元組預留的共享記憶體放置問題，39 檔案、新增 2543 行、刪除 1889 行。#241 是一筆 314 檔案的里程碑修正（新增 53049 行、刪除 69314 行），覆蓋 M1 至 M8：修正 Reshard 流量與別名、儲存例項比較、規範佈局與區域性投影、視窗繫結與詞法作用域校驗，並遷移兩個 Qwen 示例、重生成 31 個完整長組與全部 64 個短 TIR 檔案。

來源：tile-ai/TileFoundry#243、#241（10-18）

來源：tile-ai/TileOPs#2554（10-18）

五、趨勢觀察

5.1 從「運算元補齊」轉向「逐點位效能收口」

視窗內 TileOPs 44 筆合入裡，標 [Perf] 的佔絕大多數，且幾乎每筆都點名對標基線：torch-compile、quack、FA3、FlashInfer，並給出具體形狀（serving-b1-h8、serving-b1-h16、lm-head 4×102400、8192 至 16384 的 RMSNorm 行）。這說明運算元面鋪開之後，工作重心已轉為在真實服務形狀上逐個消掉零點幾個百分點的差距，而非繼續堆運算元數量。

5.2 注意力鏈路對齊 DeepSeek-V3.2 生產格式

DSAPagedFwdOp 直接實現 656 位元組行格式的 FP8 潛快取分頁解碼，MLAVarlenFwdOp 按 DeepSeek-V3 與 Kimi K2 的真實配置註冊基準，PagedKVCacheGatherFwdOp 與 MergeAttentionStatesFwdOp 補齊 KV 匯聚與狀態合併。這條鏈路加上線性注意力四家族，已經覆蓋從長上下文前填到解碼的完整推理路徑，且以 vLLM 與 FlashMLA 的儲存佈局為準繩。

5.3 昇騰從「能跑」走向「標量並行自動向量化」

上期的主線是 PTO 執行路由合入，本期 #3512 把 T.Parallel 直接編譯到 PTO VMI，並明確以 Ascend 950 為目標、與 PTOAS 分工物理暫存器與 mask 物化。同期三筆小修復（SS 緩衝、RNG 狀態、SimdVF 歸約）都是在補 dav-3510 上的儲存與同步語義。這條線正在從「把 kernel 跑起來」轉向「讓使用者按標量寫法寫、編譯器負責向量化」。

5.4 編譯器進入正確性硬化期

主倉 69 筆在審 PR 中 tilelang 佔 51 筆，其中 27 筆標 [BugFix]，集中在 ThreadSync（地址寫入判定、謂詞順序）、Transform（向量化域規範化、跨執行緒 WAW、流水線傳遞依賴）與 codegen（cp_async 等待深度、ROCm FP4 常量、Metal hoisting）。這批問題多在特定組合下才暴露，屬於典型的規模化使用後回灌的邊界條件；TileFoundry 的 #243 拆出只讀計劃物件，也是同一方向的結構性治理。
