一、核心專案進展

1.1 主倉：昇騰面四處收筆——獨立 AIV 執行（#3485）、PTO DeepGEMM codegen（#3330）、跨 warp allreduce 修復（#3494）、示例目標選擇（#3474）（10-14）

日期：2026-10-14　來源：獨立 AIV（#3485）／ PTO codegen（#3330）／ allreduce 修復（#3494）／ 示例目標選擇（#3474）

  • 獨立 AIV 執行（#3485）：擴充套件 Ascend AutoSchedule，使 AIV0 與 AIV1 可在 sid 依賴的控制流下執行不同工作——支援交替收尾（epilogue）、反量化與收尾分工、不相交輸入分割槽以及迴圈內角色切換。實現上把 AssignCore 提前到延遲估計與排程之前，為 AIV 區域性 UB 緩衝與標量狀態建立獨立身份，並按參與核建模流水線資源、特殊暫存器依賴、UB 容量與同步標誌庫；保留統一核心的 collective 路徑與一/兩 AIV 發射幾何。L0C→UB 複製仍在 AIC 上執行。
  • PTO DeepGEMM codegen（#3330）：跨控制流跟蹤 tl.ascend_set_mmad_direction 並把生效方向編碼到 MAD 指令上，拒絕在衝突方向下可達的 MAD；支援 SIMD 後增量載入（同時返回資料與更新指標）、混合 AIC/AIV 核心中的 UB 地址到 PTODSL 指標轉換、動態 L0C→UB 維度與步長、int16 有符號打包 MX scale；改進條件表示式與執行時迴圈的程式碼生成。報告稱 15 個 DeepGEMM PTO 用例中 14 個透過，test_bf16_m_grouped_padding 因 PTOAS VPTO 後端無法合法化 FP32→BF16 轉換仍受阻。
  • 跨 warp allreduce 修復（#3494）：當一個 cross-warp allreduce 呼叫覆蓋多個獨立歸約組時，ascend 與 pto 目標錯誤地把第一組結果交給所有組；本筆修復該正確性問題（跟進 #3469）。
  • 示例目標選擇（#3474）：移除昇騰示例與測試中硬編碼的 target="ascend"，改由 TILELANG_DEFAULT_TARGET 環境變數決定；DeepGEMM JIT 入口支援 execution_backend="auto"；CI 對昇騰示例套件分別以 ascend 與 pto 兩個目標各跑一遍，並在文件寫明選擇方式。

1.2 主倉：基建三筆——CPU OpenMP 並行 grid 迴圈（#3109）、C 系 codegen 共享發射（#3289）、Windows NVCC 改走 MSVC（#3510）（10-14）

日期：2026-10-14　來源：CPU OpenMP（#3109）／ codegen 共享（#3289）／ Windows MSVC（#3510）

  • CPU OpenMP 並行（#3109）：為 CPU 後端加入可選的 grid 迴圈 OpenMP 並行——新增 MaterializeCPUParallelGrid 把帶註解的 CPU grid 迴圈轉為並行迴圈，配套迴圈 collapse、執行緒數配置、最小 trip 數門限與分配下沉；補齊 Linux / macOS / Windows 的 OpenMP 編譯標誌與 pass 配置項；測試覆蓋正確性、pragma、分配下沉、門限與單維情形。CPU 後端首次具備網格級並行能力。
  • C 系 codegen 共享（#3289）：引入 CodeGenTileLangCBase 統一 CUDA、HIP、CPU C、Ascend C++、Metal 與 C 主機程式碼生成；修復 T.import_source、T.Kernel(prelude=...) 與 pragma_import_c 在源文字缺少末尾換行或以反斜槓結尾時吞掉下一生成行的問題；匯入內容按「標頭檔案→匯入→生成宣告與函式」排序並保證兩個分隔換行。驗證：聚焦迴歸 83 透過、相關 codegen 與 launch 套件 405 透過。
  • Windows NVCC 改走 MSVC（#3510）：NVCC 拒絕 get_cplus_compiler() 選出的 clang-cl——改為從 NVCC 子程序環境選擇 cl.exe（不改主機 C++ 編譯器選擇），補 VS 2026 18/* 回退路徑，非 Windows 平臺不再傳 -ccbin=None；CUDA 13.3 下復現用例修復前失敗、修復後編譯透過。

1.3 主倉：ROCm scan 波前修復（#2326）、測試基建快取（#3502）與治理配置（#3513）（10-14）

日期：2026-10-14　來源：ROCm scan（#2326）／ 測試基建（#3502）／ CodeRabbit 標籤（#3513）

  • ROCm scan 波前修復（#2326）：HIP 的 cumsum / cummax 預設按 64 lane 段執行，在 Wave32 GPU 上結果錯誤——讓既有 run 入口按目標波前寬度選擇段寬（受塊執行緒數上限約束），32 執行緒塊在編譯期排除 64 lane 模板；補 32 執行緒前向/反向掃描與源/目標步長不同的覆蓋；gfx950 MXFP4 例子與測試改用 {"kind": "hip", "mcpu": "gfx950"} 目標寫法。驗證：CUDA scan 套件在 B300 上 17 透過、CuTeDSL 原始碼生成測試 2 透過；AMD 端執行時驗證留給 ROCm CI。
  • 測試基建快取（#3502）：快取最近查詢 IR 體的呼叫資料供 collect_calls / assert_call_count 使用；把變換測試中的遞迴 visitor 與生成指令碼文字檢查替換為結構化 IR 斷言，並擴充套件軟流水、排程、同步、屏障與 Hopper intrinsic 的結構檢查。
