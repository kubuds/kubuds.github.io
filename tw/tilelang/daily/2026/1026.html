一、核心專案進展

1.1 主倉：partial-sync 命名屏障 id 在兩類儲存域間重號（#3643）

合於 10-25 14:30，2 檔案 +57/-1，修 #3642。ThreadSync 對 shared 與 shared.dyn 各跑一次，每次新建一個改寫器、各自從 kFirstUsedBarrier 重新編號；第二次執行跳過第一次已改寫的同步，卻不知道那些 id 已佔用，於是把同一個 bar.sync id, count 分給互不重疊的兩組執行緒。修法是讓編號跨兩次執行連續，併為跨域複用加斷言。這類缺陷編譯期不報錯、只在大 kernel 偶發。

來源：https://github.com/tile-ai/tilelang/pull/3643

1.2 主倉：clamp 的 NaN 傳播下降被回退，T.clamp 回到 min/max（#3628）

合於 10-23 16:51。回退 #3205 整條鏈路：刪除 tl.clamp 內建、各後端下降註冊、codegen 分支與裝置端輔助函式（含昇騰註冊），T.clamp(x, lo, hi) 恢復為 T.min(T.max(x, lo), hi)，理由是額外 NaN 處理擋住了 min/max 的化簡與向量化。NaN 訴求未消失，同日另開 #3605 以 T.clamp_symmetric 在 CUDA SM86+ 單列實現，分工是「T.clamp 保通用、新介面保語義」。

來源：https://github.com/tile-ai/tilelang/pull/3628

1.3 主倉：int64 原子 max/min 與 AtomicStore 的 int64、bf16、fp16 崩潰（#3307）

合於 10-23 18:44。normalize_atomic_type 自 #1716 起把 int64_t 歸一成 unsigned long long 以支援 atomic add，結果讓 Atomic 的 max/min 及引用形式在 int64 上直接崩，AtomicStore 同樣中招並額外波及 bf16 與 fp16。修復按操作為 int64 單獨選型，AtomicStore 走獨立型別分派。屬「為一個操作改公共歸一化、連帶打斷其餘操作」的典型迴歸。

來源：https://github.com/tile-ai/tilelang/pull/3307

1.4 主倉：VectorizeLoop 不再靜默忽略迴圈步長（#3345）

合於 10-23 19:02，屬 #3301 跟蹤的 F319。向量化器只收到 (loop_var, extent, body)，步長根本沒進去：T.vectorized(0, 8, step=2)（迭代集 0/2/4/6）被下降成覆蓋整個 [0, 8) 的連續訪問。修復在進入向量化前拒絕非單位步長並給診斷。這一批子項的共同特徵是前端接受了無法下降的寫法、後端給出另一個程式的機器碼。

來源：https://github.com/tile-ai/tilelang/pull/3345

1.5 主倉：NVRTC 命中磁碟快取後自動調優結果寫不回（#3193）

合於 10-23 15:04。NVRTC 從磁碟載入 kernel 時不設 adapter.libpath，而調優選中配置後要憑該欄位儲存快取 kernel，於是每次命中都拋 AttributeError、結論被丟棄，使用者看到的是「每次啟動都在重調」。修復在快取載入路徑恢復 libpath，與全新編譯路徑一致，補快取過載與負向對照用例。

來源：https://github.com/tile-ai/tilelang/pull/3193

1.6 在審：用獨立打包的 TIRx 替換內建 TVM，改動 1043 個檔案（#3666）

10-25 19:16 提交，1043 檔案 +71428/-104176。刪掉 3rdparty/tvm 及 submodule 條目（保留 CUTLASS 與 HIP 標頭檔案），把前端、原生張量與作用域 IR、下降 pass、後端流水線、執行適配整體遷到獨立構建釋出的 tvm_tirx，相容層限定在 TileLang 內部，不設全域性 tvm 別名、不保留第二份 TIRx。這把前幾期「tvm fork 先行、主倉跟進」推到終點：底座從 vendored 原始碼轉成外部依賴，此後可獨立發版與回滾，合入影響面覆蓋整倉。

來源：https://github.com/tile-ai/tilelang/pull/3666

1.7 在審：sm_100 的 TMEM 釋放缺 CTA 屏障，warp 特化前導語句漂移（#3645 / #3663 / #3664）

三筆同源，都在自動 warp 特化與 Blackwell 新儲存上。#3645：sm_100 上張量記憶體釋放沒有 CTA 級屏障，生產者 warp 可在消費者 tcgen05.mma/tcgen05.ld 仍讀累加器時將其釋放。#3663：特化會把 T.serial 外層迴圈之外的前導語句搬進迴圈體，本應只執行一次的初始化被每輪重放，輸出錯。#3664：if 內包特化流水且 if 後有語句時，setmaxnreg 相關下降令 ptxas 失敗。三筆合看，「哪些語句屬於哪個 warp、生命週期到哪結束」仍缺完整語義模型。

來源：https://github.com/tile-ai/tilelang/pull/3645、https://github.com/tile-ai/tilelang/issues/3663、https://github.com/tile-ai/tilelang/issues/3664

1.8 新增缺陷：sm_120 上歸約下降失敗、三張注意力示例超共享記憶體（#3647 / #3646）

10-25 09:08 同日兩報。前者是 gdn wy_fast_bwd_split 在 sm_120 上的 ReduceOp 下降失敗——源索引依賴執行緒持有的歸約分段，不在既有規則覆蓋內；後者是 attention_sink、gqa_bwd、block_causal_attention_varlen 三張示例超 101376 位元組單塊共享記憶體上限。對應修復 #3662 已開：按裝置上限選更小瓦片、更少流水級與 128 執行緒，大裝置保持原預設。消費級 Blackwell 的容量約束正成為示例與調優表的硬邊界。

來源：https://github.com/tile-ai/tilelang/issues/3647、https://github.com/tile-ai/tilelang/issues/3646

二、多後端適配（昇騰 / 海光 / 新增 CPU 與 ROCm）

2.1 昇騰主倉：DeepGEMM 示例支援 FP4×FP4 打包輸入（#3589）

合於 10-23 10:26。為 dense、M-grouped、K-grouped 三套 DeepGEMM 介面開啟打包 E2M1 FP4×FP4 輸入，複用既有 MX GEMM kernel 與啟發式，從打包位元組儲存反推邏輯維度並按 FP4 的 64 元素對齊；後端側只改 MX 的 K 尾填充，批式構造器也接受 FP4。公開的 batch/einsum 介面仍保 FP8 以對齊 DeepGEMM-Ascend-Nightly，FP8×FP4 反量化留待後續。

來源：https://github.com/tile-ai/tilelang/pull/3589

2.2 昇騰主倉：DMA 保留緩衝基偏移、區域界先提升、週期緩衝完整生命週期（#3627 / #3625 / #3606）

三筆同於 10-23 合入，都是佈局與生命週期修正。#3627：DMA 規劃丟掉 Buffer.elem_offset，UB 別名以 elem_offset=256 構造時 T.copy(別名, out) 實際從 0 號元素讀；修法是把基偏移算進地址並在跨步切片（含巢狀）保留父偏移。#3625：區域最小值與長度用 Int64Promoter 提升後再構造半開區間，避免 int32 轉型遮住動態尾界、令重疊證明耗盡 Z3 預算，給原地持久化 RoPE 引入多餘跨迭代依賴。#3606：子緩衝生命週期摘要須完整覆蓋訪問才可提升，外部預載的值跨整個父週期存活，防止巢狀與手工流水下的複用覆蓋待讀者。

來源：https://github.com/tile-ai/tilelang/pull/3627、https://github.com/tile-ai/tilelang/pull/3625、https://github.com/tile-ai/tilelang/pull/3606

2.3 昇騰主倉：CI 映象升到 cann9.3.0 周更版（#3630）

合於 10-23 19:20，只改 CI：ascend 作業測試容器從 cann9.3.0-weekly.20260930 提到 cann9.3.0-weekly.20261021-ubuntu22.04-py3.12。它決定昇騰側全部迴歸用例實際驗證的是哪版 CANN 執行時，是判斷該線結論有效期的前提。

來源：https://github.com/tile-ai/tilelang/pull/3630

2.4 昇騰在審：E4M3 的 UB→L1 複製、片上記憶體溢位提前拒絕（#3639 / #3655）

#3639 為 Ascend 950 開啟 float8_e4m3fn 的 UB→L1 複製：ND 輸入經既有 scatter/post-copy 管線重排、預打包 NZ 直接搬運，footprint 與延遲分析補 FP8 元素寬度。#3655 讓 MergeUBAllocations 在下降階段按 UB、L1、L0A、L0B、L0C 各自容量校驗計劃佔用並報診斷，而非生成越界分配——起因是兩個獨立迴圈各自合法地選中 32KB L0A 瓦片的兩個版本、合併後超限。片上記憶體管理正從執行時報錯前移到編譯期拒絕。

來源：https://github.com/tile-ai/tilelang/pull/3639、https://github.com/tile-ai/tilelang/pull/3655

2.5 昇騰在審：PTO 目標預設走 tvm_ffi 執行後端（#3516）

10-24 更新的在審改動：為 pto 支援 tvm_ffi 並設為預設，execution_backend="auto" 現解析到 tvm_ffi。共享宿主機 codegen 負責 MakePackedAPI 與 C 宿主構建，昇騰執行時模組經 aclrtLaunchKernelWithHostArgs 拉起 PTODSL 編譯的 aibin，與 AscendC 路徑一致。與主倉 CPU 側 #3634（統一到 TVM-FFI、移除 CPU 專用 Cython 包裝）同向：執行後端在做減法。

來源：https://github.com/tile-ai/tilelang/pull/3516

2.6 昇騰倉：situ_glu 運算元合入，對齊 Kimi K3 門控啟用（#1891）

合於 10-23 16:04。語義與 dtype/shape/attr 約束逐條對齊 CANN ops-nn 的 activation/situ_glu，精度基準取 CPU fp64 的 PyTorch 金標準；純 Vector 單 kernel，宿主按 dim 把輸入合軸成 (rows, cut*inner) 零複製檢視，非末維切分不跨步。運算元對應 Kimi K3 Stable LatentMoE 的前向門控啟用，與上一期的 situ_glu 梯度、稀疏 MLA 一併，昇騰倉的運算元清單正按具體對話模型結構逐個鋪開。

五、趨勢觀察

釋出工程成了主戰場。 78 筆合入裡 TileOPs 佔 51 筆，其中十餘筆屬改名、打包、語義統一、文件與 CI 門禁——不是效能也不是新運算元，而是把介面凍住。跟蹤單七成、CHANGELOG 寫定 0.1.0 並標註 10-26，此後 0.x 的相容承諾開始生效；同期 TileFoundry 做成 core/nvidia/apple 三包、Sunrise 合入 0.1.15 分發版，三條線在同一周做同一件事：把「能跑」變成「能發」。

正確性重心從形狀校驗轉向新硬體與新排程。 上週主倉合入多是形狀與幾何校驗，本視窗換成生命週期與屏障：跨儲存域屏障重號、sm_100 張量記憶體釋放缺 CTA 屏障、warp 特化搬錯前導語句、setmaxnreg 觸發 ptxas 失敗。共同點是編譯透過而結果偶發錯，且都落在自動 warp 特化與新架構儲存上——把排程權交給編譯器之後必然要付的賬。

昇騰線從跑通走到按模型鋪運算元加每日迴歸。 situ_glu 對齊 Kimi K3 Stable LatentMoE 門控啟用，在審的 sparse_mla_fwd 與 GLM-5.3 kpool 同樣是特定模型結構的部件。每日全量 2903 項全通、次日又報失敗，說明用例規模已足以當門禁；配合 CI 映象追到 cann9.3.0 周更版，這條線的結論有效期以周計。

執行後端做減法，後端清單做加法。 CPU 統一 TVM-FFI、PTO 預設 tvm_ffi，加 CuTeDSL 修復與 NVRTC 編譯，方向一致：減少執行路徑分叉。後端清單反向擴張——Intel AMX 進 CPU 路徑、ROCm 補 FP4 與 E8M0、海光重提暫存器流水線。分發形態正從「一套程式碼多後端分支」變成「一套 IR、多個打包」，與 #3666 把 TVM 變外部依賴同路。
