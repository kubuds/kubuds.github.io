一、核心專案進展

1.1 主線：CuTeDSL 的 grid 同步改到每次啟動的 workspace，多流併發不再串擾（#3868）

合於 11-08 18:00。CuTeDSL 的 sync_grid() 原先把 barrier 計數與代際放在模組級全域性（__grid_sync_ctr、__grid_sync_gen），同一 kernel 在兩個流上併發啟動會共享同一個 barrier：兩個 grid 的到達被合併，某次啟動可能在自己的 block 全部到達前就被放行，殘留計數還會掛住後續啟動。H200 NVL 上單次 17.4 毫秒、成對 17.8 毫秒，說明 cooperative launch 確實在併發。修法是用 inline PTX 復刻 cooperative_groups::details::sync_grids：barrier 字取驅動為每次 cooperative launch 提供的 grid workspace 的 barrier 欄位，地址來自 %envreg1（高半）與 %envreg2（低半）；每個 block 的 thread 0 做一次 atom.add.release.gpu，block 0 加 0x80000000 - (nblocks - 1)、其餘加 1，再以 ld.acquire.gpu 自旋等 bit 31 翻轉。狀態按啟動隔離，因此併發啟動互不影響。迴歸測試在 main 上會掛死（300 秒被殺），修復後透過；作者同時保留了 CUDA 後端作對照，後者一直正確。

來源：https://github.com/tile-ai/tilelang/pull/3868

1.2 主線：CuTeDSL 有符號整數截斷按 arith.divsi 語義修正（#3551）

合於 11-08 07:48。CuTeDSL 對有符號 TIR 的 DivNode 發出的是 Python 地板除，執行期 T.truncdiv(A[i], 3) 在 -7 上返回 -3 而不是 -2，後續的 floor/ceil 修正再基於這個商繼續算，誤差會擴散。改法是給有符號標量與向量發 tl.truncdiv（底層 MLIR arith.divsi），純 Python 輸入走精確整數運算，向量儲存路徑與無符號 lowering 不動。迴歸 25 例，覆蓋 int8/int16/int32/int64、標量與向量、負除數、整數極值，以及「商乘除數加餘數等於被除數」。報告者在 issue #2973 的討論裡獨立用 CPU 參考與 MLIR 驗證過，並指出純 Python % 的邊界，這條意見直接進了實現。

來源：https://github.com/tile-ai/tilelang/pull/3551

1.3 主線：CuTeDSL 一次補齊 63 個檔案的示例缺口，含 SM120 塊縮放 MMA（#3685）

合於 11-07 18:59，+7075 至 -394、63 個檔案，是本期體量最大的一筆。新增麵包括：warp vote、match 與位搜尋，塊謂詞屏障，顯式寬度的載入與儲存及快取提示，NaN 傳播的 min/max，TMA 與 cluster 複製（multicast、store_cluster、gather4、scatter4），SM120 的塊縮放 MMA（mxf4nvf4）與配套的 NVFP4 GEMM 示例。同一筆還修了 warp specialization 的一個老問題：夾在 pipeline 之前的 T.fill 被搬進 producer/consumer 分支後，即使隔著迴圈或條件，也會在每輪迭代後重跑，覆蓋當輪 T.clear 的結果。

來源：https://github.com/tile-ai/tilelang/pull/3685

1.4 主線：CUDA 單次 kernel 啟動可命名，profiler 裡分得清階段（#3816）

合於 11-06 17:45。一個 PrimFunc 裡的多個 T.Kernel 原先共享自動生成的名字字首，profiler 裡分不清階段。新增可選 name= 引數，T.Kernel(grid, threads=128, name="compute_stats") 與 T.ClusterKernel 都支援，生成的裝置符號就是 compute_stats，不再附加 _kernel 字尾。名字經 tl.kernel_name 註解穿過 LowerOpaqueBlock，由 SplitHostDevice 生成裝置函式時消費；顯式名字校驗為非空 ASCII 識別符號，重名與宿主函式衝突走既有的全域性符號供給，未命名的啟動保持舊命名。文件同步覆蓋了命名、宿主呼叫目標、非法輸入、eager JIT、共享記憶體與 cluster 啟動。

來源：https://github.com/tile-ai/tilelang/pull/3816

1.5 主線：多源快取目錄，讀任意、只寫第一個（#3807）

合於 11-06 13:31，+593 至 -288、18 個檔案。TILELANG_CACHE_DIR 支援冒號分隔的多個目錄，例如 /cache/read/and/write:/cache/readonly/A:/cache/readonly/B，編譯產物可以從任意目錄命中，但只寫第一個。這對應叢集裡「共享只讀快取 + 本地可寫層」的常見形態，能讓一批構建共享同一份運算元快取。作者註明邊界：CuTeDSL 後端在只讀目錄上可能出問題。

來源：https://github.com/tile-ai/tilelang/pull/3807

1.6 昇騰：移除 Z3 排程全域性鎖，冷編譯最慢項 37.3 秒降到 25.6 秒（#3812）

合於 11-06 18:17。Ascend 的 Python 排程回撥把所有 Z3 solve 用一把全域性鎖序列化，儘管每次呼叫已經持有私有的 Z3 context。移除後獨立編譯執行緒可以並行排程：8 執行緒、每 kernel 8 個配置的冷編譯批處理裡，SwiGLU backward 從 33.1 秒降到 30.0 秒，MoE gate forward 從 37.3 秒降到 25.6 秒。驗證是 884 項既有 Ascend auto-schedule CPU 測試、64 個併發請求與序列結果一致，以及 16 個取樣的 SwiGLU backward 與 MoE gate 配置在改動前後生成完全相同的排程、原始碼與裝置 ELF。

來源：https://github.com/tile-ai/tilelang/pull/3812

1.7 昇騰：access_ptr 區域修復，跨行與轉置檢視不再丟 DMA 依賴（#3805）

合於 11-06 12:08。連續 SIMD 載入跨行、或使用轉置檢視時，access_ptr 重建的區域會丟失輸入 DMA 依賴，AutoSchedule 因此可以把 load 排到 copy 之前，InsertSync 也就不再插 MTE2 到 V 的同步。改法是複用保守的指標區域重建：跨行時帶上起始偏移，無法重建的佈局回退到整緩衝；保留簡單的一維正步長快路徑。迴歸覆蓋兩個跨行用例與一個轉置檢視，分別在有/無 AutoSchedule 下驗證「DMA → set/wait → load」順序與事件 ID 對齊；171 項相關 host 側 IR 測試透過，裝置執行未測試（作者寫明瞭這條邊界）。

來源：https://github.com/tile-ai/tilelang/pull/3805

1.8 示例：sm_12x 按可用動態共享記憶體選瓦片，RTX PRO 6000 全過（#3845）

合於 11-08 06:25。dim=128 的 block-causal varlen 用例原先固定 128x128 瓦片，前向需要 128 KiB、dK/dV 約 192 KiB，而 sm_86/89/120 的動態共享記憶體上限約 99 KiB，啟動直接報 Failed to set the allowed dynamic shared memory size。改為從 get_max_dynamic_shared_memory() 取 block_size：資料中心卡保持 128x128，小共享記憶體裝置用 64x128（約 96 KiB），並保持 block_size 能被 dllm_block=64 整除。RTX PRO 6000（sm_120）上 CUDA 與 CuTeDSL 各 209 passed、26 skipped、0 failed；H200 NVL（sm_90）上 128x128 兩例透過。作者稱這是 #3701 留下的最後一個失敗示例。

來源：https://github.com/tile-ai/tilelang/pull/3845

1.9 新 issue 群：錯誤結果仍是最重的一類，涉及 WS 迴圈攜帶、複製迴圈原子、無符號語義

視窗內主倉新開 29 條 issue，最重的是「算錯但不報錯」這一組。#3842：開啟 warp specialization 後，pipeline 兩輪之間對變數的更新只在 consumer 分支生效，producer 看不到，結果錯誤。#3870：被複制的並行迴圈裡，對 fragment 的原子操作與讀改寫會在每個副本上各做一次。#3871：tvm_ffi 後端呼叫結束後不恢復呼叫方當前裝置，呼叫方隨後在錯誤裝置上啟動。#3877 與 #3881：NVRTC 路徑下只有一個引數的 kernel 無法啟動；cython 路徑動態共享記憶體超過 48 KB 時在第二臺裝置上失敗。#3866：Metal 的 packed FP16 向量算術按整數位模式運算，#3884 已在審（改用 half2）。CuTeDSL 的無符號語義也連開三條：#3874 原子 max/min 按有符號比較、#3876 無符號原子比較、#3875 從無符號緩衝讀出的值應保持無符號。這批裡前兩條與上一視窗的 #3808、#3800 同型：編譯器不報錯，生成程式碼在特定組合下給出錯誤結果。

第一，自動化的閉環已經成形，但閉環的重心從「寫程式碼」移到了「定契約」。topa 的 15 筆沒有一行 kernel 程式碼，全是輪次規則、評審清單、PR 體格式與 worktree 清理；TileOPs 的 33 筆裡大部分是「按目標條改一個引數、給一組 A/B」；TileFoundry 的 5 筆則是在定義什麼叫「放置相等」「TMA 完成」「覆蓋前的讀」。三者疊起來是一條完整的流水線：夜間跑分發現差距，佇列分配運算元，agent 在 TileFoundry 的排程空間裡改，評審按清單核對數字，合入後自動結項。這條流水線的產出效率已經體現在數字上（72 小時 71 筆），但它對「契約寫得夠不夠清楚」極其敏感——今天 #2867 標註「低於目標條」仍被合入，#301 在排不出順序時選擇報錯而不是猜，都是契約在起作用的樣子。

第二，昇騰的瓶頸從「能不能編譯」變成「宣告與實現是否一致」。14 條 issue 裡沒有一條是「不支援某功能」，全是「宣告支援但實現走了另一條路」：HCU_MCPU_SET 有 gfx928 而 C++ 沒有分支（海光同理）、T.simd.vcvt 文件寫了 int32/int64 到 f16 而實現拒絕、annotate_unlimit_memory 的錯誤資訊讓使用者傳 "shared.ss" 而函式自己拒絕、gemm_blockscaled 的位置引數與公共簽名分叉。這類缺陷的共同修法不是加功能，而是把「宣告」與「實現」放在同一張表裡做生成式檢查——例如從 HCU_MCPU_SET 生成後端必須覆蓋的架構清單，從 intrinsic 登錄檔生成 dtype/位寬支援矩陣。在做到這一點之前，3060 項全過的測試報告只能說明「已測的組合沒問題」。

第三，CuTeDSL 正處在「功能覆蓋接近 CUDA、正確性邊界尚未收斂」的階段。#3685 一次補 63 個檔案、把 cluster TMA、SM120 塊縮放 MMA、Philox、warp vote 這些 CUDA 側早已有的能力補齊，說明功能面對齊已經接近完成；但同一視窗的缺陷全在邊界上：多流併發下的 grid barrier（#3868）、有符號整除（#3551）、無符號原子與無符號緩衝（#3874/#3875/#3876）。這些都不是「沒實現」，而是「實現了但語義與 CUDA 不一致」。對使用者的實際建議是：CuTeDSL 路徑適合用來跑示例與開發，生產 kernel 在換後端前應做一輪與 CUDA 後端的逐元素差分，尤其是涉及負數除法、無符號比較與多流併發的場景。

第四，效能最佳化的記錄方式在變。TileOPs 這批 PR 的特點是每筆都寫清楚「哪個 op、哪個 benchmark、結果是否達標、根因是什麼」：#2868 給出 900444 個 sector 對 501760 個寫入的具體數字，#2869 給出 16 個記憶體放置裡 12 個落後的分佈，#2855 給出 12 輪熱身、每輪 10 次呼叫的中位數並主動宣告「未控制執行順序效應」。這種寫法讓「沒達標」也能合入（#2867），因為讀者能判斷它是否值得。相比之下，只寫「提升 X%」的 PR 在評審時無法區分是 kernel 變快還是測量變了。

最後是 RISC-V 線。四源巡檢 72 小時無變化：kubuds/tilelang-riscv-kubuds 的兩個 kubuds- 分支、RuyiAI-Stack/tilelang-riscv 的 MLIR 路線、TongmingLAIC/tilelang-riscv 索引頁與 TongmingLAIC/tilelang-tpu 的 SOPHGO 分支都停在原引用。這與主線的節奏形成對比：GPU 側的 agent 化流水線已經把迭代壓到「天」，RISC-V 側仍是「周」級的人工推進。兩條線的差距不在工程量，而在有沒有一條能自動發現差距、自動驗證、自動排隊的迴路。
