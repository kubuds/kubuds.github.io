今日重點：TileFoundry 同日落地 Metal 目標與自動微分

11-18 一天裡 TileFoundry 合入兩筆平臺級改動。#354 新增 Apple Metal 目標，#355 新增自動微分。前者把編譯流程延伸到 Apple GPU，後者讓框架自己生成反向傳播。兩筆都不產出可執行的核心：Metal 只做到 TIR，自動微分只生成 HIR 模組。

Metal 側新增 metal.Target("apple.m2_pro.gpu")。拓撲為 threadgroup 到 thread。硬體引數寫在 TOML 裡，並附公開來源。能力表直接採用 27 個 MSL 原生函式名。

T.metal 下共九個指令運算元。矩陣類為 ldmatrix、stmatrix、matmul 與 mma。歸約與亂序類為 reduce、prefix、shuffle、shuffle_fill 與 ballot。一次呼叫覆蓋 G 個 SIMD group，quad group 用同一組運算元在寬度 4 的 mesh 上表達。

每個運算元一個檔案。typeinfer、access 與 evaluator 規則寫在同一檔案內，佈局用命名常量。MSL 不規定矩陣的 lane 對映，作者在 M2 Pro 上實測後寫入規格。HIR 經 hir_matches 匹配。fragment 運算元上的 MatMul 落到 matmul，Reshard 在記憶體與 fragment 之間落到 ldmatrix 與 stmatrix。該筆取代早先的 #294，後者因目標介面重組無法 rebase。

自動微分側新增 differentiate(module, wrt, recompute)。它返回 <Name>Forward 與 <Name>Backward 兩個模組。前向返回結果和一個 saved 元組。反向接收結果梯度與 saved，按 wrt 逐個返回梯度。

反向規則按運算元寫在各自檔案裡，經新增的 interfaces/autodiff 註冊。覆蓋範圍是內建 Qwen 模型的全部運算元類，另加 ReLU 與 Log。支援兄弟與子槽呼叫、元組引數、MeshRegion，以及迭代次數靜態可數的迴圈。

迴圈只堆疊每次迭代變化的值。只被歸納變數、捕獲與常量用到的量在反向重算，因此層迴圈不復制權重。梯度佈局沿用 DTensor。

來源：https://github.com/tile-ai/TileFoundry/pull/354。

今日重點：TileOPs 一天 23 筆合入，FP8 量化鏈補齊、兩條效能欠賬當日關閉

11-18 的 TileOPs 主分支落下 23 筆合入，從北京時間 10:17 持續到 21:50。主線是 FP8：逐 token 分組量化、短行 GEMM 流式、paged decode 重寫、WGMMA 原語化四筆同一天進主幹。

FP8QuantPerTokenGroupFwdOp 起 UE8M0 尺度（#3026）。輸出與 DeepSeek-V4-Flash 的 act_quant(x, 128, "ue8m0") 逐位一致，尺度用 float8_e8m0fnu 儲存。新增 inplace 偽量化，模型裡帶步長的 kv[..., :448] 不必先複製。

UE8M0 路徑用 bfloat16x2 做歸約與縮放，並去掉飽和 e4m3 轉換前的 clamp。對照實現是 vLLM 的 per_token_group_fp8_quant，DeepSeek 與 TileKernels 的數值在註釋裡給出。

FP8 paged GQA decode 核心被整體重寫（#2997）。每個 CTA 拿一個請求的打包行、一個 KV 頭與一段 key。每個 FP8 key/value tile 只解寬一次，TMA warp 負責拷頁。上限來自共享記憶體：H200 上 8 行 tile 可服務 44,287 個請求，64 行 tile 為 33,023 個。

短行 FP8 改走 64 行塊流式（#3010）。一個生產 warpgroup 透過深 TMA 環搬 b，一個消費 warpgroup 把每個 128 寬 K 步的 FP8 WGMMA 部分和加到 float32。

主分支原來把 8 或 16 行補成 64 或 128 行 tile。這樣 160 個 tile 落在 132 個 CTA 上，或走 split-K。實測只有 DRAM 峰值的 31% 到 52%。

同一批還有兩筆收尾。#3030 把 FP8 流每步的四個 k32 WGMMA 改用 TileLang 原語發出。dense_wgmma_helper.h 隨之刪除，只有該核心使用的 TrailingFence 模板引數一併去掉。#3029 修共享記憶體記賬：尺度緩衝原先按原始位元組相加，未計 1024 位元組對齊。m=16、n=163840、k=3584 的形狀因此在啟動時失敗。

兩條效能欠賬同日關閉。#3023 重寫 TopKSelect：行數少於 SM 數兩倍的呼叫走暫存器核心。它一次全域性讀一行，4096 桶直方圖定閾值；長行走 radix，一次 16 位元組裝四個 key。三條 decode 行從落後 vLLM 約 2 倍變成領先 1.22 到 1.34 倍，關閉 #3016。

#3022 讓 MLA cache 每行按 16 位元組向量拷，最多 1024 執行緒。主分支把複製交給佈局推斷，448 寬 latent 每執行緒變成 7 次 2 位元組標量訪問。這是 DeepSeek-V4-Flash decode 落後 vLLM 的直接原因。

來源：https://github.com/tile-ai/TileOPs/pull/3026。

一、核心專案進展

1.1 主倉 CPU 後端補兩個邏輯歸約的序列降載：any_of 與 all_of

#4389 給 CPU 後端補上 tl.any_of 與 tl.all_of 的專用降載。此前這兩個運算元無法走 CPU 常規管線。實現新增 LowerCPUAnyAll pass，插在 LowerTileOp 之前。降載為按行主序的序列掃描，並帶短路：any_of 命中真值即停，all_of 命中假值即停。

空歸約取標準單位元：any_of 為 false，all_of 為 true。數值元素按非零轉真值，浮點與 bfloat16 的 NaN 視為真。while 條件裡的歸約在每次條件判斷時重新初始化並重掃，語義與原先一致。該 pass 同時暴露給 CPU 的 Python 變換介面。

來源：https://github.com/tile-ai/tilelang/pull/4389。

1.2 topk 迴歸測試給 Z3 設資源上限，壓掉 CUDA CI 上的超時

#4407 處理 test_topk_candidate_overflow 在 CUDA CI 上的超時。原因是化簡階段發起了代價高昂的 Z3 查詢。修法是在該測試載入核心時設定 arith.z3_rlimit 為 100，保留原有其它 JIT 選項。改動只作用於這條迴歸測試。

作者在本地對 topk 的四個特化生成 TIR，確認設限後 Simplify 能完成。作者同時註明：本機沒有 CUDA 程式碼生成，也無可用的遠端 GPU。完整編譯耗時與 GPU 正確性均未驗證。

來源：https://github.com/tile-ai/tilelang/pull/4407。

1.3 昇騰自調優測試移除跨 NPU 探測，避免汙染後續用例

#4401 刪掉 set_autotune_inputs 測試裡的 other_npu 分支。該分支為判斷執行時是否支援裝置間輸入對齊，會執行一次跨 NPU 複製。在部分 Torch-NPU 與 CANN 組合上，這次複製會中止 NPU 上下文。

捕獲 RuntimeError 後跳過用例並不能恢復上下文。同一 pytest 程序裡後續無關用例會跟著失敗，故障表現因此依賴執行順序。刪掉後仍保留三類覆蓋：當前 NPU 上捕獲的輸入留在當前 NPU、CPU 上捕獲的輸入搬到基準裝置、傳入張量須與基準裝置一致。

來源：https://github.com/tile-ai/tilelang/pull/4401。

1.4 CUDA Tile IR 後端 RFC 重新提交：只轉換 Tile IR 能表達的部分

#4402 與 #4403 提交了 CUDA Tile IR 後端的 RFC，中英文各一份，放在 docs/compiler_internals/tileir/。目標是從 TileLang 程式生成 CUDA Tile IR，交給 tileiras 編譯與排程。佈局、流水、warp 特化與指令選擇都由 tileiras 決定，並按硬體代際最佳化。

後端只轉換 Tile IR 能正確表達的語義。轉換不了的語義直接報編譯錯誤並拒絕該程式，不追求與現有 CUDA 後端完全相容。作者給出的收益是：不改核心、不手寫架構相關排程，僅靠自動調優就能拿到不錯效能。

這版是對早先 #3247 的重做。評審指出舊實現 try-catch 過多、按見過的形式逐個降載、另建一套 IR，並用約 1.85 萬行 Python 寫 pass。新 RFC 針對這四點重新設計，PR 目前為草稿，討論放在 #4403。

來源：https://github.com/tile-ai/tilelang/issues/4403。

二、多後端適配（昇騰 / 海光 / 摩爾執行緒 / 沐曦 / Sunrise）

2.1 MLIR 昇騰 mlir-dialect 分支一天合入 tl.shl、tl.shr、tl.cast

MLIR 昇騰倉的合入落在 mlir-dialect 分支，不在 main。該分支頭在 11-18 從 06:23 推進到 08:47（UTC），一天合入三個 TLIR 運算元。

#211 加 tl.shl，降載到 hivm.hir.vshl，複用已有的 NpuirShl 助手。#212 加 tl.shr，只支援 i16、i32、i64，round 為布林屬性且預設 true。該筆如實寫明一處已知不匹配：rhs 按張量運算元建模，而 HIVM 的 vshr 有 ScalarOnlyHWTrait<1> 約束。根因在 NpuirShr 與 npuir_shr 的構造器不接受標量，留作後續。

#214 加 tl.cast，round_mode 限定在 round、rint、floor、ceil、trunc、odd 六種。該筆還改了一處方言級設定：TL_Dialect 增加 usePropertiesForAttributes = 0。原因是 tl.cast 是該方言第一個帶非運算元屬性的運算元，走 ODS 預設的 Properties 生成會產出損壞的 CastOp。三筆都帶 FileCheck 測試，測試取自真實捕獲的輸出。

來源：https://github.com/tile-ai/tilelang-mlir-ascend/pull/214。

2.2 MLIR 昇騰在審：tl.vrelu、tl.abs、tl.or、tl.xor 與 RoPE 核心

在審的 TLIR 運算元還有四條。tl.vrelu 見 #261，tl.abs 見 #238，後者降載到 hivm.hir.vabs。tl.or 見 #225，tl.xor 見 #228。四筆都按「方言運算元 + TIR 降載 + HIVM 轉換」的同一套流程推進。

#263 走另一條路，直接加旋轉位置編碼核心，不再補單個運算元。另有 #260 把 harness 裡的 ascend-mfu 技能換成 ascend-roofline。新技能用一套 Cube/Vector 模型給出峰值、計數、roofline、MFU、BWU 與硬體參考。其 FMA 探針在該裝置與該構建下標定到 26.3 TFLOPS，為標稱 30 TFLOPS 的 88%。

來源：https://github.com/tile-ai/tilelang-mlir-ascend/pull/263。

2.3 海光單筆彙總十二項修正，覆蓋 intrinsic、精度與整數向量

海光倉視窗內只有一筆合入（#27），內容卻覆蓋十二個方向。intrinsic 側修 hexp 呼叫歧義、cos 與 sin 的分派。精度側修 fp64 截斷失敗與 __builtin_bit_cast 尺寸不等。向量程式碼生成側修 shuffle 降載，並開啟整波 shuffle 歸約。

新增能力包括：用 hipRAND 支撐 rng 操作、緩衝區載入重基、cache_warmup intrinsic。另有若干處收尾：8 位整數向量廣播、執行期迭代次數的流水 epilogue 展開、shuffle 掩碼防護、FP4 程式碼生成的順序修正。CI 側釘住 NumPy ABI。提交署名同時出現兩位海光工程師。

來源：https://github.com/tile-ai/tilelang-hygon/pull/27。

2.4 Sunrise 釋出 0.1.15+sunrise.1.2.1；沐曦在備 v0.1.12+musa.5

Sunrise 倉合入 #11，版本推到 0.1.15+sunrise.1.2.1。該筆同步更新 TileLang、TileOPs 與 TileKernels 三個上游源，並更新 TANG 與 PTPU 整合。標籤頁同日出現該版本，前一版為 0.1.15+sunrise.1.2.0。

沐曦倉視窗內 main 無提交。動靜在釋出準備上：release/v0.1.12-musa.5-source 分支存在，開放的 #13 用於釋出 v0.1.12+musa.5 原始碼與 MUSA 文件。摩爾執行緒側主倉無新提交，視窗內只有評論與 PR 更新。

來源：https://github.com/tile-ai/tilelang-sunrise/pull/11。

三、生態與採用方（TileOPs 目標清單 / TileKernels / topa / 文件站）

3.1 mHC 兩運算元退場列為公開 API 破壞，HyperConnection 三運算元接棒在審

#3021 刪除 MHCPreFwdOp 與 MHCPostFwdOp，連同核心、manifest 條目、workload、基準與測試一起移除，按 #2796 的計劃執行。DeepSeek-V4-Flash 與 GLM-5.3-Flash 改用 HyperConnection 的 pre、post、head 三個運算元。mhc.expansion 這個 manifest 原語一併刪除，只有被刪運算元用到它。

該筆在 scripts/ci/api_compat_allow.txt 裡登記為經評審的公開 API 破壞。這是運算元庫首次以清單方式管理介面刪除，被刪的介面不再回填。

接棒的三個新提案已在審：#3032 加 pre、#3035 加 post、#3039 加 head。另有 #3036 為 FusedTopKFwdOp 加 DeepSeek-V4-Flash 的 sqrt-softplus 與雜湊路由。#3038 為 DSADenseFwdOp 加 attention sink 與僅索引選擇。這一組改動指向同一件事：按 DeepSeek-V4 的實際結構重排序列建模與注意力介面。

來源：https://github.com/tile-ai/TileOPs/pull/3021。

3.2 七條效能目標 issue 把「距最快庫」寫成可驗收清單

視窗內新開七條效能目標 issue，每條都帶硬體、形狀與目標。#3018 盯 GQA 變長在頭維 72 的視覺行上落後 FlashAttention 3 的差距。#3019 盯 MLA cache 寫入落後 vLLM 的差距。這兩條的對應修復分別是 #3023 與 #3022，其中 #3022 當日關閉了 #3019。

#3037 給出 DSADense 的完整對照表：H200 跑 1500 MHz，bf16 稠密峰值約 811 TFLOPS。CSA 各行達到峰值約 58%，原因是每對的 softmax 與下一對的 key 收集夾在兩次矩陣乘之間。HCA 的 4k 行付了 64 key 塊的代價，160 個 key 按 192 個算。

#3031 盯 HyperConnection pre 在 decode 與中等序列上落後 TileKernels 的差距。#3034 盯 GatedPoolCompress 的 decode 行，目標是在該形狀上達到 SOTA。

來源：https://github.com/tile-ai/TileOPs/issues/3037。

3.3 TileKernels 對照計時提案：跑測映象仍釘在 tilelang 0.1.12

#3028 提出把 DeepSeek 的 TileKernels 加進基準對照，讓 DeepSeek-V4 的行直接用 DeepSeek 自家核心計時。障礙在版本：TileKernels 要求 tilelang 不低於 0.1.15，而跑測映象釘在 0.1.12。當前沒有任何基準能匯入它。

提案給出三條對應關係。FP4QuantPerGroupFwdOp 與 FP8QuantPerTokenGroupFwdOp 對 per_token_cast。SiLUAndMulFwdOp 對 quant.swiglu_forward。驗收條件是這些基準在 CI 裡真正計時到 TileKernels，並由夜間記錄為對照。這解釋了為何同日兩筆量化提案的說明裡，TileKernels 的數值只能在註釋中給出。

來源：https://github.com/tile-ai/TileOPs/issues/3028。

3.4 topa 一條命令跑完一輪評審，GPU 只在計時期間獨佔

topa 合入 #41 與 #43，把評審做成可迴圈的輪次。#41 讓每次 PR 變更觸發一輪新嘗試：新的 head 走完整評審，其餘只做複查。只有 PR 未變且仍開放時才釋出結果。GPU 側新增按卡加鎖的 topa-bench，只在計時期間獨佔一張卡，其餘時間讓給其它輪次。

#43 把三步流程壓成一條 topa review <PR>。評審意見固定為三條單句要點：問題、復現、修法。同一 PR 的評審目錄保留 worktree 與 posted.json，第二次評審只在本地落後於 GitHub 時才取回。評審輪次的無變化等待從 60 分鐘放寬到 10 小時。

兩筆之外，topa 在視窗內新開 10 條 issue（#35 至 #46）。它們都是帶 fix(...) 標題的可執行工作項，方向集中在 roofline 定價。包括按 CTA 的波次算 makespan、按寫入行數為 scatter 定價、把常駐 CTA 計入網格。這些是流水線給自己排的下一批任務。

來源：https://github.com/tile-ai/topa/pull/41。
