今日重點

這一天最密集的產出來自運算元庫而不是編譯器。TileOPs 在 21:06 到 22:46 的一個多小時裡連續合入六筆，加上 14:01 與 21:31 的兩筆，一天九筆，全部是 perf、fix、ci 標籤。三件事同時推進：一是廣播運算元就地讀，lerp、where、clamp、masked_fill 五類運算元不再把 stride 0 的廣播張量先展開成輸出形狀，實測廣播行耗時降到主線的 0.13 到 0.44 倍（#2832）；二是單波次啟動，一元逐元素在「體內最多兩條便宜指令、讀寫總量不超過 L2 的四分之三」時縮成一個 256 執行緒的波次，並且順手修正了 ReLU 對 NaN 返回 0 的老問題（#2829）；三是瓦片選擇器，給小 M 的 NT GEMM 造了一個寬度能填滿一波的原生寬度瓦片，decode-down 從落後變成領先最快對比項 3%（#2834）。三件事的共同點不是「更快」，而是每筆都帶著可復現的 A/B 表、都標出自己仍然落後的那一行。

第二條是可信度問題，而且橫跨兩個倉。主倉新開 issue #3808 報告：從 0.1.12 到 0.1.15，條件相關的標量化之後，共享記憶體 epilogue 少了一道 __syncthreads()，編譯器不報錯、生成的 CUDA 是錯的；報告者給了完整復現指令碼與四個版本號，屬於「靜默錯程式碼」而非效能退化。同一視窗裡 #3800 報的是另一種靜默錯：不開 warp specialization 時，T.Pipelined 會在 T.tcgen05_gemm 的 barrier 等待之前過載下一 stage，於是 MMA 讀的 operand 已經被覆蓋。這兩條與主倉當天合入的 #3759 正好構成一組對照——#3759 修的是「標量條件裡的 int64 cast 把資料向量寬度從 16 lane 壓到 4 lane」，同一個標量化/向量化交界處，一邊在修寬度，一邊在漏同步。

第三條在昇騰側。tilelang-ascend 合入 #1954，把 T.tile.bitwise_rshift 在 int64/uint64 上的編譯期段錯誤改成顯式 ValueError，只允許 int16/uint16/int32/uint32；這不是新增 64 位右移支援，而是把「編譯器崩掉」變成「編譯器說不」。同一倉當天新開兩條同題 issue（#1991、#1992），報告在 910_9362 / CANN 9.0.0、threads=2（C:V=1:2）下，AscendVidReduction 把 kernel 內所有 UB 分配無條件減半，連注入的 tmp workspace 也減半，結果是 sin/cos 作用在間接定址的 skip-set buffer 上時 3978/4096（97.1%）個元素算錯，sigmoid/round 則違反 AscendC 的 calCount <= tmp 契約、越界寫落在佈局後方的 scratch 上。與之並置的是同日 #1988 的每日測試報告：3030 項全過、透過率 100%。這兩組數字放在一起說明一件事——現有測試覆蓋不到「threads=2 加間接定址」這種組合，透過率不能當作正確性的替代指標。

第四條是生態面的動靜。海光倉從「功能分支上攢了四筆、未開 PR」變成正式進入評審：feat/hcu-scaled-cast 分支當天又落三筆 LDS 相位修（預設 swizzle 適配 64 bank、MN 切片消費端恢復 swizzle 規劃、K 分割槽的佈局感知讀），並開出 #33（scaled cast）與 #34（reduction 的 lane swap 與約束傳播）兩個 PR。摩爾執行緒結束了自 09-30 以來的完全靜默，主分支落了一筆 README 的安裝與運算元開發說明更新。加上 TileSight 倉庫出現首個 PR（修正 H20 的 WGMMA 能力宣告）與主倉 #3803 的 TIRx 遷移草案，可以看到組織層面的三條線在同時展開：國產後端從自研分支進入公共評審、效能建模從論文走向倉庫、編譯器底座準備換掉 vendored TVM。

一、核心專案進展

1.1 主線：TF32 轉換支援 round-to-nearest-even，SM90 與 SM100 分開診斷（#3714）

合於 12:09。此前 T.cast 到 tfloat32 只有預設的 TF32 就近舍入路徑，想要 ties-to-even 得自己匯入 CUDA helper。這一筆給 round="rn" 加了原生 lowering：非飽和形式發 cvt.rn.tf32.f32，飽和形式發 cvt.rn.satfinite.tf32.f32，並且繞開預設的 TF32 舍入建構函式、直接保留轉換後的位模式。標量與向量兩條路徑都覆蓋，TF32 的 lane 訪問走打包載體。架構診斷按形式分開：非飽和形式要求 SM90 以上，飽和形式要求 SM100 以上，不滿足就在編譯期報錯；沒有顯式指定 rounding 的 cast 行為不變。報告者是關掉 #3713 的需求方，屬於「使用者不必再自帶 helper」這類介面收斂。

來源：https://github.com/tile-ai/tilelang/pull/3714

1.2 主線：host-mapped 緩衝可顯式註解，CPU 張量不再被裝置檢查拒絕（#3802）

當天建立、當天合入（12:08 提交、16:02 合入）。CUDA kernel 可以直接訪問對映進 GPU 地址空間的 host 記憶體，但 TileLang 原有的裝置檢查假定張量引數都住在目標裝置上，於是這類 CPU 張量在啟動前就被拒。新增的 T.annotate_host_mapped_buffers(*buffers) 把被註解引數的索引寫進 PrimFunc 的 tl.host_mapped_params 屬性，支援多緩衝、合併重複宣告，並且能穿過 IR 序列化與 kernel 快取恢復。Cython 與 TVM-FFI 兩個 launcher 對被註解引數接受 CPU 張量，其餘 dtype、形狀、秩、步長檢查照舊；裝置側引數的檢查仍對齊當前執行裝置，host 張量則不提供 CUDA 裝置號。執行時新增一個原生 helper，用 cuMemHostGetFlags 校驗註冊狀態、用 cuMemHostGetDevicePointer 解析裝置可見地址，普通可分頁記憶體仍會被拒。

來源：https://github.com/tile-ai/tilelang/pull/3802

1.3 主線：標量條件裡的 cast 不再限制資料向量寬度（#3759）

合於 19:27，標籤裡帶 ascend。起因是 #3734 在 DecoupleTypeCast 之後正確地收緊了資料 cast 的寬度限制，但把條件裡的 cast 也算進去了：一段 T.assume(n % 16 == 0) 保護的 BF16 複製，因為條件裡有 T.Cast("int64", ...)，在 b5cb02633 上從 16 lane 被壓到 4 lane，即使條件在 16 個 lane 上一致。修法是把 planner 已有的條件一致性分析複用起來，把 cast 寬度豁免從緩衝索引擴充套件到條件：if 語句、tirx.if_then_else 與標量謂詞的 Select 的條件單獨訪問，分支仍然受限；在 lane 級向量謂詞的目標上仍保留條件 cast 的約束。stochastic rounding 的 rbits 分組在跳過寬度約束時也被保留。這一筆與視窗內的兩個新 issue 落在同一片區域，說明標量化與向量化的交界是當前缺陷的高發帶。

來源：https://github.com/tile-ai/tilelang/pull/3759

1.4 主線：Z3 的 rlimit 可按 kernel 配置，預設仍為十萬（#3752，依賴 tile-ai/tvm #91）

合於 23:05，前置是 fork 裡的 tvm #91（23:03 合入）。改動把 Z3 求解器的 rlimit 從寫死的 100,000 變成可按 kernel 定製：不配置時保持舊預設值。作者的表述很直接——「這間接修掉了很多與 Z3 證明器相關的問題」。這類改動的意義在於把「證明超預算」從不可調的環境行為變成可調的編譯引數，與昨天昇騰側收緊 AutoSchedule 週期下界（把 Z3 求解時間降 10.04%）是同一方向的兩種做法：一個改搜尋起點，一個改搜尋預算。

來源：https://github.com/tile-ai/tilelang/pull/3752、https://github.com/tile-ai/tvm/pull/91

1.5 主線：巢狀 T.macro 複用轉換模板，前端重複編譯開銷收斂（#3760）

合於 23:38。問題在外層函式每次執行時，巢狀的 T.macro 定義都會重新做原始碼解析、AST 重寫與 Python 編譯，即使 kernel 本身已經命中快取。改法是引入一個有界的程序內快取，只存與上下文無關的轉換結果（未繫結的程式碼與重寫後的原始碼），每個宏例項再繫結當前的 globals 與閉包值；依賴上下文的轉換走原路徑，被包裝過的函式繞開快取。宏呼叫點與 kernel 快取都不變。迴歸覆蓋新閉包、globals、捕獲的緩衝、註解、上下文相關回退與閉包生命週期；CPU 側前端檢查透過，GPU 執行本地未驗證——作者把這條邊界寫清楚了。

來源：https://github.com/tile-ai/tilelang/pull/3760

1.6 新 issue：條件標量化後缺 __syncthreads，0.1.12 至 0.1.15 靜默生成錯誤 CUDA（#3808）

21:14 開出，是本視窗最重的缺陷報告。復現是一個共享記憶體 epilogue 的 kernel：0.1.12、0.1.13、0.1.14、0.1.15 四個版本都會在條件相關的標量化之後丟掉一道 __syncthreads()，編譯器不報任何錯，生成的 CUDA 直接算錯。報告者給了完整可執行的 Python 復現指令碼與環境（Python 3.14.9、CUDA 2.15.0+cu134）。這類問題的破壞力在於它跨了四個釋出版本且無任何告警——凡是依賴共享記憶體在階段之間做交接的 kernel 都可能踩到，而使用者側看到的只是「結果不對」。

來源：https://github.com/tile-ai/tilelang/issues/3808

1.7 新 issue：無 warp specialization 時 T.Pipelined 在 tcgen05 等待前過載 stage（#3800）

08:44 開出。觸發條件是關掉 warp specialization（tl.disable_warp_specialized=True）後跑 T.Pipelined 加 T.tcgen05_gemm 的迴圈：stage 在 mbarrier_wait_parity 之前就被下一輪複製覆蓋，MMA 讀到的是被改寫的 operand。報告者把 lowering 出來的 kernel 原始碼貼了出來，指認 As 的寫入與 tcgen05mma_ss 的讀之間缺少順序約束。與 #3808 同屬「生成的程式碼看起來沒問題、實際不成立」這一類，區別在於這條發生在 Blackwell 的 tensor memory 路徑上。

來源：https://github.com/tile-ai/tilelang/issues/3800

1.8 在審：遷到原生 Apache TIRx 的完整遷移草案（#3803）；共享轉置改走 ldmatrix/stmatrix（#3809）

#3803 是本期最有分量的在審項：把 vendored 的 TVM 編譯器換成獨立的 Apache TIRx，前端、IR 變換、程式碼生成、JIT 適配與打包全部遷到原生物件模型，並 pin 了 apache/tvm-tirx 的 7e49a148 與 apache/tvm-ffi 的 3e906bc6 兩個上游提交，依賴樹保持乾淨上游、不注入補丁。作者把它標成 draft，本身就是一次「底座換代」的公開準備。

#3809（01:27 提交）處理另一件具體的事：T.transpose 在兩個共享緩衝之間一直走通用 SIMT 迴圈，8 位與 16 位瓦片用不上共享記憶體頻寬，examples/deepseek_v32 裡的 FP8 稀疏 MLA 只能手寫 16x16 暫存器暫存來繞開；同時 T.Pipelined 給源區加了一維 stage 軸後，秩不匹配會讓 MakeIndices 直接失敗。改法是在支援 stmatrix 的目標（SM90 及以上、排除 CuTeDSL）先試 warp-matrix lowering：16 位瓦片每個 8x8 塊用一次 ldmatrix 加一次 stmatrix.trans，8 位瓦片按 16x16 位元組塊用兩次 ldmatrix.trans 加 __byte_perm 選擇拼出四行，其餘區域回退到原 SIMT 路徑。

來源：https://github.com/tile-ai/tilelang/pull/3803、https://github.com/tile-ai/tilelang/pull/3809

二、多後端適配

2.1 昇騰：bitwise_rshift 的 64 位 dtype 改為顯式報錯，不再段錯誤（#1954）

合於 16:36（ascendc_pto 分支）。A2/A3 上透過公開 API T.tile.bitwise_rshift 傳 int64/uint64 運算元時，編譯器會在 OptimizeForTarget 階段直接段錯誤。修法是在構造 intrinsic 之前檢查 dst 與 src0 的 dtype，只允許 int16/uint16/int32/uint32，其餘拋帶實際 dtype 與支援列表的 ValueError；位移量 scalarValue 不限表示式 dtype；Buffer 與 BufferRegion 統一走 _underlying_buffer()。新增直接 API 診斷測試與子程序崩潰迴歸測試。作者明確寫了邊界：本次不新增 64 位右移支援，也不改直接構造底層 intrinsic 的路徑。關聯 #1720。

來源：https://github.com/tile-ai/tilelang-ascend/pull/1954

2.2 昇騰：A2/A3 效能技能對齊 Ascend950 工作流（#1932）

15:36 合入，純技能與流程重構：把 A2/A3 的效能調優技能與 A5（Ascend950）工作流結構對齊並統一，新增晶片型別識別與晶片資訊檢索兩項技能。單看沒有功能價值，但它意味著效能調優的「操作手冊」開始按晶片代際分叉——同一套 skill 要能識別自己跑在哪一代上，否則調優建議會跨代誤用。

來源：https://github.com/tile-ai/tilelang-ascend/pull/1932

2.3 昇騰：threads=2 下 tmp workspace 被無條件減半，sin/cos 在間接定址 tile 上 97.1% 元素算錯（#1991 / #1992）

五、趨勢觀察

第一，運算元庫的競爭點已經從「運算元數量」徹底轉到「選擇器與準備成本」。今天 TileOPs 九筆裡，真正改 GPU kernel 的只有 #2832（廣播就地讀）與 #2834（原生寬度瓦片），#2835 省的是呼叫準備（4.33% 到 6.17%，生成原始碼不變），#2836 改的是一個擬合因子，regret 從 0.89% 降到 0.06%。這說明效能差距的剩餘空間主要不在「怎麼算」，而在「選哪個瓦片、少做哪些準備工作」。這條路走到頭會得到一個用標定契約描述的代價模型，而不是一堆手調引數——今天 #2836 的「單獨擬合、只動一個常數」正是這個形態的雛形。

第二，編譯器側當前的主要缺陷型別是「靜默生成錯程式碼」，而不是編譯失敗或效能不足。#3808 跨 0.1.12 到 0.1.15 四個版本少一道 __syncthreads()，#3800 在 Blackwell 路徑上讓 MMA 讀到被覆蓋的 operand，#1991/#1992 在昇騰 threads=2 下讓 sin/cos 算錯 97.1% 的元素——三條都不報錯、都能透過常規測試、都要靠人寫出針對性的復現才能抓到。這類缺陷對使用者的傷害最大，因為它把「編譯器對不對」這個前提變成了需要驗證的假設。與之對應的工程動作應當是擴大形狀組合的差分測試（對照組用 reference 實現逐元素比），而不是繼續加單元測試數量。

第三，昇騰側的節奏從「架構改動後清迴歸」轉向「清正確性邊界」。#3512 那類結構性改動帶來的四類迴歸在上一個視窗剛清完，本視窗的兩筆合入（段錯誤改報錯、效能技能分代）和兩條新 issue（tmp workspace 減半、calCount <= tmp 違約）都屬於邊界收斂。值得注意的是 #1991 報告者是 #1897 的 review 方，而 #1897 的修法只覆蓋了 count 側——同一處佈局邏輯的另一個側面在兩週後才被指出，說明昇騰後端的佈局不變數還沒有形成可檢查的書面契約。

第四，國產後端的「公共化」在提速。海光從自研分支走到兩個正式 PR，摩爾執行緒恢復文件維護，mlir-ascend 用三個小 PR 把算術運算元一個個搬進 TLIR 方言。三條線的共同點是都不再等「一次性合入一個大後端」，而是把可評審的最小單元推到公共倉庫。這對上游是好事：評審者能早就佈局與 lowering 的設計提意見，而不是在三萬行一次性合入時才看。

最後一條風險面：主倉 #3803 的 TIRx 遷移如果推進，3rdparty/tvm 的 vendored 結構會被替換成兩個 pin 的上游提交，屆時所有依賴 TVM 內部 API 的後端（昇騰、海光、mlir-ascend 的膠水層）都要跟著改。草案裡明確寫了「不注入依賴補丁」，這既是承諾也是約束——今天 mlir-ascend 把 BishengIR 介面卡搬進 contrib、昇騰把效能技能按晶片代際分叉，都可以看作是為這類底座切換預留的可替換面。
