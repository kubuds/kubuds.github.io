一、核心專案進展

1.1 主倉：向量化分析納入非零迴圈下界（#3579）

合於 10-21 00:27，10 檔案 +818/-198，承接 #2819 的 guard 修復，同時關掉 #2669、#2616 兩個問題。原實現用 f(i) 與 f(floor(i / W) * W) 比較來判斷表示式在每個向量組內是否同值，這隱含假設迴圈從 0 起；迴圈下界非零時，unit-step 向量化會把不同 lane 的地址算成同一組，廣播裝載與整組共享條件的證明隨之失效。新的判定把迴圈最小值納入分析，並在搬運混合精度轉換時保留巢狀 guard。屬會靜默改變數值結果的編譯器缺陷。

來源：https://github.com/tile-ai/tilelang/pull/3579

1.2 主倉：共享記憶體跨執行緒 WAW 檢測（#2821）

合於 10-20 23:41，3 檔案 +153/-19，修 #2698。共享記憶體上 S[tx] 與 S[tx + 10] 對單執行緒是兩個地址，但不同執行緒的寫可以重疊；原 WAW 檢查對兩次訪問複用同一個執行緒變數，因此漏判、漏插屏障。修法是同迭代 WAW 用兩個不同執行緒例項，並重新命名各自的 Bind 定義，複用既有 RAW/WAR 模型，迴圈攜帶的 WAW 維持原處理。測試同時覆蓋”該插”與”不該插”兩種情形，含 guarded 寫、Bind 派生索引、不相交分割槽與 threadIdx.y/z 置換，執行緒同步與 issue 兩套用例 95 項透過。

來源：https://github.com/tile-ai/tilelang/pull/2821

1.3 主倉：不支援的 MMA tile 要求顯式 K 填充（#2818）

合於 10-20 16:41，5 檔案 +57/-14，修 #2715。通用 MMA emitter 可能在構造運算元佈局之前悄悄縮小 K 原子，FP16 K=8 會算出錯誤結果；K=20、K=28 這類不規則尺寸則在共享記憶體佈局推斷階段直接失敗且提示不明。現在在 emitter 初始化時按架構固定的 K 原子校驗 tile 的 K，不整除即拋 ValueError，帶上輸入 dtype、所需整除關係與建議的填充值（如 SM80 上 FP16 K=20 報原子 16、建議補到 K=32 並零填多餘元素）。

來源：https://github.com/tile-ai/tilelang/pull/2818

1.4 主倉：fragment reduce 支援保留維度目標（#2815）

合於 10-20 16:35，8 檔案 +343/-63，修 #2530。T.reduce_sum 等把 (64, 64) 沿 dim=1 歸約到 (64, 1) 時編譯期崩潰（Check failed: vars.size() == InputDim() (2 vs. 1)）。而 reduce_op.py 的文件契約明確同時接受 [X, Y] 與 [X, 1, Y] 兩種輸出形狀並已構造對應期望形狀，因此這是後端缺口而非誤用。修復同時教通兩條 lowering 路徑，並保留無保留維目標的原行為。

來源：https://github.com/tile-ai/tilelang/pull/2815

1.5 主倉：TIR 謂詞隨整數位寬提升同步改寫（#3550）

合於 10-20 09:59，4 檔案 +950/-27。整數索引被提升到更寬位寬後，控制緩衝訪問的邊界檢查仍按舊位寬計算，理論上可放過越界訪問。新增 IndexPredicateRewriter，在 ConfigIndexBitwidth 與 FlattenBuffer 中記錄每次訪問的提升資訊，訪問語句處理完後再重寫相關 guard；匹配限定在等價的加法與乘法形式上，保留無關條件、資料值表示式與定寬邊界。新增索引提升、guard 改寫、訪問作用域、向量端點與衝突提升五類測試。

來源：https://github.com/tile-ai/tilelang/pull/3550

1.6 主倉：CuTeDSL scan 補參與執行緒偏移（#3576）

合於 10-20 12:49，2 檔案 +30/-6。共享記憶體 scan lowering 在 #3536 裡引入了參與執行緒偏移，但 CuTeDSL 側的 helper 仍按舊構造引數生成呼叫，tl.CumSum1D(32, False, 0).run(...) 直接報構造引數錯誤；同批失效的 codegen 斷言也是 #2815 兩次 CUDA CI 失敗的來源。修法是為一維、二維 cumsum/cummax helper 增加可選 thread_offset（預設 0 保持相容），選參與 lane 與 warp 前先減去偏移，並給 CUDA 專屬測試打上 requires_cuda。

來源：https://github.com/tile-ai/tilelang/pull/3576

1.7 主倉 CI：效能迴歸任務鎖定 H100（#3569）

合於 10-20 16:00，1 檔案 +15/-1。PR 迴歸機器人逐 kernel 比對延遲與基線，數字只在基線採集的同型號卡上有意義。組織正在引入自託管 H20 容量機型做常規正確性 CI，其標籤集與既有的 [self-hosted, nvidia] 重合，若不區分會靜默接走基準任務：H20 的 FP16 稠密算力約 148 TFLOPS，對 H100 的約 990 TFLOPS 差約七倍，FP64 通路也被大幅裁剪，每個基準都會報出並不存在的迴歸。現要求 pr-regression 任務必須帶 h100 標籤，並在開工前校驗分配到的卡確實是 H100，標籤寫錯即快速失敗而非釋出誤導數字。

來源：https://github.com/tile-ai/tilelang/pull/3569

二、多後端適配（昇騰 / 沐曦 / 海光 / 摩爾執行緒）

2.1 昇騰主倉：L0 區域性複製支援顯式 pitch（#3511）

合於 10-20 14:16，24 檔案 +1458/-187，是本視窗昇騰方向最大的一筆。此前一個 GEMM tile 只能由單次 L1→L0A/L0B 複製填充，非零目標原點被拒絕，每次複製又從自己的區域推緊湊 pitch，因此分開搬的兩半拼不成目標整塊；MajorK/MajorMN 轉置裝載也受限。新增 Ascend 專屬引數 T.copy(..., l0_pitch=...)，按 fractal 塊指定 L0 pitch，由呼叫方給出消費方 GEMM 的緊湊 pitch（含動態尾塊），省略該引數則維持緊湊區域的原行為。示例中 64 行 A tile 的兩半均寫 l0_pitch=4。同步處理對齊後的目標偏移 lowering、物理邊界與轉置組校驗、分配與緩衝版本間距。

來源：https://github.com/tile-ai/tilelang/pull/3511

2.2 昇騰主倉 CI：單 check 內拆分構建與測試（#3564）

合於 10-20 12:06，1 檔案 +61/-9。把 Ascend 的構建與測試結果收進同一個 Test for Ascend PR 檢查，用分步呈現失敗階段，並在 workflow summary 裡列出各階段結論。CANN 環境只裝配一次、構建一次，AscendC 示例、PTO 示例與 Ascend 單測作為同一 job 的三個步驟分別執行；構建成功且工作流未被取消時，某套件失敗後仍繼續跑其餘套件，最終整體仍判失敗。CANN 變數經 GITHUB_ENV 傳遞。

來源：https://github.com/tile-ai/tilelang/pull/3564

2.3 昇騰倉：DSA 稀疏微調反向運算元 indexer_bwd（#1887）

合於 10-20 15:26，2 檔案 +1294。為昇騰 NPU 增加 indexer_bwd，服務 DSA 稀疏微調，同時支援 AscendC 與 PTO 兩個後端。運算元計算 lightning-indexer KL 微調損失對 dIndexQ、dWeights、dIndexK 的梯度，支援變長打包序列。實現分三檔：持續化 GEMM 的快速 kernel 面向連續與共享行索引布局，帶流水與更少搬運；通用 kernel 支援任意索引布局，含 -1 非法索引的梯度累加；另設 cast kernel 處理精度轉換。

來源：https://github.com/tile-ai/tilelang-ascend/pull/1887

2.4 昇騰倉：SiTU-GLU 反向運算元（#1877）

合於 10-20 15:22，5 檔案 +854。語義對齊 CANN ops-nn 的 aclnnSituGluGrad，用於 Kimi K3 Stable LatentMoE 的門控啟用反向：t = tanh(gate / beta)、s = sigmoid(gate)、situ_a = beta * t * s，上游分支按 linear_beta 是否為正走 tanh 或直通，輸出 grad_gate 與 grad_up。精度基準是獨立實現的 fp64 PyTorch 參考，並在 910B3 上與官方 aclnn 交叉校驗，最大相對誤差約 3e-3，符合 bf16 舍入預期。

來源：https://github.com/tile-ai/tilelang-ascend/pull/1877

2.5 昇騰倉：cann-bench 補 LSTM 與 GRU（#1892 / #1902）

兩筆同日合入，分別 +2304 與 +2267。LSTM 覆蓋 i/f/g/o 四門與 cell state 時序遞迴，支援多層堆疊（numLayers ≤ 8）、雙向、batchFirst 佈局、投影降維（projSize > 0，LSTMP）與可選 bias，權重按”每層每方向一個 tensor”的 TensorList 傳入，輸出 (y, hn, cn)，實現為 12 個 @tilelang.jit kernel；主力走融合 seq 路徑，每（層、方向）一次 launch，核內按 T.serial(S) 逐時間步完成雙 GEMM、bias 廣播、門控與狀態更新，與遞迴無關的 x 側門控貢獻由獨立 xgemm 全時間步並行預計算。GRU 為 8 個 kernel，z/r/n 三門合一 GEMM 在 Cube、門控與狀態更新在 Vector，跨核資料經 GM workspace 中轉，並手動關掉 AUTO_SYNC——按提交說明，自動模式每時間步約產生 58 個 PipeBarrier。

來源：https://github.com/tile-ai/tilelang-ascend/pull/1892、https://github.com/tile-ai/tilelang-ascend/pull/1902

2.6 昇騰倉：CrossEntropy 基準中文版（#1801）

合於 10-20 15:26，2 檔案 +91。為 #1567 合入的 CrossEntropy benchmark 文件補中文版，參照 FA（bench_mark.md / bench_mark_zh.md）與 SFA（README.md / README_zh.md）的 en/zh 成對慣例：在 examples/cross_entropy_loss/ 下新增 benchmark_summary_zh.md，完整翻譯最佳化路徑八步、內部效能對比、CANN 對比、已知限制與測試覆蓋，英文版頂部加語言切換連結。純文件改動。

來源：https://github.com/tile-ai/tilelang-ascend/pull/1801

2.7 昇騰在審：PTO 向量化框架、tvm_ffi 後端與 DeepGEMM 對齊

三條主線同時進審。#3512（50 檔案 +21022/-72）讓使用者在 T.SimdVF(lanes=L) 裡寫標量並行的 T.Parallel 程式（逐元素、控制流、歸約），由編譯器向量化成 PTO VMI 指令、經 PTOAS 編譯後在 Ascend 950 上執行，完整能力分多筆 PR 落地，本筆是流水線框架與逐元素支援的里程碑。#3516（18 檔案 +1473/-22）讓 target="pto" 配 execution_backend="auto" 解析到 tvm_ffi 並設為預設，主機側走 MakePackedAPI 與 C host 構建，Ascend 執行時經 aclrtLaunchKernelWithHostArgs 啟動 PTODSL 編譯出的 aibin。#3577（29 檔案 +1392/-1036）補齊 DeepGEMM-Ascend 的配置選擇與 epilogue，覆蓋密集、批次與分組 GEMM 的融合 bias、Alpha、BF16 隨機舍入與 FP8 量化。另有 #3530（NZ 緩衝的部分 UB→L1 複製）、#3573 / #3580 / #3581 / #3582 一組 PTO 謂詞、MAD 方向分析與 redux 有符號性修復。

3.1 TileOPs：分頁 GQA 前向換裝 paged warp 特化程式（#2668）

合於 10-20 22:41，8 檔案 +901/-103。新增的 GQAPrefillPagedWSKernel（SM90）承接 GQAPrefillPagedWithKVCacheFwdOp：一次 append launch 把 chunk 寫入分頁（key 在融合 RoPE 下旋轉，兩者都在 FP8 池上量化）並旋轉 query，隨後由 GQAPagedFwdOp 的 warp 特化程式在被撐大的快取上做注意力。該程式服務 head dim 256（單 query slot）與單 KV head 上寬於 16 頭的 query 組（把 (T * H, D) 的 query 攤平為行）；FP8 程式未覆蓋的維度 64 與 256 的池，經頁的 16 位映象讀取，單次上限 4 GiB；請求可能拆分時按快取長度排序、最長的先領，最多 128 個請求。

來源：https://github.com/tile-ai/TileOPs/pull/2668

3.2 TileOPs：FP8 lightning indexer 改雙 warpgroup 消費（#2666）

合於 10-20 22:41，6 檔案 +448/-2。原實現一個 warpgroup 乘 64-key tile，隨後跑與乘積等長的 epilogue（每個 head 乘 key scale，FMUL 與 FADD 分開）；另有一次乾淨掃描以 2.5 TB/s 寫視窗外的 -inf——按提交說明，這佔 chunk-prefill-kscale 472 微秒中的 425 微秒；解碼呼叫裡單 query 佔一個 CTA 走完 16384 個 key，耗時 289 微秒。新的 FP8LightningIndexerWSKernel（SM90）用 TMA warp 流式搬 64-key tile 給兩個 consumer warpgroup 輪流處理，每 tile 一次 m64n256 FP8 WGMMA，消費者 epilogue 收斂為 csrc helper。

來源：https://github.com/tile-ai/TileOPs/pull/2666

3.3 TileOPs：MLA 解碼走錯位蹺蹺板程式（#2665）

合於 10-20 22:39，7 檔案 +881/-590。MLADecodeSeesawKernel（SM90，512 + 64 latent，單 KV head）承接 MLADecodeWithKVCacheFwdOp，沿用 MLAPagedFwdOp 的錯位蹺蹺板思路，按請求經 TMA 讀 k 與 k_pe；程式本體遷到 kernels/attention/mla/seesaw.py，提供分頁與密集兩個入口，MLAPagedFwdOp 的拆分構建與原先產出同一份儲存。一個請求的 key 被切成 min(sm_count // blocks, tiles // 2) 段，用 log-sum-exp 合併；密集段按輸出 dtype 留部分結果，16 位輸出經 warpgroup 自有 key 緩衝暫存後由 TMA 落盤。

3.4 TileOPs：張量核上限改為運算元集合包絡（#2661）

五、趨勢觀察

編譯器正確性成為本視窗的主線，而非功能擴張。 主倉 9 筆合入裡 5 筆是靜默錯誤清理：向量化假定迴圈從零起（#3579）、共享記憶體 WAW 漏判（#2821）、MMA emitter 靜默縮 K 原子（#2818）、fragment reduce 保留維崩潰（#2815）、索引位寬提升後謂詞未跟（#3550）。這些缺陷的共同點是不報錯、只出錯結果或漏屏障，屬於使用者在生產裡最難定位的一類。同日 TileOPs 的 #2661 也在修”效能上限口徑”，說明專案正把”數字可信”當成與”跑得快”同級的工程目標。

昇騰線從補示例轉向訓練側。 五筆合入裡三筆是反向或遞迴運算元（indexer_bwd、situ_glu_grad、LSTM/GRU），且 situ_glu_grad 直接對齊 Kimi K3 Stable LatentMoE 的門控啟用並給出 910B3 上與 aclnn 的交叉校驗資料。配合 #3577 對 DeepGEMM-Ascend 配置選擇與 epilogue 的對齊，昇騰側的覆蓋面正從推理前向擴到訓練反向、狀態遞迴與大模型 MoE 門控。

PTO 正在成為 AscendC 之外的第二條執行路徑。 在審的 #3512 是 2.1 萬行的向量化框架（T.Parallel → PTO VMI，目標 Ascend 950），#3516 擬把 tvm_ffi 設為 pto 目標的預設執行後端，加上 #3530、#3573、#3581、#3582 一組複製與謂詞修復，PTO 線的工程量已明顯超過單點 patch 的量級。主倉同時用 #3511 補 AscendC 側的 L0 區域性複製能力，兩條路徑並行推進而非替換關係。

工具鏈外溢到獨立倉。 一日內出現三個新倉（中文教程、CANN 社群運算元倉、Hexagon 後端實驗）與一套 VS Code 擴充套件，主倉又把 lower trace 整體遷往 devkit（#3583，刪減 4390 行）。社群側的擴充套件速度已經快於主倉的模組劃分，這與 7 月”多後端語言方言”重構的方向一致：主倉收窄為語義與 IR，工具與後端實驗外接。

CI 口徑的顯式化值得留意。 #3569 把效能迴歸鎖到 H100 並對誤標卡快速失敗、#3564 把 Ascend 構建與測試拆進同一 check 的分步、#2661 用運算元集合包絡重標張量核上限——三筆都是”讓數字可比”，直接影響後續 PR 的准入門檻。
