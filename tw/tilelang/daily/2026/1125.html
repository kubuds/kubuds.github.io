今日重點：主倉版本號改到 0.1.16，標籤與 PyPI 仍停在 0.1.15

#3887 於北京時間 11-25 00:22 進主幹，只改 VERSION 一個檔案，把 0.1.15 改成 0.1.16。包後設資料與文件都從這個檔案讀版本號，所以一處改動就完成全部版本宣告。

提案列的驗證項有三條。釋出後設資料在 NO_VERSION_LABEL=ON 下解析為 0.1.16。三個 version-provider 測試透過。pre-commit run --all-files 與 bash format.sh 均透過。

釋出側尚未動作。GitHub 標籤最新仍為 v0.1.15。Releases 最新仍為 2026-09-30 的 v0.1.15。PyPI 上 tilelang 最新版也是 0.1.15。

因此本期不寫「0.1.16 已釋出」。準確說法是版本號已就位，打標籤、發 Release、推 PyPI 三步還在後面。

上一版 0.1.15 距離本次版本號推進 55 天。這期間主分支積累了 ROCm 批次修復、Z3 三處修補與昇騰輪子測試。

來源： https://github.com/tile-ai/tilelang/pull/3887。

今日重點：ROCm 單日六筆合入，修 FP4 轉換並把歸約判定改成按 wave 寬度

主倉當日 12 筆提交裡，6 筆帶 ROCm 字首。這批改動都對著真實量化與歸約路徑的缺陷。

#3665 修兩處 HIP 模板缺口。第一處是 T.cast(x, T.float4_e2m1fn) 返回值錯誤。程式碼生成把轉換寫成 (fp4_e2_t)x，而該型別只有 explicit fp4_e2_t(uint8_t raw)。於是 float 被截成整數再當作原始位存下：1.0 回來是 0.5，2.0 是 1.0，6.0 是 4.0，負數同樣錯。

第二處是 HIP 模板缺 E8M0 型別。兩處在 VeOmni 跑 DeepSeek-V4 的 QAT 量化器時暴露，環境是 gfx942 與 gfx950，含 UE8M0 尺度。0.1.15 的輪子裡這兩個標頭檔案與主分支一致，同樣受影響。

#3959 改歸約是否需要工作區的判據。舊程式碼在歸約執行緒數超過 32 時一律返回真。實際 tl::AllReduce 只在某一步跨 wave 時才用工作區，所以 wave64 上 64 執行緒歸約分配了從不訪問的 LDS。工作區在 IR 裡又是一次共享記憶體訪問，ThreadSync 會為此處每次歸約插屏障。

修法是按目標 wave 寬度比較，wave32 目標行為不變。屏障仍保留在真正跨 wave 的路徑上。

#3729 讓 gfx1200 上的 FP16 與 BF16 T.gemm 接受標準線性共享佈局。此前對 A_shared、B_shared 調 make_linear_layout 再算 T.gemm，會報 Get different layout。現有 WMMA 發射器本可按該對映取數，問題出在相容性判定。

做法是把共享佈局相容回撥的入參擴為四項：運算元、運算元緩衝、實際佈局、目標。ROCm 側據此按輸入逐項校驗複用，發射器與索引對映不變。

另有三筆屬工程細節。#3954 讓 compile_flags 與 tl.device_compile_flags 真正傳給 hipcc。此前這兩個引數只進快取 key，不改裝置程式碼。

#3958 給 hip_resource_info 加佔用率報告。#3956 在文件裡說明 T.gemm 在每 wave 行數很少時的限制。

來源： https://github.com/tile-ai/tilelang/pull/3665。

今日重點：昇騰一天報出十條缺陷，全部指向 API 引數校驗缺失

11-24 一天內，同一作者在 tilelang 開 10 條昇騰缺陷，編號 #4490 至 #4499。十份報告的測試環境一致。硬體為 Ascend 950PR 單 die、128 GB 視訊記憶體。軟體為 CANN 9.2.1、HDK 26.0.RC1、openEuler 24.03、torch 2.10.0+cpu、torch_npu 2.10.0.post4。

其中六條是「接受了後端編譯不了的輸入」。#4490 的 T.atomic_add 收 int8、uint8 與 float8 緩衝。#4492 的 T.atomic_max 與 T.atomic_min 收 int8、uint8。#4491 的 T.reduce_sum 收 bfloat16 與 float8。#4494 的 T.simd.vabs 與 T.simd.vneg 收 bf16 與 fp8 暫存器。

#4495 的 T.gemm 收任意 unit_flag_ctrl，傳 -1 或 999999 也能靜默編譯。#4497 的 T.gemm 收 GM 作用域運算元，後端找不到可編譯的路徑。

四條更接近崩潰或錯編譯。#4496 對 float8_e4m3fn 共享緩衝做 T.fill，直接讓 bisheng 編譯器 core dump。#4498 的 T.gemm 接受沒有任何 TILE_K_SUB 能整除的 K，隨後在自動排程裡斷言失敗。#4499 的標量 T.sqrt 與 T.rsqrt 在核心編譯期因 stl_pair.h 重宣告報錯。#4493 的五個原子介面在 Ascend 上沒有下降實現。

另有一條獨立來源的正確性缺陷。#4484 指出 SimdVF 的歸約下降把所有非 sum 的歸約型別都對映成 max，T.reduce_min 會返回最大值。該條來自原始碼審閱，未在裝置上覆現。

這批問題的共同點是：型別與取值本應在編譯期被拒絕，現在被放進後端才失敗。與 11-23 那批 6 條文件與實現不一致同屬介面契約缺口。

來源： https://github.com/tile-ai/tilelang/issues/4498。

一、核心專案進展

1.1 Z3 低位掩碼改整數取模編碼，主倉跟 bump 並撤回 TopK 測試的求解器限額

TVM 子模組 tilelang_main 分支當日合入一筆 #98，主倉側 #4482 於 14:03 跟 bump。三處修復都可追溯到 Z3Prover 的具體缺陷。

其一，常量有符號右移如 (n + 4095) >> 12 原先走位向量路徑，經 int2bv、bvashr、bv2int 三步。當這種移位出現在迴圈邊界裡，同作用域後續的純整數查詢會同時帶 Int 與 BitVec 約束，常在 tirx.Simplify 裡耗盡預設資源預算。

其二，VisitShiftOp 在 CanProve 中把 b >= 0 與 b < 64 兩條斷言直接加到共享求解器上。這會汙染後續查詢，也會與外層作用域衝突。同時 DivNode 與 ModNode 用了 Z3 的歐幾里得 / 與 %，於是對負被除數也能證明 truncmod(a, 4) >= 0。

其三，tx & 31 這類掩碼在索引表示式化簡中仍走位向量。#98 把 x & (2^k - 1) 翻成 x mod 2^k。提案記錄了一個具體代價：某裝置函式里簡化器問了 156 次同類問題，耗時 11.7 秒，反例是 tx = 4。

測試側先止血再撤。#4463 於 09:51 把兩個 ROCm 測試檔案的 arith.z3_rlimit 限到 100，起因是四個 DeepSeek 與 GLM 的 TopK 用例各耗 494 至 605 秒。

#4489 於 20:40 撤回該限額，理由寫的是 #4482 讓常量有符號右移變得便宜。對照用同一構建 b4c67597、TVM de131ae4、Z3 4.15.4，取三次冷跑中位數。

來源： https://github.com/tile-ai/tilelang/pull/4482。

#4419 於 22:59 進主幹。提案寫明的前提：Linux 輪子是 CUDA、ROCm、Ascend 三合一構建，而 test-wheels-gpu 只跑前兩半。昇騰半區在輪子釋出前從未在真 NPU 上執行過。

新增 test-wheels-ascend 作業，跑在自託管昇騰 runner 上，環境搭建與 ci.yml 的昇騰作業同源。當前映象為 cann9.3.0-weekly.20261112-ubuntu22.04-py3.13。登錄檔另有 cann9.2.0、9.2.1 與 py3.10 至 py3.12 變體，矩陣可擴。

作業流程是先取構建好的 Linux x86_64 輪子，裝進 --system-site-packages 虛擬環境。容器的 torch 與 torch_npu 預先 pin 住。

隨後把原始碼包移開，確保 import tilelang 命中的是輪子而不是原始碼樹。輪子為 abi3 構建，wheel.py-api = "cp39"，一個產物可裝到任意 Python 版本。

來源： https://github.com/tile-ai/tilelang/pull/4419。

1.3 vote 與 sync 內建函式保留 64 位謂詞，1 << 32 不再被判為假

#3777 於 09:53 進主幹。CUDA 的 vote 與 block-sync 內建函式只接收 32 位 int 謂詞，例如 __any_sync、__syncthreads_count。

傳 int64 或 uint64 時值被隱式收窄。低 32 位為 0 的非零謂詞因此被判假，1 << 32 是最直接的例子。

受影響介面七個。投票類為 T.any_sync、T.all_sync、T.ballot、T.ballot_sync。同步類為 T.syncthreads_count、T.syncthreads_and、T.syncthreads_or。

修法是把超過 32 位的謂詞先歸一成顯式 != 0，再向內建函式傳佈爾值。另加了 1 << 32 的執行時迴歸，整個 warp vote 測試檔案透過。

來源： https://github.com/tile-ai/tilelang/pull/3777。

三、生態與採用方（TileOPs 運算元庫 / FlashQLA / topa）

3.1 TileOPs 十六筆合入，主線仍是繞開 0.1.15 的邊界檢查開銷

十六筆的標題裡反覆出現同一句話的不同寫法：在 0.1.15 上去掉某個通用路徑帶來的邊界檢查。

#3161 讓 FP8 indexer 的 warp 特化核心繞開 0.1.15 的邊界檢查。#3151 讓 Mamba 的 CausalConv1dFwdOp 在 0.1.15 上把一波次預填網格常駐。#3142 讓 MoE 的 FP8 分組 GEMM 每個任務只保留一個分支，並把掩碼分片鋪滿所有 SM。

#3146 換了方向。它把 Tensor 的越界夾緊改在輸入 dtype 內完成，而不是提升到更寬的整數再夾。

這條線起於 11-23 的 #3133「找回 25 行退化」。兩天下來，恢復動作從「與 0.1.12 對照」變成「按檢查點逐個繞開」。

來源： https://github.com/tile-ai/TileOPs/pull/3161。

3.2 取樣、卷積、歸約三線各補一筆結構性改動

取樣側兩筆。#3157 把拆分的 top-p 行用全域性原子量做分箱。#3158 把同一行的分箱和改用定點求和，使掩碼可復現。

卷積與索引各一筆。#3148 把對稱 Conv2d 的收縮拆到空閒 SM 上。#3156 讓兩輸入 concat 在剛過一波時每執行緒走四個向量。

歸約兩筆。#3152 一次啟動跑完前導軸，跨 thread-block cluster 切分。#3154 用一次屏障或一次或運算完成塊內 any 與 all 的摺疊。

線性注意力三筆。#3160 在 chunk-parallel 路徑上為 SM90 的 KDA fp16 given-gate 預填做超一 chunk 的預處理。#3159 把 GDN 分割槽 pass 的 transfer 旗標綁成值，避免 0.1.15 丟掉它。#3144 讓 KDA 的 key-major 狀態按記憶體序解碼，並把打包序列一起走。

來源： https://github.com/tile-ai/TileOPs/pull/3158。

3.3 夜間測試改報每模型 batch-1 預填與解碼吞吐

#3153 讓夜間流水線在單卡上報出每個模型的 batch-1 prefill 與 decode 每秒 token 數。此前夜間只報對錯與耗時，不報吞吐。

同日新開 #3155，要求用 CUDA graph 重放每個模型的解碼步。這條把測量方法本身作為工作項，與 #3153 的指標口徑配套。

#3150 屬 Mamba 線，把 CausalConv1dUpdateFwdOp 的解碼狀態行經共享記憶體中轉。

來源： https://github.com/tile-ai/TileOPs/pull/3153。

3.4 topa 新開 int8 WGMMA 定價工作項，TileFoundry 在審一筆 ASTRA-sim 匯出

topa 於 23:22 新開 #69，要求讓 NVIDIA 側接受 int8 運算元進入 SM90 WGMMA 與 MatMul 的 MMA 查表。該倉主分支最後提交為 11-22，視窗內無程式碼變更。

TileFoundry 的 #366 在審，內容是把 Qwen3 的一個訓練步以五種配置匯出到 ASTRA-sim，視窗內有更新，未合入。

採用方兩倉本視窗靜默。deepseek-ai/TileKernels 最後推送仍為 10-14。QwenLM/FlashQLA 前一日合入的 #55 之後無新提交。

來源： https://github.com/tile-ai/topa/issues/69。

五、趨勢觀察

  • 版本節奏進入釋出前夜。0.1.15 於 9-30 釋出，55 天后版本號推進到 0.1.16。這一版的積累主要是 ROCm 修復、Z3 三處修補與釋出鏈工程，而非新功能。

  • 效能迴歸治理形成了固定套路。先加限額止血，再修根因，最後撤回限額並複測。#4463、#4482、#4489 三步都在一天內完成，中間隔著一次 TVM 子模組更新。

  • 昇騰的短板從運算元覆蓋轉向介面契約。一天十條缺陷裡沒有一條要求新運算元，全部是「不該接受的輸入被接受」。這類問題修起來便宜，但會持續消耗使用者信任。

  • TileOPs 的最佳化口徑仍是追框架版本。0.1.15 的通用路徑帶來的額外開銷，需要下游按運算元逐條繞開。兩天內至少五筆以此為標題，說明版本升級與運算元庫效能之間還沒有自動對賬機制。

  • RISC-V 側連續兩個視窗零變化。TVM 路線與 MLIR 路線都停在原位，本視窗連索引頁也沒有動作。
