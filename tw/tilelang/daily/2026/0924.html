今日重點：TileSight 正式開源——瓦片中心的分析式效能模型從論文落地為官方倉庫

日期：2026-09-23　來源：tile-ai/TileSight 倉庫／首個提交 init／arXiv 2607.22432

09-23 22:54（北京時間），tile-ai 組織下新增的 TileSight 倉庫完成首次提交 init：177 個檔案、約 5.67 萬行新增，MIT 許可，提交者為帝國理工學院的 Zhiwen Mo。7 月 24 日 arXiv 論文結尾「將在發表後開源」的承諾至此正式落地；組織倉庫總數由 28 增至 29。

TileSight 定位為「瓦片中心」的分析式 GPU 效能模型：以瓦片為建模單元，在 CPU 側估計運算元的操作成本、快取流量與執行時間——核內建模計算與訪存流水線重疊，核間建模快取層級，跨 GPU 建模節點間通訊；實測標定則由 CUDA 與 HIP 探針在目標 GPU 上單獨完成，與建模解耦。論文口徑的精度：在 A100、H200、B200、B6000 四代平臺上，單卡核心延遲的合併平均絕對百分比誤差為 12.35%，L2 命中率預測與實測相差約 1 個百分點；擴到 32 卡叢集，融合分散式核心與 vLLM 端到端服務的加權誤差分別為 16.18% 與 13.52%。

倉庫結構（首提範圍）：

  • tilesight/arch/：20 餘份硬體檔案，覆蓋英偉達 A100/H100/H200/B200/B6000/V100/T4/P100 與 RTX 3090/4090/5090 等、AMD MI50/MI210/MI300X/MI325X、英特爾 Arc 770；
  • tilesight/modeling/：程式前端（構建器/分析/契約）、多級快取複用距離模型（SDCM）、流水線重疊分析（序言/穩態/尾聲、佔用率、波量化）、GEMM/FlashAttention（FA3/FA4 週期排程）與 FlashMLA 解碼等介面卡；
  • micro_benchmark/：CUDA 探針（B200 tcgen05/tmem、H200 wgmma、通用 dram 掃描與 P2P）與 HIP 探針（rocBLAS GEMM、AMD 裝置資訊）；
  • examples/ 與完整測試套件，另含 NCU 對比與 CuTeDSL/私有工具鏈的預測輔助工具。

判讀：這是本主題「效能可解釋性」線索的第三段——07-24 論文（帝國理工與 TileLang 核心成員合著）→ 09-18 社群文件倉（把 TileLang 分析接入 TileSight）→ 09-23 官方程式碼倉。它把此前分散在論文與個人文件裡的方法固化為組織專案，與 TileFoundry（編譯期內的 IR 分析）形成分工：一個在建模期預測跨層成本，一個在編譯期報出快取容量結論。硬體檔案覆蓋 AMD 與英特爾獨顯這一點，也讓它天然服務於多後端敘事。

1.5 TileOPs 專題：DeltaNet 推理運算元入列，H200 對照 FLA 最高提速 3.7 倍（09-23）

日期：2026-09-23　來源：#2163

18:44 合入（+743/−3，13 檔案）：

  • 新增 DeltaNetInferenceFwdOp 與面向 H200 的稠密預填充核心（基於 Gated DeltaNet 的分塊求解/遞推管線）；既有訓練 API 與獨立解碼核心保持不變；支援呼叫方持有的非零 FP32 初始狀態；
  • 當前樹內特化覆蓋等長 BF16/FP16 預填充、K=V=64 或 128、T≥64 且整除 64 的場景；解碼、打包變長與 Q/K L2 歸一化列為後續路徑，公共推理契約暫為「規格級」；
  • 驗證：H200 上推理/GDN/roofline 測試 51 項透過、遺留前向測試 9 項透過；鎖頻（SM 1500MHz）下與 FLA 的逐用例 A/B（微秒，中位數；busy 為 GPU 活動時間之和，latency 含活動間隙）：
B / T / H / D TileOps busy FLA busy TileOps latency FLA latency
2 / 2048 / 4 / 64 44.8 67.1 293.1 497.0
2 / 8192 / 4 / 64 76.5 229.9 306.5 486.5
2 / 16384 / 4 / 64 120.5 448.2 320.6 602.1
1 / 4096 / 16 / 128 116.6 206.8 300.1 494.6

讀法：busy 口徑最高提速 3.7 倍（T=16384），含間隙的端到端延遲最高降低約 47%；每個用例在計時前都先對輸出與終態做對照檢查。另需注意：該運算元進入夜間基準後，長預填充配置出現一次超時（見 1.9）。

1.7 TileOPs：外接後端通道治理——38 處裝置檢查被拆除（09-23）

日期：2026-09-23　來源：#2179／#2164／#2182

背景：社群開發者報告在 MTT S5000 上整合外接 MUSA 後端時，多個官方運算元「在註冊的外接構造器被呼叫之前就失敗」——三道阻塞：僅 CUDA 的輸入校驗、拒絕零輸入的外接呼叫、外派前的 CUDA 裝置查詢（缺陷單 #2164；#2165、#2166 另記測試路徑與構建器註冊問題）。

視窗內的響應：

  • #2179（+797/−256）：拆除運算元層約 38 處裝置種類檢查（RoPE、Dropout、Mamba/SSD、DeltaNet、GLA、NSA、Engram、MoE、FFT、FP8 量化、TopK 等），改由樹內核心用 Kernel._require_cuda 在張量層面宣告裝置；check_tensor_shape 保留形狀檢查、去掉裝置檢查；新增 pre-commit 鉤子 op-device-kind-lint 阻止裝置種類檢查迴流；為延後構建的呼叫記錄引入 make_call 形參。零輸入與複合運算元兩類需設計決策，列為後續工作。
  • #2182（issue）：指出 BuildKernel 協議只承諾可呼叫物件，而運算元層假定更多——存在讀取樹內核心屬性、單條目解包多核心、44 個運算元類不接受 target= 引數等情況；協議無法表達的複合條目需要擴充套件。
  • #2181、#2183：把樹內測試固定到 BUILTIN 路徑並明確 iter_kernels 產出、把二元自動調優測試限定到樹內核心，配合上述治理。

判讀：外接後端從「能註冊」走到「能排程」的最後一段開始鋪路；阻塞由外接方實測給出，修復由維護方成組推進，是少見的雙邊協同節奏。

2.2 昇騰：標量 GM 儲存競態修復方案提交，差異數歸零（09-23）

日期：2026-09-23　來源：#1834（修復 #1304）

17:04 新開（+557/−1，10 檔案），兩層修復：

  • 根因分析：同一 GM 緩衝被混合寫入——批次複製走 MTE3 DMA 直寫、尾列標量 SetValue 經寫回快取做讀-改-寫並延遲寫回；行距非 64 位元組倍數時相鄰行共享快取行，髒行逐出會覆蓋 DMA 已寫入的新值；多塊核心下競態跨核發生，而快取清理與同步指令均為本核作用域，故單靠同步指令修不乾淨（復現指令碼殘留 27%）。
  • 第一層（同核）：在同步插入環節對「被標量寫過的 GM 緩衝」在 MTE3 寫前後選擇性插入快取清理與等待；同時把事件號分配改為迴圈複用（消除模板硬編碼 0 號事件與 pass 分配撞車的潛伏死鎖）。復現指令碼失配數 12,967,510 → 3,496,136（降 73%）。
  • 第二層（改寫消除）：新增 opt-in pass（預設關閉）——把「連續序列迴圈內的單條 GM 標量寫」改寫為 UB 暫存 + 單條 DMA burst，從根源上讓髒行不再產生。開啟後失配數歸零；新增 2 個迴歸測試透過、113 項既有套件透過、gqa_fwd_varlen 零開銷、量化混合核心無劣化。
  • 範圍：opt-in；條件寫、累加、散射等無法改寫為連續 burst 的形態仍有跨核隱患（平臺級限制，建議單獨跟蹤）；作者環境為 Ascend910 A3 / CANN 9.0.0。

五、趨勢觀察

5.1 分析層成形：從論文與社群文件到官方程式碼倉

TileSight 的三段式落地（07-24 論文 → 09-18 社群文件倉 → 09-23 官方程式碼倉）說明：圍繞 TileLang 的效能可解釋性正在從「個人線索」升格為「組織專案」。它與 TileFoundry（編譯內分析，本視窗把快取容量結論做到可復算）方向交錯。對生態的含義：在運算元庫與執行時之外，分析工具的完善程度正在成為 TileLang 相對同類工具鏈的差異化資產；TileSight 硬體檔案覆蓋 AMD 與英特爾獨顯，也為多後端敘事提供建模底座。

5.2 TileOPs 效能季的收口與再出發

單日七筆合入加三筆新開，說明 TileOPs 的效能季並未結束，而是從第一波「運算元入列」轉入第二波「排程與配置細粒度打磨」：varlen GQA 三連圍繞排程規劃與持久化，W4A16 圍繞暫存器與網格利用率。觀察指標：這樣的合併節奏需要再持續數個交易日才算穩住，否則仍是脈衝式推進。

5.3 多後端工程債顯性化

外接後端的三道阻塞與協議缺口把「多後端可插拔」從願景拉回工程細節：裝置種類檢查散落在運算元層、構建器協議只保證可呼叫性、44 個運算元類缺少目標引數。好訊息是視窗內已有成組的拆彈動作（一次拆除 38 處檢查並加 lint 防回潮）；按外接方口徑，這條通道的完成度將決定第三方後端能否在當前週期跑通官方運算元佇列。

5.4 空白與風險點

其一，主倉評審積壓未解：TileIR 後端 31 個提交、魔法除法與啟動不變數繼續等待，大變更視窗與發版停滯（22 天）疊加；其二，新運算元進入基準即暴露長預填充超時，效能敘事需要在基準層面補齊承載能力；其三，昇騰倉的「合入—回退」節律仍在繼續，示例類貢獻的驗收路徑未見公開說明；其四，索引邊界修復單當日關閉，若問題仍然存在而無人接續，窄索引型別的邊界行為將繼續處於懸空狀態。
