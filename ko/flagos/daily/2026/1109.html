1.2 플랫폼 측면: T-Head ZW810E PPU 편입, 2.3.0 첫 runtime 전달(11-07)

날짜: 2026-11-07　출처: build-infra #1675(base 이미지) · build-infra #1679(runtime changelog) · build-infra #1676(상태 매트릭스 키 변경) · build-infra #1682(적용 플랫폼) · 벤더 문서 thead

  • 등재: #1675 신규 백엔드 키 thead-ppu2.1.0 추가, T-Head ZW810E의 PPU 2.1.0 SDK 라인에 대응; base 레이어는 벤더 PAI-DSW 학습 이미지를 직접 참조(약 25 GB, SDK는 /usr/local/PPU_SDK에 위치), 플랫폼 entrypoint를 제거하고 pip를 스택 미러 사이트로 되돌린 뒤 cmake와 libpython3-dev를 보강.
  • 첫 runtime: #1679는 tag 2.3.0 하위에 해당 백엔드의 runtime changelog를 보강, 이는 이 백엔드 라인의 첫 runtime 인도. 의존성은 torch 2.10.0+v0.1.0.ppu2.1.1과 numpy 1.26.4, 기본 컴파일러는 FlagTree 0.7.0+ppu3.6, /opt/triton 폴백 버전은 3.5.0+v0.2.0.ppu2.1.1, 연산자 라이브러리는 FlagGems 5.4.0이며 cpp wheel은 생성하지 않음.
  • 감사 가능: #1676는 vllm, sglang, megatron 세 상태 매트릭스와 두 곳의 하드코딩된 백엔드 목록에 흩어져 있던 구 키 thead-ppu2.0.0을 thead-ppu2.1.0으로 일괄 교체하고, sglang의 제외 주석을 “기본 이미지 없음”에서 “base 있음, app 레이어 미연동”으로 수정.
  • 적용 플랫폼: #1682는 configs.yaml에 범용 platform 필드를 추가하여 이미지 설명의 “적용 플랫폼” 행으로 렌더링, T-Head 라인에는 Alibaba Cloud PAI-DSW를 기입; 동일 배치의 #1681, #1684, #1685는 2.3.0의 base와 runtime changelog 날짜를 기록.
  • 현황: app 레이어는 아직 미연동(deps_app과 launch_docs 모두 false), FlagGems 측 동일 모니터링 기간에 #6497이 이미 머지되어 MM과 MV에 FlagTune 비용 모델을 활성화.

1.3 FlagGems: 하루 123건 머지, 87개 Ascend 연산자 일괄 반영(11-06)

날짜: 2026-11-06　출처: FlagGems #8212(special_erfc) · FlagGems #8206(renorm) · FlagGems #8479(log_softmax_backward_data) · FlagGems #6497(FlagTune 비용 모델) · FlagGems #6923(enflame flagcicd 이관)

  • 규모: 모니터링 기간 내 123건 머지가 모두 11-06에 발생, 10:34부터 11:24까지 약 1시간 이내에 집중 반영, 작성자는 전부 LoserCheems, 연산자명 중복 없음.
  • Ascend 다수: 87건에 [KernelGen][Ascend] 접두사가 붙으며, xlogy 시리즈 6개 변형, mish 시리즈 3개 변형, renorm 2개 변형, deg2rad 3개 변형, arctanh 3개 변형, 그리고 amin, clamp_, clip_, permute_copy, narrow_copy, smm, euclidean_dist, cumulative_trapezoid 등을 포함.
  • 기타 백엔드: Iluvatar CoreX 10건(BI-V150의 float_power 3개 변형, avg_pool1d, expand_copy, greater_ 등), Moore Threads 9건, NVIDIA 7건; 추가로 MetaX 2건(addmm, baddbmm와 router GEMM 특화, cross_attention), Kunlunxin 3건(6개 연산자 오버라이드 및 foreach 스칼라 커널 수정).
  • 수반 변경: #6497은 T-Head PPU에 FlagTune 비용 모델을 활성화; #6923은 Enflame CI를 flagcicd로 이관하고 FlagTree를 0.7.0으로 상향; #8509는 CODEOWNERS 보강.
  • 심사 중: FlagGems에는 별도로 88건이 심사 중, 그중 Hygon 전용 연산자 20건(3.3 참조).

1.4 FlagTree: Hygon hcu3.6 릴리스, deb와 rpm을 백엔드별로 분리 패키징(11-06)

날짜: 2026-11-06　출처: FlagTree 0.7.1a1+hcu3.6 · FlagTree #1417 (deb 백엔드별 단일 패키지) · FlagTree #1461 (rpm은 기배포된 wheel 사용) · FlagTree #1583 (MThreads TLE 서브 슬라이스) · build-infra #1660 (hcu wheel 릴리스 라인 편입)

  • 릴리스: 0.7.1a1+hcu3.6이 11-06 PyPI에 릴리스되었으며, 0.7.1 시리즈에서 Hygon 백엔드의 세 번째 프리릴리스이다(앞선 두 번은 10-26의 mthreads3.6과 10-29의 tsingmicro3.6).
  • 패키징 재구성: #1417은 백엔드 표에 따라 백엔드마다 deb 패키지를 하나씩 생성하도록 변경했고, #1461은 Ascend의 rpm이 더 이상 이 저장소에서 재빌드하지 않고 기배포된 wheel로 직접 빌드하도록 했으며, #1382는 런타임이 Python 개발 헤더 파일에 의존하도록 했고, #1369는 libtriton.so의 디버그 섹션을 다시 제거했으며, #1368은 함께 배포되던 CUPTI 정적 라이브러리를 제거했다.
  • 컴파일러 측: #1583은 Moore Threads TLE 브로드캐스트 버퍼 텐서의 서브 슬라이스 기능을 추가했고, #1531은 포인터와 버퍼 뷰에서 공유 arena 지오메트리를 유지하며, #1401은 혼합 정밀도 SQMMA가 FP32 누산기를 재사용하도록 했다.
  • 릴리스 라인: build-infra #1660은 hcu 타깃을 FlagTree의 wheel 릴리스 라인에 추가했으며, 1.9의 TE-FL 릴리스 라인과 동일한 접근 방식이다.

1.5 FlagQuantum: Stim과 PyMatching, 오류 정정 워크플로에 통합 (11-07)

날짜: 2026-11-07　출처: FlagQuantum #1087 (Stim 및 PyMatching 워크플로) · FlagQuantum #1106 (동적 레코드 변환) · FlagQuantum #1102 (Clifford 샘플러) · FlagQuantum #1104 (Qmod 코퍼스 호환) · FlagQuantum #1105 (혼합 적응형 상태 벡터)

  • 오류 정정 체인: #1087은 Stim과 PyMatching의 실험 워크플로를 QEC 모듈에 통합했고, #1106은 내장 Stim을 포함한 명시적 동적 레코드 변환을 지원하며, #1102는 준비된 Clifford 샘플러가 시뮬레이션 측에서 직접 실행되도록 했다.
  • 시뮬레이션과 코퍼스: #1105는 혼합 적응형 상태 벡터의 출력 일관성을 검증했고, #1104는 검증된 Qmod 코퍼스 호환 계층을 연결했다.
  • 속도: 13건 머지, 16건 커밋으로 11-06과 11-07에 걸쳐 있으며, 모니터링 기간 내 FlagGems를 제외하면 가장 많이 머지된 프로젝트이다.
  • 위상: FlagQuantum은 FlagOS의 양자-고전 혼합 프레임워크로, 커뮤니티 거버넌스에서는 준비 중인 wg-ai4s 워킹 그룹 산하에 속한다.

1.6 FlagCX: Iluvatar CoreX 단위 테스트 파이프라인, Ascend PCI 토폴로지에 DCMI 폴백 추가 (11-07)

날짜: 2026-11-07　출처: FlagCX #670 (Iluvatar CoreX 단위 테스트) · FlagCX #692 (PCI 토폴로지 및 DCMI 폴백) · FlagCX #696 (Barrier 펜스) · FlagCX #700 (Ascend IPC 및 GPU MR) · FlagCX #699 (MetaX AllToAll 검증)

  • CI 측면: #670은 Iluvatar CoreX에 단위 테스트 파이프라인과 CI 이미지를 추가했으며, 3.4의 FlagScale, Megatron-LM-FL, TransformerEngine-FL의 CoreX CI와 동일한 작업 묶음이다.

1.7 Torch-FL: Cambricon torch.compile 단계 및 8개 연산자 네이티브화 (11-08)

날짜: 2026-11-08　출처: Torch-FL #772 (torch.compile 단계) · Torch-FL #770 (8개 연산자 네이티브화) · Torch-FL #771 (silu, CNNL 활성화 커널 사용) · Torch-FL #769 (MLU 측 스트라이드 gather) · Torch-FL #767 (CNNL 코드 생성기)

  • 경로 개통: #772는 Cambricon에 torch.compile 단계를 추가하여 이 컴파일 경로가 해당 백엔드에서 “최소한 존재”하도록 만들었다. #767은 학습 스텝 연산자를 CNNL 코드 생성기로 이전했다.
  • 성능: #770은 8개 연산자를 추가로 네이티브로 서비스하고 행렬 곱셈을 배치 처리로 변경했다. #771은 silu가 CNNL의 활성화 커널을 직접 사용하도록 했다. #769와 #768은 스트라이드 gather, softmax, negate를 MLU 디바이스에 유지하여 더 이상 호스트를 경유하지 않는다.

3.6 Moore Threads: Kimi K3.1 Pro의 Day-0, MUSA 네이티브 스택에서 구동 (11-06)

날짜: 2026-11-06　출처: Moore Threads 공지 전재 (Jiemian) · 기술 세부 보도

  • 사실: 11-06 Moore Threads는 MTT S5000 지능형 컴퓨팅 카드와 MUSA 소프트웨어 스택을 기반으로 Kimi K3.1 Pro의 Day-0 적응을 완료했다고 발표했으며, 모델 로딩, 서비스 시작 및 텍스트·이미지 기초 추론 경로를 연결했습니다.
  • 기술 경로: SGLang-MUSA로 업스트림 구현을 수용하고, MATE 연산자 라이브러리, Triton-MUSA, TileLang-MUSA 및 MTCC 컴파일러를 통해 핵심 계산 경로를 마이그레이션했습니다. 희소 어텐션의 인덱스 선택, KV 캐시 레이아웃과 Prefill·Decode 경로에 맞춰 적응했으며, MXFP4 전문가 가중치는 온라인 변환과 크로스 레이어 재사용 FP8 워크스페이스로 처리했습니다.
  • 기준: 공지와 보도 모두 FlagOS 또는 FlagGems를 언급하지 않았으며, 이 적응은 MUSA 네이티브 스택에서 실행된 것으로 회원单位的 독립적 진전에 해당하며 FlagOS 스택 성과에 포함되지 않습니다. 생태계 참조 차원에서 본 절에 배치합니다.
  • 참조 의의: 동일 모델의 FlagOS 경로에서 아직 멀티칩 Day-0 기록이 확인되지 않았으며, 다음 호에서는 FlagGems에 대응 연산자 보충이 나타나는지 주목할 수 있습니다.

4. 요약 및 동향 관찰

  • 플랫폼 측면이 ‘키 보유’에서 ‘딜리버러블’로 이동: T-Head ZW810E PPU가 이틀 만에 백엔드 키, base 이미지, runtime changelog 및 상태 매트릭스 네 가지를 정렬했으며, 2.3.0은 해당 백엔드 최초의 runtime 딜리버리입니다. 디바이스는 Alibaba Cloud PAI-DSW 이미지에서만 사용 가능하고 runner에는 GitHub 출구가 없으며, 이 두 제약이 다른 백엔드와 다른 딜리버리 형태를 결정했고 단기적으로 app 계층은 여전히 공백입니다.
  • 연산자 생산이 배치 리듬에 진입: 단일 일 123건의 FlagGems 머지, 그중 87개 Ascend 연산자가 한 사람이 1시간 이내에 저장소에 반영되었고, 별도로 20개의 Hygon 전용 연산자가 심사 대기 중입니다. KernelGen은 ‘연산자 작성’을 ‘생성 결과 심사’로 전환시켰으며, 병목이 구현에서 리뷰와 검수로 이동했습니다—이는 심사 중 PR 수(269건)가 머지 수보다 지속적으로 높은 이유를 설명합니다.
  • 배포 계층이 수렴 중: TransformerEngine-FL은 하나의 순수 Python wheel로 모든 비 NVIDIA 벤더에 공급하고, FlagTree의 deb는 백엔드당 하나의 패키지로 변경되었으며 rpm은 이미 릴리스된 wheel을 직접 가져옵니다. 두 가지 조치가 동일한 목표를 향합니다—칩별 반복 빌드를 줄이고 차이를 설정에 남기는 것입니다.
  • 프레임워크 적응이 파상형: vLLM 0.32.0과 SGLang 0.5.18의 적응이 모니터링 기간 내 집중적으로 나타났으며, T-Head, Iluvatar CoreX, MUSA, Kunlunxin, Ascend 다섯 곳을 커버하지만 대부분 여전히 심사 중입니다. 11-30의 rc0 전에 머지될 수 있는지가 2.3이 매트릭스대로 딜리버리될 수 있는지의 핵심 변수입니다.
  • 2.3 마감 카운트다운 진입: 커뮤니티 2.3 일정은 FEP 머지 마감 11-13, 기능 동결 및 rc0 11-30, rc1 12-07, rc2 12-14, 코드 락 12-25, GA 12-30입니다. 이번 호에는 새로운 FEP 제출이 없으며, 11-06의 여섯 건(0164~0168, 0170)은 여전히 Provisional Draft이고 자체적으로 GPU 검수를 실행하지 않았다고 밝혀 마감 압력이 다음 주에 집중됩니다.
  • 리스크와 관찰 포인트: T-Head app 계층 미연결, Hygon 20개 연산자 전원 심사 중, Iluvatar CoreX 네 개 CI 중 세 곳 심사 중, 대회 제출은 저장소 반영만 되고 성적 미발표—네 가지 모두 ‘조치 완료, 검수 미도달’에 해당하며, 다음 주에는 신규량보다 머지율을 중점적으로 볼 필요가 있습니다.
