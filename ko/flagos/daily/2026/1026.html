1.2 FlagRelease: MiniMax-M3.1-Flash 9개 칩 W8A8 동일자 출시, 4개사 Express 버전 사용(10-23)

날짜: 2026-10-23　출처: FlagOS 멀티칩 지원 설명 · FlagRelease 조직 모델 · vllm-plugin-FL PR #631

  • 적응 범위: 9개 플랫폼은 Damo Academy XuanTie(眞武), NVIDIA, MetaX, Hygon, Huawei Ascend, Moore Threads, Iluvatar CoreX, Kunlunxin, Tsingmicro이며, 모두 W8A8 버전을 제공합니다. 모델 저장소는 FlagRelease 조직 아래에 통합되어 있으며, ModelScope와 Hugging Face 두 채널로 배포됩니다.
  • 양자화 경로: FlagOS는 MiniMax의 네이티브 QAT NVFP4 가중치를 크로스 칩 범용 W8A8 배포 버전으로 변환하며, 자체적으로 2차 학습을 수행하지 않습니다. NVIDIA, Ascend, Kunlunxin, Damo Academy XuanTie 4개사는 Express 버전이며, 명명 규칙은 MiniMax-M3.1-Flash-W8A8-<platform>-FlagOS-Express이고 나머지 5개사는 표준 버전입니다.
  • 모델 사양: M3.1 Flash의 총 파라미터는 428B, 활성 파라미터는 23B이며, 1M 컨텍스트와 이미지, 비디오 입력을 지원하고 조정 가능한 사고 깊이 파라미터가 새로 추가되었습니다. 공식 발표 기준으로 온라인 추론 속도는 전 세대 대비 약 3배 향상되었고, Agent 시나리오의 종합 Token 비용은 70% 감소했습니다.
  • 배포 경로: 문서에서는 두 가지 경로를 제시합니다. FlagRelease 이미지를 직접 사용하는 것을 권장하며(칩에 따라 저장소를 선택하고, 모델 카드에 따라 드라이버와 컨테이너를 선택), 또는 소스에서 설치합니다. Damo Academy XuanTie 예시는 vLLM 0.24.0, vllm-plugin-FL 0.3.0, FlagGems 5.4.0이며, 필요에 따라 FlagTree와 FlagCX를 추가하고 tensor_parallel_size=8로 서비스를 시작합니다.
  • 코드 측 지원: vllm-plugin-FL은 10-24 08:25에 ‘add MiniMax-M3.1 support and inference example’(#631)을 병합하여 모델 연결과 추론 예시를 함께 메인 브랜치에 반영했습니다. FlagGems-vllm은 10-23 17:19에 PPU 측 flash_mla_sparse_fwd(#975)를 병합하여 M3.1의 희소 MLA 경로에 대응했습니다.
  • 판단: 9개 저장소가 30분 이내에 집중적으로 생성된 것은 릴리스 파이프라인이 이미 템플릿화되었음을 보여줍니다. 실제 차이는 모델 카드의 런타임 매트릭스(프레임워크 버전, 플러그인 브랜치, FlagGems 커밋, FlagCX 필요 여부)에 있으며, 이것이 ‘실제 적응 여부’를 판단하는 검증 가능한 근거입니다.

4. 요약 및 트렌드 관찰

  • Day-0 전달이 배치화 단계에 진입: 일주일 내 GLM-5.3-Flash 9개 칩과 MiniMax-M3.1-Flash 9개 칩이 연속 두 차례 같은 날 일제히 출시되었고, 이번 라운드는 W8A8 단일 경로, 네 곳의 Express 버전으로 통일되었다. 전달의 복제 가능성은 이미 확립되었으며, 다음 관찰 지점은 「동일 포맷이 서로 다른 모델에서 안정적인가」와 모델 카드 버전 매트릭스가 업스트림 업그레이드에 맞춰 동기 갱신되는지 여부다.
  • 2.3.0은 「권한 부여 완료, 미릴리스」 유예기에 있음: build-infra의 게이트, changelog, 재빌드 권한 부여, 버전 파라미터화 네 가지가 모두 갖춰졌으나 태그는 아직 찍히지 않았다. 2.2 릴리스 전과 다른 점은 이번 라운드에서 「컨테이너 시작 시 컴포넌트 버전 선택」을 정식 역량으로 만든 것으로, 이는 런타임과 연산자 라이브러리, 컴파일러의 버전 분리를 의미하며 장기적으로 적응과 검증의 세분화 단위를 바꿀 것이다.
  • 조직 활성도가 퀀텀 스택에 고도로 집중: FlagQuantum 단일 저장소가 82.5%의 커밋, 54%의 병합을 차지. 이러한 집중은 빠른 구조 재편(QEC 패키지 분리, Quafu SDK 전환)을 가져왔지만, 조직 차원의 「비퀀텀 측」 처리량을 뚜렷이 떨어뜨렸다—일평균 병합이 163건에서 91건으로 감소했고, 주요 차액은 FlagGems와 FlagGems-sglang의 하락에서 비롯되었다.
  • 경진 트랙이 연산자 공급 주경로로 부상: FlagGems-sglang 34건 병합 중 대다수가 외부 기여자의 Competition-Track1에서 발생, 2시간 내 30건을 병합 가능. 공급은 빠르고 심사는 집중되어 테스트 계약 보완은 사후 배치에 의존하는데, 이 경로의 장기 품질은 결함 회귀율을 관찰할 필요가 있다.
  • 벤더 측 수정이 롱테일 단계 진입: Kunlunxin, Ascend, MetaX, Moore Threads의 이번 기간 활동은「기존 연산자를 쓸 수 있게 수정」위주였고, 별도로 CPU 연산자 오이식 1회를 회수했다. 이는 백엔드 접속 후의 필연적 단계이며, 2.2의 1,454개 연산자 목록이 실제 칩에서 여전히 커버리지와 정밀도 격차가 있음을 보여준다.
  • 정보 측면은 상대적으로 잠잠: 44건의 뉴스 후보 중 유효한 것은 3건뿐, 신규 버전 릴리스 없음, 신규 저장소 생성 없음(신규 저장소는 모두 10-13~10-14 생성). 이번 기간 내용의 주체는 GitHub에서 나왔으며, 전형적인 「코드 활발, 발표 침묵」 모니터링 기간이다.
  • 한계 설명: 이번 기간 커밋 검색은 GitHub search의 total_count 기준(612건)이며, 커밋 URL 기준 중복 제거 후 건별로 저장소에 귀속시켰기에 일부 저장소는 페이지 간 중복으로 인한 ±1 오차가 있을 수 있다.
