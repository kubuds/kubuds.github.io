1.2 버전 측면: 2.3.0에 다섯 번째 레이어 CANN 9.2.1 추가, base 이미지는 의도적으로 FlagTree 미포함 (11-03)

날짜: 2026-11-03　출처: build-infra PR #1614 · build-infra PR #1615 · build-infra PR #1613 · community 2.2 릴리스 목록

  • base 레이어 신규 추가: #1614에서 base/ascend-cann9.2.1(aarch64 + ubuntu 24.04, 910B 전용)을 추가했습니다. CANN 9.2.1 toolkit, 910B ops 패키지, NNAL, 기존 /etc/profile.d/vendor.sh 환경 캡처를 포함하며, configs.yaml 행과 cann921 runner 오버라이드, verify 노드 별칭도 함께 보강했습니다. 198줄 추가, 5개 파일.
  • python 3.12를 선택한 이유: PR 본문에 두 가지 강한 제약이 명시되어 있습니다. flagos-pypi-ascend의 torch 2.13, torch-npu 2.13, torchvision 0.28, torchaudio 2.11 wheel은 cp312만 존재합니다. CANN의 set_env.sh는 자체 python 트리를 PYTHONPATH에 주입하므로, base 인터프리터는 런타임 venv와 완전히 일치해야 하며 그렇지 않으면 임포트 시 버전이 섞입니다. 이에 맞춰 triton은 3.6.0으로 고정하고 triton_ascend 3.6.0을 덧씌우며, numpy는 1.26.4로 고정했습니다.
  • FlagTree와 FlagCX를 의도적으로 제외한 이유: FlagTree는 아직 CANN 9.2.x용 버전 고정이 없고, 9.2.1에도 대응하는 flagcx wheel이 없습니다. 따라서 이 레이어에서는 flagtree, flagcx, env.app, deps_app을 모두 비워 두고, 빌드 순서를 base → FlagTree 없는 runtime → FlagTree builder → FlagTree wheel → runtime 갱신으로 변경했습니다. flagtree가 없으면 컴파일러는 triton으로 폴백합니다.
  • 버전 태그: #1615는 봇 커밋으로, 2.3.0 태그 아래 각 백엔드의 미작성 changelog 항목을 registry push_time 기준으로 날짜를 지정합니다. 이 항목은 ascend-cann9.2.1 레이어에 해당하며, 305줄 추가 5줄 삭제, 4개 파일로 이미지 내용은 변경하지 않습니다. 또한 #1613은 런타임의 FlagTree 버전 요청에 명시적 --index-url을 지원하도록 하여 위 “다회 빌드” 체인에 출구를 마련했습니다.
  • 릴리스 상태 점검: 31개 저장소 Release와 8개 저장소 Tag를 원자적으로 점검했으며, 모니터링 기간 내 새로운 Release 객체는 없었습니다. community 측 release/2.3/release-2.3.yaml은 여전히 404를 반환하고, release/2.2 매니페스트는 유지 중입니다. 이미지는 6개 레이어를 커버하지만 매니페스트 동결과 사이트 오픈 두 단계는 여전히 발생하지 않았으며, 이는 이전 회차 판단과 일치합니다.
  • 관찰 필요: base 레이어가 4개에서 6개로 확장되었으나 매니페스트는 그대로여서, 2.3.0의 “이미지 선행” 특성이 더욱 강화되었습니다. 이번 주에도 매니페스트를 동결하지 않으면 실제 릴리스되는 버전 내용이 2.3.0 계획과 괴리될 수 있습니다.

1.3 vLLM 0.28 라인 4개 백엔드 동일 마감: Tsingmicro, MetaX C550, Moore Threads MUSA, Ascend 디코드 그래프 (11-03)

날짜: 2026-11-03　출처: vllm-plugin-FL PR #642 · vllm-plugin-FL PR #554 · vllm-plugin-FL PR #575 · vllm-plugin-FL PR #646 · vllm-plugin-FL PR #676

1.8 융합 통신 연산자: RS+add+RMSNorm+AG 링 커널, FlagGems 및 SGLang 플러그인 진입 (11-03)

날짜: 2026-11-03　출처: FlagGems PR #8317 · sglang-plugin-FL PR #166 · FlagGems-sglang PR #279 · FlagGems PR #8347

  • 코어 설계: FlagGems #8317에 두 개의 「통신 + 정규화」 융합 Triton 코어를 추가했습니다(심사 중, 1403줄 추가, 3개 파일). fused_rs_add_rms_norm_ag는 단일 링 코어로 all_reduce(x)와 fused_add_rms_norm(x, residual)을 대체하여, 한 번에 reduce-scatter, 잔차 덧셈, RMSNorm 및 all-gather를 완료합니다. 랭크 r은 [r*chunk, min(T,(r+1)*chunk)) 행만 소유하며, 정규화는 이 행들에서만 수행되고 잔차는 분산 상태로 유지됩니다. gather=False일 때는 owner 단계 이후에 중지하여 RS + add + RMSNorm만 수행합니다. 함께 제공되는 fused_qkv_norm_ag는 반대쪽 끝을 처리합니다. 분산된 qkv 출력에 대해 q와 kv를 각각 정규화하고, rest(k_pe)는 그대로 전달하며, 링의 AG 절반만 실행합니다.
  • 링 구현: 데이터는 C개 채널에서 동시에 전송되며, 채널 c는 랭크 상의 하나의 링입니다. PPU 810E에서 pccl 28채널 그래프의 링을 직접 재사용하여 각 홉이 ICN 링크를 통과하도록 합니다. 매 전송 후 후속 노드에서 플래그를 한 번 증가시키고, 수신 측은 flag >= base + step을 기다립니다. 플래그는 증가만 하고 감소하지 않으며, 버퍼 패리티는 호출마다 토글되므로 전임자가 n+1번째 호출에 진입할 때 n번째 호출에서 여전히 읽고 있는 데이터와 충돌하지 않습니다.
  • 상위 통합: sglang-plugin-FL #166은 XuanTie 측에서 이 RS + norm + AG 융합 코어를 pure TP prefill의 선택 사항으로 만들었습니다(심사 중).   • 신규 칩 접속의 두 경로 모두 검증 완료: 비렌은 SUPA 백엔드로 TransformerEngine-FL에 진입했고(골격 선행, 하드웨어 검증 기록 없음), Moore Threads는 추론 플러그인과 텐서 라이브러리 두 라인에서 동시에 착수했으며, Iluvatar CoreX는 하루 10건의 전용 연산자로 연산자 생산 라인을 진행했습니다. 접속 속도는 더 이상 병목이 아니며, 검증 깊이가 핵심입니다—비렌의 백엔드는 현재 골격만 있을 뿐 칭웨이, MetaX와 동등한 하드웨어 게이트 기록이 없습니다.
  • 2.3.0은 여전히 이미지 선행: base 레이어가 이미 6개 레이어(CANN 9.2.1 포함)로 확장되었고, 런타임 이미지는 백엔드별로 푸시되며, changelog 날짜는 레이어별로 소급 기입되고 있지만 community의 release/2.3 목록은 여전히 404를 반환합니다. 연속 세 모니터링 기간 동안 목록 동결 움직임이 없었으며, 릴리스의 실제 내용과 계획 간의 괴리가 누적되고 있습니다.
  • 관찰이 필요한 세 가지: 첫째, release/2.3 목록이 언제 나타나는지가 2.3.0의 이번 달 내 릴리스 가능성을 결정합니다. 둘째, 0.32의 5건 어댑테이션이 언제 머지되는지가 목표 라인의 재차 연기를 결정합니다. 셋째, 융합 통신 연산자(RS+add+RMSNorm+AG)가 PPU와 SGLang의 파일럿에서 크로스 백엔드 범용 컴포넌트로 추상화될 수 있는지 여부입니다.
