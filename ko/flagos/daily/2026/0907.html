1.1 FlagGems-sglang: 챌린지 첫 대회 문제 연산자 병합——7개 SGLang Triton 연산자, 3개 팀, 벤치마크 및 참조 구현 일괄 반영(09-06)

Triton/Triton-TLE로 개발하고 다중 칩 통합 평가에서 평균 가속비로 순위를 매긴다. 대회 규칙에 따라 각 배치 심사 후 “공략” 영예를 얻은 팀은 윈도 내에 최적 코드를 규정 형식으로 FlagGems-sglang에 PR하고 CLA에 서명해야 하며, 코드 일관성은 수상의 필수 조건이다.

해석: 이 7개 연산자의 시맨틱 커버리지는 매우 전형적이다 — silu_and_mul(활성화 융합), causal_conv1d_fn / chunk_local_cumsum_scalar / merge_state(SSM/Mamba류 컨볼루션 및 상태 연산자), per_group_transpose / mrope_fused(mRoPE 그룹 전치와 융합), fused_moe_gemm(MoE 융합 GEMM)으로, SGLang의 실제 추론 워크로드(혼합 어텐션, MoE)와 일대일로 대응되어 대회 문제가 “실제 추론 업무에서 발췌했다”는 설정을 검증해 준다. FlagOS에 더 중요한 것은 커뮤니티 공동 구축 파이프라인의 첫 번째 폐루프이다: 대회가 8월 중순 개막한 후 약 3주 만에, 첫 성과물이 대회 규정에 따라 통일된 형식과 통일된 코드 규범으로 공식 저장소에 돌아왔고 메인테이너가 테스트/문서를 보완했다 — 「개방형 대회 문제→플랫폼 평가→명예 인센티브→공식 저장소 축적」이라는 연산자 집단지성 순환이 산출물을 내기 시작했으며, 또한 매 배치(이후 7일마다 1회 평가)마다 새로운 PR 머지 흐름이 생겨 FlagGems-sglang이 FlagSparse를 대체하여 “외부 기여 밀도”를 관찰하는 새로운 창구가 될 것이다(FlagSparse의 AlphaSparse 외부 큐는 이미 가동된 또 하나의 집단지성 채널이다, 09-05 데일리 리포트 참조). 또한 yzw1128이 제출한 silu_and_mul과 build-infra #763에서 iluvatar의 flag_gems silu_and_mul 블랙리스트가 이름이 같은 점에 주의하라(다른 저장소, 다른 문제 영역으로 순전히 우연의 일치다).

1.2 build-infra: 이미지 tag 기록 브랜치 per-backend 고유화, 시작 페이지는 납품 기록 기준으로 게이트 적용(09-06)

출처: #756(961c0fed), #759(8f012fd4)

  • #756(12:42): record_app_image_tag.py는 원래 모든 기록을 단일 공유 브랜치 auto/app-image-tag에 누적했는데, 역사적으로 남은 open 기록 PR(임의의 app/백엔드)이 있으면 rebase 충돌로 이후 모든 기록을 차단했다(mthreads-musa4.3.6의 기록이 run 34009399235로 한 번 실패한 바 있다) — 이를 auto/app-image-tag-<backend>-<app-key> per-record 파생 독립 브랜치로 변경하여 기록 간 결합을 해소했다.
  • #759(14:48): gen_data는 원래 configs의 deps_app key 존재 여부만으로 app 시작 페이지를 생성했는데, key는 검증 완료 이전에 추가되어(빌드를 트리거하기 위해) 검증되지 않은 백엔드(예: vllm0.20.2-iluvatar-corex4.4.0, deps_app은 존재하지만 launch_docs=false, cells 미검증)도 시작 페이지가 유출되어 모든 app 이미지에 들어갔다 — 이를 매트릭스 launch_docs 기록을 게이트로 변경하여 검증되지 않은 백엔드는 더 이상 시작 페이지를 생성하지 않는다.

해석: 두 건 모두 “납품 기록 시스템 자체의 신뢰도 복구”이다 — 전자는 기록 파이프라인의 단일 장애점(공유 브랜치 상호 충돌)을 제거하고, 후자는 검증 상태와 페이지 게시 상태의 탈동기화로 인한 거짓 양성을 제거한다(09-05 Cambricon의 “시맨틱 게이트 거짓 양성” 문제와 동원이인 다른 계층: 그때는 실행 검증 게이트 부재, 이번은 문서 생성 게이트 부재). 이런 메타 엔지니어링 수정이 2.2 “검증-tag 부여-기록” 주기에서 지속적으로 나타나는 것은 릴리스 감사 면이 계층별로 조여지고 있음을 보여준다.

1.3 FlagCX: UIL p2p hang 수정과 무가속기 CICD 게이트(09-06)

출처: PR #542(511cdace, taozhiwei), PR #568(8737bab4, MC952-arch)

  • #542(20:21 머지): [UIL] 통신 도메인이 2보다 클 때 p2p 행 문제를 수정 — PR에 완전한 unittest 재현(멀티 rank send_receive 시나리오)이 포함되어 있으며, UIL(통합 통신 계층)이 크로스 카드 토폴로지 확장 시의 수렴성 결함 수정에 해당한다. 통신 도메인(communication domain)이 2보다 크다는 것은 이 경로가 1대1 디버깅 시나리오가 아니라 멀티 카드 실제 클러스터 토폴로지를 대상으로 한다는 의미다.
  • #568(21:50 머지): [CICD] 무가속기 환경에서 API 테스트 건너뛰기 — CI가 GPU/가속기가 마운트되지 않은 runner에서 하드웨어 의존 API 테스트를 더 이상 실행하지 않아 거짓 실패/거짓 통과를 방지하고, 테스트 게이트가 실행 환경에 맞게 적응한다.

해석: FlagCX가 08-27에 FlagOS Enflame collective 전체 프로세스(#554)를 완료하고 v0.14.0-rc0.post1을 태그한 후, 이 모니터링 기간의 두 커밋은 각각 기능적 수렴 수정(p2p 다중 도메인 행)과 CI 엔지니어링화(카드 없는 게이트 자체 적응)입니다 — build-infra와 같은 리듬으로: 기능 확장은 잠시 보류하고 검증과 전달 품질을 우선시하며, 2.2 rc0 주기의 “검증-태그-기록” 마무리 특징에 부합합니다.
