1.2 런타임 2.3.0: vllm 애플리케이션 재빌드 승인 획득, 통합 태그 확정, AMD ROCm 7.2.4 기본 이미지 신규 추가(10-26)

날짜: 2026-10-26　출처: build-infra PR #1488 · PR #1504 · PR #1502 · PR #1505

  • 재빌드 승인(#1488): 20개의 vllm0.24.0 애플리케이션 changelog에 릴리스 예정 항목(사유 포함, 날짜 공란)을 추가하고, 푸시 시 changelog 게이트를 통과한 후에만 애플리케이션 이미지 재빌드를 허용했다. 사유는 런타임이 10-25에 2.3.0 스택으로 갱신되어 그 위에 빌드된 애플리케이션 이미지가 모두 만료되었기 때문이다. 항목별로 애플리케이션 이미지가 현재 무엇을 포함하는지 설명한다: 런타임의 컨테이너 시작 인자 두 개, 백엔드별로 버전을 고정한 flagcx 0.14.0, 그리고 venv 접두사.
  • 태그 수렴: 동일 PR의 두 번째 커밋은 네이티브 플러그인 태그를 이미지 태그에서 제거하고 통합 파서가 결정하도록 변경하여, 백엔드 접미사가 없는 통합 태그인 2.3.0-0.3.0이 성립하게 했다. 세 번째 커밋은 changelog와 schema 헤더에 reason 필드가 markdown으로 게시됨을 선언하여 여러 변경 사항을 목록으로 읽을 수 있게 했다.
  • 신규 백엔드(#1504): AMD ROCm 7.2.4 기본 이미지가 적용되었으며, 백엔드 키는 amd-rocm7.2.4이고, 베이스는 Ubuntu 24.04에 repo.radeon.com에서 직접 설치하는 ROCm 7.2.4이며 파일 저장소를 사용하지 않는다. 28개의 간결한 패키지만 설치하며, apt가 런타임 의존성을 해석한 후 총 94개가 된다. MIOpen, MIGraphX, rocm-gdb, rocprofiler-sdk, opencl은 명시적으로 제외한다. 리허설 중 Containerfile에 반드시 기록해야 할 두 가지 사실을 발견했다: amd 노드는 archive.ubuntu.com에 접근할 수 없으므로 ca-certificates가 존재하기 전에 Alibaba Cloud HTTP 미러로 전환해야 하며(HTTPS를 사용하면 핸드셰이크 실패), pin 파일은 버전 선호가 아니라 필수 항목이다.
  • 장애물 정리 두 건: 22:27의 #1502는 네이티브 플러그인 게이트가 동일 인터프리터 내에서 완료되도록 했고, 22:45의 #1503은 vllm 플러그인 태그를 sglang 문서 페이지에서 제거했으며, #1505는 백엔드 태그 대신 태그가 실제로 포함하는 플러그인 pin을 출력하도록 변경했다.
  • 판단: 이번 라운드의 모든 조치는 ‘릴리스 가능성’에 집중되었다—게이트, 이력 기록, 태그 형태, 기본 이미지. 10-25의 런타임 재빌드 승인과 연결해 보면, 2.3.0 파이프라인은 처음부터 끝까지 한 번 실행되었으며, 정식 태깅과 전체 백엔드 이미지 일괄 재배포만 남았다. AMD 백엔드 추가는 백엔드 매트릭스가 2.3 주기에서 수렴이 아니라 계속 확장되고 있음을 의미한다.

  • 생태계 측: Open3D-PIMC의 대외 확산이 지속 추진 중이며(2.1 참조), FlagOS의 차세대 3D 칩 주요 솔루션으로 명확히 자리매김.
  • 판단: Qingwei의 형태는 다른 멤버와 다르다. FlagOS 안에서 백엔드(TX8, TXDA)이자 새로운 하드웨어 형태(3D 적층, Open3D-PIMC)의 주도자다. 두 축은 현재 코드상 교차점이 없으며, 향후 Open3D-PIMC 백엔드가 FlagTree의 TX8 경로를 직접 재사용할 때 비로소 진정한 합류가 이루어질 것이다.

3.5 Enflame, Hygon, Iluvatar CoreX, Moore Threads: 네 백엔드 각각 구조적 변경 1건(10-26)

날짜: 2026-10-26　출처: FlagPrism PR #17 · Torch-FL PR #654 · Torch-FL PR #660 · FlagTree tags

  • Enflame: FlagPrism에 tops 헤더 파일 및 라이브러리 의존성 해석 반영 (#17, 16개 파일, 2,126줄), Enflame SDK의 헤더 파일 및 라이브러리 탐색을 암시적 방식에서 명시적 방식으로 전환; FlagAttention에는 Enflame 측의 융합 어텐션 연산자(fused_attnres) 1건이 심사 중.
  • Hygon: Torch-FL에서 DCU 런타임의 빌드 소스 수정 (#654) — DCU의 runtime_dir이 기존에 ABI 심(shim)만 배치된 디렉터리를 가리키고 있어 런타임 라이브러리가 32개의 스텁으로 링크되었고, 빌드는 통과하지만 import 시 즉시 미정의 심볼 오류 발생, 71개 파일, 1.1만 줄 변경; 같은 날 심사 중인 #627은 박싱이 활성화된 DCU 빌드에 실제 스트림을 연결.
  • Iluvatar CoreX: Torch-FL #660에서 Iluvatar 상의 bf16 GEMM이 호스트 실행으로 폴백되는 문제 수정 — 2048 정방 bf16 mm 실측 0.41 TFLOPS로 동일 머신 CPU의 0.54보다 낮으며, 동일 연산자의 fp16은 80.2, 벤더 자체 torch는 84.6; 근본 원인은 지원 판별에 bf16이 포함되지 않았고 mm과 addmm이 호스트 측에서 전치 가중치를 복사한 것. 수정 후 벤더 BLAS를 사용.
  • Moore Threads: FlagTree에서 MThreads 전용 태그 배포(0.7.1a1+mthreads3.6), FlagGems-vllm에 chunk_kda의 MThreads 최적화 반영 (#990), MUSA 백엔드의 TLE 캐시 영속화 변경은 지난주에 완료.
  • 판단: 네 업체의 공통점은 “작동은 하지만 느리거나 중간에 터지는” 문제를 수정한 것이지 새 연산자를 추가한 것이 아님.这类 결함은 외부에서 재현하기 가장 어렵고, 백엔드 매트릭스의 실제 완성도를 가장 잘 보여줌 — 벤더 측 제출은 여전히 자사 플랫폼의 정확성과 성능이 주를 이루며, 크로스 플랫폼 통합 시맨틱 작업은 여전히 FlagOS 메인라인이 추진.

4. 요약 및 트렌드 관찰

  • 2.3.0은 전체 파이프라인을 한 차례 완주했으나 태그는 아직 미배포: 런타임 게이트, changelog, 재빌드 승인, 버전 파라미터화가 10-23~10-25에 완료되었고, 10-26에 애플리케이션 계층 재빌드를 승인하며 태그를 2.3.0-0.3.0으로 수렴. “런타임 리프레시”에서 “애플리케이션 버전 추종” 단계는 통상 정식 릴리스에 바로 이어지므로, 이번 주가 여전히 핵심 모니터링 기간.
  • 백엔드 매트릭스는 수렴이 아닌 확장 중: AMD ROCm 7.2.4 기본 이미지가 새로 추가되어 2.3 주기에도 플랫폼이 계속 늘고 있음을 보여줌. 이에 대응하여 XuanTie는 BLAS1 보충, Qingwei는 RPM 패키징 연결, Kunlunxin은 디바이스 비트코드 보충 — 네 가지 사안은 수치 라이브러리, 패키징, 통신 세 계층에 속하며 모두 “연결한 후에야 필요한” 작업.
  • 수치 라이브러리와 학습 스택이 새로운 전장으로 부상: FlagBLAS가 한 번에 15개 BLAS1 연산자 그룹을 보충하고, FlagTrain이 일련의 연산자를 7개 백엔드에 배치하며 두 라인 모두 2.3 주기에서 가속. 추론 연산자의 한계 수익은 하락 중(FlagGems 이번 기에는 KernelGen 자동 생성 배치와 백엔드 튜닝 위주)이며 학습과 수치 라이브러리의 격차가 더 두드러짐.
  • 비전 방향 최초 구체화, 그러나 성능 근거 부재: FlagCV는 포지셔닝을 “Triton 구현 OpenCV 형태 비전 연산자 라이브러리, OpenCV CUDA 베이스라인 대标的”으로 규정하고 FlagTree에 연결. 현재는 설명과 골격만 있으며 벤치마크나 비 GPU 백엔드 데이터가 전무하여 가치 판단은 시기상조.
  • 리뷰 대역폭이 병목으로 부상: 커밋 37% 증가, 심사 중 23% 증가, 반영 18% 감소, 신규 오픈 18% 감소. 개발 측은 축적 중, 리뷰 측은 소화 중. FlagGems와 FlagTree 두 저장소의 심사 중 건수(52, 9)와 반영 건수(49, 4)의 격차가 가장 두드러지며, 이 두 저장소가 바로 2.3의 컴파일러 및 연산자 버전 소스.
  • 양자 스택은 시나리오 확산기 진입: 오류 정정 코드, 중성 원자, 열욕 세 가지 물리 시나리오가 동시 추진되며 여전히 4단계 증거 확보 방식으로 운영. 전체 조직 커밋의 약 60%를 계속 차지하지만 전기 대비 일평균은 3분의 2로 하락.
  • 정보 측면 연속 세 번째 모니터링 기간에 회원사 보도자료만 존재: 후보 12건 중 유효 2건, FlagOS 자체는 버전 릴리스, 신규 저장소, 대외 공지 없음. 콘텐츠 주체는 여전히 GitHub에서 나오며, 전형적인 “코드는 백엔드를 채우고, 전파는 노드를 기다리는” 모니터링 기간.
  • 한계 설명: 커밋 검색은 GitHub search의 total_count 기준(185건)이며, 병합 PR 검색(133건)과는 스쿼시 병합 및 인덱스 지연으로 기준 차이가 존재, FlagGems에서 반영 수(49)가 커밋 검색 수(28)보다 높은 것이 이에 해당하며 보고서 내에서는 반영 수를 기준으로 함; FlagQuantum의 109건은 병합 및 브랜치 동기화 커밋을 포함하며 109개의 기능 변경과 동일하지 않음; FlagTree의 0.7.1a1+mthreads3.6은 Release 목록과 Tag 인터페이스 양방향 확인 결과 순수 Tag이며 Release 설명 없음; 벤더 보도자료의 “코드 수정 불필요”, “논문 대비 동등 또는 초과” 등의 표현은 회사 기준이며 제3자 재현을 확보하지 못함; Qingwei 원고의 “20개 벤더, 30여 종 칩”은 대회 기준의 21개 벤더, 35개 칩과 불일치하며 본문에 귀속을 표기함.
