1.2 build-infra: Ascend 4라운드 하위 프로젝트를 22.04 자체 포함 builder로 이전, Tsinghua 그리고 Xiwang 당일 보완 (10-19)

날짜: 2026-10-19　출처: PR #1414 · PR #1418 · PR #1422 · PR #1417 · base 디렉터리

  • 핵심 문제: Ascend의 네 가지 휠은 원래 24.04 런타임 이미지에서 빌드되었으며, 생성된 libflagcx.so와 _C*.so가 GLIBC_2.38에 링크되어 번들의 22.04 물리 머신에서 바로 abort되었습니다. PR #1414는 각 행에 독립적인 ubuntu:22.04 빌더를 구성하여 다른 벤더 행과 동일한 채널을 사용하게 했고, glibc 하한을 2.35로 낮췄습니다.
  • 하나의 레시피로 네 개 행 서비스: ascend.mk는 -ltorch_npu -lascendcl -lhccl만 링크하며 특정 칩과 무관합니다. 그러나 툴체인 자체에는 이러한 링크 시점 의존성이 없고, libhccl.so와 <hccl/hccl.h>는 칩 ops 패키지에서 오기 때문에 레시피가 toolkit과 ops 패키지를 동시에 설치합니다(nnal/ATB 제외). 910b와 910c의 차이는 ops 설치 프로그램의 칩 토큰(builder.ops_product, 910b와 A3)을 통해 전달됩니다.
  • 검증 기준: SDK 하한은 import torch_npu(CANN 툴체인 라이브러리를 dlopen함)로 증명하며, import torch(해당 행에서는 순수 CPU)가 아닙니다. ASCEND_OPP_PATH, ASCEND_AICPU_PATH, TOOLCHAIN_HOME, LD_LIBRARY_PATH는 set_env.sh에서 /etc/profile.d/vendor.sh로 설정되며, 휠 빌드 시 source된 것과 동일한 파일입니다.
  • 같은 날 두 개의 신규 백엔드 보충: Sunrise(PR #1418, sunrise wheel의 22.04 자체 포함 빌더, 이어서 PR #1420에서 해당 휠을 22.04-clean으로 재배포 기록)와 Tsingmicro(PR #1422, tsingmicro wheel의 22.04 자체 포함 빌더). 이로써 base/ 디렉터리의 벤더 매트릭스는 nvidia(cuda12.8 / cuda13.3), ascend(cann8.5.0 / cann9.0.0, 910c 포함), cambricon(neuware4.4.3 / 4.7.2), enflame(tops1.9.10 / 1.10.6), hygon(dtk26.04), iluvatar(corex4.4.0 / 4.5.0), metax(maca3.7.2.1 / 3.8.1.3), sunrise(tangrt1.2.0), tsingmicro(tsm260610)로 총 9개 벤더입니다.
  • FlagTree 측 세 건: PR #1417은 Enflame 빌더를 추가하고 검증 단계를 데이터 기반으로 변경했습니다. PR #1419는 「빌드 시점에 Enflame 백엔드를 단정하는」 방식을 수정했습니다. PR #1421은 Enflame toolkit의 deb를 빌더 이미지에 미리 넣어 매 빌드의 다운로드 의존성을 줄였습니다. 또한 PR #1410은 pybind11 ABI를 실제 발행된 플러그인에서 읽어오도록 하고 리터럴로 하드코딩하지 않게 했으며, PR #1413은 실패한 plan이 빌드를 건너뛰지 않고 전체 run을 실패하게 했습니다.
  • 판단: 이 16건 중 기능 개발은 한 건도 없으며, 모두 「로컬에서 빌드 가능, 타깃에서 실행 가능」 사이의 간극을 제거하는 작업입니다. 10-16부터 10-18까지의 6개 백엔드 22.04 마감과 연결해 보면, FlagCX의 아티팩트 채널은 「백엔드별 패치」에서 「한 행에 한 백엔드, 동일한 22.04 레시피」로 전환되었습니다.

1.3 FlagQuantum: 405개 파일 병합으로 양자 스택 확장, M0 로드맵 확립 (10-19)

날짜: 2026-10-19　출처: PR #635 · PR #637 · PR #642 · 저장소

  • 규모: 23건의 커밋, 9건의 병합으로 당일 커밋 수 공동 1위인 저장소입니다.   • 트렌드 1: 아티팩트 채널의 통합이 기능 확장보다 선행. build-infra는 하루 16건의 커밋과 16건의 병합을 기록했으며, 모두 22.04 자체 포함 빌더에 집중되었다. Ascend 4세대 서브, XiWang, Qingwei가 같은 날 동일한 레시피에 편입되었고, base/ 디렉터리는 9개 벤더의 17개 베이스라인 이미지 매트릭스를 형성했다. glibc 하한을 2.38에서 2.35로 낮춘 것은 어떤 신규 연산자보다도 “휠이 사용자 머신에 설치될 수 있는지”를 더 직접적으로 결정한다. 이 단서는 10-16부터 10-18까지의 6개 백엔드 마무리와 연결되어 완전한 사슬을 이루며, FlagOS 2.2 릴리스 이후 첫 번째 체계적 보완으로 볼 수 있다.
  • 트렌드 2: 양자 스택이 프레임워크 초기 형태에서 범용 프레임워크의 경계 정의로 전환. FlagQuantum은 하루 405개 파일, 159개의 신규 공개名을 병합했으며, 동시에 M0~M4 로드맵으로 다섯类 하드웨어의 재사용 전제를 명확히 하고 Stable Core의 41개 익스포트를 불변으로 유지했다. 이 “서브패키지 확장, 코어 고정” 방식은 10-18 량즈윈(Liangzhiyun) 릴리스 시 FlagQuantum을 기술 기초 문서로 위치시킨 것과 일치한다——외부에 능력을 설명하기 전에 어떤 것이 안정적 인터페이스인지 먼저 명확히 한다.
  • 트렌드 3: 국산 연산력 측의 투입이 “연산자”에서 “벤치마크와 기초 라이브러리”로 이동 중. Hygon은 FlagBLAS에서 6정밀도 GEMM과 L1 지원을 보완했고; Iluvatar CoreX는 FlagDNN에서 등가 성능 베이스라인을 보완하고 master에 직접 푸시했으며; Enflame은 FlagTree에서 GCU300 베이스라인과 vLLM 벤치마크 워크플로를 구축했고; Moore Threads는 FlagGems, FlagTrain, FlagSparse 세 라인을 동시에 움직였다. 공통점은 모두 벤치마크로 직접 측정 가능하다는 것이며, 단순히 “특정 연산자를 지원한다”는 것이 아니다.
  • 트렌드 4: KernelGen이 희소 및 뷰 시맨틱의 마무리 단계에 진입. 병합 측의 _coalesce, ccol_indices_copy, _neg_view_copy와 심사 중인 10여 건의 희소 연산자(_sparse_mm 계열, coo/csr 인덱스 상호 변환, copy_sparse_to_sparse_)는 밀집 메인라인이 기본적으로 정리되었음을 보여준다. 동시에 Kunlunxin은 30건 심사 중으로 단일 백엔드 최대 큐를 구성했으며, XPU3의 어텐션 계열과 RNN 계열이 다음 배치로 병합될 주체이다.
  • 트렌드 5: 뉴스 면은 회의 후 소화 단계에 접어들었고, 정보 중심이 저장소로 회귀. 24시간 기간 내 유효 뉴스 1건(중화망 10-19 기술 해체, 7개 양자화 사례 보충), 컴포넌트명 직접 조회 연속 제로 히트, 분과 포럼 기조와 워크숍 내용은 아직 초고 미완성. 경험상 이러한 기간 후 1~2일 내에 분과 포럼의 2차 보도가 나오는 것이 일반적이며, 차기 관찰 포인트로 삼을 수 있다.
  • 차기 주목 사항: 첫째, FlagQuantum의 feat/m0-common-foundation 브랜치(10-19 16:47 생성)가 언제 PR을 올릴지; 둘째, FlagGems의 해당 희소 커널 심사 큐 병합 리듬; 셋째, build-infra가 “한 줄에 백엔드 하나” 레시피를 FlagTree와 Torch-FL 아티팩트 라인에 복제할지; 넷째, 대회 분과 포럼 기조 공개 여부.
