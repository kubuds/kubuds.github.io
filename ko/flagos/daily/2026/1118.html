  • 두 개의 정식 태그: FlagTree는 11-17 18:23에 0.7.1+ppu3.6을, 11-18 01:16에 0.7.1+enflame3.6을 생성했으며, 두 Release의 설명은 모두 한 줄 pypi 0.7.1+…뿐으로, 체인지로그가 아니라 PyPI에 게시되었음을 표시하는 태그이다.
  • 계보 변화: Pingtouge는 이전에 0.7.1.dev1+ppu3.6(개발 라인)에 머물러 있었고, Enflame은 이전에 0.7.0+enflame3.6에 머물러 있었는데, 두 커밋이 함께 이 두 백엔드를 0.7.1 정식 라인으로 끌어올렸다. 이로써 0.7.1 정식 버전은 ascend3.5, xpu3.6, ppu3.6, enflame3.6 네 개 백엔드를 포괄하며, 사전 릴리스 측은 여전히 a1 6개 백엔드와 a2 2개 백엔드가 병존하는 분할 출시 구도이다.
  • Enflame 세대 교체: build-infra #1852는 두 개의 퇴역 라인을 교체 라인으로 바꾸었다—enflame-tops1.9.10(Zixiao C200 및 S60)을 enflame-tops1.9.29로, enflame-tops1.10.6(L600)을 enflame-tops4.1.6으로 교체했다. 변경 사항은 Base Containerfile의 새 deb와 새 드라이버 패키지, configs.yaml의 torch-gcu 및 pyefml 의존성, build-config.yml의 runner 이름 변경(tops1106은 1.9.29로, tops416은 4.1.6으로), 그리고 backends.yaml에서 tops4.1.6을 해당 벤더의 default_for_vendor로 설정한 것에 반영되었다.
  • 하나의 심볼릭 링크: 4.1.6 이미지에 /opt/triton_gcu를 새로 추가했는데, 그 이유는 FlagTree의 toolkit.py가 이 경로로 컴파일러를 찾기 때문이다. 같은 커밋에서 topsaten 버전을 작업 브랜치의 3.8.20261111에서 Containerfile을 기준으로 한 4.1.20261111로 정정했다.
  • 통신 측 맞물림: FlagCX #712는 Enflame에 ECCL 디바이스 API 백엔드를 추가했다(디바이스 API 구현, 통신 traits, 플랫폼 traits, ECCL 및 TOPS 어댑터, 빌드 스크립트, +5629/-41, 21개 파일). 단일 머신 테스트 케이스 test_device_api_intra와 test_device_ir_intra는 통과했으며, 머신 간 테스트 케이스는 “구현되었으나 테스트되지 않음”으로 명시되어 있다. build-infra 측 #1854는 두 Enflame 라인의 flagcx를 0.14.1로 고정했고, #1870은 ECCL 버전을 라인별로 선언하여 두 tops 라인이 하나의 ECCL 번호를 공유하는 것을 피했다.
  • 일정 의미: #1852의 설명에는 후속 작업이 이 PR에 포함되지 않는다고 명시되어 있다—먼저 두 백엔드의 FlagCX 휠을 출시하고, 이어서 base에서 runtime 이미지로 진행하며, 애플리케이션 계층은 잠시 보류한다. 즉, Enflame의 이번 라인 교체는 현재 “컴파일러와 빌드는 준비 완료, 런타임 이미지는 출시 대기”라는 중간 상태에 있다.
  • 관찰: 라인 교체의 실제 비용은 버전 번호가 아니라 패키지와 심볼에 있다. /opt/triton_gcu 같은 경로 규약, topsaten 버전 번호가 어느 파일을 기준으로 하는지, ECCL 버전을 라인별로 선언하는 것은 모두 “동일한 코드가 여러 칩에서 실행된다”는 암묵적 계약이다. 하룻밤 사이에 세 곳이 동시에 조정되었다는 것은 이 백엔드 라인이 벤더 SDK의 추종자에서 커뮤니티가 자체 유지하는 빌드 노선으로 전환되고 있음을 보여준다.

날짜: 2026-11-17　출처: build-infra #1851 · build-infra #1863 · build-infra #1872 · vllm-plugin-FL #703

  • 오픈 범위: #1851은 nvidia-cuda13.3, amd-rocm7.2.4, ascend-cann9.2.1, iluvatar-corex5.0.1, thead-ppu2.1.0 다섯 개 라인에 deps_app.vllm0.32.0을 추가하며, 해당 애플리케이션 이미지 태그는 2.3.0-0.5.0.dev0_g814b6d3.d20261117로 통일되었다. #1863은 별도로 status_matrix.vllm0.32.0.yaml을 생성했으며, 다섯 백엔드 모두 미검증 상태이고 검증 스크립트의 VRAM 점유 파라미터를 0.6에서 0.4로 낮췄다(노드 VRAM 부족).
  • 하나의 하드 의존성: vLLM 0.32.0 라인은 0.5.0-dev 플러그인을 사용하는데, 해당 FlagGems 백엔드는 flaggems_vllm을 하드 import하면서도 이를 선언하지 않는다. 따라서 다섯 라인 모두 flaggems_vllm==0.3.0.dev20261117을 명시적으로 포함한다. 이 버전은 당일에야 각 벤더 인덱스에 릴리스되었다. nvidia 라인에는 numpy==1.26.4를 추가로 지정하는데, native 플러그인 휠의 설치 체인이 numpy를 2.x로 끌어올려 매트릭스 무결성 게이트를 트리거하기 때문이다.
  • Ascend 병목: #1872는 ascend의 changelog에 블로커를 기록했다. flaggems_vllm==0.3.0.dev20261117에는 Ascend용 V2 샘플링 export가 없으며, 0.5.0-dev 플러그인은 npu에서 import 시 무조건 install_ascend_v2_sampling_shims()를 호출하여 v2_apply_penalties, v2_apply_temperature, v2_gumbel_rng 세 심볼을 요구한다. 이 세 심볼은 FlagGems-vllm의 codex/ascend-v2-sampling 브랜치, 즉 아직 리뷰 중인 #1234에만 존재하며, 데일리 휠은 main을 빌드한다. 작성자의 결론은 명확하다. 더 새로운 데일리 패키지를 기다린다고 해결되는 문제가 아니며, Ascend 애플리케이션 이미지는 #1234가 머지될 때까지 기다려야 한다.
  • T-Head 병목: #1863은 thead 라인 검증 실패 원인이 플러그인 측 thead 벤더 적응 계층의 attention 구현 파일이 flash_attn_3._C를 하드 import하는 것인데 thead 런타임에 해당 모듈이 없기 때문이라고 설명하며, vllm-plugin-FL 측 수정이 필요하다고 밝혔다. 같은 날 #1868은 먼저 flash_attn_3를 thead의 vllm 0.32.0 애플리케이션 의존성에 추가했는데, 이는 “의존성 먼저 보충하고, 플러그인의 import 수정을 기다리는” 2단계 접근이다.
  • 기록된 태그: amd-rocm7.2.4, iluvatar-corex5.0.1, thead-ppu2.1.0, nvidia-cuda13.3 네 개의 애플리케이션 이미지 태그는 bot이 changelog에 기록했다(#1864, #1865, #1869, #1874). ascend 라인은 블로커 기록만 있을 뿐 태그는 없다.
  • 관찰: 애플리케이션 계층 오픈의 장점은 “실행 가능 여부”를 칸칸이 채울 수 있는 매트릭스로 분해한 것이다. 대가는 각 칸 뒤에 업스트림 브랜치가 매달려 있다는 점이다. 오늘 두 병목 모두 FlagOS 자체 코드 문제가 아니라 플러그인과 연산자 라이브러리 간의 심볼 계약 문제이며, 이런 문제는 매트릭스에 명시적으로 기록할 수만 있고 재시도로 덮을 수는 없다.

3.2 Ascend: 두 개의 단일 코어 융합 대형 연산자가 1.34배와 1.18배를 제시 (11-17)

날짜: 2026-11-17　출처: FlagGems-vllm #1286 · FlagGems-vllm #1287 · FlagGems-vllm #1239 · FlagTree #1637

  • MegaGate: #1286은 910B를 위해 FlagTree TLE 단일 코어를 추가하여 BF16의 MoE 라우팅 프로젝션과 전문가 선택을 하나로 융합함 — Cube 코어는 FP32 누산 라우팅 logits를 수행하고, Vector 코어는 스코어링, 선택적 보정 바이어스 및 그룹 선택을 수행하며, top-k 전문가 번호와 정규화된 라우팅 가중치를 반환함; prepare_mega_gate는 런처와 워크스페이스를 입력 형상, 라우팅 구성 및 NPU 스트림에 바인딩하고, 이후 매 호출마다 재사용함. 5개 모델 353개 형상에 걸친 평균 가속은 ACL Graph 1.336배, Eager 1.408배이며, 그중 DeepSeek V4 Flash의 106개 형상은 1.553배임.
  • MegaMHC: #1287은 mHC post, mHC pre 및 RMSNorm을 하나의 단일 코어로 융합하여 네 개의 잔차 스트림과 일반, 시프트 두 가지 실행을 지원함; 시프트 경로는 포함된 pre_mix를 사용하여 Cube가 다음 프로젝션을 계산하는 동시에 RMSNorm을 시작함. 63개 형상의 평균 가속은 ACL Graph 1.175배, 사전 바인딩된 컨텍스트의 Eager 1.182배이며, DeepSeek V4 Pro 단일 형상은 1.773배임; 사전 바인딩되지 않은 Eager는 0.648배에 불과하여, 이익이 순수 커널 연산이 아닌 런처와 워크스페이스 재사용에서 비롯됨을 보여줌.
  • 부수 사항: #1239는 mhc_pre에 mix-major 레이아웃을 적용하고 테스트를 정리함; #1637의 Triton 3.6.x 백엔드 이식은 이러한 TLE 단일 코어 유형에 컴파일러 기반을 제공함.
  • 관찰: 두 건 모두 “단일 코어 융합 + 컨텍스트 사전 바인딩”에 집중하고 있으며, 둘 다 ACL Graph와 Eager 두 가지 수치를 함께 제시함. Ascend에게 그래프 모드와 즉시 모드의 격차 자체가 제품 라인 정보임 — 동일한 커널이 두 모드에서 20% 이상 차이가 나므로, 배포 측에서 어떤 실행 방식을 선택하느냐가 이익에 직접 영향을 미침.

3.3 T-Head: INT8 MegaMoE가 영속 커널 하나로 전문가 병렬 전체 과정을 완료 (11-17)

날짜: 2026-11-17　출처: FlagGems-vllm #1274 · FlagGems #8526 · FlagGems-vllm #1280 · FlagTree 0.7.1+ppu3.6

  • 단일 커널 범위: #1274는 PPU 백엔드에 INT8 전문가 병렬 MegaMoE를 추가한다(+4691/-8, 10개 파일). 상시 상주하는 FlagTree/Triton 커널 하나 안에서 토큰 디스패치, 두 차례의 전문가 GEMM, SwiGLU, INT8 가중치 재양자화, 크로스카드 쓰기 되돌림과 병합을 완료한다. 입력은 INT8 활성값과 전문가 가중치에 FP32 스케일링과 라우팅 가중치를 더한 것이고, 출력은 카드 내 BF16이다. 호출자는 재사용 가능한 컨텍스트, 대칭 피어 버퍼, 스트림 배리어를 제공한다.
  • 스케줄링 전략: 8카드 워크로드는 전체 블록 디스패치로 처리하고, 대규모의 2카드 및 4카드 워크로드는 각 카드가 고속 경로를 충족할 때 부분 반환으로 처리한다. EP 그룹은 컨텍스트 초기화 단계에서 CUDA Graph 캡처보다 앞서 반환 레이아웃에 합의하며, 워크스페이스 정렬이 일치하지 않을 경우 전체 그룹이 라우팅별 반환으로 후퇴하여 각 카드가 동일한 피어 슬롯을 서로 다르게 해석하는 일을 피한다.
  • 당일 동반 변경: #8526은 T-Head의 GEMM 테스트 형상과 레이아웃 커버리지를 갱신하고, #1280은 PPU-ZW810E의 cooperative_topk를 최적화한다. 새벽의 0.7.1+ppu3.6 태그는 백엔드를 개발 라인에서 정식 라인으로 끌어올린다.
  • 관찰: 디스패치, 두 단계 GEMM, 활성화, 양자화, 쓰기 되돌림, 병합을 하나의 커널에 압축하면 다수의 중간 물질화와 시작 오버헤드가 줄어드는 이점이 있지만, 컨텍스트 상태와 피어 버퍼의 일관성을 호출자가 보장해야 하는 비용이 따른다. 이것이 이번 변경이 거듭해 “레이아웃을 캡처 전에 정렬한다”고 강조하는 이유이기도 하다.

4. 요약

  • 버전 라인: FlagTree 0.7.1 정식 라인은 하룻밤 사이에 Pingtouge와 Enflame을 보완했습니다(0.7.1+ppu3.6은 18:23, 0.7.1+enflame3.6은 다음 날 01:16). 정식 버전은 ascend3.5, xpu3.6, ppu3.6, enflame3.6 네 백엔드를 커버합니다. Enflame의 두 tops 라인은 같은 날 세대 교체되어 tops4.1.6이 해당 벤더의 기본이 되었습니다.
  • 빌드 라인: vLLM 0.32.0 애플리케이션 계층 다섯 백엔드가 동시에 개방되었고, 네 백엔드는 이미 이미지 태그가 기록되었습니다. Ascend는 V2 샘플링 심볼 부재(FlagGems-vllm #1234 심사 중)로 정체되었고, Pingtouge는 플러그인의 하드 import flash_attn_3로 정체되었습니다. 두 곳 모두 FlagOS 자체 코드 문제는 아닙니다.
  • 연산자 라인: FlagGems 71건 병합 중 55건은 MUSA 테스트 참조 정렬이며, 285B 모델 프로파일이 기준에 들어갔습니다. FlagGems-vllm 17건은 DeepSeek-V4.1 디코딩 블록 선택, Hygon INT8 출력 투영 및 각 백엔드 수정을 커버합니다. FlagGems-sglang은 batch12의 열일곱 연산자를 골격으로 만들고 16건의 경쟁 FP8 연산자를 병합했습니다.
  • 프런트엔드 라인: Torch-FL의 Ascend 네이티브 호스트 파일럿은 910C에서 27개 일관성 테스트 케이스를 모두 통과했지만, CI가 FlagTree 다운로드 실패로 재실행이 필요합니다. FlagCX는 Enflame ECCL 디바이스 API를 보완했고, MUSA 플랫폼 지원은 심사 중입니다.

  • 위험과 할 일: Ascend 애플리케이션 이미지는 #1234를 기다리고, Pingtouge는 플러그인 import 수정을 기다리며, Enflame 애플리케이션 계층은 FlagCX 휠과 런타임 이미지를 기다리고, Torch-FL의 CI는 재실행이 필요합니다. 이 네 항목은 모두 타인 브랜치나 후속 빌드에 있으므로 데일리 리포트는 “차단은 이미 기록됨, 다운스트림 대기”로 기록합니다.
