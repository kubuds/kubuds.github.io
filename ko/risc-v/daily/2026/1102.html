오늘의 핵심: Linux 7.4가 「빠른 비정렬 접근」을 런타임 탐지로 전환, 배포판 커널이 최대 11% 대역폭 이득 확보 가능 (10-30)

Linux 7.4의 RISC-V 아키텍처 변경이 메인라인에 병합되었으며, 그중 별도로 기록할 만한 최적화 하나: 소프트웨어 정렬 우회 판정이 컴파일 시점에서 런타임으로 이동했다.

이 최적화의 경로는 두 단계로 나뉜다. Linux 7.3에서 Tenstorrent가 제출한 변경은 「빠른 비정렬 메모리 복사를 지원하는 RISC-V 하드웨어를 위해 컴파일된 커널」이 소프트웨어 정렬을 건너뛰도록 했고, Tenstorrent 자체 측정에서 대역폭이 최대 11% 향상되었다. 그러나 7.3은 이 기능이 컴파일 시점에 켜져 있어야 하는데, 배포판 커널 하나가 여러 하드웨어를 지원해야 하고 그중에는 느린 비정렬 접근을 하는 칩도 늘 있기 때문에, 이 이점은 커스텀 커널에만 남고 일반 빌드에서는 누릴 수 없었다. 7.4는 판정을 HAVE_EFFICIENT_UNALIGNED_ACCESS에 걸어 런타임 프로브로 바꾼다. 하드웨어가 실제로 빠른 비정렬 접근을 지원하는 것이 감지된 경우에만 사용자 공간 복사가 소프트웨어 정렬을 건너뛴다. 이렇게 하면 배포판 RISC-V 커널과 다른 일반 빌드 모두 기본적으로 이 최적화를 적용할 수 있고, 구형 하드웨어를 위해 별도의 맞춤 이미지를 남길 필요가 없다.

같은 배치로 7.4에 병합된 RISC-V 변경에는 crash 핫플러그 지원, 일부 페이지 테이블 함수의 최적화 경로 적용, 컨텍스트 스위치 한 곳의 최적화, 「B」 확장의 hwcap 및 hwprobe 보고 진입, 그리고 Zic64b 확장의 보고 지원이 있다. 이 항목들은 하나씩 보면 모두 크지 않지만, 합치면 「커널이 RISC-V 플랫폼 역량을 파악해 스스로 스케줄링에 넘기는」 한 걸음이다. 특히 hwprobe 측 보고는 바로 런타임 프로브 같은 최적화의 전제다.

커뮤니티 논의에서 기록할 만한 판단이 하나 있다. Hacker News에서 한 독자가 빠른 비정렬 접근이 서버 CPU에만 해당하는지 물었고, 답변은 SiFive를 제외하면 거의 모든 업체가 지원하며 SiFive는 최신 세대 성능 코어에서만 지원한다고 지적했다. 이는 배포판이 이 최적화를 켠 뒤 실제 수혜 범위가 제품 포지셔닝이 아니라 칩이 hwprobe에 사실대로 보고하는지에 달려 있음을 시사한다.

날짜: 2026-10-30　출처: Phoronix: RISC-V Has A Nice Portable Performance Optimization With Linux 7.4, Hacker News 토론

RISC-V 100 리스트 동향

이번 점검(주말을 넘겨 지난 10-28 점검으로부터 나흘 만)에서 리스트에 실질적 변화가 발견되어, 사용자 기준에 따라 본문 앞쪽에 배치한다.

리스트 신규(크로스 아키텍처 · SPEC CPU2006과 RISC-V 채널 · SPEC CPU2006 각 한 건): 10-17｜샹산 컴파일러 팀(XSCC)｜XSCC 2.0 on 샹산 KMHv3 RTL 3GHz｜int 68.41, fp 76.95(speed/ref, Completed); 동일 컴파일러의 이전 기록(10-15, XSCC 2.0) 대비 int +0.8%, fp +0.5%. 이 기록의 날짜는 10-17로 이번 점검일보다 앞서며, 보충 등재로 리스트에 올랐다. 10-28 점검 당시 두 CPU2006 리스트의 1위는 여전히 10-15의 int 67.85, fp 76.54였다.

리스트에서 내려간 두 건: 크로스 아키텍처 · SPEC CPU2006의 07-27 기록 「LLVM 22.1.0 on 진뎨 K3 X100 2.4GHz」가 내려갔고, RISC-V 채널 · SPEC CPU2006의 08-05 기록 「XSCC 1.1 on 즈허 A210 C908 1.9GHz」가 내려갔다. 두 건의 하차와 한 건의 보충 등재가 동시에 일어난 것은 새 측정이라기보다 리스트 정리에 가깝다. 동일 컴파일러 기준의 +0.8%／+0.5% 차이도 노이즈 수준이므로 아키텍처 개선으로 단독 해석하기는 어렵다.

샹산 프런트엔드에 FtqPrefetchQueue 도입, iprefetch 리팩터링의 첫 단계(10-30)

6691번 PR은 샹산 프런트엔드의 이번 라운드에서 가장 큰 변경으로, 16개 파일, +471/−198이다. 변경의 핵심은 FtqPrefetchQueue를 새로 추가해 명령어 프리페치를 ICache-top에서 FTQ 측으로 끌어올려 통합 스케줄링하는 것이다.

기존 설계의 세 가지 문제가 아주 직설적으로 적혀 있다. 첫째, FTQ는 FDIP만 담당하고, memblock에서 오는 Zicbop 소프트웨어 프리페치 prefetch.i는 ICache-top이 처리하는데, 매 사이클 요청을 1개만 받을 수 있고 소프트웨어 프리페치를 항상 높은 우선순위로 두기 때문에 같은 사이클의 여러 prefetch.i 중 1개만 적용되고 나머지는 조용히 버려져 성능 이점이 기대에 못 미친다. 둘째, 밀집된 prefetch.i가 FDIP 요청을 막아 오히려 성능을 떨어뜨린다. 셋째, prefetchPipe는 prefetch.i 1개를 처리하거나 FDIP 1~2개를 처리하는데, 둘이 SRAM에서 충돌하지 않더라도 병렬로 처리할 수 없어 파이프라인 활용률이 낮다.

새 큐의 방식은 다음과 같다. 먼저 소프트웨어 프리페치 요청을 캐시해 손실을 완화하고, 다음으로 큐 빈자리와 현재 FDIP 거리에 따라 출열 소스를 선택해 블로킹을 해결하며, FDIP와 프리페치가 같은 사이클에 병렬 발사되도록 허용해 활용률을 해결한다. 저자는 또한 확장 포트를 남겨두었다. 추후 PDIP류 알고리즘의 결과를 동일한 큐에 직접 넣을 수 있다. 이는 프리페치를 ‘하나의 통로’에서 ‘하나의 계층적 스케줄링 리소스’로 바꾸는 개조로, 단순히 우선순위를 조정하는 것보다 장기적 해법에 더 가깝다.

날짜: 2026-10-30　출처: XiangShan #6691

샹산, 숨겨진 VBTB 브랜치에 대한 MBTB 할당 억제 수정 (10-30)

6750번 수정은 예측기 메타데이터가 서로를 억제하는 문제를 다룬다. VBTB는 예측 시 가장 먼저 히트한 브랜치 하나만 노출하지만, 학습 단계에서는 여전히 ‘숨겨진 브랜치’에 히트할 수 있다. 이 브랜치는 예측 시에는 보이지 않았으나 학습 히트로 인해 MBTB 할당을 억제하여, 결과적으로 같은 브랜치가 반복적으로 예측 실패하게 된다.

수정은 세 군데로 나뉜다. ‘예측 시 실제로 노출되었고, 학습 시에도 여전히 상주’라는 두 조건이 동시에 성립할 때만 VBTB 상주로 인해 MBTB 쓰기를 억제한다. 전체 NumWay+1개의 메타데이터 엔트리를 AlignBank에 전달하여 ‘VBTB 예측 히트’와 ‘SRAM 히트’를 구분할 수 있게 한다. 조건부 브랜치 페이로드는 실제로 taken일 때만 기록하는데, not-taken 해결 경로가 분기 목표가 아닌 순차 다음 PC를 운반하기 때문이다. 마지막 항목은 MBTB와 VBTB 모두에 적용되며, 카운터 학습과 IFU 무효화 요청(attribute=None)을 유지한다. 변경은 단 2개 파일, +33/−19에 불과하지만 ‘예측기가 복잡해질수록 메타데이터 기준을 더 정확히 맞춰야 한다’는 전형적인 수정에 속한다.

날짜: 2026-10-30　출처: XiangShan #6750

샹산, prefetch.i/r/w를 LSU 프리페치 연산으로 디코딩 (10-30)

6735번 수정은 소프트웨어 프리페치 명령의 처리 흐름을 바꾼다. prefetch.i, prefetch.r, prefetch.w가 디코딩 단계에서 LSU의 프리페치 연산으로 식별되고 CROB에서 제외된다. 이 단계는 6691번의 큐화 변경과 짝을 이룬다. 프리페치를 먼저 ‘일반 메모리 접근 명령’에서 분리해야만 FTQ 측 프리페치 큐가 독립적인 요청 소스를 가질 수 있고, 더 이상 load/store와 동일한 커밋 경로를 다투지 않아도 된다.

날짜: 2026-10-30　출처: XiangShan #6735

샹산 CI 성능 흐름에 lightSSS 활성화, GEM5 주간 테스트를 261013 구성으로 전환 (10-30)

6802번은 gsim 흐름에서 difftest 버전을 업그레이드하고 CI가 lightSSS를 활성화하도록 하여, 벤치마크와 검증이 동일한 스냅샷 메커니즘을 공유해 중복 빌드를 없앤다. 같은 기간 OpenXiangShan/GEM5의 1274번은 주간 XSCC 테스트를 261013 구성 프로파일로 전환한다. 두 변경 모두 인프라 유지보수에 속한다. 전자는 ‘오류 발생 시 빠른 재생이 가능한가’를, 후자는 ‘주간 테스트가 어느 버전의 컴파일러와 부하 조합으로 실행되는가’를 결정하며, RTL 동작은 바꾸지 않는다.

날짜: 2026-10-30　출처: XiangShan #6802, GEM5 #1274

difftest 이틀간 9건: MMA 백엔드가 FP8 곱을 cache word에 패킹 (10-30 ~ 11-01)

difftest는 사흘 동안 9건을 커밋했으며, 모두 MMA(행렬 곱셈 누산) 검증 성능을 둘러싼 것으로, 리듬상 한 차례 집중 공략이다.

가장 기술적인 커밋은 1023번이다. 인접한 FP8 곱 기록을 동일한 cache word의 하위 16비트와 상위 16비트에 넣어 레지스터를 절반으로 줄인다. 각 word는 짝수 lane으로 먼저 초기화하고, 디코딩 전에 두 반쪽 워드에 각각 마스크를 적용해 인접 부호 필드가 서로 간섭하지 않도록 보장하며, 길이가 홀수인 꼬리 블록도 같은 방식으로 처리한다. 1021번은 비교를 GPU로 옮긴다(11개 파일, +420/−90). DUT 스냅샷 업로드와 참조 계산을 분리하고, 활성 결과 행을 GPU에서 직접 비교하며, 성공 시에는 상태 바이트만 반환하고 불일치 시에만 참조 결과를 다운로드해 진단한다. 폴백 경로는 느린 SSE2 streaming-store 대신 memcpy를 사용한다. 연속 핫 슬롯을 재사용하고 CUDA 서비스에서 해당 구간을 직접 업로드한다. 각 접두사의 ready/enqueue 확인을 제거하면서도 LightSSS 세션 수명 주기를 유지한다. 1018번은 CUDA 전송, 계산, 결과 검증을 파이프라인화하고, 1017번은 LightSSS가 CUDA 백엔드를 지원하도록 하며, 1020번은 XDMA 중계 요청을 패킹해 지연을 줄이고, 1019번은 부호 있는 INT8 참조 리덕션을 단순화하며, 1016번은 연산자 슬롯의 연속 활성 접두를 재사용하고, 1004번은 Delta와 AXI 타이밍을 격리한다. 방향은 명확하다. 검증기는 더 이상 ‘정확히 계산하는 것’만이 아니라 ‘감당 가능하게 계산하는 것’까지 요구받는다.

Qwenputer, RV32IM을 Qwen3.5-4B 가중치에 컴파일하고 어텐션 상태를 RAM으로 사용 (10-30)

개발자 Divyansh Agrawal이 10-22에 공개한 실험 모델 Qwenputer가 10-30 중국 매체의 보도를 통해 대중의 시야에 들어왔습니다. 방식은 RV32IM 명령어 집합과 확장을 Qwen3.5-4B의 가중치에 「컴파일」하고, 모델 자체의 Gated DeltaNet 상태를 정밀 주소 지정이 가능한 RAM으로 활용하여 순방향 전파에서 실제 프로그램을 실행하는 것입니다. 훈련이 필요 없으며 컴파일러가 각 가중치를 직접 작성합니다. 어텐션 헤드는 조회 테이블 역할을 하고, 피드포워드 유닛은 룩업 테이블로 산술을 구현하며, DeltaNet 헤드가 메모리를 보유합니다.

검증 가능한 이점은 정밀 산술에 집중됩니다. 대정수 곱셈은 원본 55.0%에서 97.5%로, 대정수 나눗셈은 72.5%에서 97.5%로, 덧셈·뺄셈은 87.5%에서 97.5%로, 여러 번의 곱셈·나눗셈이 이어지는 더 긴 체인은 90.0%에서 100%로, 합성 정수 산술은 75.0%에서 97.5%로 상승했습니다. 장정수 벤치마크 NUPA는 48.6%에서 100%가 되었습니다. 프로젝트 자체 설명에 따르면 이 CPU는 공식 RISC-V 테스트를 통과했고 약 1,800만 개의 명령어를 연속 실행하는 동안 오류가 없었습니다. 또한 실험적으로 「모델 내 파일 시스템」을 구현하여 GDN 상태에 최대 512개의 파일, 약 5.3만 토큰을 저장합니다.

대가도 분명합니다. 모델 크기는 약 18.8GB로 커졌고(원본의 두 배에 가까움), CPU 명령어 하나마다 여러 토큰을 생성해야 하며, 원래 밀리초 수준이던 계산이 수 초로 늘어날 수 있고, 실행에는 전용 드라이버가 필요하여 일반 모델처럼 직접 로드할 수 없습니다. 프로젝트는 Hugging Face와 GitHub에 오픈소스로 공개되었으며, 24GB VRAM을 갖춘 단일 그래픽 카드에서 실행할 수 있습니다. 이 소식이 RISC-V 생태계에 갖는 의미는 성능이 아니라 「RISC-V가 결정론적 실행 계층으로서 또 다른 시스템에 의해 차용되었다」는 점입니다. 즉 RV32IM이라는 극도로 간결한 ISA가 이기종 캐리어에 형식적으로 내장되기에 적합함을 입증했습니다.

Nuclei, Nuclei Studio VS Code IDE 프리뷰 버전 발표 (10-30)

Nuclei는 10-30 선전에서 Nuclei Studio VS Code IDE를 발표했다. 공식 개발 도구가 이제 Eclipse와 VS Code 두 가지 형태를 갖추게 되었다. 현재는 Windows 개발자 프리뷰 버전 0.1.0이며, 중영문 인터페이스로 VSIX를 통해 기존 VS Code(1.134.0 이상 요구)에 설치되며, 이미 설치된 확장과 충돌하지 않는다. 하위 기반은 여전히 Nuclei Studio IDE 2025.10에 의존한다.

호환 전략은 「재작성 없이 최대한 그대로 이식」이다. VS Code 버전은 Eclipse 버전 프로젝트를 바로 가져올 수 있고, cproject 호환 처리가 내장되어 있어 열기만 하면 개발할 수 있다. 새 프로젝트 마법사는 Eclipse 버전과 동일하며(벤더, SoC, 개발 보드, SDK 선택), SDK와 BSP는 여전히 NPK 패키지로 배포되어 두 버전 간에 교환이 가능하다. 디버깅은 OpenOCD, J-Link, QEMU, NucleiModel 네 가지 방식을 지원하며, 모두 CDT gdbtarget을 통해 처리되고 브레이크포인트, 단계 실행, 변수, 호출 스택, 메모리 및 주변장치 레지스터 뷰, 시리얼 모니터, 디스어셈블리가 갖추어져 있으며 Live Watch가 새로 추가되었다. AI 측면에는 장벽이 없다. 일반 AI 프로그래밍 어시스턴트는 설치 즉시 사용할 수 있고 Kimi, GLM, DeepSeek, Qwen과 호환된다. 공식 데모에서는 Kimi Code로 @helloworld를 통해 프로젝트를 인계받아 한 문장으로 CoreMark 프로젝트를 AES-256-CBC 데모로 바꾸고, 이어서 QEMU에서 바로 디버깅하며 시리얼로 PASS를 출력한다. 로드맵에는 Linux 및 macOS 지원, profiling, 코드 커버리지, ETrace, flash 프로그래밍, 더 많은 AI 어시스턴트가 나열되어 있다.

국내 RISC-V 개발자 생태계에 있어 이 단계의 실질적 의미는 「진입점 이동」이다. Eclipse의 느린 시작과 무거움이 오랜 불만이었는데, VS Code 측에서는 로컬 또는 클라우드 모델을 손쉽게 연결할 수 있다. 툴체인 문서도 2026.10 릴리스에 맞춰 동시에 갱신되었다. xlmodel 문서, 툴체인 문서, QEMU XEC 이더넷 가이드 영문화, Studio의 npk／gdb trace／빅엔디안 디버깅 설명, 그리고 xxlvfbf／xxlvw／xxlvqmacc 사용자 정의 확장 문서 영문화로 총 5건이다.

Sophon LLM-TPU, InternVL3／LLaMa3 지원 및 Qwen3-ASR 디코딩 열화 수정 (10-30)

LLM-TPU에 178번(InternVL3, LLaMa3 지원 및 Qwen2_VL 최적화)과 182번이 병합되었다. 후자는 기록할 만한 실제 결함이다. forward_next가 lm_head의 출력을 d2d를 통해 embed_cache의 input_ids로 복사한다. --do_sample이고 lmhead_with_topk=false일 때 lm_head는 전체 [1,151936] logits(607232 바이트)를 출력하는데, 이를 4바이트 token-id 버퍼에 복사하면 각 디코딩 단계에서 임베딩 조회가 손상되어 출력이 반복되는 쓰레기 토큰으로 열화된다(예를 들어 language Chinese<asr_text>가 languagelanguage...로 변함). 수정 방법은 해당 분기에서 greedy_head의 token_id(4바이트)를 대신 입력하도록 하여 Qwen2_VL의 forward_next와 정렬하는 것이다. 작성자는 CV84X6와 1684X 두 보드에서 HF와 토큰별로 비교해 일치함을 확인했고, 변경을 롤백하면 원래의 쓰레기 출력이 재현되어 인과관계를 확인했다.

sophon-tools 업데이트도 한 건 있다. se-rag-core가 상태 표시를 24시간 자동 갱신으로 바꾸고 버전을 1.5.4로 올렸다. 같은 모니터링 기간에 sophgo의 libsophon, middleware, osdrv, linux_5.10, build, sophpi, sophon-tools 등 10개 저장소가 10-31 같은 분에 일괄 푸시되었는데, SDK 측의 일괄 동기화로 보이며 개별 기능 설명은 확인되지 않았다.

5. 요약 및 트렌드 관찰

1. 커널 측 키워드가 ‘지원’에서 ‘하드웨어 능력에 따른 스케줄링’으로 전환. Linux 7.4는 빠른 비정렬 접근 판정을 컴파일 시점에서 런타임으로 옮겼다. 7.3 시대에는 커스텀 커널에만 남길 수 있었던 최적화를 이제 배포판 커널이 기본으로 포함할 수 있게 되었으며, Tenstorrent 자체 측정 기준 대역폭 이득 상한은 11%다. 같은 배치로 병합된 hwcap／hwprobe의 ‘B’ 확장과 Zic64b 보고는 바로 이런 런타임 결정의 데이터 소스다. 국내 여러 RISC-V 배포판에는 제로 코스트 이득이지만, 전제는 칩이 hwprobe에 사실대로 보고하는 것이다. 하드웨어 업체가 능력을 빠짐없이 보고하는 것이 마이크로아키텍처 최적화를 한 번 더 하는 것보다 사용자가 즉시 혜택을 보는 길이다.

2. XiangShan 프런트엔드가 ‘프리페치 큐화’ 단계에 진입. 6691번 PR은 iprefetch를 ICache-top의 ‘사이클당 1개’에서 논리적으로 FTQ로 끌어올렸다. 손실과 블로킹을 먼저 해결하고, PDIP 같은 알고리즘은 그다음이다. 함께 들어간 MBTB／VBTB 수정은 병목이 이미 ‘명령어 인출 대역폭’에서 ‘메타데이터 정밀도’로 옮겨갔음을 보여준다. 두 흐름을 합쳐 보면 프런트엔드 최적화는 버퍼 추가에서 ‘프리페치를 1급 스케줄 가능 자원으로 취급하기’로 이동 중이며, 이런 변경의 이득은 장기 부하로만 검증되므로 단기 벤치마크 점수는 좋지 않을 수 있다.

3. 차분 검증이 가속기 연산자에 성능 비용을 지불하기 시작. difftest 사흘간 9건 모두 MMA를 둘러싼다. FP8 곱셈 패킹, GPU 측 비교, CUDA 파이프라이닝, XDMA 중계 패킹, LightSSS의 CUDA 백엔드 지원. RISC-V AI 코어가 양산으로 가려면 검증 처리량이 연산자 복잡도를 따라가야 하며, 그렇지 않으면 ‘맞게 계산함’이 ‘다 계산하지 못함’이 된다. 이 변경 묶음은 개별 건의 이득보다 방향성이 기록할 가치가 있다.

4. 툴체인 양측이 동시에 기준선을 정함. openRuyi가 llvm23을 도입하고 riscv64-openruyi-linux 트리플의 기본 ISA를 RVA23U64로 정했다. Nuclei는 IDE를 Eclipse에서 VS Code로 옮기고 xlmodel, 툴체인, 빅엔디언 디버깅 문서를 2026.10에 맞춰 동기화했다. 전자는 ‘기본으로 어떤 코드를 생성하는가’를, 후자는 ‘개발자가 어디로 들어오는가’를 정하며, 둘 다 장주기 결정이라 단기에는 효과가 보이지 않지만 향후 1~2년의 기본 선택에 영향을 준다.

5. 국내 측 이번 모니터링 기간 산출은 SuanNeng과 Nuclei에 집중, 노선은 보드에서 시스템 스택으로 상향. SuanNeng의 실질 작업은 모델 지원과 디코딩 퇴화 버그 하나의 수정이다. logits를 4바이트 token 버퍼에 복사해 매 스텝 디코딩이 룩업 테이블을 깨뜨리는 문제로, 이런 결함은 실제 기기에서 토큰 단위 비교로만 찾아낼 수 있다. Nuclei는 툴체인 진입점을 VS Code로 바꾸고 AI 어시스턴트 연동까지 보완했다. XuanTie와 ESWIN은 모니터링 기간 내 공백이었고, SpacemiT는 Bianbu AgentOS 우산 저장소와 로봇팔 제어 프레임워크를 동시에 추진했다. 한 회사가 ‘엣지 agent 런타임’과 ‘로봇팔 캘리브레이션／진단／기구학’을 나란히 밀고 있다는 것은 RISC-V 소프트웨어 스택의 무게중심이 드라이버와 문서에서 납품 가능한 시스템 계층으로 옮겨가고 있음을 뜻한다. 이번 뉴스 측은 얇은 편이다. 중영문 쿼리 중복 제거 후 실질 신규는 Linux 7.4, Qwenputer, Nuclei Studio 세 건뿐이고, 나머지는 주가 기사, 소비자 가전, 구문 재게시다. 오픈소스 측이 여전히 본체다.
