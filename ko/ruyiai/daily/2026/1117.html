오늘의 핵심: tilelang-riscv #6 머지, RISC-V 백엔드 기본 경로를 buddy-opt로 변경 (11-16)

날짜: 2026-11-16　출처: PR #6, 머지 커밋 2204c7e

11-16 14:56, tilelang-riscv가 #6 “RISC-V 백엔드 기본값을 buddy-opt로 변경하고 BOSC와 GEMM 두 예제 보충”을 머지했다. 22개 파일, +835 −284, 두 건의 커밋: 11-04의 “buddy-opt를 기본으로 선택하고 두 툴체인 루트 분리”, 11-13의 “예제 보충, 문서 수정”. 이는 해당 저장소가 11-03 #5 머지 이후 첫 변경이며, 저장소에는 현재 여전히 main 브랜치 하나만 있다.

toolchain.py에서 변경된 골격은 (+62 −4)이다. Buddy와 LLVM은 각각 독립적인 툴체인 루트 디렉터리를 가지며, TILELANG_RISCV_OPT로 옵티마이저를 명시적으로 재정의할 수 있다. 옵티마이저 선택은 RISC-V 컴파일 캐시 키에 기록된다(kernel_cache.py +4). 이 항목은 표면적인 “기본값 교체”보다 더 실용적이다. 이전에는 옵티마이저를 교체한 후에도 오래된 캐시 산출물이 적중할 위험이 있었으나, 이제 캐시 키에 옵티마이저가 포함되어 “어떤 툴체인을 사용하는가”를 검색 가능한 빌드 차원으로 만든다.

예시에는 두 가지 유형이 추가되었다. examples/riscv/gemm은 호스트 머신의 FP16 GEMM(gemm.py +47)이고, examples/riscv/bosc는 독립적으로 빌드 가능한 BOSC INT8 GEMM 펌웨어(build.py +190, launch.c +122, env.sh 및 README)이다. 문서 측에서 가장 큰 변경은 docs/get_started/BuildOnSG2044.md(+55 −178)로, 단계별 수작업 방식에서 이식 가능한 경로와 간소화된 사용법으로 바뀌었다. 테스트도 세 가지가 보강되었다. 툴체인 테스트 +126줄, 컴파일 캐시 테스트 +29줄, 적응 파이프라인 테스트 +45줄이며, 모두 testing/python/riscv 디렉터리에 있다.

오늘의 핵심: triton과 buddy가 같은 날 툴체인을 건드리다, LLVM 분리 및 dump() 복원 (11-16)

날짜: 2026-11-16　출처: triton-riscv PR #123, buddy-mlir PR #1062, triton-riscv PR #115

11-16 18:14, triton-riscv는 #123 “백엔드 툴체인을 Triton의 LLVM에서 분리”를 열었다. 문제는 설명에 적혀 있다. CPU 백엔드는 libtriton.so에 어떤 C++도 추가하지 않고, pass는 전부 프로세스 외부의 triton-shared-opt를 사용하지만, add_triton_plugin이 여전히 MLIR 라이브러리 및 그 LLVM을 libtriton.so에 링크시키므로, 백엔드 툴체인은 Triton 자체 컴파일 시점의 LLVM 하나만 사용할 수 있었다. 변경 방식은 TRITON_SHARED_BUILD_CPU_BACKEND를 끄고, llvm-hash.txt를 새로 추가하여 LLVM 패키지를 별도로 고정하는 것이다. libtriton.so는 Triton 소스와 일치하는 LLVM을 사용하고, triton-shared-opt는 Triton과 함께 빌드되며, buddy-opt／buddy-translate／buddy-llc／opt／llvm-objdump는 buddy release를 사용하며, 서로 텍스트 IR만 교환한다. RISC-V의 +v와 +xsmtime은 llc에만 필요하므로, Triton이 의존하는 LLVM이 더 이상 RISC-V 패치를 짊어질 필요가 없다. 세 파일, +16 −2; llvm-hash.txt는 잠정적으로 nightly/v0.1.4.dev20261103에 고정되며, libtriton.so에 플러그인이 하나 줄어드는 것 외에는 빌드 산출물이 변하지 않는다.

같은 날 이후(11-17 01:23), buddy-mlir는 #1062 “Build LLVM with dump() support”를 열었다. LLVM 패키지는 -DLLVM_ENABLE_ASSERTIONS=OFF로 빌드되는데, MLIR／LLVM의 dump()는 어서션을 켜거나 LLVM_ENABLE_DUMP일 때만 정의되므로, 다운스트림에서 호출하면 링크에 실패한다. PR에는 실증이 제시되어 있다. mlir::Operation::dump()는 nightly/v0.1.4.dev20261103 패키지에는 있고, nightly/v0.1.4.dev20261113 패키지에서는 사라졌다. Triton이 바로 그런 다운스트림이다. NDEBUG를 켜면 헤더에 선언조차 없고, 켜지 않으면 링크가 되지 않는다. 패치는 LLVM_ENABLE_DUMP=ON 한 줄만 추가하여 Release 빌드를 유지한다.

두 사건은 같은 지점을 가리킨다. buddy의 LLVM 패키지는 이미 triton-riscv의 기본 업스트림이며, nightly 패키지 하나만 교체해도 다운스트림 컴파일이 막힐 수 있다. Renovate의 #115는 의존성을 정확히 nightly/v0.1.4.dev20261113에 고정했으며(11-16 21:40에도 업데이트가 있었다), #1062가 들어가지 않으면 이 고정점은 계속 문제를 일으킬 것이다.

2.1 openRuyi, Go 1.27에 Zvk AES 백포트(11-16)

날짜: 2026-11-16　출처: 커밋 6592b995

11-16 14:21, 패키징 저장소에 SPECS: go: Backport SHA-2 AES optimization 커밋이 올라왔으며, 새 패치 1005-release-branch.go1.27-crypto-internal-fips140-aes-bl.patch(468줄)가 추가되고 go.spec에 두 줄이 동시에 추가되었다. 설명 문구는 매우 직설적으로 적혀 있다. Go master의 Zvk 기반 AES 지원을 1.27 릴리스 브랜치로 백포트한다는 내용이며, 커밋 작성자는 Julian Zhu이다.

Zvk는 RISC-V의 벡터 암호화 확장군이다. 이 패치는 crypto/internal/fips140/aes의 block 루틴을 보완하여 riscv64에서 AES가 순수 스칼라 구현 대신 벡터 명령어를 사용할 수 있게 한다. 활성화 여부는 런타임의 Zvk 감지에 따라 결정되며, 해당 확장이 없는 코어는 여전히 기존 경로를 사용한다. 지난주 패키징 저장소는 Go를 1.27.4로 올리고 30여 개의 Go 패키지를 보완한 바 있으며, 이번 커밋은 버전이 확정된 후 성능을 보완하는 것으로 “먼저 적응, 다음 최적화”의 두 번째 단계에 해당한다.

2.2 linux와 linux-lts, 같은 분에 patchset과 config 갱신 (11-16)

날짜: 2026-11-16　출처: linux-lts 커밋 33a1ed14, linux 커밋 ff744f31, kernel-team-tools tag

11-16 14:34, 두 커밋이 같은 분에 올라왔으며 각각 SPECS: linux-lts: refresh patchset & refresh config와 동일한 이름의 linux 버전이다. linux-lts 커밋은 3줄 추가 3줄 삭제로 patchset과 config 참조만 교체했으며, 버전 기준선은 변경되지 않아 여전히 linux 7.3.4와 linux-lts 6.18.63이다.

3. 벡터 확장과 연산자 최적화

3.1 +zvfbfmin이 기본 특징 문자열의 필수 요소가 되다 (11-16)

날짜: 2026-11-16　출처: PR #117

#117의 설명에는 기록해 둘 만한 세 가지 경계가 있다. 첫째, Zvfbfmin이 없으면 LLVM은 확장 가능한 bf16 벡터에 대해 load와 convert조차 내리지 못하고, llc가 곧바로 Scalarization of scalable vectors is not supported를 보고한다. 둘째, buddy-mlir의 lower-vir-to-vector는 확장 가능한 bf16 벡터를 보존하며 대상이 Zvfbfmin을 가지고 있다고 기본 가정하므로, 이 확장이 없으면 다운스트림에서 llc 단계에서 전체 배치가 실패한다. 셋째, 추가하면 변환이 vfwcvtbf16.f.f.v와 vfncvtbf16.f.f.w를 거치게 되는데, 즉 bf16과 fp32 사이의 확장/축소 변환을 벡터 유닛에 맡기는 것이다.

프로젝트가 지원하는 RVV 대상(SpacemiT K3, SOPHGO SG2044)은 모두 이 확장을 갖추고 있다. 없는 코어는 TRITON_RISCV_LLC_FEATURES로 기본 특징 문자열을 덮어쓸 수 있다. DEFAULT_MARCH는 변경되지 않았는데, 이는 GCC 링크 단계만 구동하며 GNU as 2.42는 zvfbfmin을 인식하지 못하기 때문이다. +zvfbfmin으로 컴파일된 오브젝트는 여전히 링크될 수 있다.

날짜: 2026-11-17　출처: VecIntrinBench, IntrinTrans, FBGEMM (RuyiAI fork)

6. 동향 관찰

6.1 툴체인 경계의 재획정: 하나의 LLVM으로 모든 것을 커버할 수 없게 되다

triton-riscv #123과 buddy-mlir #1062는 같은 날의 양면입니다. 전자는 백엔드 툴체인을 libtriton.so에서 분리하여 llvm-hash.txt로 LLVM을 별도로 고정하고, 후자는 LLVM_ENABLE_ASSERTIONS=OFF로 꺼졌던 dump()를 복원합니다. 두 가지를 합치면 RuyiAI 라인은 더 이상 “하나의 LLVM으로 모든 것을 해결한다”고 가정하지 않는다는 것을 보여줍니다: Triton 자체 내장, buddy 배포판, 백엔드 llc가 각각 한 부분씩 담당하고, 인터페이스는 텍스트 IR로 수렴됩니다.

6.2 컴파일러 선택이 빌드 차원으로 전환

tilelang-riscv #6은 buddy-opt를 기본값으로 설정하고 동시에 옵티마이저를 캐시 키에 기록합니다. 이는 “기본값 변경”보다 중요합니다: 옵티마이저가 캐시 키에 들어가면 동일한 kernel이라도 서로 다른 툴체인에서의 산출물이 서로 오염되지 않으며, 툴체인 전환도 “환경 변수를 바꿔가며 시행착오”에서 “명확한 빌드 파라미터”로 바뀝니다. 예제에 BOSC와 GEMM을 추가한 것은 이 경로에 재현 가능한 두 개의 검증 지점을 부여한 것입니다.

6.3 배포판이 RISC-V 전용 확장을 본격적으로 수용

openRuyi의 이번 주 움직임은 확장에 집중되어 있습니다: Go에 Zvk AES 백필, triton 휠 기본 +zvfbfmin 포함, 커널 patchset과 config가 하루에 두 번 갱신됨. 이들은 범용 업스트림에서 자동으로 커버할 수 없는 부분이며, 배포판과 툴체인 유지관리자가 항목별로 보완해야 합니다. RVA23 이후 차별화 지점은 “실행 가능 여부”에서 “벡터와 암호화 확장을 사용할 수 있는지”로 이동하고 있습니다.

6.4 일간 정보 면은 계속 공전

공식 홈페이지는 움직이지 않고, ruyiai-daily는 9일째 단절, 외부 뉴스는 검색 결과 제로이며, 이번 호의 모든 소재는 네 GitHub 조직의 커밋과 PR, 그리고 포럼의 두 게시물에서 나왔습니다. 이러한 상태에서 보고서의 판단 가치는 주로 뉴스 건수보다 커밋 내용에 대한 이해에 달려 있습니다 — 릴리스 노트가 비어 있는 triton 정식 버전은 특히 그러하며, tag가 가리키는 커밋을 읽으러 돌아갈 수밖에 없습니다.
