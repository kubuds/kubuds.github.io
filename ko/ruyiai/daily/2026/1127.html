오늘의 핵심: triton-riscv PR #135 병합, CPU lowering과 matmul이 VIR로 통일 (11-26)

출처: PR #135.

11-26 17:41, PR #135가 triton-riscv 메인라인에 병합되었다. 제목은 “Unify standard CPU lowering and matmul through VIR”. 작성자 WuXintong123, 12개 커밋 포함. 2개 파일 변경, 255줄 추가, 124줄 삭제.

지난 보고서에서 이 PR이 여전히 심사 중이었으며, 브랜치에 이미 병합된 #129가 포함되어 메인라인과의 차이는 backend/compiler.py만 남아 있었고, 이번에 해당 차이 전부가 반영되었다.

변경은 다섯 곳에 집중되었다. RVV 벡터 폭은 타깃 특성 중 가장 큰 +zvlNb에서 유도하도록 변경, 기본값 128비트. 동시에 명시적 target_vector_bits도 허용. 표준 파이프라인에서 masked store를 벡터화하고, crop, transpose 및 프로듀서 융합 리덕션 재작성을 bufferization 이전으로 앞당김. 표준 matmul은 고정 폭 및 RVV 타깃에서 VIR로 통일, 레지스터 타일링은 타깃 벡터 폭과 레지스터 수에 따라 구성. target_tune 신규 추가, -mtune을 opt와 llc에 전달. 예시 값으로 spacemit-x100, spacemit-a100, xt-c920v2가 있음. x86 측에서는 벡터 폭도 함께 수정. opt가 이전에 함수에 prefer-vector-width를 추가하여 Emerald Rapids 같은 타깃에서 512비트를 최대한 활용 가능.

PR 설명에 따르면 -mattr는 계속 ISA를 정의하고, -mcpu는 하드웨어가 보고하지 않은 확장을 활성화할 수 있으며, 두 가지의 역할 분담은 변하지 않는다.

의존성은 해소되지 않았다: 여전히 buddy-mlir#1068을 포함한 Buddy 배포판이 필요하며, 메인라인에 현재 고정된 버전은 필요한 pass와 옵션보다 이르다. 커널을 컴파일하는 CI는 새 배포판과 Buddy 버전 업데이트를 기다려야 한다.

오늘의 중점: buddy-mlir에 XSAIAME 방언 추가, RISC-V 매트릭스 확장이 IR 계층으로 진입(11-26)

출처: PR #1071.

11-26 17:18, PR #1071이 머지되어 xsai_ame 방언이 추가되었으며, 32개 파일 변경, 1541줄 추가, 1줄 삭제, 작성자는 xyyy1420이다.

이 방언은 XSAI의 ZAMES 매트릭스 확장과 ZMASYNC 동기화 확장을 위한 타입화된 SSA IR을 제공한다. LLVM 백엔드 지원은 이미 #1067의 LLVM 업그레이드와 함께 메인라인에 진입했으며, 이번에는 IR과 Python 바인딩만 추가한다. llvm.riscv.xsai.* intrinsic과 Linalg 변환으로의 lower는 후속 PR로 남겨두었고, LLVM gitlink는 변경되지 않았다.

타입은 두 가지다. !xsai_ame.tile<kind, MxN, element>의 kind는 a, b, c를 취하며, A는 MxK, B는 NxK, C는 MxN에 대응한다. 차원은 양수 또는 동적이다. 요소 타입은 총 15종으로, 정수 측에는 i4, u4, i8, u8, i32가 있고, 부동소수점 측에는 fp8e4m3, fp8e5m2, fp16, bf16, tf32가 있다. 나머지는 fp32, nvfp4, mxfp4, fp2pack4, fp2pack5이다. !xsai_ame.sync는 매트릭스 동기화 레지스터의 SSA 핸들로, 물리 레지스터 번호는 인터페이스에 들어가지 않는다.

연산에는 load, store, mma, mzero, 그리고 msyncregreset, mfence, mrelease, macquire가 포함된다. load/store는 레지스터와 랭크 2 memref 뷰 사이에서 tile을 옮기며, 선택적 전치가 가능하고, 뷰 형상은 tile과 일치해야 한다. mma는 a/b/c 종류와 정적 K/M/N 차원을 검사하며, 요소 타입 조합은 검증하지 않고, 어떤 조합을 지원하는지는 하드웨어 구현과 LLVM 백엔드가 결정한다.

네 가지 동기화 연산은 모두 메모리 효과를 가지며, 삭제되지 않고 메모리 접근을 넘어 재배치되지도 않는다.

방언은 이미 buddy-opt와 InitAll에 등록되었다. Python 측은 방언 등록, TileType과 SyncType, 그리고 ODS에서 생성된 연산자 생성자를 제공한다.

CPU 튜닝 세 그룹은 모두 1726건 대상이다. VLEN 128의 C920v2는 0.995, VLEN 256의 X100은 0.989. VLEN 1024의 A100은 1.000이다.

PR은 또한 복사 제거 대조의 1726건이 모두 통과했고, matmul 대조의 856건도 모두 통과했다고 밝혔다. VLEN 수정은 VLEN 256과 1024에서 대규모 유클리드 거리 객체 검사를 복구했다.

2.3 openRuyi 패키징 저장소 28건: LibreOffice 코퍼스 스택과 COIN-OR 솔버 트리에 추가, box64 포함 (11-26)

출처: openRuyi 커밋 목록.

패키징 저장소 모니터링 기간 내 28건, 네 명의 커미터로부터: Li Guan 24건, Zheng Junjie 1건, Li Hangfan 1건, Jvle 1건.

신규 패키지는 용도별로 네 그룹이다. 오피스 스위트의 코퍼스 의존성 5건: libcmis、clucene、mythes、libnumbertext、libexttextcat로 철자 및 단어 분절 스택을 보완한다. RDF 3종 세트 3건: raptor、rasqal、redland. COIN-OR 선형 계획 6건: coinutils、osi、clp、cgl、cbc、coinmp. 나머지 6건은 frozen、dragonbox、box2d、zxcvbn-c、fonts-liberation과 sane-backends이다.

단일 건 중 가장 기록할 만한 것은 box64다. 이는 x86-64 사용자 공간 바이너리를 비 x86 플랫폼으로 변환한다. 트리에 들어왔다는 것은 openRuyi의 소프트웨어 면이 x86 패키지만 배포하는 일부 시나리오를 커버할 수 있음을 의미한다.

업데이트 2건: zxing-cpp가 3.2.0으로, wpa_supplicant가 2.12로 올라갔다. 수정 5건: u-boot-tools는 openssl v3에 계속 의존하고, mdadm은 블록 디바이스에서만 O_DIRECT를 설정한다. guile은 업스트림의 병렬 테스트 경쟁 조건 수정을 반영하고, python-cffsubr는 Unix Makefiles 생성기로 전환한다. minicom은 /var/lock을 명시적으로 지정한다.

이 모니터링 기간 내 커널, triton 또는 buddy-mlir 관련 변경은 없으며, 이전 회차의 커널 이중 라인 업그레이드와 대조된다.

2.4 openRuyi 뉴스 페이지 새 공지 없음, 11월 여전히 월간 버전 없음 (11-26 상태)

출처: openRuyi 뉴스 페이지.

뉴스 페이지 최신 항목은 여전히 11-12의 「openRuyi × 오픈소스 서머」 글이다.

모니터링 기간 내 릴리스 또는 새 공지는 없다. 11월 월간 버전은 여전히 나타나지 않았으며, 월간 리듬이 두 달 연속으로 관례대로 이행되지 않았다.

#120의 배치 1~6도 여전히 검토 중입니다. 모니터링 기간 내에 새로 열린 연산자 PR은 없으며, 반영된 것은 백엔드 측의 #135뿐입니다.

벡터 벤치마크, intrinsic 변환, 저정밀 GEMM 세 라인은 여전히 정체 상태이며, 연산자 측 작업은 triton의 예제 패키지와 백엔드 lowering에 집중되어 있습니다.

4. Buddy Compiler 동향

4.1 행렬 확장은 buddy에서 AME와 XSAI AME 두 라인으로 진행 (11-26)

출처: PR #1071. 다른 라인은 부록 [19] 참조.

하나는 기존 AME 라인입니다. 11-19의 #1066은 기존 AME를 ZTT v0.6 연산으로 교체했습니다. #1072 “Lower Linalg matmul and generic regions to AME”는 여전히 검토 중이며, 최근 업데이트는 11-23입니다.

다른 하나는 이번 XSAI AME 라인입니다: ZAMES 행렬 확장에 ZMASYNC 동기화 확장을 더한 것으로, #1071은 IR과 Python 바인딩까지만 구현했습니다.

두 라인 모두 “방언은 있고 lowering 대기 중” 단계에 머물러 있으며, 아직 Linalg와 엔드투엔드 모델에 연결되지 않았습니다.

XSAI 라인의 전제 조건은 이미 갖춰졌습니다: #1067의 LLVM 업그레이드가 llvm.riscv.xsai.*의 백엔드 지원을 메인라인에 가져왔으므로, lowering 측에서 intrinsic에 직접 연결할 수 있습니다.

6. 트렌드 관찰

6.1 백엔드 통합 완료 후, 병목은 연산자 재고와 Buddy 버전 고정으로 전환

#135는 「표준 CPU와 matmul을 두 개의 lowering으로 분리」하는 구조를 닫았으며, 이익은 matmul의 0.810과 masked 메모리 재작성의 0.952에 집중되었습니다.

CPU 튜닝은 VLEN 1024의 A100에서 1.000으로, 이 항목이 넓은 벡터 머신에는 당분간 증분이 없음을 보여줍니다. 판단 근거는 PR 자술의 세 가지 튜닝 샘플이며, 전체 회귀가 아닙니다.

다음 단계의 병목은 컴파일 경로가 아니라 두 곳에 있습니다: 279개의 심사 중 연산자가 진전되지 않았고, Buddy 배포판은 여전히 #1068 이전 버전에 고정되어 있습니다.

6.2 행렬 확장의 적용 속도는 lowering과 변환이라는 두 후속 PR에 달려 있음

buddy의 행렬 확장에는 이미 두 세트의 IR이 있습니다: AME(ZTT v0.6)와 XSAI AME(ZAMES/ZMASYNC).

두 세트 모두 「Linalg에서 방언으로」와 「방언에서 intrinsic으로」의 완전한 체인이 부족합니다. #1071의 PR 자술도 이 두 단계를 후속 작업으로 나열했습니다.

판단: 행렬 명령은 단기적으로 엔드투엔드 모델 성능 데이터에 진입하지 않을 것이며, midend의 머지는 먼저 표현 가능성을 변화시킵니다.

6.3 배포판 패키징 중점이 커널 추적에서 애플리케이션 계층 사용성으로 이동

openRuyi는 이번 모니터링 기간에 28건으로, 커널 변경은 없었으며 오피스 스위트 코퍼스, RDF, 선형 계획법 솔버와 폰트가 대부분을 차지했습니다.

box64의 트리 진입은 이번 배치에서 소프트웨어 범위를 넓힌 유일한 변경으로, x86 바이너리만 배포하는 일부 소프트웨어에 실행 경로를 제공했습니다.

AI 스택 측은 이번 모니터링 기간에 새 패키지가 없었으며, triton과 buddy의 패키징 상태는 이전 호와 동일합니다.
