오늘의 핵심: LLVM fork에 XAME 병합, ZTT v0.6 매트릭스 백엔드가 한 번에 47개 파일 반영 (11-17)

날짜: 2026-11-17　출처: PR #36, 병합 커밋 542365c

11-17 15:05, RuyiAI의 llvm-project fork에 #36「[RISCV][XAME] Add ZTT v0.6 matrix backend support」가 병합되었다. PR은 전날 오전에 열렸고 하루 만에 리뷰를 마쳤다: 47개 파일, +4084 −19이며, 그중 명령 정의 RISCVInstrInfoXAME.td 하나만 1732줄, 내장 정의 517줄, 레지스터 정보 120줄, 그리고 262줄의 상태 처리 pass가 별도로 포함된다. 이는 해당 fork의 메인라인이 11-02 이후 정체된 뒤 첫 변경이자, 최근 보름 동안 가장 큰 규모의 변경이다.

병합된 것은 산발적인 명령이 아니라 완전한 행렬 백엔드 경로다: xame을 로컬 기능 이름(0.6 버전)으로 삼아 MLIR가 생성한 LLVM IR의 행렬과 누산기 SSA 값을 RISC-V 명령으로 내린다; llvm.riscv.ztt.* 내장 이름과 riscv.ztt.matrix/riscv.ztt.acc 대상 타입은 ZTT v0.6의 컴파일러 인터페이스를 따르며, 임시 버전 부가 행렬 확장(Attached Matrix Extension)의 다운스트림 구현에 속한다. 문서에는 두 가지 고정 profile이 명시되어 있다: 기본 +xame은 8×8, M 레지스터 16개, ACC 8개, 원소 상한 64비트; +xame,+xame-gem5는 4×4, M 32개, ACC 4개, 128비트. 둘 다 32비트 레지스터 단위로 계산한다.

공정량은 주로 레지스터와 호출 규약에 있다: 138개의 공유 명령 인코딩, 행렬과 ACC 레지스터 그룹, CSR 오퍼랜드, profile별로 구분되는 어셈블리와 디스어셈블리; 레지스터 할당 후 상태 pass를 한 번 새로 추가하여 디스크립터, 데이터, 상태가 레지스터 복사와 스필 시 덮어쓰이지 않도록 보장한다. 행렬 파라미터는 컴파일러 로컬 호출 규약을 따르며 RISC-V psABI 표준이 아니므로, 호출 양측이 동일한 profile과 레지스터 타입을 약정해야 하고 레지스터 파일을 초과하는 파라미터는 거부되어 메모리로만 전달된다. 스칼라 오버로드는 일률적으로 부호 없는 XLEN 비트형으로 정규화되며, 부호 해석이 필요한 프런트엔드는 자체적으로 부호 확장해야 한다.

검증은 세 곳을 커버한다: LLVM RISC-V CodeGen과 MC 3381/3382 통과, 11개의 XAME 전용 테스트 전부 통과, 유일한 실패는 xboscame-valid.s의 기존 베이스라인 인코딩 차이(테스트는 ACC 인코딩 8을 기대하지만, 변경되지 않은 정의에서 ACC0은 0이며 BOSCAME 파일 자체는 건드리지 않음); 외부 Buddy MLIR harness의 10개 AME 변환 회귀 전부 통과; 4×4 정수 행렬 곱(A는 1부터 16, B는 전부 1)을 AME_gem5에서 컴파일, 링크, 실행하여 16개 출력이 정확히 10, 26, 42, 58의 행 합이 되고 guest 종료 코드는 0이었다.

오늘의 핵심: triton-riscv, bf16 변환기 ABI 수정, riscv64 세 CI 레그 첫 실기 전부 통과(11-17)

날짜: 2026-11-17　출처: PR #121, 이슈 #114

11-17 18:37, triton-riscv에 #121「Fix the launcher ABI of the bf16 conversion helpers」가 병합되었다. 두 파일 +190 −7이며, 본체는 backend/driver.py에 있는 두 helper의 프로토타입과 166줄의 신규 테스트다. 문제는 레지스터 클래스에서 발생했다: launcher가 __truncsfbf2와 __extendbfsf2를 uint16_t 정수 프로토타입으로 정의했으나, llc가 생성한 호출 지점은 bf16에 따라 부동소수점 레지스터를 사용한다—x86-64는 xmm0, riscv64는 fa0을 쓰고 호출자는 하위 16비트에서 값을 가져간다; 정수 반환은 eax/a0에 떨어지므로, 모든 fp32→bf16 커널이 저장하는 값은 직전 부동소수점 연산의 잔여물, 즉 0이거나 쓰레기값이었다.

수정 방식은 두 helper의 프로토타입을 float로 바꿔 bf16 비트가 부동소수점 반환값의 하위 16비트에 머물게 하는 것이다; __bf16 자체는 사용할 수 없는데, launcher가 g++로 컴파일되며 Ubuntu 24.04의 g++ 13이 riscv64에서 이 타입을 지원하지 않기 때문이다. __truncdfbf2와 bf16 libcall 계열의 나머지 멤버는 명시적으로 변경 대상에서 제외되며, 현재 lowering이 이들을 생성하지 않는다.

신규 테스트 python/examples/test_bf16_convert.py는 fp32와 bf16의 상호 변환을 torch의 int16 뷰로 비트 단위 정렬하며, round-to-nearest-even의 네 가지 경계(반값 미만, 짝수와 홀수 lsb의 tie, 반값 초과, float32 최대값에서 무한대)를 커버하고, 수정 전에는 그중 네 예가 실패했다; 이어서 재배치 단언으로 libcall 경로를 고정한다—host 대상 빌드는 avx512bf16이 있는 x86에서 건너뛰고(여기서 llc는 bf16을 네이티브로 내리며 helper를 거치지 않음), riscv64 빌드는 +zvfbfmin을 제거해 변환이 launcher를 거치도록 강제하며, 겸사겸사 베어 런타임 경로의 프로브로 사용한다.

검증 결과는 기록할 만하다: x86 host에서 #114의 재현 커널은 수정 후 [-5.0, -0.5, 2.5, 7.0]을 반환했고, 수정 전에는 모두 0이었다. host 예제 스위트는 4028개 통과, 14개 스킵이었으며, 10개 실패는 test_affine_grid_generator와 test_avg_pool3d의 기존 실패다(수정을 stash한 뒤에도 동일하게 실패하며, 이 두 테스트 케이스는 bfloat16을 사용하지 않는다). riscv64의 세 CI 레그(세 가지 Python 버전)는 전체 스위트를 통과했다——이 수정이 실제 riscv64에서 검증된 것은 이번이 처음이다. #120의 FlagGems 브랜치와 합류한 후, 41개의 bf16 xfail 고정이 모두 정상 통과로 전환되었고 461개 테스트 케이스가 통과했다.

1. RuyiAI 스택 진행 상황(PyTorch / Triton / TileLang RISC-V 적응)

1.1 pytorch riscv 브랜치는 두 밤 연속 재정렬이 없었고, main의 스무 개 커밋 전부 업스트림(11-17 상태)

날짜: 2026-11-17　출처: riscv 브랜치 커밋 목록, PR 목록

이 fork의 기본 브랜치는 riscv이며, 최신 커밋은 여전히 11-16 03:00(베이징 시간)에 반영된 #57 “JENKINS_RC 제거”이고 작성자 시간은 11-13이다. 이전에 매일 밤 한 번씩 있던 브랜치 전체 재정렬은 11-16과 11-17 두 밤 모두 나타나지 않았다. 지난 호 리포트에서는 “매일 새벽 한 번 재정렬”로 기록했으나, 현재 상태에 따르면 “재정렬이 두 밤째 중단됨”으로 바꿔야 하며 더 이상 시계를 기준으로 증분을 추론해서는 안 된다. 검토 중인 8개 PR의 마지막 업데이트 시간도 11-16 08:30에 멈춰 있으며, 이 역시 재정렬로 타임스탬프를 갱신한 동작이므로 새로운 움직임으로 볼 수 없다.

main 브랜치의 모니터링 기간 내 20개 커밋은 전부 업스트림 PyTorch의 동기화 트래픽이다: MPS의 upsample 포워드를 plane grid로 이전, ROCm의 MaybeSetDevice 롤백, Inductor의 Blackwell 전치 FP32 설정 필터링, DCP의 FsspecReader 배치화 및 비동기 프리페치, TritonPrinter의 float64 리터럴 수정 등이며 RISC-V와는 무관하다.

1.2 triton-riscv의 FlagGems 예제 PR이 111개 파일로 확장, 여전히 열림(11-17)

날짜: 2026-11-17　출처: PR #120, PR #123

#120 “Add FlagGems operator examples (batches 1-6)”는 현재 가장 큰 검토 중 항목이다: 111개 파일, +8592 −4, 11-17 20:59에도 여전히 업데이트가 있다. 이는 FlagGems의 연산자 예제를 배치로 triton-riscv의 예제 디렉터리에 옮기는 것으로, RISC-V 백엔드에 업스트림 연산자 라이브러리에서 온 검증 세트를 갖추게 하는 것과 같다. #121에서 41개의 bf16 xfail이 정상 통과로 전환된 것은 바로 이 브랜치를 통해 실행된 결과다.

#123 “백엔드 툴체인을 Triton의 LLVM에서 분리”는 11-16에 열린 후 더 이상 업데이트되지 않았으며, 여전히 세 개 파일, +16 −2이고 llvm-hash.txt는 일시적으로 nightly/v0.1.4.dev20261103에 고정되어 있다. 저장소에는 현재 19개의 열린 PR이 있다.

1.3 llvm-project 검토 대기열에 XSAI와 XBOSCAME 두 라인이 남아 있음(11-17 상태)

날짜: 2026-11-17　출처: PR #33, PR #28

XAME가 합류된 후 fork에는 두 개의 오래된 PR이 여전히 열려 있다: #33 “Add XSAI ZAMES and ZMASYNC vendor extensions”는 10-26에 열려 11-05에 마지막 업데이트되었고, #28 “Feat/xboscame fpga”는 09-23에 열려 11-02에 업데이트되었다. 두 라인 모두 벤더 확장 라인으로, 방금 합류된 XAME와 공존한다——BOSCAME의 기존 인코딩 정의는 이번에 한 줄도 변경되지 않았으며, #36의 설명에서도 xboscame-valid.s의 실패가 베이스라인 차이에 해당한다고 특별히 설명했다. 매트릭스 계층에는 같은 fork 안에 이미 세 가지 이름이 있다: XBOSCAME, XAME, XSAI이며 서로를 덮어쓰지 않는다.

6. 동향 관찰

6.1 행렬 확장에 컴파일러 출구가 생기기 시작

XAME 이번 건은 138개 명령어, 두 세트의 profile, 레지스터 스케줄링과 호출 규약을 한 번에 LLVM에 넣고, Buddy의 AME 변환과 gem5 실주행으로 검수했습니다. 지난주 RVV bf16과 마찬가지로, 한 확장이 사용 가능한지는 이제 세 가지가 동시에 갖춰지는지에 달려 있습니다. 컴파일러가 생성할 수 있고, 시뮬레이터가 실행할 수 있으며, 연산자 라이브러리에 대응 진입점이 있어야 합니다. 명령어 정의만 내보내고 컴파일러를 보충하지 않는 것은 RISC-V에서 이미 릴리스하지 않은 것과 같습니다.

6.2 이번 주의 주선은 bf16

#117은 +zvfbfmin을 기본 특징 문자열에 넣었고, #121은 해당 확장이 없을 때 libcall의 레지스터 클래스를 수정했으며, IREE 3.14.0은 RISC-V V에 bf16 MMA를 보충했습니다. 세 가지 동작은 같은 일을 가리킵니다. bf16은 RISC-V에서 하나의 경로가 아니라 「벡터 확장이 있으면 벡터로, 없으면 libcall로」입니다. 두 경로는 비트 단위로 일치해야 하며, 어느 한 고리가 빠지면 「결과가 0」이라는 가장 찾기 어려운 증상으로 나타납니다.

6.3 배포판이 ABI 마이그레이션 준비 중

openssl-3 호환 패키지가 먼저 착지하고 메인 패키지는 여전히 3.6.5에 머물며, 충돌은 예상 동작으로 명시되었습니다. 같은 날 abaci-bot은 ABI 비교, SPDX 검증과 CVE 금수 캐시를 강화했습니다. openRuyi는 「장래에 끊어질 ABI」를 엔지니어링 항목으로 미리 관리하며, 전환 당일에 보충하기를 기다리지 않습니다. 이런 방식은 패키지를 몇 개 더 합치는 것보다 배포판이 장기적으로 업스트림을 따라갈 수 있는지를 더 잘 결정합니다.

6.4 정보면은 계속 공회전, 코드면은 매우 바쁨

외부 뉴스 제로 히트, 포럼 새 주제 없음, 공식 사이트 세 페이지 정지 상태이지만, 모니터링 기간 내에 두 건의 컴파일러 중간 변경이 병합되었고, 19건의 패키징 저장소 커밋, 20건의 거버넌스 로봇 커밋이 있었습니다. 데일리 리포트의 판단 가치는 계속 뉴스 건수를 세는 것이 아니라 커밋 내용을 읽는 데 달려 있습니다. 릴리스 노트가 비어 있거나 누락된 경우에는 병합 커밋과 테스트 기록으로 돌아가 확인할 수밖에 없습니다.
