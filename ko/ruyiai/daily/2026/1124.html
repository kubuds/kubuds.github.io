오늘의 중점: buddy-mlir, Qwen3-0.6B FP16 최적화 병합, Prefill 86.01 token/s (11-23)

출처: PR #1001.

#1001은 11-23 14:51에 병합되었으며, 제목은 「Optimize Qwen3-0.6B FP16 Prefill and Decode on K3 A100」. 23개 파일 변경, 560줄 추가, 50줄 삭제.

실측은 동일한 K3의 A100 코어 8~15에서 완료, 8개 물리 코어, 입력단 동일. Prefill은 128개 위치 평가, Decode는 96번째 위치부터 32스텝 측정, 로딩 시간 미포함.

구현 Prefill (token/s) Decode (token/s)
Buddy 메인 브랜치, FP16 미최적화 4.24 0.84
llama.cpp 71.64 14.38
Buddy, 본 PR 86.01 13.45

Prefill은 llama.cpp보다 20.1% 높으며, 메인 브랜치 베이스라인의 20.3배. Decode는 13.45 token/s로 llama.cpp보다 6.5% 낮지만, 여전히 메인 브랜치의 16.0배.

두 지표의 방향이 반대입니다. Prefill은 블록 GEMM과 네이티브 VLEN=1024를 사용하고, Decode는 단일 토큰의 GEMV 대역폭에 제약됩니다. PR 설명에는 비교가 all-position logits을 사용한다고 명시되어 있으며, 양측의 기준이 이 점에서 일치합니다.

커널 측은 #997의 성과를 재사용했으며, IME FP16 GEMM과 GEMV, Decode 가중치 패킹, RVV와 SiLU 최적화를 포함합니다. Attention은 벡터 폭 64를 사용하고, Decode는 KV를 한 경로로만 분할합니다.

설정은
models/qwen3/specs/f16_k3_a100.json에 집중되어 있으며, 기본 파이프라인은 영향을 받지 않습니다. 파일에서 VLEN은 1024, Prefill 벡터 폭은 64, Decode 패킹 폭은 32, 스레드 수는 8입니다. 출력 어휘 가중치는 별도로 저장되어 프로젝션별로 레이아웃을 선택할 수 있습니다.

정확성 측면에서 96개의 Decode 토큰과 세 가지 반복 탐욕 생성 사례가 모두 PyTorch 참조와 일치합니다. PR 설명은 또한 전체 check-buddy가 비활성화된 Python 패키지 대상에 의해 차단되어 전체 실행을 하지 못했다고 지적합니다.

세 건의 커밋이 당일 반영되었습니다. 초기 커밋 이후 15:02에 “extract the device runtime and add CI checks”를 추가했습니다. 16:08에 다시 “docs: describe the message lookup task”를 추가했습니다.

저장소 크기는 17 KB에 불과하며, 코드량은 이전 경로의 내장 구현과 일치합니다. 웹사이트 저장소의 PR #647이 연동을 담당하며, 15:23에 “build(device): use ruyi-imager-core submodule”이라는 제목으로 병합되었습니다.

해당 PR은 14개 파일을 변경하여 79줄을 추가하고 775줄을 삭제했으며, 삭제된 것은 원래 저장소 내에 있던 디바이스 런타임입니다. 같은 배치에서 두 가지 빌드 변경도 이루어졌습니다. 웹사이트 빌드와 서브모듈 추적이 분리되고, 빌드 권한이 별도로 격리되었습니다.

귀속에 주의해야 합니다. 새 저장소는 ruyisdk-test 조직 아래에 있으며, 해당 조직에는 현재 31개의 저장소가 있고 같은 시기에 ruyi-imager-webview와 ruyi-imager-electron 두 개의 새 저장소도 있습니다. 기존 ruyisdk/ruyi-imager는 Java 데스크톱 플래싱 도구로, 11-19 이후 커밋이 없으며 이번 외부 이전과 동일한 코드가 아닙니다.

4.2 #1077 strip과 zstd 통합 제안, 목표는 단일 자산 상한 (11-23)

출처: PR #1077.

#1077은 11-23 11:05에 생성되었으며, 파일 하나만 수정했고 아직 병합되지 않았다. 제목은 「Pack the LLVM and buddy tarballs with zstd」이다.

PR 설명에 배경이 제시되어 있다. riscv64의 LLVM 설치 패키지는 gzip 압축 후 GitHub 단일 자산 2 GiB 상한을 약간 초과한다. 이로 인해 nightly/v0.1.5.dev20261120 릴리스가 실패했고, API는 422와 「size must be less than 2147483648」을 반환했다.

해결책은 세 가지다. 바이너리와 공유 라이브러리를 strip하고, MLIR Python 바인딩을 제거하며, zstd -19 –long=27로 패키징하는 것으로 변경한다. 작성자가 제시한 예상치는 LLVM이 2047 MB에서 약 840 MB로, buddy가 264 MB에서 약 180 MB로 줄어드는 것이다.

설명에는 두 가지 부수 사항도 언급되어 있다. triton-riscv의 setup.sh는 이미 .tar.zst를 읽을 수 있다. 이 변경이 반영된 후 첫 배포 시에는 llvm_cache_mode=clean을 한 번 실행해야 한다. 캐시 키에 이번 필터링이 포함되지 않기 때문이다.

6. 트렌드 관찰

6.1 모델 최적화가 배치 재사용으로 전환

#1001에는 #997의 커널, 가중치 패키징, RVV/SiLU 최적화를 재사용한다고 명시되어 있다. 큐에 있는 Whisper Base, PaddleOCR-VL-0.9B, EmbeddingGemma도 동일한 경로를 인용한다.

이는 K3 A100에서의 모델 가속이 단일 지점 공략에서 템플릿화로 전환되었음을 보여준다. 새 모델을 추가하는 주요 작업은 커널을 다시 작성하는 것이 아니라 설정을 작성하고 정확성을 검증하는 것이다.

판단 근거는 두 가지다. 첫째, 설정이 각 모델의 specs 디렉터리에 집중되어 있고, 둘째, PR 설명에 「shared kernels」와 「reuse」라는 표현이 반복적으로 등장한다.

6.2 릴리스 번호가 내용보다 빠르게 진행

ruyi는 0.55.0-beta에서 0.56.0-alpha로 올라갔으나 코드 차이는 버전 번호 세 줄뿐이다. triton-riscv가 재발행한 정식 태그도 11-18의 이전 커밋을 가리킨다.

두 저장소에서 같은 날 「새 버전은 있으나 새 코드는 없음」 상황이 발생했다. 이는 릴리스 리듬이 변경량이 아니라 버전 계획에 의해 주도됨을 보여준다.

다운스트림에 대한 영향은 버전 번호가 더 이상 내용의 많고 적음을 나타내지 않는다는 것이다. 업그레이드 가치가 있는지 판단하려면 번호 크기가 아니라 릴리스 노트의 항목 집합을 봐야 한다.

6.3 디바이스 측 코드가 메인 저장소를 떠나기 시작

웹사이트 저장소는 이번 라운드에서 775줄을 삭제하고, 디바이스 런타임을 독립 저장소와 서브모듈로 이관했다. 같은 기간 ruyisdk-test 조직 아래에 ruyi-imager-webview와 ruyi-imager-electron이 등장했다.

방향은 플래싱 도구를 독립적으로 릴리스하고 독립적으로 테스트할 수 있는 컴포넌트로 분리하는 것이다. 이로 인해 메인 저장소가 작아지고 빌드 권한도 별도로 격리할 수 있게 된다.

유의할 점은 새 저장소가 테스트 조직 아래에 있다는 것이며, 아직 ruyisdk 메인 조직으로 이전되지 않았다. 이 단계가 실제로 일어날지는 후속 모니터링 포인트로 삼을 수 있다.

이번 모니터링 기간의 뉴스 측은 완전히 공백이었다. 네 차례의 방향성 쿼리는 모두 적중이 없었고, arXiv 역시 11-22 이후 새 항목이 없었다. 따라서 보고서 본문은 전적으로 GitHub와 커뮤니티 사이트의 실제 기록에서 나왔다.
