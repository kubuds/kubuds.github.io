오늘의 핵심: triton-riscv, 첫 정식 릴리스 태그 발행, 설치 경로가 소스에서 wheel로 전환 (11-09)

날짜: 2026-11-09　출처: 릴리스 태그 release/20261108-6895885, PR #105, PR #107

11-09 06:59(베이징 시간)에 생성된 release/20261108-6895885는 이 저장소의 첫 번째 정식 릴리스 태그입니다. 이전의 열여덞 개 태그는 모두 nightly/ 접두사였고, 저장소에는 release/ 계층이 존재한 적이 없었습니다. 릴리스 산출물은 두 개의 wheel로, 각각 x86_64(manylinux_2_27 및 2_28)와 riscv64(manylinux_2_39)이며, 통일적으로 cp312-abi3, 버전 문자열은 triton-3.9.0입니다.

태그는 커밋 6895885를 가리키며, 이는 11-06의 “AMD를 위한 codegen 라이브러리 보충”(#102) 병합 커밋으로, 나이틀리 버전 nightly/20261106-6895885와 동일한 지점입니다. 당일의 세 커밋(#105, #106, #107)은 모두 태그 이후에 반영되어 이 패키지에는 포함되지 않았습니다. 이는 “첫 번째 정식 버전”이 실제로는 지난 주말의 코드 상태를 대상으로 한 것이며, 릴리스 행위 자체가 이 태그의 전부임을 의미합니다.

태그와 같은 날의 #105는 README를 재작성하여 설치 섹션을 소스 우선에서 wheel 우선으로 변경했습니다. 먼저 wheel 경로와 이를 호스팅하는 패키지 인덱스를 제시하고, 이에 필요한 LLVM 아카이브와 이를 가리키는 변수를 제시합니다. 소스 경로는 make setup(.venv 생성, 고정 버전 Triton 클론, 고정 버전 LLVM 및 buddy 빌드 다운로드)으로 압축되었으며, 기존의 “가상 환경 생성, 의존성 설치, 환경 스크립트 15개 변수” 설명은 한 줄의 짧은 주석으로 축소되었습니다.

빠른 시작도 방식이 바뀌었습니다. 더 이상 ok: True만 출력하지 않고, 커널을 riscv64-unknown-linux-gnu로 컴파일하며, 목적 파일을 보존하고 디스어셈블리를 grep하여 백엔드가 생성한 vsetivli, vle32.v, vfadd.vv, vse32.v를 출력합니다. 컴파일러 프로젝트에서 이는 단순한 단언보다 “백엔드가 실제로 벡터 명령을 생성했다”는 것을 더 잘 보여줍니다.

나이틀리 버전에는 고유 버전 접미사 .dev<날짜>가 추가되었습니다. 이전에는 매 빌드가 Triton 자체의 버전 번호를 공유하여 패키지 인덱스가 중복 버전을 거부했습니다. wheel의 릴리스 동작은 wheel 작업 내부에 배치되어 산출물 중복 다운로드를 방지하고, PYPI 계열 키 존재를 조건으로 하며, 패키지 인덱스 측이 아직 준비되지 않은 경우에도 실패하지 않고 계속 실행됩니다.

#107은 이후 수정을 수행했습니다. 패키지 인덱스에 아직 triton과 buddy 도구가 없어 README의 바이너리 설치 주소가 실패하므로, 두 프로젝트 각각의 GitHub releases를 가리키도록 변경하고 디스크에서 wheel을 설치하며 LLVM 압축 패키지의 출처를 명시했습니다. 같은 커밋은 Python 3.14의 lit 크래시도 수정했습니다.

오늘의 중점: buddy-mlir가 전체 f32 YOLOv8 그래프를 VIR로 낮추고, K3에서 바이트 단위 일치 출력(11-10)

날짜: 2026-11-09(11-10 01:07 베이징 시간 병합)　출처: PR #1041, 병합 커밋 18c66ec

PR #1041은 #1042의 f32 YOLOv8 그래프를 엔드투엔드로 VIR까지 통과시킵니다. 먼저 Linalg에서 VIR로의 lowering을 수행하고, 그다음 VIR에서 벡터 방언으로의 lowering을 수행합니다. 이전에는 이 pass에 컨볼루션 패턴이 없었고, 그래프에는 추가로 세 가지 유형의 연산자가 직접 실패했습니다. 한 번의 변경으로 컨볼루션과 그 세 가지 유형을 동시에 보충했습니다.

규모는 14개 파일, 1,646줄 추가, 115줄 삭제, 13개 커밋입니다. 작성자는 zhanghb97이며, 11-09 08:57에 개설되어 당일 저녁에 병합되었습니다.

컨볼루션은 두 계열 모두 커버합니다. 2D NHWC와 HWCF 조합, 2D NHWC와 FHWC 조합입니다. 벡터화는 출력 채널 F(출력과 HWCF 필터의 마지막 차원)를 따라 전개되며, 각 (kh, kw, c)에 대해 입력 요소를 각 출력 픽셀당 하나의 vir.fma로 브로드캐스트하므로 모든 벡터 접근이 연속적이고 lane 간 리덕션도 없습니다. FHWC 필터는 먼저 병렬로 HWCF 버퍼에 복사되며, 출력 행은 scf.parallel에 배치되고 각 행당 하나의 F lane vir.set_vl을 가집니다.

이전에 실패했던 세 가지 연산자도 함께 보충되었습니다. 첫째, rank-0 입력: memref가 linalg.generic에 직접 들어가면 memref.expand_shape에서 invalid reassociation 오류가 발생하므로, 한 번 로드한 후 브로드캐스트하도록 변경했습니다. 둘째, 마지막 차원을 보존하는 linalg.reduce, 예를 들어 DFL softmax의 1x16x4x2100, dimensions=[1], addf와 maximumf 조합은 마지막 차원을 따라 벡터화하고 리덕션 차원의 슬라이스를 요소별로 병합하며 vir.reduce를 생성하지 않습니다. 셋째, linalg.index를 읽는 명명된 연산자, 예를 들어 업샘플링의 linalg.map iota에는 동종 linalg.generic과 동일한 스칼라 루프를 보충했습니다.

실기 측정 기준은 명확합니다. K3에서 f32 YOLOv8 pose의 원본 출력은 최대 6e-5 변화하며, PyTorch와의 차이는 여전히 6e-4(bus)와 8e-4(zidane) 이내로 변경 전과 동일합니다. detect 모델의 검출 결과는 변하지 않았고 속도도 저하되지 않았습니다. f32와 IME 동적 라이브러리의 출력은 변경 전과 바이트 단위로 동일합니다.

1. RuyiAI 스택 진행 상황(PyTorch / Triton / TileLang RISC-V 적응)

1.1 triton-riscv: torch 2.15.0으로 교체 후 flaggems 7개 테스트 케이스 실패, 방어적 읽기 방식으로 변경 (11-09)

날짜: 2026-11-09　출처: PR #106, 커밋 cfdf4f7

riscv64의 CI에는 인덱스에 포함된 torch가 설치되어 있는데, 최신 2.15.0이 등장하면서 flaggems 제품군의 7개 테스트 케이스가 실패했다. 수정 결과 3,826개 항목 통과, 2개 항목 건너뜀으로 마무리되었다.

median 관련 5개 사례의 문제는 이름 텐서에서 비롯되었다. median.py는 torch의 명명된 텐서 지원을 구현하고 있는데, 2.15.0 이 빌드에는 Tensor.names가 없어 널 검사 함수가 커널 실행 전에 AttributeError를 발생시켰다. 수정 방식은 해당 속성을 방어적으로 읽어, 이 API가 없는 빌드를 “이름 없음”으로 취급하는 것이다. 이는 기존 검사가 “이름이 모두 None인 텐서”에 대해 내놓는 답과 일치한다. 작성자는 이 코드를 그냥 삭제할 수 없는 이유도 설명했는데, 업스트림 flaggems가 여전히 names를 보호 장치 없이 호출하고 있으며 명명된 텐서가 더 이른 torch 버전에는 실제로 존재했기 때문이다.

sinh 관련 2개 fp16 사례는 원래 상대 오차와 절대 오차를 각각 1e-4로 비교했으나 fp16은 이를 충족하지 못했으므로(실측 상대 차이 6.6e-4) fp32는 1e-4를 유지했다. 동시에 torch 2.10을 riscv64 설치에서 제거하고 다시 인덱스를 따르도록 했다. 업스트림 torch를 따라가는 CI에서 이런 유지보수는 외주화할 수 없는 비용이다. 업스트림이 바뀌면 제품군을 다시 정렬해야 한다.

1.2 triton-riscv: Python 3.14에서 lit 크래시, CI는 pip로 설치한 lit을 우선 사용하도록 변경 (11-09)

날짜: 2026-11-09　출처: PR #107, 커밋 209274f

실패한 것은 CI의 Python 3.14 작업이었다. Triton은 which로 PATH에서 lit을 찾는데, LLVM 트리에 있는 lit은 모듈 수준에서 main을 호출하고, Python 3.14는 Linux에서 기본적으로 forkserver 시작 방식을 사용하므로 재임포트 시 바로 크래시가 발생한다.

수정은 매우 가볍다. 빌드 인터프리터의 bin 디렉터리를 PATH 맨 앞에 두면 탐색이 pip로 설치한 lit을 먼저 찾게 된다. 이는 1.1과 마찬가지로 “CI가 업스트림을 따라가는” 이후의 마무리 작업이며, 세 건의 커밋 중 두 건이 컴파일러가 아닌 환경 문제인 이유를 설명해 준다.

1.3 pytorch, tilelang-riscv, llvm-project: 모니터링 기간 내 커밋 없음 (11-10 상태)

날짜: 2026-11-10(상태)　출처: pytorch riscv 브랜치, tilelang-riscv, llvm-project

세 저장소 모두 모니터링 기간 내 커밋이 없다. pytorch의 riscv 브랜치 헤드 커밋은 여전히 11-04 동기화 배치이며, tilelang-riscv는 11-03 06:13 UTC에, llvm-project의 main은 11-02 14:48 UTC에 멈춰 있다. 이번 기간 RuyiAI 스택의 증분은 전부 triton-riscv의 세 건의 커밋과 buddy-mlir의 한 건의 병합에서 나왔다.

2. RuyiSDK 툴체인 및 배포판

2.1 openRuyi: KDE Plasma 6.8.2 일괄 업그레이드, 40개 데스크톱 패키지 같은 날 후속 (11-09)

날짜: 2026-11-09　출처: plasma-workspace 커밋, kwin 커밋, 커밋 목록

패키징 저장소는 이날 모니터링 기간 내 가장 큰 규모의 배치를 처리했다. 3. 벡터 확장과 연산자 최적화

3.1 buddy-mlir: 컨볼루션을 출력 채널 방향으로 벡터화, FHWC 필터를 먼저 HWCF로 변환 (11-10)

날짜: 2026-11-09(11-10 01:07 베이징 시간에 머지)　출처: PR #1041, 머지 커밋 18c66ec

컨볼루션의 하강 전략은 이후 모든 튜닝의 여지를 결정하므로 따로 살펴볼 가치가 있다. 선택은 입력 채널 C 방향으로 리덕션하는 대신 출력 채널 F 방향으로 벡터화하는 것이다: 각 (kh, kw, c)에 대해 입력 원소 하나를 각 출력 픽셀마다 하나의 vir.fma로 브로드캐스트한다.

직접적인 이점은 벡터 접근이 매번 연속적이고 레인 간 리덕션이 없다는 것이다 — 리덕션은 횡방향 명령과 후속 리덕션 트리가 필요해 좁은 VLEN에서 비용이 두드러진다. 대가는 필터 레이아웃이 일치해야 한다는 점이다: FHWC 배열의 필터를 먼저 병렬로 HWCF 버퍼에 복사해야 하며, 한 번의 추가 이동을 대가로 내부 루프의 연속 접근을 얻는다.

출력 행에는 scf.parallel을 쓰고, 각 행마다 F 레인 하나의 vir.set_vl을 둔다. 이전의 VIR에서 벡터로의 하강은 동적 벡터의 선행 정적 차원에 대해 직렬 affine.for를 발생시켰고, 병렬화 패스가 vector.load를 통과하지 못했는데, 이번에 scf.parallel로 바꾸었으며 조건은 메모리 접근이 허용되는 경우다. 또한 각 출력 픽셀이 하나의 이터레이션을 차지하는 방식은 Linalg에서 VIR로의 하강에 유지되며, “여러 이터레이션이 하나의 벡터 로드”를 공유하는 것은 백엔드가 결과를 가진 벡터 설정 내에서 스스로 병합하도록 하여 레지스터 결정을 타깃에 맡긴다.

3.2 buddy-mlir: rank-0 입력, 마지막 차원을 유지하는 reduce, linalg.index를 읽는 연산자 보완 (11-10)

날짜: 2026-11-09(11-10 01:07 베이징 시간에 머지)　출처: PR #1041, 머지 커밋 18c66ec

세 가지 실패 연산자는 각각 다른 함정이 있다. rank-0 입력(단일 원소 memref가 곧바로 linalg.generic으로 들어감)은 형상 전개 지점에서 유효하지 않은 재결합 오류를 내는데, 이제 한 번 로드한 뒤 브로드캐스트하도록 변경했다.

끝 차원을 유지하는 reduce는 더 쉽게 간과된다. DFL softmax의 1x16x4x2100, dimensions=[1], 컴비네이터 addf와 maximumf의 경우 기존 pass는 바로 오류를 냈다. 새로운 방식은 끝 차원을 따라 벡터화하고, 환원되는 차원의 슬라이스를 원소별로 병합하며, vir.reduce를 생성하지 않는다. 이전에 lowering되던 형태들은 그대로 유지된다.

세 번째는 linalg.index를 읽는 명명 연산자로, 예를 들어 업샘플링의 linalg.map iota다. 명명 연산자는 제네릭 op의 body를 복사할 수 없어 과거에는 건너뛰었는데, 이제 동종 linalg.generic과 동일한 스칼라 루프를 보충해 준다.

4. Buddy Compiler 동향

4.1 리뷰 수렴 세 지점: 병렬 행 메모리 의존성, FMA 반올림, reduce 디스패치 (11-10)

날짜: 2026-11-09 (11-10 01:07 베이징 시간 머지)　출처: PR #1041

세 가지 리뷰 의견이 모두 코드 변경으로 이어졌다. 병렬 행의 메모리 의존성: 행 간에 SSA 의존성은 없지만 메모리 의존성이 있을 수 있으므로, 각 행의 메모리 접근이 서로 독립적임을 증명할 수 있을 때만 scf.parallel을 사용한다. 즉 모든 쓰기가 vir.store이고 저장하는 벡터가 해당 행들을 포함하며, 쓰이는 원소들이 서로 겹치지 않고(단위 레이아웃, 또는 stride가 모두 정적이고 stride 기준 정렬 후 서로 중첩), 쓰이는 memref와 겹칠 수 있는 모든 접근이 동일한 기저 주소, 인덱스, 랭크를 사용해야 한다. 충족하지 못하면 직렬 affine.for로 되돌린다. 새로 추가된 테스트 파일은 네 가지 상황을 다룬다: 병렬 가능, 행 간 공유 스칼라 읽기/쓰기, stride가 0인 memref, 다른 행이 쓰고 있는 데이터 읽기.

FMA 건은 더 세밀하다: VIR에서 벡터로의 lowering이 메인 루프에서는 vir.fma를 벡터 fma로 lowering하지만 테일 루프에서는 곱셈 더하기 덧셈으로 분해하여, 동일한 op가 벡터 lane과 테일 lane에서 서로 다른 반올림을 낸다. 테스트는 a가 1 더하기 2의 마이너스 23제곱, b가 1 빼기 2의 마이너스 23제곱, c가 마이너스 1인 조합을 사용하여, 벡터 lane은 마이너스 2의 마이너스 46제곱을 얻고 테일 lane은 0을 얻는다. 이제 테일에서 math.fma를 사용하여 양쪽이 일치하며, 테스트는 양쪽을 동시에 검사한다. 이 변경은 테일 lane에 반올림 수준의 차이를 만들며, K3에서 f32 YOLOv8의 출력 변화 상한은 앞서 언급한 6e-5다.

reduce 디스패치 조건도 좁혀졌다: 판정 함수가 구 구현이 실제로 지원하는 상황(원소 타입 f32, 컴비네이터 addf 또는 maxnumf, 각 랭크에 대응하는 차원 등)과 완전히 일치하도록 하여, 고속 경로를 타서는 안 되는 reduce까지 삼키지 않도록 했다.

날짜: 2026-11-10 (상태)　출처: PR #1035, PR #1038, PR #1039, PR #1040

5. 커뮤니티와 활동 및 공식 홈페이지

5.1 공식 홈페이지 세 페이지 변화 없음, 블로그 2편, 문서 23장 (11-10 상태)

날짜: 2026-11-10(상태)　출처: RuyiAI 공식 홈페이지

index, blog, docs 세 페이지의 스냅샷은 지난 회차와 동일하며, 새 블로그 글 또는 문서 장이 없다. 블로그 인덱스는 여전히 두 편(Triton의 RISC-V 적응, PyTorch RISC-V CI 실천)이고, 문서는 23장이다.

5.2 포럼 모니터링 기간 내 새 글 없음, 최신은 여전히 11-06의 재게시글 (11-10 상태)

날짜: 2026-11-10(상태)　출처: RuyiSDK 커뮤니티 최신 토픽

5.4 외부 뉴스 제로 히트, arXiv 최신은 11-05에서 멈춤 (11-10 상태)

날짜: 2026-11-10(상태)　출처: Google News, arXiv RISC-V 검색

RISC-V 일반 크롤링은 모니터링 기간 내에 개인 학습용 CPU 저장소, ESP32 개발 보드, Infineon AURIX RC1 같은 항목만 반환했으며, Ruyi 커뮤니티와는 무관하다; RuyiAI, RuyiSDK, Ruyi, openRuyi, Buddy Compiler 다섯 그룹의 표적 쿼리는 제로 히트였다. arXiv의 RISC-V 검색 최신 한 편은 11-05의 SensorGuard-RV이며, 모니터링 기간 내에 새 논문은 없다.

6. 트렌드 관찰

6.1 이번 라운드에서 보충한 것은 연산자가 아니라 배포 체인

triton-riscv 커밋 세 건 중 두 건은 설치와 테스트 체인(README를 wheel 우선으로 변경, flaggems가 새 torch를 따라감)이고, 한 건은 CI의 Python 3.14 호환으로, 컴파일러 자체를 건드린 커밋은 한 건도 없다. 일요일의 첫 정식 릴리스 태그까지 더하면, 이날의 주제는 “사람들이 설치할 수 있게, 올바르게 설치할 수 있게” 하는 것이다.

이런 라운드는 어떤 프로젝트에서나 나타나지만, 진전이 없다고 오해되기 쉽다. 실제로 소스 설치에서 wheel 설치로 가는 것은 “개발자가 빌드할 수 있다”에서 “사용자가 설치할 수 있다”로 가는 분기점이다: 소스 경로는 사용자가 직접 LLVM, buddy 빌드, 수십 개의 환경 변수를 준비해야 하지만, wheel 경로는 명령어 하나면 된다. 오랫동안 “직접 빌드”에 의존해 온 RISC-V 같은 생태계에서 이 단계의 한계 가치는 연산자 하나를 더 최적화하는 것보다 높다.

6.2 바이트 단위 일치가 VIR lowering의 검수 기준이 되고 있다

11-08의 두 변경은 로드 시점 검증으로 VLEN 불일치를 막고 호스트 고정 크기가 실제 VLEN을 따르게 했으며, 오늘의 #1041은 다시 “f32와 IME 동적 라이브러리 출력이 변경 전과 바이트 단위로 동일”을 검증 기준에 넣었다. 세 변경은 같은 기준을 가리킨다: lowering은 구현을 바꿀 수 있지만 수치는 바꿔서는 안 된다.

이 기준은 “정밀도가 허용 오차 내”보다 더 엄격하고, 컴파일러에 더 적합하다: 허용 오차는 순서 오류를 가릴 수 있지만 바이트 단위 비교는 그럴 수 없다. 대가는 매 변경마다 재현 가능한 베이스라인이 있어야 한다는 것이며, K3 같은 이중 코어(두 클러스터의 VLEN이 다름) 머신은 마침 가장 어려운 베이스라인을 제공한다.

6.3 데스크톱 스택과 보안 업데이트가 패키징 리듬을 장악했다

65건의 커밋 중 40건은 KDE Plasma 6.8.2, 7건은 Python 보안 업데이트, 나머지는 Wayland, wget2, llvm 바인딩 같은 자잘한 버전 업이다. AI 스택은 이날 커밋이 네 건뿐인데, 배포판 쪽은 60여 건이었다.

이 비율은 openRuyi의 현재 병목이 새것을 만드는 것이 아니라 업스트림을 따라가는 데 있음을 보여준다: 데스크톱과 언어 런타임의 업스트림 버전이 나오면 패키징 저장소는 하루 이틀 안에 전부 따라가야 한다; 반면 AI 스택의 리듬은 모델과 툴체인을 중심으로 주 단위, 심지어 버전 단위로 움직인다.
