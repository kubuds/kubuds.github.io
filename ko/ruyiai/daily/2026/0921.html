오늘의 중점: XuanTie 커널 패치가 T-Head PMA 정오표를 PUD/P4D 대형 페이지로 확장

날짜: 2026-09-20　출처: linux-xuantie-kernel 커밋 167b3d7c

베이징 시간 09-20 16:33, RuyiSDK의 XuanTie 커널 트리(linux-6.6.36 브랜치)에 업스트림 백포트 패치 한 건이 병합되었으며, 제목은 riscv: mm: Apply T-Head PMA memory-type errata to PUD and P4D entries이다. 패치 설명에 따르면: Damo Academy XuanTie의 PMA 메모리 타입 정오표는 페이지 테이블 항목을 구성할 때 ALT_THEAD_PMA()를 통해 PMA 타입 비트를 주입하는데, 이전에는 pfn_pte(), pfn_pmd(), pfn_pgd()와 pte_modify()만 커버했고 pfn_pud()와 pfn_p4d()는 커버하지 않았다. 따라서 PUD 레벨(1GB) 및 sv57 하의 P4D 레벨(512GB) 대형 페이지 매핑에는 XuanTie가 요구하는 메모리 타입 인코딩이 실리지 않으며, 이러한 코어에서는 암묵적/기본 PMA로 회귀하여 메모리 속성이 다른 크기의 매핑과 일치하지 않을 수 있다. 이러한 리프 항목은 선형 매핑(create_pud_mapping()이 PUD_SIZE로 설정)과 대형 페이지 vmap을 통해 도달할 수 있다.

수정 방식은 pfn_pud()와 pfn_p4d()에서 pfn_pmd()의 방식을 미러링하여 보호 값에 ALT_THEAD_PMA()를 실행하는 것이다. 커밋에는 Cc stable과 Fixes 태그(에레타 처리를 도입한 a35707c3d850을 가리킴)가 붙어 있으며, 업스트림 논의는 커널 메일링 리스트 게시물에서 볼 수 있다. 백포트는 알리바바 클라우드 측 메인테이너 서명으로 완료되었고, 본 트리 스타일에 따라 ALT_THEAD_PMA()를 u64 보호 값에 적용했다. XuanTie 코어를 사용하고 GB급 대형 페이지에 의존하는 워크로드(데이터베이스 버퍼, 가상 머신 메모리, 대형 모델 가중치 매핑)의 경우, 이는 동일 프로세스 내에서 서로 다른 매핑 크기의 메모리 속성이 일관되지 않을 위험을 제거한다.

기간 개요: RuyiAI-Stack 조직의 16개 저장소 중 모니터링 기간 내에 동작이 있는 것은 3개다: pytorch(두 차례 브랜치 푸시와 신규 병합 요청), ruyiai-daily(1회 커밋), ruyiai-stack.github.io(1회 자동 커밋); triton-riscv, tilelang-riscv, llvm-project, pytorch-ci, FBGEMM, cpuinfo, VecIntrinBench, IntrinTrans, harness, dsh-osc, torq-tile, skills, SyncBots-DeepAgents는 모니터링 기간 내 푸시가 없다.

1.1 PyTorch의 riscv 브랜치 재푸시: 96개 커밋 재정렬, 메인라인 72회 동기화 적중 0건(09-20)

날짜: 2026-09-20　출처: riscv 브랜치 커밋, 브랜치 목록

베이징 시간 09-20 08:57, 해당 fork의 riscv 브랜치(즉 저장소 기본 브랜치)에서 대규모 푸시가 발생했다: 브랜치 헤드가 ca728fab에서 6d667e1e로 변경되었다. 푸시 전 상태와 비교한 결과 둘은 이미 분기되어 있었다(96개 커밋 앞서고 22개 뒤처짐). 이는 rebase 후 재푸시되는 자동화 동기화 형태로, 기존 RISC-V 전용 패치를 비교적 새로운 업스트림 베이스라인에 재정렬한 것이다—바이트 변환의 RISC-V 수정, 선형 교차 엔트로피 ULP 허용 오차를 RISC-V에 맞게 좁힌 것, inductor 연산자 정보 테스트의 blocklist 업데이트, 그리고 ci-riscv64 워크플로 파일을 포함한다. 이 푸시는 동시에 7개의 열린 병합 요청(#23, #35, #36, #38, #43, #46, #48)의 브랜치 상태를 갱신했으며, 그중 #46과 #48은 RVV 관련 제안(ATen 벡터 확장 지원, RVV CPU 능력 보고)이다.

메인라인 main에는 같은 기간 내에 72회의 업스트림 동기화 커밋이 별도로 있었다(마지막 푸시는 베이징 시간 09-21 03:00). 내용은 PyTorch 업스트림의 통상적 의제다: precompile 모듈화와 가드 분류 지속 구축, 분산 및 체크포인트 테스트의 안정성 정비, CUDA 13.4 Windows 빌드와 ARM64 CUDA 이미지 정의 등; RISC-V, RVV, vector, XuanTie, rv64, rv32 등 키워드로 항목별 필터링한 결과 적중 0건이다. 결론: 로컬 적응의 오늘 활동은 새 연산자나 새 백엔드가 아니라 브랜치 재정렬과 CI에 집중되어 있다.

1.2 신규 병합 요청: riscv64 로컬 이미지 빌드 스크립트, 네이티브 riscv64 하드웨어 요구(09-20)

날짜: 2026-09-20　출처: PR #51 Add riscv64 local image

베이징 시간 09-20 22:54, 해당 fork는 add-riscv64-local-image 브랜치를 새로 만들었고, 23:05에 병합 요청 #51(대상 브랜치 riscv, 1개 파일, 25줄 추가)을 제출했다: .ci/docker/build-riscv64-local.sh를 추가하여 BUILD_ENVIRONMENT=pytorch-linux-noble-riscv64-py3.12-gcc14로 로컬에서 pytorch-ci:riscv64 이미지를 빌드한다. 스크립트는 먼저 세 가지 사전 검사를 수행한다—머신 아키텍처가 반드시 riscv64여야 하고(그렇지 않으면 오류와 함께 종료하며, 주석에 이미지는 네이티브 riscv64 하드웨어에서 빌드해야 한다고 명시), docker와 docker buildx가 사용 가능해야 한다—그런 다음 저장소의 기존 build.sh를 호출하여 빌드를 완료한다. 커밋 메시지는 Add riscv64 image locally이며, 설명에는 업스트림과 정렬한다고 적혀 있고 검증 항목에는 WIP로 표시되어 있다. 이는 CI 측의 “이미지 로컬화”를 보완하는 동작으로, 이전에 업스트림이나 원격 이미지 링크에 의존하던 공백에 대응한다.

5. 동향 관찰

5.1 커널과 컨테이너 양측에서 같은 날 RISC-V 전용 동작 보완: 실행 가능에서 올바른 실행으로

이번 모니터링 기간에서 가장 기술적으로 중요한 두 건의 커밋은 모두 새로운 기능을 추가하는 것이 아니라 RISC-V 특유의 시맨틱을 수정하는 것입니다. XuanTie 커널 트리는 PMA 에라타를 PUD/P4D 수준 대형 페이지까지 보완하여 GB급 매핑 메모리 속성이 다른 크기와 일치하지 않는 문제를 방지했고, openRuyi는 riscv_hwprobe를 컨테이너 seccomp 화이트리스트에 추가하여 OpenSSL과 zlib-ng가 ENOSYS로 인해 조용히 스칼라로 폴백하는 것을 방지했습니다. 두 사례의 공통된 판단 기준은 이미 ‘실행 가능한가’가 아니라 ‘하드웨어의 실제 능력과 아키텍처 제약에 따라 실행되는가’입니다. 이 수준의 패치는 일반적으로 뉴스를 생성하지 않지만, 실측 성능과 안정성을 직접 결정하므로 데일리 리포트에서 지속적으로 추적할 가치가 있습니다.

5.2 툴체인 제품 라인이 소규모 릴리스로 전환: 플러그인은 beta 채널로, 문서는 그래픽 도구 보완

VS Code 플러그인은 0.1.7-beta.1로 다음 버전 사전 릴리스를 시작했고, 문서 사이트는 같은 날 Ruyi Imager 그래픽 라이팅(플래싱) 설명을 추가했으며, 지원 매트릭스에는 SpacemiT K3 보드의 Buildroot 보고서가 추가되었습니다. 세 가지는 각각 편집기 플러그인, 이미지 라이팅, 시스템 적응이라는 세 가지 사용 경로를 커버하며, 모두 ‘진입 장벽 낮추기’를 지향합니다. ruyi 본체는 조용히 유지되고 0.53 정식 버전은 아직 버전 번호가 매겨지지 않아, 제품 리듬은 ‘주변부 선행, 본체 소화’의 형태를 보이고 있습니다.

5.3 PyTorch fork의 riscv 브랜치가 업스트림 베이스라인 재정렬로 재배치, CI 이미지 로컬라이제이션 보완

riscv 브랜치는 이번에 96개 커밋 재배치 방식으로 로컬 패치를 최신 업스트림 베이스라인으로 옮겼으며, 단기적으로 상당한 동기화 작업량과 그에 따른 회귀 범위를 가져올 것입니다. 같은 날 새로 열린 PR #51은 네이티브 riscv64 하드웨어로 CI 이미지를 빌드할 것을 요구하며, 이는 RISC-V 측 파이프라인이 여전히 기능 추진이 아니라 인프라를 보완하고 있음을 보여줍니다. RVV 관련 두 개의 오픈 병합 요청(#46, #48)은 재배치와 함께 갱신되었으나 새로운 리뷰 진행은 없으며, 여전히 이 스택에서 가장 기다릴 만한 변경입니다.

5.4 이번 기간의 공백과 관심 지점

솔직히 기록해야 할 공백: 뉴스 측에서 RuyiAI, RuyiSDK, Ruyi 커뮤니티, openRuyi에 대한 중영문 다중 쿼리가 계속 제로 히트이고, arXiv 기간 내 신규 수록 없음, ruyi와 packages-index 조용함, 벡터와 연산자 세 가지 전용 목표 저장소 모두 조용함. 관심 지점: 첫째, 0.53 정식 버전의 버전 번호 시점과 제077호 격주 진행, 둘째, openRuyi 2026.09 월간 버전 공지(이전 버전은 2026.08), 셋째, PyTorch fork 재배치 후 새로운 RISC-V 적응 커밋이 뒤따를지 여부, 그리고 PR #51의 검증 진행 상황입니다.
