오늘의 핵심: AME 백엔드가 i32 행렬 누산기를 AccReg에 고정, 설정화된 tile 연산은 전개 전으로 연기 (11-04)

날짜: 2026-11-04　출처: 커밋 f346011, PR #35

11-04 15:40(베이징 시간), RuyiAI-Stack/llvm-project의 riscv 브랜치에 커밋 f346011이 추가되었다. 8개 파일 변경, +412/−1, 작성자 caihanyi111, 협력자 caohanghang. 변경 대상은 LLVM 내 RISC-V AME 행렬 확장 백엔드 구현(코드에서 BOSCAME로 표기)이며 두 부분으로 나뉜다.

첫 번째 블록은 레지스터 분류입니다. 루프가 운반하는 누산기 PHI는 타입 테이블에서 기본 레지스터 클래스를 가져오는데, nxv32i32는 원래 TileReg로만 등록되어 있었습니다. 누산 명령 mlce32.m, mqma.*, msce32.m의 누산기 피연산자와 결과는 모두 AccReg로 제한되어 있어, 각 루프 경계마다 tile과 accumulator 두 레지스터 뱅크 사이에서 복사가 한 번씩 생성되며, copyPhysReg는 이러한 뱅크 간 복사를 단일 AME 명령으로 전개할 수 없습니다. 수정 방안은 nxv32i32에 AccReg도 함께 등록하는 것입니다. V 확장이 동시에 활성화된 대상의 경우 RVV가 해당 타입을 다시 등록하며, 기본 동작은 변경되지 않습니다. 동일 뱅크의 전체 레지스터 복사는 mmve64.t.t와 mmve64.a.a로 전개하도록 변경되었고, 뱅크 간 복사는 하드 오류로 유지되어 더 이상 레인별 인덱스 이동으로 강등되지 않습니다.

두 번째 블록은 스케줄링입니다. 각 tile 구성과 그 소비자는 emit 전까지 순서가 있고 부작용이 있는 의사 명령 안에 유지되다가 그제서야 전개됩니다. 행렬 레지스터는 할당 가능하도록 변경되었고, MMA의 누산기는 tie 처리되며, 영 누산기 정의는 이전 값을 읽지 않고, 분기 완화는 완전히 전개된 후의 크기를 포함합니다. 이 커밋은 동시에 세 가지 테스트를 추가합니다. 구성화된 load/MMA/store의 순서, 독립 누산기와 영값 정의, RVV와 비 RVV 두 가지 선택, 그리고 완화된 분기입니다.

커밋 메시지는 동기를 명시하고 있습니다. 상위 TTIR에서 BOSCAME으로의 하향 변환은 리덕션 루프가 i32 누산기를 계속 AccReg에 유지하도록 요구합니다. 이 경로는 바로 tilelang-riscv에서 내려오는 행렬 연산자 경로이며, LLVM 측에서 보완하는 것은 새 명령을 추가하는 것이 아니라 레지스터 할당과 스케줄링 계층입니다.

1.1 llvm-project: riscv 브랜치에 BOSCAME 커밋 추가, 레지스터 분류와 tile 스케줄링 보완 (11-04)

날짜: 2026-11-04　출처: 커밋 f346011, riscv 브랜치 커밋 목록

오늘 중점 사항에서 다룬 두 가지 변경 외에도, 이 커밋의 테스트 범위는 별도로 기록할 가치가 있습니다. xboscame-ordered-tiles.ll은 구성화된 load/MMA/store의 순서와 기계 검증을 다루고, xboscame-matrix-copy.ll은 동일 뱅크 복사 전개를 다루며, xboscame-matrix-copy-cross.ll은 뱅크 간 복사가 반드시 오류를 보고해야 하는 동작을 고정합니다. 커밋 메시지가 제시하는 검증 기준은 xboscame-ordered-tiles.ll의 모든 RUN 라인 통과이며, 기계 검증과 목적 파일 생성을 포함합니다.

시간선상에서 이는 riscv 브랜치가 11-03 03:57의 CI 워크플로 변경 이후 처음으로 올린 코드 커밋입니다. 브랜치의 더 이른 [RISCV] Lower IME intrinsics to SpacemiT A100 dot instructions, [RISCV] Add A100 HP/SP and pack/unpack lowering은 여전히 11-02에 머물러 있습니다. 메인 브랜치는 같은 기간 커밋이 없습니다(최신 커밋 11-02 14:48 UTC).

3.2 격주 보고 080 초안: glibc libmvec과 newlib 벡터 수학 함수 추가 (11-04)

3.3 arXiv: bf16/fp16의 RVV 자동 벡터화 조용한 성능 저하 (11-02, 모니터링 기간 외)

날짜: 2026-11-02 (모니터링 기간 외, 최근 3일)　출처: arXiv 2611.03917

모니터링 기간 동안 arXiv에는 새로운 RISC-V 관련 논문이 없었습니다. 최근 3일 동안 RVV 벡터화와 직접 관련된 연구 한 편이 있어 기록할 만합니다. 저자 Vaishnavi Kouru와 Robert Chun은 fp32, int8, bf16, fp16 네 가지 정밀도의 곱셈-덧셈 루프로 LLVM의 RISC-V 자동 벡터화를 비교했습니다. -march=rv64gcv라는 공통 기준선에서 int8과 fp32는 깔끔하게 벡터화되지만, bf16과 fp16은 대량의 스칼라 폴백으로 퇴화하며, fp16은 zvfbfmin/zvfbfwma와 zvfhmin을 추가로 활성화하지 않으면 요소별 소프트웨어 변환 호출로까지 퇴화합니다.

QEMU 사용자 모드에서의 동적 명령 수는 규모를 보여줍니다. 기준선 bf16과 fp16 커널의 실행 명령 수는 확장 버전을 활성화한 경우의 각각 17.0배와 75.9배입니다. 논문은 또한 컴파일러 진단이 실제로 이러한 퇴화를 보고하지만, 표현 방식상 「컴파일 옵션 하나 추가로 해결 가능」과 「고유한 변환 비용」을 구분하지 않아 사용자가 수정 방법을 가리키는 직접적인 신호를 얻을 수 없다고 지적합니다. RuyiAI 스택의 관점에서 이는 080호의 벡터 수학 함수 보충과 동일한 문제의 양 끝입니다. 한쪽은 라이브러리 함수가 부족하고, 다른 쪽은 기능 스위치의 가시성이 부족합니다.

4.1 VIR의 set_vl 의미 강화: 정확한 VLEN과 임의 VLEN이 두 경로로 분리 (11-04~11-05)

날짜: 2026-11-04~11-05　출처: PR #1028, 병합 커밋 dd57775, PR #1029, 병합 커밋 61ba191

zhanghb97의 두 PR이 모니터링 기간 내에 연달아 병합되어 VIR 방언에서 set_vl의 의미를 명확히 했습니다.

#1028(11-04 23:54 병합)은 rvv-vlen이 대상의 정확한 VLEN을 나타내도록 합니다: vscale = rvv-vlen / 64, 하나의 vector<[N]xT>는 N 곱하기 vscale개의 lane을 보유하며, 분할은 전체 벡터 단위로 수행됩니다. 이전에는 rvv-vlen이 최소 VLEN으로 취급되어 마스크가 모두 참인데도 코드에 남아 있었습니다. llc는 vid와 vmslt를 유지하고, 메모리 접근에 마스크를 동반하며, RoPE의 rotate_half는 slides와 마스크 선택으로 변하고, 디코딩 어텐션에서는 마스크가 오버플로하기까지 했습니다. K3의 커널은 1024비트 벡터 폭으로 구축되는데, 이것이 바로 이 경로의 전형적인 시나리오입니다.

#1029(11-05 01:32 병합)는 rvv-vlen을 주지 않는 일반 구축을 처리합니다: 이때 코드는 임의의 VLEN에 대해 성립해야 하며, strip-mined 영역은 런타임에 N 곱하기 vscale 단위로 스텝하고, 벡터는 최소 128비트로 크기가 정해집니다. 결과를 갖는 set_vl은 직접 거부되어 「rvv-vlen, 즉 정확한 VLEN이 필요함」을 보고하는데, 이 패스는 이전에는 단순히 오류만 보고했습니다. 고정 벡터는 rvv-vlen이 없을 때 원래대로 유지되며 호스트 기준으로 크기가 정해집니다. 128보다 높은 최소 VLEN을 선언하는 것은 허용되지 않습니다.

두 PR을 합친 의미는 다음과 같습니다: 의미가 더 이상 “마스크가 우연히 모두 참”이라는 것에 기대지 않고, 컴파일 시점에 이 코드가 특정 VLEN을 위해 컴파일되었는지 아니면 임의 VLEN을 위해 컴파일되었는지를 명시해야 합니다.

4.2 CI: pytorch 2.15가 테스트 매트릭스에 진입, LLVM 배포에 NVPTX/AMDGPU와 lld 활성화 (11-04)

날짜: 2026-11-04　출처: PR #1026, PR #1027, PR #1025

#1026 pytorch 2.15를 테스트 매트릭스에 추가하여 2.11부터 2.15까지 커버한다. 변경을 촉발한 것은 실제 회귀이다. 2.15에서 최신 full check가 tests/Python/AtenOps/test_resize_enlarge.py에서 실패하며, 실패는 importer 이전에 발생한다. AOT autograd의 functionalization이 이제 함수화된 텐서에 대해 resize_ 확대를 거부하며, torch.compile도 동일 함수에서 실패하여 그래프가 ResizeOp에 도달하지 못한다. 수정 방식은 테스트를 out-of-place인 aten.resize로 교체하는 것이며, 동일한 ResizeOp handler를 거쳐 동일한 MLIR을 생성하고 2.11부터 2.15까지 전체 매트릭스가 통과한다.

6.2 패키징 측의 일상 유지보수와 릴리스 정체 공존

날짜: 2026-11-05　출처: openRuyi 커밋 목록, ruyi Release 목록

openRuyi는 하루에 10건의 커밋이 있었으며, 내용은 firefox, expat과 4개의 Python 패키지, 그리고 CI 서명 방식과 워크플로 컨테이너화 실험(그중 컨테이너화는 당일 롤백)이었습니다. ruyi와 packages-index는 커밋이 없었고, 2026.10 월간 버전은 여전히 부재합니다. 배포판의 일상 유지보수는 진행 중이지만, AI 스택을 겨냥한 릴리스는 진행되지 않고 있습니다. 지난 호에서 이런 상태를 “병목은 개발이 아닌 릴리스에 있다”고 요약했는데, 이번 호에서도 배포판 측면에서는 여전히 유효합니다.

6.3 벡터 수학 보강은 먼저 문서에서 나타남

날짜: 2026-11-05　출처: 080호 초안, VecIntrinBench

080호 초안에서 가장 실질적인 내용은 glibc libmvec과 newlib의 벡터 수학 함수 포팅이며, 대응하는 벤치마크와 변환 저장소(VecIntrinBench, IntrinTrans)는 여전히 조용한 상태입니다. 이는 저수준 라이브러리의 벡터화 작업이 진행 중임을 보여주지만, RuyiAI-Stack의 중점 저장소에 커밋 형태로 나타나지 않았다는 것을 의미합니다 — RuyiSDK의 기반 컴포넌트 라인(GCC, glibc, newlib, V8)과 RuyiAI 스택의 중점 저장소는 같은 사람들, 같은 저장소가 아닙니다. 다음 호에서는 양측의 리듬을 대조해 볼 가치가 있습니다.
