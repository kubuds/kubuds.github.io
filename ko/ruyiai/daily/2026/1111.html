오늘의 핵심: ruyi 0.54.0 정식 릴리스, 호스트 ABI 호환성 검사가 사용자 명령에 진입 (11-10)

날짜: 2026-11-10　출처: ruyi 0.54.0 릴리스, 0.53.0에서 0.54.0으로 변경 비교, PR #507

0.54.0은 11-10 21:15 (베이징 시간)에 릴리스되었으며, 사전 릴리스가 아닌 정식 버전이다. 이전 버전 0.53.0은 09-24였으며, 간격은 47일이고, 중간에는 11-02의 0.54.0-beta.20261102만 있었다. 정식 버전은 해당 사전 릴리스 대비 버전 번호 커밋 하나만 추가되었으며, 기능 면은 사전 릴리스의 전체 내용이다. 0.53.0부터 계산하면 이 버전은 총 71건의 커밋, 74개 파일이다.

핵심 기능은 ELF ABI 호환성 정보의 수집과 매칭입니다. 미리 컴파일된 바이너리가 대상 기기에서 실행될 수 있는지는 ELF 파일 헤더에 흩어져 있는 여러 사실에 달려 있습니다. 어떤 동적 라이브러리가 필요한지, 그 라이브러리에 어떤 심볼 버전을 요구하는지, 그리고 아키텍처 관련 능력 요구 사항이 무엇인지입니다. 이전에는 소프트웨어 소스 어디에도 이 정보가 기록되지 않았지만, ruyi는 이제 이 정보를 스캔해 저장하고 설치 전에 비교합니다.

수집 범위는 아키텍처별로 나뉩니다. x86-64는 ISA feature level을 기록하고, AArch64는 BTI와 PAC를, RISC-V는 ISA 문자열을 기록합니다. RISC-V 쪽이 가장 공수가 많이 드는데, 확장이 버전 번호로 문자열을 구성하기 때문입니다. 이번 커밋에는 버전이 붙은 단일 문자 확장의 파싱, 호스트 부동소수점 ABI에 따른 ld.so.cache 항목 필터링, 그리고 스택 정렬 요구 사항을 계산에 넣는 작업이 포함되어 있습니다. 호스트 측에서는 x86-64와 AArch64 탐지도 구현했으며, 호스트 라이브러리는 요청된 soname으로 해석하고 해석할 수 없는 soname을 만나면 판정 실패 대신 “미확정”으로 보고합니다.

사용자에게 보이는 변화는 세 가지 명령에 나타납니다. ruyi list는 비고에 호스트 호환성을 표시하고(비바이너리 패키지는 해당 항목을 숨김), ruyi install은 호환되지 않는 패키지를 설치할 때 경고하며, ruyi admin check-abi는 문제 해결용으로 제공됩니다. 데이터 측면은 저장소 측의 ABI sidecar를 통해 이루어지며 distfile 이름으로 해석합니다. rescan-package-abi와 플러그인 산출물에는 아카이브에 선행 디렉터리가 있는 경우를 처리하기 위해 strip-components가 새로 추가되었습니다. sidecar에는 크기 상한이 있으며, 손상된 sidecar는 “ABI 정보 없음”으로 간주되어 버려지고 전체 설치를 실패시키지 않습니다.

또 다른 부류는 패키지 가져오기 경로의 수정입니다. #509는 비 2xx HTTP 응답을 있는 그대로 오류로 보고하고, 실패한 최초 다운로드를 버리며, 멈춘 전송에 상한을 추가합니다. 이런 변경은 눈에 띄지 않지만, 미러 사이트에서 수백 메가바이트의 툴체인을 받아야 하는 패키지 관리자에게는 새 기능보다 체감에 더 큰 영향을 줍니다.

설계 문서 docs/elf-abi-compat-design.md는 버전과 함께 저장소에 포함되며, 릴리스 노트가 제시하는 설치 경로는 여전히 PyPI와 서비스 제공 미러 사이트이고, 단일 파일 바이너리는 이름을 ruyi로 바꿔야 사용할 수 있습니다.

오늘의 핵심: triton-riscv, RISC-V 호스트에서 AMD GPU 백엔드 기본 활성화 (11-10)

날짜: 2026-11-10　출처: PR #110, README

PR #110은 11-10 17:51(베이징 시간)에 “GPU 백엔드 기본 활성화”라는 제목으로 병합되었습니다. 변경 사항은 세 가지입니다. 기존 Buddy LLVM SDK로 riscv64용 AMD codegen 라이브러리를 빌드하고 패키징하는 것, riscv64에서 CPU와 GPU 드라이버 중 하나를 선택할 때의 모호함을 수정하는 것(규칙은 사용 가능한 GPU를 우선 선택), 그리고 드라이버 계층에서 선택을 모호하게 만들던 판단을 고치는 것(해당 파일은 순수하게 네 줄이 삭제됨)입니다.

검증은 실기에서 이루어졌습니다. SG2044에 RX 7900 XTX를 장착하고 torch와 ROCm은 openRuyi의 소프트웨어 저장소에서 가져왔습니다. GPU 장치를 숨겼을 때 CPU로 자동 폴백되는지도 별도로 테스트했습니다. 이 기준은 “컴파일이 통과된다”보다 훨씬 엄격합니다. RISC-V 호스트가 실제로 커널을 AMD 카드로 보내 실행했으며 CPU에서 대체 실행한 것이 아님을 보여주기 때문입니다.

README에는 AMD GPU 사용법 섹션도 동기화되어 추가되었습니다. ROCm이 설치되어 있으면 백엔드는 torch.version.hip를 통해 자체 활성화되며 작성 방식은 업스트림 튜토리얼과 같습니다. wheel에는 ROCm 런타임이 포함되지 않으므로 torch와 ROCm은 별도로 설치해야 합니다. CPU로 강제 폴백하려면 TRITON_DEFAULT_BACKEND=triton_shared를 사용합니다. 변경은 총 여섯 개 파일에 걸쳐 있으며 README, backend/driver.py, 그리고 scripts 아래의 build, env, release, setup 네 스크립트에 집중되어 있습니다.

기억해 둘 시간 차이가 하나 있습니다. 같은 날 10:22(베이징 시간)에 나온 야간 버전 nightly/2026-11-10-209274f는 커밋 209274f에 올라가 있어 이번 병합보다 이르므로, 이 패키지에는 아직 GPU 백엔드가 포함되지 않았습니다. 이를 받으려면 다음 야간 버전을 기다려야 합니다.

전체 스택 관점에서 이는 노선 차원의 변화입니다. triton-riscv는 이전에 “RISC-V CPU의 벡터 유닛에서 Triton을 어떻게 실행할 것인가”만 답했다면, 이제는 “RISC-V 호스트에서 이기종 가속기를 어떻게 구동할 것인가”도 답해야 합니다. 주요 AI 가속 카드 어느 것도 RISC-V 호스트 드라이버를 제공하지 않는 현시점에서 AMD 카드를 먼저 지원하는 것은 가장 현실적인 한 걸음입니다. ROCm의 RISC-V 측 작업은 이미 openRuyi 저장소에서 유지 관리되고 있습니다.

1. RuyiAI 스택 진척 (PyTorch / Triton / TileLang RISC-V 적응)

1.1 triton-riscv: 플러그인 이름 변경 PR 심사 중, 환경 변수 값도 함께 바뀔 예정 (11-10)

날짜: 2026-11-10　출처: PR #109, 커밋 목록

#109에서 해결하려는 문제는 이름과 실제가 맞지 않는다는 점입니다. name.conf가 설치되는 패키지 이름과 진입점을 결정하기 때문에, 현재 플러그인은 triton.backends.triton_shared라고 불리지만 보고하는 대상은 cpu이고 옵션 접두사는 이미 triton_riscv입니다. 수정 방안은 이름을 riscv로 통일하는 것이며, 그 이유는 업스트림의 명명 관행에 맞추기 위해서입니다. 즉 플러그인은 대상 패밀리(nvidia, amd)에 따라 이름을 붙이고, 장치 이름(cuda, hip)은 target에 남겨둡니다.

이에 따른 변화는 환경 변수입니다. TRITON_DEFAULT_BACKEND의 값이 triton_shared에서 riscv로 바뀌므로, 오늘 중점 사항에 있던 “CPU로 강제 복귀”하는 방식은 머지된 후에는 효력이 없어집니다. 도구 이름 triton-shared-opt와 C++ 쪽은 변경하지 않습니다. 두 번째 커밋은 이름 변경으로 영향을 받은 60개 파일에 ruff를 보완하는데, 이 파일들은 이전에 한 번도 lint된 적이 없어 19개의 기존 위반이 있습니다.

PR 상태는 열려 있으며, 11-10 18:56(베이징 시간)에도 업데이트가 있었고 아직 머지되지 않았습니다. 같은 날 업데이트된 열린 PR로는 #103(튜토리얼 보완)과 #104(BOSCAME FPGA의 SPM 예제와 AOT 계약 프런트엔드)가 있으며, 세 건 모두 “바로 시작할 수 있고 재현 가능한” 기초 작업에 속합니다.

1.2 pytorch, tilelang-riscv, llvm-project: 모니터링 기간 내 커밋 없음 (11-11 상태)

날짜: 2026-11-11(상태)　출처: pytorch riscv 브랜치, tilelang-riscv, llvm-project

세 저장소 모두 모니터링 기간 내에 커밋이 없습니다. pytorch의 riscv 브랜치 헤드 커밋은 여전히 11-04의 동기화 배치이고, tilelang-riscv는 11-03 06:13 UTC에, llvm-project의 main은 11-02 14:48 UTC에 멈춰 있습니다. 이번 기간 RuyiAI 스택의 증분은 모두 triton-riscv의 머지 1건과 검토 중 PR 1건에서 나왔습니다.

2. RuyiSDK 툴체인과 배포판

2.1 ruyi-imager: WiX를 7.0.1로 올리고 CI에서 해당 EULA 수용 (11-10)

날짜: 2026-11-10　출처: ruyi-imager 커밋 목록

굽기 도구는 모니터링 기간 내에 두 건의 커밋이 있었고, 모두 의존성 측면입니다. WiX를 이전 버전에서 7.0.1로 올렸고, 새 버전 빌드 요구 사항 때문에 CI에서 해당 EULA를 명시적으로 수용했습니다. zstd-jni는 1.5.7-26으로 올렸습니다. 전자는 Windows 설치 패키지 생성 경로와 관련되고, 후자는 이미지 압축 해제에 영향을 줍니다. 크로스 플랫폼 굽기 도구로서 이 두 커밋은 기능을 바꾸지는 않지만 CI가 여전히 패키지를 낼 수 있는지를 결정합니다.

2.2 openRuyi: 커밋 8건, 보안 수정 4건에 LLVM 스냅샷과 Wayland 스위치 (11-10)

날짜: 2026-11-10　출처: policycoreutils 커밋, lxc 커밋, cups 커밋, llvm-snapshot 커밋

패키징 저장소는 모니터링 기간 내에 8건의 커밋이 있었고, 성격은 세 가지로 나뉩니다.

보안 측면 4건: policycoreutils를 3.11로 올리고 fixfiles의 수정을 백포트했으며, lxc, libmtp, cups가 각각 업스트림 보안 패치를 백포트했습니다. 이 네 건은 모두 security-fixes 표시가 붙어 있으며, 업스트림 CVE를 추적하는 일상적인 조치에 속하지만 배포판 입장에서는 당일 반드시 따라가야 하는 부분입니다.

툴체인 2건: llvm-snapshot과 clang-wrap이 같은 날 20261109로 올라갔습니다. 이 두 패키지는 RISC-V에서 셀프호스팅 컴파일 체인의 토대이자, triton-riscv가 빌드할 때 의존하는 LLVM 아카이브의 원천입니다. 스냅샷이 매일 갱신된다는 것은 다운스트림이 받는 컴파일러가 매주 바뀐다는 뜻입니다.

나머지 두 건: libssh를 0.12.2로 올리고, SDL2에서 Wayland 백엔드를 활성화했다(이전에는 X11 경로만 있었다). SDL2의 이 변경은 겉보기보다 데스크톱과 게임 스택에 미치는 영향이 크다. 많은 그래픽 프로그램이 SDL의 창 생성을 거치는데, Wayland 스위치를 켜야 데스크톱에서 진정한 네이티브 경로가 생긴다.

2.3 openRuyi: release 규범 저장소에서 요구사항 작성 방식과 스택 명칭 정렬 (11-10)

날짜: 2026-11-10　출처: release 규범 저장소 커밋

2.4 openRuyi 월간 리듬: 태그와 뉴스 페이지는 여전히 2026.09에 정지 (11-11 상태)

날짜: 2026-11-11(상태)　출처: openRuyi 배포판 뉴스 페이지, 릴리스 태그 목록

뉴스 페이지의 최신 두 글은 모두 10-19의 것(openRuyi-Project 포지셔닝 글과 Ruyi Firmware 릴리스)이며, 월간 버전 항목은 여전히 09-30의 2026.09이다. 저장소의 태그도 2026.09-experimental에 멈춰 있다. 05부터 09까지 매월 한 버전이라는 리듬에 따르면 10월의 월간 버전은 이 모니터링 기간까지 아직 나타나지 않았고, 패키징 저장소는 계속 일평균 수 건에서 십여 건의 커밋을 유지하고 있다. 이 두 가지는 모순되지 않는다. 롤링 패키징과 월간 정식 버전은 원래 두 개의 라인이지만, 대외적으로 보이는 “버전”은 이미 한 달째 갱신되지 않았다.

3. 벡터 확장과 연산자 최적화

3.1 벡터 관련 3개 저장소 커밋 없음, 벡터 측 증분은 VIR 리덕션과 크기 제약에 집중 (11-11 상태)

날짜: 2026-11-11(상태)　출처: FBGEMM, VecIntrinBench, IntrinTrans

벡터 관련 세 저장소는 모니터링 기간 내 커밋이 없으며, 헤드 커밋은 각각 07-13, 02-13, 06-25에 멈춰 있다. 이것이 벡터 측에 진전이 없다는 뜻은 아니다. 이번 기간의 벡터 변경은 모두 buddy-mlir의 VIR 계층에서 일어났다. 리덕션의 블록 간 병합 순서(4.4)와 vir.set_vl의 영역 제약(4.2)은 모두 어떤 벡터 명령을 생성할지를 직접 결정하는 전제 조건이다. 벤치마크와 변환 두 저장소의 침묵이 수개월째 이어지고 있다는 것은 이 라인의 투자가 여전히 측정 도구가 아니라 컴파일러에 집중되어 있음을 보여준다.

4. Buddy Compiler 동향

4.1 buddy-mlir: YOLOv8 검출과 포즈를 K3 행렬 엔진에서 실행, 가중치와 TCM 복사 두 곳 수정 (11-10)

날짜: 2026-11-10　출처: PR #1042

#1042는 Ultralytics YOLOv8을 buddy-cli의 rax 형식에 연결한다. yolov8n 검출(80개 클래스 COCO)과 yolov8n-pose(17개 키포인트)이며, 입력은 모두 320x320이다. f32 모델은 VIR 하강을 거치고, 사양에 ime: true가 적혀 있으면 SpacemiT K3의 행렬 엔진에서 실행된다.

리뷰 단계에서 보완된 두 가지 수정은 모델 자체보다 정보량이 많다. 첫째는 가중치 검증이다. 매니페스트에 params_size가 포함되어 있고, 러너는 가중치 파일이 그것과 일치할 것을 요구한다. 이전에는 가중치 파일이 짧으면 모델이 버퍼를 넘어 읽을 수 있었다. 동시에 러너가 rax 패키지만 받도록 요구하는데, 라이브러리와 가중치를 따로 줄 경우 포즈 모델이 검출 모델의 파라미터로 실행되기 때문이다. 둘째는 TCM 복사다. IME 가중치의 TCM 복사본은 가중치 주소로 캐시되는데, 새 가중치를 이미 해제된 버퍼로 읽어 들일 때 이전 복사본이 적중했다. 이제는 가중치를 적재할 때마다 커널 측의 무효화 함수를 호출한다.

사양에는 params_size와 ime_params_size가 함께 유지되어, ime: false일 때도 f32 버전을 빌드할 수 있다. 이 설계는 전날의 VIR 엔드투엔드 연결과 같은 라인이다. 같은 그래프, 두 개의 백엔드 경로, 하나의 비교 가능한 베이스라인.

4.2 buddy-mlir: vir.set_vl 영역을 하나의 블록으로 축소, 다중 블록 영역에서 연산자 누락 없이 (11-10)

날짜: 2026-11-10　출처: PR #1045

vir.set_vl의 영역 타입은 원래 AnyRegion이었고, 소스 코드에는 “영역 제한 미정”이라는 주석이 남아 있었다. 검증기와 -lower-vir-to-vector의 모든 lowering은 region.front()만 취하기 때문에, 여러 블록 영역이 검증을 통과할 수 있었고 나머지 블록의 연산자는 조용히 버려졌다. 재현은 명확하다. 하나의 set_vl 안에서 load와 store가 두 번째 블록(cf.br ^bb1 이후)에 위치하면, lowering 결과는 두 개의 빈 affine.for가 된다. 빈 영역은 검증을 통과한 뒤 pass에서 “앵커 타입을 찾을 수 없음”으로 실패한다.

수정 방안은 타입을 SizedRegion<1>로 바꾸고, 주석을 삭제하며, 검증기가 더 이상 자체적으로 빈 영역을 방어하지 않고(ODS가 먼저 블록 수를 검사), “블록에 인자가 없음”이라는 조건만 유지하는 것이다. 테스트에는 두 블록과 영역 없음, 두 가지 불법 입력을 추가했다. 이런 변경은 새 기능을 만들지 않지만, “컴파일은 되고 계산은 틀리는” 경로를 컴파일 시점 오류로 바꾸며, 그 가치는 진단 가능성에 있다.

4.3 buddy-mlir: 동적 벡터 타입과 스케일링 팩터의 출력, 파싱, 검증 보완 (11-10)

날짜: 2026-11-10　출처: PR #1046

스케일링 팩터는 이전에 속성 형식 #vir.sf<m2>로 출력되었지만, 타입 문법과 예시는 m2를 제시했다. 파싱 측에는 “오류 메시지 보완 예정”이라는 주석이 남아 있었고, 동작에는 여러 불일치가 있었다. #vir.sf<x2>와 mq는 크래시가 발생했고(파싱이 오류 없이 빈 속성을 반환하고, 타입 파서가 이를 유효한 값으로 처리), m3, m0, f128은 허용되었으며, !vir.vec<0x?xf32>는 허용되었지만 !vir.vec<?xvector<4xf32>>는 거부되고 위치가 unknown으로 보고되었다.

변경은 세 부분으로 나뉜다. 출력은 sf.str()로 바뀌었고, #vir.sf<m2>는 여전히 읽을 수 있다. 속성 측에는 genVerifyDecl을 추가하여 비율이 m 또는 f이고, 값이 2에서 64 사이이며 2의 거듭제곱이어야 한다(Python 바인딩의 기존 검사와 일치). 타입 측은 동적 차원 이전의 각 차원이 정적이고 양수여야 한다. 두 번째 커밋은 오류 위치를 실제 위치로 수정한다. 아직 형성 중인 중간 다이얼렉트에서 파서의 엄격함은 프런트엔드가 신뢰성 있게 오류를 보고할 수 있는지를 직접 결정한다.

4.4 buddy-mlir: reassoc 리덕션이 먼저 lane별로 블록을 합치도록 하여 VLEN 128 호스트의 비트 불일치 수정 (11-10)

날짜: 2026-11-10　출처: PR #1047

VLEN 128 RISC-V 호스트(SG2044의 C920 코어)에서 test_k3_w4_kernels.py의 qk_norm에 비트 불일치가 나타났다. 원인은 K3 디코딩 어텐션의 q, k 정규화가 한 헤드의 64개 f32 제곱합을 shuffle이 없는 set_vl 영역에 넣고, lowering이 호스트 기준 크기(#1037)에 따라 VLEN 128에서 두 개의 vector<32xf32> 블록(LMUL 8)이 되기 때문이다. 한편 vir.reduce는 각 블록을 순차적으로 앞 블록의 결과에 병합하며, 벡터 커널의 단일 vector<64xf32> 리덕션 순서와 다르다. LLVM은 넓은 벡터를 반으로 나누고 lane별로 더한 뒤 다시 한 번 리덕션한다. CI의 riscv64는 VLEN 256에서 실행되어 블록이 하나뿐이므로 계속 통과해 왔다.

수정 방안은 여러 블록에 걸친 reassoc 리덕션을 LLVM 방식으로 병합하는 것이다. n개 블록을 먼저 2의 거듭제곱 h까지 넓히고, p번째 블록과 p+h/2번째 블록을 더하며, 하나만 남을 때까지 반복한 뒤 마지막에 한 번 리덕션한다. 이는 같은 주제의 네 번째 수정이다(앞서 로드 시점 VLEN 검증, 호스트 기준 크기, FMA 꼬리 반올림이 있었다). 지향하는 수용 기준은 일관된다. 구현을 바꿔도 되지만 수치는 바꾸면 안 된다.

4.5 buddy-mlir: Python 파일 50개 이름 변경, A100 llc 옵션을 통합 진입점으로 수렴 (11-10)

날짜: 2026-11-10　출처: PR #1043, PR #1044

#1043은 하이픈이 포함된 Python 파일 이름 50개를 밑줄로 바꾼다. 같은 디렉터리에 이미 밑줄 이름의 파일이 있어, 하이픈이 포함된 파일은 import할 수 없고 함수도 테스트하거나 재사용할 수 없다. 변경은 models, examples, .agents/skills, tests 네 곳을 포괄하며, CMake, shell 스크립트, README와 문서의 참조도 동기화했다. MLIR 업스트림의 Python 파일 241개 중 237개가 밑줄 명명이며, 이번 변경은 업스트림 규범에 맞춘 것이다.

#1044는 YOLOv8의 IME 경로를 수정한 것입니다. lower_to_obj.sh는 A100용 llc 옵션 세트를 자체적으로 조합했는데(+zvl1024b와 -riscv-v-vector-bits-max=1024 포함), 빌드된 VLEN을 검사할 때는 후자만 사용했습니다. #1032부터 VLEN은 BUDDY_RISCV_VLEN으로 통일되어 지정되며, 다른 모델들은 모두 a100_llc_args에서 가져오고 llc가 실제로 읽은 정확한 1024를 검증합니다. 기존 스크립트는 +zvl256b나 VLEN이 없는 빌드에 속아 넘어갈 수 있었습니다. VIR은 임의의 VLEN으로 lowering되는데 object는 1024로 컴파일되는 것입니다. 이제 스크립트는 통일된 진입점이 제공하는 옵션을 직접 추가하고, VLEN 1024를 충족하지 못하면 중단하며, 스텁 도구로 실행하는 테스트를 새로 추가했습니다.

4.6 buddy-mlir 야간 빌드는 0.1.4.dev20261105에 정체, 6건 머지되었으나 패키지 미출시(11-11 상태)

날짜: 2026-11-11(상태)　출처: Release 목록, 커밋 목록

최신 야간 빌드는 여전히 11-05의 0.1.4.dev20261105입니다. 이후 11-06의 SPM 머지, 11-08의 VLEN 변경 2건, 11-09의 VIR 컨볼루션 머지, 그리고 이번 모니터링 기간의 6건까지 모두 패키지가 나오지 않아 벌써 5일 연속 야간 빌드가 없습니다. 야간 빌드는 triton-riscv의 의존 항목이며 renovate가 자동으로 버전을 따라가므로, 업데이트가 멈추면 다운스트림에서 이 십여 건의 변경을 받을 수 없게 됩니다. 여기에는 4.4의 비트 일치성 수정도 포함됩니다.

5. 커뮤니티와 활동 및 공식 홈페이지

5.1 공식 홈페이지 세 페이지 변화 없음, 블로그 2편, 문서 23장(11-11 상태)

날짜: 2026-11-11(상태)　출처: RuyiAI 공식 홈페이지

index, blog, docs 세 페이지의 해시는 지난 점검과 동일합니다. 블로그는 여전히 2편(Triton의 RISC-V 적응, PyTorch RISC-V CI 실천)이며 문서 인덱스는 23장입니다. 이번 기간 triton-riscv의 GPU 백엔드는 사이트에서 가장 보충할 만한 내용인데, 아직 해당 글이 없습니다.

5.2 포럼 모니터링 기간 내 새 글 없음, 격주 진행 상황 최신은 여전히 080호(11-11 상태)

날짜: 2026-11-11(상태)　출처: RuyiSDK 커뮤니티 최신 토픽, 격주 진행 상황 080호

포럼 모니터링 기간 내 새 주제는 없으며, 최신 글은 여전히 11-06의 전재 글(Infineon RISC-V 자동차 MCU)입니다. RuyiSDK 격주 진행 상황 최신은 11-05의 080호이며 081호는 아직 발표되지 않았습니다. 080호에서 밝힌 기준은 0.54가 11월 중순 전후로 발표된다는 것이며, 오늘 이 버전이 예정대로 나왔으므로 다음 격주 진행 상황에서 정식 버전 내용을 함께 다룰 것입니다.

5.3 ruyiai-daily 아카이브가 11-08호에서 정체(11-11 상태)

날짜: 2026-11-11(상태)　출처: ruyiai-daily 커밋 목록

데일리 정보 저장소의 마지막 커밋은 11-08 06:21(베이징 시간)로 11-08호에 해당합니다. 11-09, 11-10, 11-11 세 호는 모두 생성되지 않았습니다. 이전에는 이 저장소가 매일 한 호씩 나왔는데 이번에는 벌써 3일 끊겼습니다.

5.4 외부 뉴스 적중 없음, arXiv 최신은 11-03에 정체(11-11 상태)

날짜: 2026-11-11(상태)　출처: Google News, arXiv RISC-V 검색

RISC-V 일반 수집 모니터링 기간 내 반환된 것은 모두 개인 학습용 CPU 저장소, 교육용 파이프라인 구현, Infineon AURIX RC1 관련 툴체인 글로 Ruyi 커뮤니티와 무관했습니다. RuyiAI, RuyiSDK, Ruyi, openRuyi, Buddy Compiler 다섯 그룹의 지정 검색은 적중이 없었습니다. arXiv의 RISC-V 검색 최신 논문은 11-03이며 모니터링 기간 내 새 논문은 없습니다.

6. 트렌드 관찰

6.1 0.54의 릴리스 간격이 두 배로 늘어난 대가는 세 가지 아키텍처에 걸친 ABI 수집

0.52에서 0.53까지는 22일, 0.53에서 0.54까지는 47일이 걸렸습니다. 두 배로 늘어난 이 기간 동안 커밋은 거의 한 줄기에 집중되었습니다. ELF ABI 호환성을 “기록 없음”에서 “수집 가능, 저장 가능, 비교 가능, 설치 전 경고 가능”으로 끌어올린 것입니다. 이 경로는 x86-64의 ISA level, AArch64의 BTI와 PAC, RISC-V의 버전화된 확장 문자열을 동시에 다뤄야 하므로, 세 번의 유사한 코딩이 아니라 세 가지 아키텍처에 대한 지식입니다.

주목할 점은 이것이 먼저 패키지 관리자에 적용되었고, 특정 배포판의 품질 프로세스에 적용된 것이 아니라는 것입니다. 패키지 관리자는 “사용자가 설치를 클릭하는” 바로 그 순간에 판단을 내릴 수 있는 유일한 위치이며, 호환성 판단을 여기에 두는 것은 배포판 수준의 검증 비용을 로컬 비교 한 번으로 앞당기는 것과 같습니다.

6.2 “설치 가능 여부”가 처음으로 계산 가능한 사실이 되다

RISC-V의 파편화는 명령어 집합 자체에 있는 것이 아니라 베이스라인에 있습니다. 동일한 riscv64 바이너리가 RVA20 보드에서는 실행되지 않을 수 있고, 벡터 유닛이 없는 코어에서는 곧바로 불법 명령어가 될 수도 있습니다. 이전에는 이런 문제를 문서와 포럼 답글, 그리고 시행착오에 의존해 해결했습니다. 0.54는 각 패키지의 동적 라이브러리 요구사항, 심볼 버전 및 아키텍처 기능 요구사항을 sidecar로 작성하고, 호스트 측에서 해당 사실을 탐지해 비교합니다. 그리하여 “이 패키지는 설치할 수 없다”가 하나의 경험에서 재현 가능한 결론으로 바뀌었습니다.

부작용은 데이터 유지보수입니다. sidecar는 패키지와 함께 업데이트되어야 하고, strip-components 같은 아카이브 차이는 별도로 처리해야 하며, 잘못된 sidecar에는 명확한 폴백 전략이 있어야 합니다. 0.54는 이런 주변부까지 코드에 반영했는데, 이는 설계 시 유지보수 비용을 이미 계산했음을 보여줍니다.

6.3 RISC-V 호스트 + AMD 카드가 메인라인에 진입

triton-riscv는 “RISC-V 벡터 유닛에서 Triton 실행”에서 “RISC-V 호스트에서 AMD GPU 구동”으로 확장되었으며, 기본 경로는 GPU를 직접 선택합니다. 이 조합은 이전에 벤더 데모에서만 등장했지만, 이제 기본 브랜치에 들어갔고 실제 하드웨어 검증(SG2044 + RX 7900 XTX)도 갖추었습니다.

현실적 의미는 다음과 같습니다. 주류 AI 가속 카드의 호스트 드라이버 생태계는 거의 모두 x86과 Arm을 위해 준비되어 있어, RISC-V 머신은 오랫동안 CPU로만 추론을 실행해야 했습니다. RISC-V 호스트가 커널을 소비자용 AMD 카드로 보내도록 하는 것은 이 생태계 공백을 우회하는 가장 손쉬운 길입니다. ROCm은 RISC-V에서 이미 유지보수되고 있으며, 빠진 것은 컴파일러 백엔드라는 한 고리뿐입니다.

6.4 VIR의 수정 대상이 “잘못 계산”에서 “조용한 오류”로 전환

이번 모니터링 기간 buddy-mlir의 6건 중 최소 3건은 “오류를 보고하지 않지만 결과가 틀린” 문제를 겨냥합니다. 다중 블록 set_vl 영역에서 연산자가 조용히 누락되거나, 스케일 팩터 파싱이 크래시하거나 불법 값을 통과시키거나, 블록 간 리덕션 순서가 수치를 바꾸는 경우입니다. 앞의 두 유형은 이전에 컴파일러가 조용히 잘못된 결과를 생성하게 했지만, 이제는 컴파일 시점 오류가 됩니다. 세 번째 유형은 바이트 단위 비교를 통해서만 잡을 수 있습니다.

이런 문제들의 공통점은 수정 비용은 낮고 발견 비용은 높다는 것입니다. 이들이 이 단계에서 일괄 정리될 수 있다는 것은 VIR에 이미 실제 하드웨어에서 실행하고 베이스라인과 비교할 수 있는 테스트 범위가 갖추어졌음을 의미합니다. K3와 SG2044에서의 대조가 없다면, 4.4의 VLEN 128과 256 차이는 결코 드러나지 않았을 것입니다.
