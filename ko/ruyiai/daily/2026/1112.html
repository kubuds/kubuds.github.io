날짜: 2026-11-11　출처: 격주 진행 상황 080호 (커뮤니티 포럼), wechat-articles 요약 커밋 #405

080호는 11-11 17:53(베이징 시간)에 RuyiSDK 커뮤니티 포럼에 게시되었으며, 11-05의 저장소 내 초안으로부터 엿새 만이다. 이번 호는 “도구 3연발”의 마무리다. 패키지 관리자 0.54.0, Ruyi Imager 1.1.0, VS Code 플러그인 0.1.7이 함께 명시되었는데, 이 가운데 0.54.0과 Imager 1.1.0은 이번 모니터링 기간 내의 정식 버전이고, 플러그인의 0.1.7은 실제로는 09-28의 버전이며 그 이후 이미 0.1.8-beta.1(10-30)이 있으므로, 여기서는 초안 기준을 그대로 따랐으니 독자는 이를 새 버전으로 간주하지 않는 것이 좋다.

패키지 관리자 항목은 지난 호 데일리 리포트의 0.54.0과 동일한 사안이며, 080호에서 보강한 것은 테스트 기준이다. 0.54.0-beta.20261102와 플러그인 v0.1.7이 출시 기준을 충족하는 것으로 판정되었으며 상세 내용은 테스트 리포트를 참고하기 바란다. 툴체인 측은 pygit2의 Python 3.15 적응을 기다리는 관계로 당분간 3.15에서 CI를 돌리지 않으며, 이것이 이번 호의 유일한 명시적 연기 항목이다. 다음 버전은 11월 말로 예정되어 있다.

컴파일러 측은 이번 호에서 가장 알찬 내용이다. RISC-V GCC의 세 가지 백엔드 최적화가 10-27에 GCC 개발 메인라인에 진입했다(r17-5638, r17-5639, r17-5640). Zba는 시프트 덧셈과 정수 나눗셈, 나머지 연산의 조합 인식을 보완한다. Zbs는 bclr 자체의 시프트 인덱스 의미론을 활용해 불필요한 마스크를 제거하여 RV32/RV64 비트맵 연산의 코드 생성을 개선한다. Zbkb는 packh의 비용 모델과 매칭 우선순위를 수정한 것으로, 이전에는 Zbb와 Zbkb가 동시에 활성화될 때 더 나은 명령어를 선택할 수 없었다. 세 건 모두 회귀 테스트를 포함한다. RISE-CI 측은 컨테이너 서비스와 GitHub Actions를 연동했고, multilib 빌드 시나리오 점검을 새로 추가했으며, 대형 모델을 활용한 CI 오류 평가 연동을 계획하고 있다. 성능 평가는 SPEC CPU 2026으로 전환하기 시작했으며, 우선 환경과 리소스 평가를 수행하여 K3에서 전체 SPECspeed 2026을 구동할 때의 메모리 부족 문제를 식별했다.

LLVM 측에서는 RISC-V P 확장과 GlobalISel 관련 PR 여섯 건이 업스트림에 병합되었다(#235306, #235245, #234450, #237815, #238214, #234484). 이들은 팩형 곱셈-누산의 누산 병합, RV32에서 64비트 funnel shift의 분기 제거, 그리고 XTHeadBb에서 좁은 타입의 선행 영(leading zero) 및 후행 영(trailing zero) 카운트의 확장에 집중되어 있다. RuyiSDK 자체 LLVM 브랜치에는 두 건이 더 있다. Ztt 규격과 intrinsics 문서 v0.6에 따라 RV32/RV64 행렬 확장을 초기 지원하며(#169, 어셈블리 디스어셈블리, Clang 타입과 intrinsics, IR과 코드 생성, M/A/CC 레지스터 할당 및 스필 처리 포함), AME 브랜치에 GitHub Actions CI를 보강했다(#170).

런타임과 언어 측에서는 각각 한 건씩 기록할 만하다. OpenJDK의 JEP 544(AOT 정적 컴파일) RISC-V 이식이 기능 테스트를 통과하고 성능 이득이 예상에 부합하여 메인라인에 병합되었다(#32311). 그 외에도 RISC-V 관련 PR 열 건이 메인라인에 진입했고 세 건이 17u/21u/25u로 백포트되었다. V8의 리뷰 목록에는 “Allow vlen=1024”(CL8585179)가 등장하는데, 이는 이번 호 buddy-mlir의 두 K3 수정과 동일한 하드웨어적 사실을 가리킨다. Go 측에서는 CL 다섯 건이 제출되었으며, 그중 RVV로 GreenGC의 filterNil을 구현한 것이 병합되었다.

커뮤니티와 콘텐츠 측면: packages-index는 SpacemiT K1/K3용 GNU 툴체인 적응을 추가하고 일부 패키지에 ABI 호환 정보를 보강했다. 개발 보드 지원 매트릭스에는 Milk-V Jupiter2의 Bianbu 4.0.1과 SpacemiT K3 Pico-ITX의 Bianbu 4.0.8 LXQt 중영문 리포트를 신규 추가하고, VisionFive 2 Lite의 Ubuntu 24.04.5 리포트를 갱신했다. 예제 저장소에는 HiFive Premier P550의 Dhrystone과 SiFive Kernel Library 중국어 예제, Jupiter2의 llama-server 배포 예제를 보강하고, K3의 ROS 2 강좌 진입점을 제11장에서 제15장(스캔 매칭, SLAM과 위치 추정)까지 확장했다.

오늘의 중점: buddy-mlir, VLEN 1024에서의 리덕션 레인 유실 수정, 스물다섯 개 테스트 오류에서 정상으로 (11-11)

날짜: 2026-11-11　출처: PR #1051

PR #1051은 11-11 23:51(베이징 시간)에 병합되었으며, 긴 벡터 하드웨어에서만 나타나는 오류를 수정한 것이다. 폭이 1인 가변 길이 벡터에 대해 vir.reduce를 수행하면 결과에 lane 0만 남는 문제였다. 원인은 VIR 자체의 정규화가 아니라 다운스트림에 있었다. vector.reduction의 ElideSingleElementReduction이 vector<[1]xT>를 “요소가 하나뿐인” 벡터로 간주하여 vector.extract로 lane 0을 추출한 뒤 누산기와 병합하도록 재작성하면서, 나머지 vscale - 1개의 레인이 사라진 것이다.

트리거 조건은 VLEN 1024입니다. 16개의 f32 영역은 하나의 벡터 안에서 vector<[1]xf32>(vscale 16)가 되지만, VLEN 128과 256에서는 vector<[4]xf32> 및 그보다 넓어서 이 경로에 도달하지 못합니다. 작성자는 SpacemiT K3의 A100 코어에서 실측했는데, 25개 리덕션 테스트 전부가 잘못된 값을 내놓았습니다. 예를 들어 512개 값의 amax는 4.101이 아니라 1.853이 나왔습니다. 같은 테스트 묶음이 CI의 riscv64 runner(VLEN 256)에서는 통과합니다. 바로 이것이 이런 결함이 발견되기 어려운 이유입니다. CI의 벡터 폭이 출하 하드웨어의 폭을 커버하지 못합니다.

수정 방식은 정규화를 우회하여, vector.reduction이 최종적으로 내려가는 LLVM intrinsics로 직접 리덕션을 구성하는 것입니다. 부동소수점은 llvm.vector.reduce.fadd를 누산기를 시작값으로 사용하고, fmax는 maxnum과 누산기를 연결하며, vir.reduce의 두 lowering을 모두 변경합니다. 작성자는 이것이 splat의 broadcastTo와 동일한 우회 기법이라고 명시했습니다. 함께 제공되는 테스트는 tests/Conversion 아래의 VIR 케이스로 들어가며, check-buddy가 x86(main의 LLVM 사용)과 SG2044 네이티브 양쪽에서 통과합니다.

이 스택에 대한 의미: Triton-RISCV의 K3 상 리덕션 연산자(amax, max, mean, sum, cumsum, rms_norm, mse_loss, vector_norm, euclidean_dist, attention)는 이전에 이 보드에서 조용히 잘못된 값을 냈으며, 크래시가 아니었습니다. 수정이 끝나야 비로소 성능을 논할 자격이 생깁니다.

1. RuyiAI 스택 진행 상황(PyTorch / Triton / TileLang RISC-V 적응)

1.1 triton-riscv: 세 건의 병합 모두 릴리스 체인 수정, AMD 백엔드 문서에 ROCm 버전 torch 전제 추가(11-11)

날짜: 2026-11-11　출처: PR #111 릴리스 스크립트 수정, PR #113 공유 git 인증, PR #112 AMD 백엔드의 torch 전제

모니터링 기간 내 세 건의 병합은 컴파일러 기능을 바꾼 것이 하나도 없고 모두 릴리스 체인에 관한 것입니다. #113은 CI와 release.sh가 각각 복사해 두었던 “일회성 전역 git 설정”을 scripts/_git-auth.sh로 추출해 공유하도록 했습니다. 자체 호스팅 riscv64 runner에서 익명 git 트래픽은 인증을 받지 못하는데, 같은 호스트에 직접 curl하면 정상이었습니다. 그래서 업스트림 FetchContent가 googletest를 가져올 때 401을 반환하고 tty가 없는 상황에서 사용자 이름 프롬프트에 멈췄습니다. #111은 릴리스 스크립트 자체를 수정합니다. #112는 문서입니다. #110 병합 후 CPU 경로는 torch가 전혀 필요 없어졌으므로 README의 그 설치 명령 줄을 삭제했고, AMD 절에는 빠져 있던 반 문장을 보충했습니다. 즉 torch를 설치해야 하며, 반드시 AMD GPU를 사용할 수 있는 빌드여야 한다는 것입니다.

세 건의 작성자는 동일인(Mingzhu Yan, 중국과학원 소프트웨어연구소)이며, 시간은 17:59부터 21:11까지 집중되어 있습니다. 이번 주 우선순위는 기능 면을 넓히는 것이 아니라 야간 패키지를 재현 가능하게 만드는 것임을 알 수 있습니다.

3. 벡터 확장과 연산자 최적화

3.1 strip-mined set_vl의 레인 잔량이 반폭씩 단계적으로 감소, K3에서 YOLOv8의 핫스팟이 스칼라 내적에서 벗어나다 (11-11)

날짜: 2026-11-11　출처: PR #1050

#1050은 11-11 20:12에 머지되었다. 이전에는 strip-mine된 vir.set_vl이 선택된 폭으로만 메인 루프를 실행하고, 남은 레인은 전부 스칼라 테일 루프로 떨어졌으며, 레인 수가 하나의 벡터에 미치지 못하는 영역은 통째로 스칼라였다. K3의 A100 코어(VLEN 1024)에서 f32 YOLOv8을 실행할 때, 포즈 헤드의 51개 출력 채널이 64레인 벡터를 얻었고, 그 결과 가장 뜨거운 루프(전체 모델 시간의 5%)는 스칼라 flw + fmadd.s 내적이 되어, perf로 15만 샘플을 수집했을 때 스칼라 부동소수점 명령어가 39%를 차지했다.

수정 방식은 메인 루프 이후의 레인을 반폭, 4분의 1폭으로 순차 감소시키되, 각 단계는 최대 한 번만 사용하고 레인 순서를 따르며, 마지막에야 스칼라 테일 루프로 넘기고, 테일 루프에는 최소 폭(고정 길이 2레인, 가변 길이 [1]) 미만 부분만 남긴다. 마스크는 없다: 가변 길이 벡터는 런타임에 scf.if로 잔량을 판정하고, 고정 길이 벡터는 vl이 상수일 때 컴파일 타임에 판정하여, 이로써 어파인 테일 루프의 경계가 여전히 어파인이 되도록 한다; vl이 동적일 때는 스칼라 테일을 유지한다.

수치는 변하지 않는다—각 레인이 계산하는 연산은 동일하고, 정렬된 리덕션이 보는 레인 순서도 변하지 않았으며, 작성자는 K3에서 전방 출력의 FNV 해시로 동일 비트임을 검증했다. 이 수정은 성능을 고치는 것이지 정확성을 고치는 것은 아니지만, 그 대가로 긴 벡터 하드웨어에서 가장 뜨거운 코드 구간이 마침내 벡터 유닛으로 향하게 되었다.

포럼 모니터링 기간 내 세 개의 새 토픽: 17:53의 격주 진행 상황 080호(오늘의 중점은 이미 서술됨), 12:29의 재게시글과 11:50의 “2026-11-11 오픈소스 기술 핫이슈 뉴스 정보” 요약. 뒤의 두 글은 RuyiAI 스택과 직접적인 관계가 없다: 재게시글 제목은 알리가 핑터우거를 분할하여 홍콩에 독립 상장할 계획이라고 하지만, 이는 재게시물로서 검증되지 않았으며, 핫이슈 요약 글은 매일 정례적인 업계 정보 집계이다. 포럼의 실질적인 내용은 여전히 격주 진행 상황이라는 한 축에 집중되어 있다.

5.2 《중국과학보》 1면에 소프트웨어연구소 10년 조명, 루이 커뮤니티와 커널 동일 소스 계획이 본문에 언급됨 (11-10)

날짜: 2026-11-10　출처: 중국과학보 보도

《중국과학보》 11-10 1면에 소프트웨어연구소 RISC-V 기반 소프트웨어 팀의 10년 회고가 실렸으며, 검증 가능한 몇 가지 사실이 기록할 만하다: 루이 커뮤니티는 2024년 11월에 설립되었다; “RISC-V 커널 동일 소스” 계획은 2025년 말 기준으로 알리, ZTE 등 산업 파트너가 기여한 코드가 총량의 절반을 넘었다; openEuler와 openKylin이 발표한 RVA23 버전은 모두 이 동일 소스 커널 성과를 채택했다. 본문에서는 또한 소프트웨어 마이그레이션 도구가 “신경-기호 융합” 경로를 걷는다고 언급했다(프로그램 분석과 형식 검증으로 기반을 다지고, 대형 모델로 효율을 높이며, 엔지니어 경험을 규칙과 지식 베이스로 정제하여 경계를 획정). 이는 이미 openEuler 등 커뮤니티에 적용되었으며, 한 재학 중인 석사 과정 학생이 OpenCV에 RISC-V 백엔드와 벡터 명령 최적화를 추가하여 공식 메인라인에 병합한 사례도 있다.

본문에서 말한 “RISC-V를 위한 인공지능 컴파일러 오픈소스 프로젝트”가 바로 buddy-mlir이며, 그 VIR 커밋은 대부분 해당 팀에서 나왔다. 이 보도가 제시하는 것은 이 스택의 조직적 배경이다: 루이 커뮤니티, 커널 동일 소스, 컴파일러와 마이그레이션 도구가 같은 팀에서 나왔으며, 데일리 리포트에서 서로 다른 저장소에 흩어져 있던 변경들은 기관 차원에서 동일한 라인이다.

5.3 공식 홈페이지 세 페이지 변화 없음, 블로그 2편, 문서 23장 (11-12 상태)

날짜: 2026-11-12(상태)　출처: RuyiAI 공식 홈페이지, 블로그 페이지

index, blog, docs 세 페이지 해시는 지난 점검과 일치했으며, 블로그에는 여전히 두 편(Triton의 RISC-V 적응, PyTorch RISC-V CI 실천)이 있고 문서 인덱스는 23장이다. 최근 며칠간 triton-riscv의 GPU 백엔드와 릴리스 체인 변경에 대응하는 사이트 글은 아직 없다.

5.4 ruyiai-daily 아카이브는 여전히 11-08호에 머묾 (11-12 상태)

날짜: 2026-11-12 (상태)　출처: ruyiai-daily 커밋 목록

데일리 정보 저장소의 마지막 커밋은 여전히 11-08이며, 11-09부터 11-12까지 네 호가 생성되지 않았다. 이전까지 이 저장소는 매일 한 호씩 발행했으나, 단절이 이미 나흘째다.

5.5 외부 뉴스 및 arXiv: 모니터링 기간 내 신규 없음 (11-12 상태)

날짜: 2026-11-12 (상태)　출처: Google News, arXiv RISC-V 검색

RuyiAI, RuyiSDK, 루이(Ruyi) 커뮤니티, openRuyi 네 그룹의 중영문 표적 쿼리는 모니터링 기간 내 적중 제로였다(3일 내 《중국과학보》 보도 한 건만 있었으며, 이는 5.2에 별도 기재). arXiv의 RISC-V 벡터 검색 최신 논문은 여전히 11-03이며, 모니터링 기간 내 신규 논문은 없다. RISC-V 일반 크롤링에서 반환된 것은 대부분 교육용 파이프라인 구현과 개인 CPU 저장소로, 루이(Ruyi) 커뮤니티와 무관하다.

6. 동향 관찰

6.1 릴리스 체인이 기능에 앞선다: triton-riscv가 이번 주에 고친 것은 “패키지가 나올 수 있는가”

모니터링 기간 내 triton-riscv의 세 건 머지 중 두 건은 CI와 릴리스 스크립트, 한 건은 README의 설치 전제였으며 기능 면의 변경은 전무했다. 야간 빌드의 자체 설명 문구도 runner 상의 git 인증을 다루고 있다. 이는 정체가 아니라, 막 “실기에서 작동”에서 “GPU 백엔드 기본 활성화”로 업그레이드된 프로젝트에 재현성을 보강하는 작업이다: 자체 호스팅 riscv64 runner의 익명 git 트래픽이 인증을 받지 못하는 것은 인프라의 사소한 문제로 보이지만, 실제로는 야간 패키지가 매일 나올 수 있는지를 결정한다.

RuyiSDK 쪽과 대조하면 분명하다: 패키지 관리자가 ABI 호환성을 설치 전 경고로 만들 수 있는 것은 릴리스 체인이 이미 이런 정밀 작업을 할 수 있을 만큼 안정되었기 때문이다. triton-riscv도 같은 길을 걷고 있을 뿐, 몇 걸음 늦었을 따름이다.

6.2 VLEN 1024가 컴파일러와 런타임의 공통 압력점이 되고 있다

하루 사이 세 곳의 독립적 증거가 같은 파라미터를 가리킨다: buddy-mlir의 리덕션 레인 유실은 VLEN 1024에서만 나타나고(VLEN 128과 256은 모두 정상), strip-mined 잔여량 축소의 동인은 K3 A100 코어의 64레인 벡터이며, V8의 리뷰 명단에 “Allow vlen=1024”가 등장했다. 이전까지 이런 논의는 아키텍처 파라미터 차원에 머물렀으나, 이제는 “어떤 테스트가 어떤 폭에서 오류가 나는가”로 구체화되었다.

테스트 면에 대한 직접적 요구는 출하 폭을 커버하는 것이다: 기존 CI의 riscv64 runner는 VLEN 256이어서, 마침 #1051의 문제에서 통과했다. 이 교훈은 수정된 몇 줄의 코드보다 더 값지다. vscale과 관련된 추론은 모두 1024에서 검증해야 한다.

6.3 격주 진행의 초안일과 게시일이 엿새 차이 나므로, 그 항목은 나눠서 읽어야 한다

080호는 11-05에 저장소에서 형성되었으나 11-11에야 포럼에 게시되었다. 그래서 같은 텍스트 안에서 0.54.0과 Imager 1.1.0은 “릴리스됨”(11-10의 일)이고, 플러그인 0.1.7도 “릴리스됨”(09-28의 일이며, 이후 10-30의 0.1.8-beta.1도 있음)이다. 게시일 기준으로 통독하면 세 도구를 같은 날의 삼연속 릴리스로 착각하기 쉽다.

실행 가능한 읽기 방식은 두 층으로 나누는 것이다: 도구 버전은 Release 시간을, 컴파일러와 런타임 항목은 업스트림 머지 시간(GCC 세 항목은 10-27로 기재됨)을 본다. 데일리 리포트 쪽은 이미 이 기준으로 분리했으며, 독자가 격주 진행을 대조할 때도 이렇게 하는 것이 좋다.
