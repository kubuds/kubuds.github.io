오늘의 중점: RuyiTuner v1.8 릴리스, 주말에 실제 컴파일 비교 단계 완료, 3단계 파이프라인 구체화

날짜: 2026-09-25 ~ 2026-09-27　출처: v1.8 Release, CHANGELOG, real_compile 분할 커밋

RuyiTuner는 Ruyi 커뮤니티가 LLVM을 대상으로 만든 컴파일러 튜닝 도구로, 「최적화 시너지 분석」을 기반으로 코드 크기를 최대한 줄일 수 있는 pass 시퀀스를 자동으로 탐색합니다. 베이징 시간 09-25 오전(09:06)에 이 도구는 v1.8을 릴리스했습니다(tag는 커밋 a032c28c 「Add ruyi-cc to use pass seq into project」를 가리킴). v1.8이 v1.7(09-17) 대비 수렴한 업데이트에는 프로젝트 전체를 대상으로 공용 pass 시퀀스를 탐색하는 --search_scope project 모드(집계 적합도 GA), --max-path-length 파라미터, 그리고 scripts/ruyi-cc.sh 컴파일러 래퍼 스크립트가 포함됩니다. 이는 최적 시퀀스를 프로젝트의 정상 빌드 흐름에 연결하고(make CC=scripts/ruyi-cc.sh), 시퀀스를 점수 기준에 따라 중첩 처리하며, -fPIC / -mcmodel 등 코드 생성 옵션을 llc로 전달합니다. bzip2-1.0.2에서 전체 컴파일, 링크, 압축 해제 기능 검증을 완료했습니다. 이 중 프로젝트 수준 검색과 --max-path-length 두 부분은 이전 모니터링 기간에 각각 추적된 바 있습니다(09-22 / 09-24).

릴리스 후에도 개발은 멈추지 않았습니다. 09-25(7건, 09:06 ~ 19:31)와 09-27(6건, 16:11 ~ 18:22) 이틀 동안 v1.x 브랜치에 연속 13건의 커밋이 이루어졌고(그리고 두 번 main에 병합), 1.9 버전 라인을 「실제 컴파일 비교」가 완성되는 단계로 밀어붙였습니다. 먼저 프로젝트 수준 검색의 시퀀스를 디스크에 기록하고(09-25 17:04), 이어서 「최적 시퀀스로 소스를 실제 컴파일하고 크기 축소율을 보고하는」 단계를 메인 진입점에 추가했으며(18:27), 그 후 기능을 임시 래퍼 스크립트에서 흡수하여 scripts/ruyi-cc.sh를 삭제했습니다(19:31). 09-27에는 이 단계를 독립 스크립트 real_compile.py로 분리하여(18:10), train.py, run.py와 함께 3단계 파이프라인(단계 제목 1/3 ~ 3/3)을 구성했고, 다음을 완료했습니다. 출력을 단계에 따라 재번호 부여(열거 파일은 Step1 접두사, 시퀀스와 결과는 Step2 접두사로 변경), 시너지 쌍 탐색 중간 파일을 더 이상 디스크에 기록하지 않음(메모리 전달로 변경), --dataset이 단일 .c / .i 소스 파일을 지원, GA의 obj-size 점수를 pic 재배치 모델로 전환(x86_64에서 clang의 기본 기준에 정렬), 실컴파일 단계에서 C→IR 캐시의 .ll 파일 재사용, 프로젝트별 x86 / RISC-V 코드 크기 데이터 추출, 원리 개요도 V2.0으로 업데이트.

모니터링 기간 말 기준으로 1.9는 아직 릴리스되지 않았으며(최신 Release는 여전히 v1.8), 그 변경 사항은 CHANGELOG 「1.9 버전 변경」 항목에 완전히 기록되었습니다. 도구의 버전 및 아키텍처 범용성은 변함없이 유지됩니다(LLVM 버전과 대상 아키텍처에 구속되지 않으며, 대상은 입력 IR의 대상 트리플에 의해 결정됨). 이번 리팩터링은 기존의 「2단계 검색 + 외부 컴파일 래퍼 스크립트」 형태를 하나의 내장된 3단계 파이프라인으로 수렴시켰습니다.

2.2 지원 매트릭스: ESP32C3의 RT-Thread 5.3.1 보고서 병합(PR #406, 09-27)

베이징 시간 09-27 11:26, PR #406 「ESP32C3: add RT-Thread 5.3.1 test report」가 병합되었다(커밋 2건). 보고서는 기여자 Chen Moushun이 제출했다: ESP32-C3-DevKitM-1(rev v1.1)이 공식 ESP32_C3 BSP에서 RT-Thread를 실행하여 msh에 진입했으며, 테스트 커밋은 dc3da6d8로 고정되었다(시리얼 배너에 5.3.1이 표시되나 v5.3.1 릴리스 태그는 아님). 문서에는 두 가지 보드 레벨 세부 사항이 기록되었다——Windows 측 링커 스크립트 변경, 그리고 esptool의 min_rev 처리(해당 보드의 기본 이미지 헤더 min_rev=3은 거부되므로, 보드 내장 bootloader.bin의 min_rev를 0으로 설정해야 하며 사용된 esptool 조각을 첨부했다). 중영 이중 언어 문서 총 306줄이 추가되었다. 검토 대기열 측면에서: #397(RT-Thread Smart, Milk-V Duo S), #405(Zephyr, Milk-V Duo S), #390(VisionFive2_Lite Ubuntu)은 열린 상태를 유지하고 있으며, 모니터링 기간 내 신규 리뷰는 없었다.

5. 트렌드 관찰

5.1 주말 특례: 단일 유지보수자의 고빈도 반복 모니터링 기간

RuyiTuner는 이번 모니터링 기간 유일한 고빈도 개발 면입니다——09-25와 09-27 이틀 동안 동일 유지보수자가 연속 13건의 커밋을 푸시하고 두 번 main에 병합하여, 모니터링 기간을 걸쳐 진행 중이던 리팩토링(임시 컴파일 래퍼 스크립트에서 내장 실컴파일 단계로)을 3단계 파이프라인으로 마무리했습니다. 버전 리듬을 돌아보면: v1.6(08-31)에서 v1.7(09-17)까지 약 2주 반, v1.7에서 v1.8(09-25)까지 8일, 1.9 변경이 이미 진행 중입니다——도구 라인은 “매주 사용 가능한 증분” 속도로 반복하며, 새 모니터링 기간의 메인 스택 침묵과 대조를 이룹니다.

5.2 “릴리스-유지보수” 리듬: 0.53.0 이후 메인 저장소 침묵

ruyi 0.53.0 릴리스(09-24) 후 첫 완전한 모니터링 기간 내 메인 저장소는 테스트 서브모듈 후속 1건(#503)만 있었으며, 0.53 버전 주기 관련 세 가지 이슈(#495, #498, #501)는 현재 모두 종료되었고, 장기 추적 항목 #401(PyPI의 RISC-V 설치 준비 추적)만 여전히 오픈 목록에 있습니다. 077호의 “다음 버전 10월 말” 예고와 결합하면, 현재는 버전 간 유지보수 조용한 구간——릴리스 품질 관심점이 커뮤니티 설치 피드백으로 전환됩니다.

5.3 지원 매트릭스의 RT-Thread 라인 지속 확장

모니터링 기간 내 지원 매트릭스 유일한 병합은 ESP32-C3의 RT-Thread 5.3.1 보고이며, 최근 2주간 이 매트릭스의 RISC-V 보드 커버리지는 대부분 RT-Thread와 Zephyr 두 실시간 운영체제에서 비롯되었습니다(CH32V307, ESP32-C3 연속 업데이트). 동시에 Milk-V Duo S 플랫폼 3건(RT-Thread / RT-Thread Smart / Zephyr)은 여전히 대기열에 있습니다. RISC-V 개발 보드의 운영체제 수준 테스트 디렉토리가 지속적으로 촘촘해지고 있습니다.

5.4 이번 모니터링 기간의 공백과 관심점

공백 항목: RuyiAI-Stack 메인 스택(pytorch / triton-riscv / llvm-project 등 기능 라인) 연속 침묵, 프레임워크 측 대기와 도구 측 단독 활성의 분화가 이미 2주째입니다. 기술 정보 저장소 중단이 2주째에 진입(09-24호부터 4회 결석)했으며, 포럼과 외부 뉴스 측 모두 완전 침묵입니다. 관심점: 첫째, openRuyi 2026.09 월간 버전 공지(월말 모니터링 기간), 둘째, 지원 매트릭스 심사 중 3건의 병합 리듬, 셋째, llvm-project PR #168과 두 예비 연구 브랜치의 후속 내용, 넷째, ruyiai-daily의 푸시 재개 여부, 다섯째, ruyi 0.53.0의 커뮤니티 피드백과 새로운 issue 동향입니다.
