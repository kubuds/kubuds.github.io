1.1 llvm-project: riscv 브랜치 6일 만에 다섯 번째 리베이스, 베이스라인 다시 237커밋 전진 (10-27)

riscv 브랜치는 10-27 23:00(베이징 시간)에 다섯 번째 전체 브랜치 재작성을 완료했으며, 헤드는 a18a0434에서 ed439f3e로 바뀌었고 제목은 여전히 「[RISCV] Add A100 HP/SP and pack/unpack lowering with calibrated scheduling (#31)」입니다. 지난 호 헤드와의 비교는 diverged로 앞서 237커밋, 뒤처짐 26커밋, 300개 파일에 차이가 있습니다. 뒤처진 26커밋은 바로 로컬 패치 집합의 개수이며 10-26 기록과 완전히 일치합니다.

20건의 로컬 커밋이 같은 분 안에 재작성되어 재푸시되었고(committer 시간이 15:00:29에서 15:00:31에 집중), author 시간은 7월 1일부터 10월 3일까지 이어집니다. 최신 커밋은 이번 헤드 #31의 A100 HP/SP 및 pack/unpack 하강(author 10-03)이고, 가장 오래된 것은 #9b72a085의 CI 트리거 수정(author 7-01)입니다. author 시간은 그대로이고 committer 시간이 통일된 것은 전체 브랜치 재적용의 전형적인 특징으로, 이번 라운드에 새로운 로컬 기능이 추가되지 않았고 기존 패치 집합을 새 베이스라인 위로 옮겼을 뿐임을 보여줍니다.

리베이스 시퀀스는 이제 10-21의 1769커밋, 10-23의 275커밋, 10-25의 474커밋, 10-26의 221커밋, 10-27의 237커밋입니다. 닷새 동안 다섯 번, 간격은 하루 한 번으로 안정적입니다. 지난 호의 판단, 즉 이 브랜치의 일상적 동작이 완전히 베이스라인을 따라가는 것으로 바뀌었다는 점은 이번 호에서 두 번째로 검증되었습니다. 로컬 기능 증분의 유일한 원천은 여전히 업스트림이거나, BOSC AME, Buckyball 측이 새로운 패치를 제출하기를 기다려야 합니다.

1.2 pytorch: riscv 브랜치 6일째 조용, 메인 브랜치 20커밋도 여전히 업스트림 (10-27 상태)

날짜: 2026-10-27(상태)　출처: pytorch riscv 브랜치, pytorch 메인 브랜치

riscv 브랜치 헤드는 여전히 10-22 03:00(베이징 시간)의 Add riscv64 image locally (#51)이며, 10-22부터 10-27까지 연속 여섯째 날 커밋이 없다. 지난 호에 기록된 사흘, 닷새의 정적이 이번 호에서는 엿새로 늘어났다. RVV 역량 상향의 두 가지 메인라인 제안(#46 ATen 대상 벡터 확장 지원, #48의 RISC-V Vector CPU 역량)은 이번 호에서도 업데이트가 없다.

메인 브랜치는 같은 기간 20건의 커밋이 있었으나 전부 업스트림 동기화이며 RISC-V와 관련된 것은 한 건도 없다. 그중 다섯 건은 C++ meta kernel 보완(ne.Scalar, eq.Tensor, le.Scalar, le.Tensor, bitwise_and.Tensor)이고, 한 건은 ROCm Inductor가 CK 포워드 컨볼루션 템플릿(conv_transpose)을 건너뛰는 것이며, 나머지는 빌드와 테스트 인프라에 속한다. 이는 지난 호의 결론과 일치한다. 이 브랜치의 업스트림 추적과 RISC-V 리플레이는 리듬이 다른 두 개의 파이프라인이며, 전자는 매일 갱신되고 후자는 수동으로 시기를 고른다.

함께 읽을 만한 것은 배포 측면이다. 같은 날 openRuyi의 PR #1352가 이 브랜치의 산출물을 python-torch-ruyiai 패키지로 만들고 있다(2.2 참조). 브랜치 자체는 움직이지 않지만 그 하류 배포 경로는 움직이고 있으며, 이것이 이번 호 pytorch 일선에서 유일하게 새로운 정보가 있는 지점이다.

1.3 triton-riscv: buddy-mlir 앵커가 10-17에서 10-27로 직행, 두 단계를 건너뜀 (10-27)

날짜: 2026-10-27　출처: triton-riscv PR #90, 커밋 4a066f1f, buddy-mlir 나이틀리 버전 목록

19:43, renovate 봇이 제출한 #90이 병합되었으며 변경은 단 두 줄(+2/−2)이다. buddy-compiler/buddy-mlir가 nightly/v0.1.1.dev20261017에서 nightly/v0.1.3.dev20261027로 올라갔다. 이는 일상적인 마이너 버전 추종이 아니라 단계를 건너뛴 추격이다. 중간에 0.1.2 정식 버전(10-25 06:18)과 0.1.3 라인의 나이틀리 빌드 두 건(10-26 06:37, 10-27 08:26)이 있었다.

지난 호 데일리 리포트는 「앵커가 갱신되고 재빌드되는지」를 다음 호 관찰 항목으로 꼽았으며, 이번 호에서 실행되었다. 의미는 구체적이다. 10-26 밤의 VIR 가변 벡터 변경 일곱 건(#1002~#1008)은 그동안 buddy-mlir의 소스 트리에만 존재했고, 하류 triton-riscv 빌드는 여전히 10-17의 구 패키지를 사용하고 있었다. 앵커를 교체한 후 이 변경들이 Triton의 연산자 생성 경로에 들어오게 되었다.

분명히 해둘 것은, 앵커 갱신은 「사용할 수 있는가」만 해결할 뿐 「이미 사용했다」와 같지 않다는 점이다. triton-riscv 메인 브랜치는 이 의존성 갱신 외에 이번 모니터링 기간에 다른 커밋이 없고 대응하는 적응 코드 변경도 없다. 0.1.1에서 0.1.3 사이에 buddy-mlir 측에 Triton 호출에 영향을 주는 인터페이스 변경이 있었는지는 하류에서 실제로 재빌드하고 테스트를 통과시킨 뒤에야 확인할 수 있다.

1.4 tilelang-riscv: 메인 브랜치 열두째 날 정적 (10-27 상태)

날짜: 2026-10-27(상태)　출처: tilelang-riscv 커밋 목록, 오픈 PR 목록

4.1 VIR에 Python 바인딩 추가: buddy-opt 전용에서 프로그래밍 가능한 방언으로 (10-27)

날짜: 2026-10-27　출처: PR #1009, buddy-mlir 커밋 목록

22:42에 병합된 #1009는 이번 모니터링 기간 Buddy Compiler 측의 핵심 작업입니다. 12개 파일, +614/−1로 buddy_mlir.dialects.vir 모듈이 신규 추가되었습니다. 커밋 설명은 문제점을 직설적으로 서술했습니다. VIR에는 이전까지 Python 바인딩이 전혀 없었기 때문에, VIR의 decode attention은 ir.Operation.create("vir....")로 연산자를 조립하고 ir.Type.parse("!vir.vec<...>")로 타입을 조립해야 했으며, VIR 전체 하향도 buddy-opt라는 단일 실행 파일에서만 돌릴 수 있었습니다.

구현 방식은 「기존 방언을 따르는」 쪽을 택했습니다. ODS 정의 연산자(VIRBinding.td)에 C API와 nanobind 확장을 더한 것으로, 같은 저장소에서 quant 등 자체 타입을 가진 업스트림 방언과 동일한 구조입니다. PR 설명에 따르면 세 부분으로 나뉩니다. Ops, Types, 그리고 VIR 하향을 Python에 연결하는 pass 등록입니다.

이 단계의 의미는 도구 자체가 아니라 조합 가능성에 있습니다. VIR을 Python에서 직접 생성하고 하향할 수 있게 되면, 연산자 설명, 형상 추론, 테스트 케이스를 모두 Python 측에서 작성할 수 있으며, 프런트엔드(Triton, TileLang)와 VIR의 연동이 더 이상 C++ 측 훅 추가에 의존할 필요가 없습니다. 이전까지 단일 실행 파일에서만 검증할 수 있었던 중간 표현에게 이는 「컴파일러 내부 부품」에서 「외부에서 호출 가능한 방언」으로의 전환입니다.

#1009 병합 직후 #1011 「Cast the scalable VIR piece count to int64_t」(오픈)이 등장한 점에 주목해야 합니다. 이는 확장 가능한 벡터 경로상의 정수 폭 문제가 최근에야 다루어지기 시작했음을 보여주며, Python 바인딩은 입구를 열었을 뿐 안정성은 여전히 조정 중입니다.

6.1 표현 계층, 도구 계층, 배포 계층이 같은 날 각각 한 조각씩 보충되다

그러나 이 스택이 실제로 폐쇄 루프를 이루고 있는지 판단하려면 아직 두 가지 알려진 공백이 있다. 첫째, triton-riscv의 앵커 교체는 자동화되어 있으나 적응 검증이 아직 따라가지 못했으므로, 0.1.1에서 0.1.3 사이의 인터페이스 변화가 하위에서 노출될지는 다음 회차에야 알 수 있다. 둘째, pytorch의 riscv 브랜치는 6일 연속 커밋이 없는데 배포 측에서는 이미 이를 패키징하고 있다(#1352)——패키지가 따라가는 것은 움직이지 않는 브랜치이므로, 패키지가 머지될 때 이미 업스트림 베이스라인에 뒤처져 있을 위험을 주시할 필요가 있다.

6.2 릴리스 전 정리 외에, 배포판이 감산을 시작하다

이번 회차 openRuyi의 두 가지 작업 묶음은 성격이 다르다: 한 묶음은 가산(45건 커밋, 13개 신규 패키지, 12건 보안 업데이트, Samba 패밀리 연동 업그레이드)이고, 다른 한 묶음은 감산(세 건의 revert로 LLVM IR 동봉 배포 회수)이다. 지난 몇 회차에서 보였던 것은 모두 「릴리스 전 정리」——의존성 보충, CVE 정리, 버전 전환——였는데, 이번 회차에 처음으로 명확한 기능적 회수가 나타났다.

이는 openRuyi의 유지보수 중심이 「더 많은 패키지 커버리지」에서 「기존 패키지의 품질 경계 보장」으로 이동하고 있음을 보여준다. IR 배포 같은 실험은 패키지 크기, ABI, 인프라의 연쇄 비용을 수반하며, 릴리스 압박 속에서 우선적으로 제거된다. RuyiAI 스택에는 이중 신호다 — 패키징 채널은 더 규범화되었지만(#1350, #1352 모두 배포판 관례에 따라 항목별로 수렴 중), 「실험적 성격의 빌드 방식」(예: 내장 LLVM, 자체 vendor)에 대한 허용도 역시 동시에 낮아질 것이다. 작성자는 #1350에서 buddy-mlir의 LLVM을 패키지 내에 남기겠다고 고집했는데, 이는 정확히 이 방향에 역행하는 일종의 교섭이며 결과는 지켜볼 만하다.
