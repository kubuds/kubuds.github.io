오늘의 핵심: triton-riscv가 Triton 3.9.0 플러그인화 개편에 병합, 패치 세트 제로화, 독립 배포 패키지 퇴장 (11-05)

날짜: 2026-11-05　출처: PR #98, 커밋 목록, PR #92

11-05 11:13(베이징 시간), trdthg의 PR #98 「Bump Triton to main (3.9.0)」이 머지되었다: 커밋 5건, 파일 66개, 1806줄 추가, 3868줄 삭제. 삭제량이 추가량의 약 두 배라는 점이 이번 개편의 성격을 규정한다. 즉 기존 브랜치 위에 패치를 한 겹 더 얹는 것이 아니라, 패치를 적용하는 방식 자체를 통째로 삭제한 것이다.

첫 번째 변화는 백엔드 형태다. Triton의 TRITON_PLUGIN_DIRS 메커니즘이 backend/를 triton_shared 백엔드 플러그인으로 설치하고, 진입점을 등록하며, C++ 플러그인을 libtriton.so에 연결하고, triton-shared-opt까지 패키지에 함께 복사한다. 독립적인 triton-riscv 배포 패키지는 이에 따라 사라졌고, 코드 내 임포트는 일괄적으로 이 플러그인 이름을 사용하도록 변경되었다. 백엔드 자체는 paths.py를 통해 buddy-opt, buddy-llc, mir-translate, triton-shared-opt를 찾도록 바뀌었다. CPU 드라이버는 GPU 백엔드가 전혀 없을 때만 활성 상태가 된다고 선언한다.

두 번째 변화는 패치 집합의 소거다. patches/ 디렉터리와 패치 적용 스크립트가 모두 삭제되었다. 패치 집합이 존재했던 이유는 두 가지였다. NVIDIA/AMD 툴체인이 없는 환경에서 Triton을 빌드하는 것, 그리고 LLVM API의 잦은 변경을 흡수하는 것. 이제 buddy-mlir의 LLVM 배포판이 NVPTX/AMDGPU 타깃과 lld를 포함하고, Triton의 GPU 의존 경로를 stub 디렉터리로 돌리면 되므로 두 이유 모두 성립하지 않게 되어 패치 집합도 존재 가치가 없어졌다.

세 번째 변화는 패키징 경로의 통합이다. release.sh는 더 이상 두 번째 wheel을 조립하지 않는다. Triton의 플러그인 지원이 이미 백엔드와 triton-shared-opt를 Triton의 wheel에 넣었으므로, 스크립트는 도구만 걷어내고 바로 bdist_wheel을 실행한다. Makefile은 setup, build, test, lit, clean의 통합 진입점이 되었고, test는 lit에 의존한다.

대가는 같은 PR의 커밋 설명에 적혀 있다. Triton 3.9의 프런트엔드는 백엔드에서 backend_name 등의 필드를 읽는데, 이것이 없으면 모든 tl.atomic_* 호출이 AttributeError를 던져 riscv64에서 FlagGems 테스트 케이스 383개가 실패한다. 이번에 backend_name, default_dot_input_precision, deprecated_fp8_dot_operand_dtypes 세 필드를 보충하면서 실패 범위가 줄었다. 예제 쪽에서도 양보가 있었다. 업스트림이 asin/acos/atan/atan2의 프런트엔드 패치를 거부하여, 예제는 libdevice를 사용하도록 변경했고, 이를 통해 동일한 __nv_* extern_elementwise로 내려간 뒤 triton-shared가 MLIR math 연산자로 변환한다.

같은 경로상의 PR #92 「Rebase integration onto the official Triton v3.8.0 release」는 당일 미머지 상태로 종료되었다. 지난 호에 기록된 두 노선 간의 다툼(#92는 안정적인 3.8.0, #98은 3.9.0 메인라인 추종)은 이로써 후자로 수렴되었다.

1. RuyiAI 스택 진행 상황(PyTorch / Triton / TileLang RISC-V 적응)

1.1 triton-riscv: 빌드 진입점이 Makefile로 수렴, 백엔드는 플러그인 디렉터리 방식으로 Triton 패키지에 설치(11-05)

날짜: 2026-11-05　출처: 커밋 목록, PR #98

플러그인화 이후 백엔드의 Triton 패키지 내 임포트 경로는 triton.backends.triton_shared다. 이 체계의 설치 범위는 이전보다 좁아졌다. 더 이상 두 개의 배포 패키지가 없고, 옆에 buddy-mlir 체크아웃이 있다고 가정하지도 않는다. 문서에서 “두 패키지”에 관한 서술, 패치 단계, 동일 레벨 체크아웃 가정이 모두 삭제되었고, setup.py의 shutil.which("lit")는 LLVM 배포판에 딸린 것이 아니라 pip로 설치된 lit 콘솔 스크립트를 우선적으로 가져온다. 후자는 main() 호출 시 if __name__ == "__main__" 보호가 없는데, Python 3.14의 forkserver 멀티프로세스가 메인 모듈을 임포트할 때 이를 다시 실행하므로 lit 타깃이 동시성 80에서 실패한다.

백엔드에서 로컬 도구 경로를 찾는 방식도 변경되었다: buddy-opt, buddy-llc, mir-translate, triton-shared-opt는 모두 paths.py에서 통합적으로 해석된다. CPU 드라이버의 활성 판정은 “GPU 백엔드가 존재하지 않음”이며, 이는 이전에 환경 변수로 판단하던 방식과 다르기 때문에 다중 백엔드가 공존하는 머신에서 동작이 더 예측 가능하다.

1.2 triton-riscv: 릴리스 주기를 매일 nightly, 주말 release로 변경, pytest 병렬 처리 16으로 고정 (11-05)

날짜: 2026-11-05　출처: PR #99, Release 목록

PR #99는 릴리스 주기를 buddy-mlir와 맞춘다: 야간 작업은 nightly/<date>-<sha> 프리릴리스를 발행하고, 주말 작업은 release/<date>-<sha>를 발행하며 최신 버전으로 표시한다; 새로운 커밋이 없으면 건너뛰고, release는 모든 wheel 업로드가 완료되기 전까지 초안 상태를 유지하며, workflow_dispatch는 일회성 dev/patch 선택을 제공한다. 당일 두 건의 야간 버전이 이 주기에 따라 산출되었다: nightly/20261105-48bde12(19:50)와 nightly/20261105-849a180(22:48).

테스트 측면에서는 pytest 스위트를 16개 프로세스로 변경했다. 이 숫자를 선택한 데에는 실측 근거가 있다: 207개 테스트 케이스 슬라이스에서 1개 프로세스 360초, 8개 프로세스 89초, 16개 프로세스 67초, 24개 프로세스 67초였으며, 32와 64는 오히려 더 느렸다 — 단일 테스트 케이스는 “컴파일, triton-shared-opt, llc, 실행, 비교”의 직렬 체인이므로 프로세스가 더 많아지면 공유 컴파일 캐시를 두고 경쟁한다. 이전에 직렬로 실행할 때 flaggems 스위트는 1시간 14분이 걸렸다. setup.sh는 pytest-xdist를 설치하며, PYTEST_WORKERS로 재정의할 수 있다.

1.3 triton-riscv: stable ABI wheel이 3.12부터 3.15까지 지원, manylinux 툴체인 탐지 수정 (11-05)

날짜: 2026-11-05　출처: PR #100, PR #101

PR #100은 업스트림 Triton의 cp312-abi3 방식을 따라 wheel을 빌드한다: scripts/env.sh와 scripts/release.sh에서 TRITON_STABLE_ABI=ON을 설정하고, 제한 API(Py_LIMITED_API=0x030C0000)로 nanobind를 컴파일하며, setup.py는 wheel을 cp312-abi3로 표시한다. 하나의 wheel이 3.12 이후의 모든 인터프리터(3.12/3.13/3.14/3.15)를 지원하므로 릴리스 매트릭스가 세 개의 Python에서 하나로 줄어든다. 소스는 패치되지 않은 상태로 유지된다 — 업스트림 자체가 이 스위치를 제공하기 때문이다.

같은 브랜치에서 두 가지 빌드 스크립트 문제도 수정되었다. 첫째, release.sh가 /opt/rh/gcc-toolset-14/enable을 하드코딩하고 dnf install clang 이전에 이를 검사했는데, manylinux 이미지는 롤링 업데이트되는 :latest로서 당시 이미 gcc-toolset-15를 포함하고 있어 활성화 스크립트가 전혀 실행되지 않았고, 그 결과 clang이 crtbeginS.o, -lstdc++, -lgcc(riscv64)와 libstdc++의 <version> 헤더(x64)를 찾지 못해 두 아키텍처 모두 빌드에 실패했다; 이제는 먼저 clang을 설치한 후 존재 여부에 따라 모든 툴체인을 활성화하며, 최신 것을 마지막에 둔다. 둘째, abi3 wheel이 하나만 있게 되면서 매트릭스의 python: ["3.12", "3.13", "3.14"]는 동일한 wheel을 세 번 중복 빌드하게 된다. PR #101은 당일 제출되었으나 아직 병합되지 않았으며, 릴리스 워크플로가 체크아웃 정리 단계에서 실패하는 문제를 처리한다.

1.4 pytorch: riscv 브랜치 커밋 없음, main 55건 업스트림 동기화에 RISC-V 항목 없음 (11-06 상태)

날짜: 2026-11-06(상태)　출처: riscv 브랜치 커밋 목록, main 브랜치 커밋 목록

riscv 브랜치 모니터링 기간 내 커밋 없음, 헤드 커밋은 여전히 11-04 03:00(베이징 시간)의 [SyncBots] Integrate PyTorch at 3afdbd3입니다. main 브랜치 모니터링 기간 내 55건의 업스트림 동기화가 있었으며, 항목별로 확인한 결과 RISC-V 또는 RVV 관련 변경은 없었고 내용은 XPU/oneDNN, CUDA 컴포넌트 로딩, Mooncake 전송 및 ROCm 폴백에 집중되었습니다.

4.1 runtime에 공유 serving 생성 컨트롤러 추가, 디바이스 측 토큰 선택 지원 (11-05)

날짜: 2026-11-05　출처: PR #1018, 커밋 c2fd2e1

PR #1018은 모델에 독립적인 serving 생성 컨트롤러를 추가하며, 18개 파일, 2045줄 추가로 런타임 어댑터가 동일한 생성 토큰 예산, 중지 조건, 사용량 집계, 스트리밍 정리를 공유하도록 한다. 호출자는 LLMSession의 호스트 샘플링을 사용하거나 디바이스 측에서 직접 토큰을 제공하는 토큰 소스를 사용할 수 있다.

구현상 몇 가지 기록할 만한 점이 있다. 문자열 중지 조건은 먼저 원시 바이트로 매칭한 후 UTF-8 디코딩을 수행하여 멀티바이트 경계 오판을 피한다. 토큰 예산은 첫 번째 예측과 EOS/중지 토큰을 모두 포함한다. 고정 랜덤 시드는 0 값을 지원한다. 반복 패널티는 요청의 히스토리 윈도우 내에서 토큰 ID로 중복 제거 후 각각 한 번씩 적용된다. 첫 토큰은 prefill에서 오므로, 처리량 통계는 첫 번째 선택을 prefill로, 이후 선택을 decode로 기록하며, decode 작업이 없을 때는 처리량 0을 보고한다. 기존 CLI와 서버 진입점의 생성 경로는 변경되지 않으며, 고정 logits와 프로덕션 환경의 DeepSeek 토크나이저, 샘플러로 골든 테스트를 수행하여 출력을 보호한다. 후속 어댑터 통합은 각각 DeepSeek R1(#1021), Llama 3.1 TTNN(#1022), Qwen3-VL 등의 항목에서 추적된다.

4.2 VIR 확장 가능 벡터 lowering 보완: 브로드캐스트를 vector<[2]xT>로 전환, 커널은 llc 옵션에 따라 저하 (11-05)

날짜: 2026-11-05　출처: PR #1030, PR #1031

두 건의 midend 변경 모두 확장 가능 벡터를 대상으로 한다. vir.shuffle의 lowering은 여러 단계로 분할된다. 브로드캐스트는 먼저 vector<[2]xT>를 거친 후 전반부를 추출(vector.scalable.extract)하여 vector<[1]xT>를 얻는다. 이는 vector<[1]xT>에 직접 vector.broadcast를 수행하면 LLVM이 마스크 [0]의 shufflevector를 생성하고, 이것이 createOrFold에 의해 항등 연산으로 폴딩되어 남은 vscale-1개의 레인이 모두 poison이 되기 때문이다. llc는 insertelement를 레인 0만 쓰는 vfmv.s.f로 변환하며, 이 값이 .vf 명령어에 병합되지 않고 레지스터에 저장되면 결과가 틀려진다. [2]xT로 전환하면 llc가 vfmv.v.f를 사용하여 [1]xT의 LMUL에서 브로드캐스트를 완료하며, 명령어 수는 늘지 않고 루프에서는 오히려 하나 줄어든다. 다른 한 건은 커널이 llc의 -mattr 등 옵션에 따라 저하되도록 하며, 테스트 vir-broadcast-scalable-one.mlir가 스트리핑과 set_vl 결과 포함 두 경로를 커버한다.

4.3 나이틀리 버전 0.1.4.dev20261105로 진행 (11-05)

날짜: 2026-11-05　출처: Release 목록

6. 트렌드 관찰

6.1 유지보수 브랜치에서 업스트림 기생으로: 플러그인화가 패치 비용을 버전 바인딩으로 전환

날짜: 2026-11-05　출처: PR #98, PR #92

triton-riscv는 하루 만에 스스로를 “패치가 적용된 Triton 브랜치를 유지하는 것”에서 “업스트림 Triton의 플러그인”으로 전환했으며, 순수 삭제된 줄이 2천여 행에 달하고 패치 디렉터리가 통째로 사라졌다. 이러한 방식의 이점은 매우 직접적이다. 이후 업스트림 버전 업그레이드를 따라갈 때 패치를 재적용할 필요가 없고, 배포 산출물은 wheel 하나만 남으며, 설치 대상이 두 개의 배포 패키지에서 하나로 줄어든다.

대가는 마찬가지로 명확하며, 바로 같은 날 드러났다. Triton 3.9의 프런트엔드는 백엔드에서 backend_name 필드를 읽어오는데, 이것이 없으면 383개의 FlagGems 테스트 케이스가 실패한다. 업스트림 확장 지점에 기생한다는 것은 업스트림 프런트엔드의 암묵적 계약이 반드시 충족해야 하는 인터페이스가 된다는 뜻이며, 이러한 계약은 문서화되어 있지 않은 경우가 많아 테스트에서만 부딪혀 발견할 수 있다. 이번 개편의 성공 여부는 오늘 몇 줄을 삭제했는지가 아니라, 다음 업스트림 버전 업그레이드 시 재적용 비용과 FlagGems 같은 다운스트림 제품군에 여전히 버전을 전담 관리하는 인력이 필요한지로 판단해야 한다.

6.2 패키징 측의 데스크톱 오피스 보완과 AI 스택의 조용한 병행

날짜: 2026-11-05　출처: openRuyi 커밋 목록, RuyiAI-Stack 조직

openRuyi는 하루에 41건의 커밋을 기록했으며, 그중 37건이 LibreOffice 의존성 체인에 집중되었다. 먼저 21개의 문서 가져오기 필터, 이어서 AFDKO 폰트 툴체인, 그다음 Firebird, PDFium, ZXing, SANE, Box2D의 심사 중 PR이다. 이는 산발적인 업데이트가 아니라 컴포넌트별로 배치 단위로 진행되는 데스크톱 오피스 제품군의 완전한 패키징이다.

같은 날 RuyiAI 스택은 triton-riscv를 제외하고 모두 조용했다. pytorch의 RISC-V 브랜치는 커밋 제로, tilelang-riscv는 커밋 제로, llvm-project의 riscv 브랜치는 커밋 제로였다. 두 노선은 서로 다른 사람, 서로 다른 저장소, 서로 다른 리듬으로 추진되므로 데일리 리포트 차원에서는 분리해서 볼 가치가 있으며, 패키징 측의 활발함을 AI 스택의 진전으로 간주할 필요는 없다.

6.3 080호의 증분은 컴파일러와 런타임에 있으며, 애플리케이션 계층 프런트엔드에는 아니다

날짜: 2026-11-05　출처: 080호 원고

080호에서 가장 실질적인 네 가지는 모두 저층에 있다. GCC의 세 가지 Zb* 최적화가 메인라인에 진입, LLVM의 여섯 건 P-ext와 XTHeadBb가 병합, OpenJDK의 JEP 544 AOT 이식 병합, V8의 벡터 테일과 VLEN 처리다. 애플리케이션 계층 프런트엔드(PyTorch, TileLang)에는 이번 호에 해당하는 역량 접목이 없다.

이러한 분포는 6.1과 같은 것을 가리킨다. 이 단계의 추진 중점은 기존의 연산자와 언어 런타임이 RISC-V에서 안정적으로 실행되고 올바르게 실행되도록 하는 것이지, 프런트엔드 적용 범위를 확대하는 것이 아니다. 다운스트림 사용자 입장에서 단기적으로 체감할 수 있는 변화는 새로운 프레임워크 지원 목록이 아니라 컴파일 산출물과 JDK 동작에서 나타날 것이다.
