오늘의 핵심: K3 디코드 어텐션을 VIR로 이전, 성능이 수작업 RVV 커널과 동등 (10-28)

날짜: 2026-10-28　출처: buddy-mlir PR #1014, K3 문서, triton-riscv PR #91, llvm-project 리베이스 워크플로

가장 실질적인 진전은 09:36에 있었습니다. buddy-mlir의 #1014 「K3: write the decode attention in the VIR dialect」가 머지되었습니다(4개 파일, +476/−14). 이는 K3 w4g32 커널의 디코드 어텐션 전체를 VIR 다이얼렉트로 옮긴 작업입니다. 이것은 또 한 번의 다이얼렉트 기능 보강이 아니라, 실제 모델의 커널을 처음으로 대조 검증한 것입니다. 한쪽은 이전에 수작업으로 작성한 RVV 벡터 커널이고, 다른 쪽은 Python으로 조립한 VIR 커널입니다. 수치, 명령어 수, 보드 위의 처리량을 비교합니다.

구현 방식은 네 계층으로 나눌 수 있습니다. 구성 계층은 더 이상 연산자와 타입을 수작업으로 조립하지 않고(이전에는 문자열 안에 연산자 이름과 타입 설명을 작성해야 했음), buddy_mlir.dialects.vir의 SetVLOp, load, shuffle, fma, reduce를 사용합니다. 하나의 work item은 하나의 vir.set_vl 영역이며, 길이는 헤드 차원의 절반(64 lanes)입니다. 각 헤드는 RoPE의 두 절반으로 조립된 확장 가능 벡터이고, 영역은 해당 헤드의 (max, sum)을 반환합니다. 로테이션 계층은 q를 영역 내에서 로드하고, 회전하고, 스케일링합니다. rotate_half는 하나의 vir.shuffle로 구현되고, cos/sin은 두 행의 동일 길이 데이터로 저장되므로 더 이상 vir.from_vector가 필요하지 않습니다. 메모리 뷰 계층은 memref.expand_shape를 사용하여 q, KV cache, 출력, q의 정규화 가중치를 마지막 차원 기준으로 2×64로 분할합니다. 정규화 계층(Qwen3의 q/k norm)은 별도의 1차원 vir.set_vl 영역을 열어 _head_rmsnorm 방식으로 두 절반의 제곱합을 구합니다.

파이프라인 파라미터도 함께 변경되었습니다. 커널 하향은 vector-width=128에서 rvv-vlen=1024, use-scalable=false로 바뀌었고, 벡터 크기는 A100의 레지스터를 기준으로 분석에 의해 결정됩니다. 영역 안에 vir.shuffle이 있기 때문에 각 헤드는 128개의 f32 벡터 그룹(LMUL 4)으로 유지됩니다. 작성자는 PR에서 명확히 밝혔습니다. use-scalable=true로 전환하는 것은 다음 작업이라고. 기존 _attn_decode_fn은 유지되며, A210 커널의 디코드 어텐션은 여전히 이를 사용합니다.

결과는 세 가지 모두 확실합니다. 수치적으로는 q/k 정규화를 포함하든 하지 않든 _attn_decode_fn과 비트 단위로 일치합니다. 기계어 수준에서는 두 병렬 본체가 각각 178개의 벡터 명령어이며, 키-값 루프는 이전 버전과 명령어가 동일하고, 오버플로 레지스터의 재로드 위치 두 곳만 바뀌었습니다. 보드 처리량(K3, buddy-cli 그리디 디코딩, 3회 교대, 9쌍 생성 텍스트 완전 일치)은 세 구간 모두 동일 범위에 들어갑니다. 63 token 후 28.26~28.49 대 28.10~28.58, 458 token 후 26.82~27.13 대 27.02~27.04, 900 token 후 25.37~25.41 대 25.29~25.77입니다. 작성자 스스로 명시했습니다. 동일한 코드를 두 번 빌드할 때의 차이는 최대 2%에 달할 수 있으며, 구간은 겹친다고.

같은 날 이 주제와 호응하는 두 건의 변경이 더 있었습니다. 하나는 llvm-project의 riscv 브랜치에 244줄의 자동 리베이스 워크플로를 추가한 것(상세는 1.1)으로, 「작성자 fork의 PR이 베이스라인을 따라가지 못하는」 문제를 수작업에서 Actions로 옮겼습니다. 다른 하나는 triton-riscv의 의존성 앵커가 renovate에 의해 dev20261028로 한 단계 더 올라간 것(상세는 1.3)입니다. 다만 이 야간 빌드의 패키지 생성 시각이 당일 오전 세 건의 머지보다 이르기 때문에, 이 의존성 업데이트가 머지되더라도 다운스트림에서는 아직 #1014를 받을 수 없습니다. 오늘의 성과를 사용하려면 다음 야간 빌드를 기다려야 합니다.

1. RuyiAI 스택 진척(PyTorch / Triton / TileLang RISC-V 적응)

1.1 llvm-project: 더 이상 리베이스하지 않고, 「작성자 fork 원클릭 리베이스」 워크플로 추가(10-28)

날짜: 2026-10-28　출처: riscv 브랜치 커밋 cf00909d, 워크플로 전체, riscv 브랜치 커밋 목록

이전 회차의 「5일 만의 다섯 번째 전체 브랜치 재적용」과 달리, 이번 회차 riscv 브랜치의 로컬 패치셋은 한 건도 변동이 없습니다. 브랜치 헤드는 ed439f3e에서 한 커밋 앞으로 나아갔으며, 이전 회차 헤드와 비교하면 1건 앞서고 0건 뒤처지며 파일 1개만 변경되었습니다. 이번에 추가된 커밋(cf00909d, 작성 23:27, 커밋 23:54)은 순수 CI 자산인 .github/workflows/autorebase.yml이며, +244/−0입니다.

워크플로의 설계 의도는 주석에 적혀 있다: 작성자 소스 저장소의 기본 브랜치에 설치하고, Actions에서 대상 PR 번호를 수동으로 입력해 실행하며, 소스 저장소 자체의 GITHUB_TOKEN을 사용하고, 사용자 정의 키나 라벨이 필요 없다. 트리거 방식은 workflow_dispatch이며, 두 개의 입력이 있다 — PR 번호(필수)와 「미리보기만 하고 푸시하지 않기」(기본 활성화). 실행 환경은 ubuntu-24.04, 타임아웃은 90분; 주석은 「쓰기 권한을 보유한 상태에서 절대 PR 코드, 훅, 빌드 또는 서브모듈을 실행하지 말 것」을 명확히 요구하며, git 설정에서 hooksPath, attributesFile, fsmonitor를 모두 /dev/null로 지정하고, GIT_TERMINAL_PROMPT=0, GIT_EDITOR=true로 설정한다. 충돌 처리에는 전용 함수가 있다: -Xours로 처리할 수 없는 시나리오(수정-삭제 충돌 포함)는 개별적으로 ls-files --unmerged를 순회하며, 2단계가 있으면 로컬 것을 취하고 없으면 삭제한다; 리베이스 시에는 먼저 기준선이 이미 조상인지 판단하고, 「동등 패치」를 식별해 중복된 구 기준선 패치를 버린다.

이번 건이 해결하려는 것은 지난 여러 기간 반복적으로 나타난 구체적인 비용이다: 브랜치가 하루에 한 번 전체 리플레이되면 작성자 fork의 PR이 즉시 뒤처지고, 수작업으로 하나씩 리플레이하는 것은 느릴 뿐만 아니라 패치 집합을 쉽게 어지럽힌다. 경계를 명확히 해야 한다 — 그것이 리베이스하는 것은 다른 사람의 PR이며, 브랜치 자체의 일일 전체 리플레이는 여전히 유지관리자의 조작이 필요하다; 그것은 「기준선 따라가기」 비용을 수동 판단에서 미리보기가 포함된 한 번의 스케줄링으로 낮추지만, 자동화된 트리거 조건은 갖추지 않았다. 진정한 가치는 다음 외부 PR이 새 기준선으로 제출될 때에야 검증할 수 있다.

1.2 pytorch: riscv 브랜치 7일째 조용, 메인 브랜치 20건은 여전히 업스트림 (10-28 상태)

날짜: 2026-10-28(상태)　출처: pytorch riscv 브랜치, pytorch 메인 브랜치

riscv 브랜치 헤드는 여전히 10-22 03:00(베이징 시간)의 「Add riscv64 image locally (#51)」이며, 10-22부터 10-28까지 연속 7일째 커밋이 0건이다. RVV 기능 업스트림의 두 가지 메인라인 제안(#46 ATen 대상 벡터 확장 지원, #48의 RISC-V Vector CPU 기능)은 이번 기간에도 여전히 업데이트가 없다.

메인 브랜치는 같은 기간 20건으로, 전부 업스트림 동기화이며 RISC-V와 관련된 것은 한 건도 없다: CUDA 측 max_pool3d 슬라이스 내 64비트 인덱스 수정, 온라인 softmax 병합을 정확한 지수로 전환, symbolic shapes의 폐기 API 정리 롤백, inductor-benchmarks 이미지를 pytest 9.1.1로 고정, ATen 네이티브 연산자에 c10::irange 일괄 적용, ROCm의 rocSOLVER 배치 syevd 워크스페이스를 캐시 할당자에서 가져오도록 변경. 이 브랜치의 리듬은 지난 기간의 결론과 일치한다: 업스트림 추적은 일일 갱신, RISC-V 리플레이는 수동으로 시기 선택.

함께 읽을 만한 것은 배포 측이다: openRuyi의 #1352가 여전히 이 브랜치의 산출물을 python-torch-ruyiai 패키지로 만들고 있다(이번 기간 미갱신, 10-27에 정지). 브랜치는 움직이지 않고 패키지는 기다리고 있는데, 이것이 현재 pytorch 일선에서 가장 주시해야 할 어긋남이다 — 패키지가 병합될 때 브랜치가 이미 업스트림 기준선에 뒤처졌는지, 현재로서는 답이 없다.

하지만 이 스택이 정말로 수작업 커널을 대체할 수 있는지 판단하려면 아직 두 가지가 부족하다. 첫째는 커버리지다. 이번에는 디코드 어텐션만 옮겼고 A210 커널은 여전히 구 함수를 쓰며, MoE, 양자화, 프리필 경로는 아직 건드리지 않았다. 둘째는 확장 가능 벡터다. 이번 회차에서는 use-scalable을 명시적으로 껐는데, 다음 커밋에서 이를 켜면 벡터 크기가 더 이상 컴파일 시점에 결정되지 않고 LMUL 4의 그룹 가정이 흔들리게 된다. 그때 수치와 명령어 수를 지킬 수 있을지는 다시 대조해야 한다. 그 전까지는 「VIR이 이미 수작업 커널을 따라잡았다」를 결론으로 삼기에는 이르며, 정확한 표현은 「K3 디코드 어텐션 이 구간에서, 고정 벡터 길이 하에서 따라잡았다」이다.

6.2 기반 교체의 비용이 패치 드리프트에서 거버넌스로 이동: 워크플로가 리베이스를 인수하지만 브랜치 자체는 여전히 사람에 의존

같은 날 llvm의 riscv 브랜치는 전체 브랜치 재생을 중단하고 244줄짜리 자동 리베이스 워크플로를 추가하는 방식으로 바꿨다. 이 전환은 따로 기록할 만하다. 지난 5일의 리듬은 「하루 한 번 전체 브랜치 재생, 매번 스무 건의 커밋 흐름을 다시 씀」이었고, 작성자 시간은 그대로, committer 시간은 통일되었으며, 패치 집합 자체에는 새 기능이 없었다. 이 방식은 업스트림을 따라갈 수는 있지만, 대가로 외부 기여자의 PR은 영원히 한 칸 뒤처지게 되어 누군가 제출하려면 스스로 재생해야 한다.

새 워크플로는 이 작업을 “PR 번호 입력, 기본 사전 리허설, 원클릭 푸시”의 스케줄링으로 만들었고, 충돌은 일률적으로 riscv 측을 취하며, 중복 패치는 자동으로 폐기되고, PR 코드와 빌드는 절대 실행하지 않는다. 이는 브랜치 자체의 매일 추종을 해결하지는 않지만, “베이스라인 추종 비용”을 메인테이너의 수동 판단에서 일부 분리해냈다. 다음 단계에서 관찰할 것은 외부 PR이 정말로 이로 인해 많아지는지 여부다. 만약 워크플로가 출시된 후 2주 이내에도 여전히 새로운 베이스라인으로 제출된 외부 PR이 없다면, 병목이 리베이스 도구가 아니라 다른 곳에 있다는 뜻이다.

6.3 배포 계층의 논쟁에 가격이 붙기 시작하다: 2.81배의 빌드 시간이 “선호”보다 더 설득력 있다

#1350은 거의 한 달간 논쟁했으며, 핵심 쟁점은 buddy-mlir 자체의 LLVM을 외부화할지 여부였다. 지난 호의 입장은 여전히 “GCC를 쓸 수 있지만 최소 1.5배 시간이 든다”였는데, 이번 호 저자는 실측치를 제시했다. riscv64에서 8814초가 24798초로, 2.81배가 되었고, GCC를 사용한那次는 링크 실패로 완료되지 못했다. 논쟁의 성격은 이로 인해 바뀌었다. 기술적 선호에서 빌드 팜의 일정 산술로.

이 조항이 RuyiAI 스택에 주는 시사점은 결론이 아니라 방법에 있다. RISC-V 배포판 패키징의 많은 쟁점(vendor 여부, 툴체인 외부화 여부, IR 동봉 배포 여부)은 결국 “빌드 시간, 이미지 크기, 재현성”이라는 세 가지 측정 가능한 숫자로 귀결되어야 한다. 지난 호에서 openRuyi가 “LLVM IR 동봉 배포” 노선을 철회했고, 이번 호 #1350은 2.81배로 “LLVM을 패키지 내에 유지”를 지켰으니, 두 판단의 방향은 반대지만 근거는 동일한 유형의 비용 산정이다. 다음 관전 포인트는 이 PR이 이 숫자를 가지고 합류될 수 있는지 여부다. 만약 그럴 수 없다면, 배포판이 빌드 소요 시간에 대한 허용도가 저자의 예상보다 낮다는 뜻이며, 그것이야말로 진정으로 조정이 필요한 지점이다.
