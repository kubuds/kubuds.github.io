날짜: 2026-11-12　출처: PR #1052, PR #1053, PR #1054, PR #1055, PR #1056, PR #1057, PR #1058

11-12 08:12부터 14:44(베이징 시간)까지 buddy-mlir 메인 브랜치에 중간 단계 변경 일곱 건이 연속으로 병합되었으며, 번호는 #1052부터 #1058까지이고 작성자는 모두 zhanghb97이다. 일곱 건의 공통점은 이전에는 스칼라 루프에만 머물 수밖에 없었던 연산자 형태를 유형별로 VIR의 벡터 하강 경로에 연결한 것이다: i1 마스크, libm-only 수학 함수, bf16, fast-math 플래그, 모든 리덕션 종류, rank-0 채우기, 정수 행렬 곱. 각 건에는 lit 테스트 케이스와 정량 데이터가 포함되어 있으며, 대부분은 SG2044와 SpacemiT K3에서의 실측 결과도 첨부되어 있다.

첫 번째 #1052가 해결한 것은 메모리 접근의 진입 장벽이다. memref 요소 타입이 i1일 때, 확장 가능 벡터(scalable vector)는 이전에 곧바로 거부되었다(a memref of i1 needs fixed vectors 안내). memref는 요소당 1바이트를 차지하고 i1 벡터는 비트당 1레인을 차지하므로, 레인별 하강은 고정 길이 벡터에만 존재하기 때문이다. Triton의 load/store 마스크는 정확히 i1 memref이다: 순수 VIR 파이프라인에 확장 가능 벡터를 사용할 때, 325개의 Triton-RISCV 테스트 파일 중 179개가 이 오류에서 막혔다. 변경 방식은 바이트 단위 읽기/쓰기이다 — 연속 접근은 i8 벡터의 llvm.load/store를 사용하고, 비연속 strip-mined 영역은 vp.strided.load/store로 전체 레인을 열어 처리한다; 아울러 i1 레인을 1바이트로 크기 계산하도록 했는데, 이전에는 첫 동적 벡터가 i1인 영역을 1비트로 계산하여 VLEN 256에서 vector<[512]xi1> 같은 16개 레지스터 규모가 산출되었다.

#1053은 LLVM이 확장 가능 벡터에서 하강을 거부하는 수학 함수(erf, erfc, cbrt, powf, atan2, acosh 등)를 처리하며, 레인별 전개로 변경했다: vector<[N]xT>의 N 곱하기 vscale개 레인을 하나씩 extract하고, 스칼라 함수를 호출한 뒤 다시 insert한다. 원인은 convert-math-to-libm이 확장 가능 벡터를 고정 길이 벡터와 동일하게 처리하여 앞의 N개만 계산하고 나머지는 조용히 0으로 설정하기 때문이다 — 확장 가능 erf는 VLEN 128(vscale 2)에서 절반의 레인이 잘못된다. 효과는 테스트 범위에 직접 나타난다: Triton-RISCV의 FlagGems 스위트 4045개 항목이 SG2044(VLEN 128)에서 통과 수가 3980에서 4006으로 상승했으며, 수정된 26개 항목은 test_erf와 test_gelu이고 신규 실패는 없다.

#1054는 이번 묶음에서 검증이 가장 철저한 건이다. RVV는 Zvfbfmin이 있어야만 bf16을 벡터 레지스터에 넣을 수 있으며, 해당 확장이 없으면 LLVM은 로드 한 번조차 하강을 거부한다(Scalarization of scalable vectors is not supported). 변경은 하강기(downstream)에 rvv-mattr 파라미터를 추가하여, 기본적으로 Zvfbfmin이 있는 것으로 처리한다(Buddy의 여러 RVV 타깃인 K3의 X100과 A100, SG2044 모두 보유). 명시적으로 -zvfbfmin을 주면 정수 비트로 처리하도록 변경하여, bf16 벡터를 i16 벡터로 읽고 쓰며, extf와 truncf는 정수 연산(truncf는 최근접 짝수 반올림), absf와 negf는 부호 비트를 사용한다. 두 경로는 SG2044와 K3 두 코어에서 입력별로 비교되었다: truncf는 전체 2^32개 f32를, extf, absf, negf 및 extf-mulf-truncf는 전체 2^16개 bf16을 커버했으며, 결과는 비트 단위로 동일했다.

#1055는 strip-mined 하강에서 fast-math 플래그가 유실되는 문제를 수정했다: contract가 있는 arith.mulf와 arith.addf가 일반 fmul과 fadd로 재구성되어 LLVM이 융합하지 못했다. 이제 플래그가 동일 연산자와 함께 벡터 루프와 테일에 전달되어, f32 곱셈-덧셈이 vfmacc를 생성하고 bf16은 +zvfbfwma에서 vfwmaccbf16을 생성한다; 작성자는 K3의 X100과 A100에서 4M 레인으로 fmaf 전개를 비트 단위 비교했으며 결과가 일치했다. 이 건은 일곱 건 중 명령어 선택을 직접 변경한 유일한 건이다.

#1056 vir.reduce를 부동소수점만 인식하던 add와 maxnum에서 vector.reduction의 모든 종류로 확장했다: add, mul, minsi, minui, maxsi, maxui, and, or, xor, minnumf, maxnumf, minimumf, maximumf, 정수도 함께 지원하며 verifier가 kind와 요소 타입이 일치하는지 검증한다. 이전에는 Triton의 정수 합계, min/max, 곱셈, all/any(그리고 이에 의존하는 argmin, argmax, count_nonzero, 바이토닉 정렬과 기수 정렬)가 모두 루프에 남아 있었다. 변경은 570줄을 추가하고 9개 파일을 건드렸으며, 스칼라 꼬리는 vector::makeArithReduction의 병합기를 사용하고 vector<[1]xT>는 어제 #1051의 LLVM intrinsic 경로를 탄다.

#1057과 #1058은 두 가지 잔여 유형을 마무리한다. #1057은 rank-0 memref의 linalg.fill(대부분 리덕션의 누산기)을 한 번의 memref.store로 내렸고, FlagGems 1811개 kernel에 남아 있던 linalg.fill이 393개에서 0개로 줄었다. #1058은 정수 행렬 곱도 내려갈 수 있게 했다: A, B가 같은 정수 타입이고 C보다 넓지 않을 때 먼저 부호 또는 제로 확장을 한 뒤 곱셈-덧셈(fma 없이)을 하고, RVV에서 int8 행렬 곱은 vsext.vf2 더하기 vwmacc.vx를 얻고, 부호 없는 경우는 vzext.vf2 더하기 vwmaccu.vx를 얻는다; 같은 커밋에서 동적 형상 matmul의 단언 실패도 수정했다—M과 K가 원래 vir.set_vl 영역 안에서 취해졌는데 이후 pass가 사용 중에 지워버렸다. 수정 후 1811개 kernel에 linalg.matmul이 더 이상 없다(이전 2개, 즉 int8인 것).

오늘의 중점: triton-riscv, BOSCAME FPGA의 SPM 경로 수용, 그 외 wheel 40% 감량과 명시적 대상 -O3 전환의 오픈 PR (11-12)

날짜: 2026-11-12　출처: PR #104 BOSCAME FPGA, PR #116 wheel 슬림화, PR #117 명시적 대상 -O3

#104는 17:40(베이징 시간)에 머지되어 BOSCAME FPGA의 SPM 경로를 triton-riscv에 연결했다: AOT 계약 내보내기, lit와 통합 테스트, examples/BOSCAMEFPGA 아래의 kernel, launch와 makefile, 진입 문서는 docs/BoscameAOT.md와 예제 README다. buddy-hash.txt의 첫 줄은 SPM을 안착시킨 그 buddy-mlir 커밋을 고정해 예제와 컴파일러 버전이 맞도록 보장한다. 작성자 caihanyi111이 11-09에 올린 이 PR은 자체 테스트를 형식과 lint까지만 했고, 전체 빌드는 CI의 x64와 riscv64 양쪽에 맡겼다.

같은 날 두 건의 오픈 엔지니어링 변경이 있었고, 방향은 모두 릴리스 산출물 자체다. #116은 wheel에 포함된 LLVM과 buddy 도구가 이전에 –strip-unneeded를 사용해 디버그 섹션이 여전히 남아 있음을 지적했다: triton-shared-opt 하나에 .debug 섹션 아홉 개가 붙어 407 MB; –strip-all로 바꾸면 118 MB로 줄고, 일곱 도구의 총 페이로드가 약 970 MB에서 약 576 MB로, 원래 부피의 약 60%가 된다. 작성자는 동시에 기각된 방안도 기록했다—bin/llc를 직접 buddy-llc(LLVM llc에 buddy 패치를 더한 것)로 지정하는 것인데, buddy-llc는 출력을 다 쓴 뒤 종료하지 않아 비 IME 경로가 호출하는 일반 llc를 대체할 수 없다.

#117은 크로스 컴파일 경로의 최적화 수준을 바꾼다: RISC-V 대상 트리플을 명시적으로 주거나(크로스 컴파일, 또는 RISC-V 호스트에서 크로스 컴파일 스위치를 켤 때) 빌드 흐름이 이전에 LLVM 중간 단계를 건너뛰고 llc가 기본 최적화 수준을 사용해, MLIR이 스칼라 형태의 루프로 남아 대상 파일에도 여전히 스칼라였다. 변경은 이런 빌드에 대해 먼저 opt -O3와 llc -O3를 실행하며 트리플과 features는 llc와 일치한다; 트리플이 없는 네이티브 RISC-V 경로(llc -O0, 소스 주석에 더 높은 수준에서 오컴파일이 있다고 기록됨)와 IME 경로(buddy-llc 사용)는 그대로 둔다. 같은 커밋에서 +zvfbfmin을 기본 llc features에 추가했다—그러지 않으면 확장 가능 bf16이 llc에서 바로 중단되는데, buddy-mlir의 #1054가 바로 이 확장이 있다고 기본 가정하므로 양쪽이 반드시 동기화되어야 한다.

1. RuyiAI 스택 진전 (PyTorch / Triton / TileLang RISC-V 적응)

1.1 pytorch riscv 브랜치: CI에 Jenkins 반환 코드와 제로 케이스 통과 두 가지 판정 기준 추가 (11-13)

날짜: 2026-11-13　출처: PR #56

riscv 브랜치는 00:25(베이징 시간)에 #56을 병합했으며, .github/workflows/ci-riscv64.yml 파일 하나만 변경했다(16줄 추가, 7줄 삭제). 작성자는 yuzibo이다. 발단은 커뮤니티 CI에서 PytorchCi의 39번째 빌드에서 “빌드 성공, CI 작업 실패, 상위 작업은 여전히 통과로 기록”되는 현상이 나타난 것으로, 그중 한 가지 상황은 통계에서 failed가 0이고 pass도 0인 경우였다.

3. 벡터 확장과 연산자 최적화

3.1 i1 마스크를 바이트 단위로 읽고 쓰기, 이전에 325개 테스트 파일 중 179개가 이 항목에서 막혀 (11-12)

날짜: 2026-11-12　출처: PR #1052

i1의 확장 가능 벡터 접근은 이전에 고정 길이 벡터의 레인별 하강만 있었고, 그래서 memref 원소가 i1인 load/store는 그대로 거부됐다. Triton의 마스크가 바로 i1 memref다. 순수 VIR 파이프라인을 사용할 때 325개 테스트 파일 중 179개가 이 때문에 실패했는데, 이는 일곱 건 전체 중 영향 범위가 가장 넓은 항목이다.

하강은 이제 바이트 단위로 수행된다. 연속 접근은 i8 벡터의 llvm.load/store를, 비연속이며 strip-mined 영역에 있을 때는 vp.strided.load/store를 사용한다(마스크 전부 열림, 길이 충분히 부여). 또한 크기 수정이 한 군데 있다. 영역 내 첫 동적 벡터가 i1일 때 이전에는 1비트로 원소 폭을 계산해 VLEN 256에서 vector<[512]xi1>이 나왔고, 바이트로 읽으면 16개 레지스터 그룹이었다. 이제 i1 레인은 1바이트로 계산한다.

3.2 bf16이 Zvfbfmin 없을 때 정수 비트 연산으로 하강, 두 경로를 입력별로 대조 (11-12)

날짜: 2026-11-12　출처: PR #1054

bf16 경로는 원래 “Zvfbfmin이 있음”이라는 한 가지 가능성만 있었고, 해당 확장이 없을 때 LLVM은 가변 길이 bf16에 대해 로드조차 내리지 못했다. 이번 변경은 rvv-mattr을 파라미터로 다운그레이더에 넘기며, 기본적으로 Zvfbfmin이 있다고 가정한다(K3의 X100과 A100, SG2044 모두 보유). -zvfbfmin을 주면 정수 비트 경로로 전환한다: bf16 벡터를 i16으로 읽고 쓰며, extf와 truncf는 정수 연산을 사용하고, absf와 negf는 부호 비트를 조작하며, NaN은 규범값을 취한다.

검증 방식은 입력별 완전 열거다: truncf는 전체 2^32개의 f32를, extf, absf, negf 그리고 extf-mulf-truncf는 전체 2^16개의 bf16을 실행하며, SG2044와 K3 두 코어에서 Zvfbfmin 경로와 비트 단위로 비교한다. f8 타입 또는 (Zvfbfmin이 없을 때) bf16이 다른 연산자나 비정수 메모리 공간의 memref에 나타나면, 고정 길이 벡터 다운그레이드로 폴백한다.

3.3 리덕션이 모든 kind를 수용하고, int8 행렬 곱이 vwmacc.vx를 생성 (11-12)

날짜: 2026-11-12　출처: PR #1056, PR #1058

vir.reduce는 원래 부동소수점의 add와 maxnum만 인식했고, 정수 합계, min/max, 곱, all/any는 모두 루프에 남아 있었다. 이제 정수와 부동소수점 및 vector.reduction의 모든 종류를 받아들이며, verifier는 kind와 요소 타입이 일치하는지 검증하고, 스칼라 꼬리는 병합기로 요소별 마무리한다. 정수와 min/max 리덕션은 정확하며, 부동소수점 합계와 곱은 reassoc 외에는 여전히 순서를 유지한다.

정수 행렬 곱도 보완되었다: A, B가 동일한 정수 타입이고 C보다 넓지 않을 때 먼저 확장한 뒤 곱셈-덧셈을 수행하며, RVV에서 int8은 vsext.vf2와 vwmacc.vx를 얻는다(부호 없는 경우는 vzext.vf2와 vwmaccu.vx). 같은 작업에서 동적 형상 matmul의 단언 실패도 수정했다—M과 K가 vir.set_vl 영역 내에서 취해지고, 이후 pass가 사용 중에 제거되어 “expected that op has no uses”를 보고한다.

3.4 테스트 영역의 세 가지 숫자: 3980에서 4006으로, 393에서 0으로, 2에서 0으로 (11-12)

날짜: 2026-11-12　출처: PR #1053, PR #1057, PR #1058

세 건의 변경이 각각 검증 가능한 정량적 결과를 제시했으며, 기준은 모두 Triton-RISCV의 FlagGems 스위트다: 수학 함수 건은 SG2044(VLEN 128)에서 4045개 테스트의 통과 수를 3980에서 4006으로 끌어올렸고, 수정된 26건은 test_erf와 test_gelu다; rank-0 채우기 건은 1811개 kernel에 남아 있던 linalg.fill을 393에서 0으로 줄였다; 정수 행렬 곱 건은 잔여 linalg.matmul을 2에서 0으로 줄였다.

세 숫자를 함께 놓으면 한 가지를 설명한다: VIR이 유일한 파이프라인으로서 이미 “돌아가는가”의 단계가 아니라 “어떤 연산자가 여전히 linalg나 스칼라 형태로 남아 있는가”를 수렴시키는 단계라는 것이다.

날짜: 2026-11-12　출처: triton-riscv PR #115, PR #117

triton-riscv의 #115는 buddy-mlir 야간 버전 0.1.4.dev20261112를 의존성에 기록했고, #117은 +zvfbfmin을 기본 llc features에 추가했습니다. 두 건은 업스트림 #1054와 같은 사안의 양 끝입니다. 컴파일러가 하드웨어에 Zvfbfmin이 있다고 기본 가정하면 런타임의 llc 파라미터 문자열도 따라가야 하며, 그렇지 않으면 가변 길이 bf16이 커널 컴파일 단계에서 바로 중단됩니다. 이러한 “기본 가정—파라미터 동기화”의 결합은 포크형 다운스트림이 가장 놓치기 쉬운 지점입니다.

5. 커뮤니티와 활동 및 공식 홈페이지

5.1 포럼 11-12 정례 핫토픽 게시글 한 건, 격주 진행 상황은 여전히 080호에 정체 (11-12)

날짜: 2026-11-12　출처: RuyiSDK 커뮤니티 최신 토픽, 11-12 핫토픽 게시글

포럼 모니터링 기간 내 새 주제 하나가 추가되었습니다. 11-12의 “오픈소스 기술 핫뉴스 정보” 정례 집계 게시글입니다. 격주 진행 상황은 여전히 11-11의 080호이며 제081호는 나오지 않았습니다. Ruyi Imager의 내부 테스트 게시글은 11-11에 답글이 한 번 있었으며 지속적인 문답에 해당합니다. 커뮤니티 측에는 이번 기간 새 공지가 없습니다.

5.2 공식 홈페이지 세 페이지 변화 없음, 블로그 두 편, 문서 23장 (11-13 상태)

날짜: 2026-11-13(상태)　출처: RuyiAI 공식 홈페이지, 블로그 페이지

index, blog, docs 세 페이지의 해시는 지난 점검과 일치하며, 블로그는 여전히 두 편(Triton의 RISC-V 적응, PyTorch RISC-V CI 실천), 문서 인덱스는 23장입니다. 당일의 VIR 변경 사항에 대응하는 글은 사이트에 없습니다.

5.3 ruyiai-daily 결번 다섯째 날 (11-13 상태)

날짜: 2026-11-13(상태)　출처: ruyiai-daily 커밋 목록

데일리 정보 저장소의 마지막 커밋은 여전히 11-08 06:21(베이징 시간)이며, 11-09부터 11-13까지 다섯 기간이 생성되지 않았습니다. 해당 저장소는 이전까지 매일 한 기간씩 발행했으며, 결번이 이미 닷새째입니다.

5.4 외부 뉴스와 arXiv: 모니터링 기간 내 신규 없음 (11-13 상태)

날짜: 2026-11-13(상태)　출처: Google News, arXiv RISC-V 검색

RuyiSDK, RuyiAI, Ruyi RISC-V, openRuyi, buddy-mlir, triton riscv 여섯 그룹의 중영문 쿼리에서 모니터링 기간 내 적중이 전무했으며, 반환된 것은 모두 수개월 전의 오래된 기사였습니다. arXiv의 RISC-V 검색에서 최신 논문은 여전히 11-09의 MCU 위임 보호 논문이며, 모니터링 기간 내 새 논문은 없습니다. openRuyi 배포판 뉴스 페이지의 최신은 여전히 2026-10의 두 편이며, 2026.11 월간 버전은 아직 발표되지 않았습니다.

6. 트렌드 관찰

6.1 이날은 성능이 아니라 형상 커버리지를 보충한 것

7개 커밋 중 #1055(fast-math 플래그)만이 명령 선택을 직접 변경하며, 나머지 6개는 이전에 루프에 남아 있던 형태를 벡터 경로에 연결하는 작업이다: i1 마스크, libm-only 수학 함수, bf16, 리덕션 종류, rank-0 패딩, 정수 행렬 곱. 이런 변경을 평가하는 기준은 “아직 얼마나 많은 linalg 또는 스칼라 경로가 남아 있는가”여야 하며, 벤치마크 점수가 아니다—393이 0으로, 2가 0으로, 179개의 실패 파일이 0이 된 것이 바로 이 기준이다.

어제 #1050의 strip-mined 잔여분 폭 축소와 대조하면, 이틀의 분업이 보인다: 먼저 벡터 루프가 레인을 가득 채우게 하고(성능), 그다음 모든 연산자가 벡터 루프에 들어올 수 있게 한다(커버리지). 순서를 반대로 하면 헛수고가 된다.

6.2 수치 검증이 이미 입력 전수 열거 수준에 도달

#1054는 truncf에 대해 전체 2^32개의 f32를, 변환과 부호 연산에 대해 전체 2^16개의 bf16을 실행했다; #1055는 4M 레인에서 fmaf 전개를 비트 단위로 비교했다. 이러한 검증 비용은 bf16이 이미 출하 경로로 취급되고 있음을 보여주며, “시간 되면 하자”는 최적화 항목이 아니다.

이와 호응하는 것은 11-02에 LLVM이 RISC-V에서 bf16/fp16을 자동 벡터화할 때 조용히 성능을 저하시키는 문제를 다룬 논문이다—동일한 위험 지점: 결과가 틀렸지만 오류를 보고하지 않는다. 이번 PR들의 검증 방식은 바로 이런 조용한 오류에 대한 정면 대응이다.

6.3 릴리스 산출물 자체가 엔지니어링 지표가 되었다

같은 날 “내보내는 것”과 관련된 세 가지 변경: triton-riscv의 wheel이 약 970 MB에서 약 576 MB로 감소(triton-shared-opt 단일 항목 407 MB에서 118 MB로), buddy-mlir 야간 빌드의 배치별 패키징, pytorch의 CI 판정 기준이 제로 테스트 케이스 통과라는 가짜 성공을 차단. RISC-V 사용자가 wheel 하나를 다운로드하는 비용은 x86보다 훨씬 높기에, 릴리스 산출물의 크기와 신뢰성이 기능과 나란히 지표가 되고 있다.
