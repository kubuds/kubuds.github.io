날짜: 2026-10-29　출처: PR #58, PR #83, PR #82, 커밋 목록

15:38부터 16:58까지의 80분 동안 triton-riscv 메인 브랜치에 세 건의 커밋이 연속으로 병합되었으며, 작성자는 모두 maochuanjun이고 모두 동일한 계층, 즉 Triton에서 구조화/비구조화 IR로의 하향 경로를 수정한 것이다. 이는 시간적으로 결코 평범하지 않다. 해당 저장소의 이전 비의존성 업데이트 코드 커밋은 10-09의 #86이었고, 그 사이 20일 동안은 renovate의 야간 버전 앵커만 있었으며, 이 세 건 자체는 각각 82일, 43일, 44일이 지나서야 병합되었다.

세 건은 각각 하나의 구체적인 결함을 겨냥한다. #83(16:38, 4개 파일, +160/−16)은 비균일 텐서 패딩 값을 가진 마스크 로드를 수정한다. 즉 tl.load(ptr, mask=mask, other=cur) 같은 표기법이다. 원래 구현은 스칼라 또는 splat 패딩 값만 인식했고, 실제 텐서를 만나면 스칼라 추출 단계에서 막혀 하향된 IR에 지원되지 않는 포인터 연산이 남았다. 수정 방식은 구조화 로드와 비구조화 gather 두 경로 모두에서 텐서 패딩을 지원하고, arith.select(mask, loaded, other)로 미스 채널을 복원하며, 동시에 스칼라 추출 실패를 오류 없이 허용하여 처리 권한을 호출자에게 돌려주는 것이다. #58(16:58, 2개 파일, +125/−0)은 루프 캐리 gather 오프셋 손실을 수정한다. scf.for 안에서 캐리되는 텐서가 구조화 형태를 벗어나면 보조 상태에 중립적 플레이스홀더만 남아, 이를 사용해 루프 결과를 재구성하면 gather/scatter가 연속적인 tts.make_tptr로 붕괴되어 루프에서 누적된 오프셋이 모두 사라진다. 수정 방식은 분석된 피연산자가 실제로 scf.for의 결과인지 먼저 검증하고, 맞으면 원본 루프 결과를 오프셋으로 직접 유지하며, 새로운 loop_result_gather.mlir 회귀 테스트를 추가하는 것이다. #82(15:38, 1개 파일, +23/−3)은 scatter 테스트의 비결정성을 수정한다. 원래 테스트는 무작위 인덱스를 사용하고 대상 위치 중복을 허용했으며, 비축소 scatter에서는 어떤 소스 값이 승리하든 합법인데도 단일 PyTorch CPU 결과로 정확히 비교했다. 수정 방식은 1D, 2D 및 제자리 비교를 고유 대상 인덱스로 변경하고, 6개의 중복 인덱스 사례(512, 1023, 1024 세 가지 길이, 제자리와 비제자리 각 한 그룹)를 추가하며, 승리한 값이 올바른 대상의 소스 집합에서 나왔는지, 미스 대상이 원래 값을 유지하는지만 검증하는 것이다.

세 건의 동기는 모두 PR 설명에 적혀 있으며, 모두 동일한 지점을 가리킨다. FlagGems 연산자 이전이다. #83은 unique_dim 구현을 지원하고, #58은 broadcast_to를 지원하며(해당 커널은 이전에 이 오컴파일을 우회하기 위해 range(MAX_DIMS)를 tl.static_range로 바꿨다), #82는 이전 과정에서 scatter 연산자 비교 실패로 인해 역으로 이끌어낸 테스트 수정이다. 즉, 이 세 건은 회귀 테스트가 발견한 결함이 아니라, “한 배치의 PyTorch 연산자를 triton-riscv 위에서 실행”하려는 작업이 강제로 드러낸 결함이다.

검증 강도는 기록할 만하다. #83은 RuyiAI 관련 riscv64 머신에서 검증했다고 명시되어 있다. 새 회귀 테스트의 세 가지 RUN/FileCheck가 모두 통과했고, 전체 lit 291개 통과, 9개 예상 실패, 0개 예상치 못한 실패, 텐서 패딩 런타임 검사 18개 통과(구조화 및 gather 두 경로, float32/float64/int64, 빈 마스크/부분 마스크/전체 마스크, 음의 영, NaN 및 불법 미스 gather 오프셋 포함), 업데이트된 unique_dim과의 통합 23개 통과. #58은 특정 TritonToStructured 회귀 테스트만 실행했고, #82는 해당 테스트 파일만 실행했다(21개 통과). 세 건의 검증 깊이는 고르지 않으며, 앞의 두 건은 국부적이고 세 번째는 단일 파일에 치우쳐 있다.

인과 순서에 대해서는 자제가 필요하다. 수정이 먼저 반영되었지만, 이 수정이 필요한 이전 PR #56은 여전히 09-16에 멈춰 있으며, 열려 있고 병합되지 않았다. 이는 세 건이 병합된 후 broadcast_to의 tl.static_range 우회를 철회할 수 있고 unique_dim을 원래 작성법대로 제출할 수 있지만, “전체 연산자 배치가 riscv64에서 실행 가능한가”라는 질문은 이번 호에서 답이 없다는 것을 의미한다. #56이 다시 진행되어야 검증할 수 있다.

1.2 llvm-project: riscv 브랜치 전체 재적용, 기여 가이드 추가 및 사전 실행 스위치 제거 (10-29)

날짜: 2026-10-29　출처: riscv 브랜치 커밋 목록, 커밋 faf4def312, RISCV_CONTRIBUTING.md, autorebase 워크플로

23:00 전후, riscv 브랜치는 전체 브랜치 재적용을 한 차례 수행했습니다. 확인 가능한 25건의 커밋은 committer 시간이 모두 23:00:40부터 23:00:44까지의 4초 안에 몰려 있습니다. 재적용 내용 중 한 건은 실제로 새로운 것입니다. [workflows] Push rebased PRs directly and document contribution options(author 시간 10-29 09:59)는 두 파일을 변경했습니다. autorebase.yml에서 8줄을 삭제하고(dry_run 입력과 해당 사전 실행 브랜치 제거), 82줄의 RISCV_CONTRIBUTING.md를 새로 추가했습니다.

이 가이드는 「riscv 브랜치에 어떻게 기여할 것인가」를 두 가지 경로로 정리합니다. 첫 번째 경로는 먼저 issue를 열고, 유지관리자가 현재 riscv에서 work/issue-NNN 작업 브랜치를 분기하며, 기여자가 작업 브랜치에 PR을 제출하고, 유지관리자가 통합한 뒤 riscv에 병합하는 방식입니다. 여러 사람이 협업하고 안정적인 이력이 필요한 작업 항목에 적합합니다. 두 번째 경로는 riscv에 직접 PR을 제출하고, 베이스라인이 바뀔 때마다 수동으로 리베이스 워크플로를 트리거하는 방식입니다. 워크플로는 PR 소스 저장소에서 실행되고, 소스 저장소의 GITHUB_TOKEN을 사용하며, --force-with-lease와 명시적 기대 SHA로 소스 브랜치에 다시 푸시합니다. 충돌은 일률적으로 riscv 측을 취하고(수정-삭제 충돌에서는 riscv 측의 삭제를 유지), 동등한 패치는 자동으로 건너뛰며, riscv 자체를 절대 재작성하지 않고 자동 병합도 절대 하지 않습니다.

3. 벡터 확장, 아키텍처 테스트와 연산자 최적화

3.1 벡터 네 저장소 계속 조용, 벤치마크 측 공백 여전 (10-29 상태)

날짜: 2026-10-29 (상태)　출처: VecIntrinBench, IntrinTrans, FBGEMM, cpuinfo

네 개의 벡터 관련 저장소는 모니터링 기간 내 커밋이 전부 0건이었고, 정지 기간도 변동이 없었다. VecIntrinBench는 02-13에, cpuinfo는 05-20에, IntrinTrans는 06-25에, FBGEMM은 07-13에 멈춰 있다. torq-tile은 04-09에, dsh-osc는 09-15에 멈춰 있고, pytorch-ci는 커밋 기록이 없으며, harness는 10-27에 멈춰 있다.

이번 기간에 바로 이 벤치마크가 가장 필요했던 지점이 나타났다. 세 건의 triton-riscv 수정은 모두 ‘lit 통과 수 + 런타임 케이스 통과 수’로 검증되었고, 벡터화 품질을 비교 가능한 수치(명령어 개수, 점유한 LMUL, 레지스터 스필 횟수)로 제시한 곳은 한 군데도 없었다. 지난 기간 #1014에서 이미 ‘동일한 코드를 두 번 빌드했을 때 2% 차이’라는 노이즈가 나타났으며, 보드 실측 처리량으로 결론을 내리는 것 자체가 빠듯한 상황이다. VecIntrinBench 측이 계속 움직이지 않는다면, 이후 ‘최적화가 정말로 개선이 되었는가’는 장기적으로 수작업 대조에만 의존할 수밖에 없을 것이다. 이는 이번 기간에 새로 생긴 문제는 아니지만, 세 건의 병합이 이를 더 선명하게 비춰 주었다.

3.2 FlagGems 마이그레이션이 triton-riscv의 결함 발견 메커니즘이 되다 (10-29)

날짜: 2026-10-29　출처: PR #83, PR #58, PR #82, PR #56 FlagGems 마이그레이션

세 건의 수정 동기를 펼쳐 보면, 이들의 공통 출처가 테스트 스위트가 아니라 ‘PyTorch 연산자를 한 무더기씩 triton-riscv에 이식하는’ 작업 그 자체였음을 알 수 있다. unique_dim에서 실제 텐서 채움값을 동반한 tl.load, broadcast_to의 루프 전달 오프셋, 산입 연산자의 중복 인덱스 비교——이 세 가지는 모두 RISC-V 명령어 계층이 아니라 하강(lowering) 계층과 검증 계층의 경계에 위치한다. 이런 부류의 결함은 단위 테스트에서 자연스럽게 드러나기 어렵다. 실제 연산자 라이브러리를 갖추고 배치 방식으로 밀어붙여야만 노출된다.

이 일의 방법론적 가치는 세 건의 수정 자체보다 크다. Triton을 진입점으로 하는 RISC-V AI 스택에서 FlagGems 마이그레이션은 사실상 ‘엔드투엔드 검증 집합’ 역할을 하며, 컴파일러의 lit 스위트보다 실제 부하에 더 가깝다. 반대로 이번 기간에는 이 메커니즘의 단일 의존성도 드러났다. 마이그레이션 PR #56이 09-16 이후 갱신되지 않았고, 세 건의 수정이 병합된 뒤 오히려 검증 절차가 멈춰 버렸다. #56이 장기간 진전되지 않는다면 이 ‘결함 발견 메커니즘’도 함께 무력화되어, 다음 배치의 결함은 다른 사용자가 부딪힐 때까지 발견되지 않을 것이다.

3.3 arXiv 모니터링 기간 내 신규 없음, 10-27 두 편이 최신 (10-29 상태)

날짜: 2026-10-29 (상태)　출처: arXiv 검색

RISC-V에 컴파일러, 벡터, MLIR을 조건으로 한 검색에서 모니터링 기간 내 신규 논문은 없었다. 검색된 최신 두 편은 모두 10-27이다. SecDMP: Provably Secure Data Memory-Dependent Prefetching(데이터 메모리 접근 의존 프리페칭의 증명 가능한 보안 기법)과 A lightweight C Code Generator for Heterogeneous TinyML Systems(이기종 TinyML을 위한 경량 C 코드 생성기)이다. 전자는 마이크로아키텍처 측의 보안 프리페칭과 관련되고, 후자는 엣지 측 코드 생성에 속하며, 둘 다 AI 스택의 컴파일 경로에 직접 닿지는 않는다.

이번 기간의 주제와 가장 맞닿아 있는 것은 여전히 10-21의 Reorienting the Vector Axis: Restructuring FlashAttention for Long-Vector Processors——긴 벡터 프로세서상의 FlashAttention 재구성으로, 10-28에 디코딩 어텐션을 64 lanes로 분할하고 단일 헤드당 하나의 LMUL 4 그룹으로 처리한 방식과 같은 부류의 문제에 속한다. 모니터링 기간 내 후속은 없었다.

4. Buddy Compiler 동향

4.1 buddy-server 신규 ABI 병합: 56개 파일, 모델 플러그인 체계를 통합 인터페이스로 변경 (10-29)

날짜: 2026-10-29　출처: PR #1015, 커밋 7d2ce844, RAX 패키징 및 로딩 분석 문서

15:08, #1015 “Buddy-server new ABI”가 머지되었으며, 56개 파일, +3934/−1661로 이번 기간 전체 스택에서 변경 규모가 가장 큰 건이다. PR 설명에는 buddy-server가 RAX 파일을 파싱할 때 사용하는 ABI 인터페이스를 업데이트하며, 새 인터페이스가 향후 더 많은 모델 지원에 편의를 제공한다는 의도 한 줄만 적혀 있지만, 실제 변경은 이보다 훨씬 크다.

구조적으로는 “모달리티별로 플러그인 핸들을 각각 작성”하던 방식을 “하나의 통합 인터페이스”로 교체한 것이다. 새로운 런타임 헤더 파일 네 개를 추가했다: ServerModelABI.h(392줄), ServerModelABIConversion.h(179줄), ServerModelPluginAdapters.h(742줄), ModelError.h(57줄). 동시에 기존에 모달리티별로 분리되어 있던 AudioTranscriptionModelPluginHandle, EmbeddingModelPluginHandle, MaskedLMModelPluginHandle, ResidentModelPluginHandle 네 그룹의 구현과 ModelPluginDiscovery를 삭제하고, 350줄의 ServerModelPluginHandle과 102줄의 헤더 파일로 교체했으며, 어댑터 계층이 각 모달리티의 기존 진입점을 새 ABI로 다시 연결한다. BuddyServerApp.cpp 단일 파일만 +446/−225 변경되었고, SimpleHttpServer에는 25줄이 보강되었다(요청 파싱, 오류 반환 관련).

모델 측면에서는 일곱 개 디렉터리를 동시에 재작성했다: bge_m3(임베딩), deepseek_r1, llama31_tt, proteinglm(마스킹 언어 모델), qwen3_vl(비전 언어), whisper(오디오 전사)의 Model과 Plugin을 쌍으로 조정했으며, 각 쌍은 모두 “C++ 측은 적게 작성, 공용 측은 많이 작성”하는 형태다. 이는 지난 기간 #1010의 소스 재구성과 같은 맥락이다: 먼저 디렉터리를 책임별로 분리하고, 그다음 인터페이스를 한 계층으로 수렴시키는 것이다.

테스트 측면이 이번 건에서 가장 주목할 부분이다: ServerModelPluginHandleTest.cpp(325줄), BuddyServerAbiErrorIntegrationTest.py(184줄), BuddyServerCapabilityIntegrationTest.py(135줄), ServerModelConcurrencyFakePlugin.cpp(162줄), ServerModelDependencyPlugin.cpp(38줄), ServerModelErrorFakePlugin.cpp(149줄)를 새로 추가했고, 모달리티별로 작성했던 네 그룹의 단위 테스트(총 약 226줄)를 삭제했다. 즉, 테스트의 중심이 “각 모달리티를 하나씩 테스트”에서 “통합 ABI의 오류, 기능, 동시성, 의존성 네 가지 행위”로 이동했으며, 오히려 커버리지는 더 넓어졌다. 문서 측면에서는 RAXPackagingAndLoadingAnalysis.md와 Runtime.md가 함께 업데이트되었다.

한 가지 유의할 점: 이는 인터페이스 리팩터링이며, PR에는 성능 데이터도, 새 모델 지원 증명도 없다. “더 많은 모델 지원에 편의를 제공”한다는 것은 다음에 새 ABI로 통합되는 모델이 나와야 실현되는 것이다.

6. 트렌드 관찰

6.1 수정이 검증보다 먼저: 세 건의 수정은 회귀 테스트가 아닌 마이그레이션 과정에서 쌓인 이슈 목록에 의존

이번 회차 세 건의 병합은 한 가지 순서 문제를 드러냈다: 수정이 먼저, 검증이 나중. unique_dim의 텐서 패딩, broadcast_to의 루프 오프셋, 해시 연산자의 중복 인덱스—세 결함 모두 컴파일러 자체 테스트가 발견한 것이 아니라 FlagGems 연산자를 위로 옮기다가 부딪힌 것이며, 수정은 병합되었지만 이를 필요로 하는 마이그레이션 PR #56은 09-16에 멈춰 움직이지 않았다. 결과적으로 “특정 용도를 위해 준비된 수정” 묶음에 당장 대응하는 용도가 실행되지 않는 상태다.

이 상태의 위험은 현재가 아니라 다음 달에 있다: #56이 재개될 때 Triton 업스트림이 또 여러 차례 바뀌었다면 세 건의 수정이 새 베이스라인과 여전히 호환되는지 다시 검증해야 하며, #56이 계속 재개되지 않으면 이 “엔드투엔드 검증 집합”은 사실상 정지 상태가 되어 다음 결함 묶음은 외부 사용자가 부딪힐 때까지 기다려야 한다. “실제 모델을 돌릴 수 있다”를 목표로 하는 스택에게는 마이그레이션을 상시 회귀(비록 수십 개 연산자라도, 매일 밤 한 번 실행)로 만드는 것이 수정을 몇 건 더 병합하는 것보다 가치 있다.

6.2 브랜치 거버넌스의 두 가지 방식: llvm은 규칙을 쓰고 프리뷰를 없애며, pytorch는 전체 브랜치 재생에 의존

같은 날, 두 브랜치는 두 가지 거버넌스 답을 내놓았다. llvm의 riscv 브랜치는 전체 브랜치를 한 번 재생했고, 실제로 새로 추가된 것은 기여 가이드 한 부였다: “riscv에 코드를 보내는” 일을 “메인테이너 작업 브랜치에 PR 제출”과 “riscv에 직접 PR 제출 후 수동으로 리베이스 트리거”의 두 경로로 나누고, 동시에 워크플로의 프리뷰 스위치를 삭제했다—성공하면 즉시 푸시, 프리뷰 없음. pytorch의 riscv 브랜치는 업스트림 3afdbd3으로 재생하고 동기화 봇이 의존성 캐시 수정을 한 건 보충했을 뿐, 어떤 프로세스 문서도 없다.

양자의 비용 구조는 다르다. llvm 브랜치는 패치 집합이 크고 외부 기여가 많아 충돌과 히스토리 드리프트가 주요 비용이므로 규칙화하여 문서를 쓰고 워크플로를 구성할 가치가 있다. pytorch 브랜치는 패치 집합이 작아(11건) 메인테이너가 직접 한 번 재생하는 비용이 프로세스 유지 비용보다 낮다. 프리뷰를 없앤 점은 관찰이 필요하다: 마찰을 낮추는 동시에 “잘못된 히스토리 푸시” 위험을 기여자에게 앞당겨 전가하고 --force-with-lease와 상태 재확인으로 안전망을 치는 방식의 실제 효과는 다음 한두 건의 외부 PR을 봐야 한다.

6.3 배포판은 월 단위로 물량을 깔고, 스택급 3종 세트는 월 단위로 심사를 지연

openRuyi 이번 회차 76건의 커밋, 10건 머지, 그중 64건은 KDE 프레임워크 업그레이드 묶음이다. ruyi-imager는 1.0.0에서 1.1.0-rc.1까지 7주가 걸렸으니 정상적인 리듬이다. 반면 같은 ‘배포’의 다른 축인 RuyiAI 삼종 세트의 패키징 PR #1350은 09-21에 열린 이후 지금까지도 여전히 spec 규범 차원에서 재작업 중이다. 두 파이프라인의 차이는 인력이 아니라 성숙도에 있다. KDE 패키지는 참조할 업스트림 spec이 있고 정해진 버전 리듬이 있어 재패키징은 기계적인 작업이다. 삼종 세트는 처음부터 작성한 spec이라 ‘왜 LLVM을 패키지 안에 남기는가’를 설명해야 하고, ‘왜 %check가 비어 있는가’도 설명해야 한다.

이것이 RuyiAI에 주는 시사점은 배포판이 삼킬 수 있으려면 패키지 자체가 충분히 ‘관례적’이어야 한다는 전제다. buddy-mlir는 LLVM을 자체 포함하고, triton은 git 실행 파일에 의존하며, tilelang은 buddy-mlir 툴체인을 발견해야 한다. 이 세 가지 비관례적 지점은 각각 패치와 설명이 필요하고, 모든 설명마다 메인테이너가 시간을 들여 판단해야 한다. 삼종 세트가 월간 릴리스 리듬에 진입하기를 원한다면 이 세 가지 비관례적 지점을 한두 개의 명확한 패키징 규약으로 수렴시키는 것이(예를 들어 툴체인은 통일적으로 buddy-mlir가 제공하고, 패치는 통일적으로 git format-patch의 패치 스태킹을 사용) 검토 의견에 건별로 대응하는 것보다 수월하다.
