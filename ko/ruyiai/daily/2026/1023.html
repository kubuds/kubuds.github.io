어제 리포트에 기록된 079호 초안에는 OpenJDK, 기본 C 라이브러리, 개발 보드의 세 섹션만 작성되었으나, 이번 모니터링 기간에 나머지 여섯 섹션이 모두 보완되었다: GCC, LLVM, V8, OpenJDK, Go, QEMU 및 패키지 관리자와 IDE 섹션으로, 열 개의 패치 커밋이 10-22 09:26 ~ 14:20 사이에 순차적으로 저장소에 반영되었다(#383 ~ #391).

가장 정보량이 많은 것은 QEMU 섹션이다. RuyiSDK의 QEMU 저장소는 P 확장 v0.6 구현을 릴리스하며, 현재 P 확장의 모든 명령어에 대한 시뮬레이션 지원을 완료했다고 밝혔으며, 브랜치 p-dev는 업스트림 v11.1.0을 기반으로 한다. 브랜치의 마지막 커밋 배치는 10-21 16:35에 있었으며, 내용은 SIMD 계열( Q 포맷 곱셈-덧셈, 순수 곱셈과 곱셈-누산, 2-way 및 4-way 곱셈-덧셈/뺄셈, 로드 복제, RV32 전용 명령어) 패키징과, 명세 정렬을 위한 P의 Zbkb 의존성 제거 및 TCG 테스트 추가이다.

같은 호에는 다모아카데미(DAMO Academy)의 AME 확장 v0.6이 ame-0.6 브랜치에 병합된 것도 기록되어 있다: 주요 기능 개발과 아키텍처 리팩터링을 완료하고, 32/64비트 사용자 모드와 시스템 모드를 지원하며, 행렬 연산, 정수와 부동소수점 혼합 연산, 데이터 이동 및 타입 변환을 포괄하고, 멀티코어 공유 백엔드, 상태 마이그레이션 및 디버깅을 지원하며, 역시 업스트림 v11.1.0을 기반으로 한다. 해당 브랜치에서 확인 가능한 커밋은 10-16까지이며, 이번 모니터링 기간은 성과를 간행물에 편집한 것이지 새로운 커밋이 아니다.

이 두 항목은 RuyiAI 컴파일러 측과 대응 관계를 형성한다: LLVM 브랜치의 AME 패치 #29(명령어 업데이트), #30(IME 내장을 SpacemiT A100 dot으로 하강), #31/#32(A100 HP/SP 및 pack/unpack 스케줄링)는 행렬 확장을 명령어로 컴파일하는 역할을 하며, QEMU 측은 하드웨어가 없을 때 동일한 시맨틱을 시뮬레이션하는 역할을 한다. 세 곳의 동일 소스 확장 지원이 이번 주에 동시에 v0.6에 도달했다는 것은 해당 확장이 「컴파일러가 생성 가능하고, 시뮬레이터가 실행 가능한」 최소 폐쇄 루프를 갖추었음을 의미하며, 남은 격차는 하드웨어 실측 데이터이다.

날짜: 2026-10-21 (이번 모니터링 기간 시작점보다 약간 이르나, arXiv 인덱스가 이번 기간 내에 처음 가시화되어 수록)　출처: arXiv 2610.29489v1

《Reorienting the Vector Axis: Restructuring FlashAttention for Long-Vector Processors》(Emmanuel Irabor, Marc Casas)는 PyTorch의 CPU FlashAttention 커널을 2KB 벡터 레지스터를 갖춘 RISC-V CPU로 이식하면서, 먼저 냉정한 기준선을 제시한다: 피크 부동소수점 처리량의 16.2%에 불과하다.

원인 분석은 구체적이다. 원래 커널은 쿼리 행 단위로 진행한다: V와의 곱셈은 64원소 헤드 차원으로 벡터화되고, softmax의 행별 최댓값과 합계는 “전체 레지스터를 스칼라로 붕괴시키는” 리덕션이며, 소프트웨어 지수 함수의 다항식 계수는 tile 데이터와 벡터 레지스터를 두고 경쟁하여 스택으로 오버플로된다. 세 가지가 겹쳐 벡터 레지스터 활용률이 올라가지 않는다.

두 가지 개선법 모두 알고리즘과 수치는 바꾸지 않는다. 첫째는 스코어 tile과 실행 출력을 함께 전치하여 쿼리가 선형 연속 축에 놓이게 하는 것 — 그러면 “한 tile에 쿼리를 몇 개 담을지”라는 파라미터 하나가 커널 각 구간의 벡터 길이를 통일적으로 결정하며, 머신 구성에 따라 조정 가능하고, 두 리덕션은 자연히 사라진다. 둘째는 다항식 계수를 스칼라 레지스터로 옮겨 오버플로를 제거하여, softmax의 벡터 메모리 접근 명령이 78.7% 감소한다.

실측: 헤드 차원 64에서 두 항목을 합쳐 전체 커널 사이클을 1.84~2.08배 가속으로 낮추고, 부동소수점 활용률은 16.2%에서 29.7%로 상승; 동일 설계의 FPGA에서는 두 변경의 순위가 일치하며 이익이 더 커 2.71배에 달한다.

이 스택에 대한 의의는 숫자가 아니라 방법에 있다: 벡터 길이 적응과 레지스터 압박이야말로 triton-riscv와 tilelang-riscv가 RVV 하향에서 겪는 구조적 문제이지, “intrinsics가 있느냐”의 문제가 아니다; 논문의 “머신에 맞춰 tile 내 쿼리 수를 매칭”은 IREE가 Tile N을 vlen/8로 취하는 것과 같은 부류의 결정이며, 동일 기준으로 직접 비교할 수 있다.

비용은 변하지 않았다: 커미터 시간이 통일적으로 재작성되고 SHA가 매일 무효화되며, SHA로 참조하는 모든 다운스트림은 당일 만료되므로 이 두 브랜치를 읽을 때는 SHA가 아니라 패치 제목 집합을 봐야 한다. 이익도 변하지 않았다: 패치 자체는 새로 추가되지 않았고, pytorch 일곱 건, llvm 두 건의 오픈 PR 모두 타임스탬프만 갱신했으며, 실제 진행은 여전히 리뷰 큐가 결정한다.

6.2 openRuyi 규범 보완기에 진입: 정리 54건이 업그레이드 22건을 압도

이번 모니터링 기간 81건의 커밋 중 54건은 동일한 규범화 변경(소스 체크섬 보충, %autochangelog로 전환)으로 m에서 x까지의 패키지명 구간을 커버한다. 실제 버전 업그레이드는 22건으로 비율은 2.5대 1이다.

이는 이전 단계의 「의존성 클로저 보충」과 다르다: 그때는 Go의 vendor 제거, Rust의 crate 보충으로 패키지가 빌드되게 하는 것이 목표였다. 지금 정리하는 것은 감사 가능성과 자동 기록—소스 체크섬은 빌드 입력의 검증 가능성을 결정하고, %autochangelog는 변경 기록이 수기 작성이 아니라 커밋 이력에서 생성되도록 결정한다. 사용자가 체감하는 이익은 보안 업데이트 경로에 있다: 통일된 경로가 열려야 CVE 수정이 한 경로를 따라 전파된다. ISAC 소스 동기화 문제(2.6 참조)는 다른 면을 상기시킨다—규범이 아무리 좋아도 배포 채널이 막히면 사용자는 여전히 업데이트를 볼 수 없다.

6.3 배포판이 데스크톱과 가상화 검증 스택을 깔기 시작

오픈 PR 큐에 같은 방향의 제안 그룹이 나타났다: qemu의 GUI 테스트 기능 활성화(#1421), virglrenderer 신규 추가(#1415), ovmf의 fwupd 지원(#1436), ydotool 신규 추가(#1457), xorriso의 man 페이지 충돌 수정(#1489).

다섯 항목은 각각 가상화, 그래픽 가상화, 펌웨어 업데이트, 입력 자동화, 광학 디스크 이미지 툴체인에 속하며, 합치면 동일한 목표를 가리킨다. RISC-V에서 완전한 데스크톱을 구동하고 이를 자동화 검증하는 것이다. 이는 서밋에서 선보인 「AI 기반 IDE 그래픽 테스트」와 동일한 요구의 양 끝단이다. 테스트 프레임워크가 실제 인터페이스를 구동하려면 먼저 스크립트 가능한 입력과 가상화 가능한 그래픽 스택이 있어야 한다. 데스크톱 지원은 그동안 RISC-V 배포판의 약점이었는데, 이번 제안들은 이를 항목별로 병합 가능한 작업으로 분해했다.

6.4 확장 적용 경로 구체화: 컴파일, 시뮬레이션, 연산자 3계층 순차 완성

AME를 예로 들면, 이번 주에는 확장이 제안에서 사용 가능한 상태에 이르는 완전한 경로가 보인다. 먼저 백엔드 설계와 명령어 집합 정의(LLVM #16, #24, #27, #29)가 있고, 이어서 lowering과 스케줄링 구현(#30, #31, #32)이 있으며, 동시에 시뮬레이터가 실행 가능한 시맨틱(QEMU ame-0.6)을 제공하고, 마지막으로 연산자 라이브러리가 테스트 가능한 kernel과 검증 스위트(AME-operator)를 제공한다.

P 확장은 같은 경로를 가지만 이미 후반부에 도달했다. QEMU는 모든 명령어를 커버하고, GCC 지원은 0.6으로 업데이트되었으며, LLVM 측에서는 mulq, 상위 비트 곱 누산, sati/usati, Packed Pair 등의 intrinsics가 배치로 업스트림에 병합되었다. 대조적으로 P 확장은 애플리케이션 측 benchmark가 부족하고, AME는 실기가 부족하다.

이 순서 자체는 방법론으로 기록할 가치가 있다. 시뮬레이터가 없으면 컴파일러를 검증할 수 없고, 연산자 라이브러리가 없으면 시뮬레이터를 검증할 수 없다. 세 가지가 모두 갖춰지기 전에 성능을 논하는 것은 의미가 없으며, 모두 갖춰진 후에야 병목이 하드웨어와 실측으로 전환된다. 이번 주의 진전은 「완비」이지 「더 빠름」이 아니다.
