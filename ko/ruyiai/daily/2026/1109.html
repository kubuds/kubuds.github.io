오늘의 주요 사항: Ruyi Firmware 이틀 연속 릴리스, HiFive Unmatched 지원 목록에 포함(11-07, 11-08)

날짜: 2026-11-07, 2026-11-08　출처: Ruyi Firmware 20261107, Ruyi Firmware 20261108, 펌웨어 저장소 커밋 목록

openRuyi의 UEFI 펌웨어 프로젝트가 이틀 밤 사이에 두 개 버전을 연달아 내놓았다. 11-07 22:21(베이징 시간)에 20261107을 릴리스했고, 11-08 22:47에 20261108을 릴리스하며 프리릴리스로 표시했다. 두 버전 모두 각각 네 개의 빌드 산출물을 포함한다.

20261107은 이번 모니터링 기간의 기능 버전으로, 가장 큰 변화는 지원 범위를 SpacemiT K3에서 SiFive HiFive Unmatched로 확장한 것이다. 해당 보드의 SPI 부팅, JTAG 복구, NVMe 및 USB 부팅, 그리고 영구 UEFI 변수를 새로 추가했다. 이 확장과 함께 릴리스 노트에는 네 가지 부수 조정이 포함됐다. 보드마다 DEBUG와 RELEASE 두 세트의 패키지를 각각 제공하고, Platform Settings에 PXE 및 HTTP ISO 부팅 제어를 추가하며(기본값 꺼짐), UEFI 드라이버 에뮬레이션을 기본 활성화로 변경하고(Setup에서 변경 가능하며 구성 스크립트로 이미지 기본값 설정 가능), 두 보드가 Ruyi 로고와 부팅 카운트다운 바를 통일해 사용하도록 했으며 Firmware Update 화면에 파일 선택기를 추가했다. K3 쪽에는 두 가지 사용성 수정도 있다. 그래픽 콘솔의 응답 속도를 개선하고, UEFI 부팅 단계에서 P1의 RTC를 읽도록 했다.

20261108은 K3 한 라인만 변경했다. USB Fastboot를 EDK2의 공유 구현으로 전환하여 펌웨어 업데이트, 다시 읽기, 그리고 메모리에서 EFI 애플리케이션 부팅에 사용할 수 있게 했다. 동시에 fastboot getvar version-bootloader를 통해 EDK2 펌웨어 버전을 보고한다. 이 변경은 제조사 전용 플래싱 채널을 EDK2 표준 경로로 편입시킨 것으로, 생산 라인과 사후 서비스에는 바로 사용할 수 있는 인터페이스가 되고, 개발자에게는 펌웨어 버전 확인을 위한 전용 도구가 더 이상 필요 없음을 의미한다.

두 버전 모두 동일한 호환성 선언을 유지한다. Linux 메인라인 지원은 최선 노력 방식으로 제공되며, 알려진 framebuffer 문제에 대해서는 릴리스 노트에 우회 방법을 제시한다. 10월의 20261013부터 20261015까지의 세 번 연속 릴리스(CPU 모드 선택, System Information 페이지)를 보면, 이 펌웨어 라인은 이미 일 단위 반복 리듬에 들어섰으며, Unmatched의 추가는 단일 칩 제조사를 벗어난 첫 사례다.

오늘의 핵심: 정확한 VLEN으로 컴파일된 모델은 다른 VLEN에서 조용히 잘못 계산된다, buddy-mlir는 로딩 시점 검증으로 전환(11-08)

날짜: 2026-11-08　출처: PR #1032, 커밋 4063c48

PR #1032가 해결한 문제는 한 부류의 잘못된 실패 방식이다. 오류를 보고하지 않고 그저 잘못 계산할 뿐이다. 정확한 VLEN으로 빌드된 RISC-V 모델은 벡터 코드가 그 하나의 VLEN에서만 성립한다. llc에 VLEN을 명시적으로 알려주고(+zvlNb 및 -riscv-v-vector-bits-max), decode attention의 가변 길이 벡터도 그에 맞춰 크기를 정한다(#1028, #1030). 다른 VLEN으로 옮기면 모델은 크래시하지 않고 곧바로 잘못된 결과를 낸다. 커밋 설명이 제시한 사례는 매우 구체적이다. K3에서 prefill_ime로 빌드한 DeepSeek-R1 rax(BUDDY_RISCV_VLEN=1024)는 /proc/set_ai_thread를 실행하지 않으면 X100 코어(VLEN 256)에서 실행되어, 아무런 경고 없이 잘못된 결과를 낸다.

수정 방식은 검증을 로딩 시점으로 앞당기는 것이다. runtime/rvv/BuddyRvvVlen.c가 생성자로 모델 라이브러리에 링크되어, 라이브러리가 로드되자마자 vlenb를 읽고 빌드 시의 정확한 VLEN과 일치하지 않으면 정보를 출력하고 _exit(1)로 프로세스를 종료한다. exit가 아닌 _exit를 쓰는 것은 의도적이다. 로더가 락을 보유한 동안 소멸자를 실행하면 교착 상태에 빠지기 때문이다. 생성자 형태는 명령줄 도구, 서버, 테스트를 포함한 모든 로딩 주체를 포괄한다. 일반 RVV 빌드(정확한 VLEN 미지정)와 기타 타깃은 영향을 받지 않는다.

리뷰 후 두 번째 커밋을 추가로 넣어, 검증을 “빌드 변수 기준 판단”에서 “최종 llc 옵션 기준 판단”으로 바꿨다. 기존 문제는 두 가지였다. 첫째, 네이티브 빌드가 모델 자체의 LLC_ATTRS로 VLEN을 지정할 수 있는데, BUDDY_RISCV_VLEN이 그것과 일치하지 않으면 검증 값이 실제 코드와 어긋난다. 둘째, 3단계에만 링크되어 Qwen3-VL의 비전과 디코딩 두 shim, 그리고 계층적 링크 경로가 모두 빠져 있었다. 이제 빌드 스크립트가 최종 llc 옵션에서 정확한 VLEN을 추출하며(이는 VIR lowering이 읽는 것과 같은 지점이다), 3단계와 두 shim, 계층적 링크가 모두 포함되고, 구성 단계에서 옵션이 서로 모순되면 즉시 실패한다.

테스트는 이 변경의 나머지 절반이다. test_buddy_rvv_vlen.py는 VLEN 128부터 65536까지 각각 모델 라이브러리를 빌드하며, 호스트에 해당하는 하나만 로드되고 나머지는 모두 종료 코드 1로 끝난다. test_buddy_rvv_vlen_cmake.py는 구성 스크립트로 BUDDY_RISCV_VLEN, LLC_ATTRS, prefill_ime와 zvl 파라미터의 다양한 조합을 커버한다. 실기 검증은 K3의 X100과 A100 두 코어에서 완료했고, 저장소 자체 점검 239개와 409개 항목이 통과했다.

1. RuyiAI 스택 진행 상황(PyTorch / Triton / TileLang RISC-V 적응)

1.1 triton-riscv: 배포 wheel에 백엔드 등록 보완, 릴리스 워크플로를 CI와 동일한 체크아웃 액션으로 변경 (11-06)

날짜: 2026-11-06　출처: PR #101, 커밋 d8c2b3e

PR #101은 #100 반영 후 드러난 두 가지 릴리스 체인 문제를 수정한 것으로, 총 두 파일에 열일곱 줄이 추가되었다. 릴리스 워크플로는 CI와 동일한 체크아웃 액션 버전을 사용하도록 바꿨고, scripts/release.sh에는 백엔드 등록 단계를 추가해 release가 산출하는 wheel이 CI가 빌드한 wheel과 동일한 플러그인 등록 정보를 갖도록 했다. 이전에는 release 경로가 패키징만 수행해 플러그인 디렉터리가 wheel에 등록되지 않았고, 설치 후 백엔드가 보이지 않았다. 이런 문제는 CI에서 드러나지 않는데, CI는 설치 경로를 타지 wheel 경로를 타지 않기 때문이다.

1.2 triton-riscv: AMD 백엔드에 riscv64에서 누락된 codegen 라이브러리 보완, 나이틀리 빌드에서 x86_64와 riscv64 두 wheel 산출 (11-07)

날짜: 2026-11-07　출처: PR #102, 나이틀리 빌드 aa51ac2, 나이틀리 빌드 6895885

PR #102의 제목은 “AMD 지원 추가”이지만, 실제 내용은 새로운 백엔드를 추가한 것이 아니라 누락된 라이브러리를 보완한 것이다. 업스트림 AMD 백엔드는 libtriton_amd_codegen.so를 필요로 하는데, 사전 빌드된 복사본을 내려받거나 별도로 고정된 버전의 LLVM에 맞춰 직접 빌드해야 하며, 두 경로 모두 riscv64 버전이 없다. 이 라이브러리 자체는 매우 작아서 저장소에 이미 있는 LLVM으로 몇 초 만에 빌드할 수 있다. 따라서 setup.sh는 라이브러리 누락을 감지하면 로컬에서 빌드해 약정된 경로에 두고, env.sh는 TRITON_AMD_CODEGEN_PATH가 그것을 가리키도록 한다. 기존의 GPU 의존성 stub은 모든 GPU 다운로드를 빈 디렉터리로 향하게 했고, 덩달아 업스트림의 해당 라이브러리 풀도 건너뛰었지만 플러그인 컴파일 시에는 여전히 이 경로를 읽어야 했다. 이것이 없으면 AMD 백엔드는 어떤 것도 컴파일하지 않는다.

이 변경은 플러그인화 개편 이후 이 저장소의 위치를 보여주기도 한다. 같은 트리에서 riscv64용 Triton을 산출하는 동시에 빌드 시점에 다른 백엔드에 필요한 컴포넌트를 수용하며, 다중 백엔드 공존이 더 이상 브랜치 전환에 의존하지 않는다. 모니터링 기간 내 두 나이틀리 빌드가 새로운 주기로 산출되었으며(11-06 12:08과 11-07 07:52), 각 버전은 두 산출물, 즉 cp312-abi3의 x86_64 wheel(약 320 MB)과 riscv64 wheel(약 337 MB)이다. 이전 나이틀리 빌드는 다섯에서 여섯 개 산출물이었는데, 산출물 수 감소는 stable ABI 단일 wheel과 백엔드의 Triton 패키지 병합이라는 흐름과 일치한다.

3.1 buddy-mlir: 정확한 VLEN으로 빌드된 모델 라이브러리에 로드 시점 검증 추가, K3에서 실수로 X100 코어에서 실행되면 즉시 차단됨 (11-08)

날짜: 2026-11-08　출처: PR #1032, 커밋 4063c48

변경 사항은 총 열두 개 파일, 547줄 추가, 86줄 삭제이며, 핵심은 십여 줄짜리 C 파일 하나인 runtime/rvv/BuddyRvvVlen.c이다. 이 파일은 생성자로 모델 라이브러리에 링크되어, 로드 시 vlenb를 읽고 빌드 시의 정확한 VLEN과 비교하며, 일치하지 않으면 정보를 출력한 뒤 종료한다. 함께 수정된 빌드 스크립트는 런타임 코드보다 더 복잡하다. buddy_rvv_vlen.cmake는 이제 최종 llc 옵션에서 VLEN을 추론하며(VIR 하향과 동일한 읽기 로직을 공유), buddy_model.cmake는 사양과 옵션이 확정된 후 해당 목적 파일을 컴파일하며, 세 번째 단계, Qwen3-VL의 두 shim, 계층적 링크 모두 이를 명시적으로 포함한다.

문서에는 A210과 K3 두 편의 DeepSeek-R1 배포 설명도 함께 업데이트되어, “어떤 빌드가 정확한 VLEN이고 어떤 것이 범용 RVV인지”의 경계를 명확히 했다. A210의 커널은 고정 길이 벡터이고 VIR이 없으며, llc는 128 이상의 모든 VLEN으로 하향할 수 있어 범용 빌드에 속한다. K3의 prefill_ime는 반드시 1024여야 하며 정확한 VLEN에 속한다. 이 경계는 과거에는 빌드 스크립트의 주석에만 존재했으나, 이제 런타임 강제가 생겼다.

3.2 buddy-mlir: VIR 하향 시 RISC-V 호스트의 VLEN 식별, #1030 이후 riscv64 CI의 비트 단위 실패 수정 (11-08)

날짜: 2026-11-08　출처: PR #1037, 커밋 79ffafd

같은 사람이 같은 날 제출한 두 번째 커밋으로, 다른 방향의 오류를 수정한다. -lower-vir-to-vector는 rvv-vlen을 주지 않고 확장 가능 벡터도 켜지 않을 때 호스트 레지스터 폭에 따라 고정 길이 벡터의 크기를 정하는데, 호스트 인식이 x86(AVX2, AVX-512)과 SVE만을 커버한다. V 확장이 있는 RISC-V 호스트는 실제 VLEN이 얼마이든 전부 범용 기본값(128비트, 레지스터 16개)으로 떨어진다.

그 결과는 테스트에서 드러났다. #1030 이후 kernels 파이프라인은 llc 옵션이 없을 때 호스트에 따라 VIR을 낮추는데, riscv64 CI 호스트는 VLEN 256임에도 128비트로 처리되었다. q, k 노름의 제곱이 vector<32xf32> 세그먼트 합산으로 잘려 벡터 커널과 비트 단위로 비교하는 순서가 달라졌고, vir decode qk_norm ... same bits가 거짓으로 판정되었다. 이 문제는 main의 모든 riscv64 실행에 존재했으며, x86(AVX-512)은 1024 폭을 받기 때문에 계속 통과하고 있었다. 작성자는 먼저 테스트에서만 rvv-vlen=1024 use-scalable=false를 고정하는 변경을 추가했다가 곧바로 스스로 되돌렸다. 그것은 llc 옵션 외에 VLEN 설정을 또 하나 만드는 것으로 #1032의 방향과 충돌하기 때문이다. 최종 수정 방식은 낮추기 단계에서 RISC-V 호스트를 인식하고(호스트 CPU 기능과 hwprobe를 읽음) 실제 VLEN에 따라 크기를 정하며, 테스트 파일은 호스트 형태의 새 케이스로 교체하는 것이다.

6. 트렌드 관찰

6.1 펌웨어 라인이 단일 보드에서 다중 보드로: Unmatched와 PXE 부팅이 가리키는 시나리오

날짜: 2026-11-07　출처: Ruyi Firmware 20261107

Ruyi Firmware는 이전까지 기본적으로 SpacemiT K3를 중심으로 반복되었다. 10월의 세 버전은 모두 K3의 CPU 모드 선택, 시스템 정보 페이지, 플래싱 경로를 보완했다. 20261107은 처음으로 SiFive의 HiFive Unmatched를 지원 대상에 포함했으며, 최소 동작 수준이 아니다. SPI 부팅, JTAG 복구, NVMe와 USB 부팅, 영구 UEFI 변수를 한 번에 갖추었으니, 개발 보드 하나를 “전원이 켜지는” 수준에서 “워크스테이션으로 쓸 수 있는” 수준으로 끌어올린 셈이다.

함께 제공되는 두 가지 설정은 목표 시나리오를 더 잘 보여준다. PXE와 HTTP ISO 부팅 제어(기본 비활성화), 보드마다 DEBUG와 RELEASE 두 가지 패키지. 전자는 데이터센터와 대량 배포의 진입점이고, 후자는 생산 라인과 개발의 분업이다. 오픈소스 RISC-V 플랫폼은 오랫동안 EDK2와 정렬되고 여러 벤더가 재사용할 수 있는 펌웨어 방안이 부족했다. Unmatched의 추가로 이 라인은 처음으로 두 번째 칩 벤더의 샘플을 갖게 되었다. 다음은 세 번째 보드가 누구에게서 나오는지 지켜볼 차례다.

6.2 정확한 VLEN 특화의 대가: 조용한 계산 오류는 크래시보다 발견하기 어렵다

날짜: 2026-11-08　출처: PR #1032, PR #1037

K3의 듀얼 클러스터 구조는 RISC-V의 VLEN 문제를 같은 머신 위에 펼쳐 놓는다. A100 코어의 VLEN은 1024, X100 코어의 VLEN은 256이며, 동일한 실행 파일이 잘못된 클러스터에서 실행되면 크래시하지 않고 잘못 계산할 뿐이다. 과거에는 이 문제를 배포 문서로 주의를 환기했지만(먼저 /proc/set_ai_thread 기록), 이제는 로드 시점 검증으로 막는다. 모델을 납품하는 툴체인 입장에서는 시작이 실패하는 편이 잘못된 결과를 내는 것보다 낫다. 이것이 #1032의 가치다.

같은 날 #1037은 다른 측면에서 같은 사실을 증명한다. 호스트가 정한 기본값(128비트, 레지스터 16개)은 x86에서는 큰 VLEN과 정확히 동등하지만, riscv64에서는 합산 순서를 바꾸어 비트 단위 비교가 즉시 실패한다. 두 패치는 하나는 빌드 시점을, 하나는 실행 시점을 관리하며, 공통점은 더 이상 “VLEN은 컴파일러가 마음대로 정한다”고 가정하지 않는다는 것이다. 확장 가능 벡터(scalable vector)는 원래 RVV의 표준 답이지만, 비트 수준 재현이 필요한 추론 커널에서는 정확한 VLEN이 여전히 더 유리하다. 대가는 이런 검증이 빌드 변수가 아니라 최종 llc 옵션을 따라가야 한다는 것이다.

6.3 주말 기간의 분업: AI 스택은 조용하고, 패키징과 펌웨어는 전진

날짜: 2026-11-09　출처: RuyiAI-Stack 조직, openRuyi 커밋 목록

3일 기간 동안 PyTorch의 RISC-V 브랜치, tilelang-riscv, llvm-project의 riscv 브랜치는 모두 커밋이 0건이었고, AI 스택의 실질적 변경은 triton-riscv의 빌드 스크립트 두 건과 buddy-mlir의 VLEN, SPM 관련 커밋 세 건뿐이었다. 같은 기간 openRuyi 패키징 저장소는 열 건, 펌웨어 저장소는 두 버전 릴리스로 리듬이 확실히 더 촘촘했다.

이 분업은 양측의 릴리스 주기와 관련이 있다. 패키징과 펌웨어는 일 단위 또는 야간 단위로 패키지를 내보내므로 어떤 업스트림 버전 변화든 따라가야 한다. AI 스택은 버전 기간 사이에 구조적 조정(플러그인화, VLEN 검증)을 하며 매일 산출을 추구하지 않는다. Ruyi 커뮤니티를 지켜보는 사람에게 월요일부터 금요일까지는 AI 스택을, 주말에는 배포판과 펌웨어를 보는 것이 현재로서는 비교적 수월한 읽기 방법이다.
