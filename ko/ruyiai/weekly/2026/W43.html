RuyiAI 위클리 리포트 (2026-10-19 ~ 2026-10-23)

2026-10-23 Kubuds

보고 주기: 2026년 10월 19일(월)부터 10월 23일(금)까지, 총 5영업일.

자료 출처: 본지의 데일리 RuyiAI 동향 리포트 5회분(2026-10-19~2026-10-23, 각 회차 모니터링 기간은 전일 04:30부터 당일 04:30까지이며, 월요일은 지난 3일분으로 주말을 포함)과 함께, RuyiAI-Stack, ruyisdk, buddy-compiler 세 조직의 168시간 저장소 점검, openRuyi-Project 주요 저장소 보충 점검, RuyiSDK 개발자 커뮤니티와 openRuyi 배포판 뉴스 페이지의 이중 출처 재검증, 그리고 RuyiAI 공식 홈페이지 3개 페이지 스냅샷(점검 범위는 10-24 오전까지)을 포함한다.

편성 설명: 이번 주에는 세 가지 주제가 병행되었다. 첫째, openRuyi 메인 저장소는 637건의 커밋으로 「의존성 기반 패키징」으로의 전면 전환을 완료했으며, Rust crate 클로저 보충, Python 클라우드 스토리지 백엔드 보충, Go vendor 제거에서 시작해 소스 체크섬 및 %autochangelog 규범 보완까지 추진했다. 둘째, PyTorch와 LLVM 두 riscv 브랜치의 전체 브랜치 재적용이 「시기 선택」에서 「매일」로 수렴되었으며, 패치 제목 집합은 변하지 않고 커밋 해시는 매일 무효화된다. 셋째, RISC-V 매트릭스 확장(AME와 Ztt)의 컴파일러, 시뮬레이터, 연산자 세 계층이 이번 주에 동시에 완성되어 「컴파일 가능, 실행 가능, 결과 정확」의 최소 폐쇄 루프를 형성했다. 위클리 리포트는 데일리 리포트 자료 외에 7건의 점검 신규 발견을 보충했으며, 모두 10-23 낮(데일리 리포트 모니터링 기간 이후) 또는 주기 경계에 해당하여 부록에 기재한다.

1. 이번 주 주요 뉴스

  • openRuyi, 단일 주 5일간 637건 커밋, 패키징 전략 전면 「의존성 기반 패키징」으로 전환: 자연일 기준으로 10-19부터 10-23까지 각각 221, 137, 51, 109, 119건이며, 작성자는 Leetfs(333건)와 Jingwiw(152건)가 주를 이룬다. 진화 순서는 명확히 추적 가능하다—10-19 하루에 Rust 관련 커밋 211건(신규 패키지 약 200개)과 네트워크 스토리지 스택 추진(dpdk 26.07, spdk 26.09, liburing 2.15, btrfs-progs 7.1, nvme-cli 3.1); 10-20에는 Rust/Go/Python 각 42건의 대칭 구조로 fsspec 클라우드 스토리지 백엔드 전체 패밀리를 보충; 10-21부터 10-22까지 minio(10-20 병합), sonobuoy와 umoci(10-21 병합)의 vendor 제거 개조를 메인 브랜치에 반영하고, 삭제된 vendor 이후 필수적인 임포트 경로를 보충했으며, picoclaw의 동일 제안은 여전히 대기 중; 10-22부터 규범 보완으로 전환하여 Jingwiw가 54개 패키지의 소스 체크섬을 일괄 정리하고 %autochangelog로 전환했다. 출처: openRuyi 커밋 목록, PR #1459 minio vendor 제거, PR #1466 umoci

  • 두 riscv 브랜치의 전체 브랜치 재적용이 매일 운영으로 수렴: PyTorch는 5일 연속 아침 재적용, LLVM은 8일 침묵 후 3회 연속 기반 교체: PyTorch의 riscv 브랜치는 10-18부터 10-22까지 5일 연속 재작성되었으며, 헤드는 순서대로 8b254cfd, 44826095, 7f49d33f, 3c1ea315, 29259d90이고, 매번 전체 브랜치의 커밋 작성자 시간이 통일되어 재작성되었다; LLVM의 riscv 브랜치는 10-13부터 8일간 침묵한 후 10-21, 10-22, 10-23에 연속 3회 기반을 교체했으며, 헤드는 순서대로 dd05e5b5, 58d62a47, 7c77126b이다. 두 라인의 공통 특징은 패치 제목 집합이 항목별로 변하지 않고 로컬 성과가 유실되지 않는다는 점이며, 대가는 커밋 해시로 참조하는 모든 다운스트림이 매일 무효화된다는 것이다. 같은 기간 PyTorch에서는 약 5주 만에 첫 PR 병합(#51 riscv64 로컬 이미지, 10-17 병합)이 발생했으며, 7건의 오픈 PR은 주 전체에 걸쳐 타임스탬프만 갱신되고 새로운 리뷰 의견은 없었다. 출처: PyTorch riscv 브랜치, LLVM riscv 브랜치, PR #51

  • Ztt 매트릭스 확장이 처음으로 ruyisdk/llvm-project의 AME 브랜치에 적용됨(10-23 17:15), AME 3종 세트와 함께 매트릭스 확장의 완전한 체인을 구성: 이번 주 마지막 근무일에 AME 브랜치에 「[RISCV] Add initial Ztt matrix extension support based on spec v0.6」 초기 지원이 적용되었으며, 이는 해당 브랜치가 10-19에 AME CI 워크플로를 병합한 이후 두 번째 커밋이다. 여기에 RuyiAI 측 LLVM 브랜치의 AME 패치 시리즈(확장 및 백엔드 경로 설계 #16, #24, #27, 명령어 업데이트 #29, IME 내장 하강 및 A100 HP/SP 스케줄링 #30, #31, #32), QEMU의 ame-0.6 브랜치와 AME-operator 연산자 라이브러리를 더하면, 매트릭스 확장은 컴파일, 시뮬레이션, 연산자 세 계층에서 이미 완비되었다. 세 계층의 공통된 공백은 실측이다. 컴파일 측 성능 모델은 A100 명령어 기준으로 교정되었고, QEMU는 의미론적 정확성만 보장하며, 연산자 라이브러리 검증은 시뮬레이션 또는 기존 하드웨어에서 실행되어, 어떤 계층도 실기기 처리량 데이터를 제공하지 않는다. 출처: Ztt v0.6 커밋 29fefa0f, AME CI PR #170, qemu ame-0.6, AME-operator

  • QEMU, P 확장 v0.6 전체 명령어 시뮬레이션 완비, GCC와 LLVM 측 동시 정렬: ruyisdk/qemu의 p-dev 브랜치(업스트림 v11.1.0 기반)는 10-21 16:35에 12건의 마무리 배치를 적용했으며, 모두 패킹 SIMD에 집중되었다. Q 포맷 곱셈과 곱셈-덧셈, 순수 곱셈, 곱셈-누산, 2-way 및 4-way 곱셈-덧셈/뺄셈, 수평 리덕션, 로드 복제, pack/merge/선행 카운트, RV32 전용 명령어, 그리고 새 규격에 맞추기 위해 P의 Zbkb 의존성을 제거하고 tests/tcg/riscv 테스트를 보충했다. 툴체인 측도 같은 시기에 정렬되었다. GCC는 P 확장 지원을 0.6 버전으로 업데이트했고, LLVM은 mulq, 곱셈 상위 비트 누산, sati/usati, Packed Pair 및 패킹 곱셈 등의 intrinsics를 분할 병합했다. P 확장은 이로써 「시뮬레이터 전면 커버리지, 양대 컴파일러 생성 가능」의 후반부에 진입했으며, 공백은 애플리케이션 측 벤치마크에 있다. 출처: qemu p-dev, 격주 리포트 079호

  • 격주 리포트 제079호 최종 확정, 6개 절 보충: 10-22 09:26부터 14:20 사이에 ruyisdk/wechat-articles에 연속 10건의 패치(#383부터 #391이 주)가 적용되어 GCC, LLVM, V8, OpenJDK, Go, QEMU 및 패키지 관리자와 IDE 절을 모두 작성했다. 기술 내용은 네 곳에 집중되었다. LLVM은 12건을 나열했고 9건이 병합되었으며, RVA23.1 및 RVB23.1 profile 정식 전환, GlobalISel의 Zfhmin을 사용한 f16 절단 처리, 비정렬 스칼라 메모리 접근의 LLT 재로드를 포함한다. V8은 4건을 병합했으며 riscv64 이진 검색 부호 확장과 Liftoff 상수 추적을 다룬다. Go는 6건의 메인라인 CL을 제안했고 riscv64의 sha256/sha512 하드웨어 가속(zvknha/zvknhb) 2건이 병합되었다. OpenJDK는 12건을 병합하고 JEP 544(AOT 정적 컴파일)의 RISC-V 이식 초기 구현을 완료했다. 해당 호에는 여전히 세 개 절이 비어 있다. 권두언, 버전 테스트 및 잔여 문제, 공식 웹사이트와 문서. 출처: 079호 파일

  • IREE, 이틀 만에 RVV 행렬 곱셈-누산의 1단계 정밀도 단계 완료: 10-19에 릴리스된 v3.13.0은 RISC-V V의 f32 vfmacc.vf inner_tiled MMA를 정식 버전에 포함시켰으며(PR #24933), 10-21에는 메인 브랜치에 f16 버전이 추가로 반영되었다(PR #25000, 946줄 변경, 테스트 800여 줄). 확장 기능 가용성에 따라 세 계층으로 인코딩을 선택한다——+zvfh가 있을 때는 vfmacc.vf를 사용하고, f16 곱하기 f16이 f32가 될 때는 확장된 vfwmacc.vf를 사용하며, +zvfhmin만 있을 때는 f32로 확장한 후 다시 절단하는 방식으로 퇴화한다. 성능 측면에서 제시된 방향은: X60(VLEN=256)에서 단일 스레드 inner_tiled가 이미 mmt4d ukernel보다 빠르며, 4스레드와 8스레드의 큰 형상에서는 여전히 느리고, 남은 격차는 분할과 스레드화에 있다(추적 항목 #24932). 출처: IREE v3.13.0, PR #25000

  • 커널과 펌웨어 라인이 주말 끝에 침묵에서 재가동으로 전환(10-23): linux-xuantie-kernel은 10-23 11:23에 “riscv: Migrate T-Head extensions to the vendor extension framework”를 반영하여, 이전에 이름이 변경된 XUANTIE 벤더 확장 키를 커널의 벤더 확장 프레임워크로 전면 이전했으며, 이로써 10-16부터 이어진 7일 연속 침묵이 끝났다. 같은 날 ruyi-imager는 10:30에 “Add SpacemiT K3 UFS and UEFI provisioning support”를 추가했고, support-matrix는 10:47에 RDC2022-D1s의 RT-Thread 기본 테스트 보고서 3건을 보충했다. 세 라인은 이전 주 내내 동작이 없었고 투입은 전부 openRuyi의 사용자 공간 소프트웨어 패키지에 집중되었으며, 주말의 이 커밋들은 중심을 플랫폼과 보드 측으로 되돌렸다. 출처: 커널 커밋 92c3f534, ruyi-imager 커밋 732a9214, support-matrix

  • 서밋 폐막, 커뮤니티 산출물 집중 공개: 회고 게시글에서 7개 실기기 데모와 재현 가능한 가속 데이터 제시: 제6회 RISC-V 중국 서밋이 10-18부터 10-20까지 선전에서 개최되었고, 10-22 11:31에 포럼이 회고 게시글을 발표하여 규모 데이터를 제시했다——오프라인 전문 관람객 3600명 이상, 팀 10명 현장 참석, 기술 보고 2건, 기술 포스터 6편, D15 독립 전시 구역. 포스터의 핵심 수치로는 패키지 관리자 메타데이터 인덱스 328개 이상 소프트웨어 패키지, 265개 이상 시스템 이미지, 41개 개발 보드 포함이 있으며, PyPI에 릴리스되어 RevyOS와 Bianbu 저장소에 연동되었다; 과정 재구성 누적 821개 영상, 144.1만 재생. 7개 데모 중 가장 설득력 있는 것은 OpenCV RVV 가속 대조 실험으로: 동일 하드웨어 플랫폼에서 ruyi 설치 버전이 배포판 기본 OpenCV 대비 이미지 필터링과 특징 추출 등 연산자에서 3~8배 가속을 구현했다. 다음 날 포럼에서는 “RISC-V Linux 실습 과정 02｜충분한 C 언어 기초” 강의 자료가 추가로 등록되었다. 출처: 서밋 회고 게시글 #2893, 실습 과정 02 #2894

2. RuyiAI 스택 진행 상황(PyTorch / Triton / TileLang RISC-V 적응)

모니터링 기간 개요: RuyiAI-Stack 조직(18개 저장소)의 이번 주 동작은 pytorch(다섯 번의 아침 각각 전체 브랜치 재작성 완료), llvm-project(8일 침묵 후 연속 3회 베이스 교체), triton-riscv(야간 빌드 1회 재개 후 정지), ruyiai-daily(7회 연속 발행) 및 사이트 저장소(기여자 데이터 매일 정기 갱신)에 집중되었으며; tilelang-riscv, harness, FBGEMM, IntrinTrans, VecIntrinBench, cpuinfo, torq-tile, caffe, mxnet, dsh-osc는 모니터링 기간 내 커밋이 없었다.

검증 및 캐시: riscv-arch-test 3건 머지, XiangShan CoupledL2는 set index 기준으로 bank 분할

논문: 장벡터 프로세서에서 FlashAttention 재배치, 실측 1.84~2.08배 가속

arXiv 2610.29489v1 《Reorienting the Vector Axis: Restructuring FlashAttention for Long-Vector Processors》(Emmanuel Irabor, Marc Casas)는 PyTorch의 CPU FlashAttention 커널을 2KB 벡터 레지스터를 갖춘 RISC-V CPU로 이식하고, 먼저 냉정한 베이스라인을 제시한다: 최대 부동소수점 처리량의 16.2%에 불과하다.

원인 분석은 구체적이다: 원래 커널은 쿼리 행을 행 단위로 진행하며, V와의 곱셈은 64개 원소 헤드 차원을 따라 벡터화되고, softmax의 행별 최댓값과 합계는 「전체 레지스터를 스칼라로 붕괴시키는」 리덕션이며, 소프트웨어 지수 함수의 다항식 계수는 tile 데이터와 벡터 레지스터를 두고 경쟁하여 스택으로 오버플로우된다. 세 가지가 겹쳐 벡터 레지스터 활용률이 올라가지 않는다. 두 가지 개선 방법 모두 알고리즘과 수치는 변경하지 않는다: 첫째, 점수 tile과 실행 출력을 함께 전치하여 쿼리가 선형 연속 축에 놓이게 하면, 「하나의 tile에 쿼리를 몇 개 담을지」라는 하나의 파라미터가 커널 각 구간의 벡터 길이를 통일적으로 결정하게 되어 두 리덕션이 자연히 사라진다; 둘째, 다항식 계수를 스칼라 레지스터로 옮겨 오버플로우를 제거하면 softmax의 벡터 메모리 접근 명령이 78.7% 감소한다.

실측: 헤드 차원 64에서 두 항목을 합치면 전체 커널 사이클이 1.84~2.08배 가속으로 줄고, 부동소수점 활용률은 16.2%에서 29.7%로 상승한다; 동일 설계의 FPGA에서도 두 변경의 순서가 일치하고 수익이 더 높아 2.71배에 달한다. 본 스택에 대한 의의는 숫자가 아닌 방법에 있다: 벡터 길이 적응과 레지스터 압박이야말로 triton-riscv와 tilelang-riscv의 RVV 저하에서의 구조적 문제이며, 「intrinsics가 있느냐 없느냐」가 아니다; 논문의 「머신에 맞춰 tile 내 쿼리 수를 매칭」은 IREE가 Tile N을 vlen/8로 취하는 것과 같은 종류의 결정으로, 직접 동일 기준 비교가 가능하다. 출처: arXiv 2610.29489

7. 트렌드 관찰

패키징 단위가 “소스 트리”에서 “의존성 패키지”로 전환, 이번 주 폐쇄집합 보완에서 규격 보완으로 중심 이동 완료

이번 주 637건 커밋의 주된 흐름은 하나뿐이다: “소스와 함께 vendor”를 “의존성별 패키징”으로 전환. Rust 측 crate 폐쇄집합 보완(uv 빌드 백엔드의 23개 rust-uv-* 패키지 포함), Python 측 fsspec의 모든 주요 클라우드 백엔드 보완, Go 측 vendor 제거 후 삭제된 디렉터리에 필요하게 된 가져오기 경로를 하나씩 보충. 순서 자체가 vendor 제거의 완료 조건이 vendor 디렉터리를 삭제하는 것이 아니라, 각 의존 모듈이 배포판에서 원래 가져오기 경로로 해석될 수 있게 하는 것임을 보여준다——가져오기 경로 보충이 없으면 vendor 삭제는 곧바로 컴파일 실패로 이어진다.

10-22의 초점은 이미 「빌드가 되는가」에서 「감사 가능한가」로 옮겨갔습니다. 54건의 소스 체크섬 보완과 %autochangelog 전환으로 m부터 x까지의 패키지명 구간을 커버했습니다. 소스 체크섬은 빌드 입력의 검증 가능성을 결정하고, %autochangelog는 변경 기록이 수기 작성이 아니라 커밋 이력에서 생성되도록 결정합니다. 이 두 가지가 연결되면 CVE 수정이 하나의 통일된 경로를 따라 전파됩니다. RuyiAI에 대한 간접적 가치는 상위 계층의 사용성에 있습니다. PyTorch의 DataLoader, checkpoint, 데이터셋 도구는 대부분 fsspec를 통해 원격 저장소에 접근하며, 백엔드가 갖춰졌는지 여부가 학습 스크립트가 K1/K3에서 실행 가능한지를 직접 결정합니다. 배포판이 상위 계층을 위해 보완하는 이 부분의 의존성은 단일 연산자 최적화보다 「사용 가능한가」를 더 크게 결정합니다.

AME를 예로 들면, 이번 주에 확장이 제안에서 사용 가능까지 이르는 완전한 경로가 보입니다: 먼저 백엔드 설계와 명령어 집합 정의(LLVM #16, #24, #27, #29)가 있고, 이어서 lowering과 스케줄링 구현(#30, #31, #32)이 있으며, 동시에 시뮬레이터가 실행 가능한 의미론(QEMU ame-0.6)을 제공하고, 마지막으로 연산자 라이브러리가 테스트 가능한 kernel과 검증 스위트(AME-operator)를 제공합니다. Ztt도 이번 주에 한쪽을 보완했습니다—ruyisdk/llvm-project의 AME 브랜치에 spec v0.6 초판 지원이 반영되었고, GCC 측 Ztt Md 지원, QEMU의 Ztt 명령어 패밀리 구현과 대응합니다.

P 확장은 같은 경로를 가지만 이미 후반부에 도달했습니다: QEMU는 전체 명령어를 커버(12건 마무리 배치), GCC는 0.6으로 업데이트, LLVM 측은 mulq, 승산 상위 누적, sati/usati, Packed Pair 등의 intrinsics가 배치별로 업스트림에 머지되었습니다. 대조해 보면, P 확장은 애플리케이션 측 benchmark가 부족하고, AME는 실제 기기가 부족합니다. 이 순서는 방법론으로 기록할 가치가 있습니다: 시뮬레이터가 없으면 컴파일러를 검증할 수 없고, 연산자 라이브러리가 없으면 시뮬레이터를 검증할 수 없습니다. 세 가지가 모두 갖춰지기 전에 성능을 논하는 것은 의미가 없고, 갖춰진 후에야 병목이 하드웨어와 실측으로 옮겨갑니다. 이번 주의 진전은 「갖춤」이지 「더 빠름」이 아닙니다.

RVV 백엔드의 초점이 「명령어가 있는가」에서 「블로킹과 스레딩」으로 이동

IREE는 이틀 만에 f32에서 f16으로의 정밀도 단계를 완료했으며, 두 번 모두 동일한 lowerRiscvVFmaccLike와 동일한 누산기 합법화를 재사용했습니다. 순서는 먼저 올바른 경로(f32)를 확보한 뒤, 확장 가용성에 따라 가장 빠른 경로(f16 네이티브, f16 확장, +zvfhmin 폴백)를 선택하는 것이며, 비용 모델은 세 경로에 각각 가격을 매깁니다. X60에서의 실측은 병목 위치를 명확히 보여주었습니다: 단일 스레드 inner_tiled는 이미 mmt4d ukernel보다 빠르지만, 4스레드와 8스레드는 여전히 느립니다.

arXiv의 긴 벡터 FlashAttention 재구성 논문이 내놓은 결론도 동일한 맥락입니다: 점수 tile과 실행 출력을 전치하고, 쿼리가 선형 연속 축 뒤에 위치하도록 하면 두 개의 축소가 자연히 사라지고 레지스터 오버플로가 제거되어, 전체 코어 주기가 1.84~2.08배로 줄고 부동소수점 활용률이 16.2%에서 29.7%로 상승했습니다. 둘 다 같은 것을 말하고 있습니다—단일 코어 명령어 선택이 완료된 후에 남는 것은 블로킹 파라미터와 스레딩입니다. tilelang-riscv와 triton-riscv에게 이것은 항목별로 대조 가능한 로드맵입니다: Tile N = vlen/8의 산정 방식, 비용 모델의 구간 설정 방식, tile 내 쿼리 수와 벡터 길이의 바인딩 관계는 모두 자체 lowering에서 동일 기준으로 비교해 볼 가치가 있으며, 단지 「f16을 지원하는가」만 볼 것이 아닙니다.

배포판이 데스크톱과 가상화 검증 스택을 깔기 시작, 플랫폼 형태에 서버와 임베디드 두 경로 등장

openRuyi의 오픈 PR 큐에 같은 방향의 제안 묶음이 등장했다: qemu GUI 테스트 기능 활성화(#1421), virglrenderer 신규 추가(#1415), ovmf의 fwupd 지원(#1436), ydotool 신규 추가(#1457), xorriso의 man 페이지 충돌 수정(#1489). 다섯 항목은 각각 가상화, 그래픽 가상화, 펌웨어 업데이트, 입력 자동화, 광학 디스크 이미지 툴체인에 속하며, 합치면 「RISC-V에서 완전한 데스크톱을 구동하고 이를 자동 검증한다」는 것을 가리킨다. 이는 서밋에서 선보인 「AI 기반 IDE 그래픽 테스트」와 동일한 요구의 양 끝단이다.

플랫폼 형태에도 동시에 분기가 나타났다. 서버급은 SiFive V100을 대표로 하며, 규격상의 UEFI, ACPI, SMBIOS가 필수 요건이 되고 BRS 적합성 테스트와 설치 체인이 입장권이다. 임베디드 및 소비자급은 K1/K3을 대표로 하며, 경로는 보드 이미지, 툴체인, 지원 매트릭스다. 이번 주 ruyi-imager가 K3의 UFS 및 UEFI 프로비저닝 지원을 새로 추가한 것은 이 분기가 도구 측에서 나타난 첫 번째 구체적 움직임이며, 반면 openRuyi 메인 저장소는 주 전체에 걸쳐 서버 플랫폼 관련 커밋이 0건이어서 V100의 호환 목록 이행 여부는 2026.10 버전과 후속 펌웨어 라인의 움직임을 지켜봐야 한다.
