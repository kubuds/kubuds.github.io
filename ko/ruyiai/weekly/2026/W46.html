RuyiAI 위클리 리포트 (2026-11-09 ~ 2026-11-13)

2026-11-13 Kubuds

보고 주기: 2026년 11월 9일(월)부터 11월 13일(금)까지, 총 5영업일.

자료 출처: 본 간행물의 RuyiAI 동향 데일리 리포트 5호(2026-11-09~2026-11-13, 각 호 모니터링 기간은 전일 04:30부터 당일 04:30까지이며, 월요일은 지난 3일분으로 주말을 포함); 또한 RuyiAI-Stack, ruyisdk, buddy-compiler, openRuyi-Project 4개 조직의 168시간 저장소 점검(점검 범위는 11-14 오전까지), RuyiSDK 개발자 커뮤니티와 openRuyi 배포판 뉴스 페이지의 이중 출처 재확인, RuyiAI 공식 홈페이지 3개 페이지 스냅샷과 블로그, 문서 인덱스, 그리고 Google News와 arXiv의 표적 검색을 포함.

편집 설명: 이번 주에는 두 가지 주축이 동시에 교차했다. 하나는 릴리스, 다른 하나는 벡터 경로의 커버리지다. 릴리스 측면에서 ruyi 0.54.0이 11-10에 정식 버전으로 출시되었으며, 이전 버전으로부터 47일 만이다. triton-riscv는 11-09에 저장소 역사상 첫 release/ 태그를 찍었고, 11-10에는 RISC-V 호스트에서 AMD GPU 백엔드를 기본 활성화했다. Ruyi Imager 1.1.0도 같은 날 릴리스되었으며, 격주 동향 080호는 이 “3연속 릴리스”를 대외 공식 표현으로 정리했다. 컴파일러 측면에서 buddy-mlir는 한 주에 13건을 병합하며 i1 마스크, libm-only 수학 함수, bf16, 모든 종류의 리덕션, rank-0 패딩, 정수 행렬 곱셈을 유형별로 VIR 벡터 경로에 연결했고, FlagGems 스위트의 SG2044 통과 수는 3980에서 4006으로 상승했으며, 1811개 커널에 남아 있던 linalg.fill과 linalg.matmul이 모두 0으로 떨어졌다. 커버리지와 함께 추진된 것은 안전성이다. VLEN 관련 세 가지 변경은 모두 같은 유형의 실패를 가리킨다. 오류를 보고하지 않고, 단지 잘못 계산할 뿐이다. 공백도 같은 지점에 남아 있다. openRuyi의 월간 버전은 여전히 2026.09에 머물러 있고, 10월과 11월은 지금까지 새 버전이 나오지 않았다.

2.1 triton-riscv: “열여덟 개의 야간 태그”에서 첫 정식 릴리스까지

날짜: 2026-11-06 ~ 2026-11-14　출처: 정식 릴리스 태그, PR #105 README를 wheel 우선으로 변경

이 저장소는 이번 주에 세 단계를 완료했다: 릴리스 계층을 세우고(첫 release/ 태그), 설치 경로를 소스에서 wheel로 바꾸고, 이기종 백엔드를 “컴파일 가능”에서 “실기에서 실행 가능”으로 끌어올렸다. 세 단계 사이에는 선후 의존 관계가 있다—재현 가능한 wheel 태그가 없으면 GPU 백엔드 검증은 소스 빌드에 머물 수밖에 없고, AMD 백엔드 검증은 다시 릴리스 체인에서 자체 호스팅 riscv64 runner에서만 나타나는 몇 가지 문제를 드러냈다.

2.1.1 태그 자체가 릴리스 작업의 전부다

날짜: 2026-11-06, 11-09　출처: release/20261108-6895885, PR #101

release/20261108-6895885는 커밋 6895885를 가리키며, 이는 11-06의 “AMD를 위해 riscv64에 누락된 codegen 라이브러리 보충”（#102）병합 커밋으로, 야간 버전 nightly/20261106-6895885와 동일한 지점이다. 당일 세 건의 커밋(#105, #106, #107)은 모두 태그 이후에 반영되어 이 패키지에 들어가지 않았다—이는 첫 정식 버전이 사실상 지난 주말의 코드 상태를 담고 있음을 의미한다.

릴리스 체인의 두 가지 부수 변경은 이전에 이미 모니터링 기간 내에 반영되었다: #101은 #100 이후 드러난 두 가지 릴리스 체인 문제를 수정했고(릴리스 워크플로가 CI와 동일한 체크아웃 액션 버전을 사용하도록 변경, scripts/release.sh에 백엔드 등록 단계 추가하여 release가 산출하는 wheel이 CI가 빌드한 wheel과 동일한 플러그인 등록 정보를 갖도록 함), #102는 setup.sh가 AMD codegen 라이브러리 누락을 감지하면 로컬에서 빌드하여 약정된 경로에 배치하고 env.sh가 TRITON_AMD_CODEGEN_PATH를 그곳으로 지정하도록 했다. 야간 버전에는 추가로 고유 버전 접미사 .dev<날짜>가 붙었는데, 이전에는 매 빌드가 Triton 자체 버전 번호를 공유하여 패키지 인덱스가 중복 버전을 거부했기 때문이다.

2.1.2 설치 경로를 wheel 우선으로 전환, 빠른 시작은 역어셈블리 확인으로 변경

날짜: 2026-11-09　출처: PR #105, PR #107

#105 README의 설치 섹션을 재작성했다. 먼저 wheel 경로와 이를 호스팅하는 패키지 인덱스를 제시하고, 이어서 필요한 LLVM 아카이브와 이를 가리키는 변수를 제시했다. 소스 경로는 make setup으로 압축했으며( .venv 생성, 고정 버전 Triton 클론, 고정 버전 LLVM 및 buddy 빌드 다운로드), 기존의 “가상 환경 생성, 의존성 설치, 환경 스크립트 15개 변수” 설명은 짧은 주석 한 줄로 정리했다. #107에서 이어서 수정이 이루어졌다. 패키지 인덱스에는 아직 triton과 buddy 도구가 없어 README의 바이너리 설치 항목에 제시된 주소가 실패하게 되므로, 두 프로젝트 각각의 GitHub releases를 가리키도록 바꾸고 디스크에서 wheel을 설치하도록 했다. 같은 커밋에서 Python 3.14에서의 lit 크래시도 수정했다. Triton은 which로 PATH에서 lit을 찾는데, LLVM 트리에 있는 lit은 모듈 수준에서 main을 호출하고, Python 3.14는 Linux에서 기본적으로 forkserver 시작 방식을 사용하므로 재임포트 시 바로 크래시가 발생한다. 수정 방법은 빌드 인터프리터의 bin 디렉터리를 PATH 맨 앞에 두는 것이다.

2.2 triton-riscv의 이기종 노선: RISC-V 호스트가 AMD 카드를 구동

날짜: 2026-11-10　출처: PR #110 GPU 백엔드 기본 활성화, README

#110이 머지된 후, 이 저장소의 위치는 “RISC-V CPU의 벡터 유닛에서만 Triton을 실행”하는 것에서 “RISC-V 호스트에서 이기종 가속기를 구동”하는 것으로 확장되었다. 세 가지 변경 중 빌드 측은 기존 Buddy LLVM SDK로 riscv64용 AMD codegen 라이브러리를 빌드하고 패키징한다. 드라이버 측은 CPU와 GPU 중 하나를 선택할 때의 모호성을 제거했으며, 규칙은 사용 가능한 GPU를 우선 선택하는 것이다(해당 파일에서 순수 4줄 삭제). 문서 측은 README에 AMD GPU 섹션을 추가하여, ROCm이 설치되어 있을 때 백엔드가 torch.version.hip을 통해 자체 활성화되고, wheel에는 ROCm 런타임이 포함되지 않으며, 강제로 CPU로 되돌리려면 TRITON_DEFAULT_BACKEND=triton_shared를 사용한다고 설명한다.

실기 검증이 이 변경의 무게를 보여준다. SG2044에 RX 7900 XTX를 조합하고, torch와 ROCm은 openRuyi의 소프트웨어 저장소에서 가져왔으며, GPU 장치를 숨겼을 때의 자동 폴백도 추가로 테스트했다. 주요 AI 가속 카드 어느 것도 RISC-V 호스트 드라이버를 제공하지 않는 시점에서 AMD 카드를 먼저 지원하는 것은 가장 현실적인 한 걸음이다. ROCm의 RISC-V 측 작업은 원래 openRuyi 저장소에서 유지되고 있으며, 두 가지는 같은 사람들이 추진하고 있다.

시간 차이는 기록해 둘 만하다. 당일 10:22에 나온 나이틀리 빌드 nightly/2026-11-10-209274f는 이 머지보다 앞서므로 그 패키지에는 아직 GPU 백엔드가 포함되어 있지 않다.

2.3 릴리스 체인과 릴리스물: CI 수정 3건, wheel 40% 경량화, 명시적 타깃은 -O3로 전환

날짜: 2026-11-11 ~ 11-12　출처: PR #113 공유 git 인증, PR #116 wheel 슬림화, PR #117 -O3 및 +zvfbfmin

11-11의 세 건의 머지는 모두 릴리스 체인에 관한 것으로, 컴파일러 기능을 변경한 것은 하나도 없다. #113은 CI와 release.sh가 각각 복제해 두었던 “일회성 전역 git 설정”을 scripts/_git-auth.sh로 추출하여 공유하도록 했다. 자체 호스팅 riscv64 러너에서의 익명 git 트래픽은 인증을 받지 못하며, 업스트림 FetchContent가 googletest를 가져올 때 401을 반환하고 tty가 없는 상황에서 사용자 이름 프롬프트에 멈춘다. #111은 릴리스 스크립트 자체를 수정했다. #112는 문서로, #110 이후 CPU 경로에서 더 이상 필요 없는 torch 설치 명령을 삭제하고, AMD 섹션에 “torch를 설치해야 하며, 반드시 AMD GPU를 사용할 수 있는 빌드여야 한다”는 내용을 보충했다. 세 건의 작성자는 동일 인물이며, 시간은 17:59부터 21:11에 집중되어 있다.

11-12의 두 오픈 변경 사항은 모두 릴리스 산출물 자체를 향한 것입니다. #116은 wheel에 포함된 LLVM과 buddy 도구가 이전에 --strip-unneeded를 사용했고 디버그 섹션이 여전히 남아 있음을 지적합니다. triton-shared-opt 단일 파일에 아홉 개의 .debug 섹션이 있고 크기가 407 MB였는데, --strip-all로 변경한 후 118 MB로 줄었으며, 일곱 개 도구의 총 페이로드가 약 970 MB에서 약 576 MB로 줄어 원래 크기의 약 60% 수준이 되었습니다. #117은 크로스 컴파일 경로의 최적화 수준을 변경합니다. RISC-V 타깃 트리플을 명시적으로 지정할 때 빌드 흐름이 이전에는 LLVM 중간 단계를 건너뛰고 llc가 기본 최적화 수준을 사용하여, MLIR이 스칼라 형태로 남은 루프가 목적 파일에서도 여전히 스칼라로 남았습니다. 변경 사항은 이러한 빌드에 대해 먼저 opt -O3와 llc -O3를 실행하며, 트리플이 없는 네이티브 경로(llc -O0)와 IME 경로는 변경하지 않습니다. 같은 변경에서 +zvfbfmin을 기본 llc features에 추가했습니다. 그렇지 않으면 확장 가능한 bf16이 llc에서 바로 중단되는데, buddy-mlir의 #1054가 바로 해당 확장이 있다고 기본 가정하고 있어 양쪽이 반드시 동기화되어야 합니다. 이 두 변경은 11-13 데일리 리포트에서 여전히 오픈 상태이며, 그중 #117은 11-14 15:19에 메인 브랜치에 머지되었습니다.

3.1 ruyi 0.54.0: “설치 가능한가”를 계산 가능한 사실로 바꾸다

날짜: 2026-11-10　출처: ruyi 0.54.0, PR #507 ELF ABI 호환성

0.54.0의 기능 면은 11-02 프리뷰 0.54.0-beta.20261102의 전체 내용이며, 정식 버전은 프리뷰 대비 버전 번호 커밋 한 건만 추가되어 0.53.0부터 계산하면 총 71건의 커밋, 74개 파일입니다. 핵심은 ELF ABI 호환성입니다. 미리 컴파일된 바이너리가 대상 기기에서 실행될 수 있는지는 ELF 파일 헤더에 흩어져 있는 일련의 사실에 달려 있습니다. 어떤 동적 라이브러리가 필요한지, 해당 라이브러리에 어떤 심볼 버전을 요구하는지, 그리고 아키텍처 관련 능력 요구 사항은 무엇인지입니다. 이전에는 소프트웨어 소스에 이들을 기록한 곳이 전혀 없었지만, ruyi는 이제 이 정보를 스캔하여 저장하고 설치 전에 비교합니다.

RISC-V 쪽 수집이 가장 손이 많이 간다. 확장이 버전 번호를 붙여 문자열로 구성되기 때문이다. 이번 기간 커밋에는 버전이 붙은 단일 문자 확장을 파싱하는 것, 호스트 부동소수점 ABI에 따라 ld.so.cache 항목을 필터링하는 것, 스택 정렬 요구사항을 계산에 넣는 것이 포함된다. 호스트 측에서는 x86-64와 AArch64 탐지도 별도로 구현했고, 호스트 라이브러리는 요청된 soname으로 해석하며, 해석할 수 없는 soname을 만나면 “판정 불가”로 보고하지 “불가”로 단정하지 않는다. 이 3상태 설계가 “설치 불가”와 “알 수 없음”을 구분한다. 데이터 면은 저장소 측 ABI sidecar를 통해 distfile 이름으로 해석한다. rescan-package-abi와 플러그인 산출물에 strip-components가 새로 추가되어 아카이브에 선행 디렉터리가 있는 경우를 처리한다. sidecar에는 크기 상한이 있으며, 잘못된 sidecar는 “ABI 정보 없음”으로 간주되어 버려진다.

VecIntrinBench, IntrinTrans, FBGEMM 세 저장소는 주 전체에 걸쳐 커밋이 전무했으며, 헤드 커밋은 각각 02-13, 06-25, 07-13에 멈춰 있어 침묵이 이미 수개월째 지속되고 있다. 이는 벡터 측에 진전이 없다는 뜻은 아니다. 이번 주 벡터 변경은 모두 buddy-mlir의 VIR 계층에서 발생했고, 두 가지 범주로 나뉜다. 하나는 “벡터 루프에 진입할 수 있는가”(커버리지)를 결정하고, 다른 하나는 “벡터 루프가 충분히 채워지는가”(성능)를 결정한다. 투자는 측정 도구가 아닌 컴파일러에 집중되고 있으며, 이러한 분업은 09월부터 지금까지 변함이 없다.

4.2 i1 마스크의 바이트 단위 읽기/쓰기 (#1052)

날짜: 2026-11-12　출처: PR #1052

memref 요소 타입이 i1일 때, 가변 길이 벡터는 이전까지 곧바로 거부되었다(a memref of i1 needs fixed vectors 안내). memref는 요소당 1바이트를 차지하고 i1 벡터는 비트당 하나의 레인을 차지하므로, 레인별 하강(lowering)은 고정 길이 벡터에만 존재하기 때문이다. 그런데 Triton의 load/store 마스크가 바로 i1 memref이다. 순수 VIR 파이프라인에 가변 길이 벡터를 더할 때, 325개 Triton-RISCV 테스트 파일 중 179개가 이 오류에서 막혔으며, 이번 주 일곱 건 중 영향 범위가 가장 넓은 건이다.

수정 방식은 바이트 단위 읽기/쓰기이다. 연속 접근은 i8 벡터의 llvm.load/store를 사용하고, 비연속 strip-mined 영역은 vp.strided.load/store로 전 레인을 열어 처리한다. 아울러 i1 레인을 1바이트로 크기 산정하도록 했다. 이전에는 첫 동적 벡터가 i1인 영역을 1비트로 계산하여, VLEN 256에서 vector<[512]xi1>과 같은 열여섯 개 레지스터 규모가 산출되었다.

4.3 libm-only 수학 함수의 레인별 전개 (#1053)

날짜: 2026-11-12　출처: PR #1053

LLVM이 가변 길이 벡터에서 하강시키지 않으려는 수학 함수(erf, erfc, cbrt, powf, atan2, acosh 등)는 레인별 전개로 변경되었다. vector<[N]xT>의 N 곱하기 vscale개 레인을 하나씩 extract하고, 스칼라 함수를 호출한 뒤 다시 insert한다. 발단은 convert-math-to-libm이 가변 길이 벡터를 고정 길이 벡터와 동일하게 처리하여 앞 N개만 계산하고 나머지는 조용히 0으로 설정한 것이다. 가변 길이 erf는 VLEN 128(vscale 2)에서 절반의 레인이 틀린 값이 된다. 효과는 테스트 면에 바로 나타난다. FlagGems 스위트 4045항목의 SG2044(VLEN 128) 통과 수가 3980에서 4006으로 올랐으며, 수정된 26항목은 test_erf와 test_gelu이고 신규 실패는 없다.

4.4 bf16의 두 경로와 전수 검증 (#1054)

날짜: 2026-11-12　출처: PR #1054

RVV는 Zvfbfmin이 있어야만 bf16을 벡터 레지스터에 넣을 수 있으며, 해당 확장이 없으면 LLVM은 로드 한 번조차 하강시키지 않으려 한다. 이번 변경은 하강기(downstream)에 rvv-mattr 파라미터를 추가하여, 기본적으로 Zvfbfmin이 있는 것으로 처리한다(Buddy의 여러 RVV 타깃인 K3의 X100과 A100, SG2044 모두 보유). 명시적으로 -zvfbfmin을 주면 정수 비트로 처리하도록 변경하여, bf16 벡터를 i16으로 읽고 쓰며 extf와 truncf는 정수 연산( truncf는 짝수 반올림), absf와 negf는 부호 비트로 처리한다.

검증 방법은 이번 주 가장 무거운 부분이다. truncf는 전체 2^32개 f32를, extf, absf, negf 및 extf-mulf-truncf는 전체 2^16개 bf16을 커버하며, SG2044와 K3 두 코어에서 Zvfbfmin 경로와 비트 단위로 대조한 결과 동일했다. 이러한 검증 비용은 bf16이 이미 출하 경로로 취급되고 있음을 보여주며, “시간 되면 하자”는 식의 최적화 항목이 아니다.

4.5 fast-math 플래그와 전체 리덕션 종류 (#1055, #1056)

날짜: 2026-11-12　출처: PR #1055, PR #1056

#1055은 strip-mined 하강 과정에서 fast-math 플래그가 유실되는 문제를 수정한 것이다. contract가 붙은 arith.mulf와 arith.addf가 일반 fmul과 fadd로 재구성되어 LLVM이 융합하지 못했다. 이제 플래그가 동일 연산자와 함께 벡터 루프와 테일에 전달되어, f32 곱셈-덧셈은 vfmacc를 생성하고 bf16은 +zvfbfwma 하에서 vfwmaccbf16을 생성한다. 작성자는 K3의 X100과 A100에서 4M 레인 단위로 fmaf 전개와 비트 단위 비교를 수행했고 결과가 일치했다. 이는 일곱 건 중 명령 선택을 직접 변경한 유일한 건이다.

#1056은 vir.reduce를 부동소수점 add와 maxnum만 인식하던 것에서 vector.reduction의 전체 종류로 확장했다. add, mul, minsi, minui, maxsi, maxui, and, or, xor, minnumf, maxnumf, minimumf, maximumf이며 정수도 함께 지원하고, verifier가 kind와 요소 타입의 일치 여부를 검증한다. 이전에는 Triton의 정수 합계, min/max, 곱, all/any(그리고 이에 의존하는 argmin, argmax, count_nonzero, 바이토닉 정렬과 기수 정렬)가 모두 루프에 남아 있었다. 변경은 570줄을 추가하고 9개 파일을 건드렸다.

4.6 잔여 경로 마무리: rank-0 채우기와 정수 행렬 곱셈(#1057, #1058)

날짜: 2026-11-12　출처: PR #1057, PR #1058

#1057은 rank-0 memref의 linalg.fill(대부분 리덕션의 누산기)을 단일 memref.store로 하강시켜, FlagGems 1811개 커널에 남아 있던 linalg.fill을 393에서 0으로 줄였다. #1058은 정수 행렬 곱셈도 하강할 수 있게 했다. A, B가 동일한 정수 타입이고 C보다 넓지 않을 때 먼저 부호 또는 제로 확장을 한 뒤 곱셈-덧셈(fma 없이)을 수행하며, RVV에서 int8 행렬 곱셈은 vsext.vf2와 vwmacc.vx를, 부호 없는 경우는 vzext.vf2와 vwmaccu.vx를 얻는다. 같은 건에서 동적 형상 matmul의 단언 실패도 수정했다. 두 건을 합치면 검증 가능한 커버리지 기준을 제시한다. 벤치마크 점수가 아니라 “얼마나 많은 linalg 또는 스칼라 경로가 남아 있는가”이다.

5. Buddy Compiler 동향

5.1 VLEN 정밀화의 전반부: #1032와 #1037

날짜: 2026-11-08　출처: PR #1032, PR #1037

#1032가 해결한 문제는 잘못된 실패 방식, 즉 오류를 내지 않고 그저 잘못 계산하는 유형이었다. 정확한 VLEN으로 빌드된 RISC-V 모델에서 벡터 코드는 그 하나의 VLEN에만 성립한다. llc에 VLEN이 명시적으로 전달되고(+zvlNb와 -riscv-v-vector-bits-max), decode attention의 가변 벡터도 그에 맞춰 정해진다. 다른 VLEN으로 옮기면 모델은 크래시하지 않고 잘못된 결과를 직접 내놓는다.

수정 방식은 검증을 로딩 시점으로 앞당기는 것이다. runtime/rvv/BuddyRvvVlen.c가 생성자로 모델 라이브러리에 링크되어, 라이브러리가 로드되는 즉시 vlenb를 읽고 빌드 시의 정확한 VLEN과 다르면 정보를 출력하고 _exit(1)로 프로세스를 종료한다. exit가 아니라 _exit를 쓰는 것은 의도적이다. 로더가 락을 보유한 동안 소멸자를 실행하면 교착이 발생하기 때문이다. 리뷰 후 추가 커밋으로 검증을 “빌드 변수 기준 판단”에서 “최종 llc 옵션 기준 판단”으로 변경했다. 기존에는 네이티브 빌드가 모델 자체의 LLC_ATTRS로 VLEN을 지정할 수 있었는데, BUDDY_RISCV_VLEN이 그것과 불일치하면 검증값이 실제 코드와 어긋날 수 있었고, 게다가 세 번째 단계에만 링크되어 Qwen3-VL의 비전과 디코딩 두 shim, 그리고 계층적 링크 경로가 모두 누락되어 있었다. 이제 빌드 스크립트가 최종 llc 옵션에서 정확한 VLEN을 추출하며(VIR 하강과 같은 곳을 읽음), 구성 단계에서 옵션이 서로 모순되면 즉시 실패한다. 테스트는 이 변경의 나머지 절반이다. test_buddy_rvv_vlen.py는 VLEN 128부터 65536까지 각각 모델 라이브러리를 빌드하고, 호스트에 해당하는 하나만 로드되며 나머지는 모두 종료 코드 1로 끝난다. 문서에는 A210과 K3 두 편의 DeepSeek-R1 배포 설명을 동기화하여 “어떤 빌드가 정확한 VLEN이고 어떤 것이 범용 RVV인지” 경계를 명확히 했다. A210의 커널은 고정 길이 벡터이고 VIR이 없어 범용 빌드에 속하며, K3의 prefill_ime는 반드시 1024여야 하므로 정확한 VLEN에 속한다.

#1037은 다른 방향의 오류를 수정한 것이다: -lower-vir-to-vector는 rvv-vlen을 주지 않고 확장 가능한 벡터도 켜지 않았을 때 호스트 레지스터 폭에 따라 고정 길이 벡터의 크기를 정하는데, 호스트 인식은 x86(AVX2, AVX-512)과 SVE만 커버하고 V 확장이 있는 RISC-V 호스트는 전부 일반 기본값(128비트, 레지스터 16개)으로 떨어진다. 그 결과는 테스트에서 나타났다: #1030 이후 kernels 파이프라인이 llc 옵션이 없을 때 호스트에 따라 VIR을 낮추는데, riscv64 CI 호스트는 VLEN 256인데도 128비트로 처리되어 q, k 노름의 제곱이 vector<32xf32> 세그먼트 합산으로 쪼개졌고, 벡터 커널과 비트 단위로 비교하는 순서가 달라져 vir decode qk_norm ... same bits가 거짓으로 판정되었다. 작성자는 먼저 테스트에서만 rvv-vlen=1024 use-scalable=false를 고정하는 변경을 추가했다가 곧바로 스스로 되돌렸다—그것은 llc 옵션 밖에 또 하나의 VLEN 설정을 만드는 것으로 #1032의 방향과 충돌한다. 최종 수정 방식은 낮추기 단계에서 RISC-V 호스트를 인식하고(호스트 CPU 특성과 hwprobe를 읽음) 실제 VLEN에 따라 크기를 정하는 것이다.

5.2 f32 YOLOv8 엔드투엔드로 VIR 통과(#1041)

날짜: 2026-11-09(11-10 01:07에 머지됨)　출처: PR #1041, 머지 커밋 18c66ec

#1041은 f32 YOLOv8 그래프를 엔드투엔드로 VIR에 통과시킨다: 먼저 Linalg에서 VIR로의 낮추기를 하고, 그다음 VIR에서 벡터 방언으로의 낮추기를 한다. 이전에는 이 pass에 컨볼루션 패턴이 없었고, 그래프에는 직접 실패하는 세 가지 연산자가 또 있었다—한 변경으로 컨볼루션과 그 세 가지를 동시에 보완했다. 규모는 파일 14개, 1646줄 추가, 115줄 삭제, 커밋 13개다.

컨볼루션 두 계열을 모두 커버한다: 2차원 NHWC와 HWCF 조합, 2차원 NHWC와 FHWC 조합. 벡터화는 출력 채널 F를 따라 펼쳐지고, 각 (kh, kw, c)에 대해 입력 원소를 각 출력 픽셀마다 하나의 vir.fma로 브로드캐스트하므로 매번의 벡터 접근이 연속적이고 레인 간 리덕션도 없다—리덕션은 수평 명령과 후속 리덕션 트리가 필요해 좁은 VLEN에서 비용이 뚜렷하다; 대가는 FHWC 필터를 먼저 HWCF 버퍼로 병렬 복사해야 한다는 것으로, 한 번의 추가 이동으로 내부 루프의 연속 접근을 얻는다.

이전에 실패하던 세 가지 연산자도 함께 보완했다: rank-0 입력(memref<f32>가 linalg.generic에 직접 들어가면 memref.expand_shape에서 invalid reassociation이 발생하므로 한 번 로드한 뒤 브로드캐스트하도록 변경), 마지막 차원을 유지하는 linalg.reduce(예: DFL softmax의 1x16x4x2100, dimensions=[1], addf와 maximumf 조합), linalg.index를 읽는 명명 연산자(예: upsample의 linalg.map iota). 실기 기준은 분명하다: K3에서 f32 YOLOv8 pose의 원시 출력은 최대 6e-5 변하고, PyTorch와의 차이는 여전히 6e-4(bus)와 8e-4(zidane) 이내이며 변경 전과 일치한다; detect 모델의 검출 결과는 변하지 않고 속도도 떨어지지 않았다; f32와 IME 동적 라이브러리의 출력은 변경 전과 바이트 단위로 동일하다.

5.3 YOLOv8이 rax에 진입: 검출과 자세를 K3 매트릭스 엔진에서 실행(#1042)

날짜: 2026-11-10　출처: PR #1042

#1042는 Ultralytics YOLOv8을 buddy-cli의 rax 형식에 연결한다: yolov8n 검출(COCO 80클래스)과 yolov8n-pose(키포인트 17개), 입력은 모두 320x320이다. f32 모델은 VIR 낮추기를 거치고, 명세에 ime: true가 적히면 SpacemiT K3의 매트릭스 엔진에서 대신 실행한다.

리뷰 단계에서 보완된 두 가지 수정은 모델 자체보다 정보량이 많다. 첫째는 가중치 검증: 매니페스트에 params_size가 있고 러너는 가중치 파일이 그것과 일치하기를 요구하는데, 이전에는 가중치 파일이 짧으면 모델이 버퍼를 넘겨 읽을 수 있었다; 또한 러너가 rax 패키지만 받도록 요구하는데, 라이브러리와 가중치를 따로 주면 자세 모델이 검출 모델의 파라미터로 실행되기 때문이다. 둘째는 TCM 복사: IME 가중치의 TCM 사본은 가중치 주소로 캐시되는데, 새 가중치를 해제된 버퍼로 읽어 들이면 이전 사본이 적중했다, 이제는 가중치를 적재할 때마다 커널 측의 무효화 함수를 호출한다. 명세에는 params_size와 ime_params_size를 함께 유지해 ime: false일 때도 f32 버전을 빌드할 수 있다—같은 그래프, 두 백엔드 경로, 하나의 비교 가능한 기준선.

7. 동향 관찰

7.1 릴리스 체인이 기능보다 먼저: 이번 주에 고친 것은 “패키지를 낼 수 있는가”

triton-riscv의 1주일 내 머지 중 #110(AMD 백엔드)만 기능이고, 나머지 #101, #102, #105, #107, #111, #112, #113은 전부 릴리스 체인에 속한다: 백엔드 등록을 wheel에 포함, AMD codegen 라이브러리의 로컬 빌드, README의 wheel 우선, lit 탐색 순서, git 인증 추출, AMD 섹션의 torch 전제. 여기에 #116의 wheel 슬림화와 #117의 -O3까지 더하면, 이 저장소의 이번 주 산출물은 “설치 경로를 재현 가능하고, 다운로드 가능하며, 검증 가능하게 만드는 것”으로 요약할 수 있다.

이것은 개별 현상이 아니다. ruyi 0.54.0의 주요 내용 역시 “설치 전에 설치 가능 여부를 먼저 판정”하는 것이고, pytorch의 #56은 “테스트 케이스 0개 통과도 그린으로 간주”하는 것을 막으며, buddy-mlir의 야간 빌드는 6일간의 패키징 공백을 메운다. 네 저장소가 같은 주에 같은 종류의 일을 한다는 것은, 이 스택이 이미 “실행됨을 증명”하는 단계에서 “인도됨을 증명”하는 단계로 진입했음을 의미한다.

7.2 커버리지가 성능보다 우선: 393→0, 2→0, 179→0의 기준

이번 주 buddy-mlir의 일곱 건 중 #1055만이 명령 선택을 직접 변경하며, 나머지 여섯 건은 이전에 루프에 남아 있던 형태를 벡터 경로로 연결하는 작업이다: i1 마스크, libm-only 수학 함수, bf16, 리덕션 종류, rank-0 채우기, 정수 행렬 곱셈. 이런 변경을 평가하는 기준은 벤치마크 점수가 아니라 “아직 몇 개의 linalg 또는 스칼라 경로가 남아 있는가”여야 한다. 393이 0으로, 2가 0으로, 179개의 실패 파일이 0으로 줄어든 것이 모두 이 기준이다.

전날 #1050의 strip-mined 잔여분 축소와 대조하면, 이틀의 분업은 명확하다: 먼저 벡터 루프가 레인을 가득 채우게 하고(성능), 그다음 모든 연산자가 벡터 루프에 들어갈 수 있게 한다(커버리지). 순서를 뒤집으면 헛수고가 된다—가득 찬 폭의 루프만 있고, 들어가는 연산자는 여전히 몇 개뿐이기 때문이다.

7.3 VLEN 1024가 컴파일러와 런타임의 공동 압력점이 되다

1주일 내 세 곳의 변경이 VLEN 1024를 직접 겨냥한다: 로드 시점 검증(#1032), 리덕션 레인 손실(#1051), strip-mined 잔여분(#1050). 공통점은 동일한 하드웨어 사실이 각 계층에서 반복적으로 나타난다는 것이다—K3의 prefill_ime는 반드시 1024여야 하고, A100 코어에서 16개의 f32가 하나의 완전한 벡터이며, vector<[1]xT> 같은 형태는 VLEN 128/256에서 아예 도달할 수 없다.

같은 주에 업스트림 측에서도 같은 신호가 나타난다: V8의 리뷰 목록에 “Allow vlen=1024”(CL8585179)가 등장한다. 이는 긴 벡터가 더 이상 특정 보드의 로컬 설정이 아니라 런타임과 브라우저의 범용 경로로 진입하기 시작했음을 의미한다. 위험도 따라온다—CI의 riscv64 러너는 VLEN 256이고, 출하 하드웨어는 1024이므로 양자의 테스트 커버리지는 본질적으로 어긋난다. #1051 같은 “CI는 전부 그린, 보드에서는 전부 오류”인 결함이 바로 이런 어긋남의 산물이다.

7.4 조용한 오값의 검증 비용이 이미 입력 전수 열거 수준에 도달

#1054는 truncf에 대해 모든 2^32개의 f32를, 변환과 부호 연산에 대해 모든 2^16개의 bf16을 실행했고, #1055는 4M 레인에서 fmaf 전개를 비트 단위로 비교했으며, #1041의 수용 기준은 “변경 전과 바이트 단위로 동일”이고, #1051의 수용 기준은 25개 리덕션 테스트가 오류에서 정상으로 바뀌는 것이다. 네 건의 검증 방식은 다르지만 모두 같은 질문에 답한다: 결과가 맞는가, 빠른가가 아니라.

이유도 분명하다: 이번 주에 수정한 결함은 거의 전부 “오류를 보고하지 않고, 단지 잘못 계산”하는 것들이다—정확한 VLEN으로 빌드된 모델이 하드웨어를 바꾸면 조용히 오류가 나고, 확장 가능한 erf는 절반의 레인이 0으로 설정되며, 리덕션은 lane 0만 남고, 마스크가 비트 단위로 크기를 계산해 16개 레지스터 그룹이 된다. 크래시는 발견하기 쉽지만 오값은 그렇지 않다. 검증 비용이 입력 전수 열거 수준으로 상승했다는 것은, 이 스택이 이미 bf16과 리덕션 같은 기초 연산자를 출하 기준으로 대우하고 있음을 의미한다.

7.5 롤링 패키징과 월간 정식 버전의 분리

openRuyi 패키징 저장소의 이번 주 커밋 밀도는 최근 최고치이며(일일 최대 36건, KDE, 보안, 툴체인, 디바이스 네 축이 병행), 대외적으로 보이는 월간 버전은 여전히 2026.09에 머물러 있다. 두 가지는 모순되지 않는다: 롤링 패키징과 월간 정식 버전은 원래 두 개의 축이고, 일일 업데이트는 엔지니어링이 움직이고 있음을 보여주며, 버전 부재는 릴리스 프로세스나 검증 주기가 막혀 있음을 보여준다.

주목할 점은 이번 주에 추가된 두 개의 거버넌스 저장소다: release 규범 저장소는 요구 사항 번호와 우선순위를 프로세스로 문서화하고, ruyi-deck은 “저장소와 릴리스의 운영 콘솔”로 자리매김한다. 둘 다 코드를 생산하지 않지만 가리키는 것은 같은 공백이다—하나의 월간 버전을 내려면 패키징 저장소, 이미지, 펌웨어 등 여러 저장소를 넘나들어야 하며, 부족한 것은 커밋이 아니라 커밋을 하나의 릴리스 가능한 버전으로 수렴시키는 그 공정이다.

7.6 “설치 가능 여부”가 처음으로 계산 가능한 사실이 되다

ruyi 0.54.0은 ELF ABI 호환성을 삼상 판정(호환, 비호환, 미판정)으로 만들고, list, install, admin check-abi 세 곳에서 노출한다. 이 일의 의의는 기능 자체가 아니라 “이 패키지가 내 머신에서 실행될 수 있는가”를 경험적 판단에서 조회 가능하고, 비교 가능하며, 문제 진단이 가능한 데이터로 바꾼 데 있다.

RISC-V에 특히 중요하다: 동일한 사전 컴파일 바이너리가 서로 다른 확장 조합, 서로 다른 부동소수점 ABI의 호스트에서 다르게 동작하며, 과거에는 시도에 의존할 수밖에 없었다. 삼상 설계는 “미판정”이라는 단계도 남겨, 미지를 비호환으로 간주하지 않도록 한다—이 구분이 도구가 실제 환경에서 사용 가능한지를 결정한다. 다음으로 관찰할 것은 sidecar의 커버리지다: 어떤 패키지에 ABI 정보가 보강되었고, 어떤 패키지가 여전히 “정보 없음”인지. 080호에서 언급한 packages-index가 일부 패키지에 ABI 호환 정보를 보강한 것은 이 축의 연장이다.
