1.1 USB device 호스트 제어 가능 길이 2건 동시 병합: 문자열 디스크립터 인덱스와 MS OS 호환 ID (11-02)

날짜: 2026-11-02 11:47 (병합 시간)　출처: 제안 #11545, 제안 #11546, 결함 #4782, 결함 #11287

같은 작성자, 같은 시간대에 병합된 2건으로, 모두 USB device 프로토콜 스택에서 “길이와 인덱스가 호스트로부터 오는” 오래된 문제를 수정한 것이다.

#11545는 문자열 디스크립터 인덱스를 처리한다 (39줄 추가, 15줄 삭제). 기존 구현은 문자열을 가져오기 전에 호스트가 준 인덱스를 검증하지 않고 바로 인덱스로 문자열 테이블을 읽었으며, 범위를 벗어나면 인접한 인터페이스 문자열 포인터를 읽게 되고, 미등록 시 null 포인터 역참조 가능성도 있었다. 수정 방법은 두 가지다: 테이블 읽기 전에 인덱스 경계를 판단하고, 알 수 없거나 미등록된 인덱스는 EP0가 STALL을 반환하도록 한다; Microsoft OS 호환 ID 디스크립터가 등록된 경우에만 OS 문자열을 반환한다. 해당 결함 #4782는 2021년 6월 10일에 개설되어 4년 넘게 방치되었다.

#11546 MS OS 호환 ID 응답의 길이 처리 (4줄 추가, 1줄 삭제). 호스트는 해당 디스크립터를 가져올 때 임의의 wLength를 줄 수 있으며, 기존 구현은 wLength에 따라 EP0 전송을 구성했기 때문에 이미 구성된 디스크립터 버퍼 밖의 내용을 전송할 수 있었다. 수정 방식은 응답 길이를 실제 구성된 디스크립터 크기로 클램프하는 것이며, 할당과 캐시 동작은 건드리지 않는다. 대응 결함 #11287은 2026년 3월 23일에 개설되었다.

두 제안 모두 2026년 7월 1일에 개설되어 같은 날 머지 큐에 들어갔다. 작성자는 제안에서 검증을 git diff --check와 줄바꿈 검사만 수행했고 빌드와 USB device utest는 실행하지 않았다고 솔직히 명시했는데, 이유는 당시 사용하던 Windows 머신에 scons, C 컴파일러, 임베디드 크로스 툴체인이 없었기 때문이다. 이 점은 기록해 둘 만하다. 두 변경 모두 크지 않지만 USB 디스크립터 경로에는 자동화 테스트 커버리지가 없어, 머지 시점의 신뢰는 주로 코드 리뷰에서 나왔다.

1.2 SDHCI 호스트 초기화의 32바이트 이름 버퍼, RT_NAME_MAX를 64로 올리면 스택 침범 (11-02)

날짜: 2026-11-02 11:24 (머지 시간)　출처: 제안 #11542

6줄 추가, 4줄 삭제, SDHCI 드라이버의 dev_sdhci.c에 해당. 장애 증상은 qemu-virt64-aarch64에서 SDHCI를 켜고 RT_NAME_MAX를 64로 설정하면 부팅 과정에서 바로 data abort가 발생하고 fault addr 0x228이 나오는 것이다.

근본 원인은 지역 버퍼가 32바이트로 고정된 것: char dev_name[32]인데, sdio_host_set_name()은 커널 객체 명명 규칙에 따라 최대 RT_NAME_MAX개의 문자를 쓴다. 이름이 32바이트를 채운 뒤 다음 두 줄 rt_sprintf(&dev_name[len], "-timer")와 -data-timer가 계속 뒤에 쓰면서 스택으로 넘친다. 이름 길이가 32를 넘는 순간 범위 초과는 「가능성」에서 「필연」이 된다.

수정 방식은 버퍼를 char dev_name[RT_NAME_MAX]로 바꾸고, sdio_host_set_name()이 반환된 후 dev_name[sizeof(dev_name) - 1] = '\0'를 한 번 보강한 뒤 길이를 다시 계산하며, 두 곳의 접미사 결합을 rt_sprintf에서 남은 길이 인자를 받는 rt_snprintf로 교체하는 것이다. 이렇게 하면 RT_NAME_MAX가 64나 128로 설정되어도 이름과 접미사의 총 길이는 버퍼 자체가 감당한다.

같은 형태의 문제는 RT-Thread에서 드물지 않다. 커널은 RT_NAME_MAX 설정을 허용하지만 드라이버에서 작은 버퍼를 고정한 곳이 적지 않다. 이 변경은 경진대회 출품작의 보드가 QEMU에서 SD 카드 초기화까지 진행하다 드러난 것으로, RT_NAME_MAX 비기본값 조합이 평소에는 테스트되지 않는다는 것을 보여준다.

1.3 klibc의 바이트 루프가 GCC에 의해 memset으로 인식되어, libc 없는 타깃에서 링크 실패 (11-02)

날짜: 2026-11-02 18:08 (머지 시간)　출처: 제안 #11965, 결함 #6128

13줄 추가, 1줄 삭제, src/klibc/SConscript만 수정하며 C 소스는 건드리지 않는다.

kstring.c의 rt_memset(), rt_memcpy(), rt_memmove()는 모두 바이트 단위 루프로 마무리된다. GCC는 -O2와 -Os에서 -ftree-loop-distribute-patterns를 켜는데, 이런 루프를 표준 라이브러리 호출로 인식해 memset, memcpy에 대한 참조로 바꿔 쓴다. 타깃 플랫폼에 C 라이브러리가 없으면 이 두 심볼이 존재하지 않아 펌웨어가 링크 단계에서 실패하며, undefined reference가 잔뜩 나와 문자열 구현과 관련이 있다는 것을 알 수 없다.

작성자는 arm-none-eabi-gcc 10.3.1로 QEMU의 vexpress-a9 보드 프로젝트에서 -Os로 재현했다. 수정 전 klibc의 kstring.o에 U memset이 나타났고 두 곳의 bl 0 <memset>이 rt_memset() 자체 내부에 위치했다. 즉 커널 자신의 memset이 존재하지 않는 memset을 호출한 것이다. 결함 #6128은 2022년 6월 30일에 개설되었으며, 최초 보고는 aarch64-gcc에서 rt_memset 컴파일 문제만 언급했다.

수정 방식은 Libc 그룹에 -fno-tree-loop-distribute-patterns를 추가하되 CROSS_TOOL == 'gcc'일 때만 추가하여 Keil과 IAR 빌드에는 영향을 주지 않는 것이다. 대가는 이 루프들이 더 이상 벡터화되거나 접히지 않는다는 것이지만, klibc의 이 함수들은 원래 핫 패스에 있지 않다. 이 경험은 베어메탈 포팅을 하는 팀에 보편적이다. 자체 구현 문자열 함수와 컴파일러 최적화 옵션 사이에는 암묵적 계약이 있으며, 툴체인 업그레이드 시 가장 쉽게 깨진다.

1.4 tiny vsnprintf가 long long을 long으로 처리해 INT64_MAX가 -1로 출력됨 (11-02)

날짜: 2026-11-02 16:25 (병합 시간)　출처: 제안 #11600

20줄 추가, 3줄 삭제, rt_vsnprintf_tiny.c와 해당 테스트를 수정했다. tiny 버전은 공간 절약을 위해 %lld와 %lli의 ll 한정자를 long 경로 처리에 병합했고, 그 결과 64비트 정수가 32비트로 잘리고 부호 판별도 어긋났다. 가장 직관적인 현상은 INT64_MAX가 -1로 출력되는 것이다.

수정 방식은 내부의 L(ll을 나타냄)과 l 두 부호 있는 분기를 분리하는 것이다. ll은 long long으로 인자를 받고 64비트 범위로 부호를 판별하며, l은 long 경로를 유지한다. 동시에 rt_sprintf의 경계값 회귀 테스트 케이스를 보강해 INT32_MIN, UINT32_MAX, INT64_MIN, INT64_MAX 네 값을 커버했다.

검증 구성은 qemu-vexpress-a9에 tiny 버전의 long long 지원 옵션(VSNPRINTF_LONGLONG, 표준 vsnprintf 미활성)을 사용했다. 제안은 2026년 7월 9일에 열려 대기열에서 거의 넉 달을 머물렀다. tiny 버전은 자원 제약이 큰 많은 프로젝트의 기본 선택이며, 이런 조용한 잘림은 로그 출력이나 타임스탬프 포매팅 시 발견하기 어렵다.

1.5 SCMI 리셋 컨트롤러가 잘못된 컨테이너를 참조, 드라이버 등록 순서도 서브시스템 초기화로 변경 (11-02)

날짜: 2026-11-02 18:20 (병합 시간)　출처: 제안 #11946

22줄 추가, 7줄 삭제, reset-scmi.c와 pm-domain-scmi.c 두 파일을 수정했으며, 이 모니터링 기간의 마지막 푸시다.

리셋 측 문제는 컨테이너 변환에서 잘못된 객체를 사용한 것이다. scmi_reset_reset(), assert(), deassert()와 디바이스 트리 파싱 함수 모두 raw_to_scmi_reset(rstc)로 작성되어, rt_reset_control 포인터를 SCMI 리셋 컨트롤러로 간주해 역추적했다. 올바른 방법은 rstc->rstcer를 통해 먼저 리셋 컨트롤러를 얻은 뒤 변환하는 것이다. 잘못된 포인터를 전달한 결과는 크래시가 아니라 어긋난 필드를 읽는 것이며, 증상은 메모리 레이아웃에 따라 달라진다. 그래서 이런 오류는 특정 보드에서 「리셋이 동작하지 않음」이 나타나야 발견되는 경우가 많다.

등록 측의 두 드라이버는 원래 RT_SCMI_DRIVER_EXPORT를 사용했으나, 명시적 등록 함수와 INIT_SUBSYS_EXPORT로 변경되었다. 두 익스포트 매크로의 차이는 등록 시점이다. 드라이버는 리셋과 전원 도메인 인프라가 준비된 후에 등록되어야 하며, 그렇지 않으면 소비자가 먼저 probe할 때 프로바이더를 얻지 못한다. 제안 설명에는 디바이스 트리에서 파싱한 reset domain ID로 속성을 조회하는 것과, 리셋 컨트롤러 인스턴스에 SCMI 디바이스 참조를 유지해 컨트롤러 수명이 디바이스보다 짧아지는 것을 방지하는 내용도 언급되어 있다.

2.1 그래픽 디바이스의 음수 오프셋: pread와 pwrite가 위치 검증을 우회하여 커널 임의 읽기/쓰기에 도달 (11-02)

2.2 pipe 패치는 당일 도착, 드라이버 측에서 명령별 자체 방어로 수정 (11-02)

날짜: 2026-11-02 15:23 (제안 시간)　출처: 제안 #11971, 결함 #11958

지난 호에서 보도한 pipe FIONREAD 결함에 대한 패치가 도착했다. 22줄 추가, 4줄 삭제이며, pipe_fops_ioctl이 있는 파일만 수정한다.

수정 방식은 링 버퍼의 데이터 길이 또는 잔여 공간을 먼저 스택의 int에 계산한 뒤, MMU 빌드에서는 lwp_put_to_user()로 사용자 주소에 복사해 돌려주고, 비MMU 빌드에서는 직접 쓰기를 유지하는 것이다. 단일 주소 공간에서는 격리라는 것이 없으므로 이 계층을 더하는 것이 오히려 호환성을 깨뜨린다. 덧붙여 pipe와 pipe->fifo의 널 검사를 보강하고, lwp_user_mm.h의 include를 ARCH_MM_MMU로 감쌌다.

제안에는 왜 sys_ioctl()에서 일괄 차단하지 않는지에 대한 설명이 있다. ioctl의 의미는 드라이버마다 다르며, 어떤 것은 스칼라 arg이고 어떤 것은 구조체 포인터이므로 전역 검증은 오탐을 내기 쉽고, 명령별로 드라이버 측에서 자체 방어하는 것이 더 적절하다는 것이다. 이 선택은 기록할 만하다. 지난 호에서는 pipe, 블록 디바이스, 터미널 세 곳을 같은 원인으로 묶었지만, 통합 진입점이 유일한 해법은 아니며, 대가는 각 드라이버가 스스로 해야 한다는 점을 기억해야 한다는 것이다.

5. 산업 응용

5.1 산업용 게이트웨이 오픈소스: FreeModbus 마스터, LVGL 패널, 4G 클라우드 연동과 HTTP OTA를 하나의 이미지로 통합 (11-02)

날짜: 2026-11-02 13:59 (저장소 생성)　출처: 저장소: rtthread-industrial-gateway

새로 만들어진 개인 프로젝트로, 산업용 데이터 게이트웨이의 네 가지 경로를 동일한 STM32F407VGT6 위에 구현했다: 하향은 FreeModbus로 RTU 마스터 역할을 하며 현장 슬레이브의 홀딩 레지스터를 주기적으로 폴링하고; 로컬은 LVGL 8.3으로 HMI를 구성하며 버튼 제어와 되읽기가 하나의 홀딩 레지스터 미러 테이블을 공유하고; 상향은 ML307 4G 모듈을 통해 MQTT QoS1로 ThingsBoard에 연결하며 RPC 역방향 제어를 지원하고; 원격 업그레이드는 HTTP 청크 다운로드와 CRC32 검증을 사용하며 download 파티션에 기록한 후 rtboot가 app 파티션으로 옮기고 다시 점프한다.

하드웨어 구성은 대부분의 동종 저장소보다 상세하게 기술되어 있다: FSMC 8080 병렬 16비트 TFT, xpt2046 저항식 스크린은 SPI 연결, W25Q128(16 MB)은 SPI1에 연결되고 칩 셀렉트는 PG15 소프트웨어 제어, ML307은 uart6으로 AT 명령 사용, Modbus 슬레이브는 uart3의 9600 8N1에 연결. 프로젝트는 9개 단계로 점진적으로 구성되며, 마지막 단계에서 네 가지 경로를 동일한 이미지에 통합한다.

이 조합의 의의는 「전체 경로가 보드 단에 있다」는 점이다: 많은 게이트웨이 프로젝트가 클라우드 연결을 외장 모듈이나 두 번째 MCU에 맡기지만, 이 프로젝트는 4G, 프로토콜 변환, HMI, OTA를 하나의 M4F에 압축했으며, 그 대가는 192 KB SRAM이 LVGL 버퍼, Modbus 프레임, MQTT 세션을 동시에 수용해야 한다는 것이다. 산업용 게이트웨이 선정을 하는 팀에게 이 저장소의 디렉터리 구조와 파티션 분할은 완성품보다 참고 가치가 크다.

5.2 Sifli SF32LB52 스마트워치 펌웨어, RT-Thread를 웨어러블 기반에 올리다 (11-02)

날짜: 2026-11-02 18:03(푸시 시간)　출처: 저장소: helios-sf32

OpenSifli SDK 기반의 스마트워치 펌웨어로, 대상 보드는 Sifli SF32LB52 개발 보드의 LCD 화면이며, UI는 LVGL, 기반은 RT-Thread이다. 저장소는 9월 4일에 생성되었고, 모니터링 기간 내에 한 번 푸시되었으며, 현재 5스타 1포크이다.

웨어러블은 RT-Thread가 상대적으로 드물게 진출한 영역이다. 이러한 제품의 제약은 산업용 보드와 반대다. 화면 갱신이 유려해야 하고, 대기 전력 소모가 낮아야 하며, UI 리소스가 핫 업데이트 가능해야 한다. RT-Thread의 이 영역에서의 강점은 컴포넌트 축소 가능성과 LVGL과의 성숙한 바인딩이다. OpenSifli SDK는 RT-Thread를 기본 RTOS로 채택하여, Sifli의 이 제품 라인이 SDK 계층에서 이미 기반을 선택했음을 보여주며, 서드파티 펌웨어 프로젝트가 이를 그대로 계승할 수 있다.

6. 이번 기간 동향과 요약

6.1 동향: 하루 여섯 건의 병합이 모두 오래된 안건, 보안 큐는 유지관리자가 인계 시작

이번 모니터링 24시간 동안 메인 저장소에 6건이 병합되었으며, 모두 11월 2일 11:24부터 18:20 사이에 이루어졌다. 수량은 많지 않지만 구조는 매우 집중되어 있다. 네 건의 제안은 모두 2026년 7월 1일에 열렸으며(#11542, #11545, #11546은 당일 제출, #11600은 7월 9일), 한 건은 2022년 6월의 결함 #6128에, 한 건은 2021년 6월의 결함 #4782에 대응한다. 즉, 이날은 신규 작업이 아니라 적체된 안건을 정리한 것이다.

첫 번째 흐름은 ‘구성 조합 하의 숨은 결함’이다. #11542의 SDHCI 스택 오버플로는 RT_NAME_MAX를 64로 설정해야 발생하고, #11600의 long long 절단은 tiny vsnprintf를 활성화해야 나타나며, #11965의 링크 실패는 대상 플랫폼에 C 라이브러리가 없어야 노출된다. 세 가지의 공통점은 기본 구성에서는 검출되지 않는다는 것이며, 바로 이러한 비기본 조합이 실제 프로젝트에서 가장 흔하다는 것이다. 칩을 바꾸거나, 툴체인을 바꾸거나, Flash를 조금 절약하면 바로 마주치게 된다.

두 번째 흐름은 RT-Smart와 디바이스 경계의 정리가 두 번째 단계로 진입한 것이다. 지난 기간의 판단은 ‘보고는 많고 패치는 적다’였으나, 이번 기간의 변화는 패치가 따라붙기 시작했고 응답이 빨라졌다는 것이다. 그래픽 디바이스 음수 오프셋은 보고에서 제안까지 31분(#11969에서 #11970), pipe의 패치는 당일 도착했으며(#11971은 지난 기간의 #11958에 대응), 유지관리자 본인이 getaddrinfo와 GPT 두 건의 오래된 제안을 재작성했다(#11977, #11978). 큐에는 여전히 다섯 건이 심사 중이지만, 각 건에 재현 단계가 있어 리뷰 비용은 이미 낮아졌다.

세 번째 흐름은 버전 거버넌스가 ‘계획’에서 ‘증거’로 이동한 것이다. #11955는 X/Y/Z의 주기와 책임을 문서로 작성했고, #11972는 Z 버전 릴리스 가능 여부를 QEMU 가상 디바이스와 utest의 프레임워크별 목록으로 분해했으며, adc와 dac의 시뮬레이션 디바이스 테스트까지 제안에 포함했다. 이 두 가지는 모두 커널을 변경하지 않지만, 이후 모든 Z 버전 릴리스 시의 판단 근거를 결정한다. 지난 기간에 ‘수작업으로 정리하던 부분을 검사 가능한 프로세스로 바꾼다’고 했는데, 이번 기간에는 목록이 구체화된 것을 보게 된다.

생태계 측의 움직임은 더 직접적이다. HPMicro가 13분 만에 12개 BSP 저장소를 v1.13.0으로 푸시하고 HPM5100EVK를 새로 열었으며, 이는 원제조사 측의 BSP 유지관리가 이미 스크립트화되었음을 보여준다. 커뮤니티 측에서는 Modbus, LVGL, 4G, OTA를 모두 하나의 M4F에 올린 산업용 게이트웨이 프로젝트가 등장했다. 한쪽은 제조사가 보드 간 일관성을 보장하고, 다른 쪽은 개발자가 컴포넌트를 극한까지 조합하는 것으로, 이 양 끝이 바로 RT-Thread의 현재 가장 실질적인 생태계 모습이다.

HPMicro 12개 저장소의 버전 번호는 HTML과 Atom 커밋 제출을 교차 검증했으며, 그중 세 곳은 커밋 메시지가 v1.13.0임을 확인했고, 나머지 아홉 곳은 동일한 타임스탬프 구간을 근거로 동일 배치 릴리스로 판정했으며 저장소별 커밋 본문은 가져오지 않았다. 지난 기간 심사 대기 큐에 포함된 #11897(K230D), #11892(RISC-V Smart MMU), #11944(RTL8125), #11943(RK3588 디스플레이 오디오), #11959(NXP RT1180 링커 스크립트)는 이번 기간에도 큐에 남아 있으며 병합되지 않아 항목으로 중복 기재하지 않는다. #11954와 #11958은 지난 기간에 이미 보고되었으므로, 이번 기간에는 업데이트와 패치 진행 상황만 기록한다.
