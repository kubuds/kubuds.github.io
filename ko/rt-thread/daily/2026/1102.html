1. 커널 및 버전 동향

1.1 clang-format을 22.1.8로 고정, src/ 아래 73개 커널 소스 파일 일괄 재정렬(10-30)

날짜: 2026-10-30 18:20(병합 시간)　출처: 제안 #11936

75개 파일, 3852줄 추가, 3023줄 삭제, 작성자 CYFS3, 이전 #11653 및 이미 병합된 #11859와 연관. 문제는 형식 자체가 아님: 형식 검사 CI는 pip로 clang-format을 설치하고, 수동 포맷 워크플로는 apt로 설치하는데, 두 곳 모두 버전이 고정되지 않아 동일한 코드가 다른 시점에 다른 결과를 낼 수 있어 형식 검사가 재현 불가능함.

변경은 세 개의 독립 커밋으로 분리됨. 첫째, tools/ci/requirements-format.txt 추가하여 버전을 22.1.8로 고정, 두 워크플로 모두 해당 파일에서 설치하도록 변경, 수동 워크플로에 actions/setup-python 추가하여 Python 환경 제공; 둘째, .clang-format에서 AllowShortLoopsOnASingleLine 활성화, BraceWrapping.BeforeWhile 비활성화, 빈 루프는 한 줄 유지, do-while은 통일하여 } while (...)로 작성; 셋째, 동일 버전으로 src/ 아래 73개 C 및 헤더 파일 재귀 포맷, klibc, utest, perf, smp 하위 디렉토리 포함, 69개 변경 발생, 4개는 이미 규정 준수. 중영문 코딩 규범에 설치, 버전 확인, 에디터 설정 세 절 동시 보충.

Kconfig, SConscript 및 기타 디렉토리는 이번 범위에 포함되지 않아, 이는 디렉토리별로 진행하는 형식 수렴이지 전체 저장소 재정렬이 아님을 보여줌.

1.2 dlmodule, 2022년 보고된 #5705 해결(10-30)

날짜: 2026-10-30 10:54 (머지 시간)　출처: 제안 #11915, 결함 #5705

2개 파일, 215줄 추가, 45줄 삭제, 변경 사항은 dlelf.c와 dlelf.h에 위치한다. 수정 대상은 2022년 3월에 보고되어 4년 넘게 열려 있던 결함 #5705이다: 동적 모듈에서 초기화되지 않은 전역 변수에 접근할 때 주소가 겹치거나 재배치가 불가능한 문제이다. 작성자는 최신 master에서 재현한 후 근본 원인을 네 가지로 분류했다.

첫째, BSS 세그먼트(SHT_NOBITS) 로드 후 할당 포인터가 전진하지 않아 여러 NOBITS 세그먼트가 같은 메모리 블록에 겹치게 된다. 둘째, 기존 구현은 세그먼트 이름 기준으로 rodata, bss, data 세 가지 유형의 베이스 주소를 공유하여 기호가 속한 세그먼트의 실제 로드 주소로 재배치 주소를 계산하지 않았고, 다중 세그먼트 시나리오에서 잘못된 위치를 가리키게 된다. 셋째, SHN_COMMON 기호(tentative 정의된 초기화되지 않은 전역 변수)의 재배치가 조용히 건너뛰어진다 — 코드가 shdr[0xfff2]를 읽어 쓰레기 세그먼트 이름을 얻은 후 매칭되지 않는다. 넷째, 이 경로는 module->symtab을 구축하지 않아 dlsym()이 ET_REL 모듈에 대해 항상 실패한다.

수정 방법은 네 가지에 대응한다: BSS 세그먼트 로드 완료 후 할당 포인터 전진; rodata, bss, data 세그먼트 기호를 통일적으로 “세그먼트 로드 주소 더하기 세그먼트 내 오프셋”으로 계산; SHN_COMMON을 위해 별도로 공용 블록을 할당하고 크기 산정과 재배치가 동일한 정렬 알고리즘을 공유하며 해당 분기 처리를 세그먼트 이름 매칭 이전으로 앞당겨 범위 초과 읽기를 방지; .symtab에서 GLOBAL FUNC 기호를 수집하여 module->symtab을 구축하고 ET_DYN 경로가 .dynsym에서 구축하는 방식과 정렬.

검증은 qemu-vexpress-a9에서 완료되었으며, RT_USING_MODULE을 활성화하고 세 개의 테스트 모듈을 실행하여 ET_DYN 표준 흐름과 커널 기호 GOT 가져오기 두 경로를 커버했다. 영향 범위는 ET_REL 로드 경로를 사용하는 BSP이며, Cortex-M 시리즈에서 동적 모듈을 활성화한 프로젝트가 우선 영향을 받는다.

1.3 버전 관리 CI 및 릴리스 프로세스 계획 진입 (10-30)

날짜: 2026-10-30 16:04 (보고) / 15:29 (문서 제안)　출처: 결함 #11956, 제안 #11955

#11956은 kurisaW가 제안했으며, enhancement 태그가 붙고 본문에 “계획 중, 미구현”이라고 명시되어 있으며 마일스톤은 B01 정리 후 일정이 잡힐 예정이다. 핵심은 버전 전략을 실행 가능한 CI, 보고 및 릴리스 작업으로 전환하는 것이다: Z 버전은 매월 보고서와 릴리스 제안을 생성하고 수동으로 릴리스 여부를 결정; Y 버전은 3~6개월마다 하드웨어 검증 리뷰와 함께 릴리스; 외부적으로는 개발자에게 X 및 Y 베이스라인 사용을 우선 권장. 기존 GitHub Actions, QEMU BSP 및 테스트 프레임워크를 재사용하고 별도 시스템을 구축하지 않음을 강조한다.

같은 날 15:29에 제출된 #11955는配套 문서로, 메인라인 버전 번호 규칙과 릴리스 프로세스를 문서 디렉토리에 작성하며 아직 리뷰 중이다. 두 건 모두 아직 머지되지 않았지만 방향은 명확하다: 오랫동안 수동으로 정리하고 베이스라인이 쉽게 표류하는 단계를 검사 가능한 프로세스로 전환하는 것이다.

2. 보안 추적 및 머지 대기 큐

2.1 RT-Smart mailbox가 커널 객체 포인터를 검증하지 않아 위조 객체로 커널 메모리 읽기/쓰기 가능 (10-31)

날짜: 2026-10-31 14:26 (보고 시간)　출처: 결함 #11960

보고자 XueDugu, 확인 기준은 당일 master cbc19778. 문제는 mailbox 시스템 호출 진입점에 있다: 사용자가 전달한 커널 객체 포인터를 검증 없이 커널 mailbox API로 직접 전달하며, 해당 객체가 호출자 LWP에 속하는지, mailbox인지, 커널 메모리에 위치하는지 확인하지 않는다. 따라서 비특권 프로세스가 “위조 객체”를 구성하여 커널이 자체 규칙에 따라 읽기/쓰기하도록 할 수 있으며, 이는 임의 커널 읽기/쓰기 원시 연산과 동등한 효과를 가진다.

보고서는 타임라인을 상세히 기록했다: 결함은 커밋 ecf2d8215961 (2022-12-03, RT-Smart 시스템 호출 경계 조정)에 의해 도입되었으며, 최초 영향 버전은 v5.0.0이고 v5.3.0과 현재 master (5.4.0-dev)에도 여전히 존재한다. 검증은 두 계층으로 수행되었다 — QEMU의 qemu-virt64-aarch64 전체 시스템 실행 (virt, GICv2, 단일 코어, 128 MiB, RT_USING_SMART 및 RT_USING_MAILBOX 활성화)으로 사용자 공간에서 커널로의 범위 초과 경로를 입증; Raspberry Pi Pico 2 W (RP2350)에서 보드 레벨로 커널 mailbox API 원시 연산 자체를 검증했으며, 후자는 단일 주소 공간의 일반 RT-Thread를 실행하여 문제가 Smart의 격리 계층에만 국한되지 않음을 보여준다.

발행 시점까지 이 결함은 담당자 지정도, 대응하는 수정 제안도 없으며, 댓글에는 CI 로봇의 /claim 안내만 있다.

2.2 pipe의 FIONREAD가 사용자가 제공한 포인터에 직접 쓰기, 동형 결함 연속 세 번째 발생 (10-30)

날짜: 2026-10-30 19:13 (보고 시간)　출처: 결함 #11958

동일 보고자의 두 번째 건. pipe의 ioctl은 FIONREAD와 FIONWRITE 두 분기에서 직접 *((int *)args) = ...를 수행하여 링 버퍼의 데이터 길이나 남은 공간을 args가 가리키는 주소에 쓴다. RT-Smart의 sys_ioctl()은 원시 사용자 인자를 그대로 전달하며 copyout을 하지 않고, pipe 계층도 해당 주소가 사용자 주소인지 판별하지 않는다. 그 결과 일반 프로세스가 임의의 커널 주소를 지정하여 커널이 그곳에 4바이트를 쓰게 할 수 있으며, 기록되는 값은 pipe의 현재 상태에 의해 제약된다.

영향 범위는 v5.0.0부터 v5.3.0 및 master(5.4.0-dev)이며, 검증은 QEMU vexpress-a9, Cortex-A9, 32비트 RT-Smart, RT_USING_POSIX_PIPE 활성화, pipe 버퍼 512바이트 환경에서 완료되었다.

이는 동형 결함이 연속 세 번째로 나타난 것이다. 먼저 터미널 서브시스템의 ioctl이 FreeBSD의 copyin 전제를 누락한 사례(결함 #11937), 다음으로 블록 디바이스가 24바이트 파티션 테이블을 호출자가 지정한 커널 포인터에 기록한 사례(#11952), 이번 회차는 pipe(#11958)이다. 세 곳의 원인은 동일하다. fops 계층이 “인자는 이미 커널 주소”라는 오래된 가정을 그대로 따르고 있고, 사용자 공간 진입점이 변환 계층을 보충하지 않았다. 2.1의 mailbox 결함은 동일한 도입 커밋이 남긴 계열에 속하며, 다만 범위 초과 방식이 “안쪽으로 쓰기”에서 “사용자 포인터를 커널 객체로 취급”으로 바뀐 것일 뿐이다.

2.3 poll과 epoll의 카운트 곱셈 오버플로우 (10-30)

날짜: 2026-10-30 11:59 (제안 시간)　출처: 제안 #11954

파일 1개, 28행 추가, #11925의 전반부를 수정한다. sys_poll()은 사용자가 준 개수로 커널 버퍼 크기를 계산하는데, 32비트에서는 곱셈이 오버플로우되지만 이후에도 오버플로우되지 않은 원래 개수로 순회한다. nfds가 0x20000001이고 pollfd 구조체가 8바이트일 때 곱 0x1_00000008이 8로 잘리며, 접근 검증과 kmem_get 모두 8바이트로 통과하지만 poll()은 536,870,913개 항목을 순회하게 되어 do_pollfd()에서 pollfd->fd를 읽고 revents를 쓰는 모든 동작이 할당 블록 밖에서 이루어진다. 64비트 빌드는 영향을 받지 않으며, 곱이 64비트로 승격되어 초대형 할당은 곧바로 ENOMEM을 반환한다.

sys_epoll_pwait()는 동일한 형태이며, 카운트가 int이므로 음수 값도 함께 거부해야 한다. 수정 방법은 이 개수로 어떤 크기든 계산하기 전에 먼저 판정하는 것이다. nfds가 SIZE_MAX / sizeof(*fds)보다 크면 -EINVAL을 반환하고, epoll 측에는 카운트가 0보다 작은지에 대한 판정을 추가한다. 작성 방식은 sys_sendmsg, sys_recvmsg에서 msg_iovlen을 검증하는 것과 일관되게 유지한다.

같은 배치로 진행 중인 것에는 #11899(sys_sigaction의 시그널 번호 검증)와 #11895(시그널 전달 순서와 ELF 세그먼트 보호)가 있으며, 공통점은 사용자 공간에서 전달된 번호, 길이, 포인터를 커널 로직에 진입하기 전에 먼저 검사한다는 것이다.

2.4 RISC-V AIA: APLIC 레벨 인터럽트 EOI에서 setipnum 무조건 기록 (11-01)

날짜: 2026-11-01 20:40 (제안 시간)　출처: 제안 #11966

파일 8개, 1367행 추가, 10행 삭제. 현상은 QEMU 8.2.2에서 bsp/qemu-virt64-riscv, RV64, 4코어 SMP에 AIA(APLIC와 IMSIC) 구성으로 실행할 때, rt_thread_mdelay(1000)이 포함된 카운트 프로그램이 RISC-V test: 0만 출력하고 멈추며 지연 스레드가 다시 돌아오지 않는 것이다.

원인 파악 결과 APLIC 드라이버가 레벨 인터럽트의 EOI를 처리할 때 setipnum_le를 무조건 기록하는 것이었다. 구버전 QEMU는 디바이스가 이미 인터럽트를 철회한 뒤에도 이 기록으로 인해 새로운 MSI가 발생할 수 있어 지속적인 가짜 인터럽트가 형성되고, 이것이 시스템 타이머 처리를 억누르게 되어 지연 스레드가 복구되지 못한다. 수정 방법은 먼저 in_clrip에서 해당하는 유효 입력 상태(rectified input, 인터럽트 극성이 이미 반영됨)를 읽고, 디바이스가 여전히 인터럽트를 유효하게 유지하고 있을 때만 setipnum_le를 기록하는 것이다. 이렇게 하면 레벨 인터럽트의 재트리거 능력을 유지하면서도 이미 철회된 인터럽트에 추가 발사를 하지 않게 된다.

재현 프로그램도 함께 수정되었다. BSP의 main.c가 “Hello RISC-V 한 번 출력”에서 0부터 9까지의 카운트 루프로 바뀌고, 매 출력 후 1초씩 지연한다. 검증 환경은 QEMU 8.2.2, OpenSBI v1.3, riscv64-unknown-elf-gcc 13.2.0이며, AIA 활성화, 4코어, 네트워크와 NVMe와 virtio-console과 PCI 시리얼 비활성화의 세 가지 구성 모두에서 완전한 출력이 가능했다.

5.2 대회 과제 보드에서 생산 라인으로: 듀얼 Cortex-M7의 20 kHz 센서리스 FOC 및 엔코더 폐루프 위치 결정 (10-31)

날짜: 2026-10-30 ~ 2026-11-01 (저장소 생성 시간)　출처: 저장소: NS800RT7P65D FOC 및 CANopen

Naxinwei NS800RT7P65D는 듀얼 Cortex-M7 모터 제어 칩으로, 이 프로젝트는 이를 두 개의 논리 CPU로 분할한다: 하나는 20 kHz ADC 샘플링과 PWM을 실행하며 센서리스 FOC, 슬라이딩 모드 관측기 및 PLL 추정을 수행하고 하드웨어 셧다운을 갖춘다. 다른 하나는 UART와 FinSH, CANopenNode v4.1 및 CiA 402 브리징, CAN 송수신을 실행한다. 크로스 코어는 비동기 명령 메일박스와 6개 필드, 24바이트의 일관성 스냅샷만을 통과하며, 공유 메모리를 무작위로 읽지 않는다. 하부는 RT-Thread 5.3.1의 SMP 구성이다.

Infineon PSoC Edge E84의 EdgeDoctor-RT는 다른 경로를 취한다: 매 20밀리초마다 진동 데이터 블록 하나를 처리하고, 1초 슬라이딩 윈도우로 64차원 주파수 대역 특징을 추출하여 64-32-5 MLP에 전송해 정상, 베어링 내륜 고장, 베어링 외륜 고장, 정렬 불량, 불평형 다섯 가지 상태를 판정하고 신뢰도와 처리 제안을 제공한다. 베이스라인은 공식 Edgi_Talk_M55_XiaoZhi v1.4.0이며, 응용 계층만 중첩하고 부팅, 링킹, HAL 및 Wi-Fi 리소스는 변경하지 않는다.

두 운동 제어 작품은 대회 과제 보드의 침투 정도를 더 잘 보여준다: NXP FRDM-MCXA346에서 하나는 스테퍼 모터 폐루프 위치 결정을 수행하고, 엔코더 피드백에 Python과 Tkinter 상위 컴퓨터를 더해 10도 및 90도 위치 결정, 상대 역전 45도 및 소프트웨어 영점 복귀를 실행한다. 다른 하나는 초음파 장애물 회피 및 연기 감지를 수행하는 감지 카트로, 시각 인식은 PC 측에 배치된다.

플랫폼 분포도 기록해 둘 만하다: Titan Board Mini와 MC632X가 각각 두 장, PSoC Edge E84 한 장, NS800RT7P65D 한 장, FRDM-MCXA346 두 장으로, 대회 보드 목록에 있는 다섯 종을 커버한다.

6. 이번 기간 동향과 요약

6.1 동향: 머지 쪽은 조용하고 패치 쪽은 빽빽하며, RT-Smart의 경계가 체계적으로 정리되고 있다

이번 72시간 동안 메인 저장소에는 머지가 2건뿐이었다(10-30 10:54의 dlmodule 수정, 18:20의 clang-format 재정렬). 그러나 신규 제안은 11건, 신규 결함은 3건으로 모두 10-30부터 11-01 사이에 접수됐다. 주말 기간에 “머지는 적고 커밋은 많다”는 것은 일상적인 현상이며, 볼 만한 것은 수량이 아니라 착지점이다.

첫 번째 흐름은 엔지니어링 인프라다. clang-format 버전 고정이 해결하는 것은 동일한 코드가 서로 다른 머신에서 다른 포맷 결론을 내리는 문제이고, 버전 관리 CI와 릴리스 프로세스가 해결하는 것은 기준선 드리프트와 Z와 Y의 릴리스 경계 불명확 문제다. 두 가지 모두 커널 로직 한 줄도 바꾸지 않지만, 이후 모든 패치가 안정적으로 리뷰될 수 있는지를 결정한다. 지난 기간에 lwp의 1만 1천 줄 단일 파일을 20개 파일로 쪼갠 것도 같은 길을 걸은 것이다.

두 번째 흐름은 RT-Smart의 사용자 공간 경계다. 터미널 ioctl, 블록 디바이스 ioctl, pipe ioctl, mailbox 객체 포인터, 네 곳의 문제 형태가 동일하다: fops와 시스템 콜 계층이 “인자는 이미 커널 주소이고 객체는 이미 커널 객체”라는 오래된 가정을 그대로 따르고 있다. 보고자는 도입 커밋을 2022-12-03의 ecf2d8215961까지 추적했는데, 이는 새 코드가 도입한 회귀가 아니라 이 경계가 설정된 이래 체계적 검증을 한 번도 하지 않았음을 뜻한다. 진행 중인 패치들은 poll과 epoll의 카운트 랩어라운드, sigaction의 시그널 번호, ELF 세그먼트 보호와 정적 TLS를 커버하고 있어 방향은 맞지만, mailbox와 pipe 두 건은 아직 담당자가 없다.

세 번째 흐름은 생태계 측의 표현 방식이다. 공식 뉴스 인터페이스는 6월 17일에서 멈춘 지 여섯 달째에 접어들었고, 대외 발표는 미디어 칼럼이 맡고 있다; 커뮤니티 활성도는 분명히 “작품” 쪽으로 옮겨갔다—주말 하루에 대회 작품 7개가 GitHub에 오픈소스로 공개됐고, 다섯 개는 엣지 AI 비전과 진단에, 두 개는 모터와 모션 제어에 속한다. RT-Thread의 실사용에 관심 있는 사람에게는 이 저장소들이 공식 보도자료보다 보드 제조사와 개발자들이 그것으로 무엇을 하고 있는지를 더 잘 보여준다.

6.2 한계와 중복 제거 설명

포럼 club.rt-thread.org는 이번 기간에 WAF 챌린지 페이지가 앞단에 있어 작품 게시글 목록과 본문을 직접 읽을 수 없었다. 참가 작품 정보는 GitHub 저장소 자체 설명(README, 디렉터리 구조, 생성 시간)과 EE Times China 공식 칼럼을 교차 검증했으며, 포럼 원문과 게시글별로 대조하지는 않았다.

HN Algolia 기간 내 5건의 적중은 모두 thread의 어의 오매칭(Pulling on a Thread, HN Replies, 프랑스 다운로드세 등)이어서 전량 제외했다; Google News 영어 쪽은 적중 0건, 중국어 쪽 3건 중 2건을 수록했으며(우한 교육, 11-04 라이브), 11-01의 광군제 프로모션 기사는 수록하지 않았다. 지난 기간 심사 대기열에 올린 #11897(K230D), #11892(RISC-V Smart MMU), #11944(RTL8125), #11943(RK3588 디스플레이 오디오)는 이번 기간에도 대기열에 남아 있고 머지되지 않았으므로 중복 기사화하지 않는다.
