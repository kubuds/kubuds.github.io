1.2 CAN 리팩터링 번호 교체: #12054 종료 2분 후 #12090 이어받음 (11-26)

날짜: 2026-11-26 10:33 (종료) 및 10:35 (재제출).
출처: #12054.
#12090.

#12054는 10시 33분 종료, 머지되지 않음. 11월 14일 제출, 10건 커밋, 46개 파일, 8946줄 추가, 5521줄 삭제. 2분 후 동일 브랜치 refactor/can-framework가 #12090으로 재제출, 12건 커밋, 46개 파일, 8936줄 추가, 5549줄 삭제.

작성자 wdfk-prog가 #12090 첫 마디로 리베이스 비용 불만. master 브랜치 일부 BSP의 CAN 업데이트로 인한 병합 충돌로 리베이스 불가피. 메인테이너 Bernard Xiong이 「AI Agent 투입, AI가 감시하도록」이라 답하며 env pilot 언급. 이 답변은 기술적 결론을 바꾸지 않음.

리팩터링의 책임 경계가 이번 버전에서 명확해짐. Generic CAN은 하드웨어 리소스 관리, 동기화, ownership, terminal, lifecycle만 담당. 송신 캐시, 재시도, 스케줄링, 프로토콜 QoS는 상위 프로토콜 스택 또는 애플리케이션에 위임. 새 설계는 TX 소프트웨어 큐를 삭제하고 컨트롤러 하드웨어 메일박스를 유일한 큐잉 리소스로 직접 사용.

#12090의 CI는 30건, 27건 통과, 3건 스킵, 실패 없음.

판단: 번호 교체는 방안 교체 아님. 근거는 파일 수 동일, 추가 10줄 적고 삭제 28줄 많음, 동일 브랜치 재베이스.

1.3 메인테이너 #12090 초기 검토: 두 곳 논의 필요, 명확히 승인 불가 (11-27)

날짜: 2026-11-27 03:06 (리뷰).
출처: #12090.

Bernard Xiong은 head e2224ab에 대해 1차 검토 결론을 제시하고, 검토 범위가 불완전함을 명시했다. 검토한 범위에는 can_internal.h의 계약과 can_tx.c, can_rx.c 전문이 포함된다. 또한 dev_can.c의 open/close/control 수명 주기, 그리고 STM32 bxCAN의 sendmsg와 TX 인터럽트 핵심 경로도 포함된다. 나머지 30개 BSP 어댑터, dev_can.h의 전체 API 변경, Kconfig와 CI matrix, utest 케이스는 읽지 않았다.

첫 번째 논의 사항은 STM32 bxCAN에서 AutoBusOff를 비활성화한 것이다. drv_can.c 173~175행에서 ABOM을 ENABLE에서 DISABLE로 변경하고, 동시에 AutoRetransmission을 ENABLE로 변경했다. 제안 설명에는 이 동작 변경에 대한 언급이 없다. ABOM을 비활성화하면 컨트롤러가 bus-off에 진입해도 자동으로 복구되지 않는다. 이 상태에서 다시 RT_CAN_CMD_START를 호출하면 HAL 상태가 READY가 아니므로 -RT_ERROR를 반환한다. 사용자는 close 후 다시 open하여 DeInit과 configure를 거쳐야만 복구할 수 있다. 검토에서는 이것이 자동 bus-off 복구에 의존하는 필드버스 시나리오에 대해 가시적인 회귀라고 판단했다.

두 번째 논의 사항은 관리 작업 실패 후 데이터 경로가 닫힌 채로 유지된다는 점이다. _can_reconfigure()는 BSP 작업이 오류를 반환하면 곧바로 out_unlock으로 점프한다. 이때 TX admission은 이미 닫혔고 RX는 pause된 상태이며, SET_PRIV 파라미터 검증 외에는 롤백이 없다. SET_BAUD, SET_FILTER 또는 CONFIGURE가 하드웨어 원인으로 실패하면, 다시 START하거나 close/open하기 전까지 디바이스는 송수신할 수 없다. 검토에서는 두 가지 방안을 제시했다. 의도된 fail-closed라면 공용 API 문서에 명시하고, 그렇지 않다면 STOP이 아닌 명령에 대해 was_accepting과 RX admission을 복구해야 한다.

검토 말미에는 다음과 같이 명시했다. 실보드 검증이 없고, 46개 파일, 8,936행 추가는 대규모 리팩터링이므로, 다음 라운드에서 전체 검토를 마친 후 승인 여부를 결정할 것을 권고한다.

2. 리뷰 진행: 두 건 수렴, 한 건 CI 대기

2.1 serial_v2 DMA 캐시 라인 정렬, 메인테이너 승인 획득 (11-27)

날짜: 2026-11-26 11:16 ~ 2026-11-27 03:03.
출처: #12084.
이슈 #12063.

이슈 #12063은 Cortex-M7에서 D-Cache를 켠 뒤 발생하는 오래된 문제를 다룬다. serial_v2의 DMA ping buffer는 RX FIFO 블록 내에 할당되어 시작 주소가 32바이트로 정렬되지 않는다. SCB_InvalidateDCache_by_Addr가 캐시 라인을 무효화할 때 앞뒤의 힙 블록까지 오염시킨다. TX 측에도 같은 위험이 존재한다.

제안은 ping buffer 시작 주소를 ringbuffer 이후 32바이트로 정렬한다. dma_ping_bufsz를 캐시 라인 정수 배로 올림하고, 총 할당 크기도 그에 맞게 조정한다. 작성자 liangzhan5는 hpmicro BSP에 있던 국소 수정도 함께 롤백했다. 1개 파일 변경, 9행 추가, 2행 삭제. 작성자는 실보드가 없어 정적 분석만 수행했다고 밝혔다.

Rbb666은 11시 16분에 두 곳의 인라인 의견을 제시했다. 첫 번째는 hpmicro 롤백에 관한 것이다. HPM6750의 캐시 라인은 64바이트이지만 프레임워크는 32바이트 정렬만 보장한다. BSP 정렬을 제거하면 비동기 DMA TX의 flush가 FIFO 헤더나 인접 힙 블록까지 함께 기록할 수 있다. 두 번째는 할당 조건에 관한 것이다. 전역 RT_SERIAL_USING_DMA만 보기 때문에 순수 인터럽트 수신 보드도 32바이트를 추가로 요청하게 된다.

작성자는 당일 밤 21시에 답변했다. TX 측 변경은 「실제로 보호해야 할 시나리오가 없다」는 이유로 취소했다. HPM의 BSP 정렬은 유지하고 해당 파일은 더 이상 건드리지 않는다.

11월 27일 3시 03분, Bernard Xiong이 head 156fbaf에서 승인했다. 검토에서는 변경이 RX ping buffer 정렬만 유지하고, TX 측 변경을 삭제하며, HPM의 BSP 정렬을 보존한 점이 올바른 방향이라고 확인했다. 구현 세부는 sizeof(struct rt_serial_rx_fifo) + rx_bufsz로 오프셋을 계산한다. 할당 시 RT_ALIGN(dma_ping_bufsz, RT_CPU_CACHE_LINE_SZ)에 캐시 라인 하나를 더하고, 마지막에 시작 주소를 정렬한다.

판단: 이번 호에서 리뷰 전 과정을 마친 유일한 제안이다. 근거는 의견, 재작업, 승인의 세 단계가 24시간 내에 마무리되었고, 쟁점이 하나의 버퍼로 한정되었다는 점이다.

2.2 devtmpfs 범위 초과 쓰기, 충돌과 재현 보강, 7건 대기 후 CI에서만 통과 (11-27)

날짜: 2026-11-26 20:06 ~ 2026-11-27 03:03.
출처: #11842.

#11842은 devtmpfs의 스택 오버플로를 수정한 것입니다. _path_separate()와 _get_subdir()는 버퍼 길이를 받지 않아, 임의 길이의 경로 구성 요소를 호출자의 256바이트 스택 배열에 rt_memcpy로 복사합니다. dentry->pathname은 최대 4092바이트이며, 단일 구성 요소가 255바이트를 초과하면 오버플로가 발생하고, 경계를 넘는 범위가 약 3.8 KB에 달해 반환 주소를 덮어쓸 수 있습니다. 업스트림 tmpfs의 동명 함수에는 이미 parent_size, file_size, name_size 검증이 포함되어 있고 -ENAMETOOLONG을 반환하지만, devfs 쪽은 이 부분이 누락된 항목입니다.

20시 06분, 작성자 HANYAODONG이 두 가지를 보고했습니다. 충돌은 해결되었고, mergeable_state가 dirty에서 unstable로 바뀌었습니다. 충돌은 .github/utest/configs/components/dfs.cfg 한 곳뿐입니다. master의 #12067이 dfs utest의 옵션 이름을 변경했기에, 병합 시 master의 표기를 유지하고 자신의 설정은 뒤에 추가했습니다.

검증 공백도 보완했습니다. 작성자는 utest_auto_run의 원래 순서대로 bsp/qemu-vexpress-a9에서 로컬로 재현했습니다. dfs.cfg를 .config에 추가하고, scons –pyconfig-silent로 생성한 뒤, scons로 빌드했습니다. rtconfig.h에 RT_UTEST_TC_USING_DEVTMPFS_PATH가 나타났고, 빌드가 통과했으며, QEMU에서 세 개의 테스트 케이스가 모두 PASSED했습니다.

11월 27일 3시 03분, Bernard Xiong이 새 head ebbaae39를 재검토했습니다. 56382719와 비교해 origin/master와의 병합 커밋 하나만 추가되었고, PR 자체의 5개 파일에는 새로운 변경이 없습니다. 이전 557c58de에서의 정적 검토 결론은 여전히 유효합니다. 충돌은 해제되었고, unstable은 새 head의 workflow 승인 대기 때문일 뿐입니다.

메인테이너는 이어서 해당 head의 대기 중인 실행 7건을 승인했습니다. pkgs_test, ToolsCI, MemBrowse, 형식 검사, utest_auto_run, 정적 분석, BSP 정적 빌드가 포함됩니다. 결론은 여지를 남겼습니다. 현재로서는 utest_auto_run이 통과했는지 확인할 수 없으며, devtmpfs 테스트 케이스가 CI에서 실제 실행되어 PASSED된 뒤에 업데이트하겠다는 것입니다.

2.3 STM32 이더넷 ops와 SR8201F: 메인테이너가 빌드 감시를 요구 (11-26)

날짜: 2026-11-26 17:49 (리뷰).
출처: #11819.

#11819는 세 가지를 합니다. ADC 드라이버 기본 로그 레벨을 DBG_WARNING으로 낮추고, ETH 드라이버에 ops 계층 적응을 보완하며, SR8201F PHY 지원을 추가합니다. 커밋 4개, 파일 2개, 33줄 추가, 1줄 삭제입니다.

작성자 LQL2000은 당일 오전에 인라인 답변 세 건을 연달아 남겼습니다. Kconfig를 옵션 형식으로 바꿀 필요는 없으며, PHY_USING_SR8201F로 수동 변경하는 것이 이미 검증되었다고 했습니다. 답변에는 참고용 choice 작성 방식도 함께 첨부했습니다.

17시 49분, Rbb666의 답변은 한 가지 요구만 제시했습니다. SR8201F용 ci.attachconfig.yml 빌드 테스트 케이스를 추가할 것. 테스트 케이스는 BSP_USING_ETH와 RT_USING_DEVICE_OPS를 동시에 활성화해야 하며, 통과한 CI 링크를 첨부해야 합니다. 이유는 Apollo가 현재 PHY_USING_LAN8720A를 고정 선택하고 있기 때문입니다. Apollo를 감시 용도로 사용한다면, Kconfig가 생성한 설정이 실제로 SR8201F를 선택해야만 빌드가 이 브랜치로 진입합니다.

해당 제안의 현재 CI는 21개 항목으로, 17개 통과, 3개 건너뜀, 1개 실패입니다. 실패 항목은 정적 코드 분석입니다.

3.1 이종 데모 실행 불가: C907 측 응답 없음 (11-26)

날짜: 2026-11-26 11:13 (리뷰).
출처: #12078.

#12078은 E907 측 보드 지원과 최소 이종 데모입니다. 커밋 2개, 파일 77개, 8791줄 추가입니다. Rbb666의 요약은 한 문장뿐입니다. README대로 이 PR의 이미지 두 개를 플래시하면 이종 데모가 실행되지 않으며, 원인은 C907 측 응답이 없기 때문입니다.

구체적으로 applications/main.c 11번째 줄에서 C907은 출력 후 종료만 하고, AMP_SLOT_C907과 AMP_SLOT_C907_REPLY를 쓰지 않습니다. E907은 HETERO-FAIL까지 계속 대기합니다.

또 다른 지점은 e907의 main.c 92번째 줄입니다. 코드가 이전 MSGBOX 주소 0x03003010을 직접 읽는데, #12079에서 이 베이스 주소가 사용 불가로 표시되었습니다. 리뷰는 이 읽기를 삭제할 것을 요구했습니다. 이유는 DRAM 왕복이 이번 탐지에 의존하지 않으며, 매핑되지 않은 경우 메모리 접근 예외도 발생하기 때문입니다.

3.2 UART0 소유권과 예외 반환, 세 제안 모두 같은 문제 (11-26)

날짜: 2026-11-26 11:08 및 11:13 (리뷰).
출처: #12078.
#12079.

UART0 문제가 두 번 나타났다. C907이 시작될 때 E907이 사용 중인 UART0을 리셋하며, 양쪽의 FinSH가 모두 인터럽트 수신을 활성화하고 동일한 FIFO를 경쟁적으로 읽는다. 리뷰에서는 이기종 모드에 대해 유일한 UART0 초기화와 수신 측을 지정할 것을 요구했다. #12079 쪽은 더 직접적이다: e907의 main.c 83번째 줄에서 uart0을 다시 초기화하여 FIFO를 비우고 수신 인터럽트를 끄며, 중복 등록 자체도 실패한다.

예외 처리 문제도 두 번 나타났다. 두 제안의 board/trap.c 27번째 줄은 모두 동기 예외에서 직접 반환하여 원래 mepc를 복원하므로,故障 명령이 반복적으로 트리거된다. 리뷰에서는 양쪽에서 mcause와 mepc를 기록한 후 예외 처리로 진입할 것을 요구했다.

스택 크기는 세 번째硬 충돌이다. #12077의 Kconfig 24번째 줄은 SMP 인터럽트 진입이 구성에 따라 코어별 스택 상단을 계산하도록 하지만, 시작 어셈블리와 링크 스크립트는 고정된 8192를 사용한다. 구성 값을 늘리면 인터럽트 스택이 예약 영역을 넘어서므로, 리뷰에서는 스택 크기 출처를 통일할 것을 요구했다. E907의 Kconfig 21번째 줄은 다른 방향이다: menuconfig에서 여전히 SMP를 켤 수 있지만, E907에는 SMP 포팅이 포함되지 않았고 세컨더리 코어 시작 경로도 없다.

3.3 명명과 드라이버 공유: 두 제안이 동일 지점에서 재작업 요구됨 (11-26)

날짜: 2026-11-26 11:08 및 11:13 (리뷰).
출처: #12078.
#12079.

명명 문제는 두 곳을 지적한다. drv_rpmsg와 drv_openamp는 실제로 공유 메모리 ping/reply만 래핑하며, libmetal이나 virtio-rpmsg 풀 스택이 아니다. 리뷰에서는 실제 기능을 반영하는 이름, 예를 들어 drv_amp_mailbox와 drv_amp_endpoint로 변경하고 양쪽 참조와 README를 동기화할 것을 요구했다.

드라이버 공유 문제도 반복적으로 나타났다. 양쪽의 UART, FDT, MMC 드라이버 소스 코드가 완전히 동일하므로 Allwinner의 libraries/drivers/ 아래에 두고 두 BSP가 동일한 구현을 참조해야 한다. E907 측의 MMC 사본은 빌드에 전혀 참여하지 않는다.

#12079에는 두 가지 세부 사항이 더 있다. drv_openamp.c 189번째 줄은 도어벨을 먼저 읽어 E907이 보낸 OA_EVT_LINK를 읽어버리므로, 메인 측이 먼저 타임아웃될 수 있다. 리뷰에서는 링크 루프에서 오래된 토큰을 필터링할 것을 요구했다. e907의 main.c 146번째 줄은 응답 패킷 길이로 비교하는데, 잘린 응답 패킷도 접두사만 일치하면 검증을 통과할 수 있으므로, 송수신 길이가 일치하는지 먼저 검증할 것을 요구했다.

문서도 맞지 않는다. #12079의 main은 이미 OPENAMP-EPT-OK를 출력하도록 변경되었지만, README는 여전히 RPMSG-OK를 검증 기준으로 삼고 있다.

세 제안은 이번 호 모니터링 기간까지 여전히 open 상태이며, 작성자는 아직 이 의견들에 답변하지 않았다. CI 상태는 각각 #12078 30개 중 26개 통과 4개 건너뜀, #12079 동일하게 26개 통과 4개 건너뜀, #12077 28개 통과 2개 건너뛰며, 모두 실패 항목이 없다.

4. 공식 및 커뮤니티: 콘텐츠 측 침묵

4.1 공식 뉴스 인터페이스 5건 여전히 11-06 배치 (11-26)

날짜: 2026-11-26 (확인).
출처: 공식 뉴스 인터페이스.

인터페이스는 5건을 반환한다. 제목은 산업 지능화, PLC와 Vinaro 기술 살롱, 동남아 산학 융합, 자동차 소프트웨어 생태계 살롱, 공업 박람회 AI 카트를 다룬다. 첨부 이미지 업로드 디렉터리는 모두 20261106으로, 11월 6일 배치와 일치하며 모니터링 기간 내 신규 추가는 없다.

5건 본문에 해당하는 이벤트 시점은 9월에서 10월이다. elexcon 선전 국제 전자전은 9월 9일부터 11일, 린강 자동차 소프트웨어 연맹 제5차 기술 살롱은 9월 16일, 공업 박람회 AI 카트 Workshop은 10월 13일이다.

판단: 뉴스 측은 3주 연속 새 기사가 없다. 근거는 인터페이스 배치가 11-06에 멈춰 있고, 당일 gnews에 유효한 검색 결과가 없기 때문이다.

4.2 포럼 최신 글 11-23에서 멈춤, gnews 유효 검색 결과 없음 (11-26)

날짜: 2026-11-26 (확인).
출처: 커뮤니티 포럼.

포럼 글 목록의 최신 글은 11월 23일 19시 01분의 「개인용 AI로 작성한 임베디드 디버깅 어시스턴트 공유」이다. 나머지 네 편은 11-16부터 11-20에 분포한다: 적외선 프레임워크 리팩토링, WS2812B 패키지 리팩토링, Studio SDK Manager 분석, VSCode의 Studio 프로젝트 적응. 모니터링 기간 내 새 글은 없다.

Google News는 5개 쿼리로 진행했다: RT-Thread 3일, RT-Thread IoT 3일, Ruisaide 3일, Ruiqing 3일, RT-Thread 임베디드 3일. 유일한 검색 결과는 CSDN의 EMQX MQTT Broker 튜토리얼로, 11월 25일 게시되었으며 RT-Thread와 무관하다. 「Ruiqing」 그룹의 8건은 모두 자동차 구매 가이드 기사로, 제목 기준으로 제외했다.

5. 요약 및 동향 관찰

  • 병합 0건, 리뷰가 빈자리 채움: 메인라인은 24시간 동안 커밋이 0건으로, 최근 처음으로 하루 종일 병합이 없었다. 같은 날 제안 측에서는 15건의 인라인 의견과 대형 리팩터링 1건의 1차 검토가 나왔다.
  • CAN 리팩터링 2차 리뷰 진입: 번호를 바꿔 병합 충돌을 우회한 뒤, 메인테이너는 어댑터의 3분의 1만 읽고도 두 가지 의미론적 문제를 지적했으며, bus-off 복구 경로가 치명적 결함이다.
  • 두 건의 수렴 경로는 다름: serial DMA 정렬은 범위를 좁혀 승인을 받았고, devtmpfs는 충돌 보완과 로컬 재현으로 7개의 대기 중인 run을 확보했지만, 두 건 모두 아직 메인라인에 들어가지 않았다.
  • V861의 문제가 빌드에서 의미론으로 이동: 어제는 빌드 매트릭스와 PLIC 주소에서 막혔고, 오늘은 이기종 데모 미동작, UART0 경합, 예외 반복 발생으로 바뀌었으며, 이는 설계 계층에 속한다.
  • 네이밍과 코드 재사용이 통일 기준이 됨: 두 제안 모두 drv_rpmsg와 drv_openamp의 네이밍 및 양쪽 중복 드라이버를 함께 수정하도록 요구받았으며, 이는 메인테이너가 BSP 구조를 정리하고 있음을 보여주며 기능만 보는 것이 아니다.
  • 뉴스 측은 3주 연속 조용함: 공식 인터페이스는 11-06에 멈췄고, 포럼은 11-23에 멈췄으며, 당일 수집 가능한 외부 보도는 0건이다.
