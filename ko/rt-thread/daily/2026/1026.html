1. 커널 및 버전 동향

1.1 메인라인 72시간 동안 커밋 두 건뿐: lwIP 루프백 netdev 병합, clang-format 규칙 세분화 및 thread.c 예시 포함 (10-25)

날짜: 2026-10-23 17:09 및 2026-10-25 19:26 (병합 시각)　출처: PR #11859, PR #11893, 메인 저장소 커밋 기록

주말 사흘간의 모니터링 기간 동안 master에는 이 두 건의 커밋만 반영되었으며, 이는 지난 호의 “3일간 커밋 없음 후 집중 마무리” 판단과 이어지는 흐름이다. 병합 작업은 모두 비근무 시간대(금요일 17:09, 일요일 19:26)에 이루어졌고, 리뷰 자체는 멈추지 않았으나 개발 측의 신규 코드는 없었다.

첫 번째 항목은 clang-format 규칙 정리로, 2개 파일 +83/-77이며 .clang-format과 src/thread.c만 수정합니다. 브랜치 이름에 토론 단서인 style/clang-format-discussion-11653이 붙어 있고, 두 커밋 날짜는 모두 10-09이며, 본문은 ‘정렬, 중괄호 줄바꿈 및 공백 규칙’의 세분화이고, 두 번째 커밋은 src/thread.c를 새 규칙에 따라 전체 포맷팅한 예시로 사용합니다. 즉 이것은 2주 끌린 리뷰 마무리이지 새로운 작업이 아닙니다. 제안서에는 도구 관련 사실도 하나 기록되어 있습니다: index++ 같은 표기는 clang-format 18.1.8과 23.1.3에서 모두 그대로 유지되며, 강제로 바꾸도록 지정하는 설정 항목이 없고, 검증은 --dry-run --Werror를 사용합니다.

두 번째 항목은 lwIP 루프백 장치를 netdev 프레임워크에 편입하는 것으로, 3개 파일 +54/-0입니다. 이전에는 lwIP의 루프백 포트가 netdev로 등록되지 않아 두 가지 문제가 있었습니다: 127.0.0.1을 사용하는 툴체인이 실행되지 않았고; 물리 링크가 없는 네트워크 네임스페이스에는 기본 사용 가능한 인터페이스가 없었습니다. 변경 사항은 RT_LWIP_USING_LOOPBACK 설정 항목을 추가하고, lo／lo0을 netdev로 등록해 link up 상태로 설정하며, 인터페이스를 지정하지 않을 때 루프백을 기본 인터페이스로 선택하고, 동시에 RAW 수신 메일박스를 키워 루프백 에코를 수용합니다. 검증 설정은 qemu-virt64-riscv로 제시되었고, 제안서에는 “로컬에서 컴파일하지 않았으며, CI에서 빌드를 검증한다”고 명시되어 있습니다 — 이는 지난달 여러 제안서의 승인 기준과 일치합니다: 병합은 빌드 통과를 조건으로 하고, 보드 테스트는 별도로 후속 진행합니다.

버전 측면에서는 여전히 움직임이 없습니다: 최신 릴리스와 태그는 여전히 09-10의 v5.3.0이고, 10-17의 v5.4.0 버전 매크로는 지금까지 릴리스 노트, 바이너리 또는 프리릴리스 태그가 구성되지 않았습니다.

1.2 qemu-virt64에서 RT-Thread Smart 활성화: riscv64 SMP 비활성화, ext4와 elm 블록 장치 마운트, ptyfs와 procfs 마운트 (10-25)

날짜: 2026-10-25 19:50 (최종 업데이트)　출처: PR #11896

이 제안서는 14개 파일 +1263/-1075로, qemu-virt64-riscv와 qemu-virt64-aarch64 두 BSP의 RT_USING_SMART를 활성화합니다. 이전에 이 두 virt 플랫폼은 명목상 Smart를 지원했지만, virtio 블록 장치에 표준 루트 파일 시스템 초기화 흐름이 없었고 pty에도 마운트 지점이 없어 QEMU에서 많은 기능을 테스트할 수 없었습니다.

변경 사항은 네 부분으로 나눌 수 있습니다: riscv64 측에서 SMP를 비활성화하여 Smart의 단일 코어 설정과 맞춤; virtio-blk0에 ext4 또는 elm을 마운트하는 초기화 흐름 추가; ptyfs를 /dev/pts에, procfs를 /proc에 마운트; .config와 rtconfig.h 재생성. 빌드 검증은 riscv64에 RISC-V musl 범용 툴체인, aarch64에 aarch64 musl 툴체인을 사용한다고 명시되어 있으며, 로컬에서는 실행하지 않고 CI에서 검증합니다.

주목할 점은 의존 관계입니다: 이 제안서는 방금 병합된 #11893(RT_LWIP_USING_LOOPBACK 설정 심볼)에 명시적으로 의존하며, .config는 #11893 위에서 생성되었고, 작성자는 의존 항목이 병합된 후 rebase하고 설정을 재생성하겠다고 설명합니다. 이러한 제안서 간 설정 결합은 qemu 플랫폼 개조에서 흔하며, 루프백 포트가 Smart 활성화보다 먼저 적용되어야 하는 이유도 설명합니다 — 루프백이 없으면 Smart에서 로컬 주소에 의존하는 많은 테스트가 실행되지 않습니다.

1.3 lwp_syscall.c 1만 1천 줄 분할: 165개 시스템 콜 진입점을 하위 시스템별 파일로 분리, 동작 불변 (10-25)

날짜: 2026-10-25 19:50 (최종 업데이트)　출처: PR #11894

components/lwp/lwp_syscall.c 단일 파일이 1만 1천 줄을 넘어, 메모리, 파일 시스템, socket, 프로세스, IPC, 시간 여섯 가지 시스템 콜을 한데 모아 리뷰와 검색이 매우 어려웠습니다. 제안서는 이를 components/lwp/syscall/ 디렉터리로 분할하고, 하위 시스템별 파일로 나누며, 공유 시스템 콜 디스패치 테이블과 내부 헤더 파일을 추가하고, LWP 빌드 스크립트에 새 디렉터리를 등록합니다.

규모 면에서 이는 이번 모니터링 기간 최대 항목입니다: 22개 파일 +12223/-11638로 거의 전부 이동과 이름 변경입니다. 제안서는 “기계적 리팩터링, 기능 변경 없음”이라고 자평하며, 165개 시스템 콜 진입점과 동작이 완전히 변하지 않음을 강조합니다. 검증 역시 “로컬에서 컴파일하지 않았으며, CI에서 검증”이고 설정은 CONFIG_RT_USING_SMART=y입니다.

공학적 관점에서 이런 분할 자체는 새로운 능력을 낳지 않지만, 이후 lwp 결함(예: 이번 호 2.2의 sys_poll 랩어라운드)을 읽기 쉬운 파일에서 찾을 수 있는지를 결정합니다. 지난 호에 기록된 9PFS 길이 수렴 제안서도 같은 흐름에 속합니다: Smart 측 코드가 ‘동작 가능’에서 ‘유지보수 가능’으로 전환되고 있습니다.

2. 보안 및 안정성 후속

2.1 시간 서브시스템에서 하룻밤 사이 4건 연속 보고: settimeofday 협소화, gmtime_r 음수 타임스탬프, timer_gettime 절단, 부록으로 A~F 작업 항목 조사 (10-23/10-24)

날짜: 2026-10-23 21:04 및 2026-10-24 20:25 (생성 시간)　출처: Issue #11922, Issue #11923, Issue #11924, Issue #11927

10-23 저녁, 같은 연구자가 components/libc/compilers/common/ctime.c에서 연달아 세 건을 열었고, 다음 날 조사 건 하나를 더해 시간 서브시스템의 의미론적 문제를 한꺼번에 드러냈다. 세 건의 기준선은 모두 master의 a59e72fb5c이며, 전부 소스 수준 격리 재현으로 보드에서는 검증하지 않았다.

첫 번째 건은 settimeofday()의 타입 협소화다. 검증 시 먼저 (long)tv->tv_sec으로 강제 변환하는데, time64/long32의 32비트 ARM ABI에서(time_t는 64비트 부호 있음, long은 32비트) 유효한 양수 타임스탬프가 음수로 변환되어 RTC 드라이버를 호출하기 전에 -1을 반환하고 EINVAL을 설정한다. 작성자는 GNU Arm Embedded 10.3-2021.10으로 타입 크기와 협소화 동작을 격리 검증했다.

두 번째 건은 gmtime_r()의 음수 타임스탬프 처리다. 함수는 NULL이 아닌 값을 반환하지만 필드가 유효하지 않다. 제시된 네 가지 대조값은 직관적이다. -1은 1970-01-01 00:00:-1, -86400은 1970-01-00 00:00:00(yday가 -1), -31536000의 연도 필드는 1970-01--364, -2208988800은 1900-01-01이어야 하지만 1970-01--25566이 된다. 근본 원인은 나머지 연산이 모두 C의 0 방향 절단 의미론을 사용해 음수 입력에서 나머지가 음수가 되고, 연도 루프는 미래 방향으로만 진행할 수 있기 때문이다.

세 번째 건은 timer_gettime()의 절단이다. 총 잔여 나노초를 먼저 rt_uint32_t에 저장한 뒤 초와 나노초로 분해하는데, 10초는 100억 나노초이므로 32비트 변수에 대입하면 상위 비트가 직접 손실된다. 영향을 받는 설정은 RT_USING_POSIX_TIMER와 RT_USING_CLOCK_TIME이 동시에 켜진 경우다.

네 번째 건(10-24 20:25)은 결함이 아니라 조사다. tick, clock_time, RTC, libc, VDSO가 각각 시간 기준선을 유지하는 문제를 작업 항목이 포함된 설계 제안으로 정리하고, 열 가지 부족점(시각 설정 불통일, clockid 의미론 혼란, 소프트 RTC 가짜 동기화, 랩어라운드와 오버플로, hrtimer 회귀, PM 분기, 부팅 시각 부여 상태, NTP 버전 경계 등)을 나열하며, A~F 여섯 가지 추적 가능 작업 항목과 P0~P2 우선순위를 제시하고, 일반 MCU는 A~D만 완료하면 단계적 종점에 도달한다고 명확히 했다. 이 건은 스스로 정적 분석이라고 밝혔으며 컴파일도 보드 검증도 하지 않았다.

부속 수정 제안은 이미 두 건이 열렸다. #11928은 settimeofday()가 필드 자체 타입에 따라 검증하고 더 이상 일괄적으로 long으로 변환하지 않도록 하며, #11929는 gmtime_r()의 기원전 타임스탬프 정규화를 처리한다. 두 건 모두 10-24에 제출되었으며 아직 병합되지 않았다.

날짜: 2026-10-24 03:39 (생성 시간)　출처: Issue #11925

3.2 GDR: RT-Thread 커널 객체 조회를 GDB로 이전, QEMU 폐쇄 루프가 3.1.x/4.0.x/4.1.x 커버 (10-25)

날짜: 2026-10-25 (게시)　출처: EE Times China: LoRaWAN 이식 삽질에서 출발하여, GDR 저장소

“디버깅 스캐폴딩”을 정식 엔지니어링으로 다루는 드문 커뮤니티 장문입니다. 출발점은 2년 전 Semtech의 LoRaWAN 프로토콜 스택 SWL2001을 Zephyr에서 자원이 제한된 국산 MCU로 이식한 것으로, 하부는 축소된 RT-Thread Nano입니다. 40여 개의 HAL 인터페이스를 하나씩 매핑했으며, 어떤 의미론적 편차든 런타임에서만 드러납니다. 진짜 어려움은 관측에 있었습니다. FinSH가 실행되면 radio planner의 타이밍이 교란되어 관측 행위가 피관측 시스템을 변화시킵니다. GDB는 기본적으로 포인터만 제공하므로, 세마포어 하나를 보려면 rt_object_container를 따라 연결 리스트를 순회하고 container_of 변환 후 cast해야 하며, 객체 열 개면 오륙십 개의 명령이 필요합니다.

GDR의 방식은 이런 기계적 노동을 GDB의 Python 명령으로 고정화하여 세 계층의 능력을 제공합니다. 집계 명령(rtthread threads/timers/system/semaphores/objects)은 전역 스냅샷을 출력하며, 스레드 테이블에는 스택 채움 패턴 기반의 피크 워터마크인 StkUsed와 MaxStkUsed 두 가지가 포함됩니다. 편의 함수 $gdr_thread("worker2")와 $gdr_object(...)는 네이티브 gdb.Value를 반환하며, 이후 필드 탐색은 여전히 GDB 표현식을 사용합니다. pretty-printer는 커널 객체를 한 줄 요약으로 축약하며, 예를 들어 뮤텍스는 소유자를 직접 표시합니다.

FinSH와의 본질적인 차이는 완전 무침투라는 점입니다. 모든 정보는 GDB로 심볼과 대상 메모리를 읽기만 하며, 펌웨어 내부의 어떤 함수도 호출하지 않습니다. 따라서 셸이 아예 없는 Nano 시나리오에도 적용할 수 있고, HardFault 이후 코드 실행이 불가능한 사후 분석에도 적용할 수 있습니다. 엔지니어링 측면에서 기억할 만한 몇 가지 결정이 있습니다. 더 이상 RTOS를 자동 탐지하지 않고(명시적으로 gdr init rtthread 4.0.5로 변경, 다만 SMP, 힙 관리자, IPC 컴포넌트 같은 구성 차이는 심볼 존재 여부로 탐지), 모든 레이아웃 지식을 하나의 파일에 모으고 COUPLED로 표기하며, QEMU로 실제 펌웨어를 부팅해 pytest 단언을 수행하고, CI 매트릭스가 Cortex-A9(3.1.0~3.1.5, 4.x)와 RV64(4.0.4~4.1.1)를 커버합니다. 저자는 경계도 명시했습니다. 본인은 더 이상 MCU 개발을 하지 않으며, 도구는 QEMU 매트릭스에서만 검증되었고 실제 보드에서는 아직 검증되지 않았습니다. 후속 계획은 agent skill, VSCode 플러그인, FreeRTOS 적응입니다.

4.4 드라이버와 CI: OSPI 옥타 플래시, I2C 제어 트랜잭션 직렬화, STM32 패키지 테스트 동시성 잠금 (10-23/10-25)

날짜: 2026-10-23 ~ 2026-10-25 (업데이트 및 병합 시각)　출처: PR #11912, PR #11820, pkgs-test PR #37

드라이버 계층에서 가장 큰 건은 OSPI와 OctaFlash 지원(#11912)으로 32개 파일이다. 이전에 RT-Thread의 SPI 드라이버 계층에는 네이티브 OSPI 경로가 없어 옥타 플래시는 우회해야 했다. 변경 사항은 components 계층에 OSPI의 버스, 디바이스, 설정 및 메시지 정의를 추가하고, 전송 보조 함수와 빌드 옵션을 추가하며, 기존 SPI와 QSPI 경로를 유지한다; OSPI 전송과 탐지를 SFUD에 연결하여 읽기, 쓰기, 지우기 및 상태/제어 작업을 지원하고, SFUD 디바이스 테이블에 MX25LM51245G를 추가하여 검증에 사용한다; 전체 경로가 하드웨어에서 동작할 수 있도록 범용 STM32 OctoSPI 드라이버와 stm32l4r9-st-eval의 보드 레벨 OSPI Flash 지원을 추가하여 SFUD가 1-1-1과 8-8-8(OPI STR/DTR) 두 모드로 접근할 수 있게 한다.

I2C 건(#11820)은 버스 제어와 전송의 경쟁 조건을 수정한 것입니다. rt_i2c_control()이 rt_i2c_transfer()가 버스를 사용하는 동안, 특히 SET_MAX_HZ에서 컨트롤러 설정을 변경할 수 있었습니다. 수정 방식은 제어 명령이 동일한 버스 뮤텍스를 획득하고 통합된 출구에서 해제되도록 하며, API 문서에 제어에 스레드 컨텍스트가 필요하다는 점을 명시하는 것입니다. 검증에는 호스트 측 pthread 뮤텍스 어댑터를 사용해 동시 전송과 제어, 제어와 제어, 주파수 업데이트, 잠금 및 콜백 오류, 그리고 제어 내 중첩 전송을 커버했습니다. 패치되지 않은 소스는 동일한 회귀 집합에서 실패했습니다.

CI 측 건은 pkgs-test(#37)에 있으며, 1개 파일 +11/-7로 설명이 매우 완전합니다. STM32 소프트웨어 패키지 테스트는 여러 버전을 병렬로 실행하며, 각 작업은 독립적인 BSP 복사본을 가지지만 여전히 bsp/stm32/libraries 아래의 HAL/CMSIS 드라이버 디렉터리를 공유합니다. 기존의 sem_stm32는 컴파일만 보호하고 의존성 업데이트는 보호하지 않아, 한 작업이 다른 작업의 의존성 클론이 완료되지 않은 상태에서 동일 디렉터리에 git pull을 수행하면 Git이 추적되지 않은 파일이 덮어쓰여질 것이라고 보고 중단하며, 실패는 다시 프레임워크에 의해 일괄적으로 compile failure로 보고되었습니다. 지난 호에 합입된 #11870 테스트가 바로 이 문제로 실패했습니다(실패 로그 확인 가능). 수정 방식은 잠금을 __build()로 상향 이동시켜 의존성 업데이트와 컴파일이 동일한 임계 구역에 있도록 하고, 동시에 __build_scons() 내의 중복 잠금을 제거해 자기 교착을 방지하며, try/finally로 예외 시 해제를 보장하는 것입니다.

5. 요약 및 트렌드 관찰

5.1 이번 호 트렌드

  • 차량 규격 아키텍처는 「툴체인 선행」: TriCore/AURIX는 이번에 메인 저장소가 아닌 Env SDK에 들어갔습니다. 오픈소스 GCC 13.4.1과 qemu-tricore 두 패키지가 먼저 컴파일과 시뮬레이션을 보완했으며, 메인라인 libcpu에는 여전히 tricore 포팅이 없고 bsp 아래에도 AURIX 보드 레벨 디렉터리가 없습니다. 2020년 전후 TASKING 상용 툴체인에 의존했던 시도들(모두 Closed로 종결)과 비교하면 이번 경로가 실현 가능성이 더 높지만, 「보드에 올릴 수 있는」 단계까지는 아직 BSP와 드라이버가 필요합니다.
  • 메인라인은 극히 조용하고 제안 면은 극히 활발: 72시간 동안 master에는 단 2건의 커밋만 있었지만, 모니터링 기간 내 25건의 PR이 업데이트되었고 6건이 합입되었습니다(메인 저장소 2, sdk 2, packages 1, pkgs-test 1). 합입 동작은 금요일 저녁과 일요일 저녁에 집중되었으며, 리뷰는 멈추지 않았고 개발 측은 실제로 마무리 중입니다.
  • 결함 연구가 단일 지점에서 서브시스템으로 전환: 시간 서브시스템에 하룻밤 사이 4건(3개 결함 + A부터 F까지 작업 항목이 포함된 조사 1건)이 올라왔고, 두 건의 수정 제안이 다음 날 제출되어 「보고—분석—수정」의 짧은 폐루프를 형성했습니다. lwp의 sys_poll 랩어라운드는 32비트 RT-Smart가 사용자 상태에서 제어 가능한 카운터의 정수 경계 문제를 별도로 나열했으며, 지난 호의 「디바이스 또는 서버 측 메타데이터를 길이로 사용」하는 결함군과 상호 보완적이어서 커널이 여전히 역사적 부채를 지불하고 있음을 보여줍니다(ecf2d821은 2022년까지 거슬러 올라갈 수 있음).
  • 빌드를 통과 조건으로 하는 합입이 CI에 역습당하기 시작: 지난 호 ESP-IDF v6.1 적응 합입 이틀 후, master에서 C3/C6 빌드가 빨갛게 변해 모든 PR의 정적 빌드 검사를 파급했습니다. 수정 제안은 당일 개설되었습니다. 이 사슬 자체는 건강하지만, 「로컬 미컴파일, CI 검증」이라는 기준에는 순서 안정성 보장이 뒷받침되어야 함도 보여줍니다.
  • 엣지 AI의 착점이 모델 실행에서 도구 연결로 전환: ai/Agent 패키지에 STT 업로드 엔드포인트 추가, 기본 백엔드를 DeepSeek 공식 API로 교체, 커뮤니티 대회 작품이 agent 패키지로 MQTT 조작을 도구로 등록해 커널 스케줄링에 제공, 그리고 10-26 저녁의 「듀얼코어 + 근전도 의도」 라이브 방송까지 방향이 일치합니다. RTOS는 agent의 런타임으로 간주되고 있으며, 실시간성과 이기종 분업이 범용 Linux 대비 강점입니다.
