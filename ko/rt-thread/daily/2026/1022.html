1. 커널 및 버전 동향

1.1 3년간 보류된 타임슬라이스 스케줄링 제안 재검토: 판별식이 #11907과 결론은 같으나 「READY 지연 기록」이 단일 코어에서 이중 해제 유발(10-21)

날짜: 2026-10-21 14:16 ~ 14:41(댓글 시간)　출처: PR #6645, PR #11907

2022-11-23 제출된 타임슬라이스 스케줄링 패치(#6645)는 Status: waiting for test에 장기간 걸려 있었는데, 커뮤니티 멤버 Yunlk가 모니터링 기간 내에 세 건의 댓글을 연속 게시하여 이를 다시 심사 시야로 끌어왔다. 첫째, 패치가 수정한 src/scheduler.c는 현재 메인라인에서 이미 scheduler_comm.c, scheduler_up.c, scheduler_mp.c로 분할되어 원 패치를 직접 적용할 수 없으며, 댓글은 변경 지점과 신버전 파일의 일대일 대응을 제시했다. 둘째, 해당 패치의 핵심 판별식—「여전히 실행 중이며 타임슬라이스가 소진되지 않은 채 선점된 경우」에만 대기열 선두에 삽입하고 나머지는 모두 대기열 후미로—는 #11907이 독립적으로 도출한 결론과 완전히 일치하며, 서로를 모르는 두 경로가 동일한 판단으로 수렴했기에 작성자는 이것 자체가 방향의 유효성에 대한 방증이 될 수 있다고 밝혔다. 셋째, 진정한 분기는 구현 수단에 있다: 본 패치는 삽입 시작 시 READY를 기록하는 덮어쓰기를 삭제하고 삽입 끝에서 통일하여 설정하고 YIELD를 클리어하도록 변경하여, 삽입 기간 동안 스레드 상태가 여전히 RUNNING으로 남게 된다.

이 로직에 따라 단일 코어 경로로 이식한 후, QEMU vexpress-a9에서 세마포어 웨이크업 순서가 BA에서 AB로 수정되고, 시작 순서가 DC에서 CD로 수정되었으며, 3개 스레드의 시간 분할 라운드 로빈은 정상이지만, 스케줄링 그룹 utest가 안정적으로 크래시한다: rt_smem_free 단언 실패, 백트레이스는 rt_free ← rt_defunct_execute ← idle_thread_entry, 즉 idle이 종료된 스레드를 회수할 때 동일한 TCB에 대해 이중 해제가 발생하며, 두 번의 실행에서 동일한 테스트 케이스로 재현된다. 격리 실험에서 rt_schedule() 내 기존 YIELD 제거를 다시 추가한 결과 크래시는 그대로 발생했으며, 이는 문제가 제거 위치에서 비롯된 것이 아니라 “READY 지연 쓰기”에서 비롯되었음을 보여준다. SMP(듀얼 코어 구성) 보충 테스트 후 판별식 역시 유효하며, 이중 해제는 단일 코어 경로에서만 관찰되었다. 저자는 동시에 자신의 이전 “SMP 미테스트” 발언을 정정했다. 결론 제안: 판별식은 유지할 가치가 있으나, #11907의 “먼저 stat_before를 저장한 후 판단”을 기반으로 추진하고, #6645를 계속하려면 먼저 단일 코어에서의 이중 해제를 확인해야 한다.

1.2 동적 모듈 미초기화 전역 변수 수정: BSS 세그먼트 할당 포인터 미전진 등 네 가지 결함 동시 처리 (10-21)

날짜: 2026-10-21 21:09 (생성 시간)　출처: PR #11915, Issue #5705

기여자 usualtreee가 2022년 3월에 보고된 #5705에 대한 수정을 제출했으며, 문제는 현재 메인라인 1c801efa에서 여전히 재현 가능하다. 결함은 재배치 가능 모듈(ET_REL) 로딩 경로 dlmodule_load_relocated_object()에 집중되어 있으며, 이는 Cortex-M 등 RT_USING_MODULE이 활성화된 보드가 사용하는 경로이다. 첫째, BSS 세그먼트(SHT_NOBITS) 로딩 후 할당 포인터가 전진하지 않아 여러 NOBITS 세그먼트가 동일한 메모리에 겹치게 된다. 둘째, 세그먼트 심볼 재배치 공식에 세그먼트 링크 주소 보정이 누락되어 있다. 셋째, SHN_COMMON 심볼(tentative 정의의 미초기화 전역 변수)이 조용히 건너뛰어지는데, 이는 코드가 shdr[0xfff2]를 읽어 세그먼트 이름을 얻은 후 쓰레기 값을 얻게 되어 매칭되지 않기 때문이다. 넷째, 해당 경로는 module->symtab을 전혀 구성하지 않아 ET_REL 모듈에 대한 dlsym()이 항상 실패한다.

수정 방법은 네 가지에 대응한다: BSS 세그먼트 로딩 후 세그먼트 크기만큼 포인터 전진; rodata/bss/data 세그먼트 재배치를 “세그먼트 로드 주소 − 세그먼트 링크 주소 + 심볼 값”으로 통일; SHN_COMMON을 위해 별도로 공용 블록을 할당하고 해당 분기를 세그먼트 이름 매칭 이전으로 전진시켜 범위 초과 읽기를 방지; .symtab에서 전역 함수 심볼을 수집하여 module->symtab 구성. 두 파일 변경 +147/-9, qemu-vexpress-a9에서 세 개의 테스트 모듈로 검증: 수정 전 ET_REL 모듈 dlsym 실패, 수정 후 성공하며 두 미초기화 전역 변수 주소(0x600d2008과 0x600d2004)가 서로 겹치지 않고, 특징값 쓰기 후 다시 읽기 통과, 두 ET_DYN 모듈 결과 불변. 제안은 CLA를 통과했으며 components 그룹 리뷰 중이다.

1.3 메인라인 10-19 이후 신규 커밋 없음, v5.4.0 여전히 버전 매크로만 있고 릴리스물 없음 (10-22)

날짜: 2026-10-22 (확인 시간)　출처: 메인 저장소 커밋 기록, releases, tags

모니터링 기간 내 메인라인 커밋 제로, 머지 제로, 최신 커밋은 여전히 10-19 18:49의 [bsp][spacemit/k1] first version이며, 조직 페이지의 푸시 시간 역시 10-19에 멈춰 있고, 나머지 저장소의 최근 활동은 10-18의 rtthread-skills와 smart-build, 10-17의 env와 포팅 사양 저장소이다. 버전 측 변화 없음: 최신 태그와 릴리스물은 여전히 09-10의 v5.3.0이며, 10-17의 “Bump version to v5.4.0”은 지금까지 버전 매크로만 있을 뿐 릴리스 노트와 바이너리가 없다. 이번 기간의 실제 코드 활동은 전부 심사 중인 제안, 결함 티켓 및 RT-Thread-packages 측 패키지 저장소에 집중되어 있다.

2. 보안 및 안정성 후속

2.1 NFS 읽기 경로가 서버 측 카운트로 memcpy 길이 결정: 한 번의 cat으로 반환 주소 덮어쓰기 가능 (10-22)

날짜: 2026-10-22 02:13 (생성 시간)　출처: Issue #11917, dfs_nfs.c

기여자 XueDugu가 NFS 클라이언트 결함 이슈를 새로 열었으며, 이는 직접 악용 가능한 메모리 손상에 해당한다. nfs_read()는 요청 길이를 1024바이트 이내로 제한하지만, 복사 시에는 서버 응답의 READ3resok.count를 사용하며, 이는 호출자의 요청 길이와도 비교하지 않고 같은 응답에서 디코딩된 데이터 길이와도 비교하지 않는다. XDR 디코딩 측은 xdr_bytes(..., ~0)을 상한으로 사용하므로 길이 검증이 결코 발동되지 않는다. 두 카운트 필드는 프로토콜상 서로 독립적이어서, 악의적인 서버는 80바이트 요청에 대해 count = 512와 512바이트 데이터를 응답할 수 있다.

영향은 내장 cat 명령에 미친다. dfs_file.c는 char buffer[81]로 읽기를 받아들이는데, cat으로 파일 하나를 한 번 읽는 것만으로 버퍼 끝을 최대 약 430바이트 넘어설 수 있어 finsh 스레드 스택의 반환 주소를 덮어쓴다. 이 결함은 2010-05-20의 커밋 0fbfdec40d에서 도입되었으며, v1.2.0부터 모든 버전이 영향받고 v5.3.0과 현재 메인라인도 포함된다. 작성자는 QEMU vexpress-a9와 RP2350 실보드에서 각각 재현했다. NFS 클라이언트가 직접 AUTH_SYS를 구성하고 인증 없는 UDP를 사용하므로, 마운트된 서버나 경로상의 주입자가 오버플로 내용을 제어할 수 있다. 이 이슈는 현재 아무도 담당하지 않고 있다.

2.2 raw-API DHCP 서버 옵션 순회에 경계 검사 누락: 최대 1500바이트 버퍼를 4바이트 초과 (10-21)

날짜: 2026-10-21 15:49 (생성 시간)　출처: Issue #11913, dhcp_server_raw.c

또 다른 연구자 K-ANOY가 raw-API DHCP 서버의 범위 초과 읽기를 보고했다. 옵션 검색 함수는 반환 포인터가 버퍼 내에 있음만 보장하며, 순회 시 buf[1]을 읽기 전에 buf + 1 < end를 검증하지 않아, 끝에 1바이트만 남은 옵션 헤더가 1바이트 범위를 초과해 읽힌다. 호출자는 이어서 고정 폭으로 값을 읽는데(요청 IP는 4바이트, 메시지 타입은 1바이트), 옵션 헤더를 끝에 두면 opt[2]..opt[5]가 1500바이트 pbuf 힙 블록을 최대 4바이트 초과할 수 있다. 같은 디렉터리의 소켓 기반 dhcp_server.c는 정확히 이런 검사들—길이 범위 초과 여부, 선언 길이의 유효성, length < 4와 length < 1—을 수행하므로, raw 버전에 빠진 것이 바로 이 몇 가지 검사임을 반증한다.

트리거 조건은 같은 서브넷의 임의 호스트가 UDP/67로 옵션 영역이 잘린 패킷을 보내는 것뿐이며 인증은 필요 없다. 작성자는 ASan에서 논리 수준 재현을 완료했고, 읽힌 값은 비교와 분기에만 사용되며 직접 외부로 유출되지는 않는다고 지적했다. 이 이슈에는 bug와 component: net 라벨이 붙었으며 아직 담당자가 없다.

2.3 전일 두 건의 메모리 결함 수정 제안 여전히 심사 중, 이번 호에 병합 없음 (10-21)

날짜: 2026-10-21 (확인 시간)　출처: PR #11911, PR #11910

지난 호에 수록된 두 건의 메모리 결함 모두 대응 수정이 절차 중에 있다. cromfs 디렉터리 이름 길이 제약 제안(#11911, 동일 연구자가 제출, 결함 이슈 #11905에 대응)과 tmpfs가 0 길이로 잘릴 때의 해제 후 사용 수정(#11910, RT-Smart의 aarch64에서 재현된 후 remukisama가 제출)이다. 두 건 모두 이번 모니터링 기간에는 상태와 코멘트만 갱신되었고 메인라인에 병합되지 않아, 이번 호에서는 기술 세부를 반복해 다루지 않는다.

4.1 ESP-IDF v6.1 패키지 측 병합: C3/C6에 RT-Thread로 FreeRTOS를 교체하는 공식 스위치 등장 (10-21)

4.2 BSP 측 동일 배치 제안 블로킹 해소: C3 13개 구성 전부 통과, 보드 검증 대기 (10-21)

4.3 OSPI와 OctaFlash가 컴포넌트 계층으로 진입: SFUD가 1-1-1과 8-8-8 두 모드 지원 (10-21)

4.4 Cortex-A의 GIC 출력 함수 형식 지정자 수정: %p에 비포인터 전달은 정의되지 않은 동작 (10-21)

날짜: 2026-10-21 18:00 (생성 시간)　출처: PR #11914

libcpu/arm/cortex-a 아래의 GICv2 및 GICv3 정보 출력 함수에는 네 가지 유형의 형식 지정자와 실인자 타입 불일치가 존재합니다. 물리 주소는 rt_uint32_t인데 %p로 출력하여 정의되지 않은 동작에 해당하며, GIC 버전 번호는 unsigned long, 최대 인터럽트 번호와 인터럽트 번호는 unsigned int인데 모두 %d를 사용합니다. 5.1 Ruiching V1.8.4의 산업 현장 수정: EtherCAT 인터럽트 선호도, telnet에서 netstat 멈춤, UART DMA 보레이트 (10-21)

날짜: 2026-10-21 11:50 (발표 시각)　출처: EE Times China: Ruiching 플랫폼 V1.8.4 릴리스, Ruiching 변경 로그

동일 버전의 네 가지 수정은 모두 산업 현장을 겨냥합니다. EtherCAT의 태스크와 인터럽트가 이전에 동일 CPU에 바인딩되지 않아 인터럽트가 기본적으로 CPU0에 떨어졌고, 다중 태스크 전환 시 간헐적으로 접근 충돌과 다운이 발생했으며, 수정 후 둘을 동일 코어에 바인딩했습니다. telnet 원격에서 netstat를 실행하면 응답 없이 블로킹되는 문제를 수정했습니다. UART DMA 예제에서 보레이트 설정이 실패했으며 근본 원인은 DMA 시리얼 초기화 흐름에 있었고 수정했습니다. 4.3인치 화면 예제는 백라이트 PWM을 높여 야외 시인성을 개선했습니다. 이전 호에서 이미 보도한 EG1200 산업 게이트웨이 가상 네트워크 인터페이스와 NFS 마운트, 그리고 RC-Pi-3506 기반 ROS2 허브 모터 운동 제어 방안과 결합하면, Ruiching 이 제품 라인이 이번 호에 보여주는 것은 ‘게이트웨이 측 네트워킹 능력’과 ‘운동 제어 측 실시간성’이라는 두 가지 병행 추진이며, 수정 항목도 내부 테스트보다 실제 프로젝트 피드백에서 나온 것이 많습니다.

6. 요약 및 동향 관찰

6.1 이번 호 동향

  • 스케줄러 논의가 「각자 제안」에서 「구현 비교」로 이동: 3년간 보류된 #6645가 재검토되었으며, 그 판별식이 #11907과 독립적으로 수렴했지만 두 구현 방식이 메모리 안전성에서 우열이 갈렸다. READY 지연 쓰기는 단일 코어에서 idle 회수 경로의 이중 해제를 유발했지만, 이전 상태를 저장하는 방식에는 그런 문제가 없었다. 이러한 제안 간 횡적 비교는 단일 패치보다 의사결정 가치가 크며, #11907을 사실상 추진 기준선으로 만들었다.
  • 결함 보고가 계속 외부 연구자에 의해 주도되며 완전한 영향 범위를 동반: 하루에 두 건의 메모리 문제, NFS 스택 오버플로의 도입 커밋은 2010년까지 소급 가능하며 v1.2.0 이후 모든 버전에 영향, DHCP 범위 초과 읽기는 같은 디렉토리의 다른 구현 검사 항목으로 누락 지점을 반증했다. 두 보고서 모두 재현 환경과 트리거 조건을 제공하여 수정 비용이 크게 낮아졌다.
  • RISC-V 측에 커널 교체 통로 확보: ESP-IDF 6.1 전체 패키지 업그레이드가 머지된 후, C3/C6는 CONFIG_IDF_RTOS_RTTHREAD를 통해 RT-Thread로 FreeRTOS를 교체할 수 있게 되었고, 툴체인도 동시에 GCC 15.2로 올라갔다. 메인 저장소 BSP 제안의 장애 요인도 같은 날 해소되어 보드 검증만 남았다. 이는 이번 주기에서 RISC-V 관련 가장 중요한 진전이다.
  • 메인라인 정체, 버전은 9월에 멈춤: 연속 3일 커밋 0건, 머지 0건, v5.4.0은 버전 매크로만 존재. 활동은 전부 심사 중인 제안, 결함 티켓, 패키지 저장소에 집중되어 공식 채널 중단과 같은 리듬을 형성했다.
  • 벤더 플랫폼이 버전별로 안정적으로 반복하며 현장 문제를 수정에 포함: Ruiqing V1.8.4의 6개 신규 항목과 4개 수정 항목이 모두 구체적 시나리오(엔코더 폐루프, MIPI 화면 적응, AMP 디버깅, EtherCAT 친화성)에 대응하며, IDE도 GD32H7로 동시에 확장되어 산업용 플랫폼의 경쟁력이 「돌아가느냐」에서 「현장에서 안정적이냐」로 전환되고 있음을 보여준다.

6.2 한계 및 중복 제거 설명

  • 이번 기간은 24시간 모니터링 기간(10-21 08:00 ~ 10-22 08:00)이며, 월요일이 아니므로 여러 날을 병합하지 않는다.
  • 메인 저장소는 모니터링 기간 내 커밋 0건, 머지 0건이며, 모든 항목은 심사 중인 제안, 결함 티켓, RT-Thread-packages 측 저장소와 벤더 릴리스에서 나왔으며 각 항목에 상태를 명시했다.
  • 지난 호와 중복 제거: #11907, #11909, #11911, #11910, #11903, #11870은 모두 지난 호에 수록되었으므로, 이번 호에는 모니터링 기간 내 신규 결론만 작성한다(#11870은 관리자가 esp-idf 머지 완료를 확인, #6645의 재검토 데이터, #11910과 #11911의 절차 상태).
  • 검색 결과에서 #11815(lwip 매크로 스위치)와 #11814(RA6W1 리소스 할당)는 모니터링 기간 내 업데이트로 표시되었으나, 실제 머지 시간은 각각 10-14와 10-15이며, 모니터링 기간 내에는 댓글과 상태 변경만 있어 신규 수록하지 않았다.
  • 포럼 글 인터페이스는 최신 25건만 가져오며, 최신 글은 지난 호에 수록된 작품의 편집 업데이트이다. 공식 뉴스 목록 페이지는 프론트엔드 렌더링이므로 뉴스는 인터페이스를 기준으로 한다.
  • Google News 영어는 3일간 검색 결과 0건, 중국어 3일 모니터링 기간 내 유효 기사는 Ruiqing V1.8.4 한 건뿐이며, Ruiqing 검색은 동명의 자동차 기사에 계속 묻혀 제목 의미에 따라 제외했다.
  • 본 기기의 익명 GitHub 한도 내에서 조직 수준 전체 푸시 검증을 하지 못했으므로, 저장소 커밋 흐름과 조직 페이지 교차 검증으로 대체했다. RT-Thread-packages의 조직 페이지 푸시 시간은 저장소별로 확인했다.
