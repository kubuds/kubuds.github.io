1. 커널 및 버전 동향

1.1 qemu-virt64 두 BSP에서 RT-Thread Smart 활성화, QEMU에서 처음으로 사용자 모드 완전 실행 가능 (10-29)

날짜: 2026-10-29 09:29 (병합 시간)　출처: 제안 #11896, 메인 저장소 커밋 기록

10월 18일 생성되어 큐에서 열흘간 대기하던 제안 #11896이 이번 호에 병합되었다. 14개 파일, 1263줄 추가, 1075줄 삭제, 14건 커밋을 포함한다. 사유는 명확하다: qemu-virt64 시리즈 BSP는 줄곧 RT-Thread Smart를 활성화하지 않아 사용자 모드와 LWP 관련 기능을 QEMU에서 테스트할 수 없었고, virtio 블록 디바이스와 의사 터미널의 표준 루트 파일시스템 초기화 절차도 없었다.

변경은 세 계층으로 나뉜다. 설정 계층에서는 qemu-virt64-riscv와 qemu-virt64-aarch64에 RT_USING_SMART를 활성화하고, Smart의 단일 코어 전제에 따라 riscv64의 SMP를 비활성화한다. 실행 계층에서는 applications/mnt.c를 새로 추가하여 virtio-blk0을 루트 디렉터리로 마운트하고(먼저 elm 시도, 실패 시 ext 시도, 디바이스 준비 안 됨 시 최대 100회 재시도, 회당 10밀리초 간격), 이어서 ptyfs를 /dev/pts에, procfs를 /proc에 마운트한다. CI 계층에서는 bsp_buildings, membrowse, utest_auto_run 세 워크플로에 각각 해당 항목을 추가한다. 빌드에서는 riscv64를 RISC-V general musl 툴체인으로, aarch64를 aarch64 musl 툴체인으로 전환한다. 선행 의존성 #11893(lwIP 루프백 네트워크 인터페이스 지원)은 10월 25일에 먼저 병합되었으며, 이번 설정은 해당 심볼 반영 후 재생성된 것이다.

1.2 7시간 30분 만에 기본 설정 회수: #11942, Smart를 오버레이로 되돌리고 CI 선택 로직 재작성 (10-29)

날짜: 2026-10-29 16:59 (병합 시간)　출처: 제안 #11942

같은 날 16:59, #11942가 통과되어 이전 제안이 남긴 기본 설정을 전체적으로 되돌렸다: 7개 파일, 51줄 추가, 220줄 삭제. 두 BSP의 rtconfig.h에서 RT_USING_SMART, KERNEL_VADDR_START, ARCH_REMAP_KERNEL과 PAGECACHE 설정 전체를 제거하고, RT_USING_DFS_V2와 RT_USING_DFS_ELMFAT를 추가했으며, RT_VER_NUM을 0x50301에서 0x50400으로 올렸다. 즉 메인 브랜치는 이미 5.4.0 개발 상태이다.

진짜 기술적 포인트는 CI에 있다. 기존 utest_auto_run.yml은 이 두 BSP의 표준 커널 테스트 케이스에 대해 「git checkout origin/master의 .config와 rtconfig.h」 덮어쓰기 방식을 취했는데, 이는 앞서 방금 추가한 SMP 설정 블록까지 함께 지워버린다. 이번에는 .config에 직접 # CONFIG_RT_USING_SMART is not set 한 줄을追加하는 방식으로 변경하여 Smart만 끄고 SMP는 건드리지 않는다. 동시에 ALL_BSP_COMPILE.json에서 qemu-virt64-aarch64를 aarch64 표준 컴파일 그룹으로, qemu-virt64-riscv를 riscv64-unknown-elf 표준 그룹으로 되돌리고, 기존에 별도로 나열했던 qemu-smart 컴파일 그룹을 삭제했으며, membrowse의 aarch64 대상 툴체인을 aarch64-linux-musleabi에서 aarch64-none-elf로 되돌렸다.

순효과는 Smart가 「BSP 기본 설정」에서 「utest의 설정 오버레이」로 바뀐 것이다: 동일한 BSP가 표준 커널 회귀 테스트도 수행하고 rtsmart.cfg를 통해 Smart 테스트 케이스도 추가하여, 두 경로가 서로를 덮어쓰지 않는다.

1.3 lwp 시스템 콜 구현을 서브시스템별로 20개 파일로 분할, lwp_syscall.c에서 한 번에 11638줄 삭제 (10-29)

날짜: 2026-10-29 14:50 (머지 시간)　출처: 제안 #11894

역시 10월 18일에 생성된 제안 #11894가 이번에 머지되었으며, 22개 파일, 12223줄 추가, 11638줄 삭제. 핵심 작업은 components/lwp/lwp_syscall.c라는 만 천 줄이 넘는 단일 파일을 통째로 syscall/ 디렉터리로 분할하는 것이다: 메모리, 파일, 경로, stat, 파일시스템, 소켓, netdb, 프로세스, 메시지 큐, rt_ipc, 시그널, 시스템, 시간 스케줄링, 디바이스, 채널별로 그룹화하여 20개의 구현 파일로 나누고, 추가로 syscall_internal.h와 공유 시스템 콜 디스패치 테이블을 더했으며, lwp의 SConscript에 새 디렉터리를 등록했다.

제안서 자체에 「기능 변경 없음」이라고 명시되어 있으며, 이는 뒤이은 clang-format 커밋으로 입증된다: 포매팅은 새로 추가된 파일만 건드렸고 주석에도 동작 변경 없음을 표시했다. 분할의 가치는 리뷰 측면에 있다—시스템 콜 구현이 「하나의 큰 파일에서 번호순으로 찾기」에서 「서브시스템별로 위치 찾기」로 바뀌어, 이후 copyin/copyout 같은 경계 수정(예: 2.1에서 다루는 ioctl 문제)을 보완할 때 더 이상 만 줄짜리 파일을 헤매지 않아도 된다.

1.4 터미널 호환성 보완: TIOCLINUX가 수정 키 0 반환, TTY 윈도 기본 24×80 (10-29)

날짜: 2026-10-29 14:48 (머지 시간)　출처: 제안 #11890

2개 파일, 18줄 추가, 4줄 삭제. 이전에는 TIOCLINUX가 직접 실패를 반환했는데, 많은 터미널 프로그램이 시작 시 콘솔 상태를 먼저 탐지하고 탐지 실패 시降級하거나 종료했다; 이번에 수정 키 상태 0을 반환하도록 변경하여 이러한 프로그램이 RT-Smart에서 정상 경로를 계속 진행하도록 했다. 또 다른一处는 창 크기이다: 어떤 소스도 크기를 보고하지 않을 때 TTY를 24행 80열로 초기화하여, ioctl로 크기를 가져오는 데 의존하는 프로그램이 0을 읽지 않도록 했다.

동반 커밋은 동일 코드에서 길이 가져오기 방식을 수정하여, memcpy의 길이 인자를 sizeof(tty_ctrl_charset)로 직접 표현하도록 변경하고, 겸사겸사 cppcheck의 sizeofDivisionMemfunc 경고를 정리했다.

1.5 ping 통계 수정: 첫 응답이 동시에 최솟값을 정하며, 단조 증가 시 minimum = -1을 더 이상 보고하지 않음 (10-29)

날짜: 2026-10-29 09:33 (머지 시간)　출처: 제안 #11900

components/net/netdev/src/netdev.c 파일 하나만 수정하며, 5줄 추가, 1줄 삭제이고, 작성자가 10월 19일에 커밋했습니다. 기존 로직은 max_time을 0으로, min_time을 0xFFFFFFFF로 초기화한 뒤 if / else-if 체인으로 갱신합니다. 첫 번째 응답 패킷의 지연은 반드시 0보다 크므로 max 분기를 타게 되어 최솟값이 할당되지 않습니다. 이후 응답 패킷의 지연이 계속 상승하면 매번 max만 갱신되고 min_time은 계속 0xFFFFFFFF에 머물러, 마무리에서 %d로 출력하면 minimum = -1이 됩니다. 수정 방법은 received가 1일 때 max와 min을 동시에 해당 패킷의 지연으로 설정하고, 이후 두 비교가 각각 한쪽을 담당하게 하여 통계 의미가 맞아떨어지도록 하는 것입니다.

2. 보안 후속 조치 및 병합 대기 큐

2.1 블록 디바이스 ioctl이 24바이트 파티션 테이블을 호출자가 지정한 커널 포인터에 기록 (10-29)

날짜: 2026-10-29 22:00 (보고 시간)　출처: 결함 #11952

RT-Smart 비특권 프로세스가 커널 주소를 ioctl 인자로 넘길 수 있습니다. sys_ioctl()과 blk_fops_ioctl()은 copy-in / copy-out을 하지 않고 원시 인자를 그대로 전달하며, blk_dev_control()은 RT_DEVICE_CTRL_BLK_PARTITION 분기에서 rt_memcpy(args, &blk->partition, sizeof(blk->partition))를 실행하여 24바이트 파티션 정보를 공격자가 선택한 커널 주소에 기록합니다. 영향 범위는 master(v5.4.0-dev) 및 v5.2.0부터 v5.3.0까지로 명시되어 있으며, 일반 블록 계층 커밋 c424cb81에 의해 도입되었습니다. QEMU vexpress-a9, ARMv7-A, 32비트 RT-Smart 및 SD 이미지 환경에서 검증되었고, 커널이 /dev/sd0를 생성한 뒤 트리거할 수 있습니다.

이는 연속 이틀째 같은 유형의 문제입니다. 어제는 터미널 서브시스템의 ioctl이 FreeBSD의 copyin 전제를 누락한 사례(결함 #11937)였고, 오늘은 블록 디바이스 서브시스템이 같은 계층을 누락한 사례입니다. 공통 원인은 RT-Smart의 ioctl 적응 계층이 기본적으로 “인자가 이미 커널 주소”라고 가정하는 반면, 사용자 공간 진입점에서는 이 계층의 변환을 수행하지 않는다는 점입니다. #11941(터미널 측 copyin / copyout 도입)은 현재도 큐에 남아 있으며, 본 결함에는 아직 대응하는 수정 제안이 없습니다.

2.2 하루에 다섯 건의 결함: 세 곳의 ADC 채널 범위 초과, DM365 SPI 0으로 나누기 (10-29)

날짜: 2026-10-29 19:26 ~ 19:42 (보고 시간)　출처: 결함 #11948, #11949, #11951, #11950

같은 보고자가 어느 오후에 드라이버 측 결함 다섯 건을 제출했으며, 그중 네 건은 동일한 제출자에게서 나왔고 주제가 매우 일관됩니다. 호출자가 전달한 채널 번호와 주파수가 검증되지 않는다는 점입니다.

Bluetrum AB32의 ADC는 먼저 ab32_adc_get_channel()로 채널을 매핑한 뒤 변환을 시작하지만, 이후에는 원래 채널 번호로 데이터 레지스터 배열을 인덱싱합니다. 범위를 초과하면 매핑 함수가 조용히 0으로 폴백하고 오류도 보고하지 않아 결국 배열 밖을 읽게 됩니다. Bouffalo의 ADC는 raw_data[10 + channel]을 읽는데, 해당 배열은 26워드이므로 채널이 22이면 32번째 워드에 도달하고, 채널이 -10보다 작으면 배열 앞쪽으로 넘어갑니다. HPM의 ADC는 원래의 부호 있는 채널로 chn_state[16]을 인덱싱하며, rt_adc_enable()은 검증을 하지 않습니다. DM365의 SPI는 davinci_spi_get_prescale()에서 max_speed_hz를 제수로 사용하는데, 0이면 바로 0으로 나누기가 발생하며, DIV_ROUND_UP의 클램프가 나눗셈 뒤에 작성되어 있어 보호 효과가 없습니다.

네 건의 공통점은 rt_adc_read() / rt_spi_configure() 계층에서 매개변수 검증을 하지 않고 검증 책임을 각 드라이버로 떠넘겼으며, 대부분의 드라이버는 이를 수행하지 않는다는 점입니다.

2.3 심사 대기 큐: RISC-V Smart 페이지 폴트 처리, RTL8125 2.5G 네트워크 카드, RK3588 디스플레이 및 오디오 (10-29)

날짜: 2026-10-29 11:13 ~ 17:52 (최종 업데이트)　출처: 제안 #11892, 제안 #11944, 제안 #11943, 제안 #11947

1.1과 같은 배치인 #11892(RISC-V 측 Smart의 MMU와 사용자 모드 페이지 폴트 처리)는 이번 기간에도 여전히 대기열에 있으며, 4개 파일, 105줄 추가, 8줄 삭제, 10월 29일 11:26에 업데이트되었다. 내용에는 XuanTie 아키텍처 선택과 SVPBMT 옵션 추가, 초기 페이지 테이블 포인터를 커널 물리 오프셋 기준으로 환산, MPR 구간이 링크 베이스 주소 아래까지 확장되도록 허용, MMU 활성화 전 초기 페이지 테이블 정리, 각 hart 커널 페이지 테이블의 사용자 주소 항목 제거, 처리되지 않은 사용자 페이지 폴트 발생 시 커널을 끌어내리지 않고 현재 LWP만 종료하는 것이 포함된다. 이 변경들은 1.1과 동일한 목표의 나머지 절반이다. 하나는 QEMU에서 실행되게 하고, 다른 하나는 실제 RISC-V 하드웨어에서 사용자 모드가 커널을 잘못 종료시키지 않게 한다.

나머지 세 건은 모두 대규모 신규 하드웨어 지원이다. RTL8125 이더넷 드라이버는 1934줄 추가로 RTL8125 / RTL8162 네이티브 PCI, 디스크립터 링 DMA, 인터럽트 수신과 TX 완료, 10/100/1000/2500M 자동 협상, lwIP 소프트웨어 체크섬을 지원하며, 선택적 PTP 클록과 PPS도 포함한다. RK3588과 RK3528 디스플레이 및 오디오 지원은 36개 파일, 5483줄 추가, 391줄 삭제로 HDMI 컨트롤러와 HDPTX PHY, VOP2 라우팅과 프레임 버퍼 스캔, SAI와 codec 오디오 클록을 포함한다. DHCP raw 서버 주소 풀 고갈 시의 무한 루프 수정은 규모가 크지 않지만(17줄 추가, 4줄 삭제), 3586가지 풀 크기 / 점유 비트맵 / 시작 위치 조합 대조 테스트와 ASAN 결과를 첨부하여 검증 강도가 이번 대기열에서 가장 높다. 별도로 clang-format을 22.1.8로 고정하는 제안은 75개 파일, 3852줄 추가를 포함한다.

3.2 Infineon Edgi Talk 데스크톱 파트너: 한 문장의 중국어로 감시 임무 지시, 전 과정 AI 협업 개발 (10-30)

날짜: 2026-10-30 00:54 (게시)　출처: 커뮤니티 기사: Little Watcher

2026 임베디드 대회 출품작 「Little Watcher」가 게시되었다. 작성자는 Oliver이며, 하드웨어는 Infineon Edgi Talk(PSoC Edge E84), 시스템은 RT-Thread이고 소스 코드와 릴리스 패키지가 공개되었다. 기능 정의는 매우 좁다. 한 문장의 중국어로 보이는 대상의 출현 또는 사라짐을 지정하고, 변화가 감지되면 알림과 함께 전후 화면을 저장하여 「임시 요구는 별도 인식 프로그램을 작성할 가치가 없다」는 문제를 해결한다.

엔지니어링 구현 측면에서, 보드의 M55 측은 공식 BSP의 CherryUSB UVC 예제와 공식 Wi-Fi 예제 구성을 기반으로 빌드되었으며 기존 M33 부트 펌웨어를 유지한다. RT-Thread 스레드는 각각 음성 녹음 업로드, 카메라 캡처 업로드, 알림 재생을 담당하고, 뮤텍스가 공유 상태와 카메라 중지 과정을 보호하며, 세마포어가 알림 스레드를 깨운다. 주변장치는 LCD, 터치, 마이크, 오디오 디바이스 인터페이스를 통해 접근하고, 데이터는 Wi-Fi 관리 인터페이스와 lwIP socket을 거치며, 제어 브리지는 FinSH/MSH 명령을 사용한다. 컴퓨터 측은 음성 인식, 작업 컴파일, 시각 판단을 담당하며, 작업 계획은 캐시하여 재사용할 수 있어 목표마다 모델을 다시 훈련할 필요가 없다. 경계 조건은 구체적으로 명시되어 있다. 단일 감시 세션 상한 300초, 이미지 업로드 60회(참조 프레임 1장에 최대 59회 비교), 웹페이지는 최근 이벤트 최대 100건만 보관, 확정할 수 없는 화면은 uncertain으로 표시, 재시작 시 기본값은 일시정지.

이 글의 관전 포인트는 알고리즘이 아니다. 시각 판단은 컴퓨터 측의 기성 모델에서 실행된다. 관전 포인트는 「AI가 개발에 참여」하는 과정 자체를 산출물로 취급한다는 점이다. 요구사항 분해, 코드 통합, 장애 진단, 테스트 검증, 문서와 데모의 각 단계마다 AI의 참여 방식을 기록하고, 실패와 통과 기록을 각각 보존한다.

3.3 커뮤니티 장문, 4.0.3 소스로 커널 객체 배열과 침투형 연결 리스트 해설(10-29)

날짜: 2026-10-29 08:28 (게시)　출처: 커뮤니티 글: 커널 객체 분포

커널 입문자를 위한 장문 글이 커뮤니티 글 채널에 게시되었다. 작성자는 CTIE_4063이며, RT-Thread 4.0.3의 src/object.c와 include/rtdef.h를 자료로 삼았고, 코드는 매뉴얼이 아닌 실제 소스에서 가져왔다고 밝혔다. 글의 주된 흐름은 「타입별 관리, 이름별 검색, 순회 가능, 통계 가능」이라는 요구사항군을 세 가지로 구현하는 것이다. 각 객체 유형마다 컨테이너 rt_object_information(타입, 연결 리스트 헤드, 해당 구조체 크기 포함)을 두고, 객체 내부에 침투형 rt_list 노드를 내장하여 검색과 순회에 하나의 범용 코드만 필요하게 하며, rt_object_get_information으로 타입에서 컨테이너를 얻고 container_of로 연결 리스트 노드에서 객체를 역추론한다. 글 말미에는 rt_list 핵심을 복제한 60줄 연습과 GitHub Pages 도해 버전이 첨부되어 있다.

4. 생태계와 벤더 적용

4.1 해외 커뮤니티, RT-Spark 보드로 오프라인 엣지 AI 구현했지만 펌웨어는 FreeRTOS(10-28)

날짜: 2026-10-28 (게시) / 2026-10-29 08:34 (집계 적중)　출처: Hackster 프로젝트: Smart Water Bottle Reminder

Hackster에 RT-Spark 보드를 하드웨어로 사용하는 오프라인 엣지 AI 프로젝트가 등장했다. 6축 IMU로 눕혀 둠, 휴대, 음용, 흔들림의 네 가지 상태를 판단하고, 30초 동안 음용이 감지되지 않으면 LCD에 빨간 글씨로 알림을 표시하고 경보음을 울리며 10초마다 반복한다. 깊이 5의 결정 트리는 Python으로 훈련한 뒤 순수 C로 내보내져 STM32F407에서 단일 추론에 약 154마이크로초가 걸리며, 홀드아웃 세트 정확도는 95%이고, 같은 데이터의 임계값 규칙 베이스라인은 97.5%로, 작성자는 이 차이를 사실대로 적었다. 전체 시스템은 8개 태스크, 두 개의 큐와 두 개의 뮤텍스, 168 MHz 주파수로 완전히 오프라인이다.

분명히 해야 할 점은 프로젝트가 RT-Thread의 RT-Spark 개발 보드를 사용하지만 펌웨어는 FreeRTOS에서 실행되며, 감사의 글에 RT-Thread와 FreeRTOS가 나란히 등장한다는 것이다. 이는 보드 차원의 생태계 재사용에 해당하며 RT-Thread 커널 채택 사례로는 성립하지 않으므로, 수록 시 생태계 참고로 처리하고 응용 적용으로 집계하지 않는다. 같은 작성자는 10월 26일에도 RT-Spark를 사용한 인체 활동 인식 프로젝트를 올렸으며, 이를 보면 이 흐름은 이 보드를 범용 STM32F407 개발 보드로 사용하는 것이다.

5. 이번 기간의 트렌드와 요약

5.1 트렌드: Smart는 적용 당일 기본 구성에서 회수되었고, 테스트 커버리지 레이어가 새로운 위치로 부상

이번 기간은 RT-Thread Smart 계열이 열흘간 대기한 끝에 집중적으로 적용된 사례다. 09:29에 #11896이 머지되어 QEMU의 두 virt64 BSP가 Smart를 켜고 루트 파일시스템 초기화를 보완했으며, 14:48과 14:50에 #11890, #11894가 머지되어 터미널 호환성과 시스템 호출 계층화를 보완했고, 16:59에는 #11942가 머지되어 BSP 기본 구성을 표준 커널로 전면 복구했다.

이 리듬은 반복처럼 읽히지만, 실제로는 메인테이너가 Smart의 위치를 규정하는 과정이다. 기본 구성은 반드시 예측 가능하게 유지되어 Smart가 없는 일반 회귀가 안정적으로 유지되어야 하며, Smart는 utest의 구성 오버레이를 통해 별도로 실행되어 두 경로가 하나의 BSP를 공유한다. 이렇게 하면 QEMU에서의 사용자 공간 테스트 커버리지를 확보하면서도 기본 구성 변화로 기존 BSP 빌드 매트릭스가 흐트러지지 않는다. 같은 작업 묶음에서 #11892와 #11897이 여전히 큐에 남아 있다는 것은 「QEMU에서 검증 가능한 부분은 먼저 머지하고, 실제 하드웨어와 보드 측 확인에 의존하는 부분은 나중에 머지한다」는 것이 이 제안들의 실제 리듬임을 보여준다.

두 번째 축은 보안 경계입니다. 어제는 터미널 ioctl이었고, 오늘은 블록 디바이스 ioctl인데, 두 가지의 원인은 완전히 동일합니다. RT-Smart의 ioctl 적응 계층은 기본 파라미터가 이미 커널 주소인데, 사용자 공간 진입점에서는 copy-in을 하지 않았습니다. 여기에 하루에 다섯 건의 드라이버 측 채널 번호와 0으로 나누기 결함까지 더해 보면, 현재 결함 보고의 착지점이 「기능이 틀렸다」에서 「경계를 검증하지 않았다」로 옮겨가고 있음을 알 수 있습니다. 세 번째로 기록할 만한 것은 1.3의 lwp 분할입니다. 1만 1천 줄의 단일 파일이 하위 시스템별로 그룹화된 20개의 파일로 나뉘었는데, 이런 구조적 변경 자체는 어떤 결함도 수정하지 않지만, 이후의 경계 수정 배치가 효율적으로 리뷰될 수 있는지를 결정합니다.

5.2 한계 및 중복 제거 설명

공식 뉴스 인터페이스는 연속 다섯 번째 달인 6월 17일에 멈춰 있고, 기업 측 동향은 이번 기간에 적중이 없어, 보고서 본문은 전적으로 GitHub와 커뮤니티 문서 두 채널에 의존합니다. HN Algolia가 이번 모니터링 기간에 반환한 4건(DissPair, StrictLLM, Help My Sanity, Uji)은 모두 threads류 키워드의 오매칭으로, 전량 제외했습니다. topic:rt-thread 생태 검색은 이번 모니터링 기간에 적중이 없었습니다. Google News 영어 측의 유일한 적중은 4.1의 Hackster 프로젝트이며, 중국어 측의 RTOS 및 임베디드 AI 관련 기사 두 편은 RT-Thread와 직접적인 관계가 없어 수록하지 않았습니다.

어제 보고서에서는 #11894와 #11896을 「대기열에 있음, 아직 병합되지 않음」으로 기록했는데, 이번 기간에 두 건 모두 병합되었으며 이는 정상적인 일정 진행으로, 이전 기간 결론에 대한 정정이 아닙니다. 4.1의 RT-Spark 프로젝트는 펌웨어가 FreeRTOS이므로 보드 생태 참고로만 나열했고, 애플리케이션 적용 항목에는 포함하지 않았습니다.
