오늘의 핵심: 메인 저장소 버전 번호가 0.1.16으로 변경되었으나, 태그와 PyPI는 여전히 0.1.15에 머묾

#3887이 베이징 시간 11-25 00:22에 메인라인에 진입, VERSION 파일 하나만 변경하여 0.1.15를 0.1.16으로 수정. 패키지 메타데이터와 문서 모두 이 파일에서 버전 번호를 읽으므로, 한 곳의 변경으로 모든 버전 선언이 완료됨.

제안서에 나열된 검증 항목은 세 가지. 릴리스 메타데이터가 NO_VERSION_LABEL=ON에서 0.1.16으로 해석됨. 세 가지 version-provider 테스트 통과. pre-commit run --all-files와 bash format.sh 모두 통과.

릴리스 측은 아직 조치 없음. GitHub 태그 최신은 여전히 v0.1.15. Releases 최신은 여전히 2026-09-30의 v0.1.15. PyPI의 tilelang 최신 버전도 0.1.15.

따라서 이번 호에서는 “0.1.16이 릴리스되었다”고 쓰지 않음. 정확한 표현은 버전 번호는 준비되었으나, 태깅, Release 발행, PyPI 푸시 세 단계가 아직 남아 있다는 것.

이전 버전 0.1.15에서 이번 버전 번호 추진까지 55일 소요. 이 기간 동안 메인 브랜치에는 ROCm 일괄 수정, Z3 세 곳 보수 및 Ascend 휠 테스트가 축적됨.

출처: https://github.com/tile-ai/tilelang/pull/3887.

오늘의 핵심: ROCm 하루 6건 병합, FP4 변환 수정 및 리덕션 판정을 wave 너비 기준으로 변경

메인 저장소 당일 12건 커밋 중 6건이 ROCm 접두사 포함. 이번 변경들은 모두 실제 양자화 및 리덕션 경로의 결함을 대상으로 함.

#3665 HIP 템플릿의 누락 두 곳을 수정합니다. 첫 번째는 T.cast(x, T.float4_e2m1fn)의 반환값 오류입니다. 코드 생성이 변환을 (fp4_e2_t)x로 작성하는데, 해당 타입에는 explicit fp4_e2_t(uint8_t raw)만 존재합니다. 이에 따라 float가 정수로 절단된 뒤 원시 비트로 저장됩니다. 1.0은 0.5로, 2.0은 1.0으로, 6.0은 4.0으로 돌아오며 음수도 마찬가지로 잘못됩니다.

두 번째는 HIP 템플릿에 E8M0 타입이 없는 것입니다. 두 곳 모두 VeOmni에서 DeepSeek-V4의 QAT 양자화기를 실행할 때 노출되었으며, 환경은 gfx942와 gfx950이고 UE8M0 스케일을 포함합니다. 0.1.15 휠의 두 헤더 파일은 메인 브랜치와 일치하므로 동일하게 영향을 받습니다.

#3959는 리덕션에 워크스페이스가 필요한지에 대한 판정 기준을 변경합니다. 기존 코드는 리덕션 스레드 수가 32를 초과하면 일률적으로 참을 반환했습니다. 실제로 tl::AllReduce는 특정 단계에서 wave를 넘을 때만 워크스페이스를 사용하므로, wave64에서 64스레드 리덕션은 접근하지 않는 LDS를 할당했습니다. 또한 워크스페이스는 IR에서 공유 메모리 접근이므로 ThreadSync가 이 지점의 매 리덕션마다 배리어를 삽입했습니다.

수정은 대상 wave 폭에 따라 비교하는 방식이며, wave32 대상의 동작은 변하지 않습니다. 배리어는 실제로 wave를 넘는 경로에 여전히 유지됩니다.

#3729는 gfx1200에서 FP16 및 BF16 T.gemm이 표준 선형 공유 레이아웃을 받아들이도록 합니다. 이전에는 A_shared, B_shared에 make_linear_layout을 호출한 뒤 T.gemm을 계산하면 Get different layout이 보고되었습니다. 기존 WMMA 이미터는 해당 매핑으로 데이터를 가져올 수 있었으므로, 문제는 호환성 판정에 있었습니다.

방식은 공유 레이아웃 호환 콜백의 인자를 네 개로 확장하는 것입니다. 연산자, 피연산자 버퍼, 실제 레이아웃, 대상입니다. ROCm 측은 이를 근거로 입력별로 항목을 검증해 재사용하며, 이미터와 인덱스 매핑은 변하지 않습니다.

그 외 세 건은 엔지니어링 세부 사항입니다. #3954는 compile_flags와 tl.device_compile_flags가 실제로 hipcc에 전달되도록 합니다. 이전에는 이 두 매개변수가 캐시 key에만 들어가고 디바이스 코드를 변경하지 않았습니다.

#3958은 hip_resource_info에 점유율 보고를 추가합니다. #3956은 문서에서 T.gemm이 각 wave의 행 수가 매우 적을 때의 제한을 설명합니다.

출처: https://github.com/tile-ai/tilelang/pull/3665.

오늘의 중점: Ascend에서 하루에 열 건의 결함 보고, 전부 API 매개변수 검증 누락을 지목

11-24 하루 동안 동일 저자가 tilelang에 Ascend 결함 10건을 열었으며, 번호는 #4490부터 #4499까지입니다. 열 건의 보고서는 테스트 환경이 동일합니다. 하드웨어는 Ascend 950PR 단일 die, 128 GB 메모리입니다. 소프트웨어는 CANN 9.2.1, HDK 26.0.RC1, openEuler 24.03, torch 2.10.0+cpu, torch_npu 2.10.0.post4입니다.

그중 여섯 건은 “백엔드가 컴파일할 수 없는 입력을 받아들인” 경우입니다. #4490의 T.atomic_add는 int8, uint8, float8 버퍼를 받습니다. #4492의 T.atomic_max와 T.atomic_min은 int8, uint8을 받습니다. #4491의 T.reduce_sum은 bfloat16과 float8을 받습니다. #4494의 T.simd.vabs와 T.simd.vneg는 bf16과 fp8 레지스터를 받습니다.

#4495의 T.gemm은 임의의 unit_flag_ctrl을 받으며, -1이나 999999를 전달해도 조용히 컴파일됩니다. #4497의 T.gemm은 GM 스코프 피연산자를 받지만 백엔드는 컴파일 가능한 경로를 찾지 못합니다.

네 건은 크래시나 오컴파일에 더 가깝습니다. #4496은 float8_e4m3fn 공유 버퍼에 T.fill을 수행하면 bisheng 컴파일러가 직접 core dump됩니다. #4498의 T.gemm은 어떤 TILE_K_SUB로도 나누어떨어지지 않는 K를 받아들인 뒤 자동 스케줄링에서 단언 실패합니다. #4499의 스칼라 T.sqrt와 T.rsqrt는 커널 컴파일 시점에 stl_pair.h 재선언으로 오류가 발생합니다. #4493의 다섯 가지 원자 인터페이스는 Ascend에서 하강 구현이 없습니다.

별도의 출처에서 나온 정확성 결함도 하나 있습니다. #4484는 SimdVF의 리덕션 하강이 sum이 아닌 모든 리덕션 유형을 max로 매핑하여 T.reduce_min이 최댓값을 반환한다고 지적합니다. 해당 항목은 소스 검토에서 나왔으며 디바이스에서 재현되지는 않았습니다.

이 문제들의 공통점은 유형과 값이 컴파일 시점에 거부되었어야 하는데 백엔드에 들어간 뒤에야 실패한다는 것입니다. 11-23의 문서와 구현 불일치 6건과 함께 인터페이스 계약의 누락에 속합니다.

출처: https://github.com/tile-ai/tilelang/issues/4498.

1. 핵심 프로젝트 진행

1.1 Z3 저비트 마스크를 정수 모듈로 인코딩으로 변경, 메인 저장소는 bump를 따르고 TopK 테스트의 솔버 한도 철회

TVM 서브모듈 tilelang_main 브랜치에 당일 #98이 병합되었고, 메인 저장소 측 #4482가 14:03에 bump를 따랐습니다. 세 곳의 수정은 모두 Z3Prover의 구체적인 결함으로 추적할 수 있습니다.

첫째, 상수 부호 있는 우측 시프트 예를 들어 (n + 4095) >> 12는 원래 비트 벡터 경로를 거쳤으며, int2bv, bvashr, bv2int 세 단계를 거쳤다. 이러한 시프트가 루프 경계에 나타날 때, 같은 스코프의 후속 순수 정수 쿼리는 Int와 BitVec 제약을 동시에 가지게 되어, 종종 tirx.Simplify에서 기본 리소스 예산을 소진한다.

둘째, VisitShiftOp는 CanProve에서 b >= 0과 b < 64 두 단언을 공유 솔버에 직접 추가한다. 이는 후속 쿼리를 오염시키고 외부 스코프와 충돌할 수 있다. 동시에 DivNode와 ModNode는 Z3의 유클리드 /와 %를 사용하여, 음수 피제수에 대해서도 truncmod(a, 4) >= 0을 증명할 수 있다.

셋째, tx & 31과 같은 마스크는 인덱스 표현식 단순화에서 여전히 비트 벡터를 사용한다. #98은 x & (2^k - 1)을 x mod 2^k로 변환한다. 제안서는 구체적인 비용을 기록했는데, 특정 디바이스 함수에서 단순화기가 동일한 유형의 질문을 156번 수행하여 11.7초가 소요되었고, 반례는 tx = 4이다.

테스트 측은 먼저 긴급 조치 후 철회했다. #4463은 09:51에 두 ROCm 테스트 파일의 arith.z3_rlimit를 100으로 제한했으며, 원인은 네 개의 DeepSeek와 GLM TopK 케이스가 각각 494~605초를 소모했기 때문이다.

#4489는 20:40에 해당 제한을 철회했으며, 이유는 #4482가 상수 부호 있는 우측 시프트를 저렴하게 만들었기 때문이라고 기록했다. 대조는 동일 빌드 b4c67597, TVM de131ae4, Z3 4.15.4를 사용하여 세 번의 콜드 런 중앙값을 취했다.

출처: https://github.com/tile-ai/tilelang/pull/4482.

#4419는 22:59에 메인에 병합되었다. 제안서에 명시된 전제: Linux 휠은 CUDA, ROCm, Ascend 통합 빌드이지만, test-wheels-gpu는 앞의 두 절반만 실행한다. Ascend 절반 영역은 휠 릴리스 전에 실제 NPU에서 실행된 적이 없다.

1.3 vote 및 sync 내장 함수가 64비트 술어를 유지, 1 << 32가 더 이상 거짓으로 판정되지 않음

#3777은 09:53에 메인에 병합되었다. CUDA의 vote 및 block-sync 내장 함수는 32비트 int 술어만 받으며, 예를 들어 __any_sync, __syncthreads_count가 있다.

int64 또는 uint64를 전달하면 값이 암시적으로 축소된다. 하위 32비트가 0인 비영 술어는 따라서 거짓으로 판정되며, 1 << 32가 가장 직접적인 예이다.

영향을 받는 인터페이스는 일곱 개이다. 투표류는 T.any_sync, T.all_sync, T.ballot, T.ballot_sync이다. 동기화류는 T.syncthreads_count, T.syncthreads_and, T.syncthreads_or이다.

수정 방법은 32비트를 초과하는 술어를 먼저 명시적 != 0으로 정규화한 후 내장 함수에 부울 값을 전달하는 것이다. 또한 1 << 32의 런타임 회귀를 추가했으며, 전체 warp vote 테스트 파일이 통과했다.

출처: https://github.com/tile-ai/tilelang/pull/3777.

2.2 MLIR Ascend, 방언 브랜치에 tl.wait_flag 및 tl.vbitcast 병합

#248은 tl.wait_flag를 추가한다. 이는 전일의 tl.set_flag와 함께 완전한 생산자-소비자 동기화 프리미티브를 구성한다. 표기법은 tl.wait_flag[#tl.pipe<...>, #tl.pipe<...>, %event_id] : i64이다. set_flag가 도입한 #tl.pipe 속성을 재사용하며 새로운 속성이나 타입을 추가하지 않는다. TIR에서 TLIR로의 하강은 동일한 PipeFromString과 GetEventID를 재사용한다.

#249는 tl.vbitcast를 추가하며, TIR, TLIR, HIVM의 세 단계를 거치고, verifier가 형상 일치와 요소 비트 폭 동일성을 검증한다. 이 커밋은 동시에 실제 결함 하나를 수정한다. CodeGenTileLangTLIR의 VisitStmt_(LetStmtNode*)는 이전까지 op->value를 완전히 무시하여, let 바인딩된 호출 결과가 조용히 버려졌다. tl.npuir_bitcast의 handle 반환이 바로 이 경로에 의존한다.

검토 중인 #250은 tl.ln을 hivm.hir.vln으로 하강시킨다. 제안서에는 비TLIR 경로의 BitcastCodegen에도 같은 종류의 역사적 결함이 있다고 별도로 명시되어 있다.

스타의 경우, tilelang은 9030에서 9036으로 올랐고, TileOPs는 204, MLIR Ascend는 31, Ascend 하위 저장소는 433, Hygon은 11입니다.

출처: https://github.com/tile-ai/tilelang.

4.2 뉴스 측 보도 없음, 제3자 측에 제로 스타 저장소 두 개 등장

Google News 중영문 검색에서 24시간 모니터링 기간 내에 TileLang 관련 보도는 없었습니다. 후보 네 건 중 세 건은 본 주제와 무관하고, 한 건은 HN의 인디 게임 Show HN입니다.

GitHub 저장소 검색에서 새로 만들어진 제3자 저장소 두 개가 나왔습니다. easy-tilelang/deepseek-v41-mini-repro는 11-24 19:54에 생성되었습니다. hicann/ops-tilelang은 16:03에 생성되었습니다. 둘 다 제로 스타, 설명 없음, Python 언어이며, 아직 평가할 내용이 없어 이번 호에서는 존재만 기록합니다.

arXiv 전체 필드 검색에서 TileLang을 언급한 가장 최근 논문은 여전히 11-03의 KV 압축 작업입니다. 모니터링 기간 내에 새 논문은 없습니다.

출처: https://github.com/hicann/ops-tilelang.

5. 트렌드 관찰

  • 릴리스 리듬이 릴리스 전야에 접어들었습니다. 0.1.15는 9-30에 릴리스되었고, 55일 후 버전 번호가 0.1.16으로 넘어갔습니다. 이번 버전의 축적은 주로 ROCm 수정, Z3 세 곳 패치, 릴리스 체인 엔지니어링이며, 신기능이 아닙니다.

  • 성능 회귀 관리는 고정된 패턴이 형성되었습니다. 먼저 한도를 추가해 출혈을 멈추고, 근본 원인을 수정한 뒤, 마지막으로 한도를 철회하고 재측정합니다. #4463, #4482, #4489 세 단계가 모두 하루 안에 완료되었고, 중간에 TVM 서브모듈 업데이트가 한 번 있었습니다.

  • Ascend의 약점이 연산자 커버리지에서 인터페이스 계약으로 옮겨갔습니다. 하루 열 건의 결함 중 새 연산자를 요구하는 것은 하나도 없고, 전부 “받아들이지 말아야 할 입력이 받아들여진” 것입니다. 이런 문제는 고치기는 저렴하지만 사용자 신뢰를 지속적으로 소모합니다.

  • TileOPs의 최적화 기준은 여전히 프레임워크 버전을 따라가는 것입니다. 0.1.15의 범용 경로가 가져온 추가 오버헤드는 하위에서 연산자별로 하나하나 우회해야 합니다. 이틀 안에 최소 다섯 건이 이를 제목으로 삼았으며, 이는 버전 업그레이드와 연산자 라이브러리 성능 사이에 아직 자동 대조 메커니즘이 없음을 보여줍니다.

  • RISC-V 측은 연속 두 모니터링 기간 동안 변화가 없습니다. TVM 노선과 MLIR 노선 모두 제자리에 멈춰 있고, 이번 모니터링 기간에는 인덱스 페이지조차 움직임이 없습니다.

검증 설명

기준: 모니터링 기간은 베이징 시간 11-24 07:00부터 11-25 07:00까지 총 24시간입니다. 저장소 커밋은 committer 시간 기준으로 집계하며, 먼저 이전 회차 기준 시점인 11-24 07:00과 비교한 뒤 신규 여부를 판정합니다.

버전 번호 커밋의 committer 시간은 11-24 16:22 UTC로, 베이징 시간으로 환산하면 11-25 00:22이며 이번 회차에 포함됩니다. 본문은 “버전 번호는 변경되었으나 릴리스는 미완료”로 서술했으며, 0.1.16이 이미 릴리스되었다고 쓰지 않았습니다.

MLIR Ascend의 두 건은 PR의 base 브랜치로 확인했으며, mlir-dialect에 해당하여 master 주 간선에는 포함되지 않습니다. Ascend 하위 저장소의 기본 브랜치는 ascendc_pto이며, 저장소별 스크립트를 main 기준으로 실행하면 빈 결과가 나오므로 이번 회차의 두 건은 해당 기본 브랜치 기준으로 확인했습니다.

조직 수준의 35건 병합과 저장소별 주 브랜치 커밋을 항목별로 대조했습니다: tilelang 12건은 PR 12건과 대응, TileOPs 16건은 PR 16건과 대응, MLIR Ascend 2건, Ascend 하위 저장소 2건, tvm·Hygon·MetaX 각 1건입니다.

RISC-V 4개 출처는 이번에 인용 대조만 수행했으며, PR 인터페이스는 익명 속도 제한으로 사용할 수 없었고 인덱스 페이지 README의 프로젝트 표는 재검증하지 않았으며, 이는 2.5.1에 명시했습니다.

뉴스 측은 Google News 중문·영문, Hacker News, arXiv 세 경로로 재검증했으며, 모니터링 기간 내에 TileLang 관련 보도는 확실히 없었고, 빈 결과를 수집 장애로 추정하지 않았습니다.
