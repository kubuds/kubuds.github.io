오늘의 핵심

이 모니터링 기간의 산출 중심은 「분석기」이지 「생성기」가 아니다. TileFoundry는 사흘 동안 다섯 건을 머지했는데, 그중 세 건은 원래 저자 머릿속에만 존재하던 불변식을 검사 가능한 객체로 만든 것이다. #291은 TMA 복사의 공유 오퍼랜드가 async-proxy 의미론에 진입하도록 하고, 각 TMA 로드마다 mbarrier 워드를 부여하며, 교차 CTA 시나리오에서 「한 CTA는 비동기 프록시 쓰기를 수행하고 다른 CTA는 순서 없이 동일 전역 요소를 읽는」 프로그램을 거부한다. #293은 배치 값 의미론을 정의하여 Split / Broadcast / Varying / Partial 네 가지 상태, B ⊔ V = V 병합 규칙, Reshard의 목표 검증을 계약으로 명문화하고, 더 이상 지원되지 않는 Dynamic 속성을 삭제한다(64개 파일, +1165 ~ -536). #301은 「스케줄이 이전 데이터를 덮어쓰기 전에, 여전히 이전 데이터를 읽어야 하는 영역이 먼저 와야 한다」를 처리하여 순서를 LivenessMetadata.orders에 기록하고, 배열할 수 없으면 AnalysisError를 던진다. 나머지 두 건(#290, #288)은 분석기 자체의 근사치를 수정한 것이다.

두 번째는 파이프라인화다. 72시간 동안 71건의 머지 중 TileOPs가 33건, topa가 15건으로 합계 68%를 차지했으며, 40건은 동일 저자가 제출했다. 같은 기간 세 건의 CI 변경(#2849는 야간 스코어링의 성능 격차 큐를 wiki에 기록, #2852는 Perf Tracker 프로젝트로 동기화, #2856은 따라잡은 연산자를 자동으로 Done으로 이동)과 함께 성능 작업은 이미 「야간 스코어링 → 격차 큐 → 단일 연산자 1라운드 → 리뷰 → 머지」의 폐루프를 형성했다. topa 저장소의 이틀 간 15건(topa hunt, topa round start, topa round status, topa review prepare)이 바로 이 폐루프의 명령줄 셸이다. 효율 향상은 사실이고, 리스크도 사실이다. 단일 저자에 단일 리뷰가 겹치면 파이프라인이 한 사람의 파이프라인으로 퇴화할 수 있다. 72시간 동안 리뷰 중인 PR 96건 중 여전히 59건이 tilelang 메인 저장소에 적체되어 있어, 리뷰 대역폭이 다음 병목이다.

세 번째는 Ascend다. 11-07 하루 동안 한 계정이 14건의 이슈를 열었고, 같은 날 13건의 수정 PR이 리뷰 중이었다. gemm_blockscaled의 위치 인자와 공개 시그니처가 분기되어 policy가 clear_accum으로 이동했고(#3857), vcvt의 bf16→f16 변환에서 round와 sat 파라미터가 뒤바뀌었으며(#3829), vdupv는 알 수 없는 pos를 만나면 조용히 HIGHEST로 매핑하고(#3832), fp4의 T.fill은 SimdVF에서 0으로 나누기 충돌을 일으키며(#3852), kernel 캐시 키에서 ASCEND_NPU_ARCH와 PTO 툴체인이 누락되어 한 아키텍처의 산출물이 다른 아키텍처로 재사용될 수 있다(#3853). 이 결함들의 공통 형태는 「지원 선언, 구현 분기」다. HCU_MCPU_SET에 있는 아키텍처가 C++ 백엔드에 반드시 분기가 있는 것은 아니다. Hygon gfx928의 새 이슈(#35)도 같은 형태다. 반면 같은 기간 일일 테스트 3060건은 전부 통과했는데, 이는 통과율이 이런 조합을 커버하지 못함을 보여준다. 테스트 수량은 형상 조합의 차분 검증을 대체할 수 없다.

뉴스 측에서는 TileLang과 관련된 것이 두 건뿐이다. Moore Threads는 11-06 MTT S5000과 MUSA 기반으로 3조 파라미터 Kimi-K3.1 Pro의 Day-0 적응을 완료했다고 발표했으며, 마이그레이션 경로에 TileLang-MUSA를 명시적으로 나열했다. 다른 하나는 Foro3D가 11-06 전한 기사로, DeepSeek가 Ascend 950DT에서 TileLang 스택으로 8조 파라미터 V5를 훈련할 것이라고 주장했다. DeepSeek 공식은 이 계획을 공개하지 않았으며(현역 최신은 V4.1 시리즈), 소문으로만 기록할 수 있다. RISC-V 4개 출처는 72시간 동안 변화가 없었고, TVM 노선과 MLIR 노선 모두 11-05 이전 인용에 머물러 있다.

1. 핵심 프로젝트 진행 상황

1.1 메인라인: CuTeDSL의 grid 동기화가 매 시작 시 workspace로 변경되어 멀티스트림 동시성이 더 이상 간섭하지 않음(#3868)

11-08 18:00에 병합되었습니다. CuTeDSL의 sync_grid()는 원래 배리어 카운트와 세대를 모듈 수준 전역(__grid_sync_ctr, __grid_sync_gen)에 두었기 때문에, 동일한 kernel이 두 개의 스트림에서 동시에 시작되면 같은 배리어를 공유하게 됩니다. 두 grid의 도착이 합쳐져서, 특정 시작이 자신의 block이 전부 도착하기 전에 통과될 수 있고, 잔여 카운트가 이후 시작을 붙잡아둘 수도 있습니다. H200 NVL에서 단일 실행은 17.4밀리초, 쌍으로 실행하면 17.8밀리초가 나와 cooperative launch가 실제로 동시에 이루어짐을 보여줍니다. 수정 방법은 inline PTX로 cooperative_groups::details::sync_grids를 복제하는 것입니다. 배리어 워드는 드라이버가 각 cooperative launch마다 제공하는 grid workspace의 barrier 필드에서 가져오고, 주소는 %envreg1(상위 절반)과 %envreg2(하위 절반)에서 옵니다. 각 block의 thread 0이 atom.add.release.gpu를 한 번 수행하는데, block 0은 0x80000000 - (nblocks - 1)을 더하고 나머지는 1을 더한 뒤, ld.acquire.gpu로 스핀하며 bit 31이 뒤집히기를 기다립니다. 상태가 시작별로 격리되므로 동시 시작이 서로 영향을 주지 않습니다. 회귀 테스트는 main에서 멈추지만(300초 후 종료됨), 수정 후에는 통과합니다. 작성자는 동시에 CUDA 백엔드를 대조군으로 유지했는데, 이쪽은 계속 정상이었습니다.

출처: https://github.com/tile-ai/tilelang/pull/3868

1.2 메인라인: CuTeDSL 부호 있는 정수 절단을 arith.divsi 의미에 맞게 수정 (#3551)

11-08 07:48에 병합되었습니다. CuTeDSL은 부호 있는 TIR의 DivNode에 대해 Python 바닥 나눗셈을 내보내서, 런타임의 T.truncdiv(A[i], 3)이 -7에서 -2가 아닌 -3을 반환했고, 이후의 floor/ceil 수정이 이 몫을 기반으로 계속 계산하면서 오차가 확산되었습니다. 수정 방법은 부호 있는 스칼라와 벡터에 tl.truncdiv(저수준 MLIR arith.divsi)를 내보내는 것이며, 순수 Python 입력은 정확한 정수 연산으로 처리하고, 벡터 저장 경로와 부호 없는 lowering은 변경하지 않습니다. 회귀 테스트 25건으로 int8/int16/int32/int64, 스칼라와 벡터, 음수 제수, 정수 극값, 그리고 “몫 곱하기 제수 더하기 나머지가 피제수와 같다”를 포함합니다. 보고자는 issue #2973의 논의에서 독립적으로 CPU 참조와 MLIR로 검증했고, 순수 Python %의 경계도 지적했으며, 이 의견이 구현에 직접 반영되었습니다.

출처: https://github.com/tile-ai/tilelang/pull/3551

1.3 메인라인: CuTeDSL에서 63개 파일의 예제 공백을 한 번에 보완, SM120 블록 스케일링 MMA 포함 (#3685)

11-07 18:59에 병합되었으며, +7075에서 -394, 63개 파일로 이번 기간 최대 규모입니다. 추가된 범위에는 warp vote, match와 비트 검색, 블록 프레디케이트 배리어, 명시적 폭의 로드와 스토어 및 캐시 힌트, NaN 전파 min/max, TMA와 cluster 복사(multicast, store_cluster, gather4, scatter4), SM120의 블록 스케일링 MMA(mxf4nvf4)와 이에 대응하는 NVFP4 GEMM 예제가 포함됩니다. 같은 변경에서 warp specialization의 오래된 문제도 수정했습니다. pipeline 앞에 끼어 있던 T.fill이 producer/consumer 분기로 옮겨진 후, 루프나 조건을 사이에 두더라도 매 반복 후 다시 실행되어 해당 라운드의 T.clear 결과를 덮어쓰는 문제였습니다.

5. 트렌드 관찰

첫째, 자동화의 폐루프가 형성되었으나 폐루프의 중심이 「코드 작성」에서 「계약 정의」로 이동했습니다. topa의 15건에는 커널 코드가 한 줄도 없으며 전부 라운드 규칙, 리뷰 체크리스트, PR 본문 형식 및 worktree 정리였습니다. TileOPs의 33건 중 대부분은 「목표 항목에 따라 파라미터 하나 수정, A/B 한 세트 제공」이었고, TileFoundry의 5건은 「배치 동등」「TMA 완료」「덮어쓰기 전 읽기」의 정의를 내리는 것이었습니다. 세 가지를 겹치면 완전한 파이프라인이 됩니다: 야간 벤치마크로 격차 발견, 큐가 연산자 할당, agent가 TileFoundry의 스케줄링 공간에서 수정, 리뷰가 체크리스트에 따라 수치 확인, 병합 후 자동 종료. 이 파이프라인의 산출 효율은 이미 수치로 드러났지만(72시간 71건), 「계약이 충분히 명확하게 작성되었는가」에 극도로 민감합니다. 오늘 #2867이 「목표 항목 미달」로 표시되었음에도 병합되었고, #301이 순서를 정할 수 없을 때 추측 대신 오류를 선택한 것은 모두 계약이 작동하는 모습입니다.

둘째, Ascend의 병목이 「컴파일 가능 여부」에서 「선언과 구현의 일치 여부」로 바뀌었습니다. 14건의 issue 중 「특정 기능 미지원」은 한 건도 없으며, 전부 「지원한다고 선언했으나 구현이 다른 경로로 감」입니다: HCU_MCPU_SET에 gfx928이 있으나 C++에 분기가 없음(Hygon도 동일), T.simd.vcvt 문서에는 int32/int64에서 f16으로 변환이라고 적혀 있으나 구현이 거부, annotate_unlimit_memory의 오류 메시지는 사용자에게 "shared.ss"를 전달하라고 하지만 함수 자체가 거부, gemm_blockscaled의 위치 파라미터와 공개 시그니처의 분기. 이런 결함의 공통 수정 방식은 기능 추가가 아니라 「선언」과 「구현」을 같은 표에 두고 생성적 검사를 수행하는 것입니다. 예를 들어 HCU_MCPU_SET에서 백엔드가 반드시 커버해야 할 아키텍처 목록을 생성하고, intrinsic 레지스트리에서 dtype/비트폭 지원 매트릭스를 생성하는 것입니다. 이를 달성하기 전까지 3060개 전부 통과한 테스트 보고서는 「테스트된 조합에 문제가 없다」만을 의미합니다.

셋째, CuTeDSL은 현재 「기능 커버리지는 CUDA에 근접, 정확성 경계는 아직 수렴하지 않음」 단계에 있습니다. #3685가 한 번에 63개 파일을 보완하며 cluster TMA, SM120 블록 스케일링 MMA, Philox, warp vote 등 CUDA 측에 이미 있던 기능을 채운 것은 기능 면의 정렬이 거의 완료되었음을 보여줍니다. 그러나 같은 모니터링 기간의 결함은 전부 경계에 있습니다: 다중 스트림 동시성 하의 grid barrier(#3868), 부호 있는 정수 나눗셈(#3551), 부호 없는 원자 연산과 부호 없는 버퍼(#3874/#3875/#3876). 이는 모두 「미구현」이 아니라 「구현되었으나 의미가 CUDA와 불일치」입니다. 사용자에게 실질적인 조언은 다음과 같습니다: CuTeDSL 경로는 예제 실행과 개발에 적합하며, 프로덕션 커널은 백엔드를 교체하기 전에 CUDA 백엔드와 원소별 비교 검증을 한 차례 수행해야 하며, 특히 음수 나눗셈, 부호 없는 비교 및 다중 스트림 동시성 시나리오에서 그러합니다.

넷째, 성능 최적화의 기록 방식이 변하고 있다. TileOPs의 이번 PR들의 특징은 각 건마다 ‘어떤 op, 어떤 benchmark, 결과가 기준을 충족했는지, 근본 원인이 무엇인지’를 명확히 적는다는 점이다: #2868은 900444개의 sector 대 501760개의 쓰기의 구체적 숫자를 제시하고, #2869는 16개의 메모리 배치 중 12개가 뒤처진 분포를 제시하며, #2855는 12라운드 워밍업, 각 라운드 10회 호출의 중앙값을 제시하면서 ‘실행 순서 효과를 통제하지 않았다’고 자발적으로 명시한다. 이러한 작성 방식은 ‘기준 미달’도 병합될 수 있게 한다(#2867). 독자가 그것이 가치가 있는지 판단할 수 있기 때문이다. 이에 비해 ‘X% 향상’만 적는 PR은 리뷰 시 kernel이 빨라진 것인지 측정이 변한 것인지 구분할 수 없다.

마지막으로 RISC-V 라인이다. 4개 소스 순회 점검 72시간 동안 변화 없음: kubuds/tilelang-riscv-kubuds의 두 kubuds- 브랜치, RuyiAI-Stack/tilelang-riscv의 MLIR 노선, TongmingLAIC/tilelang-riscv 인덱스 페이지와 TongmingLAIC/tilelang-tpu의 SOPHGO 브랜치 모두 원래 참조에 머물러 있다. 이는 메인라인의 리듬과 대조를 이룬다: GPU 측의 agent화 파이프라인은 이미 반복 주기를 ‘일’ 단위로 압축했지만, RISC-V 측은 여전히 ‘주’ 단위의 수동 추진이다. 두 라인의 격차는 엔지니어링 분량이 아니라, 격차를 자동으로 발견하고 자동으로 검증하며 자동으로 대기열에 넣는 회로가 있느냐에 있다.
