오늘의 핵심: SM89에서 하루에 두 건의 GEMM이 정식 반영되고, TileOPs 사양 및 벤치마크 커버리지가 205/205로 동시 보고되며, 메인 저장소가 Windows ARM64를 CI에 포함함 (10-19)

이 모니터링 기간의 호스트 측은 여전히 중국 시간 야간에 활동이 집중되었다. 조직 내 병합 36건 중 TileOPs가 19건을 차지했으며, 그중 SM89(Ada급)의 블록 스케일링 FP8 그룹 GEMM과 INT8 W8A8 GEMM이 같은 날 구현 완료되었고, 5개의 신규 연산자와 함께 MLA 페이징, KV 캐시 쓰기, QK-Norm-RoPE 융합, 토큰별 양자화 RMSNorm을 한 번에 보완했다. 조직 규격 통계 브랜치는 곧바로 「구현 완료 205/205, 벤치마크 완료 205/205」로 갱신되었으며, 이는 연산자 라이브러리가 자체 기술한 규격 커버리지와 벤치마크 커버리지가 동시에 최대치에 도달했음을 의미한다. 메인 저장소 tilelang은 11건을 병합했으며, 가장 비중 있는 것은 Windows ARM64를 릴리스 파이프라인에 포함시킨 것(12개 파일, CUDA 13.4 arm64 설치 스크립트와 clang 호환 헤더)이고, 그 외에 정확성 수정 2건(공유 버퍼상의 T.cumsum, call_extern 쓰기 표기)과 디버깅 인프라 개편 1건(lower trace의 호스트와 디바이스 소스 분리)이 있다. 백엔드 측에서는 Ascend가 호스트 연산자와 디바이스 커널을 msprof 하에서 대응시켰고, Hygon의 2건은 레지스터 파이프라인과 상수 K 주소 지정을 보완하는 중이며, TileFoundry는 처음으로 Qwen 프리필 예제를 Apple M2 Pro의 AMX 유닛에서 128 token까지 실행하는 데 성공했다.

1. 핵심 프로젝트 진행 상황

1.1 메인 저장소: Windows ARM64 CI 진입, CUDA 13.4 arm64 패키지 설치와 clang 호환 레이어(#2962)

이 커밋은 Windows on ARM을 정식 빌드 타깃으로 릴리스 파이프라인에 연결한다. PowerShell 설치 스크립트를 신규 추가하여 NVIDIA 프리릴리스 채널에서 CUDA 13.4의 windows_arm64 로컬 설치 패키지를 받아 고정 경로에 배치하고, CMake의 FindPipCUDAToolkit 모듈과 windows_arm64_clang_compat.h 호환 헤더를 신규 추가하여 ARM64에서 MSVC 툴체인의 헤더 파일 및 내장 기능 차이를 해결하며, pyproject와 두 개의 requirements를 동기적으로 조정하고 레이아웃 모듈과 MSVC 보조 모듈을 변경하여 새 플랫폼에 적응시킨다. 총 12개 파일, 356줄 추가, 45줄 삭제. 그동안 조직 측은 ROCm과 Ascend 양쪽을 연속으로 보완해 왔으며, 이 커밋은 Windows ARM64를 세 번째 비 x86 전달 면으로 추가한 것으로, Snapdragon X 시리즈 노트북으로 로컬 커널 개발을 하는 사용자에게 직접적인 사용성 개선이다.

출처: tile-ai/tilelang#2962 (10-19)

1.2 메인 저장소: 공유 버퍼상의 T.cumsum이 warp 특수화 하에서 스레드 오프셋 보완(#3536)

warp 특수화가 생산자와 소비자를 서로 다른 warp에 배분한 후, 스캔 계열 프리미티브가 공유 버퍼상에서 계산한 스레드 번호가 여전히 전체 CUDA 블록 기준으로 계산되어 cumsum의 행 귀속이 어긋났다. 이 변경은 CUDA와 HIP 두 스캔 템플릿에 thread_offset 파라미터를 도입하여 하위 파라미터의 스레드 하한(thread_bounds의 최솟값)에서 전달받고, 템플릿이 이를 기반으로 lane과 행 인덱스를 다시 정렬한다. 백엔드 범용 구현과 Python 측 테스트 케이스도 동기적으로 갱신되었으며, 총 4개 파일, 101줄 추가, 38줄 삭제. 이러한 문제는 실제로 warp 특수화를 활성화하고 버퍼가 공유 메모리에 위치할 때만 노출되며, 규모화된 사용 이후 역류된 경계 조건에 속한다.

출처: tile-ai/tilelang#3536 (10-19)

1.3 메인 저장소: call_extern의 로우 data 변수를 보수적으로 쓰기로 표기(#2618)

읽기 전용 파라미터 표기는 원래 별칭 분석으로 버퍼가 쓰였는지 판단했으나, 외부 호출(call_extern)이 로우 포인터를 통해 쓸 때 분석이 쓰기 동작을 보지 못해 읽기 전용으로 오판되어 상수 폴딩 또는 조기 재사용이 발생했다. 이 변경은 해당 pass에서 call_extern을 특별히 식별하여 그 로우 데이터 변수를 일괄적으로 보수적으로 쓰기 완료로 표기하고, 「call_extern이 출력 버퍼에 쓰기」하는 표현을 커버하는 69줄의 테스트 케이스를 추가했다. 방향상으로는 최적화를 덜 하더라도 잘못된 최적화는 하지 않는다는 것으로, 최근 메인 저장소의 정확성 수정 배치와 궤를 같이한다.

출처: tile-ai/tilelang#2618 (10-19)

1.4 메인 저장소: lower trace가 호스트와 디바이스 소스를 분리, 편집 가능한 베이스라인으로 변경(#3496)

디버깅 도구 lower trace는 원래 생성 소스 한 부만 출력하여 호스트 측 래핑과 디바이스 측 커널이 섞여 있어 한 곳을 수정해도 되돌리기 어려웠다. 이 변경은 양측을 독립 산출물로 분리한다. 디바이스 측은 codegen_device.cpp 및 그 .original 베이스라인과 .latest 최신 버전을 출력하고, 호스트 측은 호스트 코드 생성 실행 시 codegen_host.cpp와 동일 구조의 베이스라인 파일을 별도로 출력하며, report.html은 최근 실행을 가리키는 소프트 링크로 연결된다. 문서도 편집 및 재컴파일 흐름을 동기적으로 개편했으며, 총 6개 파일, 121줄 추가, 63줄 삭제.

출처: tile-ai/tilelang#3496 (10-19)

1.5 메인 저장소: Autotuner profiler 파라미터 전달, ROCm FP4 상수 출력 및 CI 유지보수 2건 (#3337 / #3548 / #3565 / #3567)

#3337은 단 3줄이지만 자동 튜닝의 측정 기준을 수정한 것이다. 데코레이터의 warmup, rep, timeout이 이전에는 튜너에 전달되지 않아 사용자가 데코레이터에서 이 세 파라미터를 바꿔도 실제로 적용되지 않았는데, 이제 파라미터를 그대로 전달한다. #3548은 ROCm 측 FP4(e2m1) 부동소수점 상수 출력을 보완한 것으로, 해당 타입은 원시 바이트로만 생성할 수 있기 때문에 디바이스 측에서 헬퍼 함수를 통해 float32에서 변환하여 상수를 생성하도록 변경해 HIP 코드 생성 오류를 방지한다. 나머지 2건은 유지보수성 변경으로, cibuildwheel 버전을 4.2에서 4.3으로 올리고 ROCm 라인에 CodeRabbit 리뷰어 1명을 추가한 것이다.

출처: tile-ai/tilelang#3337, #3548, #3565, #3567 (10-19)

2. 멀티 백엔드 적응 (Ascend / MetaX / Hygon / Moore Threads)

2.1 Ascend: 호스트 연산자와 디바이스 커널을 msprof에서 연관시키기 (#3321)

Ascend 측 profiler는 이전에 디바이스 커널 소요 시간만 보고할 수 있었고 호스트 연산자와 커널 간에 대응 관계가 없어 자동 튜닝이 얻은 샘플을 특정 호출로 귀속시킬 수 없었다. 이번 변경은 네이티브 profiling 채널을 추가한다. 빌드 시 CANN의 profiling 헤더를 탐지하며(msprof와 profiling 두 설치 레이아웃 호환), 설치되어 있으면 활성화하고 없으면 건너뛰며 사용자 대상 컴파일 스위치를 도입하지 않는다. 런타임 측에는 ascend_profiling.h와 호스트 측 profile 모듈을 보완하여 호스트 연산자의 발행과 디바이스 커널 실행을 호출 순서대로 대응시키고, 그룹 컴파일 경로가 동일한 보고 체계를 재사용하도록 했다. 총 13개 파일, 676줄 추가, 13줄 삭제로 Ascend 라인의 측정 능력에 대한 구조적 보완이다.

출처: tile-ai/tilelang#3321 (10-19)

5. 트렌드 관찰

5.1 SM89가 새 연산자의 기본 착지점이 되다

어제 TileOPs의 중점은 여전히 Hopper의 W4A8과 SM90 클러스터 협업이었으나, 이번 모니터링 기간 두 건의 새 GEMM 모두 SM89를 최초 목표로 삼았고 PR에서 SM90 실행 결과를 주장하지 않음을 명확히 선언했다. Ada급 그래픽카드(L40S, 4090류)는 국내 개발자들이 보유한 주력 하드웨어로, 저정밀 GEMM을 먼저 SM89에 착지시키는 것은 연산자 라이브러리가 ‘획득 가능성’을 기준으로 우선순위를 정하기 시작했음을 의미하며 단지 ‘피크 성능’만이 아니다.

5.2 선형 어텐션이 ‘chunk당 한 번의 행렬 곱 + SM 웨이브별 전략 선택’으로 고정되다

GLA, GDN, KDA, DeltaNet 네 라인은 이번 기간 총 8건의 성능 변경을 이루었으며, 수법은 두 가지로 수렴된다: chunk 체인의 행렬 곱을 블록당 한 번으로 압축하는 것, 그리고 SM이 수용할 수 있는 warp 그룹 수에 따라 그룹 솔버를 사용할지 단일 warp를 사용할지 결정하는 것. 이러한 ‘먼저 웨이브를 계산한 뒤 커널을 선택’하는 방식은 이전에는 수기 GEMM 라이브러리에서만 보였으나, 이제 연산자 라이브러리의 기본 경로로 진입했다.

5.3 TileFoundry, CUDA를 벗어나다: Apple AMX와 Qwen 프리필

TileFoundry는 줄곧 ‘agent용 연산자 공장’으로 자리매김했으나, 이전의 모든 예시는 NVIDIA에서 이루어졌다. 이번 기간 AMX 지원과 Qwen 전체 모델 프리필이 M2 Pro에서 실행됨으로써, 그 스펙·배치·스케줄 3계층 추상이 CUDA에 묶여 있지 않고 Apple의 행렬 보조 프로세서로 내려갈 수 있음을 보여준다. 이 라인이 계속된다면 TileFoundry의 자리매김은 ‘TileLang의 프론트엔드’에서 ‘크로스 가속기 스펙-투-커널 컴파일러’로 바뀔 것이다.

5.4 관측 가능성이 컴파일러 하드닝의 주축이 되다

이 모니터링 기간의 세 가지 변경은 같은 목표를 가리킨다. 컴파일 산출물을 측정 가능하고 원인 추적이 가능하게 만드는 것이다. lower trace는 호스트와 디바이스 소스 코드를 분리하여 저장하고, Autotuner는 데코레이터 파라미터를 실제로 측정까지 전달하며, Ascend는 호스트 연산자와 디바이스 커널을 msprof 아래에서 대응시킨다. 연산자 측면이 거의 채워진 상황(규격 통계가 이미 205/205로 보고됨)에서, 남은 격차는 연산자를 추가하는 것이 아니라 측정을 통해 찾아야 한다.

5.5 Ascend 연산자 라이브러리가 대화 모델 전용 연산자로 전환

Ascend의 리뷰 대기 큐에 GLM-5.3의 kpool 압축, KDA와 indexer의 역방향, situ_glu 및 그 그래디언트가 등장했는데, 이들은 범용 연산자가 아니라 특정 대화 모델 구조의 구성 요소다. 지난주 PTO 자동 벡터화와 함께, Ascend 라인의 작업 중심은 「TileLang을 Ascend에서 실행하기」에서 「국내 주류 모델의 핵심 연산자를 먼저 Ascend에서 구현하기」로 옮겨갔다.
