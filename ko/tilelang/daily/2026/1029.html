오늘의 핵심

오늘 모니터링 기간의 중심은 Ascend 측입니다. tilelang-mlir-ascend는 Ascend 910(A2/A3)의 NPUIR 백엔드 전체를 메인라인에 병합했습니다. 55개 파일, 21,490줄 추가의 단일 커밋으로, Python 측은 tilelang/ascend910 패키지(backend / adapter / codegen / compiler / execution_backend / jit / pipeline / runtime / target 및 language 아래의 kernel, copy, gemm, npuir 방언 면)이고, C++ 측은 src/ascend910/target 아래의 개발자·전문가 두 가지 emitter 세트, op 레이어와 LowerNpuirBlock, NpuLoopVectorize, RewriteFDivToMul 세 개의 pass이며, 런타임에는 npu_launcher.h와 npu_utils를 보강했고, 설치는 install_npuir.sh를 사용하며, target 별칭은 ascend910 / ascend-910 / a2 / a3 / npuir를 허용합니다. 작성자가 제시한 검수 결과는 저장소 자체의 두 가지 테스트 세트로, pytest testing/npuir 504개 항목 전부 통과, examples 72개 예제 중 71개 통과 및 0 타임아웃 0 오류였으며, 유일하게 실패한 deepseek_v32/fp8_lighting_indexer.py는 구 백엔드에서도 동일 머신에서 동일하게 실패하여 환경 및 허용 오차 문제입니다. 두 번째 커밋은 구 백엔드와의 동작 차이를 항목별로 정렬한 것으로, 핵심은 bf16 합법화(HIVM이 bf16 피연산자를 받지 않으므로 fp32로 계산한 뒤 명시적으로 변환)와 동적 extent의 copy 하강입니다.

TileOPs는 오늘 7건을 병합했으며, 두 가지 주요 라인 모두 성능 측입니다. 선택기는 더 이상 manifest에 밀착해 피팅하지 않고, 바쁜 시간(device_busy_ms) 기준으로 160개의 밀집 shape, 60개의 m 9–32 shape, 264개의 m≤8 shape로 재캘리브레이션하며, softmin 기대 로그 리그릿으로 좌표 하강을 수행합니다. 엔드투엔드 바쁜 시간 리그릿은 홀드아웃 manifest에서 5.79%에서 0.48%로, m≤8 홀드아웃 세트는 14.18%에서 1.79%로 낮아졌습니다. GEMM 측에는 coop2_swap이 추가되었는데, 비 NT 레이아웃을 전치된 영속 커널로 바꾸고, 두 소비자 warpgroup이 각각 128행을 보유하며, 꼬리 쓰기는 stmatrix.trans와 TMA 전치를 거쳐 되돌려 기록하고, 넓은/좁은 tile 혼합 배치(예: 2112 = 13×160 + 32를 160 너비 tile과 128 좁은 tile로 분할)를 지원하며, 2112×7168×4096 TN이 195.3마이크로초에서 175.3마이크로초로, 동일 머신의 다른 H200에서는 174.3에서 158.5마이크로초로 읽혀, 모두 QuACK의 187.9와 167.0마이크로초를 앞섰습니다.

리덕션 측은 같은 날 먼저 깨졌다가 수정되었습니다. 오전 #2787은 int32 키로 extrema 리덕션의 NaN 전파를 구현하고, #2788은 병렬 cumsum의 행 tile을 변경했으며, 두 커밋 모두 07시 전후에 반영되었고, 이후 #2790과 #2792가 각각 두 회귀를 정리했습니다. cumsum은 시드 기준 분할, 두 번의 발행으로 변경되었고((8,65536) float32가 12.75마이크로초에서 5.18마이크로초로, 동시에 메인라인의 65535 tile 초과 발행 실패도 수정), extrema는 PTX의 max.NaN / min.NaN으로 변경되고 16바이트 비정렬 벡터 행에서는 별도 커널을 사용합니다(amax (2048,4096) bf16이 8.352마이크로초에서 6.976마이크로초로 복귀, FlagGems보다 빠름). 이러한 “같은 날 도입 후 수정”의 리듬은 TileOPs의 야간 벤치마크가 회귀를 당일 차단하고 있음을 보여줍니다.

1. 핵심 프로젝트 진행

1.1 메인 저장소: 스칼라 읽기의 인덱스 계수가 더 이상 lane 수에 섞이지 않으며, 행 너비 32768 이상의 컴파일 크래시 종료(#3453)

10-28 11:06에 병합되었으며, 단일 파일 +8/-5입니다. 벡터화 방식으로 전체 행을 읽으면서 동시에 인덱스로 해당 행의 단일 요소를 읽는 kernel이, 행 너비를 65536으로 나눈 나머지가 32768 이상일 때 InternalError: Can’t fetch the lanes of a scalable vector를 컴파일 오류로 발생시킵니다. 근본 원인은 VectorTypeAccessChecker::OnArrayAccess에 있습니다. 이는 스칼라 읽기를 access_dtype.with_lanes(me->coeff)로 기록하는데, me->coeff는 인덱스를 읽는 모듈러스 계수이며 x[row, 0]의 경우 행 너비입니다. DataType의 lane 수는 16비트에 불과하고 int16으로 다시 읽히므로, 32768에서 65535는 확장 가능한 벡터로 간주되어 lanes()가 get_preferred_dtype에서 바로 오류를 던지고, 더 넓은 배수는 조용히 랩어라운드됩니다. 수정 방법은 계수를 별도의 int64_t에 저장하고, 호환성 판단에서 이를 사용해 모듈러스를 취하며, 스칼라 읽기의 dtype은 요소 타입만 유지하는 것입니다. 이 결함의 원래 트리거 시나리오는 TileOPs의 GroupNorm으로, Stable Diffusion의 40960과 163840 두 그룹 너비 모두에서 발생합니다. 검증은 두 번의 wheel 빌드 비교로 수행했습니다. 메인 브랜치는 32768과 40960 두 너비에서 컴파일 실패했고, 본 커밋은 모든 테스트 너비에서 빌드됩니다.

출처: https://github.com/tile-ai/tilelang/pull/3453

1.2 메인 저장소: 배치 all-reduce가 스칼라 분기에서 스레드 범위를 해석하도록 하여, batch>1일 때 2048개 출력이 전부 잘못되는 문제 수정 (#3341)

10-28 05:46에 병합되었으며, 2개 파일 +170/-8입니다. 스칼라 all-reduce 분기는 호출을 발행하기 전에 참여 스레드의 범위를 먼저 해석하지만(reducing_threads가 32보다 크고 대상이 명명된 펜스를 지원하면 ResolveAllReduceThreadRange를 사용), 배치 분기는 블록 경계를 오프셋과 펜스 너비로 직접 사용합니다. 감소 스레드가 [32, 96)처럼 0에서 시작하지 않는 부분 범위일 때, 배치 호출은 0번 스레드부터 인덱싱하고 전체 블록을 기준으로 펜스를 동일하게 적용하므로, 비참여 스레드의 초기화되지 않은 레지스터가 감소에 포함됩니다. batch=1은 정상이지만, batch=2에서는 동일한 kernel에서 2048개 출력 요소가 전부 잘못되며 최대 절대 오차는 1083이고 어떠한 진단도 없습니다. 수정 방법은 배치 분기가 스칼라 분기와 동일한 해석을 사용하도록 하고, 해석된 오프셋과 범위를 MakeBatchAllReduce에 전달하며, 작업 공간 stride는 여전히 블록 크기를 유지하는 것입니다. 새 테스트는 동일한 kernel에서 batch=1과 batch=2를 실행하고 torch 참조와 비교합니다.

출처: https://github.com/tile-ai/tilelang/pull/3341

1.3 메인 저장소: SIMT 원자 영역의 형상 검증 추가, 범위를 벗어난 영역은 컴파일 시점에 거부 (#3465)

5. 추세 관찰

Ascend 측의 추진 방식은 이틀간 이미 분명해졌다: 메인 저장소는 시간 단위로 소규모 수정(캐시 키, 레지스터 위상)을 병합하고, 전용 저장소 mlir-ascend는 2만 행 규모의 병합 한 번으로 910의 NPUIR 경로를 피처 브랜치에서 메인라인으로 옮겼으며, tilelang-ascend는 PTO와 AscendC 듀얼 백엔드의 기존 리듬에 따라 문서와 연산자를 보완하고 있다. 세 곳의 리듬은 다르지만 같은一件事를 가리킨다: 910의 컴파일러 경로가 “돌아간다”에서 “검수 가능”으로 전환되고 있으며, 504항목 자체 테스트와 71/72 예제가 이번에 제시된 검수 기준이다. 주목할 점은 심사 대기열에서 a2a3의 스케줄러 마이그레이션이 100개 파일을 차지한다는 것으로, 다음 단계의 변동량이 연산자 계층이 아니라 스케줄링 계층에 있음을 보여준다.

성능 측의 관전 포인트는 측정 기준 자체에 있다. TileOPs의 이번 두 건은 선택기와 GEMM의 결론을 모두 바쁜 시간(device_busy_ms) 기준으로 옮겼고, 같은 PR에서 단일 호출과 연속 호출의 차이를 제시했다: 단일 호출 기준에서는 본 구현이 QuACK를 앞서지만, 연속 호출·전력 상한 훈련 시나리오에서는 10개 대형 행 중 6개가 뒤처진다. 이는 “어떤 행이 몇 마이크로초 빨라졌는가”보다 더 중요한 신호인데, 훈련은 실제로 연속 호출이기 때문이다. #2791이 이 사안을 별도 항목으로立项한 것은 팀이 기준 문제를 벤치마크 편차로 포장하지 않고 제품 문제로 다루고 있음을 보여준다.

엔지니어링 위생 측면에서 오늘 기록할 만한 세 가지: 첫째, 같은 배치 내 자해와 자수정(#2787/#2788 오전 병합, #2790/#2792 오후 회수)은 야간 벤치마크의 안전망이 작동하고 있음을 보여주지만, 리덕션 코드의 의미 경계가 여전히 취약함도 보여준다. 둘째, without_kernel_cache()의 의미론적 허점(#3699)이 마이그레이션 과정에서 발견되었는데, 프로세스 내 2계층 캐시가 CacheState를 사용하지 않아 테스트가 콜드 컴파일이라고 착각하면서 실제로는 구 kernel을 가져오는 문제로, 이런 결함은 “우리 테스트는 모두 통과”를 무의미하게 만든다. 셋째, SM120에서 13개 예제 실패(#3701)는 예제가 Hopper 크기를 하드코딩한 문제를 드러냈으며, Blackwell 설치량이 늘어나면 이러한 “예제는 제품이 아니다” 부채가 반복적으로 계상될 것이다.
