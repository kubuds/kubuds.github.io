오늘의 핵심

이 모니터링 기간 조직 내에는 머지가 6건뿐으로, 이전 회차의 9건에서 다시 3분의 1 줄었지만, 숫자보다 구조가 더 주목할 만하다. 6건 중 3건이 메인 저장소에 있으며 모두 Ascend에 속하고, CUDA나 CPU는 단 한 건도 없다. 가장 큰 변경은 #3516(20개 파일, +1549/−182)으로, tvm_ffi를 pto 타깃의 기본 실행 백엔드로 승격시켰다. 이전에는 target="pto"가 Cython 런처를 거쳤으나, 이제 execution_backend="auto"가 tvm_ffi로 직접 해석되며, 공유 host codegen이 MakePackedAPI와 C host를 생성하고 Ascend 런타임이 aclrtLaunchKernelWithHostArgs로 PTODSL이 컴파일한 aibin을 시작한다. 경로는 AscendC 커널과 동일하다. 이에 수반되는 것은 모듈 수준 툴체인 콜백 한 곳이다. 전체 PTODSL 모듈이 device build 단계 내에서 한 번에 컴파일되며(ptodsl → ptoas → bisheng fatobj-link → .aicore_binary 추출), 결과는 ptoas 파라미터, ptoas 버전 및 CANN 아이덴티티를 기준으로 캐시 키에 들어간다. 기존 경로는 execution_backend="pto"로 유지되며, 두 산출물은 비트 단위로 일치한다.

두 번째 변경인 #3776은 솔버 측의 조 tightening이다. AutoSchedule은 원래 고정된 주기 하한으로 이분 탐색을 시작했으나, 이번에는 세 가지 필요 조건의 최댓값을 취하도록 변경되었다. 단일 태스크 경계는 각 태스크 시작 간격의 최댓값을 사용하고, 리소스 그룹 경계는 쌍별 충돌 태스크를 잔여값으로 정렬한 뒤 인접 차이와 처음·끝 차이로부터 주기가 각 시작 간격의 합 이상임을 도출하며, 자기 의존 경계는 S_u - S_u >= wait - d*P로부터 주기가 ceil(wait/d) 이상임을 역산하고, 버전 관련 거리는 num_stages로 환산한다. 추가적인 하한 탐색은 도입되지 않았고 스케줄링 모델도 변경되지 않았다. 실증은 Ascend 950PR, CANN 9.3.0 주간 버전에서 이루어졌다. 컴파일 캐시를 끄고 1회 워밍업 후 3회 측정을 교차 반복한 결과, 모든 Ascend 예제가 컴파일을 통과했고 스케줄링 결과는 변하지 않았으며, Z3 솔버 단계 누적 소요 시간이 10.04% 감소했다.

세 번째 사안은 메인 저장소에 없다. Hygon의 분산 3종 세트 #36(6개 파일, +2022/−0)은 16:20에 main이 아닌 distributed 브랜치에 머지되었으며, 내용은 Block-Push 버전의 GEMM + AllReduce, Block-Push 버전의 GEMM + ReduceScatter, Block-Pull 버전의 AllGather + GEMM 세 가지 연산-통신 융합 연산자이며, 성능 데이터와 구현 설명은 README에 작성되어 있다. 같은 날 #37이 HCU의 ds_read_vector Alt2와 LDS 레이아웃 추론을 열었다. 이 라인은 10-29의 push-wave reduce-scatter 예제에서 시작해 융합 연산자 목록까지 이어졌으며, Hygon 저장소가 처음으로 체계적으로 분산을 다루는 사례이다.

네 번째 사안은 품질 측의 집중적 폭발이다. 모니터링 기간 내 35개의 신규 이슈 중 30개가 메인 저장소에 속하며, 그중 26개가 Ascend를 직접 겨냥한다. 두 계정이 오후부터 심야 사이에 각각 십여 건을 보고했으며, 형태가 매우 일관된다. 즉 “잘못 실행된” 것이 아니라 “마땅히 오류를 내야 하는데 조용히 통과한” 것이다. T.Kernel이 0 또는 음수 block 수를 받아들이고, T.alloc_l1이 2 GiB 할당을 받아들이며, T.Persistent가 음수 wave와 stage를 받아들이고, T.unroll이 −1을 받아들여 #pragma unroll -1을 내보내며, 음수 텐서 차원이 컴파일러를 직접 붕괴시킨다. 또 다른 그룹은 의미 불일치이다. hf32의 nearest_zero가 NEAREST_AWAY로 컴파일되고, GEMM 입력 dtype 테이블과 codegen이 양방향으로 불일치하며, reduce_bitand 계열이 Ascend 템플릿에 정의되지 않은 타입을 내보내고, 동형 ND→NZ 스캐터가 마스크 카운트가 롤백되지 않아 무한 루프에 빠진다. 이 이슈들은 대부분 여전히 열려 있으나, 당일 이미 VMI mask 검증, SIMD fill 복구 등의 대응 수정이 리뷰 중이다.

1. 핵심 프로젝트 진행 상황

1.1 Ascend: PTO 타깃 기본 실행 백엔드를 tvm_ffi로 전환, 전체 모듈을 디바이스 빌드 단계에서 컴파일 및 캐시(#3516)

#3516(20개 파일, +1549/−182)은 이번 회차 최대 변경이다. 변경의 실질은 pto 타깃을 “전용 Cython 런처”에서 “AscendC와 동일한 host 경로”로 이전하는 것이다. target="pto"에 execution_backend="auto"를 설정하면 tvm_ffi로 해석되며, 공유 host codegen이 MakePackedAPI와 C host 빌드를 담당하고, Ascend 런타임 모듈이 aclrtLaunchKernelWithHostArgs로 PTODSL이 생성한 aibin을 시작한다.

디바이스 빌드 측에 모듈 수준 툴체인 콜백을 새로 추가해 전체 PTODSL 모듈을 한 번에 컴파일한다. ptodsl 프런트엔드 산출물, ptoas 하강, bisheng의 fatobj 링크, 그리고 .aicore_binary 추출까지 아우르며, 산출물은 aibin으로 캐시된다. 캐시 키에는 ptoas 파라미터, ptoas 버전과 CANN 아이덴티티가 함께 반영된다. 이 점이 핵심인데, 이전에는 이런 키에서 툴체인 버전이 빠져 있어 CANN 업그레이드를 건너뛸 때 오래된 산출물이 적중했다.

검증 범위는 넓게 펼쳐져 네 그룹의 테스트가 추가되었다. auto가 tvm_ffi로 해석되는지, 피호출 측이 출력을 할당하는지, 동적 형상과 동적 출력, 다중 디바이스 커널, 동적 공유 메모리, cube/vector 혼합 GEMM, source accessor, 내보내기 라이브러리, 호스트 측 루프 기동과 호스트 측 프로파일링 구간을 다룬다. 또한 등가성 테스트가 tvm_ffi와 기존 pto의 결과를 vecadd, 다중 커널, 동적 공유 메모리 세 가지 커널에서 비트 단위로 비교한다. 두 그룹의 캐시 테스트는 각각 바이너리 캐시와 커널 캐시를 커버하며, 캐시 적중 시 툴체인을 건너뛰는지, 손상된 항목이 오류를 던지는지, 그리고 완전히 새로운 프로세스에서 적중하는지를 검증한다. 기존 경로는 계획대로 유지되며, 커버리지가 확인된 후에 은퇴한다.

1.2 Ascend: AutoSchedule이 세 가지 필요조건으로 주기 하한을 조여 Z3 풀이 시간 10.04% 감소 (#3776)

#3776(1개 파일, +20/−1)은 초기값만 바꾸고 알고리즘은 바꾸지 않는다. 기존의 이분 탐색은 고정된 하한에서 시작했지만, 이제는 먼저 세 가지 필요조건을 계산한 뒤 최댓값을 취한다. 단일 태스크 경계는 각 태스크의 시작 간격에 대한 하드 하한을 유지한다. 리소스 클리크 경계는 쌍별 리소스 충돌의 클리크를 대상으로, 태스크 잔여값을 오름차순으로 정렬한 뒤 인접 차의 제약과 처음·끝 차의 제약을 더해 주기가 클리크 내 시작 간격의 합보다 작지 않다는 것을 도출하며, 클리크 자체는 각 태스크를 시드로 삼아 탐욕적으로 열거한다. 자기 의존 경계는 S_u - S_u >= wait - d*P에서 역으로 풀며, 버전 관련 거리는 num_stages를 상한으로 한다.

실증 환경은 매우 구체적으로 기술되어 있다. Huawei Ascend 950PR, CANN 9.3.0의 20261009.01 주간 버전, 컴파일 캐시 비활성화, 각 구성마다 1회 워밍업 후 3회 측정을 교대로 수행했다. 결과는 두 가지다. Ascend 예제가 모두 컴파일을 통과했고 스케줄 결과가 변경 전과 동일하며(하한만 조였고 해는 바꾸지 않았음을 의미), Z3 풀이 단계의 누적 소요 시간이 10.04% 감소했다. 이분 탐색의 상·하한과 풀이 상태 처리는 변경되지 않았고, 추가적인 하한 탐지 절차도 도입되지 않았다.

이런 변경이 업스트림에 주는 가치는 단일 지점 성능이 아니라, 스케줄러의 풀이 시간이 연산자 규모에 따라 증가할 때 이분 탐색 시작점의 낭비가 선형으로 증폭된다는 점에 있다. 필요조건을 초기값에 반영하는 것은 매 풀이마다 무의미한 구간을 하나씩 줄여주는 것과 같다.

출처: https://github.com/tile-ai/tilelang/pull/3776

1.3 Ascend: 정수 원자 연산이 signless 캐리어에 적응, 12개 PTO 케이스로 32비트와 64비트 커버 (#3794)

#3794(4개 파일, +52/−6)는 #3512의 후유증을 고친다. 그 변경은 부호 있는 정수 타입을 signless의 i32/i64에서 si32/si64로 바꿨는데, PTO의 원자 인터페이스는 signless 캐리어를 요구하기 때문에 SIMT 커널의 정수 add/min/max 원자 연산이 곧바로 컴파일 실패했다.

회귀 케이스는 testing/ascend/language/simtvf 아래의 test_simtvf_atomics.py에 위치하며, 32비트와 64비트의 add/min/max, 음수 피연산자, 이전 값 반환, 32비트를 초과하는 값, 그리고 상위 비트가 1인 부호 없는 초기값을 커버한다. 새로 추가된 12개 PTO 케이스는 Ascend에서 모두 통과했다. 같은 배치로 병합된 #3792는 같은 계열 문제의 다른 측면을 고친다. T.atomic_add/max/min이 부호 있는 입력 때문에 PTO에서 컴파일 실패하는 문제다.

K3의 두 가지 Q1 대조는 이전에 오래된 Triton 산출물을 사용했는데, 해당 산출물은 −128에 대한 부정 연산에서 오버플로가 발생했습니다. 경계 입력에서 −2048이 나왔으나 올바른 결과는 0이어야 합니다. 정확한 I8 리덕션을 수정한 공유 컴파일러가 재생성된 후, 두 프런트엔드의 산출물 모두 해당 입력을 통과합니다. triton_historical_us는 기존 소요 시간을 유지하고, triton_control_note는 수정된 비교를 표시합니다. 이는 이번 호에서 유일하게 「대조 자체에 오류가 있었다」는 공개로, 어떤 점수보다도 이 벤치마크가 재현성을 진지하게 다루고 있음을 잘 보여줍니다.

이 issue들의 공통점은 “결과가 틀렸다”가 아니라 “통과해서는 안 되는데 통과했다”는 것입니다. 매개변수 검증 부류: T.Kernel이 0 또는 음수 block 수를 허용, T.Persistent가 음수 wave_size와 num_stages를 허용, T.Pipelined가 음수 num_stages와 잘못된 order/stage 메타데이터를 허용, T.unroll이 −1을 허용하고 #pragma unroll -1을 출력, 루프 생성자가 0 또는 음수 extent를 허용, 음수 텐서 차원이 컴파일러를 직접 크래시(Python 예외가 아닌 네이티브 크래시), T.alloc_l1이 용량 검사 없이 2 GiB 할당을 허용. 의미 불일치 부류: hf32의 nearest_zero가 NEAREST_AWAY로 컴파일, GEMM 입력 dtype 테이블과 codegen의 양방향 불일치, reduce_bitand/bitor/bitxor가 Ascend 템플릿에 정의되지 않은 타입을 출력, batch reduction이 배치 오버로드가 없는 스칼라 AllReduce 진입점으로 퇴화, GM에서 L1 복사의 pad_value가 0만 허용하는 L1 fill로 라우팅, 동형 ND에서 NZ로의 산포가 마스크 카운트 미반환으로 인해 무한 루프에 빠짐, partial-VL 행이 존재하지 않는 PAT_VL<N> 패턴을 생성. 툴체인 부류: vsts_pack_quarter에 16비트 분기가 없어 b16 벡터의 PK4_B32 저장이 조용히 폐기, 모듈 직렬화가 device source를 잃어 캐시된 커널이 시작 실패 시 소스를 조회할 수 없음, msprof 백엔드 자동 튜닝이 워커 스레드에서 signal.signal()을 호출하여 반드시 실패.

이 무리는 산발적인 불평이 아니라 형태상 조직적인 감사에 가깝다. 동일 계정이 30분 이내에 주제별로 연속 제출했고, 제목은 통일되게 「[BUG] Ascend: …」에 근본 원인 요약 한 줄을 붙였다. 업스트림에 대한 의미는 Ascend 프런트엔드의 ‘건전성’ 공백이 한꺼번에 수면 위로 드러났다는 것이다. 매일 3060개 테스트가 전부 통과한다고 해서 불법 입력이 거부된다는 뜻은 아니다. 테스트가 커버하는 것은 합법 경로이기 때문이다.

4.2 심사 중인 수정과 감사의 호응: VMI mask 검증, SIMD fill 복원, E4M3 ND/NZ 복사 (11-11)

당일 업데이트된 심사 중 PR 중에는 위의 공백에 정확히 대응하는 것이 있었다. #3861과 #3917은 같은 사안의 두 건이다. VMI 단항 및 벡터-스칼라 팩토리가 이전에는 mask에 대해 ‘있는지 없는지’만 확인하고 dtype과 채널 수는 확인하지 않았기에, 일반 벡터를 술어로 넘겨도 codegen까지 도달할 수 있었다. vabs, vneg, vrelu, vexp, vln, vsqrt, vnot 일곱 연산자가 모두 이 팩토리 위에 구축되어 있고, 벡터-스칼라 쪽의 vadds, vmuls, vmaxs, vmins, vshls, vshrs에도 약한 형태가 있다.

#3795가 고친 것은 #3512의 또 다른 부작용이다. T.SimdVF()에서 int32 UB 버퍼에 T.clear를 수행할 때, 생성된 벡터 브로드캐스트가 부동소수점만 지원해 PTO 컴파일이 실패했다. PTO 파이프라인이 전용 Parallel pass로 원래 SIMD pass를 대체하면서 fill 하강이 덩달아 누락된 탓이다. 수정 방식은 buffer-version 정규화 이후, PTO Parallel 검증 이전에 LowerSimdVFFill을 추가해 연속적이고 완전한 벡터 영역에는 vdup/vsts를 재사용하고 나머지는 기존 경로를 유지하는 것이다. 동시에 부동소수점 tl.simd.vdup의 수치 변환을 유지해 “int32의 7이 비트 단위 브로드캐스트로 약 9.809e-45가 되는” 문제를 해결했다.

#3639는 E4M3의 ND/NZ UB에서 L1로의 복사를 보완하고, #3926은 T.Kernel이 비양수 block 수와 음수 Pipelined num_stages를 거부하게 하며, #3854는 SimdVF 하강에서 서브바이트 요소의 0 나눗셈을 고치고, #3668은 AIV 코어가 T.PerCoreTask() 내에서 UB에서 GM으로의 인터리브 스트라이드 쓰기를 보완한다. 그 외에 #3915와 #3916은 AssertStmt의 오류 종류와 조건 검사에 대한 인플레이스 단언을 처리한다.

출처: https://github.com/tile-ai/tilelang/pull/3861 , https://github.com/tile-ai/tilelang/pull/3795 , https://github.com/tile-ai/tilelang/pull/3926

4.3 뉴스 측: 중·영문 5개 쿼리 모니터링 기간 내 0건, HN과 arXiv도 관련 항목 없음 (11-11)

Google News 중·영문 쿼리는 모니터링 기간 내 0건이었고 최신 적중은 여전히 예전 기사에 머물러 있다. Hacker News의 적중은 전부 동명 노이즈(TileLang과 무관한 항목)이고, arXiv의 all:"TileLang" 최신 결과 역시 모니터링 기간을 벗어난다. 현재 검색 엔진이 잡아낼 수 있는 TileLang 관련 내용은 여전히 ICLR 2026 논문 페이지와 Microsoft Research 게재 페이지로, 장기 항목이지 뉴스가 아니다.

뉴스 측이 여러 날 연속 0건인 것은 TileLang의 일상이다. 프로젝트 확산은 주로 GitHub와 개발자 커뮤니티를 통해 이루어지며 뉴스 인덱스에는 들어가지 않으므로, 보도 주체는 계속 저장소 동향을 기준으로 삼는다.

출처: Google News 중·영문 쿼리(프록시 경유), Hacker News, arXiv, 모니터링 기간 내 관련 항목 없음.

4.4 기준 수정: K3 두 항목 Q1 대조의 구 Triton 산출물이 -128 부정 시 오버플로 (11-11)

이 항목을 따로 둔 이유는 점수가 아니라 비교 가능성에 영향을 주기 때문이다. 벤치마크 저장소는 weft-parity를 릴리스한 동일 커밋 묶음에서 공개했다. K3의 두 항목 Q1 대조가 이전에 사용한 것은 보존된 Triton Canonical 프로그램이었는데, 해당 프로그램은 −128을 부정할 때 오버플로했다. 경계 입력에서 −2048이 나왔으나 올바른 결과는 0이어야 한다. 정확한 I8 리덕션을 수정한 공유 컴파일러로 재생성한 후 두 프런트엔드의 산출물 모두 해당 입력을 통과한다. 과거 소요 시간은 triton_historical_us 필드에 보존되고 수정 설명은 triton_control_note에 기록되었다.

대조 구현의 오류는 벤치마크류 프로젝트의 흔한 함정이다. 참조 측이 경계 입력에서 틀리면, 피측정 측의 ‘참조보다 못함’은 참조가 더 빠르게 틀린 것일 뿐일 수 있다. 이 공개와 2.8의 페어링 기준을 함께 보면, 이 CPU 라인이 ‘저자 프로그램 대 외부 라이브러리 비교’에서 ‘동일 컴파일러 산출물 페어링 비교’로 전환하고 있음을 보여주며 방법론상 더 신뢰할 수 있지만, 두 표는 혼용할 수 없다.

5. 동향 관찰

첫째, Ascend의 메인라인 내 비중이 계속 상승하고 있으며, ‘연산자 보충’에서 ‘실행 경로 및 솔버 보충’으로 전환되고 있다. 이번 기간 메인 저장소의 세 건은 모두 Ascend다: 실행 백엔드 기본값 교체, 솔버 하한 강화, 원자 연산의 타입 체계 적응. 이 세 건은 모두 연산자 목록을 늘리지 않지만, ‘동일한 프로그램이 어떻게 컴파일되고, 실행되며, 얼마나 빨리 컴파일이 완료되는가’를 바꾸고 있다. 10월 이후의 기록과 대조해 보면, Ascend 측의 머지는 AscendC 연산자 보충에서 인터페이스 시맨틱, 실행 백엔드, 스케줄링 솔버의 세 계층으로 나아가고 있다.

둘째, CUDA 측은 긴 리뷰 기간에 진입했다. 지난 기간에는 CUDA 명령어 수준 원시 연산 세 건이 메인라인에 진입했지만, 이번 기간에는 머지가 0건이고 6건이 리뷰 중이다(ldmatrix/stmatrix, 256비트 벡터화, im2col 스케줄링, 파이프라인 오퍼랜드 수명 주기, 비동기 GEMM 수명 주기, PASS 설정 네임스페이스). 머지 속도 하락과 리뷰 대기열 증가가 동시에 나타나는 것은 일반적으로 리뷰 대역폭이 병목이 되었음을 의미하며, 개발이 중단된 것은 아니다.

셋째, 품질 감사가 기능 개발과 병행되기 시작했다. 하루 26건의 Ascend issue 형태는 커뮤니티에서 이미 누군가 체계적인 불법 입력 감사를 수행하고 있음을 보여주며, 대응하는 수정 PR이 당일 대기열에 올라와 있었다(mask 검증, 음수 매개변수 거부, fill 하향 복원). 이는 백엔드를 여러 국산 칩에 확장하고 있는 프로젝트에 좋은 신호다: 3060개 항목의 일일 테스트가 전부 통과하는 것은 합법 경로의 사용 가능성만 증명할 뿐, 불법 경로의 거부 능력은 이러한 감사에 의존해야 한다.

넷째, RISC-V 4개 소스가 다섯 번째 모니터링 기간 연속 침묵했지만, 4개 소스 외의 CPU 라인에서 단계적 결론이 나왔다. TVM 노선, MLIR 노선, 커뮤니티 인덱스 페이지, Sophgo TPU 네 업스트림 모두 원래 참조에 머물러 있다. 반면 TileLang–Weft는 공유 Canonical 컴파일러로 553개 항목 전부를 Triton의 1.03배 이내로 달성했으며, 4개 플랫폼의 중위 배율은 1.29에서 1.66이다. 이는 기준 전환 이후의 결과이므로 지난 기간의 0.058배와 직접 비교할 수 없다는 점에 유의해야 한다. 진정한 관찰 포인트는 이 ‘동일 컴파일러, 두 개의 프런트엔드’ 방식이 업스트림으로 역진입할 수 있는지, 그리고 RISC-V의 RVV/IME 경로가 4개 소스 외의 프로젝트에서 먼저 작동될 수 있는지 여부다.

한계 설명: 이번 기간 GitHub 익명 API 할당량이 수집 초기에 소진되어, PR 본문과 머지 상세는 검색 인터페이스와 비기본 브랜치의 커밋 원자 스트림으로 보완했으며, 일부 PR의 파일 수와 행 수는 검색 인터페이스 반환값으로 diff를 행별로 재검증하지 않았다. hygon과 mlir-ascend의 머지는 비기본 브랜치에 속하며, 브랜치별로 각각 확인했다. 뉴스 측은 적중이 전무하여 외부 보도로 교차 검증할 수 없었다.
