오늘의 핵심

TileOPs 0.1.0이 오늘 모니터링 기간 내에 릴리스되면서, 여러 날 이어진 “마지막 한 칸에 걸린” 상태가 끝났다. PyPI의 0.1.0 아티팩트는 10-27 07:45(베이징 시간)에 업로드되었으며, 이전 데일리 리포트의 마감 시점보다 45분 늦다. GitHub 릴리스 페이지는 13:15에 게시되었고, 저장소에 처음으로 정식 tag가 등장했다. 릴리스 노트의 핵심 지표는 세 가지다. 206개 연산자 전부에 manifest 항목이 있으며(시그니처, 테스트 및 벤치마크 워크로드, roofline 공식, CI에서 항목별 검증), H200에서의 2265줄 야간 벤치마크 중 2262줄이 가장 빠른 비교 구현보다 느리지 않았고 기하평균 1.37배를 기록했다(비교 대상은 torch.compile, FlashAttention 3, FlashInfer, vLLM, DeepGEMM, FlagGems). 206개 연산자 중 195건의 foundry 태그가 붙은 병합은 TileFoundry가 커널을 생성하고 동일한 CI를 통해 저장소에 반영된 것이다. 릴리스와 함께 공개 API가 동결되어 이후 0.x에서는 추가만 가능하고 변경은 불가하며, API 호환성 검사 스크립트가 새로 추가되어 이전 버전 표기법으로 호출하는 PR은 즉시 실패한다.

24시간 내 tile-ai 조직에서 20건이 병합되었고(tilelang 13, TileOPs 4, TileFoundry 2, tilelang-hygon 1), 심사 중 업데이트 45건, 신규 issue 7건(그중 2건은 Ascend 저장소의 일일 테스트 봇)이 열렸다. 병합의 중심은 두 갈래다. 하나는 부동소수점 의미론과 실행 컨텍스트로, ROCm은 일곱 개 기본 수학 함수를 빠른 내장에서 정밀 구현으로 되돌렸고(MI300X에서 sin/cos 오차가 7.8e-04에서 6.6e-08로 감소), 자동 타깃이 고정된 0번 카드 대신 현재 디바이스를 읽도록 변경했으며, NVRTC와 CuTeDSL이 입력 텐서가 위치한 디바이스 기준으로 스트림을 가져오도록 하고, 자동 튜닝 캐시 키에 compile_flags를 추가했다. 다른 하나는 정적 경계와 스레드 도메인으로, 슬라이스 채우기를 길이가 아닌 영역 끝 기준으로 검증하고, 범위를 벗어난 음수 인덱스는 컴파일 시점에 거부하며, T.ws(-1) 영역이 모든 스레드에서 실행되도록 변경했다. Hygon은 12개 파일 1389줄을 병합하여 scale 버퍼를 독립적인 이중 bank로 분리하고 LDS bank와 분리했다. 서드파티 측에서는 Hexagon DSP 백엔드가 하루 15건으로, HVX 벡터화, VTCM 아레나, Crouton 레이아웃, DMA 내장을 Crouton 상의 매핑과 리덕션까지 이어서 구축했다.

1. 핵심 프로젝트 진행 상황

1.1 메인 저장소: ROCm의 exp/sin/cos가 더 이상 기본으로 빠른 내장에 저하되지 않음, sin/cos 오차 7.8e-04에서 6.6e-08로 감소(#3621)

10-27 22:39에 병합, 5개 파일 +107/-17, #3618 수정. HIP에서 T.exp, T.exp10, T.log, T.log2, T.log10, T.sin, T.cos 일곱 개 기본 함수는 tl.enable_fast_math 설정과 무관하게 __expf 같은 빠른 내장으로 저하되었으나, CUDA 측은 #875의 규약에 따라 정밀 구현을 사용했다. 반대로 명시적 T.__exp 등 빠른 연산자는 HIP에서 전혀 내려가지 않고 tilelang.rocm.language에서 곧바로 AttributeError를 던졌다. 이번 커밋은 HIP과 CUDA가 동일한 전략을 사용하도록 한다. 일곱 개 기본 연산자는 HIPMath로 전환하고, 밑줄이 붙은 여덟 개 빠른 연산자는 HIPFastMath를 가리키는 최저 저하 규칙을 새로 추가하며, 모두 FAST_MATH_INTRINSICS 목록으로 통합해 ROCm 언어 계층에서 내보낸다. 정밀도 비교는 #3618의 재현을 사용한다. MI300X에서 exp와 exp10은 상대 오차, sin과 cos는 절대 오차(x는 1e4까지)를 보며, 네 열은 순서대로 T.exp, T.exp10, T.sin, T.cos이고, 메인 브랜치는 3.7e-06 / 4.1e-06 / 7.8e-04 / 7.8e-04, 이번 커밋은 8.3e-08 / 8.1e-08 / 6.6e-08 / 6.4e-08이다.

출처: https://github.com/tile-ai/tilelang/pull/3621

1.2 메인 저장소: 자동 타깃이 현재 HIP 디바이스를 읽도록 변경, 멀티 GPU 머신에서 더 이상 0번 카드 아키텍처로 고정되지 않음(#3594)

10-27 22:37에 병합되었으며, 2개 파일 +24/-1. determine_target(“auto”)는 ROCm에서 등록된 HIP 프로브로 귀결되는데, 해당 프로브는 torch.cuda.get_device_properties(0)를 무조건 읽으므로 현재 HIP 디바이스가 0번 카드가 아닐 때 자동 프로브는 0번 카드의 아키텍처를 반환한다. CUDA 측은 이미 torch.cuda.current_device()를 사용하고 있었으나 ROCm은 따라가지 못했다. 수정 방식은 먼저 현재 디바이스 인덱스를 가져온 뒤 속성을 조회하고, normalize_rocm_arch로 기능 접미사를 제거하는 것이다. 새 테스트는 current_device()를 스텁으로 1을 반환하게 하고, 프로브된 모든 인덱스를 기록하며, gfx942가 프로브되었고 1번 카드만 건드렸음을 단언한다. 수정 전에는 이 단언이 probed == [0]을 얻었다. 작성자는 본인 기기에 ROCm 디바이스가 없으며, 테스트는 스텁 torch로만 프로브 헬퍼를 검증했고 실제 HIP 런타임은 실행하지 않았다고 명시했다. 같은 날의 다른 변경 #3549와는 다른 함수를 다룬다(#3549는 tilelang/contrib/rocm.py, 이번 변경은 tilelang/rocm/target.py).

3.3 TileOPs 0.1.0의 알려진 격차와 다음 단계: 융합 연산자, 전체 모델, 연산-통신 융합 (10-27)

릴리스 노트는 네 가지 알려진 문제를 나열했다. FusedAddLayerNormFwdOp가 0에서 멀리 떨어진 행에서 정밀도를 잃고 1e36에 가까운 행에서 오버플로한다(#2773, 어제 데일리 리포트에서 이미 이 결함을 기록했다). 동일 호스트에 서로 다른 아키텍처의 GPU가 있으면 한 GPU용으로 컴파일된 커널이 다른 GPU에서 실행될 수 있다(#2302). Bwd 계열 연산자는 직접 호출해야 하며 torch.autograd에 연결되지 않는다. 단일 연산자 인스턴스는 동시에 하나의 스레드와 하나의 CUDA 스트림만 지원한다. 검증 범위는 H200, Python 3.12와 3.13만을 포함하며, 일부 커널은 별도로 SM80, SM86, SM89 경로가 있어 해당 디바이스에서 실행되지만 릴리스 검증 범위에는 속하지 않는다. 로드맵은 세 단계이다. 먼저 연산자 경계를 넘는 복잡한 융합(어텐션과 전후 프로젝션 및 정규화, 전체 레이어 MoE, GEMM epilogue 내 양자화)을 하고, 다음으로 전체 모델의 프리필과 디코딩을 서빙 엔진과 엔드투엔드로 비교하며, 마지막으로 연산과 통신의 융합(텐서 병렬 GEMM과 all-reduce, 전문가 병렬 MoE와 all-to-all)을 한다. 이 세 단계가 실현되면 TileOPs의 경쟁 상대는 단일 연산자 라이브러리에서 추론 프레임워크로 바뀐다.

3.4 TileOPs 4건 병합: where와 masked_fill 튜닝 가능, D128 인과 대각 64 키 기준 채점, 희소 장 GDN 프리필 분할, 변경 로그 릴리스 날짜 기준 확정 (#2782 / #2783 / #2779 / #2781)

4건이 10-27에 병합되었으며, 이는 릴리스 직전의 마무리 작업이다. #2782는 request_tune()이 WhereFwdOp, MaskedFillTensorFwdOp, MaskedFillScalarFwdOp에서 ValueError를 발생시키는 문제를 수정했다. 자동 튜닝이 무작위로 생성된 정수 입력을 거부하는데, 이 세 커널이 bool 조건이나 마스크를 uint8로 전달하기 때문이다. 무작위 선택기는 각 요소가 어떤 피연산자를 취할지만 변경하고 후보의 작업량은 바꾸지 않으므로 무작위 정수 입력을 안전하다고 선언했다. 테스트 노드 3개를 새로 추가했으며, 메인 브랜치에서 세 사례 모두 실패했다. #2783은 D128 밀집 프로그램의 인과 대각을 최적화했다. 인과 호출에 key 구간이 하나뿐이고 두 길이가 모두 128행 경계에 있을 때, 첫 번째 소비 warpgroup의 대각 key 타일이 모든 행에 대해 상위 64 키를 마스킹하므로, 이 단계를 m64n64의 QK에 64 키 softmax를 조합하여 실행하도록 변경했다. 이 선택은 컴파일 타임 플래그(diag_aligned, 커널 키에 포함)인데, 런타임에 64와 128 너비 QK 사이를 분기하면 ptxas가 일부 특수화에서 모든 WGMMA를 직렬화하기 때문이다(C7511). 플래그로 전환한 후 manifest의 모든 D128 프리필 특수화에서 더 이상 C75xx가 발생하지 않는다. #2779는 SM89에서 희소 장 시퀀스의 GDN 프리필을 상태 스캔과 독립 출력 프로그램으로 분할했으며, 밀집 key-major D128 입력이면서 최소 16384 토큰, 상태 스캔 CTA가 SM 수의 4분의 1을 넘지 않는 경우에 적용된다. 벤치마크에서 (1, 16384, 4, 128) bf16의 소요 시간이 약 0.612밀리초에서 약 0.470밀리초로 감소했으며, flash-linear-attention의 0.441밀리초 대비 0.939배이다. #2781은 CHANGELOG에서 0.1.0의 날짜를 PyPI에 등록된 날(2026-10-27)로 확정하고, 기여자 문서에서 릴리스 1회 설정과 Actions 클릭 경로를 삭제했다.

3.5 TileFoundry 2건 병합: 전체 윈도를 피연산자 자체로 하향 전달, 동적 공유 메모리를 커널 실제 사용량 기준으로 크기 결정 (#273 / #271)

두 건 모두 10-27에 병합되었다. #273은 sm_89 GEMM의 하향 전달을 수정했다. schedule finalize가 작성한 내용이 컴파일되지 않는데, 하향 전달이 전체 누산기를 0에서 시작하고 범위가 자기 자신과 같은 윈도 T.ptr_of(acc[0:0+16, 0:0+8])로 감싸기 때문이며, CUDA codegen이 분할 레지스터 타일의 포인터 슬라이스를 거부하여 “일반 소스 레이아웃 요구” 오류를 낸다. 또한 MMA가 레지스터 프래그먼트를 lhs_frag_dst[0:0+16, 0:0+32] 같은 원시 Slice로 읽는데 codegen 역시 처리기가 없다. 수정은 하향 전달 측에서 이루어졌다. StoragePlan.operand는 원래 “0에서 시작하고 피연산자 전체를 걸치는 윈도”를 피연산자 자체로 취급하지만, 구체화와 명령 하향 전달이 여전히 Slice를 구성한다. 이를 한 번만 판정하도록 변경했다. MLIR의 TrivialSubViewOpFolder에 대해 동일한 치환을 수행한다. #271은 동적 공유 메모리를 수정했다. 합성된 호스트 진입점이 각 TIR 커널에 대해 dynamic_smem=0으로 시작하므로, 정수 TensorView 오프셋으로 공유 메모리에 접근하는 커널은 공간을 할당받지 못하며, 48 KiB를 초과하면 cudaFuncAttributeMaxDynamicSharedMemorySize를 설정해야 하는데 런처는 이를 전혀 설정하지 않는다. 작성자는 #267의 “목표 용량만큼 최대한 할당” 제안을 채택하지 않고 커널 실제 사용량 기준으로 크기를 결정하는 방식으로 변경했으며, 그 이유는 정적 공유 메모리와 동적 공유 메모리가 동일한 한도를 공유하고 각 블록의 요청량이 하나의 SM에 몇 개를 배치할 수 있는지를 결정하기 때문이다. sm_89에서 99 KiB를 채우면 512바이트를 사용하는 커널도 하나만 배치할 수 있다. CUTLASS와 TileLang 모두 같은 방식으로 크기를 결정한다.

5. 트렌드 관찰

첫째, TileOPs 0.1.0은 「연산자 라이브러리」라는 일의 비용 구조를 다른 알고리즘으로 바꿨습니다. 전통적 방식은 연산자 수가 하드웨어와 모델 요구에 따라 선형으로 늘어나고 인력이 병목입니다. 여기서의 방식은 연산자마다 먼저 YAML 명세를 한 부 작성해 시그니처, 워크로드, roofline을 명확히 선언하고, 그다음 agent가 커널을 생성·튜닝하며, 마지막으로 명세에서 파생된 테스트와 벤치마크로 진입 심사를 합니다. 206개 연산자, 195건의 foundry 태그 머지는 이 프로세스의 첫 전량 납품입니다. 이것이 지속될 수 있는지는 두 가지에 달려 있습니다: 명세가 복잡한 융합 연산자를 커버할 수 있는지(로드맵 첫 단계가 바로 이것), 그리고 벤치마크가 「벤치마크에 맞춰 튜닝됐지만 실제로는 견고하지 않은」 커널을 막을 수 있는지 — FusedAddLayerNormFwdOp가 0에서 먼 행에서 정밀도를 잃는 이 알려진 문제가 바로 이런 리스크의 한 표본입니다.

둘째, 이 모니터링 기간의 머지는 거의 전부 「조용한 오류」입니다. ROCm의 수학 함수가 기본으로 빠른 내장 함수를 타면서 sin/cos가 세 자릿수만큼 차이 나게 하고, address_of가 읽기로 취급되면서 불투명 호출 이후의 공유 메모리에서 쓰기 전 내용을 읽게 하며, T.ws(-1)의 영역이 스레드 0개에서 실행되어 저장이 전부 버려지고 오류도 나지 않으며, 슬라이스 채우기가 길이가 아닌 끝점으로 검증되어 그대로 범위를 넘어 쓰고, 음수 인덱스가 랩어라운드 후에도 음수로 남아 할당 시작점 이전으로 떨어집니다. 이 다섯 가지의 공통점은 컴파일은 통과하고 실행 시 오류는 없으며 결과가 틀린다는 것이고, 모두 최근 2주 안에 집중적으로 발견됐습니다. 대형 모델용 커널을 작성하는 언어에게 이런 결함의 대가는 컴파일 시점 오류보다 훨씬 크며, 이들은 같은 엔지니어링 요구를 가리킵니다: 「오류는 없지만 동작이 틀린」 표기법을 컴파일 시점에 거부하는 것. 이 모니터링 기간의 경계 검증 두 건 수정과 ws(-1) 수정이 하는 일이 바로 이것입니다.

셋째, 백엔드 커버리지가 「벤더 주도」에서 「커뮤니티 자발」로 옮겨가고 있습니다. 공식 유지보수되는 Ascend, Hygon, MetaX, Moore Threads 네 라인 외에, Hexagon DSP 백엔드가 하루에 15건을 머지하며 선형대수 원시 연산을 Crouton 타일에 깔았고, PPU 버전에는 무변경 래퍼가 등장했으며, CANN 커뮤니티가 자체 연산자 저장소를 세우고 그것으로 DeepSeek V4.1 Flash의 모델 조각을 엮어냈습니다. 이 작업들은 모두 tile-ai 조직의 저장소에 있지 않지만, 모두 TileLang 언어 계층의 안정성에 의존합니다. 이것이야말로 0.1.0이 공개 API를 동결하고 API 호환성 검사를 CI 게이트로 만든 의미이기도 합니다 — 다운스트림이 많을수록 하위 호환의 가치가 높아집니다.

넷째, 캐시 아이덴티티 문제가 두 백엔드에 동시에 포착됐습니다. 메인 저장소는 compile_flags를 자동 튜닝 캐시 키에 포함시켰고(#3338), Ascend는 Bisheng 빌드 아이덴티티를 바이너리 캐시 키에 포함시켰습니다(#3691). 같은 커널이 서로 다른 컴파일 옵션이나 컴파일러에서 다른 바이너리를 생성하는데, 캐시가 소스와 형상만으로 키를 만들면 잘못 적중하여 측정된 성능이 실제 컴파일 결과와 맞지 않습니다. 두 개의 독립 노선이 같은 날 같은 일을 했다는 것은 이런 문제가 실제 사용에서 이미 충분히 고통스럽다는 뜻입니다.
