오늘의 핵심: Moore Threads MP31, 한 번에 14건 PR 제출, 저정밀도와 집합 통신 동시 보완

tile-ai/tilelang-musa가 11-27 새벽 02:18부터 04:16 사이에 신규 PR 14건을 생성, 번호는 #14부터 #27까지. 이 제출물은 전부 v0.1.15+musa.1을 기반 브랜치로 하며, 스택 순서를 선언하여 #25는 #19 이후에 머지되어야 함.

저정밀도가 주된 흐름이다. #19는 MP31의 fragment-A SQMMA GEMM을 합법화하고 188 KiB 공유 메모리 가드레일을 추가했다. #25는 MP31 네이티브 W4A16 SQMMA를 보완하여 fp16/bf16 × int4 → fp32와 역방향 두 조합을 모두 커버한다. #25는 또한 sqmma.h를 재작성하여 MUSA 5.2.0 헤더 파일에서 s4가 fp4로 잘못 표기된 문제를 우회했다. #20은 warp 전용 GEMM의 FP8 TME 디스크립터를 활성화했다.

메모리 접근과 동기화가 각각 한 묶음을 차지한다. #27은 4비트 가중치의 패킹된 UINT8 TME 로드를 사용 가능하게 했다. #18은 TME 커널에 종료 시 tme_flush()를 보완했다. #16은 MP31의 swizzle 인덱스를 요소 단위로 변경하여 벡터화를 유지했다. #24는 warp 전용 TMA 배리어를 수정하여 squad 간 부분 동기화를 squad당 128스레드 배리어로 낮췄다. #26은 소비자 측의 다중 warp AllReduce를 MP31 부분 배리어로 낮췄다.

언어 측면도 확장 중이다. #23은 블록 내 병렬 T.sort, T.argsort, T.topk를 추가하여 바이토닉 정렬 템플릿으로 구현했으며, int4 외 6가지 dtype과 임의의 비-2의 거듭제곱 길이를 지원한다. #15는 murand를 통해 T.rng_init과 T.rng_rand를 지원한다. #21은 T.reduce_prod, 두 배리어 다중 warp 1차원 스캔, mem-bound TIR pass를 추가했다. #22는 tl.enable_fast_math를 mcc -ffast-math에 연결했다.

검증 측은 MTT S5000(mp_31)에서 이루어졌다. #23의 정렬 케이스 25건이 전부 통과하여 MoE top-2/8, NSA top-64/512 및 비-2의 거듭제곱 길이를 커버했다. #25에는 저정밀도 및 누적 케이스가 별도로 있다.

출처: https://github.com/tile-ai/tilelang-musa/pull/25.

오늘의 중점: 메인 저장소 세 건 모두 Ascend, host-mapped 버퍼 파라미터 메인라인 진입

tile-ai/tilelang 메인 브랜치 모니터링 기간 내 커밋은 3건뿐이며 모두 Ascend 태그가 붙어 있다. 이는 이전의 캐시 서브시스템, ROCm 수정 흐름과 달라 Ascend가 메인라인의 안정적인 입력 소스가 되었음을 보여준다.

#3909는 09:44에 머지되어 Ascend에 명시적 host-mapped 버퍼 파라미터를 추가했다. 이전에는 ASCEND 커널이 이미 매핑된 CPU 텐서를 받아도 거부했기에 호출자가 텐서 검증을 꺼야만 했다. 새 경로는 #3802의 계약을 따라 동일한 T.annotate_host_mapped_buffers(...) 인터페이스를 사용한다. Cython과 TVM-FFI 양측 모두 aclrtHostGetDevicePointer로 매핑을 검증한 후 디바이스 가시 주소를 전달한다. dtype, 형상, 스트라이드 및 실행 디바이스 검사는 모두 유지된다.

#4486은 11:32에 머지되어 #4429를 수정했다. 트리거 시나리오는 nk=topk=960의 FlashMLA 프리필로, 각 query가 15개의 KV tile을 처리하고 두 query 슬롯이 교대로 사용되며 첫 슬롯은 30회 루프 후 재사용된다. 기존 구현은 동일 파이프라인 사이트 쌍마다 이터레이션 거리별로 간선을 하나씩 생성하여 단일 쌍이 0부터 30까지 총 31개의 거리를 기여할 수 있었다. 새 구현은 “소스, 목적, 엄격성”별로 서로소인 폐구간을 저장하며, 두 구간의 합성도 여전히 구간이므로 새로 커버되는 거리를 배치 단위로 전파할 수 있다.

#4390은 12:25에 머지되어 Ascend CI의 PTOAS를 PyPI 설치로 변경했다. CANN 9.2 이미지는 그대로 두고, 먼저 이미지 내장 스크립트로 그 안의 PTOAS 컴포넌트를 제거한 다음 --upgrade --no-deps --only-binary=:all:로 최신 호환 휠을 설치한다. 설치 후 Python 3.12, x86_64, 패키지와 CLI 버전 일치를 검증하고, PTOAS, PTODSL, MLIR Python 모듈 및 네이티브 확장이 모두 가상 환경에서 로드 가능한지 확인한다. 설치 또는 검증 실패 시 PTO 백엔드 예제와 단위 테스트를 건너뛰고 단계 결과를 작업 요약에 기록한다.

출처: https://github.com/tile-ai/tilelang/pull/3909.

오늘의 중점: TileFoundry, Apple ANE 타깃 개시, TIR에서 HWX 컨테이너 직접 출력

tile-ai/TileFoundry는 심사 중인 PR #369를 새로 추가했으며, 제목에 Apple ANE의 codegen 경로가 명시되어 있다. 경로는 세 단계로 나뉜다: TIR → 태스크 디스크립터 → HWX 컨테이너. 이는 #361에서 이미 도입한 ANE 타깃 위에 구축된 것으로, TileLang 생태계 최초의 엣지 디바이스 신경망 엔진 타깃이다.

구현은 두 계층으로 나뉜다. ISA 계층은 Common, L2, PE, NE, TileDMA, Kernel 여섯 가지 블록을 커버하는 레지스터 비트필드 맵을 제공한다. 태스크 디스크립터는 RUN/MASK 패킷 인코딩을 채택하며 load, store, compute-PE, compute-NE, conv, activation 여섯 가지 프리미티브를 갖춘다. 또한 선언적 수식과 교차 필드 검증 라이브러리가 있어 빌드 시점에 실패-폐쇄 방식으로 디스크립터를 검증한다.

코드 생성 계층은 이미터 디스패치, pass별 직렬화, HWX 컨테이너 출력을 담당한다. 컨테이너는 Mach-O 형식이며, 설명에 따라 리버스 엔지니어링 후 처음부터 구현했고, 기본 이미지에 대해서는 문자 제거를 수행한다. 범위를 벗어난 tile_height와 tile_width는 컴파일 시점에 즉시 거부된다.

정확성 측면에서 제안서는 커버된 연산자 범위 내에서 Apple 자사 컴파일러의 출력과 비트 단위로 일치한다고 주장한다.

같은 저장소에서 같은 날 #368이 병합되어 #162 이름 변경 후 남은 문제를 수정했다. 코드 생성이 여전히 ShardLayout인 배리어에 대해 tilefoundry::local을 투사하는데, 해당 함수는 이미 local_tensor로 이름이 바뀌어 nvcc 단계로 컴파일되면 중단된다. 수정 방법은 “전체 그리드 브로드캐스트” 배리어에 대해서만 워드를 가져오고, 분할 배리어를 만나면 즉시 거부하는 것이다. 이유는 분할 배리어가 각 warp에 서로 다른 워드를 할당하는데, CopyAsyncBulk는 첫 번째 warp의 스레드에서만 CTA 도달 기준으로 한 번 가져오고 나머지 warp는 영원히 완료되지 않는 위상의 워드를 기다리게 되기 때문이다.

출처: https://github.com/tile-ai/TileFoundry/pull/369.

1. 핵심 프로젝트 진행 상황

1.1 host-mapped 버퍼 파라미터 메인라인 진입, Ascend에서 더 이상 텐서 검증 비활성화 요구하지 않음

#3909는 Cython과 TVM-FFI 두 바인딩 경로를 변경한다. 둘 다 aclrtHostGetDevicePointer로 디바이스 측 주소를 얻고, 원본 dtype, 형상, 스트라이드를 커널로 가져온다. C++ 바인딩 시그니처는 그대로이며, 기존 디바이스 타입에 따라 런타임 쿼리를 선택하도록 변경되었다. Cython은 기본 CUDA 파서를 유지하고, Ascend만 선택적 파서를 제공한다. CUDA 측은 여전히 use_torch_stream()을 사용하며, 공유 디바이스 선택 로직은 변경되지 않았다.

“전체 host 파라미터”인 Ascend 시그니처만 원본 NPU 스트림을 명시적으로 설치한다. 테스트는 전체 host 파라미터, 자동 할당된 NPU 출력, NPU Graph 캡처 세 가지 시나리오를 커버한다.

1.2 InsertSync가 구간 기준으로 의존성 거리 전파, 31개 반복 거리에 대해 더 이상 개별 엣지 생성하지 않음

#4486은 InsertSync라는 하나의 pass만 변경한다. 이전에는 각 동일 파이프라인 사이트 쌍에 대해 각 반복 거리마다 엣지를 하나씩 삽입하고, 의존성 클로저를 구축할 때 반복적으로 합성했다. 새 구현은 도달 가능한 거리를 닫힌 구간으로 저장하고, 두 구간을 합성하여 또 다른 구간을 얻음으로써 아직 커버되지 않은 거리만 전파한다. 갭과 엄격성은 모두 명시적으로 보존되며, 거리 0과 1은 여전히 기존 epoch 도메인 투사 규칙에 따라 처리된다.

FIFO 작업 큐는 std::set으로 변경되었으며, 키는 소스, 목적지, 두 거리 경계, 엄격성으로 중복 대기 구간을 건너뛰는 데 사용된다.

1.3 Ascend CI가 PyPI에서 PTOAS 설치로 변경, CANN 9.2 이미지는 그대로 유지

#4390의 동기는 PTOAS와 CANN의 릴리스 주기가 동기화되지 않는다는 점이다. 이전에는 PTOAS가 이미지에 고정되어 업그레이드하려면 워크플로를 수정해야 했다. 변경 후에는 인덱스에 새 버전이 있으면 자동으로 선택되므로 workflow를 수정하거나 기존 의존성을 업데이트할 필요가 없다.

3. 생태계와 채택 측 (TileOPs 연산자 라이브러리 / TileFoundry / FlashQLA)

3.1 TileOPs 10건, 세 곳의 0.1.15 성능 회복이 같은 날 착지

tile-ai/TileOPs 메인 브랜치 모니터링 기간 내 10건의 커밋이 있었으며, 전부 성능 또는 테스트이고 새 연산자는 없다. 세 라인 모두 TileLang 0.1.15가 초래한 성능 손실을 회복하고 있다.

첫 번째는 dropout이다. #3181은 16비트 행의 dropout이 0.1.15부터 13%에서 16% 느려졌다고 보고했다. 원인은 T.rng_rand_float()가 T.Parallel로 벡터화되면서 하나의 벡터가 한 번의 샘플링을 공유하기 때문이다. 0.1.15는 또 16비트 벡터를 8개 원소에서 4개 원소로 좁혔다. #3187은 각 원소가 독립적으로 카운터에서 32비트 Philox4x32-10 값을 가져오도록 바꾸고, 상위 16비트는 스레드의 첫 배치 샘플링을 사용하며, 하위 16비트는 상위 비트가 임계값과 같을 때만 추가 샘플링하도록 했다. 이 변경은 동시에 벡터 내 마스크 상관성을 제거하여, 수치도 상관에서 독립으로 전환했다.

두 번째는 W4A8 프리필이다. #3172는 각 tile 반복 시작에서 소비자 warp에 T.sync_warp()를 추가한다. 이전에는 ptxas가 warp가 K 루프 지점에서 이미 수렴했음을 증명하지 못해, 링 버퍼의 stage 인덱스와 WGMMA 디스크립터를 벡터 레지스터에 남겨두고 매 WGMMA 전에 통합 레지스터로 복사했다. 그 결과 R2UR이 20에서 52로 늘어났고, 네 가지 형상이 10%에서 13% 느려졌다.

세 번째는 RoPE이다. #3173은 단계별 RoPE를 (tokens, sides) 그리드로 발사하도록 바꾸고, 각 블록이 1차원 배치 쓰기 한 번으로 전체 행을 되쓰도록 했다. 이전에는 8 KiB 행이 16번의 tensor-map 쓰기로 쪼개졌고, 매번 테이블 조회에 경계 보호가 붙었다. 실측 결과 gptj-6b 프리필이 15.440마이크로초에서 15.264마이크로초로 줄었다.

3.2 DeepSeek-V4-Flash 프리필, RoPE 행 복사와 윈도 링 복사 제거

#3186은 두 곳을 바꾼다. 압축 계층의 RoPE 테이블은 압축비에 따라 각 위치의 코사인과 사인을 미리 저장하며, 압축기 프리필은 더 이상 RoPECosSinFwdOp에 매 호출마다 복사되는 스트라이드 슬라이스를 전달하지 않는다. 프리필 말미에 마지막 window_size 행 KV를 쓸 때, 기존에는 arange, 나머지 연산, gather, scatter의 네 단계를 거쳤으나 이제는 두 번의 슬라이스 복사로 바뀌었다.

테스트 측에는 256 token 프롬프트, 두 개의 전체 윈도 케이스가 추가되었으며, 해당 링 쓰기는 슬롯 0에서 시작한다.

3.3 Qwen3.8-27B의 6헤드 쿼리 그룹, warp 전용 GQA 커널로 진입

#3174가 해결하는 것은 그룹 폭 제한이다. GQAPagedFwdWSKernel은 이전에 하나의 KV 헤드에 대한 전체 쿼리 그룹을 128행 tile에 밀어 넣고, 각 헤드가 128 // group행을 차지했다. 이렇게 하면 1, 2, 4, 8, 16헤드 또는 16헤드 초과만 지원하고, 나머지 조합은 gqa_paged_varlen_kernel로 폴백했다. Qwen3.8-27B의 6헤드 그룹은 바로 폴백 분기에 떨어졌으며, 24개의 쿼리 헤드 대 4개의 KV 헤드, head_dim 256을 가진다.

새 구현은 하나의 tile에 하나의 헤드 그룹만 넣으며, _tile_heads는 쿼리 그룹을 나누어떨어지게 하고 각 헤드가 8행 swizzle 원자를 가득 채우게 하는 최대 2의 거듭제곱을 취하며, Qwen의 경우 2이다. 하나의 KV 헤드 그룹은 slices에 따라 여러 헤드 그룹으로 나뉘어 각각 작업 항목이 되고, 생산자는 group_id // slices인 KV 헤드의 K, V와 회전된 key 열을 로드한다.

검토 측에는 같은 날 체계적인 시리즈가 등장했으며, 총 6건으로 #3189부터 #3194까지이며, 주제는 모두 「스트라이드 뷰에서의 제자리 읽기」이다. BMM의 a와 out, CausalConv1d의 x, RMSNormGated의 x와 z, PagedKVCacheWrite의 k와 v 등 6곳을 포함한다. 별도로 #3195는 Qwen3.8-27B의 positions를 매 단계 한 번만 구성하고, 더 이상 어텐션 계층마다 재구성하지 않는다.

3.4 MXFP4 그룹 GEMM, CTA별 tile 접두사로 전문가 탐색하도록 변경

#3177은 작업 위치 지정의 오버헤드를 다룬다. 공유 task_walk는 전문가를 하나씩 전진하며, 매 단계마다 의존적인 전역 읽기가 한 번, 연속 구간에서는 두 번 발생한다. 따라서 각 CTA는 레이아웃 내 모든 전문가에 대해 비용을 지불하며, 빈 전문가도 마찬가지로 지불한다.

새로 추가된 table_task_walk는 각 CTA가 각 전문가의 행 tile 수를 한 번씩 합산해 공유 메모리에 넣도록 한다. 이후 warp shuffle로 일정 구간의 전문가 합을 스캔하고, 전문가 수가 블록 내 스레드 수를 초과하면 다시 하나의 warp가 각 구간 총합을 한 번 훑는다. 마지막으로 각 warp는 한 번의 ballot으로 최대 warp 폭만큼의 전문가를 전진시킨다.

3.5 샘플링, 임베딩, KDA 및 CUDA Graph 자격 테스트 동일자 병합

#3184는 top-p 행 확률이 1인 상황을 처리하여, 전체 행을 그대로 통과시키고 보존 키를 한 번만 취하도록 변경했다. #3188은 통과율이 허용될 때 와이드 임베딩 호출이 두 warp의 CTA 단일 웨이브로 완료되도록 하여, CTA당 warp 하나라는 보수적 분할로 실행되지 않도록 했다.

#3179는 값 주순서의 KDA 디코딩이 상태가 FP32 상한에 근접할 때 발산하는 문제를 수정하여 유한하게 유지하도록 했다. #3175는 두 모델 각각의 디코딩 스텝 연산자에 대해 항목별로 CUDA Graph 캡처 자격 테스트를 수행하도록 했다. #3176은 제목 편집 후 태그가 동기화되지 않는 문제를 수정하여 GITHUB_EVENT_PATH를 읽도록 했다.

3.6 TileFoundry, 배리어 브로드캐스트 코드 생성 수정, 샤드 배리어는 직접 거부로 변경

#368은 local_tensor 이름 변경 잔재 수정 외에도 두 개의 좌표 분기를 처리했다. 이들 역시 더 이상 존재하지 않는 함수를 방출하지만, 현재 도달 가능한 경로는 없다. #186부터 타입 추론이 포인터 뷰에 좌표를 붙이는 것을 거부하며, 모든 pass는 포인터에서만 TensorView를 구성하기 때문이다.

4.1 조직 활성도: 17건 병합, 67건 심사 중, 48건 신규 생성, 16건 신규 오픈

4.2 Ascend 일일 테스트 3168건 전부 통과, 신규 결함은 RNG와 DeepGEMM에 집중

Ascend 하위 저장소의 11-26 11:37 일일 테스트 기록은 3168건 전부 통과, 통과율 100%이며, 지난 회차는 3132건이었다. 동일자에 신규 오픈된 Ascend 결함 12건은 세 곳에 집중되어 있다.

DeepGEMM 관련은 세 건이다. #4531은 K=0인 연속 BF16 피연산자에서 먼저 오류를 보고한 뒤 제로 출력 빠른 경로로 진입한다. #4534는 검증 레시피 이전에 FP8의 분수급 세분성을 조용히 잘라낸다. #4535는 등록된 TVM 디바이스 API가 존재하지 않는 NPU 인덱스를 존재하는 것으로 보고하도록 한다.

툴체인 측은 두 건이다. #4528은 단일 프로세스 내에서 BISHENG_HOME을 전환한 후 이전 컴파일러 버전이 툴체인 임프린트에 남아 있다고 보고했다. #4527은 따옴표가 있는 include 디렉터리가 Bisheng 파라미터 구성 시 이중 분할된다고 보고했다.

5. 트렌드 관찰

첫째, Moore Threads의 이번 14건은 성격상 패치가 아니라 MP31 백엔드를 한 번에 「저정밀도 사용 가능, 집합 통신 사용 가능, 언어 면 완비」로 끌어올린 것이다. 근거는 세 가지다. W4A16과 int8 누적이 모두 하드웨어 명령어 계층에서 합법화되었다. AllReduce는 이미 세 가지 구현을 갖추었으며, warp 선두, 부분 배리어, squad 간 분할을 포함한다. 정렬 계열은 PyTorch의 안정성 시맨틱에 직접 정렬된다. 이러한 조합은 통상 백엔드가 추론 연산자 라이브러리를 받아들일 준비를 마치기 직전에 나타난다.

둘째, Ascend는 이미 메인 저장소를 상시 입력으로 만들었다. 모니터링 기간 내 메인 저장소 3건 모두 Ascend 태그가 붙었고 성격도 각기 다르다. 한 건은 API 능력(host-mapped 버퍼), 한 건은 컴파일 시점 복잡도(InsertSync 거리 구간화), 한 건은 CI 공급망(PTOAS를 PyPI에서 설치하도록 변경)이다. 동시에 12건의 신규 결함이 RNG와 DeepGEMM에 집중되어, 커버리지가 이미 수치 세부 계층에 진입했음을 보여준다.

셋째, TileOPs가 0.1.15의 성능 회귀 회수를 담당하고 있다. 세 갈래(dropout, W4A8 GEMM, RoPE) 모두 0.1.15의 코드 생성 변화로 인해 발생했으며, 모두 구체적인 백분율 또는 마이크로초 수치로 귀결되었다. 이는 컴파일러 측 변경에 연산자 수준의 회귀 베이스라인이 뒷받침되어야 함을 시사한다. 그렇지 않으면 손실이 한 버전 늦게야 발견된다.

넷째, 목표가 엣지 디바이스로 확장된다. Apple ANE의 codegen PR이 병합되면 TileLang의 목표 면은 GPU와 국산 NPU에서 휴대폰과 태블릿의 뉴럴 엔진으로 확대된다. 구현 경로는 TIR을 태스크 디스크립터로 낮춘 뒤 벤더 컨테이너로 패키징하는 것이다. 이는 Ascend, Moore Threads가 걷는 「벤더 C++를 생성한 뒤 재컴파일」 경로와 다르며, 또 다른 착지 방식이다.

다섯째, RISC-V 4개 출처는 두 번째 모니터링 기간 연속으로 변화가 없다. TVM 경로와 MLIR 경로 모두 이전 호 인용에 머물러 있고, SOPHGO TPU 브랜치 수도 증감이 없다. 해당 방향은 여전히 저위에 있으며, 아직 추세를 구성하지 않는다.

기준: 모니터링 기간은 베이징 시간 11-26 07:00부터 11-27 07:00까지 총 24시간이다. 저장소 커밋은 committer 시간 기준으로 집계하며, 먼저 이전 회차 기준 시점인 11-26 07:00과 비교한 뒤 신규 여부를 판정한다.

조직 수준 수치는 search 인터페이스에서 가져왔다. 머지는 is:merged merged:>=로, 심사 중은 is:open updated:>=로, 신규 생성은 created:>=로 조회한다. 심사 중 67건은 전체량이며, 목록 인터페이스는 페이지당 50건이므로 본문에서는 검증 가능한 항목만 인용한다.

버전 측면의 서술은 세 부분으로 나눈다: VERSION 파일은 0.1.16, GitHub 태그는 v0.1.15, PyPI는 0.1.15이다. 본문에는 “0.1.16 릴리스됨”이라고 쓰여 있지 않다.

뉴스 측면은 Google News 중·영문, Hacker News, arXiv 세 경로로 재검증한 결과, 모니터링 기간 내에 TileLang 관련 보도가 확실히 없었으며, 빈 결과를 수집 장애로 추정하지 않았다.
