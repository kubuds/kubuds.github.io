오늘의 핵심: TileOPs mHC 연산자 3건 동일자 머지, 시퀀스 모델링 인터페이스 교체 완료

11-19 하루 동안 TileOPs는 HyperConnection의 pre, post, head 세 연산자를 한꺼번에 머지했다. 세 건은 각각 #3032, #3035, #3039이다. 앞서 #3021이 11-18에 기존 mHC 연산자 두 개를 삭제하고 리뷰를 거친 공개 API 파괴로 등록했다. 하루 간격으로 교체 경로가 완료되었다.

pre 단계는 #3032로 머지되었으며 18개 파일 변경, +1106/-21이다. DeepSeek-V4-Flash와 GLM-5.3-Flash의 mHC 전단을 실행한다. 내용은 fn 프로젝션과 제곱 노름, pre와 post 가중치, Sinkhorn, 그리고 가중 흐름 합산을 포함한다.

프로젝션은 float32 정밀도를 보장한다. fn은 세 개의 bfloat16 항으로 텐서 코어에 진입하며, 16채널마다 한 번씩 64×72 WGMMA를 수행한다. 각 64채널 슬롯은 다시 float32로 누적된다. token 축은 런타임 길이이며, 한 번의 실행으로 임의 token 수를 커버한다. 비교 대상은 vLLM의 TileLang mhc_pre와 torch.compile 참조 구현이다.

post 단계는 #3035로 병합되었으며, 16개 파일이 변경되고 +592/-21을 기록했다. 이는 블록 출력을 n개의 잔차 스트림에 다시 혼합한다. 원소별로 post_layer_mix[j] * x + sum_i comb_res_mix[i,j] * residual[i]로 작성되며, float32로 계산한 후 한 번에 bfloat16으로 반올림한다.

스레드는 16바이트 세그먼트 단위로 x와 각 스트림을 혼합한다. 작은 호출은 한 세그먼트, 큰 호출은 네 세그먼트를 사용한다. 출력은 TileKernels의 mhc_post_fwd와 비트 단위로 동일하다.

head 단계는 #3039로 병합되었으며, 15개 파일이 변경되고 +778/-9를 기록했다. 이는 LM head 이전에 n개의 잔차 스트림을 하나로 접으며, DeepSeek-V4-Flash의 ParallelHead.hc_head에 대응한다. SM당 최대 두 개의 토큰을 처리하며, 초과 시 하나의 CTA가 한 개에서 네 개의 토큰을 스트리밍하고 각 hc_fn 벡터가 모든 토큰을 서비스한다.

manifest 항목은 구현 완료로 전환되었으며, GLM-5.3-Flash의 3000 토큰 행이 첨부되었다. 비교 대상은 vLLM의 hc_head 융합 커널과 torch 참조이다.

세 건 모두 해당 제안을 종료했다: #2921, #2970, #2971. 구 연산자 삭제와 신 연산자 병합의 중간 상태는 하루만 유지되었으며, 인터페이스 교체로 인한 단절 버전은 남지 않았다.

오늘의 중점: GEMM 선택기 규칙 하나 변경으로 302개 형상, MXFP4 MoE 디코딩이 수락 기준 도달

11-19 TileOPs 성능 라인에서 총 여섯 건이 병합되었다. 두 건은 자체 평가에서 수락 기준에 도달했고, 네 건은 여전히 수락 기준 미만으로 표시되었다. 네 건의 지원 설명에는 모두 각 행이 메인 브랜치보다 빠르다고 명시되어 있다.

GEMM 선택기가 규칙 하나를 변경했다(#3045). NT 계열 GEMM에서 128행 그리드가 coop2 폭에서 한 웨이브에 들어갈 수 있으면, 가장 좁은 coop2 tile을 선택하고 더 좁은 다중 웨이브로 분할하지 않는다.

판정 기준은 두 가지이다. 마지막 행 tile의 두 64행 소비 그룹 모두에 행이 할당되어야 하며, 그리드가 한 웨이브의 15/16을 채워야 한다.

이 규칙은 302개 모델 형상에 영향을 준다. 단일 카드 H200에서 메인 브랜치 선택 방식보다 느린 사례는 없었으며, 286개 형상이 1.03배에서 2.6배 빨라졌다. GLM-5.3-Flash의 라우팅 prefill(N=288)은 82.24마이크로초에서 32.13마이크로초로 감소했다.

해당 변경은 잠재적 결함도 수정했다. float32 coop2 tile을 전체 블록으로 분할할 때 128번부터 383번 스레드의 누산기 복사가 누락되어 공유 메모리에 초기화되지 않은 내용이 남는 문제였다.

MXFP4의 MoE 그룹 GEMM이 수락 기준에 도달했다(#3044). 공유 디코딩 커널이 추가되었으며, 조건은 행 정렬이 128의 배수, 스케일이 e8m0, K가 2048의 배수이다. 128개 토큰을 WGMMA의 M 피연산자로, 128행 가중치를 N 피연산자로 사용한다.

가중치는 일곱 개의 프로덕션 warp가 CTA당 한 번 디코딩하여 fp8 공유 메모리 타일에 기록한다. 근본 원인은 구 커널이 수학 warp에서 가중치를 디코딩하여 원소당 한 번의 FMUL과 한 번의 FFMA가 발생한 것이었다. 수학 warp당 K 스텝마다 약 363개 명령어가 발생하여 512 텐서 사이클에 대응하며, 텐서 파이프라인은 36%만 가동되었다.

GQA 가변 길이 어텐션이 헤드 차원 56에서 80에 대해 세 개의 소비 warpgroup으로 변경되었다(#3041). 192행 tile에서 세 개의 64행 소비 그룹이 교대로 텐서 코어를 점유한다.

근본 원인은 72채널일 때 exp2의 소요 시간이 해당 곱셈 텐서 시간의 64/80을 차지한 것이다. 두 소비 그룹일 때 한 그룹의 softmax가 다른 그룹의 곱셈을 지연시켰다. ncu는 텐서 54.7%, XU 45.2%를 보여 두 요소가 거의 직렬로 실행되었음을 나타낸다.

해당 변경은 한 가지 제한을 명시했다: TileFoundry의 schedule finalize가 현재 빌드에서 전달된 스케줄을 TIR로 낮출 수 없다(tile-ai/topa#42 참조). 커널은 실측 프로토타입 기반으로 수작성되었으며, 스케줄은 final_hir.py에 작성되어 있다.

KDA의 bf16 주어진 게이팅 prefill이 단일 중앙 집중 시작으로 변경되었다(#3053, 9개 파일, +749/-225). SM90에서 기존에는 시퀀스와 값 헤드 로그 수에 따라 두 경로를 사용했다. 새 경로는 공동 중앙 집중 텐서 코어 프로그램이 모든 chunk를 먼저 준비한 후 상태 순회를 수행한다. fp16 주어진 게이팅과 원시 게이팅은 여전히 구 경로를 사용한다.

두 건은 자체 평가에서 수락 기준 미만이다. W4A16의 K tile 메타데이터가 비동기 복사로 변경되었다(#3050). 4바이트 미만의 행별 제로 포인트를 네 개의 정렬된 그룹 윈도우로 오버페치하여 4바이트 및 8바이트 cp.async로 전송한다. 프로듀서 측은 따라서 K tile의 TMA를 즉시 발행할 수 있다.

RoPE는 로드 순서를 조정했다(#3040). 열 복사가 있는 헤드는 입력 벡터를 먼저 로드한 후 위치를 읽어, ptxas가 위치 clamp에서 대기하는 것을 방지한다. 작은 GPT-J 호출은 따라서 DRAM 지연을 한 번 덜 지불한다. 동일 변경은 key.view(-1, 0)에서 남은 key가 실패하는 문제도 수정하여 이제 빈 결과를 반환한다.

1. 핵심 프로젝트 진행 상황

1.1 레이아웃 자리표시자 변수가 직렬화를 넘어 바인딩을 유지하고, spawn 하위 프로세스 오프로드 시 더 이상 단사 오류가 발생하지 않음

tilelang 메인 저장소 모니터링 기간 내 두 건이 병합되었습니다. 첫 번째는 #4410으로, 3개 파일을 변경했으며 +301/-2입니다. 이는 레이아웃 객체가 프로세스와 디스크 왕복 후 무효화되는 문제를 수정합니다.

tl.Layout, tl.Fragment, tl.PartialFragment는 프로세스 내 싱글턴 tirx::Var 자리표시자로 인덱스와 스레드 매핑을 표현합니다. _i, _j 등은 InputPlaceholder(i)를 사용하고, _rep는 ReplicationPlaceholder()를 사용합니다.

Forward, OutputShape, DetectInjective, ForwardThread의 판단 근거는 name_hint가 아니라 Var의 객체 동일성입니다.

레이아웃 또는 T.annotate_layout이 포함된 PrimFunc가 pickle 또는 tvm.ir.save_json과 load_json을 거치면, 역직렬화 시 자리표시자가 재생성됩니다. 새로 생성된 VarNode는 수신 프로세스의 싱글턴과 더 이상 동일하지 않습니다.

메인 브랜치에서 세 가지 오류를 직접 재현할 수 있습니다. pickle 왕복 후 map_forward_index([7])이 [7]이 아닌 [_i]를 반환합니다. OutputShape()는 (32,)를 (_i + 1,)로 계산합니다. spawn으로 생성된 worker 프로세스에서 주석이 포함된 PrimFunc를 오프로드하면 the forward map must be injective 오류로 실패합니다.

수정 방법은 바인딩된 자리표시 Var 참조를 동일한 ObjectGraphSerializer 채널에 포함시키는 것입니다. 두 필드가 관련됩니다: LayoutNode의 _forward_vars와 FragmentNode의 _replicate_var. 두 필드의 직렬화 순서는 forward_index와 forward_thread보다 앞섭니다. 이 필드들은 repr, init, compare, hash 및 구조적 동등성에 참여하지 않으며, 기본값은 nullptr입니다.

실제 효과는 다중 프로세스 컴파일 경로를 사용할 수 있게 된 것입니다.

출처: https://github.com/tile-ai/tilelang/pull/4410

1.2 개발 버전 번호에서 툴체인 태그 제거, 동일 wheel이 더 이상 CUDA 버전별로 분기되지 않음

#4409는 7개 파일을 변경했으며 +16/-76입니다. 버전 번호에서 백엔드 접미사를 정리합니다.

발단은 TileLang이 과거 CUDA 12.8과 13.0에 대해 각각 wheel을 빌드했기 때문입니다. #1826 이후 하나의 wheel이 여러 CUDA 툴체인 버전을 동시에 지원합니다. 따라서 기존 접미사는 오해를 유발합니다. CUDA 13.0 이미지에서 빌드된 체크아웃은 0.1.15+cu130.gitabcdef12를 보고하지만, 빌드 머신의 툴체인 버전으로는 해당 wheel이 어떤 백엔드를 지원하는지 알 수 없습니다.

변경 사항은 백엔드 접미사와 NO_TOOLCHAIN_VERSION 스위치를 삭제합니다. 동일 체크아웃은 모든 구성에서 통일되게 0.1.15+gitabcdef12를 보고합니다. TILELANG_BUILD_WHEEL_WITH_DATE=ON으로 설정하면 0.1.15+d20261119.gitabcdef12를 보고합니다. PyPI 배포에는 여전히 기본 버전 번호를 사용합니다.

tilelang.build_date()는 이에 따라 두 가지 위치를 모두 지원합니다. 날짜는 + 바로 뒤에 올 수 있으며, 기존 wheel의 0.1.15+cuda.d20261119.gitabcdef12 형식도 호환됩니다.

작성자는 검증 범위를 나열했습니다. 세 가지 패키징 테스트 통과, CUDA 12.8, CUDA 13.0, ROCm, CPU, 날짜 포함 야간 빌드 및 배포 빌드의 PEP 517 메타데이터 확인, pre-commit 전체 통과.

3.1 어텐션 sink 보완: DSADense와 DSAPaged 같은 날 병합

DSADense 측은 #3038이며, 파일 5개 변경, +228/-82이다. 이의 SM90 커널은 attn_sink와 is_causal=False를 지원하기 시작했다. 이때 인덱스만으로 key를 선택하며, -1은 해당 슬롯을 건너뛴다는 의미이고, 각 헤드의 sink logit은 해당 softmax 분모에 포함된다.

topk는 더 이상 128의 배수일 것을 요구하지 않는다. 초과 부분은 데드 슬롯이다. 마지막 블록 쌍에서 홀수 블록이 전체 구간이 topk를 넘으면 짝수 블록만 로드하고 점수화한다. 대조군 FlashMLA는 한 번의 실행으로 이번 배치의 모든 kv 행을 완료하도록 변경되었으며, 그 인덱스는 -1로 128의 배수까지 보완된다.

3.2 FP4 그룹 양자화 적용, MoE 게이팅에 해시 라우팅과 sqrt-softplus 보완

양자화 측에 FP4QuantPerGroupFwdOp가 새로 추가되었다(#3027, 파일 15개, +810/-41). 시그니처는 block_size=32, inplace=False이며, bfloat16을 e2m1 코드로 양자화하고, 두 코드를 1바이트로 하며, 블록 스케일은 2의 거듭제곱인 float8_e8m0fnu이다. 출력은 DeepSeek-V4-Flash의 fp4_act_quant와 비트 단위로 일치한다.

반올림은 FP4 변환 명령을 사용하지 않는다. 대신 float32 비트에 대한 정수 연산으로 변경하고, float32 덧셈을 한 번 추가한다. 해당 커널은 FP8QuantPerTokenGroupFwdOp와 group_quant.py를 공유한다.

write_in_place는 그룹 수가 그리드 y 범위를 초과하는 스트라이드 행이 먼저 연속 복사를 수행하도록 합니다. 이 커밋은 덤으로 FP8 토큰별 그룹 양자화의 inplace=True 경로도 함께 고쳤습니다.

MoE 쪽은 #3036으로, 4개 파일을 변경했으며 +360/-66입니다. FusedTopKFwdOp에 scoring_func="sqrtsoftplus"를 추가했고, correction_bias와 그룹화의 유무를 모두 지원합니다. 또한 호출자가 expert_ids를 지정할 수 있도록 지원하며, DeepSeek-V4-Flash의 게이팅과 그 해시 라우팅 첫 레이어를 커버합니다.

expert_ids가 주어지면, 커널은 해당 expert들의 logit만 읽습니다. 재정규화되지 않은 softmax는 전체 행을 읽으며, bias는 읽지 않습니다. 여전히 거부되는 조합은 「bias가 있는 softmax 선택」입니다.

출처: https://github.com/tile-ai/TileOPs/pull/3027 https://github.com/tile-ai/TileOPs/pull/3036

3.3 GatedPoolCompress, 한 번의 실행으로 요청별 링 분할 KV 풀링 완료

#3033은 12개 파일을 변경했으며 +1363/-3입니다. GatedPoolCompressFwdOp를 구현하며, DeepSeek-V4-Flash의 compressor와 GLM-5.3-Flash indexer의 키 풀링에 대응합니다.

요청은 묶음 처리됩니다. 특정 요청의 시작점 이전에 위치한 위치들은 해당 요청의 링에서 오며, 링 크기는 C * ratio 행입니다. 호출은 자신의 마지막 몇 개 위치의 행을 기록하며, 이전 호출의 마지막 토큰을 롤백할 수 있습니다.

구현은 이전 실행만 참조하며 호스트 동기화가 없습니다. 요청당 하나의 block으로, 먼저 자신의 링을 읽는 윈도우들을 풀링한 뒤, 링과 유효 플래그를 다시 기록합니다. 나머지 윈도우들은 cu_seqlens에 대한 warp 수준 ballot 검색을 통해 자신이 속한 요청을 찾습니다.

이 커밋은 또한 배치 처리된 torch_program을 기준으로 하는 torch 베이스라인을 추가하고, kv_state와 score_state를 연속으로 선언했습니다.

출처: https://github.com/tile-ai/TileOPs/pull/3033

3.4 TileFoundry, 슬라이스 mesh와 Varying 값을 병렬 계획 분석에 포함

TileFoundry 모니터링 기간 내 한 건이 머지되었습니다(#356, 123개 파일, +2752/-557). 메모리 및 트래픽 분석을 변경한 건입니다.

발단은 discussion #350입니다. 분석기가 PP, TP, EP, HSDP 여러 병렬 계획을 비교할 수 있어야 합니다. 기존 구현은 파이프라인 스테이지별로 각 GPU 피크를 합산했고, 슬라이스 mesh 간의 Reshard를 0바이트 뷰로 기록했으며, Varying을 가진 피연산자를 단일 피연산자 타입만 취하는 연산자에서 누락시켰습니다.

변경 후, 타입 추론은 단일 규칙을 통해 피연산자의 샤딩 속성(operand_types, combine_operand_attrs)을 읽습니다. Broadcast와 Varying이 만나면 Varying의 셀 단위 저장이 되고, Partial과 Varying이 만나면 거부됩니다.

슬라이스 mesh 간의 Reshard는 「해당 값을 얻는 셀 수」만큼 한 번의 복사로 계산합니다. 부분적으로 겹치는 슬라이스 간의 Split 또는 Partial 이동은 거부됩니다. 피크는 소속 셀 단위로 집계하도록 변경되었습니다.

추가로 세 가지가 함께 반영되었습니다. JSON 호출 행에 피호출자(callee, callee_ref)와 이를 정의한 Module을 명시합니다. 한 번의 호출이 텐서 리프 단위로 하나의 출력 경계를 제시하며, 중첩 튜플도 포함되어 생성된 Module이 분석 가능해집니다. repeat_interleave는 입력의 Broadcast mesh를 유지합니다.

이 커밋은 PP, TP, EP, HSDP, FSDP를 비교하는 CUDA 케이스를 추가했습니다. 생성된 모듈은 CLI로 기록되고, 다시 로드되며, 자동 미분 결과와 대조되고 실측됩니다.

출처: https://github.com/tile-ai/TileFoundry/pull/356

3.5 새 목표 네 건 개설: DSAPaged bf16, AvgPool1d, DeltaNet, Mamba

모니터링 기간 내 TileOPs에 형상과 목표 배율을 갖춘 작업 항목 네 건이 새로 개설되었습니다.

#3049는 DSAPaged의 bf16 행이 DeepSeek-V4-Flash에서 FlashMLA를 따라잡을 것을 요구합니다. 해당 항목은 이번 기간에 머지된 #3048과 대응하며, 「먼저 목표를 세우고, 그다음 구현을 머지」하는 순서에 속합니다.

#3051은 가장자리가 잘린 AvgPool1d 윈도우를 처리합니다. 방식은 데이터를 레지스터로 읽어들이고, block을 절약할 수 있을 때 하나의 SM이 하나의 block만 발행하도록 하는 것입니다.

#3054는 DeltaNet의 chunk 입력이 스트라이드 텐서를 받아들이도록 요구합니다. #3013은 CausalConv1dFwdOp와 CausalConv1dUpdateFwdOp에 팽창 컨볼루션과 float32 필터를 추가했습니다.

또한 #3052는 유지보수성 머지로, 주석과 문서만 보강합니다. W4A16의 메타데이터 윈도우가 왜 단일 소비 warpgroup에만 적용되는지 설명하고, 선택기의 128, 256, 512 폭 K tile과 명시적 384 폭 K tile을 docstring에 작성했습니다.

해당 커밋은 동시에 회귀 테스트를 하나 추가해 그룹 수 검사를 고정했다. 작성자가 해당 검사를 제거했을 때의 결과를 제시했다. 명시적 384 폭 설정은 잘못된 결과를 반환하며, 1x128x36864, split 24에서 상대 오차는 0.457이다.

5. 트렌드 관찰

  • 인터페이스 파괴에는 후속 대체가 동반된다: 11-18에 기존 mHC 연산자 두 개를 삭제하고 API 파괴로 등록했으며, 11-19에 대체 연산자 세 개가 전부 병합됐다. 대체 PR은 삭제 이전에 이미 열려 있었고, 중간 상태는 하루만 유지됐다.
  • 양자화 정렬은 비트 단위 일치를 기준으로 한다: FP4 그룹 양자화는 DeepSeek-V4-Flash의 fp4_act_quant와 비트 단위로 동일해야 한다. FP8 경로는 동일한 group_quant.py를 공유한다. 수용 기준은 오차 범위가 아니라 비트 수준 동등성이다.
  • 성능 최적화는 형상별 튜닝에서 선택기 규칙으로 전환 중이다: #3045는 하나의 규칙으로 302개 모델 형상을 커버하며, 단 한 건도 느려지지 않을 것을 요구한다. 이 요구는 단일 지점 속도 향상보다 충족하기 어렵지만, 장기적으로 유지하기는 더 쉽다.
  • Ascend 두 라인의 분업이 명확하다: MLIR 노선은 연산자별 방언을 계속 확장하며 하루 세 건, 메인 저장소는 릴리스와 CI 엔지니어링으로 전환해 OBS 라운드, 야간 NPU 스모크, 튜닝 스킬을 같은 주에 추진한다. 전자는 표현 범위를 넓히고, 후자는 사용 진입 장벽을 낮춘다.
  • TileFoundry는 「컴파일 가능」에서 「양자화 가능」으로 나아간다: PP, TP, EP, HSDP가 동일한 분석기에서 비교되고, 슬라이스 mesh의 Reshard가 복사 비용으로 계산되기 시작한다. 비용 모델이 신뢰할 수 있게 되면 역으로 프런트엔드 선택에 영향을 미친다.

TileOPs의 16건 병합과 조직 수준 검색의 총 23건은 건별로 일치하며 중복 집계는 없습니다. 심사 중 항목은 각각 개설 날짜와 최근 업데이트 날짜를 표기하여 오래된 제안을 당일 신규 개설로 기재하지 않도록 합니다. #1760, #3924, #4012, #4016은 모두 본 모니터링 기간 이전에 개설되었으며, 본문에 개설 날짜를 명시하고 모니터링 기간 내 진행 상황만 집계했습니다.

수집 과정에서 모니터링 기간 말미에 미인증 GitHub API 속도 제한에 도달했습니다. 브랜치와 태그 정보는 Atom 피드 및 검색 API로 재확인했으며 결론에는 영향을 미치지 않았습니다. RISC-V 4개 출처 점검 결과는 비어 있었으며, 변경 없음으로 처리하고 수집 실패로 간주하지 않습니다. 뉴스 측은 5개 쿼리로 재확인한 결과 빈 구간임을 확인했으며, 빈 결과를 수집 장애로 추정하지 않았습니다.
