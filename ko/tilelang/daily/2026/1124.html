오늘의 핵심: 메인 저장소 JIT에 프로세스 수준 병렬 컴파일 추가, GIL이 스레드 풀에 가하는 제한 우회

#3903이 11-23 11:57 메인 브랜치에 진입, 6개 파일 변경, 552줄 추가, 100줄 삭제.

tilelang.par_compile() 및 kernel.par_compile()에 선택적 매개변수 executor="process" 추가. 제안서에 명시된 동기는 Python 측에서 컴파일 부하가 무거운 경우 스레드 기반 병렬 처리가 GIL에 의해 제한된다는 점.

프로세스 모드에서 부모 프로세스는 먼저 target, 실행 백엔드, pass 설정 및 캐시 루트 디렉터리를 정규화. 메모리 또는 디스크 캐시에 이미 히트된 설정은 워커를 생성하지 않음. 미스된 항목은 key 기준 중복 제거 후 분배.

각 워커는 KernelCache.compile_to_disk()를 사용해 결과를 디스크 캐시에 기록하고, 게시된 cache_path를 반환. 워커의 예외 유형과 traceback은 IPC를 넘어 보존됨.

부모 프로세스는 KernelCache.load_published_entry()로 직접 로드하며, 직렬 컴파일로 폴백하지 않음. 오류 발생 시 대기 중인 future를 즉시 취소.

디스크 캐시를 지원하지 않는 백엔드는 워커 생성 전에 거부됨, 예를 들어 TorchKernelCache(supports_disk_cache = False). 이렇게 하면 전역 캐시 상태를 변경하지 않음.

스레드 모드는 여전히 기본값. 프로세스 모드는 캐시 활성화를 요구하며, 스크립트에 if __name__ == "__main__": 보호 진입점을 요구.

제안서에는 Ascend에서 64개 프로세스로 검증, 128개 SwiGLU 및 MoE 설정 커버 기록. 회귀 테스트는 testing/python/jit/test_tilelang_jit_parcompile.py에 위치. 케이스에는 사용자 정의 TILELANG_CACHE_DIR 하의 프로세스 컴파일 및 중복 제거 포함.

출처: https://github.com/tile-ai/tilelang/pull/3903

오늘의 핵심: TileOPs 하루 열여덟 건, 주된 흐름은 0.1.15의 성능 퇴행을 0.1.12로 되돌리는 것

11-23 종일 TileOPs에 18건이 머지되었다. 같은 날 새로 열린 작업 항목 #3133은 목표를 명시했다: 최초 TileLang 0.1.15 야간 테스트에서 0.1.12보다 느려진 25개 행을 되찾는 것.

세 건의 커밋 제목에는 직접 「0.1.12 시간으로 복구」라고 적혀 있다. #3138은 MXFP4 레지스터 프래그먼트 커널을 복구한다. #3136은 MaskedScatterFwdOp에서 0.1.15에 새로 추가된 경계 검사를 제거한다. #3131은 HyperConnectionHeadFwdOp에 대해 동일하게 처리한다.

또한 세 건은 외부 구현과의 격차를 좁힌다. #3099는 GatedPoolCompressFwdOp의 DeepSeek-V4-Flash 디코딩에서 SGLang과의 격차를 좁힌다. #3097은 HyperConnectionPreFwdOp의 디코딩 및 중간 길이 프리필에서의 격차를 좁힌다. #3101은 DSADenseFwdOp의 행을 상주 CTA에서 실행하고 행 내부의 죽은 꼬리 블록을 건너뛰게 한다.

메모리 접근 측에서 바뀐 것은 데이터 인출 입도다. #3139는 페이지드 캐시의 전체 행을 벡터당 16바이트, 섹터를 가득 채우는 저장으로 가져오게 한다. #3140은 SSDRecurrentFwdOp의 상태를 16바이트 레인 벡터로 흐르게 하고, 각 행은 warp shuffle로 합산한다.

양자화와 원소별 연산이 각각 한 건씩. #3137은 16비트 게이티드 tanh-GELU를 x / (1 + exp2)로 계산하여 float32에서 한 번만 반올림한다. #3132는 FP8의 그룹 최댓값을 입력 dtype 내에서 리덕션하고 불필요한 no-op clamp를 한 번 제거한다.

모델 측 두 건. #3129는 DeepSeek 모델을 DeepSeek-V4-Flash로 명명하고 generate가 max_seq_len을 초과하지 않도록 제약한다. #3130은 DeepSeek TileKernels를 FP8, FP4 및 hyper-connection 연산자 옆에 함께 배치하여 시간을 측정한다.

#3135는 야간 성능 퇴행을 Perf Tracker 대시보드에 등록한다. #3124와 #3125는 모니터링 기간 시작 후 24분 만에 메인에 진입하며, 각각 0.1.15에서의 동시성 튜닝 컴파일과 야간 벤치마크 참조 수정을 담당한다.

출처: https://github.com/tile-ai/TileOPs/pull/3133

1. 핵심 프로젝트 진행 상황

1.1 야간 휠이 Dist 작업으로 발행되도록 변경, GitHub Releases와 Huawei Cloud OBS 이중 채널

#4411은 11-23 21:30에 메인에 진입했으며 2개 파일을 변경하고 414줄을 추가, 11줄을 삭제했다. 제안서는 배경을 설명한다: 기존 tile-ai/tilelang-nightly 파이프라인이 중단되었고, OBS는 이전에 중국 본토 다운로드에 연결되지 않았다.

방식은 Dist 작업에서 이미 빌드된 휠을 각 플랫폼 간에 재사용하는 것이다. test-wheels-gpu가 통과한 후 각 플랫폼의 휠이 곧바로 발행에 들어간다. schedule과 workflow_dispatch로 트리거된 빌드에는 날짜와 커밋 접미사가 붙으며, 스위치는 TILELANG_BUILD_WHEEL_WITH_DATE=ON이다. PyPI 발행 버전 형식은 변경되지 않는다.

두 발행 채널은 서로 독립적이다. publish-github-nightly는 휠을 tile-ai/tilelang-nightly의 GitHub Releases에 발행한다. 동시에 SHA-256이 포함된 인덱스 https://tile-ai.github.io/whl/nightly를 갱신한다. NIGHTLY_GITHUB_TOKEN이 설정되지 않으면 해당 채널은 건너뛰고 경고를 낸다.

publish-obs는 휠과 퍼센트 인코딩된 TileLang/index.html을 obs://ascend-triton-open/TileLang/에 업로드한다. 이어서 익명 HTTPS로 읽기 가능 여부를 검증하고, 실패 시 -acl=public-read로 폴백한다. 인덱스는 https://tile-ai.github.io/whl/nightly-cn에 기록된다.

출처: https://github.com/tile-ai/tilelang/pull/4411

1.2 레이아웃과 프래그먼트 객체가 자체적으로 플레이스홀더 변수를 보유, 입력 차원 상한 16 해제

#4416은 11-23 21:07에 메인에 진입했으며 23개 파일을 변경하고 607줄을 추가, 583줄을 삭제했다.

이전에는 세 가지 레이아웃 타입이 프로세스 수준의 정적 tirx::Var 싱글턴에 의존했다. 세 타입은 tl.Layout, tl.Fragment, tl.PartialFragment이다. 싱글턴은 InputPlaceholder(0..15)와 ReplicationPlaceholder()이다.

파생된 문제는 세 가지다. FFI 직렬화에 수작업 리플렉션 접근자를 작성해야 했다. 입력 차원이 16으로 강제 제한되었다. src/layout/ 외부의 호출자가 공유 전역 Var를 통해 암묵적으로 결합되었다.

수정 방식은 TVM의 tirx::IndexMap에 맞추는 것이다. LayoutNode는 forward_vars_를 보유하고, FragmentNode는 replicate_var_를 보유한다. 둘 다 forward_index와 forward_thread 이전에 SEqHashDef()로 등록한다.

이로써 두 JSON 그래프 인터페이스는 바로 직렬화할 수 있다. StructuralEqual과 StructuralHash는 alpha 동등성을 갖는다. 생성자에서는 MakeLayoutVars(ndim)과 MakeReplicateVar()로 규범 변수를 통일해 생성한다.

출처: https://github.com/tile-ai/tilelang/pull/4416

1.3 메인 저장소 심사 대기열: CUDA 컴파일 실패 3건 수정, Ascend 측 휠 테스트 보강

메인 저장소 심사 대기 27건 중, 모니터링 기간 내 업데이트가 있는 것은 컴파일 실패와 Ascend 엔지니어링 두 갈래에 집중되어 있다.

CUDA 측 3건은 새로 보고된 결함을 겨냥한다. #4473은 bf16의 T.sigmoid가 sm_100a와 sm_120에서 컴파일 실패한다고 보고했다. 오류는 Cannot convert type float32x16 to CUDA type이며, 수정은 #4478이다. #4472는 bf16 어텐션이 sm_75와 sm_70에서 T.gemm의 FMA 폴백 프레임으로 인해 “Layout infer conflict”가 발생한다고 보고했다.

#4419는 Ascend NPU 휠 테스트를 Dist 파이프라인에 추가한다. #4399는 CANN 9.1 호환과 SDK 버전별 커널 캐시를 추가한다. #4421은 max_vector_bits 기본값을 128로 바꾸고, fp8의 SIMT 폭을 8 레인으로 제한한다. #4469는 AI 코어 용량으로 split-K의 상주 블록 수를 검증한다.

또한 2건은 skill 형태로 Ascend 지식을 축적한다. #3910은 Ascend 950 아키텍처 지식이고, #4471은 Ascend 성능 튜닝이다.

출처: https://github.com/tile-ai/tilelang/pull/4478

1.4 TVM 서브모듈, Z3 오증명 2건 수정, 메인 저장소 bump는 심사 중

TVM 서브모듈 tilelang_main 브랜치에는 모니터링 기간 내 2건이 머지되었으며, 모두 동일 저자가 제출했다.

#97은 신뢰성 결함 2건을 수정한다. 첫째, VisitShiftOp가 push()되지 않은 공유 솔버에서 solver->add를 실행하여, 모든 시프트 표현식이 시프트량 b를 영구히 제약한다. 그 결과 b < 0 또는 b >= 64인 외부 스코프에서 이후 술어들이 증명 가능하다고 판정될 수 있다.

둘째, DivNode와 ModNode는 0 방향 절단을 따르지만, Z3의 Int에 대한 네이티브 /와 %는 유클리드 의미론이다. 따라서 CanProve(truncmod(a, 4) >= 0)은 a가 음수일 수 있을 때도 거짓 성공한다. 수정 방식은 floordiv와 floormod로 대칭 인코딩하고, a >= 0 분기에 따라 식을 선택하는 것이다.

#96은 상수 부호 있는 오른쪽 시프트를 별도로 수정하여 정수 연산으로 바꾼다. 메인 저장소 측 후속 #4482는 여전히 심사 중이다.

출처: https://github.com/tile-ai/tvm/pull/97

2. 멀티 백엔드 적응 (Ascend / Hygon / Moore Threads / MetaX)

2.1 PTO 생성기, 루프 캐리 스칼라 보완, DeepGEMM 5개 케이스 컴파일 복구

#4418은 11-23 10:17에 메인라인에 진입했으며, 파일 1개만 변경하고 23줄 추가, 11줄 삭제했다.

문제는 CANN 9.2.0에 내장된 PTODSL(PTOAS 0.65)에서 발생했다. DeepGEMM의 scale 꼬리와 group padding 케이스 5개가 컴파일 실패했으며, 모두 grouped scale 변환 내의 동일한 루프에 도달했다. MLIR이 생성된 scf.while을 거부하며 operand #0 does not dominate this use를 보고했다.

커널은 group_start를 0으로 초기화한 뒤 if lo > 0 내에서 갱신한다. 첫 반복에서는 분기가 선택한 값을 사용해야 한다. PTODSL의 활성 분석이 이 의존성을 누락하여, 분기 내의 값을 루프 입력으로 직접 사용한다. lo == 0일 때 해당 값은 정의되어 있지 않다.

수정 방식은 PTO 코드 생성기가 while 헤드를 출력하기 전에 루프 캐리 지역 변수를 수집하는 것이다. 이미 스코프 내에 있고 루프 본문에서 할당되는 일반 스칼라에 대해 각각 한 번씩 베어 이름 읽기를 출력한다. 생성된 PTODSL은 루프 진입점에서 group_start, lo, num_ranges 세 줄의 읽기가 추가된다.

출처: https://github.com/tile-ai/tilelang/pull/4418

3.3 FlashQLA, sm120에서 공유 메모리가 컴파일러에 의해 조기 읽히는 문제 수정

QwenLM/FlashQLA의 #55가 11-23 18:37에 병합되었으며, 1개 파일을 변경하고 5줄을 추가했다.

근본 원인은 PTX로 확인했다. TileLang 0.1.12의 tl::mbarrier_wait는 tl_templates/cuda/barrier.h에 위치한다. 해당 인라인 어셈블리에는 "memory" clobber가 없다.

blackwell_sm120/fused_fwd.py에서 S warpgroup(tx < 128)은 정적 공유 메모리에 절대 쓰지 않는다. 이는 컴파일 타임 상수 오프셋인 g_exp_shared[block_S - 1]만 읽는다. use_initial_state=False로 특수화될 때, nvcc 또는 cicc가 ld.shared.f32를 for i_s 루프 밖으로 끌어올린다. 읽히는 것은 초기화되지 않은 공유 메모리이다.

그 결과는 0번째 블록 이후 상태 오차가 커지는 것이다. 초기화되지 않은 공유 메모리에 NaN 비트 패턴이 포함되어 있으면 곧바로 NaN이 발생한다.

수정안은 torch.empty(...)와 T.clear(h_fragment)를 그대로 유지한다. 이어서 barrier 대기 이후에 블록 내 펜스 호출을 한 번 삽입한다. 삽입 위치는 T.barrier_wait(bar_1, i_s % 2) 이후다. 호출 형식은 T.call_extern("void", "__threadfence_block")이며, 두 warpgroup 모두에 추가한다. PTX 상에서는 membar.cta로 나타난다.

검증 환경은 RTX 5090, CUDA 12.8, PyTorch 2.8.0+cu128, TileLang 0.1.12이다.

  • 버전 업그레이드의 비용이 행 단위로 정량화되었다. 0.1.15 출시 이후 TileOPs는 “25줄 되찾기”를 프로젝트로 세우고 이틀 내에 최소 네 건을 0.1.12 시점으로 되돌렸다. 나머지는 야간 대시보드에서 행별로 정리한다. 성능 회귀는 더 이상 체감으로 서술되지 않고 행 번호순으로 줄을 선다.

  • Ascend의 공학 작업이 연산자에서 릴리스 체인으로 옮겨가고 있다. MLIR Ascend는 하루에 방언 연산자 일곱 개를 병합하는 동시에 야간 휠을 아카이브와 인덱스에 연결했다. 메인 저장소는 Dist 휠을 GitHub Releases와 Huawei Cloud OBS에 연결하고, Ascend NPU 휠 테스트 추가를 계획 중이다.

  • 신규 보고 결함의 유형 분포는 안정적이다. 이날 메인 저장소 이슈 9건 중 6건은 문서와 구현 불일치, 3건은 컴파일 실패다. 문서류는 Ascend 대상 이름과 PTO 파라미터 이름에 집중되어, 이 두 곳의 이름 변경이 문서와 내보내기 목록에 동기화되지 않았음을 보여준다.

  • 병렬 컴파일이 스레드에서 프로세스로 전환된 것은 단일 머신 다중 코어가 autotune 시나리오에서 이미 GIL에 막혔음을 반영한다. 프로세스 모드는 디스크 캐시와 진입점 보호를 요구하며, 실질적으로 컴파일 산출물을 캐시 객체로 관리하는 것이지 컴파일러를 함수 호출로 다루는 것이 아니다.

  • RISC-V 측은 이날 커뮤니티 인덱스 계층의 동작만 있었다. 인덱스 페이지는 kubuds의 TVM 노선 포크를 수록했으나, 두 RISC-V 백엔드 노선 모두 코드 커밋이 없다. TVM과 MLIR 두 구현은 여전히 각자 추진 중이다.

검증 설명

기준: 모니터링 기간은 베이징 시간 11-23 07:00부터 11-24 07:00까지 총 24시간이다. 저장소 커밋은 committer 시간 기준으로 집계하며, 먼저 이전 회차 마감 시점인 11-23 07:00과 비교한 뒤 신규 여부를 판정한다.

#3124와 #3125의 병합 시각은 11-23 07:24로, 모니터링 기간 시작 이후 24분에 해당하므로 이번 회차에 포함한다. MetaX main의 동기화 커밋은 업스트림 #3903과 동일 SHA이므로, 본문에서는 업스트림 동기화로 처리하고 MetaX 백엔드 진전으로 작성하지 않는다.

RISC-V 4개 소스 중 인덱스 페이지에만 변화가 있었고, 그 변화는 병합 동작이며 README 문구 커밋은 모니터링 기간 이전이다. 본문에서는 노선별로 각각 서술하고, 인덱스 페이지 변화를 RISC-V 백엔드 코드 진전으로 계산하지 않았다.

조직 수준의 33건 병합과 저장소별 메인 브랜치 커밋을 하나씩 대조했다. TileOPs 18건 커밋은 18건 PR과, tilelang 4건은 4건과, tvm 2건은 2건과 대응한다. MLIR Ascend 메인 브랜치에는 2건의 커밋이 있으며, 별도로 7건의 연산자 PR이 병합되었고 히스토리가 압축되었거나 브랜치를 통해 병합되었다. 차이가 있는 부분은 본문에서 PR 기준으로 서술하고 커밋 수로 반복하지 않는다.

뉴스 측은 Google News 중영문, Hacker News, arXiv 세 경로로 재검증했으며, 모니터링 기간 내에 TileLang 관련 보도는 확인되지 않았고, 빈 결과를 수집 장애로 추정하지 않았다.
