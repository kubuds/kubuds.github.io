1.1 메인 저장소: 벡터화 재작성 전 analyzer 복제(#3612)

10-22 23:43에 머지되었으며, 벡터화 해당 소스 한 곳만 변경, +2/-1. 루프 벡터화는 IR을 재작성할 때 전달받은 산술 분석기를 재사용하는데, 분석기는 재작성 전의 상수와 구간 제약을 캐시하고 있다; 벡터화가 루프 경계나 인덱스 표현식을 바꾸면 이후 pass는 여전히 구 결론을 얻는다. 수정 방식은 벡터화 재작성에 진입하기 전에 분석기를 복사하여 재작성이 복사본에만 적용되도록 하는 것이다. 이 건에는 회귀 테스트가 포함되지 않았으며, 가치는 #3226과 동일한 근원의 문제를 다른 진입점에서 막는다는 데 있다 — 같은 날 그 건은 병렬 루프 분할 후의 무효화된 바인딩을 처리했으며, 두 건을 함께 보면 분석 컨텍스트의 수명주기가 독립적인 결함 유형으로 정리되고 있다.

1.2 메인 저장소: 병렬 루프 분할 후 구 analyzer 바인딩 무효화(#3226)

6개 파일 +55/-19, loop_partition, loop_vectorize, lower_tile_op 세 pass 및 해당 헤더 파일에 관련된다. 병렬 루프가 분할된 후 루프 본문의 이터레이션 변수가 재바인딩되지만, pass는 여전히 분할 전 변수로 분석기를 조회하여 구 변수의 구간과 나눗셈 정보를 얻으므로 단순화와 범위 판정이 왜곡된다. 수정은 분석 컨텍스트를 pass별로 격리하고 루프 분석 스냅샷의 초기화 경로를 단순화했으며, 최소화된 병렬 루프 분석 회귀 케이스 세트를 함께 추가했다. 제출자에는 Codex 공동 서명이 포함되어 있다.

출처: https://github.com/tile-ai/tilelang/pull/3226

1.3 메인 저장소: deepseek_v32 top-k 선택기 후보 버퍼 범위 초과(#3280)

2개 파일 +91/-10, #1351 수정. tl_topk_impl은 radix 후보를 고정 [2, 4096] 공유 버퍼에 담지만, 첫 라운드 radix에서 선택된 임계값 버킷이 4096개 요소를 초과하지 않도록 제약하는 것이 아무것도 없다 — FP32 점수의 낮은 가수 비트가 동일하거나 입력이 완전히 동일할 때 원자적 추가가 버퍼 끝을 넘어 기록되어 CUDA_ERROR_ILLEGAL_ADDRESS로 크래시한다. 수정 방식은 tl_topk 래퍼 계층에서 (batch, 2, seq_len) 크기의 전역 workspace를 할당하여 두 radix 버퍼 모두 seq_len으로 감싸지도록 하는 것이다; 공개된 tl_topk() 시그니처는 변경되지 않는다. 79줄 재현 케이스가 포함되어 있으며, #1351의 입력 구성에 따른다.

출처: https://github.com/tile-ai/tilelang/pull/3280

1.4 메인 저장소: CUDA 16비트 역삼각 함수 및 이진 수학 하향 보완(#3172)

3개 파일 +463/-8. asin, acos, asinh, acosh, atanh, log1p, atan2, hypot, copysign, ldexp, nextafter에 CUDA 전용 하향 규칙이 없었고, 범용 규칙은 float32/float64만 처리하여 float16과 bfloat16 호출이 codegen 단계에서 아무도 처리하지 않았다. 수정은 이들을 CUDAMath에 등록하고 half_t / bfloat16_t 오버로드를 추가한다: 열 개 연산자는 float32로 평가한 뒤 다시 변환하며, nextafter는 16비트 인코딩 기준 정수 비교 스텝으로 바꾸어 fast math에서도 bfloat16 서브노멀을 보존한다. float32/float64의 함수 이름은 그대로 유지되며, common.h 측에 182줄의 템플릿 구현이 새로 추가되었다.

출처: https://github.com/tile-ai/tilelang/pull/3172

1.5 메인 저장소: sm8x 희소 메타데이터 비전단사 형상을 거부로 변경 (#3125)

단일 파일 tilelang/layout/gemm_sp.py +6/-0, #2606 수정. make_cutlass_metadata_layout_sm8x의 interleave는 M이 그룹 크기의 정수 배이고 K가 짝수일 때만 전단사이며, 조건을 만족하지 않을 때 기존에는 조용히 잘못된 메타데이터를 생성하여 희소 GEMM 결과가 아무 표시 없이 틀렸다. 이제 두 조건 모두 명시적으로 거부하도록 변경했다. 원래 PR과 함께 추가되었던 희소 메타데이터 형상 테스트는 리뷰에서 제외 요구되어 메인 브랜치에 반영되지 않았다.

출처: https://github.com/tile-ai/tilelang/pull/3125

1.6 메인 저장소: eager 프런트엔드의 Python 소스 위치 보존 (#3558)

4개 파일. eager 프런트엔드가 Python의 for / with 문을 생성형 호출로 내린 뒤, 오류 및 디버깅 매핑이 생성 코드의 줄 번호로 되돌아갔다. 수정은 생성된 루프 호출을 for 문에, 컨텍스트 래핑을 with 문에 매핑하고, 이터러블 인자 언패킹 위치도 보완한다. #3125와 마찬가지로 리뷰에서 동봉된 소스 위치 회귀 테스트의 제외를 요구했다.

출처: https://github.com/tile-ai/tilelang/pull/3558

5. 동향 관찰

첫째, 메인 저장소의 결함 유형이 한 층 바뀌었다. 지난주 메인 저장소에서 정리한 것은 “형상과 기하 검증”이었다. cast 반올림 주석이 조용히 버려지고, arch 없는 CUDA target이 조용히 sm_50으로 후퇴하고, 희소 메타데이터 형상을 검증하지 않던 문제였다. 이번 모니터링 기간의 9건 중 4건은 분석기와 소스 위치 같은 컴파일 시점 상태에 속한다. analyzer가 재작성 후 재사용되고, 분할 후 변수가 재바인딩되고, eager 프런트엔드가 Python 위치를 잃는 문제다. 이런 결함의 공통점은 “생성된 kernel은 여전히 정확할 수 있지만, 컴파일러가 당신에게 말하는 것과 실제로 하는 것이 불일치한다”는 것이다. TileLang이 agent 자동 kernel 작성(4.2)을 접목하고 있는 만큼, 컴파일 시점 상태 일관성이 agent 반복 폐루프의 수렴 여부를 직접 결정하게 된다.

둘째, Ascend 측 진전이 연산자 수량에서 저수준 데이터 경로로 옮겨갔다. #3530은 18개 파일에 걸쳐 NZ 압축 레이아웃의 일부 UB→L1 복사에서의 행 간격 표현을 다룬다. #3581과 #3523은 각각 컴파일 시점 프레디커트 폭발과 SIMT 벡터 지역 변수의 할당 의미를 수정한다. 세 건 모두 연산자를 새로 추가하지 않고, 기존 경로가 더 많은 형상에서 컴파일되고 정확히 실행되도록 만든다. CANN 커뮤니티가 별도로 ops-tilelang 연산자 저장소를 새로 연 것(4.1)과 함께 읽으면 분업이 보인다. 연산자 자산은 커뮤니티 저장소가 담당하고, 메인 저장소는 백엔드 의미와 codegen에 집중한다.

셋째, TileOPs는 이틀 연속 20건을 처리하며 작업 중심이 SM90 특화와 SM89 보완에 있다. 모니터링 기간에 SM90 warp 특화 kernel 세 개(dense decode, 인과 슬라이딩 윈도 band, FP8 varlen 오버랩)를 새로 추가했고, 동시에 SM89의 SSD chunk scan, paged DSA, NSA top-k 세 가지 소규모 경로를 함께 추진했다. 주목할 점은 두 건의 NaN 수정(#2708, #2699)이 모두 warp 특화 경로에서 나타났다는 것이다. 공유 메모리 플래너의 활성 기간 판단과 fast math 하의 FMA 융합은 이런 수작업 편성 kernel에서 가장 오류가 나기 쉬운 두 지점이며, 바로 이것이 TileLang이 사용자를 대신해 관리하겠다고 약속한 부분이다.

넷째, 하나의 역방향 지표는 벤치마크 계층이다. #2692는 참조 구현을 float32 연산으로 바꿨는데, 발단은 MTT S5000에서 GroupNorm과 InstanceNorm이 실패한 것이었다. 문제는 kernel 자체가 아니라 참조 구현이 입력 dtype을 따라간 데 있었다. 같은 날 TileFoundry #256은 “장치가 시작을 거부함”을 조용한 처리에서 예외 발생으로 바꿨다. 두 건 모두 같은 방향이다. “통과한 것처럼 보임”을 “실제로 통과함”으로 바꾸는 것이다. 이 도구들에 의존해 칩 적응을 하는 팀에게 이런 수정의 실질 가치는 몇 가지 성능 수치보다 높다.

다섯째, 배포와 산업 두 축이 가속하고 있다. Sunrise 배포판은 0.1.15와 TANG 백엔드 wheel을 묶어 릴리스 PR로 올렸다. 이는 TileLang에 이미 하나 이상의 다운스트림 배포 형태가 나타났음을 뜻한다. 산업 측에서는 SCMP가 SemiAnalysis의 판단을 전재하며 “여섯 저장소 중 TileLang만 사용 가능”을 주류 매체로 밀어냈다. 기술 리듬상으로는 여전히 조용한 하루였다(메인 저장소 릴리스 없음, breaking change 없음). 그러나 생태계 계층의 조직적 움직임이 코드 계층보다 확연히 많았다.
