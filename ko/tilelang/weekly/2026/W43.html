TileLang 위클리 리포트 (2026-10-19 ~ 2026-10-23)

2026-10-23 Kubuds

보고 기간: 2026년 10월 19일(월)~10월 23일(금), 총 5영업일 자료 출처: 본지의 TileLang 커뮤니티 동향 데일리 리포트 5회분(10-19, 10-20, 10-21, 10-22, 10-23). 5회분 수집 기간 합계는 10-16 07:00부터 10-23 07:00까지이며, 추가로 tile-ai 조직 29개 저장소의 168시간 모니터링 기간 보완 점검 및 각 저장소 릴리스 페이지, 태그, VERSION 파일 재검토를 수행함(상세는 부록 참조)

1. 주간 주요 뉴스

  • TileFoundry 0.0.3 정식 릴리스, 명령어 수준 스케줄링을 agent에 위임, H200에서 Qwen3.8-27B 프리필 세 구간 모두 SGLang보다 빠름(10-21): 10-21 10:26에 v0.0.3을 태그했으며, PyPI는 tilefoundry==0.0.3, 코드명은 「Agent-driven scheduling」. 핵심 변화는 스케줄링 권한의 귀속—컴파일러가 각 HIR 연산을 어떤 명령어로 구현할 수 있는지, 각각 무엇이 필요한지 나열하면, agent가 후보 중에서 선택하고, 컴파일러가 선택된 스케줄을 TIR로 하강한다. 함께 제공되는 CLI에는 schedule candidates와 schedule facts가 추가되었고, 명령어는 AtomSched 연산으로 선언되며 명시적 TIR 오퍼랜드 계약을 가지며, CUDA MMA atom, SM90 WGMMA 및 비동기 복사부터 시작한다. 성능 측면에서는 세 가지 실제 수치를 제시했다: Qwen3.8-27B 프리필은 단일 H200에서 1024 / 4096 / 8192 token 기준 각각 80.29 / 309.61 / 631.19 ms, SGLang은 89.06 / 317.11 / 638.25 ms; 짧은 시퀀스 128 / 256 / 512 / 1024 token은 각각 SGLang의 1.88 / 1.41 / 1.10 / 1.03배. 알려진 문제 두 가지: wheel이 아직 CUDA 런타임 헤더 파일을 패키징하지 않아(설치 패키지에서 출발하면 CUDA kernel을 빌드할 수 없으며 소스 checkout 필요, 다음 버전에서 수정) 그리고 성능 타임라인이 insert_slice, tf.zeros의 mesh 위치 간 가격 책정에 오류가 있음(#239).

  • SemiAnalysis, TileLang Ascend 전용 장 마련: 승등 지원을 받은 6개 저장소 중 기사 작성 시점에 사용 가능한 것은 TileLang뿐(10-21 ~ 10-22): 10-21에 발표된 《The Huawei-DeepSeek Symbiosis》의 부제는 화웨이 Ascend 950PR 마이크로벤치마크, DSv4.1 Flash 분석, DeepSeek의 승등 지원, AICPU와 TileLang Ascend를 직접 나열한다. TileLang과 직접 관련된 세 가지: 첫째, 승등 지원을 받은 6개 저장소(TileLang, DeepGEMM, DeepEP, TileKernels, FlashMLA, DeepSelect) 중 기사 작성 시점에 사용 가능한 것은 TileLang뿐인데, CANN 9.2.0이 아직 릴리스되지 않았고 DeepSeek는 CANN 9.2.0과 C++20 컴파일러를 요구하는데 9.2.0-beta.2는 후자를 제공하지 않기 때문이다; 둘째, 승등 950 백엔드는 별도 적응 저장소에만 존재하는 것이 아니라 TileLang 메인 저장소에 병합되었으며, 네이티브 컴파일, 스케줄링, 동기화 및 런타임 통합을 제공하고, AutoSchedule은 데이터 의존성과 예상 실행 시간에 따라 중첩과 온칩 버퍼 슬롯 수를 결정하며, 950PR에서 소형 단일 연산자에 대해 최대 40% 단축한다; 셋째, CANN, Triton-ascend와 비교할 때 「일부 크기에서는 CANN과 대등하거나 능가할 수 있으며」, 최적 구현은 크기에 따라 전환된다(저자는 핫 캐시 상태의 소박한 벤치마크임을 명시). 기사는 동시에 생태계 격차도 지적한다: 대부분의 최적화가 슈퍼노드를 겨냥하며, x86 호스트에서 vLLM-Ascend 0.26.0rc1은 여전히 여러 문제가 있다. 10-22 South China Morning Post의 《Jensen’s nightmare》는 같은 보고서를 전재한 것으로, 2차 전파에 해당하며 새로운 기술적 진전은 아니지만 해당 판단이 주류 언론의 표현으로 진입하고 있음을 보여준다.

  • 메인 저장소에서 일주일 만에 세 차례의 정확성 강화 완료, 결함 유형이 ‘잘못된 계산’에서 ‘잘못된 대상 선택’과 ‘컴파일 시점 상태 왜곡’으로 확대 (10-19 ~ 10-23): 1차는 warp 특수화와 파이프라인 기하 구조 정리 — #3503는 순수 TMA 프로듀서의 모든 스레드가 정방향 배리어에 도달하도록 함(#3470의 parity 교착 수정), #2342는 형제 파이프라인이 공유 버퍼를 한 번만 확장하도록 함(#2309의 4차원 LayoutInference 크래시 수정), #3536은 공유 버퍼 상의 T.cumsum에 스레드 오프셋 보충, #2822는 전이적 복사 의존성 유지. 2차는 조용한 수치 오류 정리 — #2818은 지원되지 않는 MMA tile에 명시적 K 패딩 요구(기존에는 K 원자를 조용히 축소), #2815는 (64,1) 유지 차원 리덕션 크래시 수정, #3550은 TIR 술어가 정수 비트 폭 승격과 동기화되어 재작성되도록 함, #3070은 배치형 finalize_reducer가 첫 출력 블록만 리덕션하는 문제 수정, #3350은 cast의 소스/대상/반올림 세 조합에 대한 사전 검증, #2860은 arch 없는 CUDA target에 오류를 발생시키고 조용히 sm_50을 채우지 않도록 함. 3차는 컴파일 시점 상태 정리 — #3579는 0이 아닌 루프 하한을 벡터화 분석에 포함(10개 파일 +818/-198, #2669와 #2616 종료), #3612는 벡터화 재작성 전에 analyzer 복제, #3226은 병렬 루프 분할 후 구 analyzer 바인딩 무효화 수정. 세 배치의 공통점은 오류를 보고하지 않고 특정 크기나 루프 형태에서만 신뢰할 수 없는 결과를 낸다는 점이다.

  • Ascend 라인의 중심이 학습 역방향과 저수준 데이터 경로로 이동, 한 주에 적응 저장소 PR 11건 병합 및 sparse_mla 양방향 개설 (10-20 ~ 10-23): 학습 측 연산자 집중 반영 — #1887의 indexer_bwd(+1294, DSA 희소 미세조정 지원, AscendC와 PTO 듀얼 백엔드 동시 지원, fast/general/cast 3단 kernel), #1877의 SiTU-GLU 역방향(+854, CANN의 aclnnSituGluGrad와 의미 정렬, Kimi K3 Stable LatentMoE 게이트 활성화 역방향에 사용, 910B3에서 공식 aclnn과 교차 검증 최대 상대 오차 약 3e-3), #1892의 LSTM(+2304, 12개 jit kernel, 다층 스택·양방향·LSTMP 프로젝션 지원)과 #1902의 GRU(+2267, 8개 kernel, 시간 스텝당 약 58개의 PipeBarrier를 피하기 위해 AUTO_SYNC 수동 비활성화). 심사 대기열에는 이어서 sparse_mla 순전파와 역전파(#1929 / #1928), GLM-5.3의 kpool 압축(#1910) 및 WY fast 시리즈(#1827 등)가 보충되었다. 데이터 경로 측에서는 #3530이 18개 파일 +993/-256으로 압축 NZ 버퍼의 부분 UB→L1 복사를 지원하고 C0 그룹 행 간격을 명시적으로 제공하며, #1795는 32B 미만 컴팩트 행 간격 소스가 표현 불가함을 규명하고 실측에서 두 번째 burst가 element 1이 아닌 element 8을 읽는 문제를 확인하여 keepdim reduce의 출력 오류를 수정했으며, #1903은 JIT 캐시를 원자적 게시로 변경하고 캐시 삭제 시 복구하도록 했다.

  • TileOPs 일주일간 68건 병합, SM89와 SM90 나란히 메인 라인으로, 사양 및 벤치마크 커버리지 동시에 205/205 보고 (10-19 ~ 10-23): 조직 통계 브랜치는 10-18 하루 20건, 모니터링 기간 44건 병합 후 “구현 완료 205/205, 벤치마크 완료 205/205”로 갱신되어 두 항목이 동시에 만점을 기록했습니다. SM90 방향은 일주일간 여섯 개의 warp 특화 kernel을 새로 추가했습니다——페이지드 GQA 전방(#2668), FP8 lightning indexer 듀얼 consumer warpgroup(#2666), MLA 디코드 오프셋 시소(#2665), dense prefill 영속 순회(#2706), dense GQA decode(#2694), 인과 슬라이딩 윈도 band(#2696). SM89 방향은 소비자용 및 단일 카드 시나리오를 집중 보완했습니다: 블록 스케일링 FP8 그룹 GEMM(#2659)과 INT8 W8A8(#2655)이 같은 날 반영, FP8 BMM 기본 타일을 64×64로 변경(#2681, 1×16×64×128이 5.161에서 3.799 us로 감소), W4A16의 M 상한을 64로 확장(#2672, M=17 / 32 / 64에서 각각 43.35 / 47.20 / 40.00 퍼센트 포인트 감소), 페이지드 DSA를 MMA로 구현(#2669, 0.269 ms 대 PyTorch FP32 참조 0.727 ms), NSA top-k를 2048개 압축 블록으로 확장(#2675). 같은 기간 두 건의 NaN 수정은 모두 warp 특화 경로에서 발생했습니다: 공유 메모리 활성 기간 판단 오류(#2708)와 fast math 하의 FMA 융합 오버플로(#2699).

  • PTO, “독립 실행 경로”에서 “자동 벡터화 + 기본 실행 백엔드”로 (심사 중, 10-18부터): 메인 저장소의 PTO 벡터화 프레임워크 #3512는 사용자가 T.SimdVF(lanes=L) 내에서 스칼라 병렬 T.Parallel(원소별, 제어 흐름, 리덕션)을 작성하면 컴파일러가 이를 PTO VMI 명령으로 벡터화하고 PTOAS 컴파일을 거쳐 Ascend 950에서 실행하도록 합니다. 규모는 10-18의 44개 파일, 18988줄에서 10-21의 50개 파일, 21022줄로 증가했습니다. #3516은 target="pto"에 execution_backend="auto"를 설정하면 tvm_ffi로 해석되어 기본값으로 설정되도록 할 예정입니다. 이미 병합된 연동 작업은 일련의 저장소, 프레디케이트, 리덕션 의미론 수정입니다: #3514의 T.alloc_ss, #3437의 SimdVF dim=1 리덕션, #3582의 PTO 정수 부호성, #3581의 프레디케이트 지수 증가, #3523의 SIMT 벡터 지역 변수 할당. 메인 저장소는 동시에 #3511로 AscendC 측의 L0 로컬 복사 명시적 pitch를 보완했습니다(24개 파일 +1458/-187, 하나의 GEMM tile을 여러 번의 복사로 구성 가능하게 함)——두 경로는 병행 추진이며 대체 관계가 아닙니다.

  • 다운스트림 배포 형태에서 두 번째 사례 등장: Sunrise, 0.1.15+sunrise.1.2.0 릴리스 PR 제출(10-22): #9가 10-22 16:48에 candidate/sunrise-0.1.15-1.2.0-20261019 브랜치를 생성하고 PR을 열어 Sunrise 배포판을 0.1.15+sunrise.1.2.0으로 업데이트했으며, TileLang 0.1.15 및 함께 리뷰된 TileOPs, TileKernels, TVM, tvm-ffi 변경 사항을 포함했습니다. 소스 임포트와 병합, 배포 적응은 별도 커밋으로 분리되었고, 최종적으로 TANG 백엔드용 wheel에 적응하고 슬라이스 GEMM 회귀를 수정했습니다. 자체 보고 검증 결과 로컬 계약 테스트 55개 통과, TANG 파이프라인 codegen 테스트 54개 통과, 두 개의 lint job 및 신뢰 경계 검사 통과였으나, S2 wheel 빌드 패키징 후 설치 후 import 스모크 검사가 tangGetDeviceCount에서 실패했습니다. 해당 PR은 아직 병합되지 않았습니다.

  • 커뮤니티 측에서 일주일 사이 여러 신규 저장소 등장: 중국어 시스템 튜토리얼, CANN 커뮤니티 연산자 저장소, agent 워크플로 및 Hexagon 백엔드 실험(10-20 ~ 10-22): huandu/tilelang-tutorial이 10-20에 저장소를 생성했으며, “제로에서 원까지의 TileLang 중국어 시스템 튜토리얼”을 표방하고 연산자 작성, 컴파일 타임 메커니즘, NVIDIA와 Ascend 두 백엔드를 다루며, 체계적인 중국어 튜토리얼 저장소의 첫 등장입니다. Atlas-Ascend-Fork/ops-tilelang이 10-20에 저장소를 생성했으며, CANN 커뮤니티가 Ascend NPU를 대상으로 하는 연산자 자산 저장소(kernel 구현, 자동화 테스트, 표준 워크로드 및 성능 베이스라인 통합 관리)로, 10-22에 첫 푸시 수정이 있었습니다. tilelang/agent가 10-22에 푸시되었으며, README 자체가 실행 가능한 prompt 템플릿으로 @tilelang-operator-dev/SKILL.md를 통해 도메인 지식을 주입하고 10단계 폐루프로 연산자 최적화를 진행합니다. 또한 SoilSoi1/tilelang-hexagon(10-20 저장소 생성, Hexagon 백엔드 커뮤니티 실험)이 있으며, 메인 저장소에서 심사 중인 #2155 Hexagon HMX 백엔드 지원과 호응합니다.

  • 두 건의 NaN과 세 건의 계약 수정: 공유 메모리 플래너가 warp 역할별 버퍼를 서로 다른 시간대에 활성인 것으로 읽어, split handover를 여전히 TMA로 채워지는 key 또는 value 링 주소에 배치했다(#2708, 2개 파일 +80/-30, “7개의 단일 token 요청이 300 token 요청보다 앞서고, 4099행 FP8 cache, 48행 페이지” 조합에서 NaN 반환); 인과 윈도우에서 128×64 튜닝 타일이 마지막 몇 행에서 연속으로 두 개의 전면 마스킹된 key tile을 만나, fast math가 prev * scale - curr * scale를 FMA로 융합하고 반올림 오차 약 2의 99제곱이 오버플로하여 NaN이 됨(#2699, 수정 방법은 스케일 재조정 전에 running maxima를 먼저 빼는 것); varlen query RoPE에서 홀수 half rotation width일 때 병렬도가 rotation 분기 스레드 수로 나누어떨어지지 않으면 루프 상한을 잃음(#2700, 일반 경로에서 바로 행); 페이지드 decode의 autotune 공급이 모든 요청에 동일한 block table을 제공(#2703, 실측 MHA decode 튜너가 opt-1.3b-b16에서 block_N 128, 즉 콜드 80.0 us를 선택하고 72.5 us를 포기하여 flashinfer의 0.994로 하락); ref_program이 정확성 참조이자 torch 베이스라인 타이밍 대상으로 입력 dtype을 따라감(#2692, GroupNorm과 InstanceNorm이 MTT S5000에서 실패, 참조를 float32 이상에서 계산하도록 변경).

6. 트렌드 관찰

  • 정확성 강화의 계층이 반복이 아니라 점진적으로 심화되고 있다: 지난주 메인 저장소가 정리한 것은 「형상과 기하 검증」이었고, 이번 주 세 구간은 각기 다르다—먼저 warp 특화와 파이프라인의 기하와 배리어(#3503, #2342, #3536, #2822), 다음으로 조용한 수치 오류(#2818, #2815, #3550, #3070, #3350, #2860, #3125), 마지막으로 컴파일 시점 상태 일관성(#3579, #3612, #3226)이다. 세 번째 구간이 가장 주목할 만하다: 이런 결함이 생성한 kernel은 여전히 정확할 수 있지만, 컴파일러가 사용자에게 말하는 것과 실제로 하는 것이 불일치한다; TileLang이 agent 자동 kernel 작성에 접어들고 있는 지금, 컴파일 시점 상태의 자기 일관성은 agent 반복 폐루프의 수렴 여부를 직접 좌우할 것이다.
  • Ascend 측의 병목은 이미 연산자 수에서 메모리 모델, 런타임 경계, 학습 역방향으로 이동했다: 이번 주 어댑테이션 저장소에 11건의 커밋이 병합되었는데, 그중 역방향과 재귀 연산자가 다섯 건(indexer_bwd, SiTU-GLU 역방향, LSTM, GRU, CrossEntropy 문서)을 차지하고, 메인 저장소 측 최대 건은 NZ 레이아웃의 UB→L1 행 간격 표현(#3530, 18개 파일)이며, 기술 밀도가 가장 높은 것은 32B 미만의 컴팩트 행 간격이 표현 불가능해 명시적으로 중단하는 것(#1795)이다. 여기에 JIT 캐시 원자적 게시(#1903)와 PTO 프레디킷 지수적 증가(#3581)를 더하면, 이 라인의 주제는 「기존 연산자가 경계 조건에서 오류를 내지 않도록 만드는 것」이다. CANN 커뮤니티가 별도로 ops-tilelang 연산자 저장소를 새로 만든 것과 맞물려 보면 분업을 읽을 수 있다: 연산자 자산은 커뮤니티 저장소가 담당하고, 메인 저장소는 백엔드 의미론과 codegen에 집중한다.
  • SM89와 SM90이 나란히 두 개의 하드웨어 주류 라인이 되었고, 우선순위를 정하는 기준이 피크 성능에서 확보 가능성으로 전환되었다: SM90 방향은 이번 주 여섯 개의 warp 특화 kernel을 산출했고, SM89 방향은 블록 스케일링 FP8, INT8 W8A8, FP8 BMM, W4A16, 페이지드 DSA, NSA top-k 여섯 경로를 동시에 추진하며, PR에는 대개 단일 카드 실측이 첨부되어 있고 「SM90 실행 결과를 주장하지 않음」「대형 케이스는 대체로 동등하며 보편적 우위를 구성하지 않음」이라고 명시되어 있다. Ada급 그래픽 카드(L40S, 4090류)는 국내 개발자들이 보유한 주력 하드웨어이며, 이러한 방향은 SemiAnalysis가 지적한 「최적화가 초노드에 다변화되고 범용성이 성능에 뒤처진다」와 정확히 상호보완적이다.
  • 생태계 계층의 조직적 움직임이 코드 계층보다 많다: 메인 저장소는 이번 주 릴리스도, breaking change도 없었지만, 조직 외부에는 중국어 시스템 튜토리얼 저장소, CANN 커뮤니티 연산자 저장소, agent SKILL 워크플로, Hexagon 백엔드 실험, VS Code 확장과 SAIL 래퍼 저장소가 나타났고, 조직 내부에는 TileFoundry 0.0.3의 agent 스케줄링, Sunrise의 두 번째 배포 형태, TileOPs의 스펙 만충이 있었다. 「사람이 규칙을 작성하고, agent가 튜닝하며, 저장소에 베이스라인을 축적한다」는 세 가지를 함께 보면, Ascend 측과 TileLang 전체의 엔지니어링 분업이 재편되고 있으며, 코드 리듬 자체는 평온하다.
  • 분석 기관이 TileLang을 Ascend 가용성의 판단 기준으로 삼기 시작했다: SemiAnalysis는 「여섯 저장소 중 당시 사용 가능한 것은 TileLang뿐」이라는 기준으로 DeepSeek Ascend 지원의 완성도를 정의했는데, 이는 어떤 단일 기술 블로그보다도 TileLang이 국산 컴퓨팅 파워 담론에서 차지하는 위치—실험적 DSL에서 디폴트 캐리어 계층으로—를 잘 보여준다. 같은 보고서는 또한 반대 신호도 제시한다: 최적화가 초노드에 집중되어 있고 x86 호스트 지원은 여전히 불완전하며, 성능과 범용성 사이에 뚜렷한 트레이드오프가 존재한다. SCMP의 전언은 이러한 판단이 주류 미디어의 표현으로 진입하고 있음을 보여준다.
  • 다음 호 관심 포인트: 메인 저장소 v0.1.16의 릴리스 여부(이미 23일째 조용함); TileOPs의 0.1.12 잠금 해제 가능 여부(#2554 종료 후 새 버전 방안이 보이지 않으며, 이중 베이스라인 검증이 여전히 관문); PTO의 #3512와 #3516 병합 가능 여부(PTO가 기본 실행 백엔드가 될지 결정); TileFoundry 0.0.3의 wheel 헤더 파일 누락과 #239 가격 책정 문제가 다음 버전에서 수정될지; Sunrise의 S2 wheel이 tangGetDeviceCount에서 실패하는 문제를 어떻게 처리할지; Ascend sparse_mla 순방향과 역전파(#1929 / #1928), GLM-5.3 kpool(#1910)의 착지 리듬; Hygon gcy_merge_main의 레지스터 파이프라인 스위치 정리가 언제 main에 들어갈지.
