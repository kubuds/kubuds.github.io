1.1 build-infra: E2E-записи двух бэкендов Cambricon + E2E двух компиляторов Kunlunxin 0.20.2 (главное за окно)

Источник: PR #472, PR #476, PR #475

  • #472（вошёл 22.08 в 22:19, tengqm）：Зафиксирована E2E-проверка двух бэкендов Cambricon. На NEUWARE 4.4.3 / 4.7.2 со собранным в full-scope wheel выполнены три сценария — обучение, пост-обучение, инференс — на 8 картах MLU590-M9DE с полным PASS на обоих бэкендах (RL отложен согласно принятому решению). Ключевые действия: пробел в абстракции платформы (issue #11) устранён нативной регистрацией PlatformMLU в Megatron-LM-FL #125; после слияния в интеграционную ветку и пересборки wheel для Cambricon shim на стороне контейнера удалён и проверка повторена — loss во всех трёх сценариях побайтово совпадает с эпохой shim; одновременно исправлена запись modelopt (одиночная установка nvidia-modelopt==0.43.0 безопасна, риск OOM эпохи 0.45.0 больше не актуален).
  • #476（вошёл 23.08 в 08:37）：Зафиксирован E2E двух компиляторов для Kunlunxin P800 XPU 0.20.2 — путь FlagTree (по умолчанию) 7/7 (7.3–9.8 tok/s), путь Triton 3.6.0 — 3/3 (5.7–7.3 tok/s), serve + coherent inference пройдены. Для обеих блокирующих проблем дан A/B-анализ первопричин: искажение текста на P2 decode = патч плагина передавал в xtorch_ops.prefill_attention исходный decode scale (а не скорректированный scale × sqrt(head_size)); исправление уже отправлено в vllm-plugin-FL PR #400 (линия base release-0.2); ложное зависание P1 = вызывалось XPU_EVENT_KL3_ENABLE=1, после удаления этой строки из рецепта оба пути работают чисто. В матрице проверки vllm для Kunlunxin 0.20.2 ячейки T/F стали зелёными.
  • #475（22.08 в 23:39）：в app image добавлен лаунчер обучения megatron-train — сценарий обучения перешёл от «зафиксировано в документации» к «конвейеризации в образе» (ранее app image был в основном ориентирован на инференс).
  • #471（22.08 в 12:38）：bump xmlir для Kunlunxin до 1.0.0.1+2026****0605; #473（22.08 в 17:38）：сборка megatron-wheel переведена на –no-cache (чтобы перемещение ref вступало в силу); #474（22.08 в 22:55）：из документации Cambricon удалены детали временного shim.

Трактовка: вслед за CANN 8.5.0 для Ascend от 21.08, build-infra за два дня подряд добавила две глубокие записи о проверке — E2E двух бэкендов Cambricon и E2E двух компиляторов Kunlunxin 0.20.2; «парадигма проверки двух путей F/T» быстро расширяется. Путь на стороне Cambricon — «исправление пробела платформы в upstream + удаление shim в контейнере» — знаменует переход интеграции от временных патчей к нативной поддержке; локализация первопричины искажения текста на decode у Kunlunxin (ошибка семантики scale) и PR с исправлением показывают, что проверка численной корректности цепочки инференса детализирована до уровня операторов.

1.2 Megatron-LM-FL: нативная регистрация платформы Cambricon MLU вошла в интеграционную ветку

Источники: PR #125, ветка ci/merge-105-106-107-114

  • PR #125 (создан 22.08 в 18:42, tengqm/Qiming Teng): feat(platform): add Cambricon MLU platform registration — добавлена регистрация платформы PlatformMLU (наследует PlatformCUDA, использует модуль torch_mlu gpu_migration с псевдонимами интерфейсов torch.cuda.*), что позволяет явно выбирать MLU-хост и исправляет прежний откат к платформе CPU, приводивший к повреждению RNG-пути тензорного параллелизма (в cur_platform.default_generators[idx] был доступен только один генератор). Затронуты 4 файла: platform_manager / platform_mlu / platform_register и тесты платформы.
  • Интеграционная ветка: ci/merge-105-106-107-114 с 22.08 18:40 последовательно принимает несколько PR по платформам/упаковке (включая #125 и слияние origin/pr-125 22.08 в 20:32); pushed_at репозитория 20:51 совпадает с этим — именно эта ветка и есть «интеграционная ветка» из build-infra #472.

Интерпретация: Cambricon MLU стал вторым отечественным бэкендом после Ascend (#120 Ascend NPU paged attention + platform convergence, открыт), вошедшим в слой платформенной абстракции Megatron-LM-FL; в сочетании с #472 из раздела 1.1, подключение Cambricon к тренировочному стеку = нативная регистрация на платформе + трёхсценарная E2E-валидация без shim, что представляет собой сформировавшийся эталонный случай подключения чипов на стороне обучения в FlagOS.

2.2 Zhiyuan выпустил систему оценки Embodied AI FlagEval-Robo (8/22)

Источники: Сообщество Zhiyuan, официальный сайт

  • 21 августа Zhiyuan Research Institute опубликовал FlagEval-Robo — систему оценки embodied AI (опубликовано в сообществе Zhiyuan 22.08 в 13:10), представив два рейтинга: FlagEval-Robo-Sim (симуляция) и FlagEval-Robo-Real (реальный робот), провёл сравнительную оценку 12 открытых embodied-моделей при равном посттренинге, в комплексе с атомарным бенчмарком навыков ATOM-Bench и бенчмарком embodied-рассуждений ERQA+.
  • Четыре ключевых вывода: симуляция значительно переоценивает возможности реального робота (показатели на реальном роботе составляют лишь 24%–72% от симуляции, для двуруких задач — всего 13%–60%); атомарные навыки не обобщаются напрямую через комбинирование (максимальная успешность комбинации в сложных задачах — лишь 16,7%); качественные данные с реального робота превосходят накопление объёма данных (PI0.5 с наименьшим объёмом данных реального робота показал лучший совокупный результат); embodied-большие модели пока не демонстрируют Scaling Law, структура модели (промежуточный supervision) важнее числа параметров.
  • Команда оценки провела тестирование «из коробки» двух ведущих моделей (успешность близка к 0), что доказывает отсутствие загрязнения набора данных при предобучении.

Толкование: FlagEval-Robo и embodied-направление FlagOS (инструментальная цепочка FlagOS-Robo) относятся к единой embodied-стратегии Zhiyuan — публикация системы оценки предоставляет общую мерку для выбора embodied-моделей и для разрыва «симуляция–реальный робот», что имеет прямую справочную ценность для допуска моделей и измерения результатов в экосистеме FlagOS-Robo.

2.3 Дозапись: старт конкурса оптимизации операторов FlagOS X SGLang (21.08)

Источники: официальный аккаунт FlagOS на CSDN, сайт соревнования

  • 21 августа в 11:06 официальный аккаунт FlagOS на CSDN опубликовал (событие в рамках вчерашнего окна, пропущено во вчерашнем отчёте, дозаписывается сегодня): официально стартовал первый трек Глобального конкурса открытых вычислений FlagOS (сезон второй) — трек оптимизации производительности операторов фреймворка SGLang на различных чипах, организованный Zhongzhi FlagOS совместно с IEEE, при соорганизации SGLang, в партнёрстве с индустриальными партнёрами MetaX, Supercomputing Internet, Kunlunxin и другими.
  • Более 200 реальных задач по операторам инференса SGLang раскрываются 13 партиями (охватывают общие/слитые/моделеспецифичные операторы), единообразно разрабатываются на Triton/Triton-TLE, единая оценка на разных чипах, ранжирование по среднему ускорению на нескольких чипах; учреждены три главные награды: полное завоевание / прорывное покорение / предельная производительность, максимальная награда за одну задачу — десять тысяч юаней; регистрация до 13.11, код победителей будет отправлен через PR в репозиторий FlagGems-sglang для открытого закрепления.

Толкование: сезон второй расширяет соревнование операторов с «генерации/оптимизации» (линия KernelGen) до «многочиповой производительности операторов инференса SGLang» (линия FlagGems-sglang); MetaX и Kunlunxin как индустриальные партнёры глубоко участвуют на стороне оценки — соревнование сообщества становится полигоном операторной экосистемы чипов участников.

4. Итоги

  1. Матрица E2E-валидации build-infra продолжает расширяться (главная тема окна): в один и тот же интервал последовательно зафиксированы E2E для двух бэкендов Cambricon (MLU590-M9DE, 8 карт; после удаления shim loss в трёх сценариях побайтово совпадает, #472) и E2E для двух компиляторов Kunlunxin 0.20.2 (FlagTree 7/7 + Triton 3.6.0 3/3, #476); первопричина искажения decode на Kunlunxin (ошибка семантики scale) увязана с исправляющим PR (vllm-plugin-FL #400).
  2. Cambricon MLU выходит на уровень платформы Megatron-LM-FL: PR #125 добавляет нативную регистрацию PlatformMLU (исправление пути RNG при тензорном параллелизме), интеграционная ветка влита 8/22 20:32 — формируется стандартная парадигма подключения обучающего стека «исправление пробелов в вышестоящем проекте + удаление shim».
  3. Сигналы перехода обучения на конвейерное производство: в app image добавлен лаунчер обучения megatron-train (#475), megatron-wheel переведён на сборку с –no-cache (#473) — сценарий обучения движется от документирования к конвейеризации образов.
  4. Экстернализация поддержки DCU в FlagSparse: команда разреженных вычислений NCIC-AlphaSparse влила команды тестирования DCU и расширение операторов spsv/spmm (PR #45), продолжая ритм объединения CUDA/DCU от 8/20.
  5. Два события на стороне экосистемы: Zhiyuan выпустил систему embodied-оценки FlagEval-Robo (двойной трек Sim+Real, сравнительный обзор 12 моделей, четыре ключевых вывода); стартовал второй сезон соревнования по оптимизации операторов FlagOS X SGLang (совместно с IEEE, при участии Moore Threads / Kunlunxin / Суперкомпьютерного интернета, 200+ задач) — последнее дозаписано по событиям вчерашнего окна.
  6. На новостной стороне четвёртый день подряд нулевые попадания по компонентам: официальных GitHub Release нет; цепочка прокси gnews восстановлена, но прямых попаданий по ключевым словам компонентов нет; «адаптация пяти крупных моделей» у Cambricon — повторная публикация старой новости от 8/13. Следующие точки наблюдения за релизами: конвейеризация app image megatron-train, ритм вливания линии release-0.2 vllm-plugin-FL (исправление Kunlunxin #400).

Пояснение об ограничениях: количество коммитов и время вливания взяты из commit search и repos API pushed_at (поисковый индекс может немного запаздывать; содержимое неосновных веток проверяется по branch commits API); детали окружения build-infra E2E приводятся по описанию PR; данные FlagEval-Robo — по оригиналу в сообществе Zhiyuan; по переходам gnews невозможно получить основной текст, поэтому суждения по новостной стороне опираются на заголовки и перекрёстную проверку нескольких источников, возможны пропуски низковесных китайскоязычных источников.
