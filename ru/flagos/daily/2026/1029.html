1.3 FlagGems: ускорение слияния скалярных цепочек для Kunlunxin в десять раз, пакетные исправления эталонной реализации для Enflame на рассмотрении (10-28)

Дата: 2026-10-28　Источники: FlagGems PR #7617 · FlagGems PR #7600 · FlagGems PR #7850 · FlagGems PR #7803 · FlagGems PR #7036 · FlagGems PR #7061 · FlagGems PR #7223

Относительное время восьми операторов выросло с 0,083~0,126 до 0,813~0,934, то есть примерно в семь-десять раз.

3.1 Horizon Robotics: BPU впервые становится бэкендом PrivateUse1 с возможностью пооператорного исполнения (28 октября)

Дата: 2026-10-28　Источники: Torch-FL PR #674 · PR #676 · PR #678 · PR #673

  • Способ интеграции: единицей исполнения BPU является артефакт .hbm, производимый hbdk4, а hbdk4 может работать только на x86; на плате невозможно ни компилировать, ни использовать артефакты, поставляемые вместе с репозиторием. Прежний вывод гласил «по дизайну невозможно eager»; данный коммит разбивает его на три уровня: сборка библиотеки одиночных операторов .hbm вне платы, генерация C++ ядер для отправки этих артефактов, добавление маршрутизации конфигурации drobotics.
  • Покрытие и валидация: 40 поэлементных операторов, 11 корзин по форме, все 440 артефактов на RDK S600 прошли сравнение с NumPy с нулевым расхождением, вызовы aten на тензорах flagos действительно попадают на BPU. Автор также зафиксировал два отрицательных вывода: libhbtl.so — это лишь эталонная реализация для CPU (ldd показывает только libc/libstdc++/libm, cpu/wall у hbtl::ucp::Add равен 1.00), а динамические формы не исполняются на HBRT 4.7.5 (загрузчик объявляет эту ось как stride 0, проверка задачи требует не менее 64).
  • Три завершающих коммита: #676 добавляет в kDrobotics два switch в dispatcher.h — ранее журнал диспетчеризации сборки BPU всегда печатал unknown, а KernelSetOf сообщал о собственной библиотеке ядер BPU как не имеющей владельца; #678 исправляет три места в ветках copy, где выполнялся безусловный box в CUDA — по умолчанию wheel-пакеты NVIDIA с доминированием FlagGems и PPU XuanTie от DAMO Academy намеренно линкуются с pip torch только для CPU, DispatchStub ядра копирования CUDA пуст, и первый же вызов даёт missing kernel for cuda. #673 исправляет несоответствие имени производителя и platform id в записи сборки (hygon/dcu, mthreads/musa, enflame/gcu, nvidia/cuda) — это корневая причина восьми неудачных юнит-тестов на дорожке Hygon DCU.
  • На рассмотрении: #672 унифицирует гранулярность claim матричных операторов soft-lowp (объявление по ключу conf, декодирование по семейству), #677 направляет вызовы FlagGems с ключевыми аргументами на активный бэкенд, #680 переопределяет псевдонимы устройств по производителю, хранящемуся в записи сборки, #681 читает пробу libtorch_cuda из префикса torch, а не из цели интерфейса.
  • Оценка: это единственная интеграция в данном окне, где «новая платформа перешла из непригодной в пригодную»; ценность в прохождении пути, а не в производительности — 40 поэлементных операторов являются отправной точкой, магистральные операторы вроде свёрток по-прежнему опираются на целографический путь torch.compile.

3.2 Kunlunxin: слияние скалярных цепочек и ядра непрерывных сегментов, три ускорения на P800 (10-28)

Дата: 2026-10-28　Источники: FlagGems PR #7617 · PR #7600 · PR #7850 · PR #7803 · FlagCX PR #682

  • Скалярные цепочки: объединённое ядро восьми вынесенных скалярных цепных операторов подняло относительное время выполнения с 0,08~0,13 до 0,81~0,93 (#7617). Выигрыш в основном на стороне хоста: однократное выделение выходного буфера плюс unbind вместо вызова аллокатора на каждый тензор; для малых форм — один запуск с передачей всех указателей в качестве аргументов.
  • Непрерывные сегменты: после перевода batch-norm в режиме инференса и преобразования QKV на ядра непрерывных сегментов агрегированные метрики выросли с 0,228→1,357 и с 0,260→5,062 (#7600). Исходная реализация организовывала доступ по срезам (n,c) или двумерным tile, что давало несогласованные чтения и записи; новая реализация покрывает каждым program непрерывный участок элементов, а канал или упакованную строку восстанавливает по плоскому индексу.
  • Маскированное заполнение: masked_fill на P800 вырос с 0,577 до 0,829 (#7850); подход — замена знакового расширения целочисленной маски на умножение на 0/1 с плавающей точкой после sitofp, что делает всё ядро векторизуемым; по точности m строго равен 0/1, результат побитово совпадает.
  • Сопровождаемость: #7803 исправляет невозможность импорта бэкенда Kunlunxin на текущем master (общий исполнитель удалил помощник _result_dtype), а также ошибку компиляции отношения доминирования в общем исполнителе на uni_sram — без этого исправления ни один тест Kunlunxin не запускается.
  • Сторона коммуникаций: traits платформы Kunlunxin в FlagCX выносят cstddef за пределы стража __xpu__ (#682); ранее при разборе из comm_traits.h size_t ещё не был виден, и компиляция общедоступного API устройства на стороне хоста сразу падала.

3.3 Iluvatar CoreX: свёртки через таблицу рабочих режимов, conv3d без добивки каналов нулями (10-28)

Дата: 2026-10-28　Источники: FlagGems PR #7036 · FlagGems PR #7061

Основной массив в проверке сейчас — 181 PR FlagGems, из которых 53 новых открытых в основном представляют собой исправления эталонных реализаций Enflame — это указывает на то, что узкое место приёмки мультибэкендов находится в эталонных реализациях и методике тестирования, а не в поставке операторов.
  • Множественные ветки требуют разграничения методик: FlagGems сливается одновременно в master и kernelgen-dev (#7905, #7934), слияния FlagTree распределены по веткам triton_v3.5.x и feature/flagmega, ветка по умолчанию FlagGems-Experimental — infra-ci. Статистика по ветке по умолчанию занижает фактический объём работ, а поиск по коммитам упускает репозитории с атомарными дополнительными ядрами.
  • Три пункта для наблюдения: во-первых, будет ли после v0.14.1 добавлено описание Release и включение в список 2.3; во-вторых, расширится ли путь BPU с поэлементных операторов на магистральные, такие как свёртки; в-третьих, начнётся ли реальная отправка кода Megatron-MUSA-Titan после окна и сформируется ли переиспользование с Megatron-LM-FL.
