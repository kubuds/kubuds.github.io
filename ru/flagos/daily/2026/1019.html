1.2 Новый репозиторий FlagCV: влит каркас многобэкендной библиотеки операторов для изображений с интерфейсом, совместимым с OpenCV (10-18 ~ 10-19)

Дата: 2026-10-18 ~ 2026-10-19　Источники: FlagCV · PR #1 · журнал коммитов

  • Факт: созданный 14.10 репозиторий FlagCV получил первый коммит 18.10 в 23:14 — «Add project skeleton and bitwise_and operator», 19.10 в 01:24 добавлен «Restructure as an immediate-mode skeleton without operators», 19.10 в 01:38 влит PR #1 (автор zhangjieBaai). В описании PR указаны три проектных решения: интерфейс выровнен по OpenCV (пять заголовочных файлов core / imgproc / gpumat / handle / types в include/flagcv/, соответствующих core и imgproc из opencv2), мультибэкендная структура повторяет FlagDNN, ядра написаны на Triton; данный PR содержит только скелет, без операторов.
  • Структура: из 81 пути в репозитории в backends/ сразу развёрнуты шесть бэкендов: nvidia / thead / ascend / hygon / iluvatar / mthreads (каждый содержит CMakeLists, backend.cpp, compiler.py и kernels/registry.json); src/ разделён на пять блоков: core, imgproc, image, lowering, runtime; compiler/flagcv_codegen — точка входа кодогенерации; в docs/ уже есть три документа: architecture, numerical-tolerance, operator-development.
  • Оценка: это первый выход операторной карты FlagOS за пределы «больших моделей / научных вычислений» в сторону обработки изображений — ранее пробел вроде FlagCV закрывался FlagDNN (операторы глубокого обучения) и собственными CV-библиотеками вендоров, теперь же создан отдельный репозиторий с OpenCV-совместимым интерфейсом. Развёртывание каталогов шести бэкендов сразу, а не по одному, говорит о намерении команды напрямую переиспользовать существующую мультибэкендную парадигму FlagDNN; появление документа numerical-tolerance раньше операторов также соответствует уже сложившемуся ритму FlagOS в линии KernelGen — «сначала зафиксировать критерии приёмки, затем массово добавлять операторы». Риск в том, что соответствие операторов обработки изображений (интерполяция, цветовые пространства, морфология) выразительным возможностям Triton пока не проверено, а в репозитории ещё нет работающих операторов, поэтому в краткосрочной перспективе делать выводы о степени покрытия преждевременно.

Унификация 22.04 — другая сторона той же логики: только зафиксировав нижнюю границу glibc среды сборки и среды поставки, можно говорить о «едином артефакте, устанавливаемом в нескольких местах» для кросс-дистрибутивных wheel. Это как раз соответствует «35 чипам», о которых говорилось на главном форуме — количество чипов должно подкрепляться воспроизводимой поверхностью поставки, иначе масштаб остаётся лишь списком.

4. Итоги и наблюдения за трендами

  • Нарратив и инженерия впервые синхронизировались: на главном форуме 2.2 был представлен как «масштабируемая совместная оптимизация» (21 производитель, 35 чипов, 1454 оператора, +27,6%, 264 контрибьютора), и в том же окне самая значительная активность на стороне GitHub пришлась ровно на build-infra — 22.04 builder для шести бэкендов и ежедневная матрица колёс по каждому бэкенду. Оба факта отвечают на один вопрос: список чипов должен опираться на воспроизводимую поверхность поставки. Это наиболее показательное соответствие данного выпуска.
  • Домен операторов расширяется, но направление расширения нужно понимать ясно: KernelGen за три дня добавил более тридцати операторов NVIDIA, в основном граничные операторы вроде _dim_arange, values_copy, _has_same_storage_numel, что говорит о почти завершённом покрытии магистрали и переходе к зачистке семантики псевдонимов и представлений; при этом прирост на отечественных бэкендах по-прежнему сосредоточен на Kunlunxin (более двадцати оптимизаций) и Damo Xuantie (дополнение GEMM), разрыв в покрытии между бэкендами не сокращается. Создание репозитория FlagCV — расширение в другом направлении: от LLM и научных вычислений к обработке изображений в стиле OpenCV, каталоги шести бэкендов развёрнуты сразу, однако в репозитории пока нет ни одного работоспособного оператора, и в краткосрочной перспективе не стоит переоценивать его.
  • На квантовой линии появилась продуктовая форма: двойной выпуск FlagQuantum 0.3.0 / 0.3.1 плюс публичный запуск Liangzhiyun — в примечания к релизу внесены инженерные возможности вроде «восстановление задач Jiuding / QUAFU», при этом явно указано, что на аппаратном обеспечении не запускается и не содержит agent runtime. Разделение труда таково: «FlagOS делает стек исполнения и планирование, институт кванта — аппаратное обеспечение и облако» — это лучше объясняет границы, чем общий лозунг «слияния квантовых и интеллектуальных вычислений».
  • Действия на стороне RISC-V — в глубине компилятора: smt_rvisa от SpaceMiT позволяет автору явно управлять SEW / VL / выбором инструкций и выводит из эксплуатации приватную копию TLE — такие изменения не попадают ни в одну публичную формулировку, но определяют, сможет ли бэкенд RVV перейти от «работает» к «выжимает производительность».
  • Что наблюдать: во-первых, стенограммы по секциям форумов и воркшопов конференции ещё не опубликованы — технико-тактическое содержание помимо главного форума (унифицированный IR, Token-фабрика, развёртывание на устройстве) пока существует только в формате повестки; во-вторых, когда Liangzhiyun откроется для внешнего доступа; в-третьих, когда FlagCV получит первый работоспособный оператор; в-четвёртых, на стороне обучения (Megatron-LM-FL / TransformerEngine-FL / FlagScale) три дня нулевых пушей — это нормальное затишье перед конференцией или начало цикла 2.3, нужно подтвердить в следующем выпуске.
