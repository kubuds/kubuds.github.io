Главное за сегодня: номер версии основного репозитория изменён на 0.1.16, тег и PyPI всё ещё на 0.1.15

#3887 вошёл в основную ветку 11-25 в 00:22 по пекинскому времени, изменён только один файл VERSION — 0.1.15 заменён на 0.1.16. Метаданные пакета и документация читают номер версии из этого файла, поэтому одного изменения достаточно для объявления версии повсюду.

В предложении перечислены три пункта проверки. Метаданные релиза при NO_VERSION_LABEL=ON разрешаются в 0.1.16. Три теста version-provider проходят. pre-commit run --all-files и bash format.sh оба проходят.

Со стороны релиза действий пока нет. Последний тег GitHub по-прежнему v0.1.15. Последний Releases по-прежнему v0.1.15 от 2026-09-30. На PyPI последняя версия tilelang также 0.1.15.

Поэтому в этом выпуске не пишем «0.1.16 выпущен». Точная формулировка: номер версии уже на месте, три шага — простановка тега, публикация Release и выкладка на PyPI — ещё впереди.

С предыдущей версии 0.1.15 до текущего продвижения номера прошло 55 дней. За это время в основной ветке накопились пакетные исправления ROCm, три правки Z3 и тест колеса Ascend.

Источник: https://github.com/tile-ai/tilelang/pull/3887.

Главное за сегодня: шесть влитий по ROCm за день — исправлено преобразование FP4 и определение редукции переведено на ширину wave

Из 12 коммитов основного репозитория за день 6 имеют префикс ROCm. Все эти изменения направлены на дефекты реальных путей квантизации и редукции.

#3665 Исправление двух пробелов в шаблонах HIP. Первый — неверное возвращаемое значение T.cast(x, T.float4_e2m1fn). Генератор кода записывает приведение как (fp4_e2_t)x, тогда как у этого типа есть только explicit fp4_e2_t(uint8_t raw). В результате float усекается до целого и сохраняется как сырые биты: 1.0 возвращается как 0.5, 2.0 — как 1.0, 6.0 — как 4.0, отрицательные числа ошибаются так же.

Второй — в шаблонах HIP отсутствует тип E8M0. Оба пробела вскрылись при запуске квантователя QAT для DeepSeek-V4 в VeOmni, окружение — gfx942 и gfx950, включая масштабы UE8M0. В колёсах 0.1.15 эти два заголовочных файла совпадают с основной веткой и подвержены той же проблеме.

#3959 Изменён критерий необходимости рабочей области для редукции. Старый код всегда возвращал истину, когда число потоков редукции превышало 32. На деле tl::AllReduce использует рабочую область только тогда, когда на некотором шаге происходит переход через wave, поэтому на wave64 редукция с 64 потоками выделяла LDS, к которой никогда не обращалась. Рабочая область в IR — это ещё и обращение к разделяемой памяти, и ThreadSync вставлял барьер при каждой такой редукции.

Исправление — сравнение по целевой ширине wave; поведение для цели wave32 не меняется. Барьеры сохраняются на путях, где действительно происходит переход через wave.

#3729 FP16 и BF16 T.gemm на gfx1200 теперь принимают стандартную линейную разделяемую раскладку. Ранее вызов make_linear_layout для A_shared, B_shared с последующим T.gemm выдавал Get different layout. Существующий эмиттер WMMA мог бы извлекать данные по этому отображению; проблема была в проверке совместимости.

Решение — расширить входные параметры callback-а совместимости разделяемой раскладки до четырёх: оператор, буфер операнда, фактическая раскладка, цель. На стороне ROCm по этому выполняется поэлементная проверка повторного использования по входам; эмиттер и отображение индексов не меняются.

Ещё три изменения относятся к инженерным деталям. #3954 заставляет compile_flags и tl.device_compile_flags действительно передаваться в hipcc. Ранее эти два параметра попадали только в ключ кэша и не меняли код устройства.

#3958 добавляет в hip_resource_info отчёт о занятости. #3956 описывает в документации ограничение T.gemm при малом числе строк на wave.

Источники: https://github.com/tile-ai/tilelang/pull/3665.

Главное за сегодня: Ascend за один день отчитался о десяти дефектах, все указывают на отсутствие валидации параметров API

За 24.11 один и тот же автор открыл в tilelang 10 дефектов Ascend, номера #4490–#4499. Тестовое окружение во всех десяти отчётах одинаковое. Аппаратура — Ascend 950PR, один die, 128 ГБ видеопамяти. Программное обеспечение — CANN 9.2.1, HDK 26.0.RC1, openEuler 24.03, torch 2.10.0+cpu, torch_npu 2.10.0.post4.

Шесть из них — «принят вход, который бэкенд не может скомпилировать». #4490: T.atomic_add принимает буферы int8, uint8 и float8. #4492: T.atomic_max и T.atomic_min принимают int8, uint8. #4491: T.reduce_sum принимает bfloat16 и float8. #4494: T.simd.vabs и T.simd.vneg принимают регистры bf16 и fp8.

#4495: T.gemm принимает произвольный unit_flag_ctrl, передача -1 или 999999 также компилируется молча. #4497: T.gemm принимает операнды в области видимости GM, и бэкенд не находит компилируемого пути.

Четыре ближе к падению или ошибочной компиляции. #4496: T.fill для разделяемого буфера float8_e4m3fn напрямую вызывает core dump компилятора bisheng. #4498: T.gemm принимает K, который не делится ни на один TILE_K_SUB, после чего падает assert в автоматическом планировании. #4499: скалярные T.sqrt и T.rsqrt при компиляции ядра вызывают ошибку из-за повторного объявления в stl_pair.h. #4493: пять атомарных интерфейсов не имеют реализации понижения на Ascend.

Есть ещё дефект корректности из независимого источника. #4484 указывает, что понижение редукции в SimdVF отображает все типы редукции, кроме sum, в max, и T.reduce_min возвращает максимум. Этот пункт получен из обзора исходного кода и не воспроизведён на устройстве.

Общая черта этого набора проблем: типы и значения, которые должны отвергаться на этапе компиляции, сейчас доходят до бэкенда и падают уже там. Вместе с шестью расхождениями документации и реализации от 23.11 это относится к одному классу — пробелам в контракте интерфейса.

Источники: https://github.com/tile-ai/tilelang/issues/4498.

1. Основные результаты по проектам

1.1 Z3 переводит кодирование масок младших битов на целочисленное взятие по модулю; основной репозиторий подхватывает bump и отзывает лимит решателя в тесте TopK

В подмодуле TVM ветка tilelang_main в этот день получила коммит #98, а в основном репозитории #4482 подхватил bump в 14:03. Все три исправления прослеживаются до конкретных дефектов Z3Prover.

Во-первых, знаковый сдвиг вправо константы, например (n + 4095) >> 12, ранее шёл по пути битовых векторов через три шага: int2bv, bvashr, bv2int. Когда такой сдвиг появляется в границах цикла, последующие чисто целочисленные запросы в той же области видимости одновременно несут ограничения Int и BitVec, что часто исчерпывает бюджет ресурсов по умолчанию в tirx.Simplify.

Во-вторых, VisitShiftOp в CanProve напрямую добавляет два утверждения b >= 0 и b < 64 в общий решатель. Это загрязняет последующие запросы и конфликтует с внешней областью видимости. Одновременно DivNode и ModNode используют евклидовы / и % из Z3, поэтому для отрицательного делимого также удаётся доказать truncmod(a, 4) >= 0.

В-третьих, маски вроде tx & 31 в упрощении индексных выражений по-прежнему идут по битовым векторам. #98 переводит x & (2^k - 1) в x mod 2^k. В предложении зафиксирована конкретная цена: в некоторой функции устройства упроститель задал 156 однотипных вопросов, затратив 11,7 секунды, контрпример — tx = 4.

Сначала на стороне тестов останавливают кровотечение, затем откатывают. #4463 в 09:51 ограничивает arith.z3_rlimit двух тестовых файлов ROCm значением 100, причина — четыре варианта использования TopK из DeepSeek и GLM каждый заняли от 494 до 605 секунд.

#4489 в 20:40 отменяет это ограничение, причина указана: #4482 удешевил знаковый сдвиг вправо констант. Сравнение велось на одной и той же сборке b4c67597, TVM de131ae4, Z3 4.15.4, бралась медиана из трёх холодных прогонов.

Источники: https://github.com/tile-ai/tilelang/pull/4482.

1.2 Пайплайн Dist дополняется тестом колёс Ascend — этот полусегмент ранее никогда не исполнялся на реальном железе

#4419 вошёл в основную ветку в 22:59. В предложении указана предпосылка: Linux-колесо собирается в тройной конфигурации CUDA, ROCm, Ascend, а test-wheels-gpu прогоняет только первые две половины. Полусегмент Ascend до выпуска колёс никогда не исполнялся на реальном NPU.

Добавлено задание test-wheels-ascend, работающее на самохостируемом раннере Ascend; настройка окружения имеет тот же источник, что и задание Ascend в ci.yml. Текущий образ — cann9.3.0-weekly.20261112-ubuntu22.04-py3.13. В реестре также есть варианты cann9.2.0, 9.2.1 и py3.10–py3.12, матрица может быть расширена.

Порядок работы задания: сначала берётся собранное Linux-колесо x86_64 и устанавливается в виртуальное окружение с --system-site-packages. torch и torch_npu контейнера предварительно закреплены.

Затем исходный пакет убирается в сторону, чтобы import tilelang попадал в колесо, а не в дерево исходников. Колесо собрано как abi3, wheel.py-api = "cp39", один артефакт устанавливается на любую версию Python.

Источники: https://github.com/tile-ai/tilelang/pull/4419.

1.3 Встроенные функции vote и sync сохраняют 64-битные предикаты, 1 << 32 больше не считается ложным

#3777 вошёл в основную ветку в 09:53. Встроенные функции CUDA vote и block-sync принимают только 32-битные предикаты int, например __any_sync, __syncthreads_count.

При передаче int64 или uint64 значение неявно сужается. Ненулевой предикат с нулевыми младшими 32 битами поэтому считается ложным; 1 << 32 — самый прямой пример.

Затронуто семь интерфейсов. Группа голосования: T.any_sync, T.all_sync, T.ballot, T.ballot_sync. Группа синхронизации: T.syncthreads_count, T.syncthreads_and, T.syncthreads_or.

Исправление состоит в том, чтобы предикаты длиннее 32 бит сначала нормализовать в явное != 0, а затем передавать в встроенные функции булево значение. Дополнительно добавлена рантайм-регрессия для 1 << 32, весь тестовый файл warp vote проходит.

Источники: https://github.com/tile-ai/tilelang/pull/3777.

2. Адаптация под несколько бэкендов (Ascend / Hygon / Moore Threads / MetaX)

2.1 Два коммита подрепозитория Ascend вошли в основную ветку: свёртка числа строк DMA и усиление установочного скрипта

Ветка по умолчанию tilelang-ascend — это ascendc_pto, а не main; скрипт, обращающийся к main по каждому репозиторию, получит пустой результат. В окне мониторинга по этой ветке — два коммита.

#1805 исправляет многомерную пересылку в Ascend copy. Для областей GM и UB с размерностью более двух ведущие измерения сворачиваются в число строк DMA; восходит к #1231. #1946 усиливает install_ascend.sh: при неудаче сборки shmem происходит немедленный аварийный останов, а пути в set_env.sh теперь разрешаются относительно каталога, где находится скрипт; восходит к #1728.

В подрепозитории в окне мониторинга среди находящихся на рассмотрении PR и новых issue есть ещё несколько достойных упоминания. #2025 исправляет колоночное хранение UB в Ascend и размеры DMA. #2035 сообщает об ошибке: при threads=2 генерируемые AscendVidReduction широковещательная рассылка и результат приведения по dim=0 неверны. Ежедневный тест #2034 фиксирует, что 11-24 прогнано 3120 элементов, 3120 элементов прошли.

Источники: https://github.com/tile-ai/tilelang-ascend/pull/1805.

2.2 MLIR Ascend в ветке диалекта влил tl.wait_flag и tl.vbitcast

Оба вливания попали в ветку mlir-dialect; в master в окне мониторинга новых коммитов нет. Эта ветка — линия эволюции диалекта TLIR.

#248 добавляет tl.wait_flag. Он вместе с tl.set_flag предыдущего дня образует полную пару примитивов синхронизации производителя и потребителя. Запись имеет вид tl.wait_flag[#tl.pipe<...>, #tl.pipe<...>, %event_id] : i64. Он переиспользует атрибут #tl.pipe, введённый set_flag, не добавляя новых атрибутов или типов. Понижение из TIR в TLIR переиспользует тот же набор PipeFromString и GetEventID.

#249 добавляет tl.vbitcast, проходящий три этапа — TIR, TLIR, HIVM; verifier проверяет совпадение формы и равенство битовой ширины элементов. Этот коммит попутно исправляет реальный дефект. VisitStmt_(LetStmtNode*) в CodeGenTileLangTLIR ранее полностью игнорировал op->value, и любой результат вызова, привязанный через let, молча отбрасывался. Возврат handle в tl.npuir_bitcast как раз зависит от этого пути.

Находящийся на рассмотрении #250 понижает tl.ln в hivm.hir.vln. В предложении также отмечено, что в не-TLIR пути BitcastCodegen есть аналогичный исторический пробел.

Источники: https://github.com/tile-ai/tilelang-mlir-ascend/pull/249.

3. Экосистема и стороны внедрения (библиотека операторов TileOPs / FlashQLA / topa)

3.1. Шестнадцать слияний в TileOPs, основная линия по-прежнему обходит накладные расходы проверки границ в 0.1.15

В заголовках шестнадцати слияний неоднократно встречается одна и та же фраза в разных формулировках: в 0.1.15 убрать проверку границ, привносимую неким общим путём.

#3161 заставляет warp-специализированное ядро FP8 indexer обходить проверку границ в 0.1.15. #3151 заставляет CausalConv1dFwdOp из Mamba на 0.1.15 держать предзаполненную сетку на одну волну постоянной. #3142 заставляет FP8 групповой GEMM из MoE сохранять только одну ветку на задачу и раскладывать срезы масок по всем SM.

#3146 сменил направление. Он выполняет ограничение выхода за границы Tensor внутри входного dtype, а не с повышением до более широкого целого с последующим ограничением.

Эта линия началась с #3133 от 11-23 «вернуть 25 строк регрессии». За два дня действия по восстановлению прошли путь от «сверки с 0.1.12» до «обхода по контрольным точкам одну за другой».

Источники: https://github.com/tile-ai/TileOPs/pull/3161.

3.2. В линиях сэмплирования, свёртки и редукции по одному структурному изменению

Два изменения на стороне сэмплирования. #3157 выполняет разбиение разбитой строки top-p с использованием глобальных атомарных величин. #3158 выполняет разбиение и суммирование той же строки с фиксированной точкой, делая маску воспроизводимой.

По одному изменению в свёртке и индексировании. #3148 распределяет сжатие симметричной Conv2d на свободные SM. #3156 заставляет конкатенацию двух входов сразу после одной волны выполнять четыре вектора на поток.

Два изменения в редукции. #3152 завершает ведущую ось за один запуск, разделяя по thread-block cluster. #3154 завершает свёртку any и all внутри блока одним барьером или одной операцией ИЛИ.

Три изменения в линейном внимании. #3160 на пути chunk-parallel выполняет предобработку сверх одного chunk для предзаполнения KDA fp16 given-gate на SM90. #3159 привязывает флаг transfer прохода разделения GDN к значению, чтобы 0.1.15 его не потерял. #3144 заставляет состояние key-major KDA декодироваться в порядке памяти и проходить вместе с упакованной последовательностью.

Источники: https://github.com/tile-ai/TileOPs/pull/3158.

3.3. Ночные тесты переходят к отчёту по пропускной способности предзаполнения и декодирования batch-1 для каждой модели

#3150 относится к линии Mamba и передаёт строку состояния декодирования CausalConv1dUpdateFwdOp через разделяемую память.

5. Наблюдения за трендами

  • Ритм версий вошёл в предрелизную ночь. 0.1.15 выпущена 9-30, через 55 дней номер версии продвинулся до 0.1.16. Накопление в этой версии — в основном исправления ROCm, три правки Z3 и инженерия цепочки релиза, а не новые функции.

  • Работа с регрессиями производительности оформилась в устойчивую схему. Сначала добавляют лимит как меру остановки крови, затем исправляют корневую причину, в конце отзывают лимит и проводят повторное тестирование. Три шага #4463, #4482, #4489 выполнены в течение одного дня, между ними — одно обновление субмодуля TVM.

  • Слабое место Ascend сместилось с покрытия операторов на контракты интерфейсов. Ни в одном из десяти дефектов за день не требовался новый оператор — все они о том, что «принимается вход, который не должен приниматься». Такие проблемы дешево исправлять, но они постоянно подрывают доверие пользователей.

  • Критерий оптимизации TileOPs по-прежнему — догонять версию фреймворка. Дополнительные издержки от общего пути 0.1.15 требуют, чтобы нижестоящие проекты обходили их пооператорно. За два дня как минимум пять изменений с таким заголовком, что показывает: между обновлением версии и производительностью библиотеки операторов всё ещё нет автоматической сверки.

  • На стороне RISC-V два окна подряд нулевые изменения. Маршруты TVM и MLIR стоят на месте, в этом окне даже индексная страница без движения.

Пояснения к проверке

Окно: с 07:00 24 ноября по 07:00 25 ноября по пекинскому времени, всего 24 часа. Коммиты репозиториев учитываются по времени committer; сначала сравнивается с предыдущей контрольной точкой 24 ноября 07:00, затем определяется добавление.

Время committer коммита с номером версии — 24 ноября 16:22 UTC, что соответствует 25 ноября 00:22 по пекинскому времени, и учитывается в этом выпуске. В тексте указано «номер версии изменён, релиз не завершён», не утверждается, что 0.1.16 уже выпущен.

Два изменения MLIR Ascend проверены по базовой ветке PR: они находятся в mlir-dialect и не учитываются в основной ветке master. Ветка по умолчанию подрепозитория Ascend — ascendc_pto; при выборке по main в скрипте для каждого репозитория результат будет пустым, поэтому два изменения этого выпуска проверены по этой ветке по умолчанию.

35 слияний на уровне организации сопоставлены по одному с коммитами в основные ветки репозиториев: tilelang — 12 против 12 PR, TileOPs — 16 против 16 PR, MLIR Ascend — 2, подрепозиторий Ascend — 2, tvm, Hygon и MetaX — по 1.

Для четырёх источников RISC-V на этот раз выполнено только сравнение ссылок; интерфейс PR недоступен из-за анонимного ограничения скорости, таблица проектов в README индексной страницы не перепроверялась, что указано в разделе 2.5.1.

Новостная часть перепроверена по трём каналам — Google News на китайском и английском, Hacker News и arXiv; в окне действительно отсутствуют материалы, связанные с TileLang, и пустой результат не был истолкован как сбой сбора.
