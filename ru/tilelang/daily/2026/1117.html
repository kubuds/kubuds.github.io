Главное сегодня: публичное раскрытие злоупотребления CI в вышестоящем репозитории Ascend и кражи учётных данных контрибьютора

16-11 14:16 (пекинское время) участник liggest открыл issue #2016 в tile-ai/tilelang-ascend, публично сообщив, что его учётная запись была скомпрометирована 11-15, и описав полную цепочку атаки: с 7 утра 11-15 учётная запись под именем miramar-labs (сама по себе, предположительно, угнанная) отправила PR #2014, в который был добавлен вредоносный скрипт, собирающий информацию о сервере во время выполнения CI; CI репозитория работает на собственных серверах, после заражения атакующий похитил с сервера большое количество информации и учётных данных для входа, включая GitHub token, принадлежащий liggest. С 9:39 до 11:40 утра 11-15 атакующий использовал этот token, выдавая себя за liggest: опубликовал 18 комментариев подряд под #2014, предположительно используя публичный PR как окно для получения данных; открыл два PR со скриптами майнинга в tile-ai/TileOPs (#2902, #2903, вскоре закрытые мейнтейнерами); также открыл аналогичный PR #5086 в SemiAnalysisAI/InferenceX, пытаясь заставить их benchmark-сервер выполнить его, что было обнаружено и закрыто владельцем ранним утром 16-го. Автор утверждает, что два скрипта майнинга не были выполнены из-за автоматических проверок GitHub, и записей о выполнении не обнаружено.

Со стороны реагирования: на учётной записи была включена двухфакторная аутентификация, прямого захвата не произошло; автор отозвал старые авторизации GitHub CLI и VSCode, заявив, что token недействителен и после 15-го числа с учётной записью не было аномалий; вредоносный fork временно сохранён для криминалистики; CI-сервер с похищенными данными ожидает обработки по безопасности; #2014 также требует обработки, иначе остаётся риск повторного запуска вредоносного скрипта. Рекомендация автора: PR новых участников должны запускать CI-процессы на собственных серверах только после одобрения мейнтейнером.

Со стороны проверки: поиск по GitHub показывает, что miramar-labs в период с 11-14 23:18Z по 11-15 02:04Z отправил PR в том же стиле в четыре репозитория — tile-ai/tilelang #4148, tile-ai/tilelang-ascend #2014, tile-ai/tilelang-mlir-ascend #251, tile-ai/TileOPs #2900, номинально все они были «прогревом кэша» или «зондированием возможностей CI»; все четыре PR закрыты, ни один не был смержен, #2014 закрыт 11-16 в 11:29. После закрытия issue автор добавил ещё один комментарий, заявив, что предыдущее описание «выглядит также преувеличенным, в общем, учётная запись восстановлена», поэтому указанный выше масштаб ущерба остаётся по словам самого автора, третьей стороны проверки пока нет. Прямое влияние на данное сообщество трояко: граница доверия собственного CI была пробита внешним PR, жизненный цикл личных token’ов должен быть включён в аудит, одноимённые PR появляются одновременно в нескольких репозиториях.

Главное сегодня: 18 слияний TileOPs за один день, библиотека операторов переходит к выравниванию интерфейсов с pilot-моделью

В окне мониторинга в основную ветку TileOPs попало 18 коммитов (соответствующих 18 PR), это самый плотный день сезона, и направление крайне единообразное: сначала дополнить возможности описания интерфейсов manifest (#2958 вводит вызовные type и default, объединённые типы list[Tensor] и скаляр или тензор; #2967 регистрирует семь операторов, которые pilot-модель реально будет вызывать, как spec-only, и дополняет пятнадцать уже реализованных операторов параметрами и входами, используемыми pilot-моделью), затем один за другим [Feat][foundry] PR добивают операторы. В этот день смержены два новых оператора (Gated RMSNorm, MaskedScatter), при этом Embedding после слияния в тот же день был откатан, что показывает: новые операторы должны проходить раунд TileFoundry, а не сливаться напрямую. #2958 попутно исправляет две семантические ошибки: семейство RoPE ранее вращало только позиции 0..S-1, результат вращения для позиции декодирования p был неверным; FP8QuantPerTokenGroupFwdOp не соответствовал своей эталонной реализации.

Источники: https://github.com/tile-ai/TileOPs/pull/2958 、https://github.com/tile-ai/TileOPs/pull/2967

1. Прогресс ключевых проектов

1.1 В основной репозиторий смержены четыре bugfix: восстановление устройства JIT, один параметр NVRTC, динамическая разделяемая память cython, повторное использование рантайма ROCm HIP

В основном репозитории в окне мониторинга было слито четыре коммита, и все они касаются дефектов времени выполнения, а не новых возможностей. #3872 исправляет проблему, когда хост-заглушка tvm_ffi только устанавливала текущее устройство, но не восстанавливала его: при вызове тензора на cuda:1 с cuda:0 результат был корректным, но текущее устройство оставалось на cuda:1, и последующие выделения с device="cuda" молча смещались; исправление заключается в том, чтобы на уровне адаптера обернуть вызов в torch.cuda.device(...) и восстановить устройство при завершении. #3880 исправляет невозможность запуска одноаргументных ядер в бэкенде NVRTC: после объединения имён и типов параметров через ", " при одном параметре получалась не кортежная структура, и cuLaunchKernelEx напрямую выбрасывал TypeError; заменено на литерал кортежа с завершающей запятой. #3882 исправляет проблему бэкенда cython, где верхний предел динамической разделяемой памяти задавался только один раз в init() — это свойство является по-устройственным, и ядра, требующие более 48 KB на остальных устройствах, выдавали cudaErrorInvalidValue; заменено на генерацию вспомогательной функции _set_dynamic_smem() для каждого ядра с записью устройств, для которых предел уже повышен. #3899 исправляет проблему в ROCm, когда заглушка HIP не находила поставляемую с PyTorch libamdhip64: ROCm wheel-пакет PyTorch загружается с RTLD_LOCAL, заглушка сначала с помощью RTLD_NOLOAD проверяет уже отображённую среду выполнения, чтобы избежать появления второй копии среды выполнения через dlopen, из-за чего дескриптор модуля оказывался привязан к другой среде выполнения и первый запуск kernel завершался ошибкой.

Источники: https://github.com/tile-ai/tilelang/pull/3872 , https://github.com/tile-ai/tilelang/pull/3882 , https://github.com/tile-ai/tilelang/pull/3899

1.2 manifest обновлён до декларативных типов параметров, интерфейс pilot-модели дополнен за один раз

#2958 расширяет manifest с возможности описывать только фиксированные тензоры и скаляры до объявления трёх типов сигнатур: последовательности тензоров (torch.cat), выбор между скаляром и тензором (seqlen_offsets в flash_attn, torch.clamp(min)), обязательный, но допускающий None (bias в mamba_ssm), а также унифицирует входные данные времени вызова в виде объявлений с type и default; ранее выделенные три группы пар операторов Scalar/Tensor для случая «скаляр или тензор» при этом объединены. #2967 поверх этого дополняет интерфейс pilot-модели истинными значениями: семь новых записей, зарегистрированных как spec-only (включая эталонную реализацию torch), пятнадцать уже реализованных записей дополнены фактически передаваемыми в pilot-модель параметрами и входами, ядра при обнаружении нестандартных значений отклоняют их с OpNotAvailableError, статус записей остаётся implemented, а строки бенчмарка при такой ошибке записываются как «недоступно», а не как неудача.

Источники: https://github.com/tile-ai/TileOPs/pull/2958 , https://github.com/tile-ai/TileOPs/pull/2967

1.3 Три новых оператора: реализованы RMSNorm с гейтированием и MaskedScatter, Embedding слит и в тот же день откачен

#2984 добавляет RMSNormGatedFwdOp: RMSNorm с группировкой по последней оси, с возможностью гейтирования с помощью silu(z) или sigmoid(z) до или после нормализации, все вычисления во float32 с единственным округлением; одно ядро TileLang покрывает все формы вызова (8 lane, по два 16-байтовых обращения на каждую lane образуют строку шириной 128, 16 строк составляют CTA из 128 потоков, более широкие группы удваивают lane до 1024 и суммируют через разделяемую память между warp’ами), предел регистров установлен в 64 на поток, экспонента и обратная величина для гейтирования каждая реализована одной инструкцией. Бенчмарк соответствует RMSNormGated из vLLM, rmsnorm_fn из mamba_ssm, rms_norm_gated из fla, Qwen3_5RMSNormGated из Hugging Face, а также эталону torch и torch.compile, и достигает порога приёмки. #2982 добавляет MaskedScatterFwdOp (out-of-place версия masked_scatter, поддерживает fp16/bf16/fp32 и широковещание input и mask): каждый CTA получает полный непрерывный сегмент mask (число строк ограничено 32 KB), сначала подсчитывает истинные сегменты перед своим сегментом, затем сканирует собственный, каждое 16-байтовое векторное чтение выполняется только один раз (для истинных сегментов читается source, для ложных — input), при размере сегмента более четырёх блоков сначала выполняется блочный подсчёт; по сравнению с torch eager и torch.compile порог достигнут,原地 многомодальное объединение в vLLM из-за иной семантики отмечено как несравнимое.

В тот же день произошёл ещё один откат: после включения EmbeddingFwdOp в #2977, #2983 в тот же день полностью откатил его, поскольку этот PR был ошибочно объединён, а новый оператор должен проходить отдельный цикл TileFoundry; после отката запись вернулась в состояние spec-only, ядро, оператор, бенчмарки, тесты и рабочие нагрузки были удалены. #2975 всё ещё на рассмотрении — это официальное предложение того же оператора (gather строк весов по индексам токенов).

Источники: https://github.com/tile-ai/TileOPs/pull/2984 , https://github.com/tile-ai/TileOPs/pull/2982 , https://github.com/tile-ai/TileOPs/pull/2983

1.4 Три линии квантизации GEMM: INT8 W8A8 переходит на ping-pong шириной 192, W4A8/W4A16 stream-K доводятся по отдельности

#2959 заставляет INT8 ping-pong GEMM использовать тайл 128×192, когда «число столбцов самого занятого CTA не превышает тайл 128×128», а в конце сетки по правилу узких тайлов bf16 GEMM сворачивается в блок хранения, выровненный по 32 столбцам (в каждой строке prefill манифеста этого выпуска это 160 по ширине), для каждой ширины выпускается WGMMA соответствующей ширины; при той же нагрузке самого занятого CTA тайл шириной 192 на каждый MAC переносит меньше байтов разделяемой памяти TMA и WGMMA, а CTA в три раза реже переключает потребителей; число столбцов самого занятого CTA последней волны llama3-8b prefill-qkv снижается с 1536 до 1504. #2960 меняет завершение stream-K для W4A8 prefill: когда все остальные частичные блоки уже записаны на диск, поздно пришедший участник с номером 0 больше не записывает свою часть частичной суммы, а завершение выполняет участник, досчитавший счётчик до полного числа вкладчиков этого тайла; каждый CTA использует только одну acquire-release атомарную операцию (после именованного барьера) вместо fence на каждом потоке, и CTA не ждут друг друга; новый путь проходят только программы, содержащие тайлы stream-K, остальные результаты компиляции совпадают с основной веткой. #2964 исправляет рассогласование в W4A16 stream-K: ядро изначально защищало логику «дозаполнения неиспользуемых слотов и выполнения деления с округлением вверх» условием cta == first_cta, но упрощение TileLang полностью выбрасывало весь этот блок после второго сегмента CTA и сворачивало его после первого сегмента, из-за чего в тайле, общем для двух CTA, оставались незаписанные слоты, а редукция читала грязную память, и максимальная ошибка возрастала с 2.4 до бесконечности; исправление — однократное построение таблицы хостом на устройстве сборки этой программы с определением слота по «номеру CTA внутри тайла».

Покрытие квантизованного GEMM также дополнено: #2969 добавляет 42 строки W4A16, 13 строк W4A8 и 11 строк FP8, каждая строка соответствует реальной проекции Llama-3 8B/70B, Qwen3 8B/32B или DeepSeek-V3 (TP1 или TP8, пакет декодирования); ранее строки бенчмарков W4A16 покрывали только 3 из 45 областей планирования декодирования. Кроме того, на рассмотрении находится #2990 (ужесточение условий подбора тайлов декодирования W4A16), причиной стал зафиксированный в issue #2966 факт, что та же партия изменений на некоторых формах из 8 и 16 строк работает медленнее, чем до изменений.

1.5 Внимание и линейное внимание: продолжение калибровки paged GQA, конфигурация запуска DeltaNet, разделяемая память обратного прохода GLA

5. Наблюдения за трендами

  • Библиотека операторов стала главным полем битвы: из 30 слитых изменений за этот период 18 приходятся на TileOPs, а в основном репозитории лишь 4 bugfix рантайма; центр тяжести работы сообщества сместился с самого компилятора на реализацию операторов и эталонные значения интерфейсов.
  • Интерфейс опережает реализацию: типы параметров manifest и интерфейсы pilot-моделей были дополнены в один и тот же день, после чего новые операторы появлялись один за другим по раундам; ошибочный merge Embedding и откат в тот же день говорят о том, что процесс ужесточается, а не ослабляется.
  • Инструментализация процессов: раунды new-op в topa, конечный автомат и маршрутизация issue вместе с закрытием пробелов в модели стоимости TileFoundry образуют замкнутый цикл «потребность в операторе → выполнимость планирования → реализация и приёмка»; этот слой за последние две недели рос быстрее всего.
  • Исправления производительности начали давать обратный эффект: парные тайлы W4A16 на некоторых малых формах показывают регресс (issue #2966); оптимизация квантованного GEMM вошла в стадию, когда «необходимо разбиение по формам», и единая стратегия тайлинга уже вряд ли будет давать универсальный выигрыш.
  • Границы безопасности требуют доработки: инциденты с проникновением внешних PR в собственный CI и кражей личных token’ов показывают, что для PR новых контрибьюторов запуск CI должен по умолчанию требовать одобрения мейнтейнера; это правило применимо и ко всему сообществу RISC-V и AI-компиляторов.
  • Темп на стороне RISC-V стабилен: за период только одно слияние по линии MLIR (перевод buddy-opt в режим по умолчанию и дополнение примеров), по линии TVM и на стороне TPU Sophgo движения нет — это нормальное чередующееся продвижение.
