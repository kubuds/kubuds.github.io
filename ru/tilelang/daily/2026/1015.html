1. Прогресс ключевых проектов

1.1 Основной репозиторий: четыре завершённые работы на стороне Ascend — независимое исполнение AIV (#3485), PTO DeepGEMM codegen (#3330), исправление кросс-warp allreduce (#3494), выбор цели в примерах (#3474) (10-14)

Дата: 2026-10-14　Источники: независимое AIV (#3485)／ PTO codegen (#3330)／ исправление allreduce (#3494)／ выбор цели в примерах (#3474)

  • Независимое выполнение AIV (#3485): расширение Ascend AutoSchedule, чтобы AIV0 и AIV1 могли выполнять разную работу под управляемым зависимостью sid потоком управления — поддержка чередующегося эпилога (epilogue), разделения деквантизации и эпилога, непересекающихся входных разделов и переключения ролей внутри цикла. В реализации AssignCore перенесён до оценки задержки и планирования, для локальных UB-буферов AIV и скалярного состояния создана независимая идентичность, а также смоделированы конвейерные ресурсы по участвующим ядрам, зависимости специальных регистров, ёмкость UB и библиотека флагов синхронизации; сохранены collective-путь унифицированного ядра и геометрия запуска с одним/двумя AIV. Копирование L0C→UB по-прежнему выполняется на AIC.
  • PTO DeepGEMM codegen (#3330): сквозное отслеживание tl.ascend_set_mmad_direction через потоки управления и кодирование действующего направления в инструкцию MAD, отклонение MAD, достижимых при конфликтующем направлении; поддержка инкрементальной загрузки после SIMD (одновременный возврат данных и указателя обновления), преобразования UB-адресов в указатели PTODSL в смешанных ядрах AIC/AIV, динамических размерностей и шагов L0C→UB, знакового упакованного MX scale int16; улучшена генерация кода условных выражений и циклов времени выполнения. Сообщается, что 14 из 15 случаев использования DeepGEMM PTO проходят, test_bf16_m_grouped_padding по-прежнему заблокирован, поскольку бэкенд PTOAS VPTO не может легализовать преобразование FP32→BF16.
  • Исправление cross-warp allreduce (#3494): когда вызов cross-warp allreduce охватывает несколько независимых групп редукции, цели ascend и pto ошибочно передавали результат первой группы всем группам; этот коммит исправляет указанную проблему корректности (продолжение #3469).
  • Выбор цели для примеров (#3474): удалён жёстко закодированный target="ascend" в примерах и тестах Ascend, выбор передан переменной окружения TILELANG_DEFAULT_TARGET; точка входа DeepGEMM JIT поддерживает execution_backend="auto"; CI прогоняет набор примеров Ascend дважды — с целями ascend и pto, а способ выбора описан в документации.

1.2 Основной репозиторий: три коммита по инфраструктуре — параллельные grid-циклы CPU OpenMP (#3109), общий выпуск C-серии codegen (#3289), Windows NVCC через MSVC (#3510) (10-14)

Дата: 2026-10-14　Источники: CPU OpenMP (#3109)／ codegen общий (#3289)／ Windows MSVC (#3510)

  • CPU OpenMP параллелизм (#3109): для бэкенда CPU добавлена опциональная OpenMP-параллелизация grid-циклов — новый MaterializeCPUParallelGrid преобразует аннотированные CPU grid-циклы в параллельные циклы, в комплекте свёртка циклов (collapse), настройка числа потоков, порог минимального числа итераций (trip count) и понижение размещения (allocation sinking); добавлены флаги компиляции OpenMP и параметры pass для Linux / macOS / Windows; тесты покрывают корректность, pragma, понижение размещения, пороги и одномерный случай. Бэкенд CPU впервые получил возможность параллелизма на уровне сетки.
  • Общий codegen C-серии (#3289): введён CodeGenTileLangCBase, унифицирующий генерацию кода CUDA, HIP, CPU C, Ascend C++, Metal и C-хост-кода; исправлена проблема, когда T.import_source, T.Kernel(prelude=...) и pragma_import_c при отсутствии завершающего перевода строки в исходном тексте или при окончании обратной косой чертой «съедали» следующую сгенерированную строку; импортируемое содержимое упорядочивается как «заголовочные файлы→импорты→сгенерированные объявления и функции» с гарантией двух разделяющих переводов строки. Проверка: 83 фокусированных регрессионных теста пройдено, 405 тестов соответствующих наборов codegen и launch пройдено.
  • Windows NVCC через MSVC (#3510): NVCC отвергает clang-cl, выбираемый get_cplus_compiler() — изменено на выбор cl.exe из окружения подпроцесса NVCC (выбор основного компилятора C++ не затрагивается), добавлен запасной путь VS 2026 18/*, на не-Windows платформах -ccbin=None больше не передаётся; при CUDA 13.3 воспроизводящий случай до исправления падал, после исправления компилируется успешно.

1.3 Основной репозиторий: исправление волнового фронта ROCm scan (#2326), кэширование тестовой инфраструктуры (#3502) и конфигурация управления (#3513) (10-14)

Дата: 2026-10-14　Источники: ROCm scan (#2326) / тестовая инфраструктура (#3502) / метки CodeRabbit (#3513)

  • Исправление волнового фронта ROCm scan (#2326): HIP-реализации cumsum / cummax по умолчанию выполняются сегментами по 64 lane, что даёт неверные результаты на GPU с Wave32 — существующий вход run теперь выбирает ширину сегмента в соответствии с шириной волнового фронта целевой архитектуры (с учётом ограничения на число потоков в блоке), блоки из 32 потоков на этапе компиляции исключают шаблон с 64 lane; добавлено покрытие для прямого/обратного сканирования с 32 потоками и для случаев с разными шагами источника/назначения; пример gfx950 MXFP4 и тесты переведены на целевую запись {"kind": "hip", "mcpu": "gfx950"}. Проверка: набор тестов CUDA scan на B300 — 17 пройдено, тесты генерации исходников CuTeDSL — 2 пройдено; проверка времени выполнения на стороне AMD оставлена для ROCm CI.
  • Кэш тестовой инфраструктуры (#3502): кэшируются данные вызовов последнего запрошенного IR-тела для использования в collect_calls / assert_call_count; рекурсивные visitor’ы в тестах трансформаций и текстовые проверки сгенерированных скриптов заменены на структурированные IR-утверждения, а также расширены структурные проверки программного конвейера, планирования, синхронизации, барьеров и Hopper intrinsic.
  • Конфигурация управления (#3513): включена автоматическая расстановка меток CodeRabbit для PR и issue (13 меток для PR, 14 для issue), сохранены все 11 правил маршрутизации ревью, никакие метки не добавлены/переименованы/удалены.

1.4 Основной репозиторий на ревью: четыре новых PR семейства PTO, обновления исправлений барьеров TMA и разделяемых буферов (10-14)

Дата: 2026-10-14　Источники: PTO/tvm_ffi (#3516) / векторизация PTO VMI (#3512) / барьер TMA (#3503) / защита разделяемых буферов от двойного расширения (#2342) / список PR основного репозитория

  • Четыре новых PR семейства PTO: поддержка цели PTO в бэкенде исполнения tvm_ffi (#3516), векторизация T.Parallel в PTO VMI (инфраструктура конвейера и поэлементная поддержка, #3512), поддержка SS buffer (#3514), явный pitch для частичного копирования L0 (#3511).
  • TMA и конвейер: барьер TMA forward с синхронизацией всех потоков-производителей (#3503, обновление), защита от двойного расширения разделяемых буферов братских конвейеров (#2342), запись только проверенных имён дескрипторов TMA (#3484).
  • Прочие обновления на ревью: устранение времени компиляции тестов (#3517), безопасное уплощение нормальных константных делителей (#3488), очередь задач torch_npu (#3324), редукция SimdVF dim=1 (#3437), пример ручного планирования FlashMLA (#3464), Windows ARM64 CI (#2962). Открытых PR в основном репозитории — 160 (в предыдущем выпуске 161).

2. Мультибэкендная адаптация (Ascend / MetaX / Hygon / Moore Threads)

2.1 Hygon: принято обновление до v0.1.15 (#20), создана релизная ветка, открыта линия распределённого IPC (#19) (10-14)

Дата: 2026-10-14　Источники: обновление до v0.1.15 (#20) / Distributed (#19) / ветка distributed / ветка v0.1.15-release

  • Обновление до v0.1.15 включено (#20): репозиторий целиком обновлён до upstream TileLang v0.1.15, сохранена поддержка бэкенда HCU и существующий рабочий процесс build.sh; выполнена адаптация к обновлённому бэкенду, конвейеру lowering, языковому API и тестовым интерфейсам; добавлено планирование раскладки scale-буфера для HCU blockscaled GEMM и сопутствующая поддержка раскладки LDS; информация о релизе в README синхронизирована. После включения создана ветка v0.1.15-release (с тем же головным коммитом, что и main), чтобы зафиксировать релизную линию.
  • Открыта линия распределённого IPC (#19): с объёмом +2577/-28 и 44 файлами открыто направление «Distributed» — ветка distributed содержит ряд работ по HCU IPC (межпроцессному взаимодействию): унифицированный запускатель распределённых процессов, проверка инициализации метаданных IPC, тесты BF16 / полностью симметричного IPC allreduce, пример IPC GEMM allreduce, распространение ошибок закрытия и сбоя инициализации IPC, защита от недопустимых peer и т. д. Многокарточная коллективная коммуникация становится новым рабочим направлением бэкенда Hygon.
  • Конвейеризация регистров (#18): продолжает находиться на рассмотрении (после 10-13 новых пушей нет). В репозитории Hygon открыто 2 PR (в прошлом выпуске — 1). В ветках feat/hcu-mqa-fp8 и feat/hcu-gemm-blockscaled-async-copy-layout в окне новых пушей нет.

2.2 Ascend: три отката фактчекинга и переработка (#1888–#1890, #1893); три новых PR по примерам и операторам (10-14)

5. Наблюдения за трендами

5.1 Выравнивание всех бэкендов на v0.1.15 близится к завершению

  • После выпуска upstream v0.1.15 (09-30) MetaX 10-13 догнала main до узла v0.1.15, Hygon в этом окне через #20 завершил полное обновление и создал ветку релиза — оба бэкенда выровнялись друг за другом в течение двух недель, причём Hygon одновременно с обновлением внёс планирование раскладки блочно-масштабированного GEMM в новую базовую линию. Остаётся Moore Threads, по-прежнему застывшая после 09-30, а Ascend в дальнейшем точечно дополняет описание API через «фактчекинг документации». Основа «одна версия, одна семантика» для множества бэкендов завершается.

5.2 «День инфраструктуры» основного репозитория: рефакторинг компиляционного слоя и развёртывание платформ

  • Более половины из 10 слияний за одно окно — компиляция и платформенная инфраструктура: общий codegen для C-семейства (унифицированный базовый класс CUDA / HIP / CPU / Ascend / Metal), сеточный параллелизм CPU OpenMP, цепочка Windows MSVC, кэш тестовой инфраструктуры, волновой фронт ROCm scan — плюс четыре новых PTO/Ascend. В период затишья релизов (15 дней без новой версии после v0.1.15) усилия явно направлены на низкоуровневую расширяемость и поддержку новых платформ, что взаимно дополняет ритм «слияние MoE/производительности → рост основы → новая версия».

5.3 Ночная база +41: тесты растут синхронно с мержами

  • Корректность за сутки +41 пункт — максимальный прирост за последнюю неделю, и он взаимно однозначно соответствует 16 коммитам TileOPs (пакеты производительности обычно идут с добавлением test-node, расширение внимания — с новыми строками нагрузки). Скользящий учёт «один мерж — база подросла» продолжает осаждать проверку каждого изменения в ночной снимок — статическая подготовка перед релизом по-прежнему стабильно накапливается.

5.4 Дисциплина откатов в репозитории Ascend: низкоприоритетные用例 тоже под контролем

  • Первые три PR «проверка фактов в документации» были целиком откачены из-за некорректного несовпадения регулярного выражения в ожидаемо провалившихся用例 низкого приоритета, а затем переделаны в урезанном виде — это обнажает двухуровневую структуру верификации: «на этапе PR в CI не запускаются用例 низкого приоритета, их подхватывает ежедневный полный набор». Такая обработка «откат — переделка», а не «движение вперёд с повреждениями», говорит о том, что управление CI в репозитории адаптации Ascend переходит от «всё проходит» к «точные утверждения, единые критерии», а также означает, что качество мержей в окне постоянно ограничивается ежедневным полным прогоном.
