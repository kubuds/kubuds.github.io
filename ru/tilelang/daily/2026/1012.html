1. Основные достижения проекта

1.1 Основной репозиторий: блочное масштабирование MMA для SM121 (DGX Spark); исправления выборов барьеров CuTeDSL и идентичности параметров (10-10 ~ 10-11)

Дата: 2026-10-10, 2026-10-11　Источники: Блочное масштабирование MMA для SM121 (#3430)／ Выборы барьеров CuTeDSL (#3400)／ Идентичность параметров NVRTC / CuTeDSL (#3414)

  • SM121 включён (#3430, 11.10 00:32, коммит): SM121 (GB10, DGX Spark) фактически поддерживает warp-блочное масштабирование MMA уровня SM120, но tl::sm120_mma_sync_blockscaled проверяет только CUTLASS_ARCH_MMA_SM120A_ENABLED (определён только при __CUDA_ARCH__ == 1200), что приводит к тому, что все блочно-масштабированные MMA при sm_121a компилируются в BPT.TRAP вместо OMMA.SF; данный коммит изменён на приём целей SM120 / SM121 одновременно по arch и семейству, тесты NVF4 используют гейтинг по семейству SM12x, таблица архитектур CuTeDSL TMA пропускает sm_121 / sm_121a. Автор проверил на DGX Spark (драйвер 580.178.04, CUDA 13.0).

  • Выборы барьера (#3400, 10.10 10:47, коммит): Ранее sync_grid() выбирал все потоки с tid.x == 0, при 2D / 3D блоках потоков несколько потоков повторно публиковали достижение одного и того же блока, и барьер мог сработать преждевременно; теперь выбирается только физический поток (0, 0, 0), счётчик / протокол поколений и кооперативный запуск не изменены. Регрессия покрывает 1D / 2D / 3D сетки и повторное использование (RTX 5090, CuTeDSL 4.7.0).

  • Идентичность параметров (#3414, 10.10 13:58, коммит): NVRTC и оболочка хоста CuTeDSL ранее генерировали сигнатуры по исходным именам Var и сопоставляли параметры по печатным именам, что приводило к перекрёстным помехам при совпадении имён (stream, device_id и т. п.) и переименовании на стороне устройства; теперь имена параметров оболочки назначаются по идентичности Var с сохранением позиционного ABI, CuTeDSL позволяет повторно вызывать одно и то же ядро с различными скалярными привязками, и одноимённые символы shape / stride становятся различимыми.

1.2 Основной репозиторий: завершение белого списка dtype для GEMM — неподдерживаемые комбинации отклоняются до CUDA codegen (12.10)

Дата: 2026-10-12　Источник: Белый список dtype для GEMM (#3245)

  • Некоторые комбинации dtype операндов T.gemm (например, bf16 x bf16 в fp16) ранее принимались на фронтенде и падали только внутри nvcc с непрозрачным static_assert (баг #3004); данный коммит добавляет явный белый список dtype для пути Ampere / Ada mma.sync, принудительно применяемый как на фронтенде (tileop/gemm), так и при выборе инструкций C++, неподдерживаемые комбинации отклоняются до CUDA codegen с понятным сообщением.
  • Приложен 1 негативный кейс и 3 позитивных регрессионных теста; поведение поддерживаемых комбинаций и не-Ampere целей не изменено. Данный коммит вошёл 12.10 в 01:21 и является самым свежим на момент закрытия окна.

1.3 Основной репозиторий: шаг цикла For, индексы выходов JIT, popcount, битовые редукции и тестовая инфраструктура — пять коммитов (10.10 ~ 11.10)

Дата: 2026-10-10, 2026-10-11　Источник: Шаг цикла For (#3427) / Индексы выходов JIT (#3318) / popcount (#3300) / Битовые редукции (#3332) / Тестовая инфраструктура (#3313)

  • For шаг (#3427, влито 10-10 12:54): Анализ конфликтов переноса цикла ранее всегда рассматривал шаг как 1 (что противоречило комментарию «по умолчанию 1, если не указано»), из-за чего определение допустимых пар итераций искажалось при неединичных / знаковых шагах; теперь диапазон пар итераций сужается по явному шагу, кодогенерация CUDA и HIP сохраняет шаг и делегирует генерацию CodeGenC, учитывая лексическую область видимости переменных развёрнутого цикла.
  • Индекс вывода JIT (#3318, 10-10 12:02): out_idx=[-1] при многократном использовании между ядрами с разным числом параметров загрязнялся нормализацией (ядро с двумя параметрами нормализовало [-1] в [1], а ядро с четырьмя параметрами затем ошибочно занимало входной слот); теперь список вызывающей стороны копируется до нормализации, скалярные индексы, равные числу параметров, отклоняются с указанием допустимого диапазона.
  • popcount (#3300, 10-10 12:02): Дополнено понижение до CUDA для знаковых и узких 8 / 16-битных целых — сначала преобразование к беззнаковому с исходной шириной, затем расширение (int8(-1) считает 8 бит, а не 32), для 64-битных используется __popcll, охвачены регрессии для 8 типов dtype; исправляет #2984, на H100 (CUDA 13.0) все 16 тестов проходят.
  • Битовые редукции (#3332, 10-11 14:13): reduce_bitand / bitor / bitxor ранее проверяли только целевой буфер и пропускали вещественные источники ([1.0, 2.0, 4.5, 8.9] молча усекалось до 1 2 4 8 = 15 без предупреждения); теперь источник и цель единообразно отклоняются по правилам для целых / булевых (refs #3301).
  • Инфраструктура тестирования (#3313, 10-11 18:25): Добавлены общие помощники проверки IR (сбор узлов, точный подсчёт вызовов операторов, сбор внешних вызовов по символам), тесты issue и transform переведены с локального обхода кода на помощники; в тест lower_ldgstg добавлены структурные утверждения, выбранные тесты transform зафиксированы на цели sm_90 с пропуском по доступности.

1.4 Новые PR в основном репозитории: два по Host IR JIT и параллельная компиляция, частично-волновые редукции и ещё девять (10-10 ~ 10-11)

Дата: 2026-10-10, 2026-10-11　Источники: Унификация Host IR (#3473)／ Прямое подключение Host IR JIT (#3481)／ Параллельная компиляция JIT (#3476)／ Частично-волновые редукции (#3478)

  • Линия Host IR (#3473, #3481): Сначала унифицированы два пути исполнения CUDA и CuTeDSL в Host IR (#3473), затем попытка прямого подключения Host IR JIT с нативным кэшем (#3481, экспериментально, направление MIR) — перестройка хост-части JIT становится новой основной линией основного репозитория.
  • Пропускная способность компиляции (#3476): autotuner параллельно компилирует независимые конфигурации JIT, сокращая настенное время настройки при большом пространстве конфигураций.
  • Новые PR категории исправлений: частично-волновые скалярные редукции (#3478), группировка приведения типов хост-выражений (#3477), развёртка эпилога конвейера с известным только в рантайме числом итераций (#3472), опциональность целевой платформы в примере для Ascend (#3474); два WIP (#3482 атомарное накопление разреженных обратных градиентов, #3483 устаревшие эксперты маршрутизации MoE) открыты поздно вечером 10-11.
  • Очередь: в основном репозитории открыто 170 PR (в прошлом выпуске 177, снижение на 7).

1.5 TileFoundry: разреженное декодирование сквозь TIR; исправление области видимости mesh (10-10 ~ 10-12)

Дата: 2026-10-10, 2026-10-12　Источники: Разреженное декодирование сквозь TIR (#223)／ Область видимости mesh (#220)／ Атрибуты парсера (#221)

  • #223 (объединён 10-12 00:52, 84 файла, +4424/-1543): продолжение работы над оставшимися проблемами декодирования DSA из #218 — исправление потерянного объёма циклических вычислений, завышенного учёта поиска (lookup) и ошибок поэтапного обновления; реализация индексного асинхронного сбора, понижение Bitcast и Where; ограничения размещения изменены на единый аксессор (возвращающий Storage), захваченные обновления записываются напрямую в tile (16B разделяемой памяти), значения, переносимые при инициализации параметров, получают отдельное хранилище и предварительное копирование для сохранения входных данных; 16 групп FixtureCase охватывают вызовы CLI и проверки вывода; синхронно обновлён сгенерированный обучающий отчёт.

3.1 TileOPs: 21 коммит включён — единоразовый рефакторинг базового класса Op утверждён окончательно (уровень -5200 строк) (10-10 ~ 10-11)

3.2 TileOPs: пакет производительности MLA / KDA / NSA — декодирование на SM89 ускоряется до примерно 4,6× (10-10 ~ 10-11)

Дата: 2026-10-10, 2026-10-11　Источники: декодирование MLA SM89 (#2511) / расширение разбиения при тюнинге MLA (#2524) / отсев кандидатов MLA (#2525) / дескрипторы WGMMA (#2523)

  • Декодирование MLA (#2511, влито 10-10 22:31): на SM89 выбор разбиения KV 2/4/8/16 в зависимости от батча и числа головных блоков (цель 128 CTA, верхний предел 16), переиспользование существующего ядра сканирования и FP32-слияния разбиений — для одиночного запроса bf16 4k задержка по умолчанию с 0,158 до 0,034 мс (примерно 4,6×), 32k с 1,170 до 0,162 мс (примерно 7,2×).
  • Плоскость тюнинга MLA (#2524 / #2525): кандидаты разбиения при тюнинге расширены до 1/2/4/8/16 (кандидатов с 24 до 40, на практике есть строка с 2,00x относительно FlashInfer); кандидаты, у которых запросный тайл со временным KV превышает бюджет общей памяти, отсеиваются (при D=512 из 40 остаётся 20), холодный тюнинг с первой настройкой сокращён с 348,6 с до 151,6 с, неудачные кандидаты обнулены.
  • Дескрипторы WGMMA (#2523 / #2504): дескрипторы ядер декодирования MLA и DSA-«качелей» теперь конструируются широковещательной рассылкой из lane 0 (ожидание R2UR у HGMMA обнулено, без переполнения) — 26 строк бенчмарка MLA быстрее на 0,7% до 4,1%; попутно исправлено зависание частичного RoPE-декодирования bs1 на SM90 при нехватке последнего блока разбиения.
  • Префилл KDA (#2510): на SM89 для одной последовательности 4096 до 64k token, до 8 голов значений сценарий разбивается по тайлам значений из 16 столбцов — задержки 4k / 32k / 64k снижены соответственно на 22,9% / 19,8% / 18,5%.
  • NSA top-k (#2514): каждый сжатый блок отдаётся одному CTA (запросные головы заполняют 64-строчный тайл WGMMA), внутрирегистровая битовая сортирующая сеть сортирует целую строку (заменяя чётно-нечётный транспозиционный сортировщик), важность разрешается в пользу меньшего номера блока.
  • Постраничный GQA (#2512): ядро SM90 с warp-специализацией и TMA (один производительный warp TMA + две потребительские warpgroup с перекрытием QK и PV), постоянный CTA по одному на SM; устаревшие строки V в тайле, отрезанном на конце кэша, сначала обнуляются, затем читаются; при упакованной раскладке в среднем при наличии хотя бы одного 128-строчного тайла на запрос приоритет отдаётся диспетчеризации, на H200 время перехваченных четырёх строк снижается до 0,44–0,88 от исходного.

5.2 Завершение рефакторинга и затишье перед релизом: окно выпуска на подходе

  • Наложение трёх групп сигналов: рефакторинг базового класса Op в TileOPs позиционируется как «предрелизное» закрытие (единовременное чистое сокращение примерно на 1865 строк); сайт документации на следующий день выпускает «Руководство по базовому классу Op»; теги основного репозитория после v0.1.15 от 09-30 остаются без изменений, а ночной конвейер продолжает обновлять базу оценки с нулевым числом сбоев.
  • Работы по инженерному качеству (именование / семантика кэширования / ограничители ревью) в этом окне продолжают интенсивно выполняться — путь «сначала зафиксировать базовую линию, затем выпустить официальную версию» очевиден, статическая подготовка к следующему релизу уже готова.

5.3 Расширение аппаратного покрытия на той же неделе: включение SM121, пакет политик производительности SM89

  • В одном и том же окне: SM121 (GB10 / DGX Spark) включает блочно-масштабируемые MMA (#3430); SM89 (серия RTX 40 / уровень L40) получает пакет политик производительности декодирования (#2510 / #2511 / #2506); SM90 (H100 / H200) продолжает детализироваться (#2512 / #2497 / #2503).
  • Аппаратный акцент смещается от «оптимизации под единственный Hopper» к «одновременной доработке нескольких поколений, проникновению в потребительский сегмент»; отечественные бэкенды идут в том же ритме: Ascend — два коммита миграции разреженного MLA плюс четыре подряд исправления кэша, Hygon — обновление регистрового конвейера.
