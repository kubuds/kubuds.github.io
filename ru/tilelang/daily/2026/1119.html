Главное за день: TileFoundry в тот же день внедрил цель Metal и автоматическое дифференцирование

За один день 11-18 TileFoundry слил два изменения платформенного уровня. #354 добавляет цель Apple Metal, #355 добавляет автоматическое дифференцирование. Первое расширяет процесс компиляции до Apple GPU, второе позволяет фреймворку самостоятельно генерировать обратное распространение. Ни одно из двух не производит исполняемых ядер: Metal доведён только до TIR, автоматическое дифференцирование только генерирует модули HIR.

На стороне Metal добавлен metal.Target("apple.m2_pro.gpu"). Топология — от threadgroup к thread. Аппаратные параметры записаны в TOML и снабжены публичными источниками. Таблица возможностей напрямую использует имена 27 нативных функций MSL.

Под T.metal всего девять инструкционных операторов. Матричные — ldmatrix, stmatrix, matmul и mma. Свёртки и перестановки — reduce, prefix, shuffle, shuffle_fill и ballot. Один вызов покрывает G групп SIMD, quad group выражается теми же операторами на mesh ширины 4.

Один файл на каждый оператор. Правила typeinfer, access и evaluator записываются в одном файле; для раскладки используются именованные константы. MSL не задаёт lane-отображение матриц — автор после измерений на M2 Pro внёс его в спецификацию. HIR сопоставляется через hir_matches. MatMul на fragment-операндах опускается до matmul, Reshard между памятью и fragment — до ldmatrix и stmatrix. Этот PR заменяет более ранний #294, который не удалось перебазировать из-за реорганизации целевого интерфейса.

На стороне автоматического дифференцирования добавлен differentiate(module, wrt, recompute). Он возвращает два модуля: <Name>Forward и <Name>Backward. Прямой проход возвращает результат и кортеж saved. Обратный принимает градиент результата и saved и возвращает градиенты по одному на каждый элемент wrt.

Правила обратного прохода записываются для каждого оператора в его собственном файле и регистрируются через новый interfaces/autodiff. Покрытие охватывает все классы операторов встроенной модели Qwen, а также ReLU и Log. Поддерживаются вызовы sibling и sub-slot, кортежные аргументы, MeshRegion и циклы со статически вычислимым числом итераций.

Циклы накапливают только значения, меняющиеся на каждой итерации. Величины, используемые только индукционной переменной, захватами и константами, пересчитываются в обратном проходе, поэтому цикл по слоям не копирует веса. Раскладка градиентов следует DTensor.

Источник: https://github.com/tile-ai/TileFoundry/pull/354.

Главное за сегодня: 23 слияния TileOPs за день, цепочка квантования FP8 достроена, два долга по производительности закрыты в тот же день

18.11 в основную ветку TileOPs попало 23 слияния — с 10:17 до 21:50 по пекинскому времени. Главная линия — FP8: групповое по-токенное квантование, потоковый GEMM для коротких строк, переписанный paged decode и примитивизация WGMMA — четыре коммита в один день вошли в основную ветку.

FP8QuantPerTokenGroupFwdOp вводит масштабы UE8M0 (#3026). Выход побитово совпадает с act_quant(x, 128, "ue8m0") из DeepSeek-V4-Flash, масштабы хранятся в float8_e8m0fnu. Добавлено псевдоквантование inplace, так что kv[..., :448] со страйдом в модели не нужно сначала копировать.

Путь UE8M0 выполняет приведение и масштабирование через bfloat16x2 и убирает clamp перед насыщающим преобразованием в e4m3. Эталонная реализация — per_token_group_fp8_quant из vLLM; численные значения DeepSeek и TileKernels приведены в комментариях.

Ядро paged GQA decode для FP8 полностью переписано (#2997). Каждый CTA получает упакованную строку одного запроса, один KV-заголовок и сегмент ключей. Каждый FP8 key/value tile разворачивается по ширине только один раз, копированием страниц занимается TMA-warp. Ограничение задаёт разделяемая память: на H200 tile из 8 строк обслуживает 44 287 запросов, tile из 64 строк — 33 023.

Короткие строки FP8 переведены на потоковую обработку блоками по 64 строки (#3010). Один производственный warpgroup через глубокое TMA-кольцо переносит b, другой warpgroup-потребитель добавляет частичные суммы FP8 WGMMA для каждого шага K шириной 128 в float32.

Раньше основная ветка дополняла 8 или 16 строк до tile из 64 или 128 строк. В результате 160 tile попадали на 132 CTA или включался split-K. По измерениям достигалось лишь от 31% до 52% пиковой пропускной способности DRAM.

В той же партии есть два завершающих коммита. #3030 переводит четыре k32 WGMMA на каждом шаге FP8-потока на примитивы TileLang. Вместе с этим удаляется dense_wgmma_helper.h, а также шаблонный параметр TrailingFence, использовавшийся только этим ядром. #3029 исправляет учёт разделяемой памяти: буфер масштабов ранее суммировался в исходных байтах без учёта выравнивания на 1024 байта. Из-за этого форма m=16, n=163840, k=3584 падала при запуске.

Два долга по производительности закрыты в тот же день. #3023 переписывает TopKSelect: вызовы, где число строк меньше удвоенного числа SM, идут через регистровое ядро. Оно за одно глобальное чтение читает строку, порог определяется по гистограмме из 4096 корзин; длинные строки идут через radix, загружая четыре ключа по 16 байт за раз. Три строки decode из отставания от vLLM примерно в 2 раза перешли к опережению в 1,22–1,34 раза, что закрывает #3016.

#3022 заставляет копировать каждую строку MLA cache векторами по 16 байт, максимум в 1024 потока. В основной ветке копирование отдавалось выводу раскладки, и латент шириной 448 превращался в 7 скалярных обращений по 2 байта на поток. Это и была непосредственная причина отставания decode DeepSeek-V4-Flash от vLLM.

Источник: https://github.com/tile-ai/TileOPs/pull/3026.

1. Прогресс ключевых проектов

1.1 В главном репозитории бэкенд CPU получает последовательное понижение для двух логических свёрток: any_of и all_of

#4389 Добавление специализированного понижения tl.any_of и tl.all_of для CPU-бэкенда. Ранее эти два оператора не могли проходить через обычный конвейер CPU. Реализация добавляет проход LowerCPUAnyAll, вставляемый перед LowerTileOp. Понижение выполняется как последовательное сканирование в порядке строка-за-строкой с коротким замыканием: any_of останавливается при первом истинном значении, all_of — при первом ложном.

Пустая редукция берёт стандартные единичные элементы: any_of — false, all_of — true. Числовые элементы приводятся к истине по ненулевому значению, NaN для чисел с плавающей запятой и bfloat16 считается истиной. Редукции в условии while повторно инициализируются и пересканируются при каждой проверке условия, семантика совпадает с прежней. Этот проход также доступен через интерфейс Python-преобразований для CPU.

Источник: https://github.com/tile-ai/tilelang/pull/4389.

1.2 Регрессионный тест topk задаёт лимит ресурсов для Z3, устраняя таймаут в CUDA CI

#4407 устраняет таймаут test_topk_candidate_overflow в CUDA CI. Причина — дорогостоящие запросы к Z3 на этапе упрощения. Исправление устанавливает arith.z3_rlimit в 100 при загрузке ядра в этом тесте, сохраняя остальные прежние опции JIT. Изменение затрагивает только этот регрессионный тест.

Автор локально сгенерировал TIR для четырёх специализаций topk и подтвердил, что после установки лимита Simplify завершается. Автор также отмечает: на локальной машине нет генерации кода CUDA и нет доступного удалённого GPU. Полное время компиляции и корректность на GPU не проверялись.

Источник: https://github.com/tile-ai/tilelang/pull/4407.

1.3 Тест автотюнинга Ascend удаляет кросс-NPU проверку, чтобы не загрязнять последующие случаи

#4401 удаляет ветку other_npu в тесте set_autotune_inputs. Эта ветка для определения поддержки выравнивания входов между устройствами во время выполнения выполняла кросс-NPU копирование. На некоторых комбинациях Torch-NPU и CANN эта копия прерывает контекст NPU.

Перехват RuntimeError и пропуск теста не восстанавливает контекст. Последующие несвязанные тесты в том же процессе pytest затем падают, из-за чего проявление сбоя зависит от порядка выполнения. После удаления сохраняются три вида покрытия: входы, захваченные на текущем NPU, остаются на текущем NPU; входы, захваченные на CPU, переносятся на эталонное устройство; переданные тензоры должны соответствовать эталонному устройству.

Источник: https://github.com/tile-ai/tilelang/pull/4401.

1.4 Повторная подача RFC бэкенда CUDA Tile IR: конвертируется только то, что выразимо в Tile IR

#4402 и #4403 подали RFC бэкенда CUDA Tile IR, на английском и китайском, размещённые в docs/compiler_internals/tileir/. Цель — генерировать CUDA Tile IR из программ TileLang и передавать его tileiras для компиляции и планирования. Раскладка, конвейеризация, warp-специализация и выбор инструкций определяются tileiras и оптимизируются под поколение оборудования.

Бэкенд конвертирует только семантику, корректно выразимую в Tile IR. Невыразимая семантика немедленно приводит к ошибке компиляции и отклонению программы; полная совместимость с существующим бэкендом CUDA не преследуется. Заявленная автором выгода: без изменения ядер и без ручного написания архитектурно-зависимого планирования можно получить хорошую производительность только за счёт автотюнинга.

Эта версия — переработка ранней #3247. Ревью указало, что старая реализация страдала избытком try-catch, понижала каждый встреченный случай по отдельности, создавала отдельный IR и писала проходы примерно на 18,5 тыс. строк Python. Новый RFC переработан с учётом этих четырёх пунктов; PR пока является черновиком, обсуждение ведётся в #4403.

Источник: https://github.com/tile-ai/tilelang/issues/4403.

2. Адаптация под множество бэкендов (Ascend / Hygon / Moore Threads / MetaX / Sunrise)

2.1 Ветка mlir-dialect MLIR Ascend за один день принимает tl.shl, tl.shr, tl.cast

Слияния в репозитории MLIR Ascend происходят в ветке mlir-dialect, а не в main. Голова этой ветки 11-18 продвинулась с 06:23 до 08:47 (UTC), за один день принято три оператора TLIR.

#211 добавляет tl.shl, понижаемый до hivm.hir.vshl, с переиспользованием существующего помощника NpuirShl. #212 добавляет tl.shr, поддерживающий только i16, i32, i64, где round — булев атрибут со значением true по умолчанию. В этом коммите честно указано одно известное несоответствие: rhs моделируется как тензорный операнд, тогда как vshr в HIVM имеет ограничение ScalarOnlyHWTrait<1>. Корневая причина в том, что конструкторы NpuirShr и npuir_shr не принимают скаляры; это оставлено на будущее.

#214 добавляет tl.cast, round_mode ограничен шестью значениями: round, rint, floor, ceil, trunc, odd. Этот коммит также меняет одну настройку уровня диалекта: в TL_Dialect добавлен usePropertiesForAttributes = 0. Причина в том, что tl.cast — первый оператор этого диалекта с неоперандными атрибутами, и генерация Properties по умолчанию через ODS порождает повреждённый CastOp. Все три коммита снабжены тестами FileCheck, тесты взяты из реально захваченного вывода.

Источники: https://github.com/tile-ai/tilelang-mlir-ascend/pull/214.

2.2 MLIR Ascend на рассмотрении: tl.vrelu, tl.abs, tl.or, tl.xor и ядро RoPE

На рассмотрении находятся ещё четыре оператора TLIR. tl.vrelu — в #261, tl.abs — в #238, последний понижается до hivm.hir.vabs. tl.or — в #225, tl.xor — в #228. Все четыре продвигаются по одному и тому же процессу: «оператор диалекта + понижение TIR + преобразование HIVM».

#263 идёт другим путём — напрямую добавляет ядро вращательного позиционного кодирования, вместо добавления отдельного оператора. Кроме того, #260 заменяет навык ascend-mfu в harness на ascend-roofline. Новый навык использует модель Cube/Vector для выдачи пиковой производительности, счётчиков, roofline, MFU, BWU и аппаратных ориентиров. Его FMA-зонд на этом устройстве и этой сборке калибруется до 26,3 TFLOPS, что составляет 88% от номинальных 30 TFLOPS.

Источники: https://github.com/tile-ai/tilelang-mlir-ascend/pull/263.

2.3 Hygon: один коммит объединяет двенадцать исправлений, охватывающих intrinsic, точность и целочисленные векторы

В окне мониторинга репозитория Hygon был только один слитый коммит (#27), но его содержимое охватывает двенадцать направлений. На стороне intrinsic исправлены неоднозначность вызова hexp, диспетчеризация cos и sin. На стороне точности исправлены сбой усечения fp64 и несовпадение размеров __builtin_bit_cast. На стороне генерации векторного кода исправлено понижение shuffle и включено сокращение shuffle целыми волнами.

Добавленные возможности включают: поддержку операций rng на базе hipRAND, перебазирование загрузки буфера, intrinsic cache_warmup. Есть также несколько завершающих правок: широковещательная рассылка 8-битных целочисленных векторов, разворачивание пролога/эпилога конвейера для числа итераций времени выполнения, защита маски shuffle, исправление порядка генерации кода FP4. На стороне CI закреплён ABI NumPy. В подписи коммита фигурируют два инженера Hygon.

3. Экосистема и стороны внедрения (целевой список TileOPs / TileKernels / topa / сайт документации)

3.1 Вывод двух операторов mHC из публичного API объявлен нарушением, три оператора HyperConnection идут на смену и находятся на рассмотрении

#3021 Удалить MHCPreFwdOp и MHCPostFwdOp, вместе с ядром, записями в manifest, workload, бенчмарками и тестами, согласно плану #2796. DeepSeek-V4-Flash и GLM-5.3-Flash переведены на три оператора HyperConnection: pre, post, head. Примитив manifest mhc.expansion также удалён, поскольку его использовали только удалённые операторы.

Данный коммит зарегистрирован в scripts/ci/api_compat_allow.txt как прошедшее ревью нарушение публичного API. Это первый случай в библиотеке операторов, когда удаление интерфейсов управляется через манифест; удалённые интерфейсы больше не восстанавливаются.

Три новых предложения-преемника уже на рассмотрении: #3032 добавляет pre, #3035 добавляет post, #3039 добавляет head. Кроме того, #3036 добавляет в FusedTopKFwdOp sqrt-softplus и хеш-маршрутизацию для DeepSeek-V4-Flash. #3038 добавляет в DSADenseFwdOp attention sink и выбор только по индексам. Этот набор изменений указывает на одно: перестройку интерфейсов моделирования последовательностей и внимания в соответствии с реальной структурой DeepSeek-V4.

Источник: https://github.com/tile-ai/TileOPs/pull/3021.

3.2 Семь issue с целями по производительности оформляют «отставание от самой быстрой библиотеки» как приёмочный список

В окне мониторинга открыто семь новых issue с целями по производительности, каждый с указанием оборудования, формы и цели. #3018 отслеживает отставание GQA с переменной длиной на визуальной строке с размерностью головы 72 от FlashAttention 3. #3019 отслеживает отставание записи в MLA cache от vLLM. Соответствующие исправления для этих двух — #3023 и #3022, причём #3022 в тот же день закрыл #3019.

#3037 приводит полную таблицу сравнения для DSADense: H200 работает на 1500 MHz, пиковая производительность bf16 для плотных вычислений около 811 TFLOPS. Строки CSA достигают около 58% пика, причина в том, что softmax для каждой пары и сбор ключей для следующей пары зажаты между двумя матричными умножениями. Строка 4k в HCA платит цену за 64 блока ключей: 160 ключей считаются как 192.

#3031 отслеживает отставание HyperConnection pre на decode и средних последовательностях от TileKernels. #3034 отслеживает строку decode в GatedPoolCompress с целью достичь SOTA на этой форме.

Источник: https://github.com/tile-ai/TileOPs/issues/3037.

3.3 Предложение о сравнительном тайминге с TileKernels: образ для прогонов по-прежнему закреплён на tilelang 0.1.12

#3028 предлагает добавить TileKernels от DeepSeek в эталонное сравнение, чтобы строки DeepSeek-V4 напрямую замерялись собственными ядрами DeepSeek. Препятствие в версии: TileKernels требует tilelang не ниже 0.1.15, а образ для прогонов закреплён на 0.1.12. Сейчас ни один бенчмарк не может его импортировать.

Предложение приводит три соответствия. FP4QuantPerGroupFwdOp и FP8QuantPerTokenGroupFwdOp соответствуют per_token_cast. SiLUAndMulFwdOp соответствует quant.swiglu_forward. Условие приёмки — эти бенчмарки действительно замеряют TileKernels в CI, а ночные записи фиксируют сравнение. Это объясняет, почему в описаниях двух предложений по квантизации того же дня значения TileKernels приводятся только в комментариях.

Источник: https://github.com/tile-ai/TileOPs/issues/3028.

3.4 topa: одна команда выполняет полный цикл ревью, GPU монополизируется только на время тайминга

topa влил #41 и #43, превратив ревью в повторяемые раунды. #41 заставляет каждое изменение PR запускать новую попытку: новый head проходит полное ревью, остальные — только повторную проверку. Результаты публикуются только если PR не изменился и всё ещё открыт. На стороне GPU добавлен topa-bench с блокировкой по карте, который монополизирует одну карту только на время тайминга, а в остальное время уступает её другим раундам.

#43 сжимает трёхшаговый процесс в одну команду topa review <PR>. Замечания ревью фиксируются как три односложных пункта: проблема, воспроизведение, исправление. Каталог ревью одного и того же PR сохраняет worktree и posted.json; при втором ревью данные забираются только если локальная версия отстаёт от GitHub. Ожидание без изменений между раундами ревью расширено с 60 минут до 10 часов.

Помимо этих двух коммитов, topa открыл в окне мониторинга 10 новых issue (#35–#46). Все они — исполнимые рабочие задачи с заголовками вида fix(...), направление сосредоточено на roofline-ценообразовании. Включая расчёт makespan по волнам CTA, ценообразование scatter по числу записываемых строк, учёт резидентных CTA в сетке. Это следующая партия задач, которую конвейер ставит сам себе.

Источник: https://github.com/tile-ai/topa/pull/41.

Слияния в MLIR Ascend попадают в ветку mlir-dialect; main с 11-04 не менялся, в тексте это указано по ветке, и она не называется основной.

На завершающем этапе окна сбор данных столкнулся с ограничением частоты неаутентифицированного GitHub API. Отдельные сведения о ветках были перепроверены через Atom-подписки и git ls-remote; на выводы это не повлияло. Обход четырёх источников RISC-V дал пустой результат, что трактуется как отсутствие изменений и не считается сбоем сбора.
