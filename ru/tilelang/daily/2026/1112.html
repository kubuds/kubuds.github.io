Главное за сегодня

В этом окне в организации было всего 6 слияний, что на треть меньше, чем 9 в предыдущем периоде, но структура важнее цифр: 3 из 6 — в основном репозитории, и все они относятся к Ascend, ни одного для CUDA или CPU. Самое крупное — #3516 (20 файлов, +1549/−182), которое делает tvm_ffi бэкендом выполнения по умолчанию для цели pto — ранее target="pto" использовал Cython-запускатель, теперь execution_backend="auto" напрямую разрешается в tvm_ffi, общий host codegen генерирует MakePackedAPI и C host, а среда выполнения Ascend запускает aibin, скомпилированный PTODSL, через aclrtLaunchKernelWithHostArgs, тем же путём, что и ядра AscendC. В комплекте — модульный колбэк инструментальной цепочки: весь модуль PTODSL компилируется за один проход на этапе device build (ptodsl → ptoas → bisheng fatobj-link → извлечение .aicore_binary), результат кэшируется по ключу из параметров ptoas, версии ptoas и идентичности CANN. Старый путь сохранён как execution_backend="pto", оба варианта выдают побитово идентичный результат.

Второе — #3776, ужесточение на стороне решателя. AutoSchedule изначально запускал бисекцию с фиксированной нижней границей периода; теперь берётся максимум из трёх необходимых условий: граница одиночной задачи использует максимум интервалов запуска задач; граница ресурсной группы для попарно конфликтующих задач сортирует задачи по остаточным значениям и выводит из соседних разностей и разностей первого и последнего, что период не меньше суммы интервалов запуска; граница самозависимости из S_u - S_u >= wait - d*P даёт период не меньше ceil(wait/d), а зависимые от версии расстояния пересчитываются через num_stages. Дополнительное зондирование нижней границы не вводилось, модель планирования не менялась. Эмпирическая проверка на недельной сборке Ascend 950PR, CANN 9.3.0: с отключённым кэшем компиляции, чередование одного прогрева и трёх замеров, все примеры Ascend компилируются, результаты планирования не меняются, суммарное время этапа решения Z3 снижается на 10.04%.

Третье — вне основного репозитория. Распределённый набор из трёх компонентов для Hygon #36 (6 файлов, +2022/−0) влит в 16:20 в ветку distributed, а не в main; содержимое — три оператора слияния вычислений и коммуникаций: Block-Push версия GEMM + AllReduce, Block-Push версия GEMM + ReduceScatter и Block-Pull версия AllGather + GEMM, данные о производительности и описание реализации — в README. В тот же день #37 открыл ds_read_vector Alt2 для HCU и вывод раскладки LDS. Эта линия от примера push-wave reduce-scatter от 10-29 дошла до списка операторов слияния — это первый системный подход к распределённым вычислениям в репозитории Hygon.

Четвёртое — всплеск на стороне качества: из 35 новых issue в окне 30 приходятся на основной репозиторий, из них 26 напрямую касаются Ascend. Два аккаунта с послеобеденного времени до глубокой ночи сообщили каждый более десяти штук, характер однотипный — не «выполнилось неправильно», а «должно было выдать ошибку, но молча прошло»: T.Kernel принимает нулевое или отрицательное число блоков, T.alloc_l1 принимает выделение 2 GiB, T.Persistent принимает отрицательные wave и stage, T.unroll принимает −1 и выдаёт #pragma unroll -1, отрицательные размерности тензора просто роняют компилятор. 1. Основные достижения проекта

1.1 Ascend: бэкенд выполнения по умолчанию для цели PTO переключён на tvm_ffi, весь модуль компилируется на этапе device build и кэшируется (#3516)

#3516 (20 файлов, +1549/−182) — самое крупное изменение этого выпуска. Суть — перевод цели pto с «специализированного Cython-запускателя» на «тот же host-путь, что и AscendC»: при target="pto" с execution_backend="auto" разрешается в tvm_ffi, общий host codegen отвечает за MakePackedAPI и сборку C host, а модуль среды выполнения Ascend запускает aibin, скомпилированный PTODSL, через aclrtLaunchKernelWithHostArgs.

На стороне сборки устройства добавлен модульный колбэк инструментальной цепочки, который компилирует весь модуль PTODSL за один раз: вывод фронтенда ptodsl, понижение ptoas, компоновку fatobj в bisheng, а затем извлечение .aicore_binary; продукты кэшируются по aibin. Ключ кэша учитывает параметры ptoas, версию ptoas и идентичность CANN — это критически важно, поскольку ранее, когда такие ключи упускали версию инструментальной цепочки, при обновлении CANN происходило попадание в старые артефакты.

Плоскость валидации охвачена широко, добавлены четыре группы тестов: auto, разрешающийся в tvm_ffi; выделение выхода вызываемой стороной; динамические формы и динамические выходы; многодевайсные ядра; динамическая разделяемая память; смешанный GEMM cube/vector; source accessor; экспортируемая библиотека; циклический запуск на стороне host и интервалы профилирования на стороне host; кроме того, тесты эквивалентности побитово сравнивают результаты tvm_ffi и старого pto на трёх типах ядер: vecadd, многядерных и с динамической разделяемой памятью; две группы тестов кэша покрывают соответственно кэш бинарников и кэш ядер, включая пропуск инструментальной цепочки при попадании в кэш, выброс ошибки при повреждённой записи и попадание в свежем процессе. Старый путь по плану сохранён и будет выведен из эксплуатации после подтверждения покрытия.

Источники: https://github.com/tile-ai/tilelang/pull/3516

1.2 Ascend: AutoSchedule ужесточает нижнюю границу периода тремя необходимыми условиями, время решения Z3 снижается на 10.04% (#3776)

#3776 (1 файл, +20/−1) меняет только начальное значение, не меняя алгоритм: прежняя бисекция стартовала с фиксированной нижней границы, теперь сначала вычисляются три необходимых условия и берётся максимум. Граница отдельной задачи сохраняет жёсткую нижнюю границу интервалов запуска каждой задачи; граница ресурсной клики для клик с попарными конфликтами ресурсов сортирует остаточные значения задач по возрастанию и из суммы ограничения соседних разностей и ограничения разности первого и последнего выводит, что период не меньше суммы интервалов запуска внутри клики, причём сама клика жадным образом перечисляется с каждым заданием в качестве затравки; граница самозависимости выводится обратным решением из S_u - S_u >= wait - d*P, а версионно-зависимое расстояние ограничивается сверху величиной num_stages.

Эмпирическая среда описана очень конкретно: Huawei Ascend 950PR, недельная версия CANN 9.3.0 20261009.01, кэш компиляции отключён, для каждой конфигурации один прогрев и три замера поочерёдно. Результатов два: все примеры Ascend компилируются успешно, и результаты планирования совпадают с прежними (что показывает, что только ужесточена нижняя граница, а решение не изменилось), а суммарное время этапа решения Z3 снижается на 10.04%. Верхняя и нижняя границы бисекции и обработка состояния решения не изменены, дополнительный процесс зондирования нижней границы также не введён.

Ценность такого изменения для upstream не в точечной производительности, а в том, что при росте масштаба оператора время решения планировщика растёт, и растрата на стартовую точку бисекции линейно усиливается — запись необходимых условий в начальное значение равносильна экономии бессмысленного интервала при каждом решении.

Источники: https://github.com/tile-ai/tilelang/pull/3776

1.3 Ascend: целочисленные атомарные операции адаптированы к signless-носителю, 12 тестовых случаев PTO покрывают 32 и 64 бита (#3794)

#3794 (4 файла, +52/−6) исправляет последствия #3512. Тот коммит изменил знаковые целочисленные типы с signless i32/i64 на si32/si64, а атомарный интерфейс PTO требует signless-носителя, из-за чего целочисленные атомарные операции add/min/max в ядрах SIMT просто не компилировались.

Исправление — локальная адаптация на границе генерируемого вызова PTODSL: указатель и операнды переинтерпретируются как signless той же ширины, адресное пространство указателя сохраняется, возвращаемое значение восстанавливается в логический тип; min/max сохраняют исходную семантику знакового или беззнакового сравнения. Так введённая в #3512 система логических типов не опровергается, адаптация сосредоточена только на уровне атомарных операций.

Регрессионные случаи находятся в testing/ascend/language/simtvf в test_simtvf_atomics.py и покрывают 32- и 64-битные add/min/max, отрицательные операнды, возврат старого значения, значения свыше 32 бит, а также беззнаковые начальные значения со старшим битом 1; добавленные 12 случаев PTO полностью проходят на Ascend. В том же пакете слит #3792, исправляющий другую сторону той же проблемы: T.atomic_add/max/min не компилировались на PTO из-за знаковых входов.

Источники: https://github.com/tile-ai/tilelang/pull/3794

1.5 TIRx: два патча в рассмотрении — ceildiv и split div/mod при отрицательном scale, тот же корень, что и ошибка вложенного floor division (#93, #94)

На стороне tile-ai/tvm в окне находятся два патча в рассмотрении: #94 ([Fix][TIRx] Make ceildiv exact for signed divisors) и #93 ([Arith] Guard negative scales in canonical split div/mod). Оба исправляют два конца одной и той же проблемы — после того как знак попадает в целочисленное деление и взятие остатка, предпосылка канонического переписывания перестаёт выполняться, поэтому «точность» и «безопасность» приходится обрабатывать раздельно: ceildiv требует, чтобы результат оставался точным при знаковом делителе, а split div/mod должен отклонять канонизацию при отрицательном scale.

Это указывает на то же место, что и открытый в тот же день в основном репозитории #3937 ([BUG] вложенное floor division при отрицательном множителе даёт неверное целое): как только отрицательный коэффициент попадает в цепочку переписывания арифметического упрощения, граничные условия легко упускаются. Разница в том, что #3937 — это воспроизведение со стороны пользователя, а #93/#94 — упреждающее укрепление со стороны компилятора.

На стороне регистров изменены сразу два места — максимум строки берётся как упакованная пара 16-битных значений, и каждый элемент float16 сдвигается одним FFMA относительно масштабированного максимума тайла; bfloat16 и float32 по-прежнему сначала вычитают максимум, поскольку их максимум, умноженный на log2(e), выходит за пределы диапазона fp32. Корневая причина указана в описании: бенчмарк гоняет H200 на 1500 MHz, регистровая схема выполняет на 17% больше инструкций, чем quack, и ограничена скоростью выпуска.

#2897 (GEMMFwdOp, помечен below bar) — обратное направление, результат не достигнут. Он должен исправить решение селектора: после более чем 64 шагов K заменять более широкий тайл coop2 только тогда, когда ping-pong тайл шириной 176 или 192 покрывает больше «выхода на байт операнда», поэтому ds-v3-prefill-o-proj переключается с ping-pong 128x176/144 на coop2 128x256/240. Проблема в том, что эта строка работает под потолком мощности H200 в 700 W, и время следует за энергопотреблением на вызов: тайл шириной 176 имеет на 2.7% меньше циклов, чем DeepGEMM, но затаскивает в SM на 21% больше байтов операндов, а значит работает на более низкой частоте. Эта запись честно помечена как не достигшая цели, и её ценность в том, что она количественно фиксирует: «под потолком мощности нельзя использовать число циклов как критерий».

4.1 Систематический аудит фронтенда Ascend: 30 issue за день, 26 напрямую об Ascend (11-11)

В окне на уровне организации открыто 35 новых issue, из них 30 в основном репозитории, 3 в TileFoundry, 2 в tilelang-ascend. Из этих 30 в основном репозитории у 26 в заголовке напрямую стоит префикс Ascend, источники сосредоточены в двух аккаунтах: cn-sys — 12 (непрерывные отправки с 15:19 до 16:14), JINITAIMEI121 — 13 (с 08:31 до 10:39), ещё один — сообщение PTO о дублирующихся физических сегментах в нескольких регионах.

Общее у этих issue — не «результат посчитан неверно», а «проходит то, что не должно проходить». Категория проверки параметров: T.Kernel принимает нулевое или отрицательное число блоков, T.Persistent принимает отрицательные wave_size и num_stages, T.Pipelined принимает отрицательный num_stages и недопустимые метаданные order/stage, T.unroll принимает −1 и выдаёт #pragma unroll -1, конструктор циклов принимает нулевой или отрицательный extent, отрицательная размерность тензора напрямую роняет компилятор (нативный краш, а не исключение Python), T.alloc_l1 принимает выделение 2 GiB без какой-либо проверки ёмкости. Категория семантических несоответствий: nearest_zero у hf32 компилируется в NEAREST_AWAY, таблица dtype входов GEMM и codegen двусторонне несогласованы, reduce_bitand/bitor/bitxor выдают типы, не определённые в шаблоне Ascend, batch reduction вырождается в скалярную точку входа AllReduce без батчевой перегрузки, pad_value копирования GM в L1 маршрутизируется в L1 fill, принимающий только ноль, scatter ND в NZ того же типа зацикливается из-за отсутствия отката при подсчёте маски, строки partial-VL порождают несуществующий режим PAT_VL<N>. Категория инструментальной цепочки: vsts_pack_quarter не имеет 16-битной ветви, из-за чего сохранение PK4_B32 на векторах b16 молча теряется, сериализация модуля теряет device source, из-за чего у кэшированного ядра при сбое запуска нет исходника для проверки, автоматическая настройка бэкенда msprof неизбежно падает из-за вызова signal.signal() в рабочем потоке.

Это не разрозненные жалобы — по форме это организованный аудит: один и тот же аккаунт в течение получаса последовательно отправлял тематические группы сообщений с единообразным заголовком «[BUG] Ascend: …» и кратким описанием корневой причины. Для upstream это означает, что пробелы в «надёжности» фронтенда Ascend были разом вынесены на всеобщее обозрение — то, что все 3060 ежедневных тестов проходят, не означает, что нелегальный ввод будет отклонён, поскольку тесты покрывают легальные пути.

4.2 Рассматриваемые исправления в созвучии с аудитом: проверка mask в VMI, восстановление SIMD fill, копирование E4M3 ND/NZ (11-11)

Среди обновлённых в этот день рассматриваемых PR есть ряд, которые точно нацелены на вышеуказанные пробелы. #3861 и #3917 — это две части одного и того же: фабрики унарных и векторно-скалярных операций VMI ранее проверяли mask только на «наличие», не проверяя dtype и число каналов, поэтому обычный вектор, переданный как предикат, мог дойти до codegen — vabs, vneg, vrelu, vexp, vln, vsqrt, vnot — семь операторов построены на этой фабрике, а на векторно-скалярной стороне vadds, vmuls, vmaxs, vmins, vshls, vshrs также имеют слабые формы.

#3795 исправляет ещё один побочный эффект #3512: когда в T.SimdVF() выполняется T.clear для буфера int32 UB, генерируемое векторное широковещание поддерживает только числа с плавающей точкой, и компиляция PTO завершается ошибкой — поскольку конвейер PTO заменяет оригинальный SIMD-проход специальным проходом Parallel, попутно теряя понижение fill. Исправление состоит в добавлении LowerSimdVFFill после нормализации версии буфера и до проверки PTO Parallel, с повторным использованием vdup/vsts для непрерывных и полных векторных областей, а остальное по-прежнему идёт старым путём; при этом сохраняется числовое преобразование плавающего tl.simd.vdup, что исправляет проблему «int32 7 побитово широковещательно превращается в примерно 9.809e-45».

#3639 добавляет копирование E4M3 из ND/NZ UB в L1, #3926 заставляет T.Kernel отклонять неположительное число блоков и отрицательное Pipelined num_stages, #3854 исправляет деление на ноль для суббайтовых элементов в понижении SimdVF, #3668 добавляет для ядра AIV в T.PerCoreTask() чередующуюся запись с шагом из UB в GM. Кроме того, #3915 и #3916 занимаются видами ошибок AssertStmt и встроенными утверждениями проверки условий.

4.4 Уточнение методики: старые артефакты Triton в двух контрольных сравнениях Q1 проекта K3 переполняются при взятии отрицания от -128 (11-11)

Это выделено отдельно, потому что влияет не на оценку, а на сопоставимость. Базовый репозиторий в том же пакете коммитов, где был опубликован weft-parity, раскрыл: два контрольных сравнения Q1 проекта K3 ранее использовали сохранённую программу Triton Canonical, которая переполняется при взятии отрицания от −128 — граничный ввод даёт −2048, тогда как правильный результат должен быть 0. После перегенерации общим компилятором с исправленным точным сокращением I8 артефакты обоих фронтендов проходят этот ввод; исторические затраты времени сохранены в поле triton_historical_us, а пояснение исправления записано в triton_control_note.

Ошибка в контрольной реализации — распространённая ловушка проектов класса бенчмарков: как только эталонная сторона ошибается на граничном вводе, «хуже эталона» у испытуемой стороны может означать лишь то, что эталон ошибается быстрее. В сочетании с методикой сопоставления из 2.8 это раскрытие показывает, что данная линия CPU переходит от «сравнения авторской программы с внешней библиотекой» к «сравнению сопоставленных артефактов одного компилятора», что методологически более надёжно, но две таблицы нельзя смешивать.

5. Наблюдения за трендами

Во-первых, вес Ascend в основной линии продолжает расти, и происходит переход от «дополнения операторов» к «дополнению путей выполнения и решателей». В этом выпуске все три коммита в основном репозитории связаны с Ascend: смена бэкенда выполнения по умолчанию, ужесточение нижней границы решателя, адаптация атомарных операций к системе типов. Ни один из этих трёх коммитов не добавляет операторы в список, но все они меняют то, «как одна и та же программа компилируется, запускается и как долго компилируется». Сопоставляя с записями с октября, слияния на стороне Ascend прошли путь от дополнения операторов AscendC до трёх слоёв: семантики интерфейсов, бэкенда выполнения и решателя планирования.

Во-вторых, сторона CUDA вошла в длительный период рецензирования. В прошлом выпуске ещё три примитива уровня инструкций CUDA вошли в основную ветку, в этом выпуске — ноль слияний и шесть на рассмотрении (ldmatrix/stmatrix, 256-битная векторизация, планирование im2col, жизненный цикл операндов конвейера, жизненный цикл асинхронного GEMM, пространство имён конфигурации PASS). Одновременное снижение скорости слияний и утолщение очереди на рассмотрении обычно означает, что узким местом стала пропускная способность рецензирования, а не остановка разработки.

В-третьих, аудит качества начинает идти параллельно с разработкой функциональности. Форма 26 issue по Ascend за один день показывает, что в сообществе уже кто-то проводит систематический аудит нелегальных входных данных, а соответствующие PR с исправлениями в тот же день были в очереди (проверка mask, отклонение отрицательных параметров, восстановление понижения fill). Для проекта, который разворачивает бэкенд на нескольких отечественных чипах, это хорошо: прохождение всех 3060 ежедневных тестов доказывает лишь работоспособность легальных путей, а способность отклонять нелегальные пути должна обеспечиваться такими аудитами.

В-четвёртых, четыре источника RISC-V молчат пять окон подряд, но линия CPU за пределами этих четырёх источников дала промежуточный вывод. Маршрут TVM, маршрут MLIR, страница индекса сообщества и TPU Sophtgo остаются на исходных ссылках; а TileLang–Weft с общим компилятором Canonical довёл все 553 пункта до не более чем 1,03× от Triton, медианный коэффициент по четырём платформам — от 1,29 до 1,66. Следует отметить, что это результат после смены методики измерения, его нельзя напрямую сравнивать с 0,058× из прошлого выпуска. Настоящая точка наблюдения: сможет ли этот подход «один компилятор, два фронтенда» войти в upstream в обратном направлении, и будет ли путь RVV/IME для RISC-V впервые пройден проектами за пределами четырёх источников.

Ограничения: в этом выпуске квота анонимного API GitHub была исчерпана на ранней стадии сбора, текст PR и детали слияний были дополнены через поисковый интерфейс и атомарный поток коммитов неосновных веток; количество файлов и строк для отдельных PR — это возвращаемые значения поискового интерфейса, построчная сверка diff не проводилась; слияния hygon и mlir-ascend попали в неосновные ветки, проверка проводилась отдельно по веткам. На новостной стороне — только нулевые совпадения, внешних сообщений для перекрёстной проверки нет.
