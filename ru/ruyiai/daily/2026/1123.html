Источник: BUDDY MLIR 0.1.5, 0.1.6, 0.1.7. PR #1074.

За три дня buddy-mlir выпустил три официальные версии. 0.1.5 выпущена 11-20 в 23:40, 0.1.6 — 11-21 в 22:49, 0.1.7 — 11-22 в 01:12, интервалы составили примерно 23 часа и 2 часа.

Все три тега указывают на конкретные коммиты. 0.1.5 указывает на 20d3a102, то есть на замену диалекта ZTT v0.6, вошедшую 11-19. 0.1.6 указывает на 8cbc1a9b, то есть на #1074 «Release LLVM with dump() support». 0.1.7 указывает на a848378f с заголовком «Shrink the LLVM tarball so it fits in one release asset».

Каждый релиз содержит 8 артефактов. Помимо wheel и tar.gz для x86_64, есть wheel и tar.gz для manylinux_2_39_riscv64, однофайловый buddy-cli для riscv64, а также два набора предкомпилированных пакетов LLVM 24.0.0git.

По объёму riscv64 wheel в 0.1.7 составляет 380 057 776 байт, x86_64 wheel — 365 782 329 байт. buddy-cli для riscv64 — 436 952 байта, для x86_64 — 759 592 байта. Со стороны LLVM пакет x86_64 — 1,03 ГБ, пакет riscv64 — 1,14 ГБ.

Ни у одного из трёх релизов нет описания, текст пуст. Проверяемая информация ограничивается тегами, коммитами и списком артефактов.

Главное сегодня: оптимизация FP16 для DeepSeek-R1-Distill-Qwen-1.5B на K3 A100 вошла в основную ветку, Prefill 43,42 token/s (11-23)

Источник: PR #997. Коммит 3d5d674a. Конфигурация K3 f16_k3.json.

#997 вошёл в основную ветку 11-23 в 00:25, создан 10-25, рецензирование заняло почти месяц. Изменено 20 файлов, включая новый pass легализации A100, расширение диалекта IME и конфигурацию модели.

В описании PR приведены четыре ключевых приёма. Первый: четыре аккумулятора FP32 постоянно находятся в регистрах на всём сокращении по K, Prefill идёт блоками 8×32, Decode вычисляет по 32 выходных канала на блок. Второй: часть весов проекций Decode упакована в панели N32/K8, остальные проекции сохраняют исходную раскладку RVV. Третий: Prefill использует нативный VLEN=1024 и ширину BLIS 64, а также объединяет поэлементные операторы и векторизует SiLU. Четвёртый: перечисленные выборы сосредоточены в models/deepseek_r1/specs/f16_k3.json, конвейер по умолчанию для существующих конфигураций не меняется.

Измеренные данные зафиксированы согласно описанию PR. Prefill оценивается на 128 позициях, Decode измеряется начиная с 64-й позиции в течение 32 шагов, восемь потоков, ядра A100 с 8 по 15, берутся четыре выборки. Единица в таблице — token/s.

Реализация Prefill Decode
Основная ветка Buddy, упакованный FP16 4,53 5,88
llama.cpp (бэкенд SpacemiT 0.1.6) 27,95 3,90

Prefill относительно основной ветки Buddy вырос примерно в 8,6 раза, относительно llama.cpp выше на 55%. Decode относительно llama.cpp выше на 55%, относительно основной ветки Buddy выше лишь на 3%.

Цифры Prefill включают накладные расходы на сессию и вызовы интерфейса, что отмечено в описании PR. На стороне llama.cpp используются веса FP16 GGUF и FP16 KV cache, входные ID совпадают с обеих сторон.

Тот же набор ядер был повторно использован для других моделей. #1075 — для Whisper Base, #1076 — для PaddleOCR-VL-0.9B, #1001 — для Qwen3-0.6B. Все три ссылаются на pass и упаковку весов из #997.

1.2 Примеры FlagGems открывают ещё две ветки: 72 + 61 оператор, всего 279 (11-21, 11-22)

Источники: PR #131. PR #132.

#131 открыт 11-21 18:53, охватывает 72 оператора. #132 открыт 11-22 18:48, охватывает 61 оператор. Оба PR изменяют только python/examples/flaggems/.

Четыре группы #131 — это координатное копирование, внутреннее копирование и выделение, конструирование форм, преобразование типов и заполнение. В описании PR перечислены три расхождения с upstream: обёртка padding принимает входные данные в порядке aten (w, h, d), затем переупорядочивает их в порядок ядра (d, h, w); обратный проход replication сканирует по позициям скалярного источника, чтобы соответствовать порядку накопления aten; при rank больше 2 в rot90 пропущен член последнего измерения.

Четыре группы #132 — это обёртки BLAS и разреженный smm, специальные функции gamma, квантованные операторы, низкоточное и разреженное матричное умножение. В описании PR указано, что скалярное произведение fp64 может накапливаться только в fp32, поэтому такие свёртки переведены на скалярный цикл FMA для сохранения точности; у e5m2 fp8 нет пути понижения точности, поэтому используется повышение внутри ядра, а e4m3 и int8 идут нативно.

Число тестов продолжает расти. #131 фиксирует 7830 пройденных и 739 новых; #132 фиксирует 8617 пройденных и 787 новых. Оба прогонялись на x86_64, исключены три существующих падающих файла.

Пять PR образуют цепочку: 63 оператора в #126, 43 в #127, 40 в #130, 72 в #131, 61 в #132 — всего 279 примеров операторов. Согласно описаниям PR, пока предыдущие PR не замёржены, diff учитывает предыдущие коммиты: #131 относительно main — это 34 коммита и 548 файлов, #132 — 38 коммитов и 670 файлов.

Источники: список коммитов ветки riscv. список коммитов ветки main.

Голова ветки riscv по-прежнему 3b5279fd «[ci] Drop JENKINS_RC (#57)», время остановилось на 11-15 19:00. В окне в этой ветке ноль коммитов.

В ветке main за окно 20 коммитов, содержание — всё та же синхронизация с upstream. В выборке видны сведение опций CUTLASS в Inductor, перенос avg_pool2d_backward для MPS на Metal, проверка обучения SDPA для XPU, откат одного округления float64.

При фильтрации по ключевому слову RISC-V среди этих коммитов ноль совпадений. То есть в окне нет собственных RISC-V изменений RuyiAI.

В форке сейчас 9 веток, включая agent/riscv-linear-cross-entropy-ulp, improve-riscv64-ci и sync/upstream-lc-eps-riscv. В этих трёх ветках за окно новых коммитов нет.

2. Инструментальная цепочка и дистрибутивы RuyiSDK

2.1 Выпущен ruyi 0.55.0-beta.20261120, шесть PR влиты в окне мониторинга (21.11)

Источники: дистрибутив 0.55.0-beta.20261120. PR #521. PR #520. PR #518.

0.55.0-beta.20261120 выпущен 21.11 в 11:58. Примечания к выпуску перечисляют 19 изменений, накопленных после 0.54.0.

В окне мониторинга влиты шесть PR — с #516 по #521. Слияния сосредоточены с 20.11 07:20 до 14:58.

#521 — основной в этом выпуске. Он добавляет в ruyipkg события прогресса загрузки: отчёт шагами по 1% или 1 MiB, события с идентификатором корреляции, в режиме porcelain больше не выводится человекочитаемая полоса прогресса, а неудачи загрузки также сообщаются событиями. В реализации сначала выделен протокол logger, затем разделены flush и выход PorcelainOutput.

#520 обрабатывает недопустимые SemVer в именах файлов манифеста — теперь они пропускаются с устойчивостью к ошибкам, без падения, а также обновлены элементы локализации. #519 исправляет ошибочное использование относительных путей в спецификации базовых каталогов XDG.

#518 — изменение формата конфигурации: repo.disabled переименован в repo.active и выставлен в ruyi config. Старый ключ всё ещё работает, но помечен как устаревший. #516 обновляет зависимости и объявляет поддержку Python 3.15, #517 — полировка документации.

В примечаниях к выпуску есть ещё 13 пунктов, для которых в окне мониторинга нет соответствующих коммитов. Среди них метаданные, специфичные для производителей, и отметка «RuyiSDK Certified», сканер совместимости ELF ABI, переопределение приоритета программных источников, исправление состояния установки между репозиториями. Это накопления цикла 0.54.0.

Источники: коммит overlay ee3c01d6. коммит arpy 2.4.0.

В той же партии — два изменения arpy. Одно поднимает arpy до 2.4.0, другое обновляет метаданные upstream.

Overlay последовал примерно через 2,5 часа после выпуска. Это показывает, что приём нового beta на стороне упаковки автоматизирован.

2.3 30 коммитов в репозитории сайта сосредоточены на прошивке устройств, добавлены распаковка xz/lz4 и прогресс загрузки (21.11)

Источники: список коммитов ruyisdk-website. коммит 6d3a4a75. коммит 867358f6.

В репозитории сайта в окне мониторинга 30 коммитов, подавляющее большинство вокруг процесса прошивки устройств (provisioning). Время — с 20.11 19:43 до 21.11 11:28.

На стороне обработки образов добавлены два блока. Первый — распаковка: добавлена поддержка дисковых образов в форматах xz и lz4. Второй — загрузка: приоритет отдаётся зеркалам для настольных систем, неудачи загрузки и локальные ошибки сообщаются раздельно, отображается прогресс распаковки образа.

Больше всего изменений — в выборе целевого диска. Целевой диск для записи dd теперь выбирается в боковой панели, убрано лишнее действие отмены, предотвращается повторное открытие диалога выбора каталога, а вся подготовка образов перенесена до выбора диска.

По стабильности — три изменения. Блокировка flash-записи теперь снимается только после сходимости всех host-команд, Go bootstrap включён в provisioning worker, предзагрузка runtime.

Эти изменения не попали в примечания к релизу. Коммиты в репозитории сайта в основном с префиксами fix(device) и feat(device) — это завершение функциональности.

2.4 ruyi-backend обновляет зависимости, packages-index — ноль коммитов в окне мониторинга (11-20)

Источники: список коммитов ruyi-backend. список коммитов packages-index.

В окне мониторинга ruyi-backend — 3 коммита, все обновления зависимостей. githubkit обновлён до 0.16.1, FastAPI — до 0.165.0, плюс один poetry update.

3. Векторные расширения и оптимизация операторов

3.1 VecIntrinBench, IntrinTrans и FBGEMM продолжают молчать (состояние на 11-23)

Источники: VecIntrinBench. IntrinTrans. FBGEMM.

Три репозитория — ноль коммитов в окне мониторинга. Время последних коммитов: 02-13, 06-25 и 07-13 соответственно.

Бенчмарк и инструмент преобразования векторных интринсиков не двигались три квартала. Текущие данные по векторной производительности в основном берутся из тестов операторов triton-riscv и измерений моделей в buddy.

Это не означает, что векторное направление замерло. Векторная работа в окне мониторинга записана в ядрах моделей — см. следующий пункт.

3.2 Векторная работа переходит в ядра моделей: VLEN 1024, SiLU и приближение exp (11-22)

Источники: PR #997. PR #1076. PR #1075.

#997 делает ширину BLIS-столбцов Prefill настраиваемой и позволяет проверять аппаратный VLEN на входе функции. Конфигурация A100 берёт VLEN=1024 с шириной 64.

В том же коммите SiLU переведён на fused и векторизованную реализацию, exp идёт через полиномиальную аппроксимацию upstream MLIR. В описании PR указано, что полином меняет округление и проверяется отдельно от пути по умолчанию.

#1076 объединяет bmm1, scale, softmax и bmm2 attention в единое блочное ядро, softmax остаётся в L1, используется векторный exp. В том же коммите для -approximate-vector-exp добавлен векторизованный erf, чтобы GELU больше не вызывала скалярную функцию по каждому lane.

#1075 идёт другим путём. P @ V энкодера понижен до FP32-накопительного RVV-ядра с разворотом M на 4 строки, matmul_transpose_b и conv_1d_ncw_fcw понижены до IME.

Общее у трёх коммитов — привязка векторной ширины к аппаратному VLEN. Настройка #129 на стороне triton из прошлого выпуска использует тот же подход; параметры обеих сторон можно сопоставить.

3.3 Примеры FlagGems охватывают специальные функции и квантованные операторы (11-22)

Источники: PR #127. PR #132.

Ветка специальных функций охватывает семейство Бесселя, четыре типа Chebyshev и сдвиговые версии, два типа Hermite, Laguerre, Legendre, а также log_softmax и logsumexp.

Интринсики, которые toolchain не может понизить, переведены на замкнутую форму. erfcx использует трёхсегментную смесь, хвост log_ndtr пересчитывается как −t² + log(erfcx(t)/2).

Ветка квантования и низкой точности охватывает семейство псевдоквантования и его обучаемые варианты, 4-битный динамически квантованный linear, scaled mm, упаковку int8/int4 весов, mixed-precision linear, CSR и полуструктурированное произведение.

Обработка точности описана в PR. Точечное произведение fp64 на стороне Triton может достигать только накопления fp32; такие сокращения переведены в скалярные циклы FMA; для e5m2 fp8 нет пути понижения, внутри ядра выполняется повышение; e4m3 и int8 используют нативный путь.

4. Динамика Buddy Compiler

4.1 Соответствие тегов и коммитов от 0.1.5 до 0.1.7 (11-22)

Источники: список тегов. compare 0.1.6…0.1.7.

Каждому из трёх тегов соответствует один коммит. 0.1.5 — это 20d3a102, 0.1.6 — 8cbc1a9b, 0.1.7 — a848378f.

compare показывает, что 0.1.6 опережает 0.1.5 на 1 коммит — это исправление dump() из #1074. 0.1.7 относительно 0.1.6 находится в состоянии форка: опережает на 1 и отстаёт на 1.

Родительским коммитом 0.1.7 является 20d3a102, то есть базовая версия 0.1.5. Это означает, что 0.1.7 не содержит исправления dump().

Это имеет прямое влияние на нижестоящие проекты. triton требуется mlir::Operation::dump() для линковки; и 0.1.5, и 0.1.7 лишены этого символа, и только 0.1.6 его содержит.

В настоящее время на стороне triton по-прежнему закреплён nightly/v0.1.4.dev20261103 (#115 не смержен). Если согласно #115 обновиться до release/v0.1.7, проблема линковки вернётся.

4.2 0.1.6 добавляет поддержку dump(), 0.1.7 сжимает артефакты LLVM (11-21)

Источники: PR #1074. коммит a848378f.

Причина #1074 описана весьма конкретно. Ночная сборка собирается из main, но #1062 попал в ветку llvm-multitarget, поэтому пакет LLVM версии 0.1.5 содержит только dumpPretty(), но не dump().

Нижестоящий симптом — сбой линковки с сообщением undefined reference to mlir::Operation::dump() и mlir::Value::dump() const. Исправление заключается во включении LLVM_ENABLE_DUMP, восстанавливающем только эти два helper’а, без включения утверждений.

В описании PR также отмечено: установка LLVM кэшируется по хэшу, поэтому последующие версии должны запустить llvm_cache_mode=clean один раз, чтобы получить этот флаг.

0.1.7 решает проблему лимита артефактов. В описании коммита указано, что установочный пакет LLVM для riscv64 после gzip слегка превышает лимит в 2 GiB на один артефакт, из-за чего v0.1.6 выдавал ошибку «size must be less than 2147483648».

Исправление — усечение неиспользуемых нижестоящими проектами инструментов разработчика, удаление src, share и libexec, а также strip остального. Для x86_64 фактически измерено снижение с 1617 MB до 817 MB.

В описании также зафиксирована одна неудачная попытка. Сначала файлы просто удалялись, но LLVMExports.cmake на этапе configure прерывался из-за того, что импортированные цели указывали на отсутствующие файлы, поэтому было решено использовать усечение.

Обе версии сейчас имеют по 8 артефактов. Пакет LLVM для riscv64 в 0.1.7 составляет 1 138 715 828 байт, что ниже лимита.

6. Наблюдения за трендами

6.1. Выпуск версий смещается от помесячного графика к исправлению блокировок нижестоящих потребителей

В прошлом выпуске отмечалось, что ruyi переносит 0.55.0 на конец ноября. В текущем выпуске ruyi выпустил beta, а buddy-mlir за три дня выпустил три версии подряд.

Ни 0.1.6, ни 0.1.7 не являются функциональными версиями. Один коммит добавляет недостающий нижестоящей сборке dump(), другой сжимает объём артефактов, чтобы уложиться в лимит 2 GiB.

Основание для вывода — тексты коммитов: в #1074 прямо указана ошибка triton undefined reference, в a848378f прямо указано size must be less than 2147483648.

Это означает, что номер версии используется как канал исправлений. Цена — расхождение 0.1.7 и 0.1.6: чтобы нижестоящий потребитель получил оба исправления одновременно, придётся ждать следующего слияния.

6.2. На K3 A100 формируется конвейер оптимизации моделей

После слияния #997 один и тот же набор ядер IME фигурирует в PR для трёх моделей: Whisper, PaddleOCR-VL и Qwen3.

Показатели производительности во всех трёх коммитах зафиксированы на одной машине K3-002, одной группе ядер 8–15, восьми потоках, VLEN=1024. То есть они сопоставимы напрямую.

Масштаб выигрыша различается сильно. Для DeepSeek Prefill ускорение магистрали — 8,6 раза, для Whisper сквозное ускорение — 818,8 раза. В последнем случае база — одиночный прямой проход F32 без переиспользования энкодера, и кратность раздута заниженным базовым значением.

Проверяемая метрика — совпадение token-последовательности с эталонной реализацией. В #1076 зафиксировано полное совпадение 19 токенов и приложен текст OCR.

6.3. Сторона инструментальной цепочки входит в фазу накопления очереди на слияние

Пять PR FlagGems в triton-riscv выстроены в цепочку, в сумме 279 примеров операторов. Каждый ждёт слияния предыдущего, чтобы пересчитать diff.

На стороне ruyi картина обратная: шесть PR слиты за один день, выпущен beta. Разница в том, что изменения ruyi сосредоточены в CLI и конфигурации, а поверхность ревью узкая.

Пояснения об ограничениях

Окно мониторинга составляет 3 дня (с 11-20 04:30 до 11-23 04:30) и охватывает выходные. Окно понедельника считается за 3 дня и вплотную примыкает к конечной точке отчёта от 11-20.

Для трёх версий с 0.1.5 по 0.1.7 отсутствуют примечания к релизу, текст пуст. Различия между версиями можно вывести только по коммитам, на которые указывают теги, и по результатам compare; официально они не перечислены построчно.

Состояние расхождения между 0.1.7 и 0.1.6 получено из интерфейса GitHub compare. Если впоследствии произойдёт слияние, вывод потребует повторной проверки.

Цифры производительности в #997, #1075, #1076 измерены и предоставлены самими авторами PR; в этом выпуске они не перепроверялись на оборудовании K3. Показатель Whisper в 818,8 раза основан на однократном прямом проходе F32 без повторного использования энкодера, поэтому кратность не следует сравнивать с другими моделями напрямую.

Из 19 изменений ruyi 0.55.0-beta 13 не имеют соответствующих коммитов в окне мониторинга; в тексте они отнесены к накоплениям цикла 0.54.0, даты фактического внедрения построчно не проверялись.

Спам-сообщения на форуме определялись по заголовкам, каждое сообщение не открывалось для проверки. Из шести групп запросов Google News найдено только одно сообщение о XiangShan, не относящееся к теме этого выпуска, и оно исключено. Последняя статья на arXiv датирована 11-19, в окне мониторинга новых нет.
