Главное сегодня: официальный релиз ruyi 0.54.0, проверка совместимости ABI хоста вошла в пользовательские команды (11-10)

Дата: 2026-11-10　Источник: релиз ruyi 0.54.0, сопоставление изменений 0.53.0 → 0.54.0, PR #507

0.54.0 выпущен 11-10 в 21:15 (пекинское время), это официальная версия, а не предварительная. Предыдущая версия 0.53.0 вышла 09-24, интервал — сорок семь дней; между ними был только 0.54.0-beta.20261102 от 11-02. Официальная версия относительно этой беты содержит лишь один коммит с номером версии, функционально это всё содержимое беты; в сумме от 0.53.0 в этой версии семьдесят один коммит и семьдесят четыре файла.

Основная функция — сбор и сопоставление информации о совместимости ELF ABI. Возможность запуска предварительно скомпилированного бинарного файла на целевом устройстве зависит от набора фактов, разбросанных по заголовкам ELF-файлов: какие динамические библиотеки требуются, какие версии символов запрашиваются у этих библиотек, а также требования к возможностям, связанным с архитектурой. Ранее в источниках программного обеспечения нигде не фиксировались эти сведения; теперь ruyi извлекает их, сохраняет и сопоставляет перед установкой.

Сбор данных разделён по архитектурам: для x86-64 фиксируется уровень ISA feature, для AArch64 — BTI и PAC, для RISC-V — строка ISA. Последняя наиболее трудоёмка, поскольку расширения RISC-V собираются в строку по номерам версий; в коммитах этого выпуска реализованы разбор однобуквенных расширений с версиями, фильтрация записей ld.so.cache по ABI плавающей точки хоста, а также учёт требований к выравниванию стека. На стороне хоста дополнительно реализовано определение для x86-64 и AArch64; библиотеки хоста разрешаются по запрошенному soname, а при обнаружении неразрешимого soname сообщается «не определено», а не выносится фатальный вердикт.

Видимые пользователю изменения затрагивают три команды: ruyi list отображает совместимость с хостом в примечании (для небинарных пакетов этот пункт скрыт), ruyi install выдаёт предупреждение при установке несовместимого пакета, а ruyi admin check-abi предназначена для диагностики. Уровень данных опирается на ABI sidecar на стороне репозитория, разрешаемый по имени distfile; в rescan-package-abi и артефакты плагинов добавлен strip-components для обработки случаев с ведущим каталогом в архиве. Для sidecar задан предельный размер; повреждённый sidecar отбрасывается как «нет информации об ABI» и не приводит к сбою всей установки.

Другая категория — исправления в цепочке загрузки: #509 обеспечивает корректное сообщение об ошибке при не-2xx HTTP-ответах, отбрасывание неудачной первой загрузки и установку предела для зависших передач. Эти изменения малозаметны, но для менеджера пакетов, которому нужно вытягивать сотни мегабайт инструментальных цепочек с зеркал, они влияют на опыт сильнее, чем новые функции.

Проектный документ docs/elf-abi-compat-design.md включён в репозиторий вместе с версией; в примечаниях к выпуску указаны способы установки — PyPI и зеркало, обслуживаемое сервисом; однофайловый бинарник необходимо переименовать в ruyi для использования.

Главное сегодня: triton-riscv по умолчанию включает бэкенд AMD GPU на хостах RISC-V (11-10)

Дата: 2026-11-10　Источники: PR #110, README

PR #110 был слит 11-10 в 17:51 (пекинское время) под заголовком «Включить GPU-бэкенд по умолчанию». Изменения состоят из трёх частей: сборка и упаковка библиотеки AMD codegen для riscv64 с использованием существующего Buddy LLVM SDK; устранение неоднозначности выбора между CPU- и GPU-драйвером на riscv64 по правилу приоритета доступного GPU; а также исправление той проверки на уровне драйвера, которая делала выбор неоднозначным (в этом файле чисто удалены четыре строки).

Проверка выполнена на реальном оборудовании: SG2044 с RX 7900 XTX, torch и ROCm из репозитория ПО openRuyi; дополнительно проверен автоматический откат на CPU при скрытых GPU-устройствах. Этот критерий гораздо строже, чем «компилируется»: он показывает, что хост RISC-V действительно отправляет ядра на карту AMD, а не выполняет их на CPU в качестве запасного варианта.

В README одновременно добавлен раздел об использовании AMD GPU: при наличии ROCm бэкенд активируется самостоятельно через torch.version.hip, синтаксис совпадает с вышестоящим руководством; wheel не содержит среды выполнения ROCm, torch и ROCm устанавливаются отдельно; для принудительного возврата на CPU используется TRITON_DEFAULT_BACKEND=triton_shared. Изменения охватывают шесть файлов, сосредоточенных в README, backend/driver.py и четырёх скриптах build, env, release, setup в каталоге scripts.

Стоит отметить один временной разрыв: ночная сборка nightly/2026-11-10-209274f, выпущенная в тот день в 10:22 (пекинское время), была сделана на коммите 209274f, то есть до этого слияния, поэтому данный пакет ещё не содержит GPU-бэкенд. Чтобы его получить, нужно дождаться следующей ночной сборки.

Для всего стека это изменение на уровне маршрута: ранее triton-riscv отвечал только на вопрос «как запускать Triton на векторных блоках CPU RISC-V», теперь же он должен отвечать и на вопрос «как управлять гетерогенными ускорителями с хоста RISC-V». В момент, когда ни одна из основных AI-ускорительных карт не имеет драйвера для хоста RISC-V, поддержка карт AMD — наиболее реалистичный первый шаг: работы по ROCm на стороне RISC-V уже ведутся в репозитории openRuyi.

1. Прогресс стека RuyiAI (адаптация PyTorch / Triton / TileLang для RISC-V)

1.1 triton-riscv: PR о переименовании плагина на рассмотрении, значения переменных окружения изменятся вместе с ним (11-10)

Дата: 2026-11-10　Источники: PR #109, список коммитов

#109 Решаемая проблема — несоответствие названия: name.conf определяет имя установленного пакета и точку входа, поэтому плагин теперь называется triton.backends.triton_shared, но сообщает целевой объект cpu, а префикс опций уже triton_riscv. Решение — унифицировать название как riscv, причина — выравнивание по практике именования upstream: плагины именуются по семейству целей (nvidia, amd), а имя устройства (cuda, hip) оставляется для target.

Сопутствующее изменение — переменные окружения: значение TRITON_DEFAULT_BACKEND меняется с triton_shared на riscv, то есть описанный в сегодняшнем ключевом пункте способ «принудительного возврата на CPU» перестанет работать после слияния. Имя инструмента triton-shared-opt и сторона C++ не меняются. Второй коммит добавляет ruff для шестидесяти файлов, затронутых переименованием; эта партия файлов ранее никогда не проходила lint и содержит девятнадцать существующих нарушений.

Статус PR — открыт, 11-10 18:56 (пекинское время) ещё было обновление, пока не слит. Среди открытых PR, обновлённых в тот же день, также #103 (дополнение учебного пособия) и #104 (пример SPM для BOSCAME FPGA и фронтенд контракта AOT); все три относятся к базовой работе «можно взяться, можно воспроизвести».

2.2 openRuyi: восемь коммитов — четыре исправления безопасности плюс снимок LLVM и переключатель Wayland (11-10)

Дата: 2026-11-10　Источники: коммит policycoreutils, коммит lxc, коммит cups, коммит llvm-snapshot

В упаковочном репозитории в окне восемь коммитов, по характеру делятся на три категории.

Безопасность — четыре: policycoreutils обновлён до 3.11 с обратным переносом исправления fixfiles; lxc, libmtp и cups каждый получил обратный перенос патчей безопасности upstream. Все четыре помечены тегом security-fixes — это обычная практика отслеживания CVE upstream, но для дистрибутива это часть, которую нужно подхватывать в тот же день.

Инструментарий — два: llvm-snapshot и clang-wrap в один день обновлены до 20261109. Эти два пакета — основа цепочки самосборки компилятора на RISC-V, а также источник архивов LLVM, от которых зависит сборка triton-riscv; ежедневное обновление снимка означает, что компилятор, получаемый нижестоящими проектами, меняется каждую неделю.

Остальные два: libssh обновлён до 0.12.2, SDL2 включает бэкенд Wayland (ранее был только путь X11). Изменение в SDL2 влияет на десктопный и игровой стек сильнее, чем кажется — многие графические программы создают окна через SDL, и только с включённым переключателем Wayland на десктопе появляется настоящий нативный путь.

4. Динамика Buddy Compiler

4.1 buddy-mlir: детекция и поза YOLOv8 запущены на матричном движке K3, исправлены две вещи — веса и копирование TCM (11-10)

Дата: 2026-11-10　Источник: PR #1042

#1042 подключает Ultralytics YOLOv8 к формату rax в buddy-cli: детекция yolov8n (восемьдесят классов COCO) и yolov8n-pose (семнадцать ключевых точек), вход в обоих случаях 320x320. Модель f32 проходит понижение через VIR; если в спецификации указано ime: true, то запуск идёт на матричном движке SpacemiT K3.

Две правки, внесённые на этапе ревью, информативнее самой модели. Первая — проверка весов: в манифесте есть params_size, раннер требует соответствия файла весов ему, ранее слишком короткий файл весов приводил к чтению моделью за пределами буфера; одновременно раннер теперь принимает только пакеты rax, поскольку при отдельной передаче библиотеки и весов модель позы запускалась с параметрами модели детекции. Вторая — копирование TCM: копия весов IME в TCM кешируется по адресу весов, и при чтении новых весов в уже освобождённый буфер происходило попадание в старую копию; теперь после каждой загрузки весов вызывается функция инвалидации на стороне ядра.

В спецификации одновременно сохраняются params_size и ime_params_size, чтобы при ime: false всё ещё можно было собрать версию f32. Эта конструкция — та же линия, что и сквозной проход VIR концом в конец днём ранее: одна и та же схема, два пути бэкенда, одна сопоставимая базовая линия.

4.2 buddy-mlir: область vir.set_vl сужена до одного блока, многоблочные области больше не теряют операторы молча (11-10)

Дата: 2026-11-10　Источник: PR #1045

Тип региона у vir.set_vl изначально был AnyRegion, и в исходном коде оставался комментарий «ограничение региона не определено». Верификатор и каждая точка lowering в -lower-vir-to-vector берут только region.front(), поэтому несколько блоков региона проходят проверку, а операторы в остальных блоках молча отбрасываются. Воспроизведение очевидно: load и store в одном set_vl попадают во второй блок (после cf.br ^bb1), и результатом понижения становятся два пустых affine.for; пустой регион проходит верификацию, а затем в проходе падает с ошибкой «не найден тип якоря».

Исправление — заменить тип на SizedRegion<1>, удалить комментарий, а верификатор больше не защищает от пустого региона сам (ODS проверяет число блоков заранее), оставив только условие «у блока нет аргументов». В тесты добавлены два вида недопустимого ввода: с двумя блоками и с нулём блоков. Такое изменение не даёт новой функциональности, но превращает класс путей «компилируется, но считает неверно» в ошибку времени компиляции; ценность здесь в диагностируемости.

4.3 buddy-mlir: дополнены печать, разбор и проверка динамических векторных типов и масштабирующих коэффициентов (11-10)

Дата: 2026-11-10　Источник: PR #1046

Масштабирующий коэффициент ранее печатался в форме атрибута #vir.sf<m2>, тогда как синтаксис типов и примеры дают m2; на стороне разбора оставался комментарий «сообщение об ошибке добавить позже», и поведение было несогласованным во многих местах: #vir.sf<x2> и mq приводят к падению (разбор возвращает пустой атрибут без сообщения об ошибке, а парсер типов считает его допустимым значением), m3, m0, f128 принимаются, !vir.vec<0x?xf32> принимается, а !vir.vec<?xvector<4xf32>> отвергается с указанием позиции unknown.

Изменение состоит из трёх частей: печать переведена на sf.str(), при этом #vir.sf<m2> по-прежнему читается; на стороне атрибута добавлен genVerifyDecl, требующий, чтобы коэффициент был m или f, имел значение от 2 до 64 и был степенью двойки (в соответствии с уже существующей проверкой в Python-привязках); на стороне типа требуется, чтобы все измерения перед динамическим были статическими и положительными. Второй коммит исправляет локализацию ошибки до реальной позиции. Для ещё формирующегося промежуточного диалекта строгость парсера напрямую определяет, сможет ли фронтенд надёжно сообщать об ошибках.

4.4 buddy-mlir: reassoc-редукция сначала объединяет блоки по lane, исправлено побитовое расхождение на хосте с VLEN 128 (11-10)

Дата: 2026-11-10　Источник: PR #1047

На RISC-V-хосте с VLEN 128 (ядро C920 в SG2044) в qk_norm из test_k3_w4_kernels.py возникло побитовое расхождение. Причина в том, что нормализация q, k в декодере внимания K3 помещает сумму квадратов шестидесяти четырёх f32 одной головы в регион set_vl без shuffle, понижение выполняется по размеру хоста (#1037), и при VLEN 128 это превращается в два блока vector<32xf32> (LMUL 8); а vir.reduce последовательно вливает каждый блок в результат предыдущего, что отличается от порядка однократной редукции vector<64xf32> в векторном ядре — LLVM разбивает широкий вектор пополам, складывает по lane и затем выполняет редукцию ещё раз. CI riscv64 работает на VLEN 256, где блок только один, поэтому всё всегда проходило.

Исправление — заставить reassoc-редукцию через несколько блоков объединяться так же, как в LLVM: n блоков сначала дополняются до степени двойки h, блок p складывается с блоком p+h/2, пока не останется один блок, после чего выполняется однократная редукция. Это уже четвёртое исправление по той же теме (до него были проверка VLEN при загрузке, размер хоста и округление хвоста FMA), и все они указывают на один критерий приёмки: реализацию менять можно, численные значения — нельзя.

4.5 buddy-mlir: переименованы пятьдесят Python-файлов, опции llc для A100 сведены к единой точке входа (11-10)

Дата: 2026-11-10　Источник: PR #1043, PR #1044

#1043 переименовывает пятьдесят Python-файлов с дефисами в имени на подчёркивания: в том же каталоге уже есть файлы с подчёркиваниями, а файлы с дефисами невозможно импортировать, поэтому их функции нельзя протестировать или переиспользовать. Изменение охватывает четыре места — models, examples, .agents/skills и tests, — а также синхронно исправляет ссылки в CMake, shell-скриптах, README и документации. Из двухсот сорока одного Python-файла в upstream MLIR двести тридцать семь используют подчёркивания; это изменение приводит проект к стандарту upstream.

#1044 исправляет путь IME для YOLOv8: lower_to_obj.sh сам собирал набор опций llc для A100 (включая +zvl1024b и -riscv-v-vector-bits-max=1024), но использовал только последнюю для проверки VLEN при сборке. Начиная с #1032, VLEN единообразно задаётся через BUDDY_RISCV_VLEN, остальные модели берут его из a100_llc_args, и проверяется точное значение 1024, которое фактически читает llc. Старый скрипт обманывался сборкой с +zvl256b или без VLEN: VIR понижался под произвольный VLEN, а object компилировался под 1024. Теперь скрипт напрямую добавляет опции, выдаваемые единой точкой входа, останавливается, если VLEN не равен 1024, и добавлен тест, прогоняемый с помощью заглушки инструмента.

6. Наблюдение за трендами

6.1 Интервал выпуска 0.54 удвоился, цена — сбор ABI для трёх архитектур

От 0.52 до 0.53 прошло двадцать два дня, от 0.53 до 0.54 — сорок семь дней. За это удвоившееся время коммиты почти все легли на одну линию: довести совместимость ELF ABI от «нет записей» до «можно собирать, хранить, сравнивать и предупреждать перед установкой». Этот путь требует одновременно разбираться с ISA level x86-64, BTI и PAC AArch64, строкой версионированных расширений RISC-V — это знания трёх архитектур, а не три похожие кодировки.

Примечательно, что это сначала появилось в пакетном менеджере, а не в процессе контроля качества какого-либо дистрибутива. Пакетный менеджер — единственное место, где можно принять решение в момент «пользователь нажимает установить»; размещение проверки совместимости здесь равносильно переносу затрат на проверку уровня дистрибутива на одно локальное сравнение.

6.2 «Можно ли установить» впервые становится вычислимым фактом

Фрагментация RISC-V заключается не в самом наборе инструкций, а в базовой линии: один и тот же бинарник riscv64 может не запуститься на плате RVA20, а может выдать недопустимую инструкцию на ядре без векторного блока. Раньше такие проблемы решались документацией, ответами на форумах, методом проб. Версия 0.54 записывает требования каждого пакета к динамическим библиотекам, версиям символов и возможностям архитектуры в sidecar, хост-сторона определяет соответствующие факты и сравнивает их, — так «этот пакет не устанавливается» превращается из эмпирического утверждения в воспроизводимый вывод.

Побочный эффект — поддержка данных: sidecar должен обновляться вместе с пакетом, различия архивов вроде strip-components нужно обрабатывать отдельно, для плохого sidecar нужна явная стратегия деградации. В 0.54 все эти краевые случаи прописаны в коде, что говорит о том, что стоимость поддержки была учтена при проектировании.

6.3 RISC-V-хост с картой AMD выходит в основную ветку

triton-riscv расширился от «запуска Triton на векторном блоке RISC-V» до «управления AMD GPU с хоста RISC-V», причём путь по умолчанию сразу выбирает GPU. Такая комбинация ранее появлялась только в демонстрациях производителей, теперь она вошла в ветку по умолчанию и проверена на реальном железе (SG2044 с RX 7900 XTX).

Практический смысл в том, что экосистема хостовых драйверов для основных AI-ускорителей почти всегда готовится для x86 и Arm, и машины RISC-V долгое время могли выполнять инференс только на CPU. Отправка ядра с хоста RISC-V на потребительскую карту AMD — самый малозатратный путь обхода этого пробела в экосистеме: ROCm на RISC-V уже поддерживается, не хватает лишь звена бэкенда компилятора.

6.4 Объект исправлений VIR смещается от «неверного вычисления» к «тихой ошибке»

Из шести коммитов buddy-mlir в этом окне мониторинга как минимум три направлены на «отсутствие ошибки при неверном результате»: тихая потеря операторов в регионах с несколькими блоками set_vl, падение при разборе масштабирующего коэффициента или пропуск недопустимых значений, изменение численных результатов при порядке межблочной редукции. Первые две категории раньше заставляли компилятор молча выдавать неверный результат, теперь становятся ошибками времени компиляции; третью можно поймать только побайтовым сравнением.

Общая черта таких проблем — низкая стоимость исправления и высокая стоимость обнаружения. То, что их удаётся очищать партиями на этом этапе, говорит о том, что у VIR уже есть тестовая поверхность, способная работать на реальном железе и сравнивать с базовой линией — без сопоставления на K3 и SG2044 различия VLEN 128 и 256, подобные случаю 4.4, вообще не проявились бы.
