3.1 IREE 3.13.0: RISC-V V f32 vfmacc.vf MMA вошёл в релиз (10-19)

Дата: 2026-10-19　Источники: IREE v3.13.0 Release, PR #24933 RISC-V V inner_tiled MMA

IREE v3.13.0 выпущен 10-19 в 19:26; в бэкенде CPU добавлен inner_tiled MMA для RISC-V V f32 vfmacc.vf (PR #24933), который напрямую отображает векторное умножение-сложение с плавающей точкой на fused multiply-accumulate RISC-V V; при этом масштабируемая векторизация LLVMCPU теперь требует обязательного указания --iree-llvmcpu-vscale-range, а при наличии особенности +zvl*b берётся большее из двух нижних значений. На стороне моделей сохранён импорт квантизации PT2E per-tensor, per-channel-group, per-token в LinalgExt Q/DQ.

Значение для данного стека — в сопоставлении путей: tilelang-riscv и triton-riscv в RuyiAI идут по маршруту от DSL уровня Tile к RVV, а IREE — по маршруту MLIR→LLVMCPU с масштабируемой векторизацией. На одном и том же RVV оба фронтенда одновременно выбрали f32 multiply-add в качестве цели оптимизации, что показывает: данная форма инструкций стала общепризнанной точкой опоры для AI-бэкендов на RISC-V.

3.2 Сторона верификации и кэширования: три слияния в riscv-arch-test, групповые банки памяти CoupledL2 в XiangShan (10-19 — 10-20)

Дата: 2026-10-19 — 2026-10-20　Источники: riscv-arch-test PR #2413 Sdtrig, PR #2791 S_F/S_V/S_VF, PR #2858 покрытие SEW векторных инструкций, XSCache PR #36, XiangShan PR #6738

6. Наблюдения за тенденциями

6.1 Построение замыкания зависимостей идёт параллельно по трём языковым линиям: Rust дополняет бэкенд uv, Go избавляется от vendor, Python дополняет облачное хранилище

Структура 42/42/42 из 137 коммитов текущего периода — не совпадение, а три независимые линии пополнения пакетов, продвигающиеся в один день: на стороне Rust вокруг трёх семейств windows-* 0.61, zerocopy/rkyv, cap-std/io-lifetimes в связке с python-uv-build, что указывает на Rust-зависимости таких инструментов сборки Python, как uv; на стороне Go преобладают minio и компоненты Prometheus/Kubernetes, а в связке с тремя PR по удалению vendor «упаковка вместе с исходниками» меняется на «упаковку по зависимостям»; на стороне Python за один раз добавлены все основные облачные бэкенды fsspec. Общая цель трёх линий — заполнить замыкание зависимостей, чтобы развёртывание Python AI и cloud-native на RISC-V не требовало компиляции на месте.

Стоит зафиксировать связь этого уровня с RuyiAI: DataLoader, checkpoint и инструменты работы с наборами данных в PyTorch повсеместно обращаются к удалённому хранилищу через fsspec, и полнота бэкендов напрямую определяет, сможет ли скрипт обучения отработать на K1/K3. Эта часть зависимостей, которую дистрибутив закрывает за верхние уровни, определяет «работоспособность» в большей степени, чем оптимизация отдельного оператора.

6.2 Ветка PyTorch перешла в режим ежедневного перепроигрывания: базовая линия обновляется ежедневно, последовательность патчей не меняется

Два дня подряд наблюдается одна и та же картина: 10-19 в 09:14 и 10-20 в 08:32 — по одному принудительному обновлению всей ветки, время коммиттеров всей ветки перезаписано единообразно, заголовки локальных патчей построчно не меняются, изменения только в объёме синхронизации с upstream-базой. Такой подход развязывает «следование за upstream» и «поддержание патчей», ценой становится невозможность проследить историю ветки — любой downstream, ссылающийся по SHA (кэш CI, сборка образов, воспроизведение issue), будет ежедневно ломаться. Если этот ритм закрепится, при чтении данной ветки критерием версии следует считать «набор заголовков патчей», а не SHA.

Состояние трёх линий fork продолжает расходиться: PyTorch перепроигрывается ежедневно, LLVM молчит восемь дней с 10-12, Triton после восстановления ночных сборок до одной версии 10-19 остановился. Три линии соответствуют трём состояниям вложений и подсказывают, что текущее узкое место стека RuyiAI — не сам бэкенд компиляции, а непрерывное обеспечение ревью и выпуска сборок.

6.3 Серверная платформа приносит дистрибутиву список совместимости, а не новую задачу портирования

Материалы о Jindie V100 вносят openRuyi в перечень доступных дистрибутивов серверной платформы. Если это подтвердится, смысл не в том, что «openRuyi должна выполнить новое портирование», а в наборе требований соответствия спецификациям: RVA23, спецификации серверных SoC/платформ, BRS и модель безопасности — пять пунктов, плюс прошивочная цепочка UEFI/ACPI/SMBIOS. Дистрибутиву нужно скорее выровнять уже имеющиеся пользовательские пакеты, установщик и цепочку образов под спецификации, а не переписывать компоненты.

Текущие данные всё ещё неполны: в основном репозитории openRuyi за день ноль коммитов, связанных с серверами, линейка прошивок (ruyifirmware, edk2-ruyi) молчит с 10-15, версия 2026.10 пока не выпущена. Есть три точки наблюдения: упоминается ли серверная платформа в примечаниях к выпуску openRuyi 2026.10; возобновятся ли коммиты для V100 в ruyifirmware/edk2-ruyi; появится ли запись V100 в матрице поддержки.
