Главное за сегодня: triton-riscv смержил плагинную переработку Triton 3.9.0, набор патчей обнулён, отдельный дистрибутивный пакет уходит (11-05)

Дата: 2026-11-05　Источники: PR #98, список коммитов, PR #92

11-05 11:13 (пекинское время), PR #98 от trdthg «Bump Triton to main (3.9.0)» слит в основную ветку: 5 коммитов, 66 файлов, добавлено 1806 строк, удалено 3868 строк. Объём удалённого примерно вдвое превышает объём добавленного, и это определяет характер переделки — это не наложение ещё одного слоя патчей поверх существующей ветки, а полное удаление самого подхода с патчами.

Первое изменение — форма бэкенда. Механизм Triton TRITON_PLUGIN_DIRS устанавливает backend/ как плагин бэкенда triton_shared, регистрирует точку входа, подключает C++ плагин к libtriton.so и копирует triton-shared-opt в пакет вместе с остальным. Отдельный дистрибутивный пакет triton-riscv при этом исчезает, импорты в коде единообразно переводятся на это имя плагина. Сам бэкенд теперь ищет buddy-opt, buddy-llc, mir-translate и triton-shared-opt через paths.py; драйвер CPU объявляет себя активным только при отсутствии какого-либо GPU-бэкенда.

Второе изменение — обнуление набора патчей. Каталог patches/ и скрипты применения патчей удалены полностью. Ранее у набора патчей было две причины существования: обеспечить сборку Triton в среде без инструментальных цепочек NVIDIA/AMD и подстраховать частые изменения API LLVM. Теперь дистрибутив LLVM от buddy-mlir включает цели NVPTX/AMDGPU и lld, а путь зависимостей Triton от GPU перенаправляется в stub-каталог — обе причины отпадают, и набор патчей теряет смысл существования.

Третье изменение — слияние путей сборки пакетов. release.sh больше не собирает второй wheel: поддержка плагинов Triton уже помещает бэкенд и triton-shared-opt в wheel Triton, скрипт лишь удаляет инструменты и напрямую вызывает bdist_wheel. Makefile становится единой точкой входа для setup, build, test, lit, clean, причём test зависит от lit.

Цена записана в описании коммитов того же PR. Фронтенд Triton 3.9 читает из бэкенда поля вроде backend_name; без него каждый вызов tl.atomic_* выбрасывает AttributeError, из-за чего на riscv64 падают 383 теста FlagGems. Только после добавления трёх полей — backend_name, default_dot_input_precision и deprecated_fp8_dot_operand_dtypes — область отказов сократилась. Есть уступка и на стороне примеров: upstream отклонил фронтенд-патч для asin/acos/atan/atan2, и примеры переведены на libdevice, который сводит их к тем же __nv_* extern_elementwise, а затем triton-shared преобразует их в операторы MLIR math.

PR #92 «Rebase integration onto the official Triton v3.8.0 release» на том же пути в тот же день закрыт неслитым. Спор двух маршрутов, зафиксированный в прошлом выпуске (#92 — стабильность до 3.8.0, #98 — следование основной линии 3.9.0), на этом сошёлся ко второму.

1. Прогресс стека RuyiAI (адаптация PyTorch / Triton / TileLang к RISC-V)

1.1 triton-riscv: точка входа сборки сведена к Makefile, бэкенд устанавливается в пакет Triton через каталог плагинов (11-05)

Дата: 2026-11-05　Источники: список коммитов, PR #98

После перехода на плагины путь импорта бэкенда внутри пакета Triton — triton.backends.triton_shared. Поверхность установки этого набора стала уже, чем раньше: больше нет двух дистрибутивных пакетов и больше не предполагается наличие рядом рабочей копии buddy-mlir. Описание «двух пакетов», шаги применения патчей и допущение о рабочей копии на том же уровне удалены; shutil.which("lit") в setup.py теперь предпочитает консольный скрипт lit, установленный через pip, а не тот, что поставляется с дистрибутивом LLVM. Последний при вызове main() не имеет защиты if __name__ == "__main__", а forkserver-многопроцессность Python 3.14 при импорте основного модуля запускает его повторно, из-за чего цель lit падает при 80 параллельных задачах.

Путь к локальным инструментам для бэкенда тоже изменён: buddy-opt, buddy-llc, mir-translate, triton-shared-opt теперь единообразно разрешаются через paths.py. Определение активности CPU-драйвера — «отсутствие GPU-бэкенда на месте», что отличается от прежнего подхода с проверкой переменных окружения; на машинах с сосуществованием нескольких бэкендов поведение стало более предсказуемым.

1.2 triton-riscv: ритм релизов переведён на ежедневный nightly и выходной release, параллелизм pytest зафиксирован на 16 (11-05)

Дата: 2026-11-05　Источники: PR #99, список Release

PR #99 выравнивает ритм релизов по buddy-mlir: ночная задача публикует предрелизы nightly/<date>-<sha>, выходная задача публикует release/<date>-<sha> и помечает их как последнюю версию; при отсутствии новых коммитов задача пропускается, release остаётся в статусе черновика до завершения загрузки всех wheel, а workflow_dispatch предоставляет разовый выбор dev/patch. В тот день по этому ритму уже выпущены два ночных билда: nightly/20261105-48bde12 (19:50) и nightly/20261105-849a180 (22:48).

На стороне тестов набор pytest переведён на 16 процессов. Выбор этого числа имеет эмпирическое обоснование: на срезе из 207 тест-кейсов 1 процесс занял 360 секунд, 8 процессов — 89 секунд, 16 процессов — 67 секунд, 24 процесса — 67 секунд, а 32 и 64 оказались медленнее — отдельный тест-кейс представляет собой последовательную цепочку «компиляция, triton-shared-opt, llc, исполнение, сравнение», и при большем числе процессов начинается конкуренция за общий кэш компиляции. При прежнем последовательном запуске набор flaggems занимал 1 час 14 минут. setup.sh устанавливает pytest-xdist, переопределить можно через PYTEST_WORKERS.

1.3 triton-riscv: stable ABI wheel покрывает 3.12–3.15, исправлено определение инструментальной цепочки manylinux (11-05)

Дата: 2026-11-05　Источники: PR #100, PR #101

PR #100 собирает wheel по образцу cp312-abi3 из upstream Triton: scripts/env.sh и scripts/release.sh устанавливают TRITON_STABLE_ABI=ON, nanobind компилируется с ограниченным API (Py_LIMITED_API=0x030C0000), а setup.py помечает wheel как cp312-abi3. Один wheel покрывает все интерпретаторы после 3.12 (3.12/3.13/3.14/3.15), и матрица релизов сокращается с трёх версий Python до одной. Исходный код остаётся без патчей — сам upstream предоставляет этот переключатель.

В той же ветке исправлены две проблемы сборочных скриптов. Во-первых, release.sh жёстко задавал /opt/rh/gcc-toolset-14/enable и проверял его до dnf install clang, тогда как образ manylinux — это плавающий :latest, который на тот момент уже содержал gcc-toolset-15; в результате скрипт активации никогда не выполнялся, и clang не находил crtbeginS.o, -lstdc++, -lgcc (riscv64) и заголовок <version> из libstdc++ (x64) — сборка падала на обеих архитектурах; теперь clang устанавливается первым, затем активируются все существующие инструментальные цепочки, причём самая свежая — последней. Во-вторых, после перехода на единственный abi3 wheel строка python: ["3.12", "3.13", "3.14"] в матрице лишь трижды пересобирала один и тот же wheel. PR #101 открыт в тот же день и ещё не слит; он устраняет сбой рабочего процесса публикации на этапе очистки при checkout.

Дата: 2026-11-05　Источники: список коммитов, PR #1595, PR #1596

PR #1600 (4/n, 14 файлов, добавлено 1094 строки) пакетирует для компонента Base Firebird и его генератор парсеров btyacc, генератор интерфейсов cloop — всё ещё на рассмотрении; PR #1602 (6/n, 16 файлов, добавлено 1360 строк) добавляет PDFium, ZXing, SANE и Box2D — всё ещё на рассмотрении; PR #1603 (7/n, 47 файлов, добавлено 3342 строки) охватывает Pentaho, HSQLDB 1.8, BeanShell и движок JavaScript — закрыт без слияния. В описании PR #1595 отмечен вклад с помощью AI (Assisted-by: GPT-6-Astra xhigh), что соответствует требованиям политики AI-вклада openRuyi.

4. Динамика Buddy Compiler

4.1 runtime добавляет общий serving-контроллер генерации для поддержки выбора токенов на стороне устройства (11-05)

Дата: 2026-11-05　Источники: PR #1018, коммит c2fd2e1

PR #1018 добавляет не зависящий от модели serving-контроллер генерации, 18 файлов, 2045 новых строк, позволяющий адаптерам runtime совместно использовать единый набор бюджета генерируемых токенов, условий остановки, учёта использования и потоковой очистки. Вызывающая сторона может либо использовать хостовую выборку через LLMSession, либо token-источник, напрямую выдающий токены на стороне устройства.

В реализации есть несколько моментов, достойных фиксации: строковые условия остановки сначала сопоставляются по сырым байтам, а затем выполняется декодирование UTF-8, что избегает ошибочного определения на границах многобайтовых символов; бюджет токенов учитывает как первое предсказание, так и EOS/стоп-токены; фиксированное случайное зерно поддерживает нулевое значение; штраф за повторение применяется по одному разу для каждого уникального token ID в историческом окне запроса. Первый токен приходит из prefill, поэтому статистика пропускной способности относит первый выбор к prefill, а последующие выборы — к decode, при нулевой работе decode сообщается нулевая пропускная способность. Пути генерации существующих CLI и серверных входов остаются неизменными, выход защищён golden-тестами с фиксированными logits и production-токенизатором и сэмплером DeepSeek. Подключение последующих адаптеров отслеживается отдельно в задачах DeepSeek R1 (#1021), Llama 3.1 TTNN (#1022) и Qwen3-VL и др.

4.2 Дополнительный патч масштабируемого векторного lowering в VIR: broadcast переходит на vector<[2]xT>, ядро деградирует по опциям llc (11-05)

Дата: 2026-11-05　Источники: PR #1030, PR #1031

Оба изменения midend нацелены на масштабируемые векторы. Lowering vir.shuffle разбивается на несколько этапов: broadcast сначала идёт через vector<[2]xT>, затем берётся первая половина (vector.scalable.extract) для получения vector<[1]xT>, поскольку при прямом vector.broadcast над vector<[1]xT> LLVM генерирует shufflevector с маской [0], который сворачивается createOrFold как тождественная операция, а оставшиеся vscale-1 lane оказываются poison; llc превращает insertelement в vfmv.s.f, записывающий только lane 0, и если это значение не вливается в инструкцию .vf, а сохраняется в регистр, результат оказывается неверным. После перехода на [2]xT llc выполняет broadcast через vfmv.v.f на LMUL [1]xT, число инструкций не увеличивается, а в цикле становится на одну меньше. Другое изменение позволяет ядру деградировать по опциям llc, таким как -mattr; тест vir-broadcast-scalable-one.mlir покрывает два пути: со снятием и с результатом set_vl.

6. Наблюдения за трендами

6.1 От поддерживаемой ветки к паразитированию на upstream: плагинизация обменивает стоимость патчей на привязку к версии

Дата: 2026-11-05　Источник: PR #98, PR #92

triton-riscv за один день превратил себя из «поддерживающей пропатченную ветку Triton» в «плагин к upstream Triton», удалив более двух тысяч строк — каталог патчей исчез целиком. Выгода такого подхода прямая: при последующем обновлении версии вслед за upstream больше не нужно воспроизводить патчи, от сборки остаётся только один wheel, а поверхность установки сокращается с двух дистрибутивных пакетов до одного.

Цена столь же ясна и проявилась в тот же день: фронтенд Triton 3.9 читает из бэкенда поле backend_name, и без него падают 383 теста FlagGems. Паразитирование на точках расширения upstream означает, что неявные контракты фронтенда upstream становятся обязательным интерфейсом, а эти контракты зачастую не документированы и обнаруживаются только через тесты. Судить об успехе этой переработки следует не по тому, сколько строк удалено сегодня, а по стоимости воспроизведения при следующем обновлении upstream и по тому, нужен ли по-прежнему выделенный человек для отслеживания версий в таких нижестоящих наборах, как FlagGems.

6.3 Прирост выпуска 080 приходится на компилятор и среду выполнения, а не на фронтенд прикладного уровня

Дата: 2026-11-05　Источник: текст выпуска 080

Четыре наиболее содержательных пункта выпуска 080 находятся на нижнем уровне: три оптимизации Zb* из GCC вошли в основную ветку, шесть коммитов LLVM по P-ext и XTHeadBb влиты, перенос JEP 544 AOT из OpenJDK влит, обработка векторных хвостов и VLEN в V8. Фронтенд прикладного уровня (PyTorch, TileLang) в этом выпуске не получил соответствующего подключения возможностей.

Это распределение указывает на то же, что и 6.1: на данном этапе акцент делается на том, чтобы существующие операторы и языковые среды выполнения стабильно и корректно работали на RISC-V, а не на расширении охвата фронтенда. Для нижестоящих пользователей ощутимые в краткосрочной перспективе изменения проявятся в продуктах компиляции и поведении JDK, а не в списке поддерживаемых новых фреймворков.
