Еженедельный отчёт RuyiAI (2026-11-09 ~ 2026-11-13)

2026-11-13 Kubuds

Отчётный период: с 9 ноября 2026 г. (понедельник) по 13 ноября 2026 г. (пятница), всего 5 рабочих дней.

Источники материалов: 5 выпусков ежедневного отчёта RuyiAI за 2026-11-09 — 2026-11-13 (окно мониторинга каждого выпуска — с 04:30 предыдущего дня до 04:30 текущего дня, при этом для понедельника — за прошедшие 3 дня, включая выходные); кроме того, 168-часовая проверка репозиториев четырёх организаций — RuyiAI-Stack, ruyisdk, buddy-compiler, openRuyi-Project (проверка охватывает период до утра 11-14), двух-source перекрёстная проверка сообщества разработчиков RuyiSDK и новостной страницы дистрибутива openRuyi, снимки трёх страниц официального сайта RuyiAI, а также индексы блога и документации, а также целевой поиск в Google News и arXiv.

Пояснение к составлению: на этой неделе одновременно произошла смена двух основных направлений — одно связано с релизами, другое — с охватом векторного пути. Со стороны релизов: ruyi 0.54.0 вышел в финальной версии 11-10, спустя сорок семь дней после предыдущей версии; triton-riscv 11-09 получил первый в истории репозитория тег release/, а 11-10 по умолчанию включил бэкенд AMD GPU на хосте RISC-V; Ruyi Imager 1.1.0 выпущен в тот же день, а двухнедельный выпуск прогресса № 080 зафиксировал эту «тройную серию» в качестве официальной формулировки. Со стороны компилятора: buddy-mlir за неделю вобрал тринадцать коммитов, подключив маску i1, математические функции только из libm, bf16, все виды редукций, заполнение rank-0 и целочисленное матричное умножение по категориям в векторный путь VIR; число прохождений набора FlagGems на SG2044 выросло с 3980 до 4006, а остаточные linalg.fill и linalg.matmul в 1811 ядрах обнулились оба. Одновременно с охватом продвигается и безопасность: три изменения, связанные с VLEN, указывают на один и тот же тип отказа — отсутствие ошибки при неверном вычислении. Пробел остаётся там же: ежемесячная версия openRuyi по-прежнему停留在 2026.09, октябрь и ноябрь до сих пор без новой версии.

Основное — сбор и сопоставление информации о совместимости ELF ABI: сбор ведётся по архитектурам, для x86-64 фиксируется уровень функций ISA, для AArch64 — BTI и PAC, для RISC-V — строка ISA (включая разбор однобуквенных расширений с версиями, фильтрацию записей ld.so.cache по ABI плавающей точки хоста, требования к выравниванию стека). Видимые пользователю изменения затрагивают три команды: ruyi list показывает совместимость с хостом в примечаниях, ruyi install предупреждает при установке несовместимого пакета, ruyi admin check-abi служит для диагностики; уровень данных идёт через ABI sidecar на стороне репозитория, повреждённый sidecar отбрасывается как «нет информации об ABI», а не приводит к сбою всей установки. 2. Прогресс стека RuyiAI (адаптация PyTorch / Triton / TileLang для RISC-V)

2.1 triton-riscv: от «восемнадцати ночных тегов» до первого официального релиза

Дата: 2026-11-06 — 2026-11-14　Источники: тег официального релиза, PR #105 README переведён на приоритет wheel

Этот репозиторий за неделю прошёл три шага: установил уровни релиза (первый тег release/), перевёл путь установки с исходного кода на wheel, довёл гетерогенный бэкенд от «компилируется» до «работает на реальном железе». Между тремя шагами есть последовательная зависимость — без воспроизводимого тега wheel проверка GPU-бэкенда могла остановиться только на сборке из исходников; а проверка AMD-бэкенда, в свою очередь, выявила несколько проблем в цепочке релиза, проявляющихся только на самохостируемом riscv64 runner.

2.1.1 Сам тег — это всё содержание релизного действия

Дата: 2026-11-06, 11-09　Источники: release/20261108-6895885, PR #101

release/20261108-6895885 указывает на коммит 6895885, то есть на коммит слияния от 11-06 «добавить для AMD недостающую библиотеку codegen для riscv64» (#102), — та же точка, что и у ночной версии nightly/20261106-6895885. Три коммита того дня (#105, #106, #107) легли после тега и не вошли в этот пакет — это означает, что первый официальный релиз фактически собран из состояния кода на конец прошлой недели.

Два сопутствующих изменения в цепочке релиза были внесены ранее в рамках окна мониторинга: #101 исправил две проблемы цепочки релиза, выявленные после #100 (workflow релиза переведён на ту же версию действия checkout, что и в CI, в scripts/release.sh добавлен шаг регистрации бэкенда, чтобы wheel из release обладал той же информацией о регистрации плагинов, что и wheel из CI), #102 заставляет setup.sh при обнаружении отсутствия библиотеки AMD codegen собирать её локально и размещать по оговорённому пути, а env.sh указывает на неё TRITON_AMD_CODEGEN_PATH. В ночную версию дополнительно добавлен уникальный суффикс версии .dev<дата>, поскольку ранее каждая сборка использовала собственную версию Triton, и индекс пакетов отклонял дублирующиеся версии.

2.1.2 Путь установки переведён на приоритет wheel, быстрый старт переориентирован на дизассемблирование

Дата: 2026-11-09　Источники: PR #105, PR #107

#105 Переписан раздел установки в README: сначала указан путь к wheel и индекс пакетов, который его размещает, затем требуемый архив LLVM и переменная, на которую он указывает; путь сборки из исходников сжат до make setup (создание .venv, клонирование фиксированной версии Triton, загрузка фиксированной версии LLVM и сборка buddy), а прежнее описание «создать виртуальное окружение, установить зависимости, пятнадцать переменных в скрипте окружения» сведено к одной короткой заметке. #107 затем внёс исправление: индекс пакетов пока не содержит инструментов triton и buddy, поэтому адрес, указанный в README для установки бинарников, будет давать ошибку — в связи с этим ссылки изменены на GitHub releases обоих проектов и установку wheel с диска. В том же коммите исправлено падение lit под Python 3.14 — Triton ищет lit через which в PATH, а тот lit, что находится в дереве LLVM, вызывает main на уровне модуля; Python 3.14 на Linux по умолчанию переключился на способ запуска forkserver, и при повторном импорте происходит падение; исправление состоит в том, чтобы поместить каталог bin интерпретатора сборки в начало PATH.

2.2 Гетерогенный маршрут triton-riscv: RISC-V хост управляет картами AMD

Ключевое — совместимость ELF ABI: может ли предкомпилированный бинарник запуститься на целевом устройстве, зависит от набора фактов, разбросанных по заголовку ELF-файла — какие динамические библиотеки нужны, какие версии символов запрошены у этих библиотек, а также требования к возможностям, связанным с архитектурой; ранее нигде в программном источнике они не фиксировались, теперь ruyi извлекает эту информацию, сохраняет её и сравнивает перед установкой.

Сбор данных по RISC-V оказался самым трудоёмким, поскольку его расширения собираются в строку по номерам версий: в коммитах этого выпуска есть разбор однобуквенных расширений с версиями, фильтрация записей ld.so.cache по ABI плавающей точки хоста, а также учёт требований выравнивания стека. Плоскость данных идёт через ABI sidecar на стороне репозитория и разрешается по имени distfile; в rescan-package-abi и артефактах плагина добавлен strip-components для обработки случаев с ведущим каталогом в архиве; у sidecar есть верхний предел размера, испорченный sidecar отбрасывается как «нет информации об ABI».

4.2 Побайтовое чтение и запись масок i1 (#1052)

Дата: 2026-11-12　Источник: PR #1052

Когда тип элемента memref — i1, масштабируемые векторы ранее отклонялись напрямую (с сообщением a memref of i1 needs fixed vectors), поскольку memref занимает один байт на элемент, а вектор i1 — один бит на дорожку, и только векторы фиксированной длины имеют понижение по дорожкам. При этом маски load/store в Triton как раз и есть i1 memref: при прохождении чисто VIR-конвейера с масштабируемыми векторами 179 из 325 тестовых файлов Triton-RISCV спотыкались об эту ошибку — это самое широкое по охвату изменение из семи на этой неделе.

Решение — побайтовое чтение и запись: для непрерывного доступа используется llvm.load/store вектора i8, для несмежного strip-mined региона — vp.strided.load/store с включением всех дорожек; попутно размер дорожки i1 считается как один байт — ранее регион, где первым динамическим вектором был i1, считался по 1 биту, и при VLEN 256 получался масштаб вроде vector<[512]xi1> на шестнадцать групп регистров.

4.3 Поэлементное развёртывание математических функций libm-only (#1053)

Дата: 2026-11-12　Источник: PR #1053

Математические функции, которые LLVM не желает понижать для масштабируемых векторов (erf, erfc, cbrt, powf, atan2, acosh и др.), теперь развёртываются поэлементно: для vector<[N]xT> по каждой из N умножить на vscale дорожек выполняется extract, вызов скалярной функции, затем insert. Причина в том, что convert-math-to-libm обрабатывает масштабируемые векторы так же, как векторы фиксированной длины, — вычисляет только первые N, а остальные молча обнуляет: масштабируемый erf при VLEN 128 (vscale 2) имеет половину неверных дорожек. Эффект напрямую виден на тестовой поверхности: в наборе FlagGems число пройденных из 4045 элементов на SG2044 (VLEN 128) выросло с 3980 до 4006, исправленные 26 — это test_erf и test_gelu, новых падений нет.

4.4 Два пути bf16 и исчерпывающая проверка (#1054)

Дата: 2026-11-12　Источник: PR #1054

RVV помещает bf16 в векторные регистры только при наличии Zvfbfmin; без этого расширения LLVM не желает понижать даже одну загрузку. Изменение добавляет в понижатель параметр rvv-mattr, по умолчанию обрабатывающий наличие Zvfbfmin (у нескольких RVV-целей Buddy — X100 и A100 от K3, а также SG2044 — он есть); при явном указании -zvfbfmin обработка переключается на целочисленное представление: вектор bf16 читается и пишется как i16, extf и truncf используют целочисленные операции (truncf — с округлением к ближайшему чётному), absf и negf работают через знаковый бит.

Метод проверки — самый тяжёлый на этой неделе: truncf покрывает все 2^32 значений f32, extf, absf, negf и extf-mulf-truncf покрывают все 2^16 значений bf16, и на двух ядрах SG2044 и K3 результаты побитово сравниваются с путём Zvfbfmin — результаты совпадают. Такая стоимость проверки показывает, что bf16 уже рассматривается как отгрузочный путь, а не как оптимизация «когда будет время».

4.5 Флаги fast-math и все виды полных редукций (#1055, #1056)

Дата: 2026-11-12　Источник: PR #1055, PR #1056

#1055 исправляет потерю флага fast-math при понижении strip-mined: arith.mulf с contract плюс arith.addf перестраивались в обычные fmul и fadd, и LLVM не выполнял слияние. Теперь флаг передаётся вместе с оператором того же типа в векторный цикл и хвост, f32 умножение-сложение даёт vfmacc, bf16 при +zvfbfwma даёт vfwmaccbf16; автор побитово сравнил развёртывание fmaf на 4M дорожках на X100 и A100 платформы K3, результаты совпали. Это единственный из семи коммитов, который напрямую меняет выбор инструкций.

#1056 расширяет vir.reduce с распознавания только чисел с плавающей точкой add и maxnum до всех видов vector.reduction: add, mul, minsi, minui, maxsi, maxui, and, or, xor, minnumf, maxnumf, minimumf, maximumf, с поддержкой целых чисел, при этом verifier проверяет соответствие kind и типа элементов. Ранее целочисленное суммирование, min/max, произведение, all/any в Triton (а также зависящие от них argmin, argmax, count_nonzero, битоническая сортировка и поразрядная сортировка) оставались в цикле. Изменение добавляет 570 строк и затрагивает 9 файлов.

4.6 Завершение остаточных путей: заполнение rank-0 и целочисленное матричное умножение (#1057, #1058)

Дата: 2026-11-12　Источники: PR #1057, PR #1058

#1057 понижает linalg.fill для rank-0 memref (в большинстве случаев — аккумулятор приведения) до одного memref.store, остаточные linalg.fill в 1811 ядрах FlagGems сокращаются с 393 до 0. #1058 позволяет понижать и целочисленное матричное умножение: когда A и B одного целого типа и не шире C, сначала выполняется знаковое или нулевое расширение, затем умножение-сложение (без fma); на RVV int8 матричное умножение даёт vsext.vf2 плюс vwmacc.vx, а беззнаковое — vzext.vf2 плюс vwmaccu.vx; этот же коммит исправляет сбой утверждения в matmul с динамическими формами — M и K изначально брались внутри области vir.set_vl и стирались последующими pass при использовании. 5. Динамика Buddy Compiler

5.1 Первая половина точной спецификации VLEN: #1032 и #1037

Дата: 2026-11-08　Источники: PR #1032, PR #1037

#1032 решает проблему класса ошибочных отказов: не сообщает об ошибке, а просто считает неверно. Модель RISC-V, собранная под точный VLEN, — векторный код действителен только для этого одного VLEN: llc явно сообщается VLEN (+zvlNb и -riscv-v-vector-bits-max), масштабируемые векторы в decode attention также размеряются по нему. При переходе на другой VLEN модель не падает, а сразу выдаёт неверный результат.

Исправление — перенос проверки на момент загрузки: runtime/rvv/BuddyRvvVlen.c как конструктор линкуется в библиотеку модели, при загрузке библиотеки читается vlenb, и при несовпадении с точным VLEN на момент сборки печатается информация и процесс завершается через _exit(1). Использование _exit вместо exit намеренно — запуск деструкторов, пока загрузчик держит блокировку, приводит к дедлоку. После ревью добавлен ещё один коммит, меняющий проверку с «по переменной сборки» на «по финальным опциям llc»: ранее нативная сборка могла задавать VLEN через собственные LLC_ATTRS модели, и при несовпадении с BUDDY_RISCV_VLEN проверяемое значение не соответствовало фактическому коду; кроме того, линковка выполнялась только на третьей стадии, а оба shim визуальной и декодирующей частей Qwen3-VL и пути раздельной линковки были пропущены. Теперь сборочный скрипт извлекает точный VLEN из финальных опций llc (из того же места, откуда его читает понижение VIR), а на этапе конфигурации при обнаружении противоречивых опций сборка сразу завершается ошибкой. Тесты — вторая половина этого изменения: test_buddy_rvv_vlen.py собирает библиотеки моделей для VLEN от 128 до 65536, загружается только одна — хостевая, остальные завершаются с кодом выхода 1. Документация синхронно обновлена в двух инструкциях по развёртыванию DeepSeek-R1 для A210 и K3, где чётко прописана граница «какие сборки используют точный VLEN, а какие — универсальный RVV»: ядра A210 — векторы фиксированной длины, без VIR, относятся к универсальной сборке; prefill_ime на K3 требует 1024 и относится к точному VLEN.

#1037 исправляет ошибку в другом направлении: -lower-vir-to-vector без указания rvv-vlen и без включения масштабируемых векторов задаёт размер фиксированных векторов по ширине регистров хоста, но его определение хоста покрывает только x86 (AVX2, AVX-512) и SVE; хосты RISC-V с расширением V всегда попадают в общие значения по умолчанию (128 бит, 16 регистров). Последствия проявились в тестах: с #1030 конвейер kernels при отсутствии опций llc понижает VIR в зависимости от хоста; хост riscv64 CI имеет VLEN 256, но обрабатывается как 128-битный, квадраты норм q и k разрезаются на сегменты vector<32xf32> и суммируются, порядок отличается от побитового сравнения с векторным ядром, и проверка vir decode qk_norm ... same bits даёт ложь. Автор сначала добавил изменение, которое фиксировало rvv-vlen=1024 use-scalable=false только в тестах, но сразу же откатил его — это означало бы создать ещё одно место задания VLEN помимо опций llc, что конфликтует с направлением #1032. Окончательное исправление — распознавание хоста RISC-V на этапе понижения (чтение характеристик CPU хоста и hwprobe) и задание размера по реальному VLEN.

5.2 f32 YOLOv8: сквозное прохождение VIR (#1041)

Дата: 2026-11-09 (влито 11-10 01:07)　Источник: PR #1041, коммит вливания 18c66ec

#1041 обеспечивает сквозное прохождение графа f32 YOLOv8 через VIR: сначала понижение Linalg в VIR, затем понижение VIR в векторный диалект. Ранее в этом проходе не было паттерна свёртки, а ещё три класса операторов в графе сразу падали — одно изменение одновременно добавило свёртку и эти три класса. Масштаб: четырнадцать файлов, добавлено тысяча шестьсот сорок шесть строк, удалено сто пятнадцать строк, тринадцать коммитов.

Покрыты оба семейства свёрток: двумерная NHWC с HWCF и двумерная NHWC с FHWC. Векторизация разворачивается по выходным каналам F; для каждого (kh, kw, c) входной элемент транслируется в один vir.fma на каждый выходной пиксель, поэтому каждое векторное обращение непрерывно и нет межlane-редукции — редукция требует горизонтальных инструкций и последующего дерева свёртки, что заметно дорого при узком VLEN; цена — фильтры FHWC сначала параллельно копируются в буфер HWCF, лишняя пересылка в обмен на непрерывный доступ во внутреннем цикле.

Три ранее падавших класса операторов также добавлены: вход ранга 0 (memref<f32> напрямую в linalg.generic даёт invalid reassociation в memref.expand_shape; исправлено загрузкой один раз с последующей трансляцией), linalg.reduce с сохранением последнего измерения (например, DFL softmax 1x16x4x2100, dimensions=[1], комбинация addf и maximumf), именованные операторы, читающие linalg.index (например, linalg.map iota в upsample). Картина на реальном железе ясна: на K3 исходный выход f32 YOLOv8 pose меняется не более чем на 6e-5, расхождение с PyTorch остаётся в пределах 6e-4 (bus) и 8e-4 (zidane), как и до изменения; результаты детекции модели detect не меняются, скорость не падает; выход f32 и динамической библиотеки IME побайтово совпадает с версией до изменения.

5.3 YOLOv8 в rax: детекция и поза на матричном движке K3 (#1042)

Дата: 2026-11-10　Источник: PR #1042

#1042 подключает Ultralytics YOLOv8 к формату rax в buddy-cli: yolov8n detect (восемьдесят классов COCO) и yolov8n-pose (семнадцать ключевых точек), вход 320x320. Модель f32 идёт через понижение VIR; если в спецификации указано ime: true, запускается матричный движок SpacemiT K3.

Две правки, добавленные на этапе ревью, информативнее самой модели. Первая — проверка весов: в манифесте есть params_size, раннер требует соответствия файла весов ему; ранее слишком короткий файл весов приводил к чтению моделью за границей буфера; также требуется, чтобы раннер принимал только rax-пакеты, поскольку при отдельной передаче библиотеки и весов модель позы запускалась с параметрами модели детекции. Вторая — копирование TCM: TCM-копия весов IME кэшируется по адресу весов; при чтении новых весов в уже освобождённый буфер происходило попадание в старую копию; теперь после каждой загрузки весов вызывается функция инвалидации на стороне ядра. В спецификации одновременно сохраняются params_size и ime_params_size, так что при ime: false всё ещё можно собрать версию f32 — один и тот же граф, два пути бэкенда, одна сравнимая базовая линия.

7. Наблюдение тенденций

7.1 Цепочка релизов опережает функциональность: на этой неделе чинили «можно ли собрать пакет»

В недельном наборе коммитов triton-riscv только #110 (бэкенд AMD) является функциональным изменением, остальные #101, #102, #105, #107, #111, #112, #113 целиком относятся к цепочке релиза: регистрация бэкенда в wheel, локальная сборка библиотеки AMD codegen, приоритет wheel в README, порядок поиска lit, извлечение git-аутентификации, предпосылка torch в разделе AMD. Вместе с сокращением wheel в #116 и -O3 в #117 результат работы этого репозитория за неделю можно обобщить как «сделать путь установки воспроизводимым, загружаемым и проверяемым».

Это не единичное явление: основное содержание ruyi 0.54.0 — тоже «перед установкой сначала определить, можно ли установить», #56 в pytorch закрывает «прохождение с нулевыми тест-кейсами тоже считается зелёным», а ночная сборка buddy-mlir восполняет шестидневный пробел в выпуске пакетов. Четыре репозитория на одной неделе делают однотипные вещи, что показывает: этот стек уже перешёл от «доказательства работоспособности» к стадии «доказательства поставляемости».

7.2 Покрытие важнее производительности: критерии 393→0, 2→0, 179→0

На этой неделе из семи коммитов buddy-mlir только #1055 напрямую меняет выбор инструкций, остальные шесть подключают к векторному пути формы, ранее остававшиеся в циклах: маски i1, математические функции только из libm, bf16, виды редукций, заполнение rank-0, целочисленное матричное умножение. Критерием оценки таких изменений должно быть «сколько ещё осталось путей linalg или скалярных путей», а не результаты бенчмарков — снижение 393 до 0, 2 до 0, обнуление 179 файлов с ошибками — всё это в рамках данного критерия.

В сравнении с понижением разрядности остатка strip-mined в #1050 днём ранее разделение труда двух дней совершенно ясно: сначала заставить векторный цикл заполнить все дорожки (производительность), затем дать всем операторам возможность войти в векторный цикл (покрытие). Обратный порядок привёл бы к бесполезной работе — цикл полной ширины есть, а операторов внутри всё те же несколько.

7.3 VLEN 1024 становится общей точкой давления компилятора и среды выполнения

За неделю три изменения напрямую указывают на VLEN 1024: проверка на этапе загрузки (#1032), потеря дорожек в редукции (#1051), остаток strip-mined (#1050). Общее в них то, что один и тот же аппаратный факт повторяется на разных уровнях — prefill_ime у K3 обязан быть 1024, на ядре A100 16 значений f32 и есть полный вектор, форма vector<[1]xT> на VLEN 128/256 вообще недостижима.

На той же неделе на стороне апстрима появился тот же сигнал: в списке ревью V8 появилось «Allow vlen=1024» (CL8585179). Это показывает, что длинные векторы перестают быть локальной конфигурацией отдельной платы и начинают входить в общие пути среды выполнения и браузера. Отсюда и риск — runner riscv64 в CI имеет VLEN 256, а отгружаемое оборудование — 1024, покрытие тестами у них естественно не совпадает; дефект вроде #1051, «в CI всё зелёное, на плате всё неправильно», — именно продукт такого несовпадения.

7.4 Стоимость проверки молчаливых неверных значений достигла порядка полного перебора входов

#1054 прогнал все 2^32 значений f32 для truncf и все 2^16 значений bf16 для преобразований и знаковых операций; #1055 побитово сравнил развёртывание fmaf на 4M дорожек; критерий приёмки #1041 — «побайтово идентично до изменения»; критерий приёмки #1051 — 25 тестов редукции из неправильных стали правильными. Способы проверки у четырёх коммитов разные, но все отвечают на один вопрос: правилен ли результат, а не быстр ли он.

Причина тоже ясна: почти все исправленные за неделю дефекты — это «не падает, а считает неправильно» — модель, собранная под точный VLEN, молча ошибается при смене оборудования, у масштабируемого erf половина дорожек обнуляется, в редукции остаётся только lane 0, размер маски считается побитово, что даёт шестнадцать групп регистров. Падения легко обнаружить, неверные значения — нет. Когда стоимость проверки возрастает до порядка полного перебора входов, это означает, что стек уже относится к базовым операторам вроде bf16 и редукций по стандарту отгрузки.

7.5 Rolling-упаковка отвязана от месячной фиксации версий

Плотность коммитов в упаковочном репозитории openRuyi на этой неделе — самая высокая за последнее время (пик за день — тридцать шесть коммитов, четыре линии KDE, безопасности, инструментальной цепочки и устройств идут параллельно), а видимый извне месячный релиз по-прежнему стоит на 2026.09. Эти две вещи не противоречат друг другу: rolling-упаковка и месячная фиксация изначально две разные линии, ежедневные обновления показывают, что инженерия движется, отсутствие релиза — что застрял процесс выпуска или цикл проверки.

Стоит отметить два новых управленческих репозитория этой недели: репозиторий спецификаций release записывает номера требований и приоритеты в виде процесса, ruyi-deck позиционируется как «операционная консоль репозиториев и релизов». Оба не производят код, но указывают на один и тот же пробел — месячный релиз должен выходить через несколько репозиториев: упаковочный, зеркала, прошивки; не хватает не коммитов, а той операции, которая сводит коммиты в один пригодный к выпуску релиз.

7.6 «Можно ли установить» впервые становится вычислимым фактом

ruyi 0.54.0 превращает совместимость ELF ABI в трёхзначное определение (совместимо, несовместимо, не определено) и раскрывает его в трёх местах: list, install, admin check-abi. Значение этого не в самой функции, а в том, что «запустится ли этот пакет на моей машине» превращается из опытного суждения в данные, которые можно запросить, сравнить и использовать для диагностики.

Для RISC-V это особенно важно: один и тот же предкомпилированный бинарник ведёт себя по-разному на хостах с разными комбинациями расширений и разным ABI плавающей точки, раньше приходилось действовать наугад. Трёхзначный дизайн к тому же оставляет категорию «не определено», не позволяя считать неизвестное несовместимым — это различие определяет, пригоден ли инструмент в реальной среде. Следующий шаг для наблюдения — охват sidecar: какие пакеты дополнены информацией об ABI, какие остаются «без информации»; упомянутое в выпуске 080 дополнение packages-index информацией о совместимости ABI для части пакетов — продолжение этой линии.
