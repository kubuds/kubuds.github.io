今日重点：community 一次合入 20 份 FEP，FlagOS 2.2 的特性清单与发布边界同时落定

日期：2026-09-17　来源：community FEP 目录、FEP-0099 算子库、FlagOS 2.2 发布时间表

09-17 23:55 至 23:56 的一分钟内，community 仓库连续落下 20 条提交，全部以 FEP(sig-...) 为前缀，编号从 0085 排到 0100，分属算子、编译器、框架、训练、网络、端侧、科学智能七个方向。这批文档把「2.2 要交付什么」从会议共识变成了仓库内可逐条核对的文件。

内容上最值得记录的是每个 FEP 都写了「Release Boundary and Evidence」一节，即该方向在 2.1 的基线版本、在 2.2 候选（RC2 清单）里的版本、以及开发窗口，并在结尾交代哪些部分有代码对应、哪些仍只是路线图。以算子库为例，FEP-0099 把 2.2 的算力目标写成四条：算子总量推到 635 个（其中 301 个由 KernelGen 工作流产出）、注意力类算子对齐英伟达先进水平并跑在 5 家以上国产芯片、基于 Triton 语言扩展（TLE）的关键算子、以及低位宽与融合大核等通用优化手法；列出 2.1 基线为 FlagGems v5.3.0 等六项，2.2 候选为 FlagGems v5.4.0-rc2.post1 等，并明确开发窗口为 06-01 至 08-31。

同批文档中状态差异也写得清楚：编译器侧引入通用中间表示（Common IR）的 FEP-0095 已标记为已实现，但正文限定其范围是「昇腾 910B/910C 在 Triton 3.5 线上的概念验证」，链接到 FlagTree #974（08-13 开、08-27 合入），并声明它不等于跨硬件族的生产级统一路径；而 KernelGen 能力的 FEP-0100 主动停在草案，正文直接写明「未在公开 release 标签中找到对应的实现或实现 PR」，不把路线图当成交付。这种「同一批文档里既有已实现也有明确未实现」的写法，是本批 FEP 最实用的地方。

时间线上，这批文档落在测试与稳定期的中段：发布时间表把特性冻结定在 08-31、测试期 09-01 至 09-24、GA 定在 2026-09-28，冻结规则写明「FEP 与特性代码两扇门同时关闭，错过即顺延下一版本」。所以这批文档的功能是把已冻结的范围补齐登记，而不是往 2.2 里加新东西——距 GA 还剩 10 天。

一、开源项目进展（GitHub 动态）

窗口总览：org 内 54 个仓库中 28 个在窗口内有推送（前一期 19 个，明显放量）；单次 commit search 命中 147 条窗口内提交（两页取全量，committer-date 降序），分布于 14 个仓库：FlagGems 40、FlagFFT 21、community 19、FlagQuantum 17、Torch-FL 15、build-infra 7、FlagTree 7、FlagGems-sglang 7、FlagDNN 3、FlagCX 3、FlagAudio 3、FlagGems-vllm 3、FlagScale 1、flir 1。另有 14 个仓库在窗口内有推送但默认分支上无新提交（FlagBLAS、FlagTensor、KernelGen、KernelGenBench、Megatron-LM-FL、TransformerEngine-FL、FlagRelease、sglang-plugin-FL、FlagOS-Compressor、FlagAttention、FlagSparse 等），集中在 09-17 23:29 至 23:33 的同一分钟区间，经 git ls-remote 核验为 rc2 集成分支的创建推送——详见 1.2。

本窗口形态 = 「发布登记」+「打包与发布件」两条线：治理侧一次补齐全套 FEP 文档并固化 2.2 发布边界；工程侧的注意力明显从功能开发转向发布件本身——DEB 打包、wheel 上传通路、Nexus 制品同步、覆盖率门禁、环境变量收口，都是「能不能装、能不能发、装完对不对」层面的工作。

1.1 community：20 份 FEP 一次性合入，2.2 特性清单定稿（09-17）

日期：2026-09-17　来源：community FEP 目录、FEP 说明与版本追踪

详见「今日重点」。补充两点目录侧的事实：其一，FEP 按 SIG 分目录存放，本批新增文档落在 sig-operator（0099）、sig-compiler（0095 至 0098）、sig-framework（0086 至 0091）、sig-training（0092）、sig-kernelgen（0093、0100）、sig-network（0085）、sig-edge（0082 至 0084）、sig-ai4s（0081），一次性铺满全部活跃 SIG。其二，端侧方向的 FEP 不只写文档，还带了可执行脚本目录（fep/sig-edge/scripts/ 下的 Triton 3.7 与 arm64 推理两套），与本报告观察到的端侧路线一致。

1.2 RC2 清单与集成分支：24 个模块条目，十仓同步切出 rc2 分支（09-17）

日期：2026-09-17　来源：release-2.2-rc2.yaml、release-branch-tag 工作流

09-17 23:29 至 23:33，十个模块仓库在同一分钟区间出现推送但默认分支无新提交。用 git ls-remote 拉全量 ref 核验，确认这些仓库都已存在 0.3.0-rc2 / 0.2.0-rc2 / 0.1.0-rc2 / 2.2.0-rc2 形式的集成分支，并已打出对应的 v*-rc2.post1 标签；FlagGems 与 FlagCX 走得更前面，标签已到 rc2.post3 与 rc2.post2 一级。community 里的 release-branch-tag.yml 是这条动作链的执行者：它按 release 清单调 manage-release.py，用 release bot 身份批量创建并推送分支与标签。

清单本身也升级了：RC2 版列出 24 个模块条目，与 RC1 逐条对照可见版本线整体前移一格（如 FlagGems 由 rc1.post2 到 rc2.post2、FlagAttention 由 0.4.0-rc1.post1 到 0.4.0-rc2.post1），并在头部补充了「同一仓库拆多条目、各跟不同上游线」的写法说明。两处值得记的细节：FlagTree 因按 Triton 版本拆条，tag 格式不套用全局的 v 前缀规则；FlagScale 在 2.2 清单里的版本号是 v2.1.0-rc2.post1，已经跳出 2.0 线。

1.3 build-infra 连续两次抬版：FlagGems 到 rc2.post3、摩尔线程 FlagTree 到 0.7.0rc2（09-18）

日期：2026-09-18　来源：build-infra #925、build-infra #926、configs.yaml

沿前一日把 base 版本抬到 2.2.0 的动作，build-infra 在 09-18 07:32 与 08:35 又落两条抬版提交，都只改 configs.yaml。第一条（#925）把 flaggems 字段由 5.4.0-rc2.post2 改为 5.4.0-rc2.post3，第二条（#926）把摩尔线程后端的 flagtree 钉版由 0.6.1+mthreads3.6 改为 0.7.0rc2+mthreads3.6。同一文件头部把发布动作写成三步——更新字段、打 v<版本> 标签、结束，因此这两行改动意味着 2.2 镜像线上算子库与摩尔线程编译底座同时换到了更新一轮的候选。

把两条并排看：算子库与编译器底座都在往 rc2 的迭代位上走（post3 / 0.7.0rc2），而清单里默认的 version 字段仍停在 2.2.0——发布件还在装配，尚未正式打标。

1.4 build-infra：昇腾 FlagTree wheel 上传通路首次走通（09-17）

日期：2026-09-17　来源：build-infra #923、build-infra #924

#923 修好了昇腾 FlagTree 打包：此前两个昇腾目标一个都产不出 wheel（昇腾 3.5 在 FlagPrism 的 Metric.h 上因 uint64_t 未声明而失败），原因是打包脚本首次落地后所有修复都提交到了另一条分支、而合并走的是别的分支；本 PR 一并把两个目标文件按 CANN 版本重命名，并新增 cann8.5.0 目标。#924 随后把「上传路径尚未验证」这个悬置问题换成了实测答案：09-17 两个 wheel 都已到达 flagos-pypi-ascend 制品库，分别是 flagtree-0.7.0rc2+ascend3.5 与 flagtree-0.6.0+ascend3.2；文档同时记下昇腾节点的构建耗时（26 分钟与 14 分钟，多数花在 MAX_JOBS=32 下编译 AscendNPU-IR 与 triton）与一处环境限制：CANN 节点上的 pip 版本早于 --break-system-packages 所需版本。

1.5 FlagGems：KernelGen 单日再入库十余个 Nvidia 算子，AMD W7900D 进周测（09-17/09-18）

日期：2026-09-17、2026-09-18　来源：FlagGems #5846 分位算子、FlagGems #6312 AMD 周测、FlagGems #5731

FlagGems 本期 40 条提交是 org 内最密的一条线，其中大半是 KernelGen 工作流产出的 Nvidia 算子入库，单日新增十余个：分位与均值类（nanquantile、nanmean）、行列式对数（logdet）、极分解（linalg_polar）、循环网络反向核（GRU / LSTM 单元及其反向）、上采样反向（Lanczos 抗锯齿）、稀疏矩阵乘、特征 Dropout、打包线性层等，另有两个逐元素组合算子（and_tensor、and_scalar）与 set_ 的全部张量重载。

后端与工具侧三条：[CI] Add AMD W7900D backend to weekly test workflow 把 AMD 的 W7900D 加入周测矩阵，是较新出现的一条非国产后端线；SiliconFlow 后端新增零拷贝 real 算子并改为按调度键注册；随后一条提交把七个后端子包的 __init__.py 补齐，修的是「新增后端包未被导入链路拾取」这类结构性缺陷。另有若干门禁修补（算子导出检查、KernelGen 测试标记只扫 PR 新增行）。

1.6 FlagTree：DEB 打包与 Nexus 发布并入 build-infra 共享工作流（09-17/09-18）

日期：2026-09-17、2026-09-18　来源：FlagTree #1063、FlagTree #1066、FlagTree #1082、FlagTree #1170

FlagTree 本期七条提交里有三条是发布件工程：把发布包改用 build-infra 的共享工作流推到 FlagOS Nexus 制品库（#1063）、给 DEB 打包矩阵加一行 ubuntu22.04 / python3.12 以覆盖 ABI 组合（#1066）、以及在 DEB 包里剥掉 libtriton 与 libproton 的调试信息并跳过 dh_dwz（#1076）。翌日一条 Bump packaging baseline to 0.6.1 and plumb the wheel version 把打包基线与 wheel 版本号打通（#1082），使产物版本不再手工维护。

编译器侧一条与 2.2 的 TLE 路线直接相关：tle.signal / tle.signal_wait 前端把同步范围与内存序暴露成显式参数（#1170），对应 FEP-0096 里「分布式原语与通信计算融合」所需的语义接口。

1.7 Torch-FL：环境变量面收口为 FLAGOS 一套前缀（09-17/09-18）

日期：2026-09-17、2026-09-18　来源：Torch-FL #341、Torch-FL #337、Torch-FL #320

Torch-FL 本期 15 条提交是一串连贯的重构：只保留纳入式构建开关、去掉装箱与原生模式变量（#336）、统一 SDK 发现逻辑并给 PPU 单独一个加速器标识（#337）、只接受厂商原生 SDK 环境变量（#338）、把运行时与路由的环境变量表改成与代码一致（#339），最后统一为 FLAGOS_ 前缀的一套变量面（#341）；同期一条 CI 提交把旧的 FlagGems 开关整个退场（#320）。这条线与前一期「路由切换后的后果修复」不同，是接口面的收口——把多个历史开关合并成一套契约，属于发布前把外部可见面定死。

平台侧另有两条实质修复：解耦的 DCU wheel 上让 torch.cuda 可用（#332），以及若干昇腾语义修补（布尔 SDPA 掩码、布尔掩码索引、最近邻上采样留在设备侧）。

1.8 FlagQuantum：覆盖率下限两级抬升，量子纠错记录层落地（09-17/09-18）

日期：2026-09-17、2026-09-18　来源：FlagQuantum #64、FlagQuantum #55、FlagQuantum #52

FlagQuantum 本期 17 条提交几乎全在立工程质量标准：把全局覆盖率下限从 60% 抬到 75% 并给各包设独立下限（#55）、把整个包纳入严格类型检查（#52）、把 lint 门禁扩到现代类型标注与缺陷类别规则、让每个测试文件都归入某一档标记、以及把此前被跳过的 JAX 测试接入 CI 并绑定覆盖率增益。功能侧一条是量子纠错（QEC）记录层的第一阶段（#64），实现与具体编码方案解耦；重构侧把九处孪生写入器合并成一份实现、修掉十一个嵌套函数晚绑定循环变量的缺陷。

对照 FEP-0081 把 FlagQuantum 定位在科学智能方向，这一期的重心是「先让工程基线立住」，尚未进入算法规模扩张。

1.9 FlagFFT：MUSA 与 MACA 便携三维转置验证记录，依赖统一钉版（09-17）

日期：2026-09-17　来源：FlagFFT 提交记录、FlagFFT 仓库

FlagFFT 本期 21 条提交以硬件适配分支的合并与验证记录为主：把硬件画像分支分别与 MUSA（摩尔线程）、MACA（沐曦）及 CUDA 三条特性分支合并，并为三条各留一份验证记录文档，其中 MACA 侧连着两条提交把便携式寄存器分块三维转置打开（先做平台验证、再正式启用）。性能侧一条把大型复数叶子节点改为经单个共享缓冲区暂存，并顺手修了原生精度采集的内存上界与文件缓存释放两处问题。收尾一条把 Triton JIT 运行时依赖钉到统一后端修订版，与 FlagTree 侧的版本收口同向。

1.10 FlagCX：lane mask ABI 扩到 64 位，Fedora 43 进 RPM 矩阵（09-18）

日期：2026-09-18　来源：FlagCX #607、FlagCX #561、FlagCX #562

通信库侧三条提交都在 09-18 上午集中落地：把 lane mask 的二进制接口由 32 位放宽到 64 位（#607，随芯片规模扩大而必须做的 ABI 扩容）、把独立的 Nexus 上传流程换成 build-infra 的共享工作流（#561，与 FlagTree 同一步调）、以及把 Fedora 43 加进英伟达 RPM 构建矩阵（#562）。三条合起来看，通信库这一期做的是「接口容量 + 制品产线」两件事，而非新通信算法。

1.11 FlagAudio：音频算子库首批三个 PR 合入（09-17）

日期：2026-09-17　来源：FlagAudio #5 频谱图算子、FlagAudio #4、FlagAudio #2 打包

FlagAudio 在同一个上午合并三个 PR，是这个仓库少见的功能性动作：一个用 Triton 实现频谱图算子并配套测试、一个修正增益恒等检查并把 torchaudio 导入改为延迟加载、一个把打包收尾（依赖与许可证声明）。三条都来自外部贡献者的分支，说明该仓库开始有仓库外的开发者进入；结合 FEP 清单里 FlagAudio 已列入算子层 24 个模块条目，它正在从占位状态转为有实际交付的模块。

3.1 海光：融合 rrelu 后端核入库，解耦 DCU wheel 修好 Qwen-Image（09-17/09-18）

四、总结与趋势观察

一句话：FlagOS 2.2 进入「只收 bug 修复」的测试期末段，本期真正的主角是发布件与文档——20 份 FEP 补齐特性清单，24 个模块全部切出 rc2 分支并打标，镜像线上的算子库与编译底座继续换到更新的候选位。

三条可跟踪的线：

其一，发布件工程成为主要工作面。本期 org 内 28 个仓库有推送、147 条提交，但按内容归类，占比明显偏向打包、制品、门禁与环境变量：FlagTree 的 DEB 与 Nexus 发布迁到共享工作流、FlagCX 换掉独立上传流程、昇腾 wheel 上传通路走通、Torch-FL 把环境变量面收口成一套前缀、FlagQuantum 把覆盖率下限抬到 75%。这符合发布时间表里 09-01 至 09-24 只收 bug 修复的规定，也意味着 09-28 GA 前的剩余风险主要落在「装得上、跑得对」而非功能缺口。

其二，多后端适配的边际仍在扩张，但形态分化。同一周内，摩尔线程拿到 FlagTree 0.7.0rc2 的跳级与首个带插件的 0.20.2 镜像，沐曦与摩尔线程在 FlagFFT 上各有三维转置验证，昇腾首次跑通 wheel 上传，清微把分布式原语打开，而昆仑芯主动回退了未获收益的快路径。既有「往上走」（版本与制品），也有「往回退」（否定无效优化），后者的出现通常是平台适配进入稳定期的信号。

其三，下一版的轮廓已经开始出现在文档里。RISC-V 实验性支持、操作系统打包与发行版集成、端侧 SDK、具身智能与科学智能两个工作组，都在 FEP 说明的「规划中／孵化中」表里有了位置；FEP-0098 也已把 T-Head、燧原、摩尔线程的新后端列进架构规划。等 09-28 GA 之后，这些方向大概会接手 2.2 退出主线的注意力。

待观察：（1）build-infra 的 version 字段何时从 2.2.0 走到打标一步，以及 configs.yaml 里其余后端的版本是否还有抬升；（2）2.2 GA 前后 FEP 状态从草案转实现的比例，尤其是主动停在草案的 KernelGen 能力项；（3）FlagAudio、FlagTensor、FlagSparse 等此前较静的模块是否在 rc2 线内有验收动作。
