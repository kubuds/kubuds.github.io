1.1 FlagGems-sglang：挑战赛首批赛题算子合入——7 个 SGLang Triton 算子、3 支战队、配套 benchmark 与参考实现批量落地（09-06）

来源：PR #33 silu_and_mul、PR #34 causal_conv1d_fn、PR #37 chunk_local_cumsum_scalar、PR #38 merge_state、PR #39 per_group_transpose、PR #40 mrope_fused、PR #41 fused_moe_gemm、PR #54 batch1 配套落地、PR #55 清理、赛事公告（08-21，见 CSDN）

  • 事件：09-06 20:22~20:25（北京时间），FlagGems-sglang 仓库在 4 分钟内连续合入 7 个以 [FlagOS Competition-Track1] Add ... Triton Kernel for sglang 规范命名的 PR，来源为 3 支独立贡献者 fork：yzw1128（silu_and_mul #33、causal_conv1d_fn #34）、xuanzhengdu-eng（chunk_local_cumsum_scalar #37、merge_state #38）、c2flowDS（per_group_transpose #39、mrope_fused #40、fused_moe_gemm #41）。经核验该仓库全部 42 个 closed PR 中此前无任何 Competition 合入记录——这是赛事启动（08-21 开赛公告）以来首批进入官方仓库的赛题算子。
  • 配套落地：20:35 维护者 liuhycs（Hongyu Liu）合入内部批 PR #54 “Flagos sglang batch1”（7 commits / 30 files / +2947 行），为 7 个新算子补齐 benchmark 测试（benchmark/test_.py 七组）与开发文档（docs/tasks/.md 七篇），并在 src/flaggems_sglang/reference/ 落参考实现；22:08 再合入 #55 “Remove deprecated operators and simplify benchmark utilities”，清理废弃算子、简化基准工具。此前 12:08/12:23 还有 #44 相关 code style 与 mrope_fused 测试 import 修复。
  • 赛事规则背景（08-23 日报已录开赛，此处补闭环要素）：该挑战赛为 FlagOS 开放计算全球大赛赛季二赛道一，众智 FlagOS 社区 × IEEE 联合主办、SGLang 协办、沐曦/昆仑芯/超算互联网等为产业伙伴；200+ 道真实 SGLang 推理算子赛题分 13 批次解锁（08-17 开发期启动，11-13 截止，标准批次周期 7 天），Triton/Triton-TLE 开发、多芯片统一评测按平均加速比排名；按赛规，每批次评审后拿到「攻占」荣誉的团队须在窗口期内将最优代码以规定格式 PR 至 FlagGems-sglang 并签署 CLA，代码一致性是评奖必要条件。

解读：这 7 个算子的语义覆盖面很典型——silu_and_mul（激活融合）、causal_conv1d_fn / chunk_local_cumsum_scalar / merge_state（SSM/类 Mamba 卷积与状态算子）、per_group_transpose / mrope_fused（mRoPE 组转置与融合）、fused_moe_gemm（MoE 融合 GEMM），与 SGLang 真实推理负载（混合注意力、MoE）一一对应，验证了赛题”取自真实推理业务”的设定。对 FlagOS 而言更重要的是社区共建管道的首次闭环：赛事 8 月中旬开赛后约三周，首批成果即按赛规以统一格式、统一代码规范回到官方仓库并由维护者补全测试/文档——「开放赛题→平台评测→荣誉激励→官方仓库沉淀」的算子众智循环开始产出；且每批次（后续每 7 天一评）都会带来新的 PR 合入流，FlagGems-sglang 将取代 FlagSparse 成为观察”外部贡献密度”的新窗口（FlagSparse 的 AlphaSparse 外部队列是另一条已跑通的众智通道，见 09-05 日报）。另注意 yzw1128 提交的 silu_and_mul 与 build-infra #763 中 iluvatar 的 flag_gems silu_and_mul 黑名单同名（不同仓库、不同问题域，纯属巧合）。

1.2 build-infra：镜像 tag 记录分支 per-backend 唯一化、启动页按交付记录门禁（09-06）

来源：#756（961c0fed）、#759（8f012fd4）

  • #756（12:42）：record_app_image_tag.py 原先把所有记录累积到单一共享分支 auto/app-image-tag，任一历史遗留的 open 记录 PR（任意 app/后端）都会以 rebase 冲突阻塞后续所有记录（mthreads-musa4.3.6 的记录即以 run 34009399235 失败过一次）——改为按 auto/app-image-tag-<backend>-<app-key> per-record 派生独立分支，记录互相解耦。
  • #759（14:48）：gen_data 原先仅凭 configs 的 deps_app key 是否出现来生成 app 启动页，但 key 在验证完成之前就会被加上（以触发构建），导致未验证后端（例：vllm0.20.2-iluvatar-corex4.4.0，deps_app 存在但 launch_docs=false、cells 未验证）也会泄漏出启动页并进入每个 app 镜像——改为以矩阵 launch_docs 记录为门禁，未验证后端不再生成启动页。

解读：两条都是”交付记录系统自身的可信度修复”——前者消除记录管道单点故障（共享分支互踩），后者消除验证状态与页面发布状态脱钩造成的假阳性（与 09-05 寒武纪”无语义门禁假阳性”问题同源不同层：那次是运行验证门禁缺失，这次是文档生成门禁缺失）。这类元工程修复在 2.2”验证-打 tag-记录”周期里持续出现，说明发布审计面正在被逐层收紧。
