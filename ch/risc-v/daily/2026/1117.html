今日重点：香山昆明湖三处访存队列修复与 ROB 入队选择共享（11-16）

香山昆明湖 V3 分支在 11 月 16 日落地四笔，三笔集中在访存队列。存储队列侧两笔：一笔让非对齐存储请求在出队之前一直留在非对齐队列里，避免提前释放后在途请求失去跟踪；另一笔修 16 字节跨界请求（cross16B）误用旧信息的缺陷。加载队列一笔：保留 uncache 响应，并让延迟释放的时机与响应路径对齐。第四笔在重排序缓冲（ROB）侧，把入队首部选择在同一 bank 组内共享，减少每个 bank 各自一套选择逻辑带来的面积与时序开销。

这四笔的共同点是「边界条件」。非对齐存储跨越缓存行或页边界时，请求会在流水线里停留多个周期，何时释放、用哪一份信息、响应与释放谁先谁后，任何一处错位都只在高负载或特定对齐组合下暴露；uncache 响应不经过缓存，延迟释放若与响应路径错位，就会出现读到的数据与写回的数据不一致。这类缺陷不会出现在跑分里，但会在长时间压测、虚拟化与多核一致性场景里变成偶发错误。

ROB 那笔属于另一个方向：把入队选择按 bank 共享，是在面积与频率之间做取舍。香山 11 月 12 日刚把 ROB 的功能与调试 uop 缓冲拆开，本次再动入队选择，说明昆明湖 V3 这一阶段在同时做「正确性收口」与「后端时序优化」两件事，而不是继续堆新特性。对关注开源高性能核的人，这类提交比发布会更能反映工程进度：访存队列的缺陷密度下来了，后续才能谈频率与 IPC 的进一步提升。

一、开源社区与软件生态

openRuyi 六笔：内核补丁集与配置同步刷新，Go 回填 SHA-2 AES 优化（11-16）

openRuyi 主仓在 11 月 16 日落地六笔。上午的一笔把 rpm-config-openruyi 里的工具链主版本宏限制为只作用于工具链包，避免宏扩散到无关软件包；下午五笔里三笔是主体：把 Go 的 SHA-2 AES 优化回填进发行版，linux 与 linux-lts 各一笔「刷新补丁集并刷新配置」同步落地；随后 mupdf 移除针对 python clang 的临时绕行方案，python-maturin 补上缺失的 unicode-xid 构建依赖。

Go 那笔值得单独记。RISC-V 上多数机器没有硬件 AES 指令，TLS 与对象存储的吞吐很大程度取决于 crypto/sha256 的软件实现；把上游的 SHA-2 AES 优化回填，意味着发行版开始把「加密性能」当作 RISC-V 上的一等公民，而不是等上游版本自然滚动。两笔内核刷新是同一条基线在 linux 与 linux-lts 两条线上同时维护，说明发行版对长期支持线与滚动线采用同一套补丁集，升级时不会出现某条线漏补丁。

mupdf 与 python-maturin 两笔是打包链的清理。前者移除 workaround，说明此前为绕开 python clang 问题打的补丁已经不再需要，工具链侧的问题在源头修掉了；后者是 Rust 扩展打包的典型坑，缺一个构建期依赖就会在目标机器上编译失败，这类修复对用 RISC-V 机器做 Python 开发的人比新功能更有价值。

CORE-V Wally 向量分支：基础向量访存合入，向量 LSU 仍缺（11-16）

CORE-V Wally（CVW）的 vector 分支在 11 月 16 日 17 时 08 分合入 PR #2070，标题写得很直白：「WIP：加入最基本的 load/store，等 LSU 支持向量」。作者是 eoinoconnell04，由维护者 georgiatai 合并。也就是说，这次合入的是向量访存的第一层骨架，真正的向量加载存储单元还没有到位。

这条信息的价值在于定位。RISC-V 向量扩展在开源核上的推进通常分三步：先做译码与执行单元，再做向量寄存器堆与调度，最后才做向量访存。CVW 此前的工作集中在 RVV 指令的执行侧，本次进到访存，说明前两步已有可用基础；但「WIP」与「等 LSU」两个限定词同时出现，也说明距离「能跑真实向量负载」还有距离。

需要避免的误读是把分支合入当成主线支持。CVW 的 main 分支在本窗口内没有任何提交，向量工作全部在 vector 特性分支上进行，按开源项目的惯例，这类分支可能长期存在、也可能随时重写。对使用 CVW 做教学或流片基线的团队，可以据此判断向量支持的时间表还不到可以规划产品的阶段。

difftest 一笔：指令进度检查改为可配置（11-16）

香山差分测试框架 difftest 在 11 月 16 日落地一笔，把模拟器侧的指令进度检查改成可配置项。此前的进度检查是固定策略，长回归里只能靠超时判断「跑挂了」还是「跑得慢」；改成可配置之后，可以按目标程序的指令量设置检查节奏，卡死能被更早发现，慢但正常的用例也不会被误杀。

这与 11 月 13 日的两笔是一组：先把 fork 的检查点改成 1 秒、包槽位改为 2 的 22 次方，再让进度检查可配置。三项合起来，difftest 正在从「能比对」走向「能长时间稳定跑」——对香山这种规模的设计，验证基础设施的稳定性直接决定每天能收敛多少 bug。

差分测试在 RISC-V 生态里是公共品：它不只服务香山，也被其他开源核项目借用。这类改动的收益不在单点性能，而在于把「回归跑不动」这个隐性成本降下来。

SingNova 在安防展打包四条 RISC-V 产品线，桌面工作站口径升至 256 TOPS（11-16）

新加坡公司 SingNova（南洋理工孵化，主体为 NANYANG SINGTECH）在 11 月 16 日发布通稿，称在 11 月 10 日至 12 日于滨海湾金沙举行的 Safety & Security Asia 2026 上展出四条产品线：智能视频存储服务器、AI Power Studio 桌面 AI 计算系统、AI 虚拟员工与 Storage Station 智能 NAS。通稿给出的规格是：AI Power Studio 采用 12 核 RISC-V CPU 加数据流架构，INT8 算力最高 256 TOPS，配最高 128GB LPDDR5 ECC 统一内存，可解码 128 路 1080p@30fps，带 PCIe 4.0 x16；视频存储服务器靠芯片级智能编码把视频体积压到三分之一；Storage Station 是多核 RISC-V 架构的一体化 NAS，支持 RAID-TP 与 13 级文件权限。

需要说清楚的是这条通稿的新旧程度。同一套四条产品线在 9 月 30 日的 Tech Week Singapore 通稿里已经完整出现过，当时的 AI Power Studio 口径是 200 TOPS INT8 加 32 TFLOPS FP16；本次只写「最高 256 TOPS INT8」，没有 FP16 数字，也没有解释 200 与 256 的差异来自硬件配置、稀疏算力还是不同的计数方式。因此本期不把它当作新品发布，而当作「同一产品线换到安防行业场景重新打包」。

真正有信息量的是形态。这四台设备都不是开发板：有机箱、有管理界面、有行业协议（RTSP／ONVIF、H.265／H.264）、有冗余与审计，卖的是能直接进机房的整机。RISC-V 在这里承担的是整机底座，而不是展示用的裸板；128GB 统一内存与 128 路解码的配置，指向的也是本地大模型推理与视频分析这类实际负载，而不是跑分。缺口同样明显：通稿没有说 SoC 来自哪家、价格多少、什么时候出货，12 核 RISC-V 配 256 TOPS 的组合在公开芯片里也不常见，是自研还是外购平台无法从公开信息判断。

三、国内团队深挖

算能 SG2042／SG2044 引导改造：首分区改 FAT32，内核按芯片工作区构建（11-16）

算能的 RISC-V 引导仓库 bootloader-riscv 在 11 月 16 日落地两笔，均由 SophgoChaoWei 提交。第一笔把 SG2042 与 SG2044 的第一个分区改为 FAT32；第二笔调整构建脚本，让 openEuler 内核 RPM 在按芯片划分的工作区目录树里产出，而不是共用一个输出目录。

首分区改 FAT32 是固件兼容性问题。UEFI 规范要求固件能读的分区是 FAT 系文件系统，RISC-V 服务器平台普遍走 UEFI 加 GRUB 的启动链，第一分区若不是 FAT32，固件阶段就可能找不到启动文件。这类改动看起来只是格式化参数，实际决定了「官方镜像能不能直接被固件识别」，对要装 openEuler、openRuyi 这类发行版的用户是硬门槛。

按芯片工作区构建内核 RPM，反映的是多代产品并行维护的现实。SG2042 是 64 核的上一代，SG2044 是当前的服务器级平台，两者内核配置与补丁集不同，共用一个输出目录容易出现版本串味；拆成按芯片的工作区之后，同一条 CI 可以并行出两代的内核包，出问题时也能定位到具体芯片线。

同窗口内算能的 edge 侧还有一批提交（sophon-tools 13 笔、libsophav 2.4.0、libsophon 0.4.16、cv84x6-llm-server 0.6.38），但该平台产物按仓库说明是 arm64 deb，属 ARM 边缘产品线，本期不计入 RISC-V 条目，仅在信源核查表中留记录。

日期：2026-11-16　来源：sophgo/bootloader-riscv

进迭时空四仓：编码输入改借用、视觉 tokenizer 归一、OHOS Float16 修复（11-16）

进迭时空在这一窗口动了四个仓库。多媒体库 mpp 在 15 时 08 分加入编码器的「同步输入借用」，把输入缓冲的生命周期从拷贝改成借用；视觉模型库 model-zoo-vision 在 17 时 24 分合入 PR #121，把 CLIP 与 Gemma 两套 tokenizer 收敛到公共实现；AI SDK 在次日凌晨更新 vision 子模块；llama.cpp 的 spacemit 后端在 20 时 19 分合入 PR #70，修 OpenHarmony 上 Float16 的 RTTI 加载失败。

编码器输入借用是典型的零拷贝优化。视频编码的每一帧输入都要跨用户态与驱动，如果每次都完整拷贝，带宽与延迟都会翻倍；改成借用之后，驱动直接用应用持有的缓冲区，代价是生命周期管理更严格，应用必须保证在编码完成前不释放。这类改动在 1080p 以上分辨率与多路并发时才体现出价值，也意味着 MPP 的接口语义发生了变化，下游需要跟着改。

CLIP 与 Gemma 的 tokenizer 合并，指向的是「一套模型库支持多个模型」的维护成本。此前每个模型带一份 tokenizer，词表与预处理逻辑重复，出问题要改多处；收敛到 common 之后，新增模型只需接配置。OHOS 上的 Float16 RTTI 加载失败则是 C++ 跨 ABI 的老问题：HarmonyOS 的编译器与运行库对 half 类型的类型信息处理与常规 Linux 不同，动态库加载时找不到类型信息就会失败。这条修复说明 spacemit 的 llama.cpp 后端已经在 HarmonyOS 设备上被真实使用，而不是只做 Linux 适配。

芯来 Nuclei Studio 升到 2026.10，文档站 CI 跟到 Ubuntu 26.04（11-16）

芯来的 Nuclei Studio 文档仓库在 11 月 16 日更新两笔，均来自 fanghuaqi：14 时 54 分把文档首页的 IDE 版本更新到 2026.10，15 时 21 分修复 MkDocs 在 Ubuntu 26.04 runner 上的部署。需要说明的是，这个仓库承载的是 Nuclei Studio 的供给文档、用户指南、wiki 与讨论，IDE 本身仍以二进制包发布；README 同时指出 2026.10 已是对外的最新版本，并列出 Ubuntu 20.04 下运行 riscv64 gdb 与 QEMU 需要补的库。

把文档与发布说明放在公开仓库、接受外部提 issue 与 PR，国内 RISC-V IP 厂商里做得并不多：多数厂商只发安装包，文档挂在官网，用户发现问题只能走商务渠道。Ubuntu 26.04 runner 的部署修复看似琐碎，实际是「文档能不能自动发布」的问题——GitHub Actions 的宿主机镜像升级会带来 Python 与 MkDocs 依赖变化，不跟着改就会在发布环节静默失败。

对用芯来核做产品的团队，这类维护节奏比单次版本更新更重要。工具链与 IDE 的长期可用性，取决于三五年后还能不能找到对应版本的文档与依赖说明；把供给文档纳入版本控制与 CI，是这个问题的低成本解法。

四、具身智能与机器人专章

进迭时空 realtime-link 加视频传输模块，K3 VSLAM 指南同批刷新（11-16）

进迭时空的机器人仓库 spacemit-robotics/realtime-link 在 11 月 16 日 21 时 46 分在 feat/zhangrou/add-video-transmission 分支上提交 v1.0.0 的「视频传输模块」，作者 zhangrou651。同一窗口内，spacemit-com/docs-ros 在 11 时 37 分合入 PR #236，刷新 K3 平台的 SpacemiT VSLAM 指南。

realtime-link 从名字看是机器人侧的实时链路组件，此前的能力集中在控制与状态通道；加入视频传输意味着它开始承担感知数据的回传。对机器人系统，视频链路与控制链路的要求相反：控制要求确定性低延迟、数据量小；视频要求高带宽、可丢帧、能自适应码率。把两者放进同一个组件，做法上要么分通道调度，要么在传输层做优先级，具体实现要等代码公开更多细节。

K3 VSLAM 指南刷新则是软件成熟度的信号。VSLAM 在 RISC-V 上不是跑不通的问题，而是「帧率、精度与功耗能不能同时达标」的问题；厂商愿意把 K3 的 VSLAM 配置写成指南，说明这条链路已经在真实硬件上跑过一轮，能给客户复现的步骤。两份材料放在一起看，进迭时空在机器人侧补的是「视频进、位姿出」这一段，正好是 VLA 模型之前的感知前端。

机器人算力栈的三段与两种载体：链路、SLAM 与模型推理各归其位（11-16）

把今天的几条提交按数据流排一遍，机器人侧算力可以分成三段。第一段是视频链路：相机采到的帧要低延迟送到算力单元，对应 realtime-link 新增的视频传输。第二段是 SLAM 与几何：把帧变成位姿与地图，对应 K3 的 VSLAM 指南。第三段是模型推理：视觉语言动作模型在本地跑，对应 llama.cpp 的 spacemit 后端与视觉模型库的 tokenizer 归一。三段对硬件的要求不同——链路要 I/O 与实时性，SLAM 要单核性能与内存带宽，推理要矩阵算力与容量。

载体也在分化。一类是桌面或机架形态的工作站：SingNova 的 AI Power Studio 用 12 核 RISC-V 配 128GB 统一内存与 128 路解码，卖点是本地跑大模型加视频分析；另一类是嵌入式盒子：算能的 CV84X6 LLM Server 打成 arm64 deb，走 OpenAI 兼容接口加 Web 管理页，卖点是插上就能用。前者靠容量与带宽，后者靠功耗与集成度，两者都不是「一颗芯片解决所有事」的思路。

RISC-V 在这个分层里的位置要说准确：目前强在链路与 SLAM——K3 这类平台有真实的多核与向量能力，能承担前端处理；弱在推理侧的软件栈——llama.cpp 的后端还在修 ABI 级问题，模型库的 tokenizer 才刚归一。换句话说，机器人要的是「三段都通」，而 RISC-V 现在通了两段，第三段在补。

五、总结与趋势观察

今天没有发布会，四件事都属「补课」：香山在收访存队列的边界缺陷，openRuyi 在刷内核与加密性能，CORE-V 在补向量访存的第一层骨架，进迭时空在补 HarmonyOS 的 ABI 问题与机器人视频链路。这类提交不会出现在新闻标题里，但决定芯片到手之后能不能直接开发、能不能长期维护。

第一条判断是开源高性能核进入了「正确性收口」阶段。香山这一周的提交从 CI 拆步、文档治理转回访存队列的具体缺陷，说明昆明湖 V3 的功能面已经冻结，接下来拼的是缺陷密度与频率。对使用开源核做产品的团队，这个阶段反而是介入的好时机：接口稳定、缺陷在被系统性清理、验证基础设施同时在变强。

第二条判断是发行版开始把性能当作一等公民。openRuyi 回填 Go 的 SHA-2 AES 优化、同步刷新两条内核线的补丁集，做法与成熟发行版一致：不等上游自然滚动，而是把自己关心的路径提前拉进来。RISC-V 在通用算力上短期追不上，但在「特定路径够快」这件事上可以靠发行版补齐，这是国内发行版能做出的差异化。

第三条判断是机器人侧的竞争点从芯片转向链路。今天进迭时空的两笔都在「视频进、位姿出」这一段，而不是再报一颗新芯片；SingNova 与算能的两种载体也说明，整机形态与软件集成度比峰值算力更能决定能否落地。对做具身智能的团队，选型时要问的第一个问题不再是「多少 TOPS」，而是「视频链路、SLAM、推理三段里，哪一段需要我自己补」。

近三日趋势：整机换架构、开源核补验证、标准争矩阵扩展（11-14 ~ 11-16）

把 11 月 14 日至 16 日连起来看，三条线各自推进。整机侧，Purism 在 11 月 14 日启动 Librem 5 v2 众筹，把下一代 Linux 手机的主控换成进迭时空 K1，1599 美元的众筹价与 2028 年的交付时间表同时公开；11 月 16 日多家外媒继续跟进，口径与官方页面一致，本期不重复收录。

开源核侧，FURSOY 在 11 月 15 日公开 fursoy-cpu，一颗能启动 Linux 6.6.50、在 45nm 下收敛 500MHz 的乱序 RV64 核，交付物包含 SBI 固件、设备树与 Sail 差分验证脚本；同一天香山在收访存缺陷、CVW 在补向量访存。三件事指向同一个结论：开源核的竞争已经从「能不能跑」转到「验证与可复现」。

标准侧，FPRox 在 11 月 15 日把 RISC-V 矩阵扩展的五条提案放在一起比较——点积、胖内积、外积三类布局对应 IME、VME、AME 与 Zvdot4a8i、Zv[b]dota。提案多本身不是问题，不兼容才是：如果最后没有收敛到主线，算子库与编译后端就要为每种组合维护一条路径。这三条线共同的约束仍然是软件栈，而软件栈的进度，正体现在今天这类看似琐碎的提交里。
