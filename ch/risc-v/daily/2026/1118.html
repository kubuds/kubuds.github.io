今日重点：赛昉 JH-B100 量产交付，RISC-V 服务器 BMC 进入客户整机（11-17）

11 月 17 日，赛昉科技宣布其基于 RISC-V 架构的服务器 BMC（基板管理控制器）芯片昉·惊鸿-B100（JH-B100）已实现量产并交付客户。官方口径是：该芯片已通过多家服务器制造厂商及互联网企业的产品导入与审查流程，搭载它的客户服务器产品即将进入量产阶段。出货量、客户名称与排产时间均未披露。

规格按赛昉官网产品页：四核自研 RISC-V 内核（19200 DMIPS）配一致性片上网络（NoC），兼容 DDR4-3200 与 DDR5-4800，集成 PFR（平台固件韧性）与 PROT 功能，支持国密 SM2／SM3／SM4、安全启动与 DICE；接口含双路 PCIe 4.0 端点、全功能 eSPI Slave、PECI、I2C／I3C、USB 3.2 Gen1、SGPIO、CAN-FD、IPMB、MCTP、NCSI，内置两路 LTPI 控制器以支持双节点管理；配套 SDK 遵循 Yocto 标准，可直接对接 OpenBMC。应用面除 CPU 服务器主板，还包含 AI 基础设施里的计算托盘、交换托盘、冷却液分配单元与电源架。

这条消息的分量在「位置」而不是「性能」。BMC 不参与计算，但每台服务器要一颗，长期由 Arm 与 8051 类控制器把持；此前 RISC-V 在这个位置只有送样与验证，没有量产交付。选它作突破口的逻辑也清楚：性能要求远低于主 CPU，软件栈（OpenBMC、Yocto）成熟，客户导入的验证成本可控。赛昉给出的生态背书是 Intel 与 AMI——前者完成 CRB 平台上的 Intel CPU 管理功能验证，后者把 JH-B100 的 SDK 集成进 BMC 固件产品 OneTree；这两项在此前的 Intel Connection 与滴水湖论坛上已披露，本期是首次落到「量产交付」这一步。

克制地看，仍有几处需要观察。其一，「即将进入量产」是客户侧口径，真正放量取决于整机厂商的排产，而 BMC 的采购决策往往跟着主 CPU 平台走；其二，赛昉没有给出货量，无法判断这是小批量交付还是规模出货；其三，RISC-V BMC 的长期考验在固件维护与安全更新，OpenBMC 的社区支持度、CVE 响应速度都要跑过一两个产品周期才看得出。同一天工信部主管媒体与多家行业媒体转载了这条消息，把它与「十五五」规划中「推进第五代精简指令集研发与产业化」的条目放在一起叙述，政策语境与商业进展被绑定的意味明显。

一、开源社区与软件生态

openRuyi 十九笔：OpenSBI 升到 1.9，引入 OpenSSL 3.6.5（11-17）

openRuyi 主仓在 11 月 17 日全天落 19 笔软件包提交。固件侧把 OpenSBI 更新到 1.9；加密栈新增 openssl-3 并带 3.6.5 版本，同时把 CI 构建改为优先使用 OpenSSL；基础库把 krb5 升到 1.22.3，并修 dnf5 在 json-c 0.19 下的构建；桌面侧给 openruyi-desktop-setup-kde 补了依赖声明。下午 15 时 03 分的一批集中在 Python 与 AI 推理栈：huggingface-hub 1.32.0、sentence-transformers 6.3.0、xgrammar 0.2.9（标注安全修复）、apache-tvm-ffi 0.1.12、click 8.5.1、hf-xet 1.5.2，另新增 rust-tokio-with-wasm-proc 0.8。

三件事值得单独看。OpenSBI 1.9 是固件基线跟进，决定新平台能不能在 M 态就跑起来；引入 OpenSSL 3.6.5 并让 CI 优先用它，意味着发行版在摆脱 1.1 系的兼容包袱，代价是所有依赖它的包要重编一遍；xgrammar 与 tvm-ffi 进仓库，说明「结构化输出」与「TVM 接口」这类 AI 推理依赖已被划进发行版的范围，而不只是用户自己 pip 装。官网新闻页最新仍是 10 月 19 日的两篇（生态基础设施、Ruyi Firmware）与 2026.09 版本发布，窗口内没有新版本。

revyos/linux 重整 7.3.y 配置基线，一次落 20 笔平台补丁（11-18）

revyos/linux 在 11 月 18 日凌晨 4 时 13 分一次性把 20 笔配置提交推到 revyos/7.3.y 分支——20 笔的提交时间完全相同，作者日期最早可追到 2025 年 12 月，属分支重整后的批量落地，不是一夜之间做完的工作。内容按平台逐条开启：ESWIN EIC7700、UltraRISC DP1000、SpacemiT K3 与 K1、T-Head TH1520、Sophgo SG2042／SG2044，另加 Picoheart errata 开关与一组通用选项；同时新增 cross/native 构建 CI、linuxboot 配置与 debian_defconfig，并把包名规则改成用主版本号。

配置文件一次对齐六家平台，说明 RevyOS 的定位已经从「给某块板子做发行版」变成「一套内核配置覆盖多条 RISC-V 产品线」。对下游厂商，这类改动的价值在于少改配置：拿到新板子先看 defconfig 里有没有自己的 SoC 开关，比从零写 dts 快得多。风险也在这里——同一个分支同时承载六家平台的 errata 与 hack（提交里有强制 xe 驱动走 DG1／DG2 这类 workaround），任何一家的改动都可能影响其他家的回归，CI 加了 cross/native 两套构建算是补了一道保险。

CORE-V 两笔：RVFI CSR 日志合入，CVW 回退依赖清理（11-17）

openhwfoundation/core-v-verif 在 11 月 17 日 6 时 20 分合入 PR #2675（来自 ankit-cybertron 的 rvfi-csr-logging），给 RVFI 接口加上 CSR 日志。同一天，CVW 先合入 PR #2099（清理 uv.lock 的依赖告警并启用 uv 更新），随后又用一笔提交把它整体回退。

RVFI 是 RISC-V 形式验证与差分测试的观测口：它把每条指令的 PC、寄存器读写、内存访问暴露给验证器，此前 CSR 状态不在其中，特权态的行为只能靠间接手段比对。加上 CSR 日志之后，mstatus、mtvec 这类寄存器的逐指令变化可以被直接检查，对验证异常与中断路径尤其有用。CVW 的回退则是另一类信号——依赖告警清理看似无害，一旦改动锁文件与更新策略，回归环境的可复现性就受影响，所以宁可回退也不带着不确定性往前走。

Radxa Linkr 集中放出 v1.4.2 至 v1.6.0，插件中心与 H.265 编码到位（11-17）

Radxa 的浏览器远程管理产品线 Linkr 在 11 月 17 日 15 时 2x 分集中放出四个版本：v1.4.2、v1.5.0、v1.5.2、v1.6.0，四个 release 的发布时间相隔不足五分钟；同日还新建了 harness-linkr 仓库并落了 Initial commit。四个版本同日出现，更像仓库公开后把历史版本一次性补录，不宜读成一天连发四版。

按发布说明，v1.6.0 新增 H.265 编码、自定义 HTTPS 证书、双向剪贴板同步（需在受控机安装 Linkrd 插件附带的可执行文件）、720p 180fps 的 EDID 预设与水印开关；v1.5.0 引入插件中心（上传、安装、启停、卸载）、ZeroTier 与 EasyTier 两个组网插件、截图 OCR、实验性 IPv6，并给 Agent API 加了切换控制；v1.5.2 支持 FN 键双击切换 Wi-Fi 热点、按所连频段自动选 5GHz 或 2.4GHz，并修 Radxa Dragon Q8B 作视频输入源时无法切分辨率；v1.4.2 给 H.264 WebSocket 模式补了音频、默认关闭 Wi-Fi 降功耗、加入实验性触摸输入。

把这四个版本连起来看，Linkr 的走向是「可编排的带外管理」：插件中心解决功能扩展，Agent API 解决外部调用，组网插件解决跨网段接入，OCR 与剪贴板解决人在环路里的操作。发布说明没有披露硬件形态与所用 SoC，本报告不对其架构下判断。

三、国内团队深挖

进迭时空 xslim：量化栈在 agent 分支连推五笔（11-17）

进迭时空的模型压缩工具链 xslim 在 11 月 17 日于 agent/feat/operator-layer-quantization 分支连推五笔（8 时 46 分至 19 时 35 分），全部围绕量化策略：按用户数据选择逐层校准方法、解析并校验统一的精度计划、校验融合来源与有效精度边界、带预算的自动混合精度、任务指标搜索与受控的局部 fp16。另一条分支 agent/chore/add-agent-harness 在 11 月 13 日加了仓库级 agent harness 与贡献指南。

这些提交的方向是「把量化从手写配置变成搜索」：给一个精度预算与一个任务指标，让工具自己决定哪些层用什么精度，而不是每层手工填表。同时反复出现 provenance 与 fused 校验，说明他们在真实模型上吃过融合算子精度对不上的亏——量化后的卷积被后端融合，实际生效的精度与配置文件写的不是一回事，不校验就会出现「配置说 int8、跑的是 fp16」的静默偏差。agent 分支这个命名也值得注意：工具链开始按「给自动化代理用」来组织代码与技能，而不是只面向人。

同一天，spacemit-com/onnxruntime 合入一笔上游改动（按 EP 优先级选择模型包变体），属同步上游，不涉及 RISC-V 专属改动；xslim 主分支窗口内无提交，进展都在特性分支上。

算能 sophon-tools：se-rag-core 补分层模型配置与有界回退（11-17）

算能的 sophon-tools 在 11 月 17 日 13 时 30 分提交一笔 feat(se-rag-core)：分层 OpenAI 配置，加内置网关的 CF 优先与有界回退（提交号 MYS-2924／MYS-292x）。改动集中在 RAG 组件的模型接入层——把 OpenAI 兼容配置拆成多层（默认、环境、部署级），并按优先级合并；网关部分优先走 CF（Cloudflare）线路，失败后按有限次数回退。

这条的技术含量不高，但指向明确：SE 系列（SG2042／SG2044 服务器）上的 LLM 应用栈在往可运维走。分层配置解决的是「同一套代码在开发、测试、客户现场用不同模型端点」的问题；CF 优先加有界回退解决的是跨境访问的稳定性，回退次数要有界，否则一次故障会把请求打到所有备用线路上。需要说明的是，这是应用层工具，不是芯片或驱动；本报告收录它，是因为它反映算能在服务器整机之外补的是「开箱能用的 LLM 服务」这一段。

进迭时空机器人栈接入 Hiking 感知式运动策略，深度图经 ZMQ 进策略环（11-17）

11 月 17 日 16 时 04 至 05 分，spacemit-robotics 的两个仓库各合入一笔：humanoid_common 的 PR #33「support Hiking perceptive locomotion」与 humanoid_unitree_g1 的 PR #20「add Hiking perceptive control simulation」，作者 chenzhaoqi。humanoid_common 的改动共 16 个文件、新增 938 行，内容包含：Hiking 策略适配层（深度编码、观测历史、关节映射、模型校验和）、用离屏 EGL 渲染把 MuJoCo 相机深度经 ZMQ 发布、进 RL 之前校验深度元数据与时间戳与历史长度、支持在线 RL 交接（动作历史初始化、就绪检查、准备反馈）、交接失败或超时时保留当前策略、新增感知构建依赖并在 RL 头文件变化时重建消费方。

从提交口径看，这套接口对应的是公开的 Hiking 感知式运动策略（Hiking in the Wild，清华 IIIS 与上海期智研究院，Unitree G1 加前视深度相机，深度 60Hz、策略 50Hz）；官方未说明适配对象的确切来源，此处为按提交内容的判断。工程上值得记的三点：交接失败保留旧策略，是安全兜底，避免策略切换瞬间机器人无控制；模型校验和，是防止策略文件被替换或版本错配；头文件变化触发重建，是因为他们踩过 C++ 结构体布局不一致的坑——提交注释写明，分阶段安装会保留源文件时间戳，RL 头文件改了但缓存对象没重编，链接出来的结构体布局就对不上。

把第三方策略做成可替换的适配层，是机器人栈走向「策略生态」的必经一步：芯片厂不可能自己训练所有策略，能做的是把感知输入、策略推理、动作交接这三段标准化，让外面训练好的策略接进来就能跑。K3 这类平台在这个位置上提供的是向量与多核能力，以及跑 MuJoCo 与深度渲染的余量。

日期：2026-11-17　来源：humanoid_common PR #33、humanoid_unitree_g1 PR #20

manipulation 与 manifest 收尾：补 motion-completion 文档，仿真相机输出入忽略表（11-17）

同一天，spacemit-robotics 的 manipulation 与 manifest 两仓共落六笔。manipulation 侧：PR #4 合入 motion-completion 相关文档，PR #5 与 PR #6 分别把 MuJoCo 日志与仿真相机帧目录加进忽略表；manifest 侧合入 PR #33（refactor/finish-manipulation）。

这些都是整理性改动，但顺序值得注意：先补文档、再清产物，通常是「一段工作收口、准备交接或对外」的动作。对操作（manipulation）方向，motion-completion 文档说明他们在意的不是单次抓取成功，而是动作序列的补全与衔接；把仿真相机帧排除出版本库，则是因为这类数据每天几十 GB，误提交一次就把仓库撑爆。

日期：2026-11-17　来源：spacemit-robotics/manipulation PR #4、spacemit-robotics/manifest

五、总结与趋势观察

今天的主线只有一条：管理面先落地。赛昉 JH-B100 的量产交付，是 RISC-V 第一次在数据中心拿到「量产交付」而不是「送样验证」的位置。BMC 不参与计算，但每台服务器要一颗、量随整机走；它的性能要求远低于主 CPU，软件栈有 OpenBMC 与 Yocto 兜底，客户导入的验证成本可控，而供应链上长期只有 Arm 与 8051 两类选择。选这个位置突破，比在服务器主 CPU 上正面对撞现实得多。

第二条判断是软件侧今天在「补版本」而不是「发新东西」。openRuyi 把 OpenSBI 推到 1.9、引入 OpenSSL 3.6.5、把 xgrammar 与 tvm-ffi 纳入仓库；revyos 重整内核配置基线，把六家平台的开关一次排好。两件事都不会上新闻标题，但它们决定客户拿到板子之后能不能少改配置、能不能直接用现成的推理栈。RISC-V 的软件差距，很大一部分就藏在这种日常对齐里。

第三条判断是机器人侧的进展落在「适配层」。进迭时空把 Hiking 感知策略接进 humanoid_common，用 ZMQ 传深度图、用校验和验模型、交接失败保留旧策略——这些是工程细节，不是论文指标，但它们决定第三方策略能不能在 K3 上跑起来。芯片厂做不了所有策略，能做的是把接口标准化，这件事今天有了具体动作。

近三日趋势：管理面先落地，软件栈补版本，机器人栈补感知（11-15 ~ 11-17）

把 11 月 15 日至 17 日连起来看，三条线各自推进。整机与芯片侧，Purism 在 11 月 14 日启动 Librem 5 v2 众筹、11 月 17 日发布正式新闻稿把交付口径细化为「众筹结束后 14 至 15 个月」；赛昉在 11 月 17 日把 RISC-V BMC 推到量产交付。两条都在「RISC-V 进入整机 BOM」这件事上加了砝码，一条是消费端的手机，一条是数据中心的服务器管理芯片。

开源核与验证侧，11 月 15 日 FURSOY 公开能启动 Linux 6.6.50 的乱序 RV64 核，11 月 16 日香山在收访存队列缺陷、CVW 在补向量访存，11 月 17 日 core-v-verif 把 CSR 状态纳入 RVFI 日志、香山做命名重构。四件事的共同点是从「能跑」转向「可验证、可维护」，这也是开源核进入产品视野的前提。

软件与工具链侧，openRuyi 连续两天在做版本跟进与配置对齐，进迭时空在量化工具链上做自动化搜索、在机器人栈上做策略适配。三条线合起来看，架构叙事的窗口在收窄，工程兑现的窗口在打开：接下来半年，能决定 RISC-V 位置的不是又一颗新芯片的发布会，而是这类交付、配置与适配能不能持续。
