今日重点：进迭时空开源 RVISA 虚拟 ISA 规范工作草案，首轮补入 IME/VME/AME 三套映射与 blocked MMA（11-04 建仓、11-05 提交）

进迭时空（SpacemiT）在 GitHub 上开出一个新仓库 spacemit-com/rvisa，提出 RVISA（RISC-V Virtual ISA，RISC-V 虚拟指令集架构），为 RISC-V 的标量、向量与矩阵计算定义一层虚拟指令记法。仓库 11 月 4 日建起，11 月 5 日一天内推了三笔实质提交：先落地 MkDocs 文档站与 Pages 发布流程，再补入 RVISA 记法的示例源形与首批 IME/VME/AME 映射，最后由 PR #2 定义「程序员可表达」的 tile 布局与分块矩阵乘（blocked MMA）。当前规范版本号为 0.2.0。

RVISA 的定位写得比较清楚：它刻意站在 NVIDIA PTX 之上、cuTile 之下。往上看，它不绑定任何一门前端语言，源语言前端实现明确被排除在本版范围之外；往下看，它不直接规定某颗芯片的指令编码，而是把「目标映射」做成版本化的 profile，逐条声明映射到哪一组寄存器类、寄存器组与指令序列，并附上该 profile 对应的上游修订号与验证证据。记法形式上参照 RVV Intrinsics 的做法表达类型化操作、操作数角色与寄存器组约束，tile 从一维到 N 维，reshape 与轴置换必须保持元素位置，布局由线性布局推导。

最能说明它想解决什么问题的是「可表达性要求」这一条：任何对 RVISA tile 计算的优化，都必须能被程序员在记法层写出来。这条约束针对的正是矩阵扩展落地时最常见的失败方式——编译器偷偷做了一套向量化，程序员既看不见也改不动，换一颗芯片就得重写。RVISA 试图把这一层显式化，让同一段记法在不同实现上走不同的映射 profile，而语义保持一致。

需要说清楚的是成熟度：规范状态文件自己写明这是 working draft，不是 RISC-V International 的已批准规范。核心模型、类型与操作数规则、tile 布局与优化、关键操作签名已给出具体契约，但目标映射档案只登记为草案、尚未建立实现一致性证据；MLIR dialect 标注为 TBD；参考负载只有 .rvisa 记法的源形，不能编译执行；可执行一致性工具同样是 TBD。仓库另有 RFC 0001 至 0003 三份草案，分别覆盖指令与寄存器映射契约、核心类型与操作契约、程序员可表达的 tile 布局。

放到今天的产业坐标里看，这与同一批次 Quintauris 在 MCU 侧做的事是同一个逻辑的两种表现：开放指令集带来的碎片化，最终要由某一层稳定的「软件目标」来收敛。MCU 侧收敛在二进制兼容与中断语义上，AI 矩阵侧收敛在虚拟记法与映射契约上。差别在于，EM-Altair 背后是六家车规与嵌入式大厂的合资公司，RVISA 目前是单家厂商主导的工作草案——它能否被上游矩阵扩展的讨论接住，要看后续是否有人把 IME、VME、AME 三条线的实现证据填进那张映射表。

今日重点：Quintauris 发布 EM-Altair，MCU 级 RISC-V 标准化平台以 RV32IM 为基线做二进制兼容（11-03 发布、11-05 报道）

Quintauris 11 月 3 日发布 EM-Altair，自称是面向微控制器级 RISC-V 系统的标准化嵌入式平台。它不定义新核，而是定义一套「合规实现必须一致地表现」的硬件、固件与运行时要求：ISA profile、特权架构、启动与运行时服务、安全服务四层，厂商可以各自实现微架构，但软件面对的是同一个目标。公司首席产品官 Angel Berrio Moreno 的表述是「同一个二进制、同样的中断行为、同样的安全假设」。

具体口径上，EM-Altair 以 RV32IM 为基线，配一组边界明确的必选与可选扩展，把中断、原子操作、CSR 行为与内存序固定下来，而不是留成一颗移动的靶子。中断部分规定了一套有界且高吞吐的架构，面向硬实时负载；隔离用 PMP 覆盖机器模式与可选的用户模式，用来分隔可信与不可信代码；安全实践对齐 ASIL-B 等效要求，并为固件完整性与设备保护预留安全钩子。目标场景写得直白：车身电子、区域与座舱控制器、电动车能量管理，以及工业控制回路、物联网传感节点与可穿戴。

配套工具是 QNTAF，Quintauris 自家的验证与认证框架。按官方描述，厂商可以在云端、模拟器与 FPGA 三类目标上跑基准、一致性与安全测试套件，把这些测试接进 CI/CD，并生成认证所需的可追溯产物。规范与工具面向 SoC 厂商、RTOS 开发者与 OEM 开放。Quintauris 由博世、英飞凌、Nordic、恩智浦、高通与意法半导体于 2023 年合资成立，做的就是 profile、参考架构与软件组件这三件事。

这条消息与 11 月 4 日英飞凌发布 AURIX RC1 值得放在一起读。英飞凌是 Quintauris 的创始成员，AURIX RC1 把 AURIX 与 TRAVEO T2G 两条产品线并到同一套 RISC-V 底座上，而 EM-Altair 提供的正是这套底座之上的共同执行环境——芯片厂做实现，合资公司做一致性，RTOS 与编译器只需对一个目标适配一次。对国内做车规与工业 RISC-V 的团队，这意味着两件事同时发生：基础软件的门槛在降低（AUTOSAR、RTOS、工具链不必每家重做），而进入门槛在抬高（客户会拿「是否符合某个 profile」来问）。

香山 XiangShan 修 MissQueue 推测预取下的 store 合并，GEM5 六笔集中在评测基础设施（11-05）

香山主仓今日一笔：修 MissQueue 在预取 miss 处于推测状态时仍然合并 store 的问题（#6842）。这是正确性修复而非性能改动——store 与一次尚未确定的预取合并，一旦预取被取消，写回的数据归属就会出错。

GEM5 侧六笔，方向明显偏向评测基础设施：把 google trace 与 cbp trace 接进 CI（#1272）、补 Fetch Block Size 的统计 PMU（#1291）、更新 SPEC06 的 RVV checkpoint profile 并对齐标量浮点部分、给周性能任务加上可选开关（#1300）、加一篇硬件预取算法综述文档（#1302），以及 cpu-o3 用「最老的同周期 squash」过滤 resolve 输入（#1282）。

把这两条与 riscv100.top 上 10 月以来的榜面变化放在一起看，香山这条线近期的动作重心是「先把测法固定下来」：checkpoint profile 决定复现的是哪一段负载，trace 决定能追到什么粒度，PMU 决定性能数字能不能拆开解释，周性能任务决定这些数字多久出一次。分数只有建立在可复现的测法上才有比较价值。

P4 Launcher 在 ESP32-P4 上做出可装载应用的类 PC 体验，21 个 PAPP 应用（11-05）

开发者 Gil Tal 发布 P4 Launcher，一个面向带触摸屏的 ESP32-P4 开发板的开源应用平台。它开机直接进入自己的界面，应用以 .papp 文件存放在 microSD 卡上，启动时载入 PSRAM，因此增删应用只需往卡里拷文件，不必重刷固件、也不必重启设备。目前已有 21 个 PAPP 应用，以模拟器与游戏为主：Neo Geo 与 Atari 2600 模拟器、Doom、Quake、Duke Nukem 3D、OpenTyrian，另有时钟与文件管理。

实现上，界面基于 LVGL，合成器负责把 UI 缩放到不同分辨率；音频引擎支持最多 8 路、4 至 192kHz；最多接四个输入设备做多人游戏，支持 PS3 与任天堂手柄；固件可从 microSD 或 GitHub 更新，新版本起不来会自动回滚。项目另提供 SDK 让开发者写自己的 PAPP 应用，并带两层兼容层：一层重实现 odroid_* 接口，一层实现旧的 PAPP v1 服务表——后者正是 Doom、Quake 这些老代码能用原胶水层跑起来的原因。代码基于 ESP-IDF v5.5.2，已适配 Guition 的 4.3 英寸与 7 英寸板以及 M5Stack Tab5。

这类项目的价值不在「能玩游戏」，而在于它把应用打包、装载、更新与回滚这一套约定在 MCU 上跑通了。ESP32-P4 是乐鑫的 RISC-V 高性能型号（双核 HP 加 LP 核），PSRAM 带宽、显示与音频子系统正好是这类负载的压力点；一套成熟的应用容器约定，比多跑一个模拟器更能说明平台可用性。

日期：2026-11-05　来源：CNX Software 报道、giltal/ESP32_P4_Launcher

二、产品与生态动态

先楫第二届生态大会定档 11 月 21 日深圳，14 场议程把 RISC-V MCU 与 AI 绑在一起（11-04）

先楫半导体（HPMicro）确认第二届先楫生态大会（先楫半导体生态日）将于 11 月 21 日（周六）9:30 至 17:00 在深圳市南山区益田威斯汀酒店举行，主题为「AI 赋芯，开发者共建生态」。活动采取报名邀请制，需提前扫码报名并以先楫官方邮件回复确认。这届大会在 10 月中旬第六届 RISC-V 中国峰会（深圳）上先行预告，先楫把它定位成高性能 RISC-V MCU 生态交流与合作的主要平台。

议程把「RISC-V MCU 加 AI」这条线摊得很直白。上午从产品与工具链切：先楫软件总监钱江浩讲「拥抱 AI Agentic / Vibe Coding，让嵌入式开发也可以 Vibe」，随后是先楫的 RISC-V MCU 产品矩阵与多场景应用；SEGGER 中国技术总监盛磊讲从研发到量产的工具链配套；RT-Thread 高级工程师李镇鸿讲 RT-Thread 在 HPM6750 上的软硬件协同适配与工程实践；再由先楫讲端到端的直流拉弧检测开发平台，华秋 DFM 技术工程师凌国雄讲 DFM 前置如何把打样周期压到 48 小时。下午转向方案与开发者实战：无人机飞控与电调、AI 加持的语音识别加视觉加运控、cherry 全家桶在 HPM 芯片上的应用、PocketJS on HPMicro、AI 辅助 HPM SDK 应用开发实战、HelixLink 开源落地实录，最后是常见问题 Q&A 与现场抽奖。

议程的构成比场次数量更值得看：14 场里只有 3 场由先楫自己讲产品，其余是工具链厂商（SEGGER）、开源 RTOS（RT-Thread）、制造服务（华秋 DFM）与社区开发者（Sakumisu、Half Sweet、RCSN、HelixLink）。对一家 MCU 厂商，这种配比本身就是生态成熟度的信号——它把「生态」从自家的 SDK 文档，变成了别人在自己芯片上交付工作的汇报。

与上周动态可以对上：先楫在 10 月底到 11 月初把 12 个 RT-Thread BSP 仓库在 13 分钟内统一推到 v1.13.0，并新开了 HPM5100EVK 的 BSP 仓库；HPM5100EVK 这次就出现在大会的抽奖奖品清单里。芯片侧，HPM5100／HPM6E8Y 与 HPM5300EVK 也已被列进 RV-EAI 具身智能开放方案的本体层与小脑层选型。换句话说，这场大会的议程与先楫近两周的仓库动作指向同一个方向：把 RISC-V MCU 从「有芯片、有 SDK」推到「有第三方在自己平台上持续交付」。

四、具身智能与机器人专章

进迭 manipulation 组件：把设备独占、到位判定、超时与故障锁定收进设备会话（11-05）

manipulation 是进迭机器人 SDK 里的机械臂控制组件，做的是「统一控制机械臂与末端执行器」：用设备配置选择硬件，用同一套命令或 C++／Python 接口下发动作，并提供运动学、手眼标定与设备工具。当前带三种驱动：软件模拟的 mock_device；agx_nero_revo2，对应松灵 Nero 七轴、可选 Revo2 右手（Revo2 没有位置反馈）；so101，五轴、可选原配夹爪，附舵机校准工具。

它的架构取舍写得很明确。C++ 应用直接链组件库、在进程内用 DeviceSession；命令行与 Python 应用走 DeviceClient，由它拉起本机进程 manipulation-device serve，经 JSONL 下发请求；YAML 点位任务由 manipulation-device run 执行。设备会话统一处理设备独占、到位判定、取消、超时与故障锁定。驱动层只负责型号协议与单位换算，运动学与手眼标定从 device.yaml 与 descriptions/ 取模型，不写死型号；接新设备实现 Arm 与 EndEffector 并注册即可。

最值得记的是那段「组件不自动使能、不自动清错、不自动归位、不自动重试」。具身智能项目里最容易图省事的地方就是让中间件替人做决定，而这四件事一旦被自动做掉，出问题时现场人员就失去了判断依据。把安全边界放在会话层而不是驱动层，是机器人中间件该有的克制。

日期：2026-11-05　来源：spacemit-robotics/manipulation

dice_arena 用 K3 加 Nero 七轴加 Revo2 灵巧手跑通骰子游戏全链路（11-05）

dice_arena 是同一套 SDK 上的综合演示：视觉抓杯、摇杯放杯、手眼标定、骰子识别、语音播报与网页游戏。硬件清单写得具体——SpacemiT K3 开发板作主控，松灵 Nero 七轴机械臂经 USB-CAN 适配器（SocketCAN、1Mbps）连接，末端装 Revo2 右手灵巧手（六个控制通道，与机械臂共用控制器连接），抓杯与标定用 Intel RealSense D435i，骰子识别用自上拍摄的 USB 相机（默认罗技 C920、MJPEG），另配 ChArUco 标定板、音箱与绿色杯具。

软件链路上，dice-arena serve 启动视频转发、本地语音与游戏后端，后端跑状态机（规则讲解、抓杯、摇杯、放杯、视觉判定、结果手势、返回 HOME），按槽位调用各组件；抓杯由 CupApplication 用 RealSense 图像识别杯体、求逆解并检查路径，动作经 manipulation 的 DeviceClient 下发；识别由 vision_yolov8_objdetect 在 SpacemiT EP 上推理，画面以 RTSP 推到 MediaMTX，浏览器经 WebRTC 播放；语音由 tts_moss_nano 调用本机 MOSS-TTS 合成，经板端 PipeWire 播放。

真正有价值的是失败处理：任务策略库 libcup_task.so 以 C ABI 检查阶段顺序，动作发出后失败即锁定，需要人工处理的状态写进 task_state.json，程序重启后仍拒绝运动，直到现场人员处理完并执行 dice-arena reset。具身智能 demo 里最容易省掉的就是这条状态机，而它恰恰是量产时最不能省的部分。

五、总结与趋势观察

今天有两条主线，一条讲抽象层，一条讲标准化，落在同一个问题上。

进迭时空的 RVISA 在 AI 矩阵侧给出一层虚拟指令记法，把「程序员能表达的优化」写成硬约束，再用版本化的映射 profile 对上 IME、VME、AME 三种尚在推进的矩阵扩展；Quintauris 的 EM-Altair 在 MCU 侧给出二进制兼容的执行环境，把中断、原子、CSR 与内存序固定成一套合规实现必须遵守的行为。两者都在回答开放指令集带来的碎片化该由谁收敛：不是让芯片厂各自解释规范，而是在规范与实现之间插一层稳定的软件目标。差别在治理结构——一个是六家大厂的合资公司，一个是单家厂商的工作草案。

国内厂商的动作重心继续从「芯片与板卡」转向「组件与规范」。进迭一天里同时推进 RVISA 规范、机器人 SDK 三个仓库与 K3 的机械臂手册；算能给出 2 核与 3 核的端到端压测数字而不是峰值算力；紫荆把「生态推广」做成了可申报的案例。这三件事的共同点是都在补「别人能不能用起来」这一侧，而不是再发一颗参数更高的芯片。

车规仍是最大战场，且今天呈现出三个层次同时推进的局面：芯片层（英飞凌 AURIX RC1，11-04）、平台规范层（Quintauris EM-Altair）、生态案例层（紫荆 M100 入选中国芯示范案例）。三层之间不是竞争关系，而是同一条产业链上不同位置在做同一件事——把开放指令集变成可交付的车规产品。

评测侧则继续「先固化测法」。GEM5 今天的六笔里有五笔是 checkpoint、trace、PMU、周性能任务这类基础设施，riscv100.top 昨天的对比视图与今天的榜面回退也是同一类现象：榜面还在整理期，数字的可比性比数字本身更值得关注。
