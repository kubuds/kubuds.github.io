TileLang周报（2026-11-16 ~ 2026-11-20）

2026-11-20 苦芽科技

报告周期：2026 年 11 月 16 日（周一）至 11 月 20 日（周五），5 个工作日、5 期日报；另含发布日（11 月 21 日）对 tile-ai 组织 30 仓库的 168 小时补充核查

第一部分 · 简报

本节为本周要点筛选，默认 800 字以内（本期 701 字）；完整条目、逐笔清单与信源见第二部分存档。

  • 安全事件：11-15 上游昇腾仓 CI 被外部 PR 植入脚本，贡献者 token 被盗用；四个仓库出现同风格 PR，全部关闭未合入，披露见 issue #2016。
  • TileOPs 成主战场：五期合入 15、18、12、23、16 笔。manifest 升级为声明式参数后，pilot 模型的算子按天兑现，Embedding 误合当日回退、次日重提合入。

本周判断：主战场已连续两个窗口落在算子库，瓶颈从开发量转到评审带宽；自动 warp specialization 的屏障插桩成为一等风险，而 v0.1.15 已停 51 天，所有改动都卡在下一个 tag 之外。

运行时与执行路径

  • 设备状态还原（#3872，11-16 合入）：tvm_ffi 宿主 stub 只设当前设备、不还原。在 cuda:0 上调用 cuda:1 的张量，结果正确但当前设备被留在 cuda:1。后续 device="cuda" 的分配会静默漂移。修法是在适配器层用 torch.cuda.device(...) 包住调用，并在结束时还原。
  • NVRTC 单参数内核（#3880，11-16 合入）：参数名与类型用 ", " 拼接。单参数时拼出的不是元组，cuLaunchKernelEx 直接抛 TypeError。改为带尾逗号的元组字面量即可。
  • cython 动态共享内存（#3882，11-16 合入）：动态共享内存上限原先只在 init() 里设一次。该属性是逐设备的。需要超过 48 KB 的内核在其余设备上会报 cudaErrorInvalidValue。改为每个内核生成 _set_dynamic_smem() 帮助函数，并记录已提升的设备。
  • ROCm HIP 运行时复用（#3899，11-16 合入）：PyTorch 的 ROCm wheel 用 RTLD_LOCAL 加载 libamdhip64，stub 找不到它。修法是先用 RTLD_NOLOAD 探测已映射的运行时。这样可以避免 dlopen 出第二份后模块句柄跨运行时，导致首个 kernel 启动失败。
  • 无符号缓冲读取（#3875，11-17 合入）：CuTeDSL 目标上，从 uint8、uint16、uint32 缓冲区读出的值被当成有符号数。根因是 MLIR 整数无符号位，而代码生成对全局与共享内存的每次访问都从迭代器类型出发。作者在 RTX PRO 6000 上用 256 个 uint8 值做探针。五种写法在主分支上各错 128 个值。修法是让 tl.make_tensor 接受 dtype=，并把类型重新挂回视图。
  • 布局占位变量跨序列化保持绑定（#4410，11-20 合入）：tl.Layout、tl.Fragment、tl.PartialFragment 用进程内单例 tirx::Var 占位符表达索引与线程映射。判断依据是对象同一性，不是 name_hint。布局经 pickle 或 tvm.ir.save_json 往返后，占位符被重建。于是 map_forward_index([7]) 返回 [_i]，OutputShape() 把 (32,) 算成 (_i + 1,)。在 spawn 出来的 worker 里降载带注解的 PrimFunc，会以「forward map must be injective」失败。修法是把绑定的占位 Var 引用纳入同一个 ObjectGraphSerializer 通道。
  • CUDA Tile IR 后端 RFC 重新提交（#4402、#4403，11-19）：目标是从 TileLang 程序生成 CUDA Tile IR，交给 tileiras 编译与调度。布局、流水、warp 特化与指令选择都由 tileiras 决定。后端只转换 Tile IR 能正确表达的语义。转换不了的直接报编译错误并拒绝该程序，不追求与现有 CUDA 后端完全兼容。这版是对早先 #3247 的重做。评审曾指出旧实现 try-catch 过多，用约 1.85 万行 Python 写 pass。

正确性与缺陷修复

  • CPU 后端补逻辑归约降载（#4389，11-18 合入）：tl.any_of 与 tl.all_of 此前无法走 CPU 常规管线。新增 LowerCPUAnyAll pass，插在 LowerTileOp 之前。降载为按行主序的串行扫描，并带短路。空归约取标准单位元。浮点与 bfloat16 的 NaN 视为真。
  • topk 回归测试超时（#4407，11-18 合入）：test_topk_candidate_overflow 在 CUDA CI 上超时。原因是化简阶段发起了代价高昂的 Z3 查询。修法是给该测试设置 arith.z3_rlimit 为 100。作者注明本机没有 CUDA 代码生成，完整编译耗时与 GPU 正确性未验证。
  • 昇腾自调优测试移除跨 NPU 探测（#4401，11-18 合入）：该分支会执行一次跨 NPU 拷贝。在部分 Torch-NPU 与 CANN 组合上，这次拷贝会中止 NPU 上下文。捕获 RuntimeError 后跳过用例并不能恢复上下文。同一 pytest 进程里后续无关用例会跟着失败。故障表现因此依赖执行顺序。
  • 新报缺陷：MLA decode 示例缺写后读同步（#4412，11-19）：报告指向 examples/deepseek_mla/example_mla_decode_ws.py。它称右侧 warpgroup 读取 sum_exp_shared 时，没有等待左侧 warpgroup 的写入。该报告尚未附修复，也未标注复现环境。本期按「已报告、待处理」记录。
  • 在审修复：warp 特化时跳过布局不兼容的 TMA 提升（#4413，11-19）：在 b1367a59 上，一个面向 sm_90a 的流水线 GEMM 无法降载。触发条件是它的 8 位 B tile 使用带填充的 swizzled 布局。A 的载入让该循环具备 warp 特化资格。随后该 pass 把 B 的普通拷贝也提升成 TMA，而 LowerBulk 拒绝带填充的布局。修法是逐个检查候选 TMA 载入的目标布局注解。

六、趋势观察

第一，主战场已经从编译器本体移到算子库与调度器，这个位移连续两个窗口成立。本周 141 笔合入里，TileOPs 占 84 笔，主仓只有 12 笔。主仓那 12 笔里，四笔是运行时 bugfix，两笔是版本与文档。上一周的情形也类似。主仓的工作集中在修回归，新增能力更多以算子库的瓦片、选择器、代价模型的形式出现。判断依据不只是合入数，还有依赖方向。TileOPs 的性能结论要引用 TileFoundry 的 roofline 与调度，而主仓这一周没有给它们任何新东西。

第二，审计已经流水线化，瓶颈从「发现」转到「评审」。11-16 期 72 小时新开 406 条 issue，两个账号贡献 314 条。cn-sys 的 172 条在 1 小时 46 分钟内写完。ilovexsir 的 142 条直接对应五个 batch 修复 PR。这套模式确实在压缩「缺陷发现到修复」的周期，同一天内 issue 与 PR 并存。但它把压力转移到评审端。11-16 期在审 102 笔、合入 30 笔。其中 22 笔 mlir-ascend 同构 PR 只能由极少数人过。下一阶段的瓶颈会是评审带宽，而不是发现速度。

第三，安全边界成为本周唯一不可回避的负面事件，暴露的是结构问题。自建 CI 被外部 PR 穿透，个人 token 被盗用。四个仓库同时出现同风格 PR。这说明「新贡献者 PR 直接触发自建服务器 CI」这个默认设置在组织层面是共用的风险面。作者的处置是撤销旧授权、保留恶意 fork 取证、给自建 CI 服务器做安全处理。建议的改法是新贡献者 PR 需维护者批准后才触发。这条对整个 RISC-V 与 AI 编译社区同样适用。自建 runner 的信任边界应当默认收紧，而不是按仓库各自判断。

第四，自动 warp specialization 的正确性已经成为一等风险。#2896 到 #2901 这条链说明了一件事。当一个性能改动把同步责任交给编译器自动插桩时，插桩位置就成了正确性的一部分。而它对上层不透明。同一个 cache key 两次编译，屏障可能落在分支内，也可能落在分支外。再叠上 CI 的持久化内核缓存，偶发的坏插桩会被固化成稳定失败。这一问题目前没有结构性解法，只有「把写操作挪出条件分支」这类局部规避。如果后续更多瓦片走 ping-pong，同类挂死大概率会再出现。

第五，平台边界在向外扩，但都停在 IR 层。同一天落 Metal 目标与自动微分，编译器从推理内核伸向训练与 Apple GPU。两者都不产出可运行的内核。顺序很清楚，先立接口，后补后端与运行时。同一周 TileFoundry 用 303 个文件把术语与布局算法收敛到单一规格。这相当于把中间表示从「实现中长出来」改为「先定义再实现」。这类改动短期增加评审成本，长期决定 IR 能否被外部后端正确实现。

第六，版本长期不发，是本周所有进展的共同出口问题。v0.1.15 停在 09-30，至本周五已 51 天。主仓的运行时修复、昇腾的执行后端改动、TileOPs 的算子补齐，最早都要等下一个 tag 才能进下游发行包。与之对照，独立发行版已经在往前走。Sunrise 出 0.1.15+sunrise.1.2.1，沐曦在备 v0.1.12+musa.5，海光以合并式修正跟进。三家各自发版，版本对齐与兼容矩阵将成为新的维护成本。

第七，RISC-V 四源本周两支各推进一次，节奏仍不连续。TVM 路线新开 hikari 分支，给出 K3 移植验证与 RVV 网格数据。MLIR 路线合入 buddy-opt 默认化与两个示例。社区索引页第一次收录 TVM 侧 fork。但 11-18 起三期全部静默。两条路线的分工已经明确。TVM 路线在做「能跑起来、有实测数据」。MLIR 路线停在「有设计、有示例」。这条线值得按窗口跟，但不宜按周计算进度。
