编译器、语言层与执行路径

  • PTO 执行后端换代（#3516，11-11 合入，20 文件 +1549/−182）：target="pto" 配 execution_backend="auto" 时解析为 tvm_ffi，共享 host codegen 负责 MakePackedAPI 与 C host，昇腾运行时用 aclrtLaunchKernelWithHostArgs 启动 PTODSL 编出的 aibin，路径与 AscendC 内核一致。设备构建侧新增模块级工具链回调，把整个 PTODSL 模块一次编译完成（ptodsl → ptoas → bisheng fatobj-link → 抽取 .aicore_binary），缓存键把 ptoas 参数、ptoas 版本与 CANN 身份一并算进去。旧路径保留为 execution_backend="pto"，两套产出逐位一致；验证面含动态形状、多设备内核、cube/vector 混合 GEMM、缓存命中与损坏条目抛错等四组新测试。
  • AutoSchedule 收紧周期下界（#3776，1 文件 +20/−1）：原先从一个固定下界起二分，改为取三条必要条件的最大值——单任务界用各任务启动间隔的最大值，资源团界对成对冲突任务按残余值排序后由相邻差与首尾差推出周期不小于团内启动间隔之和，自依赖界由 S_u - S_u >= wait - d*P 反解出 ceil(wait/d)，版本相关距离按 num_stages 折算。实证在 Ascend 950PR、CANN 9.3.0 周版本上：昇腾示例全部编译通过且调度结果不变，Z3 求解阶段累计耗时降 10.04%。没有引入额外的下界探测，也没有改调度模型。
  • 跨核同步强制批调度以防死锁（#3614，5 文件 +102/−1，其中 78 行为回归）：mode=0 是「有可用核就启动」，mode=1 是「等算子所需全部核资源到位再整体启动」。做全核同步的算子若在普通模式启动，可能只拿到部分核就先跑到全核屏障上等待，而它等的核正被另一条流占着——资源成环，设备挂死。改法是在 codegen 侧识别出「带常量 0 的跨核同步」后自动置 __schedmode__(1)，并把该标志按函数重置以防泄漏。顺带把跨核 set/wait 的整数 mode_id 收窄到 0/1/2/4，并写明三个目标的模式集合并不一致（910B/910C 支持 0/1/2，950 才多出 4）。
  • VMI 描述符与逻辑覆盖校验一并收口（#3894，6 文件 +925/−550）：修 typed view 的 gather/scatter 与单元素载入两类形态在构造描述符时基址与步长取错；同时删掉前端冗余的逻辑覆盖拒绝——删校验不是放松，而是共享内存检测器的修复（#3805）已落地，前端再拦一遍会误伤跨行、转置与动态视图。
  • CUDA 侧补两组指令级原语（11-10 合入）：#3490（6 文件 +185/−1）补 L1 预取、uniform L1 预取与 L2 预取，并把驱逐优先级做成一等参数 EvictPriority（默认、普通驱逐、优先驱逐、最后驱逐、不改变、不分配六档），非默认优先级要求计算能力 8.0 以上；#3605（7 文件 +203/−1）新增 T.clamp_symmetric(x, limit)，在 SM86 及以上把 FP16/BF16/FP32 统一钳到 [-limit, limit]、保留带符号零与次正规数，任一操作数为 NaN 时返回规范 NaN，实现直接降到单条 min.NaN.xorsign.abs，并以 SASS 里三种标量与打包形态的出现作验收证据。
  • TIRx 侧两笔先手加固（11-11 在审）：tile-ai/tvm 的 #94（[Fix][TIRx] Make ceildiv exact for signed divisors）与 #93（[Arith] Guard negative scales in canonical split div/mod）在修同一类问题的两端——符号进入整除与取模后规范化的改写前提不再成立。同日主仓新开 #3937（嵌套 floor division 在负乘数下产出错误整数）指向同一处，区别是 #3937 为用户侧复现、#93/#94 为编译器侧先手。

六、趋势观察

第一，大改造的善后期比改造期更长，成本落在「原本合法的程序不再合法」上。#3512 把 PTO 的向量化与类型体系一起换掉之后，连续四个窗口都在补它的回归面：执行后端换默认（11-11）、整数原子（11-11、11-12）、显式 SIMD 并行循环与标量 cast 事实（11-12）、VMI 描述符（11-12）。这四类问题的共同点不是「新功能算错」，而是「旧写法编译不过或结果变了」。对编译器项目，这类回归的排查成本远高于新功能的 bug——报错位置常常落在一个与故障无关的标量或地址上，堆栈里看不出是谁先装错了假设。

第二，昇腾的瓶颈已从「能不能编译」移到「声明与实现是否一致」，而评审带宽是这条线的硬上限。十月的 14 条静态缺陷之后，本周两波审计把缺口从参数层扫到 T.simd 指令层，形态几乎全是「声明支持但实现走了另一条路」或「本该拒绝却静默通过」；而相对应的修复 PR 有十余笔同时在审。tilelang-ascend 默认分支四个窗口零合入、在审队列却持续增厚，3060 项每日测试全过——测试覆盖的是合法路径，非法路径的拒绝能力得靠审计。真正的验收应该从「通过率」换成「声明与实现的生成式对齐」：从 HCU_MCPU_SET 生成后端必须覆盖的架构清单，从 intrinsic 注册表生成 dtype/位宽支持矩阵。

第三，后端矩阵从「一家独进」变成四点同时开工，投入深度分成四类。本期主仓八笔全在昇腾，但同窗口 ROCm 一次开出七笔成系列、海光一条分支一天十笔、Sunrise 在走发布流水线（ci/sunrise-0.1.15-1.2.1-r6 建删 80 秒）、Hexagon 以个人 fork 的形式把 TileLang 推到手机 DSP。四种形态（上游内置后端、厂商适配仓、独立发行版、第三方 fork）对应四种投入深度，这个分化本身就是判断各厂商依赖程度的可用指标：厂商仓跟版本、发行版跟主线、fork 跟自己的硬件。

第四，TileFoundry 的定价缺口在被算子侧反复顶回，这比单个算子变慢更危险。#318 明说同一行为在四条已关闭 issue 里报过、都被标 not planned、当前构建仍复现；#319 一次给五条且带 962.1 对 1213.6 GFLOP 的偏差（26%）；bf16 的尾数口径在 check --help 与硬件事实之间差了整整一位。分析器是 TileLang「先定价再选调度」路线的前提，定价偏 26% 会让自动选择在边界网格上系统性选错。这类缺口不会让任何单个算子变慢，但会让自动化安静地做错决定。

第五，「给 agent 用的工程化」开始成规模出现。mlir-ascend 的 harness 分支一日 +7632 行，内容是技能库、仿真 trace 流程与 Roofline 计算器，服务对象是「写算子的人或 agent」而不是编译器本身；同一周，Hexagon fork 的 README 直接写明后端与模型由 AI agent 在维护者指导下重写、四天 75 个 PR 占当前代码八成以上。两件事方向一致：TileLang 这类 DSL 的抽象层恰好落在「agent 能写对」的粒度上，于是生态开始为 agent 铺工具链，而不是只为人铺文档。这一条值得按周跟。

第六，RISC-V 四源连续六个窗口静默，与整体活跃度形成明显反差，但差距的量化方式本周变了。TVM 路线、MLIR 路线、社区索引页、算能 TPU 四个上游全部停在原引用；四源之外那条 CPU 线在 11-11 换口径后给出 553/553 落在 Triton 1.03 倍内的结论，但同一批用例在前一天还是「41 例快于参考、SG2044 中位 0.0580 倍」。两套数字都不是造假，差别在于被测对象是「作者手写程序」还是「共享编译器产物」。真正的观察点是：这套「同一编译器、两套前端」的做法能否反向进入上游，以及 RVV/IME 路径是否会被四源之外的项目先跑通。停滞不是没人做，而是官方四源还没有形成「自动发现差距、自动验证、自动排队」的回路。
