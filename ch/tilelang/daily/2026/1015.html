一、核心项目进展

1.1 主仓：昇腾面四处收笔——独立 AIV 执行（#3485）、PTO DeepGEMM codegen（#3330）、跨 warp allreduce 修复（#3494）、示例目标选择（#3474）（10-14）

日期：2026-10-14　来源：独立 AIV（#3485）／ PTO codegen（#3330）／ allreduce 修复（#3494）／ 示例目标选择（#3474）

  • 独立 AIV 执行（#3485）：扩展 Ascend AutoSchedule，使 AIV0 与 AIV1 可在 sid 依赖的控制流下执行不同工作——支持交替收尾（epilogue）、反量化与收尾分工、不相交输入分区以及循环内角色切换。实现上把 AssignCore 提前到延迟估计与调度之前，为 AIV 局部 UB 缓冲与标量状态建立独立身份，并按参与核建模流水线资源、特殊寄存器依赖、UB 容量与同步标志库；保留统一内核的 collective 路径与一/两 AIV 发射几何。L0C→UB 拷贝仍在 AIC 上执行。
  • PTO DeepGEMM codegen（#3330）：跨控制流跟踪 tl.ascend_set_mmad_direction 并把生效方向编码到 MAD 指令上，拒绝在冲突方向下可达的 MAD；支持 SIMD 后增量加载（同时返回数据与更新指针）、混合 AIC/AIV 内核中的 UB 地址到 PTODSL 指针转换、动态 L0C→UB 维度与步长、int16 有符号打包 MX scale；改进条件表达式与运行时循环的代码生成。报告称 15 个 DeepGEMM PTO 用例中 14 个通过，test_bf16_m_grouped_padding 因 PTOAS VPTO 后端无法合法化 FP32→BF16 转换仍受阻。
  • 跨 warp allreduce 修复（#3494）：当一个 cross-warp allreduce 调用覆盖多个独立归约组时，ascend 与 pto 目标错误地把第一组结果交给所有组；本笔修复该正确性问题（跟进 #3469）。
  • 示例目标选择（#3474）：移除昇腾示例与测试中硬编码的 target="ascend"，改由 TILELANG_DEFAULT_TARGET 环境变量决定；DeepGEMM JIT 入口支持 execution_backend="auto"；CI 对昇腾示例套件分别以 ascend 与 pto 两个目标各跑一遍，并在文档写明选择方式。

1.2 主仓：基建三笔——CPU OpenMP 并行 grid 循环（#3109）、C 系 codegen 共享发射（#3289）、Windows NVCC 改走 MSVC（#3510）（10-14）

日期：2026-10-14　来源：CPU OpenMP（#3109）／ codegen 共享（#3289）／ Windows MSVC（#3510）

  • CPU OpenMP 并行（#3109）：为 CPU 后端加入可选的 grid 循环 OpenMP 并行——新增 MaterializeCPUParallelGrid 把带注解的 CPU grid 循环转为并行循环，配套循环 collapse、线程数配置、最小 trip 数门限与分配下沉；补齐 Linux / macOS / Windows 的 OpenMP 编译标志与 pass 配置项；测试覆盖正确性、pragma、分配下沉、门限与单维情形。CPU 后端首次具备网格级并行能力。
  • C 系 codegen 共享（#3289）：引入 CodeGenTileLangCBase 统一 CUDA、HIP、CPU C、Ascend C++、Metal 与 C 主机代码生成；修复 T.import_source、T.Kernel(prelude=...) 与 pragma_import_c 在源文本缺少末尾换行或以反斜杠结尾时吞掉下一生成行的问题；导入内容按「头文件→导入→生成声明与函数」排序并保证两个分隔换行。验证：聚焦回归 83 通过、相关 codegen 与 launch 套件 405 通过。
  • Windows NVCC 改走 MSVC（#3510）：NVCC 拒绝 get_cplus_compiler() 选出的 clang-cl——改为从 NVCC 子进程环境选择 cl.exe（不改主机 C++ 编译器选择），补 VS 2026 18/* 回退路径，非 Windows 平台不再传 -ccbin=None；CUDA 13.3 下复现用例修复前失败、修复后编译通过。

1.3 主仓：ROCm scan 波前修复（#2326）、测试基建缓存（#3502）与治理配置（#3513）（10-14）

三、生态与采用方

3.1 TileOPs：foundry 性能批 11 笔收口——softmax / 池化 / 归一化 / 归约全铺开（10-14）

日期：2026-10-14　来源：softmax（#2570）／ 池化三笔（#2572 / #2573 / #2579）／ 归一化三笔（#2576 / #2581 / #2585）／ 归约两笔（#2571 / #2578）／ GEMM 与 Elementwise 两笔（#2582 / #2577）

  • softmax（#2570）：新增 16 字节 L2 evict-last 载入 tileops::load16_evict_last；整向量行（每线程至多 64 元素）改为寄存器驻留 _held_row，用 warp shuffle 折叠最大值与和；SoftmaxWarpRowsKernel 覆盖至 2KB 行、SoftmaxOnChipKernel 寄存器与共享内存两路均走新载入。39/42 个 SoftmaxFwdOp 行领先最快对照 1.1% 至 78.1%，(32768, 65536) float32 与 quack 持平；lm-head 两行仍落后（0.909x / 0.934x）。
  • 池化三笔：#2572 MaxPool1dIndices——新 load_evict_last 标量载入，相邻输出成向量存储，sincnet-local 对 torch-compile 1.009x / 1.006x，较旧版内核提速 1.049x（float32）；#2573 AvgPool3d——固定除数且 taps ≤32 的窗口改为一次性读全部 taps（L1/L2 evict-last）并用 select 剔除域外，非 2 的幂固定除数走 float32(float64(sum) * float64(1/divisor)) 无慢路径分支，结果与 PyTorch 位一致；#2579 MaxPool3dIndices——float32 tile 对齐窗口每线程两个相邻输出、值/索引成向量存储，c3d-pool1 170.1 微秒降至 166.0 微秒。
