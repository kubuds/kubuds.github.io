一、核心项目进展

1.1 主线：dense 视图恢复精确逻辑区域，跨行依赖细化到行（#3890）

#3805 之后，显式 stride 视图的多元素指针访问一律回退到整个 buffer，即便该视图是 dense row-major。后果很具体：一个形状 (2, 128) 的 BF16 视图读第 0 行，被当成读两行，于是对第 1 行的后续 DMA 写产生了一条虚假的 V 到 MTE2 依赖。在 TileKernels 的 engram_gate_bwd 里，这抹掉了 FP32 存储上 BF16 视图两个 slot 的区别，精确区域的 assume_no_conflict 提示匹配不上，同步把下一个 slot 的 DMA 卡在上一 head 的向量计算后面。

#3890 的做法是先证明显式 stride 描述的确实是 dense row-major 视图，再复用 #3805 的 offset 感知重建（含跨行 carry，无法表达时保守回退），物理生命周期与复用分析不动，把改动限定在逻辑依赖精度上。间接访问依旧保守：gather/scatter 索引与带 offset 的 vld2 可以越过紧凑的 access_ptr 范围，无论 buffer 是 dense 视图、隐式布局还是一维，这类消费者面前保留整个逻辑 buffer，从而保住 DMA 覆盖间接可达行之前必须的 V 到 MTE2 同步。新增回归测试区分「重叠 slot」与「相邻 slot」两种情形。

来源：https://github.com/tile-ai/tilelang/pull/3890

来源：https://github.com/tile-ai/TileOPs/pull/2882 、 https://github.com/tile-ai/TileOPs/pull/2881

3.2 TileOPs：三处边界输入修好，K=0 空收缩、变长 GQA 挂死、GLA 反向共享内存

三笔缺陷的共同形态是「默认参数下不出现，边界输入才炸」。#2878：K=0 的空收缩在 SM89 上此前报 OpNotAvailableError，因为 cp.async 内核的窄行规则按 4 字节单位守护最内维加载，而 K=0 时主循环根本不跑 K 步；修后 test_gemm.py -m "smoke or sm89" 从 63 passed 6 failed 变为 66 passed 4 failed，余下四项是 SM90 专用用例。#2876：变长 GQA 前向的融合 RoPE 在旋转半宽被 padding 到不能整除线程数时挂死（rotary width 10、5 个 chunk 补到 6、128 线程），根因是 CI 的 TileLang 把 barrier 放在 guard 内，padding chunk 上的线程跳过它；新增 split_reads 让「读加旋转」与「写回」分两轮，只有变长 GQA 内核启用。#2880：float32 GLA 反向在 chunk 64 下需 114688 字节共享内存，SM89 只有 101376；改为在 dA 乘积之后、v 最后一次使用处再组 dv 的状态项，让衰减后的 key 顶替 v 的位置，压到 98304 字节，且梯度与默认顺序逐位一致。

来源：https://github.com/tile-ai/TileOPs/pull/2878 、 https://github.com/tile-ai/TileOPs/pull/2876 、 https://github.com/tile-ai/TileOPs/pull/2880

3.3 TileOPs：Softmax 整行驻寄存器，每元素一次指数，指令数降 21% 至 23%

#2886 让 SoftmaxClusterSplitKernel 也服务最长 8 个 16KB 份额的 16-bit 行：每个 CTA 把份额整行放在寄存器，128 线程一个 CTA，每元素只做一次指数。原来的分段程序每元素两次指数、一半份额经共享内存，16-bit 行比 quack 多 52% 指令，65536 元素行落后 3%。#2871 把两个寄存器驻留 softmax 的指数换成裸 MUFU.EX2 加一次行倒数，新增共享原语 exp_shifted_scaled 先乘 2 的 24 次方，保证可舍入到非零 float32 的项仍是正规数，倒数的抬升因子自动抵消。执行指令在 512 列降 23%、2048 列降 21%；bf16 512 列 16.67 微秒对 quack 16.35，2048 列 62.99 对 62.21。

来源：https://github.com/tile-ai/TileOPs/pull/2886 、 https://github.com/tile-ai/TileOPs/pull/2871

3.4 TileOPs：RMSNorm 窄块向编译器要常驻上限，短行 warp 活跃度止跌

#2884 的成对 RMSNorm 64 线程块（一行 1024 个 16-bit 元素、每线程两向量）改为向编译器请求 SM 的 32 块常驻上限；不设限时 ptxas 给到每线程 40 个寄存器，H200 的一个 SM 只保住 32 块上限中的 24 块，短行加载的 warp 活跃度掉到 64%。更宽的成对块不改寄存器配置，避免影响大行吞吐。

来源：https://github.com/tile-ai/TileOPs/pull/2884

3.5 TileFoundry：1491 个文件按源码规范重组，规则进 pre-commit

#312 是本窗口唯一的大改动：1491 个文件、+41324 至 −42379，关闭 #296。做法是把此前没有强制约束的东西写成规则：新增 docs/spec/code-organization.md，写明 S1 至 S11 与 C1 至 C11 的 Python 源码规则及分层表，配 scripts/code_organization_lint.py、ruff 与 import-linter 在 pre-commit 里执行，规则对每个 .py 文件生效，唯一配置是 src 与按文件豁免，__init__.py 只做再导出、不写 __all__。结构上 ir/ 拆成 expr、types、dim、utils、core、pattern、clause、hir、tir；visitor_registry 与 evaluator 合并为 interfaces 下的 valuation、typeinfer、verify、cost、access、evaluator、schedule 七块；根目录 compile.py 移入 compiler/，script.py 与 module.py 移入 parser/，装配逻辑进 bootstrap.py；改用 Go 风格限定名（types.TensorType），Options 仿 clang 的 CompilerInvocation 按阶段切分。对下游的意义是：TileFoundry 的内部导入路径这一版会变，引用私有符号的脚本需要跟着改。

来源：https://github.com/tile-ai/TileFoundry/pull/312

3.6 第三方：CANN 社区出现昇腾 TileLang 算子仓 ops-tilelang

五、趋势观察

第一，性能队列的产能与达标率已经脱钩。三批各 6 笔、一天 18 笔，产能是稳定的；但 10 笔标 below bar 说明当前流水线的目标不是「这轮变快」，而是「这轮把差距定位到可改的程度」。#2887 的根因写得最典型：基础瓦片按 256 字节分片跨行读 B，DRAM 的流式效率低于少行长跑，于是换成 64 行块加深环。这类改动即使分数未达标，也把下一步的方向定死了。读者判断一笔性能 PR 的成熟度，应当先看 Result 行，再看根因是否可复现。

第二，寄存器与 dispatch 成为这一批的共同瓶颈。#2884 是寄存器配额压住了 block 常驻数（40 个寄存器导致 32 块上限只保住 24 块），#2870 是 6272 个 128 线程块对 1568 个 512 线程块的 dispatch 次数差四倍，#2885 是 192 宽的瓦片填充率更高但行掩码存储的除以 192 溢出了寄存器。三笔指向同一件事：在 H200 这类 SM 上，算子性能已经不由算术量决定，而由「每线程多少寄存器、每 SM 多少块、每块多少 dispatch」这组二阶参数决定。

第三，昇腾线的瓶颈从开发量转到评审带宽。默认分支三天没有合入，在审却堆了 20 余笔，且主题从算子迁移转向工具链接口（torch.compile、L2 刷写、L0C 反量化）。#3890 那笔 dense 视图修复也在同一方向：不新增能力，而是让已有的依赖分析在更多形状上成立。对使用者而言，昇腾路径的可用性提升会先体现在「更多形状能编译且依赖正确」，而不是新算子名单变长。

第四，版本与结构在同一窗口动。tilelang 的 0.1.16 版本号 PR、TileFoundry 的 1491 文件重组、沐曦文档把 SDK 配套包推到 musa.5 并提高 glibc 门槛，三件事都属「发布前的准备」。下游若要跟版，需要同时核对三处：主仓 tag、后端仓的 musa.* 或 ascendc_pto 分支、以及构造期依赖（glibc、apache-tvm-ffi）。前一窗口出现过「只升 tilelang_musa 不升 tvm-ffi」的坑，本期文档把它写成了显式规则。

最后是 RISC-V 线。四源巡检 24 小时无变化，kubuds/tilelang-riscv-kubuds 的两个 kubuds- 分支、RuyiAI-Stack/tilelang-riscv 的 MLIR 路线、TongmingLAIC/tilelang-riscv 索引页与 TongmingLAIC/tilelang-tpu 的 SOPHGO 分支都停在原引用，这已是连续第三个窗口（11-07、11-09、11-10 留档）无变化。与 GPU 侧「一天三批」的节奏对照，RISC-V 侧仍是人工推进的周级节奏，差距不在工程量，而在有没有一条自动发现差距、自动验证、自动排队的回路。
