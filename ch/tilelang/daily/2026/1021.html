一、核心项目进展

1.1 主仓：向量化分析纳入非零循环下界（#3579）

合于 10-21 00:27，10 文件 +818/-198，承接 #2819 的 guard 修复，同时关掉 #2669、#2616 两个问题。原实现用 f(i) 与 f(floor(i / W) * W) 比较来判断表达式在每个向量组内是否同值，这隐含假设循环从 0 起；循环下界非零时，unit-step 向量化会把不同 lane 的地址算成同一组，广播装载与整组共享条件的证明随之失效。新的判定把循环最小值纳入分析，并在搬运混合精度转换时保留嵌套 guard。属会静默改变数值结果的编译器缺陷。

来源：https://github.com/tile-ai/tilelang/pull/3579

1.2 主仓：共享内存跨线程 WAW 检测（#2821）

合于 10-20 23:41，3 文件 +153/-19，修 #2698。共享内存上 S[tx] 与 S[tx + 10] 对单线程是两个地址，但不同线程的写可以重叠；原 WAW 检查对两次访问复用同一个线程变量，因此漏判、漏插屏障。修法是同迭代 WAW 用两个不同线程实例，并重命名各自的 Bind 定义，复用既有 RAW/WAR 模型，循环携带的 WAW 维持原处理。测试同时覆盖”该插”与”不该插”两种情形，含 guarded 写、Bind 派生索引、不相交分区与 threadIdx.y/z 置换，线程同步与 issue 两套用例 95 项通过。

来源：https://github.com/tile-ai/tilelang/pull/2821

1.3 主仓：不支持的 MMA tile 要求显式 K 填充（#2818）

合于 10-20 16:41，5 文件 +57/-14，修 #2715。通用 MMA emitter 可能在构造操作数布局之前悄悄缩小 K 原子，FP16 K=8 会算出错误结果；K=20、K=28 这类不规则尺寸则在共享内存布局推断阶段直接失败且提示不明。现在在 emitter 初始化时按架构固定的 K 原子校验 tile 的 K，不整除即抛 ValueError，带上输入 dtype、所需整除关系与建议的填充值（如 SM80 上 FP16 K=20 报原子 16、建议补到 K=32 并零填多余元素）。

来源：https://github.com/tile-ai/tilelang/pull/2818

1.4 主仓：fragment reduce 支持保留维度目标（#2815）

合于 10-20 16:35，8 文件 +343/-63，修 #2530。T.reduce_sum 等把 (64, 64) 沿 dim=1 归约到 (64, 1) 时编译期崩溃（Check failed: vars.size() == InputDim() (2 vs. 1)）。而 reduce_op.py 的文档契约明确同时接受 [X, Y] 与 [X, 1, Y] 两种输出形状并已构造对应期望形状，因此这是后端缺口而非误用。修复同时教通两条 lowering 路径，并保留无保留维目标的原行为。

来源：https://github.com/tile-ai/tilelang/pull/2815

1.5 主仓：TIR 谓词随整数位宽提升同步改写（#3550）

合于 10-20 09:59，4 文件 +950/-27。整数索引被提升到更宽位宽后，控制缓冲访问的边界检查仍按旧位宽计算，理论上可放过越界访问。新增 IndexPredicateRewriter，在 ConfigIndexBitwidth 与 FlattenBuffer 中记录每次访问的提升信息，访问语句处理完后再重写相关 guard；匹配限定在等价的加法与乘法形式上，保留无关条件、数据值表达式与定宽边界。新增索引提升、guard 改写、访问作用域、向量端点与冲突提升五类测试。

来源：https://github.com/tile-ai/tilelang/pull/3550

1.6 主仓：CuTeDSL scan 补参与线程偏移（#3576）

合于 10-20 12:49，2 文件 +30/-6。共享内存 scan lowering 在 #3536 里引入了参与线程偏移，但 CuTeDSL 侧的 helper 仍按旧构造参数生成调用，tl.CumSum1D(32, False, 0).run(...) 直接报构造参数错误；同批失效的 codegen 断言也是 #2815 两次 CUDA CI 失败的来源。修法是为一维、二维 cumsum/cummax helper 增加可选 thread_offset（默认 0 保持兼容），选参与 lane 与 warp 前先减去偏移，并给 CUDA 专属测试打上 requires_cuda。

来源：https://github.com/tile-ai/tilelang/pull/3576

1.7 主仓 CI：性能回归任务锁定 H100（#3569）

合于 10-20 16:00，1 文件 +15/-1。PR 回归机器人逐 kernel 比对延迟与基线，数字只在基线采集的同型号卡上有意义。组织正在引入自托管 H20 容量机型做常规正确性 CI，其标签集与既有的 [self-hosted, nvidia] 重合，若不区分会静默接走基准任务：H20 的 FP16 稠密算力约 148 TFLOPS，对 H100 的约 990 TFLOPS 差约七倍，FP64 通路也被大幅裁剪，每个基准都会报出并不存在的回归。现要求 pr-regression 任务必须带 h100 标签，并在开工前校验分配到的卡确实是 H100，标签写错即快速失败而非发布误导数字。

来源：https://github.com/tile-ai/tilelang/pull/3569

二、多后端适配（昇腾 / 沐曦 / 海光 / 摩尔线程）

2.1 昇腾主仓：L0 局部拷贝支持显式 pitch（#3511）

合于 10-20 14:16，24 文件 +1458/-187，是本窗口昇腾方向最大的一笔。此前一个 GEMM tile 只能由单次 L1→L0A/L0B 拷贝填充，非零目标原点被拒绝，每次拷贝又从自己的区域推紧凑 pitch，因此分开搬的两半拼不成目标整块；MajorK/MajorMN 转置装载也受限。新增 Ascend 专属参数 T.copy(..., l0_pitch=...)，按 fractal 块指定 L0 pitch，由调用方给出消费方 GEMM 的紧凑 pitch（含动态尾块），省略该参数则维持紧凑区域的原行为。示例中 64 行 A tile 的两半均写 l0_pitch=4。同步处理对齐后的目标偏移 lowering、物理边界与转置组校验、分配与缓冲版本间距。

来源：https://github.com/tile-ai/tilelang/pull/3511

2.2 昇腾主仓 CI：单 check 内拆分构建与测试（#3564）

合于 10-20 12:06，1 文件 +61/-9。把 Ascend 的构建与测试结果收进同一个 Test for Ascend PR 检查，用分步呈现失败阶段，并在 workflow summary 里列出各阶段结论。CANN 环境只装配一次、构建一次，AscendC 示例、PTO 示例与 Ascend 单测作为同一 job 的三个步骤分别执行；构建成功且工作流未被取消时，某套件失败后仍继续跑其余套件，最终整体仍判失败。CANN 变量经 GITHUB_ENV 传递。

来源：https://github.com/tile-ai/tilelang/pull/3564

2.3 昇腾仓：DSA 稀疏微调反向算子 indexer_bwd（#1887）

合于 10-20 15:26，2 文件 +1294。为昇腾 NPU 增加 indexer_bwd，服务 DSA 稀疏微调，同时支持 AscendC 与 PTO 两个后端。算子计算 lightning-indexer KL 微调损失对 dIndexQ、dWeights、dIndexK 的梯度，支持变长打包序列。实现分三档：持续化 GEMM 的快速 kernel 面向连续与共享行索引布局，带流水与更少搬运；通用 kernel 支持任意索引布局，含 -1 非法索引的梯度累加；另设 cast kernel 处理精度转换。

来源：https://github.com/tile-ai/tilelang-ascend/pull/1887

2.4 昇腾仓：SiTU-GLU 反向算子（#1877）

合于 10-20 15:22，5 文件 +854。语义对齐 CANN ops-nn 的 aclnnSituGluGrad，用于 Kimi K3 Stable LatentMoE 的门控激活反向：t = tanh(gate / beta)、s = sigmoid(gate)、situ_a = beta * t * s，上游分支按 linear_beta 是否为正走 tanh 或直通，输出 grad_gate 与 grad_up。精度基准是独立实现的 fp64 PyTorch 参考，并在 910B3 上与官方 aclnn 交叉校验，最大相对误差约 3e-3，符合 bf16 舍入预期。

来源：https://github.com/tile-ai/tilelang-ascend/pull/1877

2.5 昇腾仓：cann-bench 补 LSTM 与 GRU（#1892 / #1902）

两笔同日合入，分别 +2304 与 +2267。LSTM 覆盖 i/f/g/o 四门与 cell state 时序递归，支持多层堆叠（numLayers ≤ 8）、双向、batchFirst 布局、投影降维（projSize > 0，LSTMP）与可选 bias，权重按”每层每方向一个 tensor”的 TensorList 传入，输出 (y, hn, cn)，实现为 12 个 @tilelang.jit kernel；主力走融合 seq 路径，每（层、方向）一次 launch，核内按 T.serial(S) 逐时间步完成双 GEMM、bias 广播、门控与状态更新，与递归无关的 x 侧门控贡献由独立 xgemm 全时间步并行预计算。GRU 为 8 个 kernel，z/r/n 三门合一 GEMM 在 Cube、门控与状态更新在 Vector，跨核数据经 GM workspace 中转，并手动关掉 AUTO_SYNC——按提交说明，自动模式每时间步约产生 58 个 PipeBarrier。

来源：https://github.com/tile-ai/tilelang-ascend/pull/1892、https://github.com/tile-ai/tilelang-ascend/pull/1902

2.6 昇腾仓：CrossEntropy 基准中文版（#1801）

来源：https://github.com/tile-ai/tilelang-ascend/pull/1801

2.7 昇腾在审：PTO 向量化框架、tvm_ffi 后端与 DeepGEMM 对齐

来源：https://github.com/tile-ai/tilelang/pull/3512、https://github.com/tile-ai/tilelang/pull/3516、https://github.com/tile-ai/tilelang/pull/3577

2.8 海光：MLS 窗口常量 K 原点修复（#25）

合于 10-20 09:53，2 文件 +346。循环展开后 MLS 资源提升会丢掉常量窗口偏移，导致后续访问落到错误区间。修法是在选择单轴更新或前向增量寻址之前，先校验未被更新的那一维，必要时保守地重新初始化窗口；并在既有 MLS 测试上补回归覆盖。海光仓窗口内在审三笔：#26 处理 fp4 MLS 的 warp 分区（14 文件 +261/-144）、#18 补寄存器流水线与 warp-diverge 支持、#19 为分布式相关改动。

来源：https://github.com/tile-ai/tilelang-hygon/pull/25

3.1 TileOPs：分页 GQA 前向换装 paged warp 特化程序（#2668）

合于 10-20 22:41，8 文件 +901/-103。新增的 GQAPrefillPagedWSKernel（SM90）承接 GQAPrefillPagedWithKVCacheFwdOp：一次 append launch 把 chunk 写入分页（key 在融合 RoPE 下旋转，两者都在 FP8 池上量化）并旋转 query，随后由 GQAPagedFwdOp 的 warp 特化程序在被撑大的缓存上做注意力。该程序服务 head dim 256（单 query slot）与单 KV head 上宽于 16 头的 query 组（把 (T * H, D) 的 query 摊平为行）；FP8 程序未覆盖的维度 64 与 256 的池，经页的 16 位镜像读取，单次上限 4 GiB；请求可能拆分时按缓存长度排序、最长的先领，最多 128 个请求。

来源：https://github.com/tile-ai/TileOPs/pull/2668

3.2 TileOPs：FP8 lightning indexer 改双 warpgroup 消费（#2666）

合于 10-20 22:41，6 文件 +448/-2。原实现一个 warpgroup 乘 64-key tile，随后跑与乘积等长的 epilogue（每个 head 乘 key scale，FMUL 与 FADD 分开）；另有一次干净扫描以 2.5 TB/s 写窗口外的 -inf——按提交说明，这占 chunk-prefill-kscale 472 微秒中的 425 微秒；解码调用里单 query 占一个 CTA 走完 16384 个 key，耗时 289 微秒。新的 FP8LightningIndexerWSKernel（SM90）用 TMA warp 流式搬 64-key tile 给两个 consumer warpgroup 轮流处理，每 tile 一次 m64n256 FP8 WGMMA，消费者 epilogue 收敛为 csrc helper。

来源：https://github.com/tile-ai/TileOPs/pull/2666

3.3 TileOPs：MLA 解码走错位跷跷板程序（#2665）

合于 10-20 22:39，7 文件 +881/-590。MLADecodeSeesawKernel（SM90，512 + 64 latent，单 KV head）承接 MLADecodeWithKVCacheFwdOp，沿用 MLAPagedFwdOp 的错位跷跷板思路，按请求经 TMA 读 k 与 k_pe；程序本体迁到 kernels/attention/mla/seesaw.py，提供分页与密集两个入口，MLAPagedFwdOp 的拆分构建与原先产出同一份存储。一个请求的 key 被切成 min(sm_count // blocks, tiles // 2) 段，用 log-sum-exp 合并；密集段按输出 dtype 留部分结果，16 位输出经 warpgroup 自有 key 缓冲暂存后由 TMA 落盘。

来源：https://github.com/tile-ai/TileOPs/pull/2665

3.4 TileOPs：张量核上限改为操作数集合包络（#2661）

合于 10-20 22:27，4 文件 +125/-82。夜间跑批 39299002056 把 GemmW4A8FwdOp 标到 tensor_core.fp8 上限的 105% 与 108%，核查后是上限本身偏低：原校准取 cuBLAS 在随机操作数上的速率，而 700 W 功耗上限下操作数取值直接决定时钟，功耗低于随机 cuBLAS 的 kernel 可以跑在该速率之上。现在 gemm_throughput.py 同时计时全零操作数，把各操作数集合的最好速率记入 calibration_operands，取其中最大值作为校准值——与 HBM 校准既有的包络规则一致；h200.yaml 随之重标。

来源：https://github.com/tile-ai/TileOPs/pull/2661

3.5 TileOPs：后端测试与 torch-compile 基线可在非 CUDA 设备运行（#2658）

五、趋势观察

编译器正确性成为本窗口的主线，而非功能扩张。 主仓 9 笔合入里 5 笔是静默错误清理：向量化假定循环从零起（#3579）、共享内存 WAW 漏判（#2821）、MMA emitter 静默缩 K 原子（#2818）、fragment reduce 保留维崩溃（#2815）、索引位宽提升后谓词未跟（#3550）。这些缺陷的共同点是不报错、只出错结果或漏屏障，属于用户在生产里最难定位的一类。同日 TileOPs 的 #2661 也在修”性能上限口径”，说明项目正把”数字可信”当成与”跑得快”同级的工程目标。

昇腾线从补示例转向训练侧。 五笔合入里三笔是反向或递归算子（indexer_bwd、situ_glu_grad、LSTM/GRU），且 situ_glu_grad 直接对齐 Kimi K3 Stable LatentMoE 的门控激活并给出 910B3 上与 aclnn 的交叉校验数据。配合 #3577 对 DeepGEMM-Ascend 配置选择与 epilogue 的对齐，昇腾侧的覆盖面正从推理前向扩到训练反向、状态递归与大模型 MoE 门控。

PTO 正在成为 AscendC 之外的第二条执行路径。 在审的 #3512 是 2.1 万行的向量化框架（T.Parallel → PTO VMI，目标 Ascend 950），#3516 拟把 tvm_ffi 设为 pto 目标的默认执行后端，加上 #3530、#3573、#3581、#3582 一组拷贝与谓词修复，PTO 线的工程量已明显超过单点 patch 的量级。主仓同时用 #3511 补 AscendC 侧的 L0 局部拷贝能力，两条路径并行推进而非替换关系。

工具链外溢到独立仓。 一日内出现三个新仓（中文教程、CANN 社区算子仓、Hexagon 后端实验）与一套 VS Code 扩展，主仓又把 lower trace 整体迁往 devkit（#3583，删减 4390 行）。社区侧的扩展速度已经快于主仓的模块划分，这与 7 月”多后端语言方言”重构的方向一致：主仓收窄为语义与 IR，工具与后端实验外置。

CI 口径的显式化值得留意。 #3569 把性能回归锁到 H100 并对误标卡快速失败、#3564 把 Ascend 构建与测试拆进同一 check 的分步、#2661 用操作数集合包络重标张量核上限——三笔都是”让数字可比”，直接影响后续 PR 的准入门槛。
