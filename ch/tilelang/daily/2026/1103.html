今日重点

这一天的主线只有一件事：TileLang 把 DeepSeek 的 MLA 解码内核搬到了昇腾 950 上，而且是按编译器可调度的写法搬的。#3678 一次性加入 1997 行、20 个文件、42 次提交，覆盖 BF16 prefill 与紧凑 FP8 decode 两条路径，还带可选的 FP8 与 FP4 额外 KV 缓存、attention sink、非法索引与逐 query 独立长度。实现方式值得注意：注意力循环、在线 softmax、反量化与调度全部写在 TileLang 里，靠 T.Stage 让编译器管理缓冲版本与同步，QK 与 PV 用同一块 L0B 存储环的两个不同 layout 视图，L1 的落位用 T.annotate_buffer_addresses 直接指定；prefill 在一个累加器分配里分出四个不相交的输出切片，归一化算完一片就排空一片。为了让这套写法成立，编译器侧同时补了三处能力——L0C 到 UB 的拷贝保留 NZ 输出、每个 AIV 流在自身流水线之前选定、显式调度的阶段在物理发射相位相同时保持源码顺序。目标形状写得很窄：头数 64、Dqk 与 Dv 都是 512、topk 为 64 的倍数。

第二条线是修一处真实的编译器回归。#3734 处理的是 SM100 上的 ViT 前向：Cannot convert type float32x16 to CUDA type。路径很长但每一步都清楚——向量化规划器为一个 256 位的 BF16 存储选了 16 个 lane，并推迟 cast 约束，指望 DecoupleTypeCast 把计算和访存拆开；而 #3579 之前刚把「读内存的守卫」从解耦里排除（重复这些守卫会改变语义），于是最终合法化那一步仍在按推迟策略选宽度，残留的 FP32 表达式被撑成 512 位向量，CUDA 后端表达不了。修法是把推迟约束做成规划器的参数而非 IR 属性，只有最后一步合法化传 false，守卫的 FP32 转 BF16 降到 8 个 lane，成功解耦的 BF16 拷贝仍保留 16 个 lane；地址 cast 也从数据向量类型约束里摘出来，靠既有的访问分析判合法性。

第三条线是调试体验。#3703 把 #line 指令从「每条 TIR 语句只锚定首行」改成可选的分级发射：级别 0 关闭、1 保持原状、2 以上对每一行生成的非空行重新锚定，包括被展开成多行的语句和收尾大括号。实现放在 CUDA、HIP、CPU C、C host、Metal、Ascend 共用的 C 系输出流里，不动 vendored 的 TVM；没有源码跨度的语句和函数显式切到 <tilelang-generated>，用户原文逐字保留以免破坏宏续行与字符串字面量。新增环境变量 TILELANG_EMIT_LINE_DIRECTIVES 作为 Python 侧的默认值，在缓存查找之前折进 pass 配置。本地 42 项通过、6 项跳过，CUDA 与 HIP 的用例在作者机器上被跳过，cuda-gdb 的实际行为尚未直接验证——作者自己写明了这一点。同日 LSP 仓跟进一笔，把 CUDA 调试对齐到新的行映射。

算子侧的节奏没有停，但方向变了。TileOPs 单日 7 笔合入里有 6 笔性能、1 笔测试基建，全部来自同一作者；每笔仍然附 H200 实测表与清单回归门槛。其中最有价值的是 #2816：新增一个只在测试时存在的 tileops_test 目标，在 PrivateUse1 上为每个算子算出共享的 workload 参考，让 tests/ops 的冒烟测试不再必须站在 CUDA 上。改动 1281 行、59 个文件，作者同时把边界写清楚了——比对共享参考只能证明后端无关的契约与可移植性，不能证明真实后端的数值正确性，那条线仍挂在 #2611。

最后是 TileFoundry 的一条暗线。#283 把「共享内存访问应当如何排序」做成分析层：一个同步族按 lowering 的发射顺序走每个函数，对每次共享内存访问取指令、发射 mesh、操作数与字节范围，在冲突访问前规划 commit/wait 与作用域内栅栏。83 个调度夹具里它规划 52 个、拒绝 31 个（24 个用 TMA 拷贝、6 个用 wgmma，两者的完成语义尚未声明；1 个需要在跨线程边界不等的循环里插栅栏）。配套的 #285 在审，把计划变成 CUDA lowering 并反向校验：sm_89 单卡上能构建的 7 个程序里 6 个与参考完全一致、synccheck 与 memcheck 全干净，而按 main 的方式 lower，同样是这 7 个里有 4 个结果错误；#283 的描述里给出的直接症状是 sm_89 的 E4M3 GEMM 最大偏 659。

一、核心项目进展

1.1 主线：昇腾 950 的持久化 FlashMLA 内核，BF16 prefill 与紧凑 FP8 decode 双路径（#3678）

合于 11-02 09:26，新增 1997 行、删除 17 行，20 个文件、42 次提交，是本窗口最重的一笔。内核面向昇腾 950，prefill 走 BF16、decode 走紧凑 FP8，可选 FP8 与 FP4 的额外 KV 缓存，并支持 attention sink、非法索引与逐 query 的独立长度。注意力循环、在线 softmax、反量化与调度全部用 TileLang 表达，靠 T.Stage 与编译器管理的缓冲版本和同步驱动；QK 与 PV 共用一块 L0B 存储环的两个不同 layout 视图，L1 落位由 T.annotate_buffer_addresses 指定；prefill 在既有累加器分配内分出四个不相交输出切片，并配独立同步事件，归一化完成一片即排空一片；decode 用整行输出拷贝。编译器侧补三处支持：L0C 到 UB 的拷贝保留 NZ 输出、每个 AIV 流在其流水线之前选定、显式调度阶段在物理发射相位打平时保持源码顺序。目标为头数 64、Dqk 与 Dv 均 512、topk 为 64 的倍数，pair gather 沿用已记录的零 burst 代码生成绕法；随附正确性与基准运行器、缓冲复用与 query 边界回归、以及带 FlashMLA MIT 声明的 README。

来源：https://github.com/tile-ai/tilelang/pull/3678

1.2 主线：cast 解耦被跳过后残留的 512 位向量，SM100 上 ViT 前向编译失败（#3734）

合于 11-02 09:05。在 e8225d7f5 上，面向 SM100 的 ViT 前向在受守卫的 FP32 转 BF16 输出存储处报 Cannot convert type float32x16 to CUDA type：规划器为 256 位 BF16 存储选 16 个 lane 并推迟 cast 约束，期待 DecoupleTypeCast 把计算与访存分离；#3579 让解耦跳过那些会读内存的守卫之后，后续 LegalizeVectorizedLoop 仍沿用同一策略继续推迟，残留的 FP32 表达式于是变成 512 位向量，CUDA 侧无法表示。修法是把 defer_cast_constraints 做成规划器的 C++ 参数（不是 IR 属性），由调用方按阶段选择：LayoutInference 与 LowerTileOp 维持 true，最终合法化一律传 false，并把算出的宽度作为显式 vectorize_hint 前传，避免重写器用默认策略重新规划。守卫的 FP32 转 BF16 降到 8 个 lane，成功解耦的 BF16 拷贝仍保留 16 个 lane，守卫安全检查保留；地址 cast 与访问指针参数从数据向量类型约束中排除，连续地址降为标量基址加步长，由既有访问分析判定合法性，int64 索引的对齐向量访问与四 lane 原子用例不受影响。

来源：https://github.com/tile-ai/tilelang/pull/3734

1.3 主线：#line 指令改为逐行重锚定，调试器映射可选密集模式（#3703）

合于 11-02 04:06，682 行新增、11 个文件。此前的 #line 发射只锚定一条 TIR 语句生成的第一行，后续行会被编译器逻辑行号推进，cuda-gdb 于是把生成的加载、运算与存储归到无关的 Python 行；合成语句与收尾大括号可能继承已推进的映射，没有源码跨度的函数还会继承前一个函数的源文件。本笔把 tl.emit_line_directives 扩成分级：0 或 False 关闭并保持默认，1 或 True 维持语句级，2 以上对每一行非空生成行重新锚定（含多行展开的语句与收尾大括号）。实现落在 C 系输出流，覆盖 CUDA、HIP、CPU C、C host、Metal 与 Ascend，未改动 vendored TVM；同时记录语句与函数的源码跨度，无源区域显式切到 <tilelang-generated>，用户原文逐字保留以避免破坏宏续行与字符串字面量。新增 TILELANG_EMIT_LINE_DIRECTIVES 作为 Python 侧默认值，在缓存查找前折进 pass 配置，显式配置优先（包括默认值非法时）。本地用 Metal 加 LLVM 构建验证：行指令与 compile-only 两组 42 项通过、6 项跳过；去掉指令后，向量化加法与条件选择两个夹具在级别 0、1、2 下产物完全一致。作者注明 CUDA 与 HIP 用例在本机被跳过，cuda-gdb 行为未直接测试。

来源：https://github.com/tile-ai/tilelang/pull/3703

1.4 主线：注意力示例按设备共享内存上限推 tile，RTX PRO 6000 上由 2 过 7 败变为 9 全过（#3702）

合于 11-02 06:59，345 行新增、13 个文件。多个注意力示例的非调优路径把 Hopper 尺寸的 tile 写死，在 sm_86、sm_89、sm_120 上每块动态共享内存上限约 99 KiB，启动直接失败：报错原文是要求把允许的动态共享内存设为 163840 字节，而设备 0 每块最多 101376 字节。现在每个示例从 shared_memory_per_block_optin 推 tile，做法沿用既有的 GQA decode 示例（example_gqa_decode.py）；数据中心配置不变，因为每条分支只在低于上一档 tile 需求时才触发。约 99 KiB 设备上的落点：attention sink 四个示例分别是 64×64 两阶段 128 线程（前向）与 64×32 一阶段 128 线程（反向），example_gqa_bwd.py 前向 64×64、反向 64×32，example_mla_decode.py 取 BLOCK_N 32、BLOCK_H 16。后两者新增 threads 参数：64 行或 16 行 tile 下 T.gemm 需要四个 warp 才能让每个 warp 独占整块 16 行，256 线程会直接 lower 失败（分别报 acc_s 与 acc_s_cast 的 layout 冲突、以及 M=16 N=32 无合法 warp 划分）。另外 flash-attn 2.x 没有 sm_12x 内核，四个 varlen 示例原本在参考步骤就抛错，现改为探测一次 flash_attn_varlen_supported，不支持则改用纯 PyTorch 的 varlen_attention_ref（覆盖 GQA、右下对齐的 causal 与 window_size）。验证在 RTX PRO 6000 Blackwell（sm_120）上：CUDA 9 项全过（原为 2 过 7 败），CuTeDSL 同样 9 项全过；H100 有 227 KiB 可选上限，仍走原 tile，同样 9 项通过。

来源：https://github.com/tile-ai/tilelang/pull/3702

1.5 主线：CUDA float32x8 位转换改用内建 bit cast，SASS 指令从 19 条降到 18 条（#3748）

合于 11-02 09:58，20 行新增、3 行删除，修 #3679 并取代 #3681。改动只用 CUDA：把 float32x8 的位重解释从位运算序列换成 __builtin_bit_cast(uint64_t, make_float2(v, v))，生成的 SASS 指令数从 19 条降到 18 条。幅度不大，但属于编译器后端里典型的「语义等价、产物更短」的一类收尾。

2.3 昇腾在审：cython wrapper 缓存符号形状解析，承接宿主开销这条线（#1967）

11-02 更新。#1967 在 cython wrapper 里缓存符号形状的解析结果，目标是把每次调用的 dispatch 开销继续压下来，对应缺陷 #1898。这条线与上一期合入的 #1948 是同一目标的两个落点：#1948 把每次调用无条件构造 TVM Analyzer 的固定开销改成惰性构造（910B3 上从约 450 微秒降到约 106 微秒），#1967 处理的是符号路径上重复解析本身的成本。同族还有在审的 #3757，主线侧对齐动态 ABI 与共享符号校验：按 Var 对象而不是打印名做键，避免同名不同变量被当成同一符号，并把单例维度上的 stride 只当兜底、不让它抢先决定取值。

3.5 TileOPs：Norm 统计量改为减行内元素，消掉靠近 1e36 的溢出（#2811）

合于 11-02 05:10。根因写得很直接：所有均值与方差内核都对原始行做 fp32 求和，和随行的偏移量增长（约 N 乘 x ），靠近 1e36 的行直接溢出，全部输出变成 NaN；即使没溢出，均值也会在偏移量量级上舍入，x − mean 把这个舍入带进每个元素，于是常数行算出的方差等于舍入的平方，归一到正负 weight 而不是 bias。修法是给每个由行构成的 fp32 量加一条不变式：它只被行的扩散度约束，不被偏移量约束——实现上取「行内某个元素」作基准再相减，warp 主导的核用 warp 首元素、分片核用行的首元素。这条与上一期报告里 #2812 列出的四个 Norm 算子缺陷是同一类问题的正面修复。

4.2 跨行与转置视图的 SIMD 加载丢掉 DMA 依赖，根因落在逻辑区域重建（#3749）

同批里技术含量最高的一条，报告人环境为 main 分支 e8225d7f5、Ascend950PR、CANN 9.2.0。问题是两处连续 SIMD 加载丢掉了对更早一次 GM 到 UB 拷贝的依赖：一是行主序加载从行中间开始并跨到下一行，二是访问转置视图且物理连续维不是最后一个逻辑维。根因路径写得很细：生成的 tl.access_ptr 覆盖物理加载范围，而 MemoryAccessDetector::LogicalPointerRegion 重建出的逻辑区域漏掉了其中一部分，依赖分析于是认为输入 DMA 与加载无关，AutoSchedule 把输入拷贝挪到加载之后，InsertSync 也不发 MTE2 到 V 的 set/wait。最小复现里 work.shape 为 (2, 128)，先 T.copy(A, work[1, 0:64])，再在 T.SimdVF() 里 T.simd.vld(work[0, 64]) 读 128 个连续半精度元素：生成的读描述符是 tl.access_ptr(work[0, 64], 128, 1)，物理覆盖 [64, 192)，其中 [128, 192) 正是刚被 DMA 写过的部分，而重建出的区域是 work[0:1, 0:128] 即物理 [0, 128)，完全错过被写区间；行数按 ceil(128/128) 算成 1 行，起始列 64 没被计入。这条与本窗口主力在补的 FlashMLA、PTO 向量化是同一块地基，一旦命中就是静默错结果。

五、趋势观察

这一天最值得记的判断是：昇腾不再是「适配目标」，而是「首发目标」。FlashMLA 这种 DeepSeek 自家解码路径上的核心内核，直接以昇腾 950 为目标写在主线里，用的还是 T.Stage、annotate_buffer_addresses 这类为显式调度准备的底层能力，而不是另开一个仓做移植。配合编译器侧那三处支持（L0C 到 UB 保留 NZ、AIV 流在流水线前选定、显式阶段按源码顺序发射），可以看出昇腾路径正在从「能跑」转向「能按调度意图跑」。

第二条线索是正确性的重心在下移。上一期主线为 TIRX 迁移回退了一整套 ThreadSync 正确性改进，这一期立刻出现两条补位：主线 #3752 调 z3 求解资源上限，#3735 提出用模块化索引的不相交性减少需要证明的形状；同时 #3749 把一处「依赖分析看不见物理加载范围」的缺陷挖到了 MemoryAccessDetector::LogicalPointerRegion 这一层。把这些和 TileFoundry 那条暗线放在一起看——分析层能证明 83 个夹具里的 52 个共享内存排序，而 lowering 按 main 的方式做会让 7 个程序里的 4 个算错——同一个信号出现了三次：TileLang 现在的主要风险不是功能不够，而是「生成的代码看起来对、实际不对」，而团队选择的做法是把正确性做成可拒绝的证明，而不是靠补丁逐个堵。

第三条是测试与契约开始独立成层。TileOPs 的 tileops_test 把冒烟测试从 CUDA 上摘下来，compile-contract-gate 把 dispatch 契约与 workload 数据生成拆开，两者都在同一小时内合入；作者同时明确写了「共享参考不能证明真实后端正确」。这种把「能测什么」和「证明了什么」分开表述的习惯，比多合几笔性能补丁更能说明这个项目正在走出原型期。

最后注意一个反差：算子侧单日 7 笔性能合入、6 笔都带 H200 实测表格，而新闻侧三通道 24 小时零命中。TileLang 的对外声量仍然集中在「DeepSeek 开源昇腾组件」这类事件上，日常进展几乎只发生在仓库里。对跟踪这个项目的人来说，这意味着日报的主体只能是提交与 PR，而不是报道。
