今日重点：主仓 JIT 加入进程级并行编译，绕开 GIL 对线程池的限制

#3903 于 11-23 11:57 进主干，改 6 个文件，增 552 行、删 100 行。

tilelang.par_compile() 与 kernel.par_compile() 新增可选参数 executor="process"。提案写明的动机是：线程式并行在 Python 侧偏重的编译负载上受 GIL 限制。

进程模式下，父进程先规范化 target、执行后端、pass 配置与缓存根目录。内存或磁盘缓存已命中的配置不再起 worker。未命中的按 key 去重后再分发。

每个 worker 用 KernelCache.compile_to_disk() 把结果写进磁盘缓存，返回已发布的 cache_path。worker 的异常类型与 traceback 跨 IPC 保留。

父进程用 KernelCache.load_published_entry() 直接加载，不回退串行编译。出错时立即取消已排队的 future。

不支持磁盘缓存的后端在起 worker 之前被拒绝，例如 TorchKernelCache（supports_disk_cache = False）。这样不会改动全局缓存状态。

线程模式仍是默认值。进程模式要求开启缓存，并要求脚本带 if __name__ == "__main__": 保护入口。

提案记录在昇腾上以 64 进程验证，覆盖 128 组 SwiGLU 与 MoE 配置。回归测试落在 testing/python/jit/test_tilelang_jit_parcompile.py。用例含自定义 TILELANG_CACHE_DIR 下的进程编译与去重。

来源： https://github.com/tile-ai/tilelang/pull/3903

1.2 布局与分片对象自持占位变量，输入维数上限 16 取消

#4416 于 11-23 21:07 进主干，改 23 个文件，增 607 行、删 583 行。

此前的三个布局类型依赖进程级静态 tirx::Var 单例。三个类型是 tl.Layout、tl.Fragment 与 tl.PartialFragment。单例是 InputPlaceholder(0..15) 与 ReplicationPlaceholder()。

派生问题有三条。FFI 序列化要手写反射存取器。输入维数被硬性限制在 16。src/layout/ 之外的调用方会通过共享全局 Var 隐式耦合。

改法是对齐 TVM 的 tirx::IndexMap。LayoutNode 持有 forward_vars_，FragmentNode 持有 replicate_var_。两者在 forward_index 与 forward_thread 之前用 SEqHashDef() 注册。

由此两个 JSON 图接口可直接序列化。StructuralEqual 与 StructuralHash 具备 alpha 等价性。构造函数中统一用 MakeLayoutVars(ndim) 与 MakeReplicateVar() 生成规范变量。

1.4 TVM 子模块修 Z3 两处误证明，主仓跟 bump 在审

TVM 子模块 tilelang_main 分支窗口内两笔合入，均由同一位作者提交。

#97 修两处可靠性缺陷。其一，VisitShiftOp 在未 push() 的共享求解器上执行 solver->add，任何移位表达式都会永久约束移位量 b。后果是在 b < 0 或 b >= 64 的外层作用域里，后续谓词都可能被判为可证。

其二，DivNode 与 ModNode 走的是向零截断，而 Z3 对 Int 的原生 / 与 % 是欧几里得语义。因此 CanProve(truncmod(a, 4) >= 0) 在 a 可为负时也会假成功。改法是用 floordiv 与 floormod 对称编码，按 a >= 0 分支取式。

#96 单独修常量有符号右移，改为整数运算。主仓侧的跟进 #4482 仍在审。

来源： https://github.com/tile-ai/tvm/pull/97

二、多后端适配（昇腾 / 海光 / 摩尔线程 / 沐曦）

2.1 PTO 生成器补循环携带标量，五个 DeepGEMM 用例恢复编译

#4418 于 11-23 10:17 进主干，只改 1 个文件，增 23 行、删 11 行。

问题出在 CANN 9.2.0 自带的 PTODSL（PTOAS 0.65）。五个 DeepGEMM 的 scale 尾巴与 group padding 用例编译失败，都走到 grouped scale 变换里的同一个循环。MLIR 拒绝生成的 scf.while，报 operand #0 does not dominate this use。

内核把 group_start 初始化为 0，再在 if lo > 0 内更新。首次迭代要用分支选出的值。PTODSL 的活性分析漏掉这条依赖，直接用分支内的值当循环输入。当 lo == 0 时该值没有定义。

修法是 PTO 代码生成器在输出 while 头之前收集循环携带的局部量。对已在作用域内、且在循环体中被赋值的普通标量，各输出一次裸名字读取。生成的 PTODSL 在循环入口因此多出 group_start、lo、num_ranges 三行读取。

来源： https://github.com/tile-ai/tilelang/pull/4418

3.3 FlashQLA 修 sm120 上共享内存被编译器提前读取

QwenLM/FlashQLA 的 #55 于 11-23 18:37 合入，改 1 个文件，增 5 行。

根因经 PTX 核对。TileLang 0.1.12 的 tl::mbarrier_wait 位于 tl_templates/cuda/barrier.h。该处内联汇编没有 "memory" clobber。

在 blackwell_sm120/fused_fwd.py 中，S warpgroup（tx < 128）从不写静态共享内存。它只读 g_exp_shared[block_S - 1] 这个编译期常量偏移。特化到 use_initial_state=False 时，nvcc 或 cicc 把 ld.shared.f32 提升到 for i_s 循环之外。读到的就是未初始化共享内存。

后果是第 0 块之后状态误差变大。未初始化共享内存若含 NaN 位型，则直接出 NaN。

修法保留 torch.empty(...) 与 T.clear(h_fragment) 不动。随后在 barrier 等待之后插入一次块内栅栏调用。插入位置是 T.barrier_wait(bar_1, i_s % 2) 之后。调用形式为 T.call_extern("void", "__threadfence_block")，在两个 warpgroup 都加。PTX 上表现为 membar.cta。

验证环境为 RTX 5090、CUDA 12.8、PyTorch 2.8.0+cu128、TileLang 0.1.12。

来源： https://github.com/QwenLM/FlashQLA/pull/55
