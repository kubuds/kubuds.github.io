今日重点

这一天的主线是一笔「把性能要回来」的修复。上一窗口合入的 #3643 解决了一个真实的正确性问题：分别调用的 ThreadSync("shared") 与 ThreadSync("shared.dyn") 可能把同一个命名屏障 ID 分配给互不相交的线程组。修法是让后一次调用保留前一次已经用掉的 ID，但这条保留规则同时挡住了另一件事——同一组线程在两个作用域之间本来可以复用同一个 ID。代价直接落在 TileKernels 的 mhc_pre_big_fuse 内核上：这个内核每块 96 个线程，线程 32 到 95 跑两段式 cp.async 流水线，异步等待之后的同步在第一遍拿到 ID 3，同一批 64 个线程的缓冲依赖同步在第二遍拿到 ID 4，多出来的那个 ID 让编译产物声明的屏障资源从 4 变成 5；在 B300 上跑隐藏维 1280 时，屏障占用上限因此从 16 块/SM 降到 12 块/SM，寄存器、共享内存与同步指令数都没有变化。#3761 的处理办法是让 ThreadSync 接受一个有序的作用域列表，CUDA 流水线改成 ThreadSync(["shared", "shared.dyn"])，同步仍按原来的作用域顺序规划与插入，但部分屏障的 ID 在两个作用域都处理完之后才统一分配；跨作用域共用一个 ID 之前，用一个全新的分析器证明参与谓词在整个候选线程范围内成立，分支与 Bind 上下文由 ConstrVisitor 提供，线程相关的谓词按证明义务处理而不是默认成立，已证密的密集组直接用包围盒体积、跳过部分线程数的枚举，未证明的组则把作用域留在键里并让参与者计数一起入键，显式编号的屏障（含更早一次 ThreadSync 分配的 ID）继续保留。改动 401 行、涉及 4 个文件。

作者在描述里做了一个很干净的归因实验：单独改编译产物里声明的屏障资源数、不动任何可执行指令，就能复现同样的变慢。这类实验值得记一笔——它把「性能回退」从观感变成了可指认的单一变量，也让修复的验收标准变得明确：不是笼统地跑分变快，而是资源声明回到 4、占用回到 16 块/SM。

第二条是供给侧的减法与口径统一。#3736 把 tilelang/language/ast/、tilelang/language/parser/ 与 tilelang/language/tir/entry.py 一并删掉，这些是早期本地 TVMScript 解析器分叉留下的模块，约 3380 行 Python，仓内已无调用方：语言层现在通过 tilelang.language.tir.common 使用上游的 tvm.tirx.script.parser 接口，AST 与语句覆写注册在 tilelang.language.overrides，T.prim_func 与 T.macro 由 tilelang.language.eager 导出。实际改动是新增 1 行、删除 3384 行、10 个文件，同时移除了 docs/conf.py 里针对 *language/ast* 的忽略规则；公开的语言层导出由方言测试与前端口测试兜住。#3546 修的是自动调优的设备口径：set_autotune_inputs 安装的供给闭包从一个调用点从不传入的参数上解析基准设备，实际传过去的是内核参数列表，于是 CUDA 或 CPU 的兜底分支在没有 CUDA 的机器上把每个捕获张量搬到 CPU，每一轮调优都因启动器设备不匹配失败；现在闭包改用 get_current_device()，与默认张量供给同一策略，CUDA 行为不变、昇腾与 MPS 改为在当前设备上供给、其余后端仍退到 CPU。验收在双卡 Ascend950 上：三笔昇腾自动调优回归修前全败、修后全过，主仓 testing/python/autotune/ 12 项通过、28 项跳过，另有 3 项因该机没有 CUDA 而失败，作者明确留给 CUDA CI 验证。

第三条在昇腾侧：GM 到 L1 的拷贝从「一个描述符一个矩阵」扩到整批。#3689 允许把 [B, M, N] 区域写成一个 T.copy，lowering 生成批量 ND2NZ 描述符，保留源侧的批与行 stride，目的侧的批间距按物理布局推导，转置批量走 DN2NZ；超出 GM 边界的源批直接跳过并保持目的存储不动，M/N 的尾部补零只作用于合法批。既有二维与单矩阵行为不变，实现只针对 AscendC 后端、且要求 L1 目的端是规范矩阵布局，PTO 不在本次范围内。验证在 Ascend950DT 与 CANN 9.2 上：50 个 AscendC 示例测试与 1733 个昇腾单测通过，其中 28 个设备用例覆盖批与 M/N 尾块、整批越界、非连续源 stride、目的存储更大与矩形转置；CUDA 与 PTO 用例被排除，CI 镜像用的 CANN 9.3 未在本地测到，这一点作者写在了描述里。改动 579 行、10 个文件。

第四条是 TileFoundry 的一条暗线落地。上一期报告里它还挂在「在审」，这一窗口合入：#285 让 sync 分析规划出的提交、等待与栅栏真正由 CUDA lowering 发射，并逐条反向校验实际发射与计划是否一致，不一致抛 LoweringError。语料上的结果是默认流程 14 个程序加上同步、拒绝 31 个，这 14 个的 TIR 与主线差别只有新增语句，另有 30 个与主线完全相同；单张 sm_89 上跑了 7 个能构建且带同步的程序，6 个与参考完全一致、synccheck 与 memcheck 全干净，而同样这 7 个按主线的方式 lower 有 4 个结果错误。作者在动机里给的直接症状是 sm_89 的 E4M3 GEMM 最大偏 659。这一笔 788 行新增、214 行删除、25 个文件，把「分析能证明」推进到「发射必须与证明一致」。

1.1 主线：ThreadSync 允许跨存储域复用部分屏障，B300 上屏障占用从 12 回到 16 块/SM（#3761）

1.4 在审：条件中的标量 cast 不再压缩数据向量宽度，承接昨日 #3734（#3759）

11-03 14:09 更新，新增 148 行、删除 29 行，2 个文件。这是对昨日合入的 #3734 的收尾：#3734 在 DecoupleTypeCast 之后正确收紧了数据 cast 的宽度限制，但也让「标量条件里的 cast」开始限制数据向量宽度——在 b5cb02633 上，一个受守卫的 BF16 拷贝可能因为条件里有一个 int64 cast，从 16 个 lane 被压到 4 个，哪怕该条件在 16 个 lane 上完全一致。修法是把规划器已有的条件一致性分析复用到 cast 宽度豁免上，把 if 语句、tirx.if_then_else 与标量谓词的 Select 条件从它们的子句里分出来单独访问，条件里的 cast 不再施加数据类型宽度限制，子句里的 cast 仍然施加，并在带逐 lane 向量谓词的目标上保留条件 cast 的约束；#3579 的内存守卫行为与 #3734 修好的守卫 FP32 转 BF16 限制都保持不变。回归覆盖 8 lane 与 16 lane 的一致守卫、三种条件形式、子句内的 FP32 cast、向量谓词与舍入位分组，九个 int64 守卫用例修前失败，最终合法化与 cast 舍入两组套件共 74 项通过。

1.5 在审：两处用户可见错误改为明确报错（#3765 / #3767）

两笔都在 11-04 01:10 前后更新，同一个报告人提交。#3765 对应 #3653：由单个线程索引边界守卫的部分屏障，当该边界是 warp 大小的整数倍时，整 warp 的线程对条件判断一致；但通用算术证明漏掉了外层分支使用按位 & 时的 thread_binding < 448，ThreadSync 直接中止。本笔在线程维是整 warp 数时显式接受这种情形（同时覆盖边界等于或超出该维的情况），其余条件仍走既有证明路径。 #3767 对应 #3005：fragment 跨线程分布，同一 T.Parallel 体内用两个结构不同的索引读写同一 fragment（例如 buf[i] 与 buf[(i + 1) % N] 这种跨 lane 模板）无法在不做跨线程交换的前提下 lower，此前 ParallelOpNode::RecordBufferAccess 撞上 StructuralEqual 的 ICHECK，暴露成编译器内部断言；现在改成 ValueError，把两个索引表达式都写进报错并说明 fragment 不能这样访问。两笔都属于「把内部断言换成用户能读懂的诊断」，对使用者体感的影响比改动规模大。

来源：https://github.com/tile-ai/tilelang/pull/3765、https://github.com/tile-ai/tilelang/pull/3767

1.6 在审：带 padding 的共享 tile 无法整体拷贝时回退，2-CTA 的 TMA 字节按对等 leader 记账（#3738 / #3766）

两笔都在 11-03 21:31 到 21:47 之间更新。#3738 修 #3704：从比 padding 后共享 tile 更小的全局区域做 T.copy（例如 K=100 拷进 BK=112）会被 ClassifyWarpSpecializedCopy 与 SelectCopyInstForLowering 判成 TMA 整块拷贝，然后在 lowering 硬失败，报 s_extent == g_extent (112 vs. 100)。原因是选择逻辑只检查了最后一维对齐、dtype 配对与全局 stride，没有检查 padding 后的范围能否构成一次整块拷贝；本笔补上这一判据，不满足时回退到普通拷贝路径。#3766 修的是 cluster 场景下 TMA 字节计数：cta_group::2 的 TMA load 会清掉屏障地址的对等位，一对 CTA 的字节都落在偶数 CTA 的屏障上，而带 cluster 屏障的 tma_copy 原先只对 rank 0 期待 cluster_size × tile_bytes——在 (2,1,1) 与 (1,2,1) 上碰巧对，在 (4,1,1) 与 (2,2,1) 上 rank 0 只收到 2 份却期待 4 份，另有字节落到 rank 2 的屏障上。两笔都不是新功能，属于「边界条件一破就报内部错误」的那类缺陷。

3.6 TileOPs 在审：短 varlen 按 KV 组打包、L2 flush 改为只读（#2819 / #2822）

#2819 在 11-03 23:37 更新，是 #2496 的一部分，给 SM90 上的 GQAVarlenFwdOp 加了一个打包的 warp 专用程序：当一个请求用它的 KV 头分组按位填满一个 tile 更省 tile 时，键与值只按 KV 头读一次；打包内核的拒绝逻辑用一个代价模型衡量调用的批、打包后的 query 总数与组大小，只有当形状保证的节省超过实测的 9% 单头 tile 开销时才接手；宽窄两类 item 在同一次发射里交替领取，不做宿主回读、不额外加同步；当设备上数出的未拆分 item 少于 SM 数时，单 tile 的打包请求把键扫描拆成多段、经 fp32 工作区合并。窗口侧还有两笔实测收益：窗口行省 1% 到 9%，交错 RoPE 行省 3% 到 6%。同时修了主线上三个问题：带 sink 且 score scale 大于约 2.4 时无可见键的行返回 NaN（单头 warp 专用与 FP8 warp 专用两个程序）、后备的 query 旋转在请求首个键之前的行上先读 RoPE 表、以及被拒的负控制用例让调用方帧留在引用环里导致一个测试的 CUDA graph 在另一个测试的捕获期间被销毁。测试节点从 173 增到 197。#2822 在 11-03 19:01 更新，把 bench_kernel 的 L2 flush 从「对 int8 缓冲做 zero_()」改成「读一个私有 int32 缓冲，大小是报告 L2 的两倍」，缓冲由固定种子的 CPU 生成器一次抽出；CUDA 上用 Triton 内核做这次读（每元素一次加载、每 16 KB 一块一次 atomic_max），不用 torch 自己的归约是因为把它当 flush 会拖慢下一次 Marlin w4a16 调用 1.3 到 1.5 微秒。收益在 H200、1500 MHz、CUPTI 内核时间（3 次运行各 30 次调用的中位数）上：2048×11008 f32 的 Sum 从 27.81 降到 21.38 微秒，1024×11008 f32 的 Ge（torch-compile）从 31.31 降到 25.67，1024×4096 f32 从 6.30 降到 5.47；旧 flush 会留下约 120 MB 脏行，其回写落进下一次计时调用，新 flush 自身只写 71 到 445 个 L2 扇区（2 到 14 KB）。顺带修了一个主线 bug：L2 大小未知时日志写 256 MB 却分配 512 MB。

五、趋势观察

第一，性能回退开始被当成一等公民，而且修法在方法论上比结论更值得记。#3643 为修正确性引入的 ID 保留规则，本身是必要且正确的；#3761 没有把它回退，而是让保留与复用在不同层级上并存——跨作用域共用一个 ID 之前先证明参与谓词恒成立，证明不了就退回带作用域的计数。配合作者那个「只改声明的屏障资源数」的隔离实验，这条修复链把「正确性」与「资源声明」两件事拆开了：后者是可以单独复现、单独验收的变量。这种拆分能力，恰恰是编译器项目从「能跑」走向「可维护」的标志。

第二，昇腾的工程化在两条腿上同时推进。一条是架构：#1975 用 2887 个文件、60 万行新增把整个 TileLang-Ascend 搬进主线多后端框架，靠 arch="dav-2201" 这样的标识做后端分流，目标是让 A2A3 与 A5 在同一个仓里正交共存；另一条是流水线：mlir-ascend 的 #208 把 Codex 的初始化、接入、恢复三套工作流和任务交接写进 .workspace/，主仓与昇腾仓也各自有 Agent 目录。把「迁移仓」与「用智能体迁移仓」放在同一天看，能看出昇腾侧的瓶颈已经从「缺算子」转向「缺一致的工程骨架与可复用的迁移流程」。

第三，算子库的自证文化在加深。TileOPs 本期在审的几笔，几乎都把「证据」写在 PR 里：真实路由测出的 Qwen3-30B-A3B EP8 组大小（取 48 层里偏斜居中的第 44 层）、35 个掩码构建的 TIR 与主线字节一致、L2 flush 改动附 46 行实现的对照表并说明旧 flush 留下 120 MB 脏行、W4A16 的代价模型明确写出「哪些项被删掉是因为数据钉不住」。TileFoundry 走的是另一条路——把同步做成可证明的分析，再让 lowering 反向校验，分析拒绝的情形直接列出来（TMA 与 wgmma 的完成语义尚未声明、跨线程边界不等的循环）。两条路合起来说明同一个取向：宁可承认「没证明」，也不把「跑通了」当成「对了」。

第四，风险面在往安装形态上集中。一天 7 条新 issue 里，四条来自同一位使用 pip 包、跑 WSL、用消费级 sm_89 卡的外部报告人，全部附了可复现脚本；#3775 则是生产环境里「pip 包 + 多 CUDA 上下文 + nvrtc 后端 + CUDA graph 捕获」的组合。这些不是编译器的深层缺陷，却决定了新用户第一次尝试时的体验。对照昇腾仓日测 3030 项全绿而 sat=False 的语义偏差仍靠人工报告，可以看出测试覆盖的形状与真实使用形状之间还有距离。

最后一点观察：本期新闻侧依旧空白，15 条候选里 12 条是仓库发现。TileLang 的对外声量仍然绑定在「DeepSeek 与昇腾」这类事件上，而日常进展只发生在提交里。对跟踪这个项目的人来说，这意味着日报的主体只能是 PR 与 issue，而不是报道——这已经是连续多期的稳定形态。
