一、核心项目进展

1.1 主仓：partial-sync 命名屏障 id 在两类存储域间重号（#3643）

合于 10-25 14:30，2 文件 +57/-1，修 #3642。ThreadSync 对 shared 与 shared.dyn 各跑一次，每次新建一个改写器、各自从 kFirstUsedBarrier 重新编号；第二次运行跳过第一次已改写的同步，却不知道那些 id 已占用，于是把同一个 bar.sync id, count 分给互不重叠的两组线程。修法是让编号跨两次运行连续，并为跨域复用加断言。这类缺陷编译期不报错、只在大 kernel 偶发。

来源：https://github.com/tile-ai/tilelang/pull/3643

1.2 主仓：clamp 的 NaN 传播下降被回退，T.clamp 回到 min/max（#3628）

合于 10-23 16:51。回退 #3205 整条链路：删除 tl.clamp 内建、各后端下降注册、codegen 分支与设备端辅助函数（含昇腾注册），T.clamp(x, lo, hi) 恢复为 T.min(T.max(x, lo), hi)，理由是额外 NaN 处理挡住了 min/max 的化简与向量化。NaN 诉求未消失，同日另开 #3605 以 T.clamp_symmetric 在 CUDA SM86+ 单列实现，分工是「T.clamp 保通用、新接口保语义」。

来源：https://github.com/tile-ai/tilelang/pull/3628

1.3 主仓：int64 原子 max/min 与 AtomicStore 的 int64、bf16、fp16 崩溃（#3307）

合于 10-23 18:44。normalize_atomic_type 自 #1716 起把 int64_t 归一成 unsigned long long 以支持 atomic add，结果让 Atomic 的 max/min 及引用形式在 int64 上直接崩，AtomicStore 同样中招并额外波及 bf16 与 fp16。修复按操作为 int64 单独选型，AtomicStore 走独立类型分派。属「为一个操作改公共归一化、连带打断其余操作」的典型回归。

来源：https://github.com/tile-ai/tilelang/pull/3307

1.4 主仓：VectorizeLoop 不再静默忽略循环步长（#3345）

合于 10-23 19:02，属 #3301 跟踪的 F319。向量化器只收到 (loop_var, extent, body)，步长根本没进去：T.vectorized(0, 8, step=2)（迭代集 0/2/4/6）被下降成覆盖整个 [0, 8) 的连续访问。修复在进入向量化前拒绝非单位步长并给诊断。这一批子项的共同特征是前端接受了无法下降的写法、后端给出另一个程序的机器码。

来源：https://github.com/tile-ai/tilelang/pull/3345

1.5 主仓：NVRTC 命中磁盘缓存后自动调优结果写不回（#3193）

合于 10-23 15:04。NVRTC 从磁盘加载 kernel 时不设 adapter.libpath，而调优选中配置后要凭该字段保存缓存 kernel，于是每次命中都抛 AttributeError、结论被丢弃，用户看到的是「每次启动都在重调」。修复在缓存加载路径恢复 libpath，与全新编译路径一致，补缓存重载与负向对照用例。

来源：https://github.com/tile-ai/tilelang/pull/3193

1.6 在审：用独立打包的 TIRx 替换内置 TVM，改动 1043 个文件（#3666）

10-25 19:16 提交，1043 文件 +71428/-104176。删掉 3rdparty/tvm 及 submodule 条目（保留 CUTLASS 与 HIP 头文件），把前端、原生张量与作用域 IR、下降 pass、后端流水线、执行适配整体迁到独立构建发布的 tvm_tirx，兼容层限定在 TileLang 内部，不设全局 tvm 别名、不保留第二份 TIRx。这把前几期「tvm fork 先行、主仓跟进」推到终点：底座从 vendored 源码转成外部依赖，此后可独立发版与回滚，合入影响面覆盖整仓。

来源：https://github.com/tile-ai/tilelang/pull/3666

1.7 在审：sm_100 的 TMEM 释放缺 CTA 屏障，warp 特化前导语句漂移（#3645 / #3663 / #3664）

三笔同源，都在自动 warp 特化与 Blackwell 新存储上。#3645：sm_100 上张量内存释放没有 CTA 级屏障，生产者 warp 可在消费者 tcgen05.mma/tcgen05.ld 仍读累加器时将其释放。#3663：特化会把 T.serial 外层循环之外的前导语句搬进循环体，本应只执行一次的初始化被每轮重放，输出错。#3664：if 内包特化流水且 if 后有语句时，setmaxnreg 相关下降令 ptxas 失败。三笔合看，「哪些语句属于哪个 warp、生命周期到哪结束」仍缺完整语义模型。

来源：https://github.com/tile-ai/tilelang/pull/3645、https://github.com/tile-ai/tilelang/issues/3663、https://github.com/tile-ai/tilelang/issues/3664

1.8 新增缺陷：sm_120 上归约下降失败、三张注意力示例超共享内存（#3647 / #3646）

10-25 09:08 同日两报。前者是 gdn wy_fast_bwd_split 在 sm_120 上的 ReduceOp 下降失败——源索引依赖线程持有的归约分段，不在既有规则覆盖内；后者是 attention_sink、gqa_bwd、block_causal_attention_varlen 三张示例超 101376 字节单块共享内存上限。对应修复 #3662 已开：按设备上限选更小瓦片、更少流水级与 128 线程，大设备保持原默认。消费级 Blackwell 的容量约束正成为示例与调优表的硬边界。

来源：https://github.com/tile-ai/tilelang/issues/3647、https://github.com/tile-ai/tilelang/issues/3646

二、多后端适配（昇腾 / 海光 / 新增 CPU 与 ROCm）

2.1 昇腾主仓：DeepGEMM 示例支持 FP4×FP4 打包输入（#3589）

合于 10-23 10:26。为 dense、M-grouped、K-grouped 三套 DeepGEMM 接口打开打包 E2M1 FP4×FP4 输入，复用既有 MX GEMM kernel 与启发式，从打包字节存储反推逻辑维度并按 FP4 的 64 元素对齐；后端侧只改 MX 的 K 尾填充，批式构造器也接受 FP4。公开的 batch/einsum 接口仍保 FP8 以对齐 DeepGEMM-Ascend-Nightly，FP8×FP4 反量化留待后续。

来源：https://github.com/tile-ai/tilelang/pull/3589

2.2 昇腾主仓：DMA 保留缓冲基偏移、区域界先提升、周期缓冲完整生命周期（#3627 / #3625 / #3606）

三笔同于 10-23 合入，都是布局与生命周期修正。#3627：DMA 规划丢掉 Buffer.elem_offset，UB 别名以 elem_offset=256 构造时 T.copy(别名, out) 实际从 0 号元素读；修法是把基偏移算进地址并在跨步切片（含嵌套）保留父偏移。#3625：区域最小值与长度用 Int64Promoter 提升后再构造半开区间，避免 int32 转型遮住动态尾界、令重叠证明耗尽 Z3 预算，给原地持久化 RoPE 引入多余跨迭代依赖。#3606：子缓冲生命周期摘要须完整覆盖访问才可提升，外部预载的值跨整个父周期存活，防止嵌套与手工流水下的复用覆盖待读者。

来源：https://github.com/tile-ai/tilelang/pull/3627、https://github.com/tile-ai/tilelang/pull/3625、https://github.com/tile-ai/tilelang/pull/3606

2.3 昇腾主仓：CI 镜像升到 cann9.3.0 周更版（#3630）

合于 10-23 19:20，只改 CI：ascend 作业测试容器从 cann9.3.0-weekly.20260930 提到 cann9.3.0-weekly.20261021-ubuntu22.04-py3.12。它决定昇腾侧全部回归用例实际验证的是哪版 CANN 运行时，是判断该线结论有效期的前提。

来源：https://github.com/tile-ai/tilelang/pull/3630

2.4 昇腾在审：E4M3 的 UB→L1 拷贝、片上内存溢出提前拒绝（#3639 / #3655）

#3639 为 Ascend 950 打开 float8_e4m3fn 的 UB→L1 拷贝：ND 输入经既有 scatter/post-copy 管线重排、预打包 NZ 直接搬运，footprint 与延迟分析补 FP8 元素宽度。#3655 让 MergeUBAllocations 在下降阶段按 UB、L1、L0A、L0B、L0C 各自容量校验计划占用并报诊断，而非生成越界分配——起因是两个独立循环各自合法地选中 32KB L0A 瓦片的两个版本、合并后超限。片上内存管理正从运行时报错前移到编译期拒绝。

来源：https://github.com/tile-ai/tilelang/pull/3639、https://github.com/tile-ai/tilelang/pull/3655

2.5 昇腾在审：PTO 目标默认走 tvm_ffi 执行后端（#3516）

10-24 更新的在审改动：为 pto 支持 tvm_ffi 并设为默认，execution_backend="auto" 现解析到 tvm_ffi。共享宿主机 codegen 负责 MakePackedAPI 与 C 宿主构建，昇腾运行时模块经 aclrtLaunchKernelWithHostArgs 拉起 PTODSL 编译的 aibin，与 AscendC 路径一致。与主仓 CPU 侧 #3634（统一到 TVM-FFI、移除 CPU 专用 Cython 包装）同向：执行后端在做减法。

来源：https://github.com/tile-ai/tilelang/pull/3516

2.6 昇腾仓：situ_glu 算子合入，对齐 Kimi K3 门控激活（#1891）

合于 10-23 16:04。语义与 dtype/shape/attr 约束逐条对齐 CANN ops-nn 的 activation/situ_glu，精度基准取 CPU fp64 的 PyTorch 金标准；纯 Vector 单 kernel，宿主按 dim 把输入合轴成 (rows, cut*inner) 零拷贝视图，非末维切分不跨步。算子对应 Kimi K3 Stable LatentMoE 的前向门控激活，与上一期的 situ_glu 梯度、稀疏 MLA 一并，昇腾仓的算子清单正按具体对话模型结构逐个铺开。

来源：https://github.com/tile-ai/tilelang-ascend/pull/1891

2.7 昇腾仓在审：稀疏 MLA、GLM-5.3 kpool 与三张规范化示例（10-23~25）

在审 24 笔里，算子侧代表是 sparse_mla_fwd（#1929，DSA 稀疏 MLA 前向，varlen 打包随机行 gather + 在线 softmax + QK/PV 双 GEMM，fast 路径限定 H=128、G=1、dim/tail=(512,64) 等条件）与 GLM-5.3 kpool 压缩（#1910，池内逐维 softmax 池化、过 BF16 边界、Hadamard-128 旋转、E4M3 量化并把行与 scale 散射进分页 cache）。示例侧补 rms_norm（#1558）、NMS（#1748，成对 IoU 压 1 bit 进 uint16 位图，N=4096 时 2MB 取代 64MB 矩阵）与 GroupNorm（#1607）。

10-25 05:17 有用户在 tile-ai/tilescale 提问能否升级 TileScale 依赖的 TileLang 版本。该仓最后推送停在 08-25，文档与示例仍指向较早版本。这类提问通常出现在上游接口进入快速改名期之后——本窗口主仓在审的 TIRx 替换（#3666）与 TileOPs 的 26 个算子类改名，都会放大下游跟版成本。

来源：https://github.com/tile-ai/tilescale/issues/72

五、趋势观察

发布工程成了主战场。 78 笔合入里 TileOPs 占 51 笔，其中十余笔属改名、打包、语义统一、文档与 CI 门禁——不是性能也不是新算子，而是把接口冻住。跟踪单七成、CHANGELOG 写定 0.1.0 并标注 10-26，此后 0.x 的兼容承诺开始生效；同期 TileFoundry 做成 core/nvidia/apple 三包、Sunrise 合入 0.1.15 分发版，三条线在同一周做同一件事：把「能跑」变成「能发」。

正确性重心从形状校验转向新硬件与新调度。 上周主仓合入多是形状与几何校验，本窗口换成生命周期与屏障：跨存储域屏障重号、sm_100 张量内存释放缺 CTA 屏障、warp 特化搬错前导语句、setmaxnreg 触发 ptxas 失败。共同点是编译通过而结果偶发错，且都落在自动 warp 特化与新架构存储上——把调度权交给编译器之后必然要付的账。

昇腾线从跑通走到按模型铺算子加每日回归。 situ_glu 对齐 Kimi K3 Stable LatentMoE 门控激活，在审的 sparse_mla_fwd 与 GLM-5.3 kpool 同样是特定模型结构的部件。每日全量 2903 项全通、次日又报失败，说明用例规模已足以当门禁；配合 CI 镜像追到 cann9.3.0 周更版，这条线的结论有效期以周计。

执行后端做减法，后端清单做加法。 CPU 统一 TVM-FFI、PTO 默认 tvm_ffi，加 CuTeDSL 修复与 NVRTC 编译，方向一致：减少执行路径分叉。后端清单反向扩张——Intel AMX 进 CPU 路径、ROCm 补 FP4 与 E8M0、海光重提寄存器流水线。分发形态正从「一套代码多后端分支」变成「一套 IR、多个打包」，与 #3666 把 TVM 变外部依赖同路。
