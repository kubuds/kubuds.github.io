今日重点

这个窗口组织内只有 6 笔合入，比上一期的 9 笔再降三分之一，但结构比数字更值得看：6 笔里 3 笔在主仓，且全部落在昇腾，没有一笔 CUDA 或 CPU。最大的一笔是 #3516（20 个文件，+1549/−182），把 tvm_ffi 提为 pto 目标的默认执行后端——此前 target="pto" 走的是 Cython 启动器，现在 execution_backend="auto" 直接解析到 tvm_ffi，共享 host codegen 生成 MakePackedAPI 与 C host，并由昇腾运行时用 aclrtLaunchKernelWithHostArgs 启动 PTODSL 编译出的 aibin，路径与 AscendC 内核一致。配套的是一处模块级工具链回调：整个 PTODSL 模块在 device build 步骤内一次编译完成（ptodsl → ptoas → bisheng fatobj-link → 抽取 .aicore_binary），结果按 ptoas 参数、ptoas 版本与 CANN 身份进缓存键。旧路径保留为 execution_backend="pto"，两套产出逐位一致。

第二笔 #3776 是求解器侧的收紧。AutoSchedule 原本用一个固定的周期下界起二分，这次改成取三条必要条件的最大值：单任务界沿用各任务启动间隔的最大值；资源团界对成对冲突的任务按残余值排序，由相邻差与首尾差推出周期不小于各启动间隔之和；自依赖界由 S_u - S_u >= wait - d*P 反解出周期不小于 ceil(wait/d)，版本相关距离再按 num_stages 折算。没有引入额外的下界探测，也没有改调度模型。实证在 Ascend 950PR、CANN 9.3.0 的周版本上：关闭编译缓存，一热三测交替，全部昇腾示例编译通过且调度结果不变，Z3 求解阶段累计耗时降 10.04%。

第三件事不在主仓。海光的分布式三件套 #36（6 个文件，+2022/−0）在 16:20 合入 distributed 分支而非 main，内容是 Block-Push 版本的 GEMM + AllReduce、Block-Push 版本的 GEMM + ReduceScatter、Block-Pull 版本的 AllGather + GEMM 三个计算通信融合算子，性能数据与实现说明写在 README。同一天 #37 开出 HCU 的 ds_read_vector Alt2 与 LDS 布局推断。这条线从 10-29 的 push-wave reduce-scatter 示例一路走到融合算子清单，是海光仓第一次成体系地做分布式。

第四件事是质量侧的一次集中爆发：窗口内 35 条新 issue 有 30 条落在主仓，其中 26 条直指昇腾。两个账号在下午到深夜之间各报了十余条，形态高度一致——不是「跑错了」，而是「本该报错却静默通过」：T.Kernel 接受零或负的 block 数、T.alloc_l1 接受 2 GiB 分配、T.Persistent 接受负的 wave 与 stage、T.unroll 接受 −1 并吐出 #pragma unroll -1、负张量维度直接把编译器打崩。另一组是语义错位：hf32 的 nearest_zero 编译成 NEAREST_AWAY、GEMM 输入 dtype 表与 codegen 双向不一致、reduce_bitand 一族吐出昇腾模板未定义的类型、同型 ND 转 NZ 散射因掩码计数不回退而陷入死循环。这批 issue 大多仍开放，但当日已有 VMI mask 校验、SIMD fill 恢复等对应修复在审。

一、核心项目进展

1.1 昇腾：PTO 目标默认执行后端切到 tvm_ffi，整模块在设备构建阶段编译并缓存（#3516）

#3516（20 个文件，+1549/−182）是本期最大的一笔。改动的实质是把 pto 目标从「专用 Cython 启动器」迁到「与 AscendC 同一条 host 路径」：target="pto" 配 execution_backend="auto" 时解析为 tvm_ffi，共享 host codegen 负责 MakePackedAPI 与 C host 构建，昇腾运行时模块用 aclrtLaunchKernelWithHostArgs 启动由 PTODSL 编出的 aibin。

设备构建侧新增一个模块级工具链回调，把整个 PTODSL 模块一次编译完成：ptodsl 前端产出、ptoas 下沉、bisheng 的 fatobj 链接、再到 .aicore_binary 抽取，产物按 aibin 缓存。缓存键把 ptoas 参数、ptoas 版本与 CANN 身份一并算进去——这一点很关键，此前这类键漏掉工具链版本时，跨 CANN 升级会命中旧产物。

验证面铺得很宽，新增四组测试：auto 解析到 tvm_ffi、被调方分配输出、动态形状与动态输出、多设备内核、动态共享内存、cube/vector 混合 GEMM、source accessor、导出库、host 侧循环启动与 host 侧 profiling 区间；另有等价性测试逐位比对 tvm_ffi 与旧 pto 在 vecadd、多内核与动态共享内存三种内核上的结果；两组缓存测试分别覆盖二进制缓存与内核缓存，其中缓存命中跳过工具链、损坏条目抛错、以及在全新进程里命中。旧路径按计划保留，待覆盖确认后再退役。

来源：https://github.com/tile-ai/tilelang/pull/3516

1.2 昇腾：AutoSchedule 用三条必要条件收紧周期下界，Z3 求解时间降 10.04%（#3776）

#3776（1 个文件，+20/−1）只改初值，不改算法：原来的二分从一个固定下界起步，现在先算三条必要条件再取最大值。单任务界保留各任务启动间隔的硬下界；资源团界针对成对资源冲突的团，把任务残余值升序排列后，由相邻差的约束与首尾差的约束相加得出周期不小于团内启动间隔之和，团本身用每个任务作种子贪心枚举；自依赖界由 S_u - S_u >= wait - d*P 反解，版本相关距离以 num_stages 为上界。

实证环境写得很具体：华为 Ascend 950PR、CANN 9.3.0 的 20261009.01 周版本，关编译缓存，每个配置一热三测交替。结果有两条：昇腾示例全部编译通过且调度结果与改前一致（说明只收紧了下界、没有改变解），Z3 求解阶段累计耗时下降 10.04%。二分上下界与求解状态处理均未改动，也没有引入额外的下界探测流程。

这类改动对上游的价值不在单点性能，而在于调度器的求解时间随算子规模增长时，二分起点的浪费会线性放大——把必要条件写进初值，等于给每次求解省掉一段无意义的区间。

来源：https://github.com/tile-ai/tilelang/pull/3776

1.3 昇腾：整数原子操作适配 signless 载体，12 条 PTO 用例覆盖 32 位与 64 位（#3794）

#3794（4 个文件，+52/−6）修的是 #3512 的后遗症。那笔改动把有符号整数类型从 signless 的 i32/i64 改成 si32/si64，而 PTO 的原子接口要求 signless 载体，于是 SIMT 内核里的整数 add/min/max 原子操作直接编译失败。

改法是在生成的 PTODSL 调用边界做局部适配：把指针与操作数按同宽重解释为 signless，保留指针的地址空间，返回值再还原成逻辑类型；min/max 保持原本的有符号或无符号比较语义。这样 #3512 引入的逻辑类型体系不被推翻，适配只压在原子这一层。

回归用例落在 testing/ascend/language/simtvf 下的 test_simtvf_atomics.py，覆盖 32 位与 64 位的 add/min/max、负数操作数、返回旧值、超过 32 位的值、以及高位为 1 的无符号初值；新增的 12 条 PTO 用例在昇腾上全过。同批合入的 #3792 修的是同一族问题的另一面：T.atomic_add/max/min 因有符号输入在 PTO 上编译失败。

来源：https://github.com/tile-ai/tilelang/pull/3794

1.5 TIRx：ceildiv 与负 scale 的 split div/mod 两笔在审，与嵌套 floor division 报错同源（#93、#94）

tile-ai/tvm 侧窗口内有两笔在审：#94（[Fix][TIRx] Make ceildiv exact for signed divisors）与 #93（[Arith] Guard negative scales in canonical split div/mod）。两笔都在修同一类问题的两端——符号进入整除与取模后，规范化的改写前提不再成立，于是「精确」与「安全」需要分开处理：ceildiv 要求带符号除数时结果仍然精确，split div/mod 则要在负 scale 下拒绝规范化。

这与主仓当日新开的 #3937（[BUG] 嵌套 floor division 在负乘数下产出错误整数）指向同一处：负系数一旦进入算术化简的改写链，边界条件很容易被漏掉。区别在于 #3937 是用户侧复现，#93/#94 是编译器侧先手加固。

来源：https://github.com/tile-ai/tvm/pull/94 、 https://github.com/tile-ai/tvm/pull/93 、 https://github.com/tile-ai/tilelang/issues/3937

2.3 mlir-ascend：CI 收为 Ascend 950 AscendC 单一 PR 门禁（#222）

这条改动对下游的含义是：mlir-ascend 仓的准入基线从此只有一代硬件，旧代昇腾的回归将不再作为合并条件。

3.3 TileOPs：softmax 两 CTA cluster 达标，long-K NT GEMM 选择器改动未达标（#2898、#2897）

#2898（SoftmaxFwdOp，标 bar met）把两片 32 KB 的 softmax 行从四个 128 线程 CTA 的 cluster 改到两个 256 线程 CTA 的 cluster：SM90 上每个 CTA 槽位都能放下两 CTA 的 cluster，而四 CTA 的 cluster 会留下空槽。寄存器侧同时改了两处——行最大值按打包的 16 位对取，float16 的每一项用一次 FFMA 对瓦片的缩放最大值做移位；bfloat16 与 float32 仍先减最大值，因为它们的最大值乘 log2(e) 会越过 fp32 范围。根因写在描述里：基准把 H200 跑在 1500 MHz，寄存器方案比 quack 多执行 17% 指令、受发射率限制。

#2897（GEMMFwdOp，标 below bar）方向相反，结果没达标。它要修的是选择器的判定：超过 64 个 K 步之后，只有当一个 176 或 192 宽的 ping-pong 瓦片能覆盖更多「每字节操作数的输出」时才替换更宽的 coop2 瓦片，ds-v3-prefill-o-proj 因此从 128x176/144 的 ping-pong 换到 128x256/240 的 coop2。问题在于该行跑在 H200 的 700 W 功耗墙下，时间跟每次调用的能耗走：176 宽瓦片比 DeepGEMM 少 2.7% 周期，但把多 21% 的操作数字节搬进 SM，于是跑在更低的时钟上。这条如实标了未达标，价值在于把「功耗墙下不能用周期数当判据」这件事量化了。

五、趋势观察

一是昇腾在主线上的权重继续上升，且从「补算子」转向「补执行路径与求解器」。本期主仓三笔全是昇腾：执行后端换默认、求解器收紧下界、原子操作适配类型体系。这三笔都不增加算子名单，但在改「同一段程序怎么被编出来、跑起来、以及多久能编完」。对照 10 月以来的记录，昇腾侧的合入已经从补齐 AscendC 算子，走到接口语义、执行后端、调度求解器这三层。

二是CUDA 侧进入长评审期。上一期还有三笔 CUDA 指令级原语进主干，本期零合入而六笔在审（ldmatrix/stmatrix、256 位向量化、im2col 调度、流水操作数生命周期、异步 GEMM 生命周期、PASS 配置命名空间）。合入速率下降与在审队列增厚同时出现，通常意味着评审带宽成了瓶颈，而不是开发停摆。

三是质量审计开始与功能开发并行。一日 26 条昇腾 issue 的形态说明，社区里已经有人在做系统性的非法输入审计，而对应的修复 PR 当日就在队列里（mask 校验、负参数拒绝、fill 下沉恢复）。这对一个正在把后端铺到多家国产芯片的项目是好事：3060 项每日测试全过只证明合法路径可用，非法路径的拒绝能力得靠这类审计。

四是RISC-V 四源连续五个窗口静默，但四源之外的 CPU 线给出了阶段性结论。TVM 路线、MLIR 路线、社区索引页、算能 TPU 四个上游都停在原引用；而 TileLang–Weft 用共享 Canonical 编译器把 553 项全部做到 Triton 的 1.03 倍以内，四平台中位倍率 1.29 至 1.66。需要注意这是口径切换后的结果，不能与上一期的 0.058 倍直接比较。真正的观察点是：这套「同一编译器、两套前端」的做法能否反向进入上游，以及 RISC-V 的 RVV/IME 路径是否会被四源之外的项目先跑通。

局限说明：本期 GitHub 匿名 API 额度在采集早期耗尽，PR 正文与合入详情改由检索接口与非默认分支的提交原子流补齐，个别 PR 的文件数与行数为检索接口返回值，未逐行复核 diff；hygon 与 mlir-ascend 的合入落在非默认分支，已按分支分别核查。新闻侧只有零命中，无外部报道可交叉验证。
