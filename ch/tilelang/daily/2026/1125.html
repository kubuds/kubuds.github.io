今日重点：ROCm 单日六笔合入，修 FP4 转换并把归约判定改成按 wave 宽度

主仓当日 12 笔提交里，6 笔带 ROCm 前缀。这批改动都对着真实量化与归约路径的缺陷。

#3665 修两处 HIP 模板缺口。第一处是 T.cast(x, T.float4_e2m1fn) 返回值错误。代码生成把转换写成 (fp4_e2_t)x，而该类型只有 explicit fp4_e2_t(uint8_t raw)。于是 float 被截成整数再当作原始位存下：1.0 回来是 0.5，2.0 是 1.0，6.0 是 4.0，负数同样错。

第二处是 HIP 模板缺 E8M0 类型。两处在 VeOmni 跑 DeepSeek-V4 的 QAT 量化器时暴露，环境是 gfx942 与 gfx950，含 UE8M0 尺度。0.1.15 的轮子里这两个头文件与主分支一致，同样受影响。

#3959 改归约是否需要工作区的判据。旧代码在归约线程数超过 32 时一律返回真。实际 tl::AllReduce 只在某一步跨 wave 时才用工作区，所以 wave64 上 64 线程归约分配了从不访问的 LDS。工作区在 IR 里又是一次共享内存访问，ThreadSync 会为此处每次归约插屏障。

修法是按目标 wave 宽度比较，wave32 目标行为不变。屏障仍保留在真正跨 wave 的路径上。

#3729 让 gfx1200 上的 FP16 与 BF16 T.gemm 接受标准线性共享布局。此前对 A_shared、B_shared 调 make_linear_layout 再算 T.gemm，会报 Get different layout。现有 WMMA 发射器本可按该映射取数，问题出在兼容性判定。

做法是把共享布局兼容回调的入参扩为四项：算子、操作数缓冲、实际布局、目标。ROCm 侧据此按输入逐项校验复用，发射器与索引映射不变。

另有三笔属工程细节。#3954 让 compile_flags 与 tl.device_compile_flags 真正传给 hipcc。此前这两个参数只进缓存 key，不改设备代码。

#3958 给 hip_resource_info 加占用率报告。#3956 在文档里说明 T.gemm 在每 wave 行数很少时的限制。

来源： https://github.com/tile-ai/tilelang/pull/3665。

今日重点：昇腾一天报出十条缺陷，全部指向 API 参数校验缺失

11-24 一天内，同一作者在 tilelang 开 10 条昇腾缺陷，编号 #4490 至 #4499。十份报告的测试环境一致。硬件为 Ascend 950PR 单 die、128 GB 显存。软件为 CANN 9.2.1、HDK 26.0.RC1、openEuler 24.03、torch 2.10.0+cpu、torch_npu 2.10.0.post4。

其中六条是「接受了后端编译不了的输入」。#4490 的 T.atomic_add 收 int8、uint8 与 float8 缓冲。#4492 的 T.atomic_max 与 T.atomic_min 收 int8、uint8。#4491 的 T.reduce_sum 收 bfloat16 与 float8。#4494 的 T.simd.vabs 与 T.simd.vneg 收 bf16 与 fp8 寄存器。

#4495 的 T.gemm 收任意 unit_flag_ctrl，传 -1 或 999999 也能静默编译。#4497 的 T.gemm 收 GM 作用域操作数，后端找不到可编译的路径。

四条更接近崩溃或错编译。#4496 对 float8_e4m3fn 共享缓冲做 T.fill，直接让 bisheng 编译器 core dump。#4498 的 T.gemm 接受没有任何 TILE_K_SUB 能整除的 K，随后在自动调度里断言失败。#4499 的标量 T.sqrt 与 T.rsqrt 在内核编译期因 stl_pair.h 重声明报错。#4493 的五个原子接口在 Ascend 上没有下降实现。

另有一条独立来源的正确性缺陷。#4484 指出 SimdVF 的归约下降把所有非 sum 的归约类型都映射成 max，T.reduce_min 会返回最大值。该条来自源码审阅，未在设备上复现。

这批问题的共同点是：类型与取值本应在编译期被拒绝，现在被放进后端才失败。与 11-23 那批 6 条文档与实现不一致同属接口契约缺口。

来源： https://github.com/tile-ai/tilelang/issues/4498。

一、核心项目进展

1.1 Z3 低位掩码改整数取模编码，主仓跟 bump 并撤回 TopK 测试的求解器限额

TVM 子模块 tilelang_main 分支当日合入一笔 #98，主仓侧 #4482 于 14:03 跟 bump。三处修复都可追溯到 Z3Prover 的具体缺陷。

其一，常量有符号右移如 (n + 4095) >> 12 原先走位向量路径，经 int2bv、bvashr、bv2int 三步。当这种移位出现在循环边界里，同作用域后续的纯整数查询会同时带 Int 与 BitVec 约束，常在 tirx.Simplify 里耗尽默认资源预算。

其二，VisitShiftOp 在 CanProve 中把 b >= 0 与 b < 64 两条断言直接加到共享求解器上。这会污染后续查询，也会与外层作用域冲突。同时 DivNode 与 ModNode 用了 Z3 的欧几里得 / 与 %，于是对负被除数也能证明 truncmod(a, 4) >= 0。

其三，tx & 31 这类掩码在索引表达式化简中仍走位向量。#98 把 x & (2^k - 1) 翻成 x mod 2^k。提案记录了一个具体代价：某设备函数里简化器问了 156 次同类问题，耗时 11.7 秒，反例是 tx = 4。

测试侧先止血再撤。#4463 于 09:51 把两个 ROCm 测试文件的 arith.z3_rlimit 限到 100，起因是四个 DeepSeek 与 GLM 的 TopK 用例各耗 494 至 605 秒。

#4489 于 20:40 撤回该限额，理由写的是 #4482 让常量有符号右移变得便宜。对照用同一构建 b4c67597、TVM de131ae4、Z3 4.15.4，取三次冷跑中位数。

来源： https://github.com/tile-ai/tilelang/pull/4482。

来源： https://github.com/tile-ai/tilelang/pull/4419。

1.3 vote 与 sync 内建函数保留 64 位谓词，1 << 32 不再被判为假

#3777 于 09:53 进主干。CUDA 的 vote 与 block-sync 内建函数只接收 32 位 int 谓词，例如 __any_sync、__syncthreads_count。

传 int64 或 uint64 时值被隐式收窄。低 32 位为 0 的非零谓词因此被判假，1 << 32 是最直接的例子。

受影响接口七个。投票类为 T.any_sync、T.all_sync、T.ballot、T.ballot_sync。同步类为 T.syncthreads_count、T.syncthreads_and、T.syncthreads_or。

修法是把超过 32 位的谓词先归一成显式 != 0，再向内建函数传布尔值。另加了 1 << 32 的运行时回归，整个 warp vote 测试文件通过。

来源： https://github.com/tile-ai/tilelang/pull/3777。

三、生态与采用方（TileOPs 算子库 / FlashQLA / topa）

3.1 TileOPs 十六笔合入，主线仍是绕开 0.1.15 的边界检查开销

十六笔的标题里反复出现同一句话的不同写法：在 0.1.15 上去掉某个通用路径带来的边界检查。

#3161 让 FP8 indexer 的 warp 特化内核绕开 0.1.15 的边界检查。#3151 让 Mamba 的 CausalConv1dFwdOp 在 0.1.15 上把一波次预填网格常驻。#3142 让 MoE 的 FP8 分组 GEMM 每个任务只保留一个分支，并把掩码分片铺满所有 SM。

#3146 换了方向。它把 Tensor 的越界夹紧改在输入 dtype 内完成，而不是提升到更宽的整数再夹。

这条线起于 11-23 的 #3133「找回 25 行退化」。两天下来，恢复动作从「与 0.1.12 对照」变成「按检查点逐个绕开」。

来源： https://github.com/tile-ai/TileOPs/pull/3161。

3.2 采样、卷积、归约三线各补一笔结构性改动

采样侧两笔。#3157 把拆分的 top-p 行用全局原子量做分箱。#3158 把同一行的分箱和改用定点求和，使掩码可复现。

卷积与索引各一笔。#3148 把对称 Conv2d 的收缩拆到空闲 SM 上。#3156 让两输入 concat 在刚过一波时每线程走四个向量。

归约两笔。#3152 一次启动跑完前导轴，跨 thread-block cluster 切分。#3154 用一次屏障或一次或运算完成块内 any 与 all 的折叠。

线性注意力三笔。#3160 在 chunk-parallel 路径上为 SM90 的 KDA fp16 given-gate 预填做超一 chunk 的预处理。#3159 把 GDN 分区 pass 的 transfer 旗标绑成值，避免 0.1.15 丢掉它。#3144 让 KDA 的 key-major 状态按内存序解码，并把打包序列一起走。

来源： https://github.com/tile-ai/TileOPs/pull/3158。

3.3 夜间测试改报每模型 batch-1 预填与解码吞吐

同日新开 #3155，要求用 CUDA graph 重放每个模型的解码步。这条把测量方法本身作为工作项，与 #3153 的指标口径配套。

#3150 属 Mamba 线，把 CausalConv1dUpdateFwdOp 的解码状态行经共享内存中转。

来源： https://github.com/tile-ai/TileOPs/pull/3153。

五、趋势观察

  • 版本节奏进入发布前夜。0.1.15 于 9-30 发布，55 天后版本号推进到 0.1.16。这一版的积累主要是 ROCm 修复、Z3 三处修补与发布链工程，而非新功能。

  • 性能回归治理形成了固定套路。先加限额止血，再修根因，最后撤回限额并复测。#4463、#4482、#4489 三步都在一天内完成，中间隔着一次 TVM 子模块更新。

  • 昇腾的短板从算子覆盖转向接口契约。一天十条缺陷里没有一条要求新算子，全部是「不该接受的输入被接受」。这类问题修起来便宜，但会持续消耗使用者信任。

  • TileOPs 的优化口径仍是追框架版本。0.1.15 的通用路径带来的额外开销，需要下游按算子逐条绕开。两天内至少五笔以此为标题，说明版本升级与算子库性能之间还没有自动对账机制。

  • RISC-V 侧连续两个窗口零变化。TVM 路线与 MLIR 路线都停在原位，本窗口连索引页也没有动作。
