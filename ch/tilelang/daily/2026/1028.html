一、核心项目进展

1.1 主仓：ROCm 的 exp/sin/cos 不再默认降到快速内建，sin/cos 误差从 7.8e-04 降到 6.6e-08（#3621）

合于 10-27 22:39，5 文件 +107/-17，修 #3618。在 HIP 上，T.exp、T.exp10、T.log、T.log2、T.log10、T.sin、T.cos 七个默认函数无论 tl.enable_fast_math 如何设置都会降到 __expf 一类快速内建，而 CUDA 侧按 #875 的约定走精确实现；反过来，显式的 T.__exp 等快速算子在 HIP 上根本不下沉，在 tilelang.rocm.language 里直接抛 AttributeError。本笔让 HIP 与 CUDA 采用同一策略：七个默认算子改派 HIPMath，八个带下划线的快速算子新增最低下沉规则指向 HIPFastMath，并统一挪进 FAST_MATH_INTRINSICS 列表由 ROCm 语言层导出。精度对比取 #3618 的复现：MI300X 上 exp 与 exp10 看相对误差、sin 与 cos 看绝对误差（x 到 1e4），四列依次为 T.exp、T.exp10、T.sin、T.cos，主干为 3.7e-06 / 4.1e-06 / 7.8e-04 / 7.8e-04，本笔为 8.3e-08 / 8.1e-08 / 6.6e-08 / 6.4e-08。

来源：https://github.com/tile-ai/tilelang/pull/3621

1.2 主仓：自动目标改读当前 HIP 设备，多卡机上不再固定取 0 号卡架构（#3594）

合于 10-27 22:37，2 文件 +24/-1。determine_target(“auto”) 在 ROCm 上落到注册的 HIP 探测器，而该探测器无条件读 torch.cuda.get_device_properties(0)，于是当前 HIP 设备不是 0 号卡时，自动探测给出的是 0 号卡的架构；CUDA 侧早就在用 torch.cuda.current_device()，ROCm 没有跟上。修法是先取当前设备索引再查属性，并用 normalize_rocm_arch 去掉特性后缀。新增测试把 current_device() 打桩返回 1，同时记录所有被探测过的索引，断言探测到 gfx942 且只碰过 1 号卡；修复前该断言得到 probed == [0]。作者注明本机无 ROCm 设备，测试只用打桩 torch 验证探测助手，未跑真实 HIP 运行时；与本日另一笔 #3549 改动的是不同函数（#3549 在 tilelang/contrib/rocm.py，本笔在 tilelang/rocm/target.py）。

来源：https://github.com/tile-ai/tilelang/pull/3594

1.3 主仓：TMA gather/scatter 的常量行索引转为 int32，字面量写法不再编译崩（#3365）

合于 10-27 09:15，2 文件 +44/-2，修 #2601。tma_gather4 与 tma_scatter4 两个前端助手在收到 Python 整数形式的行索引时直接透传，落到 TIR 里没有确定的整型宽度，于是在 Blackwell 上编译崩溃；其他行表达式保持原样。本笔只把 Python 整数转成 int32 的 TIR 常量，并补一个受 Blackwell 门控的编译回归，用字面量行索引分别编译 gather 与 scatter，再检查生成的 CUDA 源码里确实出现对应指令。作者说明该测试只验证能编译，不验证运行时数值正确；且提交者本机的 Windows Python 3.13 环境里 Home Assistant 的 pytest 插件依赖 fcntl，pytest 收集阶段就失败，本笔的 TileLang 测试在本地并未真正跑起来。

来源：https://github.com/tile-ai/tilelang/pull/3365

1.4 主仓：NVRTC 与 CuTeDSL 按首个输入张量所在设备取当前流（#3359）

合于 10-27 08:11，2 文件 +5/-4，接 #3301 的 F149 与 #3408。两个适配器此前用字符串前缀判断目标类型，且默认取调用方当前设备的当前流，于是调用方当前 GPU 与张量所在 GPU 不一致时选错流。本笔改用目标种类判断，并按首个输入张量的设备查当前流，显式传入的流句柄仍然最高优先，无张量的 NVRTC 调用维持原语义。这是继昨日 out_idx 输出分配流（#3649）之后，流语义清理的第二笔。作者划清边界：本笔只修流选择，跨设备的默认流启动上下文仍是未解项，这类调用方必须自己在启动前把张量所在设备设为当前设备，补丁里没有逐调用的设备守卫；验证时用真实 Torch 流与 GPU 启动覆盖了同设备与跨设备的非默认流，但未建立跨设备默认流上下文的正确性。

来源：https://github.com/tile-ai/tilelang/pull/3359

1.5 主仓：自动调优缓存键纳入 compile_flags，同一内核换编译选项不再复用旧二进制（#3338）

合于 10-27 16:57，3 文件 +28/-1，接 #3301 的 F131。自动调优器把编译结果持久化缓存，但缓存标识里没有 compile_flags，于是同一个内核换一组设备编译器选项后仍会命中旧二进制，测出来的性能与真实编译结果对不上。本笔让 CompileArgs 真正存下并按原有顺序参与哈希，并把 flag 从 JIT 实现经 AutoTuner.set_compile_args() 一路透传到候选编译、逐配置的 pass 合并、分组设备编译与缓存内核加载。验证覆盖三条既有缓存键测试，以及用原生运行时对 CUDA 做的定点对比：列表与字符串两种 flag 形式都能在逐配置覆盖中存活；作者指出原先的合并逻辑会把编译器宏丢掉，正是这次要堵的口子。

来源：https://github.com/tile-ai/tilelang/pull/3338

1.6 主仓：ThreadSync 把 address_of 记为写，不透明调用后的栅栏补上（#3346）

合于 10-27 05:49，2 文件 +62/-1，接 #3301 的 F305，延续昨日的栅栏语义主线。address_of 本身不携带访问信息，它只把指针交给下游，但访问分类器把它的类型硬编码成读，于是一块共享缓冲经不透明调用写入后不会进 writes 集合，后续的全块读找不到冲突写、也不再规划栅栏，线程就这样抢过写入读到写前内容。实测的 CUDA 输出很直白：T.address_of(B[0]) 形式在 extern 之后没有栅栏，而 T.access_ptr(B, “w”) 形式有；后者显式声明了访问类型，所以这个洞一直没被发现。loop_unswitching.cc 早已按写保守处理 address_of，ThreadSync 是唯一的例外。本笔把 address_of 记为写，方向是保守的：指针用途未知就可能被写，而栅栏规划只需在安全侧错一次；新增两个用例，断言该内核下沉后 extern 之后跟着 __syncthreads()。

来源：https://github.com/tile-ai/tilelang/pull/3346

1.7 主仓：运行时行程数的流水线 epilogue 直接展开，分页解码恢复可编译（#3356）

合于 10-27 07:02，1 文件 +5/-1。T.Pipelined 循环的行程数是运行期值时，只要 epilogue 展开两步以上且带异步拷贝，CUDA codegen 就报 TypeError: Downcast from tirx.Sub to ir.IntImm failed。根因在 EmitImpl：prologue 与 epilogue 的 extent 是常量时才展开，以保证每次迭代的等待计数是常量；而 epilogue 的 extent 是 end - start，即 (n + max_stage) - n，n 为常量时在构造期折叠，n 为运行期时保持为 Sub，as_const_int 返回空，于是 epilogue 被当成 T.unroll 循环发射，其等待写成 T.ptx_wait_group(1 - k) 这样读循环变量的形式，而 ptx_wait_group 只收立即数。修法是判断前先看化简后的 extent，常量边界的情形化简回自身，与原来一致。该缺陷由下游 TileOPs#1852 报出并二分到 afcebed1 之后，破坏对象是分页解码——其行程数来自 KV 长度。作者在 sm_89、CUDA 13.0 上双版编译对比，新增测试在主干失败、在本笔通过。

来源：https://github.com/tile-ai/tilelang/pull/3356

1.8 主仓：切片填充与负索引的静态边界两修，越界写与静默负地址关闭（#3352 / #3347）

合于 10-27 05:37 与 05:14，合计 4 文件 +100/-3。前者针对 Fill 构造器的静态边界检查：原来逐维只校验 min >= 0 与 extent <= shape，而 extent <= shape 只对从缓冲起点开始的区域成立；一个起点靠里的切片两项都通过，却被下沉成越界写——T.fill(As[6:12], 7) 在长度 8 的缓冲上编译通过，发射出 As[threadIdx.x + 6] = 7，写到 6 到 11。修法是把区域末端也对照目标形状校验，且新条件要求起点与长度都是静态，锚定在零的区域与符号起点区域都不受影响；T.clear 共用同一节点，缺陷相同也一并关闭。后者针对 LegalizeNegativeIndex：原来把负索引加一次缓冲长度就了事，没有范围检查，长度 8 的缓冲上 A[-9] 得到 -1、A[-10] 得到 -2，跳出分配起点且无任何诊断，而 NumPy 与 PyTorch 对同样的索引抛 IndexError。修法是仅在分析器能证明回绕后仍为负时拒绝，并报出索引与长度，所有在范围内的常量与全部动态索引维持原行为。

来源：https://github.com/tile-ai/tilelang/pull/3352、https://github.com/tile-ai/tilelang/pull/3347

1.9 主仓：T.ws(-1) 区域在所有线程上运行，落单写法不再丢存（#3354）

合于 10-27 04:52，2 文件 +40/-3，接 #2978。WarpSpecialize 的文档把 -1 定义为「跳过 threadIdx.x 绑定」，也就是该区域不受 threadIdx 约束；实现里却把 -1 当普通 warp 组索引，构造出 [-warp_group_size, 0) 这个对任何线程都不成立的区间，于是区域在零个线程上运行，区间内所有存全部被丢弃且无诊断。最小复现很干净：256 线程里先全写 0，再在 T.ws(-1) 里写 5，结果 256 个线程写出的仍是 0；同样的存不加 ws 包装则 256 个线程都写 5。修法是当 id 里含 -1 时不发射任何范围约束，真实组索引仍按自身线程约束，并在文档串里补上 -1 这一例——原文档的示例恰好缺它。作者核查全仓未出现 ws(-1) 用法，因此没有既有代码依赖那个空区域。

1.10 主仓：profiler 未指定设备时用当前设备，缓存冲刷不再打到 0 号卡（#3357）

3.4 TileOPs 合入四条：where 与 masked_fill 可调优、D128 因果对角按 64 键打分、稀疏长 GDN 预填充拆分、变更日志按发布日定日期（#2782 / #2783 / #2779 / #2781）

四笔在 10-27 合入，恰是发布前的收尾。#2782 修 request_tune() 在 WhereFwdOp、MaskedFillTensorFwdOp、MaskedFillScalarFwdOp 上抛 ValueError 的问题：自动调优拒绝随机生成的整型输入，而这三个内核把 bool 条件或掩码当 uint8 传；随机选择器只改变每个元素取哪个操作数、不改变候选的工作量，故声明随机整型输入安全；新增三个测试节点，主干上三例全失败。#2783 优化 D128 稠密程序的因果对角：当因果调用只有一段 key 且两个长度都在 128 行边界上时，第一个消费 warpgroup 的对角 key 瓦片对全部行都屏蔽了高 64 键，于是这一步改按 m64n64 的 QK 配 64 键 softmax 跑；该选择是编译期标志（diag_aligned，进内核键），因为运行期在 64 与 128 宽 QK 之间分支会让 ptxas 在某些特化上串行化每条 WGMMA（C7511），改用标志后所有 manifest 里的 D128 预填充特化都不再出 C75xx。#2779 把 SM89 上稀疏长序列的 GDN 预填充拆成状态扫描加独立输出程序，适用于稠密、key 主序的 D128 输入且至少 16384 token、状态扫描 CTA 不超过 SM 数四分之一的情形；基准里 (1, 16384, 4, 128) bf16 的耗时从约 0.612 毫秒降到约 0.470 毫秒，与 flash-linear-attention 的 0.441 毫秒相比为 0.939 倍。#2781 把 CHANGELOG 里 0.1.0 的日期定为它进 PyPI 的那天（2026-10-27），并删掉贡献者文档里的发布一次配置与 Actions 点击路径。

3.5 TileFoundry 合入两条：整窗口按操作数本身下发、动态共享内存按内核实际用量定尺寸（#273 / #271）

两笔均在 10-27 合入。#273 修 sm_89 GEMM 的下沉：schedule finalize 写出的内容编不过，因为下沉把整个累加器包进一个从零开始、跨度等于自身的窗口 T.ptr_of(acc[0:0+16, 0:0+8])，而 CUDA codegen 拒绝分片寄存器瓦片的指针切片，报「要求普通源布局」；MMA 又把寄存器片段读成 lhs_frag_dst[0:0+16, 0:0+32] 这样的裸 Slice，codegen 同样无处理器。修法在下沉侧：StoragePlan.operand 本来就把「从零开始且跨满操作数的窗口」当作操作数本身，但物化与指令下发仍构造 Slice；改为只判定一次——对 MLIR 的 TrivialSubViewOpFolder 做同样的替换。#271 修动态共享内存：合成的宿主入口给每个 TIR 内核都用 dynamic_smem=0 启动，经整型 TensorView 偏移访问共享内存的内核因此没有分到空间，超过 48 KiB 还需设置 cudaFuncAttributeMaxDynamicSharedMemorySize 而启动器从不设置；作者没有采纳 #267 里「按目标容量给满」的建议，改为按内核实际用量定尺寸，理由是静态共享内存与动态共享内存同计一个上限、且每块申请多少决定一个 SM 能放几块——sm_89 上要满 99 KiB 会让用 512 字节的内核也只放得下一块。CUTLASS 与 TileLang 都按同样方式定尺寸。

3.6 外部生态：CANN 社区的 TileLang 算子仓、PPU 版零改动包装器、DeepSeek V4.1 Flash 片段示例（10-27）

三个外部仓在窗口内都有动作，合起来看是一条「昇腾侧算子资产」的成形过程。Atlas-Ascend-Fork/ops-tilelang 是 CANN 社区面向昇腾的 TileLang 算子仓，10-20 建仓、10-27 提交「自动发现增量测试并移除算子映射表」；README 明确只支持 Ascend 950 及以上架构、要求 CANN 9.3.0 以上并用社区 weekly 版，设计原则是接口与调度分离、按业务域聚合、正确性先于性能、benchmark 与测试分离且基线按测试文件与芯片集群分片保存。kevin3113/models-tilelang 用这个仓的七个算子串出 DeepSeek V4.1 Flash 的「Attention 输出加 FFN 前处理」片段（mhc_post_forward、带平方和 GEMM、归约加 RMSNorm、mix 拆分、sinkhorn、apply_mix、ffn_norm），HIDDEN=5120、MHC=4、默认 decode 形态 SEQ_LEN=1，支持 SuperKernel 与 npugraph_ex 的 ACL graph，B 从 1 到 256 实测 SuperKernel 收益 1.17% 到 2.75%。flytiger-eco/tilelang-wrapper-for-sail 解决另一个方向的迁移：把 CUDA 风格的 TileLang 代码零改动跑在 tilelang-sail（PPU 后端分发版）上，做法是纯运行时拦截 import 协议与 site 机制，不修改上游源码也不重新打包，无 PPU 对应物的 CUDA 特性显式报错而非静默降级。三者分别对应算子供给、模型落地、后端迁移三个环节。

来源：https://github.com/Atlas-Ascend-Fork/ops-tilelang、https://github.com/kevin3113/models-tilelang、https://github.com/flytiger-eco/tilelang-wrapper-for-sail

五、趋势观察

第一，TileOPs 0.1.0 把「算子库」这件事的成本结构换了一种算法。传统做法是算子数量随硬件与模型需求线性增长，人力是瓶颈；这里的做法是每个算子先写一份 YAML 规格，把签名、负载与 roofline 声明清楚，再由 agent 生成与调优内核，最后用规格派生的测试与基准做准入。206 个算子、195 笔 foundry 标签合入是这个流程的第一次全量交付。它能否持续，取决于两件事：规格能否覆盖复杂融合算子（路线图第一步正是这个），以及基准能否挡住「调优到基准上但实际不鲁棒」的内核——FusedAddLayerNormFwdOp 在远离零的行上丢精度这条已知问题，恰好是这类风险的一个样本。

第二，本窗口的合入几乎全是「静默错误」。ROCm 的数学函数默认走快速内建会让 sin/cos 差出三个数量级；address_of 被当成读会让不透明调用后的共享内存读到写前内容；T.ws(-1) 的区域在零个线程上运行，存全部丢弃且不报错；切片填充按长度而非末端校验，直接越界写；负索引回绕后仍为负，落到分配起点之前。这五条的共同点是编译通过、运行不报错、结果错，且都在最近两周内被集中发现。对一门要给大模型写内核的语言，这类缺陷的代价远高于编译期报错，它们指向同一个工程需求：把「不报错但行为不对」的写法在编译期拒掉。本窗口的边界校验两修与 ws(-1) 修正在做的就是这件事。

第三，后端覆盖正在从「厂商主导」转向「社区自发」。官方维护的昇腾、海光、沐曦、摩尔线程四条线之外，Hexagon DSP 后端在一天里落 15 笔并把线性代数原语铺到 Crouton 瓦片上，PPU 版出现零改动包装器，CANN 社区自建算子仓并用它串出 DeepSeek V4.1 Flash 的模型片段。这些动作都不在 tile-ai 组织的仓库里，却都依赖 TileLang 的语言层稳定性。这也是 0.1.0 冻结公开 API、并把 API 兼容性检查做成 CI 门禁的意义所在——下游越多，向后兼容的价值越高。

第四，缓存身份这件事被两个后端同时盯上。主仓把 compile_flags 纳入自动调优缓存键（#3338），昇腾把 Bisheng 构建身份纳入二进制缓存键（#3691）。同一个内核在不同编译选项或不同编译器下产生的二进制不同，缓存若只按源码与形状做键就会误命中，测出来的性能与真实编译结果对不上。两条独立路线在同一天做同一件事，说明这类问题在实际使用中已经足够痛。
