一、核心项目进展

1.1 主仓：批式 finalize_reducer 此前只归约首个输出块（#3070）

合于 10-22 01:16，2 文件 +29/-5，修 #2623。批式 finalize_reducer 的下降只在缓冲区开头调用一次 run_batch，其余连续输出块根本没有被归约：输出维度大于 batch 时，后面各段拿到的不是归约结果，而是未初始化或上一轮遗留的值。修复按 ceil(OutputDim / batch) 逐块发射带正确偏移的批式 all-reduce——128 个输出、batch=4 时发射 32 次调用，同时把重映射 reducer 缓冲改用扁平视图、每批以常量线性偏移寻址，去掉原先的形状与步长重建，并保留全部 chunk 调用。验证在 L40S 上完成：新增 sum/max/min 数值回归，覆盖 fp16 与 fp32、batch 4/8/16，23 项 finalize_reducer 相关用例通过，外部复现矩阵 16 例零失配。属典型的”小尺寸正确、大尺寸静默错”的一类缺陷。

来源：https://github.com/tile-ai/tilelang/pull/3070

1.2 主仓：BF16→FP32 向量化转换改走内联 PTX 打包 lane 转换（#3595）

合于 10-21 19:28，4 文件 +19/-7。
新增 tl::__tl_cvt_bf16x2_to_f32x2，用内联 PTX 把成对的 BF16 lane 一次转成 f32x2，替掉逐 lane 的标量提升路径；2、4、8 三种 lane 宽度均保持支持。同步更新了向量化 cast 与布局推断的期望值，并把 BF16 cast 的测试收敛到既有覆盖范围，不扩大断言面。改动不涉及语义，只动生成的指令序列，影响面是所有走向量化 cast 的 BF16 计算路径。

来源：https://github.com/tile-ai/tilelang/pull/3595

1.3 主仓：展开 pass 保留空 stepped 循环，ROCm 的 Select 改逐 lane 下降（#2887）

合于 10-21 19:20。循环展开 pass 此前会把 trip count 为 0 的 stepped 循环当成空壳消掉，改变后续 pass 看到的程序结构；修复改为在展开过程中保留这类空循环。同笔还改了 ROCm 侧的向量化 Select：改为逐 lane 下降，避免整组下降在不支持的目标上失败。两处改动一在 IR 结构、一在后端下降，合在同一笔里，说明它们由同一个复现场景引出。

来源：https://github.com/tile-ai/tilelang/pull/2887

1.4 主仓：软件流水保留传递性拷贝依赖，线程域参与区域冲突判定（#2822）

合于 10-21 18:13。流水规划此前只跟直接依赖，间接（传递性）的拷贝依赖会在规划阶段丢失，dependent copy 的等待随之被删；同时物理区域冲突检查在规划与下降两侧各有一套口径。修复用一个后向 worklist 同时跟随标量与 buffer 拷贝依赖，让规划与下降共享同一份物理区域冲突检查，保留重放绑定在作用域内，并补齐传递生产者、strided alias 与顺序 TMA 回落路径的覆盖。第二笔提交把线程域引入区域冲突判定：访问先展开到物化线程域再比较区域，使互不相交的共享内存切片仍可流水，同时保住跨线程依赖与 strided 缓冲的物理重叠；同一套域用于流水规划、依赖校验与 buffer 版本化。

来源：https://github.com/tile-ai/tilelang/pull/2822

1.5 主仓：cast 的源/目标/舍入三组合前置校验（#3350）

合于 10-21 13:49。round 只在显式列出的组合下可下降：PTX cvt.rs 要求 f32 源、32 位 rbits 操作数与特定的打包目标。其余组合此前在分支分派时被放过，舍入注解就此静默消失；标量循环本来就会拒绝这些组合，向量化循环不拒绝，于是同一个 cast 在两种循环形态下行为不同。典型例子是 f32→E8M0：它的 helper 向正无穷舍入、根本不接受舍入参数，而向量化分支从未读过 round。现在在分派之前统一拒绝非法组合，任何分支都无法再丢注解；配套测试只给真正接受 rbits 的 rs 模式传该参数。

来源：https://github.com/tile-ai/tilelang/pull/3350

1.6 主仓：无 arch 的 CUDA target 拒绝而非静默填 sm_50（#2860）

合于 10-21 13:32，1 文件，修 #1049。在有 CUDA toolkit 但没有可用 GPU 的机器上，未指定 arch 的 CUDA target 会退化成裸 cuda，TVM 随后静默填入 arch=sm_50，编译继续推进到一个错误的 SM，全程没有任何诊断——这正是 tilelang.compile(func) 配 target="auto" 的陷阱。修复落在 _cuda_target_from_arch：自动检测与显式 target="cuda" 共用的唯一入口，改为抛出可操作的错误，并在错误里给出显式 arch 的两种写法（{"kind":"cuda","arch":"sm_90"} 或 TILELANG_DEFAULT_TARGET）。headless 编译只要给了具体 arch 依然可用，因为 codegen 与 nvcc 只依赖 toolkit，设备访问推迟到 kernel 启动。PR 过程中一度加入三个无 GPU 单测，最终提交把它们撤下，改动只剩入口校验。

来源：https://github.com/tile-ai/tilelang/pull/2860

2.3 主仓昇腾：warp_reduce_max/min 在 PTO 上的整数符号性修复（#3582）

合于 10-21 10:21。PTO 的 pto.redux_max/min 拒绝带类型的整数：PTOAS 要求无符号性载体加一个显式 signedness，于是 int32/uint32 的 T.warp_reduce_max/min 直接编译失败，报「requires signedness=’signed’ or ‘unsigned’ for integer values」。修复把 warp_reduce_sum/max/min 统一走 contrib.ptodsl 的 tl.redux_* 包装（现已导出），由包装提供载体与符号性，并按 AscendAllReduce 的方式对 value dtype 设门；问题单引用了主仓 #3541 与 PTOAS #1579。验证分两层：op × dtype 网格的 lower-only codegen 测试，以及稀疏的双目标（ascend/pto）执行测试——用 ≥2^31 的 uint32 lane 把符号性写错直接暴露出来。

来源：https://github.com/tile-ai/tilelang/pull/3582

2.4 昇腾仓：亚 32B 紧凑行距源无法表达，keepdim reduce 输出错乱（#1795）

合于 10-21 17:15，2 文件 +302/-3，修 #1682，是本窗口技术含量最高的一笔。根因在模板层：copy_ub_to_gm 无条件生成一条多 burst 的 DataCopyPad，而 MTE3 引擎实现的是系统级「UB 窄行按 32B 槽存放」约定——源地址每 burst 前进 ceil(blockLen/32) + srcStride 个 32B 块。对按 32B 边界写行的生产者这是精确匹配；但 T.reduce_max 的 (M,1) fp32 输出是 V-pipe 紧凑写入、行距只有 4B，引擎无法表达。实测第二个 burst 读到的是 element 8 而不是 element 1（[127, 1151, 71, 199] 里 1151 恰是 element 8 的值），写入侧没问题，错在 DMA 读源的地址序列。修复分两半：两侧皆 packed 且 total ≤ 65535 时折叠成一条 flat 单 burst（M×L 字节，利用「单条 burst 长度任意」的契约）；不可表达的非 32B 倍数行距改为 trap() 显式中止，用编译期 if constexpr 守卫，对 32B 倍数与亚 32B 槽布局不生成额外代码。为什么不降级：bisheng 的跨管道自动同步只覆盖直线 intrinsics，用条件分支包裹 DataCopyPad、或兄弟分支里放 GM 标量写，都会让 bisheng 生成坏的同步代码并导致设备死锁（实测逐行 DMA 被运行时分支包裹即触发 aicore 异常）。14 个用例覆盖 flat/multi 路径、keepdim reduce 复现、UB 循环复用、不可表达 pitch 的合法单 burst 形式与显式中止；测试环境为 Ascend910 A3（dav-c220）/ CANN 9.0.0 本地构建。PR 自述保留两个边界：亚 32B 紧凑行距且带行距目的（如把 (M,1) fp32 写进宽张量的某一列）仍走槽步进；blockCount > 4095（12 位字段）仍会静默截断（4200 行实测只拷前 104 行），拟另立 issue。

来源：https://github.com/tile-ai/tilelang-ascend/pull/1795

2.5 昇腾仓：JIT 缓存改原子发布，并在缓存被删除时恢复（#1903）

合于 10-21 16:20，7 文件 +1026/-86，关联 #1836。原实现把编译产物原地覆盖到 kernel_lib.so，其他进程若已加载该共享库，就会读到被改写中的文件。修复先把产物复制到同目录下的独立临时文件，再用 os.replace() 原子发布；加载前若缓存库已被删除，经过错误消息与文件状态确认后返回 cache miss，重新编译；保存阶段目录消失则跳过保存、保留已经得到的编译或调优结果；权限错误、依赖库缺失、无效 ELF 与序列化内部异常继续向上传播，不被吞成 miss。覆盖面包括 KernelCache、AutoTunerCache 与 AutotuneResult，不改 cache key、算子计算逻辑与 CI 并行度。41 项 host-only 用例通过（原子发布 9 项、缓存删除恢复 32 项），PR 自述未做 NPU 侧集成验证。原子发布部分沿用 #1853 的实现并保留原作者信息。

3.1 TileFoundry：0.0.3 打 tag 发布，指令级调度 + 重构分析 + H200 与 Apple AMX 示例

上一期记录「0.0.3 公告已进 README、尚待打 tag」，本期 10-21 10:26 正式发布，PyPI 为 tilefoundry==0.0.3，代号「Agent-driven scheduling」。核心变化是调度权归属：编译器列出每个 HIR 操作可由哪些指令实现、各自需要什么，agent 在候选中选定，编译器再把选定的调度下降为 TIR。配套 CLI 有 tilefoundry schedule candidates 与 schedule facts 展示候选与约束，tf.schedule 记录选择、tilefoundry schedule finalize 完成下降；指令以 AtomSched 操作声明并带显式 TIR 操作数契约，从 CUDA MMA atom、SM90 WGMMA 与异步拷贝起步。分析部分重构为内存（分段分配、footprint 与复用窗口、循环感知的 buffer 生命周期）、成本（按执行作用域计工作量与流量、每条访问关系声明读什么）、结构（定义事实、估值上下文与作用域快照统一走 visit context，投影复用使每个语料用例只分析一次）。新教程沿一个 8192×5120 乘 5120×17408 的 GEMM 一路走到 AtomSched 在 H200 上的最优 kernel。

五、趋势观察

编译器缺陷的性质从「算错数」扩到「选错目标」。 本期主仓八笔合入里，四笔改变的是「编译器以为自己在做什么」：无 arch 的 CUDA target 静默退到 sm_50（#2860）、cast 的舍入注解按分支静默丢弃（#3350）、批式归约只处理首个输出块（#3070）、流水规划丢失传递性依赖（#2822）。它们的共同点是不报错，只在某些尺寸或某些循环形态下给出不可信结果——比崩溃更难定位，也说明项目把静默正确性放在了功能扩张之前。

昇腾线的瓶颈已移到内存模型与运行时边界。 亚 32B 紧凑行距无法用 DMA 表达、只能显式中止（#1795）；缓存并发改为原子发布并补删除恢复（#1903）；PTO 的整数符号性要靠包装层补齐（#3582）。这三笔都不是「加算子」，而是「让已有算子在边界条件下不出错」，配合 DeepGEMM 启发式对齐合入，昇腾侧正从能力覆盖转向工程可靠性。

分析机构开始把 TileLang 当作昇腾可用性的判据。 SemiAnalysis 用「六个仓库中只有 TileLang 当时可用」来定义 DeepSeek 昇腾支持的完成度，这比任何单篇技术博客都更能说明 TileLang 在国产算力叙事里的位置：从实验性 DSL 变成默认承载层。同一篇报告也给出反向信号——优化集中在超节点、x86 主机支持仍不完整，通用性落后于性能。

注意力栈的重心从推理前向移到训练反向。 TileOPs 一天内补齐 MLA 预填充反向的 op 层、SM90 warp 特化 kernel 与取数顺序优化，再加上 GQA 反向的分组 KV head 处理，与昇腾侧上月以来的反向算子补位（indexer_bwd、SiTU-GLU 反向、WY fast 反向）完全同向。训练侧的 TileLang 覆盖度正在被系统性补齐。

SM89 从「能跑」走向「调优」。 FP8 BMM 瓦片、W4A16 的 M 上界、分页 DSA、NSA top-k 四条线同日动刀，且都给出单卡实测与「不构成普遍优势」这类限定语。消费级与单卡推理场景成了性能目标之一，同时作者对基准口径的自我约束明显变严。

调度与正确性的分工在 TileFoundry 与主仓之间变得清晰。 主仓继续收紧语义与正确性，TileFoundry 0.0.3 则把「选哪条指令」交给 agent、把「保证语义」留给编译器，并用 H200 与 Apple AMX 两个示例给出可复现数字。这条分工如果稳定下来，TileLang 生态会出现「语言层守正确、agent 层搏性能」的双层结构。
