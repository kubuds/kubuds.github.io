今日重点：TileOPs 三笔 mHC 算子同日合入，序列建模接口完成接棒

11-19 一天里，TileOPs 把 HyperConnection 的 pre、post、head 三个算子一并合入。三笔分别是 #3032、#3035、#3039。此前 #3021 已在 11-18 删除旧的两个 mHC 算子，并登记为经评审的公开 API 破坏。相隔一天，替换路径走完。

pre 步由 #3032 合入，改动 18 个文件，+1106/-21。它跑 DeepSeek-V4-Flash 与 GLM-5.3-Flash 的 mHC 前段。内容包括 fn 投影与平方范数、pre 与 post 权重、Sinkhorn，以及加权流求和。

投影保证 float32 精确。fn 以三个 bfloat16 项进张量核心，每 16 个通道一次 64×72 的 WGMMA。每个 64 通道槽再累加到 float32。token 轴是运行期长度，一次启动覆盖任意 token 数。对照对象是 vLLM 的 TileLang mhc_pre 与 torch.compile 参考。

post 步由 #3035 合入，改动 16 个文件，+592/-21。它把块输出混回 n 条残差流。逐元素写为 post_layer_mix[j] * x + sum_i comb_res_mix[i,j] * residual[i]，float32 计算后一次舍入到 bfloat16。

线程按 16 字节段混 x 与各条流。小调用一段，大调用四段。输出与 TileKernels 的 mhc_post_fwd 逐位相同。

head 步由 #3039 合入，改动 15 个文件，+778/-9。它在 LM head 之前把 n 条残差流折叠成一条，对应 DeepSeek-V4-Flash 的 ParallelHead.hc_head。每 SM 最多两个 token；超过后由一个 CTA 串流一到四个 token，每条 hc_fn 向量服务全部 token。

manifest 条目转为已实现，并附 GLM-5.3-Flash 的 3000 token 行。对照对象为 vLLM 的 hc_head 融合内核与 torch 参考。

三笔都关闭了对应提案：#2921、#2970、#2971。旧算子删除与新算子合入的中间态只维持一天，接口替换没有留下断档版本。

来源： https://github.com/tile-ai/TileOPs/pull/3032 https://github.com/tile-ai/TileOPs/pull/3035 https://github.com/tile-ai/TileOPs/pull/3039

今日重点：GEMM 选择器一条规则改 302 个形状，MXFP4 MoE 解码达到验收线

11-19 的 TileOPs 性能线共六笔合入。两笔自评达到验收线（#3044、#3041），四笔仍标在验收线之下（#3045、#3053、#3050、#3040）。四笔的支持说明里都写明：每一行比主分支快。

GEMM 选择器改了一条规则（#3045）。NT 类 GEMM 若 128 行网格在 coop2 宽度下能压进一波，就选最窄的 coop2 tile，不再拆成更窄的多波。

判据有两条。最后一行 tile 的两个 64 行消费组都要分到行，且网格要填满一波的 15/16。

规则影响 302 个模型形状。单卡 H200 上没有一例比主分支的选法慢，286 个形状快 1.03 到 2.6 倍。GLM-5.3-Flash 的路由 prefill（N=288）从 82.24 微秒降到 32.13 微秒。

该笔还修掉一个隐患。float32 的 coop2 tile 整块分块时，128 到 383 号线程上的累加器拷贝被丢弃，共享内存留下未初始化内容。

尽管数字如此，该笔自评结论仍是验收线之下。

MXFP4 的 MoE 分组 GEMM 达到验收线（#3044）。新增共享解码内核，条件是行对齐为 128 的倍数、尺度为 e8m0、K 为 2048 的倍数。128 个 token 作 WGMMA 的 M 操作数，128 行权重作 N 操作数。

权重由七个生产 warp 每个 CTA 解码一次，写进 fp8 共享内存瓦片。根因是旧内核在数学 warp 里解码权重，每个元素一次 FMUL 加一次 FFMA。每个 math warp 每个 K 步约 363 条指令，对应 512 个张量周期，张量管线只有 36% 在忙。

GQA 变长注意力在头维 56 到 80 上改用三个消费 warpgroup（#3041）。192 行 tile，三个 64 行消费组轮流占用张量核心。该笔自评达到验收线。

根因是 72 通道时 exp2 的耗时占其乘积张量时间的 64/80。两个消费组时，一个组的 softmax 会拖过另一个组的乘积。ncu 显示张量 54.7%、XU 45.2%，两者近乎串行。

该笔注明一处限制：TileFoundry 的 schedule finalize 在当前构建上还不能把交付的调度降到 TIR（见 tile-ai/topa#42）。内核按实测原型手写，调度写在 final_hir.py 里。

KDA 的 bf16 给定门控 prefill 改为一次居中启动（#3053，9 个文件，+749/-225）。SM90 上原先走两条路径，视序列与值头对数而定。新路径先由联合居中张量核心程序准备全部 chunk，再走状态遍历。fp16 给定门控与原始门控仍走旧路径。

该笔给出的根因是旧路径按最长序列计时。在 glm-5.3-flash-pf-pool 上，3000 token 序列的 64 个 CTA 要走 47 个 chunk，每步都做整块 chunk 准备。该笔自评同样在验收线之下。

另两笔自评也在验收线之下。W4A16 的 K tile 元数据改异步拷贝（#3050），把不足四字节的每行零点多取成对齐的四组窗口，用 4 与 8 字节 cp.async 搬运。生产端因此能立即发出 K tile 的 TMA。

RoPE 调整了载入顺序（#3040）。带列复制的头先载输入向量再读位置，避免 ptxas 在位置 clamp 处等待。小 GPT-J 调用因此少付一次 DRAM 延迟。同一笔还修掉零头 key 在 key.view(-1, 0) 处的失败，现返回空结果。

来源： https://github.com/tile-ai/TileOPs/pull/3045 https://github.com/tile-ai/TileOPs/pull/3044 https://github.com/tile-ai/TileOPs/pull/3041

一、核心项目进展

1.1 布局占位变量跨序列化保持绑定，spawn 子进程降载不再报非单射

tilelang 主仓窗口内合入两笔。第一笔是 #4410，改动 3 个文件，+301/-2。它修布局对象跨进程与跨磁盘往返后失效的问题。

tl.Layout、tl.Fragment、tl.PartialFragment 用进程内单例 tirx::Var 占位符表达索引与线程映射。_i、_j 等用 InputPlaceholder(i)，_rep 用 ReplicationPlaceholder()。

Forward、OutputShape、DetectInjective、ForwardThread 的判断依据是 Var 的对象同一性，不是 name_hint。

一旦布局或带 T.annotate_layout 的 PrimFunc 经过 pickle 或 tvm.ir.save_json 与 load_json，反序列化就会重建占位符。新建的 VarNode 与接收进程里的单例不再同一。

主分支上可直接复现三处错误。pickle 往返后 map_forward_index([7]) 返回 [_i] 而不是 [7]。OutputShape() 把 (32,) 算成 (_i + 1,)。在 spawn 出来的 worker 进程里降载带注解的 PrimFunc，会以 the forward map must be injective 失败。

修法是把绑定的占位 Var 引用纳入同一个 ObjectGraphSerializer 通道。涉及两个字段：LayoutNode 的 _forward_vars 与 FragmentNode 的 _replicate_var。二者的序列化顺序先于 forward_index 与 forward_thread。这些字段不参与 repr、init、compare、hash 与结构相等，默认值为 nullptr。

实际效果是多进程编译路径可用。

来源： https://github.com/tile-ai/tilelang/pull/4410

1.2 开发版版本号去掉工具链标签，同一 wheel 不再按 CUDA 版本分叉

#4409 改动 7 个文件，+16/-76。它清理版本号里的后端后缀。

起因是 TileLang 曾按 CUDA 12.8 与 13.0 分别构建 wheel。自 #1826 起，一个 wheel 同时服务多个 CUDA 工具链版本。旧后缀因此会误导：在 CUDA 13.0 镜像里构建的检出会报 0.1.15+cu130.gitabcdef12，而构建机的工具链版本并不能说明这个 wheel 支持哪些后端。

改动删掉后端后缀与 NO_TOOLCHAIN_VERSION 开关。同一检出在各类配置下统一报 0.1.15+gitabcdef12。置 TILELANG_BUILD_WHEEL_WITH_DATE=ON 则报 0.1.15+d20261119.gitabcdef12。PyPI 发行仍用基础版本号。

tilelang.build_date() 随之兼容两种位置。日期可以紧跟 + 之后，也兼容旧 wheel 形如 0.1.15+cuda.d20261119.gitabcdef12 的写法。

作者列出验证范围。三个打包测试通过；检查了 CUDA 12.8、CUDA 13.0、ROCm、CPU、带日期的夜间构建与发行构建的 PEP 517 元数据；pre-commit 全量通过。

来源： https://github.com/tile-ai/tilelang/pull/4409

1.4 在审修复：warp 特化时跳过布局不兼容的 TMA 提升

#4413 修一处降载失败。在 b1367a59 上，一个面向 sm_90a 的流水线 GEMM 无法降载。触发条件是它的 8 位 B tile 使用 make_swizzled_layout(Bs, k_major=False) 的带填充布局。

A 的载入让该循环具备 warp 特化资格。随后该 pass 把 B 的普通 T.copy 也提升成 T.tma_copy，而 LowerBulk 拒绝带填充的布局（对应 issue #4053）。

修法是逐个检查候选 TMA 载入的目标布局注解，范围含流水线及其 prelude。布局不兼容的拷贝留在消费侧，兼容的仍在同一流水线内提升为 TMA。

作者报称 #4053 里的八个用例现在都能为 sm_90a 降载。H200 配 CUDA 13.0 上新增的 FP8 回归确认 A 走 TMA、B 走普通拷贝。该 PR 目前仍在审。

来源： https://github.com/tile-ai/tilelang/pull/4413

2.3 Atlas A3 被认成 910A，carver 的 L0C 容量少算一半

#2023 修 carver 的型号识别。Ascend.__init__ 用字符串包含关系判断芯片：先判 910B，再判 310P，最后兜底的 910 一律当 Ascend910A。

Atlas A3 的设备名是 Ascend910_9362，仓库内 examples/situ_glu/benchmark.md 即如此写。它既不命中 910B 也不命中 310P，于是落进兜底桶。

后果是三项硬件参数错配。ub_cap 取 262144 字节，实际为 196608 字节。l0c_cap 取 262144 字节，实际为 524288 字节，正好少算一半。compute_max_core 取 910A 默认的 32，而实际应以 cube_core_num 查询为准。

同一份代码里存在两套矛盾的映射。编译器主流程 tilelang/utils/target.py 把同一设备判为 910_93/910C → A3，carver 用的是错的那套。

carver 用这三个值做候选配置的可行性筛选与代价建模（tilelang/carver/roller/policy/ascend.py）。L0C 少算一半会把大 C tile 的配置直接筛掉。该 PR 于 11-19 08:14 开出，尚在审。

来源： https://github.com/tile-ai/tilelang-ascend/pull/2023

三、生态与采用方（TileOPs 算子库 / TileFoundry / TileKernels）

3.1 注意力 sink 补齐：DSADense 与 DSAPaged 同日合入

两笔注意力合入把 DeepSeek-V4 与 GLM-5.3 用到的 sink 与 bf16 缓存行补齐。

DSADense 侧是 #3038，改动 5 个文件，+228/-82。它的 SM90 内核开始支持 attn_sink 与 is_causal=False。此时仅凭索引选 key，-1 表示跳过该槽位，每个头的 sink logit 计入其 softmax 分母。

topk 不再要求是 128 的倍数。超出部分为死槽；最后一对块里若奇块整段越过 topk，只载入并计分其偶块。对照基线 FlashMLA 改为一次启动跑完本批全部 kv 行，其索引用 -1 补齐到 128 的倍数。

DSAPaged 侧是 #3048，改动 6 个文件，+411/-79。它支持 bf16 缓存行，值为 512 列、键再 0 或 64 列，覆盖 GLM-5.3 与 DeepSeek-V4。

单 CTA 内核用合并的 cp.async 收集。它通过掩码最后一块的尾部支持任意 topk，并把 attn_sink 加进 softmax 分母，分块合并时同样计入。

范围写得清楚。FP8 的 656 字节行生成代码不变，该行仍不支持 attn_sink 与 topk 非 64 倍数。SM89 不支持 bf16 行。

来源： https://github.com/tile-ai/TileOPs/pull/3038 https://github.com/tile-ai/TileOPs/pull/3048

3.2 FP4 分组量化落地，MoE 门控补哈希路由与 sqrt-softplus

量化侧新增 FP4QuantPerGroupFwdOp（#3027，15 个文件，+810/-41）。签名是 block_size=32, inplace=False，把 bfloat16 量化为 e2m1 码，两码一字节，块尺度为 2 的幂的 float8_e8m0fnu。输出与 DeepSeek-V4-Flash 的 fp4_act_quant 逐位一致。

舍入不用 FP4 转换指令。它改为对 float32 位做整数运算，再加一次 float32 加法。该内核与 FP8QuantPerTokenGroupFwdOp 共用 group_quant.py。

write_in_place 让组数超过网格 y 范围的带步长行先走连续拷贝。这一笔顺带修好了 FP8 逐 token 分组量化的 inplace=True 路径。

MoE 侧是 #3036，改动 4 个文件，+360/-66。它给 FusedTopKFwdOp 补 scoring_func="sqrtsoftplus"，带或不带 correction_bias 与分组均可。它还支持调用方给定 expert_ids，覆盖 DeepSeek-V4-Flash 的门控与其哈希路由首层。

给定 expert_ids 时，内核只读这些专家的 logit。未重归一化的 softmax 则读整行，且不读偏置。仍被拒绝的组合是「带偏置的 softmax 选择」。

来源： https://github.com/tile-ai/TileOPs/pull/3027 https://github.com/tile-ai/TileOPs/pull/3036

3.3 GatedPoolCompress 一次启动完成按请求分环的 KV 池化

#3033 改动 12 个文件，+1363/-3。它实现 GatedPoolCompressFwdOp，对应 DeepSeek-V4-Flash 的 compressor 与 GLM-5.3-Flash indexer 的键池化。

请求被打包处理。位于某请求起点之前的位置来自该请求的环，环大小为 C * ratio 行。调用写出其最后若干位置的行，并允许回滚上一次调用的最后一个 token。

实现上一次启动、无主机同步。每个请求一个 block，先池化读取其环的那些窗口，再写回环与有效标志。其余窗口通过对 cu_seqlens 做 warp 级 ballot 搜索定位自己所属的请求。

该笔还补了成批的 torch_program 作为基准的 torch 基线，并把 kv_state 与 score_state 声明为连续。

来源： https://github.com/tile-ai/TileOPs/pull/3033

3.4 TileFoundry 把切片 mesh 与 Varying 值计入并行计划分析

TileFoundry 窗口内一笔合入（#356，123 个文件，+2752/-557）。它改的是内存与流量分析。

起因是 discussion #350。分析器要能比较 PP、TP、EP 与 HSDP 几种并行计划。旧实现按流水级把各 GPU 峰值相加，把切片 mesh 之间的 Reshard 记成 0 字节视图，还把带 Varying 的操作数从只取一个操作数类型的算子中丢掉。

改动后，类型推断通过单一规则读操作数的分片属性（operand_types、combine_operand_attrs）。Broadcast 与 Varying 相遇得 Varying 的按单元存储，Partial 与 Varying 相遇则拒绝。

切片 mesh 之间的 Reshard 按「获得该值的单元数」计一次拷贝。部分重叠切片之间的 Split 或 Partial 移动被拒绝。峰值改为按归属单元统计。

另有三处配套。JSON 调用行写明被调者（callee、callee_ref）与定义它的 Module。一次调用按张量叶子给出一个输出边界，嵌套元组也算，使生成出的 Module 可被分析。repeat_interleave 保留输入的 Broadcast mesh。

该笔新增 CUDA 用例比较 PP、TP、EP、HSDP 与 FSDP。生成的模块由 CLI 写出、重新载入、与自动微分结果核对并实测。

来源： https://github.com/tile-ai/TileFoundry/pull/356

3.5 新开四条目标：DSAPaged bf16、AvgPool1d、DeltaNet、Mamba

窗口内 TileOPs 新开四条带形状与目标倍率的工作项。

#3049 要求 DSAPaged 的 bf16 行在 DeepSeek-V4-Flash 上追平 FlashMLA。该条与本期合入的 #3048 对应，属「先立目标、再合实现」的顺序。

#3051 处理边缘截断的 AvgPool1d 窗口。做法是把数据读进寄存器，并在能省 block 时一个 SM 只发一个 block。

#3054 要求 DeltaNet 的 chunk 输入接受带步长的张量。#3013 给 CausalConv1dFwdOp 与 CausalConv1dUpdateFwdOp 补空洞卷积与 float32 滤波器。

另有 #3052 属维护性合入，只补注释与文档。它说明 W4A16 的元数据窗口为何只对单消费 warpgroup 生效，并把选择器的 128、256、512 宽 K tile 与显式 384 宽 K tile 写进 docstring。

该笔同时加了一条回归测试锁住组数检查。作者给出丢掉该检查的后果：显式 384 宽配置会返回错结果，1x128x36864、split 24 上相对误差 0.457。

来源： https://github.com/tile-ai/TileOPs/issues/3049
