一、核心项目进展

1.1 主线：CUDA 补 L2 预取指令与六档驱逐优先级，非默认优先级要求 SM80 以上（#3490）

#3490（6 个文件，+185/−1）补齐了此前缺失的三类预取内建：L1 预取、uniform L1 预取、L2 预取，同时把「驱逐优先级」做成一等参数 EvictPriority，取值为默认、普通驱逐、优先驱逐、最后驱逐、不改变、不分配六档。全局加载模板随之改造：原先按固定宽度写死的加载封装被替换为模板化 API，可指定非一致（non-coherent）加载、L1 驱逐优先级，以及 L2 预取的字节数。

行为边界写得很清楚：默认优先级的 L2 预取走普通全局或局部指令，其余优先级映射到 evict_normal、evict_last，并要求计算能力 8.0 以上；低于该门槛的设备上这些组合不成立。对 kernel 作者的意义是，过去要拿到 prefetch.global.L2::evict_last 这类行为只能自己塞内联汇编，现在可以在 TileLang 源码里声明，编译器按目标架构选路。

来源：https://github.com/tile-ai/tilelang/pull/3490

1.2 主线：NaN 传播的对称 clamp 降到单条 min.NaN.xorsign.abs（#3605）

#3605（7 个文件，+203/−1）新增 T.clamp_symmetric(x, limit)，在 CUDA SM86 及以上把 FP16、BF16、FP32 三种操作数统一钳到 [-limit, limit]，保留带符号零与次正规数；任一操作数为 NaN 时返回规范 NaN，原 NaN 的符号与载荷不保留。非正的数值上限不在 API 契约内，既有 T.clamp 不受影响。

实现上直接降到 min.NaN.xorsign.abs.*，每个标量或每对 FP16/BF16 一次钳位指令，向量输入走既有的可向量化算子注册与 CUDA 打包发射路径，不引入运行时检查。验证口径给得很硬：语言与代码生成两套测试 86 通过 2 跳过；在 CUDA 13.1 下对 SM86 与 SM100 做 SASS 检查，确认 FMNMX.NAN.XORSIGN、HMNMX2.NAN.XORSIGN、HMNMX2.BF16_V2.NAN.XORSIGN 三种标量与打包形态都如期出现。这类改动的价值在数值稳定性：量化推理里钳位丢 NaN 是常见静默错误来源，把语义交给一条硬件指令后，NaN 不再被悄悄变成边界值。

来源：https://github.com/tile-ai/tilelang/pull/3605

1.3 主线：CI 不再因 PR 标签变更重启全量流程，ROCm 看门狗提到工作流超时之上（#3911）

#3911（1 个文件，+2/−2）只改触发条件，但问题描述值得记。主 CI 此前对 labeled 与 unlabeled 两类事件都触发，而 CodeRabbit 会给新开的 PR 一次性打多个标签，于是同一个 PR 在几秒内产生多次完全相同的全量 CI 运行；共享并发组再把这些运行逐个取消，只留最后一次。

实证在 #3908：四个标签同一时间戳落下，产生四次 CI，原始运行与前三次替换全部被取消，而没有任何 CI 作业读取 PR 标签，这些重启不提供任何覆盖。改法是把这两类事件从触发器中移除，保留 opened、synchronize、reopened、ready_for_review 与手动触发，并发策略继续负责取消过期的头部更新。同一笔改动还把 ROCm runner 的看门狗阈值提到工作流超时之上，使 AMD 作业不再在 40 分钟被强杀。

来源：https://github.com/tile-ai/tilelang/pull/3911

1.4 主线：0.1.16 版本号 PR 仍挂起，窗口内无新 tag（11-10）

#3887（[Release] Bump version to 0.1.16）最后更新停在 11-09 03:07，窗口内无任何推进，仍未合并。四个仓的发布页在窗口内都没有新版本：tilelang 仍是 09-30 的 v0.1.15（tag 序列 v0.1.15 至 v0.1.11），TileOPs 是 10-27 的 v0.1.0，TileFoundry 是 10-25 的 v0.0.4rc1，tilelang-musa 是 09-30 的 v0.1.15+musa.1。

与版本相关的另一处观察在结构侧：#3490、#3605 两笔 CUDA 原语直接进主分支，#3903（进程并行编译）、#3897（CPU 侧 cumsum/cummax）仍在审，说明 0.1.16 的功能面还在增厚而不是收口。版本号一旦落地，下游要同时核对主仓 tag 与后端仓的 musa.*、ascendc_pto 两条分支线。

来源：https://github.com/tile-ai/tilelang/pull/3887

二、多后端适配

2.1 昇腾：host-mapped 缓冲参数在审，14 个文件新增 529 行（#3909）

#3909 把 #3802 在 CUDA 侧建立的显式 host-mapped 缓冲契约扩展到昇腾：此前 Ascend kernel 一律拒绝 CPU 张量参数，即使其存储在 NPU 上可见，调用方只能关掉张量校验绕过去。改动通过同一套 T.annotate_host_mapped_buffers(...) API 声明，Cython 与 TVM-FFI 两条绑定都用 aclrtHostGetDevicePointer 校验映射，并把设备可见地址传下去，同时保留 dtype、形状、步长与执行设备三项检查；C++ 绑定保持原签名，按既有设备类型选择运行时查询。Cython 侧默认仍走 CUDA 解析器，只有昇腾提供可选解析器。

这与前一窗口在审的 #3892（torch.compile 支持）、#3893（L0C 累加器直接反量化）、#3891（L2 刷写 API）属同一条线：昇腾侧当前补的是接口与语义一致性，不是算子名单。

来源：https://github.com/tile-ai/tilelang/pull/3909

对照前几期：该仓默认分支 ascendc_pto 的最新合入仍是 11-06 的七笔，11-09 与 11-10 两个窗口都没有新合入，在审队列持续增长（本期又有 #2000 位运算 PTO uint8 包装、#1998 拷贝测试内核自动同步等更新）。测试规模上到 3060 项而合入停滞，说明瓶颈确实在评审而不在开发。

来源：https://github.com/tile-ai/tilelang-ascend/issues/2001 、 https://github.com/tile-ai/tilelang-ascend/pull/2002

2.3 沐曦：README 安装段收敛为一组命令，重复步骤与版本检查命令删除（#12）

#12（1 个文件，+10/−49）是文档净删改动。问题很具体：README 里重复出现的单包安装命令会让用户只装 TileLang-MUSA 而漏掉 TVM FFI 或环境配置。改法是在安装段只保留一组命令，同时安装 TileLang-MUSA v0.1.12+musa.5 与 TVM FFI，并在命令前后分别链到 MUSA 安装说明与文档总览；Latest News 与 TileOPs 两段统一指向安装文档，删掉重复命令、独立的源码安装步骤与版本检查命令。GEMM 示例逐字未动。

口径提醒仍成立：文档里的 v0.1.12+musa.5 是 SDK 配套渠道的版本号，开源 release 页最新 tag 是 09-30 的 v0.1.15+musa.1，两者不能互相替代。

来源：https://github.com/tile-ai/tilelang-musa/pull/12

2.4 海光：分布式三件套融合算子在审，Block-Push 与 Block-Pull 两条通信路径（#36）

#36（6 个文件，+2022/−0）在同一天内更新，一次性加入三个计算通信融合算子：Block-Push 版本的 GEMM + AllReduce、Block-Push 版本的 GEMM + ReduceScatter、Block-Pull 版本的 AllGather + GEMM，性能数据与实现说明写在 README 里。这是海光仓第一次出现分布式方向的成规模提交——此前该仓的工作集中在单卡侧（11-06 的 scaled cast #33 与 HCU reduce lane swap 布局推导 #34）。

三条算子对应两种通信发起方式：Push 由计算侧主动把结果推给对端，Pull 由计算侧去拉对端的 allgather 结果。选择哪条路径取决于通信域大小与重叠窗口，README 里给了对照数据，适合按拓扑选型。该 PR 仍为开启状态，尚未合入。

来源：https://github.com/tile-ai/tilelang-hygon/pull/36

2.5 Metal：SIMD-group 目的端越界写在 M4 上复现，修复以可证明的足迹为前提（11-10）

#3907 报的是一处静默越界：把一个显式的 8x8 metal.simdgroup 矩阵拷贝到 8x1 输出时，编译器发射的是行步长为 1 的完整 simdgroup_store，逻辑输出正确，但会覆盖输出之后的七个元素。复现环境写得很完整——Apple M4、tvm_ffi、关闭编译缓存，并用额外的后备存储作哨兵检出越界。上游基线是 72d986e1。

修复 PR #3912（2 个文件，+116/−1）的做法不是加运行时检查，而是在发射每条 SIMD-group 存储之前，要求算术分析器证明其完整 8x8 足迹同时落在目的缓冲与请求的目的区域内；证明不了就在下沉期抛出可读的 ValueError，而末元素恰好落在边界的整瓦片仍然支持。同窗口还有 #3906（[Metal] Resolve the auto execution backend to tvm_ffi）在审，属同一后端的执行路径收敛。Metal 侧本月已经是第三次出现在窗口内，从补算子转向补正确性边界，通常意味着开始有人真在 Apple 芯片上跑非玩具形状。

来源：https://github.com/tile-ai/tilelang/issues/3907 、 https://github.com/tile-ai/tilelang/pull/3912 、 https://github.com/tile-ai/tilelang/pull/3906

2.6 mlir-ascend：harness 知识库加固合入 harness 分支，Ascend 950 AscendC 收为唯一 PR 门禁（11-10）

#217（4 个文件，+140/−16）合入的是 harness 分支而非 main，这一点需要写明——该仓默认分支为 main，本窗口 main 上零提交。改动内容是让探索过程中积累的知识可靠留存：记录 hot 知识时同时保存证据快照，避免后续更新测试报告反过来使历史记录失效；禁止同一个审批编号批准不同知识条目；cooled 知识保存在临时工作区之外；知识目录出现损坏文件时提示并允许继续查看其他正常知识，但若无法确认审批编号是否重复，则暂停生成新的 cooled 知识；统一「不适用」字段的填写方式，并区分待审核知识与代码候选的命名。验证口径为 25 项 CPU 测试通过。

在审侧 #222（[CI][Ascend] Make Ascend 950 AscendC the only PR 门禁）值得记一笔：把 PR 门禁收敛到 Ascend 950 的 AscendC 一条线，意味着该仓不再为旧代昇腾维持并行门禁。若合入，昇腾 950 将成为 mlir-ascend 的唯一准入基线。

2.8 新增观察：TileLang–Weft 的 CPU/RVV 线一日 40 笔提交，553 例基准全过数值检查（11-10）

三、生态与采用方

3.1 TileOPs：33 至 40 token 的 W4A8 调用改走 40 token 解码瓦片，表外网格快 4.3% 至 11.3%（#2888）

#2888（2 个文件，+69/−47）修的是一段规则判定的错位。在 132 个 SM 的 H200 上，33 至 40 token 的 W4A8 调用一旦 128 行瓦片数超过 SM 数，就会落进「133 至 225 个瓦片、K 取 7168 / 7680 / 8192」这条带里继续走 prefill 路径，而这一类调用其实该走 40 token 的解码瓦片。

根因是过了一波之后两条路径的完成次序反转：prefill 内核用 stream-K 拆瓦片，解码内核的连续项跑在前面的先完成，原带只覆盖了部分网格，还误收了一批能整除的网格——那些网格上 prefill 反而先完成。修法是把带收窄，只保留真正该留给 prefill 的四类情形（N 非 128 的倍数、K 非 512 的倍数、512−K 项在 SM 上整除、64 行权重块按 2 的幂且至少相距 512 KiB）。表外网格上比主分支快 4.3% 至 11.3%。

同笔还补了一个此前无人覆盖的测试：解码内核跨 CTA 就绪标志漏重置。Result 行标的是 below bar，即未达该项的性能目标条，但修正的是判定规则本身，属「错路改对路」而不是「调参上分」。

来源：https://github.com/tile-ai/TileOPs/pull/2888

3.2 TileOPs：DeltaNet 前向按设备共享内存预算分流，SM89 重获 chunk 128 通路（#2891）

#2891（2 个文件，+78/−27）接的是 #2645 留下的坑：那条改动把 dim_k 小于两倍 chunk 长度的调用一律送进 state walk，而 walk 在 chunk 128、dim_v 64 时的输出趟至少需要 114688 字节共享内存（dim_v 128 时 131072），SM89 只给 101376，于是这些调用在 SM89 上直接不可用；而内核里保留的 recurrence 只需 98560 字节。

改法是让内核只在 walk 的下界确实装得下时才走 walk，否则走 recurrence，refusal 路径读取两者中较小的界。已在主分支服务的调用在 SM80、SM89、SM90 三档预算上保持原有程序不变。

性能口径如实记录：SM89 上主分支拒绝这些调用，基线只能用 FLA 的 chunk_delta_rule 前向（它自己的 chunk 是 64），chunk 128、dim_k 128 下本改动比 FLA 慢 9% 至 41%（六组用例的 TileOPs/FLA 比值为 1.41、1.21、1.28、1.09、1.28、1.09）；SM90 上主分支本来就能服务，对照主分支三组用例比值均为 1.00，无回退。测试侧新增 test_deltanet_fwd_serves_chunk_128_in_sm89_shared_memory，按 SM89 的设备事实检查分流决策，因此在 SM90 的 CI 上也能跑。

来源：https://github.com/tile-ai/TileOPs/pull/2891

3.3 TileOPs：反向 w/u 程序复用缓冲，114944 字节压到 98560 字节（#2890）

#2890（3 个文件，+155/−20）是和前一笔配对的另一半。自 #2625 之后，反向的 w/u 程序要从走出来的 dh 现组 du、dk_corr 与 dw，而 TileLang 0.1.12 把 dh 与 S、v_new 与 du 分别放在不同缓冲里，尽管它们的生命周期并不重叠，程序因此占 114944 字节，超出 SM89 的 101376。

改法是给 compute_w_u_bwd_tl 加 reuse 开关，仅在相等 head 维下启用：S、du、Aw 在各自最后一次读之后接管 dh、v_new、Au 的缓冲，程序落到 98560 字节；内核只在「不加开关时的界超出设备共享内存」时才置位，refusal 也按带 reuse 的界来读。另两处一并修好：walk 现在只在「单级就能装下」的宽度里挑 value 瓦片（此前在 batch 8、16 head、head 维 128/128 的 16 位用例上挑到需 131072 字节的瓦片，SM89 上启动即失败）；_parallel_live_bytes 补算了每个 chunk 的梯度程序在组 partial du 时仍持有的 c×c 注意力瓦片。

最后这一项带出一串连锁结论：补算之后，refusal 会让 SM90 也拒绝三笔主分支放过去却跑不起来的调用（16 位 chunk 64、head 维 256/256 在 SM90 上启动需 237568 字节），并识别出 16 位 chunk 128、head 维 32/256 与 float32 chunk 64、32/256 在主分支上启动失败、16 位 chunk 128、16/256 根本编译不过。反向基准（bf16、batch 4、4096 token、8 head、chunk 64、head 维 128/128）1.530 毫秒对 FLA 1.554 毫秒，比值 0.98。

来源：https://github.com/tile-ai/TileOPs/pull/2890

3.4 TileOPs：测试按 cluster 与共享内存事实分流，SM89 失败从 9 条降到 3 条（#2889）

#2889（3 个文件，+26/−2）是这两笔修复的测试口径配套。那条断言「行远离零时仍按行归一」的 LayerNorm 融合加法用例，其 split 分支会构建 FusedAddLayerNormHeldKernel，而该内核只在 cluster 能把每个 12288 宽 float32 行切开时才持有这些行，只有 SM90 有 cluster；SM89 上 held 内核的规则会把这类行发给 fragment 内核，于是 #2811 与 #2846 加的四条用例在数值检查通过之后仍然失败。改法是先调 check_held_launch，在没有 cluster 的设备上跳过 split 用例；8192 宽的五条 split 用例在 SM89 上同样跳过。

另把两条只装得进 SM90 的用例显式标 sm90：#2637 加的 bf16 GLA 反向（chunk 128、head 维 64/64）与 #2645 加的 float32 DeltaNet 前向（chunk 128、64/128），两者各需 196608 字节共享内存。回归数据：单张 SM89 上四个测试文件从 40 通过 9 失败 3 跳过，变为 35 通过 3 失败 14 跳过；剩下三条是 chunk 32 的 GLA 反向，需要改内核才能过。单张 SM90 上两个版本的 46 项全部通过，说明跳过标记没有把 SM90 的覆盖带走。

来源：https://github.com/tile-ai/TileOPs/pull/2889

3.5 TileOPs：paged GQA 拆分计数以窗口内 key 瓦片为上界，在审（#2892）

#2892（2 个文件，+28/−11）在审，改 GQAPagedFwdKernel._splits_for 的上界。原来拆分计数在窗口把 key 范围收窄之前就按覆盖 SM 数来计算，于是三瓦片的窗口在 batch 1 上会开出 16 个 split；不含 RoPE 时还会朝「常驻」继续增长，把 combine 端的开销翻倍——combine 要在单个 CTA 上按行瓦片读每个 split 的 partial。

新规则是先把 cp.async 的拆分计数卡在窗口内 key 瓦片数上；不含 RoPE 时，超过覆盖 SM 数之后的上界取 isqrt(key_tiles * block_N / block_M)，该点正好是 combine 的 partial 行数与一个 chunk 的 key 行数相当的位置。PR 评论里附了 #2496 要求的校准数据，覆盖 379 组配置的 regret 统计。同窗口新开的 #2893 是这一族的后续清单，仍开放。

五、趋势观察

第一，主仓的产出重心从算子转向原语。#3490 的预取与驱逐优先级、#3605 的 NaN 钳位、在审的 #3897 CPU 扫描算子与 #3903 进程并行编译，共同特征是「给作者一件新工具」，而不是「让某个算子快几个点」。这类改动的验收标准也不同：#3605 拿 SASS 里三条指令的存在与否作证据，#3490 拿计算能力门槛作边界，都可以脱离具体形状复核。对下游来说，这意味着 0.1.16 之后可用的写法会变多，但每个新原语都有自己的架构门槛，跨代移植要逐条核。

第二，共享内存预算成了线性注意力这条线的显性约束。SM89 的 101376 字节与需求侧的 114688、131072、196608 三个数字，决定了 chunk 取多大、走 walk 还是 recurrence、测试在哪个架构上跑。#2890 与 #2891 的解法思路一致：不硬压需求，而是让 dispatch 按设备事实选路，并在 refusal 里用同一个界，宁可提前拒绝也不在启动时崩。这个模式一旦在 DeltaNet 上跑顺，GLA 那一族大概率照抄——#2889 留下的三条 chunk 32 失败正好是下一块。

第三，测试口径正在从「按架构打叉」转向「按设备事实判定」。#2889 没有把 SM89 的用例删掉或永久 skip，而是先查 check_held_launch，再决定跳过；#2891、#2890 新增的两条测试也是按 SM89 的设备事实检查分流决策，因此在 SM90 的 CI 上照样能跑。这个做法比按设备算力打 skipif 标记稳，因为它验的是决策逻辑本身而不是硬件。

第四，TileFoundry 的错价问题在被算子侧反复顶回来。#318 明说同样的行为在四条已关闭的 issue 里报过、都被标 not planned，#319 一次给五条且带具体的 962.1 对 1213.6 GFLOP 偏差。分析器是 TileLang 那套「先定价再选调度」路线的前提，定价偏 26% 会让自动选择做出错误决定；这类缺口不会让任何单个算子变慢，但会让自动化在边界网格上系统性选错。

第五，RISC-V 侧的分歧在扩大而不是收敛。四源（TVM 路线、MLIR 路线、SOPHGO TPU、社区索引）整齐地停着，第三方 Weft 线却一天 40 笔，且已经把差距量化到单算子（SG2044 中位 0.0580 倍）。两条事实放在一起说明的是：停滞不是没人做，而是官方四源没有形成「自动发现差距、自动验证、自动排队」的回路——Weft 那条线是自己搭了基准引擎才跑起来的。若这套 553 例的基准能被官方四源引用为验收口径，RISC-V 侧的进展会第一次有可比的分母。
