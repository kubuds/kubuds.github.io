今日重点

这个窗口的重心换了位置。上一期主仓一天五笔合入、全部落在昇腾；本期主仓 72 小时只有一笔文档提交（LSP 仓库链接），而 TileOPs 三天十五笔、TileFoundry 三笔，加上昇腾适配仓九笔——代码量几乎全部转移到了算子库与调度器上。TileOPs 在 11-15 一天之内合入十一笔，其中解码侧的 W4A16 瓦片从单 consumer warpgroup 扩到两个，七条解码行快 10–20%，对 marlin 的领先拉到 1.20 倍以上。这不是零散修补，而是按「算子 + 选择器 + 代价模型」三层一起改：先让选择器在更多形状上选中双 warpgroup 的瓦片，再给瓦片补上按 K 切片的元数据加载，最后用 nightly 的 32 行回归确认没有一行变慢。

同一天里出现了本期最值得记的一条因果链。11-13 的 #2896 把 128 行 W4A16 瓦片换成手写 warp-specialized 主循环，在 H200 上把 chunked-prefill 从 37.3 微秒压到 31.6 微秒；约 46 小时后，#2901 在修它——sliced_pair 的 out_shared 暂存被写在 i // wg_rows == bz 的条件分支里，而 TileLang 有时会把守护这次写操作的、覆盖全部 256 个消费线程的屏障放进同一个分支，另一个 warpgroup 永远走不到那个屏障，两个 warpgroup 停在同一屏障的不同实例上，内核挂死。更麻烦的是屏障落点在同一 cache key 的两次编译之间并不稳定，而 CI 的持久化内核缓存会把坏构建一直重放下去，于是 main 上的 gpu-smoke 直接挂了。修法本身很朴素——让两个 warpgroup 都做暂存，各自只存自己那一半——但它说明了一件事：自动 warp specialization 的正确性已经不只取决于 pass 顺序，还取决于屏障被插在哪个分支里，而这个位置对编译过程不透明。

第二件事在 issue 侧，量级比代码侧更醒目。72 小时内 tile-ai 组织新开 406 条 issue，其中 cn-sys 一个账号在 11-15 傍晚 1 小时 46 分钟里连开 172 条（编号 #4208–#4381 连续，无一条夹带其他来源），ilovexsir 三天分三批开了 142 条，两人合计 314 条，占全量的七成七。cn-sys 这一批的覆盖面从 examples 与 README 的具体数字（flash-attention 号称前向误差低于 0.5%、而同目录五个检查器全用 5%；deepgemm 的 benchmark 用 8192 当 cache_size，而该参数单位是 MB，等于分配 8 GiB 去刷 128 MiB 的 L2）一直延伸到编译器本体：auto-schedule 的 IR 结构访问器漏字段、PTO codegen 的指针元素类型取了个硬编码 bfloat16 兜底。ilovexsir 那一批更成体系：142 条 issue 对应五个 batch PR（#4201–#4205，同一分钟开出），每个 PR 修一组「本该报错却没报错」的入口，比如 T.copy(transpose='False') 因为字符串 ‘False’ 是真值而静默打开了转置、_make_ascend_target() 用 dict(target_dict or {}) 把所有 falsy 配置键丢掉。审计与修复之间开始形成流水线，代价是在审队列堆到 102 笔。

第三件事是昇腾侧的算子迁移进入了「按算法家族成批落地」的阶段。11-13 一天里，tilelang-ascend 合入九笔：DSA 稀疏注意力的前向流水版、反向、topk 归约三件套，KDA 的 chunk_delta 三件套，加上 bitwise 四合一、alloc API 文档与 catlass 子模块升级。这些不再是单点补洞，而是按模型走：DeepSeek V3.2 的 sparse MLA 把 DQK 合成 512+64=576 一次 GEMM、Kimi 系 KDA 把门控衰减吸收到 host 端预计算的 M 矩阵里、反向算子把 79395 微秒压到 27388 微秒。与此同时 catlass 从 v1.0.0-6 升到 v2.2.0，顺带修掉一个此前完全静默的缺陷：旧版 CopyL1ToL0A/L0B 没有 float 特化，fp32 GEMM 直接输出 NaN 或负无穷而不报错。

RISC-V 侧本期首次打破静默。kubuds 的 TVM 路线从 mahiru、karen 之外新开 kubuds-riscv-hikari 分支，五笔提交里有 K3 移植与验证报告、rv64gc 构建解锁（USE_LLVM=ON 的链接问题与八线程构建）、解码 4 瓦片与预填充 8 瓦片的网格划分、以及 XSMTVDotII/vmadot 公开规格的溯源记录；同一时间，社区索引页收到第一笔 PR，把 kubuds fork 的项目说明写进 README。MLIR 路线（RuyiAI-Stack/tilelang-riscv）与算能 TPU 仓的引用则一动不动，两条路线仍要分开看。

窗口首日 TileOPs 连合四笔，覆盖四类不同负载。MoE 分组 GEMM 的 FP8 前向把 A 的 scale 从生产者暂存改成走 TMA box（#2894），让 ds-v3-ep8-prefill-up 与 -down 的 128 行瓦片把 stage_scales 从 1 降到 0，H200 上分别从 269.3 微秒降到 262.0、从 142.2 降到 137.2，对 DeepGEMM 的比值升到 1.096 与 1.157。W4A16 的 128 行瓦片改成手写 warp-specialized 主循环，在上一块 WGMMA 还在跑的时候解码下一块 K（#2896），chunked-prefill 从 37.3 微秒降到 31.6。软归约把 16 位 softmax 行放到两个 256 线程 CTA 的集群上而不是四个 128 线程 CTA，fp16 项用一条 FFMA 完成「按缩放后的最大值平移」（#2898）。分页 GQA 的切分上界同时被窗口内的 key 瓦片数与 combine 的读量卡住（#2892），顺带关闭了 #2496 那条悬了很久的标定请求。

来源：https://github.com/tile-ai/TileOPs/pull/2894、https://github.com/tile-ai/TileOPs/pull/2896、https://github.com/tile-ai/TileOPs/pull/2898、https://github.com/tile-ai/TileOPs/pull/2892

1.3 TileOPs：11-15 单日十一笔，W4A16 解码瓦片再快 10–20%（11-15）

11-15 一天十一笔合入，其中 #2955 是当日的收口：W4A16 选择器把「至多 32 行」的延迟缩放挑法从一个 128 线程 consumer warpgroup 挪到两个，按权重行数分摊、按 K 切片拆分以保住 CTA 数，stream-K 仍留单 warpgroup。理由是解码瓦片被指令发射卡住而代价模型偏爱单 warpgroup 的做法——实测那条路径上 issue slot 占用 49.5%、DRAM 只有 54%。结果七条解码行比 main 快 10–20%，对 marlin 领先至少 1.20 倍，prefill-mlp-up 未变且仍落后 torch 0.7%。同一天还有 #2952 把目标侧内核的两张表并成一张、读取前先复制以避免并发下「迭代中字典改变大小」，#2904 修掉一次「没有设备、没有具名 target、没有进程默认」的调用抛出 _Unresolved object is not callable 的问题。

来源：https://github.com/tile-ai/TileOPs/pull/2955、https://github.com/tile-ai/TileOPs/pull/2952、https://github.com/tile-ai/TileOPs/pull/2904

1.4 TileOPs：ping-pong 三连，MoE 共享专家在每个重复里压过 FlashInfer-CUTLASS（11-15）

同一主题三笔递进。#2919 先让分组 GEMM 选择器自己挑出的 64x256 单 warpgroup 紧致瓦片改跑双 warpgroup 的 ping-pong，使每个瓦片的收尾落在另一组的 mainloop 之下，ds-v3-grouped-t2048 的下投影 GEMM 从 1818 微秒降到 1707。#2953 把同一手法推到选择器自己的 64 行紧致瓦片上，覆盖融合 gate/up 与短分组瓦片，并明确「短分组瓦片仍留一个 warpgroup，因为它的收尾太短、藏不住东西」；结果是 FusedMoESharedExpert 的 ds-v3-grouped-t2048 在每次重复里都压过 FlashInfer-CUTLASS（中位 5674 对 5744 微秒），32 行六算子的程序变化没有一行变慢。#2915 则把未融合的 ping-pong 分组 GEMM 输出按 64 列 TMA box 暂存，换来第五个环级（64x256 瓦片多出 40 KiB 一档）。

来源：https://github.com/tile-ai/TileOPs/pull/2919、https://github.com/tile-ai/TileOPs/pull/2953、https://github.com/tile-ai/TileOPs/pull/2915

1.5 TileOPs：#2901 修 #2896 带来的挂死，屏障落进了 warpgroup 分支（11-15）

这是本期最值得读的一笔。#2896 合入后，main 上的 gpu-smoke 挂了：sliced_pair 在 i // wg_rows == bz 这个条件下暂存 out_shared，经布局 lowering 后只有「保留那半个瓦片」的 consumer warpgroup 会执行暂存循环；TileLang 有时会把守护这次写操作的、覆盖全部 256 个消费线程的屏障插进这个分支，另一个 warpgroup 永远走不到，两组停在同一屏障的不同实例上，内核死等。#2899 先前加的那道显式屏障并不足以阻止它——编译器仍可自行在分支内插屏障。修法是把暂存挪出条件：两个 consumer warpgroup 都写自己的那一半。真正刺眼的是后半句：屏障落点在同一 cache key 的两次编译之间会变化，而持久化的 CI 内核缓存会把坏构建一直重放，于是一次不稳定插桩变成了稳定失败。

来源：https://github.com/tile-ai/TileOPs/pull/2901、https://github.com/tile-ai/TileOPs/pull/2899、https://github.com/tile-ai/TileOPs/pull/2896

1.6 TileOPs：#2918 让编译图跨进程复用，一次 pyupgrade 改 1926 处（11-15）

#2918 把编译边界的键从「每进程一个 uuid」换成「算子类 + 参数摘要 + 构造期张量布局 + 该实例在类内的序号」，于是后启动的进程可以直接复用 Inductor 的 FX 图缓存与 AOT autograd 缓存；代价是参数一旦被赋新值就要重追踪，被就地修改则在追踪期直接拒绝。同一笔还把 tileops.backend、authoring、manifest 三个包的 pyright --verifytypes 拉到 100%（此前为 100%/50%/21%），并把 ruff 的 UP 规则全仓应用——307 个文件 1926 处。这类提交不产生性能数字，但它决定了 nightly 与 CI 的等待时间，也决定了新人能不能靠类型提示读代码。

来源：https://github.com/tile-ai/TileOPs/pull/2918

1.7 TileOPs：manifest 补四个 spec-only 算子，从 Embedding 到 RoPE 余弦正弦（11-15）

#2920 给试点的五个模型缺的四个算子补了「只有规格、没有实现」的清单条目：EmbeddingFwdOp（含整数表，对应 DeepSeek-V4-Flash 的哈希路由）、MaskedScatterFwdOp、RMSNormGatedFwdOp（带 sigmoid 门控的激活参数）、RoPECosSinFwdOp（按 token 给角度，允许 x 是带步长的视图以支持尾列旋转）。同时新增 tileops.indexing 家族、给每条补 torch 参考实现到 tests/test_spec_reference.py、按读取行数为 embedding、masked scatter 与 RoPE 定价（两个 roofline 函数加一个内联 bytes，各配手写 oracle）。这套做法的意义在于：先把接口与定价钉死，实现可以是后来者补的。

来源：https://github.com/tile-ai/TileOPs/pull/2920

1.8 TileOPs：#2951 自适应池化按 lane 拆分，主分支三种池化在窄长形状上编译不过（11-15）

AdaptiveAvgPool2dLanesKernel 把每个 bin 拆到 2 的幂个 lane 上（至多一个 warp），每个 lane 用带 clamp 的无条件向量载入读自己的 tap，再用 shfl_xor 折叠。驱动这条规则的是根因：原实现一个输出一个线程走完整 bin，未批处理的 ResNet 头只有 8 个 CTA，DRAM 占用低于 3%。附带修掉一个更硬的问题——adaptive_bin 在乘积越过 int32 时没有拓宽到 int64，于是三个自适应池化算子在 main 上对 (1, 1, 150001, 16) -> (100000, 1) 这个形状全部构建失败。

来源：https://github.com/tile-ai/TileOPs/pull/2951

1.9 TileFoundry：#325 用一种 FunctionRef 统一全部被调者命名（11-13）

IR 里此前有五种命名被调者的方式——绑定的 Function/PrimFunction 对象、槽绑定的实例调用、保留调用、启动目标、变体标签——每个消费者各按自己的方式解析，求值器甚至从「加载的读法」而不是模块作用域里挑定义。#325 把它们收成一个静态叶子 FunctionRef(path, name)：路径相对调用者，None 段表示运行期索引、作为前导操作数传入，core.resolve(scope, ref) 成为唯一解析器；解析器同时把「@module 里后声明的名字」定义为错误（DeclarationOrderError）。连带的清理包括 StoragePlan.scratch 改为发射前算好、删掉 relaunch、host 入口声明并转交 scratch。

来源：https://github.com/tile-ai/TileFoundry/pull/325

1.10 TileFoundry：维度算术收进标量渲染器，Mesh 选择切片不再丢（11-13）

五、趋势观察

一是主仓静、算子库动，重心位移已经连续两个窗口。上一期是主仓一天五笔全昇腾、TileOPs 连续零提交；这一期反过来，主仓 72 小时一笔文档，TileOPs 三日十五笔、TileFoundry 三笔。把两期并起来看，TileLang 的开发重心正从「编译器本体」移到「算子库 + 调度器」：编译器本体的改动集中在修回归（PTO 那条线的善后期），而新增能力更多以算子库的瓦片、选择器、代价模型的形式出现。判断依据不只是合入数，还有依赖方向——TileOPs 的性能结论要引用 TileFoundry 的 roofline 与调度，而 TileLang 主仓这一期没有给它们任何新东西。

二是自动 warp specialization 的正确性已经成为一等风险。#2896 到 #2901 这条链说明：当一个性能改动把同步责任交给编译器自动插桩时，插桩位置就成了正确性的一部分，而它对上层不透明——同一个 cache key 两次编译，屏障可能落在分支内也可能落在分支外。再叠上 CI 的持久化内核缓存，偶发的坏插桩会被固化成稳定失败。这一问题目前没有结构性解法，只有「把写操作挪出条件分支」这类局部规避；如果后续更多瓦片走 ping-pong，同类挂死大概率会再出现。

三是审计已经从「发现问题」变成「流水线生产问题」。三天 406 条 issue、两个账号 314 条，其中 cn-sys 的 172 条在 1 小时 46 分钟内写完，ilovexsir 的 142 条直接对应五个 batch 修复 PR。这套模式确实在压缩「缺陷发现到修复」的周期（同一天内 issue 与 PR 并存），但它把压力转移到了评审端：在审 102 笔、合入 30 笔，其中 22 笔 mlir-ascend 同构 PR 只能由极少数人过。下一阶段的瓶颈会是评审带宽，而不是发现速度。

四是昇腾的算子迁移进入「按模型家族成批落地」。DSA 三件套对应 DeepSeek V3.2，KDA 三件套对应 Kimi 系线性注意力，一天之内九笔都指向具体模型的完整链路，而不是零散算子。这对下游是好消息——模型迁移的成本从「逐个算子凑」变成「按家族批量搬」；但也意味着底层模板库的质量权重上升，catlass 那个 fp32 GEMM 输出 NaN 而完全不报错的旧缺陷就是例证：它藏在第三方 submodule 里，靠算子层测试发现不了。

五是RISC-V 四源首次出现实质推进，但只有一支在动。kubuds 的 TVM 路线新开 hikari 分支并给出 K3 移植验证与 RVV 网格数据，社区索引页第一次收录该 fork；而 MLIR 路线（RuyiAI）与算能 TPU 仓引用未动。两条路线的分工已经明确：TVM 路线在做「能跑起来、有实测数据」，MLIR 路线停在「有设计、无提交」。判断不变——这条线目前仍属小规模投入，值得按窗口跟，但不宜按周计算进度。

局限说明：本期结论来自 GitHub 检索接口与仓库原子流，未做代码级复核；PR 的性能数字取自作者在 PR 描述里给出的基准表（H200、CUDA 13.2、PyTorch 2.13），未在本机复测。issue 统计依赖 search 接口的 total_count 与五页翻页结果（406 条与逐条汇总一致），标题分类只按关键词粗分。tilelang-ascend 的默认分支是 ascendc_pto 而非 main，首次查询按 main 取提交返回 404，已改正后重查。mlir-ascend 的 harness 与 hygon 的 tilelang-tileops-fix 分支窗口内均无提交。新闻侧零命中，无外部报道可交叉验证。
