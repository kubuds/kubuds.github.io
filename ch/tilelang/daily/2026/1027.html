一、核心项目进展

1.1 主仓：out_idx 输出改在调用方流上分配，H100 复现的五次三次损坏归零（#3649）

合于 10-26 22:36，5 文件 +183/-31，修 #3648。cython、nvrtc、cutedsl 三个适配器都接受 stream= 并在该流上启动，但 out_idx 输出是用 torch.empty 在当前 torch 流上分配的；缓存分配器只按「分配流」排序复用，于是一块仍有排队工作的显存被当成空闲块返回，那批工作随后覆盖内核结果。修法是新增 output_allocation_stream(stream, device)：调用方流与当前流不同时返回调用方流，否则返回空；句柄为零时映射到默认流，因为旧版 PyTorch 的 ExternalStream(0) 会给出池化流而不是默认流。H100 80GB 上的复现从 4/5、5/5、5/5 损坏变为三个适配器各 0/5，新增测试文件 10 项通过。作者明确否决了加 wait_stream 的写法：那会让每次调用都把启动流排在当前流的全部工作之后。

来源：https://github.com/tile-ai/tilelang/pull/3649

1.2 主仓：NVRTC 设备端编译接进 TVM-FFI 执行路径，新增编译键项（#3285）

合于 10-27 00:02，12 文件 +133/-133。新增 tl.cuda_compiler="nvrtc"，与既有 TVM-FFI 宿主运行时配合：NVRTC 把设备端 CUDA 源编成 cubin，共享 CUDA 运行时模块导入这些字节，宿主侧绑定、标量转换、条件、循环与启动准备仍由 TVM-FFI 生成，默认值仍是 nvcc，旧的 execution_backend="nvrtc" 适配器保持原实现。二进制缓存键里加进了编译器名与 NVCC/NVRTC 版本，与目标细节和有效编译选项一起参与哈希；架构 token 如 90a 与 100f 原样保留，不兼容目标在编译前报诊断；每个成功创建的 NVRTC program 都在 finally 里销毁。该 PR 的 CI 在 H20 上跑出 5506 通过、491 跳过，示例 76 通过，ROCm 7.2 通道 3220 通过，昇腾通道 1797 项通过。

1.3 主仓：批量 TMA 加载的 cache hint 少一个模板参数，DeepSelect 的 TMA 路径编译不过（#3683）

合于 10-27 00:11，2 文件 +20/-11。eviction_policy="evict_first" 或 "evict_last" 的批量 TMA 加载在 main 上编译失败：代码生成发出一个 CacheHintSm90 模板实参，而裸指针版的 tl::tma_load 重载只接受屏障类型。这条缺陷直接压住了 DeepSelect 的 TMA 路径，在 GB200 加 CUDA 13.1 上用该示例的 ring 与 replay 用例复现。修法是从 #3296 里抽出缓存提示这一块，补上缺失的模板参数并把选定的策略传给 PTX 指令；共享内存对齐那一部分仍留在 #3296。修复后同一台机器上 DeepSelect 全文件 144 项通过、TMA 拷贝测试 22 项通过，CUDA 12.9 的 SM90 编译检查也确认三种策略的 PTX 都带上了应有的操作数（#3296 的其余改动尚未合入）。

来源：https://github.com/tile-ai/tilelang/pull/3683

1.4 主仓：归约的 FP8/FP4 非有限常量写出非法字面量，亚字节累加器改为早拒（#3189）

合于 10-26 15:44，7 文件 +204/-4，修 #2998。T.reduce_max 与 T.reduce_min 在输出为 FP8 E4M3 时发出非法的 inff 字面量；现在非有限的 E4M3、E8M0、FP4 常量改走既有的转换构造器并传入合法的 CUDART_INF_F 与 CUDART_NAN_F 表达式，饱和与 NaN 行为保持不变。同一笔改动让普通与延迟归约提前拒绝亚字节数值累加器（FP4、int4 之类），给出一句明确诊断；FP4 输入配 FP16 或 FP32 累加仍受支持，布尔归约豁免，E8M0 归约支持仍不在本次范围内。B300 加 CUDA 13.1 上 28 项聚焦测试全过，完整归约测试文件 150 项通过，另有三项批处理校验失败是 main 上已有的。

来源：https://github.com/tile-ai/tilelang/pull/3189

1.5 主仓：SM120 分块缩放 GEMM 显式展开 K 原子，FullCol 配置提升 51%（#3286）

合于 10-26 16:36，4 文件 +308/-2。这是 #3257 引入 T.gemm_blockscaled 与 T.mma_gemm_blockscaled 后的收尾：A 操作数取自寄存器分片时，K 原子循环原先用 T.serial，每次片访问都是运行期下标，nvcc 在不自行展开的流水化与 warp 特化内核里会把分片留在局部内存，也就是把 MMA 路径溢出掉；改为 T.unroll(..., explicit=True) 后每个访问都是编译期常量。第二处是 SFA 与 SFB 都在共享内存时，原来每对 MMA 要读三次共享，现在每 lane 每 K 原子只装一次紧凑选择包，行主序与分块 K 主序两种布局都覆盖。RTX PRO 6000 Blackwell 上 143 项通过、4 项跳过，输出与 float32 参考逐位一致；寄存器 A 基准里 FullRow 提升 2.7%、Square 11.1%、FullCol 51%（348.5 到 526.7 TFLOPS），ptxas 报告的溢写从 664 字节与 484 字节降到 320 与 160。作者同时标注：block_K = 128 配行主序共享 scale 的路径在 main 上本就不过校验，与本次改动无关，留待另查。

来源：https://github.com/tile-ai/tilelang/pull/3286

1.6 主仓：JIT 输出形状里的标量参数在分配前解析（#3602）

合于 10-26 10:06，7 文件 +242/-3，修 #3406。Cython 与 PTO 包装器以前在分配输出时，遇到用显式标量 PrimFunc 参数表达的输出维度就解析不出来；现在适配器传出「输出维度到标量参数位置」的映射，包装器直接用实参值，且不追加重复的启动参数。回归覆盖两个后端、零维与非零维、标量与多维输出、输出顺序、设备放置与启动参数个数。同一族缺陷的后续两笔仍在审：#3636 处理 (n, 2*n) 这类复合维度表达式，#3638 处理同名但彼此独立的动态符号被按名字合并的问题。

1.7 主仓：sm8x 稀疏元数据的操作数 dtype 不再无兜底落入（#3335）

合于 10-26 16:54，1 文件 +12/-5。稀疏元数据的布局构造函数按架构分派，把 MMA 操作数 dtype 与元数据缓冲宽度配对；sm90 分支会拒绝不支持的 dtype，sm8x 分支却写成两条白名单检查且没有兜底，于是其他拼写都会落到下面的放置逻辑，而那段逻辑只从缓冲宽度推 group 与 interweave。后果是 float8_e4m3fn（torch 的正规拼写）被按 16 位元数据接受，并套用了 fp16 的 group 32 与 interweave 4 约定；任何未识别的拼写包括打字错误也在任意宽度被接受。现在不支持的 dtype 直接报错。

来源：https://github.com/tile-ai/tilelang/pull/3335

1.8 主仓：DeepSelect Top-K 示例合入，129 组配置里相对 torch.topk 最高 8.00 倍（#3304）

1.10 新增缺陷：ThreadSync 三类错位栅栏，配三笔在审修复（#3680 / #3682 / #3681）

3.10 TileFoundry：动态共享内存按内核实际视图定尺寸（#271）

10-26 开出并在审，12 文件 +340/-32。合成的宿主入口以前给每个 TIR 内核都传 dynamic_smem=0，用整数 TensorView 偏移访问共享内存的内核因此在没有动态共享内存的情况下运行，超过 48 KiB 时也从不提升 cudaFuncAttributeMaxDynamicSharedMemorySize。作者选择按内核实际达到的最远字节数来定尺寸，而不是按目标容量，理由有两条：CUDA 把静态与动态共享内存算在同一个每块限额里，而该运行时自带若干静态共享内存（ProgramMetaData 或共享的分配张量），按满容量申请会直接起不来；每块申请多少还决定一个 SM 上能放几块，sm_89 上申请 99 KiB 时哪怕只用 512 字节也只能放一块。代码生成同时改为在首个语句前声明一次 smem_base，因为在 loop_outputs 里它原先落在第一个循环的块内，第二个循环看不见，nvcc 报未定义标识符。H200 与 sm_89 上两项 GPU 测试通过，未打补丁时前者非法访存、后者编译失败。

3.12 TileFoundry 新缺陷：分析侧把共享内存峰值算重、且不传到 TIR（#272）

10-26 开出，作者是在评审 #271 时发现的，两条缺口都指向同一种后果：分析能通过的程序在启动时被拒，或最终 TIR 无法自述需要多少共享内存。第一条，内存分析把 smem 与 facts.memory.shared.per_cta 比较（sm_89 上 101376 字节），但 CUDA 把这个限额同时作用于静态与动态共享内存，而运行时自身持有 12 字节的 __shared__ ProgramMetaData，这项占用只写在 runtime.cuh 里，没有告知分析，于是恰好差在 12 字节以内的放置能通过分析而在启动时被拒。第二条，分析把每 CTA 的共享内存高水位记在 RegionMemoryMetadata.peaks，但 ConvertHIRToTIR 不把它写进产出的 TIR，PrimFunction.metadata 既不打印也不解析，于是 finalize 之后必须重算一遍（#271 正是靠扫描所有整数地址的共享内存视图重算），而作者写的宿主入口申请过少也不会在运行前被发现。

五、趋势观察

一、正确性缺陷的重心从「性能回退」移到「编译期不报、只在特定架构或存储域上错」。当日主线三笔都属此类：输出在错误的流上分配（#3649，只在非默认流且当前流有排队工作时损坏）、TMA 缓存提示少一个模板实参（#3683，只在带 eviction_policy 的批量加载上失败）、sm8x 稀疏元数据没有兜底（#3335，只有 torch 正规拼写才被认出，且套错 fp16 的布局约定）。这类缺陷的共同点是有硬件或参数前提，常规 CI 覆盖面之外，因此越来越多由模糊测试系列驱动——本章当日关闭的六条里有五条来自该系列。

二、同步与内存规划成为主战场。当日浮出的 #3680 三条 ThreadSync 缺陷、配 #3682 与 #3681 两笔修复、tvm 分叉仓 #88 的证明器修正、主仓 #3670 的区域化 kill 重排、TileFoundry #272 的共享内存峰值不落 TIR，指向同一件事：编译器的同步与内存判断正在从「启发式」转向「可证明」。这也解释了 #3666 为何重要——它把内置 TVM 换成独立打包的 TIRx，此后这类证明器修正才能以正常版本节奏进入主线，而不是停在分叉仓里。

三、后端适配进入「精确控制」阶段。昇腾的 T.annotate_buffer_addresses 让 UB、L1、L0A、L0B、L0C、SS 各池可以按字节定址并做重叠、对齐与容量校验，海光的寄存器流水线、warp 发散与 scale 缓冲双 bank 分区，都是把「能跑」推向「能按硬件结构摆」。这些能力集中在最近两周，说明国产后端已过可用性门槛，开始处理性能上限问题。

四、发布工程仍是短板。TileOPs 的首发在文档、清单、打包、API 稳定性、输入校验全部就绪之后，卡在 TestPyPI 试跑与首个 tag 上已多日，PyPI 制品停留在 2025-10-09。对一个 196 星、当日合入 14 笔的算子库来说，可安装性比再优化 1 个百分点更能决定外部采用速度；追踪单里唯一未完成的技术项是 MHA 行 0.996，管理层不应让它继续阻塞 tag。

五、外部生态在同步扩张。RISC-V 社区枢纽仓、CANN 算子仓、Hexagon 后端仓同日出现或更新，说明 TileLang 正在从「tile-ai 组织的项目」变成多平台各自建仓的生态。对国内读者，RISC-V 方向尤其值得跟踪：它与此前 AI 眼镜、端侧推理的硬件路线直接相关，但目前仍只有空骨架，实质性进展需要看后续是否有可运行的算子与后端落地。
