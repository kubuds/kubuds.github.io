一、核心项目进展

1.1 主线：CuTeDSL 的 grid 同步改到每次启动的 workspace，多流并发不再串扰（#3868）

合于 11-08 18:00。CuTeDSL 的 sync_grid() 原先把 barrier 计数与代际放在模块级全局（__grid_sync_ctr、__grid_sync_gen），同一 kernel 在两个流上并发启动会共享同一个 barrier：两个 grid 的到达被合并，某次启动可能在自己的 block 全部到达前就被放行，残留计数还会挂住后续启动。H200 NVL 上单次 17.4 毫秒、成对 17.8 毫秒，说明 cooperative launch 确实在并发。修法是用 inline PTX 复刻 cooperative_groups::details::sync_grids：barrier 字取驱动为每次 cooperative launch 提供的 grid workspace 的 barrier 字段，地址来自 %envreg1（高半）与 %envreg2（低半）；每个 block 的 thread 0 做一次 atom.add.release.gpu，block 0 加 0x80000000 - (nblocks - 1)、其余加 1，再以 ld.acquire.gpu 自旋等 bit 31 翻转。状态按启动隔离，因此并发启动互不影响。回归测试在 main 上会挂死（300 秒被杀），修复后通过；作者同时保留了 CUDA 后端作对照，后者一直正确。

来源：https://github.com/tile-ai/tilelang/pull/3868

1.2 主线：CuTeDSL 有符号整数截断按 arith.divsi 语义修正（#3551）

合于 11-08 07:48。CuTeDSL 对有符号 TIR 的 DivNode 发出的是 Python 地板除，运行期 T.truncdiv(A[i], 3) 在 -7 上返回 -3 而不是 -2，后续的 floor/ceil 修正再基于这个商继续算，误差会扩散。改法是给有符号标量与向量发 tl.truncdiv（底层 MLIR arith.divsi），纯 Python 输入走精确整数运算，向量存储路径与无符号 lowering 不动。回归 25 例，覆盖 int8/int16/int32/int64、标量与向量、负除数、整数极值，以及「商乘除数加余数等于被除数」。报告者在 issue #2973 的讨论里独立用 CPU 参考与 MLIR 验证过，并指出纯 Python % 的边界，这条意见直接进了实现。

来源：https://github.com/tile-ai/tilelang/pull/3551

合于 11-07 18:59，+7075 至 -394、63 个文件，是本期体量最大的一笔。新增面包括：warp vote、match 与位搜索，块谓词屏障，显式宽度的载入与存储及缓存提示，NaN 传播的 min/max，TMA 与 cluster 拷贝（multicast、store_cluster、gather4、scatter4），SM120 的块缩放 MMA（mxf4nvf4）与配套的 NVFP4 GEMM 示例。同一笔还修了 warp specialization 的一个老问题：夹在 pipeline 之前的 T.fill 被搬进 producer/consumer 分支后，即使隔着循环或条件，也会在每轮迭代后重跑，覆盖当轮 T.clear 的结果。

1.4 主线：CUDA 单次 kernel 启动可命名，profiler 里分得清阶段（#3816）

合于 11-06 17:45。一个 PrimFunc 里的多个 T.Kernel 原先共享自动生成的名字前缀，profiler 里分不清阶段。新增可选 name= 参数，T.Kernel(grid, threads=128, name="compute_stats") 与 T.ClusterKernel 都支持，生成的设备符号就是 compute_stats，不再附加 _kernel 后缀。名字经 tl.kernel_name 注解穿过 LowerOpaqueBlock，由 SplitHostDevice 生成设备函数时消费；显式名字校验为非空 ASCII 标识符，重名与宿主函数冲突走既有的全局符号供给，未命名的启动保持旧命名。文档同步覆盖了命名、宿主调用目标、非法输入、eager JIT、共享内存与 cluster 启动。

来源：https://github.com/tile-ai/tilelang/pull/3816

1.5 主线：多源缓存目录，读任意、只写第一个（#3807）

合于 11-06 13:31，+593 至 -288、18 个文件。TILELANG_CACHE_DIR 支持冒号分隔的多个目录，例如 /cache/read/and/write:/cache/readonly/A:/cache/readonly/B，编译产物可以从任意目录命中，但只写第一个。这对应集群里「共享只读缓存 + 本地可写层」的常见形态，能让一批构建共享同一份算子缓存。作者注明边界：CuTeDSL 后端在只读目录上可能出问题。

来源：https://github.com/tile-ai/tilelang/pull/3807

1.6 昇腾：移除 Z3 调度全局锁，冷编译最慢项 37.3 秒降到 25.6 秒（#3812）

合于 11-06 18:17。Ascend 的 Python 调度回调把所有 Z3 solve 用一把全局锁串行化，尽管每次调用已经持有私有的 Z3 context。移除后独立编译线程可以并行调度：8 线程、每 kernel 8 个配置的冷编译批处理里，SwiGLU backward 从 33.1 秒降到 30.0 秒，MoE gate forward 从 37.3 秒降到 25.6 秒。验证是 884 项既有 Ascend auto-schedule CPU 测试、64 个并发请求与串行结果一致，以及 16 个采样的 SwiGLU backward 与 MoE gate 配置在改动前后生成完全相同的调度、源码与设备 ELF。

来源：https://github.com/tile-ai/tilelang/pull/3812

1.7 昇腾：access_ptr 区域修复，跨行与转置视图不再丢 DMA 依赖（#3805）

合于 11-06 12:08。连续 SIMD 载入跨行、或使用转置视图时，access_ptr 重建的区域会丢失输入 DMA 依赖，AutoSchedule 因此可以把 load 排到 copy 之前，InsertSync 也就不再插 MTE2 到 V 的同步。改法是复用保守的指针区域重建：跨行时带上起始偏移，无法重建的布局回退到整缓冲；保留简单的一维正步长快路径。回归覆盖两个跨行用例与一个转置视图，分别在有/无 AutoSchedule 下验证「DMA → set/wait → load」顺序与事件 ID 对齐；171 项相关 host 侧 IR 测试通过，设备执行未测试（作者写明了这条边界）。

来源：https://github.com/tile-ai/tilelang/pull/3805

1.8 示例：sm_12x 按可用动态共享内存选瓦片，RTX PRO 6000 全过（#3845）

合于 11-08 06:25。dim=128 的 block-causal varlen 用例原先固定 128x128 瓦片，前向需要 128 KiB、dK/dV 约 192 KiB，而 sm_86/89/120 的动态共享内存上限约 99 KiB，启动直接报 Failed to set the allowed dynamic shared memory size。改为从 get_max_dynamic_shared_memory() 取 block_size：数据中心卡保持 128x128，小共享内存设备用 64x128（约 96 KiB），并保持 block_size 能被 dllm_block=64 整除。RTX PRO 6000（sm_120）上 CUDA 与 CuTeDSL 各 209 passed、26 skipped、0 failed；H200 NVL（sm_90）上 128x128 两例通过。作者称这是 #3701 留下的最后一个失败示例。

来源：https://github.com/tile-ai/tilelang/pull/3845

五、趋势观察

第一，自动化的闭环已经成形，但闭环的重心从「写代码」移到了「定契约」。topa 的 15 笔没有一行 kernel 代码，全是轮次规则、评审清单、PR 体格式与 worktree 清理；TileOPs 的 33 笔里大部分是「按目标条改一个参数、给一组 A/B」；TileFoundry 的 5 笔则是在定义什么叫「放置相等」「TMA 完成」「覆盖前的读」。三者叠起来是一条完整的流水线：夜间跑分发现差距，队列分配算子，agent 在 TileFoundry 的调度空间里改，评审按清单核对数字，合入后自动结项。这条流水线的产出效率已经体现在数字上（72 小时 71 笔），但它对「契约写得够不够清楚」极其敏感——今天 #2867 标注「低于目标条」仍被合入，#301 在排不出顺序时选择报错而不是猜，都是契约在起作用的样子。

第二，昇腾的瓶颈从「能不能编译」变成「声明与实现是否一致」。14 条 issue 里没有一条是「不支持某功能」，全是「声明支持但实现走了另一条路」：HCU_MCPU_SET 有 gfx928 而 C++ 没有分支（海光同理）、T.simd.vcvt 文档写了 int32/int64 到 f16 而实现拒绝、annotate_unlimit_memory 的错误信息让用户传 "shared.ss" 而函数自己拒绝、gemm_blockscaled 的位置参数与公共签名分叉。这类缺陷的共同修法不是加功能，而是把「声明」与「实现」放在同一张表里做生成式检查——例如从 HCU_MCPU_SET 生成后端必须覆盖的架构清单，从 intrinsic 注册表生成 dtype/位宽支持矩阵。在做到这一点之前，3060 项全过的测试报告只能说明「已测的组合没问题」。

第三，CuTeDSL 正处在「功能覆盖接近 CUDA、正确性边界尚未收敛」的阶段。#3685 一次补 63 个文件、把 cluster TMA、SM120 块缩放 MMA、Philox、warp vote 这些 CUDA 侧早已有的能力补齐，说明功能面对齐已经接近完成；但同一窗口的缺陷全在边界上：多流并发下的 grid barrier（#3868）、有符号整除（#3551）、无符号原子与无符号缓冲（#3874/#3875/#3876）。这些都不是「没实现」，而是「实现了但语义与 CUDA 不一致」。对使用者的实际建议是：CuTeDSL 路径适合用来跑示例与开发，生产 kernel 在换后端前应做一轮与 CUDA 后端的逐元素差分，尤其是涉及负数除法、无符号比较与多流并发的场景。

第四，性能优化的记录方式在变。TileOPs 这批 PR 的特点是每笔都写清楚「哪个 op、哪个 benchmark、结果是否达标、根因是什么」：#2868 给出 900444 个 sector 对 501760 个写入的具体数字，#2869 给出 16 个内存放置里 12 个落后的分布，#2855 给出 12 轮热身、每轮 10 次调用的中位数并主动声明「未控制执行顺序效应」。这种写法让「没达标」也能合入（#2867），因为读者能判断它是否值得。相比之下，只写「提升 X%」的 PR 在评审时无法区分是 kernel 变快还是测量变了。

最后是 RISC-V 线。四源巡检 72 小时无变化：kubuds/tilelang-riscv-kubuds 的两个 kubuds- 分支、RuyiAI-Stack/tilelang-riscv 的 MLIR 路线、TongmingLAIC/tilelang-riscv 索引页与 TongmingLAIC/tilelang-tpu 的 SOPHGO 分支都停在原引用。这与主线的节奏形成对比：GPU 侧的 agent 化流水线已经把迭代压到「天」，RISC-V 侧仍是「周」级的人工推进。两条线的差距不在工程量，而在有没有一条能自动发现差距、自动验证、自动排队的回路。
