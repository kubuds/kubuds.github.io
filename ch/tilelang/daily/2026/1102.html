今日重点

这个窗口最重的动作是减法。主线把三周前合入的精确线程计数（#3291）整笔回退（#3733），理由写得很直白：那套改动把昂贵的计数查询搬到了满块栅栏检查之前，即使所有线程都会到达栅栏也要跑证明，当前 TVM 的求解预算会被耗尽并返回部分计数，于是本来合法的 remap 与 sequence 辅助 kernel 直接以「Cannot prove a thread rectangle」编译失败。回退在两套 ThreadSync 实现上同时进行，删掉 #3291 引入的测试，补一个「循环对多数线程为空、256 线程仍全部到达栅栏」的归约用例；商守卫、精确参与线程界、非矩形线程集这些正确性改进也一起撤回，新开的 #3732 留作迁移后重新优化的跟踪单。这是明确标注为临时措施的迁移让路：TileLang 正在准备 TIRX 迁移以摆脱当前 TVM fork 依赖，配套的 TVM fork 优化提案已经关闭。

第二条线是昇腾在补地基。#1948 修的是宿主侧一笔与算子规模无关的固定损耗：Cython wrapper 每次调用都无条件构造 TVM Analyzer，实测在 910B3 上约 0.28 毫秒一次，而它只在形状为符号表达式时才用到；改成惰性构造后，vec add 单块从 442 至 467 微秒降到 105.1 微秒，32 块从 441 至 493 微秒降到 108.0 微秒，kpool 压缩从 447 至 450 微秒降到 111.3 微秒，作为下限的裸 ctypes 调用约 12 微秒没变。同期 #1971 的 RFC 给出同步实现的替换路线：移植主线同步核心加独立的 Z3 证明服务，用旧 TIR 适配层接进现有编译流水，保留 TVM、调度、内存规划、AscendC/PTO codegen 与运行 ABI，验收通过后再切默认实现并删除旧算法——与 #1975 把整个 Ascend 仓迁到主线多后端架构是一件事的两个落点。

第三条线在算子库。TileOPs 在 11-01 一天合入 13 笔，几乎全部是性能补丁，且每笔都附 H200 实测表与 manifest 回归门槛。其中 #2808 把 GQA 稠密前向的程序选择收成一条规则，相对最快候选程序的选择遗憾从 1.818 降到 1.017（2 至 128 个 query 位置、586 次调用），并修掉主线一个真实错误：score scale 在乘上 log2(e) 后于 FP32 下消失，输出变成 NaN 或错值。

一、核心项目进展

1.1 主线：ThreadSync 的精确线程计数回退，为 TIRX 迁移让路（#3733）

合于 11-01 14:50。被回退的 #3291 把精确线程计数移到满块栅栏检查之前，并加入矩形认证，代价是即使全部线程都到栅栏也要跑一遍 CountSatisfyingValues；TVM 侧求解预算耗尽后返回部分计数，remap 与 sequence 辅助 kernel 随即以「[ThreadSync] Cannot prove a thread rectangle」失败。回归在主线 cc903dcb9 加未改动的 TVM pin 4211874e9e 上复现，新用例把它缩成「循环对多数线程为空、256 线程仍全部到达栅栏」。回退同时覆盖共享与昇腾两套实现，恢复满块快速路径与旧的部分计数行为；原文明确这是 TIRX 迁移期间的临时缓解，TVM fork 侧的优化提案 tile-ai/tvm#89 已关闭，后续优化转入 #3732。

来源：https://github.com/tile-ai/tilelang/pull/3733

1.2 主线：CUDA 跨 warp 全归约合并为一次共享内存交换，256 线程从 6 道栅栏降到 2 道（#3715）

合于 10-30 20:26。旧实现在 CUDA 归约头文件 reduce.h 里从 threads/2 递归到 scale，凡是 offset 不小于 32 的每一步都做一次完整的共享内存写读交换并配两道栅栏：256 线程块的三步（128、64、32）合计 3 次共享内存往返、6 道栅栏，512 线程块是 4 次、8 道。改法是把所有跨 warp 步骤压成一次交换（每元素一次 st.shared、共 2 道栅栏）：先在 warp 内做 scale 小于 32 的那一段，再让每个 warp 内组里不超过 cross_radix 的若干 lane 协作折叠，寄存器压力有上界。标量与批量两条路径都改了。

来源：https://github.com/tile-ai/tilelang/pull/3715

1.3 主线：PTO 后端的 T.Parallel 向量化落地第一里程碑，逐元素算子走 VMI 指令（#3512）

合于 10-30 01:29。目标是让用户在 T.SimdVF(lanes=L) 里写标量并行的逐元素 T.Parallel，由编译器向量化成 PTO VMI 指令，再经 PTOAS 在昇腾 950 上执行。分工写得很清楚：TileLang 侧负责逻辑 lane 布局推导、向量化 pass 流水线、VMI 指令生成与 Fragment 逻辑映射；PTOAS 侧负责物理寄存器切分、掩码具体化、Fragment 缓冲与向量寄存器分配、mem_bar 插入。路线图分五个里程碑，本笔是 M1 核心框架（逐元素计算，覆盖 extent 能否被 lanes 整除两种情况），M2 控制流、M3 reduce、M4 UB 容量规划与寄存器分配、M5 非连续访问与更宽的 PACK 数据类型依次跟进。

来源：https://github.com/tile-ai/tilelang/pull/3512

1.4 主线：昇腾 DeepGEMM 的 scale 缓冲改用写计数多缓冲，数据加载可提到条件加载之前（#3629）

合于 10-30 05:48。DeepGEMM 会在多个 K 块之间复用 scale factor，本笔新增显式的写计数多缓冲模式，让 scale 缓冲的版本按真实写入推进：每个 owner 循环迭代里只在第一个实际执行的写任务处推进一次，后续写入共享该版本，没有写入的迭代沿用旧值，支持多个不相交 owner 与共享时钟。这样数据加载可以排到条件化的 scale 加载之前；同时把 DeepGEMM 的 K 循环摊平，在 L1 与 L0 上都先取数据再取 scale，并补了守卫更新、嵌套更新、保留读、flag 与缓冲复用以及 FP4 的 K 主序与 MN 主序带尾块和环形回绕的用例。该模式要求显式版本数，并假定每个 owner 迭代最多一次更新。

来源：https://github.com/tile-ai/tilelang/pull/3629

1.5 主线：两笔修复合入，CPU 标量 GEMM 只清目标区域、负索引合法化跳过不可达分支（#3709 / #3712）

两笔都在 10-30 合入，属上一期在审条目的落地。#3709 让 CPU 标量 GEMM 只清理目标区域，此前会连带清掉不属于本次输出的范围；#3712 让 LegalizeNegativeIndex 跳过不可达分支，避免对不会执行的代码做负索引改写。这两条与上一期报告的 #3708、#3710 属同一批缺陷清理，其中 #3708 的位宽改 int64、#3710 的关缓存时绕过两层进程内缓存仍在审。

来源：https://github.com/tile-ai/tilelang/pull/3709、https://github.com/tile-ai/tilelang/pull/3712

1.6 主线：语言层清掉 proxy 里两个无人使用的 Ref 占位（#3722）

合于 10-31 17:31。tilelang/language/proxy.py 里同时存在两个 Ref：一个给类型检查用的 tirx.Var 桩，一个空的运行时类，两者在树内都没有消费者；对外的 T.Ref 实际来自 eager.builder，那里的实现才是宏引用参数的本体。本笔删掉两个占位、_T 类型变量以及随之无用的 Generic、TypeVar 导入，保留 T.Ref 与宏引用行为，只移除 tilelang.language.proxy.Ref 这条无人使用的直接导入路径。前端构造测试 179 项通过、6 项跳过，运行时身份检查确认 T.Ref 仍是 eager.builder.Ref。

来源：https://github.com/tile-ai/tilelang/pull/3722

1.7 新开缺陷与在审：TMEM 静默丢结果、ROCm 符号找不到、TF32 就近偶数舍入（#3721 / #3711 / #3714）

#3721 是本窗口最值得警惕的一条：在 sm_100a 上对 TMEM 做 T.gemm，当 threads/32 不能整除 N 时，编译能过、PTX 里却一条 tcgen05.mma 都没有，T.copy(Ct, Cl) 读的是没人写过的 TMEM，乘积被静默丢弃；复现里 threads=256 出一条，threads=384 出零条，作者怀疑 src/cuda/op/gemm.cc 给 TCGEN05 返回 {1, num_warps} 分区时缺了覆盖性检查。#3711 报告 ROCm 7.14 与 10.0 的 PyTorch wheel 下 kernel 报「named symbol not found」。#3714 在审，为 fp32 到 tf32 的转换补上就近偶数舍入（cvt.rn.tf32.f32 与饱和形式），非饱和要求 SM90 以上、饱和要求 SM100 以上，关闭对应的功能请求 #3713。

来源：https://github.com/tile-ai/tilelang/issues/3721、https://github.com/tile-ai/tilelang/issues/3711、https://github.com/tile-ai/tilelang/pull/3714

二、多后端适配（昇腾 / 海光 / 摩尔线程 / 沐曦）

2.1 昇腾：Cython wrapper 惰性构造 TVM Analyzer，910B3 单次调用从约 450 微秒降到约 106 微秒（#1948）

合于 10-30 07:44。CythonKernelWrapper.forward() 此前每次调用都无条件构造一个 TVM Analyzer()，在 910B3 上是约 0.28 毫秒的固定宿主开销，而该对象只在 result 或 workspace 形状为符号表达式时才用到；静态 shape 的 kernel 完全用不上，却同样付这笔钱。改法是把构造延迟到 tir.PrimExpr 分支内并按需复用。实测：vec add 单块 442 至 467 微秒降到 105.1 微秒，32 块 441 至 493 微秒降到 108.0 微秒，kpool 压缩 447 至 450 微秒降到 111.3 微秒，裸 ctypes 调用约 12.5 微秒降到约 12 微秒。新增两例回归，分别验证静态路径不构造、符号路径按需构造。

来源：https://github.com/tile-ai/tilelang-ascend/pull/1948

2.2 昇腾：RFC 提出把同步实现换成主线核心加独立 Z3 证明服务（#1971）

本 RFC 不预设提速结论，只固定比较基线：Ascend 仓在 TileLang 43b0b69 与 TVM c2921fd 上、IR 基础是旧 tvm.tir；主线在 TileLang 1c0f402 与 TVM 4211874e9e 上、IR 基础已是 tvm.tirx 与 tvm.s_tir，对象与注册体系也换成新 FFI 与反射设施。因此迁移不能简化为复制一个 InsertSync 文件。建议路线是移植主线同步核心与独立 Z3 证明服务，通过旧 TIR 适配层接入现有编译流水，保留现有 TVM、调度、内存规划、AscendC/PTO codegen 与运行 ABI，完成支持范围、正确性、性能与安装验收后再切换默认实现并删除旧同步算法。配套 PR 为 #1965。

来源：https://github.com/tile-ai/tilelang-ascend/issues/1971

2.3 昇腾在审：把 TileLang-Ascend 整体迁到主线多后端架构（#1975）

10-31 提出并持续更新，目标是按提案 #1911 把 TileLang-Ascend 迁移到 TileLang 主线的多后端架构上；描述里给出两份差异对照，一份对 ascendc_pto 分支，一份对主线。这条与 2.2 的 RFC 是同一条收敛路径的两个层面：一条改同步算法，一条改仓的骨架。

来源：https://github.com/tile-ai/tilelang-ascend/pull/1975

2.4 昇腾在审：GLM-5.3 kpool 的 fp8_mqa_logits 示例，双 kernel 加 AIV/Cube 分工（#1966）

对照主仓 kpool 目录下的 GLM-5.3 fp8_mqa_logits 示例做昇腾版。算子语义是 GLM-5.3-Flash 稀疏注意力 indexer 的池化历史打分：对每个 query 行，在有效 pool 区间内按分页表从 64-pool 页读 E4M3 key（uint8 承载字节加 fp32 scale），反量化后算 32 个 indexer 头的 MQA 打分，乘 per-pool scale，经 ReLU gate 与按头加权归约为每个 pool 一个 FP32 logit，范围外或无效页输出负无穷。实现是双 kernel：mask kernel 按 64-pool tile 生成逐 lane 的 0 或负无穷掩码以替换宿主预填，main kernel 每行每页一个 block、两个 AIV 各处理 32-pool 半页，Cube 读整页做一次 64×32×128 的 GEMM。头数 32、维度 128、页大小 64。

3.6 TileOPs 在修缺陷：Norm 四算子在远离零的行丢精度、约 1e36 溢出成 NaN（#2812）

11-01 新开。LayerNorm、AdaLayerNorm（含 -Zero）、GroupNorm 与 BatchNorm 目前都用原始行的 fp32 直接求和取均值与方差（BatchNorm 用 E[x²] 减均值平方），这正是 #2773 为 FusedAddLayerNorm 修过、#2811 为 InstanceNorm 训练核在修的同一类缺陷。表现是：常数 10000.1 的 fp32 行归一化后输出约等于正负 weight 而不是 bias，10000 加随机数的行在 fp32 容差下对不上 float64 参考；接近 1e36 的行求和溢出，fp32 与 bf16 下全部输出 NaN。受影响路径覆盖 fragment、共享内存走查、一行一 warp、分块与流式等多种实现。

4.1 RISC-V 研究链成形：三个仓把 Numba CUDA Python 转 TileLang，再把受限 PrimFunc 落到单 hart RVV C（10-31）

五、趋势观察

这一窗口最值得记录的判断来自上游自己：宁可回退正确性改进，也要把 ThreadSync 的复杂度从关键路径上撤下来。回退说明里写清了代价——商守卫、精确参与线程界、非矩形线程集这三类改进一并撤回，只保留旧的保守路径，#3732 留待 TIRX 迁移完成后再谈优化。一个编译器项目愿意公开写「我们的证明器预算不够，先退回保守实现」，比再堆多少功能都更能说明当前阶段的真实约束：TIRX 迁移是主线第一优先级，其他优化都要给它让路。

与之呼应的是昇腾侧两份「向主线收敛」的文本：#1971 的 RFC 要把同步算法换成主线核心加独立 Z3 证明服务，先调研、后替换、中间留旧 TIR 适配层；#1975 直接把整个 Ascend 仓迁到主线多后端架构。两条路都要付出迁移成本，于是近期的可见工作会偏向地基类：#1948 把每次调用的固定宿主开销从约 450 微秒压到约 106 微秒，四笔文档事实核查，CI 清理内部缓存引用，都是这类工作。

TileOPs 的节奏则从「发版」切到「调优」。72 小时 15 笔合入里 13 笔压在同一天，几乎每笔都附 H200 实测表与「manifest 无回退」声明，并且开始用选择遗憾这类指标描述调度规则的好坏（#2808 从 1.818 到 1.017）。这意味着算子库的竞争点已经从「有没有这个算子」变成「每条 shape 上是否都挑对了程序」，而这恰好是 TileLang 这类 DSL 相对手写 kernel 的长期价值所在。

生态侧出现两条新分叉。一条是硬件方言：海光把 gfx948 当 gfx946 兼容、昇腾继续补 PTO 文档与符号形状。另一条是语言出口：RISC-V 研究链把受限 PrimFunc 降到单 hart RVV C，星标很低、作者也明确声明不是官方后端，但它把 TileLang 的 IR 当作可移植资产来用，与昇腾、海光的仓级分支适配是同一类信号。多条分叉同时存在，上游 TIRX 迁移能否给出稳定的 IR 边界，将决定这些下游投入是沉淀还是返工。
