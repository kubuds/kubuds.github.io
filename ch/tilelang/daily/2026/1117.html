一、核心项目进展

1.1 主仓四笔 bugfix 合入：JIT 设备还原、NVRTC 单参数、cython 动态共享内存、ROCm HIP 运行时复用

主仓窗口内合入四笔，全部是运行时缺陷而非新特性。#3872 修 tvm_ffi 宿主 stub 只设当前设备、不还原的问题：在 cuda:0 上调用 cuda:1 的张量，结果正确但当前设备被留在 cuda:1，后续 device="cuda" 的分配会静默漂移；修法是在适配器层用 torch.cuda.device(...) 包住调用并在结束时还原。#3880 修 NVRTC 后端单参数内核无法启动：参数名与类型用 ", " 拼接后，单参数时拼出的不是元组，cuLaunchKernelEx 直接抛 TypeError；改为带尾逗号的元组字面量。#3882 修 cython 后端动态共享内存上限只在 init() 里设一次的问题——该属性是逐设备的，需要超过 48 KB 的内核在其余设备上会报 cudaErrorInvalidValue；改为每个内核生成 _set_dynamic_smem() 帮助函数并记录已提升的设备。#3899 修 ROCm 下 HIP stub 找不到 PyTorch 自带 libamdhip64 的问题：PyTorch 的 ROCm wheel 用 RTLD_LOCAL 加载，stub 先用 RTLD_NOLOAD 探测已映射的运行时，避免 dlopen 出第二份运行时后模块句柄跨运行时、首个 kernel 启动失败。

来源：https://github.com/tile-ai/tilelang/pull/3872 、https://github.com/tile-ai/tilelang/pull/3882 、https://github.com/tile-ai/tilelang/pull/3899

1.2 manifest 升级为声明式参数类型，pilot 模型接口一次补齐

#2958 把 manifest 从「只能描述固定张量与标量」扩展到能声明张量序列（torch.cat）、标量或张量二选一（flash_attn 的 seqlen_offsets、torch.clamp(min)）、必填但可为 None（mamba_ssm 的 bias）三类签名，并把调用期输入统一改成带 type 与 default 的声明；原先为「标量或张量」拆出的三组 Scalar/Tensor 算子对随之合并。#2967 在此之上补齐 pilot 模型的接口真值：七个新登记为 spec-only 的条目（含 torch 参考实现），十五个已实现条目补上 pilot 模型实际传入的参数与输入，内核遇到非默认值以 OpNotAvailableError 拒绝，条目状态仍保持 implemented，基准行遇到该错误按「不可用」记录而不是判失败。

来源：https://github.com/tile-ai/TileOPs/pull/2958 、https://github.com/tile-ai/TileOPs/pull/2967

1.3 三个新算子：门控 RMSNorm 与 MaskedScatter 落地，Embedding 合入当日回退

#2984 新增 RMSNormGatedFwdOp：按最后一轴分组做 RMSNorm，可由 silu(z) 或 sigmoid(z) 在归一化之前或之后门控，全程 float32 计算、只舍入一次；一个 TileLang 内核覆盖所有调用形态（8 条 lane、每条两次 16 字节访问构成 128 宽行，16 行组成 128 线程的 CTA，更宽的组把 lane 翻倍到 1024 并跨 warp 用共享内存求和），寄存器上限定在每线程 64，门控的指数与倒数各用一条指令。基准对齐 vLLM 的 RMSNormGated、mamba_ssm 的 rmsnorm_fn、fla 的 rms_norm_gated、Hugging Face 的 Qwen3_5RMSNormGated 以及 torch 参考与 torch.compile，达到验收线。#2982 新增 MaskedScatterFwdOp（out-of-place 版 masked_scatter，支持 fp16/bf16/fp32 与 input、mask 广播）：每个 CTA 领一段完整的 mask 连续段（行数以 32 KB 为界），先数清本段之前的真值段再扫描自身，每 16 字节向量只读一次（真值段读 source、假值段读 input），段字节超过四块时先做一次分块计数；对照 torch eager 与 torch.compile 达线，vLLM 的原地多模态合并因语义不同列为不可比。

同日另有反复：#2977 合入 EmbeddingFwdOp 后，#2983 在当天把它整体回退，理由是该 PR 属误合，新算子应走单独的 TileFoundry 轮次；回退后该条目回到 spec-only，内核、算子、基准、测试与工作负载一并移除。#2975 仍在审，是同一算子的正式提案（按 token 索引 gather 权重行）。

来源：https://github.com/tile-ai/TileOPs/pull/2984 、https://github.com/tile-ai/TileOPs/pull/2982 、https://github.com/tile-ai/TileOPs/pull/2983

1.4 GEMM 三条量化线：INT8 W8A8 改 192 宽 ping-pong，W4A8/W4A16 stream-K 各自收尾

#2959 让 INT8 ping-pong GEMM 在「最忙 CTA 的列数不多于 128×128 瓦片」时改用 128×192 瓦片，网格末尾按 bf16 GEMM 的窄瓦片规则收成整 32 列的存储盒（在本期 manifest 的每条 prefill 行上都是 160 宽），每种宽度发一条对应宽度的 WGMMA；同等最忙 CTA 工作量下，192 宽瓦片每 MAC 搬运的 TMA 与 WGMMA 共享内存字节更少、CTA 切换消费者的次数少三分之一，llama3-8b prefill-qkv 最后一波最忙 CTA 的列数由 1536 降到 1504。#2960 改 W4A8 prefill 的 stream-K 收尾：当其余部分分块都已落盘时，偏晚到达的 0 号贡献者不再写自己那份部分和，改由计数凑满该瓦片的贡献者收尾，每 CTA 只用一条 acquire-release 原子（放在命名屏障之后）替代每个线程的 fence，无 CTA 互相等待；只有含 stream-K 瓦片的程序走新路径，其余编译结果与主分支一致。#2964 修 W4A16 stream-K 的错位：内核原本用 cta == first_cta 保护「补齐未使用槽位并做 ceil 除法」的逻辑，TileLang 的化简在 CTA 的第二段之后把它整段丢掉、在第一段之后把它折叠，导致两个 CTA 共用的瓦片留下未写槽位、归约读到脏内存，最大误差从 2.4 到无穷；改为在构建该程序的设备上由宿主一次性建表，按「瓦片内第几个 CTA」定位槽位。

量化 GEMM 的覆盖面同步补：#2969 新增 42 条 W4A16 行、13 条 W4A8 行与 11 条 FP8 行，每行对应 Llama-3 8B/70B、Qwen3 8B/32B 或 DeepSeek-V3 的一个真实投影（TP1 或 TP8、解码批），此前 W4A16 的基准行只覆盖 45 个解码调度区中的 3 个。另有一笔在审的 #2990（W4A16 解码瓦片配对条件收紧），起因是 issue #2966 记录的同批改动在部分 8 行与 16 行形状上比改动前更慢。

来源：https://github.com/tile-ai/TileOPs/pull/2959 、https://github.com/tile-ai/TileOPs/pull/2964 、https://github.com/tile-ai/TileOPs/pull/2969

1.5 注意力与线性注意力：paged GQA 校准续篇、DeltaNet 启动配置、GLA 反向共享内存

#2956 续 paged GQA 的校准：拆分的归约改为按 split 为主序存权重表、每个行块一个 CTA，并读扫描生成的请求映射（原先按行并行写 [block_M, num_split] 表，在 16 与 32 路拆分时串行化）；GQAPagedFwdKernel.default_config 只在打包后的行真正填满时才用 128 行查询瓦片（48 行页会让关键瓦片窄于一条 WGMMA，解码打包反被撑到 128 行）；左窗口情形下 RoPE 预处理也改为按窗内范围准备。#2978 让 WS 内核接手「窗口覆盖整张页表、不会隐藏任何 key」的情形：此前 WS 内核拒绝一切不带 RoPE 的窗口，window4096/long-b1-q2048-kv2048 因此落到 cp.async 内核，耗时是 FA3 的 2.17 倍；该 PR 自评仍低于验收线（below bar），属改善而非达标。

线性注意力侧，#2979 修 DeltaNetChunkFwdOp 在 chunk_size=16 下的启动配置（准备与输出最多两条 warp，奇数 V/8 只允许一条，递归列的 warp 数必须整除 8 列瓦片数），#2980 把 chunk 启动上限改为从每个 GEMM 的 warp 瓦片推导，修掉 chunk 32/64/128 下一批「TileLang warp 划分失败」的形状（此前只对 chunk 16 特判），并让不合规的 chunk_size/dim_k/dim_v 在构建期被拒绝而不是随机失败。#2965 在 SM89 上把 GLA 反向的共享内存生命周期压回 99 KiB 预算内（重算门控因子、重载状态梯度），恢复四个此前超限的 dtype/形状组合（FP32 的 32×64×192、32×32×256 与 FP16/BF16 的 32×128×128），仍有三组保持拒绝。#2976 把两条 DeltaNet 计时用例标为 SM90，避免在 SM89 上先构建仅 SM90 可用的解码 warp 内核。

来源：https://github.com/tile-ai/TileOPs/pull/2956 、https://github.com/tile-ai/TileOPs/pull/2978 、https://github.com/tile-ai/TileOPs/pull/2980

1.6 测试与基准：GDN 扫描裁到每个调度区一行，fp8 用例回归各自目标

#2981 把 GDNFwdOp 的工作负载从 151 行 283 例裁到「每个调度区留一行」：规则是每个 bf16 组（内核身份、形状区间、H200/SM89 调度区）保留首行，fp16 只在每个调度区首次出现的那一行保留，q35-gva-decode-b1 与 q35-gva-decode-b8 各留一行。#2991 修 tileops_test 的设备判定：_Reference._device() 原先从标量上读 .device，而 #2958 之后内核按位置接收调用期标量，导致 nightly off-cuda-suite 在 a0b7aeb6 上出现 61 个失败；同时把三条 fp8 用例标回 in_tree_kernels，因为它们检查的是树内内核的拒绝行为，而 tileops_test 目标一律走参考实现。

来源：https://github.com/tile-ai/TileOPs/pull/2981 、https://github.com/tile-ai/TileOPs/pull/2991

3.1 TileFoundry 验证器重构为单一 ctx 遍历器，同步补共享内存写冲突分析

#336 把 TIR 验证器原先各自一套的遍历器（walk_stmt、Binders、iter_all_stmts、独立的 interfaces/verify visitor 与 mesh_scope 栈）合并到 StmtExprVisitor：可携带可选的 ctx，先按边界顺序访问语句内的表达式再访问子语句，分析不再按结构哈希索引 Call 映射。该 PR 同时交代了一个警示：FSDP 训练示例在 #325 与 #293 之后已经无法构建，而没有测试捕获到这一点。#326 补上共享内存写冲突分析：cuda/analysis/threads.py 把每个共享内存写与自身跨线程配对，只要某个 layout 能把每个字节唯一分配给发起的线程、或关系证明两个线程不会碰到同一字节，才放行；此前「每个线程都向整块共享内存瓦片发起同一次动作」会被接受，而下降阶段为填充与拷贝生成的正是这类写。

来源：https://github.com/tile-ai/TileFoundry/pull/336 、https://github.com/tile-ai/TileFoundry/pull/326

3.2 TileFoundry 单日新开 11 条 issue，集中在代价模型与调度器补洞

五、趋势观察

  • 算子库已成主战场：本期 30 笔合入里，TileOPs 占 18 笔，主仓只有 4 笔运行时 bugfix；社区的工作重心从编译器本体转向算子实现与接口真值。
  • 接口先于实现：manifest 的参数类型、pilot 模型接口在同一天补齐，随后新算子按轮次逐个落地，Embedding 的误合与当日回退说明流程正在收紧，而非放松。
  • 流程工具化：topa 的 new-op 轮次、状态机与 issue 路由，配合 TileFoundry 的代价模型补洞，构成「算子需求 → 调度可行性 → 实现与验收」的闭环，这一层是过去两周增长最快的部分。
  • 性能修复开始反噬：W4A16 配对瓦片在部分小形状上出现回退（issue #2966），量化 GEMM 的优化已进入「必须按形状分档」的阶段，单一瓦片策略很难再普遍获益。
  • 安全边界需补：自建 CI 被外部 PR 穿透、个人 token 被盗用的事件提示，新贡献者 PR 的 CI 触发权限应当默认需要维护者批准，这一条对整个 RISC-V 与 AI 编译社区同样适用。
  • RISC-V 侧节奏平稳：本期只有 MLIR 路线一笔合入（buddy-opt 默认化与示例补齐），TVM 路线与算能 TPU 侧无动作，属正常的交替推进。
