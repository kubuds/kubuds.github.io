今日重点：FlashQLA v0.1.4 发布，双卡 CP 扩到消费级 Blackwell

QwenLM/FlashQLA 于 11-25 23:16 发布 v0.1.4，仓库现有 770 星。这是采用方一侧本窗口最完整的一次版本交付。

发布说明列了三条主线。第一条是跨分区修正的精度路径，支持 FP32 与三遍 TF32x3，由运行时按 wave 感知的启发式选择。卡间 h0 与 dht 折叠改为经槽位映射直接读已汇聚的 (h, M) 缓冲，不再物化解包与重索引。

第二条是 SM120 与 SM121 上的双卡 CP，前向与反向都覆盖卡间加卡内组合。实现通过新增 aggregate_card_state 与 aggregate_m 完成。

第三条是 ZigZag 卡间 CP 布局。第 r 个 rank 负责每篇文档的第 r 块与第 2·cp−1−r 块，与注意力层的切分位置对齐，且不要求改动 TileLang kernel。

其余改动偏工程。KKT 求解改成 8×8 对角块代入，合并 FP16 MMA 与 FP32 递推，按 FlashInfer 的块状求逆独立重写。flash_qla.warmup() 可把全部静态参数组合预编译进 JIT 缓存。CP 接口 build_cp_context 默认开启卡间与卡内，并接受 zigzag=。

修复项里有一条与上一期日报的 SM120 线索相接。block_DV=64 与一处 __threadfence_block 阻止 nvcc 把 g_exp_shared 提升到屏障之外。反向屏障现在先提交 dV 写入，再让 K 复用 dqkv_shared。

基准覆盖三档硬件。单卡为 H200、GB200 与 RTX 5090。双卡 CP 为 H200×8、GB200×4 与 RTX 5090×2。发布另附 Auto-CP 与 Dual-CP 的技术报告。

来源： https://github.com/QwenLM/FlashQLA/releases/tag/v0.1.4。

今日重点：主仓三笔全在缓存子系统，缓存键纳入工具链版本

主仓窗口内只有三笔提交，两笔直接改缓存。这与前几日 ROCm 批量修复、昇腾缺陷报告形成明显分工。

#4511 把当前 CUDA 与昇腾工具链版本纳入 kernel 缓存键，改 20 个文件。新增 tilelang/contrib/bisheng.py，pto_toolchain.py 相应瘦身。BackendModule 增加 toolchain_stamp 回调，允许零参数调用。CUDA 编译器选择折叠进 _cuda_compiler_module。

改动动机是缓存失效边界。此前换编译器或换 CANN 版本后，旧二进制仍可能命中缓存。测试侧同步补了昇腾二进制缓存、PTO 缓存与 JIT 诊断三处用例。

#3756 处理共享缓存的权限。缓存条目先暂存再整目录改名发布，因此沿用创建进程的 umask。在 SGID 加组可写的共享缓存根上，umask 077 的进程会发出 0700 与 0600 的条目，其他用户读不到。

修法是发布前legalize暂存条目。缓存根带 SGID 时目录改为 0o2755，文件改为 0o644 并保留可执行位。不带 SGID 的根，以及不支持该位的文件系统，保持原样。该笔新增 148 行权限回归测试，并修了共享缓存目录初始化与多根查找。

配套还有一笔在审。#4512 题为按工具链身份给可执行缓存做键，与 #4511 属同一主题。

来源： https://github.com/tile-ai/tilelang/pull/4511。

一、核心项目进展

1.1 缓存键纳入 CUDA 与昇腾工具链版本，跨工具链复用被切断

#4511 由 LeiWang1999 于 23:09 合入，是本期唯一的功能性改动。提案说明分四步走：先按活跃工具链给 CUDA 与昇腾 JIT kernel 做键，再把工具链感知限制在 CUDA，随后把昇腾工具链也纳入，最后统一各后端的工具链印记。

结构上新增 BackendModule.toolchain_stamp 钩子。CUDA 侧由 tilelang/cuda/backend.py 提供版本串，昇腾侧由 tilelang/ascend/backend.py 提供。两者都改走 contrib 下的适配层。

测试侧改了六个文件。除三类缓存用例，还调整了 host-mapped 输出校验测试，该测试显式关掉 kernel 缓存。

来源： https://github.com/tile-ai/tilelang/pull/4511。

1.2 共享缓存按 SGID 发布组可读条目，umask 077 不再产出私有目录

#3756 由 KellyFrog 于 16:18 合入，改 kernel_cache.py 与一个新测试文件。提案把问题归因到发布方式：暂存后整目录改名，权限来自 umask，与共享根的 SGID 意图不一致。

判定条件只看缓存根是否带 SGID。带则目录 0o2755，文件 0o644，可执行位保留。不带则不动，覆盖 Windows 等不支持该位的文件系统。

测试覆盖共享根与私有根两种情形。非 POSIX 系统与不支持 POSIX 权限的文件系统会跳过。

来源： https://github.com/tile-ai/tilelang/pull/3756。

#4485 把 block causal attention 的样例用例改成并行跑，并给 Z3 加预算。改 3 个文件，含 ci.yml 一行。

提案中途撤过一次 DeepSeek TopK 的 Z3 预算覆盖，随后恢复 z3 限额。前一日的 #4463 与 #4489 也围绕同一组 TopK 用例的求解器耗时，本期这笔属测试时长的收尾。

来源： https://github.com/tile-ai/tilelang/pull/4485。

三、生态与采用方（TileOPs 算子库 / FlashQLA / TileFoundry）

3.1 TileOPs 九笔，DeepSeek-V4-Flash 两条模型级性能

TileOPs 窗口内 9 笔合入，两笔直接改模型侧调用方式。

#3171 把 DeepSeek-V4-Flash 的 indexer ReLU 改成非原地。ReLUFwdOp(inplace=True) 会把结果写进新缓冲再拷回输入，而该模型只读返回的分数。这次拷贝回写在 4096 token 预填、ratio-4 层上涉及 537 MB 分数的多一次读写。

#3170 让四类索引张量每个 Step 只算一次，由第一个读它的层负责。四类分别是 top-k 读取的 closed-entry 计数与零首项、全 closed 层的整份 key index、以及解码步的 ring 槽位。窗口类型为 int32，索引层不再逐层重算。

来源： https://github.com/tile-ai/TileOPs/pull/3171。

3.2 解码步改由 CUDA graph 重放，昨日工作项当日落地

#3168 于 15:00 合入，改 10 个文件。CausalLM.forward 现在同时服务两个模型：模型提供本次调用的索引元数据与转发主体。

cuda_graph 默认开启。解码步在 CUDA 设备上重放 _run 的图，token 缓冲与 Step.moved_to 原地改写。每个相位的首步先急切执行，再在模型自己的流上捕获。

这条正是上一期新开工作项 #3155 的实现。配套在审的 #3175 要求两个模型的每个解码算子都通过 CUDA Graph 捕获资格测试。

来源： https://github.com/tile-ai/TileOPs/pull/3168。

3.3 foundry 五笔：INT8 tile 扩到 192 宽，量化与采样各修一处空转

五笔以 foundry 为前缀，都属算子级调优。

#3162 给 INT8 64 行 GEMM 的 tile 表加 80、112、192 三档。192 宽走 T.wgmma_gemm 而非 dense WGMMA helper。48、144、176、208、224、240 仍排除，实测每次选中都更慢。

#3163 让 FP8 原地分组量化的末块只加载实际存在的行。单块启动时，例如 DeepSeek-V4-Flash 一行七组的 KV，冗余加载会让 kernel 多花 64 至 96 纳秒。

#3164 把 16 位 concat 输入经共享内存展宽到 float32，用 16 字节读与整行写。#3166 把拆分的 top-p 行分箱折叠到块内每个线程。#3167 让 16 位 isinf 一次处理两个 lane，块大小 1024 线程。

#3169 另修 RoPE 参考实现里零 token 的头数计算。

五、趋势观察

  • 缓存正从实现细节变成一等公民。一天之内三笔围绕它：缓存键认工具链、共享缓存认权限、在审那笔按工具链身份给可执行缓存做键。多用户构建与多工具链并存是驱动因素。

  • 0.1.16 的发布路径已铺到构建侧。夜间轮子先改标 0.1.16，标签与 PyPI 仍停在 0.1.15。版本串去掉 backend 标签后，两处依赖旧格式的代码当天就报了回归，说明格式变更的兼容面比预期宽。

  • 昇腾的缺陷构成在变。前一日是十个「不该接受的输入被接受」，本期是 T.fmod 缺下降、SimtVF 作用域误判、PTODSL 多 kernel 符号冲突。问题从接口契约下沉到编译与链接层，单条修复成本上升。

  • TileOPs 的优化开始落到模型调用方式，而不只是 kernel 内部。ReLU 换非原地、索引张量每步只算一次、解码步整体走 CUDA graph，三者都在减少调度与拷贝，而非提升单核算力。

  • 采用方节奏在加快。FlashQLA 一天内完成 v0.1.4 的代码、基准、文档与技术报告，TileFoundry 把验证面推到训练步级。TileLang 的下游不再只写 kernel，也开始写系统级示例。

  • RISC-V 侧连续三个窗口零变化。TVM 路线与 MLIR 路线都停在原位，索引页也没有新 PR。
