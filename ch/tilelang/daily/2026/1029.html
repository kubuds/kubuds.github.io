今日重点

今天窗口的重心在昇腾侧。tilelang-mlir-ascend 把 Ascend 910（A2/A3）的 NPUIR 后端整条并入主干，一笔 55 文件、21490 行新增：Python 侧是 tilelang/ascend910 包（backend / adapter / codegen / compiler / execution_backend / jit / pipeline / runtime / target 加 language 下的 kernel、copy、gemm、npuir 方言面），C++ 侧是 src/ascend910/target 下的开发者与专家两套发射器、op 层与 LowerNpuirBlock、NpuLoopVectorize、RewriteFDivToMul 三个 pass，运行时补了 npu_launcher.h 与 npu_utils，安装走 install_npuir.sh，target 别名接受 ascend910 / ascend-910 / a2 / a3 / npuir。作者给出的验收是仓库自带的两套用例：pytest testing/npuir 504 项全通过、examples 72 例中 71 例通过且 0 超时 0 报错，唯一失败的 deepseek_v32/fp8_lighting_indexer.py 在旧后端上同机同样失败，属环境与容差问题。第二笔提交是逐条对齐旧后端的行为差异，重点在 bf16 合法化（HIVM 不接受 bf16 操作数，改为 fp32 计算后显式转换）与动态 extent 的拷贝下沉。

TileOPs 今天合入七笔，两条主线都在性能侧。选择器不再贴着 manifest 拟合，改为在忙时（device_busy_ms）上按 160 个稠密 shape、60 个 m 9–32 的 shape、264 个 m≤8 的 shape 重新标定，用 softmin 期望对数遗憾做坐标下降；端到端忙时遗憾在留出的 manifest 上从 5.79% 降到 0.48%，m≤8 的留出集从 14.18% 降到 1.79%。GEMM 侧新增 coop2_swap：把非 NT 布局换成转置的持久内核，两个消费者 warpgroup 各持 128 行，尾写经 stmatrix.trans 与 TMA 转置落回，并支持宽窄 tile 混排（例如 2112 = 13×160 + 32 拆成 160 宽 tile 加 128 窄 tile），2112×7168×4096 TN 从 195.3 微秒降到 175.3 微秒，同机上另一块 H200 读到 174.3 降到 158.5 微秒，均压过 QuACK 的 187.9 与 167.0 微秒。

归约侧则同日先坏后修。上午 #2787 用 int32 键实现 extrema 归约的 NaN 传播、#2788 改并行 cumsum 的行 tile，两笔都在 07 时前后落地，随后 #2790 与 #2792 分别把两个回归收掉：cumsum 改成按种子分段、两次发射（(8,65536) float32 从 12.75 微秒降到 5.18 微秒，同时修掉主干的 65535 tile 以上发射失败），extrema 改用 PTX 的 max.NaN / min.NaN 并在非整 16 字节向量的行上走单独内核（amax (2048,4096) bf16 从 8.352 微秒回到 6.976 微秒，快于 FlagGems）。这类”同一天内引入再修掉”的节奏说明 TileOPs 的夜间基准已经把回归拦在了当天。

一、核心项目进展

1.1 主仓：标量读的索引系数不再混进 lane 数，行宽 32768 以上的编译崩溃关闭（#3453）

合于 10-28 11:06，单文件 +8/-5。一个用向量化方式读整行、同时又按下标读该行单个元素的 kernel，在行宽对 65536 取模后不小于 32768 时编译报 InternalError: Can’t fetch the lanes of a scalable vector。根因在 VectorTypeAccessChecker::OnArrayAccess：它把标量读记为 access_dtype.with_lanes(me->coeff)，而 me->coeff 是读下标的模系数，对 x[row, 0] 就是行宽；DataType 的 lane 数只有 16 位并按 int16 读回，32768 到 65535 因此被当成可伸缩向量，lanes() 在 get_preferred_dtype 里直接抛错，更宽的倍数则静默回绕。修法是把系数单独存进 int64_t，兼容性判断改用它取模，标量读的 dtype 只保留元素类型。这个缺陷的原始触发场景是 TileOPs 的 GroupNorm：Stable Diffusion 的 40960 与 163840 两个组宽都会踩到。验证用两次 wheel 构建对比：主干在 32768 与 40960 两个宽度上编译失败，本笔在所有测试宽度上都能构建。

来源：https://github.com/tile-ai/tilelang/pull/3453

1.2 主仓：批量 all-reduce 按标量分支解析线程区间，batch>1 时 2048 个输出全错的问题修复（#3341）

合于 10-28 05:46，2 文件 +170/-8。标量 all-reduce 分支在发射调用前会先把参与线程的区间解析出来（reducing_threads 大于 32 且目标支持命名栅栏时走 ResolveAllReduceThreadRange），批量分支却直接取块边界当偏移与栅栏宽度。当归约线程是 [32, 96) 这种不从 0 开始的局部区间时，批量调用从 0 号线程索引、按整块等栅栏，非参与线程未初始化的寄存器被折进归约：batch=1 正确，batch=2 在同一 kernel 上 2048 个输出元素全部错，最大绝对误差 1083，且没有任何诊断。修法是让批量分支与标量分支同一套解析，把解析出的偏移与范围传给 MakeBatchAllReduce，工作区 stride 仍保持块大小。新增测试在同一 kernel 上跑 batch=1 与 batch=2 并对 torch 参考比对。

来源：https://github.com/tile-ai/tilelang/pull/3341

1.3 主仓：SIMT 原子区域的形状校验补上，越界区域在编译期拒绝（#3465）

合于 10-28 08:14。SIMT 原子操作此前不校验传入区域的形状，形状不匹配的写法一路走到 codegen 才表现出错误结果或崩。本笔在 CUDA 与 ROCm 两条路径上补齐区域形状校验，把不合法区域提前到编译期拒绝。

来源：https://github.com/tile-ai/tilelang/pull/3465

1.4 主仓：稀疏 MMA 的 K 尾块不再被静默放过（#3367）

合于 10-28 16:01。稀疏 MMA 在 K 方向上有未处理的尾块时，此前不报错而是沿用整块的搬运与计算参数，数值静默偏差。本笔显式拒绝这类 K 尾块，把问题挪到编译期。

来源：https://github.com/tile-ai/tilelang/pull/3367

1.5 主仓：atomic_addx4 的目标 dtype 收窄到 float*（#3369）

合于 10-28 16:08，3 文件 +27/-9。CUDA 的 atomic_addx4 与 atomic_addx4_ret 通用实现此前接受任意目标指针，int32 或 int64 目标会落到 float 语义上算错。本笔把两个通用重载限制为 float* 目标，fp16 与 bf16 的既有特化不动；Python 侧 API 保持类型中立，CPU 后端的整数目标不受影响。CUDA 侧新增整数目标编译失败的回归用例，CPU C 后端新增两种整数宽度的累加正确性用例。

来源：https://github.com/tile-ai/tilelang/pull/3369

1.6 主仓：非 restrict 参数的 handle 后缀不再被裁掉（#3366）

合于 10-28 13:19。参数去重时按去掉 _handle 后缀的名字比较，导致同一个内核里 A 与 A_handle 两个不同参数被当成同一个，代码生成只发一份。修法改为按精确名加变量身份去重，并新增 CUDA 侧 A 与 A_handle 并存的回归用例。

来源：https://github.com/tile-ai/tilelang/pull/3366

1.7 主仓：TMA 描述符只记录已校验的名字（#3484）

合于 10-28 17:12。TMA 描述符的登记此前在校验之前完成，校验失败的描述符名留在表里，后续同名的合法描述符会被误判为重复。本笔把登记挪到校验之后。

来源：https://github.com/tile-ai/tilelang/pull/3484

1.8 主仓：profiler 输出索引统一校验，标量与列表形式同一套边界规则（#3486）

合于 10-28 19:24，2 文件 +15/-9，修 #2884。profiler 与 adapter 两侧此前对 result_idx 的处理不一致：标量形式做过边界检查、列表形式没有，负索引也未归一。本笔让 BaseKernelAdapter 与 Profiler 共用一套规则，接受 None、整数或整数列表，按 -len(params) 到 len(params)-1 判定，合法负索引归一、越界与非整数元素抛 ValueError。新增 28 项 CPU 侧回归覆盖标量与列表两种路径。

来源：https://github.com/tile-ai/tilelang/pull/3486

1.9 主仓：T.Parallel 的 coalesced_width 统一转 IntImm（#3374）

合于 10-28 16:27。coalesced_width 传 Python 整数时，部分路径直接以原生整数进入 pass，类型断言在后续变换里失败。本笔在语言层统一转成 IntImm，消除写法差异带来的失败。

来源：https://github.com/tile-ai/tilelang/pull/3374

1.10 主仓：测试基建把 cache 敏感用例改走 without_kernel_cache（#3695 / #3696）

合于 10-28 01:59 与 09:19。承接昨日记录的 issue #3694（内核缓存命中破坏假定冷编译的测试），两笔把检查编译产物、源码与诊断信息的用例改走 without_kernel_cache() 或显式 .compile(…)，让断言看到的是本次构建的结果而不是进程内缓存里的旧 kernel。

来源：https://github.com/tile-ai/tilelang/pull/3696

来源：https://github.com/tile-ai/tilelang/pull/3695

1.11 新增缺陷三条：SM120 上 13 个示例失败、IfStmtBinding 指数级编译、without_kernel_cache 不强制重编（#3701 / #3700 / #3699）

三条新开 issue 指向测试与编译时间。其一，#3701 在 RTX PRO 6000 Blackwell（sm_120，动态共享内存上限 99 KiB）上跑完整 examples 套件，CUDA 与 CuTeDSL 两个后端都是 13 失败 199 通过 27 跳过，失败集逐字相同：7 例是示例在非 –tune 路径上硬编码 Hopper 尺寸的 tile（如 attention_sink 要 163840 字节、deepseek_mla 解码要 231424 字节），4 例是参照实现 flash-attn 2.5.8 没有 sm_12x 内核，另两例分别是 ReduceOp 下沉与 ThreadSync 无法证明线程范围。其二，#3700 报告在循环里重复写 x = x + x 并加上 i < N 守卫时，tl.LayoutInference 从 0.087 秒涨到 118.5 秒，关掉 replayable bind 内联即退回 0.100 秒。其三，#3699 指出 without_kernel_cache() 只翻转 CacheState（只被磁盘缓存读取），而 @tilelang.jit 包装器在 JITImpl.compile() 之前还会查进程内的 _call_form_cache 与 _kernel_cache，因此该块内的一次普通调用并不保证重新编译。

五、趋势观察

昇腾侧的推进方式这两天已经很清楚：主仓按小时合入小修（缓存键、寄存器相位），专用仓 mlir-ascend 用一次两万行的合并把 910 的 NPUIR 路径从特性分支搬进主干，tilelang-ascend 则在 PTO 与 AscendC 双后端的既定节奏上做文档与算子补齐。三处节奏不同但指向同一件事：910 的编译器路径正在从”能跑”转向”可验收”，504 项自测与 71/72 示例就是这次给出的验收口径。值得注意的是在审队列里 a2a3 的调度器迁移占到了 100 文件，说明下一阶段的变动量在调度层而不在算子层。

性能侧的看点在测量口径本身。TileOPs 这两笔把选择器和 GEMM 的结论都挪到了忙时（device_busy_ms），并在同一份 PR 里给出单次调用与背靠背调用的差别：单次读法下本实现领先 QuACK，背靠背、功率封顶的训练场景里十条大行有六条落后。这是一个比”某行快了多少微秒”更重要的信号，因为训练实际就是背靠背。#2791 把这件事单独立项，说明团队已经把口径问题当成产品问题处理，而不是当作基准偏差粉饰过去。

工程卫生上今天有三条值得记：一是同一批内的自伤与自修（#2787/#2788 上午合入、#2790/#2792 下午收回归），说明夜间基准的兜底在起作用，但也说明归约这套代码的语义边界仍然脆；二是 without_kernel_cache() 的语义漏洞（#3699）被从迁移过程中揪出来，进程内两层缓存不吃 CacheState，测试自以为在冷编译其实拿的是旧 kernel，这类缺陷会让”我们的测试全过”失去意义；三是 SM120 上 13 个示例失败（#3701）暴露出示例硬编码 Hopper 尺寸的问题，Blackwell 装机量上来后这类”示例不是产品”的债务会被反复计入。
