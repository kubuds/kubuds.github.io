今日重点

这个窗口的主线是善后。主仓五笔合入（+1903/−617，22 处文件改动）没有一笔新增算子、没有一笔新后端，四笔都在收 #3512 那轮 PTO 向量化改造的尾巴：VMI 描述符在 typed view 的 gather/scatter 与单元素载入上取错，于是 #3894 一次改掉 6 个文件、+925/−550；分析式遍历把标量定义提前绑定，IntSet 在回绕 cast 上求值抛异常，于是 #3793 加了保护；车道布局推断把显式 SIMD 的向量块地址当成标量车道访问，老写法直接编译不过，于是 #3796 保留旧路径；codegen_pto 改成发 si32/si64 而 PTO 原子只认 signless，于是 #3792 在调用边界做局部重解释。这四笔的共同点是「改造之后原有的合法程序不再合法」，属于大改动的必然代价，但从 11-10 到 11-13 连续四个窗口都在付这笔账，说明 PTO 这条线的回归面比预估的宽。

第五笔 #3614 是另一种性质：它不是修 bug，而是防死锁。昇腾内核有两种调度模式，mode=0 是「有可用核就启动算子」，mode=1 是「等算子所需的全部核资源到位再整体启动」。做全核同步的算子如果在普通模式下启动，可能只拿到一部分核就先跑到全核屏障上等其余的核，而其余的核正被另一条流占着——资源成环，设备直接挂死。这笔改动在 codegen 侧识别出「带常量 0 的跨核同步」后自动置 __schedmode__(1)，并把该标志按函数重置以防泄漏到后续入口；同时把跨核 set/wait 接口里整数形态的 mode 收窄到 0/1/2/4，非整数不校验以保留符号量。回归文件 78 行，覆盖全 AIC、全 AIV、AIC+AIV 组合协议、三个局部模式与标志重置共七种情形。

ROCm 侧的动静比昇腾更值得记。窗口开始后不到一小时，同一账号连开七笔 PR，22 文件 +624/−19，全部基于 72d986e1，构成一套完整的 HIP 侧补丁：编译参数此前只进缓存键不进 hipcc（#3954）；8 位整型向量的 8/16 车道广播会发出 hipcc 拒收的 make_uint2/make_uint4（#3955）；小瓦片上的 T.gemm 报「Divide by zero」这类无用信息（#3956）；T.annotate_min_blocks_per_sm 在 HIP 上被丢弃，gfx90a 上一个 256×128×32 的 fp16 GEMM 因 143 个 VGPR 加 128 个 AGPR 被锁在一 CU 一块（#3957）；占用率与 scratch 用量只有原始数字没有换算（#3958）；wave64 上 64 线程的归约白分配了一块 LDS（#3959）；HIP 里 uint2/uint4 是结构体，跨循环驻留的 fp16 片段被 SROA 打回栈上，每 lane 吃掉 80 字节 scratch（#3960）。ROCm 此前在本日报的记录里长期是「偶有一笔」，一天之内成系列出现，是本期最明显的结构性变化。

第三件事在 mlir-ascend 的 harness 分支上，三笔合入合计 +7632/−24、64 处文件改动，全部不落 main 也不落 master。内容不是编译器功能，而是「写给要写算子的人（或 agent）的知识库」：#220 补 Ascend950 的仿真 trace 工作流（msprof 采集、MindStudio Insight 查看、用同一次运行的 dump 补 GET/RLS 事件、导出 npusim SQLite 供时间线分析，38 项既有测试在 WSL 上全过）；#221 是算子设计指南的可安装版本（阶段分解、SIMD/SIMT 选择、存储预算、瓦片流水，外加 Cube MFU 与条件 Roofline 计算器，并把上游九份 TileLang Skill 资料另存快照以便离线读）；#226 补 BMM 与 w4a8 的 Gemm 量化示例，同批还进了一个 conv 示例。这条线的价值不在编译能力，而在于把「怎么在这块硬件上把算子写对、算清 MFU」变成可分发的东西。

一、核心项目进展

1.1 昇腾：跨核同步 mode=0 强制 batch 调度，全核屏障不再与多流抢核死锁（#3614）

这笔改动 5 个文件、+102/−1，其中 78 行是新增的回归文件（test_ascend_schedmode.py，位于 testing/ascend/target/ 下），真正的编译器改动只有二十余行：在 Ascend codegen 里识别出「带常量 0 的跨核同步」后置 __schedmode__(1)，并把这个标志做成按函数重置的成员，避免泄漏到后续入口。

要看清它的必要性得回到调度语义。昇腾内核的 mode=0 是普通模式——只要算子所需的部分核资源可用就启动，不同流的算子可以重叠；mode=1 是批模式——等算子所需的全部核资源到位再整体启动。做全核同步的算子（全 AIC 同步、全 AIV 同步，以及「AIV 与本地 AIC 同步 → 全部 AIC 同步 → 再同步回本地 AIV」的组合协议，其内部含一个 mode=0 阶段）在普通模式下启动时，可能只拿到部分核就先跑到全核屏障上等待，而它等的那些核正被另一条流占着且不会释放，资源成环，设备死锁。批模式消除的就是这个窗口。

顺带做了接口收窄：跨核 set/wait 接口里整数形态的 mode_id 只接受 0、1、2、4，其余整数直接拒；非整数不校验，以保留符号量传参的可能。文档串也补了一句实情——同一份 API 文档列出的模式在三个目标上并不一致：910B/910C 支持 0/1/2，950 才多出 4。回归覆盖七种情形：全 AIC、全 AIV、AIC+AIV 组合各自应开批模式，mode=1/2/4 应保持默认，以及标志在函数之间不残留。

来源：https://github.com/tile-ai/tilelang/pull/3614

1.2 昇腾 PTO：VMI 描述符与逻辑覆盖校验一并收口，单笔 +925/−550 为本期最大（#3894）

#3894 是本窗口最大的一笔（6 个文件，+925/−550），把两件独立的事放在一个分支里。第一件是修 VMI 内存描述符，涉及两类形态：typed view 的 gather/scatter，以及单元素载入——两者在构造描述符时取的基址与步长与实际访问不一致。第二件是把 VMI 前端冗余的逻辑覆盖拒绝删掉。

第二件事的前提值得写清：删校验不是放松，而是因为共享内存检测器的修复（#3805）已经落地，前端再拦一遍属于重复拦截，且会误伤跨行、转置与动态视图这些本该放行的形态。换句话说，同一处语义在两个层次上各做了一次判断，先落地的那个修好之后，后一个就成了负担。

−550 行的删除量主要来自这两处的收敛。对下游的含义是：typed view 的 gather/scatter 与单元素载入两类写法在 PTO 目标上从「能过但结果不对」变成「要么正确、要么被检测器拦下」。

来源：https://github.com/tile-ai/tilelang/pull/3894

1.3 昇腾 PTO：标量 cast 事实加保护，回绕 cast 不再让 IntSet 求值抛错（#3793）

复现形态很小：u = uint32(i - 1)，i 落在 [0, 63]。u 与任何 VMI 地址都无关，但 LegalizePTOVMIMemoryAccess 会在它上面失败。根因在 #3512 引入的分析器感知遍历——它会把标量定义积极绑定进分析上下文，而 IntSet 在求 cast 端点时，若其它子分析器已经装入了一个被低估的界，回绕 cast 就会抛异常。

修法是在下沉期跳过不安全的分析（2 个文件，+571/−13）。这类「分析器之间互相污染假设」的问题在大改之后的编译器里最费时间：报错位置在一个与故障无关的标量上，堆栈里也看不出是谁先装错了界。

来源：https://github.com/tile-ai/tilelang/pull/3793

1.4 昇腾 PTO：显式 SIMD 并行循环不再被车道布局推断拒收（#3796）

#3512 引入的 PTO 车道布局推断会拒掉既有的 T.Parallel 嵌套——只要里面写了显式 SIMD 指令。原因是推断把这些循环的地址当成标量车道访问，而它们实际是在向量块上迭代。

典型例子写在 PR 里：一个 T.Parallel(2, 32) 嵌套，循环体用 S.vld(temp[h, block * 64]) 与对应的 S.vsts(...)，每次迭代处理一条 64 元素的 FP32 向量。这种写法在推断出现之前是合法且常用的，推断上线后一律编译失败。改动 5 个文件、+194/−17，做法是保留旧式的显式 SIMD 并行语义，让推断只作用于它该管的形态。

来源：https://github.com/tile-ai/tilelang/pull/3796

1.5 昇腾 PTO：整数原子改走 signless 兼容包装，有符号输入可编译（#3792）

#3512 之后 codegen_pto 对 TileLang 的整数值发 pto.si32/pto.si64，而 PTO 的原子接口只接受 signless 的 i32/i64，于是整数缓冲上的 T.atomic_add、T.atomic_max、T.atomic_min 全部编译失败（此前已在上一期的同批条目中提到，本窗口 11:27 落主干）。

改法只在生成的调用边界做局部适配（4 个文件，+111/−36）：把指针与操作数按同宽重解释为 signless，保留指针的地址空间，返回值再还原成逻辑类型；min/max 保持原本的有符号或无符号比较语义。这样 #3512 建立的逻辑类型体系不必推翻，适配压缩在原子这一层。

来源：https://github.com/tile-ai/tilelang/pull/3792

2.2 mlir-ascend：TL 方言一日补五个算子，reshape / sort / print / pow / xor 在审（11-12）

TL 方言在窗口内被集中补面，五个提案从 17:49 到次日 05:45（北京时间）陆续开出：#228 tl.xor、#229 tl.pow、#231 tl.print、#232 tl.sort、#233 tl.reshape。它们都建在 #203 引入的 TL_BinaryOp<...> 基类上，照 #218（and）与 #225（or）的模板铺开，因此单笔改动都很薄。

分工上各有讲究：tl.reshape 是纯视图算子，不带目的操作数，在 TL→HIVM 里直接落到 memref.reinterpret_cast，不经过任何 HIVM 硬件算子，与既有 NPUIR 的 ReshapeCodegen 路径对齐；tl.sort 落到 hivm.hir.vsort，补了升降序两组转换测试与 expert_mode 路径；tl.print 落到 hivm.DebugOp，同时处理标量与张量两种打印形态，验证器只查元素类型为整型或浮点；tl.pow 与 tl.xor 走元素级二元算子的常规三段（方言定义、verifyElementwiseBinary、ConvertBinary 到对应 HIVM 算子）。

2.7 ROCm：一小时内成系列开出七笔，22 文件 +624/−19（11-12）

七笔在 07:56 至 07:57（北京时间）一分钟内连续开出，同一作者，全部基于 72d986e1，合起来是一套 HIP 侧补丁：

  • #3958（2 文件，+73/−0）给 hip_resource_info 加占用率报告。hipcc 本来就报 Occupancy 与 ScratchSize，但没人把它换算成 blocks per CU，而这才决定内核能不能用满它按两块申请的 LDS。

七笔合计 22 文件 +624/−19，覆盖编译参数、代码生成、启动界、占用率报告、归约工作区与寄存器驻留六个层次。这是本日报记录 ROCm 以来第一次成体系出现。

五、趋势观察

一是大改造的善后期比改造期更长，且成本落在「原本合法的程序不再合法」上。#3512 把 PTO 的向量化与类型体系一起换掉，之后连续四个窗口都在补它的回归面：执行后端换默认（11-11）、整数原子（11-11、11-12）、显式 SIMD 并行循环与标量 cast 事实（11-12）、VMI 描述符（11-12）。这四类问题的共同点不是「新功能算错」，而是「旧写法编译不过或结果变了」。对编译器项目，这类回归的排查成本远高于新功能的 bug——报错位置常常在一个与故障无关的标量或地址上，堆栈里看不出是谁先装错了假设。

二是后端矩阵从「一家独进」变成「多点同时开工」，形态也分化成四类。本期主仓五笔全在昇腾，但同窗口 ROCm 一次开出七笔成系列、海光一条分支一天十笔、Sunrise 在走发布流水线、Hexagon 以个人 fork 的形式把 TileLang 推到手机 DSP。四种形态（上游内置后端、厂商适配仓、独立发行版、第三方 fork）对应四种投入深度，这个分化本身就是判断各厂商依赖程度的可用指标：厂商仓跟版本、发行版跟主线、fork 跟自己的硬件。

三是「给 agent 用的工程化」开始成规模出现。mlir-ascend 的 harness 分支一日 +7632 行，内容是技能库、仿真 trace 流程与 Roofline 计算器，服务对象是「写算子的人或 agent」而不是编译器本身；同一周，Hexagon fork 的 README 直接写明后端与模型由 AI agent 在维护者指导下重写、四天 75 个 PR 占当前代码八成以上。两件事方向一致：TileLang 这类 DSL 的抽象层恰好落在「agent 能写对」的粒度上，于是生态开始为 agent 铺工具链，而不是只为人铺文档。这一条值得按周跟。

四是RISC-V 四源连续六个窗口静默，与整体活跃度形成明显反差。TVM 路线、MLIR 路线、社区索引页、算能 TPU 四个上游全部停在原引用，而同期主仓一天五笔合入、ROCm 一次七笔、第三方 fork 在推进一个新硬件后端。四源之外那条 CPU 线（Weft）在 11-11 给出了阶段性结论后也未再更新。判断不变：RISC-V 侧的 TileLang 工作仍处在「有路线、少提交」的阶段，真正可跟的落点还是那两条相互独立的实现路线是否继续推进。

局限说明：本期 GitHub 匿名 API 额度（60 次/小时）在采集早期耗尽，随后改用两种不吃额度的通道补齐——PR 增删行与文件数走 diff 端点统计，非默认分支的提交走分支级 atom 流；因此 1.2 至 1.5 四笔合入的文件数与行数为 diff 端点实测值，正文描述取检索接口返回的 PR 摘要，未逐行复核 diff。Hexagon fork 的窗口内推送经七个分支的 atom 流逐一比对定位到 fix/hexagon-dma-load-only，其余分支同期无新提交。第三方算子仓的官方属性无法从仓库本身核实，已在正文标注。新闻侧只有零命中，无外部报道可交叉验证。
