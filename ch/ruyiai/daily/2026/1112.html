今日重点：buddy-mlir 修 VLEN 1024 上的归约丢车道，二十五项测试从错到对（11-11）

日期：2026-11-11　来源：PR #1051

PR #1051 在 11-11 23:51（北京时间）合入，修的是一个只在长向量硬件上现形的错误：对宽度为 1 的可伸缩向量做 vir.reduce，结果只留下 lane 0。成因不在 VIR 自己的规范化，而在下游——vector.reduction 的 ElideSingleElementReduction 把 vector<[1]xT> 当成”只有一个元素”的向量，改写成 vector.extract 取 lane 0 再与累加器合并，其余 vscale - 1 条车道就此消失。

触发条件是 VLEN 1024：一个 16 个 f32 的区域在一块向量里就是 vector<[1]xf32>（vscale 16），而 VLEN 128 与 256 上它是 vector<[4]xf32> 及更宽，走不到这条路径。作者在 SpacemiT K3 的 A100 核上实测，25 项归约测试全部给出错值，例如 512 个值的 amax 得 1.853 而非 4.101；同一批测试在 CI 的 riscv64 runner（VLEN 256）上是通过的。这正是此类缺陷难被发现的原因：CI 的向量宽度覆盖不到出货硬件的宽度。

修法绕开规范化，直接用 vector.reduction 最终会降到的 LLVM intrinsics 构造归约——浮点用 llvm.vector.reduce.fadd 并以累加器作起始值，fmax 则接 maxnum 与累加器，vir.reduce 的两条 lowering 都改。作者注明这是与 splat 的 broadcastTo 相同的绕行手法。配套测试进 tests/Conversion 下的 VIR 用例，check-buddy 在 x86（用 main 的 LLVM）与 SG2044 原生两侧通过。

对这条栈的意义：Triton-RISCV 在 K3 上的归约算子（amax、max、mean、sum、cumsum、rms_norm、mse_loss、vector_norm、euclidean_dist、attention）此前在这块板子上是静默错值，不是崩溃。修完才有资格谈性能。

三、向量扩展与算子优化

3.1 strip-mined set_vl 的车道余量按半宽逐级降低，K3 上 YOLOv8 的热点从标量点积里出来（11-11）

日期：2026-11-11　来源：PR #1050

#1050 在 11-11 20:12 合入。此前一个被 strip-mine 的 vir.set_vl 只按选定宽度跑主循环，剩下的车道全丢进标量尾循环；车道数不足一个向量的区域更是整段标量。在 K3 的 A100 核（VLEN 1024）上跑 f32 YOLOv8，姿态头的 51 个输出通道得到 64 车道的向量，结果是最热的那个循环（占整模 5% 时间）是一段标量 flw 加 fmadd.s 的点积，perf 采 15 万样本里标量浮点指令占了 39%。

改法是让主循环之后的车道依次降到半宽、四分之一宽，每一档最多用一次且按车道顺序，最后才交给标量尾循环，尾循环只留不足最小宽度（定长 2 车道、可伸缩 [1]）的部分。没有掩码：可伸缩向量在运行期用 scf.if 判余量，定长向量在 vl 为常量时编译期判掉，这样仿射尾循环的边界仍是仿射的；vl 动态时保留标量尾。

数值不变——每条车道算的还是同样的运算，有序归约看到的车道顺序也没变，作者用 K3 上前向输出的 FNV 哈希验证了同一位。这条修的是性能，不是正确性，但换来的是长向量硬件上最热那段代码终于走向量单元。

3.2 向量三仓仍静默，向量侧的增量全在 VIR 层（11-12 状态）

六、趋势观察

6.1 发布链先于功能：triton-riscv 这一周修的是”能不能出包”

窗口内 triton-riscv 三笔合入里两笔是 CI 与发布脚本，一笔是 README 的安装前提，功能面零改动；夜间版自己的说明文字也在讲 runner 上的 git 认证。这不是停滞，而是把一个刚从”能跑真机”升级到”默认启用 GPU 后端”的项目补上可复现性：自托管 riscv64 runner 的匿名 git 流量拿不到认证，看起来是基础设施小事，实际决定夜间包是否每天都能出来。

对照 RuyiSDK 那侧就清楚：包管理器能把 ABI 兼容性做成安装前的告警，是因为它的发布链已经稳到可以做这种精细活。triton-riscv 正在走同一条路，只是晚了几步。

6.2 VLEN 1024 正在成为编译器与运行时的共同压力点

一天之内三处独立证据指向同一个参数：buddy-mlir 的归约丢车道只在 VLEN 1024 上现形（VLEN 128 与 256 都对），strip-mined 余量降宽的动因来自 K3 A100 核上 64 车道的向量，V8 的审阅名单里出现 “Allow vlen=1024”。此前这类讨论停在架构参数层面，现在落到”哪条测试在什么宽度上会错”。

对测试面的直接要求是覆盖出货宽度：原 CI 的 riscv64 runner 是 VLEN 256，恰好在 #1051 的问题上通过。这条教训比修好的那几行代码更值钱——凡是与 vscale 相关的推理，都得在 1024 上验一遍。

6.3 双周进展的草稿日与上线日差六天，读它的条目要分开看

080 期 11-05 就在仓里成形，11-11 才发到论坛。于是同一份文本里，0.54.0 与 Imager 1.1.0 是”已发布”（11-10 的事），插件 0.1.7 也是”已发布”（09-28 的事，之后还有 10-30 的 0.1.8-beta.1）。如果按上线日通读，很容易把三款工具当成同一天的三连发。

可行的读法是分两层：工具版本看 Release 时间，编译器与运行时条目看上游合入时间（GCC 那三项写的是 10-27）。日报这边已按这个口径拆分，读者对照双周进展时也宜如此。
