今日重点：triton-riscv 出第一个正式发布标签，安装路径从源码改为 wheel（11-09）

日期：2026-11-09　来源：发布标签 release/20261108-6895885、PR #105、PR #107

11-09 06:59（北京时间）打出的 release/20261108-6895885 是这个仓的第一个正式发布标签：此前十八个标签全部是 nightly/ 前缀，仓里从来没有 release/ 这一层。发布物两个 wheel，分别是 x86_64（manylinux_2_27 与 2_28）与 riscv64（manylinux_2_39），统一 cp312-abi3，版本串 triton-3.9.0。

标签指向提交 6895885，也就是 11-06 那笔”为 AMD 补 codegen 库”（#102）的合入提交，与夜间版 nightly/20261106-6895885 是同一个点。当天三笔提交（#105、#106、#107）都在标签之后落地，没有进这个包。这意味着”第一个正式版”打的其实是上周末的代码状态，发布动作本身是这个标签的全部内容。

与标签同日的 #105 重写了 README，把安装段从源码优先改成 wheel 优先：先给 wheel 路径与承载它的包索引，再给它们所需的 LLVM 归档与一个指向变量；源码路径压缩成 make setup（建 .venv、克隆固定版 Triton、下载固定版 LLVM 与 buddy 构建），原先那段”建虚拟环境、装依赖、环境脚本十五个变量”的说明收成一条短注。

快速开始也换了写法：不再只打印 ok: True，而是把内核编到 riscv64-unknown-linux-gnu，保留目标文件并 grep 反汇编，打印后端生成的 vsetivli、vle32.v、vfadd.vv、vse32.v。对一个编译器项目来说，这比一句断言更能说明”后端真的出了向量指令”。

夜间版另加了唯一版本后缀 .dev<日期>：此前每次构建共用 Triton 自己的版本号，包索引会拒绝重复版本。wheel 的发布动作放在 wheel job 内部，避免重复下载产物，并以 PYPI 系列密钥存在为条件、在包索引侧尚未就绪时继续执行而不失败。

#107 随后做了修正：包索引目前还没有 triton 与 buddy 工具，README 里那条二进制安装给出的地址会失败，于是改为指向两个项目各自的 GitHub releases、从磁盘装 wheel，并写明 LLVM 压缩包的来源。同一笔提交还修了 Python 3.14 的 lit 崩溃。

今日重点：buddy-mlir 把整张 f32 YOLOv8 图降到 VIR，K3 上输出逐字节一致（11-10）

日期：2026-11-09（合入于 11-10 01:07 北京时间）　来源：PR #1041、合入提交 18c66ec

PR #1041 把 #1042 的 f32 YOLOv8 图端到端走通 VIR：先做 Linalg 到 VIR 的降低，再做 VIR 到向量方言的降低。此前这条 pass 里没有卷积 pattern，图里另有三类算子直接失败——一笔改动同时补上了卷积与那三类。

规模是十四个文件、新增一千六百四十六行、删除一百一十五行、十三个提交。作者 zhanghb97，11-09 08:57 开出，当晚合入。

卷积两族都覆盖：二维 NHWC 配 HWCF 与二维 NHWC 配 FHWC。向量化沿输出通道 F 展开（输出与 HWCF 过滤器的最后一维），对每个 (kh, kw, c) 把输入元素广播成每个输出像素一个 vir.fma，因此每次向量访问都是连续的，也没有跨 lane 的归约。FHWC 过滤器先并行拷贝进 HWCF 缓冲；输出行放进 scf.parallel，每行一个 F lane 的 vir.set_vl。

三类此前失败的算子一并补齐。一是 rank-0 输入：memref 直接进 linalg.generic 会在 memref.expand_shape 报 invalid reassociation，改为加载一次后广播。二是保留末维的 linalg.reduce，例如 DFL softmax 的 1x16x4x2100、dimensions=[1]、addf 与 maximumf 组合，改为沿末维向量化、被归约维上的切片逐元素合并，不生成 vir.reduce。三是读取 linalg.index 的命名算子，例如上采样里的 linalg.map iota，补上与同类 linalg.generic 相同的标量循环。

真机口径很清楚：在 K3 上，f32 YOLOv8 pose 的原始输出最多变化 6e-5，与 PyTorch 的差距仍在 6e-4（bus）与 8e-4（zidane）以内，与改动前一致；detect 模型的检测结果不变，速度没有下降；f32 与 IME 动态库的输出与改动前逐字节相同。

一、RuyiAI 栈进展（PyTorch / Triton / TileLang RISC-V 适配）

1.1 triton-riscv：换成 torch 2.15.0 后 flaggems 七个用例失败，改为防御式读取（11-09）

日期：2026-11-09　来源：PR #106、提交 cfdf4f7

riscv64 的 CI 装的是索引里带的 torch，最新的 2.15.0 一来，flaggems 套件里七个用例失败。修完的结果是三千八百二十六项通过、两项跳过。

五例 median 的问题出在名字张量：median.py 实现了 torch 的命名张量支持，而 2.15.0 这个构建没有 Tensor.names，判空函数在内核还没执行前就抛 AttributeError。改法是防御式读取该属性，把没有这个 API 的构建当作”无名字”，这与现有检查对”名字全为 None 的张量”给出的答案一致。作者也说明了为什么不能直接删掉这段代码：上游 flaggems 仍然无保护地调用 names，且命名张量在更早的 torch 版本里确实存在。

两例 sinh 的 fp16 用例原先按相对与绝对误差各 1e-4 比较，fp16 达不到（实测相对差 6.6e-4），fp32 保留 1e-4。同时把 torch 2.10 从 riscv64 的安装里去掉，重新跟随索引。对一条跟着上游 torch 走的 CI 来说，这类维护是无法外包的成本：上游一变，套件就要重新对齐。

1.2 triton-riscv：Python 3.14 下 lit 崩溃，CI 改为优先用 pip 装的 lit（11-09）

日期：2026-11-09　来源：PR #107、提交 209274f

红的是 CI 里 Python 3.14 那个任务。Triton 用 which 在 PATH 里找 lit，而 LLVM 树里那份 lit 在模块级调用 main，Python 3.14 在 Linux 上默认改用 forkserver 启动方式，重新导入时直接崩溃。

修法很轻：把构建解释器的 bin 目录放到 PATH 最前，查找就会先命中 pip 装的那份 lit。这与 1.1 同属”CI 跟着上游跑”之后的收尾，也解释了为什么三笔提交里有两笔是环境而不是编译器。

三、向量扩展与算子优化

3.1 buddy-mlir：卷积沿输出通道向量化，FHWC 过滤器先转成 HWCF（11-10）

日期：2026-11-09（合入于 11-10 01:07 北京时间）　来源：PR #1041、合入提交 18c66ec

卷积的降低策略值得单独看，因为它决定了后面所有调优的空间。选择是沿输出通道 F 向量化，而不是沿输入通道 C 做归约：对每个 (kh, kw, c)，把一个输入元素广播成每个输出像素一个 vir.fma。

直接好处是每次向量访存都连续，且没有跨 lane 的归约——归约需要横向指令与后续的规约树，在窄 VLEN 上代价明显。代价是过滤器布局必须匹配：FHWC 排列的过滤器要先并行拷贝进 HWCF 缓冲，多一次搬运，换来内层循环的连续访问。

输出行用 scf.parallel，每行一个 F lane 的 vir.set_vl。此前的 VIR 到向量降低对动态向量的前导静态维发串行 affine.for，而并行化 pass 穿不过 vector.load，这次改成 scf.parallel，条件是内存访问允许。另外，每个输出像素占一个迭代的做法保留在 Linalg 到 VIR 的降低里，”多次迭代共享一次向量加载”由后端在带结果的向量设定内自行合并，把寄存器决策留给目标。

3.2 buddy-mlir：补齐 rank-0 输入、保留末维的 reduce 与读 linalg.index 的算子（11-10）

日期：2026-11-09（合入于 11-10 01:07 北京时间）　来源：PR #1041、合入提交 18c66ec

三类失败算子各有各的坑。rank-0 输入（单元素 memref 直接进 linalg.generic）会在形状展开处报无效重关联，现在改为加载一次再广播。

保留末维的 reduce 更容易被忽略：DFL softmax 的 1x16x4x2100、dimensions=[1]、组合子 addf 与 maximumf，原来的 pass 直接报错。新做法是沿末维向量化、把被归约维上的切片逐元素合并，不生成 vir.reduce；此前能降的那些形态保持不变。

第三类是读 linalg.index 的命名算子，例如上采样里的 linalg.map iota。命名算子没有泛型 op 的 body 可抄，过去被跳过，现在给它补上与同类 linalg.generic 相同的标量循环。

四、Buddy Compiler 动态

4.1 评审收敛的三处：并行行内存依赖、FMA 舍入、reduce 分派（11-10）

日期：2026-11-09（合入于 11-10 01:07 北京时间）　来源：PR #1041

三处评审意见都变成了代码改动。并行行的内存依赖：行之间没有 SSA 依赖，但可能有内存依赖，于是只在能证明各行访存互相独立时才用 scf.parallel——每个写都是 vir.store 且存的向量带这些行；被写元素互不重叠（单位布局，或 stride 全为静态并按 stride 排序后互相嵌套）；凡可能与被写 memref 重叠的访问都必须用同样的基址、下标与秩。不满足就退回串行 affine.for。新增的测试文件覆盖四种情形：可并行、跨行共享标量读写、stride 为 0 的 memref、读取另一行正在写的数据。

FMA 这条更细：VIR 到向量的降低在主循环里把 vir.fma 降成向量 fma，尾部循环里却拆成乘法加加法，同一个 op 在向量 lane 与尾部 lane 上给出不同舍入。测试用 a 等于 1 加 2 的负 23 次方、b 等于 1 减 2 的负 23 次方、c 等于负 1 这一组，向量 lane 得负 2 的负 46 次方、尾部 lane 得 0。现在尾部改用 math.fma，两边一致，测试同时检查两侧。这个改动会让尾部 lane 有舍入级差异，K3 上 f32 YOLOv8 的输出变化上限就是前面那个 6e-5。

reduce 的分派条件也收窄了：判定函数与旧实现实际支持的情形完全对齐（元素类型 f32、组合子 addf 或 maxnumf、各秩对应的维度等），避免把不该走快路径的 reduce 也吞进去。

日期：2026-11-10（状态）　来源：PR #1035、PR #1038、PR #1039、PR #1040

六、趋势观察

6.1 这一轮补的是交付链路，不是算子

三笔 triton-riscv 提交里，两笔是安装与测试链路（README 改为 wheel 优先、flaggems 跟上新 torch），一笔是 CI 的 Python 3.14 兼容，没有一笔动编译器本身。加上周日那个第一个正式发布标签，这一天的主题是”让人能装上、能装对”。

这种轮次在任何项目里都会出现，但容易被误读为没有进展。实际上从源码安装到 wheel 安装，是从”开发者能编”到”用户能装”的分界：源码路径要求用户自己准备 LLVM、buddy 构建与几十个环境变量，wheel 路径只要一条命令。对 RISC-V 这种长期靠”自己编”的生态，这一步的边际价值高于再优化一个算子。

6.2 逐字节一致正在成为 VIR 降低的验收标准

11-08 的两笔改动用加载期校验拦住 VLEN 不符、让宿主定尺按真实 VLEN 走，今天的 #1041 又把”f32 与 IME 动态库输出与改动前逐字节相同”写进验证口径。三笔改动指向同一个标准：降低可以换实现，但不能改数值。

这个标准比”精度在容差内”更严格，也更适合编译器：容差能掩盖顺序错误，逐字节比较不能。代价是每次改动都要有一份可复现的基线，而 K3 这种双核心（两个簇的 VLEN 不同）的机器恰好提供了最难的基线。

6.3 桌面栈与安全更新接管了打包节奏

六十五笔提交里，四十笔是 KDE Plasma 6.8.2、七笔是 Python 安全更新，其余是 Wayland、wget2 与 llvm 绑定一类的零散升版。AI 栈这一天只有四笔提交，发行版侧却有六十多笔。

这个比例说明 openRuyi 当前的瓶颈在跟上游，而不是造新东西：桌面与语言运行时的上游版本一放，打包仓就要在一两天内全部跟上；而 AI 栈的节奏围绕模型与工具链，按周甚至按版本走。
