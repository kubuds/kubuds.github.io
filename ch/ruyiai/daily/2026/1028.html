二、RuyiSDK 工具链与发行版

2.1 openRuyi PR #1350：RuyiAI 三件套进发行版，作者当日逐条回应复核意见（10-27）

日期：2026-10-27　来源：PR #1350、PR #1350 复核评论、PR #1350 提交

PR #1350 是本期分发层最重要的一笔：一个 PR 同时加三个包——buddy-mlir（基于 LLVM 的 MLIR 编译框架）、python-triton-ruyiai（RISC-V 版 Triton）、python-tilelang-ruyiai（RISC-V 版 TileLang 后端）。3 笔提交全部落在 9-21 的 09:46 至 09:48（两分钟内），共 9 个文件、+666/−0。

时间线值得记下来：9-21 开 PR，9-24 维护者 Z572 提三处修改要求（为什么需要 git、buddy-mlir 是否应提供 macro 文件供 Triton 定位其 LLVM、buddy-mlir 是否应先用 GCC 构建固定版本 clang 再用新 clang 构建自身），9-28 作者回复并修掉两处；随后停摆近一个月，10-27 17:55、17:57、18:54 连续三条回复把剩下的争议逐条说清。

三条回复的技术内容比进度本身更有信息量。其一，triton 上游的 setup.py 会强制检查 git 能否执行，所以要么加 git 构建依赖，要么改 setup.py（需新增补丁文件，且 triton 更新时容易失配）——作者选择前者。其二，buddy-mlir 自带的 LLVM 只在该包内部使用，且这些包始终锁定到具体 LLVM 提交，因此倾向于把它留在构建流程内部，而不外置成独立 macro 包。其三，改用 GCC 构建固定版 LLVM/clang 在技术上可行，但构建时间至少增加 1.5 倍。

这三条指向同一个取舍：RuyiAI 这几个包的构建链耦合度高（Triton 依赖 buddy-mlir 的 LLVM、TileLang 依赖 buddy-mlir 工具链），一旦按发行版的「依赖外置、复用系统包」惯例拆开，构建成本与失配风险都会上升。作者选择保住耦合、承担体积与构建时间，是打包路线上的一次明确表态。

2.2 openRuyi PR #1352：PyTorch RISC-V 适配单独成包，安装后自带冒烟测试（10-27 状态）

日期：2026-10-27（状态）　来源：PR #1352、python-torch-ruyiai spec 文件

PR #1352 把 RuyiAI-Stack/pytorch 单独打成 python-torch-ruyiai（8 个文件、+783/−0），与 #1350 同日更新，状态仍为开放，唯一一笔提交停在 9-21 11:22。

补丁集读起来是一条完整的发行版适配清单：2001 强制 OpenBLAS 走 cblas 复数点积、2003 改用系统 fmt、2005 改用系统 cmake 依赖、2006 跳过无用的子模块预构建检查、2011 把 RVV kernel 按目标向量能力门控、2012 内嵌 scikit-build-core。另有一个 pytorch-smoke-test.py，说明这个包在安装后要跑一次冒烟测试才算通过——对发行版而言，这比单纯「能装上」更前进一步。

2011 那条尤其值得注意：把 RVV kernel 的启用条件从「编译时假定支持」改成「按目标向量能力门控」，正是社区里反复出现的问题——RVA20 等不含向量扩展的目标上，打包时若不门控，会生成无法运行的代码。这类修补通常要等用户在实际板子上撞到才补，现在提前进了打包补丁。

与 #1350 一样，这个包也声明了 AI 辅助（Assisted-by: Deepseek V4.1 Flash），并按 openRuyi 的 AI 贡献政策做了勾选与署名。

2.4 openRuyi：三笔 revert 收回「随包分发 LLVM IR」路线（10-27）

日期：2026-10-27　来源：PR #1509 Revert llvm ir、openRuyi 提交列表

15:15 合入的 #1509 只有三笔提交、净删 105 行（+5/−105），撤销的是此前在同一仓库里做过的三项实验性打包：gsl 的 llvmir feature、pixman 改用 clang 构建并随包产出 IR 文件、libjpeg-turbo 随包分发 LLVM IR 文件。

PR 正文没有写理由，从提交内容看，方向是把库编成 LLVM IR 随包分发，为后续的再优化或延迟代码生成留接口；现在整条线撤回，说明这条路线在发版前被判定为「暂不保留」。对 RISC-V 发行版而言这是个有意思的取舍：IR 分发在理论上能复用上游优化，但会带来包体积、ABI 与调试符号一致性的连锁问题，且需要基础设施侧配合，短期难以形成收益。

这也是本期 openRuyi 与前几期的一个分野：过去几期的关键词是「补」——补包、补安全、补 Rust crate；本期除了补，还出现了明确的减法。

2.5 在审队列：qemu 11.1.2、qemu-rustsbi、libvirt 与交叉工具链（10-27 状态）

日期：2026-10-27（状态）　来源：openRuyi 开放 PR、PR #1520 qemu 11.1.2、PR #1516 qemu-rustsbi、PR #1490 交叉工具链

四、Buddy Compiler 动态

4.1 VIR 补上 Python 绑定：从 buddy-opt 专用变成可编程方言（10-27）

日期：2026-10-27　来源：PR #1009、buddy-mlir 提交列表

22:42 合入的 #1009 是本窗口 Buddy Compiler 一侧的核心动作：12 个文件、+614/−1，新增 buddy_mlir.dialects.vir 模块。提交说明把痛点写得直白——VIR 此前没有任何 Python 绑定，所以 VIR 的 decode attention 只能用 ir.Operation.create("vir....") 拼算子、用 ir.Type.parse("!vir.vec<...>") 拼类型，整套 VIR 降级也只能在 buddy-opt 这一个可执行文件里跑。

实现方式选了「跟着现有方言走」：ODS 定义算子（VIRBinding.td）加 C API 加 nanobind 扩展，与同仓库里 quant 等自带类型的上游方言同构；按 PR 描述分三块——Ops、Types、以及把 VIR 降级挂进 Python 的 pass 注册。

这一步的意义不在工具本身，而在可组合性：一旦 VIR 能被 Python 直接构造与降级，算子描述、形状推导、测试用例都可以写在 Python 侧，前端（Triton、TileLang）与 VIR 的对接不必再依赖 C++ 侧加钩子。对一条此前只能在单一可执行文件里验证的中间表示来说，这是从「编译器内部件」转向「可供外部调用的方言」。

需注意 #1009 合入后紧接出现 #1011「Cast the scalable VIR piece count to int64_t」（开放），说明可伸缩向量路径上的整型宽度问题这两天才被触及，Python 绑定只是打开了入口，稳定性仍在磨合。

4.2 在审五笔：piece count 转 int64、Whisper 预处理复用、buddy-server 源码整理（10-27）

日期：2026-10-27（状态）　来源：PR #1011、PR #1013、PR #1012、PR #1010

窗口内有更新的开放 PR 共五笔，方向分三组。

VIR 与可伸缩向量：#1011 把 VIR 的 piece count 从默认宽度显式转成 int64_t。piece count 指一个可伸缩向量被切成几段，按 32 位参与后续乘加在大形状下有溢出风险，这条修法与上一期的 #1008（索引向量宽度断言）属同一类收尾。

模型示例：#1013 在每次转写内复用 Whisper 的预处理，#1012 为 Whisper 输出加校验并启用 x64 CI 测试。两笔都是常规示例质量改进，不涉及 RISC-V。

基础设施：#1010 整理 buddy-server 的源码与测试目录结构；另有 #993 新增 tile.upsample_nearest 算子与识别模式、#932 修 Gemmini OS 分块矩阵乘中 C 搬出的行填充，两笔更新时间也在窗口内但内容更早。

六、趋势观察

6.1 表达层、工具层、分发层在同一天各补一块

把本期的三件事放在一条时间轴上：10-26 夜里 VIR 补齐可伸缩向量表达，10-27 夜里补上 Python 绑定，10-27 全天在推发行版打包。三段本来是依次递进的——先能表达，再能被调用，最后能被分发——过去几期一直是「表达层快、工具层与分发层滞后」，本期第一次出现同日三线并进。

但要判断这条栈是否真在闭环，还有两个已知缺口。其一，triton-riscv 换锚是自动化的，适配验证尚未跟上，0.1.1 到 0.1.3 之间的接口变化会不会在下游暴露，下期才知道。其二，pytorch 的 riscv 分支连续六日零提交，而分发侧已经在给它打包（#1352）——包跟着的是一个不动的分支，等包合入时是否已经落后上游基线，是需要盯的风险。

6.2 发版前清扫之外，发行版开始做减法

本期 openRuyi 的两组动作性质不同：一组是加法（45 笔提交、13 个新增包、12 个安全更新、Samba 全家联动升级），另一组是减法（三笔 revert 收回 LLVM IR 随包分发）。过去几期看到的都是「发版前清扫」——补依赖、清 CVE、切版本；本期第一次看到明确的功能性回收。

这说明 openRuyi 的维护重心正在从「覆盖更多包」转向「保证已有包的质量边界」：IR 分发这类实验会带来包体积、ABI 与基础设施的连锁成本，在发版压力下被优先砍掉。对 RuyiAI 栈而言这是双面信号——打包通道更规范了（#1350、#1352 都在按发行版惯例逐条收敛），但对「带实验性质的构建方式」（如内嵌 LLVM、自带 vendor）容忍度也会同步下降。作者在 #1350 里坚持把 buddy-mlir 的 LLVM 留在包内，恰恰是逆着这个方向的一次交涉，结果值得观察。
