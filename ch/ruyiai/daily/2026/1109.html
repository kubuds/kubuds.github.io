今日重点：Ruyi Firmware 连续两日发版，HiFive Unmatched 进入支持列表（11-07、11-08）

日期：2026-11-07、2026-11-08　来源：Ruyi Firmware 20261107、Ruyi Firmware 20261108、固件仓提交列表

openRuyi 的 UEFI 固件项目在两晚内连出两版。11-07 22:21（北京时间）发布 20261107，11-08 22:47 发布 20261108 并标记为预发布；两版各带四个构建产物。

20261107 是本窗口的功能版，最大变化是把支持面从 SpacemiT K3 扩到 SiFive HiFive Unmatched：新增该板的 SPI 启动、JTAG 恢复、NVMe 与 USB 启动，以及持久化 UEFI 变量。围绕这一扩展，发布说明里还有四项配套调整：每块板分别提供 DEBUG 与 RELEASE 两套包；Platform Settings 里加入 PXE 与 HTTP ISO 启动控制（默认关闭）；UEFI 驱动模拟改为默认启用，可在 Setup 中改，也可用配置脚本设成镜像默认值；两块板统一使用 Ruyi logo 与启动倒计时条，Firmware Update 界面加了文件选择器。K3 侧另有两条体验修正：改善图形控制台的响应速度，以及在 UEFI 启动阶段读取 P1 上的 RTC。

20261108 只改 K3 一条线：USB Fastboot 切换到 EDK2 的共享实现，可用于固件更新、回读，以及从内存启动 EFI 应用；同时通过 fastboot getvar version-bootloader 上报 EDK2 固件版本。这条改动把厂商私有的刷机通道并入 EDK2 标准路径，对产线与售后是可直接使用的接口，对开发者则意味着不再需要专用工具确认固件版本。

两版都保留同一句兼容性声明：Linux 主线支持按尽力而为的方式提供；已知的 framebuffer 问题在发行说明里给出绕行办法。从 10 月的 20261013 至 20261015 三连发（CPU 模式选择、System Information 页）看，这条固件线已进入按日迭代的节奏，而 Unmatched 的加入是它第一次跨出单一芯片厂商。

今日重点：按精确 VLEN 编译的模型在别的 VLEN 上会静默算错，buddy-mlir 改为加载期校验（11-08）

日期：2026-11-08　来源：PR #1032、提交 4063c48

PR #1032 解决的问题是一类错误的失败方式：不报错，只算错。按精确 VLEN 构建的 RISC-V 模型，向量代码只对那一个 VLEN 成立——llc 被明确告知 VLEN（+zvlNb 与 -riscv-v-vector-bits-max），decode attention 里的可伸缩向量也按它定尺（#1028、#1030）。换到别的 VLEN 上，模型不崩溃，直接给出错误结果。提交说明给出的实例很具体：K3 上按 prefill_ime 构建的 DeepSeek-R1 rax（BUDDY_RISCV_VLEN=1024）在没有执行 /proc/set_ai_thread 时会落到 X100 核心（VLEN 256）上运行，结果错误而无任何提示。

修法是把校验前移到加载时刻。runtime/rvv/BuddyRvvVlen.c 作为构造函数被链接进模型库，库一被载入就读 vlenb，发现与构建时的精确 VLEN 不符就打印信息并以 _exit(1) 结束进程。用 _exit 而不是 exit 是有意的：加载器持锁期间跑析构函数会死锁。构造函数的形式覆盖了所有加载方，包括命令行工具、服务端与测试；通用 RVV 构建（不指定精确 VLEN）与其它目标不受影响。

评审后又补了第二笔提交，把校验从“按构建变量判断”改成“按最终 llc 选项判断”。原先的问题有两个：一是原生构建可能通过模型自带的 LLC_ATTRS 指定 VLEN，若 BUDDY_RISCV_VLEN 与它不一致，校验值会和实际代码不符；二是只链接进了第三阶段，Qwen3-VL 的视觉与解码两个 shim、以及分层链接的路径都漏掉了。现在由构建脚本从最终 llc 选项里取出精确 VLEN（与 VIR 降低读同一处），第三阶段、两个 shim 与分层链接全部带上，配置阶段发现选项互相矛盾就直接失败。

测试是这条改动的另一半：test_buddy_rvv_vlen.py 为 VLEN 128 到 65536 分别构建模型库，只有宿主那一个能加载，其余全部以退出码 1 结束；test_buddy_rvv_vlen_cmake.py 用配置脚本覆盖 BUDDY_RISCV_VLEN、LLC_ATTRS、prefill_ime 与 zvl 参数的各种组合。真机验证在 K3 的 X100 与 A100 两种核心上完成，仓库自检 239 加 409 项通过。

1.1 triton-riscv：发行 wheel 补上后端注册，发布工作流改用与 CI 相同的检出动作（11-06）

日期：2026-11-06　来源：PR #101、提交 d8c2b3e

PR #101 修的是 #100 落地后暴露的两处发布链问题，共两个文件、十七行新增。发布工作流改用与 CI 相同的检出动作版本；scripts/release.sh 增加后端注册步骤，让 release 产出的 wheel 与 CI 构建的 wheel 具备同样的插件注册信息。此前 release 路径只做打包，插件目录没有注册进 wheel，装上之后后端不可见——这类问题在 CI 里看不出来，因为 CI 走的是安装链路而非 wheel 链路。

1.2 triton-riscv：为 AMD 后端补 riscv64 缺失的 codegen 库，夜间版出 x86_64 与 riscv64 两个 wheel（11-07）

日期：2026-11-07　来源：PR #102、夜间版 aa51ac2、夜间版 6895885

PR #102 的标题是“加入 AMD 支持”，实际内容是补一个缺失的库，而不是新增一个后端。上游的 AMD 后端需要 libtriton_amd_codegen.so：要么下载预编译副本，要么针对单独固定版本的 LLVM 自行构建，而这两条路都没有 riscv64 版本。这个库本身很小，用仓库里现成的 LLVM 几秒钟就能编出来。setup.sh 因此在检测到库缺失时本地构建并放到约定路径，env.sh 把 TRITON_AMD_CODEGEN_PATH 指向它——原来的 GPU 依赖 stub 会把所有 GPU 下载指向空目录，顺带也跳过了上游对该库的拉取，而插件编译时仍要读这个路径。没有它，AMD 后端拒绝编译任何东西。

这条改动也说明插件化改造之后这个仓的定位：同一棵树既产出 riscv64 的 Triton，也在构建期容纳其它后端所需的组件，多后端共存不再靠分支切换。窗口内两笔夜间版按新节奏产出（11-06 12:08 与 11-07 07:52），每版两个产物，分别是 cp312-abi3 的 x86_64 wheel（约 320 MB）与 riscv64 wheel（约 337 MB）；此前的夜间版是五到六个产物，产物数下降与 stable ABI 单 wheel、后端并入 Triton 包这条线一致。

三、向量扩展与算子优化

3.1 buddy-mlir：按精确 VLEN 构建的模型库加加载期校验，K3 上误跑在 X100 核心会被立即拦下（11-08）

日期：2026-11-08　来源：PR #1032、提交 4063c48

改动共十二个文件、新增五百四十七行、删除八十六行，核心是一个十几行的 C 文件：runtime/rvv/BuddyRvvVlen.c。它作为构造函数链接进模型库，载入时读 vlenb 并与构建时的精确 VLEN 比对，不一致就打印信息后退出。配套的构建脚本改动比运行时代码更复杂——buddy_rvv_vlen.cmake 现在从最终 llc 选项推导 VLEN（与 VIR 降低共用同一段读取逻辑），buddy_model.cmake 在规格与选项确定后编译该目标文件，第三阶段、Qwen3-VL 的两个 shim 与分层链接都显式带上。

文档同步更新了 A210 与 K3 两篇 DeepSeek-R1 部署说明，把“哪些构建是精确 VLEN、哪些是通用 RVV”的边界写清楚：A210 的内核是定长向量、没有 VIR，llc 对任何不小于 128 的 VLEN 都能降低，属于通用构建；K3 的 prefill_ime 必须 1024，属于精确 VLEN。这条边界过去只存在于构建脚本的注释里，现在有了运行期强制。

3.2 buddy-mlir：降低 VIR 时识别 RISC-V 宿主的 VLEN，修掉 riscv64 CI 自 #1030 起的比特级失败（11-08）

日期：2026-11-08　来源：PR #1037、提交 79ffafd

同一人同日提交的第二笔，修的是另一个方向的错误。-lower-vir-to-vector 在不给 rvv-vlen、也不开可伸缩向量时，按宿主寄存器宽度给定长向量定尺，但它的宿主识别只覆盖 x86（AVX2、AVX-512）与 SVE：带 V 扩展的 RISC-V 宿主一律落到通用默认值（128 位、16 个寄存器），无论实际 VLEN 是多少。

后果出现在测试里。自 #1030 起，kernels 流水线在没有 llc 选项时按宿主降低 VIR，riscv64 CI 宿主是 VLEN 256，却被当成 128 位处理：q、k 范数的平方被切成 vector<32xf32> 分段求和，与矢量内核逐比特比较的顺序不同，vir decode qk_norm ... same bits 判定为假。这个问题在 main 的每一次 riscv64 运行中都存在，x86（AVX-512）拿到的是 1024 的宽度，所以一直通过。作者先加了一笔只在测试里固定 rvv-vlen=1024 use-scalable=false 的改动，随即自行回退——那等于在 llc 选项之外再造一处 VLEN 设定，与 #1032 的方向冲突。最终修法是在降低阶段识别 RISC-V 宿主（读取宿主 CPU 特性与 hwprobe），按真实 VLEN 定尺，测试文件换成宿主形态的新用例。

六、趋势观察

6.1 固件线从单板走向多板：Unmatched 与 PXE 启动指向的场景

日期：2026-11-07　来源：Ruyi Firmware 20261107

Ruyi Firmware 此前基本围绕 SpacemiT K3 迭代，10 月的三个版本都在补 K3 的 CPU 模式选择、系统信息页与刷机路径。20261107 第一次把 SiFive 的 HiFive Unmatched 纳入支持，且不是最小可用：SPI 启动、JTAG 恢复、NVMe 与 USB 启动、持久化 UEFI 变量一次配齐，等于把一块开发板从“能点亮”做到“能当工作站”。

配套的两项设置更能说明目标场景：PXE 与 HTTP ISO 启动控制（默认关闭）、每块板分 DEBUG 与 RELEASE 两种包。前者是机房与批量部署的入口，后者是产线与开发的分工。开源 RISC-V 平台长期缺一套与 EDK2 对齐、能跨厂商复用的固件方案，Unmatched 的加入让这条线第一次有了第二个芯片厂商的样本；接下来要看的是第三块板来自谁。

6.2 精确 VLEN 特化的代价：静默算错比崩溃更难发现

日期：2026-11-08　来源：PR #1032、PR #1037

K3 的双簇结构把 RISC-V 的 VLEN 问题摊开在同一台机器上：A100 核心 VLEN 1024，X100 核心 VLEN 256，同一个可执行文件在错误的簇上跑，不会崩，只会算错。过去这个问题靠部署文档提醒（先写 /proc/set_ai_thread），现在靠加载期校验兜住。对一个交付模型的工具链来说，宁可启动失败也不要出错误结果——这是 #1032 的价值。

同日 #1037 从另一侧证明同一件事：宿主定尺的默认值（128 位、16 个寄存器）在 x86 上恰好等价于大 VLEN，在 riscv64 上则改变了求和顺序，逐比特比较立刻失败。两个补丁一个管构建期、一个管运行期，共同点是都不再假设“VLEN 由编译器随便定”。可伸缩向量（scalable vector）本来是 RVV 的标准答案，但在需要比特级复现的推理内核里，精确 VLEN 仍然更划算；代价就是这类校验必须跟着最终 llc 选项走，而不是跟着构建变量走。

6.3 周末窗口的分工：AI 栈静默，打包与固件推进

日期：2026-11-09　来源：RuyiAI-Stack 组织、openRuyi 提交列表

三天窗口内，PyTorch 的 RISC-V 分支、tilelang-riscv、llvm-project 的 riscv 分支全部零提交，AI 栈的实质性改动只有 triton-riscv 两笔构建脚本与 buddy-mlir 三笔 VLEN、SPM 相关提交。同期 openRuyi 打包仓十笔、固件仓两版发布，节奏明显更密。

这个分工与两边的发布周期有关：打包与固件按日或按夜出包，任何一个上游版本变化都要跟；AI 栈则在版本窗口之间做结构性调整（插件化、VLEN 校验），不追求每日产出。对关注如意社区的人来说，周一到周五看 AI 栈，周末看发行版与固件，是当前比较省力的读法。
