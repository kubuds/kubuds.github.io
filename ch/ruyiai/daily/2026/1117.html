今日重点：tilelang-riscv 合入 #6，RISC-V 后端默认改走 buddy-opt（11-16）

日期：2026-11-16　来源：PR #6、合并提交 2204c7e

11-16 14:56，tilelang-riscv 合入 #6「RISC-V 后端默认改用 buddy-opt，并补上 BOSC 与 GEMM 两个示例」。22 个文件、+835 −284，两笔提交：11-04 的「把 buddy-opt 选为默认并拆开两套工具链根」，11-13 的「补示例、改文档」。这是该仓自 11-03 合入 #5 之后的第一笔改动，仓里目前仍只有 main 一个分支。

改动的骨架在 toolchain.py（+62 −4）：Buddy 与 LLVM 各自有独立的工具链根目录，TILELANG_RISCV_OPT 可显式覆盖优化器；优化器的选择被写进 RISC-V 的编译缓存键（kernel_cache.py +4）。这一条比表面上的”换默认值”更实用——此前换优化器后仍有命中旧缓存产物的风险，现在缓存键带上优化器，等于把”用哪套工具链”变成可检索的构建维度。

示例补了两类：examples/riscv/gemm 是宿主机上的 FP16 GEMM（gemm.py +47），examples/riscv/bosc 是一套可独立构建的 BOSC INT8 GEMM 固件（build.py +190、launch.c +122、env.sh 与 README）。文档侧改动最大的是 docs/get_started/BuildOnSG2044.md（+55 −178），从分步手工操作改成可移植路径与精简用法。测试同时补齐三份：工具链测试 +126 行、编译缓存测试 +29 行、适配管线测试 +45 行，都在 testing/python/riscv 目录下。

今日重点：triton 与 buddy 同一天动工具链，LLVM 解耦并补回 dump()（11-16）

日期：2026-11-16　来源：triton-riscv PR #123、buddy-mlir PR #1062、triton-riscv PR #115

11-16 18:14，triton-riscv 开出 #123「把后端工具链从 Triton 的 LLVM 里解耦」。问题写在说明里：CPU 后端不往 libtriton.so 里加任何 C++，pass 全部走进程外的 triton-shared-opt，但 add_triton_plugin 仍把 MLIR 库及其 LLVM 链进了 libtriton.so，于是后端工具链只能用 Triton 自己编译时那一个 LLVM。改法是关掉 TRITON_SHARED_BUILD_CPU_BACKEND，新增 llvm-hash.txt 单独钉 LLVM 包：libtriton.so 用与 Triton 源码匹配的 LLVM，triton-shared-opt 随 Triton 构建，buddy-opt／buddy-translate／buddy-llc／opt／llvm-objdump 走 buddy release，彼此只交换文本 IR。RISC-V 的 +v 与 +xsmtime 只有 llc 需要，因此 Triton 依赖的 LLVM 不必再背 RISC-V 补丁。三个文件、+16 −2；llvm-hash.txt 暂钉 nightly/v0.1.4.dev20261103，除 libtriton.so 少一个插件外，构建产物不变。

同一窗口稍晚（11-17 01:23），buddy-mlir 开出 #1062「Build LLVM with dump() support」。LLVM 包用 -DLLVM_ENABLE_ASSERTIONS=OFF 构建，而 MLIR／LLVM 的 dump() 只在开启断言或 LLVM_ENABLE_DUMP 时才定义，下游一旦调用就链接失败。PR 里给了实证：mlir::Operation::dump() 在 nightly/v0.1.4.dev20261103 的包里有，在 nightly/v0.1.4.dev20261113 的包里消失了。Triton 正是这样的下游：开 NDEBUG 时头文件里连声明都没有，不开又链接不上。补丁只加一行 LLVM_ENABLE_DUMP=ON，保住 Release 构建。

两件事指向同一处：buddy 的 LLVM 包已经是 triton-riscv 的默认上游，一个 nightly 换包就能把下游编译卡住。Renovate 的 #115 恰好把依赖钉在 nightly/v0.1.4.dev20261113 上（11-16 21:40 仍有更新），#1062 若不进，这颗钉子就会一直扎着。

三、向量扩展与算子优化

3.1 +zvfbfmin 成了默认特征串里的必需品（11-16）

日期：2026-11-16　来源：PR #117

#117 的说明里有三条边界值得记下来。其一，没有 Zvfbfmin 时，LLVM 对可伸缩 bf16 向量连 load 与 convert 都不降，llc 直接报 Scalarization of scalable vectors is not supported。其二，buddy-mlir 的 lower-vir-to-vector 会保留可伸缩 bf16 向量，并默认假设目标有 Zvfbfmin，所以缺这个扩展时下游会在 llc 阶段整批失败。其三，加上之后转换走 vfwcvtbf16.f.f.v 与 vfncvtbf16.f.f.w，也就是把 bf16 与 fp32 之间的宽窄转换交给向量单元。

项目支持的 RVV 目标（SpacemiT K3、SOPHGO SG2044）都带这个扩展；没有的核可以用 TRITON_RISCV_LLC_FEATURES 覆盖默认特征串。DEFAULT_MARCH 没有动，因为它只驱动 GCC 链接那一步，而 GNU as 2.42 并不认识 zvfbfmin——用 +zvfbfmin 编出来的对象仍然能链上。

六、趋势观察

6.1 工具链边界被重新划：一个 LLVM 不再包打全场

triton-riscv #123 与 buddy-mlir #1062 是同一天的两面。前者把后端工具链从 libtriton.so 里摘出去，用 llvm-hash.txt 单独钉 LLVM；后者补回被 LLVM_ENABLE_ASSERTIONS=OFF 关掉的 dump()。两件事合起来说明 RuyiAI 这条线已经不再假设”一个 LLVM 打天下”：Triton 自带一份、buddy 发行版一份、后端 llc 一份，各管一段，接口收敛到文本 IR。

6.2 编译器选择变成构建维度

tilelang-riscv #6 把 buddy-opt 设为默认，同时把优化器写进缓存键。这比”换个默认值”重要：优化器一旦进入缓存键，同一份 kernel 在不同工具链下的产物就不会互相污染，切换工具链也从”改环境变量试错”变成”明确的构建参数”。示例补上 BOSC 与 GEMM，等于给这条路径配了两个可复现的验收点。

6.3 发行版开始吃 RISC-V 专属扩展

openRuyi 这一周的动作集中在扩展上：Go 回填 Zvk AES，triton 轮子默认带 +zvfbfmin，内核 patchset 与 config 一天内两次刷新。这些都不是通用上游能自动覆盖的部分，必须由发行版与工具链维护者逐项补齐。RVA23 之后，差异化的地方正在从”能不能跑”转向”能不能用到向量与加密扩展”。

6.4 日更信息面继续空转

官方主页不动、ruyiai-daily 断档第九天、外部新闻零命中，本期全部素材来自四个 GitHub 组织的提交与 PR，以及论坛的两篇帖子。这种状态下报告的判断价值主要取决于对提交内容的理解，而不是新闻条数——发行说明为空的 triton 正式版尤其如此，只能回到 tag 指向的提交去读。
