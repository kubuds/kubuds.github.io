今日重点：Buddy Compiler 0.1.3 出正式版，十六笔提交里十笔是 RVV 可伸缩向量化，发布说明只写了服务端 ABI（10-31）

日期：2026-10-31　来源：BUDDY MLIR 0.1.3、v0.1.2 与 v0.1.3 的提交差集、PR #999 rvv-vlen、PR #1003 scalable vector 宽度选择

11-01 07:01（北京时间），buddy-mlir 发布正式版 0.1.3，上一个正式版是 10-25 的 0.1.2，中间隔了五个夜间版。发布说明只展开了一项内容：buddy-server 的新 ABI（#1015），即把按模态各写一套的模型插件句柄收敛成统一接口，外加统一的加载、状态查询、调用、流式与取消路径。

但把 v0.1.2 与 v0.1.3 的提交差集拉出来看，这一版实际装了十六笔提交、一百三十六个文件，其中十笔是 [midend][VIR] 下一整段 RISC-V 向量化工作：

  • #999 引入 (rvv-vlen)，把可伸缩向量长度作为向量化目标属性；
  • #1000 在嵌套循环里统计活跃向量数，作为向量宽度选择的输入；
  • #1002 让可伸缩 strip-mining 循环按 vscale 步进；
  • #1003 为 RVV 选择可伸缩向量宽度；
  • #1004 把带结果的 set_vl 降级成可伸缩向量；
  • #1005 处理 set_vl 中多维动态向量带结果的情形；
  • #1006 新增动态向量行级 vir.shuffle；
  • #1007 统一 vir.load / vir.store 的索引约定；
  • #1008 自动推导索引向量的宽度；
  • #996 新增 vir.from_vector 并减少重结合。

另有二笔同属 VIR 线但不在 [midend] 前缀下：decode attention 的 VIR 方言实现（[frontend][tools]）与 VIR 的 Python 绑定（#1009）。也就是说，十六笔里有十二笔动的是向量方言这一层，而发行说明一个字都没提 RISC-V 或 RVV。

这个落差值得记一笔，因为它改变了「这份栈的 RISC-V 进展在哪里」这个问题的答案。此前几期的判断是：buddy-mlir 的 RISC-V 工作主要走夜间版，正式版被 ABI 重构这类通用工作占住，下游要拿到 RVV 改动只能锚夜间标签。0.1.3 证明这条判断只对了一半——正式版确实把 RVV 那一段收进来了，但版本说明没有跟着更新，看发布页的人会以为 0.1.3 只是一次服务端重构，而实际拿到的是一个可伸缩向量化能力显著前移的版本。

对下游的直接含义是：triton-riscv 在 10-31 13:15 把依赖锚点抬到了 nightly/v0.1.3.dev20261030（PR #91），这个夜间版的日期早于 0.1.3 正式版的出包时间，但两者内容同源（0.1.3 从 10-29 的主分支头部切出），所以 RVV 那十笔已经在下游生效；真正没跟上的是「锚点仍写夜间标签」这件事——按现有的 renovate 节奏，切到 release/v0.1.3 还要再等一轮。

需要克制的是覆盖面：这十笔集中在 VIR 方言的可伸缩向量化，即从 set_vl 到 scalable vector 的降级链路，不是端到端模型性能数据；发布说明里也没有给出任何基准。向量化能力前移是可核实的，能跑多快这一期没有答案。

一、RuyiAI 栈进展（PyTorch / Triton / TileLang RISC-V 适配）

1.1 pytorch：riscv 分支 11-01 凌晨第二次整枝重放，基线仍停在 3afdbd3（11-01）

日期：2026-11-01　来源：pytorch riscv 分支、PR #51 riscv64 本地镜像、PR #44 bytes_to_scalar 修正、开放 PR 列表

11-01 03:00，riscv 分支做了一次整枝重放：分支上二十笔提交的提交时间被统一改写到 03:00:26 至 03:00:27 这一两秒内，作者时间全部保持原样。头提交是 1867c9b8，信息仍是 [SyncBots] Integrate PyTorch at 3afdbd3，而这笔同步提交本身的作者时间是 10-29 12:48——也就是说，这次重放没有换基线，分支仍停在上游 3afdbd3，与 10-29 那次重放落点相同。

与 10-29 那次相比，差别只在形式：上一期是「七日静默后重放 + 同步机器人补一笔依赖缓存修正」，这一期是「三日后再重放一次、内容不动」。分支上的补丁集也没有变化，仍是 Add riscv64 image locally (#51)、Fix bytes_to_scalar for float/complex on RISC-V (#44)、Scope linear cross entropy ULP tolerance to RISC-V (#42)、inductor opinfo blocklist (#50) 以及更早的 CI 与测试容差改动。

这种「基线不动、只改提交时间」的重放通常有两种成因：一是重放到同一基线的不同修补顺序上，用来消掉冲突标记或清理历史；二是自动化任务按周期无条件重放。无论哪种，对本期的内容是零增量，值得记的只有节奏——两周内两次整枝重放，且都没有伴随新的上游同步。

需要留意的仍是那条错位：分发侧的 python-torch-ruyiai（openRuyi #1352）按分支产物构建，分支头部每次重放都会换 SHA，包内锁定的来源落点就得重新对齐；这一期没有看到对齐动作。

11-01 23:00，riscv 分支同样做了一次整枝重放，二十六笔分支自有提交的提交时间被统一改写到 23:00:22 至 23:00:26。头提交是 afdd0982，内容是 [workflows] Push rebased PRs directly and document contribution options（作者时间 10-29 01:59），即上一期记的那笔「取消预演、新增贡献指南」的改动——它仍然是分支头部，本期没有更新的东西压在上面。

分支里与本栈最相关的仍是 A100 那两笔：[RISCV] Lower IME intrinsics to SpacemiT A100 dot instructions (#30) 与 [RISCV] Add A100 HP/SP and pack/unpack lowering with calibrated scheduling (#31)。前者把 IME 内建函数降到 A100 的点积指令，后者补上 HP/SP 两种精度形态的 pack/unpack 降级并带校准后的调度模型；再往下一层是 [AME] Update BOSC AME instructions (#29) 与 [RISCV] Update xtame design (#27)，构成「AME 设计文档 → 指令定义 → 内建函数 → 降级与调度」的完整链路。这条链路服务于矩阵扩展，是 RuyiAI「从 RVV 到 Matrix」叙事在编译器侧的落点。

一处需要下一期复核的不一致：分支上最近一条 [SyncBots] Integrate LLVM at b3b5e33 的作者时间停在 09-29，但把当前头提交与上一期头提交做提交比较，返回的差集里包含 10-30 的上游提交（如 [clang][AST] Don't give NestedNameSpecifier pointer identity in DynTypedNode (#233153)、[libc] Add truncation casts to avoid warnings in file_test.cpp (#237262)）。两者放在一起只有一种解释：这次重放在改写历史的同时把上游基线前移了，而同步机器人的记录没有随之新增一条。同步记录与实际基线脱节，会让「这条分支基于哪个上游」这类判断只能靠比较接口反推，建议后续在分支上补一条显式的基线说明。

开放队列在窗口内有二十四笔更新，规模比上一期大，结构化特征也明显：

最大一簇是 Prometheus v3.13 的模块依赖批次，共十三笔（#1540、#1441、#1547 至 #1557），全部由同一作者按 DAG 顺序分批提交，标题统一为「Add Prometheus v3.13 modules - DAG dependency batch NN」。这种「把一张依赖图切成十几笔按层提交」的做法，在发行版里通常是不得不为之——一次性提交会被审查者要求拆分，而按层拆又能保证每笔可独立构建验证。代价是合入窗口被拉长，任何一层卡住后面的都进不去。

其余是三笔常规版本跟随：#1563 把 Node.js 升到 26.13.0 并改用系统库、#1544 把 firefox 升到 159、#1421 给 qemu 打开一批 GUI 测试用的特性。

六、趋势观察

6.1 正式版的说明与代码差集脱节，RISC-V 进展被藏在提交历史里

0.1.3 这件事的方法论意义大于它本身：一个项目的「对外说明」与「实际装进去的东西」如果长期不一致，外部对它的判断就只能靠提交历史反推。这一期的具体表现是，发布说明只写了服务端 ABI 重构，而十六笔提交里十二笔动的是 VIR 向量层。

这种脱节有惯性代价。对下游而言，判断「要不要升级」需要同时看 release notes、提交差集与依赖锚点三处；对上游而言，真正想被看见的工作没有出现在该出现的页面上——近三个月最成体系的向量化进展，在博客、文档、发行说明三处都没有对应描述。一个以「RVV 到 Matrix」为叙事的栈，把向量化进展写成提交历史里的十行标题，是一种浪费。

更实际的风险在评审侧：如果版本说明只覆盖一部分改动，那么复核者的注意力也会集中在那一部分，另一部分改动在「已经被装进正式版」之后就不再有人回头看了。

6.2 triton-riscv 从「修一笔合一笔」转向「批量提审」，验收侧仍缺位

10-29 那三笔是「80 分钟内连续合入」，本期五笔是「两天内连续开出、尚未合入」。前者说明维护者对明确的缺陷修复有快速通道，后者说明新一批改动还没走到那一步。两种节奏之间的差别不在开发强度，而在评审带宽。

这五笔加上 10-29 的三笔，三周里累积八笔同类修复，全部指向降级路径的信息丢失。这个数量本身是信号：说明这条路径没有建立起系统性的等价性检查，只能靠逐个算子撞、逐个撞完补。而对下游最有价值的一件事——把 FlagGems 那 604 个算子的导出做成每晚跑一次的常驻回归——仍然没有做。PR #56 虽然从 09-16 的停滞里恢复（10-30 20:50 有一次推送，规模已扩展到 156 个新文件、导出条目从 468 到 604），但它仍是开放状态。

只要验收还在 PR 里而不在流水线里，「这批算子能不能在 riscv64 上跑通」这个问题就会反复被推迟。

6.3 发行版侧的月度承诺连续落空，栈级打包仍在 spec 层返工

十月的最后三天里，两条与「分发」直接相关的线同时错过了窗口：ruyi 0.54.0 的「10 月底」口径落空，openRuyi 的 2026.10 版本到 11-02 未发。两条线的代码侧都不算停——openRuyi 在 10-30 还有六笔提交，ruyi 有一笔文档合入——所以卡点在发版流程本身，而不在开发。

与此同时，栈级的三件套 #1350 已经跨过第六周，仍在 spec 规范层面返工。这三件事放在一起，指向同一个结构性问题：这个生态的「把东西做出来」与「把东西发出去」是两套能力，前者在多个仓库同时推进，后者在近两个月里没有一次按期完成。

对 RuyiAI 而言，短期最实际的建议不是催发版，而是把 2.3 里那三处非常规点（buddy-mlir 自带 LLVM、triton 依赖 git、tilelang 需要工具链发现）写成一份打包约定，让 #1350 的复核不必每周重新讨论同一批问题——把往返成本降下来，才谈得上进入月度发行节奏。
