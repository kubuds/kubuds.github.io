今日重点：triton-riscv 合入 Triton 3.9.0 插件化改造，补丁集清零、独立发行包退场（11-05）

日期：2026-11-05　来源：PR #98、提交列表、PR #92

11-05 11:13（北京时间），trdthg 的 PR #98「Bump Triton to main (3.9.0)」合入：5 笔提交、66 个文件、新增 1806 行、删除 3868 行。删除量约为新增量的两倍，这决定了这次改造的性质——它不是在既有分支上再加一层补丁，而是把打补丁这种做法整体删掉。

第一处变化是后端形态。Triton 的 TRITON_PLUGIN_DIRS 机制把 backend/ 装成 triton_shared 后端插件，注册入口点、把 C++ 插件链进 libtriton.so、把 triton-shared-opt 一并复制进包。独立的 triton-riscv 发行包随之消失，代码里的导入统一改走这个插件名。后端自身改为通过 paths.py 查找 buddy-opt、buddy-llc、mir-translate 与 triton-shared-opt；CPU 驱动声明自己仅在没有任何 GPU 后端时才处于活动状态。

第二处变化是补丁集清零。patches/ 目录与施加补丁的脚本全部删除。补丁集此前存在的理由有两个：让 Triton 在没有 NVIDIA/AMD 工具链的环境里构建，以及兜住 LLVM API 的频繁变动。现在 buddy-mlir 的 LLVM 发行版带 NVPTX/AMDGPU 目标与 lld，再把 Triton 的 GPU 依赖路径指向一个 stub 目录，两个理由都不成立，补丁集也就不再有存在价值。

第三处变化是出包路径合并。release.sh 不再组装第二个 wheel：Triton 的插件支持已经把后端与 triton-shared-opt 放进 Triton 的 wheel 里，脚本只剥掉工具、直接 bdist_wheel。Makefile 成为 setup、build、test、lit、clean 的统一入口，test 依赖 lit。

代价写在同一个 PR 的提交说明里。Triton 3.9 的前端会从后端读取 backend_name 等字段，缺了它每个 tl.atomic_* 调用都会抛 AttributeError，riscv64 上有 383 个 FlagGems 用例因此失败。这次补上 backend_name、default_dot_input_precision 与 deprecated_fp8_dot_operand_dtypes 三个字段，失败面才收掉。示例侧也有让步：上游拒收了 asin/acos/atan/atan2 的前端补丁，例子改用 libdevice，靠它降到同样的 __nv_* extern_elementwise，再由 triton-shared 转成 MLIR math 算子。

同一路径上的 PR #92「Rebase integration onto the official Triton v3.8.0 release」当日以未合并关闭。上一期记录的两条路线之争（#92 求稳到 3.8.0、#98 跟进 3.9.0 主线）至此收敛到后者。

一、RuyiAI 栈进展（PyTorch / Triton / TileLang RISC-V 适配）

1.1 triton-riscv：构建入口收敛到 Makefile，后端按插件目录装进 Triton 包（11-05）

日期：2026-11-05　来源：提交列表、PR #98

后端在 Triton 包内的导入路径是 triton.backends.triton_shared。这套东西的安装面比之前窄：不再有两个发行包，也不再假设旁边有一份 buddy-mlir 检出。文档里关于“两个包”的叙述、补丁步骤与同级检出假设一并删除，setup.py 里 shutil.which("lit") 会优先取 pip 安装的 lit 控制台脚本，而不是 LLVM 发行版自带的那个。后者调用 main() 时没有 if __name__ == "__main__" 保护，而 Python 3.14 的 forkserver 多进程在导入主模块时会重跑它，lit 目标在 80 并发下因此失败。

后端查找本地工具的路径也改了：buddy-opt、buddy-llc、mir-translate、triton-shared-opt 统一由 paths.py 解析。CPU 驱动的活动判定是“没有 GPU 后端在场”，这与之前靠环境变量判断的做法不同，在多后端共存的机器上行为更可预期。

1.2 triton-riscv：发版节奏改为每日 nightly、周末 release，pytest 并发定在 16（11-05）

日期：2026-11-05　来源：PR #99、Release 列表

PR #99 把发版节奏对齐 buddy-mlir：夜间任务发布 nightly/<date>-<sha> 预发布，周末任务发布 release/<date>-<sha> 并标记为最新版本；没有新提交时跳过，release 在所有 wheel 上传完成前保持草稿状态，workflow_dispatch 提供一次带外的 dev/patch 选择。当日两笔夜间版已按此节奏产出：nightly/20261105-48bde12（19:50）与 nightly/20261105-849a180（22:48）。

测试侧把 pytest 套件改成 16 进程。选这个数字有实测依据：在 207 个用例的切片上，1 进程 360 秒、8 进程 89 秒、16 进程 67 秒、24 进程 67 秒，32 与 64 反而更慢——单个用例是“编译、triton-shared-opt、llc、执行、比对”的串行链，进程再多就争用共享编译缓存。此前串行跑时，flaggems 套件要 1 小时 14 分。setup.sh 会安装 pytest-xdist，可用 PYTEST_WORKERS 覆盖。

1.3 triton-riscv：stable ABI wheel 覆盖 3.12 至 3.15，修 manylinux 工具链探测（11-05）

日期：2026-11-05　来源：PR #100、PR #101

PR #100 按上游 Triton 的 cp312-abi3 做法构建 wheel：scripts/env.sh 与 scripts/release.sh 设置 TRITON_STABLE_ABI=ON，用受限 API（Py_LIMITED_API=0x030C0000）编译 nanobind，setup.py 把 wheel 标记为 cp312-abi3。一个 wheel 覆盖 3.12 之后的所有解释器（3.12/3.13/3.14/3.15），发布矩阵从三个 Python 减到一个。源码保持未打补丁——上游本身就提供这个开关。

同一分支还修了两处构建脚本问题。其一是 release.sh 硬编码 /opt/rh/gcc-toolset-14/enable 且在 dnf install clang 之前检查它，而 manylinux 镜像是滚动更新的 :latest，当时已经带 gcc-toolset-15，导致启用脚本从不执行，clang 找不到 crtbeginS.o、-lstdc++、-lgcc（riscv64）与 libstdc++ 的 <version> 头（x64），两个架构都构建失败；现在先装 clang，再按存在性启用全部工具链、最新的放最后。其二是只有一个 abi3 wheel 之后，矩阵里 python: ["3.12", "3.13", "3.14"] 只会把同一个 wheel 重复构建三遍。PR #101 当日开出、仍未合并，处理发布工作流在检出清理阶段的失败。

三、向量扩展与算子优化

3.1 LLVM：六笔 P-ext 与 XTHeadBb 上游 PR 合入，Ztt 矩阵扩展 v0.6 初版落地（11-05）

日期：2026-11-05　来源：080 期文稿、LLVM PR 235306、LLVM PR 237815

080 期列出的上游合入共六笔，集中在打包 SIMD 与位操作：P 扩展把更多 pm*add* 加后续加法的模式合成 pm*adda* 类指令（#235306），改进 RV32 上 64 位 funnel shift 的代码生成（#235245），新增带扩宽水平加法的打包乘累加 intrinsics（#234450），并为 Clang 补上打包字节水平乘累加 intrinsics 的有符号、无符号与混合符号三种形式（#234484）；GlobalISel 侧在 XTHeadBb 下先扩宽窄类型的 G_CTLZ_ZERO_POISON（#237815）、把 G_CTTZ 扩宽到 XLEN 后再走 G_CTLZ 以选出 th.ff1（#238214）。

RuyiSDK 的 LLVM 分支另有两笔：基于 Ztt 规范与 intrinsics 文档 v0.6 初步支持 RV32/RV64 矩阵扩展，涵盖汇编与反汇编、Clang 类型与 intrinsics、LLVM IR 与代码生成，以及 M/ACC 寄存器分配、拷贝与溢出处理（#169）；为 AME 分支增加 GitHub Actions CI，自动构建 RISC-V 目标的 LLVM/Clang 并跑 CodeGen、汇编与语义测试（#170）。

3.2 GCC：Zba/Zbs/Zbkb 三项优化进入主线，启动 SPEC CPU 2026 评测准备（11-05）

日期：2026-11-05　来源：080 期文稿、GCC Zba 提交

三项 RISC-V 后端优化已于 10 月 27 日进入 GCC 开发主线（r17-5638 至 r17-5640）：Zba 侧完善移位加法与整数除法、取余的组合识别；Zbs 侧利用 bclr 自身的移位索引语义消掉多余掩码计算，改进 RV32/RV64 位图操作；Zbkb 侧修正 packh 的成本模型与匹配优先级，解决 Zbb 与 Zbkb 同时启用时选不到更优指令的问题。

配套的工具链 CI 也有进展：RISE-CI 打通了 Hertner 容器服务与 GitHub Actions，新增 multilib 构建场景检查，后续计划接入 LLM 对 CI 报错做评估与分析。性能侧启动基于 SPEC CPU 2026 的 RISC-V 真实硬件评测准备，已识别出候选 K3 平台跑完整 SPECspeed 2026 的内存瓶颈，正在评估其他硬件方案。

四、Buddy Compiler 动态

4.1 runtime 新增共享 serving 生成控制器，支撑设备侧取词（11-05）

日期：2026-11-05　来源：PR #1018、提交 c2fd2e1

PR #1018 新增一个与模型无关的 serving 生成控制器，18 个文件、新增 2045 行，让运行时适配器共享同一套生成 token 预算、停止条件、用量记账与流式清理。调用方既可以走 LLMSession 的宿主采样，也可以走设备侧直接给出 token 的 token 源。

实现上有几处值得记：字符串停止条件先按原始字节匹配、再做 UTF-8 解码，避免多字节边界误判；token 预算把首个预测与 EOS/停止 token 都计入；固定随机种子支持零值；重复惩罚在请求的历史窗口内按 token ID 去重后各施加一次。首个 token 来自 prefill，因此吞吐统计把首次选择记到 prefill、后续选择记到 decode，零 decode 工作时报告零吞吐。原有 CLI 与服务端入口的生成路径保持不变，用固定 logits 与生产环境的 DeepSeek 分词器、采样器做黄金测试保护输出。后续适配器接入分别跟踪在 DeepSeek R1（#1021）、Llama 3.1 TTNN（#1022）与 Qwen3-VL 等条目上。

4.2 VIR 可伸缩向量 lowering 补片：广播改走 vector<[2]xT>、内核按 llc 选项降级（11-05）

日期：2026-11-05　来源：PR #1030、PR #1031

两笔 midend 改动都针对可伸缩向量。vir.shuffle 的 lowering 拆成若干段：广播先经 vector<[2]xT> 再取前半（vector.scalable.extract）得到 vector<[1]xT>，因为直接对 vector<[1]xT> 做 vector.broadcast 时 LLVM 会生成掩码 [0] 的 shufflevector，被 createOrFold 当成恒等操作折叠掉，剩下的 vscale-1 个 lane 全是 poison；llc 会把 insertelement 变成只写 lane 0 的 vfmv.s.f，一旦这个值不并入 .vf 指令而是存进寄存器，结果就错了。改走 [2]xT 后 llc 用 vfmv.v.f 在 [1]xT 的 LMUL 上完成广播，指令数不增，循环里还少一条。另一笔让内核按 llc 的 -mattr 等选项降级，测试 vir-broadcast-scalable-one.mlir 覆盖剥离与 set_vl 带结果两条路径。

六、趋势观察

6.1 从维护分支到寄居上游：插件化把补丁成本换成版本绑定

日期：2026-11-05　来源：PR #98、PR #92

triton-riscv 用一天时间把自己从“维护一份打了补丁的 Triton 分支”改成“上游 Triton 的一个插件”，净删两千余行，补丁目录整个消失。这种做法的收益很直接：以后跟随上游升版不再需要重放补丁，出包只剩一个 wheel，安装面从两个发行包降到一个。

代价同样明确，而且是同一天暴露的：Triton 3.9 的前端从后端读一个 backend_name 字段，缺它就有 383 个 FlagGems 用例失败。寄生在上游扩展点意味着上游前端的隐式契约变成了必须满足的接口，而这些契约往往没有文档，只能在测试里撞出来。判断这次改造是否成功，不看今天删了多少行，看下一次上游升版时重放的成本，以及 FlagGems 这类下游套件是否还需要专人盯版本。

6.2 打包侧的桌面办公补缺与 AI 栈的静默并行

日期：2026-11-05　来源：openRuyi 提交列表、RuyiAI-Stack 组织

openRuyi 单日四十一笔提交，三十七笔落在 LibreOffice 的依赖链上：先是二十一个文档导入过滤器，再是 AFDKO 字体工具链，接着是 Firebird、PDFium、ZXing、SANE、Box2D 的在审 PR。这不是零散更新，而是按组件分批推进一次桌面办公套件的完整打包。

同一天，RuyiAI 栈除 triton-riscv 外全部静默：pytorch 的 RISC-V 分支零提交、tilelang-riscv 零提交、llvm-project 的 riscv 分支零提交。两条线由不同的人、不同的仓库、不同的节奏推进，日报层面值得分开看，不必把打包侧的活跃当作 AI 栈的进展。

6.3 080 期的增量落在编译器与运行时，不在应用层前端

日期：2026-11-05　来源：080 期文稿

080 期最实的四条都在底层：GCC 三项 Zb* 优化进主线、LLVM 六笔 P-ext 与 XTHeadBb 合入、OpenJDK 的 JEP 544 AOT 移植合入、V8 的向量尾部与 VLEN 处理。应用层前端（PyTorch、TileLang）本期没有对应的能力接入。

这个分布与 6.1 指向同一件事：这一阶段的推进重点是让已有的算子与语言运行时在 RISC-V 上稳定跑通、跑对，而不是扩大前端覆盖面。对下游使用者来说，短期内可感知的变化会出现在编译产物与 JDK 行为上，而不是新框架支持列表里。
