今日重点：IREE 主干落下 RVV f16 乘加 MMA，LLVM riscv 分支八日静默后换基重写

日期：2026-10-21　来源：IREE 提交 e7490c3b、IREE PR #25000、LLVM riscv 分支提交列表、两轮头部对比

IREE 在 10-21 16:48 把 RISC-V V 的 f16 inner_tiled MMA 下降并入主干（PR #25000，946 行改动，其中测试 800 余行）。这是 10-19 发布的 v3.13.0 里 f32 vfmacc.vf 那条路径之后的第二级精度：原生 f16 枚举已在前序提交落主干，本次补上下降与加宽两条通路——f16 乘 f16 得 f16 走 vfmacc.vf，f16 乘 f16 得 f32 走 vfwmacc.vf；只有 +zvfhmin 时分别退化为「累加器扩到 f32 做 vfmacc 再截回」与「两面板扩到 f32 做 vfmacc」。Tile N 取 vlen/8，VLEN=256 下代价模型把三条路径分别计为 14、7、6。

性能数据给出了比「已支持」更有用的信息：在 X60（VLEN=256）上，单线程 inner_tiled 在原生 f16 与 vfwmacc 两种编码下已经快于 mmt4d ukernel；4 线程与 8 线程的大形状仍然偏慢。也就是说单核上的指令选择已经到位，剩下的差距在分块与线程化，这条跟踪项是 #24932。

同一天 RuyiAI 自己的 LLVM 分支结束了八日静默。昨日报告把「LLVM 分支是否随新上游基线重启」列为观察点，本窗口给出了答案：riscv 分支于 10-21 23:00 整枝重写，head 由 0fb2da86 变为 dd05e5b5，SyncBots 把上游集成推进到 b3b5e33，与旧 head 对比为 diverged（领先 1769、落后 26、300 文件差异）。分支内的补丁序列完整保留：BOSC AME 扩展（#16）、Buckyball 厂商扩展（#20）、与 Pebble 核 ISA 对齐（#23）、AME 路径设计（#24）、xtame 设计更新（#27）、AME 指令更新（#29）、IME 内建到 SpacemiT A100 dot 指令（#30）、A100 HP/SP 与 pack/unpack 调度（#31、#32）。结论要说清楚：这是一次换基重放，不是新补丁；两笔 FPGA PR（#25、#28）在 10-22 00:59 同批刷新了时间戳，仍停在开放状态。

把两件事并排放，今日的信息是「上游在往前走、本地在等评审」：IREE 侧 f32 到 f16 的精度台阶两天走完一级，RuyiAI 侧的编译器补丁则靠换基维持可用，评审队列的消化速度仍是这条链路的实际节拍器。

三、向量扩展与算子优化

3.1 IREE：RVV f16 vfmacc 与 vfwmacc 及 Zvfhmin 回退落主干（10-21）

日期：2026-10-21　来源：提交 e7490c3b、PR #25000、性能跟踪 #24932、f32 版本 PR #24933

本次提交为 RISC-V V 的 f16 inner_tiled MMA 补上下降路径，复用 #24933 引入的 lowerRiscvVFmaccLike 与上提的累加器合法化，Tile N 取 vlen/8。编码选择按扩展可用性分三层：f16 乘 f16 得 f16 且带 +zvfh 时用 vfmacc.vf；f16 乘 f16 得 f32 时用加宽的 vfwmacc.vf；只有 +zvfhmin 时两条路径分别走「累加器 extf 到 f32、f32 vfmacc、truncf 回」与「两面板 extf 后 f32 vfmacc」。当两层都合法时按枚举先后取原生路径。VLEN=256 下代价模型给出 intrinsics_m 14（原生）、7（vfwmacc）、6（两条 zvfhmin 回退）。

性能侧只给了一个方向性结论：X60（VLEN=256）上单线程 inner_tiled 在原生 f16 与 vfwmacc 下已快于 mmt4d ukernel，4 线程与 8 线程的大形状仍偏慢。测试随提交落地，含 187 行编码物化用例、414 行下降用例与 e2e matmul 的构建改动，属可直接回归的覆盖。

3.2 IREE：可伸缩向量的分发分块对齐 base 乘 vscaleMax（10-21）

日期：2026-10-21　来源：提交 9ea0f2f2、PR #24849

LLVMCPU 后端同日另有一笔可伸缩向量相关改动：把可伸缩向量的分发 tile 对齐到 base * vscaleMax。这类对齐是 VLA（长度无关向量）路径上的常规合法化——分块尺寸必须能被硬件实际 VLEN 的整数倍整除，否则窄 VLEN 硬件上会出现尾块退化。该改动与 3.1 的 f16 MMA 同属 CPU 后端，两者共同构成 RISC-V V 在 IREE 里的当期进度。

六、趋势观察

6.1 依赖闭包进入收口期：Go 从「去 vendor」转向「补导入路径」

前三期的补包线索是分头铺开的：Python 补 fsspec 云存储全家、Rust 补 crate 闭包、Go 起步去 vendor。本期 Go 侧 51 笔的重心明显后移——先补基础依赖（etree、yaml、gnostic、tabwriter 等十笔），再补 k8s 三件套与 moby-sys、smarty-assertions 的导入路径，最后才落 sonobuoy、umoci、go-mtree 三笔真正的「build without vendored dependencies」。

顺序本身说明去 vendor 的完成条件不是删掉 vendor 目录，而是让每个被依赖模块在发行版里能按原导入路径解析；缺了导入路径的补齐，删 vendor 只会直接编译失败。因此「补导入路径」才是这一轮的最后一公里。对 RISC-V 用户的直接含义是：容器镜像工具与一致性测试工具从「随源码打包」变成「按发行版依赖打包」，构建可复现性与安全更新的传导路径同时改善，后续 CVE 只需升级单个 Go 模块，不必重建整包。

6.2 两个 riscv 分支同日整枝重写：重放已成常态运维，评审仍是瓶颈

本期 pytorch 与 llvm-project 的 riscv 分支在同一天各做了一次整枝重写：pytorch 在 03:00（连续第三日），llvm 在 23:00（八日静默后换基）。共同特征是提交者时间统一改写、补丁标题集合不变、SHA 每日失效；差异在节奏——pytorch 是日更基线，llvm 是择期换基，换基后与旧 head 的差异达 300 文件，几乎全部来自新上游。

这种做法的工程意义是把「跟上游」与「维护本地补丁」解耦，代价是历史不可追溯。任何按 SHA 引用的下游（镜像构建、CI 缓存、issue 复现）都会每天或每次换基后失效，读这两个分支应以补丁标题集合而非 SHA 作版本判据。更值得注意的是本窗口补丁本身没有新增：pytorch 七笔开放 PR 只刷新时间戳，llvm 两笔 FPGA PR 同样只刷新时间戳。重放机制已经稳固，实际节拍器变成了评审队列的消化速度。

6.3 RVV 后端先补 f16 再谈吞吐：IREE 的精度覆盖次序给出的信号

把 10-19 的 f32 vfmacc.vf（v3.13.0）与 10-21 的 f16 vfmacc/vfwmacc（#25000）连起来看，IREE 在 RISC-V V 的 inner_tiled MMA 路径上两天走完一级精度台阶，且两次都复用同一个 lowerRiscvVFmaccLike 与同一套累加器合法化。次序是先保证有正确路径（f32），再按扩展可用性挑最快的一条（f16 原生、f16 加宽、+zvfhmin 回退），代价模型对三条路径分别定价。

X60 上的实测把瓶颈位置说清楚了：单线程已快于 mmt4d ukernel，4 线程与 8 线程仍慢，说明单核指令选择到位之后，剩下的是分块与线程化。对 tilelang-riscv 与 triton-riscv 来说，这是可逐条对照的路线图——Tile N = vlen/8 的取法与代价模型的分档方式，都值得在自家 lowering 里做同口径比较，而不是只看「是否支持 f16」。
