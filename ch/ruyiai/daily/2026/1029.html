今日重点：K3 解码注意力搬上 VIR，性能与手写 RVV 内核持平（10-28）

日期：2026-10-28　来源：buddy-mlir PR #1014、K3 文档、triton-riscv PR #91、llvm-project 重基工作流

本期最实质的一步发生在 09:36：buddy-mlir 的 #1014「K3: write the decode attention in the VIR dialect」合入（4 个文件、+476/−14），把 K3 w4g32 内核的解码注意力整段搬到 VIR 方言上。这不是又一次方言能力补齐，而是第一次拿真实模型的内核去做对账——一边是此前手工写的 RVV 向量内核，一边是用 Python 拼出来的 VIR 内核，比数值、比指令数、比板上的吞吐。

做法可以拆成四层。构造层不再手工拼算子、手工拼类型（此前要在字符串里写算子名与类型描述），改走 buddy_mlir.dialects.vir 的 SetVLOp、load、shuffle、fma、reduce；一个 work item 就是一段 vir.set_vl 区域，长度取头维的一半（64 lanes），每个头是一个由 RoPE 两半拼成的可伸缩向量，区域返回该头的 (max, sum)。旋转层把 q 在区域内加载、旋转、缩放，rotate_half 落成一条 vir.shuffle，cos/sin 存成两行等长数据，于是不再需要 vir.from_vector。内存视图层用 memref.expand_shape 把 q、KV cache、输出和 q 的归一化权重按最后一维切成 2×64。归一化层（Qwen3 的 q/k norm）单独开一段一维 vir.set_vl 区域，按 _head_rmsnorm 的做法对两半求平方和。

流水线参数也跟着改了：内核降级从 vector-width=128 换成 rvv-vlen=1024、use-scalable=false，向量尺寸由分析按 A100 的寄存器定，因为区域里有 vir.shuffle，每个头保持为一个 128 个 f32 的向量组（LMUL 4）。作者在 PR 里写得很直白：切到 use-scalable=true 是下一笔的事。旧的 _attn_decode_fn 保留，A210 内核的解码注意力还在用它。

结果三项都硬。数值上，带与不带 q/k 归一化，都与 _attn_decode_fn 位级一致；机器码上，两个并行体各 178 条向量指令，键值循环与旧版指令相同，只有两处溢出寄存器的重载位置换了；板上吞吐（K3、buddy-cli 贪心解码、三轮交替、9 对生成文本完全一致）三档全部落在同一区间——63 token 后 28.26~28.49 对 28.10~28.58，458 token 后 26.82~27.13 对 27.02~27.04，900 token 后 25.37~25.41 对 25.29~25.77。作者自己注明：同一份代码两次构建的差异可达 2%，区间是重叠的。

同日另有两笔与这条主线配套。一是 llvm-project 的 riscv 分支补了一份 244 行的自动重基工作流（详见 1.1），把「作者 fork 上的 PR 跟不上基线」这件事从手工搬进 Actions。二是 triton-riscv 的依赖锚点被 renovate 再抬一级到 dev20261028（详见 1.3），但这版夜间构建的出包时间早于当日上午三笔合入，所以即便这笔依赖更新合入，下游也还拿不到 #1014——要用上今天的成果，得等下一版夜间构建。

1.1 llvm-project：不再换基，补上「作者 fork 一键重基」工作流（10-28）

日期：2026-10-28　来源：riscv 分支提交 cf00909d、工作流全文、riscv 分支提交列表

与上一期「五天内第五次整枝重放」不同，本期 riscv 分支的本地补丁集一笔未动：分支头部从 ed439f3e 往前走了一笔，与上一期头部的对比是领先 1 笔、落后 0 笔、只动 1 个文件。这笔新增的提交（cf00909d，作者 23:27、提交 23:54）是纯 CI 资产——.github/workflows/autorebase.yml，+244/−0。

工作流的设计意图写在注释里：安装在作者源仓库的默认分支上，在 Actions 里手工填入目标 PR 号执行，使用源仓库自己的 GITHUB_TOKEN，不需要自定义密钥或标签。触发方式是 workflow_dispatch，两个输入——PR 号（必填）与「只预演不推送」（默认开启）。运行环境 ubuntu-24.04、超时 90 分钟；注释明确要求「绝不在持有写权限的情况下执行 PR 代码、钩子、构建或子模块」，git 配置里把 hooksPath、attributesFile、fsmonitor 全部指到 /dev/null，GIT_TERMINAL_PROMPT=0、GIT_EDITOR=true。冲突处理有专门函数：-Xours 处理不了的场景（含改删冲突）逐个走 ls-files --unmerged，有第 2 阶段就取本地、没有就删除；重基时先判断基线是否已是祖先，能识别「等价补丁」并丢弃重复的旧基线补丁。

这笔要解决的是过去几期反复出现的一个具体成本：分支一天整枝重放一次，作者 fork 上的 PR 立刻落后，靠人工逐个重放既慢又容易把补丁集弄乱。需要说清边界——它重基的是别人的 PR，分支自身每日整枝重放仍需维护者操作；它把「跟随基线」的成本从人工判断降为一次带预演的调度，但并没有自动化的触发条件。真正的价值要等下一个外部 PR 按新基线提交时才能验证。

2.1 openRuyi PR #1350：三笔提交重基，GCC 构建代价量化为 2.81 倍（10-28）

日期：2026-10-28　来源：openRuyi PR #1350、复核评论、PR 提交列表

16:22，RuyiAI 三件套打包 PR 的三笔提交（buddy-mlir、python-triton-ruyiai、python-tilelang-ruyiai）在同一分钟内全部重写，明显是重基到最新主分支；当前规模 9 个文件、+680/−0，与上期记录相比多了 14 行。PR 在 18:15 因复核评论再次刷新，评论总数 13 条，仍未合入。

本期最有信息量的一条来自作者 10:41 的回复。上一期的口径是「可以用 GCC 替代，但构建时间至少 1.5 倍」；本期给出了实测：在 riscv64 机器上把 buddy-mlir 的构建从 LLVM 换成 GCC，时间从 8814 秒变成 24798 秒（约 2 小时 27 分对 6 小时 53 分），2.81 倍，且那次用 GCC 的构建在链接阶段失败、没有跑完。

这条把争论从立场问题变成了成本问题。「是否把 buddy-mlir 自带的 LLVM 外置」原本是两条技术路线之争，现在有了发行版构建农场能看懂的数字：2.81 倍意味着排期、机器占用与超时策略都要重算。作者的另一条理由也因此更站得住——buddy-mlir 用到的 LLVM 只在自己包内使用，且这些包都锁定了具体的 LLVM 提交，留在包内才可复现。同时他也说明 triton 上游的 setup.py 有强制检查 git 是否可执行，所以要么加 git 构建依赖，要么打补丁改 setup.py（后者会随 triton 升级而失效）。

3.2 向量宽度口径：VIR 侧定为 1024 位、单头一个 LMUL 4 组（10-28）

日期：2026-10-28　来源：buddy-mlir PR #1014、llvm riscv 分支提交 1811501f、提交 ed439f3e

六、趋势观察

6.1 从「能表达」到「跑得一样快」：VIR 第一次拿真实模型内核做性能对账

过去三期这条主线一直在补表达力：10-26 一夜七笔把可伸缩向量补进来，10-27 补上 Python 绑定，10-28 直接把 K3 的解码注意力整段搬过去，并且拿板上吞吐做了对账。三个数字合起来才是这次的意义——数值位级一致、指令数相同（各 178 条）、吞吐区间重叠。自研方言最容易卡在「能跑但慢」这一关，#1014 至少证明这一关暂时过了。

但要判断这条栈是否真的可替代手写内核，还缺两件事。一是覆盖面：这次只搬了解码注意力，A210 内核仍用旧函数，MoE、量化与预填充路径都还没动；二是可伸缩向量：本期明确关掉了 use-scalable，下一笔打开之后，向量尺寸不再由编译期决定，LMUL 4 的分组假设会松动，届时数值与指令数能不能守住，需要重新对账。在此之前，把「VIR 已追平手写内核」当成结论都过早，准确说法是「在 K3 解码注意力这一段、在固定向量长度下追平」。

6.2 换基的成本从补丁漂移转向治理：工作流接管重基，分支自身仍靠人

同一天里，llvm 的 riscv 分支停止整枝重放，改为补一份 244 行的自动重基工作流。这个转向值得单独记一笔：过去五天的节奏是「一天一次整枝重放、每次重写二十笔提交流」，作者时间不动、committer 时间统一，补丁集本身没有新增功能。这种做法能跟住上游，但代价是外部贡献者的 PR 永远落后一格，谁要提交就得自己重放。

新工作流把这件事做成了「填 PR 号、默认预演、一键推送」的调度，冲突一律取 riscv 侧、重复补丁自动丢弃、绝不执行 PR 代码与构建。它不解决分支自身的每日跟随，但把「跟随基线的成本」从维护者的手工判断里分出来一部分。下一阶段要观察的是外部 PR 是否真的因此变多——如果工作流上线后两周内仍无外部 PR 按新基线提交，那说明瓶颈不在重基工具，而在别处。

6.3 分发层的争论开始有价格：2.81 倍的构建时间比「偏好」更有说服力

#1350 争论了将近一个月，核心分歧是 buddy-mlir 自带的 LLVM 要不要外置。上一期的口径还是「可以用 GCC，但至少 1.5 倍时间」，本期作者给出了实测：riscv64 上 8814 秒变 24798 秒，2.81 倍，且用 GCC 那次链接失败没跑完。争论的性质于是变了——从技术偏好变成构建农场的排期算术。

这条对 RuyiAI 栈的启示不在结论，而在方法：RISC-V 发行版打包的很多分歧（是否 vendor、是否外置工具链、是否随包分发 IR），最终都要落到「构建时间、镜像体积、可复现性」这三个可测的数字上。上一期 openRuyi 收回「随包分发 LLVM IR」的路线，本期 #1350 用 2.81 倍守住「LLVM 留在包内」，两次判断方向相反，但依据是同一类成本核算。接下来的看点是这笔 PR 能否带着这个数字合入——如果不能，说明发行版对构建时长的容忍度低于作者预期，那才是真正需要调整的地方。
