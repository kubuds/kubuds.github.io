今日重点：buddy-mlir 一天七笔 VIR 合入，掩码、bf16、归约与整数矩阵乘逐类接进向量路径（11-12）

日期：2026-11-12　来源：PR #1052、PR #1053、PR #1054、PR #1055、PR #1056、PR #1057、PR #1058

从 11-12 08:12 到 14:44（北京时间），buddy-mlir 主干连续合入七笔中间端改动，编号 #1052 至 #1058，作者都是 zhanghb97。七笔的共同点是把此前只能留在标量循环里的算子形态，逐类接进 VIR 的向量下降路径：i1 掩码、libm-only 数学函数、bf16、fast-math 标志、全部归约种类、rank-0 填充、整数矩阵乘。每笔都带 lit 用例与量化数据，多数还附了在 SG2044、SpacemiT K3 上的实测。

第一笔 #1052 解决的是内存访问的门槛。memref 元素类型为 i1 时，可伸缩向量此前被直接拒绝（提示 a memref of i1 needs fixed vectors），因为 memref 每元素占一字节、i1 向量每位占一车道，只有定长向量有逐车道的下降。Triton 的 load/store 掩码恰好就是 i1 memref：走纯 VIR 管线加可伸缩向量时，325 个 Triton-RISCV 测试文件里 179 个卡在这个错误上。改法是按字节读写——连续访问用 i8 向量的 llvm.load/store，非连续的 strip-mined 区域用 vp.strided.load/store 全车道打开；顺带把 i1 车道按一字节计尺寸，此前首个动态向量为 i1 的区域按 1 位算，VLEN 256 下会得出 vector<[512]xi1> 这种十六组寄存器的规模。

#1053 处理 LLVM 不肯在可伸缩向量上下降的数学函数（erf、erfc、cbrt、powf、atan2、acosh 等），改为逐车道展开：对 vector<[N]xT> 的 N 乘 vscale 条车道逐条 extract、调标量函数、再 insert。诱因是 convert-math-to-libm 对可伸缩向量的处理与定长向量一样，只算前 N 条，其余静默置 0——一个可伸缩 erf 在 VLEN 128（vscale 2）下有一半车道是错的。效果直接体现在测试面：Triton-RISCV 的 FlagGems 套件 4045 项在 SG2044（VLEN 128）上通过数从 3980 升到 4006，修好的 26 项是 test_erf 与 test_gelu，无新增失败。

#1054 是这批里验证做得最重的一笔。RVV 只有带 Zvfbfmin 才把 bf16 放进向量寄存器，没有该扩展时 LLVM 连一次加载都不肯下降（Scalarization of scalable vectors is not supported）。改动给下降器加了 rvv-mattr 参数，默认按有 Zvfbfmin 处理（Buddy 的几个 RVV 目标 K3 的 X100 与 A100、SG2044 都有）；显式给 -zvfbfmin 时改为按整数位处理，把 bf16 向量当 i16 向量读写、extf 与 truncf 用整数运算（truncf 按就近取偶）、absf 与 negf 走符号位。两条路径在 SG2044 与 K3 两块核上逐输入比对：truncf 覆盖全部 2^32 个 f32，extf、absf、negf 及 extf-mulf-truncf 覆盖全部 2^16 个 bf16，结果逐位相同。

#1055 修的是 fast-math 标志在 strip-mined 下降里被丢掉：一个带 contract 的 arith.mulf 加 arith.addf 被重建成普通 fmul 与 fadd，LLVM 不会融合。现在标志随同种算子传递到向量循环与尾部，f32 乘加能出 vfmacc，bf16 在 +zvfbfwma 下出 vfwmaccbf16；作者在 K3 的 X100 与 A100 上以 4M 车道逐位比对 fmaf 展开，结果一致。这一笔是七笔里唯一直接改指令选择的。

#1056 把 vir.reduce 从只认浮点的 add 与 maxnum，扩到 vector.reduction 的全部种类：add、mul、minsi、minui、maxsi、maxui、and、or、xor、minnumf、maxnumf、minimumf、maximumf，整数一并支持，并由 verifier 校验 kind 与元素类型是否匹配。此前 Triton 的整数求和、min/max、乘积、all/any（以及依赖它们的 argmin、argmax、count_nonzero、双调排序与基数排序）都留在循环里。改动新增 570 行、涉及 9 个文件，标量尾用 vector::makeArithReduction 的合并器，vector<[1]xT> 走昨日 #1051 的 LLVM intrinsic 路径。

#1057 与 #1058 收尾两类残留。#1057 把 rank-0 memref 的 linalg.fill（多数是归约的累加器）降成一次 memref.store，FlagGems 1811 个 kernel 里残留的 linalg.fill 从 393 降到 0。#1058 让整数矩阵乘也能下降：A、B 为同一整数类型且不宽于 C 时先做符号或零扩展再乘加（不带 fma），RVV 上 int8 矩阵乘得到 vsext.vf2 加 vwmacc.vx，无符号则是 vzext.vf2 加 vwmaccu.vx；同笔还修掉动态形状 matmul 的断言失败——M 与 K 原本在 vir.set_vl 区域内取，被后续 pass 在使用中擦除。改完 1811 个 kernel 里已无 linalg.matmul（此前 2 个，即 int8 那个）。

今日重点：triton-riscv 收下 BOSCAME FPGA 的 SPM 路径，另有 wheel 减重四成与显式目标改走 -O3 的开放 PR（11-12）

日期：2026-11-12　来源：PR #104 BOSCAME FPGA、PR #116 wheel 瘦身、PR #117 显式目标 -O3

#104 在 17:40（北京时间）合入，把 BOSCAME FPGA 的 SPM 路径接进 triton-riscv：AOT 契约导出、lit 与集成测试、examples/BOSCAMEFPGA 下的 kernel、launch 与 makefile，入口文档是 docs/BoscameAOT.md 与示例 README。buddy-hash.txt 的首行钉住落地 SPM 的那笔 buddy-mlir 提交，保证示例与编译器版本对得上。作者 caihanyi111 在 11-09 提的这笔，自测只做到格式与 lint，完整构建留给 CI 的 x64 与 riscv64 两侧。

同日还有两笔开放的工程改动，方向都是发布物本身。#116 指出 wheel 里打进去的 LLVM 与 buddy 工具此前用 –strip-unneeded，调试段仍保留：triton-shared-opt 单个带九个 .debug 段、体积 407 MB；改 –strip-all 后降到 118 MB，七个工具合计载荷从约 970 MB 降到约 576 MB，约为原体积的六成。作者同时记了一个被否掉的方案——把 bin/llc 直接指向 buddy-llc（它就是 LLVM llc 加 buddy 补丁），但 buddy-llc 写完输出后不退出，无法替代非 IME 路径调用的普通 llc。

#117 改的是交叉编译路径的优化级别：显式给 RISC-V 目标三元组（交叉编译，或在 RISC-V 宿主上打开交叉编译开关）时，构建流程此前跳过 LLVM 中端，llc 用默认优化级别，MLIR 留在标量形式的循环到了目标文件里仍是标量。改动对这类构建先跑 opt -O3 与 llc -O3，三元组与 features 与 llc 一致；不带三元组的原生 RISC-V 路径（llc -O0，源码注释记着更高级别下有错编译）与 IME 路径（走 buddy-llc）不动。同一笔还把 +zvfbfmin 加进默认 llc features——否则可伸缩 bf16 在 llc 里直接中止，而 buddy-mlir 的 #1054 正是默认假设有该扩展，两边必须同步。

三、向量扩展与算子优化

3.1 i1 掩码按字节读写，此前 325 个测试文件里 179 个卡在这一条（11-12）

日期：2026-11-12　来源：PR #1052

i1 的可伸缩向量访问此前只有定长向量的逐车道下降，于是 memref 元素为 i1 的 load/store 被直接拒绝，而 Triton 的掩码正是 i1 memref。走纯 VIR 管线时 325 个测试文件有 179 个因此失败——这是整批七笔里影响面最广的一笔。

下降现在按字节做：连续访问用 i8 向量的 llvm.load/store，非连续且落在 strip-mined 区域时用 vp.strided.load/store（掩码全开、长度给足）。另有一处尺寸修正：区域内首个动态向量为 i1 时，此前按 1 位算元素宽度，VLEN 256 下得出 vector<[512]xi1>，读成字节就是十六组寄存器；现在 i1 车道按一字节计。

3.2 bf16 在无 Zvfbfmin 时降到整数位运算，两条路径逐输入比对（11-12）

日期：2026-11-12　来源：PR #1054

bf16 这条路原来只有”有 Zvfbfmin”一种可能，没有该扩展时 LLVM 对可伸缩 bf16 连加载都不下降。改动把 rvv-mattr 作为参数交给下降器，默认假设有 Zvfbfmin（K3 的 X100 与 A100、SG2044 都有）；给 -zvfbfmin 时改走整数位：bf16 向量按 i16 读写，extf 与 truncf 用整数运算，absf 与 negf 动符号位，NaN 取规范值。

验证方式是逐输入穷举：truncf 跑全部 2^32 个 f32，extf、absf、negf 以及 extf-mulf-truncf 跑全部 2^16 个 bf16，在 SG2044 与 K3 两块核上与 Zvfbfmin 路径逐位比对。f8 类型或（无 Zvfbfmin 时）bf16 出现在其他算子、非整数内存空间的 memref 里，则退回定长向量下降。

3.3 归约收全所有 kind，int8 矩阵乘出 vwmacc.vx（11-12）

日期：2026-11-12　来源：PR #1056、PR #1058

vir.reduce 原先只认浮点的 add 与 maxnum，整数求和、min/max、乘积、all/any 全部留在循环里。现在它接受整数与浮点以及 vector.reduction 的全部种类，verifier 校验 kind 与元素类型是否匹配，标量尾用合并器逐元素收尾。整数与 min/max 归约是精确的，浮点求和与乘积除 reassoc 外仍保持有序。

整数矩阵乘同样补上：A、B 同一整数类型且不宽于 C 时先扩展再乘加，RVV 上 int8 得到 vsext.vf2 与 vwmacc.vx（无符号是 vzext.vf2 与 vwmaccu.vx）。同笔修掉动态形状 matmul 的断言失败——M 与 K 在 vir.set_vl 区域内取，后续 pass 在使用中擦除，报 “expected that op has no uses”。

3.4 测试面三组数字：3980 升到 4006、393 降到 0、2 降到 0（11-12）

日期：2026-11-12　来源：PR #1053、PR #1057、PR #1058

三笔改动各给了一组可复核的量化结果，口径都是 Triton-RISCV 的 FlagGems 套件：数学函数那笔在 SG2044（VLEN 128）上把 4045 项测试的通过数从 3980 提到 4006，修好的 26 项是 test_erf 与 test_gelu；rank-0 填充那笔把 1811 个 kernel 里残留的 linalg.fill 从 393 降到 0；整数矩阵乘那笔把残留的 linalg.matmul 从 2 降到 0。

三组数字放在一起说明一件事：VIR 作为唯一管线，已经不是”能不能跑通”的阶段，而是在收敛”哪些算子仍留在 linalg 或标量形式”。

六、趋势观察

6.1 这一天补的是形状覆盖，不是性能

七笔里只有 #1055（fast-math 标志）直接改变指令选择，其余六笔做的是把此前留在循环里的形态接进向量路径：i1 掩码、libm-only 数学函数、bf16、归约种类、rank-0 填充、整数矩阵乘。评价这类改动的口径应当是”还剩多少 linalg 或标量路径”，而不是跑分——393 降到 0、2 降到 0、179 个失败文件归零，都是这个口径。

对照昨天 #1050 的 strip-mined 余量降宽，可以看出两天的分工：先让向量循环吃满车道（性能），再让所有算子都能进向量循环（覆盖）。顺序反过来会做无用功。

6.2 数值验证已到穷举输入的量级

#1054 对 truncf 跑了全部 2^32 个 f32、对转换与符号运算跑了全部 2^16 个 bf16；#1055 在 4M 车道上逐位比对 fmaf 展开。这种验证成本说明 bf16 已经按出货路径对待，而不是”有空再说”的优化项。

与之呼应的是 11-02 那篇讨论 LLVM 在 RISC-V 上自动向量化 bf16/fp16 时静默降级的论文——同一个风险点：结果错了但不报错。这批 PR 的验证方式，正是对这类静默错误的正面回应。

6.3 发布物本身成了工程指标

同一天里三处与”发出去的东西”有关的改动：triton-riscv 的 wheel 从约 970 MB 收到约 576 MB（triton-shared-opt 单件 407 MB 到 118 MB）、buddy-mlir 夜间版按批次出包、pytorch 的 CI 判据堵住零用例通过的假绿。RISC-V 用户下载一个 wheel 的成本远高于 x86，发布物的大小与可信度正在成为与功能并列的指标。
