今日重点：ruyi 修复跨软件源安装状态问题，RuyiSDK 0.53 定于今日发布

日期：2026-09-23　来源：修复 PR #502、问题 #501

北京时间 09-23 09:01，ruyi 包管理器把「Fix installation state managemet across repos」合并进 main 分支（合并提交 802dd4d9；修复提交 08fd6aeb，由维护者 xen0n 开发），关闭了社区用户 qingwan12138 于 09-21 报告的 #501 号问题：切换软件源后，已安装的软件包显示为「未安装」，且重新安装被跳过、状态永远无法更新。

问题机制：安装记录以「来源软件源 ID」为键，但安装判重仅按「名称 + 版本」。当同名同版本软件包存在于多个软件源时，用户在源 A 安装后切换到源 B，ruyi list 会因按新源 ID 查询而显示「未安装」；此时重装被「跳过已安装」短路（退出码 0）却不写新源记录；卸载又报「未按安装跟踪」。最终形成「文件在磁盘、状态永远为未安装」的死锁，只能靠 --reinstall 或先卸载恢复。修复将安装状态查询改为按安装身份（类别、名称、版本、宿主）跨源匹配、同身份时优先精确源 ID 记录，并让卸载覆盖所有软件的同一身份记录、顺带清理旧版本 --reinstall 遗留的重复记录；共改动 162 行，其中 117 行为新增回归测试（state.py 与 test_state.py 两个文件）。

该修复已写入同日完成的第 077 期双周报草稿（详见 4.1）：草稿「包管理器」章节写明「RuyiSDK 0.53 将于 2026 年 9 月 24 日发布，对应的包管理器版本也为 0.53.0」，并列出二进制包 ABI 兼容性检测基础设施、默认软件源优先级修复、下载失败镜像回退修复等同批更新。截至窗口末（09-24 04:30），已发布 Release 仍以 0.54.0-alpha.20260918 为最新、v0.53.x 分支停在 0.53.0-beta.20260917，正式版打号与发布公告是今天的首要观察点。

五、趋势观察

5.1 发布周节律：修复即时闭环叠加 0.53 发布与双周报 077

从问题到合并约 36 小时（#501 于 09-21 20:48 报告、09-23 09:01 修复合并），且维护者在合并后约一刻钟内把修复写进双周报的 0.53 更新说明——「报告、修复、发布物」在同一发布周期内完成闭环，是社区响应节奏的直观样本。接下来 24 小时值得核对的观察点：v0.53.x 分支的正式打号与 0.53.0 发布公告是否如期出现；0.53.0 的实际更新清单中该修复是否以 backport 形式落地（当前 v0.53.x 分支仍停在 0.53.0-beta.20260917）。

5.2 支持矩阵的「单板多系统」模式与在审队列

Milk-V Duo S 在三天内从 Arch Linux、Ubuntu 延伸到 Debian、RT-Thread、xv6，加上在审的 Zephyr 与 RT-Thread Smart，单一低成本板卡的操作系统覆盖被系统化铺开；同期 K510、CH32V307、ESP32C3 等边缘与 MCU 级芯片的报告也在滚动更新。对使用者而言，「先查矩阵再选板」的可复现材料密度在提高；对社区而言，此类报告多为新贡献者的练手入口，在审队列长度比单日合并数量更能反映贡献活性。

5.3 框架覆盖的广度扩张与 PyTorch 侧深度等待

RuyiAI-Stack 新入库 mxnet 与 caffe（见 1.4），与既有 pytorch fork 构成三个经典深度学习框架并置；但 PyTorch fork 的 RISC-V 功能线持续静默（riscv 分支无新提交、8 个开放 PR 时间戳不动、RVV 两笔内核支持补丁继续排队）。广度扩张与深度推进出现分化，「宽而浅」的阶段性状态可用 mxnet、caffe 两仓的首批动作来验证下一步走向。

5.4 本窗口的空白与关注点
