今日重点：LLVM fork 合入 XAME，ZTT v0.6 矩阵后端一次进 47 个文件（11-17）

日期：2026-11-17　来源：PR #36、合并提交 542365c

11-17 15:05，RuyiAI 的 llvm-project fork 合入 #36「[RISCV][XAME] Add ZTT v0.6 matrix backend support」。PR 在前一天上午开出，次日走完评审：47 个文件、+4084 −19，其中指令定义 RISCVInstrInfoXAME.td 一项就 1732 行，内建定义 517 行，寄存器信息 120 行，另有一个 262 行的状态处理 pass。这是该 fork 的主干自 11-02 停滞之后的第一笔改动。

合入的是一条完整的矩阵后端路径，不是零散指令：xame 作为本地特性名（0.6 版），把 MLIR 产出的 LLVM IR 里的矩阵与累加器 SSA 值降到 RISC-V 指令；llvm.riscv.ztt.* 内建名与 riscv.ztt.matrix／riscv.ztt.acc 目标类型沿用 ZTT v0.6 的编译器接口，属于临时版附加矩阵扩展（Attached Matrix Extension）的下游实现。文档写明两套固定 profile：默认 +xame 为 8×8、16 个 M 寄存器、8 个 ACC、元素上限 64 位；+xame,+xame-gem5 为 4×4、32 个 M、4 个 ACC、128 位。两者都按 32 位寄存器单元计。

工程量主要在寄存器与调用约定：138 条共享指令编码、矩阵与 ACC 寄存器组、CSR 操作数、按 profile 区分的汇编与反汇编；寄存器分配后新增一遍状态 pass，保证描述符、数据与状态在寄存器拷贝和溢出时不被冲掉。矩阵参数走编译器本地调用约定，不是 RISC-V psABI 标准，调用双方必须约定同一 profile 与寄存器类型，超出寄存器文件的参数会被拒绝，只能走内存。标量重载一律按无符号 XLEN 位型归一化，需要符号解释的前端自行符号扩展。

验收覆盖三处：LLVM RISC-V CodeGen 与 MC 3381/3382 通过，11 个 XAME 专项测试全过，唯一失败是 xboscame-valid.s 的既有基线编码差异（测试期望 ACC 编码 8，而未改动的定义里 ACC0 是 0，BOSCAME 文件本身未动）；外部 Buddy MLIR harness 的 10 个 AME 转换回归全过；4×4 整数矩阵乘（A 取 1 到 16、B 全一）在 AME_gem5 里编译、链接并运行，16 个输出正好是 10、26、42、58 的行和，guest 退出码 0。

今日重点：triton-riscv 修 bf16 转换器 ABI，riscv64 三条 CI 腿首次实机全绿（11-17）

日期：2026-11-17　来源：PR #121、问题 #114

11-17 18:37，triton-riscv 合入 #121「Fix the launcher ABI of the bf16 conversion helpers」，两个文件 +190 −7，主体是 backend/driver.py 里两个 helper 的原型，加一份 166 行的新测试。问题出在寄存器类：launcher 把 __truncsfbf2 与 __extendbfsf2 定义成 uint16_t 整数原型，而 llc 生成的调用点按 bf16 走浮点寄存器——x86-64 用 xmm0、riscv64 用 fa0，调用方从低 16 位取值；整数返回落在 eax／a0，于是每个 fp32 转 bf16 的内核存下去的都是上一次浮点运算的残留，要么零要么垃圾。

修法是把两个 helper 的原型改成 float，让 bf16 位待在浮点返回值低 16 位；__bf16 本身用不了，因为 launcher 由 g++ 编译，而 Ubuntu 24.04 的 g++ 13 在 riscv64 上没有这个类型。__truncdfbf2 与 bf16 libcall 家族其余成员明确列为不改动，当前 lowering 不产生它们。

新测试 python/examples/test_bf16_convert.py 把 fp32 与 bf16 的互转按 torch 的 int16 视图逐位对齐，覆盖 round-to-nearest-even 的四类边界（半值以下、偶数与奇数 lsb 的 tie、半值以上、float32 最大值到无穷），修前其中四例失败；再用重定位断言钉住 libcall 路径——host 目标构建在带 avx512bf16 的 x86 上跳过（那里 llc 原生降 bf16，不走 helper），riscv64 构建则剥掉 +zvfbfmin，逼转换走 launcher，顺带当作裸运行时路径的探针。

验证结果值得记：x86 host 上 #114 的复现内核修复后返回 [-5.0, -0.5, 2.5, 7.0]，修前全为零；host 示例套件 4028 通过、14 跳过，10 个失败是 test_affine_grid_generator 与 test_avg_pool3d 的既有失败（stash 掉修复后同样失败，且这两个用例不用 bfloat16）；riscv64 三条 CI 腿（三个 Python 版本）整套通过——这是该修复第一次在真实 riscv64 上验证。与 #120 的 FlagGems 分支合流后，41 个 bf16 的 xfail 钉全部转正，461 个用例通过。

三、向量扩展与算子优化

3.1 bf16 libcall 家族还剩两处没有回归网（11-17 状态）

日期：2026-11-17　来源：PR #121

#121 的说明自己划了边界：__truncdfbf2 与 bf16 libcall 家族其余成员不改，因为当前 lowering 不产生它们；__extendbfsf2 虽然改了原型，却没有执行测试——两个目标都把 bf16 到 f32 内联成移位，重定位为零，只能反汇编 launcher 的 .so 看 movss %xmm0 序言来确认参数寄存器类。这意味着如果将来某个 lowering 退化成标量 libcall，这条路径没有用例接住。

对照 #117 就看得更清楚：#117 把 +zvfbfmin 放进默认特征串，让有向量扩展的核走向量转换；#121 修的是没有该扩展时退回 libcall 的那条路。两条路的语义必须逐位一致，现在只有向量路径有逐位测试，libcall 路径靠这次补的四类边界用例撑着。

3.2 IREE 3.14.0 给 RISC-V V 补 f16/bf16 inner_tiled MMA（11-16）

日期：2026-11-16　来源：IREE v3.14.0

六、趋势观察

6.1 矩阵扩展开始有编译器出口

XAME 这一笔把 138 条指令、两套 profile、寄存器调度与调用约定一次做进 LLVM，并用 Buddy 的 AME 转换与 gem5 实跑验收。与上周的 RVV bf16 一样，一条扩展是否可用，现在取决于三件事是否同时到位：编译器能生成、模拟器能跑通、算子库有对应入口。只发指令定义、不补编译器，在 RISC-V 上已经等于没发布。

6.2 这一周的主线是 bf16

#117 把 +zvfbfmin 放进默认特征串，#121 修没有该扩展时 libcall 的寄存器类，IREE 3.14.0 给 RISC-V V 补 bf16 MMA——三条动作指向同一件事：bf16 在 RISC-V 上不是一条路，而是「有向量扩展走向量、没有就走 libcall」。两条路必须逐位一致，任一环缺失都会表现为「结果为零」这种最难查的症状。

6.3 发行版在做 ABI 迁移准备

openssl-3 兼容包先落地、主包仍停在 3.6.5，冲突被明确写成预期行为；同一天 abaci-bot 把 ABI 对比、SPDX 校验与 CVE 禁运缓存硬化。openRuyi 把「将来会断的 ABI」当成工程项提前管，而不是等切换当天再补。这种做法比多合几个包更能决定发行版能不能长期跟上游。

6.4 信息面继续空转，代码面很忙

外部新闻零命中、论坛无新主题、官网三页不动，但窗口内有两个编译器中改动合入、19 笔打包仓提交、20 笔治理机器人提交。日报的判断价值继续取决于读提交内容，而不是数新闻条数；发行说明为空或缺失时，只能回到合并提交与测试记录里核对。
