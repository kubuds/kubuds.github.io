今日重点：AME 后端把 i32 矩阵累加器固定在 AccReg，配置化 tile 操作延至展开前（11-04）

日期：2026-11-04　来源：提交 f346011、PR #35

11-04 15:40（北京时间），RuyiAI-Stack/llvm-project 的 riscv 分支新增一笔提交 f346011，改动 8 个文件、+412/−1，作者 caihanyi111，合作者 caohanghang。改动对象是 RISC-V AME 矩阵扩展在 LLVM 里的后端实现（代码中记作 BOSCAME），分两块。

第一块是寄存器归类。循环携带的累加器 PHI 从类型表取默认寄存器类，而 nxv32i32 原先只注册为 TileReg；累加指令 mlce32.m、mqma.*、msce32.m 的累加器操作数与结果都限定在 AccReg，于是每条循环边都要在 tile 与 accumulator 两个寄存器堆之间生成一次复制，而 copyPhysReg 无法把这种跨堆复制展开成单条 AME 指令。修法是给 nxv32i32 同时注册 AccReg；对同时启用 V 扩展的目标，RVV 会重新注册该类型，默认行为不变。同堆的整寄存器复制改用 mmve64.t.t 与 mmve64.a.a 展开；跨堆复制保留为硬错误，不再降级成按 lane 的索引搬移。

第二块是调度。每份 tile 配置与其消费者被保持在一条有序、带副作用的伪指令里，直到 emit 前才展开；矩阵寄存器改为可分配，MMA 的累加器做 tie，零累加器的定义不读旧值，分支松弛把完整展开后的尺寸计入。提交同时新增三份测试：配置化 load/MMA/store 的顺序、独立累加器与零值定义、RVV 与非 RVV 两种选择，以及放宽后的分支。

提交说明写明了动机：上层 TTIR 到 BOSCAME 的降级要求归约循环把 i32 累加器一直留在 AccReg。按提交说明的上下文，这条链路对应 TileLang 一侧的矩阵算子路径；LLVM 侧补的是寄存器分配与调度这一层，而不是新增指令。

日期：2026-11-04　来源：080 期草稿、文章仓提交列表

3.3 arXiv：bf16/fp16 在 RVV 上自动向量化静默降级（11-02，窗口外）

日期：2026-11-02（窗口外，近三日）　来源：arXiv 2611.03917

窗口内 arXiv 没有新的 RISC-V 相关论文；近三日有一篇与 RVV 向量化直接相关的研究值得记录。作者 Vaishnavi Kouru 与 Robert Chun 用 fp32、int8、bf16、fp16 四种精度的乘加循环对比 LLVM 的 RISC-V 自动向量化：在 -march=rv64gcv 这一共同基线下，int8 与 fp32 能干净地向量化，bf16 与 fp16 退化为大量标量回退，fp16 甚至退化成逐元素的软件转换调用，除非额外开启 zvfbfmin/zvfbfwma 与 zvfhmin。

QEMU 用户态下的动态指令数给出了量级：基线 bf16 与 fp16 内核执行的指令数分别是开启扩展版本的 17.0 倍与 75.9 倍。论文同时指出编译器诊断确实会报告这种退化，但措辞上不区分「加一个编译选项就能解决」与「固有转换成本」，用户拿不到指向修法的直接信号。对 RuyiAI 栈来说，这与 080 期补向量数学函数是同一问题的两端：一端缺库函数，一端缺特性开关的可见性。

4.1 VIR 的 set_vl 语义收紧：精确 VLEN 与任意 VLEN 分成两条路径（11-04 至 11-05）

日期：2026-11-04 至 11-05　来源：PR #1028、合并提交 dd57775、PR #1029、合并提交 61ba191

zhanghb97 的两笔 PR 在窗口内先后合入，把 VIR 方言里 set_vl 的语义讲清楚了。

#1028（11-04 23:54 合入）让 rvv-vlen 表示目标的精确 VLEN：vscale = rvv-vlen / 64，一个 vector<[N]xT> 持有 N 乘 vscale 条 lane，切分按完整向量做。此前 rvv-vlen 被当作最小 VLEN，掩码全部为真却仍留在代码里——llc 保留 vid 与 vmslt，访存带着掩码，RoPE 的 rotate_half 变成 slides 加掩码选择，解码注意力里掩码还发生了溢出。K3 上的内核按 1024 位向量宽度构建，正是这一路径的典型场景。

#1029（11-05 01:32 合入）处理不给 rvv-vlen 的通用构建：此时代码必须对任意 VLEN 成立，strip-mined 区域按 N 乘 vscale 在运行时步进，向量按最小的 128 位定尺寸；带结果的 set_vl 会被直接拒绝，报「需要 rvv-vlen，即精确 VLEN」，而这个 pass 以前只是报错。固定向量在无 rvv-vlen 时保持原样，按主机定尺寸；不允许声明高于 128 的最小 VLEN。

两笔合起来的含义是：语义不再靠“掩码碰巧全真”兜底，编译期就要说明这份代码是为某个确定 VLEN 编的，还是为任意 VLEN 编的。

4.2 CI：pytorch 2.15 进测试矩阵，LLVM 发行开 NVPTX/AMDGPU 与 lld（11-04）

日期：2026-11-04　来源：PR #1026、PR #1027、PR #1025

#1026 把 pytorch 2.15 加入测试矩阵，覆盖 2.11 到 2.15。引发改动的是一个真实回归：在 2.15 下最新的 full check 在 tests/Python/AtenOps/test_resize_enlarge.py 处失败，且失败发生在 importer 之前——AOT autograd 的 functionalization 现在拒绝在已函数化的张量上放大 resize_，torch.compile 在同一函数上也失败，图根本到不了 ResizeOp。改法是把测试换成 out-of-place 的 aten.resize，走同一个 ResizeOp handler，产出同样的 MLIR，2.11 到 2.15 全矩阵通过。

#1027 让 CI 发布的 LLVM 带上 NVPTX/AMDGPU 目标并启用 lld；#1025 把 LLVM 升到 bef335e2143c。三笔都是基础设施，但 #1026 记录的这个回归值得留意：上游对 functionalization 的收紧会以“图到不了后端”的形式出现，而不是后端报错。

六、趋势观察

6.1 后端先行，前端与运行时静止

日期：2026-11-05　来源：llvm-project riscv 分支、buddy-mlir 提交列表

这一天的增量都落在“编译与降级”：LLVM 的 AME 后端补寄存器归类与 tile 调度，buddy-mlir 的 VIR 把 set_vl 的 VLEN 语义收紧。与此同时，pytorch、triton-riscv、tilelang-riscv 三个前端仓全部零提交。栈的推进集中在把已有的算子稳定地降到底层，而不是接入新的前端能力。

6.2 打包侧的日常维护与发版停滞并存

日期：2026-11-05　来源：openRuyi 提交列表、ruyi Release 列表

openRuyi 一天十笔提交，内容是 firefox、expat 与四个 Python 包，加上 CI 签名方式与工作流容器化的试验（其中容器化当日回退）；ruyi 与 packages-index 零提交，2026.10 月度版仍缺位。发行版的日常维护在走，面向 AI 栈的发版没有走。上一期把这种状态概括为“卡点在发布不在开发”，本期在发行版侧仍然成立。

6.3 向量数学的补强先出现在文稿里

日期：2026-11-05　来源：080 期草稿、VecIntrinBench

080 期草稿里最实的内容是 glibc libmvec 与 newlib 的向量数学函数移植，而对应的基准与转译仓库（VecIntrinBench、IntrinTrans）仍是静默。这说明底层库的向量化工作在推进，但它没有以提交的形式出现在 RuyiAI-Stack 的重点仓里——RuyiSDK 的基础组件线（GCC、glibc、newlib、V8）与 RuyiAI 栈的重点仓并不是同一批人、同一批仓库。下期值得对照两边的节奏。
