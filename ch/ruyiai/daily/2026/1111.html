今日重点：ruyi 0.54.0 正式发布，宿主 ABI 兼容性检查进入用户命令（11-10）

日期：2026-11-10　来源：ruyi 0.54.0 发布、0.53.0 至 0.54.0 变更比对、PR #507

0.54.0 在 11-10 21:15（北京时间）发布，是正式版而非预发。上一版 0.53.0 是 09-24，间隔四十七天；中间只有 11-02 的 0.54.0-beta.20261102。正式版相对该预发只多了一笔版本号提交，功能面就是预发的全部内容；从 0.53.0 算起，这一版共七十一笔提交、七十四个文件。

主体功能是 ELF ABI 兼容性信息的采集与匹配。一个预编译二进制能否在目标设备上跑起来，取决于一批散落在 ELF 文件头里的事实：需要哪些动态库、向这些库索取了哪些符号版本、以及架构相关的能力要求。此前软件源里没有任何地方记录它们，ruyi 现在把这些信息扫出来、存下来、并在安装前比对。

采集面按架构分：x86-64 记 ISA feature level，AArch64 记 BTI 与 PAC，RISC-V 记 ISA 串。RISC-V 这条最费工，因为它的扩展是按版本号拼串的，本期提交里有解析带版本的单字母扩展、按宿主浮点 ABI 过滤 ld.so.cache 条目、以及把栈对齐要求算进去。宿主侧另外实现了 x86-64 与 AArch64 的探测，宿主库按请求的 soname 解析，遇到无法解析的 soname 报”未确定”而不是判死。

用户可见的变化落在三处命令：ruyi list 在备注里显示宿主兼容性（非二进制包隐藏该项），ruyi install 在装不兼容的包时告警，ruyi admin check-abi 供排障。数据面走仓库侧的 ABI sidecar，按 distfile 名解析；rescan-package-abi 与插件产物新增 strip-components，用来处理归档里有前导目录的情况。sidecar 有大小上限，坏 sidecar 被当作”无 ABI 信息”丢弃，不会让整次安装失败。

另一类是取件链路的修复：#509 让非 2xx 的 HTTP 响应如实报错，并丢弃失败的首次下载、给卡住的传输加上限。这类改动不显眼，但对一个要从镜像站拉几百兆工具链的包管理器来说，比新增功能更影响体验。

设计文档 docs/elf-abi-compat-design.md 随版本入仓，发布说明给出的安装路径仍是 PyPI 与服务所镜像站，单文件二进制需重命名为 ruyi 才能使用。

今日重点：triton-riscv 在 RISC-V 宿主上默认启用 AMD GPU 后端（11-10）

日期：2026-11-10　来源：PR #110、README

PR #110 在 11-10 17:51（北京时间）合入，标题是”默认启用 GPU 后端”。改动有三件事：用现有的 Buddy LLVM SDK 构建并打包 riscv64 的 AMD codegen 库；修掉 riscv64 上 CPU 与 GPU 驱动二选一时的歧义，规则是优先选用可用的 GPU；以及改掉驱动层那处让选择变含糊的判断（该文件净删四行）。

验证是在真机上做的：SG2044 配 RX 7900 XTX，torch 与 ROCm 来自 openRuyi 的软件仓；另测了隐藏 GPU 设备时能否自动回落到 CPU。这条口径比”能编过”硬得多——它说明 RISC-V 主机确实把内核发到了 AMD 卡上跑，而不是在 CPU 上兜底。

README 同步加了一节 AMD GPU 用法：ROCm 在位时后端通过 torch.version.hip 自行激活，写法和上游教程一致；wheel 不带 ROCm 运行时，torch 与 ROCm 要另装；强制回 CPU 用 TRITON_DEFAULT_BACKEND=triton_shared。改动共六个文件，集中在 README、backend/driver.py 与 scripts 下的 build、env、release、setup 四个脚本。

有一个时间差值得记下：当天 10:22（北京时间）出的夜间版 nightly/2026-11-10-209274f 打在提交 209274f 上，早于这笔合入，因此这个包还不含 GPU 后端。要拿到它得等下一版夜间版。

对整条栈来说，这是路线层面的变化：triton-riscv 此前只回答”如何在 RISC-V CPU 的向量单元上跑 Triton”，现在还要回答”如何从 RISC-V 主机驱动异构加速器”。在一个主流 AI 加速卡都不带 RISC-V 宿主驱动的时点，先支持 AMD 卡是最现实的一步——ROCm 的 RISC-V 侧工作已经在 openRuyi 仓里维护。

1.1 triton-riscv：插件改名 PR 在审，环境变量的取值将随之一变（11-10）

日期：2026-11-10　来源：PR #109、提交列表

#109 要解决的问题是名不副实：name.conf 决定安装出的包名与入口点，于是插件现在叫 triton.backends.triton_shared，可它报告的目标是 cpu，选项前缀又已经是 triton_riscv。改法是统一叫 riscv，理由是对齐上游的命名习惯——插件按目标家族命名（nvidia、amd），设备名（cuda、hip）留给 target。

四、Buddy Compiler 动态

4.1 buddy-mlir：YOLOv8 检测与姿态跑上 K3 矩阵引擎，权重与 TCM 拷贝补两处修正（11-10）

日期：2026-11-10　来源：PR #1042

#1042 把 Ultralytics YOLOv8 接进 buddy-cli 的 rax 格式：yolov8n 检测（八十类 COCO）与 yolov8n-pose（十七个关键点），输入都是 320x320。f32 模型走 VIR 降低，规格里写 ime: true 则改跑 SpacemiT K3 的矩阵引擎。

评审阶段补的两处修正比模型本身更有信息量。一是权重校验：清单里带 params_size，运行器要求权重文件与它一致，此前权重文件偏短会让模型读过缓冲区；同时要求运行器只接受 rax 包，因为单独给库与权重时，姿态模型会被按检测模型的参数跑起来。二是 TCM 拷贝：IME 权重的 TCM 副本按权重地址缓存，新权重读进已释放的缓冲区时会命中旧副本，现在每次权重装载后调用内核侧的失效函数。

规格里同时保留 params_size 与 ime_params_size，这样 ime: false 时仍能构建 f32 版本。这条设计与前一天的 VIR 端到端走通是同一条线：同一张图，两条后端路径，一份可对比的基线。

4.2 buddy-mlir：vir.set_vl 区域收紧为一个块，多块区域不再静默丢算子（11-10）

日期：2026-11-10　来源：PR #1045

vir.set_vl 的区域类型原是 AnyRegion，源码里留着”区域限制待定”的注释。校验器与 -lower-vir-to-vector 的每一处 lowering 都只取 region.front()，于是多块区域能通过校验，其余块里的算子被静默丢弃。复现很清楚：一个 set_vl 里的 load 与 store 落在第二个块（cf.br ^bb1 之后），降低结果是两个空的 affine.for；空区域则能过校验，随后在 pass 里以”找不到锚类型”失败。

改法是把类型改成 SizedRegion<1>，注释删掉，校验器不再自己防空区域（ODS 先验块数），只保留”块无参数”这一条。测试里新增两块与零块两种非法输入。这类改动不产出新功能，但它把一类”编得过、算得错”的路径变成了编译期错误，价值在可诊断性上。

4.3 buddy-mlir：动态向量类型与缩放因子的打印、解析与校验补齐（11-10）

日期：2026-11-10　来源：PR #1046

缩放因子此前打印成属性形式 #vir.sf<m2>，而类型语法与示例给的是 m2；解析侧留着”待补错误提示”的注释，行为有多处不一致：#vir.sf<x2> 与 mq 会崩溃（解析返回空属性而没有报错，类型解析器把它当成有效值），m3、m0、f128 被接受，!vir.vec<0x?xf32> 被接受，而 !vir.vec<?xvector<4xf32>> 被拒且位置报成 unknown。

改动分三块：打印改用 sf.str()，#vir.sf<m2> 仍可读入；属性侧加 genVerifyDecl，要求比例是 m 或 f、取值 2 至 64 且为二的幂（与 Python 绑定已有的检查一致）；类型侧要求动态维之前的各维静态且为正。第二个提交把错误定位修到真实位置。对一门还在成型的中间方言，解析器的严格程度直接决定前端能否可靠地报错。

4.4 buddy-mlir：reassoc 归约先按 lane 合块，修 VLEN 128 宿主上的位不一致（11-10）

日期：2026-11-10　来源：PR #1047

在 VLEN 128 的 RISC-V 宿主（SG2044 的 C920 核）上，test_k3_w4_kernels.py 的 qk_norm 出现位不一致。原因是 K3 解码注意力的 q、k 归一化把一个头的六十四个 f32 平方和放进没有 shuffle 的 set_vl 区域，降低按宿主定尺（#1037），VLEN 128 下变成两块 vector<32xf32>（LMUL 8）；而 vir.reduce 把每块依次并入前一块的结果，与向量内核里的单次 vector<64xf32> 归约顺序不同——LLVM 会把宽向量拆半、逐 lane 相加再归约一次。CI 的 riscv64 跑在 VLEN 256 上，那里只有一块，所以一直通过。

改法是让跨多块的 reassoc 归约按 LLVM 的方式合并：n 块先补宽到 2 的幂 h，第 p 块与第 p+h/2 块相加，直到只剩一块再归约一次。这已经是同一主题的第四个修正（前有加载期 VLEN 校验、宿主定尺、FMA 尾部舍入），指向的验收标准一致：换实现可以，换数值不行。

4.5 buddy-mlir：五十个 Python 文件改名，A100 llc 选项收敛到统一入口（11-10）

日期：2026-11-10　来源：PR #1043、PR #1044

#1043 把五十个带连字符的 Python 文件名改成下划线：同目录下已有下划线命名的文件，带连字符的无法 import，函数也就无法被测试或复用。改动覆盖 models、examples、.agents/skills 与 tests 四处，同步修了 CMake、shell 脚本、README 与文档里的引用。MLIR 上游二百四十一个 Python 文件里有二百三十七个是下划线命名，这次是对齐上游规范。

#1044 修的是 YOLOv8 的 IME 路径：lower_to_obj.sh 自己拼了一套 A100 的 llc 选项（含 +zvl1024b 与 -riscv-v-vector-bits-max=1024），却只用后者检查构建的 VLEN。自 #1032 起 VLEN 统一由 BUDDY_RISCV_VLEN 指定，其他模型都从 a100_llc_args 取，且校验的是 llc 实际读到的精确 1024。旧脚本会被 +zvl256b 或无 VLEN 的构建骗过：VIR 按任意 VLEN 降低，object 却按 1024 编。现在脚本直接追加统一入口给出的选项，不满足 VLEN 1024 就停下，并新增一个用桩工具跑的测试。

六、趋势观察

6.1 0.54 的发布间隔翻倍，代价在跨三种架构的 ABI 采集

0.52 到 0.53 隔了二十二天，0.53 到 0.54 隔了四十七天。翻倍的这段时间里，提交几乎都压在一条线上：把 ELF ABI 兼容性从”没有记录”做到”能采、能存、能比对、能在安装前告警”。这条路要同时处理 x86-64 的 ISA level、AArch64 的 BTI 与 PAC、RISC-V 的版本化扩展串，是三种架构的知识而不是三次相似的编码。

值得注意的是它先落在一个包管理器里，而不是某个发行版的质量流程里。包管理器是唯一能在”用户点安装”那一刻做判断的位置，把兼容性判断放在这里，等于把发行版级的验证成本前移到一次本地比较。

6.2 “能不能装”第一次变成可计算的事实

RISC-V 的碎片化不在指令集本身，而在基线：同一份 riscv64 二进制，可能在 RVA20 的板子上跑不起来，也可能在一个没有向量单元的核上直接非法指令。此前这类问题靠文档、靠论坛回帖、靠试。0.54 把每个包的动态库需求、符号版本与架构能力要求写成 sidecar，宿主侧探出对应事实再比对，于是”这个包装不上”从一句经验变成一条可复现的结论。

副作用是数据维护：sidecar 要随包更新，strip-components 一类的归档差异要单独处理，坏 sidecar 要有明确的降级策略。0.54 把这些边角都写进了代码，说明设计时已经算过维护成本。

6.3 RISC-V 宿主加 AMD 卡进入主线

triton-riscv 从”在 RISC-V 向量单元上跑 Triton”扩展到”从 RISC-V 主机驱动 AMD GPU”，默认路径直接选 GPU。这条组合此前只在厂商演示里出现，现在进了默认分支，并且有真机验证（SG2044 配 RX 7900 XTX）。

现实意义在于：主流 AI 加速卡的宿主驱动生态几乎都为 x86 与 Arm 准备，RISC-V 机器长期只能靠 CPU 跑推理。让 RISC-V 主机把内核发到一张消费级 AMD 卡上，是绕开这个生态缺口最省力的一条路——ROCm 在 RISC-V 上已经有维护，缺的只是编译器后端这一环。

6.4 VIR 的修补对象从”算错”转向”静默出错”

本窗口 buddy-mlir 的六笔里，至少三笔针对的是”不报错但结果不对”：多块 set_vl 区域静默丢算子、缩放因子解析崩溃或放过非法值、跨块归约顺序改了数值。前两类以前会让编译器安静地产出一个错的结果，现在变成编译期错误；第三类靠逐字节比对才抓得住。

这类问题的共同点是修复成本低、发现成本高。它们能在这个阶段被成批清掉，说明 VIR 已经有了一套能跑真机、能比基线的测试面——没有 K3 与 SG2044 上的对照，4.4 那种 VLEN 128 与 256 的差异根本不会显形。
