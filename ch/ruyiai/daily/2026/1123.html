三天内 buddy-mlir 打了三个正式版。0.1.5 发布于 11-20 23:40，0.1.6 发布于 11-21 22:49，0.1.7 发布于 11-22 01:12，间隔分别约 23 小时与 2 小时。

今日重点：DeepSeek-R1-Distill-Qwen-1.5B 在 K3 A100 上的 FP16 优化合入，Prefill 43.42 token/s（11-23）

来源：PR #997。提交 3d5d674a。K3 配置 f16_k3.json。

#997 在 11-23 00:25 合入，创建于 10-25，评审历时近一个月。改动 20 个文件，含新增的 A100 合法化 pass、IME 方言扩展与模型配置。

PR 说明给出的核心手段有四条。第一，四个 FP32 累加器在整条 K 归约上常驻寄存器，Prefill 走 8×32 分块，Decode 每块算 32 个输出通道。第二，部分 Decode 投影权重打成 N32/K8 面板，其余投影保留原 RVV 布局。第三，Prefill 用原生 VLEN=1024 与 BLIS 宽度 64，并融合逐元素算子、向量化 SiLU。第四，以上选择集中到 models/deepseek_r1/specs/f16_k3.json，既有配置的默认流水线不变。

实测数据按 PR 说明记录。Prefill 评估 128 个位置，Decode 从第 64 个位置起测 32 步，八线程，A100 核心 8 至 15，取四次样本。表中单位为 token/s。

实现 Prefill Decode
Buddy 主干，打包 FP16 4.53 5.88
llama.cpp（SpacemiT 后端 0.1.6） 27.95 3.90
Buddy，本 PR 43.42 6.06

Prefill 相对 Buddy 主干提升约 8.6 倍，相对 llama.cpp 高 55%。Decode 相对 llama.cpp 高 55%，相对 Buddy 主干只高 3%。

Prefill 的数字包含会话与接口调用的开销，PR 说明已注明。llama.cpp 一侧用 FP16 GGUF 权重与 FP16 KV cache，双方输入 ID 一致。

同一套内核已被复用到其他模型。#1075 做 Whisper Base，#1076 做 PaddleOCR-VL-0.9B，#1001 做 Qwen3-0.6B。三笔都引用 #997 的 pass 与权重打包。

1.2 FlagGems 示例再开两支：72 + 61 个算子，堆叠到 279 个（11-21、11-22）

来源：PR #131。PR #132。

#131 在 11-21 18:53 开出，覆盖 72 个算子。#132 在 11-22 18:48 开出，覆盖 61 个算子。两支都只改 python/examples/flaggems/。

#131 的四族是坐标拷贝、内部拷贝与分配、形状构造、类型转换与填充。PR 说明列出三处上游偏差：padding 包装按 aten 的 (w, h, d) 顺序接收，再重排到内核的 (d, h, w)；replication 的反向按标量源位置扫，以贴合 aten 的累加顺序；rank 大于 2 时 rot90 漏掉了末维项。

#132 的四族是 BLAS 包装与稀疏 smm、gamma 特殊函数、量化算子、低精度与稀疏矩阵乘。PR 说明写明 fp64 点积只能到 fp32 累加，因此这类收缩改为标量 FMA 循环保精度；e5m2 fp8 没有降级路径，改为内核内上转，e4m3 与 int8 走原生。

测试数继续上涨。#131 记 7830 项通过、739 项新增；#132 记 8617 项通过、787 项新增。都在 x86_64 上跑，排除了三个既有崩溃文件。

五支 PR 串成一条链：#126 的 63 个、#127 的 43 个、#130 的 40 个、#131 的 72 个、#132 的 61 个，合计 279 个算子示例。按 PR 说明，前序未合时 diff 会把前序提交计入，#131 相对 main 是 34 个提交、548 个文件，#132 是 38 个提交、670 个文件。

三、向量扩展与算子优化

3.1 VecIntrinBench、IntrinTrans 与 FBGEMM 继续静默（11-23 状态）

来源：VecIntrinBench。IntrinTrans。FBGEMM。

三个仓窗口内零提交。最后提交时间分别是 02-13、06-25 与 07-13。

向量内在函数的基准与转换工具已三个季度未动。当前能看到的向量性能数据，主要来自 triton-riscv 的算子测试与 buddy 的模型实测。

这并不代表向量方向停摆。窗口内的向量工作写在模型内核里，见下一条。

3.2 向量工作转入模型内核：VLEN 1024、SiLU 与 exp 近似（11-22）

来源：PR #997。PR #1076。PR #1075。

#997 把 Prefill 的 BLIS 列宽做成可配置，并可在函数入口校验硬件 VLEN。A100 配置取 VLEN=1024，配合宽度 64。

同一笔里 SiLU 改为融合并向量化，exp 走上游 MLIR 的多项式近似。PR 说明写明多项式会改变舍入，与默认路径分开验证。

#1076 把 attention 的 bmm1、scale、softmax、bmm2 合成单个分块内核，softmax 留在 L1，用向量 exp。同一笔给 -approximate-vector-exp 加了向量化 erf，让 GELU 不再逐 lane 调标量函数。

#1075 走另一条路。编码器的 P @ V 降为 4 行 M 展开的 FP32 累加 RVV 内核，matmul_transpose_b 与 conv_1d_ncw_fcw 降到 IME。

三笔的共同点是把向量宽度与硬件 VLEN 绑定。上一期 triton 侧 #129 的调优用的是同一思路，两侧的参数口径可以对照。

3.3 FlagGems 示例覆盖到特殊函数与量化算子（11-22）

来源：PR #127。PR #132。

特殊函数一支覆盖贝塞尔家族、四类 Chebyshev 与移位版、两种 Hermite、Laguerre、Legendre，另有 log_softmax 与 logsumexp。

工具链无法降级的 intrinsic 改走闭式。erfcx 用三段混合，log_ndtr 的尾部改算 −t² + log(erfcx(t)/2)。

量化与低精度一支覆盖伪量化家族及其可学习变体、4 位动态量化线性、scaled mm、int8/int4 权重打包、混合精度线性、CSR 与半结构化乘积。

精度处理写进了 PR 说明。fp64 点积在 Triton 侧只能到 fp32 累加，这类收缩改为标量 FMA 循环；e5m2 fp8 无降级路径，内核内上转；e4m3 与 int8 走原生。

四、Buddy Compiler 动态

4.1 0.1.5 到 0.1.7 的标签与提交对应关系（11-22）

来源：标签列表。compare 0.1.6…0.1.7。

三个标签各对应一笔提交。0.1.5 是 20d3a102，0.1.6 是 8cbc1a9b，0.1.7 是 a848378f。

compare 显示 0.1.6 相对 0.1.5 领先 1 个提交，就是 #1074 的 dump() 修正。0.1.7 相对 0.1.6 是分叉状态：领先 1 个、落后 1 个。

0.1.7 的父提交是 20d3a102，也就是 0.1.5 的基线。这意味着 0.1.7 不含 dump() 修正。

对下游有直接影响。triton 需要 mlir::Operation::dump() 才能链接，0.1.5 与 0.1.7 都缺这个符号，只有 0.1.6 带。

目前 triton 侧钉的仍是 nightly/v0.1.4.dev20261103（#115 未合）。若按 #115 升到 release/v0.1.7，链接问题会回来。

4.2 0.1.6 补 dump() 支持，0.1.7 压缩 LLVM 资产（11-21）

来源：PR #1074。提交 a848378f。

#1074 的起因写得很具体。夜间版从 main 构建，但 #1062 落在 llvm-multitarget 分支，所以 0.1.5 的 LLVM 包只有 dumpPretty()，没有 dump()。

下游现象是链接失败，报 undefined reference to mlir::Operation::dump() 与 mlir::Value::dump() const。修法是开 LLVM_ENABLE_DUMP，只恢复这两个 helper，不打开断言。

PR 说明另提醒：LLVM 安装按哈希缓存，之后的版本要跑一次 llvm_cache_mode=clean 才会带上该开关。

0.1.7 处理的是资产上限。提交说明写明 riscv64 的 LLVM 安装包 gzip 后略超单资产 2 GiB 上限，v0.1.6 因此报过「size must be less than 2147483648」。

修法是截断下游用不到的开发者工具，去掉 src、share 与 libexec，并 strip 其余部分。x86_64 实测从 1617 MB 降到 817 MB。

说明里还记了一次失败尝试。最初直接删除文件，结果 LLVMExports.cmake 在 configure 阶段因导入目标指向缺失文件而中止，所以改成截断。

两个版本现各有 8 个资产。riscv64 的 LLVM 包在 0.1.7 上是 1,138,715,828 字节，低于上限。

4.3 DeepSeek 优化合入，四个模型 PR 排队（11-23）

来源：PR #997。PR #1075。PR #1076。PR #1001。

#997 已在今日重点展开。这里只补它在 PR 队列里的位置：它是这轮模型优化的母本。

#1075 做 Whisper Base，11-22 17:10 开出。PR 说明给出端到端 2.031 秒，主干是 1663.03 秒，提速 818.8 倍，RTF 从 345.39 降到 0.42。预处理 0.101 秒，编码器 1.622 秒，解码 0.272 秒。

#1075 还修了一个内存问题。STFT 循环里 make_rfftp_plan(400) 每次调用都建计划，泄漏约 1 GB，改为提到 3001 帧循环之外并释放缓冲。

#1076 做 PaddleOCR-VL-0.9B，11-22 22:08 开出。端到端 30.82 秒，相对 FP16 RVV 基线 525.71 秒提速 21 倍。Prefill 25.04 秒，Decode 5.78 秒（18 个 token，3.11 token/s）。生成的 19 个 token 与 PyTorch FP16 完全一致。

#1001 做 Qwen3-0.6B，10-26 开出至今在审。它直接复用 #997 的 IME FP16 GEMM/GEMV 内核与 Decode 权重打包。

四笔合起来的信号是：一套 A100 内核正在覆盖 LLM、语音、OCR 三类负载。

4.4 方言与导出侧另有五笔在审（11-23 状态）

来源：PR #1071。PR #1072。PR #1073。PR #1035。PR #934。

六、趋势观察

6.1 发版从按月推进转向按下游阻塞修补

上一期记的是 ruyi 把 0.55.0 推到 11 月底。本期 ruyi 出了 beta，buddy-mlir 则在三天里连发三版。

0.1.6 与 0.1.7 都不是功能版。一笔补下游链接缺的 dump()，一笔压资产体积以过 2 GiB 上限。

判断的依据是提交说明：#1074 直接写出 triton 的 undefined reference，a848378f 直接写出 size must be less than 2147483648。

这说明版本号正在被当作修补通道使用。代价是 0.1.7 与 0.1.6 分叉，下游要同时拿到两笔修正，得等下一次合并。

6.2 K3 A100 上形成模型优化流水线

#997 合入后，同一套 IME 内核已出现在 Whisper、PaddleOCR-VL、Qwen3 三个模型的 PR 里。

三笔的性能数字都按同一台机器 K3-002、同一组核心 8 至 15、八线程、VLEN=1024 记录。横向可比。

收益的量级差别很大。DeepSeek 的 Prefill 是主干 8.6 倍，Whisper 的端到端是 818.8 倍。后者的基数来自未做编码器复用的 F32 单次前向，倍数被基线放大。

可复核的口径是 token 序列与参考实现一致。#1076 记了 19 个 token 全等，并贴出 OCR 文本。

6.3 工具链侧进入待合队列堆积期

triton-riscv 的五支 FlagGems PR 串成一条链，合计 279 个算子示例。每支都等前一支合入才能重算 diff。

pytorch 的 riscv 分支停在 11-15，tilelang-riscv 停在 11-16。两处都没有新提交。

ruyi 侧相反，六笔 PR 一天内合完并出了 beta。差异在于 ruyi 的改动集中在 CLI 与配置，评审面窄。
