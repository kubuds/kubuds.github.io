今日重点：BUDDY MLIR 0.1.4 正式发布，三十笔提交里十九笔落在 VIR 中间端（11-15）

日期：2026-11-15　来源：BUDDY MLIR 0.1.4、0.1.3 至 0.1.4 差异、PR #1059

2026-11-15 08:01（北京时间），buddy-mlir 发出正式版 0.1.4，距 0.1.3（10-31）两周。从 0.1.3 到 0.1.4 共三十笔提交，其中十九笔带中间端前缀，主题只有一个：把可伸缩向量（VIR）这条下降路径从”能跑几个算子”补到”覆盖一类形状”。

这十九笔可以分成四组。第一组是形状覆盖：#1017 修正可伸缩向量分片计数时的窄化；#1056 收全整数与浮点的全部归约种类；#1057 把 rank-0 memref 的 linalg.fill 降成一次 store；#1058 支持整数矩阵乘并修正动态维度；#1041 让卷积也走 VIR。第二组是 VLEN 处理：#1028 针对精确 rvv-vlen 下降 set_vl；#1029 在没有 rvv-vlen 时也能为任意 VLEN 生成代码；#1032 与 #1037 分别防止”为某个精确 VLEN 编好的模型”被搬到别的 VLEN 上、以及按宿主的 V 扩展宽度下降；#1046 给动态向量类型做校验并把缩放因子按 m2 打印；#1048 在克隆动态向量类型时保留缩放因子。第三组是分片与组合：#1031 把可伸缩向量的 shuffle 分几片下降；#1047 为可结合归约合并向量分片；#1045 给 vir.set_vl 一个单块区域；#1050 写清 strip-mined set_vl 支持哪些算子；#1051 处理 vector<[1]xT> 的全车道归约。第四组是上一期报告已经写过的 11-12 七笔（#1052 至 #1058 中的掩码、libm、bf16、fast-math、归约、rank-0、整数矩阵乘），它们在这次一并进入正式版。

VIR 之外还有十一条支线：模型侧 #1042 在 SpacemiT K3 上加了 YOLOv8 的检测与姿态，#1044 把 A100 的 llc 参数改从 a100_llc_args 取；运行时侧 #1018 加了共享的 serving 生成控制器；编译器侧 #1025 把 LLVM 升到 bef335e2143c，#1027 让发布的 LLVM 带上 NVPTX、AMDGPU 与 lld；测试侧 #1026 把 PyTorch 2.15 加进矩阵；后端侧 #1033 为 BOSCAME 加了 SPM 优化；工具侧 #1030 让内核按 llc 选项对应的目标下降 VIR。

值得记一笔的是发布时机：主干最后一笔提交仍是 11-12 14:44 的 #1058，此后到 11-15 发布之间没有任何新提交。也就是说 0.1.4 与 11-13 的夜间版是同一棵树，正式版相当于给这棵树补了两天的观察期，而不是又叠了一层改动。

今日重点：openRuyi 收下 python-torch-ruyiai，RuyiAI 的 PyTorch 快照进了发行版（11-13）

日期：2026-11-13　来源：openRuyi 提交 add python-torch-ruyiai、python-torch-ruyiai.spec、PyTorch riscv 分支

11-13 22:58（北京时间），openRuyi 打包仓落下一笔新包 python-torch-ruyiai。这是 RuyiAI 第一次以发行版软件包的形式出现在 openRuyi 里：版本号 2.15.0~a0+git20260921，源码跟随 RuyiAI-Stack 的 riscv 分支（提交 6d667e1e），CPU-only，工具链用 clang，不能与发行版原有的 python-torch 并存。

规范文件里能读出这次打包的三个难点。其一是 BLAS：OpenBLAS 的 Fortran cdotu_／cdotc_ 把复数按寄存器返回，而 PyTorch 的非 CBLAS 分支按 f2c 惯例从第一个参数取结果，于是 complex 张量上的 dot 与 vdot 静默得 0；补丁 2001 打开 CBLAS 路径，并让 spec 里的 PYTORCH_BLAS_USE_CBLAS_DOT=ON 在原生构建下也生效（上游只在交叉编译时读这个变量）。其二是 RVV 门控：__riscv_v_intrinsic 宏在 rva20 基线下也会定义，旧条件会选中根本不该用的深度卷积向量内核；补丁 2011 改成按 __riscv_vector 判断。其三是构建后端：RuyiAI 快照要求 scikit-build-core 1.0 以上，而 openRuyi 仍发 0.12.x、python-pyvex 又卡着上界，补丁 2012 干脆把这个后端作为源码自带，同时去掉第三方树裁剪后无法满足的 license 文件通配。

依赖处理走的是”尽量用系统库”的路子：USE_SYSTEM_CPUINFO、USE_SYSTEM_ONNX、USE_SYSTEM_SLEEF、USE_SYSTEM_PYBIND11、USE_SYSTEM_PTHREADPOOL 等一批开关打开，USE_CUDA、USE_ROCM、USE_MKLDNN、USE_XNNPACK 关闭，分布式与 TensorPipe 保留。第三方目录只保留实际编译的组件（gloo、flatbuffers、cpp-httplib、kineto、tensorpipe、miniz），tensorpipe 自带的 libuv 与 libnop 也一并解包。检查环节没有跑 fork 的全量测试（riscv64 上大部分被 blocklist，剩余失败记在 fork 的问题 33 与 34），而是跑一个功能 smoke：矩阵乘、autograd、两百步训练，外加一条复数 dot／vdot 不得为零的守卫——正好覆盖 2001 补丁修的那条路径。

同一晚打包仓还落了 llvm22/23/24 打开 PIE 并生成 clang resource dir、clang-wrap 升到 20261113、cmake 升到 4.4.5，从时间上看是为发行版内的 clang 构建补齐安装布局。

1.1 pytorch riscv 分支：一天之内两次改判 CI 判据，返回码换成统计文件（11-13）

日期：2026-11-13　来源：PR #56、PR #57

11-13 00:25，PR #56 合入，改动是给 riscv64 的 CI yaml 补判据：新作业在构建成功但用例全部未执行（失败 0 通过 0）时，父作业此前会记成通过，于是加了一道 Jenkins 返回码非零即失败的检查。17 小时后（17:04），PR #57 合入，把这道返回码检查整个删掉，改成先用 curl --fail 取回 pytorch-ci-stat.json 再按统计数值判。两笔合计 +35 −20 行，都只动 .github/workflows/ci-riscv64.yml。

一天之内同一处判据改两次，说明返回码这条路本身不稳：Jenkins 的退出码在构建成功、用例全挂时仍可能为 0，单看返回码挡不住假绿。改成读统计文件之后，判据从”作业死没死”变成”用例跑没跑”，与上一期报告里”零用例通过”那条判据是同一个方向的收紧。

3.1 bf16 转换辅助函数的 ABI 错配：llc 从浮点寄存器取返回值，launcher 却用整数返回（11-14）

日期：2026-11-14　来源：PR #121、issue #114

11-14 新开一笔修 bf16 的 PR。launcher 里两个转换辅助函数原本声明成整数原型：截断函数返回 uint16_t，扩展函数参数也是 uint16_t；而 llc 生成的调用点按 bfloat 走浮点寄存器——x86-64 上返回落在 xmm0，riscv64 上落在 fa0，调用方从寄存器的低 16 位取值。整数返回走 eax／a0，于是每个把 fp32 结果转成 bf16 的内核，存下去的都是上一次浮点运算残留的零或垃圾值。

PR 的验证做得挺细：在 x86 主机上直接看反汇编，调用点是 callq __truncsfbf2 接 vmovaps %xmm0 再 vpextrw，eax 从未被读；交叉编译到 riscv64（特征串去掉 +zvfbfmin）则看到 fa0 传入、fmv.x.w 从 fa0 读回，而辅助函数的整数返回在 a0。修法是把原型改成 float，让两边落在同一类寄存器，bf16 位仍放在低 16 位；不能用 __bf16，因为 launcher 用 g++ 编译，Ubuntu 24.04 的 g++ 13 在 riscv64 上没有这个类型。新增的 test_bf16_convert.py 对着 torch 逐位比对，覆盖就近取偶的多个边界，修复前其中四例失败。

3.2 五批五十四个 FlagGems 算子示例，五百八十七项通过、四十一个 bf16 严格挂起（11-13）

日期：2026-11-13　来源：PR #120

11-13 开的另一笔把 FlagGems 的算子示例成批补进 triton-riscv：五个独立批次合成一个集成序列，共十三笔提交、五十四个算子示例，覆盖一元数学（acosh、arcsin、log1p、sinc 等）、二元运算（bitwise_xor、copysign、fmax、nextafter 等）、激活（hardshrink、mish、relu6 等）、归约（amin、argwhere、frobenius_norm、nansum 等）、窗函数与损失（bartlett、blackman、hamming、kaiser、bce、huber_loss、kl_div、l1_loss）。

x86 后端上的五组测试分别通过 77、128、114、126、142 项，合计 587 项通过；另有 41 个 bf16 用例被写成严格 xfail，原因正是 3.1 那条 launcher ABI 缺陷——未加门的 riscv64 CI 跑下来 41 个 bf16 测试全挂。这批 xfail 先只锁到 x86 主机，后来改成全主机无条件生效，等 #121 合入后再拆。

3.3 显式目标走 -O3 之后，flash attention 对象多了三条向量除法（11-14）

日期：2026-11-14　来源：PR #117

#117 合入带出的一个可量化变化写在测试改动里：两个 attention 内核的汇编断言此前找的是标量 fdiv.s，中间端跑到 -O3 之后除法被向量化，断言改为接受 vfdiv.vv／vfdiv.vf。以 flash attention 内核为例，对象从 1 条 vfdiv.vf 加 1 条 fdiv.s、3 条 vfmul，变成 4 条 vfdiv.vf 与 36 条 vfmul。这是”中间端不跑”与”跑 -O3”两条构建路径之间最直观的差别。

3.4 wheel 用 strip-all 减重四成，triton-shared-opt 从四百零七兆降到一百一十八兆（11-13）

日期：2026-11-13　来源：PR #116

#116 把打包时对自带 LLVM 与 buddy 工具的 strip 从 --strip-unneeded 换成 --strip-all。此前 triton-shared-opt 一个可执行文件就带着九个调试段、407 MB，换过之后 118 MB，同法处理其余六个工具，整个 wheel 的有效载荷从约 970 MB 收到约 576 MB。PR 里还记录了一个被否掉的方案：把 bin/llc 指向 buddy-llc（两者产物相同），但 buddy-llc 写完输出不退出，无法替代非 IME 路径调用的普通 llc。

4.2 开放 PR #1059：把 memref 拷贝换成向量搬运，样例从六十六毫秒降到二点八毫秒（11-13 状态）

日期：2026-11-13　来源：PR #1059

#1059 仍在审，但数据值得先记。它处理的是 finalize-memref-to-llvm 的一个退化：只有恒等布局或静态连续形状的 memref 才能用 llvm.memcpy，其余 memref.copy 退化成 memrefCopy 调用、一次拷一个元素——而 Triton 内核里的掩码载入与存储（带偏移的动态长度、矩阵的分块）恰好都是这种拷贝。在 K3 上剖析时，这类拷贝占到 add、exp、softmax、matmul 经 VIR 下降后内核耗时的 44% 至 99%。

修法是把末维单位步长的 memref.copy 降成按末维 vir.set_vl 的向量载入加存储，行间用循环；固定向量路径下主循环与尾循环从 affine.for 改成 scf.for，因为循环内算出的 vl 不是合法的仿射操作数。效果在 K3 上：X100（VLEN 256）的 add 从 66.1 毫秒降到 2.76 毫秒，A100（VLEN 1024）从 138.9 降到 2.26；在 1811 个 FlagGems 内核里，memrefCopy 调用从 3694 降到 819（涉及的内核从 1499 个降到 317 个）；4043 项测试套件在 SG2044 与 K3 上仍然 4036 项通过，另外 7 项用原管线也失败。

六、趋势观察

6.1 打包层成了 RuyiAI 落地的新战场

这一窗口最重的两件事都不在算法上：一件是把 PyTorch 快照做成发行版软件包，一件是给 wheel 减重四成。torch 包的六个补丁里，三个是构建与 ABI 问题（CBLAS 复数 dot、系统 fmt 与 concurrentqueue、子模块检查），一个是宏定义选错了门控条件（__riscv_v_intrinsic 对 __riscv_vector），只有一个是真正的功能适配。这说明 RuyiAI 栈已经从”能不能编译”进入”能不能装、能不能链接、能不能被别的包依赖”的阶段——这一层的坑比内核里的向量化更琐碎，也更决定用户第一次上手是否成功。

6.2 正式版就是夜间版那棵树

0.1.4 的发布方式值得记下来：11-12 收完最后一批 VIR 改动，11-13 出夜间版，11-15 打正式 tag，中间两天零提交。这等于把”发布”定义成对已有夜间版的确认，而不是再一次集成。对下游来说这是好事——Renovate 钉的那版夜间版与正式版同树，切过去没有功能差异，只是版本号更可追溯。

6.3 性能账本翻到了拷贝这一页

#1059 的数据说明 VIR 路径当前最大的开销不在算术，而在数据搬运：掩码载入与存储退化成逐元素拷贝，能占到内核时间的 44% 至 99%，add 这种最简单的算子因此比非 VIR 路径慢四十倍（66.1 对 1.60 毫秒）。改成向量搬运后仍有差距（2.76 对 1.60），但已回到同一量级。这条线索和上一期的”形状覆盖”是前后脚：形状补齐之后，下一步的收益来自把拷贝、布局变换这类周边开销压下去。

6.4 CI 判据仍在试错

pytorch 的 riscv64 CI 在一天内改了两次判据：先加 Jenkins 返回码，再换成读统计文件。这类反复在小团队里很常见，但它暴露的问题不小——一个”构建成功但零用例执行”的流水线，会让所有下游的绿色徽章失去意义。判据从作业状态转向用例计数，方向是对的；真正稳定下来还需要把统计文件的口径固化下来。
