5.3 产业侧：进迭时空 V100 服务器级 RISC-V 处理器在峰会发布（10-19）

日期：2026-10-19　来源：Phoronix：SpacemiT V100

10-19，进迭时空（SpacemiT）在峰会期间发布服务器级 RISC-V 处理器 V100。按 Phoronix 报道，V100 采用 46 核混合架构——6 个香山昆明湖 V2R2 核加 40 个 SpacemiT X100 核，主频 2.2 至 2.4GHz，12nm 工艺，120W TDP，支持八通道 DDR5-4800 与 52 通道 PCIe 5.0，双路可达 92 核；厂方称其为首款完整符合 RISC-V 服务器规范的芯片，支持 UEFI、ACPI、SMBIOS。

对本主题的意义在于平台形态而非芯片本身：服务器规范把 UEFI/ACPI/SMBIOS 变成必需项，系统软件栈的适配路径与现有的开发板、嵌入式平台并不相同。当前 ruyi 0.54.0 的规划集中在 K1/K3 工具链适配与 ABI 兼容检测，支持矩阵以消费级与嵌入式板卡为主；服务器平台若要进入支持范围，需要新的固件、发行版与镜像链路。当日未见 RuyiSDK 或 openRuyi 针对 V100 的任何公开动作。

六、趋势观察

6.1 发行版打包策略转向按依赖打包：Rust crate 批量导入与 Go 去 vendor 同步推进

openRuyi 单日 221 笔提交里，约 200 个是新增包，其中绝大多数为 Rust crate；同日提交的 PR 又把 minio、picoclaw 从自带 vendor 归档改为使用发行版打包的依赖。两条线指向同一件事：发行版的打包单位从「上游源码树」变成「可复用的依赖包」，这既能减少重复打包、也让 CVE 修复可以按包下发（同期 CVE 批次正是按包拆分提交）。对 RISC-V 发行版而言，维护成本主要不在主包，而在依赖闭包的完整度，这批提交是补闭包的动作。

6.2 三条上游 fork 维护线分化：PyTorch 按日重放、LLVM 七日静默、Triton 夜间构建恢复

PyTorch 的 riscv 分支保持每日重放（本窗口 10-19 09:14 一次，属历史重写、无新补丁），上游 main 每日同步；LLVM 的 riscv 分支自 10-12 起七日无推送，两笔 FPGA 后端 PR 停在 10-13；Triton 的夜间出包在停更七日后于 10-19 恢复。三个仓库代表三种投入状态：一条流水线在跑、一条在等评审、一条刚恢复出包。观察点是 LLVM 分支是否随新上游基线重启，以及 Triton 夜间版能否回到逐日节奏。

6.3 服务器级平台进入视野：UEFI/ACPI/SMBIOS 规范要求改变系统软件适配路径

进迭 V100 把 RISC-V 服务器规范落到具体产品，规范里的 UEFI、ACPI、SMBIOS 成了硬要求。这与当前 RuyiAI/RuyiSDK 面向 K1/K3 等嵌入式与消费级平台的适配路径不同：后者以板卡镜像、工具链与支持矩阵为主，前者需要固件、引导与发行版安装链路整体对齐。openRuyi 固件线（ruyifirmware、edk2-ruyi）近两日转入静默，若服务器平台成为下一阶段目标，这条线的工作量与优先级可能需要重估。
