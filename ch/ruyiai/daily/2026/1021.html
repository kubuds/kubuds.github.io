三、向量扩展与算子优化

3.1 IREE 3.13.0 正式版：RISC-V V f32 vfmacc.vf MMA 进入 release（10-19）

日期：2026-10-19　来源：IREE v3.13.0 Release、PR #24933 RISC-V V inner_tiled MMA

IREE v3.13.0 于 10-19 19:26 发布，CPU 后端新增 RISC-V V f32 vfmacc.vf 的 inner_tiled MMA（PR #24933），把向量浮点乘加直接映射到 RISC-V V 的 fused multiply-accumulate；同时 LLVMCPU 的可伸缩向量化改为必须指定 --iree-llvmcpu-vscale-range，带 +zvl*b 特性时取两个下界中的较大值。模型侧保留 PT2E 的 per-tensor、per-channel-group、per-token 量化导入到 LinalgExt Q/DQ。

对本栈的意义在路径对照：RuyiAI 的 tilelang-riscv 与 triton-riscv 走的是 Tile 级 DSL 到 RVV 的路线，IREE 走 MLIR→LLVMCPU 可伸缩向量化。同一条 RVV 上，两种前端同时把 f32 乘加选为优化目标，说明该指令形态已成为 RISC-V AI 后端的共识落点。

3.2 验证与缓存侧：riscv-arch-test 三笔合入、香山 CoupledL2 分组存储体（10-19 至 10-20）

日期：2026-10-19 至 2026-10-20　来源：riscv-arch-test PR #2413 Sdtrig、PR #2791 S_F/S_V/S_VF、PR #2858 向量指令 SEW 覆盖、XSCache PR #36、XiangShan PR #6738

RISC-V 架构测试窗口内合入三笔：Sdtrig 的 A 扩展触发器覆盖点与 Sm/S/U 三模式 icount 覆盖（10-20 05:53）、向 S 套件添加 S_F/S_V/S_VF 以覆盖操作系统实际使用的特权层级（10-20 02:53）、向量指令扩展到所有有效 SEW 并补齐 SEW=8 的 vrgatherei16 与 fault-only-first 的 LMUL 选择（10-19 21:55）。三笔共同把验证面推向「S 模式 + 全 SEW」，对在 K1/K3 上跑 RVV 算子的团队是可用的回归基线。

香山侧，CoupledL2 按 set index 拆分目录与数据 SRAM bank，把 MCP2 停顿限制为同 bank 连续访问，并在 RequestBuffer 占满 2 个槽位时暂停接纳新预取（PR #36，10-19 15:12 合入，默认 bank 拆分值为 2、可回退为 1）；主仓随后更新 XSCache 指针纳入该变更（PR #6738）。缓存并行度与预取准入同时调整，属可核验的微架构变化。

六、趋势观察

6.1 依赖闭包建设按语言分三线并行：Rust 补 uv 后端、Go 去 vendor、Python 补云存储

本期 137 笔提交的 42/42/42 结构不是巧合，而是三条独立的补包线同日推进：Rust 侧围绕 windows-* 0.61、zerocopy/rkyv、cap-std/io-lifetimes 三族，配合 python-uv-build，指向 uv 这类 Python 构建工具的 Rust 依赖；Go 侧以 minio 与 Prometheus/Kubernetes 组件为主，配合去 vendor 的三笔 PR 把「随源码打包」改成「按依赖打包」；Python 侧一次性补齐 fsspec 的全部主流云后端。三条线的共同目标是把依赖闭包填满，让 RISC-V 上的 Python AI 与云原生部署不必现场编译。

值得记录的是这一层与 RuyiAI 的关系：PyTorch 的 DataLoader、checkpoint、数据集工具普遍经 fsspec 访问远端存储，后端齐备与否直接决定训练脚本能否在 K1/K3 上跑通。发行版替上层补的这部分依赖，比单个算子优化更能决定「能不能用」。

6.2 PyTorch 分支进入每日重放节奏：基线日更，补丁序列不动

连续两日观察到同一模式：10-19 09:14 与 10-20 08:32 各一次整枝重写推送，全分支提交者时间被统一改写，本地补丁标题逐条不变，变化只在上游基线的同步范围。这种做法把「跟上游」与「维护补丁」解耦，代价是分支历史不可追溯——任何按 SHA 引用的下游（CI 缓存、镜像构建、issue 复现）都会每天失效。若这一节奏固定下来，读取该分支时应以「补丁标题集合」而非 SHA 作为版本判据。

同期三条 fork 线的状态继续分化：PyTorch 每日重放、LLVM 自 10-12 起八日静默、Triton 夜间出包恢复到 10-19 一版后停住。三条线对应三种投入状态，也提示 RuyiAI 栈当前的瓶颈不在编译后端本身，而在评审与出包的持续供能。

6.3 服务器级平台给发行版带来的是兼容清单，而非新的移植任务

进迭 V100 的报道把 openRuyi 写进服务器平台的可用发行版清单。若这条成立，含义并非「openRuyi 要做一次新的移植」，而是一套规范符合性要求：RVA23、服务器 SoC/平台规范、BRS 与安全模型五项，加上 UEFI/ACPI/SMBIOS 的固件链路。发行版要做的更多是把已有的用户态包、安装器与镜像链路对齐到规范，而不是重写组件。

当前证据仍不完整：openRuyi 主仓当日零笔服务器相关提交，固件线（ruyifirmware、edk2-ruyi）自 10-15 起静默，2026.10 版本尚未发布。观察点有三个：openRuyi 2026.10 是否在发布说明中提及服务器平台；ruyifirmware/edk2-ruyi 是否恢复针对 V100 的提交；支持矩阵是否出现 V100 条目。
