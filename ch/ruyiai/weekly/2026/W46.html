2.1 triton-riscv：从”十八个夜间标签”到第一个正式发布

日期：2026-11-06 至 2026-11-14　来源：正式发布标签、PR #105 README 改为 wheel 优先

这条仓本周走完了三步：把发布层级立起来（第一个 release/ 标签）、把安装路径从源码改成 wheel、把异构后端从”能编”做到”能在真机上跑”。三步之间有先后依赖——没有可复现的 wheel 标签，GPU 后端的验证就只能停在源码构建；而 AMD 后端的验证又反过来暴露了发布链上几处只在自托管 riscv64 runner 上出现的问题。

2.1.1 标签本身是发布动作的全部内容

日期：2026-11-06、11-09　来源：release/20261108-6895885、PR #101

release/20261108-6895885 指向提交 6895885，也就是 11-06 那笔”为 AMD 补 riscv64 缺失 codegen 库”（#102）的合入提交，与夜间版 nightly/20261106-6895885 是同一个点。当天三笔提交（#105、#106、#107）都在标签之后落地，没有进这个包——这意味着第一个正式版打的其实是上周末的代码状态。

发布链的两处配套改动此前已在窗口内落地：#101 修 #100 之后暴露的两处发布链问题（发布工作流改用与 CI 相同的检出动作版本，scripts/release.sh 增加后端注册步骤，让 release 产出的 wheel 与 CI 构建的 wheel 具备同样的插件注册信息），#102 让 setup.sh 在检测到 AMD codegen 库缺失时本地构建并放到约定路径、env.sh 把 TRITON_AMD_CODEGEN_PATH 指向它。夜间版另加了唯一版本后缀 .dev<日期>，因为此前每次构建共用 Triton 自己的版本号，包索引会拒绝重复版本。

2.1.2 安装路径换成 wheel 优先，快速开始改成看反汇编

日期：2026-11-09　来源：PR #105、PR #107

#105 重写了 README 的安装段：先给 wheel 路径与承载它的包索引，再给所需的 LLVM 归档与指向变量；源码路径压缩成 make setup（建 .venv、克隆固定版 Triton、下载固定版 LLVM 与 buddy 构建），原先”建虚拟环境、装依赖、环境脚本十五个变量”的说明收成一条短注。#107 随后做了修正：包索引目前还没有 triton 与 buddy 工具，README 里那条二进制安装给出的地址会失败，于是改为指向两个项目各自的 GitHub releases、从磁盘装 wheel。同一笔还修了 Python 3.14 下 lit 崩溃——Triton 用 which 在 PATH 里找 lit，而 LLVM 树里那份 lit 在模块级调用 main，Python 3.14 在 Linux 上默认改用 forkserver 启动方式，重新导入时直接崩溃；修法是把构建解释器的 bin 目录放到 PATH 最前。

2.2 triton-riscv 的异构路线：RISC-V 宿主驱动 AMD 卡

日期：2026-11-10　来源：PR #110 默认启用 GPU 后端、README

#110 合入后，这条仓的定位从”只在 RISC-V CPU 的向量单元上跑 Triton”扩到”从 RISC-V 主机驱动异构加速器”。三条改动里，构建侧用现有 Buddy LLVM SDK 构建并打包 riscv64 的 AMD codegen 库；驱动侧修掉 CPU 与 GPU 二选一时的歧义，规则是优先选用可用的 GPU（该文件净删四行）；文档侧在 README 加 AMD GPU 一节，说明 ROCm 在位时后端通过 torch.version.hip 自行激活、wheel 不带 ROCm 运行时、强制回 CPU 用 TRITON_DEFAULT_BACKEND=triton_shared。

真机验证是这条改动的分量所在：SG2044 配 RX 7900 XTX，torch 与 ROCm 来自 openRuyi 的软件仓，另测了隐藏 GPU 设备时的自动回落。在一个主流 AI 加速卡都不带 RISC-V 宿主驱动的时点，先支持 AMD 卡是最现实的一步——ROCm 的 RISC-V 侧工作本来就在 openRuyi 仓里维护，两者是同一批人在推。

时间差值得记下：当天 10:22 出的夜间版 nightly/2026-11-10-209274f 早于这笔合入，因此那个包还不含 GPU 后端。

2.3 发布链与发布物：三笔 CI 修复、wheel 减重四成、显式目标改走 -O3

日期：2026-11-11 至 11-12　来源：PR #113 共享 git 认证、PR #116 wheel 瘦身、PR #117 -O3 与 +zvfbfmin

11-11 的三笔合入全在发布链上，没有一笔改编译器功能。#113 把 CI 与 release.sh 各自复制的一份”一次性全局 git 配置”抽成 scripts/_git-auth.sh 共用：自托管 riscv64 runner 上的匿名 git 流量拿不到认证，上游 FetchContent 拉 googletest 时返回 401 并在没有 tty 的情况下卡在用户名提示。#111 修发布脚本本身；#112 是文档，在 #110 之后删掉 CPU 路径已不需要的 torch 安装命令，并给 AMD 一节补上”要装 torch，而且必须是能用 AMD GPU 的构建”。三笔作者同一人，时间集中在 17:59 至 21:11。

11-12 的两笔开放改动方向都是发布物本身。#116 指出 wheel 里打进去的 LLVM 与 buddy 工具此前用 --strip-unneeded、调试段仍保留：triton-shared-opt 单个带九个 .debug 段、体积 407 MB，改 --strip-all 后降到 118 MB，七个工具合计载荷从约 970 MB 降到约 576 MB，约为原体积的六成。#117 改交叉编译路径的优化级别：显式给 RISC-V 目标三元组时，构建流程此前跳过 LLVM 中端、llc 用默认优化级别，MLIR 留在标量形式的循环到了目标文件里仍是标量；改动对这类构建先跑 opt -O3 与 llc -O3，不带三元组的原生路径（llc -O0）与 IME 路径不动。同一笔还把 +zvfbfmin 加进默认 llc features——否则可伸缩 bf16 在 llc 里直接中止，而 buddy-mlir 的 #1054 正是默认假设有该扩展，两边必须同步。这两笔在 11-13 日报里仍为开放状态，其中 #117 已于 11-14 15:19 合入主干。

2.4 pytorch：riscv 分支补 CI 判据，main 持续上游同步

4.2 i1 掩码按字节读写（#1052）

日期：2026-11-12　来源：PR #1052

memref 元素类型为 i1 时，可伸缩向量此前被直接拒绝（提示 a memref of i1 needs fixed vectors），因为 memref 每元素占一字节、i1 向量每位占一车道，只有定长向量有逐车道的下降。而 Triton 的 load/store 掩码恰好就是 i1 memref：走纯 VIR 管线加可伸缩向量时，325 个 Triton-RISCV 测试文件里 179 个卡在这个错误上，是本周七笔里影响面最广的一笔。

改法是按字节读写：连续访问用 i8 向量的 llvm.load/store，非连续的 strip-mined 区域用 vp.strided.load/store 全车道打开；顺带把 i1 车道按一字节计尺寸——此前首个动态向量为 i1 的区域按 1 位算，VLEN 256 下会得出 vector<[512]xi1> 这种十六组寄存器的规模。

4.3 libm-only 数学函数逐车道展开（#1053）

日期：2026-11-12　来源：PR #1053

LLVM 不肯在可伸缩向量上下降的数学函数（erf、erfc、cbrt、powf、atan2、acosh 等）改为逐车道展开：对 vector<[N]xT> 的 N 乘 vscale 条车道逐条 extract、调标量函数、再 insert。诱因是 convert-math-to-libm 对可伸缩向量的处理与定长向量一样、只算前 N 条，其余静默置 0——一个可伸缩 erf 在 VLEN 128（vscale 2）下有一半车道是错的。效果直接体现在测试面：FlagGems 套件 4045 项在 SG2044（VLEN 128）上通过数从 3980 升到 4006，修好的 26 项是 test_erf 与 test_gelu，无新增失败。

日期：2026-11-12　来源：PR #1054

5.1 VLEN 精确化的前半程：#1032 与 #1037

日期：2026-11-08　来源：PR #1032、PR #1037

#1032 解决的问题是一类错误的失败方式：不报错，只算错。按精确 VLEN 构建的 RISC-V 模型，向量代码只对那一个 VLEN 成立——llc 被明确告知 VLEN（+zvlNb 与 -riscv-v-vector-bits-max），decode attention 里的可伸缩向量也按它定尺。换到别的 VLEN 上，模型不崩溃，直接给出错误结果。

修法是把校验前移到加载时刻：runtime/rvv/BuddyRvvVlen.c 作为构造函数被链接进模型库，库一被载入就读 vlenb，发现与构建时的精确 VLEN 不符就打印信息并以 _exit(1) 结束进程。用 _exit 而不是 exit 是有意的——加载器持锁期间跑析构函数会死锁。评审后又补了一笔，把校验从”按构建变量判断”改成”按最终 llc 选项判断”：原先原生构建可能通过模型自带的 LLC_ATTRS 指定 VLEN，若 BUDDY_RISCV_VLEN 与它不一致，校验值会和实际代码不符；且只链接进了第三阶段，Qwen3-VL 的视觉与解码两个 shim、以及分层链接的路径都漏掉了。现在由构建脚本从最终 llc 选项里取出精确 VLEN（与 VIR 降低读同一处），配置阶段发现选项互相矛盾就直接失败。测试是这条改动的另一半：test_buddy_rvv_vlen.py 为 VLEN 128 到 65536 分别构建模型库，只有宿主那一个能加载，其余全部以退出码 1 结束。文档同步更新了 A210 与 K3 两篇 DeepSeek-R1 部署说明，把”哪些构建是精确 VLEN、哪些是通用 RVV”的边界写清楚——A210 的内核是定长向量、没有 VIR，属于通用构建；K3 的 prefill_ime 必须 1024，属于精确 VLEN。

#1037 修的是另一个方向的错误：-lower-vir-to-vector 在不给 rvv-vlen、也不开可伸缩向量时，按宿主寄存器宽度给定长向量定尺，但它的宿主识别只覆盖 x86（AVX2、AVX-512）与 SVE，带 V 扩展的 RISC-V 宿主一律落到通用默认值（128 位、16 个寄存器）。后果出现在测试里：自 #1030 起，kernels 流水线在没有 llc 选项时按宿主降低 VIR，riscv64 CI 宿主是 VLEN 256 却被当成 128 位处理，q、k 范数的平方被切成 vector<32xf32> 分段求和，与矢量内核逐比特比较的顺序不同，vir decode qk_norm ... same bits 判定为假。作者先加了一笔只在测试里固定 rvv-vlen=1024 use-scalable=false 的改动，随即自行回退——那等于在 llc 选项之外再造一处 VLEN 设定，与 #1032 的方向冲突。最终修法是在降低阶段识别 RISC-V 宿主（读取宿主 CPU 特性与 hwprobe），按真实 VLEN 定尺。

5.2 f32 YOLOv8 端到端走通 VIR（#1041）

日期：2026-11-09（合入于 11-10 01:07）　来源：PR #1041、合入提交 18c66ec

#1041 把 f32 YOLOv8 图端到端走通 VIR：先做 Linalg 到 VIR 的降低，再做 VIR 到向量方言的降低。此前这条 pass 里没有卷积 pattern，图里另有三类算子直接失败——一笔改动同时补上了卷积与那三类。规模是十四个文件、新增一千六百四十六行、删除一百一十五行、十三个提交。

卷积两族都覆盖：二维 NHWC 配 HWCF 与二维 NHWC 配 FHWC。向量化沿输出通道 F 展开，对每个 (kh, kw, c) 把输入元素广播成每个输出像素一个 vir.fma，因此每次向量访问都是连续的，也没有跨 lane 的归约——归约需要横向指令与后续的规约树，在窄 VLEN 上代价明显；代价是 FHWC 过滤器要先并行拷贝进 HWCF 缓冲，多一次搬运换内层循环的连续访问。

三类此前失败的算子一并补齐：rank-0 输入（memref<f32> 直接进 linalg.generic 会在 memref.expand_shape 报 invalid reassociation，改为加载一次后广播）、保留末维的 linalg.reduce（如 DFL softmax 的 1x16x4x2100、dimensions=[1]、addf 与 maximumf 组合）、读取 linalg.index 的命名算子（如 upsample 里的 linalg.map iota）。真机口径很清楚：在 K3 上 f32 YOLOv8 pose 的原始输出最多变化 6e-5，与 PyTorch 的差距仍在 6e-4（bus）与 8e-4（zidane）以内、与改动前一致；detect 模型的检测结果不变、速度没有下降；f32 与 IME 动态库的输出与改动前逐字节相同。

5.3 YOLOv8 进 rax：检测与姿态跑上 K3 矩阵引擎（#1042）

日期：2026-11-10　来源：PR #1042

#1042 把 Ultralytics YOLOv8 接进 buddy-cli 的 rax 格式：yolov8n 检测（八十类 COCO）与 yolov8n-pose（十七个关键点），输入都是 320x320。f32 模型走 VIR 降低，规格里写 ime: true 则改跑 SpacemiT K3 的矩阵引擎。

评审阶段补的两处修正比模型本身更有信息量。一是权重校验：清单里带 params_size，运行器要求权重文件与它一致，此前权重文件偏短会让模型读过缓冲区；同时要求运行器只接受 rax 包，因为单独给库与权重时姿态模型会被按检测模型的参数跑起来。二是 TCM 拷贝：IME 权重的 TCM 副本按权重地址缓存，新权重读进已释放的缓冲区时会命中旧副本，现在每次权重装载后调用内核侧的失效函数。规格里同时保留 params_size 与 ime_params_size，这样 ime: false 时仍能构建 f32 版本——同一张图、两条后端路径、一份可对比的基线。

七、趋势观察

7.1 发布链先于功能：这一周修的是”能不能出包”

triton-riscv 一周内的合入里，只有 #110（AMD 后端）是功能，其余 #101、#102、#105、#107、#111、#112、#113 全在发布链上：后端注册进 wheel、AMD codegen 库的本地构建、README 的 wheel 优先、lit 查找顺序、git 认证抽取、AMD 一节的 torch 前提。再加上 #116 的 wheel 瘦身与 #117 的 -O3，这条仓本周的产出可以概括为”让装机路径可复现、可下载、可验证”。

这不是个别现象：ruyi 0.54.0 的主要内容也是”装之前先判能不能装”，pytorch 的 #56 堵的是”零用例通过也算绿”，buddy-mlir 的夜间版补的是六天的出包缺口。四个仓同周做同一类事，说明这条栈已经从”证明能跑”进入”证明能交付”的阶段。

7.2 覆盖面优先于性能：393→0、2→0、179→0 的口径

本周 buddy-mlir 七笔里只有 #1055 直接改变指令选择，其余六笔做的是把此前留在循环里的形态接进向量路径：i1 掩码、libm-only 数学函数、bf16、归约种类、rank-0 填充、整数矩阵乘。评价这类改动的口径应当是”还剩多少 linalg 或标量路径”，而不是跑分——393 降到 0、2 降到 0、179 个失败文件归零，都是这个口径。

对照前一天 #1050 的 strip-mined 余量降宽，两天的分工很清楚：先让向量循环吃满车道（性能），再让所有算子都能进向量循环（覆盖）。顺序反过来会做无用功——空有满宽度的循环，进去的算子还是那几个。

7.3 VLEN 1024 成为编译器与运行时的共同压力点

一周内有三处改动直接指向 VLEN 1024：加载期校验（#1032）、归约丢车道（#1051）、strip-mined 余量（#1050）。共同点是同一个硬件事实在各层反复出现——K3 的 prefill_ime 必须 1024，A100 核上 16 个 f32 就是一个完整向量，vector<[1]xT> 这种形状在 VLEN 128/256 上根本走不到。

同一周的上游侧也出现同一信号：V8 的审阅名单里出现 “Allow vlen=1024”（CL8585179）。这说明长向量不再只是某块板的本地配置，而是开始进入运行时与浏览器的通用路径。风险随之而来——CI 的 riscv64 runner 是 VLEN 256，出货硬件是 1024，两者的测试覆盖天然错位；#1051 那种”CI 全绿、板子上全错”的缺陷，正是这种错位的产物。

7.4 静默错值的验证成本已到穷举输入的量级

#1054 对 truncf 跑了全部 2^32 个 f32、对转换与符号运算跑了全部 2^16 个 bf16；#1055 在 4M 车道上逐位比对 fmaf 展开；#1041 的验收标准是”与改动前逐字节相同”；#1051 的验收标准是 25 项归约测试从错到对。四笔的验证方式不同，但都在回答同一个问题：结果对不对，而不是跑得快不快。

原因也清楚：这一周修的缺陷几乎全是”不报错、只算错”——按精确 VLEN 构建的模型换硬件静默出错、可伸缩 erf 有一半车道被置 0、归约只剩 lane 0、掩码按位算尺寸导致十六组寄存器。崩溃容易被发现，错值不会。当验证成本上升到穷举输入的量级时，说明这条栈已经按出货标准对待 bf16 与归约这些基础算子。

7.5 滚动打包与月度定版脱钩

openRuyi 打包仓本周提交密度是近期最高（单日峰值三十六笔，KDE、安全、工具链、设备面四条线并进），而对外可见的月度版本仍停在 2026.09。两件事不矛盾：滚动打包与月度定版本来就是两条线，日更说明工程在动，缺版说明发版流程或验证周期卡住。

值得留意的是本周新增的两个治理仓：release 规范仓把需求编号与优先级写成流程，ruyi-deck 定位为”仓库与发布的操作台”。两者都不产出代码，指向的却是同一个缺口——一个月度版本要跨打包仓、镜像、固件多个仓发，缺的不是提交，而是把提交收敛成一个可发布版本的那道工序。

7.6 “能不能装”第一次变成可计算的事实

ruyi 0.54.0 把 ELF ABI 兼容性做成三态判定（兼容、不兼容、未判定），并在 list、install、admin check-abi 三处暴露。这件事的意义不在功能本身，而在把”这个包能不能在我的机器上跑”从经验判断变成可查询、可比对、可排障的数据。

对 RISC-V 尤其重要：同一份预编译二进制在不同扩展组合、不同浮点 ABI 的宿主上行为不同，过去只能靠试。三态设计还留出了”未判定”这一档，避免把未知当成不兼容——这个区分决定了工具在真实环境中是否可用。下一步可观察的是 sidecar 的覆盖面：哪些包补了 ABI 信息、哪些仍是”无信息”，080 期提到的 packages-index 为部分包补 ABI 兼容信息，是这条线的延续。
