11-04 15:40 的 f346011 是本周唯一一笔真正的编译器改动（8 个文件、+412/−1，作者 caihanyi111）。它分两块：其一是寄存器归类，循环携带的累加器 PHI 从类型表取默认寄存器类，而 nxv32i32 原先只注册为 TileReg，累加指令 mlce32.m、mqma.*、msce32.m 的累加器操作数与结果都限定在 AccReg，于是每条循环边都要在 tile 与 accumulator 两个寄存器堆之间生成一次复制，而 copyPhysReg 无法把这种跨堆复制展开成单条 AME 指令；修法是给 nxv32i32 同时注册 AccReg，同堆的整寄存器复制改用 mmve64.t.t 与 mmve64.a.a 展开，跨堆复制保留为硬错误。其二是调度，每份 tile 配置与其消费者被保持在一条有序、带副作用的伪指令里直到 emit 前才展开，矩阵寄存器改为可分配、MMA 的累加器做 tie、零累加器的定义不读旧值。提交同时新增三份测试，覆盖配置化 load/MMA/store 顺序、同堆与跨堆复制、以及 RVV 与非 RVV 两种选择。

triton-riscv：一天之内从「打补丁的分支」变成「上游插件」（11-05）

日期：2026-11-05　来源：PR #98、提交列表、PR #92

改造分三处。第一处是后端形态：Triton 的 TRITON_PLUGIN_DIRS 机制把 backend/ 装成 triton_shared 后端插件，注册入口点、把 C++ 插件链进 libtriton.so、把 triton-shared-opt 一并复制进包；独立发行包随之消失，代码里的导入统一改走 triton.backends.triton_shared；后端自身改为通过 paths.py 查找 buddy-opt、buddy-llc、mir-translate 与 triton-shared-opt，CPU 驱动声明自己仅在没有任何 GPU 后端时才处于活动状态。

第二处是补丁集清零。patches/ 目录与施加补丁的脚本全部删除。补丁集此前存在的理由有两个：让 Triton 在没有 NVIDIA/AMD 工具链的环境里构建，以及兜住 LLVM API 的频繁变动。现在 buddy-mlir 的 LLVM 发行版带 NVPTX/AMDGPU 目标与 lld（#1027），再把 Triton 的 GPU 依赖路径指向 stub 目录，两个理由都不成立。

第三处是出包路径合并。release.sh 不再组装第二个 wheel，只剥掉工具、直接 bdist_wheel；Makefile 成为 setup、build、test、lit、clean 的统一入口。顺带修了一处 Python 3.14 的坑：setup.py 里 shutil.which("lit") 会优先取 pip 安装的 lit 控制台脚本，而 LLVM 发行版自带的那个调用 main() 时没有 if __name__ == "__main__" 保护，forkserver 多进程在导入主模块时会重跑它，lit 目标在 80 并发下因此失败。

代价写在同一个 PR 的说明里：Triton 3.9 的前端会从后端读取 backend_name 等字段，缺了它每个 tl.atomic_* 调用都会抛 AttributeError，riscv64 上有 383 个 FlagGems 用例因此失败；补上 backend_name、default_dot_input_precision 与 deprecated_fp8_dot_operand_dtypes 三个字段后失败面才收掉。示例侧也有让步：上游拒收了 asin/acos/atan/atan2 的前端补丁，例子改用 libdevice，靠它降到同样的 __nv_* extern_elementwise，再由 triton-shared 转成 MLIR math 算子。

七、趋势观察

分发链路打通，但「打包完成」不等于「能力同步」

#1350 的意义不在版本号，而在分发路径第一次被写成发行版配置：以前要用这套栈，得自己拉 triton-riscv、tilelang-riscv 与 buddy-mlir，按文档设 BUDDY_MLIR_BINARY_DIR 一类变量；现在 openRuyi 的打包仓里有了这三个组件，用户的安装门槛从「会编编译器」降到「会装包」。

但三份 spec 锚定的代码都早于本期上游：triton 停在 09-13、tilelang 停在 10-28、buddy 停在 0.1.2，而三个仓库本周都还有新动作。最刺眼的是 tilelang——11-03 刚合入的 PR #5 是十八天静默后的第一笔功能，却不在当天合入的 RPM 里。版本串 3.8.0+git20261103 会强化误读，把打包日期当成代码日期。要解决这个落差，要么建立定期的 bump 流程，要么在包描述里写清快照日期；否则每合入一笔功能，包与仓库的差距就再拉大一点。

插件化把补丁成本换成版本绑定，383 个失败用例是首付

triton-riscv 的收益很直接：以后跟随上游升版不再需要重放补丁，出包只剩一个 wheel，安装面从两个发行包降到一个。代价同样明确，而且是同一天暴露的：Triton 3.9 的前端从后端读 backend_name 字段，缺它就有 383 个 FlagGems 用例失败。寄生在上游扩展点意味着上游前端的隐式契约变成必须满足的接口，而这些契约往往没有文档，只能在测试里撞出来。

判断这次改造是否成功，不看今天删了多少行，看下一次上游升版时重放的成本，以及 FlagGems 这类下游套件是否还需要专人盯版本。到本周末，跟随上游的路径已经清晰，配套的验收流水线仍未建立：#56「Migrate additional FlagGems operators」仍是开放状态，「这批算子能不能在 riscv64 上跑通」这个问题仍然只能在 PR 里回答。

后端成为本周主轴，前端与运行时静止

本周的可核增量几乎全部落在「编译与降级」：LLVM 的 AME 后端补寄存器归类与 tile 调度、buddy-mlir 的 BOSCAME 打通契约到 FPGA、VIR 把 set_vl 的 VLEN 语义收紧、tilelang 补 streaming load 的降级路径。与此同时，pytorch 的 RISC-V 分支三次重放、零功能增量，main 侧一百余笔上游同步里没有一笔涉 RISC-V。

这个分布说明这一阶段的重点是让已有算子在 RISC-V 上降得对、跑得稳，而不是扩大前端覆盖面。对下游使用者来说，短期内可感知的变化会出现在编译产物与 JDK 行为上，而不是新框架支持列表里。与之配套的短板也在同一处：性能方向唯一一条明确以优化为目标的 triton PR #85 仍停在 10-18，半个月没有动静。

发版节奏：beta 出了，正式版与月度版仍在窗口外

十月末两条月度承诺同时落空，十一月第一周各有一半下文：ruyi 在 11-02 出了 0.54.0-beta，39 天断档后第一跳，并把 0.54 的正式版定到 11 月 11 日前后；openRuyi 的 2026.10 月度公告到 11-07 仍未出现，成为首个整月缺版。

两条线的代码侧都不算停滞——openRuyi 主仓本周 156 笔提交，ruyi 有 ABI 探测与取包修复落地——所以卡点在版本冻结、公告撰写、镜像构建与发布这一段。这与上周的判断一致：这个生态的「把东西做出来」与「把东西发出去」是两套能力，前者在多个仓库同时推进，后者在近两个月里没有一次按期完成。

基准侧长期空白，让「优化是否有效」无法回答

VecIntrinBench 停更近九个月、IntrinTrans 四个月、FBGEMM 三个月，三个仓全周零提交。同一周里，glibc 与 newlib 补了十八个向量数学函数、LLVM 合了六笔 P-ext 与 Ztt v0.6、buddy-mlir 铺开 209 个文件的矩阵后端——能力在扩张，度量没有跟上。

后果不是抽象的：没有更新的内建函数基准，就无法回答「编译器实际支持集合涨了多少」；没有常驻的性能基线，就无法回答「BOSCAME 路径比旧路径快多少」。本周所有与性能有关的表述都只有「未观察到明显回归」这一级别，而这类表述无法支撑选型。

桌面包与 AI 栈并行，两条线不在同一个节奏上

openRuyi 一周 156 笔提交，其中 74 笔是 firecracker 的 Rust 依赖闭包、37 笔是 LibreOffice 依赖链——这是按组件分批推进的桌面办公套件打包。同一天（11-05），RuyiAI 栈除 triton-riscv 外全部静默：pytorch 的 RISC-V 分支零提交、tilelang-riscv 零提交、llvm-project 的 riscv 分支零提交。

两条线由不同的人、不同的仓库、不同的节奏推进。对读者而言，把打包侧的活跃当作 AI 栈的进展是一种误读；对项目而言，这种分工本身没问题，但周报层面必须分开记——否则「提交数」这个指标会持续给出错误的繁荣感。
