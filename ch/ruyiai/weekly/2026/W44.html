日期：2026-10-26　来源：InsertVSETVLI 迁移、PreAllocZilsdOpt 迁移、DeadRegisterDefinitions 迁移

七、趋势观察

VIR 走完「表达—调用—对账」，但结论只能是「不引入损失」

过去三周这条主线一直在补表达力：10-26 一夜七笔把可伸缩向量补进来，10-27 补上 Python 绑定，10-28 直接把 K3 的解码注意力整段搬过去，并拿板上吞吐做对账。三个数字合起来才是这周的意义——数值位级一致、向量指令数相同（各 178 条）、吞吐区间重叠。自研方言最容易卡在「能跑但慢」这一关，本周至少证明这一关暂时过了。

但把它读成「VIR 已追平手写内核」就过头了。准确说法是「在 K3 解码注意力这一段、在固定向量长度下不引入损失」。两处缺口明确：覆盖面只有解码注意力，A210 内核、MoE、量化与预填充路径都没动；可伸缩向量被显式关闭（use-scalable=false），下一笔打开之后向量尺寸不再由编译期决定，LMUL 4 的分组假设会松动，届时数值与指令数能不能守住，需要重新对账。作者自己也把同一份代码两次构建的 2% 差异写在 PR 里，这个量级恰好说明「持平」结论的边界。

分支治理分道：llvm 写规则并取消预演，pytorch 靠重放与同步机器人

同一个月内两条分支给出了两种答案。llvm 的 riscv 分支补丁集大（26 笔）、外部贡献多，冲突与历史漂移是主要成本，于是值得写文档（RISCV_CONTRIBUTING.md）与配工作流（autorebase.yml），并把「预演」这一步删掉——成功即推送，把摩擦降到最低、把风险前移给贡献者，靠 --force-with-lease 与 SHA 复检兜底。pytorch 的 riscv 分支补丁集小（11 笔），维护者自己重放一次的成本低于维护流程的成本，于是继续每日或隔日整枝重放，再加一个同步机器人把基线抬到上游最新。

两者的共同点是「本地补丁集长期不变」：llvm 的 26 笔、pytorch 的 11 笔，本周都没有新增功能。跟踪这两条分支的正确方式不是看 SHA 或提交数——重放会把提交者时间统一改写、把提交数随上游膨胀——而是看补丁标题集合，以及上游带进来了什么（本周是 17 个 pass 迁入 NewPM 与 P 扩展的 isel 补齐）。

判断一条分支治理是否见效，可以看两个可验证的信号：llvm 这边，工作流上线后外部 PR 是否真的变多（若两周内仍无人按新基线提交，说明瓶颈不在重基工具）；pytorch 这边，重放是否重新稳定为每日（本周是七日静默后一次补做，属择期而非流水）。

打包成为 RuyiAI 栈的真实瓶颈，争论开始有价格

#1350 争论了将近一个月，核心分歧是 buddy-mlir 自带的 LLVM 要不要外置。上周的口径还是「可以用 GCC，但至少 1.5 倍时间」，本周作者给出实测：riscv64 上 8814 秒变 24798 秒，2.81 倍，且用 GCC 那次在链接阶段失败。争论的性质于是从技术偏好变成构建农场的排期算术——2.81 倍意味着机器占用、超时策略与发布窗口都要重算。

这条对整条栈的启示在方法而非结论：RISC-V 发行版打包的许多分歧（是否 vendor、是否外置工具链、是否随包分发 IR），最终都要落到「构建时间、镜像体积、可复现性」三个可测的数字上。同一周里 openRuyi 收回「随包分发 LLVM IR」的路线（#1509），#1350 用 2.81 倍守住「LLVM 留在包内」，两次判断方向相反，依据却是同一类成本核算。

更进一步看，#1350 本周的复核意见已经从设计路线转到 spec 写法（缺 BuildRequires、Provides 对齐、补丁格式、空 %check 注释），说明「能不能被发行版吞下」的问题已经变成「包本身够不够常规」。三处非常规点——buddy-mlir 自带 LLVM、triton 依赖 git 可执行、tilelang 需要发现 buddy-mlir 工具链——每一处都需要补丁与解释，每个解释都要维护者花时间判断。若希望三件套进入月度发行节奏，把它们收敛成一两条明确的打包约定（例如统一由 buddy-mlir 提供工具链、统一用 git format-patch 的补丁堆叠），比逐条回应复核意见更省事。

月末承诺集体后移：发行版转入「按月铺量、按周清扫」节奏

本周两个月末承诺同时落空：ruyi 0.54.0 仍只有 09-18 的 alpha，openRuyi 2026.10 未发。与之对应，openRuyi 主仓本周 234 笔提交里，KDE 框架一次 64 包、Samba 全家联动、qemu 11.1.2 与 libvirt 回移、12 个 C/C++ 安全更新——这是典型的「铺量与清扫并行」，而不是「切版本前的冻结」。

两条流水线的节奏差异也值得记：KDE 包有上游 spec 可参照、有既定版本节奏，重打包是机械动作，所以能在一天内完成 64 个包；而 RuyiAI 三件套是从零写的 spec，既要解释「为什么把 LLVM 留在包内」，又要解释「为什么 %check 为空」，从 09-21 开到现在仍在返工。发行版的「按月铺量」能力与「接纳新包」的成本并不对称，后者取决于包本身有多常规。

对读者的实际含义：ruyi 用户在 10 月底仍会拿到 0.53.0；若 0.54.0 在 11 月初发布，还要看 ISCAS 软件源是否恢复，否则 ruyi update 看到的包清单会落后于仓库实际状态。这两件事是下一周期的首要核实项。

缺陷发现依赖单一入口，验收链比修复链更脆弱

本周三笔 triton-riscv 修复的共同来源不是测试套件，而是「把 FlagGems 算子搬上 triton-riscv」这件事本身：张量填充值的掩码加载、循环携带的 gather 偏移、散列算子的重复索引比对，三者都落在降级层与验证层的边界上。这类缺陷在编译器自己的 lit 套件里长不出来，得有一个真实算子库按批量方式往上压。

顺序问题随之暴露：修复先落地，需要它们的迁移 PR #56 却停在 09-16。一批「为某个用法准备的修复」暂时没有对应的用法在跑，若 #56 恢复时 Triton 上游又换了几轮，三笔修复是否还与新基线兼容需要重新验证；若长期不恢复，这套端到端验收集等于停摆，下一批缺陷要等外部使用者撞上。周期末尾 #56 有一次更新（10-30 20:50），但仍未合入——这是下周期最值得盯的一处。

推论是可以落地的：对一个以「能跑真实模型」为目标的栈，把迁移做成常驻回归（哪怕只有几十个算子、每晚跑一次）比再多合几笔修复更有价值。工具链层面的证据也在同一周出现——#83 的验证是本周三笔里最硬的一笔（lit 291 通过、18 项运行时检查），而它恰好也是与真实算子集成最深的一笔。

基准侧长期空白，让「优化是否有效」无法回答

VecIntrinBench 停在 02-13、cpuinfo 停在 05-20、IntrinTrans 停在 06-25、FBGEMM 停在 07-13——四个向量相关仓库全周零提交，停更时长以月计。与此同时，本周的性能结论只能靠 K3 板上的吞吐区间，而作者明确写下同一份代码两次构建可差 2%；三笔修复的验证也只给通过数，不给向量化质量的任何指标（指令条数、占用 LMUL、寄存器溢出次数）。

这不是本周新增的问题，但三笔合入与一次性能对账把它照得更清楚：一条以「向量能力上行」为目标的栈，缺少持续跑分的向量内建基准，就很难判断后续优化是真提升还是波动。下一步真正该补的不是更多 lowering，而是一个每晚能跑、能给指令数与 LMUL 的基准——否则「性能持平」与「性能提升」在 2% 噪声下无法区分。
