安全与审计

日期：2026-11-09 ~ 2026-11-13　来源：主仓库缺陷列表、提案 #12015、提案 #12016

  • 信任边界是本阶段的主线：11-10 的两笔最重的改动都在改「先信外部、再判类型」——dlmodule 计算重定位写目标时用「模块内存基址 + 偏移 − 虚拟起始地址」而不校验范围，构造过的 .mo 可在重定位阶段写进内核内存（#12016，五文件 +205/-37，合入）；LWP IPC 系统调用把用户传入的裸对象指针直接送进 rt_sem_*、mutex、event、mailbox、mq、timer，伪对象即造成任意内核读写（#12015，三文件 +284/-44，仍在审）。
  • 网络与文件系统侧：NFS 读路径把服务端返回的 count 直接当 memcpy 长度，异常或恶意服务器可写穿调用者缓冲区，修法是收敛到「服务端计数、请求计数、已解码长度」三者最小并把 XDR 上限收紧到 1024 字节（#12012，11-12 合入）；9PFS 的 getdents 把 16 位 name_len 截断写进 8 位 d_namlen、大于等于 256 的值回绕后绕过检查（#12035，仍在审）。
  • 配置常量与账期：DHCP 服务端的 lease_end 写入后从不被读取，租约永不过期；DHCP_DEFAULT_LIVE_TIME（0x80510100）经 PP_HTONL() 后在线上约六十八年，与「按天回收」的语义不符，一并改为 86400 秒（#12024，仍在审）。内存池一笔修的是假警报但造成真实停摆：释放「最后一块、next 指向 heap_end 哨兵」的块会误触发断言（#12014，11-12 合入，对应 2025 年旧缺陷 #10632）。
  • ptyfs 泄漏与 legacy USB 的拉锯：pts 注销路径没有释放注册时分配的 struct ptyfs_file，反复 open()／close() /dev/pts/* 可被普通用户持续触发（#12023，11-10 报告），维护者十二小时后给出 #12029（仍在审）。legacy USB 主机栈把设备回报的 bLength 当完整描述符读取长度，可越界写（#12026）；维护者 #12027 做长度校验后以「legacy 代码、不再持续修正」关闭；11-12 凌晨另一位报告者重提 #12036（五文件 +71/-13，覆盖 hub 描述符与 wMaxPacketSize），11-13 09:47 合入。
  • vDSO 时钟常量：两次提案、两次关闭：newlib 工具链编 RT-Smart vDSO 用户代码时四个时钟常量未定义（#12025）。首份补宏提案 #12028 当日关闭；第二份兼容头提案 #12041 于 11-13 06:04 关闭，议题以已完成状态关闭，留言为「先关闭、后续需要给出一些关系说明」。落点从改代码变成补文档：Smart 的工具链必须使用修改过 musl 库的专用编译器。
  • 验证口径一致且保守：本周合入的安全提案绝大多数标注「静态核对、未跑板、未构造 PoC」，唯一带自动化用例的是内存池那笔（四十余行测试），NFS 那笔有评审逐条核对实现。11-13 批次同样如此，进 release 之前不宜当作已验证的防护。

六、趋势观察

  • 审计线从「批次提出」走到「批次兑现」，节奏依赖两个人：11-10 一天十一笔、11-12 凌晨七笔，11-12 与 11-13 两天合入 28 笔，其中 11-13 单日 22 笔。日报记录的结构很清楚——提案多出自同一账号，合入多由同一位维护者完成。效率高，但这条线的吞吐完全取决于这两人的时间；一旦其中一端停顿，队列会重新堆起来（11-11 至 11-13 提案数从 149 涨到 163 就是证据）。
  • 攻击面统一收敛到「外部输入先判后拷」，但验证仍是静态的：六项 2024 年 CVE 与自家议题两个批次，修法几乎都是把长度或索引的判断挪到动作之前。代价是这批修复全部标注「未烧板、未构造 PoC」，唯一带自动化用例的是内存池与 utest 相关两笔。对下游发行版，这批补丁在进 release 之前只能算「已审读」，不能算「已验证」。
  • RISC-V 的权重在这一周明显上升：FPU 上下文（fs0 至 fs11 与 fcsr）、APLIC 的 EOI 时机、PLIC 的完成次序，三条都在一周内闭环；同时 M0 与 M23 的 HardFault 栈选择、VTOR 为零两笔也补齐。但三条 RISC-V 缺陷全部由同一位报告者在 ArtInChip D213 的 M 模式、不开设备模型的场景里发现——非 DM 路径没有常驻 CI，这是结构性缺口，不是个人勤奋能补的。
  • 测试基建开始「吐账」：utest 多轮运行上线第三天就抓到 core.atomic 每轮 25 KB 的泄漏，dlmodule 回归进了 QEMU CI，QEMU 虚拟设备清单（#11972）要求的逐框架勾选正在变成用例。这条线的价值不在当周，而在于它让「Z 版本能不能发」有了可核对的证据链。
  • 版本节奏仍未动，发布前置条件比发布日期更值得看：v5.3.0 停在 09-10，两个月无 tag；主线的动作集中在缺陷与测试，而不是版本号。上周出现的版本管理流程（#11956）与 QEMU 测试清单（#11972）仍是两份纲领性文档，本周没有新的评审结论——下一阶段的观察点是清单能否在 QEMU 上真正跑通，而不是 5.4.0 什么时候发。
  • 对外传播双轨化，产品叙事向功能安全倾斜：官网接口静默满一周，公众号侧连发大赛、STM32 巡回与 TC397X Safety OS。后者的措辞值得记：从「偶然正确地运行」到「在明确边界内受控运行」，把安全从认证清单翻译成了运行时的四层保护。这比 11-06 那批「25 亿装机、30 万开发者」的规模口径更能说明产品当前的重心。
