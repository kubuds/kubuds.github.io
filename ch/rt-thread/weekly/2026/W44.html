RT-Thread周报（2026-10-26 ~ 2026-10-30）

2026-10-30 苦芽科技

报告周期：2026 年 10 月 26 日（周一）至 10 月 30 日（周五），5 个工作日、5 期日报；另含发布日（10 月 31 日）对主仓库提交流、提案与缺陷队列、发布页与标签页的核查，覆盖 10-30 08:00 至 10-31 17:00 的收尾变动

一、本周要闻

  • RT-Thread Smart 十天排队后集中在一天落地，七个半小时后又被收回默认配置（10-29）：10 月 18 日创建的提案 #11896 于 09:29 合入，给 qemu-virt64-riscv 与 qemu-virt64-aarch64 打开 RT-Thread Smart，14 个文件、+1263/-1075、14 笔提交，新增 applications/mnt.c 把 virtio-blk0 挂成根目录并挂载 ptyfs 与 procfs；14:48 与 14:50，终端兼容提案 #11890 与 lwp 系统调用拆分提案 #11894 接连落地；16:59，提案 #11942 又把两个 BSP 的默认配置整体恢复为标准内核（7 个文件、+51/-220），Smart 改由 utest 的配置覆盖层单独运行。同一天完成「打开—验证—收回」，实际是维护者在给 Smart 划定位置：默认配置保持可预测，Smart 走独立覆盖层。

  • RT-Smart 的 ioctl 用户指针边界连报四单，从终端一路延伸到块设备、管道与邮箱（10-28 ~ 10-31）：10-28 的 #11937 指出终端子系统移植时丢掉了 FreeBSD 的 copyin 前提，非特权进程用 open 加 ioctl 即可读写任意内核内存；10-29 的 #11952 在块设备侧重复了同一形态，24 字节分区表被写进调用者指定的内核地址；10-30 的 #11958 落在 POSIX 管道，FIONREAD 与 FIONWRITE 直接把环缓冲长度写进未经校验的用户指针；10-31 的 #11960 上升到邮箱，sys_mb_send() 把用户给的指针当内核对象直接转发，可构成任意内核读写。四单共同成因是 RT-Smart 的 ioctl 适配层默认「参数已是内核地址」，而用户态入口没有做这一层转换。终端侧的修复提案 #11941 已于 10-28 晚提交（6 个文件、+577/-52），其余三处尚无对应修复。

  • 主线 21 笔提交、16 个提案，节奏是「先停摆、再集中清账」（10-25 ~ 10-30）：本周 master 共落 21 笔提交、16 个提案合入，分布为 10-25 一笔、10-26 零笔、10-27 四笔、10-28 七笔、10-29 七笔、10-30 两笔。10-27 至 10-29 的合入里有相当比例是压了九天以上的积压提案——10-27 那四笔的作者时间是 10-18，10-29 的 Smart 一组也是 10-18 创建。这与上周「三日静默、三小时收尾」的判断同源：开发侧产出集中在评审通过后一次性落地，而不是每日匀速推进。

  • 车规 TriCore（AURIX）以「工具链先行」的方式进入 Env SDK（10-26）：RT-Thread/sdk 的两个提案先后合入，tricore-gcc v13.4.1（GCC 13.4.1、binutils 2.40、newlib、GDB 14.0，覆盖 TC2xx／TC3xx／TC4xx 三代芯片）与 qemu-tricore v1.0.0（QEMU 10.2.94，支持 TC277、TC397B 与 TC4D7 三台机型）分别发布在 toolchains-ci 的 v1.12 与 v1.13。需要分清的是这只是编译与仿真通路：主仓库 libcpu 现有 19 个架构中没有 tricore，bsp 下也没有 AURIX 板级目录，2020 年前后那批依赖 TASKING 商业工具链的尝试均已关闭。与旧路径相比，这一步先解决了「能编、能跑、能调」。

  • 压了三个多月的测试提案一次合入四笔，测试基础设施集中补课（10-28）：7 月 9 日创建的 #11601 于 10-28 14:44 合入，带进 utest 汇总统计修复（后续 unit 通过不再抹掉前面 testcase 的失败数）、netdev 用例切断对 8.8.8.8 与百度的公网依赖、musl 下 signal 0 不再参与安装，以及两处 clang-format 整理。三类问题都属「测试跑错了但报表说没事」的反向风险，修完之后 CI 的判定才可信。与之配套的是 10-29 的 #11942 重写了 utest_auto_run 的配置选择逻辑，把「整份 git checkout 覆盖」改成向 .config 追加一行关闭开关。

  • 时间子系统一夜开出四单，两笔修复转入可合入状态（10-23 ~ 10-26）：同一研究者在 ctime.c 上连续报出 settimeofday() 的 long 类型窄化（ILP32 下 2040-01-01 这类合法时间戳被截成负数拒绝）、gmtime_r() 对负时间戳输出非法字段（-1 得 1970-01-01 00:00:-1）、timer_gettime() 的 32 位截断，另外提交一份带 A 至 F 六项工作项的时间基线调研单。修复提案 #11928（+185/-135）与 #11929（+104/-9）在 10-26 均勾选「成熟版本，可合入」，本周内未合入。10-29 又进一步查出 timer_settime() 用 32 位变量承接 1e13 量级结果，10 秒定时器实际被 arm 成约 21 小时（#11938，+142/-5）。

  • 版本号抬到 5.4.0 开发态，版本管理与发布流程同日提出制度化的两份材料（10-29 ~ 10-30）：10-29 的 #11942 把 RT_VER_NUM 从 0x50301 抬到 0x50400，主线正式进入 5.4.0 开发态；但 releases 与 tags 两侧仍停在 09-10 的 v5.3.0，没有预发布标签与二进制。10-30 出现两份配套材料：缺陷单 #11956 提出建立版本管理 CI 与发布流程（Z 线月度报告加人工批准、Y 线每 3 至 6 个月结合硬件验证，分 B01 至 B05 与 C01 至 C08 两组工作项），提案 #11955 补上主管线版本与发布流程文档。这是本周少见的「流程侧」信号，值得下一期复核是否落到代码。

  • 厂商侧仍是提案先行：RA6W1 二期落地，全志与 ESP32-S3 的大体积提案继续在队列里泡（10-26 ~ 10-30）：瑞萨 RA6W1 的提案 #11934 于 10-28 18:52 合入，补 24 个 Wi-Fi 侧中断向量并把 ROM 符号表两个 crypto 入口改名为 __rom_ 前缀。全志 F101 YuzukiNeko 与 H616 的 #11877（172 个文件、+35428/-6）、ESP32-S3-DevKitM-1 的 #11844（10-28 刷新后累计 +295371/-22825）仍在队列，后者自 9-28 创建已满一个月，评审关注点落在整包引入厂商 SDK 与许可条款，而不只是功能能否运行。

安全与缺陷

日期：2026-10-23 ~ 2026-10-31　来源：Issue #11960

  • 本周新开 16 单，安全类占十单以上。按族分三条线：时间与 libc 语义（#11922 settimeofday 窄化、#11923 gmtime_r 负时间戳、#11924 timer_gettime 截断、#11925 sys_poll 计数回绕、#11927 时间基线调研）、RT-Smart 边界（#11932 musl 线程链表释放后使用、#11933 signalfd 全局计数越界、#11937 终端 ioctl、#11952 块设备 ioctl、#11958 管道 ioctl、#11960 邮箱对象指针）、驱动参数校验（#11948 Bluetrum AB32、#11949 Bouffalo、#11951 HPM 三家 ADC 通道越界，以及 #11950 DM365 SPI 除零）。另有 #11956 为版本管理流程的功能单。
  • RT-Smart 边界这条线最重：终端、块设备、管道、邮箱四处的形态完全一致，都是适配层把用户指针当内核地址用。邮箱一单最严重——sys_mb_send() 不做任何校验就转发，攻击者可构造伪对象，读写范围不再受值域约束。四单的影响版本都回溯到 2022-12-03 的 RT-Smart 同步提交 ecf2d821，首个受影响版本为 v5.0.0，v5.3.0 与当前 master 全部在列，在 QEMU 上即可复现。
  • 本周内已闭环：#11913 的 DHCP raw 选项越界读由 10-28 合入的 #11940 修掉（+23/-5，12 项主机侧 ASAN 回归）；#11915 的 dlmodule 未初始化全局量于 10-30 10:54 合入；#11933 的 signalfd 越界在开单次日即收到修复提案 #11935（+41 行，改为按上下文定位的有上限槽位查找，关闭路径补监听器解绑）；#11925 的前半部分由 #11954（+28 行）在 10-30 提交，sys_poll() 在 32 位下对「字节数回绕」的计数直接拒绝。
  • 仍在队列或无人认领：#11878（lwip-dhcpd 租约池耗尽死循环）、#11905（cromfs 目录名越界）、#11917（NFS 越界写）、#11919（NVMe 堆泄漏，修复提案 #11920 未合入）、#11902 与 #11910（tmpfs 截断后使用，修复在 #11910）、#11918（9PFS 长度收敛）、#11901（FDT 深度限制）、#11931（串口 rx_indicate 被误清）、#11932（musl 线程链表），以及新开的 #11937、#11952、#11958、#11960 四单（其中 #11937 有提案 #11941，#11938 修的是它引出的定时器截断）。

评审队列观察

日期：2026-10-26 ~ 2026-10-31　来源：主仓库提案列表

  • Smart 这批被拆成两段推进：10-18 创建的六笔中，#11890、#11894、#11896、#11900 已在 10-29 落地；#11892（RISC-V 侧 MMU 与用户态缺页处理，4 个文件 +105/-8）与 #11897（K230 增加 K230D 支持）仍在队列。前者的内容是玄铁架构选择与 SVPBMT 选项、早期页表指针按内核物理偏移换算、未处理用户缺页时只终止当前 LWP 而不拖垮内核；后者涉及真实板卡，等硬件侧确认。规律是「能在 QEMU 验证的先合、依赖实机的后合」。
  • 大体量新硬件支持在审：#11944 Realtek RTL8125 以太网驱动（新增 1934 行，覆盖原生 PCI、描述符环 DMA、10/100/1000/2500M 自协商、lwIP 软件校验和，可选 PTP 与 PPS）；#11943 RK3588 与 RK3528 显示与音频（36 个文件、+5483/-391，含 HDMI 控制器与 HDPTX PHY、VOP2 路由、SAI 与 codec 音频时钟）；#11959 NXP RT1180 工业以太网链接脚本（20 个文件、+7499/-18，CM33 跑片内 RAM、CM7 从 Flash XIP）。三笔都属「一大类硬件成批进入」，评审周期通常以周计。
  • 工具与文档侧：#11930 把 __RT_KERNEL_SOURCE__ 提到 Kernel 组的全局 CPPDEFINES，修掉 Studio 导出工程里的 24 个 rt_sched_* 隐式声明警告；#11953 修 rt_sprintf() 在启用 libc vsnprintf 时把 (size_t)-1 交给 libc 导致一个字节都不写的问题（+11 行，改走 vsprintf()）；#11961 为原生线程初始化静态 TLS（6 个文件、+189/-3，AArch64 每次上下文切换恢复 TPIDR_EL0，RISC-V 仅在 MMU 的 S 模式启用）。
  • 长期挂起项：#11844（ESP32-S3 BSP）刷新后体量达 +295371/-22825，自 9-28 创建已一个月，评审焦点在整包 SDK 与许可；#10096（按需编译）被建议先变基；#11860（aarch64 中断应答）、#11864（IAR 隐式声明）仍在补测试记录。另 #11947（DHCP raw 地址池耗尽无界循环）改动不大（+17/-4），但附了 3586 组池大小与占用位图组合的对照测试与 ASAN 结果，验证强度在本周队列里最高。

三、生态与厂商适配

厂商 BSP 与驱动

日期：2026-10-26 ~ 2026-10-30　来源：PR #11896

  • 英飞凌 TriCore（AURIX）：Env SDK 侧补进 tricore-gcc 13.4.1 与 qemu-tricore 1.0.0 两个包，覆盖 TC2xx／TC3xx／TC4xx。工具链上游是 NoMore201/tricore-gcc-toolchain（EEESlab 11.3.0 的下游），Windows 包补了上游漏带的 libwinpthread-1.dll；模拟器只做 ASCLIN0 串口、STM、IR 中断路由、SCU 与时钟、SFR 桥与 RAM/Flash 映射，CAN、以太网、ADC、GPIO、DMA 均无，够跑内核与串口 shell，不够做外设驱动验证。
  • 瑞萨：RA6W1-EK 的 rafw_gen 向量表补 24 个 Wi-Fi 侧中断入口（KDMA、TDES CBC、PSK SHA1、SYSPLL 与 FPLL 锁定、整组 RTC 接口、MRM 与 D-cache MRM、CryptoCell-312、HSU、MAC 定时器／接收／发送／协议／通用／信标、radio controller），全部声明为 weak 处理函数并挂进向量表，同时把 ROM 符号表两个 crypto 入口改名为 __rom_ 前缀避免与 RAM 侧同名冲突。
  • 全志：F101 YuzukiNeko 与 H616 的 BSP 提案（#11877，172 个文件、+35428/-6）仍在队列，F101 侧补 Sun252i 设备模型驱动集与 Sunxi DE0／TCON0 显示后端（RGB、LVDS、MIPI-DSI），H616 侧是另一套驱动集并新增 AXP313A 调压器支持；D1s 的 QEMU 启动脚本（#11903，4 个文件 +145）同样在审，评审建议改成统一的目标机子目录。

六、趋势观察

  • Smart 的定位在本周被明确成「测试覆盖层」而不是「默认配置」：10-29 一天之内先开 Smart、再收回默认配置，看似反复，实际是维护者在做边界划分——默认配置必须保持可预测，让不带 Smart 的常规回归稳定；Smart 通过 utest 的配置覆盖层单独跑，两条路径共用一个 BSP。这样既拿到了 QEMU 上的用户态测试覆盖，又不打乱既有的 BSP 编译矩阵。随之而来的观察点是 #11892 与 #11897：能在 QEMU 验证的先合、依赖实机板卡确认的后合，这条排期规律在本周得到了两次印证。
  • RT-Smart 的用户态／内核态边界成为本周最重的安全主线，且已呈族化：终端、块设备、管道、邮箱四处形态完全一致，都是适配层默认参数已是内核地址、用户态入口没有 copyin/copyout。四单的影响版本全部回溯到 2022 年的同一次 RT-Smart 同步提交，说明这不是新引入的缺陷，而是移植时被整体带进来的结构性缺口。修复路径也已明确（#11941 的内核栈暂存加 copy_from_user/copy_to_user 加 lwp_in_user_space() 界限校验），接下来的看点是这套做法能否被抽成通用层，而不是在每个子系统各修一遍。
  • 主线节奏由「积压提案的批量清账」主导，而不是当日新开发：10-27 四笔、10-29 七笔的合入中，多数提案的 author 时间早于合入时间一周以上，10-29 那批更是 10-18 创建、排队十一天。这个形态对判断项目健康度有影响：单看提交数会高估当周开发强度，单看零提交日又会低估评审活动。真正稳定的指标是「提案队列的周转时间」——本周它从十天收敛到一天（#11896 合入后 #11942 当天跟上），属正向变化。
  • 测试可信度被当成基础设施来修，而不是当测试来修：本周修的三件事都不是「多加用例」，而是让判定本身可信——后续 unit 通过不再抹掉前面 testcase 的失败（#11601）、CI 不再依赖公网与非法 IP 字符串（#11601）、musl 下不再假定 signal 0 可安装（#11601），再加上 #11942 把 CI 的配置覆盖方式从「整份 checkout」改成「追加一行关闭开关」。这与上周 pkgs-test 的并发锁修复同属一条线：先把「测试通过」这个前提做实，再谈覆盖率。
  • 版本发布从「等待」转向「制度化」，但发布动作仍未开闸：v5.4.0 的版本号在 10-17 就 bump 过，10-29 又抬到 0x50400，而 releases 与 tags 停在 09-10 的 v5.3.0 已七周。10-30 出现的两份材料（#11956 的版本管理 CI 与发布流程、#11955 的版本与发布流程文档）说明社区自己也在处理这个落差——Z 线月度报告加人工批准、Y 线每 3 至 6 个月结合硬件验证，并把「QEMU 结论不扩大为实机结论」写进非目标。下一期应以 release 页与 ChangeLog 复核是否真正开闸，而不是以版本宏为准。
  • 厂商适配的形态在变：一边是工具链与仿真先行，一边是一大类硬件成批进入：TriCore 进的是 Env SDK 而非主仓库，先用开源 GCC 加 QEMU 解决「能编、能跑、能调」，BSP 与驱动留到后面；同时 RTL8125、RK3588、RT1180 三笔大体量提案同期在审，说明适配重心正从「单块开发板点亮」转向「整类平台与外设栈」。两条路径的评审成本差别很大：前者是包索引层面的低风险增量，后者动辄上千行、需要板卡侧确认，这也是为什么 BSP 队列里始终压着 172 个文件与 29 万行量级的提案。
