一、内核与版本动态

1.1 挂起三年的时间片调度提案补做核对：判别式与 #11907 殊途同归，但「延后写 READY」在单核引出重复释放（10-21）

日期：2026-10-21 14:16 ~ 14:41（评论时间）　来源：PR #6645、PR #11907

2022-11-23 提交的时间片调度补丁（#6645）长期挂在 Status: waiting for test，社区成员 Yunlk 在窗口内连发三条评论把它重新拉回评审视野。第一，补丁改的 src/scheduler.c 在当前主线上已被拆分为 scheduler_comm.c、scheduler_up.c、scheduler_mp.c，原补丁无法直接应用，评论给出了改动点与新版文件的逐处对应。第二，该补丁的核心判别式——只有「仍在运行且时间片未用尽被抢占」才插队首，其余一律队尾——与 #11907 独立得出的结论完全一致，两条互不知情的路径收敛到同一判断，作者称这本身可作为方向有效性的旁证。第三，真正的分歧在实现手段：本补丁删掉插入开头写 READY 的覆盖、改为插入末尾统一置位并清 YIELD，导致插入期间线程状态仍为 RUNNING。

按此逻辑移植到单核路径后，QEMU vexpress-a9 上信号量唤醒顺序由 BA 修正为 AB、启动顺序由 DC 修正为 CD，三线程时间片轮转正常，但调度组 utest 稳定崩溃：rt_smem_free 断言失败，回溯为 rt_free ← rt_defunct_execute ← idle_thread_entry，即 idle 回收已结束线程时对同一 TCB 二次释放，两次运行在同一用例复现。隔离实验把 rt_schedule() 里原有那处 YIELD 清除加回去，崩溃照旧，说明问题不来自清除位置，而出自「延后写 READY」。补测 SMP（双核配置）后判别式同样有效，重复释放只在单核路径观察到；作者同时更正了自己此前「SMP 未测」的说法。结论建议：判别式值得保留，但以 #11907 的「先存 stat_before 再判断」为基础推进，#6645 若要继续需先查清单核下的二次释放。

1.2 动态模块未初始化全局变量修复：BSS 段分配指针不推进等四处缺陷一并处理（10-21）

日期：2026-10-21 21:09（创建时间）　来源：PR #11915、Issue #5705

贡献者 usualtreee 针对 2022 年 3 月报告的 #5705 开出修复，问题在当前主线 1c801efa 上仍可复现。缺陷集中在可重定位模块（ET_REL）加载路径 dlmodule_load_relocated_object()，即 Cortex-M 等启用 RT_USING_MODULE 的板级所走的路径：其一，BSS 段（SHT_NOBITS）加载后分配指针不推进，多个 NOBITS 段会重叠在同一块内存；其二，段符号重定位公式缺少段链接地址修正；其三，SHN_COMMON 符号（tentative 定义的未初始化全局变量）被静默跳过，原因是代码去读 shdr[0xfff2] 取段名得到垃圾值后不匹配；其四，该路径从不构建 module->symtab，dlsym() 对 ET_REL 模块永远失败。

修法对应四点：BSS 段加载后按段大小推进指针；rodata/bss/data 段重定位统一为「段加载地址 − 段链接地址 + 符号值」；为 SHN_COMMON 单独分配公共块，并把该分支前置到段名匹配之前以避免越界读；从 .symtab 收集全局函数符号构建 module->symtab。改动两个文件 +147/-9，在 qemu-vexpress-a9 上用三个测试模块验证：修复前 ET_REL 模块 dlsym 失败，修复后成功且两个未初始化全局变量地址（0x600d2008 与 0x600d2004）互不重叠、特征值写入回读通过，两个 ET_DYN 模块结果不变。提案已过 CLA，处于 components 组评审。

二、安全与稳定性跟进

2.1 NFS 读路径以服务端计数做 memcpy 长度：一次 cat 即可覆盖返回地址（10-22）

日期：2026-10-22 02:13（创建时间）　来源：Issue #11917、dfs_nfs.c

贡献者 XueDugu 新开 NFS 客户端缺陷单，属可直接利用的内存破坏。nfs_read() 把请求长度限制在 1024 字节以内，但拷贝时用的是服务端回复里的 READ3resok.count，既不与调用方请求长度比较，也不与同一回复里解码出的数据长度比较；XDR 解码侧用 xdr_bytes(..., ~0) 作上限，长度校验永远不触发。两个计数字段在协议里相互独立，恶意服务端完全可以对一次 80 字节的请求回 count = 512 加 512 字节数据。

后果落在内置的 cat 命令上：dfs_file.c 用 char buffer[81] 承接读取，单次 cat 一个文件即可越过缓冲尾部最多约 430 字节，覆盖 finsh 线程栈上的返回地址。缺陷由 2010-05-20 的提交 0fbfdec40d 引入，自 v1.2.0 起的每个版本都受影响，含 v5.3.0 与当前主线。作者在 QEMU vexpress-a9 与 RP2350 实板上分别复现；NFS 客户端自己组装 AUTH_SYS、走无认证的 UDP，挂载的服务端或路径上的注入者均可控制溢出内容。该单目前未被认领。

2.2 raw-API DHCP 服务端选项遍历缺边界：最多越过 1500 字节缓冲 4 字节（10-21）

日期：2026-10-21 15:49（创建时间）　来源：Issue #11913、dhcp_server_raw.c

另一位研究者 K-ANOY 报告 raw-API DHCP 服务端的越界读。选项查找函数只保证返回指针落在缓冲区内，遍历时 buf[1] 未先校验 buf + 1 < end，末尾只剩一个字节的选项头会读出界一字节；调用方随后按固定宽度取值（请求 IP 读 4 字节、消息类型读 1 字节），把选项头摆在尾部即可让 opt[2]..opt[5] 越过 1500 字节的 pbuf 堆块最多 4 字节。同一目录下基于套接字的 dhcp_server.c 恰好做了这些检查——长度是否越界、声明长度是否有效、length < 4 与 length < 1——反证 raw 版本缺的正是这几道。

触发条件只是同网段任意主机向 UDP/67 发一个选项区被截断的报文，无需认证；作者在 ASan 下完成逻辑级复现，并指出被读出的值只用于比对与分支，未直接外传。该单已打 bug 与 component: net 标签，尚未认领。

4.1 ESP-IDF v6.1 包侧合入：C3/C6 出现用 RT-Thread 替换 FreeRTOS 的官方开关（10-21）

日期：2026-10-21 15:23（合入时间）　来源：RT-Thread-packages/esp-idf PR #18

RT-Thread-packages 的 esp-idf 包完成自 5.1 到 6.1.0 的整包升级并合入，变更文件两万余。相对官方 v6.1，这次合入带了三处 RT-Thread 侧的结构性改动：新增 components/rtthread/（C3/C6 的移植层、rtconfig.h、board/context、CMake 与链接脚本），新增 components/riscv/vectors_rtthread.S，并在 FreeRTOS、esp_system、esp_timer 等处加 CONFIG_IDF_RTOS_RTTHREAD 开关路径；menuconfig 里对应「Component config → FreeRTOS → Extra → Replace FreeRTOS with RT-Thread」。对 RISC-V 而言这一步的意义在于：C3、C6 属 RISC-V 内核（与 Xtensa 的 S2/S3 不同），此前只能在 IDF 5.x 上按旧集成方式跑 RT-Thread，现在拿到的是 6.1 底座加一条官方承认的内核替换通道。

日期：2026-10-21 15:24（评论时间）　来源：PR #11870

4.3 OSPI 与 OctaFlash 进入组件层：SFUD 支持 1-1-1 与 8-8-8 两种模式（10-21）

日期：2026-10-21 15:22（创建时间）　来源：PR #11912

现有驱动层只有 SPI 与 QSPI 通路，经 SFUD 访问八线 Flash 没有原生路径。本提案在组件层补 OSPI：新增总线、设备、配置与消息定义及传输助手，同时保留既有 SPI/QSPI 路径；把 OSPI 传输与器件探测接进 SFUD，覆盖读、写、擦与状态查询，并在器件表里加入 MX25LM51245G 用于验证。为跑通整条链路，另加通用 STM32 OctoSPI 底层驱动 drv_ospi.c（504 行）与 L4 系列配置头，并在 stm32l4r9-st-eval 板级补 OCTOSPI1 的引脚、时钟与 MSP 配置及进入 OPI STR/DTR 模式的辅助函数，顺带修掉该板级堆与链接布局造成的 .bss 重叠。改动 32 个文件 +3728/-956，四个提交，CLA 已签，评审已指派 STM32 组三位维护者；作者报告已在实板上以 GCC 构建运行，1-1-1 与 8-8-8 两种模式均可被 SFUD 识别。

4.4 Cortex-A 的 GIC 打印函数修正格式符：%p 传非指针属未定义行为（10-21）

日期：2026-10-21 18:00（创建时间）　来源：PR #11914

libcpu/arm/cortex-a 下 GICv2 与 GICv3 的信息打印函数存在四类格式说明符与实参类型不匹配：物理地址是 rt_uint32_t 却用 %p 打印，属未定义行为；GIC 版本号是 unsigned long、最大中断号与中断号是 unsigned int，却都用 %d。以 -Wall -Wformat 编译 Cortex-A 板级时这些全部报警。提案把 %p 改为 0x%08x、%d 改为 %u，并对由 0xfUL 取出的版本号加显式 unsigned int 转换，两个文件 +64/-40，只动格式符不动运行时逻辑。

4.5 睿擎 V1.8.4 与新 IDE：编码器、MIPI RGB666、GPIO 上下拉、GD32H7 工程支持（10-21）

5.1 睿擎 V1.8.4 的工业现场修复：EtherCAT 中断亲和性、telnet 下 netstat 卡死、UART DMA 波特率（10-21）

日期：2026-10-21 11:50（发布时间）　来源：电子工程专辑：睿擎平台 V1.8.4 发布、睿擎更新日志

同一版本的四项修复全部指向工业现场：EtherCAT 的任务与中断此前未绑定同一 CPU，中断默认落在 CPU0，多任务切换时偶发访问冲突并死机，修复后两者绑定同核；telnet 远程执行 netstat 会阻塞无响应，已修；UART DMA 示例设置波特率失败，根因在 DMA 串口初始化流程，已修正；4.3 寸屏示例调高背光 PWM，改善户外可视性。结合前一期已报道的 EG1200 工业网关虚拟网口与 NFS 挂载、以及基于 RC-Pi-3506 的 ROS2 轮毂电机运动控制方案，睿擎这条产品线本期呈现的是「网关侧联网能力」与「运动控制侧实时性」两条并行的推进，修复项也多来自实际项目反馈而非内部测试。

六、总结与趋势观察

6.1 本期趋势

  • 调度器讨论从「各提各的」走向「比对实现」：三年挂起的 #6645 被重新核对，其判别式与 #11907 独立收敛，但两种实现手段在内存安全上分出高下——延后写 READY 在单核引出 idle 回收路径的二次释放，保存旧状态的写法没有。这类跨提案的横向比对比单条补丁更有决策价值，也让 #11907 事实上成为推进基线。
  • 缺陷报告持续由外部研究者驱动，且带完整影响面：一天两笔内存问题，NFS 栈溢出的引入提交可回溯到 2010 年、影响自 v1.2.0 起的全部版本，DHCP 越界读则以同目录另一个实现的检查项反证缺失点。两份报告都给了复现环境与触发条件，修复成本因此大幅降低。
  • RISC-V 侧拿到一条内核替换通道：ESP-IDF 6.1 整包升级合入后，C3/C6 可通过 CONFIG_IDF_RTOS_RTTHREAD 用 RT-Thread 替换 FreeRTOS，工具链同时跳到 GCC 15.2；主仓 BSP 提案的阻塞点同日消除，只差上板验证。这是本周期内 RISC-V 相关最有分量的一步。
  • 主线静止、版本停在九月：连续三日零提交、零合入，v5.4.0 只有版本宏。活动全部集中在在审提案、缺陷单与包仓库，与官方渠道停更形成同一种节奏。
  • 厂商平台按版本稳定迭代，且把现场问题纳入修复：睿擎 V1.8.4 的六项新增与四项修复都对应具体场景（编码器闭环、MIPI 屏适配、AMP 调试、EtherCAT 亲和性），IDE 同步扩到 GD32H7，说明工业平台的竞争力正从「能不能跑」转向「现场稳不稳」。
