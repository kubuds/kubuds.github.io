一、内核与版本动态

1.1 RISC-V 票号自旋锁改用 AMO：放锁侧不再走 LR/SC 重试，K1 的 SMP 配置同时由 4 核开到 8 核（10-22）

日期：2026-10-22 17:59（合入时间）　来源：PR #11904、cpuport.c、K1 BSP README

这次改动落在 libcpu/risc-v/common/cpuport.c，把票号锁（ticket spinlock）的加锁与放锁两条路径分别换掉了实现。原先是两侧都用 LR/SC 循环对同一个字做「读—改—写」：加锁侧把高 16 位的下一票号加一、与低 16 位的当前持锁号拼回一个整字再写回；放锁侧同样走 LR/SC 把持锁号加一。改动后的注释点明了两种失败面：其一，取票路径与一条正在重试 LR/SC 的放锁路径会在同一保留集上互相打断，在高核数争用下陷入活锁，这正是标题里的 SMP 停顿；其二，放锁用整字读改写会把并发期间新领走的票号一起覆盖掉。

修法是把取票改成 amoadd.w.aqrl 单指令原子加（AMO 不会失败，也就不存在重试被打断的问题），票号增量取 1 << 16，两个 16 位计数器仍然共处低 32 位——注释特意写明这一点在 RV64 上同样成立，因此用的是 32 位宽的 amoadd.w 而非 amoadd.d。放锁侧则彻底去掉原子读改写：只有持锁者会写持锁号，用一次 16 位半字存储做「加一」即可，既保留了并发新领的票号，也免掉 LR/SC；两侧各补一处 rt_hw_barrier()，保证临界区访存排在观察到对方释放之后、以及在推进持锁号之前完成发布。

同一提案把 bsp/spacemit/k1 的 CONFIG_RT_CPUS_NR 与 rtconfig.h 的 RT_CPUS_NR 由 4 改为 8，并在 K1 的两个 README 与 bsp/README.md 的支持矩阵里补上说明，属「先修锁、再放开核数」的顺序。按 K1 现行 README，该 SoC 为 64 位 RISC-V、集成 8 个 X60 核心并带向量扩展，BSP 走设备树、由 U-Boot/OpenSBI 引导在 S 模式运行，验证平台是 Banana Pi BPI-F3。整个提案 6 个文件 +33/-37，改动量不大但触及 RISC-V 多核的基础设施。

1.2 消息队列 FIFO 被高优先级线程插队：挂了两年的旧单给出可在主线稳定复现的最小例（10-22）

日期：2026-10-22 13:54（评论时间）　来源：Issue #4940、ipc.c

2021 年 8 月的旧单在窗口内被重新推进。该单原指消息队列与邮箱在 RT_IPC_FLAG_FIFO 下无法保证先进先出，维护者当年的回复承认「此处没有做锁定，而 semaphore 相当于做了锁定」，此后一直未落地修法。新评论按这条线索补了一个最小复现，并声明在主线上可稳定重现。

复现配置是 rt_mq_create() 建一个 msg_size=4、max_msgs=1、RT_IPC_FLAG_FIFO 的队列：低优先级线程（20）先做阻塞式接收、队列为空因此挂在等待队列首位；高优先级线程（10）不进队列等待，而是先阻塞在一个信号量上；主线程发一条消息，低优先级线程被从等待队列摘下、进入就绪队列；主线程紧接着释放信号量，高优先级线程就绪；主线程延时让出 CPU 后，高优先级线程先跑，用非阻塞接收把那条消息取走。消息没有落到排在最前的等待者手里，FIFO 语义被优先级抢占破坏。

问题的性质与 1.1 不同：不是竞态窗口，而是「唤醒即出队」的语义选择——被唤醒者一旦离开等待队列就成为普通就绪线程，此后任何更高优先级的非阻塞取用都能合法地把它该拿的消息拿走。评论里提到 uClinux 的做法是唤醒但不出队，等真正拿到锁才从挂起队列摘除，可作为修法参考。该单目前仍是打开状态，本期没有对应提案。

二、安全与稳定性跟进

2.1 NVMe 每遇一个非活动命名空间漏 4480 字节：合规盘每次启动即丢掉约 1.1 MB 内核堆（10-23）

日期：2026-10-23 01:15（创建时间）　来源：Issue #11919、nvme.c

研究者 XueDugu 在窗口末尾提交 NVMe 驱动的内核堆泄漏。nvme_scan_device() 用 Identify Controller 回复里设备可控的 nn（Number of Namespaces）作循环上界，在 1 到 nn 之间逐号探测，而每轮都会先 rt_calloc 一块 4480 字节的 rt_nvme_device，之后才发该号的 Identify 命令。两条失败路径都不归还这块内存：nsze == 0（命名空间已分配但未激活，属规范允许的正常回复）走 continue；Identify 命令出错走 goto _free_res，跳过释放。

影响面按作者实测给出：在官方 qemu-virt64-aarch64 BSP 的默认配置下，不接 NVMe 时空闲内核堆 66,941,784 字节；接一块 nn = 1 的单命名空间盘为 66,931,592 字节，属正常；接 QEMU 原装 nvme 设备则降到 65,774,912 字节——QEMU 始终上报 nn = 256 而只暴露 1 个命名空间，这一回复合法，于是 255 个非活动号各漏 4536 字节（含 memheap 头），单次启动即 1,156,872 字节、约 1.1 MB，占 64 MB 内核堆的 1.8%。热插拔与重扫会线性累积；若设备上报更大的 nn（如 0xFFFFFF），循环会在堆耗尽前一直分配，最终系统无法启动，串口停在 hello rt-thread 之后不再出提示符。

作者给出 CWE-401 与 CVSS 3.1 4.9（Medium，AV:P），并说明「按次启动的 1.1 MB 泄漏不需要攻击者」，只有「堆耗尽致不可启动」需要恶意或畸形控制器。缺陷由 2024-11-24 的提交 945114fd5（NVMe 支持，#9591）引入，v5.2.0 起的每个版本与当前主线均含。建议修法是把这块分配挪到确认命名空间有效之后、并在两条失败路径补齐释放，同时不要直接采信 nn 作上界（可按 mnan 设上限，或改用 CNS 02h 的 Active Namespace ID 列表）。该单目前未打标签、未指派。

2.2 9PFS 直接采信服务端长度字段：ASAN 越界读穿 8.3 MB 接收缓冲，修复提案已开（10-22）

日期：2026-10-22 19:36（创建时间）　来源：PR #11918、Issue #11289、dfs_9pfs.c

dfs_9pfs_read() 与 dfs_9pfs_getdents() 存在与服务端回复长度脱钩的越界读，提案 +58/-4 只动 dfs_9pfs.c 一个文件。根因是 p9_transaction() 的返回字节数被丢弃（传入 RT_NULL），随后代码直接使用报文里的 count、每条记录的 stat_size 与 name_len，从不与真正收到的数据量比对；服务器只要回一个 count 巨大而实际很短的报文，解析器就会一路读越接收缓冲。正常情况下被跳过的 . 记录不会命中 fd->pos >= end 的退出条件，解析器因此可以持续前进。

作者用 bsp/simulator（x86-64、ASAN、-fsanitize=address）搭了一个假的内存 9P 服务器：握手与 Tstat/Topen/Tclunk 正常应答，但对 Tread 只回 11 字节报文、count 谎报约 2 GB，并在接收缓冲后方铺满伪造的 . 记录加 ASAN 毒化守卫带。修复前触发 AddressSanitizer: use-after-poison，读位置落在 8 MB 堆区之内第 8,334,515 字节，进程 ABORT；修复后恶意回复被拒（返回 P9_READ_UNEXPECTED_DATA 或 -EIO），正常目录解析不受影响，hello.txt 与 subdir 两项照旧列出。

修法四步：两个函数都把实际接收字节数传入 p9_transaction() 并校验不小于 P9_MSG_READ_DATA；count 收敛到 rx_size - P9_MSG_READ_DATA，不再采信报文值；getdents 逐记录校验剩余字节能否容纳长度字段、stat_size 是否越出剩余数据、name_len 是否越出当前记录；read 路径同样收敛实际读到的字节数（作者特别指出 got <= set 并不充分，因为 set 本身就可能超过接收容量）。补丁在最新 master 上 git apply --check 通过。

4.2 GD32VW553 进入 at_device 包：RISC-V 的 Wi-Fi 6 加 BLE 5.2 芯片可 menuconfig 直接选配（10-22）

4.4 scons –attach 在中文 Windows 上直接崩：4 处 emoji 标记换成 ASCII（10-22）

日期：2026-10-22 18:00（合入时间）　来源：PR #11908、attachconfig.py

tools/attachconfig.py 的 4 行 print 里用了 emoji 状态标记，在中文 Windows 上会导致整条命令不可用。原因是 Python 的 stdout 编码跟随区域代码页（简体中文系统为 936/GBK），无法编码 U+2705 与 U+274C，首次打印即抛 UnicodeEncodeError 并中止；由于 --attach=?、--attach=<name>、--attach=default 三种用法都走同一个函数，三条路径一并失效。设 PYTHONIOENCODING=utf-8 可以绕过，但普通用户不会知道。

修法把 4 处换成 [OK] 与 [ERR] 纯 ASCII 标记，保留原有 ANSI 颜色码——tools/env_utility.py 与 tools/ci/bsp_buildings.py 本就在用 ANSI 彩色输出，属既有约定。tools/ci/ 下的 emoji 未动，因为它们写进的是 GitHub Actions summary 的 Markdown、由 UTF-8 渲染，不受控制台编码影响。改动只碰 4 行 print，不涉及逻辑，作者在 Windows 11 中文版默认代码页 936 上做了修复前后对照，所用 BSP 是当前唯一带 attachconfig.yml 的 ra6m3-hmi-board 目录。这类问题不涉及内核，但对国内开发者的首次上手体验影响直接。

五、总结与趋势观察

5.1 本期趋势

  • RISC-V 多核路径在同一天补了两处基础件：票号锁从 LR/SC 双向重试改为「取票用 AMO、放锁用半字存储」，把活锁面从根上去掉，K1 随即放开到 8 核；ESP32-C3/C6 则拿到 ESP-IDF 6.1 底座与 GCC 15.2 工具链。前者修的是多核正确性，后者修的是新底座可得性，两者都属「不显眼但决定能跑多稳」的工作。
  • 主线从静止转为集中收尾：连续三日零提交后，10-22 三小时内合入三个提案、四笔提交。节奏上更像维护者攒了一批评审一次性处理，而不是开发强度回升；v5.4.0 至今只有版本宏，说明发布流程仍未启动。
  • 「设备或服务端可控的元数据即长度」已成一条成族缺陷线：同一研究者在两天内报出 NFS 越界写、NVMe 堆泄漏、9PFS 越界读三单，9PFS 已带收敛式修法。作者自己把这条线追溯到 mtd-cfi 与 usbhost 的旧单，逐单修补的成本远高于按族排查。
  • 中文 Windows 的编码问题开始被当作可修缺陷：scons --attach 因 emoji 在 GBK 下抛异常而整条命令不可用，属国内开发者高频踩点。这类修复技术含量低但收益直接，值得与工具链其他 Windows 适配项一起看。
  • 兆易创新把无线与界面基础件一起补：24 小时内 GD32VW553 进 at_device、GD32EmbeddedUI 示例进 LVGL 包，前者是 RISC-V 的 Wi-Fi 6 模组、后者是 UI 示例，指向的是成套方案而非单点提交。

  • 行业应用（工业、车载、机器人、具身智能）渠道在本窗口无新增报道：睿擎产品线自 V1.8.4 发布后未见后续版本或落地案例，社区文章侧亦无新的应用类长文，故本期不设该章。
