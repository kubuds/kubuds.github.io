一、内核与 RISC-V 中断

1.1 PLIC：先派发处理函数，再完成中断（11-11）

日期：2026-11-11 09:44（合入时间）　来源：提案 #12011、缺陷 #12010

上一期写的是 APLIC 的 EOI 时机，本期合入的是 PLIC 的同一处时序，两笔来自不同作者、独立提交。

handler_plic_irq() 原先的次序反了：先向 PLIC 写 claim 宣告完成，再派发处理函数。如果中断源是电平触发且在处理函数执行期间仍保持断言，PLIC 网关会把这次请求再转发一遍，同一个中断被派发两次。修法看起来只是把两行调换——先执行 handler_irq()，再写 claim 完成。

直接调换会带来第二个问题：处理函数可能顺手屏蔽了自己的中断源，而 PLIC 对「未使能」的中断忽略完成写入，这次 claim 就永远不归还，该中断此后不再到达。提案参照 Linux 的 SiFive PLIC 驱动，在完成前后临时置位使能寄存器——先读使能与掩码，已使能则直接写 claim；未使能则持 enable_lock 二次确认，临时置位、写 claim、再清位。

两个文件、35 行新增、2 行删除。libcpu/risc-v/common/interrupt.c 只改次序，libcpu/risc-v/common/pic/pic-sifive-plic.c 承担完成路径的全部逻辑。作者 boa-z，11 月 9 日提交，两天后合入，缺陷 #12010 同日关闭。

与 #11966 对照着看：一笔是 APLIC 在不该写 setipnum_le 的时候写了，一笔是 PLIC 在该先处理的时候先完成了，都属于「完成动作与中断源实际状态脱节」。RISC-V 侧两条中断控制器路径，现在各自对齐了通用做法。

二、rt-link 长帧：议题与修复相隔一小时四十三分

2.1 议题：单帧触发堆溢出，v4.1.0 起存在（11-11）

日期：2026-11-11 13:32（议题）　来源：缺陷 #12030

rt-link 的长帧接收端在重组时，把「缓冲区分配大小」「帧内偏移」「本帧长度」三个量分别信任，而三者都可被链路对端构造。单个畸形帧即可让重组写出已分配的 dataspace。

报告者给了两套复现：一是 QEMU 的 qemu-vexpress-a9，把 rt-link 端口接到板子的第二路 PL011，由对端在线路上注入帧；二是 Raspberry Pi Pico 2 W 加一份触发固件，经 USB-CDC 控制台把完全相同的字节喂进 rt_link_hw_write_cb()——即组件文档里给出的标准板级端口入口。两套都走到同一个溢出点。

影响版本写得很具体：v4.1.0 起存在，按 tag 在 v4.1.0、v5.0.0 至 v5.3.0 与 master 上逐一核对，v4.0.x 无此问题。代码位置 components/utilities/rt-link/，配置项 RT_USING_RT_LINK；报告者注明受影响面是「启用该组件、通过标准板级端口对接外部 WiFi 模块」的固件，并点出典型接法是 RT_LINK_SERVICE_WIFI。

2.2 提案：把分配长度记进记录结构（11-11）

日期：2026-11-11 15:15（提案）　来源：提案 #12031

议题提出后一小时四十三分，同一报告者给出修复：两个文件、84 行新增、12 行删除。

核心改动是给 struct rt_link_record 加一个 dataspace_size。此前结构里只有 dataspace 指针，没有它有多大——重组时想判断「偏移加长度」是否越界，手上没有可比的基准。这一栏补上之后，边界判断才成立。

四道检查随之落下：首帧 extend.parameter 必须非零且不超过 RT_LINK_FRAMES_MAX * RT_LINK_MAX_DATA_LENGTH，非法或分配失败都走 _stop_recv_long() 干净退出；次帧校验 data_len 上限、index 小于帧数与总帧数、offset + data_len 不超过 dataspace_size 且用防溢出算术，然后才调 rt_link_hw_copy()；所有释放与重置路径清空 dataspace_size；rt_link_frame_check() 增加对 head.length 超限的拒绝，让收包路径与 rt_link_send() 的约束对齐。

顺带处理了一处相邻隐患：短帧处理入口与新的长帧首帧进来时，若上一轮长帧尚未结束，先 _stop_recv_long()，避免 dataspace 被覆写或泄漏。

三、夜间七笔：审计清单转向三月旧账

3.1 GPT 与 CFI：两个整数边界的老问题（11-12）

日期：2026-11-12 00:04 与 00:49（提案）　来源：提案 #12034、缺陷 #11260、提案 #12038、缺陷 #11272

11 月 12 日凌晨 00:04 至 00:56，同一位报告者连续提交七笔，指向的不再是 2024 年的 CVE，而是今年三月到九月自己开出的议题。

#12034 处理 GPT 分区表（议题 #11260，2026-03-17）：按 num_partition_entries * sizeof_partition_entry 申请堆内存，32 位下这个乘积可以回绕，随后代码仍按盘上原始的 entries_nr 遍历 ptes[]，于是堆越界读。修法是分配前校验条目大小与个数、拒绝乘积溢出，遍历上界改为「实际分配到的条目数」与 max_partitions 的较小者。

#12038 处理 CFI 闪存扇区表（议题 #11272，2026-03-19），这一笔值得单独说，因为它补的是上一笔修复的缺口。11 月 5 日的 #11558（提交 e2e507c4）已把 sect_count > ARRAY_SIZE 改成 >=，但只堵了一半：当 sect_count 恰好等于 CFI_FLASH_SECT_MAX 时，内层循环 break 之后外层 num_erase_regions 继续运行并重复报错，探测仍返回 RT_EOK 并注册一张残缺的扇区表。这一笔满表时打正确日志并以 -RT_EINVAL 跳到 _fail 中止探测；再补 sect_count == 0 的除零与无符号下溢校验、dev_size 移位上界、size_ratio 乘法上界，以及 rt_ioremap() 返回值检查与 _fail 路径清零，防止双重 unmap。

3.2 9PFS 与串口 ioctl：服务端与用户态的信任边界（11-12）

日期：2026-11-12 00:13 与 00:40（提案）　来源：提案 #12035、缺陷 #11289、提案 #12037、缺陷 #11429

#12035 处理 9PFS（议题 #11289，2026-03-23）。getdents 把 16 位的 name_len 截断写进 8 位的 dirp->d_namlen，之后才校验记录边界——大于等于 256 的值回绕后正好绕过检查；拷贝也没有按 d_name 的本地缓冲上限夹住。另外，夸大的 Rread.count 被静默截断而不是拒绝，p9_transaction() 缺 rx_size 与 msg_size 的基础校验。修法是把长度校验提前到完整 16 位宽度上，拷贝再按本地名缓冲封顶，事务层与读路径同步收紧。

#12037 处理 RT-Smart 串口 ioctl（议题 #11429，2026-06-02）。此前提交 c5ead825 已为 RT_DEVICE_CTRL_CONFIG 等常用命令加了用户态封送，但 F_SETFL、FIONWRITE 以及内核内部或未知命令仍会穿过 arg_size == 0 分支，把裸用户指针直接传给 rt_device_control() 与 serial->ops->control()。这一笔改成白名单：F_SETFL 更新完 fd->flags 直接返回，用户态只放行已封送的结构体命令与明确无指针的标量命令，其余一律 -RT_ENOSYS；同时拒收 baud_rate == 0，补齐各命令对空指针与 ops->configure 的判空。

3.3 tty 空 LWP 与 pin legacy 中断（11-12）

日期：2026-11-12 00:53 与 00:56（提案）　来源：提案 #12039、缺陷 #11717、提案 #12040、缺陷 #11784

#12039 处理 RT-Smart 的 tty（议题 #11717，2026-08-18）：非 LWP 线程读 tty 时，tty_wait_background() 没判断 td->lwp == NULL 就解引用 pgrp，finsh 里第一次 read(stdin) 就能缺页。三个文件、23 行，空 lwp 时直接跳过后台作业等待。

#12040 处理 GPIO 的 legacy 中断路径（议题 #11784，2026-09-07）：设备没有 pin_attach_irq 时走老路径，pin_api_attach_irq 未关中断就发布 hdr/args 这一对，ISR 可能读到半更新的一组。一个文件、8 行，把发布与清除放进临界区。

两笔都是「缺一个判断」的量级，验证也都停在静态检查，未跑板。

四、BSP 与测试基建

4.1 K230 PWM 回读：补偿值当成了高电平计数（11-11）

日期：2026-11-11 17:20（提案）　来源：提案 #12032

kd_pwm_set() 写输出比较寄存器时存的是 period_count - high_count——K230 的 PWM 用「周期减去高电平」做比较值；而 kd_pwm_get() 把这个寄存器直接当成 high_count 用。结果是 rt_pwm_get() 返回的脉宽正好是互补值：设 25% 读回来 75%。

修法是只读一次 pwmcmp0 作为周期计数，两个换算共用；高电平计数由 period_count - compare 反推，当共享周期较短、导致另一通道的比较值高于 pwmcmp0 时返回 0 脉宽（这是合法的 0% 状态），仍返回 RT_EOK 并保持 pulse 不超过 period。

验证做得比这一批的平均水平扎实：主机上用真实驱动函数配模拟寄存器，另在 01Studio CanMV K230 上以 GPIO52/PWM4（pwm1 通道 1）实测。原有的五个用例点仍通过，跨通道回读从 50000 与 4294942296 纳秒变为 50000 与 0 纳秒——前一个数字本身就是回绕的证据。用例同时扩到 0%、25%、75%、100% 占空比、需要非零分频的周期，以及跨通道比较值下溢的场景。

4.2 utest 多轮运行开始吐账：原子用例每轮漏 25 KB（11-11）

日期：2026-11-11 19:55（提案）　来源：提案 #12033、提案 #11983

11 月 9 日合入的 utest 多轮运行与资源采样（#11983）开始见效：它让同一用例在一次启动内连跑多轮，并在轮次之间采样空闲内存与线程表，用例自身的资源泄漏因此无处可藏。

这一笔处理 core.atomic。test_atomic_add() 每轮新建一个信号量与三个动态线程，两者都不回收。线程退出后 TCB 与栈要等 rt_defunct_execute() 在空闲线程里执行才释放，而用例一直占着可运行线程，空闲线程根本没机会被调度。

实测数据（bsp/qemu-vexpress-a9、多轮开关开到 3 轮）：只跑 core.atomic 时，已用堆 63608 → 88848 → 114088 字节，每轮涨 25240；ps 显示残留 t1/t2/t3 各三个、状态 close。修后三轮恒定 38368，残留为 0。信号量那部分更隐蔽：与 event、atomic 三个用例连跑时每轮只涨 64 字节，正好是一个 rt_semaphore 的大小。

修法十三行：返回前延时 1 毫秒让 defunct 队列被处理，再删掉信号量。与 hooklist_tc.c 里既有的等待约定一致。

六、总结与趋势观察

6.1 从 CVE 到自家议题：审计进入第二阶段

6.2 修复的质量分层：跑过板的与只做静态检查的

日期：2026-11-12　来源：提案 #12032、提案 #12033

本期十笔新提案里，验证一栏的写法分成两类。K230 PWM 那笔跑了真实硬件，给了修改前后的具体读数；utest 原子用例那笔给了三轮的内存与线程数采样，还区分了「只跑 core.atomic」与「三个用例连跑」两种情形下的泄漏量。

另外七笔的安全提案统一写「静态确认、未跑板、未构造 PoC」，其中两笔明确写了「未搭恶意 9P 服务端」「未构造恶意 CFI 几何」。这个诚实度值得记，但也意味着这批修复目前只有编译与代码审读的保证。对使用者的现实含义是：它们进 release 之前，不宜当作已验证的防护。

6.3 待审队列 158 笔提案、365 个议题

日期：2026-11-12（核查）　来源：提案列表、议题列表

较上一期的 149 笔提案、365 个议题，提案增九笔、议题持平。构成：窗口内 1 笔合入（#12011）、10 笔新增提案、1 个新议题（#12030）、1 个议题关闭（#12010）。

上期点名的几笔本期都没有合入记录，其中 CAN 驱动重构（#11779）在窗口内有更新。tty ioctl 用户指针校验那条线现在由 #12037 承接，但它自己也还在审——同一主题从一笔议题变成一笔提案，排队位置并没有前移多少。

6.4 维护边界与修复意愿的拉锯

日期：2026-11-12　来源：提案 #12036

legacy USB 那处代码在 24 小时内走完「议题、八行修复、以不再维护为由关闭、更宽的修复重提」四步。关闭声明给出的是维护范围，重提给出的是成本，两者在同一个议题上并存，谁也没说服谁。

一个走过二十年的 RTOS 必然背着 legacy 组件，宣布不再维护是合理的资源决策。但对仍在用 RT_USING_USB_HOST 老栈的产品，这条声明等于把安全责任转移到集成方。项目若能把「不再维护但仍在树内」的组件列成清单，会比散落在单个提案评论里更有用——这件事上一期提过，本期又验证了一次。
