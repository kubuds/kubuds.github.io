二、安全与稳定性跟进

2.1 signalfd 的全局计数越界：第 11 次调用起把内核指针写到堆块之外（10-26）

日期：2026-10-26 16:13（创建时间）　来源：Issue #11933

这是本期分量最重的一条。研究者指出 components/libc/posix/io/signalfd/signalfd.c 里用一个文件作用域的全局计数器 is_head_init 去索引每个文件描述符私有的数组 sfd->lwp[10]，而 signalfd_add_notify() 在使用前没有任何边界检查。signalfd_close() 从不回退这个计数，所以它只增不减；新建上下文时又只清零 lwp[0 .. is_head_init-1]，同进程再次创建时永远匹配不到自己，必然走写入分支。

后果写得很具体：lwp[] 是 struct rt_signalfd_ctx 的最后一个成员，整个结构在 arm32 上是 1536 字节，数组正好压在堆块末尾。第 11 次调用 signalfd(-1, ...) 时，写入落在分配块之外第一个字，即小内存分配器的下一个块头；此后每创建一次再向外推 4 字节（64 位下 8 字节步长），形成持续、由调用方控制节奏的内核堆越界写，写进去的值还是内核指针。

影响面按作者逐个标签核对：引入点是 2023-09-11 的 7c3d966d（#8001），v5.0.2 / v5.1.0 / v5.2.0 / v5.2.1 / v5.2.2 / v5.3.0 与当前 master（5d1fb66d）全部命中。触发前提只有 RT_USING_SMART=y——RT_USING_POSIX_SIGNALFD 在该配置下默认为 y，两个官方 QEMU Smart BSP 的配置也都开着，因此默认的 RT-Smart 构建即可触发。复现用 bsp/qemu-vexpress-a9（Cortex-A9、32 位、FAT sd 卡根文件系统），PoC 以 /sbin/init 安装。

目前该单无对应修复提案，也未打标签。

2.2 musl 线程链表在并发退出下的释放后使用：futex 锁没有起到互斥作用（10-26）

日期：2026-10-26 11:22（创建时间）　来源：Issue #11932

第二份缺陷单来自另一位报告者，环境是 RT-Thread 5.2.2 的 RT-Smart、SMP、aarch64、musl 1.2.5。现象是并发 pthread_create 与 pthread_exit 时用户进程崩溃，崩点在 musl_pthread_exit：链表摘除时写入的线程描述符已经被释放或解除映射（Data Abort），或者线程的返回地址被改写成 0（Instruction Abort）。

作者的定位结论是问题完全在用户态：musl 用基于 futex 的 __tl_lock / __tl_sync 保护线程链表，但在 SMP 并发退出的场景下这组锁没有真正提供互斥，导致双向链表被写坏；内核侧 futex 实现本身语义正确，不承担这个缺陷。复现材料是一个 1000 轮、8 线程的 tl_race 程序，几百轮内即崩。

该单带 bug、Arch: ARM/AArch64、RT-Smart 三个标签，附完整分析文档。与 2.1 一样，落在 RT-Smart 这条线上，但层次不同：2.1 是内核堆，这一条是用户态 libc。

2.3 时间子系统两处修复转为成熟版：settimeofday 去强转、gmtime_r 处理负时间戳（10-26）

日期：2026-10-26 14:17 与 17:48（最后更新）　来源：PR #11928、PR #11929

上一期记录的时间子系统四单，对应的两笔修复在本窗口内推进了一步，且都勾选了「成熟版本，可合入」。

#11928 只改一个文件，+185/-135：settimeofday() 原来先用 (long) 把 tv_sec 强转再判断正负，在 ILP32 且 time_t 为 64 位、long 为 32 位的配置下，2^31 到 2^32-1 之间的合法时间戳会被截成负数，函数在碰 RTC 设备之前就以 EINVAL 拒绝——2208988800（2040-01-01）就是这样被拒的。修法是按字段自身类型校验，不做强转。

#11929 两个文件 +104/-9：gmtime_r() 用 C 的除法与取模拆时间戳，而 C 的除法向零截断，负输入下余数为负，年份循环又只能往未来走，于是 -1 得到 1970-01-01 00:00:-1、-31536000 的年份字段变成 1970-01--364。修法是把负数路径规范化后再拆。

两单都没有合入。另两笔（timer_gettime() 截断 #11924、时间子系统工作项调研 #11927）本窗口内无新进展。

3.2 Eclipse 工程生成器漏传内核宏：Studio 的 24 个隐式声明警告有了解法（10-26）

日期：2026-10-26 23:33（最后更新）　来源：主仓提案 #11930

上一期收录的社区长文记录过「Studio 构建报 24 个 rt_sched_* 隐式声明警告」，这轮有了对应提案：单文件 +151/-2，从工程生成器一侧修。

根因写得很清楚：include/rtsched.h 里的调度器接口由 __RT_KERNEL_SOURCE__ 与 __RT_IPC_SOURCE__ 两个宏保护，gcc 与 armclang 分支在 src/SConscript 里通过 LOCAL_CPPDEFINES 注入，命令行 scons 构建能识别，但 Studio 每次 make 之前调用的 tools/targets/eclipse.py 不收集这个组级定义，于是 dist 导出工程出现 24 条 -Wimplicit-function-declaration：clock.c 1 条、ipc.c 7 条、thread.c 12 条、timer.c 1 条、scheduler_comm.c 3 条。

修法是把 __RT_KERNEL_SOURCE__ 提到 Kernel 组的全局 CPPDEFINES，与既有的 msvc 分支保持一致。改动不涉及内核源码，只动工程生成脚本。

5.2 社区长文《rtthread启动链路分析》：从 Reset_Handler 到 main 拆成三段（10-26）

日期：2026-10-26 08:59（发布）　来源：社区文章：rtthread启动链路分析

社区文章接口在窗口内只新增了这一篇，约 5700 字，作者自述环境是 STM32F103C8T6 + RT-Thread 4.0.3 + RT-Thread Studio 2.3.1（GCC），并声明文中代码取自本工程实际构建，不是照抄手册。

链路拆成三段：第一段是汇编，Reset_Handler 把 .data 初值从 Flash 搬到 SRAM、清零 .bss、调 SystemInit、跳 entry——作者特意点出一个常见误解，SystemInit 并不把主频配到 72MHz，它只是把 RCC 打回复位状态并把 SCB->VTOR 设到 Flash 起始；第二段是 C 初始化，entry 进入 rtthread_startup()，rt_hw_board_init() 里才配 72MHz 时钟与堆，随后建 main、timer、idle 三个线程；第三段是调度器启动，rt_system_scheduler_start() 挑优先级最高的就绪线程，默认先跑 timer 线程，main() 要等到 main_thread_entry() 里 rt_components_init() 之后才出场。

文末还给了四个「容易记错的点」与一节自验方法，属于读内核代码时的常见困惑点汇总。

6.1 本期趋势：合入停摆，缺陷报告与工具链改造接棒（10-26）

日期：2026-10-26（本期）　来源：主仓库提交记录

四条线可以概括今天：

四是厂商侧仍以 BSP 为主。瑞萨 RA6W1 进入二期资源分配优化，ST 补以太网 ops 与 SR8201F PHY，乐鑫的 ESP32-S3 BSP 提案仍在 55 个文件规模上等待评审，没有芯片新品或架构级动作。
