1.3 维护者初查 #12090：两处待议，明确不构成批准（11-27）

日期：2026-11-27 03:06（评审）。
来源：#12090。

Bernard Xiong 对 head e2224ab 给出初查结论，并写明覆盖不完整。已读范围包括 can_internal.h 的契约与 can_tx.c、can_rx.c 全文。还包括 dev_can.c 的 open/close/control 生命周期，以及 STM32 bxCAN 的 sendmsg 与 TX 中断关键路径。未读其余 30 个 BSP 适配器、dev_can.h 的全部 API 变更、Kconfig 与 CI matrix、utest 用例。

第一处待议是 STM32 bxCAN 关掉了 AutoBusOff。drv_can.c 第 173 至 175 行把 ABOM 从 ENABLE 改为 DISABLE，同时把 AutoRetransmission 改为 ENABLE。提案描述没有交代这项行为变更。关掉 ABOM 后控制器进入 bus-off 不会自动恢复。此时再调 RT_CAN_CMD_START 会返回 -RT_ERROR，因为 HAL 状态不是 READY。用户只能 close 再 open，走 DeInit 与 configure 才能恢复。评审认为这对依赖自动 bus-off 恢复的现场总线场景是可见回归。

第二处待议是管理操作失败后数据路径保持关闭。_can_reconfigure() 在 BSP 操作返回错误时直接跳 out_unlock。此时 TX admission 已关、RX 已 pause，除 SET_PRIV 参数校验外没有回滚。SET_BAUD、SET_FILTER 或 CONFIGURE 因硬件原因失败后，设备仍无法收发，直到再次 START 或 close/open。评审给出两条路：若是有意 fail-closed，写进公共 API 文档；否则对非 STOP 命令恢复 was_accepting 与 RX admission。

评审末尾写明：无实板验证，46 文件、新增 8936 行属大型重构，建议下一轮完整审查后再决定是否批准。

二、评审推进：两笔收敛，一笔等 CI

2.1 serial_v2 DMA 缓存行对齐获维护者批准（11-27）

日期：2026-11-26 11:16 至 2026-11-27 03:03。
来源：#12084。
议题 #12063。

议题 #12063 说的是 Cortex-M7 开 D-Cache 后的老问题。serial_v2 的 DMA ping buffer 分配在 RX FIFO 块内，起始地址从不按 32 字节对齐。SCB_InvalidateDCache_by_Addr 作废缓存行时会连带污染前后的堆块。TX 侧同样存在这个风险。

提案把 ping buffer 起始地址在 ringbuffer 之后按 32 字节对齐。dma_ping_bufsz 向上取整到缓存行整数倍，总分配大小相应调整。作者 liangzhan5 顺手回滚了 hpmicro BSP 里的局部修复。改动 1 个文件，新增 9 行、删除 2 行。作者自报手头无实板，只做静态分析。

Rbb666 在 11 点 16 分给出两处行内意见。第一处针对 hpmicro 的回滚。HPM6750 缓存行是 64 字节，框架只保证 32 字节对齐。移除 BSP 对齐后，非阻塞 DMA TX 的 flush 可能把 FIFO 头或相邻堆块一起写回。第二处针对分配条件：只看全局 RT_SERIAL_USING_DMA，纯中断接收的板子也会多申请 32 字节。

作者当晚 21 点回复。TX 侧改动取消，理由是「其实没有需要保护的实际场景」。HPM 的 BSP 对齐保留，不再动那个文件。

11 月 27 日 3 点 03 分，Bernard Xiong 在 head 156fbaf 上批准。评审确认改动只保留 RX ping buffer 对齐，删除 TX 侧改动，保留 HPM 的 BSP 对齐，方向正确。实现细节按 sizeof(struct rt_serial_rx_fifo) + rx_bufsz 计算偏移。分配时预留 RT_ALIGN(dma_ping_bufsz, RT_CPU_CACHE_LINE_SZ) 再加一个缓存行，最后对起始地址做对齐。

判断：这是本期唯一走完评审全流程的提案。依据是意见、返工、批准三步在 24 小时内闭合，争议点被限缩到一个缓冲。

2.2 devtmpfs 越界写补上冲突与复现，七个待批 CI 才放行（11-27）

日期：2026-11-26 20:06 至 2026-11-27 03:03。
来源：#11842。

#11842 修的是 devtmpfs 的栈溢出。_path_separate() 与 _get_subdir() 不接收缓冲区长度，把任意长度的路径分量 rt_memcpy 进调用者的 256 字节栈数组。dentry->pathname 最长可达 4092 字节，单个分量超过 255 字节就溢出，越界可达约 3.8 KB，能覆盖返回地址。上游 tmpfs 的同名函数已带 parent_size、file_size、name_size 校验并返回 -ENAMETOOLONG，devfs 这一份是漏项。

20 点 06 分，作者 HANYAODONG 报了两件事。冲突已解决，mergeable_state 从 dirty 变为 unstable。冲突只在 .github/utest/configs/components/dfs.cfg 一处。master 的 #12067 改了 dfs utest 的选项名，合并时保留 master 的写法，自己的配置追加在后面。

验证缺口也补上了。作者按 utest_auto_run 的原样顺序在 bsp/qemu-vexpress-a9 上本地重放。把 dfs.cfg 追加进 .config，用 scons –pyconfig-silent 生成，再 scons 编译。rtconfig.h 中出现 RT_UTEST_TC_USING_DEVTMPFS_PATH，编译通过，QEMU 下三个用例全部 PASSED。

11 月 27 日 3 点 03 分，Bernard Xiong 复核新 head ebbaae39。相对 56382719 只多了一个与 origin/master 的合并提交，PR 自身 5 个文件没有新增改动。此前 557c58de 上的静态审查结论仍然成立。冲突已解除，unstable 只因新 head 的 workflow 待批准。

维护者随后批准了该 head 上 7 个待批 run。包括 pkgs_test、ToolsCI、MemBrowse、格式检查、utest_auto_run、静态分析与 BSP 静态构建。结论留了口子：目前还不能确认 utest_auto_run 是否通过，等 devtmpfs 用例在 CI 中实际执行并 PASSED 后再更新。

三、全志 V861：第三轮评审，15 条行内意见

3.1 异构演示跑不通：C907 侧没有应答（11-26）

日期：2026-11-26 11:13（评审）。
来源：#12078。

#12078 是 E907 侧板级支持加一个最小异构演示。2 笔提交，77 个文件，新增 8791 行。Rbb666 的总结只有一句：按 README 烧录本 PR 的两份镜像，异构演示无法跑通，因为缺少 C907 侧应答。

具体到 applications/main.c 第 11 行，C907 只打印后退出，没有写 AMP_SLOT_C907 与 AMP_SLOT_C907_REPLY。E907 会一直等到 HETERO-FAIL。

另一处指向 e907 的 main.c 第 92 行。代码直接读旧 MSGBOX 地址 0x03003010，而 #12079 已把这个基址标为不可用。评审要求删掉这次读取。理由是 DRAM 往返不依赖这次探测，未映射时还会触发访存异常。

3.2 UART0 归属与异常返回，三笔提案同病（11-26）

日期：2026-11-26 11:08 与 11:13（评审）。
来源：#12078。
#12079。

UART0 的问题出现两次。C907 启动时会复位 E907 正在使用的 UART0，两端的 FinSH 都启用中断接收，还会争读同一个 FIFO。评审要求为异构模式指定唯一的 UART0 初始化和接收端。#12079 那边更直接：e907 的 main.c 第 83 行再次初始化 uart0，会清空 FIFO、关闭接收中断，重复注册本身也会失败。

异常处理的问题也出现两次。两笔提案的 board/trap.c 第 27 行都是同步异常直接返回，恢复原 mepc，故障指令会反复触发。评审要求在两端记录 mcause 与 mepc 后进入异常处理。

栈大小是第三处硬冲突。#12077 的 Kconfig 第 24 行让 SMP 中断入口按配置计算每核栈顶，启动汇编和链接脚本却固定使用 8192。调大配置值会让中断栈越过预留区，评审要求统一栈大小来源。E907 的 Kconfig 第 21 行是另一个方向：menuconfig 仍可打开 SMP，但 E907 没有编入 SMP 移植，也没有次核启动路径。

3.3 命名与驱动共用：两笔被要求同一处返工（11-26）

日期：2026-11-26 11:08 与 11:13（评审）。
来源：#12078。
#12079。

命名问题指向两处。drv_rpmsg 与 drv_openamp 实际只封装共享内存 ping/reply，不是 libmetal 或 virtio-rpmsg 全栈。评审要求改成反映实际功能的名称，例如 drv_amp_mailbox 与 drv_amp_endpoint，并同步两端引用与 README。

驱动共用问题也重复出现。两端的 UART、FDT、MMC 驱动源码完全相同，应放到 Allwinner 的 libraries/drivers/ 下，由两个 BSP 引用同一份实现。E907 侧的 MMC 副本还完全不参与构建。

#12079 另有两处细节。drv_openamp.c 第 189 行先读门铃，会把 E907 发出的 OA_EVT_LINK 读掉，主端可能先超时，评审要求在链路循环里过滤旧 token。e907 的 main.c 第 146 行按回包长度比较，截短的回包只要前缀一致也能通过验收，要求先校验收发长度一致。

文档也没对上。#12079 的 main 已改为输出 OPENAMP-EPT-OK，README 仍以 RPMSG-OK 作验收依据。

三笔提案到本期截点仍为 open，作者尚未回复这批意见。CI 状态分别是 #12078 30 项中 26 通过 4 跳过、#12079 同样 26 通过 4 跳过、#12077 28 通过 2 跳过，均无失败项。
