一、内核与驱动合入

1.1 RISC-V APLIC：电平中断撤销后不再补发 MSI（11-10）

日期：2026-11-10 16:58（合入时间）　来源：提案 #11966

一个文件、14 行新增、1 行删除，改的是 libcpu/risc-v/common/pic/pic-riscv-aplic.c，作者 zijunteng238-dot，11 月 1 日提交、本期合入。上期报告在待审队列里点名过这一笔，今日落地。

现象是 QEMU 8.2.2 上跑 bsp/qemu-virt64-riscv：RV64、四核 SMP、开 AIA（APLIC/IMSIC），一个每 1000 毫秒打印一次的计数程序只输出 RISC-V test: 0 就停住。根因在电平中断的 EOI 路径——驱动无条件写 setipnum_le，设备其实已经撤销中断，旧版 QEMU 仍据这次写入补发一条 MSI，形成持续的虚假中断，把系统定时器压住，延时线程再也回不来。修法是 EOI 时先读 in_clrip 里该输入的整流状态（已按中断极性折算），只有设备仍在拉高才写 setipnum_le，既保留电平中断的重触发能力，也不给已撤销的源补发机会。

同一提案把 qemu-virt64-riscv 的 main.c 从打印一次改成 0 到 9 的计数循环，每次打印后延时一秒，用来观察修复后的线程恢复。验证覆盖三种配置：开 AIA 四核并关闭网络/NVMe/virtio-console/PCI serial、关 AIA 四核、开 AIA 四核默认设备组合，三者均能完整输出十行；未覆盖真实 APLIC 硬件、低电平外设与其他 QEMU 版本。

QEMU 上游已自行修掉这一模拟缺陷，RT-Thread 这一笔属于给旧版模拟器的兼容补丁——它修的不是内核逻辑错误，而是「驱动按规范写、模拟器按缺陷解」这类只在虚拟平台上出现的错位。

二、安全加固批次：一天十一笔边界检查

2.1 六项 2024 年 CVE 集中收口（11-10）

日期：2026-11-10 01:04 ~ 06:45（提案时间）　来源：提案列表

11 月 10 日一天之内，同一位报告者（cms19859230182-lang）提交十一笔边界检查补丁，其中六笔直接对应 2024 年披露的 CVE，编号相邻、修法同构——都是「先判长度，再进拷贝」：

  • 提案 #12017：FinSH 拼目录路径用无界 rt_sprintf / rt_strcpy / strcat，自动补全按 DFS_PATH_MAX 重新分配并封顶各段拷贝，长度判断由 > 改回 >=（补上 NUL 的差一），对应 CVE-2024-25390、议题 #8286。
  • 提案 #12020：rt_wlan_send_to_thread() 的 len 是有符号 int，负值会让 sizeof + len 与 memcpy 按巨大 size_t 处理，改为 len < 0 直接返回 -RT_EINVAL，对应 CVE-2024-25388、议题 #8285。
  • 提案 #12022：rt_random 是可预测 LCG 且默认种子弱，首次读取时混入 rt_tick_get() 与可选硬件随机源，并在注释与 Kconfig 里标明非 CSPRNG，对应 CVE-2024-25389、议题 #8283。
  • 提案 #12019：var_export 填充 ve_exporter_tab[2048] 时无容量限制，生产构建关掉断言后直接写穿，改为填满即停、运行时夹住计数、零元素不进冒泡排序，对应 CVE-2024-25392、议题 #8290。
  • 提案 #12018：rt-link 组帧前不校验最终帧长，超长载荷写穿静态 sendbuffer，改为先判 data_len 与帧长再 memset/memcpy，对应 CVE-2024-25395、议题 #8289。
  • 提案 #12021：YMODEM 的 _rym_send_begin 用无界 rt_sprintf 写协议缓冲，上传下载用 rt_strncpy(..., DFS_PATH_MAX) 可能不补 NUL，改为 rt_snprintf 封顶、上限 sizeof-1 并显式补零，对应 CVE-2024-25394、议题 #8291。

六笔的共同点在于「断言当边界用」：RT_ASSERT 在生产配置里常被关掉，此前多处把断言当作最后一道检查，实际等于没有检查。这一批把限制改成运行时判断，断言只留作调试辅助。

2.2 装载器与内核对象：libdl 重定位、LWP IPC 属主校验（11-10）

日期：2026-11-10 01:40 与 01:36（提案时间）　来源：提案 #12016、提案 #12015

这是本批次技术分量最重的两笔，改的都是信任边界。

#12016 改五个文件、205 行新增、37 行删除。dlmodule 计算重定位写目标时用 mem_space + r_offset - vstart_addr 而不校验范围，一个构造过的 .mo 可以让 r_offset 下溢或上溢，在重定位阶段直接写进内核内存。修法是新增 dlmodule_check_rel_target()，用防溢出的算术确认目标区间落在模块内存内，接进 ARM、RISC-V、x86 三个重定位器；同时补上 ELF 节头索引（sh_link、e_shstrndx）、符号表索引（ELF*_R_SYM）与 ET_REL 节边界检查，并让 dlelf.c 在失败时中止加载、释放 section_load_addr。对应 10 月 18 日的缺陷 #11898。

#12015 改三个文件、284 行新增、44 行删除。RT-Smart 的 LWP IPC 系统调用原先把用户传入的裸对象指针直接送进 rt_sem_* / mutex / event / mailbox / mq / timer，伪对象即可造成任意内核读写。修法是新增 lwp_user_object_get() 与 lwp_user_object_put()：解引用之前先拒绝用户空间地址，要求句柄存在于调用者的用户对象 AVL 树，比对 rt_object_get_type()，并在系统调用全程（含所有错误路径）持有一份引用；lwp_ref_count 同时覆盖属主与在途引用，内核对象要等最后一个引用消失才销毁。对应 10 月 31 日的缺陷 #11960。

两笔都没有构造攻击样本，验证停留在静态审计与编译层面，这也决定了它们短期内不会进 release。

2.3 内存与网络：内存池断言误报、DHCP 租约过期回收（11-10）

日期：2026-11-10 01:04 与 06:45（提案时间）　来源：提案 #12014、提案 #12024

#12014 修的是一个假警报，但造成的是真实的系统停摆：rt_smem_free() 释放「最后一块、其 next 指向 heap_end 哨兵」的块时会误触发 MEM_POOL 断言。修法显式接受 mem->next == heap_end 这种偏移，其余情况仍保持原有校验；作者明确拒绝改用 mem->prev 判断，理由是 prev 指向上一块（首块为 0），会把校验放松。附带的 core.mem 用例模拟只剩使用位的哨兵场景，验证整块合并。对应 2025 年的旧缺陷 #10632。

#12024 修的是 DHCP 服务端的账期：lease_end 写入后从不被读取，租约永不过期、地址永不回收；顺带发现 DHCP_DEFAULT_LIVE_TIME（0x80510100）经 PP_HTONL() 后在线上是约六十八年，与「按天回收」的语义完全不符，一并改为 86400 秒。改动把租约改成绝对过期时间，分配前惰性回收过期节点，命中、新建、ACK 三条路径统一续租。验证只做了 lwIP 2.0.3 / 2.1.2 / 2.2.1 三个版本的语法检查。

这笔属于「配置常量写错方向」的典型：宏名说的是存活时间，取值却是把纳秒级的数当秒用，不出问题只是因为没人真去等它过期。

三、议题与修复闭环

3.1 ptyfs 句柄泄漏：报告当天出修复（11-10）

日期：2026-11-10 14:04（议题）/ 11-11 02:14（提案）　来源：缺陷 #12023、提案 #12029

ptyfs_unregister_pts() 把 pts 文件从根链表摘掉、回收单元号，却不释放 ptyfs_register_pts() 分配的 struct ptyfs_file。单元号被复用之后，反复 open() / close() /dev/pts/* 就能持续泄漏内存，普通用户即可触发。报告者 XueDugu 附了循环复现。

十二小时后维护者 BernardXiong 提交 #12029（三个文件、11 行新增、2 行删除），在注销路径上把 pts 文件一起释放，目前待审。这是本期唯一一笔「报告与修复同窗闭环」的条目。

3.2 legacy USB host：一笔修复被维护政策关闭（11-10）

日期：2026-11-10 18:13（提案）/ 11-11 00:50（议题）　来源：缺陷 #12026、提案 #12027

缺陷描述的是老 USB 主机栈（components/legacy/usb/usbhost/）：设备描述符的 bLength 未经校验就被当作读取长度，进而写进静态设备数组，恶意 USB 外设可造成越界写与控制流劫持。报告者在 qemu-virt64-aarch64 上端到端复现，并注明主仓 master（自报 v5.4.0-dev，核查于提交 5d1fb66d）在 11 月 11 日重读时仍未修复。

维护者随后提交 #12027（一个文件、8 行新增）做长度校验，随即自行关闭并留言：「这个是 legacy 的代码，将不再持续修正、维护。」修复方向没有争议，关闭理由是维护范围——这条路径上的已知攻击面，此后要由使用者自己评估。

3.3 vDSO 时钟常量：议题成立、修法被否（11-10）

日期：2026-11-10 20:39（议题）　来源：缺陷 #12025、提案 #12028

用 newlib 工具链编译 RT-Smart 的 vDSO 用户代码时，CLOCK_MONOTONIC 与 GNU 系时钟 ID 均未定义：newlib 只在 _POSIX_MONOTONIC_CLOCK 下暴露前者、在 _GNU_SOURCE 下暴露后者，而 vDSO 的自由编译配置两者都没设。提案 #12028（一个文件、22 行新增）选择在本地补定义，维护者判定「这个是错误的修正，应该关闭」，当日关闭。

同一现象下两种处理方式的分歧很清楚：一种是在编译单元里补宏，让构建通过；另一种是让自由编译配置与 POSIX 特性宏对齐。后者没写进提案，缺陷本身仍开放。

4.1 ESP32-S3 移植的半截落地：构建脚本进仓、BSP 不在仓内（11-10）

日期：2026-11-10 11:53（合入时间）　来源：提案 #11844、bsp/ESP 目录

一笔容易被误读的合入。提案 #11844 的标题是「修正 xtensa_context.h 的包含路径」，正文写的却是新增 bsp/ESP/ESP32_S3 与 libcpu/xtensa/esp32s3 两个目录：ESP32-S3-DevKitM-1、Xtensa LX7、UART0 走 GPIO43/44、8MB DIO flash、应用在 0x10000、CI 新增 xtensa-esp32s3-elf GCC 12.2.0。

实际合入的只有一个文件：libcpu/xtensa/esp32s3/ 目录下的 SConscript，25 行。核查主仓 bsp/ESP 目录，当前只有 ESP32_C3、ESP32_C6、libraries、tools 四项，没有 ESP32_S3；libcpu/xtensa/esp32s3 下也只有这一个脚本，没有任何 C 源文件。脚本本身按 bsp/ESP/ESP32_S3 去解析 ESP-IDF 软件包路径，而该路径目前不存在。

也就是说这是半个移植：CPU 端口的构建脚手架先进了主仓，BSP、节拍处理、sdkconfig 与板级验证都不在。提案 9 月 28 日创建、11 月 10 日合入，六周里正文描述的其余部分没有一并落地。对使用者的现实含义是：现在拿不到可编译的 ESP32-S3 BSP，脚本引用的路径暂时解析不到。

六、总结与趋势观察

6.1 安全审查从个案转向批次

日期：2026-11-10　来源：提案列表

窗口内 14 笔新提案，11 笔来自同一位报告者，且集中在 11 月 10 日凌晨五个多小时内连续提交。题材不是零散发现，而是按模块扫过来的清单：FinSH、WLAN、随机数、var_export、rt-link、YMODEM、libdl、LWP、内存池、DHCP、ESP32-C3。每笔都附「动机 / 改动 / 验证」三段，验证口径统一写成静态检查与编译，并诚实标注「未构造 PoC」。

这种形态与零星的安全议题不同：它更像一次有计划的审计收尾，把多年积累的低危条目按可利用性排序后逐条补上。对项目方而言，代价是待审队列一天涨了九笔，全部需要人工评审。

6.2 六项 CVE 与两年半的时差

日期：2026-11-10　来源：CVE-2024-25388 等对应议题

六项 CVE 对应的原始议题编号在 #8283 至 #8291 之间，属 2024 年的报告批次，到今天补齐约两年半。这不必读作懈怠：RTOS 项目的评审资源集中在芯片适配与版本发布上，若非有人按清单回头扫，这类「需要构造畸形输入才能触发」的条目会一直沉在队列底部。

真正值得记的是修复方式的一致性——六笔都在补同一个洞：把断言当边界。断言在生产构建里会被关掉，这件事在嵌入式项目里人人知道，但把它当检查用的代码仍成规模存在。

6.4 修复被政策关闭：legacy 代码的边界

日期：2026-11-10　来源：提案 #12027

本期有两笔提案由维护者本人提交后当日关闭，理由都不是技术不成立：一笔说修正方向错（vDSO 补宏），一笔说这段代码进入不再维护状态（legacy USB host）。后者更值得注意——缺陷描述里明确写了「恶意 USB 外设可造成越界写与控制流劫持」，这是可物理接触的攻击面。

一个走过二十年的 RTOS 必然背着 legacy 组件，宣布不再维护是合理的资源决策；但对仍在用 RT_USING_USB_HOST 老栈的产品，这条声明等于把安全责任转移到集成方。项目文档里如果能把这类「不再维护但仍在树内」的组件列成清单，会比散落在单个提案评论里更有用。
