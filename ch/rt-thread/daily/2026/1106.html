1.1 ARM 配置搬出公共 Kconfig：libcpu 开始按架构分家（11-05）

日期：2026-11-05 22:26（合入时间）　来源：提案 #11988、议题 #9187

267 行新增、173 行删除，三个文件：新增 libcpu/arm/Kconfig，原 libcpu/Kconfig 里 ARM 相关的架构标识、内核型号、ARM MMU/MPU 与 GIC 配置整体搬进架构目录，原地用 rsource 引入；公共能力与跨架构的 KERNEL_VADDR_START 留在原文件。作者 zijunteng238-dot 上午 11:51 建提案，晚上 22:26 合入，十个半小时走完全程。

这次的做法值得单独记一笔：它不新增菜单、不改符号、不改默认值、不改依赖与 select 关系，只搬家。验证方式也不是「编译过了就算」——作者用 Kconfiglib 14.1.0 对拆分前后的全部解析符号做对比，配置值、类型、可见性、可赋值范围、默认值与选择关系逐项一致，排除文件路径与行号变化后没有新增解析警告；比对覆盖五个 BSP：frdm-k64f（Cortex-M4）、qemu-vexpress-a9（Cortex-A9）、renesas/rzt2m_rsk（Cortex-R52）、qemu-virt64-aarch64 与 qemu-virt64-riscv，并在 RISC-V 上跑了 scons –menuconfig 比对菜单输出。另外在内存里给 A9、AArch64、RISC-V 打开 SMART 与 IOREMAP_LATE 再比一轮，未写回配置文件。

对长期维护的意义在结构：libcpu/Kconfig 此前把 CPU 公共能力和多架构配置混在一起，任何架构加选项都要动同一个文件，冲突与误改概率随架构数量上涨。这次拆完，RISC-V、ARM 各自的 Kconfig 可以独立演进，与上一期文档化的版本发布流程是同一条治理线——先把结构理顺，再谈版本节奏。配套新增了 documentation/4.tool/scons/libcpu_kconfig_arm_split.md，把拆分范围、依赖处理与验证结果都写进仓库，后续搬其它架构可以照此执行。

1.2 RISC-V Smart 的 MMU 与用户异常：四处根因一起修（11-05）

日期：2026-11-05 11:15（合入时间）　来源：提案 #11892

109 行新增、8 行删除，四个文件，维护者 BernardXiong 提的，10 月 18 日建、本期合入，中间经过 11 条行内评审。这条对 RISC-V 侧的 RT-Smart 是本期最实质的一笔。

改动列了四条根因，都是同一类问题的不同侧面。其一，早期页表指针没有按内核物理偏移做转换，内核被加载到非零物理地址时页表描述符指错地方。其二，每个 hart 的内核页表继承了用户映射，等于在 hart 之间留下了不该有的地址空间。其三，早期页表在打开 MMU 之前没有清理。其四也是最要命的一条：未处理的用户态异常会让内核整体终止，而不是只结束当前进程——用户进程的一条野指针就能拖垮系统。

对应的修法是：新增玄铁架构选择与 SVPBMT 选项；早期页表指针带内核物理偏移转换；允许 MPR 范围延伸到低于链接内核基址；启用 MMU 前先清理早期页表；清掉每 hart 内核页表里的用户地址项；用户异常只终止当前 LWP；上报用户上下文期间保持中断开启。

验证条件写得坦白：BSP 用 qemu-virt64-riscv 与 bsp/k230，配置 RT_USING_SMART 加 ARCH_RISCV64，作者本地没跑构建，理由是环境里没有 RISC-V musleabi 工具链，交 CI 验证。这与上一期串口那笔的验证说明是同一种坦白，方向上没问题，但 RISC-V Smart 这条线上的运行时行为最好还是靠实机复测兜底。

1.3 信号投递不再持锁睡眠，ELF 段保护顺序纠正（11-05）

日期：2026-11-05 11:16（合入时间）　来源：提案 #11895、提案 #11899

两笔同属 lwp 子系统，都由 BernardXiong 合入。第一笔 #11895 改五个文件、58 行新增、27 行删除，含 RISC-V 侧的汇编入口 lwp_gcc.S、lwp_elf.c 与 lwp_signal.c，三个提交。核心是顺序问题：信号处理路径会拿睡眠锁，因此必须保持可调度，代码里用 OPEN_INTERRUPT 与 CLOSE_INTERRUPT 在关键段落显式开关中断；同时纠正了 ELF 段保护的施加顺序，避免先写后保护。

二、安全跟进与待合并队列

2.1 ivshmem 把设备配置字当可信输入，/dev 节点成了任意物理内存通道（11-06）

日期：2026-11-06 00:54（报告时间）　来源：缺陷 #11992

报告者 XueDugu，延续他最近几期在 PCI 与设备驱动侧的一条线。问题在 ivshmem 驱动的探测函数：当 BAR2 报告的尺寸为零时，代码走 JailHouse 回退分支，直接从 PCI 配置空间 0x40 到 0x4f 四个双字读取共享内存的地址与大小——这四段由设备侧决定，驱动没有任何校验，随后把它们交给 rt_ioremap，而 rt_ioremap 本身不检查物理地址合法性。

后果链条很短：恶意或格式异常的设备把「共享内存」描述成内核内存区间，映射照样成功，窗口再被注册成 /dev/ivshmemN。之后的读写走的是官方 open/read/write 路径里的两次 memcpy，一次把内核内容拷给用户，一次把用户数据写回内核。于是任何非特权进程只要打开这个设备节点，就拿到任意内核物理内存的读写能力，字节粒度、数据完全可控，不需要任何特殊 ioctl 或额外权限。

报告还指出一处附带问题：原代码把 64 位字段拆成两个 32 位写入，在 32 位构建上会写到相邻字段，等于顺手破坏结构体。这条与 MSI-X 那条同一个模式——设备固件提供的值被当作可信输入，而驱动侧缺少「先校验后使用」的固定动作。

2.2 两小时十一分钟后出修复：新增选项把 JailHouse 回退关进笼子（11-06）

日期：2026-11-06 03:05（提案时间）　来源：提案 #11993

99 行新增、7 行删除，两个文件，维护者 BernardXiong 提的，状态待审，已有一条讨论。

修法分四层。第一层是默认关闭危险路径：新增 RT_IVSHMEM_JAILHOUSE 选项，默认 n，帮助文本写明设备必须可信；不打开它时，BAR2 不存在就直接拒绝探测，不再读配置字。第二层是映射前校验：尺寸非零、地址加尺寸不溢出、整个区间能用本地指针与尺寸类型表达。第三层是类型修正：四个配置双字先读进 64 位局部变量，不再通过 32 位别名写结构体字段，顺带修掉相邻字段被踩的问题。第四层是检查配置空间读取的返回值，读失败不再继续。

验证只到编译与格式：两种选项组合（JAILHOUSE 关与开）在 qemu-virt64-aarch64 上都能编译通过，改过的文件过 clang-format。从 00:54 报告到 03:05 提案，两小时十一分钟，比上一期 MSI-X 的六小时又快了一截。

3.1 Titan Board 接上 OpenMV：170 个 Python 示例，NPU 走 TFLM（11-05）

日期：2026-11-05 17:30（专栏发布时间）　来源：电子工程专辑：Titan 也能玩 OpenMV 了、工程：Titan_Openmv

RT-Thread 官方专栏本期发布 Titan Board 的 OpenMV 工程，把 RT-Thread 5.1、OpenMV 5.0.1 与 MicroPython 一起搬到这块基于瑞萨 RA8P1 的板子上：1 GHz Cortex-M85 跑系统与应用，250 MHz Cortex-M33 协处理，Ethos-U55 NPU 配到 500 MHz，外挂 32 MiB HyperRAM 存图像与运行内存，峰值 AI 算力标称 256 GOPS。外设侧接 OV5640 MIPI 摄像头、FAT/FAT32 SD 卡、USB HS 的 CDC 与 MSC 复合设备，以及板载三色 LED 与按键。

示例规模是这次的主要卖点：共 170 个独立 Python 脚本，传统视觉 124 个，覆盖相机控制、拍照录像、绘图、滤波、颜色跟踪、条码、特征检测与 AprilTag；机器学习 23 个，配 20 个面向 Ethos-U55-256 的模型文件与一个由 CPU 执行的数值回归模型，任务覆盖手势（剪刀石头布、手掌检测、21 点手部关键点）、人脸与姿态（人脸检测、468 点关键点、人体姿态）、目标识别（行人、猫狗、COCO80 常见物体）与图像分类分割。

工程组织方式对上手有实际帮助：代码在 SDK 的 project/Titan_Openmv，同时支持 RT-Thread Studio 与 SCons；构建产出两个必须配套使用的文件——rtthread.hex 走 DAP-Link 或 J-Link 烧录，openmv-vision.bin 走 USB 复合设备传输，两者必须来自同一次构建。模型与标签放 models/sdcard/，按说明复制到 SD 根目录即可；脚本里的 /rom 是 SD 根目录的只读别名，不需要另建目录；想让作品开机自启，把应用存成 SD 根目录的 main.py。文中还特别提醒 IDE 里显示的 AE3 只是协议兼容标识，不能刷 Alif AE3 的固件，板子用的是本工程的 RA8P1 固件。

两点技术判断：一是这套组合把「相机采集、图像处理、神经网络推理、外设控制」串在同一条 Python 脚本里，端侧视觉的门槛从写 C 驱动降到改参数；二是算子按支持情况在 CPU 与 NPU 之间分流，TFLM 负责调度，意味着模型能不能跑起来取决于算子覆盖，示例里的 20 个模型本身就是一份可用的覆盖清单。

3.2 Env 插件市场改成无服务器索引：插件包放进 GitHub Release（11-06）

日期：2026-11-06 07:05（合入时间）　来源：提案 env #304、提案 sdk #11、索引目录 env-plugins

两个仓库同一批改动：sdk 仓库新增 env-plugins 目录，放一份 index.json 作为插件目录，每个插件一个子目录再放自己的 index.json；env 仓库实现读取这份「无服务器索引」，并从 GitHub Release 下载 .epack 安装包。env 侧 1108 行新增、48 行删除，18 个文件，包含市场逻辑、WebUI 前端页面、命令行子命令与五组测试；sdk 侧 125 行新增、四个文件。

对外可见的变化是使用方式：默认从本地 SDK 仓库读索引，不需要部署市场服务器；插件包发布在 GitHub Release；显式设置环境变量或执行 rt-env plugin market set 仍优先走 HTTP 市场，而 rt-env plugin market clear 可以清掉文件里的 HTTP 配置回落到 SDK 来源，环境变量始终优先级最高。首个上架插件是 RT-Kconfig 配置器 0.1.34，索引里的下载记录指向该仓库 Release 里的真实 .epack 资产，不是占位条目。

安全侧做得比预期细：下载尺寸有上限，超限返回 413；重定向必须同主机同协议，跳到意外域名直接拒绝；索引路径禁止逃出 env-plugins 目录；插件 id 有正则约束且检测重复。配套提交把插件回归测试接进 GitHub Actions，并在 CI 打包测试前先构建随包 epack。对生态的实际意义是，第三方插件不必再等官方市场审核与服务器，发一个 Release 加一条索引就能分发，代价是信任边界从「官方市场」挪到了「仓库维护者」。

4.1 ESP32-C3 预编译镜像拒绝 v1.x 芯片：最小版本字段没对齐（11-05）

日期：2026-11-05 23:24（报告时间）　来源：缺陷 #11991

报告者 anamarija-j，影响版本写明 v5.3.0 与 master cbadbdf，硬件是 ESP32-C3、芯片修订 v1.1（ROM 版本 esp32c3-eco7-20230720），BSP 为 bsp/ESP/ESP32_C3。这是本期唯一一条 RISC-V BSP 的回归缺陷。

现象分两段：esptool 直接拒绝烧写，提示预编译的 bootloader.bin 要求芯片修订 3 及以上，而这块板子是修订 1；加 –force 强烧后，二级 bootloader 能启动，但在读分区表之前停止，日志写明芯片是 V101、应用配置的最低修订是 3。

根因在字段语义：预编译 bootloader 只填了旧的 min_chip_rev 字段（值 3），全量字段 min_chip_rev_full 是 0；这颗 ESP-IDF v5.0-dev 的 bootloader 恰好拿旧字段与次版本号比较，v1.1 的次版本是 1，于是判定不满足。BSP 的 SConstruct 同样只设置 image.min_rev = 3，生成的 rtthread.bin 带同样的问题。换句话说，同一个「最低修订」用新旧两套字段表达，预编译产物与构建脚本都只写了旧的那套，遇到按新规则解读的芯片就卡住。

这条的实际影响面不小：ESP32-C3 是 RT-Thread 生态里最常见的 RISC-V 无线 MCU 之一，预编译镜像不能用等于新用户第一次上板就失败，只能自己从头编译。修法不复杂，SConstruct 与预编译产物同时写 min_chip_rev_full 即可，但要连带重新出包。

4.2 BSP 与测试基建五笔：D1s 进 QEMU、efm32 进 menuconfig、三套框架测试（11-05）

日期：2026-11-05（合入时间）　来源：提案 #11903、提案 #11867、提案 #11883、提案 #11982、提案 #11976

BSP 侧两笔，都是「让板子更好用」的方向。全志 D1s 补了 qemu-d1s.sh 启动脚本，可以直接在 d1s 的 QEMU 机型上跑这个 BSP，省掉找镜像与拼参数的步骤（#11903）。EFM32 补了 Kconfig 与 .config，正式支持 scons –menuconfig，此前只能手改配置（#11867）。

测试基建三笔，方向一致：给框架本身加模拟设备测试。看门狗补冒烟测试，容忍超时量化的误差与非可停止的关闭路径（#11883，对应缺陷 #11446）；I2C 用模拟总线覆盖框架层，不依赖真实硬件（#11982）；DAC 用模拟设备测试（#11976）。三笔都由社区贡献者提交，加上 2.5 里待审的 QEMU 自动运行改造，可以看出一个明确动作：把驱动框架的验证从「等硬件」变成「进 CI」。

五、本期趋势与总结

5.1 一天三十一笔：积压清账取代逐步推进

本期 24 小时主仓库合入 31 笔提案，是近期最大的一次单日批量。时间分布很集中：02:47 到 03:18（北京时间 10:47 至 11:18）的 31 分钟内合入 17 笔，05:23 到 10:40 之间再合入 13 笔，最后一笔 ARM Kconfig 拆分在 22:26 单独落地。

批次构成说明这不是「今天写、今天合」：多笔是 10 月中下旬建的老提案——#11892 与 #11897 同一天建（10-18）、#11901 建（10-19）、#11918 建（10-22）、#11935 与 #11941 建（10-28）、#11947 建（10-29），最老的一笔 #11558 建在 7 月 5 日。也就是一个跨了四个月的积压，在一次集中评审后统一落地。对下游的意义是：这两天拉 master 会看到一大片变更，回归测试的成本集中释放，而不是摊平到每天。

另一个信号是合入者的结构。31 笔里 usualtreee 7 笔、BernardXiong 5 笔、cms19859230182-lang 4 笔、adilalperenciftci 2 笔，其余 13 笔来自不同贡献者。审核与提交的分工已经比较清楚：外部贡献者出补丁，维护者做校验与合批。

5.2 趋势：设备侧输入成为第二个主战场

把最近四期连起来看，攻击面在挪位置。10 月底到 11 月初报的多是系统调用层的「值到对象」缺校验：getaddrinfo 的嵌套用户指针、pipe 的 ioctl 指针、timerfd、块设备分区的裸指针。这一期的两条新缺陷换了前提——MSI-X 要求插进来一块恶意设备，ivshmem 要求设备把配置字填成内核地址。共同点是：设备固件提供的寄存器被内核当作可信输入，而 rt_ioremap 不做物理地址合法性检查，于是「设备说什么就映射什么」。

处置速度是另一条线：MSI-X 从报告到提案 6 小时、到合入两天；ivshmem 从报告到提案 2 小时 11 分。报告者给的是带 PoC、带日志、带版本追溯的完整材料，维护者拿到就能直接改，这比流程规定更能压缩修复时间。代价是队列继续变厚：48 笔待审更新，块设备分区那笔挂了三天仍未合。

第三条线是结构与工具同步推进：libcpu/Kconfig 开始按架构分家，版本编号与发布流程已经成文，Env 的插件分发从中心化市场改成「仓库索引加 Release」，测试则从等硬件改成进 CI。这四件事不在一条线上，但都是把「靠人记」换成「靠结构约束」。

5.3 局限性与去重说明

论坛仍返回 468 并前置 WAF 挑战页，社区讨论侧的缺口由 GitHub 补齐；官方新闻接口与官网新闻列表均停在 6 月 17 日，连续多期无新增。电子工程专辑的专栏聚合页本期直连未取到列表，Titan 一条是靠 Google News 命中标题后用网页抽取核对正文与发布时间的。

GitHub 侧本期采集在后期触及匿名接口限额（60 次每小时），主仓库的合入、缺陷、待审列表与两个附属仓库的提交均已完成核查，但组织外部的 topic 检索本期未执行，因此不排除有个别社区仓库的小幅更新未被收录；这一点如实说明，不做推测性补充。

去重：#11986 上期按待审记录，本期按合入补记并说明链路时间；#11981 上期已列，本期只记状态；#11897 上期在队列里出现过，本期只记更新时间与 RISC-V 关联；Titan 的工程代码在 10-30 已进仓库，本期收录的是 11-05 的官方发布稿与工程说明，不重复计为代码更新。
