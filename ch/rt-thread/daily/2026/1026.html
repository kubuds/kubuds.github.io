一、内核与版本动态

1.1 主线 72 小时只有两笔提交：lwIP 回环 netdev 合入，clang-format 规则细化带 thread.c 示例（10-25）

日期：2026-10-23 17:09 与 2026-10-25 19:26（合入时间）　来源：PR #11859、PR #11893、主仓库提交记录

周末三天的窗口里，master 只落了这两笔提交，节奏与上一期「三日零提交后集中收尾」的判断连得上：合入动作都发生在非工作时段（周五 17:09、周日 19:26），评审本身没有停，只是开发侧没有新代码。

第一笔是 clang-format 规则的收口，2 个文件 +83/-77，只动 .clang-format 与 src/thread.c。分支名带着讨论线索 style/clang-format-discussion-11653，两个提交日期都是 10-09，主体是「对齐、花括号换行与空格规则」的细化，第二个提交把 src/thread.c 按新规则整体格式化作为示例。也就是说这是一笔拖了两周的评审收尾，不是新工作。提案里还记了一条工具事实：index++ 这类写法在 clang-format 18.1.8 与 23.1.3 上都会保持原样，没有对应配置项可以强制改写，校验用 --dry-run --Werror。

第二笔是 lwIP 回环设备进 netdev 框架，3 个文件 +54/-0。此前 lwIP 的回环口没有注册成 netdev，导致两类问题：走 127.0.0.1 的工具链跑不起来；没有物理链路的网络命名空间里没有默认可用的接口。改动新增 RT_LWIP_USING_LOOPBACK 配置项，把 lo／lo0 注册为 netdev 并置为 link up，在未指定接口时选回环作默认接口，同时把 RAW 接收邮箱调大以容纳回环回显。验证配置给的是 qemu-virt64-riscv，提案里写明「本地未编译，由 CI 验证构建」——这与上个月多笔提案的放行口径一致：合入以构建通过为条件，上板另行跟进。

版本侧依旧没有动作：最新发布物与标签还是 09-10 的 v5.3.0，10-17 那笔 v5.4.0 的版本宏至今没有配发布说明、二进制或预发布标签。

1.2 qemu-virt64 打开 RT-Thread Smart：riscv64 关 SMP、ext4 与 elm 挂块设备、ptyfs 与 procfs 上挂（10-25）

日期：2026-10-25 19:50（最后更新）　来源：PR #11896

这份提案 14 个文件 +1263/-1075，把 qemu-virt64-riscv 与 qemu-virt64-aarch64 两个 BSP 的 RT_USING_SMART 打开。此前这两个 virt 平台名义上支持 Smart，但 virtio 块设备没有标准的根文件系统初始化流程，pty 也没有挂载点，很多特性在 QEMU 下根本没法测。

改动可以拆成四块：riscv64 侧关掉 SMP，与 Smart 的单核配置对齐；新增一段初始化流程，在 virtio-blk0 上挂 ext4 或 elm；把 ptyfs 挂到 /dev/pts、procfs 挂到 /proc；重新生成 .config 与 rtconfig.h。构建验证写明 riscv64 用 RISC-V musl 通用工具链、aarch64 用 aarch64 musl 工具链，本地未跑、由 CI 验证。

值得注意的是依赖关系：这份提案显式依赖刚合入的 #11893（RT_LWIP_USING_LOOPBACK 配置符号），.config 是在 #11893 之上生成的，作者说明会在依赖合入后 rebase 并重新生成配置。这类跨提案的配置耦合在 qemu 平台改造里常见，也解释了为什么回环口要先于 Smart 使能落地——没有回环，Smart 下大量依赖本机地址的测试跑不起来。

1.3 lwp_syscall.c 一万一千行拆分：165 个系统调用入口按子系统分文件，行为不变（10-25）

日期：2026-10-25 19:50（最后更新）　来源：PR #11894

components/lwp/lwp_syscall.c 单个文件超过一万一千行，把内存、文件系统、socket、进程、IPC 与时间六类系统调用堆在一起，评审与检索都很困难。提案把它拆到 components/lwp/syscall/ 目录，按子系统分文件，新增共享的系统调用分派表与内部头文件，并在 LWP 的构建脚本里注册新目录。

规模上这是本窗口最大的一笔：22 个文件 +12223/-11638，几乎全是移动与改名。提案自称「机械重构，无功能变更」，并强调 165 个系统调用入口与行为完全保持不变。验证同样是「本地未编译，CI 验证」，配置是 CONFIG_RT_USING_SMART=y。

从工程角度看，这类拆分本身不产生新能力，但它决定了后续 lwp 缺陷（例如本期 2.2 的 sys_poll 回绕）能不能在一个可读的文件里定位。上一期记录的那份 9PFS 长度收敛提案也属于同一条线索：Smart 侧的代码正在从「能用」转向「可维护」。

二、安全与稳定性跟进

2.1 时间子系统一夜间四单连报：settimeofday 窄化、gmtime_r 负时间戳、timer_gettime 截断，附一份 A 至 F 工作项调研（10-23／10-24）

日期：2026-10-23 21:04 与 2026-10-24 20:25（创建时间）　来源：Issue #11922、Issue #11923、Issue #11924、Issue #11927

10-23 晚间，同一研究者在 components/libc/compilers/common/ctime.c 上连着开了三单，加上次日的一份调研单，把时间子系统的语义问题一次性摊开。三单的基线都是 master 的 a59e72fb5c，全部为源码级隔离复现，未上板。

第一单是 settimeofday() 的类型窄化：校验时先 (long)tv->tv_sec 强转，在 time64／long32 的 32 位 ARM ABI 下（time_t 为 64 位有符号、long 为 32 位），合法的正时间戳会被转成负数，于是在调 RTC 驱动之前就返回 -1 并置 EINVAL。作者用 GNU Arm Embedded 10.3-2021.10 做了类型尺寸与窄化行为的隔离验证。

第二单是 gmtime_r() 对负时间戳的处理：函数返回非 NULL，但字段非法。给出的四个对照值很直观——-1 得到 1970-01-01 00:00:-1、-86400 得到 1970-01-00 00:00:00（yday 为 -1）、-31536000 的年份字段变成 1970-01--364、-2208988800 应为 1900-01-01 却得到 1970-01--25566。根因是取模取余都用 C 的向零截断语义，负输入下余数为负，而年份循环只能向未来走。

第三单是 timer_gettime() 的截断：总剩余纳秒先存进 rt_uint32_t 再拆秒与纳秒，10 秒即 100 亿纳秒，赋给 32 位变量直接丢失高位。受影响配置是 RT_USING_POSIX_TIMER 与 RT_USING_CLOCK_TIME 同时打开。

第四单（10-24 20:25）不是缺陷而是调研：把 tick、clock_time、RTC、libc 与 VDSO 各自维护时间基线的问题整理成一份带工作项的设计建议，列出十项不足（设时不统一、clockid 语义混乱、软 RTC 假同步、回绕与溢出、hrtimer 回退、PM 分叉、启动授时状态、NTP 版本边界等），给出 A 至 F 六项可跟踪工作项与 P0 至 P2 的优先级，并明确普通 MCU 走完 A 至 D 即到阶段性终点。该单自己声明是静态分析，未编译未上板。

配套的修复提案已经开出两笔：#11928 让 settimeofday() 按字段自身类型校验、不再统一转 long；#11929 处理 gmtime_r() 对纪元前时间戳的规范化。两笔都在 10-24 提交，仍未合并。

2.2 32 位 RT-Smart 的 sys_poll 回绕：8 字节堆块被当成 0x20000001 项遍历，内核堆越界读写（10-24）

日期：2026-10-24 03:39（创建时间）　来源：Issue #11925

这份缺陷单在 10-24 凌晨提交，问题落在 components/lwp/lwp_syscall.c 的 sys_poll() 与 libc 侧的 poll() 之间。用户态传入的 nfds 在计算分配大小时，nfds * sizeof(struct pollfd) 在 32 位目标上以 size_t 宽度运算，超过约 1.79 亿项就会回绕成一个小值——于是内核按 8 字节的堆块去做 0x20000001 项的遍历，读写都落在堆外。

影响面按作者给出的口径：仅 32 位 RT-Smart 受影响，64 位构建下乘积会提升到 64 位，超大分配直接以 -ENOMEM 失败，不会回绕。引入点是 2022-12-03 的 ecf2d821（sync branch rt-smart，#6641），首个受影响版本为 v5.0.0，v5.0.0 至 v5.3.0 与当前 master（5d1fb66d）均在列。复现用的是 bsp/qemu-vexpress-a9。

这条与上一期 9PFS、NVMe 那族「设备或服务端可控的元数据当长度用」不同：这次是用户态可控的计数在窄位宽下回绕，属经典整数边界问题，但因为落点在系统调用入口与内核堆之间，后果直接是内核堆越界读写。该单目前无对应修复提案。

2.3 上一期合入的 ESP-IDF v6.1 适配在 master 上把 C3／C6 构建打红，include 顺序修复已提（10-25）

日期：2026-10-25 17:49（最后更新）　来源：PR #11926、PR #11870（上期合入）

上一期记录的 ESP32-C3／C6 适配 ESP-IDF v6.1 于 10-22 合入，当时的上板一栏写的是「待验证」。两天后 master 上的 C3／C6 构建转红：按提案描述，master 的两次 CI 运行（40043597502、39929831359）复现了同一现象，并且所有 PR 的 RT-Thread BSP Static Build Check 与 MemBrowse Memory Report 都跟着变红。

根因不在适配代码本身，而在构建顺序。ESP-IDF 包在 components/rtthread/scons/ 下放了一个 FreeRTOS.h 的 scons shim，用 #include_next 转发到 <freertos/FreeRTOS.h>，要求 RT-Thread 的 FreeRTOS-Wrapper include 目录排在 shim 之后、ESP-IDF 自带 FreeRTOS V11 内核头之前。但两个包的 SConscript 加载顺序由目录遍历顺序决定，并不稳定；一旦 ESP-IDF 先加载，#include_next 就解析到 V11 的头，Wrapper 提供的 configNUMBER_OF_CORES、configMINIMAL_STACK_SIZE、configUSE_PREEMPTION 等默认值全部落空，编译 drv_uart.c 时直接 #error。

修复提案只动 3 个文件，把 FreeRTOS include 目录顺序固定下来。这条值得记一笔的原因不是缺陷本身，而是反馈链条：上期以「构建通过」为放行条件的合入，在本期被 CI 抓到了顺序依赖，修复提案当天就开出来了。

2.4 既有缺陷提案的状态盘点：NVMe 泄漏、9PFS 长度、tmpfs UAF、dlmodule 全局量、FDT 深度均待合并（10-25）

日期：2026-10-25（核查时间）　来源：PR #11920、PR #11918、PR #11910、PR #11915、PR #11901

上期收录的几笔修复在窗口内都有更新，但都没有合入，状态停在「提案已开、等待评审」：NVMe 每遇一个非活动命名空间漏分配（#11920，10-25 00:35 更新）、9PFS 把服务端长度字段收敛到实际接收字节（#11918，10-24 17:19 更新）、tmpfs 截断到零长度时的释放后使用（#11910，10-23 23:31 更新）、可加载模块未初始化全局量（#11915，10-24 17:27 更新）。

窗口内补进来的两笔是新的：一是 FDT 解平铺的深度限制（#11901，10-25 15:49 更新），fdt_unflatten_single() 用固定 64 项的栈 np_stack 暂存遍历路径，压栈前不查深度，深度超过 64 层的 DTB 会栈越界写，作者在 qemu-virt64-aarch64 上复现，修法是在解平铺前用一条独立的手工栈遍历算出最大深度、超过 63 层直接拒绝；二是串口 rx_indicate 被误清（#11931，10-26 01:34 更新），echo xxx /dev/uart0 之后控制台不再响应，作者排除了「open_flag 被覆盖」这条旧解释——现在 rt_device_open() 在 OFLAG_MASK 匹配时根本不调驱动的 open——把真因定在 serial_fops_close() 无条件清 rx_indicate，而设备仍被控制台持有（ref_count 只从 3 降到 2）。

同一批里还有两笔驱动层的正确性修补：#11891 改 TIOCGWINSZ 不再借 finsh_getchar() 读终端应答（原来会消耗输入、且只在 tshell 线程可用），并在 termios 未变化时跳过 UART 重配以免复位 FIFO；#11885 修 utimensat() 对 UTIME_OMIT 的判断取反，此前请求「不改 mtime」反而会覆盖 mtime 并忽略调用方给的时间戳。

3.2 GDR：把 RT-Thread 内核对象查看搬进 GDB，QEMU 闭环覆盖 3.1.x／4.0.x／4.1.x（10-25）

日期：2026-10-25（发布）　来源：电子工程专辑：从 LoRaWAN 移植踩坑出发、GDR 仓库

这是一篇少见地把「调试脚手架」当正式工程来做的社区长文。起点是两年前把 Semtech 的 LoRaWAN 协议栈 SWL2001 从 Zephyr 移植到一颗资源受限的国产单片机上，底层是裁剪过的 RT-Thread Nano；四十多个 HAL 接口逐个映射，任何语义偏差都只在运行期暴露。真正的难点在观测：FinSH 一跑，radio planner 的时序就被扰动，观测行为改变了被观测系统；GDB 原生只给指针，看一个信号量要沿 rt_object_container 走链表、做 container_of 换算再 cast，十个对象就是五六十条命令。

GDR 的做法是把这类机械劳动固化成 GDB 的 Python 命令，提供三层能力：聚合命令（rtthread threads／timers／system／semaphores／objects）输出全局快照，线程表里带 StkUsed 与 MaxStkUsed 两个基于栈填充模式的峰值水位；便捷函数 $gdr_thread("worker2") 与 $gdr_object(...) 返回原生 gdb.Value，后续字段钻取仍用 GDB 表达式；pretty-printer 把内核对象折叠成一行摘要，例如互斥量直接显示持有者。

与 FinSH 的本质区别是完全无侵入：所有信息只通过 GDB 读符号与目标内存，不调用固件里的任何函数，因此既适用于根本没有 shell 的 Nano 场景，也适用于 HardFault 之后已经无法执行代码的死后分析。工程上几个决定值得记：不再自动探测 RTOS（改为显式 gdr init rtthread 4.0.5，但用符号存在性探测 SMP、堆管理器、IPC 组件这些配置差异）；所有布局知识集中在一个文件里并标注 COUPLED；用 QEMU 启动真实固件做 pytest 断言，CI 矩阵覆盖 Cortex-A9（3.1.0 至 3.1.5、4.x）与 RV64（4.0.4 至 4.1.1）。作者也写明了边界：本人已不做单片机开发，工具只在 QEMU 矩阵里验证过，尚未经真实板卡检验；后续计划是 agent skill、VSCode 插件与 FreeRTOS 适配。

4.1 TriCore（AURIX）进 Env SDK：tricore-gcc 13.4.1 与 qemu-tricore 两个包合入，覆盖 TC2xx／TC3xx／TC4xx（10-26）

日期：2026-10-26 00:10 与 07:57（合入时间）　来源：RT-Thread/sdk PR #9、RT-Thread/sdk PR #10、toolchains-ci v1.12、toolchains-ci v1.13

本期最实质的一笔不在主仓库，而在 Env 的 SDK 仓库：两个 PR 先后合入，把 Infineon TriCore（AURIX）这条车规架构的编译与仿真通路补进了 RT-Thread 的工具链体系。

第一笔是 tricore-gcc 工具链包，4 个文件 +112，Linux 与 Windows 各一套 Kconfig 与 package.json，包名 tricore-gcc、版本 v13.4.1、开关 PKG_USING_TRICORE_GCC。工具链上游是 NoMore201/tricore-gcc-toolchain（EEESlab 11.3.0 的下游，带 CI 自动构建），组成是 GCC 13.4.1、binutils 2.40、newlib、GDB 14.0，目标三元组 tricore-elf，覆盖 TriCore 1.3／1.3.1／1.6／1.6.1／1.6.2／1.8，对应 TC2xx、TC3xx、TC4xx 三代芯片。发布物放在 toolchains-ci 的 v1.12：Linux 包 251 MB，Windows 包 466 MB。Windows 包补了上游漏带的 libwinpthread-1.dll（同时放在 bin/ 与 libexec/gcc/tricore-elf/13.4.1/），否则在未装 MSYS2 的机器上编译器起不来。

第二笔是 qemu-tricore 模拟器包，同样是 4 个文件 +112，开关 PKG_USING_QEMU_TRICORE，版本 v1.0.0，发布物在 toolchains-ci 的 v1.13（Linux 5.4 MB、Windows 9.4 MB）。背景写得清楚：tricore-gcc 包自带的 QEMU 9.2.3 只有 KIT_AURIX_TC277_TRB（TC2xx）与 tricore_testboard 两台机器，仿真不了 TC3／TC4，所以单独引入 Zephyr 侧在用的一支。源码是 linumiz/qemu-tricore 的 release/ifx/tricore-1.0 分支（tag v1.0.0，QEMU 10.2.94），支持的三台机器是 KIT_AURIX_TC277_TRB、KIT_AURIX_TC397B_TRB、KIT_A3G_TC4D7_LITE，CPU 模型 tc2x／tc3x／tc4x。外设只做了 ASCLIN0 串口、STM 系统定时器、IR 中断路由、SCU 与时钟、SFR 桥、片上 RAM 与 Flash 映射，CAN、以太网、ADC、GPIO、DMA 都没有——够跑内核与串口 shell，不够做外设驱动验证。为支持 Windows 交叉编译，TriCore 侧还改了两处可移植性问题（ENOTBLK／O_* 条件编译与 hwaddr 日志格式）。

两点必须写清楚。其一，这只是工具链与仿真先行：主线的 libcpu 目录现有 19 个架构（aarch64、arc、arm、avr32、blackfin、c-sky、ia32、m16c、mips、nios、ppc、risc-v、rx、sim、sparc-v8、ti-dsp、unicore32、v850、xilinx），没有 tricore，bsp 下也没有 AURIX 板级目录；仓库里能查到的 TriCore 记录是 2020 年前后的几次尝试（#4311 架构适配、#4488 与 #4527 的 TASKING 工具链与 FinSH 支持），状态都是 Closed，没有并入主线。其二，两笔提案的 Windows 包都只做了 PE 导入表检查，未在 Windows 实机运行，作者自己在 PR 里建议合入前补跑一次编译。

把这两点合起来看，意义在于路线变化：早年的 TriCore 适配依赖 TASKING 商业工具链，门槛高且难以进社区；这次换成开源 GCC 13.4.1 加 QEMU 仿真，先解决「能编、能跑、能调」，至于 BSP 与驱动，是后面的事。对车规场景（域控、安全岛、AURIX TC3xx／TC4xx 是这块的主力）而言，这是必要但不充分的一步。

4.4 驱动与 CI：OSPI 八线 Flash、I2C 控制事务串行化、STM32 包测试并发锁（10-23／10-25）

日期：2026-10-23 至 2026-10-25（更新与合入时间）　来源：PR #11912、PR #11820、pkgs-test PR #37

驱动层最大的一笔是 OSPI 与 OctaFlash 支持（#11912），32 个文件。此前 RT-Thread 的 SPI 驱动层没有原生的 OSPI 通路，八线 Flash 只能绕。改动在 components 层补 OSPI 的总线、设备、配置与消息定义，以及传输辅助函数与构建选项，同时保留既有 SPI 与 QSPI 路径；把 OSPI 传输与探测接进 SFUD，支持读、写、擦除与状态／控制操作，并在 SFUD 设备表里加了 MX25LM51245G 用于验证；为了让整条路径能在硬件上跑通，还加了通用 STM32 OctoSPI 驱动与 stm32l4r9-st-eval 的板级 OSPI Flash 支持，使 SFUD 能以 1-1-1 与 8-8-8（OPI STR／DTR）两种模式访问。

I2C 那笔（#11820）修的是总线控制与传输的竞态：rt_i2c_control() 可能在 rt_i2c_transfer() 使用总线期间改控制器配置，尤其在 SET_MAX_HZ 上。改法是让控制命令取同一把总线互斥锁、走统一出口释放，并在 API 文档里写明控制需要线程上下文。验证用的是主机侧 pthread 互斥适配器，覆盖并发传输与控制、控制与控制、频率更新、锁与回调错误、以及控制里嵌套传输；未打补丁的源码在同一回归集里失败。

CI 侧的那笔在 pkgs-test（#37），1 个文件 +11/-7，解释得很完整：STM32 软件包测试并行跑多个版本，每个任务有独立 BSP 副本，但仍共用 bsp/stm32/libraries 下的 HAL／CMSIS 驱动目录；原来的 sem_stm32 只保护编译、不保护依赖更新，于是会出现一个任务在另一个任务克隆依赖未完成时对同一目录 git pull，Git 报未跟踪文件将被覆盖并中止，失败又被框架统一报成 compile failure。上一期合入的 #11870 测试即栽在这上面（失败日志可查）。修法是把锁上移到 __build()，让依赖更新与编译处在同一个临界区，同时删掉 __build_scons() 里的重复加锁避免自死锁，并用 try/finally 保证异常释放。

五、总结与趋势观察

5.1 本期趋势

  • 车规架构走「工具链先行」：TriCore／AURIX 这次进的是 Env SDK 而不是主仓库——开源 GCC 13.4.1 与 qemu-tricore 两个包先补齐编译与仿真，主线 libcpu 仍无 tricore 移植、bsp 下也无 AURIX 板级目录。对比 2020 年前后依赖 TASKING 商业工具链的那批尝试（均以 Closed 收场），这次的路径更可能落地，但距离「能上板」还差 BSP 与驱动。
  • 主线极静、提案面极活：72 小时 master 只有 2 笔提交，而窗口内 25 笔 PR 有更新、6 笔合入（主仓库 2、sdk 2、packages 1、pkgs-test 1）。合入动作集中在周五傍晚与周日晚间，评审没停，开发侧确实在收。
  • 缺陷研究从单点转向子系统：时间子系统一夜间四单（三缺陷加一份带 A 至 F 工作项的调研），两笔修复提案次日提交，形成「报—析—修」的短闭环；lwp 的 sys_poll 回绕则单列出 32 位 RT-Smart 在用户态可控计数上的整数边界问题，与上期那族「设备或服务端元数据当长度」的缺陷互补，说明内核仍在为历史包袱付账（ecf2d821 可追到 2022 年）。
