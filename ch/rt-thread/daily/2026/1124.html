二、内核与安全

2.1 电源管理注册先初始化再入链，分配移出临界区（11-23）

日期：2026-11-23 14:56（合入）。来源：#12075。

原来的 rt_pm_device_register() 先把节点挂进 _pm.device_list，再填 device 与 ops 两个字段。中间这段时间，链表里的节点带着未初始化的指针。

第二轮改动把 _pm.device_list 的增删都放进关中断区间，同时把 RT_KERNEL_MALLOC 与 RT_KERNEL_FREE 留在临界区之外。

这个取舍正是议题 #10075 的要害。报告者在 RISC-V 硬件上开了 RT_USING_SMP，调用注册接口时卡死在 RT_KERNEL_REALLOC 里，原因是分配动作被套进了临界区。

改动落在 pm.c 单文件，新增 39 行、删除 3 行。议题 #10075 随合入同日关闭。

判断：这是把锁范围画对，不是加一把更粗的锁。依据是修法同时做了两件事：入链前的初始化补齐，分配动作反而被挪出临界区。

2.2 DFS 打开失败改报正 errno，v2 不再回假成功（11-23）

日期：2026-11-23 10:53（合入）。来源：#12067。

两个版本的文件系统在打开失败时报的数不一样。描述符表满时，DFS v1 把 errno 置成 -ENOMEM；DFS v2 直接返回 0，调用方会把 0 当成一个有效的描述符。

提案把失败原因分开报：到描述符上限报 EMFILE，表扩容或文件对象分配失败报 ENOMEM。共享分配器在解锁之后再发布错误值。

POSIX open() 在分配失败时统一返回 -1，并把对应正值写进 errno。成功打开仍可返回描述符 0。

改动跨 6 个文件，新增 108 行、删除 71 行。其中 60 行是新增用例，覆盖文件不存在与表满两种情形。同时改了 A9 的 DFS 配置文件，让原生套件与 POSIX 套件真能跑起来。

验证环境是 qemu-vexpress-a9 配 QEMU 7.2.22。提案注明开发机是 Intel macOS，构建在 Linux 容器里做。

判断：这修的是返回值语义，不是单个调用点。依据是改动同时动了两版 dfs.c 与 dfs_posix.c，并补了回归用例。

三、驱动与框架

3.1 引脚中断兼容路径读写两端都要锁（11-23）

日期：2026-11-23 10:51（合入）。来源：#12040。

当 GPIO 控制器没有 pin_attach_irq 操作时，pin_api_attach_irq() 走兼容路径，把 hdr 与 args 分两次写进 legacy_isr。中断正好落在两次写之间，处理函数就会拿新句柄配旧参数。

提案把兼容路径上的写入与清除都放进 pin_irq_lock 保护。

维护者在 11 月 13 日给过一条 P2 意见，指出只锁写端不够。SMP 下关中断会调用 rt_cpus_lock()，只锁住本核；另一核的 GPIO 中断不持这把锁，仍可能读到半套参数。

改动落在 dev_pin_dm.c，新增 26 行、删除 12 行。从提出意见到合入隔了 10 天。

判断：这条意见把问题从「加锁」推到「谁来读」。依据是维护者点名的是读端 pin_pic_handle_isr()，不是写端。

3.2 串口 V1 换传输模式重开被拒（11-23）

日期：2026-11-23 09:54（合入）。来源：#12073。

rt_serial_open() 只在第一次打开时分配收发缓冲。重开时它只更新 open_flag，不动已分配的结构。

于是先按 INT_TX 打开、再按 DMA_TX 重开，缓冲区还是那个 4 字节的 rt_serial_tx_fifo。而 DMA 发送路径按 struct rt_serial_tx_dma 去访问它，越界读到 data_queue。

修法是拒绝这种换模式重开。改动落在 dev_serial.c，新增 18 行、删除 12 行。议题 #12072 同日关闭。

判断：这是把不成立的调用组合挡在门口，不是补齐缓冲重分配。依据是提案标题就写着 reject，正文也没做二次分配。

四、工具链与文档

4.1 klibc 用例越界拷贝，RH850 上打坏栈（11-23）

日期：2026-11-23 09:51（合入）。来源：#12065。

TC_rt_memmove_too_long 原先把 11 字节从 6 字节的源拷进 10 字节的缓冲。用例本身就越界，在 RH850 上用 -O2 编译时把栈打坏了。

改法是把两端缓冲都做成 11 字节，并在 NUL 之后补一次校验，让提前停止的拷贝也能被测出来。

改动落在 src/klibc/utest/TC_rt_memmove.c，新增 8 行、删除 5 行。提交者署名 Parthiban Nallathambi，来自 Linumiz。

判断：这是测试用例的缺陷，不是被测函数的缺陷。依据是改动只碰 utest 目录下的用例文件，没动 memmove 实现。

4.2 树莓派 Pico 文档补工具链路径（11-23）

日期：2026-11-23 09:55（合入）。来源：#12069。

bsp/raspberry-pico/RP2040 的 README 补了 12 行，写明 GNU Arm 工具链的安装路径怎么配。

改动只有文档，没有代码。提交者署名 Daiyuanranfeng，署名邮箱域为 openatom.club。

判断：这条与上一期那笔 macOS QEMU 文档修复属同一类。依据是两笔都只改 README，都在补快速上手会卡住的路径问题。

六、生态与厂商适配

6.1 全志 V861 评审落到构建可复现性：干净检出缺 DTB（11-23）

日期：2026-11-23 09:46 与 14:08（评审与答复）。来源：#12077 评审。

维护者 Rbb666 在 builtin_fdt.S 上留了行内意见。第一句是干净检出里没有 board/board.dtb，SCons 也没有调用生成脚本。第二句是照 README 直接跑 scons，会在这里报找不到文件。

意见要求把 DTB 的生成与依赖接进构建，再从干净目录完整跑一遍。

作者 14 点 08 分回复「ok没问题」。五笔 V861 提案截至目前仍未合入。

判断：评审的落点已经从功能面转到构建可复现。依据是这一轮意见完全不谈驱动逻辑，只谈干净检出能不能编过。

6.2 ivshmem 校验提案由作者关闭，说明被 #11993 覆盖（11-23）

日期：2026-11-23 16:31（关闭）。来源：#12056。

提案 11 月 14 日提出，给从 PCI 配置空间读到的共享内存地址与长度加非零、不溢出与体系结构适配性校验。

作者 16 点 31 分自己关掉了它。理由是 master 已合入 #11993（43791bbf）。那笔改动让 BAR 走可信窗口校验，JailHouse 路径在 ivshmem_shmem_from_config 里先检查配置读失败，再做范围校验。

原话是「本 PR 校验意图已被覆盖，关闭以免重复」，分支停在 990ebe7f。

判断：这是重复提案的自清，不是被否。依据是关闭由作者发起，且指认了覆盖它的那笔已合入改动。

6.3 rt-carplay 补 Classic CarPlay 元数据与关键帧恢复（11-23）

日期：2026-11-23 09:31 至 14:18（推送）。来源：rt-carplay。

这个仓库上一期已收录，今天继续推进。三笔提交分别做有线与隧道 iAP2 上的 Now Playing 封面组装、事件通道上的 Classic Screen 关键帧恢复、以及 SDK 集成文档与接口约定整理。

仓库是 CarPlay 接收端 SDK，用 C 写，GPL-3.0，把协议核心与可移植运行时做成不依赖 RT-Thread 头文件的部分，再给 RT-Thread 与嵌入式 Linux 两个宿主端口。

判断：这是社区项目把 RT-Thread 当目标运行时，不是官方动作。依据是仓库不在 RT-Thread 组织下，README 只写宿主端口。
