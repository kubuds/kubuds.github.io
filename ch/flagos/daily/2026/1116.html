今日重点：Torch-FL 把 FlagGems 的 Python 提交路径编译成原生 host，Qwen3-0.6B 热启动开销降到厂商 PyTorch 的 1.17 倍（11-14~11-16）

日期：2026-11-14 ~ 2026-11-16　来源：Torch-FL #824 · Torch-FL #839 · Torch-FL #822（需求单） · Project 14

  • 结果：#824 把 FlagGems 的 Python 侧 host 逻辑——元数据、内存分配、启发式与 Triton 发射准备——编译成带守卫的原生 host 程序，同时保留原有的设备内核。完整 Qwen3-0.6B 推理下，prefill/decode 的热启动 CPU 提交耗时从 211.51/203.92 毫秒降到 28.46/27.15 毫秒；厂商 PyTorch 为 24.43/22.96 毫秒，折算延迟比为 1.17 与 1.18。
  • 验收门槛：#822 要求国产加速器上与厂商 PyTorch 同物理卡、同工作量对比，达到吞吐比不低于 0.80 或延迟比不高于 1.25。英伟达侧已进门槛，国产卡侧尚无公开数据；#824 自述为实验性英伟达推理实现，不是默认模式切换，也不构成全算子覆盖的声明。
  • 连续性：11-15 至 11-16 凌晨连合六笔——#826 编译 FlagGems 源码与模型 host，#835 让原生 host 注册表全量入账，#836 生成带 schema 类型的 eager 条目，#837 生成源码调用桥接，#838 保留标量语义，#839 降低共享 host 开销（+2388/-55，15 文件）。这条线按「单模型跑通、注册表补齐、开销下压」的顺序推进，不是零散的性能补丁。
  • 设计取向：#823 的设计稿在实现之前定下路线，结论是决定上限的是内存分配而不是内核发射，因此第一阶段直接从分配器取内存；#824 与 #826 合入后计划获维护者批准，#829 与 #830 承接后续。
  • 含义：FlagGems 的 eager 路径一直带着一层「Python 税」——每次调用都要在 Python 里做元数据、分配与发射准备。把这层编译掉之后，跨芯推理的差距从「内核写得好不好」扩到「host 路径怎么组织」，2.3 的推理性能验收口径需要同时写明 host 侧基线。

四、总结与趋势观察

  • 2.3 走到 rc 前夜：11-13 的 FEP 合入截止已经过去，下一道门是 11-30 的特性冻结与 rc0。窗口内 build-infra 把 910C、ROCm 7.2.4、PPU 2.1.0、MUSA 5.3.0 四个后端的 2.3.0 版本数据补齐，收口单位仍是「一个后端一个 PR」。
  • 性能叙事从「算子数量」转向「host 路径」：Torch-FL 把 FlagGems 的 Python 提交开销压到厂商 PyTorch 的 1.17 至 1.18 倍，进了 #822 的 80% 门槛。若国产卡侧复现，跨芯推理的对比要同时给出 host 基线，否则数字不可比。
  • 融合算子是推理侧的主战场：海光 MegaMoE、英伟达 MegaPreAttention、昇腾 A5 的 KDA 与因果卷积，都是把通信、投影、归一化与 KV 更新绑进一次持久内核。这类工作改变的是多卡可用性，而不是单点算力。
  • 测试与 CI 的权重上升：FlagGems 62 笔对齐、82 个平台 pytest 包（#9118）、FlagGems-vllm 的 CI 自包含（#1202）、gendoc 五笔加固，都指向同一件事——2.3 的瓶颈正从「写代码」转到「验收与可追溯」。
  • 周末不是停工：11-13 一天 180 笔合入、125 笔提交，11-14 与 11-15 分别 15 与 27 笔合入。工作日攒下的评审在周末被清完，真正的新开发仍集中在 11-13 白天。
  • 新闻面与代码面继续背离：gnews 组件查询连续零命中，本期唯一有信息量的外部报道是地平线旭日芯片的具身工具适配与燧原的人事变动，均属背景。日报的判据仍以提交、PR 与打包矩阵的一手数据为准。
