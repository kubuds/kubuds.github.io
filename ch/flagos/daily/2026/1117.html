日期：2026-11-16　来源：build-infra #1831 · build-infra #1832 · build-infra #1833 · build-infra #1834

  • 落账：build-infra 当日 13 笔合入全部围绕同一条线——四笔 bot 生成的文档记录（#1824 与 #1835 更新 runtime、#1833 更新 base、#1834 补 hygon-dtk26.10 的 changelog 日期），把 2.3.0 标签写进各厂商基础镜像与运行时镜像的说明页。海光侧可直接查到 flagos-base-hygon-dtk26.10:2.3.0 与 flagos-runtime-hygon-dtk26.10:2.3.0 两个标签，镜像内固定 flagtree==0.7.1a1+hcu3.6、flag_gems==5.4.0、flagcx==0.14.1+dtk2610、torch==2.13.0+dtk2610，Triton 3.7.0 作为可选切换项保留。
  • 配对原因：#1831 的说明把根因写得很具体——hygon 26.10 的 clang-18 由裸 dtk_llvm.run 换成 dtk_llvm-1.0.0+dtk2604.2609221416.g5f9d5e，而 llvm.amdgcn.make.buffer.rsrc 的 numRecords 参数在旧包是 i32、在新包是 i64；FlagTree 0.7.0 之前发 i32、0.7.1a1 起发 i64。两者错配时每次 kernel 编译都报 Intrinsic has incorrect argument type，也就是 26.10 线此前在 F 路径上的失败。这一笔把 aillvm 与 FlagTree 锁定为同一对版本，并在 hygon25 上用本地构建的 cp312 wheel 验证 add 与 reduction 内核在 FlagTree 路径上数值与 torch 一致。
  • 入册：#1832 补上 flagtree-0.7.1a1+hcu3.6-cp312-cp312-linux_x86_64.whl 在 flagos-pypi-hygon 的索引记录——该索引此前只有 0.7.0 的 cp310 记录，而 26.10 运行时已改钉 0.7.1a1，目录里缺的正是这条线要装的 wheel。
  • 排期口径：按社区 2.3 时间表，FEP 合入截止 11-13、特性冻结并拉 rc0 为 11-30、rc1 为 12-07、rc2 为 12-14、封板 12-25、GA 12-30。今日写入的 2.3.0 标签属预发布线，不等于正式发版；日报后续按「镜像先落、发版后到」两层记录。
  • 含义：跨芯栈真正的脆弱点常常不在算子语义，而在编译器与驱动包的二进制约定——一个 intrinsic 的参数宽度变化就能让整条厂商线编译不过。把这类配对写进 build-infra 的契约检查（check_flagtree_contract.py --rows hcu-dtk2610 报无漂移），才算把「同一份代码跑在多种芯片」的前提固定下来。

1.4 FlagGems：exponential_ 重放随机流与 clone 的 FakeTensor 崩溃同日修掉（11-16）

日期：2026-11-16　来源：FlagGems #8141 · FlagGems #8893 · FlagGems #9266

  • 随机流重放：#8141 指出 vLLM 用 argmax(probs / q)、q ~ Exp(1) 的指数竞速形式采样，因此 exponential_ 必须返回独立同分布抽样并在调用间推进发生器。f32 的 unroll8 内核每个输出元素取一个 philox 计数器，包装层却只把发生器推进 N/8，于是每次调用重放上一次的 7/8 随机流——2 的 20 次方规模抽样里 q2[:-N/8] 与 q1[N/8:] 在 917504 个元素上完全重合。修法是按实际启动的程序（含尾部被掩码但仍在抽样的 lane）预约计数器。
  • 对数快速路径失真：safe_fast_log_f32 把 ln(u) 拆成 exponent*ln2 + p(mantissa)，当 u 略小于 1 时两项都约 0.69 相互抵消，多项式约 1e-5 的绝对误差直接留在结果里，造成左尾分布失真。同一笔一并修掉。
  • compile 下的崩溃：#8893 处理 x.clone() 在开启 FlagGems 后于 torch.compile 中报 “Cannot access data pointer of Tensor (e.g. FakeTensor…)” 的问题——aten::clone 是复合算子，其 Meta 实现走默认后端内核，形状传播因此落进 flag_gems/ops/clone.py 并对 FakeTensor 调 data_ptr()。修法是识别 is_meta 或 fake_mode 输入后直接解析输出布局、不启动 kernel；新增 3 种内存格式乘转置/常规的用例，test_clone.py 64 项通过。AMD 的 vllm-plugin-FL 适配正是钉在这一笔上。
  • 基准缺陷：#9266 修 router_gemm 基准里后端派发写死的问题，使基准按当前后端取内核。

  • 后端清单：#1662 在 readme 补入 Intellifusion（云天励飞）后端并更新 TLE 支持清单（-922 行属文档重排）。

  • 正确性：本期两笔修复值得单独记住——exponential_ 的随机流重放（每次调用重复 7/8 随机数，直接影响 vLLM 采样的独立性）与 FlagTree AMD 原子序屏障（16 warp 时 300/300 读到陈旧数据）。它们都不是性能问题，而是会静默改变结果的问题。
