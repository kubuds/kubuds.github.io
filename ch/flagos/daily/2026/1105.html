3.2 地平线：BPU 算子库修到可用，链式执行把四次派发压到 0.673 毫秒（11-04）

日期：2026-11-04　来源：Torch-FL PR #721 · Torch-FL PR #726

  • 三处硬故障：#721 查清 BPU 的 eager 路径其实每个算子都在 CPU 上跑——算子桶阶梯从不超过 512 lane、双输入 artifact 用单张量描述符提交导致静默错值、hbdk4 在 box64 下无法导入 numpy 导致 x86 工具链不可用。修复后把 Run 通过 C ABI 暴露，让 eager 路径绕开 aten dispatcher，并把每次调用的固定工作移出热路径。
  • 实测数据：RDK S600 上 262144 lane 的 relu 从 0.176 毫秒降到 0.073 毫秒，一个 conv block 从 23.2 毫秒降到 11.1 毫秒。
  • 链式执行：#726 新增 DeviceChain，在设备上连续跑多个 BPU artifact，中间激活不回主机、只首入末出过内存，用一小圈设备缓冲传递。S600 上序列化的 elementwise 从 0.417 毫秒降到 0.104 毫秒，四次独立派发从 1.667 毫秒降到 0.673 毫秒。
  • 判断：地平线这条线的瓶颈不是算力而是固定开销。驱动每次调用 0.09 毫秒，对单算子不算什么，对一层几十个算子的模型就是主要成本；把中间激活留在设备上，等于把这笔开销从「每算子一次」压成「每段一次」。

  • 一句话：这一天的重心从「补算子」转向「补能力边界」——Torch-FL 把统一设备层推到 Apple Silicon 与寒武纪 MLU 两端，FlagTree 把 TLE 改造成可按后端单独开关的增强集，build-infra 把 vLLM 0.28.0 repack 一次铺到 11 家索引。
  • 观察一：AI agent 已是主要提交者。Torch-FL 当日 29 笔合入的 PR 正文都带「Agent/Tool、Model、Human Reviewer」段，工具写的是 DSH（DeepSeek Harness）与 Claude Code CLI，模型写的是 deepseek-v4.1-flash 与 Claude Opus 5.5，人工评审统一为同一位维护者。这不改变代码质量的判断标准，但把瓶颈从「写」移到了「评」——288 笔在审、151 笔新开就是这条瓶颈的量化。
  • 观察二：镜像先行是计划内节奏，不是脱节。23 个 base 与 23 个 runtime 镜像都已记上 2.3.0，而清单文件要到 11-30 特性冻结才生成。按 2.3 时间表（FEP 合入截止 11-13、rc0 11-30、rc1 12-07、rc2 12-14、封板 12-25、GA 12-30），镜像跑在清单前面属正常。真正值得盯的是 11-13 的 FEP 合入截止——那才是这一版范围的硬边界。
  • 观察三：后端接入的最后一公里是 runner。寒武纪 MLU 后端合入当天就把 CI lane 撤下；FlagTree 的 Iluvatar native 系列也大量附带复现用例而非 CI 门禁。多芯片栈的成本正在从「适配代码」转向「验证环境」，这与其说是缺陷，不如说是这个阶段的常态。
  • 待观：FlagTree 的 38 笔堆叠单能否在 11-13 前分批合入；FlagGems 的 41 笔 GCU300 覆盖单会不会重演「一天几十笔」的合入节奏；vLLM 0.32 线的多后端适配是否随 2.3.0 rc0 一并收口。
