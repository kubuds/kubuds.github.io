日期：2026-11-02　来源：build-infra PR #1589 · build-infra PR #1608 · FlagGems-sglang PR #271 · FlagQuantum PR #1004 · FlagGems PR #8240（全量见附录）

日期：2026-11-02 ~ 2026-11-03　来源：FlagQuantum PR #1002 · FlagQuantum PR #1004 · FlagQuantum PR #1006 · FlagQuantum PR #1010 · FlagQuantum PR #1013 · FlagQuantum PR #1018 · FlagQuantum PR #1021

  • 算术线（AO）：#1006 建立 AO-00 的算术基线与独立 oracle，并把「验证范围不得夸大」写成校验器规则；#1010 落地 AO-01，对纯表达式做带保护的公共子表达式消除与可靠的位事实归一化；#1013 落地 AO-02，补齐受保护的平方、常量与终端 XOR 实现。三笔按 AO-00 到 AO-02 的顺序递进，每一步都保留前一步的资源基线与验收证据。

1.5 FlagGems：昆仑芯 XPU3 修复静默错误形状，十四笔性能与契约收口（11-02）

日期：2026-11-02　来源：FlagGems PR #8038 · FlagGems PR #8034 · FlagGems PR #7976 · FlagGems PR #8123 · FlagGems PR #8245 · FlagGems PR #8049

  • 正确性修复：#8038 是当日最值得读的一笔。foreach 系列的 out-of-place 标量重载在「同 dtype、同设备、同元素数」时走快路径，输出统一按第一个张量的形状分配再切视图，而快路径的准入条件比较的是元素数而非形状——于是形状不同但元素数相同的列表会全部继承首个张量的形状，产生静默错误结果。修复把准入改为按完整形状判定，另两笔把十六个标量输出改为单基址寻址、把列表输出合并为一块平坦缓冲。
  • 契约修复：#7976 把 foreach 点号取槽位的索引改为取自 program_id(0)；#8034 在提交 JIT 之前先求值自动调优的网格，避免以未求值的网格启动；#7956 解包标量解析的三元返回值，修正快步路径的取值。
  • 性能收口：#8056 为 triu_、resolve_neg、le 与位右移补快路径；#8245 为 flip、ge、lerp 补点态快路径并撤掉上一版 BF16 一维 tile 重构；#8108 融合 pool3d 反向的精确路径、对小乘法跳过点态管线；#8107 在每通道度数一致时展开 Chebyshev 的 t/w；#8030 加速 choose_qparams_optimized、kl_div 与两个 Bessel 核；#8111 把 Jacobi 扫描分块，使 nuclear_norm 只需 nb 次启动而非 k 次；#8049 为 linspace 做单公式快路径；#8248 另有一组算子特化性能修正。
  • 回滚信号：#8123 撤回「昆仑芯 BF16 点态性能优化」，理由是引入回归；同日 #8245 以不同方案重做并明确「撤掉 #8052 的 BF16 一维 tile 重构」。一撤一补同窗口发生，说明 XPU3 侧的点态优化仍在试验期，合并前缺少足够的形状覆盖。
  • 判断：昆仑芯这一组的关键词是「契约」——形状、槽位、网格、返回值四个层面的隐式约定各修一处。这类问题的共同后果是静默错误而非崩溃，比性能回退更值得在日报里留痕。

3.1 达摩院玄铁：专用算子、MM 成本模型、chunk_kda 三线同日推进（11-02）

3.2 昆仑芯：XPU3 foreach 契约修复与十四笔性能收口（11-02）

日期：2026-11-02　来源：FlagGems PR #8038 · FlagGems PR #8034 · FlagGems PR #8123 · FlagGems PR #8245

  • 静默错误：#8038 指出 foreach 的快路径只比较元素数、不比较形状，形状不同而元素数相同的张量列表会全部继承首个张量的形状，输出既不报错也不越界。修复按完整形状判定准入，并把十六个标量输出改为单基址寻址、列表输出合并为平坦缓冲。
  • 网格与槽位：#8034 在提交 JIT 前先求值自动调优网格；#7976 改从 program_id(0) 取 foreach 的槽位索引；#7956 修标量解析三元返回值的解包。
  • 性能补丁：#8056、#8245、#8108、#8107、#8030、#8105、#8111、#8049、#8248 共九笔，覆盖点态快路径、pool3d 反向融合、Chebyshev 展开、Jacobi 分块与 linspace 单公式。
  • 回滚：#8123 撤回 BF16 点态优化，理由为回归；#8245 以另一方案重做并撤掉 #8052 的一维 tile 重构。一撤一补说明该路径仍在试错。
  • 判断：昆仑芯当日的价值不在性能数字，而在修掉了一个会静默算错的形状契约。对多后端算子库而言，这类缺陷比慢十倍更危险——它不会被基准发现，只会被下游模型以「精度异常」的形式撞上。

3.3 昇腾与海光：W8A8 INT8 的 GEMM 与 BMM 两条实现（11-02）

日期：2026-11-02　来源：FlagGems PR #6060 · FlagGems PR #7741 · FlagGems PR #7774 · FlagGems PR #7760

  • 昇腾 GEMM：#6060 为 mm_w8a8_int8 与 mm_w8a8_int8_out 增加昇腾后端，走公开入口分派。算子接预量化 INT8 的 A 与 B、FP32 的标量或逐行逐列 scale、可选 bias，整数乘加后应用两侧 scale 与 bias，输出 BF16、FP16 或 FP32；小 M 窄 N 走向量乘加核，每段 FP32 归约不超过 1024 个 INT8 乘积以保证整数部分精确。不支持非对称零点。
  • 海光 BMM：#7741 为海光补通道级 bmm_w8a8，复用既有 scaled-MM 核与 tile 选择，把 INT8 矩阵乘、FP32 通道缩放与输出转换融合在一个核内。
  • 精度修：#7774 在昇腾侧先提升两个操作数再做 CANN libdevice 的 pow，避免混合精度下的下溢与精度损失。
  • Hopper 性能：#7760 用 TMA 流水线优化 FP8 W8A8 的 BMM，属 NVIDIA 侧的对应优化。
  • 判断：两家在同一个窗口各补一条 W8A8 路径——昇腾选 GEMM 的完整语义（含逐行逐列 scale、三种输出 dtype），海光选 BMM 的通道级缩放复用。差别在语义覆盖广度与实现复用的取舍，也反映各自下游模型对量化形态的不同需求。

3.4 摩尔线程：Conv1D 真一维 GEMM 把 26 个基准例全部拉过 0.8 倍线（11-02）

日期：2026-11-02　来源：FlagGems PR #6754 · FlagGems PR #7428 · FlagGems PR #6903 · FlagBLAS PR #157 · FlagTree PR #1314

  • Conv1D 结果：#6754 为 MTT S5000 增加 conv1d 后端覆盖，把官方 conv1d_padding 基准从 18/26 例达标提到 26/26 例不低于 0.80 倍 torch；此前所有 FP32 K3/K5 padding 例只有 0.41 至 0.53 倍。
  • 三层改法：其一，conv1d 原先无 MTHREADS 覆盖、全部走通用 conv2d，小分组形状会实体化 padding、W=1 形状只命中单条有效 OW 通道；改路由后去掉冗余 padding 与 bias 分配并修退化宽度分派。其二，新增专用 Triton-MUSA Conv1D 核，按 M 等于 N 乘 Lout 做三维网格切分，输出通道不再做除法取模。其三，权重预打包为按核宽、输入通道、输出通道排列，配合带精度补偿的 SQMMA。
  • 配套：#7428 优化 S5000 上 one_hot 的校验与推理；#6903 把空索引视为 index_add 的空操作；#157 补 MUSA 的 L1 BLAS；#1314 在两次异步 TME 拷贝间跳过 membar。
  • 判断：这是本窗口少见的「把基准全部拉过线」的完整案例——路由、专用核、权重布局、指令级精度补偿四层同时改，且给出前后对照。对其他后端是一个可复制的模板。

  • AMD 线在一个窗口内补齐三层：构建侧新增 FlagTree 的 amd 打包线并以 A/B 对账证明等价（maxdiff 1.526e-05，9/9）；运行时侧把 rocm7.2.4 的 torch 闭包对齐到 vLLM 0.32 的钉固组合；算子侧为 gfx1100 补 LoRA 与注意力共十个算子。三者合起来，AMD 从「有后端」变成「有可追溯的构建、可复现的运行时、可调优的算子」。
  • 量子栈进入「按验收单元交付」阶段：单日 21 笔合入分布在 UP（语义）、AO（算术）、PF（性能）三条线，每条都有独立基线、oracle 与失败即红的证据。这种拆法让量子编译器的每次改动都能被既有账目测出代价，比追求单点加速比更能支撑长期演进。
  • 玄铁把专用算子做成了批次：13 个专用算子 43 分钟内合入，平均 3.3 分钟一笔，集中在特殊函数、三维卷积、量化 LSTM 与池化反向等长尾条目。这说明 KernelGen 的玄铁产线已具备批量供给能力，评审也能按后端并行消化。
  • 评审吞吐是当前真正的瓶颈：本窗口合入 162 笔、新开 192 笔，在审总量 311 笔，其中 FlagGems 一仓 210 笔（新开 148）。合入量较上一 24 小时窗口下降 11.5%，新开量却上升 128.6%——产线开足、评审吃紧的结构没有改变。
  • 2.3.0 仍停在镜像先行：base 层与寒武纪、沐曦、海光、AMD 四层都已在 2.3.0 名下回填 changelog 日期，运行时镜像也按后端推送，但 community 的 release/2.3 清单仍为 404、GitHub Release 零新增。与上一期相比没有实质推进，若本工作周仍不冻结清单，发布窗口会被下一版规划挤压。
  • 新闻侧连续第二个平静窗口：24 组中英文查询零组件级命中，CSDN 专栏最新文仍为 10-29，HN 零直命中。生态背景两条（乌镇开源展馆、九源联合体三项联合发布）均明确标注为周边事件，未计入项目进展。
