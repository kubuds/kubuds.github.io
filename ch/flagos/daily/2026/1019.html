1.2 新仓 FlagCV：对齐 OpenCV 接口的多后端图像算子库骨架合入（10-18 ~ 10-19）

日期：2026-10-18 ~ 2026-10-19　来源：FlagCV · PR #1 · 提交记录

  • 事实：10-14 建仓的 FlagCV 在 10-18 23:14 落下首笔提交「Add project skeleton and bitwise_and operator」，10-19 01:24 追加「Restructure as an immediate-mode skeleton without operators」，10-19 01:38 合入 PR #1（作者 zhangjieBaai）。PR 说明写明三点设计取向：接口对齐 OpenCV（include/flagcv/ 下 core / imgproc / gpumat / handle / types 五个头文件，对应 opencv2 的 core 与 imgproc）、多后端结构沿用 FlagDNN、内核用 Triton 编写；本 PR 只落骨架、不含算子。
  • 结构：仓库 81 个路径中，backends/ 已一次铺开 nvidia / thead / ascend / hygon / iluvatar / mthreads 六个后端（各含 CMakeLists、backend.cpp、compiler.py 与 kernels/registry.json）；src/ 分 core、imgproc、image、lowering、runtime 五块；compiler/flagcv_codegen 为代码生成入口；docs/ 已有 architecture、numerical-tolerance、operator-development 三篇。
  • 判断：这是 FlagOS 算子版图第一次从「大模型 / 科学计算」伸向图像处理——过去 FlagCV 类的缺口由 FlagDNN（深度学习算子）与各厂商自家 CV 库分担，现在以 OpenCV 兼容接口单独立仓。六后端目录一次铺开而非逐个加，说明团队打算用既有 FlagDNN 的多后端范式直接复用；numerical-tolerance 文档先于算子出现，也符合 FlagOS 在 KernelGen 线「先立验收口径、再批量落算子」的既有节奏。风险是图像处理算子（插值、色彩空间、形态学）与 Triton 的表达能力匹配度尚未验证，且仓库尚无可运行算子，短期内不宜对其覆盖度下结论。

1.3 build-infra：FlagCX 六后端 22.04 自包含 builder 收口；FlagTree 逐后端 builder 与每日轮子矩阵成型（10-16 ~ 10-18）

日期：2026-10-16 ~ 2026-10-18　来源：build-infra #1369 · #1371 · #1372 · #1380 · #1389 · #1394 · #1398 · #1399 · #1403 · #1404 · #1407

  • FlagCX 线：24 小时内为六个后端各落一枚「22.04 自包含 builder」——nvidia（#1372）、hygon（#1380）、cambricon 4.7.2（#1389，配套补 pandas 依赖 #1391）、metax（#1394）、enflame（#1398）、iluvatar（#1403）；每枚 builder 都以 ubuntu:22.04 为 glibc 底线、把厂商 SDK 预置进镜像，再在其上出 wheel，并在 wheel-info 留痕（#1375 / #1395 / #1400）。#1407 追加 dispatch 级 --no-bitcode 开关：v0.14.0 标签早于 FlagCX #668 的 bindings/ir Makefile，重发 iluvatar 的 0.14.0+corex4.4.0 / corex4.5.0 两个 pin 时不再产出设备 bitcode，避免 setup.py 在非 nvidia adaptor 上直接抛错。
  • FlagTree 线：builder 从「两条工作流做一件事」合并为一个矩阵，backends.yaml 一行携带 Containerfile、镜像仓、runner 标签、磁盘预算与验收断言（#1369）；每日轮子同样改为逐后端一行、由 plan 逐行算版本与文件名（#1371），metax 进每日线（#1377）、iluvatar 进目标与每日行（#1390 / #1393）、sunrise 把 builder 与 wheel 收进单文件并启用每日行（#1399 / #1402）、ascend 一对后端改为两阶段 builder（#1404 / #1405，构建环境即交付环境，读 CANN 并据此 pin AscendNPU-IR）。#1397 明确把 FlagCX 从 iluvatar 的 FlagTree wheel 里剔除，划清两条产物的边界。
  • 打包线：wheel 上传从 runner 本机 python 改为在 uploader 镜像内执行（#1381 / #1382 / #1388）；发布类工作流接受 pull/<N> 作为 ref（#1347），使 PR 分支可先跑一遍发布链路；FlagGems-sglang 进入 noarch deb/rpm 与 flaglibs wheel 两条线（#1387）；bundle 深度冒烟改为真机 device + 编译器 JIT/执行（#1365），并在 bundle 的 glibc 底线（22.04）上跑验证（#1376）。
  • 判断：这一批不是零散修补，而是把「N 个后端 × M 类产物」压成「一张矩阵 + 一份 backends.yaml」——新增后端从「再写一条工作流」变成「加一行」。统一 22.04 是同一逻辑的另一面：只有把构建环境与交付环境的 glibc 底线钉死，跨发行版的 wheel 才谈得上「一份产物多处可装」。这正对应主论坛所说的「35 款芯片」——芯片数要靠可复现的交付面撑住，否则规模只是名单。

1.5 FlagTree：SpaceMiT RISC-V 后端新增 smt_rvisa 裸核 eDSL，退役私有 TLE 方言（10-16）

日期：2026-10-16　来源：FlagTree #1381 · #1394

  • 事实：#1381（作者 alex-spacemit）更新 SpaceMiT RISC-V（K3）后端，三件事一起做——新增 smt_rvisa，一个裸核（raw-kernel）eDSL，作者显式指定 SEW / VL / 分块 / 指令选择，而不是交给调度器决定；内核经 C++ builder API 下降（不生成 MLIR 文本），另有一条 LLVM 直出路径，用 MLIR Python bindings 直接产出 llvm.func 并整段跳过 spine-opt；后端不再保留私有 TLE 方言副本，改为消费通用 third_party/tle；同时修掉裸路径暴露的指针 / 内存空间下降缺陷。
  • 配套：#1394 更新昇腾 CI 的 py311 / py312 与 ascend3.5 工作流；在审 #1395（[SPEC][XPU] 复用 core analysis 并路由 TritonTypes.td）、#1396（Ascend3.5 py312 交付工作流）显示 XPU 与昇腾两条线的规格化仍在推进；#1387 把 tle.gpu.alloc 别名的测试在 enflame 上跳过。
  • 判断：RISC-V 后端过去在 FlagTree 里是「能编、能跑」，本期第一次出现面向向量单元的手写入口——SEW / VL 显式可控意味着可以把 RVV 的向量长度与分块策略写进内核，而不是依赖自动调度推断。退役私有 TLE 副本则是治理动作：多后端共用一个 TLE 方言，才不会出现「各后端一套语义」。对 RISC-V AI 芯片（进迭时空 K3 线）而言，这是把「能跑模型」往「能压性能」推进的一步。

四、总结与趋势观察

  • 叙事与工程第一次同频：主论坛把 2.2 讲成「规模化共享优化」（21 厂商 35 芯片、1454 算子、+27.6%、264 贡献者），而同一窗口 GitHub 侧最重的一笔恰好是 build-infra 的六后端 22.04 builder 与逐后端每日轮子矩阵——两者回答的是同一个问题：芯片名单要靠可复现的交付面撑住。这是本期最值得记录的对应关系。
  • 算子域在扩张，但扩张的方向需要看清：KernelGen 三日落下三十余条 NVIDIA 算子，多是 _dim_arange、values_copy、_has_same_storage_numel 这类边界算子，说明主干覆盖接近完成、进入别名与视图语义的扫尾；而国产后端的增量仍集中在昆仑芯（二十余笔优化）与达摩院玄铁（GEMM 补齐），后端之间的覆盖差距并未缩小。FlagCV 立仓是另一个方向的扩张——从 LLM 与科学计算走向 OpenCV 式图像处理，六后端目录一次铺开，但仓库尚无可运行算子，短期不宜高估。
  • 量子线出现产品形态：FlagQuantum 0.3.0 / 0.3.1 双发 + 量智云对外发布，把「九鼎 / QUAFU 任务可恢复」这类工程能力写进发布说明，同时明确不在硬件上运行、不含 agent runtime。分工是「FlagOS 做执行栈与调度、量子院做硬件与云」，这比笼统的「量智融合」口号更能说明边界。
  • RISC-V 侧的动作在编译器深处：SpaceMiT 的 smt_rvisa 让作者显式控制 SEW / VL / 指令选择，并退役私有 TLE 副本——这类改动不出现在任何对外口径里，却决定了 RVV 后端能否从「能跑」走到「能压性能」。
  • 待观察：一是大会分论坛与工作坊的逐场纪要尚未公开，主论坛之外的技战术内容（统一 IR、Token 工厂、端侧部署）目前只有议程口径；二是量智云何时对外开放；三是 FlagCV 何时落第一个可运行算子；四是训练侧（Megatron-LM-FL / TransformerEngine-FL / FlagScale）三日零推送，是大会前后的正常静默还是 2.3 周期的起点，需下一期确认。
