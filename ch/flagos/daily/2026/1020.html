1.2 build-infra：昇腾四轮子迁入 22.04 自包含 builder，清微与曦望同日补齐（10-19）

日期：2026-10-19　来源：PR #1414 · PR #1418 · PR #1422 · PR #1417 · base 目录

  • 核心问题：昇腾的四个轮子原本在 24.04 运行时镜像里构建，产出的 libflagcx.so 与 _C*.so 链到 GLIBC_2.38，在 bundle 的 22.04 物理机上直接 abort。PR #1414 为每一行配置独立的 ubuntu:22.04 builder，与其它厂商行走同一通道，glibc 底线降到 2.35。
  • 一个配方服务四行：ascend.mk 只链 -ltorch_npu -lascendcl -lhccl，与具体芯片无关；但工具链本身不带这些链接期依赖，libhccl.so 与 <hccl/hccl.h> 来自芯片 ops 包，因此配方同时安装 toolkit 与 ops 包（不含 nnal/ATB），910b 与 910c 的差异通过 ops 安装器的芯片令牌（builder.ops_product，910b 与 A3）传入。
  • 验证口径：SDK 底线用 import torch_npu（会 dlopen CANN 工具链库）证明，而不是 import torch（该行上是纯 CPU）；ASCEND_OPP_PATH、ASCEND_AICPU_PATH、TOOLCHAIN_HOME、LD_LIBRARY_PATH 从 set_env.sh 落到 /etc/profile.d/vendor.sh，与轮子构建时 sourced 的是同一份文件。
  • 同日补齐两个新后端：曦望（PR #1418，sunrise wheel 的 22.04 自包含 builder，随后 PR #1420 记录该轮子以 22.04-clean 重发）与清微（PR #1422，tsingmicro wheel 的 22.04 自包含 builder）。至此 base/ 目录下的厂商矩阵为 nvidia（cuda12.8 / cuda13.3）、ascend（cann8.5.0 / cann9.0.0，含 910c）、cambricon（neuware4.4.3 / 4.7.2）、enflame（tops1.9.10 / 1.10.6）、hygon（dtk26.04）、iluvatar（corex4.4.0 / 4.5.0）、metax（maca3.7.2.1 / 3.8.1.3）、sunrise（tangrt1.2.0）、tsingmicro（tsm260610），共 9 家厂商。
  • FlagTree 侧三笔：PR #1417 加燧原 builder 并把验证步骤改成数据驱动；PR #1419 修掉「构建期断言燧原后端」的写法；PR #1421 把燧原 toolkit 的 deb 预置进 builder 镜像，减少每次构建的下载依赖。另有 PR #1410 把 pybind11 ABI 从实际发出的插件里读回、而不是写死字面量，PR #1413 让失败的 plan 直接让整个 run 失败而不是跳过构建。
  • 判断：这 16 笔没有一笔是功能开发，全部在消除「本机能编、目标机能跑」之间的缝隙。与 10-16 至 10-18 的六后端 22.04 收口连起来看，FlagCX 的制品通道已从「逐个后端打补丁」过渡到「一行一个后端、同一套 22.04 配方」。

1.3 FlagQuantum：405 文件合入量子栈扩容，M0 路线图确立（10-19）

日期：2026-10-19　来源：PR #635 · PR #637 · PR #642 · 仓库

  • 规模：23 笔提交、9 笔合入，是当日提交量并列第一的仓库。PR #635 单笔 405 个文件、+114463/−3983，新增 159 个公开名：算法包由 45 增至 148、量子纠错由 84 增至 108、远程调用由 20 增至 32、可观测量由 12 增至 20、编译器由 12 增至 17、模拟由 8 增至 11，并新开 flagquantum.operators 包（4 个导出）。能力注册表由 68 项增至 97 项，其中 development_evidence 由 20 增至 47。
  • 边界纪律：所有新名都是子包入口，Stable Core 的 flagquantum.__all__ 仍为 41 个导出、与 main 字节一致；PR 正文明确「提升到 Stable Core 走独立提案路径」，同时新增三份契约文件（编译器 pass 准入、多级 IR 内部接口、real-time 消息）。
  • 路线图：PR #637 确立 M0 至 M4 的分阶段范围、依赖与验收标准，要求复用现有 Core IR、编译器、动力学求解器、运行时与 PyTorch 集成，覆盖超导、中性原子、离子阱、光子与拓扑五类硬件；M1 从混合维状态空间起步。同一 PR 还修正了收缩高斯重叠积分的精度问题（改用 math.fsum 处理相消敏感求和，并补一条原始基序回归）。
  • 动力学与编译器：PR #639 支持混合维状态空间，PR #640 支持显式截断的玻色算子，PR #641 支持静态算子和的系数训练，PR #642 允许调用方按名字在两个优化点注入自有 pass。另有 10 余笔测试与文档提交把数值断言改成「按精度重复性比较」，而非按固定字面量比较。
  • 判断：量子栈正在从「框架雏形」走向「通用量子计算框架」——PR #635 补的是覆盖面（纠错、化学、实时调用、超算子），PR #637 补的是边界与阶段。两者同日合入，意味着 M0 的起点是把已有能力写清楚，而不是先扩 API。

四、总结与趋势观察

  • 趋势一：制品通道的统一先于功能扩张。build-infra 单日 16 笔提交、16 笔合入，全部围绕 22.04 自包含 builder；昇腾四轮子、曦望、清微在同一天被拉进同一套配方，base/ 目录形成 9 家厂商 17 个基线镜像的矩阵。glibc 底线由 2.38 降到 2.35 这件事，比任何一个新算子都更直接地决定「轮子能不能装到用户的机器上」。这一线索与 10-16 至 10-18 的六后端收口连成完整链条，可视为 FlagOS 2.2 发布后的第一个系统性补课。
  • 趋势二：量子栈从框架雏形转入通用框架的边界定义。FlagQuantum 单日 405 文件、159 个新公开名合入，同时以 M0 至 M4 路线图明确五类硬件的复用前提，并保持 Stable Core 的 41 个导出不变。这种「扩子包、锁核心」的做法，与 10-18 量智云发布时把 FlagQuantum 作为技术底稿的定位一致——对外讲能力之前，先把哪些是稳定接口写清楚。
  • 趋势三：国产算力侧的投入正在从「算子」走向「基准与基础库」。海光在 FlagBLAS 补齐六精度 GEMM 与 L1 支持；天数在 FlagDNN 补等价性能基线并直推 master；燧原在 FlagTree 铺 GCU300 基线与 vLLM 基准工作流；摩尔线程同时动 FlagGems、FlagTrain、FlagSparse 三条线。共同点是都可被基准直接度量，而非仅「支持某算子」。
  • 趋势四：KernelGen 进入稀疏与视图语义的扫尾段。合入侧的 _coalesce、ccol_indices_copy、_neg_view_copy 与在审侧十余笔稀疏算子（_sparse_mm 族、coo/csr 索引互转、copy_sparse_to_sparse_）说明稠密主干已基本清仓；同时昆仑芯以 30 笔在审构成单一后端最大队列，XPU3 的注意力族与 RNN 族是下一批要合入的主体。
  • 趋势五：新闻面进入会后消化期，信息重心回到仓库。24 小时窗口内有效新闻 1 条（中华网 10-19 的技术拆解，补七个量化案例），组件名直查连续零命中，分论坛纪要与工作坊内容尚未成稿。按经验，这类窗口后的一到两天通常会出现分论坛的二次报道，可作为下一期的观察点。
  • 下一期关注：一是 FlagQuantum 的 feat/m0-common-foundation 分支（10-19 16:47 建立）何时落 PR；二是 FlagGems 那批稀疏内核在审队列的合入节奏；三是 build-infra 是否把「一行一个后端」的配方复制到 FlagTree 与 Torch-FL 的制品线；四是大会分论坛纪要是否公开。
