1.3 达摩院玄铁：FlagBLAS 一次性补齐 15 组 BLAS1 算子，一万六千行落库（10-26）

日期：2026-10-26　来源：FlagBLAS PR #154 · FlagBLAS 提交

  • 规模：单笔 PR 改动 17 个文件、新增 16,168 行、删除 9 行，合入时间为 10-26 08:57，是当日非量子仓里体量最大的一笔。
  • 覆盖：一次补齐 BLAS 第一层十五组算子——向量最值与求和（AMAX、AMIN、ASUM）、向量累加与拷贝（AXPY、COPY）、点积三类（DOT、DOTC、DOTU）、欧氏范数（NRM2）、平面旋转四类（ROT、ROTG、ROTM、ROTMG）、向量缩放与交换（SCAL、SWAP）。
  • 层面：这是数值库层面的补齐而非推理算子补齐。BLAS1 是上层 BLAS2 与 BLAS3、以及 LAPACK 求解器的前置依赖，缺一层就无法自底向上自洽；对玄铁而言，此前在 FlagOS 里的存在感集中在推理路径（真武 Express 版、稀疏注意力），数值库是空档。
  • 链路：该 PR 在上一期日报中仍记为在审，本窗口完成合入，从「在审」到「落库」跨了一个窗口。
  • 判断：一家后端在 FlagOS 里的成熟度，通常按「能跑推理、能跑训练、数值库自洽」三段衡量。玄铁本窗口跨到第三段的第一级台阶，后续看 BLAS2 与 BLAS3 是否跟进，以及 FP8 路径（FlagTrain 侧在审的 fp8 GEMM 有玄铁分支）能否共用同一套数值库。

1.6 FlagCV：首个定位说明合入，Triton 视觉算子库对外成形（10-26）

日期：2026-10-26　来源：FlagCV · FlagCV PR #2

  • 定位：FlagCV 自述为「以 Triton 实现的高性能计算机视觉库」，在 OpenCV 形状的接口下提供常用图像处理原语——色彩转换、滤波、几何变换、算术运算，并以 OpenCV 的 CUDA 基线为对标，目标是在多种 GPU 架构上达到参考级正确性与有竞争力的性能。
  • 依赖关系：构建在 FlagTree 之上（FlagOS 维护的 Triton 分支，支持多硬件后端），对外提供与厂商无关的算子接口，后端可插拔。
  • 时间线：仓库于 10-14 建立（当时仅有占位），10-18 落骨架并撤掉算子实现改为「即时模式骨架」，10-26 合入 About 与 README 说明。即代码骨架在前、定位说明在后，本窗口补的是「这个仓到底做什么」。
  • 判断：视觉是 FlagOS 体系里原先最薄的一块——既有 FlagDNN、FlagSparse、FlagFFT、FlagBLAS，但没有图像处理原语层。FlagCV 把视觉接在 FlagTree 而非另起一套编译器上，方向与「一次开发、多芯运行」一致；真正的检验点是色彩转换与几何变换这类访存密集算子在非 GPU 后端（NPU、DSA）上的表现，目前尚无性能数据。

四、总结与趋势观察

  • 2.3.0 已走完一遍完整管道，标签仍未打出：运行时的门禁、changelog、重建授权、版本参数化在 10-23 至 10-25 就位，10-26 授权应用层重建并把标签收敛成 2.3.0-0.3.0。从「运行时刷新」到「应用跟版」这一步通常紧跟正式发布，本周仍是关键观察窗。
  • 后端矩阵在扩张而非收敛：AMD ROCm 7.2.4 基础镜像新增，说明 2.3 周期还在加平台。与之对应，玄铁补 BLAS1、清微接 RPM 打包、昆仑芯补设备位码——四件事分属数值库、打包、通信三个层面，都是「接进来之后才需要做」的工作。
  • 数值库与训练栈成为新战场：FlagBLAS 一次性补十五组 BLAS1 算子、FlagTrain 一批算子铺到七家后端，两条线都在 2.3 周期加速。推理算子的边际收益在下降（FlagGems 本期以 KernelGen 自动生成批次与后端调优为主），训练与数值库的缺口更明显。
  • 视觉方向首次成形，但缺性能证据：FlagCV 把定位写成「Triton 实现的 OpenCV 形状视觉算子库，对标 OpenCV CUDA 基线」，接在 FlagTree 上。目前只有说明与骨架，没有任何基准或非 GPU 后端数据，判断其价值为时尚早。
  • 评审带宽成为瓶颈：提交增 37%、在审增 23%、合入降 18%、新开降 18%。开发侧在积累，评审侧在消化。FlagGems 与 FlagTree 两个仓的在审量（52 与 9）与合入量（49 与 4）的落差最明显，而这两仓恰好是 2.3 的编译器与算子版本来源。
  • 量子栈进入场景铺开期：纠错码、中性原子、热浴三类物理场景同期推进，仍按四段留证作业。它继续占据全组织近六成提交，但相对上一期的日均已回落三分之二。
  • 信息面连续第三个窗口只有成员单位通稿：12 条候选 2 条有效，FlagOS 自身无版本发布、无新仓、无对外公告。内容主体仍来自 GitHub，属典型「代码在填后端、传播在等节点」的窗口。
  • 局限说明：提交检索为 GitHub search 的 total_count 口径（185 笔），与合并 PR 检索（133 笔）因压缩合并与索引延迟存在口径差，FlagGems 出现合入数（49）高于提交检索数（28）即属此类，报告内以合入数为准；FlagQuantum 的 109 笔含合并与分支同步提交，不等同于 109 个功能改动；FlagTree 的 0.7.1a1+mthreads3.6 经 Release 列表与 Tag 接口双向核对为纯 Tag，无 Release 说明；厂商通稿中的「无需改代码」「对齐或超过论文」等表述为公司口径，未取得第三方复现；清微稿件中「20 家厂商、30 余款芯片」与大会口径的 21 厂商、35 芯片不一致，已在正文标注归属。
