I. Open-Source Community and Software Ecosystem

1.1 Canonical Details Enterprise Open-Source RISC-V Software Readiness: Ubuntu riscv64 Package Pass Rate at 55.1% (09-07)

Date: 2026-09-07 (published by ServeTheHome on Monday, in-window at 09-08 01:00 Beijing time)　Source: ServeTheHome

ServeTheHome follows up with a transcript of a Hot Chips 2026 talk: Canonical Silicon Valley Director of Partnerships Gordan Markus systematically explained Ubuntu’s multi-architecture build mechanism and the path to enterprise-grade RISC-V readiness, and provided quantitative gap data — in the Ubuntu 26.10 test snapshot, 3,443 riscv64 packages were accepted for testing and 1,898 passed, a pass rate of about 55.1%, far below amd64’s roughly 92%. Canonical attributes part of the gap to emulated build and test targets (execution times stretched from hours to days), and has introduced native RISC-V build machines, with partners providing server-class RVA23 platform support. On the open-source collaboration side: Canonical participates in RISC-V International’s RISE project (commercial software readiness for mobile, consumer electronics, data center, and automotive), and its Ubuntu 24.04 native RISC-V runners power build and board farms hosted on Scaleway Elastic Metal, using hardware from Alibaba and SpacemiT, having accumulated 116 organizations, 24,000 tasks, and 700,000 build minutes. Canonical’s core judgment is that RVA23-style profiles make software targets predictable, and that large-scale upstream collaboration can bridge the historical “software readiness gap” that slows open-source adoption of new ISAs; as server-class RVA23 hardware arrives over the next two years, the software stack will have a fixed convergence target. This is the most data-valuable item in the window on the enterprise RISC-V software ecosystem.

Date: 2026-09-07 (16:19–17:33 Beijing time batch)　Source: GitHub openxiangshan/XiangShan commits

The vector backend refactor of the XiangShan open-source high-performance core (Kunminghu) continues: the 09-07 afternoon batch merged feat(vfma) “support vfma in new vector backend”, feat(vector, vfmac) refactoring pipeline registers and supporting widen instructions, and fix(vector) initializing vfma pipe metadata, marking the new vector backend execution path’s extension from whole-register moves (yesterday’s batch) to floating-point multiply-add (vfma/vfmac) and widening operations; the same batch also includes bypass readiness and non-register source fixes, LoadQueueReplay unaligned head delayed wakeup handling, ROD encoding alignment fix (#6509), and addition of VFREC7_V/VFRSQRT7_V to the FFlagsWen table. Combined with the vialu/mgu connections and vector wide/narrow instruction support of the past few days, it can be judged that the XiangShan vector execution subsystem refactor is advancing in the order of “instruction functionality completion — path dataflow fixes — floating-point matrix operation integration”, with engineering maturity continuing to improve; no version release in this window.

1.3 CVA6: Fix Scope Expands to RV32/64 Instruction Legality, Virtualization and Memory Protection Continue to Be Refined (09-07~08)

Date: 2026-09-07 20:18 ~ 09-08 05:36 (Beijing time, 9 commits)　Source: GitHub openhwgroup/cva6 commits

OpenHW Group’s application-class open-source core CVA6 continued to merge fixes in batches within the window, with coverage further expanding from yesterday: a new dimension of instruction semantic legality was added — zip/unzip are legal only in RV32 and should decode as illegal in RV64 (#3527), rejection of illegal use of RV64-only FCVT on RV32 (#3540), and legalization of the reserved value 2’b10 for mstatus.MPP when RVH=1; the virtualization and memory protection paths continue yesterday’s themes — ptw fix that the HLVX rule does not apply to G-stage checks of VS-stage PTE reads, and PMPADDR63 out-of-bounds access fix (#3485); additionally, a misaligned branch regression test when the C extension is disabled (#3424), a false 4 KiB alias regression test (#3453), and a debug loop shared-pointer out-of-bounds fix. With more than 15 commits combined over two consecutive days, the refinement of virtualization two-stage address translation and the PMP security path has entered a high-frequency period, which can serve as an observation signal for the quality-maintenance cadence of RISC-V open-source application cores.

II. Product and Ecosystem Developments

2.1 YuzukiHD Open-Sources YuzukiNeko: Allwinner F101 (DAMO XuanTie C907) Pico-Sized Linux Board (09-08)

Date: 2026-09-08　Source: CNX Software, YuzukiHD/YuzukiNeko GitHub

Open-source hardware team YuzukiHD released a new board, the YuzukiNeko: a Raspberry Pi Pico-sized (about 51 x 21 mm) Linux single-board computer, powered by Allwinner’s new SoC, the Allwinner F101 “smart control and display processor”. The F101 uses a single-core DAMO XuanTie C907 RISC-V core (1.008 GHz, 32 KB I-cache + 16 KB D-cache), in a QFN-68 package, with SiP-integrated 8 MB (F101S2) or 16 MB (F101S3) PSRAM (252 MHz), an integrated display engine (RGB888 720p, single-link LVDS 1366x768, 4-lane MIPI DSI 1280x800), large-size JPEG/PNG decoding, USB 2.0 DRD, and 512-bit eFuse. Onboard are 128 Mbit SPI NOR + microSD, USB-C (data/power/flashing), dual 20-pin GPIO expansion headers, and a FEL button. On the software side, YuzukiHD has open-sourced on GitHub the schematic, EasyEDA project, Gerber, 3D STEP, and BOM, and provides a sun252i_f101 branch based on mainline Linux 7.2, a Buildroot external tree, and Zephyr RTOS support (Linux and Zephyr dual systems). A Whycan forum post says the F101 SoC unit price is about 18 RMB (about 2.7 USD), and the community expects the full board to sell for under 10 USD. The board is not yet on sale. Significance: following the D1 series (C906), the DAMO XuanTie C907 has once again gained large-scale low-cost adoption by a domestic SoC, and the ultra-low-cost “Linux/Zephyr dual-system” RISC-V micro-board ecosystem is expected to expand further.
