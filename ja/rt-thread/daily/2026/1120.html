2.1 メールボックスハンドル未検証、任意カーネルの読み書きに切替可能（11-19）

日付：2026-11-19 03:36（修正提案コミット）。出典：#11960。

議題は XueDugu が 10 月 31 日に提出し、タイトルは未検証の偽オブジェクトが任意カーネルの読み書きに切り替わり得るというもの。議題が示す導入点は ecf2d8215961（2022-12-03）、最初の影響バージョンは v5.0.0、v5.3.0 と master にも残存。ラベルは in progress、コメント 5 件。

機構は三層に分かれる。sys_mb_send() はユーザが渡した mb をそのまま rt_mb_send() に転送する。sys_mb_recv() は出力ポインタ value を検証したが、mb は検証していない。メールボックス実装内の RT_ASSERT は構造体の type フィールドを読むだけだ。

LWP には本来オブジェクト帰属テーブルがあり、lwp_user_object_add/delete がそれを維持している。これらの IPC システムコールはこのテーブルを迂回している。

したがって経路は非常に直接的だ。プロセスが 1 ページをマッピングし、その中に偽の struct rt_mailbox を書き込む。type を RT_Object_Class_MailBox にし、msg_pool を任意のカーネルアドレスに向け、公開されているメールボックスシステムコールを呼ぶ。

PoC は qemu-virt64-aarch64 上で動作確認済み。構成は GICv2、シングルコア、128 MiB。スイッチは RT_USING_SMART=y、RT_USING_MAILBOX=y、RT_USING_DEBUG=n。

結果として、対象の qword は 0x74003e2f2068736d から 0x1122334455667788 に変わり、sys_mb_recv は同じ qword を読み戻せる。

課題は別途 Raspberry Pi Pico 2 W（RP2350）上でもボードレベル検証を行った。ボード上で動くのは単一アドレス空間の RT-Thread であり、検証したのはカーネルメールボックス API というプリミティブだ。ユーザ態とカーネル態の境界は QEMU フルシステム実行によって証明されている。

3. デバイス層とビルドツール

3.1 デバイスライフサイクルロックを既定オフのオプションに（11-19）

日付：2026-11-19 10:44（提案）。情報源：#12068。

提案は #11234 に応答するもの。あの課題は 3 月 3 日に提出され、複数スレッドが同一デバイスを同時に open と close すると ref_count が誤って計算されるという内容だ。提案は 5 コミット、5 ファイル、追加 366 行、削除 48 行。

手法は Kconfig オプション RT_USING_DEVICE_LIFECYCLE_LOCK を新設し、device と mutex に依存させ、既定でオフとする。オンにすると各デバイスが自身の優先度継承ミューテックスを使い、初期化、open モード決定、参照カウント更新、ドライバコールバックを直列化する。

コールバックはスリープ可能。異なるスレッドの呼び出しはこの切り替えが終わるまで待つ。同一デバイス上の再帰的切り替えは -RT_EBUSY を返す。デバイスをまたぐネスト呼び出しはロック順序を自身で保証する必要がある。

欠陥は vexpress-a9 上でカウントドライバを用いて再現された。ベースラインでは独立デバイスが二回ドライバ open を受け取り、二つのアクティブ参照があった。最終的に close と reopen が重なった後は参照が一つだけ残り、open_flag がゼロになり、ドライバは reopen しなかった。シングルコアとデュアルコア SMP のいずれでも再現する。

テストケースは 229 行、kernel_basic.cfg を使用し、この設定ではこのオプションが既にオンになっている。

判断：既定オフは既存動作が変わらないことを意味し、明示的にオンにした場合のみスケジューリングとレイテンシが変わる。根拠は、オプションが device と mutex に depend しており、提案がシングルスレッドのボードレベル初期化でコンソールを開くケースを別途例外として残していることにある。

3.2 dfs の open 失敗で正の errno を返すよう変更（11-19）

日付：2026-11-19 08:54（提案）。情報源：#12067。

提案は #10558 に関連する。あの課題は 2025 年 7 月 28 日に提出され、rt_set_errno() のエラーコードの正負が統一されていないという内容だ。提案は 4 コミット、6 ファイル、追加 108 行、削除 71 行。

現象は3つある。マウントされたファイルシステム上で存在しないファイルを開くと-1を返すが、errnoは負の値になる。記述子テーブルが満杯のとき、DFS v1はerrnoに-ENOMEMを報告し、DFS v2は0を返すため、呼び出し側は0を有効な記述子とみなしてしまう。RT-SmartのARMプロセスは、生のシステムコールとmuslの両側からこの偽の成功を受け取る。

修正方法は、割り当て失敗の原因をプライベートスロットの補助関数から持ち出すことである。記述子が上限に達したらEMFILEを報告し、テーブル拡張またはファイルオブジェクトの割り当てに失敗したらENOMEMを報告し、共有アロケータのロック解除後にエラーを公開する。POSIXのopen()は失敗時に-1を返して対応する正の値のerrnoを提示し、成功したopenは引き続き0番の記述子を返せる。

ユースケースはtc_posix_api.cに追加し、60行を新設して、ファイル不在とテーブル満杯の2つの情形をカバーする。A9のDFS CI設定を現在のKconfigシンボルに置き換え、ボードレベルのsdデバイスを選択する。

検証環境はbsp/qemu-vexpress-a9、QEMU 7.2.22である。DFS v1とv2の両方を実行し、ファイルシステムはtmpfs、DFS_FD_MAX=12とする。

提案本文は現象をコミット6fdfe700に紐づけている。この番号はリポジトリ内ではmem.cfgのコミットであり、memheapユースケースのみに関係する。

判断：この参照は誤記の疑いがある。根拠は、6fdfe700のコミット説明がdfsと無関係であり、11-18にマージされた3件の中にもdfsの変更がないことである。

3.3 グループライブラリのローカルコンパイルフラグが2回適用される（11-19）

日付：2026-11-19 22:03（提案）。情報源：#12070。

提案が修正するのは#4417である。その課題は2021年3月4日に提起され、ラベルはenhancementである。変更はtools/building.pyの1ファイルのみで、27行を新設し21行を削除する。

現象は、LIBRARY=Trueで宣言され、かつローカルコンパイルフラグを持つグループが、同じオブジェクトに対して2つの異なるSCons actionを登録してしまうことである。1つはライブラリビルダーを通り、もう1つはアプリケーションがローカルフラグを処理する際に生成される。

修正方法は、ライブラリグループのオブジェクトをまず通常のグループと同様にローカルフラグ付きでコンパイルし、その後アーカイブする。通常のアプリケーションビルド時には、これらのライブラリソースを別個のローカルオブジェクト走査に加えない。

検証にはSCons 4.11.1とscons -Q -nの最小フィクスチャを使用した。ファームウェアビルドもボードレベルテストも実行していない。

4. シリアルV1の取捨

4.1 タイムアウトイベントがV1のswitchに分岐を持たない（11-19）

日付：2026-11-19 22:54（議論更新）。情報源：#11909。

RT_SERIAL_EVENT_RX_TIMEOUTの値は0x05である。これはdev_serial.hに定義があるが、rt_hw_serial_isr()のswitchは0x01から0x04までしか処理せず、default分岐もない。

ドライバがこのイベントを送信しても、フレームワークは何も行わない。イベントは静かに破棄される。

リポジトリ内には、これによってデータフレームを分割するドライバが2つある。
bsp/wch/arm/ch579m/board/drv_uart.c:335はUART_II_RECV_TOUTを受けるとこのイベントを送信する。
bsp/synwit/libraries/SWM341_drivers/drv_uart.c:287はUART_IT_RX_TOUTがセットされると同じイベントを送信する。

これらのBSPはどちらもV1を使用しているため、「1フレーム受信完了」の通知がアプリケーション層に届かない。フレーム境界が失われ、FIFO水位に基づくRX_IND上报に退化するしかない。

V2 の事情は異なる。dev_serial_v2.h は 0x01 から 0x04 しか定義しておらず、このマクロが存在しないため、ドライバが参照するとコンパイルが直接失敗する。作者は V2 の isr に case を追加すると 'RT_SERIAL_EVENT_RX_TIMEOUT' undeclared が報告されると注記している。V2 でこのセマンティクスが必要な場合は、読み取り側の RT_SERIAL_CTRL_SET_RX_TIMEOUT を使うべきである。

4.2 五行の修正と六百行のフォーマット（11-19）

日付：2026-11-19（提案の変更範囲）。情報源：34d2a002。

提案全体は 4 ファイル、868 行追加、504 行削除である。この数字は大きく見えるが、分解すれば明らかになる。

実際の修正は 34d2a002 で、dev_serial.c は 5 行追加、0 行削除である。修正方法はタイムアウトイベントを RX_IND 分岐に統合し、まずハードウェア FIFO を排出し、その後ソフトウェア FIFO にすでにキャッシュされた長さに従って rx_indicate をコールバックする。

もう一笔 87b851b4 は clang-format で、同じファイルで 622 行追加、505 行削除である。フォーマットが diff を膨らませている。

残り 3 ファイルは用例である。uart_rx_timeout.c 226 行、Kconfig 5 行、SConscript 11 行。用例はハードウェアに依存せず、ボードがなくても実行できる。

4.3 メンテナのスタンス：V1 は互換用に残し、新規 BSP は V2 へ誘導（11-20）

日付：2026-11-20 06:54（コメント）。情報源：#11909・スレッド。

議論は 10 月 22 日にすでに提示されていた。Rbb666 のコメントは：V2 が登場して久しく、V1 と V2 を長期並行メンテナンスするのは罠であり、個人的には V1 を凍結して歴史的互換のみとし、シリアルの重心を V2 に寄せるべきだと感じる、というものだ。

同じコメントには二つの事実もある。RTT のサマーキャンプと入門トレーニングは依然として V1 に対応している。多くの BSP はシリアルを MSH としてのみ使い、要求は浅く、歴史的遺留である。彼は後続の BSP が積極的に貢献者を V2 への適配に誘導すべきで、ルネサスなどの BSP はすでに V2 に適配していると考える。

今朝 Yunlk が返信し、この位置づけに沿って説明した。V1 が引き続き服役する以上、その内部で静かに破棄されるイベントは修正に値する。本提案は case を一つ追加するだけで、V2 もドライバインターフェースも動かさず、別途ハードウェア非依存の用例を添える。

判断：この議論は V1 に性質を与えた。凍結ではなく、低メンテナンスである。根拠はメンテナが「MSH としてのみ使う BSP は V1 を残す」と言っており、「V1 は修正受付を停止する」とは言っていないことである。

5.1 siot が設定可能な MQTT クライアントとしてインデックス入り（11-19）

日付：2026-11-19 14:05（提案更新）。情報源：packages #2059。

提案は yzy726 が 11 月 18 日に提出し、調査期間内に 11 月 19 日 14 時 05 分に更新された。変更は 3 ファイル、183 行追加。iot/Kconfig 1 行、iot/siot/Kconfig 128 行、iot/siot/package.json 54 行。

パッケージ本体は MQTT 3.1.1 クライアントで、QoS 1 と有界 I/O をサポートし、CA とホスト名検証の TLS はオプション、Mbed TLS 2.x に依存する。固定バージョン v1.1.1（commit c4956bee）で、インデックスには v1.1.0、v1.0.1、v1.0.0 と latest を保持し、旧バージョンは新たに追加されたチャネルオプションを隠す。

設定可能項目は Host、ポート、Client ID、アカウントと Topic である。提案には個人サーバ憑証を含まず、開発ボード、センサー、コースアプリにも紐づかないと注記されている。

さらにオプション機能の層がある：単一デバイス、グループ、デプロイレベルのコマンドルーティングで、デバイスの状態と確認 topic に従って別々に保ち、ルーティング層はデフォルトで無効である。付属として独立した Python 教師側 Web コントローラがあり、機能スイッチ、名簿、アクション許可リスト、認証 API と Mosquitto 2.x の ACL エクスポートを含む。

5.2 NFC リーダーライブラリが rtt ブランチと最初の alpha タグを開設（11-19）

日付：2026-11-19 17:21（ブランチコミット）。情報源：rtt ブランチ。

リポジトリは NXP Reader Library 07.18.00 の RT-Thread 移植で、OSAL/BAL/DAL と Kconfig を提供すると自述している。11 月 19 日に rtt ブランチを新規作成し、タグ v0.1.0-alpha.1 を同じコミット 2828285 に打った。

当該ブランチには調査期間内に二つのコミットがある。15 時 16 分のコミットは NXP Reader Library に RC663 の SPI ポートを追加した。17 時 21 分のコミットは二言語ドキュメントと CI ワークフローを補った。

main ブランチの最新コミットは11月18日10時18分で止まっており、開発はすでに rtt ブランチへ移っている。

判断：これは個人プロジェクトであり、スター数は0で、成熟度はパッケージインデックス内のパッケージとは比較にならない。ここに挙げたのは、その日に照合可能な成果があり、かつ RT-Thread エコシステムでは珍しい NFC 方向の移植であったためである。

6.2 RH850 移植が CI 認証情報で停滞（11-19）

日付：2026-11-19 19:05（コメント）。情報源：#11998。

Renesas RH850 G4KH 移植と qemu-rh850-u2c ボードパッケージは依然52ファイル、新規4122行。最新コミットは 6309b2b4（11-18 22:38）で、内容に変化はない。

変わったのはレビュー説明である。BernardXiong は19時05分にこう書いた。失敗の指紋は以前と同じ。問題が出ているのは RT-Thread BSP Static Build Check 下の ESP32C6 の Install riscv32-esp-elf ToolChains ステップのみ。そのステップが curl -H "Authorization: ***" で 401 Bad credentials を返している。

彼の結論は、これは fork PR の認証情報と環境の問題であり、本提案とは無関係だというもの。そのまま再実行しても高い確率で同じ空トークンに当たるため、CI 認証情報が修復されてから再実行するか、マージ時に該当 job を無視する必要がある。

7. まとめとトレンド観察

7.1 増分はすべて提案側にある

7.2 アサーションは帰属検証ではない

RT_ASSERT が読むのは構造体内の type フィールドである。このフィールドは偽オブジェクトでは呼び出し側が自分で埋める。

判断：この種の穴はアサーションでは防げない。根拠は、PoC が type を RT_Object_Class_MailBox と書くだけでアサーションを通過してしまい、本当の帰属チェックはオブジェクトテーブルに依存するからである。

7.3 3件の旧 Issue への再訪

#4417 は2021年3月4日、#8143 は2023年10月17日、#10558 は2025年7月28日に提起された。今日の3件の提案がそれぞれに対応している。

判断：旧 Issue が動き出す条件は誰かが同意することではなく、誰かが手を動かすことである。根拠は、3件の Issue がいずれも長期間オープンのままコメントも少なかったが、提案が届いた途端にコミットとユースケースが伴ったことだ。
