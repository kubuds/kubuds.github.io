1.1 clang-format を 22.1.8 に固定、src/ 配下の 73 のカーネルソースファイルを一括再整形（10-30）

日付：2026-10-30 18:20（マージ時間）　出典：提案 #11936

75 ファイル、3852 行追加、3023 行削除、作者 CYFS3、関連する以前の #11653 とマージ済みの #11859。問題はフォーマット自体ではない：フォーマットチェック CI は pip で clang-format をインストールし、手動フォーマットワークフローは apt でインストールしており、どちらもバージョンを固定していないため、同じコードが異なる時点で異なる結果を生む可能性があり、フォーマットチェックが再現不能になっていた。

変更は 3 つの独立したコミットに分割。第一に、tools/ci/requirements-format.txt を新設し、バージョンを 22.1.8 に固定、両ワークフローを当該ファイルからのインストールに変更、手動ワークフローには Python 環境を提供する actions/setup-python を追加；第二に、.clang-format で AllowShortLoopsOnASingleLine を有効化、BraceWrapping.BeforeWhile を無効化、空ループは単一行を維持、do-while は統一して } while (...) と記述；第三に、同一バージョンで src/ 配下の 73 の C およびヘッダファイルを再帰的に整形、klibc、utest、perf、smp サブディレクトリを含み、69 が変更を生じ、4 は既に準拠済み。中英文コーディング規約にもインストール、バージョン確認、エディタ設定の 3 節を同期追加。

Kconfig、SConscript およびその他のディレクトリは今回の範囲外であり、これはディレクトリ単位で進めるフォーマット収束であり、全リポジトリの再整形ではないことを示す。

1.2 dlmodule が 2022 年に報告された #5705 をクローズ（10-30）

日付：2026-10-30 10:54（マージ時間）　情報源：提案 #11915、欠陥 #5705

2 ファイル、215 行追加、45 行削除、変更は dlelf.c と dlelf.h に及ぶ。修正対象は 2022 年 3 月に報告され、4 年以上未解決だった欠陥 #5705：動的モジュールで未初期化グローバル変数にアクセスするとアドレスが重複する、またはリロケーションできない問題。著者は最新 master で再現した上で、根本原因を 4 つに分解した。

1 つ目、BSS セグメント（SHT_NOBITS）のロード後に割り当てポインタが進まず、複数の NOBITS セグメントが同じメモリ領域に重複する。2 つ目、元の実装はセグメント名で rodata、bss、data の 3 種類のベースアドレスを共用し、シンボルが属するセグメントの実際のロードアドレスからリロケーションアドレスを計算していなかったため、複数セグメントの場面で誤った位置を指す。3 つ目、SHN_COMMON シンボル（tentative 定義の未初期化グローバル変数）のリロケーションが暗黙にスキップされる——コードは shdr[0xfff2] を読み、ゴミのセグメント名を取得して不一致となる。4 つ目、この経路は module->symtab を一切構築しないため、dlsym() が ET_REL モジュールに対して常に失敗する。

修正方法は 4 つに対応する：BSS セグメントのロード完了後に割り当てポインタを進める；rodata、bss、data セグメントのシンボルを「セグメントロードアドレス＋セグメント内オフセット」で統一的に計算する；SHN_COMMON 用に共通ブロックを別途割り当て、サイズ核算とリロケーションで同じアライメントアルゴリズムを共用し、当該ブランチの処理をセグメント名マッチングより前に前倒しして範囲外読み取りを回避する；.symtab から GLOBAL FUNC シンボルを収集して module->symtab を構築し、ET_DYN 経路が .dynsym から構築する做法と整合させる。

検証は qemu-vexpress-a9 上で完了し、RT_USING_MODULE を有効化、3 つのテストモジュールを実行して、ET_DYN 標準フローとカーネルシンボルの GOT 経由インポートの 2 経路をカバーした。影響範囲は ET_REL ロード経路を通る BSP であり、Cortex-M シリーズで動的モジュールを有効化したプロジェクトが真っ先に該当する。

2. セキュリティフォローとマージ待ちキュー

2.1 RT-Smart mailbox がカーネルオブジェクトポインタを検証せず、偽造オブジェクトでカーネルメモリを読み書き可能（10-31）

日付：2026-10-31 14:26（報告時間）　情報源：欠陥 #11960

報告者は XueDugu、照合したベースラインは当日 master cbc19778。問題は mailbox のシステムコール入口にある：ユーザが渡したカーネルオブジェクトポインタをそのままカーネル mailbox API に転送し、このオブジェクトが呼び出し元 LWP に属するか、mailbox か、カーネルメモリに存在するかを検証しない。そのため非特権プロセスが「偽造オブジェクト」を構築でき、カーネルが自身の規則でそれを読み書きする結果、任意のカーネル読み書きプリミティブと等価になる。

報告はタイムラインを詳細に記載している：欠陥はコミット ecf2d8215961（2022-12-03、RT-Smart システムコール境界調整）で導入され、最初の影響バージョンは v5.0.0、v5.3.0 と現在の master（5.4.0-dev）でも継続している。検証は 2 層で行った——QEMU の qemu-virt64-aarch64 全システム実行（virt、GICv2、シングルコア、128 MiB、RT_USING_SMART と RT_USING_MAILBOX を有効化）でユーザ態からカーネルへの越境経路を証明；Raspberry Pi Pico 2 W（RP2350）でボードレベルにカーネル mailbox API プリミティブ自体を検証し、後者はシングルアドレス空間の通常の RT-Thread を実行しており、問題が Smart の分離層にとどまらないことを示す。

記事執筆時点で、この欠陥は未アサイン、対応する修正提案なし、コメントは CI ボットの /claim 提示のみ。

2.2 pipe の FIONREAD がユーザ指定ポインタを直接書き込み、同型欠陥が連続 3 回目（10-30）

日付：2026-10-30 19:13（レポート時刻）　情報源：欠陥 #11958

同一報告者による2件目。pipe の ioctl は FIONREAD と FIONWRITE の2つの分岐で直接 *((int *)args) = ... と書き、リングバッファのデータ長または残り容量を args が指すアドレスに書き込む。RT-Smart の sys_ioctl() は生のユーザ引数をそのまま転送し、copyout を行わず、pipe のこの層もそのアドレスがユーザアドレスかどうかを判定しない。結果として、通常のプロセスが任意のカーネルアドレスを指定でき、カーネルに4バイトを書き込ませることができる。書き込まれる値は pipe の現在の状態に制約される。

影響範囲は v5.0.0 から v5.3.0 および master（5.4.0-dev）。検証は QEMU vexpress-a9、Cortex-A9、32 ビット RT-Smart、RT_USING_POSIX_PIPE 有効、pipe バッファ 512 バイトの環境で完了した。

これは同型の欠陥が連続して3回目となる：まず端末サブシステムの ioctl が FreeBSD の copyin 前提を失い（欠陥 #11937）、次にブロックデバイスが 24 バイトのパーティションテーブルを呼び出し側指定のカーネルポインタに書き込み（#11952）、今回は pipe（#11958）である。3箇所の原因は同一——fops 層が「引数はすでにカーネルアドレスである」という古い仮定を踏襲し、ユーザ態入口で変換層を補っていない。2.1 の mailbox 欠陥は同じ導入コミットが残した同族であり、越境の仕方が「中へ書き込む」から「ユーザポインタをカーネルオブジェクトとして扱う」に変わっただけである。

2.3 poll と epoll のカウント乗算ラップアラウンド（10-30）

日付：2026-10-30 11:59（提案時刻）　情報源：提案 #11954

1ファイル、28行追加、#11925 の前半部分を修正。sys_poll() はユーザが与えた数量でカーネルバッファサイズを計算するが、32 ビットでは乗算がラップアラウンドし、その後もラップアラウンドしていない元の数量で走査する：nfds が 0x20000001、pollfd 構造が 8 バイトの場合、積 0x1_00000008 は 8 に切り捨てられる。アクセス検証と kmem_get はいずれも 8 バイトで通過するが、poll() は 536,870,913 項目を走査し、do_pollfd() 内の pollfd->fd の読み取り、revents の書き込みはすべて割り当てブロックの外に出る。64 ビットビルドは影響を受けず、積が 64 ビットに昇格し、巨大な割り当ては直接 ENOMEM を返す。

sys_epoll_pwait() も同じ形であり、かつそのカウントは int であるため、負の値も併せて拒否する必要がある。修正方法は、これらの数量で何らかのサイズを計算する前にまず判定する：nfds が SIZE_MAX / sizeof(*fds) より大きければ -EINVAL を返す。epoll 側にはさらにカウントが 0 未満かの判定を加える。書き方は sys_sendmsg、sys_recvmsg における msg_iovlen の検証と一致させる。

同じく進行中のものには #11899（sys_sigaction がシグナル番号を検証）と #11895（シグナル配送順序と ELF セグメント保護）があり、共通点はユーザ態から渡された番号、長さ、ポインタをカーネルロジックに入る前に一通り検証することである。

2.4 RISC-V AIA：APLIC レベル割り込み EOI が無条件に setipnum を書き込む（11-01）

日付：2026-11-01 20:40（提案時刻）　情報源：提案 #11966

8ファイル、1367行追加、10行削除。現象は QEMU 8.2.2 上で bsp/qemu-virt64-riscv、RV64、4コア SMP に AIA（APLIC と IMSIC）を加えた構成を動かすと、rt_thread_mdelay(1000) を含むカウントプログラムが RISC-V test: 0 を表示しただけで停止し、遅延スレッドが二度と戻ってこないというものである。

特定の結果、APLIC ドライバがレベル割り込みの EOI を処理する際に無条件に setipnum_le を書き込んでいることが分かった。旧版 QEMU ではデバイスがすでに割り込みを撤回した後でも、この書き込みによって新たな MSI が発生する可能性があり、持続的な偽割り込みとなってシステムタイマの処理を圧迫し、遅延スレッドが復帰できなくなる。修正方法は、まず in_clrip 内の対応する有効入力状態（rectified input、割り込み極性を考慮済み）を読み、デバイスが依然として割り込みを有効に保持している場合にのみ setipnum_le を書き込む——レベル割り込みの再トリガ能力を保ちつつ、撤回済みの割り込みに一発補うことをしない。

再現プログラムも併せて変更した：BSP の main.c を「Hello RISC-V を一度表示」から 0 から 9 までのカウントループに変え、各表示後に1秒遅延させる。検証環境は QEMU 8.2.2、OpenSBI v1.3、riscv64-unknown-elf-gcc 13.2.0。AIA 有効、4コア、ネットワークと NVMe と virtio-console と PCI シリアルを無効にした3組の構成でいずれも完全に出力できる。

3.1 武漢会場巡回トレーニングが 10-31 に開催、Edgi-Talk デュアルコア四大実験（10-31）

日付：2026-10-31 10:00 ~ 17:30（イベント時間）　情報源：公式コラム：武漢会場実習

RT-Thread 巡回トレーニング武漢会場は武漢地質大学西区教二棟 801 教室で開催され、ハードウェアは Infineon PSoC Edge E84 の Edgi-Talk デュアルコア開発ボードで、4 つの実験を連ねて解説した：GUI 表示、手書き認識、LLM ウェブ側デプロイ、小智 AI。プロジェクトコードと設定ファイルは会場で全量提供された。

LLM のパートは llmchat ソフトウェアパッケージに通義千問（デフォルトは qwen-plus）を組み合わせ、さらに llmchat の webnet モードを有効にし、ブラウザからボードの IP にアクセスすれば対話できる。記事はつまずきポイントを細かく書いている：webnet スレッドスタックは 8K に引き上げ、mbedtls の最大フラグメント長は 6144 に変更する必要があり、そうしないと TLS ハンドシェイクが失敗する。lwIP スレッドスタックは 4096。html は ymodem で /flash/webnet ディレクトリに転送する。

3.2 11 月 4 日ライブ配信：大模型は PC に残し、睿擎 3576 で藍鯨魚デスクトップペットを再現（10-30）

日付：2026-10-30 11:50（公開）　情報源：公式コラム：睿擎 3576 デスクトップペットライブ配信

11 月 4 日（水）20:00、睿擎技術ライブ配信ルームで「睿擎 3576 で DeepSeek 藍鯨魚デスクトップペットを再現」の実機デモを行う。作者はすでに PC 側の DeepSeek と 3576 開発ボードを接続し、DeepSeek Harness 内のデスクトップペット形象を再現している。

アーキテクチャの選択は記録に値する：ボード上で大模型を動かさず、「脳」は PC に残し、「肉体」は 3576 に任せる。ライブ配信では 4 つのパートを解説する——計算力をどこに置くか、人設をどう定めるか；ボードとコンピュータが同一ネットワークセグメントにない場合、DSH のスマホブリッジ入口を通じてどうペアリングするか、会場で curl を使って短時間 Token を取得し通信用の Cookie に交換してから RPC を送信する；session.create、session.prompt といったインターフェースでどうテキストを送信し、返信を読み戻すか；その後 LVGL で傾聴、思考、発話の 3 状態を描画し、ASR と TTS を接続し、さらに大模型に直接ペリフェラルを制御させる。

この路線は端側 AI に取り組むチームにとって参考価値がある：端側計算力の境界を認め、インタラクションと表示をボード側に置き、推論は上流に残す——コンテスト作品における「NPU で小モデルを動かし、複雑な判断はクラウドに上げる」と同じ取捨選択である。

4. エコシステムとベンダー適配

4.1 NXP RT1180 産業イーサネットリンカスクリプトが審査待ちキューに（10-30）

日付：2026-10-30 19:57（提案時間）　情報源：提案 #11959

NXP i.MX RT1180 向けの BSP 提案で、産業イーサネットシーンに必要なリンカスクリプトを補うもの。RT1180 は複数系統のギガビットイーサネットと TSN スイッチを備え、こうしたプロジェクトはメモリパーティションとセクション配置の要求が汎用 BSP より厳しく、リンカスクリプトがまず着地してこそドライバやその他のペリフェラルが接続しやすくなる。提案は依然キューにあり、マージ時期は未定。

同一期間のハードウェア側と低層の小修正はさらに 3 本がキュー待ち：#11961 は C++ スレッド初期化用の静的 TLS；#11965 は gcc が klibc 内の kstring.c のバイトループを memset と memcpy 呼び出しと認識するのを防ぐ——自前実装の文字列関数がコンパイラによってライブラリ関数呼び出しに書き換えられるが、こうした書き換えはカーネルブートストラップの文脈では別途説明が必要；#11963 と #11964 は 2 本の utest 補足テストで、それぞれ mailbox ケースを繰り返し実行可能にし、シグナルが mdelay ブロッキングスレッドに配送される情形をカバーする。

4.2 前号で報じた 2 本のドライバ欠陥にはすでにパッチあり（10-30 ~ 10-31）

日付：2026-10-30 18:16 / 10-31 21:11（提案時間）　ソース：提案 #11957、提案 #11962

前回のレポートで取り上げたドライバ側の欠陥4件のうち、2件にパッチが届いた。#11957 は DM365 SPI のゼロ除算に対応する：setup 段階で max_hz が 0 の場合を拒否し、プリスケーラ計算でそれを除数として扱わないようにする。#11962 は Bluetrum AB32 の ADC に対応する：読み取り前にチャネル番号を検証し、マッピング失敗後に黙って 0 にフォールバックし、さらに元のチャネル番号でデータレジスタ配列をインデックスすることをやめた。

いずれもまだマージされておらず、残りの2件（Bouffalo ADC の範囲外読み取り #11949、HPM ADC のチャネル状態インデックス #11951）には今期も対応する提案がない。この種の欠陥に共通する点は変わらない：rt_adc_read() と rt_spi_configure() の層ではパラメータ検証を行わず、責任を各ドライバに押し下げているが、ほとんどのドライバがそれをしていない。

5. 業界応用

5.1 大会作品の事後集中オープンソース化：4つのエッジ AI ビジョンプロジェクトが2種類のボードに集中（10-30 ~ 11-01）

日付：2026-10-30 ~ 2026-11-01（リポジトリ作成時間）　ソース：リポジトリ：Titan Mini PCB Inspector

調査期間内に GitHub 上で新規作成された RT-Thread 関連リポジトリは15件で、うち7件が 2026 RT-Thread 組み込みコンテストの応募作品と自称しており、集中オープンソース化の時期は 10-30 から 11-01 に集中し、コンテストの「作品をフォーラムに投稿しコードをオープンソース化する」という要件と一致する。

ルネサス Titan Board Mini（RA8P1、Cortex-M85 に Ethos-U55 を加えた構成）上には2件ある。1つは Titan Mini PCB Inspector：カメラで基板を確認、800×480 LCD 表示、シリアル HMI 対話、Ethos-U55 でローカル推論、クラウドの大規模モデルが提案を書き、ネットワーク切断時はテーブル駆動の専門家ルールにフォールバックし、黙って機能停止しない。もう1つは霊犀智眸：INT8 量子化された姿勢モデルが1フレームあたり最大10人、1人あたり17個のキーポイントを検出し、さらにルールに従って挙手、伏せ、起立、正座の4種類の行動を判定し、重み付けして0から100の集中度スコアを出力、イベントはタイムスタンプ付きで SD カードに CSV として書き込み、元の映像は教室の外に出さない。

富瀚 MC632X（Cortex-A7）上には同名の SENTINEL が2件ある。1つは M5Stack AtomS3R 小智を接続して音声アナウンスを行い、デュアル 800×480 MJPEG の Web プレビュー、人型検出とトリップワイヤ进出統計、夜間は周辺警備と録画証拠保存に切り替える；もう1つは PC から独立して動作することを強調し、電源ケーブル1本とネットワークケーブル1本で、電源投入後に自動でネットワーク設定、メディアパイプライン、Web サービスの起動を完了する。

4つのプロジェクトの取捨選択は一致している：モデルを端末側の NPU や MCU に压縮し、複雑な判断はクラウドまたはルールエンジンに任せ、元の映像はデバイスの外に出さない。これは 3.2 のライブ配信における「脳は PC、肉体はボード端」と同じエンジニアリング判断である。

5.2 コンテスト用ボードから生産ラインへ：デュアル Cortex-M7 の 20 kHz センサレス FOC とエンコーダ閉ループ位置決め（10-31）

日付：2026-10-30 ~ 2026-11-01（リポジトリ作成時間）　ソース：リポジトリ：NS800RT7P65D FOC と CANopen

納芯微 NS800RT7P65D はデュアル Cortex-M7 のモータ制御チップで、このプロジェクトはそれを2つの論理 CPU に分割する：1つは 20 kHz の ADC サンプリングと PWM を実行し、センサレス FOC、滑模観測器と PLL 推定を行い、ハードウェア遮断を備える；もう1つは UART と FinSH、CANopenNode v4.1 と CiA 402 ブリッジ、CAN 送受信を実行する。クロスコアは非同期コマンドメールボックスと6フィールド、24バイトの一貫性スナップショットのみを通し、共有メモリの無秩序な読み取りは行わない。基盤は RT-Thread 5.3.1 の SMP 設定である。

インフィニオン PSoC Edge E84 上の EdgeDoctor-RT は別の道を進む：20ミリ秒ごとに振動データブロックを処理し、1秒のスライディングウィンドウで64次元の周波数帯特徴を抽出し、64-32-5 の MLP に送って正常、軸受内輪故障、軸受外輪故障、ミスアライメント、アンバランスの5類状態を判定し、信頼度と処置提案を出す；ベースラインは公式の Edgi_Talk_M55_XiaoZhi v1.4.0 で、アプリケーション層のみを重ね、起動、リンク、HAL、Wi-Fi リソースは変更しない。

2例の運動制御作品はコンテスト用ボードのdownstream度合いをよりよく示している：NXP FRDM-MCXA346 上の1つはステッピングモータの閉ループ位置決めを行い、エンコーダフィードバックに Python と Tkinter の上位機を加え、10度と90度の位置決め、相対反転45度とソフトウェアゼロ点への復帰を実行する；もう1つは超音波障害物回避と煙検出の検出カーで、視覚認識は PC 側に置く。

プラットフォーム分布は特筆に値する。Titan Board Mini と MC632X が各2台、PSoC Edge E84 が1台、NS800RT7P65D が1台、FRDM-MCXA346 が2台で、大会ボードリストの5機種をカバーしている。

6. 今期のトレンドと総括

6.1 トレンド：マージ側は静か、パッチ側は密、RT-Smart の境界が体系的に清算されつつある

今期の72時間、メインリポジトリのマージはわずか2件（10-30 10:54 の dlmodule 修正、18:20 の clang-format 再整列）だったが、新規提案は11件、新規欠陥は3件で、すべて 10-30 から 11-01 に集中している。週末の調査期間は「マージ少・コミット多」が常態であり、見るべきは数ではなく着地点である。

第一条の線はエンジニアリング基盤。clang-format のバージョン固定が解決するのは、同一コードが異なるマシンで異なるフォーマット結論になる問題。バージョン管理 CI とリリースフローが解決するのは、ベースラインのドリフト、Z と Y のリリース境界の不明確さ。いずれもカーネルロジックを一行も変えないが、その後のすべてのパッチが安定してレビューできるかどうかを決める。前号で lwp の1万1千行の単一ファイルを20ファイルに分割したのも同じ道筋である。

第二条の線は RT-Smart のユーザー空間境界。端末 ioctl、ブロックデバイス ioctl、pipe ioctl、mailbox オブジェクトポインタ、四つの問題の形は一致している。fops とシステムコール層が「引数はすでにカーネルアドレス、オブジェクトはすでにカーネルオブジェクト」という古い前提を踏襲しているのだ。報告者は導入コミットを 2022-12-03 の ecf2d8215961 まで遡っており、これは新コードがもたらしたリグレッションではなく、この境界が成立して以来系統的な検証がなされていないことを示す。進行中のパッチは poll と epoll のカウント回り込み、sigaction のシグナル番号、ELF セグメント保護と静的 TLS をカバーしており方向は正しいが、mailbox と pipe の2件はまだ担当者がいない。

第三条の線はエコシステム側の表現方法。公式ニュースインターフェースは6月17日で止まって以降すでに6か月目に入り、対外発表はメディアコラムが担うようになった。コミュニティの活発度は明らかに「作品」へ移っている。ある週末には7つの大会作品が GitHub にオープンソース化され、5つがエッジ AI ビジョンと診断、2つがモーターとモーション制御に分類された。RT-Thread の実装に関心を持つ人にとって、この一連のリポジトリは公式通稿よりも、ボードベンダーと開発者が何に使っているかを雄弁に物語る。
