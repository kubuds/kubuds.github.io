1. カーネルとドライバのマージ

1.1 RISC-V APLIC：レベル割り込み取消後に MSI を再送しない（11-10）

日付：2026-11-10 16:58（マージ時間）　出所：提案 #11966

1ファイル、14行追加、1行削除、変更箇所は libcpu/risc-v/common/pic/pic-riscv-aplic.c、作者 zijunteng238-dot、11月1日提出、本期マージ。前回レポートの審査待ちキューでこの件を名指ししたが、本日着地。

現象は QEMU 8.2.2 上で bsp/qemu-virt64-riscv を実行：RV64、4コア SMP、AIA（APLIC/IMSIC）有効、1000ミリ秒ごとに1回プリントするカウントプログラムが RISC-V test: 0 だけ出力して停止。根本原因はレベル割り込みの EOI パス——ドライバが無条件に setipnum_le を書き、デバイスは実際に割り込みを取消しているのに、旧版 QEMU がこの書き込みに基づき MSI を再送し、持続的な偽割り込みが発生、システムタイマーを圧迫し、遅延スレッドが二度と戻れなくなる。修正方法は EOI 時にまず in_clrip の該当入力の整流状態（割り込み極性で換算済み）を読み、デバイスがまだハイを駆動している場合のみ setipnum_le を書く。これによりレベル割り込みの再トリガ能力を保持しつつ、取消済みのソースに再送の機会を与えない。

同一提案で qemu-virt64-riscv の main.c を1回プリントから0〜9のカウントループに変更、各プリント後1秒遅延、修正後のスレッド復帰を観察。検証は3構成：AIA 有効4コアでネットワーク/NVMe/virtio-console/PCI serial 無効、AIA 無効4コア、AIA 有効4コアデフォルトデバイス構成、三者とも10行完全出力；実 APLIC ハードウェア、低レベル外設、他 QEMU バージョンは未検証。

QEMU 上流は既にこの模拟欠陥を自行修正済み、RT-Thread のこの件は旧版エミュレータへの互換パッチ——修正するのはカーネルロジックエラーではなく、「ドライバが仕様通り書き、エミュレータが欠陥通り解釈する」という仮想プラットフォームのみで発生する不整合である。

2. セキュリティ強化バッチ：1日11件の境界チェック

2.1 6件の2024年 CVE を集中収束（11-10）

日付：2026-11-10 01:04 ~ 06:45（提案時間）　出所：提案リスト

11月10日1日のうちに、同一報告者（cms19859230182-lang）が11件の境界チェックパッチを提出、うち6件は2024年開示の CVE に直接対応、番号は隣接、修正方法は同構——いずれも「まず長さを判定し、それからコピーに入る」：

  • 提案 #12017：FinSH のディレクトリパス結合に境界なしの rt_sprintf / rt_strcpy / strcat を使用しており、自動補完は DFS_PATH_MAX に基づいて再割り当てし各セグメントのコピーに上限を設定、長さ判定を > から >= に戻す（NUL の差一を補う）。CVE-2024-25390、議題 #8286 に対応。
  • 提案 #12020：rt_wlan_send_to_thread() の len は符号付き int であり、負値の場合 sizeof + len と memcpy が巨大な size_t として処理される。len < 0 の場合は直接 -RT_EINVAL を返すよう変更。CVE-2024-25388、議題 #8285 に対応。
  • 提案 #12022：rt_random は予測可能な LCG でありデフォルトシードも弱い。初回読み取り時に rt_tick_get() とオプションのハードウェア乱数源を混入し、コメントと Kconfig に非 CSPRNG であることを明記。CVE-2024-25389、議題 #8283 に対応。
  • 提案 #12019：var_export が ve_exporter_tab[2048] を埋める際に容量制限がなく、生産ビルドでアサーションが無効化されるとそのまま書き込み超過が発生する。満杯で停止、実行時にカウントをクランプ、ゼロ要素はバブルソートに入れないよう変更。CVE-2024-25392、議題 #8290 に対応。
  • 提案 #12018：rt-link はフレーミング前に最終フレーム長を検証せず、超過载荷が静的 sendbuffer に書き込み超過する。先に data_len とフレーム長を判定してから memset/memcpy するよう変更。CVE-2024-25395、議題 #8289 に対応。
  • 提案 #12021：YMODEM の _rym_send_begin が境界なしの rt_sprintf でプロトコルバッファに書き込み、アップロード・ダウンロードで rt_strncpy(..., DFS_PATH_MAX) を使用すると NUL が補われない可能性がある。rt_snprintf で上限を設定し、上限を sizeof-1 として明示的にゼロ埋めするよう変更。CVE-2024-25394、議題 #8291 に対応。

六件の共通点は「アサーションを境界として使う」ことにある：RT_ASSERT は生産構成ではしばしば無効化され、これまで複数箇所でアサーションを最後のチェックとして扱っていたが、実際にはチェックが存在しないに等しかった。この一連の変更では制限を実行時判定に改め、アサーションはデバッグ補助としてのみ残す。

2.2 ローダとカーネルオブジェクト：libdl 再配置、LWP IPC 所有者検証（11-10）

日付：2026-11-10 01:40 および 01:36（提案時間）　情報源：提案 #12016、提案 #12015

これは今回のバッチで技術的に最も重要な二件であり、いずれも信頼境界を変更するものである。

#12016 は五つのファイルを変更し、205 行追加、37 行削除。dlmodule は再配置の書き込み先を計算する際に mem_space + r_offset - vstart_addr を使用し範囲を検証しないため、細工された .mo により r_offset がアンダーフローまたはオーバーフローし、再配置段階でカーネルメモリに直接書き込まれる可能性がある。修正方法は dlmodule_check_rel_target() を新設し、オーバーフロー防止の算術で対象区間がモジュールメモリ内に収まることを確認、ARM、RISC-V、x86 の三つの再配置器に組み込む。同時に ELF セクションヘッダインデックス（sh_link、e_shstrndx）、シンボルテーブルインデックス（ELF*_R_SYM）と ET_REL セクション境界チェックを補完し、dlelf.c が失敗時にロードを中止して section_load_addr を解放するようにした。10 月 18 日の欠陥 #11898 に対応。

#12015 は3ファイルの変更、284行の追加、44行の削除。RT-Smart の LWP IPC システムコールは以前、ユーザーが渡した裸のオブジェクトポインタをそのまま rt_sem_* / mutex / event / mailbox / mq / timer に渡しており、偽のオブジェクトだけで任意のカーネル読み書きが可能だった。修正方法は lwp_user_object_get() と lwp_user_object_put() を新設すること：参照解決の前にユーザー空間アドレスを拒否し、ハンドルが呼び出し元のユーザーオブジェクト AVL ツリーに存在することを要求し、rt_object_get_type() を照合し、システムコール全体（すべてのエラー経路を含む）を通じて1つの参照を保持する；lwp_ref_count は所有者と処理中の参照の両方をカバーし、カーネルオブジェクトは最後の参照が消えるまで破棄されない。これは10月31日の欠陥 #11960 に対応する。

いずれも攻撃サンプルは構築されておらず、検証は静的監査とコンパイル段階にとどまっており、これが短期的に release に入らないことを決定づけている。

2.3 メモリとネットワーク：メモリプールのアサーション誤検知、DHCP リースの期限切れ回収（11-10）

日付：2026-11-10 01:04 と 06:45（提案時間）　情報源：提案 #12014、提案 #12024

#12014 が修正したのは誤警報だが、引き起こされたのは実際のシステム停止である：rt_smem_free() が「最後のブロックで、その next が heap_end センチネルを指す」ブロックを解放する際に MEM_POOL アサーションを誤って発火させる。修正方法は mem->next == heap_end というオフセットを明示的に受け入れ、それ以外の場合は従来の検証を維持する；作者は mem->prev による判定への変更を明確に拒否しており、その理由は prev が前のブロックを指し（先頭ブロックは0）、検証を緩めてしまうからである。付随する core.mem テストケースは使用ビットのみが残ったセンチネルシナリオをシミュレートし、ブロック全体の結合を検証する。これは2025年の旧欠陥 #10632 に対応する。

#12024 が修正したのは DHCP サーバ側のアカウント期限である：lease_end は書き込まれた後まったく読まれず、リースは永久に期限切れにならず、アドレスは永久に回収されない；さらに DHCP_DEFAULT_LIVE_TIME（0x80510100）が PP_HTONL() を経てオンライン上では約68年となり、「日単位で回収」というセマンティクスと完全に一致しないことが判明し、合わせて86400秒に変更された。変更によりリースは絶対失効時刻に変わり、割り当て前に期限切れノードを遅延回収し、ヒット・新規作成・ACK の3経路で統一的にリースを更新する。検証は lwIP 2.0.3 / 2.1.2 / 2.2.1 の3バージョンの構文チェックのみ行われた。

これは「設定定数の方向が間違っている」典型例である：マクロ名は生存時間を意味するが、値はナノ秒級の数値を秒として使っており、問題が起きないのは誰も実際に期限切れを待たないからにすぎない。

3. 議題と修正のクローズドループ

3.1 ptyfs ハンドルリーク：報告当日に修正（11-10）

日付：2026-11-10 14:04（議題）/ 11-11 02:14（提案）　情報源：欠陥 #12023、提案 #12029

ptyfs_unregister_pts() は pts ファイルをルートリンクリストから外し、ユニット番号を回収するが、ptyfs_register_pts() が割り当てた struct ptyfs_file を解放しない。ユニット番号が再利用された後、/dev/pts/* を繰り返し open() / close() することで継続的にメモリがリークし、一般ユーザーでもトリガーできる。報告者 XueDugu はループ再現を添付した。

12時間後、メンテナ BernardXiong が #12029（3ファイル、11行の追加、2行の削除）を提出し、登録解除経路で pts ファイルも合わせて解放する。現在レビュー待ちである。これは本期唯一の「報告と修正が同一ウィンドウでクローズドループした」項目である。

3.2 legacy USB host：修正がメンテナンスポリシーによりクローズ（11-10）

日付：2026-11-10 18:13（提案）/ 11-11 00:50（議題）　情報源：欠陥 #12026、提案 #12027

欠陥が記述しているのは旧 USB ホストスタック（components/legacy/usb/usbhost/）である：デバイスディスクリプタの bLength が検証されずに読み取り長として使われ、さらに静的なデバイス配列に書き込まれるため、悪意のある USB ペリフェラルが境界外書き込みと制御フローハイジャックを引き起こせる。報告者は qemu-virt64-aarch64 上でエンドツーエンドに再現し、メインリポジトリ master（自己申告 v5.4.0-dev、コミット 5d1fb66d で確認）が11月11日の再読時点でも未修正であることを注記した。

メンテナはその後 #12027（1ファイル、8行追加）を長さ検証のために提出し、すぐに自らクローズして次のようにコメントした。「これは legacy のコードであり、今後継続的な修正・メンテナンスは行わない。」修正の方向性に議論の余地はなく、クローズの理由はメンテナンス範囲である——この経路上の既知の攻撃面は、今後利用者自身が評価する必要がある。

3.3 vDSO クロック定数：議題は成立、修正方法は否決（11-10）

日付：2026-11-10 20:39（議題）　情報源：欠陥 #12025、提案 #12028

newlib ツールチェーンで RT-Smart の vDSO ユーザーコードをコンパイルすると、CLOCK_MONOTONIC と GNU 系クロック ID がいずれも未定義となる。newlib は前者を _POSIX_MONOTONIC_CLOCK の下でのみ、後者を _GNU_SOURCE の下でのみ公開するが、vDSO の自由コンパイル設定ではどちらも設定されていない。提案 #12028（1ファイル、22行追加）はローカルでの定義追加を選択したが、メンテナは「これは誤った修正であり、クローズすべき」と判断し、当日クローズした。

同じ現象に対する2つの処理方法の相違は明確である。1つはコンパイル単位にマクロを追加してビルドを通過させる方法、もう1つは自由コンパイル設定を POSIX 機能マクロに整合させる方法である。後者は提案に盛り込まれず、欠陥自体は依然オープンのままである。

4. エコシステムとベンダー適応

4.1 ESP32-S3 移植の半端な着地：ビルドスクリプトはリポジトリ入り、BSP はリポジトリ内に無し（11-10）

日付：2026-11-10 11:53（マージ時刻）　情報源：提案 #11844、bsp/ESP ディレクトリ

誤読されやすいマージである。提案 #11844 のタイトルは「xtensa_context.h のインクルードパスの修正」だが、本文には bsp/ESP/ESP32_S3 と libcpu/xtensa/esp32s3 の2ディレクトリの新規追加が書かれている：ESP32-S3-DevKitM-1、Xtensa LX7、UART0 は GPIO43/44 経由、8MB DIO flash、アプリは 0x10000、CI に xtensa-esp32s3-elf GCC 12.2.0 を追加。

実際にマージされたのは1ファイルのみ：libcpu/xtensa/esp32s3/ ディレクトリ下の SConscript、25行である。メインリポジトリの bsp/ESP ディレクトリを確認すると、現在は ESP32_C3、ESP32_C6、libraries、tools の4項目のみで、ESP32_S3 は無い。libcpu/xtensa/esp32s3 下もこのスクリプト1つのみで、C ソースファイルは一切無い。スクリプト自体は bsp/ESP/ESP32_S3 を基に ESP-IDF ソフトウェアパッケージのパスを解決するが、そのパスは現在存在しない。

つまりこれは半分の移植である：CPU ポートのビルド足場だけが先にメインリポジトリに入り、BSP、ティック処理、sdkconfig、ボードレベルの検証はいずれも無い。提案は9月28日に作成され、11月10日にマージされたが、6週間の間に本文が記述する残りの部分は一緒に着地しなかった。利用者にとっての現実的な意味は、現時点でコンパイル可能な ESP32-S3 BSP は入手できず、スクリプトが参照するパスは当面解決できないということである。

4.2 packages とツールチェーンリポジトリは今期プッシュ無し（11-11）

日付：2026-11-11（確認）　情報源：RT-Thread org リポジトリ

35の組織リポジトリをプッシュ時刻順に並べると、期間内にプッシュがあったのはメインリポジトリのみ（11-10 16:58）。packages の最終プッシュは11月9日 10:27（前号で収録した WCH SDK 同期）で、env は 11-06、sdk は 11-05 で停止しており、rtthread-nano、smart-build、pkgs-test、toolchains-ci などはいずれも動きが無い。ソフトウェアパッケージインデックス側は本日ゼロ変化であり、前号のペアマージのリズムとは異なる。

5.2 Google News 3日間の調査期間でゼロヒット：チャネルは正常、確かに新規記事無し（11-11）

日付：2026-11-11（検証）　情報源：Google News

時間フィルタ付きの3組のクエリ（RT-Thread when:3d、睿擎派 when:7d、RT-Thread 嵌入式 when:7d）はすべてゼロヒット。 「チャネル障害」と「確かにニュースなし」を区別するため、別途2組の素のクエリで対照を実施：RT-Thread は時間フィルタなしで42件を返し（最新は11-03の烏鎮サミット稿で、すでに収録済み）、RISC-V when:1d は当日のニュース8件を返した——チャネル自体は正常であり、RT-Threadはこの3日間に確かに新規稿がインデックスに入っていない。

HN Algoliaの7件の候補はすべて “thread” の文字通りの誤マッチ（スレッドUI、free-threaded Python、HN討論スレッド推薦ツール）であり、RT-Threadとは無関係で、すべて除外済み。

6. 総括とトレンド観察

6.1 セキュリティ審査が個別案件からバッチへ

日付：2026-11-10　情報源：提案リスト

調査期間内の新規提案14件のうち、11件が同一の報告者によるもので、しかも11月10日早朝の5時間余りに連続してコミットされている。題材は散発的な発見ではなく、モジュール別にスキャンしたリストである：FinSH、WLAN、乱数、var_export、rt-link、YMODEM、libdl、LWP、メモリプール、DHCP、ESP32-C3。いずれも「動機 / 変更 / 検証」の三段構成で、検証の口径は静的チェックとコンパイルに統一され、「PoC未構築」と正直に注記されている。

この形態は散発的なセキュリティ課題とは異なる：むしろ計画的な監査の総仕上げのようであり、長年蓄積された低リスク項目を悪用可能性で並べ替えた上で、一つずつ補っている。プロジェクト側にしてみれば、代償はレビュー待ちキューが一日で九件増えたことであり、すべて人手によるレビューが必要となる。

6.2 六件のCVEと二年半のタイムラグ

日付：2026-11-10　情報源：CVE-2024-25388 等対応課題

六件のCVEに対応する元の課題番号は #8283 から #8291 の間にあり、2024年の報告バッチに属し、今日までに補完されるまで約二年半を要した。これは必ずしも怠慢とは読めない：RTOSプロジェクトのレビュー資源はチップ適配とリリースに集中しており、誰かがリストに従って振り返りスキャンしない限り、この種の「畸形入力を構築しないと触发しない」項目はキューの底に沈み続ける。

本当に記す価値があるのは修正方式の一貫性である——六件はいずれも同じ穴を補っている：アサーションを境界として扱うこと。アサーションがプロダクションビルドで無効化されることは、組み込みプロジェクトでは誰もが知っているが、それをチェック用に使うコードがまだ規模として存在している。

6.3 レビュー待ちキュー 提案149件、課題365件

日付：2026-11-11（検証）　情報源：提案リスト、課題リスト

前回の提案140件、課題362件と比較して、提案は九件増、課題は三件増。構成は明快である：調査期間内に2件のマージ、14件の新規提案、2件のコミット後クローズで、純増九件；課題側は四件増（ptyfs、USB host、vDSO、PLIC次序）で、うち一件は前回収録済みのPLIC課題のフォローアップによるもの。

前回指摘した幾つかは依然マージされていない：tty ioctl ユーザポインタ検証（#11937、v5.1.0以降すべてのRT-Smartボードに影響、リスク最高）、ivshmemウィンドウ検証（#11993）、RISC-V FPUコンテキスト（#12006）、CANドライバ再構築（#11779）。本日追加の #12015 と #12016 はちょうど #11960 と #11898 の二つのカーネル級リスクをカバーしているが、いずれもまだ審査中である。

6.4 修正が方針によりクローズ：legacyコードの境界

日付：2026-11-10　情報源：提案 #12027

本期には維持管理者本人がコミット後に当日クローズした提案が二件あり、理由はいずれも技術的に成立しないわけではない：一件は修正方向が誤り（vDSO補宏）とし、一件はこのコードが保守対象外の状態に入った（legacy USB host）とする。後者の方が注目に値する——欠陥の記述には「悪意あるUSBペリフェラルが越境書き込みと制御フロー奪取を引き起こしうる」と明記されており、これは物理的に接触可能な攻撃面である。

二十年を歩んだRTOSは必然的にlegacyコンポーネントを背負うものであり、保守しないと宣言することは合理的な資源判断である；しかし RT_USING_USB_HOST の旧スタックを使い続けている製品にとって、この宣言はセキュリティ責任を集成側に移すことに等しい。プロジェクト文書にこの種の「保守しないがツリー内に残る」コンポーネントを一覧化できれば、個々の提案コメントに散らばっているより有用であろう。
