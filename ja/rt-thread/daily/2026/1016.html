1.1 カーネルとドライバ修正のマージバッチ：ofw ハッシュテーブル境界外修正と N32 タイマー補完が確定（10-15）

日付：2026-10-15 13:32 ~ 13:50（マージ時間）　出典：PR #11845、PR #11812

メンテナは期間内に2件のコミュニティ修正をマージした。1件目はデバイスツリー ofw 修正（#11845、1ファイル +4/-2、メンテナ Rbb666 がマージ）：phandle ハッシュテーブルの2箇所の境界外の潜在的リスクを修正——割り当て数を max-min から max-min+1 に変更（検索インデックスは phandle-min であり、phandle が範囲上限を取る場合、元々は割り当て領域外にアクセスしていた）、拡張時のクリアを旧テーブル項目数に従い旧テーブル末尾から起算するよう変更（元の実装は開始値を減算しておらず、開始 phandle が1でない場合にクリア位置が不正確だった）；作者は6組のテストケースで GCC 下、ASan/UBSan による関数レベル検証を実施。2件目は N32 タイマー補完（#11812、39ファイル +3956/-105）：N32H47x_48x と N32H49x に、これまで欠落していたクロックソースと ATIM/GTIM/BTIM インスタンステーブル分岐を補充（両シリーズは drv_tim.c を共用するが、これまでは H7xx 分岐のみ実装）、LPTIM tick を実際の LSI に基づき導出するよう変更、PWM とパルスエンコーダを同期して拡張、3つのボードに対応するドライバ機能宣言に実際にコンパイルされる ci-attach エントリを追加、#11800 を引き継ぐ。

日付：2026-10-15 13:04 ~ 13:28（コミット / マージ時間）　出典：PR #11815

1.3 9PFS が2件の欠陥を連続露呈：ARMv7-A の非アライメントアクセスによるカーネルアボート、getdents の境界外読み取りが再現確認（10-15）

日付：2026-10-15 20:33 ~ 21:18（コメント / 作成時間）　出典：Issue #11868、Issue #11289

貢献者 XueDugu は調査期間内に 9PFS ファイルシステムの欠陥 2 件を進展させた。その一つは新規起票の欠陥票 #11868 である。受信パスの 64 ビット値取得マクロが通常のポインタでバッファを逆参照し（get_rx_value64_of）、ARMv7-A 上で GCC が生成する LDRD は 8 バイトアライメントを必要とするが、構造体サイズ 292 とプロトコル定数 42 により rx_buffer+42 は常に 6 mod 8 となる——いかなる Tstat 応答（完全に正常な応答を含む）も dfs_9pfs_open / dfs_9pfs_stat でアライメント例外を引き起こし、カーネル data abort を発生させる。報告では 2025-12 に 9PFS を導入したコミットを特定し、CVSS 3.1 7.5（リモート拒否サービス）の評価と QEMU vexpress-a9 による完全な再現チェーンを示し、逆アセンブルと addr2line による検証を添えている。もう一つは 3 月に起票された #11289（getdents パスがサーバから送られた stat/name 長を信頼することで範囲外読み出しが発生）で、10-15 夜間にコミュニティが master（bsp/simulator + ASan）での再現を確認し、根本原因は受信バイト数が破棄され記録境界が検証されていないことである。両案ともオープンを維持している。

1.4 新提案：DFS 層 F_GETFL/F_SETFL とデバイス制御コマンドの衝突コード曖昧性解消（10-16）

日付：2026-10-16 00:51（作成時間）　情報源：PR #11869

貢献者 CXSforHPU が DFS 層の曖昧性解消提案を起票した（2 ファイル +56/-15）：POSIX の F_GETFL(=3)/F_SETFL(=4) と RT-Thread の RT_DEVICE_CTRL_CONFIG(=3)/RT_DEVICE_CTRL_CLOSE(=4) が数値的にコード衝突し、両コマンドセットが同一の整数引数を共有するため、fcntl パス下でドライバが誤解釈する可能性がある——dfs_v2 の ioctl は純粋なパススルーであり、シリアルなどのドライバは LWP クローズ時に F_GETFL を CONFIG とみなしてハードウェアを再設定することさえある。提案はコマンドエンコーディングを変更せず、引数の形態による曖昧性解消に切り替える：コマンド 3 は引数付きでドライバへ転送し、引数なしで POSIX に従いファイル状態フラグを返す。コマンド 4 は引数なしでドライバへ転送し、引数付きで上位層の設定を通す。dfs_v1 と dfs_v2 の両世代実装を同時に改修し、socket 通知パスを保持する。

1.5 審査中提案のレビュー：ESP32-C6 SPI に 3 件の行レベル意見と作者による逐条回答（10-15）

日付：2026-10-15 13:38 ~ 16:30（レビュー / 回答時間）　情報源：PR #11846

ESP32-C6 SPI サポート提案（#11846）はメンテナ Rbb666 から 3 件の行レベルレビュー意見を得た：其一、DMA を無効化した後 IDF の単一転送上限は 64 バイトであるが、ドライバは依然としてパケット全体を送信するため、65 バイトのメッセージは中止を引き起こす。分割転送か、少なくともエラーコードを返すべきである。其二、C3/C6 が ESP-IDF-latest を共有する場合、C6 をビルドすると gdma.c が恒久的に 4 引数呼び出しに書き換えられ、その後 C3 をビルドすると引数が多すぎるエラーが発生する。ターゲットマクロまたは独立コピーに切り替えるべきである。其三、ビット幅検証がバス初期化成功後に発生するため、16 ビット要求が失敗した後 8 ビットで再試行するとバスが既に初期化されているため中止される。まず検証してからリソースを要求すべきである。作者は逐項改修することを回答した（ドライバ内での分割送信、ターゲットマクロによる 2 セットの呼び出し保持と双方向ビルド検証、ビット幅検証の前倒し）。またビルドスクリプト内の書き換えロジックの削除に同意した。

1.6 審査中討論：aarch64 GIC 応答パスの去就論争が深まる（10-15）

日付：2026-10-15 13:57 ~ 19:39（コメント時間）　情報源：PR #11860

aarch64 GIC 修復提案（#11860）は調査期間内に深い技術討論が出現した：作者 Xenithya は削除したものが EOI 前の余分な GICD_ICPENDR の pending クリア書き込みであると説明——割り込み処理中に同じエッジソースが新イベントを再現する場合（同氏の NPU シーン：先に AXI エラー次に完了を報告など）、この書き込みが再ラッチされた pending を消し去り、新たな割り込みを永久に損失させる。実測データも示した：この書き込みを保持すると約 19~33 回の推論で必ず一度完了割り込みの損失が発生し、削除後は純粋な割り込みパスで 48 万回の推論がゼロ失敗である。メンテナ GuEe-GUI が二度回答した：本関数のセマンティクスは GIC の非 EOI モードで理解する必要があり、問題は traps.c の割り込み応答インターフェースの呼び出し方にある可能性もある。trap パスの改修を同期検証することを提案する。提案はオープンを維持している。

3.1 コミュニティプロジェクト：思澈 SF32LB525（黄山派）ボード上の FreeDOS 移植リリース（10-15 ~ 10-16）

日付：2026-10-15 22:11 ~ 2026-10-16 03:08（コミット時間）　情報源：equence/sf8086

コミュニティ開発者が移植プロジェクト sf8086 をリリース：8086tiny エミュレータを RT-Thread ベースの思澈科技 SiFli SF32LB525（黄山派、Cortex-M33）開発ボードに移植し、ボード上で FreeDOS を直接実行——BIOS、起動フロッピー、Turbo C 2.01 コンパイルツールチェーンがすべてファームウェアに常駐し、外部ストレージに依存しない；A: ドライブは毎回起動時にフラッシュから再構築される RAM ディスク（約 144 KB 利用可能）で、EDIT、DEBUG、ZIP などの DOS ツールを実行可能；RT-Thread shell と DOS コンソールは UART1 を共用（シリアル仲裁、ターミナルキーマッピングなどの適配コミットを含む）。プロジェクトは調査期間内に 13 筆のコミットをプッシュ、MS-DOS 6.22 起動ディスク構築スクリプトとボード上実行スクリーンショットを含み、リポジトリには rt-thread、sifli、sf32lb525、freedos などのトピックが付与されている。
