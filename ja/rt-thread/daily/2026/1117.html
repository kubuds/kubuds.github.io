1.1 ptyfs 登録解除時にファイルオブジェクトを解放せず：2万回の開閉で露呈した1件のリーク（11-16）

日付：2026-11-16 11:29（マージ時間）　出典：提案 #12029、欠陥 #12023、コミット 7c974b59

この欠陥のタイトルは本文よりも率直に書かれている：ptyfs の登録解除時にあの pts ファイルオブジェクトを決して解放せず、非特権の open/close ループだけでカーネルメモリを枯渇させシステムをクラッシュさせることができる。報告時刻は11月10日午後で、報告者はこの一連の監査で一貫した書き方を踏襲した——まず影響を受けるバージョン区間を示し、次に導入点を示す。

区間は v5.1.0 から master まで。導入点は2024年3月28日の 83e95bdf で、提案 #8672 に由来し、その後 v5.1.0、v5.2.0、v5.3.0 と master 上で個別に検証済みで、いずれもこの欠陥を持つ。再現環境は QEMU の qemu-virt64-aarch64、公式デフォルト設定（ターミナルと ptyfs は RT_USING_SMART 下で組み込み）、公式 CI の musl ツールチェーン gcc 7.3.0 と scons と明記されている。

メンテナは当日夕方に機序を確認した。登録解除関数 ptyfs_unregister_pts() は pts をルートリンクリストから外し、その番号を回収するだけで、struct ptyfs_file は決して解放されない。修正提案 #12029 はそこで1行の解放を補うだけでなく、このライフサイクルを完成させる——オブジェクトを解放し、pts_unit を -1 に初期化し、lwp_tty_create() の失敗パス上の解放順序を修正し、lwp_tty_delete() で未登録のデバイスをスキップし、無闇に rt_device_unregister() を呼ばないようにする。

変更は3ファイルにわたり、60行追加、6行削除。3つの点がそれぞれ一段を担う：ptyfs.c が主修正（+51/-4）、tty_pts.c と tty_device.c が配套（+3/-1、+6/-1）。11月10日夕方に提出され、11月16日午前11時29分にマージ、欠陥は同じ分にクローズされた。

検証データは多くのレポートより確実だ。qemu-virt64-aarch64、RT-Smart が ptyfs をサポートし、/dev/pts/ptmx に対して2万回のオープンとクローズを実行した。修正前は利用可能メモリが 245164 KB から 237932 KB に減少し、7232 KB 減、1回あたり約 369 バイトに相当する。修正後は 245156 KB から 245116 KB となり、40 KB の正常な変動のみが残った。2万回で既に 7 MB であり、このレートで数千回、数万回のループを繰り返せば、245 MB を食い尽くすのは時間の問題だ。

メンテナ自身も境界を明確にしている。OOM パスを強制的に通しておらず、非特権プロセスでそのループを単独実行してもいない。この2点は残されており、この修正の既知のギャップと見なせる——缺陷タイトルで名指しされた「非特権」は、検証では実際には欠けている。

1.2 ivshmem 共有メモリウィンドウ：デバイスが決める物理アドレス（11-16）

日付：2026-11-16 10:47（マージ時間）　情報源：提案 #11993、缺陷 #11992、コミット 43791bbf

同日午前のもう一件は、問題の性質がより硬い。ivshmem の PCI プローブは BAR2 が欠落している場合に JailHouse 互換のフォールバックを通り、デバイスの PCI 設定ワード 0x40 から 0x4f にある共有メモリのアドレスとサイズを直接コピーする。PCI コアはこの2つの値を検証せず、rt_ioremap() は与えられたものをそのままマップする。結果として、悪意のある、またはフォーマットが乱れた ivshmem デバイスにより、カーネルが任意の物理ウィンドウをマップでき、カーネル自身の RAM も含まれ、さらに /dev/ivshmemN を通じてユーザー空間に露出され、非特権プロセスによるカーネルメモリへの任意の読み書きが形成される。

修正は4本同時に投入される。第1条が最も本質的だ。その JailHouse フォールバックは新設の RT_IVSHMEM_JAILHOUSE オプションが有効な場合のみ利用可能で、デフォルトでは無効、ヘルプテキストには「デバイスが信頼できることを要求する」と明記され、このオプションを有効にしなければ正当な BAR2 が必須となる。第2条はマッピング前にウィンドウを検証する——サイズが非ゼロ、アドレスにオーバーフローなし、範囲全体がネイティブポインタとサイズ型で表現可能。第3条は4つの設定ワードを64ビットのローカル変数に読み込み、shmem と shmem_size フィールドの32ビットエイリアス経由で書き込まないようにし、これにより32ビットビルドで隣接フィールドを壊す古い問題も併せて修正される。第4条は設定空間読み取りの戻り値のチェックだ。

規模は122行追加、7行削除、2ファイル：ivshmem.c（+110/-7）と新しい Kconfig（+12）。提案は11月5日に提出され、11月16日に別のメンテナ Rbb666 によってマージされ、その間11日間であり、最近の監査ラインの中ではレビューが比較的遅い案件に属するが、PCI とメモリマッピングを動かすことを考慮すれば、このペースは合理的だ。

検証はコンパイル段階までのみ：変更ファイルは clang-format 22.1.8 を通過し、qemu-virt64-aarch64 は RT_IVSHMEM_JAILHOUSE の無効と有効の両構成でコンパイルでき、完全なビルドは CI に委ねられる。この種の変更に実行時テストケースがないのは常態だが、「歴史的な互換パスをデフォルトで無効にする」という動作は、長さ検証を1つ補うよりも記録に値する——不安全な選択をデフォルト動作から明示的なスイッチへと格下げしている。

2.1 iso9660 ディレクトリ名長のアンダーフロー：報告と修正が同日到着（11-17）

日付：2026-11-17 01:46 から 02:03（議題と提案）　情報源：議題 #12061、提案 #12062

午前2時前後の一件は、本期で最速のペースだ。1時46分、同一位置の報告者が議題 #12061 を提出した：ISO9660 ディレクトリレコード解析において、namelen はメディアから直接来ており検証されていない。非ディレクトリレコードは無条件に ";1" バージョン接尾辞を除去し、namelen が0または1の場合、rt_size_t が減算でアンダーフローし、続く rt_strncpy() が境界外書き込みとなり、1回の getdents や ls が無制限のカーネルメモリゼロクリア書き込みに変わる。

影響範囲は控えめに書かれている：v5.2.0 から v5.3.0 および master、11月17日当日に確認。導入点は 42a41c69（2024年11月22日、提案 #9592）で、v5.2.0 で初回リリースされたため、v5.1.0 以前は影響を受けない。再現環境は QEMU virt、Cortex-A、GICv2 で、2048バイトブロックの NVMe デバイスを搭載する。

17分後、メンテナは修正提案 #12062 をコミットした。namelen をローカル名バッファが収容できる範囲に制限し、namelen が2以上の場合にのみバージョン接尾辞を剥離する。11行追加、2行削除、1ファイル。提案本文には検証の程度も明記されている。RT_USING_DFS_V1 と RT_USING_DFS_ISO9660 を有効にした qemu-virt64-riscv 上でのみコンパイルとリンク（scons -j8）を行い、ブロックデバイスを用いた実行時再現は行っていない。同一パーサ内の他のレコード走査における境界問題はこのコミットの範囲外である。

これは今期で最も対比すべき時間差の箇所である。3月から5月の一連の報告では、提起から提案までにしばしば数週間を要した。このコミットは17分だった。同一箇所の問題、同一箇所の修正で、速度が変わった。

2.2 三件の旧件に CVE 番号を付与（11-16）

日付：2026-11-16 11:17 から 11:21（コメント時間）　情報源：イシュー #11271、イシュー #11298、イシュー #11332

午前11時17分から11時21分の間に、同一の場所で既にクローズされた3つのイシューのコメント欄にそれぞれ番号が1件ずつ補足された。GPT パーティション項目のアンダーフロー（ending_lba が starting_lba より小さいことでアンダーフローしたパーティションサイズを生成）には CVE-2026-38160 が付与され、当該イシューは11月4日にクローズされた。FinSH プロンプトのディレクトリ名を経由したフォーマット文字列インジェクションには CVE-2026-50961 が付与され、4月9日にクローズされた。AT socket パーサがユーザー制御可能な数値ホスト名を受け入れることでカーネルスタックオーバーフローを引き起こす問題には CVE-2026-106729 が付与され、9月21日にクローズされた。

これら3件はいずれも新規の修正ではなく、クローズ時期はそれぞれ4月、9月、11月に位置するが、番号は同じ日の午前中にまとめて補完された。読み方としては、報告側が集中して番号を回収し、3月から5月の一連の開示プロセスを一気に完了させたと解すべきである。レポートでは番号を引用できるが、当日の新規修正として書いてはならない。

下流の利用者にとっての実際的な意義は検索性にある。これまでこれらの欠陥はイシュー番号しか持たず、検索や照合はプロジェクト自身のフィールドに依存していた。番号があれば、CVE データベースに入り、ディストリビューションの脆弱性リストに入り、企業内部の部材リストに入ることができる。搭載台数が億単位のリアルタイムオペレーティングシステムにとって、この一歩はさらに3つの欠陥を修正するよりも制度的価値が高い。

2.3 CherryUSB：メンテナが引いたバージョン線（11-16）

日付：2026-11-16 11:23（コメント時間）　情報源：イシュー #11265

同じ一連のコメントには拒否の1件もある。CherryUSB ホスト音声記述子解析における複数箇所の境界外書き込み（3月17日提起、5月13日クローズ）について、11時23分に CherryUSB 側のメンテナ sakumisu が一言残した。1.7.0 未満では cherryusb の CVE チェックを行わない、と。

時間を遡ると、彼は3月24日にも「rt-thread プロジェクト内で cherryusb をチェックしないでください」と既に述べている。2つの発言を合わせると1つの境界方針になる。CherryUSB は独立した上流プロジェクトであり、独自のバージョン線とセキュリティポリシーを持ち、RT-Thread 側はそれを保証せず、CVE のアーカイブも代行しない。

利用者にとって、この発言の実際的な意味は、CherryUSB を採用する BSP は上流のバージョンを自ら監視する必要があり、RT-Thread の脆弱性リストがそれを保証してくれることを期待してはならないということである。こうした境界宣言はレポートでは目立たないことが多いが、製品コンプライアンスに携わる者にとっては確固たる情報である。

日付：2026-11-16 16:21 から 17:14（コミット時間）　情報源：コミット b05dc049、コミット f4208433

Windows 側の Env ツールリポジトリは普段2か月に1度も動かないが、この日の午後に2件連続で動いた。16 時 21 分に同梱の clang-format を 22.1.8 に変更し、17 時 14 分に同梱の Arm GNU ツールチェーンを 13.3.Rel1 にアップグレードした。

どちらのバージョンも気まぐれに選ばれたわけではない。clang-format 22.1.8 はメインリポジトリの CI が使用するフォーマットバージョンそのものであり、同日にマージされた ivshmem 提案では、検証段に「変更ファイルが clang-format 22.1.8 を通過すること」と書かれている。これまで Windows ユーザーのローカルフォーマットと CI の判定基準がメジャーバージョン一つ分ずれる可能性があり、フォーマットチェックが失敗しても原因が分からないことがあった。Arm GNU 13.3.Rel1 は GCC 13 シリーズの最新メンテナンス版であり、長期サポートライン上での定例的な前進に属する。

このリポジトリの前回の実質的な変更は 9 月 8 日の Env 2.1.0 リリースだった。二か月余りを経ての再始動だが、動いたのはいずれも「環境のデフォルト値」であり、恩恵を受けるのはすべての Windows 開発者であるにもかかわらず、ニュースにはしにくい——こうした変更は通常、一度つまずいた人にしか感知されない。

6. 総括とトレンド観察

6.1 修正の粒度が変わりつつある

11月13日の那群は「1日20件」のバッチ硬化だったが、本期のメインリポジトリはわずか2件で、しかも2件とも完全なエンジニアリングだ。ptyfsの件は解放、番号初期化、生成失敗パスの解放順序、登録解除時のデバイス判定という4点をまとめて補修し、ivshmemの件はデフォルト無効のオプションを1つ新設し、3段の範囲チェックを追加し、ついでに32ビットビルドでのフィールド破壊も修正した。

「数量」から「個々の欠陥の完全な収束」への転換は、監査ラインが第2段階に入った標識だ。第1段階が求めたのはカバレッジで、同種パターンを一通り走査すること。第2段階が求めるのは各件が再審査に耐えることで、修正自体が証拠として見なされ始めたからだ——ptyfsの件は2万回ループのメモリ曲線を示し、ivshmemの件は2種構成のコンパイル結論を示しており、いずれもこの志向だ。

6.2 番号は開示の終点であり、修正の起点ではない

3件のCVE番号が同じ午前中に補完され、落点はそれぞれ4月、9月、11月にクローズされた議題だ。加えてCherryUSBメンテナの「1.7.0未満はチェックしない」という言葉により、この日のセキュリティラインでは2つのことが同時に起きた。すなわち、一批の旧債が正式に記帳され、1本の境界線が明確に引かれた。

プロジェクト側にとって、記帳とはこれらの欠陥が今後、外部の脆弱性データベースとコンプライアンスリストに入り、直したかどうか、どのバージョンで直したかを問い詰められることを意味する。使用者にとって、番号の価値は議題番号をはるかに超える。これも本期で最も誤読されやすい箇所だ——CVE番号を見て新規脆弱性と見なすと、逆方向に読むことになる。

6.3 ソフトウェアパッケージ側がその日の第2の主戦場になった

メインリポジトリ2件、ソフトウェアパッケージインデックス6件、Windowsツールリポジトリ2件。6件のうち3件はペリフェラルフレームワークの多重インスタンス化と新パッケージ（LEDテープ、赤外線、Wi-FiとBluetoothホストドライバ）、1件はAgentパッケージの設定化、2件は診断とツールだ。

この分布は、その日の開発重心がカーネルにないことを示している。パッケージインデックスという層は今年、明らかに引き受けるものが増えた。ベンダドライバの准入、AIコンポーネントの設定化、デバッグツールの標準化が、いずれもこの線上で完結している。「導入台数25億台」と自称するオペレーティングシステムにとって、エコシステム層のスループットは確かにカーネルのコミット数よりも活性度を反映する。

6.4 キューの緩やかな減少と2本の手がかりの交接

未クローズ提案143（前期144）、未クローズ議題341（前期342）で、それぞれ1件減。期間内マージ提案5件（メインリポジトリ2件、ソフトウェアパッケージインデックス3件）、新規提案2件（iso9660修正と1件のユースケースドキュメント修正）、新規議題1件（iso9660アンダーフロー）、クローズ議題1件（ptyfs）。
