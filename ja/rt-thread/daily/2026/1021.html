1. カーネルとバージョン動向

1.1 RISC-V チケットスピンロックをアトミック加算に変更：マルチコア競合下のライブロック経路を除去（10-20）

日付：2026-10-20 16:04（作成時間）　出典：PR #11904、cpuport.c

メンテナ GuEe-GUI が RISC-V 共通層のチケットスピンロック改造をコミット（6 ファイル +33/-37、2 コミット）。元の実装ではチケット取得と解放が同じ 32 ビットワード上で「ロード予約付き加算と条件付きストア」のループを回していた：上位 16 ビットが発行待ちチケット番号、下位 16 ビットが現在の保持番号である。解放側が同じワード上で条件付きストアをリトライすると、取得側の予約が繰り返し潰され、マルチコア高競合下でライブロックに陥る可能性がある。新実装ではチケット取得を 1 命令のアトミック加算に置き換え、上位ハーフワードに 1 を加算すればチケット取得が完了し、解放と同一の予約を争うことはあり得ない；解放は保持者のみが下位ハーフワードを書き込み、1 回のハーフワードストアで完了し、もはやワード全体の読み書き変更を行わないため、チケット取得が並行して進行中でも新しいチケットを上書きしない。ロック取得後にはメモリバリアを追加し、クリティカルセクションのアクセスが解放の観測後に順序付けられることを保証する。提案は成熟バージョンとしてマークされ、RISC-V カーネルレビューに割り当てられた。

1.2 同一優先度スレッドのレディ順序修正提案：IPC 起床と新規起動を隊列末尾への追加に変更（10-21）

日付：2026-10-21 00:06（作成時間）　出典：PR #11907、Issue #8459

コミュニティメンバー Yunlk がレディキューへの挿入順序問題に対する修正を提出した（4ファイル +255/-22、新規 utest を含む）。元のロジックでは「譲渡済み」フラグを持たないスレッドはすべて先頭に挿入され、スレッドが切り替えられる際にこのフラグはクリアされるため、セマフォなどの IPC 保留キューから復帰したスレッドや新規起動したスレッドがすべて先頭に割り込む形になり、同一優先度スレッドの実際の実行順序がレディ順序と逆になっていた。提案ではまず元の状態を保存してから上書きし、「まだ実行中で、かつタイムスライスを使い切らずにプリエンプトされた」という1つのケースのみ先頭挿入を維持し、それ以外はすべて末尾に追加する。シングルコアとマルチコアの2か所の挿入分岐を一貫して修正し、セマフォ起床と起動の2つの経路をカバーするテストケースを新規追加した。作者は qemu-vexpress-a9 で実測：修正前のセマフォ起床順序は乙甲、起動順序は丁丙であったが、修正後はそれぞれ甲乙と丙丁になった。提案はまだ審査中で、2つのワークフローがメンテナの承認待ちである。

1.3 シリアル V1 に受信タイムアウトイベントを追加：タイムアウトを RX_IND コールバックに統合（10-21）

日付：2026-10-21 00:15（作成時間）　出典：PR #11909、Issue #8143

受信タイムアウトイベント（コード 0x05）はヘッダファイルで以前から定義されていたが、V1 フレームワークの割り込み処理は最初の4つのイベントのみをカバーし、フォールバック分岐もなかったため、ドライバがこのイベントを発行してもフレームワークは何もせず、通知は黙って破棄されていた。リポジトリにはちょうど2つのドライバがこれに依存してデータフレームを分割している：沁恒 CH579M と華芯微特 SWM341 はどちらもチップの受信タイムアウト割り込みで「1フレーム受信完了」を判定しており、両者とも V1 フレームワーク上にあるため、フレーム境界が実際に失われ、ハードウェアの水位に基づく報告に退化するしかなかった。提案ではこのイベントを受信指示コールバックに統合する：まずハードウェア FIFO を排出し、次にソフトウェア FIFO のキャッシュ済み長に応じて上位層へコールバックする。変更は1行の分岐のみ（コメント含め計5行）で、V2 には手を付けていない。V2 のヘッダファイルにはこのマクロが存在しないためである。作者はコンパイルレベルの検証のみ行っており、アイドルタイムアウト割り込みを備えたハードウェアを持っていない。また、仮想シリアルデバイス上でテストケースを追加し CI に組み込むことも提案している。

2. セキュリティと安定性のフォローアップ

2.1 cromfs のディレクトリ名長が未制約：ls/getdents で越境しカーネル PC をハイジャック（10-20）

日付：2026-10-20 19:29（作成時間）　出典：Issue #11905

コントリビューター XueDugu が cromfs の欠陥チケットを新規作成した。ディレクトリエントリ読み取り時にディレクトリ名の長さに対する上限チェックが一切なく、超長い名前は固定サイズのディレクトリエントリバッファにコピーされ、その末尾を越えて、隣接データを書き換えられるだけのオーバーフロー量になる。ls やディレクトリ読み取りでトリガー可能で、作者はカーネルプログラムカウンタを制御可能な位置に誘導できると述べている。欠陥は 2022-12-14 の cromfs 同期コミットで導入され、v4.1.1 にはまだこの問題はなく、v5.0.0 から v5.3.0 および現在のメインラインがすべて影響を受ける。DFS の2つの実装は同源で、v1 と v2 にそれぞれ制約のないコピーが1つずつ存在する。作者は QEMU vexpress-a9 で再現しており、チケットは現在まだ引き受けられていない。

2.2 OFW 深度事前チェックをデバッグゲート化：メンテナの提案を受けて作者がコンパイルスイッチを追加（10-20）

日付：2026-10-20 09:11 ~ 16:03（コメント時間）　出典：PR #11901、Issue #11879

前号で収録したデバイスツリー深度事前チェック提案は、今調査期間で一回のレビューを完了した。レビューではまず事前走査のオーバーヘッドが疑問視され、実行時チェックに変更し、超過時は終了してメモリを解放するよう提案された。作者は、不完全なツリーの解放はポインタをたどって再帰的に走査する必要があり、割り当て箇所が散在して漏れや二重解放が起きやすい一方、チェック関数は読み取りのみで割り当てやプロパティ解析を行わないため、展開自体に比べてオーバーヘッドは非常に小さいと回答した。その後メンテナが方向性を示した：OFW は設計上ファームウェアを信頼する傾向があり、64 層はほとんどの SoC の実際の要件をはるかに超えているため、このチェックはデバッグモードでのみ有効にすることを提案した。作者はこれを受け入れ、深度チェックをデバッグスイッチで囲み、qemu-virt64-aarch64 でデバッグモードを有効にし、65 層のデバイスツリーで再テストした。変更はプッシュ済みで、提案はまだ審査中である。

2.3 tmpfs 切り詰め欠陥が RT-Smart の aarch64 で再現され引き受けられる（10-20）

日付：2026-10-20 22:53（再現コメント）　出典：Issue #11902

前号で収録した tmpfs 切り詰め欠陥は、今調査期間でデバイス側の証拠が追加された。コミュニティメンバーが RT-Smart の qemu-virt64-aarch64 ボードで再現：ファイルを 0 バイトに切り詰めると、バッファは解放されるのに関数は成功を返し、その後アプリケーションの読み書きが解放済みのカーネルヒープ上に落ち、情報漏洩と二重解放を引き起こす可能性がある。再現環境は QEMU 11.0.0 の virt マシンに GICv3、クロスツールチェーン 15.2.1、DFS_V2 設定。このチケットは 10-20 に別のコミュニティメンバーが引き受けており、修正パッチはまだ提出されていない。

2.4 その他の審査中進捗：割り込み応答修正は再テスト待ち、IAR 暗黙宣言の議論は継続（10-20）

日付：2026-10-20（コメント時間）　情報源：PR #11860、PR #11864、Issue #9941、PR #10096

既存4項目の調査期間内の進展。aarch64 割り込みコントローラの応答から冗長な保留クリアを削除する提案（#11860）について、作者はここ数日でトラップ処理の修正版をもう一度テストすると述べ、当面はマージしない。IAR 8.40 でログ関数の暗黙宣言により浮動小数点出力が乱れる提案（#11864）にはアセンブリレベルの説明が補足された。プロトタイプがない場合、コンパイラは固定引数渡しで可変引数を推論するため、%f が誤った位置から値を取得する。レビューでは依然としてボードレベルの設定と同一設定下での前後出力記録の補充が求められている。ほかに2件のフロー確認：#9941 は実測で scons --attach がメインラインで使用可能であることが確認され、当該要望チケットのクローズが提案された。#10096 はオンデマンドビルドオプションが依然メインラインに未投入であり、提案ブランチが大幅に遅れていることが確認され、まずリベースすることが提案された。

4.1 K1 BSP サポートマトリクス登録：デフォルト8コア、SPI と QSPI のステータスが正式化（10-20）

日付：2026-10-20 16:04（作成時間）　情報源：PR #11904、K1 BSP 説明

スピンロック改造と同一バッチで、進畳時空 K1 のデフォルトコア数が 4 から 8 に変更され、中英文説明が同時に更新された。リポジトリルートのボードレベルサポート表に当該ベンダー分区が新規追加され、K1 の行は GPIO、シリアル、ADC、I2C、SPI、ウォッチドッグ、タイマー、PWM、RTC、SDIO、PCI、DMA、イーサネット、オーディオ、ディスプレイ、暗号化・復号の各列でいずれもサポートと標記されている。SPI と QSPI は「移植済み、検証中」から「サポート」に変更され、以前から保留されていた SPI NOR の ID 読み取り問題もこれに伴いクローズされた。前号の K1 初版マージ時に残されたこの2件の未処理項目は、本調査期間内にまとめて収束した。

4.2 中国語 Windows 下で scons –attach がクラッシュ：絵文字を ASCII に置換する修正提案（10-20）

日付：2026-10-20 23:42（不具合票作成）　ソース：Issue #11906、PR #11908

中国語 Windows（コードページ 936）でscons --attachを実行すると、エンコーディング例外が直接発生し、コマンド全体が中止される。プロンプトに絵文字が 2 つ使われており、GBK ではエンコードできない。このコマンドの 3 つの用法はすべて同じ関数を通るため、中国語環境では完全に使用不可能となる。環境変数を設定して強制的に UTF-8 にすれば回避できるが、一般ユーザーは知らない。不具合票は当日提出され、同日に修正提案が出された。4 箇所の記号を ASCII マーカーに置き換え、既存の ANSI カラーを保持するもので、作者はリポジトリの他のスクリプトのカラー出力慣例と一致すると述べている。また別のコメントで、この提案のメモリレポートチェックの失敗は上流のサードパーティ action 自体の破損に起因し、本変更とは無関係であることが説明されている。

4.3 Allwinner D1s に QEMU 実行スクリプトを追加、メンテナは target-qemu ディレクトリへの変更を提案（10-20）

5. 業界応用

5.1 デュアルボード協調スマート端末：M7 表示側で RT-Thread と LVGL を実行、C3 がネットワークブリッジ（10-20）

日付：2026-10-20 08:31（公開時刻）　ソース：コミュニティ記事：NS800RT7P65 と ESP32-C3 によるデュアルボード協調スマート端末

2026 組み込みコンテストの作品で、2 つのマイクロコントローラで分担する。納芯微 NS800RT7P65（Cortex-M7、ハードウェア浮動小数点付き）で RT-Thread 5.3.0 と LVGL 9.1.0 を実行し、3×3 デスクトップと 14 のアプリを実現。画面は 240×320 のドライバチップ方式で、作者の実測では SPI 上限は 50 MHz、70 MHz を試すと画面全体が乱れた。16 MB の外付け NOR に小型ファイルシステムをマウントし、バックライト、色調整、ゲームの最高スコア、アラームが電源断でも失われない。ロータリノブは直交デコーダに接続し、ボタンは直接読み取りにソフトウェアデバウンスを加える。楽鑫 ESP32-C3 はネットワーク側として、無線接続、時刻同期、報告、および本機 Web ページからのアップグレードを担当し、Web ページで設定変更やファームウェア転送が可能。2 枚のボードは 1 系統のシリアルのみで接続され、作者はこれに基づきシリアル帯域では画面全体のピクセルを転送するには不十分と算出したため、動画再生は行っていない。

5.2 Edgi-Talk 人型検出報警システム：M55 と NPU、検出と報警をローカルでクローズドループ（10-20）

日付：2026-10-20 08:31（公開時刻）　ソース：コミュニティ記事：Edgi-Talk ベースのエッジ AI 人型検出報警システム

別の大会作品は Infineon PSoC E84 をプラットフォームとしている。M55 コアが RT-Thread を実行して映像、スケジューリング、業務を担い、M33 コアがセキュアブートを管理し、NPU が固定小数点推論を行う。カメラは USB ホスト経由で YUYV 形式 424×240 を出力し、画面表示は 320×240、5 フレームごとに 1 回推論し、入力は 320×320 の 8 ビット固定小数点、候補ボックスは最大 8 個、信頼度しきい値 0.45、重複抑制 0.45。警報は連続 3 回の命中で確認し、連続 5 回の未命中で解除し、単一フレームの誤検出による揺らぎを避ける。ストレージ書き込み、ネットワーク報告、音声再生はそれぞれキューに並び、映像スレッドを占有せず、ネットワーク断でもローカル検出と音光警報に影響しない。システムティックは 1000 Hz で、異常時にはコアプレビューへ降格する。

5.3 農田害虫声紋認識：AIoT 大会受賞作品が電子工程専輯に掲載（10-20）

日付：2026-10-20 17:30（公開日時）　情報源：電子工程専輯：オフラインでも虫を聴いて害を辨別、Edge Impulse ベースの端側声紋認識実戦

業界メディアが RT-Thread AIoT 大会優秀賞の作品を掲載した。Edgi-Talk オンボードマイクで田間の虫鳴きを収集し、Edge Impulse 上で四分類（蝉、コオロギ、ノイズ、未知）を行う。特徴量はメルフィルタバンクエネルギー、窓 1 秒、ステップ 200 ミリ秒、サンプリング 16 kHz、累計サンプル約 2 分 15 秒、82 対 18 で訓練とテストに分割し、100 エポック訓練後に固定小数点モデルを端側推論へエクスポートする。害虫と判定すれば外部接続の噴薬をトリガーし、ノイズまたは未知と認識すれば動作しない。全行程オフラインでクラウドに依存しない。作者はドキュメントとコードを公開している。

6. まとめとトレンド観察

6.1 今期のトレンド

  • カーネルの二つの低層経路が同時に修正された：スケジューラは同一優先度のレディ順序を先着順サービスに戻し、RISC-V チケットロックはチケット取得を単一命令のアトミック加算に、解放をハーフワードストアに変更した。前者は実行順序の予測可能性に影響し、後者はマルチコア競合下の活性に影響する。いずれも長らくデフォルト動作に覆われていた問題である。
  • ペリフェラルイベントのセマンティクスが補完され始めた：シリアル V1 がついに「受信タイムアウトは 1 フレーム終了に等しい」をフレームワークに接続した。影響を受けたのはまさにアイドル割り込みでフレームを切る二つの国産ボード級サポートであり、フレームワーク層の歴史的欠落が依然として一つずつ発見されていることを示す。
  • 欠陥発見は引き続き外部研究者に駆動される：今期の cromfs 越界単一は影響範囲を v5.0.0 まで遡及し、DFS の二つの実装が同源であることを指摘した。この種のバージョン区間付き報告は単点パッチより価値が高く、v1 と v2 の並行メンテナンスによる重複リスクも示唆する。
  • ベンダープラットフォームは起動可能から納品可能へ：K1 はデフォルトで 8 コアに開放され、SPI と QSPI の状態が正式化してサポートマトリクスに入った。D1s はエミュレータ実行経路を補い、レビューは「再現可能環境」をディレクトリ規範と AI 向け説明ドキュメントへ引き上げた。プラットフォーム化の思路である。
  • ツールチェーンのローカライズ細部が視野に入る：中国語 Windows 下で絵文字がビルドコマンドを中止させる。問題は小さいが影響面は大きく、クロスプラットフォーム可用性テストが依然として短板であることを反映する。
  • 公式チャネルは引き続き静穏：ニュース API は 4 か月以上更新停止し、バージョンリリースは依然として九月で止まっている。対外情報は主に GitHub とコミュニティ作品に依存し、この構図は二週連続で変わっていない。

6.2 限界と重複排除の説明

  • 今期は 24 時間窓（10-20 08:00 ~ 10-21 08:00）であり、月曜日ではないため複数日の統合は行わない。
  • メインリポジトリの窓内にマージはなく、全項目は提案、欠陥票、コミュニティ側から来ている。したがって「カーネルとバージョン動向」の三節はいずれも審査中提案であり、すでに着地した変更ではない。各条には状態を明記した。
  • 前期との重複排除：デバイスツリー深度事前検査（#11901）と tmpfs 截断単（#11902）自体は前期に収録済みであり、今期は窓内で新たに追加されたレビュー結論とデバイス側再現のみを記す。割り込み応答（#11860）、IAR 暗黙宣言（#11864）、オンデマンドビルド（#10096）、attach 設定（#9941）はいずれもより早い条目であり、今期は進展のみを記録する。
  • 二つの大会作品の主控はいずれも RISC-V ではない：納芯微 NS800RT7P65 は Cortex-M7 であり、ネットワーク側の楽鑫 ESP32-C3 こそが RISC-V である。Edgi-Talk は Cortex-M55 に M33 を加えたものである。収録理由は RT-Thread アプリケーション案例とツールチェーン実践であり、RISC-V 適配の解読は行わない。
  • 組織レベルの全量プッシュは API 核查に合格できなかった（匿名枠を使い切った）。代わりにリポジトリコミットフローと組織ページで交差検証した。Studio の SDK インデックスはコミットフローで 10-10 に停止していることを確認した。
  • フォーラム記事 API は先頭 20 条のみを取得し、超過分は未核查である。公式ニュース一覧ページはフロントエンドレンダリングのため、取得は空殻のみで、ニュースは API に準拠する。
  • Google ニュース英語窓はゼロヒット、中国語三日間の 2 条のうち 1 条は収録済み稿、1 条は 10-18 の旧稿である。睿擎クエリは同名の自動車稿件に依然として埋没し、いずれも追加条目を生まなかった。
