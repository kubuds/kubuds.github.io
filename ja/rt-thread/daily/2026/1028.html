1. カーネルとバージョン動向

1.1 2 日間の静穏を経てメインラインがマージを再開、6 分間に 4 件が着地（10-27）

日付：2026-10-27 19:20 ~ 19:26（マージ時間）　出所：メインリポジトリのコミット記録、提案 #11885

メインラインは 10-25 夜以降約 2 日間停止し、10-27 19:20 から 19:26 の 6 分間に連続して 4 件がマージされた。すべて同一のメンテナーが操作し、変更は dfs、net/sal、libc/posix、drivers/serial の 4 箇所に及び、合計 46 行追加、6 行削除。4 件のうち 3 件は author 時間が 10-18 であり、滞留提案の集中着地であって当日新規に書かれたコードではない。これが本期唯一のメインライン変動でもある。

1.2 dfs の UTIME_OMIT 判定が逆になっており、変更しないよう要求したタイムスタンプが逆に上書きされる（10-27）

日付：2026-10-27 19:20（マージ時間）　出所：提案 #11885

dfs_v2 の utimensat 実装において、UTIME_OMIT の分岐条件が逆になっていた。POSIX の意味論では、UTIME_OMIT が設定された項目のタイムスタンプはそのまま保持されなければならない。元のコードは反転後の条件で引き続き mtime を書き込んでおり、呼び出し元が明示的に変更しないよう要求したタイムスタンプを上書きするうえ、有効なタイムスタンプを 1 つ失っていた。修正は比較演算子 1 箇所のみで、ファイル dfs_posix.c の純変化は 1 行。この種の意味論的ずれは「時刻設定成功」だけをテストするケースでは見えず、隠蔽型の欠陥に属する。

1.3 RAW socket プロトコル検証をホワイトリスト方式に変更、ICMP などのプロトコルがブロックされなくなる（10-27）

日付：2026-10-27 19:21（マージ時間）　情報源：提案 #11888

SAL 層で RAW socket を作成する際、従来は protocol が IPPROTO_RAW と等しいかどうかという単一の等値判定でチェックしていたため、IPPROTO_RAW 以外のプロトコルは一律に拒否され、ICMP のようなネイティブソケットを必要とするシナリオが通せなかった。今回、VALID_PROTOCOL ホワイトリスト検証に変更し、domain と type の既存検証は変更しない。同一提案には純粋にフォーマットのみのマクロ整列修正も含まれており、機能変化はない。変更は sal_socket.c に落ち、正味の変化は1行。

1.4 poll が dfs_file から fops を取得するよう変更、DFSv1 と DFSv2 を同時に互換（10-27）

日付：2026-10-27 19:21（マージ時間）　情報源：提案 #11887

poll は以前 vnode から直接 fops を取得しており、DFSv2 下では取得した構造体が実際のファイル操作テーブルと同一のものではなく、poll を誤ったディスパッチ入口に接続しているに等しかった。今回、dfs_file を経由して fops を解決するよう変更し、DFSv1 の互換パスも保持し、デリファレンス前にヌルポインタチェックを追加した。変更は poll.c に集中し、14 行追加、2 行削除。これは DFSv2 切り替え後に残った適配問題の一種であり、修正方式は書き換えではなく保守寄りである。

1.5 8250 earlycon が reg-io-width を読むようになり、ワイドレジスタプラットフォームがバイトアクセスされなくなる（10-27）

日付：2026-10-27 19:26（マージ時間）　情報源：提案 #11889

初期シリアルコンソールは従来、デバイスツリーの記述に関わらず、レジスタをバイト幅でアクセスしていた。今回、デバイスツリーから reg-shift と reg-io-width を読み、reg-io-width に応じて MMIO アクセス幅を選択し、初期初期化段階でサポートされない幅を直接拒否する。その他の compatible は引き続き汎用 8250 パスを通る。変更は early.c に落ち、30 行追加、2 行削除。レジスタのステップやビット幅がデフォルトでないプラットフォームに対し、初期ログのずれと文字化けに統一的な解法ができ、ボードごとにコードを修正する必要がなくなった。

1.6 リリース側は依然 v5.3.0、メインラインは 10-17 に v5.4.0 へ bump 済みだが tag 未打（10-27）

日付：2026-10-27（確認時間）　情報源：リリース記録、タグ一覧

releases と tags の両側とも 24 時間以内に新規エントリはなく、最新リリース版は依然 9-10 の v5.3.0。メインラインは 10-17 にバージョン番号を v5.4.0 へ引き上げるコミットがあり、開発ブランチのバージョン番号はすでに 5.4.0 に達しているが、リポジトリには対応する tag と release 記録がまだない。例年のペースでは、正式リリースは通常 tag 打ち後に初めて対外公告されるため、本期はまだリリースのシグナルとはならない。

昨日のデイリーレポートで記録した signalfd のグローバルカウント範囲外について、コミュニティが当日修正提案を提出した。方法は、グローバルインデックスカウンタをコンテキスト単位で位置特定する上限付きスロット検索に置き換えること。signalfd_close 時に登録済みの lwp を走査し、対応する通知ノードをリンクリストから外してリスナー構造体を解放し、最後にファイルコンテキストポインタをリセットしてテーブルエントリをクリアし、残留ポインタが再度デリファレンスされるのを防ぐ。提案は正味 41 行増、単一ファイル変更で、現在マージ可能。元 Issue と提案の間隔は1日未満で、対応速度は珍しい。

3. ツールチェーン、公式、コミュニティ

3.1 コミュニティの長文が Env v2.0.3 を解説：コマンドを rt-env に集約、プラグイン体系と WebUI を新設（10-27）

日付：2026-10-27 11:01（公開日時）　情報源：コミュニティ記事：Env Tool v2.0.3 使用全記録

コミュニティが Env ツールチェーンの v2.0.3 へのアップグレードに関する完全な使用記録を公開した。記事によると、Env は 2.0 からアーキテクチャの大幅な再構築を行った：コマンドの統一入口が rt-env に変更され、menuconfig、pkgs、scons は散在するサブコマンドではなくなり、新たに sdk、plugin、webui、system が追加された。依存関係はすべて Python 仮想環境内で動作し、システム Python とは隔離されている。プラグイン体系と WebUI が新設され、ブラウザ上でツールチェーン、SDK、ソフトウェアパッケージの管理が可能になった。代償として、各ターミナルでコマンドを使用する前にまずアクティベートが必要となる。作者が実測したバージョンの組み合わせは rt-env 2.0.3 に SCons 4.11.1、kconfiglib 14.1.0。記事では互換性のレッドラインが特に明記されている：Env 2.0 は 5.1.0 以上のバージョンと master ブランチを完全にサポートするが、5.1.0 以前のプロジェクトは依然として 1.5.x リリースパッケージに留まる必要がある。

日付：2026-10-27（確認時刻）　情報源：公式ニュースインターフェース

公式ニュースインターフェースをページごとに確認したところ、最新の項目は依然として 2026-06-17 の二件で、それぞれアブダビ投資フォーラムと第 4 回ソフトウェアイノベーション発展大会に関するものだった。24 時間および 7 日間の調査期間内に新規はない。これと対照的に、コミュニティ記事インターフェースには本調査期間内に新稿が一件あった（3.1 参照）。これは公式の対外稿件とコミュニティ投稿が二つの独立したチャネルを通っていることを示しており、公式側は連続四か月低頻度となっている。そのためデイリーレポートの日常的な内容は実質的に GitHub とコミュニティ側が担っている。

3.3 電子工程専輯が三大 RTOS を横断評価、RT-Thread は低消費電力とコンシューマー向けシーンで優選に（10-27）

日付：2026-10-27 22:27（公開日時）　情報源：電子工程専輯：三大 RTOS 徹底横断評価

電子工程専輯傘下のコラムが三大RTOSの横比較を発表し、リアルタイム性、メモリ使用量、エコシステム、コミュニティ、AI対応、移行コストの6次元でFreeRTOS、RT-Thread、Zephyrを比較した。記事ではRT-ThreadをApache 2.0の軽量オールインワンパッケージと位置づけ、カーネルは3KB Flashと1.2KB RAM、POSIX、GUI、ファイルシステム、AIパッケージを内蔵。低消費電力コンポーネントはStopモードで他の2者より15%から20%省電力だとしている。選型の意思決定表では、64KB RAM以下の極限的低コストプロジェクト、およびコンシューマエレクトロニクスとウェアラブルをRT-Threadに割り当てている。記事は同時に、Zephyrがマルチプロトコル・マルチボードと長期メンテナンスの場面でより強いことも認めており、結論は一辺倒ではなく三つ巴である。データは各プロジェクトの公式ドキュメントと第三者ベンチマークから引用され、ベンダーの投放の痕跡は見られない。

4. エコシステムとベンダー適配

4.1 安謀科技 WTCC 2026 セミナー：RT-Threadは具身知能プロジェクトを重点に、3種類のAgent方案を分解（10-27）

日付：2026-10-23（イベント）/ 2026-10-27 14:13（報道）　情報源：快科技報道、21ic 同稿

安謀科技は上海西岸国際科技消費嘉年華（WTCC 2026）の期間中に小規模な具身知能方案セミナーを開催し、瑞芯微、瑞莎計算機とRT-ThreadがオープンソースAIOSアライアンスパートナーとして参加した。RT-Thread AI上級エンジニアの鄭煒氏は、ロボット犬、HyperCar、Codex編排の3種類のAgent方案について、知能エージェントが対話から実行へどう移行するかを説明し、RT-Threadが今後具身知能プロジェクトを重点とし、安謀科技とともにAgent能力を実応用に結びつけることを明言した。瑞芯微は、大規模モデル推論が計算集約型からメモリ集約型へ移行しつつあり、帯域が端末側のボトルネックになっていると指摘し、メインSoCとAIコプロセッサで算力と制御を分離する方案を示した。安謀科技は同会場でJishuFriendsとJishuBuddyの2つの落地方案を発表した。

4.2 K230上のキッチン火炎検出プロトタイプがソースコードと再現記録を公開、ベースはRT-Thread Smart（10-27）

日付：2026-10-27 19:19（プッシュ時間）　情報源：SRTP-K230-Fire-Guardian

K230とRT-Thread Smartをベースにしたキッチン火炎検出プロトタイプがソースコードを公開。内容にはマルチセンサフュージョン、適応型連動戦略、再現記録、モデル評価が含まれ、リポジトリには参考資料も置かれ、第三者が記録に従って再実行できるようになっている。プロジェクトは研究プロトタイプであり製品ではないと自ら位置づけている。これは今期のエコシステム側では珍しい、RT-Thread Smartを実際の知覚ループに用いた公開プロジェクトであり、Smartの視覚系シーンでの可用性評価に参考価値があるとともに、Smartがボードベンダー以外のコミュニティ側でも動き始めたことがうかがえる。

4.3 CH32H417デュアルコアRISC-V上でRT-Thread＋LVGL＋TFLMによる手書き記号認識（10-27）

日付：2026-10-27 08:41（プッシュ時間）　情報源：ch32h417-tinyml-symbol-recognition

沁恒CH32H417デュアルコアRISC-Vプラットフォーム上の手書き記号認識プロジェクト。技術スタックはRT-Thread＋LVGL＋TFLMで、経路にはOV5640取得、定点画像前処理、INT8量子化モデル推論、インターフェース表示が含まれ、学習側には別途ツールチェーンが添付されている。プロジェクトは立ち上げたばかりでまだ注目度はないが、価値はRISC-V上の完全な軽量視覚経路をオープンに詳述している点にあり、データ取得から量子化デプロイまで照合可能で、国産RISC-V MCUで端末側推論を行おうとするチームにとって再利用可能なサンプルとなる。

5. 業界応用と具身知能

5.1 AIoT大会作品が産業側へ転換：Titan Board上でBLDCモータ欠陥AIモニタリング（10-27）

日付：2026-10-27 11:50（メディア転載）　情報源：電子工程専輯：BLDCモータ欠陥AIモニタリングシステム

電子工程専輯が2026 RT-Thread AIoTコンテストの応募案の一つを転載：ルネサス Titan Board上でBLDCモータの動作状態欠陥をAI監視するもの。ハードウェアはRA8P1で、1GHz Cortex-M85と250MHz Cortex-M33のデュアルコア、Ethos-U55 NPU搭載、シングルチップ256 GOPS。システムは三相電流、バス電圧、インバータ温度を収集し、M85コアで前処理した後、NPU上に展開した軽量CNNに送り、リアルタイム欠陥認識を行う。ソフトウェア側はRT-Threadで3つのコアスレッドを起動し、それぞれ画面表示、データ通信、AI推論を担当。画面はLVGLベースで、モデルはRUHMI経由でTFLiteからCコードに変換して統合。方案は追加センサーを設けず、駆動電流と電圧のみから状態を分析する低コスト予知保全路線を強調している。

5.2 本期線索：チップメーカー、ボードメーカー、OS側がアライアンス枠組みの下で同台、着地点は一致して具身智能（10-27）

日付：2026-10-27（本期）　情報源：快科技報道、SRTP-K230-Fire-Guardian

本期の3つの線索を並べて見ると、方向性はかなり一致している。上流IP・チップ側では、安謀科技がオープンソースAIOSアライアンスで瑞芯微、瑞莎、RT-Threadを同じテーブルに集め、演算力の分離と端側帯域のボトルネックについて議論している。OS側では、RT-Threadが具身智能プロジェクトを重点に位置づけ、Agentが対話から実行へ移行することを語っている。コミュニティ・ボード側では、K230とCH32H417の2プロジェクトがそれぞれSmartと軽量推論を火炎検出や記号認識といった具体的タスクに落とし込んでいる。三者はいずれも「小型デバイス上で完全な知覚と意思決定の閉ループを回す」方向へ収斂しており、それぞれ機能リストを拡張しているわけではない。

6. 総括とトレンド観察

6.1 本期トレンド：マージ再開、修正は新機能ではなく境界チェックに集中

日付：2026-10-28（本期）　情報源：メインリポジトリのコミット記録

本期最も記録に値するのは、マージペースの回復とその構成である。4件のマージのうち3件のauthor時刻が10-18で、その一群の提案がレビューで9日間滞留していたことを示し、現在順次着地しつつある。同じ一群にはSmart関連の提案がさらに4件キューに残っており、今後数日間も主线はこの一群が中心になると予想できる。4件の技術的指向は一致している。ファイルシステムのタイムスタンプ意味論、ソケットのプロトコルホワイトリスト、pollの振り分け元、シリアルのレジスタ幅は、いずれも境界チェックと意味論の整合であり、新機能は一つもない。これら4種類の箇所は普段はエラーを出さないが、一度問題が起きると特定が難しい。同一批次で集中的に修正されることは、長期的な安定性にとってプラスである。
