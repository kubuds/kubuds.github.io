1.3 メンテナによる #12090 の初回確認：2 点要協議、承認にはならないと明言（11-27）

日付：2026-11-27 03:06（レビュー）。
出所：#12090。

Bernard Xiong は head e2224ab に対して初回調査の結論を示し、カバレッジが不完全であることを明記した。既読範囲には can_internal.h の契約と can_tx.c、can_rx.c の全文が含まれる。さらに dev_can.c の open/close/control ライフサイクル、および STM32 bxCAN の sendmsg と TX 割り込みのクリティカルパスも含まれる。残り 30 の BSP アダプタ、dev_can.h の全 API 変更、Kconfig と CI matrix、utest ケースは未読である。

第一の要協議点は、STM32 bxCAN で AutoBusOff が無効化されていることである。drv_can.c の 173 行目から 175 行目で ABOM を ENABLE から DISABLE に変更し、同時に AutoRetransmission を ENABLE に変更している。提案の説明にはこの動作変更が記されていない。ABOM を無効化すると、コントローラが bus-off に入っても自動復帰しない。この状態で再度 RT_CAN_CMD_START を呼ぶと、HAL の状態が READY ではないため -RT_ERROR を返す。ユーザーは close してから open し直し、DeInit と configure を経由しないと復帰できない。レビューでは、自動 bus-off 復帰に依存するフィールドバス用途にとって可視的なリグレッションであると指摘された。

第二の要協議点は、管理操作の失敗後にデータパスが閉じたままになることである。_can_reconfigure() は BSP 操作がエラーを返すと直接 out_unlock へジャンプする。この時点で TX admission は既に閉じられ、RX は pause されており、SET_PRIV の引数検証以外にロールバックがない。SET_BAUD、SET_FILTER または CONFIGURE がハードウェア起因で失敗した後も、デバイスは再度 START するか close/open するまで送受信できない。レビューでは二つの選択肢が示された。意図的な fail-closed であれば公共 API のドキュメントに明記すること、そうでなければ非 STOP コマンドに対して was_accepting と RX admission を復元することである。

レビューの末尾には、実板での検証はなく、46 ファイル・追加 8936 行は大規模なリファクタリングに該当するため、次回の完全な審査を経てから承認可否を判断することを推奨すると記されている。

2.1 serial_v2 DMA キャッシュラインアライメントがメンテナに承認される（11-27）

日付：2026-11-26 11:16 から 2026-11-27 03:03。
情報源：#12084。
議題 #12063。

議題 #12063 は Cortex-M7 で D-Cache を有効化した後の古くからの問題を扱っている。serial_v2 の DMA ping buffer は RX FIFO ブロック内に確保され、開始アドレスが 32 バイト境界に揃えられることがない。SCB_InvalidateDCache_by_Addr がキャッシュラインを無効化する際、前後のヒープブロックまで巻き込んで汚染する。TX 側にも同じリスクが存在する。

提案は ping buffer の開始アドレスを ringbuffer の後ろで 32 バイト境界に揃える。dma_ping_bufsz をキャッシュラインの整数倍に切り上げ、総確保サイズもそれに合わせて調整する。投稿者の liangzhan5 はついでに hpmicro BSP 内の局所的な修正をロールバックした。変更は 1 ファイル、9 行追加・2 行削除。投稿者は手元に実板がなく、静的解析のみを行ったと自己申告している。

Rbb666 は 11 時 16 分に二つのインラインコメントを付けた。一つ目は hpmicro のロールバックについて。HPM6750 のキャッシュラインは 64 バイトであり、フレームワークは 32 バイト境界しか保証しない。BSP のアライメントを削除すると、非ブロッキング DMA TX の flush が FIFO ヘッダや隣接ヒープブロックまで書き戻す可能性がある。二つ目は確保条件について。グローバルな RT_SERIAL_USING_DMA のみを見ているため、割り込み受信のみのボードでも余分に 32 バイトを確保してしまう。

投稿者は同日 21 時に返信した。TX 側の変更は「実際に保護が必要なシナリオはない」という理由で取り消した。HPM の BSP アライメントは維持し、そのファイルには手を入れない。

11 月 27 日 3 時 03 分、Bernard Xiong は head 156fbaf 上で承認した。レビューは、変更が RX ping buffer のアライメントのみを残し、TX 側の変更を削除し、HPM の BSP アライメントを維持するものであり、方向性は正しいと確認した。実装の詳細は sizeof(struct rt_serial_rx_fifo) + rx_bufsz でオフセットを計算する。確保時には RT_ALIGN(dma_ping_bufsz, RT_CPU_CACHE_LINE_SZ) にキャッシュライン 1 本分を加えて予約し、最後に開始アドレスをアライメントする。

判断：これは本期唯一レビューの全工程を完了した提案である。根拠は、コメント、手戻り、承認の 3 ステップが 24 時間以内に閉じ、争点が 1 つのバッファに限定されたことである。

2.2 devtmpfs の越境書き込みに競合と再現手順が追加され、7 件の承認待ちは CI 通過後に解放（11-27）

#11842 は devtmpfs のスタックオーバーフローを修正するものです。_path_separate() と _get_subdir() はバッファ長を受け取らず、任意の長さのパス構成要素を呼び出し元の 256 バイトのスタック配列に rt_memcpy します。dentry->pathname は最大 4092 バイトに達し、単一の構成要素が 255 バイトを超えるとオーバーフローし、境界外は約 3.8 KB に達して戻りアドレスを上書きできます。上流の tmpfs の同名関数は既に parent_size、file_size、name_size の検証を備え、-ENAMETOOLONG を返しますが、devfs のこのコピーは漏れています。

3.2 UART0 の帰属と例外復帰、三つの提案が同じ病（11-26）

日付：2026-11-26 11:08 と 11:13（レビュー）。
情報源：#12078。
#12079。

UART0 の問題は二回現れる。C907 の起動時に E907 が使用中の UART0 をリセットし、両端の FinSH が受信割り込みを有効にし、同じ FIFO を奪い合って読む。レビューは異種モード向けに UART0 の初期化と受信端を一意に指定するよう求めた。#12079 側はより直接的だ。e907 の main.c 83 行目で uart0 を再初期化しており、FIFO をクリアし、受信割り込みを閉じ、重複登録自体も失敗する。

例外処理の問題も二回現れる。両提案の board/trap.c 27 行目はいずれも同期例外で直接リターンし、元の mepc を復元するため、フォールト命令が繰り返し発火する。レビューは両端で mcause と mepc を記録した上で例外処理に入るよう求めた。

スタックサイズは三つ目の硬い冲突だ。#12077 の Kconfig 24 行目は SMP 割り込み入口が設定に応じてコアごとのスタック頂点を計算するが、起動アセンブリとリンカスクリプトは固定で 8192 を使用している。設定値を大きくすると割り込みスタックが予約領域を越えるため、レビューはスタックサイズの来源を統一するよう求めた。E907 の Kconfig 21 行目は別方向だ。menuconfig では依然 SMP を有効にできるが、E907 は SMP ポートが組み込まれておらず、セカンダリコアの起動パスもない。

3.3 命名とドライバ共用：二件が同一箇所の手直しを要求（11-26）

日付：2026-11-26 11:08 と 11:13（レビュー）。
情報源：#12078。

ドライバ共用の問題も繰り返し現れる。両端の UART、FDT、MMC ドライバのソースコードは完全に同一であり、Allwinner の libraries/drivers/ に置き、二つの BSP が同一実装を参照すべきだ。E907 側の MMC コピーはビルドに全く参与していない。

#12079 にはさらに二箇所の細部がある。drv_openamp.c 189 行目は先にドアベルを読み、E907 が発した OA_EVT_LINK を読み取ってしまい、主端が先にタイムアウトする可能性がある。レビューはリンクループ内で古い token をフィルタするよう求めた。e907 の main.c 146 行目は応答パケット長で比較し、切り詰められた応答パケットでもプレフィックスが一致すれば検収を通るため、送受信長の一致を先に検証するよう求めた。

ドキュメントも一致していない。#12079 の main は OPENAMP-EPT-OK を出力するよう変更済みだが、README は依然 RPMSG-OK を検収根拠としている。

5. まとめとトレンド観察

  • マージ为零、レビューが補完：メインラインは24時間ゼロコミットで、最近では初めて丸一日マージがなかった。同日、提案側では15件のインラインコメントと大規模リファクタリングの初回調査が1件産出された。
  • CAN リファクタリングが第2ラウンド審査に入る：番号を変えてマージコンフリクトを回避した後、メンテナはアダプタの3分の1を読んだだけで2箇所のセマンティック問題を指摘し、bus-off 復旧パスが致命的な欠陥であるとした。
  • 2件の収束パスは異なる：serial DMA のアライメントは範囲を限定することで承認を得て、devtmpfs はコンフリクトの補完とローカル再現により7つの保留 run を獲得したが、どちらもまだメインラインには入っていない。
  • V861 の問題はビルドからセマンティクスへ移行：昨日はビルドマトリクスと PLIC アドレスで止まっていたが、今日は異種デモが通らない、UART0 の競合、例外の繰り返し発生に変わり、設計層に属する。
  • 命名とコード再利用が統一基準に：2件の提案は drv_rpmsg と drv_openamp の命名および両端の重複ドライバを同時に修正するよう求められ、メンテナが BSP 構造を収束させており、機能だけを見ていないことを示している。
  • ニュース側は3週連続で沈黙：公式インターフェースは11-06で停止し、フォーラムは11-23で停止、当日収録可能な外部報道はゼロ。
