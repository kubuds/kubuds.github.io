1. 3件の CVE マージ：乱数、無線フレーム、rt-link

1.1 乱数：シードを固定値から tick とハードウェア源へ（11-12）

日付：2026-11-12 15:51（マージ時間）　出典：提案 #12022

rt_random はこれまで予測可能な線形合同法発生器であり、デフォルトシードは固定で、読み出される系列は起動のたびに同じだった。これを暗号学的乱数として使うコードは、鍵を起動イメージに書き込んでいるのと同じである。提案説明はリスクを直接 CVE-2024-25389 と旧議題 #8283 に結びつけており、マージされた変更は3点：初回読み出し時に rt_tick_get() をシードに混ぜる；ハードウェア暗号乱数源が有効な場合、ハードウェア出力を戻り値に XOR する；Kconfig とコードコメントにこれが暗号学的に安全な乱数ではないと明記する。

変更は小さく、2ファイル、70行追加、2行削除で、rt_random.c 以外では Kconfig の6行の説明だけを触っている。マージ者は Rbb666、作者は今週ずっと監査リストを提出し続けている同じアカウントである。この件の意義はコード量ではなく、「CSPRNG ではない」ことを設定画面に書き込んだことにある。アルゴリズムを黙って差し替えるより確実である。

1.2 無線管理：負の長さを確保の前に拒否（11-12）

日付：2026-11-12 15:47（マージ時間）　出典：提案 #12020

rt_wlan_send_to_thread() の長さ引数は符号付き整数であり、sizeof(ヘッダ) + len のような式は len が負のとき巨大な符号なし値に回り込み、その後の確保とゼロクリアがこの値に従って実行され、ヒープが書き潰される。修正はチェックを先頭に置くこと：len < 0 なら直ちに引数エラーを返し、非負を確認した後にのみ符号なし型へ変換して長さを計算する。

1ファイル、9行追加、3行削除で、CVE-2024-25388 と議題 #8285 に対応する。提案本文には「その他の無線管理動作は不変」とわざわざ書かれている。この一文はセキュリティ修正では必要である。変更が共通パスに近いほど、影響範囲を説明すべきだからだ。

1.3 rt-link：今回は送信側のフレーミングを修正（11-12）

日付：2026-11-12 10:23（マージ時間）　出典：提案 #12018、欠陥 #8289

前回は rt-link の受信側における長フレーム再構成（議題 #12030 と提案 #12031）を取り上げたが、今回は同じモジュールの送信側がマージされた。フレーム化の前に最終フレーム長を検証せず、超長ペイロードが静的送信バッファを直接書き潰す。修正方法は、コピーの前にデータ長とフレーム長を判定し、範囲外なら拒否するというもの。

1ファイル、23行追加、3行削除で、CVE-2024-25395 に対応する。両日の内容を合わせて見ると、rt-link のこの送受信パスの問題形態は一致している。フレームヘッダ内の長さが信頼できる入力として扱われており、しかもそれはリンクの対端から来ている。受信側は議題によって発見され、送信側は CVE リストによって洗い出され、二つの線が同じ月に合流した。

2. 同批でマージされた他の3件：libdl、メモリプール、NFS

2.1 libdl：3アーキテクチャのリロケータを同時に収束（11-12）

日付：2026-11-12 14:35（マージ時間）　情報源：提案 #12016、欠陥 #11898

動的モジュールローダがリロケーションの書き込み先を計算する際、「モジュールメモリ基底アドレス + オフセット - 仮想開始アドレス」を用い、結果の範囲を検証しない。細工されたモジュールファイルによってオフセットがアンダーフローまたはオーバーフローし、リロケーション段階でカーネルメモリに直接書き込まれる。修正方法は、目標区間検証関数を新設し、オーバーフロー防止演算で書き込み区間がモジュールメモリ内に収まることを確認したうえで、ARM、RISC-V、x86 の3つのリロケータに組み込む。同時に ELF セクションヘッダインデックス、シンボルテーブルインデックス、および再配置可能オブジェクトファイルのセクション境界チェックを補い、ロード失敗時には中止して既に割り当てたセクションメモリを解放する。

これは本批で最大の一件である。5ファイル、205行追加、37行削除。3アーキテクチャを同時に変更していることは、問題が共通のロードフローにあり、特定の移植にあるのではないことを示す。10月18日の欠陥 #11898 に対応する。

2.2 メモリプール：誤警報の背後にあるセンチネル規約（11-12）

日付：2026-11-12 10:14（マージ時間）　情報源：提案 #12014

この一件は脆弱性の修正ではなく、実際の停止を引き起こす誤判定の修正である。「最後のブロックで、その next がヒープ末尾センチネルを指す」メモリブロックを解放する際、検証ロジックは next 項のメモリプールポインタが現在のプールと等しいことを要求するが、旧バージョンやベンダーカスタマイズの小メモリプールではセンチネルに使用済みビットのみを保持し、ポインタは空であるため、アサーションが発火しシステムが停止する。

修正方法は、「next がヒープ末尾オフセットに等しい」というケースを明示的に受け入れ、それ以外は同プール検証を維持する。著者は本文で prev をチェックする簡略化案を明確に拒否しており、その理由は prev が前のブロックを指し、先頭ブロックが 0 であるため、検証全体が緩くなるからである。付随してメモリテストケースを追加し、使用済みビットのみのセンチネルをシミュレートしてブロック全体の結合を検証する。

2025年の旧欠陥 #10632 に対応する。この種の問題はどの CVE リストにも現れないが、現場で引き起こす再起動回数は脆弱性より多いかもしれない。

2.3 NFS：サーバ提供の長さを三者最小にクランプ（11-12）

日付：2026-11-12 09:35（マージ時間）　情報源：提案 #12012、欠陥 #11917

NFS 読み取りパスはサーバが返したバイト数をそのままメモリコピー長として使用し、要求量にもデコード済みデータ長にも責任を負わない。修正方法は、各コピーを「サーバカウント、要求カウント、デコード済み長」の三者の最小値に収束させ、実際のコピーバイト数に応じてバッファとオフセットを進め、進展のない応答に遭遇したらループを抜けて空回りを避ける。

同一関数内の他の2箇所も併せて修正された。書き込みパスのショートライトは実際のバイト数に応じて進める。部分読み取り成功後に RPC 失敗が発生した場合は、読み取り済み長を返し、累計値をゼロにクリアして呼び出し元にゼロバイト読んだと誤解させない。3ファイル、67行追加、15行削除で、読み書き両側の上限を同一の最大転送単位定義に統一した。10月18日の欠陥 #11917 に対応し、レビューは11日に逐条確認のうえ通過結論を出した。

3. 第二批10件：M0 と M23 に同題が各1件

3.1 HardFault スタック選択：アセンブリ層の旧欠陥を2つの移植に補完（11-12）

日付：2026-11-12 13:26 と 14:19（提案時間）　情報源：提案 #12043、提案 #12049、欠陥 #3584

Cortex-M0 と M23 のハードウェア例外処理エントリは、無条件にプロセススタックポインタからスタックフレームを取得する。割り込みサービスルーチン内部でトリガーされたハードウェア例外では、スタックフレームは実際にはメインスタックポインタに積まれるため、バックトラックすると誤った現場が得られる。修正方法は、例外戻り値の該当ビットに応じてメインスタックとプロセススタックを選択し、M3 移植の既存手法と整合させる。

二つの提案はそれぞれ三つのアセンブリファイル（GCC、RVDS、IAR の三つのツールチェーン）を変更し、21 行を追加、3 行を削除した。欠陥 #3584 は何年も前からの古い議題であり、今回は同一の作者が二つのポート上で補完したもので、歴史的な積み残しをポートごとに一つずつ解消していく性格のものだ。

3.2 VTOR がゼロのとき MSP を復元すべきでない（11-12）

日付：2026-11-12 13:29 と 14:30（提案時間）　出典：提案 #12044、提案 #12050、欠陥 #4728

最初のコンテキストスイッチの際、コードはベクタテーブルオフセットレジスタからスタックトップを読み出してメインスタックポインタを復元する。このレジスタを持たないカーネル、あるいは読み出し値がゼロの場合、メインスタックポインタをゼロに書き込むことに等しく、次のプッシュでアドレスゼロに落ちてしまう。修正法は、読み出し値がゼロのときは復元をスキップし、非ゼロなら従来の動作を維持するというものだ。

前項と同じ対の構造で、M0 に一つ、M23 に一つ、それぞれ三つのアセンブリ経路を変更する。二件合計で 18 行を追加し、欠陥 #4728 も同様に古い議題である。

3.3 mb/mq の FIFO 反転：先頭がバイパスされ追い越される（11-12）

日付：2026-11-12 13:56（提案時間）　出典：提案 #12045、欠陥 #4940

メールボックスとメッセージキューは先入れ先出しフラグの下では先頭の待機者のみを起床させるが、データは依然として共通キューに残っている。このとき、より高い優先度のスレッドが非ブロッキングでこのメッセージを取り去ると、起床された元の待機者は何も得られず、再び末尾に繋がれるしかなく、先着順の順序がここで反転してしまう。修正法は、先入れ先出し経路でリソースの予約と引き渡しを行い、すなわち「先に取得してからデキュー」し、タイムアウトやシグナルによる中断の際には予約を返却する。優先度モードの動作は変わらない。

一つのファイルで、435 行を追加、12 行を削除。本バッチ十件の中で最大の一件であり、カーネルのスケジューリングセマンティクスに直接触れる唯一の一件でもある。欠陥 #4940 も同様に古い積み残しだ。この一件がマージされれば、メールボックスとメッセージキューの高優先度プリエンプション時の実際の挙動が変わるため、次のリリースノートで個別に一言触れる価値がある。

3.4 四つの小さな修正：fdt 深度、musl コンソール、シリアルタイミング、sdio スレッドスタック（11-12）

日付：2026-11-12 13:23 から 14:14（提案時間）　出典：提案 #12048、提案 #12047、提案 #12042、提案 #12046

デバイスツリー展開関数は固定サイズのスタックで子ノードを再帰下降するが、実行時の深度上限がなく、既存の深度事前チェックはデバッグビルドでのみ有効で、リリースビルドでは依然としてスタックオーバーフローの可能性がある（#11879）：プッシュ前の上限判定を追加し、超過すれば失敗を返す。

musl ライブラリ設定の下では、カーネルがコンソールを設定する際にユーザー空間側のファイルオープンインターフェース群を呼び出しており、システムコールテーブルにトラップすると番号の位置がずれてコンソールが開けない（#11716）：カーネルファイルシステムの強シンボル経路に切り替え、システムコールテーブルには触れないため、ユーザー空間バイナリインターフェースには影響しない。この一件は削除行が追加行より多く、正しい階層に戻す書き直しに属する。

Smart 設定の下ではシリアルが端末デバイスとして登録されるタイミングがワークキューの作成より早く、起動がハングする可能性がある（#11718）：ワークキューが未準備のときはシリアルを保留キューに入れ、コンポーネント初期化段階で登録を補う。sdio 割り込みスレッドのデフォルトスタックサイズは元々アイドルスレッドに従っており、アイドルスレッドスタックが 512 に設定されているとこの経路がオーバーフローしやすい（#11694）：独立した 2048 のデフォルト値に変更する。

四件はいずれも静的確認とされ、ボード書き込みは未実施。これらは同一の監査ラインの延長であり、「範囲外書き込み」から「初期化タイミング」と「デフォルト設定」へと軸足を移しただけだ。

4. 機能と互換性：STM32 入力キャプチャ、YMODEM 遅延

4.1 STM32 入力キャプチャ：一つのタイマに四つのチャネル（11-12）

日付：2026-11-12 19:32（提案時間）　出典：提案 #12052

既存の STM32 入力キャプチャドライバは物理タイマを単位としてデバイスを登録し、一つのタイマで選べるキャプチャチャネルは一つだけで、同じチップ上の残りの遊休チャネルは使えず、チャネルペアに基づくパルス幅変調入力や両エッジ捕捉モードも存在しない。提案はドライバを次のように拡張する：一つの物理タイマに複数の独立したエッジキャプチャデバイスを登録でき（タイマ 1 から 4 はそれぞれチャネル 1 から 4 を選択可能）、タイマごとに排他的なパルス幅変調入力または両エッジモードを選択する。

5ファイル、1529行追加、290行削除。1週間続いた監査提案の中で、これが唯一の機能拡張であり、作者はその監査ラインではなくコミュニティ貢献者である。ドライバ類の構造的改造は通常ボードレベルの検証が必要であり、レビュー周期はセキュリティ修正より長くなる。

4.2 YMODEM：ACK と C の間に40ミリ秒を補う（11-12）

日付：2026-11-12 17:41（提案時間）　情報源：提案 #12051

YMODEM の受信側は2番目の転送終了記号を受け取った後、2バイトを連続して送信する：確認と文字 C である。2バイトを連続して送信すると、送信側のシリアルドライバのタイムアウト設定や割り込み処理が十分に安定していない場合、そのうちの1つ（確認のみ読み取り、文字 C を逃す）が呑み込まれ、送信側はそれによって転送失敗と判定する。修正方法は、2回の送信の間に40ミリ秒の遅延を挿入することである。

1ファイル、7行追加。この種の修正はプロトコルの意味を変えず、不安定なシリアルリンクに間隔を設けるだけであり、現場の経験をコードに書き戻したものに属する。

5. 公式見解とコミュニティ活動

5.1 RT-Smart ツールチェーン：同一議題に2回の提案、2回のクローズ（11-13）

日付：2026-11-10 から 2026-11-13（議題とクローズ時間）　情報源：欠陥 #12025、提案 #12041、提案 #12028

議題本体はコンパイル問題である：QEMU 仮想マシン上で Smart と vDSO を有効にした後、newlib ツールチェーンでユーザー空間ライブラリをコンパイルすると、4つのクロック定数が未定義となる。メンテナは11月10日に再現し修正方法を示したが、3時間後に自己修正し、「Smart に対しては、ツールチェーンは特別な、musl ライブラリを変更したコンパイラを使用する必要があり、通常の newlib ツールチェーンはサポートされない。この問題は処理すべきではない」と位置づけた。最初の提案は当日クローズされた。

今日未明、同一作者が2番目の提案を提出し、互換ヘッダファイルを追加して、Linux インターフェースの数値に従って欠落定数を補完し（単調原始は4、リアルタイム粗は5、単調粗は6、起動時間は7）、クロックからインデックスへのマッピングを変更していないと宣言した。この提案は北京時間今日06:04にクローズされ、議題も同時に完了状態でクローズされ、コメントはただ一言：この議題は一旦クローズし、後続でいくつかの関係説明を提示する必要がある。

2回の提案、2回のクローズ、落点は「コードを直す」から「ドキュメントを補う」に変わった。Smart を使用する開発者にとって、この点は修正自体よりも有用である：ツールチェーンを間違えるとコンパイル段階で行き詰まるが、公式ドキュメントは現在この層の関係を明確に書いていない。

5.2 公式ニュースインターフェースは連続5期目で新規なし（11-13）

日付：2026-11-13（確認時間）　情報源：RT-Thread 公式ニュースリスト

インターフェースが返すのは依然として11月6日のあの5件であり、最新の1件の時間は11-06 15:54：elexcon フルスタック能力、Vinaro 産業 PLC サロン、東南アジア大学産教融合、臨港自動車ソフトウェアエコシステムサロン、工博會 AI 小车 Workshop。これらはすでに11-09期（週末をカバーする72時間の調査期間）で全収録され、11-10から現在まで連続5期新規なし。

公式サイトのニュースページのリストはクライアントレンダリングのため、項目を取得できず、インターフェースを基準とする。対外発信は定例会議の空白期間に入ってすでに1週間が経過した。

5.3 Google News 3日間の調査期間で実質的なヒットなし（11-13）

日付：2026-11-13（確認時間）　情報源：Google News 検索

中国語の精确クエリ3日間の調査期間で2件、いずれも技術サイトの総合稿であり、テーマはそれぞれ Android プラットフォームの進化とスマートホームのフルスタック開発で、本文でついでに RT-Thread に言及しているが、報道可能な事象を構成しない。他に2件の中国語クエリはノイズに属する：「睿擎」は自動車購入ガイド稿3件にヒットし（格瑞維亜と塞納の比較、「睿擎」の2文字が車種構成名に落ちている）、「睿賽徳」はゼロヒット。英語クエリ1件は、コーヒー器具オープンソースプロジェクトのリスト稿で、誤マッチに属する。

GitHub 組織側も同様に静かである：プッシュ時間でソートしたリポジトリでは、メインリポジトリのみが調査期間内にコミットがあり、パッケージインデックスリポジトリの最終プッシュは11月9日、環境ツールリポジトリはさらに早い。新規バージョンタグはなく、最新正式バージョンは依然として9月10日の5.3.0である。

6. まとめとトレンド観察

6.1 昨日予告した第2段階が当日に実現

前号の判断は「監査が CVE リストから自社議題へ転換」であり、今日の事実が2つの段階をつないだ：11月9日と10日に提出されたあの一連の提案は、11月12日の日中に集中的に6件マージされ、そのうち3件は CVE 番号付き（乱数、無線管理、rt-link 送信側）、残り3件はそれぞれ動的モジュール再配置、メモリプールアサーション、NFS 読み取り長である。

マージ時間は北京時間09:35から15:51まで並び、6時間以内に完了した。マージ者は同一人物であり、このラインがすでに安定したレビューチャネルに入っており、もはや散発的なコミュニティ提出ではないことを示している。

6.2 6件マージの検証基準：すべてボード書き込み未実施と标注

6件の検証段はほぼ同じ構文である。静的照合、ボード未実行、攻撃サンプル未構築。唯一自動化テストケースを伴うのはメモリプールの件で、40余行のテストが添付されていた。NFSの件では、あるレビュアーが実装を項目ごとに照合し結論を出した。

これは効率の源であると同時にリスクの所在でもある。静的レビューは長さとインデックスの算術エラーを捉えられるが、タイミングと並行性は捉えられない。「先に取得してからデキュー」のようにカーネルセマンティクスを変更する提案は、やはりボードレベルと負荷試験の証拠がなければ安心できない。

6.3 3件のCVE提案は依然キュー内

同時期に提出されたCVE番号付きの別の3件は本日動きがなかった。コマンドラインファイル操作のパス構築（CVE-2024-25390）、変数エクスポートテーブルの填充（CVE-2024-25392）、YMODEMパスコピー（CVE-2024-25394）。3件の形態はすでにマージされた6件と類似しており、いずれも無界コピーと容量制限であり、レビュー未通過は単なるスケジューリングの問題かもしれない。

他にも非CVEの提案が数件キューに滞留している。Smartのプロセス間オブジェクト帰属検証（#12015、複数ファイルにまたがるセマンティクス改造）、ESP32-C3チップバージョンフィールド（#12013）、DHCP期限切れリース回収（#12024）。

6.4 レビュー待ちキュー163件の提案、358件のイシュー

前回と比較して、提案は5件増、イシューは7件減。イシューの減少は本日クローズされた若干の項目（マージ提案に伴いクローズされた旧イシューとSmartツールチェーンのイシューを含む）に対応し、提案の増加は主に本日新規提出された10件による。

単一アカウントへの集中度は記録に値する。本日マージされた6件と新建の10件（当日クローズされた1件を含む）は同一作者によるもので、マージは同一メンテナによって完了した。1本の監査ラインを1人が推進し1人がゲートキーパーを務めることは効率が高いが、このラインのリズムがこの2人の時間に完全に依存することを意味する。
