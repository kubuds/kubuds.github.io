1.1 ARM 設定を公共 Kconfig から搬出：libcpu がアーキテクチャ別に分離開始（11-05）

日付：2026-11-05 22:26（マージ時刻）　来源：提案 #11988、議題 #9187

267 行追加、173 行削除、3ファイル：libcpu/arm/Kconfig を新設し、元の libcpu/Kconfig にあった ARM 関連のアーキテクチャ識別子、カーネルモデル、ARM MMU/MPU と GIC 設定を全体としてアーキテクチャディレクトリへ移動、元の場所では rsource で導入；公共能力とクロスアーキテクチャの KERNEL_VADDR_START は元ファイルに残す。作者 zijunteng238-dot は午前 11:51 に提案を作成し、夜 22:26 にマージ、10時間半で全行程を完了。

今回の手法は特筆に値する：新規メニューを追加せず、シンボルを変更せず、デフォルト値を変更せず、依存関係と select 関係も変更せず、ただ引っ越すだけ。検証方法も「コンパイルが通れば良し」ではない——作者は Kconfiglib 14.1.0 を用いて分割前後の全解析シンボルを比較し、設定値、型、可視性、代入可能範囲、デフォルト値と選択関係を項目ごとに一致させ、ファイルパスと行番号の変化を除いて新規解析警告がないことを確認；比較は5つの BSP をカバー：frdm-k64f（Cortex-M4）、qemu-vexpress-a9（Cortex-A9）、renesas/rzt2m_rsk（Cortex-R52）、qemu-virt64-aarch64 と qemu-virt64-riscv、さらに RISC-V 上で scons –menuconfig を実行してメニュー出力を比較。加えてメモリ上で A9、AArch64、RISC-V に対して SMART と IOREMAP_LATE を有効にして再度比較し、設定ファイルには書き戻していない。

長期保守にとっての意義は構造にある：libcpu/Kconfig はこれまで CPU 公共能力とマルチアーキテクチャ設定を混在させており、どのアーキテクチャがオプションを追加しても同じファイルを触る必要があり、アーキテクチャ数の増加とともに衝突と誤変更の確率が上昇していた。今回の分割により、RISC-V、ARM それぞれの Kconfig が独立して進化可能となり、前回文書化したリリースプロセスと同じガバナンスライン上にある——まず構造を整え、それからバージョンリズムを語る。併せて documentation/4.tool/scons/libcpu_kconfig_arm_split.md を新設し、分割範囲、依存処理と検証結果をリポジトリに記載、今後の他アーキテクチャの移行はこれを踏襲できる。

1.2 RISC-V Smart の MMU とユーザ例外：四箇所の根本原因をまとめて修正（11-05）

日付：2026-11-05 11:15（マージ時間）　情報源：提案 #11892

109 行追加、8 行削除、4 ファイル、メンテナ BernardXiong による提案、10 月 18 日作成、今期マージ、途中 11 件のインライン・レビューを経過。これは RISC-V 側の RT-Smart にとって今期最も実質的な一件である。

変更は 4 つの根本原因を挙げており、いずれも同一種の問題の異なる側面である。第一に、初期ページテーブルポインタがカーネル物理オフセットによる変換を行っておらず、カーネルが非ゼロ物理アドレスにロードされた際にページテーブル記述子が誤った場所を指す。第二に、各 hart のカーネルページテーブルがユーザマッピングを継承しており、hart 間にあってはならないアドレス空間を残していた。第三に、初期ページテーブルが MMU 有効化前にクリアされていなかった。第四にして最も致命的な点：未処理のユーザ態例外が現在のプロセスのみを終了させず、カーネル全体を終了させてしまう——ユーザプロセスの一本の野ポインタでシステムが停止し得る。

対応する修正は：玄鉄アーキテクチャ選択と SVPBMT オプションを追加；初期ページテーブルポインタにカーネル物理オフセット変換を付与；MPR 範囲をリンク済みカーネルベースアドレス未満まで拡張可能に；MMU 有効化前に初期ページテーブルをクリア；各 hart のカーネルページテーブル内のユーザアドレス項目をクリア；ユーザ例外は現在の LWP のみを終了；ユーザコンテキスト報告期間中は割り込みを有効のまま維持。

検証条件は率直に書かれている：BSP は qemu-virt64-riscv と bsp/k230 を使用、RT_USING_SMART に ARCH_RISCV64 を追加、作者はローカルでビルドを実行しておらず、その理由は環境に RISC-V musleabi ツールチェーンがないためで、CI 検証に委ねている。これは前回のシリアルポートの一件の検証説明と同じ率直さであり、方向性に問題はないが、RISC-V Smart のこのラインの実行時挙動はやはり実機再テストで担保するのが望ましい。

2.1 ivshmem がデバイス設定ワードを信頼できる入力として扱い、/dev ノードが任意物理メモリへの通道になる（11-06）

日付：2026-11-06 00:54（報告時間）　情報源：欠陥 #11992

報告者は XueDugu で、最近数期にわたる PCI とデバイスドライバ側の一連の流れの続きである。問題は ivshmem ドライバのプローブ関数にあり、BAR2 の報告するサイズがゼロの場合、コードは JailHouse フォールバック分岐へ進み、PCI 設定空間 0x40 から 0x4f までの 4 つのダブルワードから共有メモリのアドレスとサイズを直接読み取る——これら 4 つはデバイス側が決定し、ドライバには何の検証もなく、その後 rt_ioremap に渡されるが、rt_ioremap 自体は物理アドレスの正当性をチェックしない。

結果の連鎖は短い：悪意のある、または異常な形式のデバイスが「共有メモリ」をカーネルメモリ領域として記述しても、マッピングはそのまま成功し、ウィンドウは /dev/ivshmemN として登録される。その後の読み書きは公式の open/read/write 経路にある 2 回の memcpy を通り、1 回はカーネル内容をユーザーへコピーし、1 回はユーザーデータをカーネルへ書き戻す。こうして非特権プロセスがこのデバイスノードを開くだけで、任意のカーネル物理メモリの読み書き能力を得られ、バイト粒度でデータは完全に制御可能であり、特別な ioctl や追加権限は一切不要である。

報告は付随する問題も 1 点指摘している：元のコードは 64 ビットフィールドを 2 つの 32 ビット書き込みに分割しており、32 ビットビルドでは隣接フィールドに書き込むことになり、構造体を破壊してしまう。これは MSI-X の件と同じパターン——デバイスファームウェアが提供する値が信頼できる入力として扱われ、ドライバ側に「まず検証してから使用する」という定型動作が欠けている。

2.2 2 時間 11 分後に修正が出る：新オプションで JailHouse フォールバックを檻に入れる（11-06）

日付：2026-11-06 03:05（提案時間）　情報源：提案 #11993

99 行追加、7 行削除、2 ファイル、メンテナの BernardXiong による提出、状態はレビュー待ちで、ディスカッションが 1 件ある。

修正方法は 4 層に分かれる。第 1 層は危険な経路をデフォルトで閉じる：新たに RT_IVSHMEM_JAILHOUSE オプションを追加し、デフォルトは n、ヘルプテキストにはデバイスが信頼できるものでなければならないと明記；これを開かない場合、BAR2 が存在しなければプローブを直接拒否し、設定ワードを読まない。第 2 層はマッピング前の検証：サイズが非ゼロ、アドレス加算でサイズがオーバーフローしない、区間全体がローカルポインタとサイズ型で表現できること。第 3 層は型修正：4 つの設定ダブルワードをまず 64 ビットローカル変数に読み込み、32 ビットエイリアス経由で構造体フィールドに書き込まないようにし、併せて隣接フィールドが踏まれる問題も修正。第 4 層は設定空間読み取りの戻り値をチェックし、読み取り失敗時は続行しない。

検証はコンパイルとフォーマットまで：2 つのオプション組み合わせ（JAILHOUSE オフとオン）は qemu-virt64-aarch64 上でいずれもコンパイル通過し、変更ファイルは clang-format を通る。00:54 の報告から 03:05 の提案まで 2 時間 11 分で、前回の MSI-X の 6 時間よりさらに一歩速い。

3. 公式・コミュニティイベント

3.1 Titan Board が OpenMV に接続：170 個の Python サンプル、NPU は TFLM を使用（11-05）

日付：2026-11-05 17:30（コラム公開時間）　情報源：電子工程專輯：Titan 也能玩 OpenMV 了、工程：Titan_Openmv

RT-Thread 公式コラムは本期、Titan Board の OpenMV プロジェクトを公開し、RT-Thread 5.1、OpenMV 5.0.1、MicroPython をルネサス RA8P1 ベースのこのボードに搭載した：1 GHz Cortex-M85 がシステムとアプリケーションを実行し、250 MHz Cortex-M33 がコプロセッシング、Ethos-U55 NPU は 500 MHz に設定され、外付け 32 MiB HyperRAM が画像と実行メモリを保存し、ピーク AI 演算性能は 256 GOPS と公称される。ペリフェラル側は OV5640 MIPI カメラ、FAT/FAT32 SD カード、USB HS の CDC と MSC 複合デバイス、およびオンボードの三色 LED とボタンに接続する。

サンプル規模が今回の主なセールスポイントである：計 170 個の独立した Python スクリプト、従来型ビジョンが 124 個で、カメラ制御、撮影・録画、描画、フィルタリング、カラートラッキング、バーコード、特徴検出、AprilTag をカバー；機械学習が 23 個で、Ethos-U55-256 向けの 20 個のモデルファイルと CPU 実行の数値回帰モデルを備え、タスクはジェスチャー（じゃんけん、手掌検出、21 点の手部キーポイント）、顔と姿勢（顔検出、468 点キーポイント、人体姿勢）、物体認識（歩行者、猫犬、COCO80 の一般的な物体）、画像分類・セグメンテーションをカバーする。

プロジェクトの構成方法は実際の導入に役立つ：コードは SDK の project/Titan_Openmv にあり、RT-Thread Studio と SCons の両方をサポート；ビルドは必ず組み合わせて使用する二つのファイルを生成する——rtthread.hex は DAP-Link または J-Link で書き込み、openmv-vision.bin は USB 複合デバイスで転送し、両者は同一のビルドに由来しなければならない。モデルとラベルは models/sdcard/ に置き、説明に従って SD ルートディレクトリにコピーすればよい；スクリプト内の /rom は SD ルートディレクトリの読み取り専用エイリアスであり、別途ディレクトリを作成する必要はない；作品を起動時に自動実行したい場合は、アプリケーションを SD ルートディレクトリの main.py として保存する。文中ではさらに、IDE に表示される AE3 はプロトコル互換の識別子に過ぎず、Alif AE3 のファームウェアを書き込んではならないこと、ボードは本プロジェクトの RA8P1 ファームウェアを使用していることを特に注意喚起している。

二点の技術的判断：一つ目は、この組み合わせが「カメラ取得、画像処理、ニューラルネットワーク推論、ペリフェラル制御」を同一の Python スクリプトに連結し、エッジビジョンの敷居を C ドライバの記述からパラメータの変更へと下げたこと；二つ目は、オペレータがサポート状況に応じて CPU と NPU の間で振り分けられ、TFLM がスケジューリングを担当するため、モデルが動作するかどうかはオペレータのカバレッジに依存し、サンプル内の 20 個のモデル自体が利用可能なカバレッジリストとなっていることである。

4. エコシステムとベンダー適応

4.1 ESP32-C3 プリビルドイメージが v1.x チップを拒否：最小リビジョンフィールドが未整合（11-05）

日付：2026-11-05 23:24（報告時間）　情報源：不具合 #11991

報告者は anamarija-j、影響バージョンには v5.3.0 と master cbadbdf と明記され、ハードウェアは ESP32-C3、チップリビジョン v1.1（ROM バージョン esp32c3-eco7-20230720）、BSP は bsp/ESP/ESP32_C3。これは今回唯一の RISC-V BSP の回帰不具合である。

現象は二段階に分かれる。esptool は書き込みを直接拒否し、プリビルドの bootloader.bin がチップリビジョン3以上を要求するのに対し、このボードはリビジョン1であると提示する；–force で強制書き込みすると、セカンドステージ bootloader は起動できるが、パーティションテーブルを読む前に停止し、ログにはチップが V101、アプリ設定の最低リビジョンが3と明記される。

根本原因はフィールドの意味論にある。プリビルド bootloader は旧フィールド min_chip_rev のみに値3を設定し、完全フィールド min_chip_rev_full は0である；この ESP-IDF v5.0-dev の bootloader はちょうど旧フィールドとマイナーバージョン番号を比較し、v1.1 のマイナー番号は1であるため、条件を満たさないと判定する。BSP の SConstruct も同様に image.min_rev = 3 のみを設定し、生成される rtthread.bin も同じ問題を抱える。言い換えれば、同じ「最低リビジョン」を新旧二組のフィールドで表現しており、プリビルド成果物とビルドスクリプトがいずれも旧の組のみを書いているため、新ルールで解釈するチップに遭遇すると詰まる。

この影響範囲は小さくない。ESP32-C3 は RT-Thread エコシステムで最も一般的な RISC-V ワイヤレス MCU の一つであり、プリビルドイメージが使えないことは新規ユーザが初めてボードに載せた時点で失敗することを意味し、自力で一からビルドするしかない。修正方法は複雑ではない。SConstruct とプリビルド成果物の両方に min_chip_rev_full を書けばよいが、併せて再パッケージが必要となる。

4.2 BSP とテスト基盤の5件：D1s が QEMU へ、efm32 が menuconfig へ、3組のフレームワークテスト（11-05）

日付：2026-11-05（マージ時間）　情報源：提案 #11903、提案 #11867、提案 #11883、提案 #11982、提案 #11976

BSP 側は2件で、いずれも「ボードを使いやすくする」方向だ。Allwinner D1s は qemu-d1s.sh 起動スクリプトを追加し、d1s の QEMU マシン上でこの BSP を直接実行できるようになり、イメージ探しとパラメータ組み立ての手間を省いた（#11903）。EFM32 は Kconfig と .config を追加し、scons –menuconfig を正式サポートした。これまでは設定を手で変更するしかなかった（#11867）。

テスト基盤は3件で、方向は一致している。フレームワーク自体に模擬デバイステストを追加するものだ。ウォッチドッグはスモークテストを追加し、タイムアウト量子化の誤差と停止不能なシャットダウンパスを許容する（#11883、対応する欠陥 #11446）。I2C は模擬バスでフレームワーク層をカバーし、実ハードウェアに依存しない（#11982）。DAC は模擬デバイスでテストする（#11976）。3件はいずれもコミュニティ貢献者から提出され、2.5 で審査待ちの QEMU 自動実行改修を加えると、明確な動きが見えてくる。ドライバフレームワークの検証を「ハードウェア待ち」から「CI へ」に変えることだ。

5.2 趨勢：デバイス側入力が第二の主戦場になる

直近4期を続けて見ると、攻撃面が移動している。10月末から11月初頭に報告されたのは主にシステムコール層の「値からオブジェクトへ」の検証欠如だ。getaddrinfo のネストしたユーザーポインタ、pipe の ioctl ポインタ、timerfd、ブロックデバイスパーティションの生ポインタなど。本期の2件の新欠陥は前提が変わっている。MSI-X は悪意あるデバイスを挿入することを要求し、ivshmem はデバイスが設定ワードをカーネルアドレスに書き込むことを要求する。共通点は、デバイスファームウェアが提供するレジスタをカーネルが信頼できる入力として扱い、rt_ioremap が物理アドレスの合法性チェックを行わないため、「デバイスが言うままにマッピングする」ことだ。

対応速度は別の軸だ。MSI-X は報告から提案まで6時間、マージまで2日。ivshmem は報告から提案まで2時間11分。報告者は PoC、ログ、バージョン追跡を備えた完全な資料を提供し、メンテナは受け取れば直接修正できる。これはプロセス規定よりも修復時間を圧縮する。代償はキューの厚みが増し続けることだ。審査待ち更新48件、ブロックデバイスパーティションの件は3日経ってもまだマージされていない。

第3の軸は構造とツールの同期推進だ。libcpu/Kconfig はアーキテクチャ別に分離を始め、バージョン番号とリリースプロセスは成文化され、Env のプラグイン配布は中央集権マーケットから「リポジトリインデックスと Release」に変わり、テストはハードウェア待ちから CI へと変わった。この4つは同じ線上にはないが、いずれも「人に覚えさせる」を「構造的制約に頼る」へ置き換えるものだ。
