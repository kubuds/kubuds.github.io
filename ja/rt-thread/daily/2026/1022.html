1. カーネルとバージョン動向

1.1 3年間保留されていたタイムスライススケジューリング提案の再確認：判別式は #11907 と結論が一致するも、「READY の書き込みを遅延」がシングルコアで二重解放を引き起こす（10-21）

日付：2026-10-21 14:16 ~ 14:41（コメント時間）　出典：PR #6645、PR #11907

2022-11-23 に提出されたタイムスライススケジューリングパッチ（#6645）は長らく Status: waiting for test のまま放置されていたが、コミュニティメンバー Yunlk が調査期間内に3件のコメントを連続投稿し、レビューの视野に再び引き戻した。第一に、パッチが変更する src/scheduler.c は現在のメインラインで scheduler_comm.c、scheduler_up.c、scheduler_mp.c に分割されており、元のパッチは直接適用できない。コメントでは変更点と新版ファイルの箇所ごとの対応が示された。第二に、このパッチの中核となる判別式——「まだ実行中でタイムスライスを使い切らずにプリエンプトされた」場合のみ先頭に挿入し、それ以外はすべて末尾に回す——は #11907 が独立に導いた結論と完全に一致しており、互いを知らない2つの経路が同じ判断に収束したことについて、作者はこれ自体が方向性の有効性の傍証になり得ると述べている。第三に、真の相違点は実装手段にある。本パッチは先頭挿入時に READY を書き込む上書きを削除し、末尾挿入時に統一してセットし YIELD をクリアする方式に変更したため、挿入期間中もスレッド状態が RUNNING のままとなる。

この論理に従ってシングルコア経路へ移植した後、QEMU vexpress-a9 上でセマフォの起床順序は BA から AB に修正され、起動順序は DC から CD に修正され、3 スレッドのタイムスライスラウンドロビンは正常に動作したが、スケジューラグループの utest が安定してクラッシュする：rt_smem_free のアサーション失敗で、バックトレースは rt_free ← rt_defunct_execute ← idle_thread_entry、すなわち idle が終了済みスレッドを回収する際に同一 TCB を二重解放しており、2 回の実行で同一テストケースにて再現した。隔離実験として rt_schedule() 内の元の YIELD クリアを戻したが、クラッシュは変わらず、問題はクリア位置に由来せず、「READY の遅延書き込み」に由来することが示された。SMP（デュアルコア構成）を追加検証した後も判別式は同様に有効であり、二重解放はシングルコア経路でのみ観察された。著者は同時に、自身の以前の「SMP 未検証」という記述を訂正した。結論としての提案：判別式は維持する価値があるが、#11907 の「先に stat_before を保存してから判定する」を基礎として進め、#6645 を継続する場合はまずシングルコア下の二重解放を調査する必要がある。

1.2 動的モジュール未初期化グローバル変数の修正：BSS セグメント割り当てポインタが進まないなど 4 箇所の欠陥を併せて処理（10-21）

日付：2026-10-21 21:09（作成時間）　情報源：PR #11915、Issue #5705

貢献者 usualtreee が 2022 年 3 月に報告された #5705 に対して修正を提出し、問題は現在のメインライン 1c801efa 上でも再現可能である。欠陥は再配置可能モジュール（ET_REL）のロード経路 dlmodule_load_relocated_object()、すなわち Cortex-M など RT_USING_MODULE を有効化したボードが通る経路に集中している：第一に、BSS セグメント（SHT_NOBITS）のロード後に割り当てポインタが進まず、複数の NOBITS セグメントが同じメモリ領域で重なること。第二に、セグメントシンボルの再配置式にセグメントリンクアドレスの補正が欠けていること。第三に、SHN_COMMON シンボル（tentative 定義の未初期化グローバル変数）が黙ってスキップされること。原因はコードが shdr[0xfff2] を読んでセグメント名を取得し、ゴミ値を得た後に一致しないためである。第四に、この経路は module->symtab を決して構築せず、dlsym() は ET_REL モジュールに対して常に失敗すること。

修正方法は 4 点に対応する：BSS セグメントのロード後にセグメントサイズに応じてポインタを進める。rodata/bss/data セグメントの再配置を一律に「セグメントロードアドレス − セグメントリンクアドレス + シンボル値」とする。SHN_COMMON 用に別途コモンブロックを割り当て、この分岐をセグメント名一致の前に置くことで範囲外読み取りを回避する。.symtab からグローバル関数シンボルを収集して module->symtab を構築する。2 ファイルの変更 +147/-9、qemu-vexpress-a9 上で 3 つのテストモジュールにより検証：修正前は ET_REL モジュールの dlsym が失敗し、修正後は成功、かつ 2 つの未初期化グローバル変数アドレス（0x600d2008 と 0x600d2004）が重ならず、特徴値の書き込み・読み戻しが通過し、2 つの ET_DYN モジュールの結果は変わらない。提案は CLA を通過済みで、components グループのレビュー中である。

2. セキュリティと安定性のフォローアップ

2.1 NFS 読み取り経路がサーバ側カウントを memcpy 長として使用：1 回の cat で戻りアドレスを上書き可能（10-22）

日付：2026-10-22 02:13（作成時間）　情報源：Issue #11917、dfs_nfs.c

貢献者のXueDugu氏がNFSクライアントの欠陥票を新規起票した。直接利用可能なメモリ破壊に該当する。nfs_read() は要求長を1024バイト以内に制限しているが、コピー時にはサーバー応答内の READ3resok.count を使用しており、呼び出し側の要求長とも、同じ応答内でデコードされたデータ長とも比較していない。XDRデコード側は xdr_bytes(..., ~0) を上限としており、長さ検証が永遠に発動しない。2つのカウントフィールドはプロトコル上互いに独立しており、悪意あるサーバーは80バイトの要求に対して count = 512 と512バイトのデータを返すことが完全に可能である。

影響は組み込みの cat コマンドに及ぶ。dfs_file.c は char buffer[81] で読み取りを受けているため、1回のcatでファイルを1つ読むだけでバッファ末尾を最大約430バイト越え、finshスレッドのスタック上の戻りアドレスを上書きできる。この欠陥は2010-05-20のコミット 0fbfdec40d で導入され、v1.2.0以降のすべてのバージョンが影響を受け、v5.3.0と現在のメインラインを含む。作者はQEMU vexpress-a9とRP2350実機でそれぞれ再現した。NFSクライアント自身がAUTH_SYSを組み立て、認証なしのUDPを使用するため、マウント先のサーバーまたは経路上の注入者がオーバーフロー内容を制御できる。この票は現在未アサインである。

2.2 raw-API DHCPサーバーのオプション走査に境界欠如：最大1500バイトバッファを4バイト超過（10-21）

日付：2026-10-21 15:49（作成時間）　情報源：Issue #11913、dhcp_server_raw.c

別の研究者K-ANOY氏がraw-API DHCPサーバーの範囲外読み取りを報告した。オプション検索関数は返却ポインタがバッファ内に収まることのみを保証しており、走査時に buf[1] について先に buf + 1 < end を検証していない。末尾に1バイトだけ残ったオプションヘッダーは1バイトの範囲外読み取りを引き起こす。呼び出し側はその後固定幅で値を取得し（要求IPは4バイト、メッセージタイプは1バイト）、オプションヘッダーを末尾に置くだけで opt[2]..opt[5] が1500バイトのpbufヒープブロックを最大4バイト超過する。同じディレクトリのソケットベースの dhcp_server.c はちょうどこれらのチェック——長さが範囲外か、宣言長が有効か、length < 4 と length < 1——を行っており、raw版に欠けているのはまさにこれらの数項目であることを裏付けている。

トリガー条件は同一セグメントの任意のホストがUDP/67へオプション領域が切り詰められたパケットを送るだけで、認証は不要である。作者はASan下で論理レベルの再現を完了し、読み出された値は比較と分岐にのみ使用され、直接外部へ送信されないと指摘した。この票には bug と component: net タグが付与済みで、未アサインである。

4.1 ESP-IDF v6.1 パッケージ側合流：C3/C6 に RT-Thread で FreeRTOS を置き換える公式スイッチが登場（10-21）

日付：2026-10-21 15:23（合流時刻）　情報源：RT-Thread-packages/esp-idf PR #18

RT-Thread-packages の esp-idf パッケージは 5.1 から 6.1.0 へのパッケージ全体のアップグレードを完了し合流した。変更ファイルは二万余。公式 v6.1 に対し、今回の合流には RT-Thread 側の構造的変更が三点含まれる：components/rtthread/（C3/C6 の移植層、rtconfig.h、board/context、CMake とリンクスクリプト）の新規追加、components/riscv/vectors_rtthread.S の新規追加、そして FreeRTOS、esp_system、esp_timer などに CONFIG_IDF_RTOS_RTTHREAD スイッチ経路を追加；menuconfig では「Component config → FreeRTOS → Extra → Replace FreeRTOS with RT-Thread」に対応する。RISC-V にとってこの一歩の意義は次の点にある：C3、C6 は RISC-V コア（Xtensa の S2/S3 とは異なる）であり、従来は IDF 5.x 上で旧統合方式により RT-Thread を動かすしかなかったが、現在は 6.1 の土台と公式に認められたカーネル置換経路を手に入れた。

4.2 BSP 側の同一バッチ提案のブロック解除：C3 の十三構成が全て通過、実機検証待ち（10-21）

日付：2026-10-21 15:24（コメント時刻）　情報源：PR #11870

パッケージ側と配套するメインリポジトリの提案 #11870 は、本調査期間中にメンテナから「esp-idf は合流済み」との返信を得て、従来のブロック要因が解消された。同提案は 55 ファイル +4554/-333 を変更：C3 と C6 はそれぞれ ESP-IDF v6.1 の互換面（portmacro.h の FreeRTOS V11 宣言、sections.ld、port.c、main.c、rtconfig.py および ADC/SPI ドライバの小修正）に適配し、RISC-V ツールチェーンを gcc 11.2（esp-2022r1）から gcc 15.2（esp-15.2.0_20251204）へ引き上げ、CI workflow、docker と tools/ci も同期調整した。作者の検証によれば、C3 の十三の attachconfig 構成が全てコンパイル通過、C6 のデフォルト構成がコンパイル・リンク通過であり、実機検証は依然として未補完；ESP32-S3 の移植と FreeRTOS 互換層の変更は別提案として起票され、このコミットには含まれない。

4.3 OSPI と OctaFlash がコンポーネント層に進出：SFUD が 1-1-1 と 8-8-8 の二モードをサポート（10-21）

日付：2026-10-21 15:22（作成時刻）　情報源：PR #11912

既存のドライバ層には SPI と QSPI の経路しかなく、SFUD を介して八線 Flash にアクセスする原生パスは存在しなかった。本提案はコンポーネント層に OSPI を補完する：バス、デバイス、設定とメッセージ定義および転送ヘルパーを新規追加しつつ、既存の SPI/QSPI 経路を保持；OSPI 転送とデバイス検出を SFUD に接続し、読み取り、書き込み、消去とステータス照会をカバーし、デバイステーブルに MX25LM51245G を検証用に追加する。全チェーンを通すため、汎用 STM32 OctoSPI 下位ドライバ drv_ospi.c（504 行）と L4 シリーズ設定ヘッダを追加し、stm32l4r9-st-eval ボード級に OCTOSPI1 のピン、クロックと MSP 設定および OPI STR/DTR モードへ入る補助関数を補完し、併せて同ボード級のヒープとリンク配置による .bss 重複を修正した。変更は 32 ファイル +3728/-956、四つのコミット、CLA 署名済み、レビューは STM32 グループのメンテナ三名がアサイン済み；作者は実機で GCC ビルドにより実行し、1-1-1 と 8-8-8 の両モードが SFUD に認識されることを報告している。

4.4 Cortex-A の GIC プリント関数の書式指定子修正：%p に非ポインタを渡すのは未定義動作（10-21）

日付：2026-10-21 18:00（作成時刻）　情報源：PR #11914

libcpu/arm/cortex-a 配下の GICv2 と GICv3 の情報出力関数には、4 種類の書式指定子と実引数型の不一致が存在する。物理アドレスは rt_uint32_t であるにもかかわらず %p で出力しており、これは未定義動作である。GIC バージョン番号は unsigned long、最大割り込み番号と割り込み番号は unsigned int であるにもかかわらず、いずれも %d を使用している。-Wall -Wformat で Cortex-A ボードをコンパイルすると、これらはすべて警告となる。提案では %p を 0x%08x に、%d を %u に変更し、0xfUL から取り出したバージョン番号には明示的な unsigned int 変換を追加する。2 ファイルで +64/-40、書式指定子のみを変更し実行時ロジックには触れない。

4.5 睿擎 V1.8.4 と新 IDE：エンコーダ、MIPI RGB666、GPIO 上下拉、GD32H7 プロジェクト対応（10-21）

日付：2026-10-21 11:50（公開時間）　情報源：電子工程専輯：睿擎プラットフォーム V1.8.4 リリース、睿擎ドキュメントセンター

睿擎プラットフォームが V1.8.4 をリリースした。SDK 側では 6 項目の新規追加、4 項目の修正があり、RuiChingStudio IDE も同時に V1.5.62 へ更新された。新規機能は RC3506 のペリフェラルと表示に集中している。QY1503 絶対値ロータリーエンコーダドライバを追加し、SSI インターフェースを使用するとともに直交パルス PWM 出力のサンプルを提供する。モータのクローズドループと角度測定向けである。MIPI DSI に RGB666（18 ビット色深度）対応を追加し、表示フォーマットと lane 数はデバイスツリーで設定する。mipi_display_start() インターフェースを公開し、アプリケーションが表示初期化のタイミングを自ら決定できるようにして、表示とバックライトの電源投入順序を調整しやすくした。GPIO には PIN_MODE_INPUT_PULLUP と PIN_MODE_INPUT_PULLDOWN の 2 種類の入力モードを追加し、外付けの上下拉抵抗を不要にした。amp_device デバッグコマンドを追加し、AMP アーキテクチャ下でのデバイス帰属（RT-Thread 側または Linux 側）、割り込みアフィニティ、クロック周波数を確認できる。IDE 側では GD32H7 シリーズのプロジェクト作成、ビルド、J-Link/DAP-Link ダウンロードデバッグ対応を追加し、GD32H7 と RK3576 プロジェクトのリンクフローを最適化した。完全な更新ログと SDK はドキュメントセンターに同期済みである。

5. 業界応用

5.1 睿擎 V1.8.4 の産業現場向け修正：EtherCAT 割り込みアフィニティ、telnet 下の netstat 停止、UART DMA ボーレート（10-21）

日付：2026-10-21 11:50（公開時間）　情報源：電子工程専輯：睿擎プラットフォーム V1.8.4 リリース、睿擎更新ログ

同一バージョンの 4 項目の修正はすべて産業現場を指向している。EtherCAT のタスクと割り込みはこれまで同一 CPU にバインドされておらず、割り込みはデフォルトで CPU0 に落ち、マルチタスク切り替え時に偶発的なアクセス競合とフリーズが発生していたが、修正後は両者が同一コアにバインドされる。telnet でリモート実行した netstat がブロックして応答しなくなる問題は修正済み。UART DMA サンプルでボーレート設定が失敗する問題は、根本原因が DMA シリアル初期化フローにあり、修正済み。4.3 インチ画面サンプルはバックライト PWM を引き上げ、屋外での視認性を改善した。前号で既報の EG1200 産業ゲートウェイの仮想ネットワークインターフェースと NFS マウント、および RC-Pi-3506 ベースの ROS2 ハブモータ運動制御方案と合わせると、睿擎のこの製品ラインは今号において「ゲートウェイ側のネットワーク接続能力」と「運動制御側のリアルタイム性」の 2 つを並行して推進している姿が現れており、修正項目も多くは実際のプロジェクトからのフィードバックに由来し、内部テストによるものではない。

6. まとめとトレンド観察

6.1 今号のトレンド

  • スケジューラ議論は「各自の提案」から「実装比較」へ：3年間保留されていた #6645 が再確認され、その判別式は #11907 と独立に収束したが、2つの実装手段はメモリ安全性で優劣が分かれた——READY の遅延書き込みはシングルコアで idle 回収経路の二重解放を引き起こすが、旧状態を保存する書き方にはそれがなかった。この種の提案横断的な比較は単一パッチよりも意思決定価値が高く、#11907 を事実上の推進ベースラインにした。
  • 欠陥報告は引き続き外部研究者が主導し、完全な影響範囲を伴う：1日で2件のメモリ問題、NFS スタックオーバーフローの導入コミットは2010年まで遡ることができ、v1.2.0 以降の全バージョンに影響、DHCP の範囲外読み取りは同ディレクトリの別実装のチェック項目で欠落点を反証した。両報告とも再現環境とトリガ条件を提供しており、修正コストが大幅に下がった。
  • RISC-V 側はカーネル置換チャネルを確保：ESP-IDF 6.1 のパッケージ全体アップグレードがマージされた後、C3/C6 は CONFIG_IDF_RTOS_RTTHREAD で FreeRTOS を RT-Thread に置換でき、ツールチェーンも同時に GCC 15.2 へ移行。メインリポジトリの BSP 提案のブロッカーも同日解消され、残るは実機検証のみ。これは今期間の RISC-V 関連で最も重要な一歩である。
  • メインラインは静止、バージョンは9月で停止：3日連続でコミットゼロ、マージゼロ、v5.4.0 はバージョンマクロのみ。活動はすべて審査中の提案、欠陥チケット、パッケージリポジトリに集中し、公式チャネルの更新停止と同じリズムを形成している。
  • ベンダープラットフォームはバージョンごとに安定してイテレーションし、現場問題を修正に取り込む：睿擎 V1.8.4 の6項目の新規追加と4項目の修正はすべて具体的なシナリオに対応し（エンコーダ閉ループ、MIPI 画面適配、AMP デバッグ、EtherCAT アフィニティ）、IDE も GD32H7 へ同時拡張。工業プラットフォームの競争力が「動くかどうか」から「現場で安定するかどうか」へ移りつつあることを示している。
