2. セキュリティと安定性のフォローアップ

2.1 signalfdのグローバルカウント越界：11回目の呼び出しからカーネルポインタをヒープブロックの外に書き込む（10-26）

日付：2026-10-26 16:13（作成時間）　情報源：Issue #11933

これは今回最も重要な項目である。研究者は、components/libc/posix/io/signalfd/signalfd.c内でファイルスコープのグローバルカウンタis_head_initを使用して各ファイル記述子に私有の配列sfd->lwp[10]をインデックスしているが、signalfd_add_notify()は使用前に境界チェックを一切行っていないと指摘している。signalfd_close()はこのカウントを巻き戻すことがないため、増加する一方である。また、新しいコンテキスト作成時にはlwp[0 .. is_head_init-1]のみをクリアするため、同一プロセスで再度作成しても自分自身に一致することは決してなく、必然的に書き込み分岐に進む。

結果は具体的に記述されている：lwp[]はstruct rt_signalfd_ctxの最後のメンバーであり、構造体全体はarm32で1536バイト、配列はちょうどヒープブロックの末尾に位置する。11回目のsignalfd(-1, ...)呼び出し時に、書き込みは割り当てブロックの外の最初のワード、すなわち小メモリアロケータの次のブロックヘッダに落ちる。以降、作成するたびにさらに4バイト（64ビットでは8バイトステップ）外側に押し出され、持続的で呼び出し側がペースを制御できるカーネルヒープ越界書き込みが形成され、書き込まれる値もカーネルポインタである。

影響範囲を著者はタグごとに確認している：導入点は2023-09-11の7c3d966d（#8001）であり、v5.0.2 / v5.1.0 / v5.2.0 / v5.2.1 / v5.2.2 / v5.3.0と現在のmaster（5d1fb66d）のすべてが該当する。トリガー条件はRT_USING_SMART=yのみ——RT_USING_POSIX_SIGNALFDはこの設定でデフォルトyであり、2つの公式QEMU Smart BSPの設定もすべて有効になっているため、デフォルトのRT-Smartビルドでトリガー可能である。再現にはbsp/qemu-vexpress-a9（Cortex-A9、32ビット、FAT sdカードルートファイルシステム）を使用し、PoCは/sbin/initとしてインストールする。

現在、このチケットに対応する修正提案はなく、タグも付いていない。

2.2 muslスレッドリンクリストの並行終了下での解放後使用：futexロックが相互排他として機能していない（10-26）

日付：2026-10-26 11:22（作成時間）　情報源：Issue #11932

2件目の欠陥チケットは別の報告者によるもので、環境はRT-Thread 5.2.2のRT-Smart、SMP、aarch64、musl 1.2.5である。現象は並行pthread_createとpthread_exit時にユーザープロセスがクラッシュし、クラッシュポイントはmusl_pthread_exit：リンクリスト摘除時に書き込まれるスレッド記述子がすでに解放またはアンマップされている（Data Abort）、あるいはスレッドの戻りアドレスが0に書き換えられている（Instruction Abort）ことである。

著者の特定結論は問題が完全にユーザー態にあるというものである：muslはfutexベースの__tl_lock / __tl_syncでスレッドリンクリストを保護しているが、SMP並行終了のシナリオではこのロック群が実際に相互排他を提供しておらず、双方向リンクリストが壊される。カーネル側のfutex実装自体はセマンティクスが正しく、この欠陥を負うものではない。再現材料は1000ラウンド、8スレッドのtl_raceプログラムであり、数百ラウンド以内にクラッシュする。

このチケットにはbug、Arch: ARM/AArch64、RT-Smartの3つのタグが付いており、完全な分析ドキュメントが添付されている。2.1と同様にRT-Smartのライン上にあるが、レイヤーが異なる：2.1はカーネルヒープ、この項目はユーザー態libcである。

2.3 時間サブシステムの2件の修正が成熟版へ：settimeofdayの強制キャスト除去、gmtime_rの負のタイムスタンプ処理（10-26）

日付：2026-10-26 14:17 と 17:48（最終更新）　ソース：PR #11928、PR #11929

前回記録した時間サブシステム関連の4件のうち、対応する2件の修正が今回の調査期間内で一歩前進し、いずれも「成熟バージョン、マージ可能」にチェックが入った。

#11928 は1ファイルのみ変更、+185/-135：settimeofday() は元々、まず (long) で tv_sec を強制キャストしてから正負を判定していた。ILP32 かつ time_t が64ビット、long が32ビットの構成では、2^31 から 2^32-1 の間の正当なタイムスタンプが負数に切り詰められ、関数は RTC デバイスに触れる前に EINVAL で拒否していた——2208988800（2040-01-01）はまさにこうして拒否されていた。修正方法はフィールド自身の型に従って検証し、強制キャストを行わないことである。

#11929 は2ファイル +104/-9：gmtime_r() は C の除算と剰余でタイムスタンプを分解していたが、C の除算はゼロ方向に切り捨てるため、負の入力では余りが負になり、さらに年のループは未来方向にしか進めない。その結果 -1 は 1970-01-01 00:00:-1 となり、-31536000 の年フィールドは 1970-01--364 になっていた。修正方法は負数のパスを正規化してから分解することである。

いずれの2件もマージされていない。残る2件（timer_gettime() の切り詰め #11924、時間サブシステム作業項目調査 #11927）は今回の調査期間内で新しい進展はない。

2.4 ESP-IDF v6.1 の include 順序はパッケージ側で修正：メインリポジトリの提案はクローズ、esp-idf パッケージの提案はマージ（10-26）

日付：2026-10-26 09:15 と 11:37（マージとクローズの時刻）　ソース：RT-Thread-packages/esp-idf 提案 #19、メインリポジトリ提案 #11926

前回記録した #11926 は、ESP-IDF v6.1 適配後に master で発生するビルド失敗を修正するため、メインリポジトリで ESP32 C3／C6 の FreeRTOS ヘッダファイルのインクルード順序を調整しようとしていた。今回の議論で別の道筋が示された。メンテナがコメントで「AI に idf を scons に変更させる」ことを提案し、パッケージリポジトリの提案 #19 を指し示した。別のメンテナがその後、先にパッケージリポジトリの件をマージすべきか追问した。

結果として、パッケージリポジトリの提案 #19（fix(scons): prioritize RT-Thread FreeRTOS headers）は 10-26 09:15 にマージされ、メインリポジトリの #11926 は 11:37 にマージされずクローズされた。つまり、ヘッダファイルの優先順位問題は SCons ビルドスクリプトのレベルで解決され、メインリポジトリでは include 順序を変更しない。この点が BSP メンテナにとって意味するのは、esp-idf 関連のビルド問題は今後パッケージリポジトリで優先的に処理し、メインリポジトリはカーネルとフレームワーク側の変更のみを担うということである。

3.2 Eclipse プロジェクトジェネレータがカーネルマクロを伝え漏れる：Studio の24件の暗黙的宣言警告に解決策（10-26）

日付：2026-10-26 23:33（最終更新）　ソース：メインリポジトリ提案 #11930

前号で収録したコミュニティ長文で記録された「Studio ビルドで 24 件の rt_sched_* 暗黙宣言警告が出る」問題について、今回対応する提案が出た。単一ファイル +151/-2 で、プロジェクト生成器側から修正する。

根本原因は明確に書かれている：include/rtsched.h 内のスケジューラインターフェースは __RT_KERNEL_SOURCE__ と __RT_IPC_SOURCE__ の 2 つのマクロで保護されており、gcc と armclang の分岐は src/SConscript 内で LOCAL_CPPDEFINES を通じて注入され、コマンドラインの scons ビルドでは認識されるが、Studio が毎回 make の前に呼び出す tools/targets/eclipse.py はこのグループレベルの定義を収集しないため、dist エクスポートプロジェクトで 24 件の -Wimplicit-function-declaration が発生する：clock.c 1 件、ipc.c 7 件、thread.c 12 件、timer.c 1 件、scheduler_comm.c 3 件。

修正方法は __RT_KERNEL_SOURCE__ を Kernel グループのグローバル CPPDEFINES に引き上げ、既存の msvc 分岐と一致させることだ。変更はカーネルソースコードに触れず、プロジェクト生成スクリプトのみを変更する。

4.2 STM32 イーサネットが ops 層と SR8201F PHY を補完、ADC ログレベルを引き下げ（10-26）

日付：2026-10-26 10:25（最終更新）　ソース：メインリポジトリ提案 #11819

三者一体のドライバ提案で、4 ファイル +34/-3、STM32 側の 3 つの独立した問題をカバーする。

一つ目は ADC ドライバのデフォルトログレベルが高すぎ、通常使用時に画面を埋め尽くすため、DBG_WARNING に変更しマクロスイッチを保持する。二つ目は ETH ドライバに ops 層の適配が欠けており、上位のネットワークフレームワークが統一インターフェースでデバイスを操作できないため、本件で ops コールバック集合を実装・登録した。三つ目は PHY ドライバが SR8201F をサポートしておらず、このチップを使うボードでイーサネットが起動できないため、本件で認識 ID、初期化フロー、レジスタ設定を補完し PHY リストに追加した。検証ボードは stm32f429-atk-apollo で、設定は RT_USING_DEVICE_OPS、BSP_USING_ETH、PHY_USING_SR8201F を有効にしている。

5.2 コミュニティ長文「rtthread起動チェーン分析」：Reset_Handler から main までを三段に分解（10-26）

日付：2026-10-26 08:59（公開）　ソース：コミュニティ記事：rtthread起動チェーン分析

コミュニティ記事インターフェースでは、調査期間内に新規追加されたのはこの1本のみで、約5700字。著者は自身の環境を STM32F103C8T6 + RT-Thread 4.0.3 + RT-Thread Studio 2.3.1（GCC）と述べ、本文中のコードは本プロジェクトの実際のビルドから取得したものであり、マニュアルからのコピーではないと明言している。

起動経路は3段階に分かれる。第1段はアセンブリで、Reset_Handler が .data の初期値を Flash から SRAM へコピーし、.bss をゼロクリアし、SystemInit を呼び出し、entry へジャンプする。著者はよくある誤解をわざわざ指摘している。SystemInit はメインクロックを72MHzに設定するのではなく、RCC をリセット状態に戻し、SCB->VTOR を Flash の先頭に設定するだけである。第2段は C の初期化で、entry が rtthread_startup() に入り、rt_hw_board_init() の中で初めて72MHzのクロックとヒープを設定し、その後 main、timer、idle の3つのスレッドを生成する。第3段はスケジューラの起動で、rt_system_scheduler_start() が優先度最高のレディスレッドを選択し、デフォルトではまず timer スレッドが実行され、main() は main_thread_entry() 内の rt_components_init() の後にようやく登場する。

文末にはさらに四つの「間違えやすい点」と自己検証方法の節が設けられており、カーネルコードを読む際によくある困惑点のまとめとなっている。

6. 総括とトレンド観察

6.1 今期のトレンド：マージ停止、欠陥報告とツールチェーン改修が引き継ぐ（10-26）

日付：2026-10-26（今期）　情報源：メインリポジトリのコミット記録

今日は4つの側面で総括できる：

第一に、コード主線の停止である。24時間でコミットゼロ、マージゼロ、13の提案がキューの中で動いているが1件も着地していない。前回の72時間の調査期間でようやく2件が着地したのみで、今日のコミットゼロは同じリズムの継続であり、開発側はレビューを待ち、レビュー側は修正完了を待っている。

第二に、セキュリティ面は引き続き外部研究者が主導している。10-24は時間サブシステムの4件だったが、今日は RT-Smart の2件に変わった。signalfd のグローバルカウントの境界外アクセス（カーネルヒープへの任意書き込み、v5.0.2以降の全バージョンが該当、デフォルト設定でトリガー可能）と、musl スレッドリンクリストの並行解放後使用である。いずれも特殊なハードウェアを必要とせず、QEMU で再現可能であり、ともに「デフォルト設定の Smart ビルド」という層を指している。

第三に、ツールチェーン側はメンテナ自身が手を動かしている。vscode-rt-smart は一度に4826行を削減し、拡張機能を「大きくて全部入りの IDE 代替」から Env 入口とエディタ内ブラウザへと縮小した。同時に Eclipse エクスポートでカーネルマクロが漏れる問題のパッチも提出され、Studio 下の24件の暗黙宣言警告を直接指摘している。

第四に、ベンダ側は依然として BSP が主体である。ルネサス RA6W1 は第二期のリソース配分最適化に入り、ST はイーサネット ops と SR8201F PHY を補い、Espressif の ESP32-S3 BSP 提案は依然として55ファイル規模でレビュー待ちであり、チップの新製品やアーキテクチャレベルの動きはない。

6.2 限界と重複排除の説明

日付：2026-10-27（今期）　情報源：メインリポジトリのコミット記録

第一に、公式ニュースインターフェースとコミュニティ記事インターフェースはいずれも確認済みで、前者は6月以降更新されておらず、今期の公式口径に新内容はない。

第二に、今期は10-26期と重複しない。前回の調査期間の終点は10-26 08:00であり、今期はその時点から起算する。#11910、#11915、#11920、#11901 などの提案は前回「マージ待ち欠陥」として既にまとめており、今期は重複して展開せず、キュー統計にのみ登場する。

第三に、#2461、#1956、#2467、#5096 の4件の旧提案は収録していない。検索結果ではこれらの更新時間が今調査期間内にあるが、クローズとマージの時間はそれぞれ2019、2018、2019、2021年であり、インデックスの更新であって新規イベントではない。

4点目、GitHub 匿名インターフェースのレート制限は今回上限に近づいており、組織レベルの調査は単一の sort=pushed リクエストで完了させ、リポジトリごとに全イベントを取得しなかった。メインリポジトリのコミットは commits インターフェースが返す先頭 100 件を基準とし、24 時間の調査期間をカバーするには十分である。
