1. カーネルとバージョン動向

1.1 メインライン72時間でコミットはわずか2件：lwIP ループバック netdev マージ、clang-format ルール細分化と thread.c サンプル（10-25）

日付：2026-10-23 17:09 および 2026-10-25 19:26（マージ時刻）　出所：PR #11859、PR #11893、メインリポジトリコミット記録

週末3日間の期間に、master にマージされたのはこの2件のコミットのみであり、そのリズムは前回の「3日間ゼロコミット後の集中クローズ」という判断とつながる：マージ操作はいずれも非業務時間帯（金曜 17:09、日曜 19:26）に発生しており、レビュー自体は止まっていないが、開発側には新規コードがなかった。

1本目は clang-format ルールの収束で、2 ファイル +83/-77、変更は .clang-format と src/thread.c のみ。ブランチ名には議論の手がかり style/clang-format-discussion-11653 が付いており、2 つのコミットの日付はいずれも 10-09、主体は「アライメント、波括弧改行、スペース規則」の細分化で、2 番目のコミットでは src/thread.c を新規則に従って全体フォーマットしたものを例として示している。つまりこれは 2 週間引きずったレビューの締めくくりであり、新規作業ではない。提案にはツール上の事実も 1 つ記録されている。index++ のような書き方は clang-format 18.1.8 と 23.1.3 のいずれでもそのまま維持され、強制書き換えに対応する設定項目は存在せず、検証には --dry-run --Werror を使う。

2本目は lwIP ループバックデバイスの netdev フレームワークへの導入で、3 ファイル +54/-0。これまで lwIP のループバックポートは netdev として登録されておらず、2 種類の問題を引き起こしていた。127.0.0.1 経由のツールチェーンが動作しないこと、物理リンクのないネットワーク名前空間にデフォルトで利用可能なインターフェースがないこと。変更では RT_LWIP_USING_LOOPBACK 設定項目を新設し、lo／lo0 を netdev として登録して link up に設定し、インターフェース未指定時にはループバックをデフォルトインターフェースとして選択し、同時に RAW 受信メールボックスを拡大してループバックのエコーを収容する。検証設定は qemu-virt64-riscv で、提案には「ローカルでは未コンパイル、CI によりビルド検証」と明記されている。これは先月の複数の提案の通過基準と一致する。マージはビルド通過を条件とし、実機確認は別途フォローする。

バージョン側は引き続き動きがない。最新のリリース物とタグは依然として 09-10 の v5.3.0 であり、10-17 の v5.4.0 のバージョンマクロには今もってリリースノート、バイナリ、プレリリースタグが付いていない。

1.2 qemu-virt64 で RT-Thread Smart を有効化：riscv64 は SMP を無効化、ext4 と elm でブロックデバイスをマウント、ptyfs と procfs をマウント（10-25）

日付：2026-10-25 19:50（最終更新）　情報源：PR #11896

この提案は 14 ファイル +1263/-1075 で、qemu-virt64-riscv と qemu-virt64-aarch64 の 2 つの BSP で RT_USING_SMART を有効化する。これまでこれらの virt プラットフォームは名目上 Smart をサポートしていたが、virtio ブロックデバイスには標準的なルートファイルシステム初期化フローがなく、pty にもマウントポイントがなく、多くの機能は QEMU 下ではまったくテストできなかった。

変更は 4 つに分解できる。riscv64 側では SMP を無効化し、Smart のシングルコア設定に合わせる。virtio-blk0 上で ext4 または elm をマウントする初期化フローを新設する。ptyfs を /dev/pts に、procfs を /proc にマウントする。.config と rtconfig.h を再生成する。ビルド検証には riscv64 は RISC-V musl 汎用ツールチェーン、aarch64 は aarch64 musl ツールチェーンを使うと明記され、ローカルでは未実行で CI により検証される。

注目すべきは依存関係である。この提案はちょうどマージされた #11893（RT_LWIP_USING_LOOPBACK 設定シンボル）に明示的に依存し、.config は #11893 の上で生成されており、著者は依存がマージされた後に rebase して設定を再生成すると説明している。この種の提案をまたぐ設定の結合は qemu プラットフォーム改修ではよくあることで、ループバックポートが Smart 有効化より先に着地する必要がある理由も説明している。ループバックがなければ、Smart 下でローカルアドレスに依存する多くのテストが動作しない。

1.3 lwp_syscall.c 一万一千行の分割：165 のシステムコール入口をサブシステム別にファイル分割、挙動は不変（10-25）

日付：2026-10-25 19:50（最終更新）　情報源：PR #11894

components/lwp/lwp_syscall.c は単一ファイルが一万一千行を超え、メモリ、ファイルシステム、socket、プロセス、IPC、時間の 6 種類のシステムコールが一箇所に積み上げられており、レビューと検索が非常に困難だった。提案ではこれを components/lwp/syscall/ ディレクトリに分割し、サブシステム別にファイルを分け、共有のシステムコールディスパッチテーブルと内部ヘッダーファイルを新設し、LWP のビルドスクリプトに新ディレクトリを登録する。

規模としてはこれが本調査期間で最大の 1 本である。22 ファイル +12223/-11638 で、ほぼすべてが移動と改名。提案は「機械的なリファクタリング、機能変更なし」と自称し、165 のシステムコール入口と挙動が完全に変わらないことを強調している。検証も同様に「ローカルでは未コンパイル、CI で検証」で、設定は CONFIG_RT_USING_SMART=y。

工学的観点から見ると、この種の分割自体は新たな能力を生まないが、今後の lwp 欠陥（例えば本号 2.2 の sys_poll ラップアラウンド）を読めるファイル内で特定できるかどうかを左右する。前号で記録した 9PFS の長さ収束の提案も同じ流れに属する。Smart 側のコードは「動く」から「保守できる」へと移行しつつある。

2. セキュリティと安定性のフォロー

2.1 時間サブシステムで一晩に4件連続報告：settimeofday の幅縮小、gmtime_r の負のタイムスタンプ、timer_gettime の切り捨て、さらに A から F までのワークアイテム調査を添付（10-23／10-24）

日付：2026-10-23 21:04 と 2026-10-24 20:25（作成時間）　情報源：Issue #11922、Issue #11923、Issue #11924、Issue #11927

10-23 の夜、同一の研究者が components/libc/compilers/common/ctime.c 上で続けて3件を起票し、翌日の調査チケット1件を加えて、時間サブシステムの意味論的な問題を一気に並べた。3件のベースラインはいずれも master の a59e72fb5c で、すべてソースレベルの隔離再現であり、ボード上での実行は行っていない。

1件目は settimeofday() の型の幅縮小である。検証時にまず (long)tv->tv_sec へ強制キャストし、time64／long32 の 32 ビット ARM ABI 下（time_t が 64 ビット符号付き、long が 32 ビット）では、正当な正のタイムスタンプが負数に変換されてしまい、RTC ドライバを呼ぶ前に -1 を返して EINVAL を設定する。作者は GNU Arm Embedded 10.3-2021.10 を用いて型サイズと幅縮小の挙動を隔離検証した。

2件目は gmtime_r() の負のタイムスタンプ処理である。関数は非 NULL を返すが、フィールドが不正になる。提示された4つの比較値は非常に分かりやすい——-1 は 1970-01-01 00:00:-1、-86400 は 1970-01-00 00:00:00（yday が -1）、-31536000 は年フィールドが 1970-01--364、-2208988800 は 1900-01-01 になるはずが 1970-01--25566 になる。根本原因は、除算・剰余のいずれも C のゼロ方向切り捨ての意味論を用いており、負の入力では余りが負になり、年ループが未来方向にしか進めないことにある。

3件目は timer_gettime() の切り捨てである。残り総ナノ秒をまず rt_uint32_t に格納してから秒とナノ秒に分解するため、10 秒すなわち 100 億ナノ秒を 32 ビット変数に代入すると上位ビットが直接失われる。影響を受ける設定は RT_USING_POSIX_TIMER と RT_USING_CLOCK_TIME が同時に有効な場合である。

4件目（10-24 20:25）は欠陥ではなく調査である。tick、clock_time、RTC、libc、VDSO がそれぞれ時間ベースラインを維持している問題を、ワークアイテム付きの設計提案として整理し、10 項目の不足（設時が統一されていない、clockid の意味論が混乱している、ソフト RTC の偽同期、回り込みとオーバーフロー、hrtimer のフォールバック、PM の分岐、起動時の授時状態、NTP バージョンの境界など）を列挙し、A から F までの6つの追跡可能なワークアイテムと P0 から P2 の優先度を示し、通常の MCU は A から D まで完了すれば段階的な終点に到達すると明言している。このチケット自体は静的解析であると宣言しており、コンパイルもボード上での実行も行っていない。

対応する修正提案はすでに2件起票されている：#11928 は settimeofday() をフィールド自身の型で検証するようにし、一律に long へ変換しないようにする；#11929 は gmtime_r() の紀元前タイムスタンプに対する正規化を扱う。2件とも 10-24 にコミットされ、まだマージされていない。

2.2 32 ビット RT-Smart の sys_poll 回り込み：8 バイトのヒープブロックを 0x20000001 項目として走査し、カーネルヒープで範囲外読み書き（10-24）

日付：2026-10-24 03:39（作成時間）　情報源：Issue #11925

この欠陥チケットは 10-24 の未明にコミットされ、問題は components/lwp/lwp_syscall.c の sys_poll() と libc 側の poll() の間に位置する。ユーザー空間から渡された nfds について、割り当てサイズを計算する際に nfds * sizeof(struct pollfd) が 32 ビットターゲット上で size_t 幅の演算となり、約 1.79 億項目を超えると小さな値に回り込む——その結果カーネルは 8 バイトのヒープブロックを 0x20000001 項目として走査し、読み書きがいずれもヒープ外に及ぶ。

影響範囲は作者の示した基準によれば、32 ビット RT-Smart のみが影響を受け、64 ビットビルドでは積が 64 ビットに昇格し、超大割り当ては直接 -ENOMEM で失敗し、回り込みは発生しない。導入点は 2022-12-03 の ecf2d821（sync branch rt-smart，#6641）であり、最初の影響バージョンは v5.0.0、v5.0.0 から v5.3.0 および現在の master（5d1fb66d）がいずれも該当する。再現には bsp/qemu-vexpress-a9 を使用している。

これは前回の 9PFS、NVMe の「デバイスまたはサーバ側で制御可能なメタデータを長さとして使う」一族とは異なる。今回はユーザ空間で制御可能なカウントが狭いビット幅でラップアラウンドするもので、古典的な整数境界問題に属するが、着地点がシステムコール入口とカーネルヒープの間にあるため、結果は直接カーネルヒープの境界外読み書きとなる。この PR には現在対応する修正提案はない。

2.3 前回マージされた ESP-IDF v6.1 適配が master 上で C3／C6 ビルドを赤にし、include 順序の修正が既に提出済み（10-25）

日付：2026-10-25 17:49（最終更新）　情報源：PR #11926、PR #11870（前回マージ）

前回記録した ESP32-C3／C6 の ESP-IDF v6.1 適配は 10-22 にマージされ、当時の実機検証欄は「検証待ち」と書かれていた。二日後、master 上の C3／C6 ビルドが赤になった。提案の説明によれば、master の 2 回の CI 実行（40043597502、39929831359）で同じ現象が再現され、さらにすべての PR の RT-Thread BSP Static Build Check と MemBrowse Memory Report も続けて赤になった。

根本原因は適配コード自体ではなく、ビルド順序にある。ESP-IDF パッケージは components/rtthread/scons/ の下に FreeRTOS.h の scons shim を置き、#include_next で <freertos/FreeRTOS.h> に転送する。これには RT-Thread の FreeRTOS-Wrapper include ディレクトリが shim の後、ESP-IDF 自前の FreeRTOS V11 カーネルヘッダの前に並ぶことが要求される。しかし 2 つのパッケージの SConscript のロード順序はディレクトリ走査順序で決まり、安定しない。ひとたび ESP-IDF が先にロードされると、#include_next は V11 のヘッダに解決され、Wrapper が提供する configNUMBER_OF_CORES、configMINIMAL_STACK_SIZE、configUSE_PREEMPTION などのデフォルト値がすべて空振りし、drv_uart.c のコンパイル時に直接 #error となる。

修正提案は 3 ファイルのみを変更し、FreeRTOS include ディレクトリの順序を固定する。この件を記す価値があるのは欠陥そのものではなく、フィードバックの連鎖にある。前回「ビルド通過」をリリース条件としてマージされたものが、今回 CI に順序依存を捉えられ、修正提案が当日に開かれた。

2.4 既存欠陥提案のステータス棚卸し：NVMe リーク、9PFS 長さ、tmpfs UAF、dlmodule グローバル変数、FDT 深度はいずれもマージ待ち（10-25）

日付：2026-10-25（確認時刻）　情報源：PR #11920、PR #11918、PR #11910、PR #11915、PR #11901

前回収録したいくつかの修正は調査期間内にいずれも更新があったが、いずれもマージされておらず、ステータスは「提案済み、レビュー待ち」で止まっている。NVMe が非アクティブな名前空間に遭遇するたびに割り当てをリークする件（#11920、10-25 00:35 更新）、9PFS がサーバ側の長さフィールドを実際の受信バイト数に収束させる件（#11918、10-24 17:19 更新）、tmpfs がゼロ長に切り詰められた際の解放後使用（#11910、10-23 23:31 更新）、ローダブルモジュールの未初期化グローバル変数（#11915、10-24 17:27 更新）。

期間内に追加された2件は新しいものだ。1つはFDTアンフラット化の深さ制限（#11901、10-25 15:49更新）で、fdt_unflatten_single() は固定64項目のスタック np_stack を用いて走査パスを一時保持するが、プッシュ前に深さを検査しないため、深さが64層を超えるDTBではスタックの範囲外書き込みが発生する。作者はqemu-virt64-aarch64上で再現し、修正方法はアンフラット化の前に独立した手動スタック走査で最大深さを算出し、63層を超える場合は直接拒否するというものだ。もう1つはシリアルの rx_indicate が誤ってクリアされる問題（#11931、10-26 01:34更新）で、echo xxx /dev/uart0 の後、コンソールが応答しなくなる。作者は「open_flag が上書きされる」という従来の説明を排除した——現在 rt_device_open() は OFLAG_MASK のマッチ時にドライバのopenをまったく呼ばない——そして真因を serial_fops_close() が無条件に rx_indicate をクリアすることに特定した。しかもデバイスは依然としてコンソールに保持されている（ref_count は3から2に下がるだけだ）。

4.4 ドライバと CI：OSPI 8 線 Flash、I2C 制御トランザクションの直列化、STM32 パッケージテストの並行ロック（10-23／10-25）

日付：2026-10-23 から 2026-10-25（更新およびマージ時間）　情報源：PR #11912、PR #11820、pkgs-test PR #37

ドライバ層で最大のものは OSPI と OctaFlash のサポート（#11912）で、32 ファイル。従来、RT-Thread の SPI ドライバ層にはネイティブな OSPI 経路がなく、8 線 Flash は回避策しかなかった。変更は components 層で OSPI のバス、デバイス、設定、メッセージ定義、および転送補助関数とビルドオプションを補完し、既存の SPI と QSPI 経路を維持する。OSPI 転送とプローブを SFUD に組み込み、読み取り、書き込み、消去、ステータス／制御操作をサポートし、SFUD デバイステーブルに MX25LM51245G を追加して検証に用いた。経路全体がハードウェア上で動作するよう、汎用 STM32 OctoSPI ドライバと stm32l4r9-st-eval のボードレベル OSPI Flash サポートも追加し、SFUD が 1-1-1 と 8-8-8（OPI STR／DTR）の 2 モードでアクセスできるようにした。

I2C の件（#11820）はバス制御と転送の競合を修正した：rt_i2c_control() が rt_i2c_transfer() のバス使用中にコントローラ設定を変更する可能性があり、特に SET_MAX_HZ で問題になる。修正方法は、制御コマンドが同じバス排他ロックを取得し、統一された出口で解放するようにし、API ドキュメントに制御にはスレッドコンテキストが必要であることを明記した。検証にはホスト側の pthread 排他アダプタを使用し、並行転送と制御、制御と制御、周波数更新、ロックとコールバックのエラー、および制御内のネスト転送をカバーした；パッチ未適用のソースは同じ回帰セットで失敗する。

CI 側の件は pkgs-test（#37）で、1 ファイル +11/-7、非常に完全に説明されている：STM32 パッケージテストは複数バージョンを並行実行し、各タスクは独立した BSP コピーを持つが、bsp/stm32/libraries 下の HAL／CMSIS ドライバディレクトリは依然として共有している；元の sem_stm32 はコンパイルのみを保護し、依存関係の更新を保護していなかったため、あるタスクが別のタスクの依存関係クローンが完了していない同一ディレクトリに対して git pull を実行し、Git が未追跡ファイルが上書きされると報告して中止し、その失敗がフレームワークによって一律 compile failure と報告される事態が発生した。前回マージされた #11870 のテストはまさにこれで失敗した（失敗ログで確認可能）。修正方法は、ロックを __build() に引き上げ、依存関係の更新とコンパイルを同じクリティカルセクションに置き、同時に __build_scons() 内の重複ロックを削除して自己デッドロックを回避し、try/finally で例外時の解放を保証する。

5. 総括とトレンド観察

5.1 今期のトレンド

  • 車載アーキテクチャは「ツールチェーン先行」：TriCore／AURIX は今回メインリポジトリではなく Env SDK に入った——オープンソースの GCC 13.4.1 と qemu-tricore の 2 パッケージでまずコンパイルとシミュレーションを補完し、メインラインの libcpu には依然として tricore ポートがなく、bsp 下にも AURIX ボード級ディレクトリがない。2020 年前後に TASKING 商用ツールチェーンに依存した一連の試み（いずれも Closed で終わった）と比較すると、今回の経路は実現可能性が高いが、「ボードに載る」までにはまだ BSP とドライバが必要だ。
  • メインラインは極めて静か、提案面は極めて活発：72 時間で master はわずか 2 コミットだが、期間内に 25 件の PR が更新され、6 件がマージされた（メインリポジトリ 2、sdk 2、packages 1、pkgs-test 1）。マージ動作は金曜夕方と日曜夜に集中し、レビューは止まっておらず、開発側は確かに収束しつつある。
  • 欠陥研究は単点からサブシステムへ：時間サブシステムは一夜で 4 件（3 欠陥＋A から F の作業項目を含む調査 1 件）、2 件の修正提案が翌日提出され、「報告—分析—修正」の短い閉ループを形成した；lwp の sys_poll ラップアラウンドは、32 ビット RT-Smart のユーザー空間で制御可能なカウンタにおける整数境界問題を個別に挙げ、前回の「デバイスまたはサービス側のメタデータを長さとして扱う」欠陥群と相補的であり、カーネルが依然として歴史的負債を支払っていることを示す（ecf2d821 は 2022 年まで遡れる）。
  • ビルドをリリース条件とするマージが CI に逆襲され始めた：前回 ESP-IDF v6.1 適応のマージから 2 日後、master 上の C3／C6 ビルドがレッドになり、すべての PR の静的ビルドチェックに波及した；修正提案は当日に起票された。この連鎖自体は健全だが、「ローカル未コンパイル、CI 検証」という方針には順序安定性の保障が必要であることも示している。
  • 端側 AI の着地点はモデル実行からツール接続へ：ai/Agent パッケージに STT アップロードエンドポイントを追加、デフォルトバックエンドを DeepSeek 公式 API に変更、コミュニティコンテスト作品が agent パッケージで MQTT 操作をツールとして登録しカーネルスケジューリングに供する、さらに 10-26 夜の「デュアルコア＋筋電意図」ライブ配信と、方向は一致している——RTOS は agent のランタイムとして扱われ始めており、リアルタイム性と異種分散が汎用 Linux に対するセールスポイントだ。
