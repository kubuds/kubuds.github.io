1. カーネルとドライバのマージ

1.1 WCH 青稞カーネル高速割り込み：27ファイルの割り込み属性を統一（11-09）

日付：2026-11-09 11:12（マージ時間）　出典：提案 #12004、コミット 95e82ec2

27ファイル、1087行追加、1424行削除、作者 kaidegit、11月7日作成、11月9日マージ。WCH の異なる QingKe カーネルでは高速割り込みのサポートが異なり、2段階のハードウェア割り込みしか持たないカーネルでは使用すべきでなく、各 BSP とドライバの割り込み記述は以前はそれぞれバラバラだった。変更では CONFIG_WCH_USING_FAST_IRQ 設定項目を新設し、統一された割り込み属性マクロでチップシリーズごとに高速または通常割り込みを選択し、ペリフェラルドライバと BSP の割り込みハンドラを個別に調整；CH32V203 の起動ファイルを新しい用法に変更。検証ボードは ch32v208w-r0 と ch32v307v-r1、デフォルト設定。

削除行数が追加行数より多いことは、これが収束であることを示す：複数の BSP にコピーペーストされた割り込み宣言を1セットのマクロに回収した。付随する SDK 更新はソフトウェアパッケージリポジトリに置かれ、v203 で回避が必要な問題を解決、4.1を参照。

1.2 ESP32-C3 リンカスクリプト：リングバッファの IRAM 規則にアスタリスクが1つ不足（11-09）

日付：2026-11-09 11:10（マージ時間）　出典：提案 #12009

1ファイル、1行の変更。sections.ld の esp_ringbuf の IRAM 規則が *esp_ringbuf?(...) と書かれ、セクションリストの前にアスタリスクが1つ不足し、どのオブジェクトファイルにもマッチしない；.flash.text が当該シンボルを除外しているため、ringbuf.o の 0x1fa4 バイトがリンカによって .flash.text の後の孤立 .text セクションに押し込まれる。.flash_rodata_dummy は SIZEOF(.flash.text) のみで領域を予約し、孤立セクションが算入されていないため、.flash.text の終了位置が64KB境界から 0x1fa4 未満になると、コードと読み取り専用データが同じ flash MMU ページに落ち、rodata がコードとして読み出され、シリアルにマシンコードが表示され、プログラムが起動しない。

修法は不足している * を補うだけである。作者は対照区間を示している。修正前は IROM 0x42000020 から 0x42070f54 まで、DROM は 0x3c070020 から（同じく 7 番目の MMU ページを使用）、修正後は IROM が 0x4206f028 で止まり、重複しなくなる。この種の問題はデフォルト設定でも発生し得る。どれだけコードを追加したかによる。

1.3 CherryUSB EHCI：SETUP パケットキャッシュのフラッシュ漏れ、8月の旧欠陥をクローズ（11-09）

日付：2026-11-09 14:31（マージ時間）　情報源：提案 #12008、欠陥 #11749

1ファイル、4行追加、作者は boa-z。これは CherryUSB 上流コミット 41f5796 のバックポートである。EHCI コントローラは非一貫性キャッシュのプラットフォーム上で古い SETUP パケットを読み取ってしまい、デバイス列挙が失敗する。RT-Thread に内蔵された CherryUSB のコピーは v1.6.1 で止まっており、この修正が含まれていない。欠陥 #11749 は8月25日に提出され、本期でクローズされた。

4行のコードで3ヶ月にわたる列挙障害を解消したが、露呈したのは内蔵サードパーティコンポーネントのバージョン追随の問題である。上流が修正してもリポジトリ内が追随せず、利用者によるバックポートに頼るしかない。

1.4 Bouffalo ADC：DMA サンプリングチャネルに範囲チェックを追加（11-09）

日付：2026-11-09 09:29（マージ時間）　情報源：提案 #12003、欠陥 #11949

1ファイル、48行追加、2行削除、作者は Wooohaaa。Bouffalo ADC ドライバは呼び出し元が渡したチャネル番号をそのまま使って DMA バッファのインデックスを計算しており、負数、範囲外、および BSP で未設定のチャネルでは無効なサンプリングスロットを読み取ってしまう。修法は、ADC/DMA の設定と読み取りセマフォの待機の前に、チャネルのバッファ範囲と BSP 設定リストを検証し、元のオフセットと容量の数値を名前付き定数に置き換えることである。

検証はホスト側のみ。未設定チャネル、CH0 のみ、CH10 のみの3通りの設定をそれぞれシミュレートし、設定テーブルと検証関数を抽出して GCC の厳格な警告付きでコンパイルし、rt_int8_t の全256値を網羅した。Bouffalo 実機には載せておらず、完全な BSP ビルドも行っていない。

1.5 utest：自動複数ラウンド実行とラウンド間リソースサンプリング（11-09）

日付：2026-11-09 09:31（マージ時間）　情報源：提案 #11983

3ファイル、123行追加、4行削除、作者は sexenteen、11月3日提出、9日マージ。この変更によりテストフレームワークはケースを連続して複数ラウンド実行でき、各ラウンド間で空きメモリとスレッドテーブル（free/ps）をサンプリングできる——ストレステストが「1回実行して結果を見る」から「複数ラウンド実行してリソース曲線を見る」へと変わる。utest コンポーネント自体に加え、CI ワークフローも1本変更している。

これはキュー内で同じくテスト基盤に属する数件の方向性と一致する。dlmodule リグレッションカバレッジ（#11989）、ulog 出力呼び出し点（#11987）はいずれも審査中である。まずリグレッション面を広げ、次に可観測性を補う——9月末以来このラインの定まった順序である。

2. 欠陥と提案

2.1 RISC-V PLIC：非 DM モードでは完了してから配布する（11-09）

日付：2026-11-09 22:35（報告）/ 23:20（提案）　情報源：欠陥 #12010、提案 #12011

報告者 boa-z は ArtInChip D213（M モード、デバイスモデル不使用）の BSP を審査中に発見した。新しい RISC-V 共通ポートでは、handler_plic_irq が先に plic_irq_ack_or_eoi を呼び、その後で割り込みを handler_irq に渡して配布する。レベルトリガ源では、デバイス処理関数が割り込み源をクリアする前に、同じ IRQ が重複して配布される可能性がある。PLIC 仕様は完了動作をサービスに続くものと要求しており、DM パスはすでに先に rt_pic_handle_isr を実行してから plic_irq_eoi を呼んでいる。このコードは #10320 で導入され、旧 virt64 ドライバでは #11305 で同種の順序問題を修正したことがある。

45分後にフォローアップした #12011 は2ファイルを変更、35行を追加：ハンドラが完了前に言及；完了時に一時的にマスクされた割り込み源を開く。PLIC は disabled 源に対する完了書き込みを無視するため（手法は Linux の SiFive PLIC ドライバを参照）；共有 EOI ヘルパー関数は同時に DM パスにも影響する。検証はローカルビルドに限定：qemu-virt64-riscv のデフォルト DM 設定はビルド可能かつ起動可能。非 DM パスはリポジトリに入れない一時的な M モード BSP を使用し、16550 UART の THRE レベル割り込みは一度だけディスパッチされ、Actions はトリガーされなかった。

2.2 dfs/nfs：サーバー側の読み取り長がコピー長として扱われていた（11-10）

日付：2026-11-10 01:28（提案時間）　情報源：提案 #12012、欠陥 #11917

2ファイル、41行追加、7行削除。nfs_read() は元々、サーバーが返す READ3resok.count をそのまま memcpy 長として扱っており、異常または悪意のあるサーバーがこれを利用して呼び出し元のバッファをはみ出して書き込む可能性があった。修正方法は、各コピーを min(サーバーカウント, リクエストカウント, デコード済み長) に制限し、実際のコピーバイト数に応じてバッファとオフセットを進め、進捗ゼロの応答は直接抜け出してスピンを避ける；XDR デコード上限を約 4GB から 1024 バイト（DFS_NFS_MAX_MTU）に厳格化；併せて WRITE3resok.count を送信長にクランプし、サーバーが書き込みオフセットを送信済み範囲を超えて進めるのを防ぐ。

欠陥は10月22日に提出され、本期で提案が出た。これは本期で技術的に最も重い一件：ネットワークファイルシステムが対端の数値をローカル制約として扱うのは、典型的な信頼境界の不整合である。

2.3 ESP32-C3 v1.x：起動ヘッダのチップバージョンフィールドが不一致（11-10）

日付：2026-11-10 01:36（提案時間）　情報源：提案 #12013、欠陥 #11991

2ファイル、3行追加、1行削除。プリコンパイル済み bootloader と app イメージには古い min_rev=3 しか書かれておらず、v1.x チップ（例：rev 1.1）は esptool とセカンドステージブートから拒否される。修正方法は ESP-IDF の完全なバージョン範囲に従い min_rev=0、min_rev_full=3、max_rev_full=199 に変更し、builtin_imgs/bootloader.bin のヘッダフィールドも同期して修改し、末尾の SHA-256 を再計算する。

作者はこれがヘッダフィールドレベルの回避策であると注記：環境に CMake がなく、IDF ブートローダを再ビルドできない；実機書き込み検証も未実施。より長期的な方法は、現在の IDF でプリコンパイル済みイメージを再生成することである。

4.3 コミュニティ側：蓄電デュアルコア学習ボードとイベントフレームワーク（11-09）

日付：2026-11-09（プッシュ時間）　情報源：VoltDuo、coact

topic:rt-threadウィンドウ内三条プッシュ、二条はRT-Threadと直接関連。VoltDuoは蓄電方向のデュアルコアコントローラ学習ボード、DSPとMCUが分業してエネルギー管理とリアルタイム制御を行う；coactはC++17のアクターと階層状態機械フレームワーク、一套のヘッダファイルでRT-Threadなど複数プラットフォームを同時サポート、状態機械を裸書きコールバックから抽出するのに適する。第三条zlgopen/awtkは汎用GUIツールキットの高頻度コミット、RT-Threadとの専項関連はなく、エコシステム参考のみ。

5. 業界応用と産教

5.1 受賞リストにある三つの落地線：モータ、視覚、端側智能（11-09）

日付：2026-11-09（公開）　情報源：コンテスト結果原文

三等賞の3席はそれぞれ3か所に決まった。ART-Pi2上のUSB列挙可視化と記述子ルール診断器は、ホスト要求、デバイス応答、ルール判定を再確認可能なセッション証拠として整理する。SENTINELデュアルカメラエッジAI無人店舗防犯は、ローカル保存、クラウド非使用、イベント自動レポート化を実現する。玄鉄D121を主局とするマルチスレーブ機器監視と異常追跡は、RS485ポーリング、TFカード記録、ESP8266によるクラウド接続、ミニプログラムによる遠隔閲覧を行う。

優秀賞10席では産業向けとコンシューマ向けが半分ずつを占める。富瀚MC6321スマートドアロックとMC632Xデュアルカメラ尾行防止入退室管理、NXP MCXA346上で小型ニューラルネットワークによりFOCを補償するもの（低速定常尾段の速度誤差平均を約4.26%低減）、GD32H759IMのUSBサブスクリーンとOV2640カメラの二合一、ArtInChip D12xのポータブル産業用デバッガ、ART-Pi2のマスター・スレーブ分散モーターサーボ。共通点は概念デモを行わないことで、いずれも明確な現場課題を抱えている。

5.2 RISC-Vボードが受賞リストに占める位置（11-09）

日付：2026-11-09（発表）　情報源：大会結果原文

受賞作品のうち、明確にRISC-V上で動作するものは2件ある。三等賞のマルチスレーブ監視は玄鉄D121を主局とし、優秀賞のポータブル産業用デバッガはArtInChip D12xとLVGL v9を用いて、Modbus-RTUポーリング、RS485現場機器スキャン、シリアル送受信、アナログ量オシロスコープ、PWM信号源を一台のハンドヘルド端末に組み込んでいる。

2件はいずれも産業現場向けツールでありデモ品ではない。一つはマルチスレーブデータの保存と追跡を解決し、もう一つは「デバッグをノートPCを背負って現場に持っていくことから、電源投入ですぐ使えること」へと変える。前号のRISC-V FPUコンテキスト欠陥と今号のPLIC順序欠陥を合わせて見ると、RT-Thread上のRISC-Vの問題は大半がQEMU内で作られたものではなく、実際の産業用ボードのMモードシーンで発見されていることが分かる。

6. 総括とトレンド観察

6.1 5件のマージはすべてBSPとドライバ層、カーネルコアはゼロ変更

日付：2026-11-09　情報源：メインリポジトリのコミット記録

調査期間内の5件のマージはそれぞれWCH高速割り込み、ESP32-C3リンカスクリプト、CherryUSB EHCI、Bouffalo ADC、utestであり、変更はbspとcomponentsの2か所に集中し、srcディレクトリはゼロ変更である。カーネルバージョンは9月以来の状態のままだ。正式リリースはv5.3.0（9月10日）で止まり、主干は5.4.0を自称している（欠陥#12010のバージョン欄を参照）。

20年を歩んだRTOSにとって、この分布は常態である。新規要件はまずチップベンダーのBSPに落ち、カーネルは欠陥がある程度蓄積されて初めて動く。

6.2 3か所の順序問題：外部値がローカル検証に先行

日付：2026-11-09から2026-11-10　情報源：欠陥#12010、提案#12012、提案#12013

今号の3件の新規欠陥は形態が異なるが、根本原因は同じである。すなわち、先に動作し、後で検証する。PLICは先に割り込みを完了してから配分し、NFSは先にサーバー側の長さに従ってコピーしてから境界を論じ、ESP32-C3は先にバージョンフィールドを固定で書き込んでから互換性を論じる。修正の方向も一致している。判断を動作の前に移すか、相手から与えられた値をローカルの許容範囲に挟み込むかである。

この種の欠陥は機能テストでは露呈せず、特定のトリガ条件でのみ現れる。重複割り込みはレベル源がずっと引かれている必要があり、バッファ書き込み越えはサーバーが正直でない必要があり、バージョン拒否はv1.xのボードを持ってくる必要がある。利用者にとって注目すべきは個々の修正ではなく、この3か所がいずれも「外部世界との接続」の境界に現れていることである。

6.3 RISC-V線は依然として同一の報告者

日付：2026-11-09　情報源：欠陥#12010、提案#12011

前号のRISC-V FPUコンテキスト欠陥と今号のPLIC順序欠陥は同一人物（boa-z）によるもので、いずれもArtInChip D213のMモード、デバイスモデルを有効にしないシーンで発見された。2回ともまず再現を書き、次に修正を提出しており、間隔はそれぞれ4時間と45分である。

これは、RISC-Vの共通移植における非DMパスの検証カバレッジが依然として薄いことを示している。DMパスにはQEMUボードが常駐するCIがあり、非DMパスは個人が実機ボードで走らせて初めて見つかる。RT-Threadがより多くのRISC-V産業顧客を受け入れるなら、このパスをCIに入れる必要がある。

6.4 バージョンリズムは依然としてv5.3.0で停止

日付：2026-11-10　情報源：releases、tags

releases と tags は今回は新規追加なし、最新は依然として9月10日の v5.3.0。リポジトリ総量は12,336スターと5,489のフォークリポジトリ、メインリポジトリのプッシュ時間は11-09 11:12。バージョン管理 CI とリリースフローのイシュー（イシュー #11956）は依然としてキューにあり、11月6日に更新があったが、結論は見られない。
