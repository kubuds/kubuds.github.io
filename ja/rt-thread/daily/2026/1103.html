1.1 USB device のホスト制御可能な長さ 2 件を同時マージ：文字列記述子インデックスと MS OS 互換 ID（11-02）

日付：2026-11-02 11:47（マージ時間）　出典：提案 #11545、提案 #11546、欠陥 #4782、欠陥 #11287

同一作者による 2 件が同じ時間帯にマージされ、いずれも USB device プロトコルスタックにおける「長さとインデックスがホストから来る」という古くからの問題を修正した。

#11545 は文字列記述子インデックスを処理する（39 行追加、15 行削除）。元の実装では文字列を取得する前にホスト指定のインデックスを検証せず、インデックスに従って直接文字列テーブルを読みに行っていた。範囲外の場合は隣接するインターフェース文字列ポインタを読んでしまい、未登録の場合はヌルポインタを逆参照する可能性もあった。修正方法は 2 つ：テーブルを読む前にインデックスの境界を判定し、未知または未登録のインデックスは一律 EP0 で STALL を返す；Microsoft OS 互換 ID 記述子が登録されている場合にのみ OS 文字列を返す。対応する欠陥 #4782 は 2021 年 6 月 10 日に起票され、4 年以上放置されていた。

#11546 MS OS 互換 ID 応答の長さを処理する（4 行追加、1 行削除）。ホストはこの記述子を取得する際に任意の wLength を指定できる。元の実装は wLength に従って EP0 転送を構成するため、既に構築された記述子バッファの外側の内容を送信してしまう可能性がある。修正方法は、応答長を実際に構築された記述子サイズにクランプすることであり、割り当てとキャッシュの挙動は変更しない。対応する欠陥 #11287 は 2026 年 3 月 23 日に開かれた。

両方の提案は 2026 年 7 月 1 日に開かれ、同日にマージキューに入った。作者は提案の中で、検証は git diff --check と改行コードのチェックのみを行い、ビルドと USB device utest は実行していないと正直に明記している。その理由は、手元の Windows マシンに scons、C コンパイラ、組み込みクロスツールチェーンがないためである。この点は記録に値する。両方の変更は大きくないが、USB 記述子パスには自動テストのカバレッジがなく、マージ時の信頼は主にコードレビューに由来している。

1.2 SDHCI ホスト初期化の 32 バイト名バッファ、RT_NAME_MAX を 64 にするとスタックを踏む（11-02）

日付：2026-11-02 11:24（マージ時間）　情報源：提案 #11542

6 行追加、4 行削除、SDHCI ドライバの dev_sdhci.c に該当する。故障現象は、qemu-virt64-aarch64 上で SDHCI を有効にし、RT_NAME_MAX を 64 に設定すると、起動過程で直接 data abort し、fault addr 0x228 となることである。

根本原因はローカルバッファが 32 バイトに固定されていることである：char dev_name[32]。一方、sdio_host_set_name() はカーネルオブジェクトの命名規則に従って最大 RT_NAME_MAX 文字を書き込む。名前が 32 バイトを満たした後、続く 2 行 rt_sprintf(&dev_name[len], "-timer") と -data-timer がさらに後ろへ書き込み、スタック上にオーバーフローする。名前の長さが 32 を超えると、越境は「可能性」から「必然」に変わる。

修正方法は、バッファを char dev_name[RT_NAME_MAX] に変更し、sdio_host_set_name() の戻り値の後に dev_name[sizeof(dev_name) - 1] = '\0' を一度補ってから長さを再計算し、2 箇所のサフィックス連結を rt_sprintf から残り長さパラメータ付きの rt_snprintf に置き換える。これにより、RT_NAME_MAX が 64 や 128 に設定されても、名前とサフィックスの合計長はバッファ自身で吸収される。

同じ形状の問題は RT-Thread では珍しくない。カーネルは RT_NAME_MAX の設定を許可しているが、ドライバ内で小さなバッファを固定で持つ箇所は少なくない。この件は、コンテスト作品のボードが QEMU 上で SD カード初期化まで進んだ際に露見したものであり、RT_NAME_MAX がデフォルト以外の値となる組み合わせは普段テストされていないことを示している。

1.3 klibc のバイトループが GCC に memset と認識され、libc なしターゲットでリンク失敗（11-02）

日付：2026-11-02 18:08（マージ時間）　情報源：提案 #11965、欠陥 #6128

13 行追加、1 行削除、src/klibc/SConscript のみを変更し、C ソースコードには一切触れていない。

kstring.c 内の rt_memset()、rt_memcpy()、rt_memmove() はいずれもバイト単位のループで終わる。GCC は -O2 と -Os で -ftree-loop-distribute-patterns を有効にし、この種のループを標準ライブラリ呼び出しとして認識し、memset、memcpy への参照に書き換える。ターゲットプラットフォームに C ライブラリがなければ、これらのシンボルは存在せず、ファームウェアはリンク段階で失敗し、一連の undefined reference が報告されるが、文字列実装に関係するとは分からない。

作者は arm-none-eabi-gcc 10.3.1 を用い、QEMU の vexpress-a9 ボードプロジェクトで -Os により再現した。変更前の klibc の kstring.o 内に U memset が現れ、しかも 2 箇所の bl 0 <memset> が rt_memset() 自身の内部に位置していた——カーネル自身の memset が存在しない memset を呼び出していたのである。欠陥 #6128 は 2022 年 6 月 30 日に開かれ、最初の報告では aarch64-gcc で rt_memset をコンパイルすると問題があるとだけ述べられていた。

修正方法は、Libc グループに -fno-tree-loop-distribute-patterns を追加し、かつ CROSS_TOOL == 'gcc' の場合にのみ追加することであり、Keil と IAR のビルドには影響しない。代償としてこれらのループはベクトル化や折り畳みの対象外となるが、klibc のこれらの関数は元々ホットパス上にはない。この経験はベアメタル移植を行うチームに普遍性がある。自前実装の文字列関数とコンパイラ最適化オプションの間には暗黙の契約が存在し、ツールチェーンのアップグレード時に最も破られやすい。

1.4 tiny vsnprintf が long long を long として扱い、INT64_MAX が -1 と表示される（11-02）

日時：2026-11-02 16:25（マージ時間）　情報源：提案 #11600

20 行追加、3 行削除、rt_vsnprintf_tiny.c と対応するテストを変更。tiny バージョンはスペース節約のため %lld と %lli の ll 修飾子を long パスに統合して処理していた。その結果、64 ビット整数が 32 ビットで切り捨てられ、符号判定もずれてしまう――最も直感的な現象は INT64_MAX が -1 と表示されることである。

修正では内部の L（ll を表す）と l の 2 つの符号付き分岐を分離した。ll は long long として引数を取得し、64 ビット範囲で符号を判定し、l は long パスを維持する。同時に rt_sprintf の境界値回帰テストケースを追加し、INT32_MIN、UINT32_MAX、INT64_MIN、INT64_MAX の 4 値をカバーした。

検証構成は qemu-vexpress-a9 に tiny バージョンの long long サポートオプション（VSNPRINTF_LONGLONG、標準 vsnprintf は無効）を加えたもの。提案は 2026 年 7 月 9 日に作成され、キューに約 4 か月間置かれていた。tiny バージョンは多くのリソース制約プロジェクトのデフォルト選択であり、この種のサイレント切り捨てはログ出力やタイムスタンプのフォーマット時に発見しにくい。

1.5 SCMI リセットコントローラが誤ったコンテナを取得、ドライバ登録順もサブシステム初期化に変更（11-02）

日時：2026-11-02 18:20（マージ時間）　情報源：提案 #11946

22 行追加、7 行削除、reset-scmi.c と pm-domain-scmi.c の 2 ファイルを変更。本調査期間最後のプッシュである。

リセット側の問題は、コンテナ変換で誤ったオブジェクトを使用していたことである。scmi_reset_reset()、assert()、deassert() およびデバイスツリー解析関数はいずれも raw_to_scmi_reset(rstc) と記述し、rt_reset_control ポインタを SCMI リセットコントローラとして逆算していた。正しい方法は rstc->rstcer を経由し、まずリセットコントローラを取得してから変換することである。誤ったポインタを渡した結果はクラッシュではなく、ずれたフィールドを読み取ることになり、その挙動はメモリレイアウトに依存する。そのためこの種のエラーは、特定のボードで「リセットが効かない」という現象が出るまで発見されないことが多い。

登録側では、2 つのドライバが元々 RT_SCMI_DRIVER_EXPORT を使用していたが、明示的な登録関数と INIT_SUBSYS_EXPORT に変更された。2 つのエクスポートマクロの違いは登録タイミングである。ドライバはリセットおよび電源ドメイン基盤の準備完了後に登録する必要があり、そうでなければコンシューマが先に probe してプロバイダを取得できなくなる。提案の説明ではさらに、デバイスツリーから解析した reset domain ID で属性を検索すること、およびリセットコントローラインスタンス内に SCMI デバイス参照を保持してコントローラのライフサイクルがデバイスより短くなるのを防ぐことにも言及している。

1.6 X/Y/Z バージョンルールがドキュメントレビューに入り、Z バージョン向け QEMU テストリストも同時に公開（11-02 ~ 11-03）

日時：2026-11-02 15:24（リスト）/ 2026-11-03 07:23（ドキュメント更新）　情報源：提案 #11955、欠陥 #11972、提案 #11974、提案 #11976

前号で報じたバージョン管理提案 #11955 が調査期間末に再度更新され（11-03 07:23）、ドキュメント内容は具体化された。X/Y/Z の 3 段階バージョン番号の判定ルール、Y バージョン周期 3～6 か月、Z バージョン周期 1 か月、各レベルのリリース責任と互換性要件などである。まだレビュー中で、未マージである。

付随する実行リストは CYFS3 が 11-02 15:24 に欠陥 #11972 として公開した。タイトルは非常に率直で――Z バージョンのリリースに向けた CI 自動テストである。核心的な考え方は「QEMU のエミュレートデバイスで実ハードウェアを代替する」ことである。マイクを例にすると、仮想 ops を 1 組登録してエミュレートマイクを作るだけで、フレームワークインターフェースの入力を網羅的にテストでき、ボードを待つ必要はない。リストはフレームワークごとに utest と QEMU 両側の現状を項目別に列挙している。SPI にはループバックテスト、PWM には周波数とデューティ比のテスト、RTC にはアラームテスト、audio にはファームウェア内のエミュレートマイクとプレーヤーおよび DMA コールバックが既にあり、adc と dac のフレームワークテストは補充中（#11974 と #11976 に対応）であり、i2c、can、watchdog、touch、usb、sdio、flash、ethernet の QEMU 側はほぼ空白である。

このチェックリストの価値は、「Z バージョンをリリースできるかどうか」をメンテナの主観的判断からチェック可能な表へと変える点にある。これは #11955 と一組のものの両半であり、半分がルールを定め、半分が証拠を提供する。締め切り時点で #11972 には 6 件のコメントがあり、adc と dac の 2 つの utest 提案はすでに提示されているが未マージである。

2.1 グラフィックデバイスの負オフセット：pread と pwrite が位置検証を迂回し、カーネルの任意読み書きに直結（11-02）

日付：2026-11-02 12:01（報告時間）　情報源：欠陥 #11969、提案 #11970

報告者は XueDugu で、照合ベースラインは当日の master 08cad4ee。影響範囲は明確に書かれている：v5.3.0 から現在の master まで、欠陥は 2025-12-12 のコミット 5abecc1fd0c3 によって導入され、現在の graphic.c の blob は 14de5a6c である。

_graphic_read() と _graphic_write() は符号付きのデバイスオフセットを受け取るが、pos >= 0 を検査せず、pos < framebuffer_len も検査しない。残り長は rt_min_t(rt_ssize_t, plane->framebuffer_len - pos, size) で計算される：pos が負の場合 framebuffer_len - pos は大きな正数になり、res はそのまま size を取る。その後 rt_memcpy(plane->framebuffer + pos, buffer, res) がフレームバッファの前または後ろで読み書きする。

入口は RT-Smart の pread64() と pwrite64() にある。現在の rw_verify_area() は count >= -pos のときのみ負の位置を拒否するため、count=8、pos=-210456 のような組み合わせが検証を通過し、そのままドライバに到達する。報告は二層の検証を示している：qemu-virt64-aarch64 に QEMU 付属の ramfb デバイスを組み合わせ、ユーザー空間からカーネルへの越境パスを証明；Raspberry Pi Pico 2 W（RP2350）は USB CDC 経由で、ボードレベルのカーネル API プリミティブ自体を検証。

修正提案 #11970 は 31 分後に提示された（12:32）。作者は usualtreee で、10 行追加、graphic.c の 1 ファイルのみ変更：2 つの関数は残り長を計算する前にまず pos を判定し、負の値と framebuffer_len 以上の位置は直接 0 を返し、正当な読み書きのフロントトリム動作は変わらない。これは本調査期間で最も速い対応である——報告からパッチまで半時間だが、パッチはまだマージされていない。

2.2 pipe のパッチは当日到着、ドライバ側でコマンドごとに自衛する形に変更（11-02）

日付：2026-11-02 15:23（提案時間）　情報源：提案 #11971、欠陥 #11958

前号で報じた pipe の FIONREAD 欠陥にパッチが到着した。22 行追加、4 行削除、pipe_fops_ioctl があるファイルのみ変更。

変更方法は、リングバッファのデータ長または残り空間をまずスタック上の int に計算し、MMU ビルドでは lwp_put_to_user() でユーザーアドレスにコピーして戻し、非 MMU ビルドでは直接書き込みを維持する——単一アドレス空間では分離などあり得ず、この層を増やすとむしろ互換性を壊す。併せて pipe と pipe->fifo の NULL チェックを補い、lwp_user_mm.h の include を ARCH_MM_MMU で囲んだ。

提案には、なぜ sys_ioctl() で一括して阻止しないかの説明がある：ioctl の意味はドライバによって異なり、スカラー引数のものもあれば構造体ポインタのものもあり、グローバル検証は誤爆しやすい。コマンドごとにドライバ側で自衛する方が適切である。この取捨は記録に値する：前号では pipe、ブロックデバイス、端末の 3 箇所を同一成因に帰したが、統一入口が唯一解ではなく、代償は各ドライバが自分でやることを覚えておく必要があることだ。

2.3 メンテナ自身が 2 件の旧提案を再作成：getaddrinfo と GPT パーティションテーブル（11-03）

5.1 産業ゲートウェイのオープンソース：FreeModbus マスター、LVGL パネル、4G クラウド接続、HTTP OTA を 1 つのイメージに統合（11-02）

日付：2026-11-02 13:59（リポジトリ作成）　情報源：リポジトリ：rtthread-industrial-gateway

新規作成された個人プロジェクトで、産業データゲートウェイの 4 つの経路を同一の STM32F407VGT6 上に実装している：下り方向は FreeModbus を RTU マスターとして用い、現場スレーブの保持レジスタを周期的にポーリングする；ローカルは LVGL 8.3 で HMI を構成し、ボタン制御と読み戻しが 1 つの保持レジスタミラーテーブルを共有する；上り方向は ML307 4G モジュールを介して MQTT QoS1 で ThingsBoard に接続し、RPC による逆方向制御をサポートする；リモートアップグレードは HTTP のチャンクダウンロードと CRC32 検証を用い、download パーティションに書き込んだ後、rtboot が app パーティションへ移動させてからジャンプする。

ハードウェア構成は同種のリポジトリの多くより詳細に書かれている：FSMC 8080 パラレル 16 ビット TFT、xpt2046 抵抗膜タッチパネルは SPI 接続、W25Q128（16 MB）は SPI1 に接続しチップセレクトは PG15 のソフトウェア制御、ML307 は uart6 で AT コマンドを使用、Modbus スレーブは uart3 の 9600 8N1 に接続。プロジェクトは 9 つの段階を踏んで段階的に進み、最終段階で 4 つの経路を同一のイメージに統合する。

この組み合わせの意義は「全経路がボード側にある」ことにある：多くのゲートウェイプロジェクトはクラウド接続を外付けモジュールや 2 つ目の MCU に任せるが、このプロジェクトは 4G、プロトコル変換、HMI、OTA を 1 つの M4F に押し込んでおり、その代償として 192 KB の SRAM に LVGL バッファ、Modbus フレーム、MQTT セッションを同時に収めなければならない。産業ゲートウェイの選定を行うチームにとって、このリポジトリのディレクトリ構造とパーティション分割は完成品以上に参考価値がある。

第二の線は RT-Smart とデバイス境界の清算が第二段階に入ったことである。前回の判断は「報告が多く、パッチが少ない」だったが、今期の変化はパッチが追いつき始め、対応も速くなったことである：グラフィックスデバイスの負のオフセットは報告から提案まで 31 分（#11969 から #11970）、pipe のパッチは当日に到着（#11971 は前回の #11958 に対応）、メンテナ本人が getaddrinfo と GPT の 2 件の古い提案を作り直した（#11977、#11978）。キューにはまだ 5 件が審査中だが、いずれも再現手順があり、レビューコストはすでに低下している。

第三の線はバージョンガバナンスが「計画」から「証拠」へ進んだことである。#11955 は X/Y/Z の周期と責務をドキュメント化し、#11972 は Z バージョンをリリースできるかどうかを QEMU 仮想デバイスと utest のフレームワーク別リストに分解し、adc と dac の模擬デバイステストにまで提案を付けている。この 2 件はいずれもカーネルを変更しないが、今後の各 Z バージョンリリース時の判断根拠を決めるものである——前回述べた「手作業で整理する工程を検査可能なフローに変える」が、今期はリストとして具体化した形だ。

エコシステム側の動きはより直接的である。先楫半導体は 13 分以内に 12 の BSP リポジトリを v1.13.0 にプッシュし、新たに HPM5100EVK を開設した。これは原廠側の BSP メンテナンスがすでにスクリプト化されていることを示す。コミュニティ側では Modbus、LVGL、4G、OTA をすべて 1 颗の M4F に載せた産業用ゲートウェイプロジェクトが現れた。一方はメーカーがボード間の一貫性を保証し、他方は開発者がコンポーネントを極限まで組み合わせる。この両端こそ、RT-Thread の現在最も現実的なエコシステムの姿である。

6.2 限界と重複排除の説明

フォーラム club.rt-thread.org は今期も 468 を返し WAF チャレンジページを前置しており、スレッド一覧と本文を直接読むことができない。コミュニティ討論側の情報欠落は GitHub とメディアコラムで補完し、スレッド単位の照合は行っていない。公式ニュース API と公式サイトのニュース一覧はいずれも 6 月 17 日で止まっており、リリース側の情報はメディアコラムに依拠するほかない。

Google News の英語側 2 組のクエリはゼロヒット、中国語側 3 組は結果あり：上海オープンソースコンテスト（収録）、恩智浦アンケート（収録）、智东西による安謀科技極術コミュニティのロボット犬に関する記事（本文に RT-Thread の具体的な技術内容がなく、未収録）。他に 11-01 のダブルイレブン販促記事があるが、期間外かつプロモーション内容のため未収録。HN Algolia では調査期間内に RT-Thread 関連のヒットはなかった。

GitHub 側は今期、匿名 API のレート制限（毎時 60 回）の影響を受けた。メインリポジトリのコミット、提案、不具合の明細はすべて取得済み。先楫の 12 リポジトリのバージョン番号は HTML と Atom のコミットフィードで交叉確認し、うち 3 箇所はコミット情報が v1.13.0 であることを確認、残り 9 箇所は同一タイムスタンプ区間から同一バッチのリリースと判定し、リポジトリごとのコミット本文取得は行っていない。前回審査待ちキューに入れた #11897（K230D）、#11892（RISC-V Smart MMU）、#11944（RTL8125）、#11943（RK3588 ディスプレイオーディオ）、#11959（NXP RT1180 リンクスクリプト）は今期もキューに残り、マージされていないため重複計上せず、#11954 と #11958 は前回既報のため、今期は更新とパッチの進展のみを記す。
