1. カーネルとバージョン動向

1.1 ビルドツールチェーン欠落チェックがマージ：ツールチェーンディレクトリ欠落時にビルドを明示的に失敗（10-12）

日付：2026-10-12 09:56（マージ時間）　出典：PR #11863

ビルドツール修正がマージ（#11863、作者 Rbb666、単一ファイル tools/building.py）：ビルドエントリにおいてツールチェーンディレクトリ欠落時の処理を、ローカル終了フラグのセット（need_exit = True）から直接 sys.exit(1) に変更し、ビルドを非ゼロ終了コードで即座に明示的失敗させ、欠落したツールチェーンのまま後続フローを実行しないようにした。本提案は 10-12 午前に作成され、約 36 分後にマージされ、期間内で最初の着地となった。

1.2 Eclipse プロジェクト生成修正がマージ：#11787 が着地、SCM メタデータディレクトリを再帰スキャンしなくなる（10-12）

日付：2026-10-12 11:06（マージ時間）　出典：PR #11787

Eclipse ターゲット生成スクリプト修正がマージ（#11787、作者 wdfk-prog、単一ファイル tools/targets/eclipse.py）：ソースファイル収集と除外ロジックに SCM メタデータディレクトリリスト（.git / .svn / .hg）を導入し、これらのディレクトリを再帰的に展開スキャンしないようにし、バージョン管理メタデータを含むプロジェクトツリーでの大量のオブジェクトファイルの走査を回避；隠しディレクトリは同時に通常ディレクトリと同じ除外ルールに統一された。本件は 09-08 に作成され、10-11 の CI 調査（失敗原因はパイプラインに scons コマンドが欠落しており、除外ロジックとは無関係）を経て本期マージされ、期間内で 2 番目の着地となった。

1.3 新提案：rtdbg.h のインクルード関係を修正、IAR 下での rt_kprintf 暗黙宣言を修正（10-12）

日付：2026-10-12 13:50（作成時間）　出典：PR #11864

新提案（#11864、作者 meng-plus、単一ファイル include/rtdbg.h）：ヘッダーファイル内の #include を #include に変更し、rtdbg.h のみを経由してログリダイレクトを行うコンポーネントでも rt_kprintf の正式な関数宣言を取得できるようにした。作者の報告：IAR 8.40 環境で rtdbg.h 経由のログリダイレクト時に rt_kprintf の暗黙宣言が発生し、%f フォーマット出力が異常となる；提案には with_proto / no_proto の 2 組の最小対照サンプルを添付。提案はオープンレビュー中。

1.4 RISC-V ベクター：vstart 提案、メンテナーの意見に従いテスト構成を調整（10-12）

日付：2026-10-12 09:17（レビュー時間）　ソース：PR #11861、Issue #11786

RISC-V ベクトルコンテキスト修正提案（#11861）は調査期間内にメンテナから新たなレビュー意見を受領：テストおよびそのアセンブリプローブを専用の utest ディレクトリへ移行し、条件付きビルド統合を有効化し、VLEN=128 と VLEN=256 の2つの構成におけるベクトルサポート、ヒープ、UTest の CI 構成を補完することが提案された。提案者は 10-11 に前回の意見に従い修正コミットをプッシュ済み（各呼び出しごとにスタックフレームを独立に確保し、成功・失敗パスで統一的に解放）。本件はオープンのまま維持され、テスト構成の調整を待っている。同一提案者が推進する OSPP 2026 課題「RISC-V 遅延 FP/RVV コンテキストスイッチ」（#11786）も調査期間内に一度更新があり、オープンを維持。

1.5 ping ゼロ除算第二案：提案者がバイパス提案を取り込み再度修正をプッシュ（10-12）

日付：2026-10-12 20:18 ~ 20:47（コメントとプッシュ）　ソース：PR #11862、PR #11853

netdev ping ゼロ除算修正第二案（#11862）は調査期間内に再イテレーション：貢献者 CXSforHPU が ping ループ内の遅延ロジックについて2点の改善を提案（最後のメッセージには遅延を追加すべきでない、0 引数での rt_thread_delay 呼び出しを避ける）し、本案で併せて修正するかどうかを問い合わせた。原作者 ymj0440 は当晚これを受け入れ修正をプッシュ——遅延判定を常に偽となる index == times から index != times - 1 へ変更し、delay_tick > 0 の場合にのみ遅延関数を呼び出して -RT_EINVAL の発生を回避。本案は第一案 #11853 と並行しており、依然としてメンテナがいずれかをマージするのを待っている。

4. 業界応用

4.1 端辺協調高機敏ロボットアームシステムのオープンソース共有：Titan Board RA8P1 による完全自律制御と 17 種ジェスチャー NPU 認識（10-12）

日付：2026-10-12（メディア公開日）　情報源：電子工程専輯原文、プロジェクトコードリポジトリ

RT-Thread AIoT コンテスト優秀賞作品「端辺協調高機敏ロボットアームシステム」が完全な技術共有を掲載しコードをオープンソース化（リポジトリは 10-12 に初期コミット完了）：一側上肢障害者向けのデスクトップ級補助ロボットアームで、ロボットアームと高機敏ハンドの制御を PC から切り離す——Titan Board（ルネサス RA8P1、Cortex-M85 + Ethos-U55 NPU）を唯一の制御コアとし、実行端は LeRobot SO101 ロボットアームと Amazing Hand 高機敏ハンド、Joy-Con コントローラは ESP32 / Bluepad32 経由で接続し遠隔操作を実現。ボード上に 17 種ジェスチャー認識モデルを展開（YOLO-Fastest を PyTorch で訓練、INT8 TFLite 量子化、RUHMI / Vela で全 NPU 単一サブグラフにコンパイル、107 個のオペレータすべてが Ethos-U55 に配置）、単回推論は約 77~78 ms、カメラ 640×480 キャプチャ、ローカル LCD 表示と WebSocket 映像クラウド送信（160×120 JPEG、約 3~6 KB/フレーム）を並行し、Web 側で MediaPipe 手部キーポイントを重ねて表示。工程上の要点は D-cache と OSPI クロックの段階的起動戦略（WHD ファームウェアダウンロードの読み戻し検証失敗を解決）、WiFi と NPU 工程の融合、TinyJPEG 低帯域ストリーミングなど。著者はさらに 2 種類の躓きポイント対処経験を公開：RT-Thread Studio ソフトウェアパッケージインデックスのエラー処理と e2 Studio に依存しないモデル変換コマンドラインフロー。
