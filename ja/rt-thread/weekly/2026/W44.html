6. トレンド観察

  • Smart の位置づけは今週、「デフォルト設定」ではなく「テストカバレッジ層」として明確化された：10-29 の一日のうちに、まず Smart を有効化し、その後デフォルト設定を撤回した。一見繰り返しのように見えるが、実際はメンテナが境界を引いている——デフォルト設定は予測可能な状態を保ち、Smart なしの通常回帰を安定させる必要がある。Smart は utest の設定オーバーレイ層を通じて個別に実行され、両パスは1つの BSP を共有する。これにより QEMU 上のユーザー空間テストカバレッジを獲得しつつ、既存の BSP ビルドマトリクスを乱さない。これに伴う観察点は #11892 と #11897 である：QEMU で検証できるものは先にマージし、実機ボードでの確認に依存するものは後にマージするという、このスケジューリングの法則が今週2回裏付けられた。
  • RT-Smart のユーザー空間／カーネル空間の境界が今週最も重いセキュリティ主線となり、すでに族化している：端末、ブロックデバイス、パイプ、メールボックスの4箇所で形態は完全に一致しており、いずれもアダプテーション層のデフォルト引数がすでにカーネルアドレスであり、ユーザー空間の入口に copyin/copyout がない。4件の影響バージョンはすべて2022年の同一の RT-Smart 同期コミットに遡り、これは新たに導入された欠陥ではなく、移植時に全体として持ち込まれた構造的ギャップであることを示している。修正パスもすでに明確である（#11941 のカーネルスタック一時保存に copy_from_user/copy_to_user と lwp_in_user_space() の境界チェックを加える）。今後の注目点は、この手法が共通層として抽出できるかどうかであり、各サブシステムごとに個別に修正することではない。
  • 主線のリズムは「滞留提案の一括清算」に支配されており、当日の新規開発ではない：10-27 の4件、10-29 の7件のマージのうち、大多数の提案の author 時間はマージ時間より1週間以上前であり、10-29 の那群はさらに10-18 作成で11日間待ち行列に並んでいた。この形態はプロジェクトの健全性判断に影響を与える：コミット数だけを見ると当週の開発強度を過大評価し、ゼロコミット日だけを見るとレビュー活動を過小評価する。本当に安定した指標は「提案キューのターンアラウンドタイム」である——今週それは10日から1日に収束した（#11896 マージ後に #11942 が当日追随）。これは前向きな変化である。
  • テストの信頼性はテストとしてではなく、インフラとして修正されている：今週修正された3つの事柄はいずれも「ケースを増やす」ことではなく、判定自体を信頼できるものにすることである——後続の unit 通過が前の testcase の失敗を抹消しなくなる（#11601）、CI が公網と不正な IP 文字列に依存しなくなる（#11601）、musl 下で signal 0 がインストール可能と仮定しなくなる（#11601）。さらに #11942 が CI の設定オーバーレイ方式を「チェックアウト全体」から「1行追記してスイッチをオフにする」に変更した。これは先週の pkgs-test の並行ロック修正と同じ線上にあり、「テスト通過」という前提をまず確実にしてから、カバレッジを語るというものである。
  • バージョンリリースは「待機」から「制度化」へ移行しているが、リリース動作の門はまだ開いていない：v5.4.0 のバージョン番号は10-17 にすでに bump され、10-29 にはさらに 0x50400 に引き上げられたが、releases と tags は09-10 の v5.3.0 で7週間停止している。10-30 に出現した2つの資料（#11956 のバージョン管理 CI とリリースプロセス、#11955 のバージョンとリリースプロセスのドキュメント）は、コミュニティ自身もこの乖離を処理していることを示している——Z 線の月次レポートと手動承認、Y 線は3〜6ヶ月ごとにハードウェア検証と組み合わせ、「QEMU の結論を実機の結論に拡大しない」ことを非目標として明記している。次回はバージョンマクロではなく、release ページと ChangeLog で実際に門が開いたかどうかを再確認すべきである。
  • ベンダー適応の形態が変化している：一方ではツールチェーンとシミュレーションが先行し、もう一方では一大類のハードウェアがまとめて参入している：TriCore は主リポジトリではなく Env SDK に入り、まずオープンソース GCC と QEMU で「コンパイルできる、実行できる、デバッグできる」を解決し、BSP とドライバは後回しにしている。同時に RTL8125、RK3588、RT1180 の3件の大規模提案が同期間に審査中であり、適応の重心が「単一開発ボードの点灯」から「プラットフォームとペリフェラルスタック全体」へ移行していることを示している。2つのパスのレビューコストは大きく異なる：前者はパッケージインデックス層の低リスク増分であり、後者はしばしば数千行に及び、ボード側の確認が必要である。これが BSP キューに常に172ファイルと29万行規模の提案が滞留している理由でもある。
