RT-Thread ウィークリーレポート (2026-10-19 ~ 2026-10-23)

2026-10-23 Kubuds

レポート期間：2026年10月19日（月）から10月23日（金）までの5営業日、5回分のデイリーレポート。さらにリリース日（10月24日）における GitHub コミットストリーム、リリースページ、Studio ツールチェーンインデックスの確認を含み、10-23 08:00 から 10-24 17:00 までの收尾変動をカバー
素材来源：本誌の毎日 RT-Thread 動態デイリーレポート5回分（10-19、10-20、10-21、10-22、10-23）。合計有効調査期間は10-16 08:00から10-23 08:00まで（月曜日分は週末をまたぐ72時間の調査期間）。リリース日の確認は GitHub メインリポジトリと packages、env、rtthread-skills、smart-build、Studio SDK インデックス各リポジトリのコミット実測に基づく

1. 今週の要聞

  • 進迭時空 K1 初版 BSP がメインラインにマージ、アプリケーションプロセッサ級 RISC-V プラットフォームが初めて主干に進出（10-19）：提案 #11132 は2026-01-11に公開され、約9か月のレビューを経て作者 GuEe-GUI により着地。4コミット、173ファイル、+53862/-12。Next RISC-V 重构（#10320）の後続に属する。BSP は8個の X60 コアを統合した64ビット RISC-V プラットフォーム向けで、U-Boot/OpenSBI によりブートされ、S モードで動作。デフォルトで MMU と SMP を有効化し、検証プラットフォームは Banana Pi BPI-F3。PCIe/NVMe、eMMC HS400、イーサネットと PTP、HDMI フレームバッファ、JPU と V2D 加速、オーディオ、CPUfreq と熱管理を既にサポート。ドライバ層は bsp/spacemit/dm に別途抽出（147ファイル、49個の C ファイル、約30モジュール）され、同系 SoC で再利用可能。

  • RISC-V チケットスピンロックをアトミック加算に変更、K1 の SMP 設定は同日4コアから8コアに開放（10-22 マージ）：提案 #11904 はチケット取得を1命令の amoadd に、ロック解放を1回の16ビット半語ストアに変更。6ファイル +33/-37。元の実装ではチケット取得とロック解放が同一ワード上でロードリザーブ+条件ストアのループを通り、マルチコア高競合下で互いのリザーブを潰し合いライブロックに陥る。ロック解放のワード全体読み書きは並行して新たに取得されたチケット番号を上書きする。2つの根本原因を一并に解消し、両側にそれぞれ1か所のメモリバリアを追加。このコードは全ての RISC-V ボードで共有されるため、影響範囲は単一 BSP より大きい。

  • ESP32-C3/C6 の ESP-IDF v6.1 全鏈適配が着地、RISC-V ツールチェーンは GCC 15.2 に移行（10-21 ~ 10-22）：パッケージ側 RT-Thread-packages の esp-idf は10-21 15:23に5.1から6.1.0へのパッケージ全体アップグレードを完了してマージ（変更ファイル2万余）。components/rtthread 移植層と CONFIG_IDF_RTOS_RTTHREAD カーネル置換スイッチを新規追加。メインリポジトリ提案 #11870 は10-22 15:42にマージされ、55ファイルに関与。C3の13設定と C6 デフォルト設定はコンパイル通過。ハードウェア上板欄は依然として「検証待ち」と記載。C3、C6 は RISC-V コアであり、この経路は現在パッケージからメインリポジトリまで整備済み。

  • 一週間で6枚の欠陥票を起票、うち5枚はメモリと境界セキュリティ、NVMe は1回の起動で約1.1 MBのカーネルヒープを漏洩（10-20 ~ 10-23）：新規 #11902（tmpfs 截断後の使用）、#11905（cromfs ディレクトリ名越界）、#11906（中国語 Windows エンコーディング）、#11913（raw DHCP オプション越界読み取り）、#11917（NFS 越界書き込み）、#11919（NVMe ヒープリーク）の計6件。エンコーディング問題を除く5件はすべてメモリと境界セキュリティに属する。うち #11919 は QEMU 純正 NVMe デバイス上で1回の起動ごとに1,156,872バイトをリークし、ホットプラグで線形に累積。レポートは CWE-401 と CVSS 3.1 4.9を提示。#11917 の導入コミットは2010年まで遡及可能で、v1.2.0以降の全バージョンが影響を受ける。

  • RT-Thread Smart は一括提案からテスト可能段階へ移行、シグナルとデバイスツリーの2か所の越界に修正提案（10-18 ~ 10-22）：メンテナは10-18 19:35から19:36までの2分間に13件の提案を連続起票（#11885 ~ #11897）。内容は qemu-virt64 での Smart 有効化、riscv64 の SMP 無効化、virtio-blk への ext4 と ptyfs マウント、lwp syscall 分割、K230D 128MB DDR 適配などを含む。今週対応する欠陥の修正フォロー：lwp シグナル番号検証（#11899）、OFW デバイスツリー深度事前検査（#11901、レビュー後デバッグゲート付きに変更）、cromfs ディレクトリ名境界（#11911）、tmpfs 截断後の使用（#11910）。メンテナは libdl 動的モジュール欠陥について見解を表明：境界検証は局所修正可能、メモリ隔離はユーザ態への移行が必要。

  • スケジューラの2つの独立経路が同一判別式に収束、3年前の旧案の再テストでシングルコアの二重解放が露呈（10-21）：コミュニティメンバーが2022年に保留されたタイムスライスパッチ #6645 に3件のコメントを連投してレビューに戻した。その「実行中かつタイムスライス未消費でプリエンプトされた場合のみ先頭に割り込む」という判別式は、今週の新提案 #11907 が独立に導いた結論と完全に一致する。しかし #6645 の「READY 書き込みを遅延」する実装は、シングルコア経路で idle 回収時に TCB の二重解放を引き起こす（スケジューラグループの utest が安定してクラッシュ）。分離実験により、問題は YIELD クリア位置にはないことが判明。結論として #11907 の「先に stat_before を保存してから判定」を基礎に進めることを推奨。

  • メインラインのリズムは「3日間静寂、1回で収束」：今週は計7コミット、6提案、10-22 の3時間内に4件（10-19 ~ 10-23）：10-19 に2件（rt_null 事前登録 #11884、K1 初版 #11132）、10-20 から 10-22 午前までゼロコミット、10-22 15:42 から 18:00 に4件連続（ESP32 #11870、チケットロックと K1 8コア #11904、attachconfig #11908）、10-23 17:09 にさらに clang-format ルール提案 #11859。バージョン側は依然動きなし：最新タグとリリース物は依然 09-10 の v5.3.0、v5.4.0 は 10-17 にマージされたバージョンマクロと Kconfig デフォルト値のみで、リリースノートとバイナリはなし。

  • ベンダー側も同週に推進：睿擎 V1.8.4 をリリースし産業現場向け修正を追加、兆易創新は24時間でネットワークと UI の2つの基盤部品を補完（10-21 ~ 10-22）：睿擎 V1.8.4 は 10-21 にリリース（QY1503 エンコーダ、MIPI RGB666、GPIO 上下プル、amp_device デバッグコマンドを追加、EtherCAT 割り込みアフィニティ、telnet 下の netstat フリーズ、UART DMA ボーレートを修正）、IDE も同時に V1.5.62 へ更新。兆易創新側では GD32VW553 が 10-22 に at_device パッケージへ、GD32EmbeddedUI サンプルはリポジトリ作成から1日後に LVGL パッケージインデックスへ、Studio SDK インデックスは同日 Gino Pi（GD32H77D）1.1.0 と PyOCD 0.3.1 を収録。

セキュリティと欠陥

日付：2026-10-20 ~ 2026-10-23　情報源：Issue #11919

  • 新規6件：#11902 tmpfs で rt_realloc(data, 0) が空ポインタを返す際に ENOMEM を設定するが成功を返し、正当な ftruncate(fd, 0) がバッファを解放した後に成功を報告する（v5.0.2 以降の全バージョン、QEMU aarch64 と RP2350 で再現、10-20 にコミュニティが引き受け済み）；#11905 cromfs のディレクトリエントリ読み取り時にディレクトリ名長に上限がなく、ディレクトリエントリバッファを越えてカーネルプログラムカウンタを乗っ取ることが可能（v5.0.0 以降、DFS の2世代実装が同源、未引き受け）；#11913 raw-API DHCP サーバのオプション走査で buf + 1 < end を事前検証せず、1500バイトの pbuf を最大4バイト越えることが可能（同ディレクトリのソケット実装では当該検証済みで、欠落点の反証となる）；#11917 nfs_read がサーバ返信の count を memcpy 長として使用し、内蔵 cat の81バイトスタックバッファでリターンアドレスを上書き可能（2010年のコミットで導入）；#11919 NVMe スキャンがデバイス報告のネームスペース数をループ上界とし、各ラウンドで4480バイトを割り当ててからコマンドを発行し、2つの失敗パスがいずれも解放しない。なお #11906 は中国語 Windows 下のコンソールエンコーディング欠陥で、ツールチェーン側に分類（第3節参照）。
  • 修正提案5件：#11899 sys_sigaction 入口でシグナル番号を1から64に限定し、lwp_signal_action 内にも同様の検証を追加；#11901 デバイスツリー展開前に事前走査で最大深度を求め、63層超過を拒否（レビュー後にデバッグスイッチでゲートする方式に変更）；#11911 cromfs のディレクトリ名長を制約；#11910 tmpfs のゼロ長切り詰め後の解放後使用を修正；#11918 9PFS の読み取りと getdents の2パスがいずれも実受信バイト数に基づいてメッセージ長を収束させるようにし、作者は bsp/simulator と ASan で偽 9P サーバを構築して再現（修正前は use-after-poison が発生し、読み取り位置は 8 MB ヒープ領域の第 8,334,515 バイト）。
  • 未クローズ：#11878 lwip-dhcpd リースプール枯渇による無限ループ、#11905、#11913、#11917 の4件が未引き受け。うち #11917 は今期ステータス更新のみ。
  • 共通判断：今週の5件のセキュリティ欠陥の共通形態は「デバイスまたはサーバ側で制御可能なメタデータを直接メモリ操作の長さまたは上界として扱う」ことである。同一研究者が2日間で NFS、NVMe、9PFS の3件を報告し、その手がかりは mtd-cfi と usbhost の旧件に遡れると自述。個別修正のコストは系列単位の排查より高い。

3. エコシステムとベンダー適配

ベンダーBSPとドライバ

日付：2026-10-19 ~ 2026-10-23　情報源：PR #11132

  • 進畳時空：K1初版BSPがマージ（#11132）。デフォルトコア数は10-22に4から8へ変更。SPIとQSPIは「移植済み・検証中」から正式化し、以前保留されていたSPI NORのID読み取り問題もこれに伴いクローズ。リポジトリルートのボードサポート表に当該ベンダー区分を新設し、GPIO、シリアル、ADC、I2C、SPI、ウォッチドッグ、タイマー、PWM、RTC、SDIO、PCI、DMA、イーサネット、オーディオ、ディスプレイ、暗号化各列をすべてサポートと記載。CI側にspacemit-k1ビルドレッグを追加。BSPにはベンダーLinuxイメージから取得したRCPUファームウェア（HDMIオーディオサービス用）が埋め込まれており、リポジトリの説明にチェックサム値と再配布条項の確認を促す記載がある。今後の追跡に値する。
  • 楽鑫：ESP32-C3/C6のESP-IDF v6.1およびGCC 15.2対応をマージ（#11870）。ESP32-S3ボードサポート（#11844）は依然依存の補完待ち。

6. トレンド観察

  • アプリケーションプロセッサ級 RISC-V プラットフォームのメインライン入りが今週最も重い構造的変化：K1 が S モード、MMU、マルチコア SMP の形態でマージされ、PCIe/NVMe、HDMI、マルチメディア加速を備えることは、RT-Thread がハイエンド RISC-V プラットフォームで「起動できる」から「ペリフェラルが揃う」へ向かうことを示す。ドライバは独立して bsp/spacemit/dm の層となり、BSP ディレクトリに「ベンダー層＋ボード層」の分業が現れ始め、K1 は最初の使用者にすぎない。この種のプラットフォームは今後も継続的に汎用コードの欠陥を逆照射していく——今週同時に持ち出されたアトミック比較交換、電源ドメイン命名、DVFS 重複チェックの3件の修正がその証拠である。
  • マルチコアの正しさが今週の技術的主線となる：チケットロックのライブロック面を根本から除去し、アトミック比較交換の期待値が状態レジスタに上書きされなくなり、同優先度のレディ順序を先着順に戻した。3件はいずれも長期的にデフォルト動作に覆われていた問題であり、しかも同一週内に特定された。スケジューラ側ではさらに「互いを意識しない2つの実装が同一の判別式に収束する」状況が現れ、提案を跨いだ横断比較が単一パッチの議論方式を代替しつつある。
  • セキュリティ監査はすでにファミリー化の特徴を呈し、個別修正のコストが収益を上回りつつある：今週の5件のセキュリティ欠陥の共通形態は、外部から制御可能なメタデータをメモリ操作の長さや上限として信頼することであり、NFS、NVMe、9PFS、cromfs、DHCP の5コンポーネントに関与する。報告者自身が導入コミット、影響バージョン区間、再現環境を備えており、修正コストはすでに压低されている。しかし v1 と v2 の2世代の DFS 実装が同源であることに起因する重複欠陥（cromfs の1件で2つのコピーがいずれも制約を欠く）は、ファミリー単位の排查と構造的収束を行うべきことを示唆する。
  • メインラインは「静寂—集中的な収尾」のリズムを呈し、リリースプロセスはまだ開始されていない：連続3日間ゼロコミットの後、3時間以内に4件が着地し、しかも同一メンテナが処理しており、貯めたレビュー後のバッチ処理に近い。v5.4.0 は 10-17 以降、バージョンマクロと Kconfig デフォルト値のみで、タグもバイナリもリリースノートもない。この「バージョン番号が先行し、リリース物が遅れる」状態はすでに1週間続いており、次号ではリリースページと ChangeLog で本当に開闸されたかを再確認すべきである。
  • ツールチェーンの2本の線が並行する：新基盤の入手性とローカライズの細部：一方は ESP-IDF 6.1 に GCC 15.2 と CONFIG_IDF_RTOS_RTTHREAD カーネル置換チャネルの開通であり、C3/C6 以外にも後続の RISC-V 製品ラインに路径を残す。他方は中国語 Windows で絵文字が原因でコマンド全体が使用不可になる問題、clang-format 規則の厳格化、Studio SDK インデックスの3件の更新といった「技術的含有量は低いが、直接的に導入体験に影響する」修补である。後者は国内開発者に対する限界収益がしばしばより高い。
  • 公式チャネルの静寂とコミュニティ負担の分業がさらに固まる：ニュース接口は4か月以上更新停止しており、今週の対外情報はほぼすべて GitHub、フォーラム大会作品、業界メディアが担い、睿擎のバージョンリリースも自社チャネルではなくメディア稿を通じている。この構図はすでに2週連続で変わらず、コミュニティコンテンツの密度（今週3作品、日平均1〜2投稿）がむしろ公式の叙事機能を代行している。
