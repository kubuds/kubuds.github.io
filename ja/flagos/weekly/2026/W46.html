今週は64リポジトリ中19から22リポジトリにプッシュがあり、5期合計でコミット1077筆、マージ済み1030筆、審査中は252から343筆に上昇した後272筆に回落した。

  • 2.3ロードマップが公開され、目標は12-30リリース：#176で三本の主線が定まり、vLLM 0.32とSGLang 0.5.18が主リリースバージョンとなる。FEP-0163 FlagMegaが同日マージされ、Qwen3.8のモデル全体コンパイルで20%の効率改善、GLM5.3 FlashのデコードスループットをvLLMより5%高めることを要求し、12-07までに主干へ切り込む必要がある。

今週の判断：2.3は提案募集からバックエンド別の納品補完へと移行しており、リスクはAPI改名ではなくプラットフォーム差異と放行速度にある。レビュー存量272筆は依然としてボトルネックで、12-07まで残り三週間しかない。

1. 今週の要聞

  • 2.3ロードマップが公開され、目標は12月30日リリース、モデルコンパイルがオペレータ、フレームワークと並ぶ位置に引き上げられた（11-12）：community #176は11月12日未明に2.3ロードマップを公開し、SIG別に提案、トラッキングチケット、担当者を列挙し、チェックボックスをリリース検収憑証とした。三本の主線はモデルとフレームワークのカバレッジ、コンパイラとruntimeの性能、開発者体験と納品。フレームワーク側ではvLLM 0.24の検収完了とvLLM 0.32を十二社廠商マトリクスの主リリースバージョンに定め、SGLangを0.5.18に上げて十社廠商をカバーすることを要求。同日FEP-0163 FlagMegaがマージされ、配套PRにより実装中と標記され、トラッキングチケット#173が納品を承接。FEPはQwen3.8とGLM5.3 Flashのモデル全体をMegaKernelにコンパイルし、英偉達、AMD、天数CoreX 5.0の三バックエンドで検証することを要求し、Qwen3.8は20%の最適化目標を定め、GLM5.3 Flashのデコードスループットは四枚のH800上でvLLMより5%以上高くする必要がある。12月7日にFlagTreeリリースブランチを切る前にfeature/flagmegaを主干へマージしなければならず、12月25日にリリース検収を完了する。

  • FlagTree 0.7.1 正式版はバックエンドごとに段階的リリース、云天励飛が 2.3 サイクル初の新規参入バックエンドに（11-12）：0.7.1+ascend3.5（15:43）と 0.7.1+xpu3.6（19:28）の二つの正式版が同日リリースされ、Release 説明は「pypi 0.7.1+<バックエンド>」の一行のみ。その他のバックエンドは依然として a1（hcu、tsingmicro）、a2（iluvatar、mthreads）または dev1（ppu）のまま。同一バージョン番号でバックエンドごとに段階的リリースするのは FlagTree の一貫した手法だが、今回はそのまま 12-07 の締め切りノードに直結：締め切り前にリリースされなかったバックエンドはプレリリース版しか 2.3 に持ち込めない。同日 #1598 が云天励飛（Intellifusion）バックエンドをマージ、ターゲットは ifwa:100、Triton 3.8 で、メモリアクセスと matmul の lowering、ソフトウェアパイプライン、非同期コピー、LHS から TMEM への昇格、および独立した手動 wheel ワークフローを含む。昇騰の Triton 3.6.x 移植（#1637）は依然レビュー中で、マージされれば triton_v3.5.x ブランチからメインラインに復帰する。

  • 2.3.0 のイメージラインとバージョンデータが一週間でバックエンドごとに逐次整備、リリース準備の最小単位はバックエンド一つにドキュメント一つ（11-07 ~ 11-14）：平頭哥 PPU 2.1.0 はまず 11-07 に base と runtime の changelog を取得し、11-11 に runtime イメージの初回納品を完了して torchvision 0.25.0 と torchaudio 2.10.0 の cp312 ベンダーホイールを補完；11-10 に 2.3.0 の変更日を AMD ROCm 7.2.4 に記録；11-12 には天数 corex5.0.1 が corex4.4.0 を全面的に置き換え、同日に昇騰 CANN 9.2.1 の 910C base と flagcx パッケージ行を追加；リリース日チェックではさらに build-infra #1792 が摩尔線程 mthreads-musa5.3.0 base レイヤを追加し、#1789 が ppu の builder とデイリー行を追加。一タグ一 PR、バージョンデータと changelog を同時に着地させるのが、今週の build-infra の唯一の作業方式である。

  • FlagGems は一週間で 591 件をマージ、KernelGen は「オペレータを書く」を「生成結果を審査する」に変える（11-06 ~ 11-12）：五期の調査期間のマージ量は順に 123、166、149、85、68 件で、全組織 1030 件の 57.4% を占め、唯一半数を超えた単一リポジトリとなった。単日ピークは三社に現れた：昇騰 87 件（11-06、一時間以内に同一作者が着地）、燧原 63 件（11-09、すべて GCU300 の境界正確性修正）、沐曦 89 件（11-10、foreach 族を一族まるごと展開）、海光 22 件（11-12、100 分以内に 20 件の foreach）。11-12 の #8740 はリポジトリの規約に合わない 7 つのホスト側オペレータを削除し、実験オペレータ表は 142 から 141 に減少、生産能力を拡大する一方で反対に帳尻合わせを始めたことを示す。

  • 寒武紀は Qwen3 訓練ステップの 17 オペレータをネイティブ実装に回収し、さらにサイレントなキューの順序乱れ欠陥を修正（11-10）：Torch-FL #809 はインプレース算術族、三つの融合 CNNL エントリ、四種類のビューオペレータ、および zeros、sqrt、div をコード生成器から直接寒武紀ネイティブ実装に供給させ、訓練ステップはこれらのオペレータのために FlagGems を迂回しなくなり、同時に fill_ のライフサイクル問題を修正。さらに重要なのはビルド欠陥である：torch_bindings は USE_CAMBRICON 付きでコンパイルされておらず、Triton にどの cnrt キューへ発射するかを伝えるバインディングがそもそも存在せず、Triton は実際には空のキュー上で動作し、CNNL カーネルとの間に順序保証がなかった——この種の欠陥はエラーを出さず、偶発的に数値がずれるだけである。PR の自述では当該訓練ステップの所要時間は依然として torch_mlu の 1.86 倍で、カバレッジと正確性のみを解決し、性能の整合は行っていない。

  • 昆仑芯は二段階実測で 618 のオペレータを 256 のルーティングに収束、vLLM 0.32.0 は py3.10 で最初の硬い障壁に遭遇（11-11）：Torch-FL #806 は前日残された空のリストを引き継いだ——#789 は P800 上の四つのブレークポイントを閉じエンドツーエンドで通したが、許可リストは空で、設定ファイルは変更前とバイト単位で同一、その理由は最初のルートには実測データの裏付けが必要だからである。翌日 #806 は P800 上で二段階測定を行い、618 オペレータの天井から 256 を選別し、設定は「ルーティングなし 1985、昆仑芯 57」から「ルーティングなし 1729、昆仑芯 57、FlagGems 256」へと変化；ルーティング数は三つのリビジョンで 316 から 315、そして 256 へと減少し、作者は重点を「リストを列挙する」から「選別基準を修正する」へと移した。同日 build-infra は早朝に vLLM 0.32.0 を deps_app に追加し、その後このバージョンの py3.10 でのインポート失敗を記録し、二時間以内に撤去した。

  • vLLM 0.32 がロードマップ上の一言から10社の移行リストへ（11-09 ~ 11-13）：11-12 の一日で2つの象徴的な適配がマージされた——英偉達 #737 は KV cache 初期化を 0.32 で削除済みの私有関数から公有の allocate_kv_cache と bind_kv_cache へ移行し、平頭哥 #706 は「0.32-empty」方式で PPU-ZW810E を 0.5.0-dev に乗せた（削除済みシンボルとその呼び出し箇所を削除し、スタブを残さない）。その後、MUSA（#715）、海光（#711）、沐曦（#693）、昆侖芯 P800（#726）、昇騰 Runner V2（#703）、天数（#674）、燧原（#675）、AMD W7900D（#659）の8社が審査中。フレームワーク移行は実行段階に入り、リスクは「アップグレードするかどうか」から「どの社が先に詰まるか」へと変わった。

  • 競賽トラック1が終盤へ：72 個の賽題定義、17 道の実装、9 件の未明審査入り、評奨は 11-13 以降に開始（11-09 ~ 11-13）：11-09 に 72 個の SGLang 競賽オペレータ定義を一括マージし、不足していた 23 個の定義を補完；11-10 に Track1 タグ付きの実装 17 道をマージ、内容は fp8 と mxfp8 のブロック単位スケーリング行列積、3種粒度の量子化、KV キャッシュの mxfp8 書き戻し、AWQ 逆量子化に集中；11-12 に awq_gemm をマージ；11-13 未明 01:07 から 01:08 にかけて、同一作者が連続して 9 件の PR を開いた。競賽日程は 8 月 17 日から 11 月 13 日まで、評奨は終了後1か月以内に検収を完了する。リポジトリ内の定義とコミットの入庫のみであり、性能榜の通過を意味しない。本レポートは成績に関する結論は出さない。

6. トレンド観察

  • 2.3 のリリース準備はすでに「バックエンド×コンポーネント」まで下りてきている：FlagTree はバックエンドごとにリリースを許可し、2.3.0 はバックエンドごとにイメージドキュメントを補い、vLLM 0.32 はベンダーごとに収束させる。この三つはいずれも一度で完了する作業ではない。これはつまり 12-30 まで、ウィークリーレポートの観察単位はバージョン番号ではなく、「あるバックエンドがあるコンポーネント上で既にリリース許可されたか」になるということだ。
  • モデルコンパイルがオペレータ、フレームワークと並ぶ第三の主線になる：FEP-0163 は 20% と 5% という二つの検証可能な指標を示し、Qwen3.8、GLM5.3 Flash と三つのバックエンドを紐付ける。これまでの主線はオペレータの拡充とバックエンド適配であり、今後は「モデル全体のコンパイルが達成できるか」をもう一層見る必要がある。これも 12-07 の切り替え前で最も不確実な項目である。
  • オペレータの生産能力が頭打ちになると、作業の重心は正確性と棚卸しに移る：燧原の 63 件はすべて GCU300 の境界修復、昆仑芯はアトミック化なしの上書きを補い、天数は単一 warp 起動に変更し、FlagGems は不適合オペレータ 7 個を削除し、実験表を 142 から 141 に減らし、テストドリフトの収束に別途 11 件。こうした作業はニュースにはならないが、「ベンダーブランチと主干のどちらが正しいか」を自動判定できるかどうかを決める。
  • バージョン移行のリスクは API からプラットフォーム差異に変わる：昆仑芯の vLLM 0.32.0 は py3.10 でインポートに失敗し、上架から二時間で撤回された。平头哥は「0.32-empty」でシンボルをスタブ化せず直接削除する。同じ上流バージョンでも、各社が自社の Python とドライバスタックに合わせて再計算する必要があり、隠れたコストは二套の検証環境を同時に維持することである。
  • レビュー側は依然として唯一のボトルネック：レビュー中の存量は 252、343、317、272 件で、常に当期のマージ量の半分以上を上回っている。11-12 には一日で 120 件が新規に開かれた。KernelGen はコードを書く側を拡大したが、マージ速度はレビューとハードウェア検証環境に制限される。これが「書くのが少なく、決めるのが多い」日の方がむしろ重要である理由でもある。
  • 配布層は収束しつつあり、差はオペレータ成果物に残る：TransformerEngine-FL は一つの純 Python wheel ですべての非 NVIDIA ベンダーに供給し、FlagTree の deb はバックエンドごとに一パッケージ、rpm は公開済み wheel を直接取得する。しかし平头哥の PPU は FlagGems のリリースマッピングに当該バックエンドが欠けているため依然として cpp ホイールがなく、オペレータ能力はコンパイル経路しか使えない。配布が統一された後、次の差は「どの会社のオペレータにプリコンパイル済み成果物があるか」である。
  • 量子スタックのテンポは他のコンポーネントより明らかに速いが、リリースレベルで解釈すべきではない：一週間で 107 件のコミット、63 件のマージがあり、Hubbard と t-V の二種類の凝縮系モデル、パリティ対称性と 216 個のプログラムのネイティブ実装を同時に進めている。これらの作業の価値はシミュレータを訓練可能・照合可能にすることにあり、製品化にはまだ遠い。2.3 の AI for Science 欄も依然として未定と記されている。
