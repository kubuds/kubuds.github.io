1.2 build-infra：昇騰四輪駆動の 22.04 セルフコンテインド builder への移行、清微と曦望が同日に補完（10-19）

日付：2026-10-19　情報源：PR #1414 · PR #1418 · PR #1422 · PR #1417 · base ディレクトリ

  • 核心問題：昇騰の4つのホイールは元々 24.04 ランタイムイメージ内でビルドされており、生成された libflagcx.so と _C*.so は GLIBC_2.38 にリンクされ、bundle の 22.04 物理マシン上で直接 abort する。PR #1414 は各行ごとに独立した ubuntu:22.04 builder を設定し、他のベンダー行と同一チャネルを通し、glibc の下限を 2.35 に引き下げた。
  • 1つのレシピで4行をサービス：ascend.mk は -ltorch_npu -lascendcl -lhccl のみをリンクし、特定のチップとは無関係である。ただしツールチェーン自体はこれらのリンク時依存を含まず、libhccl.so と <hccl/hccl.h> はチップ ops パッケージに由来するため、レシピは同時に toolkit と ops パッケージをインストールする（nnal/ATB を含まない）。910b と 910c の差異は ops インストーラのチップトークン（builder.ops_product、910b と A3）を介して渡される。
  • 検証基準：SDK の下限は import torch_npu（CANN ツールチェーンライブラリを dlopen する）で証明し、import torch（この行では純粋な CPU）ではない。ASCEND_OPP_PATH、ASCEND_AICPU_PATH、TOOLCHAIN_HOME、LD_LIBRARY_PATH は set_env.sh から /etc/profile.d/vendor.sh に落とし込まれ、ホイールビルド時に source されたものと同一のファイルである。
  • 同日に2つの新バックエンドを补齐：曦望（PR #1418、sunrise wheel の 22.04 自己完結 builder、その後 PR #1420 で当該ホイールを 22.04-clean で再リリースしたことを記録）と清微（PR #1422、tsingmicro wheel の 22.04 自己完結 builder）。これにより base/ ディレクトリ下のベンダーマトリクスは nvidia（cuda12.8 / cuda13.3）、ascend（cann8.5.0 / cann9.0.0、910c を含む）、cambricon（neuware4.4.3 / 4.7.2）、enflame（tops1.9.10 / 1.10.6）、hygon（dtk26.04）、iluvatar（corex4.4.0 / 4.5.0）、metax（maca3.7.2.1 / 3.8.1.3）、sunrise（tangrt1.2.0）、tsingmicro（tsm260610）となり、計9ベンダーとなる。
  • FlagTree 側の3件：PR #1417 は燧原 builder を追加し検証ステップをデータドリブンに変更した。PR #1419 は「ビルド期に燧原バックエンドを断言する」記述を修正した。PR #1421 は燧原 toolkit の deb を builder イメージにプリセットし、ビルドごとのダウンロード依存を削減した。さらに PR #1410 は pybind11 ABI を実際に出力されたプラグインから読み戻すようにし、リテラルをハードコードしないようにした。PR #1413 は失敗した plan がビルドをスキップするのではなく、run 全体を直接失敗させるようにした。
  • 判断：この16件はいずれも機能開発ではなく、すべて「ローカルでビルドでき、ターゲット機で動作する」間の隙間を解消するものである。10-16 から 10-18 の6バックエンド 22.04 収束と合わせて見ると、FlagCX の成果物チャネルは「バックエンドごとにパッチを当てる」から「1行1バックエンド、同一の 22.04 レシピ」へと移行した。

1.3 FlagQuantum：405 ファイルを量子スタック拡張に合入、M0 ロードマップを確立（10-19）

日付：2026-10-19　情報源：PR #635 · PR #637 · PR #642 · リポジトリ

  • 規模：23 件のコミット、9 件のマージ。当日のコミット数で並列1位のリポジトリ。PR #635 は単一で405ファイル、+114463/−3983、新規公開名159件：アルゴリズムパッケージが45から148へ、量子誤り訂正が84から108へ、リモート呼び出しが20から32へ、可観測量が12から20へ、コンパイラが12から17へ、シミュレーションが8から11へ増加し、新たに flagquantum.operators パッケージ（4つのエクスポート）を開設。能力レジストリは68項目から97項目に増加、うち development_evidence は20から47に増加。
  • 境界規律：すべての新規名はサブパッケージの入口であり、Stable Core の flagquantum.__all__ は依然として41のエクスポートで、main とバイト単位で一致。PR 本文は「Stable Core への昇格は独立した提案経路を経る」と明記し、同時に3つの契約ファイル（コンパイラ pass 准入、多段 IR 内部インターフェース、real-time メッセージ）を新規追加。
  • ロードマップ：PR #637 は M0 から M4 までの段階的範囲、依存関係、受け入れ基準を確立し、既存の Core IR、コンパイラ、動力学ソルバー、ランタイム、PyTorch 統合の再利用を要求し、超伝導、中性原子、イオントラップ、光子、トポロジカルの5類のハードウェアをカバー。M1 は混合次元状態空間から着手する。同一 PR はさらに、収縮ガウス重なり積分の精度問題を修正（相殺に敏感な総和を math.fsum で処理するよう変更し、原始基底系列の回帰を1件追加）。
  • 動力学とコンパイラ：PR #639 は混合次元状態空間をサポート、PR #640 は明示的截断のボソンオペレータをサポート、PR #641 は静的オペレータ和の係数訓練をサポート、PR #642 は呼び出し側が名前で2つの最適化ポイントに独自 pass を注入できるようにする。他に10件余りのテストとドキュメントのコミットがあり、数値アサーションを固定リテラル比較ではなく「精度に基づく再現性比較」に変更。
  • 判断：量子スタックは「フレームワークの雛形」から「汎用量子計算フレームワーク」へと進みつつある——PR #635 が補うのはカバレッジ（誤り訂正、化学、リアルタイム呼び出し、超オペレータ）であり、PR #637 が補うのは境界と段階である。両者が同日にマージされたことは、M0 の起点が API を先に拡張することではなく、既存能力を明確に記述することにあることを意味する。

1.5 FlagBLAS：海光 gfx936 六精度 GEMM マージ（10-19）

  • 昇騰：build-infra の base/ 下には ascend-cann8.5.0 と ascend-cann9.0.0 が同時に存在し（各々 910c 変種を含む）、4つの wheel の builder を 22.04 に統一（#1414）。FlagGems 側では mm 形状ディスパッチと Triton tiling 最適化（#7239）、reference 契約の修正（#7286、#7287、#7253）。FlagTree の 3.5 py312 デリバリーワークフロー（#1396、#1398）。vllm-plugin-FL の昇騰フルデコードグラフは依然レビュー中（#606）。
  • 達摩院玄鉄：FlagGems は T-Head バックエンドの GRU barrier デッドロックを修正（#7203）。FlagGems-vllm は sparse QSA の最小タイルを 16 行に引き上げ（#940）。vllm-plugin-FL は玄鉄バックエンドを vLLM 0.28.0 に更新（#574）。3つの線はそれぞれ正確性、性能下限、バージョン追従に対応する。
  • 判断：3社の当日の共通点は「新機能の追加」ではなく「境界の修正」である——MUSA はバックエンド入口を補い、昇騰はデリバリーとテスト契約を補い、玄鉄は並行正確性を補っている。この種の修正は対外的な性能指標には現れないが、マルチチップベースラインを横比較できるかどうかを決定づける。

4. 総括とトレンド観察

  • トレンド1：成果物チャネルの統一が機能拡張に先行。build-infraは1日で16件のコミット、16件のマージを記録し、そのすべてが22.04の自己完結型builderをめぐるものだった。昇騰四輪子、曦望、清微が同じ日に同じレシピへ組み込まれ、base/ディレクトリは9社・17のベースラインイメージのマトリクスを形成した。glibcの下限を2.38から2.35へ引き下げたことは、どの新規オペレータよりも直接的に「ホイールをユーザーのマシンにインストールできるかどうか」を決定づける。この手がかりは10-16から10-18の6バックエンド集約と連なり完全なチェーンを成しており、FlagOS 2.2リリース後初の体系的な補習と見なせる。
  • トレンド2：量子スタックがフレームワークの雛形から汎用フレームワークの境界定義へ移行。FlagQuantumは1日で405ファイル、159の新規公開名をマージし、同時にM0からM4までのロードマップで5類のハードウェアの再利用前提を明確化し、Stable Coreの41のエクスポートを不変に保った。この「サブパッケージを拡張し、コアをロックする」手法は、10-18の量智雲リリース時にFlagQuantumを技術底稿として位置づけたことと一致する——対外的に能力を語る前に、どれが安定インターフェースかをまず明確に書き記すのである。
  • トレンド3：国産計算力側の投入が「オペレータ」から「ベンチマークと基礎ライブラリ」へ移行中。海光はFlagBLASで6精度GEMMとL1サポートを補完し、天数はFlagDNNで等価性能ベースラインを補いmasterへ直送、燧原はFlagTreeでGCU300ベースラインとvLLMベンチマークワークフローを敷設、摩尔線程はFlagGems、FlagTrain、FlagSparseの3ラインを同時に動かしている。共通点は、いずれもベンチマークで直接測定可能であり、単に「某オペレータをサポート」するだけではないことだ。
  • トレンド4：KernelGenは疎とビュー意味論の掃討段階へ。マージ側の_coalesce、ccol_indices_copy、_neg_view_copyと審査中側の十数件の疎オペレータ（_sparse_mm族、coo/csrインデックス相互変換、copy_sparse_to_sparse_）は、稠密幹線がほぼ在庫一掃されたことを示している。同時に昆仑芯は30件の審査中で単一バックエンド最大のキューを構成し、XPU3のアテンション族とRNN族が次批のマージ主体である。
  • トレンド5：ニュース面は会後の消化期に入り、情報の重心はリポジトリへ回帰。24時間枠内の有効ニュースは1件（中華網10-19の技術分解、7つの量子化案例を補足）、コンポーネント名直查は連続ゼロヒット、分科会紀要とワークショップ内容は未成稿。経験則では、こうした枠の後1〜2日で分科会の二次報道が現れることが多く、次期の観察点となりうる。
  • 次期注目：1つはFlagQuantumのfeat/m0-common-foundationブランチ（10-19 16:47作成）がいつPRを出すか、2つはFlagGemsの疎カーネル審査中キューのマージペース、3つはbuild-infraが「1行1バックエンド」レシピをFlagTreeとTorch-FLの成果物ラインへ複製するか、4つは大会分科会紀要が公開されるかである。
