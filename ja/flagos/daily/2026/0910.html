1. オープンソースプロジェクトの進展（GitHub 動向）

調査期間総覧：org 内の 52 リポジトリのうち 18 が期間内にプッシュあり；commit search で 期間内コミット 135 件がヒット（5 ページ）、14 リポジトリに分布（FlagGems-Experimental 60、FlagGems 39、build-infra 9、FlagBLAS 8、FlagTree 4、FlagCX 2、FlagGems-sglang 2、vllm-plugin-FL 2、FlagSparse 2、FlagOS-Robo 2、FlagAttention 2、libtriton_jit 1、FlagScale 1、FlagGems-vllm 1）；他に 4 リポジトリ（sglang-plugin-FL、docs、FlagTree-AscendNPU-IR、release-info）の期間内プッシュは、デフォルトブランチとブランチ API の再確認により PR ブランチのアクションと判明。新規リポジトリなし、新規コンポーネントリリースなし。

本期間の形態 = RC1 テスト安定期の「エンジニアリング基盤 + オペレータマトリクス」二系統：デリバリ側の最大の動きは build-infra（昇騰 910C 新バックエンド + 60 個の app イメージ changelog ベースラインとゲート）に集中し、コード側はオペレータ自動生成パイプラインの高流速を継続（メインリポジトリ 39 件 + 実験リポジトリ 60 件）、ドメインライブラリとツールチェーンには FlagBLAS Ascend L3 三連続、FlagTree TLE マルチカード通信など実質的な能力拡張が出現。

1.1 build-infra：昇騰 910C base/runtime バックエンドの二系統を新規追加、60 個の app イメージ changelog ベースラインを策定（09-09/09-10）

出典：build-infra #803（09-09 20:27）、#801（09-09 13:42）、#802（09-09 20:22）、#807（09-10 09:38）、#799/#800（09-09 10:42/10:43）、#804、#805、#806

  • 昇騰 910C バックエンド新規追加（#803）：ascend-cann8.5.0-910c / ascend-cann9.0.0-910c のデュアルバックエンドを新規追加し、同一 CANN ラインから昇騰 910C チップへビルド可能とした。910C のチップ専用 ops パッケージは A3 token（Ascend-cann-A3-ops）を使用し、2 つの base Containerfile は 910B の兄弟版とバイトレベルで一致し、PRODUCT ARG のデフォルト値（910b→A3）とファイルヘッダのみが異なる。本調査期間で初めて昇騰チップマトリクスを 910B から 910C へ拡張した。
  • 範囲を意図的に限定：追加された configs.yaml ブロックは deps_app と env.app.* を意図的に省略し、910C バックエンドを当面 app ビルドマトリクスに組み込まないようにした（deps_app の有無が app 組み込みのゲートとなる）。app 成果物が産出・検証された後に開放する——「まず base/runtime を立て、その後 app に入る」という堅実な組み込み順序を踏襲。
  • ついでにベンダー解析を修正：3 つの verify スクリプトのベンダー分割を、末尾ハイフン（${VAR%-*}）から先頭ハイフン（${VAR%%-*}）へ変更し、generate_matrix.py / verify_base.py と整合させた。旧ロジックでは ascend-cann9.0.0-910c のような二重ハイフンキーで、run.vendors に存在しないベンダー名が解析され、run flags が空になっていた。関連：#804（910B runner overrides で 910b label を強制）、#806（910C base ビルドを runner proxy build-args 経由に）。
  • 60 個の app イメージ changelog ベースライン（#801）：app/<app>/changelogs/ 配下に、flagos-app がリリース済みの全 60 個の app イメージの YAML ベースラインを構築し、イメージごとに現在 registry に存在する tag とそのビルド履歴（新→旧）を記録。各エントリには再ビルド理由、push_time の日付、取り込まれた上流 PR を含む。registry にもはや存在しない旧 tag は後継エントリの history に折り込まれる（それが唯一の痕跡となる）。関連：#802（registry push_time で日付をバックフィル）、#807（push 時に changelog を強制ゲート）。デリバリーのトレーサビリティを「イメージ tag 記録」から「イメージ単位の変更史」へアップグレード。
  • 摩尔線程 Megatron アプリケーションイメージのデュアルライン登録（#799/#800）：mthreads-musa4.3.6 と mthreads-musa5.2.0 の 2 ラインについて app image tag 2.1.2-0.3.0_rc0.post1_3.g6e8d7ffc7 を記録。また #805 で外部 GitHub Actions を完全な commit SHA に固定（サプライチェーン強化）。

解読：昇騰 910C の接続方式は注目に値する——それは新たな技術ルートを開設したのではなく、910C を「910B ラインのチップ同構変体」として扱っている：Containerfile はバイトレベルで再利用し、ops パッケージの token のみを差し替え、さらに deps_app の欠位によって新チップを app マトリクスの外に締め出している。これは RC テスト期における「新対応は進めても、新特性は入れない」という規律がマルチチップエンジニアリング上に具体的に投影されたものである：新ハードウェアは骨組みだけを立て、既存の納品面を攪乱しない。60 個の app イメージ changelog ベースライン + push ゲーティングの組み合わせは、build-infra を「何が起きたかを記録する」段階から「なぜそうなったかの説明を強制する」段階へと押し進めるものであり、2.2 GA 前の監査面が引き締められるシグナルである。

1.2 FlagGems 主リポジトリ：KernelGen オペレータフローは高流速を維持、KMCompiler はマルチバックエンドをさらに拡張（09-09/09-10）

情報源：FlagGems #5957（QC/PPU W8A16 RMSNorm、09-09 10:29）、#5871（GLU TLE 自動チューニング、09-09 10:43）、#6094（KMCompiler Iluvatar gru、09-09 12:15）、#5960（KMCompiler Ascend/Metax linalg_matrix_power、09-09 12:16）、#6119（CI/CD rule-check-required、09-09 15:41）、#6090（metax-maca3720 の削除）

  • メインリポジトリの単一ウィンドウで39件のコミットがあり、直近で最も密集したウィンドウとなった。数量の主体は[KernelGen][Nvidia] 系オペレータの格納（約25件）で、hardtanh（opsへ移動）、cummax_helper、_nested_from_padded_tensor、_nested_tensor_from_mask_left_aligned、_nested_view_from_jagged、conv_tbc_backward、conv_transpose3d、matrix_exp_backward、max_pool1d、sum_to_size、embedding_renorm、cosine_embedding_loss、cov、corrcoef、cumulative_trapezoid、fft_irfftn、special_xlogy、_sparse_semi_structured_addmm、fake_quantize 系と nuclear_norm をカバー；09-10 09:03～09:52 も継続的にコミットが続いており（corrcoef/cov/cumulative_trapezoid の3件が同一分にマージされた）。
  • KMCompilerの生成パスがさらにベンダーを拡大：Iluvatar gru（Triton kernel、#6094）、Ascend + Metax が同一バッチで linalg_matrix_power（#5960）。前ウィンドウで linalg_matrix_exp が一度に7バックエンドを生成したことが記録されたばかりだが、本ウィンドウでも linalg 行列関数ファミリーが「一度の開発でマルチバックエンドに展開」する方式で引き続き補完されている。
  • 量子化オペレータがさらに達摩院玄鉄 PPU へ延伸：QC PPU W8A16 RMSNorm（#5957）；性能側では GLU kernel が TLE 自動チューニングに変更（#5871）。
  • エンジニアリング面 5件：CI が three-dot diff で PR 変更ファイルを導出するよう変更（#6097）；rule-check-required job と CICD ドキュメントを追加（#6119）；unittest workflow に並行制御を追加し、09-10 に式の構文を2回修正（#6137 など）；metax-maca3720 の CI エントリを削除（#6090、ベンダー CI ラインの調整）；[Fix] で MM テストと benchmark が FlagTune 環境設定を尊重するようにし（#6129）、all/any のゼロ除算、nextafter の NaN 伝播、2件の benchmark 構造化 JSON 出力を修正。

解釈：KernelGen の産出速度は前ウィンドウの12件/半日から本ウィンドウの約25件/半日へと回升しており、「AI によるオペレータ自動生成」がもはやバッチイベントではなく常態化したパイプラインであることを示している——これは 1.3 実験リポジトリの60件のマージ量と相互に裏付けられている。本ウィンドウの操作面の分布も現在のエンジニアリング重心を示している：2.2 凍結期中において、新規能力はすべて「ジェネレータによるオペレータ補完 + ベンダーバックエンド専用化」で対応し、手書きのアーキテクチャレベル変更はゼロ；CI 側はむしろ制約を強めており（three-dot diff、rule-check-required、並行制御）、GA 前にデリバリー規律を引き締める典型的な動きである。

1.3 FlagGems-Experimental：海光専用 flash attention オペレータが格納、Iluvatar/MThreads の二ラインでバッチ処理（09-09/09-10）

情報源：FlagGems-Experimental #597（Hygon _flash_attention_forward、09-10 08:44）、#598（Hygon adaptive_avg_pool2d_backward、09-09 17:28）、#604（MThreads var、09-10 09:11）

  • 実験リポジトリの単一ウィンドウ 60 件のウィンドウ内コミット、バックエンド別：Iluvatar 約 36 件（special 関数群、プーリング逆伝播、linalg_svdvals、histc、median、mvlgamma、matmuladd 等）、MThreads 約 16 件、Ascend 3 件（special_erfinv、unsafe_masked_index、zero）、Hygon 2 件。
  • 海光専用 flash attention がリポジトリに登録（#597）：Hygon DCU バックエンド向けに _flash_attention_forward 専用実装を新規追加、ファイルは src/flag_gems/runtime/backend/_hygon/ops/ に配置され、BAAI 側の開発者がコミット。これまでこのバックエンドは実験リポジトリに _amp_foreach_non_finite_check_and_unscale_ などの軽量オペレータしかなく、専用アテンションオペレータは初となる。
  • もう 1 件の Hygon オペレータは adaptive_avg_pool2d_backward（#598）。両件とも同日/翌日にデフォルトブランチへマージ。
  • エンジニアリング面：実験リポジトリで unittest workflow の並行設定を同時に追加（09-09 13:39、19:54 の 2 回改訂）。

解読：海光の 2 件はオペレータ数よりもその内容に情報量がある——_flash_attention_forward はアテンションパス上の核心オペレータであり、09-08 にメインリポジトリで Hygon バックエンド flash attention の BLOCK_M ブロック取得欠陥を修正したばかりで、本ウィンドウで専用実装が登録され、「まず汎用パスを修正し、次に専用実装を投入する」というリレーを構成している。Iluvatar（天数智芯）は単一ウィンドウ 36 件で引き続き実験リポジトリ最大の生産能力の源泉であり、メインリポジトリ KMCompiler の Iluvatar gru と合わせて「実験リポジトリでバッチ検証 → メインリポジトリ KMCompiler で生成/リリース」という分業の閉ループを形成している。

1.4 推論プラグイン層：達摩院玄鉄 PPU fused persistent_topk、Arm CPU Qwen W4A8/GDN、sglang オペレータ設定（09-09）

情報源：FlagGems-vllm #754（09-09 19:58）、vllm-plugin-FL #433（09-09 15:35）、#474（09-09 17:40）、FlagGems-sglang #60（09-09 18:56）

  • 達摩院玄鉄 PPU fused persistent_topk（FlagGems-vllm #754）：runtime/backend/_thead/fused/ 配下に persistent_topk.py（2394 行）を新規追加・登録、T-Head PPU-ZW810E 向け；KMCompiler により生成。前ウィンドウ（09-08）でこのオペレータのテスト/benchmark が vLLM native op から切り離して自己テスト可能に変更されたばかり（#747）で、本ウィンドウで正式な実装と登録が実現した。
  • Arm CPU 側 Qwen 量子化推論（vllm-plugin-FL #433）：CPU 上で Qwen の packed W4A8 と GDN（Gated Delta Net）パスを統合、プラグイン層の Arm CPU 推論シナリオへの拡張。
  • KV キャッシュ一貫性の修正（#474）：#382 由来の FlagGems KV cache 更新を復元（attention パスの回帰修正）。
  • sglang プラグインオペレータ設定（FlagGems-sglang #60）：operators 設定ファイルを新規追加し、sglang プラグイン側のオペレータ有効化集合を設定可能に。

解読：4 件は同じことを指し示している——プラグイン層は「マルチフレームワーク × マルチチップ × マルチデプロイ形態」のために設定面と専用オペレータを整備しつつある。玄鉄 PPU の persistent_topk は「自己テスト可能」から「登録済み」への 2 ステップを完了した；Arm CPU の W4A8/GDN はプラグイン層の作用範囲をアクセラレータカードから CPU 推論スタックへと拡張した；sglang のオペレータ設定化はチップ別にオペレータ集合を取捨選択するコストを低減する。3 件を合わせると、推論プラグイン層が「kernel ごとのベンダー化 + 設定面のガバナンス」という成熟期のエンジニアリング段階に入ったことを示している。

1.5 領域ライブラリとツールチェーン：FlagBLAS Ascend L3 三連合流、FlagTree TLE マルチカード通信、FlagCX CICD 全カバレッジ（09-09）

情報源：FlagBLAS #102/#104/#105（09-09 11:22/14:35/15:03）、FlagTree #1048（09-09 16:56）、#1123、#1099（09-09 22:25）、FlagCX #573/#575（09-10 01:28/09:35）

  • FlagBLAS Ascend L3 三連：同日に TBMV（#102）→ TBSV（#104）→ TPSV（#105） の三個の固有値/三角行列演算の昇騰サポートを順次合流し、冗長なオペレータエクスポートリストを整理（#103）。09-07 の Ascend L2 ルーチン一括合流を受けて、本調査期間では BLAS ルーチン行列を引き続き L3 へ押し上げる。
  • FlagTree 四件：TLE 分散プリミティブ distributed_barrier にマルチ GPU 通信サポートを追加（#1048）。CI に hcu qwen benchmark を追加（#1123）。XPU 側では xpu-sdnn-objects を v0.3.6.6.1 に引き上げ、int8 dot の失敗を修正（#1099）。[FlagTune] は CUDA graph ベンチマークで caller-stream の呼び出し順序を維持（#1129）。
  • FlagCX CICD 二件：CICD のカバレッジをすべての cooperative modes とすべての team/operation の組み合わせに拡大（#573/#575）。すなわち通信ライブラリの協調モードの組み合わせに対して網羅的テストカバレッジを実施する。

解読：三つのラインは性質が異なるが方向性は一致している——テスト期において「カバレッジ」を主要な着眼点としている。FlagBLAS は L3 ルーチンで昇騰の BLAS 能力面を補完し、FlagCX は組み合わせ網羅で CICD カバレッジを限界まで押し上げ（マルチカード通信の正確性は 2.2 マルチチップマトリックステストの調査期間における重要なリスク項目である）、FlagTree は TLE のマルチカードプリミティブを「利用可能」から「マルチカード通信利用可能」へと押し上げている。hcu qwen benchmark が CI に入ったことは、昇騰（hcu）側のエンドツーエンドモデルベンチマークが定例検証に組み込まれたことを示している。

  4. 会員単位の商業化とエコシステムの 2 線が同時に推進：京東雲は摩尔線程 GPU を基盤として十万カードのフル機能 GPU クラスタを構築すると発表（国産 GPU が初めて大手クラウドベンダーの中核クラスタに入り、かつ具身知能を明確に含む）。燧原科技は 9 月 11 日に科創板へ上場（調達予定額 60 億元を第五世代・第六世代チップに投入）。海光はトークン運用「双芯」加速ソリューションを発表し、北京の「詞元工場」政策表現と同頻である。ソフトウェア側と商業側の推進リズムは本調査期間において明らかに合致している。

予測：今後の観察面は 3 点。第一に、昇騰 910C がいつ deps_app を補完して app ビルドマトリクスに入るか（この動作は 910C デリバリー可用性の標識となる）。第二に、2.2 GA（09-24 テスト窓口締切）前後の release-info/community リスト動作、および FlagGems v5.4.0 rc シリーズが正式版へ進むかどうか（現在の最新タグは依然として v5.4.0-rc1.post1）。第三に、北京市計画落地後のコミュニティ側の付随動作（「国産先進計算反復検証プラットフォーム」と FlagOS 検証マトリクスの接続方式、RISC-V バックエンドの重みが上昇するかどうか）。
