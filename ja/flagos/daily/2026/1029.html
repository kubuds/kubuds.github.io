  • 接続方式：BPU の実行単位は hbdk4 が生成する .hbm 成果物であり、hbdk4 は x86 上でしか動作しない。ボード上ではコンパイルもできず、リポジトリに同梱された成果物もない。これまでの結論は「設計上 eager は不可」だったが、今回これを三層に分解した。ボード外で単一オペレータの .hbm ライブラリをコンパイルし、これらの成果物を投入する C++ カーネルを生成し、drobotics conf のルーティングを追加する、というものである。
  • カバレッジと検証：40 個の要素単位オペレータ、11 個の形状バケットについて、RDK S600 上で 440 個の成果物すべてが NumPy との比較でゼロ差分となり、flagos テンソル上の aten 呼び出しが実際に BPU に到達することを確認した。著者は同時に二つの否定的結論も記録している。libhbtl.so は CPU リファレンス実装に過ぎず（ldd では libc/libstdc++/libm のみが見え、hbtl::ucp::Add の cpu/wall は 1.00）、動的形状は HBRT 4.7.5 上では実行不可能である（ローダが当該軸を stride 0 と宣言し、タスク検証が 64 以上を要求するため）。
  • 収尾の三件：#676 は kDrobotics に dispatcher.h の二箇所の switch を補完した。これまで BPU ビルドのディスパッチログ名は一律 unknown と表示され、KernelSetOf は BPU 自身のカーネルライブラリを無所属と報告していた。#678 は三箇所の copy 分岐が無条件に CUDA へ box される問題を修正した。デフォルトの FlagGems が主導する NVIDIA と達摩院玄鉄 PPU wheel は意図的に CPU のみの pip torch にリンクしており、CUDA コピーカーネルの DispatchStub は空で、初回呼び出しで missing kernel for cuda となる。#673 はビルド記録におけるベンダー名とプラットフォーム id の不一致（hygon/dcu、mthreads/musa、enflame/gcu、nvidia/cuda）を修正した。これは海光 DCU レーンの八件の単体テスト失敗の根本原因である。
  • 審査中：#672 は soft-lowp 行列オペレータの claim 粒度を統一し（conf キー単位で宣言、ファミリ単位でデコード）、#677 はキーワード引数の FlagGems 呼び出しをアクティブバックエンド経由にし、#680 はビルド記録が保持するベンダーに基づいてデバイスエイリアスを再定義し、#681 はインターフェース対象ではなく torch プレフィックスから libtorch_cuda プローブを読み取る。
  • 判断：これは本調査期間で唯一の「新プラットフォームが利用不可から利用可能になった」接続であり、価値はパフォーマンスではなく経路の打通にある。40 個の要素単位オペレータは起点であり、畳み込みなどの基幹オペレータは依然として torch.compile の全体グラフ経路に依存している。

3.2 崑崙芯：スカラーチェーン融合と連続セグメントカーネル、P800 上の三箇所の高速化（10-28）

日付：2026-10-28　情報源：FlagGems PR #7617 · PR #7600 · PR #7850 · PR #7803 · FlagCX PR #682

  • スカラーチェーン：8つの出位スカラーチェーンオペレータの融合カーネルにより、相対所要時間が0.08〜0.13から0.81〜0.93に向上（#7617）。収益の主な源はホスト側にある。出力の一括割り当てとunbindにより、テンソルごとのアロケータ呼び出しを置き換える。小形状の単一発射では、すべてのポインタをパラメータとして渡す。
  • 連続セグメント：batch-norm推論とQKV変換を連続セグメントカーネルに変更後、集約指標は0.228→1.357および0.260→5.062（#7600）。元の実装は(n,c)スライスまたは2次元タイルで編成され、読み書きが不連続であった。新しい実装では各プログラムが連続要素のセグメントをカバーし、フラットインデックスからチャネルまたはパッキング行を逆算する。
  • マスク填充：masked_fillはP800上で0.577から0.829に向上（#7850）。手法は、整数マスクの符号拡張をsitofp後の0/1浮動小数点乗算に変更し、カーネル全体をベクトル化可能にすることである。精度面ではmがちょうど0/1であり、結果はビット単位で一致する。
  • 保守性：#7803は、現在のmaster上で昆仑芯バックエンドがインポートできない問題（共有エグゼキュータが_result_dtypeヘルパーを削除した）を修正し、さらに共有エグゼキュータのuni_sram上の支配関係コンパイルエラーを修正した。修正しない場合、いかなる昆仑芯テストも起動できない。
  • 通信側：FlagCXの昆仑芯プラットフォームtraitsはcstddefを__xpu__ガードの外に移動した（#682）。以前はcomm_traits.hからの解析時にsize_tがまだ可視でなく、公共デバイスAPIのホスト側コンパイルが直接失敗していた。

3.3 天数：畳み込みは工况档位表を採用、conv3dはチャネルゼロ埋めを除去（10-28）

日付：2026-10-28　情報源：FlagGems PR #7036 · FlagGems PR #7061

  • conv_transpose2d：汎用実装の単一デフォルトスケジューリング(64,32,32,4)に3x3/stride2の特例を加えたものを、データ型・カーネルサイズ・ストライド・出力チャネル数でインデックスされる7套のハードウェアチューニング档位（BLOCK_NHW/CI/CO、num_warps、num_stages）に置き換え、出力がL2に収まるかどうかで2つのカーネル変体を切り替える——直掃変体はL2内でより高速、位相専用変体は出力がL2を超えた後により安定（#7036、1886行追加）。
  • conv3d：天数側のBLOCK_CIはすでに16以上であり、FlagTreeのAABSも縮小されたタイルを16x16x16の下限に引き戻す。したがって汎用パスがweight_cを16にゼロ埋めするのは、毎回の呼び出しでの割り当てとコピーのオーバーヘッドに過ぎず、除去後も出力はビット単位で一致する。さらにBLOCK_NI_DO_HO_WOを32と64の2档の小空間タイルとして補い、小体積形状でもデバイスを満たせるようにした（#7061）。
  • 判断：両方ともロングテールチューニングに属し、方向は一致している——「汎用的だが遅い」パスをローカライズされたスケジューリングに置き換え、同時にゼロ埋めのような無収益オーバーヘッドを削除する。

4. まとめとトレンド観察

  • 新たな経路を開通：地平線 BPU は「設計上 eager 不可」から、オペレータごとに実行可能な PrivateUse1 バックエンドへと変貌（40 の要素単位オペレータ、440 の成果物で差異ゼロ）。併せてディスパッチログの命名と CUDA コピーカーネルのガードを修正。これは当調査期間で最も構造的に意味のある接続だが、要素単位オペレータのみをカバーし、主干は依然としてグラフ全体コンパイルに依存している。
  • 通信層がタグと配布パッケージ段階へ：FlagCX が v0.14.1 を打ち出し（アダプタごとにデバイスビットコードを生成）、rpm ラインは 3 バックエンドから 6 バックエンドへ拡大、wheel リリースも build-infra で記帳される。なお、このタグには Release 本文がなく、v0.14.0 のやり方と一致していない点に注意が必要。
  • リリースエンジニアリングが補習中：changelog のサイト掲載と Harbor、未プッシュの寒武紀 megatron イメージ 2 件の撤回、アプリケーションページの一貫性チェックを pre-commit と CI へ、AMD 7.2.4 に 22.04 ビルダーを追加。これらは新能力を生まないが、2.3 のリリース一覧が自己証明できるかどうかを直接左右する。
  • 審査中の構造変化：審査中は 401 から 288 へ、新規オープンは 269 から 101 へ減少。前号の FlagGems-Experimental の 135 件の一括コミットは合入も新規追加もなし。現在の審査中主体は FlagGems の 181 件で、うち新規オープン 53 件の多くが燧原参考実装の修正——マルチバックエンド検収のボトルネックが参考実装とテスト基準にあり、オペレータ供給ではないことを示す。
  • マルチブランチは基準の区別が必要：FlagGems は master と kernelgen-dev の両方で合入（#7905、#7934）、FlagTree の合入は triton_v3.5.x と feature/flagmega ブランチに分散、FlagGems-Experimental のデフォルトブランチは infra-ci。デフォルトブランチで集計すると実作業量を過小評価し、コミット検索では原子補核のリポジトリを取りこぼす。
  • 要観察の 3 点：第一に、v0.14.1 の後に Release 説明が補われ 2.3 一覧に入るか。第二に、BPU 経路が要素単位オペレータから畳み込みなど主干オペレータへ拡大するか。第三に、Megatron-MUSA-Titan のコードが調査期間後に本当にプッシュ開始されるか、そして Megatron-LM-FL との再利用が形成されるか。
