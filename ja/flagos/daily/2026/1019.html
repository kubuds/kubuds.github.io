1.2 新規リポジトリ FlagCV：OpenCV インターフェースに合わせたマルチバックエンド画像オペレータライブラリの骨組みがマージ（10-18 ~ 10-19）

日付：2026-10-18 ~ 2026-10-19　情報源：FlagCV · PR #1 · コミット履歴

  • 事実：10-14 に建倉された FlagCV は 10-18 23:14 に最初のコミット「Add project skeleton and bitwise_and operator」を落とし、10-19 01:24 に「Restructure as an immediate-mode skeleton without operators」を追加、10-19 01:38 に PR #1（作者 zhangjieBaai）をマージした。PR 説明には三つの設計方針が明記されている：インターフェースは OpenCV に整合（include/flagcv/ 下の core / imgproc / gpumat / handle / types の五つのヘッダファイルで、opencv2 の core と imgproc に対応）、マルチバックエンド構造は FlagDNN を踏襲、カーネルは Triton で記述；本 PR は骨格のみで、オペレータは含まない。
  • 構造：リポジトリの 81 パスのうち、backends/ は既に nvidia / thead / ascend / hygon / iluvatar / mthreads の六バックエンドを一気に展開済み（各々 CMakeLists、backend.cpp、compiler.py と kernels/registry.json を含む）；src/ は core、imgproc、image、lowering、runtime の五ブロックに分かれる；compiler/flagcv_codegen はコード生成の入口；docs/ には architecture、numerical-tolerance、operator-development の三篇が既にある。
  • 判断：これは FlagOS のオペレータ版図が初めて「大規模モデル / 科学計算」から画像処理へと伸びたことを意味する——従来 FlagCV 類のギャップは FlagDNN（深層学習オペレータ）と各ベンダー自家の CV ライブラリが分担していたが、現在は OpenCV 互換インターフェースで独立にリポジトリを立てている。六バックエンドのディレクトリを一つずつ追加するのではなく一気に展開したことは、チームが既存の FlagDNN のマルチバックエンドパラダイムをそのまま再利用する意図を示す；numerical-tolerance ドキュメントがオペレータより先に出現したことも、FlagOS が KernelGen ラインで「まず受け入れ基準を定め、その後オペレータをバッチで落とす」という既存のリズムに合致する。リスクは、画像処理オペレータ（補間、色空間、モルフォロジー）と Triton の表現能力のマッチングが未検証であり、かつリポジトリにはまだ実行可能なオペレータがないため、短期的にそのカバレッジについて結論を下すべきではないことだ。

  • FlagTree ライン：builder は「2つのワークフローで1つのことをする」構成から1つのマトリクスへ統合され、backends.yaml の1行が Containerfile、イメージリポジトリ、runner ラベル、ディスク予算、受け入れアサーションを運ぶ（#1369）。日次 wheel も同様にバックエンドごとに1行とし、plan が行ごとにバージョンとファイル名を計算する（#1371）。metax は日次ラインへ（#1377）、iluvatar はターゲットと日次行へ（#1390 / #1393）、sunrise は builder と wheel を単一ファイルにまとめて日次行を有効化（#1399 / #1402）、ascend の一対のバックエンドは2段階 builder へ（#1404 / #1405、ビルド環境がすなわちデリバリ環境であり、CANN を読み、それに基づいて AscendNPU-IR を pin する）。#1397 は FlagCX を iluvatar の FlagTree wheel から明確に除外し、2つの成果物の境界を画定する。
  • パッケージングライン：wheel アップロードは runner ローカルの python から uploader イメージ内での実行へ変更（#1381 / #1382 / #1388）。リリース系ワークフローは pull/<N> を ref として受け付け（#1347）、PR ブランチでリリース経路を先に一巡できるようにする。FlagGems-sglang は noarch deb/rpm と flaglibs wheel の2ラインへ（#1387）。bundle の深層スモークテストは実機 device + コンパイラ JIT/実行へ変更（#1365）、さらに bundle の glibc 下限（22.04）上で検証を実行（#1376）。
  • 判断：この一連は散発的な修补ではなく、「N 個のバックエンド × M 種類の成果物」を「1枚のマトリクス + 1つの backends.yaml」へ圧縮するものだ——新規バックエンドの追加は「ワークフローをもう1本書く」から「1行加える」へ変わる。22.04 への統一は同じ論理の裏面である：ビルド環境とデリバリ環境の glibc 下限を固定して初めて、クロスディストリビューションの wheel は「1つの成果物を複数箇所でインストール可能」と言える。これはまさにメインフォーラムの言う「35 種のチップ」に対応する——チップ数は再現可能なデリバリ面で支えられなければ、規模は単なる名簿にすぎない。

  • 事実：#1381（作者 alex-spacemit）が SpaceMiT RISC-V（K3）バックエンドを更新し、三つのことを同時に行った——smt_rvisa を新規追加。これはベアカーネル（raw-kernel）eDSLであり、作者が SEW / VL / ブロッキング / 命令選択を明示的に指定し、スケジューラに決定を委ねない；カーネルは C++ builder API 経由で降下し（MLIR テキストを生成しない）、別途 LLVM 直出路線があり、MLIR Python bindings を用いて直接 llvm.func を生成し spine-opt を丸ごとスキップする；バックエンドは私有 TLE 方言のコピーを保有せず、汎用の third_party/tle を消費するよう変更；同時にベア経路が露呈したポインタ / メモリ空間降下の欠陥を修正した。

4. まとめとトレンド観察

  • ナラティブとエンジニアリングが初めて同調：メインフォーラムでは2.2を「規模化共有最適化」（21社35チップ、1454オペレータ、+27.6%、264貢献者）として語ったが、同じ期間のGitHub側で最も重い一手はちょうどbuild-infraの6バックエンド22.04 builderとバックエンド別日次ホイールマトリクスだった——両者が答えるのは同じ問いである。チップ名簿は再現可能なデリバリー面で支えられなければならない。これは本期で最も記録に値する対応関係だ。
  • オペレータ領域は拡大しているが、拡大の方向は見極める必要がある：KernelGenは3日間で30余りのNVIDIAオペレータを落としたが、その多くは_dim_arange、values_copy、_has_same_storage_numelといった境界オペレータであり、幹のカバレッジがほぼ完了し、別名とビュー意味論の仕上げに入ったことを示す。一方、国産バックエンドの増分は依然として昆仑芯（20余筆の最適化）と達摩院玄鉄（GEMM補完）に集中しており、バックエンド間のカバレッジ格差は縮まっていない。FlagCVのリポジトリ立ち上げはもう一つの方向の拡大だ——LLMと科学計算からOpenCV式画像処理へと進み、6バックエンドのディレクトリを一気に展開したが、リポジトリにはまだ実行可能なオペレータがなく、短期的に過大評価すべきではない。
  • 量子ラインに製品形態が出現：FlagQuantum 0.3.0 / 0.3.1の双発 + 量智雲の対外発表により、「九鼎 / QUAFU タスク回復可能」といったエンジニアリング能力をリリースノートに書き込み、同時にハードウェア上では実行せず、agent runtimeを含まないことを明記した。分業は「FlagOSが実行スタックとスケジューリング、量子院がハードウェアとクラウド」であり、これは曖昧な「量智融合」スローガンよりも境界をよく説明している。
  • RISC-V側の動きはコンパイラの深部にある：SpaceMiTのsmt_rvisaは作者にSEW / VL / 命令選択を明示的に制御させ、私有TLEコピーを退役させた——こうした変更はどの対外口径にも現れないが、RVVバックエンドが「動く」から「性能を押さえ込む」へ進めるかを決める。
  • 要観察：1つ目は、大会分科会とワークショップの逐次議事録がまだ公開されておらず、メインフォーラム以外の技戦術的内容（統一IR、Token工場、端側デプロイ）は現時点で議題口径のみであること。2つ目は、量智雲がいつ対外開放されるか。3つ目は、FlagCVがいつ最初の実行可能オペレータを落とすか。4つ目は、訓練側（Megatron-LM-FL / TransformerEngine-FL / FlagScale）が3日間ゼロプッシュであり、大会前後の正常な静寂なのか2.3周期の起点なのかは、次期で確認する必要がある。
