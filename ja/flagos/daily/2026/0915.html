今日の重点：FlagOS 2.2 RC2 全スタック同時タグ付け——25 項目の一覧が版を切り替え、25 個の rc2.post1 tag が 10 分以内に着地

日付：2026-09-14　出典：community コミット #109（2.2 RC2 マニフェスト）、2.2 リリーススケジュール、FlagGems v5.4.0-rc2.post1

本調査期間で最も重要な出来事は、ある協調的な動きだった。09-14 10:35、community リポジトリに release/2.2/release-2.2-rc2.yaml がマージされ（251 行追加、Release Manager によるコミット）、2.2 サイクルの第 2 回候補版 RC2 マニフェストの形成が宣言された。続いて 10:45 から 10:54 までの 10 分間に、org 内の 23 のコンポーネントリポジトリが相次いで v{X}-rc2.post1 タグまたは Release を打ち、12:18 から 12:19 にかけて FlagTree の 3 つの Triton バリアントのタグが補完され、19:59 には FlagTree がさらに xpu3.6 タグを 1 つ追加した。これに vllm-plugin-FL のデュアルバージョンラインを加えると、調査期間内には合計 26 回のタグ付け動作が記録され、22 のリポジトリをカバーしている。

RC2 マニフェストは 4 層で構成される。L0 インフラ層（FlagTree の triton3.6/3.5/3.3 の 3 条目、FlagCX）、L1 計算ライブラリ層（FlagGems、FlagFFT、FlagSparse、FlagDNN、FlagBLAS、FlagTensor、FlagAudio、FlagAttention、FlagGems-vllm、FlagGems-sglang）、L2 フレームワーク層（Torch-FL、vllm-plugin-FL と vllm-plugin-fl-0.2、sglang-plugin-FL、TransformerEngine-FL、Megatron-LM-FL、FlagOS-Compressor）、L3 アプリケーション層（FlagScale、KernelGen、KernelGenBench、FlagRelease）。合計 25 条目で、すべて rc2.post1 の検証済みスナップショットを指している。

RC1 と比較すると、今回の変化の性質は「構造は不変、スナップショットの世代交代」である。モジュールのバージョン番号は rc0/rc1 と一致したままで、.postN のイテレーション位置のみが進んでいる——FlagGems は v5.4.0-rc1.post2 から v5.4.0-rc2.post1 へ、FlagCX は v0.14.0-rc1.post2 から v0.14.0-rc2.post1 へ、FlagAttention は v0.4.0 ラインに固定、FlagTree は 0.7.0rc1.post1 から 0.7.0rc2.post1 へ。マニフェストの先頭ではワークフローが実行可能なルールとして記述されている。各モジュールのベースラインブランチから rc2 統合ブランチを分岐させ、検証通過後に増分タグ（rc2.post1 → rc2.post2）を打ち、前回のタグを条目コメントの rc1 欄に記録する。ブランチ: と ベースラインブランチ: の 2 つのフィールドは manage-release.py が直接読み込むため、同一リポジトリを複数条目に分割しそれぞれ異なる上流ラインを追う場合（FlagTree、vllm-plugin-FL）、およびデフォルトブランチではなくリリースブランチから分岐させる必要がある場合（flagos-compressor）には、明示的に記載しなければならない。

スケジュールに戻して見ると、今回のタグ付けは「テスト・安定化期間（09-01 ~ 09-24）」の中盤に発生し、09-28 の 2.2 GA まで残り 14 日である。RC2 の意義は新機能の追加にはない——機能凍結はすでに 08-31 に閉じられている——むしろ、テスト期間中に蓄積された修正を、再現可能で一括取得可能なロック済みバージョンの一群として固め、マルチチップ受け入れマトリクスに統一された比較ベースラインを与えることにある。

3.8 智源（牽頭側）：RC2 ガバナンス規律と Open3D-PIMC のルール定義権の表述（09-14）

日付：2026-09-14　出典：community 2.2 リリーススケジュール

主導側は本調査期間にリポジトリ操作を一度しか行っていないが、それはリリースチェーン全体を統制するものだった。09:35 の RC2 リストのコミット後、10 分以内に 23 のコンポーネントが一斉にタグ付けされた。リスト、スケジュール、コミット説明を併読すると、このガバナンスのいくつかの明確な制約が見えてくる——機能凍結（08-31）とリリース（09-28）の間のテスト期間はバグ修正と受け入れテストのみを受け付け、GA は「FEP の Test Plan がマルチチップマトリクス上で受け入れ合格すること」を卒業基準とし、バージョン反復は .postN のインクリメントで行いモジュールのバージョン番号は変更しない。対外的な表現について、新華網の報道は Open3D-PIMC の意義を「ルールの能動的定義」に置いている。すなわち、次世代ハードウェア向けのプログラミングモデルとオープンソースエコシステムを先に構築した者が、技術ロードマップを定義する主導権を握る。これは FlagOS が一貫して掲げる「一度の開発でマルチチップ動作」という位置づけと一致している。

四、まとめとトレンド観察

本調査期間は 2.2 リリースサイクルにおいて情報密度が最も高い一日であり、三つの層から総括できる：

  • リリース側：2.2 が RC2 に入り、フルスタックスナップショットの世代交代が完了。 リストが先行し、スクリプトが実行され、10 分以内に 23 のコンポーネントが一斉にタグ付けされ、テスト期間中に蓄積された修正が一括取得可能なロック版の集合として固定された。09-28 の GA まで残り 14 日であり、今後は rc2.postN のインクリメントのペースと Go/No-Go の結論に注目すべきである。
  • エンジニアリング側：受け入れの欠落が逐条埋められており、かつ明確なベンダー分業を伴う。 海光は 17 のオペレータを補完しイメージの再検証を完了、摩尔線程は profiler と推論ホットオペレータを追加、沐曦は vLLM 0.24.0 と metax CI を接続、燧原はベンダーブランチをメインラインにマージ、昆仑芯と達摩院玄鉄は「CI → オペレータ → リスト」の経路で接続した。2.2 のデリバリ範囲を判断する直接的な根拠は、依然として build-infra に対で現れるイメージタグとバージョンラベルである。
  • エコシステム側：「チップへの対応」から「ハードウェア形態の定義」へ。 Open3D-PIMC は清微と智源が共同でオープンソース化し、FlagOS の境界をマルチチップソフトウェアスタックから 3D 演算チップ向けのプログラミングモデルとコンパイルスタックへと押し広げ、かつ第四四半期に世界のトップテック会議で最適化成果を発表すると明言している。この種の動きの収益は当該期のオペレータ数ではなく、次世代チップの設計参考権にある。
  • 要注意項目： 第一に、FlagTree で初めて +xpu3.6 形態のアクセラレータ専用ラベルが出現したが、これが各バックエンドの標準デリバリ形態に普及するかどうか。第二に、Torch-FL が実行不能なオペレータにフォールバック経路を追加したことは、「ルーティングは整合済みだがオペレータカバレッジが不完全」が依然としてマルチチップスタックの常態的制約であることを示しており、2.2 の受け入れマトリクスがこうした欠落をカバーできるかは追跡に値する。第三に、PPU（達摩院玄鉄）と XPU（昆仑芯）の二社の外部エコシステム参画者の接続速度は明らかに通常のベンダーより速く、これが正式メンバーへの移行につながるかどうか。
