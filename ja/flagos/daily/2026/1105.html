3.2 地平線：BPU オペレータライブラリを使用可能な状態に修復、チェーン実行で 4 回のディスパッチを 0.673 ミリ秒に圧縮（11-04）

日付：2026-11-04　情報源：Torch-FL PR #721 · Torch-FL PR #726

  • 3 箇所のハード障害：#721 で、BPU の eager パスが実際には各オペレータを CPU 上で実行していることを解明——オペレータバケツの階段が 512 レーンを超えない、2 入力 artifact を単一テンソル記述子でコミットしたためサイレントに誤値となる、hbdk4 が box64 下で numpy をインポートできず x86 ツールチェーンが使用不能になる。修復後、Run を C ABI 経由で公開し、eager パスが aten dispatcher をバイパスできるようにし、各呼び出しの固定作業をホットパスから外した。
  • 実測データ：RDK S600 上で 262144 レーンの relu が 0.176 ミリ秒から 0.073 ミリ秒に、1 つの conv block が 23.2 ミリ秒から 11.1 ミリ秒に短縮。
  • チェーン実行：#726 で DeviceChain を追加、デバイス上で複数の BPU artifact を連続実行し、中間アクティベーションはホストに戻さず、先頭で入力し末尾で出力するのみでメモリを通過し、小さなデバイスバッファのリングで受け渡す。S600 上でシリアライズされた elementwise が 0.417 ミリ秒から 0.104 ミリ秒に、4 回の独立ディスパッチが 1.667 ミリ秒から 0.673 ミリ秒に短縮。
  • 判断：地平線のこのラインのボトルネックは演算能力ではなく固定オーバーヘッドである。ドライバは呼び出しごとに 0.09 ミリ秒、単一オペレータなら大したことではないが、1 層に数十のオペレータを持つモデルでは主要なコストとなる。中間アクティベーションをデバイス上に留めることは、このオーバーヘッドを「オペレータごとに 1 回」から「セグメントごとに 1 回」に圧縮することに等しい。

3.3 海光：FP32 flash attention フォワードを実装、別途 FP32 最適化 9 件を起票（11-04）

日付：2026-11-04　情報源：FlagGems PR #7388 · FlagGems PR #8404 · FlagGems PR #8451 · FlagGems-vllm PR #1066 · build-infra PR #1628

  • FP32 フォワード：#7388 は _flash_attention_forward の海光実装に明示的にサポートされる FP32 パスを追加し、同時に ATen の5出力 schema と既存の FP16/BF16 の挙動を維持する。サポート範囲は非常に狭く定義されている：固定長、連続 4D BSHD、方形 MHA かつ Q/K/V 同形、head dim が 64 または 128、dropout が 0、window/alibi/seqused/varlen なし。サポートされない組み合わせは未検証パスを通さず、直接エラーを報告する。
