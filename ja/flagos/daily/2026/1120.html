今日の重点：寒武紀 Neuware 4.7.6 が一日で三層を打通、2.3.0 基盤に最新の SDK ラインを追加（11-19）

日付：2026-11-19　出典：#1906 · #1907 · #1909 · cambricon-neuware4.7.6 変更記録

  • 3層を同日に：#1906 で base 層（ubuntu:24.04）を追加、#1907 で FlagCX ビルド行を追加、#1909 で runtime 層と変更記録を追加。3件は北京時間 06:02 から 06:47 の間に相次いでマージされた。
  • バージョンの基準：ツールチェーンは cntoolkit 4.7.6、cnnl 2.2.18、cnnlextra 2.5.0、mluops 1.13.0。通信・映像側は cncl 1.30.10、cncv 2.12.1、cnclep 1.5.0、監視は cnmon 6.5.52。変更記録には、このラインが当該ベンダーの最新 SDK ラインであり、4.7.2 も引き続き稼働中であると明記されている。
  • ランタイムスタック：Python 3.12、torch 2.13.0+cpu、torch-mlu 1.34.1、torch-mlu-ops 1.13.0、torchvision 0.28.0 と torchaudio 2.11.0 を組み合わせ。コンパイラはベンダー製 Triton 3.4.0+mlu2.1.3 を使用。このラインには FlagTree をインストールせず、Triton が唯一のコンパイラである。
  • なぜ3件に分割したか：4.7.6 の3つの pip 依存関係がまだ揃っておらず、torch-mlu 1.34.1、torch-mlu-ops 1.13.0、flagcx 0.14.0+neuware4.7.6 が関係している。これらは flagos-pypi-cambricon の補完を待つ必要がある。base を先に着地させ、FlagCX ビルド行と runtime をそれぞれ1件ずつ進めた。
  • 見落としやすい修正：新しい行は cambricon ラベルを再利用する。この上書きがないと、マトリクスはデフォルトの h20 runner にフォールバックし、寒武紀ノードはこのラベルを持たないため、タスクは延々とキューに残る。
  • FlagCX を別 recipe にする理由：4.7.6 の deb ファイル名は 4.7.2 と異なり、cncl は 1.30.10、cnnl は 2.2.18 で、いずれも行キーから導出できない。recipe は 4.7.2 の ubuntu:22.04 自己完結形態を踏襲し、wheel は最大で glibc 2.35 にリンクする。default_for_vendor はまず false のままにし、ノードでの検証後に切り替える。
  • 所感：11-18 の沐曦のライン切り替えと同じ手法であり、base を先に着地させ、runtime を追従させ、インデックスを補完してから wheel を補う。沐曦の日は6件、寒武紀は今回は3件だった。rc0 の 11-30 まであと10日、基盤層は依然として項目ごとにリストを揃えている。

今日の重点：BIS 新規の発効で国産計算力株が集団急落、燧原はストップ安後に「受注残は豊富」と公告（11-19）

日付：2026-11-19　情報源：燧原科技異常波動公告 · 毎経 · 電子工程専輯 · 21経済網転載上海証券報

  • ルール自体：11月16日、米国商務省産業安全保障局は「先進半導体へのリモートアクセスへの対応」に関する暫定最終規則（RIN 0694-AK50）を発表し、11月19日に『連邦公報』に掲載されて発効した。既存の算力サービスには90日間の許可移行期間がある。
  • 3カ所の厳格化：海外データセンターがD:5国家グループの企業に累計1200万TPPを超える算力を提供する場合、許可を申請しなければならない。インドネシア、マレーシア、シンガポール、タイ、ブラジルの5カ国が許可の範囲に追加される。16/14ナノメートル及びそれ以下のFinFETロジックチップについて、ファウンドリはもはやトランジスタ数による自行検証で3A090.aの規制推定を覆すことはできない。
  • 3番目が鍵：設計企業はBISの「Approved IC Designer」リストに登録されなければ、ファウンドリは注文を受けることができない。この点は発効前の最後の2取引日で十分に価格に織り込まれていなかった。
  • 相場：11月19日、燧原科技は20%のストップ安で張り付き、364.33元で引け、91.08元下落、売買代金19.62億元、回転率28.35%。沐曦、摩尔線程、海光信息、盛科通信と香港株の天数智芯も同日下落し、日中跌幅は多くが10%以上だった。
  • 逆側：同日、中芯国際A株は4.38%上昇、華虹宏力は7.47%上昇した。資金は国産算力から離れたのではなく、設計側から製造側へ移っただけだ。
  • 噂と反証：11月18日夜から、三星がファウンドリを厳查するという噂が流れ、19日には各社のファウンドリ依存を名指ししたスクリーンショットが拡散し、天数智芯、翱捷科技、燧原科技のTSMC依存が最大だとされた。上海証券報が複数方面に確認したところ、三星にはファウンドリを厳查する公式文書はなく、噂は不正確だと報じた。14/16ナノメートルの注文は審査通過の確実性が高く、5ナノメートル以下は案件ごとに審査される。翱捷科技は同日、ECCN分類コードを取得し、制限範囲に属さないことを確認したチップは通常通り流片できると回答した。
  • FlagOSとの関係：名指しされた企業のうち5社はFlagOSメンバー単位であり、燧原、沐曦、摩尔線程、海光、天数智芯が含まれる。今回の変動はコンポーネントのコードには一切関係しないが、メンバー単位の資本市場環境が同じ日のうちに一斉に変化した。
  • 観察：市場は「許可制」を「一律禁止」として取引した。実際に変わったのは域外先進プロセス経路の商業的確実性であり、当日の生産能力ではない。国産算力の「設計はすでに国産化、製造はまだ」という構造的事実が、初めて一つの噂によって表面化した。

1.3 build-infra：910C の 3 行を dispatch 経由で FILE_STORE に変更、ハードコードを撤回（11-19）

日付：2026-11-19　情報源：#1921 · #1925

  • 問題：resource.flagos.net が hw114 と hw115 で解決できず、この 2 台まさに 910C 行をビルドしていた。2 回の base 再構築はいずれも最初の SDK ダウンロードで止まり、Could not resolve host を報告した。
  • なぜ 1 つだけ生き残ったか：9.2.1-910c が止まらなかったのは、以前にイントラネット端点を Containerfile にハードコードしていたからである（#1770）。
  • 修正方法：FILE_STORE を公共デフォルト値付きの ARG にし、build-config.yml に build_args を新設し、イントラネットを必要とする行のみイントラネット端点を使うようにした。3 行の 910C は現在同じ公共デフォルトを共有し、差異は dispatch にのみ残る。
  • 理由はコミットに書かれている：アドレスはサイトの事実であり、イメージレシピの一部ではない。したがってハードコードは良い修正方法ではない。
  • 審査中 1 件：#1925 は 8.5.0 と 9.0.0 の 2 行の runtime 再構築もイントラネット PyPI に向けている。理由は同じで、uv のダウンロードが resource.flagos.net で止まるからである。910B 行は依然として公共インデックスを使う。
  • 所見：同一種の問題を 1 日で 2 つの粒度で処理した。base 層は構造を変更し、runtime 層はまず暫定パッチを当てた。これは rc 直前の取捨選択に合致する。構造変更は 1 回だけ行い、残りはまずビルドを通す。

1.4 燧原ベンダードキュメントで 3 箇所の記述を一度に修正、ECCL の 64 ビット制限とオペレータ制限を分けて記録（11-19）

日付：2026-11-19　情報源：#1916 · #1915

  • 期限切れの記述：ベンダーページにはまだ enflame-tops1.9.10 と tops1.10.6 と書かれていたが、マトリクスはすでに tops1.9.29 と tops4.1.6 に置き換わっていた。今回まとめて修正し、4.1.6 に対応する L600 チップも補足した。
  • ECCL バージョンは無関係：2 つのラインの ECCL バージョンは 3.6.3.13 と 4.1.4 で、互いに無関係である。ドキュメントは以前、両者が同源であるかのように示唆していた。
  • #1915 の証拠：fp64 と int64 の all_reduce は MIN と SUM の両方で失敗する。これは ECCL の dtype 境界であり、特定の SDK バージョンのリグレッションではない。
  • 2 つの異なる壁：TORCH_GCU_ENABLE_INT64_AND_UINT64 と ENABLE_I64_CHECK はカーネルコード生成のみを扱う。これらを有効にしても集合通信が 64 ビット型を受け入れるようにはならず、ドキュメントはこの点を明記した。
  • 証拠の分级：1.9.10 と 1.10.6 は本リポジトリで実測、1.9.29 は issue 由来でここでは再現していない、4.1.6 は未検証。3 段階を分けて标注し、もはや混在させていない。
  • 所見：これは記述のガバナンスである。同一ドキュメント内にバージョン番号の期限切れもあれば、2 つの壁を 1 つと見なす推論エラーもあり、修正方法は証拠の出所も明記することである。

1.5 FlagGems：83 件のコミット、KernelGen が 3 線並行で摩尔線程、Nvidia、昇騰を展開（11-19）

日付：2026-11-19　情報源：FlagGems コミット · #9467 · #9533 · #9499

  • 分類カウント：KernelGen 生成オペレータ 43 件（摩尔線程 21、Nvidia 16、昇騰 4、その他 2）、残り 40 件は精度修正、CI とリファクタリング。
  • 摩尔線程：午前 09:36 から 09:57 に 14 個の _foreach オペレータを一括で、午後 15:08 から 15:13 にさらに 7 個を追加。addcmul、asin、atan、ceil、clamp、div、erf、erfc、exp などのスカラー版とリスト版をカバー。
  • Nvidia：疎側では疎パラメータ検証オペレータを 2 個（bsc と compressed の兩種）、さらに _sparse_addmm と matrix_H を追加。逆方向側では logcumsumexp、log1p、log2、lu_unpack、max、min、median、logsumexp などの autograd を追加。
  • 昇騰：divide、true_divide、conv_tbc、_adaptive_avg_pool3d_backward の 4 オペレータを同一分にマージ。
  • 精度とタイムアウト：一度に 13 件を集中的にマージ、昇騰と沐曦の両側をカバー。昇騰側は FP8 入力構築、cumprod と unique_dim の grid 上限、triangular_solve の下三角失敗。沐曦 C550 側は multi_margin_loss の検証と 4 ビット行列積の精度、平頭哥 PPU 側は nanmedian のコールドコンパイルタイムアウト。
  • 昆仑芯：4 件、ldexp 精度、batch_norm 修正、sobol_engine の早送り最適化と GRU のベンダー kernel 利用を含む。
  • 所見：KernelGen はすでにオペレータ補完をパイプライン化しており、単日 43 個は異常ではない。真に希少なのは検収側である——この日の精度修正はほぼすべて各社バックエンドに落ちており、オペレータ補完の速度が整合の速度をすでに超えていることを示している。

1.6 FlagGems：fused/ を deprecated/ に改名、343 ファイルに互換 shim を添付（11-19）

日付：2026-11-19　情報源：#9462

3.2 寒武紀：4.7.6と4.7.2が併存する取捨（11-19）

日付：2026-11-19　情報源：#1906 · #1907 · 変更記録

  • 3本のラインが併存：4.4.3、4.7.2、そして新規の4.7.6。変更記録には4.7.6がベンダー最新のSDKラインであり、4.7.2は引き続き現役であると明記されている。
  • デフォルトは切り替えない：FlagCXのdefault_for_vendorは新ラインに対してfalseに設定され、4.7.2が引き続きlibflagcx-cambriconを提供する。新ラインがノード上で検証を通るまで続く。
  • ビルド面の差異：4.7.6の22.04 debはfilestoreのcambricon/ルートに置かれ、4.7.2のものはu2204/下にある。そのためrecipeのFILE_STOREは異なる位置を指す。
  • 依存関係の断点：torch-mlu 1.34.1とtorch-mlu-ops 1.13.0は寒武紀のプライベートインデックス上でまだ揃っておらず、ホイールはFlagCXのビルドイメージの実行が完了するまでコンパイルできない。
  • なぜ待つ価値があるか：4.7.6はtorch 2.13.0とTriton 3.4.0+mlu2.1.3に対応し、4.7.2のセットより一世代新しい。2.3.0で使えれば、寒武紀バックエンドのオペレータカバレッジもそれに伴って上がる。
  • 所見：これは意図的にペースを落としたライン切り替えである。デフォルトを切り替えず、旧ラインを削除せず、載せられる層から先に落とす。3つのステップはいずれもロールバックの余地を残している。rc0まで残り10日であり、このペースは4.7.6が2.3.0のデフォルトマトリクスに間に合わない可能性が高いことを意味する。

3.3 云天励飛：IFWAをGEMS_VENDORで明示的に接続、審査中（11-19）

日付：2026-11-19　情報源：FlagGems #9545

  • 変更内容：FlagGemsに明示的なIFWAバックエンド選択を追加し、GEMS_VENDOR=intellifusionを通じてifwaデバイスを登録する。チューニングデータが揃うまでは汎用ヒューリスティックを先用する。
  • ついでに修正したバグ：共有pointwise生成器がTriton 3.8上でout_bptr.dtype.element_tyを使ってストレージ型を取得していた。従来はout_bptr.typeを使っており、3.8では集約型でelement_tyがなく、生成されたカーネルがAttributeErrorを投げていた。
  • 検証範囲：135個の生成カーネル本体を比較し、変化したのはストレージ型の式のみ。
  • 状態：審査中、性能データは追って补充、単体テストはまだカバーしていない。
  • 所見：メンバー単位のリストにはこれまで云天励飛がなかった。このマージが通れば、FlagOSの明示的バックエンドはさらに1社増える。これはバックエンドの接続方式が標準化しつつあることも示している——環境変数1つとデバイス登録1つで済み、コアを変更する必要はもうない。

4. まとめ

  • 基盤層は収尾段階に入る：寒武紀 4.7.6 の三層が落地、海光は amdsmi を補完、昇騰 910C は dispatch 経由に変更。17 件のマージのうち 11 件は差し替えと修正で、新機能はない。rc0 の 11-30 まであと十日。
  • オペレータ層は二つのことを進めている：KernelGen は一日で 43 個のオペレータを生成し、同時に 40 件のコミットが各社バックエンドの精度とタイムアウトを修正している。補完は速いが、整合は遅く、検収側がボトルネックになっている。
  • A5 はスキャフォールドから実測へ：FlagGems はアーキテクチャ検出と空ディレクトリを追加し、FlagGems-vllm は同一ブランチで最初の 950DT オペレータをマージし 4.5 倍を示した。二つのラインが同じ準備を進めている。
  • 生成型ホストがパイプライン化：沐曦、海光、燧原の三社のネイティブホストが同日マージされ、三つの PR はいずれも未達の数値をそのまま残した。このやり方は見栄えのよい加速比よりも、今後の意思決定を支えられる。
  • vLLM 0.32 が六社を同期動作に束ねる：審査中 261 件の中で最も集中しているのがこの一波で、沐曦、昆侖芯、海光、摩尔線程、清微と日出が同じことをしている。マージ数 167 がコミット数 196 を下回る原因はここにある。
  • ニュース面で確かな材料は一つだけ：BIS 新規の発効当日、五社の成員単位の株価がそろって急落し、燧原はストップ安の後に受注が潤沢と公告した。コンポーネント側に変化はないが、成員単位の資本市場環境は同じ日に一斉に変わった。
  • 要注意：寒武紀 4.7.6 が 2.3.0 のデフォルトマトリクスに間に合うか；A5 オペレータが 910 で埋め戻せるか；vLLM 0.32 の六件が今週そろってマージされるか；云天励飛 IFWA のチューニングデータがいつ揃うか。
