1.2 Torch-FL：改名後 1 日で 14 件、寒武紀 Qwen3 訓練ステップが着地（11-10）

日付：2026-11-10　情報源：Torch-FL リポジトリ · Torch-FL #809（寒武紀 Qwen3 訓練ステップ） · Torch-FL #789（崑崙芯 FlagGems ルーティング）

  • 位置づけ：Torch-FL は旧 PyTorch-Plugin-FL が改名されたリポジトリで、README は torch-fl に変更済み。外部には単一の flagos デバイスを公開し、オペレータごとに 4 種類の実装間でルーティングする——再利用可能なローカルカーネル、可搬なコンパイラカーネル、ベンダーネイティブ実装、明示的な CPU フォールバック。同一バッチの docs コミットでも関連ドキュメントが torch-fl に改名された。
  • 1 日の規模：14 件のマージ。本期のコミット数で第 4 位、増加が最も速い主力リポジトリであり、別に審査中 issue が 102 件ある。
  • 寒武紀：#809 により、Qwen3 訓練ステップに必要な 17 個の寒武紀オペレータがコード生成器から直接ローカル供給される。インプレース算術系、3 つの融合 CNNL エントリ、4 種類のビューオペレータと zeros、sqrt、div を含み、同時に fill_ のライフサイクル不具合を修正。
  • ついでに発見されたビルド不具合：torch_bindings がずっと USE_CAMBRICON 付きでコンパイルされておらず、Triton にどの cnrt キューへ発射するかを伝えるバインディングが存在しなかった。そのため Triton は実際には空のキューで動作し、CNNL カーネルとの順序保証がなかった。
  • 性能の口径：当該訓練ステップは torch_mlu の 1.86 倍の所要時間で、まだ追いついていない。PR の自己記述ではオペレータカバレッジとキューの順序不整合のみを解決し、性能の整合は行っていない。
  • 複数バックエンドを同一バッチで：#801 で TileOPs ベンダー実験ルーティングを追加、#802 で MPS に argmin と max.dim、min.dim を補充、#797 で天数バックエンドの型変換をデバイス側に戻し、#790 で天数の融合アテンションスイッチをモデル自身の呼び出し形態まで緩和。
  • 審査中の方向性：P800 上で実測済みの 316 個のオペレータを丸ごと FlagGems にルーティングする PR がまだ審査中で、崑崙芯側の次段階における規模感のある動き。

1.3 FlagGems：149 件マージ、KernelGen 130 件のうち沐曦 89、海光 20（11-10）

日付：2026-11-10　情報源：FlagGems リポジトリ · FlagGems #8723（清微バックエンドを FlagTree 0.7.0 へ） · FlagGems #8643（崑崙芯 var と vander）

  • 規模：149 件のコミットと 149 件のマージがすべて本リポジトリに集中し、組織全体のマージ数の六割を占める。うち KernelGen タグ付きが 130 件で、バックエンド別では沐曦 89、海光 20、英偉達 9、摩尔線程 9、昆侖芯 3。
  • 沐曦の foreach ファミリ：89 件は foreach プレフィックス付きオペレータ一式で、add、mul、div 系のテンソル・スカラー・リスト・インプレース変体、さらに maximum、minimum、log、log2、log10、log1p、abs、acos、neg、addcdiv などをカバーし、散発的な補完ではなくファミリ全体の補完である。
  • 海光：20 件の専用オペレータは特殊関数、プーリング、逆畳み込み、embedding_bag 逆方向、hash_tensor、融合行列積が主体で、ほかに品質検査項目として layer_norm と native_layer_norm を補完。
  • 正確性修正：cdist_backward を p ノルムに応じた勾配公式のディスパッチに変更。昆侖芯は batch_norm 逆方向の上書きを補完し、var のシグネチャと vander の上書きを修正。W8A8 INT8 行列積のベンチマーク JSON 記録を復旧。
  • 工程規範：全角句読点のプリコミットフックを追加し、併せて摩尔線程 linalg_tensorinv の未使用変数警告を修正。metax と mthreads のオペレータファイルの末尾カンマとインポート順も整理。

3.1 寒武紀：Qwen3 訓練ステップの17オペレータを CNNL へ変更、双队列乱序を修正（11-10）

日付：2026-11-10　情報源：Torch-FL #809

3.2 崑崙芯：P800 上で4つの断点が全閉、FlagGems ルーティングは空のまま勘測待ち（11-10）

日付：2026-11-10　情報源：Torch-FL #789 · FlagGems #8643 · FlagGems #8641

  • 問題：昆仑芯のホイールは実はすでにFlagGemsに組み込まれているが、バックエンド設定がゼロ個のオペレータしかルーティングしておらず、FlagGemsがカバーするすべてのオペレータが昆仑芯上でCPUフォールバックに落ちている。
  • 4つの断点：設定ジェネレータが昆仑芯向けにオペレータを一切ルーティングできない（ドキュメントに書かれた逃げ道はサイレントな空操作）、FlagGemsスロットに登録ファイルがない、CPU版torch下でFlagGemsを実行するために必要なランタイムグルーが欠けている、ネイティブとFlagGemsの優先度設定が当該プラットフォームを指名していない。
  • 結果：4つの断点はすべて解消され、P800上でエンドツーエンド検証に合格。ただし許可リストは依然として空で、設定ファイルは変更前とバイト単位で同一——作者の説明によれば、最初のルーティングにはP800の調査データによる裏付けが必須である。
  • 後続：316個のP800実測オペレータを全体としてFlagGemsにルーティングするPRがすでにレビュー中で、これがこのラインの次のステップである。
  • オペレータ側：FlagGemsは同日、昆仑芯向けにbatch_normの逆伝播オーバーライドを追加し、varのシグネチャとvanderのオーバーライドを修正した。
