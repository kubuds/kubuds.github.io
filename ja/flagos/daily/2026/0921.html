今日の重点：2.2 リリース 0.20.2 ラインの全バックエンドスナップショット完了——20 のバックエンドイメージが実機検証を通過、3 バックエンドの FlagTree ピン留め理由を公開

日付：2026-09-20　出典：build-infra #991、build-infra #956

09-20 の夕方から夜にかけて、build-infra は 2.2 リリースの更なる一本の完全なラインを完成させた：0.20.2 ライン（vLLM 0.20.2）のイメージタグ記録は上海時間 19:04–19:27 に 14 件を集中的に書き戻し（英偉達 cuda12.8、崑崙芯、天数 iluvatar の 2 バージョン、海光、摩尔線程の 2 バージョン、昇騰の 3 変体、寒武紀の 2 バージョン、清微、燧原などをカバー）、これに先立つ 14:49–18:43 の 6 件を加え、このラインの 20 のバックエンドすべてが 2.2.0-0.2.2rc2.post2 を伴う。19:40 にマージされた #991 はこれを受けて、この一巡の再ビルドを 0.20.2 ラインの 2.2.0 リリーススナップショットとして記録した——各記録は実機検証を経て初めて放出される：パッケージマトリクスの照合、vllm/vllm_fl の実際のインポート、実際の serve によるトークン出力の 3 項目すべてが通過した。

スナップショットと同時に公開されたもう一つの手掛かりは、以前はコミットタイトルにしか現れなかった——三つのバックエンドが統一コンパイラ基盤を使用できない：2.2.0 スタックは当初、全バックエンドを FlagTree 0.7.0rc2 上に統一する計画だったが、沐曦（tl.dot が BLOCK_SIZE_M=8 でコンパイラ ICE を引き起こす）、燧原 tops1.9.10（enable_i64 が旧ツールチェーンに拒否される）、英偉達 cuda13.3（TLE が libcudart.so.12 に依存）の三者が 0.7.0rc2 上では動作せず、それぞれ実機再現＋0.6.x 対照の形式で上流にコミットし、イメージ記録に各自の FlagTree ピン版を逐一注記した（昨日の三件の hold コミットに対応）。この「スナップショット＋ピン版理由」の組み合わせにより、リリース物の検証可能性がさらに一段進んだ：各イメージに何がインストールされ、何が検証され、なぜ基盤が異なるのか、すべてが記録に残されている。09-28 の GA まであと 7 日、リリースエンジニアリングは収束のペースにある。

1.2 FlagGems：TLE パスが二つのバックエンドを連続開放——昇騰 glu 適配、天数 Iluvatar の TLE 有効化（09-20/09-21）

日付：2026-09-20、2026-09-21　情報源：FlagGems #6522、FlagTree #1238

09-20 夜にコミット、09-21 午前にマージされた #6522 は一度に二箇所の TLE を開放する：昇騰側は glu オペレータに TLE 適配を追加（tle.dsa.extract_slice プリミティブを使用）、天数 Iluvatar 側は vendor descriptor 内で tle_enabled を True に設定し、TLE パスを正式にエクスポートした。これは TLE が 48 時間以内に参入した第三、第四のバックエンドである——前調査期間に達摩院玄铁 PPU が TLE を有効化したばかりで、本調査期間には昇騰と天数へと延伸した。併せて、FlagTree は審査中 PR #1238 で昇騰 TLE の raw プリミティブ命名を tle.dsa.ascend.raw から tle.raw に統一した（09-20 コミット）——TLE のバックエンド横断的な一致化が命名層でも同時に進行している。

1.3 FlagGems：KernelGen がさらに二オペレータを登録；SiliconFlow のバックエンド横断 FP8 grouped GEMM 修正がマージ（09-20/09-21）

日付：2026-09-20、2026-09-21　情報源：FlagGems #5911、FlagGems #6349、FlagGems #5064

三件のマージ：其一、KernelGen が inverse オペレータを産出（#6349、09-20 22:21）——プログラムごとに部分ピボット選択付きのガウス・ジョルダン消去を行い、作業行列と逆行列アキュムレータはすべてレジスタに常駐し、行交換は tl.gather で正確に追跡；レジスタに収まらない大行列と複素数入力はベンダーの cuSOLVER にフォールバック。其二、KernelGen がさらに _gather_sparse_backward をリポジトリに追加（#5911、09-21 09:25）——gather の逆方向で、スパース COO 勾配を産出。其三、硅基流動（SiliconFlow）による _scaled_grouped_mm のクロスバックエンド修正とチューニング（#5064、09-21 09:49 マージ、PR 開放から約二か月後に収束）：ネイティブ FP8 dot パスを持たないバックエンドは E4M3 を FP16 にデコードしてから行列積を実行（FP32 累加）；E4M3FN / E4M3FNUZ のバイト単位デコードを新規追加；天数 Iluvatar は CoreX 4.4 が dot ループに融合したデコードを誤ってコンパイルするため、独立したデバイス側デコードカーネルに切り替え；さらに海光と沐曦の専用チューニング設定を追加。

1.5 FlagTree：AMD バックエンドの二か所のコンパイラ修正（W7900 精度テストで露見）（09-20）

日付：2026-09-20　情報源：FlagTree #1240

審査中 PR #1240 で AMD バックエンドの二か所の修正が下りた。出所は W7900（gfx1100）で FlagGems オペレータ精度テストを実行した際に露見した問題：其一、CanonicalizePointers は scf.if の両アームの fat-pointer 属性について積集合を取るように変更（canNarrow が両アーム一致の場合のみ保持）、もはや両アームの等価を断言しない——FlagGems の cat / concatenate / div_tensor カーネルは両アームの属性が異なる scf.if を合法的に生成し、以前は断言を有効にした LLVM ビルドで直接 pass クラッシュを引き起こしていた；其二、AtomicCAS の非整数ビット変換の処理。両方とも上流 Triton の対応処理の移植。AMD コンシューマー向けカードが FlagGems 精度テスト面に組み入れられたことは、本調査期間で留意すべき方向性の一つ。

2.2 中国電信 Xing4.0-29B-A4B 解説：国産算力配備は智源 FlagOS 統一オープンソースソフトウェアスタックに基づく（09-20）

日付：2026-09-20　出典：量子位

量子位は 09-20 夜、中国電信が 09-17 にオープンソース化した軽量級エージェント大規模モデル Xing4.0-29B-A4B（総パラメータ 29B / アクティベーション 4B、256K コンテキスト、昇騰 910C + MindSpore/MindFormers で学習、4-bit 量子化後は単体の 3090 で動作可能）を解説する記事を掲載した。記事は「企業に AI を本当に使わせる」の節で明確に次のように述べている：国産算力を採用する企業にとって、このモデルは智源 FlagOS 統一オープンソース AI ソフトウェアスタックに基づき複数の国産チップへの適合経路を打ち開いた、これによりハードウェアプラットフォーム間の移行・配備コストを低減する。これは FlagOS が「統一ソフトウェアスタック」という位置づけで再び第三者主流技術メディアの製品解説に登場したものであり、モデルの Agent フレームワーク適合リスト（OpenCode / Claude Code / OpenClaw / Hermes）も FlagOS エコシステムの Agent 方向と同題である。

2.3 FlagOS ディストリビューションパッケージチャネル：flagos-packaging が v2026.09.20 をリリース、apt/dnf の両形式（09-21）

日付：2026-09-21　出典：flagos-packaging v2026.09.20、パッケージインデックスサイト、build-infra #955

パッケージング工程リポジトリ flagos-packaging は本日未明に v2026.09.20 をリリースした（週次更新のリズムで、以前は 09-06、09-13）。このリポジトリは FlagOS ソフトウェアスタックに APT（Debian/Ubuntu）と YUM（Fedora/RHEL/OpenEuler/OpenCloudOS/OpenAnolis）のデュアルフォーマットネイティブパッケージを提供し、el8 / el9 / fedora43 / openanolis8 / opencloudos9 / openeuler2403 の6種類のディストリビューション用 repo ファイルを既に提供しており、パッケージには GPG 署名が付与されている（例：apt install libflagcx-nvidia python3-flagscale python3-flagtree-nvidia）。現在はサンドボックスエンドポイントと計画中の本番エンドポイント（flagos-ai.github.io）が同一のサービスセットとなっており、移行期間にある。合わせて、build-infra は FlagGems に deb リリースパスを追加し（#955）、FlagBLAS 側では3件のパッケージング PR（Debian+RPM パッケージング、Nexus リリース、0.3.0-rc2 移植）が審査中である——コンテナイメージの外側で、FlagOS のディストリビューションネイティブ配布チャネルが形を成しつつある。

2.4 FlagOS × MiniCPM チャレンジは本日コミット段階へ（09-21）

日付：2026-09-21　情報源：知乎機関アカウントの以前の投稿

以前に公表されたスケジュールによると、FlagOS × MiniCPM モデル推論スループット性能最適化チャレンジの開発・コミット段階が 09-21 から開放される（11-20 まで、12 月に審査）。課題は FlagOS スタック上の推論スループット最適化を対象とし（4k / 16k の2種類の評価シナリオを含む）、SGLang クロスチップオペレータ最適化コンテストに続くコミュニティコンテスト体系の延長である。本日から実際のコミットウィンドウに入り、以降のウィンドウでは最初のコミット動向に注目できる。

3. メンバー機関の深掘り

3.1 沐曦：Qwen-Image-2.1 Day0 適配を公式発表、FlagTree 専有化リファクタリングを継続推進（09-20/09-21）

日付：2026-09-20　情報源：新浪財経（界面新聞転載）、新浪財経（観点網転載）

09-20 夜、アリ千問チームが画像生成モデル Qwen-Image-2.1 をオープンソース化すると発表した後、沐曦股份は同モデルへの Day0 適配を完了し、「リリース即適配」を実現した（界面新聞、観点網、同花順など複数の情報源が報道）。コード側では同期間に2件：第一に、FlagTree の沐曦バックエンド専有化リファクタリングがウィンドウ内で10件進行（詳細は 1.4）；第二に、FlagSparse の MACA ラインが maca spsv coo and spmv csr test をコミット（09-20 17:18）。もう一つ対比できるのは、FlagOS スタック内の Torch-FL リポジトリの Qwen-Image-2.1 マルチチップ性能最適化ラインがなお継続していることである（本期 GCU 側 #363、3.7 参照）——「大規模モデルのリリース当日にマルチチップで利用可能」というモデルは、プレスリリースから各社バックエンドの実際のコードパスへと入りつつある。

3.2 海光：fused_inv_rope_fp8_quant オペレータをマージ、FP8 grouped GEMM のチューニング（09-21）

日付：2026-09-21　情報源：FlagGems-vllm #801、FlagGems #5064

今朝マージされた #801 は海光 DCU（gfx936 / BW1000）に fused_inv_rope_fp8_quant オペレータを追加した——DeepSeek-V4 アテンションパス向けの「逆 RoPE + 128要素ごとの FP8 E4M3FN グループ量子化」融合実装であり、既存の vendor-override 機構を通じて（同名関数が runtime/backend/_hygon/ から汎用実装を上書きする）。gfx936 にはネイティブの FP8 変換命令がないため、Triton は .to(fp8) を長いシミュレーション列に展開し、この融合オペレータの性能上の意義はここに由来する。また FlagGems #5064 では、海光と沐曦の _scaled_grouped_mm 専用チューニング設定が併せて確立された。

3.3 昇騰（Asecend）：glu オペレータの TLE 適配と 910B FlagGems ベースラインワークフロー（09-20/09-21）

日付：2026-09-20、2026-09-21　出典：FlagGems #6522、FlagTree #1247、FlagGems-vllm #810

昇騰ラインは三本：glu オペレータの TLE 適配（#6522、tle.dsa.extract_slice を使用、1.2 参照）；Ascend 3.5-910B の FlagGems ベースラインとテストワークフローのコミット（#1247、審査中、1.4 参照）；vllm プラグイン側に新規 kda_state_gather Triton オペレータを追加（#810、09-21 09:29）。前回の調査期間の専用線形オペレータ（#6456）と kda_gate_cumsum（#809）に加え、昇騰方向のオペレータと CI の両ラインはいずれも密集した状態を維持している。

3.4 天数智芯：TLE パスを有効化、FP8 デコードは独立カーネルで実行（09-21）

日付：2026-09-21　出典：FlagGems #6522、FlagGems #5064

天数（Iluvatar）ラインは二本：その一、vendor descriptor で TLE パスを有効化（tle_enabled=True、#6522）——天数は TLE マルチバックエンド名簿の一員となった；その二、_scaled_grouped_mm の FP8 デコードを CoreX 4.4 上で独立したデバイス側カーネルに変更（#5064）——当該ツールチェーンは dot ループに融合したデコードシーケンスを誤ってコンパイルするため、この特化は特定バージョンの欠陥に対するエンジニアリング上の迂回策である。いずれも「チップの実際の能力に応じて差別化されたパスを取る」典型例である。

3.5 清微智能：KernelGen 2.2.0 に新規ハードウェアとして収録（09-20）

日付：2026-09-20　出典：KernelGen #89

KernelGen は Updated Tsingmicro as a new hardware をマージ（#89）——清微（Tsingmicro）が KernelGen 2.2.0 の新規ハードウェアとして列挙された。これは build-infra イメージマトリクスにおいて tsingmicro-tsm260610 バックエンドが二本の vLLM ラインのいずれにも記録されている（0.3.0 / 0.2.2 各一本）ことと相互に裏付けられる：清微は FlagOS 2.2 のマルチチップマトリクスにおいて「接続中」から「リリース品に追随する」状態へと移行した。

3.6 達摩院玄鉄：T-Head ZW810E コストモデルパッケージ 1.1.0 が FlagTune ディレクトリに追加（審査中）（09-20）

日付：2026-09-20　出典：FlagTree #1236

審査中の PR #1236 は FlagTune モデルディレクトリに T-Head ZW810E の MM/MV コストモデルパッケージ v1.1.0 を追加する：8 個の BF16 flaggems/mm 変体（mv と共用する gemv_ppu を含む）と、1.0.0 パッケージを踏襲する 2 個の flaggems/mul モデルを含む；モデル契約には「正確に順序付けられた configs リスト」のサポートが新たに追加された（項目ごとにパラメータ名と正当値を検証し、config_space との混用を拒否する）。これは前回の調査期間の PPU による TLE 有効化に続き、玄鉄方向における自動チューニングコストモデル上の連動した進展である——TLE は「どう書くか」を担い、コストモデルは「どの設定を選ぶか」を担い、両ラインは 2.2 のマルチバックエンド最適化フレームワーク内で合流する。

3.7 摩尔線程 / 燧原：MUSA CI と GCU 性能最適化（09-20）

日付：2026-09-20　出典：vllm-plugin-FL #457、Torch-FL #363、FlagBLAS PR

摩尔線程ライン：vllm-plugin-FL の MUSA CI による vLLM 0.24 ライン対応（#457）；FlagSparse の musa updates（09-20 13:58）；FlagBLAS の MUSA 二级支持ブランチ（feat/mthreads-l2-support）が調査期間起点にプッシュされ、対応する PR #112 が審査中。燧原ライン：Torch-FL の GCU 上の Qwen-Image-2.1 最適化——融合 SDPA チャネルで無効マスクを削除、complex64 乗算を分解式に変更（#363、09-20 23:58 マージ）、残量は「測定済み未追平」として正直に PR に記録。

4. 総括とトレンド観察

  • リリース品が「検証可能」な收尾を完了：0.20.2 ラインの 20/20 バックエンドイメージが実機検証（パッケージマトリクス照合 + インポート + 実 serve でのトークン出力）を完了しスナップショットを保管；3 つのバックエンドが 0.7.0rc2 に載らない理由（沐曦 ICE、燧原ツールチェーン、cuda13.3 依存）を逐一公開し、上流再現手順を添付。GA（09-28）まで 7 日、收口は速度より品質を優先。
  • TLE クロスバックエンド三連：達摩院玄鉄 PPU（09-20）→ 昇騰と天数 Iluvatar（09-21）、48 時間以内に 4 つのバックエンドに進出；命名（tle.raw 統一）、コストモデル（T-Head 1.1.0）も同期して追随。TLE は単点試験からマルチバックエンド統一最適化パスへと転換中で、10 月カンファレンス「Triton-TLE Attention kernel」ワークショップ議題と相互に裏付け。
  • チップベンダーがコンパイラバックエンドに深く参画：沐曦の専有化リファクタリングが一晩で十件（ソースレベル専有化 + 統一 CMake エントリ）、国産スタックの分業において、ベンダーエンジニアが FlagTree のようなコンパイラ基盤で深水区の改造を行っており、単なるオペレータ適配にとどまらないことを示す。
  • 配布方式の多元化：コンテナイメージ以外に、apt/dnf ネイティブパッケージチャネル（flagos-packaging 週次更新、build-infra deb パス、FlagBLAS パッケージング三点セット）が形成され始め；リリース物は「イメージ + ドキュメント」から「ディストリビューション原生パッケージ」へ拡張。
  • 静かなコンポーネント級ニュース vs 高水準の工程側：本調査期間の 163 コミット / 22 リポジトリプッシュはすべてコード由来；对外発信はエコシステム日程が担当（チャレンジ賽は本日開幕、カンファレンス 10-17/18 登録受付中）。唯一のサードパーティメディアによる FlagOS 言及は量子位による中国電信 Xing4.0 の解読（デプロイパスは FlagOS 統一ソフトウェアスタックに基づく）。
