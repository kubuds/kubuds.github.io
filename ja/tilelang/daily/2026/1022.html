今日の重点

本ウィンドウで32件をマージ（TileOPs 20、tilelang 8、tilelang-ascend 3、TileOPs ドキュメントサイト 1）。さらに正式リリースが1件：TileFoundry が 10-21 10:26 に 0.0.3 を打った。三つのラインの重心はそれぞれ異なる。メインリポジトリの8件のマージはほぼすべて「エラーは出ないが結果が信頼できない」欠陥の整理——バッチ式リダクションが最初の出力ブロックしか処理しない、cast の丸め注釈が黙って破棄される、arch のない CUDA target が黙って sm_50 に落ちる、パイプライン計画が推移的依存を失う；TileOPs は一日で MLA プリフィルの逆伝播を op 層から SM90 warp 特化 kernel まで実装し、同時に SM89 上の FP8 BMM、W4A16、ページド DSA、NSA top-k の四つの小規模パスを一挙に推進、レビュー待ちキューは 16 件から 9 件に減少；昇騰側は昨日なおレビュー中だった DeepGEMM ヒューリスティックと epilogue のアラインメント（#3577）が本日マージされ、昇騰リポジトリは keepdim reduce の出力錯乱を引き起こすメモリアクセスモデリング欠陥（#1795）を修正した。産業側では、SemiAnalysis のファーウェイ-DeepSeek 深度レポートが TileLang Ascend の節を特別に設け、昇騰サポートを得た6つのリポジトリのうち当時利用可能だったのは TileLang のみという判断を示した。

1. コアプロジェクト進捗

1.1 メインリポジトリ：バッチ式 finalize_reducer が従来は最初の出力ブロックのみリダクション（#3070）

10-22 01:16 にマージ、2ファイル +29/-5、#2623 を修正。バッチ式 finalize_reducer の下降はバッファ先頭で一度だけ run_batch を呼び、残りの連続出力ブロックはまったくリダクションされていなかった：出力次元が batch より大きい場合、後続の各セグメントが受け取るのはリダクション結果ではなく、未初期化または前ラウンドの残値であった。修正は ceil(OutputDim / batch) ごとに正しいオフセットを持つバッチ式 all-reduce を逐塊発射——128 出力、batch=4 の場合 32 回の呼び出しを発射、同時に再マッピング reducer バッファをフラットビューに変更し、各バッチを定数の線形オフセットでアドレッシング、従来の形状とストライドの再構築を除去し、すべての chunk 呼び出しを保持。検証は L40S 上で完了：sum/max/min の数値回帰を新規追加、fp16 と fp32、batch 4/8/16 をカバー、23 件の finalize_reducer 関連ケースが通過、外部再現マトリクス16例でゼロ不一致。典型的な「小サイズは正確、大サイズは静かに誤る」類の欠陥に属する。

出典：https://github.com/tile-ai/tilelang/pull/3070

1.2 メインリポジトリ：BF16→FP32 ベクトル化変換をインライン PTX パック lane 変換に変更（#3595）

10-21 19:28 にマージ、4ファイル +19/-7。
tl::__tl_cvt_bf16x2_to_f32x2 を新規追加、インライン PTX で対になった BF16 lane を一度に f32x2 へ変換、逐 lane のスカラー昇格パスを置き換え；2、4、8 の三つの lane 幅はすべてサポートを維持。同時にベクトル化 cast とレイアウト推論の期待値を更新し、BF16 cast のテストを既存のカバレッジ範囲に収束、アサーション範囲は拡大しない。変更はセマンティクスに触れず、生成される命令シーケンスのみを動かし、影響範囲は量子化 cast へ向かうすべての BF16 計算パスである。

出典：https://github.com/tile-ai/tilelang/pull/3595

1.3 メインリポジトリ：展開パスが空の stepped ループを保持、ROCm の Select を逐 lane 下降に変更（#2887）

10-21 19:20 にマージ。ループ展開パスは従来、trip count が 0 の stepped ループを空殻として消し、後続パスが見るプログラム構造を変えていた；修正は展開過程中にこの種の空ループを保持するよう変更。同じコミットで ROCm 側のベクトル化 Select も変更：逐 lane 下降に変更し、グループ全体の下降がサポートされないターゲットで失敗するのを回避。二つの変更は一方が IR 構造、他方がバックエンド下降で、同じコミットにまとめられていることは、同一の再現シナリオから導かれたことを示す。

出典：https://github.com/tile-ai/tilelang/pull/2887

1.4 メインリポジトリ：ソフトウェアパイプラインが推移的コピー依存を保持、スレッドドメインが領域競合判定に参加（#2822）

10-21 18:13 にマージ。パイプライン計画は従来、直接依存のみを追い、間接（推移的）コピー依存は計画段階で失われ、dependent copy の待機がそれに伴って削除されていた；同時に物理領域競合チェックは計画と下降の両側でそれぞれ別の基準を持っていた。修正は後方 worklist でスカラーと buffer コピー依存を同時に追跡し、計画と下降が同一の物理領域競合チェックを共有、リプレイバインディングをスコープ内に保持、推移的生産者、strided alias、順序 TMA フォールバックパスのカバレッジを補完。第二のコミットはスレッドドメインを領域競合判定に導入：アクセスをまず実体化スレッドドメインへ展開してから領域を比較し、互いに素な共有メモリスライスがなおパイプライン可能に、同時にスレッド間依存と strided バッファの物理的重なりを保持；同一のドメインをパイプライン計画、依存検証、buffer バージョニングに使用。

出典：https://github.com/tile-ai/tilelang/pull/2822

1.5 メインリポジトリ：cast のソース/ターゲット/丸め三組み合わせの事前検証（#3350）

10-21 13:49 にマージ。round は明示的に列挙された組み合わせでのみ降格可能：PTX cvt.rs は f32 ソース、32 ビット rbits オペランド、特定のパッキングターゲットを要求する。その他の組み合わせは従来ブランチディスパッチ時に見逃され、丸め注釈がそのまま静かに消えていた。スカラーループは元々これらの組み合わせを拒否するが、ベクトル化ループは拒否しないため、同じ cast が二つのループ形態で異なる動作をしていた。典型例は f32→E8M0：その helper は正の無限大へ丸め、丸め引数を一切受け付けないが、ベクトル化ブランチは round を読んでいなかった。現在はディスパッチ前に不正な組み合わせを統一的に拒否し、どのブランチも注釈を失えなくなった。付随テストは rbits を実際に受け付ける rs モードにのみこの引数を渡す。

出典：https://github.com/tile-ai/tilelang/pull/3350

1.6 メインリポジトリ：arch なしの CUDA target は sm_50 を静かに埋めず拒否（#2860）

10-21 13:32 にマージ、1 ファイル、#1049 を修正。CUDA toolkit はあるが利用可能な GPU がないマシンでは、arch 未指定の CUDA target が裸の cuda に退化し、TVM がその後 arch=sm_50 を静かに埋め、コンパイルが誤った SM まで進んでしまい、全過程で診断が一切なかった——これはまさに tilelang.compile(func) に target="auto" を組み合わせる罠である。修正は _cuda_target_from_arch にあり：自動検出と明示的 target="cuda" が共有する唯一の入口で、実行可能なエラーを投げ、エラー内で明示的 arch の二つの書き方（{"kind":"cuda","arch":"sm_90"} または TILELANG_DEFAULT_TARGET）を示す。headless コンパイルは具体的な arch さえ与えれば引き続き利用可能で、codegen と nvcc は toolkit のみに依存し、デバイスアクセスはカーネル起動まで遅延されるためである。PR の過程で一時的に GPU なしの単体テストを三つ追加したが、最終コミットでそれらを撤下し、変更は入口検証のみとなった。

出典：https://github.com/tile-ai/tilelang/pull/2860

2.3 メインリポジトリ昇騰：PTO 上の warp_reduce_max/min の整数符号性修正（#3582）

10-21 10:21 にマージ。PTO の pto.redux_max/min は型付き整数を拒否する。PTOAS は符号性のないキャリアに明示的な signedness を要求するため、int32/uint32 の T.warp_reduce_max/min はコンパイルに直接失敗し、「requires signedness=’signed’ or ‘unsigned’ for integer values」と報告される。修正では warp_reduce_sum/max/min を一律に contrib.ptodsl の tl.redux_* ラッパー（現在はエクスポート済み）経由にし、ラッパーがキャリアと符号性を提供し、AscendAllReduce の方式に従って value dtype にゲートを設ける。問題票はメインリポジトリ #3541 と PTOAS #1579 を引用している。検証は二層：op × dtype グリッドの lower-only codegen テスト、および疎なデュアルターゲット（ascend/pto）実行テスト——≥2^31 の uint32 レーンで符号性の誤りを直接露呈させる。

出典：https://github.com/tile-ai/tilelang/pull/3582

2.4 昇騰リポジトリ：32B 未満のコンパクト行間隔ソースが表現できず、keepdim reduce 出力が乱れる（#1795）

10-21 17:15 にマージ、2 ファイル +302/-3、#1682 を修正。今回の調査期間で最も技術的難度が高いコミットである。根本原因はテンプレート層にある：copy_ub_to_gm は無条件にマルチ burst の DataCopyPad を生成するが、MTE3 エンジンが実装するのはシステムレベルの「UB 細行を 32B スロットで格納する」規約——ソースアドレスは burst ごとに ceil(blockLen/32) + srcStride 個の 32B ブロックだけ進む。32B 境界で行を書くプロデューサにとっては正確に一致する。しかし T.reduce_max の (M,1) fp32 出力は V-pipe でコンパクトに書き込まれ、行間隔はわずか 4B で、エンジンには表現できない。実測では 2 番目の burst が element 1 ではなく element 8 を読んでいた（[127, 1151, 71, 199] のうち 1151 はまさに element 8 の値）。書き込み側に問題はなく、誤りは DMA の読み取り元アドレス列にある。修正は二半分：両側とも packed かつ total ≤ 65535 の場合は 1 本のフラットな単一 burst（M×L バイト）に折り畳む（「単一 burst の長さは任意」という契約を利用）。表現不能な非 32B 倍数の行間隔は trap() で明示的に中止し、コンパイル時 if constexpr ガードで守り、32B 倍数と 32B 未満スロット配置では追加コードを生成しない。なぜ降級しないのか：bisheng のクロスパイプライン自動同期は直線的な intrinsics のみをカバーし、DataCopyPad を条件分岐で包んだり、兄弟分岐に GM スカラー書き込みを置いたりすると、bisheng が不正な同期コードを生成してデバイスデッドロックを引き起こす（実測では行ごとの DMA を実行時分岐で包むと aicore 例外が発生した）。14 のテストケースが flat/multi 経路、keepdim reduce の再現、UB ループ再利用、表現不能な pitch の正当な単一 burst 形式と明示的中止をカバーする。テスト環境は Ascend910 A3（dav-c220）/ CANN 9.0.0 のローカルビルドである。PR の自述は二つの境界を残している：32B 未満のコンパクト行間隔で行間隔付きの目的（例：(M,1) fp32 を広いテンソルのある列に書き込む）は依然スロットステップで進む；blockCount > 4095（12 ビットフィールド）は依然静かに切り捨てられる（4200 行の実測では先頭 104 行のみコピーされた）。別途 issue を立てる予定である。

5. トレンド観察

コンパイラ欠陥の性質が「計算ミス」から「ターゲット選択ミス」へ拡大。 今期のメインリポジトリの8件のマージのうち、4件が変更したのは「コンパイラが自分が何をしていると思っているか」である：arch なしの CUDA target が静かに sm_50 に退避（#2860）、cast の丸め注釈が分岐ごとに静かに破棄（#3350）、バッチ縮約が最初の出力ブロックのみ処理（#3070）、パイプライン計画が推移的依存を喪失（#2822）。これらの共通点はエラーを報告せず、特定のサイズや特定のループ形態でのみ信頼できない結果を出すこと——クラッシュよりも特定が難しく、プロジェクトが機能拡張よりも静かな正確性を優先していることも示している。

昇騰ラインのボトルネックはメモリモデルとランタイム境界へ移行。 32B 未満のコンパクト行間隔は DMA で表現できず、明示的中止しかできない（#1795）；キャッシュ並行性はアトミック公開に変更し削除復元を補完（#1903）；PTO の整数符号性はラッパー層で補完する必要（#3582）。これら3件はいずれも「オペレータ追加」ではなく「既存オペレータを境界条件でエラーにしない」ことであり、DeepGEMM ヒューリスティック整合のマージと合わせて、昇騰側は能力カバレッジからエンジニアリング信頼性へと転換しつつある。

分析機関が TileLang を昇騰可用性の判断基準とし始めた。 SemiAnalysis は「6つのリポジトリのうち当時利用可能だったのは TileLang のみ」で DeepSeek の昇騰サポートの完成度を定義しており、これはどの単独の技術ブログよりも TileLang の国産算力ナラティブにおける位置——実験的 DSL からデフォルトのキャリア層へ——をよく示している。同じレポートは逆方向のシグナルも示す——最適化はスーパーノードに集中し、x86 ホストサポートは依然不完全で、汎用性は性能に後れを取っている。

アテンションスタックの重心が推論フォワードから訓練バックワードへ移動。 TileOPs は1日で MLA プレフィルバックワードの op 層、SM90 warp 特化 kernel、データ取得順序最適化を補完し、さらに GQA バックワードのグループ KV head 処理を加え、昇騰側の先月以降のバックワードオペレータ補完（indexer_bwd、SiTU-GLU バックワード、WY fast バックワード）と完全に同方向である。訓練側の TileLang カバレッジは体系的に補完されつつある。

SM89 は「動く」から「チューニング」へ。 FP8 BMM タイル、W4A16 の M 上界、ページド DSA、NSA top-k の4ラインが同日に手を入れられ、いずれもシングルカード実測と「普遍的な優位性を構成しない」といった限定句を付している。コンシューマ向けおよびシングルカード推論シナリオが性能目標の一つとなり、同時に著者のベンチマーク基準に対する自己規制が明らかに厳しくなっている。

スケジューリングと正確性の分業が TileFoundry とメインリポジトリの間で明確化。 メインリポジトリは引き続きセマンティクスと正確性を厳格化し、TileFoundry 0.0.3 は「どの命令を選ぶか」を agent に、「セマンティクスを保証する」ことをコンパイラに委ね、H200 と Apple AMX の2つの例で再現可能な数字を示した。この分業が安定すれば、TileLang エコシステムには「言語層が正確性を守り、agent 層が性能を競う」二層構造が生まれるだろう。
