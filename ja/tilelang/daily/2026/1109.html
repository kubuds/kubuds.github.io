本日の重点

このウィンドウの産出の重心は「アナライザ」であり、「ジェネレータ」ではない。TileFoundry は3日間で5筆をマージし、そのうち3筆は元々作者の頭の中にしか存在しなかった不変条件を検査可能なオブジェクトとして書き出したものだ。#291 は TMA コピーの共有オペランドを async-proxy セマンティクスに入れ、各 TMA ロードに mbarrier ワードを割り当て、クロス CTA シナリオで「ある CTA が非同期プロキシ書き込みを行い、別の CTA が順序なしで同じグローバル要素を読む」プログラムを拒否する。#293 は配置値セマンティクスを定義し、Split / Broadcast / Varying / Partial の4状態、B ⊔ V = V のマージ規則、Reshard のターゲット検証を契約として書き下し、同時にサポートされなくなった Dynamic 属性を削除した（64ファイル、+1165 から -536）。#301 は「スケジュールが古いデータを上書きする前に、依然として古いデータを読む必要がある領域を先に並べなければならない」を扱い、順序を LivenessMetadata.orders に記録し、並べられなければ AnalysisError を投げる。残る2筆（#290、#288）はアナライザ自身の近似を修正したものだ。

第二の事柄はパイプライン化だ。72時間で71筆のマージのうち、TileOPs が33筆、topa が15筆で合計68%を占める。40筆は同一著者がコミットした。同時期の3筆の CI 変更（#2849 は夜間ベンチマークの性能ギャップキューを wiki に書き出し、#2852 は Perf Tracker プロジェクトに同期し、#2856 は追いついたオペレータを自動的に Done へ移動する）と相まって、性能作業はすでに「夜間ベンチマーク → ギャップキュー → 単一オペレータ1ラウンド → レビュー → マージ」の閉ループを形成している。topa リポジトリの2日間で15筆（topa hunt、topa round start、topa round status、topa review prepare）はまさにこの閉ループのコマンドラインシェルだ。効率向上は本物だが、リスクも本物だ。単一著者に単一レビューが重なると、パイプラインは一人のパイプラインへと退化してしまう。72時間でレビュー中の96筆の PR のうち、依然として59筆が tilelang メインリポジトリに滞留しており、レビュー帯域が次のボトルネックだ。

第三の事柄は昇騰にある。11-07 の1日で、あるアカウントが14件の issue を立て、同日に13件の修正 PR がレビュー中となった。gemm_blockscaled の位置引数と公開シグネチャが分岐し、policy が clear_accum に移されてしまった（#3857）。vcvt の bf16 から f16 への変換で round と sat の引数が入れ替わった（#3829）。vdupv が未知の pos に遭遇すると黙って HIGHEST にマップする（#3832）。fp4 の T.fill が SimdVF 内でゼロ除算クラッシュする（#3852）。kernel キャッシュキーが ASCEND_NPU_ARCH と PTO ツールチェーンを欠落させ、あるアーキテクチャの成果物を別のアーキテクチャに再利用する可能性がある（#3853）。これらの欠陥に共通する形態は「宣言はサポート、実装は分岐」だ。HCU_MCPU_SET にあるアーキテクチャが、C++ バックエンドに必ずしも分岐があるわけではない。海光 gfx928 の新しい issue（#35）も同じ形態だ。一方、同時期の日次テスト3060項目はすべて通過しており、通過率がこれらの組み合わせをカバーできていないことを示している。テストの数は形状の組み合わせの差分検証の代わりにはならない。

ニュース側で TileLang に関連するものは2件のみだ。摩尔線程は11-06に MTT S5000 と MUSA に基づく3兆パラメータの Kimi-K3.1 Pro の Day-0 適配を完了したと発表し、移行パスには TileLang-MUSA が明記されている。もう1件は Foro3D の11-06の転述記事で、DeepSeek が昇騰 950DT 上で TileLang スタックを用いて8兆パラメータの V5 を訓練するとしている。DeepSeek 公式はこの計画を公表しておらず（現役最新は V4.1 シリーズ）、伝聞として記録するにとどめる。RISC-V の4つの情報源は72時間変化がなく、TVM 路線と MLIR 路線はいずれも11-05以前の引用のまま止まっている。

1. 中核プロジェクトの進展

1.1 メインライン：CuTeDSL の grid 同期を起動ごとの workspace に変更し、マルチストリーム並行がクロストークしなくなる（#3868）

11-08 18:00 にマージ。CuTeDSL の sync_grid() は元々 barrier カウントと世代をモジュールレベルのグローバル（__grid_sync_ctr、__grid_sync_gen）に置いていたため、同一 kernel を 2 つのストリームで同時起動すると同じ barrier を共有してしまう。2 つの grid の到達が統合され、ある起動が自分の block の全部到達前に解放される可能性があり、残留カウントは後続の起動を吊るす。H200 NVL 上で単発 17.4 ミリ秒、ペア 17.8 ミリ秒であり、cooperative launch が確かに並行していることを示す。修正方法は inline PTX で cooperative_groups::details::sync_grids を再現する。barrier ワードはドライバが各 cooperative launch に提供する grid workspace の barrier フィールドから取り、アドレスは %envreg1（高半）と %envreg2（低半）から来る。各 block の thread 0 が 1 回 atom.add.release.gpu を行い、block 0 は 0x80000000 - (nblocks - 1) を加算、残りは 1 を加算し、その後 ld.acquire.gpu でスピンして bit 31 の反転を待つ。状態は起動ごとに隔離されるため、並行起動は互いに影響しない。回帰テストは main ではハングする（300 秒で kill）が、修正後は通過する。作者は同時に CUDA バックエンドを対照として保持しており、後者は常に正しい。

出典：https://github.com/tile-ai/tilelang/pull/3868

1.2 メインライン：CuTeDSL の符号付き整数切り捨てを arith.divsi セマンティクスに従い修正（#3551）

11-08 07:48 にマージ。CuTeDSL は符号付き TIR の DivNode に対して Python の床除算を発行していたため、実行時の T.truncdiv(A[i], 3) は -7 で -2 ではなく -3 を返し、後続の floor/ceil 修正がこの商に基づいて計算を続けることで誤差が拡散する。修正方法は、符号付きスカラーとベクトルに tl.truncdiv（基盤の MLIR arith.divsi）を発行し、純粋な Python 入力は正確な整数演算を通し、ベクトルストア経路と符号なし lowering は変更しない。回帰 25 例で、int8/int16/int32/int64、スカラーとベクトル、負の除数、整数極値、および「商×除数＋余数＝被除数」をカバーする。報告者は issue #2973 の議論で独立に CPU リファレンスと MLIR で検証し、純粋な Python % の境界を指摘しており、この意見はそのまま実装に取り入れられた。

出典：https://github.com/tile-ai/tilelang/pull/3551

1.3 メインライン：CuTeDSL が 63 ファイルのサンプル欠落を一括補完、SM120 ブロックスケーリング MMA を含む（#3685）

11-07 18:59 にマージ、+7075 から -394、63 ファイルで、本期最大の一筆である。新規範囲には、warp vote、match とビット検索、ブロック述語 barrier、明示幅のロードとストアおよびキャッシュヒント、NaN 伝播の min/max、TMA と cluster コピー（multicast、store_cluster、gather4、scatter4）、SM120 のブロックスケーリング MMA（mxf4nvf4）と付随する NVFP4 GEMM サンプルが含まれる。同じ一筆で warp specialization の古い問題も修正した。pipeline の前に挟まれた T.fill が producer/consumer 分岐に移動された後、ループや条件を隔てていても毎回のイテレーション後に再実行され、当該ラウンドの T.clear の結果を上書きしてしまう問題である。

出典：https://github.com/tile-ai/tilelang/pull/3685

1.4 メインライン：CUDA 単発 kernel 起動に名前を付け可能、profiler で段階を区別可能（#3816）

11-06 17:45 にマージ。1 つの PrimFunc 内の複数の T.Kernel は元々自動生成の名前プレフィックスを共有していたため、profiler で段階を区別できなかった。オプションの name= パラメータを新設し、T.Kernel(grid, threads=128, name="compute_stats") と T.ClusterKernel の両方が対応する。生成されるデバイスシンボルは compute_stats となり、_kernel サフィックスは付加されない。名前は tl.kernel_name アノテーションを通じて LowerOpaqueBlock を通過し、SplitHostDevice がデバイス関数を生成する際に消費される。明示名は非空の ASCII 識別子として検証され、重複名とホスト関数の衝突は既存のグローバルシンボル供給に委ねられ、未命名の起動は旧命名を維持する。ドキュメントは命名、ホスト呼び出し対象、不正入力、eager JIT、共有メモリと cluster 起動を同期してカバーしている。

出典：https://github.com/tile-ai/tilelang/pull/3816

1.5 メインライン：マルチソースキャッシュディレクトリ、任意読み取り、最初のみ書き込み（#3807）

11-06 13:31 にマージ、+593 から -288、18 ファイル。TILELANG_CACHE_DIR はコロン区切りの複数ディレクトリをサポートし、例えば /cache/read/and/write:/cache/readonly/A:/cache/readonly/B のように指定でき、コンパイル産物は任意のディレクトリからヒットできるが、書き込みは最初のディレクトリのみ行う。これはクラスタにおける「共有読み取り専用キャッシュ + ローカル書き込み可能レイヤ」という一般的な形態に対応し、一批のビルドが同一のオペレータキャッシュを共有できる。著者は境界を明記している：CuTeDSL バックエンドは読み取り専用ディレクトリ上で問題が発生する可能性がある。

出典：https://github.com/tile-ai/tilelang/pull/3807

1.6 昇騰：Z3 スケジューリングのグローバルロックを除去、コールドコンパイルの最遅項目が 37.3 秒から 25.6 秒に短縮（#3812）

11-06 18:17 にマージ。Ascend の Python スケジューリングコールバックは、すべての Z3 solve を 1 本のグローバルロックで直列化していたが、各呼び出しはすでにプライベートな Z3 context を保持していた。除去後、独立したコンパイルスレッドが並行スケジューリングできる：8 スレッド、各 kernel 8 配置のコールドコンパイルバッチ処理において、SwiGLU backward が 33.1 秒から 30.0 秒に、MoE gate forward が 37.3 秒から 25.6 秒に短縮された。検証は 884 項目の既存 Ascend auto-schedule CPU テスト、64 個の並行リクエストが直列結果と一致すること、および 16 個のサンプリングされた SwiGLU backward と MoE gate 配置が変更前後で完全に同一のスケジューリング、ソースコード、デバイス ELF を生成することである。

出典：https://github.com/tile-ai/tilelang/pull/3812

1.7 昇騰：access_ptr 領域の修正、行跨ぎと転置ビューで DMA 依存関係が失われなくなる（#3805）

11-06 12:08 にマージ。連続 SIMD ロードが行を跨ぐ場合、または転置ビューを使用する場合、access_ptr が再構築する領域で入力 DMA 依存関係が失われ、AutoSchedule が load を copy より前にスケジューリングできるようになり、InsertSync も MTE2 から V への同期を挿入しなくなっていた。修正方法は保守的なポインタ領域再構築を再利用する：行跨ぎ時には開始オフセットを含め、再構築できないレイアウトはバッファ全体にフォールバックする；単純な一次元正ストライドの高速パスは維持する。リグレッションは 2 つの行跨ぎユースケースと 1 つの転置ビューをカバーし、AutoSchedule の有無それぞれで「DMA → set/wait → load」の順序とイベント ID の整合性を検証する；171 項目の関連ホスト側 IR テストが通過し、デバイス実行は未テストである（著者はこの境界を明記している）。

出典：https://github.com/tile-ai/tilelang/pull/3805

1.8 サンプル：sm_12x が利用可能な動的共有メモリに応じてタイルを選択、RTX PRO 6000 で全通過（#3845）

11-08 06:25 にマージ。dim=128 の block-causal varlen ユースケースは従来 128x128 タイルに固定されており、フォワードには 128 KiB、dK/dV には約 192 KiB が必要であったが、sm_86/89/120 の動的共有メモリ上限は約 99 KiB であり、起動時に直接 Failed to set the allowed dynamic shared memory size が報告されていた。get_max_dynamic_shared_memory() から block_size を取得するように変更：データセンターカードは 128x128 を維持し、共有メモリの小さいデバイスは 64x128（約 96 KiB）を使用し、block_size が dllm_block=64 で整除可能であることを維持する。RTX PRO 6000（sm_120）では CUDA と CuTeDSL がそれぞれ 209 passed、26 skipped、0 failed；H200 NVL（sm_90）では 128x128 の 2 例が通過。著者はこれが #3701 に残された最後の失敗サンプルであると述べている。

5. トレンド観察

第1に、自動化の閉ループはすでに形を成しているが、閉ループの重心は「コードを書く」ことから「契約を定める」ことへ移っている。topaの15件にはカーネルコードが一行もなく、すべてがラウンドルール、レビューチェックリスト、PR本文の形式、worktreeのクリーンアップであった。TileOPsの33件の大部分は「目標項目に従ってパラメータを1つ変更し、A/Bの組を提示する」ものであり、TileFoundryの5件は「配置の等価」「TMAの完了」「上書き前の読み取り」とは何かを定義するものであった。この3つを重ねると完全なパイプラインになる。夜間のベンチマークで差を発見し、キューがオペレータを割り当て、agentがTileFoundryのスケジューリング空間で変更し、レビューがチェックリストに従って数字を照合し、マージ後に自動でクローズする。このパイプラインの生産効率はすでに数字に表れている（72時間で71件）が、「契約が十分に明確に書かれているか」に極めて敏感である。今日#2867が「目標項目を下回る」と注記されながらマージされたこと、#301が順序を決められないときに推測せずエラーを選んだことは、いずれも契約が働いている姿である。

第2に、昇騰のボトルネックは「コンパイルできるか」から「宣言と実装が一致するか」へ変わった。14件のissueのうち「ある機能をサポートしない」というものは一つもなく、すべてが「サポートを宣言しているが実装が別の道を辿っている」ものである。HCU_MCPU_SETにはgfx928があるがC++に分岐がない（海光も同様）、T.simd.vcvtのドキュメントにはint32/int64からf16と書かれているが実装は拒否する、annotate_unlimit_memoryのエラーメッセージはユーザーに"shared.ss"を渡すよう促すが関数自身が拒否する、gemm_blockscaledの位置引数と公開シグネチャが分岐している。こうした欠陥の共通の修正法は機能を追加することではなく、「宣言」と「実装」を同じ表に置いて生成的な検査を行うことである。例えばHCU_MCPU_SETからバックエンドが必ずカバーすべきアーキテクチャ一覧を生成し、intrinsicレジストリからdtype/ビット幅のサポートマトリクスを生成する。これを実現するまで、3060項目すべて通過したテストレポートは「テスト済みの組み合わせに問題はない」ことしか示せない。

第3に、CuTeDSLは現在「機能カバレッジはCUDAに接近し、正確性の境界はまだ収束していない」段階にある。#3685は一度に63ファイルを補い、cluster TMA、SM120ブロックスケーリングMMA、Philox、warp voteといったCUDA側にすでにあった能力を補完しており、機能面の整列がほぼ完了したことを示している。しかし同じ期間の欠陥はすべて境界上にある。マルチストリーム同時実行下のgrid barrier（#3868）、符号付き整数除算（#3551）、符号なしアトミックと符号なしバッファ（#3874/#3875/#3876）。これらはいずれも「未実装」ではなく「実装はあるがセマンティクスがCUDAと一致しない」ものである。利用者への実際の助言は次のとおりである。CuTeDSL経路はサンプルの実行と開発に適しており、本番カーネルはバックエンドを切り替える前にCUDAバックエンドとの要素ごとの差分を一通り取るべきで、特に負数の除算、符号なし比較、マルチストリーム同時実行が関わるシナリオでは注意が必要である。

第四に、性能最適化の記録方法が変わりつつある。TileOPs のこの一連の PR の特徴は、各コミットが「どの op、どのベンチマーク、結果が基準を満たしたか、根因は何か」を明確に記述している点にある。#2868 は 900444 個のセクタ対 501760 個の書き込みという具体的な数字を示し、#2869 は 16 個のメモリ配置のうち 12 個が後れを取っている分布を示し、#2855 は 12 ラウンドのウォームアップ、各ラウンド 10 回の呼び出しの中位数を示し、さらに「実行順序効果を制御していない」と自ら宣言している。このような記述方法により、「基準未達」でもマージできる（#2867）。読者がそれが価値あるかどうかを判断できるからだ。これに対し、「X% 向上」とだけ書く PR は、レビュー時に kernel が速くなったのか測定が変わったのかを区別できない。

最後に RISC-V ラインである。四源巡検は 72 時間変化なし：kubuds/tilelang-riscv-kubuds の 2 つの kubuds- ブランチ、RuyiAI-Stack/tilelang-riscv の MLIR 路線、TongmingLAIC/tilelang-riscv インデックスページと TongmingLAIC/tilelang-tpu の SOPHGO ブランチはいずれも元の参照のまま停止している。これは主線のリズムと対照をなす。GPU 側の agent 化パイプラインはすでにイテレーションを「日」単位に圧縮しているが、RISC-V 側は依然として「週」レベルの人手による推進である。両ラインの差はエンジニアリング量になく、差を自動発見し、自動検証し、自動的にキューに並べる回路があるかどうかにある。
