今日の重点：メインリポジトリの JIT にプロセスレベルの並列コンパイルを追加、GIL によるスレッドプールの制限を回避

#3903 は 11-23 11:57 にメインブランチへ取り込み、6 ファイルを変更、552 行追加、100 行削除。

tilelang.par_compile() と kernel.par_compile() にオプション引数 executor="process" を新規追加。提案に明記された動機は：スレッド式並列は Python 側の負荷が偏るコンパイルワークロードで GIL の制限を受けること。

プロセスモードでは、親プロセスがまず target、実行バックエンド、pass 設定、キャッシュルートディレクトリを正規化する。メモリまたはディスクキャッシュに既にヒットした設定は worker を起動しない。未ヒットのものは key で重複排除してから配分する。

各 worker は KernelCache.compile_to_disk() で結果をディスクキャッシュに書き込み、公開済みの cache_path を返す。worker の例外型と traceback は IPC を跨いで保持される。

親プロセスは KernelCache.load_published_entry() で直接ロードし、直列コンパイルにはフォールバックしない。エラー時は既にキューに入った future を即座にキャンセルする。

ディスクキャッシュをサポートしないバックエンドは worker 起動前に拒否される。例えば TorchKernelCache（supports_disk_cache = False）。これによりグローバルキャッシュ状態を変更しない。

スレッドモードは依然デフォルト値。プロセスモードはキャッシュの有効化を要求し、スクリプトに if __name__ == "__main__": の保護エントリを要求する。

提案には昇騰上で 64 プロセスによる検証が記録され、128 組の SwiGLU と MoE 設定をカバー。回帰テストは testing/python/jit/test_tilelang_jit_parcompile.py に配置。ユースケースにはカスタム TILELANG_CACHE_DIR 下のプロセスコンパイルと重複排除を含む。

情報源： https://github.com/tile-ai/tilelang/pull/3903

今日の重点：TileOPs が1日で18件、主軸は 0.1.15 の性能退行を 0.1.12 に戻すこと

11-23 の終日で TileOPs は18件をマージした。同日に新規起票された作業項目 #3133 には目標が明記されている：初回の TileLang 0.1.15 ナイトテストで 0.1.12 より遅かった25行を取り戻すこと。

3件のコミットタイトルは直接「0.1.12 の時間に復元」と書かれている。#3138 は MXFP4 レジスタフラグメントカーネルを復元する。#3136 は MaskedScatterFwdOp で 0.1.15 に新たに追加された境界チェックを除去する。#3131 は HyperConnectionHeadFwdOp に対して同様の処理を行う。

さらに3件は外部実装との差を縮めるものだ。#3099 は GatedPoolCompressFwdOp の DeepSeek-V4-Flash デコードにおける SGLang との差を縮める。#3097 は HyperConnectionPreFwdOp のデコードと中程度長のプレフィルにおける差を縮める。#3101 は DSADenseFwdOp の行を常駐 CTA 上で走らせ、行内のデッドテールブロックをスキップする。

メモリアクセス側で変更されたのはデータ取得の粒度だ。#3139 はページドキャッシュの行全体を、ベクトルごとに16バイトでセクターを満たすストアとして取り出す。#3140 は SSDRecurrentFwdOp の状態を16バイトレーンベクトルで流動させ、各行を warp shuffle で合計する。

量子化と要素ごとの処理が各1件。#3137 は16ビットゲート付き tanh-GELU を x / (1 + exp2) として計算し、float32 内で1回だけ丸める。#3132 は FP8 のグループ最大値を入力 dtype 内でリダクションし、不要な clamp を1回除去する。

モデル側が2件。#3129 は DeepSeek モデルを DeepSeek-V4-Flash と命名し、generate が max_seq_len を超えないよう制約する。#3130 は DeepSeek TileKernels を FP8、FP4、hyper-connection オペレータの隣に並べて一緒に計時する。

#3135 はナイトリーの性能退行を Perf Tracker ダッシュボードに登録する。#3124 と #3125 は調査期間の起点から24分後に主干へ入り、それぞれ 0.1.15 上の並行チューニング付きコンパイルとナイトベンチマーク参照の修正を担当する。

1.1 ナイトリーホイールを Dist ジョブによる公開に変更、GitHub Releases と華為雲 OBS のデュアルチャネル

#4411 は 11-23 21:30 に主干へ入り、2ファイルを変更し、414行を追加、11行を削除した。提案には背景が説明されている：旧 tile-ai/tilelang-nightly パイプラインは停止済みで、OBS はこれまで中国大陸からのダウンロードに接続されていなかった。

方法は Dist ジョブで既にビルド済みのホイールを各プラットフォーム間で再利用することだ。test-wheels-gpu 通過後、各プラットフォームのホイールはそのまま公開へ進む。schedule と workflow_dispatch でトリガーされたビルドには日付とコミットサフィックスが付き、スイッチは TILELANG_BUILD_WHEEL_WITH_DATE=ON である。PyPI 公開バージョンの形式は変わらない。

2つの公開チャネルは互いに独立している。publish-github-nightly はホイールを tile-ai/tilelang-nightly の GitHub Releases へ公開する。同時に SHA-256 付きインデックス https://tile-ai.github.io/whl/nightly を更新する。NIGHTLY_GITHUB_TOKEN が未設定の場合、このチャネルはスキップされ警告が出る。

publish-obs はホイールとパーセントエンコードされた TileLang/index.html を obs://ascend-triton-open/TileLang/ へアップロードする。その後、匿名 HTTPS で可読性を検証し、失敗時は -acl=public-read にフォールバックする。インデックスは https://tile-ai.github.io/whl/nightly-cn に書き込まれる。

情報源： https://github.com/tile-ai/tilelang/pull/4411

1.2 レイアウトとシャーディングオブジェクトがプレースホルダ変数を自己保持、入力次元上限16を撤廃

#4416 は 11-23 21:07 に主干へ入り、23ファイルを変更し、607行を追加、583行を削除した。

従来、3つのレイアウト型はプロセスレベルの静的 tirx::Var シングルトンに依存していた。3つの型は tl.Layout、tl.Fragment、tl.PartialFragment である。シングルトンは InputPlaceholder(0..15) と ReplicationPlaceholder() である。

派生する問題は3つある。FFI シリアライズにはリフレクションアクセサを手書きする必要があった。入力次元が16にハード制限されていた。src/layout/ 以外の呼び出し元が共有グローバル Var を介して暗黙的に結合していた。

修正方法は TVM の tirx::IndexMap に合わせることである。LayoutNode は forward_vars_ を保持し、FragmentNode は replicate_var_ を保持する。両者は forward_index と forward_thread の前に SEqHashDef() で登録される。

これにより 2 つの JSON グラフインターフェースは直接シリアライズ可能となる。StructuralEqual と StructuralHash はアルファ等価性を備える。コンストラクタでは統一的に MakeLayoutVars(ndim) と MakeReplicateVar() を用いて正規変数を生成する。

情報源： https://github.com/tile-ai/tilelang/pull/4416

1.4 TVM サブモジュールが Z3 の誤証明 2 件を修正、メインリポジトリの bump 追随は審査中

TVM サブモジュール tilelang_main ブランチでは調査期間内に 2 件がマージされ、いずれも同一の作者がコミットした。

#97 は 2 件の信頼性欠陥を修正する。其一、VisitShiftOp が push() していない共有ソルバ上で solver->add を実行し、あらゆるシフト式がシフト量 b を恒久的に制約してしまう。その結果、b < 0 または b >= 64 の外側スコープでは、後続の述語が証明可能と判定されうる。

其二、DivNode と ModNode はゼロ方向への切り捨てを採用しているが、Z3 の Int に対するネイティブな / と % はユークリッド意味論である。したがって CanProve(truncmod(a, 4) >= 0) は a が負になりうる場合でも偽成功する。修正方法は floordiv と floormod で対称にエンコードし、a >= 0 で分岐して式を選ぶことである。

#96 は定数の符号付き右シフトを単独で修正し、整数演算に変更する。メインリポジトリ側の追随 #4482 は依然として審査中である。

情報源： https://github.com/tile-ai/tvm/pull/97

2.1 PTO ジェネレータがループキャリーのスカラーを補完、5 つの DeepGEMM ケースがコンパイル回復

#4418 は 11-23 10:17 に主干へ入り、1 ファイルのみ変更、23 行追加、11 行削除。

問題は CANN 9.2.0 に同梱の PTODSL（PTOAS 0.65）にある。5 つの DeepGEMM の scale テールと group padding ケースがコンパイル失敗し、いずれも grouped scale 変換内の同一ループに到達する。MLIR が生成された scf.while を拒否し、operand #0 does not dominate this use を報告する。

カーネルは group_start を 0 で初期化し、その後 if lo > 0 内で更新する。初回イテレーションでは分岐が選んだ値を使用する必要がある。PTODSL の活性解析はこの依存を漏らし、分岐内の値をそのままループ入力として使用する。lo == 0 の場合、その値は未定義である。

修正方法は PTO コードジェネレータが while ヘッダを出力する前に、ループキャリーのローカル量を収集することである。スコープ内に既に存在し、かつループ本体で代入される通常のスカラーについて、それぞれ裸の名前読み取りを 1 回出力する。生成される PTODSL はループ入口で group_start、lo、num_ranges の 3 行の読み取りが増える。

情報源： https://github.com/tile-ai/tilelang/pull/4418

2.3 昇騰メインリポジトリは審査中10件、新規issueはドキュメントと実装の不一致が大半

メインリポジトリでは調査期間内に新規issueが9件作成された。うち6件はドキュメントまたはエクスポートリストと実装の不一致、3件はコンパイル失敗である。

不一致類はいずれもAscendターゲットを指す。#4474 は、ドキュメントに自動検出順序がCUDA、HIP、Metalと書かれているが、実際にはAscendも登録されていると指摘する。#4479 は、tilelang.ascend.language.vmi が vsub を定義しているのに __all__ に入れていないと指摘する。#4477 のPTOエラーメッセージは unit_flag_ctl と l2_cache_ctl を使用している。実際のパラメータ名は unit_flag_ctrl と l2_cache_ctrl である。

#4480 は、Ascendのサンプルが依然として target="ascend" をハードコードしており、TILELANG_DEFAULT_TARGET=pto を設定してもサイレントに無視されると指摘する。#4476 は、T.copy の transpose パラメータのドキュメントにはGMからL1へのみ記載されているが、実際にはL1からL0AおよびL0Bのパスも認識されると指摘する。#4475 は、sfu_precision.h が2つのAscendコードジェネレータで共用されると主張しているが、AscendC側ではコピーされ、不正値の処理が失われていると指摘する。

コンパイル失敗類は3件。#4483 のint64 T.atomic_or とuint64 T.atomic_add がCUDA上で失敗する。原因は一致する cuda::atomic_ref が見つからないことである。残り2件は1.3のbf16 sigmoidとbf16アテンションである。

サブリポジトリ tilelang-ascend では調査期間内に主干へのプッシュはなかったが、審査中PRに10件の更新があった。#2023 はAtlas A3（910Cと910_93）をcarver内で独立したチッププロファイルとして解析させる。#2032 は gemm_v0 にfp32テストマトリクスを追加する。#2029 から #2031 は3つのサンプルを上流と一致するソースパスへ移動する。サブリポジトリのデイリーテストは11-23に3120項目を実行し全通過を記録した。

情報源： https://github.com/tile-ai/tilelang/issues/4480

3.3 FlashQLA が sm120 上の共有メモリのコンパイラによる早期読み取りを修正

QwenLM/FlashQLA の #55 は 11-23 18:37 にマージされ、1 ファイルを変更、5 行を追加。

根本原因は PTX で確認済み。TileLang 0.1.12 の tl::mbarrier_wait は tl_templates/cuda/barrier.h に位置する。当該箇所のインラインアセンブリには "memory" clobber がない。

blackwell_sm120/fused_fwd.py において、S warpgroup（tx < 128）は静的共有メモリに一切書き込まない。それは g_exp_shared[block_S - 1] というコンパイル時定数オフセットのみを読む。use_initial_state=False に特化されると、nvcc または cicc は ld.shared.f32 を for i_s ループの外に持ち上げる。読み取られるのは未初期化の共有メモリである。

結果として、第 0 ブロック以降の状態誤差が大きくなる。未初期化共有メモリが NaN ビットパターンを含む場合、直接 NaN となる。

修正では torch.empty(...) と T.clear(h_fragment) をそのまま残す。その後、barrier 待機の後にブロック内フェンス呼び出しを1回挿入する。挿入位置は T.barrier_wait(bar_1, i_s % 2) の後。呼び出し形式は T.call_extern("void", "__threadfence_block") で、2つの warpgroup の両方に追加する。PTX 上では membar.cta として現れる。

検証環境は RTX 5090、CUDA 12.8、PyTorch 2.8.0+cu128、TileLang 0.1.12。

情報源： https://github.com/QwenLM/FlashQLA/pull/55
