1. 核心プロジェクト進展

1.1 メインリポジトリ：昇騰 PTO 実行ルーティング——ascend × pto 直結 PTO codegen（#3316）（10-15）

日付：2026-10-15　ソース：PTO 実行ルーティング（#3316）／ メインリポジトリ PR リスト

  • 実行ルーティング（#3316）：target="ascend" と execution_backend="pto" の組み合わせを実際に機能させる——明示的な PTO 実行バックエンドが、バックエンド解決の前にネイティブ Ascend ターゲットを PTO ターゲット変種へと特殊化し（arch などのターゲット属性を保持）、コンパイルはこれに基づいて PTO バックエンドと PTO デバイスコードジェネレータ（CodeGenTileLangPTO、すなわち codegen_pto.cc）を選択する。実装上は実行を認識するターゲット正規化フックを新設し、BackendContext の生成箇所に接続する。Ascend 専用の正規化器がマッピングを担当し、デバイスコード生成は PTO_CODEGEN と target.build.tilelang_pto_without_compile に切り替わる。
  • 経路セマンティクス（PR の挙動表）：ascend × auto は AscendC + TVM-FFI 経路を維持し、ascend × tvm_ffi / cython は AscendC を通り、ascend × pto と既存の target="pto" 簡略記法はいずれも PTO バックエンドを通る。ドキュメントには等価な環境設定として TILELANG_DEFAULT_TARGET=ascend に TILELANG_EXECUTION_BACKEND=pto を加える形が示されている。テストは直接的なコンテキスト解決、ターゲット属性の保持、キャッシュディスパッチ、環境変数による選択をカバーしている。
  • 連線：10-14 にマージされたサンプルターゲット選択（#3474、CI は ascend と pto の両ターゲットで全昇騰サンプルをそれぞれ一回ずつ実行）と、審査中の PTO ファミリー（tvm_ffi 実行バックエンド #3516、VMI ベクトル化 #3512、SS buffer #3514、部分 L0 コピー pitch #3511）に接続する——昇騰側の「二重経路併存」は「一つのターゲット、二つの実行バックエンド」へと向かいつつある。

1.2 メインリポジトリ：JIT がハッシュ化不可能なコンパイル時パラメータを拒否（#3417）；テストコンパイル時間の削減（#3517）（10-15）

日付：2026-10-15　情報源：JIT ハッシュ検証（#3417）／ テストコンパイル時間（#3517）

  • JIT がハッシュ化不可能なコンパイル時パラメータを拒否（#3417）：JIT 特殊化は、コンパイル時パラメータとデフォルト値がハッシュ化可能であることを要求するようになった——ハッシュ化不可能なデフォルト値は JIT ラッパー生成時に TypeError を投げ、明示的に渡されたハッシュ化不可能なパラメータはカーネル検索またはファクトリ実行の前に拒否される。これにより可変なデフォルト値が古いカーネルを黙って再利用することを防ぎ、遅延と即時の二つのパラメータ契約を一本化する。検証には hash() を使用する（ハッシュ化不可能な値を含むタプルを含む）。呼び出し形式キャッシュはまずハッシュ化可能性を確認し、その後に「前回呼び出しとの等価」というショートカットを行う。コンテナ内容の正規化を削除し、実行期のテンソルパラメータは引き続き特殊化キーに入らない。検証：ネイティブソースの再ビルドが通過し、パラメータバインディングおよび関連スイートは合計 91 件通過、スキップなし。
  • テストコンパイル時間の削減（#3517）：
    test_tilelang_issue_2994.py 内の四つの packed-type CUDA ソース補助関数は
    target.build.tilelang_cuda_without_compile（生成ソースのみを取得し、完全なビルドを行わない）を使用するよう変更された。これらの補助関数はもともと生成ソースのみを検査するものであり、通常のビルドオーバーヘッドを負わなくなった。

1.3 メインリポジトリ審査中：cumsum 共有バッファ warp 特殊化修正が新規発行（#3536）；PTO ファミリー七件が進行（10-15）

日付：2026-10-15　情報源：cumsum 修正（#3536）／ PTO tvm_ffi（#3516）／ VMI ベクトル化（#3512）／ SS buffer（#3514）／ 部分 L0 コピー（#3511）／ UB から L1 への部分コピー（#3530）／ PTO Ramp 値（#3535）／ SIMT VF アクセス（#3523）

  • cumsum 共有バッファ warp 特化修正（#3536、10-16 未明に新規起票）：warp 特化下では消費者スレッドが 128 から採番されるが、共有メモリスキャンテンプレートがスレッド区間の下限を受け取っていなかった——CumSum1D / CumSum2D は各消費者スレッドで早期リターンし、バッファは未書き込みのままとなる。修正ではスレッド区間の最小値をスキャンテンプレートに渡す（AllReduce は既にこの書き方）。HIP 側のスキャンテンプレートも同期修正（LowerSharedScan は両バックエンドで共有）。1D / 2D 共有バッファのパイプライン T.cumsum ケースを新規追加。検証：H100 上で 19 件通過（新規パイプラインケースは main 上で 2 例失敗）。#3528 の再現ケースは修正後 131072 項すべて正解（main 上では 129019 項が誤り）。#3528 を修正。
  • PTO ファミリ 7 件の進展：#3516（PTO ターゲット tvm_ffi 実行バックエンド）、#3512（T.Parallel から PTO VMI へのベクトル化）、#3514（SS buffer）、#3511（部分 L0 コピーの明示的 pitch）、#3530（NZ バッファの UB から L1 への部分コピー、新規起票）、#3535（PTO Ramp 値を型ごとにベクトル発行、新規起票）、#3523（SIMT VF 内ベクトル局所アクセス修正、新規起票）。

3. エコシステムと採用側

3.1 TileOPs：アテンション三連マージ——varlen GQA 集約、ページング GQA 全機能とページング KV 書き込み（10-15）

日付：2026-10-15　情報源：varlen GQA 集約（#2537）／ ページング GQA 全機能（#2516）／ PagedKVCacheWriteFwdOp（#2539）／ MoEGroupedGemmFP8 ドキュメント（#71）

  • varlen GQA 集約とパイプラインスライディングウィンドウ（#2537）：FP16 / BF16 / FP8 varlen GQA にオプションの FP32 ヘッド別 sinks を追加——sink は softmax 分母に入るスケーリング未適用・トランケート未適用の logit である。「アテンション集約」議題（#2269）の varlen 部分をカバーし、同時にパイプライン化スライディングウィンドウを統合。

3.2 TileOPs：foundry 性能三筆——W4A16 ロード再配列、sigmoid IEEE 除算回避、SM89 スキャン拡幅（10-15）

日付：2026-10-15　情報源：W4A16 先行ロード（#2586）／ sigmoid IEEE 除算回避（#2588）／ SM89 スキャン拡幅（#2574）／ TileOPs PR リスト

  • W4A16 重み先行（#2586）：GemmW4A16Kernel は従来 packed 重みの前に各 K タイルのアクティベーションをコピーし、warp 特化プロデューサがこの順序で発行して段階的に待機していたため、重みの DRAM からのロードが実際には K タイル一つ分遅れていた；現在は重みを先行（その stage はデコード読み取り後に即座に解放）。8 行デコードタイルはシフト一つで三つを置き換える（w4a16_dequant_word_one_shift は奇数/偶数ニブルをインプレースマスクし、一つの FMA で中心化、重みに 1/16 を乗算）。decode-long-k は marlin-fp16 の 1.047 倍に到達（元は 0.996 倍）、8 行タイルは各行 2.5% から 7.6% 高速化、prefill-mlp-up は 5.7% 高速（torch 逆量子化行列積に対して 0.992 倍、同等）；遅くなる行はない。
  • sigmoid IEEE 除算回避（#2588）：make_unary_regcopy が evict_last ロードをサポート——16 バイト全体ベクターのスレッドは tileops::load16_evict_last を通り、末尾ブロックはベクター単位にガードを追加；SigmoidFwdKernel のみこのパスを有効化（残り 37 の単項カーネルは同一の CUDA を生成、357 のカーネルを dtype ごとに対照）。float16 sigmoid は refined_reciprocal（__fdividef の逆数にニュートン法一步、分岐なし）に切り替え、要素単位の範囲チェックと遅いパス呼び出しを置き換え；float16 / bfloat16 の結果は torch.sigmoid とビット一致、float32 は IEEE 除算を維持。forward 入力は vector_aligned を通り、開始要素が 16 バイト境界を越える際のミスアラインアドレスエラーを修正。16M 行は torch-compile を 1.020 倍から 1.042 倍リード；テストノード +2。
  • SM89 スキャン拡幅（#2574）：既存の 16 列プリフィルスキャンを 4096 から 16384 token 区間で 8 値ヘッドから 16 値ヘッドに拡張（≤8 値ヘッドの呼び出しは元の戦略を維持）；同一のスキャンプログラムとビルド同一性を共有し、GDN と DeltaNet が恩恵を受け、KDA は不変。完全なリストを A/B した後、影響を受ける 19 行のワークロードが最終的に 2.5% から 19.7% 高速化。
  • TileOPs のオープン PR は計 16 筆（前回 17）；新規 5 筆：ラスタ永続タイル（#2589）、GemmW4A8FwdOp（#2590、INT4 重み×FP8 アクティベーション）、読み取り専用ページド GQA FP8（#2591）、SM89 長プリフィル 32 列スキャン（#2592）など。

  • sinks（varlen とページング）の一括マージ、両側スライディングウィンドウ、読み取り専用 RoPE、ページング KV 書き込み、さらに審査中の読み取り専用ページング FP8 と 32 列スキャン――TileOPs のページング / 長コンテキストアテンション行列は整備が進んでおり、FlashInfer、vLLM、FLA の外部対照を検収基準としている。次の観察点は同系統の能力の昇腾への移行（審査中の Sparse MLA、KDA chunk シリーズ）である。

5.3 海光の二線保守と分散方向

  • 海光は v0.1.12-release（収塊スケーリングパッチ）と v0.1.15 メインライン（アップグレードがマージ済みでリリースブランチを樹立）を同時に保守し、さらに distributed ブランチで IPC 集合通信を推進している――「旧線は納品を確保、新線は上流を追跡、新ブランチは分散を担う」という三線構造は明確である。マルチカード通信が実現すれば、海光はシングルカード適配からマルチカードシステム段階へと進む。
