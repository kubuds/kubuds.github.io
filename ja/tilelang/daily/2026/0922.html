今日の重点：メインリポジトリ単日 6 件のマージ——Fuzzer ICE 修正 2 件、AllReduce 静黙エラー遮断とフロントエンド Pythonic サポート

日付：2026-09-21 至 2026-09-22　出典：tilelang #3207／#3206／#3260／#3266／#3262／#3230

ウィンドウ内でメインリポジトリに 6 件マージ（北京時間 09-21 13:28 から 09-22 01:42、1 日余りに集中）、5 件の issue をマージクローズ、直近で最も密度の高い 1 日となった。各件：

  • 2 件の Fuzzer ICE 修正（#3206、#3207、01:41 / 01:42 に 2 分以内で連続マージ）：#3206 はカーネル本体內の通常の assert をデバイス側の合法的なチェックに降格——従來 CUDA コード生成は汎用 visitor を継承し、ホスト専用のエラー報告呼び出しと return -1 を __global__ カーネルに書き込んでいたため、nvcc が直接コンパイルを拒否していた（#3019 を修正）；#3207 は「動的形状の出力が形状提供入力より前に並ぶ」呼び出し時クラッシュを修正——シンボルテーブル構築を先に入力へアクセスするよう変更し、tvm_ffi と cython の両アダプタで先に入力テンソルを配置してから出力を割り當て、スカラ分岐とリストを整列（#3017 を修正）。2 件の原単は同一の報告者が 08-17 同日に起票したもので、fuzzer キューの定點清算に屬する。

  • AllReduce サイレントエラーの intercept（#3266、21:18）：XOR バタフライリダクションは參加スレッドの步長が 2 の冪であることを要求するが、従來は論理幅のみをチェックしていた；(32, 3) フラグメントを第 0 次元に沿ってリダクションすると AllReduce<MaxOp, 96, 3> に降格され、列とコピーがサイレントに混算され、かつちょうど 96 または 192 スレッド時に共有メモリ交換が境界を越える。修正方法は步長検証を CheckAllReduceWidth に統合し（tl.reduce と tl.finalize_reducer が共用）、テンプレートに静的アサートを追加し、reducer v2 プランナーではこれに対して広い方案へフォールバックすること。

  • NVRTC 修正（#3260、00:15）：warp リダクションのコンパイル問題を修正し（#3259 を修正）、nvrtc_std.h テンプレートヘッダを新規追加。issue 起票（09-21 09:48）から修正マージまで約 14.5 時間。

  • フロントエンド Pythonic サポート（#3230、13:28）：コンパイル期ループが Python のイテラブルと内包表記を受け入れる；5 ファイル +1084/-24、うち 766 行の新規テストを含む；同時に PrimExpr、Buffer などの誤用に対して明示的な拒否を返す。2 件の長期 Feature Request をクローズ——#2451（ForFrame がイテラブルでない）と #2308（T.unroll 內の式リストインデックスのゼロオーバーヘッド）。

  • #3262（16:23）：不変変数の再バインドに関する警告を削除、正味 14 行削除。

判読：6 件は同種の堆積ではなく三層の縦深——コンパイラフロントエンド/境界（2 件の Fuzzer）、ランタイムラッパー層（NVRTC）、コード生成とスケジューリング（AllReduce）。うち AllReduce の 1 件が最も重い性質を持つ：これが intercept したのは「動きそうに見えて結果がひっそり間違う」サイレントエラーの一種であり、防線が静的アサートとプランナーフォールバックへ前倒しされた；フロントエンド Pythonic は週をまたぐ大型項目（09-15 起票）の著地である。

1.2 TileOPs：roofline ガバナンスの大型マージ——リスト式が唯一の実行ソースとなり再計數（09-21）

日付：2026-09-21　情報源：TileOPs #2158

09-21 21:02 マージ（09-20 07:29 起票、二日以内に完了）。三つの事柄：その一、マニフェストの roofline フィールドをすべての消費側が読み取る唯一の事実とする——一つの情報源（エントリ）、一つの評価面（生成された eval_roofline()）；これまで実装済み 175 オペレータのうち 98 個がエントリの横に別途メソッドを書いて実行しており、エントリを変更しても数値は変わらず、照合する術もなかった。その二、公式を修正、計 15 類の誤り：中間量が計上され、共通の入出力が漏計され、実装成果物が価格算入され、オペレータが誤った dtype や形状で価格算入されるなど、Conv3d、FFT、RoPE 系列、Mamba2、DeltaNetAutograd、ページド GQA、バッチ正規化、グループ化行列積などに及ぶ。その三、検査に判定可能な対象を持たせる：構造オラクルが PR ごとに 175 オペレータを再計算；NCU 監査は人手を維持（CI では付与できないカウンタ権限が必要）だが、構築可能な 78 オペレータに対する一回の全量実行で最後の二箇所の公式欠陥を発見した。

判読：「読み取り値、判定基準、溯源」から「公式と実行の合一」へ、「読み出したもの」と「書き下したもの」が同一であることが証明された；本件はこのガバナンス線の合流であり、かつ再検査能力を CI に留めた。

1.3 TileOPs：組み合わせ GEMM セレクタを実測に基づき再フィッティング、torch._grouped_mm との差が是正される（09-21）

日付：2026-09-21　ソース：TileOPs #2157

09-21 22:57 マージ。セレクタはデバイスの事実と相反する三箇所の静的コストモデルを一つずつ修正した：その一、モデルは WGMMA 命令数を認識できない（N が 2 の冪でないと二回発行される）ため、192 幅のタイルを安価と読む——実測ではタイトな行においてその最良構成が記述子に中央値で 1.38 倍遅れ、最悪 3.82 倍、74 回の比較すべてで負け、block_n=192 は排除リストに掲載された；その二、浅いリングのペナルティは波数のみを見ており、「三波でデバイスを埋める」形状を誤って損なう——「波数が少なくかつタイルが SM を埋めるに不足する」の二条件に変更；その三、階層化エピローグは従来一種のタイル形状のみに奉仕していた——リング深さによるゲーティングに変更し、m-grouped / K-grouped に拡張。背景として実測で組み合わせ GEMM は 120 測点のうち torch._grouped_mm に 14 回敗北、最大 3.3 倍。付随：融合 silu を 0.5 + 0.5 * tanh(g / 2) に書き換え（expf と正確除算を不要にし、出力はビット単位で一致）、MoE プレ配置容量を行ブロック単位で丸め、汎用組み合わせ GEMM は二つの prim_func がともに宣言しながら誰も参照解決しないメタデータテーブルを削除。

1.4 TileOPs：ガバナンスフォローアップ三件——バイパス修正、マニフェスト規則評価問題と W4A16 予備重み順（09-21）

日付：2026-09-21　ソース：#2167／#2161／#2168

  • #2167（22:34 新規起票）：roofline バイパス修正。maybe_install_eval_roofline() は eval_roofline を定義したクラスに対して静かに譲位しており、まさに 98 オペレータが手書きメソッドを実行する仕組みであった；#2158 マージ後もなお 3 つのオーバーライドが残り、本件はそのうち二つの GQA オーバーライドを削除し、「呼び出し期のペイロードを属性の上に重ねる」統一的な書き方に置き換え、さらに「ペイロードが None」（呼び出し側のタイミング問題）と「ペイロードがマッピングでない」（作者の結線ミス）の二種の誤用に明確なエラー報告を追加。
  • #2161（11:20、issue）：マニフェスト shape_rules 内の helper 定義が決して評価されない。15 の conv/pool エントリが等式で _kW、_sW などのような中間量を定義する一方、バリデータは逐条独立に評価し等式左辺を束縛しないため、234 条の規則が NameError で静かにスキップされる（ウィンドウ制約と全出力範囲規則がいずれも発効していない）。作者は三種の修正法を実測しすべて「テスト済み且つ却下」として列挙し、判断を待っている。
  • #2168（23:14、ドラフト）：W4A16 GEMM が前処理重み順を読み取る。現状では一対の FP16 重みを産出するごとに shift+mask+spread+LOP3 のデコードが必要で、実測でカーネルの 9.5% から 11.3% を占める；新たに W4A16RepackFwdOp（チェックポイントロード時に一度並べ替え、三進三出）と GemmW4A16PrepackedKernel を追加。併せて一箇所の宣言欠陥を修正：weight_scale は FP32 と宣言されており——Machete は直接拒否し、Marlin はチェックせず静かに誤計算する（参考実装に対して [inf, -1531.0, nan] を報告）；roofline の metadata_bytes も同時に修正。

1.7 TileFoundry：ループ認識バッファライフタイムと CuTe 風 swizzle の 2 件がマージ（09-21）

5. トレンド観察

5.1 修正の縦深：1日6件、Fuzzer からランタイムまでをカバー

メインリポジトリの本日マージされた6件は3層の縦深を構成する：コンパイラフロントエンドと境界（Fuzzer ICE 2件）、ランタイムラッパー層（NVRTC）、コード生成とスケジューリング（AllReduce）。2件の Fuzzer は同一報告者が 08-17 に同日開票したものだけで、今になって的を絞って処理されたことは、fuzzer キューがついでではなく系統的に処理されていることを示す；AllReduce の1件が阻止したのは「動くが静かに誤る」エラーで、検証は静的アサーションとプランナーのフォールバックへ前倒しされた——これは TileOPs 側の「公式は必ず名指しで参照可能」というトラストエンジニアリングと同じ発想が、異なるリポジトリで並行して現れたものである。

5.2 昇騰のロールバックと復旧：大型マージの検証コストが正面から支払われた

昨日の「赤」は24時間以内に「緑」へ転じた：3件のロールバックが1万行マージと2件のドキュメント撤回を巻き戻し、本日のデイリーテストは 2448 項目すべて通過で決着。ロールバックは失敗の物語ではない——マージ（09-20 午後）、検証失敗（09-21 早朝）、ロールバック（09-21 午前から午後）、全緑への復旧（09-22 早朝）、完全なチェーンは2日未満。観察点：撤回された #1753 がどのような修正形態で戻るか；回帰規模が 1936 から 2448 への増分が何で構成されるか（どのマージのテストがそれに伴い体系入りしたか）は来週照合する価値がある。

5.3 TileOPs 信頼工学は「逆戻り防止」段階に入る

先日は「誤りを正す」（意味論、物理、来歴、公式）だったが、本調査期間は「誤りを入れさせず、正しいものを退場させない」へと転換した：#2167 は清算公式を迂回するバイパス機構を撤去し、誤用に例外を付与；#2161 は「書き下したが決して実行しない」問題を公式層からルール層へと進展（234 件のサイレントスキップ）；#2157 は GEMM セレクタの三箇所のコストモデルを直感から実測読み取りへと変更。共通点は、ガバナンスに回帰能力を組み込むことであり、再度帳尻を合わせることではない。

5.4 空白とリスク点

四点：その一、k プールスタックの遺留四件（#3250、#3251、#3253、#3255）が連続二日目に収尾アクションなし、内容はすでに本線にあるが起票が宙吊り；その二、主リポジトリのリリース停滞が満 20 日に到達、レビューキューは時間単位のペースで清算し、リリース窓口は未開放；その三、昇騰が回退された FP32 行帰約と二件のドキュメントにまだ手直しスケジュールが見えない；その四、TileOPs の外部バックエンド三問（MUSA）にまだ応答なし——もし「登録式接続」が次段階の方向であるなら、この三箇所の欠落はクロスチップ普及の前提条件となるだろう。
