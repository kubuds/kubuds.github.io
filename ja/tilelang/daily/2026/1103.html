本日の重点

この日の主线はただ一つ：TileLang が DeepSeek の MLA デコードカーネルを昇騰 950 に移植したことであり、しかもコンパイラがスケジューリング可能な書き方で移植した。#3678 は一度に 1997 行、20 ファイル、42 コミットを追加し、BF16 prefill とコンパクト FP8 decode の二経路をカバーし、さらにオプションの FP8 と FP4 の追加 KV キャッシュ、attention sink、不正インデックス、query ごとの独立長を備える。実装方式は注目に値する：attention ループ、オンライン softmax、逆量子化、スケジューリングはすべて TileLang 内に記述され、T.Stage によってコンパイラにバッファバージョンと同期を管理させ、QK と PV は同一の L0B ストレージリングの二つの異なる layout ビューを使い、L1 の配置は T.annotate_buffer_addresses で直接指定する；prefill は一つのアキュムレータ割り当ての中で四つの互いに重ならない出力スライスに分け、正規化が一片終わるごとに一片を排出する。この書き方を成立させるため、コンパイラ側でも同時に三つの能力を補った——L0C から UB へのコピーで NZ 出力を保持すること、各 AIV ストリームが自身のパイプラインの前に選択されること、明示的にスケジューリングされたステージが物理発行フェーズで同一の場合にソース順を保つこと。対象形状は非常に狭く書かれている：ヘッド数 64、Dqk と Dv はともに 512、topk は 64 の倍数。

第二の線は実際のコンパイラリグレッションの修正である。#3734 が扱うのは SM100 上の ViT フォワード：Cannot convert type float32x16 to CUDA type。経路は長いが各ステップは明確——ベクトル化プランナが 256 ビットの BF16 ストアのために 16 レーンを選び、cast 制約を先送りし、DecoupleTypeCast が計算とメモリアクセスを分離することを期待する；一方 #3579 が直前に「メモリ読み取りのガード」をデカップリングから除外した（これらのガードを複製すると意味が変わる）ため、最終合法化のステップが依然として先送り戦略で幅を選び、残留 FP32 式が 512 ビットベクトルに膨らみ、CUDA バックエンドが表現できなくなった。修正は先送り制約を IR 属性ではなくプランナのパラメータにし、最後の合法化ステップのみ false を渡し、ガードの FP32→BF16 は 8 レーンに減り、デカップリングに成功した BF16 コピーは依然 16 レーンを保つ；アドレス cast もデータベクトル型制約から外し、既存のアクセス解析で合法性を判定する。

第三の線はデバッグ体験である。#3703 は #line 指令を「各 TIR 文ごとに先頭行のみをアンカーする」からオプションの段階的発行に変更した：レベル 0 はオフ、1 は現状維持、2 以上は各行が生成する非空行ごとに再アンカーし、複数行に展開された文や末尾の大括弧も含む。実装は CUDA、HIP、CPU C、C host、Metal、Ascend が共用する C 系出力ストリームに置かれ、vendored の TVM には触れない；ソーススパンのない文と関数は明示的に <tilelang-generated> に切り替え、ユーザー原文はマクロ継続行や文字列リテラルを壊さないよう逐字保持する。新環境変数 TILELANG_EMIT_LINE_DIRECTIVES を Python 側のデフォルト値とし、キャッシュ検索の前に pass 設定へ折り込む。ローカルで 42 項通過、6 項スキップ、CUDA と HIP のケースは作者のマシンでスキップされ、cuda-gdb の実際の動作はまだ直接検証されていない——作者自身がこの点を明記している。同日 LSP リポジトリが一笔追随し、CUDA デバッグを新しい行マッピングに合わせた。

オペレータ側のリズムは止まっていないが、方向は変わった。TileOPs の単日 7 笔のマージのうち 6 笔が性能、1 笔がテスト基盤で、すべて同一作者による；各笔は依然として H200 実測表とチェックリスト回帰ゲートを添付している。最も価値があるのは #2816：テスト時のみ存在する tileops_test ターゲットを新設し、PrivateUse1 上で各オペレータの共有 workload リファレンスを算出し、tests/ops のスモークテストがもはや CUDA 上に立つ必要をなくす。1281 行、59 ファイルの変更で、作者は境界も同時に明確にした——共有リファレンスとの比較はバックエンド非依存の契約と可搬性を証明できるだけで、実際のバックエンドの数値正確性は証明できず、その線は依然 #2611 に掛かっている。

最後は TileFoundry の一本の暗線である。#283 は「共有メモリアクセスをいかに順序付けるべきか」を分析層にした：同期ファミリが lowering の発行順に関数を走査し、各共有メモリアクセスについて命令、発行 mesh、オペランド、バイト範囲を取り、競合アクセスの前に commit/wait とスコープ内フェンスを計画する。83 個のスケジューリングフィクスチャのうち 52 個を計画し、31 個を拒否する（24 個は TMA コピー、6 個は wgmma を使用し、両者の完了セマンティクスはまだ宣言されていない；1 個はスレッド境界をまたいで不等なループにフェンスを挿入する必要がある）。付随する #285 が審査中で、計画を CUDA lowering に変えて逆検証する：sm_89 単卡上で構築可能な 7 プログラムのうち 6 個がリファレンスと完全一致し、synccheck と memcheck はすべてクリーン、一方 main の方式で lower すると同じ 7 個のうち 4 個が結果誤り；#283 の記述で示された直接症状は sm_89 の E4M3 GEMM が最大 659 偏る。

1. コアプロジェクト進展

1.1 主线：昇騰 950 の永続化 FlashMLA カーネル、BF16 prefill とコンパクト FP8 decode の二経路（#3678）

11-02 09:26 にマージされ、1997 行追加、17 行削除、20 ファイル、42 コミットで、本調査期間で最も大きな一笔となった。カーネルは昇騰 950 向けで、prefill は BF16、decode はコンパクト FP8 を使用し、オプションで FP8 と FP4 の追加 KV キャッシュを持ち、attention sink、不正インデックス、クエリごとの独立長をサポートする。アテンションループ、オンライン softmax、逆量子化、スケジューリングはすべて TileLang で表現し、T.Stage とコンパイラ管理のバッファバージョンおよび同期で駆動する。QK と PV は L0B ストレージリングの 2 つの異なる layout ビューを共有し、L1 の配置は T.annotate_buffer_addresses で指定する。prefill は既存のアキュムレータ割り当て内で 4 つの不相交出力スライスに分割し、独立した同期イベントを備え、正規化が 1 スライス完了するごとに 1 スライスを排出する。decode は行全体の出力コピーを使用する。コンパイラ側では 3 か所のサポートを追加する。L0C から UB へのコピーで NZ 出力を保持し、各 AIV ストリームをそのパイプラインの前に選択し、明示的スケジューリング段階が物理発射フェーズで打ち消された場合にソース順序を維持する。目標はヘッド数 64、Dqk と Dv がいずれも 512、topk が 64 の倍数であり、pair gather は既に記録されたゼロ burst コード生成の回避策を踏襲する。正確性とベンチマークのランナー、バッファ再利用とクエリ境界の回帰、および FlashMLA MIT 宣言付きの README を同梱する。

出典：https://github.com/tile-ai/tilelang/pull/3678

1.2 メインライン：cast 分離がスキップされた後に残存する 512 ビットベクトル、SM100 上で ViT フォワードのコンパイル失敗（#3734）

11-02 09:05 にマージ。e8225d7f5 上で、SM100 向け ViT フォワードがガード付きの FP32 から BF16 への出力ストア箇所で Cannot convert type float32x16 to CUDA type を報告する。プランナは 256 ビット BF16 ストアのために 16 レーンを選び cast 制約を延期し、DecoupleTypeCast が計算とメモリアクセスを分離することを期待する。#3579 がメモリを読むガードに対して分離をスキップさせた後、後続の LegalizeVectorizedLoop は同じ戦略で延期を続け、残存する FP32 式が 512 ビットベクトルとなり CUDA 側で表現できなくなった。修正は defer_cast_constraints をプランナの C++ パラメータ（IR 属性ではない）とし、呼び出し元が段階に応じて選択する。LayoutInference と LowerTileOp は true を維持し、最終合法化は一律 false を渡し、算出された幅を明示的な vectorize_hint として前方伝播し、リライタがデフォルト戦略で再計画するのを避ける。ガードの FP32 から BF16 へは 8 レーンに低下し、正常に分離された BF16 コピーは 16 レーンを維持し、ガードの安全チェックは保持される。アドレス cast とアクセスポインタ引数はデータベクトル型制約から除外され、連続アドレスはスカラベースアドレスとストライドに降格され、既存のアクセス解析で合法性を判定し、int64 インデックスの整列ベクトルアクセスと 4 レーンアトミックのユースケースには影響しない。

出典：https://github.com/tile-ai/tilelang/pull/3734

1.3 メインライン：#line 指令を行ごとの再アンカーに変更、デバッガマッピングはオプションの密集モード（#3703）

11-02 04:06 にマージ、682 行追加、11 ファイル。従来の #line 発行は 1 つの TIR ステートメントが生成する最初の行のみをアンカーし、後続行はコンパイラの論理行番号で進められるため、cuda-gdb は生成されたロード、演算、ストアを無関係な Python 行に帰属させていた。合成ステートメントと末尾の波括弧は進められたマッピングを継承する可能性があり、ソーススパンを持たない関数は前の関数のソースファイルを継承することもあった。本笔は tl.emit_line_directives を段階化する。0 または False で無効化しデフォルトを維持、1 または True でステートメントレベルを維持、2 以上で非空の生成行ごとに再アンカーする（複数行展開のステートメントと末尾の波括弧を含む）。実装は C 系出力ストリームにあり、CUDA、HIP、CPU C、C host、Metal、Ascend をカバーし、vendored TVM は変更しない。同時にステートメントと関数のソーススパンを記録し、ソースのない領域は明示的に <tilelang-generated> へ切り替え、ユーザ原文はマクロ継続行と文字列リテラルを壊さないよう逐語的に保持する。新たに TILELANG_EMIT_LINE_DIRECTIVES を Python 側のデフォルト値として追加し、キャッシュ検索前に pass 設定へ折り込み、明示的設定を優先する（デフォルト値が不正な場合を含む）。ローカルで Metal と LLVM ビルドを用いて検証した。行指令と compile-only の 2 グループ 42 項目が通過、6 項目がスキップ。指令を外した場合、ベクトル化加算と条件選択の 2 つのフィクスチャはレベル 0、1、2 で成果物が完全に一致した。作者は CUDA と HIP のユースケースが本機でスキップされ、cuda-gdb の挙動は直接テストしていないと注記している。

出典：https://github.com/tile-ai/tilelang/pull/3703

1.4 メインライン：アテンション示例がデバイスの共有メモリ上限に応じて tile を推論、RTX PRO 6000 上で 2 通過 7 失敗から 9 全通過へ（#3702）

11-02 06:59 にマージ、345 行追加、13 ファイル。複数のアテンション示例の非チューニング経路が Hopper サイズの tile をハードコードしており、sm_86、sm_89、sm_120 ではブロックあたりの動的共有メモリ上限が約 99 KiB のため、起動が直接失敗していた。エラー原文は、許可される動的共有メモリを 163840 バイトに設定するよう要求するもので、デバイス 0 のブロックあたり最大は 101376 バイトであった。現在、各示例は shared_memory_per_block_optin から tile を推論し、既存の GQA decode 示例（example_gqa_decode.py）の做法を踏襲している。データセンター構成は変更なし。各分岐は前の段の tile 要求を下回る場合にのみ発動するためである。約 99 KiB デバイスでの落とし所：attention sink の四個の示例はそれぞれ 64×64 二段階 128 スレッド（前向）と 64×32 一段階 128 スレッド（逆伝播）、example_gqa_bwd.py は前向 64×64、逆伝播 64×32、example_mla_decode.py は BLOCK_N 32、BLOCK_H 16 を取る。後ろ二者は threads パラメータを新規追加：64 行または 16 行 tile では T.gemm が四個の warp を必要とし、各 warp が 16 行ブロック全体を独占できるようにする。256 スレッドでは直接 lower 失敗となる（それぞれ acc_s と acc_s_cast の layout 衝突、および M=16 N=32 で有効な warp 分割がないと報告）。また、flash-attn 2.x には sm_12x カーネルがなく、四個の varlen 示例は元々参照ステップでエラーを投げていた。現在は flash_attn_varlen_supported を一度プローブし、非対応の場合は純 PyTorch の varlen_attention_ref（GQA、右下揃えの causal、window_size をカバー）に切り替える。検証は RTX PRO 6000 Blackwell（sm_120）上：CUDA 9 項目全通過（元は 2 通過 7 失敗）、CuTeDSL も同様に 9 項目全通過。H100 は 227 KiB の選択可能上限があり、元の tile のままで同様に 9 項目通過。

3.5 TileOPs：Norm 統計量を行内要素の減算に変更し、1e36 付近のオーバーフローを解消（#2811）

11-02 05:10 にマージ。根本原因は非常に直接的で、すべての平均と分散のカーネルが生の行に対して fp32 の総和を取っており、和が行のオフセット量（約 N 掛ける x ）とともに増大し、1e36 付近の行は直接オーバーフローして出力がすべて NaN になる。オーバーフローしなくても、平均はオフセット量の桁で丸められ、x − mean がこの丸めを各要素に持ち込み、その結果、定数行で算出される分散は丸めの二乗となり、正負の weight ではなく bias に正規化されてしまう。修正方法は、行から構成される各 fp32 量に不変条件を一つ加えることである。すなわち、それは行の拡散度によってのみ制約され、オフセット量によっては制約されない。実装上は「行内のある要素」を基準としてから減算し、warp 主導のカーネルでは warp の先頭要素を、シャードカーネルでは行の先頭要素を用いる。これは前回のレポートで #2812 が列挙した四つの Norm オペレータの欠陥と同じ種類の問題に対する正面からの修正である。

ソース：https://github.com/tile-ai/TileOPs/pull/2811

4.1 昇騰の同期正確性が集中報告面に：単日 8 件の新規 issue、二人の報告者がそれぞれ体系的に提出（11-02）

調査期間内にメインリポジトリで新規 issue が 8 件追加され、番号は #3740 から #3749 に集中し、すべて昇騰 AscendC と PTO の二つのバックエンドのコード生成と同期挿入を指している。うち 7 件は同一報告者により提出され、環境は TileLang 0.1.15、PyTorch 2.10.0+cpu、torch_npu 2.10.0 で、主題は同一プログラムが二つのバックエンドで挙動が分岐する点である：生成コードが起動するコアで不一致（AscendC は mix(1,2)、PTO は vector を出力）、enable_auto_schedule=True のとき AscendC が同期を挿入しない、自動スケジューリングをオフにすると生成成功するがオンにすると失敗しエラーメッセージが不明瞭、同一コードが AscendC では生成できるが PTO では失敗する。この一群の報告の共通点は、いずれも再現可能な prim_func と行単位で対照した生成コードを添付しており、直接回帰テストケースに変換できる形態であることだ。さらに審査中の #3735（thread sync でモジュール式インデックスの非交差を証明）と #3580（述語と昇格インデックスの同期）を加えると、昇騰側の同期正確性は現在最も集中した一線となっている。

出典：https://github.com/tile-ai/tilelang/issues/3747、https://github.com/tile-ai/tilelang/issues/3745

4.2 行跨ぎと転置ビューの SIMD ロードが DMA 依存を失う、根本原因は論理領域の再構築（#3749）

同批で技術的含有量が最も高い一件で、報告者の環境は main ブランチ e8225d7f5、Ascend950PR、CANN 9.2.0。問題は二箇所の連続 SIMD ロードが、より早い GM から UB へのコピーへの依存を失うことである：一つは行優先ロードが行の途中から開始し次の行へ跨ぐ場合、もう一つは転置ビューにアクセスし物理連続次元が最後の論理次元でない場合。根本原因の経路は詳細に記されている：生成された tl.access_ptr は物理ロード範囲を覆うが、MemoryAccessDetector::LogicalPointerRegion が再構築した論理領域はその一部を漏らし、依存分析は入力 DMA とロードが無関係と見なし、AutoSchedule が入力コピーをロードの後ろへ移動し、InsertSync も MTE2 から V への set/wait を発行しない。最小再現では work.shape が (2, 128) で、まず T.copy(A, work[1, 0:64])、次に T.SimdVF() 内で T.simd.vld(work[0, 64]) により 128 個の連続半精度要素を読む：生成された読み取り記述子は tl.access_ptr(work[0, 64], 128, 1) で、物理的に [64, 192) を覆い、うち [128, 192) はまさに直前に DMA が書き込んだ部分であり、再構築された領域は work[0:1, 0:128] すなわち物理 [0, 128) で、書き込み区間を完全に外している；行数は ceil(128/128) で 1 行と算出され、開始列 64 が算入されていない。この件は本調査期間の主力が補強している FlashMLA、PTO ベクトル化と同じ土台であり、一旦命中すればサイレントな誤結果となる。

ソース：https://github.com/tile-ai/tilelang/issues/3749

5. トレンド観察

この日最も記録に値する判断は、昇騰がもはや「適応目標」ではなく「初回リリース目標」になったということだ。FlashMLA のような DeepSeek 自社デコードパス上の核心カーネルが、昇騰 950 を直接ターゲットとしてメインラインに書かれており、しかも T.Stage、annotate_buffer_addresses といった明示的スケジューリング向けの低レベル機能を使っており、別リポジトリを開いて移植するのではない。コンパイラ側の 3 つのサポート（L0C から UB への NZ 保持、AIV ストリームのパイプライン前選択、ソース順での明示的ステージ発行）と合わせると、昇騰パスは「動く」から「スケジューリング意図どおりに動く」へと移行しつつあることがわかる。

第二の手がかりは、正確性の重心が下がっていることだ。前号のメインラインでは TIRX 移行のために ThreadSync 正確性改善一式をリバートしたが、今号ではすぐに 2 つの補完が現れた。メインライン #3752 は z3 でリソース上限を解き、#3735 はモジュール化インデックスの非交差性で証明が必要な形状を減らすことを提案。同時に #3749 は「依存性分析が物理ロード範囲を見えない」欠陥を MemoryAccessDetector::LogicalPointerRegion の層まで掘り下げた。これらを TileFoundry の暗線と合わせて見ると——分析層は 83 のフィクスチャのうち 52 の共有メモリ順序を証明でき、lowering を main の方式で行うと 7 プログラム中 4 つが誤計算になる——同じシグナルが 3 回現れている：TileLang の現在の主要リスクは機能不足ではなく、「生成コードが見た目は正しいが実際は正しくない」ことであり、チームが選んだアプローチは正確性を却下可能な証明にすることであり、パッチで個別に塞ぐことではない。

第三は、テストと契約が独立した層になり始めたことだ。TileOPs の tileops_test はスモークテストを CUDA から切り離し、compile-contract-gate は dispatch 契約と workload データ生成を分離し、両者は同じ 1 時間内にマージされた。作者は同時に「共有参照は実バックエンドの正しさを証明できない」と明記している。この「何をテストできるか」と「何を証明したか」を分けて表現する習慣は、性能パッチを数本書き足すよりも、このプロジェクトがプロトタイプ期を抜けつつあることをよく示している。

最後に一つの対照に注意：オペレータ側は単日 7 件の性能マージ、6 件が H200 実測表付きである一方、ニュース側の三チャネルは 24 時間ゼロヒット。TileLang の対外プレゼンスは依然「DeepSeek オープンソース昇騰コンポーネント」のようなイベントに集中しており、日常の進展はほぼリポジトリ内でのみ起きている。このプロジェクトを追う者にとって、これはデイリーレポートの主体が報道ではなくコミットと PR にならざるを得ないことを意味する。
