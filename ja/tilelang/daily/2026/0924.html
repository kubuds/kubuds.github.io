今日の重点：TileSight が正式にオープンソース化——タイル中心の分析的性能モデルが論文から公式リポジトリへ

日付：2026-09-23　出典：tile-ai/TileSight リポジトリ／初回コミット init／arXiv 2607.22432

09-23 22:54（北京時間）、tile-ai 組織に新規追加された TileSight リポジトリが初回コミット init を完了：177ファイル、約5.67万行の新規追加、MIT ライセンス、コミット者は帝国理工学院の Zhiwen Mo。7月24日の arXiv 論文の末尾にあった「発表後にオープンソース化する」という約束がここに正式に実現した。組織のリポジトリ総数は28から29に増加。

TileSight は「タイル中心」の分析的な GPU 性能モデルとして位置づけられる：タイルをモデリング単位とし、CPU 側でオペレータの操作コスト、キャッシュトラフィック、実行時間を推定する——カーネル内では計算とメモリアクセスのパイプライン重複をモデリングし、カーネル間ではキャッシュ階層をモデリングし、GPU 間ではノード間通信をモデリングする。実測標定は CUDA と HIP プローブがターゲット GPU 上で別途行い、モデリングとは分離される。論文の口径による精度：A100、H200、B200、B6000 の4世代プラットフォームで、単卡カーネルレイテンシの合併平均絶対百分比誤差は12.35%、L2ヒット率予測は実測と約1パーセントポイントの差。32卡クラスタに拡張すると、融合分散カーネルと vLLM エンドツーエンドサービスの加重誤差はそれぞれ16.18%と13.52%。

リポジトリ構造（初回コミット範囲）：

  • tilesight/arch/：20 余件のハードウェアアーカイブ。英偉達 A100/H100/H200/B200/B6000/V100/T4/P100 と RTX 3090/4090/5090 など、AMD MI50/MI210/MI300X/MI325X、インテル Arc 770 をカバー；
  • tilesight/modeling/：プログラムフロントエンド（ビルダー/分析/契約）、多段キャッシュ再利用距離モデル（SDCM）、パイプライン重複分析（プロローグ/定常状態/エピローグ、占有率、波動量化）、GEMM/FlashAttention（FA3/FA4 周期スケジューリング）と FlashMLA デコードなどのアダプタ；
  • micro_benchmark/：CUDA プローブ（B200 tcgen05/tmem、H200 wgmma、汎用 dram スキャンと P2P）と HIP プローブ（rocBLAS GEMM、AMD デバイス情報）；
  • examples/ と完全なテストスイート、さらに NCU 比較と CuTeDSL/プライベートツールチェーンの予測補助ツールを含む。

判読：これは本テーマ「性能の説明可能性」の手がかりの第三段――07-24 論文（インペリアル・カレッジと TileLang 核心メンバー共著）→ 09-18 コミュニティドキュメントリポジトリ（TileLang 分析を TileSight に接続）→ 09-23 公式コードリポジトリ。これまで論文と個人ドキュメントに分散していた方法を組織プロジェクトとして固化し、TileFoundry（コンパイル期内の IR 分析）と分業を形成する：一方はモデリング期に層をまたぐコストを予測し、もう一方はコンパイル期にキャッシュ容量の結論を報出する。ハードウェアアーカイブが AMD とインテル製ディスクリート GPU をカバーしている点も、それを自然にマルチバックエンドの物語に奉仕させる。

日付：2026-09-23　情報源：#3232／#3246／#3272

  • #3232（13:54 マージ、+196/−14、3 ファイル）：「ループターゲットが可変スカラー束縛を再利用する」問題を修正（欠陥単 #3231 も同時クローズ）――ループターゲット（タプルターゲットを含む）に明示的な束縛を確立し、帰納変数を既存の alloc_var や Ref 束縛に書き込むことを回避。同時に通常の可変代入と境界外チェックを保持；ループ形態、タプルターゲット、期限切れ束縛などの回帰テストを追加。

1.2 メインリポジトリ：NaN 伝播セマンティクスが浮上、コンパイル期検証が同日フォロー（09-23）

日付：2026-09-23　情報源：#3270／#3273／#3205

  • 09-24 未明 03:08 に新規起票 PR #3273：サポートされない出力 dtype に対してコンパイル期エラーを追加――診断情報は操作名、サポートする出力型、実引数 dtype を提示；検証はネイティブ ReduceOp コンストラクタ内に配置（ローカルリダクション、フラグメントリダクション、書き戻し累積が累算器 dtype 契約を統一的に保持）；回帰マトリクスは三種のオペレータ × clear 二档 × フラグ二値 × 五種の dtype をカバー；SM100 パックドリダクション回帰も同一の診断を期待するよう同時更新。
  • もう一本 #3205（NaN 伝播 clamp のデバイステンプレート低下修正）は期間内に更新が続き、依然レビュー中。

判読：これは「暗黙のセマンティクスエラーをコンパイル期失敗へ前移する」原則が新たなデータ型セマンティクス上で複製されたもので――乱数、レイアウト証明、型組合せから NaN 伝播へと延伸し、しかも報告から修正 PR までの応答が半日以内に完了した。

1.7 TileOPs：外部バックエンドチャネル治理——38 箇所のデバイスチェックが撤去（09-23）

日付：2026-09-23　情報源：#2179／#2164／#2182

背景：コミュニティ開発者が MTT S5000 上で外部 MUSA バックエンドを統合する際、複数の公式オペレータが「登録された外部コンストラクタが呼び出される前に失敗する」と報告した——三つの阻塞：CUDA のみの入力検証、ゼロ入力の外部呼び出しを拒否、外派前の CUDA デバイスクエリ（欠陥票 #2164；#2165、#2166 は別途テスト経路とビルダー登録の問題を記録）。

期間内の対応：

  • #2179（+797/−256）：オペレータ層の約 38 箇所のデバイス種別チェックを撤去し（RoPE、Dropout、Mamba/SSD、DeltaNet、GLA、NSA、Engram、MoE、FFT、FP8 量子化、TopK など）、インツリーカーネルが Kernel._require_cuda でテンソルレベルにデバイスを宣言するように変更；check_tensor_shape は形状チェックを保持し、デバイスチェックを削除；新たに pre-commit フック op-device-kind-lint を追加してデバイス種別チェックの回流を阻止；遅延構築の呼び出し記録のために make_call 仮引数を導入。ゼロ入力と複合オペレータの二類は設計判断が必要で、後続作業として列挙。
  • #2182（issue）：BuildKernel プロトコルは呼び出し可能オブジェクトのみを約束するのに対し、オペレータ層はより多くを仮定していることを指摘——インツリーカーネルの属性読み取り、単一エントリの複数カーネルアンパック、44 個のオペレータクラスが target= 引数を受け付けないなどの状況が存在；プロトコルが表現できない複合エントリには拡張が必要。
  • #2181、#2183：インツリーテストを BUILTIN 経路に固定し iter_kernels の産出を明確化、二項自動チューニングテストをインツリーカーネルに限定し、上記の治理に協調。

2.2 昇騰：スカラー GM ストア競合の修正方案が提出、差分カウントがゼロに（09-23）

日付：2026-09-23　情報源：#1834（#1304 の修正）

17:04 新規（+557/−1、10 ファイル）、二層の修正：

  • 根本原因分析：同一 GM バッファが混在書き込みされる——バルクコピーは MTE3 DMA の直接書き込み、末尾列のスカラー SetValue はライトバックキャッシュを経由してリード-モディファイ-ライトし遅延ライトバックする。行間隔が 64 バイトの倍数でない場合、隣接行がキャッシュラインを共有し、ダーティ行の排出が DMA で書き込み済みの新しい値を上書きする。マルチブロックカーネルでは競合がコアをまたいで発生し、キャッシュクリアと同期命令はいずれも自コアのスコープであるため、同期命令だけではきれいに修復できない（再現スクリプトの残存率 27%）。
  • 第 1 層（同一コア）：同期挿入の段階で「スカラー書き込みされた GM バッファ」に対して MTE3 書き込みの前後に選択的にキャッシュクリアとウェイトを挿入する。同時にイベント番号の割り当てを循環再利用に変更する（テンプレートのハードコードされた 0 番イベントと pass 割り当ての衝突による潜在デッドロックを解消）。再現スクリプトの不一致数 12,967,510 → 3,496,136（73% 削減）。
  • 第 2 層（書き換え消除）：新たに opt-in pass（デフォルト無効）を追加——「連続直列ループ内の単一 GM スカラー書き込み」を UB 一時保存 + 単一 DMA バーストに書き換え、根本的にダーティ行を発生させなくする。有効化後、不一致数はゼロに。新規 2 件の回帰テストが通過、既存 113 項目のスイートが通過、gqa_fwd_varlen はゼロオーバーヘッド、量子化混合カーネルに劣化なし。
  • 範囲：opt-in。条件付き書き込み、累加、散乱など連続バーストに書き換えられない形態には依然としてコア間の潜在的問題がある（プラットフォームレベルの制限、別途追跡を推奨）。作者の環境は Ascend910 A3 / CANN 9.0.0。

5. トレンド観察

5.1 分析レイヤの形成：論文とコミュニティドキュメントから公式コードリポジトリへ

TileSight の三段階の着地（07-24 論文 → 09-18 コミュニティドキュメントリポジトリ → 09-23 公式コードリポジトリ）は、TileLang をめぐる性能の説明可能性が「個人の手がかり」から「組織プロジェクト」へ格上げされつつあることを示す。これは TileFoundry（コンパイル内分析、本調査期間でキャッシュ容量の結論を再計算可能にした）と方向が交錯する。エコシステムへの意味：オペレータライブラリとランタイムのほか、分析ツールの完成度が TileLang の同種ツールチェーンに対する差別化資産になりつつある。TileSight のハードウェアプロファイルは AMD とインテルディスクリート GPU をカバーし、マルチバックエンドの物語にモデリング基盤を提供する。

5.2 TileOPs 性能シーズンの収束と再出発

単日七件のマージに三件の新規オープンが加わり、TileOPs の性能シーズンは終わったのではなく、第一波の「オペレータ登録」から第二波の「スケジューリングと設定の細粒度研磨」へ移行したことを示す。varlen GQA の三連はスケジューリング計画と永続化をめぐり、W4A16 はレジスタとグリッド利用率をめぐる。観察指標：このようなマージリズムがさらに数営業日続いて初めて安定したと言え、そうでなければ依然としてパルス的な推進である。

5.3 マルチバックエンドの技術的負債が顕在化

外付けバックエンドの三道の阻塞とプロトコルギャップは、「マルチバックエンドのプラグ可能」をビジョンからエンジニアリングの細部へ引き戻す：デバイス種類のチェックがオペレータ層に散在し、ビルダープロトコルは呼び出し可能性のみを保証し、44 のオペレータクラスにターゲットパラメータが欠けている。良い知らせは、調査期間内に既にまとまった負債解消の動きがあることだ（一度に 38 箇所のチェックを除去し、lint を追加して回帰を防止）。外付け側の見方によれば、このチャネルの完成度がサードパーティバックエンドの現在のサイクルでの公式オペレータキューの完走可否を決める。

5.4 空白とリスク点

第一に、メインリポジトリのレビュー滞留が未解決：TileIR バックエンドの 31 コミット、魔法の除算と起動不変条件が引き続き待機し、大規模変更の窓とリリース停滞（22 日）が重なる。第二に、新規オペレータがベンチマークに入ると即座に長いプレフィルタイムアウトが露呈し、性能の物語はベンチマーク層でキャパシティを補う必要がある。第三に、昇騰リポジトリの「マージ—ロールバック」のリズムが続いており、サンプル類貢献の検収経路について公開された説明は見られない。第四に、インデックス境界修正単が当日クローズされ、問題が依然として存在するのに引き継ぐ者がいなければ、狭いインデックス型の境界挙動は宙に浮いた状態が続く。
