今日の重点

この調査期間の組織内には合併が6件しかなく、前号の9件からさらに3分の1減少したが、数字よりも構造の方が注目に値する。6件のうち3件はメインリポジトリにあり、しかもすべて昇騰に所在し、CUDAやCPUに該当するものは1件もない。最大のものは#3516（20ファイル、+1549/−182）で、tvm_ffiをptoターゲットのデフォルト実行バックエンドに引き上げた——従来target="pto"はCythonランチャーを通っていたが、現在はexecution_backend="auto"が直接tvm_ffiに解決され、共有host codegenがMakePackedAPIとC hostを生成し、昇騰ランタイムがaclrtLaunchKernelWithHostArgsでPTODSLがコンパイルしたaibinを起動する。経路はAscendCカーネルと同一である。付随するのはモジュールレベルのツールチェーンコールバックで、PTODSLモジュール全体がdevice buildステップ内で一度にコンパイルされ（ptodsl → ptoas → bisheng fatobj-link → .aicore_binaryの抽出）、結果はptoas引数、ptoasバージョン、CANNアイデンティティによってキャッシュキーに入る。旧経路はexecution_backend="pto"として保持され、両方の産出はビット単位で一致する。

2件目#3776はソルバー側の引き締めである。AutoScheduleは元々固定の周期下限で二分探索を開始していたが、今回、3つの必要条件の最大値を取るように変更した。単一タスク界は各タスクの起動間隔の最大値を踏襲し、リソースグループ界は対で衝突するタスクを残余値でソートし、隣接差と先頭末尾差から周期が各起動間隔の和以上であることを導出し、自己依存界はS_u - S_u >= wait - d*Pから逆解して周期がceil(wait/d)以上であることを求め、バージョン関連距離はさらにnum_stagesで換算する。追加の下限探索は導入されておらず、スケジューリングモデルも変更されていない。実証はAscend 950PR、CANN 9.3.0の週バージョン上で行い、コンパイルキャッシュを無効化し、1回ウォームアップ3回測定を交互に行い、すべての昇騰サンプルがコンパイルを通過しスケジューリング結果も不変で、Z3求解段階の累計所要時間が10.04%減少した。

3つ目の事柄はメインリポジトリにはない。海光の分散三種セット#36（6ファイル、+2022/−0）は16:20にmainではなくdistributedブランチへ合併され、内容はBlock-Push版のGEMM + AllReduce、Block-Push版のGEMM + ReduceScatter、Block-Pull版のAllGather + GEMMという3つの計算通信融合オペレータで、性能データと実装説明はREADMEに記載されている。同日#37がHCUのds_read_vector Alt2とLDSレイアウト推論を開いた。このラインは10-29のpush-wave reduce-scatterサンプルから融合オペレータ一覧へと一路進んできており、海光リポジトリが初めて体系的に分散に取り組むものとなった。

4つ目の事柄は品質側の集中的な噴出である。調査期間内の新規issue 35件のうち30件がメインリポジトリに所在し、そのうち26件が昇騰を直接指している。2つのアカウントが午後から深夜にかけてそれぞれ十数件を報告し、形態は高度に一致していた——「実行が誤った」のではなく、「本来エラーになるべきところが黙って通過した」のである。T.Kernelがゼロまたは負のblock数を受け入れ、T.alloc_l1が2 GiBの割り当てを受け入れ、T.Persistentが負のwaveとstageを受け入れ、T.unrollが−1を受け入れて#pragma unroll -1を吐き出し、負のテンソル次元がコンパイラを直接クラッシュさせた。別のグループは意味のずれである。hf32のnearest_zeroがNEAREST_AWAYにコンパイルされ、GEMM入力dtype表とcodegenが双方向に不一致となり、reduce_bitand一族が昇騰テンプレート未定義の型を吐き出し、同型NDからNZへの散乱がマスクカウントがフォールバックしないことで無限ループに陥った。これらのissueの大半は依然オープンだが、当日すでにVMI mask検証、SIMD fill復旧などの対応修正がレビュー中である。

1. コアプロジェクトの進展

1.1 昇騰：PTOターゲットのデフォルト実行バックエンドをtvm_ffiに切り替え、モジュール全体をデバイスビルド段階でコンパイルしキャッシュ（#3516）

#3516（20ファイル、+1549/−182）は今号最大のもの。変更の実質はptoターゲットを「専用Cythonランチャー」から「AscendCと同じhost経路」へ移行することである。target="pto"とexecution_backend="auto"の組み合わせではtvm_ffiに解決され、共有host codegenがMakePackedAPIとC hostのビルドを担い、昇騰ランタイムモジュールがaclrtLaunchKernelWithHostArgsでPTODSLから生成されたaibinを起動する。

デバイス構築側では、モジュールレベルのツールチェーンコールバックを新たに追加し、PTODSL モジュール全体を一度にコンパイルできるようにした。ptodsl フロントエンドの生成物、ptoas による降下、bisheng の fatobj リンク、そして .aicore_binary の抽出までを一括で行い、生成物は aibin 単位でキャッシュする。キャッシュキーには ptoas のパラメータ、ptoas のバージョン、CANN のアイデンティティをまとめて算入する。この点が極めて重要であり、従来こうしたキーからツールチェーンのバージョンが抜けていると、CANN を跨いだアップグレード時に古い生成物がヒットしてしまっていた。

検証面は幅広く整備し、新たに4グループのテストを追加した。auto が tvm_ffi に解決されること、呼び出し先が出力を確保すること、動的 shapes と動的出力、マルチデバイスカーネル、動的共有メモリ、cube/vector 混在の GEMM、source accessor、エクスポートライブラリ、host 側のループ起動と host 側のプロファイリング区間である。さらに等価性テストでは、vecadd、マルチカーネル、動的共有メモリの3種類のカーネルについて tvm_ffi と旧 pto の結果をビット単位で比較する。2グループのキャッシュテストはそれぞれバイナリキャッシュとカーネルキャッシュを対象とし、キャッシュヒット時にツールチェーンをスキップすること、破損エントリがエラーを投げること、そして全く新しいプロセスでヒットすることを含む。旧パスは計画通りに保持し、カバレッジを確認した後に退役させる。

情報源：https://github.com/tile-ai/tilelang/pull/3516

1.2 昇騰：AutoSchedule が3つの必要条件で周期の下界を引き締め、Z3 求解時間が 10.04% 減少（#3776）

#3776（1ファイル、+20/−1）は初期値のみを変更し、アルゴリズムは変更しない。従来の二分探索は固定の下界から開始していたが、現在はまず3つの必要条件を計算してから最大値を取る。単一タスク界は各タスクの起動間隔のハードな下界を保持する。資源団界は、対になる資源衝突の団に対して、タスクの残余値を昇順に並べた後、隣接差の制約と先頭末尾差の制約を加算して周期が団内の起動間隔の合計以上であることを導き、団自体は各タスクをシードとして貪欲に列挙する。自己依存界は S_u - S_u >= wait - d*P から逆算し、バージョン関連の距離は num_stages を上限とする。

実証環境は具体的に記述されている。華為 Ascend 950PR、CANN 9.3.0 の 20261009.01 週次バージョン、コンパイルキャッシュを無効化し、各設定につきウォームアップ1回・測定3回を交互に実施。結果は2点ある。昇騰のサンプルはすべてコンパイルが通り、スケジューリング結果は変更前と一致した（下界のみを引き締め、解を変えていないことを示す）。Z3 求解フェーズの累積所要時間は 10.04% 減少した。二分探索の上下界と求解状態の扱いは変更されておらず、追加の下界探索プロセスも導入していない。

この種の変更の上流にとっての価値は単点の性能ではなく、オペレータ規模の増大に伴ってスケジューラの求解時間が伸びる際、二分探索の起点の無駄が線形に拡大する点にある。必要条件を初期値に書き込むことは、各求解において無意味な区間を一段省くことに等しい。

情報源：https://github.com/tile-ai/tilelang/pull/3776

1.3 昇騰：整数アトミック操作を signless キャリアに適応、12件の PTO ケースが 32 ビットと 64 ビットをカバー（#3794）

#3794（4ファイル、+52/−6）は #3512 の後遺症を修正する。あの変更で符号付き整数型を signless の i32/i64 から si32/si64 に変えたが、PTO のアトミックインターフェースは signless キャリアを要求するため、SIMT カーネル内の整数 add/min/max アトミック操作が直接コンパイル失敗していた。

修正方法は、生成される PTODSL 呼び出し境界で部分的な適応を行う。ポインタとオペランドを同じ幅で signless に再解釈し、ポインタのアドレス空間は保持し、戻り値は再び論理型に戻す。min/max は元の符号付きまたは符号なし比較セマンティクスを維持する。これにより #3512 が導入した論理型体系は覆されず、適応はアトミック層のみに押し込められる。

回帰ケースは testing/ascend/language/simtvf 配下の test_simtvf_atomics.py に置かれ、32 ビットと 64 ビットの add/min/max、負のオペランド、旧値の返却、32 ビットを超える値、上位ビットが 1 の符号なし初期値をカバーする。新規追加の12件の PTO ケースは昇騰上ですべて通過した。同批でマージされた #3792 は同じ一族の問題の別側面を修正しており、T.atomic_add/max/min が符号付き入力のために PTO 上でコンパイル失敗する問題である。

情報源：https://github.com/tile-ai/tilelang/pull/3794

1.5 TIRx：ceildiv と負の scale の split div/mod の 2 件が審査中、ネストした floor division のエラーと同源（#93、#94）

tile-ai/tvm 側では調査期間内に 2 件が審査中である：#94（[Fix][TIRx] Make ceildiv exact for signed divisors）と #93（[Arith] Guard negative scales in canonical split div/mod）。2 件とも同じ種類の問題の両端を修正している——符号が整除と剰余に入ると、正規化の書き換え前提が成立しなくなるため、「正確さ」と「安全性」を分けて扱う必要がある：ceildiv は符号付き除数でも結果が正確であることを要求し、split div/mod は負の scale の下で正規化を拒否する必要がある。

これはメインリポジトリで当日新たに開かれた #3937（[BUG] ネストした floor division が負の乗数の下で誤った整数を生成）と同じ箇所を指している：負の係数が一旦算術簡約の書き換えチェーンに入ると、境界条件が見落とされやすくなる。違いは、#3937 がユーザー側の再現であるのに対し、#93/#94 はコンパイラ側の先手の強化である点にある。

2. マルチバックエンド適応

2.1 海光：分散三種セットが distributed ブランチにマージ、Block-Push と Block-Pull の 2 つの通信経路（#36）

#36（6 ファイル、+2022/−0）は前号ではオープン状態だったが、今期 16:20 にマージされ、着地点は main ではなく distributed ブランチである——同リポジトリのデフォルトブランチ main の最新コミットは依然として 11-06 であるため、この変更はデフォルトブランチのコミット一覧には現れず、ブランチ指定でしか確認できない。着地点の差異は明記する必要がある：main と v0.1.15-release は同一参照であり、distributed は 11-03 の signal プリミティブ、10-29 の push-wave reduce-scatter の例、そして今期の三種セットを独自に歩んでいる。

内容は 3 つのオペレータ：Block-Push 版の GEMM + AllReduce、Block-Push 版の GEMM + ReduceScatter、Block-Pull 版の AllGather + GEMM。Push は計算側が主体的に結果を相手側へプッシュし、Pull は計算側が相手側の allgather 結果を取りに行く。どちらの経路を選ぶかは通信ドメインのサイズとオーバーラップウィンドウに依存し、README には性能比較と実装方式が記載されている。検証側では 11-06 に Torch 性能ベースラインを GEMM reduce-scatter ベンチマークへ追加済みで、今期はそれ以上の変更はない。

これらの issue の共通点は「結果が間違っている」ことではなく、「通るべきでないものが通ってしまう」ことである。パラメータ検証の類：T.Kernel がゼロまたは負のブロック数を受け入れ、T.Persistent が負の wave_size と num_stages を受け入れ、T.Pipelined が負の num_stages と不正な order/stage メタデータを受け入れ、T.unroll が −1 を受け入れて #pragma unroll -1 を出力し、ループコンストラクタがゼロまたは負の extent を受け入れ、負のテンソル次元がコンパイラを直接クラッシュさせ（ネイティブクラッシュであり Python 例外ではない）、T.alloc_l1 が容量チェックなしで 2 GiB の割り当てを受け入れる。セマンティクスのずれの類：hf32 の nearest_zero が NEAREST_AWAY にコンパイルされ、GEMM 入力 dtype 表と codegen が双方向で不一致であり、reduce_bitand/bitor/bitxor が昇騰テンプレートで未定義の型を出力し、batch reduction がバッチオーバーロードのないスカラー AllReduce エントリに退化し、GM から L1 へのコピーの pad_value がゼロのみを受け入れる L1 fill にルーティングされ、同型 ND から NZ へのスキャッタがマスクカウントのフォールバックなしで無限ループになり、partial-VL 行が存在しない PAT_VL<N> パターンを生成する。ツールチェーンの類：vsts_pack_quarter に 16 ビット分岐がないため b16 ベクトル上の PK4_B32 ストアが黙って破棄され、モジュールシリアライズが device source を失うためキャッシュされたカーネルが起動失敗時にソースを参照できず、msprof バックエンドの自動チューニングがワーカースレッドで signal.signal() を呼ぶために必ず失敗する。

これらは散発的な不満ではなく、形態的には組織化された監査のようだ。同一アカウントが30分以内にテーマ別に連続してコミットし、タイトルは「[BUG] Ascend: …」に根因の要約を加えたもので統一されている。上流にとっての意義は、昇騰フロントエンドの「健全性」の欠落が一度に俎上に載せられたことだ——3060項目の毎日テストが全て通ることは、不正な入力が拒否されることを意味しない。テストがカバーするのは合法パスだからである。

4.2 審査中の修正が監査と呼応：VMI mask 検証、SIMD fill 復元、E4M3 ND/NZ コピー（11-11）

当日更新された審査中の PR の中に、ちょうど上記の欠落に対応するものがあった。#3861 と #3917 は同一事項の2本立てである：VMI 単項およびベクトル-スカラー工場はこれまで mask について「在るか否か」だけを確認し、dtype とチャネル数を確認していなかった。そのため通常のベクトルを述語として渡しても codegen まで一通り到達できてしまう——vabs、vneg、vrelu、vexp、vln、vsqrt、vnot の7オペレータがすべてこの工場上に構築されており、ベクトル-スカラー側の vadds、vmuls、vmaxs、vmins、vshls、vshrs にも弱形式が存在する。

#3795 が修正するのは #3512 の別の副作用である：T.SimdVF() 内で int32 UB バッファに対して T.clear を行う際、生成されるベクトルブロードキャストが浮動小数点のみをサポートしており、PTO コンパイルが失敗する——PTO パイプラインが専用の Parallel pass で元の SIMD pass を置き換え、fill の下降をうっかり失っていたからだ。修正方法は、buffer-version 正規化の後、PTO Parallel 検証の前に LowerSimdVFFill を補い、連続かつ完全なベクトル領域には vdup/vsts を再利用し、それ以外は従来の経路を通す；同時に浮動小数点 tl.simd.vdup の数値変換を保持し、「int32 の 7 がビット単位でブロードキャストされて約 9.809e-45 になる」問題を修正する。

#3639 は E4M3 の ND/NZ UB から L1 へのコピーを補い、#3926 は T.Kernel に非正の block 数と負の Pipelined num_stages を拒否させ、#3854 は SimdVF 下降におけるサブバイト要素のゼロ除算を修正し、#3668 は AIV コアが T.PerCoreTask() 内で UB から GM へのインターリーブ・ストライド書き込みを補う。他に #3915 と #3916 が AssertStmt のエラー種別と条件チェックのインラインアサーションを処理している。

情報源：https://github.com/tile-ai/tilelang/pull/3861 、 https://github.com/tile-ai/tilelang/pull/3795 、 https://github.com/tile-ai/tilelang/pull/3926

4.4 口径修正：K3 の2項目 Q1 対照の旧 Triton 成果物が -128 の負号でオーバーフロー（11-11）

これを単独で挙げるのは、それがスコアではなく比較可能性に影響するからだ。ベンチマークリポジトリは weft-parity をリリースした同じコミット群の中で開示した：K3 の2項目 Q1 対照はこれまで保持された Triton Canonical プログラムを使用しており、このプログラムは −128 の負号でオーバーフローする——境界入力で −2048 が得られ、正しい結果は 0 であるべきだ。正確な I8 リダクションを修正した共有コンパイラが再生成された後、両フロントエンドの成果物は当該入力に通過する；履歴の所要時間は triton_historical_us フィールドに保持され、修正説明は triton_control_note に記載されている。

対照実装の誤りはベンチマーク系プロジェクトのよくある落とし穴である：参照側が境界入力で誤ると、被測側の「参照に劣る」は参照の方がより速く誤っているだけかもしれない。この開示と 2.8 のペアリング口径を合わせて見ると、この CPU ラインが「作者のプログラムを外部ライブラリと比較」から「同一コンパイラ成果物のペア比較」へ移行していることを示しており、方法論的にはより信頼できるが、2つの表は混用できない。

情報源：https://github.com/Tianchen-ai/tilelang-weft-bench/blob/main/docs/results.zh-CN.md

5. トレンド観察

第一に、昇騰のメインラインにおける比重が引き続き上昇しており、かつ「オペレータの補完」から「実行パスとソルバーの補完」へと移行している。今期のメインリポジトリの3件のコミットはすべて昇騰である。実行バックエンドのデフォルト変更、ソルバーの下限の厳格化、アトミック操作の型体系への適合である。これら3件はいずれもオペレータのリストを増やしておらず、「同じプログラムがどのようにコンパイルされ、実行され、そしてどのくらいの時間でコンパイルが完了するか」を変更している。10月以降の記録と対照すると、昇騰側のマージはAscendCオペレータの補完から、インターフェースセマンティクス、実行バックエンド、スケジューリングソルバーという3つの層へと進んでいる。

第二に、CUDA側は長いレビュー期間に入っている。前回はCUDA命令レベルのプリミティブが3件メインラインに入ったが、今期はマージゼロで6件がレビュー中である（ldmatrix/stmatrix、256ビットベクトル化、im2colスケジューリング、パイプラインオペランドのライフサイクル、非同期GEMMのライフサイクル、PASS設定名前空間）。マージ速度の低下とレビュー待ちキューの肥大化が同時に発生する場合、通常はレビュー帯域がボトルネックになっていることを意味し、開発が停止しているわけではない。

第三に、品質監査が機能開発と並行して始まっている。1日26件の昇騰issueの形態は、コミュニティ内で系統的な不正入力監査を行っている人がすでにいることを示しており、対応する修正PRは当日にキューに入っている（mask検証、負パラメータの拒否、fillの下沉復元）。これはバックエンドを複数の国産チップに展開しているプロジェクトにとって良いことである。3060項目の日次テストがすべて通過することは合法パスが使用可能であることのみを証明しており、不正パスの拒否能力はこの種の監査に頼る必要がある。

第四に、RISC-Vの4つの情報源は連続5ウィンドウにわたり静寂しているが、4つの情報源以外のCPUラインは段階的な結論を示している。TVM路線、MLIR路線、コミュニティインデックスページ、算能TPUの4つの上流はいずれも元の引用のまま停止している。一方、TileLang–Weftは共有Canonicalコンパイラを用いて553項目すべてをTritonの1.03倍以内に収め、4プラットフォームの中位倍率は1.29から1.66である。これは口径切り替え後の結果であり、前回の0.058倍と直接比較できないことに注意が必要である。真の観察点は、この「同一コンパイラ、2セットのフロントエンド」という手法が上流に逆流入できるかどうか、そしてRISC-VのRVV/IMEパスが4つの情報源以外のプロジェクトによって先に走通されるかどうかである。

制限事項：今期はGitHub匿名APIのクォータが収集初期に枯渇したため、PR本文とマージ詳細は検索インターフェースと非デフォルトブランチのコミット原子ストリームで補完し、一部のPRのファイル数と行数は検索インターフェースの戻り値であり、diffを逐行再確認していない。hygonとmlir-ascendのマージは非デフォルトブランチにあり、ブランチごとに個別に確認済みである。ニュース側はゼロヒットのみで、外部報道によるクロス検証はない。
