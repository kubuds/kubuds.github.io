今日の重点

このウィンドウの主線は後始末である。メインリポジトリの5件のマージ（+1903/−617、22ファイル変更）には新規オペレータの追加も新規バックエンドの追加も一切なく、4件はいずれも #3512 のPTOベクトル化改造の尻拭いである。VMI記述子がtyped viewのgather/scatterおよび単一要素ロードで誤った値を取る問題を #3894 が6ファイル・+925/−550で一括修正し、分析式走査がスカラー定義を早期バインドし IntSet が回り込みcastで評価時に例外を投げる問題には #3793 が保護を追加し、レーン配置推論が明示的SIMDのベクトルブロックアドレスをスカラーレーンアクセスとみなして旧来の書き方がコンパイル不能になる問題には #3796 が旧パスを残し、codegen_pto が si32/si64 を発行する一方PTOのアトミックがsignlessしか受け付けない問題には #3792 が呼び出し境界で局所的な再解釈を行った。これら4件に共通するのは「改造後、従来の正当なプログラムが正当でなくなる」という点で、大規模変更の必然的なコストではあるが、11-10から11-13まで4ウィンドウ連続でこのコストを支払っていることは、PTO路線のリグレッション範囲が想定より広いことを示している。

5件目の #3614 は性質が異なる。バグ修正ではなくデッドロック防止である。昇騰カーネルには2つのスケジューリングモードがあり、mode=0 は「使用可能なコアがあればオペレータを起動」、mode=1 は「オペレータに必要な全コアリソースが揃ってから全体を起動」である。全コア同期を行うオペレータを通常モードで起動すると、一部のコアだけを得て先に全コアバリアに到達し、残りのコアを待つことになるが、その残りのコアは別のストリームに占有されている——リソースが環をなし、デバイスはそのままハングする。この変更はcodegen側で「定数0を伴うコア間同期」を識別すると自動的に __schedmode__(1) を設定し、当該フラグを関数ごとにリセットして後続のエントリへ漏れないようにする。同時にコア間set/waitインターフェース内の整数形態のmodeを0/1/2/4に狭め、非整数は検証せず記号量を保持する。リグレッションファイルは78行で、全AIC、全AIV、AIC+AIV組み合わせプロトコル、3つのローカルモードとフラグリセットの計7ケースをカバーする。

ROCm側の動きは昇騰以上に記録に値する。ウィンドウ開始から1時間足らずで、同一アカウントが7件のPRを連続して開き、22ファイル・+624/−19、すべて 72d986e1 をベースとし、HIP側の完全なパッチ群を構成している。コンパイル引数がこれまでキャッシュキーにだけ入りhipccに入っていなかった問題（#3954）、8ビット整数ベクトルの8/16レーンブロードキャストがhipccに拒否される make_uint2/make_uint4 を発行する問題（#3955）、小タイル上の T.gemm が「Divide by zero」のような無意味な情報を報告する問題（#3956）、T.annotate_min_blocks_per_sm がHIP上で破棄され、gfx90a上で256×128×32のfp16 GEMMが143個のVGPRと128個のAGPRのために1CU1ブロックに固定される問題（#3957）、占有率とscratch使用量が生の数値のみで換算がない問題（#3958）、wave64上で64スレッドのリダクションが無駄にLDSを1ブロック確保する問題（#3959）、HIPでは uint2/uint4 が構造体でありループをまたいで残留するfp16フラグメントがSROAでスタックに押し戻され、レーンあたり80バイトのscratchを消費する問題（#3960）。ROCmはこれまで本デイリーレポートの記録では長らく「たまに1件」であったが、1日のうちにシリーズとして出現したのは今期最も明瞭な構造的変化である。

1. コアプロジェクトの進展

1.1 昇騰：クロスコア同期 mode=0 でバッチスケジューリングを強制、全コアバリアがマルチストリームとコアを奪い合ってデッドロックしなくなる（#3614）

この変更は5ファイル、+102/−1で、うち78行は新規の回帰ファイル（test_ascend_schedmode.py、testing/ascend/target/ 配下）で、実際のコンパイラ変更はわずか二十数行だ。Ascend codegen で「定数 0 を伴うクロスコア同期」を識別したら __schedmode__(1) を付与し、このフラグを関数ごとにリセットされるメンバーにして後続のエントリへ漏れないようにする。

その必要性を理解するにはスケジューリングのセマンティクスに戻る必要がある。昇騰カーネルの mode=0 は通常モードで、オペレータに必要な部分的なコアリソースが利用可能になれば起動し、異なるストリームのオペレータは重複できる。mode=1 はバッチモードで、オペレータに必要なすべてのコアリソースが揃ってから全体を起動する。全コア同期を行うオペレータ（全 AIC 同期、全 AIV 同期、および「AIV とローカル AIC の同期 → 全 AIC 同期 → ローカル AIV へ再同期」という組合せプロトコルで、その内部に mode=0 段階を含む）が通常モードで起動すると、一部のコアだけを取得したまま全コアバリアで待機し、待っているコアは別のストリームに占有されて解放されず、リソースが循環してデバイスがデッドロックする。バッチモードが排除するのはこの窓だ。

ついでにインターフェースの絞り込みも行った。クロスコアの set/wait インターフェースで整数形態の mode_id は 0、1、2、4 のみ受け付け、それ以外の整数は直接拒否する。非整数は検証せず、符号量パラメータ伝達の可能性を残す。ドキュメント文字列にも実情を一句補った。同一の API ドキュメントに列挙されたモードは3つのターゲットで一致しない。910B/910C は 0/1/2 をサポートし、950 で初めて 4 が加わる。回帰は7種の情形をカバーする。全 AIC、全 AIV、AIC+AIV の組合せがそれぞれバッチモードを開くべきこと、mode=1/2/4 はデフォルトを維持すべきこと、そしてフラグが関数間で残留しないこと。

ソース：https://github.com/tile-ai/tilelang/pull/3614

1.2 昇騰 PTO：VMI 記述子と論理カバレッジ検証を一括で収束、単一 +925/−550 は本期最大（#3894）

#3894 は本調査期間最大の一件（6ファイル、+925/−550）で、2つの独立した事柄を1つのブランチにまとめた。1つ目は VMI メモリ記述子の修正で、2種類の形態に関わる。typed view の gather/scatter、および単一要素ロードで、両者とも記述子構築時に取得するベースアドレスとストライドが実際のアクセスと一致しない。2つ目は VMI フロントエンドの冗長な論理カバレッジ拒否を削除すること。

2つ目の前提は明確に書く価値がある。検証の削除は緩和ではなく、共有メモリ検出器の修正（#3805）がすでに着地しているため、フロントエンドで再度阻止するのは重複した阻止であり、しかも行跨ぎ、転置、動的ビューという本来通すべき形態を誤って傷つける。言い換えれば、同一のセマンティクスを2つの階層でそれぞれ判断しており、先に着地した方が直れば、後者は負担になる。

−550行の削除量は主にこの2か所の収束によるものだ。下流への意味は、typed view の gather/scatter と単一要素ロードという2種類の書き方が PTO ターゲット上で「通るが結果が違う」から「正しいか、検出器に止められるか」に変わることだ。

ソース：https://github.com/tile-ai/tilelang/pull/3894

1.3 昇騰 PTO：スカラー cast の事実に保護を追加、回り込み cast が IntSet 評価で例外を投げなくなる（#3793）

再現形態は小さい。u = uint32(i - 1)、i は [0, 63] に落ちる。u はどの VMI アドレスとも無関係だが、LegalizePTOVMIMemoryAccess はそこで失敗する。根本原因は #3512 が導入したアナライザー感知走査にある。これはスカラー定義を積極的に分析コンテキストへ束縛し、IntSet が cast 端点を評価する際、他の子アナライザーがすでに過小評価された界を装入していると、回り込み cast が例外を投げる。

修正方法は沈み込み期に安全でない分析をスキップする（2 ファイル、+571/−13）。この種の「アナライザ間で仮定が相互汚染される」問題は、大規模改修後のコンパイラで最も時間を要する。エラー位置が故障と無関係なスカラー上にあり、スタックからも誰が先に境界を誤って設定したかが見えないからだ。

情報源：https://github.com/tile-ai/tilelang/pull/3793

1.4 昇騰 PTO：明示的 SIMD 並列ループがレーン布局推論に拒否されなくなる（#3796）

#3512 で導入された PTO レーン布局推論は、既存の T.Parallel ネストを拒否していた——中に明示的 SIMD 命令が書かれている限り。原因は、推論がこれらのループのアドレスをスカラーレーンアクセスと見なし、実際にはベクトルブロック上をイテレートしていることにある。

典型的な例は PR に書かれている：T.Parallel(2, 32) ネストで、ループ本体が S.vld(temp[h, block * 64]) と対応する S.vsts(...) を使い、各イテレーションで 64 要素の FP32 ベクトルを処理する。この書き方は推論登場以前は合法かつ一般的だったが、推論オンライン後は一律コンパイル失敗する。5 ファイル、+194/−17 の変更で、旧式の明示的 SIMD 並列セマンティクスを維持し、推論はそれが担当すべき形態にのみ作用させる。

情報源：https://github.com/tile-ai/tilelang/pull/3796

1.5 昇騰 PTO：整数アトミックを signless 互換ラッパー経由に変更、符号付き入力もコンパイル可能に（#3792）

#3512 以降、codegen_pto は TileLang の整数値に対して pto.si32/pto.si64 を発行していたが、PTO のアトミックインターフェースは signless の i32/i64 のみを受け付けるため、整数バッファ上の T.atomic_add、T.atomic_max、T.atomic_min がすべてコンパイル失敗していた（前回の同一バッチ項目で既に言及、本調査期間 11:27 に主干へ着地）。

修正は生成される呼び出し境界での局所適応のみ（4 ファイル、+111/−36）：ポインタとオペランドを同幅で signless に再解釈し、ポインタのアドレス空間を保持し、戻り値を論理型に復元する。min/max は元の符号付きまたは符号なし比較セマンティクスを維持する。これにより #3512 で確立した論理型体系を覆す必要がなく、適応はアトミック層に圧縮される。

情報源：https://github.com/tile-ai/tilelang/pull/3792

5. トレンド観察

一つ目は、大改造の後処理期間は改造期間より長く、しかもコストは「もともと合法だったプログラムがもはや合法でなくなる」ことに乗る。#3512 は PTO のベクトル化と型体系を一緒に置き換え、その後連続四つのウィンドウがその回帰面を補っている：実行バックエンドのデフォルト変更（11-11）、整数アトミック（11-11、11-12）、明示的 SIMD 並列ループとスカラー cast の事実（11-12）、VMI 記述子（11-12）。これら四類の問題の共通点は「新機能の計算ミス」ではなく、「旧来の書き方がコンパイルできない、または結果が変わった」ことである。コンパイラプロジェクトにとって、この種の回帰の調査コストは新機能の bug よりはるかに高い——エラー位置はしばしば故障と無関係なスカラーやアドレスの上にあり、スタックからは誰が先に仮定を誤って仕込んだのかが見えない。

二つ目は、バックエンドのマトリクスが「一社独走」から「多点同時着工」に変わり、形態も四類に分化した。本期の主リポジトリの五件はすべて昇騰だが、同じウィンドウで ROCm が一度に七件を系列として開き、海光が一ブランチで一日十件、Sunrise がリリースパイプラインを進め、Hexagon が個人 fork の形で TileLang を携帯電話の DSP に押し込んでいる。四つの形態（上流内蔵バックエンド、ベンダー適応リポジトリ、独立ディストリビューション、サードパーティ fork）は四つの投入深度に対応し、この分化自体が各ベンダーの依存度を判断するための利用可能な指標になる：ベンダーリポジトリはバージョンに従い、ディストリビューションはメインラインに従い、fork は自社ハードウェアに従う。

三つ目は、「agent 向けのエンジニアリング化」が規模を伴って現れ始めた。mlir-ascend の harness ブランチは一日で +7632 行、内容はスキルライブラリ、シミュレーション trace フローと Roofline 計算機で、サービスの対象は「オペレータを書く人または agent」であってコンパイラ自体ではない；同じ週に、Hexagon fork の README はバックエンドとモデルが AI agent によってメンテナの指導の下で書き直されたこと、四日間で 75 の PR が現在のコードの八割以上を占めることを直接明記している。二つの事柄の方向は一致している：TileLang のような DSL の抽象層はちょうど「agent が正しく書ける」粒度に落ちるため、エコシステムは人のためだけにドキュメントを整えるのではなく、agent のためにツールチェーンを整え始めた。この項目は週次で追う価値がある。

四つ目は、RISC-V の四情報源が連続六つのウィンドウで沈黙し、全体の活発度と明らかな対照をなしている。TVM 路線、MLIR 路線、コミュニティインデックスページ、算能 TPU の四つの上流はすべて元の引用のまま停止し、同期間に主リポジトリは一日五件のマージ、ROCm は一度に七件、サードパーティ fork は新しいハードウェアバックエンドを進めている。四情報源の外のあの CPU ライン（Weft）も 11-11 に段階的結論を出した後は更新されていない。判断は変わらない：RISC-V 側の TileLang の作業は依然として「路線あり、コミット少なし」の段階にあり、本当に追える着地点はあの二つの相互に独立した実装路線が引き続き推進されるかどうかである。

限界説明：本期は GitHub 匿名 API の枠（60 回/時間）が収集の早期に枯渇し、その後は枠を消費しない二つのチャネルで補完した——PR の増減行とファイル数は diff エンドポイントの統計で、非デフォルトブランチのコミットはブランチ級 atom ストリームで；したがって 1.2 から 1.5 の四件のマージのファイル数と行数は diff エンドポイントの実測値であり、本文の記述は検索インターフェースが返した PR 摘要を採り、diff を逐行再確認していない。Hexagon fork のウィンドウ内プッシュは七つのブランチの atom ストリームを一つずつ照合して fix/hexagon-dma-load-only に特定し、残りのブランチには同期間の新規コミットはなかった。サードパーティオペレータリポジトリの公式属性はリポジトリ自体からは検証できず、本文に注記した。ニュース側はゼロヒットのみで、外部報道による交差検証はない。
