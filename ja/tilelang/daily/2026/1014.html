1. 中核プロジェクトの進展

1.1 メインリポジトリ：ROCm 二件——DeepSeek mHC 前/後カーネルと safe-gated KDA デコード例（10-13 ~ 10-14）

日付：2026-10-13、2026-10-14　情報源：DeepSeek mHC（#3156）／ KDA デコード例（#3249）

  • DeepSeek mHC 前/後カーネル（#3156、2 ファイル、+83/-6、10-14 未明にマージ）：mHC 前処理は CUDA 上で 96 スレッドブロック内の 32 スレッド境界で役割分担し、TF32 GEMM 入力を採用；CDNA 上ではこれがネイティブ 64 lane 波面を分割し、かつ TF32 は MFMA の入力型ではない。HIP パスは完全な目標サイズ波面上で分割ロールを実行するよう変更し、FP32 混合重みを共有メモリ上で BF16 に変換して MFMA 計算に供する；CUDA 側は元の 96 スレッド / TF32 レイアウトを維持し、さらに gfx942 の前/後カーネルの正確性カバレッジ（32 token 前処理、8 token 後処理などのケース）を補完。
  • safe-gated KDA デコード（#3249、+360/-0）：パック済みデコードカーネルを新規追加——畳み込み後のパック QKV と生のゲーティング入力（a、b、A_log、dt_bias）、FP32 状態プールとリクエスト別状態インデックスを消費；Q/K L2 正規化と delta-rule 再帰更新を実行し、指定状態スロットを in-place で書き換え [batch, 1, value_heads, value_dim] を出力；負の状態インデックスはゼロを出力し状態プールを変更しない。実装は次元でパラメータ化し、モデル名/アーキテクチャディスパッチを含まず、ドキュメントでは GLM-5.3-Flash TP8 の専用化構成を提示。

1.2 メインリポジトリ：昇騰コンパイル面二件——SimdVF マルチバッファ T.fill（#3455）と bisheng 一時ファイル削除（#3461）（10-13）

日付：2026-10-13　情報源：SimdVF T.fill（#3455）／ bisheng クリーンアップ（#3461）

  • #3455（+247/-31）：昇騰 SimdVF の LowerFill は元々バッファ全体の充填（各次元が 0 から始まり範囲がバッファ形状と等しい）のみをサポートしていた。マルチバッファパイプラインでは MaterializeMultiBuffer がバッファにバージョン次元を追加し（例えば [64] の論理バッファが [2, 64] の物理バッファになる）、ループ内の T.fill は現在のバージョンスロット [v:v+1, 0:64] のみを充填すればよいが、バッファ全体チェックに拒否されていた。本コミットでは処理対象を実際の充填領域に変更し、領域の起点と範囲に従って各 VReg データブロックの書き込みインデックスを計算し、定数範囲、連続性、VReg アラインメントをチェックし、コンパクトレイアウトと明示的 stride をサポートする。NPU テストを 3 例追加（1D / 2D / 二段階パイプラインのマルチバッファ）。
  • #3461（+2/-1）：bisheng wrapper が一時ディレクトリを作成する際に keep_for_debug を渡していなかったため、コンパイルされた AscendC ソースが常に削除されていた——一方 nvcc、hipcc、PTO wrapper はいずれも keep_for_debug=not env.should_cleanup_temp_files() を渡している。本コミットでこれに合わせ、TILELANG_CLEANUP_TEMP_FILES=0 が昇騰バックエンドでも同様に有効になるようにした。

3.1 TileOPs：MoE 二重オペレータが確定——masked FP8 グループ GEMM と DeepSeek グループ top-k（10-13）

日付：2026-10-13　情報源：masked FP8 グループ GEMM（#2521）／ DeepSeek グループ top-k（#2535）／ MoE MMA 化リファクタリング（#2551）

  • masked FP8 グループ GEMM（#2521、20 ファイル、+1788/-37、#2388 をクローズ）：MoEGroupedGemmFP8FwdOp が spec から着地——FP8 e4m3 グループ GEMM、1x128 / 128x128 ブロックスケール、bf16 出力、セマンティクスは deep_gemm の masked 変体に整合；マニフェストは masked レイアウトに絞り込み済みとマーク、14 行の負載：E=8 の 2 行に EP=8 デコード 12 行を加算（DeepSeek-V3、Qwen3-235B-A22B、Kimi-K2、batch 64 / 256）。新たに moe.masked_routed_metadata ジェネレータがエキスパート不均衡を模擬（DeepSeek-V3 b64 空 4/32、Kimi-K2 b64 空 13/48）；sm90 カーネルは TMA producer warp + 2 つの WGMMA consumer warpgroup の永続グリッドで、タイル走査はデバイス側で行数を読み、空タイルは CTA を占有せず、各重みタイルは HBM から一度だけ読み込まれる。
  • DeepSeek グループ top-k（#2535、15 ファイル、+1193/-69、#2268 をクローズ）：FusedTopKFwdOp が num_expert_group、topk_group、routed_scaling_factor を補完（vLLM grouped_topk セマンティクス）、FusedMoEFwdOp / 共有エキスパートパスも同期；T=512 時にデフォルト TOKENS_PER_BLOCK が 32 ブロックを 32/132 の SM 上に配置するスケジューリング問題を修正；ドキュメントで fast-math の境界を明示。

  • 調査期間内に MoE 面で 2 件を連続して受領：masked FP8 グループ GEMM（deep_gemm masked セマンティクスに整合）と DeepSeek グループ top-k（vLLM grouped_topk に整合）が同日に合入され、加えてコンパクトな行単位レイアウトが統一して MMA カーネルに取り込まれた——TileOPs の MoE カバレッジは「オペレータを個別に補う」段階から「モデルレシピ単位で収束させる」段階へ移行し、DeepSeek-V3 / Qwen3-235B / Kimi-K2 の負荷がバッチで登録された。審査側では同テーマ（gpt-oss swigluoai エキスパート、permute-align、エキスパート検索スキップ）が継続的に厚みを増しており、MoE は現在の TileOPs で最も優先度の高い方向である。

  • 1 日に foundry 性能の合入 8 件と新規起票 8 件：GEMM（タイル再配置、統合選択、単一 WGMMA）に続き、プーリング、正規化、リダクション、RoPE が全面的に展開され、しかも各件に対照ベンチマーク（torch-compile / cuBLASLt / quack）が付属している。単独作者の日次更新リズムが示すのは：TileOps の性能エンジニアリングは「重点オペレータへの攻堅」から「全オペレータの日次ランキング更新」へ移行し、残存する遅れ（MoE 四行、一部 16 ビット除算行）が逐次記録されていることである。
