今日の重点

この調査期間で最も重い動きは引き算だ。メインラインは3週間前にマージされた正確なスレッドカウント（#3291）を丸ごとリバートした（#3733）。理由は率直に書かれている。あの変更は高コストなカウントクエリをフルブロックフェンスチェックの前に移動させたため、全スレッドがフェンスに到達する場合でも証明を実行する必要があり、現在の TVM の求解予算が枯渇して部分カウントが返され、本来合法な remap と sequence の補助 kernel が「Cannot prove a thread rectangle」でコンパイル失敗する。リバートは2つの ThreadSync 実装で同時に行われ、#3291 が導入したテストを削除し、「ループが大多数のスレッドにとって空でも、256 スレッドが依然として全員フェンスに到達する」というリダクションケースを追加した。商ガード、正確な参加スレッド境界、非矩形スレッド集合といった正確性の改善も一緒に撤回され、新たに開かれた #3732 は移行後の再最適化の追跡チケットとして残された。これは一時的な措置と明示的に記載された移行のための譲歩だ。TileLang は現在の TVM fork 依存から脱却するために TIRX 移行を準備しており、付随する TVM fork 最適化提案はすでにクローズされている。

第2の線は昇騰が基盤を補っている。#1948 が修正したのはホスト側の演算子規模に依存しない固定コストだ。Cython wrapper は毎回の呼び出しで無条件に TVM Analyzer を構築しており、実測で 910B3 上では1回あたり約 0.28 ミリ秒かかるが、それが使われるのは形状がシンボリック式の場合だけだ。遅延構築に変えた後、vec add のシングルブロックは 442 から 467 マイクロ秒から 105.1 マイクロ秒に、32 ブロックは 441 から 493 マイクロ秒から 108.0 マイクロ秒に、kpool 圧縮は 447 から 450 マイクロ秒から 111.3 マイクロ秒に短縮された。下限となる素の ctypes 呼び出しは約 12 マイクロ秒で変わっていない。同時期に #1971 の RFC は同期実装の置き換えロードマップを示した。メインラインの同期コアを移植し、独立した Z3 証明サービスを追加し、旧 TIR アダプタ層で既存のコンパイルパイプラインに接続し、TVM、スケジューリング、メモリプランニング、AscendC/PTO codegen、ランタイム ABI を維持し、受け入れ基準を通過した後にデフォルト実装に切り替えて旧アルゴリズムを削除する——#1975 で Ascend リポジトリ全体をメインラインのマルチバックエンドアーキテクチャに移行するのと同じ事柄の2つの着地点だ。

第3の線はオペレータライブラリにある。TileOPs は 11-01 の1日で13コミットをマージし、ほぼすべてが性能パッチで、各コミットに H200 実測表と manifest 回帰基準が付属している。そのうち #2808 は GQA の密なフォワードのプログラム選択を1つのルールにまとめ、最速候補プログラムに対する選択後悔を 1.818 から 1.017 に引き下げ（2 から 128 個の query 位置、586 回の呼び出し）、メインラインの実際のバグも修正した。score scale が log2(e) を掛けた後で FP32 下で消失し、出力が NaN または誤った値になる問題だ。

1. コアプロジェクトの進展

1.1 メインライン：ThreadSync の正確なスレッドカウントをリバート、TIRX 移行に道を譲る（#3733）

11-01 14:50 にマージ。リバートされた #3291 は正確なスレッドカウントをフルブロックフェンスチェックの前に移動し、矩形認証を追加したが、代償として全スレッドがフェンスに到達する場合でも CountSatisfyingValues を実行する必要があった。TVM 側の求解予算が枯渇すると部分カウントが返され、remap と sequence の補助 kernel が「[ThreadSync] Cannot prove a thread rectangle」で失敗する。回帰はメインライン cc903dcb9 に未変更の TVM pin 4211874e9e を加えた環境で再現し、新しいケースでは「ループが大多数のスレッドにとって空でも、256 スレッドが依然として全員フェンスに到達する」に縮小された。リバートは共有と昇騰の両方の実装を同時にカバーし、フルブロック高速パスと旧来の部分カウント動作を復元する。原文はこれが TIRX 移行期間中の一時的な緩和であることを明示しており、TVM fork 側の最適化提案 tile-ai/tvm#89 はクローズ済みで、今後の最適化は #3732 に移された。

出典：https://github.com/tile-ai/tilelang/pull/3733

1.2 メインライン：CUDA のクロス warp 全リダクションを1回の共有メモリ交換に統合、256 スレッドが6バリアから2バリアに低減（#3715）

10-30 20:26 にマージ。旧実装は CUDA リダクションヘッダ reduce.h 内で threads/2 から scale まで再帰し、offset が 32 以上の各ステップで完全な共有メモリ書き込み読み取り交換と2バリアを実行していた。256 スレッドブロックの3ステップ（128、64、32）で合計3回の共有メモリ往復、6バリア、512 スレッドブロックでは4回、8バリアだった。改法はすべてのクロス warp ステップを1回の交換に圧縮する（要素ごとに1回の st.shared、合計2バリア）。まず warp 内で scale が 32 未満の部分を実行し、次に各 warp 内グループで cross_radix 以下のいくつかの lane が協調して折り畳み、レジスタ圧力には上限がある。スカラーパスとバッチパスの両方が変更された。

出典：https://github.com/tile-ai/tilelang/pull/3715

1.3 メインライン：PTO バックエンドの T.Parallel ベクトル化が最初のマイルストーンを達成、要素ごとの演算子が VMI 命令を使用（#3512）

10-30 01:29 にマージ。目標は、ユーザーが T.SimdVF(lanes=L) 内でスカラー並列の要素ごとの T.Parallel を記述し、コンパイラが PTO VMI 命令へベクトル化し、さらに PTOAS を経て昇騰 950 上で実行できるようにすることである。役割分担は明確に書かれている。TileLang 側は論理 lane レイアウトの導出、ベクトル化パスのパイプライン、VMI 命令生成と Fragment 論理マッピングを担当し、PTOAS 側は物理レジスタ分割、マスクの具体化、Fragment バッファとベクトルレジスタの割り当て、mem_bar の挿入を担当する。ロードマップは五つのマイルストーンに分かれており、本件は M1 コアフレームワーク（要素ごとの計算、extent が lanes で割り切れる場合と割り切れない場合の両方をカバー）であり、M2 制御フロー、M3 reduce、M4 UB 容量計画とレジスタ割り当て、M5 非連続アクセスとより広い PACK データ型が順次続く。

出典：https://github.com/tile-ai/tilelang/pull/3512

1.4 メインライン：昇騰 DeepGEMM の scale バッファを書き込みカウント付きマルチバッファに変更し、データロードを条件付きロードの前に移動可能に（#3629）

10-30 05:48 にマージ。DeepGEMM は複数の K ブロック間で scale factor を再利用する。本件では明示的な書き込みカウント付きマルチバッファモードを新設し、scale バッファのバージョンが実際の書き込みに応じて進むようにした。各 owner ループ反復では、実際に実行される最初の書き込みタスクでのみ一度バージョンを進め、後続の書き込みはそのバージョンを共有し、書き込みのない反復は旧値を引き継ぎ、複数の互いに素な owner と共有クロックをサポートする。これによりデータロードを条件付き scale ロードの前に配置できる。同時に DeepGEMM の K ループを平坦化し、L1 と L0 の両方で先にデータを取得してから scale を取得するようにし、ガード更新、ネスト更新、保持読み取り、flag とバッファ再利用、および FP4 の K 主順序と MN 主順序で末尾ブロックとリングラップを含むユースケースを追加した。このモードは明示的なバージョン数を要求し、各 owner 反復で最大一回の更新を前提とする。

出典：https://github.com/tile-ai/tilelang/pull/3629

1.5 メインライン：二件の修正がマージ、CPU スカラー GEMM は対象領域のみクリア、負インデックス合法化は到達不能分岐をスキップ（#3709 / #3712）

二件とも 10-30 にマージされ、前号で審査中だった項目の着地である。#3709 は CPU スカラー GEMM が対象領域のみをクリアするようにし、従来は今回の出力に属さない範囲までクリアしていた。#3712 は LegalizeNegativeIndex が到達不能分岐をスキップするようにし、実行されないコードに対する負インデックス書き換えを回避する。これら二件は前号レポートの #3708、#3710 と同じ欠陥整理のバッチに属し、うち #3708 のビット幅を int64 に変更する件、#3710 のキャッシュ無効時に二層のプロセス内キャッシュをバイパスする件は依然として審査中である。

出典：https://github.com/tile-ai/tilelang/pull/3709、https://github.com/tile-ai/tilelang/pull/3712

1.6 メインライン：言語層で proxy 内の未使用の Ref プレースホルダ二つを削除（#3722）

10-31 17:31 にマージ。tilelang/language/proxy.py 内には二つの Ref が同時に存在していた。一つは型チェック用の tirx.Var スタブ、もう一つは空のランタイムクラスで、どちらもツリー内に消費者がない。対外的な T.Ref は実際には eager.builder 由来であり、そちらの実装がマクロ参照引数の本体である。本件では二つのプレースホルダ、_T 型変数、およびそれに伴い不要となった Generic、TypeVar のインポートを削除し、T.Ref とマクロ参照の挙動を保持しつつ、tilelang.language.proxy.Ref という未使用の直接インポート経路のみを除去する。フロントエンド構築テストは 179 件通過、6 件スキップ、ランタイムの同一性チェックで T.Ref が依然として eager.builder.Ref であることを確認した。

出典：https://github.com/tile-ai/tilelang/pull/3722

1.7 新規欠陥と審査中：TMEM の結果サイレント破棄、ROCm のシンボル未検出、TF32 の最近接偶数丸め（#3721 / #3711 / #3714）

#3721 は本調査期間で最も警戒すべき項目である。sm_100a 上で TMEM に対して T.gemm を実行する際、threads/32 が N を整除できない場合、コンパイルは通るが PTX 内に tcgen05.mma が一つもなく、T.copy(Ct, Cl) は誰も書き込んでいない TMEM を読んでおり、積がサイレントに破棄される。再現では threads=256 で一つ出力され、threads=384 でゼロ件となる。作者は src/cuda/op/gemm.cc が TCGEN05 に {1, num_warps} の分割を返す際に網羅性チェックが欠けていると疑っている。#3711 は ROCm 7.14 と 10.0 の PyTorch wheel 下で kernel が「named symbol not found」を報告する。#3714 は審査中で、fp32 から tf32 への変換に最近接偶数丸め（cvt.rn.tf32.f32 と飽和形式）を追加し、非飽和は SM90 以上、飽和は SM100 以上を要求し、対応する機能リクエスト #3713 をクローズする。

ソース：https://github.com/tile-ai/tilelang/issues/3721、https://github.com/tile-ai/tilelang/issues/3711、https://github.com/tile-ai/tilelang/pull/3714

2.1 昇騰：Cython wrapper が TVM Analyzer を遅延構築し、910B3 の単一呼び出しが約 450 マイクロ秒から約 106 マイクロ秒に短縮（#1948）

4.1 RISC-V 研究チェーンが形を成す：3 つのリポジトリが Numba CUDA Python を TileLang に変換し、さらに制限付き PrimFunc を単一 hart の RVV C に落とす（10-31）

コミュニティ研究者 zishu0131-png は 10-31 同日に 3 つのリポジトリを整理した：tilelang-riscv は総合エントリとして研究目標、2 段のコンパイルチェーンとバージョン組み合わせを説明する；numba2tilelang は Numba CUDA Python を静的解析して TileLang ソースに変換する役割を担う；tilelang2rvv はサポートされる実際の tvm.tirx.PrimFunc を RVV intrinsic C に変換し、さらに Clang で RV64GCV ELF にコンパイルして、QEMU virt 上で単一 hart として実行する。作者は境界を明確に記している：これは TileLang 公式に登録されたバックエンドではなく、汎用 GPU モデルシミュレータでもなく、threadIdx に依存するアドレッシング、hart 間同期、未サポートの IR は一律に拒否し、ブロックは順次実行し、shared と fragment は単一 hart のローカル配列にマッピングする；研究環境は TileLang 0.1.15、Clang 23.1.3、QEMU 11.1.0 であり、他のバージョンの互換性は保証せず、また上流のスレッド級成果物を自動的にこのバックエンドが受け入れる入力と見なすことはできないと明言している。

出典：https://github.com/zishu0131-png/tilelang-riscv

4.2 PTO-ISA/tilelangGym が PTO-ISA/tilelang から独立リポジトリ化、主回帰ゲートは昇騰 SimtVF 経路（10-30）

この敏感性・回帰テストセットは PTO-ISA/tilelang の examples/ascend/t_parallel_st_suite から切り出されたもので、その理由はテストセットが TileLang と PTOAS のバージョンを独立して固定できるようにするためである。現在の 3 本の主経路：昇騰 SoftLib SimtVF（target=ascend、cython、主回帰ゲート、remat バージョン上で全通過）、VectorizeParallelToPTO と VL の vload/vstore、そして benches 下で @pto.jit を用いて書かれた手書き SIMD DSL 対照実装；各ケースディレクトリには config.toml と VERDICT.md があり、さらに週次および CI 回帰スクリプトがある。

出典：https://github.com/PTO-ISA/tilelangGym

4.3 ニュース側：Google News の中英文クエリ、Hacker News、arXiv はいずれも調査期間内に実質的ヒットなし（11-02）

3 日間の Google News 中英文クエリは調査期間内に該当する TileLang 関連報道を一切返さず、Hacker News と arXiv にも新規エントリはない；候補リストの 20 件はすべて GitHub リポジトリのプッシュに由来し、通常のコード活動であってニュースではない。今期の情報面はしたがって完全にリポジトリ側とコミュニティリポジトリで構成されている。

出典：https://news.google.com/

5. トレンド観察

この調査期間で最も記録に値する判断は上流自身によるものである：正確性の改善を巻き戻してでも、ThreadSync の複雑度をクリティカルパスから外すことを選んだ。ロールバックの説明にはその代償が明記されている——商ガード、正確な関与スレッド境界、非矩形スレッド集合という 3 種類の改善を一括して撤回し、旧来の保守的経路のみを残し、#3732 は TIRX 移行完了後に改めて最適化を議論する形で保留された。あるコンパイラプロジェクトが「我々の証明器の予算が足りないので、まず保守的実装に戻す」と公開の場で書くことは、機能をどれだけ積み増すよりも、現段階の真の制約をよく示している：TIRX 移行が主線の第一優先であり、他の最適化はすべてそれに道を譲らなければならない。

これと呼応するのは昇騰側の2つの「メインラインへの収束」に関する文書である：#1971 の RFC は同期アルゴリズムをメインラインのコアと独立した Z3 証明サービスに置き換えるもので、まず調査し、その後置き換え、中間に旧 TIR 適配層を残す；#1975 は Ascend リポジトリ全体をメインラインのマルチバックエンドアーキテクチャへ直接移行する。どちらの道も移行コストを伴うため、当面の可視的な作業は基盤系に偏る：#1948 は毎回の呼び出しにかかる固定ホストオーバーヘッドを約 450 マイクロ秒から約 106 マイクロ秒へ削減し、4 件のドキュメント事実確認、CI の内部キャッシュ参照の整理も、いずれもこの種の作業である。

TileOPs のリズムは「リリース」から「チューニング」へ切り替わった。72 時間で 15 件のマージのうち 13 件が同じ日に集中し、ほぼすべてに H200 の実測表と「manifest に回帰なし」の宣言が付され、さらに選択後悔のような指標でスケジューリングルールの良し悪しを記述し始めている（#2808 は 1.818 から 1.017 へ）。これは、オペレータライブラリの競争点が「そのオペレータがあるか否か」から「各 shape ごとに正しいプログラムを選べているか」へ移ったことを意味し、まさにこれが TileLang のような DSL が手書き kernel に対して持つ長期的価値である。

エコシステム側には新たな2つの分岐が現れた。1つはハードウェア方言：海光は gfx948 を gfx946 互換として扱い、昇騰は PTO ドキュメントとシンボル形状の補完を続ける。もう1つは言語出口：RISC-V 研究チェーンは制限付き PrimFunc を単一 hart の RVV C へ降ろす。スター数は非常に少なく、作者も公式バックエンドではないと明言しているが、TileLang の IR を可搬資産として使うものであり、昇騰や海光のリポジトリ級ブランチ適配と同じ類のシグナルである。複数の分岐が同時に存在する中、上流の TIRX 移行が安定した IR 境界を示せるかどうかが、これらの下流投資が定着するか手戻りになるかを決める。
