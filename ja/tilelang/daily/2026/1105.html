今日の重点

この日の主线は「また何を統合したか」ではなく、「昨日の土台が検収され始めた」ことにある。10-14にマージされた #3512 は T.Parallel を PTO の VMI パイプラインへベクトル化したもので、Ascend バックエンドにおける構造的変更だ。整数型を符号なしセマンティクスの i* から明示的な符号付き si* へ変更し、SIMD の lowering を新たな PTO の検証・合法化・ベクトル化という三段フローに引き継がせ、明示的 SIMD 並列ループの判定も書き直した。三週間後、この変更は実際のオペレータ形状の上で四種類のリグレッションとして次々に踏み抜かれた。整数アトミック操作が pto.si32 を受け付けられずにコンパイル失敗し（#3789 報告、#3792 修正）、T.clear が T.SimdVF 内で浮動小数点のみ対応のブロードキャスト経路に落ち（#3795）、スカラー cast の境界事実が VMI メモリ合法化で早期に束縛され（#3793）、明示的 SIMD の並列ループがスカラー lane アクセスとみなされて拒否された（#3796）。さらに整数アトミックを符号なしキャリアへ適応させる一本（#3794）がある。五つのパッチはすべて主线に基づき、互いに依存しない。作者は説明の中で繰り返し同じ一文を書いている——「This PR is based directly on main and does not depend on the other PTO regression fixes」——これは意図的だ。五本をそれぞれ独立してマージ可能にし、過去のように巨大なロールバックパッケージに溜め込むのを避ける。検証も「通った」ではなく、具体的なケース数を伴うハードウェア実測となった。47、18、16、37 項目で、四つの独立オペレータ（SwiGLU、Top-k、Cache、Engram 逆方向）を代表ケースとしている。

第二は計測口径の自己修正であり、しかも二つのリポジトリが同じ日に同じことを行った。メインリポジトリの #3534 は do_bench の L2 フラッシュを「バッファへゼロを書き込む」から「バッファを一度読む」へ変更した。ゼロ書き込みは L2 に丸ごとダーティ行を残し、次ラウンドの計時中にこれらの行を書き戻す必要があり、キャッシュフラッシュのコストを被測定カーネルに摊分してしまう。 #3534 は cache.view(-1, 4096).sum(dim=1) で分割読み込みし、ついでに fast_flush という公開パラメータを削除した——このパラメータは本来 int32 か int8 でバッファを構築するかを選ぶだけのものだった。Ascend 側の msprof バックエンドはさらに徹底しており、元は SimtVF ループでゼロを UB に書き込んでから WTS_FV ストアしていたが、今は NORMAL_FV でグローバルから UB へ読み込む方式に変更し、型も int32 に固定した。TileOPs の #2822 は同じ発想の双子の変更で、さらにフラッシュ方法を記録し、方法が一致する場合にのみ履歴値と比較する。三つの変更を並べて見ると、一つのシグナルだ。性能数値は「バージョン間で比較可能」であることを要求され始めており、単に「今回が前回より速い」だけでは済まなくなっている。

第三はハードウェア前沿への補票だ。B300 が報告するターゲットアーキテクチャは sm_103a だが、CuTeDSL の TMA ヘルパー関数はホワイトリストでアーキテクチャを門前払いしており、B300 上の六つの CuTeDSL ケースが DSL に入る前に ValueError を投げていた。#3772 は sm_103a と gr100（cc 10.7）が報告する sm_107a を一緒にホワイトリストへ追加し、作者は B300 ノードで 8 通過 1 スキップ、gr100 で 13 通過 1 スキップを再現した。同じ調査期間に #3790 は別の道を取る。SM120 上の FP8 加 fp32 累加の GEMM はずっと SM89 の mma.sync アトミックを使っており、RTX 5090 では cuBLASLt の 68% しか出なかった。ue8m0 単位スケーリング付きの block-scaled MMA に置き換えたところ、8192 立方が 463 から 727 TFLOPS へ上昇し、出力は旧アトミックとビット単位で一致した。二つの性質は異なる——一つは「新しいカードを動かせるようにする」、一つは「新しいカードをフルに動かす」——だがどちらも同じことを指している。アーキテクチャ対応の境界は Hopper から Blackwell と国産アクセラレータの両端へ同時に拡大しつつある。

第四は TileOPs のコミットリズムだ。単日 7 本のマージのうち、5 本が性能、1 本が CI、1 本がドキュメント。GQA varlen は SM90 上で KV グループごとにリクエストをパッキングし、短いリクエストの key/value 読み取り回数を KV ヘッドあたり一回に削減した。ArgMax/ArgMin は一波で滞在できる前提の下で各スレッドに 16 バイトベクトルを八つ抱えさせ、(2048, 4096) の bf16 ArgMin は 8.704 マイクロ秒から 7.393 マイクロ秒へ短縮し、FlagGems の 8.543 を上回った。一元逐次要素と正規化系カーネルは「一度だけ読む」オペランドをデフォルトキャッシュ戦略へ戻し、本当に繰り返し読む箇所だけ evict-last/evict-first を残した。これらの変更の共通点は「より速い」ではなく「なぜ速いかを知っている」ことだ——どの変更も対照表を伴い、自分がまだ比較対象に劣っている行を明示している（Softmax の (32768, 4096) は 121.792 から 131.648 マイクロ秒へ後退した）。

11-04 12:46（北京時間、以下同）にマージされ、今期最初のマージとなった。B300 が報告するターゲットアーキテクチャは sm_103a だが、CuTeDSL の TMA ヘルパー関数はアーキテクチャのホワイトリストを保持しており、リストにない値に遭遇すると DSL に入る前に直接エラーを投げ、そのエラーメッセージには許容される値として sm_90、sm_90a、sm_100a、sm_110、sm_120、sm_120a、sm_121、sm_121a が列挙される。fa69f7fa のメインライン上、nvidia-cutlass-dsl 4.7.0 と CUDA 13.3 を組み合わせた環境で、B300 では六つのテストケースがこれにより失敗した。test_tilelang_jit_cutedsl.py の tma_load パスが三つ（GEMM JIT、マルチストリームカーネル、動的シェイプが各一つ）、そしてもう一つの tcgen05 の CuTeDSL テストファイルの tma_store パスにある三つの tmem_copy_roundtrip バリアントである。DSL 自体は sm_103a を受け入れる——その tcgen05 オペレータは sm_100f ファミリー全体を受け入れる——ため、問題は純粋にこのゲートにある。この項目を追加した後、二つのファイルは B300（cc 10.3、CUDA 13.3、cutlass-dsl 4.8.1）上で 8 パス 1 スキップとなった。同じマージでは sm_107a も追加されている。gr100 の bring-up ボード（cc 10.7）がこの値を報告し、同じゲートに引っかかるためだ。両項目を追加した後、同じファイルは gr100 上で 13 パス 1 スキップとなり、その中には #3685 で導入された gather/scatter ファイルも含まれる。

特筆すべきは、作者が明示した検証の境界である。手元に sm_103 のハードウェアはなく、変更は別の報告者（0z5a、#3685 で最初に報告し bisect を行った）が提供した B300 マシンで検証されたものであり、CI は sm_103a をカバーしていない。このような「コードはマージ済み、検証はマシンを借りて実施」という状況はアーキテクチャ追趕期にますます増えていくため、読者はどの機能が実測の裏付けを持ち、どれが単にホワイトリストに追加されただけなのかを知る必要がある。

1.2 メインライン：L2 フラッシュをゼロ書き込みから読み取り専用リダクションに変更、do_bench から fast_flush パラメータを削除（#3534）

11-04 11:27 にマージされ、7 ファイルを変更、36 行追加、49 行削除。うち三箇所が実際の実装で、四箇所はそれに追随するテストである。元々は cache.zero_() であった。cache_size MB のバッファにゼロを書き込んで L2 を追い出す仕組みだが、問題はゼロ書き込み後にバッファがダーティ行で満たされ、次ラウンドの被測定カーネル実行時にこれらの行をメモリへ書き戻す必要があり、その書き戻し帯域が被測定カーネルの時間に算入されてしまうことだった——バッファが大きいほどこの偏差は顕著になる。現在は cache.view(-1, 4096).sum(dim=1, dtype=cache.dtype) に変更されている。4096 列ごとに分割して読み取り、行を L2 に読み込んでリダクション出力を生成するため、ダーティ行の問題は存在しない。分割はブロック全体のリダクションによるグローバル同期を避けるためであり、dtype を保持するのはバッファ全体の int64 変換を一度トリガーしないためである。この変更は同時に bench.py の estimate ループ、torch_bench.py の event、cupti、cudagraph の三パス、そして msprof.py の昇騰専用フラッシュカーネルにも適用されている——後者は元々 SimtVF でゼロを UB に書き込み、WTS_FV でグローバルに書き戻すという典型的な書き込み式フラッシュであったが、現在は NORMAL_FV でグローバルから UB へ読み込む方式に変更され、要素型も int8/int32 の二択から int32 に固定された。

公開インターフェースの変更に注意が必要である。do_bench の fast_flush パラメータが削除された。これは元々 int32 と int8 の二つのバッファ要素型を切り替えるだけのもので（int32 の方がバッファ構築が速い）、現在バッファは int32 に固定されたため、パラメータは意味をなさない。do_bench(..., fast_flush=False) を直接呼び出すスクリプトにとっては破壊的変更であり、リポジトリ内のテストは既に同期修正されているが、外部の利用者にはリリースノートで注意を促す必要がある。

出典：https://github.com/tile-ai/tilelang/pull/3534

1.3 メインライン：AscendC CI の自動チューニング供給テストケースが二台のデバイスを明示的に同期、非同期コピーエラーが arange の失敗に偽装されなくなる（#3784）

11-04 17:01 にマージ。現象は AscendC の CI ジョブにおいて、自動チューニングの set-inputs テストケースのうち [other_npu] というパラメータ化項目が、次の torch.arange() 呼び出し時に srclen=4, dstlen=4 を報告するというものだった——4 バイトの memcpy のサイズ不一致であり、これはまさにクロスデバイスコピープローブの形状である。真の原因はクロスデバイスコピーの失敗が非同期に報告され、エラーが浮上する位置が発生位置より一歩遅れるため、エラー報告箇所が完全に無関係な arange 上に見えていたことだった。修正方法は単純である。プローブの前後にそれぞれデバイス同期（現在のデバイスと npu:other）を追加し、非同期エラーを try ... except RuntimeError のスコープ内に落とし込む。検証はシングルマシンデュアルカードで当該テストケースファイルを実行し、四項目すべてパスし、かつクロスデバイスコピーが実際に非同期失敗した場合、[other_npu] のパラメータ化項目はスキップされ、テストケース全体が失敗することはない。

このコミット自体は小さいが、前号 #3546 の続きに当たる——あのコミットは自動チューニングの入力供給を現在のデバイスに基づいて解析するように変更し、验收時に昇腾デュアルカード上のリグレッションに言及していたが、ここで補うのは同一シナリオの CI 上での安定性である。同一機能を二つの調査期間にわたってそれぞれ一回ずつ修正していることは、昇腾側の自動チューニングが依然として「動くが境界が不安定」な状態にあることを示している。

出典：https://github.com/tile-ai/tilelang/pull/3784

1.4 審査中：ThreadSync の warp 一致性証明に、warp インデックスから組み立てた複合述語を追加（#3787）

このコミットが引き継ぐのは、前号 #3761、#3765 が残した同一領域である：ThreadSync は「バリア参加スレッドが warp 全体で一致している」ことを証明する必要があり、証明できなければ lowering を拒否する。トリガーとなる形状は 192 スレッド下の複合述語 tx < 160 and tx // 32 % 2 == 0 である——warp 0、2、4 は丸ごと参加し、warp 1、3、5 は丸ごと不参加で、分割される warp は一つもなく、本来なら証明可能なはずだが、メインラインは内部エラー「参加スレッドが warp 一致ではない」を直接投げる。作者は比較表を作成し、欠陥範囲を极めて正確に絞り込んだ：単項述語 tx // 32 % 2 == 0、tx % 64 < 32、tx < 160 はメインライン上でいずれも lowering できるが、「境界項と warp インデックスの剰余項を and で組み合わせた」この形態だけが失敗する；一方 tx < 168（実際に第 5 warp を分割する）は両側で正しく拒否される。根本原因は証明器のエンコーディングにある：スレッド番号を二つの仮想スレッドにリネームし、算術ソルバーに linear1 / warp_size == linear2 / warp_size から両側の述語が等しいことを導出させるが、FloorDiv と FloorMod のエンコーディングでは「上界 + 剰余」という組み合わせの下で二つの除算の関係を確立できない。修正方法は threadIdx.x を warp_index * warp_size + lane に書き換え、二つの仮想スレッドが warp インデックスを共有し、それぞれが自由な lane を持つようにする——まさに「同一 warp」という関係そのものである；これにより warp インデックスのみを通じてスレッド番号を読む述語は両側で同一式に潰れ、一致性が証明可能となり、本当に lane に依存する述語は依然として等しくならず、 #3786 に列挙された tx < 168 は引き続き拒否される——証明は緩和されておらず、見落とされていた一類型を補っただけである。

同一作者は同日に #3786 も提出した：T.copy の目的領域がバッファを超える場合、越境アクセスを生成するのではなくコンパイル期エラーに変更する。二つのコミットを合わせると同一の指向である——「コンパイラが黙って誤ったコードを生成する」を「コンパイラが否と言う」に変える。

まず背景を明確にする。10-14 にマージされた #3512（[Ascend][PTO] Vectorize T.Parallel to PTO VMI）は、並列ループのベクトル化を旧 SIMD チャネルから PTO の VMI パイプラインへ移行した。整数型は符号なしの i* から明示的な符号付き si* に変更され、Lowering は Verify、Legalize、Vectorize の三段階を通り、明示的 SIMD ループの判定も再実装された。これら五つのパッチはそれぞれ、それが実オペレータ上で踏み抜いた一箇所に対応している：

  • #3796 明示的 SIMD 並列ループがスカラー lane として扱われる：Engram 逆伝播の初期化は Parallel ネストを使用し、その中で明示的 SIMD ストアが整数ベクトルブロック単位で進み、新しい lane レイアウト推論がそれをスカラーアクセスとして扱い拒否する（M=2, N=32, L=128）。修正方法は明示的 SIMD の分類をレイアウト推論と並列ユニット発見の間で共有し、この種のネストは #3512 以前の汎用レイアウトパスを保持し、自動要素単位ユニットは新しい PTO lane パスを引き続き通す。37 項のテストケースが通過し、代表的なテストケースは Engram 逆伝播（512 token、hc 4、hidden 2048）。著者は同時に一つの制限を明記している：FP32/128 lane の明示的＋自動混合テストケースは生成ソースレベルのカバレッジのみで、現在の PTOAS/Bisheng デバイスコンパイラはこの組み合わせで 6 KiB を超える VF スタック予算を超過し、デバイス実行結果はない。

5. トレンド観察

第一に、昇騰 PTO の清算パターンはすでに定着しており、その利益とコストの両方を記録する価値がある。#3512 は10-14にマージされ、3週間の間に実際のオペレータが次々とその境界を踏み越えており、本日の5件の補完はただ最新のバッチにすぎない。この「まずアーキテクチャを落とし、後からオペレータごとに回帰を清算する」リズムは #1975 のリポジトリ全体移行時にも見られた。利点はアーキテクチャの反復が速く、単一の変更が制御可能なこと、欠点はメインブランチがかなり長い期間「既知の不動作箇所が数か所ある」状態に置かれることである。5つのパッチが意図的に相互依存を避けているのは、メンテナがロールバックの粒度を意識的に下げていることを示す——これは大きなロールバックパッケージにまとめるより成熟しているが、同時により強力なリリース前回帰規律が必要であることを意味する。そうでなければ「独立してマージ可能」が「独立して漏れる」に変わってしまう。

第二に、性能測定が製品特性として扱われ始めている。メインリポジトリの #3534 と TileOPs の #2822 は同じ日に L2 フラッシュをゼロ書きから読み取り専用に変更しており、理由はいずれも「ダーティ行の書き戻しが次ラウンドの計時を汚染する」である。TileOPs はさらに進んで、フラッシュ方法を記録し、方法が一致する場合にのみ過去の読み値と比較する。これは小さな修正ではない：ベンチマーク数値があるバージョン間で比較不能であれば、「どれだけ速くなったか」というすべての結論を再計算しなければならない。測定方法そのものをバージョン管理に取り込むことは、性能エンジニアリングが信頼に足るものになる前提である。

第三に、オペレータライブラリの競争点は「オペレータ数」から「セレクタの品質」へ移っている。TileOPs が本日マージした W4A16 単一再フィット代价モデルと稠密 GEMM のキャリブレーション契約文書、さらに審査中の FP8 グループ GEMM 連続レイアウトと GEMM bias は、明確な一本の線を構成する：まず各形状の合法な配置を列挙し、次に統一された代价モデルで順位付けし、キャリブレーション過程を再現可能な契約として書き下す。この線が正しく引ければ、オペレータライブラリの性能は個別カーネルの手動チューニングに依存しなくなる。誤れば「ある形状は特に速く、他の形状は運任せ」に退化する。

第四に、アーキテクチャサポートの境界が両端で拡大している。一端は新しいカード：B300 の sm_103a、gr100 の sm_107a がホワイトリストに入り、SM120 の FP8 は block-scaled MMA に置き換わる。もう一端は国産アクセラレータ：海光は64バンクの LDS フェーズでマイクロアーキテクチャ級のチューニングを行い、昇騰はコア比や例外ダンプといったエンジニアリング詳細を補完している。この2つの拡大方法は作業量の構造がまったく異なる——新しいカードは主に「パスを通せるようにする」ことであり、国産カードはより「同じパスでハードウェアに近い効率を出させる」ことである。後者ははるかに高い実測密度を必要とし、まさに海光の4件のコミットでテストファイルの比率がこれほど大きい理由である。

最後のリスク面：1つのウィンドウ内で42件の審査中PR更新があり、そのうち12件が昇騰/PTOタグ付き、7件がCUDA/SM/CuTeDSLタグ付き、4件がProfilerに集中している。この構造は、リポジトリの変更圧力が「機能追加」から「境界修正」へ移行しつつあることを示している。ユーザーにとっての良いニュースは、欠陥が1つずつ指摘されていることだ。悪いニュースは、これらの欠陥の多くが検証器、キャッシュキー、証明器といった「普段は見えない」場所に落ちており、それらが顕在化する時にはすでに結果の信頼性に影響を与えていることが多いということだ。
