1. コアプロジェクトの進展

1.1 メインリポジトリ：partial-sync 名前付きバリア id が 2 種類のストレージドメイン間で重複（#3643）

10-25 14:30 にマージ、2 ファイル +57/-1、#3642 を修正。ThreadSync は shared と shared.dyn に対してそれぞれ 1 回ずつ実行され、毎回新しいリライタを生成してそれぞれ kFirstUsedBarrier から番号を振り直す。2 回目の実行は 1 回目が既に書き換えた同期をスキップするが、それらの id が既に使用済みであることを知らないため、同じ bar.sync id, count を互いに重ならない 2 組のスレッドに割り当ててしまう。修正は、番号を 2 回の実行にまたがって連続させ、ドメインをまたぐ再利用にはアサーションを追加するもの。この種の欠陥はコンパイル時にエラーにならず、大きな kernel で散発的にしか現れない。

出典：https://github.com/tile-ai/tilelang/pull/3643

1.2 メインリポジトリ：clamp の NaN 伝播低下が巻き戻され、T.clamp は min/max に回帰（#3628）

10-23 16:51 にマージ。#3205 の一連の経路を巻き戻し：tl.clamp 組み込み、各バックエンドの低下登録、codegen 分岐、デバイス側ヘルパー関数（昇騰の登録を含む）を削除し、T.clamp(x, lo, hi) は T.min(T.max(x, lo), hi) に戻る。理由は、追加の NaN 処理が min/max の簡約化とベクトル化を妨げていたため。NaN の要望は消えておらず、同日に別途 #3605 を開き、T.clamp_symmetric を CUDA SM86+ で単独実装する形とし、役割分担は「T.clamp は汎用性を保ち、新インターフェースはセマンティクスを保つ」。

出典：https://github.com/tile-ai/tilelang/pull/3628

1.3 メインリポジトリ：int64 アトミック max/min と AtomicStore の int64、bf16、fp16 クラッシュ（#3307）

10-23 18:44 にマージ。normalize_atomic_type は #1716 以降、int64_t を unsigned long long に正規化して atomic add をサポートしていたが、その結果 Atomic の max/min および参照形式が int64 上で直接破綻し、AtomicStore も同様に影響を受け、さらに bf16 と fp16 にも波及した。修正では操作ごとに int64 専用の型選択を行い、AtomicStore は独立した型ディスパッチを通す。ある操作のために共通正規化を変更し、連鎖的に他の操作を壊した典型的なリグレッションである。

出典：https://github.com/tile-ai/tilelang/pull/3307

1.4 メインリポジトリ：VectorizeLoop がループステップを黙って無視しなくなる（#3345）

10-23 19:02 にマージ、#3301 が追跡する F319 に属する。ベクトル化器は (loop_var, extent, body) しか受け取らず、ステップは全く渡されていなかった。T.vectorized(0, 8, step=2)（反復集合 0/2/4/6）は [0, 8) 全体をカバーする連続アクセスに下降されていた。修正ではベクトル化に入る前に非単位ステップを拒否し、診断を出す。この一連のサブ項目に共通する特徴は、フロントエンドが下降不可能な書き方を受け入れ、バックエンドが別のプログラムのマシンコードを生成することである。

出典：https://github.com/tile-ai/tilelang/pull/3345

1.5 メインリポジトリ：NVRTC がディスクキャッシュにヒットすると自動チューニング結果が書き戻されない（#3193）

10-23 15:04 にマージ。NVRTC がディスクから kernel をロードする際に adapter.libpath を設定しないが、チューニングで設定が選択された後はこのフィールドを使ってキャッシュ kernel を保存するため、ヒットするたびに AttributeError が発生し、結論が破棄され、ユーザーには「起動するたびに再チューニングしている」ように見えていた。修正ではキャッシュロードパスで libpath を復元し、新規コンパイルパスと一致させ、キャッシュリロードとネガティブコントロールのテストケースを追加した。

出典：https://github.com/tile-ai/tilelang/pull/3193

1.6 レビュー中：独立パッケージ化された TIRx で内蔵 TVM を置き換え、1043 ファイルを変更（#3666）

10-25 19:16 に提出、1043 ファイル +71428/-104176。3rdparty/tvm および submodule エントリを削除し（CUTLASS と HIP ヘッダーは保持）、フロントエンド、ネイティブテンソルとスコープ IR、下降パス、バックエンドパイプライン、実行アダプタを全体として独立ビルド・リリースされる tvm_tirx に移行した。互換層は TileLang 内部に限定され、グローバルな tvm エイリアスを設けず、第二の TIRx も保持しない。これにより、前号までの「tvm fork が先行、メインリポジトリが追随」が終点に達した。基盤は vendored ソースから外部依存に変わり、以後は独立してリリースとロールバックが可能になり、マージの影響範囲はリポジトリ全体に及ぶ。

出典：https://github.com/tile-ai/tilelang/pull/3666

1.7 レビュー中：sm_100 の TMEM 解放に CTA バリアが欠如、warp 特化の先頭文が移動（#3645 / #3663 / #3664）

三件は同源で、いずれも自動 warp 特化と Blackwell の新しいストレージに関するもの。#3645：sm_100 上のテンソルメモリ解放に CTA レベルのバリアがなく、プロデューサー warp がコンシューマーの tcgen05.mma/tcgen05.ld まだアキュムレータを読んでいる間にそれを解放できる。#3663：特化が T.serial の外側ループの外にある先頭文をループ本体に移動させ、本来一度だけ実行すべき初期化が毎回再生され、出力が誤る。#3664：if 内に特化パイプラインを包み、if の後に文がある場合、setmaxnreg 関連の下降が ptxas を失敗させる。三件を合わせて見ると、「どの文がどの warp に属し、ライフタイムがどこで終わるか」に関する完全な意味モデルがまだ欠けている。

出典：https://github.com/tile-ai/tilelang/pull/3645、https://github.com/tile-ai/tilelang/issues/3663、https://github.com/tile-ai/tilelang/issues/3664

1.8 新規欠陥：sm_120 でリダクション下降失敗、3 つの注意力サンプルが共有メモリ超過（#3647 / #3646）

10-25 09:08 に同日 2 件報告。前者は gdn wy_fast_bwd_split の sm_120 上での ReduceOp 下降失敗——ソースインデックスがスレッド保有のリダクションセグメントに依存し、既存ルールのカバー範囲外である。後者は attention_sink、gqa_bwd、block_causal_attention_varlen の 3 つのサンプルが 101376 バイトの単一ブロック共有メモリ上限を超えている。対応する修正 #3662 は既にオープン済み：デバイス上限に応じてより小さなタイル、より少ないパイプライン段数、128 スレッドを選択し、大型デバイスは元のデフォルトを維持する。コンシューマー向け Blackwell の容量制約が、サンプルとチューニング表のハード境界になりつつある。

出典：https://github.com/tile-ai/tilelang/issues/3647、https://github.com/tile-ai/tilelang/issues/3646

2.2 昇騰メインリポジトリ：DMA のバッファ基底オフセット保持、領域境界の先行的提升、周期バッファの完全なライフサイクル（#3627 / #3625 / #3606）

5. トレンド観察

リリースエンジニアリングが主戦場になった。 78 件のマージのうち TileOPs が 51 件を占め、そのうち十数件は改名、パッケージング、セマンティクス統一、ドキュメントと CI ゲート——性能でも新規オペレータでもなく、インターフェースを凍結するものだ。トラッキング課題は七割、CHANGELOG は 0.1.0 を確定し 10-26 と記載、以降 0.x の互換性コミットメントが発効する。同時期に TileFoundry は core/nvidia/apple の 3 パッケージ化、Sunrise は 0.1.15 配布版をマージし、3 つのラインが同じ週に同じことをしている：「動く」を「リリースできる」に変えることだ。

正確性の重心が形状検証から新ハードウェアと新スケジューリングへ移った。 先週のメインリポジトリのマージは形状と幾何検証が中心だったが、本調査期間はライフサイクルとバリアに変わった：クロスストレージドメインバリアの重複番号、sm_100 テンソルメモリ解放時の CTA バリア欠落、warp 特化が先頭ステートメントを誤って移動、setmaxnreg が ptxas 失敗を引き起こす。共通点はコンパイルは通るが結果が偶発的に誤ること、そしてすべてが自動 warp 特化と新アーキテクチャのストレージに起因すること——スケジューリング権をコンパイラに委ねた後に必ず払うことになるツケだ。

昇腾ラインは動作確認からモデル別オペレータ展開と毎日リグレッションへ進んだ。 situ_glu は Kimi K3 Stable LatentMoE のゲート活性化に整合し、審査中の sparse_mla_fwd と GLM-5.3 kpool も同様に特定モデル構造の部品だ。毎日全量 2903 項目が全通過、翌日にはまた失敗を報告しており、テストケース規模がすでにゲートとして十分であることを示す。CI イメージが cann9.3.0 週次更新版に追随していることも合わせ、このラインの結論の有効期限は週単位で計られる。

実行バックエンドは引き算、バックエンド一覧は足し算。 CPU は TVM-FFI に統一、PTO はデフォルトで tvm_ffi、さらに CuTeDSL 修正と NVRTC コンパイルを追加、方向性は一致している。実行パスの分岐を減らすことだ。バックエンド一覧は逆方向に拡張——Intel AMX が CPU パスに進出、ROCm は FP4 と E8M0 を補完、海光はレジスタパイプラインを再提起。配布形態は「一つのコードで複数バックエンドに分岐」から「一つの IR、複数のパッケージング」へと変わりつつあり、#3666 で TVM を外部依存に変えるのと同じ道筋である。
