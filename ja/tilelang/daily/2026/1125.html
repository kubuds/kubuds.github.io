今日の重点：メインリポジトリのバージョン番号を 0.1.16 に変更、タグと PyPI は依然 0.1.15 のまま

#3887 は北京時間 11-25 00:22 に主干へ進出、VERSION の1ファイルのみを変更し、0.1.15 を 0.1.16 に改めた。パッケージメタデータとドキュメントはすべてこのファイルからバージョン番号を読み取るため、1箇所の変更で全バージョン宣言が完了する。

提案に列挙された検証項目は3つ。リリースメタデータが NO_VERSION_LABEL=ON 下で 0.1.16 と解析される。3つの version-provider テストが通過。pre-commit run --all-files と bash format.sh がともに通過。

リリース側はまだ動作していない。GitHub タグの最新は依然 v0.1.15。Releases の最新は依然 2026-09-30 の v0.1.15。PyPI 上の tilelang 最新版も 0.1.15。

したがって本期は「0.1.16 リリース済み」とは書かない。正確にはバージョン番号は整備済みで、タグ付け、Release 発行、PyPI へのプッシュの3ステップがまだ残っている。

前版 0.1.15 から今回のバージョン番号推進まで55日。この間、メインブランチには ROCm の一括修正、Z3 の3箇所の修补、昇騰ホイールテストが蓄積された。

出典： https://github.com/tile-ai/tilelang/pull/3887。

今日の重点：ROCm が1日で6件マージ、FP4 変換を修正し、リダクション判定を wave 幅ベースに変更

メインリポジトリの当日12件のコミットのうち、6件が ROCm プレフィックス付き。この一連の変更はすべて実際の量子化とリダクションパスの欠陥に対応している。

#3665 HIP テンプレートの2箇所のギャップを修正。1箇所目は T.cast(x, T.float4_e2m1fn) の戻り値が誤っている点。コード生成は変換を (fp4_e2_t)x と書き出すが、この型には explicit fp4_e2_t(uint8_t raw) しかない。そのため float が整数に切り捨てられてから生ビットとして格納される。1.0 は 0.5 に、2.0 は 1.0 に、6.0 は 4.0 になり、負数も同様に誤る。

2箇所目は HIP テンプレートに E8M0 型が欠けている点。2箇所とも VeOmni で DeepSeek-V4 の QAT 量子化器を走らせた際に露呈し、環境は gfx942 と gfx950 で、UE8M0 スケールを含む。0.1.15 のホイールではこの2つのヘッダファイルがメインブランチと一致しており、同様に影響を受ける。

#3959 はリダクションがワークスペースを必要とするか否かの判定基準を変更。旧コードはリダクションのスレッド数が32を超えると一律に真を返していた。実際には tl::AllReduce はあるステップが wave を跨ぐ場合にのみワークスペースを使うため、wave64 上では64スレッドのリダクションが決してアクセスしない LDS を確保していた。ワークスペースは IR 上でもう1回の共有メモリアクセスであり、ThreadSync がここでリダクションごとにバリアを挿入していた。

修正方法は目標の wave 幅で比較することであり、wave32 ターゲットの動作は変わらない。バリアは実際に wave を跨ぐパスに残される。

#3729 は gfx1200 上の FP16 と BF16 の T.gemm が標準の線形共有レイアウトを受け入れるようにする。これまでは A_shared、B_shared に対して make_linear_layout を呼んでから T.gemm を計算すると、Get different layout が報告されていた。既存の WMMA エミッタは本来このマッピングでデータを取得できるが、問題は互換性判定にあった。

手法は共有レイアウト互換コールバックの引数を4項目に拡張することである。オペレータ、オペランドバッファ、実際のレイアウト、ターゲット。ROCm 側はこれに基づいて入力ごとに検証して再利用し、エミッタとインデックスマッピングは変わらない。

他に3件はエンジニアリングの細部に属する。#3954 は compile_flags と tl.device_compile_flags を実際に hipcc へ渡すようにする。これまでこの2つの引数はキャッシュキーに入るだけで、デバイスコードを変えていなかった。

#3958 は hip_resource_info に占有率レポートを追加する。#3956 はドキュメントで T.gemm が wave あたりの行数が非常に少ない場合の制限を説明する。

情報源： https://github.com/tile-ai/tilelang/pull/3665。

今日の重点：昇騰が1日で10件の欠陥を報告、すべて API パラメータ検証の欠如を指す

11-24 の1日で、同一の作者が tilelang に昇騰の欠陥を10件起票し、番号は #4490 から #4499。10件のレポートのテスト環境は一致している。ハードウェアは Ascend 950PR シングルダイ、128 GB ビデオメモリ。ソフトウェアは CANN 9.2.1、HDK 26.0.RC1、openEuler 24.03、torch 2.10.0+cpu、torch_npu 2.10.0.post4。

うち6件は「バックエンドがコンパイルできない入力を受け入れた」ものである。#4490 の T.atomic_add は int8、uint8、float8 バッファを受け入れる。#4492 の T.atomic_max と T.atomic_min は int8、uint8 を受け入れる。#4491 の T.reduce_sum は bfloat16 と float8 を受け入れる。#4494 の T.simd.vabs と T.simd.vneg は bf16 と fp8 レジスタを受け入れる。

#4495 の T.gemm は任意の unit_flag_ctrl を受け入れ、-1 や 999999 を渡しても静かにコンパイルできる。#4497 の T.gemm は GM スコープのオペランドを受け入れ、バックエンドはコンパイル可能なパスを見つけられない。

4件はよりクラッシュや誤コンパイルに近い。#4496 は float8_e4m3fn の共有バッファに対して T.fill を行うと、bisheng コンパイラを直接 core dump させる。#4498 の T.gemm は TILE_K_SUB が一切割り切れない K を受け入れ、その後自動スケジューリングでアサーション失敗する。#4499 のスカラー T.sqrt と T.rsqrt はカーネルコンパイル時に stl_pair.h の再宣言でエラーになる。#4493 の5つのアトミックインターフェースは Ascend 上で下降実装を持たない。

別に独立した情報源による正確性の欠陥が1件ある。#4484 は SimdVF のリダクション下降が sum 以外のすべてのリダクション種別を max にマッピングし、T.reduce_min が最大値を返すことを指摘する。この件はソースレビューによるもので、デバイス上では再現していない。

这批の問題の共通点は、型と値が本来コンパイル時に拒否されるべきところ、現在はバックエンドに渡されてから初めて失敗する点である。11-23 の6件のドキュメントと実装の不一致と同様、インターフェース契約のギャップに属する。

情報源： https://github.com/tile-ai/tilelang/issues/4498。

1. コアプロジェクトの進展

1.1 Z3 の下位ビットマスクを整数剰余エンコーディングに変更、メインリポジトリが bump に追随し TopK テストのソルバー制限を撤回

TVM サブモジュール tilelang_main ブランチに当日 #98 がマージされ、メインリポジトリ側の #4482 が 14:03 に bump に追随した。3箇所の修正はいずれも Z3Prover の具体的な欠陥に遡ることができる。

1つ目は、定数の符号付き右シフト (n + 4095) >> 12 のような式が従来ビットベクトル経路を通り、int2bv、bvashr、bv2int の3ステップを経ていたこと。この種のシフトがループ境界に現れると、同一スコープ内の後続の純粋な整数クエリに Int と BitVec の制約が同時に付き、tirx.Simplify でデフォルトのリソース予算を使い果たすことがよくある。

2つ目は、VisitShiftOp が CanProve 内で b >= 0 と b < 64 の2つのアサーションを共有ソルバに直接追加していたこと。これは後続のクエリを汚染し、外側スコープとも衝突する。同時に DivNode と ModNode は Z3 のユークリッド / と % を使っていたため、負の被除数に対しても truncmod(a, 4) >= 0 を証明できてしまっていた。

3つ目は、tx & 31 のようなマスクがインデックス式の簡略化で依然ビットベクトル経路を通っていたこと。#98 は x & (2^k - 1) を x mod 2^k に変換する。提案は具体的なコストを記録している。あるデバイス関数で簡略化器が同種の問い合わせを156回行い、11.7秒を要し、反例は tx = 4 だった。

テスト側はまず止血してから撤回した。#4463 は 09:51 に2つの ROCm テストファイルの arith.z3_rlimit を 100 に制限した。原因は4つの DeepSeek と GLM の TopK ケースがそれぞれ 494 から 605 秒を要したことだった。

#4489 は 20:40 にこの制限を撤回し、理由には #4482 により定数の符号付き右シフトが安価になったと記されている。比較は同一ビルド b4c67597、TVM de131ae4、Z3 4.15.4 を用い、3回のコールドランの中央値を取った。

ソース： https://github.com/tile-ai/tilelang/pull/4482。

1.2 Dist パイプラインに昇騰ホイールテストを追加、この半区はこれまで実機で実行されたことがなかった

#4419 は 22:59 に主干へ入った。提案に明記された前提：Linux ホイールは CUDA、ROCm、Ascend の3-in-1 ビルドだが、test-wheels-gpu は前の2つだけを実行する。昇騰半区はホイールリリース前に実際の NPU で一度も実行されたことがなかった。

新たに test-wheels-ascend ジョブを追加し、セルフホストの昇騰 runner 上で実行する。環境構築は ci.yml の昇騰ジョブと同源。現在のイメージは cann9.3.0-weekly.20261112-ubuntu22.04-py3.13。レジストリには他に cann9.2.0、9.2.1 と py3.10 から py3.12 のバリアントがあり、マトリクスを拡張できる。

ジョブの流れは、まずビルド済みの Linux x86_64 ホイールを取得し、--system-site-packages 仮想環境にインストールする。コンテナの torch と torch_npu はあらかじめ pin されている。

続いてソースパッケージを移動し、import tilelang がソースツリーではなくホイールをヒットすることを確保する。ホイールは abi3 ビルドで、wheel.py-api = "cp39"、1つの成果物を任意の Python バージョンにインストールできる。

ソース： https://github.com/tile-ai/tilelang/pull/4419。

1.3 vote と sync 組み込み関数が64ビット述語を保持、1 << 32 が偽と判定されなくなる

#3777 は 09:53 に主干へ入った。CUDA の vote と block-sync 組み込み関数は32ビットの int 述語のみを受け取る。例えば __any_sync、__syncthreads_count。

int64 や uint64 を渡すと値は暗黙的に縮小される。下位32ビットが0の非ゼロ述語はこれにより偽と判定され、1 << 32 が最も直接的な例である。

影響を受けるインターフェースは7つ。投票系は T.any_sync、T.all_sync、T.ballot、T.ballot_sync。同期系は T.syncthreads_count、T.syncthreads_and、T.syncthreads_or。

修正方法は、32ビットを超える述語をまず明示的な != 0 に正規化し、組み込み関数にはブール値を渡す。さらに 1 << 32 のランタイム回帰を追加し、warp vote テストファイル全体が通過した。

ソース： https://github.com/tile-ai/tilelang/pull/3777。

2. マルチバックエンド対応（昇騰 / 海光 / 摩尔線程 / 沐曦）

2.1 昇騰サブリポジトリに2件がメインラインへ：DMA行数折り畳みとインストールスクリプトの堅牢化

tilelang-ascend のデフォルトブランチは ascendc_pto であり、main ではない。リポジトリごとのスクリプトが main で取得すると空の結果になる。当該ブランチの調査期間内に2件のコミットがある。

#1805 は Ascend copy の多次元転送を修正する。2次元を超える GM と UB 領域に対し、先頭次元を DMA 行数へ折り畳む。由来は #1231。#1946 は install_ascend.sh を堅牢化する。shmem のビルド失敗時には直ちに中止し、set_env.sh のパスをスクリプト所在ディレクトリからの解決に変更する。由来は #1728。

サブリポジトリの調査期間内の審査中 PR と新規 issue にも記録に値するものがいくつかある。#2025 は Ascend UB の列ストアと DMA サイズを修正する。#2035 は threads=2 時に AscendVidReduction が生成するブロードキャストと dim=0 リダクションの結果が誤っていると報告する。#2034 のデイリーテストは 11-24 に 3120 項目を実行し、3120 項目が通過したと記録している。

情報源： https://github.com/tile-ai/tilelang-ascend/pull/1805。

2.2 MLIR 昇騰が方言ブランチで tl.wait_flag と tl.vbitcast をマージ

2件のマージはいずれも mlir-dialect ブランチにあり、master には調査期間内の新規コミットはない。このブランチは TLIR 方言の進化ラインである。

#248 は tl.wait_flag を追加する。前日の tl.set_flag と対になり、完全なプロデューサ・コンシューマ同期プリミティブを成す。記法は tl.wait_flag[#tl.pipe<...>, #tl.pipe<...>, %event_id] : i64。set_flag が導入した #tl.pipe 属性を再利用し、新しい属性や型は追加しない。TIR から TLIR への降下は同じ PipeFromString と GetEventID を再利用する。

#249 は tl.vbitcast を追加し、TIR、TLIR、HIVM の3段階を通る。verifier は形状の一致と要素ビット幅の等価性を検証する。このコミットは同時に実際の欠陥を1件修正する。CodeGenTileLangTLIR の VisitStmt_(LetStmtNode*) は従来 op->value を完全に無視しており、let で束縛された呼び出し結果はすべて暗黙に破棄されていた。tl.npuir_bitcast の handle 戻り値はまさにこの経路に依存している。

審査中の #250 は tl.ln を hivm.hir.vln へ降下させる。提案はさらに、非 TLIR 経路の BitcastCodegen に同種の歴史的欠落があると注記している。

情報源： https://github.com/tile-ai/tilelang-mlir-ascend/pull/249。

リダクション二件。#3152 は一回の起動で先頭軸を走り切らせ、thread-block cluster を跨いで分割する。#3154 は一回のバリアまたは一回の OR 演算でブロック内 any と all の折り畳みを完了する。

5. トレンド観察

  • バージョンリズムはリリース前夜に入った。0.1.15 は 9-30 にリリースされ、55 日後にバージョン番号は 0.1.16 に進んだ。この版の蓄積は主に ROCm 修正、Z3 の 3 箇所の修正、リリースチェーンのエンジニアリングであり、新機能ではない。

  • 性能回帰のガバナンスは定石が形成された。まず上限を追加して止血し、次に根本原因を修正し、最後に上限を撤回して再テストする。#4463、#4482、#4489 の 3 ステップはすべて 1 日以内に完了し、その間に TVM サブモジュールの更新が 1 回挟まった。

  • 昇騰の弱点はオペレータのカバレッジからインターフェース契約へ移行した。1 日 10 件の欠陥のうち、新規オペレータを要求するものは 1 件もなく、すべて「受け入れるべきでない入力が受け入れられた」もの。この種の問題は修正は安価だが、ユーザーの信頼を継続的に消耗させる。

  • TileOPs の最適化方針は依然としてフレームワークバージョンの追従。0.1.15 の汎用パスがもたらす追加オーバーヘッドは、下流がオペレータごとに個別に回避する必要がある。2 日以内に少なくとも 5 件がこれをタイトルにしており、バージョンアップとオペレータライブラリの性能の間に自動突合メカニズムがまだないことを示している。

  • RISC-V 側は連続 2 つの調査期間で変化ゼロ。TVM 路線と MLIR 路線はいずれも現状維持で、今回の調査期間はインデックスページにも動きがない。
