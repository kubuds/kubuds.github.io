今日の重点

この日最も集中的な成果はコンパイラではなくオペレータライブラリから生まれた。TileOPs は 21:06 から 22:46 までの1時間余りで6件を連続マージし、さらに 14:01 と 21:31 の2件を加えて、1日で9件、すべて perf、fix、ci タグであった。三つの事柄が同時に進んだ：一つ目はブロードキャストオペランドのオンザフライ読み込みで、lerp、where、clamp、masked_fill の5種類のオペレータは stride 0 のブロードキャストテンソルをまず出力形状に展開しなくなり、実測でブロードキャスト行の所要時間がメインラインの 0.13 から 0.44 倍に低下した（#2832）；二つ目は単一ウェーブ起動で、一元要素ごと演算が「本体内部で最大2つの安価な命令、読み書き総量が L2 の4分の3以下」の場合に 256 スレッドの1ウェーブに縮小され、ついでに ReLU が NaN に対して 0 を返す従来の問題も修正された（#2829）；三つ目はタイルセレクタで、小さい M 向けの NT GEMM に幅が1ウェーブを埋め尽くせるネイティブ幅タイルを作り、decode-down が後れから最速比較対象を 3% リードする形に変わった（#2834）。三つの共通点は「より速い」ことではなく、各件が再現可能な A/B 表を伴い、依然として後れを取っている行を自ら明示していることである。

第二条は信頼性の問題であり、しかも二つのリポジトリにまたがる。メインリポジトリで新たに issue #3808 が報告された：0.1.12 から 0.1.15 にかけて、条件関連のスカラー化の後、共有メモリ epilogue で __syncthreads() が一つ欠落し、コンパイラはエラーを出さず、生成される CUDA が誤っている；報告者は完全な再現スクリプトと4つのバージョン番号を提示しており、「サイレントな誤コード」であって性能劣化ではない。同一期間に #3800 が報告しているのは別種のサイレントエラーである：warp specialization を有効にしない場合、T.Pipelined が T.tcgen05_gemm の barrier 待機の前に次の stage を再ロードするため、MMA が読む operand がすでに上書きされている。これら2件とメインリポジトリ当日マージの #3759 はちょうど対照をなす——#3759 が修正するのは「スカラー条件内の int64 cast がデータベクトル幅を 16 lane から 4 lane に押し下げる」問題であり、同じスカラー化/ベクトル化の境界で、一方は幅を修正し、一方は同期を漏らしている。

第三条は昇騰側である。tilelang-ascend は #1954 をマージし、T.tile.bitwise_rshift の int64/uint64 におけるコンパイル時セグメンテーション違反を明示的な ValueError に改め、int16/uint16/int32/uint32 のみを許可した；これは 64 ビット右シフトサポートの新規追加ではなく、「コンパイラがクラッシュする」を「コンパイラが拒否する」に変えたものである。同一リポジトリで当日同題の issue が2件新規作成された（#1991、#1992）。報告によれば 910_9362 / CANN 9.0.0、threads=2（C:V=1:2）において、AscendVidReduction が kernel 内のすべての UB 割り当てを無条件に半減し、注入された tmp workspace すら半減するため、sin/cos が間接アドレッシングの skip-set buffer に作用する際に 3978/4096（97.1%）の要素が誤って計算され、sigmoid/round では AscendC の calCount <= tmp 契約に違反し、範囲外書き込みがレイアウト後方の scratch に落ちる。これと並置されるのが同日 #1988 のデイリーテストレポートである：3030 項目全通過、通過率 100%。この二組の数字を並べると一つのことが分かる——既存のテストは「threads=2 と間接アドレッシング」の組み合わせをカバーできておらず、通過率を正しさの代替指標にはできない。

第四条はエコシステム面の動きである。海光リポジトリは「機能ブランチに4件蓄積、PR 未作成」から正式にレビュー入りへと変わり、feat/hcu-scaled-cast ブランチは当日さらに3件の LDS 位相修正（デフォルト swizzle の 64 bank 対応、MN スライス消費側での swizzle 計画復元、K パーティションのレイアウト認識読み込み）を落とし、#33（scaled cast）と #34（reduction の lane swap と制約伝播）の2つの PR を開いた。摩尔線程は 09-30 以来の完全な沈黙を終え、メインブランチに README のインストールとオペレータ開発説明の更新を1件落とした。さらに TileSight リポジトリに最初の PR（H20 の WGMMA 能力宣言の修正）が現れ、メインリポジトリ #3803 の TIRx 移行草案と合わせて、組織レベルで三つの線が同時に展開していることが見て取れる：国産バックエンドが独自ブランチから公共レビューへ、性能モデリングが論文からリポジトリへ、コンパイラ基盤が vendored TVM の置き換えを準備している。

1. コアプロジェクトの進展

1.1 メインライン：TF32 変換が round-to-nearest-even をサポート、SM90 と SM100 を分けて診断（#3714）

12:09 にマージ。これまで T.cast から tfloat32 へはデフォルトの TF32 最近接丸め経路しかなく、ties-to-even が必要なら自分で CUDA helper をインポートする必要があった。このコミットは round="rn" にネイティブ lowering を追加した。非飽和形式は cvt.rn.tf32.f32、飽和形式は cvt.rn.satfinite.tf32.f32 を発行し、デフォルトの TF32 丸めコンストラクタを回避して変換後のビットパターンを直接保持する。スカラーとベクトルの両経路をカバーし、TF32 の lane アクセスはパック済みキャリアを通る。アーキテクチャ診断は形式ごとに分かれる。非飽和形式は SM90 以上、飽和形式は SM100 以上を要求し、満たさなければコンパイル時にエラーを出す。rounding を明示指定しない cast の動作は変わらない。報告者は #3713 をクローズした要求元であり、「ユーザーがもはや helper を自前で持つ必要がない」という類のインターフェース収束に属する。

出典：https://github.com/tile-ai/tilelang/pull/3714

1.2 メインライン：host-mapped バッファを明示的に注釈可能に、CPU テンソルがデバイスチェックで拒否されなくなる（#3802）

当日作成、当日マージ（12:08 コミット、16:02 マージ）。CUDA kernel は GPU アドレス空間にマップされた host メモリへ直接アクセスできるが、TileLang の既存のデバイスチェックはテンソル引数がすべてターゲットデバイス上にあると仮定していたため、こうした CPU テンソルは起動前に拒否されていた。新設の T.annotate_host_mapped_buffers(*buffers) は注釈された引数のインデックスを PrimFunc の tl.host_mapped_params 属性に書き込み、複数バッファに対応し、重複宣言をマージし、IR シリアライズと kernel キャッシュ復元を通過できる。Cython と TVM-FFI の 2 つの launcher は注釈された引数に対して CPU テンソルを受け入れ、その他の dtype、形状、ランク、ストライドのチェックは従来通り。デバイス側引数のチェックは現在の実行デバイスに引き続き整合し、host テンソルには CUDA デバイス番号を提供しない。ランタイムにはネイティブ helper が追加され、cuMemHostGetFlags で登録状態を検証し、cuMemHostGetDevicePointer でデバイスから見えるアドレスを解決する。通常のページャブルメモリは引き続き拒否される。

出典：https://github.com/tile-ai/tilelang/pull/3802

1.3 メインライン：スカラー条件内の cast がデータベクトル幅を制限しなくなる（#3759）

19:27 にマージ、ラベルに ascend を含む。発端は #3734 が DecoupleTypeCast の後でデータ cast の幅制限を正しく厳格化したが、条件内の cast もそれに含めてしまったことにある。T.assume(n % 16 == 0) で保護された BF16 コピーが、条件内に T.Cast("int64", ...) があるために b5cb02633 上で 16 lane から 4 lane に押し下げられた。条件が 16 lane 上で一致していてもである。修正は planner 既存の条件一貫性解析を再利用し、cast 幅の免除をバッファインデックスから条件へ拡張する。if 文、tirx.if_then_else、スカラ述語の Select の条件は個別にアクセスし、分岐は引き続き制限される。lane レベルのベクトル述語のターゲットでは条件 cast の制約が引き続き保持される。stochastic rounding の rbits グループ化も幅制約をスキップする際に保持される。このコミットと期間内の 2 つの新規 issue は同じ領域にあり、スカラー化とベクトル化の境界が現在の欠陥の高発地带であることを示している。

出典：https://github.com/tile-ai/tilelang/pull/3759

1.4 メインライン：Z3 の rlimit を kernel ごとに設定可能に、デフォルトは依然 10 万（#3752、tile-ai/tvm #91 に依存）

23:05 にマージ、前提は fork 内の tvm #91（23:03 マージ）。変更は Z3 ソルバの rlimit をハードコードされた 100,000 から kernel ごとにカスタマイズ可能にする。設定しない場合は従来のデフォルト値を維持する。著者の表現は率直で、「これにより Z3 証明器に関連する多くの問題が間接的に修正される」。この類の変更の意義は、「証明が予算超過する」を調整不能な環境挙動から調整可能なコンパイルパラメータへ変えることにあり、昨日の昇騰側で AutoSchedule の周期下限を厳格化した（Z3 求解時間を 10.04% 削減）のと同一方向の 2 つの手法である。一つは探索起点を変え、一つは探索予算を変える。

出典：https://github.com/tile-ai/tilelang/pull/3752、https://github.com/tile-ai/tvm/pull/91

1.5 メインライン：ネストした T.macro が変換テンプレートを再利用、フロントエンドの重複コンパイルオーバーヘッドが収束（#3760）

23:38 に一致。問題は、外側の関数が実行されるたびに、ネストされた T.macro 定義がソース解析、AST 書き換え、Python コンパイルを毎回やり直してしまうことにある。たとえ kernel 自体がすでにキャッシュにヒットしていてもだ。修正方法は、有界なプロセス内キャッシュを導入し、コンテキストに依存しない変換結果（未バインドのコードと書き換え後のソース）だけを保存し、各マクロインスタンスが現在の globals とクロージャ値をバインドするようにする。コンテキスト依存の変換は元の経路を通し、ラップされた関数はキャッシュを迂回する。マクロ呼び出し箇所と kernel キャッシュはどちらも変わらない。回帰テストは新しいクロージャ、globals、キャプチャしたバッファ、アノテーション、コンテキスト依存のフォールバック、クロージャのライフサイクルをカバーする。CPU 側のフロントエンドチェックは通過し、GPU 実行はローカルでは未検証——作者はこの境界を明確に書き記している。

出典：https://github.com/tile-ai/tilelang/pull/3760

1.6 新規 issue：条件付きスカラー化後に __syncthreads が欠落、0.1.12 から 0.1.15 まで誤った CUDA を無警告で生成（#3808）

21:14 に作成され、本調査期間で最も重大な欠陥報告である。再現は共有メモリ epilogue の kernel で、0.1.12、0.1.13、0.1.14、0.1.15 の 4 バージョンすべてが、条件に関連するスカラー化の後に __syncthreads() を 1 回欠落させ、コンパイラは一切エラーを出さず、生成された CUDA は直接誤った計算結果を出す。報告者は完全に実行可能な Python 再現スクリプトと環境（Python 3.14.9、CUDA 2.15.0+cu134）を提供している。この種の問題の破壊力は、4 つのリリースバージョンにまたがりながら一切の警告がない点にある——共有メモリをフェーズ間の受け渡しに依存する kernel はすべて踏む可能性があり、ユーザー側に見えるのは「結果がおかしい」だけである。

出典：https://github.com/tile-ai/tilelang/issues/3808

1.7 新規 issue：warp specialization なしの場合、T.Pipelined が tcgen05 ウェイト前に stage を再ロード（#3800）

08:44 に作成。トリガー条件は warp specialization を無効化（tl.disable_warp_specialized=True）した上で T.Pipelined と T.tcgen05_gemm のループを実行すること：stage が mbarrier_wait_parity の前に次のラウンドのコピーで上書きされ、MMA は書き換えられた operand を読んでしまう。報告者は lowering された kernel ソースを貼り付け、As の書き込みと tcgen05mma_ss の読みの間に順序制約が欠けていることを指摘している。#3808 と同じく「生成されたコードは問題なさそうに見えるが、実際には成立しない」という類であり、違いはこちらが Blackwell の tensor memory 経路上で発生する点である。

出典：https://github.com/tile-ai/tilelang/issues/3800

1.8 レビュー中：ネイティブ Apache TIRx への完全移行草案（#3803）、共有転置は ldmatrix/stmatrix 経由に変更（#3809）

#3803 は今号で最も重要なレビュー中項目である：vendored の TVM コンパイラを独立した Apache TIRx に置き換え、フロントエンド、IR 変換、コード生成、JIT 適応、パッケージングをすべてネイティブのオブジェクトモデルに移行し、apache/tvm-tirx の 7e49a148 と apache/tvm-ffi の 3e906bc6 という 2 つの上流コミットを pin し、依存ツリーはクリーンな上流を保ち、パッチを注入しない。作者はこれを draft と標記しており、それ自体が「基盤の世代交代」の公開準備である。

5. トレンド観察

第一に、オペレータライブラリの競争点は「オペレータの数」から完全に「セレクタと準備コスト」へ移った。本日の TileOPs の9件のうち、実際に GPU kernel を変更したのは #2832（ブロードキャスト就地読み）と #2834（ネイティブ幅タイル）のみで、#2835 が節約するのは呼び出し準備（4.33% から 6.17%、生成ソースコードは不変）、#2836 が変更するのは1つのフィッティング因子で、regret は 0.89% から 0.06% に低下した。これは、性能差の残された余地が主に「どう計算するか」ではなく「どのタイルを選ぶか、どの準備作業を減らすか」にあることを示している。この道を突き詰めると、手調整パラメータの山ではなく、キャリブレーション契約で記述されたコストモデルに到達する——本日の #2836 の「単独フィッティング、定数を1つだけ動かす」はまさにその形態の雛形である。

第二に、コンパイラ側の現在の主要な欠陥タイプは「静かに誤ったコードを生成する」ことであり、コンパイル失敗や性能不足ではない。#3808 は 0.1.12 から 0.1.15 の4バージョンにわたり __syncthreads() を1つ欠いており、#3800 は Blackwell パスで MMA が上書きされた operand を読んでしまい、#1991/#1992 は昇騰 threads=2 の下で sin/cos が97.1%の要素を誤計算する——3件ともエラーを出さず、通常のテストを通過し、的を絞った再現を人手で書かなければ捕捉できない。この種の欠陥はユーザーへの損害が最大である。なぜなら「コンパイラは正しいか」という前提を、検証を要する仮説に変えてしまうからだ。これに対応するエンジニアリング上のアクションは、ユニットテストの数を増やすことではなく、形状組み合わせの差分テスト（対照群は reference 実装による要素ごとの比較）を拡大することであるべきだ。

第三に、昇騰側のリズムは「アーキテクチャ変更後のリグレッション一掃」から「正確性境界の一掃」へ移っている。#3512 のような構造的変更がもたらした4種類のリグレッションを前の調査期間でちょうど一掃し終えたところで、本調査期間の2件のマージ（セグメンテーション違反をエラー報告に変更、性能スキルの世代分け）と2件の新規 issue（tmp workspace の半減、calCount <= tmp の違約）はいずれも境界の収束に属する。注目すべきは、#1991 の報告者が #1897 のレビュー側であり、#1897 の修正方法は count 側のみをカバーしていたことだ——同一のレイアウトロジックの別の側面が2週間後に指摘されたことは、昇騰バックエンドのレイアウト不変条件がまだ検査可能な書面契約として形成されていないことを示している。

第四に、国産バックエンドの「公共化」が加速している。海光は独自開発ブランチから2つの正式 PR へと進み、摩尔線程はドキュメント保守を再開し、mlir-ascend は3つの小さな PR で算術オペレータを1つずつ TLIR 方言へ移している。3つのラインの共通点は、いずれも「大きなバックエンドを一括でマージする」のを待つのではなく、レビュー可能な最小単位を公共リポジトリへ押し出していることだ。これは上流にとって良いことである。レビュー担当者が3万行の一括マージ時に初めて見るのではなく、早い段階でレイアウトと lowering の設計に意見を述べられるからだ。

最後のリスク面：主リポジトリ #3803 の TIRx 移行が推進されれば、3rdparty/tvm の vendored 構造は2つの pin された上流コミットに置き換えられ、その時点で TVM 内部 API に依存するすべてのバックエンド（昇騰、海光、mlir-ascend のグルーレイヤー）が追随して変更を迫られる。草案には「依存パッチを注入しない」と明記されており、これは約束であると同時に制約でもある——本日 mlir-ascend が BishengIR アダプタを contrib へ移し、昇騰が性能スキルをチップ世代ごとに分岐させたことは、いずれもこの種の基盤切り替えに備えて用意された交換可能な面と見なせる。
