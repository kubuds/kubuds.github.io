1. コアプロジェクトの進展

1.1 メインリポジトリ：out_idx 出力を呼び出し側ストリーム上で割り当てるよう変更、H100 で再現した 5 回中 3 回の破損がゼロに（#3649）

10-26 22:36 にマージ、5 ファイル +183/-31、#3648 を修正。cython、nvrtc、cutedsl の 3 つのアダプタはいずれも stream= を受け取りそのストリーム上で起動するが、out_idx 出力は torch.empty で現在の torch ストリーム上に割り当てられていた。キャッシュアロケータは「割り当てストリーム」順にのみ再利用するため、キューに処理が残っている VRAM ブロックが空きブロックとして返され、その処理がその後カーネル結果を上書きしていた。修正は output_allocation_stream(stream, device) を新設：呼び出し側ストリームが現在のストリームと異なる場合は呼び出し側ストリームを返し、そうでなければ空を返す。ハンドルがゼロの場合はデフォルトストリームにマッピングする。旧版 PyTorch の ExternalStream(0) はデフォルトストリームではなくプール化ストリームを返すためである。H100 80GB 上の再現は 4/5、5/5、5/5 の破損から、3 つのアダプタそれぞれ 0/5 に変化し、新規テストファイルは 10 項目通過。作者は wait_stream を追加する書き方を明確に否定している。それでは毎回の呼び出しで起動ストリームが現在のストリームの全処理の後ろに並んでしまうからだ。

出典：https://github.com/tile-ai/tilelang/pull/3649

1.2 メインリポジトリ：NVRTC デバイス側コンパイルを TVM-FFI 実行パスに接続、コンパイルキー項目を追加（#3285）

10-27 00:02 にマージ、12 ファイル +133/-133。tl.cuda_compiler="nvrtc" を新規追加し、既存の TVM-FFI ホストランタイムと組み合わせる。NVRTC がデバイス側 CUDA ソースを cubin にコンパイルし、共有 CUDA ランタイムモジュールがこれらのバイトをインポートする。ホスト側のバインディング、スカラー変換、条件、ループ、起動準備は引き続き TVM-FFI が生成し、デフォルト値は依然 nvcc、旧 execution_backend="nvrtc" アダプタは元の実装を維持する。バイナリキャッシュキーにコンパイラ名と NVCC/NVRTC バージョンを追加し、ターゲット詳細と有効なコンパイルオプションとともにハッシュに参加させる。アーキテクチャトークン 90a や 100f はそのまま保持し、非互換ターゲットはコンパイル前に診断を出す。正常に作成された各 NVRTC program は finally で破棄される。この PR の CI は H20 で 5506 件通過、491 件スキップ、サンプル 76 件通過、ROCm 7.2 チャネル 3220 件通過、昇騰チャネル 1797 項通過を記録した。

1.3 メインリポジトリ：バッチ TMA ロードの cache hint にテンプレート引数が 1 つ足りず、DeepSelect の TMA パスがコンパイルできない（#3683）

10-27 00:11 にマージ、2 ファイル +20/-11。eviction_policy="evict_first" または "evict_last" のバッチ TMA ロードが main 上でコンパイル失敗する。コード生成が CacheHintSm90 テンプレート実引数を 1 つ発行するが、生ポインタ版の tl::tma_load オーバーロードはバリア型しか受け付けない。この欠陥は DeepSelect の TMA パスを直接押さえ込み、GB200 と CUDA 13.1 上で当該サンプルの ring および replay ケースで再現した。修正方法は #3296 からキャッシュヒント部分を抽出し、欠けているテンプレート引数を補って選択したポリシーを PTX 命令に渡す。共有メモリアラインメントの部分は引き続き #3296 に残す。修正後、同一マシン上で DeepSelect 全ファイル 144 項通過、TMA コピーテスト 22 項通過、CUDA 12.9 の SM90 コンパイルチェックでも 3 種のポリシーの PTX が適切なオペランドを備えていることを確認した（#3296 の残りの変更は未マージ）。

1.4 メインリポジトリ：リダクションの FP8/FP4 非有限定数が不正リテラルを出力、サブバイトアキュムレータを早期拒否に変更（#3189）

10-26 15:44 にマージ、7 ファイル +204/-4、#2998 を修正。T.reduce_max と T.reduce_min が出力 FP8 E4M3 時に不正な inff リテラルを発行していた。非有限の E4M3、E8M0、FP4 定数は既存の変換コンストラクタ経由に変更し、正当な CUDART_INF_F と CUDART_NAN_F 式を渡す。飽和と NaN の挙動は維持される。同じ変更で通常リダクションと遅延リダクションがサブバイト数値アキュムレータ（FP4、int4 など）を早期に拒否し、明確な診断を出す。FP4 入力に FP16 または FP32 アキュムレータの組み合わせは引き続きサポートされ、ブールリダクションは免除、E8M0 リダクションのサポートは今回の範囲外。B300 と CUDA 13.1 上で 28 項のフォーカステスト全通過、完全なリダクションテストファイル 150 項通過、他に 3 項のバッチ検証失敗は main 上の既存問題。

1.5 メインリポジトリ：SM120 ブロックスケーリング GEMM で K 原子を明示展開、FullCol 構成が 51% 向上（#3286）

10-26 16:36 にマージ、4 ファイル +308/-2。#3257 が T.gemm_blockscaled と T.mma_gemm_blockscaled を導入した後の仕上げ。A オペランドをレジスタフラグメントから取得する場合、K 原子ループは従来 T.serial で、各フラグメントアクセスが実行時添字となり、nvcc は自己展開しないパイプライン化・warp 特化カーネルでフラグメントをローカルメモリに残してしまう。つまり MMA パスを溢れさせる。T.unroll(..., explicit=True) に変更後、各アクセスはコンパイル時定数となる。第二の点は SFA と SFB がともに共有メモリにある場合、従来は MMA ペアごとに共有メモリを 3 回読んでいたが、現在はレーンごと K 原子ごとにコンパクト選択パケットを 1 回ロードするだけで、行主序とブロック K 主序の両レイアウトをカバーする。RTX PRO 6000 Blackwell 上で 143 項通過、4 項スキップ、出力は float32 リファレンスとビット単位で一致。レジスタ A ベンチマークでは FullRow 2.7% 向上、Square 11.1%、FullCol 51%（348.5 から 526.7 TFLOPS）、ptxas 報告の溢れ書きは 664 バイトと 484 バイトから 320 と 160 に減少。作者は同時に注記：block_K = 128 と行主序共有 scale のパスは main 上で元々検証を通らず、今回の変更とは無関係で、別途調査待ち。

情報源：https://github.com/tile-ai/tilelang/pull/3286

1.6 メインリポジトリ：JIT 出力形状内のスカラパラメータを割り当て前に解析（#3602）

10-26 10:06 にマージ、7 ファイル +242/-3、#3406 を修正。Cython および PTO ラッパーはこれまで、出力を割り当てる際に明示的なスカラ PrimFunc パラメータで表現された出力次元を解析できなかった。現在はアダプタが「出力次元からスカラパラメータ位置への」マッピングを渡し、ラッパーは実引数値を直接用い、重複する起動パラメータを追加しない。リグレッションは両バックエンド、ゼロ次元と非ゼロ次元、スカラと多次元出力、出力順序、デバイス配置、起動パラメータ個数をカバーする。同族の欠陥に関する后续の 2 件はなお審査中：#3636 は (n, 2*n) のような複合次元式を扱い、#3638 は同名だが互いに独立した動的シンボルが名前で統合される問題を扱う。

出典：https://github.com/tile-ai/tilelang/pull/3602

1.7 メインリポジトリ：sm8x スパースメタデータのオペランド dtype がフォールバックなしで通過しなくなる（#3335）

10-26 に起票、作者は #271 のレビュー中に発見した。二つのギャップはどちらも同じ結果を指す。分析が通るプログラムが起動時に拒否される、または最終 TIR がどれだけ共有メモリを必要とするかを自己記述できない。第一に、メモリ分析は smem を facts.memory.shared.per_cta（sm_89 で 101376 バイト）と比較するが、CUDA はこの上限を静的共有メモリと動的共有メモリの両方に作用させ、ランタイム自身は 12 バイトの __shared__ ProgramMetaData を保持している。この占有は runtime.cuh にだけ書かれており分析には知らされていないため、ちょうど 12 バイト以内の配置は分析を通るが起動時に拒否される。第二に、分析は CTA あたりの共有メモリ高水位を RegionMemoryMetadata.peaks に記録するが、ConvertHIRToTIR はそれを出力 TIR に書き込まず、PrimFunction.metadata は印刷も解析もされないため、finalize の後に再計算しなければならない（#271 はまさに全整数アドレスの共有メモリビューを走査して再計算していた）。また作者が書いたホスト入口が過少申請でも実行前に発見されない。

5. トレンド観察

  1. 正確性欠陥の重心が「性能後退」から「コンパイル期に報告されず、特定のアーキテクチャやストレージドメインでのみ誤る」へ移った。当日の主線となる3件はいずれもこの類に属する：出力が誤ったストリームに割り当てられる（#3649、非デフォルトストリームかつ現在のストリームにキューされた作業がある場合にのみ破損）、TMA キャッシュヒントにテンプレート実引数が1つ足りない（#3683、eviction_policy 付きのバルクロードでのみ失敗）、sm8x のスパースメタデータにフォールバックがない（#3335、torch の正規の綴りでのみ認識され、さらに fp16 のレイアウト規約を誤って適用する）。この類の欠陥に共通するのはハードウェアまたはパラメータの前提があり、通常の CI のカバレッジ外にあるため、ますますファジングテスト系列によって駆動されるようになっている——本章で当日クローズされた6件のうち5件がこの系列に由来する。

  2. 同期とメモリ計画が主戦場に。当日浮上した #3680 の ThreadSync 欠陥3件、#3682 と #3681 の2件の修正、tvm フォークリポジトリ #88 の証明器修正、メインリポジトリ #3670 のリージョン化 kill 再配列、TileFoundry #272 の共有メモリピークが TIR に落ちない問題は、いずれも同じことを指している。コンパイラの同期とメモリ判断が「ヒューリスティック」から「証明可能」へと移行しつつあるということだ。これが #3666 の重要性を説明してもいる。組み込み TVM を独立パッケージ化された TIRx に置き換えたことで、以降この種の証明器修正がフォークリポジトリに留まらず、通常のリリースサイクルでメインラインに入れるようになった。

  3. バックエンド適応は「精密制御」段階に。昇騰の T.annotate_buffer_addresses により UB、L1、L0A、L0B、L0C、SS の各プールをバイト単位でアドレス指定でき、重なり・アライメント・容量の検証も行える。海光のレジスタパイプライン、warp 発散、scale バッファのデュアルバンク分割も、「動く」を「ハードウェア構造に沿って配置できる」へと押し上げるものだ。これらの機能は直近2週間に集中しており、国産バックエンドが可用性の閾値を超え、性能上限の問題に取り組み始めたことを示している。

  4. リリースエンジニアリングは依然として弱点。TileOPs の初回リリースは、ドキュメント、マニフェスト、パッケージング、API 安定性、入力検証がすべて整った後も、TestPyPI の試走と最初の tag で数日間止まっており、PyPI の成果物は 2025-10-09 のまま。196 スター、当日14コミットを合併したオペレータライブラリにとって、インストール可能性はさらなる1パーセントの最適化よりも外部採用速度を左右する。追跡チケットで唯一未完了の技術項目は MHA 行 0.996 であり、管理層はこれに tag を阻害させ続けるべきではない。

  5. 外部エコシステムは同期的に拡大中。RISC-V コミュニティハブリポジトリ、CANN オペレータリポジトリ、Hexagon バックエンドリポジトリが同日に出現または更新されたことは、TileLang が「tile-ai 組織のプロジェクト」から、複数プラットフォームがそれぞれリポジトリを建てるエコシステムへと変わりつつあることを示している。国内の読者にとって、RISC-V 方向は特に追跡に値する。これは従来の AI 眼鏡やエンドサイド推論のハードウェアルートと直接関係するが、現時点では空の骨格のみであり、実質的な進展は今後、実行可能なオペレータとバックエンドが着地するかどうかを見る必要がある。
