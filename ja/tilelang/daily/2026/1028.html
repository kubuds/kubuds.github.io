今日の重点

TileOPs 0.1.0 が本日の調査期間内にリリースされ、連日続いた「最後の1マスで止まる」状態に終止符が打たれた。PyPI 上の 0.1.0 成果物は 10-27 07:45（北京時間）にアップロードされ、前回デイリーレポートの締め切り時刻より45分遅い；GitHub リリースページは 13:15 に公開され、リポジトリに初めて正式な tag が付いた。リリースノートのハード指標は3グループ：206 個のオペレータすべてに manifest エントリがあり（シグネチャ、テストとベンチマーク負荷、roofline 公式、CI で逐条検証）；H200 上の 2265 行の夜間ベンチマークのうち 2262 行が最速の対照実装より遅くなく、幾何平均 1.37 倍、対照には torch.compile、FlashAttention 3、FlashInfer、vLLM、DeepGEMM、FlagGems を含む；206 個のオペレータのうち 195 件の foundry タグ付きマージは TileFoundry がカーネルを生成し同一の CI を通してリポジトリに取り込まれたものである。リリースと同時に公開 API が凍結され、以降 0.x は追加のみで変更なし、さらに API 互換性チェックスクリプトが新設され、前バージョンの書き方で呼び出す PR は直接失敗する。

24時間以内に tile-ai 組織は 20 件をマージ（tilelang 13、TileOPs 4、TileFoundry 2、tilelang-hygon 1）、審査中更新 45 件、新規 issue 7 件（うち 2 件は昇騰リポジトリのデイリーテストボット）。マージの重心は2つの線に分かれる：1つは浮動小数点セマンティクスと実行コンテキストで、ROCm は7つのデフォルト数学関数を高速組み込みから正確実装に戻し（MI300X 上の sin/cos 誤差が 7.8e-04 から 6.6e-08 に低減）、自動ターゲットは固定の 0 番カードではなく現在のデバイスを読むように変更、NVRTC と CuTeDSL は入力テンソルが存在するデバイスに応じてストリームを取得するように変更、自動チューニングのキャッシュキーに compile_flags を追加；もう1つは静的境界とスレッドドメインで、スライス填充は長さではなく領域末端で検証、範囲外の負インデックスはコンパイル期に拒否、T.ws(-1) の領域は全スレッドで実行するように変更。海光は 12 ファイル 1389 行をマージし、scale バッファを独立したデュアル bank に分割し LDS bank と分離した。サードパーティ側では Hexagon DSP バックエンドが単日 15 コミット、HVX ベクトル化、VTCM アリーナ、Crouton レイアウトと DMA 組み込みを一気に Crouton 上のマッピングとリダクションまで展開した。

1.1 メインリポジトリ：ROCm の exp/sin/cos がデフォルトで高速組み込みに降格しなくなり、sin/cos 誤差が 7.8e-04 から 6.6e-08 に低減（#3621）

10-27 22:39 にマージ、5 ファイル +107/-17、#3618 を修正。HIP 上では、T.exp、T.exp10、T.log、T.log2、T.log10、T.sin、T.cos の7つのデフォルト関数が tl.enable_fast_math の設定に関わらず __expf 一类の高速組み込みに降格していたが、CUDA 側は #875 の取り決めに従い正確実装を使用していた；逆に、明示的な T.__exp などの高速オペレータは HIP 上では全く下沉せず、tilelang.rocm.language 内で直接 AttributeError をスローしていた。本コミットで HIP と CUDA が同一戦略を採用：7つのデフォルトオペレータは HIPMath に委譲、8つのアンダースコア付き高速オペレータには HIPFastMath を指す最低下沉ルールを新設し、統一して FAST_MATH_INTRINSICS リストに移動して ROCm 言語層からエクスポートする。精度比較は #3618 の再現を使用：MI300X 上で exp と exp10 は相対誤差、sin と cos は絶対誤差（x は 1e4 まで）を見る。4列は順に T.exp、T.exp10、T.sin、T.cos、主干は 3.7e-06 / 4.1e-06 / 7.8e-04 / 7.8e-04、本コミットは 8.3e-08 / 8.1e-08 / 6.6e-08 / 6.4e-08。

1.2 メインリポジトリ：自動ターゲットが現在の HIP デバイスを読むように変更、マルチ GPU マシンで固定の 0 番カードアーキテクチャを取得しなくなる（#3594）

10-27 22:37 にマージ、2 ファイル +24/-1。determine_target(“auto”) は ROCm 上で登録済みの HIP 検出器に落ちるが、この検出器は無条件に torch.cuda.get_device_properties(0) を読むため、現在の HIP デバイスが 0 番カードでない場合、自動検出は 0 番カードのアーキテクチャを返してしまう。CUDA 側は早くから torch.cuda.current_device() を使っていたが、ROCm は追いついていなかった。修正方法は、まず現在のデバイスインデックスを取得してから属性を照会し、normalize_rocm_arch で機能サフィックスを除去する。追加テストでは current_device() をスタブ化して 1 を返し、同時に検出されたすべてのインデックスを記録し、gfx942 が検出されかつ 1 番カードにしか触れていないことをアサートする。修正前はこのアサートで probed == [0] が得られた。著者は本機に ROCm デバイスがないことを明記しており、テストはスタブ化した torch のみで検出ヘルパーを検証し、実際の HIP ランタイムは実行していない。本日別の #3549 の変更とは異なる関数である（#3549 は tilelang/contrib/rocm.py、本件は tilelang/rocm/target.py）。

1.3 メインリポジトリ：TMA gather/scatter の定数行インデックスを int32 に変換、リテラル記述でコンパイルクラッシュしなくなる（#3365）

10-27 09:15 にマージ、2 ファイル +44/-2、#2601 を修正。tma_gather4 と tma_scatter4 の 2 つのフロントエンドヘルパーは、Python 整数形式の行インデックスを受け取るとそのまま透過させ、TIR 内で確定した整数幅を持たないため Blackwell 上でコンパイルクラッシュしていた。他の行式はそのまま維持する。本件は Python 整数を int32 の TIR 定数に変換するのみで、Blackwell ゲート付きのコンパイル回帰を追加し、リテラル行インデックスで gather と scatter をそれぞれコンパイルし、生成された CUDA ソースに対応する命令が確かに現れることを確認する。著者はこのテストがコンパイル可能なことのみを検証し、実行時の数値的正しさは検証しないことを明記している。また提出者の本機の Windows Python 3.13 環境では Home Assistant の pytest プラグインが fcntl に依存しており、pytest の収集段階で失敗するため、本件の TileLang テストはローカルでは実際には実行できていない。

1.4 メインリポジトリ：NVRTC と CuTeDSL が最初の入力テンソルの所在デバイスに応じて現在のストリームを取得（#3359）

10-27 08:11 にマージ、2 ファイル +5/-4、#3301 の F149 と #3408 に続く。2 つのアダプタは以前、文字列プレフィックスでターゲット種別を判定し、かつデフォルトで呼び出し元の現在デバイスの現在ストリームを取得していたため、呼び出し元の現在 GPU とテンソルの所在 GPU が一致しない場合に誤ったストリームを選択していた。本件はターゲット種別判定に改め、最初の入力テンソルのデバイスに応じて現在ストリームを照会する。明示的に渡されたストリームハンドルは引き続き最優先であり、テンソルのない NVRTC 呼び出しは元のセマンティクスを維持する。これは昨日の out_idx 出力割り当てストリーム（#3649）に続く、ストリームセマンティクス整理の第 2 弾である。著者は境界を明確にしている。本件はストリーム選択のみを修正し、クロスデバイスのデフォルトストリーム起動コンテキストは未解決項目のままであり、この種の呼び出し元は起動前にテンソルの所在デバイスを現在デバイスに設定する必要があり、パッチには呼び出しごとのデバイスガードはない。検証では実際の Torch ストリームと GPU 起動で同一デバイスとクロスデバイスの非デフォルトストリームをカバーしたが、クロスデバイスのデフォルトストリームコンテキストの正しさは確立していない。

1.5 メインリポジトリ：自動チューニングのキャッシュキーに compile_flags を組み込み、同一カーネルでコンパイルオプションを変えても旧バイナリを再利用しなくなる（#3338）

10-27 16:57 にマージ、3 ファイル +28/-1、#3301 の F131 に続く。自動チューナーはコンパイル結果を永続キャッシュするが、キャッシュ識別子に compile_flags が含まれていなかったため、同一カーネルでデバイスコンパイラオプションを変えても旧バイナリにヒットし、測定された性能と実際のコンパイル結果が一致しなかった。本件は CompileArgs に実際に保存させ、元の順序でハッシュに参加させ、さらに flag を JIT 実装から AutoTuner.set_compile_args() を経て候補コンパイル、設定ごとの pass マージ、グループ化されたデバイスコンパイル、キャッシュカーネルロードまで一貫して透過させる。検証は既存の 3 つのキャッシュキーテストと、ネイティブランタイムによる CUDA の定点比較をカバーする。リストと文字列の両方の flag 形式が設定ごとの上書きで生存できる。著者は、従来のマージロジックがコンパイラマクロを落としており、まさに今回塞ぐべき穴であると指摘している。

出典：https://github.com/tile-ai/tilelang/pull/3338

1.6 メインリポジトリ：ThreadSync が address_of を書き込みとして記録し、不透明呼び出し後のフェンスを補完（#3346）

10-27 05:49 にマージ、2 ファイル +62/-1、#3301 の F305 を引き継ぎ、昨日のフェンスセマンティクスの主線を継続する。address_of 自体はアクセス情報を運ばず、ポインタを下流に渡すだけだが、アクセス分類器がその型を読み取りにハードコードしているため、共有バッファが不透明な呼び出しを経て書き込まれても writes 集合に入らず、後続の全ブロック読み取りは競合する書き込みを見つけられず、フェンスも計画されなくなり、スレッドはこうして書き込みを追い越して書き込み前の内容を読んでしまう。実測の CUDA 出力は非常に端的である。T.address_of(B[0]) 形式は extern の後にフェンスがなく、T.access_ptr(B, “w”) 形式にはある。後者はアクセス型を明示的に宣言しているため、この穴はずっと発見されなかった。loop_unswitching.cc はすでに address_of を書き込みとして保守的に扱っており、ThreadSync が唯一の例外である。本コミットは address_of を書き込みとして記録する。方向は保守的である。ポインタの用途が不明なら書き込まれる可能性があり、フェンス計画は安全側で一度誤えばよい。新たに 2 つの用例を追加し、当該カーネルが下沉された後、extern の後に __syncthreads() が続くことを断言する。

3.3 TileOPs 0.1.0 の既知のギャップと次のステップ：融合オペレータ、モデル全体、計算通信融合（10-27）

リリースノートは 4 つの既知の問題を列挙している。FusedAddLayerNormFwdOp がゼロから遠い行で精度を失い、1e36 に近い行でオーバーフローする（#2773、昨日のデイリーレポートでこの欠陥は既に記録済み）；同一ホスト上に異なるアーキテクチャの GPU がある場合、ある GPU 用にコンパイルされたカーネルが別の GPU 上で動作する可能性がある（#2302）；Bwd 系オペレータは直接呼び出す必要があり、torch.autograd に接続されない；単一のオペレータインスタンスは同時に 1 つのスレッドと 1 つの CUDA ストリームのみをサポートする。検証範囲は H200、Python 3.12 と 3.13 のみをカバーする；一部のカーネルには SM80、SM86、SM89 パスがあり、これらのパスは対応するデバイス上で動作するがリリース検証範囲には含まれない。ロードマップは 3 ステップである。まずオペレータ境界を跨ぐ複雑な融合（アテンションと前後の投影および正規化、層全体の MoE、GEMM epilogue 内の量子化）を行い、次にモデル全体のプリフィルとデコードを行いサービスエンジンとエンドツーエンドで比較し、最後に計算と通信の融合（テンソル並列 GEMM と all-reduce、エキスパート並列 MoE と all-to-all）を行う。この 3 ステップが実現すれば、TileOPs の對手は単一オペレータライブラリから推論フレームワークに変わる。

3.4 TileOPs に4件をマージ：where と masked_fill がチューニング可能に、D128 因果対角を64キー単位でスコアリング、疎な長 GDN プレフィルを分割、変更ログの日付をリリース日に設定（#2782 / #2783 / #2779 / #2781）

4件は10-27にマージされ、まさにリリース前の締めくくりとなった。#2782 は request_tune() が WhereFwdOp、MaskedFillTensorFwdOp、MaskedFillScalarFwdOp で ValueError を投げる問題を修正：自動チューニングはランダム生成された整数入力を受け付けないが、これら3つのカーネルは bool 条件やマスクを uint8 として渡していた。ランダムセレクタは各要素がどのオペランドを取るかだけを変え、候補の作業量は変えないため、ランダム整数入力を安全と宣言；3つのテストノードを追加し、主干では3例すべて失敗した。#2783 は D128 密プログラムの因果対角を最適化：因果呼び出しが1つの key セグメントのみで、両方の長さが128行境界上にある場合、最初に消費する warpgroup の対角 key タイルは全行に対して上位64キーをマスクするため、このステップを m64n64 の QK と64キー softmax で実行するよう変更；この選択はコンパイル期フラグ（diag_aligned、カーネルキーに含まれる）である。実行期に64と128幅の QK 間で分岐すると、ptxas が一部の特化で各 WGMMA を直列化する（C7511）ため、フラグに切り替えた後は manifest 内のすべての D128 プレフィル特化で C75xx が出なくなった。#2779 は SM89 上の疎な長系列 GDN プレフィルを状態スキャンと独立出力プログラムに分割し、密で key 主順の D128 入力かつ少なくとも16384トークン、状態スキャン CTA が SM 数の4分の1以下の場合に適用；(1, 16384, 4, 128) bf16 のベンチマークでは所要時間が約0.612ミリ秒から約0.470ミリ秒に短縮され、flash-linear-attention の0.441ミリ秒に対して0.939倍となった。#2781 は CHANGELOG の0.1.0の日付を PyPI に登録された日（2026-10-27）に定め、コントリビューター文書からリリースごとの設定と Actions のクリック手順を削除した。

3.5 TileFoundry に2件をマージ：ウィンドウ全体をオペランド自体として発行、動的共有メモリをカーネル実際使用量でサイズ決定（#273 / #271）

2件とも10-27にマージされた。#273 は sm_89 GEMM の沈み込みを修正：schedule finalize が書き出した内容がコンパイルできない。沈み込みがアキュムレータ全体をゼロ開始・自身と同一スパンのウィンドウ T.ptr_of(acc[0:0+16, 0:0+8]) で包むが、CUDA codegen はフラグメントレジスタタイルのポインタスライスを拒否し「通常のソースレイアウトが必要」と報告；MMA もレジスタフラグメントを lhs_frag_dst[0:0+16, 0:0+32] のような裸の Slice として読み、codegen は同様にハンドラを持たない。修正は沈み込み側で行う：StoragePlan.operand はもともと「ゼロ開始かつオペランド全体にまたがるウィンドウ」をオペランド自体として扱うが、実体化と命令発行は依然として Slice を構築していた。これを一度だけ判定するよう変更——MLIR の TrivialSubViewOpFolder と同じ置換を行う。#271 は動的共有メモリを修正：合成ホストエントリが各 TIR カーネルを dynamic_smem=0 で起動するため、整数 TensorView オフセット経由で共有メモリにアクセスするカーネルに領域が割り当てられず、48 KiB を超える場合は cudaFuncAttributeMaxDynamicSharedMemorySize の設定も必要だがランチャーは一切設定していなかった。作者は #267 の「ターゲット容量どおりに満額割り当てる」提案を採用せず、カーネル実際使用量でサイズ決定する方式に変更。理由は静的共有メモリと動的共有メモリが同じ上限を共有し、各ブロックの申請量が1つの SM に何ブロック載るかを決めるため——sm_89 で99 KiB を満額にすると512バイト使用のカーネルでも1ブロックしか載らなくなる。CUTLASS と TileLang も同じ方式でサイズ決定している。

5. トレンド観察

第1に、TileOPs 0.1.0は「オペレータライブラリ」のコスト構造を別のアルゴリズムに置き換えた。従来の方法ではオペレータ数がハードウェアとモデル需要に応じて線形に増加し、人手がボトルネックになる。ここでの方法は、各オペレータについてまずYAML仕様を1份書き、シグネチャ、ペイロード、rooflineを明確に宣言し、次にagentがカーネルを生成・チューニングし、最後に仕様から派生したテストとベンチマークで准入を行う。206個のオペレータ、195件のfoundryタグのマージがこのフローの初回全量納品である。これが持続可能かどうかは2つのことにかかっている。仕様が複雑な融合オペレータをカバーできるか（ロードマップの第一歩がまさにこれ）、そしてベンチマークが「ベンチマークに合わせてチューニングされたが実際にはロバストでない」カーネルを阻止できるか——FusedAddLayerNormFwdOpがゼロから遠い行で精度を失うという既知の問題は、まさにこの種のリスクのサンプルである。

第2に、本期間のマージはほぼすべて「サイレントエラー」である。ROCmの数学関数がデフォルトで高速ビルトインを使うことでsin/cosが3桁の差を生む。address_ofが読み取りと見なされることで不透明呼び出し後の共有メモリが書き込み前の内容を読む。T.ws(-1)の領域がゼロスレッドで実行され、保存がすべて破棄されかつエラーが報告されない。スライス填充が長さではなく末端で検証され、直接範囲外書き込みとなる。負のインデックスが回り込んだ後もなお負であり、割り当て開始点より前に落ちる。これら5件の共通点は、コンパイルが通り、実行時にエラーが出ず、結果が誤っていることであり、しかもすべて直近2週間以内に集中的に発見されている。大規模モデルのためにカーネルを書く言語にとって、この種の欠陥のコストはコンパイル期のエラーよりはるかに高く、それらは同じ工学的要請を指している——「エラーは出ないが動作が正しくない」書き方をコンパイル期に拒否すること。本期間の境界検証の2件の修正とws(-1)の修正が行っているのはまさにこれである。

第3に、バックエンドのカバレッジは「ベンダー主導」から「コミュニティ自発」へ移りつつある。公式に保守されているAscend、海光、沐曦、摩尔線程の4ライン之外で、Hexagon DSPバックエンドが1日で15件をマージし線形代数プリミティブをCroutonタイルに展開し、PPU版ではゼロ変更ラッパーが現れ、CANNコミュニティが独自にオペレータリポジトリを構築しそれを使ってDeepSeek V4.1 Flashのモデル断片を組み上げた。これらの動きはいずれもtile-ai組織のリポジトリにはないが、いずれもTileLangの言語層の安定性に依存している。これこそが0.1.0で公開APIを凍結し、API互換性チェックをCIゲートにした意義である——下流が多くなるほど、後方互換性の価値は高まる。

第4に、キャッシュの同一性という問題に2つのバックエンドが同時に着目した。メインリポジトリはcompile_flagsを自動チューニングのキャッシュキーに組み込み（#3338）、AscendはBishengのビルド同一性をバイナリキャッシュキーに組み込んだ（#3691）。同じカーネルでも異なるコンパイルオプションや異なるコンパイラでは異なるバイナリが生成され、キャッシュをソースコードと形状だけでキーにすると誤ヒットし、測定された性能が実際のコンパイル結果と合わなくなる。2つの独立した路線が同じ日に同じことを行ったことは、この種の問題が実用上すでに十分に痛みを伴うことを示している。
