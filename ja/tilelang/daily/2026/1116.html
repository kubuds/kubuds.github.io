    1. トレンド觀察

今日の重點

この調査期間で重心が移動した。前回はメインリポジトリで1日に5件がマージされ、すべて昇騰向けだった。今回はメインリポジトリが72時間でわずか1件のドキュメントコミット（LSPリポジトリのリンク）である一方、TileOPsが3日間で15件、TileFoundryが3件、さらに昇騰適応リポジトリの9件を加えると、コード量はほぼすべてオペレータライブラリとスケジューラに移っている。TileOPsは11-15の1日で11件をマージし、そのうちデコード側のW4A16タイルは単一consumer warpgroupから2つに拡張され、7つのデコード行が10～20%高速化、marlinに対する優位性は1.20倍以上に広がった。これは散発的な修正ではなく、「オペレータ＋セレクタ＋コストモデル」の3層を同時に変更するものだ。まずセレクタがより多くのシェイプでデュアルwarpgroupのタイルを選択するようにし、次にタイルにKスライス単位のメタデータロードを追加し、最後にnightlyの32行回帰で遅くなった行がないことを確認する。

同じ日に、今回記録すべき最も重要な因果連鎖が現れた。11-13の#2896は128行W4A16タイルを手書きのwarp-specializedメインループに置き換え、H200上でchunked-prefillを37.3マイクロ秒から31.6マイクロ秒に短縮した。36時間後、#2901がそれを修正している——sliced_pairのout_shared一時保存がi // wg_rows == bzの条件分岐内に書かれていたが、TileLangはこの書き込みを保護する、全256消費スレッドをカバーするバリアを同じ分岐内に配置することがあり、もう一方のwarpgroupはそのバリアに永遠に到達できず、2つのwarpgroupが同じバリアの異なるインスタンスで停止し、カーネルがハングする。さらに厄介なのは、バリアの配置が同じcache keyの2回のコンパイル間で安定せず、CIの永続カーネルキャッシュが悪いビルドを再生し続けるため、main上のgpu-smokeが直接落ちたことだ。修正自体は素朴で、両方のwarpgroupに一時保存を行わせ、各自が自分の半分だけを保存するようにするだけだが、これは1つのことを示している。自動warp specializationの正しさはもはやパスの順序だけでなく、バリアがどの分岐に挿入されるかにも依存し、その位置はコンパイルプロセスにとって不透明である。

第二の事柄はissue側にあり、規模はコード側より顕著だ。72時間以内にtile-ai組織で406件の新規issueが起票され、そのうちcn-sysの1アカウントが11-15夕方の1時間46分で172件を連続起票（番号#4208～#4381が連続、他ソースの混入は0件）、ilovexsirが3日間で3バッチに分けて142件を起票、2人合計で314件、全体の77%を占める。cn-sysのこのバッチの範囲は、examplesやREADMEの具体的な数値（flash-attentionが前方誤差0.5%未満を謳う一方、同ディレクトリの5つのチェッカーはすべて5%を使用。deepgemmのベンチマークはcache_sizeに8192を使用するが、このパラメータの単位はMBであり、128 MiBのL2をフラッシュするために8 GiBを割り当てることに等しい）から、コンパイラ本体にまで及ぶ。auto-scheduleのIR構造アクセサのフィールド漏れ、PTO codegenのポインタ要素型がハードコードされたbfloat16のフォールバックを取る、などだ。ilovexsirのバッチはより体系的で、142件のissueが5つのbatch PR（#4201～#4205、同一分に起票）に対応し、各PRは「本来エラーになるべきなのにならなかった」入り口のグループを修正する。例えばT.copy(transpose='False')は文字列’False’が真値であるため黙って転置を有効化し、_make_ascend_target()はdict(target_dict or {})ですべてのfalsyな設定キーを捨てる。監査と修正の間にパイプラインが形成され始め、その代償として審査待ちキューが102件に積み上がっている。

第三の出来事は、昇騰側のオペレータ移行が「アルゴリズムファミリー単位でまとめて実装」の段階に入ったことだ。11-13の一日で、tilelang-ascend は九件をマージした：DSA スパースアテンションのフォワードパイプライン版、バックワード、topk リダクションの三点セット、KDA の chunk_delta 三点セット、加えて bitwise 四合一、alloc API ドキュメントと catlass サブモジュールのアップグレード。これらはもはや単点の穴埋めではなく、モデル単位で進んでいる：DeepSeek V3.2 の sparse MLA は DQK を 512+64=576 に合成して一度の GEMM にし、Kimi 系 KDA はゲート減衰を host 側で事前計算した M 行列に吸収し、バックワードオペレータは 79395 マイクロ秒を 27388 マイクロ秒に圧縮した。同時に catlass は v1.0.0-6 から v2.2.0 へアップグレードし、ついでに以前は完全にサイレントだった欠陥を修正した：旧版の CopyL1ToL0A/L0B には float 特殊化がなく、fp32 GEMM はエラーを出さずに NaN や負の無限大を直接出力していた。

RISC-V 側は今期初めて沈黙を破った。kubuds の TVM 路線は mahiru、karen 之外に新たに kubuds-riscv-hikari ブランチを開き、五件のコミットには K3 移植と検証レポート、rv64gc ビルドのアンロック（USE_LLVM=ON のリンク問題と八スレッドビルド）、デコード 4 タイルとプリフィル 8 タイルのグリッド分割、そして XSMTVDotII/vmadot 公開仕様の溯源記録が含まれる；同時に、コミュニティインデックスページは最初の PR を受け取り、kubuds fork のプロジェクト説明を README に書き込んだ。MLIR 路線（RuyiAI-Stack/tilelang-riscv）と算能 TPU リポジトリの参照は一切動かず、二つの路線は依然として分けて見る必要がある。

1.3 TileOPs：11-15 に単日で十一件、W4A16 デコードタイルがさらに 10–20% 高速化（11-15）

11-15 の1日で11件のマージ、うち #2955 はその日の締めくくり：W4A16 セレクタが「最大32行」の遅延スケーリング選択手法を1つの128スレッド consumer warpgroup から2つに移し、重み行数で分担、K スライスで分割して CTA 数を維持、stream-K は依然として単一 warpgroup のまま。理由は、デコードタイルが命令発行で詰まり、コストモデルが単一 warpgroup の手法を好むため——実測ではその経路上で issue slot 占有率が49.5%、DRAM はわずか54%。結果として7つのデコード行が main より10〜20%高速化し、marlin に対して少なくとも1.20倍リード、prefill-mlp-up は変化なく依然として torch に0.7%遅れ。同じ日に #2952 がターゲット側カーネルの2つのテーブルを1つに統合し、読み取り前にコピーすることで並行下での「イテレーション中の辞書サイズ変更」を回避、#2904 は「デバイスなし、名前付き target なし、プロセスデフォルトなし」の呼び出しが _Unresolved object is not callable を投げる問題を修正。

1.4 TileOPs：ping-pong 三連、MoE 共有エキスパートが各繰り返しで FlashInfer-CUTLASS を圧倒（11-15）

同一テーマの3件の漸進的変更。#2919 はまずグループ化 GEMM セレクタが自ら選び出した64x256の単一 warpgroup コンパクトタイルをデュアル warpgroup の ping-pong で実行するように変更し、各タイルの收尾が別グループの mainloop の下に収まるようにし、ds-v3-grouped-t2048 のダウン投影 GEMM を1818マイクロ秒から1707マイクロ秒に短縮。#2953 は同じ手法をセレクタ自身の64行コンパクトタイルに適用し、融合 gate/up と短いグループ化タイルをカバーし、「短いグループ化タイルは依然として1つの warpgroup を残す。收尾が短すぎて何も隠せないため」と明言；結果として FusedMoESharedExpert の ds-v3-grouped-t2048 が各繰り返しで FlashInfer-CUTLASS を圧倒（中央値5674対5744マイクロ秒）、32行六オペレータのプログラム変化で遅くなった行は1つもない。#2915 は未融合の ping-pong グループ化 GEMM 出力を64列 TMA box で一時保存し、第5のリングレベル（64x256タイルで40 KiB 一档増加）を得た。

情報源：https://github.com/tile-ai/TileOPs/pull/2919、https://github.com/tile-ai/TileOPs/pull/2953、https://github.com/tile-ai/TileOPs/pull/2915

1.5 TileOPs：#2901 が #2896 によるハングを修正、バリアが warpgroup 分岐に落ちた（11-15）

これは今号で最も読む価値のある1件。#2896 のマージ後、main 上の gpu-smoke がハング：sliced_pair は i // wg_rows == bz という条件下で out_shared を一時保存し、レイアウト lowering 後は「その半分のタイルを保持する」consumer warpgroup のみが一時保存ループを実行；TileLang は時にこの書き込みをガードする、全256消費スレッドをカバーするバリアをこの分岐に挿入し、もう一方の warpgroup は永遠に到達できず、2つのグループが同一バリアの異なるインスタンスで停止し、カーネルがデッドロック。#2899 が以前追加した明示的バリアではそれを防ぐのに不十分——コンパイラは依然として自ら分岐内にバリアを挿入できる。修正方法は一時保存を条件外に移すこと：2つの consumer warpgroup がそれぞれ自分の半分を書き込む。本当に目を見張るのは後半：バリアの落ち位置が同一 cache key の2回のコンパイル間で変化し、永続化された CI カーネルキャッシュが悪いビルドをずっと再生し続けるため、一度の不安定な計装が安定した失敗に変わったことだ。

情報源：https://github.com/tile-ai/TileOPs/pull/2901、https://github.com/tile-ai/TileOPs/pull/2899、https://github.com/tile-ai/TileOPs/pull/2896

1.8 TileOPs：#2951 適応型プーリングを lane ごとに分割、メインブランチで3種のプーリングが細長い形状でコンパイル不能（11-15）

5. トレンド観察

第一に、メインリポジトリは静かでオペレータライブラリが動くという重心の移動が2期連続で起きている。前回はメインリポジトリが1日で5件すべて昇騰、TileOPsが連続ゼロコミットだった。今回は逆で、メインリポジトリは72時間で文書1件、TileOPsは3日で15件、TileFoundryは3件。2期を合わせて見ると、TileLangの開発重心は「コンパイラ本体」から「オペレータライブラリ＋スケジューラ」へ移りつつある。コンパイラ本体の変更は回帰修正（PTOの系列の事後対応）に集中し、新規機能はオペレータライブラリのタイル、セレクタ、コストモデルという形で現れることが多くなっている。判断根拠はマージ数だけでなく依存方向にもある。TileOPsの性能結論はTileFoundryのrooflineとスケジューリングを引用する必要があるが、TileLangメインリポジトリは今期それらに何も新しく提供していない。

第二に、自動warp specializationの正しさが一級リスクになっている。#2896 から #2901 への連鎖が示すのは、ある性能変更が同期の責任をコンパイラの自動計装に委ねると、計装位置が正しさの一部になり、しかもそれが上位層に対して不透明になるということだ。同じcache keyで2回コンパイルしても、バリアが分岐内に落ちることもあれば分岐外に落ちることもある。さらにCIの永続化カーネルキャッシュが重なると、偶発的な不良計装が固定化されて安定した失敗となる。この問題には現状、構造的な解決策はなく、「書き込み操作を条件分岐の外に移す」といった局所的な回避策しかない。今後より多くのタイルがping-pong方式を採るなら、同種のハングが再発する可能性が高い。

第三に、監査は「問題を発見する」段階から「問題をパイプライン生産する」段階へ変わった。3日間で406件のissue、2アカウントで314件、うちcn-sysの172件は1時間46分で書き上げられ、ilovexsirの142件は5つのbatch修正PRに直接対応している。このパターンは確かに「欠陥発見から修正まで」のサイクルを圧縮している（同一日内にissueとPRが併存）が、圧力はレビュー側に移っている。レビュー待ち102件、マージ30件、うち22件のmlir-ascend同型PRはごく少数の人しかレビューできない。次段階のボトルネックは発見速度ではなくレビュー帯域になるだろう。

第四に、昇騰のオペレータ移行が「モデルファミリー単位でまとめて着地する」段階に入っている。DSAの3点セットはDeepSeek V3.2に対応し、KDAの3点セットはKimi系の線形注意に対応する。1日のうちに9件すべてが特定モデルの完全なリンクを指しており、散発的なオペレータではない。これは下流にとって朗報だ。モデル移行のコストは「オペレータを1つずつ揃える」から「ファミリー単位でまとめて移す」へ変わる。しかし同時に、基盤テンプレートライブラリの品質の重みが上がることも意味する。catlassのfp32 GEMMがNaNを出力しながら全くエラーを報告しないという既存欠陥がその例だ。これはサードパーティのsubmoduleの中に隠れており、オペレータ層のテストでは発見できない。

5点目は、RISC-V四源で初めて実質的な進展が現れたが、動いているのは1つだけである。kubudsのTVM路線は新たにhikariブランチを開設し、K3移植検証とRVVグリッドデータを示した。コミュニティのインデックスページは初めてこのforkを収録した。一方、MLIR路線（RuyiAI）と算能TPUリポジトリの参照は動いていない。2つの路線の役割分担はすでに明確である。TVM路線は「動作し、実測データがある」状態を作っており、MLIR路線は「設計はあるが、コミットはない」状態で止まっている。判断は変わらない。この路線は現在も小規模な投入であり、調査期間に沿って追跡する価値はあるが、週単位で進捗を計算するのは適切ではない。

制約説明：本期の結論はGitHub検索インターフェースとリポジトリの原子流から得たもので、コードレベルの再確認は行っていない。PRの性能数値は、作者がPR説明に記載したベンチマーク表（H200、CUDA 13.2、PyTorch 2.13）から取得したもので、本機での再測は行っていない。issue統計はsearchインターフェースのtotal_countと5ページ分のページング結果に依存している（406件と逐条集計は一致）。タイトル分類はキーワードによる粗分類のみである。tilelang-ascendのデフォルトブランチはmainではなくascendc_ptoであり、初回クエリでmainに基づきコミットを取得した際に404が返されたため、修正後に再クエリした。mlir-ascendのharnessとhygonのtilelang-tileops-fixブランチは、調査期間内にいずれもコミットがなかった。ニュース側はゼロヒットで、外部報道によるクロス検証はできない。
