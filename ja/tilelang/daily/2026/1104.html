本日の重点

この日の主线は「性能を取り戻す」修正である。前の調査期間にマージされた #3643 は、実際の正確性の問題を解決した。個別に呼び出される ThreadSync("shared") と ThreadSync("shared.dyn") が、互いに交わらないスレッドグループに同じ名前付きバリア ID を割り当てる可能性があった。修正方法は、後の呼び出しが前の呼び出しで既に使われた ID を保持するようにするものだが、この保持ルールは同時にもう一つの事柄を妨げていた——同じスレッドグループが二つのスコープ間で本来同じ ID を再利用できるということである。代償は直接 TileKernels の mhc_pre_big_fuse カーネルに降りかかった。このカーネルはブロックごとに 96 スレッドで、スレッド 32 から 95 が二段式 cp.async パイプラインを実行し、非同期待機後の同期が第一パスで ID 3 を取得し、同じ 64 スレッドのバッファ依存同期が第二パスで ID 4 を取得する。余分なその ID により、コンパイル産物が宣言するバリアリソースが 4 から 5 に変わる。B300 上で隠れ次元 1280 を実行すると、バリア占有上限が 16 ブロック/SM から 12 ブロック/SM に低下し、レジスタ、共有メモリ、同期命令数はいずれも変化しなかった。#3761 の対処法は、ThreadSync が順序付きのスコープリストを受け入れるようにし、CUDA パイプラインを ThreadSync(["shared", "shared.dyn"]) に変更することである。同期は依然として元のスコープ順序で計画・挿入されるが、一部のバリアの ID は二つのスコープがともに処理された後に初めて統一的に割り当てられる。スコープを跨いで同じ ID を共有する前に、全く新しいアナライザで参加述語が候補スレッド範囲全体で成立することを証明する。分岐と Bind コンテキストは ConstrVisitor が提供し、スレッド関連の述語はデフォルトで成立するのではなく証明義務として扱い、証明済みの稠密グループは包围盒体積を直接用いて部分スレッド数の列挙をスキップし、未証明のグループはスコープをキーに残し参加者カウントも一緒にキーに入れ、明示的に番号付けされたバリア（より早い ThreadSync が割り当てた ID を含む）は引き続き保持される。変更は 401 行、4 ファイルに及ぶ。

著者は説明の中で非常にクリーンな帰属実験を行っている。コンパイル産物で宣言されたバリアリソース数を単独で変更し、いかなる実行可能命令も動かさなければ、同じ遅延を再現できる。この種の実験は記録に値する——「性能後退」を感覚から特定可能な単一変数に変え、修正の受け入れ基準も明確にした。すなわち、大まかにスコアが速くなることではなく、リソース宣言が 4 に戻り、占有が 16 ブロック/SM に戻ることである。

第二条は供給側の減算と口径の統一である。#3736 は tilelang/language/ast/、tilelang/language/parser/ と tilelang/language/tir/entry.py をまとめて削除した。これらは初期のローカル TVMScript パーサフォークの残したモジュールで、約 3380 行の Python であり、リポジトリ内に呼び出し元はもうない。言語層は現在 tilelang.language.tir.common を通じて上流の tvm.tirx.script.parser インターフェースを使用し、AST とステートメントのオーバーライド登録は tilelang.language.overrides にあり、T.prim_func と T.macro は tilelang.language.eager からエクスポートされる。実際の変更は 1 行追加、3384 行削除、10 ファイルで、同時に docs/conf.py の *language/ast* に対する無視ルールを削除した。公開言語層のエクスポートは方言テストとフロントエンドテストが担保する。#3546 は自動チューニングのデバイス口径を修正した。set_autotune_inputs がインストールする供給クロージャは、呼び出し点から決して渡されないパラメータ上でベースデバイスを解決していたが、実際に渡されるのはカーネルパラメータリストであった。そのため CUDA または CPU のフォールバック分岐が、CUDA のないマシン上でキャプチャした各テンソルを CPU に移動し、チューニングのたびにランチャーのデバイス不整合で失敗していた。現在クロージャは get_current_device() を使用し、デフォルトのテンソル供給と同じ戦略とした。CUDA の動作は変わらず、昇騰と MPS は現在のデバイス上で供給するように変更し、その他のバックエンドは依然として CPU にフォールバックする。受け入れはデュアルカード Ascend950 上で行った。三つの昇騰自動チューニング回帰は修正前全滅、修正後全通過し、メインリポジトリの testing/python/autotune/ は 12 項目通過、28 項目スキップ、さらに 3 項目がこのマシンに CUDA がないため失敗し、著者は明確に CUDA CI での検証に委ねている。

第三条は昇騰側である。GM から L1 へのコピーを「1 ディスクリプタ 1 行列」からバッチ全体に拡張した。#3689 は [B, M, N] 領域を一つの T.copy として書けるようにし、lowering はバッチ ND2NZ ディスクリプタを生成し、ソース側のバッチと行の stride を保持し、宛先側のバッチ間隔は物理レイアウトから導出し、転置バッチは DN2NZ で処理する。GM 境界を超えるソースバッチは直接スキップし、宛先ストレージをそのまま保持し、M/N の末尾パディングは合法なバッチにのみ作用する。既存の二次元および単一 matrices の動作は変わらず、実装は AscendC バックエンドのみを対象とし、L1 宛先が規範的な行列レイアウトであることを要求し、PTO は今回の範囲外である。検証は Ascend950DT と CANN 9.2 上で行った。50 の AscendC サンプルテストと 1733 の昇騰単体テストが通過し、うち 28 のデバイスケースがバッチと M/N 末尾ブロック、バッチ全体の越境、非連続ソース stride、宛先ストレージがより大きい場合、矩形転置をカバーする。CUDA と PTO のケースは除外され、CI イメージが使用する CANN 9.3 はローカルでテストされておらず、この点は著者が説明に記している。変更は 579 行、10 ファイルに及ぶ。

4つ目は TileFoundry の隠れた実装です。前回のレポートではまだ「審査中」でしたが、今回の調査期間でマージされました：#285 により、sync 分析が計画したコミット、待機、フェンスが実際に CUDA lowering によって発行され、発行された内容と計画が一致するかどうかが項目ごとに逆検証され、不一致の場合は LoweringError がスローされます。コーパス上での結果は、デフォルトフローで 14 個のプログラムに同期が追加され、31 個が拒否されました。この 14 個の TIR とメインラインの違いは追加された文のみで、別の 30 個はメインラインと完全に同一です。単一の sm_89 上でビルド可能かつ同期を含む 7 個のプログラムを実行したところ、6 個がリファレンスと完全に一致し、synccheck と memcheck はすべてクリーンでしたが、同じ 7 個をメインラインの方法で lower すると 4 個で結果が誤りとなりました。作者が動機で示した直接的な症状は、sm_89 の E4M3 GEMM の最大偏差 659 です。このコミットは 788 行追加、214 行削除、25 ファイルで、「分析が証明できる」から「発行は証明と一致しなければならない」へと進めました。

#3762 は昇騰側のユーザーによりコミットされました。環境は Ascend950PR（NpuArch 3510 / dav-3510）、CANN 9.2.0-beta.2、ドライバ 25.7.rc1、torch_npu 2.12.0、ソースからインストールした TileLang（10-21 の e84ce3de）です。問題は T.simd.vcvt(src, "uint8", sat=False) が int32 ベクトルに対して sat=False を暗黙に無視し、常に飽和することです。負の値は 0 に、255 を超える値は 255 になり、エラーも警告も出さず、呼び出し側はラップアラウンドセマンティクスを使っていると思い込んでしまいます。ドキュメント文字列はこの状況を明確に記載しています——sat=False のとき範囲外の値はラップアラウンドする——期待値は -1 が 255、-128 が 128、300 が 44 ですが、実測では -1 が 0、-128 が 0、300 が 255 です。影響は int8 量子化の終盤のような f32 から int8 への変換経路に及びます。負の中間値が一度でも現れると、セマンティクスがラップアラウンドからゼロへの切り捨てに変わってしまいます。#1980 は昇騰リポジトリの自動デイリーテストで、11-03 09:35 の回は 3030 項目すべて合格、合格率 100%、ワークフロー実行番号 41553942797 です。この 2 つの数字を並べて見ると興味深い点があります。昇騰リポジトリのデイリーテストは満点のグリーンですが、デイリーテストでカバーできないセマンティクスの差異（例えば sat パラメータの実際の挙動）は依然として人手による報告に頼らざるを得ません。

5. トレンド観察

第一に、性能回退が一級市民として扱われ始めており、その修正方法は結論よりも方法論の面で記録に値する。#3643 が正確性修正のために導入した ID 保留ルールは、それ自体が必要かつ正しいものである；#3761 はそれを回退せず、保留と再利用を異なる階層で併存させた——スコープを跨いで1つの ID を共有する前に、関与する述語が恒真であることをまず証明し、証明できなければスコープ付きカウントに戻す。著者の「宣言されたバリア資源数のみを変更する」という隔離実験と合わせ、この修正チェーンは「正確性」と「資源宣言」という2つの事柄を切り離した：後者は単独で再現・単独で検収できる変数である。この切り分け能力こそが、コンパイラプロジェクトが「動く」から「保守可能」へ向かう指標にほかならない。

第二に、昇騰のエンジニアリング化は2本の脚で同時に進んでいる。1本はアーキテクチャ：#1975 は2887ファイル、60万行の新規追加で TileLang-Ascend 全体をメインラインのマルチバックエンドフレームワークへ移し、arch="dav-2201" のような識別子でバックエンドを分流させ、A2A3 と A5 を同一リポジトリ内で直交して共存させることを目標とする；もう1本はパイプライン：mlir-ascend の #208 は Codex の初期化、接続、復元の3つのワークフローとタスク引き継ぎを .workspace/ に書き込み、メインリポジトリと昇騰リポジトリもそれぞれ Agent ディレクトリを持つ。「リポジトリを移行する」ことと「インテリジェントエージェントでリポジトリを移行する」ことを同じ日に見ると、昇騰側のボトルネックがすでに「オペレータ不足」から「一貫したエンジニアリング骨格と再利用可能な移行フローの不足」へ転換したことが見えてくる。

  1. オペレータライブラリの自己証明文化が深まっている。TileOPs で今期審査中の数件は、ほぼすべて「証拠」を PR に書き込んでいる。実際のルーティングで測定した Qwen3-30B-A3B EP8 のグループサイズ（48 層のうち偏りの中央寄りにある第 44 層を取得）、35 個のマスク構築による TIR がメインラインとバイト一致、L2 flush の変更には 46 行の実装比較表を添えて旧 flush が 120 MB のダーティ行を残すことを説明、W4A16 のコストモデルは「どの項目がデータで固定できず削除されたか」を明記。TileFoundry は別の道を歩んでいる——同期を証明可能な分析に仕立て、lowering に逆検証させ、分析が拒否したケースを直接列挙する（TMA と wgmma の完了セマンティクスが未宣言、スレッド境界を跨いで等しくないループ）。二つの道を合わせると同じ指向を示す。すなわち「証明していない」ことを認める方が、「動いた」を「正しい」と見なすよりましだということだ。

  2. リスク面はインストール形態に集中しつつある。1 日 7 件の新規 issue のうち 4 件は、pip パッケージを使い、WSL で実行し、コンシューマ向け sm_89 カードを使う同一の外部報告者からのもので、すべて再現スクリプトが添付されていた。#3775 は本番環境での「pip パッケージ + 複数 CUDA コンテキスト + nvrtc バックエンド + CUDA graph キャプチャ」の組み合わせである。これらはコンパイラの深層欠陥ではないが、新規ユーザーが初めて試す際の体験を決める。昇騰リポジトリの日次テスト 3030 項目が全緑でありながら sat=False というセマンティクスの偏差が依然として人手の報告に頼っていることと対照すると、テストカバレッジの形状と実際の使用形状の間にはまだ距離があることが分かる。

最後の観察：今期もニュース側は依然として空白で、15 件の候補のうち 12 件はリポジトリ発見によるものだった。TileLang の対外的な声量は依然として「DeepSeek と昇騰」のような出来事に紐づいており、日常的な進展はコミットの中だけで起きている。このプロジェクトを追う人にとって、これはデイリーレポートの主体が PR と issue であり、報道ではあり得ないことを意味する——これはすでに複数期連続で安定した形態となっている。
