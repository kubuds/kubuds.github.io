今日の重点：上流昇騰リポジトリの CI 悪用、コントリビューター資格情報盗難の公開開示

11-16 14:16（北京時間）、貢献者 liggest が tile-ai/tilelang-ascend で issue #2016 を提出し、自身のアカウントが 11-15 に冒用されたことを公開説明し、完全な攻撃チェーンを明らかにした。11-15 朝 7 時から、miramar-labs というアカウント（このアカウント自体も乗っ取りの疑い）が PR #2014 を提出し、その中に CI 実行時にサーバー情報を収集する悪意のあるスクリプトを追加した。リポジトリの CI は自社サーバー上で動作しており、被害後、攻撃者はサーバーから大量の情報とログイン資格情報を取得し、その中には liggest に属する GitHub token も含まれていた。11-15 午前 9:39 から 11:40 にかけて、攻撃者はこの token を使って liggest を装い、#2014 の下に 18 件のコメントを連投し、公開 PR を物資受け取りの窓口として利用した疑いがある。また tile-ai/TileOPs にマイニングスクリプトを含む 2 つの PR（#2902、#2903、まもなくメンテナによりクローズ）を提出し、さらに SemiAnalysisAI/InferenceX に同種の PR #5086 を提出して相手のベンチマークサーバーに実行させようと試み、16 日未明に本人が発見してクローズした。作者によると、2 つのマイニングスクリプトは GitHub の自動チェックにより実行されず、実行記録も確認されていない。

対応側：アカウント自体には二要素認証があり、直接の乗っ取りはなかった。作者は GitHub CLI と VSCode の旧認可を取り消し、token はすでに無効で 15 日以降アカウントに異常はないと述べている。悪意のあるフォークは当面フォレンジック用に保持。盗まれたデータの CI サーバーはセキュリティ処理待ち。#2014 も処理が必要で、そうでなければ悪意のあるスクリプトが再びトリガーされるリスクが残る。作者の提案は、新規貢献者の PR はメンテナの承認後にのみ自社サーバーを使用する CI フローをトリガーするよう変更することである。

検証側：GitHub 検索によると、miramar-labs は 11-14 23:18Z から 11-15 02:04Z の間に 4 つのリポジトリに同スタイルの PR を提出している——tile-ai/tilelang #4148、tile-ai/tilelang-ascend #2014、tile-ai/tilelang-mlir-ascend #251、tile-ai/TileOPs #2900。名目はいずれも「キャッシュウォームアップ」または「CI 能力検出」であった。4 つの PR はすべてクローズ済みで、一つもマージされておらず、#2014 は 11-16 11:29 にクローズされた。作者は issue クローズ後に追加コメントを寄せ、先の説明は「誇張成分もあったように見えるが、とにかくアカウントは復旧した」と述べており、したがって上記の被害範囲はあくまで作者の自述に基づくもので、第三者の再検証はまだない。本コミュニティへの直接的な影響は 3 点ある。自社 CI の信頼境界が外部 PR によって突破されたこと、個人 token のライフサイクルを監査に組み込む必要があること、同名の PR が複数のリポジトリに同時に現れることである。

情報源：https://github.com/tile-ai/tilelang-ascend/issues/2016 、https://github.com/tile-ai/tilelang-ascend/pull/2014 、https://github.com/tile-ai/TileOPs/pull/2902

今日の重点：TileOPs が 1 日で 18 件マージ、オペレータライブラリが pilot モデルのインターフェース整合へ転換

調査期間内に TileOPs メインブランチへ 18 件のコミットが着地し（18 個の PR に相当）、今シーズンで 1 日あたりの密度が最高の日となった。しかも方向性は高度に一致している。まず manifest のインターフェース記述能力を補完し（#2958 で呼び出し期の type と default、list[Tensor] とスカラーまたはテンソルの共用型を導入。#2967 で pilot モデルが実際に呼び出す 7 つのオペレータを spec-only として登録し、実装済みの 15 のオペレータに pilot モデルが使うパラメータと入力を追加）、その後 [Feat][foundry] PR を次々と重ねてオペレータを補充した。当日は 2 つの新オペレータ（ゲート付き RMSNorm、MaskedScatter）をマージし、同時に Embedding はマージ後同日に revert された。これは新オペレータが直接マージではなく TileFoundry のラウンドを経る必要があることを示している。#2958 はついでに 2 つの意味的エラーも修正した。RoPE ファミリーは従来 0..S-1 位置のみ回転しており、デコード位置 p の回転結果が誤っていた。FP8QuantPerTokenGroupFwdOp はその参照実装と一致していなかった。

1. コアプロジェクトの進展

1.1 メインリポジトリに 4 件の bugfix がマージ：JIT デバイス復元、NVRTC 単一パラメータ、cython 動的共有メモリ、ROCm HIP ランタイム再利用

メインリポジトリの調査期間内に4件がマージされたが、いずれも新機能ではなくランタイムの不具合修正である。#3872 は tvm_ffi ホスト stub が現在のデバイスのみを設定し、復元しない問題を修正：cuda:0 上で cuda:1 のテンソルを呼び出すと、結果は正しいが現在のデバイスが cuda:1 に残ってしまい、その後の device="cuda" による割り当てが暗黙にずれる。修正方法はアダプタ層で torch.cuda.device(...) を使って呼び出しを包み、終了時に復元する。#3880 は NVRTC バックエンドで単一引数カーネルが起動できない問題を修正：引数名と型を ", " で連結した後、単一引数の場合はタプルにならず、cuLaunchKernelEx が直接 TypeError を投げる。末尾カンマ付きのタプルリテラルに変更した。#3882 は cython バックエンドの動的共有メモリ上限が init() で一度しか設定されない問題を修正——この属性はデバイスごとのものであり、48 KB を超えるカーネルが他のデバイスで cudaErrorInvalidValue を報告する。各カーネルに _set_dynamic_smem() ヘルパー関数を生成し、引き上げ済みのデバイスを記録するように変更した。#3899 は ROCm 下で HIP stub が PyTorch 同梱の libamdhip64 を見つけられない問題を修正：PyTorch の ROCm wheel は RTLD_LOCAL でロードされるため、stub はまず RTLD_NOLOAD で既にマップされたランタイムを探査し、dlopen で2つ目のランタイムをロードしてモジュールハンドルがランタイムをまたぎ、最初のカーネル起動が失敗するのを避ける。

ソース：https://github.com/tile-ai/tilelang/pull/3872 、https://github.com/tile-ai/tilelang/pull/3882 、https://github.com/tile-ai/tilelang/pull/3899

1.2 manifest を宣言的パラメータ型にアップグレード、pilot モデルのインターフェースを一括补齐

#2958 は manifest を「固定テンソルとスカラーのみ記述可能」から、テンソルシーケンス（torch.cat）、スカラーまたはテンソルの二者択一（flash_attn の seqlen_offsets、torch.clamp(min)）、必須だが None を許容（mamba_ssm の bias）の3種類のシグネチャを宣言できるよう拡張し、呼び出し時の入力を type と default を持つ宣言に統一した。従来「スカラーまたはテンソル」のために分割していた3組の Scalar/Tensor オペレータペアもこれに伴い統合された。#2967 はその上で pilot モデルのインターフェース真値を补齐：新たに spec-only として登録された7項目（torch 参考実装を含む）、実装済み15項目に pilot モデルが実際に渡すパラメータと入力を追加し、カーネルが非デフォルト値に遭遇した場合は OpNotAvailableError で拒否する。項目の状態は implemented のままとし、ベンチマーク行がこのエラーに遭遇した場合は「利用不可」として記録し、失敗とは判定しない。

ソース：https://github.com/tile-ai/TileOPs/pull/2958 、https://github.com/tile-ai/TileOPs/pull/2967

1.3 3つの新オペレータ：ゲート付き RMSNorm と MaskedScatter が落地、Embedding はマージ当日に回退

#2984 は RMSNormGatedFwdOp を新規追加：最終軸でグループ化して RMSNorm を行い、silu(z) または sigmoid(z) により正規化の前または後でゲート可能。全行程 float32 で計算し、丸めは一度のみ。1つの TileLang カーネルがすべての呼び出し形態をカバーする（8レーン、各レーン2回の16バイトアクセスで128幅の行を構成、16行で128スレッドの CTA を構成、より広いグループではレーンを1024に倍増し warp をまたいで共有メモリで合計）。レジスタ上限はスレッドあたり64、ゲートの指数と逆数はそれぞれ1命令で行う。ベンチマークは vLLM の RMSNormGated、mamba_ssm の rmsnorm_fn、fla の rms_norm_gated、Hugging Face の Qwen3_5RMSNormGated、および torch 参考実装と torch.compile に整合し、验收ラインに到達した。#2982 は MaskedScatterFwdOp（out-of-place 版 masked_scatter、fp16/bf16/fp32 と input、mask のブロードキャストをサポート）を新規追加：各 CTA は完全な mask 連続セグメント（行数は32 KB を境界とする）を担当し、まず本セグメントより前の真値セグメントを数えてから自身をスキャンする。16バイトベクターごとに一度だけ読み取り（真値セグメントは source を読み、偽値セグメントは input を読む）、セグメントのバイト数が4ブロックを超える場合は先に分割カウントを行う。torch eager および torch.compile と比較してラインに到達。vLLM の in-place マルチモーダルマージはセマンティクスが異なるため比較不可とした。

同日に別途、次のような反复もあった：#2977 が EmbeddingFwdOp をマージした後、#2983 が同日中にそれを全体としてロールバックした。理由は当該 PR が誤マージであり、新規オペレータは別個の TileFoundry ラウンドを経るべきというものである。ロールバック後、当該項目は spec-only に戻り、カーネル、オペレータ、ベンチマーク、テスト、ワークロードが一括して削除された。#2975 は依然審査中で、同一オペレータの正式提案である（token インデックスにより重み行を gather する）。

情報源：https://github.com/tile-ai/TileOPs/pull/2984 、https://github.com/tile-ai/TileOPs/pull/2982 、https://github.com/tile-ai/TileOPs/pull/2983

1.4 GEMM の3本の量子化ライン：INT8 W8A8 は 192 幅 ping-pong に変更、W4A8/W4A16 stream-K はそれぞれ収尾

#2959 は INT8 ping-pong GEMM を「最も忙しい CTA の列数が 128×128 タイル以下」の場合に 128×192 タイルへ変更し、グリッド末尾は bf16 GEMM の狭タイル規則に従って 32 列単位のストレージボックスにまとめる（本期 manifest の各 prefill 行ではいずれも 160 幅）。各幅について対応する幅の WGMMA を発行する。同一の最忙 CTA ワークロードの下で、192 幅タイルは MAC あたりの TMA と WGMMA 共有メモリバイト数がより少なく、CTA がコンシューマを切り替える回数が3分の1少ない。llama3-8b prefill-qkv の最終ウェーブで最も忙しい CTA の列数は 1536 から 1504 に減少した。#2960 は W4A8 prefill の stream-K 収尾を変更する。他の部分チャンクがすべて書き込み済みとなった時点で、遅れて到着した 0 番コントリビュータは自身の部分和を書き込まず、カウントが当該タイルのコントリビュータを満たした者が収尾する方式に変更した。各 CTA は acquire-release アトミックを1つだけ（名前付きバリアの後ろに配置）使用してスレッドごとの fence を置き換え、CTA 同士の相互待機はない。stream-K タイルを含むプログラムのみが新経路を通り、それ以外のコンパイル結果はメインブランチと一致する。#2964 は W4A16 stream-K のずれを修正する。カーネルは元々 cta == first_cta で「未使用スロットの補完と ceil 除算」のロジックを保護していたが、TileLang の簡約が CTA の第2セグメント以降でそれを丸ごと削除し、第1セグメント以降で折り畳んだため、2つの CTA が共有するタイルに未書き込みスロットが残り、リダクションがダーティメモリを読むことになった。最大誤差は 2.4 から無限大に至る。修正は、当該プログラムを構築するデバイス上でホストが一度だけテーブルを構築し、「タイル内の何番目の CTA か」でスロットを特定する方式に変更した。

量子化 GEMM のカバレッジも同時に補完：#2969 は W4A16 行を42条、W4A8 行を13条、FP8 行を11条新規追加した。各行は Llama-3 8B/70B、Qwen3 8B/32B または DeepSeek-V3 の実投影（TP1 または TP8、デコードバッチ）に対応し、従来 W4A16 のベンチマーク行は45のデコードスケジューリング区間のうち3つのみをカバーしていた。別途審査中の #2990（W4A16 デコードタイルのペア条件を厳格化）があり、原因は issue #2966 に記録された同批の変更が一部の8行・16行形状で変更前より遅くなったことである。

情報源：https://github.com/tile-ai/TileOPs/pull/2959 、https://github.com/tile-ai/TileOPs/pull/2964 、https://github.com/tile-ai/TileOPs/pull/2969

1.5 アテンションとリニアアテンション：paged GQA キャリブレーション続編、DeltaNet 起動設定、GLA 逆方向共有メモリ

#2956 は paged GQA のキャリブレーション続編：分割リダクションを split 主序で重みテーブルを保存する方式に変更し、各ロウブロックに CTA を1つ割り当て、スキャンで生成されたリクエストマッピングを読む（従来は行並列で [block_M, num_split] テーブルを書き、16および32路分割時に直列化していた）。GQAPagedFwdKernel.default_config はパッキング後の行が実際に満杯の場合のみ 128 行クエリタイルを使用する（48 行ページではキータイルが1つの WGMMA より狭くなり、デコードパッキングが逆に 128 行に膨らむ）。左ウィンドウの場合、RoPE 前処理もウィンドウ内範囲で準備するよう変更した。#2978 は WS カーネルに「ウィンドウがページテーブル全体をカバーし、いかなる key も隠さない」ケースを引き継がせる。従来 WS カーネルは RoPE なしのウィンドウをすべて拒否していたため、window4096/long-b1-q2048-kv2048 は cp.async カーネルにフォールバックし、FA3 の 2.17 倍の時間を要していた。当該 PR は自評で依然として合格ライン未満（below bar）であり、改善ではあるが達成ではない。

線形注意メカニズム側では、#2979 が DeltaNetChunkFwdOp の chunk_size=16 における起動構成を修正した（準備と出力は最大2本のwarp、奇数V/8は1本のみ許可、再帰列のwarp数は8列タイル数を整除する必要がある）。#2980 はchunk起動上限を各GEMMのwarpタイルから導出するように変更し、chunk 32/64/128で発生していた「TileLang warp分割失敗」の形状群（従来はchunk 16のみ特例対応）を修正し、不適合な chunk_size/dim_k/dim_v をランダム失敗ではなくビルド時に拒否するようにした。#2965 はSM89上でGLA逆方向の共有メモリ生存期間を99 KiB予算内に抑え（ゲート因子の再計算、状態勾配の再ロード）、以前は上限超過だった4つのdtype/形状組み合わせ（FP32の32×64×192、32×32×256とFP16/BF16の32×128×128）を復活させたが、依然3グループは拒否のまま。#2976 は2つのDeltaNet計測ユースケースをSM90に指定し、SM89上でSM90専用のデコードwarpカーネルを先にビルドしてしまう事態を回避した。

5. トレンド観察

  • オペレータライブラリが主戦場に：今回のマージ 30 件のうち、TileOPs が 18 件を占め、メインリポジトリはわずか 4 件のランタイム bugfix のみでした。コミュニティの作業重心はコンパイラ本体からオペレータ実装とインターフェースの真値へ移っています。
  • 実装よりインターフェースが先行：manifest のパラメータ型、pilot モデルインターフェースが同日に補完され、その後新規オペレータがラウンドごとに順次実装されています。Embedding の誤マージと当日のロールバックは、プロセスが緩んでいるのではなく引き締まっていることを示しています。
  • プロセスのツール化：topa の new-op ラウンド、ステートマシンと issue ルーティング、さらに TileFoundry のコストモデルの穴埋めが相まって、「オペレータ要件 → スケジューリング可行性 → 実装と検収」のクローズドループを構成しています。この層は過去 2 週間で最も急速に成長した部分です。
  • 性能修正が逆効果に：W4A16 のペアタイルが一部の小さい形状で回退（issue #2966）しており、量子化 GEMM の最適化は「形状ごとの段階分けが必須」の段階に入っています。単一タイル戦略で広く利益を得ることは難しくなっています。
  • セキュリティ境界の補完が必要：自前 CI が外部 PR に突破され、個人 token が盗用された事件は、新規コントリビューターの PR の CI トリガー権限はデフォルトでメンテナ承認が必要であるべきことを示唆しています。この点は RISC-V と AI コンパイラコミュニティ全体にも同様に当てはまります。
  • RISC-V 側のペースは安定：今回は MLIR ルートのマージ 1 件のみ（buddy-opt のデフォルト化とサンプル補完）で、TVM ルートと算能 TPU 側は動きがなく、通常の交替推進です。
