本日の重点

本日調査期間の重心は昇騰側にある。tilelang-mlir-ascend は Ascend 910（A2/A3）の NPUIR バックエンド全体をメインブランチに統合した。1コミットで55ファイル、21490行の追加となる。Python 側は tilelang/ascend910 パッケージ（backend / adapter / codegen / compiler / execution_backend / jit / pipeline / runtime / target に加え、language 配下の kernel、copy、gemm、npuir 方言面）、C++ 側は src/ascend910/target 配下の開発者向けとエキスパート向けの2系統のエミッタ、op 層と LowerNpuirBlock、NpuLoopVectorize、RewriteFDivToMul の3つのパス、ランタイムには npu_launcher.h と npu_utils を追加し、インストールは install_npuir.sh を使用、target 別名は ascend910 / ascend-910 / a2 / a3 / npuir を受け付ける。作者が提示した受け入れ基準はリポジトリ同梱の2組のテストケースである。pytest testing/npuir の504項目が全通過、examples の72例中71例が通過し、タイムアウト0件・エラー0件。唯一失敗した deepseek_v32/fp8_lighting_indexer.py は旧バックエンドでも同一マシンで同様に失敗しており、環境と許容誤差の問題である。2件目のコミットは旧バックエンドとの挙動差異を項目ごとに整合させるもので、重点は bf16 の適正化（HIVM は bf16 オペランドを受け付けないため、fp32 で計算後に明示的に変換）と動的 extent のコピー沈み込みにある。

TileOPs は本日7件をマージし、2本の主線はいずれも性能側にある。セレクタはもはや manifest に密着したフィッティングを行わず、ビジー時間（device_busy_ms）上で160個の稠密 shape、60個の m 9–32 の shape、264個の m≤8 の shape で再キャリブレーションし、softmin 期待対数後悔による座標降下を用いる。エンドツーエンドのビジー時間後悔はホールドアウト manifest 上で5.79%から0.48%に低下し、m≤8 のホールドアウト集合では14.18%から1.79%に低下した。GEMM 側では coop2_swap を新規追加した。非 NT レイアウトを転置した永続カーネルに置き換え、2つのコンシューマ warpgroup がそれぞれ128行を保持し、テール書き込みは stmatrix.trans と TMA 転置を経て書き戻し、広幅・狭幅 tile の混在配置（例えば 2112 = 13×160 + 32 を160幅 tile と128狭幅 tile に分割）にも対応する。2112×7168×4096 TN は195.3マイクロ秒から175.3マイクロ秒に短縮され、同一マシン上の別の H200 では174.3から158.5マイクロ秒となり、いずれも QuACK の187.9および167.0マイクロ秒を上回った。

リダクション側は同日にまず壊れてから修正された。午前中に #2787 が int32 キーによる extrema リダクションの NaN 伝播を実装し、#2788 が並列 cumsum の行 tile を変更、いずれも07時前後に着地した。その後 #2790 と #2792 がそれぞれ2つのリグレッションを収束させた。cumsum はシードによる分割と2回の発射に変更し（(8,65536) float32 は12.75マイクロ秒から5.18マイクロ秒に短縮、同時にメインブランチの65535 tile 超での発射失敗も修正）、extrema は PTX の max.NaN / min.NaN を使用し、16バイト単位でないベクトルの行では別カーネルを通すようにした（amax (2048,4096) bf16 は8.352マイクロ秒から6.976マイクロ秒に戻り、FlagGems より高速）。この「同日中に導入して修正する」というリズムは、TileOPs の夜間ベンチマークがリグレッションを当日中に食い止めていることを示している。

1.1 メインリポジトリ：スカラー読みのインデックス係数が lane 数に混入しなくなり、行幅32768以上のコンパイルクラッシュをクローズ（#3453）

10-28 11:06 にマージ、単一ファイル +8/-5。ベクトル化方式で行全体を読みつつ、同時にインデックスでその行の単一要素を読む kernel が、行幅を 65536 で剰余した結果が 32768 以上になるとコンパイル時に InternalError: Can’t fetch the lanes of a scalable vector を報告する。根本原因は VectorTypeAccessChecker::OnArrayAccess にある。これはスカラー読みを access_dtype.with_lanes(me->coeff) として記録するが、me->coeff はインデックス読みの剰余係数であり、x[row, 0] では行幅に等しい。DataType の lane 数は 16 ビットしかなく int16 として読み戻されるため、32768 から 65535 はスケーラブルベクトルと見なされ、lanes() が get_preferred_dtype 内で直接例外を投げ、さらに広い倍数では静かにラップアラウンドする。修正方法は、係数を別途 int64_t に格納し、互換性判断ではこれを用いて剰余を取り、スカラー読みの dtype には要素型のみを保持する。この欠陥の元のトリガー場景は TileOPs の GroupNorm である。Stable Diffusion の 40960 と 163840 の 2 つのグループ幅がいずれも該当する。検証は 2 回の wheel ビルド比較で行った。主干は 32768 と 40960 の 2 つの幅でコンパイルに失敗し、本コミットはすべてのテスト幅でビルドできる。

出典：https://github.com/tile-ai/tilelang/pull/3453

1.2 メインリポジトリ：バッチ all-reduce がスカラーブランチに従ってスレッド区間を解析し、batch>1 で 2048 個の出力がすべて誤る問題を修正（#3341）

10-28 05:46 にマージ、2 ファイル +170/-8。スカラー all-reduce ブランチは発射呼び出しの前に参加スレッドの区間を解析する（reducing_threads が 32 より大きく、ターゲットが名前付きフェンスをサポートする場合は ResolveAllReduceThreadRange を通る）が、バッチブランチはブロック境界をそのままオフセットとフェンス幅として取る。帰約スレッドが [32, 96) のような 0 から始まらない局所区間である場合、バッチ呼び出しは 0 番スレッドからインデックスし、ブロック全体で等しくフェンスし、非参加スレッドの未初期化レジスタが帰約に折り込まれる。batch=1 は正しく、batch=2 では同一 kernel 上で 2048 個の出力要素がすべて誤り、最大絶対誤差は 1083 で、いかなる診断もない。修正方法は、バッチブランチとスカラーブランチを同じ解析にし、解析されたオフセットと範囲を MakeBatchAllReduce に渡し、ワークスペース stride はブロックサイズを維持する。新規テストは同一 kernel 上で batch=1 と batch=2 を実行し、torch リファレンスと比較する。

出典：https://github.com/tile-ai/tilelang/pull/3341

出典：https://github.com/tile-ai/tilelang/pull/3465

1.4 メインリポジトリ：スパース MMA の K 末尾ブロックが静かに見逃されなくなる（#3367）

出典：https://github.com/tile-ai/tilelang/pull/3367

1.5 メインリポジトリ：atomic_addx4 のターゲット dtype を float* に絞る（#3369）

10-28 16:08 にマージ、3 ファイル +27/-9。CUDA の atomic_addx4 と atomic_addx4_ret の汎用実装はこれまで任意のターゲットポインタを受け付け、int32 や int64 ターゲットは float セマンティクスに落ちて誤って計算されていた。本コミットは 2 つの汎用オーバーロードを float* ターゲットに限定し、fp16 と bf16 の既存特化は変更しない。Python 側 API は型中立を維持し、CPU バックエンドの整数ターゲットは影響を受けない。CUDA 側に整数ターゲットのコンパイル失敗回帰ケースを追加し、CPU C バックエンドに 2 種の整数幅の累加正確性ケースを追加する。

出典：https://github.com/tile-ai/tilelang/pull/3369

1.8 メインリポジトリ：profiler 出力インデックスの検証を統一、スカラー形式とリスト形式で同一の境界ルール（#3486）

10-28 19:24 にマージ、2 ファイル +15/-9、#2884 を修正。profiler と adapter の両側でこれまで result_idx の扱いが不一致だった。スカラー形式は境界チェックを行っていたがリスト形式は行っておらず、負のインデックスも正規化されていなかった。本コミットで BaseKernelAdapter と Profiler が同一のルールを共有するようにし、None、整数、整数リストを受け付け、-len(params) から len(params)-1 で判定し、正当な負のインデックスは正規化し、範囲外および非整数要素は ValueError を送出する。CPU 側の回帰テストを 28 項目追加し、スカラー形式とリスト形式の両方の経路をカバーした。

出典：https://github.com/tile-ai/tilelang/pull/3486

5. トレンド観察

昇騰側の進め方はこの二日間で既に明らかである。メインリポジトリは時間単位で小規模な修正（キャッシュキー、レジスタフェーズ）をマージし、専用リポジトリ mlir-ascend は一度の2万行のマージで 910 の NPUIR パスをフィーチャーブランチから主干線に移し、tilelang-ascend は PTO と AscendC のデュアルバックエンドという既定のリズムでドキュメントとオペレータの補完を行っている。三箇所のリズムは異なるが、指し示すものは同じである。910 のコンパイラパスは「動く」から「受け入れ可能」へと転換しつつあり、504 項の自己テストと 71/72 のサンプルが今回示された受け入れ基準である。注目すべきは審査待ちキューにおいて a2a3 のスケジューラ移行が 100 ファイルを占めていることで、次の段階の変動量がオペレータ層ではなくスケジューリング層にあることを示している。

性能側の看点は測定基準そのものにある。TileOPs のこの2件はセレクタと GEMM の結論をいずれもビジー時（device_busy_ms）に移し、同一の PR 内で単一呼び出しとバックツーバック呼び出しの差異を示した。単一読み取り方式では本実装が QuACK をリードするが、バックツーバックかつ電力上限付きのトレーニングシナリオでは10の大行のうち6行が後れを取る。これは「ある行が何マイクロ秒速くなったか」よりも重要なシグナルである。なぜならトレーニングの実際はバックツーバックだからである。#2791 はこのことを独立した項目とし、チームが基準の問題を製品の問題として扱い、ベンチマークの偏りとして粉飾していないことを示している。

エンジニアリング衛生面で本日記録すべきは3点ある。第一に、同一バッチ内の自傷と自修（#2787/#2788 は午前にマージ、#2790/#2792 は午後に撤回）で、夜間ベンチマークのフォールバックが機能していることを示すが、同時に帰約这套代码の意味的境界が依然として脆いことも示している。第二に、without_kernel_cache() の意味的欠陥（#3699）が移行過程から摘出されたことである。プロセス内の2層キャッシュが CacheState を消費せず、テストは冷間コンパイルだと思い込んで実際には古い kernel を取得している。この種の欠陥は「我々のテストはすべて通った」を無意味にする。第三に、SM120 上で13のサンプルが失敗したこと（#3701）が、サンプルが Hopper のサイズをハードコードしている問題を露呈したことである。Blackwell の搭載量が上がると、この種の「サンプルは製品ではない」という負債は繰り返し計上されるだろう。
