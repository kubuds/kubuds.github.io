今日の注目：TileFoundry が同日に Metal ターゲットと自動微分を実装

11-18 の 1 日で TileFoundry は 2 件のプラットフォーム級の変更をマージした。#354 で Apple Metal ターゲットを新規追加し、 #355 で自動微分を新規追加した。前者はコンパイルフローを Apple GPU まで延伸し、後者はフレームワーク自身に逆伝播を生成させる。いずれも実行可能なカーネルを生成しない：Metal は TIR までのみ実現し、自動微分は HIR モジュールを生成するのみである。

Metal 側では metal.Target("apple.m2_pro.gpu") を新規追加。トポロジは threadgroup から thread。ハードウェアパラメータは TOML に記載し、公開ソースを付す。機能表は 27 個の MSL ネイティブ関数名をそのまま採用する。

T.metal 下には計 9 個の命令オペレータがある。行列系は ldmatrix、stmatrix、matmul と mma。リダクションとシャッフル系は reduce、prefix、shuffle、shuffle_fill と ballot。1 回の呼び出しで G 個の SIMD group をカバーし、quad group は同じオペレータ群で幅 4 の mesh 上に表現する。

各オペレータにつき 1 ファイル。typeinfer、access、evaluator の規則は同一ファイル内に記述し、レイアウトには名前付き定数を用いる。MSL は行列の lane マッピングを規定せず、作者が M2 Pro 上で実測した後に仕様へ書き込む。HIR は hir_matches によりマッチングする。fragment オペランド上の MatMul は matmul に落ち、Reshard はメモリと fragment の間で ldmatrix と stmatrix に落ちる。本コミットは以前の #294 を置き換えるもので、後者はターゲットインターフェースの再編成により rebase できなくなっていた。

自動微分側には differentiate(module, wrt, recompute) を新設。これは <Name>Forward と <Name>Backward の 2 モジュールを返す。フォワードは結果と saved タプルを返す。バックワードは結果の勾配と saved を受け取り、wrt ごとに勾配を返す。

バックワード規則はオペレータごとにそれぞれのファイルへ記述し、新設の interfaces/autodiff 経由で登録する。対象範囲は組み込み Qwen モデルの全オペレータクラスに、ReLU と Log を加えたもの。兄弟および子スロット呼び出し、タプル引数、MeshRegion、反復回数が静的に数えられるループをサポートする。

ループは各反復で変化する値のみを積み上げる。帰納変数、キャプチャ、定数のみに使われる量はバックワードで再計算されるため、層ループは重みを複製しない。勾配レイアウトは DTensor を踏襲する。

情報源：https://github.com/tile-ai/TileFoundry/pull/354。

今日の重点：TileOPs が 1 日で 23 件をマージ、FP8 量子化チェーンを補完、2 件の性能負債を当日クローズ

11-18 の TileOPs メインブランチには 23 件のマージが落ち、北京時間 10:17 から 21:50 まで続いた。主線は FP8：トークンごとのグループ量子化、短行 GEMM ストリーミング、paged decode の書き直し、WGMMA のプリミティブ化という 4 件が同日に主干へ入った。

FP8QuantPerTokenGroupFwdOp は UE8M0 スケールを採用する（#3026）。出力は DeepSeek-V4-Flash の act_quant(x, 128, "ue8m0") とビット単位で一致し、スケールは float8_e8m0fnu で格納する。新たに inplace 疑似量子化を追加し、モデル内でストライド付きの kv[..., :448] を先にコピーする必要がなくなった。

UE8M0 パスは bfloat16x2 でリダクションとスケーリングを行い、飽和する e4m3 変換前の clamp を除去する。比較実装は vLLM の per_token_group_fp8_quant であり、DeepSeek と TileKernels の数値はコメントに記載している。

FP8 paged GQA decode カーネルは全面的に書き直された（#2997）。各 CTA は 1 リクエストのパック行、1 つの KV ヘッド、1 区間の key を受け持つ。各 FP8 key/value タイルは 1 回だけアンパックされ、TMA warp がページのコピーを担う。上限は共有メモリに由来する：H200 では 8 行タイルで 44,287 リクエスト、64 行タイルで 33,023 リクエストを処理できる。

短行 FP8 は 64 行ブロックのストリーミングへ変更（#3010）。1 つのプロデューサー warpgroup が深い TMA リングを通じて b を運び、1 つのコンシューマー warpgroup が各 128 幅 K ステップの FP8 WGMMA 部分和を float32 に加算する。

メインブランチは従来、8 行または 16 行を 64 行または 128 行タイルにパディングしていた。これにより 160 タイルが 132 CTA に載るか、split-K に回っていた。実測では DRAM ピークのわずか 31% から 52% であった。

同一バッチにはさらに 2 件の仕上げがある。#3030 は FP8 ストリームの各ステップにおける 4 つの k32 WGMMA を TileLang プリミティブで発行するよう変更。これに伴い dense_wgmma_helper.h を削除し、当該カーネルのみが使用していた TrailingFence テンプレート引数も併せて除去した。#3029 は共有メモリの記帳を修正：スケールバッファは従来、1024 バイトのアラインメントを考慮せず生バイトで加算されていた。このため m=16、n=163840、k=3584 の形状は起動時に失敗していた。

2 件の性能負債が同日にクローズされた。#3023 は TopKSelect を書き直し：行数が SM 数の 2 倍未満の呼び出しはレジスタカーネルへ回す。1 回のグローバル読み込みで 1 行を処理し、4096 バケットのヒストグラムで閾値を定める。長行は radix に回し、1 回 16 バイトで 4 つの key を装填する。3 つの decode 行は vLLM に約 2 倍遅れていた状態から 1.22 から 1.34 倍の先行へと変わり、#3016 をクローズした。

#3022 は MLA cache を 16 バイトベクター単位で行コピーするようにし、最大 1024 スレッドとする。メインブランチはコピーをレイアウト推論に委ねていたため、448 幅 latent ではスレッドあたり 7 回の 2 バイトスカラーアクセスになっていた。これが DeepSeek-V4-Flash decode が vLLM に遅れていた直接の原因である。

情報源：https://github.com/tile-ai/TileOPs/pull/3026。

1. コアプロジェクトの進展

1.1 メインリポジトリの CPU バックエンドに 2 つの論理リダクションの逐次降載を追加：any_of と all_of

#4389 CPU バックエンドに tl.any_of と tl.all_of の専用降載を追加。これまでこの2つのオペレータは CPU の通常パイプラインを通せなかった。実装は新たに LowerCPUAnyAll pass を追加し、LowerTileOp の前に挿入する。行優先順のシリアルスキャンへの降載で、短絡を伴う：any_of は真値にヒットした時点で停止し、all_of は偽値にヒットした時点で停止する。

空のリダクションは標準の単位元を取る：any_of は false、all_of は true。数値要素は非ゼロを真値に変換し、浮動小数点と bfloat16 の NaN は真とみなす。while 条件内のリダクションは各条件判定時に再初期化して再スキャンし、意味は従来と一致する。この pass は同時に CPU の Python 変換インターフェースにも公開される。

情報源：https://github.com/tile-ai/tilelang/pull/4389。

1.2 topk 回帰テストで Z3 にリソース上限を設定し、CUDA CI 上のタイムアウトを解消

#4407 は test_topk_candidate_overflow の CUDA CI 上でのタイムアウトを処理する。原因は簡約フェーズで高コストな Z3 クエリが発行されていたこと。修正はこのテストがカーネルをロードする際に arith.z3_rlimit を 100 に設定し、既存の他の JIT オプションは維持する。変更はこの回帰テストのみに作用する。

作者はローカルで topk の4つの特化について TIR を生成し、制限設定後に Simplify が完了することを確認した。作者は同時に、本機には CUDA コード生成も、利用可能なリモート GPU もないと注記している。完全なコンパイル所要時間と GPU 上の正確性はいずれも未検証である。

情報源：https://github.com/tile-ai/tilelang/pull/4407。

1.3 昇騰自動チューニングテストで NPU 間プローブを削除し、後続ケースの汚染を回避

#4401 は set_autotune_inputs テスト内の other_npu 分岐を削除する。この分岐はランタイムがデバイス間の入力アライメントをサポートするか判定するため、NPU 間コピーを1回実行する。一部の Torch-NPU と CANN の組み合わせでは、このコピーが NPU コンテキストを中止させる。

RuntimeError を捕捉してケースをスキップしてもコンテキストは復旧しない。同一 pytest プロセス内の後続の無関係なケースも連鎖的に失敗し、故障の現れ方は実行順序に依存する。削除後も3種類のカバレッジは維持される：現在の NPU 上で捕捉した入力は現在の NPU に留まる、CPU 上で捕捉した入力は基準デバイスへ移動する、渡されたテンソルは基準デバイスと一致しなければならない。

情報源：https://github.com/tile-ai/tilelang/pull/4401。

1.4 CUDA Tile IR バックエンド RFC の再提出：Tile IR で表現できる部分のみを変換

#4402 と #4403 は CUDA Tile IR バックエンドの RFC を提出した。中英それぞれ1部で、docs/compiler_internals/tileir/ に置かれる。目標は TileLang プログラムから CUDA Tile IR を生成し、tileiras にコンパイルとスケジューリングを委ねること。レイアウト、パイプライン、warp 特化、命令選択はいずれも tileiras が決定し、ハードウェア世代に応じて最適化する。

バックエンドは Tile IR が正しく表現できる意味のみを変換する。変換できない意味は直接コンパイルエラーとしてそのプログラムを拒否し、既存の CUDA バックエンドとの完全な互換性は追求しない。作者が示す利点は、カーネルを変更せず、アーキテクチャ依存のスケジューリングを手書きせず、自動チューニングのみで良好な性能が得られることである。

この版は以前の #3247 の再作である。レビューは旧実装について、try-catch が多すぎる、見たことのある形式ごとに個別に降載する、別の IR を新設する、約1.85万行の Python で pass を書く、という4点を指摘した。新 RFC はこの4点に対して再設計され、PR は現在ドラフトで、議論は #4403 で行われる。

情報源：https://github.com/tile-ai/tilelang/issues/4403。

2. マルチバックエンド適配（昇騰 / 海光 / 摩尔線程 / 沐曦 / Sunrise）

2.1 MLIR 昇騰 mlir-dialect ブランチで1日に tl.shl、tl.shr、tl.cast をマージ

MLIR 昇騰リポジトリのマージは mlir-dialect ブランチに落ち、main ではない。このブランチの HEAD は 11-18 に 06:23 から 08:47（UTC）へ進み、1日で3つの TLIR オペレータをマージした。

#211 は tl.shl を追加し、hivm.hir.vshl へ降載し、既存の NpuirShl ヘルパーを再利用する。#212 は tl.shr を追加し、i16、i32、i64 のみをサポートし、round はブール属性でデフォルト true。このコミットは既知の不一致を1点そのまま明記している：rhs はテンソルオペランドとしてモデル化されるが、HIVM の vshr には ScalarOnlyHWTrait<1> 制約がある。根本原因は NpuirShr と npuir_shr のコンストラクタがスカラーを受け付けないことで、後続課題として残される。

#214 tl.cast を追加し、round_mode は round、rint、floor、ceil、trunc、odd の六種に限定。このコミットはもう一箇所、方言レベルの設定も変更している。TL_Dialect に usePropertiesForAttributes = 0 を追加した。原因は tl.cast がこの方言で初めて非オペランド属性を持つオペレータであり、ODS デフォルトの Properties 生成を通すと破損した CastOp が生成されるため。三件のコミットはいずれも FileCheck テストを伴い、テストは実際にキャプチャした出力から取得している。

情報源：https://github.com/tile-ai/tilelang-mlir-ascend/pull/214。

2.2 MLIR 昇騰は審査中：tl.vrelu、tl.abs、tl.or、tl.xor と RoPE カーネル

審査中の TLIR オペレータはさらに四件ある。tl.vrelu は #261、tl.abs は #238 にあり、後者は hivm.hir.vabs に降載される。tl.or は #225、tl.xor は #228 にある。四件はいずれも「方言オペレータ + TIR 降載 + HIVM 変換」という同一の流れで進められている。

#263 は別の道をとり、単一オペレータを補うのではなく回転位置エンコーディングカーネルを直接追加している。別に #260 では harness 内の ascend-mfu スキルを ascend-roofline に置き換えている。新スキルは Cube/Vector モデル一式でピーク、カウント、roofline、MFU、BWU とハードウェア参考値を提示する。その FMA プローブは当該デバイスと当該ビルドの下で 26.3 TFLOPS に標定され、公称 30 TFLOPS の 88% にあたる。

情報源：https://github.com/tile-ai/tilelang-mlir-ascend/pull/263。

2.3 海光は単一コミットで十二項目の修正を集約、intrinsic、精度、整数ベクトルを網羅

海光リポジトリの調査期間内にマージされたのは一件のみ（#27）だが、内容は十二の方向を網羅している。intrinsic 側では hexp 呼び出しの曖昧性、cos と sin のディスパッチを修正。精度側では fp64 切り捨て失敗と __builtin_bit_cast のサイズ不一致を修正。ベクトルコード生成側では shuffle 降載を修正し、全波 shuffle リダクションを有効化した。

新規能力としては、hipRAND による rng 操作のサポート、バッファロードのリベース、cache_warmup intrinsic がある。ほかに若干の収尾として、8 ビット整数ベクトルブロードキャスト、実行期反復回数のパイプライン epilogue 展開、shuffle マスクガード、FP4 コード生成の順序修正がある。CI 側では NumPy ABI を固定。コミットの署名には海光のエンジニア二名が同時に現れている。

情報源：https://github.com/tile-ai/tilelang-hygon/pull/27。

2.4 Sunrise が 0.1.15+sunrise.1.2.1 をリリース；沐曦は v0.1.12+musa.5 を準備中

Sunrise リポジトリは #11 をマージし、バージョンを 0.1.15+sunrise.1.2.1 に進めた。当該コミットは TileLang、TileOPs、TileKernels の三上流ソースを同期更新し、TANG と PTPU 統合も更新している。タグページには同日このバージョンが現れ、前バージョンは 0.1.15+sunrise.1.2.0 であった。

沐曦リポジトリでは調査期間内に main へのコミットはない。動きはリリース準備にある。release/v0.1.12-musa.5-source ブランチが存在し、オープン中の #13 は v0.1.12+musa.5 ソースと MUSA ドキュメントのリリースに用いられる。摩尔線程側の主リポジトリには新規コミットはなく、調査期間内はコメントと PR 更新のみである。

情報源：https://github.com/tile-ai/tilelang-sunrise/pull/11。

2.5.1 四ソース巡検に変化なし、二路線の参照は前回と一致

3、エコシステムと採用側（TileOPs 目標リスト / TileKernels / topa / ドキュメントサイト）

3.1 mHC 二オペレータの退場を公開 API 破壊として掲載、HyperConnection 三オペレータが後を継ぎ審査中

#3021 MHCPreFwdOp と MHCPostFwdOp を削除し、カーネル、manifest エントリ、workload、ベンチマーク、テストと一緒に取り除き、#2796 の計画に従って実行する。DeepSeek-V4-Flash と GLM-5.3-Flash は HyperConnection の pre、post、head の三つのオペレータに切り替える。mhc.expansion という manifest プリミティブも併せて削除する。これは削除されたオペレータだけが使っていた。

このコミットは scripts/ci/api_compat_allow.txt にレビュー済みの公開 API 破壊として登録されている。オペレータライブラリがインターフェース削除をマニフェスト方式で管理するのは初めてであり、削除されたインターフェースは復元されない。

後を継ぐ三つの新提案はすでに審査中である：#3032 は pre を追加し、#3035 は post を追加し、#3039 は head を追加する。さらに #3036 は FusedTopKFwdOp に DeepSeek-V4-Flash の sqrt-softplus とハッシュルーティングを追加する。#3038 は DSADenseFwdOp に attention sink とインデックスのみの選択を追加する。この一群の変更は同じ一点を指している。DeepSeek-V4 の実際の構造に合わせて系列モデリングとアテンションのインターフェースを再編成することである。

情報源：https://github.com/tile-ai/TileOPs/pull/3021。

3.2 七件の性能目標 issue が「最速ライブラリとの差」を検収可能なチェックリストとして記述

調査期間内に新たに七件の性能目標 issue が開かれ、いずれもハードウェア、形状、目標を伴っている。#3018 は GQA 可変長がヘッド次元 72 の視覚行において FlashAttention 3 に後れを取る差を追跡する。#3019 は MLA cache 書き込みが vLLM に後れを取る差を追跡する。この二件に対応する修正はそれぞれ #3023 と #3022 であり、うち #3022 は当日 #3019 をクローズした。

#3037 は DSADense の完全な対照表を示す。H200 は 1500 MHz で動作し、bf16 稠密ピークは約 811 TFLOPS である。CSA の各行はピークの約 58% に達する。原因は、各ペアの softmax と次のペアの key 収集が二回の行列積の間に挟まっていることである。HCA の 4k 行は 64 key ブロックのコストを支払い、160 個の key を 192 個として計算する。

#3031 は HyperConnection pre が decode と中程度の系列において TileKernels に後れを取る差を追跡する。#3034 は GatedPoolCompress の decode 行を追跡し、目標はその形状において SOTA に達することである。

情報源：https://github.com/tile-ai/TileOPs/issues/3037。

3.3 TileKernels 対照計測提案：テスト実行イメージは依然 tilelang 0.1.12 に固定

#3028 は DeepSeek の TileKernels をベンチマーク対照に加え、DeepSeek-V4 の行を DeepSeek 自社カーネルで直接計測することを提案する。障害はバージョンにある。TileKernels は tilelang が 0.1.15 以上であることを要求するが、テスト実行イメージは 0.1.12 に固定されている。現在、それをインポートできるベンチマークは一つもない。

提案は三つの対応関係を示す。FP4QuantPerGroupFwdOp と FP8QuantPerTokenGroupFwdOp は per_token_cast に対応する。SiLUAndMulFwdOp は quant.swiglu_forward に対応する。検収条件は、これらのベンチマークが CI 内で実際に TileKernels を計測し、夜間記録によって対照として記録されることである。これは、同日の二件の量子化提案の説明において、TileKernels の数値がコメント内でしか示せない理由を説明している。

情報源：https://github.com/tile-ai/TileOPs/issues/3028。

3.4 topa は一コマンドで一巡のレビューを完走し、GPU は計測期間のみ独占

topa は #41 と #43 をマージし、レビューを循環可能なラウンドにした。#41 は各 PR 変更で新たな試行ラウンドをトリガーする。新しい head は完全なレビューを受け、それ以外は再チェックのみを行う。結果は PR が未変更かつオープンのままの場合にのみ公開される。GPU 側ではカード単位のロックを追加した topa-bench を新設し、計測期間のみ一枚のカードを独占し、それ以外の時間は他のラウンドに譲る。

#43 は三ステップのフローを一つの topa review <PR> に圧縮する。レビュー意見は三つの単文ポイントに固定される。問題、再現、修正方法である。同一 PR のレビューディレクトリは worktree と posted.json を保持し、二回目のレビューはローカルが GitHub より遅れている場合にのみ取得する。レビューラウンドの無変化待機は 60 分から 10 時間に緩和された。

この二件以外に、topa は調査期間内に新たに 10 件の issue（#35 から #46）を開いた。いずれも fix(...) タイトルを持つ実行可能な作業項目であり、方向は roofline 価格設定に集中している。CTA 単位のウェーブによる makespan の計算、書き込み行数による scatter の価格設定、常駐 CTA のグリッドへの算入を含む。これらはパイプラインが自らに課した次のバッチのタスクである。

情報源：https://github.com/tile-ai/topa/pull/41。

情報源：https://github.com/tile-ai/TileOPs.github.io/pull/88。

5. トレンド觀察

  • プラットフォーム境界の外延化：同じ日に Metal ターゲットと自動微分を着地させ、コンパイラは推論カーネルから訓練と Apple GPU へと伸びた。いずれも IR 層で止まっており、先にインターフェースを立て、後からバックエンドとランタイムを補う順序が明確である。
  • FP8 が納品期に入る：量子化、短行ストリーミング、paged decode、WGMMA の原語化が同日に着地し、いずれも vLLM、FlashInfer あるいは DeepSeek 自家実装を対照としている。性能検収は依然マージ基準とは独立しており、#3010 と #3005 の自己評価はいずれも検収ラインを下回っている。
  • 性能の負債は issue 単位の管理へ：新規に7件のターゲット issue を開き、ハードウェア、形状、目標倍率を明記。2件は起票当日に修正されクローズされ、リストが単なる負債の記録ではなく納品を駆動している。
  • 昇騰は二系統の速度差が現れる：メインリポジトリは本期テストと CI の締めくくりのみ、MLIR 路線は1日で TLIR オペレータを3つ追加。前者は収束しつつあり、後者は依然オペレータごとに道を敷く初期段階。
  • バックエンドのリリースが分岐し始める：Sunrise は既に 0.1.15+sunrise.1.2.1、沐曦は 0.1.12+musa.5 を準備中、海光はマージ型修正で追随。3社が各自リリースし、バージョン整合と互換マトリクスが新たな保守コストとなる。
