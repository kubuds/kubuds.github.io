今日の重点

この調査期間は合計9件のマージのみで、前回の21件の半分にも満たないが、構成は完全に変わっている。メインリポジトリへの貢献は3件で、テーマはCUDA命令レベルのプリミティブである。#3490 はL1およびL2プリフェッチ命令を6段階の追い出し優先度とともにグローバルロードテンプレートへ組み込み、#3605 は「NaN伝播の対称クランプ」を直接1条の min.NaN.xorsign.abs へと落とし込み、#3911 はPRラベル変更でトリガーされる全量CI再起動を収束させた。これら3件はいずれも特定のオペレータのスコアを上げるためのものではなく、kernel作者に利用可能な低レベルプリミティブとより効率的なフィードバックループを補完するものである。

第二の点は、TileOPsの4件がすべてDeltaNetにあり、しかもすべて同一の物理的制約を巡っていることである。SM89は101376バイトの共有メモリしか持たない。#2891 はフォワードにおいて、chunk 128、head次元128のとき、まずstate walkの出力パス（dim_v 64で114688、dim_v 128で131072が必要）が収まるかどうかを確認し、収まらない場合は98560バイトしか必要としないrecurrenceへ切り替える。#2890 は逆方向のw/uプログラムに reuse スイッチを追加し、等しいhead次元の下でS、du、Awが最後の読み取り後にdh、v_new、Auのバッファを引き継ぎ、114944を98560へと圧縮する。#2889 はSM90クラスタ下でのみ成立するLayerNorm splitのケースと、196608バイトを必須とする2つの線形注意力ケースを実情どおりにマークし、SM89上での失敗数を9件から3件へと減らした。3件を合わせて、完全な「予算—分流—テスト基準」の閉ループとなっている。

第三の点は、バージョンが依然として保留されていることである。#3887（0.1.16バージョン番号）は11-09 03:07以降まったく更新がなく、未マージのままで、tagの最新は依然として09-30のv0.1.15である。本当に記録に値するのは、#3911 でついでに言及された一箇所である。ROCm runnerのウォッチドッグがワークフローのタイムアウトを超えて引き上げられ、これまでAMD側のジョブは40分で打ち切られていた——これがAMD側のPRフィードバックが常にNVIDIAより一拍遅れる理由を説明している。

1. コアプロジェクトの進展

1.1 メインライン：CUDAにL2プリフェッチ命令と6段階の追い出し優先度を追加、非デフォルト優先度はSM80以上を要求（#3490）

#3490（6ファイル、+185/−1）は、これまで欠けていた3種類のプリフェッチ組み込み関数を補完した。L1プリフェッチ、uniform L1プリフェッチ、L2プリフェッチであり、同時に「追い出し優先度」を一級パラメータ EvictPriority とし、値はデフォルト、通常追い出し、優先追い出し、最終追い出し、変更なし、非割り当ての6段階を取る。グローバルロードテンプレートもこれに合わせて改造された。従来固定幅でハードコードされていたロードラッパーはテンプレート化APIに置き換えられ、非コヒーレント（non-coherent）ロード、L1追い出し優先度、およびL2プリフェッチのバイト数を指定できる。

動作境界は明確に記述されている。デフォルト優先度のL2プリフェッチは通常のグローバルまたはローカル命令を使用し、それ以外の優先度は evict_normal、evict_last にマッピングされ、計算能力8.0以上を要求する。この基準を下回るデバイスではこれらの組み合わせは成立しない。kernel作者にとっての意義は、これまで prefetch.global.L2::evict_last のような動作を得るには自分でインラインアセンブリを埋め込むしかなかったものが、今ではTileLangのソースコード内で宣言でき、コンパイラがターゲットアーキテクチャに応じて経路を選択する点にある。

情報源：https://github.com/tile-ai/tilelang/pull/3490

1.2 メインライン：NaN伝播の対称クランプを単一のmin.NaN.xorsign.absへ低減（#3605）

#3605（7ファイル、+203/−1）は T.clamp_symmetric(x, limit) を追加し、CUDA SM86 以降で FP16、BF16、FP32 の3種類のオペランドを一律に [-limit, limit] へクランプし、符号付きゼロと非正規数を保持する。いずれかのオペランドが NaN の場合は正規 NaN を返し、元の NaN の符号とペイロードは保持しない。非正の数値上限は API 契約の範囲外であり、既存の T.clamp は影響を受けない。

実装上は直接 min.NaN.xorsign.abs.* へ降下し、各スカラーまたは FP16/BF16 の各ペアごとに1回のクランプ命令を実行し、ベクトル入力は既存のベクトル化可能なオペレータ登録と CUDA パック発行経路を通り、実行時チェックを導入しない。検証基準は非常に厳格で、言語とコード生成の2套のテストは86件通過・2件スキップ。CUDA 13.1 下で SM86 と SM100 に対して SASS チェックを行い、FMNMX.NAN.XORSIGN、HMNMX2.NAN.XORSIGN、HMNMX2.BF16_V2.NAN.XORSIGN の3種類のスカラー形態とパック形態が期待どおり出現することを確認した。この種の変更の価値は数値安定性にある。量子化推論においてクランプが NaN を失うことはよくあるサイレントエラーの原因であり、セマンティクスを1つのハードウェア命令に委ねることで、NaN がこっそり境界値に変換されることがなくなる。

情報源：https://github.com/tile-ai/tilelang/pull/3605

1.3 メインライン：CI が PR ラベル変更で全量フローを再起動しなくなり、ROCm ウォッチドッグがワークフロータイムアウトの上へ（#3911）

#3911（1ファイル、+2/−2）はトリガ条件のみ変更するが、問題の説明は記録に値する。メイン CI は以前 labeled と unlabeled の2種類のイベントの両方でトリガされ、CodeRabbit が新規に開かれた PR に一度に複数のラベルを付けるため、同一の PR が数秒以内に複数回の完全に同一の全量 CI 実行を生成していた。共有並行グループがこれらの実行を順次キャンセルし、最後の1回だけを残していた。

実証は #3908 にあり、4つのラベルが同一タイムスタンプで付与され、4回の CI が生成され、元の実行と最初の3回の置換がすべてキャンセルされたが、いずれの CI ジョブも PR ラベルを読み取らず、これらの再起動は何らカバレッジを提供しなかった。修正方法はこれら2種類のイベントをトリガから削除し、opened、synchronize、reopened、ready_for_review と手動トリガを保持し、並行ポリシーが引き続き期限切れのヘッド更新のキャンセルを担当する。同一の変更で ROCm runner のウォッチドッグ閾値をワークフロータイムアウトの上に引き上げ、AMD ジョブが40分で強制終了されなくなった。

情報源：https://github.com/tile-ai/tilelang/pull/3911

2.1 昇騰：host-mapped バッファパラメータが審査中、14ファイルで529行追加（#3909）

#3909 は #3802 が CUDA 側で確立した明示的 host-mapped バッファ契約を昇騰へ拡張する。以前は Ascend kernel が一律に CPU テンソルパラメータを拒否し、そのストレージが NPU 上で可視であっても、呼び出し側はテンソル検証をオフにして回避するしかなかった。変更は同一の T.annotate_host_mapped_buffers(...) 3.1 TileOPs：33 から 40 トークンの W4A8 呼び出しが 40 トークンのデコードタイルに振り分けられ、表外グリッドで 4.3% から 11.3% 高速化（#2888）

#2888（2 ファイル、+69/−47）が修正するのは、ルール判定のずれである。132 SM の H200 上で、33 から 40 トークンの W4A8 呼び出しは、128 行タイル数が SM 数を超えると「133 から 225 タイル、K が 7168 / 7680 / 8192」の帯に入り、引き続き prefill 経路を通る。しかしこの種の呼び出しは本来 40 トークンのデコードタイルを通るべきである。

同日、Metaエンジニアリングブログが《How We Built TLX: A Hardware-Native GPU Compiler for Production ML at Scale》を公開した。内容はTriton Low-Level Extensionsについてであり、Tritonのブロック型プログラミングモデルの上に明示的なwarp-groupおよびclusterレベルの編成を補い、開発者がwarp特化、非同期転送、tensor memoryといった実行側のハードウェア能力をTritonの開発速度を犠牲にせず利用できるようにするものである。記事ではすでに本番稼働している3つの用途——推薦システム学習、推薦システム推論、大規模LLM事前学習——が示され、10か月間におけるMeta内部のカーネル数増加の図も掲載されている。Tritonカーネル数は約3.8倍、CUDAは約2.0倍に増加した。

5. トレンド観察

第一に、メインリポジトリの産出の重心がオペレータからプリミティブへ移っている。#3490のプリフェッチと追い出しの優先度、#3605のNaNクランプ、審査中の#3897 CPUスキャンオペレータと#3903プロセス並列コンパイルは、共通して「作者に新しい道具を渡す」ことであり、「あるオペレータを数ポイント速くする」ことではない。この種の変更は受け入れ基準も異なる。#3605はSASSにおける3命令の有無を証拠とし、#3490は計算能力のしきい値を境界とし、いずれも具体的な形状から切り離して再検証できる。下流にとってこれは、0.1.16以降に使える記述が増えることを意味するが、新しいプリミティブにはそれぞれアーキテクチャのしきい値があり、世代をまたぐ移植では1つずつ確認する必要がある。

第二に、共有メモリ予算が線形注意力のこの路線における明示的な制約となった。SM89 の 101376 バイトと需要側の 114688、131072、196608 という三つの数字が、chunk をどれだけ大きく取るか、walk で行くか recurrence で行くか、テストをどのアーキテクチャで走らせるかを決めている。#2890 と #2891 の解決アプローチは一致している。需要を無理に押さえつけるのではなく、dispatch にデバイスの事実に従って経路を選ばせ、さらに refusal の中で同じ境界を使い、起動時にクラッシュするより早めに拒否することを優先している。このパターンが DeltaNet 上でうまく回れば、GLA の一族もおそらくそのまま踏襲するだろう——#2889 が残した三つの chunk 32 の失敗は、まさに次の一片である。

第三に、テストの判定基準が「アーキテクチャごとにバツを付ける」から「デバイスの事実ごとに判定する」へと移りつつある。#2889 は SM89 のケースを削除したり永久 skip したりせず、まず check_held_launch を調べ、それからスキップを決めている。#2891、#2890 で新たに追加された二つのテストも、SM89 のデバイスの事実に基づいて分岐判断を検査しているため、SM90 の CI 上でもそのまま走る。このやり方は、デバイスの計算能力に応じて skipif マークを付けるより安定している。なぜなら、検証しているのはハードウェアではなく判断ロジックそのものだからだ。

第四に、TileFoundry の誤価格問題がオペレータ側から繰り返し突き返されている。#318 は、同じ挙動が既にクローズされた四つの issue で報告され、いずれも not planned とマークされたと明言し、#319 は一度に五つを挙げ、具体的な 962.1 対 1213.6 GFLOP の偏差を添えている。アナライザは TileLang の「まず価格を決めてからスケジューリングを選ぶ」路線の前提であり、価格が 26% ずれると自動選択が誤った決定を下す。この種のギャップは個々のオペレータを遅くすることはないが、自動化が境界的なグリッド上で体系的に選択を誤らせる。

第五に、RISC-V 側の分岐は収束せずむしろ拡大している。四つの情報源（TVM 路線、MLIR 路線、SOPHGO TPU、コミュニティインデックス）は整然と止まったままだが、第三者の Weft 路線は一日 40 件で、しかも既に差を単一オペレータまで定量化している（SG2044 の中央値 0.0580 倍）。二つの事実を併せて示すのは、停滞は誰もやっていないからではなく、公式の四情報源が「差を自動発見し、自動検証し、自動でキューに並べる」ループを形成できていないということだ——Weft の路線は自前でベンチマークエンジンを構築したからこそ回り始めた。もしこの 553 例のベンチマークが公式四情報源に受け入れ基準として参照されれば、RISC-V 側の進展は初めて比較可能な分母を持つことになる。
