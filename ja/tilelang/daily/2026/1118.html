今日の重点：TileOPs が 1 日で 12 件マージ、pilot モデルインターフェースが登録からオペレータ別の実現へ移行

11-17 のこの日、TileOPs のメインブランチには 12 件のマージが着地し、そのうち 7 件は TileFoundry ラウンドのオペレータ提案によるもので、方向性は前日と完全に連続している。11-16 に pilot モデル（Qwen3.6、DeepSeek-V4-Flash、GLM-5.3-Flash）が実際に呼び出すインターフェースを manifest に登録した後、11-17 からは形状ごとにカーネルを補完し始めた。当日新たにマージされたオペレータには、Embedding、Concat、「呼び出し側が cos/sin を与える」RoPE に加え、正規化のゼロ中心重みサポート、GQA 可変長注意の非標準ヘッド次元、GDN と因果畳み込みの状態スロット索引が含まれ、pilot モデルの推論チェーン上の索引、正規化、位置エンコーディング、注意、線形注意の 5 段をカバーしている。各提案には対照実装とベンチマーク行が付属しており、多くは自己評価が依然として「受け入れライン未満（below bar）」である。これはマージ基準と性能基準が別物であることを示している。まず意味的正しさとインターフェース整合性を確保し、その後ラウンドごとに性能を追い込む。もう 1 件追加された GEMM float32 出力（#3000）は、「ルーター、KV コンプレッサー、LM ヘッド」という 3 種類の狭い N 形状を bf16 から float32 累加出力へ拡張するもので、今回のインターフェース実現の中で唯一メインカーネル構造を直接変更したものである。同日新たに起票された目標 issue #2999 はネガティブリストを示している。スキャンした 53 形状のうち 5 つが依然として劣後しており、最悪の行は最速ライブラリのわずか 0.39 倍である。

情報源：https://github.com/tile-ai/TileOPs/pull/3000 、https://github.com/tile-ai/TileOPs/issues/2999

今日の重点：昇騰フロントエンドの同一人物が 5 件の dtype 監査 issue を連続投稿、約 300 のオペレータと dtype の組み合わせをカバー

11-17 20:13 からの 1 分間に、コントリビューター JeffDing はメインリポジトリへ昇騰フロントエンドの欠陥を 4 件連続投稿し（#4391 から #4394）、さらに 30 分後に 5 件目（#4395）を追加した。これは体系的な dtype カバレッジ監査を構成する。核心的な結論は、T.simd の単項・二項オペレータがコンパイラ内部呼び出しへ渡される前に dtype をまったく検証しないというものだ。CANN 9.2.1 の CCE ベクトルインターフェースは部分的なオーバーロードしか提供しておらず（例えば絶対値は 5 種類の整数と半精度、単精度のオーバーロードのみで bf16 はない。XOR は 2 種類の 32 ビット整数のみ）、フロントエンドは 225 の（オペレータ、dtype）組み合わせのうち 70 をそのまま通過させてしまう。その結果、コンパイル時に初めて破綻するか、あるいは静かに誤計算する。クロスレーンリダクション族も同様にホワイトリストを欠いており、63 の組み合わせのうち 27 が通過させられている。さらに具体的な 2 件として、T.simd.vcvt の part パラメータはデフォルト 0 で「偶数部分」に落ち、要素の半分しか変換しない。ドキュメントは 40 組の dtype ペアをサポートすると謳っているが、フロントエンドの実際の実装は 33 組である。5 件目は、6 つの T.ascend_* 同期プリミティブが T.SimdVF() 内で全滅することを指摘しており、うち 6 つのエラーメッセージはユーザーが呼び出した API にまったく言及していない。報告環境は昇騰 950PR（dav-3510）、CANN 9.2.1、openEuler 24.03 であり、新ハードウェアと新ツールチェーンの組み合わせ下でのフロントエンド品質問題に属する。5 件はいずれも再現手順と提案ラベル（bug、python、ascend、UX）を備えており、調査期間終了時点で依然としてオープン状態である。

情報源：https://github.com/tile-ai/tilelang/issues/4391 、https://github.com/tile-ai/tilelang/issues/4393 、https://github.com/tile-ai/tilelang/issues/4395

1. コアプロジェクトの進展

1.1 メインリポジトリが CuTeDSL の符号なしバッファ読み取りを修正：uint8 の 200 が -56 として扱われる

#3875 は、CuTeDSL ターゲット上で uint8 / uint16 / uint32 バッファから読み出された値が符号付き数として扱われる問題を修正する。根本原因は MLIR の整数に符号なしビットがないことであり、A.iterator.dtype は符号なしテンソルパラメータに対してすでに Int8 となっており、cute.recast_ptr と cute.make_tensor も同様に符号なし情報を失っている。要素型はテンソルラッパー層にのみ保持され、コード生成はグローバルメモリと共有メモリへの各アクセスをイテレータ型から開始している。著者は RTX PRO 6000 上で 256 個の uint8 値を使ってプローブした：Int32(x)、x > 127、x >> 7、x // 3 と 4 レーンのベクトルロードという 5 つの書き方で、メインブランチ上ではそれぞれ 128 個の値が誤っていた。修正方法は、tl.make_tensor と make_tensor_at_offset が dtype= を受け取り、型をビューへ再び紐付けるようにすることであり、コード生成は符号なしバッファの各ビューに対して明示的に cutlass.UintN を渡す。これ以前の #3764 はロード後に一度キャストを補うだけで、比較、除算、シフト、ベクトルロードをカバーできていなかった。

情報源：https://github.com/tile-ai/tilelang/pull/3875

1.2 メインリポジトリの昇騰ベンチマークがデバイス側 L2 フラッシュへ変更、一時バッファ読み取りの旧手法に代わる

#3891 昇騰ベンチマークの L2 追い出し方式を「一時バッファを1ブロック読み込む」から aclrtDeviceL2CacheFlush の呼び出しに変更し、各 NPU イベントまたは msprof サンプリングの前に実行する。旧方式のキャッシュ状態は置換ポリシーに依存し、異なるラウンド間で不一致になる可能性があり、それによってカーネルレイテンシの比較可能性に影響を与える。新方式では同期フラッシュを計時と実行時推定の外に置き、測定区間内のキャッシュ状態を確定させる。このインターフェースにはランタイムとデバイスのサポートが必要で、既存のテストスタブも同期して更新済み。著者は説明の中で本版でテストを再実行していないことをありのままに明記している。このコミットは 1.6 のベンチマーク計時改修と同方向である。両者とも「測定された数値」をより再現可能なものにしている。

情報源：https://github.com/tile-ai/tilelang/pull/3891

1.3 GEMM に float32 出力を追加、ルーター、コンプレッサー、LM ヘッドの3種類の狭い N 形状に対応

#3000 は GEMMFwdOp の出力型を float32 に設定する。すなわち bf16 または fp16 入力で float32 の累加和を計算し、TMA、狭バッチ Gemv、cp.async の3種類のカーネルがそれぞれ担当する。coop2_swap 構造を除き、すべての TMA 構造は float32 アキュムレータを直接転送する。coop2_swap の書き出し命令は16ビットのみをサポートするため、float32 出力を明確に拒否する。設定選択では4バイト出力に基づくタイル分割の推定を新たに追加し、23,040 のサンプル形状上で16ビット選択は変わらない。検証ではテンソルコアの累加限界を採用し、絶対誤差は 1e-4 と 2e-3 に（K/2048）の1.5乗を乗じたものの大きい方を取り、相対誤差は 1e-5 とする。ベンチマークは cuBLASLt、DeepGEMM、QuACK と比較し、FlagGems の行列乗算は float32 出力を持たないため、float32 行では比較から退出する。本コミットは #2927 の一部であり、翌日新規に起票された SOTA issue #2999 と同一の形状群を共有する。

情報源：https://github.com/tile-ai/TileOPs/pull/3000

1.4 オペレータライブラリの3つの新オペレータ：Embedding の再提出、Concat、カスタム cos/sin の RoPE

前日に誤ってマージされた後、当日に差し戻された Embedding は、今回正式なラウンドで再提出されマージされた：#2992 は EmbeddingFwdOp を新規追加し、int32 と int64 のインデックス、fp16/bf16/fp32/int32/int64 の5種類の重みテーブルをサポートする。カーネルは TileFoundry のタイル配置を採用する。すなわち1つの CTA が1つの行ブロック全体または幅広行の1列タイルを担当し、各スレッドは自身のベクトルを cp.async で共有メモリに落とし、L2 は evict-last ヒントを用い、その後ストリーミングで書き出す。max_norm パラメータはカーネル構築前に直接拒否され、重みがインプレースで書き換えられないことを保証する。#2987 は ConcatFwdOp を新規追加し、出力を「行×総列幅」と見なし、128スレッドの CTA で各スレッドが16バイトのベクトルを1つコピーする。行数と行幅は動的であり、1回のコンパイルで同一ベクトル幅と同一 dtype のすべての形状にサービスできる。#2988 は RoPECosSinFwdOp を新規追加し、呼び出し元が与えたトークンごとの cos/sin に従って回転を行う。NeoX とインターリーブの2種類の配置、部分回転、密とパック、単一オフセットまたは系列ごとのオフセット、ストライド付きビューへのインプレース書き込みをカバーする。同一コミットではさらに1つの通則を定めた：書き込まれるテンソル（出力または変更される入力）の2つの要素が同一アドレスに落ちる場合（拡張ビューなど）、すべてのオペレータは実行前に CheckError をスローしなければならない。3つのオペレータはいずれも torch と torch.compile に対して合格ラインに達し、自己評価はいずれも受け入れラインを下回る。

情報源：https://github.com/tile-ai/TileOPs/pull/2992 、https://github.com/tile-ai/TileOPs/pull/2987 、https://github.com/tile-ai/TileOPs/pull/2988

1.5 正規化、アテンション、線形アテンションの5項目：ゼロ中心重み、非規則ヘッド次元、状態スロットインデックス

正規化側では、#2986 により RMSNormFwdOp が Qwen3.6 の6つの「ゼロ中心重み」行（27B と 35B-A3B の prefill、decode、q-norm）をサポートし、FusedAddRMSNormFwdOp はそのうち4つをサポートする。3つのカーネル本体と融合体はいずれも重み乗算の箇所で float32 により 1+w を計算し、通常の重みでは生成されるコードがメインブランチとバイト単位で同一であり、flashinfer、vLLM、transformers、QuACK、FlagGems との比較で基準に到達している。アテンション側では、#2989 により可変長 GQA カーネルが SM90 上で自身のヘッド次元を8チャネルストライドで受け入れる：ヘッド次元 16、32、48、80、96、112 が汎用カーネルから warp 特化カーネルへ移行し、各グループは prefill、視覚、serving の形状でより高速になる。同時に Qwen3.6 視覚行を支える 72 ヘッド次元、16 グループの非因果形状をサポートし、テンソルのゼロ埋めを不要にする。線形アテンション側では、#2993 により GDNFwdOp が state_indices をサポートし（decode とパック prefill がプールスロットごとに各シーケンス状態を読み書きする）、CausalConv1dFwdOp は cache_indices を、その更新カーネルは conv_state_indices をサポートする。状態を保持する各カーネルはビルドフラグに従って自らスロットを引く。プールを持たないビルドではメインブランチと同じプログラムを生成し、値主順の GDN decode は2 warp 1組、各 lane が4つの16バイトベクトルを読む方式に変更される。#2995 は前のシーケンスを書き壊す欠陥を修正する：パック prefill の最終ブロック書き出しは「開始位置＋（反復数－1）×ブロック長」で位置決めし、反復数が0のときこの式は書き込み開始点を空シーケンスの64行前に落とし、未初期化の共有メモリで前のシーケンス末尾を上書きしてしまう。H200 上で長さ（2048、64、0）に64個の値ヘッドを組み合わせれば再現でき、修正方法は反復数が0より大きいときのみ最終ブロックを書き込むことである。#2990 は W4A16 decode のペア条件を厳格化する：ペアの K スライスが自身のリングバッファより長い場合、またはペアリングで K タイルを余分に追加しない場合にのみ2つの warpgroup を使用し、それ以外のケースでは単一 warpgroup のタイルを維持する。

出典：https://github.com/tile-ai/TileOPs/pull/2986 、https://github.com/tile-ai/TileOPs/pull/2989 、https://github.com/tile-ai/TileOPs/pull/2993

1.6 ベンチマーク計時を nvbench のコールド測定に変更、夜間スキャン予算を6時間から10時間へ拡大

#2985 は CUDA ベンチマークのサンプリング方式を書き換える：従来は各サンプルの呼び出し前に毎回ホストへ同期していたため、ホスト側の発行オーバーヘッドがデバイスの空転として現れていた。現在はブロッキングカーネルでストリームを占有し、1回の読み取りの全サンプルを連続してキューに投入し、各サンプルが個別にリセット、L2 フラッシュ、呼び出しを実行し、途中でホスト同期を行わない。これは NVIDIA nvbench のコールド測定の手法に倣ったもので、唯一の違いは「1回に1ブロック」を「1ブロックに複数サンプル」へ緩和した点である。各サンプルは0番 SM のクロックを周波数として記録し、行内では平均値を報告し、ダウンクロックによるサンプル破棄は行わない。キューに収まらないブロックはタイムアウトで無効となり、収容可能なサイズで再測定され、ブロックサイズは block_samples に記録される。準備方式も結果の l2_flush フィールドに書き込まれ、夜間履歴の口径を跨いだ比較を避ける。その代償は #2996 で定量化される：夜間スキャンの最新ラウンドは 20,259 秒実行されたところで6時間予算により打ち切られ、61個のベンチマークファイルのうち5個が未実行となり、Check benchmark coverage が失敗した。前回のオールグリーンと比較して、共有の 2,015 ケースの所要時間は 15,180 秒から 19,103 秒へ増加し（1.26倍）、新規 268 ケースがさらに 1,653 秒を消費した。修正方法は総予算を 21,600 秒から 36,000 秒へ、タスクタイムアウトを 380 分から 620 分へ引き上げることである。

出典：https://github.com/tile-ai/TileOPs/pull/2985 、https://github.com/tile-ai/TileOPs/pull/2996

1.7 審査中と目標：狭い N の prefill GEMM は最速ライブラリに仍未達で 0.39 倍の形状

新規の #2999 は GEMM の性能上の負債を明らかにした。H200、bf16 入力、K を 4096 に固定し、DeepSeek-V4-Flash のルーター、KV 圧縮器、LM ヘッドの幅で 1 から 8192 トークンまでスキャンしたところ、53 形状のうち 48 が最速ライブラリと同等以上、残り 5 が後れを取った。最悪なのは GLM-5.3-Flash のルーター形状（8192 × 288 × 4096）で、bf16 出力は 78.3 マイクロ秒対 30.6 マイクロ秒、わずか 0.39 倍、float32 出力は 0.38 倍で、選択されたのは 64 × 128 の基本タイルだった。その他の後れ行は 0.86 から 0.98 倍の間に分布している。同期間に審査中の性能系提案には、FP8 短行重みストリーミング（#3010）、W4A16 単一 warpgroup グループ帰約をクラスタペア経由に変更（#3009）、短 K の W4A8 decode で 1 CTA 1 行ブロック（#3005）、FP8 paged GQA decode のカーネル書き換え（#2997）がある。新規オペレータ側では MoE グループ GEMM の MXFP4 エキスパート重み（#3001）、KDA 状態スロットと値主順状態（#3002）、NSA 可変長アテンションのヘッド次元 256 と 4 キーブロック（#3004）が審査中である。

情報源：https://github.com/tile-ai/TileOPs/issues/2999 、https://github.com/tile-ai/TileOPs/pull/3010 、https://github.com/tile-ai/TileOPs/pull/2997
