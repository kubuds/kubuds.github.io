今日の注目：FlashQLA v0.1.4 リリース、デュアルカード CP をコンシューマー向け Blackwell に拡張

QwenLM/FlashQLA は 11-25 23:16 に v0.1.4 をリリース、リポジトリは現在 770 スター。これは採用側における本期間で最も完全なバージョン納品である。

リリースノートには三本の主線が挙げられている。第一はパーティション横断修正の精度パスで、FP32 と三回繰り返しの TF32x3 をサポートし、実行時に wave 感知のヒューリスティックで選択される。カード間の h0 と dht の折り畳みは、スロットマッピング経由で集約済みの (h, M) バッファを直接読み込むよう変更され、アンパックと再インデックスの実体化を行わなくなった。

第二は SM120 と SM121 上のデュアルカード CP で、フォワードとバックワードの両方でカード間とカード内の組み合わせをカバーする。実装は新規の aggregate_card_state と aggregate_m によって完成された。

第三は ZigZag カード間 CP レイアウトである。r 番目の rank が各ドキュメントの r 番目のブロックと 2·cp−1−r 番目のブロックを担当し、attention 層の分割位置と整合し、TileLang kernel の改変を要求しない。

その他の変更はエンジニアリング寄りである。KKT 求解は 8×8 対角ブロック代入に変更され、FP16 MMA と FP32 再帰を統合し、FlashInfer のブロック状逆行列計算に基づいて独立に書き直された。flash_qla.warmup() はすべての静的パラメータ組み合わせを JIT キャッシュに事前コンパイルできる。CP インターフェース build_cp_context はデフォルトでカード間とカード内を有効化し、zigzag= を受け付ける。

修正項目の一つは、前回のデイリーレポートの SM120 の手がかりとつながっている。block_DV=64 と一箇所の __threadfence_block が、nvcc による g_exp_shared のバリア外への昇格を防いでいる。逆方向バリアは今、まず dV 書き込みをコミットし、その後で K に dqkv_shared を再利用させる。

ベンチマークは三档のハードウェアをカバーする。シングルカードは H200、GB200、RTX 5090。デュアルカード CP は H200×8、GB200×4、RTX 5090×2。リリースには別途、Auto-CP と Dual-CP の技術レポートが添付されている。

情報源： https://github.com/QwenLM/FlashQLA/releases/tag/v0.1.4。

今日の重点：ナイトリー Wheel が 0.1.16 に切り替わり、バージョン文字列の改変が二件のリグレッションを引き起こす

tilelang-nightly の調査期間内に二つの Wheel が出た。11-25 13:18 のビルドは v0.1.16+d20261125.git3684ae6a、22:30 のビルドは v0.1.16+d20261125.gitfa93ba14。前日はまだ v0.1.15+d20261124 だった。

これは 11-24 にマージされたバージョン番号がすでにパッケージングチェーンに入っていることを示す。GitHub タグの最新は依然 v0.1.15、Releases の最新も依然 9-30 の v0.1.15、PyPI 上の tilelang も 0.1.15 である。したがって正確には、ビルド側はすでに 0.1.16 に達しているが、リリースはまだ完了していない。

バージョン文字列の形式も同時に変更された。旧形式は 0.1.15+cuda.d20260125.githash、新形式は 0.1.16+githash であり、dYYYYMMDD の日付セグメントは現れなくなった。

改変は二件のリグレッションを引き起こし、いずれも 11-25 17:26 前後に報告された。環境はソースビルド a3a4f9ce である。

#4513 は build_date() が dev バージョンに対して静かに None を返すと報告している。この関数の正規表現は [+.]d(\d{8}) であり、日付セグメントに依存している。新旧両形式のパース自体はどちらも正しく、問題は実際の成果物に日付セグメントがすでに含まれていないことにある。

#4514 は昇騰 NPU 上で do_bench が必ずクラッシュすると報告している。エラーは aclrtDeviceL2CacheFlush failed: 207000。profiler の NPU パスが cache バッファを cache_numel=0 の空プレースホルダに変更した後、_flush_cache が無条件に aclrtDeviceL2CacheFlush(None) を呼び出す。dav-3510 と CANN 9.2.1 上でこの呼び出しは失敗する。両 issue ともすでに 4 件の議論がある。

情報源： https://github.com/tile-ai/tilelang/issues/4513。

今日の重点：メインリポジトリの三件はすべてキャッシュサブシステム、キャッシュキーにツールチェーンバージョンを含める

メインリポジトリの調査期間内には三件のコミットのみで、二件がキャッシュを直接変更している。これは前幾日の ROCm 一括修正、昇騰欠陥報告とは明らかな分担を成している。

#4511 は現在の CUDA と昇騰ツールチェーンのバージョンを kernel キャッシュキーに含め、20 ファイルを変更する。新たに tilelang/contrib/bisheng.py を追加し、pto_toolchain.py は相応にスリム化された。BackendModule に toolchain_stamp コールバックを追加し、ゼロ引数呼び出しを許可する。CUDA コンパイラ選択は _cuda_compiler_module に折り込まれた。

変更の動機はキャッシュ無効化の境界である。従来はコンパイラを交換したり CANN バージョンを交換した後でも、古いバイナリがキャッシュにヒットする可能性があった。テスト側では同時に昇騰バイナリキャッシュ、PTO キャッシュ、JIT 診断の三箇所のケースを補った。

#3756 は共有キャッシュの権限を扱う。キャッシュエントリはまず一時的に置かれ、その後ディレクトリ全体をリネームして公開されるため、作成プロセスの umask を引き継ぐ。SGID とグループ書き込み可能な共有キャッシュルート上では、umask 077 のプロセスが 0700 と 0600 のエントリを発行し、他のユーザーは読めなくなる。

修正法は公開前に一時エントリを legalize することである。キャッシュルートに SGID がある場合、ディレクトリを 0o2755 に、ファイルを 0o644 に変更し実行ビットを保持する。SGID のないルート、およびこのビットをサポートしないファイルシステムでは、そのまま維持する。このコミットは 148 行の権限リグレッションテストを追加し、共有キャッシュディレクトリの初期化とマルチルート検索も修正した。

併せて審査中のコミットがもう一件ある。#4512 はツールチェーン識別子による実行可能キャッシュのキー化と題し、#4511 と同一テーマに属する。

情報源： https://github.com/tile-ai/tilelang/pull/4511。

1. コアプロジェクトの進展

1.1 キャッシュキーに CUDA と昇騰ツールチェーンバージョンを含め、ツールチェーン間の再利用を遮断

#4511 は LeiWang1999 により 23:09 にマージされ、本期唯一の機能的変更である。提案説明は四段階で進む：まずアクティブなツールチェーンにより CUDA と昇騰 JIT kernel をキー化し、次にツールチェーン認識を CUDA に限定し、続いて昇騰ツールチェーンも含め、最後に各バックエンドのツールチェーン印记を統一する。

構造上は新たに BackendModule.toolchain_stamp フックを追加する。CUDA 側は tilelang/cuda/backend.py がバージョン文字列を提供し、昇騰側は tilelang/ascend/backend.py が提供する。両者とも contrib 下のアダプタ層を経由するように変更された。

テスト側は六つのファイルを変更した。三種類のキャッシュ用例に加え、host-mapped 出力検証テストも調整した。このテストは kernel キャッシュを明示的に無効化する。

情報源： https://github.com/tile-ai/tilelang/pull/4511。

1.2 共有キャッシュが SGID によりグループ読み取り可能なエントリを公開、umask 077 でもプライベートディレクトリを生成しない

#3756 は KellyFrog により 16:18 にマージされ、kernel_cache.py と新しいテストファイル一つを変更した。提案は問題を公開方式に帰因している。ステージング後にディレクトリ全体をリネームし、権限は umask に由来するため、共有ルートの SGID 意図と一致しない。

判定条件はキャッシュルートに SGID が付いているかどうかのみを見る。付いていればディレクトリは 0o2755、ファイルは 0o644 となり、実行ビットは保持される。付いていなければ変更せず、Windows などこのビットをサポートしないファイルシステムをカバーする。

テストは共有ルートとプライベートルートの二つのケースをカバーする。非 POSIX システムと POSIX 権限をサポートしないファイルシステムではスキップされる。

情報源： https://github.com/tile-ai/tilelang/pull/3756。

1.3 CUDA アテンションサンプルテストを並列化、CI 単一ジョブ時間を短縮

#4485 は block causal attention のサンプル用例を並列実行に変更し、Z3 にバジェットを追加した。3 ファイルを変更し、ci.yml 一行を含む。

提案は途中で一度 DeepSeek TopK の Z3 バジェット上書きを撤回し、その後 z3 制限を復元した。前日の #4463 と #4489 も同じ TopK 用例群のソルバー所要時間を巡るもので、本期のこの一件はテスト所要時間の締めくくりに属する。

情報源： https://github.com/tile-ai/tilelang/pull/4485。

1.4 ナイトリーホイールを 0.1.16 に改標、build_date() が dev バージョンで None を返す

二つのナイトリーホイールはいずれも 0.1.16 に基づく。22:30 のものはコミット fa93ba14 に対応し、本期 #4485 のマージ点である。13:18 のものは 3684ae6a に対応し、調査期間起点後の最初の一件に属する。

#4513 は tilelang.build_date() が 0.1.16+gita3a4f9ce 上で None を返すことを指摘している。

解析側は旧形式と新形式のいずれも正しく処理する。旧形式 0.1.7.post3+cuda.d20260127.gita17230e4 は 20260127 を解析できる。手動で構築した新形式も同様である。ただ実際の dev 成果物だけがうまくいかない。

これは公開 API のサイレントリグレッションであり、ビルドと実行には影響しないが、ビルド日付に依存する診断や再現スクリプトを無効化する。

情報源： https://github.com/tile-ai/tilelang/issues/4513。

2. マルチバックエンド適配（昇騰 / 海光 / 摩尔線程 / 沐曦）

2.1 昇騰サブリポジトリが bitwise_xor に dtype 事前検証を追加、クラッシュを ValueError に変更

#1986 は 15:24 に ascendc_pto ブランチへマージされ、6 ファイルを変更した。提案は #1722 に関連し、サポートされない入力がコンパイラに入る前に拒否されることを目標とする。

フロントエンドは dst、src0、src1 の三つのオペランドを検査する。int8、uint8、int16、uint16、int32、uint32 を許可し、浮動小数点と 64 ビット整数を拒否する。判定はスカラー要素型に基づいて行い、ベクトル化 dtype と互換である。

lowering 段階でもう一度検査し、公開 API を迂回して intrinsic を直接構築する経路をカバーする。int32 と uint32 は PTO A5 かつ tl.ascend_memory_planning が無効な場合にのみ許可される。

デバイス側計算実装と workspace 割り当ては変更されていない。テスト側は XOR の tmp 契約を合法な int16 バッファで行い、既存の workspace スロットとレイアウト断言を保持する。

情報源： https://github.com/tile-ai/tilelang-ascend/pull/1986。

2.2 gemm_v0 に fp32 テストマトリクスを追加、catlass 精度ギャップを補填

#2032 は 11:16 にマージされ、8 ファイルを変更した。提案はこれが #1396 と #1921 が露呈したギャップを補うものだと明記している。gemm_v0 のテストマトリクスは以前 fp16 にハードコードされており、古い catlass fp32 の誤値コピーがこれまで検出されていなかった。

新增用例は歴史的に意味のある各分岐形状について修正後の振る舞いを固定する。これは 2.1 と同じパターンである。まずギャップを再現可能なマトリクスに変え、それから性能を論じる。

情報源： https://github.com/tile-ai/tilelang-ascend/pull/2032。

2.3 昇騰デイリーテスト 3132 項すべて通過、新規欠陥は低層プリミティブに集中

#2036 は 11-25 10:48 のデイリーテストを記録している。3132 項すべて通過。前日は 3120 項だった。

新規 issue はより低層のプリミティブへ移行している。T.fmod は昇騰上に下降実装がなく、Unresolved call ir.Op tirx.fmod を報告する。同じ問題が六回報告され、番号は #4501 から #4506 である。

T.SimtVF 関連が三件、番号 #4507 から #4509 で、いずれもクロスレーンの fragment 累積が誤解を招く VF スコープチェックを引き起こすもの。#4510 は T.gemm を T.SimtVF 内に置くと黙って受け入れられ、その後 bisheng によって難解なアドレス空間エラーで拒否されることを報告している。

さらにコンパイル単位レベルの欠陥が一件ある。#4500 は、単一の PTODSL コンパイル単位に二つ以上の kernel が含まれる場合、各オブジェクトファイルが同名の init_core__ptodsl_<hash>.vector を定義し、ld.lld が fatobj リンク段階で重複シンボルを報告することを報告している。

情報源： https://github.com/tile-ai/tilelang/issues/4500。

2.4 海光、摩尔線程、沐曦の主ブランチにコミットなし、それぞれ一件が審査中

三つのバックエンドリポジトリの主ブランチは調査期間内に新規コミットなし。

海光には審査中のものが一件：#46 は非同期コピー GEMM の LDS 再利用ハザードを修正。摩尔線程には審査中のものが一件：#13 は v0.1.12+musa.5 ソースと MUSA ドキュメントをリリース。沐曦には新しい PR 更新なし。

前回マージされた海光 FP8 スケーリング GEMM 修正（#45）は、依然として同リポジトリの最新メインラインコミットである。

情報源： https://github.com/tile-ai/tilelang-hygon/pull/46。

2.5 MLIR 昇騰が tl.ln 下降と評価ナレッジベースの二件をマージ、いずれも master にはない

二件のマージはいずれも master にはなく、リポジトリごとにデフォルトブランチで取得すると漏れる。

#250 は 15:48 に mlir-dialect ブランチへマージされ、9 ファイルを変更。新たに TL_UnaryOp 基底クラスと TL_LnOp を追加し、verifyElementwiseUnary 検証を備え、ConvertUnary テンプレートを追加して TL 単項オペレータを HIVM へ変換する。前回この件はまだ審査中であった。

3、エコシステムと採用側（TileOPs オペレータライブラリ / FlashQLA / TileFoundry）

3.1 TileOPs 九件、DeepSeek-V4-Flash の二件のモデルレベル性能

TileOPs は調査期間内に 9 件マージされ、二件がモデル側の呼び出し方法を直接変更している。

#3171 は DeepSeek-V4-Flash の indexer ReLU を非インプレースに変更。ReLUFwdOp(inplace=True) は結果を新しいバッファへ書き込んでから入力へコピーし戻すが、同モデルは返されるスコアを読むだけである。このコピー書き戻しは 4096 token プリフィル、ratio-4 層において 537 MB のスコアに対する一回分の余分な読み書きを伴う。

#3170 は4種類のインデックステンソルを各 Step で1回だけ計算し、最初にそれを読み取る層が担当するようにした。4種類とは、top-k読み取りのclosed-entryカウントとゼロ先頭項、全closed層の完全なkey index、そしてデコードステップのringスロットである。ウィンドウ型はint32で、インデックス層は層ごとに再計算しなくなった。

情報源： https://github.com/tile-ai/TileOPs/pull/3171。

3.2 デコードステップをCUDA graphの再実行に変更、昨日の作業項目を当日実装

#3168 は15:00にマージされ、10ファイルを変更した。CausalLM.forward は現在2つのモデルに同時にサービスを提供する。モデルは今回の呼び出しのインデックスメタデータと転送本体を提供する。

cuda_graph はデフォルトで有効。デコードステップはCUDAデバイス上で _run のグラフを再実行し、tokenバッファと Step.moved_to をその場で書き換える。各フェーズの最初のステップはまず即時実行し、その後モデル自身のストリーム上でキャプチャする。

これは前号で新規に開かれた作業項目 #3155 の実装そのものである。審査中の #3175 は、2つのモデルの各デコードオペレータがCUDA Graphキャプチャ資格テストに合格することを要求している。

情報源： https://github.com/tile-ai/TileOPs/pull/3168。

3.3 foundry五件：INT8 tileを192幅に拡張、量子化とサンプリングで各1件の空回りを修正

五件は foundry をプレフィックスとし、いずれもオペレータレベルのチューニングに属する。

#3162 はINT8 64行GEMMのtileテーブルに80、112、192の3段階を追加した。192幅はdense WGMMA helperではなく T.wgmma_gemm を使用する。48、144、176、208、224、240は引き続き除外され、実測で毎回選択されるたびにより遅くなる。

#3163 はFP8原地グループ量子化の最終ブロックが実際に存在する行のみをロードするようにした。単一ブロック起動時、例えばDeepSeek-V4-Flashの1行7グループのKVでは、冗長なロードによりカーネルが64〜96ナノ秒余計にかかる。

#3164 は16ビットconcat入力を共有メモリ経由でfloat32に拡張し、16バイト読み取りと全行書き込みを使用する。#3166 は分割されたtop-p行ビニングをブロック内の各スレッドに折りたたむ。#3167 は16ビットisinfを1回で2つのlaneを処理するようにし、ブロックサイズは1024スレッド。

#3169 はさらにRoPEリファレンス実装におけるゼロtokenのヘッド数計算を修正した。

情報源： https://github.com/tile-ai/TileOPs/pull/3162。

3.4 TileFoundry、Qwen3訓練ステップのASTRA-simエクスポート例をマージ

前号ではこの項目はまだ審査中であり、今号でマージされた。これによりTileFoundryの検証範囲は単一オペレータから訓練ステップレベルに拡大する。

情報源： https://github.com/tile-ai/TileFoundry/pull/366。

5. トレンド観察

  • キャッシュが実装詳細からファーストクラスシチズンへと変わりつつある。1 日のうちにそれを巡る 3 件：キャッシュキーはツールチェーンを認識し、共有キャッシュは権限を認識し、審査中のものはツールチェーン身分に基づいて実行可能キャッシュのキーを作る。マルチユーザービルドとマルチツールチェーンの併存が駆動要因。

  • 0.1.16 のリリース経路はすでにビルド側まで敷設済み。ナイトリーホイールは先に 0.1.16 へ改標され、タグと PyPI は依然 0.1.15 で停止。バージョン文字列から backend タグを除去した後、旧形式に依存する 2 箇所のコードが当日にリグレッションを報告し、形式変更の互換範囲が予想より広いことを示した。

  • 昇騰の欠陥構成が変化している。前日は 10 件の「受け入れるべきでない入力が受け入れられた」だったが、本期は T.fmod の下降欠如、SimtVF スコープの誤判定、PTODSL のマルチカーネルシンボル衝突。問題はインターフェース契約からコンパイル・リンク層へと沈下し、単条の修正コストが上昇。

  • TileOPs の最適化はカーネル内部だけでなく、モデル呼び出し方式に落ち始めている。ReLU を非インプレースに変更、インデックステンソルを各ステップで 1 回だけ計算、デコードステップ全体を CUDA graph で処理、の三者はいずれもスケジューリングとコピーを削減しており、単核算力の向上ではない。

  • 採用側のペースが加速している。FlashQLA は 1 日のうちに v0.1.4 のコード、ベンチマーク、ドキュメント、技術レポートを完了し、TileFoundry は検証面をトレーニングステップレベルまで押し上げた。TileLang の下流はもはやカーネルを書くだけでなく、システムレベルのサンプルも書き始めている。

  • RISC-V 側は連続 3 調査期間ゼロ変化。TVM 路線と MLIR 路線はいずれも原位で停止し、インデックスページにも新規 PR なし。
