今日の重点

本調査期間に26件がマージされた（tilelang 9、TileOPs 9、tilelang-ascend 5、TileFoundry 2、tilelang-hygon 1）。新規リリースはない。三つの系統が同時に進行している。メインリポジトリは一日の大半のマージをコンパイラの正確性に充てており（ベクトル化ループの下限、共有メモリのクロススレッド WAW、MMA tile の K アトム、fragment reduce の保留次元、TIR 述語のビット幅昇格への追従）、これは「サイレントエラー」の一掃であり機能拡張ではない。昇騰側では5件のマージすべてが訓練側と再帰オペレータ（DSA スパース微調整の逆伝播、SiTU-GLU の逆伝播、LSTM、GRU）に落ち、さらに2.1万行の PTO ベクトル化フレームワークがレビュー中で、PTO は AscendC に次ぐ第二の実行パスになりつつある。TileOPs は SM90 でページド GQA フォワード、FP8 lightning indexer、MLA デコードという3つの foundry オペレータを同日に warp 特化プログラムへと換装し、併せてテンソルコア性能上限の校正基準をオペランド集合エンベロープに変更して、夜間バッチ実行における105%の偽超過を修正した。

1. コアプロジェクトの進展

1.1 メインリポジトリ：ベクトル化解析に非ゼロループ下限を導入（#3579）

10-21 00:27 にマージ、10ファイル +818/-198。#2819 の guard 修正を引き継ぎ、同時に #2669、#2616 の2件の問題をクローズ。従来の実装は f(i) と f(floor(i / W) * W) を比較して各式が各ベクトルグループ内で同値かどうかを判定しており、これはループが0から始まることを暗黙に仮定していた。ループ下限が非ゼロの場合、unit-step ベクトル化は異なるレーンのアドレスを同一グループとして計算してしまい、ブロードキャストロードやグループ全体での共有条件の証明が無効になる。新しい判定ではループの最小値を解析に取り込み、混合精度変換の移送時にネストした guard を保持する。数値結果をサイレントに変えてしまうコンパイラの欠陥である。

出典：https://github.com/tile-ai/tilelang/pull/3579

1.2 メインリポジトリ：共有メモリのクロススレッド WAW 検出（#2821）

10-20 23:41 にマージ、3ファイル +153/-19、#2698 を修正。共有メモリ上の S[tx] と S[tx + 10] は単一スレッドにとっては2つのアドレスだが、異なるスレッドの書き込みは重なり得る。従来の WAW 検査は2回のアクセスで同一のスレッド変数を再利用していたため、判定漏れやバリア挿入漏れが生じていた。修正方法は、同一イテレーションの WAW では2つの異なるスレッドインスタンスを用い、それぞれの Bind 定義をリネームし、既存の RAW/WAR モデルを再利用する。ループキャリーの WAW は従来の処理を維持する。テストは「挿入すべき」と「挿入すべきでない」の両方の情形をカバーし、guarded 書き込み、Bind 派生インデックス、非交差パーティション、threadIdx.y/z の置換を含み、スレッド同期と issue の両スイートで95項目が通過した。

出典：https://github.com/tile-ai/tilelang/pull/2821

1.3 メインリポジトリ：未対応の MMA tile 要求に明示的な K パディングを（#2818）

10-20 16:41 にマージ、5ファイル +57/-14、#2715 を修正。汎用 MMA emitter はオペランドレイアウトを構築する前に K アトムをひそかに縮小することがあり、FP16 K=8 では誤った結果が算出される。K=20、K=28 のような不規則なサイズでは共有メモリレイアウト推論の段階で直接失敗し、しかもヒントが不明瞭だった。現在は emitter 初期化時にアーキテクチャ固定の K アトムに基づいて tile の K を検証し、割り切れなければ ValueError をスローする。入力 dtype、必要な整除関係、推奨パディング値（例：SM80 の FP16 K=20 ではアトム16を報告し、K=32 まで補い余剰要素をゼロ埋めするよう提案）を伴う。

出典：https://github.com/tile-ai/tilelang/pull/2818

1.4 メインリポジトリ：fragment reduce が保留次元ターゲットをサポート（#2815）

10-20 16:35 にマージ、8ファイル +343/-63、#2530 を修正。T.reduce_sum などが (64, 64) を dim=1 に沿って (64, 1) へ縮約する際にコンパイル時にクラッシュしていた（Check failed: vars.size() == InputDim() (2 vs. 1)）。一方 reduce_op.py のドキュメント契約は [X, Y] と [X, 1, Y] の両方の出力形状を受け入れることを明記し、対応する期待形状も構築済みであるため、これは誤用ではなくバックエンドの欠落である。修正は両方の lowering パスを同時に通し、保留次元ターゲットなしの従来動作も維持する。

出典：https://github.com/tile-ai/tilelang/pull/2815

1.5 メインリポジトリ：TIR 述語が整数ビット幅の昇格に伴い同期的に書き換え（#3550）

10-20 09:59 にマージ、4 ファイル +950/-27。整数インデックスがより広いビット幅に昇格された後も、制御バッファアクセスの境界チェックは旧ビット幅のまま計算されるため、理論上は範囲外アクセスを見逃す可能性がある。新たに IndexPredicateRewriter を追加し、ConfigIndexBitwidth と FlattenBuffer で各アクセスの昇格情報を記録し、アクセス文の処理完了後に関連する guard を書き換える。マッチングは等価な加算・乗算形式に限定し、無関係な条件、データ値式、固定幅境界は保持する。インデックス昇格、guard 書き換え、アクセススコープ、ベクトル端点、競合昇格の 5 種類のテストを新規追加。

出典：https://github.com/tile-ai/tilelang/pull/3550

1.6 メインリポジトリ：CuTeDSL scan の参加スレッドオフセット補完（#3576）

10-20 12:49 にマージ、2 ファイル +30/-6。共有メモリ scan lowering は #3536 で参加スレッドオフセットを導入したが、CuTeDSL 側の helper は依然として旧構築パラメータで呼び出しを生成しており、tl.CumSum1D(32, False, 0).run(...) は直接構築パラメータエラーを報告する。同時に失效した codegen アサーションも #2815 の 2 回の CUDA CI 失敗の原因である。修正方法は、1 次元・2 次元 cumsum/cummax helper にオプションの thread_offset（デフォルト 0 で互換性維持）を追加し、参加 lane と warp を選択する前にオフセットを減算し、CUDA 専用テストに requires_cuda を付与する。

出典：https://github.com/tile-ai/tilelang/pull/3576

1.7 メインリポジトリ CI：性能回帰タスクを H100 に固定（#3569）

10-20 16:00 にマージ、1 ファイル +15/-1。PR 回帰ボットは kernel ごとにレイテンシとベースラインを比較するが、数値はベースライン収集時と同じ型番のカード上でのみ意味を持つ。組織はセルフホストの H20 容量機種を通常の正確性 CI に導入しており、そのラベルセットは既存の [self-hosted, nvidia] と重複するため、区別しないとベンチマークタスクを静かに引き継いでしまう。H20 の FP16 稠密演算性能は約 148 TFLOPS で、H100 の約 990 TFLOPS と約 7 倍の差があり、FP64 パスも大幅に削減されているため、すべてのベンチマークが存在しない回帰を報告することになる。現在、pr-regression タスクには h100 ラベルが必須であり、作業開始前に割り当てられたカードが確かに H100 であることを検証し、ラベルが誤っていれば誤解を招く数値を公開するのではなく即座に失敗する。

出典：https://github.com/tile-ai/tilelang/pull/3569

2. マルチバックエンド対応（昇騰 / 沐曦 / 海光 / 摩尔線程）

2.1 昇騰メインリポジトリ：L0 ローカルコピーの明示的 pitch 対応（#3511）

10-20 14:16 にマージ、24 ファイル +1458/-187 で、本調査期間の昇騰方向で最大の変更。従来、1 つの GEMM tile は単一の L1→L0A/L0B コピーでのみ填充でき、非ゼロのターゲット原点は拒否され、各コピーは自分の領域からコンパクト pitch を推測していたため、別々に搬送された 2 つの半分を結合してターゲットの全体ブロックにすることができなかった。MajorK/MajorMN 転置ロードも制限されていた。新たに昇騰専用パラメータ T.copy(..., l0_pitch=...) を追加し、fractal ブロックごとに L0 pitch を指定し、呼び出し側がコンシューマ GEMM のコンパクト pitch（動的テールブロックを含む）を指定する。このパラメータを省略するとコンパクト領域の元の動作を維持する。例では 64 行の A tile の両半分に l0_pitch=4 を書き込む。同時にアライメント後のターゲットオフセット lowering、物理境界と転置グループの検証、割り当てとバッファバージョン間隔を処理する。

出典：https://github.com/tile-ai/tilelang/pull/3511

2.2 昇騰メインリポジトリ CI：単一 check 内でのビルドとテストの分離（#3564）

10-20 12:06 にマージ、1 ファイル +61/-9。Ascend のビルドとテスト結果を同じ Test for Ascend PR チェックに収め、ステップごとに失敗段階を提示し、workflow summary に各段階の結論を列挙する。CANN 環境は一度だけ構築し、ビルドも一度だけ行い、AscendC サンプル、PTO サンプル、Ascend 単体テストを同一 job の 3 つのステップとしてそれぞれ実行する。ビルドが成功しワークフローがキャンセルされていない場合、あるスイートが失敗しても残りのスイートを続行し、最終的には全体として失敗と判定する。CANN 変数は GITHUB_ENV 経由で渡す。

出典：https://github.com/tile-ai/tilelang/pull/3564

2.3 昇騰リポジトリ：DSA スパース微調整逆方向オペレータ indexer_bwd（#1887）

10-20 15:26 にマージ、2 ファイル +1294。Ascend NPU 向けに indexer_bwd を追加し、DSA スパース微調整にサービスを提供、同時に AscendC と PTO の 2 バックエンドをサポート。オペレータは lightning-indexer KL 微調整損失の dIndexQ、dWeights、dIndexK に対する勾配を計算し、可変長パックシーケンスをサポート。実装は 3 段階に分かれる：持続化 GEMM の高速 kernel は連続および共有行インデックスレイアウト向けで、パイプラインとより少ない転送を備える；汎用 kernel は任意のインデックスレイアウトをサポートし、-1 不正インデックスの勾配累積を含む；さらに精度変換を処理する cast kernel を設ける。

ソース：https://github.com/tile-ai/tilelang-ascend/pull/1887

2.4 昇騰リポジトリ：SiTU-GLU 逆方向オペレータ（#1877）

10-20 15:22 にマージ、5 ファイル +854。セマンティクスは CANN ops-nn の aclnnSituGluGrad に整合し、Kimi K3 Stable LatentMoE のゲート付き活性化逆方向に用いる：t = tanh(gate / beta)、s = sigmoid(gate)、situ_a = beta * t * s、上流分岐は linear_beta が正か否かで tanh または直通を通し、grad_gate と grad_up を出力。精度基準は独立実装の fp64 PyTorch リファレンスであり、910B3 上で公式 aclnn とクロスチェックし、最大相対誤差は約 3e-3 で、bf16 の丸め期待に適合する。

5. トレンド観察

コンパイラの正確性が今調査期間の主線となっており、機能拡張ではない。 メインリポジトリの9件のマージのうち5件はサイレントエラーの整理である：ベクトル化がループのゼロ起点を仮定（#3579）、共有メモリの WAW 見落とし（#2821）、MMA emitter が K 原子をサイレントに縮小（#2818）、fragment reduce の保留次元クラッシュ（#2815）、インデックスのビット幅拡張後に述語が追従しない（#3550）。これらの欠陥に共通するのは、エラーを報告せず、誤った結果やバリア漏れだけを生じる点であり、ユーザーが本番で最も特定しにくい類に属する。同日 TileOPs の #2661 も「性能上限の基準」を修正しており、プロジェクトが「数値の信頼性」を「速く動くこと」と同レベルのエンジニアリング目標と見なしていることを示す。

昇腾ラインはサンプル補完から訓練側へ移行。 5件のマージのうち3件は逆方向または再帰オペレータ（indexer_bwd、situ_glu_grad、LSTM/GRU）であり、situ_glu_grad は Kimi K3 Stable LatentMoE のゲート活性化に直接整合し、910B3 上で aclnn とのクロス検証データを提示している。#3577 による DeepGEMM-Ascend の設定選択と epilogue の整合と合わせ、昇腾側の対象範囲は推論フォワードから訓練バックワード、状態再帰、大規模モデル MoE ゲートへと拡大しつつある。

PTO は AscendC に次ぐ第2の実行パスになりつつある。 審査中の #3512 は 2.1 万行のベクトル化フレームワーク（T.Parallel → PTO VMI、ターゲットは Ascend 950）であり、#3516 は tvm_ffi を pto ターゲットのデフォルト実行バックエンドに設定する予定で、さらに #3530、#3573、#3581、#3582 というコピーと述語の修正群を加えると、PTO ラインの工数は明らかに単発パッチの量級を超えている。メインリポジトリは同時に #3511 で AscendC 側の L0 ローカルコピー機能を補完しており、2つのパスは置き換え関係ではなく並行して推進されている。

ツールチェーンが独立リポジトリへ溢出。 1日のうちに3つの新規リポジトリ（中国語チュートリアル、CANN コミュニティオペレータリポジトリ、Hexagon バックエンド実験）と1セットの VS Code 拡張が出現し、メインリポジトリはさらに lower trace 全体を devkit へ移行した（#3583、4390行削除）。コミュニティ側の拡張速度はすでにメインリポジトリのモジュール分割よりも速く、これは7月の「マルチバックエンド言語方言」リファクタリングの方向と一致している。すなわち、メインリポジトリはセマンティクスと IR に収斂し、ツールとバックエンド実験は外部化される。

CI 口径の明示化は留意に値する。 #3569 は性能回帰を H100 に固定し誤ラベルのカードに対して即座に失敗させ、これにより Ascend のビルドとテストを同一 check の段階に分割し、#2661 はオペランド集合の包絡でテンソルコア上限を再ラベル付けする。3件はいずれも「数値を比較可能にする」ものであり、後続 PR の参入障壁に直接影響する。
