1. コアプロジェクトの進展

1.1 メインリポジトリ：昇騰面で4箇所を収筆——独立 AIV 実行（#3485）、PTO DeepGEMM codegen（#3330）、クロス warp allreduce 修正（#3494）、サンプルターゲット選択（#3474）（10-14）

日付：2026-10-14　情報源：独立 AIV（#3485）／ PTO codegen（#3330）／ allreduce 修正（#3494）／ サンプルターゲット選択（#3474）

  • 独立 AIV 実行（#3485）：Ascend AutoSchedule を拡張し、AIV0 と AIV1 が sid 依存の制御フロー下で異なる作業を実行できるようにした——交互エピローグ、逆量子化とエピローグの分業、互いに素な入力パーティション、ループ内でのロール切り替えをサポート。実装上は AssignCore を遅延推定とスケジューリングの前に前倒しし、AIV ローカル UB バッファとスカラー状態に独立したアイデンティティを確立し、参加コアごとにパイプラインリソース、特殊レジスタ依存、UB 容量、同期フラグライブラリをモデリングした。統一カーネルの collective パスと 1/2 AIV 発射ジオメトリは保持。L0C→UB コピーは依然として AIC 上で実行される。
  • PTO DeepGEMM codegen（#3330）：制御フローを跨いで tl.ascend_set_mmad_direction を追跡し、有効な方向を MAD 命令にエンコードし、競合する方向下で到達可能な MAD を拒否する。SIMD 後のインクリメンタルロード（データと更新ポインタを同時に返す）、混合 AIC/AIV カーネルにおける UB アドレスから PTODSL ポインタへの変換、動的な L0C→UB 次元とストライド、int16 符号付きパック MX scale をサポート。条件式とランタイムループのコード生成を改善。報告によると 15 個の DeepGEMM PTO ユースケースのうち 14 個が通過し、test_bf16_m_grouped_padding は PTOAS VPTO バックエンドが FP32→BF16 変換を合法化できないため依然としてブロックされている。
  • クロス warp allreduce 修正（#3494）：1 つの cross-warp allreduce 呼び出しが複数の独立したリダクショングループをカバーする場合、ascend と pto ターゲットが誤って最初のグループの結果をすべてのグループに渡していた。本コミットでこの正確性の問題を修正（#3469 のフォローアップ）。
  • サンプルターゲット選択（#3474）：昇騰サンプルとテストでハードコードされた target="ascend" を削除し、TILELANG_DEFAULT_TARGET 環境変数で決定するように変更。DeepGEMM JIT エントリは execution_backend="auto" をサポート。CI は昇騰サンプルスイートを ascend と pto の 2 つのターゲットでそれぞれ 1 回ずつ実行し、ドキュメントに選択方法を明記。

1.2 メインリポジトリ：基盤 3 件——CPU OpenMP 並列 grid ループ（#3109）、C 系 codegen 共有発射（#3289）、Windows NVCC を MSVC に変更（#3510）（10-14）

日付：2026-10-14　情報源：CPU OpenMP（#3109）／ codegen 共有（#3289）／ Windows MSVC（#3510）

  • CPU OpenMP 並列（#3109）：CPU バックエンドにオプションの grid ループ OpenMP 並列を追加——新たに MaterializeCPUParallelGrid を追加し、アノテーション付き CPU grid ループを並列ループに変換。ループ collapse、スレッド数設定、最小 trip 数しきい値、割り当てのシンクを併せて整備。Linux / macOS / Windows の OpenMP コンパイルフラグと pass 設定項目を補完。テストは正確性、pragma、割り当てシンク、しきい値、1 次元ケースをカバー。CPU バックエンドが初めてグリッドレベルの並列能力を備えた。
  • C 系 codegen 共有（#3289）：CodeGenTileLangCBase を導入し、CUDA、HIP、CPU C、Ascend C++、Metal、C ホストコード生成を統一。T.import_source、T.Kernel(prelude=...)、pragma_import_c がソーステキストの末尾に改行がないかバックスラッシュで終わる場合に次の生成行を飲み込む問題を修正。インポート内容を「ヘッダファイル→インポート→生成宣言と関数」の順にソートし、2 つの区切り改行を保証。検証：フォーカス回帰 83 通過、関連 codegen と launch スイート 405 通過。
  • Windows NVCC を MSVC に変更（#3510）：NVCC が get_cplus_compiler() の選ぶ clang-cl を拒否——NVCC サブプロセス環境から cl.exe を選択するように変更（ホスト C++ コンパイラ選択は変更しない）。VS 2026 18/* フォールバックパスを補完し、非 Windows プラットフォームでは -ccbin=None を渡さない。CUDA 13.3 下で再現用例は修正前失敗、修正後コンパイル通過。

1.3 メインリポジトリ：ROCm scan 波面修正（#2326）、テスト基盤キャッシュ（#3502）、ガバナンス設定（#3513）（10-14）

日付：2026-10-14　出典：ROCm scan（#2326）／ テスト基盤（#3502）／ CodeRabbit ラベル（#3513）

  • ROCm scan 波面修正（#2326）：HIP の cumsum / cummax はデフォルトで 64 lane セグメント単位で実行されるため、Wave32 GPU 上では結果が誤っていた——既存の run エントリがターゲットの波面幅に応じてセグメント幅を選択するようにし（ブロックスレッド数の上限に制約される）、32 スレッドブロックではコンパイル時に 64 lane テンプレートを除外する。32 スレッドの前方/後方スキャンと、ソース/デスティネーションのストライドが異なるケースのカバレッジを追加。gfx950 MXFP4 の例とテストは {"kind": "hip", "mcpu": "gfx950"} ターゲット記法に変更。検証：CUDA scan スイートは B300 上で 17 件通過、CuTeDSL ソース生成テストは 2 件通過。AMD 側のランタイム検証は ROCm CI に委ねる。
  • テスト基盤キャッシュ（#3502）：直近にクエリした IR 本体の呼び出しデータをキャッシュし、collect_calls / assert_call_count で使用できるようにする。変換テストにおける再帰 visitor と生成スクリプトのテキストチェックを構造化 IR アサーションに置き換え、ソフトパイプライン、スケジューリング、同期、バリア、Hopper intrinsic の構造チェックを拡張。
  • ガバナンス設定（#3513）：CodeRabbit による PR と issue の自動ラベル付けを有効化（PR 13 ラベル、issue 14 ラベル）。11 件のレビュールーティングルールをすべて保持し、ラベルの追加/改名/削除は行わない。

2.2 昇腾：3 件のファクトチェックロールバックと再作成（#1888 から #1890、#1893）；サンプルとオペレータを新規 3 件開設（10-14）

日付：2026-10-14　情報源：ロールバック #1888／ ロールバック #1889／ ロールバック #1890／ 再作成版（#1893）／ 昇腾 PR リスト

  • 3 件のロールバック（#1888 / #1889 / #1890）：前調査期間にマージされた 3 件の「ドキュメントファクトチェック」PR——round セマンティクス（#1612）、bitwise_rshift（#1676）、bitwise_xor（#1681）——が順次ロールバックされた。再作成版 #1893 が原因を説明：毎日の全量スイートで低優先度ケースを実行した際、想定失敗ケースの異常正規表現が不一致であることを発見（実際にスローされたのは AscendVectorInstructionSelection の InternalError であり、アサートされた "Compilation Failed" ではなかった）；これらのケースは low_priority とマークされており、PR 段階の CI（-m "not (low_priority or ci_skip)"）では実行されないため、マージ後に毎日の全量実行がセーフティネットとして発見した。
  • 再作成版（#1893）：bitwise_rshift の再作成——レビュー意見に従い全ての想定失敗ケースを削除（サポート表外の dtype はドキュメントの dtype サポート表でカバーし、想定失敗アサートでは行わない）、docstring の書き直しと実機テストを維持。round と bitwise_xor の 2 件の再作成版はまだコミットされていない。

3.1 TileOPs：foundry 性能バッチ 11 件を収束——softmax / プーリング / 正規化 / リダクションを全面的に展開（10-14）

日付：2026-10-14　情報源：softmax（#2570）／ プーリング3件（#2572 / #2573 / #2579）／ 正規化3件（#2576 / #2581 / #2585）／ リダクション2件（#2571 / #2578）／ GEMM と Elementwise 2件（#2582 / #2577）

3.2 TileOPs：線形注意と MoE 4件——KDA プレフィル逆行列、GLA 逆方向メモリ、エキスパートサーチスキップ、permute の境界収束（10-14）

日付：2026-10-14　出典：KDA プレフィル（#2584）／ GLA 逆方向（#2569）／ MoE 探索スキップ（#2575）／ permute 境界収束（#2559）

  • KDA プレフィル逆行列安定化（#2584）：相関キー（correlated keys）下で KDA プレフィルがエラー——main は 6 個の chunk ケースと 2 個の fused ケースで失敗（NaN 含む）；修正は 16 行の対角ブロック単位で FP32 下で求解し、既存の共有バッファを再利用してブロック積を実行、ゲーティングプレフィックスは FP32 レジスタに保持、共有メタデータは参照行のみ保存、TileLang 0.1.12 下で境界を越える混合 dtype 共有ビューを削除；chunk と fused プレフィルは逆行列ヘルパーを共用、4 個の回帰ケースを追加（2 種の半精度 × 2 経路 × 部分 chunk）。sm89 ベンチマーク（FLA 0.5.2 外部ベースライン対比）は出力と終態すべて FP64 対照を通過。

5.3 夜間基盤 +41：テストがマージに同期して膨張

  • 正確性は単日 +41 項目で直近一週間で最大の伸び幅であり、TileOPs の 16 件のマージと一対一で対応している（性能バッチは一般的に test-node の追加項目を伴い、注意力拡張は新しい負荷行を伴う）。「1 件マージするごとに、基盤が一段上がる」というローリング記帳は、各変更の検証を夜間スナップショットへと沈殿させ続けている——リリース前の静的な準備は依然として着実に積み上がっている。

5.4 昇騰リポジトリのロールバック規律：低優先度のケースも守られている

  • 最初の 3 件の「ドキュメント・ファクトチェック」PR は、低優先度の想定失敗ケースにおける異常な正規表現不一致により全体がロールバックされ、削減版で再做された——露呈したのは「PR 段階の CI では低優先度ケースを実行せず、毎日の全量スイートが受け止める」という二段階の検証構造である。この「ロールバック—再做」であって「傷を負ったまま前進」ではないという処理は、昇騰適配リポジトリの CI ガバナンスが「全部通過」から「アサーションの正確さ、口径の統一」へと転換しつつあることを示しており、調査期間内のマージ品質が毎日の全量実行によって継続的に制約されていることも意味している。
