TileLang ウィークリーレポート (2026-11-16 ~ 2026-11-20)

2026-11-20 Kubuds

レポート期間：2026年11月16日（月）から11月20日（金）まで、5営業日、5期のデイリーレポート。さらに公開日（11月21日）に tile-ai 組織の30リポジトリに対する168時間の補完チェックを実施

第1部 · サマリー

本節は今週の要点を抽出したもので、既定は800字以内（今期701字）。完全な項目、逐次リスト、情報源は第2部のアーカイブを参照。

今週5期のデイリーレポートでは合計141件のマージ、新規 issue 467件を記録した。TileOPs が84件を占め、メインリポジトリはわずか12件で、うち4件はランタイム修正である。

  • セキュリティインシデント：11-15 上流の昇騰リポジトリの CI に外部 PR がスクリプトを注入し、コントリビューターの token が盗用された。4つのリポジトリに同スタイルの PR が現れ、すべてクローズされ未マージで、開示は issue #2016 を参照。
  • TileOPs が主戦場に：5期のマージは15、18、12、23、16件。manifest が宣言的パラメータにアップグレードされた後、pilot モデルのオペレータが日単位で実現し、Embedding の誤マージは当日ロールバック、翌日に再提出しマージされた。
  • 監査のパイプライン化：11-16 期の72時間で新規 issue 406件、2アカウントが314件を貢献。その後4期は19、15、20、7件で、レビュー待ちキューは一時102件まで積み上がった。
  • 昇騰はファミリー単位で着地：DSA と KDA がそれぞれ3点セットを同日マージ、catlass は v2.2.0 に昇格し fp32 GEMM のサイレント NaN を修正。11-17 にはさらに約300組み合わせの dtype 監査を追加。
  • 性能改善はセレクタルールへ：#3045 の1ルールが302形状をカバーし、286件が1.03から2.6倍高速化。TopKSelect と MLA cache の2件の未払いは当日クローズ。
  • プラットフォームの外延化：TileFoundry は同日に Metal ターゲットと自動微分を実装したが、いずれも IR 層で停止。別に303ファイルの用語とレイアウトのリファクタリングが1回。
  • RISC-V は交互に推進：TVM 路線は hikari ブランチを新規開設し5件、MLIR 路線は buddy-opt のデフォルト化と2つのサンプルをマージ。11-18 から3期にわたり静穏。

今週の判断：主戦場はすでに2つの調査期間連続でオペレータライブラリにあり、ボトルネックは開発量からレビュー帯域へ移った。自動 warp specialization のバリア計装が第一級リスクとなり、v0.1.15 は51日間停止しており、すべての変更が次の tag の外で滞留している。

第2部 · アーカイブ

以下は今週の完全な本文であり、構造・基準は過去のウィークリーレポートと同一。サマリー内の各判断はここで逐条の根拠と情報源を見つけられる。

素材出所：本誌の毎日の TileLang コミュニティ動向5期（11-16、11-17、11-18、11-19、11-20）。11-16 期は週末をまたぐ72時間の調査期間（11-13 07:00 から11-16 07:00）。残り4期は24時間で首尾相接続する。したがって5期の行動事実の区間は11-13 07:00 から11-20 07:00。前回のウィークリーレポートは11-13 07:00 で締めており、本期の起点はそれと接続する。公開日には別途 tile-ai 組織の168時間チェックを実施（30リポジトリ、期間内に12件をプッシュ）。このチェックはプッシュとバージョン状態の確認のみに用い、デイリーレポートで記録済みの事実は変更しない。

編纂説明：今週の要聞、核心プロジェクト進展、マルチバックエンド適配、エコシステムと採用側、コミュニティ教程とイベント、趨勢観察、付録の7次元で構成。マージ数、レビュー待ち数、新規 issue 数は各期デイリーレポートの GitHub 検索真値（is:merged、is:open、created）から取得し、リポジトリ別のメインブランチコミットとクロスチェックした。5期のマージは順に30、30、20、38、23件、合計141件。新規 issue は順に406、19、15、20、7件、合計467件。非デフォルトブランチのマージは逐次ブランチを明記し、デフォルトブランチとは混算しない。関与した非デフォルトブランチは hygon distributed、mlir-ascend mlir-dialect と harness。別に TileOPs stats と nightly snapshots。

ランタイムと実行パス

  • デバイス状態の復元（#3872、11-16 マージ）：tvm_ffi ホスト stub は現在のデバイスを設定するだけで、復元しない。cuda:0 上で cuda:1 のテンソルを呼び出すと、結果は正しいが現在のデバイスが cuda:1 に残ってしまう。その後の device="cuda" による割り当てが暗黙的にドリフトする。修正方法は、アダプタ層で torch.cuda.device(...) を使って呼び出しを包み、終了時に復元することである。
  • NVRTC 単一引数カーネル（#3880、11-16 マージ）：引数名と型を ", " で結合していた。単一引数の場合、結合結果はタプルにならず、cuLaunchKernelEx が直接 TypeError を投げる。末尾カンマ付きのタプルリテラルに変更すればよい。
  • cython 動的共有メモリ（#3882、11-16 マージ）：動的共有メモリの上限は従来 init() で一度だけ設定されていた。この属性はデバイスごとに異なる。48 KB を超える必要があるカーネルは、他のデバイス上で cudaErrorInvalidValue を報告する。修正方法は、カーネルごとに _set_dynamic_smem() ヘルパー関数を生成し、昇格済みのデバイスを記録することである。
  • ROCm HIP ランタイムの再利用（#3899、11-16 マージ）：PyTorch の ROCm wheel は RTLD_LOCAL で libamdhip64 をロードするため、stub はそれを見つけられない。修正方法は、まず RTLD_NOLOAD で既にマップされたランタイムを検出することである。これにより、dlopen で 2 つ目のコピーが生成され、モジュールハンドルがランタイムをまたぐことで最初の kernel 起動が失敗するのを避けられる。
  • 符号なしバッファ読み取り（#3875、11-17 マージ）：CuTeDSL ターゲット上で、uint8、uint16、uint32 バッファから読み出した値が符号付き数として扱われていた。根本原因は MLIR 整数に符号なしビットがないことであり、コード生成はグローバルメモリと共有メモリへの各アクセスをイテレータ型から出発させていた。著者は RTX PRO 6000 上で 256 個の uint8 値を使ってプローブした。5 種類の記述はいずれもメインブランチ上でそれぞれ 128 個の値を誤った。修正方法は、tl.make_tensor が dtype= を受け入れるようにし、型をビューに再び紐付けることである。
  • レイアウトプレースホルダ変数のシリアライズをまたいだバインディング維持（#4410、11-20 マージ）：tl.Layout、tl.Fragment、tl.PartialFragment はプロセス内シングルトン tirx::Var プレースホルダでインデックスとスレッドマッピングを表現する。判断根拠はオブジェクト同一性であり、name_hint ではない。レイアウトが pickle や tvm.ir.save_json を往復すると、プレースホルダが再構築される。その結果、map_forward_index([7]) は [_i] を返し、OutputShape() は (32,) を (_i + 1,) と計算する。spawn で生成された worker 内でアノテーション付き PrimFunc を降載すると、「forward map must be injective」で失敗する。修正方法は、バインドされたプレースホルダ Var 参照を同じ ObjectGraphSerializer チャネルに組み込むことである。
  • CUDA Tile IR バックエンド RFC の再提出（#4402、#4403、11-19）：目標は TileLang プログラムから CUDA Tile IR を生成し、tileiras にコンパイルとスケジューリングを委ねることである。レイアウト、パイプライン、warp 特化、命令選択はすべて tileiras が決定する。バックエンドは Tile IR が正しく表現できるセマンティクスのみを変換する。変換できない場合は直接コンパイルエラーを報告してそのプログラムを拒否し、既存の CUDA バックエンドとの完全な互換性は追求しない。この版は以前の #3247 のやり直しである。レビューでは、旧実装は try-catch が多すぎ、約 1.85 万行の Python で pass を書いていたと指摘されていた。

6. トレンド観察

第一に、主戦場はすでにコンパイラ本体からオペレータライブラリとスケジューラへ移っており、この移動は 2 つの期間で連続して成立している。今週の 141 件のマージのうち、TileOPs が 84 件を占め、メインリポジトリはわずか 12 件。メインリポジトリの 12 件のうち、4 件はランタイム bugfix、2 件はバージョンとドキュメント。先週の状況も類似している。メインリポジトリの作業はリグレッション修正に集中し、新規能力はより多くオペレータライブラリのタイル、セレクタ、コストモデルの形で現れている。判断根拠はマージ数だけでなく依存方向にもある。TileOPs の性能結論は TileFoundry の roofline とスケジューリングを引用する必要があるが、メインリポジトリは今週それらに何も新しいものを提供していない。

第二に、監査はすでにパイプライン化され、ボトルネックは「発見」から「レビュー」へ移った。11-16 期は 72 時間で 406 件の issue が新規作成され、2 アカウントが 314 件を貢献。cn-sys の 172 件は 1 時間 46 分で書き終えられた。ilovexsir の 142 件は 5 つの batch 修正 PR に直接対応する。このパターンは確かに「欠陥発見から修正まで」の周期を圧縮し、同日に issue と PR が併存している。しかしそれは負荷をレビュー側へ移している。11-16 期はレビュー中 102 件、マージ 30 件。うち 22 件の mlir-ascend 同構 PR はごく少数の人しか通せない。次段階のボトルネックは発見速度ではなく、レビュー帯域になるだろう。

第三に、セキュリティ境界が今週唯一避けられないネガティブな事件となり、露呈したのは構造的な問題である。自建 CI が外部 PR に貫通され、個人 token が盗用された。四つのリポジトリで同時に同じスタイルの PR が出現した。これは「新規コントリビューターの PR が直接自建サーバーの CI をトリガーする」というデフォルト設定が組織レベルで共有されたリスク面であることを示している。作者の対応は、旧認証の取り消し、悪意ある fork の証拠保全、自建 CI サーバーのセキュリティ処理である。推奨される修正は、新規コントリビューターの PR はメンテナーの承認後にトリガーされるようにすることだ。この点は RISC-V と AI コンパイルコミュニティ全体にも同様に当てはまる。自建 runner の信頼境界はデフォルトで厳しくすべきであり、リポジトリごとに個別判断すべきではない。

第四に、自動 warp specialization の正確性が一等リスクとなっている。#2896 から #2901 のこの連鎖は一つのことを示している。パフォーマンス変更が同期責任をコンパイラの自動計装に委ねる時、計装位置が正確性の一部となる。そしてそれは上位層に対して不透明である。同じ cache key で二回コンパイルすると、バリアが分岐内に落ちることもあれば分岐外に落ちることもある。さらに CI の永続化カーネルキャッシュが重なると、偶発的な悪い計装が固定的な失敗として固化される。この問題には現在構造的な解決策はなく、「書き込み操作を条件分岐の外に移動する」といった局所的な回避しかない。今後さらに多くのタイルが ping-pong を採用すれば、同種のハングが再発する可能性が高い。

第五に、プラットフォーム境界は外へ拡大しているが、いずれも IR 層で止まっている。同じ日に Metal ターゲットと自動微分が着地し、コンパイラは推論カーネルから訓練と Apple GPU へと伸びている。いずれも実行可能なカーネルを生成しない。順序は明確で、まずインターフェースを定め、後からバックエンドとランタイムを補う。同じ週に TileFoundry は 303 ファイルで用語とレイアウトアルゴリズムを単一の仕様に収束させた。これは中間表現を「実装の中から生えてくるもの」から「まず定義し、それから実装する」へと変えることに相当する。この種の変更は短期的にはレビューコストを増やすが、長期的には IR が外部バックエンドによって正確に実装できるかを決定する。

第六に、バージョンが長期間リリースされないことが、今週すべての進展に共通する出口の問題である。v0.1.15 は 09-30 で止まり、今週金曜日で既に 51 日である。メインリポジトリのランタイム修正、昇騰の実行バックエンド変更、TileOPs のオペレータ補完は、早くとも次の tag を待たなければ下流の配布パッケージに入らない。これと対照的に、独立ディストリビューションはすでに先へ進んでいる。Sunrise は 0.1.15+sunrise.1.2.1 を出し、沐曦は v0.1.12+musa.5 を準備し、海光はマージ型修正で追随している。三者がそれぞれリリースするため、バージョン整合と互換性マトリクスが新たなメンテナンスコストとなる。

第七に、RISC-V 四源は今週二支流がそれぞれ一回ずつ進展し、ペースは依然として不連続である。TVM 路線は新たに hikari ブランチを開き、K3 移植検証と RVV グリッドデータを示した。MLIR 路線は buddy-opt のデフォルト化と二つのサンプルをマージした。コミュニティインデックスページは初めて TVM 側の fork を収録した。しかし 11-18 から三期すべてが静默している。二つの路線の分業はすでに明確である。TVM 路線は「動作し、実測データがある」ことを進めている。MLIR 路線は「設計があり、サンプルがある」段階で止まっている。この線は調査期間ごとに追う価値はあるが、週単位で進捗を計算するのは適切ではない。
