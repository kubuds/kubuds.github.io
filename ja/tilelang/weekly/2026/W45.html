TileLang ウィークリーレポート (2026-11-02 ~ 2026-11-06)

2026-11-06 Kubuds

レポート期間：2026年11月2日（月）から11月6日（金）まで、計5営業日 素材情報源：本誌の毎日TileLangコミュニティ動態デイリーレポート5期（11-02、11-03、11-04、11-05、11-06）。5期の収集ウィンドウは端から端まで連続しており、合計で10-30 07:00から11-06 07:00までの168時間をカバーする（月曜日の分は72時間ウィンドウで前週末をカバー、火曜日から金曜日までは24時間）。前回のウィークリーレポート（10-26から10-30）とは重複しない。なお、tile-ai組織の各リポジトリに対する168時間ウィンドウの補足調査、各リポジトリのリリースページとタグ、TileLang×RISC-Vの4情報源巡回再確認を別途実施した（詳細は付録を参照）

1. 今週の主要ニュース

  • 昇騰950の永続化FlashMLAカーネルを直接メインラインに書き込み、別リポジトリへの移植ではなくコンパイラがスケジューリング可能な記述方式を採用（11-02マージ、#3678）：1件の変更で1997行追加、17行削除、20ファイル、42コミットに及び、BF16 prefillとコンパクトFP8 decodeの2経路をカバーし、オプションのFP8およびFP4追加KVキャッシュ、attention sink、不正インデックス、queryごとの独立長をサポートする。アテンションループ、オンラインsoftmax、逆量子化、スケジューリングはすべてTileLangで表現し、T.Stageによってコンパイラにバッファバージョンと同期を管理させる。QKとPVはL0Bストレージリングの同一領域を異なるlayoutビューとして共有し、L1の配置はT.annotate_buffer_addressesで直接指定する。prefillは1つのアキュムレータ割り当て内で4つの互いに素な出力スライスに分割し、正規化が1スライス完了するごとに1スライスを排出する。この記述方式を成立させるため、コンパイラ側では同時期に3つの機能を補った：L0CからUBへのコピーでNZ出力を保持する、各AIVストリームを自身のパイプラインより前に選択する、明示的スケジューリングされたステージが物理発行フェーズで同一の場合にソースコード順序を維持する。対象形状は非常に狭く定義されている：ヘッド数64、DqkとDvはいずれも512、topkは64の倍数。情報源：https://github.com/tile-ai/tilelang/pull/3678

  • ThreadSyncを週に3回改修、まず移行のために道を譲り、その後性能と証明を補う（11-01、11-04、11-05）：月曜日の#3733は3週間前にマージされた正確なスレッドカウント（#3291）を丸ごとロールバックした。理由は率直に書かれている——その変更は高コストなカウントクエリをフルブロックフェンスチェックの前に移動させ、すべてのスレッドがフェンスに到達する場合でも証明を実行する必要があり、TVMの求解予算を使い果たして部分カウントを返し、正当なremapおよびsequence補助kernelが「Cannot prove a thread rectangle」でコンパイル失敗する。商ガード、正確な参加スレッド境界、非矩形スレッド集合という3種類の正当性改善も併せて撤回され、#3732は移行後の再最適化のためのトラッキングチケットとして残された。木曜日の#3761はロールバックに派生した副作用を処理する：#3643の名前付きバリア重複番号を修正するため、同一グループのスレッドはスコープを跨いでもIDを再利用できなくなり、TileKernelsのmhc_pre_big_fuseカーネルはブロックあたり96スレッドのため、2段階のcp.asyncパイプライン上で余分に1つのIDを取得し、コンパイル生成物が宣言するバリアリソースが4から5に増え、B300上で隠れ次元1280のバリア占有上限が16ブロック/SMから12ブロック/SMに低下した。修正方法はThreadSyncが順序付きスコープリストを受け入れるようにし、スコープを跨いでIDを共有する前に新しいアナライザで参加述語が恒成立することを証明するというもの。受け入れ基準はリソース宣言が4に戻り、占有が16ブロック/SMに戻ること。#3643の修正はロールバックされていない。金曜日に審査中の#3787は証明器の盲点を引き続き補う：192スレッド下でtx < 160 and tx // 32 % 2 == 0のような「境界項とwarpインデックスの剰余項をandで結合した」形態が誤検出される。根本原因はFloorDivとFloorModのエンコーディングが「上界+剰余」の組み合わせで2つの除算の関係を確立できないことであり、修正方法はthreadIdx.xをwarp_index * warp_size + laneに書き換えること。情報源：https://github.com/tile-ai/tilelang/pull/3733、https://github.com/tile-ai/tilelang/pull/3761、https://github.com/tile-ai/tilelang/pull/3787

  • TIRx移行が「口頭の理由」から1週間に3つの確固たる証拠へ、ベースの世代交代が公開準備段階に（11-03～11-06）：火曜日の#3736でtilelang/language/ast/、tilelang/language/parser/、tilelang/language/tir/entry.pyが一括削除された——初期のローカルTVMScriptパーサー分岐の残骸であり、1行追加、3384行削除、10ファイル、言語層は上流のtvm.tirx.script.parserに切り替わり、ASTと文のオーバーライド登録はtilelang.language.overridesで行われる。木曜日の#3752が依存するtile-ai/tvm#91と金曜日の#3752により、Z3のrlimitがハードコードされた100,000からkernelごとに設定可能になり、作者の言葉によれば「これによりZ3証明器に関連する多くの問題が間接的に修正された」。金曜日の#3803では完全な移行草案（draft）が提出された：vendoredのTVMを独立したApache TIRxに置き換え、フロントエンド、IR変換、コード生成、JIT適応、パッケージングをすべてネイティブオブジェクトモデルに移行し、apache/tvm-tirxの7e49a148とapache/tvm-ffiの3e906bc6をpinし、依存ツリーはクリーンな上流を維持しパッチを注入しない。3つの線は同じことを指している：メインラインのこの段階の第一優先はベースの交換であり、その他の最適化はすべてそれに道を譲る。出典：https://github.com/tile-ai/tilelang/pull/3736、https://github.com/tile-ai/tilelang/pull/3752、https://github.com/tile-ai/tilelang/pull/3803

  • 「静かな誤コード生成」が今週の主要な欠陥類型となり、しかも4つのリリースバージョンにまたがる（11-03～11-05）：最も重いのは#3808——条件関連のスカラー化の後、共有メモリepilogueで__syncthreads()が1つ欠け、0.1.12、0.1.13、0.1.14、0.1.15の4バージョンすべてで静かに誤ったCUDAが生成され、コンパイル時に一切エラーが報告されず、報告者は完全に実行可能な再現スクリプトを提供した。同族には#3800（warp specializationをオフにすると、T.Pipelinedがtcgen05のbarrier待機の前に次のstageをリロードし、MMAが書き換えられたoperandを読む）、#3721（sm_100a上でTMEMに対してT.gemmを実行し、threads/32がNを整除できない場合PTXにtcgen05.mmaが1つもなく、積が静かに破棄される）、#3775（本番環境のTP2 sglangにnvrtcバックエンドを追加するとCUDA graphキャプチャが破損し、バイト一致の設定を3回再現すると3つの異なる最初の失敗点が出る）、#1991と#1992（昇騰910_9362上でthreads=2の場合AscendVidReductionが注入されたtmp workspaceも無条件に半減し、sin/cosが間接アドレッシングtile上で3978/4096要素を誤計算、すなわち97.1%）がある。この族はすべてエラーを報告せず、通常のテストをすべて通過し、的を絞った再現でのみ捕捉できる。出典：https://github.com/tile-ai/tilelang/issues/3808、https://github.com/tile-ai/tilelang/issues/3800、https://github.com/tile-ai/tilelang-ascend/issues/1991

  • TileFoundry、同期を「分析で証明できる」から「発射は証明と一致しなければならない」へ進める（11-02 から 11-06）：#283 は「共有メモリアクセスをどのように順序付けるべきか」を証明可能な分析層にした——lowering の発射順序に従って各関数をたどり、衝突アクセスの前に commit、wait、スコープ内フェンスを計画し、83 個のスケジューリングフィクスチャのうち 52 個を計画、31 個を拒否した（24 個は TMA コピー、6 個は wgmma を使用し、両者の完了セマンティクスはまだ宣言されていない）。デフォルトでは呼び出し元からの要求がないため、finalize される 75 個のフィクスチャのバイトは main と完全に同一である。木曜にマージされた #285 はその実行側である：CUDA lowering は同期計画に従って発射し、項目ごとに逆検証を行い、不一致があれば LoweringError を投げる。単一の sm_89 上でビルド可能な 7 個のプログラムのうち 6 個は参照と完全に一致し、synccheck と memcheck はすべてクリーンであったが、同じ 7 個を main の方法で lower すると 4 個の結果が誤りとなり、直接の症状は sm_89 の E4M3 GEMM の最大偏差 659 である。金曜にマージされた #286 は WGMMA の非同期完了セマンティクスを補い、水曜にマージされた #284 は FSDP と HSDP のトレーニングセマンティクスを HIR 評価器に組み込み、4 枚の sm90 上で実際の 2×2 PyTorch HSDP と整合させた。著者は #286 に明確な限定を残している：行列命令エミッタはまだ接続されておらず、このコミットは実行の正しさを証明するものではなく、性能も与えない。出典：https://github.com/tile-ai/TileFoundry/pull/283、https://github.com/tile-ai/TileFoundry/pull/285、https://github.com/tile-ai/TileFoundry/pull/286

  • TileOPs は 5 つの期間で 15、7、1、7、9 件をマージし、競争点は「オペレータ数」から完全に「セレクタと準備コスト」へ移った（全週）：月曜期間の 15 件のうち 13 件は 11-01 の 1 日に集中し、ほぼすべてが H200 実測表と「manifest に測定済み行がなければフォールバック」という宣言を伴っていた。木曜の 7 件、金曜の 9 件でリズムは連休後で最も密な状態に戻った。3 つのハードな数字がこの週の方向性を要約している：GQA 稠密フォワードは 1 つの実測ルールで decode または prefill プログラムを選択し、最速候補に対する選択リグレットは 1.818 から 1.017 に低下した（#2808）。warp 専用 decode は softmax と QK、PV を重ね合わせ、影響を受ける 478 回のスキャン呼び出しの幾何平均レイテンシは main の 0.952 倍であった（#2817）。ブロードキャストオペランドのインプレース読み取りにより、lerp、where、clamp、masked_fill の 5 種類のオペレータのブロードキャスト行の所要時間はメインラインの 0.13 から 0.44 倍に低下した（#2832）。同期間には roofline 计价の書き換え（物理的に不可能な 3 つの帯域幅行を 7.48、7.50、5.30 TB/s から 0.62、0.62、2.65 TB/s に修正、#2830）と 3 段階タイルファクタの個別フィッティング（選択リグレットは 0.89% から 0.06% に低下、#2836）もある。出典：https://github.com/tile-ai/TileOPs/pull/2808、https://github.com/tile-ai/TileOPs/pull/2832、https://github.com/tile-ai/TileOPs/pull/2830

コンパイラ、言語層と実行パス

  • 昇騰 950 FlashMLA カーネルと付随するコンパイラ機能（#3678、11-02 マージ、20 ファイル +1997/-17）：要聞の第1条を参照。注目すべきは、このコミットが「明示的スケジューリング」に必要な三つの低レベル機能を同時にメインラインへ追加しており、昇騰ブランチ内でパッチを当てているわけではない点である——L0C から UB へのコピーで NZ 出力を保持し、各 AIV ストリームをパイプラインの前に選択し、物理発射フェーズが同一の場合はソースコード順序を維持する。

  • tile-ai/TileSight（24 スター）は、07-24 の arXiv 論文「TileSight: A First-Principles Tile-Centric Analytical GPU Performance Model from Cores to Clusters」のオープンソース実装である。タイル形状・データ移動・ソフトウェアパイプライン・ハードウェアプロファイルから出発し、CPU 上でオペレータのコスト、キャッシュ流量、実行時間を見積もる。11-05 にリポジトリ初の PR（#1）が出現した。H20 は Hopper/GH100 であり、requires_arch=("wgmma",) 付きのプランは、アーキテクチャプロファイルが WGMMA サポートを宣言していないために従来は UnsupportedError を投げていた。本コミットは support_wgmma=True を設定し、かつ明示的に support_utcmma=False を維持するため、こうしたプランは受け入れられ、一方で tcgen05 と Tensor Memory の要求は引き続き拒否される。検証は CPU 上で 847 項目すべて通過であり、作者は明示的に「GPU 性能の検証ではない」と宣言している。
  • この路線の意義は、TileOPs の roofline 見積もり、TileFoundry の解析レイヤーと合わせて三角形を形成することにある。一つは解析モデルを提供し、一つは行単位の見積もりを提供し、一つは証明可能な同期プランを提供する。三者はいずれも今週、実質的な動きがあった。

コミュニティブランチとサードパーティリポジトリ

  • PTO-ISA/tilelangGym の独立リポジトリ化：この感度・回帰テストセットは PTO-ISA/tilelang の examples/ascend/t_parallel_st_suite から分割された。理由は、テストセットが TileLang と PTOAS のバージョンを独立して固定できるようにするためである。現在の三つの主要パスは、昇騰 SoftLib SimtVF（target=ascend、cython、主要回帰ゲート）、VectorizeParallelToPTO と VL の vload/vstore、そして benches 配下の @pto.jit で書かれた手書き SIMD DSL 対照実装である。各テストケースディレクトリには config.toml と VERDICT.md が付属する。

6. トレンド観察

第一に、TIRx移行はすでに主線の事実上の最優先事項であり、それが「減法」の形で現れ始めている。 一週間のうちに3つの証拠がある：月曜に移行のためにThreadSync正確性改善の一式を回退し（#3733、同時にTVM fork側の最適化提案#89をクローズ）、火曜に3384行の遺留パーサー分岐を削除し（#3736）、金曜に完全な移行草案をコミットした（#3803、2つの上流コミットをpinし、パッチを注入しないことを明示）。その間にZ3リソースをハードコードから設定可能への変更（#3752とtvm #91）も挟まっている。これらの動作に共通するのは、複雑さをクリティカルパスから撤退させることである：一時的に保守的な実装に戻しても、vendored依存の内部構造を言語層に生やし続けることはしない。代償として、主線は移行期間中に「既知の非最適」パスを一批抱えることになり、收益としては基盤の世代交代が完了した後にすべての下流バックエンドが安定したIR境界に対して適配できることである。

第2に、正確性リスクは形態を変えた：「コンパイルが通らない」から「コンパイルは通り、実行時にエラーも出ず、結果が誤る」へ、しかもバージョンを跨いで潜伏する。 今週は少なくとも7件がこの族に属する：#3808 は 0.1.12 から 0.1.15 までの4バージョンにわたり __syncthreads() が1つ欠けており、#3800 は Blackwell の tensor memory パス上で MMA が上書きされた operand を読むようにし、#3721 は sm_100a 上で GEMM の積全体を黙って破棄し、。#3775 は本番環境で CUDA graph のキャプチャを破壊し、。#3749 は依存関係分析から物理ロード範囲を見えなくし、。#1991/#1992 は昇騰の threads=2 下で sin/cos が 97.1% の要素を誤計算し、。#3774 と #3773 はコンシューマー向け카ードで誤った結果を出す。この族はユーザーへの被害が最大である。なぜなら「コンパイラは正しいか」という前提を、検証を要する仮説に変えてしまうからだ。今週の対応方向は、正確性を棄却可能な証明にすることだ——TileFoundry の #283/#285 はまず証明してから発射し、発射後に逆検証する。#3786 と #3787 は黙って誤ったコードを生成するのを、コンパイル時エラーまたは明示的な拒否に変える——単体テストの数を増やし続けることではない。

第3に、昇騰の役割は「適応ターゲット」から「初回ターゲット」へ変わり、エンジニアリングが2本の脚で同時に進んでいる。 1本はアーキテクチャだ。FlashMLA のような DeepSeek 自身のデコードパス上のコアカーネルが、昇騰 950 を直接ターゲットとしてメインラインに書かれており、使っているのは T.Stage、annotate_buffer_addresses といった明示的スケジューリングのために用意された低レイヤ機能だ。コンパイラ側の3箇所の配套変更と合わせ、昇騰パスは「動く」から「スケジューリング意図どおりに動く」へ転換しつつある。もう1本は骨格だ。#1975 は 2887 ファイル、60万行の追加で TileLang-Ascend 全体をメインラインのマルチバックエンドフレームワークに移し、arch="dav-2201" でバックエンドを振り分ける。mlir-ascend の #208 は Codex の初期化、接続、復旧の3つのワークフローとタスクハンドオーバーを .workspace/ に書き込む。「移行リポジトリ」と「エージェントによる移行リポジトリ」を同じ週に見ると、昇騰側のボトルネックが「オペレータ不足」から「一貫したエンジニアリング骨格と再利用可能な移行プロセスの不足」へ移ったことが分かる。

第4に、オペレータライブラリの競争点は完全にセレクタ品質と準備コストへ移り、性能差の残された空間は「どう計算するか」にはない。 金曜の TileOPs の9件のマージのうち、実際に GPU kernel を変えたのはブロードキャスト就地読みとネイティブ幅タイルの2件だけだ。reduction レイアウトキャッシュが節約するのは呼び出し準備（4.33% から 6.17%、生成ソースコードは不変）、3段階タイルファクタが変えるのは1つの定数（regret が 0.89% から 0.06% へ）だ。さらに roofline 価格計算の書き換えと L2 フラッシュを読み取り専用化を加えると、明確な路線が見える。まず各形状の合法な設定を列挙し、統一されたコストモデルで順位付けし、キャリブレーション過程を再現可能な契約として書く（#2826 は「スキャン、フィッティング、チェック」の3ステップをドキュメント文字列に書いている）。この道を正しく進めば、性能は個別カーネルの手作業チューニングに依存しなくなる。誤れば「ある形状は特に速く、他の形状は運任せ」に退化する。

第5に、国産バックエンドは「一度に大きなバックエンドをマージ」から「レビュー可能な最小単位を公共リポジトリへ push」へ転換している。 海光は自研ブランチから #33 と #34 の2つの正式 PR へ進み、摩尔線程は1本の README で2ヶ月の静寂を終わらせ、mlir-ascend は3つの小さな PR で tl.sub/mul、tl.shl、tl.shr を1つずつ TLIR 方言へ移し、昇騰はコア比率、例外ダンプ、性能スキルといったエンジニアリング詳細を項目ごとに補っていく。3本の線の共通点は、もはや大きなマージを待たないことだ。これは上流にとって良いことである。レビュアーは配置と lowering の設計に早い段階で意見を出せる。3万行の一括マージの時に初めて見るのではない。下流にも代償がある——メインラインはこうした期間、「既知のいくつかが動かない」状態にあり、より強力なリリース前回帰規律が必要になる。

最後のリスク面：ベーススイッチはすべてのグルーレイヤのコストを一度に露呈させる。 もし #3803 が進めば、3rdparty/tvm の vendored 構造は2つの pin された上流コミットに置き換えられ、その時点で TVM 内部 API に依存するすべてのバックエンド（昇騰、海光、mlir-ascend のグルーレイヤ）が追随して変更しなければならない。草案には「依存パッチを注入しない」と明記されており、これは約束でもあり制約でもある——今週 mlir-ascend が BishengIR アダプタを contrib へ移し、昇騰が性能スキルをチップ世代別に分岐させたことは、いずれもこうしたベーススイッチのために用意された交換可能面と見なせる。この線が健全かどうかは、移行草案のマージ後2週間以内に、これらのバックエンドがコア lowering に手を入れずに適応を完了できるかで判断する。
