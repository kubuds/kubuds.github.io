コンパイラ、言語層と実行パス

  • 全 warp リダクションをハードウェア redux に変更（#3692、10-29 マージ、4 ファイル +337/-35）：以前はグループ全体がアラインメントされた満杯の warp であっても、通常のクロススレッドリダクションはそのまま shuffle ツリーに展開されていた。メインブランチ 837486a 上で4つの独立した 32 lane FP32 の最大値取得を sm_103a と CUDA 13.1 の組み合わせでコンパイルすると、20 個の shuffle、0 個の redux が生成されていたが、変更後は 4 個の redux.sync.max.f32、0 個の shuffle となる。手法はスカラーおよびバッチ全リダクションで既存の warp_reduce ヘルパーを再利用し、呼び出し側はスレッドのジオメトリのみを判定する。整数リダクションは SM80 以上でハードウェア redux を使用し、FP32 の最大値・最小値取得は sm_100a、sm_100f と sm_103a、sm_103f でのみ利用可能である。狭い浮動小数点は FP32 に昇格してからヘルパーに入り、FP64 は精度を落とさずに引き続き shuffle パスを使用する。著者はエンドツーエンドの高速化を主張せず、命令レベルの対照のみを提示している。
  • autotuner の独立 JIT 設定を並行コンパイルに変更（#3476、10-29 マージ、2 ファイル +54/-46）：従来の実装はコンパイル期間全体で1つのロックを保持し、デフォルトのコンパイルオプションのみを使用する設定も直列化され、フロントエンド、ダウンストリーム、デバイスコンパイルがすべて待ち行列に入っていた。変更では、各オーバーライド設定に対して dataclasses で独立した JITImpl を複製し、デフォルトオプションは引き続き既存の遅延パスを通してカーネルキャッシュとオブジェクト同一性を保持し、第1段階のキーを共有する候補のみを直列化し、デバッグ出力の書き込みは引き続き直列化する。クロスバックエンドの検収データ：昇騰 1797 項目通過（Python 3.12.14、torch_npu 2.10.0、CANN 9.3.0、AscendC サンプル 50 例すべて通過、PTO サンプル 44 通過 6 スキップ）、ROCm 7.2 で gfx942 上 3220 項目通過、Metal 95 項目通過、CUDA で H100 PCIe cu130 上 5500 項目通過、CuTeDSL 75 通過 17 スキップ。
  • 昇騰バッファビューのレイアウトとポインタ単位をエイリアス間で伝播しないように変更（#3623、10-29 マージ、23 ファイル +1139/-438）：T.view や T.reshape で生成された複数のバッファが同一の記憶域を共有しつつ異なるレイアウトを要求する場合、以前は共有データ変数に基づいてレイアウトを解析していたため、誤った Cube マッピングや DMA アドレスが選択される可能性があった。本コミットではレイアウトを個々の Buffer ビューに付与し、レイアウト推論、フラクタル記憶正規化、マルチバッファ実体化とコピー、行列積のダウンストリームまで一貫させる。生ポインタオフセットは各自の要素単位で再マッピングされる。同一のバージョン付き割り当て上で、Cube ビューは異なる MajorK と MajorMN レイアウトを使用可能となり、条件は論理ストライドが稠密、ベースアドレスオフセットがゼロ、オペランド型が互換、パディング後の記憶サイズが等しいことである。
  • GM から L1 へのコピーと範囲外パディングを1つのスケジューリングタスクに統合（#3543、10-29 マージ）：両者は同じ L1 データを共同で準備するが、以前はパディングが独立したスケジューリングタスクに分割されることがあり、同期挿入時に余分な MTE2 パイプラインフェンスが発生していた。変更後はコンシューマがパディングを含む完全なデータを待機し、FP8 MX の K 尾部パディングも同様に統合されタスク内の条件付きパディングが保持され、元の MX 遅延パディングキューは削除された。47 項目の集中テストが通過。
  • ROCm と実行コンテキストに関する一連の修正：exp、exp10、log、log2、log10、sin、cos の7つのデフォルト関数が HIP 上で fast_math 設定に関係なく高速組み込みに低下しなくなり、アンダースコア付きの8つの高速オペレータに最低ダウンストリームルールが追加された（#3621）。自動ターゲットは固定の 0 番カードではなく現在の HIP デバイスを読み取るように変更（#3594）。NVRTC と CuTeDSL は最初の入力テンソルが存在するデバイスに基づいて現在のストリームを取得（#3359）。profiler はデバイス未指定時に現在のデバイスを使用し、キャッシュフラッシュが 0 番カードに送られなくなった（#3357）。
  • 言語層と下降の小修正：TMA gather/scatter の Python 整数行インデックスを int32 に変換し、リテラル記法が Blackwell 上でコンパイルクラッシュしなくなった（#3365）。実行期の行程数のパイプライン epilogue を直接展開し、ページドデコードが再びコンパイル可能に（この不具合は下流の TileOPs#1852 により報告）（#3356）。VectorizeLoop はループストライドを暗黙に無視しなくなった（[#3345](https://github.com/tile-ai

/tilelang/pull/3345)）；T.clamp の NaN 伝播降下が巻き戻され、min/max セマンティクスに戻る（#3628）；T.Parallel の coalesced_width を一律 IntImm に変換（#3374）；TMA 記述子は検証済みの名前のみを記録（#3484）；非 restrict 引数の handle サフィックスが切り捨てられなくなる（#3366）。

正確性と欠陥修正

  • ストリームとキャッシュの同一性：出力を呼び出し元ストリーム上に割り当て（#3649）と NVRTC、CuTeDSL のストリーム取得（#3359）の後、本調査期間では自動チューニングキャッシュキーを compile_flags に組み入れ（#3338、同一カーネルでコンパイルオプションを変えても古いバイナリを再利用しなくなる）、Ascend 側では Bisheng ビルド識別子をバイナリキャッシュキーに組み入れた（#3691）。二つの独立した路線が同じ週に同じことを行った：キャッシュがソースコードと形状だけでキーを構成すると、コンパイラを変えたときに誤ヒットする。
  • 同期とメモリ計画：ThreadSync が address_of を書き込みとして記録し、不透明呼び出し後のフェンスを補完（#3346、従来 T.address_of(B[0]) 形式では extern の後にフェンスがなく、T.access_ptr(B, “w”) 形式にはあった）；T.ws(-1) を全スレッドで実行するよう変更（#3354）；ストレージドメインを跨ぐ命名バリアの重複番号（#3643）と sm_100 の TMEM 解放に CTA バリア欠落（#3645 / #3663 / #3664）を週初に処理。水曜に三件の ThreadSync フェンス位置ずれ欠陥が浮上（#3680）：フェンスが発散分岐内に置かれる、分岐内のフェンスが誤って外側の保留依存をクリアする、スレッド数カウントループによるフェンス位置、に対し #3682 と #3681 の二件の審査中修正を用意。

6. トレンド観察

リリースエンジニアリングは「最後の1マスで止まる」から「イメージ化デリバリー」へ。 月曜のデイリーレポートではまだ TileOPs の初回リリースが「ドキュメント準備完了、成果物未アップロード」と書かれ、PyPI 上では最新が依然として 2025-10-09 の 0.0.1.dev2 であった；火曜 07:45 に成果物がアップロードされ、13:15 にリリースページが公開され、木曜のリリースイメージではオペレータライブラリ、TileFoundry、三段の環境識別子（cuda13.2、torch2.13、tilelang0.1.12）が一緒にロックされた。一週間のうちに、この線は「リリースできるか」から「どう組み合わせてデリバリーするか」に変わった。200 余オペレータのライブラリにとって、インストール可能性はさらにもう1パーセントの最適化よりも外部採用速度を決定づける。今週の答えは、インストール経路も成果物にすることである。

欠陥タイプは「コンパイル通過、実行時にエラーなし、結果が誤り」に高度に集中し、しかもハードウェアやコンテキストと強く相関する。 出力が誤ったストリームに割り当てられる（非デフォルトストリームかつキューイングされた作業がある場合のみ破損）、T.ws(-1) がゼロスレッドで実行される、スライスフィルが長さではなく末端で検証される、負のインデックスが回り込んだ後も依然として負、address_of が読み取りとして扱われる——五条すべてがコンパイル期に警告なく、実行期に異常なし。この種の欠陥のコストはコンパイルエラーよりはるかに高く、なぜならそれらが汚染するのは「テスト全通過」という前提そのものだからである；水曜に浮上した冷間コンパイルを仮定する6つのテストと木曜の without_kernel_cache セマンティクス漏洞は、まさにテストインフラも同じリスク領域にあることを示している。今週の対応は境界検証をコンパイル期に前移することであり、方向は正しいが、#3704、#3705、#3707 の三条の新規開設欠陥はこの境界がまだ遠く描き終わっていないことを示している。

昇騰は「バックエンドを移す」から「オペレータを補う」へ転じ、初めて再計算可能な受け入れ基準を示した。 水曜は NPUIR が主干に統合（504 項の自測、71/72 サンプル）、木曜から金曜の5件のマージのうち4件はオペレータとサンプルであり、しかもすべて上流モデルの需要に沿って配列されている：GLM-5.3 の indexer 圧縮、ブロックゲート付き注意の内積、4ビット量子化行列積、量子化視覚モデルの深さ方向畳み込み。共通点は量子化と融合を kernel 本体に書き込むこと（E4M3 純整数エンコード、4ビットパッキング規約、デュアル kernel に 1×1 高速パスを追加）であり、ホスト側の補救に委ねない；同時にプロファイリング skill とチェックリスト化テストチャネルをプロセスとして確立した。主要矛盾は「コンパイルできるか」から「オペレータの数値と性能が安定的に受け入れられるか」へ変わりつつあり、a2a3 スケジューラ移行の 100 ファイルは次段階の変動がスケジューリング層にあることを予告している。

実行経路は引き算、バックエンドリストは足し算。 メインリポジトリは今週、全 warp リダクションを redux.sync に収め、autotuner のコンパイルロックを細分化し、GM から L1 へのコピーとフィルを1つのタスクに統合し、buffer ビューのレイアウトを共有変数から単一ビューに戻した；同時にバックエンドリストは拡張を続けている——ROCm は pip 版 SDK と FP4 を補い、Hexagon は単日 15 件、PPU はゼロ変更ラッパーが出現し、Intel AMX は TileFoundry の中で 39 個の静的契約になる。二つの方向は矛盾しない：上流は実行経路を収束させ、下流はそれぞれパッケージングして配布する。これは TIRx が TVM を外部依存に変えるのと同じ発想である。

「fork 化」は今週最も確かな採用シグナルであり、同時に最も現実的な同期コストをもたらす。 T-HEAD が TileLang を自社ハードウェアスタックの基盤として PPU ブランチを作り、CANN コミュニティが独自にオペレータリポジトリを構築し、PTO-ISA が問題集とベンチマークをそろって配套リポジトリ化し、RISC-V にはコミュニティハブリポジトリが登場した——これらはいずれも tile-ai 組織には存在しないが、いずれも言語レイヤーの安定性に依存している。这正是 0.1.0 が公開 API を凍結し CI ゲートにした意味である。代償も同樣に明瞭だ。金曜日の第 #3705 号欠陥はブランチユーザーの実際のビルドが先に踏み、上流が後から修正した。ブランチが増えるほど、こうした「下流が先に発見し、上流が後で修復する」経路は長くなり、主リポジトリはブランチと上流をどう同期するかという長期的な問いに答え始める必要がある。

口径の問題が製品の問題として扱われ始めた。 TileOPs は木曜日に「単発呼び出しは先行、バックツーバックは後退」を単独項目化し（#2791）、金曜日の GEMM 改動は消費電力上限に基づいてグリッドグループを再計算し、DRAM 読み取りを 168 MB から 94 MB に削減した（#2794）。セレクタも manifest への当てはめフィッティングからビジー時のキャリブレーションへと変更した。「ある行が何マイクロ秒速くなったか」と比べて、こうした改動は訓練と推論の実際の呼び出し形態がベンチマークと異なることを認め、その差異をスケジューリング戦略に書き込むものである。大規模モデル向けにカーネルを書く言語にとって、これはオペレータの数を積み増すよりも、長期的に採用されるかどうかを左右する。
