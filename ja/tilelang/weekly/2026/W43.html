2026-10-23 Kubuds

レポート期間：2026年10月19日（月）から10月23日（金）まで、計5営業日 素材出典：本誌のTileLangコミュニティ動態デイリーレポート5号（10-19、10-20、10-21、10-22、10-23）。5号分の収集期間は合計で10-16 07:00から10-23 07:00まで。さらにtile-ai組織の29リポジトリについて168時間の期間で補足調査を行い、各リポジトリのリリースページ、タグ、VERSIONファイルを再確認した（詳細は付録）。

1. 今週の主要ニュース

  • TileFoundry 0.0.3が正式リリース、命令レベルのスケジューリングをagentに委ね、H200上のQwen3.8-27Bプリフィルは3段階すべてでSGLangより高速（10-21）：10-21 10:26にv0.0.3をタグ付け、PyPIではtilefoundry==0.0.3、コードネームは「Agent-driven scheduling」。中核となる変更はスケジューリング権の帰属にある。コンパイラは各HIR操作をどの命令で実装できるか、それぞれ何を必要とするかを列挙し、agentが候補の中から選択し、コンパイラが選択されたスケジュールをTIRへと下降させる。付随するCLIにはschedule candidatesとschedule factsが追加され、命令はAtomSched操作として宣言され、明示的なTIRオペランド契約を伴い、CUDA MMA atom、SM90 WGMMA、非同期コピーから着手する。性能面では3組の実数値が示されている。Qwen3.8-27Bプリフィルは単一のH200上で1024 / 4096 / 8192 tokenがそれぞれ80.29 / 309.61 / 631.19 ms、SGLangは89.06 / 317.11 / 638.25 ms。短系列128 / 256 / 512 / 1024 tokenではそれぞれSGLangの1.88 / 1.41 / 1.10 / 1.03倍となる。既知の問題は2点。wheelにCUDAランタイムヘッダーがまだ同梱されておらず（インストールパッケージからはCUDA kernelをビルドできず、ソースのcheckoutが必要、次バージョンで修正）、また性能タイムラインがinsert_slice、tf.zerosのmesh間位置に対する価格設定を誤っている（#239）。

2. コアプロジェクトの進展（メインリポジトリ tilelang）

バージョンとリリース

  • メインリポジトリの最新タグとリリースは依然としてv0.1.15（09-30リリース）であり、週全体で新規タグなし、新規リリースページ項目なしで、今週金曜時点で既に23日経過している。VERSIONファイルを確認しても依然0.1.15であり、READMEの最新マイルストーンも09-30のAscend 950バックエンドのまま止まっている。
  • TileFoundry 0.0.3は今週唯一の新バージョン（10-21 10:26）であり、組織内で09-30以来の最初の新規タグでもある。適応ラインのタグは週全体で動きなし：沐曦v0.1.14（09-17）、摩尔線程v0.1.15+musa.1（09-30）、MLIR昇騰v0.1.2.020.sglang.poc（09-09）、昇騰v0.1.2.000。
  • 下流の制約は依然0.1.12と0.1.15の間で停滞：TileOPsのpyproject.tomlは今もtilelang==0.1.12を固定で記載しており、10-18に0.1.15へ引き上げを試みた#2554はクローズ済みでマージされていない。PR自身が述べたブロッカーは、0.1.12で通過した29件のsmoke testが0.1.15で失敗することである：うち28件は動的extentのT.Pipelinedがcp.asyncの末尾でptx_wait_group(3 - t * 2)を残し、CUDA codegenがDowncast失敗を報告するためであり、残り1件はLegalizeSafeMemoryAccessがFalseに折り畳まれた分岐下でnull判定に失敗するためである。今週新たにマージされたSM89のユースケースは同時に0.1.12と0.1.15開発版を実行しており、アップグレードのゲートがデュアルベースライン検証を前提としていることを示している。

コンパイラ、言語層と実行パス

  • Windows ARM64 をリリースパイプラインへ（#2962、10-19 マージ、12 ファイル +356/-45）：PowerShell インストールスクリプトを新設し、NVIDIA プレリリースチャネルから CUDA 13.4 の windows_arm64 ローカルインストーラを取得して固定パスへ配置する。FindPipCUDAToolkit モジュールと windows_arm64_clang_compat.h 互換ヘッダを追加し、ARM64 上の MSVC ツールチェーンにおけるヘッダと組み込みの差異を解決する。あわせて pyproject、2 つの requirements とレイアウト、MSVC 補助モジュールを調整する。これは ROCm と昇騰に続いて補完された 3 つ目の非 x86 デリバリ面である。
  • lower trace でホストとデバイスのソースを分離（#3496、10-19 マージ、6 ファイル +121/-63）：デバイス側は codegen_device.cpp と .original ベースライン、.latest 最新版を出力し、ホスト側は別途 codegen_host.cpp と同じ構造のベースラインを出力する。report.html は最新の実行を指すソフトリンクとなる。これと呼応して、審査中の #3583（13 ファイル +106/-4390）は lower trace の実装、専用環境設定、関連テストをメインリポジトリから丸ごと切り離し、共有のコンパイラ計装インターフェースのみを残して、トレーシングツールを独立して進化させる。
  • CUDA 16 ビット数学の降格規則を補完（#3172、3 ファイル +463/-8）：asin、acos、asinh、acosh、atanh、log1p、atan2、hypot、copysign、ldexp、nextafter に CUDA 専用の下降規則が欠けており、float16 と bfloat16 の呼び出しが codegen 段階で誰にも処理されなかった。修正ではこれらを CUDAMath に登録し、half_t、bfloat16_t のオーバーロードを追加する。10 個のオペレータは float32 で評価してから戻し、nextafter は 16 ビットエンコーディングによる整数比較ステップに変更し、fast math 下でも bfloat16 の非正規数を保つようにする。
  • eager フロントエンドで Python ソース位置を保持（#3558、4 ファイル）：生成されたループ呼び出しを for 文へ、コンテキストラッパーを with 文へマッピングし直し、イテラブル引数の展開位置も補い、traceback とカバレッジのずれを修正する。
  • BF16→FP32 のベクトル化変換をインライン PTX に変更（#3595、4 ファイル +19/-7）：ペア lane を一度に f32x2 へ変換する実装を追加し、lane ごとのスカラー昇格を置き換える。lane 幅 2、4、8 のいずれもサポートを維持し、セマンティクスは変えず命令列のみを変更する。
  • 展開パスと ROCm Select（#2887）：ループ展開は trip count が 0 の stepped ループを消さなくなり、ROCm 側のベクトル化 Select は lane ごとの下降に変更され、サポートされないターゲットで一括下降が失敗するのを避ける。
  • softmax の 16-CTA クラスタ跨ぎ分割（#2632、10-18 マージ）：lm-head のような行数が少なく行が長いケース（4×102400）向けに新しいカーネルを追加する。旧実装は各行 58 セグメントでグローバルメモリを介して (max, sum) を交換し grid 障壁を跨いでいたが、新実装は 1 行を 16-CTA クラスタのレジスタ上に展開し、各要素の指数を一度だけ取り、warp 跨ぎ・CTA 跨ぎ・クラスタ跨ぎで shuffle ツリーにより max-first で畳み込む。
  • 審査中の方向性：PTO の 2 件のほか、[Transform] Locate VerifyBufferInit reads outside tile ops（#3620）、[Codegen] Add unsigned mulhi intrinsic（#3617）、[Transform] Keep assumption checks with local dependencies in scope（#3611）、[Transform] Preserve tl.assume predicates that simplify to true（#3610）、[CPU] Support clz in C and C host code generation（#3609）が調査期間内に更新された。#3597 の混合符号シフト修正と tile-ai/tvm fork の #87

6. トレンド観察

  • 正確性の堅牢化は層が段階的に進んでおり、同層での繰り返しではない：先週メインリポジトリで整理したのは「形状と幾何の検証」であり、今週の三段はそれぞれ異なる——まず warp 特化とパイプラインの幾何とバリア（#3503、#2342、#3536、#2822）、次にサイレントな数値エラー（#2818、#2815、#3550、#3070、#3350、#2860、#3125）、最後にコンパイル期の状態一貫性（#3579、#3612、#3226）である。第三段が最も注目に値する：この種の欠陥が生成する kernel は依然として正しい可能性があるが、コンパイラがユーザーに語る内容と実際に行うことが一致していない；TileLang は現在 agent による kernel の自動記述を組み込んでおり、コンパイル期の状態が自己整合できるかどうかが agent の反復ループを収束させられるかを直接左右する。
  • 昇騰側のボトルネックはすでにオペレータの数からメモリモデル、ランタイム境界、訓練の逆伝播へ移っている：今週マージされた適応リポジトリの 11 件のうち、逆伝播と再帰オペレータが 5 件を占め（indexer_bwd、SiTU-GLU 逆伝播、LSTM、GRU、CrossEntropy ドキュメント）、メインリポジトリ側で最大のものは NZ レイアウトの UB→L1 行間隔表現（#3530、18 ファイル）、技術密度が最も高いのは 32B 未満のコンパクトな行間隔が表現できず明示的に中止するしかないもの（#1795）である。加えて JIT キャッシュの原子的公開（#1903）と PTO 述語の指数増加（#3581）があり、この路線のテーマは「既存のオペレータを境界条件下でエラーを出さないようにする」ことである。CANN コミュニティが別途 ops-tilelang オペレータリポジトリを立ち上げたことと合わせると、分業が読み取れる：オペレータ資産はコミュニティリポジトリが担い、メインリポジトリはバックエンドのセマンティクスと codegen に専念する。
  • SM89 と SM90 が並列する二本のハードウェア主軸となり、優先順位を決める基準はピーク性能から入手可能性へ移っている：SM90 方向は今週 6 つの warp 特化 kernel を生み出し、SM89 方向はブロックスケーリング FP8、INT8 W8A8、FP8 BMM、W4A16、ページド DSA、NSA top-k の 6 経路を同時に推進し、しかも PR は一般的にシングルカード実測を添付し「SM90 での実行結果を主張しない」「大規模ユースケースではほぼ互角であり、普遍的な優位性を構成しない」と明記している。Ada 級グラフィックスカード（L40S、4090 の一类）は国内開発者が手にする主力ハードウェアであり、この志向は SemiAnalysis が指摘する「最適化がスーパーノードに多面的に向かい、汎用性が性能に後れを取る」とちょうど補完し合う。
  • エコシステム層の組織的動きはコード層より多い：メインリポジトリは今週リリースも breaking change もなかったが、組織外には中国語システムチュートリアルリポジトリ、CANN コミュニティのオペレータリポジトリ、agent SKILL ワークフロー、Hexagon バックエンド実験、VS Code 拡張と SAIL ラッパーリポジトリが現れ；組織内には TileFoundry 0.0.3 の agent スケジューリング、Sunrise の第二の配布形態、TileOPs の仕様フル搭載がある。「人間がルールを書き、agent がチューニングし、リポジトリにベースラインを蓄積する」の三者を合わせて見ると、昇騰側と TileLang 全体のエンジニアリング分業は再編成されており、コードのリズム自体は平穏である。
  • 分析機関が TileLang を昇騰の可用性の判断基準として扱い始めている：SemiAnalysis は「6 つのリポジトリのうち当時利用可能だったのは TileLang だけ」を用いて DeepSeek の昇騰サポートの完成度を定義しており、これはどの単一の技術ブログよりも TileLang が国産算力の語りにおける位置を示している——実験的 DSL からデフォルトの担持層へ。同一のレポートは逆方向のシグナルも示している：最適化はスーパーノードに集中し、x86 ホストのサポートは依然として不完全で、性能と汎用性の間には明らかなトレードオフが存在する。SCMP の転述はこの判断が主流メディアの言説に入りつつあることを示している。
  • 次号の注目点：メインリポジトリ v0.1.16 がリリースされるか（すでに 23 日間沈黙）；TileOPs の 0.1.12 ロックが解除できるか（#2554 クローズ後に新バージョンの方案は見られず、デュアルベースライン検証が依然としてゲート）；PTO の #3512 と #3516 がマージできるか（PTO がデフォルト実行バックエンドになるかを決める）；TileFoundry 0.0.3 の wheel のヘッダファイル欠落と #239 の価格設定問題が次バージョンで修正されるか；Sunrise の S2 wheel が tangGetDeviceCount で失敗する件をどう処理するか；昇騰 sparse_mla の順伝播と逆伝播（#1929 / #1928）、GLM-5.3 kpool（#1910）の実装ペース；海光 gcy_merge_main のレジスタパイプラインスイッチのクリーンアップがいつ main に入るか。
