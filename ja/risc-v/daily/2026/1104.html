香山 TAGE が alt 情報を meta に格納、訓練読み出しは予測または結果の誤り時のみ発生（11-03）

第 6800 号の変更は TAGE 予測器における訓練読み出しと予測読み出しが同一のストレージを奪い合う競合である。従来は前者が alt 分岐の情報を取得してから訓練方法を決定する必要があり、この情報は予測段階でも一度読み出されるため、二つの経路が同じテーブルエントリ上で衝突していた。変更では alt 情報を追加で meta に格納し、訓練側は毎回の予測で読み出しを行わず、TAGE の予測誤り、または実際の分岐結果が予測と一致しない場合にのみ訓練読み出しを発起する。

この種の変更の利益は IPC には現れず、一本の高頻度読み出し経路をクリティカルパスから外すことにある：予測器は毎サイクル結果を出す必要があり、訓練は誤り一回につき一回しか発生しないため、作業を低頻度イベントに移すのは分岐予測器における最も典型的なトレードオフである。高周波数化を進める香山にとって、節約されるポート競合は節約されるテーブルエントリよりも価値がある。

日付：2026-11-03　情報源：XiangShan #6800

香山が CBO オペコード結合誤りを修正：CBIE の inval-to-flush が誤って cbo.zero に合成（11-03）

第6754号は極めて深刻な結果をもたらすデコードバグである。cache block操作（CBO）の命令では、操作種別が全体として完全なオペコードを選択すべきところ、コードは「完全なCBOオペコード」と「基本オペコード」をビット単位のORで結合していた。CBIEがinvalをflushに変換する要求を出した際、OR演算がcbo.invalとcbo.flushを合成してcbo.zeroにしてしまった——意味が「このブロックを無効化する」から「このブロックをゼロクリアする」に変わってしまったのだ。

両者の違いはキャッシュ状態だけにとどまらない。invalは単に破棄するだけだが、zeroはデータを書き込む。データ付きのゼロクリアが、他のhartによって使用中またはまもなくライトバックされる行に落ちると、サイレントなデータ破壊となる。しかも特定の操作シーケンス下でのみ発生するため、ベンチマークや通常の回帰テストでは発見できない。作者はコミット説明で原因を非常に直接的に書いている。この種の「本来なら選択すべきところをOR演算で書いてしまう」ビットフィールドの誤りは、RISC-Vに新たに追加されたCBO拡張では特に犯しやすい。オペコード自体が階層化されているからだ。

日付：2026-11-03　情報源：XiangShan #6754

香山 StoreQueue と LoadUnit の4件の修正：CBO zero のエンキュー、16B 跨ぎのフォワーディングマスク、MdpHit 判定、ロールバック情報の欠落（11-03）

同日にマージされたメモリアクセス関連の修正4件は、合わせてload-store経路の集中的なデバッグとなっている。第6762号はflush前にCBO zeroのエンキュー完了を待つようにし、キューがフラッシュされる際にゼロクリア操作が失われるのを防ぐ。第6718号は16バイト跨ぎの非アラインドアクセスのフォワーディングマスクを修正する。この種のアクセスは同時に2つのエントリにヒットするため、マスクの計算を誤ると誤ったバイトをフォワーディングしてしまう。第6714号はwaitSqidxがすでにリタイアしている際のMdpHit判定条件を修正する。タイミング境界上の状態判断に属する。第6678号は同一RobIdx下でLoadUnitのロールバック情報が後続命令に上書きされる問題を修正する。

4件の共通点は、いずれも特定のインターリーブ下でのみ誤る点にある。非アラインドアクセスとフォワーディングの重なり、リタイアとヒット判定の同一拍、同一RobIdxで連続する2つのloadによるリプレイ誘発などだ。香山は最近この領域への投入を明らかに密にしており、Matrix拡張が導入する広帯域なメモリアクセス経路とも関係している——経路が広くなるほど、境界条件は増える。

difftest が行列検証の書き戻しと完了イベントを分離（11-03）

第 1025 号はマトリックスユニットの AMU イベントを「書き戻し」と「完了」の 2 種類に分離した。従来は 1 つのイベントが 2 つの意味を同時に担い、参照モデルと被試験設計がアウトオブオーダーで交錯する際に「データが書き戻された」を「命令が完了した」と誤認したり、その逆が起きたりして、検証器が中間状態で通過させてしまうことがあった。分離後は 2 種類のイベントがそれぞれシーケンス番号を持ち、検証を意味に沿って整合させられる。

これはマトリックス拡張の検証が実用に近づくための必須の一歩である：MMA のような長レイテンシ命令の完了順序と書き戻し順序はもともと一致せず、1 つのイベントで 2 つの事柄を表現すれば、マルチコアやリプレイのシナリオでは必ず誤判定が生じる。同日このリポジトリはこの 1 件のみである。

ドイツ・ルール大学など 4 機関が RISC-V マルチコア SoC 上で 4 種のランダム化キャッシュを実測（11-04）

ルール大学ボーフム校、マックス・プランク安全保障・プライバシー研究所、ジョージア工科大学の共同チームがプレプリント《Randomized Caches in Hardware: Challenges and Trade-offs》（arXiv、2026 年 10 月、CC BY 4.0）を発表した。著者は Xinrui Wang、Pascal Kosak、Christof Paar、Daniel Genkin、Yuval Yarom、Anirban Chakraborty である。ランダム化キャッシュはアドレスからキャッシュ位置へのマッピングを撹乱することでサイドチャネル攻撃に耐えるもので、従来の方式はアーキテクチャ層の記述にとどまることが多く、ハードウェア実装の落とし穴を体系的に論じたものはなかった。

チームは CEASER-S、ScatterCache、SassCache、MIRAGE の 4 設計をすべて同一のマルチコアアウトオブオーダー RISC-V SoC の最終レベルキャッシュとして実装し、完全な FPGA プロトタイプを作成し、SPEC CPU 2017 rate と GAPBS の全負荷を実行し終えた。その説明によれば、同一のフルシステムハードウェアプラットフォーム上でこれら 4 設計を横断評価したのは初めてである。論文は実装の難点とトレードオフに重点を置き、公開アブストラクトでは性能オーバーヘッドの定量的比較を示していない——この点は留意に値する。セキュリティ機構のコストデータは往々にして本文の表に隠れているからである。

OpenBSD 8.0 の RISC-V 改善がメディアに再解釈される（10-20 リリース、11-03 報道）

OpenBSD 8.0 は10月20日にリリースされ、11月3日にメディアがその中の RISC-V 部分を改めて整理した。これは個別に記録する価値がある。というのも、このバージョンの riscv64 プラットフォームにおける増分はドライバではなくアーキテクチャ特性に集中しているからだ。カーネルは CPU 拡張の検出を開始し、elf_aux_info の AT_HWCAP と AT_HWCAP2 を通じてユーザー空間へ報告する。ユーザー空間のプログラムはこれ以降、ハードウェア能力に応じてコードパスを振り分けられる。カーネルには V ベクトル拡張サポートが追加され、bounce buffers が実装され、RISC-V の高度割り込みアーキテクチャがサポートされて imsic と aplic の2つのドライバが新設され、Sstc タイマ拡張サポートが加わった。同一バージョンでは Loongson ポートも引退した。

RISC-V ディストリビューションにとって、hwcap の報告はあらゆる単点最適化よりも基礎的な施設である。これがなければ、ユーザー空間はコンパイル時に推測した分岐しか持てない。AIA と Sstc の実装は、このボードの割り込みとタイマのパスが旧来の割り込みコントローラの想定から脱却し始めたことを意味する。

5. まとめとトレンド観察

1. 玄鉄の今回の情報量は「受賞」ではなく「名簿」にある。 C950 の受賞は予想通りであり、真の増分は同じリスト上で10款の顧客チップが C908 から E902 まで4つの中核グレードをカバーし、近接メモリ計算、産業用 SoC、クラウド推論、Wi-Fi ルータ、再構成可能 AI、ディスプレイドライバの6市場にまたがっている点である。これは玄鉄の収益構造が「少数の大口顧客にコアを売る」から「グレード別に展開するロングテール」へと転換したことを示しており、60億個と400社の顧客はこの構造の自然な結果である。同日 repos 側の玄鉄はゼロプッシュで、ニュース側の密集とは対照的である——製品ラインが成熟した後、公開リポジトリはもはや主要な観察窓口ではなくなる。

2. 香山のこの日の作業の重心は「機能追加」ではなく「バグ探し」だった。 9件のコミットのうち6件がfixであり、そのうちCBOオペコードがOR演算によって誤ってcbo.zeroに統合された件は、データをサイレントに破壊しうる重大なデコード欠陥である。StoreQueueと非アライメント前送りの4件は、特定のインターリーブでのみ発生する境界条件に集中している。こうした問題に共通する特徴は、ベンチマークや通常のリグレッションでは発見できず、形式手法や的を絞った刺激に頼るしかないことだ。香山をプロトタイプチップに使うチームにとって、これは一つのことを思い起こさせる。検証への投資は、機能拡張のスピードに追いつかなければならない。特にCBOやマトリックスといった新しい拡張ではなおさらだ。

3. openRuyiがRuyiAIコンポーネントをディストリビューションに取り込んだことは、このスタックが「プロジェクト」から「製品」へ変わる分界线である。 TileLang、TritonのRuyiAIパッケージ、そしてbuddy-mlirがSPEC形式でリポジトリに入ったことは、ユーザーがドキュメントに従ってソースをビルドするのではなく、パッケージマネージャ経由でインストールできることを意味する。同じ日にカーネルのdebuginfoサポートが補完されたことで、オンラインのパフォーマンス問題におけるスタックトレースが初めて利用可能になった。この二つの出来事が同じ日に起きたことは、同じ方向を指し示している。このディストリビューションは「動かせること」だけでなく「運用可能性」を補っているのだ。

4. revyosが一度に20件の設定をマージしたことで、K3のプラットフォームサポート範囲は明らかに広がった。 UFS、ディスプレイコントローラ、USB3とType-Cの一式、奕斯偉EIC7700のネットワークポートとpinctrl、さらにlinuxboot設定とCIのクロスコンパイルパイプラインは、このディストリビューションが「ボードが起動できる」段階から「筐体全体の周辺機器が揃い、変更が検証可能」な段階へ進んでいることを示している。特にlinuxbootは注目に値する。これはファームウェア方式でカーネルをロードする一类のデプロイシナリオに対応している。

5. セキュリティ分野の論文と買収が同じ日に現れたのは偶然ではない。 一方では4つの機関が4種類のランダム化キャッシュを同一のRISC-VマルチコアSoCに実装して横断評価を行い、他方ではCodasipが汎用コア事業を売却してCHERIへ舵を切った。この二つの線が語っているのは実は同じことだ。RISC-Vの汎用コアはすでに価格競争に入っており、プレミアムを語れるのはセキュリティと専用化である。国内でRISC-Vに取り組むチームにとって、この判断はどんなベンチマークよりも記憶に値する。

局限性説明

今号はニュース側がやや薄く、Google News はウィンドウ内でスポーツ試合ライブ配信系のスパム記事に大面積で汚染され、複数組のクエリが返す上位 100 件はほぼ同一の SEO ページの束であったため、タイトルパターンにより一括除外した上で人手による照合を行った。GitHub 組織レベル API の匿名レート制限が中盤で枯渇し、GEM5、llvm-project、CORE-V と openRuyi のコミットはリポジトリコミットフィード（Atom）によるフォールバックに切り替えたため、一部組織の全量プッシュをリポジトリごとに展開できなかった；CORE-V のプッシュは検証の結果、非デフォルトブランチに属し、メインブランチにはウィンドウ内コミットなし。会員公式サイト巡回の 68 社の取得失敗は国内サイトと JavaScript レンダリングが必要なページに集中しており、今号の結論には影響しない。
