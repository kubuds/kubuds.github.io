今日の重点：進畳時空が RVISA 仮想 ISA 仕様の作業草案をオープンソース化、初回に IME/VME/AME の三組のマッピングと blocked MMA を追加（11-04 リポジトリ作成、11-05 コミット）

進畳時空（SpacemiT）は GitHub 上に新リポジトリ spacemit-com/rvisa を開設し、RVISA（RISC-V Virtual ISA、RISC-V 仮想命令セットアーキテクチャ）を提案した。RISC-V のスカラー、ベクトル、行列計算のために仮想命令記法のレイヤを定義するものである。リポジトリは 11 月 4 日に作成され、11 月 5 日に 1 日で 3 件の実質的コミットが Push された：まず MkDocs ドキュメントサイトと Pages 公開フローを導入し、次に RVISA 記法のサンプルソース形式と初回の IME/VME/AME マッピングを追加し、最後に PR #2 で「プログラマが表現可能な」tile レイアウトとブロック行列積（blocked MMA）を定義した。現在の仕様バージョン番号は 0.2.0。

RVISA の位置づけは比較的明確に書かれている。それは意図的に NVIDIA PTX の上、cuTile の下に立っている。上から見れば、特定のフロントエンド言語に縛られず、ソース言語フロントエンドの実装は明確に本バージョンの範囲外とされている。下から見れば、特定チップの命令エンコーディングを直接規定するのではなく、「ターゲットマッピング」をバージョン化された profile とし、どのレジスタクラス、レジスタグループ、命令シーケンスへマッピングするかを項目ごとに宣言し、その profile に対応する上流リビジョン番号と検証証拠を付す。記法の形式は RVV Intrinsics のやり方を参照して、型付き操作、オペランドの役割、レジスタグループ制約を表現し、tile は一次元から N 次元まで、reshape と軸置換は要素位置を保持しなければならず、レイアウトは線形レイアウトから導出される。

それが何を解決しようとしているかを最もよく示すのは「可表現性要件」の項目である。RVISA の tile 計算に対するあらゆる最適化は、プログラマが記法レベルで書き出せなければならない。この制約が狙うのは、行列拡張の実装時によくある失敗の仕方そのものである——コンパイラがこっそりとベクトル化の一式をやってのけ、プログラマはそれを見ることも変更することもできず、チップを変えれば書き直しになる。RVISA はこの層を明示化し、同じ記法の断片が異なる実装上で異なるマッピング profile を通るが、セマンティクスは一貫に保たれるようにしようとしている。

明確にすべきは成熟度である。規範状態ファイル自体に、これは working draft であり、RISC-V International の承認済み規範ではないと明記されている。コアモデル、型とオペランド規則、tile レイアウトと最適化、主要操作のシグネチャは具体的な契約が示されているが、ターゲットマッピングアーカイブはドラフトとして登録されているのみで、実装一貫性の証拠はまだ確立されていない。MLIR dialect は TBD と記載されている。参照負荷は .rvisa 記法のソース形式のみで、コンパイル・実行はできない。実行可能な一貫性ツールも同様に TBD である。リポジトリには他に RFC 0001 から 0003 までの三つのドラフトがあり、それぞれ命令とレジスタマッピング契約、コア型と操作契約、プログラマが表現可能な tile レイアウトをカバーしている。

今日の産業座標に置いて見ると、これは同じバッチの Quintauris が MCU 側で行っていることと同じ論理の二つの現れである。オープン命令セットがもたらす断片化は、最終的にある層の安定した「ソフトウェアターゲット」によって収束されねばならない。MCU 側はバイナリ互換性と割り込みセマンティクスで収束し、AI 行列側は仮想記法とマッピング契約で収束する。違いは、EM-Altair の背後には車載規格と組み込みの大手六社の合弁会社があるのに対し、RVISA は現在単一ベンダー主導の working draft であることだ——それが上流の行列拡張の議論に受け止められるかどうかは、今後誰かが IME、VME、AME の三ラインの実装証拠をあのマッピング表に埋めるかどうかにかかっている。

今日の重点：Quintauris が EM-Altair をリリース、MCU 級 RISC-V 標準化プラットフォームが RV32IM をベースラインにバイナリ互換を実現（11-03 リリース、11-05 報道）

Quintauris は 11 月 3 日、EM-Altair をリリースし、マイクロコントローラ級 RISC-V システム向けの標準化組み込みプラットフォームと自称した。それは新しいコアを定義するのではなく、「準拠実装が一貫して示さなければならない」ハードウェア、ファームウェア、ランタイム要件の一式を定義する。ISA profile、特権アーキテクチャ、起動とランタイムサービス、セキュリティサービスの四層で、ベンダーはそれぞれマイクロアーキテクチャを実装できるが、ソフトウェアが向き合うのは同じターゲットである。同社最高製品責任者 Angel Berrio Moreno の表現は「同じバイナリ、同じ割り込み動作、同じセキュリティ前提」である。

具体的な仕様では、EM-Altair は RV32IM をベースラインとし、境界の明確な必須拡張と任意拡張の一组を備え、割り込み、アトミック操作、CSR 動作、メモリ順序を固定する。動く標的として残すのではない。割り込み部分は有界かつ高スループットのアーキテクチャを規定し、ハードリアルタイム負荷に向ける。分離は PMP でマシンモードと任意のユーザーモードをカバーし、信頼できるコードと信頼できないコードを分ける。セキュリティ実践は ASIL-B 相当要件に整合し、ファームウェア完全性とデバイス保護のためにセキュリティフックを予約する。対象シナリオは率直に書かれている。ボディエレクトロニクス、ゾーン・コックピットコントローラ、EV エネルギー管理、さらに産業制御ループ、IoT センシングノード、ウェアラブルである。

付属ツールは QNTAF で、Quintauris 自身の検証・認証フレームワークである。公式説明によれば、ベンダーはクラウド、シミュレータ、FPGA の三類ターゲットでベンチマーク、一貫性、セキュリティのテストスイートを実行でき、これらのテストを CI/CD に接続し、認証に必要なトレーサブルな産物を生成できる。規範とツールは SoC ベンダー、RTOS 開発者、OEM 向けに公開される。Quintauris はボッシュ、インフィニオン、Nordic、NXP、クアルコム、STMicroelectronics によって 2023 年に合弁設立され、profile、参照アーキテクチャ、ソフトウェアコンポーネントの三つを行う。

このニュースは 11 月 4 日のインフィニオンによる AURIX RC1 発表と併せて読む価値がある。インフィニオンは Quintauris の創業メンバーであり、AURIX RC1 は AURIX と TRAVEO T2G の二製品ラインを同じ RISC-V 基盤に統合する。そして EM-Altair が提供するのはまさにこの基盤の上にある共通実行環境である——チップ廠が実装を行い、合弁会社が一貫性を行い、RTOS とコンパイラは一つのターゲットに一度適応するだけでよい。国内で車載規格と産業向け RISC-V に取り組むチームにとって、これは二つのことが同時に起きていることを意味する。基礎ソフトウェアの敷居は下がり（AUTOSAR、RTOS、ツールチェーンを各社が作り直す必要はない）、参入の敷居は上がる（顧客は「ある profile に適合するか」で問うてくる）。

これらのパッケージは個別バラバラのものではなく、LibreOffice の各文書形式インポートフィルタが依存する同一ファミリーのライブラリ（librevenge ファミリー）とその基盤データ構造依存である。同一秒に一括で着地したことは、散発的なパッケージ補充ではなく依存関係クロージャの収束を行っていることを示す——オフィススイート全体の導入に向けた布石か、あるいは既存ソフトウェアスタックのビルド依存を一時的な回避から正式なパッケージングへ切り替えているかのいずれかである。なお、openRuyi 公式サイトのニュースページは最新でも2026年10月の2本（Ruyi Firmware ファームウェア方案、RISC-V エコシステム公共インフラ）のままで、11月版は未リリースであるため、本日のこの項目はリポジトリ側の進展にとどまり、ディストリビューションリリースとして書くことはできない。

香山 XiangShan が MissQueue の投機的プリフェッチ下での store マージを修正、GEM5 の6件は評価基盤に集中（11-05）

香山メインリポジトリは本日1件：プリフェッチミスが投機状態にあるとき MissQueue が依然として store をマージしてしまう問題を修正（#6842）。これはパフォーマンス変更ではなく正確性の修正である——store がまだ確定していないプリフェッチとマージされ、プリフェッチがキャンセルされると、書き戻しデータの帰属が誤ることになる。

GEM5 側は6件で、方向は明らかに評価インフラ寄りである。google trace と cbp trace を CI に接続し（#1272）、Fetch Block Size の統計 PMU を追加し（#1291）、SPEC06 の RVV checkpoint profile を更新してスカラー浮動小数点部分を整合させ、週次性能タスクに任意スイッチを追加し（#1300）、ハードウェアプリフェッチアルゴリズムの綜述ドキュメントを1本追加し（#1302）、さらに cpu-o3 で「最も古い同周期 squash」を用いて resolve 入力をフィルタする（#1282）。

これら2件と riscv100.top における10月以来のランキング面の変化を合わせて見ると、香山のこのラインの最近の動きの重心は「まず測定方法を固定する」ことにある。checkpoint profile はどの負荷区間を再現するかを決め、trace はどの粒度まで追跡できるかを決め、PMU は性能数値を分解して説明できるかどうかを決め、週次性能タスクはそれらの数値がどれくらいの頻度で出るかを決める。スコアは再現可能な測定方法の上に立ってこそ比較価値を持つ。

P4 Launcher が ESP32-P4 上でアプリをロード可能な PC ライク体験を実現、21 個の PAPP アプリ（11-05）

開発者 Gil Tal 氏が P4 Launcher をリリースした。タッチスクリーン付き ESP32-P4 開発ボード向けのオープンソースアプリケーションプラットフォームである。起動すると直接独自のインターフェースに入り、アプリは .papp ファイルとして microSD カードに保存され、起動時に PSRAM にロードされる。そのためアプリの追加・削除はカードにファイルをコピーするだけで済み、ファームウェアを再書き込みする必要も、デバイスを再起動する必要もない。現在 21 個の PAPP アプリがあり、エミュレータとゲームが中心である。Neo Geo と Atari 2600 のエミュレータ、Doom、Quake、Duke Nukem 3D、OpenTyrian、さらに時計とファイル管理がある。

実装上、インターフェースは LVGL をベースにし、コンポジタが UI を異なる解像度にスケーリングする。オーディオエンジンは最大 8 チャンネル、4 から 192kHz をサポートする。最大 4 つの入力デバイスを接続してマルチプレイが可能で、PS3 と任天堂のコントローラをサポートする。ファームウェアは microSD または GitHub から更新でき、新しいバージョンが起動しない場合は自動的にロールバックする。プロジェクトはさらに SDK を提供し、開発者が独自の PAPP アプリを書けるようにしており、2 層の互換レイヤを備える。1 層は odroid_* インターフェースを再実装し、1 層は旧 PAPP v1 サービスデーブルを実装する。後者こそが Doom、Quake といった古いコードが元のグルーレイヤで動作できる理由である。コードは ESP-IDF v5.5.2 をベースにし、Guition の 4.3 インチと 7 インチボード、および M5Stack Tab5 に適合済みである。

この種のプロジェクトの価値は「ゲームができる」ことではなく、アプリのパッケージング、ロード、更新、ロールバックという一連の取り決めを MCU 上で動作させた点にある。ESP32-P4 は Espressif の RISC-V 高性能モデル（デュアルコア HP に LP コアを加える）であり、PSRAM 帯域、ディスプレイ、オーディオサブシステムはまさにこの種の負荷の圧力点である。成熟したアプリケーションコンテナの取り決めは、エミュレータをもう1つ動かすことよりも、プラットフォームの可用性をよく示す。

進畳 manipulation コンポーネント：デバイス独占、到達判定、タイムアウト、故障ロックをデバイスセッションに集約（11-05）

manipulation は進迭ロボット SDK 内のマニピュレータ制御コンポーネントで、「マニピュレータとエンドエフェクタの統合制御」を実現します。デバイス設定でハードウェアを選択し、同一のコマンドセットまたは C++／Python インターフェースで動作を指令し、運動学、ハンドアイキャリブレーション、デバイスツールを提供します。現在3種類のドライバを備えています。ソフトウェアシミュレーションの mock_device、松霊 Nero 7軸に対応しオプションで Revo2 右ハンド（Revo2 は位置フィードバックなし）を選択できる agx_nero_revo2、5軸でオプションの純正グリッパ付き、サーボキャリブレーションツール付属の so101 です。

そのアーキテクチャのトレードオフは明確に記述されています。C++ アプリケーションはコンポーネントライブラリを直接リンクし、プロセス内で DeviceSession を使用します。コマンドラインと Python アプリケーションは DeviceClient を経由し、これがローカルプロセス manipulation-device serve を起動して JSONL でリクエストを送信します。YAML ポイントタスクは manipulation-device run で実行されます。デバイスセッションはデバイスの排他制御、到達判定、キャンセル、タイムアウト、故障ロックを統一的に処理します。ドライバ層は型番プロトコルと単位換算のみを担当し、運動学とハンドアイキャリブレーションは device.yaml と descriptions/ からモデルを取得し、型番をハードコードしません。新しいデバイスを接続するには Arm と EndEffector を実装して登録するだけです。

最も記録に値するのは「コンポーネントは自動で有効化せず、自動でエラークリアせず、自動で原点復帰せず、自動でリトライしない」という部分です。具身智能プロジェクトで最も手を抜きやすいのはミドルウェアに人間の代わりに判断させることですが、この4つが自動で行われてしまうと、問題発生時に現場の人員は判断の根拠を失います。安全境界をドライバ層ではなくセッション層に置くことは、ロボットミドルウェアにあるべき自制です。

dice_arena が K3 と Nero 7軸と Revo2 器用ハンドでサイコロゲームの全チェーンを走破（11-05）

dice_arena は同じ SDK 上の総合デモです。視覚によるカップ把持、カップを振って置く、ハンドアイキャリブレーション、サイコロ認識、音声アナウンス、ウェブゲーム。ハードウェアリストは具体的に記述されています。SpacemiT K3 開発ボードをメインコントローラとし、松霊 Nero 7軸マニピュレータを USB-CAN アダプタ（SocketCAN、1Mbps）経由で接続し、末端に Revo2 右手器用ハンド（6つの制御チャネル、マニピュレータとコントローラ接続を共用）を装着、カップ把持とキャリブレーションに Intel RealSense D435i、サイコロ認識に上方撮影の USB カメラ（デフォルトはロジテック C920、MJPEG）、さらに ChArUco キャリブレーションボード、スピーカ、緑色のカップを備えます。

ソフトウェアチェーン上では、dice-arena serve が映像転送、ローカル音声、ゲームバックエンドを起動し、バックエンドはステートマシン（ルール説明、カップ把持、カップ振り、カップ置き、視覚判定、結果ジェスチャー、HOME 復帰）を実行し、スロットごとに各コンポーネントを呼び出します。カップ把持は CupApplication が RealSense 画像でカップ本体を認識し、逆解を求めパスを検査し、動作は manipulation の DeviceClient 経由で送信されます。認識は vision_yolov8_objdetect が SpacemiT EP 上で推論し、映像は RTSP で MediaMTX に送られ、ブラウザは WebRTC 経由で再生します。音声は tts_moss_nano がローカルの MOSS-TTS を呼び出して合成し、ボード側の PipeWire 経由で再生します。

本当に価値があるのは失敗処理です。タスクポリシーライブラリ libcup_task.so が C ABI でフェーズ順序を検査し、動作送出後に失敗すれば即座にロックし、手動処理が必要な状態を task_state.json に書き込み、プログラム再起動後も現場の人員が処理を終えて dice-arena reset を実行するまで動作を拒否します。具身智能デモで最も省略されやすいのがこのステートマシンであり、まさに量産時に最も省略できない部分です。

humanoid ラインが立ち姿勢ポリシーとナビゲーションを補完：LingLong SuperMimic と G1 の RGBD SLAM/Nav2（11-05）

humanoid_linglong は本日2件：#22 で LingLong の SuperMimic 立ち姿勢ポリシー設定を追加、#21 でグリッパモデルと操作系タスクシーンの構築を補完。前者は学習済みの立ち姿勢ポリシーを設定体系に接続するもので、後者は把持側のモデルとシーンを補うもの——一方は「立てる」ことを、他方は「掴める」ことを担います。

ros2_humanoid は同日1件、ヒューマノイドプラットフォーム G1 に RGBD SLAM と Nav2 ナビゲーション設定を追加。11月4日の同種コミットと比べ、今回は完全な2セットの設定をまとめてリポジトリに投入しており、単点のパラメータ調整ではありません。立ち姿勢ポリシー、ナビゲーションスタック、グリッパシーンの3つが同じ午後に並行して進んでいることは、このラインが基礎能力を補完しているのであってデモ動画を積み上げているのではないことを示します——ヒューマノイドロボットが本当に詰まるのは、たいてい立ち姿勢の安定性と自律移動の2つです。

5. まとめとトレンド観察

本日は2本の主線がある。1本は抽象層、もう1本は標準化であり、同じ問題に帰着する。

進畳時空の RVISA は AI マトリクス側で仮想命令記法の層を提示し、「プログラマが表現できる最適化」をハード制約として書き下し、さらにバージョン化されたマッピング profile で IME、VME、AME というなお進行中の3種のマトリクス拡張に対応させる。Quintauris の EM-Altair は MCU 側でバイナリ互換の実行環境を提示し、割り込み、アトミック、CSR、メモリ順序を、準拠実装が必ず従うべき一連の振る舞いとして固定する。両者はいずれも、オープン命令セットがもたらす断片化を誰が収束させるのかという問いに答えている。チップメーカー各社に仕様をそれぞれ解釈させるのではなく、仕様と実装の間に安定したソフトウェアターゲットの層を挿入するのである。違いはガバナンス構造にある。一方は6社の大企業による合弁会社であり、他方は単一ベンダーのワーキングドラフトである。

国内ベンダーの動きの重心は引き続き「チップとボード」から「コンポーネントと仕様」へ移っている。進畳は1日のうちに RVISA 仕様、ロボット SDK の3リポジトリ、K3 のロボットアームマニュアルを同時に進めた。算能はピーク性能ではなく2コアと3コアのエンドツーエンド負荷試験の数値を示した。紫荊は「エコシステム普及」を申請可能な事例に仕立てた。これら3件の共通点は、より高いパラメータのチップをもう1つ出すことではなく、「他者が使いこなせるかどうか」という側を補っていることにある。

車載は引き続き最大の戰場であり、本日は3つの層が同時に進む局面が現れた。チップ層（Infineon AURIX RC1、11-04）、プラットフォーム仕様層（Quintauris EM-Altair）、エコシステム事例層（紫荊 M100 の中国芯模範事例選出）。3層は競争関係ではなく、同じ産業チェーンの異なる位置で同じことをしている。すなわち、オープン命令セットを納品可能な車載製品に変えることである。

評価側は引き続き「まず測定法を固める」動きが続く。GEM5 の本日の6件のうち5件は checkpoint、trace、PMU、週次性能タスクといった基盤的なものであり、riscv100.top の昨日の比較ビューと本日のランキング表示の後退も同種の現象である。ランキング表示はまだ整理期間中であり、数値そのものよりも数値の比較可能性の方が注目に値する。

補足観察（riscv100.top と会員公式サイト巡回）
