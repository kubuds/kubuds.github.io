今日の重点：達磨院玄鉄が XL-300 スループット型インターコネクト IP を発表、8 コア非同期接続に 32MB 設定可能 L3 を搭載（11-12）

IT之家が 11 月 12 日午前に報じたところによると、アリババ達磨院傘下の RISC-V ブランド玄鉄（XuanTie）が高スループットキャッシュコヒーレントインターコネクト IP 設計 XL-300 を発表した。報道が示した仕様は次の通り：最大 8 コアの非同期接続をサポート、データビット幅 256bit、L3 Cache は最大 32MB まで設定可能、8 コア同時線形度は 90% 以上、帯域上限は前世代 XL-200 比で約 2 倍。新たに追加された Direct Memory Transfer サポートが個別に言及され、その役割は従来のパスを迂回し、大容量 L3 と高いバス遅延がもたらすスループットのボトルネックを突破することにある。駆動之家、鳳凰網科技、新浪科技、搜狐が同日に同一の消息を転載し、内容は一致しており、いずれも IT之家の口径である。

このニュースの重みは単一のパラメータにあるのではなく、「インターコネクト IP」という位置にある。RISC-V はこの数年、シングルコア性能、ベクトル・行列拡張における進展は検証可能なものになっているが、複数のコアを組み合わせて 1 つの使える SoC にするには、キャッシュコヒーレントプロトコル、コア間帯域と遅延、L3 の容量とパーティション戦略——この部分はかつて Arm と x86 エコシステムが長年の反復で積み上げてきた堀であり、国内 RISC-V サーバチップがシリコン後にもっとも問題を露呈しやすいところでもある。玄鉄が XL-300 の 3 つの指標（8 コア非同期接続、32MB L3、90% 線形度）を真っ先に掲げたことは、まさに「マルチコアが本当にマルチコア性能を出せるか」というもっとも素朴な問いを指し示している。8 コア同時線形度 90% とは、8 番目のコアがもたらす限界収益が依然として 1 番目のコアの 9 割あることを意味し、この数字はピーク帯域よりもコヒーレントプロトコルとバスアービトレーションの実力をよく物語っている。

タイムラインを明確にして、旧製品を新製品と読み違えないようにする必要がある。XL-300 は初登場ではない。今年 3 月の C930 深掘り記事の中で、玄鉄の技術責任者はすでにこれをフラッグシップサーバーコア C930 と組み合わせる最強のインターコネクト IP として挙げており、当時の説明はシングル Cluster で最大 8 コア、L3 最大 23MB、XL-200 比で周波数 20% 向上かつ帯域倍増、面積はわずか 5% 増というものだった。さらに遡ると、2025 年 2 月の玄鉄エコシステム大会では、XL200 はまだ「より大規模で高性能なマルチクラスタ一致性インターコネクトを提供予定」という研究開発計画に過ぎなかった。つまり、XL-300 の位置づけは C930 世代のサーバー級 IP の伴走インターコネクトであり、本期の報道でもたらされたのはより完全な対外仕様の開示である。

二つの説明の差異は記録に値する。第一に、L3 容量：3 月の説明は最大 23MB、本期の報道は 32MB である。両者は異なる構成グレード（シングル Cluster とマルチ Cluster、あるいは異なるプロセスライブラリ下の SRAM 容量）の可能性もあれば、仕様が反復で引き上げられた可能性もある。公式は照合可能な仕様書をまだ公開しておらず、本刊は二つの独立した説明を並記し、一方で他方を上書きすることはしない。第二に、本期の報道は「リリース」を用いており、「量産」や「ライセンス供与の実現」ではない。これは 3 月の「すでに C930 と組み合わせ済み」という表現と矛盾しない——IP の対外リリース、顧客へのライセンス供与、シリコン上での検証は三つの異なる段階であり、報道自体はライセンス供与先の顧客数を開示していない。

産業観察者にとって、より価値のある問いはこの路線が次にどこへ向かうかである。玄鉄の XT-Link シリーズは 2024 年 7 月の XL100（初のキャッシュ一致性マルチ Cluster インターコネクト、8 から 32 コアへの拡張、ビッグ・リトル対応）から XL200、さらに XL300 へと歩み、そのペースはおおむね一年一代であり、各世代の力点は「接続できるかどうか」から「どれだけ速く接続できるか」、さらに「大容量 L3 下でのスループット効率」へと移っている。この経路は C930 の SPECint2006 15/GHz 級のシングルコア性能と伴走関係にある：シングルコアが強いほど、インターコネクトの帯域と一致性への要求は高くなり、そうでなければマルチコアはボトルネックを実行ユニットからバスへ移すだけである。国内でサーバーや高性能 SoC を手がけるチームが玄鉄コアを採用する場合、インターコネクト IP の選択可能範囲とライセンス条件が、実際に 32 コア以上の機種を実現できるかどうかを決める。

1. オープンソースコミュニティとソフトウェアエコシステム

香山昆明湖 V3 の三コミット：ROB 拆分機能とデバッグバッファ、FP 発射キューを topdown カウンタへ接続、BJU に isRVC メタデータを補完（11-12）

香山昆明湖 V3 ブランチは調査期間内に三つのコミットを着地させ、それぞれ三つの方向に属する。第一のコミットはリオーダーバッファ（ROB）の構造ガバナンスである：従来、ROB は各スロットに対して無条件に完全な入隊 uop を一份保存しており、それを debug_microOp フィールドに置いていた。名前はデバッグ用だが、例外処理と VLS 処理もそれを読んでいたため、通常の RTL がデバッグ専用であるべき構造に依存してしまっていた。変更では RobSlotInfo を導入し、通常の RTL が本当に必要とする三つのフィールド（commitType、fuType、fuOpType）のみを slotUopBuf に保存し、デバッグ用の完全なコピーを切り離した。この種の変更の利益はサイクル数になく、面積、タイミング、そして今後の拡張コストにある：余分なワイドビットベクタが ROB 内に数世代にわたって居座り、フィールドを一つ追加するたびにそれも拡大する必要があった。

第二のコミットは浮動小数点発射キューと ROB の topdown カウンタを接続する：浮動小数点の発射活動とキューの状態を topdown コレクタへ報告し、発射キャンセルの発生源を含む。整数と浮動小数点の発射キューの状態を併せて ROB ヘッドの分類に供給し、浮動小数点の已発射 uop を発射カウントに計上する。キャンセル発生源の履歴はすべてのエンコード源に応じて長さを割り当て、ROB ヘッドが発射キャンセルとして分類された場合にのみキャンセル時刻を更新する。第三のコミットは修正である：JumpUnit は予測誤りやバックエンド障害時にバックエンドリダイレクトを生成するが、リダイレクトバンドルをクリアしてしまい、io.in.bits.ctrl.isRVC を redirect.isRVC へ代入していなかった。その結果、圧縮ジャンプ命令（c.jr など）のバックエンドリダイレクトで isRVC が false にクリアされ、後続の命令長判定に影響していた。

三つのコミットを合わせて見ると、典型的な「構造ガバナンス + 可観測性補完」の組み合わせである。topdown カウンタの意義は、「パイプラインがなぜ空転しているか」を経験的判断から帰属可能なデータへ変えることにある：フロントエンドのフェッチ不足、バックエンドの発射ブロック、あるいは ROB 満杯によるストールが、それぞれ独立したカウントを持つ。香山のような SPEC と実負荷を走らせるオープンソースコアにとって、ボトルネックを素早く特定できるかどうかが反復速度を決める。一方、ROB 拆分や isRVC 修正のような作業は性能数値を一切生まないが、新機能追加時の変更半径を直接左右する。

openRuyi の五コミット：LLVM 23 を 23.1.5 へ更新、デュアルカーネルパッチと設定リフレッシュ、gcab と OVMF の fwupd サポートをツリーへ導入（11-12）

openRuyi 主リポジトリは調査期間内に5件のコミットを実施し、すべて SPECS ディレクトリに集中しており、時間帯は午前9時13分から11時27分にわたる。1件目は llvm23 を 23.1.5 にアップグレードしたもので、これは今月内における LLVM 23 ブランチのさらなるパッチレベルの追従である。続く2件は同一のコミッターによるもので、それぞれ linux と linux-lts のパッチセットと設定を更新している。ここで注意すべきは「refreshing patchset」と「refresh config」の2つを同時に行っている点で、下流でメンテナンスしている RISC-V パッチ群を新たなベースラインに合わせて再配列し、同時にカーネル設定項目も再調整する必要があることを意味する。このような対になる更新は、カーネル安定版のマイナーバージョン更新後にしばしば発生し、ディストリビューションがビルド可能な状態を維持するための必須作業である。

4件目は gcab ソフトウェアパッケージの新規追加である。gcab は GNOME 陣営の Cabinet ファイル（.cab）読み書きツールで、それ自体は小さいが、依存チェーン上に現れるということは通常、上位コンポーネントがファームウェアやドライバパッケージを処理する必要があることを意味する。5件目はまさにそれを裏付けるもので、ovmf が fwupd のサポートを追加している。fwupd は Linux 上のファームウェア更新デーモンであり、OVMF（UEFI ファームウェア）の層にまで達しているということは、openRuyi が「ファームウェア更新可能」をディストリビューションの機能として作り込んでおり、ユーザーに手動での書き込みをさせていないことを示す。RISC-V プラットフォームにとってこれは見落とされがちだが非常に実用的な要件である。ボードベンダーのファームウェアリリースのタイミングはディストリビューションと同期しないため、fwupd のチャネルがあってこそ、システムを再インストールすることなく BIOS やファームウェアの修正を配信できる。

5件をまとめて見ると、openRuyi はこの調査期間に新バージョンのリリースもなく、大きな機能もなく、「上流のベースラインに追従し、ファームウェア更新の経路を補完する」ことを行っている。これは10月の2つのアナウンス（Ruyi Firmware がオープンな UEFI ファームウェア方案を提供、エコシステム基盤としての位置づけ）と一線でつながる継続である。ファームウェア方案が語るのは「いかにオープンに起動するか」であり、fwupd サポートが語るのは「起動後にいかに継続的に修正するか」である。

difftest 2件：イメージデコードと RAM ロードの分離、gsim ビルドでの tee パイプ削除（11-12）

difftest リポジトリの調査期間内の2件の変更はいずれもエンジニアリング層のものである。1件目はイメージのデコードと RAM ロードの2ステップを分離している。従来はイメージをロードする際、フォーマットの解析とメモリへの書き込みが同一のロジックに結合されていたが、この変更では独立したデコード段階を導入し、「イメージを読み解く」ことと「メモリに載せる」ことをそれぞれテスト可能かつ置換可能にした。差分テストフレームワークにとって、このような分離の価値は、新しいイメージフォーマットを追加する際にメモリレイアウトのコードに触れる必要がなく、逆にメモリモデルを調整してもフォーマット解析に影響しない点にある。

2件目は非常に見落とされやすいビルドの罠を修正している。gsim の生成ルールに gsim-gen-cpp ... | tee gsim-gen-cpp.log と書かれており、Make はデフォルトで -o pipefail を設定しないため、パイプの終了コードは tee のステータスを取ることになり、常に 0 となる。その結果、gsim-gen-cpp がバグや OOM で kill されても、make はそのまま gsim-gen-emu の呼び出しを続け、最後には不可解な SimTop.h not found というエラーで終わる。この変更は内部の tee を直接削除しており、理由は明確に書かれている。verilator.mk はそうしておらず、ログを残したいユーザーはコマンドラインの外側で自分でパイプを追加すればよい。これは「一度直せば後に続く全員の30分を節約する」タイプのコミットである。

日付：2026-11-12　情報源：OpenXiangShan/difftest

Espressif 22リポジトリの一括プッシュ：モジュールライブラリ、映像・音声コンポーネント、チップ errata を同時更新（11-12）

Espressif（espressif）は調査期間内に22のリポジトリでプッシュがあり、調査期間全体で組織レベルのプッシュが最も集中した企業である。リストはいくつかに分類できる。ホスト側とクラウド側には esp-hosted-linux、esp-cloud-common；チップ関連には esp-chip-errata、esp-phy-lib、esp-coex-lib、esp-hal-3rdparty、usb-pids；無線・Bluetooth モジュールライブラリには esp32s31-bt-lib、esp32h4-bt-lib；マルチメディアには esp-video-components、esp-vision、esp-gmf；フレームワークとツールには esp-matter、esptool-js、idf-eclipse-plugin、esp-board-manager、esp-idf-security-dashboard、homebrew-eim；その他に esp-claw（2379スター）、esp-ptp、developer-portal、musl がある。

このような同日の複数リポジトリプッシュは Espressif では常態であり、リリーストレインと上流の同期に属するため、本誌では個別に分割しない。注目すべきはメディアと Bluetooth の2つの支線が依然として拡大している点で、esp-video-components、esp-vision、esp-gmf の3リポジトリが同時に動いていることは、エッジ側のビジョンとオーディオの経路でまだコンポーネントを補完していることを示す。esp32s31-bt-lib と esp32h4-bt-lib が同一バッチに現れているのは、新チップの関連ライブラリが追従しているためである。ESP32-C シリーズ（C2/C3/C5/C6/C61、RISC-V コア）で製品を作るチームにとって、これらのライブラリの更新ペースが、新しいモジュールでいち早く使用可能なファームウェアを入手できるかどうかをほぼ決めている。

2. 製品とエコシステムの動向

spacemit-robotics は調査期間内に2つのリポジトリでそれぞれ1件。ros2_spacemit_vslam は18時21分にコミットされ、タイトルは「spacemit-vslam：ステレオ定位とマッピングアプリの初期化」である。コミットの意味から見ると、これはステレオビジョンの定位とマッピング（SLAM）を起動可能な ROS 2 アプリケーションパッケージにしたもので、単なるアルゴリズムライブラリの集合ではない。ロボット本体を作るチームにとってこの違いは実用的だ。アルゴリズムライブラリなら launch を自分で書き、カメラキャリブレーションと TF ツリーを設定する必要があるが、アプリケーションパッケージならマシンを替えてもパラメータを変えるだけで済む。ステレオ方式は RISC-V 上で特に意味がある。計算量的に LiDAR より安く、単眼より信頼できるが、代償として特徴抽出とマッチングを行う十分なベクトル演算能力が必要だ。

ros2_humanoid は16時47分にコミットされ、「G1 の Nav2 制限とネイティブ歩行を整合させる」修正である。Nav2 は ROS 2 のナビゲーションスタックで、独自の速度・加速度上限パラメータを持つ。人型ロボットのネイティブロコモーションコントローラにも独自の制限がある。2つの制限が不一致のときの典型的な症状は、ナビゲーションがパスを計画しても下層がそれを実行できないことだ。その場で滑るか、急停止するかである。この種の修正はどのデモ動画にも現れないが、人型ロボットが実現場でナビゲーションタスクを連続実行できるかどうかを決める。

2つのコミットを合わせると、進畳のロボット路線が「デリバリー可能」へ向かっていることが分かる。一方で知覚側のアプリケーション化パッケージを補い、もう一方で制御側のパラメータ整合性を修正している。北京が11月11日に公布した具身智能（エンボディドインテリジェンス）3カ年行動方案は「平均故障間隔2000時間超」を指標に盛り込んだが、こうした故障のかなりの割合はパラメータ不整合による度重なる非常停止と過熱に由来し、ハードウェアの破損ではない。

3段階の参考設計から見る Physical AI の演算力レイヤリング：リアルタイムコア、ベクトルコア、NPU がそれぞれの持ち場に（11-12）

今日の2件の製品ニュースを並べて見ると、ちょうど対照表を構成する。MIPS の3段階参考設計は、具身智能の演算力を3層に分解している。Actus-1 は2つのリアルタイム RISC-V コアと512ビットのベクトルユニットでモーター制御と TSN 通信を担い、重視するのは決定性である。Acies-1 は8コア RVA23 とベクトル行列拡張で50 TOPS、10W を実現し、重視するのはワットあたりのスループットである。Aegis-1 はマルチコア ARC-V で Linux とエージェント負荷を動かし、さらにセキュリティプロセッサと NPU を組み合わせ、重視するのはシステム編成と認証である。一方、SingNova は別の道を進む。デスクトップ機1台に12コア RISC-V とデータフローアーキテクチャを詰め込み、公称256 TOPS、128GB ユニファイドメモリ、128路のビデオデコードを備え、「1つの大きなボックスですべてをカバーする」方式でリアルタイム分析とローカル推論を網羅する。

2つの経路に正誤はなく、デリバリー形態によって決まる。車載や産業制御に取り組む場合、認証と決定性が優先され、たとえ3つのチップに役割を分担させても、Linux 側の1回のスケジューリングの揺らぎがモーターループに影響することを許容できない。セキュリティやエッジ動画分析に取り組む場合、カメラ台数密度と総保有コストが優先され、1台のボックスが128路のカメラを接続できることは、3つのチップがそれぞれ優れていることよりも説得力がある。真の分水嶺はソフトウェアである。3段階方案はベンダーに3つのツールチェーンと3つのデバッグ手法をすべて維持することを要求し、単一ボックス方案は1つのチップ上の異種スケジューリングが十分に成熟していることを要求する——どちらの道もソフトウェアでコストを払うが、払う場所が異なるだけである。

国内 RISC-V 供給に対して、この対照表が与える示唆は「1つのチップですべての問題に答えようとしないこと」である。進畳 K1 は低消費電力汎用路線を進み（Start9 ルーターはその筐体としての実装である）、算能 SG と BM シリーズはサーバーとエッジ推論を進め、芯来 N1000／NI1000 はリアルタイムコアとベクトル行列コアをカバーし、玄鉄 C930 と XL-300 はサーバー級マルチコアを進む——各段階に対応する製品は見つかるが、欠けているのはこれらの段階を筐体要求に合わせて組み上げ、認証まで完了するインテグレーターである。北京方案の「重要部品の配套率60%超」という指標が試すのは、まさにこの統合能力である。

5. 総括とトレンド観察

1. インターコネクト IP が脇役から RISC-V サーバー化の主線へ。 玄鉄 XL-300 が今回開示した仕様で最も問題を説明しているのは、32MB L3 ではなく「8コア同時実行の線形度90%以上」である——これは実際にマルチコア負荷を走らせた者でなければ出せない指標である。シングルコア性能はマイクロアーキテクチャに依存し、マルチコア性能はコヒーレンシとバスに依存する。国内 RISC-V はシングルコアで既に SPECint2006 15/GHz という水準で対話できる。今後2〜3年の勝負手はマルチコア拡張効率とシリコン後安定性に落ちる。XL100 から XL300 へ1年1世代というペースは、この路線が単発デリバリーではなく製品として取り組まれていることを示す。

2. 筐体の実装は開発ボードから消費財へ移行しつつある。 Start9 の RISC-V ルーターは300ドル、8コア K1、そして「どのオープンソースを開示しどれを開示しないか」を項目ごとに明記しており、これは成熟したハードウェア製品の書き方である。SingNova は12コア RISC-V とデータフローを128路カメラを接続できるデスクトップボックスに仕上げ、これも同じく筐体思考である。両者の共通点はソフトウェアスタックを自社で維持すること（StartWRT、自研データフローランタイム）であり、もはやある x86 ホストに依存しない。RISC-V が証明すべきは「Linux が動く」ことではなく、「一般ユーザーやインテグレーターに販売するデバイスを支えられる」ことである。

3. オープンソースハードウェアというこの支線は「監査可能」へ向かっている。 Baochip-1x は 22nm、RV32IMAC、公開 RTL と RRAM で「すべてのトランジスタを説明できる」ことを実現しており、市場は小さいが需要は実在する。これは高性能サーバ路線と衝突せず、むしろ RISC-V の物語で最も欠けやすい部分を補っている。すなわち、セキュリティ審査とサプライチェーン追跡が厳しくなる場面では、RTL を読めることのほうがベンチマークスコアの高さより価値がある。

4. ツールチェーンとエンジニアリング衛生がこの日の暗線となった。 difftest が | tee を一つ外したことでビルド失敗が SimTop.h not found に偽装されなくなり、香山はデバッグ用の uop コピーを通常の RTL から切り離し、進迭は漏れて発行されたバージョンに手動チャネルを補い、openRuyi はファームウェア更新を fwupd に接続した——四つの出来事はいずれも性能数値を生まないが、いずれも「次回の変更で支払う代償」を減らしている。エコシステムが成熟しているかどうかは、しばしばこうしたリリースノートに書かれないコミットがどれだけ密かを見ればわかる。
