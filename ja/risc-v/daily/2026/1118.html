今日の重点：賽昉 JH-B100 量産出荷、RISC-V サーバー BMC が顧客完成品に搭載（11-17）

11月17日、賽昉科技は RISC-V アーキテクチャに基づくサーバー BMC（ベースボード管理コントローラー）チップ昉・驚鴻-B100（JH-B100）が量産を達成し、顧客へ出荷したと発表した。公式の説明は以下の通り：同チップは複数のサーバーメーカーおよびインターネット企業の製品導入・審査プロセスを通過しており、これを搭載した顧客のサーバー製品はまもなく量産段階に入る。出荷量、顧客名、生産計画時期はいずれも非公開。

仕様は賽昉公式サイトの製品ページによる：4コア自社開発 RISC-V コア（19200 DMIPS）にコヒーレントなオンチップネットワーク（NoC）を組み合わせ、DDR4-3200 と DDR5-4800 に対応、PFR（プラットフォームファームウェア・レジリエンス）と PROT 機能を統合し、国密 SM2／SM3／SM4、セキュアブート、DICE をサポート。インターフェースにはデュアル PCIe 4.0 エンドポイント、フル機能 eSPI Slave、PECI、I2C／I3C、USB 3.2 Gen1、SGPIO、CAN-FD、IPMB、MCTP、NCSI を含み、2系統の LTPI コントローラーを内蔵してデュアルノード管理をサポート。付属 SDK は Yocto 標準に準拠し、OpenBMC に直接接続可能。応用面は CPU サーバーマザーボードのほか、AI インフラの計算トレイ、スイッチトレイ、冷却液分配ユニット、電源ラックも含む。

このニュースの重みは「性能」ではなく「位置」にある。BMC は計算には関与しないが、サーバー1台につき1個必要で、長らく Arm と 8051 系コントローラが握ってきた。これまで RISC-V はこの位置ではサンプル出荷と検証しかなく、量産納品はなかった。それを突破口に選ぶ論理も明快だ。性能要件はメイン CPU よりはるかに低く、ソフトウェアスタック（OpenBMC、Yocto）は成熟しており、顧客導入時の検証コストも抑制できる。賽昉が示したエコシステムの裏付けは Intel と AMI だ。前者は CRB プラットフォーム上での Intel CPU 管理機能の検証を完了し、後者は JH-B100 の SDK を BMC ファームウェア製品 OneTree に統合した。この2点は既に Intel Connection と滴水湖フォーラムで公表されており、今回は初めて「量産納品」という段階に落とし込まれたものだ。

冷静に見れば、なお観察すべき点がいくつかある。第一に、「まもなく量産入り」は顧客側の表現であり、実際の拡大はシステムベンダーの生産計画次第で、BMC の購買判断は多くの場合メイン CPU プラットフォームに追随する。第二に、賽昉は出荷量を示しておらず、これが小ロット納品か規模出荷かは判断できない。第三に、RISC-V BMC の長期的な試練はファームウェア保守とセキュリティ更新にあり、OpenBMC のコミュニティ支援度や CVE 対応速度は1～2製品サイクルを走り抜けて初めて見えてくる。同じ日、工信部主管メディアと複数の業界メディアがこのニュースを転載し、「十五五」計画の「第5世代縮小命令セットの研究開発と産業化を推進する」項目と併記して報じており、政策文脈と商業的進展を結びつける意図が明らかだ。

openRuyi 19件：OpenSBI を 1.9 に更新、OpenSSL 3.6.5 を導入（11-17）

openRuyi メインリポジトリは 11 月 17 日一日で計 19 件のソフトウェアパッケージコミットを記録した。ファームウェア側では OpenSBI を 1.9 に更新。暗号スタックには openssl-3 を新規追加し 3.6.5 バージョンを搭載、同時に CI ビルドを OpenSSL 優先に変更した。基盤ライブラリでは krb5 を 1.22.3 に更新し、json-c 0.19 下での dnf5 ビルドを修正。デスクトップ側では openruyi-desktop-setup-kde に依存関係の宣言を補った。午後 15 時 03 分の一括分は Python と AI 推論スタックに集中：huggingface-hub 1.32.0、sentence-transformers 6.3.0、xgrammar 0.2.9（セキュリティ修正を明記）、apache-tvm-ffi 0.1.12、click 8.5.1、hf-xet 1.5.2、さらに rust-tokio-with-wasm-proc 0.8 を新規追加。

3点は個別に見る価値がある。OpenSBI 1.9 はファームウェアベースラインの追随であり、新プラットフォームが M モードで起動できるかどうかを左右する。OpenSSL 3.6.5 を導入し CI で優先使用するのは、ディストリビューションが 1.1 系の互換負担から脱却することを意味し、代償として依存パッケージすべての再ビルドが必要になる。xgrammar と tvm-ffi のリポジトリ入りは、「構造化出力」や「TVM インターフェース」といった AI 推論依存がユーザーの pip インストール任せではなく、ディストリビューションの範囲に組み込まれたことを示す。公式サイトのニュースページは最新でも 10 月 19 日の2本（エコシステム基盤、Ruyi Firmware）と 2026.09 リリースのままで、調査期間内に新バージョンはない。

revyos/linux が 7.3.y 設定ベースラインを再整備、プラットフォームパッチ 20 件を一括投入（11-18）

revyos/linux は 11 月 18 日午前 4 時 13 分、20 件の設定コミットを一気に revyos/7.3.y ブランチへプッシュした。20 件のコミット時刻は完全に同一で、作成者日付は最も早いもので 2025 年 12 月まで遡れる。ブランチ再整備後の一括反映であり、一夜で成し遂げた作業ではない。内容はプラットフォームごとに個別有効化：ESWIN EIC7700、UltraRISC DP1000、SpacemiT K3 と K1、T-Head TH1520、Sophgo SG2042／SG2044、さらに Picoheart errata スイッチと汎用オプション群。同時に cross/native ビルド CI、linuxboot 設定、debian_defconfig を新規追加し、パッケージ名規則をメジャーバージョン番号方式に変更した。

設定ファイルを一度に6社のプラットフォームに揃えたことは、RevyOS の位置づけが「あるボード向けのディストリビューションを作る」から「1つのカーネル設定で複数の RISC-V 製品ラインをカバーする」へ変わったことを示している。下流のベンダーにとって、この種の変更の価値は設定変更の少なさにある。新しいボードを手にしたら、まず defconfig に自社 SoC のスイッチがあるかを見る。ゼロから dts を書くよりはるかに速い。リスクもそこにある——同じブランチが6社のプラットフォームの errata と hack を同時に抱えており（コミットには xe ドライバを強制的に DG1／DG2 経由にする这类の workaround が含まれる）、いずれか1社の変更が他社のリグレッションに影響し得る。CI に cross/native の2系統のビルドを追加したのは保険を1つ足したようなものだ。

香山昆明湖：CSR と bundle の命名を統一するリファクタリング（11-17）

香山メインリポジトリは11月17日10時27分、kunminghu-v3 ブランチでリファクタリングのコミットを1件行った。作者は Lemover で、内容は CSR および関連 bundle の命名を標準化すること。純粋なリファクタリングであり機能は変えず、機能凍結後のインターフェース整合性の整理に属する。

説明しておく価値があるのは push とコミットの違いだ。XSCache、NEMU、difftest、GEM5 の4リポジトリはいずれも pushed 時刻が調査期間内に収まっているが、デフォルトブランチのコミット履歴には調査期間内の記録がないため、他のブランチやタグへの push（XSCache では dev-oceanus-draft 系列のブランチが活動中）と判断し、個別の項目としては挙げない。昆明湖 V3 のこの2日間の動き（まずメモリアクセスキューの欠陥、次に命名のリファクタリング）はいずれも「保守性」の線上にあり、性能チューニングとは無関係だ。

CORE-V 2件：RVFI CSR ログのマージと、CVW の依存関係整理の巻き戻し（11-17）

openhwfoundation/core-v-verif は11月17日6時20分に PR #2675（ankit-cybertron による rvfi-csr-logging）をマージし、RVFI インターフェースに CSR ログを追加した。同じ日、CVW はまず PR #2099（uv.lock の依存関係警告を整理し uv 更新を有効化）をマージし、その後コミット1件でそれを全体ごと巻き戻した。

RVFI は RISC-V の形式検証と差分テストの観測口である。各命令の PC、レジスタの読み書き、メモリアクセスを検証器に露出するが、これまで CSR 状態はそこに含まれておらず、特権状態の挙動は間接的な手段でしか比較できなかった。CSR ログを加えたことで、mstatus、mtvec 这类のレジスタの命令ごとの変化を直接検査できるようになり、例外と割り込みの経路の検証に特に有用だ。一方 CVW の巻き戻しは別種のシグナルである——依存関係警告の整理は無害に見えるが、いったんロックファイルと更新ポリシーを変更すると、リグレッション環境の再現性が影響を受ける。だからこそ不確実性を抱えたまま進むより巻き戻す方を選んだのだ。

日付：2026-11-17　情報源：core-v-verif PR #2675、openhwfoundation/cvw

riscv.org ブログ：SC26 期間中の5問インタビュー（11-17）

RISC-V International は11月17日11時40分、「V Questions with…」の新号を公開した。対象は Inspire Semiconductor 最高マーケティング責任者で HPC-AI Society 会長の Doug Norton と、EPCC（英国国立スーパーコンピュータセンター、エディンバラ大学）の上級研究員 Nick Brown。背景は SC26 がその週シカゴで開催されていたこと。記事によれば両者は会場で会えなかったため、インタビューはオンラインで実施し、挿絵は AI 合成のアバターの寄せ集めだという。

取得済みのページ内容から見ると、これは人物インタビューであり製品発表ではない。主題は RISC-V の HPC におけるソフトウェアスタックとエコシステムにある。これをデイリーレポートに入れる理由は「新しいものがある」からではなく、語りの枠組みにある。スーパーコンピュータ年会の期間中、RISC-V 側が出してきたのは依然として人とエコシステムであり、ピーク演算性能の数字ではない。これは国内ベンダーが今月 BMC、ロボット、ディストリビューションで行った実際の動きと対照をなす——両端とも「正面からの演算性能比べ」という題を避けている。

Radxa Linkr が v1.4.2 から v1.6.0 を集中的に公開、プラグインセンターと H.265 エンコードが搭載（11-17）

Radxa のブラウザリモート管理製品ライン Linkr は、11 月 17 日 15 時 2x 分に 4 つのバージョンを集中リリースした：v1.4.2、v1.5.0、v1.5.2、v1.6.0。4 つのリリースの公開時刻は 5 分も離れていない。同日には harness-linkr リポジトリも新規作成され、Initial commit が記録された。4 つのバージョンが同日に現れたのは、リポジトリ公開後に過去のバージョンを一括で追記したように見え、1 日に 4 版を連続リリースしたと読むべきではない。

リリースノートによると、v1.6.0 は H.265 エンコード、カスタム HTTPS 証明書、双方向クリップボード同期（被制御機に Linkrd プラグイン付属の実行ファイルをインストールする必要あり）、720p 180fps の EDID プリセットとウォーターマークスイッチを追加した；v1.5.0 はプラグインセンター（アップロード、インストール、起動停止、アンインストール）、ZeroTier と EasyTier の 2 つのネットワーク構築プラグイン、スクリーンショット OCR、実験的 IPv6 を導入し、Agent API に切り替え制御を加えた；v1.5.2 は FN キー双击による Wi-Fi ホットスポット切り替え、接続帯域に応じた 5GHz または 2.4GHz の自動選択、Radxa Dragon Q8B を映像入力源とした際に解像度を切り替えられない問題の修正をサポートした；v1.4.2 は H.264 WebSocket モードに音声を追加し、Wi-Fi をデフォルトで無効化して消費電力を低減し、実験的タッチ入力を加えた。

これら 4 つのバージョンを続けて見ると、Linkr の方向性は「オーケストレーション可能な帯外管理」である：プラグインセンターが機能拡張を解決し、Agent API が外部呼び出しを解決し、ネットワーク構築プラグインがクロスセグメント接続を解決し、OCR とクリップボードが人をループに含める操作を解決する。リリースノートはハードウェア形態と使用 SoC を開示していないため、本レポートはそのアーキテクチャについて判断を下さない。

Purism 公式プレスリリースが Librem 5 v2 の仕様と納品条件を確認（11-17）

Purism は 11 月 17 日に正式なプレスリリースを発表し、Librem 5 v2 が 8 コア RISC-V プロセッサを採用し、PureOS を実行し、クラウドファンディング価格が 1599 ドルであることを確認するとともに、納品条件を示した：クラウドファンディング終了後約 14 から 15 か月で納品され、開発が進行中であるため、リワードとスケジュールはいずれも保証されない。プレスリリースは同時にエンジニアリング範囲を明確にした：グラフィックス、ペリフェラル、電源管理、アプリケーション互換性のすべてを埋める必要がある。CTO の Jonathon Hall の表明は「RISC-V は未来であり、Librem 5 v2 はこのことを主流ユーザーの手に届ける製品である」というものだった。

進畳時空 xslim：量子化スタックが agent ブランチで 5 コミットを連続プッシュ（11-17）

進畳時空のモデル圧縮ツールチェーン xslim は、11 月 17 日に agent/feat/operator-layer-quantization ブランチで 5 コミットを連続プッシュした（8 時 46 分から 19 時 35 分）。すべて量子化戦略を巡るものである：ユーザーデータに応じたレイヤーごとのキャリブレーション手法の選択、統一された精度計画の解析と検証、融合来源と有効精度境界の検証、予算付き自動混合精度、タスク指標の探索と制御されたローカル fp16。もう 1 つのブランチ agent/chore/add-agent-harness は 11 月 13 日にリポジトリレベルの agent harness とコントリビューションガイドを追加した。

これらのコミットの方向性は「量子化を手書き設定から探索へ変える」ことである：精度予算とタスク指標を与え、どの層にどの精度を使うかをツール自身に決めさせるのであって、層ごとに手作業で表を埋めるのではない。同時に provenance と fused の検証が繰り返し現れることは、実際のモデルで融合オペレータの精度が合わないという痛い目を見たことを示している——量子化後の畳み込みがバックエンドで融合され、実際に有効な精度と設定ファイルに書かれたものが一致せず、検証しなければ「設定は int8、実行は fp16」というサイレントな偏差が生じる。agent ブランチという命名も注目に値する：ツールチェーンが人間向けだけでなく「自動化エージェントに使わせる」ためにコードとスキルを組織し始めたのである。

同日、spacemit-com/onnxruntime は上流の変更を 1 件マージした（EP 優先度によるモデルパッケージ変体の選択）。上流への同期であり、RISC-V 固有の変更には関与しない；xslim のメインブランチには調査期間内にコミットがなく、進展はすべてフィーチャーブランチ上にある。

算能 sophon-tools：se-rag-core が階層化モデル設定と有界フォールバックを補完（11-17）

算能の sophon-tools は 11 月 17 日 13 時 30 分に feat(se-rag-core) を 1 件コミットした：OpenAI 設定の階層化、内蔵ゲートウェイの CF 優先と有界フォールバック（コミット番号 MYS-2924／MYS-292x）。変更は RAG コンポーネントのモデル接続層に集中しており、OpenAI 互換設定を複数層（デフォルト、環境、デプロイレベル）に分割し、優先度順にマージする。ゲートウェイ部分は CF（Cloudflare）回線を優先し、失敗後は限られた回数でフォールバックする。

このコミットの技術的な中身は多くないが、指し示す方向は明確だ：SE シリーズ（SG2042／SG2044 サーバ）上の LLM アプリケーションスタックが運用可能な方向へ進んでいる。階層化設定が解決するのは「同一のコードを開発、テスト、顧客現場で異なるモデルエンドポイントに対応させる」問題であり、CF 優先＋有界フォールバックが解決するのは越境アクセスの安定性である。フォールバック回数は有界でなければならず、そうでなければ一度の障害でリクエストがすべての予備回線に流れてしまう。なお、これはアプリケーション層のツールであり、チップやドライバではない。本レポートがこれを収録するのは、算能がサーバ整機以外に補っているのが「すぐ使える LLM サービス」という部分であることを反映しているからだ。

進迭時空のロボットスタックが Hiking 知覚式運動ポリシーを接続、深度画像は ZMQ 経由でポリシーループへ（11-17）

11 月 17 日 16 時 04 分から 05 分にかけて、spacemit-robotics の 2 つのリポジトリがそれぞれ 1 件ずつマージした：humanoid_common の PR #33「support Hiking perceptive locomotion」と humanoid_unitree_g1 の PR #20「add Hiking perceptive control simulation」、作者は chenzhaoqi。humanoid_common の変更は計 16 ファイル、938 行追加で、内容は以下を含む：Hiking ポリシー適配層（深度エンコード、観測履歴、関節マッピング、モデルチェックサム）、オフスクリーン EGL レンダリングで MuJoCo カメラ深度を ZMQ 経由で発行、RL に入る前に深度メタデータとタイムスタンプと履歴長を検証、オンライン RL ハンドオーバーをサポート（動作履歴の初期化、準備チェック、準備フィードバック）、ハンドオーバー失敗またはタイムアウト時は現在のポリシーを保持、知覚ビルド依存を追加し RL ヘッダファイル変更時にコンシューマを再ビルド。

コミット内容から見ると、このインターフェースは公開されている Hiking 知覚式運動ポリシー（Hiking in the Wild、清華 IIIS と上海期智研究院、Unitree G1 に前視深度カメラ、深度 60Hz、ポリシー 50Hz）に対応する。公式は適配対象の正確な出所を説明していないため、ここではコミット内容に基づく判断とする。エンジニアリング上、記録すべき点は 3 つ：ハンドオーバー失敗時に旧ポリシーを保持することは安全のためのフォールバックであり、ポリシー切り替えの瞬間にロボットが無制御になるのを避ける；モデルチェックサムはポリシーファイルの差し替えやバージョン不整合を防ぐ；ヘッダファイル変更が再ビルドをトリガーするのは、C++ 構造体レイアウトの不整合という問題を踏んだことがあるためだ——コミットコメントには、段階的インストールではソースファイルのタイムスタンプが保持され、RL ヘッダファイルは変わったがキャッシュされたオブジェクトが再コンパイルされず、リンクされた構造体レイアウトが一致しなくなる、と明記されている。

サードパーティのポリシーを交換可能な適配層にすることは、ロボットスタックが「ポリシーエコシステム」へ向かう必经の一歩だ：チップメーカーがすべてのポリシーを自前で訓練することは不可能であり、できるのは知覚入力、ポリシー推論、動作ハンドオーバーという 3 段を標準化し、外部で訓練済みのポリシーを接続すればすぐ動くようにすることである。K3 のようなプラットフォームがこの位置で提供するのは、ベクトルとマルチコア能力、そして MuJoCo と深度レンダリングを動かす余裕である。

5. まとめとトレンド観察

今日の主線はただ一つ、管理面が先に着地したことだ。賽昉 JH-B100 の量産出荷は、RISC-V がデータセンターにおいて「サンプル検証」ではなく「量産出荷」の位置を初めて得たことを意味する。BMC は計算には関与しないが、サーバー1台につき1個必要で、数量は筐体に連動する。その性能要件はメイン CPU よりはるかに低く、ソフトウェアスタックには OpenBMC と Yocto が支えとなり、顧客導入時の検証コストは制御可能であり、サプライチェーン上では長らく Arm と 8051 の二択しかなかった。この位置での突破を選ぶことは、サーバーメイン CPU で正面衝突するよりもはるかに現実的だ。

第二の判断は、ソフトウェア側が今日「新規リリース」ではなく「バージョン補完」を行っているということだ。openRuyi は OpenSBI を 1.9 に引き上げ、OpenSSL 3.6.5 を導入し、xgrammar と tvm-ffi をリポジトリに取り込んだ。revyos はカーネル設定のベースラインを再整備し、6社のプラットフォームのスイッチを一度に整えた。どちらもニュースの見出しにはならないが、顧客がボードを受け取った後に設定変更を減らせるか、既存の推論スタックをそのまま使えるかを決める。RISC-V のソフトウェア格差の大部分は、こうした日常的な調整の中に隠れている。

第三の判断は、ロボティクス側の進展が「適応層」にあるということだ。進畳時空は Hiking 知覚ポリシーを humanoid_common に接続し、ZMQ で深度画像を伝送し、チェックサムでモデルを検証し、引き継ぎ失敗時には旧ポリシーを保持する。これらはエンジニアリングの詳細であり論文の指標ではないが、サードパーティのポリシーが K3 上で動作できるかどうかを決める。チップメーカーはすべてのポリシーを作ることはできないが、インターフェースを標準化することはできる。このことに今日、具体的な動きがあった。

直近3日のトレンド：管理面が先に着地、ソフトウェアスタックはバージョン補完、ロボティクススタックは知覚を補完（11-15 ~ 11-17）

11月15日から17日を連続して見ると、三つの線がそれぞれ前進している。筐体とチップ側では、Purism が11月14日に Librem 5 v2 のクラウドファンディングを開始し、11月17日に正式プレスリリースを発行して出荷時期を「クラウドファンディング終了後14〜15ヶ月」と細分化した。賽昉は11月17日に RISC-V BMC を量産出荷に押し上げた。両方とも「RISC-V が筐体 BOM に入る」という事柄に重みを加えており、一つはコンシューマー向けスマートフォン、もう一つはデータセンターのサーバー管理チップである。

オープンコアと検証側では、11月15日に FURSOY が Linux 6.6.50 を起動できるアウトオブオーダー RV64 コアを公開し、11月16日には香山がメモリアクセスキューの欠陥を修正し、CVW がベクトルメモリアクセスを補完し、11月17日には core-v-verif が CSR 状態を RVFI ログに組み込み、香山が命名リファクタリングを行った。四つの事柄に共通するのは「動作する」から「検証可能・保守可能」への転換であり、これもオープンコアが製品視野に入る前提である。

ソフトウェアとツールチェーン側では、openRuyi が連日バージョン追従と設定調整を行い、進畳時空が量子化ツールチェーンで自動探索を行い、ロボティクススタックでポリシー適応を行っている。三つの線を合わせて見ると、アーキテクチャの物語の窓は狭まり、エンジニアリングの実現の窓が開いている。次の半年で RISC-V の位置を決めるのは、また新しいチップの発表会ではなく、こうした出荷、設定、適応が継続できるかどうかである。
