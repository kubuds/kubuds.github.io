今日の重点：Linux 7.4 が「高速非整列アクセス」を実行期探測に変更、ディストリビューションカーネルで最大 11% の帯域利益を得られる（10-30）

Linux 7.4 の RISC-V アーキテクチャ変更がメインラインに統合され、そのうち 1 つの最適化は個別に記録する価値がある：ソフトウェア整列をスキップする判定がコンパイル期から実行期に移された。

この最適化の経緯は二段階に分かれる。Linux 7.3 で Tenstorrent がコミットした変更により、「高速な非整列メモリコピーをサポートする RISC-V ハードウェア向けにコンパイルされたカーネル」がソフトウェア整列をスキップできるようになり、Tenstorrent の自社測定では帯域幅が最大 11% 向上した。しかし 7.3 ではこの機能をコンパイル時に有効化する必要があり、あるディストリビューションのカーネルは一群のハードウェアにサービスを提供するため、その中には必ず低速な非整列アクセスを伴うチップが存在し、したがってこの恩恵はカスタムカーネルに留まり、汎用ビルドでは享受できなかった。7.4 では判定を HAVE_EFFICIENT_UNALIGNED_ACCESS に掛ける形で実行時プローブへと変更した。ハードウェアが実際に高速な非整列アクセスをサポートしていることをプローブで確認できた場合にのみ、ユーザー空間のコピーがソフトウェア整列をスキップする。これにより、ディストリビューションの RISC-V カーネルもその他の汎用ビルドも、旧型ハードウェア用に特別なイメージを維持することなく、この最適化をデフォルトで搭載できるようになった。

同じく 7.4 にマージされた RISC-V の変更には、crash ホットプラグのサポート、一部のページテーブル関数が最適化パスを通るようにする変更、コンテキストスイッチの 1 箇所の最適化、「B」拡張の hwcap および hwprobe での報告、そして Zic64b 拡張の報告サポートが含まれる。これらは単独で見ればいずれも大きくはないが、合わせると「カーネルが RISC-V プラットフォームの能力を把握し、自らのスケジューリングに委ねる」一歩となる——特に hwprobe 側の報告は、まさに実行時プローブによるこうした最適化の前提である。

コミュニティの議論の中で記録に値する判断が一つある。Hacker News で読者が、高速な非整列アクセスはサーバー向け CPU だけのものかと質問したのに対し、回答は SiFive を除くほぼ各社がサポートしており、SiFive は新世代の高性能コアでのみサポートしていると指摘した。これは、ディストリビューションがこの最適化を有効化した後、実際に恩恵を受ける範囲が、製品の位置づけではなく、チップが hwprobe で正しく報告するかどうかに依存することを示唆している。

日付：2026-10-30　情報源：Phoronix：RISC-V Has A Nice Portable Performance Optimization With Linux 7.4、Hacker News の議論

1. オープンソースコミュニティとソフトウェアエコシステム

香山フロントエンドが FtqPrefetchQueue を導入、iprefetch 再構築の第一歩（10-30）

第 6691 号は香山フロントエンドにおける今回最も大きな変更で、16 ファイル、+471/−198。変更の核心は FtqPrefetchQueue を新設し、命令フェッチプリフェッチを ICache-top から FTQ 側へと引き上げて統一スケジューリングする点にある。

元の設計の三つの問題は明快に記されている。第一に、FTQ は FDIP のみを担当し、memblock 由来の Zicbop ソフトウェアプリフェッチ prefetch.i は ICache-top が処理するが、毎サイクル 1 リクエストしか受け付けられず、しかも常にソフトウェアプリフェッチを高優先度に置く——同一サイクル内の複数の prefetch.i は 1 つしか有効にならず、残りは静かに破棄され、性能上の恩恵は期待を下回る。第二に、密集した prefetch.i は FDIP リクエストを阻害し、逆に性能を引き下げる。第三に、prefetchPipe は 1 つの prefetch.i を処理するか、1 から 2 の FDIP を処理するかのいずれかであり、両者が SRAM 上で競合しない場合でも並行処理できず、パイプラインの利用率が低い。

新しいキューの方式は、まずソフトウェアプリフェッチ要求をキャッシュして消失を緩和し、次にキューの空きと現在の FDIP 距離に応じてデキュー元を選択してブロックを解決する。さらに FDIP とプリフェッチが同一サイクルで並行発行できるようにして利用率を解決する。著者は拡張口も残している——後続で PDIP 一类のアルゴリズムの結果をそのまま同じキューに投入できる。これはプリフェッチを「一本の経路」から「一级のスケジューリング可能なリソース」に変える改法であり、単に優先度を調整するよりも長期的な解に近い。

日付：2026-10-30　情報源：XiangShan #6691

香山、MBTB による隠れ VBTB 分岐の割り当て抑制を修正（10-30）

第 6750 号は予測器メタデータが互いに压制し合う問題を修正する。VBTB は予測時に最も早くヒットした分岐のみを露出するが、訓練段階では「隠れ分岐」にヒットし得る——この分岐は予測時には見えていないが、訓練ヒットによって MBTB の割り当てを抑制してしまい、結果として同じ分岐が繰り返し予測失敗する。

改法は三箇所に分かれる：予測時に確かに露出され、かつ訓練時にも依然として駐留しているという二つの条件が同時に成立する場合にのみ、VBTB 駐留によって MBTB 書き込みを抑制する；全ての NumWay+1 個のメタデータエントリを AlignBank に渡し、「VBTB 予測ヒット」と「SRAM ヒット」を区別できるようにする；条件分岐ペイロードは実際に taken のときのみ書き込む。not-taken の解決経路が運ぶのは順序上の次 PC であり分岐ターゲットではないためである。最後の一条は MBTB と VBTB の両方に適用し、カウンタ訓練と IFU 無効化要求（attribute=None）を保持する。変更はわずか 2 ファイル、+33/−19 だが、「予測器が複雑になるほどメタデータの口径を揃える必要がある」典型的な修正である。

日付：2026-10-30　情報源：XiangShan #6750

香山、prefetch.i/r/w を LSU プリフェッチ操作としてデコード（10-30）

第 6735 号はソフトウェアプリフェッチ命令の処理フローを変更する：prefetch.i、prefetch.r、prefetch.w はデコード段階で LSU のプリフェッチ操作として識別され、CROB から除外される。このステップは第 6691 号のキュー化変更と配套する——まずプリフェッチを「通常のメモリアクセス命令」から分離して初めて、FTQ 側のプリフェッチキューに独立した要求ソースが生まれ、load/store と同一のコミット経路を争う必要がなくなる。

日付：2026-10-30　情報源：XiangShan #6735

香山 CI 性能フローで lightSSS を有効化、GEM5 週次テストを 261013 設定に切替（10-30）

第 6802 号は gsim フロー内で difftest バージョンをアップグレードし、CI で lightSSS を有効化する。ベンチマークと検証が同一のスナップショット機構を共有し、重複ビルドを省く。同じ調査期間の OpenXiangShan/GEM5 第 1274 号は毎週の XSCC テストを 261013 設定プロファイルに切り替える。両筆ともインフラ保守に属する：前者は「エラー時に迅速にリプレイできるか」を決め、後者は「週次テストがどのバージョンのコンパイラと負荷の組み合わせで走るか」を決めるもので、RTL の振る舞いは変えない。

日付：2026-10-30　情報源：XiangShan #6802、GEM5 #1274

difftest 二日間で九筆：MMA バックエンドが FP8 積を cache word に詰める（10-30 から 11-01）

difftest は三日間に 9 筆をコミットし、すべて MMA（行列積和）検証の性能を巡るもので、テンポとしては一度の集中的な攻堅である。

最も技術的な一筆は第 1023 号：隣接する FP8 積レコードを同一 cache word の下位 16 ビットと上位 16 ビットに詰め、レジスタを半分節約する；各 word はまず偶数 lane で初期化し、デコード前に二つの半字にそれぞれマスクをかけ、隣接する符号フィールドが互いに串扰しないことを保証し、長さが奇数の末尾ブロックも同様に処理する。第 1021 号は比較を GPU 上に移す（11 ファイル、+420/−90）：DUT スナップショットのアップロードと参照計算を分離し、アクティブな結果行は直接 GPU 上で比較し、成功時は状態バイトのみを返送し、ミスマッチ時のみ参照結果をダウンロードして診断する；フォールバック経路は memcpy で比較的遅い SSE2 streaming-store を置き換える；連続するホットスロットを再利用し、CUDA サービスから直接その区間をアップロードする；各プレフィックスの ready／enqueue 確認を除去しつつ、LightSSS セッションのライフサイクルを保つ。第 1018 号は CUDA 転送、計算、結果検証をパイプライン化し、第 1017 号は LightSSS に CUDA バックエンドをサポートさせ、第 1020 号は XDMA 中継要求をパッキングして遅延を低減し、第 1019 号は符号付き INT8 参照リダクションを簡素化し、第 1016 号はオペランドスロットの連続アクティブプレフィックスを再利用し、第 1004 号は Delta と AXI のタイミングを分離する。方向性は明快である：検証器はもはや「正しく計算できる」だけでは足りず、「計算しきれる」ことも求められる。

日付：2026-10-30 から 2026-11-01　情報源：difftest コミット記録、#1023、#1021

NEMU、AME 向けに replay 状態のロールバックを追加、hosttlb の行列レジスタセレクタを修正（10-30、10-31）

第 1255 号は replay_state.c（178 行）を新規追加し、replay state API を通じて行列レジスタ、token カウンタ、AMU 制御と同期イベントのスナップショットと復元を行い、さらに AME_MEM_ACCESS_CHECK 有効時には行列とスカラ／ベクトルストアを同時に追跡し、AME_TILEREG_UB_CHECK 有効時には tile レジスタ定義領域を追跡する。スナップショットは意図的に行列ストアのコミットキューから独立させており、ロールバック時に未コミットの書き込み操作に汚染されるのを避けている。第 1274 号はシグネチャの不一致による機能エラーを修正する。行列読み書きの定義と呼び出し側は char m_name を使っているが、公開ヘッダファイルでは bool isacc と宣言されていたため、ヘッダファイル経由の呼び出しでは A/B/C セレクタが一律 true に変換されていた。2 か所の宣言を修正し、host-tlb.c に共通ヘッダを導入することで、今後同様のシグネチャ不一致が発生した場合にコンパイルが直接失敗するようにした。

日付：2026-10-30、2026-10-31　情報源：NEMU #1255、NEMU #1274

XSCache、CoupledL2 でもう一方の hint が継続的にブロックされる問題を修正（10-30）

第 48 号は 1 行のみの変更で、CoupledL2 において一方の hint がもう一方によって継続的にブロックされるのを防ぐ。前日の第 46 号で既にヒントのアービトレーションを固定優先度からラウンドロビンに変更しており、このコミットは同じ系列の仕上げである。キャッシュ階層におけるスターベーション系の問題は通常、長時間のストレステスト下でしか顕在化せず、1 行の変更の背後には再現しにくい検証がある。

日付：2026-10-30　情報源：XSCache #48

openRuyi、llvm23 23.1.4 を導入、riscv64-openruyi-linux のデフォルトを RVA23U64 に（10-30）

6 件のコミットの中で最も重要なのは llvm23 パッケージの新規追加（1220 行の spec と 2 つのパッチ）である。パッチの内容はバージョン番号よりも情報量が多い。LLVM に openruyi という vendor を追加し、riscv64-openruyi-linux トリプレットのデフォルト ISA レベルを直接 RVA23U64 に定める。つまり、追加で -march を渡さない場合、コンパイラは RVA23 に従ってコードを生成する。これはディストリビューションにとって明確な表明であり、RVA23 はもはや「オプションの最適化段階」ではなくデフォルトのベースラインとなる。同時にパッチは openruyi-linux トリプレットを x86_64 と riscv64 の 2 つの Triple 処理経路に接続し、クロスビルドが利用可能であることを保証する。

残りの 5 件はローリングメンテナンスである。ollama を 0.40.7 に更新し security-fixes を付与、clang-wrap を 20261030 に更新、tree-sitter の C++ と Go の 2 つの Go 言語バインディングパッケージおよび go-pointer 依存を新規追加。公式サイトのニュースページで最新は依然として 2026.09 版（9-30 リリース）であり、10 月版は未リリースである。10-19 の 2 本（Ruyi Firmware、コミュニティ公共インフラ）は 10 月中旬レポートに既に収録済みのため、今回は重複して扱わない。

5. 総括とトレンド観察

1. カーネル側のキーワードは「サポート」から「ハードウェア能力に応じたスケジューリング」へ。 Linux 7.4 は、高速非整列アクセスの判定をコンパイル時から実行時に移した。7.3 時代にはカスタムカーネルにしか残せなかった最適化を、今やディストリビューションのカーネルがデフォルトで備えられる。Tenstorrent の自社測定では帯域幅の收益上限は 11% である。同時にマージされた hwcap／hwprobe の「B」拡張と Zic64b の報告は、まさにこの種の実行時判断のデータ源である。国内のいくつかの RISC-V ディストリビューションにとって、これはゼロコストの收益だが、前提としてチップが hwprobe で正直に報告することが必要だ。ハードウェアメーカーが能力を漏れなく報告することは、マイクロアーキテクチャの最適化をもう一回行うよりも、ユーザーが直ちに恩恵を受けられる。

2. 香山のフロントエンドは「プリフェッチのキュー化」段階に入った。 第 6691 号は iprefetch を ICache-top の「毎サイクル 1 条」から論理的に FTQ に収め、まず消失とブロックを解決し、その後 PDIP 一类のアルゴリズムを論じる。付随する MBTB／VBTB の修正は、ボトルネックがすでに「フェッチ帯域」から「メタデータ精度」へ移ったことを示している。両者を合わせて見ると、フロントエンドの最適化はバッファ追加から「プリフェッチを一級のスケジューリング可能な資源として扱う」ことへ移行しており、この種の変更の收益は長期負荷でしか検証できず、短期的なベンチマークは必ずしも良くないかもしれない。

3. 差分検証がアクセラレータのオペレータに性能コストを払い始めた。 difftest の 3 日間 9 件はすべて MMA を巡っている。FP8 積のパッキング、GPU 側の比較、CUDA のパイプライン化、XDMA 中継パッキング、LightSSS の CUDA バックエンド対応。RISC-V AI コアが量産に向かうには、検証スループットがオペレータの複雑さに追いつかねばならない。さもなければ「正しく計算できる」が「計算し終わらない」に変わる。この一群の変更は、単件の收益よりも方向性が記録に値する。

4. ツールチェーンの両側が同時にベースラインを定めた。 openRuyi は llvm23 を導入し、riscv64-openruyi-linux 三元组のデフォルト ISA を RVA23U64 に定めた。芯来は IDE を Eclipse から VS Code へ移し、xlmodel、ツールチェーン、大端デバッグ文書を 2026.10 に同期した。前者は「デフォルトでどんなコードを生成するか」を定め、後者は「開発者がどこから入るか」を定める。どちらも長周期の決定であり、短期では効果が見えないが、以後 1〜2 年のデフォルト選択に影響する。

5. 国内側の今期間の産出は算能と芯来に集中し、路線はボードからシステムスタックへ上がった。 算能の実質的な作業はモデルサポートと 1 つのデコード退化バグの修正（logits を 4 バイトの token バッファにコピーし、各ステップのデコードで查表が破壊される）であり、この種の欠陥は実機で逐 token 比較しないと特定できない。芯来はツールチェーンの入口を VS Code に替え、ついでに AI アシスタント接続を補完した。玄鉄と奕斯偉は調査期間内に空档であり、進畳時空は Bianbu AgentOS 傘倉と機械臂制御フレームワークを同時に推進している——ある企業が「端側 agent ランタイム」と「機械臂のキャリブレーション／診断／運動学」を並行して進めるのは、その RISC-V ソフトウェアスタックの重心がドライバと文書から納品可能なシステム層へ移りつつあることを示す。今号のニュース側は薄めである。中英文のクエリを重複除去した後の実質的な新規は Linux 7.4、Qwenputer、Nuclei Studio の 3 件のみで、残りは株式市場記事、コンシューマエレクトロニクス、旧稿の再掲である。オープンソース側が依然として主体である。
