2. RuyiAI スタックの進展（PyTorch / Triton / TileLang RISC-V 適配）

2.1 triton-riscv：「18個の夜間タグ」から初の正式リリースへ

日付：2026-11-06 から 2026-11-14　出典：正式リリースタグ、PR #105 README を wheel 優先に変更

このリポジトリは今週3つのステップを完了した：リリース階層を立ち上げ（最初の release/ タグ）、インストール経路をソースコードから wheel に変更し、異種バックエンドを「コンパイルできる」から「実機で動かせる」まで持っていった。3つのステップの間には先行依存関係がある——再現可能な wheel タグがなければ、GPU バックエンドの検証はソースコードビルドにとどまらざるを得ない；そして AMD バックエンドの検証が逆にリリースチェーン上の数か所、セルフホスト riscv64 runner 上でのみ出現する問題を露呈させた。

2.1.1 タグ自体がリリース動作の全内容

日付：2026-11-06、11-09　出典：release/20261108-6895885、PR #101

release/20261108-6895885 はコミット 6895885 を指し、これは 11-06 の「AMD 用に riscv64 の欠落 codegen ライブラリを補完」（#102）のマージコミットであり、夜間版 nightly/20261106-6895885 と同じ点である。当日の3件のコミット（#105、#106、#107）はいずれもタグの後に着地しており、このパッケージには入っていない——つまり最初の正式版が実際に打ったのは先週末のコード状態である。

リリースチェーンの2か所の配套変更は既に期間内に着地していた：#101 は #100 の後に露呈した2か所のリリースチェーン問題を修正（リリースワークフローを CI と同じチェックアウトアクションバージョンに変更、scripts/release.sh にバックエンド登録ステップを追加し、release が産出する wheel と CI がビルドする wheel に同じプラグイン登録情報を持たせる）、#102 は setup.sh が AMD codegen ライブラリの欠落を検出した際にローカルビルドして約定パスに配置し、env.sh が TRITON_AMD_CODEGEN_PATH をそこに指すようにした。夜間版にはさらに唯一のバージョンサフィックス .dev<日付> を追加した。これまで毎回のビルドが Triton 自身のバージョン番号を共用していたため、パッケージインデックスが重複バージョンを拒否するからである。

2.1.2 インストール経路を wheel 優先に変更、クイックスタートを逆アセンブリを見る形に変更

日付：2026-11-09　出典：PR #105、PR #107

#105 READMEのインストールセクションを書き直した。まずwheelのパスとそれを提供するパッケージインデックスを示し、次に必要なLLVMアーカイブとそれを指す変数を示す。ソースからのパスはmake setupに圧縮した（.venvの作成、固定バージョンTritonのクローン、固定バージョンLLVMとbuddyビルドのダウンロード）。以前の「仮想環境の作成、依存関係のインストール、環境スクリプトの15個の変数」という説明は短い注記1行にまとめた。#107でその後修正を加えた。パッケージインデックスには現在tritonとbuddyツールがまだないため、READMEにあるバイナリインストールのアドレスは失敗する。そこで2つのプロジェクトそれぞれのGitHub releasesを指すように変更し、ディスクからwheelをインストールするようにした。同じコミットでPython 3.14でのlitクラッシュも修正した。TritonはwhichでPATHからlitを探すが、LLVMツリー内のlitはモジュールレベルでmainを呼び出しており、Python 3.14がLinuxでデフォルトでforkserver起動方式に切り替わったため、再インポート時に直接クラッシュする。修正方法は、ビルド用インタプリタのbinディレクトリをPATHの先頭に置くことだ。

2.2 triton-riscvの異種路線：RISC-VホストがAMDカードを駆動

日付：2026-11-10　情報源：PR #110 GPUバックエンドをデフォルトで有効化、README

#110のマージ後、このリポジトリの位置づけは「RISC-V CPUのベクトルユニット上でのみTritonを動かす」から「RISC-Vホストから異種アクセラレータを駆動する」へと広がった。3つの変更のうち、ビルド側では既存のBuddy LLVM SDKを使ってriscv64のAMD codegenライブラリをビルド・パッケージングする。ドライバ側ではCPUとGPUの二択時の曖昧さを修正し、利用可能なGPUを優先するルールとした（該当ファイルは純削除4行）。ドキュメント側ではREADMEにAMD GPUのセクションを追加し、ROCmが存在する場合にバックエンドがtorch.version.hipを通じて自動的に有効化されること、wheelにROCmランタイムは含まれないこと、CPUに強制フォールバックするにはTRITON_DEFAULT_BACKEND=triton_sharedを使うことを説明した。

3.1 ruyi 0.54.0：「インストールできるかどうか」を計算可能な事実に変える

4.2 i1 マスクをバイト単位で読み書き（#1052）

日付：2026-11-12　情報源：PR #1052

memref の要素型が i1 の場合、可変長ベクトルはこれまで直接拒否されていた（a memref of i1 needs fixed vectors と表示される）。memref は1要素あたり1バイトを占め、i1 ベクトルは1ビットあたり1レーンを占めるため、レーンごとの下降があるのは固定長ベクトルだけだからである。一方 Triton の load/store マスクはまさに i1 memref であり、純粋な VIR パイプラインに可変長ベクトルを加えて通すと、325 個の Triton-RISCV テストファイルのうち 179 個がこのエラーで詰まる。今週の7件の中で影響範囲が最も広い一件である。

修正方法はバイト単位の読み書きである。連続アクセスは i8 ベクトルの llvm.load/store を使い、非連続の strip-mined 領域は vp.strided.load/store で全レーンを開く。ついでに i1 レーンを1バイトとしてサイズ計算する——これまでは最初の動的ベクトルが i1 である領域を1ビットとして計算していたため、VLEN 256 では vector<[512]xi1> のような16組レジスタの規模になってしまっていた。

4.3 libm-only 数学関数のレーンごとの展開（#1053）

日付：2026-11-12　情報源：PR #1053

LLVM が可変長ベクトル上で下降しようとしない数学関数（erf、erfc、cbrt、powf、atan2、acosh など）をレーンごとの展開に変更した。vector<[N]xT> の N 掛ける vscale 本のレーンを1本ずつ extract し、スカラー関数を呼び、再び insert する。誘因は convert-math-to-libm の可変長ベクトルに対する処理が固定長ベクトルと同じで、先頭 N 本だけを計算し、残りを黙って 0 にしてしまうことだった——可変長の erf は VLEN 128（vscale 2）では半分のレーンが誤っている。効果はテスト面に直接現れている。FlagGems スイート 4045 項の SG2044（VLEN 128）上での通過数は 3980 から 4006 に増え、修正された 26 項は test_erf と test_gelu であり、新たな失敗はない。

4.4 bf16 の2つの経路と網羅的検証（#1054）

日付：2026-11-12　情報源：PR #1054

RVV は Zvfbfmin を伴う場合にのみ bf16 をベクトルレジスタに入れる。この拡張がない場合、LLVM はロード1回すら下降しようとしない。変更では下降器に rvv-mattr パラメータを追加し、デフォルトでは Zvfbfmin ありとして処理する（Buddy のいくつかの RVV ターゲットである K3 の X100 と A100、SG2044 はいずれも備えている）。明示的に -zvfbfmin を指定した場合は整数ビットとして処理し、bf16 ベクトルを i16 として読み書きし、extf と truncf は整数演算（truncf は最近接偶数丸め）、absf と negf は符号ビットで処理する。

検証方法は今週で最も重い箇所である。truncf は全 2^32 個の f32 をカバーし、extf、absf、negf および extf-mulf-truncf は全 2^16 個の bf16 をカバーし、SG2044 と K3 の2つのコア上で Zvfbfmin 経路とビット単位で比較し、結果は同一だった。この検証コストは、bf16 が出荷経路として扱われていることを示しており、「暇になったらやる」最適化項目ではない。

4.5 fast-math フラグと全リダクション種別（#1055、#1056）

日付：2026-11-12　情報源：PR #1055、PR #1056

#1055 は、fast-math フラグが strip-mined 下降時に失われる問題を修正した：contract 付きの arith.mulf と arith.addf が通常の fmul と fadd に再構築され、LLVM が融合しなくなる。現在はフラグが同種オペレータとともにベクトルループとテールへ伝播され、f32 の積和は vfmacc を、bf16 は +zvfbfwma の下で vfwmaccbf16 を生成できる。著者は K3 の X100 と A100 上で 4M レーンごとに fmaf 展開とビット単位で比較し、結果が一致することを確認した。これは 7 件のうち、命令選択を直接変更する唯一のコミットである。

#1056 は vir.reduce を浮動小数点の add と maxnum のみから、vector.reduction の全種類へ拡張した：add、mul、minsi、minui、maxsi、maxui、and、or、xor、minnumf、maxnumf、minimumf、maximumf に対応し、整数も併せてサポートし、verifier が kind と要素型の一致を検証する。従来、Triton の整数総和、min/max、積、all/any（およびこれらに依存する argmin、argmax、count_nonzero、双調ソートと基数ソート）はすべてループ内に残っていた。変更は 570 行を追加し、9 ファイルに及ぶ。

4.6 残存パスの收尾：rank-0 填充と整数行列積（#1057、#1058）

日付：2026-11-12　情報源：PR #1057、PR #1058

#1057 は rank-0 memref の linalg.fill（大半は帰約のアキュムレータ）を 1 回の memref.store に降下させ、FlagGems の 1811 カーネルに残存する linalg.fill を 393 から 0 へ減らした。#1058 は整数行列積も下降可能にした：A、B が同一整数型で C より広くない場合、符号拡張またはゼロ拡張してから積和する（fma なし）。RVV 上では int8 行列積が vsext.vf2 と vwmacc.vx を、符号なしでは vzext.vf2 と vwmaccu.vx を生成する。同じコミットでは動的形状 matmul のアサート失敗も修正した——M と K は元々 vir.set_vl 領域内で取得されており、後続の pass で使用中に消去されていた。修正後、1811 カーネルには linalg.matmul が残っていない。

5. Buddy Compiler 動向

5.1 VLEN 精確化の前半戦：#1032 と #1037

日付：2026-11-08　情報源：PR #1032、PR #1037

#1032 が解決したのは、ある種の誤った失敗の仕方である：エラーを出さず、ただ誤った計算結果を出す。精確な VLEN でビルドされた RISC-V モデルでは、ベクトルコードはその VLEN でのみ成立する——llc には VLEN が明示され（+zvlNb と -riscv-v-vector-bits-max）、decode attention 内の可変長ベクトルもそれに合わせてサイズ決めされる。別の VLEN に移すと、モデルはクラッシュせず、直接誤った結果を返す。

修正方法は検証をロード時刻へ前倒しすることだった：runtime/rvv/BuddyRvvVlen.c がコンストラクタとしてモデルライブラリにリンクされ、ライブラリがロードされると vlenb を読み取り、ビルド時の精確な VLEN と一致しない場合は情報を出力して _exit(1) でプロセスを終了する。exit ではなく _exit を使うのは意図的である——ローダがロックを保持している間にデストラクタを実行するとデッドロックする。レビュー後、検証を「ビルド変数で判断」から「最終的な llc オプションで判断」へ変更するコミットを追加した：従来はネイティブビルドがモデル付属の LLC_ATTRS で VLEN を指定する可能性があり、BUDDY_RISCV_VLEN と一致しない場合、検証値と実際のコードが食い違う恐れがあった。また、サードステージにのみリンクされ、Qwen3-VL の vision と decode の 2 つの shim、および階層リンクのパスが漏れていた。現在はビルドスクリプトが最終的な llc オプションから精確な VLEN を取り出し（VIR 下降と同じ箇所を読む）、設定段階でオプション同士が矛盾していれば直ちに失敗する。テストはこの変更のもう半分である：test_buddy_rvv_vlen.py は VLEN 128 から 65536 までそれぞれモデルライブラリをビルドし、ホストのものだけがロードでき、残りはすべて終了コード 1 で終わる。ドキュメントでは A210 と K3 の 2 つの DeepSeek-R1 デプロイ説明も同時に更新され、「どのビルドが精確な VLEN で、どれが汎用 RVV か」の境界が明確にされた——A210 のカーネルは固定長ベクトルで VIR を持たず、汎用ビルドに属する；K3 の prefill_ime は 1024 が必須で、精確な VLEN に属する。

#1037 は別方向の誤りを修正する：-lower-vir-to-vector は rvv-vlen を与えず、伸縮可能ベクトルも有効にしない場合、ホストのレジスタ幅に応じて固定長ベクトルのサイズを決めるが、そのホスト認識は x86（AVX2、AVX-512）と SVE のみをカバーし、V 拡張付き RISC-V ホストは一律で汎用デフォルト値（128 ビット、16 レジスタ）に落ちる。結果はテストに現れる：#1030 以降、kernels パイプラインは llc オプションなしの場合にホストに応じて VIR を低下させ、riscv64 CI ホストは VLEN 256 であるにもかかわらず 128 ビットとして扱われ、q、k ノルムの二乗が vector<32xf32> に分割されて合計され、ベクトルカーネルとのビット単位比較の順序が異なり、vir decode qk_norm ... same bits が偽と判定される。作者はまずテスト内でのみ rvv-vlen=1024 use-scalable=false を固定する変更を加えたが、直ちに自らロールバックした——それは llc オプションの外に VLEN 設定をもう一箇所作ることに等しく、#1032 の方向と衝突する。最終的な修正方法は、低下段階で RISC-V ホストを識別し（ホスト CPU 特性と hwprobe を読み取る）、実際の VLEN に応じてサイズを決定することである。

5.2 f32 YOLOv8 がエンドツーエンドで VIR を通過（#1041）

日付：2026-11-09（11-10 01:07 にマージ）　情報源：PR #1041、マージコミット 18c66ec

#1041 は f32 YOLOv8 グラフをエンドツーエンドで VIR に通す：まず Linalg から VIR への低下を行い、次に VIR からベクトル方言への低下を行う。従来このパスには畳み込みパターンがなく、グラフには他に三種類のオペレータが直接失敗していた——一つの変更で畳み込みとその三種類を同時に補った。規模は十四ファイル、千六百四十六行追加、百十五行削除、十三コミット。

畳み込みは二系統ともカバー：二次元 NHWC と HWCF の組み合わせ、および二次元 NHWC と FHWC の組み合わせ。ベクトル化は出力チャネル F に沿って展開し、各 (kh, kw, c) について入力要素を各出力ピクセルごとに一つの vir.fma にブロードキャストするため、各ベクトルアクセスは連続であり、レーンをまたぐリダクションもない——リダクションは横方向命令と後続の縮約木が必要で、狭い VLEN ではコストが顕著である；代償として FHWC フィルタはまず HWCF バッファへ並列コピーする必要があり、一回の転送を追加して内側ループの連続アクセスを得る。

従来失敗していた三種類のオペレータも併せて補完：rank-0 入力（memref<f32> が直接 linalg.generic に入ると memref.expand_shape で invalid reassociation を報告するため、一度ロードしてからブロードキャストするよう変更）、末尾次元を保持する linalg.reduce（例 DFL softmax の 1x16x4x2100、dimensions=[1]、addf と maximumf の組み合わせ）、linalg.index を読み取る名前付きオペレータ（例 upsample 内の linalg.map iota）。実機の基準は明確：K3 上で f32 YOLOv8 pose の元出力は最大 6e-5 変化し、PyTorch との差は依然として 6e-4（bus）と 8e-4（zidane）以内で、変更前と一致；detect モデルの検出結果は不変、速度も低下なし；f32 と IME 動的ライブラリの出力は変更前とバイト単位で同一。

5.3 YOLOv8 が rax へ：検出と姿勢が K3 行列エンジン上で動作（#1042）

日付：2026-11-10　情報源：PR #1042

7. トレンド観察

7.1 リリースチェーンが機能に先行：今週直したのは「パッケージを出せるかどうか」

triton-riscv の1週間のマージのうち、機能と言えるのは #110（AMD バックエンド）だけで、残りの #101、#102、#105、#107、#111、#112、#113 はすべてリリースチェーン上にある。バックエンドの wheel への登録、AMD codegen ライブラリのローカルビルド、README の wheel 優先、lit の検索順序、git 認証の抽出、AMD セクションの torch 前提。さらに #116 の wheel スリム化と #117 の -O3。このリポジトリの今週の成果は「インストール経路を再現可能・ダウンロード可能・検証可能にする」と要約できる。

これは個別現象ではない。ruyi 0.54.0 の主な内容も「インストール前にインストール可能か判定する」ことであり、pytorch の #56 が塞いだのは「ゼロ件のテスト通過でもグリーンとみなす」ことであり、buddy-mlir のナイトリー版が補ったのは6日分のパッケージ欠落である。4つのリポジトリが同じ週に同じ種類のことを行っているのは、このスタックが「動くことを証明する」段階から「デリバリーできることを証明する」段階に入ったことを示している。

7.2 カバレッジ優先于性能：393→0、2→0、179→0 の基準

今週の buddy-mlir の7件のうち、命令選択を直接変えたのは #1055 だけで、残り6件はそれまでループに残っていた形態をベクトルパスに接続するものだった：i1 マスク、libm-only 数学関数、bf16、リダクション種別、rank-0 パディング、整数行列積。この種の変更を評価する基準は「linalg やスカラーパスがどれだけ残っているか」であるべきで、ベンチマークではない——393 が 0 に、2 が 0 に、179 個の失敗ファイルがゼロになった、というのがこの基準である。

前日 #1050 の strip-mined 余剰量の幅縮小と対照すると、2日間の分担は明瞭である：まずベクトルループにレーンを満たさせる（性能）、次にすべてのオペレータをベクトルループに入れる（カバレッジ）。順序を逆にすると無駄になる——幅だけ広いループがあっても、入るオペレータは同じ数少ないものだ。

7.3 VLEN 1024 がコンパイラとランタイムの共通の圧力点に

1週間のうちに3箇所の変更が直接 VLEN 1024 を指している：ロード時の検証（#1032）、リダクションのレーン欠落（#1051）、strip-mined 余剰量（#1050）。共通点は同じハードウェア事実が各層で繰り返し現れることだ——K3 の prefill_ime は必ず 1024、A100 コア上の 16 個の f32 は完全な1ベクトル、vector<[1]xT> のような形状は VLEN 128/256 では到底たどり着けない。

同じ週の上流側にも同じシグナルが現れている：V8 のレビュー名簿に “Allow vlen=1024”（CL8585179）が登場した。これは長ベクトルがもはや特定ボードのローカル設定ではなく、ランタイムとブラウザの汎用パスに入り始めたことを示す。リスクも伴う——CI の riscv64 ランナーは VLEN 256、出荷ハードウェアは 1024 であり、両者のテストカバレッジは本質的にずれている。#1051 のような「CI は全緑、ボード上では全エラー」という欠陥は、まさにこのずれの産物である。

7.4 サイレントな誤値の検証コストは入力の全列挙の規模に達した

#1054 は truncf に対して全 2^32 個の f32 を実行し、変換と符号演算に対して全 2^16 個の bf16 を実行した；#1055 は 4M レーンで fmaf 展開をビット単位で比較した；#1041 の受け入れ基準は「変更前とバイト単位で同一」；#1051 の受け入れ基準は25項目のリダクションテストが誤りから正しくなること。4件の検証方法は異なるが、すべて同じ問いに答えている：結果が正しいかどうかであり、速いかどうかではない。

理由も明快だ：今週修正した欠陥はほとんどが「エラーを出さず、ただ計算を誤る」ものだ——正確な VLEN でビルドされたモデルがハードウェアを替えるとサイレントに誤る、スケーラブルな erf は半分のレーンが 0 にされる、リダクションは lane 0 しか残らない、マスクがビット単位でサイズを計算して16組のレジスタになる。クラッシュは発見しやすいが、誤値はそうではない。検証コストが入力の全列挙の規模にまで上がるということは、このスタックがすでに bf16 やリダクションといった基本オペレータを出荷基準で扱っていることを意味する。

7.5 ローリングパッケージングと月次定版のデカップリング

openRuyi パッケージングリポジトリの今週のコミット密度は近年最高（単日ピーク36件、KDE、セキュリティ、ツールチェーン、デバイス面の4ラインが並行）である一方、対外的に見える月次バージョンは依然として 2026.09 に留まっている。両者は矛盾しない：ローリングパッケージングと月次定版はもともと2本のラインであり、日次更新はエンジニアリングが動いていることを示し、バージョン欠落はリリースプロセスや検証サイクルが詰まっていることを示す。

注目すべきは今週新設された2つのガバナンスリポジトリだ：release 規範リポジトリは要件番号と優先度をプロセスとして書き下し、ruyi-deck は「リポジトリとリリースの操作台」と位置づけられている。どちらもコードを産出しないが、指し示すのは同じ欠落である——1つの月次バージョンはパッケージングリポジトリ、イメージ、ファームウェアの複数リポジトリにまたがってリリースされる必要があり、欠けているのはコミットではなく、コミットをリリース可能なバージョンへ収束させる那道の工程である。

7.6 「インストールできるか」が初めて計算可能な事実になった

ruyi 0.54.0 は ELF ABI 互換性を三態判定（互換、非互換、未判定）にし、list、install、admin check-abi の3箇所で公開した。このことの意義は機能そのものではなく、「このパッケージが自分のマシンで動くか」を経験的判断から、照会可能・比較可能・トラブルシュート可能なデータに変えたことにある。

RISC-V にとって特に重要だ：同じプリコンパイル済みバイナリでも、異なる拡張の組み合わせ、異なる浮動小数点 ABI のホストでは動作が異なり、過去には試すしかなかった。三態設計はさらに「未判定」という段階を設け、未知を非互換とみなすことを避けている——この区別が、ツールが実環境で使えるかどうかを決める。次に観察すべきは sidecar のカバレッジだ：どのパッケージが ABI 情報を補ったか、どれが依然として「情報なし」か。080 期で言及された packages-index が一部パッケージに ABI 互換情報を補ったのは、このラインの延長である。
