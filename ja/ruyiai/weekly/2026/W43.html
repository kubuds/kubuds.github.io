RuyiAI ウィークリーレポート (2026-10-19 ~ 2026-10-23)

2026-10-23 Kubuds

レポート期間：2026年10月19日（月）から10月23日（金）までの計5就業日。

素材情報源：本誌の毎日RuyiAI動態レポート5期（2026-10-19から2026-10-23、各期の調査期間は前日04:30から当日04:30まで、うち月曜は過去3日間で週末をカバー）；加えてRuyiAI-Stack、ruyisdk、buddy-compilerの3組織における168時間のリポジトリ核查、openRuyi-Project重点リポジトリの補足核查、RuyiSDK開発者コミュニティとopenRuyiディストリビューションニュースページの二重情報源による再確認、およびRuyiAI公式ホームページ3ページのスナップショット（核查は10-24午前までをカバー）。

編制説明：今週は3本の主線が並行した。第一に、openRuyiメインリポジトリは637件のコミットで「依存関係に基づくパッケージング」への全体的な転換を完了し、Rust crateクロージャの補完、Pythonクラウドストレージバックエンドの補完、Goのvendor除去から、さらにソースチェックサムと%autochangelogの規範補完へと一気に推進した。第二に、PyTorchとLLVMの2つのriscvブランチのブランチ全体リプレイが「適期実施」から「毎日」へと収束し、パッチタイトルの集合は不変であるが、コミットハッシュは毎日無効化される。第三に、RISC-Vマトリックス拡張（AMEとZtt）のコンパイラ、シミュレータ、オペレータの3層が今週同時に整い、「コンパイル可能、実行可能、結果正確」という最小閉ループを形成した。ウィークリーレポートはデイリーレポートの素材に加えて7項目の核查上の新発見を補入しており、いずれも10-23の日中（デイリーレポートの調査期間以降）または期間境界に該当し、付録に記載する。

1. 今週の主なニュース

  • openRuyiは単週5日間で637件のコミット、パッケージング戦略は全体的に「依存関係に基づくパッケージング」へ転換：自然日別に集計すると、10-19から10-23まではそれぞれ221、137、51、109、119件で、作者はLeetfs（333件）とJingwiw（152件）が主である。進化の順序は明確に追跡できる——10-19の単日でRust関連コミット211件（新規パッケージ約200個）およびネットワークストレージスタック（dpdk 26.07、spdk 26.09、liburing 2.15、btrfs-progs 7.1、nvme-cli 3.1）を推進；10-20はRust/Go/Python各42件の対称構造でfsspecクラウドストレージバックエンドの全ファミリーを補完；10-21から10-22にかけてminio（10-20マージ）、sonobuoyとumoci（10-21マージ）のvendor除去改造をメインブランチに反映し、削除されたvendor後に必須となるインポートパスを補完、picoclawの同種提案はまだ待機中；10-22からは規範補完に移行し、Jingwiwが一度に54個のパッケージを一掃してソースチェックサムを補完し%autochangelogに切り替えた。情報源：openRuyiコミット一覧、PR #1459 minio vendor除去、PR #1466 umoci

  • QEMU が P 拡張 v0.6 の全命令シミュレーションを補完、GCC と LLVM 側も同期して整合：ruyisdk/qemu の p-dev ブランチ（上流 v11.1.0 ベース）は 10-21 16:35 に 12 件の収尾バッチを導入した。すべてパッキング SIMD に集中しており、Q 形式の乗算と積和、純粋な乗算、積和累算、二路および四路の乗加減算、水平帰約、ロード複製、pack/merge/先行カウント、RV32 専用命令、さらに P の Zbkb への依存を削除して新版仕様に整合させ、tests/tcg/riscv テストを追加した。ツールチェーン側も同期して整合：GCC は P 拡張サポートを 0.6 バージョンに更新し、LLVM は mulq、乗算高位累算、sati/usati、Packed Pair とパッキング乗算などの intrinsics を段階的にマージした。これにより P 拡張は「シミュレータ全カバー、デュアルコンパイラで生成可能」という後半段階に到達し、欠落はアプリケーション側のベンチマークにある。出典：qemu p-dev、バイウィークリー 079 期

  • IREE は二日で RVV 行列積加算の第一級精度段階を走破：10-19 にリリースされた v3.13.0 は RISC-V V の f32 vfmacc.vf inner_tiled MMA を正式版に取り込み（PR #24933）、10-21 にはメインブランチでさらに f16 版を着地させた（PR #25000、946 行の変更、テストは八百余行）。拡張機能の利用可否に応じて三層でエンコーディングを選択する——+zvfh がある場合は vfmacc.vf を使用し、f16 同士の乗算で f32 を得る場合は拡張幅の vfwmacc.vf を使用し、+zvfhmin のみの場合は f32 に拡張してから切り戻す形に退化する。性能面での方向性として、X60（VLEN=256）上のシングルスレッド inner_tiled はすでに mmt4d ukernel より高速である一方、4 スレッドおよび 8 スレッドの大形状では依然として遅く、残る差はブロック化とスレッド化にある（トラッキング項目 #24932）。出典：IREE v3.13.0、PR #25000

PyTorch fork：五つの朝に連続して整枝を再適用、10-23 に初めて一時停止

riscv ブランチの今週の運用リズムはすでに固定されている。毎日 03:00 前後にブランチ全体が書き換えられ、先頭は順に 8b254cfd（10-18）、44826095（10-19）、7f49d33f（10-20）、3c1ea315（10-21）、29259d90（10-22）となる。各書き換えの特徴は、コミッタの時刻が統一的に書き換えられ、ローカルパッチのタイトルが一つずつ変わらず、変化は上流ベースラインの同期範囲のみにあることだ。10-21 の回を直前の先頭と比較すると、先行 67、遅延 24、208 ファイルの差異であり、10-22 の回は先行 60、遅延 24、106 ファイルの差異で、差異面はすべて上流（MPS オペレータ、Metal カーネル、CI ワークフローと pr_review スクリプト）にあり、ローカルパッチファイルは差異リストに現れていない。

ローカルパッチの系列は安定して四組である。riscv64 ローカルイメージ（#51）、bytes_to_scalar 浮動小数点修正（#44）、inductor opinfo blocklist（#50）、linear cross entropy の ULP 許容範囲限定（#42）、加えて CI 系列（#20 core/full 分割、#21 CI ワークフロー修正、#40 Jenkins 失敗後の継続解析、#41 判定バイパス）。マージ側は今週新規なし。直近五週間の最初のマージは PR #51「Add riscv64 image locally」で、10-17 00:04 に squash 方式で着地し、.ci/docker/build-riscv64-local.sh を追加してビルドとイメージスクリプトを調整し、月曜日のデイリーレポートの三日間ウィンドウに現れた。

特筆すべきはリズムの中断である。10-23 の朝には新たな書き換えが現れず、10-24 午前の確認時点で、先頭は依然として 10-22 の 29259d90 にとどまっている。これは今回の「ベースライン日次更新」開始後、初めての空白である。リズムが毎日から適期に低下することを意味するかは、次の周期で確認する必要がある。七件のオープン PR（#23 Enable XNNPACK、#35 テスト用、#36 タイムアウト緩和、#38 DataLoader 一時無効化、#43 パッチ簡素化、#46 ATen RVV サポート、#48 RVV CPU capability）は丸一週間オープンのままで、毎日リプレイとともに同批のタイムスタンプが更新され、新たなレビュー意見はない。うち #46 と #48 は依然として RVV 能力向上の二本の主線提案である。出典：riscv ブランチ、PR #51、PR #46、PR #48

三度のベース交換の跨度の差異がメカニズムを説明する。初日は滞留の消化、後の二日は単日増分の通常の追趕である。ブランチはすでに「毎日ベースラインを一小歩前進させる」状態に入り、PyTorch と同じ運用に収斂している。パッチ系列は完全に保持され順序も変わらず、BOSC AME 拡張（#16）から A100 HP/SP と pack/unpack スケジューリング（#31、#32）まで、Buckyball ベンダー拡張（#20）、Pebble コア ISA との整合（#23）、xtame 設計更新（#27）、IME ビルトイン下降（#30）を含む。二件の FPGA バックエンド PR（#25 BOSCAME FPGA、#28 xboscame FPGA）はベース交換のたびに同批でタイムスタンプが更新され、丸一週間オープンのままで、レビューの進展はない。出典：riscv ブランチ、PR #25、PR #28

triton-riscv：夜間ビルドが一期回復後に停止、PR #85 は依然唯一の活発な提案

tilelang-riscv：10-16 の五コミット以降、一週間静寂

論文：長ベクトルプロセッサ上で FlashAttention を再配置、実測 1.84〜2.08 倍高速化

arXiv 2610.29489v1「Reorienting the Vector Axis: Restructuring FlashAttention for Long-Vector Processors」（Emmanuel Irabor、Marc Casas）は、PyTorch の CPU FlashAttention カーネルを 2KB ベクトルレジスタを備えた RISC-V CPU に移植し、まず手厳しい基線を示す：ピーク浮動小数点スループットのわずか 16.2% にしか達しない。

原因分析は具体的である：元のカーネルはクエリ行ごとに逐次進み、V との積は 64 要素のヘッド次元に沿ってベクトル化され、softmax の行ごとの最大値と総和は「レジスタ全体をスカラーに潰す」リダクションであり、ソフトウェア指数関数の多項式係数はさらに tile データとベクトルレジスタを奪い合い、スタックへのスピルを引き起こす。この 3 つの重なりがベクトルレジスタ利用率を上げられなくしている。2 つの改善はいずれもアルゴリズムと数値を変えない：第一に、スコア tile と実行出力を一緒に転置し、クエリを線形連続軸上に落とすことで、「1 つの tile にいくつのクエリを詰めるか」という 1 つのパラメータがカーネル各段のベクトル長を統一的に決定し、2 つのリダクションが自然に消える；第二に、多項式係数をスカラーレジスタへ移し、スピルを解消し、softmax のベクトルメモリアクセス命令を 78.7% 削減する。

実測：ヘッド次元 64 のとき、2 項目を合わせてカーネル全体のサイクルを 1.84〜2.08 倍の高速化に短縮し、浮動小数点利用率は 16.2% から 29.7% へ上昇；同設計の FPGA では 2 項目の改善の順序が一致し、かつ収益はさらに高く、2.71 倍に達する。本スタックにとっての意義は数字ではなく方法にある：ベクトル長の適応とレジスタプレッシャーこそが triton-riscv と tilelang-riscv が RVV 降級において抱える構造的問題であり、「intrinsics があるかどうか」ではない；文中の「マシンに合わせて tile 内のクエリ数を一致させる」は IREE が Tile N を vlen/8 と取るのと同種の決定に属し、直接同口径の比較が可能である。出典：arXiv 2610.29489

七、トレンド観察

パッケージング単位が「ソースツリー」から「依存パッケージ」へ、今週は閉包補完から規範補全への重心移行が完了

今週 637 件のコミットの主線はただ一条： 「ソースコードに vendor する」を「依存ごとにパッケージングする」に改めることである。Rust 側では crate 閉包を補完（uv ビルドバックエンドの 23 個の rust-uv-* パッケージを含む）、Python 側では fsspec の全主流クラウドバックエンドを補完、Go 側では vendor を除去し、削除されたディレクトリの後に必須となるインポートパスを逐条補出した。順序そのものが示すのは、vendor 除去の完了条件が vendor ディレクトリを削除することではなく、依存される各モジュールがディストリビューション内で元のインポートパスで解決できるようにすること——インポートパスの補完を欠けば、vendor 削除は直接コンパイル失敗を招くだけである。

10-22の重点は「コンパイルできるか」から「監査可能か」へ移った。54件のソースチェックサム補完と%autochangelogへの切り替えで、パッケージ名mからxの範囲をカバーした。ソースチェックサムはビルド入力の検証可能性を決め、%autochangelogは変更記録を手書きではなくコミット履歴から生成することを決める。この二つが通れば、CVE修正は統一された経路で伝播する。RuyiAIへの間接的価値は上位層の可用性にある。PyTorchのDataLoader、checkpoint、データセットツールは一般にfsspecを経由してリモートストレージにアクセスするため、バックエンドが揃っているかどうかが訓練スクリプトをK1/K3上で動かせるかを直接左右する。ディストリビューションが上位層のために補うこの部分の依存は、単一のオペレータ最適化よりも「使えるかどうか」を大きく決定づける。

リリースチャネルが新たなボトルネックに：パッケージマネージャとインデックスの二重沈黙、原因はコードに非ず

今週は二つの現象が併存した。ruyiパッケージマネージャの0.53.0は丸一ヶ月動かず、0.54.0は10月末に確定。packages-indexは10-13以降ゼロコミット。079号で示された説明はISCASソフトウェア源のデータ同期異常で、ビルド済みパッケージが公網に反映されていないというもの。これにチームの峰会用の投入が重なり、「コード側は毎日数百コミット、ユーザー側は新しいパッケージが見えない」という対比が生じている。

これはディストリビューションの進捗評価をコミット数だけで見てはいけないことを示唆する。パッケージ補完、チェックサム補完、依存パス補完はいずれも最終納品の準備だが、どこか一环がリリースチャネルで詰まれば、ユーザーの実体験は停滞となる。次の観測点は0.54.0が予定通り月末にalphaを出すか、そしてISCASの同期問題が2026.10バージョンとともに解決されるかだ。

リプレイは「機会を見て」から「毎日」へ：二つのriscvブランチが同一の運用に収束、レビューが依然として実際のメトロノーム

PyTorchは10-18から10-22まで連続五日の朝に全面書き換えを行い、LLVMは八日間の沈黙の後10-21、10-22、10-23に連続三回リベースした。共通の特徴はコミッター時刻が統一的に書き換えられ、パッチタイトルの集合が変わらず、コミットハッシュが毎日無効になること。差異はスパンのみ——LLVMは初日1769件先行（八日分の滞積）、その後二日は約275件（単日の通常追趕）。

工学的意義は「上流に追従する」ことと「ローカルパッチを維持する」ことを分離することだが、代償は履歴が追跡不能になることだ。ハッシュで参照する下流（ミラー構築、CIキャッシュ、issue再現）は当日またはリベースの度に無効になるため、これら二つのブランチを読む際はハッシュではなくパッチタイトルの集合をバージョン判断の基準とすべきだ。より注目すべきは今週パッチ自体に新規がないこと——PyTorchの七件のオープンPR、LLVMの二件のFPGA PRはいずれもタイムスタンプを更新しただけで、新しいレビュー意見もマージもない。リプレイ機構はすでに安定し、実際のメトロノームはレビューキューの消化速度に変わった。10-23にPyTorchが初めてリプレイを暂停したが、リズムの調整かどうかは次周期で確認が必要だ。

拡張の実装経路が成形：コンパイル、シミュレーション、オペレータの三層が揃って初めて可用、揃った後のボトルネックはハードウェア実測へ

AMEを例にすると、今週は拡張が提案から可用に至る完全な経路が見えた。まずバックエンド設計と命令セット定義（LLVM #16、#24、#27、#29）があり、次に lowering とスケジューリング実装（#30、#31、#32）があり、同時にシミュレータが実行可能なセマンティクス（QEMU ame-0.6）を提供し、最後にオペレータライブラリがテスト可能な kernel と検証スイート（AME-operator）を提供する。Zttも今週一侧を補完した——ruyisdk/llvm-projectのAMEブランチがspec v0.6初版サポートを落とし、GCC側のZtt Mdサポート、QEMUのZtt命令族実装と対応する。

P拡張は同じ道を辿るがすでに後半戦にある。QEMUは全命令をカバー（12件の収尾バッチ）、GCCは0.6に更新、LLVM側はmulq、乗算上位累加、sati/usati、Packed Pairなどのintrinsicsが分批で上流にマージされた。対照的に見ると、P拡張はアプリケーション側のbenchmarkが欠け、AMEは実機が欠けている。この順序は方法として記録に値する。シミュレータがなければコンパイラを検証できず、オペレータライブラリがなければシミュレータを検証できない。三者が揃う前に性能を語る意味はなく、揃った後にボトルネックはハードウェアと実測に移る。今週の進展は「揃った」ことであり「より速く」ではない。

RVVバックエンドの焦点は「命令があるか」から「タイリングとスレッド化」へ

IREEは二日でf32からf16への精度段階を走り切った。二回とも同じlowerRiscvVFmaccLikeと同じアキュムレータ合法化を再利用し、順序はまず正しい経路（f32）を保証し、次に拡張の可用性に応じて最速のもの（f16ネイティブ、f16拡幅、+zvfhminフォールバック）を選び、コストモデルが三経路それぞれに価格付けする。X60での実測がボトルネック位置を明確にした。シングルスレッドのinner_tiledはすでにmmt4d ukernelより速く、4スレッドと8スレッドはまだ遅い。

arXivの長ベクトルFlashAttention再構築が出した結論も同源だ。スコアtileと実行出力を転置し、クエリを線形連続軸の後に落とすことで、二つのリダクションが自然に消え、レジスタ溢れが解消され、コア全体の周期が1.84〜2.08倍に低下し、浮動小数点利用率が16.2%から29.7%に上昇した。両者は同じことを言っている——シングルコアの命令選択が到位した後、残るのはタイリングパラメータとスレッド化だ。tilelang-riscvとtriton-riscvにとって、これは一つ一つ対照できるロードマップだ。Tile N = vlen/8の取り方、コストモデルの段階分け方式、tile内クエリ数とベクトル長の結び付き関係は、いずれも自前のloweringで同口径の比較を行う価値があり、「f16をサポートするか」だけを見るべきではない。

ディストリビューションがデスクトップと仮想化検証スタックを整備し始め、プラットフォーム形態にサーバーと組み込みの二経路が出現

openRuyi のオープン PR キューに同方向の提案が一群現れた。qemu の GUI テスト機能の有効化（#1421）、virglrenderer の新規追加（#1415）、ovmf の fwupd サポート（#1436）、ydotool の新規追加（#1457）、xorriso の man ページ衝突の修正（#1489）である。5項目はそれぞれ仮想化、グラフィックス仮想化、ファームウェア更新、入力自動化、光ディスクイメージツールチェーンに属し、合わせて「RISC-V 上で完全なデスクトップを動作させ、それを自動検証する」という方向を指し示す。これはサミットで展示された「AI 駆動 IDE によるグラフィカルテスト」と同じ要求の両端である。

プラットフォーム形態には同時に分岐が現れている。サーバー級は進畳 V100 に代表され、仕様における UEFI、ACPI、SMBIOS が必須要件となり、BRS 適合性テストとインストール経路が参入条件となる。組み込み・コンシューマー級は K1/K3 に代表され、その道筋はボードイメージ、ツールチェーン、サポートマトリクスである。今週 ruyi-imager が K3 の UFS と UEFI プロビジョニングサポートを新規追加したことは、この分岐のツール側における最初の具体的動作である。一方、openRuyi メインリポジトリは週全体でサーバープラットフォーム関連のコミットがゼロ件であり、V100 の互換性リストが実現できるかは 2026.10 バージョンと今後のファームウェアラインの動向次第である。
