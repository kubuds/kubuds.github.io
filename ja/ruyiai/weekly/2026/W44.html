今週のリベース系列は 10-25 の 474 件、10-26 の 221 件、10-27 の 237 件である。三回のリプレイに共通する特徴は一致している。先頭のタイトルは依然として「[RISCV] Add A100 HP/SP and pack/unpack lowering with calibrated scheduling (#31)」であり、遅れている 26 件はちょうどローカルパッチセットの件数に等しく、タイトルと順序を一件ずつ比較しても変化はない。10-27 の回では、20 件のローカルコミットが同一分内に書き換えられ再プッシュされた（コミッター時刻は 15:00:29 から 15:00:31 に集中し、一方で著者時刻は 7 月 1 日から 10 月 3 日まで並んでいる）。つまり、この三日間の動作は既存のパッチセットを新しいベースラインへ移すことであり、機能の増分はすべて上流に由来する。

10-28 からリズムが変わった。ブランチは cf00909d の一件だけ進み、内容は .github/workflows/autorebase.yml（+244/−0）である。著者ソースリポジトリのデフォルトブランチにインストールされ、workflow_dispatch でトリガーされ、二つの入力は PR 番号と「事前演習のみでプッシュしない」（デフォルトで有効）であり、実行環境は ubuntu-24.04、タイムアウトは 90 分である。コメントは、書き込み権限を保持した状態で PR コード、フック、ビルド、サブモジュールを絶対に実行しないことを明確に要求しており、git 設定は hooksPath、attributesFile、fsmonitor をすべて /dev/null に指定している。コンフリクト処理は -Xours でカバーできないシナリオに対して ls-files --unmerged を個別に実行し、第 2 ステージがあればローカルを採用し、なければ削除し、さらに「等価パッチ」を識別して重複する旧ベースラインパッチを破棄できる。

10-29 23:00 のブランチ全体リプレイで、実際に新規追加されたのは [workflows] Push rebased PRs directly and document contribution options（著者時刻 10-29 09:59）の一件である。autorebase.yml から 8 行を削除し（dry_run 入力と事前演習ブランチを除去）、82 行の RISCV_CONTRIBUTING.md を新規追加した。ガイドは二つの道筋を示している。まず issue を開き、メンテナが現在の riscv から work/issue-NNN 作業ブランチを切って、コントリビューターがその作業ブランチへ PR を出す。あるいは直接 riscv へ PR を出して手動でリベースをトリガーし、ワークフローが --force-with-lease と明示的な期待 SHA を伴ってソースブランチへプッシュバックする。ドキュメントはさらに、GITHUB_TOKEN でプッシュすると通常は後続の push/PR ワークフローがトリガーされないため、更新後の SHA 上で CI が実行されたかどうかは手動で確認する必要があると注意を促している。

判断：このブランチの日常的な動作は以前から完全に「ベースラインに追従する」ことになっており、5 日間で 5 回、ローカルパッチに変化はゼロであった。今週の新情報はガバナンス方式が変わったことである。外部コントリビューターが「常に一歩遅れる」コストをメンテナの手動判断から切り離し、明確な境界（PR コードを実行しない、riscv 自体を書き換えない、自動マージしない）を持つスケジューリングにした。事前演習を廃止して摩擦を下げる一方で、「履歴を誤ってプッシュする」リスクをコントリビューター側へ前倒ししており、その効果は次の一、二件の外部 PR を待たなければ検証できない。

llvm-project 上流：17 個の RISC-V pass が一時間で NewPM へ移行

日付：2026-10-26　情報源：InsertVSETVLI 移行、PreAllocZilsdOpt 移行、DeadRegisterDefinitions 移行

10-26 のリベースで取り込まれた 221 件の上流コミットのうち、RISC-V 関連は 21 件で、そのうち 17 件が NewPM 移植であり、著者はすべて Aiden Grossman、時刻は 12:59 から 13:55（北京時間）に集中し一時間未満である。リストはバックエンドの主要 pass をカバーしている。命令選択後の VSETVLI 挿入、CSR の読み書きと VXRM 書き込み、VMV0 除去、圧縮命令生成、スタックプッシュ/ポップ最適化、ベースアドレス結合、LoadStore 最適化、Zilsd 事前割り当て、分岐最適化と QCRelax マーキング、さらにレジスタ死定義除去、冗長コピー除去、間接ジャンプ追跡、ランディングパッド設定、定数昇格である。

残り4件は3つの方向に分かれる。vxrm-pipeline-flush 属性は VXRM の投機的書き込みをフラッシュ保証付きループ内に制限する。LSR は Zibi ターゲットで等値比較をループ出口として優先選択する。GlobalISel は G_FPTOSI_SAT と G_FPTOUI_SAT の合法化を補い、浮動小数点から整数への飽和変換をグローバル命令選択経路で利用可能にする。もう1件は収集散播の降級と VL オプティマイザの分析への適用を遅延リクエストに変更する。

意義は個々の変更ではなくパイプラインの帰属にある。この一群の pass は長らく LegacyPM に掛かっており、NewPM へ移行した後は新しい pass manager の分析キャッシュ、pass 順序、デバッグインターフェースと整合する。下流 fork への直接的な影響は、基底を切り替えるたびにこの一式の変動が付随することであり、-passes= の名称と pipeline 構成もそれに伴って上方へ移動する——これも今週 riscv ブランチが「基底は変わったがパッチは不変」の際に、実際の中身が変化した数少ない箇所の一つである。

7. トレンド観察

VIR は「表現—呼び出し—突合」を走り切ったが、結論は「損失を持ち込まない」にとどまる

過去3週間、この主线はずっと表現力を補ってきた：10-26 の一晩で7件のコミットでスケーラブルベクトルを補い、10-27 に Python バインディングを追加し、10-28 には K3 のデコードアテンションを丸ごと移行し、ボード上のスループットで突合した。3つの数字を合わせてこそ今週の意味がある——数値はビットレベルで一致、ベクトル命令数も同一（各178条）、スループット区間は重なる。自作方言は「動くが遅い」という関門で詰まりやすいが、今週は少なくともこの関門を一時的に通過したことを証明した。

しかしこれを「VIR は手書きカーネルに追いついた」と読むのは行き過ぎである。正確な言い方は「K3 デコードアテンションのこの区間において、固定ベクトル長の下で損失を持ち込まない」である。2つのギャップは明確だ：カバー範囲はデコードアテンションのみで、A210 カーネル、MoE、量子化とプリフィル経路はいずれも手つかず；スケーラブルベクトルは明示的に無効化されており（use-scalable=false）、次のコミットで有効化されればベクトルサイズはコンパイル期に決定されなくなり、LMUL 4 のグループ化仮定が緩む。その際に数値と命令数を守れるかは再突合が必要だ。著者自身も同一コードを2回ビルドした際の2%の差異を PR に書いており、この量級はまさに「互角」結論の境界を示している。

ブランチガバナンスの分岐：llvm はルールを書き予演を廃止、pytorch はリプレイと同期ボットに依存

同じ月内に2つのブランチが2つの答えを出した。llvm の riscv ブランチはパッチセットが大きく（26件）、外部貢献も多く、コンフリクトと履歴ドリフトが主なコストであるため、ドキュメント（RISCV_CONTRIBUTING.md）を書きワークフロー（autorebase.yml）を整備する価値があり、「予演」のステップを削除した——成功すれば即プッシュ、摩擦を最小化しリスクを貢献者に前倒しし、--force-with-lease と SHA 再検査で担保する。pytorch の riscv ブランチはパッチセットが小さく（11件）、メンテナ自身が一度リプレイするコストがプロセス維持コストより低いため、毎日または隔日のブランチ全体リプレイを続け、さらに同期ボットでベースラインを上流最新に引き上げている。

両者の共通点は「ローカルパッチセットが長期的に不変」であることだ：llvm の26件、pytorch の11件は、今週いずれも新機能の追加はない。これら2ブランチを追跡する正しい方法は SHA やコミット数を見ることではない——リプレイはコミッター時刻を一律に書き換え、コミット数を上流に伴って膨張させる——パッチタイトル集合と、上流が何を持ち込んだか（今週は17個の pass の NewPM 移行と P 拡張の isel 補完）を見ることである。

あるブランチガバナンスが効いているかは、2つの検証可能なシグナルで判断できる：llvm 側では、ワークフロー稼働後に外部 PR が実際に増えたか（2週間以内に新ベースラインで提出する者がいなければ、ボトルネックはリベースツールにない）；pytorch 側では、リプレイが毎日へ再安定したか（今週は7日間の静默後の一回の補完であり、定期ではなく流水ではない）。

パッケージングが RuyiAI スタックの真のボトルネックとなり、議論に価格が付き始めた

#1350 は約1か月にわたり議論され、核心的な対立点は buddy-mlir が内蔵する LLVM を外部化するか否かであった。先週の見解はまだ「GCC も使えるが、少なくとも 1.5 倍の時間がかかる」であったが、今週、作者は実測値を示した。riscv64 上で 8814 秒が 24798 秒になり、2.81 倍であり、しかも GCC を使った回はリンク段階で失敗した。議論の性質はこれにより技術的嗜好からビルドファームのスケジュール計算へと変わった。2.81 倍は、マシン占有、タイムアウト戦略、リリースウィンドウのすべてを再計算しなければならないことを意味する。

この件がスタック全体に示す示唆は結論ではなく方法にある。RISC-V ディストリビューションのパッケージングにおける多くの対立（vendor するか、ツールチェーンを外部化するか、IR をパッケージに同梱するか）は、最終的に「ビルド時間、イメージサイズ、再現性」という 3 つの測定可能な数値に落とし込まれる。同じ週に openRuyi は「LLVM IR をパッケージに同梱する」路線を撤回し（#1509）、#1350 は 2.81 倍で「LLVM をパッケージ内に残す」を守った。二つの判断の方向は逆であるが、根拠は同じ種類のコスト計算である。

さらに見ると、#1350 の今週のレビュー意見は設計路線から spec の書き方へと移っている（BuildRequires の欠落、Provides の整合、パッチ形式、空の %check コメント）。これは「ディストリビューションに飲み込めるか」という問題が「パッケージ自体が十分に常规的か」という問題に変わったことを示す。三つの非常規点——buddy-mlir が LLVM を内蔵すること、triton が git 実行ファイルに依存すること、tilelang が buddy-mlir ツールチェーンを発見する必要があること——はいずれもパッチと説明を必要とし、各説明はメンテナが時間をかけて判断しなければならない。三つ組を月次リリースのリズムに乗せたいなら、それらを一、二本の明確なパッケージング規約に収束させること（例えばツールチェーンは一律 buddy-mlir が提供し、パッチは一律 git format-patch のパッチスタックを使う）が、レビュー意見に一つ一つ回答するより手間が少ない。

月末の約束がそろって後ろ倒し：ディストリビューションは「月次で量を敷き、週次で掃除する」リズムへ

今週、二つの月末約束が同時に果たされなかった。ruyi 0.54.0 は依然として 09-18 の alpha のみで、openRuyi 2026.10 は未リリースである。これに対応して、openRuyi 主リポジトリの今週 234 コミットのうち、KDE フレームワークが一度に 64 パッケージ、Samba 全家連動、qemu 11.1.2 と libvirt のバックポート、12 件の C/C++ セキュリティ更新——これは典型的な「量を敷くことと掃除の並行」であり、「バージョン切り替え前の凍結」ではない。

二つのパイプラインのリズムの違いも記録に値する。KDE パッケージは参照できる上流 spec があり、既定のバージョンリズムがあり、再パッケージングは機械的な動作であるため、1 日で 64 パッケージを完了できる。一方、RuyiAI 三つ組はゼロから書いた spec であり、「なぜ LLVM をパッケージ内に残すのか」を説明しなければならず、「なぜ %check が空なのか」も説明しなければならず、09-21 に開始してから今もなお手戻りが続いている。ディストリビューションの「月次で量を敷く」能力と「新しいパッケージを受け入れる」コストは非対称であり、後者はパッケージ自体がどれほど常规的かに依存する。

読者にとっての実際的な意味：ruyi ユーザーは 10 月末でも 0.53.0 を受け取ることになる。0.54.0 が 11 月初めにリリースされたとしても、ISCAS ソフトウェアソースが復旧しているかを見る必要があり、さもなければ ruyi update で見えるパッケージリストはリポジトリの実際の状態より遅れる。この二つは次のサイクルの首要の確認事項である。

欠陥発見が単一の入口に依存し、受け入れチェーンは修正チェーンより脆い

今週の triton-riscv の三件の修正の共通の來源はテストスイートではなく、「FlagGems オペレータを triton-riscv に載せる」という行為そのものである。テンソル充填値のマスク付きロード、ループに持ち越される gather オフセット、散列オペレータの重複インデックス比較——いずれも降級層と検証層の境界に落ちている。この種の欠陥はコンパイラ自身の lit スイートでは育たず、実際のオペレータライブラリがバッチ方式で上から圧力をかける必要がある。

順序の問題がこれに伴い露呈した。修正が先に着地したが、それらを必要とする移行 PR #56 は 09-16 で止まっている。一群の「ある用法のために用意された修正」には、当面対応する用法が走っていない。もし #56 が復旧するとき Triton 上流がさらに何回か変わっていれば、三件の修正が新しいベースラインとまだ互換かどうかを再検証する必要がある。もし長期間復旧しなければ、この端到端検証セットは停止に等しく、次の一群の欠陥は外部の利用者がぶつかるまで待つことになる。サイクル末尾に #56 は一度更新された（10-30 20:50）が、依然としてマージされていない——これは次のサイクルで最も注視に値する箇所である。

推論は実行可能である。「実際のモデルを走らせられること」を目標とするスタックにとって、移行を常駐リグレッションにすること（たとえ数十のオペレータだけで、毎晩一度走るだけでも）は、さらに数件の修正をマージするより価値がある。ツールチェーン層面の証拠も同じ週に現れている——#83 の検証は今週の三件の中で最も硬い一件であり（lit 291 通過、18 項目の実行時チェック）、しかもそれはちょうど実際のオペレータとの統合が最も深い一件でもある。

ベンチマーク側の長期的空白が「最適化が有効か」を答えられなくする

VecIntrinBench は 02-13 で停止し、cpuinfo は 05-20 で停止し、IntrinTrans は 06-25 で停止し、FBGEMM は 07-13 で停止している——四つのベクトル関連リポジトリは全週ゼロコミットで、更新停止期間は月単位に及ぶ。同時に、今週の性能結論は K3 ボード上のスループット区間に頼るしかなく、作者は同一のコードでも二回のビルドで 2% 差が出ると明記している。三件の修正の検証も通過数を与えるだけで、ベクトル化品質に関するいかなる指標（命令数、占有 LMUL、レジスタスピル回数）も与えていない。

これは今週新たに増えた問題ではないが、三件のマージと一度の性能対賬がそれをより鮮明に照らし出している。「ベクトル能力の上昇」を目標とするスタックが、継続的に走らせるベクトル組み込みベンチマークを欠くと、後続の最適化が本当の向上なのか変動なのかを判断しにくい。次に本当に補うべきは、より多くの lowering ではなく、毎晩走らせられ、命令数と LMUL を出せるベンチマークである——さもなければ「性能横ばい」と「性能向上」は 2% のノイズの下では区別できない。
