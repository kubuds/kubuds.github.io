triton-riscv：一日で「パッチを当てたブランチ」から「上流プラグイン」へ（11-05）

日付：2026-11-05　情報源：PR #98、コミット一覧、PR #92

改造は三箇所に分かれる。第一はバックエンドの形態である。Triton の TRITON_PLUGIN_DIRS メカニズムにより backend/ を triton_shared バックエンドプラグインとしてインストールし、エントリポイントを登録し、C++ プラグインを libtriton.so にリンクし、triton-shared-opt もパッケージにコピーする。独立配布パッケージはそれに伴って消滅し、コード内のインポートは一律 triton.backends.triton_shared 経由に変更された。バックエンド自身は paths.py を通じて buddy-opt、buddy-llc、mir-translate、triton-shared-opt を探すように変更され、CPU ドライバは GPU バックエンドが全くない場合にのみアクティブ状態になると宣言する。

第二はパッチ集のゼロ化である。patches/ ディレクトリとパッチ適用スクリプトはすべて削除された。パッチ集がこれまで存在した理由は二つあった。NVIDIA/AMD ツールチェーンのない環境で Triton をビルドできるようにすること、そして LLVM API の頻繁な変更を吸収することである。現在 buddy-mlir の LLVM 配布版は NVPTX/AMDGPU ターゲットと lld を備えており（#1027）、さらに Triton の GPU 依存パスを stub ディレクトリに向けることで、二つの理由はどちらも成立しなくなった。

三つ目はパッケージ出力パスの統合である。release.sh は二つ目の wheel を組み立てなくなり、ツールを剥がして直接 bdist_wheel するだけになった。Makefile は setup、build、test、lit、clean の統一入口となった。ついでに Python 3.14 の落とし穴も一箇所修正した。setup.py 内の shutil.which("lit") は pip でインストールされた lit コンソールスクリプトを優先的に取得するが、LLVM ディストリビューションに同梱されているものは main() を呼び出す際に if __name__ == "__main__" の保護がなく、forkserver のマルチプロセスがメインモジュールをインポートする際にそれを再実行してしまい、lit ターゲットが 80 並列で失敗する原因となっていた。

代償は同じ PR の説明に書かれている。Triton 3.9 のフロントエンドはバックエンドから backend_name などのフィールドを読み取るため、それが欠けるとすべての tl.atomic_* 呼び出しが AttributeError を投げ、riscv64 上では 383 個の FlagGems テストケースが失敗する。backend_name、default_dot_input_precision、deprecated_fp8_dot_operand_dtypes の三つのフィールドを補って初めて失敗範囲は収束した。サンプル側にも譲歩がある。上流は asin/acos/atan/atan2 のフロントエンドパッチを拒否したため、サンプルは libdevice を使うように変更し、それによって同じ __nv_* extern_elementwise まで落とし、さらに triton-shared で MLIR math オペレータに変換している。

triton-riscv 関連の三件：夜間・週末リリース、16 プロセス pytest、cp312-abi3 wheel（11-05 から 11-06）

日付：2026-11-05 から 2026-11-06　情報源：PR #99、PR #100、PR #101、Release リスト

#99 はリリースのリズムを buddy-mlir に合わせた。夜間ジョブは nightly/<date>-<sha> のプレリリースを発行し、週末ジョブは release/<date>-<sha> を発行して最新バージョンとしてマークする。新しいコミットがない場合はスキップし、release はすべての wheel のアップロードが完了するまでドラフト状態を保ち、workflow_dispatch は一度だけの帯域外 dev/patch 選択を提供する。当日の二件の夜間版はすでにこのリズムで産出された。

7. トレンド観察

配布経路は打通したが、「パッケージング完了」は「能力同期」ではない

#1350 の意義はバージョン番号になく、配布経路が初めてディストリビューション設定として書かれたことにある：以前このスタックを使うには、自分で triton-riscv、tilelang-riscv、buddy-mlir を取得し、ドキュメントに従って BUDDY_MLIR_BINARY_DIR 一类の変数を設定する必要があった。現在は openRuyi のパッケージングリポジトリにこの三コンポーネントが存在し、ユーザーのインストール障壁は「コンパイラをビルドできること」から「パッケージをインストールできること」に下がった。

しかし三份の spec がアンカーするコードはいずれも今期の上流より早い：triton は 09-13 で停止、tilelang は 10-28 で停止、buddy は 0.1.2 で停止しているが、三つのリポジトリはいずれも今週新たな動きがある。最も際立つのは tilelang——11-03 にマージされたばかりの PR #5 は十八日間の沈黙後の最初の機能であるが、当日マージされた RPM には含まれていない。バージョン文字列 3.8.0+git20261103 は誤読を強化し、パッケージング日をコード日と見做させる。この落差を解決するには、定期的な bump フローを確立するか、パッケージ説明にスナップショット日を明記するかのいずれかが必要である。さもなければ機能がマージされるたびに、パッケージとリポジトリの差はさらに広がる。

プラグイン化はパッチコストをバージョン結合に置き換え、383 件の失敗用例が頭金

triton-riscv の收益は直接的である：今後上流のバージョンアップに追随する際にパッチの再適用が不要になり、リリースは wheel 一つだけになり、インストール面は二つのディストリビューションパッケージから一つに減る。代償も同樣に明確であり、しかも同じ日に露呈した：Triton 3.9 のフロントエンドはバックエンドから backend_name フィールドを読み取り、それが欠けると 383 件の FlagGems 用例が失敗する。上流の拡張点に寄生することは、上流フロントエンドの暗黙の契約が満たすべき必須インターフェースになることを意味し、これらの契約はしばしばドキュメント化されておらず、テストでしかぶつからない。

今回の改造が成功したかどうかは、今日何行削除したかではなく、次回上流バージョンアップ時の再適用コスト、および FlagGems のような下流スイートが依然として専任でバージョンを注視する必要があるかどうかで判断する。今週末までに、上流追随の経路はすでに明確であるが、配套の受け入れパイプラインはまだ確立されていない：#56「Migrate additional FlagGems operators」は依然としてオープン状態であり、「この批のオペレータが riscv64 上で動作するかどうか」という問題は依然として PR の中でしか回答できない。

バックエンドが今週の主軸となり、フロントエンドとランタイムは静止

今週の検証可能な增量はほぼすべて「コンパイルと降級」に落ちている：LLVM の AME バックエンドはレジスタ分類と tile スケジューリングを補完、buddy-mlir の BOSCAME は契約から FPGA まで打通、VIR は set_vl の VLEN セマンティクスを厳格化、tilelang は streaming load の降級経路を補完。一方、pytorch の RISC-V ブランチは三度再適用され、機能增量はゼロ、main 側の一百余りの上流同期には RISC-V に関するものが一件もない。

この分布は、この段階の重点が既存オペレータを RISC-V 上で正しく降級させ安定して動作させることにあり、フロントエンドのカバレッジ拡大ではないことを示している。下流の使用者にとって、短期的に感知できる変化はコンパイル産物と JDK の動作に現れ、新しいフレームワークサポートリストには現れない。これに配套する短板も同じ箇所にある：性能方向で唯一明確に最適化を目標とする triton PR #85 は依然として 10-18 で停止し、半月動きがない。

リリースリズム：beta は出たが、正式版と月次版は依然として期間外

十月末の二つの月次約束が同時に不履行となり、十一月第一週にそれぞれ半分の下文がある：ruyi は 11-02 に 0.54.0-beta を出し、39 日間の断絶後の第一跳となり、0.54 の正式版を 11 月 11 日前後に定めた；openRuyi の 2026.10 月次公告は 11-07 まで依然として現れず、初の丸一ヶ月欠版となった。

二つの線のコード側はいずれも停滞とは言えない——openRuyi 主リポジトリは今週 156 筆のコミット、ruyi には ABI 探測とパッケージ取得修復が落地している——したがって卡点はバージョン凍結、公告執筆、イメージビルドとリリースの段階にある。これは先週の判断と一致する：このエコシステムの「物を作る」と「物を発信する」は二つの能力であり、前者は複数のリポジトリで同時に推進され、後者は直近二ヶ月で一度も期日通りに完了していない。

基準側の長期的空白が「最適化が有効かどうか」を回答不能にする

VecIntrinBench は約9か月間更新停止、IntrinTrans は4か月、FBGEMM は3か月で、3つのリポジトリはすべて週間でコミットゼロ。同じ週に、glibc と newlib は18個のベクトル数学関数を追加し、LLVM は6件の P-ext と Ztt v0.6 をマージし、buddy-mlir は209ファイルのマトリックスバックエンドを展開した——能力は拡張しているが、度量が追いついていない。

結果は抽象的なものではない。更新された組み込み関数ベンチマークがなければ、「コンパイラが実際にサポートする集合がどれだけ増えたか」に答えられない。常設の性能ベースラインがなければ、「BOSCAME パスが旧パスよりどれだけ速いか」に答えられない。今週の性能に関するすべての記述は「明らかな回帰は観測されていない」というレベルにとどまり、この種の記述は選型を支えることができない。

デスクトップパッケージと AI スタックは並行し、二つの線は同じリズムにない

openRuyi は週間156コミットで、うち74件は firecracker の Rust 依存クロージャ、37件は LibreOffice 依存チェーン——これはコンポーネントごとにバッチで進めるデスクトップオフィススイートのパッケージングである。同じ日（11-05）、RuyiAI スタックは triton-riscv を除いてすべて静かであった。pytorch の RISC-V ブランチはコミットゼロ、tilelang-riscv はコミットゼロ、llvm-project の riscv ブランチはコミットゼロ。

二つの線は異なる人々、異なるリポジトリ、異なるリズムで推進されている。読者にとって、パッケージング側の活発さを AI スタックの進展と見なすのは誤読である。プロジェクトにとって、この分業自体に問題はないが、ウィークリーレポートのレベルでは分けて記録しなければならない——さもなければ「コミット数」という指標は継続的に誤った繁栄感を与え続ける。
