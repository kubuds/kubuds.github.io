今日の重点：K3 デコードアテンションを VIR に移行、性能は手書き RVV カーネルと同等（10-28）

日付：2026-10-28　出典：buddy-mlir PR #1014、K3 ドキュメント、triton-riscv PR #91、llvm-project リベースワークフロー

今期最も実質的な一歩は 09:36 に起きた。buddy-mlir の #1014「K3: write the decode attention in the VIR dialect」がマージされ（4 ファイル、+476/−14）、K3 w4g32 カーネルのデコードアテンションを丸ごと VIR 方言へ移した。これは単なる方言機能の補完ではなく、実モデルのカーネルを使って初めて突き合わせを行ったものだ。一方はこれまで手書きしてきた RVV ベクトルカーネル、もう一方は Python で組み上げた VIR カーネルであり、数値、命令数、ボード上のスループットを比較する。

手法は四つの層に分解できる。構築層ではもはやオペレータや型を手作業で組み上げず（従来は文字列にオペレータ名と型記述を書く必要があった）、buddy_mlir.dialects.vir の SetVLOp、load、shuffle、fma、reduce を使う。一つの work item は一つの vir.set_vl 領域であり、長さはヘッド次元の半分（64 レーン）を取る。各ヘッドは RoPE の二つの半分から組み上げたスケーラブルベクトルであり、領域はそのヘッドの (max, sum) を返す。回転層では q を領域内でロードし、回転し、スケーリングする。rotate_half は一つの vir.shuffle に落とし込み、cos/sin は等長の二行データとして保存するので、vir.from_vector は不要になる。メモリビュー層では memref.expand_shape を使い、q、KV cache、出力、および q の正規化重みを最終次元で 2×64 に分割する。正規化層（Qwen3 の q/k norm）は別途一次元の vir.set_vl 領域を開き、_head_rmsnorm のやり方に従って二つの半分の平方和を求める。

パイプラインのパラメータもそれに合わせて変更された。カーネルの降格は vector-width=128 から rvv-vlen=1024、use-scalable=false へ切り替わり、ベクトルサイズは A100 のレジスタに基づいて解析が決定する。領域内に vir.shuffle があるため、各ヘッドは 128 個の f32 からなる一つのベクトルグループ（LMUL 4）として保たれる。著者は PR の中で率直にこう書いている。use-scalable=true への切り替えは次のコミットで行う、と。旧来の _attn_decode_fn は残されており、A210 カーネルのデコードアテンションは依然としてこれを使っている。

結果は三項目とも強力だ。数値面では、q/k 正規化の有無にかかわらず、_attn_decode_fn とビット単位で一致する。機械語面では、二つの並列体がそれぞれ 178 条のベクトル命令を持ち、キー値ループは旧版と命令が同一で、唯一二か所のレジスタ溢出の再ロード位置が変わっただけだ。ボード上のスループット（K3、buddy-cli の貪欲デコード、三回交替、9 対の生成テキストは完全に一致）は三つの段階すべてが同一区間に収まった。63 token 後は 28.26~28.49 対 28.10~28.58、458 token 後は 26.82~27.13 対 27.02~27.04、900 token 後は 25.37~25.41 対 25.29~25.77。著者自身が注記している。同一コードを二回ビルドした差異は最大 2% に達し、区間は重なっている、と。

1.1 llvm-project：リベースをやめ、「著者フォークのワンクリックリベース」ワークフローを追加（10-28）

日付：2026-10-28　情報源：riscv ブランチコミット cf00909d、ワークフロー全文、riscv ブランチコミット一覧

前号の「五日間で五回目のブランチ全体再適用」とは異なり、今号の riscv ブランチのローカルパッチセットは一つも動いていない。ブランチヘッドは ed439f3e から一コミット進み、前号のヘッドとの比較では 1 コミット先行、0 コミット遅れ、変更ファイルは 1 つのみである。この新規コミット（cf00909d、著者 23:27、コミット 23:54）は純粋な CI 資産——.github/workflows/autorebase.yml、+244/−0 である。

ワークフローの設計意図はコメントに記されている。作成者ソースのリポジトリのデフォルトブランチにインストールされ、Actions で目標 PR 番号を手動入力して実行し、ソースリポジトリ自身の GITHUB_TOKEN を使用し、カスタムのシークレットやラベルは不要である。トリガー方法は workflow_dispatch で、2 つの入力——PR 番号（必須）と「プレビューのみでプッシュしない」（デフォルトで有効）——を取る。実行環境は ubuntu-24.04、タイムアウトは 90 分。コメントには「書き込み権限を保持した状態で PR コード、フック、ビルド、またはサブモジュールを絶対に実行しない」ことが明記されており、git 設定では hooksPath、attributesFile、fsmonitor をすべて /dev/null に指定し、GIT_TERMINAL_PROMPT=0、GIT_EDITOR=true としている。競合処理には専用の関数がある。-Xours で処理できないシナリオ（変更・削除の競合を含む）は 1 件ずつ ls-files --unmerged を辿り、第 2 ステージがあればローカルを採用し、なければ削除する。リベース時にはまずベースラインが既に祖先であるかどうかを判断し、「等価なパッチ」を識別して重複する古いベースラインパッチを破棄する。

この項目が解決しようとするのは、過去数期に繰り返し現れた具体的なコストである。ブランチは 1 日に一度全体をリプレイし、作成者の fork 上の PR は即座に遅れ、手作業で 1 件ずつリプレイするのは遅い上にパッチセットを乱しやすい。境界を明確にしておく必要がある。それがリベースするのは他者の PR であり、ブランチ自身の毎日の全体リプレイは依然としてメンテナーの操作が必要である。「ベースラインに追随する」コストを人手の判断からプレビュー付きの 1 回のスケジューリングへと引き下げるが、自動化されたトリガー条件は持たない。真の価値は、次の外部 PR が新しいベースラインで提出されたときに初めて検証できる。

2.1 openRuyi PR #1350：3コミットをリベース、GCC ビルドコストを2.81倍と定量化（10-28）

日付：2026-10-28　情報源：openRuyi PR #1350、レビューコメント、PR コミット一覧

16:22、RuyiAI 三点セットパッケージング PR の3つのコミット（buddy-mlir、python-triton-ruyiai、python-tilelang-ruyiai）が同一分内にすべて書き換えられ、明らかに最新メインブランチへのリベースである。現在の規模は9ファイル、+680/−0 で、前期の記録と比較して14行増えている。PR は 18:15 にレビューコメントにより再び更新され、コメント総数は13件で、依然としてマージされていない。

今期最も情報量の多いものは、作者の 10:41 の返信である。前期の見解は「GCC で代替可能だが、ビルド時間は少なくとも1.5倍」であったが、今期は実測値が示された：riscv64 マシン上で buddy-mlir のビルドを LLVM から GCC に変更すると、時間は 8814 秒から 24798 秒（約2時間27分対6時間53分）になり、2.81倍であり、しかもその GCC を使用したビルドはリンク段階で失敗し、完走しなかった。

この点は議論を立場の問題からコストの問題へと変えた。「buddy-mlir が内蔵する LLVM を外置きするかどうか」はもともと2つの技術路線の争いであったが、今ではディストリビューションのビルドファームが理解できる数字が出た：2.81倍はスケジューリング、マシン占有、タイムアウト戦略のすべてを再計算する必要があることを意味する。作者のもう一つの理由もこれによってより説得力を持つ——buddy-mlir が使用する LLVM は自身のパッケージ内でのみ使用され、かつこれらのパッケージは特定の LLVM コミットに固定されているため、パッケージ内に留めることで再現性が確保される。同時に彼は、triton 上流の setup.py には git が実行可能かどうかの強制チェックがあるため、git ビルド依存を追加するか、setup.py にパッチを当てるか（後者は triton のアップグレードで無効になる）のいずれかが必要であるとも説明した。

6.1 「表現できる」から「同じ速さで走る」へ：VIR が初めて実モデルカーネルで性能照合

過去 3 期にわたりこの主线はずっと表現力を補ってきた。10-26 の一夜 7 件で可伸縮ベクトルを追加し、10-27 に Python バインディングを追加し、10-28 には K3 のデコードアテンションを丸ごと移行し、さらにボード上のスループットで照合を行った。3 つの数字が合わさってこそ今回の意味がある——数値はビットレベルで一致、命令数も同一（各 178 条）、スループット区間は重複。自研方言が最も詰まりやすいのは「動くが遅い」という関門であり、#1014 は少なくともこの関門を一時的に通過したことを証明している。

しかしこのスタックが本当に手書きカーネルを代替可能か判断するには、まだ 2 つ足りない。1 つはカバレッジ：今回はデコードアテンションのみを移行し、A210 カーネルは依然として旧関数を使用、MoE、量子化、プリフィル経路はいずれも未着手である。2 つは可伸縮ベクトル：本期は明確に use-scalable をオフにしており、次にオンにするとベクトルサイズはコンパイル期に決定されなくなり、LMUL 4 のグループ化仮定が揺らぐ。その際に数値と命令数を守れるかは再照合が必要である。それまでは「VIR はすでに手書きカーネルに追いついた」を結論とするのは早すぎる。正確な表現は「K3 デコードアテンションのこの区間で、固定ベクトル長の下で追いついた」である。

6.2 基盤交換のコストはパッチドリフトからガバナンスへ：ワークフローがリベースを引き受け、ブランチ自体は依然として人手に依存

同じ日に、llvm の riscv ブランチはブランチ全体の再適用を停止し、244 行の自動リベースワークフローを追加する形に変更した。この転換は単独で記す価値がある。過去 5 日のリズムは「1 日 1 回のブランチ全体再適用、毎回 20 件のコミット列を書き換え」であり、作者時間は動かさず、committer 時間を統一し、パッチセット自体に新機能はなかった。この方式は上流に追随できるが、代償として外部コントリビューターの PR は常に一歩遅れ、提出したい者は自分で再適用する必要がある。

新しいワークフローはこの作業を「PR 番号を入力、デフォルトでドライラン、ワンクリックでプッシュ」というスケジューリングに仕立てた。コンフリクトは一律 riscv 側を採用し、重複パッチは自動的に破棄し、PR のコードとビルドは決して実行しない。これはブランチ自体の毎日の追従を解決するものではないが、「ベースラインへの追従コスト」の一部をメンテナーの手作業の判断から切り分けた。次の段階で観察すべきは、外部 PR が本当にこれによって増えるかどうかだ——もしワークフロー公開後 2 週間以内に、新しいベースラインに従って提出される外部 PR が依然として無ければ、ボトルネックはリベースツールではなく別のところにあるということになる。

6.3 配布層の議論に価格が付き始めた：2.81 倍のビルド時間は「好み」よりも説得力がある

#1350 は約 1 か月にわたって議論されており、核心的な相違点は buddy-mlir が内蔵する LLVM を外に出すかどうかだ。前号の見解はまだ「GCC を使ってもよいが、少なくとも 1.5 倍の時間がかかる」というものだったが、今号で作者は実測値を示した：riscv64 上で 8814 秒が 24798 秒になり、2.81 倍であり、しかも GCC を使った回はリンクに失敗して完走しなかった。これで議論の性質が変わった——技術的な好みから、ビルドファームのスケジューリング算術へと。

この指摘が RuyiAI スタックに示す示唆は結論ではなく方法にある：RISC-V ディストリビューションのパッケージングにおける多くの相違点（vendor するか、ツールチェーンを外に出すか、IR をパッケージに同梱して配布するか）は、最終的に「ビルド時間、イメージサイズ、再現性」という 3 つの測定可能な数字に落とし込まれる。前号で openRuyi は「LLVM IR をパッケージに同梱して配布する」路線を撤回し、今号の #1350 は 2.81 倍で「LLVM をパッケージ内に残す」を守った。二度の判断は方向が逆だが、根拠は同じ種類のコスト計算だ。今後の注目点は、この PR がこの数字を携えてマージできるかどうかだ——もしできないなら、ディストリビューションのビルド所要時間に対する許容度が作者の予想を下回っていることになり、そここそが本当に調整すべき点だ。
