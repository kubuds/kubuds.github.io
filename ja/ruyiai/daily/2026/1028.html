今日の重点：三点セットのディストリビューションパッケージング、triton-riscvのアンカー変更、VIRにPythonバインディングを追加（10-27）

日付：2026-10-27　出典：openRuyi PR #1350、triton-riscv PR #90、buddy-mlir PR #1009

本期の三本柱が同じ期間内にそれぞれ一歩を踏み出し、しかも初めて互いに接続した。

第一條は配布層である。openRuyi の PR #1350「Add Ruyiai packages」は buddy-mlir、python-triton-ruyiai、python-tilelang-ruyiai の 3 つの spec を一度にコミットし（3 コミット、9 ファイル、+666/−0）、9-21 にオープンされた後、メンテナ Z572 が 9-24 に修正要求を出し、議論は 9-28 で止まっていた。10-27 17:55 から 18:54（北京時間）にかけて、作者 nekorouter が三つのレビュー指摘に連続して返信し、git ビルド依存、buddy-mlir が内蔵する LLVM を外置きにするかどうか、そして GCC ビルドに切り替えるコストについて項目ごとに説明した。同日、別の PR #1352 は PyTorch の RISC-V 適配を単独のパッケージにした。二者はいずれもまだマージされていないが、「棚上げ」から「項目ごとの収束」へと戻っている。

第二條はツール層である。triton-riscv の依存アンカーは 19:43 に renovate ボットによってコミットされマージされた（#90、+2/−2）。buddy-mlir は nightly/v0.1.1.dev20261017 から直接 nightly/v0.1.3.dev20261027 へ跳び、0.1.2 正式版と 2 つのナイトリービルドを丸ごと飛び越えた。前回のデイリーレポートでは「アンカーが更新されるか」を観察項目として挙げたが、今回はその答えが出た。更新されたうえに、一度で二段階を跨いだのである。これは、10-26 の夜の 7 件の VIR 可変長ベクトル変更が、今回から下流のビルド経路に入ったことを意味する。

第三條は表現層である。buddy-mlir の #1009「[midend][VIR] Python bindings」が 22:42 にマージされた（12 ファイル、+614/−1）。VIR という、これまでは buddy-opt の中でしか動かせず、ir.Operation.create("vir....") で手作業でオペレータを組み、ir.Type.parse("!vir.vec<...>") で手作業で型を組む必要があった方言を、正式に buddy_mlir.dialects.vir モジュールとした。ODS と C API と nanobind 拡張という通常の経路をたどっている。

三つを並べて見ると、VIR は可変長ベクトルを表現でき（前回）、今回 Python から駆動でき、さらにその下にはディストリビューションパッケージングの経路がある（今回は審査中）。このスタックに欠けていたのは単点の能力ではなく、「表現—ツール—配布」の三段の接続であり、今回は珍しく同じ日にそれぞれ進展があった。

2.1 openRuyi PR #1350：RuyiAI 三種セットをディストリビューションへ、作者が当日レビュー意見に逐条回答（10-27）

日付：2026-10-27　情報源：PR #1350、PR #1350 レビューコメント、PR #1350 コミット

PR #1350 は今回の配布レイヤーで最も重要な一件である。一つの PR で同時に三つのパッケージを追加する——buddy-mlir（LLVM ベースの MLIR コンパイルフレームワーク）、python-triton-ruyiai（RISC-V 版 Triton）、python-tilelang-ruyiai（RISC-V 版 TileLang バックエンド）。3 件のコミットはすべて 9-21 の 09:46 から 09:48（2 分以内）に集中しており、合計 9 ファイル、+666/−0。

タイムラインは記録に値する：9-21 に PR を作成、9-24 にメンテナ Z572 が三つの修正要求を提示（なぜ git が必要か、buddy-mlir は Triton がその LLVM を特定するための macro ファイルを提供すべきではないか、buddy-mlir はまず GCC で固定バージョンの clang をビルドし、その新しい clang で自身をビルドすべきではないか）、9-28 に作者が返信し二点を修正；その後約一か月停滞し、10-27 17:55、17:57、18:54 に連続三件の返信で残りの議論を逐条的に説明した。

三件の返信の技術的内容は進捗そのものより情報量が多い。第一に、triton 上流の setup.py は git が実行可能かどうかを強制的にチェックするため、git をビルド依存として追加するか、setup.py を変更するか（新しいパッチファイルが必要で、triton 更新時に不整合が起きやすい）の二択となり——作者は前者を選択した。第二に、buddy-mlir が同梱する LLVM はそのパッケージ内部でのみ使用され、かつこれらのパッケージは常に特定の LLVM コミットに固定されるため、ビルドフロー内部に留め、独立した macro パッケージとして外置しない方針とした。第三に、GCC で固定版 LLVM/clang をビルドする方式は技術的には可能だが、ビルド時間が少なくとも 1.5 倍増加する。

これら三件は同じトレードオフを指し示している：RuyiAI のこれらのパッケージはビルドチェーンの結合度が高く（Triton は buddy-mlir の LLVM に依存し、TileLang は buddy-mlir ツールチェーンに依存）、ディストリビューションの「依存を外置し、システムパッケージを再利用する」慣例に従って分割すると、ビルドコストと不整合リスクがともに上昇する。作者は結合を維持し、サイズとビルド時間を引き受けることを選んだ——パッケージング路線における明確な意思表明である。

2.2 openRuyi PR #1352：PyTorch RISC-V 適配を単独パッケージ化、インストール後にスモークテストを同梱（10-27 状態）

日付：2026-10-27（状態）　情報源：PR #1352、python-torch-ruyiai spec ファイル

PR #1352 は RuyiAI-Stack/pytorch を単独で python-torch-ruyiai としてパッケージ化する（8 ファイル、+783/−0）。#1350 と同じ日に更新され、状態は依然オープンで、唯一のコミットは 9-21 11:22 で止まっている。

パッチセットは完全なディストリビューション適配リストとして読める：2001 は OpenBLAS を cblas 複素数ドット積に強制、2003 はシステム fmt に切り替え、2005 はシステム cmake 依存に切り替え、2006 は不要なサブモジュールのプリビルドチェックをスキップ、2011 は RVV カーネルをターゲットのベクトル能力に応じてゲート、2012 は scikit-build-core を内蔵。さらに pytorch-smoke-test.py があり、このパッケージはインストール後に一度スモークテストを実行してはじめて合格となる——ディストリビューションにとって、単に「インストールできる」より一歩進んでいる。

2011 の項目は特に注目に値する：RVV カーネルの有効化条件を「コンパイル時にサポートを仮定」から「ターゲットのベクトル能力に応じたゲート」に変更するのは、コミュニティで繰り返し現れる問題そのものである——RVA20 などベクトル拡張を含まないターゲットでは、パッケージング時にゲートしなければ実行不能なコードが生成される。この種の修正は通常、ユーザーが実機ボードで遭遇してから初めて補われるが、今回は事前にパッケージングパッチに入った。

#1350 と同様、このパッケージも AI 支援を明記し（Assisted-by: Deepseek V4.1 Flash）、openRuyi の AI 貢献ポリシーに従ってチェックと署名を行っている。

2.3 openRuyi：45 件のコミット、12 件の PR をマージ、Samba ファミリーを一括で 4.25.1 と Waf ビルドへ移行（10-27）

日付：2026-10-27　情報源：openRuyi コミット一覧、PR #1428 Samba とライブラリ、PR #1506 セキュリティ更新、PR #1508 ceph バックポート

4. Buddy Compiler 動態

4.1 VIR に Python バインディングを追加：buddy-opt 専用からプログラマブル方言へ（10-27）

日付：2026-10-27　情報源：PR #1009、buddy-mlir コミットリスト

22:42 にマージされた #1009 は、今期の Buddy Compiler 側における中核的な動きである：12 ファイル、+614/−1、新規モジュール buddy_mlir.dialects.vir を追加。コミット説明は課題を率直に記している——VIR はこれまで Python バインディングを一切持っていなかったため、VIR の decode attention は ir.Operation.create("vir....") でオペレータを組み立て、ir.Type.parse("!vir.vec<...>") で型を組み立てるしかなく、VIR 全体の降級も buddy-opt という単一の実行ファイル内でしか実行できなかった。

実装方式は「既存方言に追随する」ことを選んだ：ODS 定義オペレータ（VIRBinding.td）に C API と nanobind 拡張を加え、同リポジトリ内の quant など独自型を持つ上流方言と同構である；PR の記述によれば三つの部分——Ops、Types、および VIR 降級を Python に掛ける pass 登録に分かれる。

この一歩の意義はツール自体になく、組み合わせ可能性にある：ひとたび VIR が Python から直接構築・降級できるようになれば、オペレータ記述、形状推導、テストケースをすべて Python 側で書くことができ、フロントエンド（Triton、TileLang）と VIR の对接はもはや C++ 側でのフック追加に依存する必要がない。これまで単一の実行ファイル内でしか検証できなかった中間表現にとって、これは「コンパイラ内部部品」から「外部から呼び出し可能な方言」への転換である。

注意すべきは、#1009 のマージ直後に #1011「Cast the scalable VIR piece count to int64_t」（オープン）が現れたことであり、スケーラブルベクトル経路における整数幅の問題がここ二日でようやく触れられたことを示している。Python バインディングは入口を開いたにすぎず、安定性はなお調整中である。

6.1 表現層、ツール層、配布層が同じ日にそれぞれ一ブロックを補完

今号の三つの事象を一本の時間軸に置くと：10-26 夜に VIR がスケーラブルなベクトル表現を補完し、10-27 夜に Python バインディングを補い、10-27 全日にわたってディストリビューションパッケージングを推進した。この三段は本来順次進展するもの——まず表現でき、次に呼び出せ、最後に配布できる——であり、過去数号は「表現層が速く、ツール層と配布層が遅れる」状態が続いていたが、今号で初めて同日に三線が並進する形が現れた。

しかしこのスタックが本当に閉ループにあるかを判断するには、まだ二つの既知のギャップがある。第一に、triton-riscv のアンカー変更は自動化されており、適配検証が追いついていない。0.1.1 から 0.1.3 の間のインターフェース変更が下流で露見するかは次号でわかる。第二に、pytorch の riscv ブランチは連続六日間ゼロコミットであり、配布側はすでにそのパッケージングを行っている（#1352）——パッケージは動かないブランチに追随しており、パッケージのマージ時に上流ベースラインから遅れていないかは注視すべきリスクである。

6.2 リリース前清扫の外で、ディストリビューションが引き算を始める

今号の openRuyi の二組の動作は性質が異なる。一組は足し算（45 コミット、13 の新規パッケージ、12 のセキュリティ更新、Samba 全家連動アップグレード）であり、もう一組は引き算（三つの revert で LLVM IR の同梱配布を撤回）である。過去数号で見られたのはいずれも「リリース前清扫」——依存関係の補完、CVE の除去、バージョン切替——であり、今号で初めて明確な機能性回収が見られた。

これは openRuyi のメンテナンスの重心が「より多くのパッケージをカバーすること」から「既存パッケージの品質境界を保証すること」へ移りつつあることを示している。IR 配布のような実験はパッケージサイズ、ABI、インフラの連鎖的なコストをもたらし、リリースプレッシャーの下で優先的に削られる。RuyiAI スタックにとってこれは両面のシグナルだ——パッケージング経路はより規範化され（#1350、#1352 はいずれもディストリビューションの慣例に従って項目ごとに収束しつつある）、一方で「実験的性質を帯びたビルド方式」（例：LLVM の内蔵、独自 vendor の同梱）への許容度も同時に低下する。作者は #1350 で buddy-mlir の LLVM をパッケージ内に留めることにこだわっており、まさにこの方向に逆らう一度の交渉であり、結果は注目に値する。
