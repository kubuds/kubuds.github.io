今日の重点：DeepSeek-R1-Distill-Qwen-1.5B の K3 A100 における FP16 最適化がマージ、Prefill 43.42 token/s（11-23）

情報源：PR #997。コミット 3d5d674a。K3 設定 f16_k3.json。

#997 は 11-23 00:25 にマージされ、10-25 に作成、レビューに約1か月を要した。変更は 20 ファイルで、新規追加の A100 リーガライゼーションパス、IME 方言拡張、モデル設定を含む。

PR 説明で示された核心的な手段は4つある。第一に、4つの FP32 アキュムレータを K リダクション全体で常時レジスタに保持し、Prefill は 8×32 のタイル分割、Decode は各タイルで 32 個の出力チャネルを計算する。第二に、一部の Decode 投影重みを N32/K8 パネルにまとめ、残りの投影は元の RVV レイアウトを維持する。第三に、Prefill はネイティブ VLEN=1024 と BLIS 幅 64 を使用し、要素ごとのオペレータを融合し、SiLU をベクトル化する。第四に、以上の選択を models/deepseek_r1/specs/f16_k3.json に集約し、既存設定のデフォルトパイプラインは変更しない。

実測データは PR 説明の記録による。Prefill は 128 位置を評価し、Decode は 64 番目の位置から 32 ステップを測定、8スレッド、A100 コア 8 から 15、4回のサンプルを取得。表中の単位は token/s。

1.2 FlagGems サンプルがさらに 2 本追加：72 + 61 個のオペレータ、累積 279 個に（11-21、11-22）

情報源：PR #131。PR #132。

#131 は 11-21 18:53 に作成され、72 個のオペレータをカバーする。#132 は 11-22 18:48 に作成され、61 個のオペレータをカバーする。いずれも python/examples/flaggems/ のみを変更している。

#131 の 4 グループは座標コピー、内部コピーと割り当て、形状構築、型変換と充填である。PR 説明には上流との相違点が 3 箇所挙げられている：padding ラッパーは aten の (w, h, d) 順で受け取り、カーネルの (d, h, w) に並べ替える；replication の逆方向はスカラーソース位置で走査し、aten の累積順に合わせる；rank が 2 より大きい場合、rot90 は最終次元の項を欠落している。

#132 の 4 グループは BLAS ラッパーとスパース smm、gamma 特殊関数、量子化オペレータ、低精度とスパース行列積である。PR 説明には、fp64 ドット積は fp32 累積までしか対応できないため、この種の縮約はスカラー FMA ループに変更して精度を保つこと；e5m2 fp8 には降級パスがないためカーネル内でアップコンバートし、e4m3 と int8 はネイティブで処理することが明記されている。

テスト数は増え続けている。#131 は 7830 件通過、739 件新規を記録。#132 は 8617 件通過、787 件新規を記録。いずれも x86_64 上で実行され、既存の 3 つのクラッシュファイルを除外している。

5 本の PR が連なり 1 本のチェーンを形成している：#126 の 63 個、#127 の 43 個、#130 の 40 個、#131 の 72 個、#132 の 61 個、合計 279 個のオペレータサンプル。PR 説明によれば、前序が未マージの場合 diff は前序のコミットを算入するため、#131 は main に対して 34 コミット・548 ファイル、#132 は 38 コミット・670 ファイルとなる。

2.3 サイトリポジトリの 30 件がデバイス書き込みに集中、xz/lz4 解凍とダウンロード進捗を追加（11-21）

情報源：ruyisdk-website コミット一覧。コミット 6d3a4a75。コミット 867358f6。

サイトリポジトリは調査期間内に 30 件、その大半がデバイス書き込み（provisioning）フローに関するもの。時刻は 11-20 19:43 から 11-21 11:28 にわたる。

イメージ処理側では 2 つの領域を補完した。1 つは解凍で、xz と lz4 形式のディスクイメージのサポートを追加した。もう 1 つはダウンロードで、デスクトップミラーソースを優先し、ダウンロード失敗とローカルエラーを分けて報告し、イメージ解凍の進捗を表示するようにした。

ターゲットディスク選択の変更が最も多い。dd 書き込みのターゲットディスクをサイドバー内で選択するよう変更し、余分なキャンセル動作を削除し、ディレクトリ選択ダイアログの重複オープンを防止し、すべてのイメージ準備をディスク選択より前に前倒しした。

安定性側には3件ある。フラッシュ書き込みロックは全ホストコマンドが収束してから解放するよう変更し、Go bootstrap を provisioning worker に組み込み、ランタイムをプリロードする。

これらの変更はリリースノートには記載されていない。サイトリポジトリのコミットは fix(device) と feat(device) のプレフィックスが主体で、機能の仕上げに属する。

これはベクトル方向が停止したことを意味しない。調査期間内のベクトル作業はモデルカーネル内に書かれており、次の項目を参照されたい。

3.2 ベクトル作業はモデルカーネルへ移行：VLEN 1024、SiLU、exp 近似（11-22）

情報源：PR #997。PR #1076。PR #1075。

#997 は Prefill の BLIS 列幅を設定可能にし、関数入口でハードウェア VLEN を検証できるようにする。A100 構成では VLEN=1024 を取り、幅 64 と組み合わせる。

同じコミットで SiLU は融合・ベクトル化され、exp は上流 MLIR の多項式近似に乗る。PR の説明には、多項式が丸めを変えるためデフォルト経路とは分けて検証すると明記されている。

#1076 は attention の bmm1、scale、softmax、bmm2 を単一のタイルカーネルに統合し、softmax は L1 に残し、ベクトル exp を用いる。同じコミットで -approximate-vector-exp にベクトル化 erf を加え、GELU がレーンごとにスカラー関数を呼ばないようにする。

#1075 は別の道を取る。エンコーダの P @ V を 4 行 M 展開の FP32 累積 RVV カーネルに落とし、matmul_transpose_b と conv_1d_ncw_fcw を IME に落とす。

3件の共通点は、ベクトル幅をハードウェア VLEN に結び付けることである。前号の triton 側 #129 のチューニングも同じ考え方で、両側のパラメータの基準は照合できる。

3.3 FlagGems のサンプルが特殊関数と量子化オペレータまで拡大（11-22）

情報源：PR #127。PR #132。

特殊関数の一支はベッセル関数ファミリー、4種の Chebyshev とシフト版、2種の Hermite、Laguerre、Legendre をカバーし、ほかに log_softmax と logsumexp がある。

ツールチェーンが降格できない intrinsic は閉形式に切り替える。erfcx は3段の混合を用い、log_ndtr の裾は −t² + log(erfcx(t)/2) を計算するよう変更する。

量子化と低精度の一支は、疑似量子化ファミリーとその学習可能変体、4ビット動的量子化線形、scaled mm、int8/int4 重みパッキング、混合精度線形、CSR と半構造化積をカバーする。

精度処理は PR 説明に書き込まれた。fp64 ドット積は Triton 側では fp32 累積までしか到達できず、この種の縮約はスカラー FMA ループに変更する。e5m2 fp8 には降級パスがなく、カーネル内でアップキャストする。e4m3 と int8 はネイティブで処理する。

4. Buddy Compiler の動向

4.1 0.1.5 から 0.1.7 へのタグとコミットの対応関係（11-22）

ソース：タグ一覧。compare 0.1.6…0.1.7。

3 つのタグはそれぞれ 1 コミットに対応する。0.1.5 は 20d3a102、0.1.6 は 8cbc1a9b、0.1.7 は a848378f。

compare によると、0.1.6 は 0.1.5 に対して 1 コミット先行しており、それは #1074 の dump() 修正である。0.1.7 は 0.1.6 に対して分岐状態にあり、1 先行・1 遅行となっている。

0.1.7 の親コミットは 20d3a102、すなわち 0.1.5 のベースラインである。これは 0.1.7 に dump() 修正が含まれていないことを意味する。

下流に直接影響する。triton は mlir::Operation::dump() がないとリンクできないが、0.1.5 と 0.1.7 はいずれもこのシンボルを欠いており、0.1.6 のみが持っている。

現在 triton 側で固定されているのは依然として nightly/v0.1.4.dev20261103（#115 未マージ）。#115 に従って release/v0.1.7 に上げると、リンク問題が再発する。

4.2 0.1.6 で dump() サポートを追加、0.1.7 で LLVM アセットを圧縮（11-21）

ソース：PR #1074。コミット a848378f。

#1074 の原因は具体的に書かれている。ナイトリー版は main からビルドされるが、#1062 は llvm-multitarget ブランチに入ったため、0.1.5 の LLVM パッケージには dumpPretty() しかなく、dump() がなかった。

下流の現象はリンク失敗で、undefined reference to mlir::Operation::dump() と mlir::Value::dump() const が報告された。修正方法は LLVM_ENABLE_DUMP を有効にし、この 2 つのヘルパーのみを復活させ、アサーションは有効にしない。

PR 説明ではさらに、LLVM のインストールはハッシュでキャッシュされるため、以降のバージョンでは llvm_cache_mode=clean を一度実行しないとこのスイッチが反映されないと注意している。

0.1.7 が扱うのはアセットの上限である。コミット説明には、riscv64 の LLVM インストールパッケージが gzip 後に単一アセットの 2 GiB 上限をわずかに超え、v0.1.6 で「size must be less than 2147483648」が報告されたと明記されている。

修正方法は、下流で使われない開発者ツールを切り詰め、src、share、libexec を削除し、残りを strip することである。x86_64 の実測では 1617 MB から 817 MB に減少した。

説明には失敗した試みも記録されている。当初はファイルを直接削除したが、LLVMExports.cmake が configure 段階でインポートターゲットが欠落ファイルを指すため中止したので、切り詰めに変更した。

両バージョンは現在それぞれ 8 つのアセットを持つ。riscv64 の LLVM パッケージは 0.1.7 では 1,138,715,828 バイトで、上限を下回っている。

4.3 DeepSeek 最適化がマージ、4 つのモデル PR が待機中（11-23）

ソース：PR #997。PR #1075。PR #1076。PR #1001。

#997 は本日の重点で詳述済み。ここでは PR キューにおける位置のみ補足する。これは今回のモデル最適化の母体である。

#1075 は Whisper Base を扱い、11-22 17:10 に作成された。PR 説明によるとエンドツーエンドで 2.031 秒、主干は 1663.03 秒で、818.8 倍の高速化、RTF は 345.39 から 0.42 に低下した。前処理 0.101 秒、エンコーダ 1.622 秒、デコード 0.272 秒。

#1075 はさらにメモリ問題を修正した。STFT ループ内の make_rfftp_plan(400) は呼び出しごとにプランを生成し、約 1 GB がリークしていたため、3001 フレームのループの外に移動し、バッファを解放するようにした。

#1076 PaddleOCR-VL-0.9B を作成、11-22 22:08 に起票。エンドツーエンド 30.82 秒、FP16 RVV ベースラインの 525.71 秒に対して 21 倍の高速化。Prefill 25.04 秒、Decode 5.78 秒（18 トークン、3.11 トークン/s）。生成された 19 トークンは PyTorch FP16 と完全に一致。

#1001 Qwen3-0.6B を作成、10-26 に起票されて現在審査中。これは #997 の IME FP16 GEMM/GEMV カーネルと Decode 重みパッキングを直接再利用している。

4 件を合わせたシグナルは、A100 カーネル一式が LLM、音声、OCR の 3 種類のワークロードをカバーしつつあるということだ。

4.4 方言とエクスポート側に別途 5 件が審査中（11-23 時点）

情報源：PR #1071。PR #1072。PR #1073。PR #1035。PR #934。

6.2 K3 A100 上でモデル最適化パイプラインが形成

#997 のマージ後、同じ IME カーネル群がすでに Whisper、PaddleOCR-VL、Qwen3 の 3 モデルの PR に現れている。

3 件の性能数値はいずれも同一マシン K3-002、同一コア群 8 から 15、8 スレッド、VLEN=1024 で記録されている。水平比較が可能である。

収益の規模の差は非常に大きい。DeepSeek の Prefill は主干で 8.6 倍、Whisper のエンドツーエンドは 818.8 倍。後者の基数はエンコーダ再利用を行わない F32 単回フォワードに由来し、倍率はベースラインによって増幅されている。

検証可能な口径はトークン列が参照実装と一致することである。#1076 は 19 トークンの完全一致を記録し、OCR テキストを貼り付けている。

6.3 ツールチェーン側はマージ待ちキュー滞留期に

triton-riscv の 5 本の FlagGems PR は一つのチェーンをなし、合計 279 のオペレータ示例になる。各本は前の 1 本がマージされて初めて diff を再計算できる。

pytorch の riscv ブランチは 11-15 で止まり、tilelang-riscv は 11-16 で止まっている。いずれも新規コミットはない。

ruyi 側は逆で、6 件の PR が 1 日でマージ完了し beta を出した。差異は ruyi の変更が CLI と設定に集中しており、レビュー面が狭いことにある。
