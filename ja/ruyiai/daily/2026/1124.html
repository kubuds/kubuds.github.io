今日の重点：buddy-mlirがQwen3-0.6B FP16最適化をマージ、Prefill 86.01 token/s（11-23）

出典：PR #1001。

#1001は11-23 14:51にマージ、タイトルは「Optimize Qwen3-0.6B FP16 Prefill and Decode on K3 A100」。23ファイル変更、560行追加、50行削除。

実測は同一K3のA100コア8から15上で完了、8物理コア、入力端は同一。Prefillは128位置を評価、Decodeは96番目の位置から32ステップ測定、ロード時間は含まず。

実装 Prefill（token/s） Decode（token/s）
Buddyメイン、未最適化FP16 4.24 0.84
llama.cpp 71.64 14.38
Buddy、本PR 86.01 13.45

Prefillはllama.cppより20.1%高く、メイン基線の20.3倍。Decodeは13.45 token/sで、llama.cppより6.5%低いが、メインの16.0倍。

二つの指標は逆方向に動く。Prefill はブロック分割 GEMM とネイティブ VLEN=1024 で進み、Decode は単一トークンの GEMV 帯域に制限される。PR 説明には比較が all-position logits を使用すると明記され、双方の口径はこの点で一致している。

カーネル側は #997 の成果を再利用しており、IME FP16 GEMM と GEMV、Decode 重みパッキング、RVV と SiLU の最適化を含む。Attention はベクトル幅 64 を使用し、Decode は KV を 1 路のみ分割する。

設定は次に集約される
models/qwen3/specs/f16_k3_a100.json、デフォルトパイプラインには影響しない。ファイル内で VLEN は 1024、Prefill のベクトル幅は 64、Decode のパッキング幅は 32、スレッド数は 8。出力語彙重みは別途保存され、投影に応じてレイアウトを選択できる。

正確性側では、96 個の Decode トークンと 3 組の重複貪欲生成テストケースがいずれも PyTorch リファレンスと一致した。PR 説明はまた、完全な check-buddy が無効化された Python パッケージターゲットに阻まれ、全量実行できなかったことも指摘している。

4.2 #1077 がstripとzstdの統一を提起、目標は単一資産上限（11-23）

情報源：PR #1077。

#1077 は 11-23 11:05 に作成され、1ファイルのみ変更、まだマージされていない。タイトルは「Pack the LLVM and buddy tarballs with zstd」。

PR 説明に経緯が示されている。riscv64 の LLVM インストールパッケージは gzip 後に GitHub の単一アセット上限 2 GiB をわずかに超える。nightly/v0.1.5.dev20261120 はこれによりリリースに失敗し、API は 422 と「size must be less than 2147483648」を返した。

方針は3点。バイナリと共有ライブラリの strip、MLIR Python バインディングの削除、zstd -19 –long=27 でのパッケージングへの変更。作者の試算では LLVM は 2047 MB から約 840 MB に、buddy は 264 MB から約 180 MB に削減される。

説明には関連する2点も記されている。triton-riscv の setup.sh は既に .tar.zst を読める。この変更の反映後、最初のリリースでは llvm_cache_mode=clean を一度実行する必要がある。キャッシュキーに今回のフィルタが含まれていないためである。

この6件はマージ済みの #997、#1001 と同じ pass と重みパッケージングの経路を共有している。キュー内のモデルのカバー範囲は既に OCR と音声にまで及んでいる。

6. トレンド観察

6.1 モデル最適化はバッチ再利用へ移行

#1001 には #997 のカーネル、重みパッケージング、RVV/SiLU 最適化を再利用することが明記されている。キュー内の Whisper Base、PaddleOCR-VL-0.9B、EmbeddingGemma も同じ経路を参照している。

これは K3 A100 上のモデル高速化が単点攻関からテンプレート化へ移行したことを示す。新規モデルの追加での主な作業は設定の記述と正確性の実行であり、カーネルの書き直しではない。

判断根拠は2点。1つは設定が各モデルの specs ディレクトリに集約されていること、もう1つは PR 説明に「shared kernels」と「reuse」の表現が繰り返し現れることである。

6.2 リリース番号の進行が内容より速い

ruyi は 0.55.0-beta から 0.56.0-alpha へ進んだが、コード差分はバージョン番号の3行のみ。triton-riscv が追加発行した正式タグも 11-18 の旧コミットを指している。

2つのリポジトリで同日に「新バージョンあり、新コードなし」の状況が生じた。これはリリースのペースが変更量ではなくバージョン計画に駆動されていることを示す。

下流への影響は、バージョン番号が内容の多寡を指示しなくなることである。アップグレードに値するかどうかは、番号の大小ではなくリリースノートの項目集合を見る必要がある。

6.3 デバイス側コードがメイン倉から離れ始める

ウェブサイトリポジトリは今回のラウンドで775行を削除し、デバイスランタイムを独立リポジトリとサブモジュールに委ねた。同時期にruyisdk-test組織下にruyi-imager-webviewとruyi-imager-electronが出現した。

方向性は、書き込みツールを独立してリリース可能、独立してテスト可能なコンポーネントに分割することである。メインリポジトリはその分小さくなり、ビルド権限も個別に分離できる。

留意すべきは、新リポジトリがテスト組織の下に置かれ、まだruyisdkメイン組織に移行されていない点である。この移行が行われるかどうかは、今後の観察ポイントとなり得る。
