今日の重点：RuyiTuner v1.8 リリース、週末に実コンパイル比較段階を完了、三段的パイプラインが成形

日付：2026-09-25 ~ 2026-09-27　出典：v1.8 Release、CHANGELOG、real_compile 拆分提交

RuyiTuner は如意コミュニティが LLVM 向けに提供するコンパイラ調優ツールであり、「最適化相乗効果分析」に基づいてコードサイズを最大化して削減できるパス列を自動探索する。北京時間 09-25 午前（09:06）、本ツールは v1.8 をリリースした（tag はコミット a032c28c「Add ruyi-cc to use pass seq into project」を指す）。v1.8 が v1.7（09-17）に対して取り込んだ更新には、プロジェクト全体で共通パス列を探索する --search_scope project モード（適応度を集約する GA）、--max-path-length パラメータ、および scripts/ruyi-cc.sh コンパイララッパースクリプトが含まれる——最適列をプロジェクトの通常のコンパイルフローに接続し（make CC=scripts/ruyi-cc.sh）、列は評分基準に従ってネスト処理を行い、-fPIC / -mcmodel などのコード生成オプションを llc に転送し、すでに bzip2-1.0.2 上で全量コンパイル、リンク、圧縮解凍の機能検証を完了している。このうちプロジェクト級探索と --max-path-length の 2 部分は、以前の調査期間でそれぞれ個別に追跡済みである（09-22 / 09-24）。

リリース後も開発は止まっていない：09-25（7 コミット、09:06 ~ 19:31）と 09-27（6 コミット、16:11 ~ 18:22）の 2 日間で、v1.x ブランチは連続 13 コミット（うち 2 回 main にマージ）を行い、1.9 バージョンラインを「実際のコンパイル対比」の成型へと押し進めた——まずプロジェクト級探索の列をディスクに書き出し（09-25 17:04）、次に「最適列でソースを実コンパイルし体積削減率を報告する」段階をメインエントリに追加し（18:27）、続いてその能力を一時的なラッパースクリプトから取り込み、scripts/ruyi-cc.sh を削除した（19:31）；09-27 にこの段階を独立スクリプト real_compile.py（18:10）に分割し、train.py、run.py とともに三階段パイプラインを構成した（段階タイトル 1/3 から 3/3）。そして以下を完了した：出力を段階ごとに再番号付け（列挙ファイルを Step1 プレフィックスに、列と結果を Step2 プレフィックスに変更）、協同ペア探索の中間ファイルをディスクに書き出さない（メモリ受け渡しに変更）、--dataset が単一の .c / .i ソースファイルをサポート、GA の obj-size 評分が pic 再配置モデルに切り替え（x86_64 上の clang のデフォルト口径に整合）、実コンパイル段階が C→IR キャッシュの .ll ファイルを再利用、プロジェクト別に x86 / RISC-V コード体積データを抽出、原理模式図を V2.0 に更新。

調査期間末時点で、1.9 はまだリリースされていない（最新 Release は依然 v1.8）。その変更は CHANGELOG の「1.9 版本変更」段に完全に記載されている；ツールのバージョンとアーキテクチャの汎用性は不変である（LLVM バージョンとターゲットアーキテクチャに束縛されず、ターゲットは入力 IR のターゲット三元組で決定される）。このたびのリファクタリングにより、以前の「二階段探索 + 外部コンパイルラッパースクリプト」の形態が、内蔵の三階段パイプラインへと収束した。

RuyiTuner は本調査期間で唯一の高頻度開発面である——09-25 と 09-27 の2日間に同一メンテナが連続して13件のコミットをプッシュし、2回 main にマージし、調査期間をまたいで進行中だったリファクタリング（一時コンパイルラッパースクリプトから組み込み実コンパイル段階へ）を3段階パイプラインとして収束させた。バージョンリズムを振り返ると：v1.6（08-31）から v1.7（09-17）までは約2週間半、v1.7 から v1.8（09-25）は8日、1.9 の変更はすでに進行中——ツールラインは「毎週利用可能な增量」の速度でイテレーションしており、新調査期間におけるメインスタックの静けさと対照をなしている。

5.2 「リリース-メンテナンス」リズム：0.53.0 以降メインリポジトリは静か

ruyi 0.53.0 リリース（09-24）後の最初の完全な調査期間内に、メインリポジトリはテストサブモジュールのフォローアップ1件のみ（#503）；0.53 バージョンサイクルに関連する3件の問題（#495、#498、#501）は現在すべてクローズ済みで、長期トラッキング項目 #401（RISC-V 上での PyPI インストール準備状況トラッキング）のみがオープンリストに残っている。第077期の「次バージョンは10月末」の予告と合わせると、現在はバージョン間のメンテナンス安静段階にある——リリース品質の関心はコミュニティのインストールフィードバックへと移っている。

5.3 サポートマトリックスの RT-Thread ラインは拡張を継続

調査期間内のサポートマトリックスで唯一マージされたのは ESP32-C3 の RT-Thread 5.3.1 レポート；直近2週間、このマトリックスの RISC-V ボードカバレッジはほとんどが RT-Thread と Zephyr の2つのリアルタイムオペレーティングシステムによるもの（CH32V307、ESP32-C3 が連続更新）、同時に Milk-V Duo S プラットフォームの3件（RT-Thread / RT-Thread Smart / Zephyr）が依然キューにある。RISC-V 開発ボードのオペレーティングシステムレベルテストディレクトリは継続的に稠密化している。

5.4 本調査期間の空白と注目点

空白項目：RuyiAI-Stack メインスタック（pytorch / triton-riscv / llvm-project などの機能ライン）は連続して静かで、フレームワーク側の待機とツール側の独走の分化はすでに2週目に入っている；技術情報リポジトリの中断は2週目に入った（09-24 期から4期欠席）；フォーラムと外部ニュース側は完全に静か。注目点：1つは openRuyi 2026.09 月版公告（月末の調査期間）；2つはサポートマトリックスの審査中3件のマージリズム；3つは llvm-project PR #168 と2本の予備研究ブランチの今後の内容；4つは ruyiai-daily がプッシュを再開するか；5つは ruyi 0.53.0 のコミュニティフィードバックと新しい issue の動向。
