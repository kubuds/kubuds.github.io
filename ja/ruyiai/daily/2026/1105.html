今日の注目：AME バックエンドが i32 行列アキュムレータを AccReg に固定し、設定化された tile 操作を展開前に延期（11-04）

日期：2026-11-04　来源：コミット f346011、PR #35

11-04 15:40（北京時間）、RuyiAI-Stack/llvm-project の riscv ブランチに新規コミット f346011 が追加され、8 ファイル変更、+412/−1、作者 caihanyi111、協力者 caohanghang。変更対象は RISC-V AME 行列拡張の LLVM バックエンド実装（コード内では BOSCAME と記録）で、二つの部分に分かれる。

最初のブロックはレジスタの分類である。ループ的に持ち越されるアキュムレータ PHI は型テーブルから既定のレジスタクラスを取得するが、nxv32i32 は元々 TileReg としてのみ登録されていた。アキュムレータ命令 mlce32.m、mqma.*、msce32.m のアキュムレータオペランドと結果はいずれも AccReg に限定されているため、各ループエッジで tile と accumulator という2つのレジスタファイル間のコピーを1回生成する必要があり、copyPhysReg はこのクロスファイルコピーを単一の AME 命令に展開できない。修正方法は、nxv32i32 を AccReg にも同時に登録することである。V 拡張を同時に有効にするターゲットでは、RVV がこの型を再登録するため、既定の動作は変わらない。同一ファイル内のレジスタ全体コピーは mmve64.t.t と mmve64.a.a で展開するように変更し、クロスファイルコピーはハードエラーとして保持し、レーン単位のインデックス移動への降格は行わない。

第2のブロックはスケジューリングである。各 tile 設定とそのコンシューマは、順序付きで副作用を持つ擬似命令の中に保持され、emit 直前に展開される。行列レジスタは割り当て可能に変更され、MMA のアキュムレータは tie され、ゼロアキュムレータの定義は旧値を読まず、分岐緩和は完全展開後のサイズを計上する。コミットでは同時に3つのテストを新規追加している。設定化された load/MMA/store の順序、独立アキュムレータとゼロ値定義、RVV と非 RVV の2つの選択、および緩和後の分岐である。

コミットメッセージには動機が明記されている。上位の TTIR から BOSCAME への降格では、リダクションループが i32 アキュムレータを AccReg に留め続けることが要求される。この経路こそが tilelang-riscv からの行列オペレータ経路であり、LLVM 側で補っているのはレジスタ割り当てとスケジューリングの層であり、新規命令ではない。

3.2 隔週進捗 080 ドラフト：glibc libmvec と newlib のベクトル数学補関数（11-04）

日付：2026-11-04　情報源：080 号ドラフト、記事リポジトリのコミットリスト

RuyiSDK 微信記事リポジトリの 11-04 更新で、080 号ドラフトの「基礎コンポーネント」2 節が書き上がった。基礎 C ライブラリ部分：glibc は sinpif、sqrt、sqrtf、tanf を既存の libmvec フレームワークに移植した。newlib は atanhf、atan2f、atanpif、atan2pif、exp2f、cosf、coshf、cospif、exp10f、expf、log2f、log2p1f、rsqrtf、expm1f の計 14 関数を既存のベクトル数学フレームワークに移植した。

これらの関数は RVV 上で低精度推論と活性化計算を行うための土台である：ベクトル数学ライブラリに関数が欠けていると、オペレータはスカラーパスに retreat するしかなく、コンパイラ側の RVV 降級がどんなに優れていても活かせない。ドラフトの残りの章節（パッケージマネージャ、IDE、GCC、LLVM、OpenJDK、Go、QEMU など）はまだ空である。

3.3 arXiv：bf16/fp16 が RVV 上で自動ベクトル化によりサイレント降級（11-02、調査期間外）

日付：2026-11-02（調査期間外、直近三日）　情報源：arXiv 2611.03917

調査期間内に arXiv で RISC-V 関連の新規論文はなかった。直近3日間に RVV ベクトル化と直接関連する研究が1件あり、記録に値する。著者の Vaishnavi Kouru と Robert Chun は、fp32、int8、bf16、fp16 の4精度の積和ループを用いて LLVM の RISC-V 自動ベクトル化を比較した。-march=rv64gcv という共通ベースラインでは、int8 と fp32 はクリーンにベクトル化できるが、bf16 と fp16 は多数のスカラーへのフォールバックに退化し、fp16 はさらに要素ごとのソフトウェア変換呼び出しに退化する。ただし zvfbfmin/zvfbfwma と zvfhmin を追加で有効化した場合は除く。

QEMU ユーザーモードでの動的命令数はその規模を示している。ベースラインの bf16 と fp16 カーネルが実行する命令数は、拡張を有効化したバージョンのそれぞれ 17.0 倍と 75.9 倍である。論文は同時に、コンパイラの診断は確かにこの退化を報告するものの、その文言では「コンパイルオプションを1つ追加すれば解決する」場合と「固有の変換コスト」を区別しておらず、ユーザーは修正方法を指し示す直接的なシグナルを得られないと指摘している。RuyiAI スタックにとって、これは 080 号でベクトル数学関数を補ったのと同じ問題の両端である。一端はライブラリ関数の欠如、もう一端は機能スイッチの可視性の欠如である。

4. Buddy Compiler ダイナミクス

4.1 VIR の set_vl セマンティクスの厳格化：精确 VLEN と任意 VLEN が2つのパスに分離（11-04 から 11-05）

日付：2026-11-04 から 11-05　情報源：PR #1028、マージコミット dd57775、PR #1029、マージコミット 61ba191

zhanghb97 による2件の PR が調査期間内に相次いでマージされ、VIR 方言における set_vl のセマンティクスが明確になった。

#1028（11-04 23:54 マージ）は rvv-vlen をターゲットの精确 VLEN として扱う。vscale = rvv-vlen / 64 となり、1つの vector<[N]xT> は N 掛ける vscale 本のレーンを保持し、分割は完全なベクトル単位で行われる。これ以前は rvv-vlen は最小 VLEN として扱われ、マスクはすべて真であるにもかかわらずコード内に残っていた。llc は vid と vmslt を保持し、メモリアクセスはマスクを伴い、RoPE の rotate_half は slides とマスク選択になり、デコードアテンションではマスクがオーバーフローさえ起こしていた。K3 上のカーネルは 1024 ビットのベクトル幅で構築されており、まさにこのパスの典型シナリオである。

#1029（11-05 01:32 マージ）は rvv-vlen を指定しない汎用ビルドを扱う。この場合、コードは任意の VLEN に対して成立する必要があり、strip-mined 領域は N 掛ける vscale で実行時にステップし、ベクトルは最小の 128 ビットでサイズ決定される。結果を伴う set_vl は直接拒否され、「rvv-vlen、すなわち精确 VLEN が必要」と報告される。このパスは以前は単にエラーを報告するだけだった。固定ベクトルは rvv-vlen がない場合にそのまま維持され、ホストに応じてサイズ決定される。128 を超える最小 VLEN の宣言は許可されない。

2件を合わせた意味は、セマンティクスがもはや「マスクがたまたますべて真」に依存して担保されるのではなく、コンパイル時にこのコードが特定の VLEN 向けにコンパイルされたのか、任意の VLEN 向けにコンパイルされたのかを明示する必要があるということである。

4.2 CI：pytorch 2.15 がテストマトリクスに参入、LLVM リリースで NVPTX/AMDGPU と lld を有効化（11-04）

日付：2026-11-04　情報源：PR #1026、PR #1027、PR #1025

#1026 pytorch 2.15 をテストマトリックスに追加し、2.11 から 2.15 をカバーする。変更のきっかけは実際のリグレッションである。2.15 では最新の full check が tests/Python/AtenOps/test_resize_enlarge.py で失敗し、しかも失敗は importer より前で発生している。AOT autograd の functionalization が、関数化済みのテンソルに対する resize_ の拡大を現在拒否しており、torch.compile も同じ関数で失敗し、グラフはそもそも ResizeOp に到達しない。修正方法は、テストを out-of-place の aten.resize に置き換え、同じ ResizeOp handler を通し、同じ MLIR を生成することであり、2.11 から 2.15 の全マトリックスで通過する。

#1027 は CI が公開する LLVM に NVPTX/AMDGPU ターゲットを含め、lld を有効化する。#1025 は LLVM を bef335e2143c に引き上げる。三件はいずれもインフラストラクチャだが、#1026 が記録したこのリグレッションは留意に値する。上流の functionalization の厳格化は「バックエンドにグラフが到達しない」形で現れ、バックエンドのエラーにはならない。
