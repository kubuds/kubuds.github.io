今日の重点：BUDDY MLIR 0.1.4 正式リリース、30件のコミットのうち19件が VIR 中間端に集中（11-15）

日付：2026-11-15　情報源：BUDDY MLIR 0.1.4、0.1.3 から 0.1.4 への差分、PR #1059

2026-11-15 08:01（北京時間）、buddy-mlir は正式版 0.1.4 をリリースした。0.1.3（10-31）から2週間ぶりとなる。0.1.3 から 0.1.4 までのコミットは計30件で、そのうち19件に中間端プレフィックスが付いており、テーマはただ一つ。「スケーラブルベクトル（VIR）のこの下降パスを『いくつかのオペレータが動く』段階から『ある種の形状をカバーする』段階へ引き上げる」ことである。

この19件は4つのグループに分けられる。第1グループは形状カバレッジ：#1017 はスケーラブルベクトルのフラグメントカウント時のナローイングを修正し、#1056 は整数と浮動小数点のすべてのリダクション種別を網羅し、#1057 は rank-0 memref の linalg.fill を1回の store に下降し、#1058 は整数行列乗算をサポートして動的次元を修正し、#1041 は畳み込みも VIR を通すようにした。第2グループは VLEN の扱い：#1028 は正確な rvv-vlen に対して set_vl を下降し、#1029 は rvv-vlen がなくても任意の VLEN 向けのコードを生成でき、#1032 と #1037 はそれぞれ「ある正確な VLEN 向けにコンパイルされたモデル」が別の VLEN に持ち込まれるのを防ぐこと、およびホストの V 拡張幅に応じて下降することを担い、#1046 は動的ベクトル型の検証を行いスケーリングファクタを m2 として出力し、#1048 は動的ベクトル型のクローン時にスケーリングファクタを保持する。第3グループはフラグメントと合成：#1031 はスケーラブルベクトルの shuffle をいくつかのフラグメントに分けて下降し、#1047 は結合可能なリダクションのためにベクトルフラグメントをマージし、#1045 は vir.set_vl に単一ブロック領域を与え、#1050 は strip-mined set_vl がどのオペレータをサポートするかを明記し、#1051 は vector<[1]xT> の全レーンリダクションを処理する。第4グループは前回のレポートですでに書いた 11-12 の7件（#1052 から #1058 のうちマスク、libm、bf16、fast-math、リダクション、rank-0、整数行列乗算）で、これらは今回まとめて正式版に入った。

VIR 以外にも11本の支線がある：モデル側では #1042 が SpacemiT K3 上に YOLOv8 の検出と姿勢推定を追加し、#1044 は A100 の llc パラメータを a100_llc_args から取るように変更した。ランタイム側では #1018 が共有 serving 生成コントローラを追加した。コンパイラ側では #1025 が LLVM を bef335e2143c に上げ、#1027 はリリースする LLVM に NVPTX、AMDGPU、lld を含めるようにした。テスト側では #1026 が PyTorch 2.15 をマトリクスに追加した。バックエンド側では #1033 が BOSCAME に SPM 最適化を追加した。ツール側では #1030 がカーネルを llc オプションに対応するターゲットに応じて VIR へ下降させる。

特筆すべきはリリースのタイミングである：主干の最後のコミットは依然として 11-12 14:44 の #1058 であり、その後 11-15 のリリースまでに新しいコミットは一切ない。つまり 0.1.4 と 11-13 のナイトリー版は同一のツリーであり、正式版はこのツリーに2日間の観察期間を加えたものに相当し、さらなる変更を重ねたわけではない。

今日の重点：openRuyi が python-torch-ruyiai を取り込み、RuyiAI の PyTorch スナップショットがディストリビューションに入る（11-13）

日付：2026-11-13　情報源：openRuyi コミット add python-torch-ruyiai、python-torch-ruyiai.spec、PyTorch riscv ブランチ

11-13 22:58（北京時間）、openRuyi のパッケージリポジトリに新しいパッケージ python-torch-ruyiai のコミットが入った。これは RuyiAI が初めてディストリビューションのソフトウェアパッケージとして openRuyi に登場したものである：バージョン番号は 2.15.0~a0+git20260921、ソースは RuyiAI-Stack の riscv ブランチ（コミット 6d667e1e）に追随し、CPU-only、ツールチェーンは clang を使用し、ディストリビューション既存の python-torch とは共存できない。

仕様ファイルから、今回のパッケージングにおける三つの難点が読み取れる。第一は BLAS：OpenBLAS の Fortran cdotu_／cdotc_ は複素数をレジスタで返すが、PyTorch の非 CBLAS 分岐は f2c の慣例に従って最初の引数から結果を取るため、complex テンソル上の dot と vdot が無言で 0 になる。パッチ 2001 は CBLAS パスを開き、spec 内の PYTORCH_BLAS_USE_CBLAS_DOT=ON をネイティブビルドでも有効にする（上流はクロスコンパイル時にのみこの変数を読む）。第二は RVV ゲーティング：__riscv_v_intrinsic マクロは rva20 ベースラインでも定義されるため、旧条件では使うべきでない深層畳み込みベクトルカーネルが選択されてしまう。パッチ 2011 は __riscv_vector で判断するよう変更する。第三はビルドバックエンド：RuyiAI スナップショットは scikit-build-core 1.0 以上を要求するが、openRuyi は依然として 0.12.x を配布し、python-pyvex がさらに上限を塞いでいる。パッチ 2012 はこのバックエンドをソースに同梱し、同時にサードパーティツリーの裁剪後に満たせなくなる license ファイルのワイルドカードを削除する。

依存関係の処理は「できるだけシステムライブラリを使う」方針を取る：USE_SYSTEM_CPUINFO、USE_SYSTEM_ONNX、USE_SYSTEM_SLEEF、USE_SYSTEM_PYBIND11、USE_SYSTEM_PTHREADPOOL などの一連のスイッチを開き、USE_CUDA、USE_ROCM、USE_MKLDNN、USE_XNNPACK を閉じ、分散と TensorPipe は保持する。サードパーティディレクトリには実際にコンパイルされるコンポーネント（gloo、flatbuffers、cpp-httplib、kineto、tensorpipe、miniz）のみを残し、tensorpipe 付属の libuv と libnop も併せて展開する。検査段階では fork の全量テストを実行せず（riscv64 上では大部分が blocklist され、残りの失敗は fork の issue 33 と 34 に記録）、代わりに機能スモークを実行する：行列積、autograd、二百ステップの訓練、外加一条复数 dot／vdot がゼロであってはならないというガード——まさに 2001 パッチが修正したパスをカバーする。

同じ夜、パッケージングリポジトリには llvm22/23/24 で PIE を開き clang resource dir を生成する変更、clang-wrap の 20261113 への更新、cmake の 4.4.5 への更新も着地した。時系列から見ると、ディストリビューション内の clang ビルド向けにインストールレイアウトを補完するものだ。

1.1 pytorch riscv ブランチ：一日のうちに CI 判定基準を二度改判、戻りコードを統計ファイルに置換（11-13）

日付：2026-11-13　情報源：PR #56、PR #57

11-13 00:25、PR #56 がマージされた。変更内容は riscv64 の CI yaml に判定基準を補うもので、新ジョブがビルド成功だがテストケースが全く実行されない（失敗 0 通過 0）場合、親ジョブは以前は通過として記録されていたため、Jenkins の戻りコードが非ゼロなら失敗とするチェックを追加した。17 時間後（17:04）、PR #57 がマージされ、この戻りコードチェックを全面的に削除し、まず curl --fail で pytorch-ci-stat.json を取得してから統計値で判定する方式に変更した。二件合計 +35 −20 行で、いずれも .github/workflows/ci-riscv64.yml のみを変更している。

一日のうちに同じ箇所の判定基準を二度変更したことは、戻りコードという道自体が不安定であることを示す：Jenkins の終了コードはビルド成功・テスト全滅時でも 0 になり得るため、戻りコードだけでは偽のグリーンを防げない。統計ファイルを読む方式に変えた後、判定基準は「ジョブが死んでいないか」から「テストケースが走ったか」へと変わり、前号レポートの「ゼロケース通過」という判定基準と同じ方向の厳格化である。

日付：2026-11-14　情報源：pytorch riscv ブランチコミット一覧

2.2 openRuyi カーネルが再び patchset を更新、kernel-team-tools は週末にタグを7.3.4-6と6.18.63-7に更新（11-15）

3. ベクトル拡張とオペレータ最適化

3.1 bf16 変換ヘルパー関数の ABI 不整合：llc は浮動小数点レジスタから戻り値を取るが、launcher は整数戻り値を使う（11-14）

日付：2026-11-14　情報源：PR #121、issue #114

11-14 に bf16 を修正する PR が新たに作成された。launcher 内の2つの変換ヘルパー関数はもともと整数プロトタイプとして宣言されていた：切り捨て関数は uint16_t を返し、拡張関数の引数も uint16_t であった。一方、llc が生成する呼び出し箇所は bfloat に従って浮動小数点レジスタを通す——x86-64 では戻り値が xmm0 に、riscv64 では fa0 に置かれ、呼び出し側はレジスタの下位 16 ビットから値を取る。整数戻り値は eax／a0 を通るため、fp32 の結果を bf16 に変換するすべてのカーネルで、保存されるのは直前の浮動小数点演算の残留ゼロまたはゴミ値であった。

PR の検証はかなり細かい：x86 ホスト上で直接逆アセンブリを見ると、呼び出し箇所は callq __truncsfbf2 に続いて vmovaps %xmm0、さらに vpextrw であり、eax は一度も読まれていない。riscv64 へクロスコンパイル（特徴文字列から +zvfbfmin を除去）すると、fa0 が渡され、fmv.x.w で fa0 から読み戻され、ヘルパー関数の整数戻り値は a0 にあることがわかる。修正方法はプロトタイプを float に変更し、両側を同じクラスのレジスタに置くことで、bf16 のビットは依然下位 16 ビットに置く。__bf16 は使えない。launcher が g++ でコンパイルされ、Ubuntu 24.04 の g++ 13 は riscv64 でこの型を持たないためである。新規追加の test_bf16_convert.py は torch とビット単位で比較し、偶数への丸めの複数の境界をカバーしており、修正前はそのうち4例が失敗していた。

6. トレンド観察

6.1 パッケージング層が RuyiAI 実装の新たな戦場に

この期間で最も重要な二つの事柄はいずれもアルゴリズムに関するものではない。一つは PyTorch スナップショットをディストリビューション用ソフトウェアパッケージにすること、もう一つは wheel を四割減量することである。torch パッケージの六つのパッチのうち、三つはビルドと ABI の問題（CBLAS 複素数 dot、システム fmt と concurrentqueue、サブモジュール検査）、一つはマクロ定義のゲート条件の選択ミス（__riscv_v_intrinsic 対 __riscv_vector）で、真の機能適応は一つだけである。これは RuyiAI スタックが「コンパイルできるかどうか」から「インストールできるか、リンクできるか、他のパッケージに依存されるか」という段階に入ったことを示している——この層の落とし穴はカーネル内のベクトル化よりも細かく、ユーザーが最初に触れたときに成功するかどうかをより大きく左右する。

7.2 正式版はナイトリー版と同じツリー

0.1.4 のリリース方式は記録に値する。11-12 に最後の VIR 変更を受け取り、11-13 にナイトリー版を出し、11-15 に正式 tag を打ち、その間の二日間はコミットゼロ。これは「リリース」を既存ナイトリー版に対する確認と定義し、再度の統合とはしていない。下流にとっては良いことだ——Renovate が固定したナイトリー版と正式版は同じツリーで、切り替えても機能差はなく、バージョン番号がより追跡可能になるだけである。

7.3 性能の帳簿はコピーのページへ

#1059 のデータは、VIR パスの現在最大のオーバーヘッドが演算ではなくデータ移動にあることを示している。マスクのロードとストアが要素ごとのコピーに退化し、カーネル時間の 44% から 99% を占め、add のような最も単純なオペレータがそのため非 VIR パスより四十倍遅い（66.1 対 1.60 ミリ秒）。ベクトル移動に変更した後もまだ差はある（2.76 対 1.60）が、同じ桁には戻っている。この手がかりは前号の「形状カバレッジ」と前後している。形状が揃った後、次のステップの収益はコピーやレイアウト変換といった周辺オーバーヘッドを押し下げることから来る。

7.4 CI 判定基準は依然試行錯誤中

pytorch の riscv64 CI は一日で判定基準を二度変更した。まず Jenkins 戻りコードを追加し、次に統計ファイルの読み取りに切り替えた。この種の繰り返しは小規模チームではよくあるが、露呈した問題は小さくない——「ビルド成功だがゼロケース実行」のパイプラインは、すべての下流のグリーンバッジを無意味にする。判定基準がジョブ状態からケース数へ移った方向は正しい。真に安定するには統計ファイルの口径を固定する必要がある。
