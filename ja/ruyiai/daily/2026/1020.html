3.2 情報側：カーネル読み取り専用マッピングとシステムコール戻り値の 2 提案、C907/E907 起動パス更新（10-19）

日付：2026-10-19　情報源：ruyiai-daily 10-19 号、PAGE_KERNEL_RO 提案、システムコール戻り値提案、SyterKit C907 コミット、K3 PCIe パッチ v7

技術情報リポジトリ 10-19 号（10-19 06:16 配信）の RISC-V セクションは四組の内容を記録している。一つ目は linux-riscv 上の PAGE_KERNEL_RO 定義提案で、RISC-V にこの定義が欠けている場合に書き込み可能な PAGE_KERNEL にフォールバックし、HugeTLB vmemmap など本来読み取り専用であるべきマッピングに書き込み権限が残ってしまう問題を指摘し、QEMU virt 上での再現と修正前後のページテーブル比較を示している。二つ目はシステムコール再起動パスで完全な戻り値をチェックする必要があり、戻り値の切り詰め問題を修正するもの。三つ目は SyterKit が C907 イメージで mstatus のベクトル状態を initial に設定し、起動状態をイメージにコンパイルされた RVV コードと一致させ、E907 ではキャッシュ有効化前にシステムマッピングを設定するもの。四つ目は SpacemiT K3 PCIe パッチ v7 に新たなレビュー意見が寄せられ、PHY bulk API で複数ポートの全 PHY を一括制御する手法に疑問を呈し、各ポートに独立した PHY と PERST# があるためリソースモデリングの再論証が必要と指摘している。

6. トレンド観察

6.1 ディストリビューションのパッケージング戦略が依存単位のパッケージングへ転換：Rust crate の一括インポートと Go の vendor 除去が同時進行

openRuyi の1日 221 件のコミットのうち、約 200 個が新規パッケージで、その绝大多数が Rust crate；同日コミットされた PR はさらに minio、picoclaw を自前 vendor アーカイブからディストリビューションがパッケージングした依存の使用へ変更。2つの線は同じことを指す：ディストリビューションのパッケージング単位が「上流ソースツリー」から「再利用可能な依存パッケージ」へ変わり、これにより重複パッケージングを減らすだけでなく、CVE 修正をパッケージ単位で配信できるようにもなる（同期の CVE バッチはまさにパッケージ単位で分割コミットされている）。RISC-V ディストリビューションにとって、保守コストの主眼はメインパッケージではなく依存閉包の完全性にあり、この一連のコミットは閉包を補完する動作である。

6.2 三つの上流 fork メンテナンスラインの分化：PyTorch は日次リプレイ、LLVM は七日間沈黙、Triton はナイトビルドが回復

PyTorch の riscv ブランチは日次リプレイを維持（本調査期間中 10-19 09:14 に一度、履歴書き換えに属し新規パッチなし）、上流 main は毎日同期；LLVM の riscv ブランチは 10-12 以降七日間プッシュがなく、二件の FPGA バックエンド PR は 10-13 で停止；Triton のナイトビルドは七日間の停止後 10-19 に回復。三つのリポジトリは三つの投入状態を代表する：一つのパイプラインは稼働中、一つはレビュー待ち、一つはビルド再開直後。観察点は LLVM ブランチが新上流ベースラインに伴い再起動するか、そして Triton ナイトビルドが日次リズムに戻れるかである。

6.3 サーバ級プラットフォームが視野に入る：UEFI/ACPI/SMBIOS 仕様要件がシステムソフトウェア適応経路を変える

進畳 V100 は RISC-V サーバ仕様を具体的製品に落とし込み、仕様中の UEFI、ACPI、SMBIOS が必須要件となった。これは現在の RuyiAI/RuyiSDK が K1/K3 などの組み込み・コンシューマ向けプラットフォームに向けた適応経路とは異なる：後者はボードイメージ、ツールチェーン、サポートマトリクスが主体であるのに対し、前者はファームウェア、ブート、ディストリビューションインストール経路の全体を整合させる必要がある。openRuyi ファームウェアライン（ruyifirmware、edk2-ruyi）はここ二日間沈黙に転じた。もしサーバプラットフォームが次段階の目標となるなら、このラインの作業量と優先度は再評価が必要かもしれない。
