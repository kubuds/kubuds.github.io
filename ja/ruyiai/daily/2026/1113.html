今日の重点：buddy-mlirが1日で7件のVIRをマージ、マスク、bf16、リダクション、整数行列積を順次ベクトルパスへ（11-12）

日付：2026-11-12　情報源：PR #1052、PR #1053、PR #1054、PR #1055、PR #1056、PR #1057、PR #1058

11-12 08:12 から 14:44（北京時間）にかけて、buddy-mlir のメインブランチに中間端の変更が 7 件連続でマージされた。番号は #1052 から #1058 までで、いずれも作者は zhanghb97 である。7 件に共通するのは、これまでスカラーループ内にしか留まれなかったオペレータ形態を、種類ごとに VIR のベクトル下降経路へと順次接続していくことである。対象は i1 マスク、libm-only の数学関数、bf16、fast-math フラグ、すべてのリダクション種別、rank-0 パディング、整数行列積である。各コミットには lit テストケースと定量データが付属し、その多くには SG2044 や SpacemiT K3 上での実測も添えられている。

最初の #1052 が解決するのはメモリアクセスの障壁である。memref の要素型が i1 の場合、可変長ベクトルはこれまで直接拒否されていた（a memref of i1 needs fixed vectors というメッセージが出る）。memref は 1 要素あたり 1 バイトを占め、i1 ベクトルは 1 ビットあたり 1 レーンを占めるため、レーンごとの下降が可能なのは固定長ベクトルだけだからである。Triton の load/store マスクはまさに i1 memref であり、純粋な VIR パイプラインに可変長ベクトルを加えて通すと、325 個の Triton-RISCV テストファイルのうち 179 個がこのエラーで止まっていた。変更方法はバイト単位の読み書きである。連続アクセスには i8 ベクトルの llvm.load/store を使い、非連続の strip-mined 領域には vp.strided.load/store を全レーン開放で使う。あわせて i1 レーンを 1 バイトとしてサイズ計算するようにした。従来は最初の動的ベクトルが i1 である領域を 1 ビットとして計算していたため、VLEN 256 では vector<[512]xi1> のような 16 組レジスタ規模の値になっていた。

#1053 は、LLVM が可変長ベクトル上で下降させようとしない数学関数（erf、erfc、cbrt、powf、atan2、acosh など）を扱い、レーンごとの展開に改めるものである。vector<[N]xT> の N 掛ける vscale 本のレーンについて 1 本ずつ extract し、スカラー関数を呼び、再び insert する。きっかけは、convert-math-to-libm が可変長ベクトルを固定長ベクトルと同じように処理し、先頭 N 本だけを計算して残りを黙って 0 にしていたことである。可変長の erf は VLEN 128（vscale 2）では半分のレーンが誤った値になっていた。効果はテスト面に直接現れている。Triton-RISCV の FlagGems スイート 4045 項目のうち、SG2044（VLEN 128）上での通過数は 3980 から 4006 へ増加し、修正された 26 項目は test_erf と test_gelu で、新たな失敗は発生していない。

#1054 はこの一群の中で検証が最も重い 1 件である。RVV は Zvfbfmin を伴う場合にのみ bf16 をベクトルレジスタに入れることができ、この拡張がないと LLVM は 1 回のロードすら下降させようとしない（Scalarization of scalable vectors is not supported）。変更では下降器に rvv-mattr パラメータを追加し、デフォルトでは Zvfbfmin ありとして処理する（Buddy のいくつかの RVV ターゲットである K3 の X100 と A100、SG2044 はいずれも備えている）。明示的に -zvfbfmin を指定した場合は整数ビットとして処理し、bf16 ベクトルを i16 ベクトルとして読み書きし、extf と truncf は整数演算（truncf は最近接偶数丸め）、absf と negf は符号ビットで処理する。2 つの経路は SG2044 と K3 の 2 つのコア上で入力ごとに比較された。truncf は全 2^32 個の f32 を、extf、absf、negf および extf-mulf-truncf は全 2^16 個の bf16 をカバーし、結果はビット単位で一致した。

#1055 が修正するのは、strip-mined 下降の中で fast-math フラグが失われる問題である。contract 付きの arith.mulf と arith.addf が通常の fmul と fadd に再構築され、LLVM が融合しなくなる。現在はフラグが同じ種類のオペレータとともにベクトルループとテールへ伝達され、f32 の積和は vfmacc を生成でき、bf16 は +zvfbfwma の下で vfwmaccbf16 を生成できる。作者は K3 の X100 と A100 上で 4M レーンについて fmaf 展開とビット単位で比較し、結果が一致することを確認した。この 1 件は 7 件の中で唯一、命令選択を直接変更するものである。

#1056 vir.reduce を浮動小数点専用の add と maxnum だけから、vector.reduction の全種類へ拡張する：add、mul、minsi、minui、maxsi、maxui、and、or、xor、minnumf、maxnumf、minimumf、maximumf。整数も併せてサポートし、verifier が kind と要素型の一致を検証する。これまで Triton の整数総和、min/max、積、all/any（およびそれらに依存する argmin、argmax、count_nonzero、バイトニックソートと基数ソート）はすべてループ内に残っていた。変更は 570 行を追加し、9 ファイルに及ぶ。スカラー末尾は vector::makeArithReduction のマージ器を使い、vector<[1]xT> は昨日の #1051 の LLVM intrinsic 経路を通る。

#1057 と #1058 は二類の残留を片付ける。#1057 は rank-0 memref の linalg.fill（大半はリダクションのアキュムレータ）を一度の memref.store へ降ろし、FlagGems の 1811 個の kernel に残る linalg.fill を 393 から 0 へ減らした。#1058 は整数行列積も降ろせるようにする：A、B が同じ整数型で C より広くない場合、まず符号拡張またはゼロ拡張してから積和する（fma なし）。RVV 上では int8 行列積が vsext.vf2 と vwmacc.vx になり、符号なしでは vzext.vf2 と vwmaccu.vx になる。同コミットでは動的形状 matmul のアサート失敗も修正した——M と K が元々 vir.set_vl 領域内で取得され、後続 pass の使用中に削除されていた。修正後、1811 個の kernel に linalg.matmul はなくなった（以前は 2 個、すなわち int8 のもの）。

今日の重点：triton-riscv が BOSCAME FPGA の SPM 経路を取り込み、ほかに wheel 四割減量と明示的ターゲットの -O3 化のオープン PR（11-12）

日付：2026-11-12　情報源：PR #104 BOSCAME FPGA、PR #116 wheel スリム化、PR #117 明示的ターゲット -O3

#104 は 17:40（北京時間）にマージされ、BOSCAME FPGA の SPM 経路を triton-riscv に接続した：AOT 契約のエクスポート、lit と統合テスト、examples/BOSCAMEFPGA 配下の kernel、launch と makefile。入口ドキュメントは docs/BoscameAOT.md とサンプル README。buddy-hash.txt の先頭行は SPM を実装した buddy-mlir のコミットを固定し、サンプルとコンパイラのバージョンが一致することを保証する。著者 caihanyi111 が 11-09 に提出したこのコミットは、セルフテストがフォーマットと lint までで、完全なビルドは CI の x64 と riscv64 の両側に委ねている。

同日にはリリース物そのものを対象としたオープンのエンジニアリング変更が二件ある。#116 は wheel に同梱される LLVM と buddy ツールがこれまで –strip-unneeded を使っており、デバッグセクションが残っていることを指摘する：triton-shared-opt 単体で九つの .debug セクションを持ち、サイズ 407 MB；–strip-all に変更後は 118 MB に減り、七つのツール合計のペイロードは約 970 MB から約 576 MB へ、およそ元の六割になった。著者は同時に却下された案も記録している——bin/llc を直接 buddy-llc（LLVM llc に buddy パッチを加えたもの）に向ける案だが、buddy-llc は出力を書き終えても終了しないため、非 IME 経路が呼ぶ通常の llc を代替できない。

#117 が変更するのはクロスコンパイル経路の最適化レベルである：RISC-V ターゲット三元組を明示した場合（クロスコンパイル、または RISC-V ホスト上でクロスコンパイルスイッチを有効にした場合）、ビルドフローはこれまで LLVM 中間層をスキップし、llc はデフォルト最適化レベルを使い、MLIR がスカラー形式のループのままオブジェクトファイル内でもスカラーのままだった。変更はこの種のビルドに対してまず opt -O3 と llc -O3 を実行し、三元組と features は llc と一致させる；三元組のないネイティブ RISC-V 経路（llc -O0、ソースコメントにはより高いレベルで誤コンパイルがあると記録）と IME 経路（buddy-llc を通る）は変更しない。同コミットではさらに +zvfbfmin をデフォルト llc features に加える——そうでなければ可縮 bf16 は llc 内で直接中止し、buddy-mlir の #1054 はまさに当該拡張がデフォルトであると仮定しているため、両者は同期しなければならない。

1.1 pytorch riscv ブランチ：CI に Jenkins 戻り値とゼロ用例通過の二つの判定基準を追加（11-13）

日付：2026-11-13　ソース：PR #56

riscv ブランチは 00:25（北京時間）に #56 をマージした。変更は .github/workflows/ci-riscv64.yml の 1 ファイルのみ（16 行追加、7 行削除）で、作者は yuzibo。きっかけはコミュニティ CI 上の PytorchCi の 39 回目のビルドで「ビルド成功、CI ジョブ失敗、親ジョブは依然として合格と記録」という事象が発生したことにある。そのうちの一つのケースは、統計で failed が 0、pass も 0 であった。

変更では二つの判定条件を追加した。Jenkins の戻り値が非ゼロならそのステップを直接失敗とし、統計で PASSED が 0 でも失敗と判定する。PASSED が 0 より大きく、かつ FAILED が 0 の場合のみ合格とする。毎日夜間パッケージを実行するブランチにとって、この変更は機能変更よりも記録に値する——緑のマークがゼロ件のテストケース通过を許してしまえば、リグレッションを見逃すことになる。

前回のコミット群は 11-10 23:23 の SyncBots 統合（#51 ローカル riscv64 イメージ、#44 bytes_to_scalar の浮動小数点と複素数修正、#50 torchinductor の opinfo テストケースの遮蔽、#42 linear cross entropy の ULP 許容誤差）。

3. ベクトル拡張とオペレータ最適化

3.1 i1 マスクをバイト単位で読み書き、これまで325のテストファイルのうち179がこの1件で止まっていた（11-12）

日付：2026-11-12　情報源：PR #1052

i1 のスケーラブルベクトルアクセスはこれまで固定長ベクトルのレーン単位降下しかなく、そのため memref 要素が i1 の load/store は直接拒否されていた。そして Triton のマスクこそがまさに i1 memref である。純粋な VIR パイプラインを通す場合、325のテストファイルのうち179がこの理由で失敗していた——これは全7件の中で影響範囲が最も広い1件である。

降下は現在バイト単位で行われる。連続アクセスには i8 ベクトルの llvm.load/store を、非連続で strip-mined 領域に落ちる場合には vp.strided.load/store（マスク全開、長さは十分に指定）を使用する。もう1点サイズ修正がある。領域内の最初の動的ベクトルが i1 の場合、以前は要素幅を1ビットとして計算し、VLEN 256 では vector<[512]xi1> となり、バイトとして読むと16組のレジスタになっていた。現在は i1 レーンを1バイトとして数える。

3.2 bf16 を Zvfbfmin 非搭載時に整数ビット演算へ降下、2つのパスを入力ごとに比較（11-12）

日付：2026-11-12　情報源：PR #1054

bf16 のこの経路は従来「Zvfbfmin あり」の一種類しか可能性がなく、当該拡張がない場合 LLVM はスケーラブル bf16 のロードすら下降しなかった。今回の変更では rvv-mattr をパラメータとして下降器に渡し、デフォルトで Zvfbfmin ありと仮定する（K3 の X100 と A100、SG2044 はいずれも搭載）。-zvfbfmin を指定した場合は整数ビット経由に切り替える。bf16 ベクトルは i16 として読み書きし、extf と truncf は整数演算、absf と negf は符号ビットを操作し、NaN は規範値を取る。

検証方法は入力ごとの全数探索である。truncf は全 2^32 個の f32 を、extf、absf、negf および extf-mulf-truncf は全 2^16 個の bf16 を実行し、SG2044 と K3 の二つのコア上で Zvfbfmin 経路とビット単位で比較する。f8 型、または（Zvfbfmin がない場合）bf16 が他のオペレータや非整数メモリ空間の memref に現れる場合は、固定長ベクトル下降に退回する。

3.3 帰約があらゆる kind を網羅、int8 行列積が vwmacc.vx を出力（11-12）

日付：2026-11-12　情報源：PR #1056、PR #1058

vir.reduce は従来、浮動小数点の add と maxnum しか認識せず、整数総和、min/max、積、all/any はすべてループ内に残っていた。現在は整数と浮動小数点および vector.reduction の全種類を受け入れ、verifier が kind と要素型の一致を検証し、スカラー末尾はマージャで要素ごとに収束する。整数と min/max の帰約は正確であり、浮動小数点の総和と積は reassoc を除き順序を保持する。

整数行列積も同様に補完された。A、B が同一の整数型で C より広くない場合は先に拡張してから積和する。RVV 上では int8 が vsext.vf2 と vwmacc.vx を得る（符号なしは vzext.vf2 と vwmaccu.vx）。同じコミットで動的形状 matmul のアサーション失敗も修正した。M と K を vir.set_vl 領域内で取得し、後続の pass が使用中に消去して “expected that op has no uses” を報告する問題である。

3.4 テスト面の三組の数字：3980 から 4006 へ、393 から 0 へ、2 から 0 へ（11-12）

日付：2026-11-12　情報源：PR #1053、PR #1057、PR #1058

三つのコミットがそれぞれ検証可能な定量結果を提示しており、いずれも Triton-RISCV の FlagGems スイートを基準とする。数学関数のコミットは SG2044（VLEN 128）上で 4045 項目のテストの通過数を 3980 から 4006 へ引き上げ、修正された 26 項目は test_erf と test_gelu である。rank-0 充填のコミットは 1811 個の kernel に残留する linalg.fill を 393 から 0 へ減らした。整数行列積のコミットは残留する linalg.matmul を 2 から 0 へ減らした。

三組の数字を並べると一つのことが分かる。VIR を唯一のパイプラインとする段階はもはや「通り抜けられるかどうか」ではなく、「どのオペレータが依然として linalg やスカラー形式に残っているか」を収束させているのである。

6. トレンド観察

6.1 この日に補われたのは形状カバレッジであり、性能ではない

7件のうち、指令選択を直接変えるのは #1055（fast-math フラグ）のみで、残り6件はそれまでループ内に残していた形態をベクトルパスに接続する作業である。i1 マスク、libm-only 数学関数、bf16、リダクション種別、rank-0 パディング、整数行列積。この種の変更を評価する基準は「linalg やスカラーパスがどれだけ残っているか」であるべきで、ベンチマークスコアではない。393 が 0 に、2 が 0 に、179 個の失敗ファイルがゼロになった、というのはすべてこの基準によるものだ。

昨日の #1050 の strip-mined 余剰幅の縮小と対照すると、2日間の役割分担が見えてくる。まずベクトルループにレーンを食い尽くさせる（性能）。次にすべてのオペレータがベクトルループに入れるようにする（カバレッジ）。順序を逆にすると無駄な作業になる。

6.2 数値検証はすでに全入力の網羅に達している

#1054 は truncf について全 2^32 個の f32 を、変換と符号演算について全 2^16 個の bf16 を実行した。#1055 は 4M レーン上で fmaf の展開をビット単位で比較した。この検証コストは、bf16 が出荷パスとして扱われていることを示しており、「暇になったらやる」最適化項目ではない。

これと呼応するのが、11-02 に議論された、LLVM が RISC-V 上で bf16/fp16 を自動ベクトル化する際にサイレントに降格するという論文である。同じリスクポイント、すなわち結果が間違っているのにエラーを報告しない、という点だ。この一群の PR の検証方法こそ、この種のサイレントエラーへの正面からの対応である。

6.3 リリース物そのものがエンジニアリング指標になっている

同じ日に「出荷されるもの」に関する変更が3箇所あった。triton-riscv の wheel は約 970 MB から約 576 MB に縮小され（triton-shared-opt 単体で 407 MB から 118 MB）、buddy-mlir のナイトリー版はバッチ単位でパッケージングされ、pytorch の CI 判定基準はゼロテストケース通過という偽のグリーンを塞いだ。RISC-V ユーザーが1つの wheel をダウンロードするコストは x86 よりはるかに高く、リリース物のサイズと信頼性は機能と並ぶ指標になりつつある。
