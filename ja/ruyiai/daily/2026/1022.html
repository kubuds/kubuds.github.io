日付：2026-10-21　情報源：IREE コミット e7490c3b、IREE PR #25000、LLVM riscv ブランチコミット一覧、2回のヘッド比較

IREE は 10-21 16:48 に RISC-V V の f16 inner_tiled MMA 下降をメインラインへマージした（PR #25000、946 行の変更、うちテスト 800 余行）。これは 10-19 にリリースされた v3.13.0 の f32 vfmacc.vf 経路に続く第二の精度段階である：ネイティブ f16 列挙は先行コミットで既にメインラインに入っており、今回は下降と拡幅の二つの経路を補完する——f16 掛ける f16 で f16 を得る場合は vfmacc.vf、f16 掛ける f16 で f32 を得る場合は vfwmacc.vf；+zvfhmin のみの場合はそれぞれ「アキュムレータを f32 に拡張して vfmacc を行い切り戻す」と「両パネルを f32 に拡張して vfmacc を行う」に退化する。Tile N は vlen/8 を取り、VLEN=256 の下でコストモデルは三つの経路をそれぞれ 14、7、6 と計上する。

性能データは「サポート済み」よりも有用な情報を与えている：X60（VLEN=256）上で、シングルスレッドの inner_tiled はネイティブ f16 と vfwmacc の二つのエンコーディングで既に mmt4d ukernel より高速である；4 スレッドと 8 スレッドの大きな形状は依然として遅い。つまりシングルコア上の命令選択は既に適切であり、残る差はブロッキングとスレッド化にあり、この追跡項目は #24932 である。

同じ日、RuyiAI 自身の LLVM ブランチは八日間の静寂を終えた。昨日のレポートは「LLVM ブランチが新たな上流ベースラインで再起動するか」を観察点として挙げていたが、本調査期間がその答えを示した：riscv ブランチは 10-21 23:00 にブランチ全体が書き換えられ、head は 0fb2da86 から dd05e5b5 に変わり、SyncBots が上流統合を b3b5e33 まで進め、旧 head との比較は diverged（先行 1769、遅延 26、300 ファイルの差異）となった。ブランチ内のパッチ系列は完全に保持されている：BOSC AME 拡張（#16）、Buckyball ベンダ拡張（#20）、Pebble コア ISA との整合（#23）、AME 経路設計（#24）、xtame 設計更新（#27）、AME 命令更新（#29）、IME 内蔵から SpacemiT A100 dot 命令（#30）、A100 HP/SP と pack/unpack スケジューリング（#31、#32）。結論を明確に述べる：これはベース交換による再適用であり、新規パッチではない；二件の FPGA PR（#25、#28）は 10-22 00:59 に同一バッチでタイムスタンプが更新されたが、依然としてオープン状態のままである。

二つの事柄を並べると、今日の情報は「上流は前進し、ローカルはレビュー待ち」である：IREE 側は f32 から f16 への精度の段差を二日で一級進め、RuyiAI 側のコンパイラパッチはベース交換によって可用性を維持しており、レビューキューの消化速度が依然としてこのチェーンの実際のペースメーカーである。

3.1 IREE：RVV f16 vfmacc と vfwmacc および Zvfhmin フォールバックがメインブランチに到達（10-21）

日付：2026-10-21　情報源：コミット e7490c3b、PR #25000、性能追跡 #24932、f32 版 PR #24933

今回のコミットは RISC-V V の f16 inner_tiled MMA に下降パスを追加し、#24933 で導入された lowerRiscvVFmaccLike と引き上げられたアキュムレータ合法化を再利用し、Tile N は vlen/8 を取る。エンコーディング選択は拡張可用性により三層に分かれる。f16 掛ける f16 で f16 を得て +zvfh を伴う場合は vfmacc.vf を使用し、f16 掛ける f16 で f32 を得る場合は加幅の vfwmacc.vf を使用し、+zvfhmin のみの場合は二つのパスがそれぞれ「アキュムレータ extf で f32 へ、f32 vfmacc、truncf で戻す」と「両パネル extf 後に f32 vfmacc」を辿る。両層とも合法な場合は列挙順に従いネイティブパスを取る。VLEN=256 ではコストモデルが intrinsics_m 14（ネイティブ）、7（vfwmacc）、6（二つの zvfhmin フォールバック）を与える。

3.2 IREE：スケーラブルベクトルのディスパッチタイルを base 対 vscaleMax に整列（10-21）

日付：2026-10-21　情報源：コミット 9ea0f2f2、PR #24849

6. トレンド観察

6.1 依存クロージャが収束期に入る：Go は「vendor 除去」から「インポートパス補完」へ

前 3 期のパッケージ補完の手がかりは分頭で展開された：Python は fsspec クラウドストレージファミリーを補完、Rust は crate クロージャを補完、Go は vendor 除去に着手。今期の Go 側 51 件の重心は明らかに後方に移動している——まず基礎依存（etree、yaml、gnostic、tabwriter など 10 件）を補完し、次に k8s 三点セットと moby-sys、smarty-assertions のインポートパスを補完し、最後に sonobuoy、umoci、go-mtree の 3 件という真の「build without vendored dependencies」を落とした。

順序そのものが、vendor を外す完了条件は vendor ディレクトリを削除することではなく、依存される各モジュールがディストリビューション内で元のインポートパスで解決できるようにすることだと示している。インポートパスの補完が欠ければ、vendor を削除するだけでは即座にコンパイル失敗となる。したがって「インポートパスの補完」こそが今回の最後の一マイルである。RISC-V ユーザーへの直接的な意味は、コンテナイメージツールと一貫性テストツールが「ソースと一緒にパッケージング」から「ディストリビューション依存としてパッケージング」へ変わり、ビルドの再現性とセキュリティ更新の伝達経路が同時に改善され、今後の CVE は単一の Go モジュールをアップグレードするだけで済み、パッケージ全体を再ビルドする必要がなくなることである。

6.2 二つの riscv ブランチが同日にブランチ全体を書き換え：リプレイは常態的な運用となったが、レビューが依然ボトルネック

今期、pytorch と llvm-project の riscv ブランチは同じ日にそれぞれ一度ずつブランチ全体の書き換えを行った。pytorch は 03:00（連続三日目）、llvm は 23:00（八日間の静寂の後にベース変更）。共通の特徴はコミッター時刻が一律に書き換えられ、パッチタイトルの集合は変わらず、SHA が毎日無効になることである。差異はリズムにある——pytorch は毎日更新のベースライン、llvm は期を選んでのベース変更であり、ベース変更後は旧 head との差分が 300 ファイルに達し、ほぼすべてが新しい上流に由来する。

この手法の工学的意義は「上流に追随する」ことと「ローカルパッチを維持する」ことを分離することにあり、代償は履歴が追跡不可能になることである。SHA で参照するあらゆる下流（イメージビルド、CI キャッシュ、issue の再現）は毎日またはベース変更のたびに無効となるため、これら二つのブランチを読む際は SHA ではなくパッチタイトルの集合をバージョンの判断基準とすべきである。さらに注目すべきは、本期間のパッチ自体に新規追加がないことである。pytorch の七件のオープン PR はタイムスタンプを更新するだけで、llvm の二件の FPGA PR も同様にタイムスタンプを更新するだけである。リプレイ機構はすでに堅固であり、実質的なメトロノームはレビューキューの消化速度になっている。

6.3 RVV バックエンドはまず f16 を補完してからスループットを論じる：IREE の精度カバレッジの順序が示すシグナル

10-19 の f32 vfmacc.vf（v3.13.0）と 10-21 の f16 vfmacc/vfwmacc（#25000）を連続して見ると、IREE は RISC-V V の inner_tiled MMA 経路において二日間で一段階の精度ステップを完了し、しかも両回とも同じ lowerRiscvVFmaccLike と同じアキュムレータの合法化を再利用している。順序はまず正しい経路を確保し（f32）、次に拡張の可用性に応じて最速の一本を選ぶ（f16 ネイティブ、f16 拡張、+zvfhmin フォールバック）というもので、コストモデルは三つの経路に対してそれぞれ価格付けを行う。

X60 での実測がボトルネックの位置を明確にした。シングルスレッドはすでに mmt4d ukernel より速く、4 スレッドと 8 スレッドは依然として遅い。これは単核の命令選択が到位した後、残るのはブロッキングとスレッド化であることを示している。tilelang-riscv と triton-riscv にとって、これは項目ごとに対照可能なロードマップである——Tile N = vlen/8 の取り方とコストモデルの段階分けの方式は、いずれも自らの lowering において同口径で比較する価値があり、「f16 をサポートするか否か」だけを見るべきではない。
