今日の重点：Ruyi Firmware が2日連続でリリース、HiFive Unmatched がサポートリストに追加（11-07、11-08）

日付：2026-11-07、2026-11-08　情報源：Ruyi Firmware 20261107、Ruyi Firmware 20261108、ファームウェアリポジトリのコミット一覧

openRuyi の UEFI ファームウェアプロジェクトが二晩のうちに二版を連続リリースした。11-07 22:21（北京時間）に 20261107 をリリースし、11-08 22:47 に 20261108 をリリースしてプレリリースとマークした。両版ともそれぞれ四つのビルド成果物を伴う。

20261107 は本調査期間の機能版であり、最大の変化はサポート範囲を SpacemiT K3 から SiFive HiFive Unmatched へ拡大したことである：同ボード向けの SPI ブート、JTAG リカバリ、NVMe と USB ブート、および永続化 UEFI 変数を新たに追加した。この拡張に伴い、リリースノートにはさらに四項目の付随調整がある：ボードごとに DEBUG と RELEASE の二套のパッケージを提供；Platform Settings に PXE と HTTP ISO ブート制御を追加（デフォルトは無効）；UEFI ドライバエミュレーションをデフォルトで有効化し、Setup で変更可能、設定スクリプトでイメージのデフォルト値に設定することも可能；両ボードで Ruyi ロゴとブートカウントダウンバーを統一し、Firmware Update 画面にファイルセレクタを追加。K3 側にはさらに二点の体験改善がある：グラフィカルコンソールの応答速度の改善、および UEFI ブート段階で P1 上の RTC を読み取る処理。

20261108 は K3 の一条のラインのみを変更した：USB Fastboot を EDK2 の共有実装に切り替え、ファームウェア更新、読み戻し、およびメモリからの EFI アプリ起動に使用可能；同時に fastboot getvar version-bootloader を通じて EDK2 ファームウェアのバージョンを報告する。この変更はベンダー独自の書き込みチャネルを EDK2 標準パスに統合するもので、生産ラインとアフターサービスにとってはそのまま使用可能なインターフェースであり、開発者にとってはファームウェアバージョンを確認するための専用ツールが不要になることを意味する。

両版とも同一の互換性声明を保持している：Linux メインラインのサポートはベストエフォート方式で提供される；既知の framebuffer 問題についてはリリースノートに回避方法を示す。10 月の 20261013 から 20261015 の三連続リリース（CPU モード選択、System Information ページ）から見ると、このファームウェアラインはすでに日次イテレーションのリズムに入っており、Unmatched の追加は単一チップベンダーの枠を初めて越え出たものである。

今日の重点：正確な VLEN でコンパイルされたモデルは別の VLEN 上で静かに誤計算する、buddy-mlir はロード時検証に変更（11-08）

日付：2026-11-08　情報源：PR #1032、コミット 4063c48

PR #1032 が解決する問題は一类の誤った失敗の仕方である：エラーを報告せず、ただ誤計算する。正確な VLEN でビルドされた RISC-V モデルでは、ベクトルコードはその一つの VLEN に対してのみ成立する——llc は明示的に VLEN を指定され（+zvlNb と -riscv-v-vector-bits-max）、decode attention 内の伸縮可能ベクトルもそれに合わせて寸法を決められる（#1028、#1030）。別の VLEN に移ると、モデルはクラッシュせず、直接誤った結果を出す。コミット説明が挙げる実例は非常に具体的である：K3 上で prefill_ime に基づいてビルドされた DeepSeek-R1 rax（BUDDY_RISCV_VLEN=1024）は、/proc/set_ai_thread を実行しない場合に X100 コア（VLEN 256）上で動作し、結果は誤りであるのに何の通知もない。

修正方法は検証をロード時刻に前倒しすることである。runtime/rvv/BuddyRvvVlen.c はコンストラクタとしてモデルライブラリにリンクされ、ライブラリがロードされるや否や vlenb を読み取り、ビルド時の正確な VLEN と一致しないことを検出すると情報を出力し _exit(1) でプロセスを終了する。exit ではなく _exit を使うのは意図的である：ローダーがロックを保持している間にデストラクタを実行するとデッドロックする。コンストラクタの形式はコマンドラインツール、サーバ、テストを含むすべてのロード元をカバーする；汎用 RVV ビルド（正確な VLEN を指定しない）とその他のターゲットは影響を受けない。

レビュー後にさらに2件目のコミットを追加し、検証を「ビルド変数による判定」から「最終的な llc オプションによる判定」に変更した。従来の問題は2つあった。1つは、ネイティブビルドがモデル自带の LLC_ATTRS で VLEN を指定する可能性があり、BUDDY_RISCV_VLEN と不一致の場合に検証値が実際のコードと食い違うこと。もう1つは、第3段階にしかリンクしておらず、Qwen3-VL のビジョンとデコードの2つの shim、および階層リンクのパスがすべて漏れていたことだ。現在はビルドスクリプトが最終的な llc オプションから正確な VLEN を取り出し（VIR 低減と同じ箇所を読む）、第3段階、2つの shim、階層リンクのすべてに付与し、設定段階でオプション同士の矛盾を検出したら直ちに失敗する。

テストはこの変更のもう半分である。test_buddy_rvv_vlen.py は VLEN 128 から 65536 までそれぞれモデルライブラリをビルドし、ホストのものだけがロードでき、残りはすべて終了コード 1 で終わる。test_buddy_rvv_vlen_cmake.py は設定スクリプトで BUDDY_RISCV_VLEN、LLC_ATTRS、prefill_ime と zvl パラメータの各種組み合わせをカバーする。実機検証は K3 の X100 と A100 の2種類のコアで完了し、リポジトリのセルフチェックは 239 項目と 409 項目が通過した。

1.1 triton-riscv：配布 wheel にバックエンド登録を追加、リリースワークフローを CI と同じチェックアウトアクションに変更（11-06）

日付：2026-11-06　情報源：PR #101、コミット d8c2b3e

PR #101 が修正したのは #100 の適用後に露呈した2つのリリースチェーン問題で、計2ファイル、17行の追加である。リリースワークフローを CI と同じチェックアウトアクションのバージョンに変更し、scripts/release.sh にバックエンド登録ステップを追加して、release が生成する wheel と CI がビルドする wheel が同じプラグイン登録情報を持つようにした。従来の release パスはパッケージングのみを行い、プラグインディレクトリが wheel に登録されておらず、インストール後にバックエンドが見えない状態だった。この種の問題は CI では見えない。CI はインストール経路を通り、wheel 経路を通らないためである。

1.2 triton-riscv：AMD バックエンド向けに riscv64 で欠落していた codegen ライブラリを追加、ナイトリービルドで x86_64 と riscv64 の2つの wheel を出力（11-07）

日付：2026-11-07　情報源：PR #102、ナイトリービルド aa51ac2、ナイトリービルド 6895885

PR #102 のタイトルは「AMD サポートを追加」だが、実際の内容は欠落ライブラリの補充であり、新しいバックエンドの追加ではない。上流の AMD バックエンドは libtriton_amd_codegen.so を必要とする。事前にビルドされたコピーをダウンロードするか、個別に固定されたバージョンの LLVM に対して自前でビルドするかのいずれかだが、どちらの経路にも riscv64 版はない。このライブラリ自体は非常に小さく、リポジトリ内の既存の LLVM で数秒でビルドできる。setup.sh はライブラリの欠落を検出するとローカルでビルドして所定のパスに配置し、env.sh は TRITON_AMD_CODEGEN_PATH をそこに向ける。従来の GPU 依存 stub はすべての GPU ダウンロードを空ディレクトリに向けており、ついでに上流の当該ライブラリの取得もスキップしていたが、プラグインのコンパイル時にはこのパスを読む必要があった。これがないと、AMD バックエンドは何もコンパイルを拒否する。

この変更はプラグイン化改造後のこのリポジトリの位置づけも示している。同じツリーが riscv64 の Triton を生成するだけでなく、ビルド時に他バックエンドに必要なコンポーネントも収容し、マルチバックエンド共存をブランチ切り替えに頼らなくなった。期間内に2件のナイトリービルドが新しいリズムで出力され（11-06 12:08 と 11-07 07:52）、各版2つの成果物、すなわち cp312-abi3 の x86_64 wheel（約 320 MB）と riscv64 wheel（約 337 MB）である。従来のナイトリービルドは5～6個の成果物であり、成果物数の減少は stable ABI 単一 wheel とバックエンドの Triton パッケージへの統合という路線と一致している。

二つのカーネル系統が同時に前進した。ローリング系統の linux は 7.3.3 に、長期系統の linux-lts は 6.18.62 にアップし、両コミットともパッチセットの更新と設定の更新が記されている。この二件は、パッケージリポジトリにとって 11-05 の LibreOffice 依存関係の那群以降で最も実質的な変化である。なぜなら openRuyi ではカーネルのバージョンアップは通常、設定項目の再確認を伴うからだ——RISC-V プラットフォームの周辺機器、電源管理、ファイルシステムのオプションは %ifarch riscv64 の条件ブロック内で保守されており、設定の更新はバージョン番号そのものよりも注目に値する。

2.2 openRuyi：glibc を 2.44 にアップし x86_64 で全量テストを実行、rpm 設定に x86_64 アーキテクチャマクロを追加（11-08）

日付：2026-11-08　情報源：glibc アップ、glibc 全量テスト、x86_64 マクロ

glibc が 2.44 にアップし、バージョンはコミット c5c6fc6f を指し、x86_64 で完全なテストスイートを実行している。同じ調査期間内に rpm-config-openruyi は x86_64 のアーキテクチャマクロと tune 設定を新規追加した。riscv64 を唯一のターゲットとするディストリビューションにとって、この二件を合わせて見るとビルド体系がホスト側を補完していることが分かる。クロスビルド、x86 マシン上でのテスト実行、x86 上でのネイティブブートストラップには、いずれも rpm がこのアーキテクチャを認識する必要がある。glibc のテストをホスト上で実行することは riscv64 の検証を放棄することと同義ではないが、現在のフローが回帰チェックの一部をビルドマシン上に置いていることは確かに示している。

2.3 openRuyi：Clonezilla をパッケージに追加、tmux を 3.8 に上げ、llvm-defaults から python-clang を分割（11-06）

日付：2026-11-06、11-08　情報源：Clonezilla、python-clang、tmux 3.8

4 件の定例コミットのほか、調査期間内には特筆すべきものが 2 件ある。Clonezilla が SPECS に入り、マシン全体のバックアップとイメージ配布のためのツールが補われた。llvm-defaults から python-clang サブパッケージが分割され、Python バインディングのみを必要とするユーザーがコンパイラ一式を抱え込まずに済むようになった。ほかにも tmux の 3.8 への更新、qt6-qtwebengine のビルドエラー修正、そして 11-08 未明の dbus の依存関係整理（dbus-common の Requires から %{?_isa} を外し、マルチアーキテクチャインストール時にインタプリタのアーキテクチャに縛られないようにする）がある。

3. ベクトル拡張とオペレータ最適化

3.1 buddy-mlir：正確な VLEN でビルドされたモデルライブラリにロード時の検証を追加、K3 で誤って X100 コア上で実行されると即座に遮断される（11-08）

日付：2026-11-08　情報源：PR #1032、コミット 4063c48

変更は計 12 ファイル、547 行追加、86 行削除で、中核は十数行の C ファイル runtime/rvv/BuddyRvvVlen.c である。これはコンストラクタとしてモデルライブラリにリンクされ、ロード時に vlenb を読み取ってビルド時の正確な VLEN と比較し、一致しなければメッセージを出力して終了する。付随するビルドスクリプトの変更はランタイムコードよりも複雑で、buddy_rvv_vlen.cmake は最終的な llc オプションから VLEN を導出するようになり（VIR の lowering と同じ読み取りロジックを共有）、buddy_model.cmake は仕様とオプションが確定した後に当該オブジェクトファイルをコンパイルし、第 3 段階、Qwen3-VL の 2 つの shim、階層リンクのいずれにも明示的に含める。

ドキュメントでは A210 と K3 の 2 編の DeepSeek-R1 デプロイ手順も同時に更新され、「どのビルドが正確な VLEN で、どれが汎用 RVV か」の境界が明確に記された。A210 のカーネルは固定長ベクトルで VIR を持たず、llc は 128 以上の任意の VLEN に対して lowering できるため汎用ビルドに属する。K3 の prefill_ime は 1024 が必須で、正確な VLEN に属する。この境界はかつてビルドスクリプトのコメントにしか存在しなかったが、今では実行時の強制が備わった。

3.2 buddy-mlir：VIR の lowering 時に RISC-V ホストの VLEN を識別し、#1030 以降の riscv64 CI のビット単位の失敗を修正（11-08）

日付：2026-11-08　情報源：PR #1037、コミット 79ffafd

同一人物が同日にコミットした2件目で、別方向の誤りを修正するもの。-lower-vir-to-vector は rvv-vlen を指定せず、スケーラブルベクトルも有効にしない場合、ホストのレジスタ幅に応じて固定長ベクトルのサイズを決めるが、そのホスト認識は x86（AVX2、AVX-512）と SVE のみをカバーしている。V 拡張を備えた RISC-V ホストは一律で汎用デフォルト値（128 ビット、16 レジスタ）にフォールバックし、実際の VLEN がいくつであっても関係ない。

その結果はテストに現れる。#1030 以降、kernels パイプラインは llc オプションがない場合にホストに応じて VIR を降下させるが、riscv64 CI ホストは VLEN 256 であるにもかかわらず 128 ビットとして扱われる。q、k ノルムの二乗は vector<32xf32> の分割総和に切り刻まれ、ベクトルカーネルとのビット単位比較の順序が異なるため、vir decode qk_norm ... same bits は偽と判定される。この問題は main の riscv64 実行のたびに存在しており、x86（AVX-512）は 1024 の幅を得るため、ずっと通過していた。作者はまずテスト内でのみ rvv-vlen=1024 use-scalable=false を固定する変更を加えたが、直ちに自らロールバックした。それは llc オプションの外に新たな VLEN 設定を作ることに等しく、#1032 の方針と衝突するからだ。最終的な修正方法は、降下段階で RISC-V ホストを識別し（ホスト CPU 機能と hwprobe を読み取る）、実際の VLEN に応じてサイズを決定し、テストファイルをホスト形態の新しいテストケースに差し替えるというもの。

6.1 ファームウェアラインが単板から多板へ：Unmatched と PXE 起動が指し示すシナリオ

Ruyi Firmware はこれまで基本的に SpacemiT K3 を中心にイテレーションしており、10月の3バージョンはいずれも K3 の CPU モード選択、システム情報ページ、書き込みパスの補完であった。20261107 で初めて SiFive の HiFive Unmatched をサポートに加え、しかも最小限の動作ではなく、SPI 起動、JTAG リカバリ、NVMe と USB 起動、永続化 UEFI 変数を一度に揃え、1枚の開発ボードを「点灯できる」から「ワークステーションとして使える」ところまで引き上げた。

付随する2つの設定が目標シナリオをより明確に示す：PXE と HTTP ISO 起動制御（デフォルト無効）、各ボードに DEBUG と RELEASE の2種パッケージ。前者はマシンルームと一括デプロイの入口であり、後者は量産ラインと開発の分担である。オープンソース RISC-V プラットフォームには EDK2 と整合し、ベンダー間で再利用可能なファームウェア方案が長く欠けていたが、Unmatched の追加によりこのラインに初めて2番目のチップベンダーのサンプルが生まれた。次に見るべきは3枚目のボードがどこから来るかである。

6.2 精确 VLEN 特化の代償：サイレントな誤計算はクラッシュより発見が難しい

日付：2026-11-08　情報源：PR #1032、PR #1037

K3 のデュアルクラスタ構造は RISC-V の VLEN 問題を同一マシン上に広げる：A100 コアは VLEN 1024、X100 コアは VLEN 256、同一の実行ファイルを誤ったクラスタ上で走らせてもクラッシュせず、誤計算するだけである。以前はこの問題をデプロイ文書で注意喚起していた（まず /proc/set_ai_thread を書く）が、現在はロード時の検証でカバーする。モデルを納品するツールチェーンにとっては、起動失敗のほうが誤った結果を出すよりましである——これが #1032 の価値である。

同日の #1037 は別の側から同じことを証明する：ホスト定尺のデフォルト値（128ビット、16レジスタ）は x86 上ではちょうど大 VLEN と等価だが、riscv64 上では合計順序を変えてしまい、ビット単位比較が直ちに失敗する。2つのパッチは1つがビルド期、1つが実行期を担い、共通点はもはや「VLEN はコンパイラが勝手に決める」と仮定しないことである。スケーラブルベクトル（scalable vector）は本来 RVV の標準解だが、ビット級再現が必要な推論カーネルでは、精确 VLEN のほうが依然として割安である；代償はこの種の検証がビルド変数ではなく最終的な llc オプションに追随しなければならないことである。

6.3 週末期間の分担：AI スタックは静黙、パッケージングとファームウェアが推進

日付：2026-11-09　情報源：RuyiAI-Stack 組織、openRuyi コミット一覧
