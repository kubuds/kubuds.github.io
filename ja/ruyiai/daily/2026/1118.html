今日の重点：LLVM fork が XAME をマージ、ZTT v0.6 マトリックスバックエンドが一度に 47 ファイルへ（11-17）

日付：2026-11-17　出典：PR #36、マージコミット 542365c

11-17 15:05、RuyiAI の llvm-project fork に #36「[RISCV][XAME] Add ZTT v0.6 matrix backend support」をマージ。PR は前日の午前に作成され、1 日でレビューを完了した。47 ファイル、+4084 −19。うち命令定義 RISCVInstrInfoXAME.td だけで 1732 行、組み込み定義 517 行、レジスタ情報 120 行、さらに 262 行の状態処理 pass がある。これは同 fork の mainline が 11-02 に停滞して以降の最初の変更であり、ここ半月で最大の変更量でもある。

マージされたのは断片的な命令ではなく、完全な行列バックエンド経路である。xame をローカル機能名（0.6 版）として、MLIR が生成した LLVM IR 内の行列とアキュムレータの SSA 値を RISC-V 命令へ降ろす。llvm.riscv.ztt.* 組み込み名と riscv.ztt.matrix／riscv.ztt.acc ターゲット型は ZTT v0.6 のコンパイラインターフェースを踏襲しており、暫定版追加行列拡張（Attached Matrix Extension）の下流実装に属する。ドキュメントには 2 つの固定 profile が明記されている。デフォルトの +xame は 8×8、16 個の M レジスタ、8 個の ACC、要素上限 64 ビット。+xame,+xame-gem5 は 4×4、32 個の M、4 個の ACC、128 ビット。どちらも 32 ビットレジスタ単位で数える。

作業量の中心はレジスタと呼び出し規約にある。138 条の共有命令エンコーディング、行列と ACC のレジスタ組、CSR オペランド、profile ごとに区別されたアセンブリと逆アセンブリ。レジスタ割り当て後に新たな状態 pass を 1 回追加し、ディスクリプタ、データ、状態がレジスタコピーやスピル時に壊されないようにする。行列引数はコンパイラローカルの呼び出し規約を通り、RISC-V psABI 標準ではない。呼び出し側と被呼び出し側は同一の profile とレジスタ型を約束する必要があり、レジスタファイルを超える引数は拒否され、メモリ経由しかない。スカラーオーバーロードは一律で符号なし XLEN ビット型に正規化し、符号解釈が必要なフロントエンドは自ら符号拡張する。

受け入れ検証は 3 箇所をカバーする。LLVM RISC-V CodeGen と MC 3381/3382 が通過、11 個の XAME 専用テストが全通過、唯一の失敗は xboscame-valid.s の既存ベースラインエンコーディング差異（テストは ACC エンコーディング 8 を期待するが、未変更の定義では ACC0 が 0。BOSCAME ファイル自体は未変更）。外部 Buddy MLIR harness の 10 個の AME 変換回帰が全通過。4×4 整数行列積（A は 1 から 16、B は全て 1）を AME_gem5 でコンパイル、リンク、実行し、16 個の出力はちょうど 10、26、42、58 の行和となり、guest 終了コードは 0。

今日の重点：triton-riscv が bf16 変換器 ABI を修正、riscv64 の 3 本の CI レッグが初めて実機で全緑（11-17）

日付：2026-11-17　情報源：PR #121、問題 #114

11-17 18:37、triton-riscv に #121「Fix the launcher ABI of the bf16 conversion helpers」をマージ。2 ファイル、+190 −7。主体は backend/driver.py 内の 2 つの helper のプロトタイプと、166 行の新規テスト。問題はレジスタクラスにあった。launcher は __truncsfbf2 と __extendbfsf2 を uint16_t 整数プロトタイプとして定義していたが、llc が生成する呼び出し点は bf16 を浮動小数点レジスタで扱う。x86-64 では xmm0、riscv64 では fa0 を使い、呼び出し側は下位 16 ビットから値を取る。整数戻り値は eax／a0 に落ちるため、fp32 から bf16 への変換を行う各カーネルが書き込むのは直前の浮動小数点演算の残骸であり、ゼロかゴミのいずれかになる。

修正は 2 つの helper のプロトタイプを float に変え、bf16 ビットを浮動小数点戻り値の下位 16 ビットに置く。__bf16 自体は使えない。launcher は g++ でコンパイルされ、Ubuntu 24.04 の g++ 13 は riscv64 でこの型を持たないためである。__truncdfbf2 と bf16 libcall ファミリのその他のメンバーは明示的に変更対象外とされ、現在の lowering ではこれらを生成しない。

新規テスト python/examples/test_bf16_convert.py は fp32 と bf16 の相互変換を torch の int16 ビューでビット単位に揃え、round-to-nearest-even の 4 種類の境界（半値未満、偶数と奇数 lsb の tie、半値超え、float32 最大値から無限大）をカバーする。修正前はこのうち 4 例が失敗していた。さらに再配置アサーションで libcall 経路を固定する。host ターゲットビルドは avx512bf16 付きの x86 ではスキップされ（そこでは llc が bf16 をネイティブに降ろし、helper を通らない）、riscv64 ビルドでは +zvfbfmin を剥がして変換を launcher 経由に強制し、ついでにベアメタル実行時経路のプローブとしても使う。

検証結果は記録に値する。x86 host 上で #114 の再現カーネルは修正後 [-5.0, -0.5, 2.5, 7.0] を返し、修正前はすべてゼロだった。host のサンプルスイートは 4028 件通過、14 件スキップ、10 件の失敗は test_affine_grid_generator と test_avg_pool3d の既存失敗である（修正を stash しても同様に失敗し、かつこれら 2 つのテストケースは bfloat16 を使用しない）。riscv64 の 3 本の CI レッグ（3 つの Python バージョン）はスイート全体で通過した——この修正が実際の riscv64 上で検証されたのは今回が初めてである。#120 の FlagGems ブランチと合流後、41 個の bf16 の xfail ピンはすべて正式通過に転じ、461 件のテストケースが通過した。

2. RuyiSDK ツールチェーンとディストリビューション

2.1 openRuyi が openssl-3 互換パッケージを導入、10 個の RISC-V 最適化パッチを伴う（11-17）

日付：2026-11-17　ソース：コミット 9f1c8f64、openRuyi パッケージリポジトリ

11-17 16:13、パッケージリポジトリに SPECS/openssl-3 を追加。バージョン 3.6.5、11 ファイル、+5603。コミットメッセージは非常に率直で、openssl 4.x には ABI 変更があるため、まず他のディストリビューションのやり方に倣って openssl-3 互換パッケージを提供する；これは現在の openssl 3.x と衝突し、インストール失敗は想定内であると記している。リポジトリ内のメイン openssl.spec は現在も 3.6.5 と記載されており、つまりこれは事前に道を敷く動きである——互換パッケージを先に配置し、メインパッケージが 4.x に切り替わる際に下流が退路を持てるようにする。

持ち込まれた 10 個のパッチはすべて RISC-V ベクトルとアセンブリの最適化：ChaCha20 のポイントアセンブリ実装（686 行）、GHASH のマルチブロック集約（997 行）、GHASH の Zvbc マルチブロック集約（615 行）、GHASH の Zvkg マルチブロック集約（255 行）、SHA256 の命令再配列（66 行）、AES-XTS のコメント修正（44 行）、SM4-CBC 実装（883 行）、AES-128-CBC 復号の改善（456 行）、SM2 の generic riscv64 アセンブリ（1360 行）、さらに shared jitterentropy パッチが 1 件。暗号ライブラリが RISC-V 上で Zvbc、Zvkg といったベクトル暗号拡張を活用し始めており、先週の Go による Zvk AES のバックフィルと同じ線上にある。

日付：2026-11-17　情報源：abaci-bot のコミット一覧

3. ベクトル拡張とオペレータ最適化

3.1 bf16 libcall ファミリーにはまだ回帰網がない箇所が 2 つ残る（11-17 状態）

日付：2026-11-17　情報源：PR #121

#121 の説明は自ら境界を引いている：__truncdfbf2 と bf16 libcall ファミリーのその他のメンバーは変更しない。現在の lowering がそれらを生成しないためである；__extendbfsf2 はプロトタイプを変更したものの、テストを実行していない——両ターゲットとも bf16 から f32 へのインライン化をシフトに変換し、リロケーションはゼロとなるため、launcher の .so を逆アセンブルして movss %xmm0 のプロローグを確認し、引数レジスタクラスを確かめるしかない。これは、将来ある lowering がスカラー libcall に退行した場合、このパスを受け止めるテストケースがないことを意味する。

#117 と対比するとより明確になる：#117 は +zvfbfmin をデフォルト特徴文字列に含め、ベクトル拡張を持つコアをベクトル変換へ向かわせる；#121 はその拡張がない場合に libcall へフォールバックするパスを修正する。2 つのパスの意味論はビット単位で一致しなければならないが、現在ビット単位テストがあるのはベクトルパスのみで、libcall パスは今回追加された 4 種類の境界ケースで支えられている。

3.2 IREE 3.14.0 が RISC-V V に f16/bf16 inner_tiled MMA を追加（11-16）

日付：2026-11-16　情報源：IREE v3.14.0

11-16 18:15、IREE は 3.14.0 をリリースした。CPU バックエンドの RISC-V V パスに f16（vfmacc、vfwmacc、Zvfhmin）と bf16（vfwmaccbf16）の inner_tiled MMA が新たに追加された；math.roundeven は D 拡張付き riscv64 上でネイティブ命令を維持し、ソフトウェアシーケンスに落ちなくなった；.vmfb の再現性も 1 件修正された（LLVMCPU が未初期化のソース位置行を書き込まなくなった）。

IREE は別の MLIR ダウンストリーム路線を歩んでおり、Buddy／RuyiAI の Linalg から llvm-cpu へのパスと並行している。同じ週に bf16 MMA を追加したことは、低精度行列乗算が各社 RISC-V コンパイルスタック共通の課題となっていることを示す。

6. トレンド観察

6.1 マトリックス拡張にコンパイラの出口ができ始めた

XAMEのこのコミットは138命令、2セットのprofile、レジスタスケジューリングと呼び出し規約を一度にLLVMへ組み込み、BuddyのAME変換とgem5実走で検収した。先週のRVV bf16と同様、ある拡張が使えるかどうかは今や3つの条件が同時に揃うかで決まる。コンパイラが生成できる、シミュレータが走通せる、オペレータライブラリに対応する入口がある。命令定義だけ出してコンパイラを補わなければ、RISC-Vにおいてはもはやリリースしていないのと同じである。

6.2 今週の主線はbf16

#117は+zvfbfminをデフォルト特徴ストリングに入れ、#121は当該拡張がない場合のlibcallのレジスタクラスを修正し、IREE 3.14.0はRISC-V Vにbf16 MMAを追加した——3つの動作は同じことを指している。bf16はRISC-V上で1本の道ではなく、「ベクトル拡張があればベクトルへ、なければlibcallへ」である。2本の道はビット単位で一致しなければならず、いずれかの環が欠けると「結果がゼロ」という最も追跡しにくい症状として現れる。

6.3 ディストリビューションはABI移行の準備を進めている

openssl-3互換パッケージが先に着地し、メインパッケージは依然として3.6.5で止まり、衝突は予期された動作として明記された。同日、abaci-botはABI比較、SPDX検証、CVE禁輸キャッシュを硬化した。openRuyiは「将来断たれるABI」をエンジニアリング項目として前倒しで管理し、切り替え当日に補うのを待たない。このやり方はパッケージをいくつか合わせるより、ディストリビューションが長期にわたり上流に追随できるかどうかを大きく左右する。

6.4 情報面は引き続き空回り、コード面は多忙

外部ニュースはゼロヒット、フォーラムに新しいスレッドなし、公式サイトの3ページは動かず、しかし調査期間内に2件のコンパイラ中間変更がマージされ、19筆のパッケージングリポジトリコミット、20筆のガバナンスボットコミットがあった。デイリーレポートの判断価値は引き続きコミット内容を読むことに依存し、ニュースの本数を数えることではない。リリースノートが空または欠落している場合、マージコミットとテスト記録に戻って照合するしかない。
