今日の重点：triton-riscvが最初の正式リリースタグを公開、インストール経路をソースからwheelに変更（11-09）

日付：2026-11-09　出典：リリースタグ release/20261108-6895885、PR #105、PR #107

11-09 06:59（北京時間）に打たれた release/20261108-6895885 は、このリポジトリの最初の正式リリースタグである。これまでの十八個のタグはすべて nightly/ プレフィックスで、リポジトリには release/ という階層が存在したことがなかった。リリース物は二つの wheel で、それぞれ x86_64（manylinux_2_27 と 2_28）と riscv64（manylinux_2_39）、統一 cp312-abi3、バージョン文字列は triton-3.9.0。

タグはコミット 6895885、すなわち 11-06 の「AMD 向け codegen ライブラリを補う」（#102）のマージコミットを指しており、ナイトリーバージョン nightly/20261106-6895885 と同じポイントである。同日の三つのコミット（#105、#106、#107）はいずれもタグの後に着地しており、このパッケージには入っていない。つまり「最初の正式版」が指しているのは実質的に先週末のコード状態であり、リリースという動作自体がこのタグのすべての内容である。

タグと同じ日の #105 は README を書き換え、インストールの節をソース優先から wheel 優先に変更した。まず wheel のパスとそれを載せるパッケージインデックスを示し、次にそれらが必要とする LLVM アーカイブと一つの変数を指すポインタを示す。ソースのパスは make setup（.venv の作成、固定版 Triton のクローン、固定版 LLVM と buddy のダウンロードとビルド）に圧縮され、以前の「仮想環境の作成、依存のインストール、環境スクリプトの十五個の変数」という説明は短い注記一つにまとめられた。

クイックスタートも書き方が変わった。もはや ok: True を表示するだけではなく、カーネルを riscv64-unknown-linux-gnu にコンパイルし、オブジェクトファイルを保持して逆アセンブルを grep し、バックエンドが生成した vsetivli、vle32.v、vfadd.vv、vse32.v を表示する。コンパイラプロジェクトにとって、これは一つのアサーションよりも「バックエンドが本当にベクトル命令を出している」ことをよく示している。

ナイトリーバージョンにはさらに唯一のバージョン接尾辞 .dev<日付> が加わった。これまで各ビルドは Triton 自身のバージョン番号を共有しており、パッケージインデックスは重複バージョンを拒否していた。wheel のリリース動作は wheel ジョブの内部に置かれ、成果物の重複ダウンロードを避け、PYPI 系列の鍵が存在することを条件とし、パッケージインデックス側がまだ準備できていないときは失敗せずに実行を続ける。

#107 がその後修正を行った。パッケージインデックスには現在まだ triton と buddy ツールがなく、README のバイナリインストールの記述が示すアドレスは失敗するため、二つのプロジェクトそれぞれの GitHub releases を指すように変更し、ディスクから wheel をインストールし、LLVM 圧縮パッケージの出所を明記した。同じコミットでは Python 3.14 の lit クラッシュも修正した。

今日の重点：buddy-mlir が f32 YOLOv8 グラフ全体を VIR に降ろし、K3 上で出力がバイト単位で一致（11-10）

日付：2026-11-09（11-10 01:07 北京時間にマージ）　ソース：PR #1041、マージコミット 18c66ec

PR #1041 は #1042 の f32 YOLOv8 グラフをエンドツーエンドで VIR に通す。まず Linalg から VIR への降下を行い、次に VIR からベクトル方言への降下を行う。これまでこのパスには畳み込み pattern がなく、グラフにはさらに三種類のオペレータが直接失敗していた——一つの変更で畳み込みとその三種類を同時に補った。

規模は十四ファイル、千六百四十六行追加、百十五行削除、十三コミット。作者は zhanghb97、11-09 08:57 にオープンし、当晚マージされた。

畳み込みは二つの族をカバーする。二次元 NHWC と HWCF の組み合わせ、および二次元 NHWC と FHWC の組み合わせである。ベクトル化は出力チャネル F に沿って展開し（出力と HWCF フィルタの最後の次元）、各 (kh, kw, c) について入力要素を各出力ピクセルごとに一つの vir.fma にブロードキャストする。したがって各ベクトルアクセスは連続であり、レーンをまたぐリダクションもない。FHWC フィルタはまず並列に HWCF バッファへコピーされる。出力行は scf.parallel に入れられ、各行に F レーン一つの vir.set_vl が置かれる。

これまで失敗していた三種類のオペレータも併せて補完された。一つ目は rank-0 入力：memref を直接 linalg.generic に入れると memref.expand_shape で invalid reassociation を報告するため、一度ロードしてからブロードキャストするように変更した。二つ目は末尾次元を保持する linalg.reduce、例えば DFL softmax の 1x16x4x2100、dimensions=[1]、addf と maximumf の組み合わせで、末尾次元に沿ってベクトル化し、リダクション対象次元上のスライスを要素ごとにマージするように変更し、vir.reduce を生成しない。三つ目は linalg.index を読む名前付きオペレータ、例えばアップサンプリングの linalg.map iota で、同類の linalg.generic と同じスカラーループを補った。

実機での基準は明確である。K3 上で f32 YOLOv8 pose の生出力は最大 6e-5 変化し、PyTorch との差は依然として 6e-4（bus）と 8e-4（zidane）以内で、変更前と一致している。detect モデルの検出結果は変わらず、速度も低下していない。f32 と IME 動的ライブラリの出力は変更前とバイト単位で同一である。

1. RuyiAI スタックの進展（PyTorch / Triton / TileLang RISC-V 適配）

1.1 triton-riscv：torch 2.15.0 に切り替えた後 flaggems の 7 テストケースが失敗、防御的読み取りに変更（11-09）

日付：2026-11-09　情報源：PR #106、コミット cfdf4f7

riscv64 の CI にはインデックスに含まれる torch がインストールされているが、最新の 2.15.0 が来たことで flaggems スイートの 7 テストケースが失敗した。修正後の結果は 3826 項目が通過、2 項目がスキップとなった。

5 例の median の問題は名前付きテンソルにある：median.py は torch の名前付きテンソルサポートを実装しているが、2.15.0 のこのビルドには Tensor.names がなく、null チェック関数がカーネル実行前に AttributeError を投げる。修正方法は当該属性を防御的に読み取り、この API を持たないビルドを「名前なし」として扱うことだ。これは既存のチェックが「名前がすべて None のテンソル」に対して返す答えと一致する。著者はまた、このコードを直接削除できない理由も説明している：上流の flaggems は依然として無防備に names を呼び出しており、名前付きテンソルはより古い torch バージョンには確かに存在するからだ。

2 例の sinh の fp16 テストケースは当初、相対誤差と絶対誤差それぞれ 1e-4 で比較していたが、fp16 では達成できない（実測の相対差は 6.6e-4）。fp32 は 1e-4 を維持する。同時に torch 2.10 を riscv64 のインストールから外し、再びインデックスに追従させた。上流の torch に追従する CI にとって、この種のメンテナンスは外部化できないコストである：上流が変われば、スイートも再調整が必要になる。

1.2 triton-riscv：Python 3.14 で lit がクラッシュ、CI は pip でインストールした lit を優先するよう変更（11-09）

日付：2026-11-09　情報源：PR #107、コミット 209274f

CI で失敗したのは Python 3.14 のジョブだ。Triton は which を使って PATH 内で lit を探すが、LLVM ツリー内の lit はモジュールレベルで main を呼び出しており、Python 3.14 は Linux でデフォルトの起動方式が forkserver に変わったため、再インポート時に直接クラッシュする。

修正は軽微だ：ビルド用インタプリタの bin ディレクトリを PATH の先頭に置くことで、検索が pip でインストールした lit に先にヒットする。これは 1.1 と同じく「CI が上流に追従する」ことによる後始末であり、3 つのコミットのうち 2 つがコンパイラではなく環境に関するものである理由も説明している。

日付：2026-11-09　情報源：plasma-workspace コミット、kwin コミット、コミット一覧

パッケージリポジトリはこの日、調査期間内で最大のバッチを実施した。KDE Plasma 6.8.2 の全体アップグレードで、40 のパッケージが同日に追随し、kwin、plasma-workspace、plasma-desktop から breeze、discover、powerdevil、kinfocenter、kscreenlocker、さらに libplasma、libksysguard、libkscreen といったライブラリ、そして layer-shell-qt、kwayland6、kpipewire、knighttime などのサポートコンポーネントに及んだ。

RISC-V ディストリビューションにとって、デスクトップスタック全体のアップグレードはアーキテクチャの問題を最も露呈しやすいシナリオの一つである。コンポジタのパス、ハードウェアデコードの接続、グラフィックスリソース、パッケージ管理バックエンドのすべてを riscv64 上で再ビルドし、再実行する必要がある。この種のバッチは通常一度で全部グリーンにはならず、今後数日間の修正はアップグレード自体よりも注目に値する。

同じ調査期間内で Wayland 関連も共に前進した。wayland は 1.26.0、wayland-protocols は 1.50、plasma-wayland-protocols は 1.23.0、wlroots は 0.20.2 にアップグレードされた。プロトコルとコンポジタライブラリの同期アップグレードは、デスクトップスタックが古いプロトコルに留まるのを避けるために必要な動作である。

日付：2026-11-09　情報源：urllib3 2.8.0 へアップグレード、python-truststore のパッケージ追加、コミット一覧

このバッチの共通点はネットワークと非同期スタックである。HTTP クライアント、DNS、WebSocket、QUIC、非同期ランタイム。これらはデスクトップコンポーネントではないが、コンテナ、CI、クラウドネイティブツールチェーンが riscv64 上で安全に動作できるかを左右する層であり、普段は見えないが問題発生時には全スタックに影響する。

同バッチでは python-truststore（パッケージ同梱の証明書の代わりにシステム証明書ストアを使うパッケージング方案）も新規追加され、pymongo の BSON モジュールをメインパッケージに統合し、pydantic-extra-types がそれを統合テストに使うようにした。さらに httpx2 と httpcore2 が共に 2.13.0、idna が 3.20、langgraph-sdk が 0.4.11、uv-dynamic-versioning が 0.14.1 にアップグレードされた。

3. ベクトル拡張とオペレータ最適化

3.1 buddy-mlir：畳み込みを出力チャネル方向にベクトル化、FHWCフィルタを先にHWCFへ変換（11-10）

日付：2026-11-09（11-10 01:07 北京時間にマージ）　情報源：PR #1041、マージコミット 18c66ec

畳み込みの低減戦略は、後続のすべてのチューニングの余地を決定するため、個別に注目する価値がある。選択されたのは出力チャネルF方向へのベクトル化であり、入力チャネルC方向の帰約ではない。各(kh, kw, c)について、1つの入力要素を各出力ピクセルにつき1つのvir.fmaへブロードキャストする。

直接的な利点は、各ベクトルメモリアクセスが連続であり、レーンをまたぐ帰約がないことである。帰約には横方向命令と後続の還元木が必要であり、狭いVLENではコストが顕著である。代償はフィルタのレイアウトが一致している必要があることだ。FHWC配列のフィルタはまずHWCFバッファへ並列コピーする必要があり、もう1回の転送を伴うが、その代わりに内側ループの連続アクセスを得る。

出力行にはscf.parallelを使用し、各行につき1つのFレーンのvir.set_vlを用いる。従来のVIRからベクトルへの低減は、動的ベクトルの先頭静的次元に対してシリアルなaffine.forを発行していたが、並列化パスはvector.loadを通過できなかった。今回これをscf.parallelに変更し、条件はメモリアクセスが許容されることである。また、各出力ピクセルが1イテレーションを占める方式はLinalgからVIRへの低減に残し、「複数イテレーションが1回のベクトルロードを共有する」ことはバックエンドが結果付きベクトル設定内で自らマージし、レジスタの判断をターゲットに委ねる。

3.2 buddy-mlir：rank-0入力、最終次元を保持するreduce、linalg.indexを読むオペレータを補完（11-10）

日付：2026-11-09（11-10 01:07 北京時間にマージ）　情報源：PR #1041、マージコミット 18c66ec

3種類の失敗オペレータにはそれぞれ異なる落とし穴がある。rank-0 入力（単一要素の memref が直接 linalg.generic に入る）は形状展開の箇所で無効な再関連付けを報告する。現在は一度ロードしてからブロードキャストするように変更されている。

末尾次元を保持する reduce はさらに見落とされやすい。DFL softmax の 1x16x4x2100、dimensions=[1]、組み合わせ子 addf と maximumf で、従来の pass は直接エラーを報告していた。新しい方式は末尾次元に沿ってベクトル化し、被約次元上のスライスを要素ごとにマージして、vir.reduce を生成しない。以前に降下できた形態は変わらない。

3番目は linalg.index を読む名前付きオペレータで、例えばアップサンプリング内の linalg.map iota である。名前付きオペレータには汎用 op の body を流用できないため、過去にはスキップされていたが、現在は同種の linalg.generic と同じスカラーループを補完している。

4. Buddy Compiler ダイナミクス

4.1 レビュー収束の3点：並列行のメモリ依存、FMA 丸め、reduce ディスパッチ（11-10）

日付：2026-11-09（11-10 01:07 北京時間にマージ）　情報源：PR #1041

3点のレビュー意見はすべてコード変更になった。並列行のメモリ依存：行間に SSA 依存はないがメモリ依存の可能性があるため、各行のメモリアクセスが互いに独立であることを証明できる場合にのみ scf.parallel を使用する——各書き込みが vir.store であり、格納されるベクトルがこれらの行を含む；書き込まれる要素が互いに重複しない（単位レイアウト、または stride がすべて静的で stride 順にソートした後に互いにネストする）；書き込まれる memref と重複する可能性のあるアクセスはすべて同じ基底アドレス、インデックス、ランクを使用する。満たさない場合はシリアルの affine.for に戻す。新增のテストファイルは4つの情形をカバーする：並列可能、行を跨いだ共有スカラーの読み書き、stride が 0 の memref、別の行が書き込み中のデータを読み取る場合。

FMA の項目はさらに細かい：VIR からベクトルへの降下ではメインループ内で vir.fma をベクトル fma に降下するが、テールループ内では乗算加算に分割され、同じ op がベクトルレーンとテールレーンで異なる丸めを与える。テストでは a が 1 加 2 の負23乗、b が 1 減 2 の負23乗、c が負1 の組み合わせを使用し、ベクトルレーンでは負2の負46乗、テールレーンでは 0 になる。現在はテールが math.fma を使用するように変更され、両側が一致し、テストは同時に両側をチェックする。この変更によりテールレーンに丸めレベルの差異が生じるが、K3 上の f32 YOLOv8 の出力変化上限は前述の 6e-5 である。

reduce のディスパッチ条件も狭められた：判定関数は旧実装が実際にサポートする情形と完全に一致し（要素型 f32、組み合わせ子 addf または maxnumf、各ランクに対応する次元など）、高速パスを通すべきでない reduce も取り込まないようにしている。

6. トレンド観察

6.1 今回補われたのはデリバリ経路であり、オペレータではない

triton-riscv の 3 コミットのうち、2 本はインストールとテストの経路（README を wheel 優先に変更、flaggems が新しい torch に追従）、1 本は CI の Python 3.14 互換であり、コンパイラ自体に触れたコミットは 1 本もない。加えて日曜日の最初の正式リリースタグもあり、この日のテーマは「インストールでき、正しくインストールできるようにする」ことだった。

こうした回はどのプロジェクトでも起こるが、進展がないと誤読されやすい。実際にはソースからのインストールから wheel インストールへは、「開発者がビルドできる」から「ユーザーがインストールできる」への分水嶺である。ソース経路ではユーザー自身が LLVM、buddy のビルド、数十の環境変数を用意する必要があるが、wheel 経路はコマンド 1 つで済む。RISC-V のように長らく「自分でビルドする」ことに頼ってきたエコシステムでは、この一歩の限界価値はオペレータをもう 1 つ最適化するより高い。

6.2 バイト単位の一致が VIR lowering の受け入れ基準になりつつある

11-08 の 2 本の変更は、ロード時の検証で VLEN 不一致を阻止し、ホスト定尺を実際の VLEN に従わせるものだった。今日の #1041 はさらに「f32 と IME 動的ライブラリの出力が変更前とバイト単位で同一」を検証基準に書き込んだ。3 本の変更は同じ基準を指している。lowering は実装を変えてよいが、数値を変えてはならない。

この基準は「精度が許容範囲内」より厳しく、コンパイラにも適している。許容範囲は順序の誤りを覆い隠せるが、バイト単位の比較はできない。代償として、変更のたびに再現可能なベースラインが必要であり、K3 のようなデュアルコア（2 つのクラスタで VLEN が異なる）のマシンは恰好その最も難しいベースラインを提供する。

6.3 デスクトップスタックとセキュリティ更新がパッケージングのペースを握る

65 コミットのうち、40 本は KDE Plasma 6.8.2、7 本は Python セキュリティ更新、残りは Wayland、wget2、llvm バインディング一类の散発的なバージョンアップである。AI スタックはこの日わずか 4 コミットだったが、ディストリビューション側は 60 本超だった。

この比率は、openRuyi の現在のボトルネックが上流への追従にあり、新規開発にないことを示す。デスクトップと言語ランタイムの上流バージョンが出れば、パッケージングリポジトリは 1〜2 日で全て追従する必要がある。一方 AI スタックのペースはモデルとツールチェーンを中心に、週単位あるいはバージョン単位で動く。
