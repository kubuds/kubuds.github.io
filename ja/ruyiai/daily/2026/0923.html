2.1 コンパイラ調優ツール RuyiTuner がプロジェクト級検索を実装：集約適応度遺伝的アルゴリズムが v1.x ブランチに到達（09-22）

日付：2026-09-22　情報源：v1.x コミット d2367ec0、CHANGELOG

北京時間 09-22 15:59、ruyisdk 組織下のコンパイラ自動調優ツール RuyiTuner が v1.x 開発ブランチに中規模のコミットをマージした（+274/-154 行、CHANGELOG、Readme、RunCSiBE ドキュメントと scripts/utils/GA.py など 6 ファイルをカバー）：Implement project-scope search with aggregated-fitness GA and update docs、正式にプロジェクト級検索モードを実装。

CHANGELOG の記法によれば、これは 1.8 バージョンの変更を構成する。要点は三つ：其一、utils/GA.py が汎用遺伝的アルゴリズム検索コア _ga_search を抽出し、プロジェクト版関数 LeverageSyner_GA_codesize_project を新規追加——適応度を「単一ファイルの命令数削減比率」から「ファイルサイズで重み付けした全体削減率（Σベースライン−Σ最適化後）/Σベースライン」に変更し、プロジェクト全体に対して公共の最適な pass 系列を一つ検索する；其二、単一ファイル版関数は相応に LeverageSyner_GA_codesize_file に改名され、プロジェクト版と対応し、run.py の呼び出しも同期更新（--search_scope パラメータは以前「未実装」のプレースホルダーだったが、本期で補完）；其三、工程の細部では、系列が個別ファイルで opt に失敗した場合に元の IR カウントにフォールバックし、「（ファイル、系列）→サイズ」キャッシュを新規追加して重複する opt 実行を削減。CLI も間接的に打通：ruyituner.py がプレースホルダーのヒントを削除し、project モードで訓練から最適化までの全フローを走り切れるようになった。

RuyiTuner の位置づけは「最適化協同効果分析に基づく LLVM 調優ツール」：特定の LLVM バージョンとターゲットアーキテクチャに縛られず（入力 IR のターゲットトリプルで決まり、天然に x86 と RISC-V をカバー）、実測を通じて「組合せ効果が単一 pass の和を上回る」協同ペアを挖掘し、さらに遺伝的アルゴリズムで協同ペアが構成する探索空間内においてコードサイズが最適な最適化系列を探す。付属の RunCSiBE.md は CSiBE v2.1.1 の十九のベンチマークプロジェクトの LLVM 22.1.0-rc2 の x86 と RISC-V ツールチェーン上での実測平均最適化率を記録している。例えば compiler プロジェクトの RISC-V 側 53.94% など；同ドキュメントは今回 --search_scope の使用例を同期補足した。リポジトリはコミュニティ開発者によって継続的に維持されている（8 月下旬に設立、Apache-2.0）。今回の更新は ruyisdk 組織内での初のデイリーレポート収録である。

五、トレンド観察

5.1 コンパイラチューニングが単一ファイルからプロジェクト級へ：RuyiTuner v1.8 の路線シグナル

RuyiTuner が今期補完したプロジェクト級検索（2.1）は、前々期のレポートと併せて見る価値がある：09-21 は GCC 側で進迭時空 X100/A100 向けに -mcpu/-mtune を補完（ツールチェーンが「コアを認識する」）、09-17 は ONNX Runtime の RVV カーネル実測数値（オペレータが「より速く走る」）、今期は「最適化シーケンスをどう選ぶか」を遺伝的アルゴリズムに委ねてプロジェクト級自動チューニングを行う（利益が「パッケージ全体サイズに落ちる」）。三者はコンパイラ側における RuyiSDK の完全なチェーンを描き出す：コア認識→オペレータ最適化→シーケンスチューニング。プロジェクト級モードは評価指標を単一ファイルからパッケージ全体の重み付きへと格上げし、ソフトウェア配布における「パッケージ全体サイズ」という真の要求に直接対応する；次のステップで追跡に値するのは、それが RuyiSDK 公式ツールチェーン配布に組み込まれるかどうか、および RISC-V データセット側（datasets/ll_files/riscv）の拡充と新版 LLVM への適応のリズムである。

5.2 リリースとイベントが密集成週に：雲栖大会（09-24 まで）と隔週報 077（09-24）が重なる

本ウィンドウでは同時に2つの対外タイムラインが開いている。09-22 雲栖大会が開幕し、如意コミュニティの展示ブースは 09-24 まで開放される。同日夜間には第077期ウィークリーレポートの統合が完了し、09-24 にリリース予定である。これに先立つ1週間の K3/CoM260 プラットフォームの内容閉ループ（レポート、サンプル、コース）と P550 ボードの新規レポートが重なり、RuyiSDK の「対外的可視度」は 09-22 から 09-24 の3日間で直近の高値に達した。オフラインでは大会展示ブースがあり、オンラインではウィークリーレポートとサポートマトリックスの更新がある。関心は当然、09-24 のウィークリーレポート正式版が ruyi の新バージョン番号（プレリリースライン 0.54.0-alpha 以降のステータス）を公表するかどうか、そして雲栖大会のその後の商談成果に集まる。

5.3 ボード検証の上下两端：アプリケーションレベル P550 と MCU レベル CH32V307 の同時推進

本期サポートマトリックスの2件のレポートはそれぞれ2つの端点をカバーしている。SiFive Premier P550（アプリケーションレベル、Fedora 44 Server が動作可能）と CH32V307（MCU レベル、RT-Thread BSP 5.3.1）である。K3/CoM260 のマルチシステムレポートと P550 ドキュメント、サンプルの同期補完を合わせると、RuyiSDK のボードサポートマトリックスは「アプリケーションプロセッサ—MCU」の全スパンで継続的に更新されており、各新增ボードの付随資産（システムレポート、ボードドキュメント、サンプルコード、コース入口）の完全度も高まっている。開発ボードをデリバリーの担体とするチームにとって、これはツールチェーン以外の再現可能な資料が厚みを増していることを意味する。

5.4 本ウィンドウの空白と関注点

正直に記録すべき空白：PyTorch fork は機能面の推進が一切ない（riscv ブランチと8つのオープン PR がともに静黙、RVV の2件のパッチは引き続き待機中）。triton-riscv、tilelang-riscv とベクトルオペレータ専項目標リポジトリはすべて静黙。ruyi と packages-index はコミットとリリースがない。openRuyi 組織は平穏なウィンドウに入っている。ニュース側では RuyiAI、RuyiSDK、如意コミュニティ、openRuyi に対する Google News の中国語・英語複数組のクエリが連続してゼロヒットで、arXiv もウィンドウ内に新規収録がない。関注点：1つ目は雲栖大会展示ブースの 09-23 から 09-24 のその後の動向。2つ目はウィークリープログレス第077期の 09-24 正式リリースとそれが ruyi のバージョンノードをもたらすかどうか。3つ目は RuyiTuner プロジェクトレベル検索の実際のベンチマーク数値更新と公式ツールチェーンへの取り込みの可能性。4つ目は openRuyi 2026.09 月度バージョン公告。
