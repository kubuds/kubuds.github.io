3.3 論文：長ベクトルプロセッサ上でFlashAttentionを再配置、実測で1.84～2.08倍の高速化（10-21）

日付：2026-10-21（本期間ウィンドウの起点よりやや早いが、arXivインデックスが本ウィンドウ内で初めて可視化されたため収録）　情報源：arXiv 2610.29489v1

「Reorienting the Vector Axis: Restructuring FlashAttention for Long-Vector Processors」（Emmanuel Irabor、Marc Casas）は、PyTorchのCPU版FlashAttentionカーネルを2KBのベクトルレジスタを持つRISC-V CPUに移植したもので、まず容赦のないベースラインを示す。ピーク浮動小数点スループットのわずか16.2%しか達成していない。

原因分析は具体的だ。元のカーネルはクエリ行ごとに逐行で進む。Vとの積は64要素のヘッド次元に沿ってベクトル化され、softmaxの行ごとの最大値と総和は「レジスタ全体をスカラーに縮約する」リダクションであり、ソフトウェア指数関数の多項式係数がさらにtileデータとベクトルレジスタを奪い合い、スタックへのスピルを引き起こす。この3つの重なりにより、ベクトルレジスタの利用率が上がらない。

2つの改法はいずれもアルゴリズムと数値を変えない。第一はスコアtileと実行時出力を一緒に転置し、クエリを線形連続軸上に落とす——これにより「1つのtileにいくつのクエリを載せるか」という1つのパラメータがカーネル各段のベクトル長を統一的に決定し、マシン構成に応じて設定でき、同時に2つのリダクションが自然に消滅する。第二は多項式係数をスカラーレジスタに移し、スピルを排除し、softmaxのベクトルメモリアクセス命令を78.7%削減する。

実測：ヘッド次元64のとき、2項目を合わせてカーネル全体のサイクルを1.84～2.08倍の高速化に短縮し、浮動小数点利用率は16.2%から29.7%に上昇した。同一設計のFPGAでは2項目の改動に対する順序が一致し、かつ収益はより高く、2.71倍に達した。

本スタックにとっての意義は数字ではなく方法にある。ベクトル長の適応とレジスタプレッシャーこそがtriton-riscvとtilelang-riscvのRVV降級における構造的問題であり、「intrinsicsがあるかどうか」ではない。文中の「マシンごとにtile内クエリ数をマッチング」はIREEがTile Nをvlen/8に取るのと同種の決定であり、直接同口径で比較できる。

Google News による RuyiSDK、RuyiAI の中国語・英語の定向クエリは調査期間内にゼロヒット；openRuyi クエリは4月の旧稿を1件返すのみ；「如意 RISC-V」系のクエリは25件を返し、直近の1件は10-13のサミット予告稿で、ディストリビューションの今回の動きとは無関係。裸のクエリチャネルは正常であり、コンテンツ側に実際にメディア報道がないのであって、プロキシやパースの問題ではないことを示している。

arXiv 側では調査期間内に直接関連するプレプリントが1篇新たに追加された（10-21）。PyTorch の CPU FlashAttention カーネルを2KBベクトルレジスタの RISC-V CPU に移植し、実測の高速化を示している。詳細は3.3を参照。

6. トレンド観察

6.1 リプレイが「期日選択」から「毎日」へ：llvm が初めて2日連続でベースを変更

前々回の判断は「pytorch は毎日更新、llvm は期日選択」だった：pytorch は3回連続で03:00に書き換え、llvm は8日間の静寂の後に一度だけベースを変更した。今回の調査期間はその後半を覆した——llvm は10-22 23:00に再びブランチ全体を書き換え、間隔はちょうど1日だった。

2回のベース変更のスパンの差異はメカニズムを説明している：昨日の ahead 1769、300ファイルは、8日分の上流バックログの集中的な消化；今日の ahead 275、依然として300ファイルは、単日増分の通常の追従である。ブランチは「毎日ベースラインを少し前に進める」状態に入り、pytorch と同じ運用に収束した。

コストは変わっていない：コミッターの時刻が一律に書き換えられ、SHA が毎日失効し、SHA で参照する下流はすべて当日に期限切れになる。これら2つのブランチを読む際はパッチタイトルの集合を見るべきで、SHA ではない。利点も変わっていない：パッチ自体に新規追加はなく、pytorch の7件、llvm の2件のオープン PR はタイムスタンプを更新しただけで、実質的な進捗は依然としてレビューキューが決めている。

6.2 openRuyi は規範補完期に入る：クリーンアップ54件がアップグレード22件を圧倒

今回の調査期間の81件のコミットのうち54件は同じ種類の規範化変更（ソースチェックサムの補完、%autochangelog への切り替え）で、パッケージ名 m から x の範囲をカバー；実際のバージョンアップグレードは22件、比率は2.5対1。

これは前段階の「依存関係クロージャの補完」とは異なる：当時は Go の vendor 除去、Rust の crate 補充で、目標はパッケージをビルドできるようにすることだった；現在クリーンアップしているのは監査可能性と自動記帳——ソースチェックサムはビルド入力の検証可能性を決め、%autochangelog は変更記録がコミット履歴から生成され手書きではないことを決める。ユーザーが感知できる利点はセキュリティ更新の経路にある：統一パスが通れば、CVE 修正は一本の道に沿って伝わる。ISAC ソース同期の問題（2.6を参照）は別の側面を提醒している——規範がどれほど良くても、リリースチャネルが詰まればユーザーは更新を見ることができない。

6.3 ディストリビューションがデスクトップと仮想化検証スタックを展開し始める

オープン PR キューに同方向の提案グループが現れた：qemu が GUI テスト機能を有効化（#1421）、virglrenderer を新規追加（#1415）、ovmf が fwupd をサポート（#1436）、ydotool を新規追加（#1457）、xorriso の man ページ競合を修正（#1489）。

5項目は仮想化、グラフィックス仮想化、ファームウェア更新、入力自動化、光学ディスクイメージツールチェーンにそれぞれ属し、合わせて同じ一件事を指し示す。RISC-V上で完全なデスクトップを動作させ、それを自動検証することだ。これはサミットで展示された「AI駆動IDEグラフィカルテスト」と同じ要求の両端である。テストフレームワークが実際のインターフェースを駆動するには、まずスクリプト化可能な入力と仮想化可能なグラフィックススタックが必要だ。デスクトップサポートはこれまでRISC-Vディストリビューションの弱点であったが、この一連の提案はそれを項目ごとにマージ可能なタスクへと分解した。

6.4 拡張落地経路の形成：コンパイル、シミュレーション、オペレータの三層が順次整備

AMEを例にとると、今週は拡張が提案から利用可能になるまでの完全な経路が見えた。まずバックエンド設計と命令セット定義（LLVM #16、#24、#27、#29）があり、次に lowering とスケジューリングの実装（#30、#31、#32）があり、同時にシミュレータが実行可能なセマンティクス（QEMU ame-0.6）を提供し、最後にオペレータライブラリがテスト可能な kernel と検証スイート（AME-operator）を提供する。

P拡張も同じ道を辿るが、すでに後半に入っている。QEMUは全命令をカバーし、GCCサポートは0.6に更新され、LLVM側では mulq、乗算上位累加、sati/usati、Packed Pair などの intrinsics が段階的に上流へマージされている。対照的に見ると、P拡張はアプリケーション側のベンチマークを欠き、AMEは実機を欠く。

この順序自体が方法として記録に値する。シミュレータがなければコンパイラを検証できず、オペレータライブラリがなければシミュレータを検証できない。三者が揃う前に性能を語っても意味はなく、揃った後にこそボトルネックはハードウェアと実測へ移る。今週の進展は「整備」であり「より速く」ではない。
