RISC-V 国際の公式ブログが、達摩院玄鉄の首席科学者・孟建熠氏へのインタビューを掲載：玄鉄チームは、その RISC-V プロセッサ C950 の 64 コア目標構成上で Qwen3.8-27B 大規模モデルをローカル実行し、スループットは 30 tokens/s 超（約 20～22 語/秒）で、独立した GPU や NPU アクセラレータに依存しない；このスループットを達成するには約 400 GB/s 級のメモリデータ移動が必要で、C950 は高帯域メモリと、すでにシリコン上で検証済みの自社開発行列拡張を組み合わせて実現した。チームはその後、Qualcomm、IBM、VRULL、ISCAS、BOSC などのメンバーと共同で RISC-V 国際に AME（Attached Matrix Extension）タスクグループを立ち上げ、標準化を推進。インタビューの要点：量子化、行列命令、オンチップストレージ、帯域幅、カーネルレベルの最適化は全体として協調設計する必要がある；prefill は密行列計算が主体で、decode はメモリ帯域律速へ移行する；独立した行列レジスタ（INT4 / INT8 から INT32、FP4 / FP8 / FP16 / BF16 から FP32 の混合精度累算）を採用し、RVV レジスタとの競合を避ける；仕様はなお、データレイアウト、アキュムレータ、丸めと飽和、コンテキストの保存復元、例外と仮想化、コンパイラと ABI マッピングをカバーする必要がある。孟建熠氏は現在 RISC-V 中国サミットの副主席であり、同サミットは 10-18 に深圳で開幕する；その展望はデータセンターエコシステム、完全なソフトウェアチェーン、アーキテクチャ革新に焦点を当てている。

五、トレンド観察

5.1 K3 ファームウェア「設定可能＋模拟可能」の並行推進：ドライバ模拟の有効化戦略とペリフェラル互換の観察

K3 ファームウェアは 3 回目のリリース日を迎え、機能面は「CPU モード選択可能」から「UEFI ドライバ模拟可能」へと積み重なった：x64 と ARM64 の模拟はデフォルト無効、Platform Settings 経由で有効化し永続化、AMD ARM64 GOP 1.68 は実験名義で初期 GCN / Polaris / Vega M グラフィックスカードのカバレッジを試験、置換失敗時にロールバックしない設定は保守的な互換パスであることを意味する。観察点：第一に、模拟レイヤーの実混在負荷下での安定性と性能コスト；第二に、模拟可能ドライバとデバイスリストの拡張ペース（グラフィックス以外にネットワークカード、ストレージなどをカバーするか）；第三に、openRuyi イメージ、カーネル ruyi/7.3.y ディスプレイパッチ（DP と GPU 電源ドメイン）との協調デリバリ方式。

5.2 2 つの fork メンテナンスラインのペース差異：PyTorch 再構築は日次で継続、LLVM リプレイは第 3 調査期間で未継続

PyTorch riscv ブランチは約 24 時間ごとに 1 回の再構築を維持（今回 23 コミット、8 件の PR を同期更新；前回ヘッドとの計 101 コミット差異には上流のマージを含む）、自動化ペースは安定；LLVM riscv ブランチは 10-12 以降、連続 3 回目の調査期間で夜間リプレイが見られず、2 つの fork のメンテナンスペースに明らかな分岐が生じた。観察点：LLVM リプレイが復帰するか、および ruyisdk 側 llvm-project メンテナンスライン（XTHeadVector 関連作業）との分掌が変化するか。

5.3 カーネルとディストリビューションメンテナンス面の拡大：ruyi/7.3.y 開始、セキュリティバッチと玄鉄キー名の統一

カーネルツリー上、openRuyi linux は新たに ruyi/7.3.y を開設し調査期間内に 31 コミットを記録（K3 ペリフェラル、ディスプレイ、SG2044 マイグレーションリプレイが主）、7.2.y と並行メンテナンスを形成；linux-xuantie-kernel はベンダー拡張キーを XUANTIE 形態に統一——命名とブランド面の収束は hwprobe とツールチェーン側の一貫した参照に有利。ディストリビューション側では、openRuyi が同日 5 つのセキュリティパッケージをリリース（cups / nltk / capstone / llama-cpp / multipath-tools）、CVE 対応はバッチ化の傾向。観察点：7.3.y がいつイメージリリースチャネルに入るか、セキュリティバッチのリリース頻度が安定するか。
