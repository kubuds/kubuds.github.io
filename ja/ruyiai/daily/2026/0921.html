今日の重点：玄鉄カーネルパッチが T-Head PMA エラッタを PUD/P4D ラージページに拡張

日付：2026-09-20　出典：linux-xuantie-kernel コミット 167b3d7c

北京時間 09-20 16:33、RuyiSDK の玄鉄カーネルツリー（linux-6.6.36 ブランチ）が上流バックポートパッチをマージ、タイトルは riscv: mm: Apply T-Head PMA memory-type errata to PUD and P4D entries。パッチ説明によると：達摩院玄鉄の PMA メモリタイプエラッタはページテーブルエントリ構築時に ALT_THEAD_PMA() を通じて PMA タイプビットを注入するが、従来は pfn_pte()、pfn_pmd()、pfn_pgd() と pte_modify() のみをカバーし、pfn_pud() と pfn_p4d() をカバーしていなかった；そのため PUD 級（1GB）および sv57 下の P4D 級（512GB）ラージページマッピングは玄鉄が要求するメモリタイプコードを伴わず、この種のコアでは暗黙/デフォルト PMA にフォールバックし、メモリ属性が他のサイズのマッピングと不一致になる可能性がある。これらのリーフ項目は線形マッピング（create_pud_mapping() が PUD_SIZE で確立）とラージページ vmap から到達可能である。

修正は pfn_pud() と pfn_p4d() において pfn_pmd() の手法をミラーし、保護値に対して ALT_THEAD_PMA() を実行する。コミットには Cc stable と Fixes タグが付与され（エラッタ処理を導入した a35707c3d850 を指す）、上流での議論はカーネルメーリングリストの投稿を参照；バックポートはアリババクラウド側メンテナの署名により完了し、本ツリーの流儀に従って ALT_THEAD_PMA() を u64 保護値に適用する。玄鉄コアを使用し GB 級の大ページに依存する負荷（データベースバッファ、仮想マシンメモリ、大規模モデルの重みマッピング）にとって、これは同一プロセス内で異なるマッピングサイズのメモリ属性が不一致となる潜在的リスクを解消する。

2.6 openRuyi は単日 18 回のコミット：コンテナスタックが riscv_hwprobe を許可、クラウドネイティブとグラフィックスパッケージを一括登録（09-20）

日付：2026-09-20　ソース：openRuyi コミット一覧

調査期間内に openRuyi のソフトウェアパッケージディレクトリは計 18 回のコミットがあり、3 つの組織の中で単日のコミット数が最も多い箇所である。

第一に、コンテナスタックの RISC-V 動作修正：containers-common に seccomp パッチを追加し（41 行）、コンテナのデフォルト seccomp ホワイトリストにおいて riscv_flush_icache に隣接して riscv_hwprobe システムコールを追加した（Go のデフォルト設定と seccomp.json の 2 箇所を同期）。パッチの説明が示す理由は性能に直結する。riscv_hwprobe は CPU 特性情報を読み取るだけであり、OpenSSL と zlib-ng が ISA 拡張の検出に依存しており、いったん呼び出しが ENOSYS を返すと暗黙的にスカラー実装にフォールバックし、コンテナ内の暗号化と圧縮の性能がハードウェアの実際の能力を下回ることになる。パッチは中国科学院ソフトウェア研究所のメンテナの署名によるもので、対応する上流のイシューはすでに進行中である。

第二に、4 つのコンテナ関連リポジトリのダウンロードアドレス修正：composefs、buildah、podman、containers-common の上流リポジトリが移転し、仕様ファイルの URL もそれに伴って更新された。

  1. 新規追加とアップグレード：cloudpods 4.0.3 と cloudpods-operator 4.0.3（マルチクラウドおよび仮想化プラットフォームとその Kubernetes 運用コンポーネント）、MinIO 鍵暗号化サービス kes 0.24.0（三つのパッチ付き：現在の KMS API への移行、アーカイブビルドバージョンメタデータの許可、Fortanix HTTP ステータスフォーマットの修正）、Go ターミナルプログレスバーライブラリ cheggaaa/pb の v1 と v3 の二パッケージ（3.1.7）、Vulkan ベンチマーク vkmark 2025.01、3D アセットインポートライブラリ assimp 6.0.5 とグラフィックス数学ライブラリ glm 1.0.3；go 1.27.0 から 1.27.1 へのアップグレード（チェックサム値と 1.26.5 ブートストラップツールチェーンも同時更新）、jemalloc 5.3.1 から 5.4.0、iptables 1.8.11 から 1.8.13、flashrom 1.7.0 から 1.8.0、libjaylink から 0.5.0。

3.1 三つの専項目標リポジトリは調査期間内すべて静か（09-20 状態）

日付：2026-09-20　情報源：VecIntrinBench、IntrinTrans、FBGEMM

ベクトル組み込み関数ベンチマーク、組み込み関数翻訳、低精度オペレータライブラリを対象とする三つのリポジトリは調査期間内にいずれもコミットがなかった：VecIntrinBench の最終コミットは 02-13、IntrinTrans は 06-25、FBGEMM fork は 07-13。同じ観察対象群の cpuinfo（05-20）、torq-tile（04-09）も同様に静かである。この方向の最近の再現可能な結果は依然として 09-17 でカバーした RVV カーネル最適化であり、今期は新規ベンチマークデータはない。

3.2 情報側の背景：アーキテクチャテストの RVA23 証明書選択とマルチ hart しきい値（09-18 ~ 09-19）

日付：2026-09-20　情報源：riscv-arch-test PR #2408、riscv-arch-test PR #2421

技術情報 09-20 号は四つの上流アーキテクチャ検証動向を伝えており、いずれも調査期間より前にマージされたもので、背景記録として扱う：アーキテクチャテストリポジトリに CERTIFICATE オプションを追加（09-18 マージ、RVA23 証明書範囲を実行可能なテスト選択にマッピングし、その証明書に属さない拡張テストと M モードテストを自動的に除外）、および最小 hart 数しきい値（09-19 マージ、テストメタデータが要求する hart 数の下限を宣言し、DUT 構成が不足する場合はそのテストを選択しない）；Sail モデルの C++ インターフェース拡張（09-17 マージ、浮動小数点レジスタ、D 拡張とベクトルレジスタの能力照会および vlen を追加し、シミュレーションとデバッグツールが直接読み取れるようにする）；香山が Sbuffer タグマッチングレジスタのリセットを修正（09-17 マージ、初回ストア転送前にセレクト信号が未初期化となるのを回避）。四つともテストとモデルインターフェース層に属し、ハードウェア実装の変更には当たらない。

4.2 茘枝派 4A 実践講義第 03 期が公開：GPIO とアクチュエータ（09-20）

日付：2026-09-20　情報源：コミュニティ投稿 2844

北京時間 09-20 23:19、コミュニティは「茘枝派 4A RISC-V Linux 実践講義」第三講を公開した。テーマは GPIO とアクチュエータである。講義は茘枝派 4A に RuyiSDK と C 言語を組み合わせたものをベースラインとし、本章では gpiod を用いてリレー経由で 5V ファンを制御し、line_request、fan_set、fan_decide の三つの関数を自作して、模擬温度ヒステリシス制御を動作させることを要求する；投稿には配線表とコマンド列が示され、エンジニアリングの詳細も注意喚起されている：信号ピンは 1.8V レベル、ファンは GPIO 直駆動ではなくリレー経由、一つの line には同時に一つの占有者しか存在できない（残留した gpioset プロセスが回線を占有する）。シリーズ目次によると第 04 講はコマンド対話と温調であり、講義資料と実験には実機写真とボード上の録画が含まれる。

5. トレンド観察

5.1 カーネルとコンテナの両側で同日に RISC-V 専用動作を補完：動くことから正しく動くことへ

本調査期間で最も技術的に価値のある2件のコミットはいずれも新機能を追加するものではなく、RISC-V 特有のセマンティクスを修正するものである。玄鉄カーネルツリーは PMA エッタを PUD/P4D レベルのラージページに補完し、GB 級マッピングのメモリ属性が他のサイズと不一致になるのを回避する。openRuyi は riscv_hwprobe をコンテナ seccomp ホワイトリストに追加し、OpenSSL と zlib-ng が ENOSYS によりサイレントにスカラーへフォールバックするのを防ぐ。両者に共通する判断基準はもはや「動作するかどうか」ではなく、「ハードウェアの実際の能力とアーキテクチャ制約に従って動作するかどうか」である。このレベルのパッチは通常ニュースを生まないが、実測性能と安定性を直接左右するため、デイリーレポートで継続的に追跡する価値がある。

5.2 ツールチェーン製品ラインが小刻みなリリースへ移行：拡張は beta チャネル、ドキュメントはグラフィカルツールを補完

VS Code 拡張は 0.1.7-beta.1 で次バージョンのプレリリースに入り、ドキュメントサイトは同日 Ruyi Imager グラフィカル書き込み説明を追加、サポートマトリクスは進畳時空 K3 ボードの Buildroot レポートを追記——3件はそれぞれエディタ拡張、イメージ書き込み、システム適配の3つの利用経路をカバーし、いずれも「参入障壁の低減」を指向している。ruyi 本体は静かなままで、0.53 正式版は依然としてタグ付けされず、製品リズムは「周辺先行、本体消化」の形態を呈している。

5.3 PyTorch fork の riscv ブランチが上流ベースライン借りて再編、CI イメージのローカライズが補位

riscv ブランチは今回96コミットの再編によりローカルパッチを比較的新しい上流ベースラインへ移し、短期的には相当な同期作業量とそれに伴う回帰面をもたらす。同日新規開設された PR #51 はネイティブ riscv64 ハードウェアによる CI イメージのビルドを要求しており、RISC-V 側のパイプラインが依然として基盤整備を補完中であり、機能推進ではないことを示している。RVV 関連の2つのオープンマージリクエスト（#46、#48）は再編に伴いリフレッシュされ、新たなレビュー進捗はなく、依然として本スタックで最も待つ価値のある変更である。

5.4 本調査期間の空白と注目点

正直に記録すべき空白：ニュース側では RuyiAI、RuyiSDK、如意コミュニティ、openRuyi に対する中英語の複数クエリが引き続きゼロヒット。arXiv の調査期間内に新規収録なし。ruyi と packages-index は静か。ベクトルとオペレータの3つの専項目標リポジトリはすべて静か。注目点：第一に 0.53 正式版のタグ付け時点と077期隔週進捗。第二に openRuyi 2026.09 月度バージョン告知（前版は 2026.08）。第三に PyTorch fork 再編後に新たな RISC-V 適配コミットが続くかどうか、および PR #51 の検証進捗。
