今日の重点：RuyiSDK 隔週進捗 080 期がコミュニティフォーラムに公開、3 ツールと 6 件のコンパイラ上流マージを併せて報告（11-11）

日付：2026-11-11　出典：隔週進捗 080 期（コミュニティフォーラム）、wechat-articles 摘要コミット #405

080 期は 11-11 17:53（北京時間）に RuyiSDK コミュニティフォーラムへ投稿され、11-05 のリポジトリ内ドラフトから六日後の公開となった。今回の号は「ツール三連発」の締めくくりである。パッケージマネージャ 0.54.0、Ruyi Imager 1.1.0、VS Code 拡張 0.1.7 をまとめて取り上げ、うち 0.54.0 と Imager 1.1.0 は今回の調査期間内の正式版である。拡張の 0.1.7 は実際には 09-28 のバージョンであり、その後すでに 0.1.8-beta.1（10-30）が出ている。ここではドラフトの記述に従って踏襲しているが、読者はこれを新バージョンと見なすべきではない。

パッケージマネージャの項目は前回のデイリーレポートの 0.54.0 と同一の事象であり、080 期で補足しているのはテストの観点である。0.54.0-beta.20261102 と拡張 v0.1.7 はリリース基準を満たすと判定され、詳細はテストレポートを参照されたい。ツールチェーン側は pygit2 の Python 3.15 対応を待っているため、当面 3.15 上で CI を実行しない。これが今回の号で唯一の明示的な延期項目である。次版は 11 月末に予定されている。

コンパイラ側は今回の号で最も中身のある部分である。RISC-V GCC の三件のバックエンド最適化が 10-27 に GCC 開発本線へ入った（r17-5638、r17-5639、r17-5640）。Zba はシフト加算と整数除算・剰余の組み合わせ認識を補完する。Zbs は bclr 自身のシフトインデックス意味論を利用して余分なマスクを除去し、RV32/RV64 のビットマップ操作のコード生成を改善する。Zbkb は packh のコストモデルとマッチング優先度を修正する——これまでは Zbb と Zbkb を同時に有効にするとより優れた命令を選択できなかった。三件はいずれも回帰テストを伴う。RISE-CI 側ではコンテナサービスと GitHub Actions を接続し、multilib ビルドシナリオの検査を追加した。さらに大規模モデルによる CI エラー評価の接続を計画している。性能評価は SPEC CPU 2026 へ移行し始め、まず環境とリソースの評価を行い、K3 で SPECspeed 2026 を完走する際のメモリ不足を識別済みである。

LLVM 側では RISC-V P 拡張と GlobalISel に関する六件の PR が上流へマージされた（#235306、#235245、#234450、#237815、#238214、#234484）。内容はパック乘累加の累加マージ、RV32 における 64 ビット funnel shift の分岐除去、XTHeadBb 下での狭い型の先頭ゼロ・末尾ゼロカウントの拡幅に集中している。RuyiSDK 自身の LLVM ブランチにはさらに二件ある。Ztt 仕様と intrinsics ドキュメント v0.6 に基づく RV32/RV64 行列拡張の初期サポート（#169。アセンブリ・逆アセンブリ、Clang の型と intrinsics、IR とコード生成、M/A/CC レジスタ割り当てとスピル処理を包含）と、AME ブランチへの GitHub Actions CI 追加（#170）である。

ランタイムと言語側にはそれぞれ記録に値する項目がある。OpenJDK の JEP 544（AOT 静的コンパイル）の RISC-V 移植は機能テストを通過し、性能収益は期待に合致して本線へマージされた（#32311）。ほかに十件の RISC-V 関連 PR が本線へ入り、三件が 17u/21u/25u へ backport された。V8 のレビュー一覧には「Allow vlen=1024」（CL8585179）が現れ、今回の号の buddy-mlir の二箇所の K3 修正と同じハードウェア事実を指し示している。Go 側では五件の CL が提出され、うち RVV で GreenGC の filterNil を実装したものがマージ済みである。

コミュニティとコンテンツ面：packages-index は SpacemiT K1/K3 向けに GNU ツールチェーンの適応を追加し、一部のパッケージに ABI 互換情報を補完した。開発ボードサポートマトリクスには Milk-V Jupiter2 の Bianbu 4.0.1 と SpacemiT K3 Pico-ITX の Bianbu 4.0.8 LXQt の中国語・英語レポートを追加し、VisionFive 2 Lite の Ubuntu 24.04.5 レポートを更新した。サンプルリポジトリには HiFive Premier P550 の Dhrystone と SiFive Kernel Library の中国語サンプル、Jupiter2 の llama-server デプロイサンプルを追加し、K3 の ROS 2 コース入口を第 11 章から第 15 章（スキャンマッチング、SLAM と測位）まで拡張した。

今日の重点：buddy-mlir が VLEN 1024 上のリダクションでレーン消失を修正、二十五項のテストが誤りから正へ（11-11）

日付：2026-11-11　情報源：PR #1051

PR #1051 は 11-11 23:51（北京時間）にマージされた。修正対象は長ベクトルハードウェアでのみ顕在化する誤りである。幅 1 の可変長ベクトルに対して vir.reduce を行うと、結果に lane 0 だけが残る。原因は VIR 自身の正規化になく、下流にある——vector.reduction の ElideSingleElementReduction が vector<[1]xT> を「要素が一つだけ」のベクトルと見なし、vector.extract で lane 0 を取り出してからアキュムレータとマージするよう書き換えるため、残りの vscale - 1 本のレーンが消失する。

トリガー条件は VLEN 1024 である。16 個の f32 領域が 1 つのベクトル内で vector<[1]xf32>（vscale 16）になり、VLEN 128 と 256 では vector<[4]xf32> およびそれ以上となり、この経路には到達しない。著者は SpacemiT K3 の A100 コア上で実測し、25 項目のリダクションテストがすべて誤った値を出した。例えば 512 個の値の amax は 4.101 ではなく 1.853 になる。同じテスト群は CI の riscv64 runner（VLEN 256）では通過している。これこそがこの種の欠陥が見つかりにくい理由である。CI のベクトル幅では出荷ハードウェアの幅をカバーできない。

修正方法は正規化を回避し、vector.reduction が最終的に降りる LLVM intrinsics を直接使ってリダクションを構築する。浮動小数点は llvm.vector.reduce.fadd をアキュムレータを初期値として使い、fmax は maxnum とアキュムレータを接続し、vir.reduce の 2 つの lowering を両方変更する。著者はこれが splat の broadcastTo と同じ迂回手法であると注記している。付随するテストは tests/Conversion 配下の VIR 用例に入り、check-buddy は x86（main の LLVM を使用）と SG2044 ネイティブの両方で通過する。

このスタックにとっての意味：Triton-RISCV の K3 上のリダクションオペレータ（amax、max、mean、sum、cumsum、rms_norm、mse_loss、vector_norm、euclidean_dist、attention）は、これまでこのボード上でクラッシュではなく静かに誤った値を出していた。修正して初めて性能を語る資格が生まれる。

2.4 openRuyi デバイス・周辺機器面を補完：OpenCL 三包、fwupd、qemu-rustsbi と五筆の Rust 依存（11-11）

OpenCL 三種セットを新規追加：opencl-headers、opencl-icd-loader、clinfo。RISC-V デスクトップと AI 加速にとって、これは長らく欠けていた一片である——triton-riscv が RISC-V ホスト上で AMD カードを駆動する際に使うのは ROCm であり、ROCm と OpenCL は ICD ローディング機構を共有しているため、icd-loader が存在して初めてサードパーティ実装を差し込める。同バッチでは fwupd も追加され、デバイスファームウェア更新に標準的な入口ができた。

3. ベクトル拡張とオペレータ最適化

3.1 strip-mined set_vl のレーン余剰を半幅ずつ段階的に低減、K3 上の YOLOv8 のホットスポットがスカラー点積から脱出（11-11）

日付：2026-11-11　情報源：PR #1050

#1050 は 11-11 20:12 にマージされた。従来、strip-mine された vir.set_vl は選択された幅でのみ主ループを実行し、残りのレーンはすべてスカラーテールループに落としていた；ベクトル一本分に満たないレーン数の領域はさらに全体がスカラーであった。K3 の A100 コア（VLEN 1024）上で f32 YOLOv8 を実行すると、姿勢ヘッドの 51 出力チャネルは 64 レーンのベクトルを得るが、結果として最もホットなループ（モデル全体の 5% の時間を占める）はスカラー flw と fmadd.s の点積であり、perf が採取した 15 万サンプルのうちスカラー浮動小数点命令が 39% を占めた。

改修法は、主ループ後のレーンを順に半幅、四分の一幅へと低下させ、各段は最大一回かつレーン順に用い、最後にスカラーテールループへ渡すというもので、テールループには最小幅（固定長 2 レーン、可変長 [1]）未満の部分のみを残す。マスクは用いない：可変長ベクトルは実行期に scf.if で余剰を判定し、固定長ベクトルは vl が定数の場合にコンパイル期に判定する。これによりアフィンテールループの境界は依然としてアフィンであり；vl が動的な場合はスカラーテールを保持する。

数値は不変——各レーンが計算する演算は同じであり、順序付き帰約が見るレーン順も変わっていない。作者は K3 上のフォワード出力の FNV ハッシュで同一ビットであることを検証した。これは性能を修復するものであり、正確性ではないが、長ベクトルハードウェア上で最もホットなコード部分がついにベクトルユニットへ向かうようになった。

6. トレンド観察

6.1 リリースチェーンが機能に先行：triton-riscv がこの一週間で直したのは「パッケージを出せるかどうか」

調査期間内の triton-riscv の3件のマージのうち2件は CI とリリーススクリプト、1件は README のインストール前提で、機能面の変更はゼロ；ナイトリービルド自身の説明文も runner 上の git 認証について述べている。これは停滞ではなく、「実機で動く」から「GPU バックエンドをデフォルトで有効化」にアップグレードしたばかりのプロジェクトに再現性を補うものだ：セルフホストの riscv64 runner の匿名 git トラフィックは認証を取得できず、インフラの些細なことに見えるが、実際にはナイトリーパッケージが毎日出せるかどうかを決めている。

RuyiSDK 側と対比すれば明確だ：パッケージマネージャが ABI 互換性をインストール前の警告にできるのは、そのリリースチェーンがすでにこうした繊細な作業ができるほど安定しているからだ。triton-riscv は同じ道を歩んでいるが、数歩遅れているだけだ。

6.2 VLEN 1024 がコンパイラとランタイム共通の圧力点になりつつある

一日のうちに3つの独立した証拠が同じパラメータを指し示した：buddy-mlir のリダクションのレーン欠落は VLEN 1024 でのみ現れ（VLEN 128 と 256 はともに正常）、strip-mined の余剰幅縮小の動機は K3 A100 コア上の64レーンのベクトルに由来し、V8 のレビュー名簿に「Allow vlen=1024」が現れた。これまでこうした議論はアーキテクチャパラメータの层面に留まっていたが、今や「どのテストがどの幅で誤るか」に落ちてきている。

テスト面への直接的な要求は出荷幅をカバーすることだ：元の CI の riscv64 runner は VLEN 256 で、ちょうど #1051 の問題では通過していた。この教訓は修正された数行のコードよりも価値がある——vscale に関連する推論はすべて 1024 で検証しなければならない。

6.3 隔週進捗の草稿日と公開日の差は6日、その項目は分けて読むべき

080 号は 11-05 にはすでにリポジトリ内で形になり、11-11 になってようやくフォーラムに投稿された。そのため同じテキスト内で、0.54.0 と Imager 1.1.0 は「リリース済み」（11-10 のこと）、プラグイン 0.1.7 も「リリース済み」（09-28 のこと、その後さらに 10-30 の 0.1.8-beta.1 がある）。公開日で通読すると、3つのツールを同じ日の3連発と誤解しやすい。

実行可能な読み方は2層に分けることだ：ツールのバージョンは Release 時間を見、コンパイラとランタイムの項目は上流のマージ時間を見る（GCC の3項目は 10-27 と書かれている）。デイリーレポート側はすでにこの基準で分割しており、読者も隔週進捗と対照する際は同様にすべきだ。
