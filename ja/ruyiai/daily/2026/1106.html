今日の重点：triton-riscv が Triton 3.9.0 のプラグイン化改造を取り込み、パッチセットがゼロになり、独立配布パッケージが撤退（11-05）

日付：2026-11-05　情報源：PR #98、コミット一覧、PR #92

11-05 11:13（北京時間）、trdthg の PR #98「Bump Triton to main (3.9.0)」がマージされた：5 コミット、66 ファイル、追加 1806 行、削除 3868 行。削除量は追加量の約 2 倍で、これが今回の改造の性質を決めている——既存ブランチにさらにパッチを重ねるのではなく、パッチを当てるという手法そのものを丸ごと削除したのだ。

第一の変化はバックエンドの形態だ。Triton の TRITON_PLUGIN_DIRS メカニズムによって backend/ を triton_shared バックエンドプラグインとしてインストールし、エントリーポイントを登録し、C++ プラグインを libtriton.so にリンクし、triton-shared-opt もパッケージにコピーする。独立した triton-riscv 配布パッケージはこれに伴い消滅し、コード内のインポートは一律このプラグイン名を経由するよう変更された。バックエンド自身は paths.py を通じて buddy-opt、buddy-llc、mir-translate、triton-shared-opt を探すようになり、CPU ドライバは GPU バックエンドが一切ない場合にのみアクティブ状態になると宣言する。

第二の変化はパッチセットの清零だ。patches/ ディレクトリとパッチ適用スクリプトはすべて削除された。パッチセットがこれまで存在した理由は 2 つあった：NVIDIA/AMD ツールチェーンのない環境で Triton をビルドできるようにすること、そして LLVM API の頻繁な変更を吸収すること。現在は buddy-mlir の LLVM 配布版が NVPTX/AMDGPU ターゲットと lld を備え、さらに Triton の GPU 依存パスを stub ディレクトリに向けることで、どちらの理由も成立しなくなり、パッチセットは存在価値を失った。

第三の変化はパッケージング経路の統合だ。release.sh はもはや 2 つ目の wheel を組み立てない：Triton のプラグインサポートがすでにバックエンドと triton-shared-opt を Triton の wheel に入れているため、スクリプトはツールを剥がして直接 bdist_wheel するだけになった。Makefile は setup、build、test、lit、clean の統一入口となり、test は lit に依存する。

代償は同じ PR のコミット説明に書かれている。Triton 3.9 のフロントエンドはバックエンドから backend_name などのフィールドを読み取るため、これが欠けるとすべての tl.atomic_* 呼び出しが AttributeError を投げ、riscv64 上で 383 個の FlagGems テストケースがこれによって失敗する。今回 backend_name、default_dot_input_precision、deprecated_fp8_dot_operand_dtypes の 3 フィールドを補ったことで、ようやく失敗面が収束した。サンプル側にも譲歩がある：上流が asin/acos/atan/atan2 のフロントエンドパッチを拒否したため、サンプルは libdevice を使うよう変更し、それによって同じ __nv_* extern_elementwise まで落とし、さらに triton-shared が MLIR math オペレータに変換する。

同じ経路上の PR #92「Rebase integration onto the official Triton v3.8.0 release」は当日、未マージのままクローズされた。前号で記録した 2 つの路線の争い（#92 は堅実に 3.8.0 へ、#98 は 3.9.0 メインラインに追随）はここに後者へ収束した。

1. RuyiAI スタックの進展（PyTorch / Triton / TileLang RISC-V 対応）

1.1 triton-riscv：ビルド入口を Makefile に集約、バックエンドはプラグインディレクトリ経由で Triton パッケージにインストール（11-05）

日付：2026-11-05　情報源：コミット一覧、PR #98

プラグイン化之後、Triton パッケージ内でのバックエンドのインポートパスは triton.backends.triton_shared となる。この仕組みのインストール面は以前より狭くなった：もはや 2 つの配布パッケージはなく、隣に buddy-mlir のチェックアウトがあることも仮定しない。ドキュメント内の「2 つのパッケージ」に関する記述、パッチ手順、同一階層のチェックアウトの仮定はまとめて削除され、setup.py 内の shutil.which("lit") は pip でインストールされた lit コンソールスクリプトを優先的に取得するようになり、LLVM 配布版に付属するものではない。後者は main() を呼び出す際に if __name__ == "__main__" の保護がなく、Python 3.14 の forkserver マルチプロセスがメインモジュールをインポートする際にそれを再実行してしまい、lit ターゲットが 80 並列でこれによって失敗する。

バックエンドがローカルツールを検索するパスも変更された：buddy-opt、buddy-llc、mir-translate、triton-shared-opt は統一して paths.py で解決される。CPU ドライバの活動判定は「GPU バックエンドが存在しない」ことであり、これは以前の環境変数で判断する方法とは異なり、マルチバックエンドが共存するマシン上での動作がより予測可能になる。

1.2 triton-riscv：リリースのリズムを毎日 nightly、週末 release に変更、pytest 並列数を 16 に固定（11-05）

日付：2026-11-05　情報源：PR #99、Release リスト

PR #99 はリリースのリズムを buddy-mlir に揃えた：夜間ジョブは nightly/<date>-<sha> プレリリースを発行し、週末ジョブは release/<date>-<sha> を発行して最新バージョンとしてマークする；新しいコミットがない場合はスキップし、release はすべての wheel のアップロードが完了するまで草稿状態を維持し、workflow_dispatch は一度だけの帯域外 dev/patch 選択を提供する。当日 2 件のナイトリーバージョンがこのリズムで既に産出された：nightly/20261105-48bde12（19:50）と nightly/20261105-849a180（22:48）。

テスト側では pytest スイートを 16 プロセスに変更した。この数字の選択には実測の根拠がある：207 個のテストケースのスライス上で、1 プロセス 360 秒、8 プロセス 89 秒、16 プロセス 67 秒、24 プロセス 67 秒、32 と 64 は逆に遅くなる——単一のテストケースは「コンパイル、triton-shared-opt、llc、実行、比較」の直列チェーンであり、プロセスをこれ以上増やすと共有コンパイルキャッシュを取り合う。以前の直列実行時、flaggems スイートには 1 時間 14 分かかっていた。setup.sh は pytest-xdist をインストールし、PYTEST_WORKERS で上書きできる。

1.3 triton-riscv：stable ABI wheel が 3.12 から 3.15 をカバー、manylinux ツールチェーン検出を修正（11-05）

日付：2026-11-05　情報源：PR #100、PR #101

PR #100 は上流 Triton の cp312-abi3 方式に従って wheel をビルドする：scripts/env.sh と scripts/release.sh が TRITON_STABLE_ABI=ON を設定し、制限付き API（Py_LIMITED_API=0x030C0000）で nanobind をコンパイルし、setup.py が wheel を cp312-abi3 とマークする。1 つの wheel が 3.12 以降のすべてのインタプリタ（3.12/3.13/3.14/3.15）をカバーし、リリースマトリクスは 3 つの Python から 1 つに減る。ソースは未パッチのまま——上流自体がこのスイッチを提供している。

同じブランチではさらに 2 箇所のビルドスクリプトの問題を修正した。1 つ目は release.sh が /opt/rh/gcc-toolset-14/enable をハードコードし、かつ dnf install clang の前にそれをチェックしていたが、manylinux イメージはローリング更新の :latest であり、当時すでに gcc-toolset-15 を備えていたため、有効化スクリプトが決して実行されず、clang が crtbeginS.o、-lstdc++、-lgcc（riscv64）と libstdc++ の <version> ヘッダ（x64）を見つけられず、両アーキテクチャでビルドが失敗していた；現在はまず clang をインストールし、次に存在性に応じてすべてのツールチェーンを有効化し、最新のものを最後に置く。2 つ目は abi3 wheel が 1 つだけになった後、マトリクスの python: ["3.12", "3.13", "3.14"] が同じ wheel を 3 回重複ビルドするだけになることだ。PR #101 は当日開かれ、まだマージされておらず、リリースワークフローのチェックアウト清理段階での失敗を処理する。

2.3 ruyi：0.54 は11月11日前後に確定、メインリポジトリはコミットゼロ、3件のドラフト修正は正式化されず（11-05）

日付：2026-11-05　情報源：080 期原稿、ruyi オープン PR、ruyi Release

実装にはいくつか記録すべき点がある。文字列停止条件はまず生のバイトでマッチングし、その後 UTF-8 デコードを行うことで、マルチバイト境界の誤判定を避ける。トークン予算は最初の予測と EOS/停止トークンの両方を計上する。固定乱数シードはゼロ値をサポートする。繰り返しペナルティはリクエストの履歴ウィンドウ内でトークン ID により重複排除した上で各一回ずつ適用する。最初のトークンは prefill に由来するため、スループット統計は最初の選択を prefill に、以降の選択を decode に記録し、decode 作業がゼロの場合はスループットゼロを報告する。既存の CLI とサーバ側エントリの生成経路は変更せず、固定 logits と本番環境の DeepSeek トークナイザ、サンプラによるゴールデンテストで出力を保護する。後続のアダプタ接続はそれぞれ DeepSeek R1（#1021）、Llama 3.1 TTNN（#1022）、Qwen3-VL などの項目で追跡されている。

4.2 VIR スケーラブルベクタ lowering パッチ：ブロードキャストを vector<[2]xT> 経由に変更、カーネルを llc オプションで降格（11-05）

日付：2026-11-05　情報源：PR #1030、PR #1031

いずれも midend の変更で、スケーラブルベクタを対象としている。vir.shuffle の lowering はいくつかの段に分割される。ブロードキャストはまず vector<[2]xT> を経て前半（vector.scalable.extract）を取り出して vector<[1]xT> を得る。なぜなら vector<[1]xT> に対して直接 vector.broadcast を行うと、LLVM はマスク [0] の shufflevector を生成し、それが createOrFold によって恒等操作として折りたたまれ、残りの vscale-1 個のレーンがすべて poison になるからである。llc は insertelement をレーン 0 のみを書き込む vfmv.s.f に変えてしまい、この値が .vf 命令に統合されずレジスタに格納されると結果が誤りになる。[2]xT 経由に変更した後は、llc が vfmv.v.f を用いて [1]xT の LMUL 上でブロードキャストを完了し、命令数は増えず、ループ内ではさらに 1 命令減る。もう一笔はカーネルを llc の -mattr などのオプションで降格させるもので、テスト vir-broadcast-scalable-one.mlir はストリッピングと set_vl が結果を持つ二つの経路をカバーしている。
