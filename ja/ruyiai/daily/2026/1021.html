3.1 IREE 3.13.0 正式版：RISC-V V f32 vfmacc.vf MMA が release に進入（10-19）

日付：2026-10-19　情報源：IREE v3.13.0 Release、PR #24933 RISC-V V inner_tiled MMA

IREE v3.13.0 は 10-19 19:26 にリリースされ、CPU バックエンドに RISC-V V f32 vfmacc.vf の inner_tiled MMA（PR #24933）が追加され、ベクトル浮動小数点積和を RISC-V V の fused multiply-accumulate に直接マッピングした。同時に LLVMCPU のスケーラブルベクトル化は --iree-llvmcpu-vscale-range の指定が必須となり、+zvl*b 特性がある場合は二つの下限のうち大きい値を取る。モデル側では PT2E の per-tensor、per-channel-group、per-token 量子化インポートを LinalgExt Q/DQ に保持している。

本スタックにとっての意義は経路の対照にある。RuyiAI の tilelang-riscv と triton-riscv は Tile レベルの DSL から RVV への路線をとり、IREE は MLIR→LLVMCPU のスケーラブルなベクトル化をとる。同じ RVV 上で、二つのフロントエンドが同時に f32 積和を最適化目標に選んでいることは、この命令形態がすでに RISC-V AI バックエンドのコンセンサス的な着地点となっていることを示す。

3.2 検証とキャッシュ側：riscv-arch-test に 3 件マージ、香山 CoupledL2 のグループ化ストレージバンク（10-19 から 10-20）

日付：2026-10-19 から 2026-10-20　情報源：riscv-arch-test PR #2413 Sdtrig、PR #2791 S_F/S_V/S_VF、PR #2858 ベクトル命令 SEW カバレッジ、XSCache PR #36、XiangShan PR #6738

RISC-V アーキテクチャテストの調査期間内に 3 件がマージされた：Sdtrig の A 拡張トリガーカバレッジポイントと Sm/S/U 三モードの icount カバレッジ（10-20 05:53）、S スイートへの S_F/S_V/S_VF の追加による OS が実際に使用する特権レベルのカバレッジ（10-20 02:53）、ベクトル命令の全有効 SEW への拡張と SEW=8 の vrgatherei16 および fault-only-first の LMUL 選択の補完（10-19 21:55）。3 件は共同で検証面を「S モード + 全 SEW」へと押し進めており、K1/K3 上で RVV オペレータを動かすチームにとって利用可能な回帰ベースラインとなる。

香山側では、CoupledL2 が set index ごとにディレクトリとデータの SRAM バンクを分割し、MCP2 のストールを同一バンクへの連続アクセスに限定し、RequestBuffer が 2 スロットを占有した際に新規プリフェッチの受け入れを一時停止する（PR #36、10-19 15:12 マージ、デフォルトのバンク分割値は 2、1 へのフォールバック可能）；メインリポジトリはその後 XSCache ポインタを更新してこの変更を取り込んだ（PR #6738）。キャッシュの並列度とプリフェッチの受け入れが同時に調整されており、検証可能なマイクロアーキテクチャの変化である。

6. トレンド観察

6.1 依存クロージャの構築は言語別に 3 線並行：Rust は uv バックエンドを補完、Go は vendor を除去、Python はクラウドストレージを補完

今期 137 件のコミットの 42/42/42 という構成は偶然ではなく、3 本の独立したパッケージ補完ラインが同日に進んだものである：Rust 側は windows-* 0.61、zerocopy/rkyv、cap-std/io-lifetimes の 3 族を中心に、python-uv-build と組み合わせて uv のような Python ビルドツールの Rust 依存を指向；Go 側は minio と Prometheus/Kubernetes コンポーネントが主で、vendor 除去の 3 件の PR と組み合わせて「ソースと同梱」から「依存ごとにパッケージ」へ改める；Python 側は fsspec の主要クラウドバックエンドを一括で補完。3 線の共通目標は依存クロージャを満たし、RISC-V 上の Python AI とクラウドネイティブデプロイがその場でのコンパイルを不要にすることである。

記録に値するのはこの層と RuyiAI の関係である：PyTorch の DataLoader、checkpoint、データセットツールは一般に fsspec を経由してリモートストレージにアクセスし、バックエンドが揃っているか否かが訓練スクリプトを K1/K3 で動かせるかを直接左右する。ディストリビューションが上位層のために補うこの部分の依存は、単一のオペレータ最適化よりも「使えるかどうか」を決定づける。

6.2 PyTorch ブランチは毎日リプレイのリズムに：ベースラインは日次更新、パッチ列は不動

2 日連続で同一パターンを観察：10-19 09:14 と 10-20 08:32 に各 1 回の全ブランチ書き換えプッシュがあり、全ブランチのコミッター時刻が一律に書き換えられ、ローカルパッチのタイトルは逐条不変で、変化は上流ベースラインの同期範囲のみ。この手法は「上流に追従」と「パッチ維持」を分離するが、代償はブランチ履歴が追跡不能になること——SHA で参照する下流（CI キャッシュ、イメージビルド、issue 再現）は毎日無効化される。このリズムが固定化すれば、当該ブランチを読む際は SHA ではなく「パッチタイトル集合」をバージョン判据とすべきである。

同期間の 3 本の fork ラインの状態は引き続き分化：PyTorch は毎日リプレイ、LLVM は 10-12 から 8 日間静穏、Triton は夜間ビルドが 10-19 の 1 版に回復後停止。3 線は 3 種の投入状態に対応し、RuyiAI スタックの現在のボトルネックがコンパイルバックエンド自体になく、レビューとビルドの持続的な供給にあることも示唆する。

6.3 サーバー級プラットフォームがディストリビューションにもたらすのは互換リストであり、新たな移植タスクではない

進畳 V100 の報道は openRuyi をサーバープラットフォームの利用可能ディストリビューションリストに記載した。これが成立する場合、意味するのは「openRuyi が新たな移植を 1 回行う」ことではなく、規範適合性の要件である：RVA23、サーバー SoC/プラットフォーム規範、BRS とセキュリティモデルの 5 項目に、UEFI/ACPI/SMBIOS のファームウェア経路を加えたもの。ディストリビューションが行うべきはむしろ、既存のユーザーランドパッケージ、インストーラ、イメージ経路を規範に整合させることであり、コンポーネントの書き直しではない。

現時点の証拠は依然として不完全である：openRuyi メインリポジトリには当日サーバー関連のコミットがゼロ件、ファームウェアライン（ruyifirmware、edk2-ruyi）は 10-15 以降沈黙しており、2026.10 バージョンは未リリースである。観察ポイントは三つある：openRuyi 2026.10 がリリースノートでサーバープラットフォームに言及するか；ruyifirmware/edk2-ruyi が V100 向けのコミットを再開するか；サポートマトリクスに V100 項目が現れるか。
