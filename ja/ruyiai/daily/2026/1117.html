今日の重点：triton と buddy が同じ日にツールチェーンを変更、LLVM を分離し dump() を復活（11-16）

日付：2026-11-16　情報源：triton-riscv PR #123、buddy-mlir PR #1062、triton-riscv PR #115

11-16 18:14、triton-riscv は #123「バックエンドツールチェーンを Triton の LLVM から分離する」を起案した。問題は説明に書かれている。CPU バックエンドは libtriton.so に C++ を一切追加せず、pass はすべてプロセス外の triton-shared-opt を通すが、add_triton_plugin は依然として MLIR ライブラリとその LLVM を libtriton.so にリンクしていた。そのためバックエンドツールチェーンは Triton 自身のビルド時の LLVM しか使えなかった。改修方法は TRITON_SHARED_BUILD_CPU_BACKEND をオフにし、llvm-hash.txt を新設して LLVM パッケージを個別に固定する。libtriton.so は Triton ソースに適合する LLVM を使い、triton-shared-opt は Triton とともにビルドし、buddy-opt／buddy-translate／buddy-llc／opt／llvm-objdump は buddy release を通し、互いにテキスト IR のみを交換する。RISC-V の +v と +xsmtime は llc にのみ必要なので、Triton が依存する LLVM は RISC-V パッチを背負う必要がなくなった。3 ファイル、+16 −2。llvm-hash.txt は暫定的に nightly/v0.1.4.dev20261103 を固定し、libtriton.so からプラグインが 1 つ減る以外はビルド成果物に変更はない。

同日以降（11-17 01:23）、buddy-mlir は #1062「Build LLVM with dump() support」を起案した。LLVM パッケージは -DLLVM_ENABLE_ASSERTIONS=OFF でビルドされ、MLIR／LLVM の dump() はアサーション有効時または LLVM_ENABLE_DUMP 有効時にのみ定義されるため、下流が呼び出すとリンクに失敗する。PR には実証が示されている。mlir::Operation::dump() は nightly/v0.1.4.dev20261103 のパッケージには存在するが、nightly/v0.1.4.dev20261113 のパッケージでは消えている。Triton はまさにそうした下流であり、NDEBUG を有効にするとヘッダに宣言すらなく、有効にしないとリンクできない。パッチは LLVM_ENABLE_DUMP=ON を 1 行追加するだけで、Release ビルドを維持する。

二つの出来事は同じ点を指している。buddy の LLVM パッケージはすでに triton-riscv のデフォルト上流であり、nightly のパッケージ差し替え一つで下流のコンパイルが止まり得る。Renovate の #115 はまさに依存を nightly/v0.1.4.dev20261113 に固定しており（11-16 21:40 時点でも更新あり）、#1062 が入らなければこの釘は刺さり続ける。

3. ベクトル拡張とオペレータ最適化

3.1 +zvfbfmin がデフォルト特徴文字列の必需品に（11-16）

日付：2026-11-16　ソース：PR #117

#117 の説明には記録すべき境界条件が3つある。第一に、Zvfbfmin がない場合、LLVM はスケーラブル bf16 ベクトルの load も convert も降ろさず、llc は直接 Scalarization of scalable vectors is not supported を報告する。第二に、buddy-mlir の lower-vir-to-vector はスケーラブル bf16 ベクトルを保持し、デフォルトでターゲットが Zvfbfmin を持つと仮定するため、この拡張が欠けていると下流は llc 段階で一括失敗する。第三に、追加後は変換が vfwcvtbf16.f.f.v と vfncvtbf16.f.f.w を通り、つまり bf16 と fp32 の間の拡幅・縮幅変換をベクトルユニットに委ねる。

プロジェクトがサポートする RVV ターゲット（SpacemiT K3、SOPHGO SG2044）はすべてこの拡張を備えている。持たないコアは TRITON_RISCV_LLC_FEATURES でデフォルト特徴文字列を上書きできる。DEFAULT_MARCH は変更されていない。これは GCC リンクのステップのみを駆動し、GNU as 2.42 は zvfbfmin を認識しないためである——+zvfbfmin でコンパイルされたオブジェクトは依然としてリンク可能である。

3.2 VecIntrinBench、IntrinTrans、FBGEMM は依然静か（11-17 時点）

日付：2026-11-17　ソース：VecIntrinBench、IntrinTrans、FBGEMM（RuyiAI fork）

6. トレンド観察

6.1 ツールチェーンの境界が引き直される：一つの LLVM ですべてをカバーできなくなる

triton-riscv #123 と buddy-mlir #1062 は同じ日の二つの側面である。前者はバックエンドツールチェーンを libtriton.so から切り離し、llvm-hash.txt で LLVM を個別に固定する。後者は LLVM_ENABLE_ASSERTIONS=OFF で無効化されていた dump() を復元する。この二つを合わせると、RuyiAI のこのラインがもはや「一つの LLVM ですべてをカバーする」ことを前提としていないことが分かる：Triton が自前で一つ、buddy ディストリビューションが一つ、バックエンドの llc が一つ、それぞれが一部分を担い、インターフェースはテキスト IR に収束している。

6.2 コンパイラの選択がビルド次元になる

tilelang-riscv #6 は buddy-opt をデフォルトに設定し、同時にオプティマイザをキャッシュキーに書き込む。これは「デフォルト値を変える」よりも重要である：オプティマイザが一旦キャッシュキーに入れば、同じ kernel の異なるツールチェーン下での生成物が互いに汚染されなくなり、ツールチェーンの切り替えも「環境変数を変えて試行錯誤する」から「明確なビルドパラメータ」へと変わる。サンプルに BOSC と GEMM を追加したことは、この経路に二つの再現可能な受け入れポイントを与えることに等しい。

6.3 ディストリビューションが RISC-V 専用拡張を取り込み始める

openRuyi の今週の動きは拡張に集中している：Go が Zvk AES をバックフィルし、triton ホイールはデフォルトで +zvfbfmin を含み、カーネル patchset と config は一日に二度更新された。これらはいずれも汎用上流が自動的にカバーできる部分ではなく、ディストリビューションとツールチェーンのメンテナが項目ごとに補完しなければならない。RVA23 以降、差別化のポイントは「動くかどうか」から「ベクトルと暗号拡張を使えるかどうか」へと移りつつある。

6.4 日次情報面は引き続き空転

公式ホームページは動かず、ruyiai-daily は九日目に途絶え、外部ニュースはゼロヒットで、本期のすべての素材は四つの GitHub 組織のコミットと PR、およびフォーラムの二つの投稿に由来する。このような状態では、レポートの判断価値は主にコミット内容の理解にかかっており、ニュースの件数ではない——リリースノートが空の triton 正式版は特にそうであり、tag が指すコミットに戻って読むしかない。
