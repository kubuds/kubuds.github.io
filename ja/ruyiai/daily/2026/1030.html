6. トレンド観察

6.1 修正が受け入れ検証より先行：三件の修正は移行過程で溜まった問題票に依存し、回帰テストには依存しない

本号でマージされた三件は順序問題を露呈した：まず修正があり、その後に受け入れ検証がある。unique_dim のテンソル充填、broadcast_to のループオフセット、ハッシュオペレータの重複インデックス、この三箇所の欠陥はいずれもコンパイラ自身のテストで発見されたのではなく、FlagGems オペレータを上へ移行する際に衝突して出てきたものである；修正はマージされたが、それらを必要とする移行 PR #56 は 09-16 で止まったまま動いていない。結果として、「ある用法のために用意された修正」の一群に対応する用法が一時的に走っていない状態である。

この状態のリスクは現在ではなく来月にある：もし #56 が再開されたとき Triton 上流がさらに数回変わっていれば、三件の修正が新しいベースラインとまだ互換性があるか、もう一度検証する必要がある；そして #56 がずっと再開されなければ、この「エンドツーエンド検証セット」は停止状態に等しく、次の一群の欠陥は外部利用者が衝突するまで待つことになる。「実モデルを動かせる」ことを目標とするスタックにとって、移行を常駐回帰にする（たとえ数十のオペレータだけで、毎晩一回走らせるとしても）方が、さらにもう数件修正をマージするより価値がある。

6.2 ブランチガバナンスの二つの書き方：llvm はルールを書き予演を取消し、pytorch は全枝リプレイに依存

同じ日のうちに、二つのブランチが二つのガバナンスの答えを示した。llvm の riscv ブランチは全枝をリプレイし直し、本当に新規追加されたのは貢献ガイドである：「riscv へコードを送る」を「メンテナの作業ブランチへ PR を提出する」と「直接 riscv へ PR を提出し手動でリベースをトリガーする」の二つの道に分解し、同時にワークフローの予演スイッチを削除した——成功即プッシュ、プレビューなし。pytorch の riscv ブランチは上流 3afdbd3 へリプレイしただけで、さらに同期ボットに依存キャッシュ修正を一筆補わせ、プロセス文書は一切ない。

両者のコスト構造は異なる。llvm ブランチはパッチセットが大きく外部貢献が多く、衝突と履歴ドリフトが主要コストであるため、ルール化は文書を書く価値があり、ワークフローを配置する価値がある；pytorch ブランチはパッチセットが小さく（11 筆）、メンテナ自身が一度リプレイするコストはプロセスを維持するコストより低い。予演を取消した点は観察が必要である：摩擦を下げると同時に「誤った履歴をプッシュする」リスクを貢献者へ前倒しし、--force-with-lease と状態再検査で受け止めるが、実際の効果は次の一、二件の外部 PR を見る必要がある。

6.3 ディストリビューションは月次で量を敷き、スタック級三件セットは月次で審査が滞る

openRuyi 本期 76 コミット、10 件マージ、うち 64 件は KDE フレームワークの一括アップグレードである。ruyi-imager は 1.0.0 から 1.1.0-rc.1 まで七週間かかっており、ペースは正常である。一方、「配布」に属するもう一方の側では、RuyiAI 三件セットのパッケージング PR #1350 が 09-21 にオープンされてから現在に至るまで、依然として spec 規範のレベルで手戻りが発生している。二つのパイプラインの差は人手ではなく成熟度にある。KDE パッケージには参照可能な上流 spec があり、既定のバージョンペースもあるため、再パッケージングは機械的な作業である。三件セットはゼロから書いた spec であり、「なぜ LLVM をパッケージ内に残すのか」を説明しなければならず、さらに「なぜ %check が空なのか」も説明しなければならない。

これが RuyiAI に示唆するのは、ディストリビューションに取り込まれる前提は、パッケージ自体が十分に「常规」であることだ。buddy-mlir は LLVM を同梱し、triton は git 実行ファイルに依存し、tilelang は buddy-mlir ツールチェーンの発見を必要とする——三つの非慣例点はそれぞれパッチと説明を必要とし、各説明はメンテナが時間をかけて判断しなければならない。三件セットを月次リリースペースに乗せたいのであれば、これら三つの非慣例点を一、二の明確なパッケージング規約に収束させること（例えば、ツールチェーンは一律 buddy-mlir が提供する、パッチの積み重ねは一律 git format-patch を使うなど）が、レビュー意見に一件ずつ対応するよりも手間が少ない。
