今日の重点：ruyi 0.54.0 正式リリース、ホスト ABI 互換性チェックがユーザーコマンドに登場（11-10）

日付：2026-11-10　出典：ruyi 0.54.0 リリース、0.53.0 から 0.54.0 への変更差分、PR #507

0.54.0 は 11-10 21:15（北京時間）にリリースされ、正式版でありプレリリースではない。前版 0.53.0 は 09-24 で、間隔は47日；中間には 11-02 の 0.54.0-beta.20261102 のみ。正式版はこのプレリリースに対しバージョン番号のコミット1件が追加されただけで、機能面はプレリリースの全内容そのもの；0.53.0 から計算すると、この版は合計71件のコミット、74ファイル。

主要機能は、ELF ABI 互換性情報の収集とマッチングです。プリコンパイル済みバイナリがターゲットデバイス上で動作するかどうかは、ELF ファイルヘッダに散在する一連の事実に依存します。必要な動的ライブラリ、それらのライブラリに対して要求するシンボルバージョン、そしてアーキテクチャ固有の能力要件です。これまでソフトウェアリポジトリのどこにもこれらの情報は記録されていませんでしたが、ruyi は現在これらの情報をスキャンして保存し、インストール前に比較を行います。

収集面はアーキテクチャ別に分かれています。x86-64 は ISA feature level を記録し、AArch64 は BTI と PAC を記録し、RISC-V は ISA 文字列を記録します。RISC-V の部分が最も手間がかかります。というのも、その拡張はバージョン番号で文字列を組み立てるためであり、今期のコミットにはバージョン付きの単一文字拡張の解析、ホストの浮動小数点 ABI による ld.so.cache エントリのフィルタリング、そしてスタックアラインメント要件の計算が含まれています。ホスト側では別途 x86-64 と AArch64 の検出を実装し、ホストライブラリは要求された soname で解決し、解決できない soname に遭遇した場合は「未確定」と報告するのであって、致命判定は下しません。

ユーザーに見える変化は三つのコマンドに現れます。ruyi list は備考欄にホスト互換性を表示し（非バイナリパッケージではこの項目を非表示）、ruyi install は互換性のないパッケージをインストールする際に警告し、ruyi admin check-abi はトラブルシューティング用に提供されます。データ面はリポジトリ側の ABI sidecar を経由し、distfile 名で解決します。rescan-package-abi とプラグイン成果物には strip-components が新たに追加され、アーカイブに先頭ディレクトリがある場合に対処します。sidecar にはサイズ上限があり、破損した sidecar は「ABI 情報なし」として破棄され、インストール全体を失敗させることはありません。

もう一类是下载链路的修复：#509 让非 2xx 的 HTTP 响应如实报错，并丢弃失败的首次下载、给卡住的传输加上限。这类改动不显眼，但对一个要从镜像站拉几百兆工具链的包管理器来说，比新增功能更影响体验。

設計ドキュメント docs/elf-abi-compat-design.md はバージョンとともにリポジトリに格納され、リリースノートが示すインストール経路は依然として PyPI とサービスがミラーするミラーサイトであり、単一ファイルバイナリは ruyi にリネームしないと使用できません。

今日の重点：triton-riscv が RISC-V ホスト上で AMD GPU バックエンドをデフォルト有効化（11-10）

日付：2026-11-10　情報源：PR #110、README

PR #110 は 11-10 17:51（北京時間）にマージされ、タイトルは「GPU バックエンドをデフォルトで有効化」です。変更点は三つあります。既存の Buddy LLVM SDK を用いて riscv64 の AMD codegen ライブラリをビルド・パッケージングすること。riscv64 上で CPU と GPU ドライバの二択となる際の曖昧さを修正し、ルールは利用可能な GPU を優先すること。そして、ドライバ層で選択を曖昧にしていた判断箇所を修正すること（当該ファイルは正味四行削除）。

検証は実機で行われました。SG2044 に RX 7900 XTX を搭載し、torch と ROCm は openRuyi のソフトウェアリポジトリから取得。さらに GPU デバイスを隠した際に自動的に CPU へフォールバックできるかもテストしました。この基準は「コンパイルが通る」よりもはるかに厳しいものです。つまり、RISC-V ホストが実際にカーネルを AMD カードへ送って実行しており、CPU でフォールバックしていないことを示しています。

README には AMD GPU の使い方の節も同期して追加されました。ROCm が存在する場合、バックエンドは torch.version.hip を通じて自動的に有効化され、書き方は上流のチュートリアルと同一です。wheel には ROCm ランタイムが含まれないため、torch と ROCm は別途インストールする必要があります。CPU へ強制フォールバックするには TRITON_DEFAULT_BACKEND=triton_shared を使用します。変更は合計六ファイルで、README、backend/driver.py、および scripts 配下の build、env、release、setup の四スクリプトに集中しています。

一つ記録しておくべきタイムラグがあります。同日 10:22（北京時間）に公開されたナイトリービルド nightly/2026-11-10-209274f はコミット 209274f 上にビルドされており、このマージより前であるため、このパッケージにはまだ GPU バックエンドが含まれていません。入手するには次のナイトリービルドを待つ必要があります。

スタック全体にとって、これはロードマップ上の変化です。triton-riscv はこれまで「RISC-V CPU のベクトルユニット上で Triton をどのように動かすか」にのみ答えていましたが、今は「RISC-V ホストから異種アクセラレータをどのように駆動するか」にも答える必要があります。主要な AI アクセラレータカードがいずれも RISC-V ホストドライバを備えていない時点で、まず AMD カードをサポートすることが最も現実的な一歩です。ROCm の RISC-V 側の作業はすでに openRuyi リポジトリで維持されています。

1.1 triton-riscv：プラグイン改名 PR が審査中、環境変数の値もそれに伴い変更へ（11-10）

日付：2026-11-10　情報源：PR #109、コミット一覧

#109 が解決しようとしている問題は名実相伴わないことである。name.conf がインストールされるパッケージ名とエントリポイントを決定するため、プラグインは現在 triton.backends.triton_shared と呼ばれているが、報告するターゲットは cpu であり、オプション接頭辞はすでに triton_riscv となっている。修正方法は riscv に統一することであり、その理由は上流の命名慣習に合わせるためである——プラグインはターゲットファミリー（nvidia、amd）で命名し、デバイス名（cuda、hip）は target に残す。

関連する変更は環境変数である：TRITON_DEFAULT_BACKEND の値は triton_shared から riscv に変わり、つまり本日の重点の項目にある「強制的に CPU に戻す」書き方はマージ後に無効になる。ツール名 triton-shared-opt と C++ 側は変わらない。第二のコミットは改名が影響する六十のファイルに ruff を追加し、これらのファイルはこれまで一度も lint されたことがなく、十九の既存違反がある。

PR の状態はオープンで、11-10 18:56（北京時間）にも更新があり、まだマージされていない。同日に更新されたオープン PR には #103（チュートリアル追加）と #104（BOSCAME FPGA の SPM サンプルと AOT 契約フロントエンド）もあり、三つとも「すぐに試せて、再現できる」基礎作業に属する。

2.2 openRuyi：八件のコミット、四件のセキュリティ修正に LLVM スナップショットと Wayland スイッチ（11-10）

日付：2026-11-10　情報源：policycoreutils コミット、lxc コミット、cups コミット、llvm-snapshot コミット

パッケージリポジトリの調査期間内の八件のコミットは、性質により三種類に分かれる。

セキュリティ面四件：policycoreutils を 3.11 にアップグレードし fixfiles の修正をバックポート、lxc、libmtp、cups はそれぞれ上流のセキュリティパッチをバックポート。これら四件はすべて security-fixes マークが付いており、上流 CVE を追跡する定例作業に属するが、ディストリビューションにとっては当日フォロー必須の部分である。

ツールチェーン二件：llvm-snapshot と clang-wrap が同日に 20261109 へアップグレード。この二つのパッケージは RISC-V 上での自举コンパイルチェーンの基盤であり、triton-riscv のビルド時に依存する LLVM アーカイブの供給源でもあり、スナップショットの日次更新は下流が手にするコンパイラが毎週変わっていることを意味する。

残り二件：libssh を 0.12.2 に更新、SDL2 は Wayland バックエンドを有効化（従来は X11 経路のみ）。SDL2 のこの一件は、見た目以上にデスクトップとゲームスタックへの影響が大きい——多くのグラフィックスプログラムが SDL のウィンドウ生成を経由しており、Wayland スイッチが入って初めて、デスクトップ上に真のネイティブ経路が生まれる。

4. Buddy Compiler の動向

4.1 buddy-mlir：YOLOv8 の検出と姿勢推定が K3 行列エンジン上で動作、重みと TCM コピーに二件の修正（11-10）

日付：2026-11-10　情報源：PR #1042

#1042 は Ultralytics YOLOv8 を buddy-cli の rax フォーマットに接続する：yolov8n 検出（八十クラスの COCO）と yolov8n-pose（十七個のキーポイント）、入力はいずれも 320x320。f32 モデルは VIR の lowering を通り、スペックに ime: true と書けば SpacemiT K3 の行列エンジンで走る。

レビュー段階で補われた二件の修正は、モデル本体よりも情報量が多い。一つは重みの検証：マニフェストに params_size があり、ランナーは重みファイルがそれと一致することを要求する。従来は重みファイルが短いとモデルがバッファを読み過ぎていた。同時にランナーは rax パッケージのみを受け付けることを要求する。ライブラリと重みを個別に渡すと、姿勢モデルが検出モデルのパラメータで走ってしまうからだ。もう一つは TCM コピー：IME 重みの TCM コピーは重みアドレスでキャッシュされ、新しい重みが解放済みバッファに読み込まれると古いコピーにヒットしていた。現在は重みをロードするたびにカーネル側の無効化関数を呼ぶ。

スペックには params_size と ime_params_size の両方を残し、これにより ime: false のときも f32 版をビルドできる。この設計は前日の VIR エンドツーエンドの疎通と同じラインにある：同じ一枚のグラフ、二本のバックエンド経路、比較可能な一つのベースライン。

4.2 buddy-mlir：vir.set_vl の領域を一ブロックに絞り、複数ブロック領域でオペレータを静かに落とさない（11-10）

日付：2026-11-10　情報源：PR #1045

vir.set_vl の領域型は元々 AnyRegion で、ソースには「領域制限は未定」というコメントが残っていた。検証器と -lower-vir-to-vector の各 lowering はすべて region.front() しか取らないため、複数のブロックを持つ領域は検証を通過し、残りのブロック内のオペレータは黙って破棄される。再現は明快だ。一つの set_vl 内の load と store が二番目のブロック（cf.br ^bb1 の後）に落ちると、lowering の結果は空の affine.for が二つになる。空の領域は検証を通過し、その後 pass 内で「アンカー型が見つからない」として失敗する。

修正は型を SizedRegion<1> に変更し、コメントを削除し、検証器が自ら空領域を防ぐのをやめ（ODS が先にブロック数を検証）、「ブロックに引数がない」という条件だけを残す。テストには二ブロックとゼロブロックの二種類の不正入力を追加した。この変更は新機能を生まないが、「コンパイルは通るが計算が誤る」経路の一種をコンパイル時エラーに変えるもので、その価値は診断可能性にある。

4.3 buddy-mlir：動的ベクトル型とスケーリングファクターの印刷・解析・検証を補完（11-10）

日付：2026-11-10　情報源：PR #1046

スケーリングファクターは以前、属性形式 #vir.sf<m2> で印刷されていたが、型構文とサンプルが示すのは m2 だった。解析側には「エラーメッセージ補完待ち」のコメントが残り、挙動には複数の不一致があった。#vir.sf<x2> と mq はクラッシュし（解析が空の属性を返してもエラーを出さず、型解析器がそれを有効値とみなす）、m3、m0、f128 は受け入れられ、!vir.vec<0x?xf32> も受け入れられ、一方 !vir.vec<?xvector<4xf32>> は拒否され、位置が unknown と報告された。

変更は三つの部分に分かれる。印刷は sf.str() に切り替え、#vir.sf<m2> は引き続き読み込めるようにした。属性側には genVerifyDecl を追加し、比率が m または f であること、値が 2 から 64 で 2 の冪であることを要求する（Python バインディングに既存のチェックと一致）。型側は動的次元より前の各次元が静的かつ正であることを要求する。二番目のコミットではエラー位置を実際の位置に修正した。まだ形成途上の中間方言にとって、パーサーの厳格さはフロントエンドが確実にエラーを報告できるかどうかを直接左右する。

4.4 buddy-mlir：reassoc リダクションはまず lane ごとにブロックを結合し、VLEN 128 ホスト上のビット不一致を修正（11-10）

日付：2026-11-10　情報源：PR #1047

VLEN 128 の RISC-V ホスト（SG2044 の C920 コア）上で、test_k3_w4_kernels.py の qk_norm にビット不一致が現れた。原因は、K3 デコードアテンションの q、k 正規化が一つのヘッドの六十四個の f32 平方和を shuffle なしの set_vl 領域に置き、lowering がホスト定尺（#1037）に従うため、VLEN 128 では二つの vector<32xf32>（LMUL 8）になることにある。一方 vir.reduce は各ブロックを順に前のブロックの結果へ併合するため、ベクトルカーネル内の単一の vector<64xf32> リダクションとは順序が異なる——LLVM は広いベクトルを半分に分割し、lane ごとに加算してからもう一度リダクションする。CI の riscv64 は VLEN 256 上で動作し、そこではブロックが一つだけなので、ずっと通過していた。

修正は、複数ブロックにまたがる reassoc リダクションを LLVM の方式で結合することだ。n ブロックをまず 2 の冪 h まで幅を補い、第 p ブロックと第 p+h/2 ブロックを加算し、一ブロックだけになるまで続けてからもう一度リダクションする。これは同じテーマの四番目の修正であり（これまでにロード時の VLEN 検証、ホスト定尺、FMA 末尾の丸めがあった）、指し示す受け入れ基準は一貫している。実装を変えるのはよいが、数値を変えてはならない。

4.5 buddy-mlir：五十個の Python ファイルを改名、A100 llc オプションを統一入口に集約（11-10）

日付：2026-11-10　情報源：PR #1043、PR #1044

#1043 は五十個のハイフン付き Python ファイル名をアンダースコアに変更した。同じディレクトリに既にアンダースコア命名のファイルがあり、ハイフン付きのものは import できず、関数もテストや再利用ができない。変更は models、examples、.agents/skills、tests の四箇所に及び、CMake、shell スクリプト、README、ドキュメント内の参照も同期して修正した。MLIR アップストリームの二百四十一個の Python ファイルのうち二百三十七個はアンダースコア命名であり、今回の変更はアップストリーム規範への整合である。

#1044 は YOLOv8 の IME パスを修正する：lower_to_obj.sh は独自に A100 用の llc オプション一式（+zvl1024b と -riscv-v-vector-bits-max=1024 を含む）を組み立てていたが、構築された VLEN のチェックには後者しか使っていなかった。#1032 以降、VLEN は BUDDY_RISCV_VLEN で統一して指定され、他のモデルはすべて a100_llc_args から取得し、llc が実際に読み取った正確な 1024 を検証している。旧スクリプトは +zvl256b や VLEN なしのビルドに騙されてしまう：VIR は任意の VLEN で lowering されるが、object は 1024 でコンパイルされる。現在のスクリプトは統一入口が与えるオプションを直接追加し、VLEN 1024 を満たさなければ停止し、さらにスタブツールで実行するテストを新たに追加した。

6. トレンド観察

6.1 0.54 のリリース間隔が倍増、その代償は 3 種類のアーキテクチャにまたがる ABI 収集

0.52 から 0.53 までは 22 日、0.53 から 0.54 までは 47 日だった。倍増したこの期間、コミットはほぼ一本の線に集中している：ELF ABI 互換性を「記録なし」から「収集でき、保存でき、比較でき、インストール前に警告できる」状態へと作り上げることだ。この道は x86-64 の ISA level、AArch64 の BTI と PAC、RISC-V のバージョン化拡張文字列を同時に扱う必要があり、3 種類のアーキテクチャの知識であって、3 回の類似したコーディングではない。

注目すべきは、それがまずパッケージマネージャの中に落ちたことであり、あるディストリビューションの品質プロセスの中ではないということだ。パッケージマネージャは「ユーザーがインストールをクリックする」まさにその瞬間に判断できる唯一の場所であり、互換性の判断をここに置くことは、ディストリビューションレベルの検証コストを一度のローカル比較に前倒しすることに等しい。

6.2 「インストールできるかどうか」が初めて計算可能な事実になる

RISC-V の断片化は命令セットそのものになく、ベースラインにある。同じ riscv64 バイナリが、RVA20 のボードでは動かない可能性もあれば、ベクトルユニットのないコアでは直接不正命令になる可能性もある。これまではこうした問題をドキュメントに頼り、フォーラムの返信に頼り、試行に頼ってきた。0.54 は各パッケージの動的ライブラリ要件、シンボルバージョン、アーキテクチャ能力要件を sidecar として書き出し、ホスト側で対応する事実を探り出してから照合する。これにより「このパッケージはインストールできない」が一つの経験則から再現可能な結論へと変わる。

副作用はデータのメンテナンスである。sidecar はパッケージとともに更新する必要があり、strip-components のようなアーカイブの差異は個別に処理し、壊れた sidecar には明確なフォールバック戦略が要る。0.54 はこれらの端々までコードに書き込んでおり、設計時にメンテナンスコストをすでに計算済みであったことを示している。

6.3 RISC-V ホストと AMD カードがメインラインに参入

triton-riscv は「RISC-V ベクトルユニット上で Triton を実行する」から「RISC-V ホストから AMD GPU を駆動する」へと拡張され、デフォルトパスは直接 GPU を選ぶ。この組み合わせはこれまでベンダーのデモにしか現れなかったが、今やデフォルトブランチに入り、実機検証（SG2044 と RX 7900 XTX の組み合わせ）もある。

現実的な意味はこうだ。主流の AI アクセラレータカードのホストドライバエコシステムはほとんどが x86 と Arm 向けに用意されており、RISC-V マシンは長らく CPU でしか推論を実行できなかった。RISC-V ホストがカーネルをコンシューマ向け AMD カードに送り込めるようにすることは、このエコシステムの空白を回避する最も労力の少ない道である——ROCm は RISC-V 上ですでにメンテナンスされており、欠けているのはコンパイラバックエンドという一环だけだ。

6.4 VIR の修正対象が「計算ミス」から「サイレントエラー」へ移行

今調査期間の buddy-mlir の6件のうち、少なくとも3件は「エラーを報告しないが結果が正しくない」ものを対象としている。複数ブロックの set_vl 領域でのオペレータのサイレント消失、スケーリングファクタ解析のクラッシュまたは不正値の見逃し、ブロック間リダクション順序による数値の変化。最初の2種類は以前、コンパイラが静かに誤った結果を生成していたが、今はコンパイル時エラーになる。3種類目はバイト単位の比較によってのみ捕捉できる。

こうした問題に共通するのは、修正コストが低く、発見コストが高いことだ。これらがこの段階でまとめて一掃できるということは、VIR がすでに実機を動かし、ベースラインと比較できるテスト面を持っていることを示している——K3 と SG2044 での対照がなければ、4.4 のような VLEN 128 と 256 の差異は決して顕在化しない。
