今日の重点：Buddy Compiler 0.1.3が正式版リリース、16件のコミットのうち10件がRVVスケーラブルベクトル化、リリースノートにはサーバー側ABIのみ記載（10-31）

日付：2026-10-31　情報源：BUDDY MLIR 0.1.3、v0.1.2 と v0.1.3 のコミット差分、PR #999 rvv-vlen、PR #1003 scalable vector 幅選択

11-01 07:01（北京時間）、buddy-mlir は正式版 0.1.3 をリリースした。前回の正式版は 10-25 の 0.1.2 であり、その間には 5 つのナイトリービルドが挟まっている。リリースノートで展開されている項目は 1 つだけである。buddy-server の新しい ABI（#1015）、すなわちモダリティごとに別々に書かれていたモデルプラグインハンドルを統一インターフェースに収束させ、加えて統一されたロード、状態照会、呼び出し、ストリーミング、キャンセルの経路を備えたものである。

しかし v0.1.2 と v0.1.3 のコミット差分を取得して見ると、このバージョンには実際に 16 件のコミット、136 ファイルが含まれており、そのうち 10 件は [midend][VIR] 配下の RISC-V ベクトル化に関する一連の作業である：

  • #999 で (rvv-vlen) を導入し、可変長ベクトル長をベクトル化ターゲット属性とする；
  • #1000 でネストループ内のアクティブベクトル数を集計し、ベクトル幅選択の入力とする；
  • #1002 で可変長 strip-mining ループを vscale ステップで進めるようにする；
  • #1003 で RVV 向けに可変長ベクトル幅を選択する；
  • #1004 で結果を持つ set_vl を可変長ベクトルに降格する；
  • #1005 で set_vl 内の多次元動的ベクトルが結果を持つケースを処理する；
  • #1006 で動的ベクトルの行レベル vir.shuffle を新規追加する；
  • #1007 で vir.load / vir.store のインデックス規約を統一する；
  • #1008 でインデックスベクトルの幅を自動導出する；
  • #996 で vir.from_vector を新規追加し、再結合を削減する。

さらに 2 件が VIR ラインに属するが [midend] プレフィックスの下にはない。decode attention の VIR 方言実装（[frontend][tools]）と VIR の Python バインディング（#1009）である。つまり 16 件のうち 12 件がベクトル方言の層に手を入れており、しかもリリースノートには RISC-V や RVV について一言も触れられていない。

この落差は記録に値する。なぜなら「このスタックの RISC-V 進展はどこにあるのか」という問いへの答えを変えるからである。これまでの数期の判断はこうだった：buddy-mlir の RISC-V 作業は主にナイトリービルドで行われ、正式版は ABI リファクタリングのような汎用作業に占拠されており、下流が RVV の変更を入手するにはナイトリータグにアンカーするしかない。0.1.3 はこの判断が半分しか正しくないことを証明した——正式版は確かに RVV の一連を取り込んだが、リリースノートがそれに追随して更新されていない。リリースページを見る人は 0.1.3 が単なるサーバーサイドのリファクタリングだと思うだろうが、実際に手に入るのは可変長ベクトル化能力が著しく前進したバージョンである。

下流への直接的な意味はこうである：triton-riscv は 10-31 13:15 に依存アンカーを nightly/v0.1.3.dev20261030 に引き上げた（PR #91）。このナイトリービルドの日付は 0.1.3 正式版のパッケージ生成時刻より早いが、両者の内容は同源であり（0.1.3 は 10-29 のメインブランチ先頭から切り出された）、したがって RVV の 10 件はすでに下流で有効になっている。本当に追随できていないのは「アンカーが依然としてナイトリータグと書かれている」という点である——現行の renovate のリズムでは、release/v0.1.3 に切り替えるにはもう一巡待つ必要がある。

抑制すべきはカバレッジである。この 10 件は VIR 方言の可変長ベクトル化、すなわち set_vl から scalable vector への降格経路に集中しており、エンドツーエンドのモデル性能データではない。リリースノートにもベンチマークは一切示されていない。ベクトル化能力の前進は検証可能だが、どれだけ速く動くかについては今期は答えが出ていない。

日付：2026-11-01　情報源：pytorch riscv ブランチ、PR #51 riscv64 ローカルイメージ、PR #44 bytes_to_scalar 修正、オープン PR 一覧

10-29 の回と比べると、違いは形式のみだ。前回は「7日間の静寂の後のリプレイ + 同期ボットによる依存キャッシュ修正の追加」であったのに対し、今回は「3日後に再度リプレイ、内容は不変」。ブランチ上のパッチセットも変化しておらず、依然として Add riscv64 image locally (#51)、Fix bytes_to_scalar for float/complex on RISC-V (#44)、Scope linear cross entropy ULP tolerance to RISC-V (#42)、inductor opinfo blocklist (#50) およびそれ以前の CI とテスト許容差の変更である。

この「ベースラインを動かさず、コミット時刻だけを変更する」リプレイには通常2つの原因がある。1つは同一ベースラインへの異なるパッチ適用順でのリプレイで、コンフリクトマーカーの除去や履歴の整理に用いられる。もう1つは自動化タスクによる周期的な無条件リプレイである。いずれにせよ、今回の内容に対する増分はゼロであり、記録に値するのはリズムだけ——2週間で2回のブランチ全体リプレイがあり、いずれも新たな上流同期を伴っていない。

引き続き留意すべきはあのズレである。配布側の python-torch-ruyiai（openRuyi #1352）はブランチ成果物に基づいてビルドされ、ブランチ先頭はリプレイのたびに SHA が変わるため、パッケージ内で固定されたソースの落とし所を再調整する必要がある。今回はその調整動作が見られなかった。

ブランチ内で本スタックに最も関連するのは依然として A100 の2件、[RISCV] Lower IME intrinsics to SpacemiT A100 dot instructions (#30) と [RISCV] Add A100 HP/SP and pack/unpack lowering with calibrated scheduling (#31) である。前者は IME 組み込み関数を A100 のドット積命令に降下させ、後者は HP/SP の2つの精度形態の pack/unpack 降下を補い、校正済みのスケジューリングモデルを伴う。さらに下の層には [AME] Update BOSC AME instructions (#29) と [RISCV] Update xtame design (#27) があり、「AME 設計ドキュメント → 命令定義 → 組み込み関数 → 降下とスケジューリング」という完全なチェーンを構成している。このチェーンは行列拡張に資するもので、RuyiAI の「RVV から Matrix へ」という物語のコンパイラ側における着地点である。

次回確認が必要な不整合が1つある。ブランチ上の直近の [SyncBots] Integrate LLVM at b3b5e33 の作者時刻は 09-29 で止まっているが、現在の先頭コミットと前回の先頭コミットをコミット比較すると、返される差分集合には 10-30 の上流コミット（例えば [clang][AST] Don't give NestedNameSpecifier pointer identity in DynTypedNode (#233153)、[libc] Add truncation casts to avoid warnings in file_test.cpp (#237262)）が含まれる。両者を並べると解釈は1つしかない。今回のリプレイは履歴を書き換えると同時に上流ベースラインを前進させたが、同期ボットの記録にはそれに伴う1件が追加されていない。同期記録と実際のベースラインが乖離すると、「このブランチはどの上流に基づくか」といった判断は比較インターフェースから逆算するしかなくなる。今後、ブランチ上に明示的なベースライン説明を追加することを推奨する。

2. RuyiSDK ツールチェーンとディストリビューション

2.1 openRuyi：六件のコミットはすべて 10-30 に集中、LLVM 23 と ollama のセキュリティ更新がマージ（10-30）

日付：2026-10-30　情報源：PR #1424 LLVM 23、PR #1514 ollama セキュリティ更新、PR #1545 clang-wrap、メインリポジトリのコミット一覧

6. トレンド観察

6.1 正式版の説明とコード差分の乖離、RISC-Vの進展がコミット履歴に隠れている

0.1.3の這件事の方法論的意義はそれ自体よりも大きい。プロジェクトの「対外説明」と「実際に組み込まれたもの」が長期間一致しない場合、外部からの判断はコミット履歴から逆推測するしかない。今期の具体的な現れは、リリースノートにはサーバー側ABIリファクタリングしか書かれておらず、16筆のコミットのうち12筆がVIRベクトル層を変更していることである。

この乖離には慣性のコストがある。下流にとっては「アップグレードすべきか」を判断するためにリリースノート、コミット差分、依存アンカーの3箇所を同時に見る必要がある。上流にとっては、本当に見てほしい作業が本来出るべきページに出ていない。直近3ヶ月で最も体系的なベクトル化の進展は、ブログ、ドキュメント、リリースノートの3箇所のいずれにも対応する記述がない。「RVVからMatrixへ」を語るスタックが、ベクトル化の進展をコミット履歴の10行のタイトルとして書いてしまうのは無駄である。

より実際的なリスクはレビュー側にある。バージョン説明が一部の変更しかカバーしていなければ、レビュー者の注意力もその部分に集中し、もう一方の変更は「すでに正式版に組み込まれた」後には誰も振り返らなくなる。

6.2 triton-riscvは「1筆修正して1筆マージ」から「バッチ申請」へ転換、検収側は依然不在

10-29の3筆は「80分以内に連続マージ」、今期の5筆は「2日以内に連続オープン、未マージ」である。前者はメンテナが明確な欠陥修正に対して迅速なチャネルを持っていることを示し、後者は新たな一群の変更がまだその段階に達していないことを示す。2つのリズムの違いは開発強度になく、レビュー帯域にある。

この5筆に10-29の3筆を加えると、3週間で同類の修正が8筆累積し、すべてデグレード経路の情報欠落を指している。この数量自体がシグナルである。この経路には体系的な等価性チェックが確立されておらず、オペレータごとに突き当て、突き当てるたびに補うしかないことを示している。そして下流にとって最も価値のあること——FlagGemsの604個のオペレータのエクスポートを毎晩1回実行する常駐リグレッションにすること——は依然として行われていない。PR #56は09-16の停滞から回復したものの（10-30 20:50に1回プッシュがあり、規模は156の新規ファイルに拡大、エクスポート項目は468から604へ）、依然としてオープン状態である。

検収がPRの中にありパイプラインの中にない限り、「この一群のオペレータがriscv64で動作するか」という問題は繰り返し先送りされる。

6.3 ディストリビューション側の月次コミットメントが連続不履行、スタックレベルパッケージングは依然spec層で手戻り

10月の最後の3日間で、「配布」に直接関連する2つのラインが同時にウィンドウを逃した。ruyi 0.54.0の「10月底」の表現は不履行となり、openRuyiの2026.10バージョンは11-02時点で未リリースである。両ラインともコード側は停止していない——openRuyiは10-30にも6筆のコミットがあり、ruyiにはドキュメントのマージが1筆ある——したがってボトルネックはリリースプロセス自体にあり、開発にはない。

同時に、スタックレベルの三点セット#1350はすでに第6週を越え、依然としてspec規範レベルで手戻りしている。この3件を合わせると、同じ構造的問題を指す。このエコシステムの「ものを作る」と「ものを出す」は2つの能力であり、前者は複数のリポジトリで同時に推進されているが、後者は直近2ヶ月で一度も期日通りに完了していない。

RuyiAIにとって、短期的に最も実際的な提案はリリースを急かすことではなく、2.3の3つの非定型点（buddy-mlirがLLVMを自前で持つ、tritonがgitに依存、tilelangがツールチェーン検出を必要とする）をパッケージング規約として書き下し、#1350のレビューが毎週同じ一群の問題を再討論しなくて済むようにすることである——往復コストを下げてこそ、月次リリースリズムへの移行が語れる。
